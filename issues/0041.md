## Description

Create, edit, list, and cancel campaigns, with the state machine that prevents a half-configured campaign from ever sending.

## Root cause

Not a bug — Phase 5's founding CRUD surface. `#0040` created the schema;
nothing in the tree read or wrote `email_campaigns`/`campaign_interests` yet,
so `#0044` (audience) and `#0045` (worker) had no admin-facing state machine
to build against.

## Fix

Two new files own this surface, following the package boundaries CLAUDE.md
§1 requires (narrow store interfaces, SQL in the owning package):

- `internal/mailing/campaigns.go` — `CampaignStore`: `List`, `GetByID`,
  `Create`, `Update`, `Send`, `Cancel`. `Create`/`Update` write
  `email_campaigns` and replace the full `campaign_interests` set
  (delete-then-insert, mirroring `subscribers.Store.SetInterests`) inside one
  transaction. No `…Tx` variant is exposed for any of them — nothing outside
  this package needs to compose a campaign write with another table's write
  in the same transaction, unlike `#0033`/`#0038`'s `AddTx`/`WriteTx` cases.
- `internal/handlers/admin_campaigns.go` — `AdminCampaignsHandler` over a
  narrow `campaignStore` interface, wired into `adminRoutes` (nil-guarded for
  `STORAGE=json`, matching `adminInterestsH`/`adminSuppressionsH`'s existing
  precedent) at six routes: `GET/POST /admin/campaigns`,
  `GET/PATCH /admin/campaigns/{id}`, `POST .../send`, `POST .../cancel`.

**The state machine.** `PATCH` is content-only (name, subject, preheader,
body_md, audience_mode, interest_ids) and never changes status; it 409s
(`ErrCampaignNotEditable`) unless the campaign is currently `draft` or
`scheduled`, re-checked inside `Update`'s own `FOR UPDATE`-locked read so a
concurrent transition can't race a stale decision. Two dedicated routes own
every operator-triggered status move:

- `POST /admin/campaigns/{id}/send` — `draft`|`failed` → `scheduled`.
  `failed` is a legal source (a retry path — see `#0045`'s note below) so a
  campaign the worker gave up on can be re-queued; this package never writes
  `sending` itself, the worker's own claim does that. Enforced twice
  (defence in depth): a Go pre-check against the freshly-read row, and the
  `UPDATE … WHERE status IN ('draft','failed')` itself, so even a concurrent
  transition between the two loses the race safely (409, not corruption —
  verified by mutation-check, see `## Verification`).
- `POST /admin/campaigns/{id}/cancel` — `scheduled`|`sending` → `canceled`.
  Never recalls an already-sent message (this issue's own Notes; restated in
  the handler's doc comment).

Every illegal transition is `mailing.ErrIllegalStatusTransition` → HTTP 409
with a clear message, never a silent no-op — table-driven tests cover every
non-legal source status for both `Send` and `Cancel` (`## Verification`).

**The empty-interest write-time guard** (`#0044`'s carried-in criterion):
`normalizeAudience` rejects `any_of`/`all_of` with zero interest ids at
*every* write — `Create`, `Update`, and defensively again inside `Send`
against the stored row (so a row that somehow reached an invalid state some
other way is still refused at send). Returns a typed
`mailing.ErrCampaignInterestsRequired`, mapped to HTTP 400 by the handler.
`#0044` hasn't landed yet, so this rule is enforced independently here, not
shared — `#0044`'s own materialize-time check is a second, deliberate layer,
not a call into this one.

**No `DELETE` route** — `#0040`'s carried-in review note. Only `cancel`
exists; nothing in this issue touches the FK cascade that would destroy
`#0049`'s send-history record.

**Audit** — `email_campaign.created` / `.updated` / `.scheduled` / `.canceled`
(new constants + `TargetEmailCampaign`, `internal/audit/actions.go`).
`.scheduled` fires on both the fresh-send and the retry-from-`failed` path,
distinguished by a `retry` metadata flag.

### Two concurrent planning passes folded in mid-implementation

`#0045`'s plan (`225ba09`) and `#0047`'s plan (`b67af26`) both landed while
this issue was being implemented and each named requirements for `#0041`.
Both were verified against the actual commit (not taken on faith) before
folding in — see the acknowledgement messages sent to the orchestrator at the
time.

**From `#0045`'s plan:**

1. **Advisory `Preflight` seam.** `#0045`'s plan requires the send-transition
   handler to call `mailing.Preflight` and 409 on failure. `mailing.Preflight`
   does not exist yet (it's `#0045`'s own file,
   `internal/mailing/preflight.go`) — rather than block on it or write a
   throwaway version of a type `#0045`'s plan already specifies in exact
   detail, `Send` depends on a narrow, **locally-typed**
   `campaignPreflightChecker` interface (`Check(ctx, campaignID) ([]campaignPreflightFailure, error)`)
   in `internal/handlers/admin_campaigns.go`. `NewAdminCampaignsHandler`'s
   `preflight` parameter is `nil` today (wired that way in
   `cmd/opencircuit/main.go`); `Send` simply skips the advisory check when
   nil and proceeds to the transition. **This is not a compliance gap** —
   CLAUDE.md §9 and `#0045`'s plan are explicit that the worker's own copy of
   the gate, evaluated immediately before a campaign leaves `scheduled`, is
   the sole authoritative enforcement point. **What `#0045` must do:** add a
   small adapter over its own `SendStore.GatherPreflight` + `Preflight` that
   satisfies `campaignPreflightChecker`, and pass it as the `preflight`
   argument at the `main.go` call site.
2. **`test_sent_at` clearing on content edit.** Migration `000017` has no
   `test_sent_at` column (confirmed: not in the `CREATE TABLE` this issue
   read) — it arrives in `#0045`'s own migration `000018`. Not added here,
   per the brief. `internal/mailing/campaigns.go`'s `Update` doc comment
   flags exactly where the clearing logic (`SET test_sent_at = CASE WHEN
   subject IS DISTINCT FROM $2 OR body_md IS DISTINCT FROM $5 THEN NULL ELSE
   test_sent_at END`, or equivalent) must be added to the `UPDATE` statement
   once `000018` lands.
3. **`failed → scheduled` retry transition.** Implemented as described above
   — `Send` accepts `failed` as a source status alongside `draft`.

**From `#0047`'s plan:**

4. **Typed send confirmation.** `sendCampaignRequest.ConfirmCount` (JSON
   `confirm_count`) is now **required** — a missing or negative value is a
   400, and the campaign never transitions. `#0041` lands before `#0044` (the
   real audience count), so there is nothing yet to compare it against; a
   `TODO(#0044)` at the exact call site in `Send` marks where the real
   comparison (409 on mismatch) must be wired in.
5. **Two distinguishable 409 shapes.** Already true by construction and now
   asserted by a test: a failed preflight check answers
   `{"unmet":[{code,message}]}`; every other 409 from `Send`/`Cancel`/`Patch`
   (illegal transition, bad audience state, a future confirm_count mismatch)
   goes through `writeError`'s `{"error":"..."}` envelope. Never conflated.
6. **List/detail response fields.** `campaignView` already carried `status`,
   `scheduled_at`, `started_at` (needed unmodified). `test_sent_at` is
   omitted — same "column doesn't exist yet" reason as item 2.
7. **Unschedule transition clearing `scheduled_at`.** Moot: this
   implementation adds **no** `scheduled → draft` transition at all (neither
   PATCH nor any dedicated route), so `#0047`'s
   `wasDemotedAfterScheduling` detection is unaffected by anything shipped
   here.
8. **Surface `test_sent_at` clearing in the response.** Deferred with item 2
   — nothing clears it today since the column doesn't exist.

### Deviations from the plan brief

- Interpreted PRD §8's `POST /admin/campaigns/{id}/send` ("requires typed
  confirmation of the count") as this issue's to build (the state-machine
  entry point into the send pipeline), not `#0045`'s — `#0045`'s own plan
  confirms this reading explicitly ("`#0041` lands before this issue, so the
  send-transition handler already exists when this is implemented").
- `PATCH` deliberately carries no `status` field at all (routing every status
  move through `Send`/`Cancel` instead) — simpler to reason about and test
  exhaustively than overloading one endpoint with both content edits and
  transitions.

## Acceptance criteria

- [x] `GET/POST/PATCH /admin/campaigns[/{id}]`, admin-gated
- [x] Campaign targeting stored via `campaign_interests` with the four audience modes
- [x] A campaign can only be edited while `draft` or `scheduled`

## Carried in from `#0044`'s plan (2026-08-21)

- [x] **Reject an empty interest set at write time** for the `any_of` and
      `all_of` audience modes. `all_of` over an empty array evaluates `0 = 0`
      for every subscriber and silently degrades to "the entire list" — so a
      campaign saved with a mode selected but no interests ticked would mail
      everyone. `#0044` re-validates at materialization regardless, but catching
      it here tells the operator at compose time rather than at send time.

## Carried in from `#0040`'s review (2026-08-21)

- [x] **Do not add a `DELETE /admin/campaigns/{id}` route without deciding what
      happens to the send history.** `email_sends.campaign_id` and
      `campaign_interests.campaign_id` are both `ON DELETE CASCADE` (PRD §6.2
      specifies this, and `#0040` shipped it), so deleting a campaign row
      silently destroys every `email_sends` row for it — the per-recipient
      audit record `#0049`'s stats view reads, and the only answer to "who did
      campaign N go to". This issue's acceptance criteria specify `cancel`, not
      delete, so nothing reaches that path today; the constraint is recorded
      here because this issue owns the CRUD surface where such a route would be
      added. If one is ever wanted, gate it on the campaign never having left
      `draft`/`scheduled` (i.e. having no `email_sends` rows) rather than
      loosening the FK — the cascade is correct for a draft that was never
      sent, and wrong for one that was.

## Notes

PRD §8. Cancelling a `sending` campaign stops the worker from claiming further queued rows; it cannot unsend. Make that explicit in the UI copy (#0047) — an operator hitting cancel mid-send needs to know what it does and does not do.

## Review notes (2026-08-21, non-blocking)

Recorded for whoever touches this surface next; none of these blocked the
resolution.

- **`Cancel` has one enforcement layer, not two.** `Send` has a Go pre-check
  *and* a SQL `WHERE`; `Cancel` has only the SQL `WHERE status IN ($3,$4)`
  plus a `GetByID` afterwards to tell 404 from 409. That is correct — the SQL
  predicate is atomic and authoritative, and mutation-testing confirmed it
  fires — but the asymmetry is deliberate and worth knowing before someone
  "tidies" it. `Update` is likewise a single Go check, made race-free by the
  `FOR UPDATE` row lock it holds for the rest of its transaction rather than
  by a second predicate.
- **`Cancel`'s illegal-source coverage is not exhaustive.** `Send` is
  table-driven over all four illegal sources; `Cancel` tests only `draft` and
  `sent`, leaving `canceled` and `failed` untested. Behavior is correct by the
  SQL predicate, but the table-driven shape `Send` uses would be better.
- **`TestAdminCampaigns_Cancel_NotFound` targets the literal id `99999999`**
  on a mutating route. The risk is negligible (`BIGSERIAL` from 1, truncated
  at entry) but §8b's "never target a literal id" is worded absolutely; a
  seeded-then-deleted row would satisfy it exactly.
- **The `TODO(#0044)` sits above `Send`'s `GetByID` call.** Computing the real
  audience count needs the campaign row, so the comparison will have to move
  below that load (or the load move up). Noted on `#0044`.
- **`scheduled_at`/`started_at`/`completed_at` are `omitempty`**, so a NULL
  comes back as an *absent key*, not `null`. This matches `subscriberView`'s
  existing precedent and is not a defect here, but `#0047`'s demotion
  predicate compares against `null` strictly and would be wrong both ways.
  Amended onto `#0047`.
