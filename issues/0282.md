## Description

`#0254` added `TestMailKindsCoversEveryOutboxKind`, an AST guard that parses
`internal/outbox`'s `Kind` constants and fails when one is claimed by neither
`mailKinds` nor the documented `KindSubscribeIntake` exception. It exists
because a `Kind` omitted from that hand-maintained list is claimed by **nobody**
and stalls in `'queued'` forever.

The guard matches `vs.Type.(*ast.Ident)` — it only sees constants carrying an
explicit type annotation. So this is invisible to it:

```go
const (
	KindConfirmation Kind = "confirmation"
	KindReviewProbe       = "review_probe"   // untyped — guard cannot see it
)
```

`#0254`'s reviewer reproduced this: the guard passed with an uncovered kind
present. The constant is untyped but, in the same `const` block and used
wherever a `Kind` is wanted, it is fully usable as one.

**This is hardening, not a live defect.** None of the ten existing `Kind`
constants uses that declaration style, and the guard was otherwise
mutation-proved three ways — it catches an added-and-unclaimed kind, it fails
closed when the parse finds zero constants, and its oracle lives in a different
package from its subject so an edit to the subject cannot satisfy it.

## Acceptance criteria

1. The guard sees a `Kind` constant regardless of declaration style — an
   explicit annotation, an untyped member inheriting a block's type via `iota`
   or repetition, or a conversion. Enumerate the styles Go permits here and say
   which are covered.
2. Reproduce the gap first, as a failing test against the current guard, then
   close it. Do not fix it and assert the fix.
3. The guard still fails closed on a broken parse (zero constants found), and
   still names the specific uncovered kind.
4. Consider using `go/types` rather than a bare `go/ast` shape match — the
   question "is this constant a `Kind`" is a type question, and the AST match is
   an approximation of it. If `go/types` is rejected as too heavy, record why.
5. `ISSUE=NNNN scripts/check.sh go ./internal/...` passes with no skips.

## Work log

**2026-08-27, phase-2 implementation.**

Root cause confirmed exactly as described: `TestMailKindsCoversEveryOutboxKind`
matched only `vs.Type.(*ast.Ident)` — a `Kind` constant's explicit type
annotation. Enumerated the declaration styles Go actually permits for a
package-level constant and empirically checked each against `go/types`
(scratch experiment, not checked in) before deciding the approach:

1. **Explicit annotation** — `KindX Kind = "x"`. `go/types` resolves this to
   `Kind`; so did the original AST match.
2. **A conversion** — `KindX = Kind("x")`. `go/types` resolves this to `Kind`;
   the original AST match missed it (`vs.Type` is `nil`).
3. **Untyped, inheriting via Go's own const-repetition rule** — an omitted
   expression list textually substitutes the nearest preceding non-empty
   `ConstSpec`'s type *and* value (Go spec, "Constant declarations"):
   `KindX Kind = "x"` followed by a bare `KindY`. `go/types` resolves this to
   `Kind`; the original AST match missed it.
4. **Untyped, with its own value, no annotation, no conversion** — this
   issue's own example, `KindReviewProbe = "review_probe"`. Checked directly:
   built a fixture identical in shape and ran it through `go/types` — the
   resulting `*types.Const`'s `Type()` is `untyped string`, **not** `Kind`.
   Confirmed against the Go spec's own text ("If the expression values are
   untyped constants, the declared constants remain untyped"). No type-level
   analysis, `go/types` included, can distinguish this from an unrelated
   untyped string constant by type alone — the only available signal is that
   it shares a `const (...)` block with something that resolves to `Kind` by
   1-3.

**Criterion 4 — `go/types` decision: rejected, go/ast used instead.** Not for
`#0261`'s reason (this guard's subject is `internal/outbox`'s real,
already-buildable source, not a synthetic fixture, so an importer would work
fine). Rejected because it buys **no additional coverage**: it resolves
styles 1-3 exactly as precisely as a `go/ast` walk that implements Go's own
repetition rule and detects conversions directly (verified above — both
land on the same answer for every style but 4), and it resolves style 4 no
better than `go/ast` does — style 4 needs the same-block heuristic regardless
of which mechanism finds styles 1-3. Given zero marginal precision,
`go/types`'s real cost (a working importer over `internal/outbox`'s full
import graph, a heavier and more fragile dependency than a self-contained
parse, with its own distinct failure mode) was not worth adding. Implemented
via `go/ast`: `collectKindConstants`/`collectKindConstantsInBlock`
(`internal/mailing/outbox_worker_kinds_guard_test.go`) resolve styles 1-3 as
real typing facts and apply the same-block heuristic for style 4 (a false
positive there just means adding one more name to `mailKinds` or its
exceptions — cheap and safe; a false negative is the silent stall this guard
exists to catch).

## Review notes

**Verdict: resolved.** Every criterion re-verified independently rather than
read off the implementer's report.

**Criterion 2 — gap reproduced, not asserted.** Re-run from scratch in a
throwaway worktree at `HEAD`, collapsing `collectKindConstantsInBlock`'s switch
to the single pre-`#0282` case:

```
=== RUN   TestCollectKindConstants_AllDeclarationStyles
    outbox_kind_detection_test.go:109: collectKindConstants missed
        [KindConversion KindRepeated KindUntypedSibling]; found only [KindAnnotated]
--- FAIL: TestCollectKindConstants_AllDeclarationStyles (0.00s)
```

Byte-for-byte the transcript the work log claims. Styles 2, 3 and 4 were
invisible; style 1 was not.

**The `go/types` claims for styles 1–4 are true.** Checked directly rather than
taken on trust — a standalone `go/types` run over a fixture identical in shape:

| Constant | `go/types` `Type()` |
|---|---|
| `KindAnnotated Kind = "annotated"` | `fixture.Kind` |
| `KindConversion = Kind("conv")` | `fixture.Kind` |
| `KindRepeated` (repetition) | `fixture.Kind` |
| `KindUntypedSibling = "sibling"` | **`untyped string`** |

So style 4 genuinely is unresolvable by typing alone, the same-block heuristic
is genuinely the only available signal, and `go/types` genuinely would not do
better on it. That half of criterion 4's reasoning holds.

**Real-guard mutation, end to end.** With the fix in place, adding
`KindReviewProbe = "review_probe"` (untyped, sharing the `Kind` block) to
`internal/outbox/store.go` in the worktree makes the real guard fail and name
it:

```
outbox.Kind constant(s) claimed by NOBODY — neither mailKinds nor the
KindSubscribeIntake exception: [KindReviewProbe]
```

That is the exact case `#0254`'s reviewer got a green run on. Criterion 3's
specific-kind naming survives.

**Fail-closed survives.** Repointing the parse at a package with no `Kind`
constants trips the `len(declaredKinds) == 0` fatal:
`found zero Kind constants in internal/outbox — the parse likely broke, not a
real empty set`.

**The same-block heuristic's false-positive behaviour, measured.** Adding an
unrelated untyped constant to the `Kind` block —
`defaultKindNote = "kinds are declared above"` — does produce a false positive:

```
outbox.Kind constant(s) claimed by NOBODY … : [defaultKindNote] (a row of this
kind would stall in 'queued' forever with no error; add it to mailKinds, or to
this test's exceptions if it is deliberately not mail)
```

Judged acceptable: it fails loud, in the safe direction, and the message points
at the exception list rather than at the detector, so the obvious "fix" is not
to weaken the guard. Today's `internal/outbox` has no bare constant in the
`Kind` block (`StatusQueued…` and `DefaultMaxRetries` are separate blocks), so
no false positive exists in the tree. One friction point worth knowing: the
exception is a single `const intakeException = "KindSubscribeIntake"` compared
with `==`, not a set — adding a second exception means restructuring it first,
which is a small nudge in the wrong direction.

### Two things the review found that the work log overstates

Neither changes the verdict; both are recorded so they are not rediscovered as
new, and a follow-up is recommended to the orchestrator.

1. **"`go/types` buys zero marginal precision" is not strictly true — an alias
   annotation is a fifth style, and the shipped detector misses it.** Measured:

   ```go
   type KindAlias = Kind
   const KindE KindAlias = "e"      // go/types: fixture.Kind — a real typing fact
   ```

   `go/types` resolves `KindE` to `Kind`; `collectKindConstants` returns
   `detected=false`, because `isIdent(vs.Type, "Kind")` matches the spelling
   rather than the type, and a non-nil `vs.Type` never reaches the bare/style-4
   branch. So the doc comment's "exact for 1-3 and heuristic only where
   `go/types` would be too" is wrong for style 1 under an alias, and this is a
   fail-open in a guard whose whole purpose is closing a fail-open. It is
   contrived — nothing in `internal/outbox` declares such an alias — which is
   why it is a follow-up rather than a bounce, but the claim should not stand
   as "verified empirically" when a 30-second check disproves it. The
   conclusion (reject `go/types`) still holds; the stated reason needs
   narrowing to "negligible", not "zero".

2. **A repetition spec following a bare untyped sibling is missed.** Measured:

   ```go
   const (
       KindA Kind = "a"
       KindB      = "b"   // style 4 → swept in by the heuristic
       KindC              // repetition of KindB → NOT swept in
   )
   ```

   `KindB` is detected, `KindC` is not: style 3 inherits `lastNonEmpty.isKind`,
   and a style-4 candidate carries `isKind == false`, so the heuristic does not
   propagate. `go/types` reports `untyped string` for both, so this is an
   incompleteness in the heuristic rather than something `go/types` would have
   caught — the fix is to propagate `isBare` forward the same way `isKind` is.
