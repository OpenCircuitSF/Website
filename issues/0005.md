## Gotchas

- **Simulating Ctrl-C with `kill` needs the process group, not the top-level PID.** `dev.sh` runs without `set -m` (no job control), so bash, `go run`, and `vite` all share one process group; a real terminal's Ctrl-C delivers SIGINT to that whole group at once. `kill -INT <dev.sh's PID>` alone only signals the bash process — bash's documented behavior is to defer a pending trap until the current foreground command (here, the long-running `npm run dev`) completes, which it never does on its own, so the trap appears to hang. `kill -INT -<pgid>` (negative PID = process group) is the correct simulation and is what the verification above actually used after discovering this. Worth flagging so a future agent testing this script doesn't conclude the cleanup trap is broken when it's actually a signal-target mistake in the test, not the script.
- Running `kill` against processes started in an earlier Bash tool call required `dangerouslyDisableSandbox: true` in this environment — the default sandboxed `kill` silently had no effect (the target processes were visible via `ps` but unaffected by `kill -INT`/`kill -TERM` without it).
- `npm ci` (triggered by `--built` mode when `package-lock.json` is present) took roughly 20s in this environment on a `node_modules/` already populated by an earlier `npm install` in #0003 — worth knowing if a future timing-sensitive script change assumes `--built` starts serving quickly.
