# 0153 — Decide whether workshops need a cover-image upload endpoint

## Description

`#0138` struck its upload criterion with a decision: cover images are **path-or-URL text entry in v1**, and an upload endpoint "deserves its own future issue". This is that issue.

The current state after `#0138`: `cover_image` must be a same-origin path (`/assets/…`), validated in both the browser and the API. So an admin can reference an image only if someone has already put it on the server by some means outside the product — which today means a deploy.

## Acceptance criteria

- [x] Decide whether v1 ships an upload path at all. "No" is a legitimate answer if workshop cover images are set rarely and deploys are frequent — record the reasoning either way — **decided: no. See `## Decision`.**
- [ ] If yes, the design questions to settle before any code: where files are stored (filesystem beside the binary, S3, database), how they are served, size and content-type limits, what happens on duplicate filenames, and whether uploads are pruned when a workshop is deleted
- [ ] If yes: uploads are admin-gated, the stored path is what lands in `cover_image`, and the result passes `#0138`'s same-origin validation without special-casing
- [ ] If no: `#0052`'s cover-image criterion is struck with a note pointing here, rather than left unticked forever

## Decision

**No upload endpoint in v1.** Cover images stay path-or-URL text entry against a
same-origin `/assets/…` path, exactly as `#0138` left them. Recorded by the
orchestrator on 2026-08-24 under the user's standing instruction to resolve
Phase 7 rather than stall on open questions.

The reasoning, so a later reader can weigh whether it still holds:

- **The volume does not justify the surface.** This is one San Francisco group
  running workshops; the home page shows three at a time. An upload endpoint
  brings content-type sniffing, path traversal, size limits, duplicate-name
  collision, and orphan pruning on workshop delete — five things to get right
  and keep right, for a field set a handful of times a month.
- **It would be the first mutable data directory in the deploy model.** The
  binary embeds `web/dist` via `//go:embed` and the only mutable state is
  Postgres. Filesystem uploads would add a directory that must survive deploys,
  be included in the backup scope (`#0062`, `#0229`), and be served as
  untrusted bytes from the same origin as the admin console. That is a real
  architectural change, not an added handler.
- **S3 is not available.** `CLAUDE.md` §10 item 2 records the AWS account as
  not started, and the user deferred all AWS work to deployment. Choosing the
  storage backend now would be choosing it blind.
- **Adding an image is currently a commit, and deploys are frequent.** During
  build-out that is a smaller cost than the endpoint.

**What would reopen this:** Phase 9 (`#0232` — making the platform usable as a
dependency) changes the calculus outright. A downstream consumer cannot commit
an image into *this* repository's `assets/`, so a configured storage location
becomes necessary rather than convenient. Revisit there, with the storage
question answered by whatever Phase 9 decides about deploy-time configuration.

## Notes

Filed from `#0138`'s decision record and its phase-3 review, which noticed the promised follow-up had not actually been filed.

The honest framing: this is a product question about how often workshops get cover images and who sets them, not a technical one. It is Phase 7 because nothing blocks on it and because the answer may reasonably be "not in v1".
