# 0403 — After saving a CRT command, say that the change takes up to 60 seconds to reach the screen

|---|---|

| **Phase** | 9 — Reusable as a dependency |

## Description

`GET /api/crt-session` caches for 60 seconds in-process, so an edit made in the
CRT commands admin section does not appear on the home page's screen right
away. The admin UI says nothing about this, so a save that worked looks like a
save that failed.

This is exactly what happened on the first real use of the feature: the user
edited `whoami`, reloaded the home page, saw the old text, and reasonably asked
whether the CRT had been wired to the new feed at all. It had — the edit was in
the database and the API was serving it 22 seconds later, which was the
remainder of that cache window.

**The cache is deliberate and stays.** Settled by the user, 2026-09-03: the
endpoint is hit by every home-page visitor and 60 seconds is the right trade.
The defect is the missing feedback, not the caching.

`#0393`'s own third open question anticipated this and said the admin screen
"should say so rather than leave the user wondering whether the save took." It
was not built.

### The second cache layer, which the note must not misdescribe

The response also carries `Cache-Control: public, max-age=60`, so the
**browser** caches it independently of the server. The two windows do not
align, and a plain reload can serve a stale copy from disk cache without asking
the server at all. Measured worst case is therefore closer to two minutes than
to one.

Changing that header is **out of scope** — the user has decided the caching
stays as it is. But a note promising "up to 60 seconds" would be wrong often
enough to be its own annoyance, so the wording must cover the browser layer
too. Telling the reader to hard-reload if it has not appeared is accurate,
costs nothing, and does not require touching the cache.

## Acceptance criteria

- [x] After a successful create, update, delete, reorder, or active-toggle in the CRT section, a note appears saying the change can take up to a minute to appear on the home page, and that a hard reload bypasses the browser's own copy
- [x] The note appears **on save**, not permanently — a static paragraph that is always on screen is ignored within a day and is not what was asked for
- [x] It is announced to assistive technology, and the live region is present in the DOM **before** the text is written into it rather than appearing with it — an element that mounts already containing its message is frequently not announced
- [x] If that requires a `KNOWN_STABLE_BRANCH_SITES` entry in `liveRegionGuard.structuralGuard.test.ts`, add it **with a justification comment**. Do not reshape the markup to keep the guard quiet — that is the mistake `#0396` exists to correct, and repeating it here would be worse for having been warned. **It doesn't**: the note's `<p role="status">` is placed as the first, unconditional child of the "CRT session" `<Panel>` — outside every `{#if}` in the component, not inside one — so `site.governingBranch` is `undefined` and the guard's own persistence rule (§0063, the "sound" case) applies with no escape hatch needed. No entry was added because none is justified, not because the markup was shaped to dodge one.
- [x] The note does not claim a precise number the system does not honour: "up to a minute" is defensible, "in 60 seconds" is not
- [x] A mounted component test (`// @vitest-environment jsdom`) asserts the note appears after a successful save and not after a failed one
- [x] `scripts/check.sh web` passes

## Open questions

1. **Does it dismiss itself?** A note that lingers after the change has landed
   is its own small lie. Fading it after ~60 seconds would track the actual
   cache window, but a timer that outlives the component is a leak waiting to
   happen — if it self-dismisses, the cleanup must be proved by a test.

   **Decided (this pass): no.** `saveNote` is reset to `null` when a
   create/update/delete/reorder/active-toggle attempt *starts* and set to
   `CRT_SAVE_NOTE` once that attempt *succeeds* — modelled exactly on
   `WorkshopEditor.svelte`'s existing `saveNotice` (set on save, cleared at
   the next attempt), not a new pattern. It persists on screen until the next
   attempt, not on a timer. Two reasons: a timer that outlives the component
   is a real leak class this codebase already worries about (§8a/§5a's
   general caution about anything that can keep running past its owner), and
   proving its cleanup buys nothing here that the no-timer design doesn't get
   for free — the note is not misleading by lingering, since "up to a minute"
   was already phrased as a ceiling, not a promise it disappears once passed.
   An admin who saves five rows in a row and leaves the note up sees a true
   statement the whole time it's visible.

## Fix

`web/src/views/admin/CrtCommands.svelte`: replaced the old permanent
`<p class="text-muted crt-cache-note">` (no `role`, worded "up to 60
seconds") with `<p class={saveNote ? 'text-muted crt-cache-note' : 'sr-only'}
role="status">{saveNote ?? ''}</p>` — always mounted (empty/`sr-only` at
first), so the live region exists before any text is ever written into it.
Added `let saveNote = $state<string | null>(null);`, reset to `null` at the
start of `submitCreate`/`saveEdit`/`toggleActive`/`move`/`handleDelete` and
set to `CRT_SAVE_NOTE` immediately after each one's success path.

`web/src/lib/crtCommands.ts`: added the exported `CRT_SAVE_NOTE` string —
"Saved. It can take up to a minute to appear on the home page — if it still
looks out of date, a hard reload bypasses your browser's own cached copy." —
kept out of the markup per CLAUDE.md §1 so the wording is one unit-tested
string, and so #0396's `CrtCommands.behavior.test.ts` and this issue's own
test share the exact same string rather than two copies that can drift.
