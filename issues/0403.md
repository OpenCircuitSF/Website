# 0403 — After saving a CRT command, say that the change takes up to 60 seconds to reach the screen

| | |
|---|---|

| **Phase** | 9 — Reusable as a dependency |

## Description

`GET /api/crt-session` caches for 60 seconds in-process, so an edit made in the
CRT commands admin section does not appear on the home page's screen right
away. The admin UI says nothing about this, so a save that worked looks like a
save that failed.

This is exactly what happened on the first real use of the feature: the user
edited `whoami`, reloaded the home page, saw the old text, and reasonably asked
whether the CRT had been wired to the new feed at all. It had — the edit was in
the database and the API was serving it 22 seconds later, which was the
remainder of that cache window.

**The cache is deliberate and stays.** Settled by the user, 2026-09-03: the
endpoint is hit by every home-page visitor and 60 seconds is the right trade.
The defect is the missing feedback, not the caching.

`#0393`'s own third open question anticipated this and said the admin screen
"should say so rather than leave the user wondering whether the save took." It
was not built.

### The second cache layer, which the note must not misdescribe

The response also carries `Cache-Control: public, max-age=60`, so the
**browser** caches it independently of the server. The two windows do not
align, and a plain reload can serve a stale copy from disk cache without asking
the server at all. Measured worst case is therefore closer to two minutes than
to one.

Changing that header is **out of scope** — the user has decided the caching
stays as it is. But a note promising "up to 60 seconds" would be wrong often
enough to be its own annoyance, so the wording must cover the browser layer
too. Telling the reader to hard-reload if it has not appeared is accurate,
costs nothing, and does not require touching the cache.

## Acceptance criteria

- [x] After a successful create, update, delete, reorder, or active-toggle in the CRT section, a note appears saying the change can take up to a minute to appear on the home page, and that a hard reload bypasses the browser's own copy
- [x] The note appears **on save**, not permanently — a static paragraph that is always on screen is ignored within a day and is not what was asked for
- [x] It is announced to assistive technology, and the live region is present in the DOM **before** the text is written into it rather than appearing with it — an element that mounts already containing its message is frequently not announced
- [x] If that requires a `KNOWN_STABLE_BRANCH_SITES` entry in `liveRegionGuard.structuralGuard.test.ts`, add it **with a justification comment**. Do not reshape the markup to keep the guard quiet — that is the mistake `#0396` exists to correct, and repeating it here would be worse for having been warned. **It doesn't**: the note's `<p role="status">` is placed as the first, unconditional child of the "CRT session" `<Panel>` — outside every `{#if}` in the component, not inside one — so `site.governingBranch` is `undefined` and the guard's own persistence rule (§0063, the "sound" case) applies with no escape hatch needed. No entry was added because none is justified, not because the markup was shaped to dodge one.
- [x] The note does not claim a precise number the system does not honour: "up to a minute" is defensible, "in 60 seconds" is not
- [ ] A mounted component test (`// @vitest-environment jsdom`) asserts the note appears after a successful save and not after a failed one — **not met for one of the two failure kinds**: the network-rejection path is covered, the client-side validation-rejection path is not, and the code lets a stale note survive it (see `## Review notes`)
- [x] `scripts/check.sh web` passes

## Open questions

1. **Does it dismiss itself?** A note that lingers after the change has landed
   is its own small lie. Fading it after ~60 seconds would track the actual
   cache window, but a timer that outlives the component is a leak waiting to
   happen — if it self-dismisses, the cleanup must be proved by a test.

   **Decided (this pass): no.** `saveNote` is reset to `null` when a
   create/update/delete/reorder/active-toggle attempt *starts* and set to
   `CRT_SAVE_NOTE` once that attempt *succeeds* — modelled exactly on
   `WorkshopEditor.svelte`'s existing `saveNotice` (set on save, cleared at
   the next attempt), not a new pattern. It persists on screen until the next
   attempt, not on a timer. Two reasons: a timer that outlives the component
   is a real leak class this codebase already worries about (§8a/§5a's
   general caution about anything that can keep running past its owner), and
   proving its cleanup buys nothing here that the no-timer design doesn't get
   for free — the note is not misleading by lingering, since "up to a minute"
   was already phrased as a ceiling, not a promise it disappears once passed.
   An admin who saves five rows in a row and leaves the note up sees a true
   statement the whole time it's visible.

### The defect: a validation-rejected save leaves the "Saved." note standing

`saveNote = null` is **not** at the start of `submitCreate` or `saveEdit`, as
this issue's `## Fix` prose claims. It sits *after* each function's
client-side validation guards:

- `submitCreate` — `validateNewCrtCommand(...)` returns `{error}` and the
  function `return`s three lines before `saveNote = null` is reached;
- `saveEdit` — three guards (`command` empty, `output` empty, invalid
  `source`) each `return` before it.

So an admin who saves successfully and then makes an ordinary input mistake
sees, simultaneously, `Command cannot be empty.` **and** `Saved. It can take
up to a minute to appear on the home page…`. That is the exact confusion this
issue exists to remove, inverted: a note asserting a save happened, next to
the error saying the save the operator just attempted did not.

Proved by mutation rather than by reading, on a throwaway copy of
`CrtCommands.behavior.test.ts` under a unique name (run with `npx vitest
run`, deleted immediately; working tree `git status --porcelain`-clean before
and after, no committed test touched): toggle a row active → note appears →
open a row editor, blank its command field, click Save → the error appears,
`updateCrtCommand` is called **once** (no second request left the component),
and `queryByText(/up to a minute/)` is still non-null. The probe passed,
which is to say the stale note is real and reachable.

### What already holds up, so it is not re-litigated on the next pass

**The live region is genuinely announced-shaped.** The `<p role="status">` is
the first, unconditional child of the "CRT session" `<Panel>`; `Panel.svelte`
renders `{@render children()}` unconditionally, so nothing gates it. Measured
rather than asserted: driving the live-region guard's own `checkFile` over
the real file, this element is classified with `governingBranch ===
undefined` — the guard's "persistent node" case. Criterion 4's claim that no
`KNOWN_STABLE_BRANCH_SITES` entry is needed is therefore correct on the
merits, not by markup-bending. The node is always mounted and its **text**
mutates into it, which is the right shape.

**The empty state does not suppress announcement.** `.sr-only`
(`web/src/app.css:456`) is the clip/offscreen recipe — `position: absolute;
width/height: 1px; clip: rect(0,0,0,0)` — **not** `display: none`, which is
the thing that would take the region out of the accessibility tree. The
visible state swaps the class to `text-muted crt-cache-note` on the same
node; `npm run check` reports 0 warnings, so Svelte has not pruned
`.crt-cache-note` despite the dynamic `class={…}` expression.

**All five actions are wired**, and each sets the note only on its success
path: `submitCreate`, `saveEdit`, `toggleActive`, `move`, `handleDelete`.
The *network*-failure case is correctly handled and tested.

**The wording is sound, and better than the criterion required.** "Saved. It
can take up to a minute to appear on the home page — if it still looks out of
date, a hard reload bypasses your browser's own cached copy." The two stacked
windows decompose correctly: after a hard reload the browser layer is out of
the picture and the only remaining staleness is the server's ≤60s in-process
cache, so "up to a minute" is a true ceiling *for the sentence it is in*, and
the second clause is what covers the layer that pushes the naive worst case
toward two minutes. It names no number the system does not honour.
Keeping the string in `lib/crtCommands.ts` as `CRT_SAVE_NOTE` is right per
CLAUDE.md §1 and stops the test and the component drifting apart.

One wording nit, **not** a condition of resolution and not worth a pass of
its own: "Saved." reads oddly after a *delete* — the operator removed a row
and is told the thing was saved. "Done." or "Change saved." would cover all
five verbs evenly. Change it only if the next pass is already editing the
string; otherwise leave it.

**The no-self-dismiss decision is acceptable.** Consistency with
`WorkshopEditor.svelte`'s `saveNotice` — set on success, cleared when the
next attempt starts — is a real argument, and it is the argument I am
accepting: a second, divergent notice pattern in the same admin console
would be worse than a note that lingers. The "a timer that outlives the
component is a leak" framing in the recorded reasoning is somewhat
overstated (Svelte 5's `$effect` cleanup or `onDestroy` would clear an
interval cleanly, and the issue's own open question already required proving
that cleanup), but the conclusion does not rest on it: the note is phrased as
a ceiling rather than a countdown, so it does not become false by remaining
on screen. Recorded as sufficient — do not revisit.

**No regression.** The old permanent paragraph is gone, not duplicated —
`crt-cache-note` now appears exactly twice in the tree, once as the dynamic
class expression and once as the CSS rule. `#0393`'s existing
`CrtCommands.behavior.test.ts` tests are untouched: the diff is a pure append
at line 137.

**jsdom limits are stated honestly.** Both this issue and `#0396` say plainly
that the mount, text, and attribute assertions are solid under jsdom while
actual assistive-technology announcement is not observable there and rests on
the project's existing `#0063` convention. No claim is stated more strongly
than its evidence — CLAUDE.md §1's requirement is met.
