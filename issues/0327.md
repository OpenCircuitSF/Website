## Description

`scripts/testdb.sh gc --all` sweeps databases matching `opencircuit_test_%` and
excludes **only `$TEMPLATE`**. When `TEMPLATE_DB` is overridden to point
somewhere else, the real shared `opencircuit_test_template` is no longer
excluded — **and gets dropped**.

Pre-existing, from the `#0150` era. What makes it worth filing now is that
**`#0315` and `#0320` actively teach agents to set `TEMPLATE_DB`.** Both issues'
dispatches, implementations, and reviews all use a private override as the
correct way to test template behaviour without disturbing concurrent agents. So
the safe habit those issues established and the unsafe behaviour of `gc --all`
now compose badly.

Not triggered in either review — both ran bare `gc` only — and found by `#0320`'s
reviewer while auditing the surrounding script.

**The blast radius is real.** Dropping the shared template does not lose data,
but every agent's next `create` has to rebuild or provision from scratch, and
`#0315` exists because a template problem locks out everyone at once.

## Acceptance criteria

1. `gc` never drops the **default** shared template, whatever `TEMPLATE_DB` is
   set to. Exclude the default name explicitly, not just `$TEMPLATE`.
2. It also never drops the **overridden** template. Both are templates; both are
   somebody's.
3. Consider excluding anything matching a template naming pattern rather than a
   single literal — an agent following `#0315`'s advice may create
   `..._template`-suffixed databases of its own.
4. `#0150`'s protection survives exactly: `gc` still refuses without `--all`, and
   still skips databases with live connections. That guard exists because one
   agent swept another's databases mid-session.
5. A guard case in `scripts/testdb_gc_guard_test.sh` proves a `TEMPLATE_DB`
   override does not expose the default template to `gc --all`. **Prove it fails
   against the current script** before fixing.
6. Verify by running the guard suite, not by reading — and use a scratch template
   you create, never the real one.
7. `ISSUE=NNNN scripts/check.sh guards` passes, run at least twice.

## Root cause

`gc --all`'s sweep query excluded only `datname <> '$TEMPLATE'`. `$TEMPLATE`
is `${TEMPLATE_DB:-opencircuit_test_template}` — whatever the current
invocation resolves it to. Overriding `TEMPLATE_DB` (the pattern `#0315` and
`#0320` teach) repoints `$TEMPLATE` away from the real default, and the real
`opencircuit_test_template` was then just another `opencircuit_test_%` row
with nothing protecting it.

## Fix

- `PREFIX` now comes first in the variable block, and `DEFAULT_TEMPLATE` is
  defined from it (`"${PREFIX}template"`) rather than as a second hardcoded
  literal — it always names the real default regardless of any
  `TEMPLATE_DB` override, and it automatically tracks `PREFIX` if that ever
  changes.
- `gc`'s exclusion is now `datname <> '$TEMPLATE' and datname <>
  '$DEFAULT_TEMPLATE' and datname not ilike '%template%'` (criteria 1–3):
  the current override, the real default, and — per criterion 3's
  suggestion — anything that merely looks like a template by name, since an
  agent following `#0315`'s advice may create its own
  `..._template`-suffixed scratch database.
- `#0150`'s refusal-without-`--all` and live-connection skip are untouched
  (criterion 4) — only the `dbs=` selection query changed, not the refusal
  or per-database connection check that follow it.

### §8 guard-design audit of Part 4

- **The oracle is not the subject's bytes.** Part 4's three assertions are
  *behavioural* (`db_exists` after a real `gc --all`), which no textual decoy can
  satisfy — a shadowing second `exclude_clause=` line would change actual
  behaviour and be caught. This is the shape §8 prefers, and it is why the
  "marker block appears exactly once" rule does not apply here: there is no
  textual oracle for the property.
- The one textual check (`grep -Fq` for the mutation's own replacement text) is a
  *fail-closed abort*, not an assertion about the property, and I confirmed it
  fires correctly against a script with no matching line.
- **The mutation proof is sensitive, not vacuous** — confirmed twice by running
  it, and separately by the pre-fix run above.
- One weakness, not blocking: the mutation removes the `DEFAULT_TEMPLATE`
  exclusion and the `%template%` exclusion together, so it cannot show which of
  the two is load-bearing. Removing only `datname <> '$DEFAULT_TEMPLATE'` would
  still pass Part 4, because `%template%` catches the same database.

### Findings (none blocking; recommended for follow-up issues)

- **B — `not ilike '%template%'` is unanchored.** Any scratch database whose
  name merely *contains* "template" is now permanently invisible to **both** of
  `gc`'s paths: `gc --all` will not sweep it, and the bare-`gc` refusal listing
  will not even mention it, so nobody is told it exists. `list` still shows it
  and `drop <ISSUE>` still removes it, and the failure direction is safe
  (refuse-to-drop), so this is a leak rather than a loss. Anchoring to
  `%_template` or `%template` would keep criterion 3's intent without the
  reverse blast radius.
- **C — `scripts/testdb.sh drop template` still drops the real shared
  template.** `name_for template` returns `opencircuit_test_template` (also for
  `TEMPLATE`, since `#0208` lower-cases). Pre-existing, but now inconsistent:
  after this change `gc` protects the shared template and `drop` does not, and
  the blast radius is exactly the one `#0327` was filed about — every agent's
  next `create` falls back to a full `migrate up`.
- **E — cosmetic.** `build_template`'s "other scratch databases exist" notice
  still selects on `datname <> '$TEMPLATE'` only, so under a `TEMPLATE_DB`
  override it lists the real default template as somebody's scratch database.
  Informational output only.
