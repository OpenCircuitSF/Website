## Description

`#0340` added `tokenGatedKinds` as a `map[Kind]bool` and
`TestTokenGatedKindsPartitionEveryMailKind` to keep the enumeration a live
artifact. **The guard checks map *membership* but never the `bool` value.**

So an entry flipped from `true` to `false` is silently ungated while the guard
still reports that a decision was made for that kind — the enumeration looks
complete and the gate does nothing.

**Measured, not inferred.** `#0340`'s review ran exactly this mutation: setting
`tokenGatedKinds[KindImportInvite]` to `false` failed the send-path tests that
depend on the gate, **and `TestTokenGatedKindsPartitionEveryMailKind` passed.**
The partition guard did not notice the kind it names had been disarmed.

The model it was built from, `#0365`'s `gatedKinds`, is a `map[Kind]string` with
**no off state** — membership there genuinely is the decision. Copying the shape
to a `map[Kind]bool` silently introduced one.

This is the phase's recurring defect once more — an assertion passing for a
reason that does not distinguish what it names (`#0364`, `#0389`, `#0390`,
`#0394`) — and specifically the sub-family where the check *cannot fail* for the
thing it claims to cover (`#0354`, `#0358`, `#0363`).

## The remedy, from the review that found it

One loop:

	for k, on := range tokenGatedKinds {
		if !on {
			t.Errorf(...)
		}
	}

Consider instead whether `map[Kind]bool` is the wrong type — if there is no
legitimate `false`, a set type (`map[Kind]struct{}`) makes the defect
unrepresentable rather than merely detected. Say which you chose and why.

## The second half — an untested stale-row site

`#0340`'s plan named **four** sites that leave a deliverable stale row.
Three are covered by tests in the tree; **`RestartSignup` is not.**

It is the sharpest of the four: it moves a subscriber's status *back* to
`pending`, re-opening `#0365`'s status gate on a queued row still carrying the
pre-restart token. The token gate is what catches it, and nothing in the tree
proves that.

`#0340`'s reviewer wrote that test and confirmed it lands `skipped` on the fixed
tree and **delivered** against a gate-disabled mutant, but did not land it. It
is preserved at:

	<scratchpad>/0340-review-restart-signup-test.go.txt

**That path is session-scoped and will not survive.** Recover the file early, or
rewrite the case from its description: create pending → enqueue `import_invite`
with the live token → `Unsubscribe` → `RestartSignup` → run the worker → assert
`skipped`.

### Criterion 1 — the type change, assessed rather than confirmed

**The compile failure reproduces exactly as reported.** Writing
`outbox.KindImportInvite: false` back into the new literal in an export of
`HEAD` gives `cannot use false (untyped bool constant) as struct{} value in map
literal`. The disarmed-but-present state is genuinely unrepresentable, not
merely detected.

The choice over the value-assertion loop is right, and for a reason stronger
than the implementer's: `#0340`'s review found the guard blind because the guard
had to *remember* to look at the value. Adding a loop makes the guard's
correctness depend on a second thing living in the same file it guards — the
shape CLAUDE.md §8's "a guard inside the file it guards becomes new mutable
surface" entry warns about. The type change removes the question instead.

**What it cost — nothing measurable, checked rather than assumed.** The map's
value had exactly two readers in the tree, both re-derived by grep across
`internal/` and `cmd/`: `sendGate`'s predicate, and the partition guard, which
already used the comma-ok form and so never read a value at all. Nothing in
`docs/`, and nothing outside the doc comments recording the change, describes
the old type.

**The call-site rewrite preserves semantics exactly.** The old
`!tokenGatedKinds[row.Kind]` leant on the `bool` zero value for *absent* keys —
that was the load-bearing use of the zero value, and comma-ok reproduces it
identically. For present keys the two forms agree because both literal entries
were `true`; had either been `false`, the forms would have diverged, which is
precisely the state the new type forbids. Behaviourally confirmed: the
ungated-kind pin (`TestSendGateNeverWithholdsUngatedKinds`) and the whole
`internal/mailing` package pass unchanged.

One asymmetry is now deliberate and documented: `gatedKinds` stays
`map[outbox.Kind]string` because its value *is* the wanted status, and
`tokenUngatedKinds` stays a string map because its value is the written reason
the partition guard asserts non-empty. Only `tokenGatedKinds` had a value
carrying no information, and only it became a set.

### Criterion 3 — the recovered test proves the TOKEN gate, not the status gate

This was the question worth the most attention, and it is answered by
measurement, not by reading the test.

| # | Mutation | Exit | Result |
|---|---|---|---|
| — | **Control**, fixed tree, own database | 0 | passes; the worker log shows the row withheld with reason `"confirm token was rotated since enqueue"` |

**E1 is the direct answer to "does the row genuinely pass the status gate".**
With the token gate removed, the row is delivered `sent` — so nothing upstream
was withholding it, and the status gate demonstrably waves it through.

here because `Unsubscribe` only suppresses on its invite-decline branch
(`import_id` set with `consent_basis` NULL), which a `Create`-made website
signup never satisfies.

**E7 is what makes the test discriminating rather than merely correct.** The
`errText` assertion is the half that separates "withheld by the token gate"
from "withheld by anything else"; E7 proves it fires when the withholding moves
to the status gate.

### An invented mutation the fix does not cover — worth filing

| # | Mutation | Exit | Result |
|---|---|---|---|
| F | move `KindAlreadySubscribed` from `tokenUngatedKinds` into `tokenGatedKinds` (partition kept intact) | 0 | **the entire `internal/mailing` package passes green** |

`already_subscribed`'s producer enqueues `alreadySubscribedPayload{ManageToken:
…}` — no `confirm_token` at all. Measured inside the mutant with a throwaway
probe rather than inferred: `tokenGate` on that payload returns
`skip=true, reason="queued row's payload carries no confirm token"`. So a kind
added to `tokenGatedKinds` whose payload carries no confirm token has **every
one of its messages silently withheld**, and nothing in the suite notices.

This is the `#0296` item 4 shape again, in the opposite direction from the one
`#0340`'s review found: `#0400` closed "a member can be present but disarmed";
this is "a member can be present but ungateable". It is an availability failure
of exactly the class `TestSendGateNeverWithholdsUngatedKinds` exists to prevent
for the status gate, and the token gate has no sibling of that test.

Remedy, if filed: a parity guard asserting that every `tokenGatedKinds` member's
producer payload declares a `confirm_token` JSON field — the direction an AST
or `go/types` guard can decide, and the one thing the partition guard
structurally cannot. Not filed here (CLAUDE.md §9); reported to the
orchestrator.

**Byte-unmodified, proved by digest rather than by reading the diff.** Each of
the three pin functions was extracted from `9ac9425` (the commit before this
issue's implementation) and from `HEAD` and hashed:

| `TestAdminResendInvitation_PhysicalAddressGateNotBypassable` | `32504fdd1cb12ba1` | 3033 |

Identical in both revisions. All three pass.

**§9's refusal remains structurally unreachable by any new path**, checked in
`sendOne` rather than accepted from the claim: `sendGate` runs as `sendOne`'s
first statement and its three outcomes are *fail* (`finishFailed`, retry),
*withhold* (`finishSkipped`, terminal), or *proceed*. `render` — which raises
`errWelcomePhysicalAddressRequired` / `errImportInviteMissingPhysicalAddress`
and routes them to `deferMissingPhysicalAddress` — runs strictly after, and
nothing in the token predicate can skip it. A token-gate change can only ever
withhold more mail, never let a physical-address-less send through.
`TestOutboxWorker_TokenGateDoesNotShortCircuitPhysicalAddressDefer` pins the
same property behaviourally and passes.

`#0340`'s M1/M2/M3 all pass unchanged.
