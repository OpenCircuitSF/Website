## Description

`#0237` was bounced three times for statements about this guard's behaviour
written without running it, and resolved on the fourth pass — whose header
change was to stop *counting* exceptions and describe the **boundary** instead,
a claim that can be falsified. The reviewer tried thirty synthetic shapes
against it and could not.

It then found **two further false claims in the same file**, both predating
that pass and untouched by it.

**1. The header claims the guard "walks every `audit.Entry{…}` composite
literal in production Go source". It does not — four demonstrated shapes are
invisible or silent:**

| Shape | Result |
|---|---|
| `var seedEntry = audit.Entry{…}` at package level | `SITES=0` — not seen at all |
| `audit.Entry{…}` inside a func literal on a package-level `var` | `SITES=0` |
| elided-type element in `[]audit.Entry{{…}}` | `SITES=0` |
| `e := audit.Entry{}` then `e.Metadata = map[string]any{"email": …}` | seen, **silent pass** |

The fourth is the one that matters. **It is the plausible refactor shape** — the
form someone naturally reaches for when an entry needs building across a few
lines — and it passes silently rather than failing as unclassifiable. The other
three are structural blind spots that would report `SITES=0` and therefore never
contradict the pinned list.

None is live today (`OUTSIDE_FUNC=0`), which is exactly the condition under which
an overstated claim survives review.

**The same claim is echoed in `PrivacyPolicy.svelte`'s comment block**, so the
privacy page's own justification rests on it.

**2. `auditEmailMetadataSuspectKeyTokens`' doc comment contradicts itself two
clauses apart.** It says no key in the tree contains `to` as an
underscore-delimited token today — while `"to"` **is** a key, at
`admin_campaign_preview.go:419`. That key is the reason `to` was added to the
token set in the first place.

## Root cause

Two independent false claims, both predating the fourth pass's
boundary-description fix and untouched by it:

1. The header's opening sentence said the guard "walks every `audit.Entry{…}`
   composite literal in production Go source." It does not: `scanAuditEntrySites`
   only descends into composite literals found inside a top-level function's
   body (`ast.Inspect(sf.file, ...)` keys specifically on `*ast.FuncDecl`
   nodes before doing anything else). A literal that never sits inside one —
   a package-level `var`, a `var`'s func literal, an elided-type slice
   element — is never visited, and the walk finds it not at all. A fourth
   shape, `e := audit.Entry{}` followed by `e.Metadata = ...`, IS visited
   (the empty literal is a real composite literal inside a function body),
   but the Metadata-reading loop only ever looked at the literal's own
   `Elts`, so it silently resolved as `hasEmail=false, unresolved=""` — a
   real site, wrongly cleared.
2. `auditEmailMetadataSuspectKeyTokens`'s doc comment said "no key in the
   tree contains 'to' ... as an underscore-delimited token today" in the same
   breath as naming `admin_campaign_preview.go:419`'s `"to": actor.Email` as
   the key that motivated adding `"to"` to the token set. Both cannot be
   true; the key exists, splits to the single token `"to"`, and is why `"to"`
   was added at all.

## Fix

**Claim 1, verified empirically before writing anything** (`## Verification`
below shows the actual `scanAuditEntrySites` output for all four shapes):

- The three structurally invisible shapes (package-level `var` literal,
  `audit.Entry{}` inside a func literal on a package-level `var`,
  elided-type `[]audit.Entry{{...}}` element) are genuine, unfixed blind
  spots — the walk finds `SITES=0` for each. Documented plainly in the
  guard file's header (a new paragraph, boundary-description style) and
  pinned as committed tests
  (`TestAuditEmailMetadataGuardDocumentedInvisibleShapes`), the same
  treatment the camelCase key gap and the original four silent-pass shapes
  already get.
- The fourth shape (`e := audit.Entry{}` + `e.Metadata = ...`) was **fixed,
  not just documented** — this is the one criterion 5 calls "the plausible
  refactor shape," and the guard's own established philosophy elsewhere is
  "cannot classify ⇒ FAILURE," so leaving a genuinely closeable hole open
  favored the guard's own precedent, not "avoid touching working code."
  Added two small, self-contained helpers to `scanAuditEntrySites`:
  `collectDeferredMetadataFieldIdents` (identifiers later assigned via
  `ident.Metadata = ...`) and `compositeLitAssignedIdents` (maps an
  `audit.Entry{}` literal that IS the direct RHS of `ident := ...`/`ident =
  ...` back to `ident`'s name). When a literal has no `Metadata` key of its
  own AND its assigned identifier is later given one via a struct-field
  assignment, the site is now reported `unresolved` — the same conservative
  default every other unclassifiable shape already gets — instead of
  passing silently. Pinned by
  `TestAuditEmailMetadataGuardFailsOnDeferredStructFieldAssignment`,
  **mutation-proved**: disabled the new check with a `false &&` guard,
  confirmed the test fails with exactly the expected message, restored from
  a `cp` taken first, and confirmed `shasum -a 256` identical before and
  after.
- Rewrote the header's opening claim to name the actual boundary (found
  inside a top-level function's body, not "every ... composite literal, full
  stop") and added a full paragraph naming all four shapes, in the
  boundary-description style the fourth pass established — not a count, not
  a blanket claim.
- `PrivacyPolicy.svelte`'s comment block echoed the same overclaim ("walks
  every production `audit.Entry{` construction in internal/ and cmd/") —
  corrected in place, and a new chronological bullet added (matching the
  file's own established style of dating each correction) summarizing what
  #0252 found and fixed, so the page's own justification no longer rests on
  the false claim.

**Claim 2**: rewrote the doc comment to stop claiming no key contains `"to"`
as a token. It now says plainly that `"mail"` and `"contact"` are the two
that match nothing in the tree today, and that `"to"` is different — the key
`"to"` is real, present at `admin_campaign_preview.go:419` today, and is the
entire reason the token was added, not something absent the way `"mail"`/
`"contact"` are.

**Decision on criterion 5**: fixed, not left open. Chose to actually resolve
the struct-field-assignment shape (report it as `unresolved`) rather than
merely pin it as a documented gap, because (a) it is cleanly separable from
every other code path in this file — verified by running the full existing
suite plus the real-tree census both before and after, all passing
identically — and (b) the guard's own stated philosophy throughout this file
is that an unclassifiable shape should fail loudly, not pass quietly, and
this shape was the one place that philosophy had a hole. The three
structurally invisible shapes were left open and pinned instead: closing
those would mean walking package-level declarations and `*ast.FuncLit`
bodies too, a materially larger change with no real site in this tree
motivating it today, and exactly the kind of change this file's own header
says should be "a deliberate, reviewed change to this file, not a byproduct"
of a bug-fix pass for something else.

## Notes

Reported by `#0237`'s fourth phase-3 review under `CLAUDE.md` §9.

**Worth stating plainly**: this is the fifth round of false claims in one file,
and the pattern across all of them is a claim about *coverage* — how many sites,
how many exceptions, what is walked. The fourth pass fixed one such claim by
changing its kind, from a count to a falsifiable boundary. That worked. These
two are the same class in the same file, unreached because they sit in the
header's opening sentence and in a token list's comment rather than in the
paragraph under review.

The lesson is not "be more careful". It is that a guard's own documentation
should state what it *cannot* see, in a form a test can pin — which is what
criterion 5 asks for.
