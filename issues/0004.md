## Description

Keep only the migrations that build the auth and admin schema, renumber them to a contiguous `000001`–`000007`, and confirm a clean `up` and `down` against a real PostgreSQL database.

> 🟢 Resolved 2026-08-18 — Seven contiguous auth migrations verified `up` → `down -all` → `up` against local PostgreSQL 16.14 with no orphaned objects, and migration 000007's executable SQL is identical to ShortLinks' 000013 apart from its renumbered abort message.

## Root cause

Not applicable — foundation work, not a bug. The copied migration set (#0001) carries the full ShortLinks schema (links, clicks, campaigns, UTM, url_filter_rules) alongside the auth/admin tables this project keeps; the two later fixup migrations (backup flags, NOT NULL enforcement) also needed a decision on whether to squash or keep separate.

## Fix

Deleted `000002_create_links`, `000003_create_clicks`, `000008_create_url_filter_rules`, `000010_create_campaigns`, `000011_links_campaign_and_utm`, `000012_clicks_campaign_and_bot` (all `.up.sql`/`.down.sql` pairs). Renumbered the seven survivors to a contiguous `000001`–`000007` via `git mv`-equivalent copies (confirmed by `git status` showing them as renames, not add+delete): `000001_create_users` (unchanged), `000004_create_auth_credentials` → `000002`, `000005_create_sessions` → `000003`, `000006_create_settings` → `000004`, `000007_create_audit_log` → `000005`, `000009_passkey_backup_flags` → `000006`, `000013_enforce_session_passkey_not_null` → `000007`.

**No squashing.** The issue's Notes call squashing the two fixups into their base migrations "acceptable and preferable" since there's no deployed database. I considered it, but the acceptance criteria's literal "renumber them to a contiguous `000001`–`000007`" already matches one migration per surviving item, one-for-one — seven items, seven files. Squashing would have produced five files and missed that explicit target range, so I renumbered instead of squashing.

`000007`'s (formerly `000013`'s) SQL logic is byte-for-byte unchanged — the same defensive existence-check-then-`ALTER … SET NOT NULL`, the same deliberate no-op `down.sql`. Its comments, though, narrated a ShortLinks-specific production incident (commit `791e7d3`, `issues/0110.md`, `issues/0111.md`, "production runs 15.15") that has no referent in this repo — there is no deployed OpenCircuitSF database and no such drift history. Rewrote the prose to explain what the migration does and why it is a practical no-op on every database this project will ever run it against, dropping the borrowed incident narrative, and updated every internal cross-reference to the new numbers (`000004`/`000005` → `000002`/`000003`, "version 12/13" → "6/7", `force 12` → `force 6`).

Reviewed `000004_create_settings`'s (formerly `000006`'s) seed row set per the acceptance criterion: it already seeds only `registrations_enabled` — no shortener-specific keys were present to remove.

Updated `scripts/db/create.sql` and `scripts/db/drop.sql`: role and database name `shortlinks` → `opencircuit` throughout (including the placeholder-password reminder and the DATABASE_URL note).

Created the `opencircuit` PostgreSQL role and the `opencircuit` / `opencircuit_test` databases locally (mirroring the pre-existing `shortlinks`/`shortlinks_test` setup), then ran the full migration `up`/`down`/`up` cycle against `opencircuit` and a plain `up` against `opencircuit_test` for the Go suite to use.

While verifying `go test ./...` against the live `opencircuit_test` database, found two more Go integration-test `TRUNCATE` statements still listing the now-nonexistent `clicks`/`links` tables — `internal/auth/registration_test.go` and `internal/middleware/auth_test.go` (a third, `internal/handlers/credentials_test.go`, was already fixed in #0002). These are compiling-but-runtime-broken leftovers from #0002's Go-tree strip: #0002's verification ran with no `TEST_DATABASE_URL` set, so these particular `TRUNCATE` statements never actually executed against Postgres and the dangling table references went unnoticed until #0004 stood up a real database. Fixed both to drop `clicks, links` from their table lists, matching #0002's `credentials_test.go` fix.

## Verification

Environment: PostgreSQL 16.14, `golang-migrate` v4.19.1 (`migrate -version` confirmed). Created role `opencircuit` and databases `opencircuit` / `opencircuit_test`, both owned by that role, via `psql`/`createdb` as the local superuser — mirroring `scripts/db/create.sql`'s statements rather than running the script directly (no superuser access was needed beyond what the local Postgres install already grants this user).

```
$ migrate -path migrations -database "postgres://opencircuit:devpassword@localhost:5432/opencircuit?sslmode=disable" up
1/u create_users (10.35ms) ... 7/u enforce_session_passkey_not_null (43.09ms)
```
Applied cleanly, 7/7, against an empty database. `psql \dt` afterward showed exactly the 8 expected relations (7 domain tables + `schema_migrations`): `audit_log`, `passkey_credentials`, `pending_registrations`, `schema_migrations`, `sessions`, `settings`, `users`, `webauthn_challenges`. `\d sessions` confirmed `user_id`/`created_at`/`expires_at`/`last_seen_at` all `NOT NULL`, `created_at DEFAULT now()` — migration 7's constraints took effect. `schema_migrations` read `version=7, dirty=f`.

```
$ migrate -path migrations -database "$DATABASE_URL" down -all
7/d enforce_session_passkey_not_null ... 1/d create_users
```
Reversed cleanly, 7/7. `psql \dt` and `\di` afterward showed only `schema_migrations` and its primary-key index remaining — no orphaned tables, indexes, or sequences from any of the seven migrations.

```
$ migrate -path migrations -database "$DATABASE_URL" up
```
Re-applied cleanly a second time (1/u … 7/u), confirming the down migrations left the schema in a state a fresh `up` replay accepts without conflict — the same 8 relations came back.

Ran the same `up` against `opencircuit_test`, then, with `TEST_DATABASE_URL` exported:

```
go build ./...   →  clean
go vet ./...     →  clean
go test ./...    →  ok: cmd/opencircuit, internal/audit, internal/auth (1.815s, live DB),
                     internal/db, internal/devstore, internal/events, internal/handlers,
                     internal/middleware (0.699s, live DB); internal/testdb/web: no test files
                     FAIL: internal/config — same pre-existing TestLoad_DefaultsApplied
                     recorded in #0001/#0002, untouched here
```

Re-ran the three DB-backed packages individually with `-count=1 -v` (bypassing cache) to get real numbers: `go test ./internal/auth/... ./internal/middleware/... ./internal/handlers/... -count=1 -v` — **144 tests passed, 0 failed, 0 skipped**. This is the first point in Phase 0 these suites have run against a real database rather than skipping on a missing `TEST_DATABASE_URL`; the 144-pass/0-skip result is what caught the two stale `TRUNCATE` statements above; both are now included in that 144.

## Gotchas

- The `opencircuit`/`opencircuit_test` PostgreSQL role and databases exist only on this machine's local Postgres instance — they are not captured anywhere in version control (by design; `scripts/db/create.sql` is the reproducible record). Any other environment running these migrations needs `psql -U postgres -f scripts/db/create.sql` first.
- The two `TRUNCATE`-statement fixes are arguably #0002's responsibility (a Go-tree stripping leftover) surfacing only under #0004's live-database verification. I fixed them here rather than bouncing back to #0002, since leaving `go test ./...` broken against a real database is worse than a small scope overlap — flagging for the reviewer in case a stricter split is preferred.
- `internal/db/pool.go`, `internal/audit/audit.go`, and `internal/audit/actions.go` still carry doc-comment references to `links`/`clicks`/`campaigns` domain packages and ShortLinks issue numbers (e.g. "#0098-#0099", "campaigns.Store"). These are prose only — no functional or SQL impact — and were left untouched as out of scope for a migrations issue; worth a documentation pass in a later issue.
