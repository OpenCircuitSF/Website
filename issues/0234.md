## Description

`pg_locks` is **cluster-wide**. `diagnoseLockHolders` queries it without
filtering on `l.database`, so it reports lock holders in *every* database on the
instance — and then presents one as the reason *your* `TRUNCATE` is stuck.

This is not theoretical, and it is not rare. `CLAUDE.md` §5a makes per-agent
test databases the norm, and `scripts/testdb.sh` creates them as
`CREATE DATABASE … TEMPLATE opencircuit_test_template` clones. **Template clones
share relation OIDs verbatim**, so `audit_log` is the same OID in every one of
them — measured as `12933693` across `opencircuit_test_template`,
`opencircuit_test_0217revmut` and `opencircuit_test_0217revset` alike. A lock
held on `audit_log` in one agent's database is therefore indistinguishable, by
OID, from one held in yours.

Demonstrated by `#0225`'s review, holding a real `ACCESS EXCLUSIVE` lock in one
database and running the diagnostic's query from another:

```
59703|audit_log|active|opencircuit_test_0217revmut   -- asked from _0217revset
```

The diagnostic answers a question about a database nobody asked about.

**This is pre-existing, not a `#0225` regression** — the review confirmed the
pre-`#0225` query does exactly the same thing, and it was correctly out of that
issue's scope, which was the text-versus-OID dialect mismatch.

**Why it matters more than a cosmetic wrong answer.** This diagnostic exists
precisely for the concurrent-agent scenario, and that is exactly the scenario
where it misleads. An agent whose suite hangs is told the culprit is a pid in a
database it does not own — inviting it either to chase an unrelated process or,
worse, to terminate another agent's backend. The project has already lost a day
to misattributing concurrency symptoms to code (`#0084`, `#0087`, `#0091`,
`#0096`, `#0099`), which is the same failure with the blame pointing the other
way.

## Implementation notes

Added the exact predicate the Notes specified to `diagnoseLockHolders`'s query
in `internal/testdb/testdb.go`:

```sql
AND l.database IN (0, (SELECT oid FROM pg_database WHERE datname = current_database()))
```

`0` is what `pg_locks.database` reads for a shared-catalog lock (e.g.
`pg_database`, `pg_shdepend`) regardless of which database is doing the
locking — a naive `l.database = current_database()` alone would silently drop
that whole class of lock from the diagnostic, which the acceptance criteria
call out explicitly. Extended the function's doc comment to explain both the
cross-database hazard and why `0` has to stay in the predicate.

## Verification

All against a real PostgreSQL 16 instance (`TEST_DATABASE_URL`), never
mocked — nothing about this fix is deferrable to deployment per `CLAUDE.md`
§10, since it only touches local test tooling.

Two new tests added to `internal/testdb/lock_diagnosis_test.go`:

- **`TestDiagnoseLockHolders_IgnoresLocksInOtherDatabase`** — reproduces the
  bug the way it was found. Creates a genuine sibling database by cloning
  `opencircuit_test_template` (the exact mechanism `scripts/testdb.sh create`
  uses), and first *proves* the precondition rather than assuming it: queries
  `'audit_log'::regclass::oid` in both the current test database and the
  sibling and asserts they're equal (they are — template clones share
  relation OIDs verbatim, matching the issue's own measurement). Holds a real
  `ACCESS EXCLUSIVE` lock on `audit_log` in the sibling database and asserts
  `diagnoseLockHolders`, run against the current database's pool, reports
  nothing. Then, in the same test, holds a lock on `audit_log` in the
  *current* database and asserts it IS reported — the converse, so an
  implementation that always returns `""` cannot pass for the wrong reason.
- **`TestDiagnoseLockHolders_SharedCatalogLockStillReported`** — the other
  half of the acceptance criteria: takes a real `ACCESS SHARE` lock on
  `pg_database` (a genuine shared catalog), confirms via a direct
  `pg_locks` query that Postgres itself records `l.database = 0` for that
  lock (the precondition, proved not assumed), then confirms
  `diagnoseLockHolders` still names it. This is what would have caught a
  naive `l.database = current_database()` fix that dropped the `0` branch.

## Notes

Reported by `#0225`'s phase-3 review under `CLAUDE.md` §9.

The fix is one predicate:

```sql
AND l.database IN (0, (SELECT oid FROM pg_database WHERE datname = current_database()))
```

`0` is what `pg_locks` records for shared catalogs; omitting it would make the
diagnostic silently blind to a class of lock it can currently see.

A trivial related nit, recorded rather than filed separately: `#0223`'s Part 4
leak census matches `like '${TESTPREFIX}%'` with `_` left unescaped, so the
underscores act as single-character wildcards. That can only *broaden* the
census, never narrow it, so it cannot produce a false pass — but it is not what
the code appears to say.
