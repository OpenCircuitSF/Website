## Description

Step 9 of `docs/deployment.md`'s restore drill cannot drop the database it
created. Every run leaves one behind.

```
scripts/testdb.sh drop "${ISSUE}dst"
ERROR: must be owner of database
```

**Deterministic, not intermittent** — reproduced identically in both of
`#0248`'s runs and in `#0239`'s review before it. The cause: `restore.sh` with
`RESTORE_CREATE=1` under `BACKUP_RUN_AS=""` calls `createdb` as the **local OS
user**, so that user owns the database — while `testdb.sh drop` connects as
`opencircuit`, which does not.

The drill documents the failure, so a follower is not surprised. But
documenting a leak is not the same as not leaking:

- **Every drill run costs a manual cleanup** that the drill itself cannot
  perform, by a person who has to work out which role actually owns the thing.
- **`#0247` just namespaced the drill so it can be run concurrently.** Its
  reward for being run more often is more orphans, each under a different
  `$$`-derived name, and nothing sweeps them.
- `scripts/testdb.sh gc --all` will not help: `#0150` deliberately made it
  refuse databases with live connections and require an explicit flag, and it
  operates on the `opencircuit_test_*` prefix rather than the drill's names.

This is the same class as `#0223` — a cleanup path that reports success while
leaving a database behind — with the difference that here the failure is
visible and simply tolerated.

## Implementation notes

**Root cause confirmed to be exactly what the issue describes.** `restore.sh`'s
`RESTORE_CREATE=1` path called plain `createdb "$TARGET"`, so the *database
object itself* ended up owned by whichever role connected to run it — the
local OS user under `BACKUP_RUN_AS=""`, `postgres` in production. The
existing `reassign_ownership` step (`#0228`, `#0235`) only ever reassigns
what lives *inside* the database — its tables, sequences, views, schemas —
never the database object's own `pg_database.datdba`, which is exactly what
`DROP DATABASE` (and therefore `testdb.sh drop`, which always connects as
`opencircuit`) checks.

**Fix, per criterion 2's first option**: `restore.sh` now creates the
database already owned by `RESTORE_OWNER` when one is set —
`createdb -O "$RESTORE_OWNER" "$TARGET"` instead of plain `createdb`. This
works on both documented paths because `-O` to a role other than the
connecting one requires the connecting role to be a superuser (or a member
of the target role): `BACKUP_RUN_AS=postgres` in production is a superuser,
and on this dev machine the local OS role (`brennan`) is also a superuser
(`select rolsuper from pg_roles where rolname=current_user` → `t`) —
confirmed directly, not assumed. `RESTORE_OWNER=""` skips the `-O` flag
entirely and falls back to plain `createdb`, so the opt-out still opts out
of database ownership, matching its existing behavior for the objects
inside it (criterion 3).

Chose this over step 9 dropping as the actually-owning role (criterion 2's
second option) because that would have meant either hardcoding "the OS user
who ran the drill" into `testdb.sh drop` — which has no way to know that
role in the concurrent, multi-agent case — or adding a second drop path
just for this drill. Fixing `restore.sh` means every caller of
`RESTORE_CREATE=1`, not just this drill, gets a database `testdb.sh drop`
(or any other tool connecting as `opencircuit`) can actually drop.

**Interaction with `#0235` checked, not assumed.** `-O` only sets the
*database's* owner at creation time; it has no effect on the tables,
sequences, views, or the `public` schema itself that `pg_restore`/`psql`
and then `reassign_ownership` create and touch afterward — those are a
separate mechanism (`ALTER TABLE/SEQUENCE/VIEW/SCHEMA … OWNER TO`) working
on objects that don't exist yet when `createdb` runs. Ran the **full**
drill, not just step 9, to prove this isn't hand-waved: seeded a source
database, rolled it back one migration (step 1b), backed it up, restored it
with the fixed script, then ran a real `migrate -path migrations -database
"$DST_DSN" up` (step 6) as the `opencircuit` role. It applied migration 20
cleanly (`20/u create_workshops`) and a subsequent `select count(*) from
workshops` **connected as `opencircuit`** succeeded — the exact check
`#0235`'s own regression proof relies on. `#0235`'s fix is intact.

**Orphan census (criterion 5).** Checked before starting any work and again
right before finishing — both times the only databases on the machine were
the long-lived ones (`opencircuit`, `opencircuit_live`, `opencircuit_test`,
`opencircuit_test_template`, `shortlinks`, `shortlinks_test`), none matching
the drill's `opencircuit_test_*src`/`*dst` naming. **No orphans found to
enumerate.** Per the issue's own caution, no sweep was attempted regardless
— this was a read-only `select datname, pg_get_userbyid(datdba) from
pg_database`, nothing dropped that this session didn't create itself.

**`#0248`'s exit-status prose (criterion 6).** `docs/deployment.md`'s "no
`set -e`" paragraph named two legitimate non-zero exits in the drill's code
block — step 7's expected constraint-count `diff` and step 9's
now-fixed `testdb.sh drop`. Updated it in this commit: step 9 is no longer
one of them, so only step 7's remains. **`issues/0248.md` itself carries its
own copy of the same reasoning in its working tree, uncommitted at the time
of this pass** (last modified alongside `docs/deployment.md` commit
`3e2a4af`, apparently not yet folded into a markdown commit) — that copy is
now stale in the same way and needs the same correction, but editing another
in-flight file's uncommitted content was out of scope here per `CLAUDE.md`
§8a; flagged to the orchestrator instead of touched directly.

rests on reasoning alone or on infrastructure not yet standing (`CLAUDE.md`
§10); every claim below was actually run.

pre-fix `restore.sh` to a scratch path (`git show HEAD:scripts/db/restore.sh`

=== census (FIXED script) ===

## Notes

Found by `#0248` while running the current drill for real, and independently
seen by `#0239`'s review. Reported under `CLAUDE.md` §9.

**Check the interaction with `#0235` before changing who creates the database.**
That issue made `restore.sh` reassign ownership of every object *and* the
`public` schema to `RESTORE_OWNER` after restoring, precisely so the app role
can migrate afterwards. Whatever fixes database ownership must not undo that,
and the drill's step 6 — a real `migrate up` as the app role — is the test that
catches it if it does.

The fourth criterion is the real one. This defect has been observed at least
three times across three passes and tolerated each time because the error
message is honest about what happened.
