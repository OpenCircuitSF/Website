# 0618 — The default event type lives in an `is_default` column instead of the settings table

## Description

`#0613` marks the default event type with `event_types.is_default`. The user's
decision (2026-11-04) is that defaults belong in the existing `settings` table
instead: one value for the default event type, and, through `#0617`, one for the
default location. Move the event type default there and remove the column, so the
two defaults work the same way. What an admin sees does not change.

## Acceptance criteria

- [ ] A new migration, using the next free number, adds a `default_event_type_id`
      row to `settings` holding the id of the current default type, and removes
      `is_default` with its check constraint and unique index. It does not edit
      `000045`, so it is correct whether or not `000045` has reached production by
      then. The down migration restores the prior schema and marks the same type.
- [ ] A listing created with no type still gets the default, including a raw
      `INSERT INTO workshops (slug, title)`: `event_types_default_id()` reads the
      setting instead of the column.
- [ ] The rules from `#0613` still hold. The default must name an existing, enabled
      type. It cannot be disabled or deleted, and setting a disabled or unknown type
      as the default is refused. Because `settings.value` is text and has no foreign
      key, the store enforces this in a transaction, and concurrent calls cannot leave
      the setting naming a disabled or deleted type. Tests cover the concurrent case.
- [ ] The generic settings endpoint (`PATCH` on a setting key) cannot write an invalid
      `default_event_type_id`: it either validates the value by the same rules or
      refuses that key. The plan says which, and the settings screen does not offer a
      free-text box for it.
- [ ] Choosing a default writes one audit entry, as it does today.
- [ ] The admin API and the Event types screen behave as before: a list response still
      says which type is the default, now derived from the setting, so the screen and
      the editor's pre-selection need no behavior change.
- [ ] `PRD.md`, the `AGENTS.md` migration range and the relevant `docs/` page reflect
      this.

## Notes

- The `settings` table is `key`, `value`, `updated_at` (migration `000004`).
- Do not reopen `#0613`. Its record describes what was done and why.
- Trade-off the user accepted: the database previously enforced one enabled default on
  its own. A setting holds a text id, so that guarantee moves to the application, and a
  hand-written `UPDATE` could break it. Reading the default must fail clearly, not
  silently pick another type, if the setting is missing or names no row.
