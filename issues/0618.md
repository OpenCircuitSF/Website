## Resolution notes

> 🟢 Resolved 2026-11-04 — The default event type now lives in `settings.default_event_type_id`, the column, check and index are gone, and the store's locking keeps the setting naming an existing, enabled type.

## Description

`#0613` marks the default event type with `event_types.is_default`. The user's
decision (2026-11-04) is that defaults belong in the existing `settings` table
instead: one value for the default event type, and, through `#0617`, one for the
default location. Move the event type default there and remove the column, so the
two defaults work the same way. What an admin sees does not change.

## Root cause

`#0613` stored the default on the type's own row, so it was a schema-enforced flag
rather than a value in `settings`, where the user wants every default to live.

## Fix

Followed the plan: migration `000047`, the new `internal/defaults` package, locking
in `internal/eventtypes` (setting, then row), the named error in `internal/workshops`,
the refusal in `PATCH /admin/settings`, and the 409 mappings.

Deviations from the plan, all from one thing it did not anticipate: `000047` is the
first migration to drop a column.

- **`internal/testdb/schema_check.go`** refused to run at all on a `DROP COLUMN`, which
  failed every DB-backed package at startup. It now retires a column dropped by one
  plain single-column statement. `IF EXISTS`, `CASCADE`, several clauses in one
  statement, `DROP TABLE` and `RENAME` are still refused. The test that pinned the old
  refusal was renamed `TestExpectedObjectsFromFiles_RetiresPlainDropColumn`, and the
  still-refused shapes were added to `TestExpectedObjectsFromFiles_RefusesDropTableAndRename`.
  The reviewer should look at this one; it changes a guard's premise.
- **`internal/db/prd_index_parity_test.go`**: `liveColumnsFromMigrations` replayed only
  additions, so it demanded `is_default` stay in the PRD. It now replays drops, pinned by
  `TestLiveColumnsRetireADroppedColumn`.
- The workshops 409 test lives in `admin_event_types_test.go`, beside the
  `removeDefaultSetting` helper it uses, not in the workshops test file.
- The mutation proof swapped the `defaults.Lock` calls for an unlocked read. Commenting
  them out, as the plan said, would not compile, because their result is used.
- Added `Keys`-driven `seedsManagedDefault` as a named helper for step 9's skip.

## Gotchas

- With a missing setting, saving a type that is already disabled is refused too, even for a
  rename, because `Update` takes the lock whenever `enabled` is false. Choosing a default
  clears it. This follows the plan's wording.
- `TestMigration000047FailsWithNoDefault` aborts its transaction on purpose; only rollback
  follows it.
- Once `000047` is applied, the binary-only rollback in `docs/deployment.md` is not enough
  to go back to a build that reads `is_default`: that build's event type queries fail until
  `migrate down 1` also runs. Between `migrate up` and the restart, an already-running build
  of that kind fails the same way.

## Plan

Written 2026-11-04 against the tree at `6b278dd5`.

**Decisions this plan makes**

- **The generic endpoint refuses the key.** `PATCH /admin/settings` with
  `default_event_type_id` answers 400 and writes nothing. It does not validate
  instead, because `validSettingValue` is a pure shape check and a check made there
  could not hold the locks that make the rule true: a validated write could still
  race a disable. Refusing also keeps the audit trail to one action,
  `event_type.default_changed`, rather than two ways of recording one change.
- **The settings screen needs no change.** `web/src/views/Admin.svelte` only reads
  `registrations_enabled` and `physical_address` by key and has no loop over
  `settings`, so the new row is never rendered. `GET /admin/settings` keeps listing
  it. A test pins the absence of a field.
- **Server settings is not involved.** `internal/serversettings` and
  `server_setting_values` hold environment-backed operational values with a key
  check. This row goes in plain `settings`, as the user decided.
- **One serialization point.** Every path that could break the rule takes
  `SELECT ... FROM settings WHERE key = 'default_event_type_id' FOR UPDATE` first,
  and then touches the `event_types` row. The order is always setting, then type, so
  the paths cannot deadlock.
- **A broken setting fails closed and can be repaired.** A missing, non-numeric,
  dangling or disabled-type setting makes `event_types_default_id()` raise an error
  naming the key. It never picks another type. Disabling or deleting a type while
  the setting is missing or unparseable is refused, because the store cannot tell
  whether that type is the default. Choosing a default with "Make default" writes the
  row back, so the screen is the repair path. The list keeps loading so that the
  admin can reach that button.

**Approach**

1. **Up migration**, in this order:

   ```sql
   INSERT INTO settings (key, value, updated_at)
   VALUES ('default_event_type_id', (SELECT id::text FROM event_types WHERE is_default), now());

   CREATE OR REPLACE FUNCTION event_types_default_id() RETURNS BIGINT LANGUAGE plpgsql STABLE AS $$
   DECLARE
       raw TEXT;
       resolved BIGINT;
   BEGIN
       SELECT value INTO raw FROM settings WHERE key = 'default_event_type_id';
       IF raw IS NULL THEN
           RAISE EXCEPTION 'settings.default_event_type_id is missing' USING ERRCODE = 'OCDEF';
       END IF;
       SELECT id INTO resolved FROM event_types WHERE id::text = raw AND enabled;
       IF resolved IS NULL THEN
           RAISE EXCEPTION 'settings.default_event_type_id (%) names no enabled event type', raw
               USING ERRCODE = 'OCDEF';
       END IF;
       RETURN resolved;
   END $$;

   ALTER TABLE event_types DROP CONSTRAINT event_types_default_enabled;
   DROP INDEX event_types_one_default;
   ALTER TABLE event_types DROP COLUMN is_default;
   ```

   With no default row the subquery is NULL, and `settings.value`'s `NOT NULL` fails
   the migration, which is the right outcome. Use `VALUES` as shown, with no `ON
   CONFLICT`. Comparing `id::text = raw` avoids a cast error on a non-numeric value.
   `CREATE OR REPLACE` keeps the function's OID, so `workshops.event_type_id`'s
   column default keeps working.

2. **Down migration:** add `is_default BOOLEAN NOT NULL DEFAULT FALSE`; set it `TRUE`
   where `id::text` equals the setting; a `DO` block raises if no row is now marked;
   re-add `event_types_default_enabled` and `event_types_one_default` with the
   definitions from `000045`; `CREATE OR REPLACE` the function back to its `000045`
   SQL body; delete the settings row. The column comes back last in column order
   instead of in the middle. Every query names its columns, so this has no effect.

3. **`internal/defaults`**, the piece for `#0617`. Its doc comment explains that a
   default held in `settings` has no foreign key, and that the owning store enforces
   the rules by locking through this package.

   ```go
   const KeyEventType = "default_event_type_id"
   var ErrUnset = errors.New("defaults: setting is missing or is not a valid id")
   func Keys() []string                 // every key this package manages
   func IsManaged(key string) bool
   func Lock(ctx context.Context, tx pgx.Tx, key string) (int64, error)
   func Write(ctx context.Context, tx pgx.Tx, key string, id int64) error
   ```

   `Lock` runs `SELECT value FROM settings WHERE key = $1 FOR UPDATE`, and returns
   `ErrUnset` for no row or a value that does not round-trip through
   `strconv.ParseInt` and `FormatInt` (so `"01"` and `" 1"` are refused, matching the
   SQL function's text comparison). Split the parse into an unexported `parseID` so it
   can be unit tested. `Write` is `INSERT ... ON CONFLICT (key) DO UPDATE SET value =
   EXCLUDED.value, updated_at = now()`, so it repairs a missing row. `#0617` adds one
   constant and one entry in `Keys`, and gets the handler refusal and the test reset
   below for free.

4. **`internal/eventtypes/store.go`**
   - Keep `EventType.IsDefault`. Change `eventTypeColumns` so the flag is derived:
     `id, slug, name, enabled, (enabled AND COALESCE(id::text = (SELECT value FROM
     settings WHERE key = 'default_event_type_id'), FALSE)) AS is_default, sort_order,
     created_at`. Build the key from `defaults.KeyEventType`. This works in the
     `SELECT`s and in each `RETURNING`.
   - `Update`: when `enabled` is false, run in a transaction. Call `defaults.Lock`,
     return its `ErrUnset` wrapped with `%w`, and return `ErrIsDefault` if the locked
     id equals `id`. Then run the existing `UPDATE`. When `enabled` is true, no lock is
     needed; keep it a single statement so a rename works even with a broken setting.
     Remove the `event_types_default_enabled` case and rewrite the doc comment.
   - `SetDefault`: replace the lock-all-rows and two-`UPDATE` body with: `defaults.Lock`
     (ignore `ErrUnset`, because this is the repair path); `SELECT enabled FROM
     event_types WHERE id = $1 FOR UPDATE`, returning `ErrNotFound` or `ErrDisabled` as

   - `Delete`: call `defaults.Lock` first and return a wrapped `ErrUnset`; lock the row

      the setting naming a disabled or deleted type. Tests cover the concurrent case.

## Notes

- The `settings` table is `key`, `value`, `updated_at` (migration `000004`).
- Do not reopen `#0613`. Its record describes what was done and why.
- Trade-off the user accepted: the database previously enforced one enabled default on
  its own. A setting holds a text id, so that guarantee moves to the application, and a
  hand-written `UPDATE` could break it. Reading the default must fail clearly, not
  silently pick another type, if the setting is missing or names no row.
