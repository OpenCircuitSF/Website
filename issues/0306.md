## Description

`#0299` tightened the whole-panel-swap hatch and moved five sites into
`KNOWN_STABLE_BRANCH_SITES`. Measured by its review:

| | before | after |
|---|---|---|
| whole-panel-swap targets | 21 | **16** |
| named stable-branch entries | **7** | **12** |
| unchecked | 0 | 0 |

The tightening is real — deleting the five new entries makes the guard flag
exactly those five sites, which passed silently under the old rule.

**But by `#0299`'s own recursive framing, the stable-branch hatch is now the
next-loosest load-bearing mechanism**, and its entire validation is a
human-written sentence. Each entry asserts its site is "unconditionally rendered
inside a large, stable, multi-purpose branch". Nothing checks that.

The pattern each widening has followed: `#0242` → `#0286` closed the sole-content
gap → `#0299` closed the unrelated-modal gap → this. Each pass promotes the next
mechanism to carrying the weight.

## The claim is partly machine-checkable

`#0286` removed `isGoverningBranchDynamic` as dead code once every in-branch site
ran the same checks. That predicate — a significant-node count of the governing
branch — is close to the property these entries assert. **Reintroduce it as a
validator of allowlist entries rather than as a gate on scanning.**

An entry claiming a large stable branch can then be checked against one, instead
of being believed.

## Acceptance criteria

1. Each `KNOWN_STABLE_BRANCH_SITES` entry is validated structurally: its site
   must genuinely sit unconditionally within a governing branch that measures as
   large and multi-purpose, by a stated metric.
2. **Measure whether all 12 current entries pass non-trivially**, and report the
   figures. An entry that only passes because the threshold was chosen to admit
   it is not validated. If any fails, fix the site or say why the entry stands.
3. The metric is justified in a comment with its number, not left implicit —
   and the threshold must not be fitted to today's twelve entries. State what a
   real violation would measure.
4. Prove it fires: a fixture whose site sits in a small, single-purpose branch
   must fail even with an entry present.
5. `#0280`'s justification rule and `#0298`'s unscanned-file rule both still
   apply to these entries — the structural check is in addition to them, not
   instead. A reason string stays required.
6. Say what your change promotes to next-loosest, and record the re-measured
   tally in the table form above so the next pass starts from a measurement.
7. `ISSUE=NNNN scripts/check.sh web` passes; the `'../**/*.svelte'` glob is not
   narrowed and `filesScanned >= 35` still fails closed.

## A correction to fold in

`#0299`'s review measured one loose clause worth fixing while here:
`KNOWN_STABLE_BRANCH_REASON_MAIN_FORM` claims the two `WorkshopEditor.svelte`
sites rest on "the same stable branch" as the `Rendering preview…`/`previewStale`
entries. They do not — those two sit deeper, inside `{#if previewOpen}`@448 and
`{#if hasPreviewContent}`@454, not directly in `{#if workshop}`@406. The
load-bearing half of the reason is correct; only the comparison clause is loose.
Correct it under `issues/Issues.md`'s correction convention.
