## The claim is partly machine-checkable

`#0286` removed `isGoverningBranchDynamic` as dead code once every in-branch site
ran the same checks. That predicate — a significant-node count of the governing
branch — is close to the property these entries assert. **Reintroduce it as a
validator of allowlist entries rather than as a gate on scanning.**

An entry claiming a large stable branch can then be checked against one, instead
of being believed.

## Root cause

`KNOWN_STABLE_BRANCH_SITES` entries asserted "unconditionally rendered
inside a large, stable, multi-purpose branch" in a `reason` string that
nothing checked against the actual AST. Matching on `file`+`rawSource`
proved the entry named a real site; it proved nothing about whether the
claim itself was true.

## Fix

- Added `elementCountInSubtree` (counts `RegularElement` nodes anywhere in
  a branch's subtree, crossing further-nested `{#if}/{#each}/{#await}/
  {#key}` inside it) and `KNOWN_STABLE_BRANCH_MIN_ELEMENT_COUNT = 8`,
  justified in its own comment against the guard's existing 3-element
  forked-branch decoy fixture (more than double it, real margin) —
  independent of what the twelve then-current entries happened to
  measure, per criterion 3.
- `checkFile`'s stable-branch hatch now runs this check on every entry
  that MATCHES a site: a branch under the floor is a new, distinct
  violation ("not structurally supported"), not silently accepted. The
  entry is still marked "used" (not reported stale) since it did name a
  real site — matching alone is just no longer sufficient.
- Measured all twelve then-current entries (criterion 2): `settingsNotice
  14, addressNotice 14, newSlugInvalid 57, createSubNotice 156,

### Is 8 fitted? No — but it is under-determined, and that is fine

The honest answer, stated plainly because criterion 3 turns on it:

- **A fitted threshold would be 10 or 11** (just under the minimum entry, 11).
  It is not that; 8 sits three below the floor of the admitted set.
- **The decisive evidence is behavioural, not arithmetic.** The one entry the
  threshold actually adjudicated measured **1**. Fitting the threshold to the
  entry set would have meant a floor of 1 — i.e. abandoning the metric. The
  implementer fixed the site instead. That is the proof criterion 3 wanted and
  no comment could supply.
- **What 4 or 10 would change: nothing, today.** Every threshold in **4–11**
  produces the identical split — all twelve entries (min 11) pass, the guard's
  3-element decoy fixture fails, and pre-fix `previewStale` (1) fails. 12 would
  newly fail `Pending.svelte`'s `resendNotice`; 3 would newly admit the decoy.
  So the number 8 is justified only to within that band, and the stated
  justification ("more than double the 3-element decoy — real margin, not one
  more than 3") picks a point inside it by judgement rather than derivation.
  That is what a non-fitted threshold looks like: anchored to an artifact that
  exists independently of the entries, with the residual choice disclosed.
- Criterion 3's "state what a real violation would measure" **is** answered in
  the comment: the decoy shape, 3 elements — a couple of trivial siblings around
  the live region.

**Margin (criterion 2).** Smallest is `Pending.svelte`'s 11 vs 8. I judge that
comfortable, for a reason independent of the percentage: if an ordinary edit did
drop that branch from 11 to 7, the branch would genuinely have stopped being
"large, multi-purpose", so the guard firing would be *correct*, not a false
positive — and it fires as a loud test failure, never a silent pass. The metric
degrades in the safe direction.

**A property worth recording for the next pass**: because `collectSites` binds
each site to its **nearest** enclosing branch, this check also enforces the
"unconditionally rendered" half of the claim, not just the "large" half. Wrap an
allowlisted site in its own small `{#if}` and its governing branch becomes that
`{#if}` — small count, violation. That is exactly how `previewStale` was caught,
and it makes the element count a better proxy than its own comment claims.

### The `previewStale` hoist — the part that changed rendering

Old render condition: `previewOpen && !previewLoading && !previewError &&
hasPreviewContent && previewStale`.
New: `previewOpen && hasPreviewContent && previewStale`, on a node that is now
always mounted (empty text otherwise).

Walked the state space against the script (`WorkshopEditor.svelte:156–186`,
`288–306`):

| state | old | new | verdict |
|---|---|---|---|
| preview closed | element absent | element present, text `''` | equivalent output; adds `.text-warn`'s `margin-top: var(--space-1)` on a zero-height `<p>`, the same cosmetic cost `saveNotice`/`unsavedInterestsHint` already pay |
| `previewError` set | element absent | `refreshPreview`'s `catch` sets `previewHtml = ''`, so `hasPreviewContent` is false → text `''` | **cannot show a stale warning over an error** — but only because of an implicit coupling (`previewError !== null ⇒ previewHtml === ''`), not because the condition names it |
| no preview content yet | element absent | text `''` | equivalent |
| `previewLoading` with prior content | element absent | *could* show the warning alongside "Rendering preview…" | **unreachable today**: the only `refreshPreview` call that can run with `previewOpen === true` is `save()`'s, and `save()` assigns `workshop` and `fields` from the saved record *before* awaiting it, so `previewStale` is already false. On `load()`, `previewOpen` is still `false`. |
| open, stale, content present | warning | warning | unchanged, and now announced from a node that was already mounted — strictly better for `role="status"`, which is #0063's whole point |

So: the element renders in states it previously did not, but it renders **empty**
in all of them, and its content is correct in every reachable state. The claim
that it now matches `saveNotice`/`unsavedInterestsHint`'s placement is verified,
not asserted: all three measure **78**, i.e. the same `{:else if workshop}`
branch, and `saveNotice`(:594)/`unsavedInterestsHint`(:662) use the identical
always-mounted-with-`''` shape.

The one thing to keep in mind: the error state is excluded *transitively*. If a
future change stops clearing `previewHtml` on error, the stale warning would
appear over the error message. Low risk, no code change asked for here.

No test mounts `WorkshopEditor.svelte`, so nothing in the suite covers this
render — the implementer disclosed exactly that, which is the right disclosure.
