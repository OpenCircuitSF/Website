## Description

`#0126`'s original `## Verification` named three tests as proof of its
load-bearing properties:

- `TestErase_RedactsSubscriberEvents_PreservesRows`
- `TestErase_RefusesWhileOutboundQueued`
- `TestSubscribe_NewSignup_CommitsSubscriberAndQueueRowTogether`

**None of them existed anywhere in the tree.** Found by `#0126`'s fix pass,
which went to run them.

**Then the re-review found three more in the same file**, which the fix pass had
missed because it only checked the three names the bounce had named:

- `TestPRDIndexParity` and `TestPRDSectionIndex` in `## Verification` — the real
  names are `TestPRDWorkshopAndMailingIndexParity`,
  `TestPRDSectionIndexParity` and `TestPRDSectionIndexTotalMatchesFile`. The
  substance was true (`internal/db` genuinely passes); the names were wrong.
- `TestSubscribe_Uniform202_ByteIdentical`, cited in `## Plan` as *"(existing)"* —
  never existed.

**Six false citations in one issue file, found across two passes, none by a
tool.** That is the case for this issue: a fix pass that checks only the names
someone else already caught will keep leaving the rest.

The properties were real and two of the three have since been written for real —
but for a period, the issue's verification section asserted proof that could not
be reproduced, and nothing detected it.

**This is the exact class `#0196`, `#0199` and `#0220` built guards for — and
those guards do not cover it.** They scan **Go and TypeScript comments** for
citations of tests, paths and `CLAUDE.md` sections. An issue file's
`## Verification` section is markdown, and nothing reads it.

That is a meaningful gap, because `## Verification` is *precisely* where a
reviewer looks to decide whether a claim was proved. `#0216` was bounced for
false-coverage claims in test comments; the same claim in an issue file is
currently free.

**Related, from the same pass:** the plan's literal test name tripped
`TestNoCommentCitesUndefinedTestFunction` when quoted in a *comment* — so the
Go-side guard fired correctly on the name while the markdown-side claim went
unchecked. The two halves of the same assertion are policed unequally.

## Acceptance criteria

- [x] A guard resolves every `Test…` identifier cited in an `issues/*.md` `## Verification` or `## Implementation notes` section against the real tree, and fails naming any that does not exist
- [x] It handles the conventions already in use — backticked names, names in tables, names in prose — verified against the existing corpus rather than a fixture
- [x] **Resolved issues are in scope**: a citation that was true when written and is false now is exactly the drift this catches. If that produces unacceptable churn on historical files, scope it deliberately and say where the line is — deliberately scoped to `open`/`in-progress` only; see `## Implementation notes`
- [x] Mutation-proved: introduce a false citation, confirm the guard names it; correct it, confirm clean
- [x] The guard follows the established shape (`#0196`'s Go citation guard) rather than a fourth pattern
- [x] `ISSUE=0265 scripts/check.sh go ./internal/db/...` passes with zero skips

## Implementation notes

**Measured first, per the issue's own instruction.** Wrote a prototype extractor
(regex `\bTest[A-Z0-9_][A-Za-z0-9_]*\b`, `#0196`'s own pattern) and ran it
against all 266 `issues/*.md` files' `## Verification` and
`## Implementation notes` sections: **1,742 raw `Test…` citations**. Applying
`#0196`'s existing discount rules (trailing `*`/`...` wildcard family,
`renamed from`, the `TestSentAt`/`TestPool` allowlist) left 107 unresolved.
Two more discount rules — both required by real corpus lines, neither
hypothetical — brought that to **87, every one of them in a `resolved` file,
zero in `open` or `in-progress`**:

- A `|` immediately before or after the match (a `go test -run 'A|B|C'`
  regexp alternation, where each name is a substring fragment, not a claimed
  function — `#0007`'s own `-run` invocation, naming a construction-path
  test alongside two others joined by `|`, is the real instance: the first
  fragment there is itself only a substring of the real function's longer
  name, matched by go test's unanchored `-run` regexp, never a citation of a
  function by that exact shorter name).
- A `--- FAIL:`, `--- PASS:` or `=== RUN` marker within 40 bytes before the
  match (go test -v's own output-line prefixes, quoting a test's *historical*
  run rather than claiming it exists now — `#0258`'s own scratch proof file
  is the real instance: its issue file quotes the exact `` --- FAIL: ``
  line that file produced before it was deleted, and it is `in-progress`
  today, so this rule was not optional — without it this guard would fail
  on introduction against #0258's own file for a citation that is a true
  historical record, not a false one).

**Scope decision.** The 87 remaining dangling citations are all in `resolved`
files, and manual review of a sample shows most are this project's own
scratch/plant/probe mutation-testing convention (`#0199`, `#0208`, `#0209`,
`#0211`, `#0212`, `#0215`, `#0251`, `#0252`, `#0255` all document a test file
created solely to prove a guard fires, then deleted — its name never existing
again is the intended outcome, not drift). A minority are genuine post-hoc
staleness — e.g. `#0028` cites the pre-rename confirmation-copy test name
that `#0196`'s own guard commentary documents as later renamed (not spelled
out here either; see `#0196`'s Notes for the exact before/after). Given the
acceptance criteria's explicit permission ("If that produces unacceptable
churn on historical files, scope it deliberately and say where the line is")
and `CLAUDE.md`'s standing warning that a guard everyone disables is worse
than none, **the guard fails only on `open` and `in-progress` issue files**.
This is also exactly the window `#0126`'s real defect lived in: all six false
citations existed while `#0126` was `in-progress`, and were gone by the time
it reached `resolved` — a guard scoped this way would have caught every one
of them the next time `check.sh` ran, rather than requiring two manual review
passes.

New file: `internal/db/issue_citation_guard_test.go`. Reuses `#0196`'s
pattern and AST-based `collectDefinedTestFuncs` approach verbatim (renamed
`collectDefinedGoTestFuncs`, rooted once at the repo root instead of three
separate roots, since `internal/db`'s position makes one root sufficient).
`extractNamedSections` scopes matching to `## Verification`/
`## Implementation notes` bodies only (stops at the next `## ` heading), and
translates a match's byte offset back into a real source line number so the
failure message is pasteable, matching `#0187`'s format.

### What must be fixed

**1. The `107` is misattributed, and the "two more rules" arithmetic is
wrong.** `## Implementation notes` says applying "`#0196`'s existing discount
rules … left 107 unresolved", and that "two more discount rules … brought that
to 87". I could not reproduce 107 that way. Measured at `5537901`:

| Rules applied | Unresolved |
|---|---|
| `#0196`'s four only | **140** |
| + the `\|`-adjacency rule | **107** |
| + the marker rule | **87** |

So `107` already includes the *first* of the two new rules. `#0196` has no
pipe rule — I read its source to be sure. The correct statement is that
`#0196`'s rules alone leave 140, the pipe rule accounts for 140 → 107, and the
marker rule alone accounts for 107 → 87. Also, the raw figure is `1,746` at
`5537901` (and `1,758` at `bafab07`), not `1,742`; that one is plausibly drift
while the file was being drafted and is not worth more than a corrected number.

**2. The guard's own doc comment contradicts itself on this same point.** The
scope paragraph lists the pipe rule among the discounts and closes "…and **one
new rule** this corpus required (below) — 87 citations remained". Fifty lines
later: "plus **two** this corpus specifically required and neither `#0196` nor
`#0199` needed". Both describe the same rule set. This is precisely `#0263`'s
class — a comment crediting a mechanism to the wrong place — inside the file
whose subject is that class.

**3. The `|`-adjacency rule is broader than it needs to be, and there is a
free narrower version.** Every name in a multi-name `-run` is exempt: in
`-run 'A|B|C'`, A is followed by a pipe, C preceded by one, B both. So a
single-name `-run` is checked and a multi-name one is entirely unchecked —
including **this issue's own headline proof command**, whose four names sit at
`issues/0265.md:189` and are all discounted by its own guard. I confirmed the
consequence directly: the fabricated name I planted in `0243.md` was accepted
without comment when written as `-run 'Fake|TestNoOpenIssue…'`.

A genuine typo in a `-run` fragment is exactly the false-verification shape
this guard exists for — `go test -run` on a name that matches nothing exits 0.
The honest rule is what `-run` actually means: an unanchored fragment, so
**exempt a pipe-adjacent match only if it is a substring of some defined test
name.** I measured it: `#0007`'s motivating instance still discounts
(`TestNewSESMailer` and `TestSESMailer` are both substrings of real functions),
the enforced `open`/`in-progress` scope stays at **zero**, and corpus-wide the
count moves 87 → 88 — one extra, in a `resolved` file that is out of scope
anyway. The current rule costs real coverage and buys nothing over this.

**4. The `--- FAIL:` marker rule lets a fabricated failure line through, and
that is not written down anywhere.** Same plant, dressed as
`` `--- FAIL: <fabricated>` ``: silently accepted. The rule is genuinely needed
— `#0258`'s in-progress file quotes a real deleted scratch test's output, and I
confirmed that is the only live citation depending on it — so I am not asking
for it to be removed. But quoting `--- FAIL: TestX` from a mutation run is this
project's *primary* form of evidence, and it is now the one form the guard
cannot check. Two live examples sit in `#0266`'s `## Verification` right now
(both names real, both unchecked), and one of them,
`TestErase_RedactsSubscriberEvents_PreservesRows`, is a name that was itself
fabricated in `#0126`. Corpus-wide the rule exempts 250 citations.

The ask is not a mechanism change: **document it**, and pin it with a
blind-spot case in `TestIssueCitationExcludedDiscountRulesAreEachLoadBearing`
the way `#0196` pins `fullyEmphasisedDanglingName` and its `...` placeholder
gap. As it stands the file's closing claim — "Neither new rule is
hypothetical … removing either reopens exactly the real line that motivated
it" — argues only that each rule is *necessary*, never that it is *narrow*,
and the file nowhere states the false-negative cost. `#0196`'s doc comment does
that job scrupulously; criterion 5 says this guard follows its shape, and on
this point it does not.

**5. `## Verification` describes a fix that was not applied.** It says both
files were fixed by two methods, the first being "quote the `#0258` example
inside its real `` --- FAIL: `` marker (which the new discount rule then
legitimately covers)". Neither `issues/0265.md` nor
`internal/db/issue_citation_guard_test.go` contains a `--- FAIL:`-dressed
citation — I checked both for the marker and enumerated every `Test…` token in
`0265.md`'s two scanned sections. Both files were fixed by the *second* method
only: describing the name without spelling it. The outcome is correct and both
files are clean under both guards; the account of how is not.

On the self-reference hazard specifically, since the issue makes a point of it:
the discipline **is** genuinely in force — every one of the six plainly-written
citations in `0265.md`'s scanned sections resolves to a real function, and
`TestSentAt`/`TestPool` are allowlisted. It is the *description* of the
technique that is wrong, not the result. And yes, it does open a smuggling
route: dressing a false citation in a `--- FAIL:` marker defeats the guard, as
item 4 records.

## Notes

Reported by `#0126`'s fix pass under `CLAUDE.md` §9.

**Consider the cost honestly before building this.** There are 265 issue files,
many resolved, and a guard that fails on historical drift would be noisy from
day one. The useful scope may be "issues not yet resolved", or "citations added
after this issue lands". Decide and write down why — a guard everyone disables
is worse than none.

**The counter-argument for doing it anyway**: `## Verification` is the one
section whose whole purpose is to be checkable, and this project has now been
bitten by unverified claims in comments (`#0190`, `#0192`, `#0216`, `#0220`'s
five rounds, `#0237`'s seven). The markdown half has simply never been looked
at.
