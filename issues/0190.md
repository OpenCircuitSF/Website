## Description

`#0188` changed `adminSendErrorMessage`'s transport discriminator from
`strings.HasPrefix(err.Error(), sesWrapPrefix)` to
`errors.As(err, &opErr)` against `*smithy.OperationError`. Its phase-3 review
re-ran 21 boundary probes, confirmed every one lands where `#0185` established,
and passed the change. It also found three things worth fixing.

**1. The discriminator change is unguarded — this is the item with teeth.**
Reverting `errors.As` to the old `strings.HasPrefix` leaves **the whole package
green**. The two rows that moved under the new logic were caught only by the
reviewer's own hand-built probes, which do not live in the tree. So the tree
currently asserts nothing about a classification decision that was deliberately
changed.

The same fix closes a second defect: the new "nested one layer deeper" subtest's
comment claims an `awshttp.ResponseError` nesting that the case **does not
build** — it is structurally identical to the subtest above it. Two table rows
close both: `wrapSES(opErr(respErr(net.OpError)))` and `wrapSES(net.OpError)`.

This is the **fourth** appearance of the "a test guards its neighbour, and the
thing itself is unguarded" shape in this subsystem — see `#0171`, `#0182`,
`#0185`.

**2. Empty `ErrorMessage()` yields a dangling `": "`.** A modeled exception with
a nil/empty `Message` produces a bare `"MessageRejected: "`. This is reachable
from the real SDK: `awsRestjson1_deserializeDocumentMessageRejected` sets
`Message` only when the body carries `message`/`Message`, with no default. The
review ruled it acceptable — the actionable half (the code) is always present,
and the old behaviour in the same case was the same empty message with
scaffolding in front — but a fallback would finish it. (The fully degenerate
`": "` is **not** reachable: the generic path initialises
`errorCode := "UnknownError"; errorMessage := errorCode`.)

**3. `sesWrapPrefix` no longer has a job in production code.** Nothing outside
comments reads it — `ses_mailer.go` writes the literal
`"mailing: sending via SES: "` in three places and never references the
constant. Its only non-comment consumer is now `worker_test.go`, so the constant
and the literal can drift silently.

## Implementation notes

Two new table rows in `TestAdminSendErrorMessage_DiscriminatesPrefixedFromOwnErrors`
(`internal/mailing/worker_test.go`), built independently of `worker_test.go`'s
own `sesResponseError` helper — a helper the implementer wrote is not what
should prove the implementer's own discriminator swap:

- `wrapSES(opErr(respErr(net.OpError)))` — a genuine `*net.OpError` (dial
  failure) nested inside a hand-built `*awshttp.ResponseError` inside
  `*smithy.OperationError`, all inside `sesWrapPrefix`. Lands on
  `adminSendUnreachableMessage` under both the old and new discriminator (it
  is not the row that differs — see below), but it is the row the "nested one
  layer deeper" subtest's comment claimed to build and previously did not:
  that subtest was structurally identical to the bare-OperationError subtest
  above it (same `errors.New(...)` wrapped directly in `*smithy.OperationError`,
  no `ResponseError` layer at all). Rewrote the case to actually build the
  nesting the comment describes rather than rewrite the comment to match a
  shallower case.
- `wrapSES(net.OpError)` — `sesWrapPrefix` present, but the wrapped value is
  a bare `*net.OpError` with **no** `*smithy.OperationError` anywhere in the
  chain. This is the row that actually differs between the two
  discriminators: under the old `strings.HasPrefix(err.Error(), sesWrapPrefix)`
  check it silently landed on `adminSendUnreachableMessage` (prefix present
  was treated as sufficient evidence of an SDK transport failure); under the
  new `errors.As(err, &opErr)` check it is not an `*smithy.OperationError`, so
  it falls through to the catch-all and logs. Extended the table-test loop to
  assert a `wantLog bool` per case (fresh `bytes.Buffer` logger per subtest,
  replacing the shared `discardLogger()`) so this row pins both the returned
  string *and* that the catch-all actually fires — the acceptance criterion
  asked for the log line to be pinned, not just the text. Marked the existing
  "unrecognized unprefixed error" row `wantLog: true` too, since it already
  exercised the same catch-all and previously went unchecked on that axis.

**Mutation proof (criterion 1).** Copied `worker.go` aside first (§8a).
Reverted the transport branch from `errors.As(err, &opErr)` /
`if errors.As(err, &opErr) { return adminSendUnreachableMessage }` back to
`if strings.HasPrefix(err.Error(), sesWrapPrefix) { return
adminSendUnreachableMessage }` (dropping the now-unused `opErr` variable —
`smithy.APIError` is still referenced by the branch above it, so no import
changes were needed). Ran the full `internal/mailing` suite: exactly one test
failed, `TestAdminSendErrorMessage_DiscriminatesPrefixedFromOwnErrors`, and
within it exactly the one subtest the design predicts —
`SDK_transport_failure,_prefix_present_but_wraps_*net.OpError_directly_(no_*smithy.OperationError_at_all)`
— with both the wrong return value (`adminSendUnreachableMessage` instead of
`adminSendBuildFailureMessage`) and the wrong log outcome (`logged = false,
want wantLog true`) reported. All 20 other subtests in that table, plus every
other test in the package, still passed under the mutation — matching
`#0188`'s review table, which marked only this one row "changed by design".
Restored from the copy; `shasum -a 256` matched the pre-mutation file exactly,
and `git diff --stat -- internal/mailing/worker.go` after restoring showed
only my intended (non-mutation) changes.

**Criteria 2 and 3 (tidy-ups).** `adminSendErrorMessage`'s `smithy.APIError`
branch now returns bare `apiErr.ErrorCode()` when `apiErr.ErrorMessage()` is
empty, instead of concatenating to a dangling `"Code: "`. New test
`TestAdminSendErrorMessage_EmptyMessageHasNoDanglingSeparator` covers a nil
`Message`, an empty-string `Message`, and the production-shaped nesting.
`ses_mailer.go`'s three `fmt.Errorf("mailing: sending via SES: %w", …)` call

production consumer again and cannot drift from the literal silently; updated

### Is one distinguishing subtest enough? Not for the whole delta — and that is worth a follow-up

`#0188`'s table records **two** rows that moved when the discriminator changed,
not one:

| Moved row | Old (`HasPrefix`) | New (`errors.As`) | Guarded in the tree? |
|---|---|---|---|
| `wrapSES(net.OpError)` — prefix, no `OperationError` | unreachable | catch-all + log | **yes** — the new row |
| bare `opErr(credential failure)`, **no** prefix | catch-all + log | unreachable | **no** |

Re-derived rather than assumed. I rebuilt all 21 of `#0188`'s probes as an
independent table and re-ran the same mutation against them: **probes 07 and
21 both failed**, confirming the delta really is two rows wide. The committed
table contains a counterpart for 07 and none for 21 — every `OperationError`
row in it (`SDK transport/credential failure, bare OperationError` and the
rebuilt nested one) carries `sesWrapPrefix`, so neither can tell the two
implementations apart.

The practical consequence, measured: a **partial** revert —
`if errors.As(err, &opErr) && strings.HasPrefix(err.Error(), sesWrapPrefix)`,
which restores exactly the old classification for the unprefixed-`opErr` row
and nothing else — leaves the **entire package green**. So the tree now
asserts one direction of a decision that moves in two.

This does **not** fail the issue: criterion 1 asks that a revert turn *at
least one* test red (it does, loudly, on both axes), and criteria 2–3 name
exactly the two rows the implementer added — those were prescribed at filing
time by `#0188`'s reviewer, and the implementer built precisely them. The gap
is in the criteria, not in the work. Reported below for filing.

### The rebuilt "nested one layer deeper" case — chain unwrapped at runtime

Not read off the constructor and believed. I temporarily instrumented the
table loop to walk `errors.Unwrap` over each case's real `tc.err` and print
`reflect.Type` with full `PkgPath`, ran it, then restored `worker_test.go`
(`dba28cf6a3953025e84ba08a908ab703e5f049410297619261e254a452913a33`). The
rebuilt case's actual chain:

```
*fmt.wrapError
  -> *github.com/aws/smithy-go.OperationError
  -> *github.com/aws/aws-sdk-go-v2/aws/transport/http.ResponseError
  -> *net.OpError
  -> *errors.errorString
```

That is the shape the comment claims, with the `ResponseError` resolved to
`awshttp`'s and not smithy-go's lookalike of the same package name — the
`%T` rendering alone (`*http.ResponseError`) cannot tell those apart, which is
why I printed `PkgPath`. `awshttp.ResponseError`'s `Unwrap` is promoted from
the embedded `*smithyhttp.ResponseError`, so the chain steps straight from it
to the `*net.OpError`, exactly as the production-shaped `sesResponseError`
rows do (`… -> *http.ResponseError -> *types.MessageRejected`). And it is
genuinely distinct from the bare-`OperationError` row above it, whose chain is
`*fmt.wrapError -> *smithy.OperationError -> *errors.errorString` — the defect
`#0190` item 1 named is fixed, not papered over.

### Criterion 3 — the `%s%w` refactor, diffed rather than reasoned about

Two checks, because a format-string refactor is exactly where a lost space
hides.

**Static.** Extracted every `fmt.Errorf` literal from `0754920^`'s
`ses_mailer.go` and compared bytes: the old literal is
`"mailing: sending via SES: %w"`, and `sesWrapPrefix + "%w"` is the same 28
bytes. (The unrelated `"mailing: cannot construct SES mailer: missing %s"`
literal is untouched and was not converted.)

**Empirical.** Compared `fmt.Errorf("mailing: sending via SES: %w", inner)`
against `fmt.Errorf("%s%w", sesWrapPrefix, inner)` over six inners, asserting
equal strings, equal lengths, equal wrapper type, and preserved unwrapping:

| inner | produced string | identical |
|---|---|---|
| `*types.MessageRejected` | `mailing: sending via SES: MessageRejected: Email address is not verified` (72 B) | yes |
| `*types.TooManyRequestsException` | 81 B | yes |
| `context.DeadlineExceeded` | `mailing: sending via SES: context deadline exceeded` (51 B) | yes |
| `errors.New("100% of attempts failed: %s %w %d")` | 59 B — no verb re-interpretation | yes |
| `errors.New("")` | `mailing: sending via SES: ` (26 B) | yes |
| `*net.OpError` | 63 B | yes |

`%T` is `*fmt.wrapError` on both sides and `errors.Unwrap(new) == inner` in
every case, so `#0182`'s byte-identical property and `errors.Is`/`errors.As`
traversal are both intact. `sesWrapPrefix` now has three production consumers,
closing the drift path.
