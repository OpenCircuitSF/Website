## Description

`#0365`'s plan introduces `skipped` as a new terminal status for a message the
system **correctly withheld**. `outbox.Store.Counts` will not count it.

**That omission is deliberate in `#0365`**, and its reasoning is worth
preserving: `failed` is uncounted too, and extending `Counts` drags in
`admin_dashboard.go`, `types.ts` and the overview component — while
`internal/handlers` was under concurrent review. So the plan scoped it out.

But a terminal state nothing counts is invisible to the operator. The point of
`skipped` is that it is **not** a failure, so the right treatment is an
**informational figure that raises no warning** — unlike `abandoned`, whose
`counts.Abandoned > 0` check raises a permanent dashboard alarm
(see `#0378`).

## Depends on `#0365`

`skipped` does not exist until `#0365` lands migration `000027`. **Land it
first.** If `#0365` took a different route than the plan, re-scope or close this.

## Acceptance criteria

6. Per §5 name the specific tests that ran; the mailing subsystem needs
   Postgres. §8b: mutations use your own database, never a literal or seeded id.

## Root cause

`outbox.Store.Counts` (`internal/outbox/store.go`) was written before
`#0365` added `skipped`, and `#0365`'s plan deliberately scoped extending it
out (§11 of that issue's plan). Re-verified before changing anything
(criterion 5): `Counts`' `SELECT` only had `count(*) FILTER` clauses for
`queued`/`sending`/`sent`/`abandoned`, and
`internal/handlers/admin_dashboard.go`'s `Overview` only reads
`counts.Abandoned` for the `outbound_queue_abandoned` warning — nothing in
that logic references a skipped figure at all, confirming the omission was
real and the warning logic was genuinely untouched by it.

## Fix

Added a `Skipped int64` field to `outbox.Counts` and a fifth
`count(*) FILTER (WHERE status = 'skipped')` to its query. Added a matching
`Skipped int64 \`json:"skipped"\`` field to
`dashboardOutboundQueueView` and populated it from `counts.Skipped` in
`Overview` — on a **separate line** from the `outboundQueueAbandoned =
counts.Abandoned > 0` assignment, which is untouched and still reads only
`Abandoned` (criterion 2). Surfaced in the SPA: `web/src/lib/types.ts`'s
`DashboardOutboundQueue` gained a `skipped: number` field, and
`Dashboard.svelte`'s outbound-queue stat block gained one more plain `<li>`
alongside `queued`/`sending`/`sent`/`abandoned` — no CSS class, no `alert`
styling, the same informational treatment every other figure in that list
already gets (criterion 4; the "Needs attention" alert region is a
structurally separate part of the template driven by `dashboard.ts`'s
`buildWarnings`, which was not touched and does not read `skipped`).

**`failed` decision (criterion 3): explicitly NOT counted in this pass.**
`grep -rn "StatusFailed" internal --include="*.go"` shows `outbox.StatusFailed`
is declared (`internal/outbox/store.go`, marked "reserved; unused") but no
producer anywhere in the codebase ever sets `outbound_queue.status =
'failed'` — every other `StatusFailed` hit in the codebase is
`mailing.CampaignStatusFailed`, an unrelated status on a different table
(`email_campaigns`). Counting a status with zero producers would add a field
that always reports 0, which no test can meaningfully exercise, and would
pre-empt how a future "failed" terminal state ought to be counted or alerted
on before whatever issue eventually gives it a first producer decides what
it means. Documented directly in `Counts`' doc comment, not only here.

### The `failed` decision — the enumeration redone, not inherited

This is the judgement call in the issue, and the implementer's reasoning
inverts if a single missed producer exists. Checked four ways, deliberately
not just by repeating its `grep`:

1. **`StatusFailed` across all Go** — declared once in
   `internal/outbox/store.go` (`"failed" // reserved; unused`), and every
   other hit in the tree is `mailing.CampaignStatusFailed`, a status on
   `email_campaigns`, plus its tests. No assignment to an `outbound_queue`
   status parameter anywhere.
2. **Every write to the table, not every mention of the constant.** Grepped
   `UPDATE outbound_queue` / `INSERT INTO outbound_queue`: exactly ten
   statements, all in `internal/outbox/store.go`
   (`Enqueue`/`EnqueueTx`, `ClaimDue`, `ClaimRow`, `MarkSent`,
   `MarkSkipped`, `MarkDone`, `CancelQueuedTx`, `MarkRetryOrAbandon`,
   `Release`, `OrphanSweep`). Every one binds its status as a **parameter**
   holding a `Status*` constant — none builds a status by concatenation,
   none writes a bare literal. So the constant-level grep is not missing a
   raw SQL string.
3. **Every `SET status` in the repo.** The only `'failed'` literals are
   `internal/mailing/worker_store.go`'s three, and all three target
   `email_sends` or `email_campaigns` — a different table, as claimed.
4. **The schema.** `migrations/000021` declares
   `status TEXT NOT NULL DEFAULT 'queued'` and lists `'failed'` in the CHECK
   only, with its own comment saying it is reserved "for a future use rather
   than invented one here"; `000027` widens that CHECK for `'skipped'` and
   leaves the default alone. No migration writes `'failed'`.

The premise holds: `outbound_queue.status = 'failed'` has zero producers and
no default path. Counting it would report a permanent, unexercisable zero,
and the decision is correctly recorded in `Counts`' own doc comment rather
than only in this issue.

### Criterion 2 — it raises no warning

Verified structurally, not by assertion. `Overview`'s
`outboundQueueAbandoned = counts.Abandoned > 0` is byte-unchanged (a comment
was added above it, not to it), the new `Skipped` is assigned on its own
line into the view struct, and `web/src/lib/dashboard.ts` contains exactly
one reference to the whole subject — `if (w.outbound_queue_abandoned)` — and
no occurrence of `skipped` at all. In the template the new `<li>` sits in the
"Outbound queue" stat block, which is a separate `{#if
overview.outbound_queue}` region from the `{#if warnings.length > 0}`
"Needs attention" block; the `alert` class is applied only by
`{#if w.alert}` inside the latter. No CSS was added.

### Criterion 4 — which claims rest on jsdom, and whether that is the right scope

The SPA assertion is `web/src/views/admin/Dashboard.behavior.test.ts`'s
*"renders the skipped figure as informational text, not an alert, and raises
no warning"*, mounted with `@testing-library/svelte`'s `render()` under the
`// @vitest-environment jsdom` pragma. **Three claims rest on that mount, and
only these three:** that the rendered node is an `LI`; that its `classList`
does not contain `alert`; and that the "Needs attention" region's
`textContent` matches neither `/skipped/i` nor `/outbound queue/i`.

That is the right scope, and it is the scope the implementer claimed. Tag
name, class membership and text content are exactly what jsdom models
faithfully; CLAUDE.md §1's caveat bites on layout, visibility, focus order
and IME, and this test asserts none of those. It does **not** prove a human
reads the figure as calm — the implementer says so explicitly in
`## Verification`, which is the correct disclosure. The server-side half of
"raises no warning" does not rest on jsdom at all: it is
`TestAdminDashboardOverview_CancelledInviteSkippedRaisesNoWarning`, against
real Postgres.

One deliberate fixture asymmetry, judged acceptable: the payload carries
`abandoned: 1` while `warnings.outbound_queue_abandoned` is forced `false`,
which a real server would not emit. The comment explains why — it isolates
the assertion to "a nonzero `skipped` does not itself produce a warning
row", which is precisely the claim, and the realistic coupling is proved
server-side instead.
