## Description

After `#0519`, a slow page load shows the server fallback content, then `App.svelte`'s `Loading…` state while `/api/me` answers, then the real page. `#0519`'s plan records this flash rather than hiding it.

## Acceptance criteria

1. On public routes, the server content stays visible until the SPA can render the route, with no intermediate `Loading…` screen.
2. Admin and account routes, which genuinely need `/api/me`, keep correct gating.
3. No duplicated content and exactly one `<h1>` at every stage (`#0519` criterion 4).
4. Verified in a real browser with a throttled network, not only jsdom.
5. `scripts/check.sh web` passes.

## Verification (implementation, 2026-09-14 — awaiting review)

- jsdom: `web/src/lib/AppLoading.test.ts` mounts the real App — public routes (/, /about) render their view while `/api/me` never settles, no App-level Loading…; admin keeps the gate until it answers; exactly one `<h1>` post-mount. `router.test.ts` pins `needsSessionGate`. `npm run check` + full `npm test` (4162) ok at `836ffe3`.
- Real browser (criterion 4): headless Chrome for Testing (playwright-core, cached ms-playwright chromium-1234) behind a 2.5s-delayed `/api/me` latency proxy, MutationObserver recording any App-level Loading… element and h1 count. POST-FIX (`836ffe3` build): `loadingSeen:false, maxH1:1`. PRE-FIX control (HEAD~1 build, same harness): `loadingSeen:true` — the harness demonstrably catches the flash it exists to catch. Harness in `.scratch/0521-browser/` (removed worktrees, binaries in /tmp).
- Gated set (recorded): admin, account, register-verify, recover-verify (`SESSION_GATED_ROUTES`). Home's own "Next up" fetch has an in-section Loading… state of its own — that is view-local data fetching, not the inter-stage flash this issue names; left as is.
