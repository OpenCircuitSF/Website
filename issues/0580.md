## Description

Brennan, 2026-10-17: "Run a local server and have a sonnet subagent use the
new admin screens to capture screenshots of everything. Create a fictional
workshop for LED Programming. You will need to mock both Bluesky and
Mastodon so you can use some features. Make sure we have the ability to
create mocks for this purpose in a development server."

The outreach features can't be exercised locally end to end today. Posting,
Test connection and engagement tracking need Bluesky and Mastodon, and links
need ShortLinks. The tests use `httptest` fakes, but there's nothing a
running dev server can point at.

## Acceptance criteria

- [ ] **A mock server** (for example `cmd/devmocks`, or a `devmocks`
      subcommand of the binary, whichever is simpler) serves, on one
      loopback port with path prefixes or on separate ports, enough of each
      API for every outreach feature to work against it:
  - **Bluesky** (atproto XRPC): `com.atproto.server.createSession`,
    `refreshSession`, `com.atproto.repo.createRecord`, `uploadBlob`,
    `app.bsky.notification.listNotifications`, plus whatever the tracker and
    engagement code call (likes, reposts, replies counts), and the
    link-card fetch if the server does it.
  - **Mastodon**: `GET /api/v1/accounts/verify_credentials`,
    `POST /api/v1/statuses`, `POST /api/v2/media`,
    `GET /api/v1/notifications`, and `GET /api/v1/statuses/{id}` if
    engagement reads it.
  - **ShortLinks**: the endpoints `internal/shortlinks`' client calls (`me`,
    campaigns, links, stats/rollups), with plausible click counts.

  The mocks keep in-memory state, so a post created by the app shows up in
  later reads. They return realistic ids and URLs (for example
  `http://127.0.0.1:<port>/mastodon/@opencircuitsf/<id>`) and log each
  request to stdout. They accept any token or app password, except a
  documented magic value (for example `bad-token`) that returns 401, so
  Test connection's failure path can be shown.
- [ ] **Never reachable in production.** The mock binary or subcommand binds
      loopback only and refuses non-loopback addresses. It isn't installed by
      `deploy.sh` or `release.sh`. No production code path imports it.
- [ ] **A demo seed** (for example `opencircuit seed --demo-outreach` or
      `scripts/dev-demo.sh`) creates, in the local dev Postgres:
  - a fictional published workshop, "LED Programming"
    - a believable summary, a venue and a date about a week out
    - a cover image from the repo's assets, or a generated placeholder
  - three or four outreach locations

  It's idempotent. It only ever targets the local dev database, and refuses
  any `DATABASE_URL` whose host isn't localhost.
- [ ] **One-command dev run** (for example `scripts/dev-outreach-demo.sh`)
      that:
  - starts the mocks
  - starts the dev server against Postgres with `DEV_ADMIN_LOGIN` and
    `MAILER_NOOP`
  - runs the seed
  - saves the mock URLs and credentials as outreach connection values in the
    local database, so Settings shows them as "saved"
  - prints the URLs

  It binds a non-default port (`#0` §8b), records the pids it starts and
  kills them on exit. It must also work when the server is reached from a
  Tart VM guest, at the host's bridge address, so state whether BASE_URL or
  cookie settings need adjusting for that and handle it. `DEV_ADMIN_LOGIN`
  stays refused unless BASE_URL is loopback, so if the VM needs a
  non-loopback origin, find a safe way (for example a host-side
  port-forward from the guest's view of the host), and don't weaken the
  guard.
- [ ] `docs/dev.md` gains a "Outreach demo with mocks" section.
- [ ] Go tests for the mock server (a round trip per service) and for the
      seed's localhost refusal. Verified with `ISSUE=0580 scripts/check.sh`
      plus the AGENTS.md §5 guard packages reached. Zero skips.
