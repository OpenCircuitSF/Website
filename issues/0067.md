## Description

`.env.example:18` reads `SESSION_SECRET=replace_with_random_64_char_hex_string`. That value is non-empty, so it satisfies the config loader's required-variable check and the service starts normally. Anyone who copies the template and forgets that one line runs production with a session HMAC key that is published in a public repository.

> 🟢 Resolved 2026-08-18 — `.env.example` now ships `SESSION_SECRET=` blank so an unedited copy fails closed at startup instead of signing sessions with a key published in a public repo, with the generation command and the fail-closed rationale stated inline and in `docs/configuration.md`; the loader was correctly left untouched and the existing `TestLoad_MissingRequired/missing_SESSION_SECRET` subtest referenced rather than duplicated.

## Expected behavior

PRD §9 specifies a **blank** `SESSION_SECRET` in the template so startup fails closed with `config: missing required variable SESSION_SECRET`, forcing the operator to set a real one.

## Actual behavior

The placeholder is a valid non-empty string. The service boots, signs sessions with a known key, and gives no warning. Session forgery requires only reading `.env.example` on GitHub.

## Root cause

Inherited verbatim from the ShortLinks template in `#0001`'s skeleton copy and preserved through `#0007`'s regeneration, which reproduced the existing line rather than PRD §9's specified blank.

## Fix

Changed `.env.example`'s `SESSION_SECRET` line from `SESSION_SECRET=replace_with_random_64_char_hex_string` to `SESSION_SECRET=` (empty), and rewrote the surrounding comment to state: required with no default, the generation command (`openssl rand -hex 32`), and *why* it's blank rather than a placeholder — a forgotten line now fails loudly at startup instead of booting with a known key.

Updated `docs/configuration.md`'s `SESSION_SECRET` table row to explain the same blank-template rationale, referencing this issue.

Did not touch `internal/config/config.go` — its presence-only validation is already correct, and no new test was added: `TestLoad_MissingRequired/missing_SESSION_SECRET` (in `internal/config/config_test.go`) already sets `SESSION_SECRET=""` and asserts `Load()` returns an error mentioning `SESSION_SECRET`, which is exactly the scenario `.env.example` now produces if left unedited. Confirmed it actually covers this by running it directly (see Verification).

Audited every other `.env.example` value against the acceptance criteria's actual standard ("a value that satisfies validation while being publicly known is the defect, not the specific variable") rather than just eyeballing which ones look secret-shaped:

- `DATABASE_URL`'s password is the sentinel `CHANGE_ME_IN_PRODUCTION`. It's non-empty and passes `Load()`'s presence check the same way `SESSION_SECRET` did, but an unedited copy fails loudly at the first real connection attempt (Postgres auth rejects the placeholder password against any real database) — not a silent defect, so left unchanged.
- `ADMIN_EMAIL` is `you@example.com`. Also non-empty and passes the presence check. If left unedited, whoever completes registration with the literal address `you@example.com` becomes the pre-authorized admin — but `example.com` has no functioning inbound mail, so an attacker (or the operator) generally cannot receive the magic-link email needed to complete that registration. Meaningfully lower risk than `SESSION_SECRET` (no interaction needed to exploit a known signing key vs. needing to actually receive mail at a domain with no MI), so left unchanged rather than blanked — blanking it would just move the "remember to set this" burden without closing a real silent-boot hole.
- Every other variable (`PORT`, `BASE_URL`, `AWS_REGION`, `SES_CONFIGURATION_SET`, `EMAIL_FROM`/`EMAIL_REPLY_TO`/`EMAIL_LIST_DOMAIN`, `SES_INBOUND_BUCKET`, `MAX_SEND_RATE`, `SEND_BATCH_SIZE`, `SEND_WORKER_ENABLED`) is not secret-bearing — public URLs, region names, and tuning knobs — so out of scope for this audit.

## Gotchas

- None. This was a two-line functional change (plus doc prose); the existing test coverage already asserted the behavior the fix relies on.

**Added by review (2026-08-18):** the placeholder audit's reasoning was checked rather than just its outcome, and it holds.

- The criterion's standard is "a value that satisfies validation while being publicly known is the defect". Read purely literally, `CHANGE_ME_IN_PRODUCTION` and `you@example.com` both qualify. But the axis the issue's own Notes set out is narrower and is the right one: the defect is a placeholder that "converts a loud startup error into a silent security defect". The implementer applied exactly that axis to all three variables and reached a defensible answer on each.
- `DATABASE_URL` — sound. A wrong password cannot produce a running-but-compromised service; it produces a service that cannot connect. That is a loud failure, not a silent one, so it is a different defect class from a signing key.
- `ADMIN_EMAIL` — sound, and verified against the actual code path rather than taken on faith. Admin promotion happens in `internal/auth/registration.go:210` during `FinishRegistration`, which is reachable only after `VerifyRegistration` consumes a token delivered by `Mailer.SendVerification`. `example.com` is RFC 2606 reserved with no deliverable MX, so nobody — operator or attacker — can complete a registration as `you@example.com`. Left unedited it also fails visibly: the real operator registers with their real address and simply does not get admin, which they discover immediately. Fail-closed, not silent.
- The `ADMIN_EMAIL` bullet in `## Fix` contains a typo — "a domain with no MI" should read "no MX". Cosmetic; the analysis is correct.
- Not a defect in this issue, but worth carrying: `BASE_URL` in `.env.example` is `https://opencircuitsf.com` (apex) while `WEBAUTHN_RP_ORIGIN` is `https://www.opencircuitsf.com` (www) and `CLAUDE.md` §7 makes www canonical with the apex 301-redirecting to it. Not secret-bearing, so correctly outside this issue's audit, but an operator copying the template gets an apex `BASE_URL` that redirects. Worth confirming in [#0064](0064.md).

## Notes

Fail-closed is the whole point. A placeholder that validates is worse than no placeholder: it converts a loud startup error into a silent security defect that surfaces only if someone thinks to check.

This is a template and documentation fix. **Do not change the loader** — it is correct to require the variable, and `#0065` already proved that requirement is genuinely asserted.

Audit the other placeholders while here. `ADMIN_EMAIL` and `DATABASE_URL` carrying real-looking defaults is a related hazard, though a much smaller one than a signing key.
