## Description

An admin-only CSV import for audiences the group already collected elsewhere — a Google Form, an event sign-in sheet, a spreadsheet — where every batch records where the addresses came from, when the source collected them, and how consent was obtained, and where a batch that turns out to lack consent can be revoked in one action. This issue covers `prior_consent` mode, which sends nothing; `#0129` adds `invite` mode.

## Notes

PRD §6.10 is the specification. §6.2 carries the schema.

**Why a `prior_consent` import lands `active` and sends nothing.** The user's decision, 2026-08-21. An import asserts that consent already exists — that is what `consent_note` records. Re-running double opt-in over an audience that already opted in at the source produces mail nobody asked for and a low confirmation rate that reads to SES as a spam signal. No welcome email either: the welcome (`#0127`) is what a subscriber gets for confirming, and these subscribers did not confirm here. The whole weight of the mode therefore rests on the admin's attestation, which is why `consent_note` is mandatory and why revocation is one action.

When the prior opt-in is anything less than clear, the answer is `invite` mode (`#0129`), not a `prior_consent` import with a hopeful note.

**The suppression check is the whole point.** An import is precisely the mechanism by which an address that hard-bounced or complained gets resurrected and complains again. Skipping the check would undo `#0033`, `#0038`, and `#0100` in a single upload.

**Luma is probably not a real source.** PRD §14 Q9 is now closed: exporting attendee addresses out of Luma to mail them from here is not something this project expects to do. Google Forms and event sign-in sheets are the realistic sources. **The website is the primary signup path.** Import is secondary and low-volume. Do not let it grow features the signup form does not have.

**This pairs with `#0059`.** Export exists; import is its counterpart and is also what makes `#0062`'s restore path and `#0060`'s erasure verifiable end to end.

**A full-list import is as sensitive as a full-list export.** `#0059` audits export because it is the highest-value action a stolen admin session could take. Import is the second: it is how an attacker would inject addresses. Audit it with the same weight.

The issue's `## Notes` greenfield paragraph and acceptance criterion 2 were
written 2026-08-21 and are simply out of date. The implementer followed them
faithfully; the premise, not the execution, is what failed.

**Consequence, reproduced rather than argued.** A throwaway database was
migrated to version 22 using `migrations/` as of `e722542^` (i.e. exactly what
production is), then `migrate up` was run against the committed tree:

```
23/u create_subscriber_imports
  (details: pq: column "import_id" referenced in foreign key constraint does not exist)
select version, dirty from schema_migrations  ->  23|t
```

The deploy **fails and leaves `schema_migrations` dirty at 23**, which blocks
every later migration until a human forces it. Worse, even setting the FK aside,
production's `subscribers` table would still lack `source`, `source_detail`,
`consent_basis`, `import_id`, and `invited_at` — while this commit widens
`subscriberColumns` / `qualifiedSubscriberColumns` to select all five. Every
subscriber query in the service would start erroring the moment the new binary
started. The whole mailing subsystem, not just import.

**The fix, prototyped and proven in a throwaway worktree.** Revert
`migrations/000010_create_subscribers.up.sql` to its `e722542^` content, and move
the five columns plus `subscribers_source_check` /
`subscribers_consent_basis_check` into `000023`, *above* the
`subscribers_import_id_fkey` statement:

```sql
ALTER TABLE subscribers
    ADD COLUMN source        TEXT NOT NULL DEFAULT 'signup_form',
    ADD COLUMN source_detail TEXT,
    ADD COLUMN consent_basis TEXT,
    ADD COLUMN import_id     BIGINT,
    ADD COLUMN invited_at    TIMESTAMPTZ;
```

with the matching `DROP CONSTRAINT`/`DROP COLUMN` statements prepended to
`000023`'s `down.sql`. Measured with that patch applied:

- a version-22 database migrates to 23 cleanly (`23|f`);
- a **fresh** database and an **upgraded** version-22 database produce
  byte-identical `pg_dump --schema-only` output — the upgrade path converges;
- the patched-schema database runs `internal/subscribers` and
  `internal/handlers` green, so nothing depends on the columns' ordinal
  position (the only diff against the committed tree's schema is that the five
  columns sit at the end of `subscribers` instead of mid-table).

`docs/database.md`'s `000023` row and `000010`'s new comment block both say the
columns land "via `000010` directly, per the greenfield note" and will need
