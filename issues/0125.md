# 0125 — Import subscribers from CSV with recorded consent provenance

| | |
|---|---|
| **Status** | open |
| **Module** | subscribers / admin / web |
| **Platform** | All |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-08-21 |

## Description

An admin-only CSV import for audiences the group already collected elsewhere — a Google Form, an event sign-in sheet, a spreadsheet — where every batch records where the addresses came from, when the source collected them, and how consent was obtained, and where a batch that turns out to lack consent can be revoked in one action. This issue covers `prior_consent` mode, which sends nothing; `#0129` adds `invite` mode.

## Acceptance criteria

**Provenance**

- [ ] A new migration creates `subscriber_imports` per PRD §6.2, including `consent_mode`
- [ ] `subscribers` gains `source` (`NOT NULL DEFAULT 'signup_form'`), `source_detail`, `consent_basis`, `import_id`, `invited_at` — added to `migrations/000010` directly, per the greenfield note below
- [ ] An import cannot be committed without `source`, `collected_at`, and a non-empty `consent_note`
- [ ] `consent_mode` is stored per batch. This issue implements `prior_consent`; the UI must not offer `invite` until `#0129` lands, and must never silently downgrade an `invite` request to `prior_consent`
- [ ] `GET /admin/subscribers/{id}` shows source, source detail, consent basis, and the originating import

**Import**

- [ ] `POST /admin/subscribers/import/preview` parses the CSV and returns counts — new, duplicate, suppressed, malformed — plus a sample of each, writing nothing
- [ ] Column mapping is chosen in the UI; the email column is never guessed from the header
- [ ] An optional interest-slug column maps to `subscriber_interests`; unknown slugs are reported in the preview, not silently dropped
- [ ] `POST /admin/subscribers/import` commits, requiring the preview's checksum so the file cannot change between preview and commit
- [ ] **Every address is checked against `suppressions` before insert.** A suppressed address is skipped and counted. This is absolute
- [ ] An address already in `subscribers` is skipped, never overwritten — an import never changes an existing subscriber's status, interests, or consent basis
- [ ] `prior_consent` imports land `status = 'active'` with a `manage_token`, `source = 'import'`, `consent_basis = 'imported_prior_consent'`
- [ ] **A `prior_consent` import sends no email whatsoever** — no confirmation, no welcome, no notification. A test asserts the outbound queue is empty after a committed import
- [ ] Malformed addresses are rejected by the same normalization `#0026` uses (`lower(trim(email))`, no dot or `+tag` stripping)
- [ ] Import is transactional — a failure mid-file commits nothing
- [ ] The whole import writes one `audit_log` entry and one `subscriber_events` row per inserted address (`#0126`)
- [ ] `synthetic` test-send rows (`migrations/000019`) are never produced by an import

**Revocation**

- [ ] `POST /admin/imports/{id}/revoke` moves every subscriber with that `import_id` and status `active` to `unsubscribed`, `unsubscribe_source = 'admin'`
- [ ] The import row goes `status = 'revoked'` with `revoked_at` and `revoked_reason`
- [ ] Revocation applies regardless of whether an address has since engaged
- [ ] Revocation is audited and writes an `import_revoked` subscriber event per address
- [ ] Revoking an already-revoked import is a no-op, not an error

**Safety**

- [ ] The import UI states, in the interface and not only the docs, that importing without prior consent violates CAN-SPAM and burns the sending domain
- [ ] Import size is bounded, and the bound is stated in the UI
- [ ] CSV injection is not a concern on the read path, but any field echoed back into the preview is escaped

## Notes

PRD §6.10 is the specification. §6.2 carries the schema.

**Why a `prior_consent` import lands `active` and sends nothing.** The user's decision, 2026-08-21. An import asserts that consent already exists — that is what `consent_note` records. Re-running double opt-in over an audience that already opted in at the source produces mail nobody asked for and a low confirmation rate that reads to SES as a spam signal. No welcome email either: the welcome (`#0127`) is what a subscriber gets for confirming, and these subscribers did not confirm here. The whole weight of the mode therefore rests on the admin's attestation, which is why `consent_note` is mandatory and why revocation is one action.

When the prior opt-in is anything less than clear, the answer is `invite` mode (`#0129`), not a `prior_consent` import with a hopeful note.

**Greenfield — amended 2026-08-21.** Nothing is deployed but the static placeholder: no PostgreSQL instance on AWS holds real data and no subscriber has ever signed up. Until the first production release, `migrations/` may be squashed or rewritten and the dev database dropped and recreated. Add the new `subscribers` columns to `000010` rather than an `ALTER TABLE`, and write no backfill — there are no rows to backfill. See PRD §6.2's greenfield note.

**The suppression check is the whole point.** An import is precisely the mechanism by which an address that hard-bounced or complained gets resurrected and complains again. Skipping the check would undo `#0033`, `#0038`, and `#0100` in a single upload.

**Luma is probably not a real source.** PRD §14 Q9 is now closed: exporting attendee addresses out of Luma to mail them from here is not something this project expects to do. Google Forms and event sign-in sheets are the realistic sources. Build against a generic CSV with UI column mapping and hardcode no vendor's schema; `luma` survives as a `source` value for labelling only.

**The website is the primary signup path.** Import is secondary and low-volume. Do not let it grow features the signup form does not have.

**This pairs with `#0059`.** Export exists; import is its counterpart and is also what makes `#0062`'s restore path and `#0060`'s erasure verifiable end to end.

**A full-list import is as sensitive as a full-list export.** `#0059` audits export because it is the highest-value action a stolen admin session could take. Import is the second: it is how an attacker would inject addresses. Audit it with the same weight.
