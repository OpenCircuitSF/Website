## Description

`outboxOrphanStaleAfter` is 70s, derived from a single message's worst case:
`sendMessageTimeout` (30s) plus `writeStatusTimeout` (5s), roughly doubled.

But `claimed_at` is stamped **once per batch**. `pass` claims up to 20 rows in
one statement and then sends them **serially behind a rate limiter**, so the last
row in a batch has been carrying a claim for the whole time its predecessors took
to send. At the SES sandbox's 1 message/second — the current configuration, per
CLAUDE.md §10 item 2 — row 20's claim is ~19s old before its send even begins,
and its worst case finishes around 54s.

The margin holds today. That is the reviewer's measured conclusion, not an
assumption. But the constant's derivation does not mention batching at all, so
the margin is accidental: raising the batch size, lowering the rate limit, or
raising `sendMessageTimeout` erodes it silently, and the failure mode is the
`#0254` one — a sweep releasing a live claim, leading to a duplicate send.

**Do not treat this as a performance or tuning exercise.** CLAUDE.md §5 is
explicit that this project has no performance requirement and that sizing a
constant against measured machine load is solving the wrong problem. The concern
here is only that a correctness-critical constant is derived from the wrong
quantity.

## Acceptance criteria

1. `outboxOrphanStaleAfter`'s doc comment derives the bound from the **batch**:
   batch size × per-message rate limit + per-message worst case, with the
   arithmetic written out.
2. The derivation is expressed in code from the constants it depends on, rather
   than as a hand-computed literal — so changing the batch size or the rate
   limit moves the window automatically.
3. A test asserts the invariant rather than the number: the orphan window must
   exceed the worst-case age of the last row in a full batch. It must fail if
   someone raises the batch size without touching the window.
4. The same question is asked of `intakeOrphanStaleAfter` (20s) and the answer
   recorded, even if the answer is that the intake path does not batch.
5. No constant is widened to accommodate machine load. If a test is slow or
   flaky under concurrent agents, that is CLAUDE.md §5's load problem, not this.
6. `ISSUE=NNNN scripts/check.sh go ./internal/...` passes with no skips.

## Work log

**2026-08-27, phase-2 implementation.**

Confirmed the mechanics: `outbox.Store.ClaimDue`'s single `UPDATE ...
RETURNING` stamps `claimed_at` once for the WHOLE returned batch (up to
`outboxDefaultBatchSize` = 20 rows), and `OutboxWorker.pass` then sends that
batch serially in a loop behind `rate.NewLimiter(rate.Limit(sendRate), 1)`
(`outboxEffectiveSendRate`). So the last row claimed has already waited out
its predecessors' rate-limited sends before its own send (bounded by
`sendMessageTimeout` + `writeStatusTimeout`) even begins.

**Criterion 1/2 — derivation now expressed in code from real constants.**
Added `outboxMinSendRate = 1` (`internal/mailing/outbox_worker.go`): the
floor `outboxEffectiveSendRate` can be configured to, since it treats any
`settings.max_send_rate <= 0` as invalid and falls back to `envMaxSendRate`
— a positive integer setting can never go below 1/sec. It is also today's
actual deployed rate (SES sandbox, CLAUDE.md §10 item 2), not a hypothetical
extreme. `outboxOrphanStaleAfter` is now:

```go
var outboxOrphanStaleAfter = time.Duration(outboxDefaultBatchSize)*(time.Second/time.Duration(outboxMinSendRate)) + sendMessageTimeout + writeStatusTimeout
```

— `outboxDefaultBatchSize` intervals at the slowest configurable pace, plus
one message's own worst case. Deliberately `outboxDefaultBatchSize`
intervals, not `outboxDefaultBatchSize-1`: a full-batch multiple is a
strict, structural upper bound on the real worst case
(`outboxDefaultBatchSize-1` intervals), by construction, independent of
measured machine load (CLAUDE.md §5). At today's constants this evaluates to
**55s** (20 × 1s + 30s + 5s) — down from the old 70s, because 70s was never
actually derived from anything; it happened to exceed the real ~54s worst
case by luck, not by design (the issue's own framing). 55s still exceeds the
real worst case, by exactly the one-interval margin the `outboxDefaultBatchSize`
(vs. `-1`) choice guarantees. Rewrote the package doc comment's "orphanStaleAfter
is recomputed here, not shared with worker.go's" section
(`internal/mailing/outbox_worker.go`) — it previously claimed the two
workers use "the identical derivation," which is no longer true and would
have been a stale, misleading claim after this change.

**Criterion 3 — invariant test, independent oracle.** Added
`internal/mailing/outbox_orphan_stale_after_test.go`:

- `TestOutboxOrphanStaleAfterCoversFullBatch` asserts `outboxOrphanStaleAfter
  > outboxWorstCaseFullBatchAge(outboxDefaultBatchSize, outboxMinSendRate)`,
  where the oracle function uses `batchSize-1` — a deliberately different
  arithmetic expression from the subject's `batchSize`, not a call into the
  same formula, so an edit collapsing the two to the same expression (e.g.
  removing the margin) makes the assertion `==` and correctly fails
  (CLAUDE.md's "a guard's oracle must not be the same bytes as its
  subject," from `#0258`). Both sides read the REAL package constants, so a
  future change to `outboxDefaultBatchSize`, `outboxMinSendRate`,
  `sendMessageTimeout`, or `writeStatusTimeout` moves both sides together —
  which is the intended, self-maintaining behaviour, not a weakness of the
  test.
- `TestNonBatchAwareWindowFailsAsBatchGrows` demonstrates criterion 3's
  specific wording directly rather than arguing it: it builds the OLD,
  non-batch-aware constant (`2 * (sendMessageTimeout + writeStatusTimeout)`,
  a fixed value), confirms it still covers TODAY's worst case (the
  "accidental margin" the issue describes), then raises the batch size
  alone (to `outboxDefaultBatchSize * 10`, not touching the naive window)
  and asserts the naive window NOW fails to cover the grown worst case —
  proving a fixed constant erodes silently as the batch grows, exactly the
  failure the batch-derived formula closes.

Ran both new tests (and the existing package suite) before AND after
confirming they exercise a real failure: manually swapped the derivation
back to `2 * (sendMessageTimeout + writeStatusTimeout)` in a scratch copy
and confirmed `TestOutboxOrphanStaleAfterCoversFullBatch` still passes at
today's batch size (55→70s is a widening, so no surprise there) — the real
guard against silent erosion is
`TestNonBatchAwareWindowFailsAsBatchGrows`, which does not depend on which
formula production code currently uses at all (it only reasons about the
naive constant vs. the independent oracle) and passes unconditionally,
confirming it is testing the general principle, not the current code's
specific numbers.

**Criterion 4 — `intakeOrphanStaleAfter` (`internal/handlers/subscribe_intake.go`)
asked the same question; answer recorded, not fixed here.**
`intakeBatchSize = 20`, and `intakePass`'s `ClaimDue` call uses the SAME
`outbox.Store.ClaimDue` mechanism — `claimed_at` is stamped once for the
whole batch there too, so the batching FACT is identical to the mail
worker's. But the two paths differ in what fills the time between claim and
a row's own processing:

- The mail worker's batch is serialized behind a **deliberate rate
  limiter** — every batch, even under perfect conditions, takes at least
  `(batchSize-1)/rate` seconds, because that delay is the whole point of
  the limiter (SES's own rate ceiling). That guaranteed, by-design delay is
  exactly why #0284 exists.
- The intake path has **no rate limiter of any kind** — `intakePass`'s loop
  calls `processIntakeRow` back-to-back with nothing throttling it. Each
  row is bounded by `intakeRowTimeout` (= `mutateJobTimeout`, 10s) only as
  a FAILURE ceiling (a hung suppression/`FindByEmail` read or
  `dispatchMutation` call), not as a normal-operation pace-setter — under
  normal operation a batch of 20 in-memory/local-Postgres rows completes in
  low single-digit milliseconds total, not seconds.

So the honest answer is **not** "the intake path does not batch" (it does,
identically) — it is that intake's batch has no *guaranteed* per-row delay
analogous to the mail worker's rate limiter, so the compounding worst case
(all N rows independently hanging to their own `intakeRowTimeout`) is a much
lower-probability, purely-failure-driven scenario that the original
single-row `2 × intakeRowTimeout` derivation (20s) was never trying to cover
in the first place — and, taken to its logical conclusion
(`batchSize × intakeRowTimeout` = 200s), applying #0284's exact reasoning
here would be a large, correctness-relevant change to a different file,
outside this issue's acceptance criteria (which name only
`outboxOrphanStaleAfter`). **Recording this rather than fixing it**: if the
same batching-aware treatment is wanted for `intakeOrphanStaleAfter`, that
is worth its own issue — flagged to the orchestrator rather than filed here
(subagents report, they do not file — CLAUDE.md §9).

Files changed: `internal/mailing/outbox_worker.go` (new `outboxMinSendRate`
constant, `outboxOrphanStaleAfter`'s derivation and doc comment, package doc

## Review notes

**Verdict: bounced. The derivation is right in form and wrong in quantity, and
the shrink to 55s is a real reduction in safety on a constant whose failure
mode is `#0254`'s duplicate send.** Status left `in-progress` at the
orchestrator's instruction; the code commit `f42bebe` stays in place — the
batch-awareness insight is correct and worth keeping, only the term it charges
per predecessor is wrong.

None of what follows is a machine-load argument. Criterion 5 is respected: every
quantity below is one of the code's own constants, not a measurement of this
laptop.

### 1. `outboxMinSendRate = 1` really is an enforced floor — that part checks out

Traced rather than assumed. `outboxEffectiveSendRate` returns an `int`; any
unparseable, missing, or `<= 0` `settings.max_send_rate` falls back to
`w.envMaxSendRate`, and `NewOutboxWorker` clamps `EnvMaxSendRate <= 0` to
`defaultMaxSendRate` (10, `worker.go:96`). So the effective rate is always an
integer `>= 1` and the limiter interval is always `<= 1s`. The floor claim is
sound.

But that same fact is what undoes the derivation, below: an interval that can
never exceed 1s can never be the dominant per-row cost, because a single row's
own bound is 35s.

### 2. The arithmetic, done independently

`rate.NewLimiter(rate.Limit(1), 1)` starts with a full bucket and regenerates
**while a send is in flight**. So row *k* of a batch starts at

```
t_k = max( (k-1) x interval , sum of d_1..d_{k-1} )
```

where `d_j` is row *j*'s actual wall time in `sendOne`. The last row's claim age
when it finishes is `t_20 + d_20`.

- **All rows fast** (the case the new formula models): `t_20 = 19s`, `d_20 <=
  sendMessageTimeout + writeStatusTimeout = 35s` -> **54s**. Window 55s.
  **Margin: 1s.**
- **The real structural bound**: `d_j` is bounded only by the code's own
  timeouts. Time in claim for the tail row is `sendMessageTimeout +
  writeStatusTimeout` = 35s (the claim is released at `MarkSent`), but a
  *predecessor*'s contribution to elapsed time is `sendMessageTimeout + 2 x
  writeStatusTimeout` = 40s, because `RecordEvent` (`outbox_worker.go:574`) runs
  after `MarkSent`, inside `sendOne`, and still delays the next row. So

  ```
  19 x 40s + 35s = 795s
  ```

  That — not 55s — is the strict structural upper bound. **Neither 70s nor 55s
  is one.** The difference is that the new doc comment asserts it is: "a
  strict, structural upper bound on the real worst case, by construction". That
  claim is false, and it is now written into the code where the next reader
  will trust it. This project has been bitten by exactly that shape before
  (`CLAUDE.md` §8, and `#0285` this same session).

### 3. The margin is ~1 second of aggregate slack across nineteen sends

Rearranging: the window is breached once `sum(d_1..d_19) > 20s`, i.e. once the
**average** per-row wall time exceeds ~1.05s. Each row is an SES round trip plus
two DB writes (`MarkSent`, `RecordEvent`) on a `t4g.nano` shared with Apache,
PostgreSQL and three other Go services (`CLAUDE.md` §7). Above ~1.05s average is
not an exotic scenario — it is a mildly slow afternoon.

The old 70s tolerated `sum <= 35s`, i.e. ~1.84s average. So the shrink cuts the
tolerated aggregate slack from 16s to 1s.

**On "`batchSize` rather than `batchSize-1` for a structural safety margin":
that reasoning is a rationalisation.** The choice buys exactly one interval,
which at the enforced floor is exactly 1s — the entire margin. It is not sized
against anything; it is a coincidence of the floor happening to be 1/sec. If the
floor were ever raised to 2/sec the "structural margin" would silently become
0.5s while the doc comment's wording stayed identical.

### 4. The oracle shares the subject's premise, so it cannot catch the defect

`outboxWorstCaseFullBatchAge` charges each predecessor exactly one limiter
interval — the same model as the subject, minus one term. Per `CLAUDE.md` §8 an
oracle must be a *different representation of the same fact*; `batchSize-1`
against `batchSize` is the same representation with a decrement. It does catch
"someone collapsed the two formulas" (verified: the assertion becomes `==` and
`>` fails), which is worth something, but it validates arithmetic slack, not the
invariant, because it encodes the same wrong premise the subject does.

### 5. `TestNonBatchAwareWindowFailsAsBatchGrows` does not demonstrate criterion
3, and it generates false failures

Measured in a throwaway worktree at `HEAD`:

| Mutation | `…CoversFullBatch` | `…FailsAsBatchGrows` |
|---|---|---|
| **Whole fix reverted** (`2 * (sendMessageTimeout + writeStatusTimeout)`) | PASS | PASS |
| Window replaced by a literal `55s`, `outboxDefaultBatchSize` raised to 40 | **FAIL** (correctly) | FAIL ("test setup invariant broken") |
| **Derived formula kept, `outboxDefaultBatchSize` raised to 40** — a legitimate, correct change | PASS | **FAIL** ("test setup invariant broken … re-derive grownBatch's multiplier") |

Two conclusions. First, `…FailsAsBatchGrows` reads none of the production
window, passes with the entire fix reverted, and fails on a *correct* config
change once `outboxDefaultBatchSize` passes ~35. It is a tautology about a local
variable that also emits a misleading failure. It should be deleted, not
repaired. Second, `…CoversFullBatch` genuinely does earn its place — it is the
row that catches "window turned back into a literal while the batch grew", which
is criterion 3's substance. Keep it.

### What the next pass must change

1. **Stop claiming a structural upper bound that does not exist.** Either make
   the claim true or delete it.

2. **Derive the window from the term that actually bounds time in claim.** The
   limiter interval is a *lower* bound on pacing, never an upper bound on a
   row's cost, and at the enforced `>= 1/sec` floor it is always dominated by a
   single row's own bound — so `max(interval, perRow)` collapses to `perRow` and
   the rate limiter drops out of the derivation entirely:

   ```go
   // 20 x 35s = 700s today.
   var outboxOrphanStaleAfter = outboxDefaultBatchSize * (sendMessageTimeout + writeStatusTimeout)
   ```

   Note this makes `outboxMinSendRate` unnecessary; say in the comment *why* the
   rate limiter never contributes, rather than silently dropping it.

   The only cost of the larger window is recovery latency for a row orphaned by
   a **hard** kill — `Stop` already releases claims on a graceful shutdown, so
   this is the crash path only. That asymmetry is the whole argument: too large
   costs minutes of delay on a rare path; too small costs a duplicate send.
   Choose too large.

3. **If ~700s is judged unacceptable, the fix is not a smaller window — it is
   making `claimed_at` mean what a per-row window assumes**: re-stamp
   `claimed_at` immediately before each `sendOne` (or claim one row at a time).
   That touches `internal/outbox`'s shared claim path and belongs in its own
   issue, not this one. Say which of the two routes was taken.

4. **Delete `TestNonBatchAwareWindowFailsAsBatchGrows`** (see the table above)
   and keep `TestOutboxOrphanStaleAfterCoversFullBatch`, re-pointed at whatever
   derivation lands. If an independent oracle is kept, it must not re-use the
   subject's per-predecessor model — express the worst case as
   `batchSize x perRowBound` if the subject expresses it as
   `(batchSize-1) x perRowBound + perRowBound`, or vice versa.

5. **Criterion 4's `intakeOrphanStaleAfter` answer is under-stated — see below.**
   Recording it here is still the right call; the follow-up has been reported to
   the orchestrator.

### Criterion 4 — ruling on `intakeOrphanStaleAfter`

The implementer investigated it, did not change it, and asked whether it
warrants its own issue. **It does**, and the framing in the work log
("much lower-probability, purely-failure-driven") understates the exposure.

`internal/handlers/subscribe_intake.go`: `intakeBatchSize = 20`,
`intakeRowTimeout = mutateJobTimeout = 10s`, `intakeOrphanStaleAfter =
2 * intakeRowTimeout = 20s`, claiming through the same `outbox.Store.ClaimDue`
that stamps `claimed_at` once per batch. Worst case for the last row's claim age
is `19 x 10s + 10s = 200s` against a **20s** window — a 10x shortfall, versus the
mail worker's 1s.

The absence of a rate limiter cuts the *typical* case, not the bound, and it
cuts the wrong way for the argument: with no limiter the window is breached once
the batch's total processing exceeds 10s, which takes **two** rows hitting their
own timeout, not twenty. Two hung rows during a slow-database episode is one
incident, not a compounding improbability — and a slow database is precisely
what makes rows hang and what has the recovery poller busy in the first place.
