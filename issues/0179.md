## Description

`web/src/lib/sendConfirm.ts`'s **`confirmHint`** — the hint shown when an admin's typed recipient count does not match the server's — is **not imported by `sendConfirm.test.ts` at all**, despite three real branches: empty input → `null`, matching count → `null`, mismatch → a hint naming the expected count.

That function is part of a **safety affordance**, not decoration. `#0047`'s send gate requires a server-verified typed recipient count precisely so an admin cannot fire a campaign at the wrong audience by reflex — `#0056`'s review leaned on that gate when accepting the `all`-audience fallback as survivable. The hint is what tells someone their number is wrong.

Found by `#0178`'s implementer while auditing every string-returning export in `web/src/lib/` against what the test files actually import — the same read-don't-search method that has now turned up five findings on this project.

## Acceptance criteria

- [x] `confirmHint` has tests covering all three branches, asserting **semantically** — what the hint claims, and that it names the expected count — rather than pinning one phrasing. `#0174` exists because a phrase-match test masqueraded as a behavior guard
- [x] The mismatch branch's test fails if the hint stops naming the expected count, or names the wrong one
- [x] Confirm nothing else in `sendConfirm.ts` is unexercised while you are there — the audit that found this checked imports, not coverage depth
- [x] `scripts/check.sh web` passes

## Root cause

`confirmHint` was implemented (as part of `#0047`'s send gate) but never
imported by `sendConfirm.test.ts`. `sendGuardState`, `sendGuardDescription`,
`sendGuardSummaryClass`, `normalizeCountInput`, and `confirmMatches` all had
tests; `confirmHint` — the function that turns a mismatched typed count into
the hint an admin actually reads — had none. Grepping the test file's import
list against every export of `sendConfirm.ts` confirms `confirmHint` was the
only gap; everything else exported from the module is imported and exercised.

## Fix

Added a `describe('confirmHint', …)` block to `sendConfirm.test.ts` covering
all three branches:

- empty input → `null` (no scolding an untouched field)
- exact match → `null`
- mismatch → names the expected count

Asserted semantically per the acceptance criteria: `toContain(String(count))`
rather than pinning the whole sentence. The mismatch case uses `999` against
an expected `482` — two numbers with no shared digits — so `toContain('482')`
fails both if the hint stops naming the expected count *and* if it names the
wrong one (e.g. the typed value instead), which is exactly what criterion 2
asks the test to catch. A second mismatch case (`'abc'`, non-numeric input)
confirms the branch also fires correctly when `normalizeCountInput` returns
`null` rather than a mismatched number.

### The four assertions are genuinely mutation-covered

`web/src/lib/sendConfirm.ts` baseline md5 `41330f9ecd290d0785aecbad83c0f10d`;
every mutation was applied, run, and restored, with the md5 re-checked after.

| # | mutation to `confirmHint` | result |
|---|---|---|
| N1 | names the **typed** count instead of the expected one (`type ${count}` → `type ${raw.trim()}`) | **2 failed** / 39 passed |
| N2 | stops naming a count at all ("check the count and try again") | **2 failed** |
| N3 | empty-input guard removed — scolds an untouched field | **1 failed** |
| N4 | matching-count guard removed — hint shown when the count is right | **1 failed** |
| N5 | off-by-one on the named count (`${count + 1}`) | **2 failed** |

N1 is the one the issue's criterion 2 turns on, and it fails for two independent
reasons: `toContain('482')` goes red *and* `not.toContain('999')` goes red. The
digit-disjoint pair (999 vs 482) does hold as claimed — `Doesn't match — type
482 to confirm.` shares no digit with `999`, so neither assertion can be
satisfied by accident.

**Is `toContain` on a bare number strong enough?** Yes here, and the
`not.toContain('999')` half is what makes it so. The failure mode a bare
`toContain` invites — an unrelated `999` elsewhere in the string satisfying the
check — cannot arise for a one-clause hint whose only variable is `count`, and
the negative assertion independently forbids the single realistic wrong number
(the typed one). N5 confirms even a `+1` drift is caught. Not a weakness worth
trading the semantic assertion for a pinned sentence, which is what criterion 1
explicitly rules out.
