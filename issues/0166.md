## Description

`#0136` moved workshop body rendering to goldmark on the server and deleted `renderMarkdownPreview`, which had run **every body link** through `isSafeLinkHref`. Goldmark's safe mode refuses dangerous *schemes* but enforces less than that validator did, so three forms now render as live links where they previously did not:

1. **`//evil.host/x`** — resolves to `https://evil.host/x`.
2. **`///evil.host/x`** — resolves off-site identically. Any replacement rule must match the **normalized** form, not a literal two-slash prefix.
3. **`data:image/png|gif|jpeg|webp`** — survives as a live `<a href="data:…">`, because goldmark's `IsDangerousURL` allowlists those four types. The deleted validator rejected all `data:`. Found by `#0136`'s review and **not disclosed by the implementer**, unlike the first form.

**None of this is a live vulnerability.** `#0138` decided body links may point off-site by design, so `//evil.host` grants nothing an ordinary `https://evil.host` link didn't; §9's self-contained rule governs loads the page performs, not navigations a reader chooses. `data:image/svg+xml` **is** still refused (verified), and browsers block top-level `data:` navigation. The property is also inherited unchanged from campaigns, which render through the same function.

**The reason it needs an owner** is bookkeeping, not risk: `#0138`'s acceptance criterion 5 explicitly extended its ruling to "link destinations in Markdown body text". That box is ticked and `#0138` is resolved — but `#0136` deleted the only code enforcing it. The tracker currently claims a rule that nothing implements.

## Root cause

`#0136` moved workshop body rendering from the client (`web/src/lib/markdown.ts`'s
`renderMarkdownPreview`, which ran every body link through `isSafeLinkHref`
before that module was later renamed `linkSafety.ts` by `#0157`) to the
server, through `internal/mailing.RenderMarkdownHTML` — the same goldmark
pipeline `email_campaigns.body_md` has rendered through since `#0042`/`#0043`.
Goldmark's own safe mode (`html.IsDangerousURL`) refuses a link whose
*scheme* is dangerous (`javascript:`, `vbscript:`, `file:`, most `data:`
subtypes) but does not refuse a *protocol-relative* destination, and it
allowlists four `data:image/*` raster subtypes the deleted validator refused
outright. `#0138`'s criterion 5 had explicitly extended its cover-image URL
ruling to body links specifically so this class of narrowing wouldn't slip
through unnoticed — but `#0136` deleted the only code that enforced it and
nothing replaced it server-side, so the tracker was left claiming a rule
nothing implemented. That gap, not any live vulnerability, is what this issue
closes.

## Fix

**Decision: amend `#0138`'s criterion 5, do not rebuild a body-link
validator.** `#0138`'s own ruling on body links was that they may point
off-site by design — a workshop's `signup_url` is routinely an external
ticketing page, and a body link is a navigation the reader chooses, not a
load the page performs unasked (the distinction §9's self-contained rule
actually turns on). Given that, `//evil.host/x` and `///evil.host/x` both
resolve (verified with Node's WHATWG `URL` against
`https://www.opencircuitsf.com/workshops/soldering-101`) to
`https://evil.host/x` — exactly the plain absolute-https link `#0138` always
permitted. Enforcing the two/three-slash *spelling* against body links would
have reproduced a rule that grants nothing over what `https://evil.host/x`
already allows. `#0136`'s reviewer reached the identical conclusion
independently while reviewing that issue. `#0138.md` now carries a dated note
on criterion 5 recording this reasoning in place; see that file's diff.

**The alternative considered and rejected: restore a server-side body-link
validator** (a Go twin of the deleted `isSafeLinkHref`, run over every body
link before goldmark renders it, or a custom goldmark link-destination
transformer). Rejected because:

1. It would buy nothing over the status quo — see the resolution argument
   above; the two/three-slash forms already reduce to an always-permitted
   absolute URL.
2. It would be a *third* implementation of "safe URL" alongside the existing
   Go/TS `isSafeLinkHref`/`isSafeCoverImage` twins `#0157`'s fixture already
   guards — exactly the drift-risk shape `#0157` exists to prevent, applied
   to a case that doesn't need a rule at all.
3. It would diverge workshops from campaigns for no reason: both bodies
   render through the identical `mailing.RenderMarkdownHTML`, and a
   workshop-only link validator would either have to also apply to campaigns
   (out of this issue's scope, a mailing-subsystem change) or leave the two
   bodies with different link policies for the first time.

**The `data:image/*` exception, checked rather than assumed:**

- `data:image/svg+xml` **is** still refused — re-verified by executing the
  real `RenderMarkdownHTML` on
  `[x](data:image/svg+xml;base64,PHN2ZyB4bWxucz0iaHR0cDovL3d3dy53My5vcmcvMjAwMC9zdmciLz4=)`;
  it emits `href=""` (goldmark drops the destination). Pinned by
  `TestRenderMarkdownHTML_BodyLinkPolicyDocumented`'s
  `"data:image/svg+xml stays refused"` subtest.
- `data:image/png|gif|jpeg|webp` **do** survive as a live
  `<a href="data:...">` — reproduced by executing `RenderMarkdownHTML` on all
  four subtypes (see `## Verification`).
- What that live `href` actually does: a `data:` URL cannot be a top-level
  navigation target in a modern browser. Verified empirically, not assumed —
  a real headless Chromium (`playwright-core`'s bundled `chromium-1234`, the
  project's own browser per `CLAUDE.md`'s gotchas) loaded a minimal page with
  `<a href="data:image/png;base64,...">`, clicked it, and the click produced
  no navigation (`page.url()` stayed `about:blank`) and one console message:
  `Not allowed to navigate top frame to data URL: data:image/png;base64,...`.
  So the emitted `href` is inert in the one context a body link is ever
  rendered in (a clicked `<a>` in a browser tab) — genuinely inert, not a
  finding requiring a fix. Recorded in `#0138`'s amendment note.

**The `#0157` fixture gap.** `#0157`'s `scheme-shape` source group tests
`javascript:`/`mailto:`/`data:text/html`/etc. shapes only for `link_href`;
`cover_image` had no `data:` case at all, even though both twins already
reject every `data:` spelling structurally (`isSafeCoverImage` requires a
leading `/`, which no `data:` URI has). `#0157`'s `## Fix` documents the
fixture as generated by a throwaway Node script (V8-ground-truth codepoint
sweep) cross-checked against a throwaway Go test
(`GENERATE_URL_FIXTURE=1 go test ... -run TestGenerateURLFixture`) — both
deleted after the fixture was frozen, and neither exists in this checkout or
anywhere in `git log` (confirmed: no committed generator script, no deleted
generator ever appears in history). There is no generator left to extend, so
this pass hand-appended exactly one JSON object to the end of the array —
`{"id":"cover_image-scheme-shape-3139","rule":"cover_image","source":"scheme-shape","value":"data:image/png;base64,…","want":false}`
— after independently computing `want` by executing the real
`web/src/lib/workshopAdmin.ts` `isSafeCoverImage` under Node 26 (native
`.ts` import) and the real Go `internal/handlers.isSafeCoverImage` under a
throwaway `go test` (deleted immediately after, `git status` clean
afterward), matching the fixture's own generation methodology on this one
case even though the batch script itself couldn't be rerun. The append was
verified to be a pure suffix: `new[:len(old)] == old` byte-for-byte before
writing.
