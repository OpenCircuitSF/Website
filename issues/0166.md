## Description

`#0136` moved workshop body rendering to goldmark on the server and deleted `renderMarkdownPreview`, which had run **every body link** through `isSafeLinkHref`. Goldmark's safe mode refuses dangerous *schemes* but enforces less than that validator did, so three forms now render as live links where they previously did not:

1. **`//evil.host/x`** — resolves to `https://evil.host/x`.
2. **`///evil.host/x`** — resolves off-site identically. Any replacement rule must match the **normalized** form, not a literal two-slash prefix.
3. **`data:image/png|gif|jpeg|webp`** — survives as a live `<a href="data:…">`, because goldmark's `IsDangerousURL` allowlists those four types. The deleted validator rejected all `data:`. Found by `#0136`'s review and **not disclosed by the implementer**, unlike the first form.

**None of this is a live vulnerability.** `#0138` decided body links may point off-site by design, so `//evil.host` grants nothing an ordinary `https://evil.host` link didn't; §9's self-contained rule governs loads the page performs, not navigations a reader chooses. `data:image/svg+xml` **is** still refused (verified), and browsers block top-level `data:` navigation. The property is also inherited unchanged from campaigns, which render through the same function.

**The reason it needs an owner** is bookkeeping, not risk: `#0138`'s acceptance criterion 5 explicitly extended its ruling to "link destinations in Markdown body text". That box is ticked and `#0138` is resolved — but `#0136` deleted the only code enforcing it. The tracker currently claims a rule that nothing implements.

## Acceptance criteria

- [ ] Decide, and record: does `#0138`'s body-link rule still apply? Either restore it server-side, or amend `#0138`'s criterion 5 with a note saying it no longer holds and why
- [ ] If restoring: enforce on the **normalized** destination so `//host`, `///host`, and backslash spellings are all caught, and decide whether `data:image/*` should stay allowed
- [ ] Whatever is decided applies to `email_campaigns.body_md` too, or the decision records why the two bodies differ — they share `mailing.RenderMarkdownHTML`
- [ ] Tests cover all three forms plus the legitimate cases that must keep working (`https://`, `mailto:`, root-relative)
- [ ] Add a `cover_image` `data:` case to `#0157`'s fixture (`testdata/url_validators.json`). Its `scheme-shape` group is `link_href`-only, so `data:image/png;base64,…` has no cover-image case at all. Both twins already reject it — Go's `isSafeCoverImage` requires a leading `/`, so every `data:` spelling dies structurally — making this a coverage gap rather than a defect. But a base64 image is the most plausible thing an admin pastes into that field, and `#0157`'s reviewer noted it closes naturally alongside this issue's `data:image/*` finding
- [ ] `ISSUE=0166 scripts/check.sh go ./internal/...` passes

## Notes

Reported by `#0136`'s phase-3 review under `CLAUDE.md` §9, which ruled the narrowing acceptable but found no existing issue that owns it: `#0138` is resolved, and `#0157` owns a build-time guard over two Go↔TS twins, not a third rule living inside goldmark.

Worth weighing before doing the work: the honest reading may be that `#0138`'s rule was always about *images* and *cover art*, and that extending it to body links was over-application. Amending the criterion is a legitimate outcome and cheaper than a validator nobody needs.
