## Description

Three small, specific items found by `#0063`'s phase-3 re-review. None falsifies
a ticked criterion — the issue passed — but each sits inside work that pass
touched, which is what makes them worth closing together rather than letting
them scatter.

**1. `PreferenceCenter.svelte:226-229`'s `loadState === 'error'` branch gets
neither decided pattern.** It is a whole-panel swap with no focus movement —
while its two sibling branches received exactly that treatment in the same fix
pass, and `ConfirmSubscription`'s identical case did too. So one public flow
has an inconsistency introduced by the pass that fixed its neighbours. A
subscriber whose preference page fails to load is the person least able to
afford a silent failure.

**2. `aria-describedby` / `aria-invalid` exist on exactly one field in the whole
SPA.** `#0063`'s criterion 7 is ticked unqualified with no supporting section.
It genuinely holds for the four public flows — the re-review proved the only
field-level case live — but not for `/login` or the admin console. Criteria 1, 2
and 10 all carry scope annotations; this one should too, or the gap should be
closed.

**3. `WorkshopEditor.svelte:636` says "~10" placeholders; the real figure is
14**, which is what the issue body says. A stale count in a comment, which is
the class `#0220` exists to catch.

## Notes

Reported by `#0063`'s phase-3 re-review under `CLAUDE.md` §9.

Item 2 is the one with judgement in it. Ticking a criterion that holds for the
public flows and not the console is defensible — the console has one admin, the
public flows have every subscriber — but it should say so. `#0063`'s other
criteria already model this; the annotation is the fix, not necessarily the
code.

**A note on evidence for item 1**, carried from that re-review: it is the first
pass in which `document.hasFocus()` was `true`, so the painted focus indicator
was measured directly — `outline: solid 2px rgb(104,255,35)` (`--accent`) with
`:focus-visible` matching. A literal Tab traversal is still not measurable,
because macOS Safari's default keyboard setting visits form controls only,
skipping every `<a>`. That is an OS setting rather than a site defect, and it is
why `#0063`'s criterion 1 rests on a by-construction argument.

## Work log

**Item 1 — `PreferenceCenter.svelte`'s `loadState === 'error'` branch.**
Added an `errorMessage` ref (`web/src/views/PreferenceCenter.svelte`): the
error `<p>` now carries `tabindex="-1"` + `bind:this={errorMessage}`, and
`onMount`'s `.catch()` handler (`.catch(async (err) => { ...; loadState =
'error'; await tick(); errorMessage?.focus(); })`) moves focus to it once it
mounts — matching `unsubscribed`/`unsubscribeNoOp`'s existing pattern in the
same file and `ConfirmSubscription.svelte`'s `confirming -> error`
transition. Reused the `.result-message` class already defined in this
file's `<style>` block for the `:focus` accent ring (no new CSS needed).

While implementing #0242's guard against the real tree, the identical gap
turned up one branch over in the SAME if/else chain: the `!isActive` branch
(both its `showSubscribeAgainAffordance` true/false sub-branches) had no
focus management either, reached the same way (the same `onMount` fetch
resolving). Given `loadState === 'error'` in this file, its sibling notices,
and `ConfirmSubscription.svelte`'s equivalent transition all now get this
treatment, leaving `!isActive` as the one remaining inconsistency would have
been indefensible, so it got the same fix (one shared `inactiveNotice` ref
bound on both its `<p role="status">` elements, focused from the same
`.then()` callback when `res.status !== 'active'`). Out of this issue's
literal text but directly downstream of it; disclosed here rather than left
unmentioned.

**Item 2 — criterion 7 scope annotation.** `issues/0063.md`'s criterion 7
("Form errors announced and programmatically associated with their fields")
now carries the same style of scope annotation criteria 1, 2, and 10 already
had: it holds for the four public transactional flows (`SubscribeForm
.svelte:145-146` is the only public field-level `aria-describedby`/
`aria-invalid` pairing; the preference center's and `/login`'s remaining
errors are form-level `aria-live` regions or unassociated) and does **not**
hold for `/login`'s two email fields or any admin form error.

**Item 3 — `WorkshopEditor.svelte:636`'s stale count.** Corrected, and
re-derived from the tree rather than copied from either `#0063.md` or
`#0244.md`'s own filed text: `grep -rn 'role="status"' web/src | grep -v
'\.test\.ts' | grep -i loading` finds **17** placeholders today (not the
"~10" the comment said, and not even the "14" `#0063`'s own contemporaneous
count said — one more site, `Dashboard.svelte`'s "Loading overview…", has
grown this exact shape since `#0063` shipped). The comment now says 17 and
explains why that number can drift, pointing at
`liveRegionGuard.structuralGuard.test.ts` (`#0242`/`#0243`) for the current
authoritative count (20 — that guard's allowlist additionally names two
more same-shape sites that aren't worded "Loading…", see `#0242`'s Work
log).
