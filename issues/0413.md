## Description

`internal/db`'s doc-parity guard finds a documented migration range with
`docRangePattern`, which requires the word `numbered` or `contiguous`
immediately before a backticked range. **The alternation has no leading word
boundary**, so a word merely *ending* in one of those — `renumbered` — also
matches.

`PRD.md` carries `renumbered` followed by a range (`000001`–`000007`), which the
pattern matches. **Nothing fails today** because `PRD.md` is not among the files
the guard checks. But adding it — or moving that prose into a file that is
checked — would silently pin the guard to the **wrong range**, and the guard
would then pass while measuring something nobody intended.

This is `#0218`'s family: a pattern that quietly matches more than its author
described. Latent rather than live, exactly like `#0395`'s nested-fence case.

**Reported by `#0407`'s review**, which found it while confirming the pattern
matched exactly once in `CLAUDE.md`.

**Unverified by the orchestrator** — the `renumbered` match is the reviewer's
measurement. Reproduce it before building on it.

## The suggested fix

A `\b` before the alternation. One character, and it makes the pattern mean what
its name and its doc comment already claim.

## Verification

**The `renumbered` match reproduced (was unverified — see the filed note
above).** `PRD.md` (`grep -n "renumbered" PRD.md`, at the §3.1
"Copy unchanged" table row): `| \`internal/auth/\` (13KB) | Auth schema,
renumbered \`000001\`–\`000007\` |`. Ran the Go pattern's exact translation
against `PRD.md`'s bytes (`python3`, `.decode('utf-8')`, never BSD `grep -P`):

```
before: (?:numbered|contiguous) `(\d{6})`[–-]`(\d{6})`
  -> matches "numbered `000001`–`000007`" (inside "renumbered"), 1 match
after:  \b(?:numbered|contiguous) `(\d{6})`[–-]`(\d{6})`
  -> 0 matches
```

**Fix applied**: `internal/db/docs_parity_test.go`'s `docRangePattern` gained a
leading `\b` before the alternation (was
`"(?:numbered|contiguous) \`(\\d{6})\`[–-]\`(\\d{6})\`"`, now
`"\\b(?:numbered|contiguous) \`(\\d{6})\`[–-]\`(\\d{6})\`"`), plus a doc-comment
line naming the `renumbered` hazard and this issue.

**Legitimate matches unaffected, and CLAUDE.md's single match confirmed
unchanged (criterion 3).** Same `python3`-bytes harness run before and after
against both guarded files:

- `CLAUDE.md`: before **and** after, exactly 1 match, both
  `"contiguous \`000001\`–\`000027\`"`, at the same byte offset (the
  Repository-layout table row) — unchanged.
- `docs/database.md`: before and after, 1 match, identical match text
  (`match equal: True`) — unchanged.
- `PRD.md`: before 1 (the `renumbered` false positive), after 0 — this is the
  intended change, and `PRD.md` is not in the guarded file set so nothing in
  the actual test suite depended on it.

**Criterion 4 — should the guarded file set widen to include `PRD.md`? No,
and not as a consequence of this fix.** `internal/db/docs_parity_test.go`'s
`docParityCase` list (`docsPath` = `docs/database.md`, `claudeMDPath` =
`CLAUDE.md`) is exactly two files, and `TestDatabaseDocMigrationParity`
`t.Fatalf`s if `docRangePattern.FindStringSubmatch(doc)` returns `nil` for a
case — the pattern must find its "numbered/contiguous `NNNNNN`–`NNNNNN`"
frozen-range sentence in every guarded file. `PRD.md` does not carry that
sentence: its only near-match was the `renumbered` false positive this fix
just correctly excludes (an unrelated claim, about the Auth-schema migrations
being renumbered during the copy-and-strip, §3.1 — not a frozen-range
assertion), and PRD.md §6.2's own migration-range statement ("Migrations
`000001`–`000022` are now frozen") is phrased without a preceding
`numbered`/`contiguous` token, so it would not match either. Adding `PRD.md`
to `docParityCase` today would make the test fail outright (no match found),
not silently pass on the wrong range — so there is no live hazard requiring
the widen. Manufacturing a matching sentence in `PRD.md` just to admit it into
this guard would be scope beyond the one-character fix and beyond what
criterion 5 permits ("no new mechanism ... beyond the boundary and whatever
criterion 4 concludes"). Conclusion: **do not widen the guarded file set.**
The fix already makes widening *safe* in the narrow sense asked (no
mis-pinning), which is worth recording, but nothing about `PRD.md`'s current
prose calls for actually doing it.

## Review notes

**Verdict: pass**, and the fix is worth more than the issue claimed for it —
see the reframing below.

**My own before/after measurement**, run with `python3` over each file's
**bytes** decoded as UTF-8 (never BSD `grep -P`, per §8), using a pattern
extracted programmatically from the Go source literal rather than retyped, so
the probe cannot drift from what the guard actually compiles:

| File | before (`(?:numbered\|contiguous) …`) | after (`\b(?:numbered\|contiguous) …`) |
|---|---|---|
| `PRD.md` | **1** — `numbered `000001`–`000007`` at line 125, inside `renumbered` | **0** |
| `CLAUDE.md` | 1 — `contiguous `000001`–`000027`` at byte offset 1648, line 37 | **1, same offset, same text** |
| `docs/database.md` | 1 — `numbered `000001`–`000027`` at byte offset 140, line 4 | **1, same offset, same text** |

Criterion 2 and criterion 3 are both satisfied by that table: the false
positive dies, and `CLAUDE.md`'s single match is byte-identical and at the same
row (the Repository-layout table row), not merely still-single. `PRD.md` line
125 is confirmed to sit in §3.1 "Copy unchanged" — the "Auth schema,
renumbered" row — by locating the nearest preceding `##`/`###` heading, so the
occurrence is the one the issue described.

**Criterion 4, assessed rather than accepted — and the implementer's reframing
is correct, though for a slightly stronger reason than they gave.** Both halves
check out:

1. *The guard fails closed on a missing sentence.* `TestDatabaseDocMigrationParity`
   calls `docRangePattern.FindStringSubmatch(doc)` and, on `nil`, `t.Fatalf`s
   with "could not find the numbered/contiguous range sentence". I confirmed
   this by running it, not by reading it — see the mutation table below.
2. *`PRD.md` carries no qualifying sentence.* A whole-file scan for **any**
   backticked six-digit pair finds exactly two occurrences in `PRD.md`: the
   §3.1 `renumbered` row, and one in §6.2's `#0293` correction block reading
   "Migrations `000001`–`000022` are now frozen". The second is preceded
   by the word "Migrations", not `numbered`/`contiguous`, so it does not match
   the pattern in either form. So post-fix `PRD.md` has zero matches, and
   adding it to the guarded set today would `t.Fatalf` outright.

So the hazard as filed — "the guard would then pass while measuring something
nobody intended" — is indeed narrower than described, and in a second way the
implementer did not mention: even **pre-fix**, admitting `PRD.md` would not have
passed silently. The guard does not merely find a range, it asserts both bounds
against the migrations on disk, and the `renumbered` row's `000001`–`000007`
disagrees with the on-disk high of `000027`. It would have failed — with a
confusing message pointing at the wrong sentence, which is a real cost, but not
a silent one. Genuine silence needs a false positive whose bounds *coincide*
with the disk bounds, and there is no such text in the tree.

**But `PRD.md` should not join the guarded set for a reason better than "it
would fail" — the two files measure a different fact than `PRD.md` does.**
`docs/database.md` and `CLAUDE.md` state the range of migration **files on
disk** (`000001`–`000027`, which is what the guard compares against
`migrations/`). `PRD.md` §6.2's only range sentence states the range **applied
to production** (`000001`–`000022`), which §1 is explicit is a dated snapshot
re-derived by `ssh ec2`, not a property of the repository. Wiring the disk-range
guard onto that sentence would pin a production fact to a filesystem
measurement and break on the next deploy — so the right answer is "no", and it
would still be "no" if someone added a `contiguous` to the wording. The
implementer reached the correct conclusion; this is the load-bearing half of
the argument, and it is worth having recorded.

**Is the `\b` still worth having on its own terms? Yes — and it is not purely
latent.** I mutated a **copy** of the tree (a throwaway `git worktree` at
`1c2e3e8` with its own scratch database, per §8a/§8b — the shared tree was never
touched) and ran `TestDatabaseDocMigrationParity` four ways:

| Mutation | Result |
|---|---|
| A — unmutated | `ok` |
| B — `docs/database.md`'s upper bound changed to `000026`, genuinely disagreeing with the `000027` on disk | **FAIL**, naming the stated and on-disk bounds and citing `#0082` |
| C — `docs/database.md`'s `numbered` changed to `renumbered`, fix in place | **FAIL**, the "could not find … range sentence" `Fatalf` — fails closed |
| D — same as C but with the leading `\b` reverted | **`ok`** |

D is the finding that upgrades this issue. With the old pattern, a guarded file
whose range sentence said `renumbered` instead of `numbered` passed **green**:
the guard silently stopped identifying the sentence it was written to identify
and matched mid-word instead. That is not a hypothetical about a file set nobody
plans to widen — it is a live weakness in the guard's own
sentence-identification, in a repository whose §1 prose discusses migrations
being "squashed, renumbered, or rewritten" and where `#0086`'s own comment uses
the word "renumbered". The one-character fix converts that from silent to
`Fatalf`. Criterion 1 is met, and B confirms criterion 4's real worry — that a
boundary fix might break the guard's actual job — does not apply: a genuine
range disagreement still fails, with the same message and the same bounds.

**Nothing else changed.** The diff is the pattern literal plus five doc-comment
lines; no other declaration, no new mechanism (criterion 5). The comment uses
`--` rather than an em dash and contains no doubled `''`, so it is
gofmt-stable, and it carries no `<file>.go:<line>` citation (`#0352`) — it
names `PRD.md`'s §3.1 row and `#0413`, both of which are stable identifiers.
`gofmt -l` reports nothing, checked non-destructively.
