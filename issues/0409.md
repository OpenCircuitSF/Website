# 0409 — A stale session cookie disables `DEV_ADMIN_LOGIN`, locking a developer out of the mode that exists to prevent lockout

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | auth / tooling |
| **Phase** | 0 — Foundation |
| **First seen** | 2026-09-03 |

## Description

`DevAdminAutoLogin` (and `DevAutoLogin` before it) short-circuits when the
request already carries a session cookie:

```go
if c, err := r.Cookie(auth.SessionCookieName); err == nil && c.Value != "" {
    next.ServeHTTP(w, r)
    return
}
```

The comment explains the intent — "let RequireSession validate it normally, no
new token needed" — and for a *valid* cookie that is right. But the branch keys
on the cookie being **present**, not on it being **valid**. A stale, revoked, or
garbage value takes the same path, `RequireSession` rejects it, and the response
is 401. Auto-login never runs.

Measured against the running dev server:

| Request | Result |
|---|---|
| No cookie | **200** — auto-login works |
| Stale cookie (a token whose row was deleted) | **401** |
| Garbage cookie (`opencircuit_session=nonsense`) | **401** |

**The recovery path is manual cookie deletion in devtools**, which is precisely
the friction `#0402` was filed to remove. The user hit this immediately after
`#0402`'s logout fix landed and had to ask how to sign in again.

### Why this is not the same as the bug review already caught

`#0402`'s bounce #2 was the *server-side* cache handing out a token whose row
had been deleted. That is fixed, and the fix is sound. This is the *client-side*
mirror of it: the browser keeps the dead cookie, and its mere presence now
suppresses the auto-login that would otherwise heal the situation. The two
compose badly — sign out, and both halves fire at once.

`POST /auth/logout` deletes the row **and** clears the cookie, so the ordinary
sign-out flow may self-heal in a browser. The states that do not heal are a
cookie surviving a database reset, a token invalidated out of band (this is how
it was found), a `sessions` row expiring, and any hand-set cookie — all routine
in local development.

### Server A — Postgres, `DEV_ADMIN_LOGIN=true`

| Request | This issue measured | Measured now |
|---|---|---|
| No cookie | 200 | **200**, `{"id":1,"email":"admin@localhost","is_admin":true}` |
| Stale cookie (row deleted) | **401** | **200**, with a replacement `Set-Cookie` |
| Garbage cookie | **401** | **200**, with a replacement `Set-Cookie` |
| Unusable bearer alone | not measured | **200** |
| Unusable bearer + stale cookie | not measured | **200** |

A **valid** cookie passed through untouched: 200, zero `Set-Cookie` headers,
and the `sessions` row count unchanged at 1 across the request. Eight
consecutive credential-less requests left **exactly one** row, so the
cache-or-mint contract still holds. `GET /admin/settings` under a stale
cookie and `GET /admin/interests` under a garbage cookie both returned real
admin JSON rather than an SPA shell, so these are the guarded routes and not
a static fallback.

### Server B — Postgres, flag off (the control)

No cookie, a stale cookie, and a garbage cookie each answered **401**. The
fix is inert unless an operator turns it on.

### The residue: `DevAutoLogin` still keys on presence, and it is reachable

`internal/middleware/devauth.go`'s `DevAutoLogin` is byte-for-byte unchanged
and still short-circuits on `err == nil && c.Value != ""`, with the comment
that states the intent which produced this bug. `TestDevAutoLogin_SkipsWhenCookiePresent`
pins that behaviour as intended, so any fix must revise that test rather than
merely satisfy it.

Server C, `STORAGE=json`, measured live:

| Request | Result |
|---|---|
| No cookie | 200, seeded mock admin |
| Garbage cookie | **401** |
| A cookie minted by a *different* server | **401** |
| A cookie this same server minted, after a restart | **401** |

The last row is the one that matters. `internal/devstore` holds sessions in a
plain in-memory map with no persistence, so **every restart of the Go process
invalidates every session while the browser keeps the cookie** — a code edit
under `./scripts/dev.sh`, or simply stopping and starting it. That makes the
json path's exposure strictly worse than the Postgres path's was: there the
lockout needed a database reset or an out-of-band revocation, here it is the
most routine action in the dev loop. The recovery is the same devtools cookie
deletion this issue was filed to eliminate.

### The smallest correct fix, if this is taken as a scope extension

Give `DevAutoLogin` the same validity-keyed shape its sibling already has,
and nothing else. It would take a `SessionResolver` alongside its existing
`devSessionCreator`, resolve the extracted token first, pass through only on
`err == nil`, and otherwise mint — rebuilding the `Cookie` header with
`Header.Set` and deleting `Authorization`, since `sessionToken`'s bearer
preference is a property of the shared extractor and not of either
middleware. The `devMode` panic guard, the `devAuthOnce` warning, and the
`serveDevMode` wiring all stay exactly as they are; the only call site
already has the dev store, which is itself the resolver. Its cheapest proof
is a sibling of `TestDevAdminAutoLogin_StaleCookieHeals` driving a stale and
a garbage cookie through a composed `RequireSession`, plus a rewrite of
`TestDevAutoLogin_SkipsWhenCookiePresent` to assert pass-through on a
**valid** cookie rather than a present one.

### One acceptance criterion is met by weaker evidence than it asks for

The criterion asking for a DB-backed test driving all four states through the
real `mountAndServe` route table is only partly satisfied.
`TestNewDevAdminAutoLogin_RealRouteTable` drives the no-credential, flag-off,
and one-row-cache states through that table, while the stale and garbage
states are pinned one layer down by `TestDevAdminAutoLogin_StaleCookieHeals`
and `TestDevAdminAutoLogin_GarbageCookieHeals` against a composed
`RequireSession` with a fake resolver. This pass drove all five states
through the real route table in a real binary, which is stronger evidence
than either test but is not a regression pin — nothing would catch a
reintroduction at the wiring layer.

## Proposed fix

Make the short-circuit depend on the cookie being **usable**, not merely
present. Two shapes, either acceptable:

- **Validate first**: resolve the cookie; if it resolves to a live session, pass
  through unchanged; if it does not, fall through to minting. Costs one lookup
  on a dev-only path.
- **Overwrite unconditionally**: in `DEV_ADMIN_LOGIN` mode, always mint and set
  the cookie. Simpler, and defensible because the mode's entire contract is
  "you are the admin" — but it discards a *deliberately* set cookie, which
  matters if anyone tests multi-user behaviour locally.

Prefer validate-first: it preserves a real session when there is one, and heals
when there is not.

**Do not change `DevAutoLogin`'s `STORAGE=json` behaviour as a side effect**
unless the same defect is proved there — and if it is, fix it deliberately and
say so. That middleware's `devMode` panic guard and its wiring have now been
verified across three review passes and must stay intact.

## Acceptance criteria

- [ ] With `DEV_ADMIN_LOGIN` active, a request carrying a **stale** session cookie is authenticated as the admin rather than answered 401 — the response must also replace the dead cookie, or the next request repeats the lookup forever
- [ ] Same for a **garbage** cookie value
- [ ] A **valid** session cookie still passes through untouched: no new `sessions` row, no cookie rewrite — asserted on the row count, mirroring `#0402`'s existing cache test
- [ ] The behaviour is unchanged when the flag is off: a stale cookie still yields 401 on the Postgres path
- [ ] The token cache from `#0402`'s bounce-#2 fix still holds — repeated cookie-less requests leave exactly one row
- [ ] A DB-backed test drives all four states (none, valid, stale, garbage) through the **real** `mountAndServe` route table
- [ ] `internal/middleware/devauth.go`'s comment is rewritten: it currently states the intent that produced the bug, and a reader following it would reintroduce this

## Notes

Found 2026-09-03 by the orchestrator while answering the user's question "I need
to sign in again. What is the cookie again?" — the answer being that no cookie
should ever have been needed.

The immediate workaround, for anyone who hits this before it is fixed: clear the
cookie in the browser console and reload.

```js
document.cookie = "opencircuit_session=; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT"
```

**The shape worth remembering**: a guard that tests for the *presence* of a
credential rather than its *validity*. It reads as a safe pass-through and is
one, right up until the credential goes bad — at which point it converts a
self-healing system into a stuck one.
