## Description

`DevAdminAutoLogin` (and `DevAutoLogin` before it) short-circuits when the
request already carries a session cookie:

```go
if c, err := r.Cookie(auth.SessionCookieName); err == nil && c.Value != "" {
    next.ServeHTTP(w, r)
    return
}
```

The comment explains the intent — "let RequireSession validate it normally, no
new token needed" — and for a *valid* cookie that is right. But the branch keys
on the cookie being **present**, not on it being **valid**. A stale, revoked, or
garbage value takes the same path, `RequireSession` rejects it, and the response
is 401. Auto-login never runs.

Measured against the running dev server:

| Request | Result |
|---|---|
| No cookie | **200** — auto-login works |
| Stale cookie (a token whose row was deleted) | **401** |
| Garbage cookie (`opencircuit_session=nonsense`) | **401** |

**The recovery path is manual cookie deletion in devtools**, which is precisely
the friction `#0402` was filed to remove. The user hit this immediately after
`#0402`'s logout fix landed and had to ask how to sign in again.

### Why this is not the same as the bug review already caught

`#0402`'s bounce #2 was the *server-side* cache handing out a token whose row
had been deleted. That is fixed, and the fix is sound. This is the *client-side*
mirror of it: the browser keeps the dead cookie, and its mere presence now
suppresses the auto-login that would otherwise heal the situation. The two
compose badly — sign out, and both halves fire at once.

`POST /auth/logout` deletes the row **and** clears the cookie, so the ordinary
sign-out flow may self-heal in a browser. The states that do not heal are a
cookie surviving a database reset, a token invalidated out of band (this is how
it was found), a `sessions` row expiring, and any hand-set cookie — all routine
in local development.

## Root cause

`DevAutoLogin`'s short-circuit keyed on `r.Cookie(auth.SessionCookieName)`
returning without error and a non-empty value — that is, on a session
cookie being *present*, not on it being *valid*. `internal/devstore`'s
`Store` keeps sessions in a plain in-memory map with no persistence, so a
process restart under `STORAGE=json` empties that map while the browser
keeps its cookie. The next request still carries a "present" cookie, so
auto-login skipped and `RequireSession` rejected the now-unknown token with
401 — a self-healing system converted into a stuck one, exactly the shape
the sibling defect in `DevAdminAutoLogin` had before the verification pass
that reopened this issue proved it closed by construction there and still
reachable here.

## Fix

Gave `DevAutoLogin` a `middleware.SessionResolver` parameter alongside its
existing `devSessionCreator`, mirroring `DevAdminAutoLogin`'s already-proven
shape: extract the token with the shared `sessionToken` helper, resolve it
first, and pass the request through completely unchanged only when
`ResolveSession` returns no error. Any other case — no token, or an
unusable one (absent, stale, garbage, expired) — mints a fresh dev session
for the seeded mock admin, rebuilds the `Cookie` header from scratch with
`Header.Set` (never `Header.Add`/`r.AddCookie`, which appends behind a
still-live stale entry that `sessionToken`'s first-match extraction would
keep honouring), and drops any `Authorization` header so an unusable bearer
token cannot win by that second route.

The sole call site, `serveDevMode` in `cmd/opencircuit/main.go`, already
held `ds` (the dev store), which was already passed to
`middleware.RequireSession` a few lines above as its `SessionResolver` —
`internal/devstore.Store` satisfies both `devSessionCreator` and
`SessionResolver` already, so the fix is passing `ds` a second time, not
new plumbing. Added a nil-resolver panic at construction, mirroring
`DevAdminAutoLogin`'s guard against the same class of miswiring. The
`devMode` panic guard, `devAuthOnce`, and the `serveDevMode` wiring shape
(order of `requireSession`/`requireAdmin`/`devAutoLogin` construction) are
byte-for-byte unchanged — confirmed by reading `git diff` for both files
before committing.

`TestDevAutoLogin_SkipsWhenCookiePresent` asserted the buggy presence-only
behaviour as intended, so it was rewritten rather than merely satisfied: it
now registers a *valid* session with the fake store first and asserts
pass-through keyed on that validity, and is renamed
`TestDevAutoLogin_PassesThroughValidCookie` to say so. Two new regression
pins were added alongside it, mirroring `DevAdminAutoLogin`'s existing
stale/garbage tests: one drives a stale cookie (a token the fake resolver
has never heard of) through a composed `RequireSession` chain and asserts
200 plus exactly one surviving session cookie in the rebuilt header; the
other drives a garbage cookie value through the same chain. A
`TestDevAutoLogin_PanicsOnNilResolver` test was added for the new
construction-time guard.

`#0402`'s criterion 6 (a DB-backed test driving stale/garbage through the
real `mountAndServe` route table) was left as-is for the Postgres path.
Extending `TestNewDevAdminAutoLogin_RealRouteTable` to add those two states
would mean building requests with an explicit stale/garbage `Cookie` header
against server A (its `http.Client` today has no `CookieJar` and issues
only credential-less `client.Get` calls) and inserting then deleting a real
`sessions` row via `pool.Exec` to produce the stale case — a real but
non-trivial addition to a DB-backed `cmd/opencircuit` test, which costs
roughly 8× `internal/db` per `CLAUDE.md` §5a, and it is the Postgres/
`DevAdminAutoLogin` side rather than the `STORAGE=json`/`DevAutoLogin` side
this pass's scope covers. Left alone rather than grown this pass, per the
instruction not to let it expand here.

`r.Header.Del("Authorization")` in `DevAutoLogin` is load-bearing and
unpinned. This was verified behaviourally, not assumed: a temporary probe
composing `DevAutoLogin` over `RequireSession` and issuing one request
carrying `Authorization: Bearer unusable-garbage-token` returns **200**
against the committed code and **401** with that single line deleted. A 401
that auto-login cannot heal is precisely this issue's defect, arriving by the
route the middleware's own doc comment calls out — `sessionToken` prefers the
bearer header over the cookie, so a stale bearer survives a successful mint
unless it is deleted.

`DevAdminAutoLogin` already has exactly this regression pin. The commit
message and doc comment both describe this change as mirroring that sibling's
tests; the stale and garbage siblings were mirrored and this one was not.

**The remedy, precisely:** add one test to
`internal/middleware/devauth_test.go`, modelled on
`TestDevAdminAutoLogin_UnusableBearerTokenDropped` in
`internal/middleware/devadminauth_test.go` and named the same way with the
middleware prefix swapped to match the function under test. It should build
the chain as `DevAutoLogin(store, store, true)(RequireSession(store)(inner))`

`Authorization: Bearer unusable-garbage-token` and no cookie, and assert

`Authorization` header observed at the inner handler is empty. Capturing the
header requires the same interposed `http.HandlerFunc` the sibling uses,
since the assertion is about what `RequireSession` sees rather than about the
response. Nothing else in the commit needs to change.

That is the entire remedy — no design decision is left open, so this stays a
Sonnet pass (`CLAUDE.md` §3).

## Proposed fix

Make the short-circuit depend on the cookie being **usable**, not merely
present. Two shapes, either acceptable:

- **Validate first**: resolve the cookie; if it resolves to a live session, pass
  through unchanged; if it does not, fall through to minting. Costs one lookup
  on a dev-only path.
- **Overwrite unconditionally**: in `DEV_ADMIN_LOGIN` mode, always mint and set
  the cookie. Simpler, and defensible because the mode's entire contract is
  "you are the admin" — but it discards a *deliberately* set cookie, which
  matters if anyone tests multi-user behaviour locally.

Prefer validate-first: it preserves a real session when there is one, and heals
when there is not.

**Do not change `DevAutoLogin`'s `STORAGE=json` behaviour as a side effect**
unless the same defect is proved there — and if it is, fix it deliberately and
say so. That middleware's `devMode` panic guard and its wiring have now been
verified across three review passes and must stay intact.

- [ ] With `DEV_ADMIN_LOGIN` active, a request carrying a **stale** session cookie is authenticated as the admin rather than answered 401 — the response must also replace the dead cookie, or the next request repeats the lookup forever

- [ ] A **valid** session cookie still passes through untouched: no new `sessions` row, no cookie rewrite — asserted on the row count, mirroring `#0402`'s existing cache test

- [ ] `internal/middleware/devauth.go`'s comment is rewritten: it currently states the intent that produced the bug, and a reader following it would reintroduce this

## Notes

Found 2026-09-03 by the orchestrator while answering the user's question "I need
to sign in again. What is the cookie again?" — the answer being that no cookie
should ever have been needed.

The immediate workaround, for anyone who hits this before it is fixed: clear the
cookie in the browser console and reload.

```js
document.cookie = "opencircuit_session=; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT"
```

**The shape worth remembering**: a guard that tests for the *presence* of a
credential rather than its *validity*. It reads as a safe pass-through and is
one, right up until the credential goes bad — at which point it converts a
self-healing system into a stuck one.
