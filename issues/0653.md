## Description

This is part of the request in `#0652`: Home Assistant checks once a day whether there's been any engagement on Bluesky or Mastodon.

The data already exists:
- `outreach_engagement` (migration 35) stores snapshots of likes, reposts, replies and quotes per post. Captures run hourly for a post's first week and daily up to 30 days (`internal/outreach/engagement.go`).
- `outreach_mentions` stores fetched mentions per channel.

The endpoint summarises the change over a window. It is shaped so a Home Assistant REST sensor can read it with a simple template.

Decisions:
- **Auth.** A bearer token with the `engagement:read` scope, from `#0652`.
- **Window.** Defaults to the last 24 hours. `?hours=N` accepts 1 to 168, or `?since=<RFC 3339>`. The response echoes the window it used.
- **"New" interactions** are the increase in each counter between the last snapshot before the window and the latest snapshot in it. They are never negative: a fall, such as an unlike, counts as 0. A post first captured inside the window counts its whole total.
- **Mentions** are the rows in `outreach_mentions` created or fetched within the window.
- **Response.** A flat top level so Home Assistant templates stay short, plus detail:

      {
        "since": "...", "until": "...",
        "has_engagement": true,
        "total": 7,
        "bluesky": {"likes": 3, "reposts": 1, "replies": 0, "quotes": 0, "mentions": 1, "total": 5},
        "mastodon": {"likes": 2, "reposts": 0, "replies": 0, "quotes": 0, "mentions": 0, "total": 2},
        "posts": [{"event": "Hack Night", "event_date": "2026-11-09", "wave": "reminder", "channel": "bluesky", "url": "...", "likes": 2, "...": 0}],
        "summary": "7 new interactions: Bluesky 5 (3 likes, 1 repost, 1 mention), Mastodon 2 (2 likes)."
      }

  `summary` is a plain sentence that Home Assistant can pass straight into a notification. When nothing happened, it reads `No new engagement on Bluesky or Mastodon in the last 24 hours.`
- **Read-only.** The endpoint doesn't trigger a capture; it reports what the existing pollers stored. Each response says when the latest snapshot was taken (`data_as_of`), so a stalled poller can be spotted.
- **Visible text.** The copy guard's banned words ("wave", "held") apply only to visible SPA text, and `wave` here is a JSON key. The planner confirms that.

## Acceptance criteria

- [ ] With a valid `engagement:read` token, the endpoint returns the shape above for the default 24 hours, for `?hours=`, and for `?since=`. Out-of-range or malformed values return `400`.
- [ ] Interaction deltas are correct across snapshots. An unlike never produces a negative count, and a first capture inside the window counts in full. Table tests cover each case.
- [ ] Mentions inside the window are counted per channel.
- [ ] `summary` and `has_engagement` are right for both the empty case and a mixed case.
- [ ] `data_as_of` reports the newest snapshot time.
- [ ] Without a token the endpoint returns `401`, and with the wrong scope `403`, as set up in `#0652`.

- No counter has fallen yet, but nothing prevents it. An unlike, or a deleted repost, lowers the next snapshot.

### Decisions

**The window** is half-open, `(since, until]`. `until` is the request time, `h.now().UTC().Truncate(time.Second)`. `since` is either `until − hours` or the parsed `?since=`, also UTC and truncated to the second.

**The per-post delta.** For each Bluesky or Mastodon post:
- `current` is the latest snapshot with `captured_at <= until`.
- `baseline` is the latest snapshot with `captured_at <= since`, which may not exist.
- Only posts whose `current.captured_at > since` are considered, since a post with no capture in the window has a delta of 0.
- Per counter, `delta = max(0, current − baseline)`. With no baseline, `delta = current`, so a first capture inside the window counts in full.
- A post appears in `posts` only when its delta total is above 0.

The delta compares two snapshots and never sums snapshot-to-snapshot steps. A like, then an unlike, then a like again in the window therefore counts 1, not 2. That is intended: the endpoint reports net new interactions.

**Mentions are windowed by `created_at`, not `fetched_at`.**
- `fetched_at` is when our poller happened to see the row. On a first enable, or after an outage, the poller backfills up to 30 days, and every backfilled row has a fresh `fetched_at`. Production's only mention shows this: windowed by `fetched_at`, a six-week-old reply would have been reported as new engagement on the day the poller was switched on.
- `created_at` also makes a window's answer stable: asking twice about the same `(since, until]` gives the same count.
- The cost is a mention created inside the window but fetched only after `until`. The poller runs every 15 minutes, so a daily check misses at most the last few minutes, and the next day's check doesn't pick it up either. This is accepted and noted in the doc comment.

**Mentions don't double-count post counters.** A reply to or quote of one of our posts (`kind IN ('reply','quote')` with `post_id` set) is already in that post's `replies`/`quotes` counter whenever a snapshot of that post was taken at or after the mention's `created_at` and at or before `until`. Those rows are excluded from `mentions`. Every other row counts: plain mentions, replies to posts we don't track, and replies to posts whose captures have stopped (past 30 days).

**`data_as_of`** is `max(captured_at)` over all of `outreach_engagement` with `captured_at <= until`, or `null` when there is none. A stalled poller shows up as a value hours old. The doc comment also says the value goes stale legitimately when no post is younger than 30 days, because nothing is captured then.

The store method runs three queries and computes deltas in Go with `EngagementDelta`, so SQL never does the clamping.

Posts (`$1` = since, `$2` = until, `$3` = `ReportChannels`):

    SELECT p.id, p.channel, p.wave, p.remote_url, p.posted_at, w.title, w.starts_at,
           c.likes, c.reposts, c.replies, c.quotes,
           b.likes, b.reposts, b.replies, b.quotes
    FROM outreach_posts p
    JOIN outreach o ON o.id = p.outreach_id
    JOIN workshops w ON w.id = o.workshop_id
    JOIN LATERAL (SELECT captured_at, likes, reposts, replies, quotes FROM outreach_engagement e
                  WHERE e.post_id = p.id AND e.captured_at <= $2
                  ORDER BY e.captured_at DESC, e.id DESC LIMIT 1) c ON true
    LEFT JOIN LATERAL (SELECT likes, reposts, replies, quotes FROM outreach_engagement e
                  WHERE e.post_id = p.id AND e.captured_at <= $1
                  ORDER BY e.captured_at DESC, e.id DESC LIMIT 1) b ON true
    WHERE p.channel = ANY($3) AND c.captured_at > $1

Scan the baseline into four `*int`. If the first is nil, the baseline is nil; otherwise build a `Counts`. Both laterals use `outreach_engagement_post_captured_idx`. Drop rows whose delta total is 0, then sort in Go with `sort.SliceStable` by delta total desc, then `PostedAt` desc (nil last), then `PostID` asc.

Mentions:

    SELECT m.channel, count(*) FROM outreach_mentions m
    WHERE m.created_at > $1 AND m.created_at <= $2 AND m.channel = ANY($3)
      AND NOT (m.post_id IS NOT NULL AND m.kind IN ('reply','quote') AND EXISTS (
            SELECT 1 FROM outreach_engagement e
            WHERE e.post_id = m.post_id AND e.captured_at >= m.created_at AND e.captured_at <= $2))
    GROUP BY m.channel

Seed `Mentions` with 0 for every `ReportChannels` entry first.

Data as of: `SELECT max(captured_at) FROM outreach_engagement WHERE captured_at <= $1` with `until`, scanned into `*time.Time`.

Wrap errors as `outreach: engagement window: %w`, the package's style.

Also in this file, the pure presentation helpers, so they're tested without a DB:

    // ChannelEngagement is one channel's new interactions in a window.
    type ChannelEngagement struct {
        Counts
        Mentions int
    }
    func (c ChannelEngagement) Total() int   // Counts.Total() + Mentions

    // EngagementSummary is the one-sentence notification text (#0653).
    // windowPhrase is used only by the empty sentence.
    func EngagementSummary(bluesky, mastodon ChannelEngagement, windowPhrase string) string

    // WindowPhrase describes the window for the empty sentence: hours > 0
    // gives "in the last hour" / "in the last N hours"; hours == 0 gives
    // "since Jan 2 at 3:04 PM MST" with since in America/Los_Angeles.
    func WindowPhrase(hours int, since time.Time) string

    // PacificDate formats t's calendar date in America/Los_Angeles as 2006-01-02.
    func PacificDate(t time.Time) string

Load the Pacific location once, in a package var built like `internal/luma/match.go`'s `pacific`, which panics on failure. The binary embeds tzdata through `cmd/opencircuit`'s `time/tzdata` import. The test file must add `_ "time/tzdata"` itself, as `internal/luma/ical_test.go` does.

**Summary grammar**, exactly:
- When the total over both channels is 0, the sentence is `No new engagement on Bluesky or Mastodon ` + windowPhrase + `.`. The default 24-hour window gives `No new engagement on Bluesky or Mastodon in the last 24 hours.`
- Otherwise the sentence is `<N> new interaction` (or `interactions` when N ≠ 1) `: ` + the channel parts joined by `, ` + `.`.
- A channel part is `Bluesky <n> (<items>)` or `Mastodon <n> (<items>)`. A channel with a total of 0 is omitted. Bluesky comes first.
- The items are joined by `, `, in the order likes, reposts, replies, quotes, mentions. Zero items are omitted. Each item is `<k> <noun>`, with the singular noun when k = 1: `like/likes`, `repost/reposts`, `reply/replies`, `quote/quotes`, `mention/mentions`.
- Examples: `7 new interactions: Bluesky 5 (3 likes, 1 repost, 1 mention), Mastodon 2 (2 likes).` and `1 new interaction: Mastodon 1 (1 reply).`

### 2. `internal/handlers/engagement_api.go`

    type engagementWindowStore interface {
        EngagementWindow(ctx context.Context, since, until time.Time) (outreach.EngagementWindow, error)
    }
    type EngagementAPIHandler struct {
        store engagementWindowStore
        now   func() time.Time
    }
    func NewEngagementAPIHandler(store engagementWindowStore) *EngagementAPIHandler  // now = time.Now
    func (h *EngagementAPIHandler) ServeHTTP(w http.ResponseWriter, r *http.Request)

**Parameter validation**, in order. Each failure is `writeError(w, http.StatusBadRequest, msg)`, using these exact messages:
1. `q.Has("hours") && q.Has("since")` gives `use either hours or since, not both`.
2. `hours` present: `strconv.Atoi`. An error, `< 1` or `> 168` gives `hours must be a whole number from 1 to 168`. An empty `?hours=` takes the same path and fails.
3. `since` present: `time.Parse(time.RFC3339, v)`. An error gives `since must be an RFC 3339 time`. If `since.After(now)`, the message is `since must not be in the future`. If `now.Sub(since) > 30*24*time.Hour`, the message is `since must be within the last 30 days`. `since == now` is allowed and returns the empty report.
4. Neither present: `hours = 24`.

Other query parameters are ignored. When `since` is given, the handler uses `hours = 0` for `WindowPhrase`.

A store error gives `writeError(w, 500, "internal error")`, plus one `slog.Error("engagement api: window", "err", err)`. On success it sets `Cache-Control: no-store` (the middleware already does; set it again so the handler is safe alone) and calls `writeJSON(w, 200, resp)`.

**JSON**: every time is `time.RFC3339` in UTC (`t.UTC().Format(time.RFC3339)`, giving `…Z`).

- **Deltas.** `EngagementDelta` clamps each counter at 0, and a nil baseline counts in full.
