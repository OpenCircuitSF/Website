## Description

`#0260` routed registration and recovery mail through `outbound_queue` instead
of calling the mailer directly. `SESMailer.SendVerification` and
`SESMailer.SendRecovery` therefore have no production callers left. Only
`SendSessionsRevoked` is still live on that interface.

They remain on the `Mailer` interface, so every implementation must still
provide them and a reader cannot tell from the interface which methods are real.

Low priority — nothing is broken. It is a tidiness and legibility item, filed so
the dead surface is a recorded decision rather than something the next agent has
to re-derive.

## Acceptance criteria

1. Decide explicitly between narrowing the `Mailer` interface to what is live
   and retaining the methods, and record the decision in the code.
2. If narrowed: `SendVerification`/`SendRecovery` come off the interface and off
   every implementation that only had them to satisfy it. `SendSessionsRevoked`
   stays.
3. If retained: a doc comment on each says it has no production caller and why
   it is kept, so the next reader does not go looking for one.
4. Whichever is chosen, `internal/auth`'s no-op and test mailers stay consistent
   with it — do not leave an implementation carrying a method the interface no
   longer names.
5. Note the interaction with [#0277](0277.md), which may delete
   `auth.NoOpMailer`'s equivalents. Sequence the two rather than having both
   edit the same declarations.
6. `ISSUE=NNNN scripts/check.sh go ./internal/... ./cmd/...` passes with no
   skips.

## Work log

**Decision: RETAIN, not narrow.** `SendVerification`/`SendRecovery` stay on
`auth.Mailer`, implemented by both `SESMailer` and `NoOpMailer`, unchanged in
behavior — only doc comments were added.

Considered narrowing the interface to `SendSessionsRevoked` alone (the only
method with a live production caller). Chose retain instead, for reasons
specific to this codebase rather than a general preference:

- Four test files build fake mailers whose whole purpose is to assert
  `SendVerification`/`SendRecovery` are **not** called by the current
  start-flow: `internal/auth/registration_test.go`'s `recordingMailer`,
  `internal/auth/recovery_test.go`'s `recoveryRecordingMailer`,
  `internal/handlers/logout_all_test.go`'s `logoutAllRecordingMailer`, and
  `internal/handlers/settings_test.go`'s `gateMailer`. Narrowing the
  interface would not have made those assertions wrong, but it would have
  meant rewriting or restructuring all four fakes to drop methods the
  interface no longer named — real surface for a change this issue itself
  describes as "low priority... a tidiness and legibility item."
- `SESMailer.SendVerification`/`SendRecovery` are not merely stubs — they
  correctly enqueue onto `outbound_queue` and are exercised by
  `TestSESMailer_SendVerification_Enqueues`/`_SendRecovery_Enqueues`
  (`internal/auth/ses_mailer_test.go`). Deleting live, tested, correct code
  because its current caller moved elsewhere is a bigger amputation than
  "dead code cleanup" for a one-paragraph tidiness item.
- Retaining costs nothing at compile time or runtime: every implementation
  already had these methods before `#0260`, so "retain" is the zero-diff
  option modulo documentation.

What changed, recorded in the code itself (criterion 1):

- `internal/auth/mailer.go`: the `Mailer` interface doc comment gained a
  `# #0278: SendVerification and SendRecovery are production-dead` section
  naming the decision and why; `SendVerification`'s and `SendRecovery`'s own
  doc comments each got a one-line pointer back to it (criterion 3).
- `internal/auth/ses_mailer.go`: `SESMailer.SendVerification`/`SendRecovery`
  doc comments note no production caller since `#0260` and point back to the
  interface's doc comment.
- `internal/auth/mailer.go`: `NoOpMailer.SendVerification`/`SendRecovery`
  (the pair `#0277` also touches) documented the same way, for consistency
  (criterion 4) — `#0277` retained rather than deleted these, matching this
  decision rather than working at cross purposes with it.
- No implementation lost a method the interface still names, and no
  interface method lost an implementation — criteria 2 and 4 are vacuous
  under "retain" (there is nothing to narrow off, nothing to keep
  consistent by removal) but are satisfied by construction: every
  `Mailer`-implementing type in `internal/auth` and its test files (grepped:
  `recordingMailer`, `recoveryRecordingMailer`, `logoutAllRecordingMailer`,
  `gateMailer`, `NoOpMailer`, `SESMailer`) still implements exactly the same
  three methods the interface still names — none were touched.
- Sequenced after `#0277` per criterion 5 (both touch
  `internal/auth/mailer.go`'s declarations) — `#0277`'s change there
  (documenting `NoOpMailer`'s two methods) landed first in the same session,
  and this issue's edits were made on top of it rather than concurrently.
