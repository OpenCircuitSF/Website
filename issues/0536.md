## Description

While mutation-proofing `#0525` (removing the noindex middleware wrap to prove
the new wiring test fails), the mutated run consistently reported
`context deadline exceeded` from `mountAndServe`'s return after SIGTERM, where
the green path returns `nil`. The observation appeared only in an
already-failing run and has not been reproduced on a passing tree, so it may be
benign shutdown timing — but it is exactly the silent-decline shape CLAUDE.md
§5 warns about (`#0470`): a shutdown that surfaces as a bare expired deadline
with no error in it.

## Characterization

The only return path after SIGTERM is `srv.Shutdown(shutdownCtx)`
(main.go, SIGTERM branch, returned as `shutdownErr`); the worker Stops and
`subscribeH.Close` log their own errors and never reach the return. So a
deadline error after SIGTERM is always `srv.Shutdown` hitting
`shutdownServerTimeout` (5s) with a connection still not idle.
Empirically probed (`.scratch/0536/shutdown_probe.go`, kept untracked) with
the same shape — net.Listen + Serve + Notify + Shutdown:

- idle keep-alive connection → `nil` immediately (the green path every
  wiring test asserts);
- open SSE-style stream (handler alive) → `DeadlineExceeded`, full budget —
  the designed case #0087 documents;
- half-open connection whose request header never completes →
  `DeadlineExceeded`, full budget. Server-side `StateNew` is treated as
  idle only after ~5s of unread header (golang/go#22682), which collides
  with the 5s budget — so "nothing in flight" from any handler's point of
  view can still burn the whole budget.

The deadline is therefore real work, not a mask — but the bare
`context.DeadlineExceeded` says nothing about WHICH connections were still
active, indistinguishable between the benign SSE case and a hang. The
mutated-run observation (#0525's proof) is consistent with this: removing
the noindex wrap (a pure header middleware) cannot alter connection
lifecycle, and this issue's own mutation proof reproduced the bare
`context deadline exceeded` against a half-open connection — the shape,
not the mutation, was the cause.

## Fix

- `cmd/opencircuit/main.go`: mountAndServe's server now carries a ConnState
  hook (`activeConnSet`, new unexported type beside the budget vars) that
  records connections in the states Shutdown's own quiescence check treats
  as busy (new/active/hijacked). When Shutdown returns
  `context.DeadlineExceeded`, mountAndServe logs and returns a named,
  self-describing error — "graceful shutdown incomplete after <budget>:
  context deadline exceeded — connections still active at expiry: N
  connection(s): addr state" — preserving `errors.Is(err,
  context.DeadlineExceeded)`. Only the deadline case is annotated; a
  listener-close error on Shutdown's fast path passes through unwrapped.
  The hook is observational; no timing, ordering, or state changed.
- `cmd/opencircuit/shutdown_decline_wiring_test.go` (new): drives the real
  mountAndServe over an ephemeral port with a half-open connection (header
  never terminates → StateNew), shrunk budget (500ms, package-var override,
  restored in t.Cleanup), real SIGTERM; asserts the returned error names
  the budget, the count, the remote address, and the StateNew state while
  still wrapping the deadline. No DB needed (okPinger, noindex shape);
  client-side conn closed in t.Cleanup; no leaked listener or registration.
- Mutation proof: with the annotation disabled, the new test fails against
  the exact observed symptom — a bare `context deadline exceeded` naming
  nothing; restored and hash-verified afterwards.

  they do not actually hold the budget, so the expiry report could name
  one that wasn't what held shutdown open. Nothing in this codebase
  hijacks, and the report is post-expiry prose only, so no behavior is
  wrong; noting for any future SSE-adjacent work.
