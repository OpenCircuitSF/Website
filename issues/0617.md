## Description

`workshops` stores `location_name`, `location_address` and `location_note` as free
text on every row. All seven publicly visible listings are at Sequoia Fabrica, with
three different spellings of its address. Add an admin-managed `locations` table,
consolidate the existing values into it, and point each listing at a location by
foreign key. The listing editor then offers a drop-down, with one location set as
the default: **Sequoia Fabrica**.

This is the user's request (2026-11-04). It follows the same shape as `#0613`'s
`event_types`: rows an admin can add, edit and disable without a deploy.

## Plan

Written 2026-11-04 against the tree at `025b5a2e`. Names follow the corrections in the
acceptance criteria: table `venues`, column `workshops.venue_id`, setting
`default_venue_id`, screen **Venues**. `outreach_locations` is a different table, for
flyer posting places, and nothing here touches it, its routes or its `location_id`
fields.

**Decisions this plan makes**

- **Keep the three text columns, unread and unwritten, in `000048`. Drop them in a later
  issue.** The reasons:
  - The consolidation runs on draft values nobody could read while planning. Keeping the
    text means a surprise there can be recovered, including a draft's different note,
    which the criterion otherwise discards.
  - The previous binary keeps working while the migration has run and the new binary has
    not started.
  - A binary-only rollback stays possible.
  - The cost is three stale columns and one follow-up issue. `COMMENT ON COLUMN` and the
    PRD mark them retired, and `TestWorkshopReadsIgnoreRetiredLocationColumns` proves
    nothing reads them, so there is still one source of truth.
- **Between the migration and the new binary starting.** The previous build runs
  unchanged, because every column it names still exists and it ignores `venue_id`. Public
  pages and the admin console keep working. The one gap is a listing saved during those
  seconds: a new one has no venue, and a location edit to an existing one is not carried
  over. The post-deploy query below finds them. Then `systemctl restart` causes the usual
  brief interruption.
- **Binary-only rollback, as the columns stand after this issue.** It works, in a degraded
  way. The previous build reads the text as it stood at migration time, so:
  - venue edits made since do not show on it;
  - a listing created since shows no location;
  - anything it writes to the text columns is ignored if you later roll forward.

  `migrate down 1` is not needed for this and should not be run after such a rollback,
  because the down migration treats venues as the truth and overwrites that text. Once
  the follow-up drops the columns, this rollback ends and the second row below applies.
- **What the same choice would cost if the columns were dropped now.**

  | | Keep (this plan) | Drop in `000048` |
  |---|---|---|
  | Migration to restart | Previous build keeps serving | Every query the previous build makes on `workshops` fails, so listings error, until the restart |
  | Binary-only rollback | Works, with the stale text above | Fails the same way until `migrate down 1`, which `docs/deployment.md` calls untested on production |
  | Draft text the consolidation discards | Still in the row | Gone, except in the backup |
  | Later work | One follow-up migration | None |

  To switch to dropping, make these changes and nothing else:
  - replace the three `COMMENT` lines with three separate plain `ALTER TABLE workshops DROP
    COLUMN ...` statements, one per column, which is the only shape the test schema census
    accepts;
  - in the down migration, first add the three columns back as `TEXT`;
  - remove them from the PRD;
  - delete `TestMigration000048PriorBuildQueriesStillRun` and
    `TestWorkshopReadsIgnoreRetiredLocationColumns`.
- **Consolidating values nobody has seen.** After trimming spaces, tabs and line breaks, a
  blank value counts as absent.
  - The grouping key is the lower-cased name.
  - A listing with no name but an address or a note still has location data, so that text
    becomes the venue's name and is not repeated in the address or note field. It then
    shows once on public pages, as a name.
  - Within a group, the name spelling comes from the most recently edited listing, and the
    address and note are the most common non-blank values.
  - `sequoia fabrica` in any case always maps to the seeded row, whose address and note win.
  - `updated_at` on listings is left alone, so the sitemap's dates do not all jump.
- **No unique constraint on the venue name.** The issue's Notes tell an admin to disable a
  venue and add a new one when it moves, and a moved venue keeps its name. The default
  cannot be disabled first, so a uniqueness rule would block that flow. The drop-down shows
  the address beside the name, so two rows can be told apart.
- **Default handling is in the handler and store, not a column default.** A raw `INSERT`
  and the store's zero value mean no venue. `POST /admin/workshops` with `venue_id` absent
  means the default, explicit `null` means no location, and a number means that venue. So
  `venue_id` uses `Optional[int64]`, as `capacity` does.
- **`PATCH` follows the same three cases**, with absent meaning unchanged.
- **The wire stays the same for readers.** `location_name`, `location_address` and
  `location_note` stay on the public and admin views, read from the venue. They leave the
  admin request bodies, so `decodeJSON` answers 400 if they are sent, which only a browser
  tab left open across the deploy would do. `venue_id` is added to the admin view only.
- **The editor has no separate new-listing mode.** Creating happens in the dialog, then the
  editor opens the created row, which already has its venue. So pre-selecting the default
  is only the dialog's job, plus the server's default for an API caller.

**Approach**

1. **Up migration.** This exact SQL ran through the `migrate` CLI on a scratch database at
   version 47, up, down and up, with rows for every shape above. Add a header comment naming
   `#0617` and saying why the columns stay.

   ```sql
   CREATE TABLE venues (
       id         BIGSERIAL PRIMARY KEY,
       name       TEXT NOT NULL,
       address    TEXT,
       note       TEXT,
       enabled    BOOLEAN NOT NULL DEFAULT TRUE,
       sort_order INT NOT NULL DEFAULT 0,
       created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
       updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
       CONSTRAINT venues_name_not_blank CHECK (btrim(name) <> '')
   );

   ALTER TABLE workshops ADD COLUMN venue_id BIGINT REFERENCES venues(id) ON DELETE RESTRICT;
   CREATE INDEX idx_workshops_venue ON workshops (venue_id);

   COMMENT ON COLUMN workshops.location_name IS 'Retired by #0617: unread and unwritten; venues holds this. Kept for rollback and recovery.';
   COMMENT ON COLUMN workshops.location_address IS 'Retired by #0617: unread and unwritten; venues holds this. Kept for rollback and recovery.';
   COMMENT ON COLUMN workshops.location_note IS 'Retired by #0617: unread and unwritten; venues holds this. Kept for rollback and recovery.';

   INSERT INTO venues (name, address, note, sort_order)
   VALUES ('Sequoia Fabrica', '1736 18th Street, San Francisco, CA 94107', 'Foot of Potrero Hill', 0);

   WITH cleaned AS (
       SELECT id, updated_at,
              NULLIF(btrim(location_name, E' \t\r\n'), '') AS n,
              NULLIF(btrim(location_address, E' \t\r\n'), '') AS a,
              NULLIF(btrim(location_note, E' \t\r\n'), '') AS t
         FROM workshops
   ), sources AS (
       SELECT id, updated_at,
              COALESCE(n, a, t) AS name,
              CASE WHEN n IS NOT NULL THEN a END AS address,
              CASE WHEN n IS NOT NULL OR a IS NOT NULL THEN t END AS note
         FROM cleaned
        WHERE COALESCE(n, a, t) IS NOT NULL
   ), inserted AS (
       INSERT INTO venues (name, address, note, sort_order)
       SELECT (array_agg(name ORDER BY updated_at DESC, id DESC))[1],
              mode() WITHIN GROUP (ORDER BY address),
              mode() WITHIN GROUP (ORDER BY note),
              10 * row_number() OVER (ORDER BY lower(name))
         FROM sources
        WHERE lower(name) <> 'sequoia fabrica'
        GROUP BY lower(name)
       RETURNING id, name
   ), targets AS (
       SELECT id, name FROM inserted
       UNION ALL
       SELECT id, name FROM venues WHERE name = 'Sequoia Fabrica'
   )
   UPDATE workshops w SET venue_id = tg.id
     FROM sources s
     JOIN targets tg ON lower(tg.name) = lower(s.name)
    WHERE s.id = w.id;

   INSERT INTO settings (key, value, updated_at)
   VALUES ('default_venue_id', (SELECT id::text FROM venues WHERE name = 'Sequoia Fabrica'), now());
   ```

   Do not use a `pg_temp` function, view or table here. An earlier draft did. The migration
   tests run down and up on one connection, where a second `CREATE` of a temp object fails,
   and the census refuses `DROP TABLE`.

   ```sql
   UPDATE workshops w
      SET (location_name, location_address, location_note) =
          (SELECT v.name, v.address, v.note FROM venues v WHERE v.id = w.venue_id);
   COMMENT ON COLUMN workshops.location_name IS NULL;
   COMMENT ON COLUMN workshops.location_address IS NULL;
   COMMENT ON COLUMN workshops.location_note IS NULL;
   DROP INDEX idx_workshops_venue;
   ALTER TABLE workshops DROP COLUMN venue_id;
   DROP TABLE venues;
   DELETE FROM settings WHERE key = 'default_venue_id';
   ```

## Root cause

`workshops` stored `location_name`, `location_address` and `location_note` as free text on every row, so nothing tied two listings at one place together. That is how one venue reached three address spellings, and why a corrected address meant editing every listing.

## Fix

Followed the plan, keeping the three text columns unread and unwritten. Switching to dropping them stays the plan's short list; nothing added here depends on the columns except the two tests that list names.

Migration `000048` is the plan's SQL with its header comment. `internal/venues` and `admin_venues.go` follow `internal/eventtypes` and `admin_event_types.go` without the slug. `workshops.Store` reads the three location fields through `venue_id`. The public and admin views keep their `location_*` fields. The editor and the new-listing dialog have a Venue select with **No location** first.

Deviations from the plan's file list and text, for the reviewer:

- **Audit metadata keys.** `admin_venues.go` records the venue's address under `location`, `old_location` and `new_location`, not `address`. `TestAuditEntryEmailMetadataMatchesKnownSites` (`internal/handlers/audit_email_metadata_guard_test.go`) treats any `address` key as an email carrier, and a street address is not one. Pinning those sites would have claimed a privacy disclosure that does not apply, so the guard is unchanged and the keys were renamed.
- **Padded-content test.** The padded `location_note` case in `TestAdminWorkshops_PatchTreatsWhitespaceOnlyOptionalFieldAsCleared` now uses `body_md`, so that test keeps its point. The venue rule moved to a new test, `TestAdminVenues_NoteVerbatimAndBlankClears`.
