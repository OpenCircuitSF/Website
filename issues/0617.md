## Description

`workshops` stores `location_name`, `location_address` and `location_note` as free
text on every row. All seven publicly visible listings are at Sequoia Fabrica, with
three different spellings of its address. Add an admin-managed `locations` table,
consolidate the existing values into it, and point each listing at a location by
foreign key. The listing editor then offers a drop-down, with one location set as
the default: **Sequoia Fabrica**.

This is the user's request (2026-11-04). It follows the same shape as `#0613`'s
`event_types`: rows an admin can add, edit and disable without a deploy.

## Acceptance criteria

- [ ] A new migration, using the next free number, creates `locations` with a name,
      address, note, enabled flag, is-default flag, sort order and timestamps. The
      database enforces at most one default row and that the default is enabled.
- [ ] The migration creates Sequoia Fabrica as the default location, with the address
      `1736 18th Street, San Francisco, CA 94107` and the note `Foot of Potrero Hill`.
      Every listing named Sequoia Fabrica points at that one row, whichever spelling
      of the address it had.
- [ ] Any other listing with location data, in any status including drafts, gets a
      location consolidated by whitespace-trimmed, case-insensitive name, so no
      location text is lost. A listing with no location data stays without a location.
- [ ] `workshops` gains a nullable `location_id` with a foreign key that refuses to
      delete a location in use. The old text columns are removed or left unread, as
      the plan decides, so that one source of truth remains. The plan states how this
      behaves between the migration and the new binary starting. The down migration
      restores the prior schema and repopulates the text columns from the location.
- [ ] An admin can list, create, edit, reorder, enable and disable locations, and
      choose the default, under the same authorization as `/admin/interests`. Each
      mutation writes an audit entry. The admin console has a screen for this, reachable
      from its navigation, following the Event types screen's patterns.
- [ ] A location in use cannot be deleted; the response says why and points to
      disabling instead. The default location cannot be disabled or deleted.
- [ ] A disabled location is not offered for new assignments and the API refuses one.
      Existing listings keep it, stay publicly visible, and can still be edited without
      being forced to change it.
- [ ] The listing editor replaces the three location text fields with a drop-down of
      enabled locations, plus an explicit "No location" choice for a listing without
      one. A new listing, in the editor and in the new-listing dialog, pre-selects the
      default. A listing created through the API with no location field gets the default.
- [ ] Public pages, the public API's location fields, structured data, social cards,
      flyers, outreach text, email announcements and the CRT output show the same
      location information as before, read from the location row. Consumers of those
      fields do not need a new wire shape.
- [ ] Editing a location or its enabled state invalidates the cached server-rendered
      pages (`#0614`'s invalidation pattern), so a corrected address reaches them.
- [ ] `PRD.md`, the `AGENTS.md` migration range and PRD index, and the relevant `docs/`
      page reflect the new table.

## Notes

- Prior art: `#0613` for the table constraints, store, admin handler, screen and the
  "choose the default is a `PATCH` field" decision recorded in its plan.
- **Editing a location changes every listing that uses it, including past ones.** That
  is the point of consolidating, and it is accepted. Disable a venue and add a new one
  when a venue actually changes.
- `location_note` moves to the location, because it is the same on all seven listings.
  An event-specific instruction belongs in the listing's body. If a draft in production
  has a different note, the consolidation criterion keeps it only if the name differs,
  so the plan should re-read production's distinct values on the day it is worked.
- Read production's distinct values, read-only, as `AGENTS.md` §1 does for its version
  check. If that read needs user approval, request it before dispatching phase 2.
- The address spelling is editable in admin after deploy, so the chosen form is a
  starting value rather than a decision to protect.
