## Description

`#0509` settles how a deploy *runs*. This issue is the **automation on the
workstation** that produces what it consumes: one script that builds the SPA
and the binary, assembles the bundle, and publishes a GitHub Release with
`gh`.

Decided by the user 2026-09-12: **public releases**, on the existing public
repo, because the source is already public so a prebuilt artifact reveals
nothing new, and it keeps the box's fetch an unauthenticated `curl`.

`gh` is installed and authenticated as `brennanMKE`. The repo currently has
**no tags and no releases**, so this defines the scheme from scratch.

## What the script does

1. Refuse to run on a dirty tree or a non-`main` branch, unless explicitly
   overridden — a release built from uncommitted work has a tag that does not
   describe it.
2. Build `web/dist`, then the binary — that order, because of
   `//go:embed all:dist`. Honour `CLAUDE.md` §8b: a real `npm run build`
   overwrites the tracked `web/dist/index.html` placeholder, and the safe
   restore is `git show HEAD:web/dist/index.html > web/dist/index.html`, never
   `git checkout --`. Building in a throwaway `git worktree` sidesteps this
   entirely and is the better default.
3. `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`, with `-ldflags` embedding the
   commit hash — the tag names the release, the hash proves the contents.
4. Assemble the bundle and compute `SHA256SUMS`.
5. `gh release create <tag> --notes …` with the bundle and checksums attached.

## Bundle contents

Everything the box needs and nothing it must not have:

- the `linux/arm64` binary
- `migrations/` — so the box needs no git checkout to migrate
- the systemd unit
- `SHA256SUMS`

**Never** `config.env`, credentials, or anything from the private AWS repo.
Add an explicit check that the archive contains none of `#0511`'s restricted
identifiers before publishing — a public release asset is as public as the
repo, and unlike a commit it cannot be quietly amended.

## Why this shape

The box currently holds a git checkout 900 commits behind and dirty
(`M web/dist/index.html`, observed 2026-09-12). Bundling `migrations/` removes
the reason that checkout exists at all, which fits the no-toolchain decision
better than keeping a stale clone in sync. Rollback becomes "download the
previous release" rather than "hope the old binary is still on disk".

## Acceptance criteria

1. One command produces a published release from a clean checkout.
2. Tag scheme decided and documented — semver, date-based, or commit-derived.
   **Either answer is fine; an unexamined one is not.** Whatever is chosen must
   sort correctly, since "the previous release" is the rollback path.
3. The script is idempotent about failure: a partial run leaves no half-created
   release or dangling tag.
4. `shellcheck` clean and `bash -n`. `CLAUDE.md` §8: this machine's bash is
   3.2.57, so `${var,,}`, `declare -A`, `mapfile` and `&>>` fail at runtime
   while **both** `bash -n` and `shellcheck` pass on them. Use
   `tr '[:upper:]' '[:lower:]'`.
5. Respects `#0511`: no host, account, instance, zone or role literals in the
   script or in release notes.
6. Verified by publishing a real release and fetching it back — not by
   reasoning that it would work.

## Residuals inherited from `#0509`, to fix here

`#0509`'s final review left three non-blocking defects deliberately, because
this issue replaces steps 1–2 with a script and fixing them there would be
throwaway work. Measured, not speculative:

1. **The push guard false-`STOP`s for a non-tip commit.** `git ls-remote origin
   | grep -q "^$COMMIT"` matches only ref *tips*, so a commit that is genuinely
   on `origin` but one behind — `origin/main~1` was measured — reports `STOP`.
   It cannot fire on the intended path (you release what you just pushed) and
   it fails closed, so it is safe but imprecise. A script should use
   `git merge-base --is-ancestor "$COMMIT" origin/main` instead.

2. **`git push origin HEAD` fails from a detached HEAD** — which is the state
   step 1 recommends, since building in a throwaway `git worktree` detaches.
   Confirmed with a dry-run push in a scratch clone: git refuses before
   contacting the remote. The script must push from a branch, or resolve the
   branch explicitly, rather than relying on `HEAD`.

3. **Relocated prose says "this step"** where it means the build step, a
   harmless artifact of moving the cleanup block from step 1 to step 2.

## Notes on ordering

Items 1 and 2 are the ones that matter: both are places where the documented
procedure works only because the operator is paying attention. A script has no
attention, so both must be correct before it runs unsupervised.

### `--dry-run` cannot publish — proven, not read

Traced every `gh` call site, then re-ran the whole script with a shim earlier
on `PATH` that logs each invocation and hard-fails (`exit 99`) on `release
create|delete|edit|upload`. Under `--dry-run 0.1.0` the shim recorded exactly
two calls, both read-only:

    gh auth status
    gh repo view --json nameWithOwner -q .nameWithOwner

Zero mutation attempts, exit 0, no local or remote tag created. The single
`gh release create` is unreachable under the flag: the `DRY_RUN` branch ends
in an unconditional `exit 0` before it.

Argument parsing fails closed, which matters more than the flag itself — a
mistyped dry-run must never fall through to a real publish. All of
`--dryrun`, `-n`, `-dry-run` die with `unknown flag`, exit 1, before preflight;
`0.1`, `0.1.0-rc1`, a missing VERSION and a duplicate VERSION all die too.
`v0.1.0` is accepted and the `v` stripped.

All seven gates fire in the documented order (preflight, version const, clean
tree, detached HEAD, on main, pushed to `origin/main`, tag free, then the
bundle scan after the build).

### The base64 identifier scan

Judged against `CLAUDE.md` §8's oracle rule and it passes for the right
reason: the oracle (the encoded list) lives in `scripts/release.sh`, the
subject is the assembled *bundle*, and the script is not in the bundle. An
edit to what gets released cannot also satisfy the check. This is not the
`#0258` shape.

Confirmed the decoded values are actually the nine. Each decodes to a
non-empty string present in tracked files, and the per-value tracked-file
counts reproduce `#0511`'s own table exactly — 18 (account id), 21 (two
instance ids), 21 (two IPs), 18 (two hostnames), 10 (hosted zone), 9 (IAM
role). Values are not reproduced here.

Scan behaviour tested in both directions, since one that silently matches
nothing is worse than none: a stage directory of innocuous text plus a random
200 KB binary scores `SCAN_HIT=0`; the same with one identifier planted
mid-blob inside the binary, no newline either side, scores `SCAN_HIT=1`. So
`grep -rlaF` does cover the binary's strings, and no separate pass is needed.

`scripts/release.sh` contains none of the nine as literals, the commit message
contains none, and the `docs/deployment.md` diff **added** none — the
occurrences already in that file predate this commit and remain `#0511`'s open
scope. Criterion 5 met.

### Cleanup path

Exercised, not reasoned about: under the shim, a real (non-`--dry-run`) run
reached `gh release create`, took the failure branch, attempted `gh release
delete "$TAG" --repo … --yes --cleanup-tag`, and — when that could not confirm
either — died with the exact manual recovery commands. Exit 1, and the real
repo was left with no local tag, no remote tag, a clean tree and no worktree.

It cannot delete a pre-existing release today: gate 6 refuses if the tag exists
locally or on origin, and a published release always has a tag. The script
never runs `git tag` or `git push` at all — the only ref-creating action in the
whole file is `gh release create --target`, which is what makes criterion 3
structurally true rather than merely handled.

### `git stash` (§8a)

It was used, and it was safe, but it is worth recording precisely. The
implementer ran `git stash push -- issues/0514.md` — the pathspec form, on a
file it had itself edited that session, which §8a's primary rule permits.
Verified empirically in a throwaway repo that `git stash push -- <pathspec>`
leaves every other dirty file untouched in the working tree; it is genuinely
not `#0120`'s bare-stash-described-as-scoped shape. Current state: `git stash
list` empty, `.git/logs/refs/stash` absent, tree clean, `.git/info/exclude`
back to pristine, no leftover worktrees, `HEAD` unmoved. Nothing was at risk
and nothing was lost. **`scripts/release.sh` itself contains no `git stash`,
no `git push`, and no `git reset`.**

### Non-blocking observations — none can cause a bad publish

1. `--help` runs `sed -n '2,110p'` but the header comment ends at line 112, so
   the last two lines are cut mid-sentence.
2. Nothing positively controls the encoded array. A future entry mis-typed
   into a still-valid base64 string decodes with `rc=0` to a wrong value and
   that one check goes silently dead. Verified correct today; the exposure is
   drift. An empty decode fails closed (matches everything) and an
   invalid-charset one fails closed via `set -e`, so only the
   decodes-to-garbage case is silent.
3. `--allow-non-main` is narrower than its name: gate 5 still requires the
   commit be an ancestor of `origin/main`, so it only permits a differently
   *named* branch pointing at already-merged code. Safe, arguably the right
   default, but the flag oversells itself.
4. A pre-existing GitHub **draft** release sharing the tag name would slip past
   gate 6 (drafts create no git ref), and the cleanup could then delete it.
   Inapplicable today — the repo has zero releases.
5. When `gh release create` fails before creating anything (auth, network), the
   cleanup delete also fails and the script prints "cleanup could not confirm
   removal" — alarming wording for a benign case, but it fails safe.
