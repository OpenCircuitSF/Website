## Description

`cmd/opencircuit`'s wiring tests use five fixed literal session tokens (`"zz-events-nonadmin-token"`, `"zz-shutdown-budget-token"`, and three more without a `zz-` prefix). They do not collide today, and `#0163`'s review established *why* — but the stated reason was wrong on both counts, and the real one carries a trap.

**Not** because "each package truncates at `TestMain`": `cmd/opencircuit`'s `TestMain` truncates nothing, it only takes `testdb.Lock()`. And the tokens are in the *same* package, so a per-package truncate could not separate them even in principle.

The actual mechanism is `truncateAdminWiringTables`, which runs on entry **and** again in `t.Cleanup`. That is stronger than the claimed one: it does not depend on `-shuffle` ordering and does not depend on the tests living in different packages.

**But it does depend on `t.Parallel()` never appearing in `cmd/opencircuit`** — currently zero occurrences, verified. If any wiring test ever gains it, the per-test `TRUNCATE` would destroy a concurrently running sibling's rows mid-test. That failure is worse than a token collision and far more confusing: nothing in the package would attribute it correctly, and it would present as an unrelated test mysteriously losing its fixtures.

## Acceptance criteria

- [x] A comment on `truncateAdminWiringTables` states that it truncates shared tables and is therefore incompatible with `t.Parallel()` in this package
- [x] Decide whether a stronger guard is warranted than a comment — e.g. the helper failing loudly if it detects parallel execution — and record the reasoning. A comment is the cheap insurance; a guard is the one that survives someone not reading it
- [x] Consider whether the five fixed literal tokens should draw from `testdb.Unique()` anyway, so correctness stops depending on the truncate at all. `#0163` left them alone as out of scope, which was right for that issue
- [x] `ISSUE=0165 scripts/check.sh go ./cmd/opencircuit/...` passes

## Notes

## Implementation notes

**Facts established before changing anything:**

- `truncateAdminWiringTables` is called by four tests:
  `TestMountAndServe_AdminRoutesRequireSessionAndAdmin` (admin_wiring_test.go),
  `TestMountAndServe_EventsRequiresSessionAndAdmin` (events_wiring_test.go),
  `TestMountAndServe_WorkshopMutationInvalidatesSharedSEOSite`
  (seo_wiring_test.go), and
  `TestMountAndServe_ShutdownAndCloseHaveIndependentBudgets`
  (shutdown_budget_wiring_test.go). Each calls it once on entry and once via
  `t.Cleanup`. It runs `TRUNCATE sessions, passkey_credentials, audit_log,
  users RESTART IDENTITY CASCADE`; the shutdown-budget test additionally
  truncates `subscriber_interests, subscribers` on both ends.
- `grep -rn "t.Parallel()" cmd/opencircuit/` returned zero matches before this
  change — confirmed, matching the issue's own claim.
- `cmd/opencircuit`'s `TestMain` (main_test.go) only calls `testdb.Lock()`; it
  truncates nothing, confirming the issue's correction of `#0163`'s stated
  mechanism.

**Reproduced the hazard before building anything** (own database,
`opencircuit_test_0165`, lowercase token per `#0140`): added `t.Parallel()`
temporarily to `TestMountAndServe_AdminRoutesRequireSessionAndAdmin` and
`TestMountAndServe_EventsRequiresSessionAndAdmin`, ran
`go test ./cmd/opencircuit/... -run '...' -v -parallel 2` five times. 4 of 5
runs failed: three showed the admin-routes test's later assertions getting
401 where 200/403 was expected (its session row wiped mid-test by the
sibling's truncate), one showed `sessions_user_id_fkey` violated inserting a
session (the user row truncated between the two seed calls). One run passed
only because the scheduler happened not to interleave them. This matches the
issue's prediction exactly: "an unrelated test mysteriously losing its
fixtures." Restored both files afterward and verified `shasum -a 256`
byte-identity against the pre-edit originals.

**Shape chosen: make the hazard loud, not silently safe.** Added
`registerWiringTest(t, pool)` (admin_wiring_test.go) — an
`atomic.Pointer[string]` (`wiringTablesOwner`) that a test claims via
`CompareAndSwap(nil, &name)` on entry and releases via `t.Cleanup`, held for
the test's whole body (not just the truncate call, since the corruption
window is the whole time between entry-truncate and cleanup-truncate). A
second wiring test trying to claim it while another holds it fails
immediately with `t.Fatalf`, naming both tests and pointing at
`truncateAdminWiringTables`'s doc comment. All four callers now call
`registerWiringTest(t, pool)` once, immediately after connecting `pool` and
before their first `truncateAdminWiringTables` call. A comment alone was
rejected per the issue's own instruction (comments in this tracker have
repeatedly been wrong or unread, e.g. `#0140`, `#0150`); this fails instead of
warning.

Rejected the "make the helper safe under parallelism" shape: doing that
properly would mean replacing the blanket `TRUNCATE` with scoped `DELETE`s
keyed to rows each test itself inserted (tracking ids, or partitioning by a
`testdb.Unique()`-derived value), which is a materially bigger, riskier change
for a hazard that is not live today. The loud guard costs four one-line call
sites and protects exactly the failure mode reproduced above.

**On the five fixed literal tokens (acceptance criterion 3):** considered and
rejected switching them to draw from `testdb.Unique()`. That would fix a
*different* hazard (two tests racing on `sessions_token_key` from an
accidental token collision) but does nothing for this one — `TRUNCATE`
deletes every row in the table regardless of what value the token holds, so
even fully unique tokens would still be wiped by a sibling's truncate under
`t.Parallel()`. Token uniqueness and truncate-safety are orthogonal; only the
guard above addresses the truncate hazard. Left the five tokens as they are,
matching `#0163`'s decision to leave them out of scope.

**Nothing found worth filing beyond this issue's own scope.**

## Review notes — 2026-08-23 (phase 3, **resolved**)

Re-verified independently in a throwaway worktree at `0222113` (the main tree
was dirty with `#0161`'s gofmt sweep and `scripts/` work), against a private
database `opencircuit_test_0165rev` created with `scripts/testdb.sh create`
— lowercase token per `#0140`'s finding. `uptime` first: load average 2.28,
well under the ~4 idle ceiling, so nothing below is machine noise.

**Half 1 — the hazard is real, and worse than reported.** Built a second
worktree at `0222113^` (pre-guard), confirmed `grep -rn "t.Parallel()"
cmd/opencircuit/` returned **zero** there, then added `t.Parallel()` to
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` and
`TestMountAndServe_EventsRequiresSessionAndAdmin` and ran under `-parallel 2`.

**13 of 13 runs failed** (5, then 8 more for error detail) — a worse ratio
than the implementer's 4/5, in the same direction. Both predicted symptoms
appeared:

- `admin_wiring_test.go:212: seed session: ERROR: insert or update on table
  "sessions" violates foreign key constraint "sessions_user_id_fkey"
  (SQLSTATE 23503)` — the user row truncated between the two seed calls;
- `admin_wiring_test.go:354: admin session: GET /admin/settings status = 401,
  unexpected for this case` (and the same for `PATCH /admin/settings`,
  `GET /admin/users`, …) — the session row wiped mid-test, so routes that
  should return 200/403 return 401.

Nothing in either output points at `truncateAdminWiringTables`. The issue's
characterisation — "an unrelated test mysteriously losing its fixtures" — is
exactly right.

**Half 2 — the guard fires, loudly and immediately.** Re-added the same two
`t.Parallel()` calls at `0222113`: **5 of 5 runs failed at
`registerWiringTest`**, with zero FK violations and zero assertion failures.
The loser fatals before its first `truncateAdminWiringTables`, so the winner
runs alone and **no corruption occurs at all**. The message names both tests
and the helper:

    registerWiringTest: TestMountAndServe_EventsRequiresSessionAndAdmin cannot
    run concurrently with TestMountAndServe_AdminRoutesRequireSessionAndAdmin
    -- both use truncateAdminWiringTables's shared tables with no isolation, so
    this package must not run *_wiring_test.go tests under t.Parallel() (see
    truncateAdminWiringTables's doc comment, #0165)

Which test loses the race varies (3/5 events, 2/5 admin), as it should. Files
restored and `shasum -a 256` verified byte-identical to `0222113` in both
worktrees; `git status --porcelain` clean afterward.

**Claim scope — no leak, on any exit path.** The design decision under review
is holding the claim for the test's whole lifetime rather than just the
truncate, so the release path matters more than the acquire path. Probed it
with four throwaway tests in the package, run in declaration order:

| Probe | Holder's exit | Next test can claim? |
|---|---|---|
| A | `t.Fatalf` mid-body while holding the claim | — |
| B | `t.Skip()` while holding the claim | — |
| C | normal pass | **yes** — claimed cleanly after both A and B |
| D | normal pass | **yes** — claimed cleanly after C |

`--- FAIL: A`, `--- SKIP: B`, `--- PASS: C`, `--- PASS: D`. The release is a
`t.Cleanup`, and Go runs cleanups on failure, on skip, and on panic alike, so
there is no exit path that strands the claim and poisons the next test. This
was the failure mode that would have made the guard worse than the hazard;
it does not exist. (A panic aborts the whole binary anyway, so no subsequent
test could observe a leak even in principle.)

**The unregistered-fifth-test gap is real — and already recorded.** Wrote a
fifth test that calls `truncateAdminWiringTables` in a loop with
`t.Parallel()` and *no* `registerWiringTest` call, ran it against the real
admin wiring test: the original corruption came straight back — the same
spurious 401s in 2 of 3 runs, and `ERROR: deadlock detected (SQLSTATE 40P01)`
in the third. So a wiring test added tomorrow that omits the call **is
silently unprotected**.

This is not a hidden defect: `truncateAdminWiringTables`'s doc comment states
it plainly — "Adding `t.Parallel()` to a test that skips that call is still a
bug this guard cannot see; it protects the tests that use the established
pattern, not the package against every possible misuse." Verified all four
callers do register (`registerWiringTest(t, pool)` at `admin:77`,
`events:49`, `seo:96`, `shutdown_budget:131`), and that the set of files
calling `truncateAdminWiringTables` is exactly those four. Closing the gap
properly would want a source-level check — the shape already used in this
repo by the citation guard — which is a separate piece of work, reported to
the orchestrator rather than filed here per `CLAUDE.md` §9.

**Message pasteability (`#0187`).** Satisfied. The message is one line and
every token in it is searchable as written: both fully-qualified test names,
the helper name `truncateAdminWiringTables`, the literal `t.Parallel()`, the
glob `*_wiring_test.go`, and `#0165`. There are no abbreviated or
inconsistent paths of the kind `#0187` item 4 objected to.

**Verdict on the shape choice.** Correct call. "Make the helper parallel-safe"
means replacing a blanket `TRUNCATE` with scoped `DELETE`s keyed to
self-seeded rows — and half 1 shows the hazard is not live today (zero
`t.Parallel()` in the package), so that is a large, risky rewrite bought
against a hypothetical. The loud guard costs four one-line call sites and
demonstrably converts the exact reproduced failure into an immediate named
error.

The accepted cost is real and permanent: this package can now never use
`t.Parallel()` for these tests. On whether that is recorded where someone
would find it — yes, and by the better mechanism. The doc comment states it,
but the discovery path that actually works is the guard itself: someone
reaching for `t.Parallel()` gets a fatal error on their first run that names
the constraint and points at the comment. That is strictly better than a
comment they would have had to already be reading.

**Verdict on the declined criterion 3 — the reasoning holds, and is stronger
than stated.** The criterion asks whether the fixed literal tokens should
draw from `testdb.Unique()` "so correctness stops depending on the truncate at
all." The implementer declined on orthogonality: `TRUNCATE` deletes every row
regardless of token value, so unique tokens do nothing for *this* hazard.
That is correct as far as it goes, but it slightly under-reads the criterion,
whose real aim is to remove the dependency on the truncate at the root — and
on that reading the answer is still no, for a reason the implementation notes
did not give:

- The truncate is load-bearing for more than tokens. `admin_wiring_test.go`
  seeds three **fixed literal emails** (`wiring-nonadmin@example.com`,
  `wiring-admin@example.com`, `wiring-target@example.com`) into a column that
  `migrations/000001_create_users.up.sql` declares `email TEXT UNIQUE NOT
  NULL`. Tokenising `sessions.token` would leave those colliding on re-run.
  "Correctness stops depending on the truncate" is therefore **not reachable**
  by the change the criterion proposes; it would need the emails too, and then
  scoped deletes — i.e. exactly the rewrite rejected above.

So the criterion is satisfied in its literal form ("consider … and record"):
it was considered, the decision is recorded, and the decision is right. Ticked
on that basis, not on the basis that the tokens were changed — they were not.

Minor: the issue's Description says "five fixed literal session tokens"; there
are in fact **six** (`wiring-nonadmin-token`, `wiring-admin-token`,
`zz-events-nonadmin-token`, `zz-events-admin-token`, `seo-wiring-admin-token`,
`zz-shutdown-budget-token`). Miscount in the filing, not in the fix.

**One small observation, reported not filed:** `registerWiringTest(t, pool)`

package-level global — which is the correct scope, since the hazard is
in-process. Worth either dropping the parameter or saying why it is there.
