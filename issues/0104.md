## Description

`PreferencesHandler.patchUnsubscribe` (`#0031`) and `UnsubscribeHandler.Post`
(`#0034`) both decide whether an unsubscribe was a no-op by comparing a status
they read *before* the mutating call:

```go
before := sub.Status                                  // read at FindByManageToken time
updated, err := h.subs.Unsubscribe(ctx, sub.ID, ...)  // guarded UPDATE
noOp := before == subscribers.StatusComplained        // decided from the stale read
```

`Store.Unsubscribe` already returns the post-`UPDATE` row in `updated`, whose
status reflects what the database actually did, atomically. Both handlers hold
that value and neither consults it for this decision.

## Resolution notes

> 🟢 Resolved 2026-08-20 — both `UnsubscribeHandler.Post` and
> `PreferencesHandler.patchUnsubscribe` now derive `noOp` from the row
> `Store.Unsubscribe` returns, closing the read-then-act window; verified by
> mutation that both new race-window tests fail against the pre-`b8abe93`
> pre-call read.

**One correction to this issue's Root cause, for the record (no code change
needed).** The claim that the stale read "rotates `manage_token` on a
complained row" overstates the impact: `Store.RotateManageToken` carries its
own `CASE WHEN status = $4 THEN manage_token ELSE $2 END` guard against
`statusLockedFromNonAdmin`, so the token was never actually rotatable on a
complained row. Under the mutation above the `ManageToken changed, want
unchanged` assertion accordingly did *not* fire — only the audit assertion
did. The tests' `manage_token` assertions are therefore defense-in-depth
against that store guard being weakened later, not the load-bearing proof;
the spurious `subscriber.unsubscribed` audit row was the real defect, and it
is fixed.

## Root cause

Read-then-act across two round trips. If an SES complaint notification lands
between the `SELECT` and the `UPDATE` for the same subscriber —
`sesnotify` → `MarkComplained` — then `before` says `active`, the store's
`CASE WHEN status = complained` guard correctly refuses the write, and the
handler proceeds down the non-no-op branch anyway. It then:

- writes an `audit.ActionSubscriberUnsubscribed` row for an unsubscribe that
  never happened — the exact corruption of the consent-evidence record that
  bounced `#0031`, and that `#0038`/`#0060` read back as fact; and
- (on the `#0034` path only) rotates `manage_token` on a complained row,
  invalidating every live footer link that person holds for an action that
  changed nothing.

The window is one database round trip and requires a concurrent complaint for
the same address, so this is unlikely rather than impossible. It is filed
because the correct version is not harder: `noOp := updated.Status ==
subscribers.StatusComplained` is decided from what the guarded `UPDATE`
actually did and closes the window entirely, while still being a check that
happens before the rotation decision (which is what `#0034`'s carried-in
criterion requires).

## Fix

Both call sites now compute `noOp` from the `Subscriber` row
`Store.Unsubscribe` itself returns, not from a status captured before the
call:

- `internal/handlers/unsubscribe.go` (`UnsubscribeHandler.Post`) — removed
  `before := sub.Status` (captured right after `FindByManageToken`); `noOp`
  is now `updated.Status == subscribers.StatusComplained`, computed
  immediately after `h.subs.Unsubscribe(...)` returns and before either the
  `RotateManageToken` call or the audit write. Both of those still happen
  strictly after this check and are still skipped together on `noOp`,
  matching `#0034`'s carried-in ordering requirement (rotation only on a
  real unsubscribe, audit write only on a real unsubscribe, in that order).
- `internal/handlers/preferences.go` (`PreferencesHandler.patchUnsubscribe`)
  — same shape: removed the pre-call `before := sub.Status`, `noOp` is now
  derived from `updated.Status` immediately after `h.subs.Unsubscribe(...)`
  returns, and the audit write (`if !noOp && h.auditor != nil`) still runs
  after that check. `#0031`'s carried-in requirement — check complained
  status before deciding whether to write the audit row — is unchanged;
  only what the check reads from changed.
- `internal/subscribers/store.go` — `Store.Unsubscribe`'s doc comment gained
  a paragraph stating the returned row is the authoritative answer to "did
  this actually change anything," naming both call sites this issue fixed
  as the ones that used to reach for a pre-call read instead, so a future
  caller doesn't reintroduce the pattern.

Neither handler's package doc comment claim about ordering needed to change
— `unsubscribe.go`'s "complained no-op" section and its inline comments were
updated to describe deriving `noOp` from the returned row rather than the
pre-call read, since the old comment text specifically credited the
pre-call pattern.

**Divergence from a literal reading of the acceptance criteria's test
description:** rather than only "a store wrapper calling `MarkComplained` on
first entry," the test in both packages wraps the real store and calls
`subscribers.Store.MarkComplained` the first time `Unsubscribe` is invoked
for the seeded subscriber's id — i.e. the race is triggered from inside the
wrapped `Unsubscribe` method itself (which runs after the handler's own
`FindByManageToken` lookup already returned an "active" row), rather than
from a wrapped `FindByManageToken`. This is the more precise reproduction of
the actual race window described in this issue's Root cause (between the
`SELECT` and the `UPDATE`), and matches the criterion's own wording ("mark
the row complained *between* the handler's lookup and its `Unsubscribe`
call").

## Acceptance criteria

- [ ] Both handlers derive `noOp` from the row `Store.Unsubscribe` returns, not
      from a status read before the call
- [ ] The rotation decision and the audit-write decision both still happen
      *after* that check and before any write — `#0034`'s and `#0031`'s
      carried-in ordering requirement is unchanged by this
- [ ] `Store.Unsubscribe`'s doc comment states that its returned row is the
      authoritative answer to "did this actually change anything", so the next
      caller does not reach for a pre-call read again
- [ ] A test proves it: mark the row complained *between* the handler's lookup
      and its `Unsubscribe` call (a store wrapper that calls `MarkComplained`
      on first entry is enough), then assert zero audit rows and an unchanged
      `manage_token`
- [ ] Seed a throwaway subscriber for that test — never a literal or seeded id
      (`CLAUDE.md` §8b)

## Notes

Found during `#0034`'s review; the pattern originates in `#0031` and
`AdminSubscribersHandler.Suppress`'s before/after comparison (`#0032`), so fix
the call sites together rather than one at a time. Neither `#0031` nor `#0034`
is wrong against its own acceptance criteria — both were required to check the
complained status before deciding, and both do.

Nothing here weakens the rule in `CLAUDE.md` §9: `complained` subscribers never
auto-resubscribe, and the store's `statusLockedFromNonAdmin` guard is what
enforces that. This issue is only about the two handlers agreeing with the
store afterwards about what it did.
