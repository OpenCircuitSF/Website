## Description

`CancelQueuedTx` (added by `#0313`) marks a superseded `KindImportInvite` row
**`abandoned`** when an invited person self-signs-up. That is correct behaviour
recorded in the wrong terminal state.

`#0365`'s planning pass measured why `abandoned` is not neutral in this codebase
— it is a **delivery-health signal with three live readers**, none of which
reads the `error` column `CancelQueuedTx` relies on as a disambiguator:

1. `admin_dashboard.go:357` → `AbandonedCountByKind(KindConfirmation)` →
   `abandoned_confirmations`, documented in `types.ts:654` as "how many pending
   signups never got a confirmation **delivered**".
2. `admin_dashboard.go:370` → `counts.Abandoned > 0` raises the
   `outbound-queue-abandoned` dashboard warning. **Abandoned rows are terminal
   and nothing clears them**, so one correctly-cancelled invite raises a
   permanent, never-clearing alarm.
3. `pending.ts:64` → `abandoned` is the sole `badge-danger` state, its comment
   calling it "the one state that actually explains a non-confirmation as a
   delivery failure".

So an admin sees a red **delivery failure** against a row the system correctly
cancelled, and it never goes away.

**This is a behaviour change to resolved code** (`#0313`), which is why it is
filed rather than folded into `#0365`.

## Depends on `#0365`

`#0365`'s plan introduces **`skipped`** as a new terminal status via migration
`000027`, chosen for exactly this class of "correctly withheld, not failed"
outcome, and mirroring `email_sends`' existing `MarkSkippedTx` /
`RecheckEligibleTx` pair. **Land `#0365` first**; this issue is then a one-line
change of terminal state plus its tests.

Do not introduce a second new status for this.

## Root cause

`CancelQueuedTx` (`internal/outbox/store.go`) hardcoded `StatusAbandoned` as
the target of its `UPDATE`. `#0365` landed the `skipped` terminal status
(migration `000027`) after `#0313` wrote this method, so the right target
state didn't exist yet when `CancelQueuedTx` was added — it now does.

## Fix

Re-verified all three `abandoned` readers directly in the current tree before
changing anything (criterion 4), rather than trusting this issue's citations:

1. `internal/handlers/admin_dashboard.go`'s `Overview` calls
   `h.outbox.AbandonedCountByKind(ctx, outbox.KindConfirmation)` and puts the
   result on `dashboardOutboundQueueView.AbandonedConfirmations`
   (`json:"abandoned_confirmations"`), which `web/src/lib/types.ts`'s
   `DashboardOutboundQueue.abandoned_confirmations` doc comment describes as
   "how many pending signups never got a confirmation delivered".
2. The same `Overview` sets `outboundQueueAbandoned = counts.Abandoned > 0`
   and copies it to `warnings.OutboundQueueAbandoned`
   (`json:"outbound_queue_abandoned"`) — `abandoned` is terminal and nothing
   in the codebase ever moves a row off it, so this warning never clears once
   set.
3. `web/src/lib/pending.ts`'s `queueStateBadgeClass` returns `badge-danger`
   only for `'abandoned'`; every other state (including `'skipped'`, already
   handled by `#0365`) falls through to `badge-muted`.

Changed `CancelQueuedTx`'s target status from `StatusAbandoned` to
`StatusSkipped` — a one-line change to the `UPDATE`'s parameter list — and
rewrote the method's doc comment to explain why, cross-referencing
`MarkSkipped`'s own analysis rather than duplicating it. No other file in
`internal/subscribers` needed touching: the only call site
(`Store.ClaimAndEnqueueConfirmation`'s converting branch, in
`internal/subscribers/store.go`) passes the reason string through unchanged
and needed no edit — left alone throughout, since another session was
concurrently working that file for `#0379`.

Updated the two existing handler-level tests that pinned the old `abandoned`
outcome (`TestSubscribe_PendingInvitedRow_SendsGenericConfirmation`,
`TestSubscribe_PendingInvitedRow_CancelsQueuedInvitation`, both in
`internal/handlers/subscribe_test.go`) to expect `skipped`, and added a new
dashboard-level test,
`TestAdminDashboardOverview_CancelledInviteSkippedRaisesNoWarning`
(`internal/handlers/admin_dashboard_test.go`), that seeds the
self-signup-after-invite path through the real production code (not a
synthetic status write) and asserts the row lands on `skipped` and that
`Abandoned`/`OutboundQueueAbandoned` are unchanged by the action — measured
as a before/after delta around the one action rather than an absolute
`false`, because this package's shared test database is never truncated
between tests within one run, so an earlier test's genuinely-abandoned row
could otherwise already have the warning latched true for reasons unrelated
to this fix. This test is placed to run before any test in the file that
abandons a row, so the literal "warning is absent" framing also holds
directly, and the test additionally checks that unconditionally.

No test in the touched packages asserts an `abandoned` outcome for a genuine
delivery failure (`TestOutbox_AbandonsAtMaxRetries_RetainsLastError`,
`TestOutbox_MarkSent_DoesNotResurrectAbandonedRow`,
`TestOutbox_AbandonedCountByKind_ScopedToKind`,
`TestAdminDashboardOverview_OutboundQueue`,
`TestAdminDashboardOverview_AbandonedConfirmationsScopedToKind`) — all
re-run and confirmed still green and still asserting `abandoned`, unaffected
by this change (criterion 3).

### The central question, answered in both directions

**Does `skipped` now mean what `abandoned` used to, to every reader?** Yes,
and no genuine failure moved with it.

**Direction 1 — the three readers, re-enumerated from the tree (third
independent pass, criterion 4).** Read directly, not transcribed:

1. `internal/outbox/store.go`'s `AbandonedCountByKind` is
   `SELECT count(*) FROM outbound_queue WHERE kind = $1 AND status = $2` bound
   to `StatusAbandoned`, called from `internal/handlers/admin_dashboard.go`'s
   `Overview` with `outbox.KindConfirmation` and surfaced as
   `abandoned_confirmations`, whose `web/src/lib/types.ts` doc comment reads
   "how many pending signups never got a confirmation delivered". It reads
   `status`, never `error`. A `skipped` row is now excluded from it.
   (Confirming `#0365`'s plan §3.2: this reader is scoped to
   `KindConfirmation` while `CancelQueuedTx` cancels `KindImportInvite`, so
   it never misfired on this path — the issue's framing is right that reader
   2 is the one that did.)
2. The same `Overview` sets `outboundQueueAbandoned = counts.Abandoned > 0`
   and copies it to `warnings.OutboundQueueAbandoned`. That expression is
   byte-unchanged by this diff (only a comment was added above it), and
   `web/src/lib/dashboard.ts` keys `outbound-queue-abandoned` off
   `w.outbound_queue_abandoned` alone — the only occurrence of the word
   "abandoned" in that file.
3. `web/src/lib/pending.ts`'s `queueStateBadgeClass` still returns
   `badge-danger` for `'abandoned'` and nothing else; `'skipped'` falls to the
   `default:` arm, `badge-muted`, and `queueStateLabel` already renders it as
   "Skipped" (landed by `#0365`). So a correctly-cancelled row is no longer a
   red delivery-failure badge.

**Direction 2 — every producer of `StatusAbandoned`, enumerated (criterion
3).** Grepped `StatusAbandoned` across all Go, then independently every
`UPDATE`/`INSERT` against `outbound_queue` and every `SET status` in the
repo, then `migrations/` for a default or a raw literal. The complete set of
`abandoned` **writers** after this diff is one SQL statement:

- `outbox.Store.MarkRetryOrAbandon` — `status = CASE WHEN attempts >= $3
  THEN 'abandoned' ELSE 'queued' END`. Its three call sites:
  - `internal/handlers/subscribe_intake.go`'s recovery poller, on a genuine
    intake-processing error — a real failure;
  - `internal/mailing/outbox_worker.go`'s `finishFailed`, on a genuine
    send/render failure — a real failure;
  - `internal/mailing/outbox_worker.go`'s `deferMissingPhysicalAddress` —
    the one *other* deliberate withholding in the subsystem, and the
    candidate that would have needed to move too. It does **not**: it passes
    `welcomeAddressDeferMaxRetries = math.MaxInt32`, which keeps
    `attempts >= maxRetries` permanently false, so the row always takes the
    `'queued'` branch and the abandoned branch is unreachable by
    construction. Its own doc comment says exactly that, and
    `TestOutboxWorker_DefersWelcome_MissingPhysicalAddress` /
    `TestOutboxWorker_DefersImportInvite_MissingPhysicalAddress` pin it (both
    re-run, both PASS).

So `CancelQueuedTx` was the only correct-withholding that reached
`abandoned`, and it is the only one that moved. The implementer's list of
five still-`abandoned` tests is complete for what it claims; I extended the
check beyond tests to producers, which is the stronger form.

### The delta-based dashboard test — can it pass spuriously?

Asked directly: **no.** Three independent reasons, each checked rather than
assumed.

1. **Nothing else can move the counter inside the window.** Grepping
   `t.Parallel()` across `internal/handlers` and `internal/outbox` returns
   only *comments* about its absence — zero live calls — so tests within
   each package are strictly serial. Across packages, both `TestMain`s call
   `internal/testdb.Lock()` on the same fixed advisory key against the same
   database, so `-p 2` never overlaps two DB-backed packages. There is no
   concurrent writer between the `before` and `after` snapshots.
2. **The load-bearing oracle is not the delta.** The assertion that actually
   discriminates is the absolute one: a direct
   `SELECT status FROM outbound_queue WHERE recipient = $1 AND kind =
   'import_invite'`, keyed to an address minted by `subscribeUniqueEmail`,
   with `t.Fatalf` on anything but `"skipped"`. That cannot pass spuriously
   under any amount of unrelated table churn. The `Skipped == before+1` and
   `Abandoned` deltas corroborate it.
3. **The failure mode of the technique is a false FAIL, not a false PASS.**
   If some other writer did move `Skipped` in the window, the delta would
   exceed 1 and the test would go red — the safe direction.

The one genuinely order-dependent assertion is the literal
`!before.OutboundQueueAbandoned && after.OutboundQueueAbandoned` check, which
goes **vacuous** (not wrong) if an earlier test in the package has already
latched the warning. The test says so in its own comment and does not rest on
it. Judged sound.
