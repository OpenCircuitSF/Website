## Description

Second-batch Raspberry Pi guides. **Read `#0723`'s description first**: it carries the shared rules (no new set, `demoLoaders.ts`, `PROMPTS.md` sections, counts, links inside demos, the pattern in `#0719`–`#0721`).

Guides in this issue:

- `pi-zero-usb-ports` — the Zero 2W's two micro-USB ports: the one marked PWR IN takes power only; the one marked USB is the data (OTG) port, which needs an OTG adapter or hub for a keyboard, drive or USB DAC. The video port is **mini**-HDMI, not micro. Symptoms of the wrong port (keyboard dead, drive not seen). Demo: a drawn Zero 2W with its two ports and the mini-HDMI; drag or pick a device (charger, keyboard via adapter, USB drive, USB DAC, a hub) into a port and see what happens.
- `pi4-micro-hdmi` — no picture from a Pi 4: it has two micro-HDMI ports and the one next to the USB-C power port (HDMI0) is the primary; a monitor turned on after boot or a passive adapter can leave the screen blank; mini vs micro HDMI confusion with the Zero. Check against current Bookworm/KMS behaviour (the old `hdmi_force_hotplug` setting applies to the legacy driver) and mark what is from memory. Demo: plug into port 0 or 1, monitor on before or after boot, cable/adapter type, and see whether there's a picture and why.
- `pi4-heat-throttling` — a Pi 4 slows itself down when hot: soft throttling from 80 °C, harder at 85 °C; `vcgencmd measure_temp` and `vcgencmd get_throttled` (link `pi-undervoltage` for the decoder); a sustained load like an RGB panel or a compile; heatsinks, a fan, a vented case; why the bare board in a closed box is the worst case. Demo: pick load and cooling, and see a temperature curve over a few minutes cross the 80 °C line, with the clock speed dropping. Illustrative model; say so.

**3. Pi 4 heat throttling (illustrative model)**

```ts
export const AMBIENT_C = 25;
export const SOFT_C = 80;        // Arm cores throttled progressively from here (Raspberry Pi docs)
export const HARD_C = 85;        // Arm cores and GPU throttled (Raspberry Pi docs)
export const FLOOR_C = 90;       // model only: clock bottoms out here
export const MAX_MHZ = 1500;
export const SOFT_MIN_MHZ = 1000; // model only: clock at 85 °C
export const MIN_MHZ = 600;       // model only
export const IDLE_W = 2.7;        // model only
export const FULL_W = 6.4;        // model only
export const DURATION_S = 600;
export const HOT_THROTTLED = 0x60006; // capped + throttled, now and since boot

export type HeatLoadId = 'idle' | 'music' | 'rgb' | 'compile';
export const HEAT_LOADS: { id: HeatLoadId; label: string; fraction: number }[] = [
  { id: 'idle', label: 'Idle', fraction: 0 },
  { id: 'music', label: 'Playing music or a small web server', fraction: 0.25 },
  { id: 'rgb', label: 'Driving an RGB LED panel', fraction: 0.6 },
  { id: 'compile', label: 'Compiling code on all four cores', fraction: 1 },
];
export type CoolingId = 'closedBox' | 'bare' | 'heatsink' | 'fan';
export const COOLING: { id: CoolingId; label: string; cPerW: number; tauS: number }[] = [
  { id: 'closedBox', label: 'Bare board in a closed box', cPerW: 13, tauS: 120 },
  { id: 'bare', label: 'Bare board, open air', cPerW: 9, tauS: 90 },
  { id: 'heatsink', label: 'Heatsinks, open air or a vented case', cPerW: 7, tauS: 150 },
  { id: 'fan', label: 'Heatsink and fan', cPerW: 3, tauS: 60 },
];
export function clockMhz(tempC: number): number
//  t < 80 → 1500; 80 ≤ t < 85 → 1500 − (t−80)/5·500; 85 ≤ t < 90 → 1000 − (t−85)/5·400; t ≥ 90 → 600  (continuous, no rounding)
export function powerW(load: HeatLoadId, mhz: number): number
//  IDLE_W + fraction·(FULL_W − IDLE_W)·mhz/MAX_MHZ
export interface HeatSample { t: number; tempC: number; mhz: number }
export type HeatStatus = 'ok' | 'warm' | 'soft' | 'hard';
export const HEAT_TITLES: Record<HeatStatus, string> = {
  ok: 'Full speed, plenty of room',
  warm: 'Warm, still full speed',
  soft: 'Throttling: the Pi slows itself down',
  hard: 'Hot: Arm and GPU both throttled',
};
export interface HeatRun { samples: HeatSample[]; startC: number; endC: number; peakC: number; endMhz: number; minMhz: number; softAtS: number | null; hardAtS: number | null; status: HeatStatus; throttled: number }
export function heatRun(load: HeatLoadId, cooling: CoolingId): HeatRun
export function minSec(s: number): string   // 64 → '1 min 4 s'; 229 → '3 min 49 s'; 45 → '45 s'; 120 → '2 min'
```

`heatRun`, exactly (Euler, 1 s steps): `T = AMBIENT_C + cPerW·IDLE_W`; for `t = 0..600` inclusive: `mhz = clockMhz(T)`; push `{ t, tempC: T, mhz }`; then `T += (AMBIENT_C + cPerW·powerW(load, mhz) − T) / tauS`. So `samples.length === 601`. `startC = samples[0].tempC`, `endC = samples[600].tempC`, `peakC` = max tempC, `endMhz = Math.round(samples[600].mhz)`, `minMhz = Math.round(min mhz)`, `softAtS` = first `t` with `tempC >= 80` else null, `hardAtS` likewise for 85. `status` from `endC`: `< 70` ok, `< 80` warm, `< 85` soft, else hard. `throttled` = `HOT_THROTTLED` for soft/hard, else `0`.

Expected values (computed by the planner with exactly that loop; use `toBeCloseTo(x, 1)` for temperatures, `toBe` for the rest):

| load, cooling | startC | endC | endMhz | softAtS | hardAtS | status |
|---|---|---|---|---|---|---|
| rgb, closedBox (the demo default) | 60.10 | 83.06 | 1194 | 140 | null | soft |
| compile, closedBox | 60.10 | 87.01 | 839 | 64 | 103 | hard |
| compile, bare | 49.30 | 80.81 | 1419 | 229 | null | soft |
| compile, heatsink | 43.90 | 69.33 | 1500 | null | null | ok |
| compile, fan | 33.10 | 44.20 | 1500 | null | null | ok |
| music, closedBox | 60.10 | 72.05 | 1500 | null | null | warm |
| rgb, bare | 49.30 | 69.26 | 1500 | null | null | ok |
| rgb, heatsink | 43.90 | 59.16 | 1500 | null | null | ok |
| idle, fan | 33.10 | 33.10 | 1500 | null | null | ok |

If a value disagrees, the loop differs from the one above (order of push and update, `>=`, or rounding); fix the loop, not the table.

### `TOPIC_BODIES` (plain text, no markup or links)

`pi-zero-usb-ports` — tryIt: "Pick a device and a port and see what happens. Start with the classic mistake: a keyboard in the power port." Ideas:
1. **Two ports, one job each** — "The Zero 2W has two micro-USB ports side by side. The one at the corner, marked PWR IN, takes power and nothing else. The one marked USB is the only data port. A keyboard, a drive or a USB sound card in PWR IN gets power but no data, so nothing happens: the keyboard stays dead, the drive never appears."
2. **You need an adapter, or a hub** — "Keyboards and drives have full-size USB plugs. A micro-USB OTG adapter (a micro-USB plug with a USB-A socket) puts one device on the USB port; a hub on that port gives you several. A hard drive draws more than the port can supply, so give it a powered hub."
3. **The video port is mini-HDMI** — "The third port is mini-HDMI, not micro-HDMI like the Pi 4. A Pi 4 cable won’t fit: you need a mini-HDMI to HDMI cable or adapter."
Takeaway: "Power in PWR IN, everything else in USB through an OTG adapter or a hub."

`pi4-micro-hdmi` — tryIt: "Pick the port, when the screen is switched on and the cable, and see whether you get a picture and why." Ideas:
1. **Two ports, and HDMI0 comes first** — "A Pi 4 has two micro-HDMI ports. HDMI0, the one next to the USB-C power socket, is the first output: with one screen, use it. If one port gives nothing, try the other."
2. **Switch the screen on first** — "At boot the Pi asks the screen what it can show. Most screens answer even when they come on later, but a few say nothing while they are off, and the Pi starts with no picture. Turn the screen on before the Pi, especially when both share a power strip. Very cheap cables can leave out the wire that tells the Pi a screen is there."
3. **Forcing a picture on Bookworm** — "Bookworm’s KMS graphics driver ignores the old hdmi_force_hotplug line in config.txt. To force an output, add video=HDMI-A-1:1280x720@60D to the end of the single line in /boot/firmware/cmdline.txt (HDMI-A-2 for the second port), then reboot. And mini-HDMI is the Zero’s connector: a Zero cable won’t fit a Pi 4."
Takeaway: "HDMI0 next to the power socket, the screen on before the Pi, a decent micro-HDMI cable."

`pi4-heat-throttling` (`temps: true`) — tryIt: "Pick what the Pi is doing and how it is cooled, and watch ten minutes of temperature and clock speed. The numbers are an illustrative model." Ideas:
1. **The Pi protects itself** — "Between {temp:80} and {temp:85} a Pi 4 slows its Arm cores step by step; at {temp:85} it slows the GPU too. Nothing breaks, but everything gets slower: a compile takes longer, an LED panel flickers, music stutters."
2. **Check it** — "vcgencmd measure_temp prints the chip temperature (always in Celsius). vcgencmd get_throttled shows whether it has been capped or throttled; the under-voltage guide decodes it. If it is throttling but under-voltage isn’t set, it is heat."
3. **Give the heat somewhere to go** — "A long busy job, like a compile or driving an RGB panel, heats the chip for minutes. A bare board in a closed box is the worst case: the air inside just gets hotter. Stick-on heatsinks help, a case with vents helps, and a small fan fixes it."
Takeaway: "Under a long load, give a Pi 4 a heatsink and moving air; never a bare board in a sealed box."

### Facts the implementer must list under `### Assumptions` (not confirmed in official docs today)

- Zero 2W silkscreen labels `PWR IN` and `USB`, and their order: mini-HDMI, USB, PWR IN (PWR IN at the corner).
- The Zero 2W can be powered through its USB data port.
- A hard drive may need a powered hub on the Zero's port.
- HDMI0 is the port next to the USB-C power socket, and the Pi 4 port order USB-C, HDMI0, HDMI1, audio (Pi retailer support pages and community docs; the white paper names HDMI 0 without placing it).
- Most screens switched on after boot are picked up by KMS hotplug; HDMI1 alone normally gives a picture on Bookworm.
- HDMI-to-VGA adapters: whether one works depends on the adapter (active conversion; EDID may not pass through).
- A thermally throttled Pi 4 reports `0x60006` (bits 1, 2, 17, 18); real values may differ. Bit 3 is not modelled because the Pi 4 has no soft limit defined.
- The heat model's numbers: 25 °C room, 2.7 W idle and 6.4 W full load, °C/W and time constants per cooling, the 1000 MHz and 600 MHz clock points and the 90 °C floor. Pi 4 base clock 1.5 GHz (1.8 GHz on newer boards).
- `vcgencmd measure_temp` prints `temp=NN.N'C`.
