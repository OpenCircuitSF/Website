# 0097 — Three latent fragilities the suite rewrite left behind

| | |
|---|---|
| **Status** | open |
| **Module** | infra / testdb |
| **Platform** | All |
| **Phase** | 7 — Inbound and polish |

## Description

`#0091`'s review found three things that are **sound today and silently break on a
plausible future edit**. None justified bouncing that fix; all three are the kind of
thing nobody rediscovers until it costs an afternoon.

## 1. `internal/audit`'s read-backs now mean "newest row", not "the only row"

Three assertions use `ORDER BY id DESC LIMIT 1` to read back what a test just wrote.
Before `#0091` the table was truncated per test, so that returned *the* row. Now rows
accumulate within a run, so it returns the *newest* row.

Sound today, because each of those tests performs exactly one `Write` and reads it back
strictly afterwards. It breaks silently the moment someone adds a second `Write` to one
of those tests, or introduces `t.Parallel()` — and it breaks by asserting against the
wrong row, not by erroring.

- [ ] Scope each read-back to the row the test created (by id, or by a value unique to
      it) rather than to recency
- [ ] Or, if recency is genuinely what is being asserted, say so in a comment so the
      next reader knows it is deliberate

## 2. `TestMain`'s entry truncate carries a new fixed 10 s deadline

The `TestMain` entry truncates added by `#0091` impose their own fixed **10-second**
deadline and `os.Exit(1)` the whole package when it expires. The ordering is correct —
pool closed, advisory lock released, then exit, so no lock is leaked — but this is a
new instance of exactly the pattern `#0084` is about: a fixed wall-clock bound on an
operation whose duration depends on contention.

At load ~300 the 5-second truncate deadline fails reliably. A 10-second one is not
obviously safe, and its failure mode is worse: the package dies rather than one test.

- [ ] Bring this deadline under whatever `#0084` decides for the others rather than
      leaving a second, differently-valued fixed bound
- [ ] Ensure the failure is legible — a package that `os.Exit(1)`s should say why

## 3. A shared-pool transaction leak would not fail legibly

`#0091`'s own notes asked that a leaked transaction on the now-shared pool fail with a
clear message. It does not: the message names neither the blocking session nor the
table involved.

There is nothing to chase today — the reviewer polled `pg_stat_activity` through a full
`internal/handlers` run and found no lingering `idle in transaction` session. This is
about the *next* one being diagnosable, given the pool is now shared across every test
in a package rather than created per test.

- [ ] On a lock-wait or truncate timeout, report enough to identify the culprit — the
      blocking pid and the table are the two facts that turn an hour into a minute

## Notes

All three from `#0091`'s review. Recorded rather than fixed there because none is a
defect in that change: items 1 and 2 are consequences of a correct design decision, and
item 3 predates it.

Two facts established by that review and worth keeping: there is **no `t.Parallel()`
anywhere in the repository**, and **no hardcoded row-id literal in any DB-backed test**.
Item 1 stays safe only while the first remains true.
