## Description

`#0091`'s review found three things that are **sound today and silently break on a
plausible future edit**. None justified bouncing that fix; all three are the kind of
thing nobody rediscovers until it costs an afternoon.

## 1. `internal/audit`'s read-backs now mean "newest row", not "the only row"

Three assertions use `ORDER BY id DESC LIMIT 1` to read back what a test just wrote.
Before `#0091` the table was truncated per test, so that returned *the* row. Now rows
accumulate within a run, so it returns the *newest* row.

Sound today, because each of those tests performs exactly one `Write` and reads it back
strictly afterwards. It breaks silently the moment someone adds a second `Write` to one
of those tests, or introduces `t.Parallel()` — and it breaks by asserting against the
wrong row, not by erroring.

- [x] Scope each read-back to the row the test created (by id, or by a value unique to
      it) rather than to recency
- [ ] Or, if recency is genuinely what is being asserted, say so in a comment so the
      next reader knows it is deliberate

## 2. `TestMain`'s entry truncate carries a new fixed 10 s deadline

The `TestMain` entry truncates added by `#0091` impose their own fixed **10-second**
deadline and `os.Exit(1)` the whole package when it expires. The ordering is correct —
pool closed, advisory lock released, then exit, so no lock is leaked — but this is a
new instance of exactly the pattern `#0084` is about: a fixed wall-clock bound on an
operation whose duration depends on contention.

At load ~300 the 5-second truncate deadline fails reliably. A 10-second one is not
obviously safe, and its failure mode is worse: the package dies rather than one test.

- [x] Bring this deadline under whatever `#0084` decides for the others rather than
      leaving a second, differently-valued fixed bound — **done for the four packages in
      lane; `internal/subscribers/main_test.go:44` still carries a bare `10*time.Second`.
      The deferral is legitimate (`#0060` owns the file); the claim that the policy is
      "already unified across every DB-backed package" is not. See Review notes.**
- [x] Ensure the failure is legible — a package that `os.Exit(1)`s should say why

## 3. A shared-pool transaction leak would not fail legibly

`#0091`'s own notes asked that a leaked transaction on the now-shared pool fail with a
clear message. It does not: the message names neither the blocking session nor the
table involved.

There is nothing to chase today — the reviewer polled `pg_stat_activity` through a full
`internal/handlers` run and found no lingering `idle in transaction` session. This is
about the *next* one being diagnosable, given the pool is now shared across every test
in a package rather than created per test.

- [x] On a lock-wait or truncate timeout, report enough to identify the culprit — the
      blocking pid and the table are the two facts that turn an hour into a minute —
      **met as of `6c14922`. The first review found this unmet for tables reached only
      via `CASCADE`; `cascadeClosure` now derives that set from `pg_constraint` instead
      of trusting a hand-written list, and the re-review confirmed the derived closure
      equals Postgres's own `truncate cascades to table` notices at all four call sites,
      exactly. See Review notes, second pass.**

## Implementation notes

All three items reproduced concretely before being touched, per this pass's instructions.

**Item 1 — reachable but silent, and confirmed to trigger exactly as described.**
The three bare `ORDER BY id DESC LIMIT 1` read-backs (`internal/audit/audit_test.go`,
`TestWrite_FullEntryPersists`/`TestWrite_NilActorAndTargetStoreNull`/
`TestWrite_PartialActorWithUser`) are reachable today by any future edit that adds a
second `Write` to one of those tests — no `t.Parallel()` needed. Fixed by adding

scoping the read-back to `WHERE id > $1 ORDER BY id ASC LIMIT 1` (the oldest row after

LIMIT 1` (whichever row is newest at read time). This is "by id", the first option the
checklist offers, not the "say so in a comment" fallback — no test currently depends on
the recency reading, so there was nothing to preserve.

**Item 2 — reachable and, per `#0090`'s recorded evidence, has already fired in
production runs at high load.** `internal/audit`, `internal/workshops`,
`internal/middleware`, and `internal/mailing`'s `TestMain`s each carried their own
`context.WithTimeout(context.Background(), 10*time.Second)` around their entry
`TRUNCATE`, independently of the 20s `handlersDBOpTimeout`/`wiringDBOpTimeout` policy
`#0084` settled on for `internal/handlers`/`cmd/opencircuit`'s equivalent single-statement
bounds. Fixed by adding `testdb.TruncateTimeout` (20s, matching `#0084`'s value and its
justification — see that issue's Work log) and `testdb.EntryTruncate`, a shared helper
every one of those four `TestMain`s now calls instead of composing its own

shared `testdb.EntryTruncate` helper) differs from the four packages this pass
touched. **`internal/subscribers` is different in the number, not just the

**Item 3 — not reachable today** (the issue's own text says as much: the reviewer polled
`pg_stat_activity` and found nothing), but proven fixed by mutation: see Verification.
`testdb.EntryTruncate` now runs a `pg_locks`/`pg_stat_activity` diagnostic query on any
truncate failure, naming every session (other than itself) holding a granted lock on one
of the truncated tables — pid, table, state, query text, and query_start — before
printing why the whole test binary is exiting and calling `os.Exit(1)`. Advisory locks
(the cross-package serialization lock `testdb.Lock` takes) are excluded by construction,
since `pg_locks.relation` is NULL for those and the diagnostic query inner-joins on it —
otherwise every diagnosis would report the currently-running package as a false
"culprit".

**Item 3, phase-2 fix (bounce response).** The mechanism above was sound and stayed
untouched; the defect the reviewer found was that the four call sites' hand-written
`tables` arguments were incomplete — `internal/audit` omitted 6 CASCADE-reached
relations, `internal/middleware` 4, `internal/workshops` 3 — so the diagnostic's own
query never looked at the table actually holding the blocking lock, and its fallback
branch then asserted "the failure was not a lock wait at all" in exactly that
situation (reproduced by the reviewer: a lock on `sessions`, a cascade target of
`internal/audit`'s truncate but absent from its list, produced that false claim).

Fixed by removing the class rather than patching the four instances: `tables` now
means only the relations named literally in the `TRUNCATE` statement itself (what
every call site already passed, except `internal/workshops`, which had hand-added
`workshop_interests` — trimmed back to `[]string{"workshops"}`, since it no longer
needs to). `EntryTruncate` derives the actual `TRUNCATE ... CASCADE` lock set itself,
on a failure, via a new `cascadeClosure` helper in `internal/testdb/testdb.go`: it
reads every foreign key in `pg_constraint` (`contype = 'f'`) — not only the
`ON DELETE CASCADE` subset, because `TRUNCATE ... CASCADE` locks (and truncates) any
referencing table regardless of that FK's `ON DELETE` action, which is exactly how
`internal/audit`'s missing `email_campaigns` (referenced from `users.id` by
`email_campaigns.created_by`, a plain `REFERENCES` with no `ON DELETE` clause at all,
`migrations/000017_create_campaigns.up.sql`) and `internal/workshops`'s missing
`email_campaigns` (referenced from `workshops.id` the same way, `migrations/000020`)
were actually being locked — then walks that graph breadth-first from the literal
roots to a fixed point. This makes the doc comment's contract ("names every relation
the TRUNCATE locks") structurally true rather than a per-call-site obligation that
silently rots as the schema grows a new foreign key. Verified against Postgres's own
behavior for all four statements — see Verification.

Also fixed, both named by the review:

- The fallback message no longer claims a conclusion the code hasn't earned. It now
  reads `"no lock holder found on <relations> at diagnosis time — the blocker may
  have released between the timeout and this check, or is holding a lock this
  diagnostic did not check for"` — honest about what was and wasn't checked, instead
  of asserting the failure "was not a lock wait at all."
- `diagnoseLockHolders`' dedupe was by pid alone (`seen[pid]`), so a session holding
  locks on several of the truncated/cascaded tables was reported against only
  whichever relation sorted first. It now aggregates every distinct relation name a
  given pid holds a lock on into one line (`pid N holds a lock on a, b, c, ...`)
  instead of dropping the rest.

**The watermark itself probes clean**, on all three questions asked:

- **Empty table.** `SELECT MAX(id) FROM audit_log` returns NULL, `auditLogWatermark`
  maps that to `0`, and `id > 0` is a safe sentinel because the sequence behind
  `audit_log.id` has `seqmin = 1, seqstart = 1, seqincrement = 1` — no real row can
  ever be `<= 0`. This path is not theoretical: `TestMain`'s
  `TRUNCATE ... RESTART IDENTITY` means the first writing test in every run takes
  the watermark against an empty table.
- **Identical timestamps.** Inserted two rows in one statement with a
  byte-identical `created_at`; they got ids 1 and 2, and
  `WHERE id > 0 ORDER BY id ASC LIMIT 1` returned the *first*
  (`ORDER BY id DESC LIMIT 1` returned the second). Ordering is by the sequence,
  not the clock, so a timestamp tie cannot confuse it.
- **Monotonicity.** `audit_log.id` is `BIGSERIAL PRIMARY KEY`
  (`migrations/000005_create_audit_log.up.sql:4`), i.e. sequence-backed with
  increment 1. The only reset is `TestMain`'s `RESTART IDENTITY`, which runs before
  any watermark is taken.

One residual, **not** a bounce reason: the doc comment says the scoping "stays
correct … even if another test's rows land around it in the same run." Strictly,
"oldest row after the watermark" is the test's own row only if the test's Write is
the *next* insert. A concurrent writer between watermark and Write would break it.
That cannot happen today (no `t.Parallel()`, one advisory lock, one pool), and the
comment's premise is stated a few lines above it — so this is a slightly
over-broad sentence, not a defect.

**It uses a fresh context, and this is proven rather than read.**
`diagnoseLockHolders` builds its own `context.WithTimeout(context.Background(),
5*time.Second)` (`internal/testdb/testdb.go`) rather than inheriting the truncate's.
The reproduction above is the proof: the diagnostic ran and returned rows *after*
the truncate context had already expired. It also cannot hang — its own 5s bound —
and it queries `pg_locks`/`pg_stat_activity`, which no table lock can block.

showed both (`locktype='advisory'` with `relation` NULL for pid 85046;
`locktype='relation'` for pid 85045). The diagnostic named **only** pid 85045.
The inner join on `pg_class.oid = l.relation` drops advisory rows exactly as the
comment claims — no false-culprit noise.

#### Why this bounces

`EntryTruncate`'s own doc comment states the contract for its `tables` argument:

> tables names **every relation sqlStmt's TRUNCATE takes a lock on — including any
> table it reaches only via ON DELETE CASCADE**, since TRUNCATE ... CASCADE locks
> those too.

Three of the four call sites the same commit wrote break that contract. Measured
by running each statement and reading Postgres's own `truncate cascades to table`
notices:

| Package | Declared `tables` | Cascade targets it also locks but does **not** declare |
|---|---|---|
| `internal/audit` | `audit_log, users` | `passkey_credentials`, `webauthn_challenges`, `sessions`, `email_campaigns`, `campaign_interests`, `email_sends` — **6 missing** |
| `internal/middleware` | the 6 named | `webauthn_challenges`, `email_campaigns`, `email_sends`, `campaign_interests` — **4 missing** |
| `internal/workshops` | `workshops, workshop_interests` | `email_campaigns`, `campaign_interests`, `email_sends` — **3 missing** |
| `internal/mailing` | the 6 named | none — complete, incidentally |

`internal/workshops` is the sharp one: its comment specifically works through the
cascade rule for `workshop_interests` ("CASCADE locks it too, and #0097 item 3's
diagnosis needs to know to look there"), so the rule was understood — and then
applied at one call site, partially.

**Reproduction B — what the gap actually does.** Held
`LOCK TABLE sessions IN ACCESS EXCLUSIVE MODE` (pid 85687) — `sessions` is a
cascade target of `internal/audit`'s truncate, and is absent from its `tables`
list — and ran `EntryTruncate` with `internal/audit`'s verbatim arguments. The
truncate blocked and timed out, as it must. The diagnostic said:

```
testdb: entry truncate failed: timeout: context deadline exceeded
testdb: no lock holder found on audit_log, users at diagnosis time — the blocker may have released between the timeout and this check, or the failure was not a lock wait at all
```

The blocker had not released, and the failure *was* a lock wait. The pid was
sitting in `pg_locks` the whole time. This is not "item 3 covers less than hoped";
it is the diagnostic asserting, in the one situation it exists for, that the thing
that just happened probably did not happen. That is worse than the bare
`context deadline exceeded` it replaced, because the bare error at least does not
send the reader somewhere else. Item 3's criterion — "the blocking pid and the
table are the two facts that turn an hour into a minute" — is inverted here.

#### What to change

Preferred: **stop trusting a hand-written list**. The cascade closure is derivable
from the catalog, so the helper can compute it and the call sites cannot get it
wrong — walk `pg_constraint` (`contype='f'`, `confdeltype='c'`) transitively from
the named relations, or simply have `diagnoseLockHolders` report every session
holding a conflicting lock on any relation in that closure. That makes the doc
comment's contract structurally true instead of a per-call-site obligation.

Acceptable alternative: complete the three lists by hand — but then the contract is
one migration away from silently breaking again (a new `ON DELETE CASCADE` child
of `users` re-opens the `internal/audit` gap with nothing to catch it), so if you
take this route, add a test that asserts each declared list equals the statement's
actual cascade closure.

Either way, the fallback message should stop asserting a cause. "No lock holder
found on the tables I was told to check" is honest; "the failure was not a lock
wait at all" is a conclusion the code has not earned.

#### One smaller thing, worth fixing in the same pass

`diagnoseLockHolders` de-duplicates by pid (`seen[pid]`, `internal/testdb/testdb.go:215`),
so a session holding locks on two of the truncated tables is reported against only
whichever relation `ORDER BY l.pid` happens to surface first. The pid is the
load-bearing fact and it survives, but the table named alongside it may be an
arbitrary one of several. Either drop the dedupe or aggregate the relnames per pid.

### The walk itself

- **Breadth-first from the literal roots, and it terminates on a cycle.** The `seen`
  map is set at enqueue time, so a node is queued at most once. Proved rather than
  read: built a two-node FK cycle (`zz_rr_a.bid → zz_rr_b.id`, `zz_rr_b.aid →
  zz_rr_a.id`) in my own database; `cascadeClosure` returned `[zz_rr_a zz_rr_b …]`
  and returned promptly from either root.
- **Self-referencing FK does not loop.** `zz_rr_self(parent → zz_rr_self.id)` returns
  `[zz_rr_self]` — the child is already `seen` as a root, so it is skipped.
- **Neither exists in the real schema.** A recursive `pg_constraint` walk found no FK
  cycle and no self-referencing FK anywhere in this database. So both properties are
  latent-only today; they are still worth having, since the walk is unconditional and
  a future `parent_id`-style column would otherwise hang `TestMain`'s failure path.
- **Different schema / quoting is a real, latent format mismatch.** `cascadeClosure`
  emits `conrelid::regclass::text`, which quotes and schema-qualifies as needed, while
  `diagnoseLockHolders` matches on `pg_class.relname`, which is raw and unqualified.
  Held a genuine `ACCESS EXCLUSIVE` lock on a table in a non-`search_path` schema and
  on one with a quoted mixed-case name, then asked the diagnostic using exactly the
  strings the closure produces (`zz_rr_other.zz_rr_child` and `"zz rr Quoted"`, quotes
  included): it returned **nothing**, while the same query with bare relnames
  (`zz_rr_child`, `zz rr Quoted`) named the holder correctly. The converse also holds —
  a bare `relname` match would report a same-named table in *any* schema, a false
  positive. **Not a bounce reason:** every relation in this schema is in `public` with
  a lowercase unquoted name (verified — `regclass::text` returns bare names for all of
  them), and the failure mode now degrades to the honest fallback message rather than
  a false claim. Worth a small follow-up; reported to the orchestrator, not filed.
