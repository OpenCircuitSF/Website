## Description

`#0091`'s review found three things that are **sound today and silently break on a
plausible future edit**. None justified bouncing that fix; all three are the kind of
thing nobody rediscovers until it costs an afternoon.

## 1. `internal/audit`'s read-backs now mean "newest row", not "the only row"

Three assertions use `ORDER BY id DESC LIMIT 1` to read back what a test just wrote.
Before `#0091` the table was truncated per test, so that returned *the* row. Now rows
accumulate within a run, so it returns the *newest* row.

Sound today, because each of those tests performs exactly one `Write` and reads it back
strictly afterwards. It breaks silently the moment someone adds a second `Write` to one
of those tests, or introduces `t.Parallel()` — and it breaks by asserting against the
wrong row, not by erroring.

- [x] Scope each read-back to the row the test created (by id, or by a value unique to
      it) rather than to recency
- [ ] Or, if recency is genuinely what is being asserted, say so in a comment so the
      next reader knows it is deliberate

## 2. `TestMain`'s entry truncate carries a new fixed 10 s deadline

The `TestMain` entry truncates added by `#0091` impose their own fixed **10-second**
deadline and `os.Exit(1)` the whole package when it expires. The ordering is correct —
pool closed, advisory lock released, then exit, so no lock is leaked — but this is a
new instance of exactly the pattern `#0084` is about: a fixed wall-clock bound on an
operation whose duration depends on contention.

At load ~300 the 5-second truncate deadline fails reliably. A 10-second one is not
obviously safe, and its failure mode is worse: the package dies rather than one test.

- [x] Bring this deadline under whatever `#0084` decides for the others rather than
      leaving a second, differently-valued fixed bound
- [x] Ensure the failure is legible — a package that `os.Exit(1)`s should say why

## 3. A shared-pool transaction leak would not fail legibly

`#0091`'s own notes asked that a leaked transaction on the now-shared pool fail with a
clear message. It does not: the message names neither the blocking session nor the
table involved.

There is nothing to chase today — the reviewer polled `pg_stat_activity` through a full
`internal/handlers` run and found no lingering `idle in transaction` session. This is
about the *next* one being diagnosable, given the pool is now shared across every test
in a package rather than created per test.

- [x] On a lock-wait or truncate timeout, report enough to identify the culprit — the
      blocking pid and the table are the two facts that turn an hour into a minute

## Notes

All three from `#0091`'s review. Recorded rather than fixed there because none is a
defect in that change: items 1 and 2 are consequences of a correct design decision, and
item 3 predates it.

Two facts established by that review and worth keeping: there is **no `t.Parallel()`
anywhere in the repository**, and **no hardcoded row-id literal in any DB-backed test**.
Item 1 stays safe only while the first remains true.

## Implementation notes

All three items reproduced concretely before being touched, per this pass's instructions.

**Item 1 — reachable but silent, and confirmed to trigger exactly as described.**
The three bare `ORDER BY id DESC LIMIT 1` read-backs (`internal/audit/audit_test.go`,
`TestWrite_FullEntryPersists`/`TestWrite_NilActorAndTargetStoreNull`/
`TestWrite_PartialActorWithUser`) are reachable today by any future edit that adds a
second `Write` to one of those tests — no `t.Parallel()` needed. Fixed by adding
`auditLogWatermark(t, pool)`, called immediately before each test's own `Write`, and
scoping the read-back to `WHERE id > $1 ORDER BY id ASC LIMIT 1` (the oldest row after
the watermark — the row that specific `Write` created) instead of `ORDER BY id DESC
LIMIT 1` (whichever row is newest at read time). This is "by id", the first option the
checklist offers, not the "say so in a comment" fallback — no test currently depends on
the recency reading, so there was nothing to preserve.

**Item 2 — reachable and, per `#0090`'s recorded evidence, has already fired in
production runs at high load.** `internal/audit`, `internal/workshops`,
`internal/middleware`, and `internal/mailing`'s `TestMain`s each carried their own
`context.WithTimeout(context.Background(), 10*time.Second)` around their entry
`TRUNCATE`, independently of the 20s `handlersDBOpTimeout`/`wiringDBOpTimeout` policy
`#0084` settled on for `internal/handlers`/`cmd/opencircuit`'s equivalent single-statement
bounds. Fixed by adding `testdb.TruncateTimeout` (20s, matching `#0084`'s value and its
justification — see that issue's Work log) and `testdb.EntryTruncate`, a shared helper
every one of those four `TestMain`s now calls instead of composing its own
`context.WithTimeout` + `Exec` + error-handling block. `internal/handlers` and
`internal/subscribers` were left untouched — out of scope for this pass (owned by
`#0060`) — but `internal/handlers` already carries the same 20s value via its own local
`handlersDBOpTimeout` constant (added during `#0084`'s work), so the numeric policy is
already unified across every DB-backed package; only the *mechanism* (a shared helper
vs. a locally duplicated one) differs for that one package. `internal/db` and
`cmd/opencircuit`'s own `TestMain`s have no entry truncate at all (confirmed by
inspection), so item 2 does not apply to them.

**Item 3 — not reachable today** (the issue's own text says as much: the reviewer polled
`pg_stat_activity` and found nothing), but proven fixed by mutation: see Verification.
`testdb.EntryTruncate` now runs a `pg_locks`/`pg_stat_activity` diagnostic query on any
truncate failure, naming every session (other than itself) holding a granted lock on one
of the truncated tables — pid, table, state, query text, and query_start — before
printing why the whole test binary is exiting and calling `os.Exit(1)`. Advisory locks
(the cross-package serialization lock `testdb.Lock` takes) are excluded by construction,
since `pg_locks.relation` is NULL for those and the diagnostic query inner-joins on it —
otherwise every diagnosis would report the currently-running package as a false
"culprit".

## Verification

`ISSUE=0097 scripts/check.sh go ./internal/... ./cmd/...` — all 16 packages `ok`, zero
skips, real non-zero elapsed times (`internal/handlers` 3.065s, `internal/interests`
3.006s, `cmd/opencircuit` 1.518s, etc.). `go build ./...`, `go vet ./...`, `gofmt -l`
all clean.

**Mutation proof, item 1** (`internal/audit/audit_test.go`, `TestWrite_FullEntryPersists`):
added a second `logger.Write` between the test's real `Write` and its read-back (the
exact "someone adds a second Write" scenario the issue names). With the fix in place the
test still passed — the watermark-scoped read-back still located the first `Write`'s row.
Reverting only the read-back's `WHERE` clause to the original `ORDER BY id DESC LIMIT 1`,
under the same two-`Write` mutation, reproduced the predicted failure exactly:
`action = "account.registration_started", want "link.created"` plus four other field
mismatches and a JSON-unmarshal error on a NULL `metadata` — i.e. it silently read the
second (wrong) row. Reverted; `shasum -a 256` confirmed `audit_test.go` byte-identical
to its pre-mutation state afterward.

**Mutation proof, items 2 and 3** (`internal/testdb`): held a real `AccessExclusiveLock`
on `audit_log` from a separate `psql` session (`BEGIN; LOCK TABLE audit_log IN ACCESS
EXCLUSIVE MODE; SELECT pg_sleep(15); COMMIT;`), confirmed via `pg_locks` that the lock
was actually granted, then ran a temporary test calling `testdb.EntryTruncate` against
`audit_log` (with `TruncateTimeout` temporarily shrunk to 3s so the proof didn't need a
20s wait) while the lock was held. Output:

```
testdb: entry truncate failed: timeout: context deadline exceeded
testdb: session(s) holding a lock on audit_log at diagnosis time:
  pid 80358 holds a lock on audit_log, state=active, query_start=2026-08-23T19:49:42-07:00: <lock-holder's query text>
testdb: exiting this test binary (os.Exit(1)) — TestMain cannot guarantee a clean starting state for audit_log, so no test in this package can safely run
```

pid `80358` matched the lock-holding session's actual backend pid, independently
confirmed via `select pid from pg_stat_activity`/`pg_locks` before the run. Process
exited 1, as designed. Reverted the temporary `TruncateTimeout` shrink and deleted the
temporary test file; `shasum -a 256` confirmed `internal/testdb/testdb.go` byte-identical
to its pre-mutation state afterward.

`scripts/testdb_gc_guard_test.sh` — `all guards hold (0 failures)`; confirmed
`scripts/testdb.sh` itself unchanged (`sha256` printed by the script matches before/after).

**Database census.** Before this pass: `opencircuit`, `opencircuit_test`,
`opencircuit_test_template` only. `opencircuit_test_0097` created via `scripts/testdb.sh
create 0097` for the `check.sh` run and dropped automatically by `check.sh` on exit
(confirmed absent afterward). The mutation proofs' lock-holder `psql` session ran against
`opencircuit_test_0097` directly and was terminated (not dropped — no scratch database of
its own). `testdb_gc_guard_test.sh`'s own run left one scratch database
(`opencircuit_test_0150gt_conn`) behind — that script's own cleanup trap kills its
background `pg_sleep` connection then immediately runs `DROP DATABASE`, and the two can
race; the connection wasn't fully closed by the time the drop ran, so `dropdb_raw`'s
swallowed-error `DROP DATABASE IF EXISTS ... || true` silently no-opped. Confirmed no
live connection remained and dropped it by hand. This is a pre-existing gap in
`testdb_gc_guard_test.sh`'s own cleanup ordering (not something this pass's code changes
could cause or fix, since `scripts/testdb.sh` itself was never touched) — worth a small
follow-up (e.g. a short poll/wait after the `kill` before the `DROP DATABASE`, mirroring
the poll this same script already uses to wait *for* the connection to appear) but out
of scope here. Final census: `opencircuit`, `opencircuit_test`,
`opencircuit_test_template` only.
