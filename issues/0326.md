## Description

`#0054`'s scope note already concedes that `cmd/opencircuit/seo_wiring_test.go`
**rebuilds the wiring shape by hand** and would not catch a literal `nil` or a
second `buildSEOSite` reintroduced inside `servePostgres`.

That gap now covers **three** nil-tolerant call sites:

- `NewAdminWorkshopsHandler`
- `NewAdminCampaignArchiveHandler` (added by `#0319`)
- `newSendWorkerIfEnabled` (added by `#0319`)

All three accept `nil` and degrade silently. `admin_wiring_test.go` and
`worker_wiring_test.go` already pass literal `nil`. So a future `servePostgres`
edit that passes `nil`, or calls `buildSEOSite` twice and hands out two different
`*seo.Site` instances, would **compile, keep every test green, and silently
restore the 60-second staleness `#0319` just removed**.

`#0319`'s reviewer identified this as a live fail-open rather than a theoretical
one, and it is the same shape as `#0054`'s Ruling 1: a counting fake "only proves
`InvalidateWorkshops` gets CALLED, never that the object it's called on is the
one anything actually reads from."

## The shape to use

The project already has this pattern — `#0181`, `#0197`, `#0120` are AST guards
over source structure. **An AST guard over `servePostgres` asserting that the
same `site` identifier reaches all three call sites closes all three at once**,
and would keep closing them as more are added.

## Acceptance criteria

1. A guard asserts that within `servePostgres`, one `*seo.Site` value flows to
   every consumer that takes one — today `NewAdminWorkshopsHandler`,
   `NewAdminCampaignArchiveHandler`, and `newSendWorkerIfEnabled`.
2. It fails when a call site is passed `nil`, and when `buildSEOSite` is called
   more than once. **Prove both** against mutated copies, in a worktree — do not
   mutate the shared tree.
3. It fails closed if its scan finds no call sites at all — `#0275`'s lesson, and
   `#0300`'s. An empty extraction must be an error, never an input.
4. The guard enumerates consumers rather than hard-coding today's three, so a
   fourth is covered on the day it appears. If that is not practical, say why and
   make the omission loud.
5. Per CLAUDE.md §8's placement rule: decide whether this belongs in Go or in the
   external harness, using the falsifiability test — after the mutation, is the
   assertion still falsifiable by the thing it measures? Record the reasoning.
6. `#0054`'s existing test stays. This adds a check it explicitly declined to
   make; it does not replace it.
7. `ISSUE=NNNN scripts/check.sh go ./cmd/opencircuit/... ./internal/seo/...`
   passes with no skips.

## Root cause

`#0054`'s `seo_wiring_test.go` proves same-instance identity between
`servePostgres`'s `site` and what `mountAndServe` mounts, but it does that
by re-deriving the wiring shape and driving a real HTTP listener — it never
reads `servePostgres`'s own source, so it cannot notice a *different* future
edit that quietly hands a *different* consumer `nil`, or that duplicates
`buildSEOSite`. `admin_wiring_test.go` and `worker_wiring_test.go` pass
literal `nil` on purpose (to prove the nil-tolerant degrade path), so a
regression here would not even show up as a new kind of test failure — it
would look identical to the deliberate nil-tolerance tests already passing.

## Fix

Added `cmd/opencircuit/servepostgres_seo_instance_guard_test.go`,
`TestServePostgres_OneSEOSiteFlowsToEveryConsumer` — an AST test in the same
family as `admin_routes_ast_test.go` (`#0079`) and the citation guards
(`#0181`/`#0197`/`#0120`). It:

1. Parses `main.go`, finds `servePostgres`, and asserts `buildSEOSite` is
   called **exactly once** inside it — zero is a broken-scan failure
   (fail-closed), more than one is criterion 2's "two different instances"
   mutation.
2. Enumerates every call in `servePostgres`, resolves each callee's own
   declared parameter types (parsing the callee's defining file — in
   `cmd/opencircuit` itself for a package-local helper like
   `newSendWorkerIfEnabled`, or in `internal/handlers`/`internal/mailing`
   for a package-qualified call), and treats a parameter as
   "*seo.Site-shaped*" if it is literally `*seo.Site`, or a type whose full
   declared method set is exactly one method, `Invalidate()` — the exact
   shape `#0325` just gave `*seo.Site.Invalidate`,
   `workshopCacheInvalidator`, and `mailing.ArchiveCacheInvalidator` alike.
   **No function name is hardcoded anywhere in this file** — the scan finds
   today's three consumers because their signatures have that shape, and
   would find a fourth the same way, satisfying criterion 4 directly rather
   than by promise.
3. Asserts every discovered position receives the exact identifier
   `buildSEOSite`'s call bound (`site`), not `nil` and not a different
   expression.
4. Fails closed (criterion 3) at two separate points: if it resolves zero
   callee signatures at all, or if it resolves callees but finds zero
   site-shaped parameters among them — either is treated as "this scan
   broke", never as "there is nothing to check".

### Criterion 5 — placement: in Go, not an external harness

Applied CLAUDE.md §8's falsifiability test directly: the subject is
`main.go`'s own source text, and this test calls `parser.ParseFile("main.go",
...)` fresh on every run — identical to how `admin_routes_ast_test.go`
already does it. There is no compiled or cached form of `servePostgres`'s
wiring for a mutation to hide behind (the "self-check can start measuring
the process instead of the file" trap CLAUDE.md documents), and no
subprocess boundary an external shell harness would need to cross to see
the same text — it would have to reimplement Go parsing to gain nothing an
in-process `go/ast` read doesn't already have. Full reasoning is in the
test's own doc comment.

## Gotchas

- BSD `sed -i` on this machine does not support `\b` word-boundary regex
  syntax — a `sed 's/\bbuildSEOSite\b/.../'` mutation silently matched
  nothing (exit 0, zero replacements) rather than erroring, which read
  exactly like "no such string" rather than "wrong regex dialect". Switched
  to Python's `re.sub` for that one mutation. Consistent with CLAUDE.md's
  own "agent shell is zsh, scripts are bash" entry — the underlying lesson
  generalizes to any platform-specific tool behavior assumed identical
  across machines.
- A first attempt at proving the "zero call sites" fail-closed path by
  renaming the `buildSEOSite` **function definition** broke compilation of
  ten unrelated `*_wiring_test.go` files that also call `buildSEOSite`
  directly for their own fixtures — a realistic mutation would never do
  this (it is simply a compile error, a much louder and different failure
  mode than this guard). Used the closure-wrapping mutation instead, which
  changes nothing about `buildSEOSite` itself and isolates exactly the
  "this scan's literal-name match finds nothing" case this guard needs to
  survive.

The issue mandated two mutations; the implementer proved three (one nil
position, the second instance, and the fail-closed path). M2, M3, M6, and M7
are additional and were the ones worth having: **M1–M3 prove each of the three
consumers independently** rather than inferring the other two from one, **M6
proves the anti-vacuity floor actually fires** when discovery silently
degrades rather than collapsing to zero, and **M7 proves criterion 4's
open-endedness by construction** — a consumer that did not exist when the
guard was written is discovered and enforced with no edit to the guard.

The implementer's M6-equivalent (adding a second method to the interface) is
worth noting as a mutation that proves nothing: it makes `*seo.Site` stop
satisfying the interface, so the tree no longer compiles. A compile error is a
louder and different failure than the one under test. The embedded-interface
form above is the version that keeps the program valid while breaking only the
guard's own type-shape matcher.

### It cannot report success vacuously

Four independent fail-closed points, three of which were exercised above:
`len(buildCalls) == 0` → `t.Fatal` (M5); `resolvedCalleeCount == 0` →
`t.Fatal`; `len(consumers) == 0` → `t.Fatal`; and the
`knownConsumersAsOfWriting` floor (M6). The exactly-once assertion **cannot**
be satisfied by zero calls — zero is its own `t.Fatal` arm, not a `default`
that falls through. `findFuncParamTypes` `t.Fatalf`s on an unreadable
directory rather than returning "not found", so a moved package fails loudly
instead of shrinking the consumer set.

**Oracle vs subject (§8):** the subject is `cmd/opencircuit/main.go`'s source
text; the oracle is a separate file that re-parses it with `parser.ParseFile`
on every run. No edit to `main.go` can also satisfy the oracle — this is not
the "copy of the answer stored next to the question" shape. Criterion 5's
placement reasoning is sound and correctly recorded in the test's doc comment:
an external shell harness would have to reimplement Go parsing to see the same
text, buying no falsifiability the in-process `go/ast` read lacks. There is no
compiled or cached form for a mutation to hide behind, which is what makes
this different from the `scripts/check.sh` self-check family.

### `web/dist` and the route table (unaffected)

`92543aa` adds one new file and touches nothing else — `git show --stat`
confirms `main.go` is not in the commit, so the route table and the
`//go:embed all:dist` wiring are untouched. The guard **does not require

Verified directly — the baseline run above was in exactly such a worktree.

### Two minor inaccuracies, neither blocking

- The scan actually discovers **four** site-shaped consumer positions, not
  three: `mountAndServe param 34 (site)` is a literal `*seo.Site` parameter and
  is enforced too (visible in M6's failure output). The
  `knownConsumersAsOfWriting = 3` floor is therefore set one below the real
  count, leaving exactly one consumer's worth of silent-degradation slack — a
  4→3 regression would pass. The comment "as of writing there are three known
  consumers" is likewise off by one. It is a floor and is documented as one, so
  this weakens rather than breaks the guard.
- `interfaceIsInvalidateOnly`'s doc comment says "no parameters, no results",
  but the code checks only `ft.Params`; an `Invalidate() error` interface would
  still match. This can only *widen* discovery, never narrow it, so it cannot
  cause a false pass.

Both are reported for a follow-up rather than bounced.
