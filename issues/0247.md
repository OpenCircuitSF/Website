## Description

> 🟢 **Resolved 2026-08-24** (`479bf81`) — re-reviewed by running the
> drill twice concurrently myself, with `ISSUE` unset so the `$$` default was
> the thing under test. Two distinct namespaces, zero cross-references between
> the logs, both runs reaching the same result independently. Cleanup is fully
> parameterised — there is no bare fixed name left anywhere in the drill.

`docs/deployment.md`'s restore drill names fixed resources throughout: the
database `0062src`, the target `opencircuit_test_0062dst`, and the directory
`/tmp/backup-drill` — including a fixed `-latest.dump` inside it.

Two people following the drill at once collide on all three. `CLAUDE.md` §5a
makes concurrent agents the norm on this project and §8b is explicit that a
shared mutable resource must be namespaced or ownership-verified. The drill is
a procedure that creates and **drops** databases and overwrites a dump file, so
a collision is not a confusing error — it is one run destroying another's target
mid-restore, or restoring from a dump the other run just replaced.

Pre-existing rather than introduced by `#0239`'s rewrite, and found by that
issue's review while following the drill verbatim.

**The drill is also the one document most likely to be followed by two people
simultaneously** — during an incident, or while someone rehearses it. That is
precisely when a silent cross-run collision is least affordable.

## Implementation notes

Reused the project's existing `ISSUE=NNNN` / `scripts/testdb.sh` convention
(`CLAUDE.md` §5a) rather than inventing a second naming scheme, exactly as
the first acceptance criterion asks. Step 1 — the first point in the drill
where a namespace is actually needed, not a preamble someone would skip
past — now reads:

```bash
ISSUE="${ISSUE:-$$}"
echo "Running the drill under ISSUE=${ISSUE}"
DSN="$(scripts/testdb.sh create "${ISSUE}src")"
```

and every database name, `BACKUP_ROOT`, and dump path in the rest of the
drill is derived from `$ISSUE` from there on: `opencircuit_test_${ISSUE}src`
/ `opencircuit_test_${ISSUE}dst` for the two databases, and
`/tmp/backup-drill-${ISSUE}` for the backup directory (step 4). The dump
filename itself is protected two independent ways, not just one: it lives
inside the per-run `BACKUP_ROOT` directory, and `backup.sh` already names it
after the database (`opencircuit_test_${ISSUE}src-latest.dump`), which is
now also namespaced. Step 9's cleanup drops only `"${ISSUE}src"` /
`"${ISSUE}dst"` via `scripts/testdb.sh drop` and removes only
`/tmp/backup-drill-${ISSUE}` — never a bare `DROP DATABASE` or `rm -rf` on a
fixed name, satisfying the fourth criterion.

Setting `ISSUE` defaults to `$$` (the running shell's PID) if unset, which
is always a distinct, purely-numeric token per process — deliberately, to
sidestep a real bug found while testing this fix (see `## Gotchas` below):
`scripts/testdb.sh`'s `CREATE DATABASE $db ...` interpolates the database
name unquoted into SQL, so Postgres folds a mixed-case id to lowercase, and
a token containing letters silently doesn't round-trip through the DSN
`testdb.sh create` hands back. The project's own `ISSUE=NNNN` convention is
already numeric-only in every example in `CLAUDE.md`/`Issues.md`, so this
never bites in normal use; the PID default keeps the drill's own generated
default in that same safe shape.

Folded in the smaller item from the same review: step 2's comment now names
both enum values correctly, checked directly against the CHECK constraints
that define them rather than guessed — `migrations/000012_create_suppressions.up.sql`
(`suppressions_reason_check`: `hard_bounce | complaint | manual |
repeated_soft_bounce`) and `migrations/000010_create_subscribers.up.sql`
(`subscribers_status_check`: `pending | active | unsubscribed | bounced |
complained`).

Landed together with `#0239`'s bounce fix (step 7) in one editing pass
since both touch the same ~200-line drill block and were found by the same
review, but as **two separate commits**: `c7812ef` (`#0239`) carries only
the step-7 fix, applied first against the drill's pre-existing
`0062src`/`0062dst` names; this issue's commit `479bf81` layers the
`ISSUE=NNNN` namespacing on top of that already-committed state. `git show
479bf81` is a clean, isolated diff of just the namespacing change plus the
step-2 enum correction.

## Gotchas

Found and worked around, not introduced by this fix: an early attempt at
the concurrency proof used mixed-case `ISSUE` values (`0247concA` /
`0247concB`) and both runs failed immediately at step 1 with `database
"opencircuit_test_0247concAsrc" does not exist` — `scripts/testdb.sh`
(a file this dispatch was told not to touch; another agent's session was
mid-edit on it and landed a fix for the same underlying case-folding issue,
`#0208`, while this pass was running) folds an unquoted `CREATE DATABASE`
identifier to lowercase, so the DSN handed back (built from the original,
unfolded string) named a database that was never actually created under
that spelling. Not a namespacing defect in this fix — `ISSUE=NNNN` is
numeric-only everywhere else in this project's convention — but worth
recording so nobody "fixes" this drill's `$$`-default away in favor of
something with letters in it. The two mis-cased leftover databases
(`opencircuit_test_0247concasrc`/`...concbsrc`) were dropped by hand before
the real concurrency proof below.

### The concurrency proof, re-run independently

Same extraction method as `#0239`'s re-review: `sed -n '978,1158p'
docs/deployment.md` gives the drill code block byte-for-byte; `bash -n` and
`shellcheck` both pass **clean** on it (shebang prepended — it is a doc

extraction.

Launched two copies of that identical script together, **`ISSUE` unset** via
`env -u ISSUE` so each run had to fall back to the documented `$$` default —
that default is the mechanism under test, so special-casing a value would have
proved nothing:

```
( env -u ISSUE bash drill.sh > concA.log 2>&1; echo "A exit=$?" ) &
( env -u ISSUE bash drill.sh > concB.log 2>&1; echo "B exit=$?" ) &
wait
```

`A exit=0`, `B exit=0`. Run A picked `ISSUE=52802`, run B `ISSUE=52803` — their
own PIDs, distinct. `uptime` 2.59 at launch, so this was a genuinely
concurrent pair on an idle machine, not two runs serialised behind a busy one.

**Isolation, checked mechanically rather than by eye.** I enumerated every

of database`. The implementer's conclusion is right, but it rests on their
line-by-line log grep, not on the exit codes they lead with. I verified by
milestone table above rather than by exit status.

### Criterion 4 — cleanup drops only that run's resources

Audited the drill for any fixed name by stripping comments and listing every
executable line that names a database or directory. **Every one is derived from
`$ISSUE`:**

```
ISSUE="${ISSUE:-$$}"
DSN="$(scripts/testdb.sh create "${ISSUE}src")"
BACKUP_ROOT="/tmp/backup-drill-${ISSUE}" … backup.sh "opencircuit_test_${ISSUE}src"
DST_DSN="…/opencircuit_test_${ISSUE}dst?sslmode=disable"
   "/tmp/backup-drill-${ISSUE}/opencircuit_test_${ISSUE}src/opencircuit_test_${ISSUE}src-latest.dump"
   "opencircuit_test_${ISSUE}dst"
scripts/testdb.sh drop "${ISSUE}src"
scripts/testdb.sh drop "${ISSUE}dst"
rm -rf "/tmp/backup-drill-${ISSUE}"
```

`grep -nE "0062|DROP DATABASE|rm -rf"` over the block finds no `0062` anywhere,
no bare `DROP DATABASE`, and the single `rm -rf` is the parameterised one.
Confirmed.
