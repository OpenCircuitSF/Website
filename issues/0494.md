## Description

In `cmd/opencircuit`'s route table, `GET /api/workshops/{slug}` is registered
**inside the `publicListStatsH` guard**, where it dereferences a different
handler:

	if publicWorkshopsH != nil {
		mux.Handle("GET /api/workshops", ...(publicWorkshopsH.List))
		// #0274: aggregate mailing-list counts for the home page's live CRT.
		// ... (this comment describes the NEXT block)
	}

	if publicListStatsH != nil {
		mux.Handle("GET /api/list-stats", ...(publicListStatsH.Stats))
		mux.Handle("GET /api/workshops/{slug}", ...(publicWorkshopsH.GetBySlug))
	}

Two defects, one cause — a block boundary in the wrong place:

1. **The workshop detail route is gated on a mailing-list handler.** A
   configuration with `publicListStatsH` nil and `publicWorkshopsH` non-nil
   silently drops `/api/workshops/{slug}` — no error, no log, a 404 on a route
   the binary is fully capable of serving.
2. **`#0274`'s comment is orphaned**, sitting at the tail of the workshops block
   while describing the list-stats block below it. A reader attributing it to
   the code it is attached to gets the wrong subsystem.

## Why it is benign today, and why that is not a reason to leave it

Both handlers are constructed together: nil together on the `STORAGE=json` dev
path, non-nil together under Postgres. So no current configuration reaches the
broken case.

That makes this latent rather than live — and latent on a **route-registration
seam nobody tests directly**. `CLAUDE.md` §8 records `#0325`, where a rename
silently moved two interfaces onto an unintended type with no compile error and
no diagnostic; this is the same class, one construct over. The cost of fixing it
now is two moved lines. The cost of finding it later is a 404 nobody can explain.

## How it was found

By the `#0393` cherry-pick, which placed the new CRT route immediately after
this block and read the surrounding structure to decide where the branch's
equivalent registration belonged. It **did not touch it** — correctly, since it
predates that work and was outside its scope.

## Acceptance criteria

1. **Move `GET /api/workshops/{slug}` into the `publicWorkshopsH` block**, next
   to `GET /api/workshops`, and move `#0274`'s comment to the block it
   describes.
2. **Check for siblings.** This is a long route table with several
   `if handler != nil` blocks; re-derive whether any other route is registered
   under a guard that does not match the handler it dereferences. **Say what you
   searched for**, so a clean result means the ground was covered rather than
   assumed.
3. **Decide whether the seam deserves a guard.** `#0490` and `#0492` pinned
   `mountAndServe`'s `outerMiddleware` hand-offs with AST assertions after the
   same "one argument position, no test" reasoning, and this is the adjacent
   shape: a registration whose guard and dereference disagree is mechanically
   detectable. Weigh it against `CLAUDE.md` §8's warning about guard sprawl and
   say where you land — **either answer is acceptable, an unexamined one is
   not**.
4. **Prove the routes still resolve.** The existing route-table tests are the
   oracle; confirm they exercise both paths, and if they do not, say so rather
   than assuming the move is safe because it compiles.
5. Do not change either handler's behaviour, and do not alter the construction
   site that makes both nil or both non-nil — that coupling is what keeps this
   benign, and changing it is a separate decision.
