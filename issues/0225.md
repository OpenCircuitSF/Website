## Description

`#0097` replaced four hand-written cascade lists with `cascadeClosure`, derived
from `pg_constraint`. Its second review verified the closure exactly against
Postgres's own `NOTICE: truncate cascades to table` output at all four call
sites — nothing missing, nothing spurious — and found one latent mismatch on the
consuming side.

**`cascadeClosure` emits `conrelid::regclass::text`**, which **quotes** names
needing quotes and **schema-qualifies** anything outside `search_path`.
**`diagnoseLockHolders` matches against `pg_class.relname`**, which is raw and
unqualified. The two do not agree for either shape.

Demonstrated with a genuine `ACCESS EXCLUSIVE` lock held: asking the diagnostic
with the closure's own strings for a non-`search_path` table
(`zz_rr_other.zz_rr_child`) and a quoted mixed-case name (`"zz rr Quoted"`)
returned **nothing**, while bare `relname`s named the holder correctly. The
converse is a false positive across schemas — a lock on `other_schema.audit_log`
would be reported as a lock on `audit_log`.

**Not reachable today**: every relation in this schema is in `public` and
lowercase-unquoted. And when it does miss, it now degrades to `#0097`'s honest
fallback rather than the false "not a lock wait at all" claim that caused the
bounce. So this is a correctness gap in a diagnostic, not a live defect.

**A smaller residual in the same fallback**, noted by the same review and
non-blocking: its two stated possibilities both presuppose a blocker existed,
while a non-lock-wait failure is a third case. No reader is actually misled,
because the underlying error prints on the line above.

## Acceptance criteria

- [x] A lock on a schema-qualified relation outside `search_path` is found and named — demonstrated with a real `ACCESS EXCLUSIVE` lock, as `#0097`'s review did
- [x] A lock on a quoted mixed-case relation is found and named

- [x] `ISSUE=0225 scripts/check.sh go ./internal/... ./cmd/...` passes with zero skips

## Implementation notes

**`internal/testdb/testdb.go`** — `cascadeClosure` is untouched. The fix is
entirely in `diagnoseLockHolders`'s matching query:

- Old: `JOIN pg_class c ON c.oid = l.relation ... WHERE ... c.relname =
  ANY($1)` — compares `cascadeClosure`'s `conrelid::regclass::text` output
  (quoted where needed, schema-qualified outside `search_path`) against raw
  `pg_class.relname` (never quoted, never qualified). Agrees only for a
  plain, lowercase, `public`-schema, unquoted name — true of every relation
  in this schema today, per the issue, which is why it wasn't reachable in
  production.
- New: `WHERE ... l.relation = ANY(SELECT to_regclass(t)::oid FROM
  unnest($1::text[]) AS t)`. `pg_locks.relation` is already an oid — no join
  needed to get one — and `to_regclass()` parses exactly the syntax
  `::regclass::text` produces (quoted, schema-qualified, or bare) under the
  same `search_path` rules, so pairing them compares relation identity as
  `oid = oid`, sidestepping quoting/qualification/search_path entirely (the
  review's own suggested direction). Unlike a plain `::regclass` cast,
  `to_regclass()` returns `NULL` instead of erroring for a name that no
  longer resolves (e.g. a relation dropped between the timeout and this
  diagnosis), so a stale `tables` entry degrades to "no match" rather than
  failing the whole diagnostic query.
- The display column changed from `c.relname` to `l.relation::regclass::text`
  — reconstructed canonically from the oid that was actually matched, rather
  than trusting `pg_class.relname` to already be a correct, unambiguous
  name. This is what makes AC 2/AC 3 ("found *and named*") hold, not just
  "found."
- `EntryTruncate`'s no-lock-holder fallback message gained a third clause:
  the original two ("the blocker released" / "is holding a lock this
  diagnostic did not check for") both presuppose a blocker existed; the
  message now also names the case where the original failure (printed on
  the line above, per the existing code) was not a lock wait at all.

**`internal/testdb/lock_diagnosis_test.go`** (new file) — package `testdb`
(same package, to reach the unexported `cascadeClosure`/`diagnoseLockHolders`
directly) gained its own `TestMain` (this package previously had none; only
`testdb_test.go`'s clock-independent `Unique` tests existed, which need no
database) and six tests, all gated on `TEST_DATABASE_URL` via
`lockDiagPoolOrSkip`:

- `TestCascadeClosure_MatchesPostgresNoticesAtRealCallSites` — a regression
  guard automating #0097's own by-hand check: for each of the four real
  `EntryTruncate` call sites' root tables, `cascadeClosure`'s output is
  compared against what a real `TRUNCATE ... CASCADE` (in a
  connection configured with an `OnNotice` handler, inside a transaction
  always rolled back) actually names in its own `NOTICE: truncate cascades
  to table "X"` messages. Written because `cascadeClosure` itself wasn't
  under test at all before this issue, and AC 5 asks for it explicitly.
- `TestDiagnoseLockHolders_DirectLockOnRealTable` /
  `_CascadeTargetLock` — automate #0097's review's two named reproductions
  (`issues/0097.md`'s Review notes): a direct `ACCESS EXCLUSIVE` lock on
  `audit_log`, and a lock on `sessions` (reached only via CASCADE from
  `internal/audit`'s literal `audit_log, users` roots — the exact scenario
  the pre-#0097 diagnostic missed and wrongly called "not a lock wait at
  all"). Both use plain, unquoted, `public`-schema names, so both already
  passed before this fix — they exist to prove #0225 didn't regress the
  case that was already working.
- `TestDiagnoseLockHolders_SchemaQualifiedOutsideSearchPath` /
  `_QuotedMixedCaseRelation` — the two positive reproductions AC 2/AC 3 ask
  for: create a real relation outside `search_path` (a fresh, uniquely-named
  schema) or with a mixed-case name needing quotes, confirm independently
  what `X::regclass::text` actually produces for it (rather than assuming
  the format), take a real `ACCESS EXCLUSIVE` lock on it from a second
  connection, and assert `diagnoseLockHolders` finds and names it. The
  quoted-name test also asserts the converse within itself: the unquoted,
  lowercase-folded spelling must *not* match (it names a different,
  nonexistent relation).
- `TestDiagnoseLockHolders_SameNameDifferentSchema_NoFalsePositive` — AC 4's
  converse case as its own test: two schemas, each with a table named
  `shared_name`; lock only one; assert asking about the *other* one's
  qualified name returns nothing (not the locked one's report under a
  shared bare name), then sanity-checks that asking about the actually-locked
  one does find it, so the negative result is a real converse case and not
  "the query never works here."

All scratch schemas/tables are named via this package's own `Unique()` and
removed via `t.Cleanup`; the real-table tests only ever hold their lock
inside a transaction that is rolled back, never committed.

## Notes

Reported by `#0097`'s second phase-3 review under `CLAUDE.md` §9.

Comparing on `oid` is almost certainly the right answer: it sidesteps quoting,
schema qualification, and `search_path` entirely, and both sides already have
one available — `cascadeClosure` walks `pg_constraint.conrelid`, and
`pg_locks.relation` **is** an oid.

Worth keeping from that review, because it justifies the design this builds on:
the every-FK decision in `cascadeClosure` was verified by counterfactual.
Filtering to `confdeltype='c'` returns, for `internal/audit`, exactly
`audit_log, users` — byte-for-byte the broken hand-written list that caused the
original bounce. Every FK pointing at `users` or `workshops` here is NO ACTION,
and Postgres cascades all of them regardless.

The walk itself was proved terminating on a constructed two-node cycle and a
self-referencing FK; neither exists in the real schema.

**One defect found that this issue does not close, reported to the
orchestrator for filing.** `diagnoseLockHolders` matches `pg_locks`, which is
**cluster-wide**, without filtering on `l.database`. Per-agent test databases
are `CREATE DATABASE ... TEMPLATE`-cloned, so they share relation oids
verbatim — measured here: `audit_log` is oid `12933693` in
`opencircuit_test_template`, `opencircuit_test_0217revmut` and
`opencircuit_test_0217revset` alike. Demonstrated with a real lock: holding
`ACCESS EXCLUSIVE` on `audit_log` in one database and running the diagnostic's
query from another reports it as a culprit —

```
59703|audit_log|active|opencircuit_test_0217revmut     -- new (#0225) query, asked from ..._0217revset
59703|audit_log|active|opencircuit_test_0217revmut     -- old (pre-#0225) query, same question
```

This is **pre-existing, not a `#0225` regression** — the old `pg_class` join
had the identical collision — and it is out of this issue's scope, which is
the text-vs-oid dialect. It is worth its own issue because the false positive
is reachable *today*, in exactly the concurrent-agent situation the diagnostic
exists for. One predicate fixes it:
`AND l.database IN (0, (SELECT oid FROM pg_database WHERE datname =
current_database()))` (0 covers shared catalogs).

**What else was looked for and not found:** a test leaking a scratch schema or
`public` table into the shared database (all use `Unique()` names and
`t.Cleanup`, and no test anywhere in `internal/` enumerates `pg_class` or
`information_schema.tables`, so a stray one could not break a parity suite);
a `TRUNCATE` that could commit (it is inside a transaction with a deferred
unconditional `Rollback`); and drift between the new doc comments and the
query they describe (none — the comment's account of `to_regclass`,
`NULL = ANY`, and the reconstructed display column all match the SQL).
