## Description

**The user does not want the green focus outline on any link, anywhere on the
site** (2026-09-12). This widens `#0517`, which removes it from page titles and
other text the app moves focus to. This issue covers every link and link-like
navigation control. The two ship together.

Seen in Safari on `/account`: a thick green box in the Account/Admin header. That
particular box is `#0517`'s heading case, but the same 2px `--accent` outline
appears on any link that receives keyboard focus.

## Where the outline comes from

`web/src/app.css`:

```css
:where(a, button, summary, [tabindex]):focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
  border-radius: 2px;
}
```

`--accent` is the brand green. Check for any other rule that outlines links or
navigation controls in green — component `<style>` blocks included — and remove
it the same way.

## Scope

**In scope — no green outline, ever:**

- every `<a>` element: header navigation, footer links, links inside page
  content, the "Skip to content" link, and links rendered from newsletter and
  workshop bodies;
- **link-like navigation controls**, even though they are `<button>`s: the
  Account/Admin header tabs (`.nav-tab`) and the admin section tabs
  (`.subtabs`).

**Out of scope unless the user asks:** form fields (`input`, `select`,
`textarea`), ordinary action buttons (Sign out, Revoke, Save), and the **active
route indicator** — the green text and underline marking the current page in
the public header (`.primary-nav a[aria-current='page']`) and the active
Account/Admin tab (`.nav-tab.active`). None of those is a focus outline.

## Keep focus visible, without the green outline

Keyboard users still need to see which link is focused (WCAG 2.4.7). So replace
the outline on links with a **non-green, non-outline** indicator: for example,
an underline in the text colour. This satisfies the requirement — no green
outline — without making keyboard navigation invisible. Record the choice in a
comment at the rule so nobody "restores" the green ring as an accessibility fix.

If the user later wants no focus indicator at all on links, removing the
replacement is a one-line change; say so in the comment.

## Acceptance criteria

1. **No link shows a green outline**, in any browser, either theme, after a mouse
   click, after keyboard focus (Tab), or after back and forward.
2. **The Account/Admin header tabs and the admin section tabs show no green
   outline** in the same conditions.
3. A keyboard-focused link or navigation tab is still visibly distinguishable
   through a non-green, non-outline indicator. Verify by tabbing through the
   public header, the footer, the Account/Admin tabs, and the admin section tabs.
4. Form fields and ordinary action buttons keep their current focus ring.
5. The active route indicators are unchanged.
6. **A test pins this**: it fails if any stylesheet rule would give an `<a>`, a
   `.nav-tab`, or a `.subtabs` control a green or `--accent` outline, and it
   passes for form fields. Prove it fails against the current `app.css`.
7. **Checked in real browsers** — Safari and one Chromium-based browser, both
   themes — including the exact Account/Admin case the user screenshotted.
   jsdom does not paint outlines; say which claims rest on a browser.
8. `scripts/check.sh web` passes.

> 🟢 Resolved 2026-09-12 — no link, `.nav-tab`, or `.subtab` shows a green (or any) focus outline in real Chromium or Safari, in either theme; each shows a non-green underline on keyboard focus instead, while buttons and form fields keep their accent ring.

## Review notes

Reviewed as one batch with #0517 (Opus, 2026-09-12). Verdict: approve. The
full evidence is in #0517's `## Review notes`. This section covers what is
specific to this issue.

- **Selectors hit real elements.** The admin section tabs are `button.subtab`
  (inside `nav.subtabs`), and the header tabs are `button.nav-tab`, in both
  `Admin.svelte` and `Account.svelte`. The implementer was right to target
  `.subtab` rather than the container. Both are proved live in the browser,
  not just by grep.
- **Real Chromium 151, both themes, against the real built SPA with
  `STORAGE=json` and the mock admin.** A Tab sweep covered:
  - the skip link, header nav links, and in-page and footer links on `/`
    (15 links);
  - on `/admin`: both nav tabs, all 12 subtabs, and the 6 footer links.

  Every one had `outline-style: none` and a `text-decoration-line: underline`,
  with the underline in the element's own text colour. A mouse click on a
  subtab also showed no outline.
- **Positive controls.** Ordinary buttons kept `solid 2px` in the theme's
  accent colour: the theme toggle, Subscribe, Sign out, and Retry. The email
  input kept its accent `box-shadow`. `.nav-tab.active` and `.subtab.active`
  are unchanged.
- **Safari.** The reviewer's own Safari run covered the Account/Admin tab
  switch, back and forward, and a nav-link click, all with no outline. Safari
  keyboard focus on links (Option+Tab) rests on the implementer's run.
- **`!important`** is limited to `text-decoration-line` inside the link rule.
  It is needed because the Header and Footer components reset
  `text-decoration`. Chromium confirmed the underline wins.
- The one defect found (`d170f68`, the browser's own focus ring on non-h1
  `tabindex="-1"` targets) belongs to #0517, not to links.
- `scripts/check.sh web` passed after the fix: 4145 tests.

## Work log

Implemented together with #0517 (same CSS problem, one batch) — see that
issue's `## Work log` for the full change list. Summary of what this issue
specifically drove:

- The shared `:where(a, button, summary, [tabindex]):focus-visible` rule in
  `web/src/app.css` no longer matches `<a>`, `.nav-tab`, or `.subtab` —
  `button` is now `button:not(.nav-tab):not(.subtab)` (needed because
  `.nav-tab`/`.subtab` are real `<button>`s and would otherwise still match
  the plain `button` clause even after being excluded from the new rule
  below).
- A new rule gives links and the link-like `.nav-tab`/`.subtab` controls a
  non-green, non-outline indicator instead:
  `:where(a, .nav-tab, .subtab):focus-visible { outline: none;
  text-decoration-line: underline !important; text-decoration-thickness:
  2px; text-underline-offset: 3px; }`. `!important` is deliberate (the only
  use in this file) — several components set `a { text-decoration: none }`
  at higher specificity than a bare `:where(...)` rule, so without it this
  rule would silently lose the cascade and render no indicator at all.
- Both `web/src/lib/focusOutline.guard.test.ts` (the new automated test,
  #0517's criterion 6 and this issue's criterion 6) and the real-browser
  verification cover `<a>`/`.nav-tab`/`.subtab` explicitly — see #0517's
  `## Verification` for the full transcript and methodology; not
  duplicated here.
- Note on criterion 6's exact wording: it names `.subtabs`, which is the
  *container* class (`<nav class="subtabs">` in `Admin.svelte`); the
  individual clickable admin-section-tab elements carry class `.subtab`
  (singular). The fix and the test target `.subtab`, the actual focusable
  control, not its container.
