# 0535 — No green outline on any link

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web / accessibility |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-12 |

## Description

**The user does not want the green focus outline on any link, anywhere on the
site** (2026-09-12). This widens `#0517`, which removes it from page titles and
other text the app moves focus to. This issue covers every link and link-like
navigation control. The two ship together.

Seen in Safari on `/account`: a thick green box in the Account/Admin header. That
particular box is `#0517`'s heading case, but the same 2px `--accent` outline
appears on any link that receives keyboard focus.

## Where the outline comes from

`web/src/app.css`:

```css
:where(a, button, summary, [tabindex]):focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
  border-radius: 2px;
}
```

`--accent` is the brand green. Check for any other rule that outlines links or
navigation controls in green — component `<style>` blocks included — and remove
it the same way.

## Scope

**In scope — no green outline, ever:**

- every `<a>` element: header navigation, footer links, links inside page
  content, the "Skip to content" link, and links rendered from newsletter and
  workshop bodies;
- **link-like navigation controls**, even though they are `<button>`s: the
  Account/Admin header tabs (`.nav-tab`) and the admin section tabs
  (`.subtabs`).

**Out of scope unless the user asks:** form fields (`input`, `select`,
`textarea`), ordinary action buttons (Sign out, Revoke, Save), and the **active
route indicator** — the green text and underline marking the current page in
the public header (`.primary-nav a[aria-current='page']`) and the active
Account/Admin tab (`.nav-tab.active`). None of those is a focus outline.

## Keep focus visible, without the green outline

Keyboard users still need to see which link is focused (WCAG 2.4.7). So replace
the outline on links with a **non-green, non-outline** indicator: for example,
an underline in the text colour. This satisfies the requirement — no green
outline — without making keyboard navigation invisible. Record the choice in a
comment at the rule so nobody "restores" the green ring as an accessibility fix.

If the user later wants no focus indicator at all on links, removing the
replacement is a one-line change; say so in the comment.

## Acceptance criteria

1. **No link shows a green outline**, in any browser, either theme, after a mouse
   click, after keyboard focus (Tab), or after back and forward.
2. **The Account/Admin header tabs and the admin section tabs show no green
   outline** in the same conditions.
3. A keyboard-focused link or navigation tab is still visibly distinguishable
   through a non-green, non-outline indicator. Verify by tabbing through the
   public header, the footer, the Account/Admin tabs, and the admin section tabs.
4. Form fields and ordinary action buttons keep their current focus ring.
5. The active route indicators are unchanged.
6. **A test pins this**: it fails if any stylesheet rule would give an `<a>`, a
   `.nav-tab`, or a `.subtabs` control a green or `--accent` outline, and it
   passes for form fields. Prove it fails against the current `app.css`.
7. **Checked in real browsers** — Safari and one Chromium-based browser, both
   themes — including the exact Account/Admin case the user screenshotted.
   jsdom does not paint outlines; say which claims rest on a browser.
8. `scripts/check.sh web` passes.
