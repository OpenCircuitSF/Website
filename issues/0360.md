## Description

`opencircuit_test` stamps `schema_migrations.version = 25, dirty = f`, while its
`subscribers` table has **24 columns** and is missing `soft_bounce_streak`,
`last_bounce_at`, and `last_delivery_at`. `opencircuit` — the user's dev
database, at version 24 — has the same gap.

**Confirmed independently by the orchestrator**: 24 columns, version 25, not
dirty.

**The version stamp does not detect this.** That is the whole problem: an agent
has no cheap signal that the database it is about to use disagrees with
`migrations/`.

### Why it matters, and what it already cost

Any run that falls back to the shared database — a bare `go test` with §5's
documented default `TEST_DATABASE_URL`, rather than
`ISSUE=NNNN scripts/check.sh` — gets `column … does not exist` errors that read
**exactly like flakes**. A read-only
`select soft_bounce_streak from subscribers limit 1` reproduces it verbatim and
deterministically; the same query against the template succeeds.

This already cost `#0356`'s fourth implementation pass a misattribution: it
recorded the failure as "concurrent schema drift from another session", which
was wrong in mechanism though right that it was not its own defect. `#0356`'s
third review ran it down: no migration changed today (newest `migrations/`
commit is `d9f877a`, 2026-08-27), and the per-agent template is **healthy** —
v25, clean, 27 `subscribers` columns, `soft_bounce_streak` present.

### A second, related half

`scripts/testdb.sh` now reports that the **template's content digest disagrees
with `migrations/`**, though both are at 25 — so every agent is silently
falling back to direct provisioning instead of the ~0.2s clone. `#0123` amended
`migrations/000025` in place on 2026-08-27, which fits the timing.

Independently reproduces [#0339](0339.md)'s review measurement. The template is
**legitimately ahead** of this checkout, carrying `000028_create_crt_commands`
from a branch absent from `main`. Rebuilding it would destroy a healthy template
out from under the worktree that owns it, and the mismatch would return on the
next worktree migration.

### Why `opencircuit` is at 28 and `opencircuit_test` at 27

The user's dev database has had that same stranded `000028` applied to it; the
shared test database has not. So the two shared databases now disagree with each
other **and** with `main`'s `migrations/`, and neither is wrong in a simple
sense. Any detection added here has to give a useful answer in that state rather
than merely flag it — see step 3 of the plan, which classifies `opencircuit` as
*ahead by one, schema clean* and `opencircuit_test` as *in agreement*, with
neither reported as a defect.

### The failure mode is invisible to *every* mechanism now in the tree

Measured on a private database, not inferred. `migrations/*.up.sql` was migrated
into a scratch database, then the three columns were dropped to reproduce a
migration recorded as applied whose DDL never took effect:

| Signal | Reads |
|---|---|
| `schema_migrations` | `27 \| f` — unchanged, reports healthy |
| `migrate up` | exits 0, applies nothing (per this issue's own 2026-09-03 work-log entry) |
| `testdb.sh`'s version + digest check | unaffected — both describe `migrations/` on disk, not the live catalog |

**No stamp, comment, or version number can see this**, because every one of them
records *provenance* while the defect is in the *realised schema*. Only a census
of the live catalog against the DDL the migrations claim to have applied detects
it. That is what step 1 below builds.

### `COMMENT ON DATABASE` does not survive a template clone

Measured, because a stamp-based design would have rested on it:

```
CREATE DATABASE a;  COMMENT ON DATABASE a IS 'PROBE';
CREATE DATABASE b TEMPLATE a;   -- b's comment reads (NONE)
```

`pg_shdescription` is a shared catalog keyed by database oid, so a clone starts
uncommented. This is also why `opencircuit` and `opencircuit_test` carry no
digest comment today. It rules out "stamp every database and compare stamps" as
a cheap route, independently of the point above that a stamp cannot see the
defect anyway.

### The census was prototyped and is sound on this corpus

A prototype extracting expected relations and columns from `migrations/*.up.sql`
— `CREATE TABLE` bodies **and** `ALTER TABLE ... ADD COLUMN` — was run against
all three real databases and against the deliberately drifted private one:

| Database | Expected: 20 tables, 187 columns | Result |
|---|---|---|
| `opencircuit` | ≤ 27 | clean — **zero** false positives |
| `opencircuit_test` | ≤ 27 | clean |
| `opencircuit_test_template` | ≤ 27 | clean |
| private, three columns dropped | ≤ 27 | **names exactly `subscribers.soft_bounce_streak`, `subscribers.last_bounce_at`, `subscribers.last_delivery_at`, and attributes all three to `migrations/000010_create_subscribers.up.sql`** |

Three facts from that prototyping that the implementation depends on:

1. **The three columns come from a `CREATE TABLE` body, not an `ADD COLUMN`.**
   They are declared in `migrations/000010_create_subscribers.up.sql`. A first
   prototype that scanned only `ADD COLUMN` reported the drifted database clean
   — it missed the exact defect this issue is about. Parsing `CREATE TABLE`
   bodies is not optional.
2. **Comment stripping is load-bearing, measured.** Without it the same scan
   reports 10 false positives on a healthy `opencircuit_test`, from prose such
   as a comment reading `CREATE TABLE that owns the table` and another quoting
   an `ADD COLUMN` clause it is explaining. With stripping: zero.
3. **No `.up.sql` in this tree contains `DROP COLUMN`, `DROP TABLE`, or
   `RENAME`** (verified across all 27). A purely cumulative census is therefore
   sound — but only while that stays true, so the implementation must assert it
   rather than assume it (step 1c).

### Incidental observation, not this issue's business

A database named `opencircuit_live` exists in the local cluster. It is outside
`testdb.sh`'s `opencircuit_test_` pool and outside `db-reset.sh`'s two managed
names, so nothing here touches it. Noted only so the next agent taking a
`pg_database` listing is not surprised by it.

## Plan

The whole plan is **read-only with respect to every shared database**. Nothing
in it requires rebuilding the shared template, resetting `opencircuit`, or any
other step the user would have to authorise.

**It also touches no shell script.** `scripts/testdb.sh` — currently owned by
the concurrent `#0481`/`#0482` work — and `scripts/db-reset.sh` are both left
alone, deliberately and not merely to avoid the conflict (see step 5).

### 1. Add the schema census to `internal/testdb`

Create `internal/testdb/schema_check.go`. Keep the repo-root resolution and
every `..`-shaped path literal **in this non-test file**; see step 4 for why
that placement is load-bearing.

a. `migrationsDir()` — resolve `<repo>/migrations` from this file's own path via
   `runtime.Caller(0)`, the idiom `internal/subscribers`' guard already uses. If
   the directory does not exist, that is a hard error, not a skip: in this
   repository it can only mean the resolution is broken, and a silent skip is
   the fail-open shape `#0476` closed in this same file.

b. `expectedObjects(dir string, maxVersion int)` — for each `NNNNNN_*.up.sql`
   whose number is ≤ `maxVersion`, in ascending order:
   - strip `--` line comments first (Finding 2 above: 10 false positives
     otherwise);
   - for each `CREATE TABLE [IF NOT EXISTS] <name> (` , record the table, then
     balance parentheses to delimit its body, split that body on **depth-zero**
     commas, and record the first identifier of each item as a column — skipping
     items whose first word is `PRIMARY`, `UNIQUE`, `CHECK`, `FOREIGN`,
     `CONSTRAINT`, `EXCLUDE`, or `LIKE`. Depth-aware splitting is required:
     `NUMERIC(10,2)` and `CHECK (... , ...)` both contain commas;
   - for each `ALTER TABLE [ONLY] <name>` statement (split the file on `;`),
     record every `ADD COLUMN [IF NOT EXISTS] <col>` within it against that
     table — the multi-column form in `migrations/000023_create_subscriber_imports.up.sql` shares one
     `ALTER TABLE` across several `ADD COLUMN` clauses, so the table name must
     carry forward within the statement;
   - fold identifiers to lower case (Postgres folds unquoted identifiers, the
     same hazard `#0208` hit in `name_for`);
   - record the owning migration filename alongside each object — that filename
     is the diagnosis, and the prototype's output above shows why.

c. In the same pass, if any scanned file contains `DROP COLUMN`, `DROP TABLE`,
   or `RENAME` outside a comment, return an error saying the cumulative census
   is no longer sound and this function needs revisiting. Finding 3 measured
   that none does today; this is what stops that premise going stale silently,
   and it fails closed rather than starting to emit false positives.

d. `CheckSchema(ctx, conn, dir)` — the classifier. Read
   `schema_migrations.version, dirty` and compute `diskVersion` as the highest
   number in `dir`. Then:

   | Condition | Verdict | Behaviour |
   |---|---|---|
   | `dirty` is true | broken | **fail closed** |
   | `dbVersion > diskVersion` | **ahead** | warn on stderr, continue to the census |
   | `dbVersion < diskVersion` | **behind** | **fail closed** |
   | equal | in agreement | continue to the census |

   Then, **in all three surviving cases**, run the census over migrations
   ≤ `min(dbVersion, diskVersion)` and compare against
   `information_schema.tables` / `information_schema.columns` for schema
   `public`, in two queries. Any missing object is a **fail closed**.

   Running the census in the *ahead* case too is deliberate and costs nothing: a
   database ahead of this tree still claims every migration this tree has, so
   every object from those files must exist in it. It is the only way phantom
   DDL is caught on `opencircuit`-shaped databases.

e. **Message content** (criterion 4). On any failure, name: the database, the
   recorded version and the disk version, the verdict word (`behind`,
   `dirty`, or `phantom DDL`), every missing object as `table.column` with the
   migration file that declares it, and the remedy — **drop and recreate**
   (`scripts/testdb.sh create <id>`, or `scripts/db-reset.sh --force <db>` for a
   shared one). The remedy line must state that `migrate up` exits 0 having
   fixed nothing, per this issue's 2026-09-03 work-log entry; that is the trap
   the message exists to close, and omitting it sends the next agent down the
   same path.

   The *ahead* warning is a different message and must not read as a defect: it
   says the database was built from a `migrations/` newer than this checkout —
   the state `#0315`'s fallback exists for — reports both versions, confirms the
   census over the shared range came back clean, and stops there.

### 2. Call it from `Lock()`

In `internal/testdb/testdb.go`, call `CheckSchema` from `Lock` on the connection
it already opens, after the advisory lock is acquired, and `log.Fatalf` on
error — the escalation path `Lock` already uses, and the reasoning transfers
exactly. A schema mismatch *is* noticed downstream, but only as an unattributable
`column ... does not exist` that reads like a flake; that is a worse fail-open
than the one `#0476` closed, not a lesser one.

`Lock` is the right seam because it is the **only** one on every path. The
scenario the Description describes — a bare `go test` with §5's documented
default `TEST_DATABASE_URL` — never invokes `scripts/testdb.sh` at all. Putting
the check in `Lock` also needs no call-site changes across the DB-backed
packages, and so cannot be defeated by a `TestMain` that forgets to call it —
the argument `Lock`'s own doc comment already makes for its signature.

Keep the early return when `TEST_DATABASE_URL` is unset, unchanged. Extend
`Lock`'s doc comment and the package doc comment to state the new
responsibility.

**Do not add an environment-variable escape hatch.** Every verdict that fails
closed is a database genuinely wrong to test against, and a bypass lever is the
fail-open this is closing.

### 4. Tests, and the trap to avoid while writing them

Add `internal/testdb/schema_check_test.go`:

- parser cases over fixture `.up.sql` files written into `t.TempDir()`: a
  `CREATE TABLE` body with constraint clauses and a comma inside a type
  modifier; a multi-column `ALTER TABLE ... ADD COLUMN` block; a comment
  containing the literal words of a `CREATE TABLE` clause, asserting it yields
  no object — Finding 2's exact shape, pinned as a string literal in the test
  body rather than described in a comment (§8, `#0384`);
- `maxVersion` truncation: an object declared in a fixture above the cap is not
  expected;
- the step-1c refusal: a fixture containing `DROP COLUMN` produces the error;
- classifier cases for `behind`, `ahead`, `dirty`, and equal;
- **the `#0360` reproduction**, DB-backed, against a **private** database
  (§8b — never the shared one): migrate a private database up from a fixture
  directory, drop a column, and assert `CheckSchema` fails naming that column
  and the fixture file that declares it. Create the database with a name derived
  from `Unique()`, drop it in a `t.Cleanup`, and target no literal or seeded id.

**Keep every `..` path literal and every `runtime.Caller`/`os.Getwd` call out of
these `_test.go` files** — use `t.TempDir()` fixtures and pass directories in as
parameters. `internal/db`'s `TestClaudeMDRepoWideGuardPackageSetParity` scans
only `_test.go` files, and `internal/testdb` has neither idiom in its tests
today. Introducing one there would make the parity guard demand a new row in
`CLAUDE.md` §5's repo-wide-guard table; adding such a row **without** the idiom
present would fail the guard from the other direction. Neither is wanted: the
reach belongs in `schema_check.go`, which that guard does not scan, and §5's
table should stay as it is.

### 5. Criterion 3 — judgement: redirect, do not extend

**Do not extend `scripts/testdb.sh`'s digest check to `opencircuit_test`.** The
substance of criterion 3 is met by steps 1–2; its literal instruction names the
wrong file, for three measured reasons:

1. **`testdb.sh` is not on the failure's path.** The Description's scenario is a
   bare `go test` against the default `TEST_DATABASE_URL`, which never runs the
   script. A check there cannot fire in the case the issue was filed about.
2. **`testdb.sh` already guarantees what it hands back.** `create` clones only
   when the template matches `migrations/` and otherwise provisions from
   `migrations/` directly, so the database it returns is correct by
   construction. A digest check on `opencircuit_test` inside that script would
   only ever describe a database the script neither built nor is about to use.
3. **A digest cannot see this defect at all** — Finding "invisible to every
   mechanism" above. Extending a provenance check would add code and detect
   nothing new.

Leaving both scripts untouched also removes the `#0481`/`#0482` handoff from
this issue's critical path entirely, rather than merely sequencing around it.

### 6. Criterion 2 — judgement: void as written

Do not rebuild the shared template, and do not attempt the timing measurement.

1. **Its premise is dead.** It attributes the mismatch to `#0123`'s in-place
   amendment of `migrations/000025`; that database state no longer exists.
   Today's mismatch is `#0339`'s measured *ahead* condition, re-derived above.
2. **Acting on it would cause harm.** A rebuild destroys a healthy template the
   stranded worktree owns, and the mismatch returns at that worktree's next
   migration. `#0339`'s review reached the same conclusion.
3. **The refinement it asks for already exists.** `warn_template_mismatch` in
   `scripts/testdb.sh` already branches three ways — template ahead, working
   tree ahead, and equal-version-with-differing-digest — and names which. There
   is nothing left to build for the template side; step 1d adds the same
   three-way classification on the side that lacked it, the live database.

Record criterion 2 as void with this reasoning rather than as met.
