## Description

Adding one column to `subscribers` requires four hand edits:

| Site | Kind | Failure if missed |
|---|---|---|
| `subscriberColumns` | list | — |
| `qualifiedSubscriberColumns` (`Store.List`'s JOIN-safe duplicate) | list | **runtime 500** |
| `scanSubscriber`'s `Scan` order | positional | runtime |
| the struct | fields | compile |

Three are positional, so a wrong-order addition fails at **runtime**, not at
compile time. And `qualifiedSubscriberColumns` is **the one with no by-name
test**.

**This already fired.** `#0312`'s implementer added `invite_resent_at`, missed
`qualifiedSubscriberColumns`, and 500'd the admin subscribers list. It was caught
by the existing suite and fixed, and the implementer disclosed it — but the
minimum fix leaves the duplication in place for the next column.

## Acceptance criteria

1. `qualifiedSubscriberColumns` is **derived** from `subscriberColumns` (by
   prefixing) **or** the two parsed identifier sequences are pinned against each
   other, so adding a column to one and not the other fails.
2. Prove it discriminates: add a column to `subscriberColumns` alone and confirm
   the check fails, naming what diverged. **A check that cannot fail pins
   nothing** — `#0354`, `#0358` and `#0363` each shipped exactly that this
   phase, and `#0364` exists because a passing assertion can pass for the wrong
   reason.
3. If you choose the pinning route rather than derivation, the oracle must not
   be **a copy of the answer stored next to the question** (§8). Derive both
   sequences from the source, do not transcribe either into a fixture.
4. Consider whether `scanSubscriber`'s positional order can be pinned the same
   way, and say explicitly whether you did or why not — a positional list that
   fails at runtime is the worse of the two hazards, even though it is not the
   one that fired.
5. **Do not over-build.** If derivation closes it in a few lines, stop there;
   `#0330`, `#0347` and `#0356` all ended with "record the limit rather than add
   another mechanism", and §8's `#0258` case is six passes of the opposite. If
   the sound fix needs more machinery than the defect costs, say so and stop.
6. `gofmt` stability; the floor harness stays **42 total / 12 non-exempt**
   (`#0323`); per §5 name the specific tests that ran.

## Fix

**Route taken: derive, per criterion 1's first branch.**
`qualifiedSubscriberColumns` changed from a separately hand-maintained
`const` to a `var` computed by a new `deriveQualifiedColumns(cols, table
string) string` (`internal/subscribers/store.go`), which prefixes each
comma-separated column reference in `subscriberColumns` with
`"<table>."` — including the single identifier inside the one wrapped call
`host(signup_ip)` → `host(subscribers.signup_ip)`. There is now only one
column list to remember to edit when a column is added; the specific defect
class that fired in #0312 (an edit to one list, forgotten in the other)
is closed structurally rather than by convention.

**Criterion 2 — the discrimination proof.** Under true derivation, "add a
column to `subscriberColumns` alone" can no longer happen (there is only
one list to edit), so the regression this issue is actually about is
someone *reintroducing* the old two-list shape. Two tests close that:

- `TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns` pins
  `qualifiedSubscriberColumns == deriveQualifiedColumns(subscriberColumns,
  "subscribers")` — literally #0312's mistake, reproduced and caught (see
  `## Verification`).
- `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip` independently
  catches the same omission (a column-count mismatch errors `Store.List`
  outright) *and* catches something the list-identity test cannot: a
  same-typed positional reorder in `scanSubscriber`'s `Scan(...)` call that
  leaves both column lists untouched and the code compiling clean. See
  criterion 4 below.

**Criterion 3.** `TestDeriveQualifiedColumns` (the derivation function's own
unit test) uses a small literal input/output pair constructed in the test
itself — not `subscriberColumns`/`qualifiedSubscriberColumns` — so its
oracle is not a copy of the answer sitting next to the question (§8). The
round-trip test's oracle is *inserted, distinct-per-type sentinel values*
read back from Postgres — also not a transcription of either column list.

**Criterion 4 — scanSubscriber's positional order, considered explicitly.**
Did **not** build a general AST-based pin (comparing `Scan(...)`'s argument
identifiers against `subscriberColumns`' column identifiers in order). This
repo already has one general-purpose AST guard for a comparable problem
(`internal/db/issue_citation_guard_test.go`, ~1000 lines, built for a
genuinely corpus-wide citation-checking problem) — building an equivalent
parser here would be disproportionate machinery for a defect that, unlike
`qualifiedSubscriberColumns`, **has not actually fired** (this issue's own
description). Per criterion 5: stopped short of that.

Instead, added `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip`: it
inserts one `subscribers` row (plus one `subscriber_imports` row for the
`import_id` FK) with every column set to a value distinct from every other
column of the same Go type — eleven distinct timestamps across the
`*time.Time`/`time.Time` fields, a dozen distinct strings across the
`*string`/`string` fields — then reads it back through **both**
`scanSubscriber` call sites that matter: `GetByID` (`subscriberColumns`,
unqualified) and `List` (`qualifiedSubscriberColumns`, qualified — the
JOIN-safe path #0312 actually broke). A same-typed reorder in
`scanSubscriber`'s `Scan` order swaps values into the wrong struct fields
and this test's per-field assertions catch it; a pure column-count check
would not have. Proven by mutation (`## Verification`): the round-trip test
catches a `ConfirmSentAt`/`ConfirmExpiresAt` swap that
`TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns` correctly
does **not** flag (that swap touches neither column list), demonstrating
the two tests catch genuinely different mistakes and neither subsumes the
other.

**Criterion 5 — stop condition.** Reached it for the AST-guard question
(criterion 4, above): the sound general fix costs roughly 1000 lines of
comparable machinery already in this tree, for a defect class that has not
fired; recorded the limit and did not build it. The derivation itself
(`deriveQualifiedColumns`, ~15 lines) is proportionate to the defect that
*did* fire (#0312) and was built.

**Criterion 6.** `gofmt -l` clean on every file touched (see
`## Verification`); the guards harness floor (42 total / 12 non-exempt,
#0323) is untouched by this change — nothing here adds or removes a guard
script.

### (a) Does the derivation actually close the `#0312` failure? — yes, proved end to end

Criterion 2 asks for "add a column to `subscriberColumns` alone and confirm the
check fails". Under true derivation that framing inverts: there is no second
list to forget, so the right proof is that the column **propagates**. I ran
exactly that, in an isolated `git archive HEAD` export against my own scratch
database:

1. `ALTER TABLE subscribers ADD COLUMN zz_probe text` (my scratch DB only).
2. Added `zz_probe` to `subscriberColumns` — **the only list** — plus the
   compile-enforced sites (`Subscriber` struct field, `scanSubscriber`'s `Scan`
   argument).
3. **Made no edit whatsoever to `qualifiedSubscriberColumns`** — it cannot be
   edited; it is `deriveQualifiedColumns(subscriberColumns, "subscribers")`.

```
BUILD OK
--- PASS: TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns
--- PASS: TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip
```

`Store.List` — the JOIN-safe path that `#0312` actually 500'd — worked with a
29th column and zero second edits. This is the precise edit that broke
production behaviour in `#0312`, and it is now structurally incapable of
diverging. Criterion 1's first branch is satisfied in substance, not just in
form.

I also confirmed the derived string is **column-for-column identical to the old
literal it replaced** — 28 references, same order, with `host(signup_ip)`
correctly becoming `host(subscribers.signup_ip)`. That fell out of mutation A's
failure message, which printed both sequences side by side. So this is a pure
refactor at the SQL level, not a behaviour change smuggled in as one.

Then the regression direction, which is what a derived value still needs
pinning against — reintroducing the old two-list shape:

| Mutation | Test | Observed |
|---|---|---|
| `qualifiedSubscriberColumns` replaced by a hardcoded 27-column `const` omitting `invite_resent_at` (i.e. `#0312`'s mistake, literally) | `..._IsDerivedFromSubscriberColumns` | FAIL — `qualifiedSubscriberColumns has drifted…`, and **names `subscribers.invite_resent_at` as what is missing** |
| same | `..._ScanSubscriberColumnOrderRoundTrip` | FAIL — `number of field descriptions must equal number of destinations, got 27 and 28` |

Two independent oracles, both firing, reproducing `#0312`'s exact runtime
failure. Neither is a copy of the answer stored next to the question (§8):
`TestDeriveQualifiedColumns`'s oracle is a small literal pair built in the test
(`"id, host(signup_ip), foo_bar"`), and the round-trip's oracle is *values read
back out of Postgres*. Criterion 3 satisfied.

### (b) Does the round-trip test discriminate? — yes, re-run myself

I re-ran the implementer's same-typed-reorder mutation independently: swapped
`&sub.ConfirmSentAt` and `&sub.ConfirmExpiresAt` in `scanSubscriber`'s `Scan`
call — both `*time.Time`, so the code compiles clean and neither column list is
touched.

```
compiles clean (same-typed swap, no compile error)

--- PASS: TestDeriveQualifiedColumns
--- PASS: TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns
--- FAIL: TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip
    GetByID (subscriberColumns):  ConfirmSentAt    = …19:00, want …01:00
    GetByID (subscriberColumns):  ConfirmExpiresAt = …18:00, want …02:00
    List (qualifiedSubscriberColumns): ConfirmSentAt    = …19:00, want …01:00
    List (qualifiedSubscriberColumns): ConfirmExpiresAt = …18:00, want …02:00
```

This is the finding that matters most. The list-identity test **correctly
passes** — the mutation touches neither list — while the round-trip test fails
on *both* scan call sites. The two tests catch genuinely different mistakes and
neither subsumes the other, exactly as claimed. This is not `#0354`/`#0358`/
`#0363`'s "a check that cannot fail": it fails, for the right reason, naming
the right fields.

I audited the sentinel data for the distinctness the whole design rests on, and
it holds: eleven timestamps at `base+1h … base+11h` across the eleven time
fields, and every `*string` field given a distinct value
(`zz-roundtrip-confirm-token`, `zz-roundtrip-manage-token`, `203.0.113.7`,
`zz-roundtrip-user-agent`, four distinct UTM values, `admin`,
`zz-roundtrip-source-detail`, `admin_attested`). No two same-typed fields share
a value, so **any** same-typed transposition among the 28 is detectable, not
just the one that was demonstrated.

### (c) Is the declined AST guard sound reasoning, or convenient? — sound

I pushed on this, because "it would be too much machinery" is exactly what a
convenient decline sounds like. Three things make it sound here:

1. **The cost claim is real and checkable.** The comparable guard
   (`internal/db/issue_citation_guard_test.go`) is genuinely ~1000 lines, and
   the tree's guard family is the subject of §8's `#0258` case — six passes of
   hardening a mechanism that became new mutable surface. `#0330`, `#0347` and
   `#0356` all ended with "record the limit rather than add another
   mechanism". Building a Go parser to compare `Scan(...)` identifiers against
   column identifiers would be the seventh in-file check §8 warns against.
2. **The decline did not leave the hazard uncovered.** This is the difference
   between a sound stop and a convenient one. Criterion 4 asks whether the
   positional order "can be pinned the same way"; the answer delivered is a
   *cheaper mechanism that actually detects the defect* — proved in (b) above —
   rather than nothing. A decline that shipped no coverage for the worse hazard
   would have been a bounce.
3. **The value-based approach is arguably the better oracle**, not merely the
   cheaper one. An AST guard compares two *textual* representations and can be
   satisfied by an edit to its subject (§8's `#0258` lesson). The round-trip's
   oracle is data that has been through Postgres and back — a different
   representation of the same fact, which no edit to `scanSubscriber` can also
   satisfy. It also covers something an AST guard would not: it exercises
   `List` and `GetByID` as real callers, so it catches an arity mismatch and a
   SQL-level error too.

Criterion 5 ("do not over-build") is honoured on both sides: `deriveQualified
Columns` is ~15 lines for the defect that *did* fire, and the AST guard is
declined with the limit recorded for the one that has not.

### One limit of `deriveQualifiedColumns`, measured — contained, not a gap

The function splits on `,` and handles a **one-argument** wrapped call. A
future multi-argument call in `subscriberColumns` would be split across its
inner comma and mis-derived. I checked whether that fails loudly or silently,
because a silent mis-derivation would be a real gap:

```
PROBE: coalesce(signup_user_agent, signup_user_agent) added to subscriberColumns
--- FAIL: TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip
    List: subscribers: listing: ERROR: syntax error at or near ")" (SQLSTATE 42601)
```

It fails loudly, at test time, in the new test. The limit is real but
self-detecting, and `subscriberColumns` has contained exactly one such call
(`host(signup_ip)`) for the life of the file. Not blocking; the function's doc
comment describes the shape it handles but does not warn about the shape it
does not, which is worth one sentence if anyone is next in this file.
