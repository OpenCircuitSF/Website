## Description

Adding one column to `subscribers` requires four hand edits:

| Site | Kind | Failure if missed |
|---|---|---|
| `subscriberColumns` | list | — |
| `qualifiedSubscriberColumns` (`Store.List`'s JOIN-safe duplicate) | list | **runtime 500** |
| `scanSubscriber`'s `Scan` order | positional | runtime |
| the struct | fields | compile |

Three are positional, so a wrong-order addition fails at **runtime**, not at
compile time. And `qualifiedSubscriberColumns` is **the one with no by-name
test**.

**This already fired.** `#0312`'s implementer added `invite_resent_at`, missed
`qualifiedSubscriberColumns`, and 500'd the admin subscribers list. It was caught
by the existing suite and fixed, and the implementer disclosed it — but the
minimum fix leaves the duplication in place for the next column.

## Acceptance criteria

1. `qualifiedSubscriberColumns` is **derived** from `subscriberColumns` (by
   prefixing) **or** the two parsed identifier sequences are pinned against each
   other, so adding a column to one and not the other fails.
2. Prove it discriminates: add a column to `subscriberColumns` alone and confirm
   the check fails, naming what diverged. **A check that cannot fail pins
   nothing** — `#0354`, `#0358` and `#0363` each shipped exactly that this
   phase, and `#0364` exists because a passing assertion can pass for the wrong
   reason.
3. If you choose the pinning route rather than derivation, the oracle must not
   be **a copy of the answer stored next to the question** (§8). Derive both
   sequences from the source, do not transcribe either into a fixture.
4. Consider whether `scanSubscriber`'s positional order can be pinned the same
   way, and say explicitly whether you did or why not — a positional list that
   fails at runtime is the worse of the two hazards, even though it is not the
   one that fired.
5. **Do not over-build.** If derivation closes it in a few lines, stop there;
   `#0330`, `#0347` and `#0356` all ended with "record the limit rather than add
   another mechanism", and §8's `#0258` case is six passes of the opposite. If
   the sound fix needs more machinery than the defect costs, say so and stop.
6. `gofmt` stability; the floor harness stays **42 total / 12 non-exempt**
   (`#0323`); per §5 name the specific tests that ran.

## Re-measurement (before acting)

Re-read the four sites directly in `internal/subscribers/store.go` rather
than trusting this issue's prose:

- `subscriberColumns` (a `const`, line ~372): 28 bare/expression column
  references, ending `..., synthetic, invite_resent_at`.
- `qualifiedSubscriberColumns` (was a separate `const`, line ~1935): 28
  `subscribers.`-qualified references, ending
  `..., subscribers.synthetic, subscribers.invite_resent_at` — **currently
  in sync** with `subscriberColumns` (confirmed by diffing the two column
  sequences by hand). The issue's framing ("kept in sync by eye") is
  accurate as a structural description, not a claim that they are
  presently desynced — #0312's own fix already closed the specific
  instance that fired.
- `scanSubscriber`'s `Scan(...)` argument list: 28 `&sub.X` arguments, in
  the same order as `subscriberColumns`' columns.
- The `Subscriber` struct: same 28 fields, same order (`AlreadySubscribedSentAt`
  sits between `ConfirmedAt` and `ManageToken` in both the struct and the
  scan order, confirmed side by side).

Confirmed: all four are presently consistent, and three of the four
(`qualifiedSubscriberColumns`, `scanSubscriber`'s order, the struct's field
order) are each independently hand-maintained against `subscriberColumns` —
the issue's premise holds.

## Fix

**Route taken: derive, per criterion 1's first branch.**
`qualifiedSubscriberColumns` changed from a separately hand-maintained
`const` to a `var` computed by a new `deriveQualifiedColumns(cols, table
string) string` (`internal/subscribers/store.go`), which prefixes each
comma-separated column reference in `subscriberColumns` with
`"<table>."` — including the single identifier inside the one wrapped call
`host(signup_ip)` → `host(subscribers.signup_ip)`. There is now only one
column list to remember to edit when a column is added; the specific defect
class that fired in #0312 (an edit to one list, forgotten in the other)
is closed structurally rather than by convention.

**Criterion 2 — the discrimination proof.** Under true derivation, "add a
column to `subscriberColumns` alone" can no longer happen (there is only
one list to edit), so the regression this issue is actually about is
someone *reintroducing* the old two-list shape. Two tests close that:

- `TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns` pins
  `qualifiedSubscriberColumns == deriveQualifiedColumns(subscriberColumns,
  "subscribers")` — literally #0312's mistake, reproduced and caught (see
  `## Verification`).
- `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip` independently
  catches the same omission (a column-count mismatch errors `Store.List`
  outright) *and* catches something the list-identity test cannot: a
  same-typed positional reorder in `scanSubscriber`'s `Scan(...)` call that
  leaves both column lists untouched and the code compiling clean. See
  criterion 4 below.

**Criterion 3.** `TestDeriveQualifiedColumns` (the derivation function's own
unit test) uses a small literal input/output pair constructed in the test
itself — not `subscriberColumns`/`qualifiedSubscriberColumns` — so its
oracle is not a copy of the answer sitting next to the question (§8). The
round-trip test's oracle is *inserted, distinct-per-type sentinel values*
read back from Postgres — also not a transcription of either column list.

**Criterion 4 — scanSubscriber's positional order, considered explicitly.**
Did **not** build a general AST-based pin (comparing `Scan(...)`'s argument
identifiers against `subscriberColumns`' column identifiers in order). This
repo already has one general-purpose AST guard for a comparable problem
(`internal/db/issue_citation_guard_test.go`, ~1000 lines, built for a
genuinely corpus-wide citation-checking problem) — building an equivalent
parser here would be disproportionate machinery for a defect that, unlike
`qualifiedSubscriberColumns`, **has not actually fired** (this issue's own
description). Per criterion 5: stopped short of that.

Instead, added `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip`: it
inserts one `subscribers` row (plus one `subscriber_imports` row for the
`import_id` FK) with every column set to a value distinct from every other
column of the same Go type — eleven distinct timestamps across the
`*time.Time`/`time.Time` fields, a dozen distinct strings across the
`*string`/`string` fields — then reads it back through **both**
`scanSubscriber` call sites that matter: `GetByID` (`subscriberColumns`,
unqualified) and `List` (`qualifiedSubscriberColumns`, qualified — the
JOIN-safe path #0312 actually broke). A same-typed reorder in
`scanSubscriber`'s `Scan` order swaps values into the wrong struct fields
and this test's per-field assertions catch it; a pure column-count check
would not have. Proven by mutation (`## Verification`): the round-trip test
catches a `ConfirmSentAt`/`ConfirmExpiresAt` swap that
`TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns` correctly
does **not** flag (that swap touches neither column list), demonstrating
the two tests catch genuinely different mistakes and neither subsumes the
other.

**Criterion 5 — stop condition.** Reached it for the AST-guard question
(criterion 4, above): the sound general fix costs roughly 1000 lines of
comparable machinery already in this tree, for a defect class that has not
fired; recorded the limit and did not build it. The derivation itself
(`deriveQualifiedColumns`, ~15 lines) is proportionate to the defect that
*did* fire (#0312) and was built.

**Criterion 6.** `gofmt -l` clean on every file touched (see
`## Verification`); the guards harness floor (42 total / 12 non-exempt,
#0323) is untouched by this change — nothing here adds or removes a guard
script.

## Verification

```
ISSUE=0369 scripts/check.sh go ./internal/handlers/... ./internal/subscribers/... \
  ./internal/db/... ./internal/audit/... ./internal/outbox/...
```
→ all five packages `ok`, zero skips, `gofmt -l` clean, `VERIFICATION
PASSED`. New/changed tests naming this issue, all in
`internal/subscribers/store_test.go`: `TestDeriveQualifiedColumns`,
`TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns`,
`TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip`.
`scripts/check.sh guards` → all guard scripts pass (floor unaffected).

**Fails-without-the-fix proofs**, run in an isolated copy of the working
tree (`git stash create` → `git archive` → extracted to a scratchpad
subdirectory, CLAUDE.md §8b), against a dedicated scratch database
(`opencircuit_test_mut0367`, provisioned by a real `migrate up` through
`000026`) — never the shared tree. Restored via a saved pre-mutation copy
plus `diff`/`shasum -a 256` confirmation after every mutation.

- **Reintroducing the two-list shape, missing the new column** — replaced
  the derived `var qualifiedSubscriberColumns = deriveQualifiedColumns(...)`
  with a separate hardcoded `const` reproducing the exact pre-#0312 literal:
  27 columns, omitting `invite_resent_at` (`subscriberColumns` itself was
  left untouched, still 28). Both new tests failed independently:
  `TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns`
  (`qualifiedSubscriberColumns has drifted...`) and
  `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip` (`List: ...
  number of field descriptions must equal number of destinations, got 27
  and 28`) — reproducing #0312's actual failure mode (a 500 on the admin
  subscribers list) under two independent oracles.
- **Same-typed positional reorder, no list touched** — swapped
  `scanSubscriber`'s `&sub.ConfirmSentAt`/`&sub.ConfirmExpiresAt` Scan
  arguments (both `*time.Time`, code compiles clean).
  `TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip` failed on both
  the `GetByID` and `List` assertions (`ConfirmSentAt = ..., want ...`);
  `TestQualifiedSubscriberColumns_IsDerivedFromSubscriberColumns`
  correctly **passed** (neither column list was touched by this mutation)
  — confirming the round-trip test closes a gap the list-identity test
  cannot.
