## Description

`#0195`'s phase-3 review passed the branch reorder and then made a point that
outlives it: **this tracker has now hit the replicated-logic trap three times.**

- `#0184` — a hand-rolled `normalizeCountInput` replica, caught by hex dump.
- `#0189` — the same replica, wrong separator class, caught by hex dump again.
- `#0195` — `countInputDisabled` / `escapeCloses` / `backdropCloses` in
  `CampaignSendDialog.guard.test.ts`, one-token mirrors of the component's own
  `sending` / `!sending` / `!sending` gates.

The `#0195` instance is the mildest — an identity function cannot disagree with
`disabled={sending}`, and the assertive weight sits on
`expect(sendingDuringFlip).toBe(true)`, which mutation B genuinely catches. But
it can drift silently: changing the component to `disabled={sending ||
blockedAgain}` leaves the replicas green while their coverage claim goes stale.
`#0186`'s `oldSending` / `oldBlockedAgain` formulas have the same shape.

**The fix is cheaper than it looks, and it already exists in this repo.**
`web/src/lib/citationGuard.test.ts` parses `.svelte` files with
`svelte/compiler`'s AST inside vitest — no DOM, no `#0094`. A structural guard in
that style can assert the component's real gate expressions match what the tests
claim they are, making drift loud at a fraction of `#0094`'s cost.

**A second, low-value item from the same review:** `sendGuardState`'s doc comment
quotes only one of `#0184`'s three arguments for the original branch order (the
render-gate one). `#0184` also argued `status` is durable and server-authoritative,
and — the actual tie-breaker — that neither ordering differed in safety. It was
that third argument collapsing (once `#0186` wired in a consumer where
`unavailable` disables nothing) that justified `#0195`'s reorder. The comment
should name all three so the reasoning survives.

## Implementation notes

**New file: `web/src/views/admin/CampaignSendDialog.structuralGuard.test.ts`.**
Reads `CampaignSendDialog.svelte`'s AST with `svelte/compiler`'s
`parse({ modern: true })` (`citationGuard.test.ts`'s technique) and
`CampaignSendDialog.guard.test.ts`'s AST with the TypeScript compiler API
(also `citationGuard.test.ts`'s technique, applied to the `.ts` side).
Neither file is loaded through a DOM.

**What it asserts: tree-to-tree agreement, not agreement with a typed
constant.** Concretely:

1. It finds the component's own `sending` local — not by assuming the name
   `sending`, but by searching the instance script for whichever
   `VariableDeclarator` has the shape `let X = $derived(guard.kind ===
   'sending')` and reading `X` off of it (`findSendingVarName`). `'sending'`
   here is the `SendGuardState` discriminant defined in `sendConfirm.ts`,
   not an invented string — matching that value is how the guard finds
   "the dialog's own submitting-state variable," whatever it is named.
2. It locates the three real gates by structural role, not by name: the
   `<input id="send-confirm-count">`'s `disabled` attribute; the backdrop
   (`<div role="presentation">`)'s `onclick`, verified to be a `&&` guard
   whose right side actually calls `onClose()`; and the Escape branch,
   found by first reading the *identifier* the backdrop's `onkeydown`
   points at (so it uses whatever function is really wired, not a
   hardcoded `handleKeydown`), then finding that function's `if` branch
   whose test compares `.key === 'Escape'`.
3. Each of those three real expressions is classified purely from its own
   AST shape as `identity` (a bare reference to some variable) or
   `negation` (`!` of some variable) — never compared to a string.
4. Separately, `CampaignSendDialog.guard.test.ts`'s `countInputDisabled` /
   `escapeCloses` / `backdropCloses` helpers are read from THEIR OWN AST
   (TypeScript compiler API) and classified the same way, keyed off each
   helper's own parameter name — again, no typed string.
5. The two classifications (component vs. test-helper) are asserted equal,
   and the component's operand is asserted equal to the `sending` local
   found in step 1.

So a passing run proves "the component's real disabled/Escape/backdrop
gates are identity/negation of the same `$derived(guard.kind === 'sending')`
value the guard test's helpers also claim identity/negation of" — two real
files compared to each other, never a hand-typed `"sending"` string
standing in for either side. (Structural selectors like the element `id`,
the `role="presentation"` attribute, and the `'Escape'` key name are used
to *locate* the right AST nodes, the same way `citationGuard.test.ts` uses
`.test.ts`/`.d.ts` suffixes to select files — they are not duplicating any
of the logic being checked.)

### Would this mechanism have caught the three instances? — 2 of 3, and the class is not closed

This is the question the issue exists to answer, so it is answered per instance
rather than in aggregate.

| instance | shape of the replica | would this guard have caught it? |
|---|---|---|
| **`#0184` / `#0189`** — hand-rolled `normalizeCountInput` copy at `CampaignSendDialog.guard.test.ts:93`, using an ASCII-space separator class (`0x20`) where the real function uses U+2009 (`e2 80 89`) | a **re-implementation** — a function body that can *disagree* with the original | **No.** |
| **`#0195`** — `countInputDisabled` / `escapeCloses` / `backdropCloses`, one-token mirrors of `disabled={sending}`, `!sending`, `!sending` | **mirrors** — identity/negation that cannot disagree, only go stale | **Yes**, and proved by mutation below. |

**On the `#0184`/`#0189` verdict, explicitly, so nobody believes the class is
closed.** This guard is scoped to one component's three gates, and its entire
classification vocabulary is `identity` / `negation` / `other` over a single
identifier. That vocabulary cannot express a regex character class, a
`Number.isSafeInteger` call, or any other function body — nothing in the file
compares a test-local helper's *body* against a real library function's body. A
fourth `normalizeCountInput` replica landing tomorrow in a different test file
would be exactly as invisible as it was in `#0189`. That is not a defect in this
issue — the issue's own Description scopes itself to the `#0195` instance — but
the honest statement is: **this closes the mild form (mirrors going stale) for
these three gates, and leaves the severe form (re-implementations disagreeing)
untouched.**

Worth recording alongside it: the severe form already has a better answer than a
guard, and `#0189` applied it — *delete the replica and call the real function*.
`CampaignSendDialog.guard.test.ts:118` now calls `normalizeCountInput` directly,
with a doc comment naming `#0184`/`#0189`. A structural guard is the right tool
only where the real thing cannot be called, which is exactly the `.svelte` case
`#0094` creates. That distinction is the useful generalisation, and it is why
this issue's mechanism does not need to grow to cover `#0189`.

### The "no fourth replica" claim — verified by inspection *and* by rename

The implementer's central claim is that the guard hardcodes neither `"sending"`
nor `"!sending"` as a gate expression. Read, then probed.

**By inspection.** `findSendingVarName` searches the instance script for a
`VariableDeclarator` whose init is `$derived(<member>.kind === 'sending')` and
reads the declarator's `id.name` off of it — the name is discovered, never
assumed. `findInputDisabledExpr` selects on `id="send-confirm-count"`,
`findBackdropDiv` on `role="presentation"`, `findKeydownHandlerName` reads the
identifier the backdrop's `onkeydown` *actually* points at rather than assuming
`handleKeydown`, and `findEscapeGate` then locates the `if` whose test's left

its own AST shape by `classifySvelteGate`; each helper from its own AST and its
**own parameter name** by `classifyTsGate`. The two `kind`s are compared to each
other. The only hand-typed strings are locators (`'sending'` as the
`SendGuardState` discriminant, the element `id`, `role`, `'Escape'`,
`onClose`) — and each one, if it stopped matching, throws a named error rather
than silently passing. Confirmed on the `'sending'` discriminant specifically:
it is `sendConfirm.ts`'s own union tag, not an invented value.

### Criterion 4's decline — judged, and the reasoning is sound

The criterion permits "covered by the same mechanism, **or** their staleness risk
is recorded as accepted", so the decline is within the criterion; the question is
whether the *reason* is good. It is, and the load-bearing premise was checked
rather than accepted:

- `oldSending(c) = c.inFlight` and `oldBlockedAgain(c) = c.unmet.length > 0` are
  written against the test's own `Case` interface, not extracted from any
  component file.
- Grepped `CampaignSendDialog.svelte`: **nothing derives from `inFlight` or
  `unmet.length` directly any more.** Line 55 passes `inFlight` into
  `sendGuardState` and line 159 iterates `unmet` for display; `sending` (72) and
  `blockedAgain` (81) both read `guard.kind`. So there is genuinely no live
  expression in the tree for these two formulas to be compared against —
  structurally guarding them would be asserting agreement with code `#0186`
  deleted. Incoherent, as claimed, not merely hard.
- And the assertive weight in that `describe` block sits on
  `newSending`/`newBlockedAgain`, which route through the real `sendGuardState`
  via `guardOf` — not a re-implementation. Verified by mutation C below, which
  turns those two cases red.

**Was a weaker check available?** One was, and it is worth naming even though it
does not change the verdict: the guard could assert the *negative* — that the
component contains no local derived directly from `inFlight` or
`unmet.length > 0`. That would pin the premise the whole "old vs new" block rests
on, so that reintroducing a raw-boolean derivation would stop the comparison
being a before/after comparison loudly rather than silently. It is marginal (the
reintroduction would have to be deliberate, and `#0186`'s own tests would likely
notice), so its absence is not a bounce — but it is the one thing that could have
been done and was not, and it is recorded here so the decline is on the record
with its alternative rather than as a bare "accepted".
