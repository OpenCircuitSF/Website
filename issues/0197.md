## Description

`#0195`'s phase-3 review passed the branch reorder and then made a point that
outlives it: **this tracker has now hit the replicated-logic trap three times.**

- `#0184` — a hand-rolled `normalizeCountInput` replica, caught by hex dump.
- `#0189` — the same replica, wrong separator class, caught by hex dump again.
- `#0195` — `countInputDisabled` / `escapeCloses` / `backdropCloses` in
  `CampaignSendDialog.guard.test.ts`, one-token mirrors of the component's own
  `sending` / `!sending` / `!sending` gates.

The `#0195` instance is the mildest — an identity function cannot disagree with
`disabled={sending}`, and the assertive weight sits on
`expect(sendingDuringFlip).toBe(true)`, which mutation B genuinely catches. But
it can drift silently: changing the component to `disabled={sending ||
blockedAgain}` leaves the replicas green while their coverage claim goes stale.
`#0186`'s `oldSending` / `oldBlockedAgain` formulas have the same shape.

**The fix is cheaper than it looks, and it already exists in this repo.**
`web/src/lib/citationGuard.test.ts` parses `.svelte` files with
`svelte/compiler`'s AST inside vitest — no DOM, no `#0094`. A structural guard in
that style can assert the component's real gate expressions match what the tests
claim they are, making drift loud at a fraction of `#0094`'s cost.

**A second, low-value item from the same review:** `sendGuardState`'s doc comment
quotes only one of `#0184`'s three arguments for the original branch order (the
render-gate one). `#0184` also argued `status` is durable and server-authoritative,
and — the actual tie-breaker — that neither ordering differed in safety. It was
that third argument collapsing (once `#0186` wired in a consumer where
`unavailable` disables nothing) that justified `#0195`'s reorder. The comment
should name all three so the reasoning survives.

## Implementation notes

**New file: `web/src/views/admin/CampaignSendDialog.structuralGuard.test.ts`.**
Reads `CampaignSendDialog.svelte`'s AST with `svelte/compiler`'s
`parse({ modern: true })` (`citationGuard.test.ts`'s technique) and
`CampaignSendDialog.guard.test.ts`'s AST with the TypeScript compiler API
(also `citationGuard.test.ts`'s technique, applied to the `.ts` side).
Neither file is loaded through a DOM.

**What it asserts: tree-to-tree agreement, not agreement with a typed
constant.** Concretely:

1. It finds the component's own `sending` local — not by assuming the name
   `sending`, but by searching the instance script for whichever
   `VariableDeclarator` has the shape `let X = $derived(guard.kind ===
   'sending')` and reading `X` off of it (`findSendingVarName`). `'sending'`
   here is the `SendGuardState` discriminant defined in `sendConfirm.ts`,
   not an invented string — matching that value is how the guard finds
   "the dialog's own submitting-state variable," whatever it is named.
2. It locates the three real gates by structural role, not by name: the
   `<input id="send-confirm-count">`'s `disabled` attribute; the backdrop
   (`<div role="presentation">`)'s `onclick`, verified to be a `&&` guard
   whose right side actually calls `onClose()`; and the Escape branch,
   found by first reading the *identifier* the backdrop's `onkeydown`
   points at (so it uses whatever function is really wired, not a
   hardcoded `handleKeydown`), then finding that function's `if` branch
   whose test compares `.key === 'Escape'`.
3. Each of those three real expressions is classified purely from its own
   AST shape as `identity` (a bare reference to some variable) or
   `negation` (`!` of some variable) — never compared to a string.
4. Separately, `CampaignSendDialog.guard.test.ts`'s `countInputDisabled` /
   `escapeCloses` / `backdropCloses` helpers are read from THEIR OWN AST
   (TypeScript compiler API) and classified the same way, keyed off each
   helper's own parameter name — again, no typed string.
5. The two classifications (component vs. test-helper) are asserted equal,
   and the component's operand is asserted equal to the `sending` local
   found in step 1.

So a passing run proves "the component's real disabled/Escape/backdrop
gates are identity/negation of the same `$derived(guard.kind === 'sending')`
value the guard test's helpers also claim identity/negation of" — two real
files compared to each other, never a hand-typed `"sending"` string
standing in for either side. (Structural selectors like the element `id`,
the `role="presentation"` attribute, and the `'Escape'` key name are used
to *locate* the right AST nodes, the same way `citationGuard.test.ts` uses
`.test.ts`/`.d.ts` suffixes to select files — they are not duplicating any
of the logic being checked.)

**Criterion 4 — `#0186`'s `oldSending`/`oldBlockedAgain`.** Recorded as an
accepted staleness risk, not covered by the same mechanism, for a reason
specific to what those two formulas are: they are a frozen snapshot of the
component's PRE-`#0186` behavior (`c.inFlight` and `c.unmet.length > 0`
directly, with no `sendGuardState` involved at all) — deliberately kept
static as the "before" side of a before/after regression comparison. There
is no live AST in the current component that represents "the old raw
`inFlight` boolean drove `disabled` directly," because `#0186` removed
that code; structurally guarding `oldSending`/`oldBlockedAgain` against the
current component would be comparing them to something that no longer
exists, which is incoherent, not merely hard. The risk is bounded for two
reasons already true today: (a) they are one-line formulas written
directly against the `Case` interface, not extracted from or copied out of
any component file, so there is nothing for them to silently drift away
from except their own stated intent; and (b) the assertive weight in that
`describe` block sits on `newSending`/`newBlockedAgain`, which route
through the real, tested `sendGuardState` (`guardOf`, not a
re-implementation) — `oldSending`/`oldBlockedAgain` are the reference
column being compared against, not a claim about current behavior that
could go stale in a way that produces a false pass. This mirrors `#0195`'s
own review finding on `countInputDisabled`/`escapeCloses`/`backdropCloses`
before this issue closed that gap: identity/negation "replicas" cannot
disagree with real logic about anything; only a re-implementation can.

**Criterion 6 — `sendGuardState`'s doc comment.** Rewrote the `#0184`
bullet in `web/src/lib/sendConfirm.ts` to name all three of `#0184`'s
original arguments — (a) `status` is durable and server-authoritative while
`inFlight` is transient; (b) `unavailable` should win because
`canSendCampaign` is "the render gate"; and (c), named explicitly as the
actual tie-breaker, that neither ordering differed in *safety* at the time,
so the tie went to the more authoritative fact — and states plainly that
(c) is the one `#0195` invalidated: `#0186` wired the dialog to the guard
and `#0189` threaded the real `status` prop, which made `unavailable`
reachable in the one consumer (`CampaignSendDialog`) where it disables
nothing, so the two orderings stopped being safety-equivalent and (c)
collapsed — which is what actually licensed revisiting (a) and (b), not a
preference for one true fact over the other.
