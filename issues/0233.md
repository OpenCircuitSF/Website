## Description

`#0231` put a photograph of a green-phosphor Zenith monitor in the home hero.
The screen in that photograph is a **still image**: it says `> Open Circuit SF _`
and always will.

The user supplied a reference implementation —
`../open-circuit-sf-perspective-crt.html` — that makes the screen **live**: a
canvas is projectively warped onto the four corners of the photographed glass,
so real text can be typed, scrolled and re-rendered while still appearing to sit
on a monitor photographed at an angle. It is a genuine perspective mapping, not
a rotate/skew, so the illusion survives the ~15° yaw of the photograph.

The user asked for a **static-HTML proof of concept matching the current home
page design first**, before any of it touches `web/src/views/Home.svelte`. That
prototype is the deliverable of this issue; integration is a separate one.

## What has been built

`prototypes/crt-live-screen/index.html` — standalone, no build step, opened over
a local HTTP server. It reproduces the real hero (design tokens copied from
`web/src/app.css`, the `TerminalPanel` chrome, the real headline, status list
and command line, the theme toggle's three states) and composites a live screen
onto the real hero photographs, referenced by relative path out of
`web/public/` so there is exactly one copy of each asset in the tree.

**The technique**, carried over from the reference and rewritten to this
project's conventions:

1. Four corners of the photographed raster are stored as **percentages of the
   photograph**, so the fit survives any resize.
2. A projective homography is solved from the unit rectangle to those four
   corners — eight unknowns, Gauss-Jordan with partial pivoting.
3. Its coefficients are packed into a CSS `matrix3d()` (column-major, `z = 0`)
   on a plane whose `transform-origin` is `0 0`.
4. Canvas draws the terminal; a second, blurred canvas composited with
   `mix-blend-mode: screen` supplies the phosphor bloom; scanline and glass
   gradients sit on top.

## How the corners were measured

Worth recording, because **two automatic approaches were tried and both
failed**, and the failures look like successes if not checked visually.

- **Thresholding the phosphor green finds the glow, not the raster.** Light
  pools on the bezel and inner surround, so a green mask reaches well outside
  the glass. Eroding it hard and taking extremes of `x±y` gave a quadrilateral
  covering roughly half the screen.
- **Half-maximum crossing per scanline is worse.** The brightest point in most
  columns *is* that glow, so the reported bottom edge jumped between 23% and
  75% of image height depending on the column.

**What worked:** fill the warped plane with flat magenta, screenshot it over the
photograph via `safaridriver`, and compare footprints. Over- and under-shoot at
all four corners are visible at once, which a text render does not show. Two
refinement passes converged on:

```
tl {x:22.5, y:24.0}   tr {x:69.8, y:18.0}
br {x:68.2, y:72.4}   bl {x:23.0, y:72.3}
```

**One calibration serves both themes.** `#0231` ships a dark and a light
photograph; their registration was checked against the red power LED — an
unambiguous landmark present in both — whose centroids agree to within **2px in
x and 5px in y on a 1402×1122 image** (0.14% and 0.45%). Verified by rendering,
not inferred: the same corners were screenshotted against both photographs.

## Acceptance criteria

- [x] A standalone static HTML prototype exists that matches the home page's design — real tokens, real panel chrome, real hero copy, working theme toggle
- [x] The live screen is projectively warped onto the photographed glass and stays registered when the stage is resized
- [x] The same corner calibration is proved correct against both the dark and the light photograph
- [x] Calibration is adjustable in the prototype — draggable handles, numeric fields, and JSON output to paste into the component
- [x] `prefers-reduced-motion` renders a static finished frame rather than a blank screen or an animation
- [ ] A decision is recorded on what the live screen should *say* on the real home page — see `## Open questions`
- [ ] The performance cost is measured, not assumed: repaint rate, CPU while idle, and behaviour when the hero scrolls out of view
- [ ] Integration into `web/src/views/Home.svelte` is filed as its own issue and does not happen here

## Open questions

These need answering before integration, and none is settled by the prototype:

1. **What does it say?** The prototype shows upcoming workshops, which is
   appealing but duplicates the "Next up" section directly below the hero and
   would need the real API. A fixed brand loop needs no data and cannot go
   stale. This is a content decision.
2. **What does it cost?** The reference implementation repaints on a 100ms
   timer *plus* a 520ms cursor blink *plus* a 720ms line timer, all
   unconditionally and forever. The prototype already drops the opacity jitter
   and stops the cursor under `prefers-reduced-motion`, but nothing yet pauses
   the canvas when the hero is scrolled out of view or the tab is hidden. On a
   marketing home page that is a battery cost paid by every visitor for
   something most will scroll past in seconds.
3. **Does it become the LCP element?** `#0231` measured the still photo taking
   LCP from the headline. A canvas that starts empty and types in may push LCP
   later, or may not count at all. Must be measured, not reasoned about.
4. **What happens with JavaScript off, or before hydration?** The still
   photograph is currently correct on its own. The live version must degrade to
   exactly that rather than to a blank rectangle.
5. **Accessibility.** The prototype marks the whole stage `aria-hidden` on the
   grounds that the screen repeats the adjacent headline. That holds only while
   the content stays decorative — a screen showing real workshop dates is
   information, and hiding it would be wrong.

## Notes

Filed at the user's request on 2026-08-24, along with the prototype itself.

The reference file is 2.4 MB because it embeds its photograph as a base64 data
URI, and its photograph is a **different crop** (1365×1097) from this project's
asset (1402×1122) — so its own corner defaults do not transfer, which is why
this issue re-measures them.

Not to be confused with `#0231`, which placed the still photograph. This issue
only makes the screen live.
