## Description

These are follow-ups from `#0679`'s review.

1. **No idempotency for MCP writes.** REST creates accept `Idempotency-Key`, but MCP tool calls have no equivalent. An agent that retries `create_guide_posts` or `create_event` after a timeout can create duplicates. One option is an optional `idempotency_key` argument on create tools, mapped onto the same store (`#0675`, `#0684`). Another is to have the tool description tell agents to check with `list_*` before retrying.
2. **No cancellation policy.** `PropagateRequestCancellation` is unset, so a tool call keeps running after the client disconnects. For `send_guide_post`, finishing the send is probably the right behaviour. Decide this per operation and document it.

## Plan

Planned and implemented in one pass (opus · medium), at the user's "keep moving" direction.

1. **Shared runner in `internal/api`.** Move REST's Begin/replay/run/Abandon/Complete sequence out of `serve` into an exported `api.RunIdempotent`, and export `ValidIdempotencyKey`, `Registry.IdempotencyStore()` and `Registry.Now()`. REST then calls the runner, so both adapters have the same conflict, replay, abandon and complete semantics.
2. **MCP adapter (`internal/mcpserver/tools.go`).** For every operation with `Idempotency` set, `toolFor` adds an optional `idempotency_key` string to the input schema and a sentence to the description. `handlerFor` removes the key from the arguments before `op.Decode`, so unknown-field rejection still works. When a key is present, it runs `api.RunIdempotent` per token with `sha256("mcp\n" + op + "\n" + canonical args)`, and a replay returns the stored bytes. This is generic: any operation registered later with `Idempotency: true` gets it. `NewHandler` panics if an idempotent operation has no store, or if an operation's `In` already uses the `idempotency_key` name.
3. **Cancellation.** Set `PropagateRequestCancellation: true`, then make the policy per operation in `api.CallContext`: GETs stay cancellable, and every write (non-GET) runs on `context.WithoutCancel`, so a started create, send or publish finishes and records its idempotency result. REST's `serve` uses the same helper. Document this in `doc.go` and the server instructions.
4. **Tests.** Add `internal/mcpserver/idempotency_test.go` (in-memory store, an idempotent fixture op): a retry replays and runs once, different arguments with the same key conflict, no key behaves normally, an in-flight key conflicts, a bad key is a validation error, the key is in the schema only for idempotent ops, and a cancelled read is cancelled while a cancelled write finishes. Add a Postgres test in `internal/handlers` for `create_guide_posts` that creates its rows once. Existing schema and description oracles allow for the extra key.

## Fix

Commit `1f9ec678`, in worktree branch `worktree-agent-aad1e2d4e26b775c1`.

1. **Shared runner in `internal/api`.** `api.RunIdempotent(ctx, store, now, tokenID, key, op, hash, fn)` does Begin, replay, run, Abandon on error and Complete on success, with Abandon and Complete detached from `ctx`. It is lifted out of REST's `serve`, which now calls it, so the two adapters cannot drift. Also new: `api.ValidIdempotencyKey` (exported), `Registry.IdempotencyStore()` and `Registry.Now()`. The conflict messages are unchanged.
2. **MCP tools.** For an operation with `Idempotency` set (today `create_guide_posts`; `#0677`'s `create_event`/`duplicate_event` get it automatically), `toolFor` adds an optional `idempotency_key` string (1 to 255 characters) to the input schema and appends `mcpserver.IdempotencyKeyNote` to the description. `handlerFor` takes the key out of the arguments before `op.Decode`, so other unknown fields are still rejected. A key that is not a string or not 1 to 255 printable ASCII characters is a validation error naming `idempotency_key`. With a key, the call runs through `api.RunIdempotent`, per API key, with `sha256("mcp\n" + op + "\n" + canonical args)`, where the canonical form has sorted keys and numbers exactly as sent. A replay returns the stored bytes. A mismatch or an in-flight key is a `conflict` tool error. Without a key, nothing changes. On a tool whose operation takes no key, the argument is still an unknown-field error. `NewHandler` panics if an exposed idempotent operation has no store (mirroring `NewHTTPRouter`) or already has an `idempotency_key` input field.
3. **Cancellation policy.** The SDK option is all or nothing, and it only applies to clients on the 2026-07-28 protocol or later. So it is set (`PropagateRequestCancellation: true`) and the policy per operation is `api.CallContext`, which both adapters use. A GET runs on the request context and is cancelled with the client. Every write runs on `context.WithoutCancel`, so a started create, send or publish finishes, writes its audit rows, and records its idempotency result for a retry to replay. I detached every write rather than only `PublicEffect` ones. A write the client cancels is otherwise ambiguous to the agent, and a DB write gains nothing from being stopped partway. REST's `serve` follows the same policy. The server instructions and `doc.go` document it.

## Assumptions

- A key is scoped per adapter, and this is deliberate. REST hashes path, query and raw body, while MCP hashes canonical arguments, so the same key string used over both is a conflict, not a replay. A REST success body (Encoder output, trailing newline) is therefore never replayed into an MCP result.
- The status stored for an MCP result is 200. It is never read back, because MCP results carry no status.
- REST now also runs writes on a detached context. Before this, a client disconnect could cancel a REST write mid-operation.

## Review notes

Reviewed 2026-11-15 (opus · medium) on `main` after the merge.

- **REST extraction.** `api.RunIdempotent` is the old `serve` sequence: Begin, the two conflict messages, replay of stored status and body with `Idempotent-Replayed`, Abandon on error and Complete on success, both on `context.WithoutCancel`. REST's own hash (operation, path, query, raw body) is unchanged, and so is `#0684`'s takeover (it lives in the store's `Begin`). The REST idempotency tests in `internal/api` and `internal/handlers` pass unchanged.
- **MCP key.** `idempotency_key` is added only when `op.Idempotency` is set, and both schema oracles require that. It is removed before `Decode`, so `bogus` beside a key is still rejected, and a key on a non-idempotent tool is an unknown field. The key is per token. A replay returns the stored bytes, and validation reuses `ValidIdempotencyKey`. Canonical hashing sorts keys and keeps numbers as sent, so `1` and `1.0` hash differently. That is acceptable because it fails safe: a re-serialised retry gets a `conflict`, never a duplicate, and it is already looser than REST, which hashes raw bytes.
- **Cancellation, one defect fixed.** The detached write had **no bound at all**. There is no `http.Server` `WriteTimeout`, no `TimeoutHandler`, and no `statement_timeout`. `Shutdown` never cancels request contexts (`main.go`'s own comment says so), so graceful shutdown is unchanged: its budget bounds it, and process exit ends whatever is left. Before `#0685`, Apache's proxy timeout closing the backend connection was what eventually cancelled a hung write. With that gone, a write stuck past `IdempotencyInFlightTimeout` (5 min, `#0684`) could have its in-flight key **taken over by a retry and run twice**, which is exactly what the key exists to prevent. The fix: `CallContext` now returns `(ctx, cancel)` and bounds a write with `api.WriteTimeout = 2 * time.Minute` on top of `WithoutCancel`. Values are kept. Both call sites `defer cancel()`. `TestCallContextPolicy` now asserts that every write has a deadline within `WriteTimeout`, and that `WriteTimeout < IdempotencyInFlightTimeout`. The `IdempotencyInFlightTimeout` comment and `doc.go` were updated to match.
- **REST writes ignore client disconnect.** Accepted. It is the same policy, and now bounded as above.
- **The 300 ms settle wait** in `TestCancellationPolicy` cannot make the real code fail: a detached context never fires within 300 ms. Under heavy load it can only weaken the mutation check, by letting a mutation pass vacuously, and never the passing run. I kept it, because the deadline assertion in `TestCallContextPolicy` is now the deterministic unit-level check.
