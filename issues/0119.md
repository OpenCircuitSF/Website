`CampaignEditor.svelte`'s Send button carries
`aria-describedby="preflight-panel-hint"`, but **no element in the SPA has that
id** — `grep -rn "preflight-panel-hint" web/src` returns exactly one hit, the
reference itself. The attribute is silently ignored, so a blocked Send button
announces as "Send, unavailable" (`aria-disabled="true"`) with no reason
attached. That is precisely the failure `#0047`'s own Notes exist to prevent:
"an operator staring at a greyed-out send button with no reason given will work
around it or give up."

`#0047`'s plan §7 committed to this explicitly — "`aria-describedby` also points
the button at the pre-send panel." It ships pointing at nothing.

Partially mitigated today: the "Pre-send checks" panel is rendered
unconditionally and is visible, and activating the blocked button moves focus to
the panel's heading (`onOpenSend`'s `preflightHeadingEl?.focus()`), which does
work. So the information is reachable — it just is not announced with the
control.

## Root cause

Two independent defects, both in `CampaignEditor.svelte`:

1. **Dangling id.** The Send button carried `aria-describedby="preflight-panel-hint"`
   but no element in the SPA had that id — the pre-send panel's `role="status"`
   container was never given one. The `unmet` (server preflight) rendering
   itself was correct; it just wasn't wired to the button.
2. **A second, unannounced blocking reason.** The pre-send panel's content was
   driven purely from the `unmet` list. `sendGateOpen` (the button's actual
   enabled/disabled decision, via `sendGuardState`/`editorGuard`) can also be
   `false` for a reason `unmet` never carries: the live audience count is 0
   (`SendGuardState`'s `'empty-audience'` kind, distinct from `'blocked'`).
   Wiring the id alone would have fixed only the case that happened to be
   exercised — `#0047`'s own two-code test (`no_test_send` +
   `physical_address_missing`) — and left `empty-audience` silent, which is
   exactly the failure mode this issue's task named: "every blocking reason
   must be announced, not just the one that happened to be tested."
3. **Dead-end focus target (found during the fix, not in the original
   report).** `<h3 class="preflight-heading" tabindex="-1">` — the element
   `onOpenSend` moves focus to — was styled screen-reader-only (clipped to
   1×1px), while a separate, non-semantic `<Panel title="Pre-send checks">`
   header showed the same text visibly. A sighted keyboard user (no screen
   reader) who triggered a blocked Send therefore had focus move to an
   invisible element with no visible focus ring at all — AC 3's "duplicates
   the panel header visually" is, read literally, not what was happening
   (the `<h3>` was invisible, so nothing visually duplicated), but the
   underlying defect AC 3 was reaching for — two elements carrying the same
   label, one of them a focus target nobody can see land — was real.

## Fix

- `web/src/lib/sendConfirm.ts` gained two pure, tested functions next to
  `sendGuardState` (already documented as this screen's single source of
  truth for whether Send may act):
  - `sendGuardDescription(guard: SendGuardState): string` — the exact text
    for each guard kind. `'blocked'` names "Pre-send checks" per AC 2;
    `'empty-audience'` gets its own distinct sentence naming the audience,
    closing the gap in root cause #2; `'ready'` describes success;
    `'unavailable'` is `''` (the control isn't rendered in that state).
  - `sendGuardSummaryClass(guard): string` — `'text-notice'` (success
    green) only when `'ready'`, `'text-muted'` otherwise, so the summary
    line's color decision also lives in `lib/`, not the template.
- `CampaignEditor.svelte`: the pre-send panel's status `<div>` now carries
  `id="preflight-panel-hint"` — matching the Send button's existing
  `aria-describedby`. Its content is `sendGuardDescription(editorGuard)`
  (read through a new `preflightPanelSummary` derived value) followed by the
  existing itemized `unmet-list` when non-empty. Because `editorGuard` is
  the exact same guard state `sendGateOpen` reads, the button's
  enabled/disabled state and its announced reason can never drift apart.
  Also removed the now-dead `preflightClear` derived value and replaced the
  inline `unmetDisplay.length > 0` template comparison with a `hasUnmetItems`
  derived value (CampaignEditor's own header comment: no comparison operator
  belongs directly in this file's markup, #0094).
- Dropped `Panel`'s `title="Pre-send checks"` and un-hid `.preflight-heading`
  (removed the `position:absolute`/`clip:rect(0 0 0 0)` sr-only rule, gave it
  normal heading styling instead). The `<h3>` is now the panel's one visible
  "Pre-send checks" label AND `onOpenSend`'s focus target — visible focus
  ring now lands on real, visible content (via app.css's global
  `:where([tabindex]):focus-visible` rule).

## Gotchas

- The literal wording of AC 3 ("duplicates the panel header visually")
  doesn't match what the code was actually doing — the `<h3>` was already
  `sr-only`, so nothing was visibly duplicated. The real defect underneath
  it (a focus target nobody sighted could see land on) is what got fixed;
  flagging this in case a reviewer checks the AC text literally against a
  screenshot and finds no pre-existing visual duplication to compare against.
- Checked the rest of the admin views for the same dangling-`aria-describedby`
  mistake: `grep -rn "aria-describedby" web/src` returns only this file and
  `web/src/lib/SubscribeForm.svelte` (a public view, not admin). That one's
  id (`subscribe-form-error`) does resolve to a real element — it is not the
  dangling-reference defect — but two different `<p>` elements both carry
  that same id (lines 194/196), which is a distinct, pre-existing bug
  (duplicate DOM ids). Not fixed here: it's a different defect than #0119
  and outside admin views. Leaving it for the reviewer/`#0063` to decide
  whether it warrants its own issue.
  - **Reviewer correction (2026-08-22): this is not a bug.** The two `<p>`
    elements are the `{#if errorMessage}` and `{:else}` arms of a single
    conditional block — exactly one is ever in the DOM, so the id is never
    duplicated. The pattern is deliberate and correct: an always-present
    `aria-live` region (empty and `sr-only` when there is no error) with the
    input's `aria-describedby` pointed at it only while a message exists.
    No follow-up issue is warranted.
