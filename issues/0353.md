## Description

`#0349` replaced the AST satisfier scan in
`internal/seo/invalidator_satisfier_guard_test.go` with `types.Implements` over
every **named** type in `internal/seo`.

Under `gotypesalias=1` (the default), a package-scope alias resolves to
`*types.Alias`, **not** `*types.Named`, so the guard's type assertion skips it
silently. Therefore:

```go
type FeedCache = struct{ *Site; cached []byte }
```

is a real satisfier of both `handlers.seoCacheInvalidator` and
`mailing.ArchiveCacheInvalidator` — `var _ interface{ Invalidate() } =
FeedCache{}` compiles — while the guard reports `ok`.

**This is a measured loss relative to the guard it replaced.** The retired
`structTypesWithEmbeddedFields` tripwire inspected any `*ast.TypeSpec` whose
`Type` was a struct literal, alias or not. `#0349`'s reviewer ran the retired
file against this identical mutation and it **fails, naming `FeedCache`**.

Not a defect against any of `#0349`'s criteria, which say "every *named* type",
and the construct is exotic — which is why it was handed forward rather than
bounced, matching how `#0346`'s review disposed of `#0350` and `#0351`.

**Note the alias case that is NOT a defect**: `type FeedCache = Renderer` and
`type FeedCache = *Site` are merely new spellings of a type the loop already
checks, and `#0337`'s third review already ruled that a legitimate survival.
Do not "fix" those into failures.

## Root cause

`#0349`'s replacement guard asserted `tn.Type().(*types.Named)` on every
package-scope name. Under `gotypesalias=1` (the Go default), a `type X = ...`
alias declaration's `Type()` returns `*types.Alias`, not `*types.Named`, so
the assertion silently `continue`d past it — including when the alias names a
type literal (`type FeedCache = struct{ *Site; cached []byte }`) that is a
real, compiling satisfier of `interface{ Invalidate() }`. The retired AST
scan caught this construct (it inspected any `*ast.TypeSpec` whose `Type` was
a struct literal, alias or not); the `go/types` replacement did not, because
it only ever asked "is this a `*types.Named`."

Separately, two sentences in the guard's doc comment stated things `#0349`'s
own review had already measured false — "export-data backed" (it
source-type-checks; an export-data-backed load of the same package costs
5.4s/240MB cold against the guard's 1.3s/6.8MB) and "there is nothing left for
a hand-reviewed allowlist to guard" (overstated by exactly this alias case) —
and a third sentence, present byte-parallel in both this file and
`sitemap.go`, overstated the half-invalidation's relationship to `#0319`.

## Fix

**Criterion 1.** Added a `*types.Alias` branch, checked before the
`*types.Named` assertion, inside a new `scanInvalidatorSatisfiers(scope
*types.Scope, invalidateOnly *types.Interface) (got map[string]bool,
concreteTypesChecked int)` helper (factored out of `TestInvalidatorSatisfierSet`
so a second, permanent test can call the identical scanning logic rather than
re-deriving it — CLAUDE.md §8's "a guard's oracle must not be the same bytes
as its subject"). The branch calls `types.Unalias(tn.Type())` and then:

- `continue`s if the result is a `*types.Named`, or a `*types.Pointer` whose
  element is a `*types.Named` — `type FeedCache = Renderer` and `type
  FeedCache = *Site` are new spellings of a type the loop already checks under
  its own name;
- `continue`s if the result's `Underlying()` is `*types.Interface` — an alias
  to a declared interface is a seam, not a concrete type joining one, mirroring
  the existing declared-interface rule for `*types.Named`;
- otherwise increments `concreteTypesChecked` and records the name in `got` if
  `types.Implements(target, invalidateOnly) ||
  types.Implements(types.NewPointer(target), invalidateOnly)` — checking both
  forms because `target` here is not a `*types.Named`, so promotion from an
  embedded *value* field lands only on the pointer form, unlike the
  `*types.Named` case where the pointer form alone is sufficient.

**Standing regression (criterion 3).** Added
`TestInvalidatorSatisfierSet_AliasToTypeLiteral`, which type-checks a small
synthetic in-memory source file (`go/types.Config.Check`, no `packages.Load`,
no dependency on `internal/seo`'s own contents) declaring a `Site` with an
`Invalidate()` method, a `FeedCache` alias to `struct{ *Site; cached []byte
}`, and an `AliasToNamed` alias to `Site` — then calls the shared
`scanInvalidatorSatisfiers` and asserts `FeedCache` is reported (the fix
holds) and `AliasToNamed` is not double-counted under its own name (the N2
survival still holds). Runs in milliseconds and is a permanent part of
`go test ./internal/seo/...`, not something exercised only in a throwaway
mutation worktree.

**Criterion 2.** Rewrote the "export-data backed" parenthetical with the
measured mechanism and numbers (source-type-checked, 1.3s/6.8MB vs.
5.4s/240MB for an export-data-backed load of the same package), and appended
a correction to the "nothing left for a hand-reviewed allowlist to guard"
sentence naming the one remaining gap this commit closes and how (structurally,
via `types.Unalias`, not an allowlist).

**Criteria 9–11 — the `#0319` attribution.** Read `#0319` in full (see
`## Verification` below for what it says). It was filed because
`AdminCampaignArchiveHandler` and the send worker's completion path
invalidated **nothing**, leaving both the sitemap and the per-path meta cache
stale, with the sitemap as the headline symptom (`#0319`'s Description leads
with "`sitemap.xml` keeps advertising a just-**withheld** campaign's URL").
The half-invalidation a bare `*Sitemap` produces is the opposite shape: it
*clears* the sitemap cache and leaves only the meta cache stale — the
meta-cache half of `#0319`'s staleness class, not the sitemap staleness
`#0319` led with, and not identical to what `#0319` was filed to fix. Replaced
the phrase "the exact failure `#0319` was filed to fix" with "the meta-cache
half of `#0319`'s staleness class, not the sitemap staleness `#0319` led
with" — byte-identical in both `invalidator_satisfier_guard_test.go` and
`sitemap.go`, preserving the files' deliberate parallelism. The `sitemap.go`
edit changes no code; verified comment-only with a purpose-built tool (see
`## Verification`).

## Added by `#0351`'s review, 2026-08-31

That review resolved `#0351` and found a third false claim in the same doc
comment — one that must be fixed **in two files at once**.

**`"the exact failure #0319 was filed to fix"` overstates `#0319`.** The phrase
appears in both `internal/seo/invalidator_satisfier_guard_test.go` and
`internal/seo/sitemap.go`, attributing to `#0319` the
sitemap-cleared/meta-stale half-invalidation that a bare `*Sitemap` produces.

But `#0319` was filed because `AdminCampaignArchiveHandler` and the send worker
invalidated **nothing**, leaving *both* caches stale, and its headline symptom
is a stale **sitemap**. The half-invalidation *clears* the sitemap and reopens
only the **meta-cache** half. It is half of `#0319`'s staleness class — and not
the half `#0319` leads with.

The mechanism around it is correct and verified: `site.go:48`'s `Invalidate` is
`renderer.Invalidate()` + `sitemap.invalidate()`, so a bare `*Sitemap` runs only
the second. Only the `#0319` attribution is wrong.

**Both copies must change together.** They are byte-parallel by design —
`#0337` and `#0351` deliberately built that consistency, and `#0351` could not
fix this because it was barred from touching `sitemap.go` and criterion 2
required the guard's phrasing to match it. So this pass edits `sitemap.go` too.

Low severity, but this comment pair is the project's canonical record of the
`#0325` incident, and it has now been wrong in print twice.
