## Description

Render a campaign without sending it, and deliver a real test message to an admin address before the campaign can go out.

## Root cause

Not a bug fix — new feature work. Before this issue, `#0045`'s Preflight
gate already checked `test_sent_at IS NOT NULL` (`no_test_send`), but
nothing in the codebase ever wrote that column, so **every** campaign was
permanently stuck at that one preflight failure — a campaign could never
actually leave `draft`. There was also no way for an operator to see a
campaign's rendered output at all before scheduling it.

## Fix

Two new endpoints in a new file, `internal/handlers/admin_campaign_preview.go`
(`AdminCampaignPreviewHandler`), following `AdminCampaignAudienceHandler`'s
precedent (`#0044`) rather than growing `AdminCampaignsHandler` further:

- **`POST /admin/campaigns/{id}/preview`** — loads the campaign's stored
  row, renders it through the injected `mailing.CampaignRenderer` (the same
  seam `#0045`'s `SendStore`/`Worker` use — in production,
  `mailing.MarkdownCampaignRenderer{}`, i.e. the real goldmark pipeline) with
  a non-functional sentinel manage token (`PREVIEW-DRY-RUN`), and returns
  `{"subject", "html", "text"}`. Never touches `email_sends`,
  `email_campaigns`, or `subscribers`.
- **`POST /admin/campaigns/{id}/test`** — renders the same way, assembles a
  `mailing.Message` the same way `mailing.BuildCampaignMessage` would
  (subject, HTML/text bodies, and the RFC 8058
  `List-Unsubscribe`/`List-Unsubscribe-Post`/`List-Id` headers via the
  already-exported `mailing.CampaignHeaders`) — but goes through the
  handler's own injected `render` seam rather than calling
  `BuildCampaignMessage` directly, so both endpoints share one renderer
  dependency and one is fake-able in tests. Delivers it through the real
  `mailing.Mailer` and, on success, calls the new
  `CampaignStore.MarkTestSent` to stamp `test_sent_at = now()`, then writes
  an `email_campaign.test_sent` audit row.

**Neither route accepts a request body — structurally, not by convention.**
`decodeJSON` is never called by either handler. `#0047`'s carried-in
constraint says preview/test must render the *stored* row, never an
unsaved client override; rather than accept a body and ignore particular
fields (a rule a later edit could forget to maintain), there is simply no
code path that reads one. Proved by mutation (see `## Verification`):
temporarily wiring a `subject`/`body_md` override into `Preview` made
`TestAdminCampaignPreview_Preview_IgnoresRequestBody` fail immediately.

**Test-send recipient: always the requesting admin's own address, never a
client-supplied one — a deliberate narrowing of this issue's own acceptance
criterion.** The criterion says "sends one real message to a specified
admin address"; an admin-suppliable destination would turn this endpoint
into a session-authenticated open relay for attacker-controlled HTML (the
campaign body itself is already attacker/admin-controlled the moment they
can edit it). The recipient is always `middleware.AuthUser.Email` — the
session `RequireAdmin` already authenticated — read fresh on every call,
never a request field. Proved by mutation: hardcoding a different `To`
address broke `TestAdminCampaignPreview_Test_SendsToRequestingAdminOnly`.

**Why the message goes to a dedicated synthetic subscriber row, not the
admin's real one, per this issue's own Notes.** A real, working
`manage_token` is required (so the unsubscribe link is genuinely
clickable), and the only place `FindByManageToken` resolves one is the
`subscribers` table. Reusing (or creating) a row *at* the admin's own email
address is unsafe two ways: (1) if that admin also happens to be a genuine
list member, clicking the test message's unsubscribe link would unsubscribe
their real subscription; (2) a `status='active'` row at that address would
count toward a real "all" campaign's audience. `ensureTestRecipient`
finds-or-creates one synthetic row per admin
(`campaign-test+admin-<id>@internal.opencircuitsf.test` — `.test` is
RFC 2606-reserved and never resolves), left at `status='pending'` for its
entire life so it is excluded from every audience predicate (all of
`internal/mailing`'s eligibility SQL filters `status = 'active'`
unconditionally), and rotates a fresh `manage_token` onto it before every
test send. The `Message.To` is still the admin's real inbox — only the
token is anchored to the disposable row. Proved by
`TestAdminCampaignPreview_Test_UsesDedicatedRecipientRow_NotARealSubscriber`,
which seeds the SAME address as a real, confirmed, active subscriber,
test-sends, confirms the embedded token belongs to a *different* row, and
confirms simulating a click on that token never changes the real
subscriber's status.

**What `Preflight` subset a test send requires: none of the ten codes,
called out explicitly rather than silently skipped.** `Test` does not call
`mailing.Preflight` at all.

- `physical_address_missing` / `reply_to_missing` / `list_domain_unset` are
  deploy-configuration prerequisites for a *real* send to subscribers
  (CAN-SPAM §7704 for the address; PRD §6.6 for reply-to). Requiring them
  here would make it impossible to review a campaign's rendering before
  that configuration lands — backwards, since testing early is exactly how
  an operator notices the address is still blank. `CLAUDE.md` §9's
  `physical_address` restriction is about the send **worker's** gate (the
  one that actually delivers to subscribers) staying unbypassable from the
  UI; a test send to the operator's own inbox is not the "commercial email
  message" CAN-SPAM regulates delivery of, and the worker's own,
  unconditional copy of `Preflight` is completely untouched by this issue —
  a campaign that has been test-sent a hundred times still cannot leave
  `scheduled` without `physical_address` set.
- `no_test_send` is circular here — this *is* the test send.
- `audience_invalid` / `empty_audience` describe the real audience; `Test`
  never touches it.
- `subject_empty` / `body_empty` / `body_render_failed` are not enforced as
  a separate check — letting an operator test-send an empty subject/body is
  the useful feedback loop the feature exists for. A genuine render failure
  still surfaces (422), not because this issue re-implements
  `body_render_failed`, but because rendering itself cannot succeed without
  one.

The one thing `Test` *does* require, unconditionally, is that a mailer is
actually configured: `h.mailer == nil` (`MAILER_NOOP=true` with no real
`SendStore`-backing configuration wired, or a deploy/test that never wired
one in) answers `503` before touching the database at all — not a
`Preflight` code, but the same operational precondition `#0027`'s
`MAILER_NOOP` guard already enforces for every other outbound path. Proved
by mutation: removing the nil check made the handler panic with a nil
pointer dereference on the interface call (see `## Verification`) — the
guard is load-bearing, not decorative.

**Fidelity decision: a test send goes through the identical
render+header-assembly path a real send uses, including the RFC 8058
headers.** The alternative — a simplified test-only rendering path — was
rejected: a test that renders differently from the real thing tells the
operator little. The one deliberate difference from a real send is the
recipient-safety mechanism above (the dedicated synthetic row), which does
not change what is rendered or which headers are attached, only which
`manage_token` anchors the unsubscribe link.

**`Campaign.TestSentAt` / `campaignView.TestSentAt` newly exposed.** The
`test_sent_at` column has existed since `#0045`'s migration `000018`, but
`CampaignStore`'s `campaignColumns`/`scanCampaign`/`Campaign` struct never
read it, and `#0041`'s `campaignView` never surfaced it (both explicitly
flagged as "deferred — column doesn't exist yet" in `#0041`'s own Fix).
Since this issue is the one that starts writing the column, it also starts
reading and surfacing it — `CampaignStore.MarkTestSent` is the sole writer;
`#0045`'s `SendStore.GatherPreflight` continues to read the column with its
own direct query, unaffected.

**`mailing.ResolveFromHeader` extracted from `Worker.resolveFromHeader`.**
Same `default_from_name` → `Message.From` composition (blank stays blank;
refuses anything but printable ASCII with no `"`/`\`), now a standalone
exported function the test-send path calls directly so its `From` header is
byte-identical to what a real send would produce, without duplicating the
safety checks or constructing a full `Worker`. `Worker.resolveFromHeader`
is now a one-line wrapper; every existing `worker_test.go` call site
compiles and passes unchanged.

**Wiring.** `adminRoutes`/`mountAndServe` (`cmd/opencircuit/main.go`) gained
`adminCampaignPreviewH *handlers.AdminCampaignPreviewHandler`, nil-guarded
exactly like `adminCampaignAudienceH` (omitted under `STORAGE=json`). In
production it is constructed with `sesSender` — the exact same
`mailing.Mailer` the send worker uses, including the log-only
`noOpMailingMailer` under `MAILER_NOOP=true` — so a test send behaves like
every other outbound path in this project under that flag, rather than
introducing a second, special "unconfigured" state. The ripple through
`cmd/opencircuit`'s eight other `mountAndServe` call sites (seven wiring
test files) follows `#0041`'s own precedent exactly: each passes `nil` with
a `not exercised by this test` comment, except `admin_wiring_test.go`,
which wires a real handler with a deliberately **nil mailer** — so its
admin-session case for `POST .../test` reaches the real handler and answers
`503` (proof enough that `RequireAdmin` let the request through, the same
standard that file already applies to `POST /admin/subscribers`'s `503`
when `manualAdd` is nil) without attempting a real network call from a
wiring test.

### Second pass (`498ebb6`) — addressing the review's bounce

The phase-3 review (see `## Review notes` below) accepted two of this
issue's three design decisions — no `Preflight` codes for a test send, and
the session-admin-only recipient — and bounced on the third: the "dedicated
synthetic subscriber row" mechanism itself. It kept the row out of every
audience (verified, and unchanged by this pass) but not out of the `#0032`
admin subscribers screen, and its address format was an enumerable
hard-bounce vector against the public subscribe endpoint. Both are fixed
here; nothing from "What passes" in the review notes was reworked.

**A. Admin-screen invisibility — the review's preferred option, taken.**
Migration `000019` (append-only; `000018` untouched per `CLAUDE.md` §1) adds
`subscribers.synthetic boolean NOT NULL DEFAULT false`. `ensureTestRecipient`
now creates the recipient row with `NewSignup{..., Synthetic: true}`.
`subscribers.Store.StatusCounts` and `subscribers.Store.List` both exclude
`synthetic = true` **unconditionally** — not exposed as a `ListFilter`
option, so the `#0032` admin screen can never be made to show one no matter
what it filters by. Deliberately **not** applied to `FindByEmail`,
`FindByManageToken`, `GetByID`, or `audienceWhere`: the first three must
keep resolving the row exactly like a real one (that's what makes the test
message's unsubscribe link genuinely clickable — this issue's own Notes),
and `audienceWhere` was already correct (`status = 'active'` equality) and
did not need the flag. This is the "mark them in the schema" option the
review called out as preferred over a domain-string comparison scattered
across call sites, and over dropping the `subscribers` row entirely (which
would have required rebuilding how `FindByManageToken` resolves a token).

**B. The enumerable hard-bounce vector — closed at the domain, not the row.**
`internal/subscribers` now exports `ReservedTestEmailDomain` (the single
source of truth for `internal.opencircuitsf.test`, replacing the
locally-duplicated constant `admin_campaign_preview.go` used to define) and
`IsReservedTestEmail(email) bool`. `SubscribeHandler.processMutateJob`
(`subscribe.go`) checks it immediately after the existing `isBot` check and
silently no-ops — same as `isBot`/`suppressed` — for **any** address at that
domain, not only ones a synthetic row already happens to exist for: the
enumeration risk (small, sequential admin ids) lives in the domain string
being public, not in a particular row's state, so checking "does a synthetic
row already exist here" would have left a brand-new admin id's address still
mailable on its first probe. This required no change to the uniform `202`:
`#0088` (landed before this issue) already moved every branch-dependent
write — including `sendConfirmation`'s enqueue — onto an async queue
(`mutateQueue`) drained strictly **after** `Subscribe` has written the
response. The new check sits inside that already-deferred path, so it
cannot introduce an observable branch in the endpoint's response
(`CLAUDE.md` §9; `#0026`; `#0088`) — proven by mutation, see
`## Verification`.

**C. `gofmt` regression.** `internal/handlers/admin_campaigns.go`'s
`CreatedAt`/`UpdatedAt` field alignment, dirtied by `5ec8774`, is restored by
a plain `gofmt -w`. No other file needed it — `static_test.go` and
`sesnotify/verify_test.go` were already unformatted before `5ec8774` and are
untouched here, per the review's own note that they are not this issue's
problem.

**D. Five stale doc-comment test names.** `admin_campaign_preview.go`'s
package comment cited five `TestPreview_*`/`TestTest_*` symbols that were
never shipped (the actual tests use the `TestAdminCampaignPreview_*`
prefix). All five references are corrected to the real names; one — the
"no unsaved-body override" reference for `Test` — now points at the test
added for finding E below instead of a name that never existed.

**E. Missing `Test`-endpoint body-override coverage.** Added
`TestAdminCampaignPreview_Test_IgnoresRequestBody`, `Test`'s counterpart to
the existing `TestAdminCampaignPreview_Preview_IgnoresRequestBody`: sends a
body claiming a different `subject`/`body_md` and asserts the mailer
actually received the **stored** row's content, not the injected one.
`TestAdminCampaignPreview_Test_SendsToRequestingAdminOnly` already sent a
similar body but only ever asserted on the recipient, not on whether the
override reached the rendered content — this was a genuine gap the stale
doc comments had implied was already covered.

**New regression test for A**:
`TestAdminCampaignPreview_Test_SyntheticRecipientInvisibleOnAdminScreens` —
snapshots `StatusCounts` and `List`'s total before a real test send, runs
the send through the real mux, and asserts both are unchanged and that
`List` filtered to the synthetic recipient's own address returns zero rows.
Confirms the row exists and is marked `Synthetic` first, so this isn't a
test that nothing happened.

**New regression test for B**: `TestSubscribe_ReservedTestDomain_NoActionTaken`
(`subscribe_test.go`) covers both the brand-new-address branch and the
existing-synthetic-row branch, asserting the uniform `202`, no subscriber
row created (first branch), and zero mailer sends in either case.
