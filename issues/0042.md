## Description

One authored Markdown source produces both the HTML part and the plain-text alternative, with per-recipient token substitution.

### What must change

**`writeTextInline`'s `*ast.Link` case checks and emits the raw
`v.Destination`; goldmark's HTML renderer checks and emits the *normalized*
destination.** `renderer/html/html.go`'s `renderLink` is:

```go
dest := util.URLEscape(n.Destination, true)   // UnescapePunctuations +
if r.Unsafe || !IsDangerousURL(dest) {        // ResolveNumericReferences +
    _, _ = w.Write(util.EscapeHTML(dest))     // ResolveEntityNames, then %-escape
}
```

`campaign_markdown.go` does `dest := string(v.Destination)` and calls
`isDangerousLinkURL(dest)` on that. Same function, different input — so the
`## Fix` section's claim that the check is "applied identically in
`writeTextInline`'s `*ast.Link`/`*ast.AutoLink` cases" and the package doc's
"the two parts can never disagree about which links are live" are **both false
as written**. The session fixed the *presence* of the check, not the
*normalization* of what it checks. Two demonstrations, printing the raw and
normalized destination side by side:

| Markdown | raw dest (text path) | normalized (HTML path) | HTML output | text output |
|---|---|---|---|---|
| `[x](javascript&#58;alert(1))` | `javascript&#58;alert(1)` — safe | `javascript:alert(1)` — **dangerous** | `<a href="">` | `x <javascript&#58;alert(1)>` |
| `[x](javascript\:alert(1))` | `javascript\:alert(1)` — safe | `javascript:alert(1)` — **dangerous** | `<a href="">` | `x <javascript\:alert(1)>` |

**This is not a live exploit and the next pass should not over-rotate on it.**
The strings that leak into the text part are entity- or backslash-encoded, so
no mail client's plain-text linkifier will turn `javascript&#58;alert(1)` into
a working `javascript:` URL. I probed for a form whose *raw* spelling is both
clickable and dangerous and could not construct one — any destination
containing a literal `javascript:`/`vbscript:`/`file:`/`data:` prefix is caught
by the raw check already. The defect is the broken invariant, not a script
running in someone's inbox.

**The same root cause breaks ordinary links, which is the more likely way this
bites in production.** The text part prints the un-normalized destination, so
it can show a recipient a URL that differs from the one the HTML part links to:

| Markdown | HTML `href` | text part |
|---|---|---|
| `[docs](https://ok.example/s?a=1&amp;b=2)` | `...?a=1&b=2` | `<https://ok.example/s?a=1&amp;b=2>` |
| `[x](https://ok.example/x?q=a&copy;b)` | `...?q=a%C2%A9b` | `<https://ok.example/x?q=a&copy;b>` |
| `[x](<https://ok.example/a b>)` | `.../a%20b` | `<https://ok.example/a b>` |
| `[x](https://ok.example/a\_b)` | `.../a_b` | `<https://ok.example/a\_b>` |

A text-part reader copy-pastes the second column and lands somewhere else — or
nowhere. This issue's own `## Notes` say "Links in particular have to survive
as visible URLs or the text part is worse than useless"; a URL with a stray
`&amp;` or an unescaped space in it does not survive in any useful sense. Any
query string containing an entity-shaped substring (`&amp;`, `&copy;`,
`&sect;`, `&para;`, `&reg;` — a `sect` or `copy` query parameter is enough)
hits this.

**The fix is small and local.** Normalize once and use the result for both the
danger check and the emitted URL, so the two parts are byte-identical about
every destination — e.g. `dest := util.URLEscape(v.Destination, true)` in the
`*ast.Link` case (and the matching treatment for `*ast.AutoLink`, which goes
through `renderAutoLink`'s own escaping). Percent-escaping costs a little
readability on non-ASCII URLs (`café` → `caf%C3%A9`); if that trade is
unwanted, resolve references without percent-escaping for *display* but still
run the danger check on the fully normalized bytes. Either is fine — what is
not fine is the two paths seeing different bytes. Please also:

- add a regression test pinning HTML/text agreement over a table of
  destinations including `javascript&#58;alert(1)`, `javascript\:alert(1)`,
  and `https://ok.example/s?a=1&amp;b=2`;
- correct the package doc, the `## Fix` section, and the commit's claim that
  the check is applied identically, so the next reader is not misled.

### Second pass (`1063ef7`) — fix for the normalization drift

Root cause, precisely: goldmark's HTML renderer computes
`dest := util.URLEscape(n.Destination, true)` (Link) /
`util.URLEscape(n.URL(source), false)` (AutoLink) — resolving backslash
escapes, numeric character references, and named entities, then
percent-escaping — and runs `IsDangerousURL`/emits the href from that single
normalized value. `writeTextInline`'s `*ast.Link`/`*ast.AutoLink` cases
called `isDangerousLinkURL` and emitted the text-part URL from
`string(v.Destination)` / `string(v.URL(source))` — the **raw**, un-normalized
source bytes. Same `isDangerousLinkURL`/`IsDangerousURL` function, different
input, so the two paths could and did disagree.

**Fix:** added `normalizedLinkDestination(raw []byte, resolveReference bool)
string` in `internal/mailing/campaign_markdown.go` — the single call this
package now makes to compute a link/autolink's normalized destination,
mirroring goldmark's own `util.URLEscape` calls byte for byte (`true` for a
`*ast.Link`'s `Destination`, `false` for an `*ast.AutoLink`'s
`URL(source)`, matching which of goldmark's two call sites each stands in
for). Both the `*ast.Link` and `*ast.AutoLink` cases in `writeTextInline`
now call it once per node and reuse the single returned value for both the
`isDangerousLinkURL` check and the emitted `<url>` — there is exactly one
normalization call site per node, so the check and the emitted text cannot
read different bytes without both being changed together.

**Correcting the false claims the review flagged:** the package doc's
"the two parts can never disagree about which links are live" (now on
`isDangerousLinkURL`'s doc comment, revised) and this section's now-struck
"applied identically" claim above were true of *whether* the check ran, not
of *what bytes* it ran against. Both are now accurate: `isDangerousLinkURL`
requires its argument to already be normalized by
`normalizedLinkDestination`, and the two call sites in `writeTextInline` are
the only two producers of that argument in this package, so the invariant
holds structurally rather than by convention. The commit message for
`1cc840d` carried the same overstated claim; it is not amended (commits are
immutable), but this issue file — the durable record — is corrected here.

**Plain-text heading nit — left alone, deliberately, for this pass.** The
review flagged `#`/`##`/`###` headings rendering as bare lines as a
non-blocking quality nit, optional to fix. Not touched here: it is
unrelated to the bounce reason, and any change to `renderTextBlock`'s

## Root cause

Not a bug — this is Phase 5's rendering engine. `internal/mailing` had
templates for transactional mail (`#0028`) and RFC 8058 headers (`#0035`)
but nothing that turned an admin-authored campaign body (Markdown, per PRD
§6.6) into the two MIME parts a send actually needs. `#0045` (the send
worker) and `#0046` (preview/test-send) both depend on this seam and
neither could be built without it.

## Fix

Two new files in `internal/mailing`:

- **`campaign_markdown.go`** — the Markdown → HTML/text engine.
  `RenderMarkdownHTML(md string) (string, error)` and
  `RenderMarkdownText(md string) (string, error)` are the two low-level,
  exported primitives; `RenderMarkdownText` is a hand-written AST walker
  (not a second pass through goldmark's HTML renderer with tags stripped),
  because "strip the tags" and "genuinely readable" are different goals —
  see the plain-text decisions below.
- **`campaign_render.go`** — the orchestration seam.
  `CampaignRenderInput` (Subject, Preheader, BodyMarkdown, BaseURL,
  ManageToken, PhysicalAddress — field names match `issues/0045.md` §5's
  plan exactly), the `CampaignRenderer` interface with a `Campaign(...)
  (html, text string, err error)` method, `MarkdownCampaignRenderer` (the
  production implementation), and `RenderCampaign` (the actual work).

**Markdown library: `github.com/yuin/goldmark` v1.8.5.** Nothing else was
already in `go.sum`. It's the de facto standard Go CommonMark
implementation (Hugo, Docker's docs toolchain, most Go static-site
generators use it), has zero transitive dependencies of its own (`go get`
added exactly one line to `go.sum` beyond goldmark itself — none), and is
actively maintained. `go mod tidy` correctly promotes it to a direct,
non-indirect requirement since `internal/mailing` imports it directly.

**Raw HTML decision — escaped/suppressed, not passed through, and no
sanitizer allowlist needed because none is used:** `campaignMarkdown` is
configured *without* `html.WithUnsafe()`, which is goldmark's own default
("safe") mode. Confirmed against goldmark's source
(`renderer/html/html.go`): `renderRawHTML`/`renderHTMLBlock` only emit
anything when `r.Unsafe` is true, and `renderLink`/`renderImage` check
`html.IsDangerousURL` and drop the destination when unsafe mode is off.
So a literal `<script>`/`<iframe>`/etc. typed into the campaign body is
replaced with an HTML comment (`<!-- raw HTML omitted -->`), never
rendered as live markup; a `javascript:`/`vbscript:`/`file:`/`data:` link
destination is dropped (empty `href`) the same way. No custom sanitizer
or allowlist was written — I'm not passing any raw HTML through, so
there's nothing to allowlist; this is entirely goldmark's own vetted
default. Ordinary literal `<`/`>`/`&` characters in body text are
HTML-escaped as normal (`TestRenderMarkdownHTML_TextIsHTMLEscaped`).

**Images are disallowed entirely, not scheme-restricted.** A separate,
deliberate decision beyond raw-HTML suppression: `campaignImageRenderer`
overrides goldmark's default `ast.KindImage` rendering (registered at
priority `0`, which — per goldmark's renderer registering highest-priority
first and letting the *last* registration for a kind win — beats the
default `html.Renderer`'s priority `1000`) so **no** `![alt](src)`
survives as an `<img>`, regardless of scheme. There's no mechanism in this
project for hosting an image a campaign body could legitimately
reference, so the only images that could ever appear are third-party
URLs — exactly the "open-tracking pixel by another name" this issue's
brief and CLAUDE.md §9 forbid. The alt text (if any) survives as plain,
escaped text (`[image not included: …]`) so the author's content isn't
silently dropped without a trace.

**Plain-text rendering is a genuine AST walk, not tag-stripped HTML:**

- Links render as `text <url>` (the acceptance criterion's exact form),
  or just `<url>` when the link text equals the URL (a bare autolink) —
  avoids the redundant `https://x <https://x>` case.
- Headings/paragraphs/blockquotes render as blank-line-separated blocks;
  lists render with `- `/`N. ` markers (honoring the source's own ordered
  start number) with continuation lines indented under the text, not the
  marker; code spans keep backticks, code blocks are indented 4 spaces
  and never word-wrapped; emphasis survives as `*strong*`/`_em_` rather
  than silently vanishing.
- Images and raw HTML are omitted in text too, for the same reason as
  HTML: **the two parts must never disagree about what the campaign
  fetches or renders.** This caught a real bug during implementation (see
  Gotchas): an early version applied goldmark's dangerous-URL check only
  on the HTML side, so `[x](javascript:alert(1))` came out neutralized in
  HTML but leaked verbatim as `<javascript:alert(1)>` in text.
  `isDangerousLinkURL` (wrapping `html.IsDangerousURL`) was applied in both
  `writeTextInline`'s `*ast.Link`/`*ast.AutoLink` cases — **but, as the
  review below caught, on differently-normalized bytes in each path,
  which is a distinct and narrower bug than the one just described. See
  "Second pass" below for the corrected claim and the fix.**
- Line endings are `\r\n` throughout, matching `templates.go`'s
  `renderText` and the rest of this project's plain-text sends.

**Token substitution and physical address:** `RenderCampaign` builds
`manageURL`/`unsubscribeURL` from `BaseURL + "/preferences?token=" +
ManageToken` / `BaseURL + "/unsubscribe?token=" + ManageToken` — the same
construction the five transactional templates already use — and passes
them into both `wrapCampaignHTML` and `wrapCampaignText`, which each
include both PRD §6.5 labels verbatim ("Manage your interests",
"Unsubscribe from everything") and append `PhysicalAddress` when
non-blank. **Substitution failures are hard errors:**
`strings.TrimSpace(in.ManageToken) == ""` returns `ErrMissingManageToken`
before any rendering happens (no partial document); the same treatment is
applied to `BaseURL` (`ErrMissingBaseURL`) since a blank base URL produces
the identical failure mode — a relative, un-resolvable footer href — even
though only the token case is named in the acceptance criteria.
`RenderCampaign` also wraps its body-render step in a `recover()` that
converts any panic into a typed error, since `#0045`'s plan calls this
during preflight with the sentinel token `"PREFLIGHT-DRY-RUN"`
specifically to surface `body_render_failed` without crashing the worker.

**Determinism:** no map iteration, no time-of-day, no randomness anywhere
in the render path (goldmark's parser and this package's own AST walk are
both pure functions of the input bytes). Pinned by
`TestRenderMarkdownHTML_Deterministic`, `TestRenderMarkdownText_Deterministic`,
and `TestRenderCampaign_Deterministic` (each renders the same input twice
and compares byte-for-byte), plus the golden-file tests themselves.

**Seam left for `#0043` ("Build the campaign HTML email template"), named
explicitly rather than silently:** `wrapCampaignHTML` in `campaign_render.go`
produces a complete, valid, mail-safe HTML document — single-column table
layout, inline styles only, explicit `bgcolor` on the outer table, a
footer with both required links and the address — but does **not** carry
the dark/terminal brand skin (`colorPageBG`/`colorCardBG`/mono headers
from `templates.go`) or the max-width-600px/multi-client verification
`#0043`'s acceptance criteria call for; it currently uses a plain

Applying inline brand styling to arbitrary Markdown-shaped HTML at N

already describe as its job. `#0043` should replace `wrapCampaignHTML` (or

## Gotchas

- **A real HTML/text-parity bug was caught by manual probing before any
  permanent test existed**, and is now pinned by
  `TestRenderMarkdownText_DangerousLinkDropsURLButKeepsText`,
  `TestRenderMarkdownText_DangerousAutolinkDropsEntirely`, and
  `TestRenderCampaign_RawHTMLNeverReachesEitherPart`'s href/src assertion:
  an early version of `writeTextInline`'s `*ast.Link` case had no
  dangerous-URL check at all, so `[click me](javascript:alert(1))` came
  out correctly neutralized in the HTML part (`<a href="">`) but leaked as
  `click me <javascript:alert(1)>` verbatim in the text part — exactly the
  "two parts disagree about what the campaign fetches" failure this file's
  own package doc warns against. Fixed by applying goldmark's
  `html.IsDangerousURL` identically on both the `*ast.Link` and
  `*ast.AutoLink` text-mode cases.
- **One test assertion was initially wrong, not the code.** An early
  `TestRenderCampaign_RawHTMLNeverReachesEitherPart` asserted the
  substring `"evil.example"` was absent from the rendered output entirely.
  That's too strict: the literal text between suppressed `<script>` tags
  (an attacker's URL, typed as plain copy) surviving as inert, non-clickable
  text is correct and expected — identical to what `html.EscapeString`
  alone would produce for the same input. Fixed the assertion to check for
  a live `href="`/`src="` on that domain instead, which is the actual
  property that matters. Documented inline in the test so a future reader
  doesn't "fix" the render to satisfy the wrong check.
- **`go get` alone left goldmark marked `// indirect`** in `go.mod` even
  though `internal/mailing` imports it directly — `go mod tidy` was needed
  afterward to reclassify it. Worth remembering for any future dependency
  addition in this repo: `go get <pkg>` is not sufficient by itself.
- **goldmark's `renderer.Renderer` overrides "the last-registered wins"
  by priority ascending, not descending** — a node renderer registered at
  a *lower* priority number overrides one at a higher number (verified by
  reading `renderer/renderer.go`'s `Render` method directly, then
  confirmed by mutation-testing the priority value; see Verification item
  2). This is the opposite of what "priority" intuitively suggests and is
  easy to get backwards; documented at the registration site in
  `campaign_markdown.go` so nobody re-derives it from scratch.

## Notes

PRD §6.6. Passing raw HTML through from Markdown is an injection path into every recipient's inbox — escape it.

The plain-text part must be genuinely readable, not HTML with the tags stripped. Links in particular have to survive as visible URLs or the text part is worse than useless.

A missing token producing an empty `href` means an unsubscribe link that silently does nothing — which is a compliance failure, not a cosmetic bug. Fail loudly.
