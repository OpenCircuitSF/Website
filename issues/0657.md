## Description

The user wants to schedule posts to Bluesky and Mastodon outside the existing event-focused Outreach feature. The first use is the short topic guides under `/guides/<slug>` (`#0656`). Each topic in `web/src/lib/topics/topics.ts` already carries a `post` field with ready-made post copy.

Reuse the existing Bluesky and Mastodon posting code and stored credentials where that makes sense. Nothing has been designed yet.

**This issue starts with a planning pass.** The plan must lay out the design options and list the product questions only the user can answer, including:

- Approval flow: whether a scheduled post publishes automatically or waits for confirmation.
- Recurring posts, or one-off only.
- Image attachments, for example the guide's OG card, with alt text.
- Which accounts post.
- Where the post copy lives: `topics.ts`, the database, or editable in the admin.

## Open questions for the user

Each has a recommended default. The plan below builds the defaults; the acceptance criteria mark where a different answer changes the work.

1. **Approval flow.** When a scheduled post's time comes, should it publish automatically, or wait for you to confirm it in the admin? *Recommended: publish automatically.* Scheduling is already a deliberate act in the admin, drafts never post, and it matches how Outreach posts work today. A confirm step means a post that falls due while you are away sits unposted until you look.
2. **Recurring or one-off.** Should a guide post be one-off, or repeat on a schedule (for example, every guide re-shared once a quarter)? *Recommended: one-off for now, plus a "Schedule again" button that copies a posted post into a new draft.* Recurring posts need a schedule rule, rotation, and a guard against posting identical text twice, which both platforms frown on; it can be a follow-up once the one-off flow has been used.
3. **Images.** Should posts attach an image (such as the guide's OG card) with alt text, or rely on the link preview card? *Recommended: link preview card only.* On Bluesky the guide's OG card becomes the card's thumbnail; on Mastodon the server builds the card from the guide's OG tags. Both platforms drop the link card when an image is attached, and link-card thumbnails have no alt-text field. Attaching images with alt text is possible but needs new upload code for both platforms (see `### Images`, option B).
4. **Which accounts.** Should guide posts go from the same Bluesky and Mastodon accounts Outreach uses (Settings → Outreach), or from different ones? *Recommended: the same accounts.* The credentials already exist, are tested from Settings, and can be changed without a restart. A second set of accounts needs new credential storage and a second Settings group.
5. **Where the copy lives.** Should post text come only from `topics.ts` (change it by deploying), only from the database, or start from `topics.ts` and be editable per post in the admin? *Recommended: start from `topics.ts`, editable per post.* The guide's `post` field pre-fills each new draft; whatever you edit is saved on that post. Changing `topics.ts` later changes new drafts only, never a post already drafted or scheduled.
6. **Link tracking** (not in the original list, but it decides the link). Should the link be the guide's own URL with UTM tags, or a tracked `go.opencircuitsf.com` short link like Outreach uses? *Recommended: the guide's own URL with UTM tags.* It needs no ShortLinks call and shows the real address. A short link would add click counts in ShortLinks, at the cost of one more dependency per post.

## Plan

### Summary

A new, self-contained "guide posts" feature: its own table, its own store and publisher in a new package `internal/guideposts`, its own outbox kind, its own admin API and admin section. It reuses, without changing them: the Bluesky and Mastodon clients (`internal/bluesky`, `internal/mastodon`), the stored credentials and runtime client switching (`internal/outreachconn.Manager`, which already satisfies `outreach.ClientSource`), the durable queue (`internal/outbox`: `EnqueueTx`, `SelectDue`, `ClaimRow`, `OrphanSweep`, `MarkRetryOrAbandon`, `MarkDone`, `HasPriorAttempt`), and Outreach's exported pure helpers (`outreach.ChannelByName`, `outreach.Length`, `outreach.ValidateForSend`, `outreach.BlueskyRKey`).

### Design options considered

**Where the rows live.**

- A. **New table `guide_posts`** (recommended). Clean separation; no Outreach query changes.
- B. Reuse `outreach_posts` with a nullable `outreach_id` and a new `guide_slug`. Rejected: `outreach_id` is `NOT NULL` with a foreign key, and every Outreach query (`PromoteDue`, `LoadForSend`, `classifySend`, the `publishedWorkshop` clause, reset, takedown, the tracker) joins through `outreach` to `workshops`. Each would need a guide branch, which is exactly the coupling the issue asks to avoid.

**Who sends.**

- A. **A separate `guideposts.Publisher` with its own outbox kind** (recommended). It follows `internal/outreach/publisher.go`'s loop (sweep, promote, select, claim, send, settle) at about a third of the size: no thumbnails cache from `/media`, no card URL setting, no workshop hold, no tracker.
- B. Teach `outreach.Publisher` a second kind and dispatch on `row.Kind`. Less loop code, but every guide change then edits Outreach's publisher and its tests. Rejected for the separation requirement.

The cost of A is about 150 lines of loop and settle code that mirror Outreach's. Accept it; do not extract a shared base in this issue.

**Copy source.** See Q5. The Go side needs each topic's `slug`, `title`, `hook`, and `post`. `#0656` already adds a Go mirror of the topic slugs (and the title and hook, which the SEO fallback needs) with a guard against `topics.ts`. Extend that same mirror with `Post` and extend its guard to compare it. Do not create a second mirror.

### Data model: `migrations/000052_create_guide_posts.{up,down}.sql`

`000051` is the highest migration today, so this is `000052`; re-check `ls migrations | tail -2` before writing, in case another issue took the number. It is a new file that creates a new table, so AGENTS §1's append-only rule is satisfied whatever production's frozen bound is.

```sql
-- #0657: one scheduled social post for a topic guide (/guides/{slug}),
-- separate from workshop Outreach (outreach_posts). guide_slug is checked
-- against the Go topic list in internal/guideposts, not by a foreign key:
-- the guides are constants in code, not rows.
CREATE TABLE guide_posts (
    id                 BIGSERIAL PRIMARY KEY,
    guide_slug         TEXT NOT NULL,
    channel            TEXT NOT NULL,
    body               TEXT NOT NULL,
    link_url           TEXT NOT NULL,
    status             TEXT NOT NULL DEFAULT 'draft',
    scheduled_at       TIMESTAMPTZ,
    posted_at          TIMESTAMPTZ,
    remote_id          TEXT,
    remote_url         TEXT,
    last_error         TEXT,
    attempt_generation INTEGER NOT NULL DEFAULT 0 CHECK (attempt_generation >= 0),
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ,
    CONSTRAINT guide_posts_channel_check CHECK (channel IN ('bluesky','mastodon')),
    CONSTRAINT guide_posts_status_check
        CHECK (status IN ('draft','scheduled','queued','posted','failed')),
    CONSTRAINT guide_posts_scheduled_at_check
        CHECK (status <> 'scheduled' OR scheduled_at IS NOT NULL),
    CONSTRAINT guide_posts_posted_at_check
        CHECK (status <> 'posted' OR posted_at IS NOT NULL)
);
CREATE INDEX idx_guide_posts_due ON guide_posts (scheduled_at, id) WHERE status = 'scheduled';
CREATE INDEX idx_guide_posts_slug ON guide_posts (guide_slug, id);
```

Down: `DROP TABLE IF EXISTS guide_posts;` (the indexes go with it).

No uniqueness on `(guide_slug, channel)`: one-off posts can be re-posted later as new rows. If Q1 is "confirm", add `'awaiting_approval'` to the status check. No `server_settings` key is added (the `server_settings` key check in `000050` would need a new migration); the default schedule hour reuses `outreach_post_hour`.

`attempt_generation` is carried so a future takedown (not in this issue) can follow `#0604`'s pattern without another migration; nothing increments it yet.

### Links: `link_url`, set at create time

- Bluesky text gets the plain canonical URL, `{BASE_URL}/guides/{slug}`, which keeps the longest topic copy (about 155 graphemes) plus the URL well under 300. The external card's URI is the UTM form below.
- Mastodon text gets the UTM form: Mastodon counts any URL as 23 characters, so length is not a concern.
- UTM form: `{BASE_URL}/guides/{slug}?utm_source={channel}&utm_medium=social&utm_campaign=guides&utm_content=gp{id}`. `utm_content=gp{id}` makes each post's link unique, which is what makes `mastodon.FindRecentStatusWithURL` safe: re-posting the same guide must never adopt an earlier post's status. Because `id` is only known after insert, `Create` inserts and then sets `link_url` in the same transaction (or uses `nextval` first).
- Store `link_url` as the link the body carries (plain for Bluesky, UTM for Mastodon). The Bluesky card URI is computed at send time from `id`.

If Q6 is "short links", replace this with `conns.ShortLinker()` at create time, storing the short URL; the Mastodon adoption check then uses the short URL as Outreach does.

### Images

- **Option A, recommended (Q3 default): link card only.** Bluesky: `bluesky.ExternalCard{URI, Title: topic.Title, Description: topic.Hook, Thumb, ThumbMIME}`. The thumbnail is the guide's OG card PNG, obtained through an injected `CardFn func(ctx context.Context, slug string) (data []byte, mime string, err error)` in `PublisherDeps`. `cmd/opencircuit` wires it to whatever `#0656` builds: if `#0656` renders per-guide cards with `internal/seo`'s card renderer, expose an exported method on `*seo.Site` that returns the PNG bytes for a guide slug (the same bytes its card handler serves); if `#0656` uses the site-wide default card, return that file's bytes. The PNG must be under `bluesky.MaxThumbBytes` (1,000,000); a 1200x630 card is about 60 KB, but check it, and if over, re-encode as JPEG the way `outreach.shrinkToJPEG` does (copy that function rather than export it). A `CardFn` error posts without a thumbnail and logs a warning.
  Mastodon: nothing to do; the instance fetches the guide URL and builds the card from `#0656`'s OG tags.
- **Option B: image attachment with alt text.** Bluesky: a new `app.bsky.embed.images` embed in `internal/bluesky` (upload blob, then `{image, alt, aspectRatio}`); it replaces the link card, so the link survives only as a text facet. Mastodon: a new `POST /api/v2/media` with `description` (the alt text), poll until processed, then `media_ids[]` on the status; the instance then drops the link preview. Needs an `image_alt TEXT` column and an alt-text field in the composer. Roughly doubles the client work and needs its own tests; file it as a follow-up if chosen.

### Recurring (only if Q2 is "recurring")

A `guide_post_series` table (slug, channel, body template, interval in days, next_at, active) and a step in the publisher's pass that, when `next_at` is due, inserts a `scheduled` `guide_posts` row and advances `next_at`. The one-off rows stay the unit of sending, so nothing above changes. This is a separate issue.
