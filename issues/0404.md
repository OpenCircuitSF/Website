## Description

**This blocks the deploy the user is waiting on.** The goal is to send the first
newsletter with a working "View this email in your browser" archive link, which
needs migrations 23–27 applied to production.

`migrations/000025` opens with:

	ALTER TABLE email_campaigns ADD COLUMN slug TEXT UNIQUE NOT NULL;

No `DEFAULT`. Postgres rejects that against a table containing rows:

	ERROR: column "slug" of relation "email_campaigns" contains null values

**The migration's own header states the premise that makes it safe, and that
premise is now false.** It reads: *"no email_campaigns row exists in production
(#0272 names what production data does exist, and it is not campaign rows) and
this repository has no seed script or fixture that inserts one outside a test's
own isolated database."* True when written on 2026-08-27. **Not true now.**

**Measured on production, 2026-09-03:**

| | |
|---|---|
| `schema_migrations` | 22, not dirty |
| `email_campaigns` rows | **1** |
| The row | id 1, "Open Circuits SF: September 2026", status `draft`, `test_sent_at` set |

The user drafted it through the admin console and sent themselves a test send.
The row is real user work and **must not be discarded**.

### The consequence if run as-is

`migrate up` fails at 25 and leaves `schema_migrations` **dirty at 25**, which
then blocks every subsequent migration until cleared by hand. This is the same
shape `CLAUDE.md` §1 records for `#0125` — a migration written under an
assumption that expired, failing against a database built to production's real
version and leaving the version table dirty.

## What the fix has to do

Give the existing row a valid slug as part of the migration, without weakening
the invariant the column carries for new rows. Sketch, to be designed properly:

1. `ADD COLUMN slug TEXT` (nullable, no constraint);
2. backfill every existing row with a unique, non-empty slug derived from the
   same rule `mailing.slugifyCampaign` applies to `Subject`, uniquified;
3. `SET NOT NULL`, then add the `UNIQUE` constraint and whatever `CHECK` the
   current line 25–36 block adds against the empty string.

### 0. Two corrections to this issue's own text — read before anything else

Both are in the "What the fix has to do" section above, and an implementer who
follows them faithfully will produce something that cannot work.

**(a) The frozen range is `000001`–`000022`, not `000001`–`000027`.**
`CLAUDE.md` §1's actual sentence, measured:

    **So: never edit an existing migration. `000001`–`000022` are frozen.** New
    work goes in a new numbered migration, ...

and the rule it states first is *"Never edit a migration that has been applied
to a database anyone cares about."* `000025` has never been applied to
production. Everything else it has been applied to is rebuildable from
`migrations/` in seconds. This matters because the whole "it must be a new
migration" conclusion rests on a range that §1 does not actually assert.

**(b) ~~"the repair is a **new migration**"~~ — struck. A new migration cannot
work, and the reasoning is short enough to check.** `golang-migrate` applies
pending versions in ascending order. Production is at 22, so `migrate up` runs
23, then 24, then **25 — which fails** — and stops. A `000028` never executes.
Nor is there any escape by numbering: migration versions are the integer prefix,
and there is no integer strictly between 24 and 25, so a repair cannot be
inserted ahead of the failing statement. Confirmed independently by the shape of
`schema_migrations` itself, which holds exactly two columns (`version`, `dirty`)
— there is no per-file checksum for a new migration to reconcile against.

"Correction (#0293)" precedent: the instruction is the record of what was

### 1. Decision

**Edit `migrations/000025_add_campaign_archive_columns.up.sql` in place to be
row-safe.** No new migration file, no new migration number, no manual step in
the deploy.

Seven things decided it, in descending weight:

1. **It is the only option that removes the manual step from the deploy.** The
   user is waiting on a deploy; every alternative leaves a hand-typed sequence
   on the critical path.
2. **§1's rationale points at it, not away from it.** "A database anyone cares
   about" is production, and production has never applied `000025`. The
   databases that *have* applied it are the local dev DB, `opencircuit_test`,
   `opencircuit_test_template`, and per-agent scratch DBs — every one of them
   built from `migrations/` and rebuildable in ~2s.
3. **The final schema is byte-identical either way, so nothing already at 25+
   needs any action at all.** `ADD COLUMN slug TEXT UNIQUE` produces the
   constraint name `email_campaigns_slug_key` — measured as exactly the name
   already present on the local dev DB — and a later `SET NOT NULL` produces
   the same `attnotnull`. There is no drift for a rebuild to repair.
4. **The tooling was already built for precisely this case.**
   `scripts/testdb.sh` (#0320) records a sha256 content digest of
   `migrations/*.sql` as the template's `COMMENT ON DATABASE` and compares it on
   every `create`; its own header says *"The version number alone cannot catch
   an in-place edit to an existing migration file (same filename, same number,
   different contents) — #0320."* A digest mismatch routes to direct
   provisioning from `migrations/` instead of a stale clone. So an in-place edit
   is handled automatically, and **no one has to rebuild the shared template**.
5. **`000028` is not available.** Another session's uncommitted
   `000028_create_crt_commands.{up,down}.sql` exists in
   `.claude/worktrees/agent-a16d8f8a64eadf32f/migrations/` and has already been
   applied to the shared dev database and the shared template (both measured at
   version 28). Taking `000028` here would collide on merge.
   `internal/db/docs_parity_test.go`'s `verifyContiguous` forbids skipping to
   `000029`, so there is no free number to move to either.
6. **It fixes the file for every future database, not just this deploy.**
   `docs/deployment.md`'s restore drill replays `migrations/` against a restored
   dump — i.e. against a database *with rows*. Leaving `000025` broken leaves
   that drill broken.
7. **The adjacent precedent is already in the tree.** `000024` does exactly the
   backfill → `SET NOT NULL` → `CHECK` sequence this needs, against a table it
   also expected to be empty, and it is green under every guard. Copying a
   neighbour is cheaper and lower-risk than inventing a shape.

#### Rejected: a pre-migration data step on production plus `migrate force`

The sequence would be `migrate goto 24`; hand-apply `000025`'s three `ALTER`s in
a row-safe order plus the backfill; `migrate force 25`; `migrate up`. It works,
and it keeps `migrations/` untouched. Rejected on four counts:

- **`migrate force` asserts a version without verifying the schema.** It clears
  `dirty` and writes the number. If the hand-applied SQL was partial — one
  `ALTER` mistyped at 11pm on a `t4g.nano` over ssh — the database silently
  claims a state it does not have, and 26 and 27 build on that lie. That failure
  is *worse* than the dirty-at-25 failure this issue exists to prevent, because
  dirty-at-25 is loud.
- **It puts an irreversible, hand-typed step on the critical path** of the
  deploy the user is waiting on, at the moment they are least inclined to be
  careful.
- **It leaves the defect in the repo.** Every future database built from
  `migrations/` with rows in `email_campaigns` — the documented restore drill
  first among them — hits the identical wall.
- **It makes production's schema unreproducible from `migrations/`**, which is
  the property the append-only rule exists to protect in the first place. Purity
  of file history would be bought by sacrificing the thing that history is for.

#### Rejected: delete the row, migrate, restore it

Rejected. It risks the only piece of real user work on the box to save an edit
to a file that has never run in production. A faithful restore must reproduce
`id = 1`, `created_by = 2`, `created_at`, `updated_at`, `materialized_at`,
`test_sent_at`, and any `campaign_interests` rows exactly, then repair
`email_campaigns_id_seq` so the next `Create` does not collide. Every one of
those is a chance to lose the draft the user intends to send. It buys nothing
the edit does not give for free.

### 3. The edited `000025`

Replace only the first statement's shape; leave the `archive_status` and
`archived_at` halves of the file exactly as they are, and leave
`000025_add_campaign_archive_columns.down.sql` **unchanged** (`DROP COLUMN slug`
takes the unique constraint with it, and the not-blank `CHECK` is still dropped
by name).

    -- 1. nullable, so this is legal against a table that already has rows.
    --    The inline UNIQUE yields the constraint name `email_campaigns_slug_key`,
    --    which is byte-for-byte what every database that already applied the
    --    previous version of this file carries -- so this edit is a no-op for them.
    ALTER TABLE email_campaigns ADD COLUMN slug TEXT UNIQUE;

    -- 2a. The one row that exists anywhere this migration will ever meet a
    --     non-empty email_campaigns: production's id 1, measured by #0404.
    --     Its slug is `09-2026`, decided by the user in #0405 (the MM-YYYY
    --     newsletter template) -- deliberately NOT the subject-derived value
    --     slugifyCampaign would mint. Identity-checked on subject as well as
    --     id so this can never stamp `09-2026` onto some other database's
    --     unrelated row 1.
    UPDATE email_campaigns
       SET slug = '09-2026'
     WHERE id = 1
       AND subject = 'Open Circuits SF: September 2026'
       AND slug IS NULL;

    -- 2b. Safety net. No row anywhere is expected to reach this statement --
    --     every database that has already applied this migration had zero
    --     rows, and production has exactly the one row 2a names. But SET NOT
    --     NULL below fails hard on any straggler, so give it a value that is
    --     non-blank and unique by construction (id is the primary key), and
    --     that reads unmistakably as a placeholder rather than impersonating
    --     a minted slug. An UPDATE matching zero rows is a no-op -- the same
    --     belt-and-braces shape migrations/000024 already uses.
    UPDATE email_campaigns
       SET slug = 'campaign-' || id
     WHERE slug IS NULL;

    -- 3. now the invariant can be enforced.
    ALTER TABLE email_campaigns ALTER COLUMN slug SET NOT NULL;

    -- 4. the existing not-blank CHECK, unchanged, now added after the backfill.
    ALTER TABLE email_campaigns
        ADD CONSTRAINT email_campaigns_slug_not_blank_check
        CHECK (btrim(slug) <> '');

**Do not implement the `MM-YYYY` template in the migration.** #0405 owns the
minting rule for *new* campaigns and has three questions still open (which
campaign kinds get the template, where the month comes from, what a second
campaign in a month does). This migration's whole job is to get the one existing
row right and leave the column's invariants intact. `09-2026` appears here as a
decided literal, not as a rule.

**Rewrite the file's header comment.** Its current "Existing-row safety"
paragraph asserts a premise that is now false; leaving it in place is how this
bug reproduces. Say instead: the column is added nullable and backfilled because
a row *does* exist, cite `#0404` for the measurement and `#0405` for the value,
and record that this file was edited in place under §1's "never applied to a
database anyone cares about" clause with the measured evidence (production at
22; every other applier rebuildable; the resulting schema identical).

**Also update `docs/database.md`'s `000025_add_campaign_archive_columns` table row.** It currently reads
*"`slug` needs no backfill: no `email_campaigns` row exists in production"* --
false, and `docs_parity_test.go` reads this table. The `000001`-`000027` range
prose in that file's opening paragraph stays correct and must not be touched.

**No PRD change.** §6.2's `email_campaigns` listing still describes the final schema
(`slug TEXT UNIQUE NOT NULL`) correctly, and `prd_index_parity_test.go`'s
`columnDef` carries only `sourceFile` -- it matches column *names* per table, not
types or constraints, so splitting the constraint off the `ADD COLUMN` is
invisible to it.

**No `CLAUDE.md` change** -- §1 as written already permits this, and editing it
would drag `internal/handlers` (~8x) into the verification scope for no gain.

#### Guard-compatibility, checked ahead of time

- `checkAlterTableStatementCoverage` counts `ALTER TABLE` occurrences against
  parsed statements. A plain `UPDATE` contains no `ALTER TABLE` and no
  `CREATE TABLE`, so both backfills are invisible to the coverage guards --
  exactly as `migrations/000024`'s `UPDATE` already is.
- `ALTER TABLE ... ALTER COLUMN ... SET NOT NULL;` is the exact form `000024`
  uses and is green today.
- `ADD CONSTRAINT ... UNIQUE (...)` is in `tableConstraintKeywords`, so the
  inline `UNIQUE` can be split into a named constraint if anything objects --
  but name it `email_campaigns_slug_key` so the schema stays identical to what
  databases already at 25 carry.

#### If the identity check misses

If someone edits the campaign's subject before the deploy, statement 2a matches
nothing and the row gets `campaign-1` from 2b instead. That failure is **loud
and trivially recoverable**: §8 step 5 reads the slug back before anything is
rebuilt, and the repair is one `UPDATE email_campaigns SET slug = '09-2026'
WHERE id = 1;`. That is the right trade against a blind `WHERE id = 1`, which
would silently stamp `09-2026` onto an unrelated row on any other database that
ever runs this from below version 25.

### 5. The slug the existing row gets: `09-2026`

**Decided by the user and filed as #0405** (`061968a`): the default newsletter
slug is the `MM-YYYY` template -- zero-padded two-digit month, hyphen, four-digit
year. September 2026 is `09-2026`, so the archive URL is
`https://www.opencircuitsf.com/archive/09-2026`. The user's words: *"It can be
short and specific."*

**This supersedes the subject-derived value for the backfill.** The dispatch that
opened this planning pass asked for a value matching `mailing.slugifyCampaign`;
that instruction was withdrawn once the user settled the template. Recorded here
so a reviewer can see #0404 and #0405 agree rather than reading it as drift.

For the record, the function was read rather than guessed
(`internal/mailing/campaigns.go`'s `slugifyCampaign`) and both implementations were run --

| Input | Go `slugifyCampaign` | The SQL mirror |
|---|---|---|
| `Open Circuits SF: September 2026` | `open-circuits-sf-september-2026` | `open-circuits-sf-september-2026` |
| `!!! (all punctuation)` | `campaign` | `campaign` |

-- and `open-circuits-sf-september-2026` is exactly the value **not** to use. Two
details of that function are still worth carrying forward: it slugifies
**`Subject`**, not `Name` (on production both hold the same string, so it does
not matter here), and its collision suffix is `-2`, `-3`, ... , which is what
#0405's remaining "second newsletter in a month" question will have to reckon
with. Neither is this migration's problem.

On criterion 7: the row stays `status = 'draft'`, `archive_status = 'pending'`
after the migration, so `/archive/09-2026` correctly **404s until the campaign is
sent** -- PRD §6.8's "reserved, 404 until sent". The worker's `CompleteIfDone`
stamps `archive_status = 'published'` in the same `UPDATE` that flips status to
`sent`, at which point the page resolves. Criterion 7 is satisfied by the slug
being one `CampaignStore.GetBySlug` can find, not by the page being live now.

### 6. Test design — a faithful replica, never an empty table

Use a **private** database (§8b), named outside the `opencircuit_test_` prefix
so `scripts/testdb.sh gc --all` cannot sweep it and `scripts/db-reset.sh` cannot
touch it:

    DSN='postgres://opencircuit:opencircuit@localhost:5432/opencircuit_0404_replica?sslmode=disable'
    psql "postgres://opencircuit:opencircuit@localhost:5432/postgres?sslmode=disable" \
      -c 'CREATE DATABASE opencircuit_0404_replica'

**Path A — production's real starting point.**

1. `migrate -path migrations -database "$DSN" goto 22`
2. Insert a row matching production's measured shape — `id = 1`, name and
   subject both `Open Circuits SF: September 2026`, `status = 'draft'`,
   `test_sent_at` non-null, `created_by` a seeded user. Insert `id` explicitly
   and then `setval` the sequence, so the replica is faithful rather than
   merely non-empty.
3. Capture the row **before**: `\copy (SELECT * FROM email_campaigns ORDER BY id) TO 'before.tsv'`
4. `migrate -path migrations -database "$DSN" up`
5. Assert `select version, dirty from schema_migrations` → `27`, `f`
   (**criterion 1**)
6. Assert `slug = '09-2026'` -- the value #0405 decided, **not** a
   subject-derived one -- plus `archive_status = 'pending'` and
   `archived_at IS NULL` (**criterion 2**, the slug half)
7. Capture **after** with the same column list minus the three new columns and
   `diff` it against `before.tsv` — must be empty (**criterion 2**, the
   "untouched" half). A diff, not an eyeball.
8. Assert the constraints landed with the expected names:
   `select conname, pg_get_constraintdef(oid) from pg_constraint where
   conrelid='email_campaigns'::regclass` must contain
   `email_campaigns_slug_key | UNIQUE (slug)` and
   `email_campaigns_slug_not_blank_check`, and `attnotnull` must be true for
   `slug` (**criterion 6**).
9. Negative proof that the invariant still bites: `UPDATE email_campaigns SET
   slug = NULL` must fail, `SET slug = '  '` must fail, and inserting a second
   row with the same slug must fail. Run these **last**, in a transaction you
   `ROLLBACK`.

**Path B — a database that already applied the old 25** (criterion 4). Do *not*
test this by pointing at the shared dev DB. Build it, so the comparison is
mechanical:

1. `git show HEAD:migrations/000025_add_campaign_archive_columns.up.sql` into a
   throwaway directory holding a copy of `migrations/` **with the old 25**
   (never `git stash`, never `git checkout --` — §8a), migrate a second scratch
   database to 27 with it, `pg_dump --schema-only -t email_campaigns`.
2. Migrate a third scratch database to 27 from the *edited* tree, dump the same
   way.
3. `diff` the two dumps — **must be empty**. That is the actual proof that
   databases already at 25+ need no action, and it is stronger than "migrate
   reported ok".

**Path C -- the safety net is real, not decorative.** On a fourth scratch
database at 22, insert production's row 1 **plus** two extra rows the identity
check deliberately will not match (different ids, different subjects), then
migrate. Assert row 1 gets `09-2026` and the other two get `campaign-<id>`,
all three distinct and non-blank, and that `migrate up` still reaches 27 clean.
This is what proves statement 2b actually prevents the `SET NOT NULL` failure
rather than merely looking like it would.

**Path D — round trip:** `migrate … down 1` then `… up` from 27, per
`docs/deployment.md`'s drill, proving the unchanged `.down.sql` still pairs.

Drop all scratch databases when done, by name, individually.

### 8. The deploy sequence

Ordering is load-bearing in one place, and it is the opposite of the intuitive
order.

**Migrate first, then rebuild and restart.** The running binary is `ef0a58f`
(2026-08-25) and contains **zero** references to `slug` — measured — and
`CampaignStore` selects an explicit column list, never `SELECT *`. So the
migrated schema is invisible to it and it keeps serving normally in the window
between the two steps. Reverse the order and the new binary queries `slug`
against a table that lacks it, and every campaign query 500s until `migrate up`
lands.

On the box, as the normal user:

1. `cd /opt/opencircuit && git pull --rebase origin main` — moves off `ef0a58f`.
2. **Back up first.** `docs/deployment.md` §Backups; this is the step that makes
   every later one reversible, and the one row this issue exists to protect is
   in it.
3. `migrate -path migrations -database "$DATABASE_URL" up`. Note `migrate` is at
   `/home/ec2-user/go/bin/migrate`, **not on `sudo`'s `PATH`** — run it as the
   normal user with `DATABASE_URL` sourced from `/etc/opencircuit/config.env`.
   `scripts/deploy.sh` does **not** run migrations; this is a separate step and
   always has been.
4. `migrate … version` → expect `27`, and no `dirty`.
5. `psql "$DATABASE_URL" -c "select id, slug, archive_status from email_campaigns"`
