## Description

**This blocks the deploy the user is waiting on.** The goal is to send the first
newsletter with a working "View this email in your browser" archive link, which
needs migrations 23–27 applied to production.

`migrations/000025` opens with:

	ALTER TABLE email_campaigns ADD COLUMN slug TEXT UNIQUE NOT NULL;

No `DEFAULT`. Postgres rejects that against a table containing rows:

	ERROR: column "slug" of relation "email_campaigns" contains null values

**The migration's own header states the premise that makes it safe, and that
premise is now false.** It reads: *"no email_campaigns row exists in production
(#0272 names what production data does exist, and it is not campaign rows) and
this repository has no seed script or fixture that inserts one outside a test's
own isolated database."* True when written on 2026-08-27. **Not true now.**

**Measured on production, 2026-09-03:**

| | |
|---|---|
| `schema_migrations` | 22, not dirty |
| `email_campaigns` rows | **1** |
| The row | id 1, "Open Circuits SF: September 2026", status `draft`, `test_sent_at` set |

The user drafted it through the admin console and sent themselves a test send.
The row is real user work and **must not be discarded**.

### The consequence if run as-is

`migrate up` fails at 25 and leaves `schema_migrations` **dirty at 25**, which
then blocks every subsequent migration until cleared by hand. This is the same
shape `CLAUDE.md` §1 records for `#0125` — a migration written under an
assumption that expired, failing against a database built to production's real
version and leaving the version table dirty.

## What the fix has to do

Give the existing row a valid slug as part of the migration, without weakening
the invariant the column carries for new rows. Sketch, to be designed properly:

1. `ADD COLUMN slug TEXT` (nullable, no constraint);
2. backfill every existing row with a unique, non-empty slug derived from the
   same rule `mailing.slugifyCampaign` applies to `Subject`, uniquified;
3. `SET NOT NULL`, then add the `UNIQUE` constraint and whatever `CHECK` the
   current line 25–36 block adds against the empty string.

**Migrations are append-only and `000001`–`000027` are frozen** (§1). `000025`
has been applied to every developer database and to the shared test template, so
**it cannot be edited** — the repair is a **new migration**, and the fix must
work for a database that has already applied 25 as well as one that has not.
Say explicitly how you handle both, because they are genuinely different states:
a dev database applied 25 successfully against zero rows; production has not
applied it at all.

## Acceptance criteria

1. `migrate up` from production's real state — version 22 with **one** existing
   `email_campaigns` row — completes to 27 with `dirty = false`.
2. The existing row ends with a **non-empty, unique** slug, and its other
   columns are untouched. **Prove the row survives**: capture its full contents
   before and after and diff them.
3. **Prove it against a faithful replica, not an empty database.** Build a
   scratch database, migrate it to 22, insert a row matching production's shape
   (id 1, that name/subject, status `draft`, `test_sent_at` set), then migrate
   forward. **A test starting from an empty table proves nothing here** — that
   is exactly the assumption that produced this bug.
4. A database that **has already applied 25** (every dev database, and the
   shared template) also migrates forward cleanly. Test both paths.
5. `000001`–`000027` are unmodified. The fix is a **new** migration file. Verify
   by diffing the existing files against `HEAD`.
6. The invariant survives for new rows: still `NOT NULL`, still `UNIQUE`, still
   non-empty. `mailing.CampaignStore.Create` must keep minting slugs at draft
   time and its existing tests must pass unmodified.
7. The archive page for the backfilled row resolves once it is sent — the slug
   must be one the public archive route actually serves.
8. Run `./internal/mailing/...`, `./internal/db/...`, `./internal/handlers/...`
   and `./internal/outbox/...` (§5's repo-wide-guard table; `internal/db` also
   scans `migrations/`). Per §5 name the specific tests that ran. `gofmt`
   stability. No Go-file-plus-line-number citation (`#0352`), scanned with
   `python3` bytes rather than BSD `grep -P`.
9. **Do not touch production.** This issue produces and proves the migration;
   applying it is a separate, user-approved deploy step.
