## Description

`#0158` replaced every `time.Now().UnixNano()`-derived test identifier with `testdb.Unique()`. `internal/subscribers/suppressions_test.go`'s `uniqueSuppressionEmail` had **already** worked around the clock collision locally, back in `#0108`, with its own `suppressionEmailSeq` counter — so it now stacks that counter on top of `testdb.Unique()`.

Two consequences, both cosmetic:

- Two redundant uniqueness mechanisms where one would do.
- The helper's doc comment still explains that the counter exists *because* `time.Now().UnixNano()` collided — describing a mechanism the helper no longer uses. That is the same class of stale-explanation defect `#0134` was filed for.

`#0158`'s reviewer judged leaving it alone the correct scope call for that issue, and reported this rather than expanding the sweep.

## Acceptance criteria

- [x] `suppressionEmailSeq` is removed and `uniqueSuppressionEmail` relies on `testdb.Unique()` alone
- [x] The doc comment describes the current mechanism, and keeps whatever history is worth keeping about `#0108` — the point is that it should not read as though the counter is load-bearing
- [x] `TestUniqueSuppressionEmail_NeverCollidesAcrossManyBackToBackCalls` is kept as the guard, and still passes
- [x] Check whether any other helper acquired a similar local workaround before `#0158` centralised this — `#0108`'s was found only because `#0158`'s sweep tripped over it
- [x] `ISSUE=0160 scripts/check.sh go ./internal/...` passes

## Root cause

`internal/subscribers/suppressions_test.go`'s `uniqueSuppressionEmail` grew a
package-level `suppressionEmailSeq` counter under `#0108` to work around
`time.Now().UnixNano()` colliding on ~62% of adjacent calls under a warm test
binary. `#0158` replaced the underlying `time.Now().UnixNano()` call
tree-wide, including this file, with `internal/testdb.Unique()` — a
process-PID-plus-atomic-counter scheme that is collision-free by
construction — but left the pre-existing `suppressionEmailSeq` layered on
top, since removing another helper's local workaround was judged out of
scope for `#0158`. That left two uniqueness mechanisms stacked where one
suffices, and a doc comment that still explained the counter as a defense
against a clock collision `testdb.Unique()` no longer reads from.

## Fix

- Removed `suppressionEmailSeq` (the package-level `uint64` counter) and its
  `atomic.AddUint64` call; `uniqueSuppressionEmail` now builds its return
  value from `testdb.Unique()` alone (`zz-suppress-%d@example.com`).
- Removed the now-unused `sync/atomic` import — it was not used anywhere
  else in the file.
- Rewrote the doc comment above `uniqueSuppressionEmail` to describe what
  the helper does today (draws from `testdb.Unique()`) while keeping the
  `#0108` history (the original clock-collision problem) and noting `#0158`
  (the fix that made the local counter redundant) and `#0160` (this issue,
  which removed it).
- Rewrote `TestUniqueSuppressionEmail_NeverCollidesAcrossManyBackToBackCalls`'s
  doc comment the same way: it now reads as a regression guard for the
  `#0108` requirement against the current `testdb.Unique()`-only
  implementation, rather than describing the counter it no longer exercises.

**Sweep for other pre-`#0158` local workarounds (fourth criterion).** Searched
the whole tree, not just `internal/subscribers`, for:

- `grep -rl '"sync/atomic"' --include='*_test.go' .` — three files besides
  the one just fixed: `cmd/opencircuit/seo_wiring_test.go`,
  `internal/mailing/worker_test.go`, `internal/sesnotify/verify_test.go`.
- `grep -rn 'atomic\.Add' --include='*_test.go' .` — the same three files.
  Read each call site: all three increment a call-count for a mock/hook
  (`bySlugCalls`, `passes`, `hits`/`finalHits`) to assert *how many times*
  something was invoked, not to derive a unique identifier. Different
  purpose from `uniqueSuppressionEmail`'s stacked scheme; left alone.
- `grep -rnE '^var\s+\w+\s+(u?int(32|64)?)\b' --include='*_test.go' .` — a
  broader net for any remaining package-level counter variable of the same
  shape as `suppressionEmailSeq`. Zero results after this fix (one result,
  the counter itself, before it).
- `grep -rl '"math/rand"\|"crypto/rand"' --include='*_test.go' .` — three
  files (`cmd/opencircuit/ses_notifications_wiring_test.go`,
  `internal/handlers/ses_notifications_test.go`,
  `internal/sesnotify/verify_test.go`), all using `crypto/rand.Reader` for
  RSA key generation in SES-signature tests — not an identifier-uniqueness
  source. Left alone.
- `grep -rn 'UnixNano\|UnixMilli\|UnixMicro' --include='*_test.go' .` — the
  remaining `UnixMilli` hits are the genuine `rendered_at` fixture
  timestamps and `internal/handlers/subscribe_test.go`'s timing-gate
  boundary table, already confirmed correct-to-leave-alone by `#0158`'s
  review. The remaining `UnixNano` hits are all prose in comments (this
  file's history and `internal/testdb/testdb_test.go`'s), not code.

No other helper acquired a similar stacked workaround. `suppressionEmailSeq`
was the only package-level counter of its kind in the tree.

## Review notes

Re-verified independently on 2026-08-22 in a throwaway worktree detached at
`f5fb611`. The main checkout was clean at the time, but `#0159`'s reviewer was
running concurrently in `internal/db/`, which this issue's scoped run compiles
— the worktree removes any chance of grading this change against someone
else's in-flight edit. `uptime` before the run: load averages 2.22 → 3.31,
idle, so nothing below is the CLAUDE.md §5 "machine is busy" case.

**The commit is exactly one file, and the import removal is the only
collateral change.** `git show --stat f5fb611` lists
`internal/subscribers/suppressions_test.go` alone (18 insertions, 19
deletions). Reading the diff: the deletions are the `sync/atomic` import, the
`suppressionEmailSeq` declaration with its comment, the `atomic.AddUint64`
line, and the two old doc comments; the insertions are the two rewritten doc
comments and the one-line `fmt.Sprintf`. No assertion, fixture, or expected
value moved. `sync/atomic` appears nowhere else in the file, so removing the
import was required rather than opportunistic.

**The collision claim holds for this helper's actual call pattern**, which is
the part worth checking rather than taking in the abstract. `testdb.Unique()`
is `int64(os.Getpid())<<32 | (atomic.AddInt64(&uniqueCounter, 1) & 0xffffffff)`
(`internal/testdb/testdb.go:128`). Against the four ways that guarantee could
be defeated here:

- **Parallel subtests.** There is no `t.Parallel()` anywhere in
  `internal/subscribers` — `grep -rn 't.Parallel()' internal/subscribers/`
  is empty. And it would not matter if there were: `atomic.AddInt64` is the
  synchronization, so concurrent goroutines in one process still get distinct
  values. The old `atomic.AddUint64` added nothing this did not already have.
- **Helpers called from a loop.** Three of the 20 call sites are inside
  table-driven subtest loops (lines 262, 304, 506) and two are adjacent
  statements in one test (`withSub`/`orphan`, lines 398–399) — the tightest
  adjacency in the file. All are in-process, so all are distinct by the
  counter.
- **Two processes at once.** `internal/handlers` also writes `suppressions`
  against the same `TEST_DATABASE_URL`, but `testdb.Lock()`'s session
  advisory lock serializes DB-backed packages per database, and two *live*
  processes cannot share a PID in any case. Its helper also mints a different
  prefix (`zz-subtest-suppress-` vs `zz-suppress-`), so the namespaces do not
  overlap even in principle.
- **Sequential PID reuse across runs** — the caveat `#0158`'s review raised.
  It is real (a later process can reuse a PID and replay identifiers, which
  the old monotonic clock could not) and it is harmless *here* specifically,
  which is worth stating rather than assuming: `suppressions` is keyed
  `PRIMARY KEY (email, reason)` since `migrations/000013`, so a replayed
  address would be a hard constraint violation rather than a silent
  overwrite — but `internal/subscribers`' `TestMain`
  (`main_test.go:50`) `TRUNCATE`s `subscriber_interests, subscribers,
  suppressions RESTART IDENTITY CASCADE` before any test runs, so no run ever
  sees a prior run's rows for a replayed identifier to land on. `check.sh`
  cloning a fresh per-`ISSUE` database is a second layer over the same
  property.

**The retained guard is not merely still passing — it is strictly stronger
than it was.** This is the part the issue text undersells. With the local
counter in place, the guard could not have detected a `testdb.Unique()`
regression at all: the counter alone made every address distinct. Proved both
directions in the throwaway worktree, by replacing `Unique()`'s body with
`return time.Now().UnixNano()`:

- at `f5fb611` (counter removed), the guard **fails on call 3** —
  `uniqueSuppressionEmail returned a duplicate address
  "zz-suppress-1787459830645205000@example.com"`;
- at `f5fb611^` (counter present), the same regressed `Unique()` and the same
  guard **pass**, `ok 0.284s`.

So the old guard was vacuous with respect to the mechanism it named, and
removing the counter is what connected it to the thing it guards. Both files
were restored from `git`/a copy afterwards and `git status --short` in the
worktree was empty before it was removed.

**Sweep for other pre-`#0158` local workarounds — redone with four axes the
implementer did not use.** Its own five axes reproduce as reported: no
package-level `(u)int32/64` counter variable remains in any `_test.go`, the
three `atomic.Add*` sites are mock call-counters, the three `rand` imports are
RSA keygen, and every surviving `UnixNano` is prose. Added:

- `os.Getpid` in test files — two hits, both `syscall.Kill(os.Getpid(),
  SIGTERM)` in shutdown wiring tests, not identifier generation.
- `uuid` — one hit, a word in a comment.
- `t.Name()`-derived identifiers — zero hits tree-wide.
- Hand-rolled non-atomic sequence variables — `^\s*\w*(Seq|Counter|Ctr|Num|Idx)\+\+`
  and `^var \w*([Ss]eq|[Cc]ounter|[Nn]ext|[Cc]ount)\w*` in `_test.go`: zero
  hits each. This was the axis most likely to hide a survivor, since a plain
  `int` incremented in a helper matches none of the implementer's searches.
- `time.Since` — three hits, all elapsed-duration assertions.

The fourth acceptance criterion is met: `suppressionEmailSeq` was the only
stacked local counter in the tree, and nothing else of that shape survives.

**But the sweep did surface something adjacent, and it is a real defect** —
reported here rather than filed, per CLAUDE.md §9. Enumerating every
identifier-minting helper in the tree (`^func [a-z]\w*\([^)]*\) string {`
across `_test.go`) rather than searching for known-bad tokens, two packages
turn up that `#0158` never touched — `internal/middleware` and
`internal/audit` have **zero** `testdb.Unique()` call sites — because they
derive uniqueness from the clock via `Format`, not via `UnixNano()`:

- `internal/middleware/auth_test.go:39` `uniqueAuthEmail`
- `internal/middleware/auth_test.go:48` `uniqueSessionToken`
- `internal/middleware/clientip_signup_test.go:91` `uniqueSignupEmail`
- `internal/audit/audit_test.go:36` `seedUser`

All four build an identifier from
`time.Now().UTC().Format("20060102T150405.000000000")` — the same
nanosecond-resolution wall clock `#0158` measured repeating on 94.7% of
adjacent reads on this machine, just rendered as a string. `#0158`'s sweep
searched for the literal `time.Now().UnixNano()` and this issue's searched
`UnixNano|UnixMilli|UnixMicro`; `.Format(...)` matches neither, which is
exactly why a token search missed it and an enumeration of helpers found it.

Three of the four are currently latent rather than live: `uniqueAuthEmail`,
`uniqueSessionToken`, and `seedUser` all interpolate a `label`, and every
call site passes a distinct one (`expired`, `valid`, `deactivated`, `admin`,
`regular`; `victim`, `rollback`, `admin`, `actor`), so no two calls share a
discriminator today. `uniqueSignupEmail` has **no label at all** — the clock
is its only discriminator, and it is called from two tests
(`clientip_signup_test.go:51` and `:78`) that are separated only by a DB
insert. That is precisely the "masked so far by intervening round trips"
shape `#0158`'s review flagged for `uniqueAdminWorkshopTitle`. Worth filing as
a follow-up to finish `#0158`'s migration; out of scope for `#0160`, which is
about the stacked counter.

**The rewritten comments are correct and appropriately scoped.** The helper's
comment now leads with what the code does ("draws from `testdb.Unique()`"),
puts `#0108` in the past tense as history ("this helper grew its own atomic
counter"), and names `#0158` and `#0160` for why it went away — no sentence
reads as though a counter is still load-bearing, which was half the defect.
The guard test's comment gets the same treatment and, importantly, now
describes itself as guarding the `#0108` *requirement* rather than the
`#0108` *mechanism*, which is what it actually does. One nit, not worth a
bounce: the helper comment's `TestSuppressionStore_List_JoinsSubscriberStatus`
reference runs the line well past the file's prevailing width, and `gofmt`
does not reflow comments. Cosmetic.
