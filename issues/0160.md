## Description

`#0158` replaced every `time.Now().UnixNano()`-derived test identifier with `testdb.Unique()`. `internal/subscribers/suppressions_test.go`'s `uniqueSuppressionEmail` had **already** worked around the clock collision locally, back in `#0108`, with its own `suppressionEmailSeq` counter — so it now stacks that counter on top of `testdb.Unique()`.

Two consequences, both cosmetic:

- Two redundant uniqueness mechanisms where one would do.
- The helper's doc comment still explains that the counter exists *because* `time.Now().UnixNano()` collided — describing a mechanism the helper no longer uses. That is the same class of stale-explanation defect `#0134` was filed for.

`#0158`'s reviewer judged leaving it alone the correct scope call for that issue, and reported this rather than expanding the sweep.

## Acceptance criteria

- [ ] `suppressionEmailSeq` is removed and `uniqueSuppressionEmail` relies on `testdb.Unique()` alone
- [ ] The doc comment describes the current mechanism, and keeps whatever history is worth keeping about `#0108` — the point is that it should not read as though the counter is load-bearing
- [ ] `TestUniqueSuppressionEmail_NeverCollidesAcrossManyBackToBackCalls` is kept as the guard, and still passes
- [ ] Check whether any other helper acquired a similar local workaround before `#0158` centralised this — `#0108`'s was found only because `#0158`'s sweep tripped over it
- [ ] `ISSUE=0160 scripts/check.sh go ./internal/...` passes

## Notes

Reported by `#0158`'s phase-3 review under `CLAUDE.md` §9's rule that subagents report issues rather than filing them.

Low priority: nothing is wrong at runtime, and the doubled mechanism is harmless. It is worth doing because the stale comment will mislead the next person who reads it, and because a local workaround left in place after the general fix is how a codebase accumulates two ways to do one thing.
