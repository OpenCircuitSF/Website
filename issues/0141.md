## Description

`web/dist/index.html` is a **tracked file that `npm run build` rewrites in place.** `.gitignore` deliberately un-ignores it so a clean `go build` has something to embed, and the committed version is meant to be a minimal placeholder carrying the `%%OC_*%%` substitution tokens. Nothing enforces that.

Any agent or person who runs a build and then stages broadly commits a real bundle — hashed `/assets/index-*.js` references and all — over the placeholder. The only defence today is `CLAUDE.md` §8a's "never `git add -A`" convention.

This is not hypothetical. It has already caused two distinct failures:

1. **ShortLinks' placeholder survived into this repo** and sat there token-free, so a clean `go build` embedded an index in which `#0019`/`#0020`'s entire SEO feature was inert. Found by `#0054`'s first review; fixed in `06a65fc`.
2. **It masked that very defect.** `#0054`'s implementer saw its own wiring test pass only because its local `npm run build` had overwritten the file; reverting it (correctly) broke the test, and the broken `scripts/check.sh` (`#0140`) hid the failure.
3. **It recurred during `#0054`'s second review.** The reviewer's first command found the file identical to `HEAD`; minutes later a concurrent agent's build had made it 3,339 bytes of real output. That reviewer worked around it by verifying against a pristine `git archive HEAD` extraction.

## Acceptance criteria

- [x] A guard fails when the **committed** `web/dist/index.html` looks like build output rather than the placeholder — e.g. it references a hashed `/assets/index-*.js`, or it is missing the `%%OC_*%%` tokens `internal/seo` substitutes
- [x] The guard runs somewhere it cannot be skipped — a Go test alongside the existing doc-parity guards is the cheapest home, since `scripts/check.sh` already runs them
- [x] The guard's failure message says what to do (restore the placeholder from `HEAD`; do not commit build output)
- [x] Decide and record whether the placeholder should instead be generated or embedded from a non-`dist` path, removing the collision entirely — a guard is the cheap fix, not necessarily the right one
- [x] `ISSUE=0141 scripts/check.sh go ./internal/...` passes with the guard in place, and the guard is proved to fail against a real bundle

## Implementation notes

**Current-state check, before changing anything (as instructed):**

- The committed `web/dist/index.html` was confirmed intact: `git log --oneline -- web/dist/index.html` shows `06a65fc` (`#0054`) as the commit that gave it its `%%OC_*%%` tokens, on top of `34b80f3` (`#0001`)'s original ShortLinks copy and `f94eb20` (`#0055`, JSON-LD). The on-disk file's sha256 (`7bb5f85694...`) matched `git show HEAD:web/dist/index.html`'s exactly — no drift going in.
- `web/dist/index.html` is the **only** tracked file under `web/dist/`; everything else there (`assets/`, `fonts/`, icons, `mark*.png`, `site.webmanifest`, etc.) is generated/gitignored per `.gitignore`'s `web/dist/*` / `!web/dist/index.html` pair. That one-file collision is the whole surface area — nothing else under `dist/` needed consideration.
- Ran `npm run build` in a **throwaway git worktree** (`git worktree add --detach`), never the shared checkout. The real build's `dist/index.html` is 4,256 bytes vs. the placeholder's ~1,071: it still contains all nine `%%OC_*%%` tokens (Vite doesn't touch literal text it doesn't recognize), but additionally injects `<script type="module" crossorigin src="/assets/index-<hash>.js">` and a matching `<link rel="stylesheet" ... href="/assets/index-<hash>.css">`. This matters for the guard's design: **checking only for missing tokens would not have caught this** — the hashed-asset reference is the distinguishing signal for a real build, independent of the token check (which catches the *other* historical failure, ShortLinks' original token-free placeholder).

**Fix chosen: a guard test**, not the structural "stop tracking dist/index.html" option. `internal/seo/dist_placeholder_guard_test.go` adds `TestDistIndexPlaceholder`, which fails when the committed `web/dist/index.html` (a) is missing any of the nine `%%OC_*%%` tokens, or (b) references a hashed `/assets/*.js|css` path. The failure message names the file, both problems found, and the exact restore command (`git checkout HEAD -- web/dist/index.html`), plus a caveat for the case where the edit was intentional this session.

Placement went through two iterations:
1. First placed in package `web` (alongside `web/embed.go`, which owns `//go:embed all:dist` and already documents this exact hazard).
2. **Relocated to `internal/seo`** on review of `scripts/check.sh`: the default `ISSUE=NNNN scripts/check.sh` (no subcommand) only runs `go test ./internal/... ./cmd/...` (its `*)` case) — `./web/...` is exercised only by `scripts/check.sh all`, which `CLAUDE.md` reserves for a batch's single review pass, not per-issue verification. A guard left in package `web` would in practice almost never run. `internal/seo` sits under the default scope and already defines the `tokenTitle … tokenJSONLD` constants the guard checks, matching the acceptance criteria's own suggestion ("a Go test alongside the existing doc-parity guards... since `scripts/check.sh` already runs them") and avoiding a second, driftable copy of the token list.

**Decision recorded (per the AC's explicit requirement to decide and record, not just apply the cheap fix):** did **not** pursue generating/embedding the placeholder from a non-`dist` path. That is the more durable option but a materially bigger change — `//go:embed all:dist` (`web/embed.go`) needs the directory to exist and contain something at compile time from a clean checkout, so removing the collision means either a new pre-build step (copying a differently-named seed file into place before both `go build` and `npm run build`, touching `scripts/`) or mechanically generating `web/dist/index.html` from `web/index.html`. `#0208` is already contesting restructuring of `scripts/check.sh`'s `run bash` call sites, and this issue's own scope note says to stop and report if the fix needs to restructure those — a pre-build-step change plausibly would. Recommend filing a follow-up issue for "stop tracking `web/dist/index.html`, generate it instead" if the guard proves insufficient in practice; not filed by me per `CLAUDE.md` §9 (subagents report, don't file).

**Mutation proof:** overwrote the tracked `web/dist/index.html` with real `npm run build` output (from the throwaway worktree). `TestDistIndexPlaceholder` failed, naming both hashed assets (`/assets/index-Cs2-8eM1.js`, `/assets/index-TVYljy6F.css`) and the restore command. Restored the original bytes and confirmed `shasum -a 256` byte-identity with `HEAD` (`7bb5f85694...`) both times (once per placement iteration). `git status web/dist/` was clean before, during setup, and after.

## Review notes

> 🟢 **Resolved 2026-08-23** (`499bc17`) — verified independently by the phase-3
> reviewer at load average 1.8 (idle). All five acceptance criteria hold. The
> guard is the right fix for this issue, and the declined structural change is

**The build-output finding was re-derived, not taken on report.** Built the SPA
in a throwaway `git worktree add --detach` (its own `npm ci`, never the shared
checkout — `CLAUDE.md` §8b, `docs/obstacles.md` §4). The result reproduced the
implementer's claim exactly, down to the asset hashes: `web/dist/index.html`
comes out at **4,256 bytes** (placeholder is 1,071), it **still contains all
nine `%%OC_*%%` tokens** — counted one occurrence each of `OC_TITLE`,
`OC_DESCRIPTION`, `OC_OG_TITLE`, `OC_OG_DESCRIPTION`, `OC_OG_IMAGE`,
`OC_OG_URL`, `OC_OG_TYPE`, `OC_TWITTER_CARD`, `OC_JSONLD` — and it adds
`/assets/index-Cs2-8eM1.js` plus `/assets/index-TVYljy6F.css`. So a
token-presence check alone would **not** have caught a real build. The
hashed-asset check is the load-bearing half; the token check independently
covers the *other* historical failure (ShortLinks' token-free placeholder,
`#0054` finding 1). Both signals are needed and the guard implements both.

**Boundary probe — what the guard catches and what it does not.** Ran the
guard's own `hashedAssetPattern` (`/assets/[^"'\s]+\.(?:js|css)\b`) against
synthetic references:

| Input | Result |
|---|---|
| `/assets/index.js` (unhashed filename) | **caught** |
| `/assets/app-abc123.js`, `/assets/index-X.css` | **caught** |
| `/static/index-abc.js` (non-default `assetsDir`) | missed |
| `assets/index-abc.js` (relative — non-default `base`) | missed |
| `/assets/index-abc.mjs` | missed |

The first row is the important one and it answers the question the review was
asked: the regex is **broader than "hashed"** — it matches any `/assets/*.js|css`
reference — so a build configured with `entryFileNames: 'assets/[name].js'`
would still be caught. The misses all require someone to have edited
`web/vite.config.ts`, which currently sets neither `base` nor `assetsDir` and so
takes Vite's defaults (`/` and `assets`). That is a deliberate act that would
also need the Go static handler changed, and the guard would be the least of
what needed updating. **The gap does not matter for this issue's failure mode**,
which is an accidental `npm run build` + broad `git add` under the current
config.

Two residual gaps worth naming rather than fixing here: a **partial overwrite**
that keeps every token and adds no asset reference passes the guard — but such a
file is not build output, and the guard's job is the toolchain collision, not
hand-edits. And the guard's asset regex is **implicitly coupled to Vite's
default `base`/`assetsDir`**; if either is changed the guard silently stops
catching build output while still reporting green. A cheap belt-and-suspenders
exists and is config-independent: the committed placeholder carries a unique
`This is a MINIMAL PLACEHOLDER, not real build output` comment that a real build
does not (verified: 1 occurrence in the committed file, 0 in build output), so
asserting that marker's *presence* would catch any regeneration regardless of
asset paths. Reported to the orchestrator as a possible follow-up; not filed
here (`CLAUDE.md` §9).

**Mutation reproduced.** Copied the worktree's real build output over the
tracked `web/dist/index.html` and ran `go test ./internal/seo/ -run
TestDistIndexPlaceholder -count=1`. It failed, naming both hashed assets and the
restore command verbatim:

```

    /assets/index-TVYljy6F.css). ... restore the placeholder with
    `git checkout HEAD -- web/dist/index.html` ...
```

Restored from a pre-mutation copy; `shasum -a 256` matched `git show
HEAD:web/dist/index.html` byte for byte
(`7bb5f85694324910da8dd9c65fe1d266d28ee43612865248e289155fd2ee7ded`) and `git
status web/dist/` was clean. That hash is identical before and after the whole
review.

**The relocation is complete, and "it runs by default" was proved by making it
fail, not by reading a package list.** `git show --stat 499bc17` records a pure
rename (`{web => internal/seo}/dist_placeholder_guard_test.go`); nothing of the
first attempt remains under `web/`, whose only Go file is `embed.go`. The guard
reuses `internal/seo`'s own `tokenTitle … tokenJSONLD` constants from `seo.go`
rather than duplicating a token list, so the token set has one owner — and a
tenth token added to `Render` extends the guard automatically. For the run
proof: the throwaway worktree already held real build output in its
`web/dist/index.html`, so `ISSUE=0141rev2 scripts/check.sh go` was run there
**with no package arguments** — i.e. the script's own default
`./internal/... ./cmd/...` scope. It went red on `TestDistIndexPlaceholder` and
`VERIFICATION FAILED`. That simultaneously confirms the relocation's premise:
`./web/...` is absent from that default scope, so the guard's first home would
in practice almost never have run.

**Verdict on the declined structural fix — a guard is sufficient; treat this as
settled.** AC 4 asks the implementer to *decide and record* whether the
placeholder should be generated or embedded from a non-`dist` path; it does not
mandate that change. The record is present in both the issue and the test's
package doc comment, with the reasoning: `//go:embed all:dist` needs the
directory populated at compile time from a clean checkout, so removing the
collision requires a new pre-build step in `scripts/` — call sites `#0208` is
actively contesting — and this issue's own scope note says to stop and report in
that case. The implementer stopped and reported, which is the correct behaviour,
not an omission. The guard closes the actual failure mode (three incidents in one
day, all "build output silently became the committed file") and closes it loudly
and cheaply: filesystem-only, no `TEST_DATABASE_URL`, no advisory lock, ~0.00s,
never skipped. Re-opening the structural question is warranted only if the guard
is observed failing to prevent a recurrence.
