### The circuit breaker — decision and argument (issue's "decide and argue")

Recorded here per the dispatch instruction; `internal/mailing/
delivery_health.go`'s package doc comment carries the same argument in the
code itself, since that is where a future reader is more likely to look.

- **What stops.** Only *this* campaign's drain, on the worker that is
  running it. Remaining `email_sends` rows stay `queued` — nothing is lost
  or marked failed. Other campaigns and transactional mail (`internal/
  outbox`, a separate queue) are unaffected.
- **At what threshold.** `send_health_bounce_pct` (default 5.0%) OR
  `send_health_complaint_pct` (default 0.1%), either independently
  sufficient — PRD §6.9's table, verbatim. Below `send_health_min_sample`
  (default 50) sends, the rate is never evaluated at all: "5% of 3" is not a
  rate.
- **Automatic or advisory.** Automatic, deliberately. The worker pauses the
  campaign itself, no human in the loop, the instant it observes the
  crossing. An advisory-only breaker (warn, keep sending) was rejected: the
  account-wide SES re-sandboxing this guards against can happen in the
  first sixty seconds of a bad send, before anyone is watching a dashboard.
- **What un-trips it.** A deliberate admin action only —
  `POST /admin/campaigns/{id}/resume`, gated by a typed confirmation
  (the campaign's own subject, typed back). Never automatic: a
  self-resetting breaker would either re-trip immediately on the next batch
  or, worse, quietly resume into a rate that dipped below threshold while
  the underlying list problem was still there. A breaker nothing can reset
  is worse than none (a bad-but-recoverable send stuck forever) — so Resume
  exists, but re-evaluates the identical cumulative rate on the very next
  batch rather than granting immunity, which is what makes it not
  bypassable from the UI: there is no request shape that skips the worker's
  own check.
- **Who is told.** `ActionEmailCampaignPausedDeliveryHealth` to `audit_log`
  (reason, observed rate(s), threshold(s), sent-so-far) plus an
  `outbox.KindAdminAlert` to `ADMIN_EMAIL` through #0126's durable queue
  (never a synchronous SES call that could itself fail silently and lose
  the notification). An empty `ADMIN_EMAIL` (CLAUDE.md §10 item 4: still
  undecided) skips only the alert enqueue — the pause and the audit row are
  not conditioned on it, since those are the load-bearing safety action.

### Departures and judgment calls, disclosed

- **`bounced_soft` written on every soft bounce, not only the
  threshold-crossing one** (see commit 2 above) — a correction to PRD
  §6.11's literal table, not a change #0126 asked for. Judged low-risk: it
  only adds rows to an append-only log nothing else reads exclusivity from.
- **The deliverability list is scoped to addresses with a live subscribers
  row** (`internal/subscribers/deliverability.go`'s package doc comment):
  an address hard-bounced or suppressed and then GDPR-erased (#0060) has no
  streak left to show and surfaces on `/admin/suppressions` (#0100)
  instead, which is the list built to survive erasure. Not a gap — a
  deliberate split between "the streak-bearing view" and "the suppression
  list", argued in that file.
- **Resume's typed confirmation is the campaign's subject, not a recipient
  count.** Send's `confirm_count` re-verifies the audience, which Resume
  has no equivalent of (the audience was already materialized before the
  breaker tripped) — so this borrows #0060's Erase pattern ("type the
  resource's own identifying text back") instead. Server-side, this is the
  authoritative check; the client-side `resumeSubjectMatches` is an offer
  gate only.
- **No dedicated `resumeConfirm.ts` guard-state module** to match
  `sendConfirm.ts`'s multi-pass-reviewed rigor (#0186/#0189's precedence
  rules for `inFlight` vs `unmet` vs `status`). Resume's guard is simpler by
  construction (one boolean: does the typed text match), so a single pure
  function (`resumeSubjectMatches`) plus inline `$derived`/`$state` in
  `CampaignEditor.svelte` covers it without inventing an equivalently
  elaborate state machine for a genuinely simpler problem.

- No fourth path exists. The admin `ResetStreak` handler calls only
  `ResetSoftBounceStreakByEmail` and does not remove suppressions.

Status is still written only through `MarkBouncedTx`/`setStatusTx`, which
preserve `complained` — unchanged by this issue.

### The resume path cannot mail a since-bounced or complained address

`CampaignStore.Resume` only reaches `scheduled`; the worker then takes its
ordinary claim, and **`ClaimBatch` runs `RecheckEligibleTx` on every batch**,
which requires `status == active && !suppressed && !emailChanged` and marks
everything else `skipped`. A subscriber who bounced or complained during the
pause is `complained`/`bounced` or suppressed, so they are skipped rather
than mailed. `drainLoop` also re-runs the `physical_address` refusal at the
top of every resume, so that §9 guarantee survives a resume too.

### Judgement: automatic-vs-advisory, and the migration edits

- **Automatic is right.** The failure being guarded against is an
  account-wide SES re-sandboxing that takes down confirmation mail, and it
  can start inside one batch with nobody watching. An advisory breaker
  protects nothing at 3am. The typed-confirmation reset is the correct
  balance: it cannot clear itself (which would defeat it) and it is not
  unclearable (which would strand a recoverable send). Requiring the
  campaign's own subject — `#0060`'s Erase pattern — is a better fit than
  `#0045`'s `confirm_count`, since the audience was already materialized and
  there is no count left to re-verify. The confirmation is checked
  **before** any mutation, so a mistyped attempt changes nothing.
- **The in-place migration edits are legitimate and were done properly.**
  `000010`/`000014`/`000015`/`000017` are edited directly, which `CLAUDE.md`
  §1's greenfield rule expressly prefers over stacking `ALTER TABLE`s. The
  template rebuilds cleanly and the schema on disk matches the schema in the
  database. Keeping `000016` as a documented no-op rather than renumbering
  six later migrations is the right trade — but see defect 1 below, because
  the tree does not say so consistently.
- **The no-op is not hiding a lost change.** `000016`'s only effect was
  widening a partial index that `000014` now no longer creates at all, and
  `000014` creates the replacement index directly. Nothing was dropped on
  the floor.

### New defects found (reported, not filed — `CLAUDE.md` §9)

1. **`migrations/000014_create_email_events.up.sql` contains a false
   statement about `000016`.** Its new comment reads "000016 (which only
   widened that now-removed index) is **deleted outright** rather than folded
   forward, per this issue's acceptance criteria". `000016` was **not**
   deleted — it is on disk as a documented no-op. This contradicts
   `000016`'s own file, `docs/database.md` line 51 ("**Folded away by
   `#0124`, not deleted.**"), and this issue's own Implementation notes. It
   is a leftover from the delete-first attempt that was tried and rejected.
   One-line fix; no behavioral effect, but it is wrong on exactly the point
   the criterion turned on.

2. **`breakerTestMailer` generates colliding `ses_message_id` values, making
   the breaker tests mutually polluting.** `newBreakerTestMailer` starts its
   counter at zero per instance, so every test emits `breaker-1`,
   `breaker-2`, … . `CampaignStatsStore.EventCounts` joins `email_sends` to
   `email_events` on `ses_message_id` **alone**, so one test's bounce events
   are visible to another test's campaign. Measured after one run of the six
   breaker tests: **219 `email_events` rows sharing only 100 distinct ids**,
   with `breaker-1` appearing 6 times. A reviewer probe seeded 5 bounces and
   `EventCounts` reported **200**. The boundary tests nevertheless still hold
   today — proved by the mutations above — because the polluting id set
   happens to be a subset of the polluted test's own. That is luck, not
   design: any reordering, reseeding, or change to which indices bounce would
   silently change the measured rate and could turn a boundary test green
   against the wrong number. Fix: include `testdb.Unique()` in the generated
   id. Production is unaffected — real SES message ids are unique.

3. **One Resume puts a full batch on the wire before the breaker looks
   again.** `checkDeliveryHealth` is called at the *end* of `drainLoop`'s
   batch loop, never before the first `ClaimBatch`. So a resumed campaign
   always sends `SEND_BATCH_SIZE` messages (production default **50**,
   `internal/config`) before the rate is re-evaluated. Measured directly: a
   300-recipient campaign at a **100% bounce rate**, `batchSize=100`, tripped
   after 100 sends; a single `Resume` then sent **exactly +100 more** before
   re-pausing. Repeating the confirmation therefore drains 50 messages per
   resume, indefinitely, at a known-bad rate. This does not make the breaker
   bypassable — it always re-arms and re-trips, and every resume is
   typed-confirmed, audited and alerted — but it is weaker than
   `delivery_health.go`'s own claim that "there is no request shape that
   skips the worker's own check": the check is skipped for exactly one batch
   per resume. Suggested fix: evaluate `checkDeliveryHealth` once at the top
   of `drainLoop`, before the first `ClaimBatch`, so a resume into a
   still-over-threshold rate sends zero messages and immediately re-pauses.

   Related and worth stating explicitly: the rate's **denominator grows
   synchronously with sends while its numerator grows asynchronously with
   SES webhooks**, so a resumed campaign's cumulative rate dilutes as it
   sends. Combined with the above, a moderately-bad campaign can resume and
   run to completion. That is arguably correct — the true cumulative rate
   really did fall below threshold — but it is a property nothing in the
   tree currently writes down.

## Notes

PRD §6.9 is the specification. §6.7 (SES event ingestion) is the code this modifies.

**This deliberately supersedes the shipped rule.** `#0039` and `#0112` implemented the threshold as *N Transient bounces in a rolling 30-day window*, computed at decision time from `email_events` (`migrations/000015`, `000016`). The window self-heals as it rolls, so it is not the bug `#0112` describes — but it has no concept of a successful delivery. An address that bounces four times, then delivers cleanly for a month, still carries four bounces. Consecutive-with-reset-on-delivery is what Mailchimp, Postmark, and SES's own reputation guidance describe, and it is what the user asked for. Read `#0039`, `#0109`, and `#0112` before starting; this issue changes a decision all three reasoned about.

**Why the breaker is a safety feature, not a metric.** AWS enforces a bounce rate under 5% and a complaint rate under 0.1% **account-wide**. Crossing either puts the SES account under review and then back into sandbox — which takes down confirmation emails, not just campaigns. A bad import or a stale list can cross 5% in the first few hundred sends. Nothing currently watches.

**`Undetermined` counts as soft.** `#0109` established this; do not regress it. An address that only ever produces `Undetermined` bounces must still reach the threshold.

**Do not conflate the three logs.** `email_events` is SES's words verbatim, `audit_log` is what staff did, `subscriber_events` (`#0126`) is what happened to an address in our vocabulary. The deliverability screen reads the first.

**Greenfield — amended 2026-08-21.** Nothing is deployed but the static
placeholder: there is no PostgreSQL instance on AWS holding real data, no
subscriber has ever signed up, no campaign has ever been sent. Until the first
production release, `migrations/` may be squashed, renumbered, or rewritten and
the dev database dropped and recreated. **Prefer editing the migration that owns
the table over adding an `ALTER TABLE`,** and write no backfill for data that
does not exist. See PRD §6.2's greenfield note; CLAUDE.md §1's append-only rule
resumes at first deploy.

This is what makes the rule change cheap: there is no live database carrying a
30-day window of `email_events` that has to be converted into streaks. Reset the
dev database and the new rule is simply the only rule that ever existed.

**Concurrency.** `#0122` is an open defect in `drainCampaign`'s `OrphanSweep`. Read it before touching the worker loop — the breaker adds a second reason for the drain to stop early, and the two must not interact badly.
