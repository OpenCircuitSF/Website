# 0124 — Track bounce history per address and stop a send that is bouncing

| | |
|---|---|
| **Status** | open |
| **Module** | sesnotify / mailing / subscribers / admin |
| **Platform** | All |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-08-21 |

## Description

Replace the rolling-window soft-bounce rule with an industry-standard consecutive streak that resets on a successful delivery, keep every bounce in a per-address history an admin can read, and stop a campaign mid-send when its running bounce or complaint rate crosses the SES thresholds.

## Acceptance criteria

**Streak**

- [ ] `subscribers` gains `soft_bounce_streak INT NOT NULL DEFAULT 0`, `last_bounce_at TIMESTAMPTZ`, `last_delivery_at TIMESTAMPTZ` — added to `migrations/000010` directly, per the greenfield note below
- [ ] A SES `Bounce` of type `Permanent` suppresses immediately with reason `hard_bounce` (unchanged from `#0038`)
- [ ] A SES `Bounce` of type `Transient` or `Undetermined` increments `soft_bounce_streak` and stamps `last_bounce_at`
- [ ] A SES `Delivery` event sets `soft_bounce_streak = 0` and stamps `last_delivery_at`
- [ ] Reaching `soft_bounce_threshold_count` (settings, default 5) suppresses with reason `repeated_soft_bounce`
- [ ] Removing a suppression resets the streak to 0 — a re-enabled address gets a fresh runway, not one bounce from re-suppression
- [ ] `soft_bounce_threshold_window_days` is removed from `migrations/000015`'s seed, along with the code path that read it
- [ ] `migrations/000016` is folded back into `000014`'s index definition or deleted outright — it exists only to widen the windowed query this issue removes

**History**

- [ ] `email_events` stays append-only. Nothing in this issue deletes or rewrites a row
- [ ] Index `idx_email_events_recipient_time (recipient, received_at DESC)` added
- [ ] `GET /admin/deliverability` lists addresses with bounce activity, sorted by streak then recency: email, status, streak, last bounce, last delivery, suppression state
- [ ] `GET /admin/deliverability/{email}` returns the full event history for one address: event type, bounce type, SES diagnostic code, originating campaign, timestamp
- [ ] `POST /admin/deliverability/{email}/reset-streak` clears the streak, audited
- [ ] The admin view links to the existing `#0100` suppression add/remove endpoints rather than duplicating them
- [ ] `#0110` and `#0111`'s documentation of `soft_bounce_count` is corrected to describe the streak

**Circuit breaker**

- [ ] Settings `send_health_min_sample` (50), `send_health_bounce_pct` (5.0), `send_health_complaint_pct` (0.1) seeded alongside the existing rows in `000015`/`000018`
- [ ] The send worker computes the running bounce and complaint rate for the campaign in flight
- [ ] Below `send_health_min_sample` sends, the breaker never trips
- [ ] Crossing either threshold sets campaign status `paused_delivery_health`, leaves remaining `email_sends` rows `queued`, and writes the reason to the audit log
- [ ] An alert email goes to `ADMIN_EMAIL` via the outbound queue (`#0126`) naming the campaign, the rate, and the threshold
- [ ] `POST /admin/campaigns/{id}/resume` restarts a paused send, requiring typed confirmation like `#0045`'s send confirmation, and is audited
- [ ] The breaker is not bypassable from the UI — same rule as `#0045`'s `physical_address` check
- [ ] The campaign compose UI and the SSE stream (`#0048`) surface `paused_delivery_health` as a distinct, explained state
- [ ] Tests named explicitly in `## Verification`, per CLAUDE.md §5

## Notes

PRD §6.9 is the specification. §6.7 (SES event ingestion) is the code this modifies.

**This deliberately supersedes the shipped rule.** `#0039` and `#0112` implemented the threshold as *N Transient bounces in a rolling 30-day window*, computed at decision time from `email_events` (`migrations/000015`, `000016`). The window self-heals as it rolls, so it is not the bug `#0112` describes — but it has no concept of a successful delivery. An address that bounces four times, then delivers cleanly for a month, still carries four bounces. Consecutive-with-reset-on-delivery is what Mailchimp, Postmark, and SES's own reputation guidance describe, and it is what the user asked for. Read `#0039`, `#0109`, and `#0112` before starting; this issue changes a decision all three reasoned about.

**Why the breaker is a safety feature, not a metric.** AWS enforces a bounce rate under 5% and a complaint rate under 0.1% **account-wide**. Crossing either puts the SES account under review and then back into sandbox — which takes down confirmation emails, not just campaigns. A bad import or a stale list can cross 5% in the first few hundred sends. Nothing currently watches.

**`Undetermined` counts as soft.** `#0109` established this; do not regress it. An address that only ever produces `Undetermined` bounces must still reach the threshold.

**Do not conflate the three logs.** `email_events` is SES's words verbatim, `audit_log` is what staff did, `subscriber_events` (`#0126`) is what happened to an address in our vocabulary. The deliverability screen reads the first.

**Greenfield — amended 2026-08-21.** Nothing is deployed but the static
placeholder: there is no PostgreSQL instance on AWS holding real data, no
subscriber has ever signed up, no campaign has ever been sent. Until the first
production release, `migrations/` may be squashed, renumbered, or rewritten and
the dev database dropped and recreated. **Prefer editing the migration that owns
the table over adding an `ALTER TABLE`,** and write no backfill for data that
does not exist. See PRD §6.2's greenfield note; CLAUDE.md §1's append-only rule
resumes at first deploy.

This is what makes the rule change cheap: there is no live database carrying a
30-day window of `email_events` that has to be converted into streaks. Reset the
dev database and the new rule is simply the only rule that ever existed.

**Concurrency.** `#0122` is an open defect in `drainCampaign`'s `OrphanSweep`. Read it before touching the worker loop — the breaker adds a second reason for the drain to stop early, and the two must not interact badly.
