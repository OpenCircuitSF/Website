## Description

`#0252` closed the deferred-assignment blind spot: `e := audit.Entry{}` followed
by `e.Metadata = map[string]any{"email": …}` now reports `unresolved` instead of
passing silently. Its review confirmed that fix, mutation-proved all four new
pins, and ran fourteen constructed shapes against the corrected header without
falsifying it.

It then found **four more shapes**, all predating that pass. Three are silent
passes; one of those carries an email.

**1. A one-line variant defeats the new check — and this is the consequential
one.**

```go
e := audit.Entry{Metadata: map[string]any{"slug": s}}
e.Metadata = map[string]any{"email": addr}
```

→ `hasEmail=false, unresolved=""`. **A silent pass carrying an email.**

The new path is gated on `if !metadataKeyFound`, so it never fires when the
literal *also* sets `Metadata` — and classification then comes from the
literal's map rather than from the assignment that actually wins at runtime.
The guard reads the losing value.

**2. An entry held in a struct field is invisible to both halves.**
`w.e = audit.Entry{}` then `w.e.Metadata = {"email": …}` → silent pass. Both
helpers require a bare `*ast.Ident`.

**3. Pointer mutation through a helper is not modelled.**
`e := audit.Entry{}` then `setMeta(&e)` → silent pass.

**4. Two false positives, both failing closed.**
`collectDeferredMetadataFieldIdents` matches on identifier *name* across the
whole function body, with no scope analysis and no ordering. So a variable of a
different type also named `e` in a disjoint block, or an `e.Metadata =`
appearing *before* `e = audit.Entry{…}`, each make an innocent site report
`unresolved`. The direction is safe — it fails closed — but **the message names
the wrong cause**, which costs whoever hits it real time.

## Notes

Reported by `#0252`'s phase-3 review under `CLAUDE.md` §9. None of the four
falsifies the committed text, but all sit directly beside a "now FIXED" claim,
which is what makes them worth closing together rather than leaving as known
gaps.

**Shape 1 deserves priority over the other three.** Shapes 2 and 3 are
structural blind spots of a kind the codebase does not currently produce.
Shape 1 is a *near-miss of the fix itself* — one extra field in the literal and
the new path silently declines to run — and it is a shape a developer would
write without thinking, since initialising some metadata inline and replacing it
later is ordinary code.

**The pattern across this whole file, now six rounds deep**, is that each fix
closes the shape it was shown and leaves the adjacent one open. `#0252`'s
approach — pin what you do not close — is the thing that has actually worked;
prefer it over chasing completeness.
