## Description

`#0252` closed the deferred-assignment blind spot: `e := audit.Entry{}` followed
by `e.Metadata = map[string]any{"email": …}` now reports `unresolved` instead of
passing silently. Its review confirmed that fix, mutation-proved all four new
pins, and ran fourteen constructed shapes against the corrected header without
falsifying it.

It then found **four more shapes**, all predating that pass. Three are silent
passes; one of those carries an email.

**1. A one-line variant defeats the new check — and this is the consequential
one.**

```go
e := audit.Entry{Metadata: map[string]any{"slug": s}}
e.Metadata = map[string]any{"email": addr}
```

→ `hasEmail=false, unresolved=""`. **A silent pass carrying an email.**

The new path is gated on `if !metadataKeyFound`, so it never fires when the
literal *also* sets `Metadata` — and classification then comes from the
literal's map rather than from the assignment that actually wins at runtime.
The guard reads the losing value.

**2. An entry held in a struct field is invisible to both halves.**
`w.e = audit.Entry{}` then `w.e.Metadata = {"email": …}` → silent pass. Both
helpers require a bare `*ast.Ident`.

**3. Pointer mutation through a helper is not modelled.**
`e := audit.Entry{}` then `setMeta(&e)` → silent pass.

**4. Two false positives, both failing closed.**
`collectDeferredMetadataFieldIdents` matches on identifier *name* across the
whole function body, with no scope analysis and no ordering. So a variable of a
different type also named `e` in a disjoint block, or an `e.Metadata =`
appearing *before* `e = audit.Entry{…}`, each make an innocent site report
`unresolved`. The direction is safe — it fails closed — but **the message names
the wrong cause**, which costs whoever hits it real time.

> 🟢 Resolved 2026-08-24 — Shape 1's ungated deferred-assignment check re-verified by running the issue's own fixture plus thirteen variants through `scanAuditEntrySites`; both pins mutation-proved to fail when their shape is closed; census independently re-derived at 45 sites / 87 keys / 0 unresolved.

## Root cause

`#0252`'s deferred-struct-field-assignment check
(`collectDeferredMetadataFieldIdents` + `compositeLitAssignedIdents`,
`internal/handlers/audit_email_metadata_guard_test.go`) had four unhandled
edges, confirmed by running each one through `scanAuditEntrySites` before
touching anything (see `## Verification` for the exact commands and output):

1. `scanAuditEntrySites`'s deferred-assignment check only ran
   `if !metadataKeyFound`, so a literal that ALSO set its own `Metadata` key
   skipped the check entirely and classification fell through to
   `classifyMetadataExpr` on the literal's own map — the value that **loses**
   at runtime, since the later `e.Metadata = ...` assignment is what the
   running code actually inserts. Reproduced exactly as the issue describes:
   `hasEmail=false, unresolved=""`.
2. `w.e = audit.Entry{}` / `w.e.Metadata = ...` — both
   `compositeLitAssignedIdents` (`ident := audit.Entry{...}`) and
   `collectDeferredMetadataFieldIdents` (`ident.Metadata = ...`) require a
   bare `*ast.Ident` on the relevant side of the assignment. `w.e` is an
   `*ast.SelectorExpr` on both sides, so neither helper ever sees it.
   Reproduced: `hasEmail=false, unresolved=""`.
3. `setMeta(&e)` — `collectDeferredMetadataFieldIdents` only inspects
   `*ast.AssignStmt` nodes matching `ident.Metadata = ...` directly in the
   enclosing function's body; a helper call that mutates the field through a
   pointer argument produces no such node, so it is invisible regardless of
   what the call does. Reproduced: `hasEmail=false, unresolved=""`.
4. Both false positives trace to the same root: `collectDeferredMetadataFieldIdents`
   matches a later `.Metadata = ...` assignment by identifier **name** only —
   no `go/types` scope resolution, no statement-order check against the
   literal's position. A same-named variable of an unrelated type in a
   disjoint block, and a `.Metadata = ...` that textually precedes the
   literal it gets attributed to, both trip the check and produce
   `unresolved`, with a message that asserted a same-variable runtime
   override the lookup had not actually established. Reproduced both:
   `unresolved` fires in both cases with the old (misleading) wording.

## Fix

- **Shape 1 (priority, fixed):** removed the `if !metadataKeyFound` guard
  around the deferred-assignment check in `scanAuditEntrySites`, so it now
  runs unconditionally whenever `literalIdents[cl]` resolves to an
  identifier that also appears in `deferredMetadataIdents` — regardless of
  whether the literal itself set a `Metadata` key. The site is reported
  `unresolved` either way, matching this guard's conservative default
  everywhere else (unclassifiable fails, it never passes).
- **Shapes 2 and 3 (pinned, not fixed):** both are structural blind spots
  the codebase does not currently produce (confirmed:
  `grep -rn '\.Metadata\s*=' internal cmd --include='*.go'` excluding
  `_test.go` files finds exactly one hit tree-wide,
  `internal/audit/read.go:159`, an unrelated type's field — no production
  `audit.Entry` is ever held in a struct field or mutated through a pointer
  argument). Following `#0252`'s own approach ("pin what you do not close"),
  added two new subtests to `TestAuditEmailMetadataGuardDocumentedSilentPassShapes`
  rather than attempting a structural fix (which would need `go/types`-level
  identifier resolution, a materially larger change for shapes with zero
  live risk today).
- **Shape 4 (message fixed, detection unchanged):** reworded the
  deferred-assignment failure message to describe what was actually found —
  "a struct-field assignment (%s.Metadata = ...) appears somewhere in this
  function ... possibly before or after this ... literal, and possibly on an
  unrelated variable of the same name, since this guard matches by
  identifier name only and has no scope or statement-order awareness" —
  instead of asserting a specific same-variable override. The detection
  still fails closed (unresolved, never silent) for both false-positive
  shapes; only the message's claim changed. Pinned by a new test,
  `TestAuditEmailMetadataGuardDocumentedFalsePositiveShapes`.
- Updated the file's header comment with a new `#0255` paragraph block (in
  the same falsifiable style `#0237`'s fourth pass and `#0252`'s pass used)
  describing all four shapes, which were fixed/pinned, and re-stating that
  the 45-site/87-key census is unchanged.
- Added `TestAuditEmailMetadataGuardFailsWhenLiteralAlsoSetsMetadataThenOverridden`,
  mutation-proved against the pre-fix gate (see `## Verification`), pinning
  shape 1's fix the same way `#0252`'s own fix was pinned.

### NEW — one more silent pass, carrying an email (report, not filed)

Reported to the orchestrator under `CLAUDE.md` §9 rather than filed. Found by
probing around the newly-ungated path:

```go
e := audit.Entry{Metadata: map[string]any{"slug": s}}
e.Metadata["email"] = addr        // index assignment through the struct field
```

→ `hasEmail=false, unresolved=""`. **A silent pass carrying an email**, the
same class as this issue's shape 1. `collectDeferredMetadataFieldIdents`
requires the assignment's LHS to be an `*ast.SelectorExpr`; here it is an
`*ast.IndexExpr` whose `.X` is the selector, so nothing sees it.

What makes it worth its own issue rather than a footnote is the contrast: the
*local-variable* form of the identical mutation **is** caught —

```go
m := map[string]any{"slug": s}
m["email"] = addr
e := audit.Entry{Metadata: m}     // → hasEmail=true, caught
```

— because `collectLocalMapKeys` handles `x["k"] = v` on a bare identifier. So
the gap is exactly "index through the struct field instead of through the
local", a one-line reordering of code the tree already contains. That is a
