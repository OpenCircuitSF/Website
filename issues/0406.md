## Description

`web/src/lib/liveRegionGuard.structuralGuard.test.ts` carries a `#0306`
measurement comment that enumerates the `KNOWN_STABLE_BRANCH_SITES` entries and
concludes "All twelve clear …". `#0396` added a thirteenth — the CRT commands
per-row width warning — without updating the prose.

Nothing is unprotected: the guard measures every entry at run time, and the
comment is careful enough to say "then-current", so it is not strictly false.
The cost is narrower and duller — a reader counting entries against the prose
miscounts, and the discrepancy invites a second look at a guard that is
actually fine.

This is the drift class `CLAUDE.md` §11 already documents for the PRD section
index: a hand-maintained count next to the thing it counts, with nothing
tying them together. §11's table drifted twice before it was guarded, and
neither pass noticed.

## Acceptance criteria

- [ ] The comment's count matches the array, and names the thirteenth entry alongside the others
- [x] An assertion ties the prose to the array so this cannot drift silently again — the count in the comment and `KNOWN_STABLE_BRANCH_SITES.length` must be checked against each other, not merely both edited today
- [x] That assertion fails if an entry is added without updating the comment — proved by mutating an **in-memory copy**, never the file on disk (`CLAUDE.md` §8a)
- [x] The oracle is not the same bytes as its subject: a single edit must not be able to satisfy both the assertion and the thing it checks (`CLAUDE.md` §8, the `#0258` rule)
- [x] `scripts/check.sh web` passes

## Root cause

The array-vs-prose count agreed and the discrepancy this issue describes does
**not** exist on `main`. `KNOWN_STABLE_BRANCH_SITES` still holds twelve
entries and the "All twelve clear …" comment is accurate as of this pass. The
`#0396` work the issue credits with a thirteenth entry (the CRT commands
per-row width warning) has **not landed on `main`** — it exists only on an
unrelated, unmerged worktree branch. Verified directly rather than trusted:

```
git merge-base --is-ancestor 6699fbb HEAD   -> NOT ANCESTOR
git merge-base --is-ancestor 08bf77a HEAD   -> NOT ANCESTOR
git branch --contains 08bf77a               -> worktree-agent-a16d8f8a64eadf32f (only)
```

`main` and that worktree branch diverge right after `#0393`'s filing commit
(`bf59158`); `main`'s own history only *files* `#0396`/`#0397`/`#0398`
(`9f0460f`) and never implements them. So the underlying hazard the issue
describes was real in principle — a hand-maintained count with nothing tying
it to the array, the drift class `CLAUDE.md` §11 documents for the PRD
section index — but the specific instance ("twelve" vs. an actual thirteen)
had not (yet) occurred on this branch.

## Fix

Re-derived the count directly by counting `KNOWN_STABLE_BRANCH_SITES`'s
entries and the per-entry table rows in the real-tree test's own measurement
comment: both are twelve, matching the prose. Rather than mechanically
bumping "twelve" to "thirteen" per the issue's stated premise, built the
assertion the remaining acceptance criteria ask for, using the true current
count:

- Added `KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT = 12` as a literal constant
  declared next to the array, with a doc comment explaining it is a separate
  declaration from `.length` on purpose.
- Added `expect(KNOWN_STABLE_BRANCH_SITES).toHaveLength(KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT)`
  in the real-tree test, right where the "All twelve clear …" comment lives —
  this ties the prose to the array (criterion 2).
- Added `describe('KNOWN_STABLE_BRANCH_SITES recorded count (#0406)')`, which
  builds an **in-memory copy** of the array with one synthetic entry appended
  and asserts the copy's length now disagrees with
  `KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT` — proving the assertion is
  sensitive to exactly the drift this issue describes, without ever touching
  the file on disk or the real `KNOWN_STABLE_BRANCH_SITES` binding
  (`CLAUDE.md` §8a) (criterion 3).
- The oracle (`KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT`, a hand-edited
  literal in one location) is not the same bytes as its subject
  (`KNOWN_STABLE_BRANCH_SITES.length`, computed from the array in a different
  location) — adding an array entry does not also edit the constant, so a
  single edit cannot satisfy both (`CLAUDE.md` §8, the `#0258` rule)
  (criterion 4).

**Decisions recorded, per the phase-2 briefing:**

- **Count vs. phrase:** kept a numeral ("twelve") rather than switching to a
  vague phrase (the `#0466`/"several hundred" precedent). That precedent
  applies to an unchecked count; this one is now backed by a live assertion,
  so a numeral is safe and more useful than a phrase would be.
- **Pinning:** built the pin the acceptance criteria explicitly ask for. This
  differs from `#0462`'s reviewer, who declined a similar mechanism — but
  that decision was made by a reviewer weighing an *unrequested* addition;
  here the issue's own acceptance criteria mandate the assertion, phrased
  generically (not contingent on any specific count), so building it does not
  add an unrequested mechanism.
- **No new mechanism beyond the assertion:** no new guard script, no
  repo-wide scan, no change to `scripts/check.sh` — the fix is one constant,
  one assertion, and one sensitivity test, all inside the existing test file
  the issue names.

**Divergence from criterion 1** ("names the thirteenth entry alongside the
others"): there is no thirteenth entry on `main` to name — see `## Root
cause`. Criterion 1 does not apply as written given the current tree; the
count is accurate today, with nothing to bump. Worth a note for whoever picks
this back up: if/when the `#0396` worktree work merges into `main`, the new
`toHaveLength` assertion will immediately fail and name the drift, rather
than it going unnoticed the way it apparently did on that other branch.

### The premise finding, re-verified independently

Every part of the implementer's `## Root cause` was re-measured by this pass
rather than accepted:

- `git merge-base --is-ancestor 6699fbb HEAD` and the same for `08bf77a` both
  report NOT ANCESTOR; `git branch --contains` on each names only
  `worktree-agent-a16d8f8a64eadf32f`. Neither commit is reachable from
  `main`'s `HEAD`.
- `main`'s own history mentions `#0396` exactly once, in `9f0460f`, which
  **files** `#0396`/`#0397`/`#0398` and implements none of them. `#0396` is
  still `open` on `main`.
- The component the thirteenth entry would describe does not exist here at
  all: no `CrtCommands.svelte` is tracked anywhere under `web/src` on `main`
  (only unrelated `prototypes/crt-live-screen/` assets match "crt"). So the
  `#0393` CRT admin line the issue's Description assumes is likewise absent.
- The count itself was re-derived from the file on disk with `python3`
  (`CLAUDE.md` §8 — not BSD `grep -P`): the array literal contains
  twelve top-level entries, the measurement comment's per-entry table has
  twelve rows, the prose says "All twelve clear …", and
  `KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT` is `12`. A naive brace-count
  over the same range returns 38, because the entries' `reason` strings
  contain Svelte `{#if}` / `{:else if}` text — worth knowing for anyone
  re-deriving this later, since the wrong method produces a confidently wrong
  number.

So the implementer was right not to bump twelve to thirteen. Doing so would
have written a number into `main` that contradicts `main`'s own array, and the
new assertion would then have failed immediately.

### The oracle rule, and the sensitivity test

The subject is `KNOWN_STABLE_BRANCH_SITES.length`, computed from the array
literal. The oracle is `KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT`, a
hand-edited numeric literal in its own declaration above the array. Adding an
array entry does not touch that line, so a single edit cannot satisfy both —
this is the separability `CLAUDE.md` §8's `#0258` rule requires, and it is
the opposite of `#0258`'s failure, where the oracle was a stored copy of the
subject's own bytes.

The sensitivity test operates on an **in-memory copy** — confirmed by
reading it, not inferred: it builds `mutatedCopy` with a spread plus one
synthetic entry, leaves the real `const` binding untouched, and performs no
filesystem write. Nothing on disk is mutated, satisfying `CLAUDE.md`
§8a. It then asserts the copy's length disagrees with the constant, which
is exactly the condition under which the real `toHaveLength` assertion throws.

**Honest limit on the strength of that proof.** The sensitivity test
demonstrates the drift rather than executing a failure — it asserts
`length !== constant` instead of asserting that the real assertion throws.
Given that the real assertion compares a computed length against a literal,
its falsifiability is arithmetic, and this pass verified both operands
independently from the file on disk. This pass did **not** mutate the real
file or a copy of it inside the tree to watch the suite go red, deliberately:
two other agents are testing concurrently, and a temporarily red test file in
`web/src/lib/` would have been picked up by their full `npm test` runs. The
conclusion rests on inspection plus independent re-derivation of both
operands, which is stated here rather than dressed up as an execution proof.

### Keeping the numeral, and the residual gap

Keeping "twelve" rather than retreating to a vague phrase is the right call,
and the implementer's distinction from `#0466` holds: that precedent applies
to an unchecked count, and this one is now backed by an assertion that runs on
every `npm test`.

The gap worth recording, so nobody later believes more than is true: the
assertion ties the **constant** to the array, not the **prose** to the array.
Someone who adds a thirteenth entry and dutifully bumps the constant to `13`
could still leave the "All twelve clear …" sentence and its twelve-row
table stale, and the suite would stay green. That is a strictly smaller hazard
than the one this issue names — the pre-fix state had no signal at all,
whereas now the suite goes red and names the constant, whose own doc comment
instructs the reader to update the prose and the table too. A stricter tie
(having the test read its own source and parse the numeral out of the
comment) was considered and declined: it buys little over the forcing function
already in place, and it is exactly the in-file-guard accretion `CLAUDE.md`
§8 warns produces one more bounce per mechanism. Recorded, not re-filed.

### Criterion 1, and why this resolves rather than staying open

Criterion 1 asks the fix to name the thirteenth entry. There is no thirteenth
entry on `main`, so the criterion is unsatisfiable as written — not
skipped, not deferred. The implementer flagged this rather than quietly
satisfying it, which is the correct handling.

Resolving is the right outcome because the criterion's *intent* — the
recorded count must be right, and must not drift silently — is fully met,
and met more durably than an edited sentence would have managed. Leaving the
issue open pending another session's unmerged branch would park it on work
this repository does not contain and cannot schedule, and a later pass would
have nothing available to it that this one lacked. When `#0396`'s work merges,
the `toHaveLength` assertion fails on the merge itself and names the constant;
bumping it, the prose, and the per-entry table is then part of that merge, not
a revival of this issue.
