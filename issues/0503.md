## Description

`#0499` records a durable `audit_log` row whenever an inbound message is left
in place for manual review. That row carries the sender's `From:` address,
which is **load-bearing** — without it the record names an S3 key that the
30-day lifecycle rule deletes, leaving something an admin can count but not
act on.

`#0499`'s reviewer approved storing it and flagged that it needs a deliberate
policy decision, which the implementation correctly declined to make on its
own. This issue is that decision.

## The two cases, which are genuinely different

**1. `auto_reply` — a current subscriber's own address.** Measured, not
hypothetical: `#0499`'s test asserts the recorded `from` equals a real seeded
subscriber's `Email`. This is the same category as the seven `audit_log` call
sites already disclosed in `PrivacyPolicy.svelte`, and the question is simply
whether it joins them and the erasure path.

**2. `from_not_found` / `no_identifying_signal` — someone with no relationship
to the project at all.** A stranger's address, or a spammer's, written into an
**append-only table with no expiry and no erasure path**. This is the case that
deserves real thought.

`#0499`'s own `## Notes` anticipated the shape of this — "keeping a record of
the failure longer than the message is probably the right split" — but
`audit_log` makes the record *permanent* rather than merely longer-lived. That
is defensible under `#0499` criterion 2, and it is a stronger commitment than
the note contemplated.

## Why it matters beyond tidiness

`CLAUDE.md` §10 item 4 records that GDPR erasure and data-export requests route
to `contact@opencircuitsf.com`, and `#0075`'s privacy policy is what promises
that. A permanent store of non-subscriber addresses that no erasure path
reaches is a promise the site does not currently keep for those people.

## What to decide

1. Does `auto_reply`'s `from` join `PrivacyPolicy.svelte`'s disclosure list and
   the erasure path? (Probably yes — it is a subscriber address like the other
   seven.)
2. What retention is right for a **non-subscriber** address in `audit_log`?
   Options worth weighing: redact the local part after some window; store a
   hash rather than the address for the non-subscriber reasons; add a retention
   sweep for `target_type = 'inbound_mail'` specifically; or accept permanence
   and disclose it plainly.
3. Whichever is chosen, does `PrivacyPolicy.svelte` need new wording, and does
   the erasure runbook need a step for this table?

## Decision (recorded 2026-09-13 — user's call, made via the orchestrator)

**Redact after a window.** Non-subscriber addresses (`from_not_found`,
`no_identifying_signal`) keep their full address for **90 days** — comfortably
past the 30-day S3 lifecycle, satisfying criterion 2 — after which a retention
sweep redacts the local part, leaving the domain and the row actionable as a
count. Subscriber addresses (`auto_reply`) join `PrivacyPolicy.svelte`'s
disclosure list and the erasure path like the other seven audit call sites.
The privacy policy gains wording covering both cases, `#0237`'s known-sites
fixture is updated in the same change (criterion 3), and `docs/` records where
an erasure request has to reach (criterion 4). Rejected: hash-only storage
(weakens actionability), indefinite permanence (the promise #0075 makes cannot
cover strangers' addresses).

## Acceptance criteria

1. A decision is recorded with its reasoning — an unexamined answer is not
   acceptable; any of the above is.
2. If retention changes, it does not weaken `#0499` criterion 2: the record
   must still outlive the 30-day S3 object, which is the whole point of it.
3. If disclosure changes, `PrivacyPolicy.svelte` and `#0237`'s known-sites
   fixture are updated together — see `#0502`, which must land first for the
   site to be visible to that guard at all.
4. `docs/` records where an erasure request has to reach.

## Notes

This is a **policy call, not an engineering one**, and it is the user's to make.
Do not implement a retention scheme before the decision is recorded. Note the
tension to resolve deliberately: the bucket holds raw inbound mail and is
deliberately short-lived, so the durable record exists precisely to outlive it —
the question is how much of a stranger's identity that record needs to keep in
order to remain actionable.

## Root cause

#0499's parked-message audit row wrote a correspondent's raw `From:` address
into an append-only table with no expiry and no erasure path, and no policy
existed for what that means for a stranger's address versus a subscriber's
own. The recorded decision (above) is the policy; this change is its
implementation.

## Fix

- **Sweep** — `internal/audit/redact.go`:
  `Logger.RedactExpiredInboundSenders(ctx, now)` runs one idempotent UPDATE
  that replaces the local part of a parked row's metadata `from` value with
  a fixed placeholder (`redacted@<domain>`) once the row is past the 90-day
  window (`inboundSenderRetention`, a constant beside the table owner — the
  pattern `outboxOrphanStaleAfter` established; no new env var, since
  `internal/config`'s loader is the established home for operator knobs and
  this is a policy number, not a dial). The WHERE clause redacts every
  parked row carrying a real address EXCEPT `reason = 'auto_reply'` (the
  decision's subscriber case, retained and disclosed) and already-redacted
  rows (idempotency guard, also making the count meaningful); it therefore
  covers `from_not_found` and `no_identifying_signal` — the decision's named
  two — plus `token_not_found`, which the decision's parenthetical did not
  name: that path deliberately never checks `From:` against the list
  (`internal/handlers/ses_inbound.go`'s `match`), so its recorded address is
  the same kind of unverified data and leaving it permanent would
  under-disclose a subscriber's own address if the stale token was theirs.
  Rows with no `from` key (unparseable messages) and addresses with no `@`
  are naturally untouched. Other metadata keys (S3 key, message id, subject,
  reason) survive verbatim, so the row stays actionable as a count —
  criterion 2: 90 days comfortably outlives the 30-day S3 lifecycle.
- **Cadence** — the sweep rides the outbox worker's existing poll loop
  (`internal/mailing/outbox_worker.go`'s `pass`, immediately after #0128's
  expire-pending sweep — the ride-the-existing-cadence precedent the design
  guidance named), via a nil-tolerant `OutboxWorkerDeps.Audit` field;
  `cmd/opencircuit`'s `newOutboxWorker` wires it unconditionally on the
  Postgres serve path (the sweep is policy, not an optional feature; dev
  mode never constructs the worker). No new scheduler, no new ticker.
- **Index** — `migrations/000030` (new pair, append-only) adds the partial
  index `idx_audit_log_inbound_redactable` mirroring the sweep's WHERE
  clause minus its cutoff, so the every-2s-pass cost never sequential-scans
  the whole `audit_log`; the template was rebuilt to migration 30. The
  sweep's SQL inlines the action/target_type literals so a prepared
  statement's generic plan can always match the index predicate;
  `TestRedactionSQLTracksActionConstants` pins those literals to the audit
  constants.
- **Disclosure** — `PrivacyPolicy.svelte`'s audit-log item widened both
  ways: the email enumeration gained "an automated out-of-office reply your
  mail program sends us" as the eighth email-carrying action (the
  `auto_reply` case joins the erasure-path disclosure), and a final clause
  discloses the 90-day window, the placeholder redaction, and what survives
  (domain + row-as-count) for unmatched senders.
  `internal/handlers/audit_email_metadata_guard_test.go`'s known-sites
  fixture comment was updated in the same change (criterion 3 — the fixture
  row itself is unchanged: the sweep is an UPDATE of one metadata key, never
  a new audit.Entry site); `PrivacyPolicy.guard.test.ts`'s audit_log
  category gained the four new required phrases, its two affected mutation
  proofs were updated, and a new mutation proof drops the redaction clause.
- **Docs** — criterion 4: `docs/unsubscribe.md` records the retention
  policy, the sweep, and where an erasure request has to reach
  (`contact@opencircuitsf.com`); `docs/ses-inbound-remaining.md`'s #0503 row
  records the decision as landed; `docs/database.md` and `CLAUDE.md` carry
  the migration range 000001–000030 and the 000030 row.

## Gotchas

- `matchItemToCategory`'s missing-phrase list is order-sensitive
  (`toEqual`), so the new expected arrays must follow `requiredPhrases`'
  order — the first draft of both updated mutation proofs listed the
  out-of-office phrase after "your email address" and failed on order
  alone.
- The decision's parenthetical names `from_not_found` and
  `no_identifying_signal` as the non-subscriber reasons; this
  implementation sweeps `token_not_found` too (same unverified-address
  shape — the token path never checks `From:`), excluding only
  `auto_reply`, which also keeps a future parked reason from silently
  re-creating the gap. Flagged for review rather than decided silently.
- The sweep could not parameterize its action/target_type literals without
  risking a generic prepared-statement plan that misses the partial index,
  so the literals are inlined in SQL and pinned to the Go constants by
  `TestRedactionSQLTracksActionConstants`.
