# 0503 — Decide disclosure and retention for email addresses now held permanently in `audit_log`

## Description

`#0499` records a durable `audit_log` row whenever an inbound message is left
in place for manual review. That row carries the sender's `From:` address,
which is **load-bearing** — without it the record names an S3 key that the
30-day lifecycle rule deletes, leaving something an admin can count but not
act on.

`#0499`'s reviewer approved storing it and flagged that it needs a deliberate
policy decision, which the implementation correctly declined to make on its
own. This issue is that decision.

## The two cases, which are genuinely different

**1. `auto_reply` — a current subscriber's own address.** Measured, not
hypothetical: `#0499`'s test asserts the recorded `from` equals a real seeded
subscriber's `Email`. This is the same category as the seven `audit_log` call
sites already disclosed in `PrivacyPolicy.svelte`, and the question is simply
whether it joins them and the erasure path.

**2. `from_not_found` / `no_identifying_signal` — someone with no relationship
to the project at all.** A stranger's address, or a spammer's, written into an
**append-only table with no expiry and no erasure path**. This is the case that
deserves real thought.

`#0499`'s own `## Notes` anticipated the shape of this — "keeping a record of
the failure longer than the message is probably the right split" — but
`audit_log` makes the record *permanent* rather than merely longer-lived. That
is defensible under `#0499` criterion 2, and it is a stronger commitment than
the note contemplated.

## Why it matters beyond tidiness

`CLAUDE.md` §10 item 4 records that GDPR erasure and data-export requests route
to `contact@opencircuitsf.com`, and `#0075`'s privacy policy is what promises
that. A permanent store of non-subscriber addresses that no erasure path
reaches is a promise the site does not currently keep for those people.

## What to decide

1. Does `auto_reply`'s `from` join `PrivacyPolicy.svelte`'s disclosure list and
   the erasure path? (Probably yes — it is a subscriber address like the other
   seven.)
2. What retention is right for a **non-subscriber** address in `audit_log`?
   Options worth weighing: redact the local part after some window; store a
   hash rather than the address for the non-subscriber reasons; add a retention
   sweep for `target_type = 'inbound_mail'` specifically; or accept permanence
   and disclose it plainly.
3. Whichever is chosen, does `PrivacyPolicy.svelte` need new wording, and does
   the erasure runbook need a step for this table?

## Acceptance criteria

1. A decision is recorded with its reasoning — an unexamined answer is not
   acceptable; any of the above is.
2. If retention changes, it does not weaken `#0499` criterion 2: the record
   must still outlive the 30-day S3 object, which is the whole point of it.
3. If disclosure changes, `PrivacyPolicy.svelte` and `#0237`'s known-sites
   fixture are updated together — see `#0502`, which must land first for the
   site to be visible to that guard at all.
4. `docs/` records where an erasure request has to reach.

## Notes

This is a **policy call, not an engineering one**, and it is the user's to make.
Do not implement a retention scheme before the decision is recorded. Note the
tension to resolve deliberately: the bucket holds raw inbound mail and is
deliberately short-lived, so the durable record exists precisely to outlive it —
the question is how much of a stranger's identity that record needs to keep in
order to remain actionable.
