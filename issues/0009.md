## Description

Bring across the admin console's user management, settings, and audit log screens, dropping the URL-filter tab that has no counterpart here.

> 🟢 Resolved 2026-08-18 — The three admin tabs, their handlers, and the `requireAdmin` route gating were already in place from the Phase 0 port; this pass added the missing `physical_address` settings row (migration `000008`, devstore seed, Settings-tab editor) and a route-table-level wiring test that the reviewer independently proved meaningful by re-running it against two separate guard removals.

## Root cause

Not a bug — feature/port work, and most of it turned out to already be done. `Admin.svelte` (three tabs: Settings/Users/Audit log), `internal/handlers/{settings,users,audit}.go`, and the `main.go` route table with `requireAdmin` composition all survived the Phase 0 port intact and already satisfied five of the seven acceptance criteria: the tab set, the Users/Audit log screens including deactivate/reactivate and pagination, `/admin/url-filters*` being absent (confirmed by grep — it never existed in this repo, consistent with `#0002` deleting the shortener backend before the SPA could reference it), and the `RequireSession`+`RequireAdmin` gating with the SPA already hiding the Admin nav entry for non-admins in `Account.svelte`.

The one real gap was `physical_address`: `#0007`'s Notes deliberately excluded it from `internal/config` so it could be added here as a `settings`-table value instead of an env var — `#0045`'s send worker reads it fresh from `settings` at send time, and CAN-SPAM (15 U.S.C. §7704) requires a non-empty physical postal address in every commercial message. Nothing seeded or exposed that key yet: no migration row, no devstore seed, no UI.

The secondary gap was proof, not code: the existing `NonAdminForbidden` tests in `settings_test.go`/`users_test.go`/`audit_test.go` each build their own small mux composing `requireAdmin` the same way `main.go` does, which proves the middleware composition is correct but not that `main.go`'s actual route table (`mountAndServe`) wires every `/admin/*` route through it. A future edit that added a route and forgot `requireAdmin` would go uncaught by those suites.

## Fix

- Added migration `000008_add_physical_address_setting` seeding `physical_address=''` (the store's `UpdateSetting` only mutates an *existing* key — see `internal/auth/store.go`'s `ErrSettingNotFound` — so the row must exist before an admin `PATCH` can ever set it). Applied it to both `opencircuit` and `opencircuit_test` via `migrate ... up` (now at version 8 on both).
- Seeded `physical_address` alongside `registrations_enabled` in `internal/devstore/devstore.go` so the `STORAGE=json` dev path has the same setting available.
- No change needed to `internal/handlers/settings.go`: `ListSettings`/`UpdateSetting`/`validSettingValue` are already key-generic (only `registrations_enabled` gets a format check; any other key, including `physical_address`, passes through as free text), and the admin/gating middleware in `main.go` already covers `GET`/`PATCH /admin/settings`.
- `web/src/views/Admin.svelte`: added a `physical_address` textarea + Save button to the Settings tab, below the existing `registrations_enabled` toggle. Tracks the last-saved value separately from the live input (`addressDirty`) so Save is disabled until the input actually differs, and shows an inline "Empty — campaigns cannot be sent until this is set" hint mirroring `#0045`'s refusal. Reuses the existing `getSettings`/`updateSetting` API calls — no new endpoint or `lib/api.ts` function needed.
- `internal/handlers/settings_test.go`: `resetSettings` now reseeds `physical_address=''` alongside `registrations_enabled='false'` so it matches the real two-row migration seed (previously it reset to a single-row shape that predates `#0009`). Added `TestAdminSettings_PhysicalAddressRoundTrip`, proving the seeded-empty state, a `PATCH` with free-text value, and that both the `PATCH` response and a subsequent `GET` reflect it.
- Added `cmd/opencircuit/admin_wiring_test.go` (`TestMountAndServe_AdminRoutesRequireSessionAndAdmin`), modeled on `#0008`'s `TestMountAndServe_RateLimitsAuthLoginStart`: it boots the real `mountAndServe` (the exact function `servePostgres` calls in production) over a live HTTP listener and drives `GET /admin/settings` for no session (401), a non-admin session (403), and an admin session (200) — proof against the route table itself, not a hand-rolled mux.
- Confirmed no `/admin/url-filters*` handlers, routes, or frontend calls exist anywhere in the repo (`grep -rni "url-filter"` — the only hits are `internal/audit/actions.go`'s retained `url_filter.*` audit action constants, explicitly out of scope per this issue's "Scope discipline" — `#0068` owns that file).

## Gotchas

- Migrations had to be applied by hand with the `migrate` CLI (`migrate -path migrations -database "$DSN" up`) against both `opencircuit` and `opencircuit_test` — there is no automatic migration-on-boot in this repo yet, so a fresh migration file alone does not make the DB-backed tests see the new row. Anyone else touching `physical_address` on a different checkout needs the same step.
- `t.Cleanup` funcs run *after* a test's own deferred statements, not interleaved with them — an early draft of `admin_wiring_test.go` had a standalone `defer pool.Close()` plus a separate `t.Cleanup(truncate)`, and the cleanup tried to query a pool `defer` had already closed. Fixed by folding truncate-then-close into one `t.Cleanup`, matching the existing `settingsTestPool`/`credsTestPool` convention.
- `web/src/lib/api.ts`'s `updateSetting` and `getSettings` are already key-generic, so no frontend API surface change was needed for `physical_address` — only the view.
- **Docs drift on the migration set (recorded at review, not fixed here).** `docs/database.md` still opens with "numbered `000001`–`000007` as of Phase 0" and its migration table stops at `000007`, and `CLAUDE.md` §1 likewise says `migrations/` is "contiguous `000001`–`000007`". Both are now one migration stale. The documented apply command (`migrate -path migrations -database "$DATABASE_URL" up`) is still correct and does reach version 8 on a fresh checkout, so reproducibility is intact — but the `000004_create_settings` table row should gain a sibling `000008_add_physical_address_setting` row noting it seeds `physical_address=''`. Fold this into the next issue that touches `docs/database.md`.
- **Criterion 6 is proven by inspection plus a single-route end-to-end spot check, not exhaustively.** `TestMountAndServe_AdminRoutesRequireSessionAndAdmin` drives `GET /admin/settings` only. The reviewer read `cmd/opencircuit/main.go` and confirmed all seven `/admin/*` routes (`GET`/`PATCH /admin/settings`, `GET /admin/users`, `GET /admin/users/{id}`, `POST /admin/users/{id}/deactivate`, `POST /admin/users/{id}/reactivate`, `GET /admin/audit`) are wrapped in `requireAdmin`, and the per-handler suites re-prove the composition for each. A future `/admin/*` route added without `requireAdmin` would still slip past the wiring test — the test's own comment is honest about `/admin/settings` being "representative". Consider a table-driven variant when the Phase 3–5 admin routes land.
