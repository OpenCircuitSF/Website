## Description

`CLAUDE.md` §7 records the production public IP as **`44.222.209.183`**.
Measured today, that is no longer where the site answers:

| Name | Resolves to |
|---|---|
| `www.opencircuitsf.com` | **`98.84.75.184`** |
| `ec2.smallsharptools.com` (the wildcard's CNAME target) | `44.222.209.183` |
| `*.opencircuitsf.com` | an **A** record at `98.84.75.184` |

**It is the same service**, so this is a stale fact rather than an outage:
`#0057`'s review confirmed `/.well-known/atproto-did` still hashes to §7's
expected `4198e742…5948d`, and Apache 2.4.68 / OpenSSL 3.5.7 still match.

The part worth a second look is not the number but the **split**. `www` and the
wildcard now answer at `98.84.75.184` while `ec2.smallsharptools.com` — which
§7 and `docs/` treat as the box — still answers at `44.222.209.183`. Those were
the same host when §7 was written. Either the instance was re-addressed and one
name was left behind, or there are now two hosts. Nobody has recorded which,
and the answer changes what "`ssh ec2` gets you there" means.

### A second, related error the same investigation found

`docs/email-setup.md` described the zone's wildcard as a **CNAME** to
`ec2.smallsharptools.com`. Measured against the authoritative nameserver
`ns-923.awsdns-51.net`, it is an **A record** at `98.84.75.184` — a CNAME query
returns empty. `#0057` corrected the three occurrences in that file
(`cc91629`); this issue covers `CLAUDE.md` §7 and any other file carrying the
old IP or the CNAME description.

## Notes

Found 2026-09-11 while preparing `#0057`'s DNS artifacts, and confirmed
independently by the orchestrator with `dig`.

**Do not "fix" this by editing the IP alone.** §7 is the file agents trust for
production facts, and a number updated without the explanation behind it
invites the same confusion next time. The reason `#0057` hit this at all is
that a rollback check told the reader to expect one IP at a name that serves
another — a stale fact in a rollback procedure is worse than no fact.

**Nothing here should change DNS.** This is a documentation-correctness issue.
If the investigation concludes a DNS record *is* wrong, file that separately
rather than changing a zone from inside a doc fix — and remember the apex MX
must never be touched (`CLAUDE.md` §9).
