# 0499 — "Left in place for manual review" has no reviewer, and the lifecycle rule deletes the evidence

| | |
|---|---|
| **Status** | open |
| **Platform** | All |
| **Module** | inbound / admin |
| **Phase** | 7 — Inbound and polish |

## Description

`#0058` criterion 5 says an inbound message matching neither the subject token
nor a known `From:` address is "logged, object left in place for manual
review, 200 returned". The implementation does exactly that. The gap is in the
criterion itself: **nothing constitutes the manual review.**

Concretely, an unmatched message produces:

- a log line on the box, and nothing else;
- no audit row;
- no admin surface listing parked objects;
- no counter, no metric, no alert.

Meanwhile `#0057`'s S3 lifecycle rule `expire-inbound-30d` deletes everything
under `unsubscribe/` after 30 days. So the full lifecycle of a failed
unsubscribe request is: arrive, get parked, be invisible, be deleted.

## Why this matters

This is the backstop for the other two failure modes in this subsystem. Both
`#0498` (a legitimate request misclassified as an auto-reply) and any future
parsing gap degrade into "the object sits in the bucket" — which is only a safe
degradation **if someone looks in the bucket**. Today nobody does, and after
30 days nobody can.

A silently-dropped unsubscribe request is precisely what `PRD.md` §6.5's three
mandatory paths exist to prevent.

## Suggested shape

The cheapest thing that closes it is a counter plus a place to look. Options,
roughly in increasing cost:

1. **An audit row** on the parked path, with a distinguishable source, so the
   existing audit surface shows them without new UI.
2. **An admin list view** of objects currently parked under `unsubscribe/`,
   read straight from S3 — the instance role already gets `s3:GetObject` on
   that prefix from `#0057` A11, so this needs `s3:ListBucket` scoped to the
   prefix as well.
3. **A periodic notice** when the parked count is non-zero, reusing whatever
   `#0469` settles on for backup-failure notices rather than inventing a second
   notification channel.

Option 1 alone is probably enough for v1 volumes and is a small change.

## Acceptance criteria

1. An unmatched inbound message leaves a durable, queryable record — not only a
   log line — that an admin can find without SSH access to the box.
2. That record survives the object's own 30-day expiry, or the expiry is
   reconsidered for unmatched objects specifically.
3. Criterion 5's behaviour is otherwise unchanged: still 200, still no
   redelivery loop, object still left in place.
4. Whatever surface is chosen is written into `docs/`, so the next person
   knows where to look.

## Notes

PRD §6.5 path 3. Note the tension to resolve deliberately rather than by
accident: the bucket holds raw inbound mail, so retaining it indefinitely has
its own privacy cost. Keeping a *record* of the failure longer than the
*message* is probably the right split.
