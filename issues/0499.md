## Description

`#0058` criterion 5 says an inbound message matching neither the subject token
nor a known `From:` address is "logged, object left in place for manual
review, 200 returned". The implementation does exactly that. The gap is in the
criterion itself: **nothing constitutes the manual review.**

Concretely, an unmatched message produces:

- a log line on the box, and nothing else;
- no audit row;
- no admin surface listing parked objects;
- no counter, no metric, no alert.

Meanwhile `#0057`'s S3 lifecycle rule `expire-inbound-30d` deletes everything
under `unsubscribe/` after 30 days. So the full lifecycle of a failed
unsubscribe request is: arrive, get parked, be invisible, be deleted.

## Why this matters

This is the backstop for the other two failure modes in this subsystem. Both
`#0498` (a legitimate request misclassified as an auto-reply) and any future
parsing gap degrade into "the object sits in the bucket" — which is only a safe
degradation **if someone looks in the bucket**. Today nobody does, and after
30 days nobody can.

A silently-dropped unsubscribe request is precisely what `PRD.md` §6.5's three
mandatory paths exist to prevent.

## Suggested shape

The cheapest thing that closes it is a counter plus a place to look. Options,
roughly in increasing cost:

1. **An audit row** on the parked path, with a distinguishable source, so the
   existing audit surface shows them without new UI.
2. **An admin list view** of objects currently parked under `unsubscribe/`,
   read straight from S3 — the instance role already gets `s3:GetObject` on
   that prefix from `#0057` A11, so this needs `s3:ListBucket` scoped to the
   prefix as well.
3. **A periodic notice** when the parked count is non-zero, reusing whatever
   `#0469` settles on for backup-failure notices rather than inventing a second
   notification channel.

Option 1 alone is probably enough for v1 volumes and is a small change.

## Acceptance criteria

1. An unmatched inbound message leaves a durable, queryable record — not only a
   log line — that an admin can find without SSH access to the box.
2. That record survives the object's own 30-day expiry, or the expiry is
   reconsidered for unmatched objects specifically.
3. Criterion 5's behaviour is otherwise unchanged: still 200, still no
   redelivery loop, object still left in place.
4. Whatever surface is chosen is written into `docs/`, so the next person
   knows where to look.

## Root cause

Not a bug — `#0058` built exactly what its own criterion 5 asked for
("logged, object left in place for manual review, 200 returned"). The
criterion itself named no reviewer: a log line on the box is not a review
mechanism an admin can reach, and `#0057`'s `expire-inbound-30d` lifecycle
rule deletes the S3 object 30 days later regardless, so the evidence a
request ever arrived does not outlive the log rotation on the box.

## Fix

Implemented option 1 from the Suggested shape above — a durable audit row
on the parked path, reusing the existing `audit_log`/`GET /admin/audit`
machinery rather than building new admin UI or a periodic-notice channel
(both of which `#0469` still has open design questions about, per
`## Relation` below).

**Scope: all three left-in-place outcomes, not only "unmatched".** The
acceptance criteria's own wording ("an unmatched inbound message") and
`#0058`'s criterion 5 both name the token/From no-match case specifically,
but `## Why this matters` frames this issue as the general backstop for
"the object sits in the bucket" — explicitly including `#0498`'s
auto-reply-misclassification shape. Since `internal/handlers/
ses_inbound.go`'s `handleNotification` already has three branches that
leave a real, known-key S3 object behind without acting on it —
unparseable message, auto-reply, and no token/From match — all three now
call the same `recordParked` helper. (Two earlier branches, an
unparseable SES *event* and an unresolvable object key, are deliberately
untouched: neither reliably names a real S3 object to point an admin at,
and the latter is `#0500`'s territory.)

**What's recorded.** A new `audit.ActionInboundMailParked` row
(`target_type = audit.TargetInboundMail`, `target_id` nil — mirrors
`TargetSNSTopic`'s convention for a target with no BIGINT id) with
metadata: `key` (S3 object key), `message_id` (the SNS envelope's
`MessageId`, matching every other log line in this file), `reason` (one of
`unparseable`, `auto_reply`, `token_not_found`, `from_not_found`,
`no_identifying_signal` — reconstructed from `ParsedMessage.Token`/`.From`
rather than widening `match`'s own return signature), and `from`/`subject`
when the parse got far enough to produce them (omitted, not stored empty,
when it didn't — e.g. the unparseable-message case has neither). Never the
message body. `internal/inbound.ParsedMessage` gained a `Subject` field
(the same MIME-decode `extractToken` already applied to the raw header,
factored into a shared `decodeMIMEHeader` helper) since nothing previously
surfaced the decoded subject line outside the token regex.

**Criterion 3 (still 200, no redelivery loop) is unchanged by
construction:** `recordParked` is called and its result never inspected —
`w.WriteHeader(http.StatusOK)` follows unconditionally in every branch,
exactly as before. `recordParked` itself is a no-op when `h.auditor` is
nil, and the write goes through `audit.Logger.Record` — the existing
log-and-swallow path this file's `handleSubscriptionConfirmation`/
`handleUnsubscribeConfirmation` already use for their own audit rows — so
a failed insert can never surface as anything but a WARN log line. No
reordering: the auto-reply check still runs first, and `match`'s
token-before-`From:` precedence (including the stale-token
doesn't-fall-back-to-From rule) is untouched.

**Migrations: none needed.** `audit_log` (migration `000005`) has no
retention/expiry mechanism of its own, so satisfying criterion 2 ("survives
the object's 30-day expiry") required no schema change at all — reusing
the existing table is what makes this option genuinely cheap, not just
nominally so.

**A privacy-disclosure question I'm surfacing rather than deciding.** The
`from`/`subject` metadata can carry a real email address and free-text
subject line. `internal/handlers/audit_email_metadata_guard_test.go`
(`#0237`) — the repo-wide guard that forces every audit site carrying an
email address into `auditEmailMetadataKnownSites` *and*
`PrivacyPolicy.svelte`'s disclosure list — does not flag this site, because
`"from"` is not one of its suspect-key tokens (`email`, `address`,
`recipient`, `query`, `to`, `mail`, `contact`). That's a genuine gap in the
guard's heuristic, not a design choice I made to dodge it: I kept the
natural key name (matching `pm.From`/`match`'s own `"from"` `matchedVia`
value) rather than renaming it to trigger detection, since deciding
whether a raw email seen on the *no-match* path (by definition NOT a
current subscriber, for the `token_not_found`/`from_not_found`/
`no_identifying_signal` reasons) should be added to a legally-worded
privacy policy is a policy call outside a phase-2 implementer's remit, not
a mechanical one. The `auto_reply` reason is the one case where `from` can
be a genuine subscriber's own address (an out-of-office bouncing off a
real campaign). Flagging for review, not filing per `CLAUDE.md` §9.

## Review notes

Reviewed `3b893c6` independently (Opus, phase 3). **Approved on the first
pass**; no design bounce arose, so per `CLAUDE.md` §3 implementation stays on
Sonnet and no escalation was considered.

### The widened scope is right

Covering all three left-in-place branches rather than only the literal
"unmatched" one is the correct reading, not an overreach. `#0058`'s criterion 5
names the token/`From:` no-match case because that is the branch *it* built;
this issue's own `## Why this matters` names the general shape ("the object
sits in the bucket") and cites `#0498` — a legitimate request misclassified as
an auto-reply — as the motivating case. A fix scoped to the no-match branch
alone would have closed the backstop everywhere except the one failure mode the
issue was filed about. The two branches deliberately left alone (an unparseable
SES *event*, an unresolvable object key) are correctly excluded: neither names a
real S3 object, so a record of one would point an admin at nothing.

### The privacy question: declining to decide was correct

Three things, in the order they were asked.

**1. Declining was right, and structurally forced.** Registering this call site
in `auditEmailMetadataKnownSites` is not possible without first widening
`#0237`'s heuristic. That guard compares its fixture against a live scan and
fails on drift in *either* direction, so a fixture entry the scanner does not
itself classify as an email carrier fails as a "known site disappeared". The
only ways to register it were to widen the guard — which its own header says
must be "a deliberate, reviewed change to this file, not a byproduct" — or to
rename the metadata key to trip the heuristic, which would be exactly the
"store a copy of the answer next to the question" evasion `CLAUDE.md` §8 warns
about. The implementer took neither shortcut and said so in the open. That is
the behaviour the rule wants.

**2. Storing `from` here is acceptable, and in fact load-bearing.** Criterion 1
asks for a record "an admin can find" and act on. A parked record without the
sender's address is not actionable: the S3 object it points at is deleted in 30
days, after which the row names a key that no longer resolves and a message
nobody can answer. The address is what makes this a review mechanism rather
than a counter. It is proportionate — the project already stores subscriber
addresses in `subscribers` and at seven other `audit_log` metadata sites — and
the body is correctly excluded.

Two follow-on points that are **not** grounds to bounce but are worth deciding
deliberately, because this issue's own `## Notes` predicted the tension and the
implementation resolves it one specific way:

- The `auto_reply` reason writes a **current subscriber's own address**; the
  test asserts `from == created.Email` against a real seeded row, so this is
  measured, not hypothetical. That is materially the same category as the seven
  sites the privacy page already discloses, and it should join them.
- The `from_not_found` / `no_identifying_signal` reasons write the address of
  someone with **no relationship to the project at all**, into a table that is
  append-only with no expiry and no erasure path (erasure is keyed to
  subscribers). `## Notes` above said "keeping a *record* of the failure longer
  than the *message* is probably the right split" — `audit_log` makes it
  permanent rather than merely longer, which is a defensible reading of
  criterion 2 ("survives the object's own 30-day expiry") but is a stronger
  commitment than "longer".

**3. `#0237`'s heuristic is genuinely under-covering, and the fix is not a
one-liner.** Verified by running `scanAuditEntrySites` directly rather than
reasoning about it: the new site at `ses_inbound.go:366` is **seen and
resolved** — `hasEmail=false, unresolved=""` — so it is a classification miss,
not one of the documented structural blind spots.
`metadataKeyIsSuspectedEmailCarrier("from")` returns false. `"from"` is the
canonical email-bearing header name in this entire subsystem, and its
counterpart `"to"` is already in the token set (added for
`admin_campaign_preview.go`), which makes the omission an oversight rather than
a considered exclusion.

The reason it needs its own issue rather than a token addition here: a census of
every string-literal map key in production `internal/` and `cmd/` (205 distinct
keys) shows adding `"from"` as a token is **not free** the way `"mail"` and
`"contact"` were. `admin_campaigns.go` writes `"from_status"` — a campaign
draft→sending transition — which splits to tokens `from`/`status` and would be
dragged in as a false positive, the exact hazard the guard's own doc comment
records for `"recipients"`. The same census rules out `"subject"` as a token:
`delivery_health.go`'s `"subject"` and `admin_campaigns.go`'s
`"old_subject"`/`"new_subject"` are our own campaign copy, not user data. So
closing this needs an exact-key rule or a compound-token rule, plus a decision
about which of this site's reasons to disclose — reported to the orchestrator
for filing per `CLAUDE.md` §9, not fixed here.

**Criterion 3's failure path proved empirically, not only by reading.** A
throwaway probe test built the handler with `audit.New(pool)` over a
deliberately **closed** pool, so every insert errors. Result: `WARN audit:
write failed (action recorded, audit row lost) … err="… closed pool"`, HTTP
**200**, object still present in the store. So a failed audit write cannot
produce the 500 that would make SNS redeliver and loop. `audit.Logger.Record`
was read directly (`internal/audit/audit.go:113`): it returns nothing and logs
the insert error rather than propagating it. The probe file was removed;
`git status` confirmed clean afterwards.

**Criterion 2**, checked at the source rather than from the summary:
`migrations/000005_create_audit_log.up.sql` declares the table "append-only …
Rows are never updated or deleted" and defines no retention mechanism; no
`DELETE FROM audit_log` exists anywhere in the tree outside one test helper
scoped to `target_type = 'email_campaign'`. The record genuinely outlives
`expire-inbound-30d`.

**Criterion 4**, checked as an executable claim rather than a documented one:
`GET /admin/audit` is routed at `cmd/opencircuit/main.go:1211`;
`AdminAuditHandler.List` reads `?target_type=` as a free-form string with no
allowlist and passes it to `audit.Filter`, whose `whereClause` emits a
parameterized `target_type = $N`; `ListAuditLog`'s doc comment explicitly notes
that a machine-written row with a NULL `actor_id` is reachable through
`TargetType` exactly like an operator-written one, which is what this row is.
The SPA side of the claim also holds — `Admin.svelte`'s audit screen carries
the `#0114` target-type filter field (`parseAuditTargetFilter` in
`web/src/lib/admin.ts`). The documented query works as written.

**`decodeMIMEHeader` is behaviour-neutral for `extractToken`.** The old form
assigned `subject = decoded` only when `err == nil` and otherwise left the raw
value; the helper returns `decoded` when `err == nil` and `raw` otherwise, and
`extractToken`'s first line now assigns its result. Same value on both paths,
with no other caller of the old inline form. `internal/inbound` passes.

**`noMatchReason`'s three branches map onto `match`'s no-match returns
one-to-one**, checked against `match`'s actual control flow: a present token
that fails to resolve returns `""` without ever trying `From:` (the stale-token
rule), so `pm.Token != ""` uniquely means `token_not_found`; an absent token
with an absent `From:` short-circuits before any lookup
(`no_identifying_signal`); otherwise the `From:` lookup returned `ErrNotFound`
(`from_not_found`). `match`'s genuine *error* return still takes the 500 path
and correctly writes no record.

**Ordering and deletion unchanged.** `handleNotification` still parses, then
checks `AutoReply`, then matches; `recordParked`'s return value is never
inspected and `w.WriteHeader(http.StatusOK)` follows unconditionally in all
three branches. The only `Delete` remains inside `handleMatch`, so deletion
stays confined to processed messages.

**Mock-based verification is the correct standard here** and the `##
Verification` section says so explicitly: `#0057`'s bucket and topic are built
but not activated and no `lists.opencircuitsf.com` MX is published, so there is
no live path to test against (`CLAUDE.md` §10).

1. **`#0237`'s suspect-key heuristic misses `"from"`** — the detail, including
   the `"from_status"` false-positive that makes a bare token addition wrong,
