## Description

Per-campaign outcome: how many sent, failed, bounced, and complained, with the ability to drill into failures.

## Acceptance criteria

- [ ] `GET /admin/campaigns/{id}/stats` returns counts by send status
- [ ] Bounce and complaint counts reconciled from `email_events`
- [ ] Complaint rate shown as a percentage with a visible warning above 0.3%
- [ ] Failed sends listable with their error messages
- [ ] Stats view linked from the campaign list
- [ ] Handler and component tests pass

## Carried in from `#0044`'s plan (2026-08-21)

- [ ] **`skipped` is its own bucket, distinct from `failed`.** A skipped
      recipient unsubscribed or was suppressed between materialization and
      send; counting it as a failure would misreport a correctly-working
      unsubscribe path as a delivery problem.

## Carried in from `#0045`'s plan (2026-08-21)

- [ ] **`email_sends` gains a seventh status, `sending`** (migration `000018`).
      A stats view that buckets only the original six silently drops every row
      in flight at the moment it is read.

## Carried in from `#0047`'s review (2026-08-21)

Recorded after reading the shipped compose UI (`9f8895c`), which is the screen
this one is linked from.

- [ ] **"Stats view linked from the campaign list" has no link yet.**
      `web/src/views/admin/Campaigns.svelte` renders a table of
      Name / Status / Updated rows whose only control opens the editor. Adding
      the stats affordance means a column or a per-row control there, plus a
      third arm on that component's master/detail swap (it is currently a
      binary `{#if hasSelection}` between list and `CampaignEditor`).
- [ ] **Admin-only views live in `web/src/views/admin/`.** `#0047` created that
      directory; put the stats view there rather than in `web/src/lib/`, which
      holds reusable motif components, or inline in `Admin.svelte`, which is
      already ~2,050 lines across seven sections.
- [ ] **"Handler and component tests pass" is not achievable as written.**
      `#0094` records that no test in this repository imports a `.svelte` file —
      there is no jsdom and no component harness, so a "component test" cannot
      exist until `#0094` decides to add one. Follow `#0047`'s convention
      instead: put every decision (bucket ordering, the 0.3% threshold verdict,
      percentage formatting, the reconciliation of `email_sends` against
      `email_events`) in a pure `web/src/lib/` module with its own vitest file,
      and keep the component to markup and wiring. Read that criterion as
      "handler tests and `lib/` unit tests pass".
- [ ] **The complaint-rate threshold is a client-side number, unlike everything
      else on these screens.** `#0047` renders the server's `unmet` list and
      warnings verbatim precisely so no requirement exists in two places. 0.3%
      is a presentation threshold rather than a server rule, so a client-side
      constant is defensible — but it belongs in the `lib/` module with a test
      pinning both sides of the boundary, not inline in the component.

## Notes

PRD §11. The 0.3% complaint threshold is Gmail's published limit — crossing it is what gets a sending domain throttled or blocked, so surfacing it prominently is the whole point of this screen rather than a nice-to-have metric.
