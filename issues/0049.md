## Implementation

**Endpoint.** `GET /admin/campaigns/{id}/stats`
(`internal/handlers/admin_campaign_stats.go`, `AdminCampaignStatsHandler`),
registered through `adminRoutes()` (mirroring `#0047`'s `.../preflight`
pattern, `#0079`'s guard-by-table rule) and nil-tolerant in
STORAGE=json/dev mode. Deliberately **not** gated on `MAILER_NOOP` the way
`adminCampaignPreflightH` is (`sendStore == nil` under `MAILER_NOOP=true`):
whether *this* instance can send has no bearing on whether a past campaign's
outcome can be read, so `campaignStatsStore`/`adminCampaignStatsH` are
constructed unconditionally in `cmd/opencircuit/main.go`'s Postgres path.

**Store.** `internal/mailing/campaign_stats.go`'s new `CampaignStatsStore`,
deliberately its own store rather than added to `SendStore` (worker-only
audience/settings/render deps this read doesn't need) or `CampaignStore`
(the CRUD write path):
- `StatusCounts` — raw `COUNT(*) FILTER (WHERE status = …)` over all seven
  `email_sends.status` values.
- `EventCounts` — the reconciliation: `email_sends JOIN email_events ON
  e.ses_message_id = s.ses_message_id`, `COUNT(DISTINCT s.id) FILTER (WHERE
  event_type = 'Bounce'/'Complaint')`. This is the load-bearing piece: I
  confirmed by grep (`internal/sesnotify/*.go`, `internal/mailing/worker.go`)
  that **nothing in this codebase ever writes `email_sends.status` to
  `'bounced'`/`'complained'`** — SES/SNS bounce and complaint notifications
  (`#0038`) land exclusively in `email_events` and never touch `email_sends`.
  So `StatusCounts.Bounced`/`.Complained` are always 0 in production
  regardless of real bounce/complaint volume, and `EventCounts` — joined via
  `ses_message_id`, using `idx_email_sends_message_id`/
  `idx_email_events_message_id` (both already indexed for exactly this join
  per migration `000017`'s own comment) — is the only source of truth. This
  is the "reconciliation" the acceptance criterion asks for. `DISTINCT s.id`
  (not a plain row count) so a recipient bounced twice counts as one
  affected recipient, matching what the 0.3% threshold is actually defined
  against.
- `FailedSends` — every `status='failed'` row, `id`, `email`,
  `coalesce(error, '')`, `attempts`, ordered by `id`.

**Response shape**: `{campaign_id, status, counts: {queued, sending, sent,
failed, bounced, complained, skipped}, reconciled: {bounced, complained},
failed_sends: [{id, email, error, attempts}]}`. `counts` carries the raw
seven-bucket vocabulary (the literal acceptance criterion); `reconciled` is
the separate, actually-meaningful bounce/complaint figure.

**Client lib module**: `web/src/lib/campaignStats.ts` (17 vitest cases in
`campaignStats.test.ts`), owning every presentation decision per `#0047`'s
convention:
- `buildStatBuckets` — the ordered bucket list (`sent` leads as the headline
  success; `queued`/`sending` next as in-flight, not-yet-an-outcome;
  `failed`/`bounced`/`complained` as the operator-actionable problems;
  `skipped` last and its own bucket, distinct from `failed`). Critically,
  `bounced`/`complained` buckets read from `stats.reconciled`, **not**
  `stats.counts.bounced`/`.complained` — rendering the always-zero raw figure
  on the one screen whose purpose is surfacing real bounces/complaints would
  be actively wrong.
- `complaintRateVerdict`/`campaignComplaintRateVerdict` — rate =
  `reconciled.complained / counts.sent * 100` (Gmail's own definition:
  complaints ÷ *sent*, not ÷ total audience); `sentCount <= 0` reads as rate
  0 and not-over-threshold (never a false-positive warning on a fresh
  draft); the 0.3% boundary is **inclusive** (`>=`) — "exactly at the
  ceiling" reads as already crossing it.
- `failedSendErrorLabel` — falls back to "No error message recorded" for a
  blank/whitespace-only error (the Go handler coalesces `NULL` to `""`,
  never omits the key).
- `canViewCampaignStats` — `false` only for `draft` (never materializes
  `email_sends` rows; every other status can, including `scheduled`, which
  is included and simply renders all-zero — simpler and no less correct
  than inventing a second "not yet" state).

**View**: `web/src/views/admin/CampaignStats.svelte`, in
`web/src/views/admin/` per the carried-in note, markup and wiring only —
loads via `getCampaignStats` on mount, renders the status badge (reusing
`lib/campaigns.ts`'s `campaignStatusLabel`/`campaignStatusBadgeClass`), the
complaint-rate banner, the bucket grid, and a failed-sends table shown only
when `failed_sends` is non-empty.

**Linked from the list**: `Campaigns.svelte`'s binary `{#if hasSelection}`
(list ⟷ editor) is now a three-way `mode: 'list' | 'editor' | 'stats'`
(`isListView`/`isEditorView`/`isStatsView`, `activeCampaignId`), with a
fourth "Stats" table column carrying a per-row link button
(`disabled={!row.canStats}`, `row.canStats = canViewCampaignStats(c.status)`).

## Gotchas

- The single most important fact in this issue: `email_sends.status`'s
  `'bounced'`/`'complained'` values (allowed by the CHECK constraint since
  migration `000014`) are **dead code paths in production** — nothing
  writes them. A naive implementation that just did
  `COUNT(*) FILTER (WHERE status = 'bounced')` would compile, pass a
  shallow smoke test (0 bounces on a fresh campaign), and silently report
  zero complaints forever on a domain that is actually being throttled by
  Gmail. This is why `TestAdminCampaignStats_ReconcilesBounceAndComplaintFromEvents`
  asserts the raw `counts.bounced`/`.complained` are 0 *in the same test*
  that proves `reconciled.bounced`/`.complained` are correct — a reviewer
  changing the query to read the "obviously right-looking" raw column
  would see that test fail immediately.
- `mountAndServe`'s parameter list is now 25 positional arguments long
  across `main.go` and 9 wiring-test call sites; every one needed a
  mechanical edit for this one new handler. This is the same shape
  `#0047`'s own review already lived through for `adminCampaignPreflightH`
  — no new pattern, just more of the existing one.

**1. The dead-status finding — real, and larger than this issue.**

The implementer's claim is confirmed. `email_sends.status` has exactly five
reachable values (`queued`, `sending`, `sent`, `failed`, `skipped`), but
three places document seven: PRD §6.2 line 129 lists
`queued | sending | sent | failed | bounced | complained | skipped`;
`migrations/000017`'s `email_sends_status_check` permits `'bounced'` and
`'complained'`; and `migrations/000018` re-adds the constraint carrying both
forward. `internal/sesnotify` writes bounce and complaint notifications
exclusively to `email_events` and never touches `email_sends`, so the schema
is documenting two states no code path can produce.

This is not a defect in `#0049` — the issue handled it correctly, and
arguably the only correct way: it reports the raw seven-bucket vocabulary
verbatim (satisfying the literal criterion) while surfacing the reconciled
figures to the operator, and
`TestAdminCampaignStats_ReconcilesBounceAndComplaintFromEvents` asserts the
raw buckets are 0 *in the same test* that proves the reconciled ones are
right, so a future change to the "obviously right-looking" raw column fails
immediately. That is the right shape of guard.

It does warrant a follow-up issue (next free number is `#0131`), because the
resolution is a design decision outside this issue's scope: either `#0038`'s
ingestion should also stamp `email_sends.status`, making the raw column
meaningful and the JOIN a cross-check, or the two values should be dropped
from the CHECK in a new migration and struck from PRD §6.2, making the schema
honest. Leaving it undecided means every future reader of `email_sends`
re-derives this the hard way. Recommended, not filed — the orchestrator's
call.
