# 0711 — Client-side navigation leaves stale preview meta, so Messages shares the wrong card

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web, seo |
| **Phase** | 10 — Outreach |

## Description

User report, 2026-11-17: sharing `https://www.opencircuitsf.com/guides/bjt-vs-mosfet` to Apple Messages showed the title "Guides" and the default `/og-default.png` card, while Bluesky showed the guide's own art (`#0709`).

Cause, from the production access log: Messages did not fetch the page. Sharing from Safari, LinkPresentation read the metadata from the **open tab's live DOM**. The user had loaded `/guides` and navigated client-side to the guide. The SPA updates `document.title` on navigation (`#0238`, `web/src/lib/pageTitle.ts`, `App.svelte`), but never the `<head>` meta the server rendered for the first page: `og:title`, `og:description`, `og:image`, `og:url`, `twitter:*`, `description`, and `link rel=canonical`. So the tab still carried `/guides`'s preview meta. The log shows `com.apple.WebKit.Networking` fetching `/og-default.png` at 01:41:43 UTC, and no document request for the guide from that client.

Crawlers and Bluesky fetch the URL fresh and get correct server-rendered meta (`internal/seo`), so only live-tab sharing (Safari share sheet, Messages, Notes, AirDrop, possibly Chrome's share) is affected.

Fix: on client-side navigation, update the head meta to match what the server would render for the new route — at minimum `og:title`, `og:description`, `og:url`, `og:image`, `link rel=canonical` and `meta name=description`, with `og:image` using the guide's `/guides/{slug}/og.png` URL. The `?v=` hash isn't known client-side; decide whether that matters for live-tab sharing (it reads the DOM, not a cache keyed on the URL). Keep a single source of truth with the server where practical (the server already knows each route's meta; the SPA has the guide catalog in `web/src/content/guides/guides.json`).

## Acceptance criteria

- [ ] After client-side navigation from `/guides` to `/guides/{slug}`, the document's `og:title`, `og:description`, `og:url`, `og:image`, canonical link and description match the server-rendered values for `/guides/{slug}` (allowing the `?v=` suffix difference if the plan justifies it).
- [ ] The same holds for at least the other public routes the server renders specific meta for (events, workshop guide, archive), or the plan names which routes are covered and why.
- [ ] Navigating back to a generic page restores generic meta (no guide meta lingering).
- [ ] A test proves it (jsdom), and a parity guard keeps the client meta from drifting from the server's for guides.
