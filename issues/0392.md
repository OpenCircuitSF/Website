## Description

**Five times this phase**, a guard's own documentation tripped a sibling guard.
`#0384`'s reviewer nearly made it six while writing its review notes — by citing
a fabricated `Test…` name that the sibling test-name guard would have flagged had
the issue not just moved to `resolved`. It caught and rephrased it.

The pattern is structural, not carelessness. A guard that forbids a textual shape
must be **described** using that shape — the doc comment explaining why
`<file>.go:<int>` citations are forbidden wants to show one; the test proving a
`go test -v` transcript is exempt wants to contain one.

Recorded instances this phase include `#0347`'s doc comment tripping its own
directional axis, `#0356`'s guard flagging text written to explain it, `#0374`'s
records quoting real wrapped comment text, `#0384` tripping
`TestNoCommentCitesUnresolvedPathOrSection` with an illustrative path, and
`#0366`'s prose constrained by the guard it documents.

**The cost is real but bounded**: each instance cost a rephrase, and in one case
a red HEAD for ~18 minutes (`#0381`). None was a defect in the guard.

## What already works, and is worth generalising

`#0384`'s fix is the strongest precedent: it moved a concrete `go vet` example
out of a **comment** and into a **test body as an asserted string literal**. That
is strictly better than rephrasing —

- decorative comment text became an **executed assertion**;
- a string literal is not a comment, so the comment-scoped guard is satisfied
  **for the right reason** rather than by evasion;
- the example is now pinned, so it cannot drift from the pattern it illustrates.

`#0347` reached a weaker version independently: rephrase rather than delete,
because deleting also goes green and leaves no trace.

## Acceptance criteria

1. **Decide whether this needs recording at all, and say so explicitly.** The
   honest answer may be that five rephrases is a tolerable cost and a convention
   note buys nothing — three guard families this phase (`#0330`, `#0347`,
   `#0356`) ended by recording a limit rather than acting, and one (`#0381`)
   ended by recording a lookup rather than building. **"Record nothing, close
   this" is a legitimate outcome** if argued.
2. If recorded: the convention goes where an author writing guard documentation
   will meet it — §8's guard-family rules, or each guard family's own header —
   and states the **string-literal-assertion** technique concretely, with
   `#0384`'s instance named as the worked example.
3. **Do not build a mechanism.** There is no defect to fix; the guards are
   behaving correctly in every recorded instance. A checker for "documentation
   that would trip a sibling guard" is precisely `#0258`'s spiral.
4. **Re-verify the five instances** rather than trusting this issue's list —
   several details in issues this phase were transcribed rather than measured,
   including a floor figure the orchestrator propagated nine times. If the count
   is wrong, say so; the argument depends on the pattern being frequent, not on
   the exact number.
5. Whatever you write must not itself trip a guard. **That is the test of
   whether the advice is any good** — if the convention cannot be stated without
   violating itself, that is the finding, and it should be reported rather than
   worked around.
6. Documentation only. Run `./internal/db/...` and `./internal/handlers/...`
   (`#0381`); your issue-file edits are in scope of `#0384`'s guard while this is
   `in-progress`. `gofmt` stability if any Go file is touched.
