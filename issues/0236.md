## Description

> ✅ **Resolved 2026-08-24** (`fc2bd14`) — the script now fails closed before
> it touches the filesystem or the database, and the unit sets
> `BACKUP_DATABASES` explicitly. Re-verified at review against the committed
> tree, and the "backs up the wrong project" branch turned out to be worse
> than the implementer could show: `shortlinks` is a real, populated database
> on this machine.

`deploy/systemd/opencircuit-backup.service` ships with `BACKUP_DATABASES`
**commented out**. `scripts/db/backup.sh` then falls through to its own default,
which is the literal `shortlinks` — **the other project's database**, inherited
when the script was ported from ShortLinks by `#0001`.

The failure is loud rather than silent: on this box `shortlinks` either does not
exist, so `pg_dump` fails and the `OnFailure=` alert fires, or it does exist and
the timer quietly backs up the wrong project every night while Open Circuit is
never backed up at all. Which of those happens depends on whether ShortLinks
shares the instance — and `CLAUDE.md` §10 item 6 records that we do not yet know
whether the existing Postgres is the target.

Either way the operator learns about it from an alert or an empty backup
directory, not from the install.

**This is a one-line fix with a disproportionate consequence**, which is exactly
the kind of thing a runbook step should not leave optional. A commented-out
variable reads as "optional tuning" and is in fact load-bearing.

## Implementation notes

Did **both** halves the acceptance criteria offer as alternatives, since each
alone is a single point of failure and this bug's whole shape is "a single
point of failure had a disproportionate consequence":

1. **`deploy/systemd/opencircuit-backup.service`** — uncommented and set
   `Environment=BACKUP_DATABASES=opencircuit` (this project's own database),
   with a comment explaining why it's required rather than optional tuning.
2. **`scripts/db/backup.sh`** — removed the fourth, silent fallback
   (`DATABASES=("${db_from_env:-shortlinks}")`). The resolution order is now:
   positional args → `$BACKUP_DATABASES` → the `.env` `DATABASE_URL`'s db
   name → **hard error, exit 2**, naming exactly which of the three sources
   was checked and came up empty, and naming the pre-fix "shortlinks"
   behavior explicitly so a future reader understands why there's no
   fallback left to restore.
3. **`docs/deployment.md`** and **`deploy/systemd/README.md`** — both now
   call out `BACKUP_DATABASES` as a required install step (a new callout at
   the top of the "Schedule and failure alert" section in the former, an
   addition to the "edit the unit file" paragraph in the latter), not a
   suggestion to uncomment if you feel like it.

**Sweep of `scripts/db/` for other inherited ShortLinks defaults (the
issue's Notes asked for this), reported here rather than fixed — out of this
issue's scope:**

`scripts/db/pull-backups.sh` defaults `BACKUP_SSH_HOST` to
`ec2-user@go.sstools.co` (line 27, and documented as the default in its own
header comment). This reads like a real ShortLinks production hostname
(`go.` prefix, a domain unrelated to `opencircuitsf.com`), not a
generic placeholder — the same shape of defect as this issue, but on the
*pull* side rather than the *dump* side, and with SSH rather than a database
name: if this script is ever run unmodified with `BACKUP_SSH_HOST` unset, it
attempts to pull backups from a stranger's host. Unlike `backup.sh`'s
`BACKUP_DATABASES`, `pull-backups.sh` has **no** systemd unit or install-step
documentation pointing at `BACKUP_SSH_HOST` at all in this repo, so there is
no analogous "required, not commented out" fix to make yet — this is a
finding for whoever wires up the offsite pull (`#0064`/Mac mini setup), not
a code change made here, since fixing it well needs to know the real value
to put in its place, which nobody has yet. `create.sql`, `drop.sql`,
`restore.sh`, and `backup-alert.sh` were also checked and found clean — their
defaults (`opencircuit` role/database name, `RESTORE_OWNER=opencircuit`) are
already this project's own, not inherited.

## Verification

`bash -n scripts/db/backup.sh` and `shellcheck scripts/db/backup.sh` — both
clean, no warnings.

**Fail-closed path, run for real** (no `TEST_DATABASE_URL` needed — this is
shell script behavior, not a Go test; no `.env` exists in this checkout,
matching the exact scenario the issue describes):

```
$ unset BACKUP_DATABASES
$ BACKUP_RUN_AS="" bash scripts/db/backup.sh; echo "exit: $?"
ERROR: no database to back up was configured, and this script now refuses to guess.

Checked, in order:
  1. command-line arguments        (none given)
  2. $BACKUP_DATABASES             (unset or empty)
  3. DATABASE_URL in .../.env (not found, unreadable, or unparseable)

This script no longer defaults to a database name — a prior version silently
fell back to the literal "shortlinks" ...
exit: 2
```

**Positive path unaffected** — with `BACKUP_DATABASES` set, a real
`pg_dump -Fc` still runs and produces a dump (`opencircuit_test_template`
used as a harmless stand-in database for this check): `ok — 56K` /
`Done — all databases backed up.`, exit 0.

**Mutation test against the pre-fix script** (copied out, not stashed, per
`CLAUDE.md` §8a: `git show HEAD:scripts/db/backup.sh > /tmp/old-0236-backup.sh`).
Same unset/no-args/no-`.env` scenario against the OLD script:

```
$ unset BACKUP_DATABASES
$ BACKUP_RUN_AS="" bash /tmp/old-0236-backup.sh
============================================================
 databases:  shortlinks
============================================================
mkdir: /var/backups/postgres: Permission denied
exit: 1
```

This is exactly the bug: the old script silently picked `shortlinks` and
proceeded — the only reason it failed at all on this dev machine is an
unrelated permission error creating `/var/backups/postgres` (root-owned by
default). On a real server where that directory is writable (the documented
production path, `postgres`-owned), this would have **exited 0** having
backed up a database with nothing to do with this project, or failed with a
`pg_dump` error about a nonexistent database — either way silently, with no
indication anything was misconfigured. The new script fails immediately and
explicitly, before ever touching the filesystem or the database.

## Review notes

Independent phase-3 re-verification (Opus). This is shell-script behavior on
this machine against a real local PostgreSQL 16 cluster — the *unit file* half
rests on reading, not on running systemd, because deployment is deferred
(`CLAUDE.md` §10) and there is no box. That distinction is stated rather than
blurred: nothing below claims the timer has fired anywhere.

**A caution about what I ran against.** While this review was in flight another
agent was mid-change on `scripts/db/backup.sh` for `#0245`, so the working copy
was dirty. Every check below was therefore re-run in a throwaway `git worktree`
pinned to the committed tree, and the other agent's in-flight diff was
confirmed to be **comment-only** (`git diff` — usage examples and the directory
tree illustration, no behavioral lines). Nothing of theirs was touched, staged,
or committed by this review.

**1. Fails closed, and does so before anything happens.** Against the committed
script, with no `.env` in the checkout (the exact scenario the issue describes):

```
$ env -u BACKUP_DATABASES BACKUP_RUN_AS="" bash scripts/db/backup.sh
ERROR: no database to back up was configured, and this script now refuses to guess.
Checked, in order:
  1. command-line arguments        (none given)
  2. $BACKUP_DATABASES             (unset or empty)
  3. DATABASE_URL in …/.env (not found, unreadable, or unparseable)
…
exit: 2
```

**The failure genuinely precedes the destructive and long-running work**, which
is the part worth proving rather than assuming — checked two ways. Statically:
the `exit 2` is at line 117, `mkdir -p "$BACKUP_ROOT"` at line 150 and the
first `pg_dump` at line 171. Dynamically: run with `BACKUP_ROOT` pointed at an
empty scratch directory, the run exits 2 and **the backup root is never
created** (`ls -d …/root` → `No such file or directory`).

`BACKUP_DATABASES=""` (explicitly empty, not merely unset) takes the same path
— the `-n` test is correct here.

**2. The unit really sets it.** `grep -c '^Environment=BACKUP_DATABASES=opencircuit$'`
→ `1`, uncommented, at line 39, with the `#Environment=BACKUP_DATABASES=…`
line removed from the "optional overrides" block rather than left as a
confusing duplicate. Read the whole unit: `WorkingDirectory`'s comment still
correctly describes `.env` as a *fallback* source, which it remains
(resolution order is args → `$BACKUP_DATABASES` → `.env`), so the two are not
in conflict.

**3. The pre-fix behavior, reproduced — and it is worse here than the
implementer was able to show.** The implementer's mutation run only reached a
`Permission denied` on `/var/backups/postgres`, so it had to argue the harmful
branch rather than demonstrate it. Traced the old script's resolution directly
instead (`git show`-ed to a scratch path, never `git stash` — `CLAUDE.md` §8a;
`BACKUP_FORMAT=bogus` aborts it after resolution and before any dump):

```
+ DATABASES=("${db_from_env:-shortlinks}")
```

and then asked this cluster what `shortlinks` actually is:

```
shortlinks      | 10231 kB
shortlinks_test | 17 MB
```

So on *this very machine* the pre-fix script does not fail — it resolves to a
real, populated 10 MB database belonging to another project and, given a
writable `BACKUP_ROOT`, exits 0 having backed up the wrong thing. That is the
silent branch the issue describes, and it is not hypothetical.

**4. Positive path still works.** With `BACKUP_DATABASES` set to one of my own
scratch databases and `BACKUP_ROOT` in my scratchpad, a real `pg_dump -Fc` ran
and produced a dump: `ok — 56K` / `Done — all databases backed up.`, exit 0.

**5. Shell hygiene.** `bash -n` and `shellcheck` both clean on the committed
`scripts/db/backup.sh` — no warnings. The new heredoc is unquoted `<<EOF` (it
has to be, to interpolate `$ENV_FILE`) and correctly escapes `\$BACKUP_DATABASES`;
I checked its body for backticks specifically, since an unquoted heredoc turns
those into command substitution and that has already bitten `restore.sh` in
this repo. There are none.

All four acceptance criteria hold as ticked. Criterion 3 verified in
`docs/deployment.md` as a bolded **"Required install step, not optional
tuning"** callout opening the "Schedule and failure alert" section, and
mirrored in `deploy/systemd/README.md` immediately before the install-and-
enable commands — i.e. it is in front of the reader at the moment they would
act, not buried.

**Cross-check against the rest of the backup set** (`#0062`, `#0064`, `#0228`,
`#0229`, `#0235`, `#0239`) found no disagreement about what ships: local
`pg_dump` + offsite `rsync` pull, S3 deferred. Every remaining `S3` mention in
those files sits inside an explicit correction record (struck criteria in
`#0062`, `#0229`'s `## Decision`), and `PRD.md` §10.6 describes the same
shipped design.

**Confirmed, not fixed:** the `pull-backups.sh` finding this issue reported is
real — `SSH_HOST="${BACKUP_SSH_HOST:-ec2-user@go.sstools.co}"`, filed as
`#0245` and already being worked. See this review's report for one severity
correction to `#0245` and for the rest of my own `scripts/` / `deploy/` /
`migrations/` sweep.
