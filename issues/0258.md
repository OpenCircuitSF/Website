## Description

`#0251` added a positive assertion that `runpipe()`'s definition still spells
`-o pipefail`. **`run()`, one line above it, has no such assertion — and it
carries the entire failure-reporting contract.**

```
scripts/check.sh:50
run()  { "$@"; local rc=$?; [ $rc -eq 0 ] || { FAILED=1; printf …; }; return 0; }
```

Replace it with `run() { "$@"; return 0; }` — dropping the `FAILED=1`
accounting — and **every failing step passes silently.** Verified end to end by
`#0251`'s reviewer: a `--- FAIL` prints, and the script still reports
`VERIFICATION PASSED` and exits 0.

Nothing catches it. The mutation spells no `bash`, no `-c`, no `pipefail`, so
all four checks in the `GUARD-0208` block stay silent, and nothing outside
`check.sh` asserts anything about `run()` — grepped across `internal/`, `cmd/`,
`web/src/` and `scripts/`.

**This is `#0251`'s own defect class, one function over.** And `run()` is the
function `#0140` was originally about: the whole point of that issue was that
`check.sh` could report success while a step failed. The guard built since
protects the pipe, not the accounting.

**Two smaller items in the same file, from the same review:**

**1. `#0208`'s shell-`-c` scan misses combined short options.** The pattern is
`-c\b`, and `-cu` has no word boundary — so `run bash -cu "$1"` is a working
bypass, verified as valid syntax with pipefail off. `-ce` and `-cx` are
identical. This is a one-line pattern fix, smaller than the already-accepted
mutant 7 and actually closable.

**2. Trailing whitespace after `runpipe()`'s closing brace trips the new
guard.** A no-op edit fails the run, because the comment strip only removes
whitespace *preceding* a `#`. Fails safe, but it is a false alarm on a change
that means nothing. A trailing `[[:space:]]*` in the `grep -qxE` pattern fixes
it.

## Root cause

`GUARD-0208` (added by `#0208`, hardened by `#0251`) only ever inspected
`runpipe()`'s own definition line — the funnel that spells `-o pipefail`. It
never looked at `run()`, one line above, even though `run()` is what actually
sets `FAILED=1` on a non-zero exit and is therefore what the whole script's
`VERIFICATION PASSED`/`VERIFICATION FAILED` report depends on. Stripping
`run()`'s accounting spells neither `bash`, `-c`, nor `pipefail`, so none of
`GUARD-0208`'s four checks (pipefail-spelling scan, shell-`-c` scan, call-count
floor, definition-line match) had any way to notice.

## Fix

Added a new `GUARD-0258` block, structurally next to `GUARD-0208`:

1. Asserts `run()`'s definition is the **unique** line in the file starting
   `^run\(\)` — closing the decoy/duplicate class of evasion `#0251` had to
   fight for `runpipe()`. Because the expected text is *also* embedded
   verbatim in a heredoc a few lines later (needed for the comparison in step
   2), that heredoc is wrapped in its own `# BEGIN RUNDATA-0258` / `# END
   RUNDATA-0258` marker pair (built the same "two concatenated string
   literals" way as the file's existing `$BG`/`$EG`/`$BR`/`$ER`, so this
   line's own source can't self-match) and excluded from the scan before
   counting — otherwise the count would always find 2 and every ordinary run
   would report a false regression.
2. Extracts that one line, strips a trailing `# ...` comment and trailing
   whitespace, and compares it — via **literal string equality against a
   quoted heredoc** (`<<'RUN_EOF'`), not a hand-built regex — against the
   exact expected text.

**Why a heredoc instead of `runpipe()`'s regex approach:** `run()`'s
definition embeds a single-quoted `printf` format
(`'\033[31mFAILED (%d): %s\033[0m\n'`) that would need multiple layers of
escaping to express safely as a bash-single-quoted ERE literal — exactly the
class of mistake that cost `#0251` two review rounds on a *simpler* line (no
embedded quotes at all). A quoted heredoc performs no expansion, so nothing
needs escaping.

**Shared-assertion decision (the issue's explicit question):** share the
*structure* — unique-line assertion, then a comment/whitespace-stripped exact
comparison of that one line — not one literal code path. `runpipe()`'s
definition has no embedded quotes and correctly stays regex-based (`grep
-qxE`); forcing `run()`'s embedded quotes through that same machinery would
reintroduce the exact escaping risk the heredoc form avoids. A future third
critical line should follow the same two-part shape and pick regex or heredoc
comparison based on whether its own text embeds quotes.

**Item 1 (`-c\b` misses combined short options):** replaced
`grep -E -- '-c\b'` with
`grep -E -- '(^|[[:space:]])-[a-zA-Z]*c[a-zA-Z]*\b'` — requires the `-` be
preceded by whitespace or start-of-line (so it can't fire inside a GNU long
option like `--color`, where the introducing `-` is never preceded by
whitespace) and matches any short-option cluster containing `c` in either
order. Catches `-cu`, `-ce`, `-cx`, and the reversed `-uc`.

**Item 2 (trailing-whitespace false alarm):** `RUNPIPE_LINE`'s extraction sed
now also strips trailing whitespace (`s/[[:space:]]+$//`), not just the
trailing comment, so a no-op trailing-space edit no longer fails the
whole-line `grep -qxE` match. The regression message's parenthetical was
updated to say so.

**Known, accepted residual gap** (documented in the code comment, same shape
as `#0208`'s mutant 7 and `#0251`'s documented I/J): an edit that *both*
indents `run()`'s real definition (so it stops matching `^run\(\)`) *and*
plants a column-0 decoy elsewhere reading the exact expected text would still
pass. That needs two coordinated edits to a top-level function — indenting one
is not something anyone does by accident, and an agent willing to do that
could delete the guard outright. Not closed; closing it needs a shell parser,
not a grep.

### Bypass A — a single global search-and-replace defeats the heredoc oracle

```

regex — `runpipe\(\) \{ run bash -o pipefail -c "[$]1"; \}` — textually

### Bypass B — no marker-count assertion, so `#0251`'s fake (B) works one function over

Line 50 is **left completely untouched**. A single block is *added* after
`# END GUARD-0258`:

```

### What the next pass needs

1. Assert the `RUNDATA-0258` marker pair occurs **exactly once** in `"$0"`
   (`grep -cxF "$BD"` / `grep -cxF "$ED"`), mirroring the `BR_COUNT`/`ER_COUNT`

2. Make the oracle **not byte-identical** to the subject, so one textual
   transformation cannot rewrite both. Options, in rough order of cost: derive
   the expected text from something other than a verbatim copy of the line; or
   assert separately on the *properties* the line must have (it sets `FAILED=1`;
   it tests `$rc`), so a rewrite that removes the accounting cannot also rewrite
   the assertion into agreement; or keep the heredoc but add an independent
   fingerprint (e.g. a pinned `shasum` of the definition line) that a
   search-and-replace does not update. Note the escaping argument in `## Fix` is
   sound as far as it goes — a hand-built regex here really is risky — but it
   trades a *hypothetical* escaping mistake for a *demonstrated* self-agreement
   failure, which is the worse of the two.

### Judgement on the shared-assertion decision the issue asked about

The implementer's answer — share the *structure*, not one code path, and pick
regex or heredoc per line by whether the text embeds quotes — is **half right,
and the half it gets wrong is what produced Bypass A.** Sharing the structure is
correct and the escaping risk is real (it cost `#0251` two rounds on a simpler
line). But the criterion it chose, *"does the text embed quotes"*, is the wrong
one. The property that actually matters is **whether the oracle can be
distinguished from the subject by any edit that touches the subject.** A regex is
safe not because it escapes well but because it is a *different representation* —
`[$]1`, escaped braces — so a replace of the code does not touch it. A quoted
heredoc is the same representation, in the same file, with the same bytes, and
is therefore not an independent oracle at all. So "two things to keep in step" is
not the objection; the objection is that these two things **cannot get out of
step**, which is worse. A fourth critical line should follow the structure, and
choose its comparison by independence-from-the-subject, not by quoting
convenience.

`git status --porcelain` showed only this session's own target files at the

**Root cause of both bypasses, restated per the new CLAUDE.md §8 rule this
review's judgement section produced:** the pass-2 oracle (a quoted heredoc
holding a byte-identical copy of `run()`'s expected definition) was not an
independent check — it was the same bytes as the subject, in the same file,
so a single textual edit to the subject could also satisfy the oracle
(Bypass A). And nothing asserted the `RUNDATA-0258` marker pair — needed only
to exclude that duplicate from the uniqueness scan — appeared exactly once,
so a second, unmarked-as-decoy `run()` definition slipped through uncounted
(Bypass B).

**Fix — replaced the duplicate-text oracle with a pinned SHA-256 digest, and
deleted the marker machinery it existed to support, rather than patching
around it:**

1. `RUN_DEF_COUNT` and `RUN_LINE` now scan `"$0"` directly, with nothing
   excluded — there is no more embedded duplicate of the subject text
   anywhere in the file, so there is nothing that needs to be deleted from
   the scan before counting. This closes Bypass B by construction, the same
   way `GUARD-0208`'s own design note argues structure beats patching:
   any second `^run()` line, decoy-marked or not, is now always counted, so
   `RUN_DEF_COUNT` catches it directly. No `BD_COUNT`/`ED_COUNT` pair was
   needed because there is no longer a marker pair to protect.
   **CORRECTION (2026-08-24, third re-review):** this claim is false. The
   anchor `^run\(\)` is column-0 and contiguously-spelled, so it "always
   counts" only a second definition that happens to be spelled that exact
   way — a decoy reading ` run()`, `function run {`, `run () {`, or a
   tab-indented copy is invisible to it while still shadowing `run()` at
   runtime. Four such one-line decoys were demonstrated as live bypasses;
   see `## Fix pass` (fourth pass) below for the replacement, which does
   not repeat this claim in the same form because it no longer depends on
   any single anchor's spelling.
2. The comparison changed from `"$RUN_LINE" != "$RUN_EXPECTED"` (heredoc,
   literal-text equality) to a SHA-256 digest of `$RUN_LINE` compared against
   a pinned hex constant (`RUN_EXPECTED_SHA256="805d033eb6d0…9d0df3e"`,
   recomputed straight from the current tracked line with `sed -n '50p'
   scripts/check.sh | sed -E 's/[[:space:]]*#.*$//; s/[[:space:]]+$//' |
   shasum -a 256`). This closes Bypass A: the pinned digest is unrelated
   bytes to the code it verifies (hex digits bear no textual resemblance to
   a `printf` call), so a `sed` search-and-replace over the definition line
   has no matching text to also rewrite in the digest. `runpipe()`'s
   sibling check gets this property from being a regex; `run()` now gets it
   from being a hash — both are answers to the same question the review's
   judgement section named: not "does the subject's text embed quotes" but
   "can an edit to the subject also satisfy the oracle." `shasum -a 256` is
   already an established pattern in this repo's own guard tests
   (`scripts/db_reset_guard_test.sh`, `scripts/dev_guard_test.sh`,
   `scripts/testdb_gc_guard_test.sh`), guarded the same way here with
   `command -v shasum` before use.
3. Rewrote the `GUARD-0258` block comment to describe the new mechanism
   accurately (the old comment's heredoc/escaping rationale no longer
   describes the code) and to record why a hash was chosen over a
   hand-built regex here: `run()`'s definition embeds a single-quoted
   `printf` format that would need multi-layer escaping to express safely
   as a bash-single-quoted ERE — the same mistake that cost `#0251` two
   review rounds on a simpler line. A digest needs no escaping at all.
4. Recorded, in `CLAUDE.md` §8, as instructed: "A guard's oracle must not
   be the same bytes as its subject" — already present at the top of this

## Fix pass (fourth pass)

**Judgement call this pass had to make first, per the orchestrator's explicit
instruction: is a fail-closed design practical here, or is widening the
anchor (as the third review measured and handed over) the right call?**
Chose fail-closed, and it worked out cheaper than expected. Enumerating
recognized spellings has now lost three review rounds in a row on this
exact guard — the fix is not a wider enumeration, it's to stop enumerating.
`bash 3.2`'s `declare -f`/`declare -F` machinery (available and stable on
this machine, confirmed by direct measurement, not assumed) lets bash's own
parser decide what a name resolves to, instead of a regex guessing at
spelling. The mechanism (`FUNCDEF-0258`, added to `scripts/check.sh` between
`runpipe()`'s definition and `GUARD-0208`, shared by both guards):

1. Extract every line in the file that is a COMPLETE, single-line function
   definition — `NAME() { ... }`, `function NAME { ... }`, any mix of the
   optional `function` keyword, optional `()`, and leading whitespace bash
   accepts, PROVIDED the opening brace's match closes on the same line.
   This describes "a function definition sits on this line," not "the
   function is named run/runpipe" — it does not care what the function is
   called, so there is nothing left to enumerate per name. Measured against
   the tracked file: exactly four such lines (`step`, `run`, `runpipe`,
   `cleanup`) — the four single-line top-level functions that exist today.
2. Source those candidate lines, and only those lines, into a private
   subshell, in file order. Sourcing a `name() { ... }` construct only ever
   REGISTERS the function; it never executes the body — so this is safe
   even though the candidate set includes functions the check doesn't care
   about, and, in a mutated copy, an attacker-planted decoy: nothing in
   either its header or its body runs merely by being defined. Sourcing in
   file order means bash's own shadowing rule (last definition wins)
   resolves a duplicate/decoy exactly the way running the real script
   would — there is no separate "count the definitions" step, because the
   property that matters is not how many spellings of NAME appear, it's
   what NAME ends up bound to.
3. `declare -f NAME` prints bash's own canonical, reformatted rendering of
   whatever won the shadowing. Measured directly (not assumed): leading
   space, `function run {`, `run () {`, and a tab-indented copy of the same
   body all produce byte-identical `declare -f` output — so hashing THAT,
   rather than a copy of the source line, makes the oracle
   spelling-independent. Bash's parser does the recognition, not this
   script's regex, and `CLAUDE.md` §8's rule from the last bounce still
   holds: the pinned hex digest is unrelated bytes to the code it verifies,
   so no edit to the code can also rewrite it.

**Why this is stronger than the handed-over widened-anchor regex, not just
a different way to write it:** the reviewer's regex
(`^[[:space:]]*(function[[:space:]]+)?run[[:space:]]*\(\)|...`) closes
exactly the four demonstrated shapes and was explicitly offered as "measured
against the mutants above," i.e. against a known set. `resolve_func_hash`
closes every shape in that set for the same underlying reason (bash accepts
them and normalizes them identically) but does not need the set enumerated
first — a fifth one-line spelling bash accepts that nobody has thought of
yet is handled by the same mechanism, because the recognizer is bash's own
parser, not a pattern written by whoever is fixing this today. This is the
"stop enumerating" version of the reviewer's own regex, not a rejection of
it — it was the sanity check that confirmed candidates were correctly
identified (grepped, by hand, before writing `resolve_func_hash`, and it
found exactly `step`/`run`/`runpipe`/`cleanup`).

**What this does NOT close, argued concretely rather than left implicit:**
closing these needs executing untrusted code rather than merely defining
functions, which is a materially different (and materially riskier) thing
for a guard inside the script "everything is verified with" (`CLAUDE.md`
§5b) to do:

- **A definition built at runtime** — `eval 'run() { ... }'`, sourcing
  another file, `unset -f run` followed by a later indirect define — is
  invisible to a scan that only looks at literal `name() { ... }` text.
  Verified: an eval-built `run()` ADDED alongside the real definition is
  NOT caught (only an eval that REPLACES the real line is, since the scan
  then finds nothing else to shadow it with — narrower than the third
  pass's `## Fix pass` claimed "eval-defined run is caught" without that
  qualifier; corrected here).
- **A definition split across multiple lines** (the opening brace on its
  own line, body on subsequent lines, closing brace on its own line) is
  outside a one-line candidate scan by construction. Nothing in this file
  is written that way today — the four existing single-line functions are
  the only functions defined this way in `scripts/check.sh` — so this is a
  theoretical gap, not a demonstrated one.
- Fully closing either needs a real shell parser reading the whole file's
  control flow (or, equivalently, actually running the file up to the
  point of interest and asking bash what got defined along the way, which
  reintroduces the side-effect risk this design deliberately avoids by
  only ever DEFINING candidate functions, never executing the rest of the
  script). Considered and rejected: sourcing the whole file (or a prefix of
  it) to let bash resolve everything, including multi-line and
  runtime-built definitions, was rejected because the file's own top-level
  statements between `run()`'s definition and end-of-file are NOT all
  side-effect-free function definitions — they include `GUARD-0208`'s own
  checks (which `exit 2` on failure) and, further down, the real
  build/test dispatch loop. Sourcing far enough to see every possible decoy
  location would mean actually running the guard checks and stepping
  towards the real work from inside a check that is supposed to be cheap
  and side-effect-free, and a decoy placed inside a function body that
  never gets called would still be invisible to it, so it does not even
  fully close the gap it would be taken on for. Restricting the source to
  self-contained one-line candidates avoids all of this at the cost of the
  two narrow, explicitly-named gaps above — a trade judged worth making
  rather than defaulting to "widen the anchor and call it done."

### Defect 1 — four one-line static shapes bash accepts and the candidate regex does not

`FUNCDEF_CANDIDATE_RE` requires the line to *end* at the closing `}` (plus
optional whitespace and a trailing comment), and requires the body to be a brace
group introduced by an optional `()`. Four complete, single-line, top-level
definitions fail that and are therefore never handed to bash at all. Each one
shadows `run()` at runtime, and each produced **`VERIFICATION PASSED`, exit 0,
with the `FAILED=1` accounting gone**:

| # | decoy inserted after `run()`'s real line | result |
|---|---|---|
| S1 | `run() { "$@"; return 0; };` — a trailing `;` | *** BYPASS *** |
| S2 | `run() ( "$@"; return 0 )` — subshell body, no braces | *** BYPASS *** |
| S3 | `{ run() { "$@"; return 0; }; }` — wrapped in a group command | *** BYPASS *** |
| S4 | `if true; then run() { "$@"; return 0; }; fi` | *** BYPASS *** |

All four are valid bash 3.2.57, all four resolve `run` to the decoy (verified
independently with `bash -c 'run() { echo REAL; }; <shape>; run'` → `DECOY`),
and all four pass `bash -n`.

**The same four defeat `runpipe()`**, proved end to end with the pipefail
oracle: S2, S1, S3 and S4 spelled for `runpipe` with the flag dropped and the
shell reached through a variable (so `SHELLC_HITS` cannot cover) each produced
**`VERIFICATION PASSED` with `-o pipefail` genuinely lost**, while the named
leading-space shape with the identical body was CAUGHT. So `#0262`'s
"the masking dependency is removed, not just documented" holds for the four
shapes it enumerated and **not** for these.

### Defect 2 — one ordinary helper line blinds the entire mechanism

`resolve_func_hash` strips comments with `sed -E 's/[[:space:]]*#.*$//'`, which
does not know about quoting. A `#` **inside a string** is stripped too, and the
truncated line is then fed to `source`. This is not a contrived construction —
a plausible helper is enough:

```
hdr_0258() { printf '# %s\n' "$1"; }
```

After the strip that becomes `hdr_0258() { printf '` — an unterminated quote,
which swallows every following candidate line into the string and ends in
`unexpected EOF while looking for matching '`. Adding that one line **plus the
plainest possible column-0 decoy**, the exact shape the guard demonstrably
catches on its own:

```
hdr_0258() { printf '# %s\n' "$1"; }
run() { "$@"; return 0; }
```

→ **`VERIFICATION PASSED`, exit 0.** Measured directly: the poisoned file
resolves `run` to `b5ca2df355ef…`, byte-for-byte the pinned digest.

This is worse than a bypass, because it needs no attacker. A future maintainer
adding any one-line helper whose body contains a `#` inside quotes silently
disables **both** `GUARD-0258` and `GUARD-0208`'s digest check, with no signal
of any kind. The guard's coverage is not stable under ordinary maintenance of
the file it guards.

### Defect 3 — the "private subshell" is not isolated from the running script

`( source "$tmp" >/dev/null 2>&1; declare -f "$name" )` is a subshell **of the
running `check.sh`**, which by that point has already executed lines 58–77 and
therefore already has `step`, `run`, `runpipe` and `cleanup` in its function
table. `declare -f NAME` therefore falls back to the **live** definition
whenever the candidate file fails to define `NAME`. Minimal proof:

```
run()  { echo "LIVE-REAL"; }
( source /dev/null >/dev/null 2>&1; declare -f run )   # prints LIVE-REAL
```

The candidate set was empty and `declare -f` still answered. So in every failure
mode of the extraction — the poison above, a `mktemp` failure, a `grep` that
matches nothing — the guard stops measuring *the file* and silently starts
measuring *the running process*, which is the thing under test. That is a
circularity of the same family `CLAUDE.md` §8 names, arriving by a different
route than the pass-1 heredoc: the pinned digest is still independent bytes, but
the **subject** quietly swaps from the file to the live process. It is also
exactly why Defect 2 stays silent instead of failing closed: `runpipe` is
defined *after* the poison line, its candidate scan contributes nothing, and
`declare -f runpipe` returns `check.sh`'s own live definition, which matches the
pin. Measured outside a running `check.sh` the same file yields
`e3b0c44298fc…` — the SHA-256 of the empty string — i.e. it *would* have failed
closed had the subshell actually been private.

### Defect 4 — a candidate line can execute code at source time

The comment asserts: *"Sourcing a `name() { ... }` construct only ever REGISTERS
the function; it never executes the body … nothing in either its header or its
body runs merely by being defined."* **This is false.** `(\(\))?` is optional in
`FUNCDEF_CANDIDATE_RE`, so `NAME { … }` with no parens is a candidate — and for
a shell keyword that takes a brace group, that is a command, not a definition:

```
time { touch "$d/PWNED"; echo executed-at-source-time; }
```

matches the candidate regex, and sourcing it printed `executed-at-source-time`
and created the file. Not a privilege escalation — anyone editing `check.sh`
already has the script — but the stated safety property of the extraction does
not hold, and a legitimate `time { … }` line in `check.sh` would execute on
every single run of every verification in this project.

### Comments that are not reproducible, read adversarially as asked

The pass-2 comment shipped a claim (*"any second `run()` definition … is always
counted"*) that the third review showed was false. Three claims in
`FUNCDEF-0258` are false in the same way:

1. *"Extract every line in FILE that is a COMPLETE, single-line function
   definition"* — it does not; S1–S4 are complete single-line definitions and
   none is extracted. What the regex actually tests is "the line ends at a `}`",
   which is a different property from "the opening brace's match closes on the
   same line".
2. *"the fix is not a wider enumeration, it is to stop enumerating spellings at
   all"* / *"bash's parser does the recognition, not this script's regex"* — the
   regex still decides which lines bash is allowed to see. It is a wider
   enumeration, of line *shapes* rather than of names, and it still fails
   **open** on an unrecognised one. `#0262`'s Notes asked precisely that this be
   the judging criterion.
3. The safety claim about sourcing, refuted in Defect 4.

The disclosed-gap list is honest about what it names, but it is scoped to
"built at runtime" and "split across multiple lines", which leaves the reader
with the impression that a *static, one-line, literal* definition is covered.
S1–S4 are all three of those things.

### Judgement on the two disclosed gaps, and on `declare -f`

- **Both disclosed gaps are genuinely still open**, confirmed: an
  `eval 'run() { "$@"; return 0; }'` added alongside the real line → BYPASS; a
  multi-line `run() {` / body / `}` → BYPASS. They are documented accurately.
- **Reachability**: I judge both *more* reachable than `#0208`'s accepted mutant
  7. Mutant 7 (`run "$SHELL" -c`) requires inventing an indirect shell
  invocation that nothing in the file resembles. A multi-line function
  definition is the ordinary way most people write a function longer than one
  line — the only reason `run()` and `runpipe()` are one-liners is stylistic —
  so this gap opens the moment anyone reformats either function, and the guard
  would then be silently protecting nothing. That is not a contrived shape; it
  is the default shape. It should not be accepted on mutant 7's precedent.
- **`declare -f` canonicalisation**: tested for the converse the fourth pass did
  not test — can two *semantically different* bodies canonicalise to the same
  output? Ten pairs run under bash 3.2.57. Collisions occur **only** on
  differences that are not semantic: inter-token whitespace, `;` versus newline
  as a separator, and a trailing space before `;`. Everything meaning-bearing
  survives: `[ $r -eq 0 ]` vs `[ "$r" -eq 0 ]` differ; `'a b'` vs `"a b"` differ;
  `a; b` vs `a && b` differ; `"$@"` vs `$@` differ. **I found no
  semantically-different pair that collides, and I consider this risk closed.**

### Judgement on the maintenance constraints

Acceptable, and correctly documented in the block comment — but the cost is
real and slightly understated. The message for an innocent `unset TMPVAR` says
the line "could bind, rebind or unbind the run helper," which is false for that
line, and its suggested remedy ("move the mention into a whole-line comment")
does not apply to a line you actually need. The constraint that `check.sh` may
never spell `eval`/`source`/`unset` anywhere in code is a genuine restriction on
a 600-line script that will keep growing. It is a defensible trade for
fail-closed behaviour, and the block comment does state it plainly; the error
message should state it too, rather than asserting a binding relationship it
cannot know.

### What I tried that did not work

Offered so the next pass does not re-spend the time: `BASH_ENV=…` does **not**
rebind `run` in the running process (it is read only when a *new* non-interactive
bash starts, so it reaches `runpipe`'s child shell but not the accounting);
`declare -f run` as a line binds nothing; `trap '…' DEBUG` spelling a definition
is caught by the suspect scan; `alias run=true` without `shopt -s
expand_aliases` is inert in a non-interactive shell. Deep-nesting a definition
inside another function's body is caught (the documented over-approximation
holds). The digest cannot be edited into agreement without changing the pinned
constant, and the two constants are unrelated bytes to the code they verify, so
