## Description

`#0251` added a positive assertion that `runpipe()`'s definition still spells
`-o pipefail`. **`run()`, one line above it, has no such assertion — and it
carries the entire failure-reporting contract.**

```
scripts/check.sh:50
run()  { "$@"; local rc=$?; [ $rc -eq 0 ] || { FAILED=1; printf …; }; return 0; }
```

Replace it with `run() { "$@"; return 0; }` — dropping the `FAILED=1`
accounting — and **every failing step passes silently.** Verified end to end by
`#0251`'s reviewer: a `--- FAIL` prints, and the script still reports
`VERIFICATION PASSED` and exits 0.

Nothing catches it. The mutation spells no `bash`, no `-c`, no `pipefail`, so
all four checks in the `GUARD-0208` block stay silent, and nothing outside
`check.sh` asserts anything about `run()` — grepped across `internal/`, `cmd/`,
`web/src/` and `scripts/`.

**This is `#0251`'s own defect class, one function over.** And `run()` is the
function `#0140` was originally about: the whole point of that issue was that
`check.sh` could report success while a step failed. The guard built since
protects the pipe, not the accounting.

**Two smaller items in the same file, from the same review:**

**1. `#0208`'s shell-`-c` scan misses combined short options.** The pattern is
`-c\b`, and `-cu` has no word boundary — so `run bash -cu "$1"` is a working
bypass, verified as valid syntax with pipefail off. `-ce` and `-cx` are
identical. This is a one-line pattern fix, smaller than the already-accepted
mutant 7 and actually closable.

**2. Trailing whitespace after `runpipe()`'s closing brace trips the new
guard.** A no-op edit fails the run, because the comment strip only removes
whitespace *preceding* a `#`. Fails safe, but it is a false alarm on a change
that means nothing. A trailing `[[:space:]]*` in the `grep -qxE` pattern fixes
it.

## Root cause

`GUARD-0208` (added by `#0208`, hardened by `#0251`) only ever inspected
`runpipe()`'s own definition line — the funnel that spells `-o pipefail`. It
never looked at `run()`, one line above, even though `run()` is what actually
sets `FAILED=1` on a non-zero exit and is therefore what the whole script's
`VERIFICATION PASSED`/`VERIFICATION FAILED` report depends on. Stripping
`run()`'s accounting spells neither `bash`, `-c`, nor `pipefail`, so none of
`GUARD-0208`'s four checks (pipefail-spelling scan, shell-`-c` scan, call-count
floor, definition-line match) had any way to notice.

## Fix

Added a new `GUARD-0258` block, structurally next to `GUARD-0208`:

1. Asserts `run()`'s definition is the **unique** line in the file starting
   `^run\(\)` — closing the decoy/duplicate class of evasion `#0251` had to
   fight for `runpipe()`. Because the expected text is *also* embedded
   verbatim in a heredoc a few lines later (needed for the comparison in step
   2), that heredoc is wrapped in its own `# BEGIN RUNDATA-0258` / `# END
   RUNDATA-0258` marker pair (built the same "two concatenated string
   literals" way as the file's existing `$BG`/`$EG`/`$BR`/`$ER`, so this
   line's own source can't self-match) and excluded from the scan before
   counting — otherwise the count would always find 2 and every ordinary run
   would report a false regression.
2. Extracts that one line, strips a trailing `# ...` comment and trailing
   whitespace, and compares it — via **literal string equality against a
   quoted heredoc** (`<<'RUN_EOF'`), not a hand-built regex — against the
   exact expected text.

**Why a heredoc instead of `runpipe()`'s regex approach:** `run()`'s
definition embeds a single-quoted `printf` format
(`'\033[31mFAILED (%d): %s\033[0m\n'`) that would need multiple layers of
escaping to express safely as a bash-single-quoted ERE literal — exactly the
class of mistake that cost `#0251` two review rounds on a *simpler* line (no
embedded quotes at all). A quoted heredoc performs no expansion, so nothing
needs escaping.

**Shared-assertion decision (the issue's explicit question):** share the
*structure* — unique-line assertion, then a comment/whitespace-stripped exact
comparison of that one line — not one literal code path. `runpipe()`'s
definition has no embedded quotes and correctly stays regex-based (`grep
-qxE`); forcing `run()`'s embedded quotes through that same machinery would
reintroduce the exact escaping risk the heredoc form avoids. A future third
critical line should follow the same two-part shape and pick regex or heredoc
comparison based on whether its own text embeds quotes.

**Item 1 (`-c\b` misses combined short options):** replaced
`grep -E -- '-c\b'` with
`grep -E -- '(^|[[:space:]])-[a-zA-Z]*c[a-zA-Z]*\b'` — requires the `-` be
preceded by whitespace or start-of-line (so it can't fire inside a GNU long
option like `--color`, where the introducing `-` is never preceded by
whitespace) and matches any short-option cluster containing `c` in either
order. Catches `-cu`, `-ce`, `-cx`, and the reversed `-uc`.

**Item 2 (trailing-whitespace false alarm):** `RUNPIPE_LINE`'s extraction sed
now also strips trailing whitespace (`s/[[:space:]]+$//`), not just the
trailing comment, so a no-op trailing-space edit no longer fails the
whole-line `grep -qxE` match. The regression message's parenthetical was
updated to say so.

**Known, accepted residual gap** (documented in the code comment, same shape
as `#0208`'s mutant 7 and `#0251`'s documented I/J): an edit that *both*
indents `run()`'s real definition (so it stops matching `^run\(\)`) *and*
plants a column-0 decoy elsewhere reading the exact expected text would still
pass. That needs two coordinated edits to a top-level function — indenting one
is not something anyone does by accident, and an agent willing to do that
could delete the guard outright. Not closed; closing it needs a shell parser,
not a grep.

### Bypass A — a single global search-and-replace defeats the heredoc oracle

```

```

One command, no marker forgery, no coordination. It rewrites **line 50 (the live
definition) *and* line 284 (the `RUN_EXPECTED` heredoc)**, because the heredoc
stores the expected text **byte-identical** to the definition it is supposed to
police. `RUN_LINE` and `RUN_EXPECTED` then agree, `GUARD-0258` passes, and the
run reports `--- FAIL` … `VERIFICATION PASSED`, **exit 0**. Confirmed by `diff`
against the fixed script: exactly two changed lines, 50 and 284.

`runpipe()` is **immune to the identical attack**, and the asymmetry is the
point: its literal definition text occurs **once** in the file (its oracle is a
regex — `runpipe\(\) \{ run bash -o pipefail -c "[$]1"; \}` — textually
distinct from the code), whereas `run()`'s definition text occurs **twice**.
Measured, not argued: the same global-replace against `runpipe()` is **caught**
(`PIPEFAIL REGRESSION (#0208/#0251): runpipe()'s own definition line no longer
reads exactly …`, exit 2).

### Bypass B — no marker-count assertion, so `#0251`'s fake (B) works one function over

Line 50 is **left completely untouched**. A single block is *added* after
`# END GUARD-0258`:

```
# BEGIN RUNDATA-0258
run()  { "$@"; return 0; }
# END RUNDATA-0258
```

`RUN_SCAN`'s `sed -e "/${BD}/,/${ED}/d"` deletes *both* marker ranges, so
`RUN_DEF_COUNT` still sees exactly one `^run()` (the real, correct one) and
`RUN_LINE` still equals `RUN_EXPECTED` — while at runtime the later definition
shadows the earlier one and the accounting is gone. Result: `--- FAIL` …
**`VERIFICATION PASSED`, exit 0.**

This is precisely `#0251`'s documented fake **(B)**, the decoy marker block.
`GUARD-0208` closed it with `BR_COUNT`/`ER_COUNT` assertions that the
`RUNPIPE-0208` pair appears exactly once — and I re-ran that fake to confirm it
is still caught (`expected the RUNPIPE-0208 marker pair exactly once …`).
`GUARD-0258` has **no `BD_COUNT`/`ED_COUNT` equivalent** for `RUNDATA-0258`, so
the same evasion is open. The block comment even notes the marker pair exists so
the scan can delete it, without ever asserting there is only one.

### What the next pass needs

1. Assert the `RUNDATA-0258` marker pair occurs **exactly once** in `"$0"`
   (`grep -cxF "$BD"` / `grep -cxF "$ED"`), mirroring the `BR_COUNT`/`ER_COUNT`
   check ten lines above. That closes Bypass B outright.
2. Make the oracle **not byte-identical** to the subject, so one textual
   transformation cannot rewrite both. Options, in rough order of cost: derive
   the expected text from something other than a verbatim copy of the line; or
   assert separately on the *properties* the line must have (it sets `FAILED=1`;
   it tests `$rc`), so a rewrite that removes the accounting cannot also rewrite
   the assertion into agreement; or keep the heredoc but add an independent
   fingerprint (e.g. a pinned `shasum` of the definition line) that a
   search-and-replace does not update. Note the escaping argument in `## Fix` is
   sound as far as it goes — a hand-built regex here really is risky — but it
   trades a *hypothetical* escaping mistake for a *demonstrated* self-agreement
   failure, which is the worse of the two.

### Judgement on the shared-assertion decision the issue asked about

The implementer's answer — share the *structure*, not one code path, and pick
regex or heredoc per line by whether the text embeds quotes — is **half right,
and the half it gets wrong is what produced Bypass A.** Sharing the structure is
correct and the escaping risk is real (it cost `#0251` two rounds on a simpler
line). But the criterion it chose, *"does the text embed quotes"*, is the wrong
one. The property that actually matters is **whether the oracle can be
distinguished from the subject by any edit that touches the subject.** A regex is
safe not because it escapes well but because it is a *different representation* —
`[$]1`, escaped braces — so a replace of the code does not touch it. A quoted
heredoc is the same representation, in the same file, with the same bytes, and
is therefore not an independent oracle at all. So "two things to keep in step" is
not the objection; the objection is that these two things **cannot get out of
step**, which is worse. A fourth critical line should follow the structure, and
choose its comparison by independence-from-the-subject, not by quoting
convenience.

Third implementation pass, closing both bypasses the review demonstrated.
`git status --porcelain` showed only this session's own target files at the

**Root cause of both bypasses, restated per the new CLAUDE.md §8 rule this
review's judgement section produced:** the pass-2 oracle (a quoted heredoc
holding a byte-identical copy of `run()`'s expected definition) was not an
independent check — it was the same bytes as the subject, in the same file,
so a single textual edit to the subject could also satisfy the oracle
(Bypass A). And nothing asserted the `RUNDATA-0258` marker pair — needed only
to exclude that duplicate from the uniqueness scan — appeared exactly once,
so a second, unmarked-as-decoy `run()` definition slipped through uncounted
(Bypass B).

**Fix — replaced the duplicate-text oracle with a pinned SHA-256 digest, and
deleted the marker machinery it existed to support, rather than patching
around it:**

1. `RUN_DEF_COUNT` and `RUN_LINE` now scan `"$0"` directly, with nothing
   excluded — there is no more embedded duplicate of the subject text
   anywhere in the file, so there is nothing that needs to be deleted from
   the scan before counting. This closes Bypass B by construction, the same
   way `GUARD-0208`'s own design note argues structure beats patching:
   any second `^run()` line, decoy-marked or not, is now always counted, so
   `RUN_DEF_COUNT` catches it directly. No `BD_COUNT`/`ED_COUNT` pair was
   needed because there is no longer a marker pair to protect.
2. The comparison changed from `"$RUN_LINE" != "$RUN_EXPECTED"` (heredoc,
   literal-text equality) to a SHA-256 digest of `$RUN_LINE` compared against
   a pinned hex constant (`RUN_EXPECTED_SHA256="805d033eb6d0…9d0df3e"`,
   recomputed straight from the current tracked line with `sed -n '50p'
   scripts/check.sh | sed -E 's/[[:space:]]*#.*$//; s/[[:space:]]+$//' |
   shasum -a 256`). This closes Bypass A: the pinned digest is unrelated
   bytes to the code it verifies (hex digits bear no textual resemblance to
   a `printf` call), so a `sed` search-and-replace over the definition line
   has no matching text to also rewrite in the digest. `runpipe()`'s
   sibling check gets this property from being a regex; `run()` now gets it
   from being a hash — both are answers to the same question the review's
   judgement section named: not "does the subject's text embed quotes" but
   "can an edit to the subject also satisfy the oracle." `shasum -a 256` is
   already an established pattern in this repo's own guard tests
   (`scripts/db_reset_guard_test.sh`, `scripts/dev_guard_test.sh`,
   `scripts/testdb_gc_guard_test.sh`), guarded the same way here with
   `command -v shasum` before use.
3. Rewrote the `GUARD-0258` block comment to describe the new mechanism
   accurately (the old comment's heredoc/escaping rationale no longer
   describes the code) and to record why a hash was chosen over a
   hand-built regex here: `run()`'s definition embeds a single-quoted
   `printf` format that would need multi-layer escaping to express safely
   as a bash-single-quoted ERE — the same mistake that cost `#0251` two
   review rounds on a simpler line. A digest needs no escaping at all.
4. Recorded, in `CLAUDE.md` §8, as instructed: "A guard's oracle must not
   be the same bytes as its subject" — already present at the top of this
   file's context before this pass started (added by the prior review), so
   no further edit to `CLAUDE.md` was needed from this pass.
