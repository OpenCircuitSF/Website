## Description

**1. Neither `complained` message names the one exit.** `CLAUDE.md` §9 has two halves: a complained subscriber never auto-resubscribes, **and only an admin explicitly clearing that state changes it**. `#0178`'s rewrites keep the first half forcefully ("By design… enforced, not a glitch") and say nothing about the second.

`#0178`'s review judged this not a regression — the strings it replaced said no more — but sharpened where it matters:

- `Suppress`'s message has a `Use "Clear complaint" first` pointer, but it is appended only in the `else` branch (`h.suppressions == nil`), which is dev/test wiring — **production never takes it**. Mitigated in practice by `Admin.svelte:1596` rendering a **Clear complaint** button on the very row the modal sits over.
- `manualAddMessage`'s case is **sharper**: it lands in `createSubNotice` on the manual-add form, where **no Clear-complaint button is adjacent**. An admin is told the address was refused and given no route forward.

**2. Worker error strings render to admins verbatim.** `failed_sends[].error` is an API `error` field rendered per-row in `CampaignStats.svelte`, and its values come from `internal/mailing/worker.go`'s `MarkFailedRow`/`MarkRetryOrFailed` — including the literal `"empty manage token from eligibility recheck"` (`worker.go:671`) and raw `rerr.Error()` / `sendErr.Error()` output.

That is `#0175`'s defect class on a surface **no sweep has covered**: not a citation, but implementation vocabulary shown to someone who cannot act on it. `#0178`'s review confirmed there is no *citation* defect there, so `#0178`'s own conclusion stands — this is the next layer.

## Root cause

Both `complained` messages carried the refusal's force but not its exit.
`Suppress`'s "Use \"Clear complaint\" first" pointer was appended only in the
`else` branch of `if suppressionAdded { … } else { … }` — i.e. only when
`h.suppressions == nil`, dev/test wiring the production handler (constructed
with a real `adminSuppressionWriter`) never takes. On the production path
`suppressionAdded` is always true after a successful `Suppress` call, so the
pointer never rendered. `manualAddMessage`'s `StatusComplained` case never
had a pointer at all, and it renders into `createSubNotice` on the
manual-add form (`Admin.svelte:790`), which has no "Clear complaint" button
nearby — that button lives on the subscriber row, not the add form.

Separately, `internal/mailing/worker.go` wrote three kinds of raw Go/AWS
error text straight into `email_sends.error`, which `CampaignStats.svelte`
renders verbatim per failed-send row: a literal implementation-vocabulary
string (`"empty manage token from eligibility recheck"`), a raw render
error from `RenderCampaign` (goldmark/template failures, `ErrMissingBaseURL`,
etc.), and `sendErr.Error()` — which for `SESMailer.Send` is always prefixed
with our own `"mailing: sending via SES: "` wrapping text ahead of the
actual AWS-produced error.

## Fix

**Complained messages.** Both now name the exit unconditionally:

- `Suppress`'s noOp message: `This subscriber has complained. By design,
  unsubscribing a complained row makes no status change — that is enforced,
  not a glitch. Use "Clear complaint" to change that.` (plus the existing
  suppression-list sentence when `suppressionAdded`).
- `manualAddMessage`'s `StatusComplained` case: `This address has previously
  complained. By design, adding it here does not resubscribe it — only
  clearing the complaint on that subscriber's row changes that. Nothing was
  sent.`

**Decision recorded (criterion 3):** `Suppress`'s pointer moved out of the
`h.suppressions == nil` branch rather than being left redundant behind the
adjacent "Clear complaint" button. The button mitigates the gap on the
subscriber-row modal, but the acceptance criterion asks the message itself
to name the exit "without weakening the refusal's force" — a UI affordance
elsewhere doesn't satisfy that for the message text, and `manualAddMessage`'s
sharper case (no adjacent button at all) makes clear the copy has to carry
this on its own. Making both messages self-sufficient is also more
consistent: an admin reading either screen's notice gets the same shape of
answer.

**Worker error strings**, classified by source rather than flattened
uniformly:

- **Our own code's doing** — replaced with fixed, jargon-free admin text,
  no raw diagnostic:
  - The empty-`ManageToken` guard (`worker.go`, previously
    `"empty manage token from eligibility recheck"`) is a should-never-happen
    invariant violation in our own bookkeeping (`RecheckEligibleTx` only
    returns rows it judged eligible, with a token read from the same query).
    New constant `adminEligibilityFailureMessage`: `"Not sent — a required
    unsubscribe link could not be generated for this recipient, so the
    message was withheld rather than sent without one."`
  - `RenderCampaign`'s errors (`ErrMissingManageToken`, `ErrMissingBaseURL`,
    a wrapped Markdown-conversion failure, or a recovered panic) are all our
    own rendering code, never anything the recipient's mail system said. New
    `adminRenderFailureMessage(err)`: `"Not sent — this message's content
    could not be rendered for this recipient. The campaign draft or server
    configuration needs attention before this row is retried."`
- **The recipient's mail system's doing (via SES)** — kept intact. New
  `adminSendErrorMessage(err)` strips only `SESMailer.Send`'s own
  `"mailing: sending via SES: "` wrapping prefix via `strings.TrimPrefix` and
  returns everything after it unchanged: an SES rejection reason
  (`MessageRejected`), a quota (`LimitExceededException`), a throttling
  exception exhausted after retries, or `ErrNoMessageID`'s text, all reach
  the admin exactly as SES/the AWS SDK phrased them. Used at both
  `MarkFailedRow` (terminal-row class) and `MarkRetryOrFailed` (retryable,
  exhausted) call sites in `sendOne`.

No behavior changed — `sendOne`'s classification (`classifySendError`,
`sendClassTerminalRow` vs `sendClassRetryable`), the row/campaign status
transitions, and `Unsubscribe`/`Create`'s no-op handling of `complained` rows
are all untouched. Only the strings written to `email_sends.error` and the
two `message` fields changed.

### Why this bounces — the classification, case by case

**The strip mechanic itself is sound.** `"mailing: sending via SES: "` is
emitted at exactly three places, all inside `SESMailer.Send`
(`ses_mailer.go:170,173,178`), all with the identical literal and no double
wrapping; `sendOne` hands `w.mailer.Send`'s error to `adminSendErrorMessage`
directly with nothing in between. `strings.TrimPrefix` on an error lacking the
prefix is a no-op, so an error without it passes through unharmed rather than
mangled. Confirmed.

**But the function's stated premise is false, and false for a case the fix
explicitly enumerated.** `adminSendErrorMessage`'s doc comment says "every
error that reaches this function came from SES itself — a rejection reason, a
quota, a throttling exception", and `## Fix` repeats it, listing
"`ErrNoMessageID`'s text" among the things that reach the admin "exactly as
SES/the AWS SDK phrased them". `SESMailer.Send` has **three returns that are
our own sentences and carry no prefix**:

| Return | Where | Class → call site | What the admin sees |
|---|---|---|---|
| `ErrNoMessageID` | `ses_mailer.go:32`, returned bare | `sendClassTerminalRow` → `MarkFailedRow` | `mailing: SES accepted the send but returned no MessageId` |
| `errors.New("mailing: message has no recipient")` | `ses_mailer.go:111` | unrecognized → retryable → `MarkRetryOrFailed` | `mailing: message has no recipient` |
| `errors.New("mailing: message has neither an HTML nor a text body")` | `ses_mailer.go:114` | same | `mailing: message has neither an HTML nor a text body` |

Those are the literal observed outputs of `classifySendError` +
`adminSendErrorMessage`, not inference.

`ErrNoMessageID` is not a corner found by reading around: it sits in the
codebase's own `TestClassifySendError` table (`worker_test.go:953`) as a
`sendClassTerminalRow` input — the exact path the new function serves — and the
fix named it. It is written by us (`errors.New`, our package), describes an
anomaly in SES's *response* rather than anything SES said, and lands on
`CampaignStats.svelte` with the Go package name `mailing:` in front of it.
That is this issue's own headline defect — worker error strings reaching
admins raw — surviving the fix on the one surface the issue exists to clean.

The other two are effectively unreachable from `sendOne` (`r.Email` comes from
`RecheckEligibleTx`; `RenderCampaign` returns both bodies) — but that is
precisely the argument the fix used to justify replacing the empty-`ManageToken`
guard's text, which it correctly called a should-never-happen invariant.
Applying that reasoning to `worker.go`'s guard and not to `ses_mailer.go`'s two
is inconsistent by the fix's own standard.

Smaller, third: `sleepErr` at `ses_mailer.go:173` is a *context* error wrapped
in the SES prefix, so it strips to a bare `context deadline exceeded` — Go
runtime vocabulary shown to an admin as a send-failure reason. Observed. Less
clear-cut than the three above (the SDK's own deadline errors arrive as
`operation error SES v2: SendEmail, …`, legitimately SDK text), but one more
case where "came from SES" is not what the prefix strip actually guarantees.

### What the next implementation pass must fix

1. **Correct the premise before the strings.** `adminSendErrorMessage`'s doc
   comment and `## Fix`'s "every error that reaches this function came from SES
   itself" are wrong, and a future reader will build on them. The true
   invariant is narrower: *an error carrying `"mailing: sending via SES: "`
   wraps something the AWS SDK produced; everything else `SESMailer.Send` can
   return is ours.*
2. **Handle the three unprefixed returns explicitly**, not by fall-through. The
   prefix's presence is the discriminator the code already has — carries it,
   it is SES's and passes through stripped; lacks it, it is ours and needs
   admin text, the same way the eligibility and render guards got it.
   `errors.Is(err, ErrNoMessageID)` deserves its own sentence (SES accepted the
   message but returned no id, so delivery cannot be tracked — worth saying
   plainly, without the package prefix); the two argument guards can share one
   "the message could not be built for this recipient" line beside
   `adminEligibilityFailureMessage`.
3. **Do not lose SES's text doing it.** The end-to-end proof above is the
   property to preserve: a `MessageRejected` must still arrive byte-identical
   minus our prefix.

Items 1 and 3 of the `## Fix` (the complained copy, and the eligibility/render
replacements) are correct as written and should not be redone.

### Not blocking, but worth the next pass's attention

`adminRenderFailureMessage(err)` ignoring `err` is a defensible decision for
the admin — the sentence tells them the right thing either way — but nothing
else on that path records the discarded error: `sendOne` logs only the *store
write* failure, not `rerr`. A mass render failure now leaves neither a useful
UI string nor a log line, so a render panic, `ErrMissingBaseURL`, and a
Markdown failure are indistinguishable to an engineer as well as to an admin.
One `w.log.Error("mailing: rendering campaign for recipient", "send_id", …,
"err", rerr)` beside the `MarkFailedRow` call closes that without touching any
admin-facing text. The empty-token guard has the same shape.
