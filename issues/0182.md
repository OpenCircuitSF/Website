## Description

**1. Neither `complained` message names the one exit.** `CLAUDE.md` §9 has two halves: a complained subscriber never auto-resubscribes, **and only an admin explicitly clearing that state changes it**. `#0178`'s rewrites keep the first half forcefully ("By design… enforced, not a glitch") and say nothing about the second.

`#0178`'s review judged this not a regression — the strings it replaced said no more — but sharpened where it matters:

- `Suppress`'s message has a `Use "Clear complaint" first` pointer, but it is appended only in the `else` branch (`h.suppressions == nil`), which is dev/test wiring — **production never takes it**. Mitigated in practice by `Admin.svelte:1596` rendering a **Clear complaint** button on the very row the modal sits over.
- `manualAddMessage`'s case is **sharper**: it lands in `createSubNotice` on the manual-add form, where **no Clear-complaint button is adjacent**. An admin is told the address was refused and given no route forward.

**2. Worker error strings render to admins verbatim.** `failed_sends[].error` is an API `error` field rendered per-row in `CampaignStats.svelte`, and its values come from `internal/mailing/worker.go`'s `MarkFailedRow`/`MarkRetryOrFailed` — including the literal `"empty manage token from eligibility recheck"` (`worker.go:671`) and raw `rerr.Error()` / `sendErr.Error()` output.

That is `#0175`'s defect class on a surface **no sweep has covered**: not a citation, but implementation vocabulary shown to someone who cannot act on it. `#0178`'s review confirmed there is no *citation* defect there, so `#0178`'s own conclusion stands — this is the next layer.

## Acceptance criteria

- [ ] Both `complained` messages name the exit — that an admin can clear the complaint, and where — without weakening the refusal's force
- [ ] `manualAddMessage`'s case in particular gives a route forward, since no button is adjacent to it
- [ ] Check whether `Suppress`'s pointer should move out of the `h.suppressions == nil` branch, or whether the adjacent button makes it redundant. Record which
- [ ] `worker.go`'s admin-visible failure strings are written for an admin, or deliberately mapped to admin-facing text at the boundary rather than passed through raw
- [ ] Decide what to do with raw `err.Error()` values in `failed_sends[].error` — an SES rejection reason is genuinely useful, a Go wrapping chain is not. Distinguish them
- [ ] `ISSUE=0182 scripts/check.sh go ./internal/...` and `scripts/check.sh web` both pass

## Notes

Reported by `#0178`'s phase-3 review under `CLAUDE.md` §9.

The second item is worth doing carefully rather than aggressively: an admin debugging a failed send often *wants* the underlying error, and flattening everything to "sending failed" would be worse than the current state. The distinction to draw is between an error the recipient's mail system produced and an error our own code produced.
