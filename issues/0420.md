## Why it is worth closing

This is not tidiness. **It already cost a detour this session.** `#0412` needed
`#0293`'s resolution date to write one sentence; the field was absent, so the
date had to be reconstructed from `git log` on the resolution commit and then
corroborated against a same-day review commit before it could be trusted.

That is the shape this whole family keeps producing — a fact that should be
recorded in one obvious place instead being inferred, with the inference
sometimes going wrong. `#0407`, `#0414`, `#0418` and `#0419` are all the same
class.

**A commit date is not the same fact.** It records when bytes landed, not when
an issue was judged done. For most issues those coincide; for a bounced one they
need not.

## The important nuance, from the review that found it

**The guard matters more than the backfill.** Backfilling these 23 means taking
their dates from git — the very inference this issue exists to remove — so the
backfill inherits whatever uncertainty git leaves. What actually prevents
recurrence is a check that a `resolved` issue carries a `Closed` row.

So treat the guard as the deliverable and the backfill as the cleanup, not the
other way round.

## Decisions on non-`resolved` states

- **`closed`**: included in the guard's scope, matching `issues/Issues.md`'s
  own text ("When status moves to `resolved` or `closed`, add a `**Closed**`
  row…"), not just this issue's title, which names only `resolved`. All 7
  live `closed`-status issues already carry the row, so this widening changes
  nothing about today's pass/fail outcome — it only closes the gap for the
  next issue closed directly rather than through `resolved`.
- **`wontfix`**: deliberately **excluded**. `issues/Issues.md` never states
  the `**Closed**`-row requirement for `wontfix`, only for `resolved`/`closed`,
  and 2 of the 3 live `wontfix` issues (`#0096`, `#0099` — both named in
  `CLAUDE.md` §5 as legitimate `wontfix` closures from the same session)
  currently have no `**Closed**` row. Enforcing it here would invent a
  requirement the project's procedure doesn't state and immediately fail two
  issues nobody asked this guard to touch. `wontfix` is a terminal state, as
  the issue prompt notes, and there's a real argument it should record a
  close date too — but that is a decision about `issues/Issues.md`'s own text,
  not something to smuggle into this guard's scope unasked. Worth a small
  follow-up if the reviewer or user wants it; not filed here per §9 (agents
  report, they don't file).
- **`open`, `in-progress`**: excluded — neither is a terminal state, so
  neither has a resolution date to record.

   The pre-existing citation guard in the same package has the same shape, so
   this is a family trait rather than a regression introduced here.
