## Description

`#0177`'s review found a mutation that **escapes every test**: appending a false history claim to either shared copy branch, without using the literal phrase the guard watches for, passes **77/77**.

- `staysPrivate` → *"…is not currently published **and has not been published before**…"*
- `becomesVisible` → *"…**it has no publication history at all**."*

Both are false for at least one reachable state, and nothing notices — because the assertions check that the **true** claim is *present*, never that a false one is *absent*. `#0174`'s `.not.toMatch(/never published/i)` was meant to cover that, and its own review showed it is a literal-phrase pin: reword the falsehood and it sails through.

**This dialog has now been through three passes, each shipping copy that was wrong for a state nobody had enumerated** — `#0171` gave it a boolean, `#0174` fixed the false-history phrasing, `#0177` derived it from the matrix. The reviewer's point is that pinning the whole sentence with `toBe` is three one-line changes, and cheaper than a fourth pass.

## Acceptance criteria

- [x] Each of the three copy branches asserts its **complete** sentence with `toBe`, not a set of `toMatch`es
- [x] The three `#0177` mutations still fail, and **the fourth one now fails too** — append a false history clause to each shared branch and confirm the tests catch it
- [x] Any test comment claiming a guard is semantic is corrected to describe what it actually pins. `#0177`'s review noted one half-sentence overstates: the positive assertion "pins presence of the true claim, never absence of a false one"
- [x] Consider whether this applies to the other copy functions the recent passes touched — `announceTargetingDescription`, `announceUnsavedInterestsHint`, `demotionExplanation`, `cancelCopy` — and either extend the approach or record why whole-sentence pinning suits this dialog specifically
- [x] `scripts/check.sh web` passes

## Root cause

The three `cancelConfirmMessage` branch tests in `workshopAdmin.test.ts`
asserted with `toMatch`/`not.toMatch` on individual phrases (the true claim
present, one specific known-false phrase absent), never on the sentence as a
whole. That leaves a gap a phrase-level check cannot close: a mutation that
appends an *additional*, differently-worded false clause to the end of an
already-true sentence. Every existing assertion still passes — the true
claim is still present, the one banned phrase (`never published`) is still
absent — because none of them checks that nothing *else* false was said.
Reproduced this against the pre-fix tests: appending "and has not been
published before" to the `staysPrivate` branch and "it has no publication
history at all" to `becomesVisible` passed 77/77.

## Fix

Replaced the three `toMatch`/`not.toMatch` assertion blocks on
`cancelConfirmMessage`'s `staysVisible`, `staysPrivate`, and `becomesVisible`
branches with a single `toBe` on the exact, complete sentence each branch
returns. A `toBe` on the whole string has no room for an appended,
reworded, or reordered false clause to hide in — any deviation from the
pinned sentence fails.

Corrected the test comment that previously claimed the negative
`not.toMatch(/never published/i)` check was "backed by the positive
assertion that actually pins the wording" — the positive assertion only
pinned *presence* of the true claim, never *absence* of a false one. The
new comment states plainly what changed and why (see the block above the
three tests in `workshopAdmin.test.ts`).

**Decision on whole-sentence pinning, and the reasoning:**

`toBe` on a full sentence is deliberately brittle — every wording tweak
becomes a test edit. For this specific dialog that brittleness is worth
buying: it has shipped a false claim on **three separate passes**
(`#0171`'s boolean, `#0174`'s phrasing, `#0177`'s matrix), each time because
the assertions covered what the sentence claimed but not what it didn't.
Fragment-style assertions have now twice proven insufficient in practice,
not in theory, so the fix matches the actual failure mode rather than
hardening one more phrase-level check that a fourth pass could route around
the same way the third did.

**The fourth criterion, answered per neighboring function:**

- **`announceTargetingDescription` / `announceUnsavedInterestsHint`**
  (`workshopAdmin.ts`) — **no.** Each has exactly one true/false branch with
  no derived-fact clause riding along (no history claim, no "and X was never
  Y"), and neither has a multi-pass history of shipping a false claim. The
  existing `toMatch`/`not.toMatch` pins already check both "says the right
  thing" and "doesn't say the specific wrong thing" for the one axis that
  varies, and there's no known escape shaped like the cancel dialog's. Left
  as-is.
- **`demotionExplanation` / `cancelCopy`** (`campaigns.ts`) — **no**, and for
  a different reason: these are read separately in `#0178`'s own audit and
  already assert semantically (`toContain(formatDateTime(...))`,
  `/\d{4}/.test(msg)`, `toContain('refused')`, `not.toContain('worker')`,
  digit-presence checks keyed to a `remaining` count) rather than either
  pinning a literal phrase or leaving room for the cancel dialog's specific
  escape (an appended false clause co-existing with a true one). Neither
  function has a demonstrated history of a false claim slipping past review.
  `campaigns.test.ts` is out of scope for this pass regardless (owned by the
  concurrent `#0178` review subagent this batch), so no change was made
  there; the recorded answer is "no, current semantic assertions already
  cover the failure mode this issue is about."

## Notes

Reported by `#0177`'s phase-3 review under `CLAUDE.md` §9.

There is a real tension here worth resolving deliberately rather than by reflex. Whole-sentence `toBe` assertions are brittle: every wording tweak becomes a test edit, which is exactly the kind of friction that trains people to update tests without reading them. The counter-argument, which the reviewer makes well, is that this particular dialog has a **demonstrated three-pass history of shipping false claims**, so the brittleness is buying something specific rather than being applied on principle.

Whichever way it goes, record the reasoning — including for the other copy functions, where the answer may well be different.
