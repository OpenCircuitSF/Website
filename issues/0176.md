## Description

`#0173` added `sqlFencePattern`/`extractFencedSQL` to narrow `PRD.md` §6.2 to its fenced SQL before tokenizing — a regex over the section text.

**The same Go package already contains a CommonMark-aware fence state machine**: `docs_parity_test.go`'s `docTableRowLines`, which handles backtick *and* tilde fences, indented fences, and enforces that a closer must be at least as long as its opener (`fenceLen`, added by `#0086`'s review for exactly this bug class).

`#0173`'s review classified 21 extractor probes and found none wrong-and-silent — but five wrong-but-loud, all of them shapes the existing parser already handles:

- a second untagged or ` ```SQL `-tagged block is skipped;
- a bare ``` ``` ``` inside a four-backtick body truncates the tail;
- two over-capture cases leak prose back to the tokenizer.

It also noted that the four-backtick case only works **by accident** — ` ````sql ` happens to contain ` ```sql ` at offset 1.

Nothing is broken today: §6.2 has exactly one ` ```sql ` block holding all 13 `CREATE TABLE` and 16 `CREATE INDEX` statements, and a dropped block surfaces loudly through `#0148`'s one-directional scope. This is robustness, and it is cheap because the parser already exists.

Reported by `#0173`'s phase-3 review under `CLAUDE.md` §9.

**This would be the sixth pass over `internal/db/prd_index_parity_test.go`.** That is worth weighing openly: five passes have each been justified, and the file is now materially better than when it started — but a sixth for robustness against markdown this repo does not write is a different proposition from the five that fixed silent failures. **`wontfix` with recorded reasoning is a legitimate outcome**, and if the answer is instead "do it", the argument is that reusing an existing correct parser is *less* code than the regex it replaces, not more.
