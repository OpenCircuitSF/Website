## Description

`#0052`'s admin editor previews the workshop body with `web/src/lib/markdown.ts`, a dependency-free Markdown→HTML renderer written for that issue and rendered through `{@html}`. Its first version shipped a live XSS hole — control characters smuggled `javascript:` past the scheme allowlist, past 22 passing tests — fixed in `b562800`.

Campaigns already solved this problem the other way: the body is rendered by **goldmark on the server**. That gives preview/publish parity for free and moves the attack surface out of the browser entirely.

`#0052`'s reviewer put it plainly: the library-vs-hand-rolled question is a false choice, because "no external CDNs" (`CLAUDE.md` §9) governs runtime loading, not npm build dependencies — but the right answer is neither. A `/preview` endpoint mirroring campaigns' means the preview a person sees is produced by the same renderer that will produce the published page.

- [x] The admin editor previews through that endpoint rather than through client-side rendering
- [x] Preview output and published output are produced by the same code path — demonstrate it, don't assert it
- [x] `web/src/lib/markdown.ts` and its tests are deleted once nothing imports them, **or** the issue records why they must stay

- [x] Emphasis inside link text renders again — `[**bold**](/p)` currently emits literal asterisks inside the anchor. That is the cost of the single left-to-right scan `#0052`'s fix introduced to stop emphasis rewriting `href` attributes, and a server-side renderer makes it moot
- [x] `ISSUE=0136 scripts/check.sh go ./internal/handlers/...` and `scripts/check.sh web` both pass

## Root cause

`#0052` shipped `web/src/lib/markdown.ts`, a dependency-free Markdown->HTML
renderer, and rendered its output client-side via `{@html}` for the admin
editor's preview and (`#0054`) the public workshop detail page. Its first
version shipped a live XSS hole — control characters smuggling `javascript:`
past the scheme allowlist, past 22 passing tests — because a hand-rolled
sanitizer and a browser's URL-normalization algorithm can silently disagree
about what counts as a URL. `b562800` closed that specific hole, but every
future edit to the same hand-rolled renderer was a chance to reopen a
sibling bug — and it already had one: the fix's own left-to-right link/
emphasis scan broke emphasis *inside* link text (`[**bold**](/p)` emitted
literal asterisks), because links and emphasis were two separate regex
passes with no shared parse tree. Campaigns had already solved the general
problem the right way (goldmark on the server, `#0042`/`#0043`), and
`#0052`'s own reviewer named the fix as a follow-up rather than re-hardening
the client renderer a second time.

    byte the way `markdown.ts`'s original bug did. Verified independently
    against Node's WHATWG `URL` parser: `new URL("%01javascript:alert(1)",

    (checks `href="javascript:`/`href="data:`, etc.) rather than a bare
    substring search — a bare search would have failed on genuinely safe
    output.

    seeding a workshop with one via the real store fails with

## Gotchas

- **Goldmark's safe mode does not reject a protocol-relative link
  (`//evil.host/x`) inside body Markdown text.** It only refuses a
  dangerous *scheme* (`javascript:`, `vbscript:`, `file:`, most `data:`);
  a `//host/path` destination survives as a live, off-site `<a href>`.
  This is **not a regression #0136 introduces** —
  `internal/mailing.RenderMarkdownHTML` is the exact function
  `email_campaigns.body_md` has rendered through since `#0042`/`#0043`,
  shipped and reviewed, with this same property; reusing it for workshops
  inherits campaigns' existing posture unchanged. It **is** a narrowing
  relative to the deleted client renderer specifically for workshop BODY
  content: `markdown.ts`'s `renderMarkdownPreview` ran every link through
  `isSafeLinkHref`, which has rejected protocol-relative destinations since
  `#0138`. `signup_url` and `cover_image` are unaffected — both are still
  gated by their own dedicated Go validators (`isSafeLinkHref`/
  `isSafeCoverImage`, `#0138`/`#0152`) at the API boundary, untouched by
  this change. Pinned by
  `TestAdminWorkshopPreview_ProtocolRelativeLinkInheritsCampaignBehavior`,
  which documents the current behavior rather than asserting a fix — left
  for the reviewer to judge whether a follow-up extending goldmark's link
  policy (which would also affect campaigns, an unrelated subsystem) is
  worth filing. Per `CLAUDE.md` §9, this implementer does not file it.
- **Workshop body preview is no longer "live while typing."** The editor
  has explicit Save (not autosave, unlike `CampaignEditor.svelte`), and the
  new preview endpoint always renders the STORED row — the same contract
  campaigns' preview already enforces. So the preview pane now shows the
  last-saved body, refreshed after `load()` and after each successful
  `save()`, not the in-progress unsaved buffer. This is a deliberate
  consequence of "preview must equal publish," not an oversight.
- **`web/dist/index.html` was not touched.** `npm run build` was never run
  during this issue (only `npm run check` and `npm test`), so the tracked
  placeholder (`#0141`) needed no restoring; `git status -- web/dist/index.html`
  stayed clean throughout.
- A temporary, uncommitted probe test
  (`internal/mailing/zz_probe_test.go`) was written and deleted during
  verification to inspect goldmark's actual output for the control-character
  payloads before writing assertions against them — see `## Verification`.
  It never touched `git add`/`git status` as tracked content; confirmed via
  `git status --porcelain internal/mailing` showing nothing both before and
  after.

and zero emitted a live element tag or an event-handler attribute.** The
angle-bracket destination form is the interesting new result: CommonMark's
`<…>` destination grammar *does* accept the control characters the bare
`(…)` form rejects, so those inputs now parse as links — but
`util.URLEscape` percent-encodes the control byte, `%` is not a legal
scheme-start character under RFC 3986/WHATWG, and the parser therefore
resolves them same-origin. The property holds for a reason, not by luck.

The implementer's `hrefStartsWithDangerousScheme` choice over a bare
`strings.Contains` is **correct and load-bearing**: `%01javascript:alert(1)`
genuinely contains the substring `javascript:` as inert path text, so a
substring assertion would fail on safe output and invite someone to
"fix" it by weakening the payload.

### Ruling on the protocol-relative narrowing — acceptable, but it needs an owner

**Not a bounce.** The reasoning, weighed rather than waved through:

1. **It grants an attacker nothing.** `//evil.host/x` resolves to
   `https://evil.host/x`, and `[x](https://evil.host/x)` has always been
   allowed by design — `#0138` decided explicitly that body links may point
   off-site because a workshop's signup is routinely an external ticketing
   page. `#0052`'s pass-2 review reached the same conclusion in the same
   words: "**Not a bypass** — an ordinary `[x](https://evil.host/x)` is
   allowed by design, so this grants nothing new." The §9 self-contained
   rule that made protocol-relative *images* a real defect does not apply:
   a link is a navigation the reader chooses, not a load the page performs.
2. **It is inherited, not introduced.** `mailing.RenderMarkdownHTML` is the
   exact function `email_campaigns.body_md` has rendered through since
   `#0042`/`#0043`, shipped and reviewed with this property. Reusing it
   does not weaken campaigns and does not weaken workshop `signup_url` or
   `cover_image`, both still gated by their own Go validators at the API
   boundary (`#0138`/`#0152`) — re-confirmed unchanged by this diff.
3. **The content is admin-authored**, behind a passkey-gated console.
4. **Fixing it here would be out of scope in the literal sense**: the only
   place to enforce it is goldmark's link policy, which is campaigns' too.

**But it is not nothing, and the implementer under-stated one thing.**
`#0138`'s acceptance criterion 5 reads: "The same decision covers **link
destinations in Markdown body text**, not just cover images:
`renderMarkdownPreview` accepts `//evil.host/x` and `\\evil.host/x`…
one ruling should settle both." That box is ticked and `#0138` is closed —
so the project has a shipped, resolved decision whose only enforcing code
this issue deleted. The decision is now true for `signup_url` and
`cover_image` and false for body text, with nothing recording that.

**Where it should live: neither `#0138` nor `#0157` — file a new one.**
`#0138` is closed and cannot absorb a criterion that is now false.
`#0157` is about a *build-time guard* keeping two existing Go↔TS twins from
drifting; a goldmark link policy would be a third implementation of the
rule, which changes `#0157`'s table but is not the decision `#0157` makes.
Reported to the orchestrator to file, not filed here (`CLAUDE.md` §9). It
should fold in two further variants found by this review, same family and
same owner:

- **`///evil.host/x`** resolves off-site identically; any rule must match
  on the normalized form, not on a literal two-slash prefix.
- **`data:image/png|gif|jpeg|webp` link destinations survive** as a live
  `<a href="data:…">` (goldmark's `IsDangerousURL` allowlists those four
  raster types). The deleted `isSafeLinkHref` rejected every `data:`
  destination, so this is a *second*, undisclosed narrowing of the same
  shape. It is inert in practice — `data:image/svg+xml` (the executable
  one) **is** refused, verified above, and browsers have blocked top-level
  navigation to `data:` URLs since Chrome 60 — which is why it is a note
  and not a finding.

`TestAdminWorkshopPreview_ProtocolRelativeLinkInheritsCampaignBehavior` is
the right shape for pinning this: it documents current behavior and its
failure message tells a future reader that campaigns' policy changed
underneath it rather than inviting a widened assertion.

### The last-saved preview — the right contract, an incomplete affordance

The UX consequence is real and the implementer was right to call it out.
Judgment: **acceptable, not a bounce, but the editor does not make it
evident in the case that matters.**

- The contract is correct. "Preview renders the stored row" is what makes
  parity provable, it is what campaigns already do, and this issue's own
  Description asks for exactly it. Criterion 2 ("the admin editor previews
  through that endpoint") is met.
- The affordance is half-built. `hasPreviewContent` is derived from
  `previewHtml`, not from `fields.bodyMd`, so the explanatory copy —
  "Nothing to preview yet. Save the body first — the preview shows the last
  saved version." — appears **only when the stored body is empty**, i.e.
  only on a brand-new workshop. On the common case, editing a workshop that
  already has a body, an admin types, clicks "Show preview", and sees the
  *previous* text with no cue at all. The button reads "Show preview", not
  "Preview last saved".
- Why it is not blocking: Save sits directly above, the pane refreshes on
  every successful save and shows "Saved.", and the failure mode is a stale
  render rather than a wrong or unsafe one. An admin recovers in one click.
  The fix is small and additive — mark the pane stale when
  `fields.bodyMd !== workshop.body_md`, or label it "Preview (last saved)".
  Reported to the orchestrator as a follow-up.

### Non-blocking observations

1. **`toPublicView` is called from the list handler too**
   (`public_workshops.go:155`), so `GET /api/workshops` now renders every
   listed workshop's full body through goldmark and ships the HTML.
   `body_md` was already in that response, so this roughly doubles a field
   already being sent rather than introducing a new class of payload — and
   `CLAUDE.md` §5 is explicit that this project has no performance
   requirement. Worth knowing, not worth changing.
2. **No test covers `body_html` in the *list* response** — the parity test
   exercises the detail route only. Low value; the same function produces
   both.
3. **`refreshPreview()` fires on `load()` even though `previewOpen` starts
   `false`**, so every editor open costs one `POST .../preview` that may
   never be looked at. Harmless, and it makes the pane instant when opened.
4. **Error-path asymmetry**: a render failure 422s on the preview route and
   is silently omitted on the public route. Both are defensible for their
   own context (`toPublicView`'s existing degraded-but-safe posture) and
   `RenderMarkdownHTML` does not error on ordinary input.

### Summary

Every acceptance criterion is met and independently re-verified. The
parity claim survives mutation, the safety claim survives 32 payloads
checked against a real URL parser, the deletion left nothing dangling, and
the one disclosed narrowing is a genuine narrowing with no security
consequence that needs a follow-up rather than a bounce. Resolved.
