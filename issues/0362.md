## Description

Two low-priority residues in `CLAUDE.md` §8's satisfier entry, both found by
`#0357`'s review and **deliberately left below that issue's bar** rather than
fixed silently (its criterion 3 says report, do not fix).

**1. A stale imperative.** The value-receiver paragraph ends:

> Any guard modeled on this one must scan both receiver forms.

Written when `#0337`'s guard was an AST scan. Since `#0349` the guard is
`go/types.Implements` over the package's full named-type set, and the
receiver-form special cases, the embedding tripwire and the `embeddingReviewed`
allowlist were **all deleted**.

The imperative is **not false** — a `go/types` guard covers both forms
automatically, satisfying it vacuously — and the clause immediately after names
`go/types` as the sound oracle, so a reader of the whole sentence is not misled.
But **quoted alone it implies the current guard does something it no longer
does**, which is the same staleness family as `#0356`.

**2. A category slip** in the same paragraph: "that exact zero-parameter,
zero-result **name**". A signature has parameters and results; a name does not.

Neither inverts, which is why `#0357` left them.

## Root cause

Both residues trace to the same event: `#0349` replaced the AST declaration
scan in `internal/seo/invalidator_satisfier_guard_test.go` with
`go/types.Implements` over the package's full named-type set, which checks
`types.Implements(target, ...) || types.Implements(types.NewPointer(target),
...)` (method-set membership on both `T` and `*T`) rather than walking
declaration syntax for pointer- and value-receiver forms. The `#0346`/`#0350`
prose describing the guard's behavior and the property of
`(*seo.Sitemap).Invalidate` predated that rewrite and was never revisited when
it landed, so the imperative kept describing an action (scanning) the guard no
longer performs, and the earlier "name" wording (a category slip independent
of `#0349`) went unnoticed until `#0357`'s adversarial re-read.

### Criterion 1 — is "cover" right, and is it true of the guard as it exists?

The cited line exists and says what the implementer claims.
`internal/seo/invalidator_satisfier_guard_test.go:267` reads

```go
if types.Implements(target, invalidateOnly) || types.Implements(types.NewPointer(target), invalidateOnly) {
```

**But that line is not where the guard's receiver-form coverage comes from**,
and the record should say so. Line 267 sits inside the `types.Unalias` branch
(`#0353`), reached only when the target is *not* a `*types.Named`. Per the doc
comment directly above it (`#0354`), its two disjuncts are load-bearing for
**alias** shapes — `type X = struct{ Site }` implements in the pointer form
only, `type X = *struct{ *Site }` in the value form only — not for value- versus
pointer-*receiver* declarations. Ordinary named types take the branch at line
285, which checks the **pointer form alone**:

```go
if types.Implements(types.NewPointer(named), invalidateOnly) {
```

That single check is exactly why **"cover" is the right verb and not a
euphemism.** Go's method-set rule is that the method set of `*T` contains every
method declared with receiver `T` *or* `*T`; so one `types.Implements` call on
`*T` covers both receiver forms without scanning either. The guard **covers**
both and **scans** neither — which is precisely the achieve-versus-technique
distinction the word change makes, and why the imperative is now true of a
`go/types` oracle and of an AST scan alike. The same doc comment corroborates
this from the other side: it says checking only the pointer form "(as the loop
below does) is not sound **here**", the exception existing because an alias
target is not a `*types.Named` — which presupposes soundness for the named
types the loop does handle.

`internal/seo/invalidator_satisfier_guard_test.go` was read only, never edited.

**Note for the record, not a bounce:** the citation in `## Fix`, the work log
and the commit message points at line 267 for a property that line 285 supplies.
The prose it defends is true either way, and the issue is documentation-only, so
this does not fail the criterion — but it is one line off, and this entry's
history is exactly a history of references that were nearly right.

### Criterion 2 — "signature": preserved, not weakened

This is the question I was asked to answer, so I will answer it directly.
The sentence now reads:

> `(*seo.Sitemap).Invalidate` already carried that exact zero-parameter,
> zero-result signature, so passing a bare `*Sitemap` into either seam went
> from a compile error to a silent half-invalidation.

**Preserved.** Three grounds, in ascending order of weight.

1. **The name fact has not left the sentence; it moved into the subject.** The
   subject is the qualified designator `(*seo.Sitemap).Invalidate`, and the
   verb is `already carried`. A reader is told the method *is* `Invalidate` by
   the subject and that its parameters and results *already* matched by the
   predicate — together, exactly the two conditions Go requires for interface
   satisfaction (same name, identical signature). Under `name` the predicate
   restated what the subject already said, and did so with a category error;
   under `signature` the predicate contributes the fact the subject cannot
   carry. It is strictly more informative, not less.

2. **The neighbouring sentence states the name fact more strongly than the old
   predicate did, and checkably.** Immediately before: "`f7771ed` rewrote the
   doc comment directly above `func (s *Sitemap) Invalidate()`, so the
   recruited declaration sat in the rename commit's own diff as context". I
   re-verified that against `git show f7771ed -- internal/seo/sitemap.go`: one
   hunk, `@@ -145,8 +145,10 @@`, whose only `+`/`-` lines are doc comment; the
   `func (s *Sitemap) Invalidate() {` line appears as **context**. So the name
   *and* the signature demonstrably pre-dated the rename, and the entry proves
   the name half by exhibiting the declaration rather than by asserting it.

3. **Decisively: the code's own record already says "signature", in these exact
   words.** `internal/seo/sitemap.go`'s `invalidate` doc comment (unchanged
   since `#0337`) reads "Sitemap already had a method with this exact
   zero-parameter, zero-result **signature** before Site.Invalidate was itself
   named InvalidateWorkshops". `#0346`'s review quoted that comment as the
   authority the inverted entry conflicted with. So `name` was the outlier all
   along, and this change restores parity between `CLAUDE.md` and the file it
   describes — the "the doc and the guard do not disagree" criterion that
   governed `#0346` and `#0350`. Trading grammar for meaning would have moved
   the two apart; this moved them together.

The one thing genuinely given up is redundancy: under `name`, the sentence
asserted the name pre-existed twice. Quoted alone the new sentence asserts
