## Description

`#0314`'s plan adds a `status <> 'complained'` guard to
`ClaimAndEnqueueConfirmation`'s claim, inside the SQL.

`AdminResendConfirmation`, its twin, guards `status = 'pending'` in Go under
`FOR UPDATE` instead. That is **sound** — the row lock makes the check-then-act
atomic, and `pending` excludes `complained` today.

~~The defect is the asymmetry, not a live hole.~~ **Correction (#0341,
2026-09-01).** This was written on the assumption that `#0314`'s plan — "adds a
`status <> 'complained'` guard to `ClaimAndEnqueueConfirmation`'s claim, inside
the SQL" — had already landed by the time this issue would be worked. It had
not: as of this implementation pass, `#0312`/`#0313`/`#0314` are still `open`,
carrying only the shared `## Plan` section from their 2026-08-28 planning pass
(commit `b8af685`), with no implementing commit. So the code this issue was
actually implemented against had **no status guard on `ClaimAndEnqueueConfirmation`'s
claim at all** — not even the `<> 'complained'` form this description compares
against — which is a live hole, not merely an asymmetry of expression: a
`complained` row that lost its `confirm_token` race (an SES complaint landing
between a caller's status read and this claim's commit) would be claimed and
mailed a fresh confirmation. See `## Verification` below for the failing-test
proof against the pre-fix code. Two functions doing the same job
now express the same safety property two different ways, in two different
layers, and only one of them names `complained` explicitly. `complained`
subscribers never auto-resubscribe — only an admin clears that state — and §9
lists that among the restricted rules. A rule that load-bearing should be
expressed the same way everywhere it is enforced, or the divergence should be
deliberate and documented.

It is worth an issue rather than a note because the next person to add a third
claim path has two incompatible precedents to copy, and the Go-side one depends
on an implicit `pending`-excludes-`complained` invariant that nothing asserts.

## Acceptance criteria

1. Both claim paths express the `complained` exclusion the same way, or the
   divergence is documented at both sites with the reason.
2. The implicit invariant — that `status = 'pending'` excludes `complained` —
   is either asserted by a test or made explicit in the predicate.
3. No path can auto-resubscribe a `complained` address (§9, restricted). Proved
   by mutation against both claim paths: the mutation must fail on the un-fixed
   code.
4. `FOR UPDATE`'s atomicity is preserved wherever it currently provides it —
   this must not become a check-then-act race.
5. Enumerate every claim path that transitions a subscriber toward `confirmed`
   and confirm each is covered; there may be more than these two.

**What changed** (`internal/subscribers/store.go`,
`internal/subscribers/pending.go`):

- `ClaimAndEnqueueConfirmation`'s claim UPDATE gained `AND status = $4` (bound
  to `StatusPending`) in its `WHERE` clause, alongside the existing
  `confirm_sent_at`-cooldown condition. This is the same predicate
  `AdminResendConfirmation` already checks in Go (`sub.Status != StatusPending`
  -> `ErrNotPending`) under its `SELECT … FOR UPDATE` — criterion 1 ("the same
  way") and criterion 2 (no implicit invariant: the predicate now says
  `pending`, full stop, rather than relying on `pending` happening to exclude
  `complained`) are both closed by using the identical predicate value, in the
  layer each method's own transaction shape calls for.
- No change to `AdminResendConfirmation`'s mechanism or to any `FOR UPDATE`
  site — criterion 4 holds by construction (nothing that had a row lock lost
  it or gained a check-then-act gap; `ClaimAndEnqueueConfirmation` never had a
  prior `SELECT`, so its claim staying a single atomic conditional `UPDATE`
  with one more `AND` term preserves the exact same atomicity it had before).
- Both methods' doc comments now cross-reference each other and record the
  reasoning for the two-different-layers choice, closing criterion 1's
  "or documented" branch as belt-and-suspenders alongside the "same predicate"
  fix itself.
- `ClaimAndEnqueueConfirmation`'s doc comment enumerates all three
  outbox.KindConfirmation-producing paths (`Create`, `ClaimAndEnqueueConfirmation`,
  `AdminResendConfirmation`) and states why each is covered — criterion 5.
  Verified nothing else produces this event kind: `grep -rn KindConfirmation
  internal/` (not pasted here, just the file list) turns up only
  `internal/outbox/store.go` (the constant), `internal/subscribers/pending.go`
  and `store.go` (the three claim methods, `pending.go`'s doc comment), the two
  admin handler files that only *display* pending state, and
  `internal/mailing/outbox_worker.go`, which sends whatever a claim already
  enqueued and never re-derives or re-checks subscriber status.
- Criterion 3 (no path can auto-resubscribe a `complained` address):
  independent of this issue, `Confirm` (`store.go`) already refuses outright on
  `sub.Status == StatusComplained` (`ErrComplainedLocked`) before any status
  write — that is the actual resubscribe gate, and it was never in question
  here. What this issue closes is the narrower, still real gap the mutation
  test below proves: `ClaimAndEnqueueConfirmation` claiming and mailing a
  confirmation to an already-`complained` row, which it could do today even
  though the mail would lead nowhere (any click would hit `Confirm`'s guard).
