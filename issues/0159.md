## Description

`#0154` built `TestPRDWorkshopAndMailingColumnParity` and the two coverage
checks that make an unparseable statement fail loudly instead of vanishing
(`checkTableStatementCoverage`, `checkColumnAddCoverage`, in
`internal/db/prd_index_parity_test.go`). Both work — `#0154`'s pass-2 review
proved they genuinely fire, and proved the guard's live column map is
identical, column for column, to the real migrated schema (91 columns across
the ten guarded tables).

Three forms still slip past **silently** — no failure, no coverage error, green
suite — and all three come from the same place: `looseColumnAddPattern`
(`ALTER\s+TABLE\s+\w+\s+ADD\b`) is supposed to be the maximally permissive
ceiling the strict pattern is measured against, but it is not permissive
enough to be one.

**1. Multi-clause `ADD` — the ordinary one.** Postgres allows

```sql
ALTER TABLE workshops ADD COLUMN mc_one TEXT, ADD COLUMN mc_two TEXT;
```

Both the loose and the strict pattern match once, at the `ALTER TABLE workshops
ADD` prefix. The second and later `ADD` clauses are invisible to *both* sides,
so the counts agree and the coverage check cannot fire. Proved fully silent: a
scratch migration adding `mc_one` and `mc_two`, with only `mc_one` documented
in a scratch `PRD.md`, ran green — `mc_two` was never guarded. This repo
already writes multi-clause `ALTER`s: `migrations/000007` ends with
`ALTER TABLE sessions ALTER COLUMN user_id SET NOT NULL, ALTER COLUMN
created_at SET NOT NULL, …`.

**2. `ALTER TABLE ONLY` and a quoted table name.**

```sql
ALTER TABLE ONLY workshops ADD COLUMN only_col TEXT;
ALTER TABLE "workshops"  ADD COLUMN q_col    TEXT;
```

Neither matches the loose pattern's `\w+` table-name slot, so loose and strict
are both `0` and the mismatch the coverage check looks for never exists. Both
proved silent end-to-end. Note the asymmetry with the table side, which is
already correct here: `looseTableStartPattern` is just `CREATE\s+TABLE\b`, so a
quoted `CREATE TABLE "t" (` *does* fire the coverage check. The ADD ceiling
should be equally dumb.

**3. No dollar quoting in the quote-aware scanner.** `stripSQLComments`,
`splitTopLevel`, and `columnsFromCreateTable`'s close-paren finder each track
`'…'` state (with Postgres's `''` escape) but know nothing about `$tag$…$tag$`.
A dollar-quoted string containing an *odd* number of apostrophes flips the
scanner into "inside a string" for the rest of the file. Proved:

```sql
DO $$ BEGIN RAISE NOTICE $x$it's fine$x$; END $$;

CREATE TABLE scratch_dq (
    a INT,                 -- the worker's column
    b TEXT,
    c INT
);
```

The `--` comment is no longer stripped, so the body scan meets its apostrophe
and the table parses as `[a, "--"]`: a bogus column named `--` (loud) with
**`b` and `c` silently dropped**. The current tree is clear —
`migrations/000007` is the only file containing `$$` at all, its `RAISE
EXCEPTION` literal has balanced apostrophes, and it touches only auth tables,
which are outside `prdIndexParityTables` — but the exposure is real for any
future migration that ships a trigger or function body.

None of the three exist in `migrations/` today, so nothing is currently
mis-guarded. This is the same standing `#0154` had when `#0148`'s review filed
it, and it is filed the same way: as hardening, deliberately not a bounce.

## Root cause

All three gaps trace to the same structural limit in `looseColumnAddPattern`
and `columnAddPattern` as they existed after `#0154`: both patterns matched
**once per `ALTER TABLE` statement**, anchored on the literal shape
`ALTER TABLE <\w+> ADD`.

- A second or later comma-joined `ADD` clause in one statement never got a
  chance to match at all — the regex engine had already consumed the
  statement's only `ALTER TABLE <name> ADD` prefix on the first clause, and
  nothing about a later `, ADD COLUMN b …` clause looks like a fresh
  `ALTER TABLE` statement to either pattern.
- `\w+` cannot match `ONLY workshops` (two tokens) or `"workshops"` (quoted),
  so those forms produced zero matches on *both* the loose and strict side —
  agreement by mutual absence, not correctness.
- The quote-aware scanners (`stripSQLComments`, `splitTopLevel`,
  `columnsFromCreateTable`'s close-paren finder) tracked only Postgres's
  `'…'`/`''`-escaped string literals. A dollar-quoted body's apostrophes are
  not string literals to the scanner, so an odd count inside one silently
  toggled `inString` for everything after it.

## Fix

Replaced the single-shot `columnAddPattern`/`looseColumnAddPattern` pair with
a two-tier design that separates "can we identify this ALTER TABLE
statement's boundaries?" from "can we classify each of its clauses?":

- **`alterTableStmtPattern`** / **`looseAlterTableStmtPattern`** recognize one
  whole `ALTER TABLE` statement — table name (accepting an optional `ONLY`
  and optional double-quoting, unwrapped) through its terminating `;` —
  capturing the entire clause list as one blob rather than trying to match a
  single clause inline. `looseAlterTableStmtPattern` requires the literal
  trailing whitespace after `TABLE` (`ALTER\s+TABLE\s+`, not just `\b`)
  specifically because PRD.md §6.2 has several prose mentions of
  `` `ALTER TABLE` `` in backtick-quoted text with no space before the
  closing backtick — a bare `\b` ceiling would have counted those as loose
  matches with nothing on the strict side, a false positive against text
  that was never SQL. **`checkAlterTableStatementCoverage`** is this tier's
  guard-for-the-guard, mirroring `checkTableStatementCoverage`.
- The statement's clause blob is split on top-level commas with the existing
  `splitTopLevel` (already quote/paren-aware from `#0154`), so **every**
  clause — not just the first — is examined independently. **`clauseAddPattern`**
  / **`looseClauseAddPattern`** are `columnAddPattern`/`looseColumnAddPattern`'s
  direct successors, anchored (`^\s*ADD…`) since they now run against one
  already-isolated clause rather than scanning a whole file.
  **`checkColumnAddCoverage`** was rebuilt to iterate statements → clauses and
  count per clause; **`columnAddsInClauses`** does the matching extraction for
  `liveColumnsFromMigrations`, sharing `classifyColumnAdd`/
  `isTableConstraintSegment` with the coverage check so the two can never
  disagree about what counts as a column versus a constraint add.
- For dollar quoting: **decided to lex it properly, not detect-and-refuse.**
  A blanket "refuse any file containing `$$`" would have been a straightforward
  false positive against the current tree — `migrations/000007`'s `DO $$ …
  $$;` block already exists and is harmless (its one string literal has
  balanced apostrophes), so refusing on sight of `$$` would fail a file that
  isn't actually broken. Properly lexing it is also not much code:
  **`dollarQuoteEnd`** finds a dollar-quote tag opener (`$$` or `$tag$`,
  restricted to Postgres's actual identifier rule so a stray `$1` positional
  parameter is never mistaken for one) and jumps straight to the *next*
  literal occurrence of the same tag — which is exactly how Postgres itself
  resolves dollar-quote boundaries (not nesting-aware; a differently-tagged
  `$x$…$x$` textually inside an outer `$$…$$` does not close the outer tag).
  Wired into `stripSQLComments`, `splitTopLevel`, and
  `columnsFromCreateTable`'s close-paren finder as one more branch alongside
  the existing `'…'` handling: a dollar-quoted span is copied through / jumped
  over as one atomic, opaque unit, so nothing inside it — including an odd
  apostrophe count — is ever re-inspected for quote state.

Scope stayed strictly one-directional; no allowlist was added anywhere.

## Gotchas

- `migrationsDir` (`internal/db/docs_parity_test.go`) is a hardcoded const,
  unlike `prdPath`, so every migrations-side proof had to write real scratch
  files into the worktree's `migrations/` directory rather than pointing at a
  temp copy. Harmless here — the worktree itself is the throwaway copy — but
  worth knowing before reaching for a `t.TempDir()` trick on that side.
- `listMigrations` has no contiguity/down-file requirement of its own (those
  live in `verifyContiguous`/`verifyDownPairs`, called only from
  `TestDatabaseDocMigrationParity`), so oddly-numbered scratch migrations
  (`999997_…`, `999996_…`, …) are safe as long as proofs are scoped to
  `-run TestPRDWorkshopAndMailingColumnParity` — the same constraint `#0154`'s
  Gotchas already recorded, reconfirmed here.
- Proving the dollar-quote fix actually changed behavior (not just that the
  new code produces the right answer) needed a genuine before/after: I
  temporarily short-circuited `dollarQuoteEnd` to always return `(0, false)`,
  reran the identical `scratch_dq` input, watched it reproduce the exact
  `[a, "--"]` bug the issue describes, then restored the file and confirmed
  it was byte-identical to the pre-mutation copy (`diff` empty) before
  continuing. `go vet` flags the short-circuited version's now-dead code
  (`unreachable code`), so that specific comparison run needed `-vet=off`;
  the real, shipped code has no such branch and vets clean.
- Confirmed `internal/db/prd_index_parity_test.go`'s pre-existing `gofmt -l`
  flag (`#0161`) is unrelated to this change: `gofmt -d` shows exactly one
  diff, a smart-quote character in a doc comment several lines above anything
  `#0159` touched, present before this commit. Left alone per the task's
  instruction not to muddy this diff with an unrelated formatting fix.
