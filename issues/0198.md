## Description

`#0193` unified the two guards' `PRD §` whitespace handling, and its phase-3
review proved the result exhaustively: sweeping U+0000–U+10FFFF in both real
engines, the Go class, the web class, and V8's native `\s` are **the same
25-codepoint set**, with no disagreement in any direction.

But they are equivalent in *meaning*, not in *text*. Go spells `\x{00A0}` and
`[0-9]{3}`; web spells `\u00A0` and `\d{3}`. Both divergences are proven
cosmetic today — and **nothing keeps them in step**. Editing one guard's
character class would not fail the other guard's tests, so the next change to
either can silently re-open the divergence `#0193` just closed.

The coupling is currently conventional (two files that happen to agree) where it
should be structural (one source of truth, or a test that fails when they drift).

That matters because the divergence `#0193` fixed was itself invisible for as
long as it existed: `PRD\s*§` looked identical in both files and meant different
things, and it took a reviewer extracting both patterns and running a 38-case
battery to notice.

## Implementation notes

**Design chosen: a shared canonical codepoint list, asserted independently
against each engine's shipped `citationPattern` — not generating one pattern
from the other.** The two options this issue's `## Notes` named were
recorded, weighed, and one picked:

- *Generate one pattern from the other.* Rejected. RE2 (`x{...}` ranges,
  `\b`, no lookbehind) and V8 (`\u`-escapes, `u`/`v`-flag semantics) read
  different escape and range syntaxes even for an identical class — there is
  no single pattern-text representation both engines accept verbatim, so
  "generate" would mean building a small codegen step that emits two
  different literal strings from one internal representation. That is a
  bigger change than this issue's scope (two test files) supports, and it
  would still need its own test to prove the generator itself stays correct.
- *A shared codepoint list both suites read and assert against.* Chosen. Each
  file gets an identical, hardcoded `MUST_MATCH` (25 codepoints) /
  `MUST_NOT_MATCH` (10 codepoints, `#0193`'s near-miss set) pair and a new
  test that runs its own file's `citationPattern` against every entry, in
  that file's real engine — Go's `regexp` in
  `internal/handlers/citation_guard_test.go`
  (`whitespaceClassMustMatch`/`whitespaceClassMustNotMatch` and
  `TestCitationPatternWhitespaceClassStaysCoupledWithWebGuard`), V8 via
  vitest in `web/src/lib/citationGuard.test.ts`
  (`WHITESPACE_MUST_MATCH`/`WHITESPACE_MUST_NOT_MATCH` and the "citation
  guard whitespace class stays coupled with the Go guard" describe block).
  Neither file reads the other's source, and there is no third shared data
  file — the coupling is that both are pinned to the *same* hardcoded ground
  truth. If either engine's live class drifts off that ground truth (loses a
  codepoint it should accept, or gains one it should reject), that file's own
  new test fails on its own — no dependency on the other suite, the other
  language, or the other engine having run in the same process.

  This is a stronger property than "the two guards agree with each other":
  since both are checked against a fixed, spec-derived list (ECMA-262's
  `WhiteSpace` + `LineTerminator` union, the same list `#0193`'s phase-3
  review proved both live patterns already equal to V8's native `\s`), a
  hypothetical future edit that moved *both* patterns the same wrong way
  would also be caught — not just an edit that moves one and not the other.

**The codepoint list is `#0193`'s already-derived fixture list, reused
verbatim rather than re-derived.** `MUST_MATCH` is the 25-codepoint accepted
set from that review's exhaustive U+0000–U+10FFFF sweep (TAB, LF, VT, FF, CR,
SPACE, NBSP, Ogham space mark, the eleven general-punctuation spaces
U+2000–U+200A, LS, PS, narrow no-break space, medium mathematical space,
ideographic space, ZWNBSP/BOM). `MUST_NOT_MATCH` is the near-miss set this
issue's `## Notes` names: U+0085 (NEL), U+00AD (soft hyphen), U+180E
(Mongolian vowel separator — Zs before Unicode 6.3, Cf since, the plausible
drift), U+200B–U+200D (ZWSP/ZWNJ/ZWJ), U+2060 (word joiner), U+2064
(invisible plus), U+3164 (Hangul filler), U+FFFC (object replacement
character).

**Fixture discipline (`CLAUDE.md` §8).** Every codepoint is built at runtime
from its hex value — `string(rune(cp))` in Go, `String.fromCodePoint(cp)` in
TS — never typed as a literal character. This actually caught a live
instance of the exact trap §8 warns about while drafting the web-side
explanatory comment: a typed `\`+`u00A0` (intended as literal backslash-u
text describing the Go escape form in prose) landed as an actual NBSP byte
(confirmed via `python3 -c "print(open(P,'rb').read())"`, `\xc2\xa0` where six
ASCII characters were intended). Fixed by replacing it with an escaped
`\\u00A0` built the same way the file's existing whitespace-shape test
already does. A full non-ASCII census of both edited files after the fix
found exactly `§` (U+00A7) and `—` (U+2014, existing prose) — nothing else —
in both files.

**Web-side tests call `citationPattern.test()` directly on a runtime-built
string, not through `scanTsSource`.** The existing `'fires on every
whitespace shape...'` test routes through `scanTsSource` because it exercises
the *scanner*, which requires generating and parsing TS source text — and LF/
CR can't appear raw in a single-quoted string literal, hence that test's
`\uXXXX`-escape-in-source technique. The new coupling test only needs to
prove pattern membership, so it skips source generation entirely and calls
`citationPattern.test(str)` on a string assembled with
`String.fromCodePoint` at runtime — legal for every codepoint including LF/CR
since it's a JS runtime value, not parsed TS source. This mirrors the Go
side's direct `citationPattern.MatchString(...)` call exactly.

### Verdict on duplicating the list rather than a single source of truth: **the trade is right**

Interrogated, because it is the crux, and it is not the anti-pattern
`#0184`/`#0189`/`#0195`/`#0197` were about. Those were **two implementations of
one rule** — logic that can silently mean different things. This is **one
spec-derived constant written down twice**, with each copy checked against a
different real engine. The distinction matters:

- The two lists are not each other's oracle. Each is an assertion against
  ECMA-262's `WhiteSpace` ∪ `LineTerminator`, which is fixed and external. If
  the two copies ever disagreed, the spec — not the other file — says which is
  wrong. That is the property the implementer claims, and it holds: a future
  edit moving *both* patterns the same wrong way still fails both suites.
- Go cannot import TypeScript, so "one source of truth" means a third
  JSON/fixture file parsed by both languages. That buys textual identity of
  the two copies and costs a new untyped file, two parsers, and a fixture the
  compiler cannot check — and, decisively, **it does not fix the residual
  failure mode below.** Deleting an entry from a shared file removes the
  assertion from *both* sides at once, which is if anything worse.
- Codegen was rejected for a sound reason, verified: RE2 spells the class
  `\x{00A0}` and V8 `\u00A0`; there is no pattern text both engines accept
  verbatim, so generation means a codegen step plus a test for the generator.
  Out of a two-file issue's scope, and not obviously better.

Sound trade. Not bounced.

### The residual gap, measured: list *shrinkage* is silent (reported for filing, not a criterion failure)

Reasoned through and then tested. Removing `0x2007` from the Go
`whitespaceClassMustMatch` **only**, and `0x200b` from the web
`WHITESPACE_MUST_NOT_MATCH` **only** — the lists, not the patterns — leaves
both suites fully green (`ok`; `60 passed`). Neither file asserts its own list
length, and nothing cross-checks the counts.

It fails safe in the narrow sense — coverage shrinks, no wrong behaviour is
blessed — but the plausible bad repair is exactly this: a coupling test fails
naming U+2007, and the lazy fix is to delete U+2007 from that file's list
rather than repair the pattern. The guards would then have genuinely drifted
with **no test failing anywhere**. One line per list closes it —
`if len(whitespaceClassMustMatch) != 25 { t.Fatalf(...) }` and the vitest
equivalent — and `#0187`'s matrix in this very file already carries exactly
that meta-assertion on its case count, so the pattern is established here.
Hardening, not a defect in what was asked for; all six criteria are met
without it.
