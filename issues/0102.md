# 0102 — The SNS redirect-refusal test passes even when the redirect guard is deleted

| | |
|---|---|
| **Status** | open |
| **Module** | sesnotify |
| **Platform** | All |
| **Phase** | 4 — Unsubscribe and list hygiene |
| **First seen** | 2026-08-20 |

## Description

`TestFetchCertReal_RefusesRedirect` in `internal/sesnotify/verify_test.go`
asserts only that `fetchCertReal` returns *a* non-nil error when pointed at a
302. It passes whether or not the redirect was followed, so it does not guard
the property it is named for. The production guard added in `fc801c1` is
correct — this is a test defect, not a code defect.

## Steps to reproduce

1. Delete the `CheckRedirect` field from the `http.Client` literal in
   `NewVerifier` (`internal/sesnotify/verify.go`).
2. `go test ./internal/sesnotify/... -run TestFetchCertReal_RefusesRedirect -count=1`
3. The test still passes.

## Expected behavior

Removing the redirect guard fails the test.

## Actual behavior

With `CheckRedirect` gone, `Do` follows the 302 to the test's `final` server,
which answers `200` with the body `should never be reached`. The
`resp.StatusCode != http.StatusOK` check is therefore satisfied, so the fetch
proceeds to `pem.Decode`, finds no PEM block, and returns
`no PEM block found in certificate response`. The test's only assertion is
`err == nil` → fatal, so a non-nil error of *any* kind satisfies it. Confirmed
by running the mutation standalone outside the repo.

The guard is load-bearing for the same reason `validateCertURL` is: the host
allowlist constrains the *initial* URL only, so a redirect away from the pinned
`sns.<region>.amazonaws.com` host is the one remaining way the certificate
fetch could be steered at an internal address. `#0037`'s plan §3 calls it out
as "a second SSRF vector" and §10.5 asks for exactly this test.

## Notes

Two ways to make the test real; either is fine:

- Have the `final` handler increment a counter (or call `t.Error` when hit) and
  assert it was never reached. This is the same fetcher-was-never-invoked idiom
  `TestVerify_HostileSigningCertURL` already uses successfully, and is the more
  direct statement of the property.
- Assert the error specifically identifies the redirect status (`302`) rather
  than accepting any error.

Serve a valid PEM from `final` while you are at it, so the test cannot pass by
accident on a body-parsing failure again.

`fetchCertReal` carries a comment, and `#0037`'s `## Gotchas` an entry, noting
that `http.ErrUseLastResponse` makes `Do` return the redirect *response* rather
than an error — the status check is what refuses it. That reasoning is correct
and should stay; it is precisely why asserting "some error occurred" is too
weak here.
