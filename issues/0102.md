## Description

`TestFetchCertReal_RefusesRedirect` in `internal/sesnotify/verify_test.go`
asserts only that `fetchCertReal` returns *a* non-nil error when pointed at a
302. It passes whether or not the redirect was followed, so it does not guard
the property it is named for. The production guard added in `fc801c1` is
correct — this is a test defect, not a code defect.

## Root cause

The test's only assertion was `err == nil` → `t.Fatal`. With the
`CheckRedirect` guard intact, `fetchCertReal` refuses the redirect and returns
a non-nil "unexpected status 302" error, satisfying the assertion. But with
the guard *deleted*, `http.Client.Do` transparently follows the 302 to the
test's `final` server, which answered `200` with the plain-text body `should
never be reached` — not valid PEM. `pem.Decode` then failed and returned a
*different* non-nil error ("no PEM block found in certificate response"),
which the assertion accepted just as readily. The test could not distinguish
"the guard refused the redirect" from "the guard was gone and something else
downstream happened to fail."

## Fix

Took the first of the two approaches the issue names (the fetcher-was-never-
invoked idiom), and layered in the second concern (serve a valid PEM) as the
issue's Notes also asked:

- `final`'s handler now serves a real PEM (encoded from the test fixture
  certificate already generated by `testFixture`) instead of an arbitrary
  string, and increments an `int32` hit counter (via `sync/atomic`, since the
  handler runs on the httptest server's own goroutine) each time it is
  reached.
- The test now asserts, in addition to the existing `err == nil` check, that
  the hit counter is `0` after `fetchCertReal` returns — i.e., the redirect
  target must never be reached at all, regardless of what it would have
  returned. This is the same idiom `TestVerify_HostileSigningCertURL` already
  uses (asserting `calls == 0` on the fetcher seam).
- Left `fetchCertReal`'s and `NewVerifier`'s existing comments about
  `http.ErrUseLastResponse` unchanged — production code in `verify.go` was not
  touched, only `verify_test.go`.

Did not additionally assert the error text names status `302` specifically;
the hit-counter check is the more direct statement of the property and makes
a status-string assertion redundant.

## Steps to reproduce

1. Delete the `CheckRedirect` field from the `http.Client` literal in
   `NewVerifier` (`internal/sesnotify/verify.go`).
2. `go test ./internal/sesnotify/... -run TestFetchCertReal_RefusesRedirect -count=1`
3. The test still passes.

## Expected behavior

Removing the redirect guard fails the test.

## Actual behavior

With `CheckRedirect` gone, `Do` follows the 302 to the test's `final` server,
which answers `200` with the body `should never be reached`. The
`resp.StatusCode != http.StatusOK` check is therefore satisfied, so the fetch
proceeds to `pem.Decode`, finds no PEM block, and returns
`no PEM block found in certificate response`. The test's only assertion is
`err == nil` → fatal, so a non-nil error of *any* kind satisfies it. Confirmed
by running the mutation standalone outside the repo.

## Files changed

- `internal/sesnotify/verify_test.go` — `TestFetchCertReal_RefusesRedirect`
  now serves a valid PEM from `final` and asserts (via an `int32` hit counter)
  that `final` is never reached, rather than accepting any non-nil error;

  `internal/sesnotify/verify.go` (production code) is unchanged — confirmed by
  `git diff` after the mutation-and-restore cycle above.

The guard is load-bearing for the same reason `validateCertURL` is: the host
allowlist constrains the *initial* URL only, so a redirect away from the pinned
`sns.<region>.amazonaws.com` host is the one remaining way the certificate
fetch could be steered at an internal address. `#0037`'s plan §3 calls it out
as "a second SSRF vector" and §10.5 asks for exactly this test.

## Notes

Two ways to make the test real; either is fine:

- Have the `final` handler increment a counter (or call `t.Error` when hit) and
  assert it was never reached. This is the same fetcher-was-never-invoked idiom
  `TestVerify_HostileSigningCertURL` already uses successfully, and is the more
  direct statement of the property.
- Assert the error specifically identifies the redirect status (`302`) rather
  than accepting any error.

Serve a valid PEM from `final` while you are at it, so the test cannot pass by
accident on a body-parsing failure again.

`fetchCertReal` carries a comment, and `#0037`'s `## Gotchas` an entry, noting
that `http.ErrUseLastResponse` makes `Do` return the redirect *response* rather
than an error — the status check is what refuses it. That reasoning is correct
and should stay; it is precisely why asserting "some error occurred" is too
weak here.
