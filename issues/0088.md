## Description

`#0026` moved the SES call off the request goroutine, which collapsed an 80 ms timing channel and dropped a two-probe attack from 120/120 to chance. Its review disclosed a residual — a brand-new address still does a synchronous `INSERT` — and characterised it as "much weaker", mitigated because probing creates the row so an attacker gets one clean observation per target.

**Measured directly, that residual is not weaker in kind. It is total.** `#0029`'s reviewer produced four **non-overlapping** clusters against the shipped build, each request in its own rate-limit bucket so the shipped limiter was measured unmodified:

| Branch | min (ms) | median | max |
|---|---|---|---|
| honeypot filled | 0.27 | **0.30** | 0.45 |
| already active | 0.58 | **0.63** | 1.02 |
| pending (resend) | 0.76 | **0.84** | 5.07 |
| brand new | 1.51 | **1.67** | 3.68 |

The **fastest** brand-new sample (1.51 ms) is slower than the **slowest** already-active one (1.02 ms). `P(active > new) = 0.000` over 50 paired samples.

So a **single observation** classifies membership with 100% accuracy — which is exactly the one-observation case the earlier mitigation relied on. The magnitude shrank by ~50×; the separability did not.

It also leaks the honeypot: a bot learns from response time alone that its fill was detected, which is the one thing a honeypot must never reveal.

## Why this matters despite the small numbers

`CLAUDE.md` §9 makes the uniform `202` non-negotiable because varying the response turns this endpoint into an email-enumeration oracle. Everything *readable* is now byte-identical — status, `Content-Type`, `Content-Length`, body — verified across 160 samples. Elapsed time is the one channel left, and it is fully diagnostic.

Two things bound the damage today: `#0077` fixed `X-Forwarded-For` so the per-IP limiter (5/min, burst 3) actually works, and sub-millisecond gaps are harder to resolve across a WAN than the 79 ms gap `#0026` closed. Neither makes it not an oracle — they make it slower to exploit.

## Where it lives

`internal/handlers/subscribe.go` — `#0026`'s file, **not** `#0029`'s frontend. The form is clean: it reads the response body exactly once as an ignored argument, navigates to a fixed route with static copy, and has no client-side timing branches. It cannot amplify or fix this.

Consider equalising work (every branch performing the same query count), or a constant-time floor on the handler, or moving the remaining synchronous writes off the request path as `#0026` did for the send. **Weigh the options and justify the choice** — a sleep-to-pad has real cost under load and its own failure modes

## Notes

Take the earlier "one clean observation per target" mitigation as **refuted**, not merely qualified — one observation is all this needs.

`#0081` and `#0087` are next door in the same file; coordinate rather than colliding.

A test that asserts timing directly will be flaky (`#0084` exists because of load-sensitive tests). Prefer a structural assertion — equal query counts per branch, say — with the distribution measurement recorded in `## Verification` as evidence rather than as a gate.
