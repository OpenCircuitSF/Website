## Description

`#0026` moved the SES call off the request goroutine, which collapsed an 80 ms timing channel and dropped a two-probe attack from 120/120 to chance. Its review disclosed a residual — a brand-new address still does a synchronous `INSERT` — and characterised it as "much weaker", mitigated because probing creates the row so an attacker gets one clean observation per target.

**Measured directly, that residual is not weaker in kind. It is total.** `#0029`'s reviewer produced four **non-overlapping** clusters against the shipped build, each request in its own rate-limit bucket so the shipped limiter was measured unmodified:

| Branch | min (ms) | median | max |
|---|---|---|---|
| honeypot filled | 0.27 | **0.30** | 0.45 |
| already active | 0.58 | **0.63** | 1.02 |
| pending (resend) | 0.76 | **0.84** | 5.07 |
| brand new | 1.51 | **1.67** | 3.68 |

The **fastest** brand-new sample (1.51 ms) is slower than the **slowest** already-active one (1.02 ms). `P(active > new) = 0.000` over 50 paired samples.

So a **single observation** classifies membership with 100% accuracy — which is exactly the one-observation case the earlier mitigation relied on. The magnitude shrank by ~50×; the separability did not.

It also leaks the honeypot: a bot learns from response time alone that its fill was detected, which is the one thing a honeypot must never reveal.

## Why this matters despite the small numbers

`CLAUDE.md` §9 makes the uniform `202` non-negotiable because varying the response turns this endpoint into an email-enumeration oracle. Everything *readable* is now byte-identical — status, `Content-Type`, `Content-Length`, body — verified across 160 samples. Elapsed time is the one channel left, and it is fully diagnostic.

Two things bound the damage today: `#0077` fixed `X-Forwarded-For` so the per-IP limiter (5/min, burst 3) actually works, and sub-millisecond gaps are harder to resolve across a WAN than the 79 ms gap `#0026` closed. Neither makes it not an oracle — they make it slower to exploit.

## Where it lives

`internal/handlers/subscribe.go` — `#0026`'s file, **not** `#0029`'s frontend. The form is clean: it reads the response body exactly once as an ignored argument, navigates to a fixed route with static copy, and has no client-side timing branches. It cannot amplify or fix this.

## Notes

`#0081` and `#0087` are next door in the same file; coordinate rather than colliding.

A test that asserts timing directly will be flaky (`#0084` exists because of load-sensitive tests). Prefer a structural assertion — equal query counts per branch, say — with the distribution measurement recorded in `## Verification` as evidence rather than as a gate.

## The mechanism chosen

Neither option offered alone was sufficient, so the fix combines both:

1. **Equalize the fixed reads.** Every accepted request — honeypot-caught,
   timing-gate-failed, or human — now performs exactly the same two
   synchronous store calls, always, in the same order: one
   `SuppressionChecker.IsSuppressed` and one `subscriberStore.FindByEmail`.
   The honeypot and timing-gate checks no longer short-circuit before these
   reads; they only change what happens afterward.
2. **Defer everything branch-dependent.** `Create`, `RestartSignup`,
   `SetInterests`, `ClaimConfirmationSend`/`ClaimAlreadySubscribedSend`, the
   mail enqueue, and the audit record all move onto a new async queue
   (`mutateQueue`, a second worker pool mirroring `#0026`'s `sendQueue`),
   drained after the response is already written. `Subscribe`'s entire
   request-path cost is now: decode, two fixed reads, one interest-slug
   resolution (attacker-controlled, not account-state-dependent), and a
   channel send.

Rejected: a **sleep-to-pad constant-time floor**. It adds real,
unconditional latency to every legitimate signup forever (not just the
currently-slow branches), has to be re-tuned by hand whenever the slowest
branch's own cost drifts, and is actively worse under load — it ties up a
response goroutine for the padding duration on every request, so concurrent
in-flight goroutines scale directly with traffic instead of draining as
fast as the backend allows. Equalizing work *alone*, without deferring the
writes, was also rejected as insufficient: it does nothing to shrink the
request-path cost itself, only to keep it equal, so a slow branch is still
felt by every branch.

Cost: a client that receives the `202` has even less signal than before
about whether its specific request was actually acted on (queue-full or
in-flight-at-shutdown drops are already unobservable, per `#0026`/`#0081`
design). This isn't a new promise being broken — the endpoint never
guaranteed synchronous action — but it's worth naming as what was given up.
See `subscribe.go`'s package doc comment ("The elapsed-time channel —
`#0088`") for the full writeup, including the concurrency-safety argument
for closing two queues instead of one in `Close`.

### `#0081`'s defect is not reintroduced one queue over — proven

This was the sharpest question against this change, and the answer is clean.

`mutateQueue` has a real shutdown path and is wired into the same budget:

- `Close` closes **both** channels under the same `closeMu`/`closed` guard, and
  cancels the shared `sendCtx` that `processMutateJob` derives from, so a job
  that is queued-but-not-started or in flight is interrupted rather than run
  out.
- Both WaitGroups are waited in the **`mutateWG`-before-`sendWG`** order, which
  is required rather than incidental: a mutate worker calls `enqueueSend`
  (`sendWG.Add(1)`) strictly before its own `mutateWG.Done()` fires, so waiting
  the other way could observe `sendWG` at zero before a still-running mutate
  job had queued its send. `waitForSends` uses the same order for the same
  reason. Both are correct.
- `enqueueMutation` mirrors `enqueueSend`'s hard-won happens-before shape
  exactly — `Add(1)` only inside the branch that observed `closed == false`
  while holding `closeMu`, never before the check — so the `WaitGroup` misuse
  `#0081`'s review reproduced at ~5,000 rounds cannot recur here.
- `cmd/opencircuit/main.go:724` calls `subscribeH.Close(closeCtx)` on its own
  `subscribeCloseTimeout`, independent of `shutdownServerTimeout` — i.e. the
  new queue rides `#0087`'s split budget automatically, with no change needed.
  `go test ./cmd/opencircuit/ -run Shutdown` passes (11.79s).

And the guard is real, which I proved rather than assumed. Deleting
`close(h.mutateQueue)` from `Close`:

```
=== RUN   TestNewSubscribeHandler_NoGoroutineLeakAcrossConstruction
    subscribe_test.go:1309: goroutines before=3 after=203 across 50 constructions (each starting 4 workers, 200 total if leaked)
    subscribe_test.go:1312: goroutine count grew from 3 to 203 ... workers are leaking
--- FAIL
```

`#0081`'s leak test covers the second pool for free because it counts *all*
goroutines. Unmutated it reports `before=3 after=3`. **The defect was not
reintroduced.** (Minor: the failure message now names only `sendWorkerCount`,
which is no longer the whole story — worth a word change, not a bounce.)

Behaviour at shutdown is a deliberate narrowing rather than a leak: a queued
mutation is *cancelled*, not completed, when `sendCancel` fires. Unlike a
dropped send there is nothing to compensate — no claim has been taken yet — the
drop is logged, and the visitor's retry works immediately. Same for
`enqueueMutation`'s queue-full path. `#0026`'s uniform `202` does not become a
new kind of lie: it never promised synchronous action, both drop paths log, and
the failure mode (nothing happened, retry works) is strictly more recoverable
than the send-queue drop this project already accepted.

### Ordering — no new race class

Two requests for the same address were already concurrent before this change
(two request goroutines); they are now concurrent on four workers instead. The
races that existed are covered as before: `Create`'s `ErrEmailExists`,
`RestartSignup`'s `statusLockedFromNonAdmin` re-check, and the two atomic
`Claim*` calls. The pre-existing double-`RestartSignup` hazard (the second
restart re-issuing a token that invalidates the first, already-claimed email's
link) is unchanged in kind and marginally wider in window — worth its own issue
eventually, **not** a bounce reason and not introduced here.

Nothing relies on `Create` having happened when the handler returns, tests
included: `doSubscribeFrom` calls `h.waitForSends()`, which now waits both
WaitGroups in the correct order. `TestSubscribe_*`, `TestNewSubscribeHandler_*`,
`TestPassesTimingGate`, `TestValidEmailSyntax`, `TestIsDisposableDomain` all
pass (24.8s, zero skips, zero failures).

### Why this bounces: the deferral half has no regression guard at all

The gate asserts `IsSuppressed == 1` and `FindByEmail == 1` per branch, and
that a mutation call happens only for branches that need one. It says nothing
about **when** any of it runs — the counters are snapshotted after
`waitForSends()` has already drained the queue, so an async call and a
synchronous one are indistinguishable to it.

That matters because the deferral is the half that closed the actual oracle.
The short-circuit produced the honeypot's 0.017 ms outlier; the *write
asymmetry* (`Create` + `SetInterests` + `Claim*` + audit versus one `Claim*`
versus nothing) is what produced `P(active > new) = 0.000` and the three
non-overlapping member clusters this issue is named after.

I reverted that half in full — `Subscribe` calls `processMutateJob`
synchronously on the request goroutine instead of `enqueueMutation`, with every
per-branch store-call count left exactly as it is today:

```go
func (h *SubscribeHandler) runMutationSynchronously(job mutateJob) {
	h.closeMu.Lock()
	if h.closed { h.closeMu.Unlock(); return }
	h.mutateWG.Add(1)
	h.closeMu.Unlock()
	h.processMutateJob(job)   // Create/RestartSignup/SetInterests/Claim*/audit, all on the request goroutine
}
```

Result:

```
$ go vet ./internal/handlers/          # clean
$ go test ./internal/handlers/ -count=1 -run 'TestSubscribe|TestNewSubscribeHandler|TestPassesTimingGate'
ok  	github.com/brennanMKE/OpenCircuitSF/internal/handlers	28.952s
```

**Green.** Including `TestSubscribe_SyncQueryCountEqualAcrossBranches` and
`TestSubscribe_AsyncSendDoesNotBlockResponse` — the latter still passes because
`enqueueSend` is untouched, so it guards `#0026`'s channel and not `#0088`'s.
That is a complete reversion of this issue's fix with nothing to catch it.

The gate's own doc comment claims otherwise, in as many words: *"with all of
the calls that legitimately differ by branch … deferred onto the async mutation
queue `#0088` added, so they can never contribute to request-path latency."*
The assertions underneath it do not check that. This project has just spent
three passes on `#0090` over a test whose stated purpose outran what it
asserted; the same shape, one file over, is what this bounces on — and the

### The fix — small, and the pattern already exists in this file

Add a deterministic deferral test modelled on
`TestSubscribe_AsyncSendDoesNotBlockResponse`, which already solves exactly
this problem for the send queue: wrap the store so `Create` (and ideally
`RestartSignup`) blocks on a test-controlled channel, serve one new-signup
request on its own goroutine, and assert `ServeHTTP` returns well inside a
short bound while `Create` is still blocked — then confirm `Create` was
actually entered, so a fast response is not vacuously fast. Release, then
`waitForSends()` and clean up. Under the mutation above the response cannot
return, so the test fails; under the shipped code it returns immediately.

Prefer that over snapshotting the counters before `waitForSends()`: the
counters can be incremented by a worker concurrently with the response being
written, so a pre-drain snapshot is inherently racy. The blocking-store shape is
deterministic and is the convention this file already established.

While there: correct
`TestNewSubscribeHandler_NoGoroutineLeakAcrossConstruction`'s failure message to
name both pools (it now covers `mutateWorkerCount` too — verified above), and
soften the gate's doc comment so it claims only what it asserts.

### On the measured distributions — the conclusion is supportable, with a caveat worth recording

Interleaved paired sampling is the right instrument here and I accept it: it
cancels the drift and the multi-second contention spikes that make the absolute
medians (0.52–0.77 ms, maxima 142–324 ms) worthless against this issue's
quiet-box table. The sign statistic `P(X > Y)` is robust to exactly that.

The five reported values (0.440–0.560) are all within about one standard error
of chance — with `n = 50`, `SE ≈ 0.071` — so the pre-fix effect
(`P(active > new) = 0.000`, or 0.075 in the implementer's own reproduction) is
excluded decisively. What `n = 50` does **not** have is the power to exclude a
*small* residual: it could not reliably distinguish 0.50 from about 0.62. So the
right claim is "the measured oracle is closed", not "no residual exists at any
magnitude".

I do not think a quiet-box re-measurement should gate this. The load-bearing
evidence is structural, and I verified it by reading rather than timing: the
request path is branch-independent by construction. The one residual it cannot
remove is inside `FindByEmail` itself — a row-hit and a row-miss are not
identical work in Postgres — which no design short of a constant-time store
addresses, and which is orders of magnitude below what this issue measured.
Worth a sentence in `## Verification` acknowledging the power limit rather than
another sampling run.

### Not held against this fix

- The `#0084` `truncate tables: timeout: context deadline exceeded` failures in
  unrelated packages under load — per the coordinator, and consistent with the
  evidence already recorded in `issues/0084.md`.
- Bot traffic now consuming `mutateQueue` slots (every accepted request
  enqueues, honeypot included). A bot job returns from `processMutateJob`
  immediately, so it holds a worker for microseconds; `mutateQueueCapacity`'s
  doc comment already names and reasons about this. Considered, correct.
- Second-order back-pressure: branches with more async work occupy workers
  longer, so under sustained load queue depth and DB-pool contention could in
  principle couple back into the synchronous reads. Aggregate rather than
  per-request, and it requires an attacker who can already drive the box.
  Noting it so it is not re-derived, not asking for a change.
