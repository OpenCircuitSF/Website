## Description

`CampaignStore.Create` mints a slug by lowercasing the **subject** and replacing
every non-alphanumeric run with a hyphen (`slugifyCampaign`), falling back to
`campaign` when that leaves nothing.

So the archive URL is whatever the subject happens to be. The user's first real
newsletter, subject *"Open Circuits SF: September 2026"*, would yield
`open-circuits-sf-september-2026`.

## The decision — made by the user, not open for re-litigation

**The default newsletter slug is `MM-YYYY`.** September 2026 is `09-2026`, giving
`/archive/09-2026`. The user's words: *"It can be short and specific."*

Zero-padded two-digit month, hyphen, four-digit year. Implement that; do not
substitute a variant you prefer.

One consideration recorded rather than raised again: a date-only slug carries no
keywords, so **search discovery rests on the archive index page, the sitemap, and
each entry's title and heading — not on the slug.** All three of those already
exist and already carry the subject, so the trade-off is already covered.

### What is already in place, and is NOT part of this issue

Verified against the code, so the work here stays narrow:

- **Collision handling is done and is robust.** Create uniquifies with a numeric
  suffix (`-2`, `-3`, …), and each candidate is a **real INSERT** fought out
  against the `UNIQUE(slug)` constraint inside its own savepoint — never a
  check-then-insert race, so two concurrent Creates cannot both win a slug.
- **Overrides are done.** `PATCH` accepts a `slug`, rejecting a taken one and
  refusing edits once the campaign is no longer editable. This is how an
  exception to the template is expressed.
- **Minting happens at draft time, not send time** — PRD §6.8 calls this
  load-bearing, because promotion has to be written against a URL that already
  exists.
- **The archive index, its footer link, and sitemap coverage all exist** — see
  the note at the end of this issue.

## The questions still to settle

1. **Which campaigns get the template?** Not every campaign is a monthly
   newsletter — a workshop announcement slugged `09-2026` would be actively
   wrong, and would also consume that month's slug so the real newsletter falls
   back to `09-2026-2`. **That failure is silent and permanent once sent**, so
   this is the question that matters most. Decide whether the template is
   unconditional, opt-in, or inferred from campaign kind, and say how an author
   chooses.
2. **Where does the month come from?** Creation time is the obvious source, but a
   newsletter drafted on 31 August for September would be misnamed `08-2026`.
   Consider letting the author supply it, defaulting to now.
3. **Second newsletter in one month.** The existing suffix yields `09-2026-2`.
   Confirm that is acceptable rather than an error worth surfacing to the author.
4. **Configurable or constant?** The project has a settings table, but this is a
   one-organisation site. A constant is likely right; argue whichever you choose.

### 1. Question 1 — which campaigns get the template

**Answer: opt-in, chosen per campaign at compose time. Never inferred, never
unconditional.**

#### What actually distinguishes a newsletter in the schema: nothing

There is no `kind`, `type`, or `is_newsletter` column, and PRD §6.8 defines
none. The three columns that could plausibly stand in for one were each
checked against the real call sites, and all three fail:

| Candidate rule | Why it fails |
|---|---|
| `workshop_id IS NULL` → newsletter | Sound in one direction only. `workshop_id IS NOT NULL` really does mean "workshop announcement" (only the announce shortcut ever sets it). But `workshop_id IS NULL` covers **every hand-composed campaign** — the September newsletter *and* a one-off "the space is closed this weekend" note. Those are exactly the two things that must not share a slug rule |
| `audience_mode = 'all'` → newsletter | Measured, and it is unconditional in disguise. The SPA's "New campaign" modal sends `audience_mode: 'all'` for **every** draft it creates, and the announce shortcut *also* falls back to `'all'` whenever the workshop carries no interests. So this rule would hand the month's slug to a workshop announcement on the most ordinary path there is |
| Subject or name matching (`/newsletter/i`, a month name) | Guessing at prose. Silent when it guesses wrong, in both directions, and it makes a URL depend on wording the author is free to edit |

#### Why unconditional is worse than it looks

It is not merely that an announcement would take `09-2026`. If **every**
campaign uses the month, then every campaign in a month collides, and the
archive fills with `09-2026`, `09-2026-2`, `09-2026-3` — slugs that identify
nothing and cannot be told apart. The template only carries meaning while it
is scarce.

#### Why opt-in is the right shape, in one sentence

Opt-in is the only option whose failure mode is **loud and reversible**:
forget to tick the box and you get `open-circuits-sf-september-2026`, visible
in the editor immediately, fixable by `PATCH` while the campaign is still a
draft. Inference fails the other way — silently, and permanently once sent,
which is the exact failure this issue exists to prevent.

#### How an author chooses

One optional field on the create path, carrying the opt-in **and** the month
together, so there is no invalid combination to validate:

- **API:** `POST /admin/campaigns` gains one optional body field,
  `"newsletter_month": "2026-09"`. Absent → today's behaviour exactly
  (subject-derived). Present → `MM-YYYY`.
- **Admin UI:** the "New campaign" modal in `web/src/views/admin/Campaigns.svelte`
  gains a checkbox — *"Monthly newsletter (archive URL is MM-YYYY)"* — and,
  shown only when it is ticked, a native `<input type="month">` defaulted to
  the current month. `type="month"`'s value is literally `YYYY-MM`, so the
  client sends the field verbatim with no formatting logic of its own (§5
  explains why keeping the format knowledge server-side matters).
- **Announce shortcut:** excluded **by construction** — it builds its own
  `CampaignInput` and simply never sets the field. §7 pins that with a
  behavioural test rather than leaving it to inspection.

Rejected, deliberately: a separate boolean plus a separate month (two fields,
one invalid state — `newsletter: false` with a month set — for no gain), and
adding `newsletter_month` to `PATCH` (after creation the slug already exists
and `slug` is the override; two ways to set one thing is how they drift).

### 2. Question 2 — where the month comes from

**Answer: the author supplies it explicitly; the compose form defaults the
input to the current month. `CampaignStore.Create` never reads a clock.**

Three reasons, in order:

1. **It fixes the bug the question names.** A newsletter drafted 31 August for
   September is the *normal* case, not an edge case, and any server-side
   `time.Now()` default gets it wrong with no way for the author to see or
   correct it before the slug is permanent.
2. **It keeps `Create` clock-free.** `Create` today has no time dependency at
   all — `created_at` is a column default. Introducing `time.Now()` would
   mean either injecting a clock seam for tests or writing tests that are
   correct only until a month boundary. Neither is worth it when the caller
   already knows the answer.
3. **The added UI surface is one checkbox and one native input**, and the
   default is computed where the author can see and change it. `<input
   type="month">` is a real browser control with a month picker; nothing has
   to be invented.

The one cost — a non-browser caller (curl) must spell the month out — is
acceptable and arguably correct: an API client asserting "this is the
September newsletter" should say September.

### 3. Question 3 — a second newsletter in one month

**Answer: `09-2026-2` is the right outcome, and the collision algorithm must
not change. But the likely trigger is not two newsletters.**

Confirmed as desired, on three grounds: the suffix is unique, permanent and
honest; a genuine second newsletter in one month is rare under a monthly
cadence; and turning a collision into an error is not available anyway —
acceptance criterion 4 pins the savepoint-based `UNIQUE` contention, and any
"refuse if taken" behaviour is precisely the pre-check that criterion forbids.

**The real hazard is different and worth stating plainly.** Two measurements
combine badly:

- there is **no `DELETE /admin/campaigns/{id}`**, so a draft created by
  mistake exists forever; and
- the slug override has **no admin UI**.

So an author who clicks "New campaign" twice with the newsletter box ticked
permanently parks `09-2026` on a stray draft, and the real newsletter becomes
`09-2026-2` — with no way to repair it from the console. That is a genuine
trap, but it is a *reachability* gap in the override, not a defect in the
minting rule, and the fix is a slug field in `CampaignEditor.svelte`. Reported
in §10 rather than built here, so this issue stays narrow.

Nothing else is needed to surface the collision: `CampaignEditor.svelte`
already displays the full archive URL as a copyable field the moment the draft
is created, so an author who ends up with `09-2026-2` sees it immediately.

### 4. Question 4 — constant, not a setting

**Answer: an unexported format constant in `internal/mailing`.**

For the setting: the `settings` table exists and is already used for
operator-tunable numbers.

Against, and it decides it:

1. **Every existing `settings` row is something the send worker reads at
   runtime and an operator legitimately tunes** — send rate, soft-bounce
   thresholds, the physical postal address, queue retry limits. A URL format
   is not operational tuning; it is a published contract.
2. **A settings row invites a false expectation.** Changing it would not — and
   must not — alter slugs already minted, so the setting would silently mean
   "the format for campaigns created from now on". A constant carries no such
   implication.
3. **The real cost is not the constant.** A settings key needs a seeding
   migration (the `000008` pattern: the row must exist before `PATCH
   /admin/settings` can touch it), validation on the patch path, and a UI —
   for one organisation with one cadence and no second format in prospect.
4. **Per-campaign deviation is already expressible**, via the `slug` override.
   That is the right granularity for an exception; a global format switch is
   not.

Concretely: `const newsletterSlugFormat = "%02d-%04d"` in `internal/mailing`,
with a doc comment recording that it is `#0405`'s user-made decision and that
changing it does not retroactively change minted slugs.

### 5. The change, precisely

Four files, plus tests.

**`internal/mailing/campaigns.go`** — `CampaignInput` gains one field:

    // NewsletterMonth opts this campaign into #0405's MM-YYYY archive-slug
    // template ... nil (the default) leaves slug minting exactly as it was:
    // slugifyCampaign(Subject).
    NewsletterMonth *NewsletterMonth

and `Create`'s single existing line

    base := slugifyCampaign(in.Subject)

becomes

    base := slugifyCampaign(in.Subject)
    if in.NewsletterMonth != nil {
        if !in.NewsletterMonth.valid() {
            return Campaign{}, ErrInvalidNewsletterMonth
        }
        base = in.NewsletterMonth.Slug()
    }

**That is the whole store change.** Everything downstream of `base` — the
savepoint-per-candidate loop, the `-2`/`-3` suffix, the `UNIQUE` contention,
the `INSERT`, `maxSlugAttempts` — is untouched, so the template inherits
collision handling rather than reimplementing it.

**The fallback when the template does not apply is the current behaviour,
unchanged**, including `slugifyCampaign`'s `"campaign"` result for a subject
that is empty or entirely punctuation. That is what lets
`TestCampaignStore_Create_MintsSlugFromSubject`,
`TestCampaignStore_Create_UniquifiesSlugOnCollision` and
`TestCampaignStore_Create_EmptySubjectFallsBackToPlaceholderSlug` pass
**byte-for-byte unmodified** (criterion 4).

**`internal/mailing/newsletter_month.go`** (new, small):

    type NewsletterMonth struct { year int; month time.Month }   // fields unexported
    func ParseNewsletterMonth(s string) (NewsletterMonth, error) // "YYYY-MM"
    func (m NewsletterMonth) Slug() string                       // "MM-YYYY"

plus `ErrInvalidNewsletterMonth`. Unexported fields mean the only way to build
a valid value outside the package is `ParseNewsletterMonth`, so the range rule
lives in exactly one place; `Create`'s `valid()` check above is the
belt-and-braces backstop for a caller that constructs a zero value anyway —
the same shape `normalizeAudience` already uses behind the database's CHECK.

**The wire format is `YYYY-MM` and the slug is `MM-YYYY`, deliberately
inverted, and the inversion is safe rather than a footgun.** `YYYY-MM` is what
`<input type="month">` produces; `MM-YYYY` is what the user decided the URL
should read. Because the accepted pattern anchors four digits first
(`^\d{4}-(0[1-9]|1[0-2])$`), a transposed `"09-2026"` cannot parse as anything
— it is rejected outright, never silently misread. §7 pins that property.

**`internal/handlers/admin_campaigns.go`** — `createCampaignRequest` gains
a `NewsletterMonth *string` field tagged `json:"newsletter_month,omitempty"`; when non-nil
it is trimmed and passed to `mailing.ParseNewsletterMonth`, with a parse
failure answered `400` ("newsletter_month must be YYYY-MM"). `PATCH` is
untouched. The audit metadata written on create is untouched too — no new key,
so `internal/handlers`' audit-metadata guard is not in play.

**`web/`** — `CampaignDraftFields` (`web/src/lib/types.ts`) gains
`newsletter_month?: string`; `web/src/lib/campaigns.ts` gains a pure
`currentMonthValue(now: Date): string` helper returning `YYYY-MM` from local
calendar fields; `web/src/views/admin/Campaigns.svelte`'s modal gains the
checkbox and the month input.

**The client deliberately does not format the slug.** It was tempting to
preview `/archive/09-2026` in the modal, but that would put the `MM-YYYY`
ordering in two languages and create a drift surface the repo would then need
a parity guard for (the `campaign_progress_parity_test.go` /
`routes_parity_test.go` pattern). Instead the modal's help text names the
shape in prose only, and the **real** URL appears in `CampaignEditor.svelte`'s
existing copyable field the instant the draft is created, straight from the
server's response. One formatter, one source of truth.

### 6. The existing production row — nothing re-derives it

**Explicitly: nothing in this change reads, re-derives, or overwrites an
existing `email_campaigns.slug`.** The only code path touched is the value of
`base` inside `Create`, which runs only on `INSERT`. `Update` is not touched;
`GetBySlug`, `ListArchived` and `SetArchiveStatus` are not touched.

So production's id 1 keeps the `'09-2026'` that `#0404`'s migration backfills,
and it keeps it for the same reason it has it: because a migration wrote a
literal, not because a rule recomputes it. `#0405` and `#0404` agree by
construction rather than by coincidence.

Two things the implementer must therefore **not** do, stated so a reviewer can
check them mechanically:

- do not add any backfill, re-mint, or "fix up existing slugs" step; and
- do not let the literal `09-2026` appear anywhere under `internal/` or
  `web/src/` — it belongs to `migrations/000025` and to issue prose. Tests use
  a distinct far-future month (§7) so a test can never contend with it.

### 7. Test design

### 9. Migration: none

**No migration is needed, and none should be written.** The month is an *input
to minting*, not durable state: nothing new is persisted, because the only
output — the slug — is already a column. `PRD` §6.2's `email_campaigns`
listing is therefore unchanged, and `prd_index_parity_test.go` (which matches
column names per table) has nothing to see.

1. **The campaign slug override is unreachable from the admin console.**
   `PATCH /admin/campaigns/{id}` accepts `slug` and enforces every rule
   correctly, but no SPA view sends it: `CampaignDraftFields` has no slug
   field and `CampaignEditor.svelte` renders the archive URL read-only. So
   "the override is how an exception to the template is expressed" is true of
   the API and false of the product. Combined with (2) this is a real trap.
   Fix: an editable slug field in `CampaignEditor.svelte`, enabled only while
   `status == 'draft'`, mapping `409` to the existing messages.
2. **There is no way to delete a campaign draft.** No `DELETE
   /admin/campaigns/{id}` exists, so a draft created by mistake holds its slug
   forever. Harmless while slugs are subject-derived and disambiguated by
   wording; sharper once a slug is a scarce, meaningful `MM-YYYY`.
