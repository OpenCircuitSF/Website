## Description

`docs/media.md` (added 2026-09-04) documents the intended workflow: workshop
covers live on disk at `/var/www/media`, served by an Apache carve-out at
`/media/`, so adding a photo needs no rebuild and does not grow the binary.

**The repo has not caught up.** Four small things still point at the old
embedded path, and one of them will quietly cause the next workshop to repeat
the mistake.

### The old path, for context

Both live images sat in `web/public/`, which `npm run build` sweeps into
`web/dist/`, which `//go:embed all:dist` compiles **into the binary**. Confirmed:
`grep -c programming_leds /usr/local/bin/opencircuit` → 1. Apache's wildcard
proxied the request to the Go service, which served it from memory. Every image
cost a rebuild and permanent binary size — exactly what `/media/` exists to
avoid.

The user has since copied both to `/var/www/media` and verified
`/media/programming_leds.jpg` serves with the documented `max-age=604800` and
the sandboxing CSP.

## What needs doing

1. **The `.gitignore` rule is premised on the wrong location.** `/web/public/*.jpg`
   and `*.jpeg` were added on 2026-09-04 (`43f4ee4`) when workshop photos were
   thought to belong in `web/public/`. Under `docs/media.md` **nothing** belongs
   there — the directory holds 23 tracked design assets and nothing else. Remove
   the rule or replace it with a comment pointing at `docs/media.md`, so it stops
   silently permitting the old workflow.

2. **The admin editor gives no hint.** `WorkshopEditor.svelte`'s label reads
   *"Cover image (site-relative path)"*. Nothing tells an operator the path
   should start `/media/`. **This is the one that matters** — it is where the
   next workshop's path gets typed. A placeholder or hint naming the convention
   is enough; do not add validation, since `isSafeCoverImage` deliberately
   accepts any same-site path and `docs/media.md` explains why.

3. **`docs/media.md` says "The directory is currently empty (checked
   2026-09-04)."** No longer true. Update it, and consider whether that sentence
   should be dated-and-kept or simply corrected.

4. **`migrations/000020`'s `cover_image` comment says `-- path under /assets`.**
   Wrong twice: the path is under `/media`, and `/assets/` is Vite's embedded
   build output — `docs/media.md` explains that excluding `/assets/` from the
   proxy would cut the SPA off from its own JS. **`000020` is frozen** (§1 —
   applied to production long before the current bound), so **do not edit it**.
   Record the correction where a reader will meet it instead, and say where you
   chose and why.

- **Removing the two files from `/opt/opencircuit/web/public/` on the box.**

## Root cause

`docs/media.md` (added 2026-09-04) documented the new `/var/www/media` +
Apache-carve-out workflow, but the change landed as a doc-only addition: it
never propagated to the four other places in the repo that still encoded the
old, superseded assumption that a cover image is either embedded (`web/public/`
+ `//go:embed`) or under Vite's `/assets/` output. Nothing was broken by this —
`isSafeCoverImage` accepts any same-site path either way — but each of the four
either quietly permitted a repeat of the old workflow or actively pointed the
next operator at it.

## Fix

Four independent corrections, none touching `migrations/000020` (frozen,
`CLAUDE.md` §1):

1. **`.gitignore`** — replaced the `/web/public/*.jpg` and `*.jpeg` rules
   (added 2026-09-04 alongside `#0416`, premised on cover images belonging in
   `web/public/` but merely staying untracked) with a comment stating the
   corrected fact: nothing workshop-photo-related belongs in `web/public/` at
   all, tracked or ignored, and pointing at `docs/media.md`.
2. **`WorkshopEditor.svelte`** — the cover-image field already had a
   `cover-hint` paragraph, but its example was `"/assets/workshops/soldering.jpg"`
   — the stale, embedded-path convention, shown at exactly the point an
   operator types the next workshop's path. Changed the example to
   `"/media/soldering-101.jpg"` and reworded the sentence to say covers are
   placed directly on the server, not uploaded. Per the file's own existing
   rule (`#0172`, restated in the adjoining Svelte comment), the `docs/media.md`
   citation and the `#0432` note explaining the change stay in that comment,
   not in the rendered copy — confirmed by `web/src/lib/citationGuard.test.ts`,
   which fails on any admin-facing string that cites an internal doc.
3. **`docs/media.md`** — the "directory is currently empty (checked
   2026-09-04)" operational note was rewritten to state what is now true: the
   two live covers were copied over and verified serving with the documented
   headers, and `#0417`'s dimensions/EXIF work on those same two files remains
   open. Also updated its existing `000020` callout (which already recorded
   the frozen-migration hazard, added the same day) to point at where the
   correction actually landed — see next.
4. **`migrations/000020`'s `-- path under /assets` comment** — not editable.
   `internal/handlers/admin_workshops.go`'s `isSafeCoverImage` doc comment
   already quoted that exact string verbatim, to justify why the validator
   refuses any other-host URL ("PRD §6.2's own schema comment ... both say a
   cover image belongs on THIS site"). Added a paragraph immediately after
   that quote recording that the quoted text is wrong twice over — `/media`,
   not `/assets`; `/assets/` is Vite's own embedded build output, not a media
   location at all — and pointing at `docs/media.md` for the real convention.
   Chose this location over `docs/media.md` alone because it is the one place
   in the Go source that already repeats the wrong string, so a reader who
   goes looking for why that quote looks odd meets the correction immediately
   next to it; `docs/media.md`'s callout was updated to cross-reference it
   rather than duplicate the explanation.

**No client-side validation was added or changed.** `isSafeCoverImage`
(`internal/handlers/admin_workshops.go`) and its TypeScript twin
(`web/src/lib/workshopAdmin.ts`) are both untouched; the `/media/...` example
is only ever a hint string, never a pattern the validator checks against.

- **The citation guard is real and was respected, not worked around.**
  `web/src/lib/citationGuard.test.ts` fails on any string literal or rendered

### Findings, recorded rather than blocking

1. **The stale `/assets/workshops/soldering.jpg` example survives in the
   client-side validation error message**, in `web/src/lib/workshopAdmin.ts`'s
   `validateWorkshopForm`. That string reaches `saveError` and renders in this
   same editor as a `role="alert"` paragraph, roughly twenty lines below the
   hint this issue corrected. So an operator who mistypes a path is handed the
   superseded example at the very point of entry, contradicting the hint
   directly above it. This is the same defect shape the issue was filed for, on
   a surface the issue's four-item inventory did not include, and neither
   acceptance criterion covers it. It is also a copy change, not a validation
   change: the Go twin's `coverImageErrorMessage` carries no example at all, so
   the two messages are already non-identical and no Go/TypeScript parity
   fixture constrains the wording. Worth a follow-up issue; the fix is the
   example inside that one string plus the assertion that pins it in
   `web/src/lib/workshopAdmin.test.ts`.
2. **`web/src/lib/workshopAdmin.ts` carries the same verbatim quote of the
   erroneous migration comment**, in `isSafeCoverImage`'s own doc comment, and
   did not receive the correction paragraph its Go twin did. The implementer's
   stated rationale — that the Go comment is "the one place in the source that
   already repeats the wrong string verbatim" — is therefore not accurate;
   there are two such places and one was corrected. Not blocking, since the
   correction is recorded and findable, but the asymmetry belongs in the same
   follow-up as finding 1, which touches that file anyway.
3. **Typography.** The hint's new clause uses an ASCII `--`, which renders as
   two literal hyphens. Rendered copy elsewhere in the SPA uses an em dash
   essentially without exception — 121 lines across `web/src` do. Cosmetic
   only, and not worth a round trip on its own; folding it into finding 1's
   follow-up is the cheap moment to fix it.
