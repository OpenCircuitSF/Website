**RGB panel**

```ts
export type GpioMapping = 'regular' | 'adafruit-hat' | 'adafruit-hat-pwm';
export interface MatrixConfig { slowdown: number; soundOff: boolean; isolatedCore: boolean; mapping: GpioMapping; pwmMod: boolean; pwmBits: number; chain: number }
export const MATRIX_START: MatrixConfig;   // { slowdown: 1, soundOff: false, isolatedCore: false, mapping: 'regular', pwmMod: false, pwmBits: 11, chain: 1 }
export const PANEL_W = 32, PANEL_H = 16;    // drawn cells (a half-resolution picture of a 64×32 panel)
export type Look = 'dark' | 'garbage' | 'shimmer' | 'clean';
export type Problem = 'sound' | 'mapping' | 'slowdown' | 'core' | 'refresh';
export interface MatrixState { runs: boolean; look: Look; jitter: boolean; refreshHz: number; refreshLowHz: number; flicker: 'visible' | 'camera' | 'steady' | 'none'; problems: Problem[] }
export function refreshHz(cfg: MatrixConfig): number;
export function matrixState(cfg: MatrixConfig): MatrixState;
export function colorLevels(bits: number): number;         // 2 ** bits
export function panelPixels(state: MatrixState, pwmBits: number): string[];  // PANEL_W*PANEL_H hex colors, row-major
export function rowOpacity(row: number, state: MatrixState): number;        // 1, or a static dimming (see below)
export function matrixCommand(cfg: MatrixConfig): string;
```

`MATRIX_START` is a fresh install: library defaults (slowdown 1, mapping `regular`, 11 bits) and Raspberry Pi OS defaults (sound on, no isolated core).

`refreshHz` is an **illustrative model**, documented as such in a comment, for 64×32 panels (1:16 scan) chained `chain` times:
`Math.round(1e9 / (16 * ((2 ** pwmBits - 1) * 130 + pwmBits * 64 * chain * 40 * (slowdown + 1))))`
(130 ns is the library's lowest-bit time; 40 ns × (slowdown + 1) per clocked pixel is invented to give realistic magnitudes). Values: (11 bits, 1 panel, slowdown 2) = 178; (11, 3, 4) = 91; (7, 3, 4) = 219; (11, 3, 2) = 120.

`matrixState` rules, evaluated in order:
1. `!soundOff` → `runs: false`, `look: 'dark'`, `refreshHz: 0`, `refreshLowHz: 0`, `flicker: 'none'`, `jitter: false`, problems `['sound']` only (the library exits when `snd_bcm2835` is loaded, so nothing else can be seen).
2. Otherwise `runs: true`, `refreshHz = refreshHz(cfg)`. Look: mapping wrong (`regular`, or `adafruit-hat-pwm` without `pwmMod`) → `'garbage'` + `'mapping'`; else slowdown 0 → `'garbage'` + `'slowdown'`; slowdown 1 → `'shimmer'` + `'slowdown'`; slowdown ≥ 2 → `'clean'`. (`adafruit-hat` with the mod soldered is fine.)
3. `!isolatedCore` → `jitter: true`, `refreshLowHz = Math.round(refreshHz * 0.7)`, push `'core'`; else `refreshLowHz = refreshHz`.
4. `flicker` from `refreshLowHz`: < 100 `'visible'` (push `'refresh'`), < 200 `'camera'`, else `'steady'`.
Problems order: sound, mapping, slowdown, core, refresh.

`panelPixels`: `'dark'` → all `#111111`. `'clean'` → test pattern: rows 0–11 are eight 4-column bars (white `#ffffff`, yellow `#ffff00`, cyan `#00ffff`, green `#00ff00`, magenta `#ff00ff`, red `#ff0000`, blue `#0000ff`, black `#000000`); rows 12–15 are a grey ramp across the 32 columns quantised to `Math.min(colorLevels(pwmBits), 32)` steps (so 1–4 bits visibly band; that is the colour-depth cost of fewer bits). `'shimmer'` → the clean pattern with every cell where `(i * 7) % 11 === 0` replaced by a wrong bar colour (deterministic). `'garbage'` → each cell a palette colour picked by a deterministic hash of the index (for example `((i * 2654435761) >>> 0) % 8`). Never random, never time-dependent: the same state always yields the same pixels.

`rowOpacity`: 1 by default; if `jitter`, rows 4–5 and 12–13 are 0.55 (a static uneven band); if `flicker === 'visible'`, every other group of two rows (`Math.floor(row / 2) % 2 === 1`) is 0.45 (static banding, as a phone camera catches it). When both apply, take the minimum.

`matrixCommand`: `sudo ./demo -D 0 --led-rows=32 --led-cols=64 --led-chain={chain} --led-gpio-mapping={mapping} --led-slowdown-gpio={slowdown} --led-pwm-bits={pwmBits} --led-show-refresh` (the library's `examples-api-use/demo`).

Plain text, three ideas each, in the house voice (short sentences, second person, no marketing). Draft; tighten as needed but keep the facts:

`pi-volumio-streaming` (demo `VolumioDemo`)
- tryIt: "Pick how people will play: a phone’s Spotify app, an iPhone, internet radio. See which Volumio feature handles it, whether it’s free, and the path the sound takes to the speakers."
- idea "A music player set up from a web page": Volumio is a whole operating system image for music. Flash it with Raspberry Pi Imager, boot, and open volumio.local in a browser on the same network; everything after that, from the output to the plugins, is set in that page. If the Pi isn’t on your network yet, it starts its own WiFi hotspot so you can join it and finish setup. At our space one runs the front speakers on a Pi Zero 2W.
- idea "Everyone plays from their own app": the free version takes AirPlay from iPhones and Macs, UPnP/DLNA from laptop and Android apps, its own internet radio, and files on a USB stick or network share. Spotify Connect comes from a free plugin; each person casts from their own Spotify app, which needs their own Spotify Premium account, so nobody shares a login. Tidal Connect, Qobuz Connect and Bluetooth input need Volumio Premium, a paid subscription. Volumio moves features between plans, so check the current plans.
- idea "Make it easy to share": give the player a clear name such as "Front Speakers" so people pick the right one, and set a maximum volume. A Zero 2W only sees 2.4 GHz WiFi, wants a proper power supply, and has no headphone jack: add a DAC HAT, a USB DAC, or run HDMI to a receiver, then an amplifier unless the speakers are powered. Volumio keeps its system read-only and writes only settings to the card, but shut it down from its menu when you can.
- takeaway: "Volumio turns a Pi into a speaker anyone on the WiFi can play to. AirPlay, UPnP, radio and Spotify are free; Tidal, Qobuz and Bluetooth need Premium."

`pi-rgb-matrix-flicker` (demo `RgbMatrixDemo`)
- tryIt: "The panel starts as a fresh install leaves it. Turn the sound off, match the mapping to the HAT and raise the slowdown, then reserve a core and trade PWM bits for refresh."
- idea "The Pi 4 is too fast for the panel": a HUB75 panel is fed by clocking pixels in over GPIO, and a Pi 4 can toggle the pins faster than the panel can latch them. You get garbage or shimmering pixels. --led-slowdown-gpio adds wait states; try 2, then 3 or 4. --led-gpio-mapping must match the adapter: adafruit-hat for the Adafruit Bonnet or HAT, adafruit-hat-pwm only if you have soldered a wire between GPIO 4 and GPIO 18.
- idea "Sound and Linux get in the way": the onboard sound uses the same PWM hardware, and the library refuses to start while its driver (snd_bcm2835) is loaded. Put dtparam=audio=off in /boot/firmware/config.txt (or blacklist snd_bcm2835) and reboot. Linux also moves other work onto the core refreshing the panel; reserving core 3 with isolcpus in /boot/firmware/cmdline.txt (on the same line as everything else) steadies it. Run the program with sudo; the library drops root once it has set up the pins.
- idea "Refresh against color, and a separate supply": fewer PWM bits mean fewer brightness levels per color but a higher refresh rate; the library’s --led-show-refresh prints the real number. Chaining panels lowers it. Power the panels from their own 5 V supply sized for every LED at full white, never from the Pi’s 5 V pin, and join the grounds.
- takeaway: "Sound off, the right mapping, a slowdown of 2 or more, a reserved core, and its own 5 V supply. Then trade PWM bits for refresh."
