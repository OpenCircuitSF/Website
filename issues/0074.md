# 0074 — Leaving a page mid-restore stamps a clamped 0 over its saved scroll offset

| | |
|---|---|
| **Status** | open |
| **Module** | web |
| **Platform** | All |
| **Phase** | 2 — Brand and marketing pages |
| **First seen** | 2026-08-18 |

## Description

`saveScrollToCurrentEntry()` in `web/src/lib/router.ts` does not consult `restoringScroll`. Navigating away while a restore is still clamped at 0 — through `navigate()` or through `pagehide` — stamps that 0 over the entry's good saved offset. A later Back to that entry lands at the top.

Confirmed live at `#0014`'s fourth review. **Pre-existing since `243abad`; not introduced by `f6b204e`** — both paths behave identically on the unfixed parent build, so this is inherited, not a regression from the `cancelRestore()` fix.

## Steps to reproduce

1. Scroll a tall page so a non-trivial offset is saved into its history entry.
2. Arrange for a restore to that entry to clamp — the document must be shorter than the target offset when the restore runs, which is what the `Loading…` placeholder or a slow fetch produces.
3. Navigate away 150 ms into the spinning restore, via a link click or a full document unload.
4. Return to that entry with Back.

## Expected behavior

The entry keeps its saved offset and Back restores it.

## Actual behavior

The entry's state carries `{ scrollY: 0 }` — the clamped value observed mid-restore — and Back lands at the top.

## Root cause

`saveScrollToCurrentEntry()` stamps `window.scrollY` unconditionally. While a restore is in flight and clamped, that reads 0 rather than the offset the user actually left. The `navigate()` path looks worse on inspection because `cancelRestore()` clears `restoringScroll` *before* the save runs, but both paths produce the same wrong result.

## Acceptance criteria

- [ ] `saveScrollToCurrentEntry()` does not overwrite a saved offset with a clamped value while a restore is in flight — skip the stamp, or retain the pending target instead of the observed position
- [ ] Correct for **both** exits: the `navigate()` path and the `pagehide` path
- [ ] Ordering fixed so `cancelRestore()` clearing `restoringScroll` cannot re-open the hole
- [ ] Reproduced in a real browser **before** the fix and shown gone after — the three-step recipe above is known to work
- [ ] Mutation-proven: reintroduce the unconditional stamp, watch the check fail, revert, record the output
- [ ] No regression in `#0014`'s 31-check suite: Back, Forward, three-deep, cross-document, reload, unscrollable routes, `#0022`'s 404s, `history.length` accounting

## Notes

**Severity is low today and rises with Phase 6.** Nothing is misnavigated — only a restore target is lost, and the user was visibly at the top when they left. Reachability is currently narrow: it needs a destination tall enough to scroll, and the `Loading…` placeholder renders only `/privacy` and `/login`, both of which have no scrollable height.

It becomes routine on the first route that fetches its own content, which is `/workshops/:slug` — see [#0054](0054.md). Worth fixing in `router.ts` before that lands rather than after.

`#0014`'s reviewer raised this twice and the implementer twice declined to bundle it with a verified one-line fix. That was the right call — this is a behaviour change on an untouched path and belongs in its own commit with its own proof.
