## Description

`saveScrollToCurrentEntry()` in `web/src/lib/router.ts` does not consult `restoringScroll`. Navigating away while a restore is still clamped at 0 — through `navigate()` or through `pagehide` — stamps that 0 over the entry's good saved offset. A later Back to that entry lands at the top.

Confirmed live at `#0014`'s fourth review. **Pre-existing since `243abad`; not introduced by `f6b204e`** — both paths behave identically on the unfixed parent build, so this is inherited, not a regression from the `cancelRestore()` fix.

## Steps to reproduce

1. Scroll a tall page so a non-trivial offset is saved into its history entry.
2. Arrange for a restore to that entry to clamp — the document must be shorter than the target offset when the restore runs, which is what the `Loading…` placeholder or a slow fetch produces.
3. Navigate away 150 ms into the spinning restore, via a link click or a full document unload.
4. Return to that entry with Back.

## Expected behavior

The entry keeps its saved offset and Back restores it.

## Actual behavior

The entry's state carries `{ scrollY: 0 }` — the clamped value observed mid-restore — and Back lands at the top.

## Root cause

`saveScrollToCurrentEntry()` stamps `window.scrollY` unconditionally. While a restore is in flight and clamped, that reads 0 rather than the offset the user actually left. The `navigate()` path looks worse on inspection because `cancelRestore()` clears `restoringScroll` *before* the save runs, but both paths produce the same wrong result.

## Fix

`saveScrollToCurrentEntry()` stamped `window.scrollY` unconditionally. Added a
module-level `pendingRestoreTarget: number | null`, set by `restoreScroll()`
to the offset it is trying to reach (the same value read back off the
entry's own state to start the restore), and cleared either by `finish()`
on a completed/timed-out restore or by `saveScrollToCurrentEntry()` once it
has consumed it. `saveScrollToCurrentEntry()` now stamps
`pendingRestoreTarget` in place of `window.scrollY` whenever it is
non-null.

The ordering trap called out in the issue: `navigate()` calls
`cancelRestore()` (which clears `restoringScroll`) immediately before
calling `saveScrollToCurrentEntry()`, so a naive `if (restoringScroll)
return` guard inside the save would never fire on that path.
`cancelRestore()` was changed to deliberately leave `pendingRestoreTarget`
alone — only `saveScrollToCurrentEntry()` clears it, after reading it — so
it survives being called after `restoringScroll` is already false. The
`pagehide` exit needed no such reordering fix since it calls
`saveScrollToCurrentEntry()` directly while `restoringScroll` (and
therefore `pendingRestoreTarget`) is still set; it started passing as soon
as the save function itself was fixed.

## Gotchas

- The obvious "skip the stamp while `restoringScroll` is true" guard fails
  on the `navigate()` exit specifically because `cancelRestore()` clears
  `restoringScroll` *before* `saveScrollToCurrentEntry()` runs (both are
  called back-to-back at the top of `navigate()`). The fix has to survive
  that ordering by using a separate piece of state that `cancelRestore()`
  does not touch.
- `/about`'s max scrollable offset at the test viewport (1024×700) is 776
  px (`scrollHeight` 1476 − viewport 700), not the round numbers (900,
  1000) tried first — `window.scrollTo()` silently clamps to the real max,
  which looked like a router bug at first and was actually a test-script
  bug. Compute the real max before picking a probe offset.
- Confirming this app's routes grow from the Loading placeholder to full
  content in one binary Svelte re-render (not incrementally across frames)
  was necessary to understand why "the loop yields to a mid-restore user"
  can't be freshly proven with a real user-scroll probe here: during the
  clamp phase the document has ~0 scrollable height, so any scroll attempt
  the "user" makes is itself clamped to 0 by the browser and never diverges
  from what the restore loop already sees.
- `npm run build` run for verification overwrote the committed
  `web/dist/index.html` placeholder (real build output, not the minimal

### The headline question: does the divergence bail-out leave a stale target?

**No — it clears it.** `attempt()`'s bail-out calls `finish()`, and `finish()`
clears `pendingRestoreTarget` as well as `restoringScroll`. The token guard does
not interfere: on a bail-out the loop has not been superseded, so `token ===
restoreToken` and `finish()` runs its body in full.

Proved in the browser rather than argued from the source. Because a restore
whose target is *reachable* completes on its first successful apply — leaving no
window for a user to diverge — the probe seeds the entry with an offset **above**
`/about`'s real max (2000 vs 776), so the loop clamps at 776 and keeps
re-applying for the full `RESTORE_DEADLINE_MS` against a fully scrollable
document. That is the only state in which `attempt()`'s bail-out can fire at all.

```
##### 85013a8 (BPrhFVIP) — divergent scroll mid-restore, then navigate() #####
served bundle: index-BPrhFVIP.js
/about max scrollable offset: 776 | seeding entry with target 2000
restore in flight: scrollY=0 scrollHeight=1476 (loop still re-applying 2000)
user scrolled mid-restore; after 120ms scrollY=176 (loop should have bailed and left them here)
300ms later scrollY=176 -> loop is NOT fighting the user
exit: navigate() -> /privacy
BACK -> path=/about scrollY=176 history.state={"scrollY":176}
RESULT: entry carries 176 (not the 2000 target)
```

So the sequence the issue's reviewer was worried about — restore targets 776,
user scrolls to 100, loop bails, user leaves — stamps **where the user actually
is**, not the abandoned target.

That probe was then shown to have teeth. **Mutation A** deleted the single line
`pendingRestoreTarget = null;` from `finish()` and changed nothing else
(`CX4Ph0OQ`); the identical probe flipped:

```
##### MUTATION A (finish() does not clear the target) #####
user scrolled mid-restore; after 120ms scrollY=176
BACK -> path=/about scrollY=776 history.state={"scrollY":2000}
RESULT: WRONG-VALUE STAMP -- the entry carries the intended target 2000, not where the user was
```

Which also **independently re-proves the one item the implementer left on the
byte-identical argument**: the loop demonstrably does not fight a mid-restore
user (176 held steady across 300 ms of a still-live restore, on both
`85013a8^` and `85013a8`), and the bail-out's interaction with the *new* state
is exercised directly rather than assumed.

### Can a stale target survive into a later, unrelated save?

**No, and it is bounded three ways.**

1. Every exit from the restore loop — reached target, deadline, divergence
   bail-out — goes through `finish()`, which nulls it.
2. `saveScrollToCurrentEntry()` reads it and clears it in the same breath, so
   the value is strictly single-use: the *first* save of any kind consumes it.
3. `cancelRestore()` — the one place that deliberately leaves it set — has
   exactly one caller, `navigate()`, and `saveScrollToCurrentEntry()` is the
   very next statement. There is no path on which the value outlives that pair.

Probed anyway, letting the deadline lapse and then scrolling around normally so
the throttled listener performs ordinary unrelated saves:

```
after normal scrolling, throttled saves: scrollY=416 history.state={"scrollY":416}
RESULT: PASS (unrelated save recorded the real position)
```

There is also a **structural invariant** that makes the whole design safe rather
than merely lucky: `pendingRestoreTarget` is only ever assigned from the value
`restoreScroll()` was handed, and both call sites read that off the *current*
entry's own `history.state` (`initRouter()`'s `window.history.state.scrollY`,
the popstate handler's `event.state.scrollY`). The current entry cannot change
between the assignment and the consumption without re-entering `restoreScroll()`
(a traversal) or passing through `navigate()` (which consumes first, then
pushes). So when the save stamps `pendingRestoreTarget`, it is writing the entry
its own already-stored value — the write is idempotent. **The worst case of this
patch is a no-op save, never a novel wrong offset.**

### Residual, recorded rather than bounced

There is a **one-animation-frame** window in which the save still uses the
target: the bail-out runs on the next `requestAnimationFrame`, so a save
dispatched between a divergent user scroll and that frame consumes the target
instead of the observed position. Measured by sweeping the delay between a real
wheel scroll and a real click (3 trials each), on the target-above-max setup:

```
85013a8  delay   0ms: stamps=[2000,2000,2000]   delay  17ms: stamps=[176,176,176]
         delay   8ms: stamps=[2000,2000,2000]   delay 33/50/100ms: stamps=[176,...]
85013a8^ delay   0ms: stamps=[ 776, 776, 776]   delay  17ms: stamps=[176,176,176]
         delay   8ms: stamps=[ 776, 776, 776]
```

The window is one frame wide and shuts at 17 ms on both builds. **It is not a
regression**: in that same window the old code stamped the clamp (776) rather
than the user's 176 — composited wheel scrolling has not yet reached the main
thread's `window.scrollY` — and 2000 clamps to 776 on the way back, so Back
lands at **776 either way**. The two builds are user-visibly identical here;
only the number recorded in `history.state` differs, and per the invariant above
the new number is the entry's own prior value.

It becomes worth a second look only for `#0054`, where a *progressively growing*
document could make the entry's prior offset land further from the user's last
position than a clamp would. If that turns out to matter, the fix is small —
have `onScroll` clear `pendingRestoreTarget` when it observes a scroll that
diverges from the restore, instead of waiting for the next frame. Filing that
now would be speculative; noted here for whoever builds `/workshops/:slug`.
