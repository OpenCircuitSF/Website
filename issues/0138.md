## Description

Two related gaps in how `#0052`'s admin UI handles a workshop cover image.

**No upload path exists.** The editor accepts a path or URL as text because there is no multipart or upload route anywhere in the API — `#0052`'s reviewer confirmed that. The criterion reads "upload **or** path entry", so it is arguably satisfied as worded, but an admin currently has no way to get an image onto the server through the product.

**The validator admits off-site URLs.** `isSafeCoverImage` accepts a protocol-relative `//host/path`, which loads an asset from an arbitrary third-party host. `CLAUDE.md` §9 says the site carries no external CDNs and is self-contained by design; a cover image pulled from someone else's host is exactly that, plus a referer leak on every page view.

- [x] ~~Decide whether an upload endpoint is in scope for v1. Path entry (a site-relative path saved to `cover_image`) is the intended v1 behavior. An upload endpoint deserves its own future issue, not a rider on this one.

## Notes

Filed from `#0052`'s phase-3 review. The protocol-relative hole is the part worth fixing regardless of how the upload question resolves — it is a one-line validator change plus a test, and it is the half that contradicts a stated project rule rather than merely leaving a convenience unbuilt.

## Root cause

Three independent gaps, all shaped the same way: a check that tested for the
presence of a scheme/prefix instead of testing for "does this resolve
off-site."

1. **`isSafeCoverImage`** (`web/src/lib/workshopAdmin.ts`) was
   `value.startsWith('/') || isHttpUrl(value)`. A protocol-relative
   `//evil.host/x` starts with `/`, so it passed the first branch — the
   check never distinguished "one leading slash" (root-relative, safe) from
   "two" (network-path reference, off-site).
2. **`isSafeLinkHref`** (`web/src/lib/markdown.ts`) treated "no scheme
   detected" as sufficient for "safe": `HAS_SCHEME` requires a leading
   letter, so `//evil.host/x` (and `\\evil.host/x`, `/\evil.host/x`, which a
   browser's URL parser treats identically to `//evil.host/x` for a special
   http/https base — backslash counts as slash there) fell through to the
   unconditional `return true` for "no scheme = relative = safe." `#0054`'s
   `hasExternalSignup` (`workshopDetail.ts`) calls this same function for
   `signup_url`, so it silently inherited the hole too.
3. **`cover_image` was never checked server-side.** `internal/handlers/admin_workshops.go`'s
   `Create`/`Patch` round-tripped whatever the client sent straight into
   `workshops.CreateInput`/`UpdateInput` with no validation, so the two
   client-side checks above were the *only* defense — any other caller of
   the admin API (a script, a future import route, a bug in the editor)
   could write an arbitrary string into `cover_image`, which `internal/seo`'s
   `absoluteURL` then prefixes unconditionally into `og:image` and the
   JSON-LD `image` field.

## Fix

**Decision — cover images are same-origin only; a leading `/` and nothing
that can resolve off-site.** `CLAUDE.md` §9 ("no external CDNs ...
self-contained by design") and `PRD.md` §6.2's own schema comment
(`cover_image TEXT, -- path under /assets`) both say a cover image belongs
on this site, and an image is a load the page performs on the reader's
behalf without asking — unlike a link, which the reader chooses to follow.
So `isSafeCoverImage` no longer accepts an absolute `http(s)://` URL to
*any* host, including one that looks entirely reasonable
(`https://example.com/cover.jpg` used to pass and no longer does). It now
requires a leading `/`, then rejects a leading `//` after normalizing any
backslash to a forward slash (catching `//evil.host/x`, `\\evil.host/x`,
and `/\evil.host/x` with one rule). Mirrored server-side as
`isSafeCoverImage` in `internal/handlers/admin_workshops.go`, wired into
both `Create` and `Patch` — a bad `cover_image` now gets a 400 before it
ever reaches the store or `internal/seo`.

**Decision — Markdown link destinations (and `signup_url`, which reuses the
same helper) keep allowing an absolute `https://` URL to any host.** A link
is a navigation the reader affirmatively clicks, and a workshop's
`signup_url` is routinely an external ticketing site (Eventbrite etc.), so
restricting links to same-origin would break a legitimate use case §9
isn't actually worried about. `isSafeLinkHref` therefore only closes the
protocol-relative/backslash hole (same normalize-then-check-`//`
technique as the cover-image fix) — it does not touch the existing
http/https/mailto scheme allowlist or the "no scheme = relative, safe"
branch for a genuinely root-relative path like `/workshops/soldering-101`.

**No upload endpoint.** Struck per the acceptance criteria above — path
entry to a site-relative `cover_image` is the intended v1 behavior; an
upload route is future work with its own design questions (storage
location, size/type limits, how the stored path reaches the row) that
don't belong riding along on a validator fix.

### Ruling on the asymmetry: **correct, and ratified.**

Cover images same-origin-only while Markdown links and `signup_url` may go
anywhere is not an inconsistency to be flattened. The two cases differ in
mechanism, and §9 is about exactly the mechanism that differs:

- An `<img src>` is a **subresource the page fetches automatically**, for every
  visitor, without anyone choosing it — leaking Referer and client IP to a
  third party and creating an availability dependency on a server this project
  does not control. `CLAUDE.md` §9's "no external CDNs … self-contained by
  design" is precisely a rule about automatic third-party fetches, and PRD
  §6.2's own schema comment (`cover_image TEXT, -- path under /assets`)
  independently says the same thing about this column.
- A link is a **navigation the reader affirmatively clicks**. §9 says nothing
  about outbound links, and the product needs them: `#0054`'s
  `hasExternalSignup` renders `signup_url` with `target="_blank"
  rel="noopener noreferrer"`, which is the shape of a deliberate outbound
  link, and a workshop's registration page is routinely Eventbrite.

Dropping the previously-accepted absolute `https://` cover image is therefore
right, and **strands no data**: this is greenfield (`CLAUDE.md` §1), nothing is
live but the static placeholder, `migrations/000020_create_workshops` has no
seed rows, no `cover_image` value appears anywhere in `cmd/`, `scripts/db/` or
the migrations, and `select … from workshops` against the dev database errors
with `relation "workshops" does not exist`. There is no existing absolute
cover-image URL anywhere to be rejected on its next save.

**And the rule is not too tight.** Every legitimate shape I could think of is
accepted, verified by execution against both twins: a query string
(`/img/c.jpg?w=100&u=//evil.host`), a fragment (`/img/c.jpg#//evil.host`), a
`//` mid-path (`/a//b/c.jpg`), interior `..` (`/assets/../img/c.jpg`), an
encoded backslash (`/%5Cevil.host/x.jpg`), encoded slashes
(`/%2F%2Fevil.host/x.jpg`), a non-ASCII path (`/assets/café/über.jpg`), a bare
`/`, and a 10,012-character path. Empty and whitespace-only are treated as
"cleared", identically on both sides.

### Blocking finding 1 — an interior tab, LF or CR still reaches a third-party host

`isSafeCoverImage` (both twins) tests for a *prefix*. A browser's URL parser
**deletes every ASCII tab, LF and CR from the input before parsing it**, so a
control character placed between the two slashes reassembles into exactly the
protocol-relative URL this issue exists to reject:

| `cover_image` value | Both twins | Chromium resolves to |
|---|---|---|
| `/` `<TAB>` `/evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |
| `/` `<LF>` `/evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |
| `/` `<CR>` `/evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |
| `/` `<CR><LF>` `/evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |
| `/` `<TAB>` `\evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |
| `/` `<LF>` `\evil.host/x.jpg` | **ACCEPT** | `http://evil.host/x.jpg` |

Confirmed in a **real browser**, not only against Node's parser: headless
Chromium was pointed at a page rendering the same `<img src={…}>` that
`WorkshopDetail.svelte:121` renders, on an ephemeral port, with server
ownership proved by a per-run marker attribute before trusting any output
(§8b), and all off-origin traffic intercepted and recorded rather than sent.
Chromium **attempted `http://evil.host/x.jpg`**. That is a third-party
subresource fetch on a public page for every visitor — the precise thing §9
forbids and the precise thing this issue was filed to stop.

Three reasons this is a bounce rather than a follow-up issue:

1. **The issue's own `## Root cause` condemns it.** It diagnoses all three
   original gaps as "a check that tested for the presence of a scheme/prefix
   instead of testing for *does this resolve off-site*." The new
   `isSafeCoverImage` makes that identical mistake a fourth time.
2. **Criterion 2 is not met.** "The full set of what it accepts is written
   down and matches §9." What is written down — in the Go doc comment, the
   TypeScript doc comment, and `workshopAdmin.ts`'s module header — is
   "a leading `/` and **nothing else that could resolve off-site**", and
   "SAME-ORIGIN ONLY". Six accepted values resolve off-site. The prose is
   not merely incomplete, it is affirmatively false.
3. **The fix was already in a file this commit edits.** `#0052`'s pass-2
   review found this exact class and armored `isSafeLinkHref` with
   `HAS_CONTROL_CHAR = /[\x00-\x1f\x7f]/`, seven lines above the branch this
   commit changed in `markdown.ts`. `isSafeLinkHref` correctly **rejects** all
   six payloads above; its cover-image sibling does not. The hardening exists,
   was read, and was not carried across.

**Suggested fix** — reject control characters before the prefix test, in both
twins, mirroring `markdown.ts`:

```go
// internal/handlers/admin_workshops.go
if strings.ContainsFunc(v, func(r rune) bool { return r < 0x20 || r == 0x7f }) {
    return false
}
```

```ts
// web/src/lib/workshopAdmin.ts
if (/[\x00-\x1f\x7f]/.test(value)) return false;
```

Add the six payloads to `TestIsSafeCoverImage` and to
`workshopAdmin.test.ts`, and at least one to the HTTP-level
`…RejectsUnsafeCoverImage` pair so the API boundary is covered too. Note that
`\x00`, `\x0b`, `\x0c` and `\x7f` do *not* resolve off-site (a browser
percent-encodes them into the path), so rejecting them is defence in depth
rather than a fix — but a denylist of "just tab/LF/CR" is the same
enumerate-the-bad-spellings trap this issue was filed against, and
`markdown.ts` already chose the whole C0+DEL range. Match it.

**Scope note, so the next pass does not over-fix:** the SEO surface is *not*
affected and needs no change. `internal/seo`'s `absoluteURL` concatenates
base + path, so `https://www.opencircuitsf.com` + `/<TAB>/evil.host/x.jpg`
parses with the authority already fixed as `www.opencircuitsf.com` and the
`//` landing harmlessly in the path — verified. `og:image` and the JSON-LD
`image` field stay same-origin for every payload above. The damage is confined
