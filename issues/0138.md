## Description

Two related gaps in how `#0052`'s admin UI handles a workshop cover image.

**No upload path exists.** The editor accepts a path or URL as text because there is no multipart or upload route anywhere in the API — `#0052`'s reviewer confirmed that. The criterion reads "upload **or** path entry", so it is arguably satisfied as worded, but an admin currently has no way to get an image onto the server through the product.

**The validator admits off-site URLs.** `isSafeCoverImage` accepts a protocol-relative `//host/path`, which loads an asset from an arbitrary third-party host. `CLAUDE.md` §9 says the site carries no external CDNs and is self-contained by design; a cover image pulled from someone else's host is exactly that, plus a referer leak on every page view.

- [x] The full set of what it accepts is written down and matches §9 — decide explicitly whether absolute `https://` URLs to other hosts are allowed at all, or whether cover images must be same-origin
- [x] ~~Decide whether an upload endpoint is in scope for v1. Path entry (a site-relative path saved to `cover_image`) is the intended v1 behavior. An upload endpoint deserves its own future issue, not a rider on this one.
- [x] `#0052`'s cover-image criterion ends up ticked or struck, not floating — struck, as above (and per the note directly above it)

## Notes

Filed from `#0052`'s phase-3 review. The protocol-relative hole is the part worth fixing regardless of how the upload question resolves — it is a one-line validator change plus a test, and it is the half that contradicts a stated project rule rather than merely leaving a convenience unbuilt.

## Root cause

Three independent gaps, all shaped the same way: a check that tested for the
presence of a scheme/prefix instead of testing for "does this resolve
off-site."

1. **`isSafeCoverImage`** (`web/src/lib/workshopAdmin.ts`) was
   `value.startsWith('/') || isHttpUrl(value)`. A protocol-relative
   `//evil.host/x` starts with `/`, so it passed the first branch — the
   check never distinguished "one leading slash" (root-relative, safe) from
   "two" (network-path reference, off-site).
2. **`isSafeLinkHref`** (`web/src/lib/markdown.ts`) treated "no scheme
   detected" as sufficient for "safe": `HAS_SCHEME` requires a leading
   letter, so `//evil.host/x` (and `\\evil.host/x`, `/\evil.host/x`, which a
   browser's URL parser treats identically to `//evil.host/x` for a special
   http/https base — backslash counts as slash there) fell through to the
   unconditional `return true` for "no scheme = relative = safe." `#0054`'s
   `hasExternalSignup` (`workshopDetail.ts`) calls this same function for
   `signup_url`, so it silently inherited the hole too.
3. **`cover_image` was never checked server-side.** `internal/handlers/admin_workshops.go`'s
   `Create`/`Patch` round-tripped whatever the client sent straight into
   `workshops.CreateInput`/`UpdateInput` with no validation, so the two
   client-side checks above were the *only* defense — any other caller of
   the admin API (a script, a future import route, a bug in the editor)
   could write an arbitrary string into `cover_image`, which `internal/seo`'s
   `absoluteURL` then prefixes unconditionally into `og:image` and the
   JSON-LD `image` field.

## Fix

**Decision — cover images are same-origin only; a leading `/` and nothing
that can resolve off-site.** `CLAUDE.md` §9 ("no external CDNs ...
self-contained by design") and `PRD.md` §6.2's own schema comment
(`cover_image TEXT, -- path under /assets`) both say a cover image belongs
on this site, and an image is a load the page performs on the reader's
behalf without asking — unlike a link, which the reader chooses to follow.
So `isSafeCoverImage` no longer accepts an absolute `http(s)://` URL to
*any* host, including one that looks entirely reasonable
(`https://example.com/cover.jpg` used to pass and no longer does). It now
requires a leading `/`, then rejects a leading `//` after normalizing any
backslash to a forward slash (catching `//evil.host/x`, `\\evil.host/x`,
and `/\evil.host/x` with one rule). Mirrored server-side as
`isSafeCoverImage` in `internal/handlers/admin_workshops.go`, wired into
both `Create` and `Patch` — a bad `cover_image` now gets a 400 before it
ever reaches the store or `internal/seo`.

**Decision — Markdown link destinations (and `signup_url`, which reuses the
same helper) keep allowing an absolute `https://` URL to any host.** A link
is a navigation the reader affirmatively clicks, and a workshop's
`signup_url` is routinely an external ticketing site (Eventbrite etc.), so
restricting links to same-origin would break a legitimate use case §9
isn't actually worried about. `isSafeLinkHref` therefore only closes the
protocol-relative/backslash hole (same normalize-then-check-`//`
technique as the cover-image fix) — it does not touch the existing
http/https/mailto scheme allowlist or the "no scheme = relative, safe"
branch for a genuinely root-relative path like `/workshops/soldering-101`.

**No upload endpoint.** Struck per the acceptance criteria above — path
entry to a site-relative `cover_image` is the intended v1 behavior; an
upload route is future work with its own design questions (storage
location, size/type limits, how the stored path reaches the row) that
don't belong riding along on a validator fix.

## Gotchas

- **The cover-image and link-href rules are deliberately different, by
  design, not oversight.** A reviewer checking "did this treat both cases
  the same" should find that it didn't, on purpose — see the two
  `## Fix` decisions above. Don't flatten them to match without re-reading
  the reasoning.
- **`isHttpUrl` (workshopAdmin.ts) is untouched** — it still backs
  `signup_url`'s own separate check (not `isSafeLinkHref`) and correctly
  allows any host, matching the "links may be external" decision.
- I did not touch `internal/seo/*`, `web/index.html`, or `web/dist/index.html` —
