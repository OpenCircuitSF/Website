## Description

`scripts/db_reset_guard_test.sh` Part 9 (`#0250` item 3) failed once during a
`scripts/check.sh guards` run, on a file the agent had never touched, with a
**`SUPERUSER`-only permission message**. An immediate re-run passed. A second
agent could not reproduce it.

**This is not CLAUDE.md §5's "the machine is busy" case.** That rule covers
timing failures under concurrent agent load. This is a permission error, and
there is a concrete mechanism.

`scripts/db-reset.sh:170` is:

```sql
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE datname = '$DB' AND pid <> pg_backend_pid();
```

**No `backend_type` or `usename` filter.** Any non-client backend attached to
that database is a target — most plausibly an **autovacuum worker**, which runs
as a superuser process and produces exactly a superuser-only permission error
when a non-superuser tries to signal it.

Part 9 uses a *private* scoped database (`opencircuit${RUNID}gt`), so "another
agent held a connection" does not explain it. Autovacuum attaching to a
freshly-created, freshly-written database does — and it is far likelier when
several agents are working the cluster, which explains the correlation with load
**without** being a timing flake, and explains why an immediate retry passed.

## Why this matters more than a nuisance

`scripts/check.sh guards` is the one target the whole external-oracle design
rests on (`#0300`). A non-deterministic failure there corrodes trust in exactly
the mechanism built because in-file checks could not be trusted.

## Acceptance criteria

1. The terminate query is narrowed to client backends —
   `AND backend_type = 'client backend'`, and consider `AND usename = current_user`.
   State which you used and why.
2. A backend the script may not signal is **reported clearly** rather than
   aborting the reset. The script's job is to clear client connections; an
   autovacuum worker is not an obstacle to that and must not read as one.
3. `scripts/db_reset_guard_test.sh` gains a case proving a **non-client backend**
   attached to the target database does not fail the run. Constructing one
   deterministically is the interesting part — if you cannot, say so and pin the
   narrowed query itself instead, explaining what that does and does not prove.
4. `#0207`'s protections are preserved exactly: the script must still refuse
   without `--force` and still report who holds the database, and still refuse a
   per-agent scratch database (`opencircuit_test_NNNN`), which belongs to
   `scripts/testdb.sh`.
5. Do not widen what the script may terminate. This narrows the query; it must
   not become a reason to reach for superuser.
6. `scripts/check.sh guards` passes, and the other four guard scripts still do.
   Run it more than once — the symptom is intermittent, and a single green run
   is what made this look fine before.

**`scripts/db-reset.sh`.** Introduced `CLIENT_WHERE`, one `WHERE`-clause
fragment used by both the connection-refusal check and the terminate
statement:

```sql
datname = '$DB' and pid <> pg_backend_pid()
  and backend_type = 'client backend' and usename = current_user
```

Used both `backend_type = 'client backend'` and `usename = current_user`
(criterion 1 offered the second as something to consider). `backend_type`
is the semantically direct fix — it is exactly what distinguishes a normal
session from autovacuum, the background writer, checkpointer, walsender,
parallel workers, etc., and it alone is what stops `pg_terminate_backend()`
from being asked to sign a backend the connecting role has no standing to
touch. `usename = current_user` is added as a second, independent
narrowing: every legitimate connection this project's tooling makes — an
agent, the user's dev session, this script itself — authenticates as
whatever role `$PGHOST_URL` names, `opencircuit` by convention across every
script in `scripts/`. Combining both with `AND` narrows further, never
wider, satisfying criterion 5.

Both the old CONNS-listing query (decides whether to refuse without
`--force`) and the terminate statement itself now read `$CLIENT_WHERE`
rather than each spelling an independent, driftable copy — this also fixes
a second-order bug the issue didn't name explicitly: under the old unscoped
query, a bare (non-`--force`) invocation would spuriously refuse merely
because autovacuum (or any other background process) had attached, even
with zero real client connections present.

Added a third, purely informational query (criterion 2): any backend
attached to `$DB` that the narrowed filter excludes — non-client, or a
client connected as a different role — is now printed as a `note:` line
before the reset proceeds. It is never counted toward the refusal decision
and never targeted by the terminate step; a failure to run this check is
not fatal to the reset, since it's a courtesy, not a gate.

**`scripts/db_reset_guard_test.sh`.** Added Part 11 and Part 11b.

Part 11 constructs a **deterministic non-client backend** attached to the
scoped test database (`TESTDB`) using a Postgres **parallel worker**:
`parallel_setup_cost`/`parallel_tuple_cost` driven to 0 plus a cross join
against `generate_series()` over a 500k-row seed table reliably produces
`backend_type = 'parallel worker'` rows in `pg_stat_activity` that persist
for several seconds — no fixture, no special privileges, no waiting on a
background process's own schedule. Verified empirically first (outside the
guard test) that this is a genuine, reproducible construction: a bare
`EXPLAIN` shows `Workers Planned: 4`, and polling `pg_stat_activity` during
the real query catches worker pids attached to the target database.

**What Part 11 does and does not prove**, stated in its own header comment:
it proves the narrowed `backend_type = 'client backend'` filter is exercised
against a real, live, non-client row — `db-reset.sh --force` completes
successfully (exit 0), the output never mentions `superuser`, and the
non-client backend is reported per criterion 2. It does **not** reproduce
the exact `SUPERUSER`-only permission error the issue diagnosed:
independently verified (`pg_terminate_backend()` issued directly against a
live parallel-worker pid, as the same non-superuser role that ran the
query) that parallel workers are **not** superuser-restricted the way
autovacuum is — the call succeeded with no error. A real autovacuum worker
cannot be constructed on demand; it attaches on its own schedule, not this
test's, so the literal permission error cannot be deterministically
reproduced. This is disclosed in the header rather than glossed over.

Part 11b is the requested fallback/complement (criterion 3): a static pin
of the narrowed query's source text, run unconditionally regardless of
whether Part 11's live construction works on a given machine. It reads the
tracked `scripts/db-reset.sh` directly (not a duplicated copy of expected

once; that single definition narrows by both `backend_type = 'client

### Blocking — the shared `$CLIENT_WHERE` breaks `#0207`'s refusal

Narrowing what may be **terminated** is what this issue asked for and is
correct. Reusing the same fragment for the **connection-refusal check** cuts the
opposite way: it makes the script *more* willing to proceed, which is exactly
the property `#0207` exists to prevent.

Measured on this machine (PostgreSQL 16.14, role `opencircuit`, no
`pg_read_all_stats`), with a `psql` session held open on a private scratch
database as role `brennan` — the machine's own login role, reachable over trust
auth with no password, and therefore what `psql opencircuit` typed by the user
actually connects as:

| | parent `921d4a4^` | this commit `921d4a4` |
|---|---|---|
| bare invocation | `refusing: '…' has other active connection(s) … pid 61078  brennan  psql  local`, exit 1 | **no refusal** — prints a `note:`, prints `resetting …`, then `ERROR: database "…" is being accessed by other users`, exit 1 |

The database survives (Postgres blocks the `DROP`, so this is not data loss),
but `#0207`'s protection — *refuse, and report who holds it* — is replaced by a
raw Postgres error, preceded by a `note:` that describes a live user session as
"not something this script needs to (or can) signal, and not counted above".
That note is actively misleading about the very thing that is about to fail.

**The root cause is deeper than `usename = current_user`, and dropping that
predicate alone does not fix it.** `pg_stat_activity` NULLs `backend_type` for
any backend the querying role does not own. Measured, all three from role
`opencircuit`:

| backend | `backend_type` | `usename` |
|---|---|---|
| own-role client backend | `client backend` | `opencircuit` |
| other-role client backend (`brennan`) | **NULL** | `brennan` |
| autovacuum worker | **NULL** | **NULL** |
| own-role parallel worker | `parallel worker` | `opencircuit` |

So `backend_type = 'client backend'` excludes autovacuum (good, and this is why
the fix works) but **also excludes every other-role client session** — verified:
with both a `brennan` and an `opencircuit` session attached, the proposed
`backend_type = 'client backend'` predicate counts 1, not 2. The distinguisher
that *is* available at this privilege level is `usename IS NOT NULL`: background
processes have no logged-in user, client sessions always do.

### Required remedy

**1. Split the fragment in `scripts/db-reset.sh`.** Keep `$CLIENT_WHERE` exactly
as committed for the terminate step — it is correct and must not widen. Add a
second, wider fragment for the refusal/holder-report check:

```bash
# What this script may TERMINATE. Unchanged: only client backends owned by
# this script's own role. Anything else either cannot be signalled by a
# non-superuser at all (the SUPERUSER error #0309 found) or is not ours to clear.
CLIENT_WHERE="datname = '$DB' and pid <> pg_backend_pid() and backend_type = 'client backend' and usename = current_user"

# What COUNTS as a holder for #0207's refusal decision. Deliberately NOT the
# same fragment: narrowing what may be terminated is safe, narrowing what
# counts as a holder makes the script willing to proceed. pg_stat_activity
# NULLs backend_type for any backend this role does not own, so
# `backend_type = 'client backend'` silently drops a real client session
# belonging to another role — including the user's own psql, which
# authenticates as their login role, not 'opencircuit'. `usename IS NOT NULL`
# is what actually separates a logged-in session from a background process here.
HOLDER_WHERE="datname = '$DB' and pid <> pg_backend_pid() and usename is not null and backend_type is distinct from 'parallel worker'"
```

`is distinct from` is required, not `<>`: `backend_type` is NULL for foreign
backends and `<>` would yield NULL. The `parallel worker` exclusion is cosmetic
(such a worker's leader is itself counted) but keeps the holder report honest.

- the `CONNS` query uses `$HOLDER_WHERE`;
- the terminate statement keeps `$CLIENT_WHERE`;
- the `note:` query's predicate becomes the negation of the holder body —
  `datname = '$DB' and pid <> pg_backend_pid() and not (usename is not null and backend_type is distinct from 'parallel worker')`
  — so it reports background backends only, which is what its wording already
  claims.

This keeps the genuine side benefit the implementer found: autovacuum
(`usename` NULL) still never causes a spurious refusal.

**Recommended, not required:** when `FORCE=1` and `$CONNS` holds rows the
terminate step cannot signal, say so explicitly — otherwise `--force` against a
foreign-role holder still ends in the bare `is being accessed by other users`
error with no explanation.

**2. `db_reset_guard_test.sh` Part 11b must pin both fragments.** As committed
it pins `usename = current_user` onto the shared fragment, so it would fail the
correct fix. Assert instead: `CLIENT_WHERE` defined exactly once, carrying both
predicates, referenced by the terminate step; `HOLDER_WHERE` defined exactly
once, containing `usename is not null` and **not** `usename = current_user`,
referenced by the refusal check.

**3. Add a foreign-role holder regression test.** Parts 1/2/3/5 all connect as
the same role, so none of them can see this class of failure — which is why the
break passed a green suite. Discover a second login role at runtime rather than
hardcoding one:

```sql
select rolname from pg_roles where rolcanlogin and rolname <> current_user
  order by rolsuper desc, rolname limit 1
```

try to connect as it, and if the connection cannot be made (auth), `pass` with
an explicit skip note rather than failing — this must not become a
machine-specific test. Assert: with that session attached, a **bare** invocation
exits non-zero, its output contains `refusing:` and names the holder, and the
connection survives. Verified sensitive: against `921d4a4` this case prints
`resetting` and dies on `DROP DATABASE`.

### Criterion 3 — Part 11 does not test what broke

Verified by running Part 11's exact construction (same `parallel_setup_cost`/
`parallel_tuple_cost` settings, same 500k-row cross join, worker confirmed
attached at pid 61557) against a scoped copy of the **parent** `921d4a4^`
script: **exit 0, and no `superuser` in the output.** Both of Part 11's core
assertions pass against the unfixed code, so neither is a regression test for
the terminate narrowing. Only its third assertion — the `note:` line — is
sensitive, and that is sensitive to criterion 2's *reporting*, not criterion 1's
narrowing.

The disclosure in Part 11's header is honest about the narrower point (parallel
workers are not `SUPERUSER`-restricted, so the literal error cannot be
reproduced that way) and that honesty is credited. But the header also claims it
"proves the general mechanism (a non-client-backend row is never selected, so it
can never trigger ANY permission error a client-owned row wouldn't)" — nothing
in the part observes whether the row was selected, and the run is byte-for-byte
equivalent either way. Soften that claim, or make the part sensitive.

**A deterministic construction of the exact error does exist**, contrary to the
implementer's conclusion — just not via a background worker. Measured:

```
ERROR:  permission denied to terminate process
DETAIL:  Only roles with the SUPERUSER attribute may terminate processes of roles with the SUPERUSER attribute.
```

from `pg_terminate_backend()` issued as `opencircuit` against a **superuser-owned
client backend**. That is the same error class `#0309` diagnosed, constructible
on demand wherever a second superuser login role is reachable, and it aborts the
reset under the old unscoped query while `$CLIENT_WHERE` excludes it. Folding it
into item 3's test gets both the `#0207` regression case and a sensitive
criterion-1 case from one fixture.
