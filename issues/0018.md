## Description

Turn the green PCB badge (`Logo 2026.png`) into the asset set the site needs. The raster derivatives — transparent, per-theme tinted, plus a favicon-safe chip mark — are already produced in `assets/logo/`; what remains is the vector trace and wiring the assets into the SPA.

## Long Description

The black ground has been removed by luminance keying (alpha from `max(R,G,B)`, black point 6, white point 212), so edges keep their anti-aliasing and there is no fringe on light backgrounds. Two tints exist because the brand green `#68FF23` measures 14.8:1 on the dark ground but only **1.32:1 on white** — transparency alone does not make the logo theme-adaptive. Light contexts use `#30800C` (same hue and saturation, value reduced to clear 4.5:1 on white).

The full logo is illegible below roughly 96 px, so the central chip with the `>_` prompt is extracted as a separate mark that reads cleanly from 32 px.

Full derivation notes are in [`assets/logo/README.md`](../assets/logo/README.md).

## Notes

PRD §4.5. The blue hexagonal badge is **retired** — this mark replaces it and the green-UI / blue-mark conflict that PRD §14 Q4 tracked is resolved.

`assets/logo/` is the source-of-truth asset folder; `web/public/` holds what the site actually serves. Keep the distinction — the masters are 1254 px and should not be served.

The `-webkit-mask` prefix is still required for Safari. A masked element has no `alt`, so the accessible name has to come from `role="img"` + `aria-label`.

`apple-touch-icon.png` is deliberately opaque: iOS composites a transparent touch icon onto an unpredictable ground and it can come out black on black.

Tracing is the one genuinely open piece. Auto-tracing this level of detail is lossy — expect to hand-correct, or trace only the chip mark and keep the full logo as raster.

## Root cause

Feature work. `assets/logo/` already had every raster derivative (previous
issue), but nothing was wired into `web/`: `web/public/` still carried
ShortLinks' PNG-only favicon (`favicon.png`/`favicon-16.png`, "the old
white-line one"), `index.html` still said `<title>Short Links</title>`, and
no vector trace of the mark existed anywhere — the PRD explicitly names this
as the one remaining deliverable ("Remaining deliverable: a vector trace,
tracked in issue #0018").

## Fix

**Vector trace.** Installed `potrace` via Homebrew (not present locally).
Converted `assets/logo/mark-mask-512.png` and `logo-mask-512.png` (already
clean, high-contrast, anti-aliased alpha masks — ideal potrace input, no
additional cleanup needed) to inverted-alpha PGM bitmaps with Pillow/numpy,
then `potrace -b svg --alphamax 1 --opttolerance 0.2 --turdsize 2` on each.
Post-processed the output: stripped the DOCTYPE/metadata boilerplate,
dropped the pt-unit `width`/`height` (sized via CSS/attrs at each call
site instead, keeping only `viewBox`), replaced the hardcoded `fill="#000000"`
with `fill="currentColor"`, and added `role="img"` + `<title>` for a
non-CSS accessible fallback. Rendered both at 16px through 900px with
Playwright to check quality (see Verification) — output was clean enough
to ship without hand-correction; the small solid-block "cursor" flourishes
after "open_circuit_sf" and "hack · build · learn" in the source art traced
faithfully rather than as artifacts (double-checked at high resolution
before concluding that).

**`favicon.svg`** is a separate derivative built from the same mark trace,
not just `mark.svg` re-served: a favicon has no page `color` to inherit, so
`currentColor` doesn't work there. Instead it carries its own `<style>`
block with an internal `@media (prefers-color-scheme: dark)` rule that
swaps the fill between the two logo tints — a real browser feature (both
Chromium and Firefox evaluate media queries inside a referenced favicon
SVG), verified by screenshotting it under both `colorScheme: 'light'` and
`'dark'` Playwright contexts with no page-level color set at all.
`favicon-32.png` (copied from `assets/logo/mark-green-32.png`) is the `<link
rel="icon" sizes="32x32">` fallback for browsers without SVG favicon
support.

**`site.webmanifest`** — name/short_name/description, `theme_color` and
`background_color` both `#0A0D0B` (the dark page background the mark was
designed against), `display: standalone`, and two icon entries
(`mark-green-256.png`, `mark-green-512.png` — accurate declared sizes,
not padded to a conventional-but-wrong 192×192). Chose the transparent
`mark-green-*` files rather than a new opaque asset because
`background_color` gives Android manifest consumers the matching dark
ground to composite onto; `apple-touch-icon.png` stays the separately
opaque asset since iOS ignores `background_color` and composites onto an
unpredictable ground (this is exactly the failure mode the existing
opaque-icon gotcha describes).

**Wiring into `web/public/` and `index.html`.** Copied a curated subset
of `assets/logo/` (not the whole 1254px-master folder — masters stay in
`assets/logo/`, only what the site serves lives in `web/public/`, per the
Notes): `logo.svg`, `mark.svg`, `favicon.svg`, `favicon-32.png`,
`logo-mask-512.png`, `mark-mask-64.png`, `mark-green-256.png`,
`mark-green-512.png`, `apple-touch-icon.png` (overwrites the ShortLinks
one), `site.webmanifest`. Replaced `index.html`'s favicon block with
`<link rel="icon" type="image/svg+xml">` + the PNG fallback + apple-touch +
manifest links, added light/dark `<meta name="theme-color">` (ported from
`placeholder/index.html`), and fixed `<title>Short Links</title>` →
`<title>Open Circuit SF</title>` — noticed while touching this exact block
and not worth leaving. Deleted the two old ShortLinks favicon PNGs
(`favicon.png`, `favicon-16.png`).

**`Logo.svelte`** (`web/src/lib/`) wraps the alpha-mask tinting technique
(`background-color: var(--logo-color)` + `mask-image: url(...)`) as a
component: `variant?: 'mark' | 'full'` (default `'mark'`), `size?: number`
px (default 34, matching `placeholder/index.html`'s header mark size). This
is the AC's "logo rendered via the mask technique, with `role="img"` and an
`aria-label`" requirement, built as the reusable unit `#0017` (site header,
next batch, which `#0018` blocks specifically so this export shape exists
before that work starts) imports directly — building the actual header
markup itself is out of this batch's scope per the assignment brief. Added
a new `--logo-color` token to `app.css` (all three token blocks: light,
dark-media, dark-attr) rather than aliasing `--accent`: the dark value is
identical to dark `--accent` (`#68FF23`, the literal brand green both come
from), but the light value (`#30800C`) is a separately-tuned tint from
`assets/logo/build-logo.py`, not identical to light `--accent` (`#2F7D0C`)
even though both follow "same hue/saturation, lowered until 4.5:1 on
white" — conflating them would have been a real, if subtle, deviation from
`assets/logo/README.md`'s documented recommended usage.

**`docs/frontend.md`** gets a new "Logo, favicon, and app icons" section
naming every file under `web/public/` and its purpose, plus the `file://`
mask restriction — written from a verification actually performed during
this issue (see below), not copied from the existing gotcha list in
`docs/design.md`/`CLAUDE.md`.

## Gotchas

- `potrace` was not preinstalled (`brew install potrace`, ~373 KB, no
  network issues). Its SVG output needs light post-processing before it's
  a good component asset: pt-unit dimensions that fight CSS sizing, a
  hardcoded `fill="#000000"`, and a `<metadata>` block worth stripping.
- Converting the alpha mask to potrace's expected bitmap input matters:
  fed it *inverted* alpha (opaque → black/ink, transparent → white) as a
  grayscale PGM, not the raw RGBA mask — potrace treats dark pixels as the
  traced foreground.
- Confirmed (again, as in `#0013`) that a Node script's `require()`
  resolves against the script's own directory, not the shell's cwd —
  `playwright`-using scripts had to live inside `web/` to see
  `web/node_modules`.
- `assets/logo/README.md`'s two-tint rationale is easy to accidentally
  collapse into "just reuse `--accent`" since the dark values are
  identical — worth the explicit `--logo-color` token comment in `app.css`
  so a future edit doesn't quietly break the light-mode logo's contrast.

**`--logo-color` is justified, not token sprawl.** It is not in PRD §4.2's
table, but `assets/logo/README.md` already prescribed this exact token and
these exact values before `#0018` started. The values come from
`build-logo.py`'s `GREEN_DARKBG`/`GREEN_LIGHTBG` constants and are baked into
the shipped raster derivatives — so the mask tint has to equal them or a
masked logo and a `logo-light.png` on the same page would not match. Dark is
`#68FF23`, identical to dark `--accent`; light is `#30800C` against `--accent`'s
`#2F7D0C`, measuring 4.98:1 vs 5.17:1 on white. The two light values are
perceptually indistinguishable, so the case for a separate token rests on
provenance and on staying locked to the raster assets, not on appearance — but
that case is real, it is documented, and the token is actually used
(`Logo.svelte`). Approved.

**The traced SVGs, compared against the originals by eye.** Rendered
`mark.svg` and `logo.svg` beside `mark-green-512.png` / `logo-green-512.png`
at 400/256/128/96/48/32/16 px on the dark ground, and the mark against white
in the light tint. The traces are essentially indistinguishable from the
raster masters at every size — no dropped detail, no polygonisation on the
board traces, the `hack · build · learn` line and the ring text intact. The
full logo collapses into noise at 128 px and below in *both* the trace and the
original, confirming `CLAUDE.md` §8's ~96 px note is a property of the artwork
rather than of the tracing. The `>_` prompt in the mark is legible at 32 px and
readable at 16 px. Potrace was the right call here and needed no hand-correction.

**The `file://` mask hazard, reproduced independently.** Built an isolated page
using `Logo.svelte`'s mask CSS verbatim against the shipped
`mark-mask-64.png`, with a plain `<img>` of the same file as a control, and
loaded it twice. Over `python3 -m http.server` the masked element renders the
tinted mark; under `file://` it renders **completely empty** — no console
error, no broken-image glyph, while the `<img>` control still paints. Exactly
as `CLAUDE.md` §8 and `docs/frontend.md` describe. The implementer's claim to
have reproduced this firsthand holds, and the hazard is documented in
`docs/frontend.md` as this issue requires.

**`Logo.svelte` uses the mask technique** as shipped, with `role="img"` and
`aria-label="Open Circuit SF"`. Both mask masters are square (512×512 and
64×64), so the single square `size` prop is correct for both variants.

### Findings carried forward — not blocking, but `#0017` should fix

1. **The mark mask ships only at 64 px and is visibly soft on retina.**
   `Logo.svelte` hardcodes `/mark-mask-64.png` for every `size`. Rendered at
   64 CSS px on a 3× display beside `mark-mask-256.png`, the shipped master is
   clearly blurred where the 256 is crisp. Even the default `size={34}` is
   68–102 device px from a 64 px source. `assets/logo/mark-mask-256.png`
   already exists; copying it into `web/public/` and pointing the component at
   it is a two-line fix, and `#0017` is the first real consumer.
2. **`site.webmanifest` has no 192×192 icon** (it ships 256 and 512).
   Chromium's installability heuristics have historically wanted a 192 px
   entry. Worth adding when PWA install is actually a goal.
3. `favicon-32.png` is the transparent `mark-green-32.png`, so it shows a
   faint warm fringe where its antialiased edge composites onto a near-black
   tab strip. The SVG favicon is cleaner and is listed first, so this only
   affects browsers without SVG favicon support. Cosmetic.
