## Description

`#0320` added a content digest so an in-place migration edit is no longer
invisible. Its review verified the mechanism thoroughly — fail-closed on every
malformed `shasum` output, safe under every stray-file shape tested, digest
reproduced across four locales and from a different absolute path. Three
residuals, none of them a defect today.

### 1. `template_digest` costs two extra `psql` round trips

`#0320`'s reviewer measured `create` at **0.182s** before and **0.243s** after —
criterion 6 met, but the margin is thin, and **only 0.017s of the +0.061s is the
digest itself**. About 0.04s is two extra `psql` invocations, because
`template_digest()` re-runs a `db_exists` check that `template_version()` already
did, then opens a second connection.

Reading version and digest in one query recovers most of it.

### 2. The `pg_shdescription` join is under-qualified

It lacks `and ds.classoid = 'pg_database'::regclass`. That catalog is keyed
`(objoid, classoid)` and also holds role and tablespace comments, so an OID
collision across catalogs could match the wrong row. Fails safe today — a wrong
digest routes to provisioning — but it is one clause.

### 3. `find | sort | xargs cat` is not NUL-delimited

A migration filename containing a space or a quote breaks `xargs`. The reviewer
tested it: the digest comes back empty, `valid_digest` catches it, and `create`
falls back to provisioning with `xargs: unterminated quote` on stderr. **Fails
safe**, and no such filename exists or is likely. `find -print0 | sort -z |
xargs -0 cat` closes it.

## An operational note that is not an acceptance criterion

The shared `opencircuit_test_template` **predates `b0aa902`**, so it carries no
digest comment and `template_digest` returns `none`. **Every `create` on this
tree currently mismatches and takes the ~0.26s direct-provision path.** It
self-heals the moment someone runs `scripts/testdb.sh template` explicitly, at a
quiet moment. That is expected transitional behaviour, not a defect — but it is
also exactly what made an observer conclude the template was being rebuilt
implicitly (it was not; `#0320`'s reviewer disproved that three ways).

## Acceptance criteria

1. `template_version` and `template_digest` share one `psql` invocation and one
   existence check. Re-measure `create` and report the number; the target is
   recovering most of the ~0.04s.
2. The `pg_shdescription` join is qualified by `classoid`.
3. The digest pipeline is NUL-delimited end to end.
4. **None of these may weaken the fail-closed behaviour** `#0320`'s review
   verified: empty, non-hex, short, and uppercase `shasum` output must each still

5. Every stray-file case still fails **toward** provisioning, never toward a

6. `ISSUE=NNNN scripts/check.sh guards` passes, run at least twice.

## Fix

**1 — one `psql` invocation.** `template_version()` and `template_digest()`
each opened their own connection and re-ran their own `db_exists()` probe.
Replaced with `template_state()`: one `psql` connection to `$TEMPLATE`
itself, one query selecting both the migration version (from
`schema_migrations`, which lives in the template) and the digest comment
(from `pg_shdescription`/`pg_database` — shared catalogs visible from any
database in the cluster, so no second connection into `postgres` is needed)
concatenated with an ASCII US (`chr(31)`) separator that cannot appear in
either a version number or a hex digest. No up-front existence check: a
nonexistent template simply fails to connect, and an empty result routes to
`"none"`/`"none"` the same as an explicit check would. `template_version()`
and `template_digest()` are now thin wrappers over `template_state()` (kept
for `warn_template_mismatch()`'s messaging, which only needs the version);
`template_matches_disk()` — the one call on `create`'s hot path — calls
`template_state()` directly once, not through the two wrappers, so it costs
exactly one `psql` invocation.

**2 — qualified join.** `template_state()`'s `pg_shdescription` join now
reads `... on ds.objoid = db.oid and ds.classoid = 'pg_database'::regclass
where db.datname = current_database()`, closing the OID-collision-across-
catalogs gap #0320's review flagged.

**3 — NUL-delimited pipeline.** `disk_digest()` now enumerates via `find
-print0`, collects names through a `while IFS= read -r -d ''` loop (a bash
builtin, no per-file fork — this shell is 3.2.57, no `mapfile`/`readarray`
to build an array from a NUL stream directly) into an array, sorts that
array (safe to do newline-delimited — no migration filename contains a
newline, a different hazard than the one this criterion is about), and
feeds file contents to `xargs -0 cat` over a NUL-delimited stream. A
filename with a space or a quote — the case that used to abort `xargs`
with "unterminated quote" and fall back to provisioning — is now digested
correctly instead of merely failing safe.

## Gotchas

**These two issues' code landed in a single commit (`34147d4`), titled only
for `#0327`, despite being implemented and staged as two deliberately
separate commits.** Recording this in full because it's a previously-
undocumented git hazard, not specific to either issue:

I split the accumulated `scripts/testdb.sh` diff into two hunk-groups with
`git apply --cached <patch>` (verified via `git diff --cached` immediately
before committing that only the intended hunks were staged — confirmed
correct), then ran `git commit -F - -- scripts/testdb.sh
scripts/testdb_gc_guard_test.sh <<'EOF' ... EOF`. **Passing a pathspec to
`git commit` does not commit what's staged for those paths — it commits
their current WORKING TREE content**, silently overriding the index. Since
the working tree still had *both* issues' unstaged hunks at that point (I
hadn't run `git add` on the remainder yet), the commit captured all of it,
not just the staged #0327 hunks. `git show --stat HEAD` immediately after
showed the full diff size for `scripts/testdb.sh`, which is what caught it.

**Recovery**: nothing was lost, but it happened concurrently with another
agent's commit (`#0322`, `0b781f2`) landing on top of mine. `git reset
--soft HEAD~1` was the wrong first move — I hadn't checked what `HEAD`
actually pointed to first, and it undid the *other* agent's commit (moved
the branch pointer from their `0b781f2` back to my `34147d4`, its parent),
not mine. Caught immediately from `git log --oneline` (their commit was
sitting right there as the prior `HEAD`) and fixed with `git reset --soft
0b781f2` — a second `--soft` reset, safe because it only moves a ref and
touches neither the index nor the working tree, restoring the branch to
exactly where it was. Verified with `git log --oneline` and `git status
--porcelain` before touching anything else. No file content was ever at
risk (`--soft` never discards anything); the risk was purely to the other
agent's commit's *reachability*, and it was restored within the same
sequence of commands, before any new commit could have stranded it.

Left the merged commit as-is rather than rebasing it apart from under
`0b781f2` — CLAUDE.md §8a is explicit that rewriting history under a
commit another agent has already built on is exactly the hazard to avoid,
even via `--soft`. The commit's actual diff is complete and correct for
both issues (verified: `git diff 34147d4 -- scripts/testdb.sh
scripts/testdb_gc_guard_test.sh` is empty), so no functionality is missing
— only the commit message's subject line under-names it, corrected by
recording `34147d4` as the **Commit** on both issue files with an
explanation on each.

**Recommend filing**: this `git commit -- <pathspec>` behavior (staged
index silently overridden by working-tree content for the named paths) as
a new `CLAUDE.md` §8a gotcha, alongside the existing `git commit --
<paths> -m "<msg>"` pathspec-swallows-`-m` entry (`#0268`) — both are
"the `--` pathspec form of `git commit` does something other than the
obvious thing" traps.

### Finding A — latent, not live: `template_state()` can kill the script silently

`#0328` removed the explicit `db_exists "$TEMPLATE" || { echo "none"; return; }`
guard and the `|| echo "none"` fallback, so `row="$(psql "$PGHOST_URL/$TEMPLATE"
…)"` is now an unguarded failing assignment when the template does not exist
(psql exits 2). Under `set -euo pipefail` a **direct** call therefore aborts the
shell with no output — I reproduced exactly that by sourcing the function
definitions and calling `template_state` with a nonexistent `$TEMPLATE`.

It does **not** bite today, and I confirmed that end to end:
`TEMPLATE_DB=…_nope scripts/testdb.sh create 0327a` still prints the friendly
"template … does not exist yet — provisioning … directly" message and provisions
all 25 migrations, exit 0. It survives for two reasons, both incidental:
`template_matches_disk` calls `template_state` bare but is itself only ever
invoked as an `if` condition (which suspends `set -e` through the whole call),
and `warn_template_mismatch`'s `tv="$(template_version)"` is protected by a
bash 3.2 quirk I verified in isolation — `row="$(exit 2)"` inside a function
aborts when that function is called directly, but **not** when it is reached from
inside a command substitution.

So the "no up-front existence probe is needed" reasoning in the code comment is
correct about the *result* and wrong about the *mechanism*: the `"none"` fallback
lines are reached by luck of call-site shape, not by the function's own control
flow. The next call site that invokes `template_state` (or an unconditioned
`template_matches_disk`) in ordinary flow gets a silent death. One-token fix:
`… 2>/dev/null || true)`. Recommended as a follow-up rather than a bounce, since
no current path reaches it.
