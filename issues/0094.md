## Description

No test in the repository imports a `.svelte` file. There is no jsdom or happy-dom, no
`@testing-library/svelte`, and no component harness. The house convention — logic in
plain TypeScript under `web/src/lib/`, components kept thin — is what makes this
tolerable, and it is a good convention. But it leaves the wiring *between* a tested
function and its template completely uncovered.

`#0090`'s review demonstrated the gap concretely. It deleted the entire `{#if}` wrapper
that suppresses the fake "Subscribe again" button for complained subscribers —
restoring the exact dead end `#0090` was filed to fix — and **all 152 tests stayed
green**. Only mutating `subscribe.ts` fails anything.

This is not held against `#0090`: that fix followed the house convention exactly, and
its pure-function half is properly mutation-proven. The exposure is project-wide.

## Implementation notes

**What existed vs. what was missing.** `web/` already ran Vitest and several tests
(`modalEscapeGuard.test.ts`, `CampaignSendDialog.structuralGuard.test.ts`,
`citationGuard.test.ts`) parsed `.svelte` source with `svelte/compiler`'s `parse()` —
so the gap was never "no test runner." It was that nothing imported a `.svelte` file as
a *component*: no DOM environment (no `jsdom`/`happy-dom` dependency at all), no
`@testing-library/svelte`, and `vite.config.ts` had no `test` block. Every existing
`.svelte`-adjacent test proves its claim either by walking the component's own AST or
by re-deriving its formulas side by side in plain TypeScript — never by mounting the
component and driving it.

**Harness chosen: `@testing-library/svelte@5.4.2` + `jsdom@30.0.1`**, scoped per test
file with a `// @vitest-environment jsdom` docblock rather than switching Vitest's
global `test.environment` — the other 25 existing test files stay on the fast default
(no environment = effectively synchronous), and only files that opt in pay jsdom's
setup cost.

Rejected Vitest browser mode: heavier install (a real browser binary + a
Playwright/WebDriver provider) and heavier CI weight, for no answer to the decisive
question that jsdom couldn't also give directly — see below.

One resolution wrinkle, not obvious in advance: Vite's default module resolution
handed `@testing-library/svelte`'s `render()` Svelte's **server** build even though the
test ran under `jsdom`, so the first attempt failed with `Svelte error:
lifecycle_function_unavailable — mount(...) is not available on the server` (`render()`
calls Svelte's client `mount()`). Fixed by adding `resolve: { conditions: ['browser'] }`
to `vite.config.ts`, gated on `process.env.VITEST` so `vite build`/`vite dev` are
untouched.

**Runes/`$effect` evidence — the decisive question.** `CampaignSendDialog.svelte`'s
`$effect(() => { void tick().then(() => dialogEl?.focus()); })` is the exact
`tick()`-then-`focus()` shape `#0120`/`#0047 §8` established and several deferred
verifications depend on. Under jsdom + `@testing-library/svelte`, `document
.activeElement` reliably became the dialog panel after `waitFor()`, across every test
in the new file. `$derived` also verifiably ran real component logic, not a stub: the
"does NOT close while sending" test only passes because `sending = $derived(guard.kind
=== 'sending')` actually evaluates `sendGuardState({ inFlight: true, ... })` — a stub
or no-op derived would have left the assertion vacuously true or false at random.

**Deferred verification proved.** `#0120`'s claim ("Escape closes the modal") was
proven on `CampaignSendDialog.svelte` — `#0120`'s own fix site where the panel's
`onkeydown` was **deleted outright** (rather than rewritten to call `isModalEscape`,
the shape the other five sites use), letting the keydown bubble to the backdrop's
pre-existing `handleKeydown`. New file:
`web/src/views/admin/CampaignSendDialog.behavior.test.ts` — mounts the real component,
waits for the real `tick()`-then-`focus()` effect to move focus into the dialog panel,
dispatches a real bubbling DOM `keydown` event with `key: 'Escape'`, and asserts
`onClose` fires; a parallel case with `inFlight: true` asserts it does **not** fire
(the `#0195` sending-wins-over-Escape rule); a third asserts a non-Escape key is a
no-op.

**Mutation-proved, not just written and trusted.** Temporarily reintroduced the exact
pre-`#0120` regression — `onkeydown={(e) => e.stopPropagation()}` on the panel — and
reran the new test file: 2 of 5 tests failed (0 calls where 2 were expected). Reverted
immediately (`git diff` on `CampaignSendDialog.svelte` is clean).

**A genuine finding, only visible by mounting, not by inspection.** Because
`handleKeydown` is bound to *both* the backdrop's and the panel's `onkeydown` (same
function reference, and nothing in the file calls `stopPropagation` in the keydown
path — deliberate, per that component's own doc comment), a real Escape keypress on
the focused panel bubbles and fires `handleKeydown` **twice**, so `onClose()` is
called twice per Escape. This is real production behavior (confirmed: DOM `keydown`
bubbles by default, and `fireEvent.keyDown` dispatches with `bubbles: true`), not a
jsdom artifact. Harmless today — closing an already-closing dialog is idempotent from
`CampaignEditor.svelte`'s side — but it was previously unverified by anything, AST or
otherwise, and would matter if `onClose` ever grew a non-idempotent side effect (e.g.
an audit-log write keyed on the close action). **Worth a follow-up issue**; not fixed
here since #0094 is test infrastructure, not a behavior change, and the double-fire is
currently harmless.

**What this harness does NOT establish.** `jsdom` is not a browser. Its focus, layout,
and `aria` semantics are approximations — real layout/visibility, IME composition, and
some focus-order edge cases are not modeled faithfully. A passing test here is weaker
evidence than a real-browser test (Vitest browser mode / Playwright) would be. It DOES
faithfully establish that Svelte 5 runes (`$state`/`$derived`/`$effect`) execute
correctly under it, that DOM event bubbling and `document.activeElement` tracking work
as modeled, and that the `tick()`-then-`focus()` pattern several deferred
verifications need is reproducible outside a real browser.

**Guards not removed.** `modalEscapeGuard.test.ts`, `modalKeydown.test.ts`,
`CampaignSendDialog.structuralGuard.test.ts`, `CampaignSendDialog.guard.test.ts`, and
`citationGuard.test.ts` are all unchanged. They catch a different class of drift (a
component's AST shape vs. what a test claims about it, repo-wide) that one
props-fixed behavioral test does not replace — e.g. a *different* future modal built
by copying old markup would trip the AST guard immediately but is not covered by this
one behavioral test until someone deliberately extends coverage to it.

**Newly-testable surface, left for follow-up issues:** `Admin.svelte`'s five modals,
`CampaignEditor.svelte`'s modal, `Campaigns.svelte`'s "New campaign" modal (note: its
`onMount` calls `listCampaigns()` over the network — mounting it under jsdom will need
either a mocked `fetch` or accepting the `loadError` catch path), `WorkshopEditor
.svelte` / `Workshops.svelte`'s pre-`#0120` modals, and `#0090`'s original `{#if}`
wrapper suppressing the "Subscribe again" button for complained subscribers — the
issue's own originally-named first case, still untested by a mounted component.

**Install and run-time cost.** Two new direct `devDependencies`
(`@testing-library/svelte@5.4.2`, `jsdom@30.0.1`), 53 packages added transitively,
~11.6MB added to `node_modules` (`jsdom` 8.3M + `@testing-library` 3.3M, measured
directly; `package-lock.json` diff is +722 lines, purely additive). All
`devDependencies` — no effect on `web/dist` or the production bundle; nothing here is
reachable from any app entry point, so PRD §7.6's performance budget is unaffected.
Run time: `npm test` went from 25 files / 3744 tests / 1.03s to 26 files / 3749 tests /
1.16s — about 130ms slower, of which Vitest's own reporting attributes ~270ms to
environment setup (jsdom only spins up for the one file that opts in via the
`// @vitest-environment jsdom` pragma; the other 25 files keep running under the fast
default). Small next to `#0207`'s ~48s `dev_guard_test.sh` benchmark, and it will grow
roughly linearly as more component tests are added — worth watching once several more
land.
