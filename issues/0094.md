# 0094 — Svelte components have no test infrastructure, so conditional rendering is unverifiable

## Description

No test in the repository imports a `.svelte` file. There is no jsdom or happy-dom, no
`@testing-library/svelte`, and no component harness. The house convention — logic in
plain TypeScript under `web/src/lib/`, components kept thin — is what makes this
tolerable, and it is a good convention. But it leaves the wiring *between* a tested
function and its template completely uncovered.

`#0090`'s review demonstrated the gap concretely. It deleted the entire `{#if}` wrapper
that suppresses the fake "Subscribe again" button for complained subscribers —
restoring the exact dead end `#0090` was filed to fix — and **all 152 tests stayed
green**. Only mutating `subscribe.ts` fails anything.

This is not held against `#0090`: that fix followed the house convention exactly, and
its pure-function half is properly mutation-proven. The exposure is project-wide.

## Acceptance criteria

- [ ] Decide explicitly whether component tests are wanted, and record the decision —
      "no, and here is why the pure-function convention is sufficient" is a legitimate
      outcome and should be written down rather than left implicit
- [ ] If yes: add a DOM environment and component-testing library, wired into the
      existing `npm test` run
- [ ] If yes: cover the conditional renders that gate user-visible affordances, with
      `#0090`'s `{#if}` wrapper as the first case — deleting the wrapper must fail a test
- [ ] If yes: the performance budget in PRD §7.6 is unaffected (test-only dependencies)

## Notes

Found during `#0090`'s review, by mutation rather than by inspection.

The cost is real and so is the gap; this issue exists to force the choice, not to
presume the answer. Worth weighing against how many user-visible affordances are
currently gated by an untested `{#if}` — that count is the actual input to the decision.
