## Description

`#0304` set `claimKindsGuardMinPlausibleNonExemptCallSiteCount = 6` against 12
non-exempt `ClaimDue`/`OrphanSweep` call sites. `#0304`'s review measured which
narrowings that floor actually catches:

| Narrowing | Sites left | Caught by floor 6? |
|---|---|---|
| `{"."}` | 0 | yes |
| `cmd` only | 0 | yes |
| `internal/handlers` only | 5 | yes |
| worst single file | 3 | yes |
| **`internal/mailing` only** | **7** | **no** |

**The one that evades it is the one that matters most.** A `mailing`-only
narrowing drops `internal/handlers/subscribe_intake.go` — the production caller
the guard most exists for, since `#0254`'s duplicate-send defect came from an
unscoped sweep on exactly that path.

A floor of **8** closes it (`8 > 7`, `8 <= 12`).

## The trade-off to weigh

`#0275`'s failure mode is the opposite one: a floor set **above** its population
makes the guard impossible to pass, and that issue had to lower a floor from 150
to 80 for precisely that reason.

At 8 against 12 there are 4 sites of shrink headroom. Note that **3 of the 12 are
`mailing.SendStore`'s unrelated same-named `OrphanSweep`** — a rename or a
refactor removing those would leave 9, still above 8 but with only 1 to spare.

So this is a judgement, not an arithmetic result. Make it deliberately.

## Acceptance criteria

1. Decide the floor and **record the package-granularity table above** as its
   justification, re-measured rather than copied from this issue.
2. Whatever number is chosen, state in the comment which narrowings it catches
   and which it does not. A floor that silently fails to catch the
   `subscribe_intake.go`-dropping case must say so.
3. Weigh the `#0275` failure mode explicitly: how much shrink headroom remains,
   and what happens if `mailing.SendStore`'s `OrphanSweep` is renamed.
4. If the answer is that a count-based floor cannot catch this case robustly,
   say so and propose what would — for instance asserting that specific known
   production call sites are present, which is a different and stronger check
   than counting.
5. `#0321` is open on the same section's comments; sequence the two rather than
   editing the same lines twice.
6. `ISSUE=NNNN scripts/check.sh go ./internal/outbox/...` and
   `scripts/check.sh guards` pass, the latter run at least twice.

this issue's changes are entirely in
`internal/outbox/claim_kinds_call_site_guard_test.go`, a different file, so

Re-measured the package-granularity table (criterion 1) from scratch this
session, via a throwaway `internal/outbox/zzz_scratch_count_test.go` that
called the guard's own `walkClaimKindsGuardFiles`/`findOutboxCallSitesInFile`
directly (deleted before anything was committed, `git status --porcelain`
confirmed empty): **12** non-exempt sites today, unchanged from `#0304`/the
issue's own figures — `internal/handlers` 5
(`subscribe_intake.go` x2, `admin_dashboard_test.go` x2,
`admin_pending_test.go` x1), `internal/mailing` 7 (`outbox_worker.go` x2,
`worker.go` x1, `worker_store_test.go` x3 — `mailing.SendStore`'s unrelated
same-named `OrphanSweep`, `outbox_worker_test.go` x1).

**Decision: raised `claimKindsGuardMinPlausibleNonExemptCallSiteCount` from
6 to 8** (criterion 1). Rewrote its doc comment in
`internal/outbox/claim_kinds_call_site_guard_test.go` to carry:

- The package-granularity table above, re-measured.
- Which narrowings 8 catches (criterion 2): `{"."}` (0), `cmd` only (0),
  `internal/handlers` only (5), worst single file (3), and now
  **`internal/mailing` only (7)** — the one 6 missed, and the one that
  matters, since it drops `subscribe_intake.go`, the production caller
  `#0254`'s duplicate-send defect came from. All five re-verified against 8
  rather than assumed from the issue's own table.
- The `#0275` trade-off, weighed explicitly (criterion 3): 8 against 12
  leaves 4 sites of headroom. 3 of the 12 are `mailing.SendStore`'s
  unrelated same-named `OrphanSweep` (counted only because the guard
  matches call sites by method name, not by declaring type — see
  `nameMatchesGuardedMethod`'s doc comment); a rename or removal of that
  unrelated method would drop the population to 9, leaving only 1 site of
  headroom before 8 becomes unsatisfiable. Accepted deliberately: that risk
  is visible (a loud, permanent `go test` failure) rather than the silent
  underprotection 6 left in place, and it is not today's state.
- Criterion 4 — stated plainly that a count-based floor cannot close this
  robustly **in general** (it is blind to WHICH sites it counted, so a
  narrowing that coincidentally preserves >= floor non-exempt sites, none
  of them `subscribe_intake.go`, still passes), and proposed the stronger
  alternative without building it: assert specific known production call
  sites — starting with `subscribe_intake.go`'s two — are present, which is
  a presence check rather than a count and so cannot be fooled the same
  way. Left as a documented recommendation (reported below, per CLAUDE.md
  §9), not implemented — out of this issue's scope, which was the floor's
  value and its justification, not a rework of the guard's shape.

No change to `scripts/go_file_visit_floor_guard_test.sh` — it reads the
constant dynamically via `extract_const` and computes populations
independently via `grep`, so it needed no edit for the value change alone
(re-confirmed by both scoped verification runs below reporting the new
floor of 8 against the same externally-measured population of 12).

## Recommendation reported, not filed (CLAUDE.md §9)

**A count-based floor cannot robustly guarantee the specific
`subscribe_intake.go` call sites survive a narrowing.** Consider a stronger
guard that asserts specific known production call sites (starting with
`internal/handlers/subscribe_intake.go`'s two `ClaimDue`/`OrphanSweep`
calls) are present in the non-exempt population, rather than only counting
them. This is a presence check, not a count, so it cannot be defeated by a
narrowing that happens to leave enough OTHER non-exempt sites standing.
Rationale: acceptance criterion 4 above; not built here because it is a
change to the guard's shape, out of this issue's scope (the floor's value).
