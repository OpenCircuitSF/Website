## Description

`#0238` shipped a route-change effect that sets `document.title` and moves focus
to the view's `<h1>`. Its first pass also silently destroyed back/forward scroll
restoration, because `focus()` defaults to `preventScroll: false`:

| after Back | `window.scrollY` | `history.state.scrollY` |
|---|---|---|
| before `#0238` | 1200 | 1200 |
| after `#0238`'s first pass | **0** | **0** |

The `history.state` column is what made it more than cosmetic — the throttled
scroll listener stamped the bogus `0` into the history entry, so the damage
outlived the moment.

**Title and focus were green the whole time.** The two properties that were
silently wrong are exactly the two nothing checked.

`#0238`'s fix added `appNavigationFocus.structuralGuard.test.ts`, an AST guard
asserting the call site carries `{ preventScroll: true }`. Its review judged that
adequate for *this* defect — the runtime behaviour is fully determined by one
boolean at one call site, so the source invariant is a tight proxy rather than a
loose statement of intent.

**But the guard covers the call site, not the property.** "Back/forward restores
the user's scroll position" is a system property. A future `scrollIntoView`, a
smooth-scroll behaviour, a second focus move in a child component during a route
change, or a change to `router.ts`'s restore timing would all break it with that
call site untouched — which is precisely the class of thing that cost `#0238` a
bounce.

**jsdom cannot evidence any of this.** Measured, not assumed: on a 5000px-tall
jsdom document, `h1.focus()` with the default leaves `window.scrollY` at `0` —
identical to `focus({ preventScroll: true })`. Zero evidence, not weak evidence.

## The cost argument

**Four passes have now each hand-rolled the same throwaway rig and thrown it
away**: `#0063`, `#0244`, and `#0238` twice. Each built a production bundle in a
worktree, stood up a stub server on a private port, verified the bundle hash from
`document.scripts` before trusting a response, and drove real Safari via
`safaridriver`. That is the harness this issue asks to keep.

This repo has no browser test infrastructure at all. Standing one up is a project
capability rather than a line item inside an accessibility polish issue, which is
why it was not folded into `#0238`.

## Acceptance criteria

1. A repeatable check builds the SPA, serves it on a port it verifies it owns
   (CLAUDE.md §8b — a `curl` that succeeds is not evidence the *right* server
   answered; confirm a build-specific detail such as the hashed bundle filename
   from the page itself), and drives a real browser.
2. It asserts, across **all three** navigation paths — a link click, a
   programmatic `navigate()`, and a `popstate` — every one of:
   - `document.title`
   - `document.activeElement` identity
   - `window.scrollY`
   - `history.state.scrollY`
   The last two are the pair that were silently wrong while the first two were
   green. Do not drop them as awkward to assert.
3. It is runnable by one command and does not bind a fixed shared port (§8b:
   agents run concurrently, and a fixed port has already had one agent verify
   against another's server).
4. It is **not** added to `scripts/check.sh`'s default `web` scope if it is slow.
   Follow the `scripts/check.sh guards` precedent — a separate target, because
   `dev_guard_test.sh` alone costs ~48s and binds `:5173`.
5. Whether it uses `safaridriver` or Playwright is the implementer's call.
   Record the choice and what it costs to install, since the next agent has to
   run it.
6. It cleans up after itself: no server left listening, no worktree left behind
   (§8b).
7. `#0238`'s existing AST guard stays. The two are complementary — one pins the
   call site, this pins the property.

## Work log

**Criterion 5 — tool choice: `safaridriver`, not Playwright.** Recorded as
asked, with the cost actually measured rather than assumed. `safaridriver`
(`/System/Cryptexes/App/usr/bin/safaridriver`, Safari 26.6.2) needed **no
install and no `sudo`**: `safaridriver -p <port>` came up immediately and
`POST /session` succeeded against a plain `open -a Safari`, with no
`safaridriver --enable` step and no manual "Allow Remote Automation" toggle
— `defaults read com.apple.Safari AllowRemoteAutomation` shows that key is
not even set on this machine, so whatever authorizes it is already in place
some other way. The one real gotcha, also recorded in the script's own
header: the very first session request timed out ("Could not create a
session... waiting for its RWIApplication to appear") because Safari.app
was not running yet; `open -a Safari` before starting `safaridriver` (a
no-op if it is already open) fixed it, and the script now does this itself.
Total cost: $0, zero new files, zero new dependencies. Playwright is **not**
a `web/package.json` dependency today (only `jsdom` + `vitest` are); adding
it would mean a new devDependency plus whatever `npx playwright install`
needs beyond the chromium/ffmpeg builds already cached under
`~/Library/Caches/ms-playwright`, for browser diversity this issue does not
ask for. `safaridriver` is also what all four prior throwaway rigs this
issue exists to stop re-hand-rolling used (`#0063`, `#0244`, `#0238` x2), so
it is the already-proven path in this exact codebase.

**Build strategy — deliberately not a `git worktree`.**
`scripts/browser_nav_guard_test.sh` `rsync`s `web/` (minus `node_modules`
and `dist`) into a fresh `mktemp -d`, symlinks `node_modules` from the real
checkout (the same shortcut the four prior rigs used, rather than a fresh
`npm install`), and runs `npm run build` there. Two reasons this beats a
`git worktree`: (1) it picks up the CURRENT working tree, including
uncommitted edits — an implementer who just edited `App.svelte` gets THAT
edit tested, not last commit's, which a worktree checked out at `HEAD`
would silently miss; (2) it sidesteps the git-worktree-cleanup risk class
entirely (CLAUDE.md §8a/§8b, and `#0399`'s note that a stray
`.claude/worktrees/` copy makes `internal/handlers`'s path-citation guard
fail open) — there is no worktree to forget to remove, because none is ever
created. Confirmed: `git worktree list` before and after every run shown
below is unchanged (only the two pre-existing worktrees belonging to other
sessions).

**Ports (criteria 1, 3).** Both the stub server and `safaridriver` bind a
per-run port pair derived from `${ISSUE:-$$}`, verified free via `lsof`
first, with the same collision-retry shape `scripts/dev_guard_test.sh`'s
`pick_pbase()` uses (`#0253`/`#0259`) — range `20000..39900`, below macOS's
ephemeral-port floor and clear of the real listeners `#0259` found
occupying the old range on this machine. Verified live: a long-lived,
unrelated `python -m http.server` on `:39181` (6+ days uptime, not started
by this session) sat inside that range throughout, and every run below
picked a different pair without incident.

**Server-ownership check (criterion 1).** Not a bare `curl` — the exact
hashed bundle filename this run's own `npm run build` just produced
(`assets/index-<hash>.js`, read from the freshly-built `dist/index.html`)
is asserted present in `document.scripts` **inside the actual browser
page**, matching CLAUDE.md §8b's "confirm a build-specific detail... before
trusting a single byte of it." Proved discriminating, not just present: two
consecutive runs against source differing only in `App.svelte`'s one line
produced two different hashes (`index-Dc5mMUC_.js` vs `index-BUOeae_4.js`),
and each run's own check passed against its own hash.

**Cleanup (criterion 6).** The `EXIT`/`INT`/`TERM` trap deletes the
WebDriver session, then kills `safaridriver` and the stub server **by the
pids the script itself recorded** when it started them (`$!` captured
immediately after each background launch) — never a pattern-matched
`pkill -f`, per CLAUDE.md §5a's record of that reaching past its own
process twice. `scripts/check.sh browser-nav`'s own "leftover processes you
may have started" audit reported `(none)` after every run below. Safari.app
itself is left running — quitting a real user's browser is not this
script's business, and the machine this ran on has one.

**Proof the harness actually catches the `#0238` regression, not just that
it can pass.** With the fix in place (`heading?.focus({ preventScroll: true
})`, current `App.svelte`), all 17 assertions across the three paths pass.
`web/src/App.svelte`'s focus call was then temporarily edited back to the
bare `heading?.focus()` `#0238`'s review found defective (backed up first —
`shasum -a 256` recorded before and after, restore confirmed byte-identical
and `git status --porcelain -- web/src/App.svelte` clean afterward — no
commit ever carried the mutation), and the same script re-run against that
regressed source:

| Assertion | Fixed source | Regressed source (`heading?.focus()`, no options) |
|---|---|---|
| `document.title` after Back | `Privacy Policy — Open Circuit SF` (PASS) | `Privacy Policy — Open Circuit SF` (PASS) |
| `document.activeElement` after Back | `H1` "Privacy Policy" (PASS) | `H1` "Privacy Policy" (PASS) |
| `window.scrollY` after Back | `1200` (PASS) | `0` (**FAIL** — expected 1200) |
| `history.state.scrollY` after Back | `1200` (PASS) | `0` (**FAIL** — expected 1200) |

This is exactly the shape `#0238`'s review measured in real Safari — title

The regressed build's own bundle hash (`index-BUOeae_4.js`, different from
the fixed build's `index-Dc5mMUC_.js`) confirms the two runs genuinely
