## Description

The landing page every social link points at: a terminal hero block, a short statement of what Open Circuit SF is, the next few workshops, and an inline subscribe form.

## Acceptance criteria

- [x] Hero `TerminalPanel` composing `Prompt` (`> open_circuit // san_francisco`), a heavy uppercase display headline, a `StatusList`, and a `CommandLine`
- [x] A short section stating what the group is and that workshops run at varied locations including neighborhood garages
- [x] "Next up" section rendering up to three upcoming workshops (a static placeholder until #0053 provides the API)
- [x] Inline `SubscribeForm` placeholder region wired in #0029
- [x] Single `<h1>`; semantic `<header>`/`<main>`/`<footer>` landmarks
- [x] Renders correctly at 375 px through 1440 px with no horizontal page scroll
- [x] LCP under 2.0 s on a simulated 4G profile
- [x] No mention of Sequoia Fabrica or any other venue as an affiliation

## Root cause

Feature build, not a bug fix — the landing page every social link points at
didn't exist yet.

## Fix

`web/src/views/Home.svelte`: a `TerminalPanel` hero (`title="open_circuit_sf"`)
composing `Prompt text="open_circuit // san_francisco"`, an `<h1
class="headline">` (`font-weight: 800`, `text-transform: uppercase`,
`clamp(28px, 7vw, 52px)` so it scales from phone to desktop without ever
forcing horizontal scroll), a four-item `StatusList`, and `CommandLine
command="opencircuitsf.com"`. Below the hero: a "What this is" section (two
paragraphs, adapted from `placeholder/index.html`'s already-validated copy,
including its exact venue-independence framing), a "Next up" section
rendering three static `Panel`-wrapped workshop placeholders (`UPCOMING`
array, deliberately generic — no invented dates/locations that could be
mistaken for a real scheduled event), and a "Stay in the loop" section
holding the `SubscribeForm` placeholder region for `#0029`. `TraceDivider`
separates each section per the motif set.

`App.svelte`'s public-marketing branch now renders `<Home />` (inside
`#0017`'s `<Header />`) when `$currentRoute.name === 'home'`; every other
public route still falls through to the interim one-line placeholder.

The `<main id="main-content">` landmark and the single `<h1>` live in
`Home.svelte` itself; `<header>` (`#0017`'s `Header.svelte`) and `<footer>`
(`Footer.svelte`) are provided by the surrounding shell in `App.svelte`, so
together the rendered page has all three landmarks exactly once each (see
Verification for how the four `<header>` DOM elements — one real page banner
plus three decorative `Panel` card headers — resolve to a single ARIA banner
landmark).

## Verification

```
cd web && npm run check 2>&1 | tail -20   # svelte-check: 185 files, 0 errors, 0 warnings
npm test 2>&1 | tail -20                  # vitest: 7 files, 103 tests (unchanged -- no new pure logic to unit test here)
npm run build 2>&1 | tail -10             # vite build: 151 modules, succeeded
cd .. && go build ./... && go test ./... -count=1   # unaffected; all `ok` with TEST_DATABASE_URL exported
```

This view is markup/copy/layout, not logic — there is nothing here a Vitest
unit test can meaningfully cover (no new exported pure function), so
verification for the visual/layout/performance acceptance criteria was done
with a live Playwright render against the **production build** (`npm run
build` + `vite preview`, not the `vite` dev server — the dev server's
unbundled ES-module waterfall makes any LCP measurement against it
meaningless; this was caught mid-verification: an initial dev-server LCP
measurement read 6.1s, which looked like a real budget failure until
re-measuring against `vite preview`'s actual production bundle gave 752ms).

**What was verified by rendering, with the exact checks and results:**

- **No horizontal scroll** at 375/480/768/1024/1440px:
  `document.documentElement.scrollWidth === clientWidth` at every width
  tested.
- **Single `<h1>`**: `document.querySelectorAll('h1').length === 1`, text
  "Hands-on electronics workshops".
- **Landmark count**: exactly one `<main>`, one `<footer>`, and — despite four
  `<header>` elements in the DOM — exactly one that maps to the ARIA
  `banner` landmark. Checked by walking each `<header>`'s ancestor chain for
  `article`/`aside`/`main`/`nav`/`section` (the HTML-AAM rule that demotes a
  `<header>` to `role="generic"` once it's inside sectioning content): the
  page's real `<header class="site-header">` has no such ancestor and is the
  one true banner; the three `Panel.svelte` card headers (`"Soldering
  fundamentals"`, etc.) are all inside `<section class="next-up">` and
  correctly carry no landmark role.
- **No venue mention**: `document.body.innerText` searched case-insensitively
  for "sequoia fabrica" — no match. (This is a substring check on the
  rendered text, not a semantic read of the copy; a human read of the two
  "What this is" paragraphs during authoring is what actually confirms the
  positioning is venue-independent, not this regex.)
- **LCP under 2.0s on 4G**: measured via a real `PerformanceObserver`
  (`largest-contentful-paint`, `buffered: true`) in-page, against the
  production build, under `Network.emulateNetworkConditions` (150ms RTT,
  1.6 Mbps down / 750 Kbps up — Lighthouse's own "Slow 4G" mobile-throttling
  profile) and `Emulation.setCPUThrottlingRate({ rate: 4 })` (Lighthouse's
  default mobile CPU slowdown). Result: **752ms**, well under the 2.0s
  budget.

Screenshots at 375px and 1440px were inspected during this pass (not
committed — ephemeral verification artifacts) and confirmed the layout reads
correctly: hero panel, status list, next-up cards in a responsive
`auto-fit` grid, subscribe placeholder, all readable at both extremes.

**Not verified at all**: real 4G on a physical device (only CDP network/CPU
emulation), and a Lighthouse/axe automated accessibility pass (that's
`#0063`'s job per this issue's `Blocks` relation).

## Gotchas

The dev-server-vs-production-build LCP discrepancy above (6.1s vs. 752ms) is
worth flagging for whoever verifies performance budgets on later views
(`#0053`, `#0054`, etc.): `./scripts/dev.sh` / `npm run dev` serve unbundled
ES modules with many small requests, which is realistic for *development*
but not for *measuring* the performance budget. Always measure against `npm
run build` + `vite preview`.

Same `web/dist/index.html` placeholder-restoration step as `#0014`/`#0017`
(`npm run build` overwrites it; restored by rewriting the file to its exact
committed content, confirmed via `git status --porcelain web/dist/`).

## Review notes — 2026-08-18 (phase 3, approved)

Re-verified against the **production build served by the Go binary**, not the
dev server. `npm run check` 187 files / 0 errors; `npm test` 103 tests; `go
test ./... -count=1` all `ok` with `TEST_DATABASE_URL` exported and zero skips.

- **Single `<h1>`** — `document.querySelectorAll('h1').length === 1`, text
  "Hands-on electronics workshops". Heading run is `H1 → H2 → H2 → H2`.
- **Landmarks** — exactly one `<main>` and one `<footer>`. Independently
  re-walked the four `<header>` elements' ancestor chains for
  `article`/`aside`/`main`/`nav`/`section`: exactly **one** has no such
  ancestor and is the page's only ARIA `banner`; the three `Panel` card headers
  all sit inside `<section class="next-up">` and correctly expose no landmark
  role. The implementer's claim reproduces exactly.
- **No horizontal overflow** at 320/375/414/480/768/1024/1440 px, measured
  through a device-metrics override rather than `--window-size`, so the narrow
  widths are genuinely narrow and not silently clipped by headless Chromium's
  ~485 px floor (`CLAUDE.md` §8). An element-level sweep for right edges past
  the viewport found nothing at any width. This exceeds the criterion's
  375–1440 px range on the low side.
- **LCP re-measured against the built artefact.** Served the embedded
  production bundle from the Go binary and observed
  `largest-contentful-paint` (`buffered: true`) at 390 px / DPR 3 under
  `Network.emulateNetworkConditions` (150 ms RTT, 1.6 Mbps down — Lighthouse
  Slow 4G) plus `setCPUThrottlingRate({rate: 4})`. Three runs: **1168 / 1176 /
  1176 ms**, FCP ~995 ms. Comfortably inside the 2.0 s budget. Higher than the
  implementer's 752 ms because this run is a 390 px mobile viewport at 3× DPR
  rather than desktop, but the conclusion is the same and — the point of the
  check — it is unambiguously the built bundle, not the dev server's unbundled
  module waterfall. The implementer was right to discard its 6.1 s dev-server
  figure.
  One observation for `#0063`/`#0019`: the LCP element is a body `<p>` in the
  "What this is" section, not the hero headline this issue's Notes assume.
  Harmless today, but if a later change makes the hero heavier, that assumption
  is the thing to re-check.
- **No venue affiliation** — case-insensitive search of the rendered body for
  "sequoia"/"fabrica" found nothing, and the two "What this is" paragraphs were
  read: they state the group is "deliberately venue-independent" and that a
  workshop "might run in a makerspace, a co-working room, or somebody's
  garage". The positioning is correct, not just the absence of a string.
