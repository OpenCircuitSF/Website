## Description

`PRD.md` §10.2 and `docs/deployment.md`'s DNS table both document DMARC at
**`_dmarc.opencircuitsf.com`**. Measured live, that name has **no DMARC record**
— it resolves through the zone's wildcard to `ec2.smallsharptools.com`, so a
receiver querying it finds a CNAME, not a policy.

The real policy sits at **`_dmarc.mailing.opencircuitsf.com`**:

	v=DMARC1; p=none; rua=mailto:contact@opencircuitsf.com; fo=1

**That placement is deliberate**, and consistent with the rest of the design:
list mail sends from the `mailing.` subdomain precisely so the apex — which
carries a real Google Workspace MX (`CLAUDE.md` §9, §10 item 5) — is untouched.

### Three discrepancies, not one

Confirmed by the orchestrator with `dig`:

| | Documented | Live |
|---|---|---|
| **Name** | `_dmarc.opencircuitsf.com` | `_dmarc.mailing.opencircuitsf.com` |
| **Policy** | `p=quarantine` (`PRD.md`) / `p=none` (`docs/deployment.md`) | `p=none` |
| **Alignment tags** | `adkim=s; aspf=s` in both | **absent** |

So the two documents disagree with each other on strictness *and* both disagree
with reality on the name and the tags.

### Why it matters

`#0057` is about to add DNS records to this zone. A runbook naming a record that
does not exist invites someone to "restore" DMARC at the apex — which would
publish a policy governing the **Workspace** mail the apex actually carries.
That is adjacent to §9's standing rule that the apex MX must never be touched.

The `adkim=s; aspf=s` gap is the subtler half: strict alignment is a real
policy choice, and a document asserting it while the live record omits it will
mislead anyone reasoning about deliverability.
