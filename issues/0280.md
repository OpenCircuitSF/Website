## Description

`#0242`'s guard carries two escape hatches, `KNOWN_LOADING_PLACEHOLDERS` and
`KNOWN_DYNAMIC_ROLE_SITES`. Two problems, both procedural rather than
functional — the guard works, and its review confirmed both sets are currently
justified and minimal.

**They are keyed by `file:line`.** Any edit that adds a line above an entry
invalidates it. The failure is not silent — the guard reports a stale entry —
but it means ordinary editing produces guard failures unrelated to the change,
and the cheapest way to make one go away is to renumber it without rechecking
whether it is still justified.

**Nothing mechanically requires a justification.** A future agent can append an
entry and go green. Both sets today carry written arguments per entry, by the
implementer's discipline rather than by the guard's rule. That is exactly the
shape CLAUDE.md §8 warns about — a mechanism that depends on the next person
choosing to be careful.

Low priority. Filed so the hygiene question is tracked rather than rediscovered
the next time someone widens the guard.

## Resolution notes

> 🟢 Resolved 2026-08-27 — both allowlists now key on the site's own stable
> content, a non-empty `reason` is enforced at runtime by
> `unjustifiedEntryViolations`, and `staleEntryViolations` adds an explicit

## Acceptance criteria

1. Entries key on something stable — the enclosing component and a distinctive
   attribute or text, or a `data-` marker in the source — rather than a line
   number. If a line number is genuinely the only workable key, record why.
2. The guard fails when an allowlist entry carries no justification text. A
   non-empty reason string is a required field of an entry, not a comment
   beside it.
3. A stale entry — one naming a site that no longer matches — still fails
   loudly. Do not trade the current loud staleness for silent tolerance while
   fixing the churn.
4. A test proves both new rules fire: one fixture adds an unjustified entry, one
   points an entry at a site that no longer exists. Per CLAUDE.md §8 the oracle
   must not be the same bytes as the subject.
5. The existing entries are migrated with their current justifications intact,
   not rewritten from memory.
6. `ISSUE=NNNN scripts/check.sh web` passes.

## Root cause

Both allowlists (`KNOWN_DYNAMIC_ROLE_SITES`, `KNOWN_LOADING_PLACEHOLDERS`)
were `Set<string>` keyed by `${file}:${line}`, and the `reason` for each
entry lived only as a source comment beside it — nothing in `checkFile`
ever read or validated that text. Two independent consequences followed:
an edit adding a single line above any entry silently invalidated it
(`#0125`'s diff rewrote all 7 `KNOWN_LOADING_PLACEHOLDERS` entries for
exactly this reason, same 7 sites, only the numbers changed), and a future
agent could append a bare `'file:line'` string with zero justification and
go green.

## Fix

Converted both sets to `AllowlistEntry[]` (`{ file, match, reason }`).
`match` is the site's own stable content rather than its position: for
`KNOWN_LOADING_PLACEHOLDERS` that's the element's static text (verified
unique per file — no two loading placeholders in the same file share
copy); for `KNOWN_DYNAMIC_ROLE_SITES` it's the dynamic attribute's own raw
source text (`role={w.alert ? 'alert' : 'status'}`), extracted via a new
`rawAttrSource` helper using the Attribute node's `start`/`end` offsets and
threaded through `UnclassifiableSite.matchKey`.

Two new functions enforce the two new rules at runtime:
- `unjustifiedEntryViolations(list, fileName)` — every entry whose `file`
  matches the file being checked must have `reason.trim().length > 0`.
- `staleEntryViolations(list, fileName, used)` — `checkFile` tracks which
  entries actually matched a real site (`usedDynamicRoleEntries`,
  `usedLoadingPlaceholderEntries`) while scanning that file, and any entry
  naming that file that never matched anything is reported as stale —
  preserving the pre-existing "a bad entry fails loudly" property that
  keying on content, by itself, would otherwise have relaxed.

`checkFile` now takes both allowlists as optional parameters (defaulting
to the real `KNOWN_*` arrays), specifically so the criterion-4 fixtures
can exercise the two new rules against small throwaway entries instead of
mutating the real ones — CLAUDE.md §8's "the oracle must not be the same
bytes as the subject."

All 21 existing entries (1 dynamic-role + 20 loading-placeholder) were
migrated with their original justification prose intact, condensed into a
shared `KNOWN_LOADING_PLACEHOLDER_REASON` constant for the common case
plus the specific extra sentence each of the three special-shaped entries
(WorkshopEditor's and CampaignEditor's second placeholders, Dashboard's
second placeholder) already carried in its own comment.

## Review notes

> 🟢 Reviewed 2026-08-27 (Opus, phase 3) — **pass**. Verified independently,
> not from the drafted `## Verification`.

**Criterion 1 (stable keys).** `KNOWN_LOADING_PLACEHOLDERS` keys on the
element's static text, `KNOWN_DYNAMIC_ROLE_SITES` on the dynamic attribute's
raw source via `rawAttrSource`. Both survive line shifts. Confirmed the 20
placeholder entries and the (then-present) single dynamic-role entry match the
real tree with the new keys.

**Criterion 2 (justification is a required field).** `unjustifiedEntryViolations`
runs at the top of `checkFile` for all three allowlists. Proved by the two
`#0280` fixtures, which use throwaway entries rather than mutating the real
arrays. Judgment on strength: `reason.trim().length > 0` is a weak rule — a
single character satisfies it — but it is exactly what the criterion asked for,
and CLAUDE.md §8's real concern does not apply: the oracle here is a runtime
predicate over an entry's own field, not a stored copy of the subject's bytes,
so an edit to `checkFile`'s message breaks the fixtures (fail-closed) rather
than satisfying them.

**Criterion 3 (staleness still loud).** Verified as *strictly stronger* than
before, not a trade. At `eb6c78f^` there was **no staleness check in code at
all** — a stale `file:line` entry manifested only indirectly, as the site it
no longer covered failing on its own merits. That indirect signal is still
present, and `staleEntryViolations` is new on top of it. Proved live rather
than by fixture: adding a `KNOWN_STABLE_BRANCH_SITES` entry naming
`Admin.svelte`'s (now unconditional) import notice makes the real-tree test
fail with `stale allowlist entry -- no site in web/src/views/Admin.svelte
matches …`.

**Criterion 5 (migration intact).** Spot-checked against `eb6c78f^`. Counts
match (20 placeholders + 1 dynamic-role = 21). The three specially-worded
entries — `WorkshopEditor`'s "Rendering preview…", `CampaignEditor`'s
"Rendering…", `Dashboard`'s "Nothing needs attention right now." — each kept
its own extra sentence, condensed but not reinvented; the other 17 inherit the
set-level argument that previously lived in the set's doc comment. The
dynamic-role entry's prose was carried over faithfully at `eb6c78f` before
`#0279` emptied the set.

**Criterion 6.** `ISSUE=0280r scripts/check.sh web` — `npm run check` 287
files / 0 errors / 0 warnings; `npm test` 40 files / **3964 tests / 0
failures**. Per-commit deltas re-derived from the diffs: `#0280` +4, `#0279`
+7, `#0286` +4 (3 in `admin.test.ts`, net +1 guard fixture).

**One residual gap, reported for filing rather than bounced.** Both
`unjustifiedEntryViolations` and `staleEntryViolations` filter on
`e.file === fileName`, so an entry whose `file` matches **no scanned file** —
a typo, or a component later renamed or deleted — is validated by neither.
Measured: an entry `{ file: 'web/src/views/DoesNotExistAnywhere.svelte', match:
'nothing', reason: '' }` added to `KNOWN_STABLE_BRANCH_SITES` leaves the suite
green. It cannot exempt any real site (`findAllowlistEntry` matches on `file`
too), so it is inert rather than a bypass, and the same hole existed before
this change — but it is the most likely way an entry goes stale now that keys
are content-based, and criterion 3's spirit is that such an entry fails loudly.
