## Description

`#0031` correctly stops a non-`active` subscriber's save from claiming success, and shows a status panel with a "Subscribe again" affordance instead. For four of the five statuses that is right. For `complained` it is a dead end the UI knowingly steers into.

`goToSubscribe()` is a client-side `navigate('/subscribe')` — it performs **no mutation**, so the guard is not undone and the row cannot leave `complained` by any route reachable from this UI. That part is sound. But the person then submits the public form and receives `#0026`'s uniform `202` — *"Check your email to confirm."* — for a mail that `existingSignup`'s `StatusComplained` branch never sends.

Meanwhile `inactiveStatusMessage('complained')` returns the vague *"This address isn't currently subscribed."*, while the **same component's** unsubscribe path already has honest copy for exactly this case:

> …complained addresses can't be unsubscribed or resubscribed from this page. Contact us…

## Why this is a residual and not a bounce

`#0031`'s reviewer judged it so, and I agree: nothing is falsely *stated*, no guard weakens, no record is corrupted, and the same dead end exists site-wide by `CLAUDE.md` §9's design — the uniform `202` is what makes it invisible, deliberately. This is about not walking someone into it from a page that already knows their status.

- [x] The other four statuses keep the affordance — `pending`, `unsubscribed` and `bounced` can legitimately resubscribe, and `active` never sees the panel

## Review notes

**Bounced 2026-08-19 — the replacement path is inert: "Contact us" never says
how.**

Everything else in this fix is correct and was independently re-proven. The
affordance suppression is right and complete: `showSubscribeAgainAffordance`
returns `false` for `complained` and `true` for `pending`, `unsubscribed`,
`bounced`, `active` and an unrecognized status, and all three reported
mutations reproduced exactly — forcing the predicate to `true` fails only
*is suppressed for complained*, forcing it to `false` fails only *is present
for every other status the panel can show*, and reverting the copy fails only
the two message assertions, 25 tests each time. The claim that the other two
`goToSubscribe` call sites needed no change holds on inspection: the `invalid`
panel has no subscriber status at all (the token was never resolved), and the
`unsubscribed` panel is reachable only after a *successful* unsubscribe PATCH,
which a complained row can never produce — its PATCH routes to the separate
`unsubscribeNoOp` panel, which has no resubscribe button. No server file was
touched: `e76b385` is three files, all under `web/src/`, and the store guard is
untouched. `npm run check` reports 195 files / 0 errors, `npm test` 8 files /
152 tests, `npm run build` succeeds (run in an isolated worktree), and
`web/dist/index.html` in the main tree is byte-identical to the committed
placeholder. The constant matches the server string word for word apart from
the deliberately dropped `"No change: "` lead-in and the resulting
capitalisation — that judgement was right, and the sentence does read naturally
on page load rather than as a reply to an action.

### 1. Why this bounces

The acceptance criterion is not "reuse the copy"; it is "reuse the honest copy
… **including how to reach a human**." The shipped sentence ends:

> Contact us if you believe this is a mistake.

There is no address and no link. That names *that* a human exists, not *how* to
reach one, so the criterion is unmet and was checked in error.

This matters more here than it would anywhere else on the site, because of what
this fix just did. Before it, a `complained` visitor had a button — a fake path,
but a path. Now the button is correctly gone and this sentence is the **only**
remaining path offered. Making it the sole route and leaving it inert
reconstructs the defect the issue exists to close, one shape over: the visitor
is still told to do something and still given nothing to act on.

`#0075` published `hello@opencircuitsf.com` for exactly this class of request,
and the app already treats naming it as the house convention — `Footer.svelte`,
`About.svelte` and `PrivacyPolicy.svelte` each hold a `CONTACT_EMAIL` constant
and render it as `<a href="mailto:{CONTACT_EMAIL}">`, and `PrivacyPolicy.svelte`
goes out of its way to write "contact us **at the address below**." This panel
is the one place that says "contact us" and stops.

The footer does carry the address site-wide, so it is not strictly
unreachable — but requiring the visitor to infer that, scroll, and connect it to
the sentence is not the same as offering it, and a person who has just been told
they are marked as a complainer is the least likely visitor to go hunting.

### 2. One design tension to resolve while fixing it

Adding the address to `COMPLAINED_NO_RESUBSCRIBE_MESSAGE` would break the
"matching, word for word, the no-op message" guarantee its own doc comment
makes, since `internal/handlers/preferences.go:250` has the same inert
"Contact us" and is out of lane for this batch. Two clean options:

- Render the mailto link in `PreferenceCenter.svelte` beside the message (a
  sibling `<p>` or a trailing anchor), leaving the constant a faithful mirror.
  This keeps the change entirely in-lane and is probably the smaller edit.
- Or add the address to both strings and update the doc comment. This needs
  `internal/handlers/preferences.go`, so it must wait for that file to be free.

Either way the server's own message has the same gap and should be tracked —
**this belongs in a new issue** against `patchUnsubscribe`'s no-op copy.

### 3. Two further findings, neither a bounce reason

**a. The `{#if}` wiring is untested.** The new tests assert on the pure
predicate, never on the rendered panel. Deleting the `{#if}` wrapper from
`PreferenceCenter.svelte` entirely — restoring the exact dead end this issue
closes — leaves all 152 tests green; only mutating `subscribe.ts` fails
anything. So the one line that actually delivers the user-visible fix carries no
regression protection. This is **not** held against the fix: the project has no
component-test infrastructure at all (no jsdom/happy-dom, no
`@testing-library/svelte`, and no test anywhere imports a `.svelte` file), every
suite is a pure-logic test under `src/lib/`, and this fix followed that
convention exactly by extracting the decision into a testable function. The
exposure is project-wide rather than specific to `#0090`. **Belongs in a new
issue** if component coverage is ever wanted.

**b. Stale cross-reference.** `web/src/lib/subscribe.ts:184` points the reader
at `COMPLAINED_UNSUBSCRIBE_NO_OP_MESSAGE`; no such symbol exists — the constant
is `COMPLAINED_NO_RESUBSCRIBE_MESSAGE` at line 219. Worth correcting in the same
pass.

### 4. The two deferred decisions

**`no_op`'s `,omitempty` — deferral correct, "cosmetic" is the wrong word.**
Leaving it alone was right: `internal/handlers/preferences.go` is explicitly out
of lane and under concurrent review, and editing another agent's file mid-review
is what `CLAUDE.md` §8 warns against. But the characterisation understates it.
This is not a formatting matter; it is two handlers serialising the same field
name under two different schemas. `omitempty` on a `bool` erases the difference
between `false` and absent, and in JS `undefined !== false`, so a consumer
writing `result.no_op === false` or `'no_op' in result` gets different answers
from `/preferences` than from `/admin/subscribers/{id}/suppress` — which is
exactly why `api.ts:426` types the admin field as required `no_op: boolean`
while `types.ts:175` types this one optional. The codebase already documents the
intended convention and breaks it one line later: the comment at
`preferences.go:120` says the field "mirrors AdminSubscribersHandler.Suppress's
no_op field, #0032", and line 121 does not. Call it latent contract drift —
harmless only because no caller reads it today, which is a fact about today's
callers, not about the field. "Left for a follow-up issue or the next pass" is a
wish rather than a tracked item; **this needs a new issue** against
`internal/handlers/preferences.go`.

**`maskEmail`'s two-rune reveal — declined correctly.** Agreed on the merits.
`ab@x.com` → `a•••••b@x.com` does reveal the whole local part while the bullets
imply hidden characters that are not there, so the mask mildly over-promises.
But it is not a security boundary — the caller already holds the row's token —
the affected input class is negligible, and tightening it means inventing a
policy (mask fully below N runes) that nobody has specified. Recording it as
confirmed-not-a-bug is right. Worth noting only that the two labels ended up
swapped: the genuinely cosmetic item was called not-a-bug, and the contract item
was called cosmetic.

## Fix

**1. Affordance suppressed for `complained`.** Added
`showSubscribeAgainAffordance(status: string): boolean` to
`web/src/lib/subscribe.ts` — `status !== 'complained'` — and wrapped the
"Subscribe again" `<button>` in the `!isActive` branch of
`PreferenceCenter.svelte` in `{#if showSubscribeAgainAffordance(status)}`.
Only that one panel changed; the two other places `goToSubscribe` is wired
(the `invalid` token panel and the `unsubscribed`-after-a-real-unsubscribe
success panel) are unrelated to a subscriber's current `status` — a
complained row's own unsubscribe attempt routes to the separate
`unsubscribeNoOp` panel, which has no resubscribe button at all — so neither
needed a change.

**2. Honest copy for `complained`.** Added the exported constant
`COMPLAINED_NO_RESUBSCRIBE_MESSAGE` to `subscribe.ts`, carrying the same
substantive sentence `internal/handlers/preferences.go`'s `patchUnsubscribe`
already returns for a complained row's no-op PATCH: *"This address is
marked as having complained about a previous email, and complained
addresses can't be unsubscribed or resubscribed from this page. Contact us
if you believe this is a mistake."* Deliberately drops only that server
message's leading `"No change: "` clause, which describes a PATCH that was
just attempted — not applicable when this copy is shown on page load,
before anyone has clicked anything. `inactiveStatusMessage('complained')`
now returns this constant instead of the generic `"This address isn't
currently subscribed."` every other unrecognized/default status still gets.
One exported constant, not two independently-typed strings, so the two call
sites cannot quietly drift apart on a future edit — though note this is
copy *duplication* across a Go string literal and a TS constant, not a
single shared source; a future edit to either still needs a human to update
the other by hand.

## Gotchas

- The server's no-op message starts with `"No change: "`, which reads
  correctly only in the context of a PATCH that was just attempted. Reusing
  it verbatim in `inactiveStatusMessage` (shown on page load, no action
  taken yet) would have been confusing, so the constant is the same
  sentence minus that clause — "reuse the copy" was interpreted as "reuse
  the substantive honest sentence," not "byte-for-byte reuse the whole
  server string including context-specific framing."
- `web/node_modules` doesn't exist in a fresh `git worktree` (it's
  gitignored, not part of the tree) — `npm run check`/`test`/`build` all
  fail with `command not found` until something provides it. Symlinked to
  the main tree's `web/node_modules` rather than running `npm install`
  again in the worktree; removed no files, left the main tree's
  `node_modules` untouched, and the symlink itself is gitignored so it
  never shows up in `git status` as anything to clean up.
- Confirmed by reading `internal/handlers/preferences.go` around line 121
  that the `no_op` tag mismatch (`#0032`'s `admin_subscribers.go:368` is
  plain `json:"no_op"`) is real and exactly as described — not re-verified
  by a mutation test since the fix itself was deliberately not made.
