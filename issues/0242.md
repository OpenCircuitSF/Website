## Description

`#0063` settled a console-wide question: a live region must be a **persistent
DOM node whose text mutates**, never a node created and destroyed by an `{#if}`.
A recreated node is not announced — the assistive technology has nothing to
observe changing.

That decision is recorded only in prose and in comments. Nothing enforces it,
and the failure mode is already demonstrated twice over:

- `#0063`'s own sweep left six identical instances unconverted while its
  comments described the decision as applied console-wide.
- `SubscribeForm.svelte`'s error region **looked correct by inspection** —
  an `{#if}/{:else}` with matching `id`s — and was only proved broken by driving
  a real browser and watching a `__marker` property fail to survive the
  transition.

That second point is the argument for a guard rather than review discipline:
**this defect is invisible to reading.** The markup looks right. Only the
compiled template, or the live DOM, shows the node being replaced.

The project already has the technique. `#0181`, `#0197` and `#0120` are AST
guards over Svelte source, and `#0222`'s focus-wiring guard walks templates for
exactly this kind of structural property. `#0095`, built in the same session,
exists to argue that comments cannot hold invariants — while this invariant is
held by comments.

## Acceptance criteria

- [ ] An AST guard fails when a `role="status"` / `aria-live` element is created by an `{#if}` or `{#each}` rather than persisting with mutating text
- [ ] It distinguishes the legitimate alternative — a whole-panel swap that moves focus instead, as `Unsubscribe.svelte` does — rather than flagging it
- [ ] Mutation-proved in both directions: reverting a converted site fails the guard; every currently-correct site passes
- [ ] It runs over the whole `web/src` tree, not a hand-maintained file list — `#0063` was bounced precisely for sweeping the files it happened to be editing
- [ ] Any site it cannot classify is reported loudly rather than skipped, per the silent-row-masking class (`#0083`, `#0092`, `#0224`)
- [ ] `scripts/check.sh web` passes

## Notes

Reported by `#0063`'s phase-3 review under `CLAUDE.md` §9.

Worth writing the guard against the **compiled** template rather than the source
where practical: the `SubscribeForm` case proves source markup can look correct
while the compiler still emits two branches. The reviewer distinguished the two
builds precisely that way — pre-fix served two `$.if` templates, post-fix one
inline `<p>` via `$.sibling`.

`CLAUDE.md` §1 is explicit that these AST guards are not redundant with the
component harness: they catch drift between what a test claims and what a
component says, which mounting cannot.

  `{#if}/{:else}/{#each}` branch, after unwrapping single-significant-child

**The defect — criterion 4.**

`liveRegionGuard.structuralGuard.test.ts` globs `'../views/**/*.svelte'`, which
resolves to `web/src/views` only. Thirteen `.svelte` files live outside it
(`web/src/App.svelte` and all twelve of `web/src/lib/*.svelte`) and are never
scanned. One of them holds a live region:

```
web/src/lib/SubscribeForm.svelte:203:  <p id={errorId} class={errorMessage ? 'text-error' : 'sr-only'} aria-live="polite">{errorMessage ?? ''}</p>
```

That is **the component this issue's own Description names as the motivating
case** — the one that "looked correct by inspection" and was only proved broken
in a real browser. It is currently correct, and nothing would notice if it
stopped being: reverting it to its original `{#if}/{:else}` shape is invisible
to this guard.

Proved, not argued. In a throwaway worktree at the review commit I dropped a
canonical violation at `web/src/lib/ZzProbeOutsideViews.svelte`:

```svelte
{#if msg}<p role="status">{msg}</p>{/if}
```

— the exact shape the guard's own synthetic fixture flags — and the real-tree
test stayed **green**. Criterion 4 exists verbatim because "`#0063` was bounced
precisely for sweeping the files it happened to be editing"; this repeats that
scoping error one directory up.

**The fix is two lines and I verified it is free.** Changing the glob to
`'../**/*.svelte'` and `toRepoRelativePath` to `web/src/${globKey.slice(3)}`
leaves the guard **green on the current tree** (no new violations surface), and
the probe fixture above then fails it. Do that, and re-derive the enumeration
floors afterwards.

**Second, weaker finding — criterion 1 is met only for the single-child case.**
`isGoverningBranchDynamic` examines a `role="status"` site only when its
enclosing branch unwraps, through single-significant-child containers, down to
that element. On today's tree that is 23 of the 47 status sites that sit inside
a branch at all; the other 24 are waved through with **no** persistence check
and **no** focus-swap check. So this passes the guard:

```svelte
{#if err}
  <div class="wrap">
    <h2>Something went wrong</h2>
    <p role="status">{err}</p>
  </div>
{/if}
```

Verified by fixture (`web/src/views/ZzProbeFork.svelte` in the worktree: guard
green). That is a `role="status"` node created and destroyed by an `{#if}`,
dynamic text, no focus target — criterion 1's literal subject — and it is not an
exotic shape, it is what any conditional error panel looks like. The file header
discloses this ("a two-sibling branch that toggles in lockstep with the notice
would still slip past it"), and the disclosure is the right instinct, but a
disclosed gap is not a met criterion.

The unwrap step itself is **principled, not fitted to make the suite green** — I
checked the four sites it is defended by (`settingsNotice`, `audience-count`,
`testSendMessage`, `Unsubscribe`'s `doneMessage`) and each is genuinely a
persistent node in a stable branch, so the naive rule really was producing false
positives. The problem is not the unwrap; it is that the fork case then gets no
check at all. Even read as "this is a whole-panel swap", criterion 2 says a
whole-panel swap is the legitimate alternative **when it moves focus** — and the
fork path never asks whether it does. Note this is exactly the gap `#0244`'s own
item 1 was: `PreferenceCenter`'s two-child `{#if showSubscribeAgainAffordance}`
branch had no focus management, and this guard would not have found it.

Not asking for a redesign. Either extend the rule to require a focus target for
*any* in-branch status site (growing a named allowlist for the stable-branch
ones, the same shape `KNOWN_LOADING_PLACEHOLDERS` already has), or record the
boundary against criterion 1 explicitly in the issue rather than only in the
source header, so the next reader knows the criterion is partially met.
