# 0122 — `drainCampaign`'s unconditional `OrphanSweep` un-claims a row another worker is mid-send on, duplicating one delivery

| | |
|---|---|
| **Status** | open |
| **Module** | mailing |
| **Platform** | All |
| **Phase** | 5 — Campaigns |
| **First seen** | 2026-08-21 |

## Description

Two `mailing.Worker` instances draining the same campaign can deliver one
recipient's message **twice**. `Worker.drainCampaign`
(`internal/mailing/worker.go:344`) runs `SendStore.OrphanSweep` unconditionally
before draining, and `OrphanSweep` (`internal/mailing/worker_store.go:246`) is:

```sql
UPDATE email_sends SET status = 'queued' WHERE campaign_id = $1 AND status = 'sending'
```

It cannot tell a **crashed** worker's abandoned row from a **live** worker's
in-flight one. `sendOne` sets a row to `sending` in `ClaimRow`, makes the SES
call, then writes `sent` in `MarkSent`. Any `OrphanSweep` landing inside that
window returns the row to `queued`; the sweeping worker's next `ClaimBatch`
picks it up and sends it again.

This defeats the mutual-exclusion claim written into `sendOne` itself:

```go
	if !claimed {
		// Another worker claimed this row first — see #0044's
		// "increment attempts before the SES call" requirement and this
		// issue's plan §4 for why this statement IS the mutual exclusion.
```

`ClaimRow`'s `AND status = 'queued'` is only mutual exclusion if nothing else
moves rows back into `queued`. `OrphanSweep` does exactly that, on every claim
and every resume.

Impact is a duplicate commercial email to a real subscriber. `CLAUDE.md` §10
item 4 records an operational "exactly one instance runs the worker"
assumption, but `TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce`
exists specifically to prove the concurrent guarantee holds, and it does not.

## Steps to reproduce

Deterministic — no timing luck, no load, no `-count=N`. Inject worker 2's
**real** resume at the instruction boundary `sendPreCrashHook` already exposes
(after `ClaimRow`, before the SES call), inside
`TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce`, replacing its
two goroutines with:

```go
	var fired bool
	sendPreCrashHook = func(sendID int64) bool {
		if !fired {
			fired = true
			c2, err := w2.store.ClaimResume(context.Background())
			if err != nil || c2 == nil {
				t.Errorf("probe ClaimResume: %+v %v", c2, err)
				return false
			}
			if err := w2.drainCampaign(context.Background(), c2); err != nil {
				t.Errorf("probe drainCampaign: %v", err)
			}
		}
		return false
	}
	t.Cleanup(func() { sendPreCrashHook = nil })

	c1, err := w1.store.ClaimResume(context.Background())
	if err != nil || c1 == nil {
		t.Fatalf("ClaimResume: c=%+v err=%v", c1, err)
	}
	if err := w1.drainCampaign(context.Background(), c1); err != nil {
		t.Errorf("drainLoop: %v", err)
	}
```

Then:

```
$ go test ./internal/mailing/ -count=1 -p 1 -run TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce
--- FAIL: TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce (0.04s)
    worker_test.go:203: mailer.Sent() = 25 messages, want 24
```

No fakes are involved: the probe calls the same `ClaimResume` and
`drainCampaign` a second worker process calls. It only removes the scheduling
luck required to land in the window.

## Expected behavior

Every recipient is mailed exactly once, no matter how many workers resume the
same campaign concurrently.

## Actual behavior

Exactly one recipient is mailed twice per interleaving that lands in the
`ClaimRow` → `MarkSent` window.

## Notes

**This is the failure `#0048`'s implementation pass recorded as a transient
flake**, as `mailer.Sent() = 25, want 24` on a combined `-p 2` run. That
diagnosis was wrong on both of its claims, and both are worth stating so the
next agent does not re-derive them:

- It blamed `-p 2` running `internal/handlers` and `internal/mailing`
  concurrently against the shared test database. **That cannot happen.**
  `internal/testdb.Lock()` takes a shared PostgreSQL session advisory lock
  (`0x53484F52544C4B`) and every DB-backed package's `TestMain` calls it —
  `cmd/opencircuit`, `internal/handlers`, `internal/mailing`, `auth`, `audit`,
  `db`, `middleware`, `interests`, `subscribers`, `sesnotify`. They serialize
  regardless of `-p`.
- It filed the failure under `#0121`'s class. **It is not.** `#0121` is three
  `internal/handlers` tests that assert exact audience counts and break on
  leftover `active` **subscribers**. Different package, different table,
  different mechanism. `internal/mailing`'s own seeds are clean —
  `seedScheduledCampaign` registers `cleanupCampaign`, and
  `-shuffle` over `internal/mailing` passes.

This is the third time in this project a real defect was first recorded as a
flake (`#0108`, `#0121`). "Passed on re-run" remains not a diagnosis.

## Acceptance criteria

- [ ] `OrphanSweep` can no longer reclaim a row a live worker holds. The
      obvious shapes: stamp a claim owner/heartbeat on the row and sweep only
      rows whose claim is stale, or sweep only rows whose `updated_at` is older
      than a bound safely above `sendMessageTimeout`. Whatever is chosen, the
      "crashed process leaves a row stuck in `sending`" case that `OrphanSweep`
      exists for (`TestSendStore_OrphanSweep_ResetsOnlySendingRows`,
      `TestWorker_AbortBetweenSESAcceptAndStatusWrite_ResumesWithOneDuplicate`)
      must still be recovered.
- [ ] `TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce` gains the
      deterministic interleaving above as its own test, so the property is
      proven rather than sampled. The current test only fails when scheduling
      happens to land in the window — which is exactly why it was mistaken for
      a flake.
- [ ] `sendOne`'s "this statement IS the mutual exclusion" comment is corrected
      or made true.
- [ ] `go test ./internal/mailing/ -count=1` passes, and the new deterministic
      test fails when the fix is reverted.
