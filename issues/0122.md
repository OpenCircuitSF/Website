> the phase-3 reviewer (second cycle) at load average 2.16. All five acceptance
> criteria are met. `OrphanSweep` can no longer un-claim a live worker's
> in-flight row, the crash-abandoned row it exists for is still recovered, and
> `Run` no longer busy-spins during the staleness window. The two properties
> were proven to hold **simultaneously** by mutating each independently: with
> the throttle broken the busy-loop test fails (828 passes / 250 ms) while

Two `mailing.Worker` instances draining the same campaign can deliver one
recipient's message **twice**. `Worker.drainCampaign`
(`internal/mailing/worker.go:344`) runs `SendStore.OrphanSweep` unconditionally
before draining, and `OrphanSweep` (`internal/mailing/worker_store.go:246`) is:

```sql
UPDATE email_sends SET status = 'queued' WHERE campaign_id = $1 AND status = 'sending'
```

It cannot tell a **crashed** worker's abandoned row from a **live** worker's
in-flight one. `sendOne` sets a row to `sending` in `ClaimRow`, makes the SES
call, then writes `sent` in `MarkSent`. Any `OrphanSweep` landing inside that
window returns the row to `queued`; the sweeping worker's next `ClaimBatch`
picks it up and sends it again.

This defeats the mutual-exclusion claim written into `sendOne` itself:

```go
	if !claimed {
		// Another worker claimed this row first — see #0044's
		// "increment attempts before the SES call" requirement and this
		// issue's plan §4 for why this statement IS the mutual exclusion.
```

`ClaimRow`'s `AND status = 'queued'` is only mutual exclusion if nothing else
moves rows back into `queued`. `OrphanSweep` does exactly that, on every claim
and every resume.

Impact is a duplicate commercial email to a real subscriber. `CLAUDE.md` §10
item 4 records an operational "exactly one instance runs the worker"
assumption, but `TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce`
exists specifically to prove the concurrent guarantee holds, and it does not.

## Steps to reproduce

Deterministic — no timing luck, no load, no `-count=N`. Inject worker 2's
**real** resume at the instruction boundary `sendPreCrashHook` already exposes
(after `ClaimRow`, before the SES call), inside
`TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce`, replacing its
two goroutines with:

```go
	var fired bool
	sendPreCrashHook = func(sendID int64) bool {
		if !fired {
			fired = true
			c2, err := w2.store.ClaimResume(context.Background())
			if err != nil || c2 == nil {
				t.Errorf("probe ClaimResume: %+v %v", c2, err)
				return false
			}
			if err := w2.drainCampaign(context.Background(), c2); err != nil {
				t.Errorf("probe drainCampaign: %v", err)
			}
		}
		return false
	}
	t.Cleanup(func() { sendPreCrashHook = nil })

	c1, err := w1.store.ClaimResume(context.Background())
	if err != nil || c1 == nil {
		t.Fatalf("ClaimResume: c=%+v err=%v", c1, err)
	}
	if err := w1.drainCampaign(context.Background(), c1); err != nil {
		t.Errorf("drainLoop: %v", err)
	}
```

Then:

```
$ go test ./internal/mailing/ -count=1 -p 1 -run TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce
--- FAIL: TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce (0.04s)
    worker_test.go:203: mailer.Sent() = 25 messages, want 24
```

No fakes are involved: the probe calls the same `ClaimResume` and
`drainCampaign` a second worker process calls. It only removes the scheduling
luck required to land in the window.

## Expected behavior

Every recipient is mailed exactly once, no matter how many workers resume the
same campaign concurrently.

## Actual behavior

Exactly one recipient is mailed twice per interleaving that lands in the
`ClaimRow` → `MarkSent` window.

### `claimed_at IS NULL` = "always orphaned" — verified safe

Grepped every non-test writer of `email_sends.status`. `SendStore.ClaimRow`
(`worker_store.go:395`) is the **only** statement in the codebase that writes
`status = 'sending'`, and it stamps `claimed_at = now()` in the same
statement. `AudienceStore.Materialize` inserts with the column default
(`queued`) and `MarkSkippedTx` only touches `queued` rows. `internal/devstore`
has no `email_sends` at all. No live claim can present a NULL `claimed_at`.
Leaving a stale `claimed_at` behind on rows that exit `sending` is likewise
harmless — the predicate is gated on `status = 'sending'` and `ClaimRow`
re-stamps on the next claim.

### `orphanStaleAfter` — the derivation holds

I traced the whole claim-hold window and the derivation is semantic, not a
timing constant sized against machine load:

- `limiter.Wait` is **before** `sendOne` (`worker.go:472`), so the rate limiter
  never delays inside a claim.
- The retry backoff (`w.sleep(ctx, backoff)`) runs **after** `sendOne` returns,
  by which point `MarkRetryOrFailed` has already moved the row out of
  `sending`.
- So a live hold is `ClaimRow` → `w.render.Campaign` → SES call (hard 30s
  `context.WithTimeout`) → `MarkSent` (hard 5s) = 35s, doubled to 70s.

The only unbounded step is `render.Campaign`, which is in-memory markdown
rendering — microseconds. **I judge the remaining window genuinely unreachable
in practice**, with one caveat worth a comment in the code: the 70s bound is
maintained by *derivation*, not by construction. Nothing enforces it. If a
later change inserts any operation on the drain `ctx` (which carries no
deadline) between `ClaimRow` and `MarkSent`, the bound silently breaks and the
duplicate delivery returns with no test catching it. A one-line comment at
`sendOne`'s claim, or a compile-time link between the two, would keep that
honest.

### ❌ Blocking: the fix busy-spins `Run` for up to 70s after a real restart

`Run` (`worker.go:265`) does `if processed { continue }` — no ticker wait —
and `claimAndDrain` returns `processed = true` for *every* resume, whether or
not the pass did any work. Before this commit that was fine: the unconditional
sweep always recovered the orphan on the first pass, `drainLoop` sent it,
`CompleteIfDone` flipped the campaign to `sent`, and the next `ClaimResume`
returned nil. Now, for the whole 70s the orphan is not yet stale:

`ClaimResume` → campaign still `sending` → `drainCampaign` → `OrphanSweep`
resets 0 rows → `ClaimBatch` returns 0 → `CompleteIfDone` returns false
(the orphan still counts as `sending`) → return nil → `processed = true` →
`continue` **with no sleep**. Roughly 8 queries per pass, forever, until the
claim goes stale.

Measured, not theorised. I added a throwaway probe to `internal/mailing`
(deleted afterwards; the tree is back at `1bd0575`) that seeds one campaign
with a single `ClaimRow`-claimed row, marks it materialized, and runs `Run`
for 2s while sampling `pg_stat_database`:

```
at 1bd0575:                 56,572 transactions in 2.00s  (28,278/sec)
same probe, sweep made unconditional (pre-fix):
                             2,394 transactions in 2.00s  ( 1,197/sec, row sent, campaign completed)
```

That is a 24× step up, and it persists for `orphanStaleAfter` — on the order
of **two million transactions** before the row is recovered. It is
**independent of `PollInterval`**, because the spin path never reaches
`time.After(w.pollInterval)`; the production 2s tick does not throttle it at
all. On the production box Postgres shares hardware with Apache and the Go
service (`CLAUDE.md` §7), so this is a resource-exhaustion window on the host
serving `www.opencircuitsf.com`, not a performance-budget question — `CLAUDE.md`
§5's "no performance requirement" does not cover an unbounded busy loop.

Reachability is narrower than "every restart" but entirely real: it needs a
crash or restart within 70s of the campaign's **last** claim, since with queued
rows remaining `drainLoop` is rate-limited and the orphan goes stale long
before the queue drains. The tail of a campaign plus a `systemctl restart` is
exactly that. It also fires whenever `MarkSent` errors (the `werr` at
`worker.go:648` is logged and swallowed), which leaves a row `sending` with a
fresh `claimed_at` while the drain runs on to completion.

**What the next pass must do:** make a resume pass that neither sent nor
completed anything fall back to the poll ticker instead of `continue`. The
smallest shapes, in increasing invasiveness — pick one, they are equivalent
for this purpose:

1. Have `Run` wait `pollInterval` after a resume pass (a resume already drains
   to completion, so the immediate `continue` buys nothing).
2. Have `drainCampaign`/`drainLoop` report whether the pass did work, and
   return that as `claimAndDrain`'s `processed`.
3. Have `drainLoop`'s "nothing queued but `CompleteIfDone` said no" branch wait
   `pollInterval` before returning.

Add a regression test asserting a **bounded** number of passes (or DB
transactions) over a fixed window with one not-yet-stale orphan present. A
count assertion, not a deadline — it will not be load-sensitive.

### Is the new test a count assertion or a deadline in disguise? — a count

This was the sharpest question in the brief, and the answer is that the test's
residual timing component points the **safe** way.

`passes <= elapsed / pollInterval` is a structural bound: each throttled pass
must wait a fresh `time.After(20ms)`. Machine load makes each pass *slower*
(DB round trips, scheduler delay), so load pushes the count **down**, away from
the failure boundary — the opposite of the `#0084`/`#0087`/`#0096` class
CLAUDE.md §5 warns about, where load pushed a measured duration up through a
deadline. Observed: 11 passes against a bound of 20 (nominal ceiling 12.5), and
the mutant produces 828 — a ~75× discrimination gap, not a marginal one.

The one false-failure path is the *measuring* goroutine's `time.Sleep(250ms)`
overshooting by >80 % while the *measured* goroutine's twenty 20 ms timers stay
punctual — two contradictory starvation patterns in one process and one
scheduler. I judge that not a realistic flake source. **Verdict: a genuine
count assertion.** `w.pollInterval = 20 * time.Millisecond` is load-bearing
(the fixture's default is 1 ms, which would make the bound meaningless) and is
explicitly set.

Non-blocking refinement for whoever next touches it: computing `maxPasses` from
the *measured* elapsed time rather than the nominal 250 ms window would remove
even that residual and cost two lines.

### `drainLoop`'s `didWork` on an all-skipped batch — not too permissive

The brief asked whether a campaign whose every row loses its claim race can
spin. It cannot. Every exit from `queued` is one-way within a batch:
`AudienceStore.MarkSkippedTx` (`audience.go:553`) sets `status='skipped'`, and
a lost `ClaimRow` race leaves the row `'sending'` under the winning worker. So
`ClaimBatch`'s `WHERE status='queued' ... FOR UPDATE SKIP LOCKED` strictly
shrinks its own candidate set on every iteration and can never re-return the
same rows. A batch of entirely-skipped rows is therefore real progress, and
`didWork=true` costs at most **one** extra immediate `Run` pass before the next
pass hits the empty-batch branch and falls to `pollInterval`. That extra pass
is desirable — a campaign that just finished draining should re-poll at once.

### `pgx/v5` `time.Duration` → `interval` — verified behaviourally, at scale

The implementer confirmed the mapping by reading driver source, and the two
store-level tests use `time.Hour` / `-time.Hour`, which proves only the **sign**
— a driver that encoded nanoseconds as microseconds would pass them both. I
probed the real thing:

```
Go 0s      -> postgres interval 0.000000 s
Go 1m10s   -> postgres interval 70.000000 s     (orphanStaleAfter)
Go 1h0m0s  -> postgres interval 3600.000000 s
Go -1h0m0s -> postgres interval -3600.000000 s
```

and then end-to-end through the production predicate: a row backdated to

(0 rows swept, still `sending`), and one backdated to `orphanStaleAfter + 1s`
is recovered (1 row swept, back to `queued`). The zero duration behaves as

`TestSendStore_OrphanSweep_ResetsOnlySendingRows` relies on. Removing the
two-clock comparison is a strict improvement and it is correctly wired.

## Root cause

`SendStore.OrphanSweep` (`internal/mailing/worker_store.go`) had no way to
tell a `sending` row a crashed process abandoned from a `sending` row a
different, still-running `Worker` had claimed a moment ago via `ClaimRow` —
its `UPDATE` matched every `sending` row for the campaign, unconditionally.
`drainCampaign` runs it on every claim (start or resume), and `ClaimResume`
takes no lock, so two live `Worker`s draining the same campaign each ran an
unconditional sweep that could reset the *other* worker's in-flight claim
back to `queued`. The reset row was then re-claimed and mailed by the
sweeping worker while the original claimant — which never re-checks a row's
status after its own `ClaimRow` succeeds — went on to send its own copy,
producing exactly one duplicate delivery per interleaving that landed in the
window.

## Fix

Added `email_sends.claimed_at` (migration `000018`, edited in place — this
project is greenfield until first deploy, so the append-only rule in
CLAUDE.md §1 does not bind a migration that has never shipped). `ClaimRow`
now stamps `claimed_at = now()` in the same statement that flips a row to
`sending` and increments `attempts`. `OrphanSweep` takes a `staleBefore
time.Time` cutoff and only resets a row whose `claimed_at` is `NULL` (never
went through `ClaimRow` — always treated as orphaned) or older than that
cutoff.

`drainCampaign` (`worker.go`) computes the cutoff as `w.now().Add(-orphanStaleAfter)`,
using the `Worker`'s own injectable clock. `orphanStaleAfter` is `2 *
(sendMessageTimeout + writeStatusTimeout)` — double the longest time a
*live* claim can legitimately hold a row in `sending` (the SES call's own
detached-context bound, plus the status write's), so ordinary scheduling
jitter at the boundary can never be mistaken for a crash. This is a `var`,
sized against the two hard timeouts a send attempt is already built around,
not against measured machine load (CLAUDE.md §5).

Rejected a worker-owner/heartbeat lease: it solves the same problem but
needs a renewal mechanism and its own timeout to decide a lease has expired
— strictly more machinery than a claim timestamp for the same guarantee, and
`#0045`'s plan already rejected a `worker_id`/`locked_at` lease column for
the analogous per-row claim design for the same reason (issues/0045.md §4,
"Rejected — a `worker_id`/`locked_at` lease column").

Also corrected `sendOne`'s "this statement IS the mutual exclusion" comment,
which was true only among `ClaimRow` calls and not against `OrphanSweep` —
it now says so, and explains why the fix restores the original claim.
Extended the package doc comment's "At-least-once, honestly" section with a
new "The orphan sweep must not un-claim a live worker's row" subsection.

### Review pass 2 (2026-08-21) — the busy-loop fix and the two latent items

**Busy-loop fix — shape 2 chosen ("report whether the pass did work").**
`claimAndDrain`, `drainCampaign`, and `drainLoop` (`internal/mailing/worker.go`)
now each return `(bool, error)` instead of always reporting `true`: the bool
means "this pass did something real" — materialized an audience,
failed/completed a campaign, or claimed at least one batch row — not merely
"ran without error". `Run`'s `if processed { continue }` is unchanged; only
what `processed` MEANS changed. `drainLoop`'s specific "nothing queued,
`CompleteIfDone` says not done" branch (the exact busy-loop trigger) now
returns `didWork=false` unless an earlier batch in that same call already set
it, so a resume that genuinely found nothing yet claimable falls through to
`Run`'s `time.After(w.pollInterval)` instead of looping immediately.

Rejected the other two shapes the review offered:

- **Shape 1 ("`Run` always waits `pollInterval` after a resume pass")** was
  rejected because it can't distinguish "resumed and did nothing" from
  "resumed and sent something" — which the review explicitly asked for. It
  would also slow down chaining between multiple ready campaigns (a
  just-completed campaign's `continue` picking up the next scheduled one
  immediately) by up to one full tick for no correctness benefit, since
  `Run` has no way to tell a resume-shaped pass from a fresh-start-shaped one
  without the same `claimAndDrain` plumbing shape 2 already requires.
- **Shape 3 ("`drainLoop`'s empty-batch-but-not-done branch waits
  `pollInterval` before returning")** is a strictly less general version of
  shape 2 — it only fixes the one branch the review measured, whereas shape 2
  threads the same "did this pass do anything real" property through
  `claimAndDrain` and `drainCampaign` too, so a `PeekScheduledCandidate` miss,
  a lost `ClaimStart` race, or a `GatherPreflight` vanish (all of which
  already correctly returned `false`) and the new orphan-only-resume case are
  now expressed by the same mechanism instead of two different ones.

**Measured, not theorised (bounded-pass-count regression test).**
`TestWorker_Run_ResumeWithLiveOrphan_DoesNotBusyLoop`
(`internal/mailing/worker_test.go`) seeds a campaign forced to `sending` with
one row claimed through the real `ClaimRow` path (a live, not-yet-stale
orphan) and nothing else queued — the exact "resumed and did nothing" shape —
then runs `Worker.Run` for a **fixed 250ms wall-clock window** with
`pollInterval=20ms`, counting every `claimAndDrain` pass via a new
package-private, nil-in-production counting seam (`claimAndDrainHook`,
the same pattern as `sendPreCrashHook`/`sendPostCrashHook`). The assertion is
`passes <= 20` (roughly `window/pollInterval` plus scheduling slack) — **a
count, not a deadline**, exactly what the review's criterion calls for and
what `CLAUDE.md` §5 says a day was already spent establishing the difference
between:

```
$ go test ./internal/mailing/ -run TestWorker_Run_ResumeWithLiveOrphan_DoesNotBusyLoop -v -count=1
    worker_test.go:337: claimAndDrain ran 11 times in 250ms (pollInterval=20ms)
--- PASS: TestWorker_Run_ResumeWithLiveOrphan_DoesNotBusyLoop (0.26s)
```

**Mutation proof.** Temporarily reverted `drainLoop`'s "nothing queued,
`CompleteIfDone` says not done" branch to `return true, nil` (the pre-fix
behavior) and re-ran the same test:

```
    worker_test.go:337: claimAndDrain ran 823 times in 250ms (pollInterval=20ms)
    worker_test.go:344: claimAndDrain ran 823 times in 250ms with pollInterval=20ms
    (want <= 20) — Run is busy-looping instead of falling back to the poll
    ticker on a resume that did nothing
--- FAIL: TestWorker_Run_ResumeWithLiveOrphan_DoesNotBusyLoop (0.26s)
```

823 passes in 250ms is ~3,300 passes/sec — three at least three DB
round trips each (`OrphanSweep`, `ClaimBatch`, `CompleteIfDone`), so on the
order of 10,000 transactions/sec by this measurement's own (goroutine-loop,
not `pg_stat_database`) methodology. Different instrument from the review's
28,278 tx/sec `pg_stat_database` sample, same defect, same order-of-magnitude
conclusion: unthrottled. Reverted the mutation and reconfirmed the 11-pass
green result above before moving on.

**Two-clock comparison removed, not merely documented.** `OrphanSweep`
(`internal/mailing/worker_store.go`) now takes `staleAfter time.Duration`
instead of an absolute `staleBefore time.Time`, and the statement itself
computes the cutoff — `claimed_at < now() - $2::interval` — entirely in
Postgres. `pgx/v5` maps `time.Duration` to `interval` natively (verified via
`go doc`/`grep` on the driver's `pgtype` package: `registerDefaultPgTypeVariants[time.Duration](defaultMap, "interval")`),
so no serialization shim was needed. `drainCampaign` now passes the
package-level `orphanStaleAfter` var straight through — no per-call cutoff
computed from any Go clock. The `Worker.now` field this issue's first pass
introduced (its only call site) is removed entirely, restoring the class to
zero call sites, matching its state before `1bd0575`.

This changes how the two crash/resume tests
(`TestWorker_AbortBetweenSESAcceptAndStatusWrite_ResumesWithOneDuplicate`,
`TestWorker_AbortBeforeSESCall_ResumesWithNoDuplicate`) simulate a resume
happening well after `orphanStaleAfter`'s window: instead of shifting
`w2.now` forward, they now call a new test helper,
`forceOrphansStale(t)` (`internal/mailing/worker_test_helpers_test.go`),
which shrinks the package-level `orphanStaleAfter` var to `-time.Hour` for
the rest of the test (restored via `t.Cleanup`, same pattern as the existing
`setSetting` helper) — a negative duration pushes the SQL cutoff PAST
Postgres's own `now()`, catching a claim stamped microseconds ago exactly as
a real 70-second-stale claim would be caught. This package's tests never run
in parallel (`grep -rn "t.Parallel()"` — no matches), so mutating the shared
package var is safe. `TestSendStore_OrphanSweep_ResetsOnlySendingRows` and
the new `TestSendStore_OrphanSweep_LeavesFreshlyClaimedRowAlone`
(`internal/mailing/worker_store_test.go`) were updated the same way: absolute
cutoffs (`time.Now().Add(-time.Hour)` / `time.Now().Add(time.Hour)`) became
plain durations (`time.Hour` / `-time.Hour`) passed straight to the new
`OrphanSweep` signature.

**Migration comment corrected.**
`migrations/000018_add_campaign_send_state.up.sql`'s comment above the
`email_sends_status_check` widening still quoted the pre-`#0122` claim SQL
(`UPDATE email_sends SET status='sending', attempts=attempts+1 WHERE
id=$1 AND status='queued'`) without `claimed_at=now()`. Corrected to match
`ClaimRow`'s actual statement and `docs/database.md`'s already-correct
`000018` row, which quotes the same statement with `claimed_at=now()`
included. No SQL changed, only the comment — the up.sql/down.sql pair the
review already round-tripped is untouched.
