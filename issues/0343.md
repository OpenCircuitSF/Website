## Description

`ConsentBasisAdminAttested` is declared in `internal/subscribers/store.go` and
permitted by `migrations/000023`'s CHECK constraint. **Nothing writes it today.**

`#0336` narrowed `imported_30d` to `consent_basis = ConsentBasisImportedPriorConsent`
while `unsubscribed_30d` continues to exclude only `consent_basis IS NULL`. That
asymmetry is correct for the two values that exist (`#0336`'s review measured
it). It is **wrong for the third**.

The first change that writes `admin_attested` onto an import-sourced row gets:

- **no arrival** — `imported_30d` demands exactly `imported_prior_consent`, and
  `confirmed_30d` does not claim it either; and
- **a full departure** — `unsubscribed_30d`'s exclusion only fires on `IS NULL`.

Net `-1` per person. That is `#0311`'s bug reopened, silently, by a change that
was correct when made. Neither the predicate nor `#0336`'s new doc comments
mention the value.

This is filed now, while nothing writes it, precisely because the failure
appears in a *later* issue that looks unrelated — whoever adds the first
`admin_attested` writer will see a growth figure drift and have no reason to
suspect a predicate written months earlier.

## Acceptance criteria

1. `admin_attested` is handled deliberately: either `imported_30d` uses an
   `IN`-list covering every basis that represents a real arrival, or the value
   is explicitly documented as excluded with the reason.
2. Whichever is chosen, the arrival and departure predicates agree about it —
   no basis may be excluded from arrivals while counted as a departure.
3. The doc comments on `Growth30Days`, `RestartSignup`, and
   `web/src/lib/dashboard.ts`'s `formatGrowthDetail` name every `consent_basis`
   value and say which bucket each belongs to, so the next value added cannot
   be silently omitted.
4. A test asserts the three components (`confirmed`, `imported`, `unsubscribed`)
   **separately**, not the net — `#0336`'s review showed a net-only table hides
   compensating errors (its cells O3/P3 netted zero from two opposite errors).
5. Covers a row that reaches `admin_attested` and then unsubscribes, proving it
   nets 0 rather than −1. Prove by mutation against the un-fixed predicate.
6. A guard or test fails if a new `consent_basis` value is added to the CHECK
   constraint without being classified by the predicates. The value set and the
   predicate must not be able to drift apart again.
7. No migration needed; `000001`–`000022` are frozen (§1) and the tree is at
   `000025`.

### Criterion 1, 2 — one slice read by both sides, so the asymmetry cannot recur

`growthArrivalConsentBases` is read by `imported_30d`'s arrival FILTER and by
`unsubscribed_30d`'s departure FILTER as the same `$3`, in the same query. That
makes criterion 2 structural rather than asserted: there is no second place for
a value to be classified differently. Criterion 1's first option was taken (an
`IN`-list, expressed as `= ANY($3::text[])`), and `admin_attested` is in it.

### Criterion 3 — the `dashboard.ts` edit is required, not scope creep

comment-only — `formatGrowthDetail`'s body is untouched — which is why no TS
test accompanies it, matching `#0324`'s and `#0336`'s own precedent for a
comment-only change to this file. All three consent_basis values are named
with their bucket, on the Go side (`Growth30Days` and `RestartSignup` doc

### Criteria 4, 5 — component-wise, and the mutation reproduced

`TestGrowth30Days_AdminAttestedArrivalAndDeparture` asserts `confirmed`,

about two seconds and is what this review used.

### Criterion 6 — the CHECK-constraint oracle cannot silently match nothing

This was checked specifically, because an extraction that finds no values and
then asserts over an empty set is the fail-open this repo has shipped twice
(`#0258`, `#0428`). `TestConsentBasisValuesAreClassified` is fail-closed at
both stages: `t.Fatalf` when the constraint pattern does not match, and a
second `t.Fatalf` when the value pattern extracts zero entries. Probed the
regexp directly against the real migration bytes:

| Input | Result |
|---|---|
| `migrations/000023_create_subscriber_imports.up.sql` as committed | captures all three values |
| a fourth value added to the `IN` list | captures four — the new one is reported unclassified |
| the `IN (...)` reshaped to `= ANY (ARRAY[...])` | no match → `t.Fatalf`, fail-closed |

`000023` is also the right migration to read: it is the only file in
`migrations/` that creates `subscribers_consent_basis_check`, and no later
migration alters or drops it. The check is bidirectional (a permitted value
missing from the map, and a stale map entry) and additionally compares the map
against the real `growthArrivalConsentBases` slice, so the two cannot drift.
