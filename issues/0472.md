## Description

Two guards, each correct on its own, together leave **no supported configuration
in which the service starts without SES**:

- `mailing.NewSESMailer` refuses to construct without `SES_CONFIGURATION_SET`
  (`CLAUDE.md` §10 records that `docs/configuration.md` calling it optional is
  simply wrong);
- `cmd/opencircuit/main.go`'s `checkMailerNoOp` refuses to start when
  `MAILER_NOOP=true` unless `BASE_URL`'s host is `localhost` or `127.0.0.1`.

So the no-op mailer is confined to local development by design — correctly, since
§10 records that guard is what stops a production host silently swallowing every
outbound email — and the real mailer cannot be constructed without SES
configuration.

Found by `#0232`'s planning pass while measuring which integrations are actually
optional. Filed separately because **it is a real gap in this project today**,
not only an obstacle to reuse.

## Why it matters here, not just downstream

`CLAUDE.md` §10 already prescribes the intended shape: *"Turn SES off in
production is expressed as `SEND_WORKER_ENABLED=false` plus an unconfigured SES,
not as `MAILER_NOOP`."* **That sentence describes a configuration the code does
not currently permit** — an unconfigured SES stops the mailer constructing at
all. The documented answer and the enforced behaviour disagree, which is exactly
the class this phase has spent a dozen issues closing.

It also bears on `#0415`: production runs `SES_SANDBOX=false` with
`SEND_WORKER_ENABLED=true` while access may still be sandboxed, and the
"no-email" posture is the thing nobody can currently express.

## Acceptance criteria

1. Establish what §10's prescribed configuration actually does today —
   `SEND_WORKER_ENABLED=false` with SES unconfigured. **Run it**, do not reason
   about it; that is how every wrong claim in this lineage was caught.
2. Decide whether the fix is code or documentation: either the service supports
   a genuine no-email mode, or §10's sentence is corrected. **Do not weaken
   `checkMailerNoOp`** — §10 says plainly it must not be weakened, and it is the
   guard stopping a production host swallowing mail silently.
3. If a no-email mode lands, it must **fail loudly at the point of send**, not
   silently discard. §9's standing concern is mail that vanishes without trace.
4. Confirm the interaction with `#0415` and say which of the two issues owns
   correcting §10 item 2, so the same sentence is not fixed twice differently.
5. `docs/configuration.md` still lists `SES_CONFIGURATION_SET` as optional —
   §10 records this as wrong. Fix it or say which issue does.
