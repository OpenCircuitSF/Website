## Description

Two guards, each correct on its own, together leave **no supported configuration
in which the service starts without SES**:

- `mailing.NewSESMailer` refuses to construct without `SES_CONFIGURATION_SET`
  (`CLAUDE.md` §10 records that `docs/configuration.md` calling it optional is
  simply wrong);
- `cmd/opencircuit/main.go`'s `checkMailerNoOp` refuses to start when
  `MAILER_NOOP=true` unless `BASE_URL`'s host is `localhost` or `127.0.0.1`.

So the no-op mailer is confined to local development by design — correctly, since
§10 records that guard is what stops a production host silently swallowing every
outbound email — and the real mailer cannot be constructed without SES
configuration.

Found by `#0232`'s planning pass while measuring which integrations are actually
optional. Filed separately because **it is a real gap in this project today**,
not only an obstacle to reuse.

## Root cause

`cmd/opencircuit/main.go`'s `servePostgres` called `mailing.NewSESMailer(ctx,
cfg)` unconditionally whenever `MAILER_NOOP` was false, with no other branch.
`NewSESMailer` refuses to construct without `SES_CONFIGURATION_SET`, so any
instance with `MAILER_NOOP=false` (the only choice outside `localhost`, since
`checkMailerNoOp` correctly confines the no-op mailer there) and no SES
configuration failed to construct its mailer and `servePostgres` returned an
error — the process never bound its listener. `SEND_WORKER_ENABLED` played no
part in that construction at all: it only gates whether the *campaign* send
worker goroutine starts later, so CLAUDE.md §10 item 2's prescribed
"`SEND_WORKER_ENABLED=false` plus an unconfigured SES" recipe could never have
worked — it was describing a state the code had no path to.

**Confirmed by running it (criterion 1), not by reading the code.** Built the
binary, pointed it at a scratch Postgres database
(`opencircuit_test_0472`, via `scripts/testdb.sh create 0472`), and started it
with `SEND_WORKER_ENABLED=false` and every SES variable unset:

```
DATABASE_URL=postgres://opencircuit:opencircuit@localhost:5432/opencircuit_test_0472?sslmode=disable \
BASE_URL=https://www.opencircuitsf.com WEBAUTHN_RP_ID=opencircuitsf.com \
WEBAUTHN_RP_ORIGIN=https://www.opencircuitsf.com SESSION_SECRET=<32 hex chars> \
ADMIN_EMAIL=admin@example.com AWS_REGION=us-east-1 \
EMAIL_FROM=contact@mailing.opencircuitsf.com EMAIL_LIST_DOMAIN=lists.opencircuitsf.com \
SEND_WORKER_ENABLED=false PORT=18472 ./opencircuit serve
```

Output: `opencircuit: opencircuit: constructing SES mailer: mailing: cannot
construct SES mailer: missing SES_CONFIGURATION_SET`, process exit — exactly
the failure the description predicted, reproduced rather than assumed.

## Fix

**Code, not documentation (criterion 2).** `cmd/opencircuit`'s new
`newSESSender(ctx, cfg)` picks the `mailing.Mailer` that backs `sesSender`,
with a third outcome alongside the existing two:

1. `MAILER_NOOP=true` → `noOpMailingMailer` (unchanged).
2. `SEND_WORKER_ENABLED=false` **and** `SES_CONFIGURATION_SET` is empty → the
   new `mailing.UnconfiguredMailer` (`internal/mailing/unconfigured_mailer.go`).
3. Otherwise → the real `mailing.NewSESMailer(ctx, cfg)` (unchanged), which
   still fails construction loudly if SES is unconfigured — this is the
   ordinary, common-typo case (`SEND_WORKER_ENABLED` left at its `true`
   default), and it must keep crash-looping exactly as before. `checkMailerNoOp`
   itself is untouched, per the explicit prohibition.

Case 2 requires **both** conditions deliberately, not "SES unconfigured" alone
— an operator who simply forgets `SES_CONFIGURATION_SET` almost always leaves
`SEND_WORKER_ENABLED` at its default `true`, so that mistake still hits case 3
and fails loudly at boot, unchanged. Only a deliberate `SEND_WORKER_ENABLED=false`
combined with no SES configuration opts into case 2. Checking only
`cfg.SESConfigurationSet` (not `AWS_REGION`/`EMAIL_FROM`, `NewSESMailer`'s other
two checks) is sufficient because `config.Load` already requires both of those
unconditionally — by the time a `*config.Config` reaches `newSESSender` they can
never be empty, so `SES_CONFIGURATION_SET` is the only one of the three that can
actually be missing here.

**Criterion 3 — fails loudly, not silently.** `mailing.UnconfiguredMailer.Send`
always returns `mailing.ErrSESUnconfigured` and never a fake success or message
ID — the opposite of `noOpMailingMailer`, whose entire job is to look like
success for local development. No new failure-handling was needed: every
caller of `sesSender.Send` (`internal/mailing.OutboxWorker` for transactional
mail, `mailing.Worker` for campaigns, the admin test-send handler) already
retries a `Send` error on `outbound_queue`'s existing backoff and marks the row
`abandoned` after `queue_max_retries` — the same fate CLAUDE.md §10 already
documents for "a magic link requested before SES exists." `auth.Mailer`
(`regSvc`/`loginSvc`/`recoverSvc`) needed no change at all: `auth.NewSESMailer`
only enqueues onto `outbound_queue` (`#0126`) and never touches AWS directly
regardless of which `sesSender` is selected.

**Criterion 4 — `#0415` owns the sandbox-state contradiction**, unchanged by
this issue. `CLAUDE.md` §10 item 2's numbered table row (the
`SES_SANDBOX=false`/`SEND_WORKER_ENABLED=true`-while-possibly-still-sandboxed
claim) was left untouched. This issue only edited the two bullets in the
prose immediately above that table — the `MAILER_NOOP` prohibition sentence and
the now-independently-stale `SES_CONFIGURATION_SET` bullet — which are a
different part of item 2's material and not `#0415`'s subject.

**Criterion 5 — already fixed, not by this issue.** `docs/configuration.md`
already reads `**yes**, unless SEND_WORKER_ENABLED=false` for
`SES_CONFIGURATION_SET` at the start of this pass — `git log -S` shows it was
corrected to "yes, required" on 2026-08-25 (commit `049dd4d`), the same day
`CLAUDE.md`'s "the doc is wrong" bullet was written (commit `8bcc7f4`, ~17
minutes later in that day's history). The `CLAUDE.md` bullet was stale from
the moment it was written and stayed stale until this pass; it's corrected
here (see `## Files changed`), and `docs/configuration.md`'s two affected rows
(`SES_CONFIGURATION_SET`, `SEND_WORKER_ENABLED`) got an additive note about
the new conditional behavior rather than a rewrite.

## Why it matters here, not just downstream

`CLAUDE.md` §10 already prescribes the intended shape: *"Turn SES off in
production is expressed as `SEND_WORKER_ENABLED=false` plus an unconfigured SES,
not as `MAILER_NOOP`."* **That sentence describes a configuration the code does
not currently permit** — an unconfigured SES stops the mailer constructing at
all. The documented answer and the enforced behaviour disagree, which is exactly
the class this phase has spent a dozen issues closing.

It also bears on `#0415`: production runs `SES_SANDBOX=false` with
`SEND_WORKER_ENABLED=true` while access may still be sandboxed, and the
"no-email" posture is the thing nobody can currently express.

### Is the new type the minimum?

Yes, on balance. The type is a bare empty struct with one method that returns a
sentinel — roughly ten lines of behaviour, no new configuration surface, no new
guard, and no self-checking mechanism of the kind §8 warns spirals. The
existing `noOpMailingMailer` could not have been reused: its entire contract is
to look like success, which is precisely what criterion 3 forbids here.

The one alternative worth naming is that the type could have lived unexported
in `cmd/opencircuit` beside `noOpMailingMailer`, sparing `internal/mailing` a
new file and its test. Placing it next to the `Mailer` interface it satisfies
is the better home, and exporting the sentinel is what lets a caller tell this
apart from a genuine SES failure with `errors.Is`. Worth recording that
**nothing outside the tests consumes that sentinel today** — the rationale is
forward-looking, which is acceptable for a sentinel but should not be mistaken
for exercised behaviour.

### Recommendation, not a bounce — no boot-time announcement of the mode

A single startup line naming the selected mailer would close the gap. This is
outside the five criteria and below the bounce threshold, so it is reported to
the orchestrator for filing rather than filed here (§9).
