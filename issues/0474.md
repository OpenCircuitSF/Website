## Description

`interests.Store.Delete` refuses to delete an interest that is still referenced —
but its `NOT EXISTS` subquery covers **`subscriber_interests` only**.

Two other tables reference the same rows, and **both are `ON DELETE CASCADE`**:

- `workshop_interests` (`migrations/000020`)
- `campaign_interests` (`migrations/000017`)

Neither `internal/interests` nor `internal/handlers/interests.go` mentions either
table anywhere. So deleting an interest that **no subscriber has selected** — and
which therefore passes the guard — **silently drops every workshop's tag and
every campaign's recorded segment** referencing it.

Found by `#0471`'s review while checking whether that issue's documentation
overstated what an operator can safely do. **Pre-existing**: `#0024` built the
delete guard, and both `workshop_interests` and `campaign_interests` landed
afterwards, so the guard was correct when written and was never widened.

## Why it matters more than a stale check

A campaign's `campaign_interests` rows are **the record of who a sent campaign
was targeted at**. They are not working state — they are the answer to "who did
we send this to, and why", which is the same question the consent-provenance
work (`#0336`, `#0343`, `#0344`) exists to keep answerable. Losing them for a
campaign already delivered removes evidence, silently, from an admin action that
reported success.

The workshop case is more visible — a workshop loses a topic tag — but the
campaign case is the one that cannot be reconstructed.

## Acceptance criteria

1. **Re-derive the reference set** rather than trusting this issue: find every
   table with a foreign key to `interests` and its `ON DELETE` behaviour. `#0343`'s
   review did exactly this for `email_campaigns` using both a `grep` over
   `migrations/` and a `pg_constraint` query, and found one more reference than
   the prose claimed. Do both.
2. Widen the guard to cover every referencing table, **and return an error that
   distinguishes which one blocked the delete** — "still in use" without saying
   by what leaves an operator with no next step.
3. **Decide what an admin should be able to do instead.** Deactivation already
   exists and is the intended path for a retired interest; if that is the answer,
   the error should say so.
4. Prove it: seed a throwaway interest, reference it from each table in turn, and
   confirm the delete is refused each time with the right message. **Never target
   a literal or seeded id** (§9) — `#0024` permanently destroyed a seeded taxonomy
   row in the shared test database doing exactly that, and it was *this* taxonomy.
5. Check whether any interest is **currently** referenced only by a workshop or a
   campaign, since that is the population a careless delete would hit. Read-only.

  **The priority order is fine as shipped — decided, not merely noted.**
  When two tables reference the same interest only one is named, and the
  worry is an operator clearing that reference and hitting a second refusal
  nobody warned them about. That cannot happen here, because the message
  does not tell them to clear anything. Every one of the three messages
  prescribes `deactivate it instead`, and deactivation resolves the case in
  one step no matter how many tables reference the row. An operator who
  instead un-tags the named campaign and then meets the workshop refusal got
  there by ignoring the advice the message gave them. Naming all blockers
  would be a marginal improvement to a path nobody is directed down, at the
  cost of a variable-length message and a variable-length test assertion.
  Leave the order and the single-blocker message as they are.

  **What must change: the `default` branch is live, not an invariant
  violation, and it regresses a case the pre-`acdb05f` code got right.**

  The doc comment says Postgres guarantees `deleted == false` with
  `stillExists == true` and all three reference flags false cannot happen
  inside one statement. It can. Under `READ COMMITTED` the outer `SELECT`
  reads the statement snapshot while the `DELETE` inside the CTE re-checks
  the target row through `EvalPlanQual` after blocking on a concurrent
  writer's lock. Two `psql` sessions against my scratch database, session A
  holding an open transaction that had deleted the same throwaway interest
  and committing three seconds later, session B running the exact statement
  from `Store.Delete`:

      deleted | still_exists | has_subs | has_camp | has_ws
      --------+--------------+----------+----------+--------
      f       | t            | f        | f        | f

  That is the `default` branch, reached by two admins deleting the same
  unused interest at the same time. Pre-`acdb05f` the follow-up existence
  check was a *separate* statement and therefore a fresh snapshot, so it
  saw the row gone and returned `ErrNotFound` — a 404. `acdb05f` turns that
  same case into a 500 `internal server error`, because
  `AdminInterestsHandler.Delete` has no case for the wrapped error. No data
  is lost, but a correct 404 became an incorrect 500, and the comment
  asserting the case is unreachable is what would stop the next reader from
  spotting it.

  The atomicity claim the CTE was built for is otherwise sound, and I
  verified it rather than reasoning about it. On the same scratch database,
  a successful delete of an unreferenced throwaway interest returns
  `deleted=t, still_exists=t` and a follow-up count of `0` — so
  `stillExists` really does read the pre-statement snapshot, and the code is
  right to check `deleted` first and to say so in a comment. A
  workshop-referenced throwaway interest returns `deleted=f, has_ws=t` with
  the row and its join row both surviving. The reported blocker and the
  `DELETE`'s own `NOT EXISTS` clauses read one snapshot and cannot disagree.
  What the shared snapshot does **not** buy is a race-free delete, and the
  comment currently claims more than that.

  **Remedy — apply exactly this; no decision is left open.**

  1. In `internal/interests/store.go`, replace the `default:` case of
     `Delete`'s `switch` with a call to a new helper, and add the helper
     immediately after `Delete`:

     ```go
     	default:
     		// deleted is false, yet this statement's own snapshot showed the
     		// row present and no referencing row in any of the three tables.
     		// That is reachable, not an invariant violation. Under READ
     		// COMMITTED a concurrent transaction that deletes or updates the
     		// same interests row after this statement's snapshot is taken
     		// makes the DELETE affect zero rows via EvalPlanQual, while the
     		// outer SELECT still reads the pre-statement snapshot. #0474's
     		// review reproduced exactly that with two sessions. Only a fresh
     		// read can say what is true now, so take one -- it costs a second
     		// round trip on a path nothing but a concurrent admin action
     		// reaches, and the fast path above stays one atomic statement.
     		return s.deleteOutcomeAfterRace(ctx, id)
     	}
     }

     // deleteOutcomeAfterRace re-reads, in a NEW statement and therefore a
     // NEW snapshot, why Delete's atomic statement removed nothing when its
     // own snapshot said it should have. Delete's concurrent-modification
     // branch is the only caller (#0474). Returns ErrNotFound when the row
     // is gone, or the same priority-ordered sentinel Delete itself uses
     // when something now references it.
     func (s *Store) deleteOutcomeAfterRace(ctx context.Context, id int64) error {
     	var exists, hasSubscribers, hasCampaigns, hasWorkshops bool
     	if err := s.pool.QueryRow(ctx,
     		`SELECT
     		    EXISTS (SELECT 1 FROM interests WHERE id = $1),
     		    EXISTS (SELECT 1 FROM subscriber_interests WHERE interest_id = $1),
     		    EXISTS (SELECT 1 FROM campaign_interests WHERE interest_id = $1),
     		    EXISTS (SELECT 1 FROM workshop_interests WHERE interest_id = $1)`,
     		id,
     	).Scan(&exists, &hasSubscribers, &hasCampaigns, &hasWorkshops); err != nil {
     		return fmt.Errorf("interests: re-reading refused delete for id %d: %w", id, err)
     	}
     	switch {
     	case !exists:
     		return ErrNotFound
     	case hasSubscribers:
     		return ErrHasSubscribers
     	case hasCampaigns:
     		return ErrHasCampaigns
     	case hasWorkshops:
     		return ErrHasWorkshops
     	default:
     		// The row is present and unreferenced right now, so the writer
     		// that blocked the DELETE has released it and the call is simply
     		// retryable. ErrNotFound would be a lie and a table-naming
     		// sentinel would be a guess; report the transient condition.
     		return fmt.Errorf("interests: delete id %d lost a race with a concurrent modification; retry", id)
     	}
     }
     ```

     	"time"

     // waitUntilBlockedBy polls obs -- a third connection, independent of both
     // racing sessions -- until the server itself reports some other backend
     // waiting on blockerPID, and returns that backend's pid and query text.
     //
     // This is what makes the race test deterministic rather than timing
     // dependent. It contains no sleep-and-hope: the blocking transaction holds
     // its lock until the test commits it, so the condition polled for is
     // guaranteed to become true and to stay true once it does. If it somehow
     // does not, the test fails here with an explicit message rather than
     // proceeding to assert against a run in which nothing actually raced -- a
     // green result from a race test that never raced would be worse than no
     // test at all.
     func waitUntilBlockedBy(t *testing.T, obs *pgx.Conn, blockerPID uint32, since time.Time) (uint32, string, time.Duration) {
     	t.Helper()
     	ctx := context.Background()
     	deadline := time.Now().Add(25 * time.Second)
     	for time.Now().Before(deadline) {
     		var pid uint32
     		var q string
     		err := obs.QueryRow(ctx,
     			`SELECT pid, left(regexp_replace(query, '\s+', ' ', 'g'), 78)
     			   FROM pg_stat_activity
     			  WHERE $1 = ANY (pg_blocking_pids(pid))`, blockerPID).Scan(&pid, &q)
     		if err == nil {
     			return pid, q, time.Since(since)
     		}
     		if !errors.Is(err, pgx.ErrNoRows) {
     			t.Fatalf("observer query: %v", err)
     		}
     		time.Sleep(20 * time.Millisecond)
     	}
     	t.Fatalf("no backend ever blocked on pid %d: the two sessions did not interleave, so this test proved nothing", blockerPID)
     	return 0, "", 0
     }
