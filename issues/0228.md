## Description

`#0062` verified the backup/restore round trip exhaustively — row counts,
sequence positions, `schema_migrations`, every constraint definition and index
definition, both dump formats, all matching. Its phase-3 review reproduced that
independently and found the one thing the comparison did not cover.

**Table ownership is not preserved.** Source tables owned by `opencircuit`;
after restore, owned by whoever ran the restore. `backup.sh` dumps with
`--no-owner --no-privileges`, so ownership and grants do not travel.

Locally this is invisible — the restoring user happens to be able to read
everything. **On the documented production path it is not.** That path is
`sudo -u postgres pg_restore`, which would leave every table owned by
`postgres` with grants stripped — so the application role gets
`permission denied` on its first query after a restore that otherwise reported
complete success.

This is the failure mode a backup exists to prevent, arriving at the worst
moment: you restore during an incident, the restore says it worked, every row is
present, and the site stays down.

**`docs/deployment.md` currently asserts the opposite** — a parenthetical claims
`tableowner` was confirmed identical. That is true only because the local drill
runs as the owning role, and it is wrong in the general case.

**Three smaller defects in the same territory**, all found by the same review:

1. **The drill's step 1 is broken**: it calls `scripts/testdb.sh create` twice —
   and `create` drops first — then `-f seed.sql`s a file that does not exist.
2. **The drill's step 7 fails silently.** `testdb.sh drop` against a
   `restore.sh`-created database hits `ERROR: must be owner`, then prints "does
   not exist" and **exits 0**, leaving a stray database. That is a `testdb.sh`
   bug, outside `#0062`'s diff.
3. **Two undocumented behaviours worth stating**, both benign: a custom-format
   re-restore is idempotent, and a plain `.sql.gz` into a non-empty database
   aborts at the first `CREATE TABLE` with exit 3 — it fails safe.

## Acceptance criteria

- [ ] After a restore run as a role other than `opencircuit`, every table, sequence, and index is owned by `opencircuit` and the app role can read and write — demonstrated by connecting **as the app role** and issuing a real query, not by inspecting catalog rows
- [ ] The restore path does this itself, or the runbook makes it an explicit, gated step that cannot be skipped by someone following the happy path
- [ ] `docs/deployment.md`'s `tableowner` claim is corrected — it is currently false in the general case
- [ ] The drill's step 1 runs as written: one `create`, and no reference to a seed file that does not exist
- [ ] `testdb.sh drop` reports failure when it fails — a foreign-owned database must not produce "does not exist" and exit 0
- [ ] The two undocumented behaviours (idempotent custom re-restore; plain-format abort into a non-empty database) are stated in the runbook
- [ ] `#0062`'s full round-trip comparison still passes for both formats
- [ ] `ISSUE=0228 scripts/check.sh go ./internal/...` passes with zero skips

## Notes

Reported by `#0062`'s phase-3 review under `CLAUDE.md` §9.

Criterion 1's method is the point. Checking `pg_tables.tableowner` after a local
restore is exactly the check that passed while the defect was present, because
the local drill runs as the owning role. **Connect as the application role and
issue a query** — that is the only test that would have failed.

Note the review deliberately left `#0062` resolved with its S3 criteria unticked
(see `#0229`), so this issue is about the path that *was* verified, not the one
that was not.

`#0062`'s `## Review notes` carry the full snapshot-diff method — row counts,
`pg_sequences` including `is_called`, every `pg_get_constraintdef()` and
`indexdef` — which is the regression suite for criterion 7.
