## Description

`#0062` verified the backup/restore round trip exhaustively — row counts,
sequence positions, `schema_migrations`, every constraint definition and index
definition, both dump formats, all matching. Its phase-3 review reproduced that
independently and found the one thing the comparison did not cover.

**Table ownership is not preserved.** Source tables owned by `opencircuit`;
after restore, owned by whoever ran the restore. `backup.sh` dumps with
`--no-owner --no-privileges`, so ownership and grants do not travel.

Locally this is invisible — the restoring user happens to be able to read
everything. **On the documented production path it is not.** That path is
`sudo -u postgres pg_restore`, which would leave every table owned by
`postgres` with grants stripped — so the application role gets
`permission denied` on its first query after a restore that otherwise reported
complete success.

This is the failure mode a backup exists to prevent, arriving at the worst
moment: you restore during an incident, the restore says it worked, every row is
present, and the site stays down.

**`docs/deployment.md` currently asserts the opposite** — a parenthetical claims
`tableowner` was confirmed identical. That is true only because the local drill
runs as the owning role, and it is wrong in the general case.

**Three smaller defects in the same territory**, all found by the same review:

1. **The drill's step 1 is broken**: it calls `scripts/testdb.sh create` twice —
   and `create` drops first — then `-f seed.sql`s a file that does not exist.
2. **The drill's step 7 fails silently.** `testdb.sh drop` against a
   `restore.sh`-created database hits `ERROR: must be owner`, then prints "does
   not exist" and **exits 0**, leaving a stray database. That is a `testdb.sh`
   bug, outside `#0062`'s diff.
3. **Two undocumented behaviours worth stating**, both benign: a custom-format
   re-restore is idempotent, and a plain `.sql.gz` into a non-empty database
   aborts at the first `CREATE TABLE` with exit 3 — it fails safe.

## Implementation notes

**Root cause confirmed exactly as described.** `backup.sh` dumps with
`pg_dump --no-owner --no-privileges`; `restore.sh` restored with no
ownership-fixing step of its own, so every object ended up owned by whichever
role ran `pg_restore`/`psql` — `opencircuit` locally (invisible), `postgres`
on the documented production path (`sudo -u postgres`, per `restore.sh`'s
`BACKUP_RUN_AS` default) — with the app role locked out.

**Fix — `scripts/db/restore.sh`:** after the restore completes (both the
custom-format `pg_restore` branch and the plain-format `gunzip | psql`
branch — one call site, after the `case`), a new `reassign_ownership()`
function walks every table, sequence, and view in every non-system schema of
the target database and `ALTER … OWNER TO`s each one to a new `RESTORE_OWNER`
variable (default `opencircuit`, matching `scripts/db/create.sql`'s bootstrap
role; unset-only default via `${RESTORE_OWNER-opencircuit}`, same pattern as
the existing `BACKUP_RUN_AS` fix from `#0062`, so `RESTORE_OWNER=""`
genuinely skips the step rather than silently falling back). Because
ownership implies full privileges on an object in PostgreSQL, this also
restores what `--no-privileges` stripped, with no separate `GRANT` needed.
`RESTORE_OWNER` is validated against `[A-Za-z0-9_]+` before use (rejecting
anything else with exit 2) and additionally passed through SQL's
`quote_ident()` before being used in `ALTER … OWNER TO`, so it is safe even
though it is spliced into generated SQL text.

**A real implementation snag, worth recording:** the first version of
`reassign_ownership()` tried to pass `RESTORE_OWNER` into the `DO $$ … $$`
block via `psql -v owner=... ` and referenced it as `:'owner'` inside the
block body. That does not work — verified empirically, not assumed: psql's
`:'var'` interpolation does **not** reach inside a `$$`-quoted string (its
lexer treats the dollar-quoted body as opaque text it does not scan for
`:name` tokens), so every attempt raised `syntax error at or near ":"`. The
fix uses an *unquoted* heredoc with bash substituting the (already-validated)
`$owner` directly into the SQL text, with `$$` escaped to `\$\$` so bash
doesn't read it as this shell's PID.

**Fix — `scripts/testdb.sh drop`:** the old `db_exists && DROP DATABASE &&
echo dropped || echo "does not exist"` chain fell into the same `||` branch
whenever the `DROP DATABASE` failed for *any* reason — not just
non-existence — so a database that exists but is owned by a different role
(exactly what a `restore.sh RESTORE_CREATE=1` run produces at the *database*
level; see below) printed the misleading "does not exist" and exited `0`,
leaving the stray database behind. Existence and drop-success are now checked
separately; a real drop failure prints the psql error, an explanatory
message, and exits `1`.

**One more thing worth naming (not required by the acceptance criteria, but
adjacent):** `RESTORE_OWNER` reassigns ownership of the tables/sequences/views
*inside* the target database, not the database object itself. A database
`restore.sh` creates via `RESTORE_CREATE=1` is still owned, at the database
level, by whoever ran `createdb` (the `BACKUP_RUN_AS` role) — reassigning
that too would need the new owner to hold `CREATEDB` (or superuser), which
`opencircuit` is not granted in `scripts/db/create.sql`. Left alone
deliberately: the app only needs to read/write the *objects*, which the fix
now guarantees; `testdb.sh drop`'s honest failure (above) is what makes the
remaining database-level mismatch visible instead of silently lying.

**`docs/deployment.md` updated:** the drill's step 1 (double `create` call,
phantom `seed.sql` reference) is fixed to capture the DSN once; the
`tableowner` claim's parenthetical is corrected and replaced with the general
case, the fix, and how it was proven; a new step 6b demonstrates criterion
1's method directly in the copy-pasteable drill (connect as `opencircuit`,
not the restoring role); step 7's comment explains why `testdb.sh drop` may
still fail on a `RESTORE_CREATE=1` database's *database*-level ownership, and
that this is now surfaced loudly instead of silently; both undocumented
behaviours (idempotent custom re-restore; plain-format abort at exit 3 into a
non-empty target) are now stated as their own bullets rather than buried in
a sequences aside.

## Verification

2.63 2.58 2.66` (idle). This claim rests on **local Postgres**, not production
infrastructure — see the caveats below for what is not yet proven on the real
`sudo -u postgres` path (`CLAUDE.md` §10).

**Criterion 1, proved by a real dump/restore round trip against a scratch
database, not asserted:**

1. Created `opencircuit_0228src` owned by `opencircuit` (matching
   `create.sql`'s bootstrap), with a throwaway `widgets` table + rows.
2. Backed it up with the real `scripts/db/backup.sh` (`BACKUP_RUN_AS=""`,
   custom format).
3. **Before fix**: restored with the pre-fix `restore.sh` (`git show
   HEAD:scripts/db/restore.sh`, run from a scratch copy — the tracked file
   was never reverted) as `brennan` (a role distinct from `opencircuit`,
   standing in for production's `postgres`, `BACKUP_RUN_AS=""`,
   `RESTORE_CREATE=1`). Result: `tableowner` = `brennan`; connecting **as
   `opencircuit`** and running `select count(*) from widgets` returned
   `ERROR: permission denied for table widgets` — the exact failure mode the
   issue describes, reproduced, not assumed.
4. **After fix**: repeated into a fresh target with the fixed `restore.sh`.
   Result: table and sequence owner = `opencircuit`; connecting as
   `opencircuit` both `SELECT`ed (`count = 2`) and `INSERT`ed
   (`RETURNING id` succeeded) — a real query, not a catalog inspection,
   satisfying criterion 1's stated method exactly.
5. Repeated the "after" case with a **plain-format** (`.sql.gz`) dump —
   same result: owner reassigned, app role reads and writes.
6. Confirmed `RESTORE_OWNER=""` opts out cleanly: ownership stayed with the
   restoring role, no reassignment attempted, no error.
7. Confirmed the two "undocumented behaviours" still hold with the fix in
   place: a second custom-format restore over the same target came back to
   the dump's row count (idempotent, `--clean --if-exists`) with ownership
   correct again; a plain-format restore into that same now-populated target
   aborted with `ERROR: relation "widgets" already exists`, exit `3`, target
   row count unchanged (fails safe).
8. `testdb.sh drop` bug reproduced and fixed: created
   `opencircuit_test_0228dropbug` owned by `brennan`, ran the pre-fix
   `testdb.sh drop 0228dropbug` — printed "does not exist" and exited `0`
   despite the database still existing (confirmed via a follow-up catalog
   query). Ran the fixed `testdb.sh drop 0228dropbug` — printed the real
   `ERROR: must be owner of database` plus an explanatory message and exited
   `1`.
