## Description

Clearing an optional field and saving does not clear it on the server. The editors build their PATCH body by omitting empty values rather than sending `""`, so the server sees "field not supplied" — leave it alone — instead of "field set to empty" — clear it. The value silently comes back on the next load.

This affects both editors, and the second is the reason it is one issue rather than a note on `#0052`:

- `web/src/views/admin/WorkshopEditor.svelte` (`#0052`)
- `web/src/views/admin/CampaignEditor.svelte:384` — the already-committed precedent

`#0052`'s reviewer verified the precedent verbatim and ruled that following an existing convention is acceptable for that issue, while the convention itself is wrong and wants fixing in both places at once.

## Acceptance criteria

- [ ] Clearing an optional field and saving actually clears it, in both editors
- [ ] The wire format distinguishes "not supplied" from "set to empty" unambiguously — decide how (explicit `""`, `null`, or a JSON `omitempty`-aware pointer on the Go side) and apply the same choice to both editors
- [ ] The server side is checked, not assumed: confirm each handler's patch struct can actually represent an explicit clear, and fix it where it cannot — a pointer-less `string` field cannot tell `""` from absent
- [ ] Tests cover clearing at least one optional field end to end, per editor
- [ ] `scripts/check.sh web` and `ISSUE=0139 scripts/check.sh go ./internal/handlers/...` both pass

## Notes

Filed from `#0052`'s phase-3 review. Low severity, easy to hit: an admin who removes a location note or a signup URL will believe it is gone, and the public page will keep showing it.

The Go side may need the larger share of the work — if a patch struct uses plain `string` fields, no client change can express an explicit clear.
