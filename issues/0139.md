## Description

Clearing an optional field and saving does not clear it on the server. The editors build their PATCH body by omitting empty values rather than sending `""`, so the server sees "field not supplied" — leave it alone — instead of "field set to empty" — clear it. The value silently comes back on the next load.

This affects both editors, and the second is the reason it is one issue rather than a note on `#0052`:

- `web/src/views/admin/WorkshopEditor.svelte` (`#0052`)
- `web/src/views/admin/CampaignEditor.svelte:384` — the already-committed precedent

`#0052`'s reviewer verified the precedent verbatim and ruled that following an existing convention is acceptable for that issue, while the convention itself is wrong and wants fixing in both places at once.

## Acceptance criteria

- [x] Clearing an optional field and saving actually clears it, in both editors
- [x] The wire format distinguishes "not supplied" from "set to empty" unambiguously — decide how (explicit `""`, `null`, or a JSON `omitempty`-aware pointer on the Go side) and apply the same choice to both editors
- [x] The server side is checked, not assumed: confirm each handler's patch struct can actually represent an explicit clear, and fix it where it cannot — a pointer-less `string` field cannot tell `""` from absent
- [x] Tests cover clearing at least one optional field end to end, per editor

The Go side may need the larger share of the work — if a patch struct uses plain `string` fields, no client change can express an explicit clear.

## Root cause

Both editors' PATCH bodies substitute `undefined` for a blanked optional
field (`WorkshopEditor.svelte`'s `validateWorkshopForm`/`emptyToUndefined`,
`CampaignEditor.svelte:384`'s `preheader === '' ? undefined : preheader`).
`JSON.stringify` drops any key whose value is `undefined`, so the PATCH
request never mentions the field at all. That is byte-for-byte identical, on
the wire, to a request that never touched the field.

**The server side turned out to already be correct — checked, not
assumed.** Both patch structs
(`internal/handlers/admin_workshops.go`'s `patchWorkshopRequest`,
`internal/handlers/admin_campaigns.go`'s `patchCampaignRequest`) already use
`*string` pointer fields for every optional string, and both handlers already
route them through `normalizeOptionalCampaignField` (nil or `""` → cleared,
anything else → set) or, for `starts_at`/`ends_at`, `parseOptionalTime` (nil
or `""` → cleared). A `req.Field != nil` check (key present) vs. `nil` (key
absent) already distinguishes "clear" from "leave alone" correctly, and has
since `#0051`/`#0041`. `#0052`'s review guessed the Go side "may need the
larger share of the work"; it needed none. The whole defect was client-side:
the server could already represent an explicit clear, but neither editor
ever sent one.

## Fix

**Wire convention: an explicit `""` on an optional string field means
"clear it"; an omitted key means "leave it alone."** This was already the
server's convention (`normalizeOptionalCampaignField`/`parseOptionalTime`);
the fix makes both editors actually use it instead of collapsing "clear" and
"leave alone" into the same omitted-key shape.

- `web/src/lib/workshopAdmin.ts` — `ValidatedWorkshopFields`'s optional
  string fields (`summary`, `body_md`, `starts_at`, `ends_at`,
  `location_name`, `location_address`, `location_note`, `signup_url`,
  `cover_image`) are now always-present `string`, never `string | undefined`.
  `validateWorkshopForm` returns the trimmed value directly (`''` when
  blank) instead of routing it through the now-deleted `emptyToUndefined`.
  Sending `''` on Create (not just Patch) is harmless: `normalizeOptionalCampaignField('')`
  and `normalizeOptionalCampaignField(nil)` both produce `nil`, so an unset
  field on a brand-new workshop behaves identically either way.
- `web/src/views/admin/CampaignEditor.svelte` — `saveDraft` sends `preheader`
  directly (the already-trimmed `$state` value) instead of substituting
  `undefined` when blank.
- `web/src/lib/api.ts` — updated `updateWorkshop`'s and `updateCampaign`'s
  doc comments to describe the actual "omitted = unchanged, explicit `''` =
  cleared" contract, since the old wording ("send only the fields that
  changed") was already misleading before this issue (both editors always
  send the full form snapshot, not a diff).
- No Go changes. Two mutation tests (below) confirm the Go side already
  enforces this convention and would fail loudly if it regressed.

**Known, deliberately unfixed gap: `capacity`.** Workshops' `capacity` is
the one optional field that is not a string — `*int` on the wire
(`patchWorkshopRequest.Capacity`). JSON `null` and an absent key both decode
to the same `nil` pointer in Go, so there is no value this client can send
that unambiguously means "clear capacity" without a Go-side wire-type
change (e.g. a sentinel value, or restructuring the field). `#0052`'s review
(Finding 5) never named capacity among the affected fields — only
summary/location/signup URL/cover image — so this is treated as in scope for
a follow-up, not this issue. See `## Gotchas`.

## Gotchas

- **`capacity` is not covered.** It's the one optional workshop field that
  isn't string-shaped (`*int` on the wire), and Go can't tell an explicit
  JSON `null` apart from an absent key when decoding into a plain pointer —
  both produce `nil`. Fixing it needs a wire-type change on the Go side (a
  sentinel value such as `0`, since a valid capacity must already be a
  positive integer client-side; or a wrapper type that tracks "was this key
  present"). `#0052`'s review never flagged capacity as affected, and fixing
  it is a materially different, Go-side change — recommend filing a
  follow-up rather than folding it into this issue's scope.
- **The server needed no fix.** `#0052`'s review guessed "the Go side may
  need the larger share of the work" and the issue's own acceptance
  criteria said to check, not assume — checking found both patch structs
  already used pointer fields routed through an already-correct
  empty-string-means-clear helper (`normalizeOptionalCampaignField`) or an
  equivalent (`parseOptionalTime`). Don't assume this issue implies a Go
  diff exists to review; the diff here is entirely `web/`.
- **Both editors send the full form snapshot on every save, not a diff.**
  Neither `WorkshopEditor.svelte` nor `CampaignEditor.svelte` computes which
  fields actually changed — they PATCH every field's current form value
  every time. That's why sending `''` for an already-blank field is safe
  (it's a no-op clear-to-already-clear) and why `api.ts`'s old "send only
  the fields that changed" doc comment was already inaccurate before this
  issue; the updated comment describes the real contract.
- A second, unrelated agent was concurrently editing `internal/workshops/store.go`,
  `migrations/000020_create_workshops.up.sql`, `docs/database.md`, and
  `issues/0142.md` throughout this session (uncommitted the whole time). None
  of those files were touched by this issue's commit; `git diff --cached
  --name-only` was checked immediately before both `git add` and `git commit`
  to confirm only this issue's six files were staged.

### The load-bearing claim — "no Go change was needed" — is correct

Re-derived from the source, not from the implementer's account:

- `patchWorkshopRequest` (`internal/handlers/admin_workshops.go:325`) is
  pointer-typed for every field: `Title`, `Summary`, `BodyMD`, `StartsAt`,
  `EndsAt`, `LocationName`, `LocationAddress`, `LocationNote`, `SignupURL`,
  `CoverImage`, `Status` are `*string`; `Capacity` is `*int`; `InterestIDs`
  is `*[]int64`. `patchCampaignRequest` (`admin_campaigns.go:443`) is the
  same shape. **There is no plain `string` field in either struct.**
- Every merge in both `Patch` handlers is guarded by `if req.X != nil`, with
  the current row's value as the default — so an absent key genuinely means
  "leave alone".
- Inside those guards, optional strings go through
  `normalizeOptionalCampaignField` (`admin_campaigns.go:430` — `nil` or `""`
  → `nil`) and `starts_at`/`ends_at` through `parseOptionalTime`
  (`admin_workshops.go:595` — `nil` or blank → `nil`, else RFC 3339).
  `parseOptionalTime`'s `nil` branch is unreachable except via an explicit
  `""`, because it is only ever called under `req.StartsAt != nil`.

The server could already represent an explicit clear. The defect was
entirely client-side, and the issue's own guess that "the Go side may need
the larger share of the work" was wrong. Confirmed.

### End to end, per editor — and the inverse

Both new Go tests read the value back from the **database**
(`workshops.Store.GetByID` / `mailing.CampaignStore.GetByID`), not from the
response body, and both seed their own throwaway row rather than targeting a
literal id. Re-run by name with `-v`: both pass in ~0.02s against a real
database. `workshopAdmin.test.ts` re-run with `--reporter=verbose`: 39/39.

Both tests carry the leave-alone case in the same request — `signup_url` and
`subject` are never mentioned in the PATCH body and are asserted unchanged
afterwards. **That assertion was independently proved to have teeth**, which
is the regression this issue was most at risk of introducing: collapsing
`signupURL := current.SignupURL; if req.SignupURL != nil { … }` into an
unconditional `signupURL := normalizeOptionalCampaignField(req.SignupURL)`
failed with `SignupURL = <nil> after a PATCH that never mentioned it, want
unchanged "https://example.com/rsvp"`.

The production leave-alone path is real and still works: `WorkshopEditor`'s
`confirmTransition` PATCHes `{ status }` alone, mentioning no content field.
Sending a full snapshot from `save()` is safe because both editors hydrate
the form from the loaded row first (`workshopToFormFields(w)`;
`preheader = c.preheader ?? ''`), so no field is ever blanked by omission
from the form.

### Ruling 1 — `capacity` is correctly out of scope; file a follow-up

Confirmed by reading the code: `Capacity *int` with
`if req.Capacity != nil { capacity = req.Capacity }`. JSON `null` and an
absent key both decode to `nil`, so no value this client can send means
"clear capacity". Fixing it needs a Go-side wire-type change (a sentinel, or
a presence-tracking wrapper), which is a materially different change from
this issue's one-line-per-field client fix, and `#0052`'s review never named
capacity among the affected fields. **Out of scope for `#0139` — a follow-up
issue should be filed**, not left floating. Symptom to carry into it: an
admin who clears the capacity box and saves sees the old number return.

### Ruling 2 — the `workshopAdmin.ts` type change is safe

`ValidatedWorkshopFields` has exactly one consumer,
`WorkshopEditor.svelte:225`, which spreads it into `updateWorkshop`.
`emptyToUndefined` has no remaining references anywhere in `web/src`.
`createWorkshop` is called from one place, `Workshops.svelte:148`, with
`{ title }` alone — it never goes through `validateWorkshopForm`, so the
"harmless on Create" reasoning in `## Fix` describes a path that does not
currently exist (true, but moot). `undefined` cannot reach the wire by
another path: `starts_at`/`ends_at` coerce `fromDatetimeLocalValue`'s
`string | undefined` with `?? ''`, and the only remaining optional key is
`capacity`, whose omission is the known gap above rather than a leak.
`svelte-check` at 228 files / 0 errors confirms no other typed consumer
depended on the old shape.

### Ruling 3 — the two editors share the convention, with one asymmetry worth a follow-up

The wire convention itself is genuinely identical: both editors now always
emit the key, both send `''` for a blanked optional string, both hydrate
from the loaded row so a full-snapshot PATCH cannot blank anything by
accident, and both land on the same server helper.

They are not byte-for-byte identical in one respect. `workshopAdmin.ts`
trims client-side (`fields.summary.trim()`), so a whitespace-only value
becomes `''` and clears. `CampaignEditor.svelte` sends `preheader` straight
from `bind:value` with no `.trim()` anywhere, and
`normalizeOptionalCampaignField` compares `*v == ""` **without** trimming —
so a preheader left as `"   "` is stored as `"   "` rather than cleared, and
reloads looking blank. That is the same *class* of symptom this issue fixed
(the admin believes the field is gone and it is not), with a much narrower
trigger. The in-code comment added at `CampaignEditor.svelte:384` says "send
the trimmed value", which is not accurate — nothing trims it.

Not a bounce: the acceptance criterion is about blanking a field, and the
actual blanking gesture (select-all + delete) produces exactly `''`, which
works in both editors and is covered by tests. **Recommended follow-up:**
trim inside `normalizeOptionalCampaignField`
(`strings.TrimSpace(*v) == ""`), which closes it for both editors at once
and matches `parseOptionalTime`, which already trims; and correct the
`CampaignEditor.svelte:384` comment.
