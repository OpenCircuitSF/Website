## Description

`POST /api/subscribe` starts double opt-in. It must be resistant to bots and must never behave as an email-enumeration oracle.

## Root cause

Not a bug fix — a new endpoint. `internal/subscribers` (`#0025`) and `internal/mailing`/`internal/auth`'s `BuildConfirmationEmail`/`BuildAlreadySubscribedEmail` (`#0027`/`#0028`) existed but nothing called them from an HTTP path, and two data-layer gaps blocked doing so safely: no store method existed for the "unsubscribed → treat as new signup" branch (`#0025`'s review predicted this was "the single most likely place" the complained-laundering bug would return), and `Create` stamped `confirm_sent_at` at INSERT time, before any send was attempted.

## Fix

- **`internal/handlers/subscribe.go`** (new) — `SubscribeHandler.Subscribe` serves `POST /api/subscribe`. Every branch — new signup, existing `active`/`pending`/`unsubscribed`/`bounced`/`complained`, suppressed, honeypot-caught, timing-gate-caught, and every internal error along any of those paths — funnels to a single `writeSubscribeUniform202` call site that writes one package-level `subscribeResponse` value, so byte-identical output is structural, not merely tested-for. Honeypot (`website` non-empty) and the timing gate (`rendered_at`, a client-declared unix-ms timestamp, must be ≥2s in the past) are both silent 202 discards — no distinguishable signal a bot could use to tell "caught" from "accepted". Email syntax validation (`validEmailSyntax`) rejects non-ASCII input outright (see Gotchas) and a small disposable-domain blocklist (`isDisposableDomain`) is applied; both are pre-existence checks that don't depend on whether the address is already subscribed, so a 400 for either can't leak enumeration information. Interest slugs are resolved via `interests.Store.GetBySlug`, rejecting unknown or inactive slugs with 400; a nil/empty array is accepted and passed through as `nil`. A `SuppressionChecker` seam (`NoSuppressions` wired until `#0033`'s suppressions table lands) is consulted before any store write; a checker error fails safe to the uniform 202 with no mutation, same as a genuine suppression hit. `bounced` is not in the acceptance-criteria table; it's routed through the same restart path as `unsubscribed` (conservative default — see Gotchas) rather than silently doing nothing.
- **`internal/subscribers/store.go`** — added `RestartSignup` (the previously-missing "unsubscribed → new signup, fresh token" method) and `MarkConfirmationSent`. `RestartSignup` guards `statusLockedFromNonAdmin` in its own `UPDATE` exactly like every other status mutator in the package, so even a race between the handler's status read and this write (a complaint landing in between) cannot move a subscriber out of `complained`. `Create` no longer stamps `confirm_sent_at` at INSERT (`NULL` instead); the handler calls `MarkConfirmationSent` only after `mailer.Send` actually succeeds, for every branch that sends a confirmation (new, restart, resend), so a failed send never consumes the once-per-hour resend cooldown.
- **`internal/audit/actions.go`** — added `ActionSubscriberSignup` ("subscriber.signup") and `TargetSubscriber`, used by the handler's `auditSignup` (actor `NULL`, pre-auth, matching `ActionAccountRegistrationStarted`'s convention). Metadata distinguishes `"kind":"new"` vs `"kind":"restarted"` rather than separate action constants.
- **`cmd/opencircuit/main.go`** — wires `handlers.NewSubscribeHandler` on the Postgres path with a shared `internal/mailing.Mailer` (constructed once, used both directly by the subscribe handler and wrapped via the existing `auth.NewSESMailerWithSender` for the three transactional auth emails — avoids two separate SES v2 clients). Added `checkMailerNoOp`/`mailerNoOpAllowed`: refuses to start with `MAILER_NOOP=true` unless `BASE_URL`'s host is exactly `localhost` or `127.0.0.1`, and `slog.Warn`s once when honored (carried in from `#0027`'s review). `POST /api/subscribe` is rate-limited via the existing `middleware.RateLimiter` at `5/min, burst 3`, matching the auth routes' construction. Dev mode (`STORAGE=json`) passes a `nil` `*handlers.SubscribeHandler`; `mountAndServe` only registers the route when non-nil, since `internal/devstore` has no subscriber/interest backing yet (out of this issue's lane) and every other dev-mode route is unaffected.

## Gotchas

- **Suppression seam, not a real check.** `#0033` (the `suppressions` table) is a separate, later-numbered issue that `#0026` does not depend on and is not blocked by. Rather than either skip the "suppressed → 202, nothing sent" criterion or build `#0033`'s table myself (out of scope, risks conflicting with that issue's own design), I added `handlers.SuppressionChecker` — an interface `Subscribe` consults before any store write — and `NoSuppressions`, wired in `main.go` until `#0033` lands. The criterion is genuinely tested now (`TestSubscribe_SuppressedAddress_NoActionTaken` via a fake), and `#0033` only needs to implement the interface and swap the one wiring line in `main.go`.
- **`bounced` routed through the restart path.** Not in the acceptance-criteria table (only `active`/`pending`/`unsubscribed`/`complained` are enumerated). I chose to route it through the same "treat as new signup" path as `unsubscribed` rather than silently doing nothing, on the reasoning that this endpoint can't distinguish a stale hard bounce from a transient soft one, and requiring a fresh confirm click before any mail resumes is the safer direction to err in. `#0033`/`#0038` (suppression list, SES bounce/complaint ingestion) will have the classification to do better than this guess.
- **`confirm_sent_at` decision: deferred stamping, not "accept and document".** Rather than leave `Create`'s original stamp-at-INSERT behavior, I changed `Create` to leave the column `NULL` and added `MarkConfirmationSent`, called by the handler only after a send succeeds — for new signups, restarts, *and* resends. This closes the described failure mode entirely rather than accepting it.
- **Email syntax: ASCII-only, not merely "valid per RFC".** The carried-in `normalizeEmail`/CHECK-constraint disagreement is closed by rejecting any non-ASCII byte in `validEmailSyntax`, before the address ever reaches the store. This is stricter than full RFC 6531 (SMTPUTF8) support would allow, but the alternative was teaching the handler to pre-compute Postgres's exact `lower()` semantics, which is far more fragile. Flagging for the reviewer in case a wider Unicode-email allowance is wanted later — that would need a different fix at the DB layer, not just here.
- **`mailing.formatDuration` ragged-duration drift (per #0028's review, folded in here):** every `mailing.BuildConfirmationEmail` call site — new signup, restart, resend — passes the nominal `subscribeConfirmTTL` constant (7 days), never a computed remaining-time-until-expiry. Verified by reading `formatDuration`'s implementation rather than assumed.
- **Shared `mailing.Mailer` construction in `main.go`.** Rather than let the subscribe handler construct its own second SES v2 API client, `servePostgres` builds one `mailing.Mailer` and both wraps it (`auth.NewSESMailerWithSender`) for the three auth emails and passes it directly to `NewSubscribeHandler`. Neither `internal/mailing` nor `internal/auth` needed modification — both already exposed the seams this uses.
- **Dev mode (`STORAGE=json`) does not serve `POST /api/subscribe`.** `internal/devstore`'s own doc comment says subscriber/interest fakes are "added incrementally as those later phases land"; building that backing store is out of this pass's stated lane (`internal/subscribers`, `internal/handlers`, `internal/interests`, `cmd/opencircuit/main.go` — not `internal/devstore`). `mountAndServe` accepts a nilable `*handlers.SubscribeHandler` and only registers the route when non-nil, so every other dev-mode route is unaffected; only this one endpoint is unavailable under `STORAGE=json` until a devstore backing is added.
- **Not independently verified:** a live SES v2 send (per `#0027`'s own unresolved Gotcha — SES isn't configured in this environment, `CLAUDE.md` §10 item 2); this issue's tests use `mailing.RecordingMailer` throughout, per the task's "no network calls in the suite" instruction.

## Notes

PRD §6.3. **The uniform 202 is the whole security property.** Varying the response by whether an address is already on the list turns this endpoint into an email-enumeration oracle. Differentiation happens in the inbox, where only the address owner sees it. Test that the bodies are identical, not merely similar.

A subscriber with zero interests is valid and expected — they receive general announcements only. Do not reject an empty interest array.

`complained` never auto-resubscribes. Once someone has hit "this is spam", only an admin can clear that state.

### Finding 1 (blocking) — the enumeration oracle survives in the response *timing*

`mailer.Send` runs synchronously inside the request, so "an email was sent" is
directly observable as latency. Measured over a real loopback HTTP listener
driven through the production `mountAndServe`, 250 interleaved samples per
branch, latency in ms:

| branch | min | p10 | p50 | p90 | p99 |
|---|---|---|---|---|---|
| new signup | 0.404 | 0.438 | 0.717 | 1.851 | 2.201 |
| active (already-subscribed mail) | 0.064 | 0.077 | 0.130 | 0.324 | 0.410 |
| pending, resend | 0.154 | 0.174 | 0.280 | 0.696 | 0.990 |
| unsubscribed, restart | 0.413 | 0.444 | 0.736 | 1.871 | 2.443 |
| pending, in cooldown | 0.062 | 0.073 | 0.128 | 0.303 | 0.368 |
| complained | 0.062 | 0.070 | 0.126 | 0.307 | 0.443 |
| suppressed | 0.028 | 0.036 | 0.048 | 0.134 | 0.184 |
| honeypot | 0.028 | 0.036 | 0.058 | 0.135 | 0.337 |

With a mailer that never touches the network the four *existing-subscriber*
states are indistinguishable from one another (single-sample classifier
accuracy `active` vs `complained` 50.2%, `active` vs `pending-in-cooldown`
50.4% — a coin flip, which is the desired result), but a brand-new address is
separable from any existing row at 97.6–100% on a single observation, because
only that branch does an `INSERT` + `SetInterests` + audit write.

Repeating the measurement with an 80 ms mailer — the realistic cost of a
synchronous SES v2 `SendEmail` call — makes it far worse, because the split
stops being "one extra INSERT" and becomes "a network round trip or not",
n=120 per branch:

| branch | min | p10 | p50 | p90 | p99 |
|---|---|---|---|---|---|
| new signup | 82.050 | 83.931 | 87.214 | 90.042 | 99.637 |
| active | 80.728 | 82.006 | 82.959 | 83.778 | 86.288 |
| pending, resend | 81.209 | 82.842 | 84.520 | 85.505 | 86.382 |
| unsubscribed, restart | 82.328 | 84.097 | 87.710 | 89.425 | 93.158 |
| pending, in cooldown | 0.307 | 0.387 | 1.171 | 1.872 | 15.494 |
| complained | 0.157 | 0.253 | 0.802 | 1.440 | 2.642 |
| suppressed | 0.102 | 0.130 | 0.517 | 0.812 | 1.117 |
| honeypot | 0.078 | 0.093 | 0.403 | 0.659 | 0.799 |

The gap between "sent something" and "sent nothing" is ~80 ms with fully
disjoint distributions — `complained` p99 is 2.6 ms, `active` p10 is 82.0 ms, a
79 ms margin. Single-sample classifier accuracy `active` vs `complained`,
`active` vs `pending-in-cooldown`, and `new` vs `complained`: **100.0%**.

That yields a direct two-probe membership test, which was run end to end
against 60 seeded `active` addresses and 60 addresses not on the list, 120
total, classifying on the *second* probe's latency alone:

- probe an address twice in a row;
- if it was **not** on the list, probe 1 creates the `pending` row and stamps
  `confirm_sent_at`, so probe 2 hits the once-per-hour cooldown and sends
  nothing → **fast**;
- if it was **already `active`**, the "already subscribed" mail is sent on
  *every* request with no cooldown at all → **slow**.

**Result: 120/120 addresses classified correctly, 100.0%.** That is exactly the
email-enumeration oracle `CLAUDE.md` §9, PRD §6.3 and this issue's `## Notes`
exist to prevent. The byte-identical body is intact and the oracle is intact
alongside it.

Severity, honestly graded: the 80 ms signal is the exploitable one. Remote WAN
jitter would have to exceed ~79 ms to mask it in a single observation, and
averaging a handful of probes defeats far more jitter than that — so this is
practical from anywhere on the internet, not only from a co-located host. The
residual sub-millisecond `INSERT`-shaped signal that remains after the send is
taken off the request path is much weaker: burying a ~0.35 ms difference under,
say, 5 ms of jitter needs on the order of 10²–10³ samples per address, which a
*working* per-IP rate limit makes impractical. Hence the fix is graded:

1. Get `mailer.Send` off the request path (enqueue it, or dispatch it on a
   detached context) so no branch's latency depends on whether mail went out.
   This removes the whole 80 ms channel and is the one change that matters.
2. Then the residual channel is only exploitable if probing is unlimited —
   which today it is, see finding 2.

Note also that the `active` branch sends a message to a third party on *every*
request with no per-address throttle at all (verified: 20 sequential submits of
one active subscriber's address produced 20 "already subscribed" emails). That
is both the engine of the oracle above and an unauthenticated mail-amplification
vector against any confirmed subscriber, with the SES reputation consequences
that implies.

### Finding 2 (blocking) — the per-IP rate limit is bypassable in the deployed topology, and `signup_ip` is forgeable

Acceptance criterion 2 is met in the code and the wiring test proves the
limiter is attached to the real route in `mountAndServe`. It is not met in
production. `middleware.clientIP` (and `handlers.clientIP`, which supplies
`signup_ip`) take the **first** entry of `X-Forwarded-For` unconditionally,
with no trusted-proxy handling. `deploy/apache/opencircuitsf.com.conf` uses
`mod_proxy_http`, which **appends** the real peer to a client-supplied
`X-Forwarded-For` rather than replacing it — so the first entry is whatever the
client sent.

Verified end to end against `mountAndServe`, simulating exactly what Apache
forwards (`X-Forwarded-For: <spoofed>, 198.51.100.9`):

```
XFF-rotating attacker (one real source IP, 50 requests): 50/50 accepted 202 (limit is 5/min burst 3)
signup_ip recorded as consent evidence for xff-7@example.com: "172.16.0.7/32" (attacker-supplied, real peer was 198.51.100.9)
```

Two consequences, both landing on this issue's criteria:

- **Criterion 2 is defeated entirely.** One rotating header value per request
  gives every request its own fresh token bucket. The handler's own doc comment
  says the honeypot and the per-IP limiter "are what carry the real weight";
  the limiter currently carries none, which is also what makes finding 1
  cheaply exploitable at scale.
- **Criterion 8's consent evidence is attacker-controlled.** PRD §6.3 calls
  `signup_ip` "the record you produce if a deliverability complaint ever needs
  answering". A forged value makes that record worthless and lets a third party
  be framed. This is worth flagging to `#0033`/`#0038`.

The fix is to derive the client IP from the right-hand side of
`X-Forwarded-For` against a configured trusted-proxy count/CIDR (or set
`RemoteIPHeader`/`mod_remoteip` in Apache and stop trusting the header in Go).
`middleware.clientIP` and `handlers.clientIP` are duplicated implementations of
the same logic and should converge on one.

### Finding 3 (blocking) — "resend rate-limited to once per hour" is not enforced under concurrency, and this pass introduced the window

Moving the `confirm_sent_at` stamp from `Create` to a post-send
`MarkConfirmationSent` is the right call for the failure mode `#0025`'s review
raised, and the answer to "is the user stuck if the send succeeds but
`MarkConfirmationSent` fails?" is **no** — the row keeps a valid `confirm_token`,
the emailed link still works, and a resubmission re-sends immediately because
`ConfirmSentAt` is still `nil`. That direction of failure is correct.

But the cooldown is now a read-then-write with no atomicity, and the read
happens against a row that has not been stamped yet for the whole duration of
the send. Measured against the real endpoint:

```
A. 8 simultaneous submits of a BRAND-NEW address           -> 3 confirmation emails sent
B. 8 simultaneous submits of a PENDING address, confirm_sent_at = NULL -> 7 confirmation emails sent   (criterion: 1/hour)
B2. 5 SEQUENTIAL submits of that same address afterwards   -> 0 more emails (cooldown holds once stamped)
```

Case A is the plain double-submit the question asked about: `Create`'s
`ErrEmailExists` guard catches the `Create`-vs-`Create` race, but the requests
that lose it re-read the row, find a `pending` subscriber with
`confirm_sent_at = NULL`, and take the *resend* branch — so a fast double-click
does send more than one confirmation. Case B is the same window widened. Under
the old stamp-at-INSERT behaviour this could not happen; the fix traded a
"stuck for an hour after a failed send" bug for an "unbounded duplicate sends"
bug. Both are avoidable: claim the cooldown atomically *before* sending —
`UPDATE subscribers SET confirm_sent_at = $now WHERE id = $1 AND (confirm_sent_at IS NULL OR confirm_sent_at < $cutoff) RETURNING …`,
treating zero rows as "another request owns this send" — and restore the prior
value (or a sentinel) if the send then fails, so the retry property from
`#0025`'s review is kept.

  `TestSubscribe_ComplainedSubscriber_NoActionTaken` — `status = "pending", want
  unchanged "complained"`. **Additionally**, with only the *handler* mutation
  applied and the store guard intact, the end-to-end test still passes: the
  data-layer guard alone holds the line, so the defence-in-depth claim in
  `RestartSignup`'s doc comment is real and not just asserted. Both files
  restored byte-identical (`git diff` empty) and green again.
- **Honeypot** disabled (`if false && req.Website != ""`) →
  `TestSubscribe_HoneypotDiscardsSilently` fails (row created, 1 email sent).
- **Timing gate** disabled → `TestSubscribe_TimingGateRejectsTooFastOrMissing`
  fails both subtests plus the mailer assertion.
- **Rate-limiter wiring** removed from the `POST /api/subscribe` registration →
  `TestMountAndServe_RateLimitsSubscribe` fails (request 4 = 202, want 429).
  The test drives the **real** `mountAndServe` over a real listener, not a
  hand-built mux — confirmed by reading it.
- **`MAILER_NOOP` host check holds.** Every bypass attempt I could construct
  fails closed: `LOCALHOST`, `LocalHost`, `localhost.`, `localhost.:8080`,
  `[::1]`, `[::ffff:127.0.0.1]`, `0177.0.0.1`, `2130706433`, `127.1`,
  `127.0.0.001`, `localhost.evil.com`, `evil.com#localhost`,
  `evil.com?x=localhost`, `localhost@evil.com`, `localhost:8080@evil.com`,
  `localhost%2eevil.com`, `loc%61lhost`, `127%2e0%2e0%2e1`, `localhost:8080`
  (no scheme), `http:// localhost`, `HTTP://LOCALHOST`, `127.0.0.1.`, and two
  Unicode homoglyph spellings of "localhost" — all refused. Only genuine
  localhost forms are allowed, including `http://evil.com@localhost/` and
  `http://user:pass@localhost:8080`, where the *host* really is localhost and
  the string before the `@` is userinfo. `checkMailerNoOp` runs in
  `servePostgres` before the mailer is constructed, refuses with a message
  naming the offending `BASE_URL`, and warns once at `WARN` when honoured. The
  over-strict rejections (`LOCALHOST`, IPv6 `[::1]`, trailing dot) all fail in
  the safe direction; worth a one-line mention in `#0008`'s manual procedure so
  a developer on IPv6 loopback isn't puzzled by a startup refusal.
- **Uniform response, beyond the body.** The endpoint emits no rate-limit
  headers, no cookies, no conditional headers; `writeJSON` sets only
  `Content-Type`, and identical bodies give identical `Content-Length`. Status
  is 202 on every post-validation branch; the only non-202 outcomes (malformed
  JSON, invalid syntax, disposable domain, unknown interest slug, too many
  slugs) are all pre-existence checks that never read the subscribers table, so
  none of them can be driven by attacker-chosen input to distinguish one
  address from another. Confirmed by reading every path and by the mutation
  work above.
- **Test gap, minor, not blocking.** `TestSubscribe_UniformResponseAcrossBranches`
  compares status, body bytes and `Content-Type` only. A mutation adding
  `w.Header().Set("X-Suppressed", "1")` before the shared write on the
  suppressed branch — a genuine per-branch oracle — passes the test. The
  single-call-site design makes this unlikely to happen by accident, but the
  criterion says "byte-identical responses"; comparing the full header set
  (minus `Date`) would close it for the cost of three lines.

### Judgement calls the review agrees with

- **Rejecting non-ASCII email bytes: acceptable as shipped, but record it as a
  deliberate limitation with the narrower fix named.** The Go/Postgres
  disagreement is real — verified on this server (`en_US.UTF-8`): Go's
  `strings.ToLower("ǅ")` (U+01C5) yields `ǆ` (U+01C6) while Postgres `lower()`
  leaves it unchanged, so `subscribers_email_normalized` would reject the row
  the store just normalized. It is also *narrow*: across a battery of
  case-folding hazards (`İ`, `ẞ`, `Σ`, `ﬀ`, `Ⅷ`, `K`, `ß`, `ΑΣ`) that titlecase
  digraph class was the only divergence. Against that, RFC 6531 SMTPUTF8 local
  parts exist and are legitimate, and IDN domains (`someone@café.fr`) are the
  more plausible real case for a San Francisco community list — a person whose
  address contains non-ASCII simply cannot subscribe. Two things make this a
  tolerable trade rather than a defect: no mainstream consumer provider issues
  non-ASCII local parts, so the realistic incidence is very low; and the
  rejection is **not** silent — it returns `400 {"error":"invalid email"}`,
  the same as any other syntax failure, so the visitor does see a rejection
  (see the note to `#0029` below about the message). The narrower fix, for
  whenever internationalised addresses are wanted, is not "teach Go Postgres's
  `lower()`" — it is to stop normalizing in Go at all: have the store write
  `lower(trim($1))` in SQL on `Create`/`RestartSignup` and compare with
  `lower(trim($1))` in `FindByEmail`, at which point one engine defines the
  normalization, the CHECK is satisfied by construction, and the ASCII
  restriction can be dropped. That is a change to `internal/subscribers`
  (`#0025`'s layer), not to this handler.
- **`bounced` routed through the restart path**, `SuppressionChecker` as a seam
  for `#0033`, the shared `mailing.Mailer` construction, and passing the nominal
  7-day TTL to every `BuildConfirmationEmail` call site (verified by reading
  `formatDuration`) — all sound, all well argued in `## Gotchas`.
- **Dev-mode gap: acceptable, but it must be recorded for `#0029`.** With
  `STORAGE=json` the route is never registered, so `POST /api/subscribe`
  returns **`405 Method Not Allowed`** with `Allow: GET, HEAD` and a
  `text/plain` body (the `GET /` SPA catch-all matches the path but not the
  method) — not a 404, and not a JSON envelope. `./scripts/dev.sh` is
  `STORAGE=json`, so the standard dev loop cannot exercise the signup form at
  all. See the notes to `#0029` below.

### Not a defect in this issue, but it breaks verification from a clean checkout

`internal/mailing`'s golden files must contain CRLF (email bodies are CRLF per
RFC 5322), but `.gitattributes` declares `* text=auto eol=lf`, so the committed
blobs are LF-normalized. The working tree that produced them still has CRLF and
`git status` is clean, which hides it completely — but a fresh worktree at
`c0cff5d` fails four tests:
`TestBuildConfirmationEmail_Golden`, `TestBuildAlreadySubscribedEmail_Golden`,
`TestBuildRegistrationEmail_Golden`, `TestBuildRecoveryEmail_Golden`. Copying
the CRLF files back in makes them pass. This predates `#0026` (it arrived with
`#0028`'s templates) and is not this issue's to fix, but it does mean this
issue's "all 13 packages ok" claim is not reproducible from the commit, and it
will fail on CI or on any other machine. Needs its own issue: mark
`internal/mailing/testdata/*.txt` `-text` (or `binary`) in `.gitattributes` and
re-commit them with CRLF intact.
