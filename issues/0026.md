## Description

`POST /api/subscribe` starts double opt-in. It must be resistant to bots and must never behave as an email-enumeration oracle.

> 🟢 Resolved 2026-08-19 — Reviewer re-measured `5d86b4d` independently against a private `opencircuit_rev26b` database and the real `mountAndServe` listener: the ~80 ms send-or-not latency channel is gone (every branch now p99 < 6 ms), the two-probe membership attack that scored 120/120 at `c0cff5d` now scores **55.0% on 120 addresses — chance**, all four concurrency reproductions collapse to exactly one email under `-race`, migration `000011` cycles `up`/`down`/`up` with a byte-identical constraint and index set, `café`/`ǅ`-class addresses round-trip with the CHECK satisfied by construction, and the full header set minus `Date` is identical across all eleven branches including the new already-subscribed cooldown; three residuals — a `SIGTERM` that silences a visitor's retry for an hour, the absence of any regression test for the async-send property itself, and a missing `docs/database.md` row — are recorded below and routed rather than blocking.

## Root cause

Not a bug fix — a new endpoint. `internal/subscribers` (`#0025`) and `internal/mailing`/`internal/auth`'s `BuildConfirmationEmail`/`BuildAlreadySubscribedEmail` (`#0027`/`#0028`) existed but nothing called them from an HTTP path, and two data-layer gaps blocked doing so safely: no store method existed for the "unsubscribed → treat as new signup" branch (`#0025`'s review predicted this was "the single most likely place" the complained-laundering bug would return), and `Create` stamped `confirm_sent_at` at INSERT time, before any send was attempted.

## Fix

- **`internal/handlers/subscribe.go`** (new) — `SubscribeHandler.Subscribe` serves `POST /api/subscribe`. Every branch — new signup, existing `active`/`pending`/`unsubscribed`/`bounced`/`complained`, suppressed, honeypot-caught, timing-gate-caught, and every internal error along any of those paths — funnels to a single `writeSubscribeUniform202` call site that writes one package-level `subscribeResponse` value, so byte-identical output is structural, not merely tested-for. Honeypot (`website` non-empty) and the timing gate (`rendered_at`, a client-declared unix-ms timestamp, must be ≥2s in the past) are both silent 202 discards — no distinguishable signal a bot could use to tell "caught" from "accepted". Email syntax validation (`validEmailSyntax`) rejects non-ASCII input outright (see Gotchas) and a small disposable-domain blocklist (`isDisposableDomain`) is applied; both are pre-existence checks that don't depend on whether the address is already subscribed, so a 400 for either can't leak enumeration information. Interest slugs are resolved via `interests.Store.GetBySlug`, rejecting unknown or inactive slugs with 400; a nil/empty array is accepted and passed through as `nil`. A `SuppressionChecker` seam (`NoSuppressions` wired until `#0033`'s suppressions table lands) is consulted before any store write; a checker error fails safe to the uniform 202 with no mutation, same as a genuine suppression hit. `bounced` is not in the acceptance-criteria table; it's routed through the same restart path as `unsubscribed` (conservative default — see Gotchas) rather than silently doing nothing.
- **`internal/subscribers/store.go`** — added `RestartSignup` (the previously-missing "unsubscribed → new signup, fresh token" method) and `MarkConfirmationSent`. `RestartSignup` guards `statusLockedFromNonAdmin` in its own `UPDATE` exactly like every other status mutator in the package, so even a race between the handler's status read and this write (a complaint landing in between) cannot move a subscriber out of `complained`. `Create` no longer stamps `confirm_sent_at` at INSERT (`NULL` instead); the handler calls `MarkConfirmationSent` only after `mailer.Send` actually succeeds, for every branch that sends a confirmation (new, restart, resend), so a failed send never consumes the once-per-hour resend cooldown.
- **`internal/audit/actions.go`** — added `ActionSubscriberSignup` ("subscriber.signup") and `TargetSubscriber`, used by the handler's `auditSignup` (actor `NULL`, pre-auth, matching `ActionAccountRegistrationStarted`'s convention). Metadata distinguishes `"kind":"new"` vs `"kind":"restarted"` rather than separate action constants.
- **`cmd/opencircuit/main.go`** — wires `handlers.NewSubscribeHandler` on the Postgres path with a shared `internal/mailing.Mailer` (constructed once, used both directly by the subscribe handler and wrapped via the existing `auth.NewSESMailerWithSender` for the three transactional auth emails — avoids two separate SES v2 clients). Added `checkMailerNoOp`/`mailerNoOpAllowed`: refuses to start with `MAILER_NOOP=true` unless `BASE_URL`'s host is exactly `localhost` or `127.0.0.1`, and `slog.Warn`s once when honored (carried in from `#0027`'s review). `POST /api/subscribe` is rate-limited via the existing `middleware.RateLimiter` at `5/min, burst 3`, matching the auth routes' construction. Dev mode (`STORAGE=json`) passes a `nil` `*handlers.SubscribeHandler`; `mountAndServe` only registers the route when non-nil, since `internal/devstore` has no subscriber/interest backing yet (out of this issue's lane) and every other dev-mode route is unaffected.

### Phase 3 rework (`5d86b4d`, 2026-08-19) — the three blocking review findings

`cmd/opencircuit/main.go` was **not** touched by this pass (the `#0077` review was concurrently in `internal/middleware`/`internal/handlers/request.go`; this stayed out of both lanes). No new wiring was needed: the async send infrastructure self-starts inside `NewSubscribeHandler`.

- **Finding 1 (timing oracle) — `mailer.Send` is off the request path.** `internal/handlers/subscribe.go` adds `sendJob`, `sendQueue` (buffered, capacity 256) and a fixed pool of `sendWorkerCount = 4` goroutines started once in `NewSubscribeHandler`. `sendConfirmation` and `sendAlreadySubscribed` build the `mailing.Message` and hand it to `enqueueSend`, which returns immediately (non-blocking `select`/`default`); `Subscribe` itself never calls `h.mailer.Send`. A worker calls `mailer.Send` on a `context.WithTimeout(context.Background(), 30*time.Second)` — detached from the request, which has already returned. **A send failure is never silently dropped**: `processSendJob` logs it (`h.log.Error`, subscriber id + which mail) and releases the claim (below) so a later legitimate request retries; a saturated queue does the same (logs + releases) rather than blocking the response, which would have silently reopened the exact channel this closes. `waitForSends` (a `sync.WaitGroup`) is a test-only hook so `internal/handlers/subscribe_test.go` can assert on mailer/DB state deterministically despite the response no longer indicating completion.
- **Finding 1 (amplification) — the "already subscribed" email now has a cooldown.** Migration `000011` adds `subscribers.already_subscribed_sent_at`. `internal/subscribers/store.go` adds `ClaimAlreadySubscribedSend`/`ReleaseAlreadySubscribedClaim`, the same shape as the confirmation pair below. 20 sequential submits of one active subscriber's address now produce exactly 1 email, not 20 (`subscribeAlreadySubscribedCooldown = time.Hour`, reusing the only cooldown value PRD §6.3 actually names — flagged in Gotchas as a judgment call).
- **Finding 3 (unsynchronized cooldown) — the claim is now atomic.** `MarkConfirmationSent` (an unconditional stamp, called after send) is replaced by `ClaimConfirmationSend(ctx, id, now, cooldown) (bool, error)`: a single `UPDATE ... WHERE id = $1 AND (confirm_sent_at IS NULL OR confirm_sent_at < $cutoff)`, called **before** the send is enqueued. Zero rows affected means "another request owns this send" (cooldown active, or a concurrent claim already won) — not an error, just this request declining. `ReleaseConfirmationClaim` reverts to `NULL` (not the pre-claim value) on a failed send; this is provably equivalent to restoring the exact prior value here, because `ClaimConfirmationSend`'s own `WHERE` clause guarantees the prior value was already either `NULL` or more than `cooldown` old — both permit an immediate resend, same as `NULL`. `existingSignup`'s `pending` branch now calls `sendConfirmation` directly (the claim IS the cooldown check); the old separately-timed `resendConfirmation` method is gone.
- **Defect 3 (non-ASCII narrowing) — normalization moved into SQL.** `internal/subscribers/store.go`'s `Create`, `RestartSignup`-adjacent `FindByEmail`, and `Create` itself now compute `lower(trim($1))` in the SQL statement instead of calling a Go-side `normalizeEmail` (removed). `internal/handlers/subscribe.go`'s `validEmailSyntax` no longer rejects non-ASCII bytes — `net/mail.ParseAddress` already accepts UTF-8 local parts and domains (verified directly), so removing the byte-range check was the entire handler-side change. `isDisposableDomain`'s `strings.ToLower` on the domain is unaffected (ASCII-only blocklist; a non-ASCII domain just never matches, a false negative not a bypass).

## Gotchas

- **Suppression seam, not a real check.** `#0033` (the `suppressions` table) is a separate, later-numbered issue that `#0026` does not depend on and is not blocked by. Rather than either skip the "suppressed → 202, nothing sent" criterion or build `#0033`'s table myself (out of scope, risks conflicting with that issue's own design), I added `handlers.SuppressionChecker` — an interface `Subscribe` consults before any store write — and `NoSuppressions`, wired in `main.go` until `#0033` lands. The criterion is genuinely tested now (`TestSubscribe_SuppressedAddress_NoActionTaken` via a fake), and `#0033` only needs to implement the interface and swap the one wiring line in `main.go`.
- **`bounced` routed through the restart path.** Not in the acceptance-criteria table (only `active`/`pending`/`unsubscribed`/`complained` are enumerated). I chose to route it through the same "treat as new signup" path as `unsubscribed` rather than silently doing nothing, on the reasoning that this endpoint can't distinguish a stale hard bounce from a transient soft one, and requiring a fresh confirm click before any mail resumes is the safer direction to err in. `#0033`/`#0038` (suppression list, SES bounce/complaint ingestion) will have the classification to do better than this guess.
- **`confirm_sent_at` decision: deferred stamping, not "accept and document".** ~~Rather than leave `Create`'s original stamp-at-INSERT behavior, I changed `Create` to leave the column `NULL` and added `MarkConfirmationSent`, called by the handler only after a send succeeds — for new signups, restarts, *and* resends.~~ **Superseded in the phase 3 rework.** The deferred-stamp direction was right but, as the bounce review found (finding 3), a *stamp-after-send* with a separately-timed cooldown *read* is a read-then-write race under concurrency. `MarkConfirmationSent` is now `ClaimConfirmationSend` — the stamp and the cooldown check are the same atomic `UPDATE`, taken *before* the send is enqueued, with `ReleaseConfirmationClaim` as the compensating action on failure. See `## Verification`'s phase 3 subsection for the before/after concurrency numbers.
- **Email syntax: ASCII-only, not merely "valid per RFC".** ~~The carried-in `normalizeEmail`/CHECK-constraint disagreement is closed by rejecting any non-ASCII byte in `validEmailSyntax`, before the address ever reaches the store.~~ **Superseded in the phase 3 rework**, per the review's own "narrow the non-ASCII rejection" finding: normalization moved from Go into SQL (`lower(trim($1))` on `Create`/`FindByEmail`), so the Go/Postgres `lower()` disagreement this restriction existed to avoid no longer exists, and the ASCII-only rejection is gone. RFC 6531 addresses are now accepted.
- **Already-subscribed cooldown value is a judgment call.** PRD §6.3 only names a cooldown for the confirmation resend (1 hour); it says nothing about the already-subscribed email, which had no cooldown at all pre-fix. I reused `time.Hour` (`subscribeAlreadySubscribedCooldown`) on the reasoning that it's the only value PRD §6.3 gives this endpoint and the two emails share the same abuse shape. Worth the reviewer's explicit sign-off; a different value (or a per-address vs. global limit) is a one-line change (`internal/handlers/subscribe.go`).
- **Async send queue has no shutdown hook.** ~~`NewSubscribeHandler` starts `sendWorkerCount` (4) goroutines against a channel that is never closed — by design, this issue's lane is `internal/handlers`/`internal/subscribers`/`internal/mailing`, not `cmd/opencircuit/main.go`, and wiring a graceful-shutdown context through would touch the latter. In production the process only ever exits via `SIGTERM`/process death, at which point in-flight sends are simply lost (same failure mode as any other in-memory work at shutdown, no worse than before this fix — pre-fix, an in-flight synchronous send died with the request's connection anyway). A future pass wiring `main.go`'s shutdown context into `SubscribeHandler` (a `Close(ctx)` that closes `sendQueue` and waits, bounded) would close this cleanly; flagging for whoever next touches `main.go`'s shutdown path (plausibly `#0045`'s send worker, which needs the same pattern).~~ **Corrected by `#0081` (2026-08-19): the "no worse than before" claim above is false, not merely incomplete.** `#0081`'s own review (see this issue's `## Review verification`, section 5) reproduced the actual pre-`5d86b4d` behaviour directly: a killed synchronous send meant `MarkConfirmationSent` never ran, `confirm_sent_at` stayed `NULL`, and the visitor's immediate retry worked. Post-`5d86b4d`, the atomic claim (`ClaimConfirmationSend`) is taken *before* the send is even enqueued — so a `SIGTERM` landing mid-send left the claim **stamped** with the mail never sent, silencing that visitor's retry for `subscribeResendCooldown` (up to an hour), a regression this issue's own async-queue redesign introduced rather than merely carried forward. `#0081` fixes it: `SubscribeHandler.Close(ctx)` (cancels the shared send context, closes `sendQueue`, waits bounded) is now wired into `cmd/opencircuit/main.go`'s `mountAndServe` via `signal.Notify(syscall.SIGTERM, syscall.SIGINT)` + `http.Server.Shutdown`, and `deploy/systemd/opencircuit.service` sets `KillSignal=SIGTERM`/`TimeoutStopSec=30`. ### 2. The residual, measured — and one correction to the resolution notes

The disclosed residual is real and is confirmed: **probe 1** still separates a
brand-new address from an existing row, because only that branch does an
`INSERT` + `SetInterests` + audit write. Single-observation threshold accuracy
on loopback: **90.0%** back-to-back (0.275 vs 0.631 ms medians — the disclosed
~0.3–0.8 ms), rising to 95.7–98.3% in the paced regime where the gap widens to
~2.2 ms. What makes this genuinely weaker than what it replaced is not only its
magnitude but that **it is not repeatable**: probing an address creates the row,
so an attacker gets exactly one clean observation per target address, ever. It
cannot be averaged down. Over a WAN, a single observation of a 0.36 ms signal
under multi-millisecond jitter is worth close to nothing, and `#0077` has made
the 5/min-burst-3 per-IP limit real (verified: 3× `202` then 27× `429` across 30
requests from an attacker prepending `X-Forwarded-For` behind the trusted hop;
`signup_ip` recorded the real peer, `198.51.100.9`, not the attacker's
`172.16.0.0`). Accepted.

**Correction, for the record.** `## Verification` claims the residual "does
**not** separate `active`/`pending`/`complained`/`suppressed` from each other"
and that flagging a brand-new row "is not itself an enumeration answer." Both
sentences are wrong, though neither changes the verdict:

- "brand-new row created" **is** the enumeration answer — that is precisely the
  membership bit. It is defensible because it is one-shot and sub-millisecond,
  not because it leaks something else.
- The existing-subscriber branches are **not** mutually indistinguishable.
  Isolated back-to-back, n=400 each: `active` in cooldown p50 0.099 ms,
  `pending` in cooldown 0.099 ms, `complained` 0.073 ms, `suppressed` 0.038 ms.
  Threshold accuracy: `active` vs `pending` **52.0%** (genuinely chance — same
  query count), but `active` vs `complained` **95.6%**, `pending` vs
  `complained` **95.2%**, `complained` vs `suppressed` **99.0%**. The cause is
  structural and will not go away: `complained` does one query (`FindByEmail`),
  the cooldown branches do two (`FindByEmail` + the no-op claim `UPDATE`), and
  a send adds a third (`GetSetting` for the footer).

  Severity: the signal is **26 µs**, about 3,000× smaller than the 79 ms channel
  just closed, and it distinguishes *status among members*, not membership. Over
  a WAN it needs on the order of 10⁴ averaged samples per address to recover,
  against a 5/min limit. Not worth acting on now; worth knowing before anyone
  adds another query to one branch only.

### 4. The queue is bounded, and a full queue drops rather than blocks

`sendQueueCapacity = 256`, `sendWorkerCount = 4`; `enqueueSend` uses a
non-blocking `select`/`default`. Saturated deliberately (10 s mailer, 400
requests, 4 workers): **all 400 answered `202` with the byte-identical body**,
140 = 400 − 256 − 4 sends were dropped, each logged at `Error` and each with its
claim released back to `NULL` so the visitor's next attempt sends for real.
Latency under saturation did not rise (p50 0.488 ms full vs 1.000 ms empty), so
the synchronous release on the drop path does not reopen a timing difference.
This is the right one of the three bad options, and it is bounded memory:
256 × one built `mailing.Message`, a few MB ceiling. **Not the `#0073` class of
defect.** Answered.

### 5. `SIGTERM` — what actually happens, reproduced

There is no graceful shutdown **anywhere in this repo**: `mountAndServe` ends in
`http.ListenAndServe` (no `http.Server` handle, no `Shutdown`), there is no
`signal.Notify` in any file, and `deploy/systemd/opencircuit.service` sets no
`KillSignal`/`TimeoutStopSec`, so the default `SIGTERM` terminates a Go process
with no handler immediately. Reproduced the resulting state directly:

```
immediately after the 202: status=pending  confirm_sent_at=STAMPED  emails actually sent=0
after a restart, 5 retries by the same visitor -> 0 emails sent (the visitor saw 5x 202)
after the 1h cooldown expires, one retry -> 1 email sent
```

**The claim is not released on shutdown; the address goes quiet for up to one
hour.** The visitor received `202 {"message":"Check your email to confirm."}`,
no mail will ever arrive, and their retries are silenced by the cooldown the
lost send anchored. It self-heals after `subscribeResendCooldown` with no
operator action.

This also corrects one sentence in `## Gotchas`: the loss is **not** "no worse
than before this fix". Pre-`5d86b4d` a killed synchronous send meant
`MarkConfirmationSent` never ran, `confirm_sent_at` stayed `NULL`, and the
visitor's immediate retry worked. Post-fix it does not. That is a new failure
mode, honestly flagged by the implementer but understated.

**Judgement: not blocking, carried into `#0045`.** Expected impact is very small
— the window is the queue residency of a single message (~100–200 ms against a
healthy SES), so at this project's signup rate a deploy is overwhelmingly likely
to hit zero users; the worst case (SES backed up, 256 queued) is bounded, and
every case self-heals within an hour. Decisively, the fix cannot be built inside
this issue's lane: it needs `signal.Notify` and an `http.Server` in
`cmd/opencircuit/main.go`, which does not exist yet for anything, and `#0045`
owns the send worker and shutdown wiring.

### 6. Claim-before-send under process death

Same mechanism, same one-hour lockout, same `202`-then-silence. Two points for
whoever fixes it:

- **A sweep does not help.** `#0045`'s token-sweep ticker cannot distinguish a
  claim whose send is legitimately in flight from one whose process died, and a
  sweep that releases claims older than the cooldown is a no-op — the cooldown
  predicate already expires them. The real fixes are draining the queue on
  shutdown and, if the guarantee needs to be stronger than that, persisting the
  queue.
- **The unconditional `NULL` release is safe as written.** A release could in
  principle wipe a *newer* claim, but only if a send outlived the one-hour
  cooldown; `sendJobTimeout` is 30 s and `releaseSendClaim` adds 5 s, so the
  window is ~35 s against 3,600 s. Sound, and worth keeping that ratio in mind
  if either constant is ever raised.

### 7. Non-ASCII — round-trips end to end

Through the real endpoint and back out of the database, CHECK re-evaluated on
every stored value:

| submitted | stored | CHECK ok |
|---|---|---|
| `jose@café.fr` (IDN domain) | `jose@café.fr` | yes |
| `josé@example.com` (RFC 6531 local part) | `josé@example.com` | yes |
| `ǅoe@example.com` (U+01C5, the exact codepoint) | `ǅoe@example.com` | yes |
| `Ǆoe2@example.com` (U+01C4) | `ǆoe2@example.com` | yes |
| `straße@example.com` | `straße@example.com` | yes |
| `  spaced@example.com  ` | `spaced@example.com` | yes |

Every mixed-case resubmit found the existing row rather than creating a second
(7 rows from 6 first-submits + 6 case variants, the seventh being a
deliberately different address). The three paths are consistent by
construction, not by coincidence: `Create` and `FindByEmail` both compute
`lower(trim($1))` in SQL, and `RestartSignup` **never writes `email` at all** —
it keys on `id` — so there is no third normalization to disagree with. Verified
by grep that no Go-side `strings.ToLower` remains on any subscriber email path
(`isDisposableDomain`'s is on an ASCII-only blocklist lookup, a false negative
at worst). Unsubscribing `josé@example.com` and resubmitting it as
`JOSÉ@Example.com` restarted **the same row id**, `pending`.

One consequence worth knowing: normalization is now the database's, so it
follows the server's collation. This host's `lower()` leaves U+01C5 unchanged;
another build may fold it. That is harmless *within* one database — the CHECK
and the stored value are computed by the same engine — but a collation or ICU
change under an existing database (a Postgres major upgrade) could make stored
values stop matching freshly-computed ones. Standard Postgres collation hygiene,
not this issue's to solve.
