## Description

`#0325` renamed `InvalidateWorkshops` to `Invalidate` (`f7771ed`). The rename
is correct and its review verified it is mechanical — token-stream and AST
equivalence, 14 IDENT and 3 STRING tokens changed across 11 files and nothing
else.

But shortening the method name **moved two interfaces onto a type that was
never meant to satisfy them.** `*seo.Sitemap` already had an `Invalidate()`
method of its own. `handlers.workshopCacheInvalidator` and
`mailing.ArchiveCacheInvalidator` both now require exactly `Invalidate()`, so
`go/types.Implements` reports `*seo.Sitemap` as a satisfier of both — confirmed
by `#0325`'s reviewer.

The consequence is a **lost compile error**. Passing a `Sitemap` into either
seam was a type error before `f7771ed` and compiles silently after. The runtime
result would be a half-invalidation: the sitemap cleared, the meta cache left
stale — the exact failure `#0319` was filed about.

**No live code does this**, which is why `#0325` resolved and this is filed
separately rather than as a bounce. The risk class is also partly pre-existing:
`*seo.Renderer` was already a satisfier. What changed is that the accidental
satisfier set grew, silently, as a side effect of a rename.

This is the hazard `CLAUDE.md` should probably record generally: **in Go, a
rename that shortens an identifier is how accidental interface satisfaction
happens**, and nothing in the toolchain reports it.

## Acceptance criteria

1. `*seo.Sitemap` no longer satisfies `handlers.workshopCacheInvalidator` or
   `mailing.ArchiveCacheInvalidator`, or it is documented why it may.
2. The chosen mechanism is stated and justified — a distinguishing method, a
   named `seo.CacheInvalidator` the intended types implement explicitly, or an
   unexported marker.
3. Proved with `go/types.Implements`, enumerating the full satisfier set of
   both interfaces before and after, not by reading declarations.
4. `*seo.Renderer` remains a satisfier — it is the intended one — and the
   pre-existing part of the risk is either closed too or explicitly scoped out.
5. A guard prevents regrowth: an assertion naming the intended satisfier set,
   failing when an unintended type joins it. Per §8 its oracle lives outside the
   file it protects, and an empty extraction fails closed.
6. `#0326`'s `servepostgres_seo_instance_guard_test.go` identifies site-shaped
   parameters by resolving an interface whose method set is exactly
   `Invalidate()` — confirm this change does not break that discovery, and
   re-run its mutation proofs.

- 2026-08-31 — Implemented (Sonnet, phase 2), as one commit (`83036c3`) with
  `#0335` and `#0338`.
  **Mechanism chosen (criteria 1, 2).** Unexported `(*Sitemap).Invalidate` to
  `(*Sitemap).invalidate` (`internal/seo/sitemap.go`), and updated its only
  call site (`Site.Invalidate`, `internal/seo/site.go`) and every test
  reference (`sitemap_test.go`, a doc-comment mention in `site_test.go`).
  Chosen over a named `seo.CacheInvalidator` the intended types implement
  explicitly, or an unexported marker method, because it is the smallest
  change that removes exactly the unintended satisfier: `*Site` is the only
  type any production call site ever passes into either seam, and `*Site`'s
  own `Invalidate` already delegates to both `renderer.Invalidate()` and
  `sitemap.invalidate()` internally (same package, unexported access is
  fine) — no caller anywhere needs `Sitemap`'s method to stay exported.
  **Criterion 4.** `*Renderer` remains exported and satisfying — untouched by
  this fix. Its own pre-existing accidental-satisfier status (predates
  `#0325`, per that issue's own review table) is explicitly scoped OUT, not
  closed: nothing in this codebase ever passes a bare `*Renderer` into either
  seam, so it carries no live risk, and closing it would mean unexporting a
  method that's part of `*Renderer`'s otherwise-conventional public surface
  for no behavioural gain.
  **Criterion 3.** Verified with `go/types.Implements` against the real,
  compiled `internal/seo` package (`importer.ForCompiler(fset, "source",
  nil)`, ~12s per run — parses the full dependency tree from source, so not
  suitable as a fast per-run guard, used only for this one-off proof), before
  and after, enumerating `*Site`/`*Renderer`/`*Sitemap` against an ad hoc
  `Invalidate()`-only interface: before = true/true/**true**, after =
  true/true/**false**. This is the same technique `#0325`'s reviewer used.
  **Criterion 5 (regression guard).** Could not reference
  `handlers.seoCacheInvalidator` or `mailing.ArchiveCacheInvalidator`
  directly from a guard test: the former is unexported (package-private by
  design), and `internal/seo` already imports `internal/handlers` (for route
  helpers), so the reverse import needed to reach either real type from a
  test in `internal/seo` would be a cycle regardless of visibility. Instead
  added `internal/seo/invalidator_satisfier_guard_test.go`, an in-package
  `go/ast` scan (mirroring `cmd/opencircuit`'s own
  `interfaceIsInvalidateOnly`, applied to method declarations instead of
  interface declarations) asserting the exact intended satisfier set:
  `Site`=true, `Renderer`=true, `Sitemap`=false. Since none of the three
  types embeds another (plain structs, confirmed by reading all three
  declarations), "has a matching method" and "structurally satisfies any
  `Invalidate()`-only interface" are the same fact, so this is a legitimate
  in-package oracle per CLAUDE.md §8, not one needing an external harness —
  mutating `internal/seo`'s own method declarations (the guard's actual
  subject) changes what the scan finds. Mutation-proven: temporarily
  re-exported `Sitemap.invalidate` back to `Invalidate` (own edit from this
  session, backed up first, hash-verified identical after restore) —
  `TestInvalidatorSatisfierSet` correctly failed
  (`*Sitemap has an Invalidate()-only method: got true, want false`), then
  restored and re-passed.
