## Description

`#0325` renamed `InvalidateWorkshops` to `Invalidate` (`f7771ed`). The rename
is correct and its review verified it is mechanical — token-stream and AST
equivalence, 14 IDENT and 3 STRING tokens changed across 11 files and nothing
else.

But shortening the method name **moved two interfaces onto a type that was
never meant to satisfy them.** `*seo.Sitemap` already had an `Invalidate()`
method of its own. `handlers.workshopCacheInvalidator` and
`mailing.ArchiveCacheInvalidator` both now require exactly `Invalidate()`, so
`go/types.Implements` reports `*seo.Sitemap` as a satisfier of both — confirmed
by `#0325`'s reviewer.

The consequence is a **lost compile error**. Passing a `Sitemap` into either
seam was a type error before `f7771ed` and compiles silently after. The runtime
result would be a half-invalidation: the sitemap cleared, the meta cache left
stale — the exact failure `#0319` was filed about.

**No live code does this**, which is why `#0325` resolved and this is filed
separately rather than as a bounce. The risk class is also partly pre-existing:
`*seo.Renderer` was already a satisfier. What changed is that the accidental
satisfier set grew, silently, as a side effect of a rename.

This is the hazard `CLAUDE.md` should probably record generally: **in Go, a
rename that shortens an identifier is how accidental interface satisfaction
happens**, and nothing in the toolchain reports it.

## Acceptance criteria

1. `*seo.Sitemap` no longer satisfies `handlers.workshopCacheInvalidator` or
   `mailing.ArchiveCacheInvalidator`, or it is documented why it may.
2. The chosen mechanism is stated and justified — a distinguishing method, a
   named `seo.CacheInvalidator` the intended types implement explicitly, or an
   unexported marker.
3. Proved with `go/types.Implements`, enumerating the full satisfier set of
   both interfaces before and after, not by reading declarations.
4. `*seo.Renderer` remains a satisfier — it is the intended one — and the
   pre-existing part of the risk is either closed too or explicitly scoped out.
5. A guard prevents regrowth: an assertion naming the intended satisfier set,
   failing when an unintended type joins it. Per §8 its oracle lives outside the
   file it protects, and an empty extraction fails closed.
6. `#0326`'s `servepostgres_seo_instance_guard_test.go` identifies site-shaped
   parameters by resolving an interface whose method set is exactly
   `Invalidate()` — confirm this change does not break that discovery, and
   re-run its mutation proofs.

## Review notes

**Verdict: BOUNCED (phase 3, Opus, 2026-08-31).** The *fix* is correct and stays
in place — `83036c3` genuinely removes `*Sitemap` from both interfaces' satisfier
set, independently confirmed. The **guard does not meet criterion 5**: it does not
fail when an unintended type joins the satisfier set, which is the one thing
criterion 5 names. Two mutations prove the gap. The remedy is small and fully
specified below; it is additive to the existing file, and nothing already
committed needs reverting.

### What passed

- **Criteria 1, 3, 4 — the satisfier set, measured independently.** Ran
  `go/types.Implements` against the real compiled `internal/seo` (source
  importer, ~11s) and **enumerated every named type in the package** rather than
  only the three of interest — a stronger check than the implementer's, and it
  confirms no fourth satisfier was lurking. Before (`83036c3^`): `{*Site,
  *Renderer, *Sitemap}`. After (`83036c3`): `{*Site, *Renderer}`, with `*Sitemap`
  `value=false pointer=false`. Unexporting the method is the right mechanism and
  the smallest one that removes exactly the unintended satisfier.
- **Criterion 4's scoping of `*Renderer` — accepted.** Leaving
  `(*Renderer).Invalidate` exported is within what the criterion permits
  ("explicitly scoped out"), the rationale is stated, and it carries no live risk:
  nothing passes a bare `*Renderer` into either seam. Reviewed specifically and
  I do not think it should be closed here — unexporting a method on `*Renderer`'s
  otherwise-conventional public surface for no behavioural gain would be the
  worse trade. It must, however, stay *named* in the guard's intended set (it is).
- **Criterion 6.** `#0326`'s guard re-run post-fix: baseline `ok`, and two of its
  own mutation proofs still fire (`nil` to `NewAdminWorkshopsHandler` → FAIL;
  second `buildSEOSite` call → FAIL).
- **`gofmt`** stable on all three touched/added files; `ISSUE=0335r
  scripts/check.sh go ./internal/handlers/... ./internal/seo/... ./cmd/...` —
  VERIFICATION PASSED, zero skips, `internal/seo` `ok`.
- **Guard placement — the in-package home is correct.** Under CLAUDE.md §8's
  falsifiability rule this does *not* belong in an external
  `scripts/*_guard_test.sh`. The guard's subject is `internal/seo`'s own method
  declarations, and it lives in a *different file* (`invalidator_satisfier_guard_test.go`)
  from its subject (`sitemap.go`), reading that subject fresh with
  `parser.ParseFile` on every run. A mutation to the subject changes what the scan
  finds — verified: re-exporting `Sitemap.invalidate` makes it FAIL. There is no
  "oracle stored next to the question", no in-file check that the edit it guards
  could delete, and no subprocess that could answer from a stale binary. An
  external harness would have to reimplement Go parsing for no falsifiability
  gain. **Keep it in Go.**

### What must change (criterion 5)

**Gap 1 — regrowth by a NEW type is not caught.** The test iterates the
three-key `want` map and checks each, instead of iterating the *discovered* set
and rejecting anything unexpected. So a new type in this package that acquires an
`Invalidate()` method joins both interfaces' satisfier sets silently — exactly the
"the accidental satisfier set grew, silently" failure this issue was filed about,
one instance later.

Proven in a throwaway worktree by adding:

```go
type FeedCache struct{ cached []byte }
func (f *FeedCache) Invalidate() { f.cached = nil }
```

`go/types.Implements` then reports `*FeedCache` as a satisfier of both
interfaces, and `TestInvalidatorSatisfierSet` reports **`ok`**.

**Gap 2 — a value receiver defeats the scan, and the stated reason it cannot is
wrong.** `invalidateOnlyMethodReceivers` only inspects `*ast.StarExpr` receivers,
justified by the doc comment's claim that "a value-receiver method would not be
how an accidental satisfier could arise here". That is incorrect as a matter of
Go's method-set rules: **the method set of `*T` includes value-receiver methods.**
Proven in the worktree by adding:

```go
func (s Sitemap) Invalidate() {}
```

`go/types` then reports `Sitemap value=true pointer=true` — the original
regression fully restored, `*Sitemap` satisfying both seams again — while
`TestInvalidatorSatisfierSet` reports **`ok`**.

**Gap 3 (minor) — the fail-closed message describes the wrong quantity.**
`methods` maps *every* receiver type in the package to whether it has a matching
method, so `len(methods) == 0` means "found zero receiver types", not "found zero
`Invalidate()`-only method receivers" as the message asserts. The real
fail-closed behaviour is currently supplied by the `want` loop, not by this check.

### The remedy — apply exactly this

All three changes are in `internal/seo/invalidator_satisfier_guard_test.go`.

**1. Accept value receivers.** In `invalidateOnlyMethodReceivers`, replace the
receiver-type extraction:

```go
		star, ok := fd.Recv.List[0].Type.(*ast.StarExpr)
		if !ok {
			continue
		}
		ident, ok := star.X.(*ast.Ident)
		if !ok {
			continue
		}
```

with:

```go
		// Both receiver forms matter: the method set of *T includes
		// value-receiver methods, so `func (s Sitemap) Invalidate()` makes
		// *Sitemap satisfy both seams just as surely as a pointer receiver
		// does (#0337's review proved this with go/types).
		recvType := fd.Recv.List[0].Type
		if star, ok := recvType.(*ast.StarExpr); ok {
			recvType = star.X
		}
		ident, ok := recvType.(*ast.Ident)
		if !ok {
			continue
		}
```

and **delete** the doc comment's final sentence beginning "Only pointer receivers
are considered:", replacing it with one saying both receiver forms are scanned
because `*T`'s method set includes value-receiver methods.

**2. Close the regrowth gap.** After the existing `for typeName, wantSatisfies
:= range want` loop, add:

```go
	// Criterion 5's actual requirement: fail when an UNINTENDED type joins
	// the satisfier set. The loop above only re-checks the three types known
	// when this guard was written, so on its own it cannot see a new type
	// acquiring Invalidate() -- which is precisely the "the satisfier set
	// grew, silently" failure #0337 was filed about.
	for typeName, gotSatisfies := range methods {
		if !gotSatisfies {
			continue
		}
		if _, known := want[typeName]; known {
			continue
		}
		t.Errorf("%s declares an Invalidate()-only method but is not in this guard's intended "+
			"satisfier set, so it now structurally satisfies handlers.seoCacheInvalidator and "+
			"mailing.ArchiveCacheInvalidator -- either it is a deliberate new satisfier (add it "+
			"to `want` with a comment saying why) or it is #0337's defect regrowing (unexport "+
			"the method, as Sitemap.invalidate is)", typeName)
	}
```

**3. Fix the fail-closed check** so it measures what its message claims:

```go
	satisfiers := 0
	for _, has := range methods {
		if has {
			satisfiers++
		}
	}
	if satisfiers == 0 {
		t.Fatal("found zero Invalidate()-only method receivers in internal/seo -- this scan is broken " +
			"(fail closed, never treat this as 'nothing to check'): as of #0337, *Site and *Renderer " +
			"both declare one")
	}
```

replacing the current `if len(methods) == 0 {` block.

**4. Re-prove by mutation**, in a throwaway `git worktree` (never the shared
tree), restoring and hash-verifying after each. All three must FAIL:

| Mutation | Required result |
|---|---|
| re-export `Sitemap.invalidate` → `Invalidate` | FAIL (already does today — must not regress) |
| add `type FeedCache struct{}` + `func (f *FeedCache) Invalidate() {}` | FAIL — currently passes |
| add `func (s Sitemap) Invalidate() {}` | FAIL — currently passes |

Baseline unmutated must remain `ok`, and `ISSUE=NNNN scripts/check.sh go
./internal/seo/...` must pass.

No design decisions are left open here — this is transcription (CLAUDE.md §3),
so the next pass stays on Sonnet.

**Recommended for filing** (reviewers do not file issues, §9): this issue's own
description says "This is the hazard `CLAUDE.md` should probably record
generally", and it still is not recorded. Proposed title: "CLAUDE.md §8 does not
record that shortening an identifier can silently widen an interface's satisfier
set." Description: `#0325`'s `InvalidateWorkshops` → `Invalidate` rename moved two
unrelated single-method interfaces onto `*seo.Sitemap` with no source change of
its own and no toolchain diagnostic; `#0337` closed that instance, but §8 has no
entry warning that Go interface satisfaction is structural, that shortening an
identifier is the common way an accidental satisfier appears, and that
`go/types.Implements` over a package's full type set is the cheap way to check
before and after such a rename. Add it alongside the existing gotchas so the next
rename pass looks for it.
