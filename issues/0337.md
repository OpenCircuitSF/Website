## Description

`#0325` renamed `InvalidateWorkshops` to `Invalidate` (`f7771ed`). The rename
is correct and its review verified it is mechanical — token-stream and AST
equivalence, 14 IDENT and 3 STRING tokens changed across 11 files and nothing
else.

But shortening the method name **moved two interfaces onto a type that was
never meant to satisfy them.** `*seo.Sitemap` already had an `Invalidate()`
method of its own. `handlers.workshopCacheInvalidator` and
`mailing.ArchiveCacheInvalidator` both now require exactly `Invalidate()`, so
`go/types.Implements` reports `*seo.Sitemap` as a satisfier of both — confirmed
by `#0325`'s reviewer.

The consequence is a **lost compile error**. Passing a `Sitemap` into either
seam was a type error before `f7771ed` and compiles silently after. The runtime
result would be a half-invalidation: the sitemap cleared, the meta cache left
stale — the exact failure `#0319` was filed about.

**No live code does this**, which is why `#0325` resolved and this is filed
separately rather than as a bounce. The risk class is also partly pre-existing:
`*seo.Renderer` was already a satisfier. What changed is that the accidental
satisfier set grew, silently, as a side effect of a rename.

This is the hazard `CLAUDE.md` should probably record generally: **in Go, a
rename that shortens an identifier is how accidental interface satisfaction
happens**, and nothing in the toolchain reports it.

### What must change (criterion 5)

**Gap 1 — regrowth by a NEW type is not caught.** The test iterates the
three-key `want` map and checks each, instead of iterating the *discovered* set
and rejecting anything unexpected. So a new type in this package that acquires an
`Invalidate()` method joins both interfaces' satisfier sets silently — exactly the
"the accidental satisfier set grew, silently" failure this issue was filed about,
one instance later.

Proven in a throwaway worktree by adding:

```go
type FeedCache struct{ cached []byte }
func (f *FeedCache) Invalidate() { f.cached = nil }
```

`go/types.Implements` then reports `*FeedCache` as a satisfier of both
interfaces, and `TestInvalidatorSatisfierSet` reports **`ok`**.

**Gap 2 — a value receiver defeats the scan, and the stated reason it cannot is
wrong.** `invalidateOnlyMethodReceivers` only inspects `*ast.StarExpr` receivers,
justified by the doc comment's claim that "a value-receiver method would not be
how an accidental satisfier could arise here". That is incorrect as a matter of
Go's method-set rules: **the method set of `*T` includes value-receiver methods.**
Proven in the worktree by adding:

```go

```

`go/types` then reports `Sitemap value=true pointer=true` — the original
regression fully restored, `*Sitemap` satisfying both seams again — while
`TestInvalidatorSatisfierSet` reports **`ok`**.

**Gap 3 (minor) — the fail-closed message describes the wrong quantity.**
`methods` maps *every* receiver type in the package to whether it has a matching
method, so `len(methods) == 0` means "found zero receiver types", not "found zero
`Invalidate()`-only method receivers" as the message asserts. The real
fail-closed behaviour is currently supplied by the `want` loop, not by this check.

Gaps 4 and 5 are the same root cause, and it is one the guard's own doc comment

question is not a check.

**Gap 6 — a GENERIC receiver is skipped entirely.**

```go
type FeedCache[T any] struct{ cached []T }

func (f *FeedCache[T]) Invalidate() { f.cached = nil }
```

`types.Instantiate(FeedCache, int)` → `*FeedCache[int] pointer=true`, a satisfier.
Guard: **ok**. Cause: `func (f *FeedCache[T]) …` parses its receiver as
`*ast.StarExpr{X: *ast.IndexExpr{X: Ident("FeedCache")}}`, so unwrapping only the
star yields an `*ast.IndexExpr`, the `*ast.Ident` assertion fails, and the
declaration is `continue`d — the type never even enters `methods`. Two or more
type parameters give `*ast.IndexListExpr` and behave the same.

**Not a defect, recorded so it is not re-litigated:** `type FeedCache = Renderer`
(an alias) also stays green while `go/types` lists `FeedCache` as a satisfier —
but an alias denotes the *same type*, so nothing new joined the set, only a new
spelling of `*Renderer`. Leave it. Likewise, a type declared in a `_test.go` file
is deliberately out of scope: the seams are wired from non-test code.

**3. Add its helper**, at the end of the file:

```go
// structTypesWithEmbeddedFields parses every non-test .go file in dir and
// returns, sorted, the name of every struct type declared there that has at
// least one embedded (anonymous) field. It exists because
// invalidateOnlyMethodReceivers reads method declarations, and an embedded
// field can supply Invalidate() with no declaration to read: `struct{ *Site }`
// and `struct{ cacheInvalidator }` both make the outer type satisfy every
// Invalidate()-only seam. Deciding whether a particular embedding does that
// needs full type information (the embedded type may come from another
// package), so this reports the construct rather than trying to resolve it --
// the caller fails closed on anything not explicitly reviewed. Interface type
// declarations are deliberately not reported: an interface in this package
// whose method set is Invalidate() is a declared seam, not a concrete type
// accidentally joining one.
func structTypesWithEmbeddedFields(t *testing.T, fset *token.FileSet, dir string) []string {
	t.Helper()
	entries, err := os.ReadDir(dir)
	if err != nil {
		t.Fatalf("read dir %s: %v", dir, err)
	}

	var found []string
	for _, e := range entries {
		name := e.Name()
		if e.IsDir() || !strings.HasSuffix(name, ".go") || strings.HasSuffix(name, "_test.go") {
			continue
		}
		file, err := parser.ParseFile(fset, dir+string(os.PathSeparator)+name, nil, 0)
		if err != nil {
			t.Fatalf("parse %s: %v", name, err)
		}
		ast.Inspect(file, func(node ast.Node) bool {
			ts, ok := node.(*ast.TypeSpec)
			if !ok {
				return true
			}
			st, ok := ts.Type.(*ast.StructType)
			if !ok || st.Fields == nil {
				return true
			}
			for _, field := range st.Fields.List {
				if len(field.Names) == 0 {
					found = append(found, ts.Name.Name)
					return true
				}
			}
			return true
		})
	}
	sort.Strings(found)
	return found
}
```

### Why criterion 5 is now met — a completeness argument, not a hole count

The three prior rounds all closed holes by enumeration, which is why each one
found a new one. The argument that ends that regress is structural: **in Go a
named concrete type acquires a method in exactly two ways** — a method
declaration whose receiver base type is that type, or promotion from an
embedded field, which requires a struct with an anonymous field. There is no
third way. The guard now covers the first exhaustively across every spelling a
receiver can take (value, pointer, blank name, one/two/three-plus type
parameters, any file in the package, build constraints included), and it
**refuses to answer at all** on the second. So the AST substitution is sound for
concrete types in `internal/seo` — closed by refusal rather than by modelling,
which is the right shape when the alternative is reimplementing method-set
resolution. N1's and N2's survivals are outside the property, not gaps in it.
