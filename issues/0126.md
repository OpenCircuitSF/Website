## Description

Confirmation email is dispatched from an in-process goroutine with about a second of SES retry, so an SES outage or a process restart loses a signup silently — the subscriber sits `pending` and never hears anything. Move transactional mail onto a database-backed queue with real backoff, and add an append-only activity log recording every meaningful thing that happens to an address.

## Acceptance criteria

**Outbound queue**

- [x] Migration creates `outbound_queue` per PRD §6.2
- [x] `Enqueue` happens inside the same transaction as the state change that caused it — a committed signup can never have an unsent confirmation
- [x] A worker claims due rows (`status = 'queued' AND next_attempt_at <= now()`), stamps `claimed_at`, and releases on completion
- [x] Backoff schedule 1m, 5m, 15m, 1h, 6h, 24h; `queue.max_retries` default 8, then terminal `abandoned` with the last error retained
- [x] An orphan sweep reclaims rows whose worker died, using the same approach as `email_sends` — and **not** the unconditional sweep `#0122` reports as a defect
- [x] `payload` stores template inputs, not rendered MIME, so a template fix applies to queued mail
- [x] `POST /api/subscribe` enqueues instead of calling the mailer through `subscribe.go`'s goroutine; the in-memory `sendQueue` and its `Close` path are removed
- [x] `#0081`'s graceful-shutdown property is preserved or superseded — shutdown drains claims rather than losing them — **re-ticked by the fix pass: `OutboxWorker.Stop` now releases claimed-but-unsent rows via a new `releaseAll`, proved by `TestOutboxWorker_Stop_ReleasesClaimedRow`, which constructs a real worker and calls `Stop`; see `## Fix pass`**
- [x] The uniform `202` and byte-identical response bodies of `POST /api/subscribe` are unchanged (CLAUDE.md §9), and the timing-oracle hardening from `#0088` still holds
- [x] Registration and recovery mail (`internal/auth`) move onto the same queue — see Implementation notes for the one disclosed atomicity gap
- [x] Admin alerts from `#0124`'s circuit breaker use `kind = 'admin_alert'` — the kind, template, and enqueue path exist and are tested; `#0124` itself supplies the trigger (plan §9 item 7)
- [x] Queue depth and abandoned count appear on the admin overview (`#0061`)

**Activity log**

- [x] Migration creates `subscriber_events` per PRD §6.2 with its three indexes
- [x] `action` is a closed set validated in Go, matching PRD §6.11's table exactly. An unknown action is a programming error, not a stored row
- [x] Every action in that table **with a live call site today** is written at its point of occurrence; the nine that need a later issue's feature (welcome/import/invite) are reserved constants with a named owner (plan §9 item 1)
- [x] `email` is snapshotted on every row so history survives erasure of the subscriber row
- [x] `#0060`'s GDPR erasure redacts the `email` column and nulls `subscriber_id` on that address's event rows rather than deleting them — the erasure's own evidence must survive it — **re-ticked by the fix pass: the redaction predicate now also matches by normalized email, closing the `suppressed`/`unsuppressed` (`subscriber_id = NULL`) leak; see `## Fix pass`**
- [x] The subscriber detail drawer (`#0032`) renders the address's event history
- [x] `subscriber_events` is append-only; no update or delete path outside erasure redaction

### 0. Shape of the change

Two new tables, one new leaf package, one new worker, and a set of write points
threaded through code that already exists. Nothing about `POST /api/subscribe`'s
observable behaviour changes.

| New | Where | Why there |
|---|---|---|
| `outbound_queue` + its store | **new package `internal/outbox`** | must be callable from `internal/subscribers`, `internal/auth`, `internal/handlers` and `internal/mailing` inside *their* transactions |
| the queue's worker | `internal/mailing` (`outbox_worker.go`) | it needs `mailing.Mailer` and the `Build*Email` template family |
| `subscriber_events` + its writer | `internal/subscribers` (`events.go`) | subscriber-scoped, and it must be redacted inside `Erase`'s existing transaction |

**The import graph forces this.** `go list -deps` says `internal/mailing` →
`internal/subscribers`, and `internal/subscribers` imports nothing internal at
all. So `subscribers` can never import `mailing`. If the queue lived in
`mailing`, `subscribers.Confirm` could not enqueue inside its own transaction —
which is the one property this issue exists to establish. `internal/outbox` must
therefore be a **leaf: no internal imports, and specifically not `mailing`**
(`subscribers` → `outbox` → `mailing` → `subscribers` is a cycle). It owns the
table, the `Kind` constants, the payload structs, and the claim/backoff/sweep
SQL. It does not know what an email looks like.

`subscriber_events` does **not** need a package of its own: `subscribers` is
already a leaf that every relevant caller imports, and the erasure redaction has
to run inside `Erase`'s transaction anyway.

### 2. The queue — `internal/outbox`

```go
package outbox   // imports: context, time, encoding/json, pgx. Nothing internal.

type Kind string
const (
    KindConfirmation      Kind = "confirmation"
    KindAlreadySubscribed Kind = "already_subscribed"
    KindWelcome           Kind = "welcome"          // producer lands in #0127
    KindGoodbye           Kind = "goodbye"          // no producer yet
    KindAdminAlert        Kind = "admin_alert"      // producer lands in #0124
    KindRegistration      Kind = "registration"
    KindRecovery          Kind = "recovery"
    KindSessionsRevoked   Kind = "sessions_revoked" // exists today (#0076); see §9
    KindImportInvite      Kind = "import_invite"    // producer lands in #0129
)

type Item struct {
    Kind         Kind
    Recipient    string
    SubscriberID *int64
    Payload      any      // marshalled to JSONB
}

func (s *Store) EnqueueTx(ctx context.Context, q Querier, it Item) (int64, error)
func (s *Store) Enqueue(ctx context.Context, it Item) (int64, error)   // pool, for callers with no tx
```

`Querier` is the same `Exec/QueryRow` shape `internal/audit` already uses, so
`*pgxpool.Pool` and `pgx.Tx` both satisfy it. `EnqueueTx` is the only enqueue any
state-changing caller may use.

Store methods, modelled on `mailing.SendStore` because that shape is already
reviewed and already survived `#0122`:

| Method | SQL |
|---|---|
| `ClaimDue(ctx, limit)` | `UPDATE … SET status='sending', attempts=attempts+1, claimed_at=now() WHERE id IN (SELECT id FROM outbound_queue WHERE status='queued' AND next_attempt_at <= now() ORDER BY next_attempt_at, id LIMIT $1 FOR UPDATE SKIP LOCKED) RETURNING …` |
| `MarkSent(ctx, id, messageID)` | `… SET status='sent', ses_message_id=$2, sent_at=now(), payload='{}'::jsonb WHERE id=$1 AND status='sending'` |
| `MarkRetryOrAbandon(ctx, id, errMsg, maxRetries)` | `… SET status = CASE WHEN attempts >= $3 THEN 'abandoned' ELSE 'queued' END, error=$2, next_attempt_at = now() + <backoff(attempts)>, claimed_at=NULL WHERE id=$1 AND status='sending'` |
| `Release(ctx, id)` | `… SET status='queued', claimed_at=NULL WHERE id=$1 AND status='sending'` — shutdown, so a claimed-but-unsent row is retried immediately rather than waiting out the sweep |
| `OrphanSweep(ctx, staleAfter)` | `… SET status='queued', claimed_at=NULL WHERE status='sending' AND (claimed_at IS NULL OR claimed_at < now() - $1::interval)` |
| `Counts(ctx)` | queued / sending / sent / failed / abandoned + oldest queued age, for `#0061` |

Note `SKIP LOCKED` on the claim: unlike `email_sends`, whose worker is
single and serial per campaign, this queue may be claimed by more than one poll
pass. It is not strictly required with one worker, and it is free insurance.

**`status = 'failed'` is not used by this issue.** PRD §6.2 lists it in the
column comment; the state machine here is `queued → sending → sent | abandoned`.
Reserve `failed` rather than inventing a use for it.

#### Decision — retry, backoff, and dead-lettering

`attempts` is incremented by the claim (exactly as `SendStore.ClaimRow` does), so
inside the send it is the 1-based attempt number.

```
backoff = [1m, 5m, 15m, 1h, 6h, 24h][min(attempts-1, 5)]
```

The acceptance criterion pairs a **six-step** schedule with **`max_retries`
default 8**, and says nothing about attempts 7 and 8. Clamping to the last step
(24h) is the reading taken here; the alternative (stop at six) contradicts the
stated default. State the clamp in a comment so nobody "fixes" it later.

`queue.max_retries` is read from `settings`. **Use the key `queue_max_retries`**
— every existing settings key is snake_case with no dots (`max_send_rate`,
`soft_bounce_threshold_count`, `physical_address`), and `UpdateSetting` only
mutates keys that already exist, so the migration must seed the row exactly as
`000015`/`000018` seed theirs, with the same in-code fallback to 8 if the row is
missing or unparseable. Seeding a `settings` row is not a §6.2 schema change and
does not touch either PRD guard.

**Dead-lettering.** `abandoned` is terminal and nothing retries it
automatically. There is deliberately **no** `subscriber_events` action for
abandonment: PRD §6.11's action set is closed and has no failure counterpart to
`confirmation_sent`, and the criteria say an unknown action is a programming
error. The `outbound_queue` row *is* the record — `status='abandoned'` with the
last `error` retained — and it is surfaced by the overview counter (§7) and, per
address, by `#0128`. **No requeue endpoint in this issue** (§8).

#### Decision — extend `#0045`'s worker, or a new one? A new one.

A new `mailing.OutboxWorker`, in the same process, with its own `Run`/`Stop`,
wired in `cmd/opencircuit/main.go` beside `sendWorker`.

`mailing.Worker`'s claim unit is a *campaign*, and it drains one campaign to
completion before returning to its ticker (`worker.go`'s `Run`: "there is no
concurrency across campaigns within one Worker"). Folding transactional mail
into it would put a confirmation email behind a five-thousand-recipient drain —
the exact failure this issue is closing, reintroduced with a different cause.
Reuse the *shape* — atomic claim, staleness-gated orphan sweep, detached
contexts bounded by `sendMessageTimeout`/`writeStatusTimeout`, signal-based
`Stop` — and none of the code path.

**`orphanStaleAfter` must be recomputed, not shared.** Copy `worker.go`'s
derivation (`2 × (sendMessageTimeout + writeStatusTimeout)`) as an
`outboxOrphanStaleAfter` var in the new file, sized against those two timeouts —
not against measured machine load (CLAUDE.md §5).

**Copy `#0122`'s fix, not `#0122`'s defect.** The sweep is gated on
`claimed_at < now() - staleAfter`. An unconditional sweep un-claims a row a live
worker is mid-send on and mails it twice. Mirror
`TestWorker_TwoWorkersOneCampaign_OrphanSweepDuringLiveClaim_NoDuplicate` for
this queue.

**Rate limiting.** Give the outbox worker its own `rate.Limiter` at the existing
`max_send_rate` setting. Two workers can therefore momentarily exceed that rate
while a campaign is draining. That is accepted: transactional volume here is a
handful of messages a minute, SES's account rate is the real ceiling, and
CLAUDE.md §5 is explicit that there is no performance requirement in this
project. Say so in a comment rather than inventing a shared limiter.

#### Decision — payload contents, and the token-archive problem

`payload` stores **template inputs, not rendered MIME** (criterion), so a
template fix applies to mail already queued. For `confirmation` that means
`{"confirm_token": …, "manage_token": …, "ttl_seconds": 604800}`.

That archives a live secret in a second table. `subscribers.confirm_token` is
already plaintext, so this is not a new *class* of exposure — but a `sent` queue
row otherwise keeps the token forever, long after the row's purpose ends.

**Decision: `MarkSent` blanks `payload` to `'{}'::jsonb` in the same UPDATE.**
One extra `SET`, no sweep, no new job; the token's lifetime in the queue equals
the row's queued lifetime. `attempts`, `error`, `ses_message_id` and `sent_at`
— everything with forensic value — survive. **`abandoned` rows keep their
payload**, because that row is the diagnostic and the token is dead anyway.

Rejected alternative: store only `subscriber_id` and re-read the live token at
render time. It is tidier for subscriber mail and impossible for
registration/recovery (whose tokens live in `pending_registrations` and the
recovery table, not in a row the renderer is given a handle to), so it would
split the payload contract by kind for no gain.

### 3. Rendering, and where the `physical_address` rule lands

The worker switches on `kind` and calls the existing builders in
`internal/mailing/transactional_templates.go`, resolving `physical_address` from
`settings` **at send time**. This is a small improvement: an address set between
enqueue and send now produces a correct footer, where today it would not.

**Do not add a physical-address refusal to this worker.** CLAUDE.md §9's rule is
about `#0045`'s *campaign* send worker, and `BuildConfirmationEmail` already
documents `""` as simply omitting the line. Refusing to send a confirmation
because a setting is unset would turn a cosmetic gap into a broken signup flow.
`#0045`'s check is untouched by this issue and must stay untouched.

**One new template: `BuildAdminAlertEmail(subject string, lines []string, …)`.**
Small, generic, golden-file tested with CRLF fixtures per `#0078`. It is in scope
here rather than in `#0124` so that `#0124` supplies only inputs and a trigger —
which is the whole point of `#0126` blocking it.

### 4. Cutting `POST /api/subscribe` over

This is the part with the sharpest constraints, because two resolved issues have
already hardened this handler and both must survive intact.

**The enqueue happens in `processMutateJob`'s path, never on the request
goroutine.** `#0088` moved every branch-dependent write off the request path; the
request path is two fixed reads plus a channel send, and that is what makes the
endpoint not a timing oracle. Adding a database write to `Subscribe` would
reopen `#0088` exactly. The uniform `202` and its byte-identical body
(CLAUDE.md §9) are untouched — no branch gains or loses work that a client can
observe.

**Collapse claim-and-enqueue into one store call.** All three confirmation call
sites (`newSignup`, `restartSignup`, the pending resend in `existingSignup`) go
through `sendConfirmation`, which today does `ClaimConfirmationSend` and then
`enqueueSend`. Replace with a single `subscribers` method that runs both in one
transaction:

```go
func (s *Store) ClaimAndEnqueueConfirmation(ctx, sub Subscriber, now time.Time,
        cooldown time.Duration) (claimed bool, err error)
```

The conditional `UPDATE … confirm_sent_at` **is** the state change, and the
`outbound_queue` INSERT commits with it or not at all. The atomic-claim
anti-abuse property from `#0026` (which is also PRD §6.3's once-per-hour resend
limit, and what stops concurrent double-submits mailing twice) is preserved
exactly — it becomes *stronger*, because the claim can no longer be stamped for
a send that then fails to be queued.

Same treatment for `sendAlreadySubscribed` →
`ClaimAndEnqueueAlreadySubscribed`.

**A brand-new signup must be one transaction end to end.** Criterion:
"a committed signup can never have an unsent confirmation". `Create` followed by
`ClaimAndEnqueueConfirmation` is two transactions, and a crash between them
leaves precisely the state the criterion forbids. So `Create` itself
(insert + claim + enqueue) becomes one transaction — a new row has no cooldown to
lose, so the claim is unconditional there. `SetInterests` stays a separate call
and stays allowed to fail without failing the signup (`newSignup`'s existing
comment explains why; do not fold it in).

**Release-on-failure disappears.** `ReleaseConfirmationClaim` /
`ReleaseAlreadySubscribedClaim` existed because a failed in-memory send had to
un-stamp the cooldown so a later request could retry. The queue retries on its
own now, so the compensating action has no job. Remove the release path with the
send queue; keep the two store methods only if something else calls them (check
before deleting).

**What "remove the in-memory `sendQueue` and its `Close` path" means precisely.**
Delete `sendJob`, `sendQueue`, `sendWG`, `sendQueueCapacity`, `sendWorkerCount`,
`runSendWorker`, `processSendJob`, `enqueueSend`, `releaseSendClaim`,
`sendJobTimeout`. **Keep `Close`, `mutateQueue`, `mutateWG`, `sendCtx`/
`sendCancel`** — `#0088`'s mutation queue still exists and still must be drained
at shutdown, and it is now the thing that commits the enqueue. Rename
`waitForSends` → `waitForMutations` and `sendCtx` → `jobCtx` while you are there,
or leave the names; do not leave a `sendCtx` that nothing sends on without a
comment. `h.mailer` on `SubscribeHandler` becomes unused — remove the field and
the constructor parameter, and update `cmd/opencircuit/main.go`.

**Test surface.** `internal/handlers/subscribe_test.go` is ~1,860 lines with ~71
references to the recording mailer. Every assertion of the form "the mailer
recorded a confirmation" becomes "an `outbound_queue` row exists with
`kind='confirmation'` for this subscriber". This is the single largest chunk of
mechanical work in the issue; budget for it, and do not weaken an assertion to
make it easier. The byte-equality tests on the `202` must not be touched at all.

#### Decision — `#0081`'s shutdown property, stated precisely

The criterion says "preserved or superseded". Concretely, after this change:

- `SubscribeHandler.Close` still drains `mutateQueue` so every accepted mutation
  reaches Postgres (or is dropped with a log line, as today).
- `OutboxWorker.Stop` stops claiming, lets an in-flight send finish on its
  detached context, and **releases any claimed-but-unsent row back to
  `queued`** so restart picks it up immediately instead of waiting out
  `outboxOrphanStaleAfter`.
- The goroutine-leak regression guard `#0081` added must keep passing; if it
  asserts on the send pool specifically, it needs re-pointing at the mutate pool
  rather than deleting.

**Non-goal, stated so it is not mistaken for an oversight.** `mutateQueue` is
still in-memory, and `#0088` made it so deliberately. A signup that got its
`202` can still be lost before it ever reaches Postgres (queue full, or shutdown
in flight). `#0126` makes *committed signup ⇒ queued confirmation* durable; it
does **not** make *accepted 202 ⇒ committed signup* durable. That residual is
worth its own issue — see the report; subagents do not file (CLAUDE.md §9).

### 5. `internal/auth` mail onto the queue

`auth.SESMailer` wraps `mailing.Build{Registration,Recovery,SessionsRevoked}Email`
and calls `sender.Send` inline. Replace the implementation of
`auth.Mailer`'s three methods with an enqueue (`internal/auth` may import
`internal/outbox`; it is a leaf). The registration and recovery ceremonies
already own a transaction and already write their audit rows inside it via
`audit.WriteTx` — enqueue there too, for the same reason and with the same
argument.

Criterion 10 names registration and recovery only. **Move `sessions_revoked`
too** and add `KindSessionsRevoked`: leaving one of three auth mails on the
synchronous path preserves the failure mode for no reason, and `login.go:379`
already treats its failure as non-fatal. PRD §6.2's `kind` list is a SQL comment
with no CHECK constraint, so adding kinds touches neither PRD guard.

### 6. `subscriber_events`

```go
// internal/subscribers/events.go
type Action string   // the closed set, one constant per PRD §6.11 row

type Event struct {
    SubscriberID *int64
    Email        string        // snapshot, always
    Action       Action
    CampaignID   *int64
    ActorUserID  *int64
    Detail       any           // JSONB
}

func RecordEventTx(ctx context.Context, q Querier, e Event) error
func (s *Store) RecordEvent(ctx context.Context, e Event) error
```

Validation is in Go, against a `map[Action]bool` of the closed set; an unrecognised
action returns an error rather than inserting (criterion). `Email` empty is also
an error — the snapshot is what makes the row survive erasure.

#### Decision — a new table, not an extension of `audit_log`. Argued.

The cost of a second log is real: two schemas, two writers, and a standing
question of "which one?" every time someone adds an event. It is still the right
call, on four grounds — and the last two are dispositive:

1. **Different subject.** An `audit_log` row is keyed to an *actor* and a
   target; a `subscriber_events` row is keyed to an *address* that must outlive
   the `subscribers` row entirely. `audit_log` has no email column, so the
   snapshot would have to go in `metadata`.
2. **That directly attacks `#0237`/`#0252`.** `audit_email_metadata_guard_test.go`
   walks every `audit.Entry{}` literal and pins the set of sites whose metadata
   carries an email against a fixture, because the privacy policy enumerates
   exactly that set. Routing ~20 machine-generated per-address actions through
   `audit_log` with the email in `metadata` would add up to twenty rows to that
   fixture and make the privacy page's promise materially harder to keep
   honest. The guard would not be *defeated* — it would be *swamped*, which is
   worse.
3. **`audit_log` has no update path, by design.** Its package doc: rows "are
   only ever inserted; they are never updated or deleted." The erasure criterion
   here *requires* redacting the email column in place. Adding an UPDATE path to
   `audit_log` to serve this would break that invariant for every row in the
   table, including the auth ceremonies'.
4. **Volume and audience.** `#0114` filters the audit screen by
   `target_type`/`target_id` for staff review. A `delivered` event per address
   per campaign would bury it.

**The guard must not be silently defeated in the other direction either.** Its
fixture fails when a *known site disappears*. So: do **not** delete
`auditSignup`, the confirm/unsubscribe/preferences audit writes, or any other
`audit.Entry{}` site on the theory that `subscriber_events` now covers it. The
two logs coexist; PRD §6.11 and this issue's Notes both say so. If a new
`audit.Entry{}` literal is added anywhere in this issue, its `Metadata` must be
an inline map literal or a local map built from string-literal keys — the guard
treats a `Metadata` expression it cannot resolve as a **failure**, not a pass.

#### Decision — erasure redaction

Inside `Erase`'s existing transaction, **before** the `DELETE`:

```sql
UPDATE subscriber_events
   SET email = 'erased-' || $1 || '@erased.invalid'
 WHERE subscriber_id = $1;
```

`subscriber_id` is nulled for free by PRD §6.2's `ON DELETE SET NULL`.

Note the deliberate difference from the `email_sends` redaction three lines
above it, which derives the placeholder **per row** (`'erased-' || id || …`) so
two erased subscribers' rows cannot be correlated. Here the placeholder is
derived from the **subscriber id**, so the address's history stays grouped. That
is the point: once `subscriber_id` is NULL the placeholder is the only key left,
and an unlinked pile of rows is not evidence that an erasure was performed —
which is the stated reason the criterion preserves them at all. A subscriber id
is not personal data, and the row it pointed at no longer exists.

Then write the `erased` event **after** the redaction, with the same placeholder
address, so the erasure's own evidence does not reintroduce the address.

**Also extend `Erase`'s in-flight-send refusal.** It currently returns
`ErrHasPendingSends` when `email_sends` has a `queued`/`sending` row for the
subscriber. `outbound_queue.subscriber_id` is `ON DELETE CASCADE`, so without the
same check the `DELETE` would silently remove a row a worker has claimed and is
mid-send on. Add `outbound_queue` to that `EXISTS` check.

#### Decision — which actions get written *now*

The criterion "Every action in that table is written at its point of
occurrence" **cannot be satisfied by this issue**, and pretending otherwise is
how an implementer ends up inventing half a feature. Roughly nine of the
twenty-two actions have no point of occurrence in the tree yet.

Resolution: **define the whole closed set in Go now** — that is the contract
`#0124`/`#0125`/`#0127`/`#0128`/`#0129` code against, and it is the real value
`#0126` delivers to them — and **write only the actions whose call site exists**,
with a guard test mapping every constant to either a live call site or an
explicit owner issue, so the set cannot rot silently.

| Action | This issue writes it | Where / owner |
|---|---|---|
| `signup_requested` | yes | `Create` / `RestartSignup` tx |

### Defect 1 — BLOCKER: GDPR erasure leaves the real address in `subscriber_events`

`Erase`'s redaction is `UPDATE subscriber_events SET email = $2 WHERE
subscriber_id = $1`. But two of the new event write sites set **no**
`SubscriberID`:

- `internal/subscribers/suppressions.go:174` — `ActionSuppressed`
- `internal/subscribers/suppressions.go:330` — `ActionUnsuppressed`

Both write `Email: sup.Email` — the real, normalized address — with
`subscriber_id = NULL`, deliberately (suppressions are keyed by email, and the
code comment says so). The redaction's `WHERE subscriber_id = $1` therefore
never matches them.

**`Erase` creates one of these itself.** It calls `addSuppression` (the
permanent `manual` suppression) *before* the redaction, so every erasure writes
a `suppressed` row carrying the address in plaintext and then fails to redact
it. Any *pre-existing* `suppressed`/`unsuppressed` row for that address — from a
hard bounce, a complaint, or an admin action — survives the same way.

Proved by execution, not by reading. A throwaway test in the review worktree
did `Create` → `Erase` and then counted rows by email:

```
subscriber_events: redacted rows=2, rows still holding the real address=1
LEAK: 1 subscriber_events row(s) still hold the real address
```

This breaks the ticked criterion *"`#0060`'s GDPR erasure redacts the `email`
column and nulls `subscriber_id` on that address's event rows"*, and it makes
`PrivacyPolicy.svelte`'s new fifth item **false**:

> "…kept after erasure **with your email address replaced by a placeholder** …
> but the placeholder no longer identifies you"

That is the same defect `#0237` was filed for, on the same page, reproduced by
the commit that was supposed to prevent it. The guard did not catch it because
`PrivacyPolicy.guard.test.ts` pins the page's *wording* against the code's
*intent*, not against executed erasure behaviour.

**Fix direction:** widen the redaction to cover the address as well as the id —
it already runs after `addSuppression`, so one predicate change is enough:

```sql
UPDATE subscriber_events SET email = $2
 WHERE subscriber_id = $1 OR email = lower(trim($3))
```

and add a regression test that erases a subscriber who already carries a
suppression and asserts **zero** `subscriber_events` rows match the original
address.

```
after Stop: sending=1 queued=0
DEFECT CONFIRMED: 1 row(s) left in 'sending' after Stop
```

**Impact is bounded, not catastrophic**: the orphan sweep does reclaim the row,
but only after `outboxOrphanStaleAfter` = `2 × (30s + 5s)` = **70 seconds**, so
a restart delays that message by ≥70s instead of retrying immediately. Nothing
is lost. But the code, three comments, and a test name all say something the
program does not do, which is worse than the delay.

**Fix direction:** either implement the release (track claimed ids on the
worker; drain them through `store.Release` in `Stop` before returning) and
point the existing test at `Stop`, or drop the claim honestly — delete
`Store.Release`, delete the four comments, rename the test to
`TestOutbox_Release_RequeuesClaimedRow`, and say in the issue that the orphan
sweep alone covers shutdown. The first is what the criterion asks for.

### Defect 3 — the issue's load-bearing property has no regression guard

*"A crash between insert and enqueue is impossible (they share a transaction)"*
is the property `#0126` exists to establish. It is **true in the code** — I read
`Create`, `ClaimAndEnqueueConfirmation`, and `ClaimAndEnqueueAlreadySubscribed`
and all three pass `tx` to `EnqueueTx`. Nothing tests it.

Mutation-proved: I rewrote `Create` to capture the enqueue in a closure and run
it **after `tx.Commit`** — the exact regression the issue forbids — and

```
ok  internal/subscribers   ok  internal/outbox   ok  internal/handlers   ok  cmd/opencircuit
```

The whole suite stayed green. `TestCreate_ClaimsAndEnqueuesConfirmationAtomically`
only asserts the end state, which a post-commit enqueue also produces.
`TestOutbox_EnqueueTx_RollbackLeavesNoRow` proves only that `EnqueueTx` honours
a transaction it is handed, not that `Create` hands it one.

The plan §10 named `TestSubscribe_NewSignup_CommitsSubscriberAndQueueRowTogether`
**"and its negative: a failure injected between them commits neither"**. The
negative half was never written, and `## Verification`'s claim that "a `Create`
that fails after `EnqueueTx` leaves no queue row" is not backed by any test.

**Fix direction:** inject a failure after the enqueue inside `Create`'s
transaction (a test-only hook, or a `Create` variant fed a poisoned
`SetInterests`-style step) and assert that **neither** the `subscribers` row nor
the `outbound_queue` row exists. Same for `ClaimAndEnqueueConfirmation`.

### Judgement on the two disclosed departures

**Departure 1 — `Erase`'s `outbound_queue` refusal scoped to `'sending'` only:
CORRECT. Keep it.**

The implementer's claim was verified by trying it. Restoring the plan's literal
`IN ('queued','sending')` fails **8 tests** with `ErrHasPendingSends`
(`TestErase_HardDeletesAndCascadesInterests`,
`TestErase_AnonymizesEmailSendsPreservingCountAndStatus`, `TestErase_NotFound`,
`TestErase_PreservesAndAddsToExistingSuppressions`,
`TestErase_RepeatManualSuppressionIsIdempotent`, plus three
`TestAdminSubscribers_Erase_*` returning 409 instead of 200). That is not a test
artefact: since `bace190`, **every** non-synthetic `Create` leaves a `queued`
confirmation row, so the plan's literal text would make ordinary GDPR erasure
return 409 for as long as the queue is behind — up to the 24h backoff clamp
during an SES outage. Refusing a legal-compliance path on a routine queue row is
worse than the risk it guards.

**And the narrower scope leaves no hole.** I traced the payload rather than
assuming: `outbound_queue.subscriber_id` is `ON DELETE CASCADE`, and all three
subscriber-mail enqueue sites (`Create`, `ClaimAndEnqueueConfirmation`,
`ClaimAndEnqueueAlreadySubscribed`) set `SubscriberID`. Executed proof —
`Create` then `Erase`:

```
outbound_queue rows BEFORE erase: 1
outbound_queue rows AFTER  erase: 0   statuses=[] payloads=[]
```

The queued row is destroyed by the cascade, so it can never deliver to an erased
address. A `sent` row is likewise cascade-deleted, and its payload was already
scrubbed by `MarkSent`. The only reachable state left is `'sending'`, which the
narrow check refuses. The departure is safe and should be recorded as the
correct reading of the plan, not carried forward as debt.

**Departure 2 — auth-mail enqueue not atomic with its token commit: the residual
is REAL, correctly characterised, and acceptable.**

Confirmed the plan's premise was simply wrong: `Store.CreatePendingRegistration`
(`internal/auth/store.go:188`) and `Store.CreateRecoveryToken` (`:350`) are both
`s.pool.Exec` — no transaction. The transaction the plan meant belongs to
`FinishRegistration`/`FinishRecovery`, which never call the mailer.

Characterised precisely:

- **What is lost:** the email, not the token. A crash between the token's commit
  and `outbox.Enqueue`'s commit leaves a valid `pending_registrations` /
  recovery-token row with no queued mail, and nothing retries it.
- **What the user sees:** *not* a silent success. An enqueue **error** returns
  500 from both `RegisterStart` (`internal/handlers/auth.go:106`) and
  `RecoverStart` (`:307`), so the person is told to retry. A **crash** in that
  window also kills the HTTP connection, so again no false "check your email".
  This is materially unlike the subscriber case `#0126` was filed about, where
  the unconditional `202` tells the visitor the mail is coming.
- **Narrower than before:** the pre-`#0126` window was a full SES round trip
  with three retries (~1s); it is now one `INSERT`.

Worth its own follow-up issue (transaction-scoped variants of those two store
methods), not a blocker here.

## Notes

PRD §6.11 is the specification. §6.2 carries the schema.

**Where the current gap is.** `internal/handlers/subscribe.go:742` runs the send on a goroutine off an in-memory channel; `internal/mailing/ses_mailer.go` retries three times over roughly a second (200/400/800 ms). Past that the message is gone. `#0081` fixed the goroutine leak and added shutdown, but a clean shutdown that drains an in-memory queue still loses everything if the process is killed or SES is down for a minute. Campaign mail already has the durable shape — `email_sends` with a `UNIQUE (campaign_id, subscriber_id)` idempotency key, claims, and an orphan sweep. This is that pattern applied to the other half of the outbound mail.

Mitigating factor worth knowing before sizing this: re-submitting the signup form re-sends the confirmation, so today's failure mode is recoverable *by the subscriber*, who has no idea anything went wrong. It is silent, not permanent.

**Three logs, three jobs.** `audit_log` records what staff did to the console. `email_events` stores what SES said, verbatim, for forensics. `subscriber_events` records what happened to an address in our own vocabulary, and is the one an operator reads. Do not merge them and do not write the same fact to two of them.

**Enqueue-in-transaction is the load-bearing property.** Enqueueing after the commit reintroduces the exact gap this issue closes, just with a smaller window. A test must prove that a transaction rolled back after enqueue leaves no queue row.

**Read `#0122` first.** It reports `drainCampaign`'s unconditional `OrphanSweep` un-claiming a row another worker is mid-send on, duplicating a delivery. Copying that sweep into the new worker would copy the defect.
