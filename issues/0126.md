# 0126 — Make transactional email durable and log every subscriber action

| | |
|---|---|
| **Status** | open |
| **Module** | mailing / subscribers / db |
| **Platform** | All |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-08-21 |

## Description

Confirmation email is dispatched from an in-process goroutine with about a second of SES retry, so an SES outage or a process restart loses a signup silently — the subscriber sits `pending` and never hears anything. Move transactional mail onto a database-backed queue with real backoff, and add an append-only activity log recording every meaningful thing that happens to an address.

## Acceptance criteria

**Outbound queue**

- [ ] Migration creates `outbound_queue` per PRD §6.2
- [ ] `Enqueue` happens inside the same transaction as the state change that caused it — a committed signup can never have an unsent confirmation
- [ ] A worker claims due rows (`status = 'queued' AND next_attempt_at <= now()`), stamps `claimed_at`, and releases on completion
- [ ] Backoff schedule 1m, 5m, 15m, 1h, 6h, 24h; `queue.max_retries` default 8, then terminal `abandoned` with the last error retained
- [ ] An orphan sweep reclaims rows whose worker died, using the same approach as `email_sends` — and **not** the unconditional sweep `#0122` reports as a defect
- [ ] `payload` stores template inputs, not rendered MIME, so a template fix applies to queued mail
- [ ] `POST /api/subscribe` enqueues instead of calling the mailer through `subscribe.go`'s goroutine; the in-memory `sendQueue` and its `Close` path are removed
- [ ] `#0081`'s graceful-shutdown property is preserved or superseded — shutdown drains claims rather than losing them
- [ ] The uniform `202` and byte-identical response bodies of `POST /api/subscribe` are unchanged (CLAUDE.md §9), and the timing-oracle hardening from `#0088` still holds
- [ ] Registration and recovery mail (`internal/auth`) move onto the same queue
- [ ] Admin alerts from `#0124`'s circuit breaker use `kind = 'admin_alert'`
- [ ] Queue depth and abandoned count appear on the admin overview (`#0061`)

**Activity log**

- [ ] Migration creates `subscriber_events` per PRD §6.2 with its three indexes
- [ ] `action` is a closed set validated in Go, matching PRD §6.11's table exactly. An unknown action is a programming error, not a stored row
- [ ] Every action in that table is written at its point of occurrence
- [ ] `email` is snapshotted on every row so history survives erasure of the subscriber row
- [ ] `#0060`'s GDPR erasure redacts the `email` column and nulls `subscriber_id` on that address's event rows rather than deleting them — the erasure's own evidence must survive it
- [ ] The subscriber detail drawer (`#0032`) renders the address's event history
- [ ] `subscriber_events` is append-only; no update or delete path outside erasure redaction

## Notes

PRD §6.11 is the specification. §6.2 carries the schema.

**Where the current gap is.** `internal/handlers/subscribe.go:742` runs the send on a goroutine off an in-memory channel; `internal/mailing/ses_mailer.go` retries three times over roughly a second (200/400/800 ms). Past that the message is gone. `#0081` fixed the goroutine leak and added shutdown, but a clean shutdown that drains an in-memory queue still loses everything if the process is killed or SES is down for a minute. Campaign mail already has the durable shape — `email_sends` with a `UNIQUE (campaign_id, subscriber_id)` idempotency key, claims, and an orphan sweep. This is that pattern applied to the other half of the outbound mail.

Mitigating factor worth knowing before sizing this: re-submitting the signup form re-sends the confirmation, so today's failure mode is recoverable *by the subscriber*, who has no idea anything went wrong. It is silent, not permanent.

**Three logs, three jobs.** `audit_log` records what staff did to the console. `email_events` stores what SES said, verbatim, for forensics. `subscriber_events` records what happened to an address in our own vocabulary, and is the one an operator reads. Do not merge them and do not write the same fact to two of them.

**Enqueue-in-transaction is the load-bearing property.** Enqueueing after the commit reintroduces the exact gap this issue closes, just with a smaller window. A test must prove that a transaction rolled back after enqueue leaves no queue row.

**Read `#0122` first.** It reports `drainCampaign`'s unconditional `OrphanSweep` un-claiming a row another worker is mid-send on, duplicating a delivery. Copying that sweep into the new worker would copy the defect.
