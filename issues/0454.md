## Description

`issues/Issues.md` carries a literal status row inside the **issue-file-format
template** it documents. `issueStatus` reads that row, concludes the document is
an open issue, and both citation-guard families then scan the template's own
example sections as though they were a real issue's evidence.

Found by `#0446`'s reviewer while re-deriving that issue's corpus sweep: the
in-scope file count includes a document that is not an issue.

## Why it is worth closing, and why it is not urgent

**It is clean today**, and pre-existing — `#0446` did not introduce it. So this
is not a live failure.

It matters for two reasons:

1. **The guards' scope should be describable.** `#0446` settled that the
   allowlist of scanned sections stays, on the grounds that the admitted set is
   small and template-backed while the unadmitted set is 47 one-off heading
   spellings. That argument rests on knowing exactly which files are in scope,
   and a file that is in scope only by accident undermines it.
2. **The template will eventually demonstrate something the guards forbid.**
   `Issues.md` documents conventions, and documenting a convention naturally
   involves showing its shape. `CLAUDE.md` §8 records that writing about a
   citation guard tends to write the exact pattern it forbids — measured at nine
   trips across six issues in one phase. The one document whose job is to *show*
   the format is the likeliest place for that to happen next, and it would fail
   with a confusing message about a file nobody thinks of as an issue.

## Acceptance criteria

1. Decide whether the scan should skip `Issues.md` by name, or whether
   `issueStatus` should require something an actual issue file has and the
   template does not. **Record the reasoning**, not just the choice — a name
   skip is simple but goes stale if the file is ever renamed, while a structural
   test is more robust and easier to get subtly wrong.
2. Whichever you choose, prove it by measurement: the in-scope file count must
   drop by exactly one, and every genuine issue file must remain in scope. State
   the before and after counts. `#0446`'s review established the current figures
   — 454 issue files read, 33 `open`/`in-progress` — so re-derive rather than
   copy them.
3. **No new mechanism** (§8, `#0258`, and `#0446`'s own criterion 5). This is a
   predicate change, not a new guard.
4. Confirm the change does not alter which *sections* are scanned in real issue
   files. `#0446` widened that set to include the work-log section, and that
   widening was proved to bite; this must not narrow it.
5. Add nothing to `Issues.md` itself unless the chosen fix requires it — and if
   it does, say why a change to the document was preferable to a change in the
   guard.

- 2026-09-05 — **Implemented (phase 2, Sonnet).**

  **Criterion 1 — decision and reasoning.** Chose the structural option, not a
  name skip of `Issues.md`. The distinguishing fact is not the filename but
  where a Status row physically sits: `issueStatus`'s regex already matches
  the template's worked example because that example is written to look
  exactly like a real metadata row — that is the document's whole point. What
  a genuine issue file has, and the template's demonstration does not, is that
  the row is never inside a fenced (```` ``` ````-delimited) code block. Made
  `issueStatus` fence-aware: it now walks lines, toggles fence state on a line
  whose trimmed form starts with a triple-backtick, and only returns a match
  found outside any fence. A name skip would have been one line, but goes
  stale the moment the template is renamed (the issue's own stated risk); the
  fence check instead asks the question that actually separates "a real
  issue" from "prose demonstrating what one looks like," so it keeps working
  under a rename with no further edit, and it fixes all three call sites of
  the shared `issueStatus` function (the two citation-guard families plus the
  closed-row guard) in one place rather than needing a per-loop filename
  filter added to each.

  **Fence-edge probes — what the walk actually does.** Ran the *real*
  `issueStatus` (not a re-implementation) against 18 hand-built documents in
  the worktree. Grouped by direction:

  | Shape | Result | Verdict |
  |---|---|---|
  | Row inside a backtick fence with an info string | not a status | correct — the target case |
  | Row inside a fence indented 1–3 columns | not a status | correct |
  | Row inside a tilde fence | **status** | diverges; safe direction |
  | Row inside a 3-backtick fence nested in a 4-backtick fence | **status** | diverges; safe direction |
  | Row after a closer carrying trailing text | **status** | diverges; safe direction |
  | Plain unfenced row | status | correct |
  | Unfenced row followed later by an unclosed fence | status | correct |
  | Row preceded by an unclosed fence, or by an odd number of fences | not a status | matches CommonMark, which runs an unclosed fence to end of document |
  | Inline triple backtick mid-prose above the row | status | correct |
  | Row preceded by a fence line indented 4+ columns, or by a tab-indented one | not a status | **diverges; dangerous direction** |
  | Row preceded by a fence opener with a backtick in its info string | not a status | **diverges; dangerous direction** |

  The three safe-direction divergences reproduce the pre-existing behaviour
  (a demonstration row still counted), never a new failure. The two
  dangerous-direction ones are real: CommonMark does not open a fence there,
  so the walk's spurious open masks a live row and would drop a genuine issue
  out of every guard's scope silently — including the closed-row guard, which
  would then stop checking that file with no message.

  **Why that residual is accepted rather than bounced.** Its exposure is
  measured at zero and is structural, not lucky: every one of the 454 genuine
  issue files carries its status row at line 5 (one at line 7), with **zero**
  fence-shaped lines anywhere above it, because the metadata table is the
  second block of the file by the template's own definition. `issueStatus`
  returns at the first unfenced match, so fence-state errors below line 7 —
  and the corpus does contain 19 indented and 4 four-backtick fence lines,
  all of them lower in their files — cannot reach the result. Triggering the
  masking would require putting a fenced or indented code block between an
  issue's title and its metadata table, which breaks the format far more
  visibly than it breaks this guard. `#0176` is the standing precedent for
  exactly this trade and was declined on the same reasoning, with the note
  that a robustness pass over markdown this repo does not write is a
  different proposition from fixing a silent failure. The distinguishing
  factor there was loud-versus-silent, and this one is silent, which is why
  it is recorded here in full rather than waved off.
