## Description

`internal/handlers/admin_subscribers.go`'s doc comment on `subscriberView`
(lines 190–197) describes `SoftBounceCount`/`SoftBounceThreshold`/
`SoftBounceWindowDays` as "the count of **Transient-bounce** `email_events`
rows for this address within the currently configured window". After `#0109`
(`8f900fe`) that is wrong in both directions, exactly as `#0110`'s text was:
the count also includes `Undetermined` bounces, and it excludes the
sender-fault `Transient` subtypes (`MessageTooLarge`, `ContentRejected`,
`AttachmentRejected`).

`internal/handlers/soft_bounce.go`'s package-level file comment (line 3) has
the same narrower wording — it says `ses_notifications.go` uses the threshold
"to decide whether a **Transient** bounce crosses the threshold", but that
arm is now `case sesnotify.BounceTypeTransient, sesnotify.BounceTypeUndetermined`
(`ses_notifications.go:456`).

Documentation only — no behaviour is affected, and **this does not block Phase
4's deployable gate.** Same severity and same class as `#0110`.

## Root cause

`#0110` corrected the SPA-side mirror of this comment
(`web/src/lib/types.ts`) and its Notes recorded, on the strength of `#0109`'s
review, that types.ts was "the *only* remaining stale description of the
widened count". That sweep covered `web/` and `docs/` but not
`internal/handlers/`. `admin_subscribers.go` is the *authoritative* one of the
pair — `types.ts` mirrors the Go struct, not the other way round — so the two
are now corrected in the wrong order, with the source-of-truth still stale.

Current text, `internal/handlers/admin_subscribers.go` lines 190–197:

```
// SoftBounceCount/SoftBounceThreshold/SoftBounceWindowDays are #0039's
// "admin can see the current soft-bounce count" criterion: the count of
// Transient-bounce email_events rows for this address within the currently
// configured window, plus the threshold/window themselves so the admin
// screen can show "N of THRESHOLD in the last WINDOW days" rather than a
// bare number. Like Interests, populated by Get only (List omits them to
// avoid a query per row); all three are nil together when the handler was
// constructed with a nil bounces/settings dependency (STORAGE=json dev mode).
```

The rest of that sentence is accurate and was re-verified during `#0110`'s
review: the three fields really are set together in one
`if h.bounces != nil && h.settings != nil` block whose only other exit is an
error return, so "all three are nil together" holds. Only the
"Transient-bounce" clause is wrong.
