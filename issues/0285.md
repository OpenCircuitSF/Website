## Description

`TestOutbox_OrphanSweep_DoesNotUnclaimLiveRow` asserts `swept == 1` from an
**unscoped** `OrphanSweep` — one that sweeps every kind. The test databases are
per-agent but shared across packages within a run, and `scripts/check.sh` forces
`-p 2`, so a stale row another package left behind is counted and the assertion
fails.

`#0254` made `outbound_queue` busier: every signup now writes a
`subscribe_intake` row alongside the mail row. So the population this unscoped
assertion sweeps has grown, and with it the chance of a cross-package count.

**This is not the load problem.** CLAUDE.md §5 is emphatic that a test failing
under concurrent agent load is the machine being busy, and that widening a
deadline to accommodate it is the wrong move. That is not this. This is a test
asserting an exact count over state it does not own, which will fail on an idle
machine just as readily given the wrong interleaving. The fix is to scope the
assertion, not to relax it.

## Acceptance criteria

1. The test asserts only about rows it created. Seed a distinctive kind or a
   throwaway set of ids and scope both the sweep and the count to them.
2. Never target a literal or seeded id (CLAUDE.md §8b) — create the rows the
   test needs and target those.
3. The unscoped default is still exercised somewhere, since it is documented
   behaviour and `#0281` may formalise it. Do not delete the coverage; isolate it.
4. Audit the sibling tests in `internal/outbox` for the same shape — an exact
   count over the whole table — and fix any found. Report the list.
5. The change must not consist of widening a timeout, adding a retry, or
   `-count=N` flake-hunting, all of which CLAUDE.md §5a bans for this class.
6. `ISSUE=NNNN scripts/check.sh go ./internal/...` passes with no skips, run
   while nothing else is running (check `uptime` first — an idle load average
   here is under ~4).

## Sibling audit (criterion 4)

Added a `distinctKind(t)` helper (`internal/outbox/store_test.go`) — a
`Kind` fabricated per test call from `testdb.Unique()`, valid because
`outbound_queue.kind` carries no CHECK constraint (package doc comment).
Confirmed with `grep` that `internal/mailing` and `internal/handlers` both
enqueue real rows into this same shared `outbound_queue` table from their
own DB-backed tests, including `outbox.KindConfirmation` (in
`internal/mailing/outbox_worker_test.go`) and `outbox.KindSubscribeIntake`
(in three `internal/handlers` test files), so scoping by a real `Kind`
constant is not sufficient isolation — only a kind unique to the individual
test call is.

**Correction (post-review):** an earlier version of this paragraph, and
`distinctKind`'s doc comment, said these other packages' tests run
**concurrently** with `internal/outbox`'s. That is false. Every DB-backed
package's `TestMain` takes `internal/testdb`'s single, fixed-key advisory
lock, and that package's own doc comment says plainly that packages "run
one-at-a-time even under `go test ./...`" — confirmed by measurement
(two `go test` binaries launched at once against one database, polling
`pg_locks`, showed exactly one holder and one blocked waiter, never
overlapping) and independently reinforced by `internal/outbox/main_test.go`
`TRUNCATE`-ing `outbound_queue` on entry while holding that lock, which
clears any other package's residue before this package's own tests run. The
`grep` above confirmed those other packages' enqueues **exist**, not that
they ever execute at the same moment as this package's tests — they cannot.
The real reason to scope by a distinct kind, restated accurately: it makes
each assertion depend only on rows the test itself created, independent of
anything else that might land in the table — defence against a real Kind
being shared surface this package does not own, not against a concurrency
that the locking model already rules out.

Audited every assertion in `internal/outbox/store_test.go` that depends on
an operation's affected/returned row **count** rather than checking its own

   `swept == 1` from an unscoped `OrphanSweep`. Fixed: scoped to a

   unscoped code path is kept covered by a new sibling test,
   `TestOutbox_OrphanSweep_Unscoped_SweepsAcrossKinds` (criterion 3) — it

2. **`TestOutbox_AbandonsAtMaxRetries_RetainsLastError`** — a loop of
   unscoped `store.ClaimDue(ctx, 10)` calls each asserting
   `len(rows) != 1 || rows[0].ID != id`. Fixed: scoped to a `distinctKind`.
3. **`TestOutbox_MarkRetryOrAbandon_RetriesBeforeMax`** — same shape, one
   unscoped `ClaimDue` with `len(rows) != 1`; worse, `rows[0].Attempts` was
   passed to `MarkRetryOrAbandon` without confirming `rows[0]` was even this
   test's own row, so an unscoped collision could have fed the wrong
   attempt count into a real assertion, not just failed the length check.
   Fixed: scoped to a `distinctKind`.
4. **`TestOutbox_MarkSent_ClearsErrorFromFailedAttempt`** — two unscoped

5. **`TestOutbox_AbandonedCountByKind_ScopedToKind`** — not the `swept`-style

   `KindConfirmation` rows in its own tests, so a concurrent abandon landing

### Finding 1 — the stated mechanism is not what happens

`distinctKind`'s doc comment — now the canonical in-repo explanation of why
six tests are scoped — says:

> Test databases are per-agent but shared ACROSS PACKAGES within a run
> (scripts/check.sh forces -p 2), and internal/mailing and internal/handlers
> both enqueue real rows … into this same outbound_queue table from their own
> **concurrently-running** tests.

They do not run concurrently, and cannot. `internal/testdb`'s own package doc
states the opposite in as many words:

> Each such package calls Lock from its TestMain to hold a PostgreSQL
> session-level advisory lock for the duration of its test run; **only one
> package can hold the lock at a time, so they run one-at-a-time** even under
> `go test ./...`.

Every DB-backed package's `TestMain` calls `testdb.Lock()` on the same fixed
key (`advisoryLockKey`, `internal/testdb/testdb.go`) — `internal/outbox`,
`internal/handlers`, `internal/mailing`, and the rest. `-p 2` lets two package
binaries *start*; the second then blocks in `TestMain` until the first
releases.

I measured it rather than reading it. Two `go test` binaries
(`./internal/handlers/...` and `./internal/mailing/...`) launched
simultaneously against one test database, polling `pg_locks` once a second:

```
probe2: granted=false n=1    probe2: granted=true n=1
probe3: granted=false n=1    probe3: granted=true n=1
probe4: granted=false n=1    probe4: granted=true n=1
probe5: granted=true n=1
```

One holder, one blocked waiter, until the first finished. They never overlap.

There is a second, independent reason the stated mechanism cannot bite:
`internal/outbox/main_test.go` runs `TRUNCATE outbound_queue RESTART IDENTITY
CASCADE` **on entry**, while holding that lock. So rows another package left
behind on an earlier turn are gone before this package's first test runs.

The consequence is not that the change is wrong — scoping by a distinct kind
is correct and robust under any mechanism, and I am not asking for it to be
reverted. The consequence is that the file now carries an authoritative-sounding
explanation that contradicts `internal/testdb`'s package doc, and the next
person who reasons from it about this test suite will reason from a false
model. That is the class `CLAUDE.md` names for `#0263` and `#0095`. The issue
text was already imprecise on this ("a stale row another package left behind"),
and the audit's "Confirmed with `grep`" confirmed that those enqueues *exist* —
not that they ever run at the same time as this package's tests.

**Required:** rewrite `distinctKind`'s doc comment (and the corresponding
sentence in this issue's `## Sibling audit`) to state the real justification.
An accurate one is available and is a better argument than the false one: the
tests are scoped to a kind unique to the call so that each assertion is about
rows the test itself created, independent of anything else in the table —
whether that is another package's residue, a future test in this package, or a
future run that stops truncating on entry. Do not assert cross-package
concurrency; `internal/testdb` prevents it. If a concrete reachable failure
interleaving is claimed, name it and show it.
