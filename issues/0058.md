## Description

Fetch the message from S3, extract the subscriber, and unsubscribe them.

## Root cause

Not a bug fix — `POST /api/ses/inbound` and everything behind it did not
exist yet. `#0057` (still open, gated on the user for the AWS/DNS side) and
`#0037`/`#0034` (both resolved) supplied the pieces this issue wires
together: the receipt rule's shape (a single `S3Action` with `TopicArn` set,
per `#0057`'s plan), the SNS trust boundary (`internal/sesnotify.Verifier`),
and the subscribers-table mutators (`Unsubscribe`/`RotateManageToken`,
already built for `#0034`'s one-click path).

## Fix

Built entirely against mocks/fakes, per `CLAUDE.md` §10 — the S3 bucket and
the `opencircuit-inbound-mail` SNS topic are `#0057`'s to create and do not
exist yet.

**`internal/inbound` (new package)** — owns S3 access and message parsing,
independent of any HTTP or database dependency:

- `S3Store` (`s3.go`): fetches and deletes one object by key, behind a
  locally-defined `s3API` interface (mirrors `internal/mailing`'s `sesAPI`
  seam) so no concrete `*s3.Client` reaches a handler signature. Bounded to
  5 MiB (`ErrObjectTooLarge`) since this is a webhook-adjacent read path
  with no authentication of its own beyond the SNS signature check.
- `Parse` (`parse.go`): parses the fetched bytes with `net/mail` and
  extracts three independent fields — `Token` (from a `unsubscribe:<token>`
  Subject, matched case-insensitively and RFC 2047-decoded first, so a
  `Re: ` reply or an encoded subject still resolves), `From` (lowercased,
  trimmed address), and `AutoReply` (see design decision 2 below). An
  unparseable message returns `net/mail`'s own error, which the handler
  treats the same as "no match" — logged, left in S3.

**`internal/sesnotify/event.go`** — added `SESReceiptAction`/`SESReceipt`
and `SESEvent.ObjectKey()`. `#0057`'s plan corrects its own criteria: the
S3 action's own `TopicArn` publishes SES's "Received" notification (the
same `mail`/`receipt` envelope shape as every other SES event this package
already parses), not a standalone SNS action's raw mail content — so the
object key comes from `receipt.action.objectKey`, falling back to
`objectKeyPrefix + mail.messageId` if the explicit field is ever absent.

**`internal/handlers/ses_inbound.go`** — `SESInboundHandler`, wired the same
way `#0038`'s `SESNotificationsHandler` is, deliberately reusing rather than
reimplementing:

- `sesVerifier` — the exact interface `ses_notifications.go` already
  defines, satisfied by a **second** `*sesnotify.Verifier` instance pinned
  to `SESInboundTopicARN` (new config, `SES_INBOUND_TOPIC_ARN`) instead of
  `SESEventsTopicARN`. Reusing the same topic would let either endpoint's
  messages satisfy the other's `TopicArn` check.
- `inboundObjectStore` — a narrow interface (`Fetch`/`Delete`) satisfied by
  `*inbound.S3Store`, matching `CLAUDE.md` §1.
- `inboundSubscriberStore` — the same four methods `#0034`'s
  `unsubscribeSubscriberStore` already declares, satisfied directly by the
  already-constructed `*subscribers.Store` — no new store needed.

Status-code contract mirrors `ses_notifications.go`'s exactly (200 for
anything a retry can't fix, `403` for a failed signature, `500` only when
the certificate can't be fetched or an operation on an already-verified
message fails and a retry is genuinely safe — the object is never deleted
before that point).

### Design decision 1 — the S3 fetch seam

Per the brief: `internal/inbound` owns the concrete `*s3.Client` (via its
own unexported `s3API` interface, constructed with the AWS SDK's default
credential chain — the EC2 instance role in production, identical to
`internal/mailing.SESMailer`'s pattern); `internal/handlers` defines its
own `inboundObjectStore` interface and depends on that, never on
`internal/inbound.S3Store` directly. This is the same shape `sesVerifier`/
`sesTxBeginner` already use in `ses_notifications.go` for AWS SNS and the
connection pool respectively, applied to AWS S3. `NewS3StoreForTesting`
lets `internal/inbound`'s own tests exercise `Fetch`/`Delete` against a
fake `s3API` with no network access; `internal/handlers`' tests never touch
`internal/inbound.S3Store` at all — they use their own `fakeInboundObjectStore`.

### Design decision 2 — auto-reply/bounce detection

Chose six independent signals, any one sufficient (deliberately not a
scored combination — each is, on its own, standard practice for one of the
automated-mail shapes this endpoint will actually see):

- `Auto-Submitted` (RFC 3834) present with anything other than `no`.
- `Precedence: bulk` / `auto_reply` / `list` / `junk` — conventional list-
  software/autoresponder marker.
- `X-Autoreply` / `X-Auto-Response-Suppress` present at all (value
  irrelevant) — vacation-responder and Exchange/Outlook conventions.
- `Return-Path: <>` — the null-reverse-path convention RFC 3834 §4 and
  RFC 5321 use for mail that must never itself bounce or auto-reply.
- `Content-Type: multipart/report; report-type=delivery-status` — an
  RFC 3464 delivery status notification (a bounce-to-sender).

Tested with a message that carries a **valid, resolvable subject token**
alongside `Auto-Submitted: auto-replied`
(`TestSESInboundHandler_AutoReply_IgnoredEvenWithAValidToken`) — this is
the actual hazard the issue's Notes describe (an out-of-office quoting the
original campaign's subject verbatim), and the check runs before any
token/From lookup at all, so it can't be reached by getting the match logic
"right" first.

### The two required constraints

- **From: stays the fallback, never the primary path.** `match` (in
  `ses_inbound.go`) tries the token first and returns immediately on any
  outcome — a resolvable token, or an `ErrNotFound` — without ever falling
  through to From: in either case. From: is tried **only when no token was
  present at all**, so a forged-but-stale token can't fall through to
  trusting an equally-forgeable From: header for the same message.
  `TestSESInboundHandler_SubjectTokenMatch_...` proves the token wins even
  when the message also carries an unrelated third-party From: address.
- **Audit row carries `source = 'mailto'`.** Reuses
  `subscribers.SourceMailto` (already defined in `store.go`, unused until
  now) and the existing `audit.Logger.Record` / `audit.ActionSubscriberUnsubscribed`
  — no second audit helper invented. `matched_via` (`"token"` or `"from"`)
  rides in the same metadata map for operator visibility.
- **Delete only on processed, never on no-match.** "Processed" is defined
  as "a subscriber was genuinely identified" — which includes a
  complained-row match that correctly does nothing (mirrors `#0034`'s
  no-op), since there is nothing left for a human to review there either.
  No-match, an unparseable message, and an auto-reply all leave the object
  in place; `#0057`'s 30-day S3 lifecycle rule is what eventually reclaims
  those.

### What is right, checked rather than assumed

- **Criterion 5 holds on every path it covers.** An unreadable body, a
  non-JSON SNS envelope, an unrecognized `Type`, an unparseable SES event, an
  unresolvable object key, an unparseable fetched message, an auto-reply, and
  a genuine no-match all answer 200 with the object untouched. The two 500s
  (S3 fetch failure, subscriber-store failure) are deliberate, both sit
  strictly before any delete, and both mirror `ses_notifications.go`'s
  existing contract — retryable because a retry is the only thing standing
  between a transient failure and a lost unsubscribe request, and bounded by
  SNS's own retry policy rather than looping forever.
- **Deletion is confined to a genuine match.** No other path reaches
  `objects.Delete`. Deleting on the complained no-op is the right call: a
  subscriber *was* identified and correctly handled, so there is nothing left
  for a human to review, and it mirrors `#0034`'s no-op exactly.
- **Auto-reply genuinely precedes matching**, and the test proves it rather
  than restating it: `TestSESInboundHandler_AutoReply_IgnoredEvenWithAValidToken`
  carries a resolvable manage token *and* a `From:` that matches the same
  subscriber, and still asserts the row stays `active`, the object is not
  deleted, and no audit row is written. That is falsifiable by the ordering it
  measures.
- **Signature verification is pinned to a distinct topic.** `servePostgres`
  builds a second `sesnotify.NewVerifier` over `cfg.SESInboundTopicARN`, not
  the events verifier; `Verify` rejects an empty ARN outright and rejects a
  mismatched `TopicArn` before any certificate fetch, so an
  events-topic-signed notification cannot reach this endpoint. The config doc
  comment and `.env.example` both state the must-differ rule.
- **The notification shape matches the rule.** `#0057`'s rule is one
  `S3Action` with `TopicArn` set, which publishes SES's Received event
  (`mail`/`receipt` envelope). `SESReceiptAction` models the fields that
  action populates and `ObjectKey()` reads `receipt.action.objectKey`
  verbatim — correct, because SES writes the *full* key there, prefix
  included. The `ObjectKeyPrefix + messageId` fallback composes correctly for
  the configured `unsubscribe/` prefix (it ends in a slash), and is dead in
  practice; see the follow-up list below.

### Design decisions

1. **The S3 seam: approve.** Concrete `*s3.Client` confined to
   `internal/inbound` behind an unexported `s3API`, with `internal/handlers`
   declaring its own two-method `inboundObjectStore`, is exactly `CLAUDE.md`
   §1's rule and the same shape `sesVerifier` already uses for SNS. No SDK
   type reaches a handler signature or a handler test.
2. **Six independent auto-reply signals: approve the structure, one member is
   too broad.** Any-one-sufficient is right for this problem — each signal is
   standard practice for a different automated-mail shape, and a scored
   combination would just invent a threshold nobody can justify. Treating
   `Auto-Submitted: no` as *not* automated is a nice detail. But
   `Precedence: list` is over-broad; see the follow-up list.

### Reported for the orchestrator to file (not part of this issue)

- **`Precedence: list` over-rejects, and the failure is not neutral.**
  Legitimate human mail relayed through any list manager carries it, so a real
  unsubscribe request would be silently ignored — 200, object parked in a
  bucket nobody watches. That is a compliance-adjacent miss, unlike `bulk`,
  `auto_reply` and `junk`, which no ordinary person's reply carries. Suggest
  either dropping `list` or requiring it to co-occur with a second signal.
  Out of scope here: this issue's criteria say only that auto-replies and
  bounce-to-sender messages are ignored.
- **"Left in place for manual review" has no reviewer.** No-match,
  auto-reply and unparseable messages produce a log line and nothing else —
  no audit row, no admin surface, no counter — and `#0057`'s 30-day
  lifecycle then deletes them. Worth a minimal operator surface.
- **`ObjectKey()`'s prefix fallback is dead against real SES.** The Received
  notification's S3 action publishes `type`, `topicArn`, `bucketName` and
  `objectKey` only; there is no `objectKeyPrefix` field, and `objectKey`
  already carries the full prefixed key. Nothing is wrong, the branch is just
  unreachable. Confirm against the first real message once `#0057`'s rule set
  is activated and delete it if it stays dead — and note that if `objectKey`
  ever did arrive without the prefix, `Fetch` would 404 into the 500 path and
  SNS would retry to exhaustion, so that first live message is the check that
  matters.
- **A `Delete` failure after a committed unsubscribe is slightly lossy.** It
  returns 500; on retry the token path no longer resolves (the token was
  rotated), so the object stays until lifecycle, while the `From:` path
  re-unsubscribes and writes a second audit row for the same event. Low harm,
  no action needed now.

## Notes

PRD §6.5 path 3. The `From:` fallback is genuinely spoofable, which is why the subject token is preferred. Unsubscribing on a spoofed From is a low-harm outcome (someone gets removed from a mailing list they can rejoin) but it should still be the fallback, not the primary path.

Auto-replies are the practical hazard: an out-of-office bouncing off a campaign can land in this mailbox and must not be read as an unsubscribe request.
