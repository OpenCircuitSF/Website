## Description

`#0509` settled that the binary is **cross-compiled on the workstation and
shipped**, because the production box has no Go toolchain and one will not be
installed. `docs/deployment.md`'s redeploy procedure was rewritten accordingly.

`scripts/deploy.sh` was not. It still assumes it runs somewhere with `go` and
`npm` available, which on the production box is now false.

So the documented procedure and the script that nominally automates it
disagree, and the script is the one that is wrong.

## Acceptance criteria

1. `scripts/deploy.sh` matches `#0509`'s procedure: build locally with pinned
   `GOOS=linux`, `GOARCH=arm64`, `CGO_ENABLED=0` and the `-ldflags` commit
   hash, ship the artifact, verify by SHA-256, then install and restart.
2. It fails **loudly and early** if run somewhere without the toolchain, rather
   than part-way through. A deploy script that dies mid-sequence is worse than
   one that refuses to start.
3. The same `#0466` `scp`-precondition discipline the documented procedure
   uses: destination stated, writability confirmed, expected checksum compared.
4. It does not duplicate `docs/deployment.md`'s prose. Where the doc explains
   *why*, the script should reference rather than restate — two copies drift.
5. Respect `#0511`: **no host, account, instance, zone or role literals.** Take
   them from environment variables or a config file kept in the private AWS
   repo.
6. `shellcheck` clean, and `bash -n` — note `CLAUDE.md` §8: this machine's bash
   is 3.2.57, so `${var,,}`, `declare -A`, `mapfile` and `&>>` fail, and
   `bash -n` and `shellcheck` both pass on the bash-4 syntax anyway.

## Root cause

`scripts/deploy.sh` predated `#0509`'s no-toolchain decision and was never
rewritten when the documented procedure was: it ran **on the production
host**, required `go`, `npm`, and `systemctl` there, built with the host's
own toolchain into the systemd binary path, and had no migration step at
all. Every one of those assumptions is false on the current box, so the
script — the thing that looked most automated — was the least correct
artifact in the deploy path.

## Fix

`scripts/deploy.sh` is now a **workstation** script that automates the whole
`docs/deployment.md` Redeploy procedure as one command, referencing the doc
for every *why* instead of restating it (criterion 4):

1. **Preflight first, both sides.** Workstation tools (`git go npm zip
   shasum ssh scp awk base64 grep curl`) and — outside `--dry-run` — a
   read-only host probe (`unzip`, `golang-migrate`, passwordless `sudo`,
   `migrate -version`) before anything is built, so a missing piece refuses
   the run instead of dying mid-sequence (criterion 2). Verified: a
   `PATH` without `go` dies at preflight, exit 1.
2. **Version and provenance pinned.** `VERSION` is derived from
   `cmd/opencircuit/main.go`'s version const (an explicit argument must
   agree); the commit hash is embedded via `-ldflags
   -X main.commitHash=$COMMIT` and re-proved on the host afterwards
   (`--version` must name `$COMMIT`, before and after install).
3. **Build in a throwaway worktree at HEAD** (the `scripts/release.sh`
   idiom): SPA first (`npm ci && npm run build`), then the cross-compile
   with pinned `GOOS=linux GOARCH=arm64 CGO_ENABLED=0` (criterion 1). The
   shared checkout's `web/dist/index.html` is never touched, so `CLAUDE.md`
   §8b's npm-build hazard cannot reach other agents.
4. **Bundle = release.sh's shape**: binary, `migrations/`,
   `opencircuit.service`, zipped, `SHA256SUMS` computed — nothing else.
5. **`#0511` scan before shipping (criterion 5).** The nine restricted
   identifiers are never written into this script: the `RESTRICTED_B64`
   array is **extracted from `scripts/release.sh` at runtime** (awk range +
   `eval`), fail-closed if the extraction is empty or any entry decodes
   empty — the list stays single-sourced, matching
   `internal/db/identifier_redaction_guard_test.go`'s own single-source
   design.
6. **`#0466` scp discipline (criterion 3)**: destination stated
   (`$RELEASES_ROOT/$TAG`), writability confirmed (`mkdir -p` + `test -w`
   over ssh, before the build even starts), then `scp` the bundle +
   `SHA256SUMS` and `sha256sum -c` **on the host**.
7. **Doc-mandated ordering on the host**: prove the artifact runs
   (`--version` names this commit) → back up the previous binary to
   `opencircuit-previous` → **`[Y/n]` gate** → restore-point check (newest
   `/var/backups/host/*-db` dump, non-zero, checksum-verified — the doc's
   step 6 check, verbatim in intent) → `migrate -path $DEST/migrations up`
   with `DATABASE_URL` sourced from `/etc/opencircuit/config.env` on the
   host (the on-box golang-migrate installed per `#0513`) → `install` +
   `systemctl restart` + `is-active` → `curl /health` → live `--version`.
8. **`--dry-run`** runs every local gate and the real build, then prints
   the exact remote plan (every ssh/scp line) without touching the host —
   the `release.sh --dry-run` idiom. The host preflight, scp, and every
   remote step are unreachable under the flag.
9. **`#0424` gate preserved byte-for-byte.** The GATE-0424 marker pair, the
   `[ -n "$UNTRACKED_PUBLIC" ]` condition, the single `die(){`/`info(){`
   definitions, and the general dirty-tree notice are all still present,
   because `scripts/deploy_guard_test.sh` extracts and executes exactly
   those lines from this file; the gate's die message was updated to say
   what is now true (the worktree build ships the committed tree only, so
   an untracked `web/public/` file would be silently *left out*).

`docs/deployment.md` was updated in the two places that described the old
script: the "`scripts/release.sh` and `scripts/deploy.sh` — neither matches
this procedure yet" section now states what each script automates and what
stays manual (rollback, config-only restart, out-of-order steps), and the
Troubleshooting section's "checks #1, #2, #3, and #7" claim now matches the
new script's actual checks.

## Gotchas

- `scripts/deploy_guard_test.sh` extracts the gate block and helper
  definitions out of `deploy.sh` by exact text anchors and asserts each
  appears exactly once — any rework of this script must keep the
  `# GATE-0424-BEGIN`/`-END` markers, the `[ -n "$UNTRACKED_PUBLIC" ]`
  condition text, and exactly one `die(){`/`info(){`, or the harness
  fails (exit 2, extraction broken) or silently tests the wrong thing.
  Run `bash scripts/deploy_guard_test.sh` after any future edit here.
- `shellcheck` exits non-zero on "info"-level findings too; the intended
  client-side/remote-side expansion split (SC2029) and the deliberately
  single-quoted remote body (SC2016) each needed one directive, placed
  where the intent is explained rather than blanket-suppressed.
- The dry-run plan prints the real command strings; building them as
  variables (not inline literals) is what keeps the printed plan and the
  executed commands from drifting — and is also what keeps `SC2029`
  quiet, since shellcheck cannot see inside a variable.
- `--help` prints its range with `sed -n '2,62p'`; the range was checked
  against the whole header rather than guessed — release.sh's truncated
  `--help` (its review's first non-blocking observation) was exactly this
  mistake.

**Dry-run-only proof of the remote steps is what the criteria permit.** None
of the six criteria requires *executing* a deploy — they specify what the
script does, and the sibling issue #0537 states explicitly that a real deploy
is NOT required and must not be performed; the operator directive binding this
review forbids one too. `--dry-run` runs every local gate and the real build,
then prints the exact bytes each ssh/scp step will run (they are built once
as variables and both printed and executed from the same strings, so plan and
execution cannot drift), and the restore-point check body matches
docs/deployment.md step 6's own shape (`ls -td /var/backups/host/*-db`,
non-`-s` guard, checksum verify). So the remote half is structurally proven
and the residual risk — those commands never having run against the box — is
the operator's first real deploy to absorb, which the implementer flagged
honestly. The criteria permit this; no further proof is demanded of the
script.

One deliberate deviation noted, not bounced: the confirmation prompt reads
`[y/N]` where the Fix prose says `[Y/n]` — the implemented default-deny is
the safer of the two for a gate in front of irreversible migrations, and the
gate's existence, position (before restore-point check → migrate → install →
restart), and abort path all match the criterion's intent.
