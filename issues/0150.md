## Description

`scripts/testdb.sh gc` dropped **every** `opencircuit_test_*` database unconditionally. An implementer finishing `#0147` ran it as a cleanup step and destroyed `opencircuit_test_0055b`, which belonged to a concurrently running `#0055` agent.

The database itself is cheap — a ~0.2s clone from the template — and nothing was lost. The defect is the shape of the command: the *destructive-to-everyone* action was the bare default, sitting one word away from the safe per-agent `drop`, in a project whose whole concurrency model (§5a) is "every agent gets its own database". `CLAUDE.md` even listed `gc` under cleanup, so running it was following instructions.

The agent that did it disclosed it unprompted, which is the only reason it was caught.

## What has been done

Fixed immediately by the orchestrator, because three agents were running at the time and the next reflexive `gc` would have done it again:

- `gc` now **refuses without `--all`**, listing the databases it would have dropped and pointing at `drop <ISSUE>` for the caller's own.
- With `--all`, it **skips any database with live connections** rather than racing whoever holds them.
- `CLAUDE.md` §5a's cleanup guidance now says plainly that `gc` is not a cleanup step, and the script's own usage header says the same.

## Acceptance criteria

- [x] A bare `gc` cannot destroy another agent's database — verified: it refuses and lists them
- [x] `gc --all` skips databases with active connections
- [x] `CLAUDE.md` §5a and the script header describe the new semantics
- [x] A guard test covers the refusal, so the safe default cannot quietly regress the way `#0140`'s `pipefail` did
- [x] Check the other scripts for the same shape — an unqualified destructive default that assumes the caller is alone. `db-reset.sh` is the obvious candidate to read

## Implementation notes (phase 2, 2026-08-23)

**Criterion 4 — guard test.** Added `scripts/testdb_gc_guard_test.sh`, a
standalone shell test (no Go/bats harness exists for `scripts/` in this repo,
so it follows the same pattern as the scripts it tests: `set -uo pipefail`,
clear PASS/FAIL lines, a paste-able failure message naming the regression).

It asserts three things:

1. Bare `scripts/testdb.sh gc` (the real, tracked script, unmutated) refuses
   (non-zero exit) and does not drop scratch databases that exist.
2. `gc --all` skips a database with a live connection and still drops one
   without one — run against a **private copy** of `testdb.sh` with `PREFIX`
   rewritten to `opencircuit_test_0150gt_`, a prefix no real issue id can ever
   produce, so the `--all` sweep in this assertion can only ever touch
   databases the test itself created.
3. **Mutation proof**: a second private copy has the refusal `if` neutered
   (`if false; then`) *and* the same scoped prefix. Bare `gc` against that
   mutant DOES sweep, proving assertion (1) is actually sensitive to the
   #0150 regression rather than vacuously true.

**Why the mutation runs on copies, not the tracked file in place.** The issue
text asks to "make bare gc sweep again, confirm the guard fires, restore,
verify byte-identity with shasum -a 256." Editing `scripts/testdb.sh` in place
to remove the guard and then running its real `gc --all` would, for the
seconds until it's restored, sweep the REAL `opencircuit_test_` prefix — which
matches every other agent's scratch database, live-connection or not. `CLAUDE.md`
§8b / `docs/obstacles.md` §4 are explicit that a guard-removal mutation test
must run against databases the test creates and owns, never a real agent's.
So the mutation is applied only to throwaway copies in a `mktemp -d` workdir,
each copy's prefix substitution is verified with `grep` before any destructive
command runs against it (aborting loudly if the substitution silently failed),
and the byte-identity requirement is satisfied by hashing the real, tracked
`scripts/testdb.sh` at the start and end of the whole run — it is provably
unchanged, because the run never touches it, only private copies of it.

Ran twice back-to-back: both runs `PASS` on all assertions, exit 0, and leave
`scripts/testdb.sh list` showing only `opencircuit_test_template` before and
after (confirmed via `git status --porcelain -- scripts/` and `git diff
--stat -- scripts/testdb.sh`, both showing no change to the tracked file).

**Criterion 5 — other scripts checked for the same shape.**

| Script | Destructive default assumes solitude? | Blast radius |
|---|---|---|
| `scripts/db-reset.sh` | **Yes, and not yet guarded the way `testdb.sh` now is.** Bare invocation targets the single shared `opencircuit` database (or `opencircuit_test` if named); it force-terminates every other backend connected to that database (`pg_terminate_backend(... datname=$DB ...)`) before dropping and recreating it, unconditionally — no live-connection skip, no confirmation. It does correctly refuse a non-localhost host and a non-`opencircuit*` name (guards against hitting production), but nothing stops one agent's `db-reset.sh` (or the user's) from destroying another agent's or the user's in-progress work on the shared dev/test database while they're mid-session. This is the same class of bug #0150 fixed in `testdb.sh gc`, just on the single shared database name instead of the per-agent scratch pool. **Not fixed here** — out of scope per this dispatch's instructions (report, don't fix a sweep across scripts). Worth filing.
| `scripts/dev.sh` | **Yes — already filed as `#0117`.** `free_port()` runs `kill -9` on whatever holds `:8080` or `:5173`, no ownership check. Confirmed present, unchanged; not refiled, not fixed here.
| `scripts/sim.sh` | Minor instance. No kill/drop, but its default `OUTPUT_PATH` is a fixed shared path (`/tmp/opencircuit-sim.png`); two agents running it concurrently with default args overwrite each other's screenshot — the same "prove your fix against someone else's build" hazard `CLAUDE.md` §8b describes for the port-8099 incident, just for a screenshot file rather than a server. Low blast radius (a stale/wrong image, not data loss), but worth a caller passing a distinct `OUTPUT_PATH`.
| `scripts/deploy.sh` | No — appropriately gated. Single production target, requires an interactive `[y/N]` confirmation before the one destructive step (service restart), uses `mktemp` for its build artifact rather than a fixed path. Assuming solitude is actually correct for a production deploy; not a candidate for this pattern.

Nothing beyond `#0117` (already filed) is fixed in this dispatch. `db-reset.sh`'s
gap and `sim.sh`'s fixed output path are reported to the orchestrator to file,
per `CLAUDE.md` §9 (subagents report issues, they do not file them).

## Verification

Guard test is a shell script, not a Go test — run directly, twice:

```
./scripts/testdb_gc_guard_test.sh   # run 1: exit 0, all PASS
./scripts/testdb_gc_guard_test.sh   # run 2: exit 0, all PASS (idempotent)
```

`uptime` before starting: `load averages: 1.78 2.13 2.16` (idle). Database
census before and after (`scripts/testdb.sh list`): `opencircuit_test_template`
only, both times — nothing belonging to another agent existed or was touched.
`git status --porcelain -- scripts/` after the run shows only the new,
untracked `scripts/testdb_gc_guard_test.sh`; `git diff --stat -- scripts/testdb.sh`
is empty, confirming the tracked script was never modified. No `go test`/`.test`
processes left running (`pgrep -f 'go test|\.test '` empty). No Go or web
code changed, so `scripts/check.sh` was not run — nothing in its scope was
touched.
