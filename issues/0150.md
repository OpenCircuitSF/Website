## Description

`scripts/testdb.sh gc` dropped **every** `opencircuit_test_*` database unconditionally. An implementer finishing `#0147` ran it as a cleanup step and destroyed `opencircuit_test_0055b`, which belonged to a concurrently running `#0055` agent.

The database itself is cheap — a ~0.2s clone from the template — and nothing was lost. The defect is the shape of the command: the *destructive-to-everyone* action was the bare default, sitting one word away from the safe per-agent `drop`, in a project whose whole concurrency model (§5a) is "every agent gets its own database". `CLAUDE.md` even listed `gc` under cleanup, so running it was following instructions.

The agent that did it disclosed it unprompted, which is the only reason it was caught.

## What has been done

Fixed immediately by the orchestrator, because three agents were running at the time and the next reflexive `gc` would have done it again:

- `gc` now **refuses without `--all`**, listing the databases it would have dropped and pointing at `drop <ISSUE>` for the caller's own.
- With `--all`, it **skips any database with live connections** rather than racing whoever holds them.
- `CLAUDE.md` §5a's cleanup guidance now says plainly that `gc` is not a cleanup step, and the script's own usage header says the same.

## Acceptance criteria

- [x] A bare `gc` cannot destroy another agent's database — verified: it refuses and lists them
- [x] `gc --all` skips databases with active connections
- [x] `CLAUDE.md` §5a and the script header describe the new semantics
- [x] A guard test covers the refusal, so the safe default cannot quietly regress the way `#0140`'s `pipefail` did
- [x] Check the other scripts for the same shape — an unqualified destructive default that assumes the caller is alone. `db-reset.sh` is the obvious candidate to read

## Implementation notes (phase 2, 2026-08-23)

**Criterion 4 — guard test.** Added `scripts/testdb_gc_guard_test.sh`, a
standalone shell test (no Go/bats harness exists for `scripts/` in this repo,
so it follows the same pattern as the scripts it tests: `set -uo pipefail`,
clear PASS/FAIL lines, a paste-able failure message naming the regression).

It asserts three things:

1. Bare `scripts/testdb.sh gc` (the real, tracked script, unmutated) refuses
   (non-zero exit) and does not drop scratch databases that exist.
2. `gc --all` skips a database with a live connection and still drops one
   without one — run against a **private copy** of `testdb.sh` with `PREFIX`
   rewritten to `opencircuit_test_0150gt_`, a prefix no real issue id can ever
   produce, so the `--all` sweep in this assertion can only ever touch
   databases the test itself created.
3. **Mutation proof**: a second private copy has the refusal `if` neutered
   (`if false; then`) *and* the same scoped prefix. Bare `gc` against that
   mutant DOES sweep, proving assertion (1) is actually sensitive to the
   #0150 regression rather than vacuously true.

**Why the mutation runs on copies, not the tracked file in place.** The issue
text asks to "make bare gc sweep again, confirm the guard fires, restore,
verify byte-identity with shasum -a 256." Editing `scripts/testdb.sh` in place
to remove the guard and then running its real `gc --all` would, for the
seconds until it's restored, sweep the REAL `opencircuit_test_` prefix — which
matches every other agent's scratch database, live-connection or not. `CLAUDE.md`
§8b / `docs/obstacles.md` §4 are explicit that a guard-removal mutation test
must run against databases the test creates and owns, never a real agent's.
So the mutation is applied only to throwaway copies in a `mktemp -d` workdir,
each copy's prefix substitution is verified with `grep` before any destructive
command runs against it (aborting loudly if the substitution silently failed),
and the byte-identity requirement is satisfied by hashing the real, tracked
`scripts/testdb.sh` at the start and end of the whole run — it is provably
unchanged, because the run never touches it, only private copies of it.

Ran twice back-to-back: both runs `PASS` on all assertions, exit 0, and leave
`scripts/testdb.sh list` showing only `opencircuit_test_template` before and
after (confirmed via `git status --porcelain -- scripts/` and `git diff
--stat -- scripts/testdb.sh`, both showing no change to the tracked file).

**Criterion 5 — other scripts checked for the same shape.**

It does correctly refuse a non-localhost host and a non-`opencircuit*` name (guards against hitting production), but nothing stops one agent's `db-reset.sh` (or the user's) from destroying another agent's or the user's in-progress work on the shared dev/test database while they're mid-session. This is the same class of bug #0150 fixed in `testdb.sh gc`, just on the single shared database name instead of the per-agent scratch pool. **Not fixed here** — out of scope per this dispatch's instructions (report, don't fix a sweep across scripts). | `scripts/dev.sh` | **Yes — already filed as `#0117`.** `free_port()` runs `kill -9` on whatever holds `:8080` or `:5173`, no ownership check. Confirmed present, unchanged; not refiled, not fixed here.

## Review notes (phase 3, 2026-08-23)

**Verdict: pass.** All five criteria hold. The guard test is real, sensitive, and
cannot reach anything it does not own.

**Database census, before and after.** `select datname from pg_database order by 1`,
run by the reviewer immediately before and immediately after
`scripts/testdb_gc_guard_test.sh`:

```
opencircuit, opencircuit_test, opencircuit_test_template,
postgres, shortlinks, shortlinks_test, template0, template1
```

Byte-identical lists. Nothing outside the test's own
`opencircuit_test_0150gt_` prefix was created, dropped, or altered.
`shasum -a 256 scripts/testdb.sh` was `e6ead00a…5cff2` before and after;
`git status --porcelain` was empty after the run. `scripts/check.sh` (under
review for `#0140` by another agent) was not touched — its hash is unchanged
too. `uptime` at the start: load averages `2.40 2.21 2.16` — idle.

**Trace of every destructive statement.** Three sites, all scoped:

| Where | Statement | Reachable names |
|---|---|---|
| `dropdb_raw` / `cleanup` | `DROP DATABASE IF EXISTS $1` | only names from `CREATED_DBS`, every one built from `TESTPREFIX` |
| Part 2 | `"$SCOPED" gc --all` | `datname like 'opencircuit_test_0150gt_%'` |
| Part 3 | `"$MUTANT" gc` (guard neutered) | same scoped prefix |

Part 1 is the only place the **real** tracked `scripts/testdb.sh` is executed,
and it is executed as bare `gc`, whose entire behaviour under test is to refuse
and exit 1. No real `gc --all` is ever run against the real
`opencircuit_test_` prefix.

The prefix is unreachable by a real agent in practice. `name_for()` builds
`opencircuit_test_<ISSUE stripped to [:alnum:]_>` and `scripts/check.sh` passes
`$ISSUE` straight through, so producing a colliding name would require somebody
to set `ISSUE=0150gt_something` literally. Four-digit issue ids cannot reach it.
Both copies verify their own prefix substitution with `grep` and abort with a
`FATAL:` before any destructive command if it silently failed — the right order.

**Mid-run failure.** The `EXIT` trap was probed directly: it fires on `SIGTERM`
and on `SIGINT`, so an interrupted or bounced run still drops its databases and
removes its `mktemp -d`. Only `SIGKILL` (or a crash) skips it, leaving
`opencircuit_test_0150gt_*` databases behind. Those are *not* orphaned forever:
the real prefix is a strict prefix of the test's, so an ordinary
`scripts/testdb.sh gc --all` sweeps them. The backgrounded
`psql … pg_sleep(20)` holding the live connection can outlive a `SIGKILL`ed
parent for up to 20s, during which `gc --all` correctly *skips* that one
database; after it exits, the leftover is sweepable like the rest. No leftover
can be mistaken for another agent's work, and none blocks anyone.

**The live-connection skip is observed, not merely reported.** The assertion is
`db_exists "$CONN_DB"` — a `select 1 from pg_database` — not a grep of the
script's stdout. The paired assertion that `$IDLE_DB` *was* dropped is what
keeps it from passing vacuously: if the `gc --all` invocation silently no-opped,
`CONN_DB` would survive (apparent pass) but `IDLE_DB` would survive too, and
that is a `FAIL`.

**Mutation sensitivity reproduced independently.** The reviewer built its own
copy of `testdb.sh` under a separate prefix (`opencircuit_test_0150rv_`) with
the refusal `if` neutered, seeded one database, and ran bare `gc`:

- mutant, bare `gc` → exit **0**, `opencircuit_test_0150rv_probe` **dropped**;
- real tracked script, bare `gc` → exit **1**, refusal listing printed,
  `opencircuit_test_0150rv_probe2` **survived**.

So criterion 1's assertion is genuinely sensitive to the `#0150` regression —
not the vacuous shape `#0140` had one file over. Both probe databases were
dropped afterwards; they appear in neither census.

Other checks: the commit is confined to the one new file (219 insertions,
nothing else); the file is `0755` with a `#!/usr/bin/env bash` shebang; it
derives `REPO` from `BASH_SOURCE` and was run from an unrelated working
directory with identical output; failure messages name the regression and the
next command (`git diff -- scripts/testdb.sh`), meeting `#0187`'s pasteable
standard.

**Criterion 5 spot-check.** Read `db-reset.sh` and `deploy.sh` directly rather
than accepting the implementer's table.

- `db-reset.sh` — the report is accurate. It runs
  `SELECT pg_terminate_backend(pid) … WHERE datname='$DB' AND pid <> pg_backend_pid()`
  unconditionally, then `DROP DATABASE`/`CREATE DATABASE`, with no
  live-connection skip and no confirmation. Its two refusals do hold: a `case`
  on `PGHOST_URL` rejects any host that is not `localhost`/`127.0.0.1`, and a
  `case` on `$DB` rejects any name not matching `opencircuit*`. One point the
  implementer's table missed and `#0207` should carry: that second guard admits
  `opencircuit_test_0055`, so `scripts/db-reset.sh opencircuit_test_0055` will
  terminate and destroy **another agent's per-agent scratch database** — the
  exact `#0150` failure, reachable through a different script. (`$DB` is also
  interpolated into SQL unquoted, though the prefix guard limits what can get
  through.)
- `deploy.sh` — confirmed no issue. Single production target, an interactive
  `[y/N]` before the only destructive step, `mktemp` for the build artifact, and
  six fail-fast gates. Assuming solitude is correct for a production deploy.

**Reported to the orchestrator, not filed** (`CLAUDE.md` §9): the `db-reset.sh`
scratch-database widening above, for `#0207`; the test's Part 2 writing its
capture file to `/tmp/testdb_gc_guard_test_part2.$$` instead of the `$WORKDIR`
it already owns (PID-suffixed, so low risk, but gratuitously shared and left
behind on `SIGKILL`); `createdb_raw` discarding `CREATE DATABASE` errors, so a
role missing `CREATEDB` would surface as a loud but misdiagnosed
"REGRESSION #0150"; and that nothing invokes the guard test automatically, so it
protects the fix only when somebody remembers to run it.
