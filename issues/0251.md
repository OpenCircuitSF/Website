## Description

`#0208` replaced a per-call-site pipefail grep with a single `runpipe()` funnel
and a marker-delimited self-check. A review ran **nine evasion mutants** against
it and eight were caught, including every form that defeated the old grep
(`/bin/bash -c`, `env bash -c`, a split `bash \`+newline+`-c`, `$SH -c`). It
also proved the self-check cannot flag itself in both directions.

Two gaps remain, and the first is a real regression against what the old check
provided:

**1. Nothing asserts that `runpipe()`'s own definition still spells
`-o pipefail`.** The guard deletes the `GUARD-0208` block before scanning, so
the definition is invisible to it. Delete `-o pipefail` from that one line and
**every check still passes** — while the property the whole issue exists to
enforce is gone. The review demonstrated this: with the flag stripped, a test
that printed `--- FAIL` still produced `VERIFICATION PASSED` and exit 0.

The old per-call-site grep had this positive assertion by construction, because
it looked *for* the flag rather than for its absence elsewhere. The refactor
made the structure better and lost the one check that mattered most.

**2. `run "$SHELL" -c "… | tail"` evades all three checks.** Contrived — nobody
writes that — and recorded for completeness rather than as a live concern.

## Implementation notes

Added a new check inside the existing `GUARD-0208` marker block (so it is
itself excluded from the negative scan, the same protection every other
check in that block already has), right after the existing call-count check
and before `# END GUARD-0208`:

```sh
RUNPIPE_DEF="$(sed -n "/${BR}/,/${ER}/p" "$0" | grep -vE '^[[:space:]]*#')"
if ! printf '%s\n' "$RUNPIPE_DEF" | grep -qE 'run[[:space:]]+bash[[:space:]]+-o[[:space:]]+pipefail[[:space:]]+-c'; then
  printf '...PIPEFAIL REGRESSION (#0208/#0251)...' >&2
  exit 2
fi
```

`$BR`/`$ER` are the same `RUNPIPE-0208` marker variables the existing
negative scan already builds (two concatenated string literals, so this
line's own source never spells the marker contiguously — same technique
`#0208` used for `$BG`/`$EG`). `sed -n "/${BR}/,/${ER}/p"` is the print-range
complement of the delete-range the negative scan already uses on the same
markers — it extracts runpipe()'s own definition **from `"$0"`**, not from
`$SCAN` (which has that block deleted), which is exactly why the existing
checks were blind to it. Comment lines inside the extracted range are
stripped so a mention of the phrase in a comment can't satisfy the match —
in practice the range currently contains only the `BEGIN`/`END` marker
comments and the one-line function definition, so after stripping,
`$RUNPIPE_DEF` is exactly that one line.

Scoping the extraction to the marker-delimited range (rather than grepping
the whole file for the phrase) is what satisfies "cannot be satisfied by the
string appearing anywhere else" — a call site elsewhere in the file that
happened to spell `run bash -o pipefail -c` would not be inside the
`RUNPIPE-0208` range and so could not make this check pass; only the actual
definition, sitting inside its own marker block, can.

**Item 2** (`run "$SHELL" -c "…"` evades every check) is not closed — it
remains genuinely unreachable through this design's grep-based approach, and
closing it would need a real shell parser. Recorded instead as a comment
directly above `step "self-check: pipefail funnel guard (#0208)"`, next to
the existing "what must NOT appear" paragraph, so a future reader sees it in
the same place they'd look for the guard's other known boundaries.

### What fails: criterion 3

> "The assertion cannot be satisfied by the string appearing anywhere else in
> the file — it must be the definition"

It can. The assertion is

```sh
RUNPIPE_DEF="$(sed -n "/${BR}/,/${ER}/p" "$0" | grep -vE '^[[:space:]]*#')"
if ! printf '%s\n' "$RUNPIPE_DEF" | grep -qE 'run[[:space:]]+bash[[:space:]]+-o[[:space:]]+pipefail[[:space:]]+-c'; then
```

Two properties defeat it. `grep -vE '^[[:space:]]*#'` strips only **whole-line**
comments, so a trailing comment survives into `$RUNPIPE_DEF`. And `sed`
range-printing reopens on every later start-pattern match, so **all**
`RUNPIPE-0208` blocks in the file are concatenated, not just the first. The
match is then made against the whole block, never against the definition line.

Crucially, all three fakes are also invisible to the negative checks above,
because `$SCAN` deletes the same ranges — so nothing else catches them either.

**All three were run end to end, against a real always-failing test**
(`internal/config`, one `t.Fatal`), under `ISSUE=…` with its own database:

| fake | one-line edit | guard | result |
|---|---|---|---|
| **A — trailing comment** | `runpipe() { run bash -c "$1"; }  # was: run bash -o pipefail -c` | silent | `--- FAIL` printed, **`VERIFICATION PASSED`, exit 0** |
| **B — decoy marker block** | flag stripped; a `# BEGIN RUNPIPE-0208` / `# END RUNPIPE-0208` pair added near the bottom of the file wrapping `_unused() { run bash -o pipefail -c "$1"; }` | silent | `--- FAIL` printed, **`VERIFICATION PASSED`, exit 0** |
| **C — extra line inside the block** | flag stripped; `_RUNPIPE_NOTE=': run bash -o pipefail -c'` added inside the real marker block | silent | `--- FAIL` printed, **`VERIFICATION PASSED`, exit 0** |

Control, for contrast: the **unmutated** `scripts/check.sh` against the same
failing test printed
`FAILED (1): bash -o pipefail -c go test ./internal/config/... -p 2 -count=1 2>&1 | tail -40`
and ended `VERIFICATION FAILED`, exit 1. So the property really is lost in all
three fakes, not merely the assertion cosmetically dodged.

**Fake A is the one that matters.** It is not contrived the way mutant 7 is —
`# was: …` is the single most natural thing anyone writes when removing a flag.
The implementation notes claim "Comment lines inside the extracted range are
stripped so a mention of the phrase in a comment can't satisfy the match"; that
is true only of full-line comments, and the guard is defeated by the ordinary
case.

**Fake B falsifies the criterion literally.** The string appears *somewhere else
in the file* — in a second marker block — and satisfies the assertion. Both
`issues/0251.md` ("only the actual definition, sitting inside its own marker
block, can") and `scripts/check.sh` lines 154–157 ("only the actual definition
can produce a match here") state the opposite. A false claim written into the
source is worse than a missing one, because the next reader will trust it.

### What the next implementation pass must do

The fix is small; the current extraction is just aimed one level too coarse.

1. **Match the definition line, not the block.** Select it inside the range —
   e.g. `grep -E '^runpipe\(\)'` — and assert on that line alone.
2. **Strip trailing comments before matching**, or anchor the pattern to the
   whole line so text after the closing `}` cannot contribute. Fake A must
   fail.
3. **Assert the marker block appears exactly once.** Count lines matching
   `$BR` (and `$ER`) in `"$0"` and fail if the count is not 1. This closes
   fake B, and is worth having anyway — a duplicated marker block silently
   changes what *every* check in this guard scans, not just this one.
4. **Assert exactly one `runpipe()` definition exists.** A second definition
   later in the file would shadow the first at runtime; today nothing notices.
5. Re-prove with fakes A, B and C explicitly, not only with the plain strip —
   the plain strip is already caught and is not the interesting case.
6. Correct the two prose claims (the issue's implementation notes and the
   comment at `scripts/check.sh` 154–157) to describe what the check actually
   guarantees.

This is the same shape as the defect the issue was filed against, one level in:
`#0208`'s guard could not see its own definition; this fix can see the block but
still not the line. The question that found both is the one this issue's own
Notes names — "what does this guard *not* look at?"
