# 0096 — internal/auth is the suite's long pole and cannot be de-truncated mechanically

| | |
|---|---|
| **Status** | open |
| **Module** | infra / auth |
| **Platform** | All |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-08-19 |

## Description

`#0091` removed the per-test `TRUNCATE ... RESTART IDENTITY CASCADE` from the
subscriber-facing helpers and brought the whole suite from "never completes" to under
six minutes. It deliberately **kept** truncation wherever a test asserts over a whole
table. `internal/auth` is the largest such place, and it is now the longest-running
package in the suite: measured at **88–149 s** across three runs by `#0091`'s reviewer,
against `internal/handlers`' 137 s and `internal/subscribers`' 9 s.

It is also one of the two surviving sources of the `truncate tables: timeout: context
deadline exceeded` flake that `#0084` is about.

**The mechanical fix does not apply here.** `internal/subscribers` could switch to
nanosecond-unique seeded rows because its assertions were all scoped, or could be
scoped, to rows the test itself created. `internal/auth` has at least one genuine
whole-table assertion — `recovery_test.go`'s `SELECT COUNT(*) FROM users` — which is
meaningful *because* it counts every user. Removing truncation without first rewriting
that assertion changes what the test proves.

So this is a design task, not a repeat of `#0091`, and it is why `#0091` correctly left
it alone rather than forcing a uniform treatment.

## Acceptance criteria

- [ ] Every whole-table assertion in `internal/auth` is identified and each one either
      rewritten to be scoped to rows the test owns, or documented as genuinely needing
      an empty table with the reason
- [ ] `recovery_test.go`'s `SELECT COUNT(*) FROM users` specifically: decide what it is
      really asserting and express that without depending on global emptiness
- [ ] Per-test truncation removed wherever the rewritten assertions allow it
- [ ] Real before/after numbers for `internal/auth`, measured one package at a time,
      with the machine's load average recorded alongside
- [ ] The package survives **two consecutive `-count=1` runs against the same
      un-recreated database**, and `-count=2 -shuffle=on` — the checks `#0091`'s
      reviewer used, which are what actually prove order-independence
- [ ] Isolation is demonstrated by mutation, not asserted: break it, watch a test fail,
      quote the output, revert

## Notes

Surfaced by `#0091`'s review, which explicitly recommended filing it and could not
(it owned only `issues/0091.md`).

Useful facts established there, so nobody re-derives them:

- **There is not one `t.Parallel()` in the repository**, and no hardcoded row-id literal
  in any DB-backed test. Both were checked directly.
- Under a plain `go test ./...` (no `-p 1`), `testdb.Lock()`'s wait is billed to each
  package's reported time — `internal/subscribers` reads 540 s there and 8 s under
  `-p 1`. That is an artefact of the lock, not a regression. Measure with `-p 1`.

Worth doing only if the time is actually bought back: 90 s in a 6-minute suite is real
but not urgent, and the assertion-rewriting carries a genuine risk of weakening what
these tests prove. If the analysis concludes the truncation is load-bearing and should
stay, **that is a legitimate outcome** — record it and close the question rather than
forcing a change.
