## Description

Swap ShortLinks' SES SMTP transport for the SES v2 API using the EC2 instance role, keeping the `Mailer` interface seam so tests can inject a recorder.

## Root cause

Not a bug fix — a planned transport swap. ShortLinks' `auth.SESMailer` sent over SES SMTP with STARTTLS + `PLAIN` auth, authenticated by a static username/password derived from IAM credentials. `#0007` removed every SES SMTP config variable (`SES_SMTP_HOST/PORT/USERNAME/PASSWORD`) because this project has no static AWS credentials anywhere — only the EC2 instance role, which authenticates API calls, not SMTP AUTH. That left `SESMailer.username`/`password` permanently empty and `cmd/opencircuit/main.go` wired `NoOpMailer` on the Postgres path instead, since the SMTP mailer could never actually send. `#0027` was the planned fix: replace the transport with the SES v2 API, which the instance role *can* authenticate.

## Fix

- **`internal/mailing`** (new package) — the shared SES v2 sending primitive: `Mailer` (`Send(ctx, msg) (messageID, err)`, ShortLinks' seam verbatim) and `SESMailer`, its implementation on `github.com/aws/aws-sdk-go-v2/service/sesv2`. Every send builds a `types.EmailContent.Simple` message with `ConfigurationSetName` set from `SES_CONFIGURATION_SET`, custom `types.MessageHeader`s from `Message.Headers` (for #0035's `List-Unsubscribe`/`List-Unsubscribe-Post`/`List-Id`), and both `Body.Html`/`Body.Text` when both are present — SES builds the `multipart/alternative` MIME structure itself from the two `Content` parts, so nothing here hand-rolls MIME. `Send` retries `*types.TooManyRequestsException` (SES v2's throttling error — SES v1's `ThrottlingException` by another name) up to 4 attempts with exponential backoff (200ms → 400ms → 800ms via an injectable `sleep` func so tests never wait in real time); every other error wraps and returns immediately. The returned `messageID` is read directly off `SendEmailOutput.MessageId`; if SES ever accepts a send but returns no ID, `Send` errors rather than fabricating one. `NewSESMailer` validates `AWS_REGION`/`SES_CONFIGURATION_SET`/`EMAIL_FROM` are non-empty and fails construction with a named-variable error otherwise — deliberately, per the task's "fail clearly, don't silently swallow" instruction, since #0026's uniform `202` response would otherwise mask a misconfigured mailer completely. `RecordingMailer` records every `Send` call (or returns a configured error) for tests, mirroring ShortLinks' recorder.
- **`internal/auth/ses_mailer.go`** — `SESMailer` no longer dials SMTP; it composes each of the three transactional emails (verification, recovery, sessions-revoked) into a `mailing.Message` (text-only; these are single-recipient auth emails, not campaign HTML) and calls an injected `mailing.Mailer.Send`. The "recipient omitted from wrapped errors" PII-leak protection is preserved exactly — `send()`'s `fmt.Errorf` still never embeds `toEmail`.
- **`NewSESMailerWithAddr` deleted**, per `#0007`'s conditional approval. Its one dependent, `internal/handlers/logging_test.go`'s `TestAuthHandler_MailerErrorDoesNotLeakEmail`, previously forced a deterministic failure by dialing a closed local port (`127.0.0.1:1`) — meaningless for an API client with no dial step. It now uses the new `auth.NewSESMailerWithSender(sender mailing.Mailer, cfg)` seam, injecting a `failingMailer` fake that returns a realistic non-email-containing SES-style error (`api error MessageRejected: Email address is not verified`). This still exercises the real production `SESMailer.send` composition/wrapping path — only the network-facing SES client underneath is faked, matching the task's instruction to give the test "an injectable interface or a fake, not an address override."
- **`cmd/opencircuit/main.go`** — `servePostgres` now wires the real `auth.SESMailer` (via `auth.NewSESMailer(ctx, cfg)`) by default instead of always falling back to `NoOpMailer`. Construction errors are fatal at startup rather than silently swallowed. A new `MAILER_NOOP` config flag (default `false`) keeps `NoOpMailer` reachable: `#0008`'s manual passkey-verification procedure depends on running the *Postgres* path locally and reading the magic link `NoOpMailer` logs to stdout, and SES isn't configured yet (`CLAUDE.md` §10 item 2) — with `MAILER_NOOP` unset, that procedure would now fail outright at every local run since there's no verified SES identity to send through. `MAILER_NOOP=true` in a local `.env` restores the old NoOp behavior; production leaves it unset, so it always gets the real mailer. This is new config surface beyond the issue's stated acceptance criteria, called out here since it wasn't explicitly requested — but the debt-cleanup note this pass was given ("keep NoOpMailer reachable for dev... do not break that [manual verification]") had no other clean way to be satisfied once the Postgres path defaults to a real mailer that cannot yet actually send.
- **`internal/config`** — added `MailerNoOp bool` / `MAILER_NOOP`, documented in `docs/configuration.md` and `.env.example`. No SMTP credential fields exist or were reintroduced — `#0007` already removed them and `TestLoad_RemovedVariablesIgnored` still guards that.

## Gotchas

- **`MAILER_NOOP` is new config surface not in the issue's acceptance criteria.** It exists solely to keep `#0008`'s manual local passkey-verification procedure working now that the Postgres path defaults to a mailer that cannot yet actually send (SES isn't configured — no verified domain, no production access; `CLAUDE.md` §10 item 2). Flagging for reviewer judgment: an alternative would have been to leave `NoOpMailer` wired until SES is actually set up and let a later issue flip the switch, but that would have left the "wire it properly" half of this task's instructions unaddressed.
- **What cannot be verified until SES is actually configured**, per `CLAUDE.md` §10 item 2 (domain verification, DKIM, custom MAIL FROM, DMARC, and production access are all "not started"): no real email has been sent by this code, and can't be from this environment. Specifically unverified: that a live SES v2 API call with the actual EC2 instance role succeeds; that the returned `MessageId` format matches what `#0038`'s bounce/complaint ingestion expects to join against; that `types.TooManyRequestsException` is in fact the error SES returns under real throttling (confirmed only from SDK documentation, not observed); that a real multipart/alternative send renders correctly in an inbox: and that the configuration set actually publishes events to SNS once one exists. All of this is proven only against a fake `sesAPI` in this pass.
- `types.Message.Headers []types.MessageHeader` (added to the SES v2 SDK's Simple email content) is what makes custom `List-Unsubscribe` headers possible without hand-rolling raw MIME — confirmed via `go doc`, not from memory, since this is exactly the kind of AWS API detail worth checking rather than assuming.

## Review notes

Reviewed 2026-08-19. Approved. Recorded here because this is the sending
primitive #0028/#0035/#0038/#0043/#0045 all build on, so its shape and its
config surface outlive this issue.

### `MAILER_NOOP` — necessary, but a footgun in its current ungated form

**Necessary: yes.** The two cheaper alternatives were checked and neither
works. Dev mode cannot serve the need — #0008's manual procedure explicitly
requires the *Postgres* path because `STORAGE=json` bypasses the WebAuthn
ceremony entirely via `devstore.DevRegistrar`/`DevRecoverer` and
`middleware.DevAutoLogin`, so the very thing being verified is what dev mode
skips. And an implicit "no SES configuration → `NoOpMailer`" selection is
unavailable *and* undesirable: `#0007` already makes `AWS_REGION` and
`EMAIL_FROM` required in **all** modes (`skipInDev: false`), so only the
optional `SES_CONFIGURATION_SET` could carry an implicit signal — and a silent
fallback is exactly the anti-pattern `config.go`'s own `Storage` comment
rejects ("An empty `DATABASE_URL` does NOT engage dev mode, so production can't
accidentally fall back"). An explicit, default-`false` flag is the right *kind*
of mechanism. Config tests cover it properly (`TestLoad_AllRequiredPresent`,
the default-`false` assertion in `TestLoad_DefaultsApplied`, and
`TestLoad_InvalidMailerNoOpBoolean`).

**Footgun: yes, as committed.** Measured against this repo's own precedent for
a development-only switch (`STORAGE=json`), `MAILER_NOOP` has one of the three
guards and is missing the two loud ones:

| Guard | `STORAGE=json` | `MAILER_NOOP` |
|---|---|---|
| Explicit opt-in only; no implicit/default engagement | yes (`DevMode()` requires the literal `"json"`) | yes (default `false`) |
| Loud one-time startup warning when engaged | yes — `slog.Warn("DEV MODE: … NEVER run this in production")` | **none** |
| Hard refusal when reached on the wrong path | yes — `DevAutoLogin` **panics** if `devMode` is false | **none** |

`MAILER_NOOP` cannot gate on `DevMode()` — its whole purpose is the Postgres
path — so the equivalent guard is the host. #0008's procedure sets
`BASE_URL='http://localhost:8080'`, so gating on it costs nothing and closes
the hazard by construction. Left ungated, `MAILER_NOOP=true` in a systemd
`EnvironmentFile` routes every email to stdout while the service looks
perfectly healthy: registration and recovery return success, #0026's uniform
`202` (CLAUDE.md §9) makes a broken double opt-in indistinguishable from a
working one, and no error is ever emitted. That is the "set once for debugging,
never unset" shape.

**Binding criterion carried forward — `#0026`.** Before that issue is
resolved, `MAILER_NOOP=true` must be **refused at startup** unless `BASE_URL`'s
host is `localhost` or `127.0.0.1`, and must emit a one-time `slog.Warn` when
it is honored — with a config or `main` test asserting both. `#0026` is the
right home because it is the issue whose deliberate uniform `202` is what makes
a no-op'd mailer invisible, it is the next `#0027`-dependent issue in this
phase, and it touches this exact `servePostgres` mailer wiring. (This reviewer
was scoped to commit `issues/0027.md` alone, so the criterion is recorded here
rather than edited into `#0026` directly.)

### The replacement test seam differs in kind, not just in name

`#0007`'s hazard note asked for two things: delete the SMTP-shaped
`NewSESMailerWithAddr`, and rework the PII-leak guard "some other way" — while
warning that "a fake `auth.Mailer` would have made the PII-leak guard synthetic
and therefore worthless." `NewSESMailerWithSender(sender mailing.Mailer, cfg)`
satisfies both. The fake is injected **below** `auth.SESMailer.send`, not in
place of it, so the exact line the regression protects —
`fmt.Errorf("auth: sending email: %w", err)`, with `toEmail` deliberately
absent — is still production code executing under test. That is the opposite of
the synthetic case #0007 warned about, and mutation 3 in `## Verification`
(reintroducing the leak) is the proof that the guard still fires. The seam is
also no longer transport-shaped: it takes the package's own dependency
interface at the boundary `SESMailer` already depends on, which is ordinary
constructor injection rather than a test-only backdoor — `NewSESMailer` is now
just `NewSESMailerWithSender` plus AWS client construction. Verdict: genuinely
better, not the same trap relocated.

### `internal/mailing`'s shape survives #0035, #0043 and #0045 unchanged

Checked against each downstream issue's acceptance criteria. The `Mailer`
interface needs no reshaping:

- **#0035** — `Message.Headers []Header` maps to `types.MessageHeader` and is
  per-`Message`, so per-recipient `List-Unsubscribe`/`-Post`/`List-Id` work
  directly; "campaign mail only" holds because the auth path sets no headers.
- **#0043** — `HTMLBody` + `TextBody` both set produces SES-built
  `multipart/alternative`; the footer's reply-to address is already carried via
  `ReplyToAddresses` from `EMAIL_REPLY_TO`.
- **#0045** — `Send` returns the real `MessageId` for the `ses_message_id`
  column, and `TooManyRequestsException` retry/backoff is in place. The worker's
  own `max_send_rate` throttle and 3-attempt failure counting are worker-level
  concerns (PRD §6.6 puts `worker.go` in this package) and need nothing from the
  interface; errors are wrapped with `%w`, so the worker can classify with
  `errors.As` if it wants to.

One **additive** gap to expect, not a break: `Message` has no per-message
`From`, while PRD §9 lists `default_from_name` as a runtime-editable `settings`
value the campaign sender will want to override. Adding a `From string` field
that falls back to `SESMailer.from` is a struct addition, not an interface
change, and breaks no existing caller.

### Failure behaviour

Both halves verified. **Construction:** `mailing.NewSESMailer` returns a
named-variable error when `AWS_REGION`/`SES_CONFIGURATION_SET`/`EMAIL_FROM` is
empty (`TestNewSESMailer_FailsClearlyOnMissingConfig`, 4 subtests);
`auth.NewSESMailer` wraps and propagates it
(`TestNewSESMailer_PropagatesConstructionError`); `servePostgres` returns it,
and `main` `log.Fatalf`s — the process does not start. **Send-time:**
`Send` returns an error on every non-throttling failure, on exhausted
throttling retries, on a cancelled context mid-backoff, and — importantly — on
an accepted send that carries no `MessageId`
(`TestSESMailer_Send_NoMessageIDIsAnError`), so a placeholder can never
silently reach #0038's join key. `auth.SESMailer.send` propagates it to the
handlers' 500 branches. Nothing in this path swallows.

### Scope and dependencies

`go.mod` gained exactly the three direct requires named in the acceptance
criteria (`aws-sdk-go-v2`, `.../config`, `.../service/sesv2`); everything else
AWS is `// indirect`. `go mod tidy` re-run by the reviewer produced **no diff**.
No access-key variable was added and nothing reads one — the only `SES_SMTP_*`
occurrences left in the tree are `TestLoad_RemovedVariablesIgnored`'s
regression guard and `docs/configuration.md`'s "removed" section, which is
correct. `internal/mailing`'s tests construct `SESMailer` directly with a fake
`sesAPI` and never reach `awsconfig.LoadDefaultConfig`, so no test can dial AWS.
