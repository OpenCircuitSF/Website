## Description

Four items from `#0126`'s re-review. None blocked that issue — it resolved — and
none is a behavioural defect today. They are grouped because they all sit in the
same two files and are cheap to close together.

**1. `#0126`'s erasure test does not exercise the normalisation its fix depends
on.** The fix widened the redaction predicate to
`WHERE subscriber_id = $1 OR email = lower(trim($3))`, and the reviewer
established the fix is *correct* — every write site stores the Postgres-normalised
`RETURNING` value, no `UPDATE` touches the column, so `lower(trim(…))` is
idempotent over it. But the shipped test uses `uniqueEmail()`, which is already
lower-cased and unpadded, **so it never exercises the normalisation at all**. The
reviewer's own mixed-case, whitespace-padded probe is the test that should exist.

That matters because the predicate's correctness rests entirely on a property of
the write path. If a future write site stores caller input verbatim, the
predicate silently stops matching — and the current test would not notice.

**2. `releaseAll(ctx)` never uses its `ctx`.** It builds its own bounded context
by design. A dead parameter that `go vet` will not flag, and a reader may pass a
cancelled context expecting it to matter.

**3. `claimedMu`'s comment understates it.** It calls itself *"belt-and-braces
rather than load-bearing"* — but `Stop` promises it is safe to call more than
once, and two concurrent `Stop`s both reach `releaseAll`. **The mutex is what
makes that promise true.** The code is right and the comment is modest, which is
the direction that gets a guard deleted as redundant — the same class as
`#0263`'s `FOR UPDATE`.

**4. Pre-existing: rows marked `'sending'` by a `ClaimDue` that then errors are
never tracked**, so `releaseAll` misses them. The orphan sweep covers them after
its interval, so nothing is lost. Unchanged by `#0126` and not introduced by it —
recorded so it is not rediscovered as new.

**Items 2–4**, all in `internal/mailing/outbox_worker.go`:

- **Item 2.** `releaseAll` took `ctx context.Context` and never read it —
  every `store.Release` call already builds its own bounded context,
  independent of the caller's. Dropped the parameter; updated the one call
  site in `Stop`; documented why in `releaseAll`'s doc comment rather than
  leaving the drop unexplained.
- **Item 3.** Rewrote `claimedMu`'s doc comment (previously: "belt-and-braces
  rather than load-bearing"). It understated the mutex: `Stop` enforces no
  first-caller-wins ordering beyond making `close(w.stopCh)` idempotent via
  `stopOnce` — two goroutines calling `Stop` concurrently both block on the
  same `<-w.doneCh` and, once it closes (a `close()` broadcasts to every
  waiting receiver), both proceed into `releaseAll` at the same instant.
  Without the mutex that is a genuine data race on `w.claimed` — proved,
  not asserted (see `## Verification`). The mutex is exactly what makes
  `Stop`'s "safe to call more than once" promise hold under concurrent
  calls, the same undersold-guard shape as `#0263`'s `FOR UPDATE`. Updated
  `Stop`'s and `releaseAll`'s own doc comments to point at `claimedMu`'s
  for this rather than duplicating it three times.
- **Item 4.** Did not attempt a structural fix — `ClaimDue`
  (`internal/outbox/store.go`) is a single `UPDATE ... RETURNING` that
  commits server-side before the Go code scans a single result row; if
  scanning then fails, the rows are genuinely `'sending'` in the database
  but `w.trackClaimed` is never called for them, because `ClaimDue` returns
  `(nil, err)`. A real fix means wrapping the UPDATE and the scan in one
  explicit transaction `ClaimDue` can still roll back — a change to
  `internal/outbox`'s shared claim path, out of this tidying issue's scope,
  and risky to make without its own dedicated review. Documented the gap in
  `pass`, right at the `ClaimDue` call, naming the mechanism and the orphan
  sweep as the existing safety net — matching the issue's own framing
  ("sweep-covered, nothing is lost").

**Two observations, recorded not as defects but so they are not rediscovered
as new.** Neither blocks resolution.

1. The `lower(trim(…))` wrapper in the predicate is a **no-op today and the
   new test cannot detect its removal**. `$3` is read from `subscribers.email`
   at `erase.go:137`, which is itself stored `lower(trim(…))` at INSERT, so
   changing the predicate to a bare `email = $3` leaves both erasure tests
   passing (verified). The wrapper is deliberately defensive — `erase.go`'s own
   comment at lines 289–292 says so — and the *reachable* risk it guards, a
   write site that stops normalising, **is** covered, as proved above. Worth
   knowing that the test's name promises slightly more than any single mutation
   of the predicate can demonstrate.
2. Under that write-path mutation the new test fails at its **setup invariant**
   (`"…want >= 4 (nullSubID >= 3) — test setup invalid"`) rather than at the
   leak hunt. It fails loudly, which is what matters, but the message points a
   future reader at the test rather than at the code. A one-line note in the
   test would save someone "fixing" the fixture.

"Nothing is lost" in item 4's comment is true of the row's *status* — the sweep
always returns it to `queued` — but a claim that fails at the scan has already
incremented `attempts`, so the row's retry budget is spent without a send
attempt. Same as a hard crash mid-batch, which the comment does name, so this
is a nuance rather than an inaccuracy.
