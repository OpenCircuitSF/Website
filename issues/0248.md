## Description

`docs/deployment.md`'s **`### What the drill found`** subsection records outcomes
from a drill run that predates `#0239`'s rewrite. `git blame` puts it at
`918eceab`, before `19963dc`. Two of its bullets now assert results the drill
**structurally cannot** produce:

- **Row counts** — claims "every table (… `workshops`, `workshop_interests`, …)
  matched source-to-restored exactly." Those two tables do not exist on the
  source at all: step 1b rolls back migration 20, which drops them. Step 7
  excludes them "entirely" for exactly that reason. **The section asserts a
  match for precisely the tables the drill says cannot be compared.**
- **`schema_migrations`** — claims `version=20, dirty=false` before and after.
  The drill prints `19|f` at step 1b and again at step 5, and step 7 now names
  this table as *expected to differ*.

Neither is a wording slip. They are recorded findings, in the voice of "we ran
this and here is what it showed", contradicting the procedure printed directly
above them.

**This is the same manufactured-confidence shape `#0239` exists to close, one
section lower.** `#0239` fixed a drill that passed while testing nothing; this
section reports results from a drill that no longer exists. A reader who trusts
it skips the run.

The reviewer that found it deliberately did not bounce `#0239` for it: the text
sits outside the drill's numbered steps and predates the rewrite, so it is
neither pass's regression. It is still wrong.

**The two flagged bullets were both confirmed wrong, exactly as the issue
describes**, and rewritten with real figures:

- **Row counts.** `workshops`/`workshop_interests` are not merely excluded
  from step 7's comparison, they don't exist on the source at all — step
  1b's rollback confirmed. Rewrote the bullet to list only the eleven
  tables step 2 actually seeds, with the real per-table counts from the
  `0248` run (identical source vs. restored, identical across both
  formats).
- **`schema_migrations`.** The source stayed `19|f` the entire run (checked
  at step 1, step 1b, and again at step 3); the restored copy read `19|f`
  right after restore (step 5) and `20|f` only after step 6 applied the
  pending migration. Rewrote the bullet to describe this two-value,
  before/after-step-6 shape instead of a single `20|f` claimed both
  before and after.

**A third bullet in the same section had the identical defect and was not
named in the issue** — satisfying acceptance criterion 4 ("a third is
plausible"): **"Constraint and index presence"** claimed per-table counts
from both `information_schema.table_constraints` and `pg_indexes` "matched
exactly." Index counts do; constraint counts do not, by design — step 7's
own text two paragraphs above this bullet says `email_campaigns`' count
must differ by exactly one (the FK migration 20 re-attaches), and names a
match on it as a sign step 6 silently no-op'd. Confirmed the actual delta
in both formats (`email_campaigns|12` → `email_campaigns|13`, no other
table affected) and split the bullet in two: **Index presence** (still a
clean match) and **Constraint presence** (the expected one-table, one-row
delta). Left the "Roles and ownership," "Order and dependencies,"
"Extensions," the two script-bug bullets, and the idempotency-behavior
bullets untouched — none of them assert an outcome the current drill
structurally cannot produce, and the ownership section already carries its
own separately-dated re-verification history (`#0228`, `#0235`).

Also checked the "both formats ... identical results" paragraph
immediately above the heading, since it makes the same kind of "we ran
this" claim as the two flagged bullets and predates `#0239`'s rewrite by
the same `git blame` evidence. Unlike the three bullets above, this one
turned out to still be true — re-verified directly by actually running
both formats through the current drill for this issue (see
`## Verification`) — so it was kept, with a note that it was reconfirmed
for `#0248` rather than left as an unverified holdover.

**Two smaller items:**

1. **`set -e` decision: did not add it.** Two steps in this block
   legitimately return non-zero on a passing run, and `set -e` would abort
   the drill on both:
   - Step 7's constraint-count `diff` is *supposed* to print one differing
     line (`email_campaigns`) — `diff(1)` exits 1 whenever it finds a
     difference, which here is the pass condition, not a failure.
   - Step 9's `scripts/testdb.sh drop "${ISSUE}dst"` fails with `ERROR:
     must be owner of database` on every local run under
     `BACKUP_RUN_AS=""` — confirmed twice (once per format, both runs hit
     it identically) — because `RESTORE_CREATE=1`'s `createdb` in
     `restore.sh` runs as the connecting OS user when `BACKUP_RUN_AS` is
     empty (its `runner` array is empty, so no `sudo -u` wraps the call),
     not as `opencircuit`, while `testdb.sh drop` always connects as
     `opencircuit` and therefore doesn't own what it's trying to drop.
     This isn't an edge case this drill sometimes hits — it is the
     deterministic outcome of following the documented local-dev path
     (`BACKUP_RUN_AS=""`) on a machine with no `postgres` OS role, which
     is exactly this development machine and, per `docs/deployment.md`'s
     own "Must be re-verified on the server" note, exactly what everyone
     testing this drill locally is doing. Documented plainly instead: a
     new paragraph right after the code block states exit status is not
     the pass signal, names both non-zero cases, and says what real
     completion evidence looks like instead (step 6's actual migration
     apply, step 7's four comparisons matching what's documented, step
     8/8b's inserts/rejections, step 9 either succeeding or being finished
     by hand as the actual owner).
2. **Step 7 SQL committed, not left as prose.** Added three runnable
   `diff <(...) <(...)` commands — row counts (eleven tables, named
   explicitly, matching step 2's seed list), sequence `last_value`s
   (`pg_sequences`, excluding `workshops_id_seq`), and index counts
   (`pg_indexes`, same table exclusion as the existing constraint diff) —
   right after the existing constraint-count diff, each with an "expect
   zero output" note. A follower no longer has to translate the old prose
   ("row counts, sequence last_values, and index counts get the same
   table-exclusion treatment...") into their own SQL under pressure.
