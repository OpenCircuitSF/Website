# 0340 — A deferred `import_invite` outbox row can outlive the `confirm_token` it carries

## Description

`deferMissingPhysicalAddress` requeues an outbound row indefinitely while no
physical postal address is configured — correct behaviour, and `#0045`'s
refusal is a restricted rule that must not be made bypassable (§9).

But an `import_invite` row's payload holds a `confirm_token`, and that token can
be rotated underneath it by a resend or by an expiry sweep. Nothing ties the
queued row's lifetime to the validity of the token it carries. A row deferred
long enough can therefore be delivered with a token that no longer resolves,
producing an invitation whose link is dead on arrival — and the recipient has no
way to tell that from an expired one.

`#0313`'s planned `CancelQueuedTx` covers the single case that change
introduces. **The general hazard is pre-existing and unguarded**, and it widens
as soon as any further path rotates a token.

The exposure is real rather than theoretical right now: SES production access is
still pending (§10 item 2), and `#0045` refuses to start a campaign without a
physical address, which is item 3 and not started. Both make long defers the
expected state rather than an edge case.

## Acceptance criteria

1. A queued or deferred outbound row carrying a `confirm_token` cannot be
   delivered after that token has been rotated or invalidated — either the row
   is cancelled when the token changes, or the token is resolved at send time
   rather than captured at enqueue time.
2. The chosen mechanism is stated, with its trade-off: cancel-on-rotate versus
   resolve-at-send.
3. `deferMissingPhysicalAddress`'s indefinite requeue is preserved — `#0045`'s
   refusal is a restricted rule (§9) and must not become bypassable.
4. Covered for every token-bearing kind, not only `import_invite` — enumerate
   the kinds and say which carry tokens.
5. Proved by mutation: a test that rotates a token while a row is deferred and
   asserts the row cannot be delivered with the stale token. The mutation must
   fail against the un-fixed code.
6. Interacts with `#0313`'s `CancelQueuedTx` — if that lands first, this must
   generalise it rather than duplicate it. Say which.

That is the single most important input to this plan: **the structural home for

### 2. The token-bearing kinds — criterion 4, read from the code

Enumerated from the `Kind` constants in `internal/outbox/store.go` and the
payload structs and `render` switch in `internal/mailing/outbox_worker.go`.
**Correction to the issue's framing:** it is not only `import_invite`, and it is
also not "every kind with a token" — three separate token *populations* are
involved and only one of them is rotatable.

| Kind | Payload token fields | Token lives in | Rotatable under a queued row? |
|---|---|---|---|
| `KindConfirmation` | `confirm_token`, `manage_token` | `subscribers` | **Yes — `confirm_token`** |
| `KindImportInvite` | `confirm_token`, `manage_token` | `subscribers` | **Yes — `confirm_token`** |
| `KindAlreadySubscribed` | `manage_token` | `subscribers` | No — see below |
| `KindWelcome` | `manage_token` | `subscribers` | No — see below |
| `KindRegistration` | `token` | `pending_registrations` | No — see below |
| `KindRecovery` | `token` | `pending_registrations` | No — see below |
| `KindSessionsRevoked` | none (`at` only) | — | n/a |
| `KindAdminAlert` | none (`subject`, `lines`) | — | n/a |
| `KindGoodbye` | no producer, no payload struct, no `render` case | — | n/a |
| `KindSubscribeIntake` | not email; never reaches `render` | — | n/a |

The three "No" arguments, each of which must be written into the code as a
reason rather than left as an omission (the `ungatedKinds` / `kindExceptions`
convention, `#0296` item 4 — an allowlist anyone can append to without an
argument is a guard with a hole):

- **`manage_token` (`already_subscribed`, `welcome`, and the second token on the
  two above).** The only mutator is `subscribers.Store.RotateManageToken`, and
  its only production caller is `#0034`'s one-click unsubscribe handler, which
  calls it *after a real, non-no-op unsubscribe*. So any row carrying a stale
  `manage_token` necessarily belongs to a subscriber whose status is now
  `unsubscribed` — and `already_subscribed` and `welcome` are gated by
  `gatedKinds` to `StatusActive`, `confirmation` and `import_invite` to
  `StatusPending`. `#0365`'s status gate therefore already withholds every one
  of them. This is a derived property, not a coincidence, and the reason must
  say so, because it stops being true the moment a second `RotateManageToken`
  caller appears that does not also change status.
- **`registration` / `recovery`.** `pending_registrations` is INSERT / SELECT /
  DELETE-by-its-own-token in `internal/auth/store.go`; there is no `UPDATE` that
  rotates a token out from under a queued row. A second ceremony inserts a
  *second* row and leaves the first token valid to its own TTL. These kinds also
  never take the indefinite defer (`render` refuses only `welcome` and
  `import_invite` for a blank `physical_address`), and `Row.SubscriberID` is
  always nil for them, so there is nothing for a subscriber-keyed check to read.
- **`sessions_revoked` / `admin_alert` / `goodbye`.** No token in the payload at
  all; `goodbye` has no producer and no renderer.

So the enforced surface is exactly **`confirm_token`, on `KindConfirmation` and
`KindImportInvite`** — and the guard in §7 is what keeps that list honest as
kinds are added.

### 3. Where `confirm_token` actually moves, and why `#0365` does not subsume it

Every write to `subscribers.confirm_token` in the tree, with what it does to
`status` in the same statement:

| Site | Token | Status after | Leaves a stale queued row? |
|---|---|---|---|
| `Store.Create` | minted | `pending` | No — the row is INSERTed and enqueued in one tx; nothing older exists |
| `Store.ClaimAndEnqueueConfirmation` | **reused if still live**, minted only when NULL/expired (`#0314`) | `pending` (unchanged) | Yes, on the mint branch |
| `Store.Confirm` | set NULL | `active` | Row exists, but the status gate already skips it |
| `Store.Unsubscribe` | cleared | `unsubscribed` | Status gate already skips it |
| `Store.RestartSignup` | **minted** | `unsubscribed`/`bounced` → **`pending`** | **Yes — and it re-opens the status gate** |
| `Store.AdminResendConfirmation` | **minted**, new row enqueued | `pending` (unchanged) | **Yes** |
| `Store.AdminResendInvitation` | **minted**, new row enqueued | `pending` (unchanged) | **Yes** |
| `Store.ExpirePendingSweep` | **set NULL** | `pending` (deliberately unchanged) | **Yes** |

Four sites leave a deliverable stale row, and the `#0365` status gate catches
none of them, because three of them do not touch `status` at all and the fourth
(`RestartSignup`) moves it *back* to the value the gate wants. `RestartSignup`
is the sharpest of the four: a row that the status gate would have skipped a
moment earlier becomes sendable again, still carrying the pre-restart token.

**`ExpirePendingSweep` is the case the Description names as "an expiry sweep",
and it is worse than a rotation:** it sets the token to NULL and leaves the row
`pending` on purpose (`#0128`'s "the row left pending rather than deleted"), so
a deferred invitation delivered afterwards carries a link that resolves to
nothing at all.

### 4. The decision — criterion 2

**Recommendation: a send-time token-validity check inside
`OutboxWorker.sendGate`, as the single load-bearing mechanism. Do not add
cancel-on-rotate call sites.**

This is the *validate*-at-send member of the resolve-at-send family: the payload
keeps carrying the token it was enqueued with, and the worker compares it
against the live `subscribers.confirm_token` immediately before sending,
skipping the row when they differ. It satisfies criterion 1's property ("cannot
be delivered after that token has been rotated or invalidated") without either
of the two costs below.

**Why not pure resolve-at-send** (drop the token from the payload; read the live
one at send time and mail *that*):

- It converts every rotation into a **duplicate send**. `AdminResendConfirmation`
  and `AdminResendInvitation` each mint a new token *and enqueue a new row* in
  the same transaction. Resolve-at-send would make the stale row and the fresh
  row resolve to the identical live token, so the person receives two identical
  invitations — the exact class of defect `#0254` cost a session to remove.
- It **cannot be made to work for `ExpirePendingSweep`** anyway: there is no
  live token to resolve, so that path degenerates back into a skip decision. A
  mechanism that needs a second mechanism for its most likely trigger is not one
  mechanism.
- It **changes the payload contract** for two kinds and silently changes what
  `MarkSent`'s payload-blanking means (the package doc comment's "payload is
  template inputs" invariant and its "a 'sent' row archives a live secret … for
  as long as the row exists" reasoning both key off the token being *in* the
  payload).
- It converts a stale link into a **live** link, which is the wrong direction on
  a security-relevant object: an invitation that was superseded because the
  previous link may have leaked (`AdminResendConfirmation`'s own doc comment
  says exactly that) would be re-armed with the current secret.

**Why not cancel-on-rotate as the load-bearing mechanism** (call `CancelQueuedTx`
at each of the four sites in §3):

- It is **per-site and therefore forgettable**, which is precisely the fragility
  criterion 4 warns about ("it widens as soon as any further path rotates a
  token"). The send-time check is one place and covers rotation paths that do
  not exist yet.
- `CancelQueuedTx` matches `status = 'queued'` **only**, by deliberate design —
  its doc comment refuses to race a worker for a `'sending'` row. So it cannot
  close the window at all for a row that is mid-claim.
- It is **redundant given the gate, and the redundancy is not free**: four new
  call sites, each with an ordering trap (a same-kind `CancelQueuedTx` must run
  *before* the sibling `EnqueueTx` or it cancels the row it just created), plus
  two statements per swept row inside `ExpirePendingSweep`'s hot batch loop.

**The property that makes the gate sufficient, and that decided this:**
`sendOne` calls `sendGate` *before* `render`. So a stale row is skipped on its
very next worker pass — **before** the `physical_address` defer is reached. A
long-deferred row with a rotated token therefore terminates promptly as
`skipped` rather than looping forever, and the queue cleans itself without any
write-path change. Cancel-on-rotate would buy only immediacy, on rows that are
by construction not going anywhere.

**Residual, stated rather than argued away:** a row already in `'sending'` when
the rotation commits has already passed the gate and will be sent with a token
that was live microseconds earlier. This is the same unclosable microsecond race
`sendGate`'s own doc comment already records for a complaint landing after
`Send` returns, and it is not what this issue is about — the issue is *queue
latency*, seconds to indefinite, and that is what the gate closes.

### 5. Criterion 6 — this generalises `#0313`, it does not duplicate it

`#0313`'s `CancelQueuedTx` stays exactly as it is, with its one call site
unchanged. The relationship is layered, not overlapping:

- `CancelQueuedTx` is a **write-path** cancellation for one specific supersession
  (self-initiated signup supersedes a pending invitation). It is the tidy,
  immediate answer for the case its author could see, and it also carries a
  second payload the gate does not: it clears the row's payload at the moment of
  supersession, shortening the token's residency in `outbound_queue`.
- The send-time token check is the **general backstop**: it covers that same
  case *and* the four in §3 *and* any future one, and it is the only one of the
  two that can act on a row nobody remembered to cancel.

So: **generalises.** The plan adds no second cancellation mechanism, and the
implementer must not "unify" them by deleting the `CancelQueuedTx` call — it is
still the correct thing to do at a site that already knows it is superseding a
message.

### 6. Criterion 3 — the `physical_address` refusal survives intact, and cannot be weakened by this

`deferMissingPhysicalAddress` and its `welcomeAddressDeferMaxRetries`
(`math.MaxInt32`) are **not touched**. The gate is upstream of `render`, and the
gate's only two outcomes are *send unchanged* and *withhold*. There is no branch
in this design that causes a message to be sent which would not have been sent
before, so `#0045`'s refusal (CLAUDE.md §9, CAN-SPAM §7704) cannot be made
bypassable by it — the change can only ever reduce what goes out.

Two pins for this, in §8: the existing
`TestOutboxWorker_DefersImportInvite_MissingPhysicalAddress` and
`TestAdminResendInvitation_PhysicalAddressGateNotBypassable` must both stay
green unmodified, plus one new test asserting that a row with a **valid** token
and a blank `physical_address` still lands back in `'queued'` with `attempts`
climbing — never `'skipped'`, never sent.

### 7. Implementation steps

**Step 1 — `internal/subscribers/send_eligibility.go`.** Add
`ConfirmToken *string` to `SendEligibility` (nil when the column is NULL) and
add `s.confirm_token` to the existing `SELECT`. One extra column on a query that
already runs; no extra round trip. Document that nil means "no live confirm
token", which is a *positive* fact (swept or consumed), not a read failure.

**Step 2 — `internal/mailing/outbox_worker.go`, the kind partition.** Add,
beside `gatedKinds` / `ungatedKinds` and modelled on them exactly:

- `tokenGatedKinds` — the set whose payload `confirm_token` is re-validated:
  `KindConfirmation`, `KindImportInvite`.
- `tokenUngatedKinds` — every other `mailKinds` member mapped to a **non-empty
  written reason**, the three arguments in §2 spelled out per kind.

**Step 3 — `sendGate`.** After the existing `switch` cases (so every current
reason string and every existing test is untouched), add the token predicate,
reached only for a kind in `tokenGatedKinds`:

- unmarshal `row.Payload` into a minimal anonymous struct carrying one field,
  `ConfirmToken string`, tagged with the JSON name `confirm_token` — the same
  field name both `confirmationPayload` and `importInvitePayload` already use,
  which is why one extractor serves both kinds. A JSON error is returned to the
  caller —
  **fail closed**, into `finishFailed`'s ordinary backoff, matching `sendGate`'s
  own documented "must not fail open on an unknown state".
- payload token empty on a token-gated kind → **skip**. Every producer sets it,
  so this is unreachable by construction; but unlike the `row.SubscriberID ==
  nil` branch, failing *open* here would mail a link with an empty token, which
  is the exact harm — so this defensive branch skips rather than sends.
- `elig.ConfirmToken == nil` → skip, reason `"confirm token has been cleared
  since enqueue"`.
- `*elig.ConfirmToken != payloadToken` → skip, reason `"confirm token was
  rotated since enqueue"`.

**The reason strings must not contain either token value.** They land in
`outbound_queue.error`, which admins read and which gets pasted into issue files
— CLAUDE.md §8b and `#0277`'s live-magic-link leak; `finishSkipped`'s Warn
already omits the recipient for the same reason.

Nothing else changes. `MarkSkipped`, `finishSkipped`, `StatusSkipped`, and the
`skipped` badge in `web/src/lib/pending.ts` are all reused as-is, so there is no
new terminal state and no SPA change.

**Step 4 — deliberately not done, and recorded as such in a comment**: no new
`CancelQueuedTx` call sites (§4), no change to `deferMissingPhysicalAddress`,
no change to `internal/outbox/store.go`.

### 8. Mutation proof — criterion 5

Four named mutations. Note the CLAUDE.md §8 test: does the mutation leave the
assertion falsifiable by the thing it measures? For M1–M3 the oracle is the
`RecordingMailer`'s captured messages and the `outbound_queue` row's own status,
neither of which is the code being mutated — so these are legitimate in-package
Go tests, not circular, and **no external `scripts/*_guard_test.sh` harness is
needed**. M4 mutates a map that the guard's own `got` is computed from, which is
the same in-Go-is-sound case `TestGatedKindsPartitionEveryMailKind` already
occupies.

**M1 — the expiry-sweep case, on a genuinely deferred row.** New test
`TestOutboxWorker_SkipsDeferredImportInviteWhoseConfirmTokenWasSwept`, modelled
on `TestOutboxWorker_DefersImportInvite_MissingPhysicalAddress` and
`TestOutboxWorker_SkipsImportInviteForDeclinedInvitee`:

1. `setSetting(t, pool, settingPhysicalAddress, "")`.
2. Create a pending subscriber via `subscribers.NewStore(pool).Create`; enqueue
   an `outbox.KindImportInvite` row with `SubscriberID` set and
   `confirm_token` = the subscriber's live token.
3. `runWorkerUntilStopped`; poll until `attempts >= 1 && status == 'queued'` —
   this is what proves the row is in the **deferred** state the issue is about,
   and it reuses the existing test's own comment about `'sending'` being a real
   intermediate state.
4. Rotate through a **real production path, never a raw `UPDATE`**: back-date
   `confirm_expires_at` and call `subStore.ExpirePendingSweep(ctx, now)`. The
   row stays `pending`; the token goes NULL.
5. Set `physical_address` to a real value, so the row is otherwise fully
   deliverable and the defer is no longer the reason anything is withheld.
6. Assert `waitForQueueStatus(...) == outbox.StatusSkipped`, that
   `outbound_queue.error` names the confirm token, and that
   `sentTo(mailer, sub.Email) == 0`.

*Against un-fixed code* the row is `'sent'` and `sentTo == 1`, carrying a link
that resolves to nothing — all three assertions fail. This is the mutation the
issue asks for: the fix removed, the stale row delivered.

**M2 — the admin-resend rotation case, and that fresh mail still flows.** New
test `TestOutboxWorker_SkipsConfirmationWhoseConfirmTokenWasRotated`:

1. `subStore.Create` — which enqueues an `outbox.KindConfirmation` row with the
   live token. Do **not** run the worker yet.
2. `subStore.AdminResendConfirmation(ctx, id, now, 0, ttl)` — mints a new token
   and enqueues a second row, both in one transaction. (Watch
   `ErrResendCooldownActive`: `Create` stamps `confirm_sent_at`, so pass
   `cooldown = 0`, or a `now` a moment later.)
3. Run the worker. Assert the **first** row → `StatusSkipped` with an error
   naming the confirm token; the **second** row → `StatusSent`; and exactly
   **one** confirmation message reached that address.

*Against un-fixed code* both rows send and the address gets two confirmations —
the second assertion and the message count both fail. This test is doing double
duty: it proves the stale row is withheld *and* that the mechanism does not
withhold the legitimate replacement, which is the failure mode a careless
implementation of this would actually ship.

**M3 — criterion 3's pin.** New test
`TestOutboxWorker_TokenGateDoesNotShortCircuitPhysicalAddressDefer`: valid,
unrotated token plus blank `physical_address` → the row must settle back to
`'queued'` with `attempts >= 1` and nothing sent, exactly as today. Mutate the
token predicate to skip unconditionally and the row becomes `'skipped'`,
failing it. Plus: `TestOutboxWorker_DefersImportInvite_MissingPhysicalAddress`,
`TestOutboxWorker_DefersWelcome_MissingPhysicalAddress` and
`TestAdminResendInvitation_PhysicalAddressGateNotBypassable` must all pass
**unmodified** — if the implementer needs to edit any of them, that is a signal
the design drifted, not a test that needs updating.

**M4 — the criterion-4 coverage guard.** New test
`TestTokenGatedKindsPartitionEveryMailKind`, a direct sibling of the existing
`TestGatedKindsPartitionEveryMailKind`: every `mailKinds` element appears in
exactly one of `tokenGatedKinds` / `tokenUngatedKinds` (no overlap, no gap), and
every `tokenUngatedKinds` value is a non-empty reason. Mutation: delete
`outbox.KindImportInvite` from both maps — the test fails naming it. This is
what makes §2's enumeration a live artifact rather than prose that rots.
