# 0516 — Show the running version and commit in the admin console

## Description

`#0509` embeds the build commit into the binary via
`-ldflags -X main.commitHash=...`, and `#0514` publishes releases tagged with
plain semver. Together they answer "what is production running?" — but only
over SSH:

    $ /usr/local/bin/opencircuit --version
    opencircuit 0.1.0 (8b37cc925b73a6229ba1b5d6f238abcd8629befb)

An admin should be able to see that in the console without shell access.

## Why this matters more since the release-based deploy

Before `#0509`, the deployed code was traceable to an on-box git checkout —
`git -C /opt/opencircuit rev-parse HEAD` answered the question. That checkout
is no longer the source of truth: `#0514`'s bundle ships a binary and
`migrations/`, and the checkout is deliberately not kept current.

So the **binary itself is now the only on-box record of what is deployed**, and
the only way to read it is a shell. That is a real regression in observability,
accepted knowingly when option 2 was chosen (`#0509`'s decision section says
so). This issue is the compensating control.

The first release, `v0.1.0`, exposed the gap concretely: the previously
installed binary predated `commitHash` and printed only `opencircuit 0.1.0`,
so there was no way to tell which commit production was serving without
inferring it from the deploy history.

## Acceptance criteria

1. An authenticated admin can see the running **version** and **commit hash**
   in the admin console.
2. The values come from the same variables `--version` reads — not a second,
   independently-maintained constant that can drift. A duplicated version
   string is worse than none.
3. The commit hash is shown in a form that is useful: the full sha available
   (copyable), a short form displayed.
4. It degrades honestly. A binary built without `-ldflags` reports `unknown`
   (this is existing behaviour, and `#0509`'s review confirmed it is a loud
   placeholder rather than an empty string) — the console must show that
   plainly rather than a blank or a fabricated value.
5. **Do not widen `/health`.** `#0509` deliberately rejected that: `PRD` §8
   fixes its response shape and it answers liveness and DB connectivity, which
   is a different question, and it is unauthenticated. Use an admin-scoped
   surface.
6. Consider showing the **schema version** alongside it (`schema_migrations`),
   since "which code" and "which schema" are the two halves of the same
   question and a mismatch between them is exactly what a bad deploy looks
   like. **Either answer is acceptable; an unexamined one is not.**

## Notes

deploy, which is exactly when the absence is felt: the deploy succeeded, and
confirming *which* commit was live still meant an SSH session.

Worth keeping small. This is a read-only display of two strings the process
already holds.
