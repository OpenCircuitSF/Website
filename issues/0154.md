## Description

`#0148` added `TestPRDWorkshopAndMailingIndexParity` (`internal/db/prd_index_parity_test.go`), which replays every `CREATE`/`DROP INDEX` across `migrations/*.up.sql` and asserts `PRD.md` §6.2 names each one correctly. It works, and `#0148`'s review re-proved it bites in both branches (missing index, diverged definition). Two gaps in it are worth closing on their own clock.

**1. Unmatched statements are skipped in silence.** The extraction regex is

```
(?i)CREATE\s+INDEX\s+(\w+)\s+ON\s+(\w+)\s*(\([^;]*?\))(?:\s+WHERE\s+([^;]*?))?;
```

Probed directly (`#0148` review), it handles more than its own comment claims — functional indexes (`lower(email)`), doubled parens, `INCLUDE`, and multi-line statements all match, because Go's leftmost-first submatch semantics expand the non-greedy column-list capture past a nested close-paren. But four real SQL forms produce **no match at all**, and a no-match on the migrations side means the index simply never enters the live map and is never checked:

| Form | Result |
|---|---|
| `CREATE UNIQUE INDEX …` | silently skipped |
| `CREATE INDEX IF NOT EXISTS …` | silently skipped |
| `CREATE INDEX CONCURRENTLY …` | silently skipped |
| statement with no terminating `;` | silently skipped |

None of these exist in `migrations/` today, so the guard is correct right now. The failure mode is the one that makes a guard worse than no guard: the first `CREATE UNIQUE INDEX` anyone adds is invisible to it, and the suite stays green while the PRD falls behind — exactly the drift `#0148` was filed about.

A related, lesser fragility: the patterns run over raw file text including SQL comments, so a commented-out `-- CREATE INDEX …` in a migration would register as a live index. That direction at least fails loudly (as a false "PRD does not mention"), so it is the smaller problem.

**2. Column parity was deferred, and the deferral's stated reason is weaker than it looks.** `#0148` scoped the guard to indexes, arguing a column would require "replaying a `CREATE TABLE` plus every later `ALTER TABLE ADD COLUMN` across up to 20 files with no single-statement anchor — materially more parsing surface". `#0148`'s review prototyped exactly that during the sweep: ~30 lines, comparing both column names and their type/default text, across all 20 migrations. It reproduced the one real column drift (`email_sends.claimed_at`, live since `000018`, absent from §6.2 until `#0148` fixed it by hand) and produced no false positives on the Phase 8 forward declarations. The extraction is not materially harder than the index case; the honest reason to defer was cost, not difficulty.

## Root cause

Two independent gaps in `internal/db/prd_index_parity_test.go`, both consequences of the same design choice: the guard is a hand-written regex, not a real SQL parser, and nothing checked that the regex's coverage matched what was actually in the file.

1. `createIndexPattern`'s prefix was `CREATE\s+INDEX\s+` only. `CREATE UNIQUE INDEX`, `CREATE INDEX CONCURRENTLY`, and `CREATE INDEX IF NOT EXISTS` all have extra tokens between `CREATE` and the index name that the pattern didn't account for, so none of them matched at all. A non-match on the migrations side of `liveIndexesFromMigrations` simply meant the statement contributed nothing to the `live` map — no error, no skip notice, just absence. Same failure shape for a statement missing its terminating `;`, since the pattern's own closing anchor is the semicolon.
2. Column parity was never built. `#0148` scoped the original guard to indexes only, reasoning (in the code comment) that column extraction would need "replaying a `CREATE TABLE` plus every later `ALTER TABLE ADD COLUMN` … with no single-statement anchor". `#0148`'s own review prototyped exactly that in ~30 lines and found it wasn't materially harder than the index case — the stated reason was cost, not difficulty — and it reproduced `email_sends.claimed_at`'s known drift mechanically.

## Fix

**Gap 1 (silent parse failures).**
- Widened `createIndexPattern`'s prefix to `CREATE\s+(?:UNIQUE\s+)?INDEX\s+(?:CONCURRENTLY\s+)?(?:IF\s+NOT\s+EXISTS\s+)?`, matching Postgres's required clause order. Capture group numbering is unchanged (the three new clauses are non-capturing), so no caller needed updating.
- Added `looseIndexStartPattern` (`CREATE\s+(?:UNIQUE\s+)?INDEX\b`) and `checkIndexStatementCoverage`, which counts loose occurrences against `createIndexPattern`'s actual match count and `t.Errorf`s on a mismatch, naming the file (or `PRD.md §6.2`). This is what makes a *remaining* unparseable form (a missing `;`, or any future form the prefix doesn't yet handle) fail loudly instead of vanishing. Wired into `liveIndexesFromMigrations` (once per migration file) and into `TestPRDWorkshopAndMailingIndexParity` (once for the PRD section).
- Added `stripSQLComments` (`--[^\n]*` stripped) and applied it to both the migration file text and the extracted PRD section before any pattern runs, so a commented-out `-- CREATE INDEX …`/`-- CREATE TABLE …` can never register as live on either side, and so the loose/strict counts in `checkIndexStatementCoverage` are counting the same text.

**Gap 2 (column parity).**
- Added `columnsFromCreateTable`, which locates a `CREATE TABLE name (` body by depth-tracking to the matching close paren (handles nested parens from `REFERENCES t(id)` etc. — something a `createIndexPattern`-style non-greedy regex can't safely do for a column list), splits the body on top-level commas with `splitTopLevel`, and takes each segment's first token as the column name unless it's a table-constraint keyword (`PRIMARY`, `UNIQUE`, `CHECK`, `FOREIGN`, `CONSTRAINT`, `EXCLUDE`).
- Added `liveColumnsFromMigrations`, which replays `CREATE TABLE` and `ALTER TABLE … ADD COLUMN` across `migrations/*.up.sql` in migration-version order and by byte position within each file — the same ordering discipline `liveIndexesFromMigrations` already uses for `idx_email_events_soft_bounce`'s `DROP`+`CREATE` pair, preserved here even though every column change in this tree today is a monotonic addition, so a future `DROP COLUMN` or table recreation doesn't silently get the wrong answer.
- Added `prdColumnsFromSection`, the PRD-side counterpart using the same `columnsFromCreateTable`.
- Added `TestPRDWorkshopAndMailingColumnParity`: one direction only (migrations → PRD §6.2), scoped to `prdIndexParityTables` (the same table set the index guard already uses), asserting column *names* only — not types/defaults, per the acceptance criteria's "optional, ship only if false-positive-free" and to keep the assertion to one axis.

Did not change the guard's one-directional scope, per the issue's explicit instruction — no bidirectional check, no allowlist.

### Fix pass 2

Commit `67dcb47`, building on `689a5de` (kept, not reverted). Addresses every
item in the review's "What would clear the bounce" list.

1. **Column-side coverage check**, mirroring `checkIndexStatementCoverage`:
   `checkTableStatementCoverage` (loose `CREATE\s+TABLE\b` vs strict
   `createTableStart` matches) and `checkColumnAddCoverage` (loose
   `ALTER\s+TABLE\s+\w+\s+ADD\b`, requiring nothing at all after `ADD`, vs
   strict `columnAddPattern` matches, both classified through the new
   `classifyColumnAdd`/`isTableConstraintSegment` so a constraint-add is
   excluded identically on both sides). `checkColumnStatementCoverage` runs
   both and is wired into `liveColumnsFromMigrations` (once per migration
   file) and `TestPRDWorkshopAndMailingColumnParity` (once for the PRD
   section) — the same call-site pattern the index guard already uses.
   The loose ADD pattern deliberately requires nothing after `ADD` (not even
   an identifier), unlike an earlier draft that mirrored `columnAddPattern`'s
   own optional groups too closely and turned out to be structurally
   *unable* to disagree with the strict pattern — a coverage check that can
   never fire is exactly the kind of false confidence this issue is about
   removing. Reworked before committing; see "Verification pass 2" below for
   the malformed-ADD proof this produces.
2. **Widened `createTableStart`** to
   `CREATE\s+TABLE\s+(?:IF\s+NOT\s+EXISTS\s+)?(\w+)\s*\(` (parses `IF NOT
   EXISTS` correctly now, rather than merely failing loudly) and
   **`columnAddPattern`** to
   `ALTER\s+TABLE\s+(\w+)\s+ADD\s+(COLUMN\s+)?(?:IF\s+NOT\s+EXISTS\s+)?(\w+)(?:\s+(\w+))?`
   — the `COLUMN` group is now capturing (not non-capturing), so
   `classifyColumnAdd` can tell "the `COLUMN` keyword said so" apart from
   "no keyword present — check whether the token after `ADD` is actually a
   constraint (`CONSTRAINT`, `PRIMARY`, …), not a column name" without a
   second pattern. `ADD CONSTRAINT`/`ADD PRIMARY KEY` (five real instances
   across `000009`, `000010`, `000012`, `000013`, `000014`, `000017`,
   `000020`) are matched and then classified out, never silently dropped
   from the coverage count on one side only.
3. **`stripSQLComments`, `splitTopLevel`, and `columnsFromCreateTable`'s
   close-paren finder are each a single quote-aware pass now** — tracking
   whether the scan is inside a `'…'` string literal (with Postgres's
   doubled-quote escape, `'it''s'`) before treating `--`, `/* */`, `(`, `)`,
   or `,` as SQL structure. This retires five of the six review-proved
   attacks in one change, exactly as the review predicted: a `--` inside a
   literal no longer eats the following column's comma, a `/* … */` block
   comment inside a table body no longer invents a bogus column and drops
   the next real one, a block-commented-out column definition parses
   correctly, and an unbalanced `)` inside a `DEFAULT ')'` literal no longer
   closes the table body early.
4. **`EXCLUDE` fixed** — dropped from the blanket `tableConstraintKeywords`
   map (it is non-reserved in Postgres, so `exclude BOOLEAN` is a legal bare
   column name) and replaced with `isTableConstraintSegment`, which only
   treats `EXCLUDE` as a constraint when the following token is `USING` —
   its only valid constraint syntax.
5. **`prdPath` is now a package `var`**, not a `const` — not required by the
   review, but folded in as suggested, so a future proof of the
   column-deletion failure mode can point at a scratch copy instead of
   editing `PRD.md` in place.

The seventh review-proved item — a quoted table name (`CREATE TABLE "t" (`)
— was deliberately *not* added to `createTableStart`'s matched forms (the
review's fix list only asked for the `IF NOT EXISTS` widen); it is instead
caught by `checkTableStatementCoverage` and reclassified from
**wrong-and-silent** to **wrong-but-loud**, same as the review said a form
that "now merely fails loudly rather than parsing correctly" is acceptable
for.

- Scratch migration files (`999999_…`, `999998_…`, `999997_…`) break `TestDatabaseDocMigrationParity`'s contiguity/down-file checks if run through the whole `internal/db` package — each proof was run scoped to just the affected test (`-run 'TestPRDWorkshopAndMailing…'`) and the scratch file deleted before running anything broader, so the full-package and full-suite verification runs never saw them.
- `looseIndexStartPattern` intentionally does not try to parse `CONCURRENTLY`/`IF NOT EXISTS` — it only needs to count "a CREATE [UNIQUE] INDEX statement started here", and letting the strict pattern be the one that determines whether it actually completed is what makes the coverage check meaningful (a widened strict pattern narrows the gap; the loose count is the fixed ceiling).

### The attacks — `columnsFromCreateTable` and the coverage check

Classified as the brief asks: **right**, **wrong-but-loud** (a bogus or drifted
column that produces a test failure), or **wrong-and-silent** (a real column or
table leaves the live map with no failure — the exact defect this issue exists
to remove).

| # | Attack | Result | Class |
|---|---|---|---|
| 1 | `DEFAULT '(a literal with parens)'` | `[a b]` | **right** |
| 2 | `CHECK (a IN ('a,b','c'))` as a table constraint | `[a b]` — comma is at depth > 0, constraint skipped by keyword | **right** |
| 3 | `DEFAULT to_timestamp(0)` (nested function) | `[a b]` | **right** |
| 4 | trailing comma before `)` | `[a b]` — empty segment skipped by `len(fields)==0` | **right** |
| 5 | `-- comment` inside the body | `[a b]` — stripped before depth-tracking, which also neutralises unbalanced parens *inside* comments (`000014` has one) | **right** |
| 6 | `GENERATED ALWAYS AS (a * 2) STORED` | `[a b c]` | **right** |
| 7 | quoted reserved-word column `"check" TEXT` | `["check" b]` — kept, and identically on both sides | **right** |
| 8 | comma inside a top-level string literal (`DEFAULT 'x,y'`) | `[a y' b]` — real columns kept, spurious `y'` invented; symmetric if both sides carry the same text, otherwise a confusing failure | **wrong-but-loud** |
| 9 | `/* block comment */` in the body | `[a /*]` — `stripSQLComments` handles only `--`; the comment's first token becomes a column **and `b` disappears** | wrong-but-loud **and silent** |
| 10 | block-commented-out column `/* b INT, */` | `[a /* */]` — and the *next* real column `c` disappears | wrong-but-loud **and silent** |
| 11 | bare `exclude BOOLEAN` (non-reserved in PG, legal unquoted) | `[b]` — dropped by `tableConstraintKeywords`, symmetrically on both sides, so the column is simply unguarded | **wrong-and-silent** |
| 12 | bare `primary`/`unique`/`check`/`foreign`/`constraint` | dropped — but all five are *reserved* in PG and illegal unquoted, so unreachable | theoretical |
| 13 | unbalanced paren in a literal (`DEFAULT ')'` / `DEFAULT '('`) | `[a]` — depth tracking closes the body early; `b` disappears | **wrong-and-silent** |
| 14 | `--` inside a string literal (`DEFAULT 'see -- below'`) | `[a]` — the strip eats the rest of the line **including its comma**, so the *following* column disappears | **wrong-and-silent** |
| 15 | `CREATE TABLE IF NOT EXISTS t (` | `{}` — `createTableStart` doesn't match, the **entire table** never enters the live map | **wrong-and-silent** |
| 16 | quoted table name `CREATE TABLE "t" (` | `{}` — same, whole table | **wrong-and-silent** |
| 17 | `ALTER TABLE t ADD COLUMN IF NOT EXISTS c …` | records a column named `IF`; `c` never enters the map | wrong-but-loud **and silent** |
| 18 | `ALTER TABLE t ADD c TEXT;` (`COLUMN` is optional in PG) | nothing recorded at all | **wrong-and-silent** |

Coverage check (`checkIndexStatementCoverage`), attacked separately — this half
holds up:

| Attack | loose / strict | Outcome |
|---|---|---|
| `CREATE UNIQUE INDEX` / `CONCURRENTLY` / `IF NOT EXISTS` / all three combined | 4 / 4 | parsed, correct name+table+columns |
| missing `;`, last statement in file | 1 / 0 | **loud** |
| missing `;` followed by another `CREATE INDEX` | 2 / 1 | **loud** (and the drift diff shows the swallow) |
| `ON t USING btree (x)` | 1 / 0 | **loud** — unparsed, as designed |
| unnamed index (`CREATE INDEX ON t (x);`) | 1 / 0 | **loud** |
| `ON ONLY t (x)` | 1 / 0 | **loud** |
| opclass (`(x text_pattern_ops)`) | 1 / 1 | parsed |
| `-- CREATE INDEX …` commented out | 0 / 0 | correctly ignored — comments are stripped **before** counting, in both `liveIndexesFromMigrations` and the test's PRD path (verified by reading the call order, not assumed) |
| `/* CREATE INDEX …; */` commented out | 1 / 1 | registers as live → **loud** false positive (block comments unstripped) |
| `CREATE INDEX …` inside a string literal (`INSERT … VALUES ('…')`) | 1 / 1 | registers as live → **loud** false positive |
| `'a -- b'` literal on the line before a real statement | 1 / 1 | the following statement still parses (the strip keeps the newline) |
| double-counting / two statements collapsing | — | not reachable with equal counts: the strict pattern's `[^;]` capture cannot cross a `;`, so a collapse always leaves loose > strict, or a garbage column list that fails the drift branch |

`found` can never come out *less* than `matched`, since every strict match
begins with a loose match and both scans are non-overlapping — so the check is
sound in the direction it is used.

### Why this bounces

Three of the silent cases are not hypothetical parser trivia — they are ordinary
SQL, and each was proved end-to-end against the real tree, with a control run
showing the guard catching the identical drift when the form is spelled the
plain way:

**1. `CREATE TABLE IF NOT EXISTS` hides an entire table.** In the worktree,
`workshops.signup_url` was deleted from `PRD.md` §6.2 — a real drift. Control
(`CREATE TABLE workshops (`):

```
--- FAIL: TestPRDWorkshopAndMailingColumnParity
    PRD.md §6.2's CREATE TABLE workshops does not mention column "signup_url",
    added by migrations/000020_create_workshops.up.sql — …
```

Then the *only* change: `CREATE TABLE workshops (` → `CREATE TABLE IF NOT
EXISTS workshops (`, same deleted PRD column:

```
ok  	github.com/brennanMKE/OpenCircuitSF/internal/db	0.207s
```

All 17 `workshops` columns silently left the live map. No coverage error, no
notice, green suite. `IF NOT EXISTS` is one of the three forms named in this
issue's own title — the fix widened the index prefix for it and reintroduced the
identical blind spot in the new column half.

**2. `ALTER TABLE t ADD <col>` (without the optional `COLUMN` keyword) is
invisible.** `migrations/999997_scratch.up.sql` containing
`ALTER TABLE workshops ADD scratch_col TEXT;` — a brand-new column §6.2 has
never heard of — produced `ok … 0.208s`. Zero failures. With `ADD COLUMN IF NOT
EXISTS` it fails, but names the wrong thing: `does not mention column "IF"`,
while `scratch_col` itself stays unguarded.

**3. A `--` inside a string literal eats the next column.** Changing `000020`'s
`signup_url TEXT,` to `signup_url TEXT NOT NULL DEFAULT 'see -- below',` and
deleting the *following* column (`cover_image`) from §6.2 produced `ok …
0.211s`; restoring the literal and re-running the same PRD deletion produced the
expected `does not mention column "cover_image"` failure. `stripSQLComments`
removed the rest of the line **including the comma**, merging two column
definitions into one segment.

This issue's own criterion 2 states the principle in its heading — *"The guard
fails loudly on anything it cannot parse"* — and the index half now honours it
completely. The column half, shipped in the same commit, has no coverage check
at all, and fails silently on three ordinary forms. Approving it would mean
closing an issue about silent parse failures with a new parser that skips
silently: the specific outcome the issue's own `## Description` calls "the
failure mode that makes a guard worse than no guard". None of these forms exist
in `migrations/` today (`grep -i 'if not exists' migrations/` is empty, no
block comments anywhere, `000014`'s only `--`-in-context is a genuine comment),
so nothing is *currently* mis-guarded — same standing as `#0148` when this issue
was filed against it. The difference is that removing exactly this silence is
`#0154`'s job.

### What would clear the bounce

Small and bounded — the index half is the template:

1. **A coverage check for the column half**, mirroring
   `checkIndexStatementCoverage`: per migration file and for §6.2, count loose
   `CREATE\s+TABLE\b` occurrences against `createTableStart` matches, and loose
   `ALTER\s+TABLE\s+\w+\s+ADD\b` (excluding `ADD CONSTRAINT`) against
   `columnAddPattern` matches, and `t.Errorf` on a mismatch. This is what makes
   attacks 15–18 loud instead of silent, including any form nobody has thought
   of yet.
2. **Widen the two patterns** the way the index prefix was widened:
   `createTableStart` → `CREATE\s+TABLE\s+(?:IF\s+NOT\s+EXISTS\s+)?(\w+)\s*\(`;
   `columnAddPattern` → `ADD\s+(?:COLUMN\s+)?(?:IF\s+NOT\s+EXISTS\s+)?(\w+)`,
   taking care that `ADD CONSTRAINT`/`ADD PRIMARY KEY` still don't match (this
   tree has five such `ALTER`s, in `000010`, `000013`, `000017`, `000018`,
   `000020`).
3. **Make `stripSQLComments` quote-aware**, and use the same scan for
   `splitTopLevel`/`columnsFromCreateTable`'s depth tracking: one left-to-right
   pass that tracks whether it is inside a `'…'` literal, skipping `--`, `/* */`,
   parens and commas found inside one. ~20 lines, and it retires attacks 8, 9,
   10, 13, and 14 together, plus the block-comment false positive on the index
   side.
4. Optional, cheap: drop `EXCLUDE` from `tableConstraintKeywords` or match it as
   `EXCLUDE\s+USING`, since `exclude` is non-reserved in Postgres and is the one
   keyword in that list that is a legal bare column name (attack 11). The other
   five are reserved and unreachable.

Not required, but worth folding in while the file is open: make `prdPath` a
package variable so the column proof can point at a scratch copy instead of
editing the project's specification in place (the implementer's own gotcha).
