## Description

**`opencircuit` has no backups and never has.** Measured on the box:

	systemctl is-enabled opencircuit-backup.timer
	→ Failed to get unit file state … No such file or directory

`/etc/systemd/system/` contains **only** `opencircuit.service`. `systemctl
list-timers` reports **0 timers**. The only dumps on disk belong to ShortLinks
(`/var/backups/postgres/shortlinks/`, newest 2026-08-17) plus a one-off
`pgdumpall-2026-08-14.sql.gz` from the AL2023 upgrade.

**Everything needed already exists and is correct.** `scripts/db/backup.sh`,
`restore.sh`, `pull-backups.sh` and `backup-alert.sh` are all present in the
repo *and* deployed to `/opt/opencircuit/scripts/db/`. All three unit files —
`opencircuit-backup.service`, `.timer`, and `-alert.service` — are in
`deploy/systemd/`. The service correctly sets `BACKUP_DATABASES=opencircuit`.

**They were written and never installed.** Only `opencircuit.service` was.

## Why this is the most urgent open issue

Production holds real, irreplaceable data: subscribers, the interest taxonomy,
audit rows, and the user's first newsletter draft. **None of it has ever been
dumped.**

And a **migration is about to run against it**. `#0404`'s deploy sequence says
"back up before `migrate up`" — a step that cannot currently be performed by any
installed mechanism.

## Acceptance criteria

1. The timer is installed, enabled and running, per `deploy/systemd/README.md`'s
   documented procedure. **Follow that document**; do not invent an install.
2. **A real dump exists and is verified** — not merely a green unit. Confirm the
   file, its size, and that it is a valid archive.
3. **A restore is proved.** `scripts/db/restore.sh` exists and is untested here.
   Restore into a **scratch database, never over `opencircuit`**, and compare
   row counts for `subscribers`, `email_campaigns`, `workshops` and
   `interests` against the source. §8b: a mutation that touches real data must
   run against a database you created.
4. Retention and disk are checked: `backup.sh`'s prune keeps the volume bounded
   on a `t4g.nano` (§7 — 418 MB RAM, and disk is not unlimited either).
5. `backup-alert.sh`'s path is considered — it reads
   `EnvironmentFile=-/etc/opencircuit/backup-alert.env`, which has **no
   committed template** and is optional. Say whether alerting should be wired
   now or deliberately left.
6. `docs/deployment.md` and `CLAUDE.md` §7 record the real state afterwards.
   **Note `#0431` is concurrently sweeping that file** for pre-deploy claims —
   coordinate rather than colliding.
7. **Installing units and enabling a timer changes production.** Do not do it
   without the user's explicit go-ahead; prepare and verify everything that can
   be verified without it, and say exactly what remains.

  **Four questions, answered (full reasoning in
  `deploy/systemd/README.md`):**
  1. `chown postgres:postgres` (non-recursive, top-level directory only) is
     right, not a mode change — nothing live depends on the current root
     ownership, and a mode-only fix would require opening the directory to
     "other" (it holds session tokens, passkey credentials, and the audit
     log per `backup.sh`'s own header), which is strictly worse. The
     sibling `shortlinks/` directory is untouched by a non-recursive chown.
  2. Dumps land at
     `/var/backups/postgres/opencircuit/opencircuit-<timestamp>.dump` (+
     `-latest.dump`) and `/var/backups/postgres/media/media-<timestamp>.tar.gz`
     (+ manifest/`-latest`). At today's data volume (9.6 MB database, 152 KB
     media) the compressed footprint is negligible against 9.1 GB free; a
     full disk fails `pg_dump`'s temp-file write, which `backup.sh` already
     detects (`rc≠0` or an empty `$tmp`), removes the partial file, leaves
     every prior good dump untouched, exits non-zero, and fires the alert —
     it does not free space itself.
  3. Retention is local-only, `BACKUP_RETENTION_DAYS` (default 14). The
     offsite pull (`pull-backups.sh` to the user's "joe" machine) is treated
     as **out of scope** for this issue — joe's hostname and reachability
     for an unattended pull are not recorded anywhere in this repo, and per
     the task's instruction this is a question for the user, not a default
     to invent.
  4. First run behaves correctly: re-confirmed `#0445`'s control-flow finding
     still holds (unchanged bytes, `sha256sum` verified) — the prune step is
     reachable only in the same loop iteration immediately after a fresh
     publish, so a first run with no prior dump writes one file (age 0) and
     the `-mtime +14 -delete` prune matches nothing.
