## Description

**`opencircuit` has no backups and never has.** Measured on the box:

	systemctl is-enabled opencircuit-backup.timer
	→ Failed to get unit file state … No such file or directory

`/etc/systemd/system/` contains **only** `opencircuit.service`. `systemctl
list-timers` reports **0 timers**. The only dumps on disk belong to ShortLinks
(`/var/backups/postgres/shortlinks/`, newest 2026-08-17) plus a one-off
`pgdumpall-2026-08-14.sql.gz` from the AL2023 upgrade.

**Everything needed already exists and is correct.** `scripts/db/backup.sh`,
`restore.sh`, `pull-backups.sh` and `backup-alert.sh` are all present in the
repo *and* deployed to `/opt/opencircuit/scripts/db/`. All three unit files —
`opencircuit-backup.service`, `.timer`, and `-alert.service` — are in
`deploy/systemd/`. The service correctly sets `BACKUP_DATABASES=opencircuit`.

**They were written and never installed.** Only `opencircuit.service` was.

## Why this is the most urgent open issue

Production holds real, irreplaceable data: subscribers, the interest taxonomy,
audit rows, and the user's first newsletter draft. **None of it has ever been
dumped.**

And a **migration is about to run against it**. `#0404`'s deploy sequence says
"back up before `migrate up`" — a step that cannot currently be performed by any
installed mechanism.

### The restore drill — audited hardest, and it holds

- **It never targets `opencircuit`.** `restore.sh` is invoked with the literal
  scratch name, and `scripts/db/restore.sh` never drops a database at all (its
  own header says so, and the code has no `dropdb` outside the caller's hands).
  The only statement aimed at `opencircuit` is a read-only `count(*)`.
- **It cannot silently overwrite.** `RESTORE_CREATE=1` calls `createdb`, which
  fails if the name already exists, and the script runs under `set -euo
  pipefail` — so a stale scratch database aborts the drill instead of being
  restored over.
- **The evidence is content, not an exit code — and that is load-bearing
  here, not decorative.** `pg_restore` without `--exit-on-error` continues past
  failures and still exits 0, so `restore.sh` returning success proves little.
  The row-count comparison is what actually decides it, which is exactly the
  answer `#0434`'s review asked for.
- **It would fail on a bad restore, not pass vacuously.** A table that failed
  to restore makes `count(*)` raise `relation … does not exist`, so that
  database's block prints an error instead of four numbers; a structurally
  complete but empty restore prints `0` against `6/1/3/12`. Every count is
  label-prefixed (`subscribers|6`), so the two blocks stay comparable even if
  `UNION ALL` branch order ever differed. I could not construct a corruption
  that leaves the two blocks matching.

One gap, non-blocking (N4 below): if the restore aborts partway the scratch
database is left behind, and the `dropdb` is a later step the reader may never
reach.

### Required fixes

**F1 — two verification commands cannot produce their stated output.** Proved
against the live box just now, as `ec2-user`:

    $ stat -c '%U:%G %a' /var/backups/postgres /var/backups/postgres/shortlinks
    root:root 700
    stat: cannot statx '/var/backups/postgres/shortlinks': Permission denied
    rc=1

    $ ls -la /var/backups/postgres/
    ls: cannot open directory '/var/backups/postgres/': Permission denied
    rc=2

`ec2-user`'s groups are `ec2-user, adm, wheel, systemd-journal` — **not**
`postgres`. The directory is mode `700` before the `chown` and mode `700`
after it, so `ec2-user` has no traverse bit either way, and `backup.sh` itself
re-asserts `chmod 0700` on `BACKUP_ROOT` every run. The instruction tells the
reader to "Expect `postgres:postgres 700` on the first line and `root:root
700`, unchanged, on the second" — **the second line is unobtainable without
`sudo`, before or after the fix.** A reader sees a permission error in the
first thing they check after chowning a production backup directory, which
reads exactly like the `chown` broke something. The same applies to the
`ls -la` opening the dump-verification block; the two lines under it already
carry `sudo -u postgres` and are correct.

Remedy — in "Fix the `/var/backups/postgres` permission blocker", the
verification block becomes:

```bash
sudo stat -c '%U:%G %a' /var/backups/postgres /var/backups/postgres/shortlinks
```

and in "Verify the dump is real, and prove a restore", step 1, the block's
first line becomes:

```bash
sudo ls -la /var/backups/postgres/opencircuit/
```
