## Description

```go
e := audit.Entry{Metadata: map[string]any{"slug": s}}
e.Metadata["email"] = addr    // hasEmail=false, unresolved=""  — SILENT PASS
```

The left-hand side is an `*ast.IndexExpr`, while
`collectDeferredMetadataFieldIdents` requires an `*ast.SelectorExpr`. So the
guard does not see it, and an entry carrying a subscriber's address passes as
email-free.

**What makes this one more plausible than the two shapes `#0255` chose to pin:
the local-variable form of the identical mutation is already caught.**

```go
m := map[string]any{"slug": s}
m["email"] = addr
e := audit.Entry{Metadata: m}   // hasEmail=true — correctly caught
```

Both express the same intent. The caught version and the missed version differ
by a one-line reordering of code the tree already contains — not by an exotic
construct nobody writes. No production site uses the missed form today
(verified: no `.Metadata[` anywhere in production code), which is the condition
under which this kind of gap survives unnoticed.

**Worth considering in this pass:** rather than adding a ninth node type,
invert the default. Any write to a `Metadata` map that the guard cannot fully
resolve should report `unresolved` rather than pass, so an unrecognised shape

that inversion is impractical — it may produce false positives on legitimate

## Root cause

`collectDeferredMetadataFieldIdents` recognized exactly one AST shape for "an
identifier's Metadata was mutated after its own composite literal": a bare
`ident.Metadata = ...` assignment, i.e. an `*ast.AssignStmt` whose LHS is an
`*ast.SelectorExpr`. `e.Metadata["email"] = addr`'s LHS is an
`*ast.IndexExpr` — `X` is that same `*ast.SelectorExpr` (`e.Metadata`),
`Index` is the string literal `"email"` — one syntactic layer further down,
and nothing in the walk was looking there. The literal's own (unrelated)
Metadata key, or no Metadata key at all, is what the classifier saw; the
later index assignment was invisible, so the site resolved as
`hasEmail=false, unresolved=""` — a silent pass.

## Fix

Widened `collectDeferredMetadataFieldIdents` to also match
`ident.Metadata[...] = ...`, deliberately without inspecting the index
value at all — mirroring the existing `ident.Metadata = ...` case, which
never reads what it's assigned either. Either shape means this guard cannot
prove which keys the running code ends up with, so both are reported
`unresolved` unconditionally, regardless of the specific key. This is why
the fix "covers index assignment on a field generally, not just the literal
key `\"email\"`" per the acceptance criteria — it isn't string-matching
`"email"` at all, it's recognizing the assignment shape.

**Design question, answered rather than deferred**: the issue asked whether
any `Metadata` write this guard cannot fully resolve should report
`unresolved` by default, instead of adding a ninth recognized node type.
Split into two halves:

- **The READ side** (`classifyMetadataExpr`, examining a `Metadata: <expr>`
  value's own shape) **already works this way** — an unrecognized
  `*ast.Ident`, `*ast.CallExpr`, or any other expression type returns
  unresolved via the `switch`'s `default` case, not `hasEmail=false`. Every
  silent pass this file's history documents, `#0257` included, was never
  this half defaulting to pass on something unrecognized.
- **The WALK side** (`collectDeferredMetadataFieldIdents`, noticing a
  mutation happened at all) is where every one of these gaps has actually
  lived, `#0257` included — it pattern-matches specific `*ast.AssignStmt`
  LHS shapes, so there is no dispatch point where "unrecognized ⇒ fail"
  already sits for this half; each new shape needs a new pattern taught to
  it, the same way this fix teaches it one more.

A maximal inversion — flag any assignment anywhere in the function whose LHS
is a `*ast.SelectorExpr` or `*ast.IndexExpr` matching an
audit.Entry-holding identifier's **name**, regardless of which field is
touched — was considered and rejected: it would flag ordinary, unrelated
field writes (`e.Action = "..."`) as Metadata risk, and it would multiply
the already-documented same-name false-positive class (a same-named
variable of an unrelated type in a disjoint block already gets flagged
today, only when its own `.Metadata` field specifically is touched;
matching on any field of any same-named identifier would catch far more
innocent code with nothing to do with Metadata at all). The fix implemented
is the narrow form of "invert the default" this shape actually calls for:
it teaches the walk one more Metadata-specific mutation shape and reports
it unresolved unconditionally once seen, without widening what counts as
"touches Metadata" to fields that are not Metadata.
