## Description

`#0113` added `internal/db/prd_section_index_test.go`, which runs every `CLAUDE.md`
§11 row's own `sed` command against `PRD.md` and fails naming any row whose line
count disagrees. Its phase-3 review recomputed all 48 rows independently — sed,
table, and guard all agreed — and then found the gap.

**The guard's BRE→RE2 translation is one-directional.** `sedBREToGoRegex` rewrites
`\{`→`{`, which is the bug `#0113`'s implementer found and fixed in its own draft.
But the **inverse** is untranslated: a *bare* `{n,m}` is **literal in BRE and an
interval in RE2**.

Demonstrated, not argued: mutating §3.1's Extract cell to `/^#{2,3} [0-9]/` makes
real `sed` print **1,690 lines** — no terminator matches, so it runs to EOF —
against a stated 19, while `TestPRDSectionIndexParity` **passes**.

The same silent divergence applies to bare `+`, `?`, `(`, `)`, and to `\(` `\)`.
Backreferences fail loudly, which is fine. `\+ \? \|` diverge only under GNU sed,
which this repo does not use.

**Two structural divergences from `sed` as well:** `countPRDSection` stops after
the first matching range where real `sed` restarts one, and `parseSedRangeCmd`
mis-splits on an escaped `\/`.

**No current row triggers any of these** — the guard is correct on the table as it
stands. What is wrong today is the claim: the file's doc comment calls itself
"the mechanical check on the extraction commands themselves", which is more than
it does.

## Implementation notes

Added `sedPatternUnsafeConstruct` to `internal/db/prd_section_index_test.go`
and call it from `parsePRDIndexTable` on both `startPat` and `endPat` before
either pattern reaches `sedBREToGoRegex`/`regexp.Compile`. It scans char by
char, tracking whether the previous rune is a backslash, and rejects:

- a bare (unescaped) `{` or `}` — literal in BRE, an RE2 interval char if left untranslated
- a bare `(` or `)` — literal in BRE, an RE2 group char if left untranslated
- an escaped `\(` or `\)` — a BRE group; `sedBREToGoRegex` doesn't rewrite it, so RE2 reads it as a literal paren instead, losing the group either way
- a bare `+`, `?`, or `|` — literal in BRE, an RE2 metacharacter if left untranslated

`\+ \? \|` are intentionally left alone: literal on this repo's BSD sed and
still literal, unrewritten, in RE2 — they only diverge under GNU sed, which
this repo doesn't use (per the issue's own note). Backreferences (`\1`) are
also left alone — an unrewritten `\1` already fails `regexp.Compile` loudly,
so no lint is needed there. On rejection, `t.Errorf` names the row (with its
`CLAUDE.md:%d` line), the pattern, and a human-readable description of the
offending construct, then the row is skipped (`continue`) rather than fed to
`countPRDSection`.

**Mutation proof 1 (the case from `#0113`'s review).** Captured
`shasum -a 256 CLAUDE.md` = `8da3eb7e…bbae186`, changed §3.1's Extract cell
END pattern from `` /^#\{2,3\} [0-9]/ `` to `` /^#{2,3} [0-9]/ `` (bare brace),
ran `go test ./internal/db/... -run TestPRDSectionIndexParity -v`. Fails:

```
prd_section_index_test.go:356: CLAUDE.md:717 §11 row "§3.1 Copy unchanged
(rename module path + branding strings only)": END pattern /^#{2,3} [0-9]/
contains a bare `{` (literal in sed's BRE, an RE2 interval character if
untranslated) — this cannot be translated from sed's BRE to Go's RE2
faithfully, so the row's count cannot be trusted. Rewrite the pattern to
avoid it, or teach sedBREToGoRegex and sedPatternUnsafeConstruct together.
```

Real `sed -n '/^### 3\.1 /,/^#{2,3} [0-9]/p' PRD.md | wc -l` = 1699 (runs to
EOF, no terminator matches) against a stated 19 — the exact silent-false-pass
this issue was filed about, now a named failure instead. Restored
`CLAUDE.md`, re-ran `shasum -a 256` — matched byte-for-byte — and
`git diff -- CLAUDE.md` was empty.

**Mutation proof 2 (a different construct).** Same before/after shasum
discipline. Changed §4.2's START pattern from `` /^### 4\.2 /`` to
`` /^### 4\.2+ / `` (bare `+`). Fails:

```
prd_section_index_test.go:356: CLAUDE.md:723 §11 row "§4.2 Color tokens":
START pattern /^### 4\.2+ / contains a bare `+` (literal in sed's BRE, an
RE2 metacharacter if untranslated) — this cannot be translated from sed's

the pattern to avoid it, or teach sedBREToGoRegex and
sedPatternUnsafeConstruct together.
```

Restored; shasum matched; `git diff -- CLAUDE.md` empty.

**Default-scope confirmation.** With the §3.1 mutation still in place, ran

**The doc comment overclaim (criterion 4).** The file's top comment used to
say the test "is the mechanical check on the extraction commands themselves,
not just the numbers." Rewrote that paragraph to state what the test
actually verifies: the arithmetic — that each row's stated count matches
what its own START/END patterns produce against `PRD.md` — for the subset of
BRE the 48 rows currently use (literal text, `\.`, character classes, and
`\{n,m\}`). It is explicit now that this is not a general BRE validator, and
that the new lint is what converts an untranslatable Extract cell into a
loud, named failure rather than a silent wrong count. `sedBREToGoRegex`'s own
doc comment was extended similarly, noting it depends on
`sedPatternUnsafeConstruct` having already screened its input.

**Criterion 5 — one fixed, one documented with a loud check, per the issue's
own permission to do either:**

- **`parseSedRangeCmd`'s `\/` mis-split — fixed.** The old split used
  `strings.Index(body, "/,/")`, the first textual match. Replaced with a scan
  that finds a `/,/` whose leading `/` is not itself escaped (an even count
  of immediately preceding backslashes), so a pattern containing its own
  escaped literal slash before a `,` and `/` can no longer be mistaken for
  the START/END separator. No current row's pattern contains a `/` at all,
  so this was latent, not triggered — fixing it was cheap enough (a bounded
  scan, no new dependency) that documenting a known-wrong split felt worse
  than just closing it.
- **`countPRDSection`'s single-range behaviour — documented, with a loud
  check rather than a source-only comment.** Reimplementing `sed`'s full
  restart-on-repeated-START semantics for a case nothing in the table
  exercises felt like scope creep for this issue. Instead, `countPRDSection`
  now also returns `mayRestart`: after computing the first START/END range,
  it scans the remainder of `PRD.md` for another START match. Every current
  row's START pattern is a unique heading anchor (confirmed: none of the 48
  rows sets `mayRestart` today), so this adds no failures now — but a future
  row whose START pattern isn't unique will fail loudly, by row and pattern,
  in `TestPRDSectionIndexParity` itself:
  `"START pattern /%s/ matches PRD.md again after this row's computed range
  ends — real sed would restart a new START/END range there... (known limit,
  #0218)"` — legible from the failure message alone, not only from a source
  comment.

Two corrections to `#0113`'s review table fall out of measuring rather than
reasoning: `\<` `\>` are **literal on BSD sed and literal in RE2** — they
agree, where `#0113` recorded "compiles, matches nothing"; and a leading `*` is
loud, not silent.

**The residual gap, stated precisely.** `sedPatternUnsafeConstruct` decides
"escaped" with `runes[i-1] == '\\'` — one preceding rune, not a parity count.
So a metacharacter preceded by an *even* number of backslashes (≥2) is treated
as escaped and allowed. This is the same odd/even reasoning the implementer
fixed five lines away in `parseSedRangeCmd` and did not carry into the lint.
Measured, not argued: `a\\{b` matches `a\{b` under BSD sed and `a{b` under the
guard; `a\\+b` matches `a\+b` under sed and "a, one-or-more backslashes, b"
under the guard. Both slip through. So criterion 1's literal wording
("*unescaped* `{`") is not fully met at ≥2 backslashes. It is unreachable —
no §11 row contains a `\\`, and no heading anchor plausibly would — and the
same is true of a mid-pattern `^`/`$` (a trailing `$` is an anchor in both and
is fine). Reported below for filing rather than bounced.

**The `\+` allowance is provably safe on this repo's sed.** Two measurements:

1. *Which semantics does BSD sed use?* `/aX\+b/` against a corpus of `aXXXb`,
   `aXb`, `aX+b` matched **only `aX+b`** — literal plus, not GNU's one-or-more.
   `/aX\?b/` matched only `aX?b`; `/a\|b/` matched only `a|b`.
2. *Do sed and the guard extract the same range?* Built a row whose START uses
   `\+` as a literal plus against real `PRD.md` text:
   `sed -n '/^or .\+tag. suffixes/,/^## [0-9]/p' PRD.md | wc -l` = **586**,
   first line `PRD.md:749` (``or `+tag` suffixes — …``), last line
   `## 7. Frontend`. The guard, on the same pair: START first matches
   `PRD.md:749`, `countPRDSection` returns **585** — `raw − 1` per §11's
   convention. Identical range. The allowance holds, exactly as the doc comment
   scopes it (BSD, not GNU).

One follow-up issue, low priority — all of it latent:

- **`sedPatternUnsafeConstruct` counts one backslash, not parity, and ignores
  bracket expressions.** Three separate small defects in one function: (a) a
  metacharacter preceded by ≥2 backslashes is wrongly treated as escaped, so
