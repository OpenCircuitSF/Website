## Description

Two robustness gaps in how rendered output is constructed, both found during `#0076`'s review. Neither is a live defect today; both are the kind that surface at deploy time on someone else's machine.

> 🟢 Resolved 2026-08-19 — The full boundary table was re-measured end to end through `loadFromFile` against a real on-disk `.env` (not the function in isolation) and every row collapses to a single slash — `https://x.com/`, `//`, and `///` all load as `https://x.com`, and `https://x.com/base/` and `/base//` as `https://x.com/base` — while four probes nobody had tried confirm `strings.TrimRight` is nowhere worse than the `TrimSuffix` it replaced: an all-slashes value (`/`, `//`, `///`) collapses to `""` and is rejected by the required-field check (a strict tightening — under `TrimSuffix`, `//` became a non-empty `/` that passed validation and still produced `//login`), a trailing slash before a query or fragment (`https://x.com/?a=1`, `https://x.com/#f`) is left untouched because there is no trailing slash to strip, and a scheme-relative `//x.com/` keeps its leading pair and yields `//x.com/login` since `TrimRight` only touches the right-hand end. Both mutations were re-run independently: reverting to `strings.TrimSuffix(raw, "/")` fails exactly the three multi-slash subtests (`two_slashes`, `three_slashes`, `path_with_two_slashes`) while `one_slash` and `path_with_one_slash` stay green, which is precisely why the defect was latent; and the count-preserving case — a new exported `BuildProbeFEmail` plus a duplicate `sessions_revoked_dup` entry re-calling an existing builder — was run against both guards in an isolated worktree, passing silently under `f8624a1`'s `len(found) != len(allMessages())` check and failing under the rewritten identity check with `allMessages() does not call [BuildProbeFEmail]`, so the identity rewrite closes the exact gap it was written for. Both recorded decisions hold: no `internal/seo` test constructs a `Site`, `Renderer`, `Sitemap`, or `BuildRobotsTxt` with a trailing-slash `baseURL` — the package's only two test values, `testBaseURL` and `configuredBaseURL`, are both slash-free — and the sole non-test caller is `cmd/opencircuit/main.go:573` passing `cfg.BaseURL`, so the three `TrimSuffix` calls are genuinely redundant rather than load-bearing and the single-normalisation-point claim stands; the `Build…Email` naming gap is documented on `buildEmailFuncName` with a named actor and is acceptable as recorded, though a return-type check (exported top-level funcs returning `Message`) would close it without the non-`Message`-helper false positive the decision cites as its reason not to widen — recorded as a follow-up on #0043, the campaign builder that will actually hit it. `go build ./...` and `go vet ./...` are clean, `go test ./internal/config/... ./internal/mailing/... ./internal/seo/... -count=1` is green with zero failures and zero skips, and `5268309` touches exactly its three declared files.

## 1. `BASE_URL` accepts a trailing slash and nothing strips it

`internal/config/config.go`'s `BASE_URL` is a bare `os.Getenv`. Every consumer concatenates directly — `BuildRegistrationEmail`, `BuildRecoveryEmail`, `BuildConfirmationEmail`, and `BuildSessionsRevovedEmail` all do `baseURL + "/path"`. So `BASE_URL=https://www.opencircuitsf.com/` yields `https://www.opencircuitsf.com//login`.

Production's value has no trailing slash, which is the only reason this is latent. But `BASE_URL` is operator-supplied in `/etc/opencircuit/config.env`, a trailing slash is the single most common way to write a base URL, and the failure is silent — the links still resolve on most servers while looking wrong in a security email, and `og:url`/sitemap `<loc>` values would carry the doubled slash into indexed pages.

`#0072` already established that `BASE_URL` drives canonical URLs, `og:image`, sitemap entries and `robots.txt`, so the blast radius is wider than email.

## 2. `TestNoRenderedBodyContainsCTAToken` only catches the token it knows

The guard matches `{{cta}}` specifically, so an unknown token like `{{nope}}` ships silently into a rendered body. A generic `{{…}}` check would cover the class rather than the instance.

Related, and inherent to every property test in that file: it iterates a fixed `allMessages()` of five, so a sixth `Build*Email` is not covered until someone remembers to add it there. The file's own doc comment says as much.

Neither is an injection risk — substitution precedes `html.EscapeString`.

## Acceptance criteria

- [x] `BASE_URL` is normalised once, at config load, with **every** trailing slash stripped (`strings.TrimRight`) — not patched at each call site. **Mutation-proven**: reverting to `strings.TrimSuffix` fails exactly the multi-slash subtests
- [x] A test asserts `https://example.com/` and `https://example.com` produce identical rendered URLs. **Mutation-proven** by removing the normalisation and watching it fail
- [x] Every existing consumer is confirmed to go through the normalised value: the four email builders, `internal/seo`'s canonical/`og:url`/`og:image`, the sitemap `<loc>` values, and `robots.txt`'s `Sitemap:` line
- [x] `TestNoRenderedBodyContainsCTAToken` matches a generic `{{…}}` pattern rather than one literal token, and fails on an unknown token — mutation-proven
- [x] A decision, recorded either way, on whether `allMessages()` can be made to enumerate builders automatically rather than by hand

## Notes

The trailing-slash fix belongs in `internal/config`, not in the callers — the whole point is that one place defines the value. `#0072` made the same argument about apex-versus-www: `internal/seo` was right to trust `BASE_URL`, and the template was the defect.

`#0076`'s reviewer also observed that `/login` emits `og:url` as the site root rather than `…/login`. That is plausibly deliberate — a staff route, excluded from the sitemap — but nobody has confirmed it. Recorded on `#0019` rather than here.

## Fix

**Re-implemented after the 2026-08-19 review bounce.** The bounce's one
blocker — `normalizeBaseURL` stripping only one trailing slash — is fixed
below (updated item 1). The bounce's second finding — the enumeration guard
comparing counts, not identities — is also fixed below (updated item 3).
Everything the reviewer verified good (consumer coverage, the generic
`{{…}}` scope) was re-confirmed unchanged and is not re-described here; see
the 2026-08-19 review record in the resolution note above.

**1. `BASE_URL` is normalised once, at config load — every trailing slash,
not one.** `internal/config/config.go`'s `normalizeBaseURL` now uses
`strings.TrimRight(raw, "/")` (previously `strings.TrimSuffix(raw, "/")`,
which only removed a single trailing slash and left `BASE_URL=https://x.com//`
producing `https://x.com//login` — the exact defect this issue was filed
about, still reproducible against the bounced version). `Config.BaseURL`
routes through it instead of the bare `os.Getenv("BASE_URL")`. Every caller
downstream of `cfg.BaseURL` (traced in `cmd/opencircuit/main.go`, read-only,
not edited — that file is another subagent's lane) now receives the clean
value without any per-call-site patch:

- `internal/auth/mailer.go`'s `NoOpMailer.BaseURL` → `verificationURL`,
  `recoveryURL`
- `internal/auth/ses_mailer.go`'s `SESMailer.baseURL` (set from `cfg.BaseURL`
  in `NewSESMailer`/`NewSESMailerWithSender`) →
  `mailing.BuildRegistrationEmail`, `BuildRecoveryEmail`,
  `BuildSessionsRevokedEmail`
- `internal/handlers.NewSubscribeHandler(..., cfg.BaseURL, ...)` →
  `mailing.BuildConfirmationEmail`, `BuildAlreadySubscribedEmail`
- `internal/seo.NewSite(indexHTML, cfg.BaseURL, nil)` → `NewRenderer`
  (canonical/`og:url`/`og:image`), `NewSitemap` (sitemap `<loc>`),
  `BuildRobotsTxt` (`Sitemap:` line)

`internal/seo`'s own `strings.TrimSuffix(baseURL, "/")` calls inside
`NewRenderer`, `NewSitemap`, and `BuildRobotsTxt` (predating this issue) were
left in place as a harmless, now-redundant second normalisation rather than
removed — see `## Gotchas`.

**2. `TestNoRenderedBodyContainsCTAToken` now matches any `{{…}}` token.**
Unchanged from the previous implementation — the reviewer re-verified this
correct and not a false-positive risk (2026-08-19 review). Replaced the
literal `strings.Contains(msg.X, ctaToken)` checks in
`internal/mailing/templates_test.go` with a package-level
`unresolvedTemplateToken = regexp.MustCompile(`+"`"+`\{\{[^{}]*\}\}`+"`"+`)`
and `FindString` calls that report the actual leaked token in the failure
message, not just the one the test happened to be looking for.

**3. `allMessages()` enumeration decision: not automatable by invocation,
but made self-checking — now by identity, not count.** Go has no runtime
reflection over a package's own top-level function declarations, so
`allMessages()` cannot be made to *call* a newly added `Build*Email`
function without a code-generation step — more machinery than five (soon
six) functions justifies; that part of the decision stands. But the
reviewer proved the original guard's `len(found) != len(allMessages())`
comparison has a false-positive gap: adding a new builder *and* a second,
duplicate `allMessages()` entry that re-calls an existing builder keeps the
counts equal while the new builder stays genuinely uncovered.
`TestAllMessagesEnumeratesEveryBuildEmailFunc` now parses the package's own
non-test source with `go/parser` to collect the set of exported top-level
`Build*Email` declarations, separately parses `allMessages()`'s own function
body (including test files, since `allMessages()` lives in
`templates_test.go`) with `go/ast.Inspect` to collect the set of
`Build*Email` identifiers it actually *calls*, and asserts every declared
builder appears in the called set — an identity check. This turns "forgot
to wire the sixth builder into `allMessages()`" from a silent gap (per the
file's own doc comment) into a named test failure that survives the
duplicate-entry false positive, not just the missing-entry case.

**Naming-convention decision, recorded per the review's ask:** kept
`buildEmailFuncName` scoped to `^Build[A-Za-z0-9]*Email$` rather than
widening to a bare `^Build`. Every exported top-level `Build*` function in
`internal/mailing` today ends in `Email` (five, confirmed by grep), and
widening now would risk the regex matching a future non-`Message` helper
(e.g. a `BuildAddressBlock` string helper) that `allMessages()` has no
reason to enumerate. The tradeoff, recorded in a comment on
`buildEmailFuncName` in `templates_test.go`: a future `Message`-returning
builder named without the `Email` suffix (e.g. a `BuildWorkshopReminder`)
would be invisible to this guard. Whoever adds one must either follow the
convention or widen the regex at that time.

## Gotchas

- **Re-confirmed after the fix: `internal/seo`'s three `TrimSuffix` calls
  stay in place, unchanged, still one-slash.** `NewRenderer`/`NewSitemap`/
  `BuildRobotsTxt` still do their own local `strings.TrimSuffix(baseURL, "/")`
  (`internal/seo/seo.go:136`, `internal/seo/sitemap.go:54`,
  `internal/seo/robots.go:26`) — not touched by this pass. With
  `normalizeBaseURL` now stripping every trailing slash at config load, these
  are idempotent no-ops on the value every real caller (`cmd/opencircuit/main.go`
  → `seo.NewSite(indexHTML, cfg.BaseURL, nil)`) actually passes, so they
  remain harmless. They are, however, still only single-slash themselves: if
  a caller ever constructed `NewSite`/`NewRenderer`/`NewSitemap`/
  `BuildRobotsTxt` directly with a raw multi-slash string (bypassing
  `cfg.BaseURL`), these three would not fully protect against the class
  `internal/config` now handles — same gap as before, just demoted from
  primary defense to redundant defense-in-depth. Re-checked
  `internal/seo/*_test.go`: still no test exercises a raw trailing-slash
  `baseURL` directly (`testBaseURL = "https://www.opencircuitsf.com"`, no
  slash), so there is nothing new to prove either way. Decision, unchanged
  from the bounced version: leave them — removing them touches three more
  files outside this issue's fix for no behavioral gain given the one real
  call path, and `internal/config` is the single normalisation point the
  acceptance criteria actually ask for. If a future cleanup pass wants zero
  redundancy, those three `TrimSuffix` calls are the ones to remove (and, if
  removed, should become `TrimRight` if kept as any kind of guard at all).
- `cmd/opencircuit/main.go` and `internal/handlers` are out of lane for this
  batch (another subagent is fixing `#0031` there this round) — the
  consumer trace above is read-only confirmation via `grep`, not an edit.
- The mutation probes for criterion 3 (both the missing-entry case and the
  count-preserving duplicate-entry case) append/edit real (if inert)
  content in `transactional_templates.go` and `templates_test.go` during the
  proof; both files are restored from `cp`-saved backups immediately after
  and diffed
  byte-identical before moving on, per CLAUDE.md §8a (never leave a mutation
  in a file someone else might be mid-edit on — though `internal/mailing` is
  this batch's own lane).
