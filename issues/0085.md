## Description

Two robustness gaps in how rendered output is constructed, both found during `#0076`'s review. Neither is a live defect today; both are the kind that surface at deploy time on someone else's machine.

## 1. `BASE_URL` accepts a trailing slash and nothing strips it

`internal/config/config.go`'s `BASE_URL` is a bare `os.Getenv`. Every consumer concatenates directly — `BuildRegistrationEmail`, `BuildRecoveryEmail`, `BuildConfirmationEmail`, and `BuildSessionsRevovedEmail` all do `baseURL + "/path"`. So `BASE_URL=https://www.opencircuitsf.com/` yields `https://www.opencircuitsf.com//login`.

Production's value has no trailing slash, which is the only reason this is latent. But `BASE_URL` is operator-supplied in `/etc/opencircuit/config.env`, a trailing slash is the single most common way to write a base URL, and the failure is silent — the links still resolve on most servers while looking wrong in a security email, and `og:url`/sitemap `<loc>` values would carry the doubled slash into indexed pages.

`#0072` already established that `BASE_URL` drives canonical URLs, `og:image`, sitemap entries and `robots.txt`, so the blast radius is wider than email.

## 2. `TestNoRenderedBodyContainsCTAToken` only catches the token it knows

The guard matches `{{cta}}` specifically, so an unknown token like `{{nope}}` ships silently into a rendered body. A generic `{{…}}` check would cover the class rather than the instance.

Related, and inherent to every property test in that file: it iterates a fixed `allMessages()` of five, so a sixth `Build*Email` is not covered until someone remembers to add it there. The file's own doc comment says as much.

Neither is an injection risk — substitution precedes `html.EscapeString`.

## Acceptance criteria

- [ ] `BASE_URL` is normalised once, at config load, with any trailing slash stripped — not patched at each call site *(one slash only; see Review notes)*
- [x] A test asserts `https://example.com/` and `https://example.com` produce identical rendered URLs. **Mutation-proven** by removing the normalisation and watching it fail
- [x] Every existing consumer is confirmed to go through the normalised value: the four email builders, `internal/seo`'s canonical/`og:url`/`og:image`, the sitemap `<loc>` values, and `robots.txt`'s `Sitemap:` line
- [x] `TestNoRenderedBodyContainsCTAToken` matches a generic `{{…}}` pattern rather than one literal token, and fails on an unknown token — mutation-proven
- [x] A decision, recorded either way, on whether `allMessages()` can be made to enumerate builders automatically rather than by hand

## Notes

The trailing-slash fix belongs in `internal/config`, not in the callers — the whole point is that one place defines the value. `#0072` made the same argument about apex-versus-www: `internal/seo` was right to trust `BASE_URL`, and the template was the defect.

`#0076`'s reviewer also observed that `/login` emits `og:url` as the site root rather than `…/login`. That is plausibly deliberate — a staff route, excluded from the sitemap — but nobody has confirmed it. Recorded on `#0019` rather than here.

## Fix

**1. `BASE_URL` is normalised once, at config load.** Added
`normalizeBaseURL` in `internal/config/config.go` — a one-line
`strings.TrimSuffix(raw, "/")` — and routed `Config.BaseURL` through it
instead of the bare `os.Getenv("BASE_URL")`. Every caller downstream of
`cfg.BaseURL` (traced in `cmd/opencircuit/main.go`, read-only, not edited —
that file is another subagent's lane) now receives the clean value without
any per-call-site patch:

- `internal/auth/mailer.go`'s `NoOpMailer.BaseURL` → `verificationURL`,
  `recoveryURL`
- `internal/auth/ses_mailer.go`'s `SESMailer.baseURL` (set from `cfg.BaseURL`
  in `NewSESMailer`/`NewSESMailerWithSender`) →
  `mailing.BuildRegistrationEmail`, `BuildRecoveryEmail`,
  `BuildSessionsRevokedEmail`
- `internal/handlers.NewSubscribeHandler(..., cfg.BaseURL, ...)` →
  `mailing.BuildConfirmationEmail`, `BuildAlreadySubscribedEmail`
- `internal/seo.NewSite(indexHTML, cfg.BaseURL, nil)` → `NewRenderer`
  (canonical/`og:url`/`og:image`), `NewSitemap` (sitemap `<loc>`),
  `BuildRobotsTxt` (`Sitemap:` line)

`internal/seo`'s own `strings.TrimSuffix(baseURL, "/")` calls inside
`NewRenderer`, `NewSitemap`, and `BuildRobotsTxt` (predating this issue) were
left in place as a harmless, now-redundant second normalisation rather than
removed — see `## Gotchas`.

**2. `TestNoRenderedBodyContainsCTAToken` now matches any `{{…}}` token.**
Replaced the literal `strings.Contains(msg.X, ctaToken)` checks in
`internal/mailing/templates_test.go` with a package-level
`unresolvedTemplateToken = regexp.MustCompile(`+"`"+`\{\{[^{}]*\}\}`+"`"+`)`
and `FindString` calls that report the actual leaked token in the failure
message, not just the one the test happened to be looking for.

**3. `allMessages()` enumeration decision: not automatable by invocation,
but made self-checking.** Go has no runtime reflection over a package's own
top-level function declarations, so `allMessages()` cannot be made to
*call* a newly added `Build*Email` function without a code-generation step —
more machinery than five (soon six) functions justifies. Added
`TestAllMessagesEnumeratesEveryBuildEmailFunc`, which parses the package's
own non-test source with `go/parser`, counts exported top-level
`Build*Email` function declarations, and asserts that count equals
`len(allMessages())`. This turns "forgot to wire the sixth builder into
`allMessages()`" from a silent gap (per the file's own doc comment) into a
named test failure.

## Gotchas

  their own local `strings.TrimSuffix(baseURL, "/")` before this fix (visible
  at `internal/seo/seo.go:136`, `internal/seo/sitemap.go:55`,
  `internal/seo/robots.go:25`). Config-level normalisation makes those calls

## Review notes — 2026-08-19 (phase 3, bounced)

One blocker. Everything else in this issue was independently re-verified and
holds; the list below records what does **not** need redoing.

### Blocker — `normalizeBaseURL` strips one slash, so the reported failure survives

`strings.TrimSuffix(raw, "/")` removes exactly one trailing slash. Probed
through `normalizeBaseURL` directly and end-to-end through `loadFromFile`
against a real `.env`:

| `BASE_URL` | `cfg.BaseURL` | `+ "/login"` |
|---|---|---|
| `https://x.com/` | `https://x.com` | `https://x.com/login` ✅ |
| `https://x.com//` | `https://x.com/` | `https://x.com//login` ❌ |
| `https://x.com///` | `https://x.com//` | `https://x.com///login` ❌ |
| `https://x.com/base/` | `https://x.com/base` | `https://x.com/base/login` ✅ |
| `https://x.com/base//` | `https://x.com/base/` | `https://x.com/base//login` ❌ |
| `/` | `` (empty) | fails the required-field check |
| `` (empty) | `` | fails the required-field check |
| `  https://x.com/  ` | unchanged by the function; **godotenv trims it first**, so the `.env` path yields `https://x.com` |

`//login` is the exact string this issue was filed about, and
`BASE_URL=https://x.com//` still produces it. Two things make that a bounce
rather than a follow-up:

1. The acceptance criterion says **any** trailing slash stripped. One is
   stripped.
2. `normalizeBaseURL`'s own doc comment declares itself "the single
   normalisation point for BASE_URL" whose consumers "trust this value to
   already be clean". That contract is not delivered for a doubled slash, and
   it is the kind of overstated comment `#0086` item 3 exists to correct.
   `internal/seo`'s three redundant `TrimSuffix` calls are one-slash too, so
   nothing downstream compensates.

It is also internally inconsistent with this issue's own part 2, which argues
explicitly for covering "the class rather than the instance" — part 1 covers
only the instance.

**Fix:** `strings.TrimRight(raw, "/")`, one identifier, plus a
`https://example.com//` case in `TestLoad_BaseURLTrailingSlashNormalised`.
Re-check the two boundary values it changes: `/` and `//` both collapse to
`""`, which the required-field check already rejects (note the message will
say "missing required variable BASE_URL" for a `BASE_URL=/` that *is* set —
acceptable, arguably an improvement, worth a sentence in `## Gotchas` either
way). No realistic base URL ends in a run of slashes, so there is no case
`TrimRight` breaks that `TrimSuffix` handles.

Whitespace is **not** part of this: `godotenv` trims it on the `.env` path
(verified) and systemd's `EnvironmentFile` does the same, so it never reaches
`normalizeBaseURL` in practice. No change wanted there.

### Verified, do not redo

- **Consumer trace is complete and correct.** `os.Getenv("BASE_URL")` appears
  exactly once in the tree (`internal/config/config.go:106`); nothing
  re-reads it. Every listed consumer traces to `cfg.BaseURL`:
  `cmd/opencircuit/main.go:122` → `auth.NoOpMailer.BaseURL`;
  `internal/auth/ses_mailer.go:57` → `SESMailer.baseURL` →
  `BuildRegistrationEmail` / `BuildRecoveryEmail` / `BuildSessionsRevokedEmail`;
  `main.go:163` → `handlers.NewSubscribeHandler` → `BuildConfirmationEmail` /
  `BuildAlreadySubscribedEmail`; `main.go:573` → `seo.NewSite` → `NewRenderer`
  (canonical, `og:url`, and `og:image` at `seo.go:224`/`241` as
  `baseURL + "/og-default.png"`), `NewSitemap` (`<loc>`), and `BuildRobotsTxt`
  (the `Sitemap:` line). All five email builders concatenate `baseURL + "/…"`
  directly, as claimed.
- **The generic `{{…}}` check is correctly scoped and will not bite
  admin-authored content.** `TestNoRenderedBodyContainsCTAToken` iterates
  `allMessages()`, a hard-coded map of the five transactional builders called
  with test-owned inputs (`testTo`, `testBaseURL`, …). No campaign or
  workshop content exists in `internal/mailing` yet, and none flows through
  this test. When `#0043`/`#0047` land, the only exposure is a *test fixture*
  that deliberately contains `{{` — a one-line fixture change, not a
  production failure. Worth knowing rather than acting on: `\{\{[^{}]*\}\}`
  does not match nested braces (`{{ {a} }}`).
- **`TestAllMessagesEnumeratesEveryBuildEmailFunc` has no false positives.**
  Probed all four vectors; each left the test green: a `Build*Email` declared
  in a `_test.go` file (excluded by the `ParseDir` filter), a **method**
  `Build*Email` on a type (`fn.Recv != nil` skip), an unexported
  `buildProbeCEmail` (the `^Build…` regex), and an exported `Build*Email` in a
  sibling subpackage (`ParseDir` reads `"."` only). The control — an exported
  top-level `BuildProbeEEmail` absent from `allMessages()` — fails with
  exactly the reported message.
- Suites: `go build ./...` and `go vet ./...` clean; `go test ./... -count=1`
  with `TEST_DATABASE_URL` exported green across all thirteen packages, zero
  failures and zero skips. `f8624a1` touches only its three declared files.
  `migrations/` byte-identical to `HEAD`; no throwaway migration left behind.

### Follow-ups, not blockers

- **The enumeration guard compares counts, not identities.** Proved: add an
  exported `BuildProbeFEmail` to `transactional_templates.go` *and* a second
  `allMessages()` entry pointing at an existing builder, and the test is green
  while the new builder is still uncovered. It also keys off the
  `Build…Email` naming convention, so a future `BuildWorkshopReminder` (no
  `Email` suffix) or `Build_Foo_Email` is invisible to it. Comparing the found
  names against a `map[string]string` of builder-name → `allMessages()` key
  would close both; the recorded decision is still sound as far as it goes.
- **`#0043`'s campaign builder will be forced into `allMessages()`** by this
  guard the moment it lands, which will subject it to the transactional
  property tests (unsubscribe-footer, CTA-wording, no-`{{…}}`) that may not
  all apply to campaign mail. Decide there whether to split the map or relax
  the guard — do not weaken it by reflex.
