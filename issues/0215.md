## Description

`internal/auth/registration_test.go` calls `setRegistrationsEnabled` **seven
times with no `t.Cleanup` anywhere in the file**. `#0132`'s phase-3 review
demonstrated the leak: the setting reads `false` before and `true` after
`go test ./internal/auth/`.

Every DB-backed package shares one physical `TEST_DATABASE_URL`, so this is not
confined to `internal/auth`.

**It has already cost a full implementation pass.** `#0132`'s first fix
snapshotted the live `settings` table from `TestMain` and reseeded from the
snapshot. That passed every scoped run *and* two `-shuffle=on` runs, and failed
only under the full `./internal/...` suite — because the snapshot captured
`internal/auth`'s leaked `true` as though it were canonical. The approach was
sound; the polluted table made it look broken, and it was rewritten.

**It also silently props up a verification claim.** `#0132`'s criterion that
`settings` matches `opencircuit_test_template` after a full `./internal/...` run
holds **only because `internal/handlers` happens to run after `internal/auth`**
and resets the table on its way through. Reorder the packages and that check
stops meaning what it says.

`#0130` fixed a different leak of this same key — `TestAudit_SettingsUpdated`,
in `internal/handlers`. This one is untouched, and the fix is the same shape: a
`t.Cleanup` in the helper.

## Acceptance criteria

- [ ] `setRegistrationsEnabled` restores the prior value, via `t.Cleanup` in the helper rather than at each of the seven call sites
- [ ] After `go test ./internal/auth/`, `registrations_enabled` reads what it did before — demonstrated by measuring the value on both sides, not by inspection
- [ ] The `settings` table is byte-identical to `opencircuit_test_template` after `go test ./internal/auth/` **alone**, without relying on another package running afterwards
- [ ] A test proves the restore happens even when the test that changed the setting **fails** — `t.Cleanup` runs on failure, skip and panic, and that is the property being bought
- [ ] `#0130`'s fix to the `internal/handlers` leak still holds
- [ ] `ISSUE=0215 scripts/check.sh go ./internal/...` passes with zero skips, and the `settings` table matches the template afterwards

## Implementation notes

Confirmed the leak first, before touching code, exactly as described: on a
private database (`opencircuit_test_0215`, created via `scripts/testdb.sh
create 0215`), set `registrations_enabled='false'`, ran `go test
./internal/auth/`, queried again — `true`. Matches `#0132`'s review finding.

**Fix, in the helper (`setRegistrationsEnabled`,
`internal/auth/registration_test.go`), not at the seven call sites** — same
shape as `#0130`'s fix to the sibling leak in
`internal/handlers/audit_seams_test.go`. Before writing the requested value,
the helper reads the row's current value (`pgx.ErrNoRows` handled explicitly
for a table with no matching row) and registers a `t.Cleanup` that restores
either that prior value or the row's absence. `t.Cleanup` was used rather
than a deferred restore in the test body specifically for criterion 4: a
plain `defer` in the test function wouldn't cover a later `t.Fatalf` inside a
different helper the test calls afterward, whereas `t.Cleanup` still runs.

**Four-probe proof of the failure/skip property**, matching the arrangement
`#0165`'s review used for the same claim about a different helper. Ran as a
throwaway test file (`internal/auth/probe_0215_test.go`, deleted after,
never committed) against the private database, `go test ./internal/auth/
-run 'TestProbe0215' -v -count=1`:

| Probe | Action | Result |
|---|---|---|
| A | `setRegistrationsEnabled(t, pool, true)` then `t.Fatal` | `--- FAIL` |
| B | `setRegistrationsEnabled(t, pool, true)` then `t.Skip` | `--- SKIP` |
| C | asserts `registrations_enabled` still `false` on entry, then sets it | `--- PASS` |
| D | same assertion, after C | `--- PASS` |

C and D both found the setting at its pre-A baseline (`false`) on entry —
A's and B's cleanups fired despite one failing and one skipping.

**Two optional hardenings from `#0132`'s review — skipped.** Both live in
`internal/handlers` (the regex anchor and the `settingsMigrationsDir` note),
outside this issue's `internal/auth/` scope, and another agent's `#0120`
review is active in this working copy concurrently. Reported rather than
taken, per the issue's own instruction to skip if it means touching that
package while its work is settling.
