## Description

`internal/auth/registration_test.go` calls `setRegistrationsEnabled` **seven
times with no `t.Cleanup` anywhere in the file**. `#0132`'s phase-3 review
demonstrated the leak: the setting reads `false` before and `true` after
`go test ./internal/auth/`.

Every DB-backed package shares one physical `TEST_DATABASE_URL`, so this is not
confined to `internal/auth`.

**It has already cost a full implementation pass.** `#0132`'s first fix
snapshotted the live `settings` table from `TestMain` and reseeded from the
snapshot. That passed every scoped run *and* two `-shuffle=on` runs, and failed
only under the full `./internal/...` suite — because the snapshot captured
`internal/auth`'s leaked `true` as though it were canonical. The approach was
sound; the polluted table made it look broken, and it was rewritten.

**It also silently props up a verification claim.** `#0132`'s criterion that
`settings` matches `opencircuit_test_template` after a full `./internal/...` run
holds **only because `internal/handlers` happens to run after `internal/auth`**
and resets the table on its way through. Reorder the packages and that check
stops meaning what it says.

`#0130` fixed a different leak of this same key — `TestAudit_SettingsUpdated`,
in `internal/handlers`. This one is untouched, and the fix is the same shape: a
`t.Cleanup` in the helper.

## Acceptance criteria

- [x] `setRegistrationsEnabled` restores the prior value, via `t.Cleanup` in the helper rather than at each of the seven call sites
- [x] After `go test ./internal/auth/`, `registrations_enabled` reads what it did before — demonstrated by measuring the value on both sides, not by inspection
- [x] The `settings` table is byte-identical to `opencircuit_test_template` after `go test ./internal/auth/` **alone**, without relying on another package running afterwards
- [x] A test proves the restore happens even when the test that changed the setting **fails** — `t.Cleanup` runs on failure, skip and panic, and that is the property being bought
- [x] `#0130`'s fix to the `internal/handlers` leak still holds
- [x] `ISSUE=0215 scripts/check.sh go ./internal/...` passes with zero skips, and the `settings` table matches the template afterwards

## Implementation notes

Confirmed the leak first, before touching code, exactly as described: on a
private database (`opencircuit_test_0215`, created via `scripts/testdb.sh
create 0215`), set `registrations_enabled='false'`, ran `go test
./internal/auth/`, queried again — `true`. Matches `#0132`'s review finding.

**Fix, in the helper (`setRegistrationsEnabled`,
`internal/auth/registration_test.go`), not at the seven call sites** — same
shape as `#0130`'s fix to the sibling leak in
`internal/handlers/audit_seams_test.go`. Before writing the requested value,
the helper reads the row's current value (`pgx.ErrNoRows` handled explicitly
for a table with no matching row) and registers a `t.Cleanup` that restores
either that prior value or the row's absence. `t.Cleanup` was used rather
than a deferred restore in the test body specifically for criterion 4: a
plain `defer` in the test function wouldn't cover a later `t.Fatalf` inside a
different helper the test calls afterward, whereas `t.Cleanup` still runs.

**Four-probe proof of the failure/skip property**, matching the arrangement
`#0165`'s review used for the same claim about a different helper. Ran as a
throwaway test file (`internal/auth/probe_0215_test.go`, deleted after,
never committed) against the private database, `go test ./internal/auth/
-run 'TestProbe0215' -v -count=1`:

| Probe | Action | Result |
|---|---|---|
| A | `setRegistrationsEnabled(t, pool, true)` then `t.Fatal` | `--- FAIL` |
| B | `setRegistrationsEnabled(t, pool, true)` then `t.Skip` | `--- SKIP` |
| C | asserts `registrations_enabled` still `false` on entry, then sets it | `--- PASS` |
| D | same assertion, after C | `--- PASS` |

C and D both found the setting at its pre-A baseline (`false`) on entry —
A's and B's cleanups fired despite one failing and one skipping.

**Two optional hardenings from `#0132`'s review — skipped.** Both live in
`internal/handlers` (the regex anchor and the `settingsMigrationsDir` note),
outside this issue's `internal/auth/` scope, and another agent's `#0120`
review is active in this working copy concurrently. Reported rather than
taken, per the issue's own instruction to skip if it means touching that
package while its work is settling.

## Review notes — 2026-08-23 (phase 3, approved)

Re-verified independently from the diff at `7c7182e`, not from the
implementer's `## Verification`. Machine idle throughout — `uptime` reported
load averages 1.69–3.14 at the head of every run, far under the ~8 threshold
at which §5 says a timing result stops meaning anything. Every run below used
a private database cloned from `opencircuit_test_template`
(`scripts/testdb.sh create`), and the pre-fix control ran from a detached
worktree at `7c7182e^` rather than from a stash (§8a).

**Two hashes, because the fix restores `value` but not `updated_at`.**
Throughout, `kv` is `SELECT key||'='||value FROM settings ORDER BY key |
shasum -a 256`; `full` adds `updated_at`.

**Criterion 3 — `go test ./internal/auth/` ALONE, `-count=1`.** Stated
explicitly because `#0132`'s reviewer found a cached run made exactly this
check dishonest: every run in these notes passed `-count=1`, and none reported
`(cached)`.

| | `kv` hash | `registrations_enabled` |
|---|---|---|
| `opencircuit_test_template` | `e4a01861306665ec3389a4854d92118ee702d5bb2c21e0c78ed7a9cb50bb8f46` | `false` |
| own DB, before | `e4a01861…bb8f46` | `false` |
| own DB, after (`ok … 0.697s`) | `e4a01861…bb8f46` | `false` |

Byte-identical to itself **and** to the template on `(key, value)`, with no
other package running afterwards to launder the result.

**The pre-fix control, which is what makes the above mean anything.** Same
measurement against a second private database from a worktree at `7c7182e^`:

| | `kv` hash | `registrations_enabled` |
|---|---|---|
| before | `e4a01861…bb8f46` | `false` |
| after (`ok … 0.779s`) | `04d3efe537d59996a82fadcc39ff668be20654f8f63e39ef25b0b87255406e1c` | **`true`** |

The leak was real and the harness detects it. A before/after that only ever
comes back clean would have proved nothing.

**`updated_at` is the one thing not restored, and it is deliberate to
accept.** The `full` hash does move: template `555f2c3c…83e7e2` → after
`fbac46c8…157976`, differing on exactly one field —
`registrations_enabled`'s `updated_at`, `15:16:06.208129` → `15:41:59.622098`.
The restore's `ON CONFLICT DO UPDATE … updated_at = now()` stamps a fresh
timestamp even when it writes back an unchanged value. Read strictly,
criterion 3's "byte-identical" is met on `(key, value)` and not on
`updated_at`. Judged acceptable, not a bounce, for three reasons: nothing
reads an *absolute* `settings.updated_at` anywhere in the tree — the only
consumer, `internal/handlers/settings_test.go`'s `settingUpdatedAt`, is used
purely relatively (`after.After(before)` in
`TestAdminSettings_PatchUpdatesRow`); the pre-fix helper bumped the timestamp
too, so this is a reduction in leakage, not a regression; and `#0130`, the
sibling fix this one is shaped after, established `(key, value)` as the
comparison. Preserving the prior `updated_at` alongside the prior value would
close it for a few characters — reported to the orchestrator as a possible
follow-up, not required here.

**Criterion 4 — the four-probe arrangement, rebuilt and re-run.** The
implementer's probe file was deleted, and a deleted probe is not evidence, so
it was reconstructed independently (as `probe_0215rev_test.go` inside a
throwaway worktree at `7c7182e`, against a third private database, `-count=1
-v`) and extended with edge-case probes:

```
--- FAIL: TestProbe0215revA_Fatal      PROBE A entry: value="false" present=true
--- SKIP: TestProbe0215revB_Skip       PROBE B entry: value="false" present=true
--- PASS: TestProbe0215revC_Observe    PROBE C entry: value="false" present=true
--- PASS: TestProbe0215revD_Observe    PROBE D entry: value="false" present=true
--- PASS: TestProbe0215revE_NoRow      entry after delete: present=false → after helper: value="true"
--- PASS: TestProbe0215revF_NoRowObs   PROBE F entry: value="" present=false
--- PASS: TestProbe0215revG_Repeated   entry "false"; three calls; before cleanup "true"
--- PASS: TestProbe0215revH_RepeatedObs PROBE H entry: value="false" present=true
```

C and D both found `false` on entry — A's cleanup fired despite A failing, and
B's despite B skipping. **The panic leg was checked too**, which the
implementer's table did not cover although the helper's doc comment claims it:
a separate single-test run panicked with `registrations_enabled='true'`
(`panic: … [recovered, repanicked]`), and a query from a fresh process
afterwards read `false`. `testing` recovers, runs cleanups, then re-panics, so
the claim holds.

**Edge cases probed, since the helper now reads-then-restores.**

- *The row that never existed.* Probe E deleted the row, called the helper
  (which then read `pgx.ErrNoRows`, set `hadRow=false`, and wrote `true`);
  probe F found the row **absent** again, not resurrected at a default. The
  `ErrNoRows` branch is correct.
- *Nested / repeated calls.* Probe G called the helper three times in one test
  (`true`, `false`, `true`); probe H found the **original** `false`, not an
  intermediate. This is `t.Cleanup`'s LIFO ordering doing the work: each call
  snapshots the value it sees, and the cleanups unwind outermost-last, so the
  first call's snapshot — the true original — is what lands. It matters
  because the fix is in the helper rather than at the call sites, so repeated
  calls are structurally possible; it happens to be safe.
- *Concurrency.* The read-then-write is not atomic, but there is no window
  today, and the lock is genuinely why. `internal/testdb.Lock()` takes a
  session-level advisory lock from every DB-backed package's `TestMain`, so
  only one package's test binary touches a given database at a time — checked
  in `internal/testdb/testdb.go`, not assumed. Within the package, `grep
  't.Parallel()' internal/auth/` returns **zero** hits, so no two tests in
  `internal/auth` interleave either. Two caveats worth knowing rather than
  fixing: the lock is scoped to the database `TEST_DATABASE_URL` names, so it
  protects nothing against a non-`TestMain` writer on the same database; and
  adding a single `t.Parallel()` to `internal/auth` would open the window —
  precisely the hazard the declined `settingsMigrationsDir` note flags one
  package over.

**The fix is broader than the criteria say, in a good way.** The issue counts
"seven" call sites; that is the count inside `registration_test.go` alone.
`grep` finds **30** calls to `setRegistrationsEnabled` across six files in the
package (`login_test.go` 12, `logout_all_test.go` 7, `registration_test.go` 7,
`relying_party_test.go` 3, `audit_seams_test.go` 1, `recovery_test.go` 1).
Fixing the helper covers all thirty; fixing seven call sites would have left
twenty-three leaking. The chosen shape is the right one.
