## Description

`#0466` fixed the **precondition prose** in three prepared instructions so each
tells the user to bring a file to the box before consuming it. It did not
address the underlying state, and `#0435`'s reviewer said so plainly: this is a
standing production-state defect that will keep generating the same class of
finding.

Measured read-only:

- `/opt/opencircuit` is at `ef0a58f` (`#0274`), roughly **719 commits behind**
  `main` — the figure was 711 at filing, 716 hours later, 719 at review, which
  is itself the reason `#0466` chose "several hundred" over a number.
- Its working tree is **dirty**: `M web/dist/index.html`.
- `/home/ec2-user/OpenCircuitSF` is a different repository entirely — HEAD
  `6e7af65` "adds placeholder website".

## Why it is worth its own issue

Every instruction of the form *"install this file from the repo"* has to carry
its own workaround. Three already do. The next one will too, and each
workaround is a place for the kind of error `#0466` and `#0435` both caught —
`#0465`'s `sudo cp` would have **succeeded silently** with a stale unit.

There is also a second-order fact worth settling: the dirty `web/dist/index.html`
is exactly what `CLAUDE.md` §8b warns about, where `./scripts/dev.sh --built`
overwrites the tracked placeholder. On the **production** checkout that means a
`git pull` will either conflict or need the file restored first, and whoever
runs the next deploy meets that.

## What this issue is not

**Not a request to deploy.** Bringing the checkout current is a step in the
user's own deploy, and the binary and SPA rebuild that follows is theirs to run.
This issue is about deciding and recording how the box's checkout is kept
current, so instructions stop carrying private workarounds.

## Acceptance criteria

1. **Re-derive the state yourself** — both checkouts, the commit gap, and the
   dirty file. Do not copy the figures above; three different values for the gap
   have already been recorded in one day.
2. Decide and record how the checkout is brought current, and by whom. The
   options already surfaced: a `git pull` as the first step of a deploy, a
   targeted `scp` per instruction (what `#0466` chose, for reasons that are
   sound *given* the staleness), or something else. **State the trade rather
   than picking by habit.**
3. Say what happens to the dirty `web/dist/index.html` on a pull, and record the
   safe restore — `CLAUDE.md` §8b gives it as `git show HEAD:… > …`, explicitly
   **not** `git checkout --`, which §8a forbids.
4. Establish whether `/home/ec2-user/OpenCircuitSF` is still needed at all, or
   is an artefact of the pre-deploy placeholder era. **Do not delete anything**
   — record the answer and let the user decide.
5. **Nothing runs on the box** without the user's approval (§5b, §9). This is
   preparation and a recommendation.
6. Once decided, check whether `#0466`'s per-instruction preconditions should be
   simplified — but **do not remove them** unless the checkout is actually
   current, and say so.

  All three edits are in `docs/deployment.md`'s "Redeploy procedure", and no
  other file changes. This is transcription, so it stays on Sonnet (§3).

  `git status --porcelain` in the first fenced block, and in the second fenced
  block's trailing comment line.

  **(b)** In block 1, after the existing `git show HEAD:…` fenced block, add:

      A tracked file the checkout has modified shows as `M`, and the `git show`
      form above restores it. A file `scp`'d in that this checkout does not
      track yet shows as `??` — the `git show HEAD:… >` form cannot restore it
      (`fatal: path '…' exists on disk, but not in 'HEAD'`). Remove it instead

      ```bash

      ```
