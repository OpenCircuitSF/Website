## Description

`#0305` added `imported_30d` so import-driven growth stops being invisible, and
`net_30d` became `confirmed_30d + imported_30d - unsubscribed_30d`. That is
correct as far as it goes, and `#0305`'s review verified the predicate is exact
against every subscriber status and that the two positive buckets are mutually
exclusive, so nothing double-counts on the way *in*.

**But `imported_30d` is a current-state count while its two siblings are event
counts.** Its predicate is `status='active' AND confirmed_at IS NULL AND
created_at >= since` — the `status='active'` clause means a subscriber who
leaves stops being counted, retracting their own `+1`, *and* is counted again by
`unsubscribed_30d`.

Measured by `#0305`'s reviewer in a rolled-back transaction on a scratch
database:

| Step | `net_30d` |
|---|---|
| baseline | 1 |
| after import | 2 |
| after that subscriber unsubscribes | **0** |

So someone who joined and left inside the window contributes **−1**. A locally
confirmed subscriber correctly nets 0, because `confirmed_at` is never cleared —
the asymmetry is entirely in the stock-versus-event mismatch.

**`ImportStore.Revoke` (`#0125`) makes this reachable in bulk.** Revoking a
500-address import renders `net_30d = −500` on a list that is merely flat.

**This is not a regression.** The old code produced the identical end state and
never showed the `+1` at all, so `#0305`'s formula is no worse in any case and
better in most — which is why its review resolved rather than bounced.

## The doc comment is also describing a flow while measuring a stock

`Growth30Days`'s comment says imported subscribers "landed active via an import
… since that time". Today it describes an event and measures a current state.
The fix below makes the sentence literally true.

**Predicate.** `internal/subscribers.Store.Growth30Days`'s `imported` count is

**Not the issue's literal suggested form.** The issue's "natural form" was
`created_at >= since AND source = 'import'` alone. Implemented with an added
`confirmed_at IS NULL` guard instead, because `source` is never rewritten
after INSERT (`#0317`), so a committed IMPORT INVITE that is later accepted
within the same window keeps `source='import'` even after `Confirm` sets its
`confirmed_at` — without the guard it would count in both `imported_30d` AND
`confirmed_30d` for the same join, double-counting one new subscriber as two.
`confirmed_at IS NULL` is exactly the test that already defines "confirmed"
for the first return value, so the two buckets stay mutually exclusive on the
way in — `#0305`'s reviewer-verified invariant (criterion 4/5) — while still
being a pure event count, independent of `status`, on the way out: nothing a
row does later (unsubscribe, get bulk-revoked, bounce) changes whether it was
counted here, which is what actually fixes the double-subtraction. Read
`#0317` first, per the batch's instruction — its "Source is historical
provenance, never rewritten" finding is what makes this guard correct rather
than an unrelated afterthought.

### The override of criterion 1 was right, and the claim it rests on holds

Criterion 1 proposed `created_at >= since AND source = 'import'` alone. The
implementer added `AND confirmed_at IS NULL`, arguing that without it an
accepted import *invitation* would be counted in `imported_30d` **and** in
`confirmed_30d` for the same join. That reasoning is sound and its premise is
verified:

- **`source` is never rewritten.** Every `UPDATE subscribers` in the tree was
  enumerated (`internal/subscribers/store.go` ×11, `pending.go` ×2,
  `imports.go` ×1, plus test-only fixtures); none has `source` in its `SET`
  list. `RestartSignup`'s eleven-column `CASE`-per-column `UPDATE`
  (`store.go:1209`) touches `confirmed_at` and `import_id` and leaves `source`
  alone. No migration backfills it either. So an invite row keeps
  `source='import'` forever, including after `Confirm` stamps `confirmed_at`.
- **The guard preserves `#0305`'s mutual-exclusivity invariant.**
  `confirmed_30d` is `confirmed_at >= since`; `imported_30d` now requires
  `confirmed_at IS NULL`. The two predicates are disjoint on the same column,
  by construction rather than by argument, so no row can be in both.
- **It is still a genuine event count.** `Unsubscribe`, `Revoke`, and the
  bounce/complaint paths never touch `confirmed_at`, so nothing a row does
  after being counted removes it from the bucket — which is the whole point of
  the issue. Measured, not inferred (below). The one writer that *does* clear
  `confirmed_at` is `RestartSignup`, and for a `source='import'` row that is
  self-cancelling: the row leaves `confirmed_30d` and re-enters `imported_30d`
  in the same statement, so `net_30d` is unchanged.

Without the guard, an invite sent and accepted inside one window would read as
two joins for one person. Criterion 1's literal form was wrong; the
implementation is right.

### Two follow-ups to file (reported, not filed — CLAUDE.md §9)

**(a) An unaccepted import invitation now counts as growth.** This is a
behaviour change introduced by this commit, and it reverses a decision
`#0305`'s own review recorded and justified ("a pending invite-mode row is not
growth — deliberate; an invitation is not an accepted subscription").
Invite-mode `Commit` inserts `status=pending, source='import',
confirmed_at NULL`, so it now matches the predicate the moment the invitation
is *sent*. Measured on both predicates, same code path, same database:

| Scenario (invite mode) | parent predicate | this commit | truth |
|---|---|---|---|
| 1 invite sent, nobody accepts | net **0** | net **+1** | 0 |
| same invite expires (`ExpirePendingSweep` leaves the row `pending`) | net **0** | net **+1**, permanently in-window | 0 |
| invite accepted | +1 (via `confirmed`) | +1 (via `confirmed`) | +1 |
| invite batch revoked while pending | net **−1** | net **0** | 0 |

So a 500-address invite import reads as `+500` growth before a single
acceptance, and stays there after every invitation expires. The commit is a net
improvement — it fixes the revoke case, which the old predicate got wrong in
the other direction — but this half is new and wrong.

The remedy is **not** a one-clause change, which is why it is a follow-up
rather than a bounce: adding `AND consent_basis IS NOT NULL` restores the
invite exclusion and keeps every `prior_consent` fix intact, but it also
restores `−N` on a revoked pending-invite batch, because
`ImportStore.Revoke` stamps `unsubscribed_at` on rows that were never active.
Whether a revoked (or expired) unaccepted invitation is a *departure* at all is
a real design question about `unsubscribed_30d`, not about `imported_30d`. Also
worth a line in that issue: `formatGrowthDetail`'s new wording ("addresses an
import batch placed on the list") is inaccurate for an invitation, which was
asked and not placed.

**(b) `RestartSignup` clearing `confirmed_at` drops a confirmation that
already happened.** Pre-existing (not from `#0129` or this issue), different
mechanism, and I judge it **worth filing** — the implementer was right to flag
it and right not to fix it here. Measured, ordinary website signup, all inside
one window:

| Step | `confirmed` | `unsubscribed` | `net_30d` |
|---|---|---|---|
| after `Confirm` | 1 | 0 | +1 |
| after `Unsubscribe` | 1 | 1 | 0 |
| after `RestartSignup` | **0** | 1 | **−1** |

The reason to file rather than leave it as a code comment: the end state is
**persistent, not transient**. `RestartSignup` never clears `unsubscribed_at`,
so if the person abandons the new confirmation email (or it expires), the row
sits at `−1` for the rest of the window — a departure counted with no
matching arrival, which is the same family as this issue. It needs no admin
action: unsubscribe, re-enter your address on the public form, ignore the
email. Magnitude is one row per person rather than bulk, which is why it is a
follow-up and not a bounce. Note it is self-cancelling for `source='import'`
rows (they move into `imported_30d`), so it only bites ordinary signups.

Both remaining defects live in the same predicate block, so folding them into
one issue is defensible; I would keep (a) separate if the record of "introduced
by `3c9eaf8`" matters more than the saved cycle.
