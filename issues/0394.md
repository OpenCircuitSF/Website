### The timing problem is genuinely gone, not relocated

`Counts` scans into `*float64` and converts with `int64(*oldestSecs)`, which
**truncates toward zero**. The target row's `created_at` is `now() -
targetAgeSecs` at UPDATE time, so the reported value is
`trunc(targetAgeSecs + Δ)` with `Δ ≥ 0` — wall-clock only moves forward.
Therefore `OldestQueuedAgeSecs >= targetAgeSecs` is **arithmetically
unfalsifiable by load**: no amount of machine load can drive it below the
lower edge. Nothing in the assertion is a real elapsed duration, and no
constant is sized against query timing (criterion 6, CLAUDE.md §5). The upper
edge is the fixture's own 100000s separation, reachable only by 100000s of
drift. Observed value on every control run: exactly `5000`, i.e. `Δ` truncates
to zero.

### Finding 2 — the tolerance does rest on elapsed time

The reported value is `extract(epoch FROM now() - created_at)`, and
`created_at` is set to `now() - targetAgeSecs` **at UPDATE time**. So the
reported age is `targetAgeSecs + (T_counts - T_update)`, and that second term
is genuine wall-clock time spanning **nine** database round trips — four
`Enqueue`s, four `UPDATE`s and the `Counts` call. The tolerance is the headroom
that term consumes.

The test's doc comment states that its tolerance "covers only the round trip
... not machine load", and that "this test's running time does not depend on
machine load". The second claim is true and the first is not the same claim:
running time is not the risk, **headroom** is, and nine round trips are
precisely what a loaded machine stretches. §5 records this project closing five
issues against timing failures at load averages near 320, where a local
`TRUNCATE` exceeded five seconds. A five-second budget for nine round trips is
a constant sized against expected query timing — the anti-pattern criterion 6
names.

Measured on an idle machine (load 3.2–7.8) the drift is **0 seconds**, three
runs out of three, so nothing fails today. This is a latent defect and a
misleading comment, not a live failure.

**An exact equality assertion is achievable but is the wrong fix** — it would
be fragile in the opposite direction, since any drift reaching one whole second
would break `== targetAgeSecs`. The correct fix removes the constant entirely
by deriving both bounds from the fixture's **own signal separation**.

## Description

`outbox.Store.Counts` returns a sixth column beyond the five status counts:
`OldestQueuedAgeSecs`, built from a `min(created_at) FILTER` clause. **No test
asserts it.**

`#0390`'s review measured two independent mutations, each leaving
`internal/outbox` **fully green**:

- repointing the `FILTER` at the **abandoned** status rather than the queued one;
- **removing the `FILTER` entirely**, so the column reports the oldest row in
  any state.

So the admin delivery-health dashboard could report the oldest *abandoned*
row's age as "oldest queued age" and nothing in the tree would notice.

**This is the same family as `#0364`, `#0389` and `#0390`** — an assertion
passing for a reason that does not distinguish the thing it names, except here
the assertion is absent rather than weak. It sits in the **same query** those
issues have now hardened, and it is outside their five-column swap space
precisely because it is not one of the five counts.

**Unverified by the orchestrator.** The two mutations above are reported from
`#0390`'s review and have not been independently reproduced. Confirm them
before building on them, and correct this issue if they do not hold.

## Fix

Added `TestOutbox_Counts_OldestQueuedAgeSecs` to
`internal/outbox/store_test.go`, as a sibling of `TestOutbox_Counts` and
`TestOutbox_Counts_ReportsSkippedDistinctlyFromAbandoned` rather than folded
into either (the age column is a single scalar with no natural delta the
way the five counts have, so it needed its own before/after shape).

The test backdates one queued row to a precisely known age
(`targetAgeSecs`, computed as `before.OldestQueuedAgeSecs + 5000` so it is
guaranteed to become the new oldest queued row regardless of residue left
by earlier tests in this package — the table is truncated once in
`TestMain`, not between tests) and backdates one "poison" row per **other**
status — sending, sent, abandoned, skipped — to an age two orders of
magnitude larger (`poisonAgeSecs = targetAgeSecs + 100000`). Both are set
via a direct `UPDATE outbound_queue SET created_at = now() - ($n * interval
'1 second') ...`, the same technique
`TestOutbox_LatestByRecipients_ReturnsMostRecentPerRecipient` already uses
to backdate a row — **no `time.Sleep`, no real elapsed wait** (criterion 6).

A single assertion then checks `after.OldestQueuedAgeSecs` is within 5
seconds of `targetAgeSecs`. That tolerance covers only the round trip
between the `UPDATE`s and the following `Counts()` call, not machine load —
it is two orders of magnitude smaller than the gap to `poisonAgeSecs`, so it
cannot be satisfied by a `FILTER` that reports any of the poison rows'
status instead of `queued`, or by no `FILTER` at all (which reports the
oldest row in the whole table — one of the poison rows, since they are all
backdated further than the target).

Because a poison row exists for **all four** other statuses rather than
just `abandoned`, the same single assertion also detects the `FILTER`
repointed at `sending`, `sent`, or `skipped` — a stronger result than
criterion 3 asked for (it asks only that the sweep be run and reported, not
that every column be closed). See `## Verification` for the sweep table.

## The remedy's shape, from the review that found it

Same as `#0389`'s and `#0390`'s: **a moment where the measured quantity must be
attributable to the queued row and to nothing else.** Enqueue a row, let it age
past a measurable threshold, and assert the reported age tracks *that* row
while rows in other states are present and older or newer.

The discriminating property is the one `#0390` settled on: an **asymmetric**
window. If the queued row and an abandoned row are both present and the
assertion holds only when the age matches the queued one, relabelling the
filter cannot satisfy it. `#0390`'s own first attempt failed exactly because
its window moved two quantities by the same amount — see its `## Work log`.
