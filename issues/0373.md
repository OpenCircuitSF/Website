## Description

`#0369` replaced the hand-maintained `qualifiedSubscriberColumns` with
`deriveQualifiedColumns`, computed from `subscriberColumns`. That closed the
duplication that 500'd the admin subscribers list.

The derivation **splits on `,` and handles only single-argument wrapped calls.**
A multi-argument call in `subscriberColumns` — `coalesce(a, b)` — is
mis-derived.

**It fails loudly, not silently.** `#0369`'s reviewer probed it: the result is
`ERROR: syntax error at or near ")" (SQLSTATE 42601)`, caught by the new
`TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip`. So this is **low
priority** — the failure mode is a caught error at test time, not wrong data.

But the doc comment does not name the limit, and someone adding a `coalesce`
column would meet a SQL syntax error with no hint of the cause.

## Acceptance criteria

1. The doc comment names the unsupported shape — a multi-argument call — and
   says what happens (a SQL syntax error caught by the round-trip test), so the
   next reader diagnoses it in seconds rather than from the SQLSTATE.
2. **Do not "fix" the derivation** unless a multi-argument column is actually
   needed. §8's `#0258` case is six passes of building for a defect that had not
   fired, and three guard families this phase (`#0330`, `#0347`, `#0356`) ended
   by recording a limit rather than closing it. One sentence is the deliverable.
3. The claim is **re-verified**, not transcribed: reproduce the mis-derivation
   yourself and confirm the error text and that the round-trip test catches it.
   Five issues this phase received a wrong identifier because prose was
   transcribed as though measured.
4. The doc comment must not overstate in the other direction either — five
   issues bounced this phase for comments claiming more than the code delivers.
   Say what is unsupported; do not imply everything else is guaranteed.
5. Comment-only unless criterion 2's exception applies. Prove it structurally —
   parse both revisions with comments excluded and compare, with the tool proved
   falsifiable first and failing closed on empty input (**eight agents found
   genuine fail-opens in their own instruments over the last two days**).
6. `gofmt` stability (§8's smart-quote gotcha — this is a declaration doc
   comment).

## Premise re-verified (not transcribed)

`#0369`'s review already reproduced this once; re-measured it independently
rather than transcribing its output, per criterion 3.

Confirmed the derivation mechanism directly, in an isolated `git archive
HEAD` export (CLAUDE.md §8b — never the shared tree), with a one-off test
calling `deriveQualifiedColumns` on a small literal input:

```go
deriveQualifiedColumns("id, coalesce(a, b), foo_bar", "subscribers")
// => "subscribers.id, coalesce(subscribers.a), subscribers.b), subscribers.foo_bar"
```

The naive `strings.Split(cols, ",")` cuts `coalesce(a, b)` into two parts at
the inner comma; each half is independently "qualified", producing
mismatched parens (`coalesce(subscribers.a)` immediately followed by a
stray `subscribers.b)`).

Then reproduced the failure at the SQL layer, against a dedicated scratch
database (`opencircuit_test_0373mut`, provisioned by a real `migrate up`
through `000026`, created and dropped by me — never the shared database).
Appended `coalesce(email, email)` to `subscriberColumns` (an existing
two-argument call over an existing column, not a hypothetical one) plus a
matching throwaway `Scan` destination in `scanSubscriber` (so `GetByID`'s
column count still matches and the qualified/`List` path is isolated as the
one under test), then ran the existing round-trip test:

```
ISSUE=0373mut go test ./internal/subscribers/... \
  -run TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip -v
--- FAIL: TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip
    store_test.go:2545: List: subscribers: listing: ERROR: syntax error at
    or near ")" (SQLSTATE 42601)
```

Matches `#0369`'s own reproduction exactly: fails loudly, at test time, in

either this issue's prose or `#0369`'s.

## Fix

Added one doc-comment paragraph to `deriveQualifiedColumns`
(`internal/subscribers/store.go`) naming the unsupported shape and what
happens:

> #0373: it does NOT handle a multi-argument wrapped call such as
> coalesce(a, b) — the naive split on "," cuts through the inner comma and
> mis-derives it, which fails loudly rather than silently: Postgres rejects
> the resulting malformed SQL with a syntax error, caught at test time by
> TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip. subscriberColumns
> has never contained such a call.

No change to `deriveQualifiedColumns` itself, per criterion 2 — `#0369`'s
own review already judged the AST-guard alternative disproportionate for
this defect class, and `subscriberColumns` has never actually contained a
multi-argument call. The existing scope note ("a one-argument function call
such as host(signup_ip)") already only claimed support for the single-arg
shape; the new sentence names the negative space without implying anything
else is guaranteed beyond what the function already documented (criterion
4).

**Criterion 5 — comment-only, proved structurally, not by inspection.**
Built a standalone Go tool (`astdiff`, in the scratchpad, not part of this
repo) that parses two Go source files with `go/parser` in comment-excluding
mode, reformats each AST with `go/format`, and diffs the two textual
results — so a change confined to comments produces identical output and
anything else does not. It fails **closed**: an empty or unparseable input
file is refused outright as `PARSE_ERROR` (a non-zero exit), never silently
read as `AST_IDENTICAL`, addressing the "eight agents found genuine
fail-opens in their own instruments" note directly. Proved falsifiable
*before* trusting the real comparison, against three synthetic cases:

```
case 1 (comment-only diff)         -> VERDICT: AST_IDENTICAL  (exit 0)
case 2 (a real code change)        -> VERDICT: AST_DIFFERS    (exit 1)
case 3 (one file empty)            -> VERDICT: PARSE_ERROR    (exit 2)
```

Then ran it on the actual before/after `internal/subscribers/store.go`
(`git show HEAD:...` vs. the working tree):

```
VERDICT: AST_IDENTICAL (comment-only or no diff)
```

`gofmt -l` reports clean on the touched file, and `gofmt -w` followed by a
diff against the pre-format copy showed no change — the smart-quote/
backtick gotcha (CLAUDE.md §8, `#0210`) does not apply here since the added
comment contains no doubled `''` or backtick.

### The sentence, clause by clause

> #0373: it does NOT handle a multi-argument wrapped call such as coalesce(a, b)
> — the naive split on "," cuts through the inner comma and **mis-derives it**,
> which **fails loudly rather than silently: Postgres rejects the resulting
> malformed SQL with a syntax error**, **caught at test time by
> TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip**. **subscriberColumns
> has never contained such a call.**

**Clause 1 — "the naive split cuts through the inner comma and mis-derives it".**
True, and byte-for-byte what the issue records. Called the function directly in an
isolated `git archive HEAD` export:

```
deriveQualifiedColumns("id, coalesce(a, b), foo_bar", "subscribers")
  => "subscribers.id, coalesce(subscribers.a), subscribers.b), subscribers.foo_bar"
parens: open=1 close=2 (mismatch => malformed SQL)
```

**Clause 2 — "fails loudly rather than silently … a syntax error".** True, and
structurally guaranteed rather than merely observed once: splitting an `N`-argument
call always leaves `N-1` unmatched `)`, so it can never coincidentally produce
valid SQL that returns wrong data. Reproduced at the SQL layer by appending
`coalesce(email, email)` (a two-argument call over an existing column) to
`subscriberColumns` plus a matching throwaway `Scan` destination, against my own
scratch database `opencircuit_test_0372rev`.

**Clause 3 — "caught at test time by
`TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip`".** True of that
specific test, checked by running **only** that test rather than the package, so
nothing else could have been the catcher:

```
go test ./internal/subscribers/ -run '^TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip$' -v
--- FAIL: TestList_And_GetByID_ScanSubscriberColumnOrderRoundTrip (0.01s)
    store_test.go:2545: List: subscribers: listing: ERROR: syntax error at or near ")" (SQLSTATE 42601)
```

Matches `#0369`'s reproduction and the implementer's, independently measured.

**Clause 4 — "`subscriberColumns` has never contained such a call".** True. This
is the clause most likely to have been transcribed rather than measured, so I
checked the whole history: all 30 commits touching
`internal/subscribers/store.go`, extracting the constant from each revision and
testing for a comma at paren depth > 0.

- 6 distinct historical values of `subscriberColumns`, from `c0cff5d` (2026-08-19)
  to `b611735` (today).
- Every one contains exactly one function call, `host(signup_ip)` — single
  argument.
- Multi-argument calls found: **none**, in any revision.

The scan **fails closed** rather than skipping quietly, which matters because a
revision defining the constant with a double-quoted string instead of a backtick
literal would otherwise have produced zero matches and been silently counted as
clean: I asserted that every one of the 30 revisions yields *exactly one*
definition in *exactly* the backtick form, and separately that
`internal/subscribers/store.go` is the only file that has ever defined the name.
Both hold.

### Criterion 2 — no derivation change was attempted

`deriveQualifiedColumns`' body is untouched. The judgement is right: the failure
mode is a caught error at test time, the shape has never occurred, and `#0330`,
`#0347` and `#0356` set the precedent for recording a limit rather than building
for a defect that has not fired.

### Criterion 4 — it does not overstate in the other direction

The pre-existing first paragraph already scoped its positive claim to "the single
identifier inside a one-argument function call such as `host(signup_ip)`". The new
paragraph adds only negative space — what is *not* handled and what happens — and
claims no guarantee about anything else. Nothing here says the derivation is
correct in general, which is the shape five issues bounced for this phase.

### Criterion 5 — comment-only, proved with my own instrument

Deliberately **not** the implementer's `astdiff` (parse → `go/format` → text
diff). Different representation of the same fact: a raw **`go/scanner` token
stream** with comments not scanned at all, comparing token kind and literal
pairwise. A comment-only edit cannot move it.

Proved falsifiable *before* trusting it, on seven cases:

```
comment-only diff            -> TOKENS_IDENTICAL  exit 0
real code change             -> TOKENS_DIFFER     exit 1
comment removed entirely     -> TOKENS_IDENTICAL  exit 0
empty file (2nd arg)         -> SCAN_ERROR        exit 2
empty file (1st arg)         -> SCAN_ERROR        exit 2
lexically odd input          -> TOKENS_DIFFER     exit 1
missing file                 -> SCAN_ERROR        exit 2
```

It fails **closed**: a zero-token stream is an error, never an input, so an
extraction that produced nothing can never be reported as agreement — the
fail-open shape `#0258` and eight agents this week have hit.

Then, sensitivity on the **real** file rather than only on toys, which is the
other half of the same trap — an instrument can pass synthetic cases and still be
blind at 6,680 tokens:

```
git show b611735^:internal/subscribers/store.go  vs  git show b611735:...
  VERDICT: TOKENS_IDENTICAL (6680 tokens each; comments not scanned)

same, with one token mutated in the after-copy (Split(cols, ",") -> ";")
  VERDICT: TOKENS_DIFFER (at token 6251: "STRING\x00\",\"" vs "STRING\x00\";\"")
```

The working-tree file is byte-identical to the committed one
(`f583a90e…`), so the comparison is of what actually landed.

### Criterion 6 — gofmt

Proved by hash, and **without** running `gofmt -w` on the shared tree (§8a —
other agents are live): `shasum(store.go) == shasum(gofmt store.go) ==
shasum(gofmt(gofmt store.go))` = `f583a90e…`, i.e. idempotent, not merely
unflagged. The added paragraph is a declaration doc comment, so `#0210`'s
smart-quote rewrite applies to it; it contains no doubled `''` and no backtick,
and its only non-ASCII character is `—`.
