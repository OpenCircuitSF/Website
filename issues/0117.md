## Description

`scripts/dev.sh`'s `free_port 5173` sends `kill -9` to whatever is listening,
without checking whose process it is. Vite's port is fixed, so two agents — or
an agent and the user — running `dev.sh` concurrently means the second silently
destroys the first's dev server mid-session.

## Steps to reproduce

1. Start `./scripts/dev.sh` (or anything else bound to `5173`).
2. Start `./scripts/dev.sh` again from another session.
3. The first server is gone, with no warning to either party.

## Expected behavior

`dev.sh` either refuses to start when `5173` is held by a process it did not
launch, or says whose it is and asks, or picks another port.

## Actual behavior

It kills the process and continues, and the owner of the killed server sees
only that their server stopped answering.

## Root cause

`free_port()` called `lsof -ti tcp:"$p"` to get every pid bound to the port
and unconditionally ran `kill -9 $pids` on the result. It never inspected
what the process *was* — a foreign agent's `go run`/`vite`, the user's editor
preview, or (as found live during verification below) an unrelated macOS
service — only that something answered on the port. Both call sites at
startup (`free_port "$PORT"`, `free_port 5173`) hit this path identically.
Neither port is configurable to sidestep the collision: `$PORT` defaults to
`8080` and can be overridden via env var, but nothing downstream reads an
override for Vite's `5173` (hardcoded in `web/vite.config.ts`'s dev server
and baked into the "Open: http://localhost:5173" messaging), so an
override wouldn't currently do anything for that port.

## Fix

Gave `free_port()` a second `force` argument and a `RECLAIM_PORTS` env var,
following the shape `#0150` settled on for `testdb.sh gc`: refuse by
default, name exactly what's blocking, and require an explicit opt-in to
override.

- **Default (no force, `RECLAIM_PORTS` unset):** if the port is held, print
  the pid and full command line for every holder (via `ps -p $pid -o
  command=`), point at `CLAUDE.md` §5a as the likely cause, list three
  options (kill it yourself if it's genuinely yours, set
  `RECLAIM_PORTS=1` to force dev.sh to reclaim it, or `lsof -i tcp:$p` to
  find the owner first), and `exit 1`. Nothing is killed.
- **`RECLAIM_PORTS=1`:** old behavior — kill and continue. This is the
  explicit opt-in for the common, safe case: a developer's own dev.sh was
  orphaned by a closed terminal and they're rerunning it.
- **The EXIT-trap backstop** (`cleanup()`'s call to free `$PORT` on
  shutdown) passes `force=1` unconditionally rather than reading
  `RECLAIM_PORTS`. That call exists specifically to catch dev.sh's *own*
  leaked `go run` child after `kill "$GO_PID"`/`pkill -P "$GO_PID"` — there
  is nothing foreign to ask permission about there, and gating it on an env
  var would leave a normal Ctrl-C failing to clean up its own mess unless
  the user happened to also set `RECLAIM_PORTS=1`.

**Considered and rejected: auto-picking a free port instead of refusing.**
`$PORT` is threaded into `BASE_URL`, `WEBAUTHN_RP_ORIGIN`, and the printed
URLs; `5173` is Vite's own dev-server port and the Vite proxy target for
`5173` is spelled directly into the "Open" message. Silently picking a
different port would mean plumbing the discovered value through all of
those, and would still leave the *caller* not knowing which URL to open
without reading the log — no quieter than telling them up front that the
port is taken. Refuse-and-name-the-holder is also the one shape that can't
regress into "kill a stranger's process," which is the actual defect here;
an auto-pick path can't make that guarantee once two agents pick different
free ports that both then get published as "the" dev URL to different
people. Rejected in favor of the explicit refuse/opt-in shown above.

**Considered and rejected: no CLI flag, env var only.** `dev.sh` already
uses env vars for every other override (`ADMIN_EMAIL`, `PORT`,
`WEBAUTHN_RP_ID`, …), documented via `KEY=value ./scripts/dev.sh` in the
header comment. Adding a matching `RECLAIM_PORTS=1` keeps that one
consistent surface instead of introducing positional-flag parsing (today's
`case "${1:-}"` only accepts a single flag) for a rare case.

## Implementation notes

Changed only `scripts/dev.sh`:
- `free_port(p, force=0)` — refuses and reports by default; kills only when
  `force=1` or `RECLAIM_PORTS=1`.
- Header comment gained a paragraph documenting `RECLAIM_PORTS=1`.
- `cleanup()`'s backstop call changed from `free_port "$PORT"` to
  `free_port "$PORT" 1` (force, since that port is dev.sh's own).

No other files touched. `shellcheck scripts/dev.sh` is clean (exit 0).

## Verification

Ran `uptime` first: load average ~1.4–1.9, idle — any timing was real, not
machine contention.

**`bash -n scripts/dev.sh`** — syntax OK. **`shellcheck scripts/dev.sh`** —
exit 0, no findings.

**Direction 1 — refuses and survives.** Bound an unrelated Python socket to
an unlikely test port (`48213`, chosen to avoid any real dev.sh/Vite/agent
port) and ran `PORT=48213 ./scripts/dev.sh`:

```
  ERROR: port 48213 is already in use — dev.sh will not kill a process it did not start.
    pid 56746: /Applications/.../Python.app/Contents/MacOS/Python -c ...
  This may be another agent's dev.sh (CLAUDE.md section 5a) or an unrelated process — not necessarily yours to kill.
  Options:
    - if it is genuinely yours (e.g. an orphaned dev.sh from a closed terminal), stop it: kill 56746
    - or force dev.sh to reclaim it: RECLAIM_PORTS=1 ./scripts/dev.sh
    - or find out whose it is first: lsof -i tcp:48213
```

Exit code `1`. Confirmed the holder (`ps -p 56746`, `lsof -ti tcp:48213`)
was **still alive and still listening** after dev.sh exited — the assertion
that matters. Killed it myself afterward (§5a — it was my own test
process).

**Direction 2 — ordinary path still works.** With the port genuinely free
(`48213` again after cleanup; `5173` confirmed free via `lsof` before
starting — note `:8080` itself was live-occupied for the whole session by
an unrelated `com.apple.WebDriver.HTTPService` process, real evidence this
guard fires for real users too, and correctly left untouched), ran `PORT=48214
./scripts/dev.sh` in the background: Go API bound and logged
`opencircuit 0.1.0 listening on 127.0.0.1:48214`, Vite bound and printed
`VITE v6.4.2 ready`. Verified `curl http://localhost:48214/` returned `200`
with the Open Circuit SF page title — the build-specific detail proving
this was my own server, not a leftover (§8b). Sent `SIGINT` to the whole
process group (the way a terminal Ctrl-C would, not just the script's own
pid — a plain `kill -INT` on the script pid alone doesn't reach its
foreground `npm run dev` child and doesn't exercise the trap the same way)
and confirmed the `Shutting down… stopped` trap ran, both `48214` and
`5173` were released, and every child (`go run`, the compiled binary,
`npm`, `vite`, `esbuild`) exited.

Cleaned up: no `go test`/`.test` processes running, no `opencircuit serve`
processes running, ports `48213`/`48214`/`5173` all clear, confirmed via
`pgrep` and `lsof` after the run.

No guard test script was added — `scripts/testdb_gc_guard_test.sh` is a
model for pinning a refusal-by-default guard against future regression,
and the same shape would fit here (bind a throwaway port, assert
`dev.sh`'s refusal, assert the holder survives, assert `RECLAIM_PORTS=1`
does reclaim it) — worth filing as a follow-up rather than folding into
this pass, since `dev.sh` isn't `scripts/check.sh`-shaped and needs its own
harness the way `#0150`'s guard needed one for `testdb.sh`.

## Notes

Found during `#0116`'s review (2026-08-21), which pre-checked the port by hand
and found it free. Pre-existing behaviour, not introduced by `#0116` — filed
separately rather than widening that issue's scope.

This is the same hazard class `CLAUDE.md` §8b already documents from the other
direction: an agent once bound a fixed shared port, its own bind failed, and
`curl` cheerfully returned 200 from *another agent's* server on that port. §8b
tells agents not to trust a shared port; this issue is the tooling doing the
destroying rather than the trusting.

Subagents frequently run concurrently in this repo (§5a permits two at once),
so this is reachable in normal use, not a hypothetical.
