## Description

`scripts/dev.sh`'s `free_port 5173` sends `kill -9` to whatever is listening,
without checking whose process it is. Vite's port is fixed, so two agents — or
an agent and the user — running `dev.sh` concurrently means the second silently
destroys the first's dev server mid-session.

## Steps to reproduce

1. Start `./scripts/dev.sh` (or anything else bound to `5173`).
2. Start `./scripts/dev.sh` again from another session.
3. The first server is gone, with no warning to either party.

## Expected behavior

`dev.sh` either refuses to start when `5173` is held by a process it did not
launch, or says whose it is and asks, or picks another port.

## Actual behavior

It kills the process and continues, and the owner of the killed server sees
only that their server stopped answering.

## Root cause

`free_port()` called `lsof -ti tcp:"$p"` to get every pid bound to the port
and unconditionally ran `kill -9 $pids` on the result. It never inspected
what the process *was* — a foreign agent's `go run`/`vite`, the user's editor
preview, or (as found live during verification below) an unrelated macOS
service — only that something answered on the port. Both call sites at
startup (`free_port "$PORT"`, `free_port 5173`) hit this path identically.
Neither port is configurable to sidestep the collision: `$PORT` defaults to
`8080` and can be overridden via env var, but nothing downstream reads an
override for Vite's `5173` (hardcoded in `web/vite.config.ts`'s dev server
and baked into the "Open: http://localhost:5173" messaging), so an
override wouldn't currently do anything for that port.

## Fix

Gave `free_port()` a second `force` argument and a `RECLAIM_PORTS` env var,
following the shape `#0150` settled on for `testdb.sh gc`: refuse by
default, name exactly what's blocking, and require an explicit opt-in to
override.

- **Default (no force, `RECLAIM_PORTS` unset):** if the port is held, print
  the pid and full command line for every holder (via `ps -p $pid -o
  command=`), point at `CLAUDE.md` §5a as the likely cause, list three
  options (kill it yourself if it's genuinely yours, set
  `RECLAIM_PORTS=1` to force dev.sh to reclaim it, or `lsof -i tcp:$p` to
  find the owner first), and `exit 1`. Nothing is killed.
- **`RECLAIM_PORTS=1`:** old behavior — kill and continue. This is the
  explicit opt-in for the common, safe case: a developer's own dev.sh was
  orphaned by a closed terminal and they're rerunning it.
- **The EXIT-trap backstop** (`cleanup()`'s call to free `$PORT` on
  shutdown) passes `force=1` unconditionally rather than reading
  `RECLAIM_PORTS`. That call exists specifically to catch dev.sh's *own*
  leaked `go run` child after `kill "$GO_PID"`/`pkill -P "$GO_PID"` — there
  is nothing foreign to ask permission about there, and gating it on an env
  var would leave a normal Ctrl-C failing to clean up its own mess unless
  the user happened to also set `RECLAIM_PORTS=1`.

**Considered and rejected: auto-picking a free port instead of refusing.**
`$PORT` is threaded into `BASE_URL`, `WEBAUTHN_RP_ORIGIN`, and the printed
URLs; `5173` is Vite's own dev-server port and the Vite proxy target for
`5173` is spelled directly into the "Open" message. Silently picking a
different port would mean plumbing the discovered value through all of
those, and would still leave the *caller* not knowing which URL to open
without reading the log — no quieter than telling them up front that the
port is taken. Refuse-and-name-the-holder is also the one shape that can't
regress into "kill a stranger's process," which is the actual defect here;
an auto-pick path can't make that guarantee once two agents pick different
free ports that both then get published as "the" dev URL to different
people. Rejected in favor of the explicit refuse/opt-in shown above.

**Considered and rejected: no CLI flag, env var only.** `dev.sh` already
uses env vars for every other override (`ADMIN_EMAIL`, `PORT`,
`WEBAUTHN_RP_ID`, …), documented via `KEY=value ./scripts/dev.sh` in the
header comment. Adding a matching `RECLAIM_PORTS=1` keeps that one
consistent surface instead of introducing positional-flag parsing (today's
`case "${1:-}"` only accepts a single flag) for a rare case.

### Fix for phase-3 bounce (2026-08-23)

The review below found the `EXIT`-trap backstop re-derived "whoever holds
`:$PORT` right now" from `lsof` **at exit time** and killed it
unconditionally — so a foreign process that took over the port after
`dev.sh`'s own Go server died mid-session (or after two `dev.sh` runs raced
on `free_port`) got `kill -9`ed by an ordinary Ctrl-C. Changed only
`scripts/dev.sh` again, no other files:

- Added `OWNED_PIDS=""`, declared right after `GO_PID=$!` (so it's always
  bound under `set -u` even if the script exits before the server comes
  up), then populated with `lsof -ti tcp:"$PORT"` immediately after the
  existing `kill -0 "$GO_PID"` readiness check passes — i.e. the pids
  `dev.sh` itself confirmed it bound to `$PORT`.
- Added `release_owned_port(p, owned)`, defined next to `free_port()`. At
  exit it re-`lsof`s `$p`, splits the current holders into "ours"
  (intersects `$owned`) and "foreign" (does not), kills only the ours set
  with `kill -9` + a re-check that the kill actually took (see below), and
  prints a warning — without killing — for anything foreign it finds
  holding the port. It never calls `exit`; this runs inside the shutdown
  path, so a foreign holder gets a warning, not a hard failure.
- `cleanup()`'s backstop line changed from `free_port "$PORT" 1` to
  `release_owned_port "$PORT" "$OWNED_PIDS"`.
- **Secondary fix, same pass:** `free_port()`'s force branch (still used by
  the startup path's `RECLAIM_PORTS=1`/`force=1`) previously logged
  `freeing port …` and returned 0 right after `kill -9`, without checking
  whether the kill actually worked. It now re-`lsof`s after the existing
  `sleep 1` and, if the port is still held, prints an `ERROR` naming the
  survivor(s) and exits 1 instead of claiming success.
- The `force=1`/pre-#0117 comment block above `free_port()` was rewritten —
  it previously justified the *removed* unconditional-backstop call; it now
  explains the verify-after-kill requirement instead. A new comment above
  `release_owned_port()` explains why the trap tracks pids instead of
  re-deriving them.

Added `scripts/dev_guard_test.sh` — the regression test the review asked
for — as a new, separate file. `scripts/dev.sh` itself gained no test
harness hooks; the guard test drives it as an ordinary subprocess.

pid comes from `lg="$(launch_group ...)"` — command substitution runs
`launch_group` in a subshell, so the backgrounded process is a child of
*that subshell*, not of this script; the subshell exits immediately after
echoing the pid, so `wait "$pid"` is waiting for something that was never
this shell's child. Bash returns from an unwaitable `wait` immediately
rather than blocking, so the check that followed (`kill -0 "$foreign"`) ran
before the mutant's `sleep 1`-then-verify sequence had actually finished,

contradicting the automated run. Fixed `wait_pid_gone()` to poll `kill -0`

### What must change before this resolves

**The `EXIT` trap re-derives the holder from the port and kills a stranger.**
`cleanup()` does not track a pid it started. It runs
`free_port "$PORT" 1`, whose first act is `lsof -ti tcp:"$p"` — *at exit time*.
The commit message's justification ("that process is unambiguously ours") is
therefore false whenever `$PORT` changed hands during the session.

Reproduced live, against the shipped `ffc796e`:

1. `RECLAIM_PORTS=1 PORT=49317 ./scripts/dev.sh` running normally (listener
   59167, a descendant of the script).
2. `kill -9 59167 59162` — the Go server dies mid-session, as a panic or a
   stray `pkill` would do. Port `49317` goes free.
3. A **foreign** process binds `49317` (pid 59487 — stand-in for the other
   agent §5a permits).
4. SIGINT to `dev.sh`'s process group, i.e. an ordinary Ctrl-C.
5. Trap output: `freeing port 49317 (stale process: 59487)`. Pid 59487 was
   **`kill -9`ed**. `ps -p 59487` afterwards: nothing.

`dev.sh` killed a process it did not start, printed the old "stale process"
wording while doing it, and gave the owner no warning — the exact behaviour in
this issue's `## Actual behavior`, relocated from startup to shutdown.

A second reachable route needs no crash at all: two `dev.sh` runs that both
clear `free_port` before either binds (a sub-second window, and §8b exists
because agents do collide on fixed ports). The loser's `go run` fails with
`address already in use`, the loser's trap then fires and kills the **winner's**
server. That is this issue's "Steps to reproduce" verbatim.

Note also that the trap is nearly always a no-op: in the clean shutdown above,
`kill "$GO_PID"` + `pkill -P "$GO_PID"` had already reaped the child and no
`freeing port` line was printed at all. So the backstop is doing almost nothing
in the normal case, and everything in the dangerous one — which is a good trade
to make ownership-checked.

**Required:** make the backstop kill only pids it knows are its own. The cheapest
correct shape is to record the holders once the server is confirmed up (after
the `kill -0 "$GO_PID"` check, e.g. `OWNED_PIDS="$(lsof -ti tcp:"$PORT")"`) and
have `cleanup()` kill only the intersection of that set with the current
holders, printing the ordinary refusal text (as a warning, not an `exit 1` —
this is the shutdown path) for anything outside it. Walking `GO_PID`'s
descendants at exit time works equally well. Either way the invariant to hold is
the one the issue title states: *no `kill` of a pid this run did not start.*

**Secondary, fix in the same pass.** The force path never confirms the port was
actually freed. With an unsignalable holder (probed with pid 1) `kill -9` fails,
the failure is swallowed by `2>/dev/null || true`, and `free_port` returns 0
after printing `freeing port 49999 (stale process: 1)` — so the log claims the
port was cleared, and the run fails later with a confusing
`address already in use`. Re-check with `lsof` after the `sleep 1` and report
honestly if the port is still held.

### What `OWNED_PIDS` actually records — and why it is not sound

```sh
go run ./cmd/opencircuit serve &
GO_PID=$!
…
sleep 1
kill -0 "$GO_PID" || exit 1                       # line 227
OWNED_PIDS="$(lsof -ti tcp:"$PORT" 2>/dev/null)"  # line 232
```

Three facts follow from reading it, all confirmed live:

- **The forked pid is not tracked; only a listener is.** `OWNED_PIDS` is derived
  from `lsof`, never from `$!`. `GO_PID` is the `go run` wrapper (65322 above),
  which holds no socket, so **`GO_PID` is never in `OWNED_PIDS`** — the set
  contains the compiled `opencircuit serve` child (65327), which `dev.sh` learns
  about only by asking the port who is on it. The parent is killed separately by
  `cleanup()`'s `kill "$GO_PID"` / `pkill -P "$GO_PID"`, so nothing is *lost*;
  the point is that ownership is inferred from the port, not from the fork.
- **`free_port`'s refusal is ordered correctly.** `free_port "$PORT"` runs at
  line 135, `OWNED_PIDS` is captured at line 232 — so a process *already*
  holding the port at startup can never be recorded as owned: it either caused
  `exit 1` or was reclaimed under an explicit `RECLAIM_PORTS=1`. That part is
  sound. What is not sound is everything that can attach to the port in the
  ~1 s **between** those two lines.
- **`lsof -ti tcp:P` does not mean "listening on P".** It matches *any* TCP
  endpoint on that port, including a client's ESTABLISHED connection *to* the
  server. `-sTCP:LISTEN` is the flag that would mean what the code assumes.

Both live failures below fall out of those last two points.

#### Repro A — a mere client connection is recorded as "own process" and killed (no race between runs, no stub, no crash)

Started a foreign `python3` that retries `connect()` to `:53351` in a tight loop
and then holds the connection open. Started `PORT=53351 ./scripts/dev.sh`
normally. At capture time `lsof` legitimately reports two pids:

```
Python    66224  TCP 127.0.0.1:62624->127.0.0.1:53351 (ESTABLISHED)   ← foreign client
opencircu 66245  TCP 127.0.0.1:53351 (LISTEN)                         ← dev.sh's server
```

Ordinary Ctrl-C (`SIGINT` to the process group):

```
==> Shutting down…
    freeing port 53351 (own process: 66224 66245)
RESULT: connector 66224 WAS KILLED BY dev.sh
```

`dev.sh` `kill -9`ed a process it never started, called it **"own process"**, and
printed no warning. Nothing exotic is required to hit this: a browser tab left
open on the dev API, another agent's `curl`, a health-check loop, or a poller
that reconnects — anything with a socket on `:$PORT` at the instant of capture
is enrolled as owned for the rest of the session.

#### Repro B — the "two runs race on `free_port`" route the first review required to be closed

The readiness check tests `kill -0 "$GO_PID"` — that `go run` is *alive*, not
that anything **bound**. With a warm build cache the binary binds in ~0.3 s and a
losing `go run` dies before the `sleep 1` elapses, so the check happens to fail
safe. Whenever `go run` needs longer than that fixed one second to bind — any
recompile or relink, i.e. the normal state right after editing Go code, and
always on a cold cache — the check passes while nothing of ours is on the port
yet, and `lsof` hands back whoever *is*.

Simulated a cold cache with a `go` shim on `PATH` that sleeps 6 s and then
`exec`s the real `go` (nothing else stubbed; `dev.sh` unmodified). Bound a
foreign holder to `:53341` just after `dev.sh` cleared `free_port`:

```
FOREIGN pid=66004 bound 53341  (before dev.sh readiness check)
readiness line present: 1
…
opencircuit: listen tcp 127.0.0.1:53341: bind: address already in use
==> Shutting down…
    freeing port 53341 (own process: 66004)
RESULT: foreign 66004 WAS KILLED BY dev.sh
```

This is this issue's `## Steps to reproduce` verbatim, relocated to the trap —
and it is the second route the first review explicitly listed under "What must
change": *"two `dev.sh` runs that both clear `free_port` before either binds …
the loser's trap then fires and kills the **winner's** server."* The fix narrowed
that window from "always" to "whenever `go run` takes longer than one second",
but did not close it. Note the first review offered two shapes and the weaker one
was implemented; its alternative — *"walking `GO_PID`'s descendants at exit time
works equally well"* — has neither hole, because a descendant of `GO_PID` is by
construction a process this run started.

### The guard test — re-verified, and where it falls short

**Re-ran the mutation proof myself.** `scripts/dev_guard_test.sh` exits 0 in
~20 s, all five assertions passing, including Part 4: `[part4] foreign holder
(pid 65851) after EXIT trap: killed` against the mutant versus `[part3b] …
survived` against the real script. So the mutation proof is real and Part 3b is
not vacuous — the `wait`-on-a-non-child bug the implementer disclosed is
genuinely fixed (`wait_pid_gone` polls `kill -0`).

**Mutant hygiene is correct.** `scripts/.dev_guard_test_mutant.$$.sh` is
untracked and `$$`-unique; it is produced by `sed` *reading* the tracked file and
writing a new one; it is `rm -f`ed by the test's own `EXIT` trap; the `sha256` of
`scripts/dev.sh` is asserted identical before and after. After my run: no
`scripts/.dev_guard_test_mutant.*` survives, `scripts/` contains no dotfiles at
all, and `git status --short` is empty. The in-repo location is justified
correctly (`dev.sh` self-locates `REPO` from `${BASH_SOURCE[0]}/..`).

**But the guard test cannot catch either failure above**, because its foreign
holder always binds *after* `OWNED_PIDS` has been captured. It pins the exact
scenario the first review reproduced and nothing wider, so it will go on passing
against both repros here. Any re-fix needs an assertion where the stranger is on
the port **before** the capture.

**A third instance of the disclosed bug class is still in the file** — in fact
two, of both shapes named:

- **`wait` on a non-child, twice more.** Line 165 (`wait "$holder"`) and line 288
  (`wait "$foreign"`). `holder`/`foreign` come from `holder="$(bind_holder …)"`,
  and command substitution runs `bind_holder` in a subshell, so the backgrounded
  `python3` is that subshell's child, not the script's. Verified the shape
  directly: `wait: pid … is not a child of this shell`, rc 127, elapsed 0 s.
  Both are currently harmless — each follows a `kill -9` and nothing is asserted
  afterwards — but they are the same construct that produced the disclosed false
  pass, left in place, one edit away from being load-bearing again.
- **Asserting immediately after a log line instead of polling for the condition.**
  Line 186 (Part 2's ancestry walk) and line 253 (`gopid="$(lsof -ti
  tcp:"$port")"`) both run `lsof` the instant `"Go API server started"` appears —
  the very log line proven above not to imply that anything is bound. On a slow
  compile line 186 yields `owned=0` and a spurious FAIL, and line 253 yields
  empty and an "inconclusive" FAIL. Worse, line 253 then `kill -9`s whatever
  `lsof` returned: if a foreign process holds the port at that moment, **the
  guard test itself kills a stranger** — the §8b hazard, inside the test written
  to prevent it. Both want `wait_for N port_bound "$port"` first, and line 253
  wants an ancestry check (Part 2 already has one) before it kills anything.
  Line 220's `port_free "$P3A" && port_free 5173` is the same unpolled shape,
  lower risk.

### What must change before this resolves

1. **Derive ownership from the fork, not from the port.** Record only pids that
   are descendants of `GO_PID` (the ancestry walk in the guard test's Part 2 is
   already the right ~8 lines), or walk `GO_PID`'s descendants at exit time as
   the first review's alternative suggested. A pid that is merely *on* the port
   is not evidence of anything.
2. **If `lsof` stays in the picture anywhere, scope it to listeners** —
   `lsof -ti tcp:P -sTCP:LISTEN` — so a client's ESTABLISHED connection can never
   be enrolled as owned. (This also makes `free_port`'s startup refusal stop
   firing on a mere client connection, which today it does.)
3. **Make the readiness check test the thing it claims.** `kill -0 "$GO_PID"`
   after a fixed `sleep 1` says only that `go run` has not exited. Poll for the
   port to actually be bound *by our own descendant*, with a timeout, and fail
   loudly if it never happens — that closes Repro B at its source and removes the
   silent-degradation case where `OWNED_PIDS` ends up empty and the backstop
   quietly does nothing.
4. **Extend the guard test** with a case where the stranger is on `:$PORT`
   *before* `OWNED_PIDS` is captured — both variants are worth pinning: a client
   connection held across the capture (Repro A) and a foreign listener that wins
   the bind during a slow `go run` (Repro B). Both are one-liners against the
   helpers already in the file.
5. **Clean up the two remaining `wait`-on-a-non-child calls** (lines 165, 288)
   and poll before the `lsof` assertions at lines 186, 253 (and 220).
