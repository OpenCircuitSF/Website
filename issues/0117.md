## Description

`scripts/dev.sh`'s `free_port 5173` sends `kill -9` to whatever is listening,
without checking whose process it is. Vite's port is fixed, so two agents — or
an agent and the user — running `dev.sh` concurrently means the second silently
destroys the first's dev server mid-session.

## Steps to reproduce

1. Start `./scripts/dev.sh` (or anything else bound to `5173`).
2. Start `./scripts/dev.sh` again from another session.
3. The first server is gone, with no warning to either party.

## Expected behavior

`dev.sh` either refuses to start when `5173` is held by a process it did not
launch, or says whose it is and asks, or picks another port.

## Actual behavior

It kills the process and continues, and the owner of the killed server sees
only that their server stopped answering.

## Root cause

`free_port()` called `lsof -ti tcp:"$p"` to get every pid bound to the port
and unconditionally ran `kill -9 $pids` on the result. It never inspected
what the process *was* — a foreign agent's `go run`/`vite`, the user's editor
preview, or (as found live during verification below) an unrelated macOS
service — only that something answered on the port. Both call sites at
startup (`free_port "$PORT"`, `free_port 5173`) hit this path identically.
Neither port is configurable to sidestep the collision: `$PORT` defaults to
`8080` and can be overridden via env var, but nothing downstream reads an
override for Vite's `5173` (hardcoded in `web/vite.config.ts`'s dev server
and baked into the "Open: http://localhost:5173" messaging), so an
override wouldn't currently do anything for that port.

## Fix

Gave `free_port()` a second `force` argument and a `RECLAIM_PORTS` env var,
following the shape `#0150` settled on for `testdb.sh gc`: refuse by
default, name exactly what's blocking, and require an explicit opt-in to
override.

- **Default (no force, `RECLAIM_PORTS` unset):** if the port is held, print
  the pid and full command line for every holder (via `ps -p $pid -o
  command=`), point at `CLAUDE.md` §5a as the likely cause, list three
  options (kill it yourself if it's genuinely yours, set
  `RECLAIM_PORTS=1` to force dev.sh to reclaim it, or `lsof -i tcp:$p` to
  find the owner first), and `exit 1`. Nothing is killed.
- **`RECLAIM_PORTS=1`:** old behavior — kill and continue. This is the
  explicit opt-in for the common, safe case: a developer's own dev.sh was
  orphaned by a closed terminal and they're rerunning it.
- **The EXIT-trap backstop** (`cleanup()`'s call to free `$PORT` on
  shutdown) passes `force=1` unconditionally rather than reading
  `RECLAIM_PORTS`. That call exists specifically to catch dev.sh's *own*
  leaked `go run` child after `kill "$GO_PID"`/`pkill -P "$GO_PID"` — there
  is nothing foreign to ask permission about there, and gating it on an env
  var would leave a normal Ctrl-C failing to clean up its own mess unless
  the user happened to also set `RECLAIM_PORTS=1`.

**Considered and rejected: auto-picking a free port instead of refusing.**
`$PORT` is threaded into `BASE_URL`, `WEBAUTHN_RP_ORIGIN`, and the printed
URLs; `5173` is Vite's own dev-server port and the Vite proxy target for
`5173` is spelled directly into the "Open" message. Silently picking a
different port would mean plumbing the discovered value through all of
those, and would still leave the *caller* not knowing which URL to open
without reading the log — no quieter than telling them up front that the
port is taken. Refuse-and-name-the-holder is also the one shape that can't
regress into "kill a stranger's process," which is the actual defect here;
an auto-pick path can't make that guarantee once two agents pick different
free ports that both then get published as "the" dev URL to different
people. Rejected in favor of the explicit refuse/opt-in shown above.

**Considered and rejected: no CLI flag, env var only.** `dev.sh` already
uses env vars for every other override (`ADMIN_EMAIL`, `PORT`,
`WEBAUTHN_RP_ID`, …), documented via `KEY=value ./scripts/dev.sh` in the
header comment. Adding a matching `RECLAIM_PORTS=1` keeps that one
consistent surface instead of introducing positional-flag parsing (today's
`case "${1:-}"` only accepts a single flag) for a rare case.

### Fix for phase-3 bounce (2026-08-23)

The review below found the `EXIT`-trap backstop re-derived "whoever holds
`:$PORT` right now" from `lsof` **at exit time** and killed it
unconditionally — so a foreign process that took over the port after
`dev.sh`'s own Go server died mid-session (or after two `dev.sh` runs raced
on `free_port`) got `kill -9`ed by an ordinary Ctrl-C. Changed only
`scripts/dev.sh` again, no other files:

- Added `OWNED_PIDS=""`, declared right after `GO_PID=$!` (so it's always
  bound under `set -u` even if the script exits before the server comes
  up), then populated with `lsof -ti tcp:"$PORT"` immediately after the
  existing `kill -0 "$GO_PID"` readiness check passes — i.e. the pids
  `dev.sh` itself confirmed it bound to `$PORT`.
- Added `release_owned_port(p, owned)`, defined next to `free_port()`. At
  exit it re-`lsof`s `$p`, splits the current holders into "ours"
  (intersects `$owned`) and "foreign" (does not), kills only the ours set
  with `kill -9` + a re-check that the kill actually took (see below), and
  prints a warning — without killing — for anything foreign it finds
  holding the port. It never calls `exit`; this runs inside the shutdown
  path, so a foreign holder gets a warning, not a hard failure.
- `cleanup()`'s backstop line changed from `free_port "$PORT" 1` to
  `release_owned_port "$PORT" "$OWNED_PIDS"`.
- **Secondary fix, same pass:** `free_port()`'s force branch (still used by
  the startup path's `RECLAIM_PORTS=1`/`force=1`) previously logged
  `freeing port …` and returned 0 right after `kill -9`, without checking
  whether the kill actually worked. It now re-`lsof`s after the existing
  `sleep 1` and, if the port is still held, prints an `ERROR` naming the
  survivor(s) and exits 1 instead of claiming success.
- The `force=1`/pre-#0117 comment block above `free_port()` was rewritten —
  it previously justified the *removed* unconditional-backstop call; it now
  explains the verify-after-kill requirement instead. A new comment above
  `release_owned_port()` explains why the trap tracks pids instead of
  re-deriving them.

Added `scripts/dev_guard_test.sh` — the regression test the review asked
for — as a new, separate file. `scripts/dev.sh` itself gained no test
harness hooks; the guard test drives it as an ordinary subprocess.

### Fix for the second phase-3 bounce (2026-08-23, escalated to Opus per `CLAUDE.md` §3)

The re-review's diagnosis is adopted whole: `OWNED_PIDS` answered the wrong
question. Ownership is now derived from the **fork**, never from the port.
Changed `scripts/dev.sh` and `scripts/dev_guard_test.sh` only.

**`scripts/dev.sh` — a new "Process ownership (#0117)" block above
`free_port()`:**

- `port_listeners(p)` — `lsof -ti tcp:p -sTCP:LISTEN`. **Every** port lookup in
  the script now goes through it: `free_port()`'s refusal and its
  force-path re-check, `release_owned_port()`'s current-holder set, and the
  readiness poll. A client's ESTABLISHED connection can no longer be enrolled
  as owned, and no longer makes startup refuse either.
- `proc_start(pid)` — the process's `lstart`, whitespace-collapsed. Pids are
  recorded as `pid:start-time` fingerprints so a pid the OS recycles during a
  long session can never be mistaken for the process we forked. Its trailing
  `|| true` is load-bearing: with `set -o pipefail`, `ps` failing on a dead pid
  would otherwise make `x="$(proc_start …)"` a failing command and errexit
  would kill the script mid-shutdown.
- `descendant_pids(root)` — one `ps -Ao pid=,ppid=` piped to an `awk`
  fixed-point walk (the process table is not topologically ordered), returning
  the root plus every live descendant.
- `own_pids(root)` — the ownership model, deliberately a **single delegating
  line** so the guard test can mutate exactly that line back to
  ownership-by-port and prove its assertions are sensitive.
- `own_fingerprints(root)`, `is_owned(pid, list)`, `own_holds_port(port, root)`
  — fingerprinting, exact membership, and "is a pid *we forked* LISTENing
  there?" (which also records the owned set).

**Readiness now tests the thing it claims.** `sleep 1` + `kill -0 "$GO_PID"` is
replaced by a poll on `own_holds_port "$PORT" "$GO_PID"`, bounded by
`DEV_READY_TIMEOUT` (default 180s, documented in the header comment and
overridable for a very cold cache). It exits 1 with a distinct message if
`go run` dies, and a second one if it never binds. This closes repro B **at
its source**: when a stranger wins the bind, dev.sh never reaches a state where
it believes it owns anything, and it says so loudly rather than degrading
silently.

**`cleanup()` gathers lineage evidence before it signals anything.** `GO_FP`
(`GO_PID` + its start time) is captured at the fork. At exit, `cleanup()` first
checks `GO_PID` is still that process, then snapshots
`own_fingerprints "$GO_PID"` — *before* `kill`/`pkill`, because afterwards a
leaked grandchild is reparented to `launchd` and the tree is unwalkable. That
snapshot is unioned with the readiness-time set and handed to
`release_owned_port`, which kills only fingerprint-exact matches and warns,
without killing, about everything else.

**Also fixed, same class:** `kill "$GO_PID"` and `pkill -P "$GO_PID"` were
unconditional. Against a recycled `GO_PID`, `pkill -P` would kill another
program's children — this issue's defect wearing a different hat. Both are now
inside the `GO_FP` check.

Untouched: `dev.sh:39,41` (`BASE_URL` / `WEBAUTHN_RP_ORIGIN` hardcoded to
`:8080` — `#0213`'s surface), the startup refusal's wording and exit-1
behaviour, and the `RECLAIM_PORTS=1` force path's fail-loudly re-check. Both
passed review and are re-pinned by guard-test Parts 1 and 2.

**`scripts/dev_guard_test.sh` — the three flaws the review named, plus the two
missing scenarios:**

- **No `wait` on a non-child anywhere in the file.** The two remaining calls
  (old lines 165, 288) are gone; a `reap()` helper kills a pid this script
  forked and then *polls* for it to be gone. The comment on `wait_pid_gone()`
  now explains the trap for the next editor.
- **Nothing asserts on a log line as a proxy for a condition.** Old line 186's
  ancestry walk and old line 253's `lsof` both ran the instant
  `"Go API server started"` appeared. Both now poll `own_listeners_ready`,
  which returns only listeners **proved to descend** from the dev.sh this test
  launched — so the crash-simulation kill (old line 253, which would have
  `kill -9`ed a stranger on a slow compile) is aimed at pids the test owns.
  Old line 220's post-shutdown port check now polls too.
- **A new `devsh_fully_up()`** polls through to *listener of ours + readiness
  line + Vite on 5173* before any scenario interferes. Without it a
  "mid-session crash" could land inside dev.sh's own startup, which exits 1 on
  its own — a different code path. This was not theoretical: it made Part 4's
  mutant look like a setup failure on the first run of this pass.
- **`make_mutant`** replaces the single inline `sed`, with per-mutation marker
  assertions so a moved target line fails loudly instead of silently producing
  an unmutated "mutant". Three mutations are defined, each reverting one half
  of the fix to a shape proven to kill a stranger: `M1` the unconditional exit
  backstop, `M2` ownership-by-port, `M3` the unscoped exit-time `lsof`.
- **Two new scenarios**, both with the stranger on the port **before** the
  ownership capture: `run_connector_survives_scenario` (repro A) and
  `run_slow_build_scenario` (repro B, using a `go` shim on `PATH` — `dev.sh` is
  never modified to simulate the slow compile).

Mutant hygiene is unchanged and still correct: untracked, `$$`-unique, in
`scripts/` (dev.sh self-locates `REPO` from `${BASH_SOURCE[0]}/..`), removed by
the EXIT trap, with a `sha256` bookend on the tracked file.

2. **`RECLAIM_PORTS=1` reclaims** — the original holder is killed, and the

   its repo root from `dirname "${BASH_SOURCE[0]}"/..`, so a copy living
   outside `scripts/` resolves to the wrong directory and can't find

**A real bug in the guard test itself, found and fixed before trusting any
of this.** The first working draft's `wait_pid_gone()` called `wait "$pid"`
on the `dev.sh` group-leader pid to block until shutdown completed. That
pid comes from `lg="$(launch_group ...)"` — command substitution runs
`launch_group` in a subshell, so the backgrounded process is a child of
*that subshell*, not of this script; the subshell exits immediately after
echoing the pid, so `wait "$pid"` is waiting for something that was never
this shell's child. Bash returns from an unwaitable `wait` immediately
rather than blocking, so the check that followed (`kill -0 "$foreign"`) ran
before the mutant's `sleep 1`-then-verify sequence had actually finished,
and read "survived" for a case that would, one second later, correctly
read "killed" — a false pass for assertion 4 that would have shipped a
guard test blind to the exact regression it exists to catch. Caught by
manually single-stepping the same scenario by hand (own process group,
kill the simulated crash, bind a foreign holder, SIGINT, then an explicit
`sleep 3` before checking) and finding the foreign process correctly dead —
contradicting the automated run. Fixed `wait_pid_gone()` to poll `kill -0`
instead of relying on `wait`, since the pid is never actually this shell's
child (which also means no zombie-reap risk — a non-child pid is reaped by
whatever adopted it, not by this script). Reran the full suite twice more
after the fix; both runs pass all five parts, including the mutation
sensitivity proof.

Cleanup after every run (manual and automated): no `dev.sh`, `go run`,
`vite`, `esbuild`, or `python3 -m http.server` processes left running
(`pgrep -fl` empty); every test port (`52101`, `52111`, `52121`, `52131`,
`52141`, `53201`, `5173`) confirmed free via `lsof`; `:8080` — held for the

### What `OWNED_PIDS` actually records — and why it is not sound

```sh
go run ./cmd/opencircuit serve &
GO_PID=$!
…
sleep 1
kill -0 "$GO_PID" || exit 1                       # line 227
OWNED_PIDS="$(lsof -ti tcp:"$PORT" 2>/dev/null)"  # line 232
```

Three facts follow from reading it, all confirmed live:

- **The forked pid is not tracked; only a listener is.** `OWNED_PIDS` is derived
  from `lsof`, never from `$!`. `GO_PID` is the `go run` wrapper (65322 above),
  which holds no socket, so **`GO_PID` is never in `OWNED_PIDS`** — the set
  contains the compiled `opencircuit serve` child (65327), which `dev.sh` learns
  about only by asking the port who is on it. The parent is killed separately by
  `cleanup()`'s `kill "$GO_PID"` / `pkill -P "$GO_PID"`, so nothing is *lost*;
  the point is that ownership is inferred from the port, not from the fork.
- **`free_port`'s refusal is ordered correctly.** `free_port "$PORT"` runs at
  line 135, `OWNED_PIDS` is captured at line 232 — so a process *already*
  holding the port at startup can never be recorded as owned: it either caused
  `exit 1` or was reclaimed under an explicit `RECLAIM_PORTS=1`. That part is
  sound. What is not sound is everything that can attach to the port in the
  ~1 s **between** those two lines.
- **`lsof -ti tcp:P` does not mean "listening on P".** It matches *any* TCP
  endpoint on that port, including a client's ESTABLISHED connection *to* the
  server. `-sTCP:LISTEN` is the flag that would mean what the code assumes.

Both live failures below fall out of those last two points.

#### Repro A — a mere client connection is recorded as "own process" and killed (no race between runs, no stub, no crash)

### The five ownership-logic probes

**1. `proc_start`'s `|| true` is load-bearing, and pipefail is the mechanism.**
Confirmed by construction. `x="$(f 99999)"` where `f` is the shipped pipeline
minus the `|| true`: under `set -eu` alone it survives (the trailing `tr` masks
`ps`'s status), under `set -euo pipefail` the script dies with rc 1. The `||`
binds to the whole pipeline, so it does rescue the pipefail status.
**What `own_fingerprints` records when `ps` fails is also correct**: given a
stubbed `own_pids` returning one live and one dead pid, only the live entry is
emitted (`[ -n "$s" ]` filters the empty start time), and `is_owned` refuses a
dead pid — *including* a hand-crafted `pid:` entry with an empty start time, so
an empty start time cannot make an entry match a recycled pid. `is_owned` also
rejects a correct pid carrying a stale start time, which is the recycling guard
working as designed.

**2. The pre-signal snapshot covers a child forked between the two moments.**
Built a tree that forks child `A` immediately and child `B` six seconds later,
took the readiness-time snapshot at t+2 and the pre-signal snapshot at t+10.
`B` is **absent** from the readiness set and **present** in the pre-signal set,
so the union covers it; `A` is in both. Killing the root then made
`descendant_pids "$ROOT"` return **empty** — the tree really is unwalkable after
signalling, which is exactly why the snapshot is taken first, and both `A` and
`B` still match the union after reparenting. A stranger does not match the
union.

**3. `pkill -P` is guarded on the parent's own fingerprint, and a recycled
`GO_PID` cannot pass it.** Tested with the real thing rather than by reading:
two untracked copies of `dev.sh` that, *after* readiness, overwrite `GO_PID`
with the pid of a **foreign** `bash` that has two children — the exact
recycled-pid state — leaving `GO_FP` pinned to the original fork.
- shipped guard: foreign parent **alive**, foreign children **2/2 alive**;
- guard replaced by `if true`: foreign parent **Terminated: 15** by
  `kill "$GO_PID"`.

So the guard is what stops `dev.sh` killing another program's process and its
children, and it is on the parent's fingerprint, not on the pid.

**4. `descendant_pids`'s fixed-point `awk` walk terminates and is correct.**
Fed the awk program a synthetic ten-deep chain emitted in **reverse** order with
two unrelated pids mixed in: it returned exactly `1000…1009` and neither
unrelated pid. On a real three-level tree (`bash → bash → sleep`, plus siblings)
it returned all five members and nothing else. The outer loop is bounded by `n`,
which is ≥ the longest possible chain, so it cannot spin.

**5. `DEV_READY_TIMEOUT` fails loudly and kills nothing it does not own.**
`go` shim replaced by `exec sleep 100000` (a genuinely stuck build),
`DEV_READY_TIMEOUT=8`, a foreign listener parked on the port after preflight:

```
  ERROR: Go server did not bind 127.0.0.1:55911 within 8s — giving up.
    Either something else holds the port, or the build is slower than the timeout (raise DEV_READY_TIMEOUT).
==> Shutting down…
  WARNING: port 55911 is now held by a process this run did not start — leaving it alone.
```

Exited in 6s of waiting rather than hanging; the foreign listener **survived**;
`dev.sh`'s own stuck `go` process was gone immediately afterwards (`pgrep` for
it returns nothing). Both halves of the failure path are right.

**Bonus probe — `release_owned_port`'s *other* branch.** No end-to-end scenario
exercises the case where the backstop actually has to reap `dev.sh`'s own leaked
child (in a clean shutdown it is a no-op, as scenario 4 shows). Unit-tested it
by sourcing the shipped `release_owned_port` against a listener I owned: with a
deliberately wrong fingerprint it printed the "did not start" warning and
**spared** the holder; with the correct fingerprint it printed
`freeing port 55912 (own process: …)` and **killed** it, leaving the port free.
Both branches behave.

### For the orchestrator to file (reported, not filed — §9)

1. **`cleanup()`'s `GO_FP` guard does not reject an empty start time, unlike
   `is_owned`.** If `go run` were to exit in the microseconds between
   `GO_PID=$!` and `GO_FP="$GO_PID:$(proc_start "$GO_PID")"`, `GO_FP` is
   recorded as `"<pid>:"`; at shutdown `proc_start` on the dead pid is also
   empty, so `[ "$GO_PID:" = "$GO_FP" ]` **matches** and `kill "$GO_PID"` /
   `pkill -P "$GO_PID"` run against a pid this run no longer owns. Verified the
   comparison does match (`GO_FP='[79391:]'`, guard true), and verified the
   contrast: `is_owned` refuses the same empty-start-time entry outright. Not
   reachable in practice — it needs a sub-millisecond `go run` death *and* pid
   recycling before shutdown, which on macOS means ~99k intervening forks — and
   the readiness poll turns that case into `ERROR: Go server exited
   unexpectedly` regardless. The one-line hardening is to require a non-empty
   start time in the guard, the way `is_owned` already does. Worth a small
   follow-up, not a bounce.
