## Description

`scripts/dev.sh`'s `free_port 5173` sends `kill -9` to whatever is listening,
without checking whose process it is. Vite's port is fixed, so two agents — or
an agent and the user — running `dev.sh` concurrently means the second silently
destroys the first's dev server mid-session.

## Steps to reproduce

1. Start `./scripts/dev.sh` (or anything else bound to `5173`).
2. Start `./scripts/dev.sh` again from another session.
3. The first server is gone, with no warning to either party.

## Expected behavior

`dev.sh` either refuses to start when `5173` is held by a process it did not
launch, or says whose it is and asks, or picks another port.

## Actual behavior

It kills the process and continues, and the owner of the killed server sees
only that their server stopped answering.

## Root cause

`free_port()` called `lsof -ti tcp:"$p"` to get every pid bound to the port
and unconditionally ran `kill -9 $pids` on the result. It never inspected
what the process *was* — a foreign agent's `go run`/`vite`, the user's editor
preview, or (as found live during verification below) an unrelated macOS
service — only that something answered on the port. Both call sites at
startup (`free_port "$PORT"`, `free_port 5173`) hit this path identically.
Neither port is configurable to sidestep the collision: `$PORT` defaults to
`8080` and can be overridden via env var, but nothing downstream reads an
override for Vite's `5173` (hardcoded in `web/vite.config.ts`'s dev server
and baked into the "Open: http://localhost:5173" messaging), so an
override wouldn't currently do anything for that port.

## Fix

Gave `free_port()` a second `force` argument and a `RECLAIM_PORTS` env var,
following the shape `#0150` settled on for `testdb.sh gc`: refuse by
default, name exactly what's blocking, and require an explicit opt-in to
override.

- **Default (no force, `RECLAIM_PORTS` unset):** if the port is held, print
  the pid and full command line for every holder (via `ps -p $pid -o
  command=`), point at `CLAUDE.md` §5a as the likely cause, list three
  options (kill it yourself if it's genuinely yours, set
  `RECLAIM_PORTS=1` to force dev.sh to reclaim it, or `lsof -i tcp:$p` to
  find the owner first), and `exit 1`. Nothing is killed.
- **`RECLAIM_PORTS=1`:** old behavior — kill and continue. This is the
  explicit opt-in for the common, safe case: a developer's own dev.sh was
  orphaned by a closed terminal and they're rerunning it.
- **The EXIT-trap backstop** (`cleanup()`'s call to free `$PORT` on
  shutdown) passes `force=1` unconditionally rather than reading
  `RECLAIM_PORTS`. That call exists specifically to catch dev.sh's *own*
  leaked `go run` child after `kill "$GO_PID"`/`pkill -P "$GO_PID"` — there
  is nothing foreign to ask permission about there, and gating it on an env
  var would leave a normal Ctrl-C failing to clean up its own mess unless
  the user happened to also set `RECLAIM_PORTS=1`.

**Considered and rejected: auto-picking a free port instead of refusing.**
`$PORT` is threaded into `BASE_URL`, `WEBAUTHN_RP_ORIGIN`, and the printed
URLs; `5173` is Vite's own dev-server port and the Vite proxy target for
`5173` is spelled directly into the "Open" message. Silently picking a
different port would mean plumbing the discovered value through all of
those, and would still leave the *caller* not knowing which URL to open
without reading the log — no quieter than telling them up front that the
port is taken. Refuse-and-name-the-holder is also the one shape that can't
regress into "kill a stranger's process," which is the actual defect here;
an auto-pick path can't make that guarantee once two agents pick different
free ports that both then get published as "the" dev URL to different
people. Rejected in favor of the explicit refuse/opt-in shown above.

**Considered and rejected: no CLI flag, env var only.** `dev.sh` already
uses env vars for every other override (`ADMIN_EMAIL`, `PORT`,
`WEBAUTHN_RP_ID`, …), documented via `KEY=value ./scripts/dev.sh` in the
header comment. Adding a matching `RECLAIM_PORTS=1` keeps that one
consistent surface instead of introducing positional-flag parsing (today's
`case "${1:-}"` only accepts a single flag) for a rare case.

## Implementation notes

Changed only `scripts/dev.sh`:
- `free_port(p, force=0)` — refuses and reports by default; kills only when
  `force=1` or `RECLAIM_PORTS=1`.
- Header comment gained a paragraph documenting `RECLAIM_PORTS=1`.
- `cleanup()`'s backstop call changed from `free_port "$PORT"` to
  `free_port "$PORT" 1` (force, since that port is dev.sh's own).

No other files touched. `shellcheck scripts/dev.sh` is clean (exit 0).

## Review notes (phase 3, 2026-08-23)

**Verdict: bounced.** The startup half of the fix is correct, and every claim in
`## Verification` reproduced independently. The `EXIT`-trap half is not: the
shipped script still `kill -9`s a process `dev.sh` never started, and the
reviewer reproduced that live. That is this issue's own defect surviving on the
shutdown path — not a follow-up, but the thing this issue exists to remove.

`uptime` before starting: load averages `1.92 1.82 1.85` — idle, so nothing
below is machine contention. Every port used (`49317`, `49318`, `49319`) was
confirmed free first, and every holder was a process the reviewer spawned and
identified by a pid the holder printed on its own stdout, cross-checked against
`lsof` (§8b — a port answering is not proof of whose it is).

### What passes

**1. Refusal, and the holder survives — the assertion that matters.** Bound a
Python listener on `127.0.0.1:49317` (pid 58806, ownership confirmed), then
`PORT=49317 ./scripts/dev.sh`:

- exit code **1**;
- pid and full command line printed for the holder;
- afterwards `ps -p 58806` still showed it, `lsof -ti tcp:49317` still returned
  it, and a fresh `socket.connect(('127.0.0.1', 49317))` **succeeded** — the
  holder was not merely alive but still accepting connections.

**2. The assertion is sensitive to the regression.** Extracted `free_port` from
`ffc796e^` (the pre-fix version) and ran it against that same holder: it printed
`freeing port 49317 (stale process: 58806)` and the process was **gone**. Same
port, same holder, opposite outcome — so the surviving-holder result above is
load-bearing, not vacuous.

**3. `RECLAIM_PORTS=1` genuinely reclaims.** Re-bound `49317` (pid 59123), ran
`RECLAIM_PORTS=1 PORT=49317 ./scripts/dev.sh`: holder 59123 gone, Go server
bound the port, Vite came up. The listener afterwards was pid 59167, whose
ancestry is `59167 ← 59162 (go run ./cmd/opencircuit serve) ← 59143 (bash
./scripts/dev.sh)` — mine by lineage, not by a hopeful `curl`. `GET /health`
returned `200 {"status":"ok","db":"ok"}`. The opt-in works; it is not an
untested branch.

**4. Ordinary path, proved to be the reviewer's own server.** With `49319` and
`5173` both confirmed free, ran
`PORT=49319 ADMIN_EMAIL=review-0117-marker@example.test ./scripts/dev.sh`.
`GET /api/me` returned
`{"id":1,"email":"review-0117-marker@example.test","is_admin":true}` — a value
that exists nowhere but this run, which is the run-specific detail §8b demands
instead of a bare `200`. Ctrl-C (SIGINT to the process group) printed
`Shutting down… ✓ stopped` and released every port.

**5. Multiple pids on one port — handled.** A forked listener sharing one socket
gave `lsof -ti tcp:49318` → `60045`, `60051`. `dev.sh` enumerated **both** with
their command lines, printed one pasteable `kill 60045 60051`, exited 1, and
**both survived**. No crash, no truncation to the first pid.

**6. Unsignalable and already-dead holders — no crash.** Probed the shipped
`free_port` with a stubbed `lsof` (the function extracted verbatim):

| Holder shape | Refusal path |
|---|---|
| pid that had already exited | `pid 60125: (process exited before it could be inspected)`, exit 1 |
| pid 1 (`launchd`, `kill` is `EPERM` for uid 501) | `pid 1: /sbin/launchd`, exit 1 |
| reaped/zombie child (`ps -o command=` is empty) | same fallback string as the exited case |

A zombie can never actually hold a listening socket — its fds are released at
exit — so the reachable case is a holder that exits between the `lsof` and the
`ps`, and that is precisely the one the fallback covers. Nothing in the refusal
path assumes `ps` succeeds. `bash -n` clean; `shellcheck scripts/dev.sh` exit 0,
no findings. The diff is confined to `scripts/dev.sh` (42 insertions, 4
deletions, one file). The message meets `#0187`'s pasteable standard: `kill
60045 60051` and `lsof -i tcp:49318` can both be pasted as printed.

**7. The incidental finding is real, and still live.** `:8080` is held right now
by pid 69367,
`/System/Library/PrivateFrameworks/WebDriver.framework/…/com.apple.WebDriver.HTTPService`,
owner `brennan`, started 2026-08-22 14:55 — i.e. **killable by the old code**,
which would have `kill -9`ed a macOS system service on any plain
`./scripts/dev.sh`. The hazard this issue describes is not hypothetical on this
machine; it is the default state of it.

### What must change before this resolves

**The `EXIT` trap re-derives the holder from the port and kills a stranger.**
`cleanup()` does not track a pid it started. It runs
`free_port "$PORT" 1`, whose first act is `lsof -ti tcp:"$p"` — *at exit time*.
The commit message's justification ("that process is unambiguously ours") is
therefore false whenever `$PORT` changed hands during the session.

Reproduced live, against the shipped `ffc796e`:

1. `RECLAIM_PORTS=1 PORT=49317 ./scripts/dev.sh` running normally (listener
   59167, a descendant of the script).
2. `kill -9 59167 59162` — the Go server dies mid-session, as a panic or a
   stray `pkill` would do. Port `49317` goes free.
3. A **foreign** process binds `49317` (pid 59487 — stand-in for the other
   agent §5a permits).
4. SIGINT to `dev.sh`'s process group, i.e. an ordinary Ctrl-C.
5. Trap output: `freeing port 49317 (stale process: 59487)`. Pid 59487 was
   **`kill -9`ed**. `ps -p 59487` afterwards: nothing.

`dev.sh` killed a process it did not start, printed the old "stale process"
wording while doing it, and gave the owner no warning — the exact behaviour in
this issue's `## Actual behavior`, relocated from startup to shutdown.

A second reachable route needs no crash at all: two `dev.sh` runs that both
clear `free_port` before either binds (a sub-second window, and §8b exists
because agents do collide on fixed ports). The loser's `go run` fails with
`address already in use`, the loser's trap then fires and kills the **winner's**
server. That is this issue's "Steps to reproduce" verbatim.

Note also that the trap is nearly always a no-op: in the clean shutdown above,
`kill "$GO_PID"` + `pkill -P "$GO_PID"` had already reaped the child and no
`freeing port` line was printed at all. So the backstop is doing almost nothing
in the normal case, and everything in the dangerous one — which is a good trade
to make ownership-checked.

**Required:** make the backstop kill only pids it knows are its own. The cheapest
correct shape is to record the holders once the server is confirmed up (after
the `kill -0 "$GO_PID"` check, e.g. `OWNED_PIDS="$(lsof -ti tcp:"$PORT")"`) and
have `cleanup()` kill only the intersection of that set with the current
holders, printing the ordinary refusal text (as a warning, not an `exit 1` —
this is the shutdown path) for anything outside it. Walking `GO_PID`'s
descendants at exit time works equally well. Either way the invariant to hold is
the one the issue title states: *no `kill` of a pid this run did not start.*

**Secondary, fix in the same pass.** The force path never confirms the port was
actually freed. With an unsignalable holder (probed with pid 1) `kill -9` fails,
the failure is swallowed by `2>/dev/null || true`, and `free_port` returns 0
after printing `freeing port 49999 (stale process: 1)` — so the log claims the
port was cleared, and the run fails later with a confusing
`address already in use`. Re-check with `lsof` after the `sleep 1` and report
honestly if the port is still held.

### Two findings for the orchestrator to file (reported, not filed — §9)

1. **`PORT` is only half-honoured, and this issue's rejected-alternative
   reasoning names the wrong mechanism.** `## Fix` argues auto-picking a port is
   costly because "`$PORT` is threaded into `BASE_URL`, `WEBAUTHN_RP_ORIGIN`".
   It is not: `dev.sh` lines 39 and 41 hardcode `http://localhost:8080`
   independently of `$PORT`, and `web/vite.config.ts` hardcodes all four proxy
   targets to `http://localhost:8080` while line 177 prints
   `Vite proxies … → http://localhost:${PORT}`. So `PORT=49319 ./scripts/dev.sh`
   already produces a Vite proxy aimed at `:8080` — on this machine, at the
   WebDriver service — and a message that says otherwise. Pre-existing, not
   introduced here.
   **The conclusion still stands, on better grounds.** `5173` really is spelled
   into `web/vite.config.ts`, `README.md:61`, `docs/dev.md:12,24`,
   `CLAUDE.md:209`, and three of `dev.sh`'s own messages, so auto-picking it is
   genuinely not free; and the half-honoured `PORT` override above is a live
   demonstration of what silently picking a different port produces. Refuse and
   name the holder is the right call.
2. **No regression test.** The implementer's own suggestion, and it is the right
   one: `scripts/testdb_gc_guard_test.sh` (`#0150`) is the model. The
   assertions are already written out above — bind a throwaway port, assert
   exit 1, assert the holder still answers a connect, assert `RECLAIM_PORTS=1`
   reclaims, and (once fixed) assert a foreign holder survives the `EXIT` trap.

**Cleanup (§5a).** Every process started by this review was killed: holders
58806, 59123, 59487, 60045, 60051, and both `dev.sh` runs with their `go run`,
compiled binary, `npm`, and `vite` children. `lsof -ti` on `49317`, `49318`,
`49319`, and `5173` all return nothing; `pgrep -fl 'dev.sh|opencircuit|go run
./cmd|vite|esbuild|holder-0117|multi-0117'` is empty. No database was created or
touched — this issue has no DB surface. `:8080`'s WebDriver service was left
strictly alone.

## Notes

Found during `#0116`'s review (2026-08-21), which pre-checked the port by hand
and found it free. Pre-existing behaviour, not introduced by `#0116` — filed
separately rather than widening that issue's scope.

This is the same hazard class `CLAUDE.md` §8b already documents from the other
direction: an agent once bound a fixed shared port, its own bind failed, and
`curl` cheerfully returned 200 from *another agent's* server on that port. §8b
tells agents not to trust a shared port; this issue is the tooling doing the
destroying rather than the trusting.

Subagents frequently run concurrently in this repo (§5a permits two at once),
so this is reachable in normal use, not a hypothetical.
