## Description

`internal/testdb`'s `TestDiagnoseLockHolders_IgnoresLocksInOtherDatabase` fails
consistently:

```
lock_diagnosis_test.go:553: expected audit_log's oid to be identical across a
template clone (the precondition that makes #0234 reachable at all),
got ours=23834384 sibling=22246789
```

The assertion is a **precondition check**, not the behaviour under test. It
exists because `#0234`'s bug — `diagnoseLockHolders` reporting locks held in a
*different* database — is only reachable when the same relation carries the same
oid in two databases, which is what cloning from a shared template normally
guarantees. When the oids differ, the test cannot exercise what it was written
to exercise, so it fails rather than passing vacuously. **That design is
correct**; the failure is real information, not a broken assertion.

What it is telling us is that the two databases were **not clones of the same
template generation**. Reproduced by the orchestrator on a database created
immediately after `scripts/testdb.sh` rebuilt the template from scratch (all 25
migrations), so it is not a one-off stale-template artifact.

It is **pre-existing and unrelated to any current work**: the file last changed
at `dd845c9` (`#0234`), and `#0297`/`#0302`/`#0303` touch neither
`internal/testdb` nor `migrations/`.

### Why it matters beyond the one test

`internal/testdb` is infrastructure every DB-backed suite depends on. A
consistently red test there is exactly the kind of standing noise that trains
agents to skim failures, and `CLAUDE.md` §5 already warns that a green run can
prove less than it looks like it does. It should be either fixed or
consciously marked.

Note also that `scripts/testdb.sh` prints a migration/template digest-mismatch
warning (citing `#0320`) when provisioning against a stale template. Determine
whether that mechanism and this failure share a root cause — a template
generation drifting from `migrations/` — or are independent.

## Acceptance criteria

1. Root cause identified: why the sibling database's `audit_log` oid differs
   from ours when both are expected to descend from one template generation.
   Name the mechanism, do not just make the test pass.
2. If the precondition is legitimately unreachable in some environments, the
   test **skips with a message naming why**, rather than failing — and the skip
   is narrow enough that `#0234`'s regression is still caught wherever the
   precondition does hold.
3. If the cause is a template generation drifting from `migrations/`, the fix
   addresses that, and its relationship to `#0320`'s digest mechanism is stated.
4. `go test ./internal/testdb/...` is green with `TEST_DATABASE_URL` set, with
   zero skips other than any introduced by criterion 2 and documented there.
5. Verified on a database created immediately after `scripts/testdb.sh template`
   rebuilds, and on one created without a rebuild, so both generations are
   covered.
6. `#0234`'s original regression is still caught — prove it by mutation, in a
   throwaway worktree, restored and hash-verified.
7. No change to `migrations/`. They are append-only and `000001`–`000022` are
   frozen (§1); `migrations/` now runs to `000025`.
