## Description

`internal/testdb`'s `TestDiagnoseLockHolders_IgnoresLocksInOtherDatabase` fails
consistently:

```
lock_diagnosis_test.go:553: expected audit_log's oid to be identical across a
template clone (the precondition that makes #0234 reachable at all),
got ours=23834384 sibling=22246789
```

The assertion is a **precondition check**, not the behaviour under test. It
exists because `#0234`'s bug — `diagnoseLockHolders` reporting locks held in a
*different* database — is only reachable when the same relation carries the same
oid in two databases, which is what cloning from a shared template normally
guarantees. When the oids differ, the test cannot exercise what it was written
to exercise, so it fails rather than passing vacuously. **That design is
correct**; the failure is real information, not a broken assertion.

What it is telling us is that the two databases were **not clones of the same
template generation**. Reproduced by the orchestrator on a database created
immediately after `scripts/testdb.sh` rebuilt the template from scratch (all 25
migrations), so it is not a one-off stale-template artifact.

It is **pre-existing and unrelated to any current work**: the file last changed
at `dd845c9` (`#0234`), and `#0297`/`#0302`/`#0303` touch neither
`internal/testdb` nor `migrations/`.

### Why it matters beyond the one test

`internal/testdb` is infrastructure every DB-backed suite depends on. A
consistently red test there is exactly the kind of standing noise that trains
agents to skim failures, and `CLAUDE.md` §5 already warns that a green run can
prove less than it looks like it does. It should be either fixed or
consciously marked.

Note also that `scripts/testdb.sh` prints a migration/template digest-mismatch
warning (citing `#0320`) when provisioning against a stale template. Determine
whether that mechanism and this failure share a root cause — a template
generation drifting from `migrations/` — or are independent.

## Root cause

**The two databases were built by two different mechanisms, and relation oids
are assigned at creation time from a cluster-wide counter.**

`TestDiagnoseLockHolders_IgnoresLocksInOtherDatabase` compared two databases of
unlike provenance. The sibling was always an explicit
`CREATE DATABASE ... TEMPLATE opencircuit_test_template` clone, hard-coded in
the test. "Ours" was whatever `TEST_DATABASE_URL` named — the database
`scripts/testdb.sh create` had handed back, whose provenance depends on the
environment. `#0315` made that dependence deliberate: when the shared template
disagrees with the working tree's `migrations/`, `create` stops cloning and
calls `provision_from_migrations`, which creates an empty database and runs a
full `migrate up` against it so the schema matches the working tree exactly.
A `migrate up` database and a template clone have no reason to share oids, and
they do not.

So the assertion was over-strong. It conflates two claims: that template clones
share oids, which is the `#0234` hazard and is always true, and that *your own*
database is a template clone, which `#0315` makes false by design.

### Measured, not inferred

Two arms, one machine, one `migrations/` tree at `000027`:

| Arm | How the databases were built | `audit_log` oid |
|---|---|---|
| A | one private template, two `CREATE DATABASE ... TEMPLATE` clones | `59945228`, `59945228` — **identical** |
| B | two independent `migrate up` runs | `59945743`, `59946256` — **differ** |
| C | the real failing pairing: a `migrate up` database vs a template clone | `59945743` vs `59945228` — **differ** |

The reproduction under `ISSUE=0339 scripts/check.sh` reported
`ours=59946772 sibling=31567648`, and `31567648` is exactly the shared
template's own `audit_log` oid measured independently beforehand — the sibling
was the template clone, and "ours" was not.

### Why the template disagrees right now, and why that is *not* a stale environment

The shared template stamps version **28** while this working tree's
`migrations/` runs to **000027**. That looks like `#0360`, and it is not.

The template's content digest is `07e7947b8f9e2361...`. Recomputing
`disk_digest` over the `migrations/` directory of the git worktree
`.claude/worktrees/agent-a16d8f8a64eadf32f` yields the same
`07e7947b8f9e2361...`. That worktree carries an uncommitted
`000028_create_crt_commands` migration pair. The shared template is therefore
**healthy and current for the tree that built it** — it is legitimately ahead of
this checkout, not stale.

That is precisely the condition `#0315` designed `warn_template_mismatch` and
the direct-provisioning fallback for, and `build_template` warns about it in so
many words. It recurs every time any agent adds a migration in a worktree, so
it is a permanent, expected state rather than a defect to repair.

### Relationship to `#0360` and to `#0320`

**`#0339` is a defect of its own, not a symptom of `#0360`.** `#0360` describes
a genuinely stale database — a migration recorded as applied whose DDL never
took effect — and repairing it would make this symptom disappear today. It
would return on the next worktree migration, because the fallback that produces
it is correct behaviour. Nothing here is `#0360`'s to fix, and `#0360` needs no
change on this account.

`#0320`'s digest mechanism shares a root cause with the *filed* observation but
not with the defect: the digest is what detects the disagreement that routes
`create` down the `migrate up` path, so it is the proximate trigger. It is
working as intended. This also explains the Description's puzzling claim that
the failure reproduced immediately after a from-scratch template rebuild: at
filing time `#0123` had amended `migrations/000025` in place, so the version
matched on both sides while the digest did not, and `create` fell back exactly
as it does today.

## Fix

`TestDiagnoseLockHolders_IgnoresLocksInOtherDatabase` now creates **both**
databases itself, as two clones of one template generation, and runs
`diagnoseLockHolders` against a pool it opens on one of them. Neither side is
the ambient `TEST_DATABASE_URL` database.

This is not a weakened precondition — it is the same precondition asserted
between the right pair of databases. It restores exactly what `#0234`'s own
review measured: two `scripts/testdb.sh`-shaped clones, each asked for its own
`audit_log` oid. The assertion still fails, loudly, if Postgres ever stops
preserving relation oids across `CREATE DATABASE ... TEMPLATE`, which is the
property `#0234`'s fourth acceptance criterion exists to protect. What it no
longer does is fail because of how this agent's own database happened to be
provisioned.

No skip was added, so criterion 2 does not apply — the precondition is now
reachable in every environment that has a template at all, which the test
already required. `migrations/` is untouched, satisfying criterion 7.

## Gotchas

**A precondition assertion is only as good as the pair it compares.** This one
was correct about the property and wrong about the operands, which is why it
read as a broken environment for twelve days. When a test asserts that two
things built by a shared mechanism agree, it has to build both of them — taking
one from the ambient environment silently imports that environment's
provenance into the assertion.

**`scripts/testdb.sh create` handing back a database is not a promise that it
cloned.** The fallback is silent apart from a note on stderr, which a Go test
never sees. Anything that depends on clone semantics rather than merely on
schema correctness must create its own clone.

### Scope and skip audit

No skip was added. The inlined `lockDiagPool == nil` check is byte-equivalent in
effect to `lockDiagPoolOrSkip`, which is nothing but that nil check and is still
used by seven other tests in the file. `migrations/` is untouched — the commit
carries one file. Both template generations were exercised, satisfying criterion
5: a run where the ambient database was a clone, and one where the digest
mismatch sent it down a full `migrate up`.

**Minor observation, not a defect.** The test now takes two
`CREATE DATABASE ... TEMPLATE` windows instead of one, and Postgres refuses that
statement while any session is connected to the template. The ordering is
correct — both databases are created before the pool opens, so this test never
holds a connection that blocks its own second clone — but under three concurrent
agents it is marginally more contention than before. Inherent to the approach
and the approach is right.

### On the implementer's note for `#0360`

**Agreed on the substance, with one refinement.** A template *ahead* of a
checkout is a legitimate and recurring state under `#0315`, not staleness, and
any detection added for `#0360` must classify it as such — a rebuild in that
case would destroy a healthy template out from under the worktree that owns it,
which is a worse outcome than the fallback it would be trying to avoid. The
signal is cheap and unambiguous, since a template version above the tree's is
distinguishable from one below it and from an in-place edit at equal versions.

The refinement: criterion 4 as written already asks for a diagnosis that names
what disagrees, which is compatible with reporting "ahead" correctly. The risk
is in how an implementer reads it, not in the words. `#0360`'s own failure mode
is orthogonal — it is detectable only by column census — so nothing there needs
to change on `#0339`'s account.
