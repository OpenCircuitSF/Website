## Description

Nothing is sent after a successful double opt-in confirmation. The welcome message is the highest-engagement email the list will ever send and the natural place to set expectations about frequency and show the way out — both of which measurably reduce complaints later.

## Implementation notes

Phase 2 (Sonnet), 2026-08-24. No separate phase-1 planning pass ran; design
decisions were made and disclosed inline (code comments + this section)
rather than in a `## Plan`.

**`internal/subscribers.Store.Confirm`** enqueues `outbox.KindWelcome`
inside its own confirmation transaction, immediately after recording the
`confirmed` event — mirroring #0126's "committed signup can never have an
unsent confirmation" one step later in the flow: a committed confirmation
can never have an unsent welcome. Two guards run first, inside the same
transaction:

- **Suppressed addresses.** Checked via a direct `EXISTS (SELECT 1 FROM
  suppressions WHERE email = $1)` inline in `Confirm` rather than going
  through `SuppressionStore` — same package, same transaction, no second
  round trip. The subscriber still confirms normally (status → active);
  only the welcome enqueue is skipped.
- **Complained subscribers.** `Confirm` already refuses with
  `ErrComplainedLocked` before any of this runs, so a complained subscriber
  never reaches the enqueue at all — proved explicitly rather than left
  implicit (`TestConfirm_ComplainedSubscriberNeverGetsWelcome`).

**"Sent exactly once per subscriber; a second confirmation does not
re-send"** is true by construction, not by a separate check: `confirm_token`
is single-use (cleared to `NULL` on activation), so a retried `Confirm` call
with the same, now-stale token returns `ErrTokenInvalid` before reaching the
enqueue.

**Selected interest names** are read inside `Confirm`'s transaction via a
new `selectedInterestNamesTx` — a raw join against `interests` (no import of
`internal/interests`, keeping this package a leaf per its own package doc
comment) — and stored in the queue payload. Read AT CONFIRM TIME, not
re-read by the worker at send time, so a later preference change can't
retroactively rewrite what the email already said.

**`internal/mailing.BuildWelcomeEmail`** is a seventh template. Content:
what Open Circuit SF is (paraphrased from `Home.svelte`'s own "What this
is" copy), the subscriber's selected interests (or a general-announcements
fallback when none), a "roughly once a month" cadence line (flagged the
same way `About.svelte` flags it — sourced from PRD §4.1's own reference
layout, not invented), a CTA to `/workshops`, and the standard
manage/unsubscribe footer + physical address via `ShowListFooter`.

**Deliberate, disclosed departure:** unlike every other template in this
file, `BuildWelcomeEmail` carries the RFC 8058 `List-Unsubscribe` /
`List-Unsubscribe-Post` / `List-Id` header set (via the same
`CampaignHeaders` helper campaign mail uses) — historically "campaign mail
only" in this package's own doc comments. #0127's acceptance criteria name
the headers explicitly for this message, and the privacy policy's "every
campaign email carries a one-click unsubscribe link" is a floor commitment,
not an exclusivity claim, so this does not contradict it. Both package doc
comments (`templates.go`, `transactional_templates.go`) and
`TestNoTransactionalMessageCarriesCampaignHeaders` are updated to state and
prove this positively for "welcome" going forward, the same way they already
did for "campaign".

**No `/archive` link**, per this issue's own Notes: #0127 depends on #0123
(the public campaign archive), which had not landed when this was
implemented. Pinned by `TestBuildWelcomeEmail_NoArchiveLink`. Add the link
once #0123 lands.

**`internal/mailing.OutboxWorker`** renders `KindWelcome` from a new
`welcomePayload` (mirrors `internal/subscribers.welcomePayload`
field-for-field, matched by JSON field name per this package's existing
producer/consumer convention) and writes `welcome_sent` on `MarkSent` — the
exact `confirmation_sent` precedent (#0126's plan §6: written when the
message actually LEAVES the queue, not at enqueue time). `listDomain`
(`config.Config.EmailListDomain`) is threaded through
`OutboxWorkerDeps`/`OutboxWorker` and wired in `main.go`'s
`newOutboxWorker`, since `BuildWelcomeEmail` needs it for the header set.

**Disclosed design call (flagged for the reviewer, not resolved
unilaterally):** a subscriber who unsubscribes and later resubscribes
(`RestartSignup`) gets a fresh `confirm_token` and, on that later `Confirm`,
a SECOND welcome email. The acceptance criterion's "second confirmation of
an already-confirmed address does not re-send" reads as token-replay
protection, not a lifetime cap across a genuine resubscribe — but this is a
judgment call, not a certainty.

**Closed-set guard updated.** `#0126`'s
`TestSubscriberEventActions_EveryConstantHasCallSiteOrOwner` named `#0127`
as `ActionWelcomeSent`'s pending owner. That entry moved from
`ownedByLaterIssue` to `hasCallSite`. Verified the guard is load-bearing by
manually removing the entry (leaving `welcome_sent` with neither a call
site nor an owner) and observing the exact failure ("has neither a call
site nor a recorded owner issue — the closed set has rotted"), then
restoring the file and confirming the restored content hashes identical to
the pre-mutation copy (`shasum -a 256`).

### Rulings on the two questions the implementer flagged

**1. The `List-Unsubscribe` / `List-Unsubscribe-Post` / `List-Id` departure
is CORRECT.** Judged on the merits, not on the disclosure:

- A welcome email to a *confirmed* subscriber is list mail addressed to a
  consenting member, and it is promotional — it advertises workshops and
  carries a CTA. Gmail's and Yahoo's bulk-sender requirements ask for
  one-click unsubscribe on exactly that class of message. Omitting the
  headers here would be the defect; carrying them is the safer reading.
- The messages that must **not** carry them still do not. A double opt-in
  confirmation is the clear case: the recipient is not yet subscribed, and a
  one-click unsubscribe on it would be incoherent. All six purely
  transactional templates (`confirmation`, `already_subscribed`,
  `registration`, `recovery`, `sessions_revoked`, `admin_alert`) still carry
  zero custom headers, and the test enforces it.
- **`#0035` is not violated in substance.** Its criterion 5 ("headers applied
  to campaign mail only — not to transactional confirmation or auth mail")
  enumerates an exclusion list that the welcome is not on; the welcome did
  not exist when `#0035` was written. Its literal "campaign mail only"
  phrasing is now inaccurate, though — worth a one-line note on `#0035`
  someday, not this issue's job.
- **`#0045` is not affected.** Its `list_domain_unset` preflight gates
  *campaign* sends; the welcome path reaches `CampaignHeaders` directly,
  which already degrades to a valid HTTPS-only header set on a blank
  `listDomain` rather than emitting a malformed `mailto:` (`#0105`).
- **The test now proves the rule positively, not permissively** — this was
  worth checking, because a `continue` that merely *skips* welcome would look
  identical in a passing run. `oneClickNames` drives both halves: the
  skip-list and a second loop that requires a `List-Unsubscribe` on each
  named message. Mutation-confirmed above: removing the assignment fails the
  welcome case by name.

**2. A resubscriber getting a SECOND welcome is CORRECT.** The criterion
reads "a second confirmation of an **already-confirmed** address does not
re-send", and someone who unsubscribed is not an already-confirmed address —
`RestartSignup` puts them back to `pending` with a fresh token, and they
complete a genuinely new double opt-in. The welcome exists to set
expectations and show the way out at the moment consent is given; a person
rejoining after leaving is owed that as much as a first-timer, and their
interest selection may well have changed, which the welcome reflects (the
payload is read at confirm time). Token-replay protection is the property
the criterion is about, and it holds. No change needed.
