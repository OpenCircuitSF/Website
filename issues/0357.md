## Description

Two prose defects in `CLAUDE.md` §8's satisfier-set entry. Neither misleads a
reader who reads the surrounding sentence — both do when quoted or skimmed,
**which is exactly how `#0346`'s inversion propagated**: illustrative prose was
lifted out of context, transcribed into an issue as though measured, copied
into `CLAUDE.md`, and survived a full verification pass before a three-tree
`go/types` measurement caught it.

**1. A triple negative predicated of the wrong thing.** `#0350` added:

> — a type whose own method the commit never edited, though not a file it never
> touched:

Three negations in sixteen words, and "not a file…" is predicated of a *type*.
Excerpted without the gloss that follows the colon, it asserts the opposite of
the fact.

**Exact remedy** (from `#0350`'s review, which reported it rather than patching
it): replace with

> — a type whose own code the commit never changed, in a file it did touch:

One negation, no category slip, one word shorter, both facts intact. Everything
after the colon stays byte-identical.

**2. A dangling "it" that is now false under the likelier binding.** In the
value-receiver paragraph, untouched since `#0346`:

> `go/types` is the sound oracle, since … not something an AST walk can fully
> reconstruct on its own (**it** also can't see a method acquired by embedding
> … or hiding behind a generic receiver …)

The intended antecedent is *the AST walk*. A reader can bind "it" to
`go/types` — and since `#0349`/`#0353` that reading is **false**, and
contradicted by the very file the sentence points at, where
`types.Implements` resolves promotion and generic receivers.

**Exact remedy**: change "it also can't see" to "an AST walk also can't see".

  internal/seo/sitemap.go` is **exactly one hunk** (`@@ -145,8 +145,10 @@`),

### Criterion 1 — sentence 2, re-derived rather than inherited

`an AST walk also can't see a method acquired by embedding a satisfying struct
or interface field, or hiding behind a generic receiver`. I did not take this
from `#0337`'s reviews. I type-checked a synthetic package with `go/types`
(stdlib only, run from the scratchpad outside the checkout; `git status --
go.mod go.sum` clean before and after) containing a promoting embedded
**struct** field, a promoting embedded **interface** field, and a **generic**
receiver, then ran a naive AST scan of method declarations accepting both
pointer and value receivers of the plain form over the same source:

```
go/types.Implements satisfiers : [*Base *EmbedIface *EmbedStruct *FeedCache EmbedIface EmbedStruct Iface]
naive AST declaration scan     : [Base]
```

The AST scan misses **all three** — both promotion cases and the generic
receiver (whose receiver is `*ast.StarExpr{*ast.IndexExpr}`, not the plain
`*ast.Ident` form). `go/types` resolves all three with no manual
`types.Instantiate`. So the sentence is true, and it does **not** understate
`go/types`: the blind spots are now attributed unambiguously to the AST walk,
which is the correction `#0349`/`#0353` made necessary. The old dangling "it"
could bind to `go/types`; the replacement admits no such binding, because it
names its subject.
