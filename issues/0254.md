## Description

`#0126`'s plan makes **committed signup ⇒ queued confirmation** durable: the
insert and the enqueue share one transaction, so a crash cannot separate them.

It does not make **accepted `202` ⇒ committed signup** durable. `#0088` moved
subscribe's work off the request goroutine onto an **in-memory** `mutateQueue`,
which is where the uniform-202 timing guarantee comes from (§9 — the response
must not vary by whether an address is already on the list). That queue is
lossy:

- On **shutdown**, anything still queued is dropped.
- On **queue-full**, the job never runs.

In both cases the subscriber already received a `202`. They believe they signed
up. Nothing was written, no confirmation will ever arrive, and **no record
exists that it happened** — the failure leaves no trace to reconcile against,
which is what separates this from an ordinary dropped job.

**`#0126` narrows the window rather than closing it**, and that is the right
scope for that issue. This is the remaining half, and it is worth being
explicit that the two are different guarantees rather than one job half-done.

**The uniform-202 rule is why this is awkward.** The obvious fix — write
synchronously, return after the commit — is precisely what `#0088` removed,
because a synchronous write makes the response time vary with whether the
address already exists, turning the endpoint into a timing oracle. Any fix here
must preserve byte-identical bodies **and** indistinguishable timing. `#0126`'s
plan is explicit that its enqueue must not move onto the request path for the
same reason.

## Acceptance criteria

- [x] Shutdown drains or persists in-flight jobs; a job lost at shutdown leaves a record that can be reconciled
- [x] Queue-full is handled deliberately — shed with a different status, block, or persist — rather than silently dropping an accepted request

- [x] `ISSUE=0254 scripts/check.sh go ./internal/...` passes with zero skips

## Root cause

`#0088` moved every branch-dependent write for `POST /api/subscribe` onto
`mutateQueue`, an in-memory Go channel, specifically so `mailer.Send`/the
account mutation would never run on the request goroutine (the fix for the
timing-oracle findings in `#0026`/`#0088`). `#0126` made the confirmation
enqueue transactional with the subscriber write *once that job actually
ran*, but the job itself — the honeypot verdict, the two fixed reads, and
which mutation to run — still lived only in that channel. Two failure modes
existed with nothing to show for them afterward: `enqueueMutation`'s
queue-full branch dropped the job outright, and a process kill (or a
`Close` whose bound elapsed) could lose a job that was queued or mid-flight.
In both cases the client had already received the `202`.

## Fix

Reused `internal/outbox`'s `outbound_queue` (the durable queue `#0126`
built) rather than inventing a second mechanism:

- Added `outbox.KindSubscribeIntake` — not an email, a durable record of
  "a `202` was returned for this address." Added `Item.Delay` (so a row can
  be enqueued already due some duration in the future), `Store.MarkDone`
  (transitions `'queued'` **or** `'sending'` straight to `'sent'`, for a
  caller that finishes a row without ever claiming it via `ClaimDue`), and
  a `kinds` filter on `ClaimDue` (so `outbound_queue`'s two independent
  consumers — `internal/mailing.OutboxWorker` for mail,
  `SubscribeHandler`'s own recovery poller for intake rows — never steal
  each other's rows; `internal/mailing/outbox_worker.go` now claims via an
  explicit `mailKinds` list).
- `Subscribe` (`internal/handlers/subscribe.go`) now performs a third,
  unconditional, fixed-cost synchronous write — one `KindSubscribeIntake`
  row, identical in shape across every branch (isBot included) — right
  before the `202`. By the time a client sees the response, that row is
  committed. This does not reopen the timing-oracle finding: no branch
  gains or loses request-path work by this write existing.
- `mutateQueue`/`processMutateJob` are otherwise unchanged (the fast path):
  `processMutateJob`'s dispatch logic was factored out into
  `dispatchMutation` so a second call site could reuse it verbatim, and a
  `defer h.markIntakeDone(...)` marks the durable row done once dispatch
  returns, regardless of outcome — the same "processed, not necessarily
  succeeded" convention every branch already followed.
- A new recovery poller (`internal/handlers/subscribe_intake.go`),
  auto-started by `NewSubscribeHandler` and stopped by the existing
  `Close` (no new wiring in `main.go`/`mountAndServe` beyond one new
  `*outbox.Store` constructor argument), claims any `KindSubscribeIntake`
  row still `'queued'` once `intakeGraceDelay` (a generous multiple of the
  fast path's own bound) has passed, and reprocesses it through the exact
  same `dispatchMutation` — re-reading suppression/`FindByEmail` fresh
  rather than trusting anything captured at the original request. Running
  that dispatch twice for the same signup is safe by construction, not by
  luck: `Create`'s `ErrEmailExists` handling (`#0026`) and
  `ClaimAndEnqueueConfirmation`/`ClaimAndEnqueueAlreadySubscribed`'s
  atomic, cooldown-gated claims (`#0126`) already make a second attempt a
  safe no-op — the same idempotency two concurrent human requests already
  relied on.

**Uniform-202/timing**: unchanged from `#0088`'s design — every branch
still performs exactly the same synchronous work (now three fixed steps
instead of two), and every branch-dependent decision still happens off the
request goroutine. `TestSubscribe_SyncQueryCountEqualAcrossBranches`
(pre-existing, still passing unmodified) continues to prove the
suppression/`FindByEmail` call counts are fixed per branch; the new
durability write adds no branch, so it introduces no new observable.

## Gotchas

- **`outboundQueueRowsFor`/`outboundQueueCountFor`/`outboundQueueCountWiring`
  all needed a kind filter.** Any test helper written before this issue that
  counts `outbound_queue` rows "for this recipient" now silently includes
  the new intake row unless scoped — this bit the wiring test above and
  would have bitten any future one written the same way. There is no
  compile-time signal for this; only a test run surfaces it.
- **The recovery poller races its own construction if driven directly.**
  An earlier version of `TestSubscribeIntakeWorker_RecoversRowTheFastPathNeverProcessed`
  called `h.intakePass()` explicitly for determinism (mirroring how
  `internal/mailing/outbox_worker_test.go` drives `OutboxWorker.pass`
  directly) — but `NewSubscribeHandler` already starts `runIntakeWorker` as
  a background goroutine (unlike `OutboxWorker`, whose `Run` the caller
  starts explicitly), so the explicit call raced the background one for the
  same seeded row and intermittently found nothing left to claim. Fixed by
  polling for the outcome instead of driving the pass by hand — see that
  test's own doc comment.

**Sequencing:** this should follow `#0126`, not precede it. `#0126` builds the

completed — but this endpoint's copy tells the subscriber to check their email,
which is a promise. Either the plumbing or the copy has to change.

### The defect — `ClaimDue` was filtered by kind; `OrphanSweep` was not

`internal/outbox.Store.OrphanSweep` has **no** kinds filter, and this commit
gives it a second caller with a much shorter stale window derived from a
different subsystem's bound:

| Caller | Window | Legitimate hold it must not interrupt |
|---|---|---|
| `mailing.OutboxWorker.pass` | `outboxOrphanStaleAfter` = `2*(30s+5s)` = **70s** | `sendMessageTimeout` (30s, incl. SESMailer throttling retries) + `writeStatusTimeout` (5s) |
| `SubscribeHandler.intakePass` (new) | `intakeOrphanStaleAfter` = `2*mutateJobTimeout` = **20s** | the intake path's own 10s bound |

The 70s figure exists precisely because a live mail claim can legitimately sit
in `'sending'` for up to 35s. The new 20s sweep runs every 5s, in the same
process, over **every kind**.

Proven, not argued. Driving the real `h.intakePass()` against a `confirmation`
row claimed 25s ago:

```
WARN subscribe: intake orphan sweep reclaimed rows count=1
mail row after the intake poller's pass: status="queued" claimed_at=<nil>
DEFECT: a live mail claim (25s old, well inside the mailing worker's own 1m10s
legitimate window) was reset to "queued" by the intake poller's unfiltered
OrphanSweep(20s) — it is now claimable and sendable a second time
```

And the consequence, proven at the store level in the same worktree:

```
first send's MarkSent affected 0 rows (OutboxWorker.sendOne discards this bool)
DEFECT CONFIRMED: row 1 (kind=confirmation, recipient=…) was re-claimed after
the intake poller's sweep released a live claim — the same message is rendered
and sent a second time
```

The chain in full: intake sweep releases the live claim → the in-flight send's
`MarkSent` requires `status='sending'` and so affects zero rows, which
`sendOne` discards (`if _, err := w.store.MarkSent(...)`) → the row stays
`'queued'` → the next pass claims and **sends it again**. That is a duplicate
confirmation, registration magic link, or recovery link — the exactly-once
property `#0254` and `#0260` both rest on.

**Reachability is not exotic.** `pass` claims a batch of up to
`outboxDefaultBatchSize` (20) rows in one `UPDATE`, stamping them all with the
same `claimed_at`, then sends them **serially** behind a `rate.Limiter`. At the
SES sandbox's 1 msg/sec (CLAUDE.md §10 item 2, the configuration this project
is in today) the eleventh row of a batch has already been `'sending'` for
20 seconds. A single slow send also does it on its own, since 30s is inside the
mailing worker's documented legitimate window.

It is also a latent test-cross-talk source: every `NewSubscribeHandler` in
`internal/handlers`' suite starts a poller sweeping the shared per-agent
database every 5 seconds, while `internal/mailing` may be running against the
same database under `-p 2`.

### What the next pass must change

1. **Give `OrphanSweep` a `kinds ...Kind` filter**, exactly mirroring the one
   just added to `ClaimDue` (same `cardinality($n::text[]) = 0 OR kind =
   ANY(...)` predicate, same "no kinds means every kind" default), and pass
   `mailKinds...` from `mailing.OutboxWorker.pass` and
   `outbox.KindSubscribeIntake` from `SubscribeHandler.intakePass`. Neither
   consumer may touch the other's rows, in *either* direction — claiming or
   sweeping.
2. **Add a regression test that fails against `4af0ea3`.** A `confirmation`
   row claimed inside the mailing worker's legitimate window must still be
   `'sending'` after an intake pass. The two probes above are the shape; both
   fail on the current tree and must pass after the fix.
3. **Close the `mailKinds` completeness hole while you are there.** `mailKinds`
   is a hand-maintained list of nine kinds and there is no guard on it. Before
   this commit an unrecognised kind was claimed and hit `render`'s default case,
   failing loudly; now a `Kind` added to `internal/outbox` and forgotten in

   list*, not one omitted *from* it. A cheap guard: a test asserting every
   `outbox.Kind` constant is either in `mailKinds` or is `KindSubscribeIntake`.

Everything else in the commit stands; this is an addition, not a rework.

### The AST guard, against CLAUDE.md §8

Mutation-proved rather than read, three ways:

1. **Adding `KindReviewProbe Kind = "review_probe"` to `internal/outbox`
   without touching `mailKinds`** → guard fails, naming the constant. It is
   load-bearing.
2. **Removing the explicit `Kind` type from every constant (a total parse
   break)** → `found zero Kind constants in internal/outbox — the parse likely
   broke, not a real empty set`. It **fails closed**, which is exactly the
   `#0275` fail-open shape it needed to avoid. `foundMailKindsDecl` and the
   `len(claimedByMailKinds) == 0` check cover the other half symmetrically.
3. Its oracle is `internal/outbox`'s own constant list — a *different
   package's* source, not a copy of the answer stored beside the question. It
   satisfies §8's "an edit to the subject must not also satisfy the oracle":
   editing `mailKinds` cannot edit `internal/outbox`.

**On the exception absorbing a future kind:** it cannot do so silently. The
exception is a single `const intakeException = "KindSubscribeIntake"`, not a
growable list, so widening it is an edit visible in a diff. Renaming the
constant makes the guard *fail*, not pass. The failure message does invite
"add it to this test's exceptions if it is deliberately not mail" — a human
judgment, but an explicit one.

**One narrow gap, measured:** the guard matches `vs.Type.(*ast.Ident)`, so it
only sees constants carrying the explicit `Kind` annotation. A constant
declared `KindReviewProbe = "review_probe"` (untyped, same const block) is
invisible to it — and proven usable as a real Kind anyway:

```
Item.Kind="review_probe", typed var="review_probe" — compiles and is a real Kind
not in mailKinds: … the guard passed anyway
```

All ten existing constants spell `Kind`, so this needs a deliberately
inconsistent declaration style to reach. Reported as hardening, not a bounce.

### `sendOne`'s new Warn — sufficient here, but not the whole answer

The judgment asked for, stated plainly: **logging is sufficient for this
issue, and it does leave a known-bad row that a later pass will re-send.**

- Sufficient, because the *proven* cause of a zero-row `MarkSent` — a
  cross-kind sweep releasing a live claim — is now structurally impossible,
  and turning a silently-discarded bool into a `Warn` is precisely what would
  have surfaced this bug instead of letting it masquerade as a healthy pass.
- Not the whole answer, because the message has already been accepted by SES
  at that point and the row is left `'queued'`; the `Warn` narrates the
  duplicate rather than preventing it. A stronger response exists — record the
  send unconditionally (`WHERE id = $1 AND status <> 'sent'`) since the send
  demonstrably happened — but that is a change to the queue's state machine and
  belongs in its own issue, not bolted onto this one.
- Noted in passing: execution deliberately continues past the `Warn` to the
  `confirmation_sent`/`welcome_sent` event write, which is right — the message
  did leave.

### To file (reported, not filed — CLAUDE.md §9)

1. **Guard that no `ClaimDue`/`OrphanSweep` caller outside `internal/outbox`
   omits its kinds.** Both are variadic, so the unscoped call is what you get
   by forgetting, and that exact omission is what `#0254` bounced on. A grep-
   or AST-level test over call sites is cheap.
2. **The `mailKinds` AST guard misses an untyped `Kind` constant** (case (b)
   above, reproduced). Match constants by inferred type or by name prefix
   within the known const block, not solely by an explicit `*ast.Ident` type.
3. **A zero-row `MarkSent` leaves a row that will be re-sent.** Consider
   recording the completed send unconditionally rather than only warning.
4. **Pre-existing, surfaced while reviewing this — not caused by it:**
   `outboxOrphanStaleAfter` (70s) is derived from *one row's* bound, but
   `claimed_at` is stamped once for a whole batch of up to 20 rows sent
   serially behind a rate limiter. At the SES sandbox's 1 msg/sec the last
   row's claim is already ~20s old before its send starts. The margin holds
   today; it is nowhere analysed.
5. **Pre-existing:** `TestOutbox_OrphanSweep_DoesNotUnclaimLiveRow` asserts
   `swept == 1` from an *unscoped* sweep over the shared per-agent database
   while other packages run under `-p 2`. `#0254` makes `outbound_queue`
   busier, so this exact-count assertion is a slightly more likely
   cross-package flake than it was.
