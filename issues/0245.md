## Description

> 🟢 **Resolved 2026-08-24** (`af43941`) — re-verified the fail-closed
> path with my own fake `rsync` *and* fake `ssh`, and re-ran the ShortLinks
> sweep independently from that project's own checkout. The script exits 2
> before `mkdir`, before `rsync`, before anything; the old one demonstrably
> reached `go.sstools.co`. No inherited default survives anywhere in
> `scripts/`, `deploy/`, or `migrations/`.

`#0236` fixed `backup.sh`'s silent fall-through to the literal `shortlinks`
database. The sweep it prompted found the **same defect on the offsite leg**,
which is the more consequential half:

```
scripts/db/pull-backups.sh:28
SSH_HOST="${BACKUP_SSH_HOST:-ec2-user@go.sstools.co}"
```

`go.sstools.co` is a real ShortLinks hostname, inherited when the script was
ported by `#0001`. Run without `BACKUP_SSH_HOST` set, the offsite pull reaches
out to **another project's server**.

**Why this is worse than `#0236`'s instance.** `backup.sh` failing over to the
wrong local database produced a loud `pg_dump` error or a useless local file.
This one opens an SSH connection to a host outside this project — so the
failure is a connection attempt against infrastructure we do not intend to
touch, and if that host happens to accept it, backups land somewhere nobody is
looking for them. Either way the operator's first signal is an SSH error whose
hostname they do not recognise.

**A third instance, and NOT cosmetic — corrected 2026-08-24.** `scripts/db/backup.sh` and
`scripts/db/restore.sh`'s usage examples still use `shortlinks` as the worked
example throughout — `backup.sh:14,20-22` and `restore.sh:7-8,11`. Harmless to
run, but it means someone reading the restore procedure under pressure is
copying commands naming the wrong database.

This is now the **third** defect traced to a surviving ShortLinks default
(`migrations/000007` in `CLAUDE.md` §1, `#0236`, and this). The pattern is
established enough to be worth closing out rather than fixing one at a time.

## Implementation notes

1. **`scripts/db/pull-backups.sh`** — removed the `${BACKUP_SSH_HOST:-ec2-user@go.sstools.co}`
   default. The check is now the first executable statement after `set
   -euo pipefail` — before `REMOTE_DIR`/`LOCAL_DIR` are resolved, before
   `mkdir -p "$LOCAL_DIR"`, before `rsync` is ever invoked. Unset or empty
   `BACKUP_SSH_HOST` prints an error naming the missing variable, the exact
   prior default it will no longer guess, and the fix, then `exit 2` —
   mirroring `#0236`'s pattern in `backup.sh` (same shape: named checks,
   named prior bad default, exit 2, no partial side effects before the
   error). The header's usage example and the `## Configuration` table
   comment were updated to show the variable as required.

2. **`docs/deployment.md`** — added a paragraph to the "Schedule and failure
   alert" section, parallel to the existing `BACKUP_DATABASES` callout,
   documenting `BACKUP_SSH_HOST` as a required install step for the offsite
   leg specifically (not covered by the systemd units, since
   `pull-backups.sh` runs on a separate machine).

3. **`deploy/systemd/README.md`** — added a matching paragraph to the
   "Backup timer and failure alert" section. `pull-backups.sh` isn't wired
   into any of the systemd units documented there (it runs on the Mac mini,
   not the EC2 host), so it needed its own explicit reminder rather than
   riding along with the `BACKUP_DATABASES` note.

4. **`scripts/db/backup.sh`** and **`scripts/db/restore.sh`** — replaced the
   `shortlinks` worked examples with `opencircuit` (this project's actual
   database name). `backup.sh`'s multi-database example already used a
   second, generic placeholder name (`otherdb`) for the "back up more than
   one database" case — left that as-is and only swapped the first,
   `shortlinks`-named entry to `opencircuit`, so the example now reads
   `backup.sh opencircuit otherdb` and the ASCII tree shows an `opencircuit/`
   folder instead of `shortlinks/`. `restore.sh`'s two examples (a restore
   drill and a live restore) were updated the same way.

5. **Deliberately left alone**, per the issue's own note and confirmed by
   the sweep below: `deploy/systemd/README.md:63` (now shifted a few lines
   by this diff) and `opencircuit-backup.service:26`'s `/opt/shortlinks`
   path-convention comments, `deploy/systemd/opencircuit-backup.timer`'s
   comment about ShortLinks' cron schedule, and the `migrations/000007` /

**Static checks — real tools, not reasoning:**

```

(all pass, no output)

(all pass, no output)
```

**Fail-closed path — proved with a stubbed `rsync` on `PATH`, never a real
network call**, per the task's constraint against ever making a real SSH
connection:

Old script (`git show HEAD:scripts/db/pull-backups.sh`, copied to a scratch
path per `CLAUDE.md` §8a rather than `git stash`), `BACKUP_SSH_HOST` unset,
`PATH` prepended with a fake `rsync` that logs its arguments and exits 0
instead of connecting:

```
$ unset BACKUP_SSH_HOST
$ BACKUP_LOCAL_DIR=<scratch> PATH=<fakebin>:$PATH bash /tmp/old-0245-pull.sh
Pulling ec2-user@go.sstools.co:/var/backups/postgres/ → <scratch>/
FAKE-RSYNC-CALLED: -avz --delete-after --partial --partial-dir=.rsync-partial -e ssh ec2-user@go.sstools.co:/var/backups/postgres/ <scratch>/
NETWORK CALL WOULD HAVE HAPPENED HERE
Done. Local mirror: <scratch>/
OLD exit: 0
```

This is exactly the bug: the old script silently resolved the foreign
hostname and would have opened a real SSH connection to it — the fake
`rsync` is the only thing standing between this run and reaching
`go.sstools.co`.

New script, same scenario:

```
$ unset BACKUP_SSH_HOST
$ BACKUP_LOCAL_DIR=<scratch2> PATH=<fakebin>:$PATH bash scripts/db/pull-backups.sh
ERROR: BACKUP_SSH_HOST is not set, and this script no longer defaults to a
host to pull backups from.
... (full message naming the prior default and the fix) ...
NEW exit: 2
$ ls <scratch2>
ls: <scratch2>: No such file or directory
```

The new script exits before `mkdir -p "$LOCAL_DIR"` even runs — confirmed
the local mirror directory was never created, let alone `rsync`/`ssh`
invoked. No network call was attempted at any point in this verification;
the fake `rsync` was never reached by the new script and only used to prove
the old one *would* reach it.

**Positive path unaffected** — with `BACKUP_SSH_HOST` set to a
`.invalid`-suffixed placeholder host (RFC 2606; guaranteed non-resolvable,
belt-and-suspenders on top of the fake `rsync` already intercepting the
call), the script proceeds normally and calls the stubbed `rsync` with the
expected arguments, exit 0.

### Fail-closed, proved with my own stubs (no network call, ever)

I built a fake `rsync` **and** a fake `ssh` on `PATH`, each printing a loud
marker and exiting 0, so that any attempt to reach the network would announce
itself instead of failing silently.

**New script, `BACKUP_SSH_HOST` unset** (`env -u BACKUP_SSH_HOST`):

```
ERROR: BACKUP_SSH_HOST is not set, and this script no longer defaults to a
host to pull backups from.
… (names the prior default "ec2-user@go.sstools.co", names the fix) …
NEW exit=2
```

Neither stub printed. Crucially, the local mirror directory **was not
created** — `ls` on the parent showed it empty, so the script exits before
`mkdir -p "$LOCAL_DIR"`, which is the first side effect of any kind. Reading
confirms why: the guard is the first executable statement after
`set -euo pipefail`, ahead of `REMOTE_DIR`/`LOCAL_DIR` resolution. **Empty
string also fails closed** — `BACKUP_SSH_HOST=""` → `exit 2` (the check is
`-z "${BACKUP_SSH_HOST:-}"`, so unset and empty behave alike).

**The old script, same scenario** (`git show af43941^:scripts/db/pull-backups.sh`
copied to a scratch path — not `git stash`, per `CLAUDE.md` §8a):

```
Pulling ec2-user@go.sstools.co:/var/backups/postgres/ → …
FAKE-RSYNC-REACHED: … -e ssh ec2-user@go.sstools.co:/var/backups/postgres/ …
NETWORK CALL WOULD HAVE HAPPENED HERE
OLD exit: 0
```

The bug was real and my stub is the only thing that stood between that run and
a stranger's server. **Positive path unaffected**: with `BACKUP_SSH_HOST` set
