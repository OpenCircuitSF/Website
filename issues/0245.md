# 0245 — The offsite backup pull defaults to a ShortLinks host, and the doc examples still use its database

## Description

`#0236` fixed `backup.sh`'s silent fall-through to the literal `shortlinks`
database. The sweep it prompted found the **same defect on the offsite leg**,
which is the more consequential half:

```
scripts/db/pull-backups.sh:28
SSH_HOST="${BACKUP_SSH_HOST:-ec2-user@go.sstools.co}"
```

`go.sstools.co` is a real ShortLinks hostname, inherited when the script was
ported by `#0001`. Run without `BACKUP_SSH_HOST` set, the offsite pull reaches
out to **another project's server**.

**Why this is worse than `#0236`'s instance.** `backup.sh` failing over to the
wrong local database produced a loud `pg_dump` error or a useless local file.
This one opens an SSH connection to a host outside this project — so the
failure is a connection attempt against infrastructure we do not intend to
touch, and if that host happens to accept it, backups land somewhere nobody is
looking for them. Either way the operator's first signal is an SSH error whose
hostname they do not recognise.

**A third instance, cosmetic but the same root.** `scripts/db/backup.sh` and
`scripts/db/restore.sh`'s usage examples still use `shortlinks` as the worked
example throughout — `backup.sh:14,20-22` and `restore.sh:7-8,11`. Harmless to
run, but it means someone reading the restore procedure under pressure is
copying commands naming the wrong database.

This is now the **third** defect traced to a surviving ShortLinks default
(`migrations/000007` in `CLAUDE.md` §1, `#0236`, and this). The pattern is
established enough to be worth closing out rather than fixing one at a time.

## Acceptance criteria

- [ ] `pull-backups.sh` has no default `BACKUP_SSH_HOST` — it fails closed, naming what is missing, exactly as `#0236` made `backup.sh` do
- [ ] Proved: with the variable unset the script exits non-zero and attempts no connection, verified before any network call is made
- [ ] `docs/deployment.md` and `deploy/systemd/README.md` list `BACKUP_SSH_HOST` as a required install step alongside `BACKUP_DATABASES`
- [ ] The `shortlinks` worked examples in `backup.sh` and `restore.sh` use this project's database
- [ ] **A complete sweep of `scripts/`, `deploy/` and `migrations/` for other inherited ShortLinks identifiers** — hostnames, database names, paths, service names, ports — with the findings listed in the issue whether or not each is fixed here
- [ ] `shellcheck` and `bash -n` clean on every script touched

## Notes

Found by the `#0236` sweep and reported under `CLAUDE.md` §9.

The fifth criterion is the point. Three instances have surfaced one at a time,
each found only because someone happened to look while fixing something else.
An explicit sweep costs an hour and ends the class; the alternative is finding
the fourth one on the deployment day.

Note `deploy/systemd/README.md:63` and `opencircuit-backup.service:26`
deliberately mirror ShortLinks' `/opt/shortlinks` path convention and say so —
that is a documented choice, not an inherited default, and should be left alone
unless the sweep concludes otherwise.

Nothing here is reachable until the box exists (`CLAUDE.md` §10, deployment
deferred), but like `#0236` it must be fixed **before** the first install,
because the failure mode is silent misdirection rather than an error.
