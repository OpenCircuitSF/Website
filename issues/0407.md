## Description

`CLAUDE.md` §1 states the migration rule twice, and the two statements do not
carry the same meaning:

- The **principle**: *"Never edit a migration that has been applied to a database
  anyone cares about; add a new one."*
- The **range**: *"never edit an existing migration. `000001`–`000022` are
  frozen."*

The range was written when production stood at 22 and it still says 22. The
principle is the load-bearing rule; the range is a snapshot of it from
2026-08-25.

**Read as a range, it is wrong in both directions.** It under-states for anything
production later applies, and it over-states by implying every numbered file on
disk is untouchable — which is how it is in fact being read. Nothing anywhere
states the distinction that actually matters: **applied to production**, not
**present in `migrations/`**.

## What the misreading already cost

`#0404` was a deploy blocker: `000025` could not run against production because
its `ADD COLUMN slug ... NOT NULL` premise had expired. **The orchestrator
asserted the frozen range was `000001`–`000027`** — repeating it in the issue
text and in two dispatches — which made the only correct fix look forbidden and
sent the issue toward an impossible design, since a new migration cannot run
before the one that fails.

`#0404`'s planning pass caught it by reading §1 rather than accepting the
premise, and recorded the correction. The fix landed as an in-place edit to
`000025`, which the literal rule permits: production has never applied it.

This is the same shape §1 already documents for `#0125` — an instruction that was
true when written, followed faithfully after it stopped being true.

## The tension to resolve, which is why this is not a one-line fix

A bare principle is harder to apply than a range. An implementer wants to know
*"may I edit this file?"* and a range answers instantly, where the principle
requires knowing production's applied version — which is not in the repo and
needs a query against the box.

So the fix is not simply deleting the range. Options worth weighing:

- **State the principle first and the range as a derived snapshot**, dated, with
  the command that establishes production's real version so a reader can refresh
  it themselves.
- **Drop the range** and give the lookup instead.
- **Keep both and reconcile the wording**, making explicit that the range means
  "applied to production as of this date" rather than "on disk".

`docs/database.md` and several issue files paraphrase the rule too; they should
not be left disagreeing with whatever §1 ends up saying.

## Acceptance criteria

1. `CLAUDE.md` §1 makes the **applied-to-production** distinction explicit, so a
   reader can tell whether a given file is editable without inferring it.
2. Whatever replaces or supplements the range is either **self-dating** or
   **derivable**, so it cannot silently rot the way `000001`–`000022` did. If it
   carries a number, it says as-of-when and how to re-derive it.
3. **Re-derive production's current applied version before writing any number**,
   read-only. Do not copy `22` from this issue or from §1 — that is the exact
   failure being fixed.
4. `docs/database.md` and any other paraphrase agree with the new §1 wording.
   Find them rather than assuming this issue's list is complete.
5. **Do not build a mechanism.** A guard that checks the range against production
   would need production access from a test. Per `#0330`/`#0347`/`#0356`/`#0381`,
   recording is the expected outcome — but say so explicitly rather than by
   omission.
6. Editing `CLAUDE.md` means running **both** `./internal/db/...` and
   `./internal/handlers/...` (§5's own repo-wide-guard table): renumbering or
   deleting a `##` section fails the citation guard while `internal/db` passes
   clean. Note `internal/db` also parses §1's migration-range sentence — check
   whether `docs_parity_test.go` pins the wording before changing it, or the
   change will fail its own guard.
7. Per §5 name the specific tests that ran. No Go-file-plus-line-number citation
   (`#0352`), scanned with `python3` bytes rather than BSD `grep -P`.

### What must be fixed

**1. The blocking one — a new unchecked count, in the paragraph that exists to
stop unchecked counts.** The new text ends its "wrong in both directions"
sentence with:

> over-states by implying every numbered file in `migrations/` is untouchable
> — most of them have never reached production at all.

`migrations/` holds 27 up-migrations and production has applied 22 of them, so
**22 of 27 have** reached production. "Most of them have never reached
production" is false by a wide margin, whichever plural it is read against: as
"most migration files" it inverts the real ratio, and as "most of the files the
over-statement wrongly covers" it should be *all*, not *most*. Either way it is
a quantity asserted without measuring it — the precise thing `#0404` cost a
planning pass to catch.

Fix it without introducing another number that can rot. Replace the two lines

      over-states by implying every numbered file in `migrations/` is untouchable
      — most of them have never reached production at all.

with

      over-states by implying every numbered file in `migrations/` is untouchable
      — every file above the frozen bound has never reached production at all,
      and `#0404` needed to edit one of them.

That is true by construction, so it cannot go stale on the next deploy the way a
count would, and it points at the concrete case.

**2. The recorded command output is not what the command prints.** The file says

> As of **2026-09-03** that returns `22 | f`

`psql -tAc` is tuples-only and **unaligned**, so it emits `22|f` with no spaces.
Measured, by running the documented command itself. A reader who copies the
command and gets `22|f` should not have to wonder whether they ran it wrong, and
"here is the exact command, here is exactly what it returns" is the whole
contract this paragraph is offering. Replace `` `22 | f` `` with `` `22|f` ``.

**3. A stale status claim in a sentence this pass rewrote.** The paragraph above
the new text reads:

> production's PostgreSQL holds a live `opencircuit` database with real rows in
> it — `#0272` is open about two specific `outbound_queue` rows there.

`81e6b58` edited that sentence (it removed the `schema_migrations.version = 22`
clause from it) and carried "`#0272` is open" through unchanged. `#0272` has
been **resolved since 2026-08-27** — `MarkSent` was fixed and the commit is
`8bd4a1b`; what remains is the two production rows, deliberately deferred with
the corrective SQL recorded in that issue. A sentence that was edited in a pass
whose entire subject is stale assertions in this file should not leave a false
one standing in it. Replace

      it — `#0272` is open about two specific `outbound_queue` rows there.

with

      it — `#0272` (resolved 2026-08-27) names two specific `outbound_queue`
      rows there.

That drops the false status without asserting anything new about the current
state of those rows, which this pass did not measure.
