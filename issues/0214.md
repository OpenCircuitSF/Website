## Description

> 🟢 **Resolved 2026-08-24** (`418f95a`) — re-verified the `strictPort` decision
> by experiment rather than by argument: a second Vite now hard-fails with
> `Error: Port 5173 is already in use` instead of sliding to 5174, and
> `scripts/dev.sh` with `:5173` held refuses in its preflight and never reaches
> Vite at all — so the behaviour change really is confined to the bare
> `npm run dev` path, as claimed.

`#0213` made `BASE_URL` and `WEBAUTHN_RP_ORIGIN` derive from `$PORT` instead of
a hardcoded `8080`. Its phase-3 review found the documentation did not follow.

**`docs/dev.md:51,53` still list both defaults as the literal
`http://localhost:8080`.** They are now `http://localhost:${PORT}`. The table's
own example, six lines further down, is `PORT=9090 ./scripts/dev.sh` — which is
precisely the case where the stale literal misleads: a reader sets `PORT=9090`,
reads that `BASE_URL` defaults to `:8080`, and concludes the override is the
half-broken thing `#0213` just fixed.

**A second, cosmetic finding from the same review.** `web/vite.config.ts` sets
no `server.port` or `strictPort`, so `5173` is *inherited* from Vite's default
rather than declared. A bare `npm run dev` with `5173` occupied slides silently
to `5174` while `README.md`, `docs/dev.md`, `CLAUDE.md`, and `dev.sh`'s messages
all still say `5173`. Unreachable through `dev.sh` — `#0117`'s preflight refuses
before Vite starts — so this is about the bare-`npm` path only.

- `docs/dev.md`'s environment table: `BASE_URL` and `WEBAUTHN_RP_ORIGIN` rows
  now read `http://localhost:${PORT}` instead of the stale literal
  `http://localhost:8080`, each with a one-line note that they derive from

  default off of it"). Added a sentence directly under the `PORT=9090`

  that example sitting six lines below the stale literal was exactly what
  made the old text misleading.
- Checked `README.md` and `CLAUDE.md` for the same stale defaults
  (`grep -n '8080\|localhost' README.md docs/*.md CLAUDE.md`, filtered to
  `BASE_URL`/`WEBAUTHN_RP_ORIGIN`/literal `:8080`  mentions). `README.md` does
  not mention either variable. The `:8080` mentions in `docs/architecture.md`
  and `docs/deployment.md` describe the **production** reverse-proxy target

  not a claim about what `BASE_URL`/`WEBAUTHN_RP_ORIGIN` resolve to under an
  override — left unchanged.
- `web/vite.config.ts`'s `server` block previously set no `port` or
  `strictPort`, so `5173` was inherited from Vite's own default rather than
  stated. Added `port: 5173` (states what every doc already claims) and
  `strictPort: true` (fail loudly on a collision rather than silently
  sliding to `5174`, matching this project's general preference for refusing
  over silently substituting something else — see `scripts/dev.sh`'s own
  `free_port`). Recorded in a comment on why this is unreachable through
  `scripts/dev.sh` itself: `#0117`'s preflight (`free_port 5173`) already
  refuses before Vite starts, so this only changes behavior on the bare
  `npm run dev` path.

### The `strictPort` behaviour change, measured (criteria 3, 4)

The config is genuinely read — `loadConfigFromFile({command:'serve'})` reports
`server.port = 5173`, `server.strictPort = true` (Vite 6.4.2), so this is a
stated value now, not an inherited one.

**A first attempt of mine was a false negative, and it is worth recording.** I
held `127.0.0.1:5173` with a Python IPv4 listener and started `npm run dev`;
Vite started **successfully** and reported `Local: http://localhost:5173/`.
`strictPort` had not failed — Vite binds `[::1]:5173` by default, so an
IPv4-only holder does not collide with it at all. Anyone testing a port guard
on this machine should bind both families or race two real servers, or they
will conclude a working guard is broken.

Racing two real Vite instances is the test that actually proves it:

```
v1: Local:   http://localhost:5173/
v2: error when starting dev server:
    Error: Port 5173 is already in use
```

The second process **exited**; `:5174` was never bound. That is the intended
change — loud collision instead of a silent slide to a port every doc denies.

**The ordering claim holds, and I did not take it on trust.** With `:5173` held,
`./scripts/dev.sh` printed its preflight (`repo`, `storage`, `admin`, `port:
8080`) and then:

```
  ERROR: port 5173 is already in use — dev.sh will not kill a process it did not start.
    pid 63074: … python … s.bind(('127.0.0.1',5173))
```

and exited — before `npm run dev` is ever reached. Statically the same:
`free_port "$PORT"` / `free_port 5173` are at `scripts/dev.sh:228-229`, `cd web
&& npm run dev` at line 366, with nothing between them that starts Vite. So
`strictPort` is unreachable through `dev.sh`, exactly as the implementation
note says.

One consequence worth stating plainly, since it is a real behaviour change:
two agents each running a **bare** `npm run dev` now collide loudly instead of
one silently taking `:5174`. That is the wanted direction — it matches
`dev.sh`'s own `free_port` policy of refusing rather than substituting, and
`README.md`, `docs/dev.md`, `CLAUDE.md` and seven places in `dev.sh` all assert
`5173` — but it is louder than before and should not surprise anyone.

`server.*` affects only the dev server, never `vite build`, so `web/dist/` is
untouched by this change; I deliberately did **not** run a build, since
`web/dist/index.html` is a tracked shared resource (`#0141`).
