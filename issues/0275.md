## Description

Five guards in `internal/handlers` walk the tree and fail when they find a bad
shape. All five share `citedTestScanRoots` and `walkGoFiles`:

- `misattached_doc_comment_guard_test.go` (`#0267`)
- `dangling_test_citation_guard_test.go`
- `citation_guard_test.go`
- `citation_target_guard_test.go`
- `audit_email_metadata_guard_test.go`

**None of them asserts it visited anything.** A guard's pass condition is "the
findings slice is empty", and an empty slice is exactly what a walk over zero
files produces. So emptying or mistyping `citedTestScanRoots` — one shared
variable, five guards — silently disarms all five at once, and the suite stays
green.

`#0267`'s review measured the adjacent case and found it fails *closed*:
pointing the walk at `../../no-such-dir` produces `t.Fatalf("walk …: lstat …:
no such file or directory")`. That is the *broken-path* case. The
**empty-roots** case has no such protection — an empty list is not an error to
`filepath.WalkDir`, it is simply nothing to do.

This is the fail-open shape CLAUDE.md §8 already names twice, in different
clothes: *"assert the extraction produced something before hashing it — an
empty result must be an error, never an input."* Here the extraction is a file
walk and the input is a findings slice, but the failure is identical.

## Why this is worth closing now

The guard family is growing — `#0267` made it five, and reviewers keep reaching
for the pattern because it works. Every new member inherits the same blind
spot, and the blind spot is in the *shared* helper, so one fix covers all
present and future members.

It also interacts badly with `#0258`'s lesson: a guard living in the file it
guards becomes new mutable surface. These guards do not guard their own scan
roots, so the cheapest way to defeat any of them is not to edit the guard at
all — it is to edit the one variable they all read.

## Acceptance criteria

1. `walkGoFiles` (or a wrapper every guard uses) counts the `.go` files it
   visited and returns that count alongside the findings.
2. Each of the five guards fails when the visited count is zero, with a message
   naming the guard and the roots it tried — not a bare assertion failure.
3. The floor is a plausible number, not literally one. A tree-wide walk over
   `internal/` and `cmd/` visits hundreds of files; a threshold of `0 < n` would
   still pass if the roots were narrowed to a single directory. Pick a floor
   that a real narrowing would trip, and justify the number in a comment.
4. `citedTestScanRoots` itself is asserted non-empty, once, in a place all five
   guards reach.
4a. **The count must measure files the scan actually parses, not files the walk
   yields.** `#0261` added a floor to the audit-metadata guard and `#0261`'s
   review measured the gap: `countVisitedGoFiles` counts all 247 walked files
   while `scanAuditEntrySites` parses only the **108** non-test ones, so the
   floor is sized against a population 2.3x larger than the coverage it is
   meant to protect. Not exploitable today, but a floor that measures the wrong
   population is exactly the reassurance-without-protection this issue is about.
   Whatever mechanism lands here must count the parsed set.
5. A test proves the new check fires: set the roots to an empty slice in a
   fixture or via the helper's parameter and assert the guard fails. Per
   CLAUDE.md §8, the oracle must not be the same bytes as the subject — do not
   store a copy of the expected count next to the count.
6. All five guards still pass unchanged against the real tree, and
   `scripts/check.sh go ./internal/...` reports no skips.

### The floor, computed independently

The crux of this review was criterion 3 against a **lowered** floor. Every
population below was recomputed from scratch — first with `find`, then again at
runtime through the guards' own helpers in a worktree pinned to `a048233`. Both
methods agree, and both agree with the implementer's figures:

| Guard family | Roots | Population it parses | Floor | Largest single package under those roots |
|---|---|---|---|---|
| `citedTestScanRoots` × 3 guards | `..`, `../../cmd`, `../../web` | **255** (all `.go`) | 150 | `internal/handlers` = **96** |
| `TestNoAdminFacingStringCitesInternalDocs` | same three | **111** (non-test only) | 80 | `internal/handlers` = **40** |
| `TestAuditEntryEmailMetadataMatchesKnownSites` | `..`, `../../cmd` | **110** (non-test only) | 80 | `internal/handlers` = **40** |

**The lowering was forced.** Setting `auditEmailMetadataMinPlausibleFileCount`
back to 150 in a worktree and running the guard against the real tree fails:
`examined only 110 .go file(s) — expected at least 150`. Once criterion 4a is
honoured and the count measures the parsed set, a floor of 150 is not a stricter
guard — it is a guard that cannot pass at all. So this is the opposite of
"weaken it until it goes green": the floor moved because the *measurement* was
corrected underneath it.

**80 catches a real narrowing, not merely an empty scan.** The concern raised at
dispatch — that a narrowing to one package leaves ~96 files, above 80 — conflates
the two populations. 96 is the *all-`.go`* count for `internal/handlers`, and it
belongs to the guards floored at **150**, where 96 < 150 trips. The two guards
floored at 80 parse **non-test files only**, and `internal/handlers` has **40**
of those. Measured directly, with every scan-roots variable narrowed to `{"."}`:

```
TestAuditEntryEmailMetadataMatchesKnownSites:        examined only 40  — expected at least 80   FAIL
TestNoAdminFacingStringCitesInternalDocs:            examined only 40  — expected at least 80   FAIL
TestNoCommentCitesUnresolvedPathOrSection:           examined only 96  — expected at least 150  FAIL
TestNoCommentCitesUndefinedTestFunction:             examined only 96  — expected at least 150  FAIL
TestNoDocCommentNamesADifferentDeclarationInSameFile: examined only 96 — expected at least 150  FAIL
```

All five floors trip a narrowing to the single largest package under their own
roots. None is a floor that only catches zero.

The one narrowing no floor here catches is dropping `cmd/` and `web/` while
keeping `internal/` (110 → 107, and 255 → 236). That is a 3-file difference; no
floor could catch it without sitting so close to the population that ordinary
tree churn would false-alarm. Accepted, and it is the same trade `#0261` made.

### Criteria 4, 4a, and 5

- **Criterion 4** — the non-empty assertion lives once, in
  `goFileVisitCountImplausible`'s `len(roots) == 0` branch, reached by all five
  guards through `assertGoFileVisitCountPlausible`. Confirmed by the mutation
  above firing from five distinct call sites.
- **Criterion 4a** — checked per guard rather than taken on trust. The three
  `citedTestScanRoots` guards apply no post-walk filter:
  `collectDefinedTestFuncs`, `collectTestCitations`, `collectCitationTargetHits`
  and the misattached-doc walk each parse *every* path `walkGoFiles` yields, so
  the walk count already is the parsed count. `scanDirForCitations` filters
  `_test.go` *before* parsing and returns `collected`, so its count is likewise
  the parsed set. Only the audit guard filtered after the walk, and it now
  returns `len(files)` from the same walk that populates `files` — no second,
  driftable walk anywhere in the family. `countVisitedGoFiles`, which was the
  mismeasuring walk, is gone.
- **Criterion 5** — `TestGoFileVisitCountGuardFiresOnEmptyOrLowCount` calls the
  pure `goFileVisitCountImplausible` with its own literals (`0`, `3`, `150`) and
  its own roots lists; it references no guard's floor constant. Editing any
  floor cannot make it agree with itself, which is CLAUDE.md §8's actual
  selection rule. It is also two-sided — it asserts a clearing count is reported
  *plausible* — so a function that always returned a reason would fail it.

### Two smaller observations, neither blocking

1. **The floor constants themselves have no external oracle.** Setting
   `citedTestScanRootsMinPlausibleFileCount = 0` leaves every test in this
   package green. That is the structural limit CLAUDE.md §8 describes — a guard
   living in the file it guards is new mutable surface — and closing it needs an
   external harness of the `scripts/*_guard_test.sh` shape, not a seventh
   in-file check. Out of scope here; worth filing.
2. `#0261`'s historical paragraph about the pointer form now floats detached
   between `isBuiltinClearCall` and `auditEntryLiteralBehindIdent`, two
   declarations above the `compositeLitAssignedIdents` it describes. It is a
   free comment, not a misattached doc comment — `#0267`'s guard passes — and
   `gofmt -l` is clean. Cosmetic only.
