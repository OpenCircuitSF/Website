## Description

`#0269` item 2 fixed a real cross-test contamination: `breakerTestMailer`
returned message ids that collided across campaigns, so a campaign seeded with
**zero** bounces read back `Bounced=5` from an unrelated campaign's events. The
fix stamps a `testdb.Unique()` prefix into every id.

`internal/mailing/recording_mailer.go` has **the same shape**. It restarts
`nextID` at 1 per instance, producing `"recorded-1"`, `"recorded-2"`, … into
`email_sends.ses_message_id`. Note this one is production code, not a test
helper.

The mechanism that made `#0269` item 2 bite is in the schema: `email_events` is
`UNIQUE (sns_message_id, recipient)` while `idx_email_events_message_id` is
**non-unique**, so a lookup by message id happily returns another run's rows.

**Nothing writes `email_events` with those ids today**, which is why this is
latent rather than live. It is one fixture away from mattering, and the failure
it would produce is the `#0266` class — a test passing, or failing, for a reason
that has nothing to do with what it is testing.

`internal/mailing/worker_store_test.go:209`'s literal `"ses-message-1"` belongs
with this.

## Acceptance criteria

1. `RecordingMailer`'s ids are unique per instance, not per-instance sequential.
   Follow `#0269` item 2's precedent — `testdb.Unique()` where it is available.
2. It is production code, so the fix must not make it depend on `internal/testdb`.
   Use a mechanism appropriate to a non-test package and say why it was chosen.
3. `worker_store_test.go:209`'s hardcoded `"ses-message-1"` is replaced with a
   generated id. Per CLAUDE.md §8b, never target a literal or seeded id in a
   test — seed a throwaway row and target that.
4. Audit the rest of `internal/mailing` for the same shape — an id that is
   unique only within one instance or one test — and fix any found. Report the
   list even if empty.
5. A test demonstrates the ids do not collide across two instances. Proving the
   *absence* of the `#0269` symptom is not enough on its own, since nothing
   currently writes the colliding events; assert the ids directly.
6. `ISSUE=NNNN scripts/check.sh go ./internal/...` passes with no skips.

### The mechanism (criteria 1 and 2)

`nextRecordingMailerID()` is `fmt.Sprintf("recorded-%d-%d", os.Getpid(),
atomic.AddInt64(&recordingMailerIDCounter, 1))`. Compared against
`internal/testdb/testdb.go:435`, which is
`int64(os.Getpid())<<32 | (n & 0xffffffff)` — the same two ingredients, and
the string form is marginally the stronger of the two, since it does not
truncate the counter to 32 bits the way the packed integer does.

**Both claimed guarantees hold.**

- *Unique across every instance in one process*: the counter is package-level
  and incremented atomically, so no two `Send` calls anywhere in the process
  can observe the same `n`, regardless of how many `RecordingMailer` values
  exist. This is the actual defect closed — the old `r.nextID` lived on the
  struct and restarted at 1 for each one.
- *Unique across concurrently running processes*: distinct live processes
  have distinct pids by construction, so `recorded-<pidA>-*` and
  `recorded-<pidB>-*` cannot intersect. This matters here because CLAUDE.md
  §5a's fallback case is real — an agent that cannot get its own database
  shares `opencircuit_test`, and `go test` runs one process per package.

**PID reuse, decided rather than waved past.** A pid is reused by the OS
after the original process exits, so the guarantee is over *concurrently
live* processes, not over all time. That is not a gap here, for three
reasons, and the same reasoning already licenses `testdb.Unique()`, which
this deliberately mirrors: the ids are never persisted beyond a test run
(`TestMain` truncates the tables through `testdb.EntryTruncate`); a reused
pid also needs the *same counter value*, i.e. the Nth send of the run, to
actually collide; and the value has no meaning outside a test database.
Recording it here so the next reader does not have to re-derive it — the
mechanism is "unique among simultaneously running processes", and that is
sufficient for what these ids are for.

**`os.Getpid()` in production code is fine here, and the reason is not the
package name.** Checked rather than assumed: the only non-test references to
`RecordingMailer` anywhere in the tree are its own definition, a mention in
`internal/mailing/mailer.go`'s doc, and a comment in
`cmd/opencircuit/main.go:549` that exists specifically to say "RecordingMailer
exists for tests, not for a 'log to stdout in dev' mode". Nothing constructs
one outside `_test.go` files. So it is a **test double that happens to live
in a production file** — it links into the binary but is never executed by
the service. `os.Getpid()` is in any case a cheap, side-effect-free call, so
even the hypothetical production path would be unobjectionable; the point of
establishing this is that the choice carries no runtime cost or behavioural
risk to weigh against it.
