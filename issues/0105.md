## Description

`config.Config.EmailListDomain` is read as a bare `os.Getenv("EMAIL_LIST_DOMAIN")`
with no default and no required-field check. `mailing.CampaignHeaders` (#0035)
interpolates it directly into the `mailto:` half of `List-Unsubscribe`, so if the
variable is ever unset in production the header goes out as
`<mailto:unsubscribe@?subject=unsubscribe%3A…>` — a syntactically invalid URI in
the one header Gmail's and Yahoo's bulk-sender rules actually parse.

> 🟢 Resolved 2026-08-21 — Reviewer independently re-verified on an idle machine
> (load average 2.08, well under `CLAUDE.md` §5's ~8 threshold). Both halves of
> the fix are correct and neither breaks an existing boot path: the full
> `go test ./... -p 2 -count=1` suite is green — **795 passes counting
> subtests, 0 failures, 0 skips** — with `TEST_DATABASE_URL` exported and all
> five DB-backed packages reporting `ok` with non-zero timings. Both mutations
> re-run and confirmed. Ruling on required-vs-defaulted: **required is right.**

## Review notes

Independently verified, 2026-08-21 (phase 3, Opus). Approved. What was checked
beyond re-running the implementer's own commands:

**1. The claimed convention is real — checked against the loader, not the
summary.** `config.go`'s `required` table holds exactly `BASE_URL`,
`DATABASE_URL`, `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_ORIGIN`, `SESSION_SECRET`,
`ADMIN_EMAIL`, `AWS_REGION`, `EMAIL_FROM` — every one a domain, identity, or
secret string. The `const` default block holds exactly `defaultPort`,
`defaultMaxSendRate`, `defaultSendBatchSize`, `defaultSendWorkerEnabled` — all
numeric or boolean operational dials. **There is not one defaulted string in
the file.** So "required, no default" is the existing pattern for a value of
this kind and defaulting `EMAIL_LIST_DOMAIN` to `lists.opencircuitsf.com`
would have invented a third one. `skipInDev: false` is likewise correct:
`DATABASE_URL` is the sole `skipInDev: true` entry and it earns that because
`STORAGE=json` genuinely removes the database, whereas there is no dev-mode
condition under which a list domain stops being needed.

The decision also holds on its merits independent of precedent. A hardcoded
default would let a deploy that never provisioned the subdomain boot cleanly
and advertise an unsubscribe address that black-holes mail — and that is not
hypothetical today, because `#0057` has not yet pointed `lists.opencircuitsf.com`'s
MX at SES (`CLAUDE.md` §10). The value is a deliberate per-deploy decision
constrained by `CLAUDE.md` §9 ("never point the apex MX at SES"); those are
exactly the values that must not be silently assumed.

**2. Nothing that used to boot now fails — verified empirically, not argued.**
Invoking the binary with precisely the environment `scripts/dev.sh` exports and
nothing else (`env -i`, `PORT=58771`) yields:

```

EMAIL_FROM; missing required variable EMAIL_LIST_DOMAIN
```

`AWS_REGION` and `EMAIL_FROM` were already required with `skipInDev: false`

`dev.sh` from a clean checkout was **already** failing to boot. This change
lengthens that error by one variable; it does not create a new failure mode.
The implementer's claim checks out exactly.

Every other config construction site was enumerated: `cmd/opencircuit` (×8),

rather than calling `Load`, so a new required field cannot reach them — which
the green full suite confirms. `cmd/opencircuit/seed.go` does call
`config.Load()` and now needs the variable, exactly as it already needed
`AWS_REGION` and `EMAIL_FROM`. `scripts/sim.sh` reads no configuration at all

**3. Documentation and deploy assets are consistent.** `.env.example` line 38
ships `EMAIL_LIST_DOMAIN=lists.opencircuitsf.com` uncommented — confirmed to be

**4. The RFC 8058 reading is correct.** Checked against the RFC text, §3.1:
*"The List-Unsubscribe header field MUST contain one HTTPS URI. It MAY contain
other non-HTTP/S URIs such as MAILTO:"*. HTTPS-only is compliant and the
`mailto:` form is explicitly optional. The header set also stays **coherent**,
which was the real risk given `#0035` established the three headers only work
as a set: `List-Unsubscribe-Post` and `List-Id` are emitted *unconditionally*,
outside the new guard, so the degraded output is `HTTPS URI` +
`List-Unsubscribe-Post: List-Unsubscribe=One-Click` — precisely the RFC 8058
one-click configuration, not the two-click fallback. The new test asserts all
three headers in the blank case, so that coherence is pinned rather than
incidental.

**5. Silently dropping vs. returning an error — dropping is right here, and
this is *not* the project's "silently degraded output" defect shape.** The
distinguishing test is whether the fallback output is *valid*, and it is: the
function emits a fully compliant one-click header set. The only loss is PRD
§6.5's Path 3, and losing Path 3 is strictly better than the malformed URI it
replaces, which broke Path 1 **and** Path 3 at once by rendering the whole
header unparseable. An error return would change a pure three-argument
function's signature and push an error onto `#0045`'s per-recipient loop for a
case two upstream guards already prevent — and it would be loud at the wrong
layer. `#0045`'s `list_domain_unset` gate is the correct place to be loud,
because it refuses to let the campaign leave `scheduled` at all: zero messages
go out, rather than `N` going out with a quietly shortened header.

That reasoning depends entirely on `#0045`'s gate continuing to exist, so
**`issues/0045.md` was amended** as part of this review. Its plan previously
said that if `#0105` made the variable required the gate would be "unreachable
and harmless" — true, but an implementer could reasonably delete an unreachable
check as dead code, which would leave the silent degrade as the *only*
defence. The amendment records that `#0105` shipped both branches and that the
gate must still be implemented, with the reasoning above.

## Steps to reproduce

Not yet reachable at runtime — `CampaignHeaders` has no caller until #0045's send
worker exists. Reproducible today at the unit level:

```go
mailing.CampaignHeaders("https://www.opencircuitsf.com", "", "SOME-TOKEN")
// List-Unsubscribe: <https://www.opencircuitsf.com/api/unsubscribe?token=SOME-TOKEN>, <mailto:unsubscribe@?subject=unsubscribe%3ASOME-TOKEN>
```

## Expected behavior

An unset or blank `EMAIL_LIST_DOMAIN` fails fast at boot, the same way `BASE_URL`,
`EMAIL_FROM`, and `AWS_REGION` already do — or `CampaignHeaders` omits the
`mailto:` form entirely and emits an HTTPS-only `List-Unsubscribe`, which is
still valid RFC 8058. Silently emitting a malformed URI is the one option that
should not be available.

## Actual behavior

`internal/config/config.go` line 126 reads the variable with no default, and its
`required` table (lines 138–152) does not list it. `docs/configuration.md` marks
it Required = no, Default = —. Nothing anywhere validates the value.

## Notes

Found during #0035's review (2026-08-20), not by #0035's code — `CampaignHeaders`
is a pure function that is correctly parameterised and takes the domain from its
caller. The gap is that its future caller (#0045) will pass a config value nobody
guarantees is set.

Two candidate fixes, decide deliberately:

1. **Add `EMAIL_LIST_DOMAIN` to the `required` table** in `config.Load`. Cheapest
   and most consistent with the other email variables, but it makes the variable
   mandatory for every deploy including dev — check `internal/devstore`/`STORAGE=json`
   runs and `scripts/dev.sh` before doing this, and consider `skipInDev: true`.
2. **Make `CampaignHeaders` drop the `mailto:` form when `listDomain` is empty.**
   RFC 8058 permits an HTTPS-only `List-Unsubscribe`, and `List-Unsubscribe-Post`
   still applies, so one-click keeps working. Belt-and-braces alongside (1).

Whichever is chosen, add a test pinning it — `internal/config`'s existing
`config_test.go` already asserts the loaded value, so the missing-variable case is
a small addition there, and `campaign_headers_test.go` is the place for (2).

Must be closed **before the first real campaign send**, not merely before #0045
merges — a malformed `List-Unsubscribe` on live mail is a deliverability problem
that costs sender reputation, which is exactly what PRD §6.5's opening paragraph
warns about.

Related but distinct: the `List-Id` header uses the *singular*
`list.opencircuitsf.com` as a hard-coded constant (PRD §6.5 gives it verbatim) and
is deliberately not derived from this variable, so it is unaffected.

## Root cause

`internal/config/config.go`'s `required` table validates `BASE_URL`,
`WEBAUTHN_RP_ID`, `WEBAUTHN_RP_ORIGIN`, `SESSION_SECRET`, `ADMIN_EMAIL`,
`AWS_REGION`, and `EMAIL_FROM` — every string that is a domain/identity value
rather than an operational knob — but `EMAIL_LIST_DOMAIN` was left out despite
belonging in that same category (added in #0007, unused by any caller until
#0035 wired `mailing.CampaignHeaders` to it). `CampaignHeaders` in turn
concatenates `listDomain` directly into the `mailto:` host with no guard, so
an unset variable produces `mailto:unsubscribe@?subject=...` — syntactically
invalid per RFC 6068.

## Fix

Two changes, matching this issue's own "belt-and-braces" framing:

1. **`EMAIL_LIST_DOMAIN` is now required, with no default** — added to
   `config.go`'s `required` table with `skipInDev: false`. I chose "required"
   over "defaulted to `lists.opencircuitsf.com`" by following the codebase's
   own established convention rather than inventing a third pattern: every
   *identity/domain* string already in the required table (`WEBAUTHN_RP_ID`,
   `EMAIL_FROM`, `AWS_REGION`, …) has **no** default — defaults in this file
   are reserved for numeric/boolean operational dials (`PORT`,
   `MAX_SEND_RATE`, `SEND_BATCH_SIZE`, `SEND_WORKER_ENABLED`). A default
   domain would exactly reproduce the "opaque failure from a silent mismatch"
   CLAUDE.md §7 already warns about for `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_ORIGIN`:
   a deploy that never set `EMAIL_LIST_DOMAIN` would boot fine and mail out
   headers pointing at an unsubscribe address nobody provisioned to receive
   it. Failing loud at boot is strictly better for a value this deployment-
   specific. `skipInDev: false` (not skipped) also matches precedent —
   `EMAIL_FROM` and `AWS_REGION` are likewise required unconditionally, not
   just in non-dev mode; `DATABASE_URL` is the *only* field with
   `skipInDev: true`, because `STORAGE=json` genuinely has no database to
   need one. `EMAIL_LIST_DOMAIN` has no comparable dev-mode exemption: dev
   mode still needs *a* value to exercise `CampaignHeaders` correctly, even
   though nothing sends real mail until #0045. `.env.example` already ships a
   real value (`lists.opencircuitsf.com`), so this does not newly break
   `./scripts/dev.sh` for the next person — verified below.
2. **`mailing.CampaignHeaders` no longer trusts its callers.** It is a pure
   function reachable from anywhere (a future test, a wiring mistake in
   #0045), and "config requires it" plus "#0045's Preflight independently
   refuses to send on `list_domain_unset`" are both defence outside this
   function's own boundary — not proof of what a caller actually passes. A
   blank or whitespace-only `listDomain` now drops the `mailto:` form
   entirely and emits an HTTPS-only `List-Unsubscribe`, which RFC 8058
   explicitly permits; `List-Unsubscribe-Post` still applies, so one-click
   unsubscribe keeps working with zero degradation to the recipient. This
   does **not** duplicate #0045's `list_domain_unset` gate — that gate
   decides whether a campaign is *allowed to start sending at all*; this
   guard decides what one function emits if it is ever called with an empty
   string regardless of that gate's outcome.

`docs/configuration.md`'s `EMAIL_LIST_DOMAIN` row is updated from
`Required: no` to `yes`, with a note pointing at both this issue and
`mailing.CampaignHeaders`. `.env.example` needed no change — it already
ships `EMAIL_LIST_DOMAIN=lists.opencircuitsf.com` uncommented.
`scripts/dev.sh` needed no change either: it does not export `EMAIL_FROM` or
`AWS_REGION` (both already required, unconditionally, before this issue) and
relies on a real `.env` supplying those — `EMAIL_LIST_DOMAIN` now follows
that identical, pre-existing pattern rather than a new one.

## Gotchas

- `scripts/dev.sh` and `.env.example` needed **no** changes — worth calling
  out explicitly because the task brief flagged this as a real risk
  ("a required variable that dev tooling doesn't set will break
  `./scripts/dev.sh`"). It turned out this project already has that exact
  gap for `EMAIL_FROM` and `AWS_REGION` (both required, unconditionally,
  since before this issue, and neither exported by `dev.sh`), so
  `EMAIL_LIST_DOMAIN` joining them doesn't introduce a new failure mode —
  it was already true that a from-scratch checkout with no `.env` file
  cannot run `dev.sh` successfully. That gap is pre-existing and out of
  this issue's scope; flagging it here in case it's worth its own issue.
- `Load` does not `strings.TrimSpace` before the required-field `== ""`
  check (matching every other required field's convention — the
  `normalizeBaseURL` doc comment notes godotenv/systemd already trim
  whitespace before values reach `config.go`), so I likewise did not add a
  bare-hostname format check to the config guard itself — that would be a
  new, unprecedented validation tier the other six required string fields
  don't get. The whitespace-tolerant defence lives in `CampaignHeaders`
  instead, where it also protects against a caller (not just the
  environment) passing a blank string.
