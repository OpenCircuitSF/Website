## Description

Both topic-ARN checks in `Verifier.Verify` run *last* — after the signing
certificate has already been fetched over the network and after
`rsa.VerifyPKCS1v15`. The `v.topicARN == ""` case is the clearest: it reads
one config field, takes no attacker input, and can never be satisfied, yet a
misconfigured service still performs an outbound HTTPS fetch for every message
it is about to reject. Conventional ordering is to fail fast on the cheap,
local check before the network call. `#0038` is about to mount this on a
public, unauthenticated endpoint.

## Root cause

`Verify`'s checks were written in the order the fields happen to be needed for
signature verification (cert URL → fetch → key → canonical string → signature)
with the topic-ARN allowlist appended at the very end almost as an
afterthought, rather than in the order that fails cheapest first. Nothing
about the topic-ARN checks actually depends on anything computed in between —
`m.TopicArn` is read straight off the incoming message and `v.topicARN` is a
config field set at construction — so both checks could always have run
immediately, they just never did.

## Fix

`internal/sesnotify/verify.go`, `func (v *Verifier) Verify`: moved the
`v.topicARN == ""` and `m.TopicArn != v.topicARN` checks from after
`rsa.VerifyPKCS1v15` to immediately after `validateCertURL` succeeds and
before `v.getCert` (the network fetch). This preserves `#0037`'s
host-validation-before-fetch property exactly: `validateCertURL` itself is
untouched and still runs first, unconditionally, before any other check —
only the topic-ARN checks moved, and they moved to *before* the fetch, never
after it.

The two checks that used to sit after `rsa.VerifyPKCS1v15` were removed
outright rather than kept as a second "defense in depth" copy, contrary to
the issue's suggested shape. Reasoning: `Verify` never mutates `m`, and both
the early and late copies would read the exact same `v.topicARN` /
`m.TopicArn` values with nothing in between able to change them. A duplicate
check under those conditions can never fire — the early copy has already
returned for every input that would trip the late one — so keeping it would
be unreachable dead code, not a real second layer. Removing it keeps the
function's control flow honest about what can actually happen.

**Error identity — confirmed unchanged for every case that previously
succeeded or failed on its own terms** (nil message, hostile
`SigningCertURL`, valid signature, tampered body/subject, unsupported
`SignatureVersion`, fetch failure, signature failure): each still returns the
exact same error text it did before, just earlier in the function where the
topic checks fired even earlier. No case here changes which side of the
`ErrCertUnavailable` (500/retry) vs. plain-error (403/no-retry) split in
`#0038`'s planned mapping it falls on.

**One error-classification change, exactly as the issue predicted and
intended:** a message whose `TopicArn` is unconfigured or non-allowlisted
*and* whose `SigningCertURL` happens to be unreachable used to return
`ErrCertUnavailable` (because the fetch ran first and failed) — `#0038` would
have mapped that to a 500, and SNS would retry a message that could never
have been accepted regardless of how many times it retried. After this fix
the same message is rejected by the topic-ARN check before the fetch is ever
attempted, so it returns the plain `"no topic ARN configured"` /
`"...does not match the configured topic"` error instead — a terminal
rejection (403, no retry) under `#0038`'s planned mapping. This is the fix
the issue asked for, called out explicitly here per the assignment's
instruction to flag any classification change since `#0038` depends on it.

One more ordering detail worth naming: a message with *both* a hostile
`SigningCertURL` *and* a bad `TopicArn` still returns the `SigningCertURL`
error, not the topic error — `validateCertURL` runs first in both the old and
new code, unchanged. Only the relative order of the topic checks versus the
fetch/signature-verification steps changed, not their order versus
`validateCertURL`. No test exercises that specific hostile-URL-plus-bad-topic
combination, and no acceptance criterion depends on it; noted here for
completeness.

`doc.go` was reviewed and requires no change: it already describes the
signature fact and the topic fact as two independent things `Verify`
establishes, without asserting an order between them (this was also `#0106`'s
finding). That description remains accurate after this reorder.

`internal/sesnotify/verify_test.go`:

- `TestVerify_EmptyConfiguredTopicArnRejectsEverything` — inverted the
  `calls != 1` → fail assertion (which encoded the old order — see `#0106`'s
  `## Gotchas`) to `calls != 0` → fail, the `TestVerify_HostileSigningCertURL`
  idiom, since the fetcher must now never be invoked for an unconfigured
  topic.
- `TestVerify_TopicArnMismatch` — added the same `calls == 0` assertion
  (previously this test only checked `err != nil` and never inspected
  `calls`), so both the empty-config case and the wrong-topic case named in
  the assignment are covered by a fetcher-was-never-invoked proof.

No other test needed a change: `TestVerify_TamperedTopicArn` signs under a
topic outside the allowlist and only tampers `m.TopicArn` to the allowlisted
value *after* signing, so `Verify` sees an allowlisted `TopicArn` throughout
and the early topic check passes exactly as before — the test still isolates
the signature-integrity property it is named for, unaffected by the reorder.

## Steps to reproduce

Read `Verify` top to bottom in `internal/sesnotify/verify.go`, or observe it
empirically: `TestVerify_EmptyConfiguredTopicArnRejectsEverything` builds a
`Verifier` with `topicARN == ""` and a counting fake fetcher, and the counter
reads `1`, not `0`, after `Verify` returns its rejection.

The order in `internal/sesnotify/verify.go`, `func (v *Verifier) Verify`:

1. nil-message check
2. `v.validateCertURL(m.SigningCertURL)` — the SSRF host/region guard (`#0037`)
3. `v.getCert(ctx, certURL)` — **network fetch**, cached by URL
4. public-key type assertion, `canonicalString`, base64-decode of `Signature`
5. the `SignatureVersion` switch
6. `rsa.VerifyPKCS1v15` — signature verification
7. `if v.topicARN == ""` — reject, "no topic ARN configured"
8. `if m.TopicArn != v.topicARN` — reject, "does not match the configured topic"

Steps 7 and 8 are both after step 3.

## Expected behavior

A message whose `TopicArn` this service can never accept is rejected before
any outbound request is made on its behalf.

## Actual behavior

Every syntactically well-formed message with a valid-looking `SigningCertURL`
causes a certificate fetch, regardless of `TopicArn`, and regardless of
whether a topic is configured at all.

## Notes

**Severity: hardening, not a vulnerability.** This is explicitly *not* an open
SSRF — `validateCertURL` (`#0037`) pins the fetch to
`sns.<region>.amazonaws.com`, refuses redirects, bounds the body at 32 KiB,
and bounds the fetch at 5s. The target is always AWS's own endpoint. What is
wrong is that unauthenticated work is performed on behalf of a message that
will be rejected regardless.

Why it is worth fixing before `#0038` exposes it publicly:

- The URL-keyed cache is bounded at `certCacheCap = 16` and **flushes the
  whole map** on overflow rather than evicting one entry. `verify.go`'s own
  comment on that constant already names the amplification: "an attacker who
  can reach the endpoint can drive cache growth by cycling through distinct
  valid-host paths". An attacker cycling distinct valid `sns.<region>` paths
  therefore forces roughly one 5s-bounded outbound fetch per request, none of
  which can lead to an accepted message.
- The `topicARN == ""` guard is a pure config read with zero attacker input.
  Hoisting it to the top of `Verify` is free and strictly better: during the
  window before `SES_EVENTS_TOPIC_ARN` is provisioned, the endpoint currently
  makes a network round trip for every hostile POST while accepting nothing.
- Hoisting the `m.TopicArn != v.topicARN` check is safe. `m` is not mutated
  anywhere in `Verify`, so an early comparison is on the same bytes as the
  late one. `TopicArn` is unauthenticated at that point, but the check is a
  *rejection* — it can only reject messages that step 8 would have rejected
  anyway. It leaks nothing: the attacker supplied the value.
- It also improves error classification. Today a wrong-topic message whose
  cert URL happens to be unreachable returns `ErrCertUnavailable`, which
  `#0038` maps to a 500 so SNS **retries**. A message for a topic we do not
  accept should get a terminal 403, not a retry loop.

Suggested shape — keep the existing post-signature checks as defense in
depth and add an early pre-filter immediately after the nil-message check:

```go
if v.topicARN == "" {
    v.log.Error("sesnotify: SES events topic ARN not configured; rejecting all SNS deliveries")
    return errors.New("sesnotify: no topic ARN configured")
}
if m.TopicArn != v.topicARN {
    v.log.Warn("sesnotify: rejected message for unconfigured topic",
        "message_id", m.MessageId, "topic_arn", m.TopicArn)
    return fmt.Errorf("sesnotify: TopicArn %q does not match the configured topic", m.TopicArn)
}
```

Any fix must come with a test asserting the fetcher was **not** invoked
(`calls == 0`) for both the unconfigured and the mismatched case — the
`TestVerify_HostileSigningCertURL` idiom. Note that
`TestVerify_EmptyConfiguredTopicArnRejectsEverything` currently asserts
`calls != 1` → fail, encoding today's order; that assertion is the one to
invert when this lands. The `#0037` ordering property (host validation before
any fetch) must be preserved: the topic pre-filter goes *before*
`validateCertURL` or between it and `getCert`, never after the fetch.

Documentation is not out of sync — `doc.go` describes the signature fact and
the topic fact as independent and does not claim an order. `#0106`'s own
`## Actual behavior` table did claim the guard ran "before any fetch"; that
claim was wrong and its implementer corrected it empirically.

## Gotchas

- The issue's suggested shape said to keep the post-signature checks "as
  defense in depth" alongside the new early pre-filter. That was not done —
  see `## Fix` for why a literal duplicate of the same condition on
  never-mutated values is unreachable rather than a real second layer. If a
  reviewer disagrees and wants the duplicate restored anyway (e.g. as a
  guard against a future refactor that reintroduces mutation), it is a
  four-line re-add at the end of `Verify`; flagging the deviation here rather
  than silently following the letter of the suggestion.
- Placement choice: the topic pre-filter was put *between* `validateCertURL`
  and `v.getCert`, not before `validateCertURL` (the issue's other permitted
  placement, and the one shown in its suggested code snippet). This keeps
  `validateCertURL`'s error taking precedence for the (untested,
  hypothetical) case of a message with both a hostile `SigningCertURL` and a
  bad `TopicArn` — matching the precedence that already existed before this
  fix — rather than having the topic error start winning that race instead.
