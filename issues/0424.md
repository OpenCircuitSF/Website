## Description

`scripts/deploy.sh`'s preflight already runs `git status --porcelain` and prints
`note: working tree has uncommitted changes`. **That notice fired on every
deploy for two days while the two workshop cover images sat untracked on the
box** (`#0416`), and it conveyed nothing — because it is **always** lit:
`web/dist/index.html` is modified after every build (§8b), so the notice is on
permanently and therefore carries no information.

The signal existed. It was useless because it never turns off.

## Why a mechanism, when this project usually records instead

`#0416`'s review reached this conclusion deliberately, against the
`#0330`/`#0347`/`#0356`/`#0381` record-rather-than-build precedent, and the
argument is specific:

- **This hazard was already recorded once, and recurred anyway.** `#0153`'s
  Decision (2026-08-24) states that an admin can reference a cover image "only if
  someone has already put it on the server by some means outside the product."
  **Eight days later exactly that shipped**, undetected until `#0273`'s planning
  pass went looking for something else.
- Those four precedents recorded *tooling* limits that needed new harnesses and
  had no production symptom. This one has a production symptom and a live near-miss.
- There is **nowhere else it could live**. `cover_image` values are production
  database rows; no test connects to production. A repo-side `web/public/` guard
  is tautological — in any checkout every file there is tracked by construction.
  The untracked file exists only in the **deploy checkout**, where no test runs.
  `deploy.sh` is the only place that sees it.

## Premise changed 2026-09-04 — read this before implementing

**The motivating example no longer exists.** The user has decided workshop
photos are deliberately **not** in source control, and `web/public/*.jpg` and
`*.jpeg` are now gitignored (`43f4ee4`, recorded in [#0416](0416.md)).

So the two files this issue was filed about are **ignored, not untracked** —
`git status --porcelain` will not report them as `??` at all, and the gate
described below would fire on nothing.

**That does not automatically make this issue wrong**, but it does change the
question, and the question is now the deliverable:

- A gate on `??` under `web/public/` would still catch a *genuinely* forgotten
  asset — a `.png`, `.webp` or `.svg` dropped there and never committed, which
  is a real shape given 23 tracked design assets live in that directory.
- But it can no longer catch the case that motivated it, and **the ignore
  pattern is now the mechanism** for the photo workflow — arguably making the
  gate redundant for the class it was meant to cover.
- There is a sharper hazard the ignore introduces: a pattern that is *too*
  broad silently swallows a real asset. `43f4ee4` scoped it to `.jpg`/`.jpeg`
  deliberately for that reason, and recorded why in `.gitignore` itself.

**Decide whether this issue still earns a mechanism**, and say so plainly.
Closing it as superseded is a legitimate outcome — per
`#0330`/`#0347`/`#0356`/`#0381`, and now with the additional argument that the
ignore pattern already encodes the intent. If you do build the gate, its
criteria below still apply, but **criterion 4's reconstruction must use an
extension the ignore does not cover**, or it will prove nothing.

## Decision — build the gate

The 2026-09-04 note's own bullet list settles this once the extra fact above
is folded in: "a gate on `??` under `web/public/` would still catch a
genuinely forgotten asset ... which is a real shape given 23 tracked design
assets live in that directory" is not weakened by `#0432` — it is the entire
remaining case, since the jpg/jpeg carve-out that used to compete with it is
gone. The three-part argument in "Why a mechanism" above (recorded once
already and recurred anyway; a production symptom with a live near-miss;
nowhere else it can live) still holds unchanged — none of it was about the
`.gitignore` pattern, all of it was about `web/public/` being swept verbatim
into the embedded binary with nothing else watching it. Built below, with an
external harness per criterion 5.

## The shape of the fix

Keep the general notice, and add a **hard gate on `??` entries under
`web/public/`** specifically.

`web/dist/index.html` is `M`, not `??`, and outside that path — so it cannot trip
the gate. That is what makes a hard failure safe here where the existing blanket
notice could never be one.

## Acceptance criteria

1. A deploy **fails** when an untracked file exists under `web/public/`, naming
   it, and explains that the file would be embedded into the binary without
   being in the repository.
2. **It does not fire on `web/dist/index.html`** or on any other ordinary
   post-build modification. Prove both directions.
3. The existing general notice still works for other dirt.
4. **Prove it against the real failure**: reconstruct the `#0416` situation —
   an untracked file under `web/public/` — and confirm the gate catches it, with
   a control where the tree is clean apart from the usual `dist/` modification.
   Do this in a throwaway copy, never the tracked tree or the box.
5. `scripts/deploy.sh` is a script, so per §8 the proof belongs in an **external
   harness** — `scripts/*_guard_test.sh`, wired into `scripts/check.sh guards` —
   which cannot be disarmed by editing its subject. Follow
   `scripts/db_reset_guard_test.sh`'s shape.
6. Mind `CLAUDE.md` §8's shell traps: **bash here is 3.2.57**, so no `${var,,}`,
   `declare -A`, `mapfile`, or `&>>`; and backticks inside an unquoted heredoc

7. Run `scripts/check.sh guards` (note `dev_guard_test.sh` alone costs ~48s and

## Root cause

`scripts/deploy.sh`'s only signal for "something is in the tree that shouldn't
be" was one blanket check — `[ -n "$(git status --porcelain)" ] && info
"note: working tree has uncommitted changes"` — covering the entire working
tree. `npm run build` rewrites `web/dist/index.html` with fresh hashed asset
references on every single deploy, so that file is `M` on every run, so the
notice fires on every run. A notice with no "off" state carries zero
information regardless of what else is dirty — which is exactly why two
untracked cover images under `web/public/` (`#0416`) went unnoticed for two
days even though the notice was, technically, correctly reporting dirt the
whole time.

## Fix

Added a second, narrower check in `scripts/deploy.sh`'s preflight, ahead of
the existing blanket notice: `git status --porcelain -- web/public/`, filtered
to `??` entries only. If any exist, the deploy **fails** (`die`), naming every
offending path and explaining that `web/public/` is swept verbatim into
`web/dist/` by `npm run build` and then embedded into the binary by
`//go:embed all:dist` — so an untracked file there reaches production without
ever being committed. The block is bracketed with `# GATE-0424-BEGIN` / `#
GATE-0424-END` marker comments so an external harness can extract exactly this
logic (see `## Verification`) without depending on a hand-copied restatement
of it.

This is safe as a hard failure, unlike the general notice, because it is
scoped to one directory: `web/dist/index.html` is `M`, not `??`, and lives
outside `web/public/`, so the ordinary post-build modification can never trip
it. The general notice is left completely unchanged and still runs for
everything else.

Per the issue's own "Premise changed" notes: the two files that originally
motivated this (`soldering.jpg`, `programming_leds.jpg`) are gone from
`web/public/` entirely as of `#0432`, and nothing there is gitignored any
more — so the reconstruction in `## Verification` uses `.jpg`, the original
extension, with no need to route around an ignore rule that no longer exists,
and additionally proves the gate is scoped (does not fire on dirt elsewhere)
and that the general notice still functions.

No divergence from the issue's own "The shape of the fix" section — implemented
exactly as sketched there, after concluding above that `#0432` did not
retire the case for it.

## Gotchas

- **`:5173` was live from another agent for the entire session** — this is
  exactly the shared-resource situation `CLAUDE.md` §8b describes, and the

- **`sed -i` is not portable** (BSD vs GNU differ on the in-place flag) — the

  pulls `deploy.sh`'s own current source at run time rather than embedding a
  restated copy of the logic, precisely so a future edit to the gate is what

  and it is why the mutation proof (Part 5) had to mutate a *copy* rather than
  assert against a second hardcoded string.

### What was verified and is correct

**The hard failure is what this issue asked for, not an escalation.**
Criterion 1 says a deploy *fails*, and "The shape of the fix" says to add a
hard gate. The implementer did not widen scope on its own reasoning.

**The safety argument for making it hard is sound, and I re-measured it rather
than taking it on trust.** In a throwaway repo shaped like the real one, with
only the ordinary post-build change present, `git status --porcelain` reports
` M web/dist/index.html` — non-empty, so the general notice fires — while
`git status --porcelain -- web/public/` reports nothing at all. So the two
"quiet" assertions pass because the gate is genuinely scoped, not because the
tree happened to be clean. Adding untracked dirt at the repo root leaves the
scoped query still empty; adding `web/public/oops.jpg` makes it report
`?? web/public/oops.jpg`. An untracked *subdirectory* is caught too — porcelain
collapses it to `?? web/public/photos/`, which the gate's `/^\?\? /` still
matches.

**Empty-extraction handling is right.** All four extractions are asserted
non-empty before use, with exit 2 reserved for a broken harness. Deleting the
markers, renaming them, or reformatting `die()` all fail closed rather than
passing vacuously. This is the one §8 rule the harness gets right by
construction.

**Isolation is genuine.** This is not `#0258`'s fourth-attempt shape: nothing
is sourced into a subshell of the running `scripts/check.sh`, and nothing is
read back with `declare -f`. Each case writes a standalone file under
`mktemp -d` and runs it as `bash FILE` — a separate process — with `die` and
`info` written into that file explicitly. `scripts/check.sh` exports no
functions, so no live definition can leak in. The "measuring the running
process instead of the file" failure mode cannot occur here.

**Oracle representation is right for the gate.** It executes `scripts/deploy.sh`'s
own bytes rather than a hand-copied restatement, and the general notice is
anchored on its user-facing text — a different representation from the marker
pair, so a single edit cannot satisfy both. The mutation proof's `sed` pattern
is a hardcoded restatement of the condition, but both of its failure branches
call `fail`, so it fails closed when the pattern stops matching. Right
direction.

**bash 3.2.57 clean, checked independently of the implementer's `bash -n` and

### The defect: `grep -m1` extraction with no exactly-once assertion

§8 states the rule for exactly this design: assert the marker block appears
exactly once, because leaving the real definition intact and adding a second
one shadows it at runtime while the scan takes the first — and anything
modelled on GUARD-0208 must carry its begin/end counts. This harness asserts
**no** counts at all: not for the marker pair, and not for the two helper
definitions, which it pulls with `grep -m1`.

`grep -m1` takes the **first** match. Bash resolves a duplicated function
definition to the **last**. Those point in opposite directions, and the gap
between them is a silent bypass. Measured on a private copy of both scripts
under `mktemp -d`, never the tracked tree: inserting one extra line above the
preflight section —

```
die(){  printf '    (soft) %s\n' "$*" >&2; }
```

— leaves the entire `GATE-0424` block byte-identical, so the harness extracts
the original `die` and reports:

```
VERIFICATION PASSED — all deploy.sh web/public/ gate checks hold (#0424)
```

while the mutated `deploy.sh`, run against a repo holding an untracked
`web/public/forgotten.png`, prints the gate's message as an ordinary note and
**exits 0** — the deploy is no longer blocked. A disarmed production gate with
a green harness is precisely the failure §8 records for `#0258`.

Also measured: duplicating the marker pair with a benign decoy block is
accepted silently, because the extraction's `awk` sweep concatenates both
blocks. That one is latent rather than an active bypass today — I could not
construct a duplicate-block edit that disarms the gate, since everything
between the markers is what gets executed — but it should still be counted, for
the reason GUARD-0208's own failure message gives.
