## Description

`scripts/deploy.sh`'s preflight already runs `git status --porcelain` and prints
`note: working tree has uncommitted changes`. **That notice fired on every
deploy for two days while the two workshop cover images sat untracked on the
box** (`#0416`), and it conveyed nothing — because it is **always** lit:
`web/dist/index.html` is modified after every build (§8b), so the notice is on
permanently and therefore carries no information.

The signal existed. It was useless because it never turns off.

## Why a mechanism, when this project usually records instead

`#0416`'s review reached this conclusion deliberately, against the
`#0330`/`#0347`/`#0356`/`#0381` record-rather-than-build precedent, and the
argument is specific:

- **This hazard was already recorded once, and recurred anyway.** `#0153`'s
  Decision (2026-08-24) states that an admin can reference a cover image "only if
  someone has already put it on the server by some means outside the product."
  **Eight days later exactly that shipped**, undetected until `#0273`'s planning
  pass went looking for something else.
- Those four precedents recorded *tooling* limits that needed new harnesses and
  had no production symptom. This one has a production symptom and a live near-miss.
- There is **nowhere else it could live**. `cover_image` values are production
  database rows; no test connects to production. A repo-side `web/public/` guard
  is tautological — in any checkout every file there is tracked by construction.
  The untracked file exists only in the **deploy checkout**, where no test runs.
  `deploy.sh` is the only place that sees it.

## Premise changed 2026-09-04 — read this before implementing

**The motivating example no longer exists.** The user has decided workshop
photos are deliberately **not** in source control, and `web/public/*.jpg` and
`*.jpeg` are now gitignored (`43f4ee4`, recorded in [#0416](0416.md)).

So the two files this issue was filed about are **ignored, not untracked** —
`git status --porcelain` will not report them as `??` at all, and the gate
described below would fire on nothing.

**That does not automatically make this issue wrong**, but it does change the
question, and the question is now the deliverable:

- A gate on `??` under `web/public/` would still catch a *genuinely* forgotten
  asset — a `.png`, `.webp` or `.svg` dropped there and never committed, which
  is a real shape given 23 tracked design assets live in that directory.
- But it can no longer catch the case that motivated it, and **the ignore
  pattern is now the mechanism** for the photo workflow — arguably making the
  gate redundant for the class it was meant to cover.
- There is a sharper hazard the ignore introduces: a pattern that is *too*
  broad silently swallows a real asset. `43f4ee4` scoped it to `.jpg`/`.jpeg`
  deliberately for that reason, and recorded why in `.gitignore` itself.

**Decide whether this issue still earns a mechanism**, and say so plainly.
Closing it as superseded is a legitimate outcome — per
`#0330`/`#0347`/`#0356`/`#0381`, and now with the additional argument that the
ignore pattern already encodes the intent. If you do build the gate, its
criteria below still apply, but **criterion 4's reconstruction must use an
extension the ignore does not cover**, or it will prove nothing.

## The shape of the fix

Keep the general notice, and add a **hard gate on `??` entries under
`web/public/`** specifically.

`web/dist/index.html` is `M`, not `??`, and outside that path — so it cannot trip
the gate. That is what makes a hard failure safe here where the existing blanket
notice could never be one.

## Acceptance criteria

1. A deploy **fails** when an untracked file exists under `web/public/`, naming
   it, and explains that the file would be embedded into the binary without
   being in the repository.
2. **It does not fire on `web/dist/index.html`** or on any other ordinary
   post-build modification. Prove both directions.
3. The existing general notice still works for other dirt.
4. **Prove it against the real failure**: reconstruct the `#0416` situation —
   an untracked file under `web/public/` — and confirm the gate catches it, with
   a control where the tree is clean apart from the usual `dist/` modification.
   Do this in a throwaway copy, never the tracked tree or the box.
5. `scripts/deploy.sh` is a script, so per §8 the proof belongs in an **external
   harness** — `scripts/*_guard_test.sh`, wired into `scripts/check.sh guards` —
   which cannot be disarmed by editing its subject. Follow
   `scripts/db_reset_guard_test.sh`'s shape.
6. Mind `CLAUDE.md` §8's shell traps: **bash here is 3.2.57**, so no `${var,,}`,
   `declare -A`, `mapfile`, or `&>>`; and backticks inside an unquoted heredoc
   execute. `bash -n` and `shellcheck` both pass on bash-4 syntax, so neither
   will catch it.
7. Run `scripts/check.sh guards` (note `dev_guard_test.sh` alone costs ~48s and
   binds `:5173`). Per §5 name the specific tests that ran. No
   Go-file-plus-line-number citation (`#0352`).
