## Description

`#0057`'s plan specifies the A1 identity as **receive-only**: "no DKIM, no MAIL
FROM, never used to send". Verification for receiving needs only the
`_amazonses` TXT token.

Three Easy DKIM CNAMEs are nevertheless published in the zone:

```
5mmlcrvrq6cdasr7nesrsn3dccbegjxe._domainkey.lists.opencircuitsf.com.
hawuw6ipm5grsf2lt2352tawz6r67rxl._domainkey.lists.opencircuitsf.com.
matlz3nwf4655blljbpeewyspc2delzj._domainkey.lists.opencircuitsf.com.
```

Read from `route53 list-resource-record-sets` on zone `Z0825067RV8QY5UIKS96`,
2026-09-11, and confirmed independently by the orchestrator. SES enables Easy
DKIM by default on a new domain identity unless told otherwise, so this was
most likely automatic rather than deliberate.

## Fix

Per the recorded decision: DKIM stays enabled, no DNS changes, the docs are
corrected. Both runbooks now describe A1 as having Easy DKIM enabled (SES's
automatic default on identity creation) instead of "receive-only; no DKIM",
name the three CNAMEs with their sources and dates, and state plainly that
**nothing sends from `lists.opencircuitsf.com`** and no configuration in
either runbook makes it able to — sending stays on `mailing.opencircuitsf.com`.
The CNAMEs are explicitly left in place rather than removed to tidy DNS, and
the apex MX and `mailing.` DKIM records are untouched. The "automatic"
conclusion is presented as evidence-based, not assumed: no runbook of ours ever
created those records (`#0057`'s plan specified the identity receive-only, and
the only change batch kept for it is D1's TXT) — while saying plainly that the
SES-side reads that would prove it directly remain denied, so the conclusion
rests on the DNS evidence plus the plan record.

## Verification

All read-only, per the decision:

- `dig CNAME` on each of the three `_domainkey.lists.opencircuitsf.com`
  tokens — each resolves to its `<token>.dkim.amazonses.com.` (2026-09-13);
  the records are live.
- `dig TXT _amazonses.lists.opencircuitsf.com` — still returns the D1 token,
  so the identity's verification record is intact; no records were removed, so
  inbound receipt verification is a read-back of the existing setup, not a
  post-change test.
- `dig +noall +answer MX opencircuitsf.com` — still exactly
  `1 smtp.google.com.`; the apex MX was never touched.
- Live SES read attempted and denied: `aws sesv2 get-email-identity`,
  `aws ses get-identity-dkim-attributes`, and
  `aws ses get-identity-verification-attributes` all return AccessDenied for
  `certbot-dns-updater` (the only credential available from this workstation),
  matching what both docs already recorded. A direct `DkimEnabled` read
  therefore did not happen and is recorded as an obstacle, not assumed away.
- No Go or web code changed; nothing in this fix affects a test suite.

### Why it is worth a look rather than a shrug

Functionally this is harmless — DKIM keys on an identity nothing sends from
sign nothing. Two reasons it should not just be left undescribed:

1. **`#0057`'s own documentation says the opposite.** An operator reading
   "receive-only, no DKIM" and then finding three `_domainkey` records has to
   stop and work out which is wrong. `#0057` has already been through three
   review bounces caused by exactly this class of documentation-versus-reality
   gap.
2. **It makes `lists.opencircuitsf.com` a send-capable identity.** Nothing
   sends from it today — `EMAIL_LIST_DOMAIN` is consumed only by
   `mailing.CampaignHeaders`' `mailto:` builder — but the capability now exists
   without a decision behind it. The project deliberately sends from
   `mailing.opencircuitsf.com` and deliberately keeps the apex MX on Google
   Workspace; a second send-capable identity appearing by default is the kind
   of thing worth noticing before it is load-bearing.

## Decision (recorded 2026-09-13 — user's call, made via the orchestrator)

**Leave DKIM enabled; correct the docs.** The conservative default the issue
itself flags as defensible: removing DNS records to tidy up carries more risk
than the untidiness. `docs/aws-requests.md` and `docs/email-setup.md` are
updated to describe the identity as having Easy DKIM enabled (SES's automatic
default on creation), nothing sends from `lists.opencircuitsf.com` and no
config change makes it able to, the apex MX and `mailing.` DKIM records are
untouched, and inbound receipt is verified unaffected (no records removed, so
verification is a read-back of the existing setup, not a post-change test).
