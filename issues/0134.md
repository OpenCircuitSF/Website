## Description

Four surgical defects `#0051`'s phase-3 review found and proved. None was an unmet acceptance criterion, so `#0051` passed; the first is a real runtime bug and the other three are claims that contradict the code they sit next to.

**1. `Create` is not atomic.** Passing an unknown `interest_id` returns `ErrInterestNotFound` **and leaves the workshop row behind** — the reviewer measured `count(*) = 1` after the error. The slug-retry loop has to insert outside a transaction, so the insert survives the failed tag step. The result is a ghost draft that burns a slug and gets no audit row, reachable from `#0052`'s admin UI. `Update`, tested the same way, *is* atomic, and the precedent cited in `#0051`'s own `## Fix` — `mailing.CampaignStore.Create` — does the whole thing in one transaction.

**2–4. Three statements that are false as written**, each next to the code that disproves it:
- `internal/audit/actions.go`'s new comment says a `-> canceled` transition is recorded as `ActionWorkshopUpdated`. It is not: `ActionWorkshopCanceled` is declared three lines below and the shipped handler emits it — `#0051`'s own test observes `published, unpublished, published, canceled`.

## Root cause

1. **`Create` was two units of work stitched together, not one.** The
   slug-collision retry loop ran as plain autocommitted `INSERT`s against
   `s.pool` (no open transaction), so once one candidate succeeded the
   workshop row was already durably committed. Only *after* that did `Create`
   open a transaction to link `workshop_interests`. A bad `interest_id`
   returned `ErrInterestNotFound` from inside that second transaction, which
   rolled back the interest links — but had nothing to say about the
   already-committed workshop row from step one. Proved by execution before
   the fix: `Create` with `InterestIDs: []int64{999999999}` returned
   `ErrInterestNotFound`, and `SELECT count(*) FROM workshops WHERE slug =
   $1` for the slug it would have taken returned `1`.
2. `internal/audit/actions.go`'s workshop-lifecycle comment said any status
   change other than `-> published` / `published -> draft` is recorded as
   `ActionWorkshopUpdated`, "e.g. -> canceled, or canceled -> draft". Checked
   against `internal/handlers/admin_workshops.go`'s PATCH handler (lines
   446–463): a third `case current.Status != workshops.StatusCanceled &&
   updated.Status == workshops.StatusCanceled` emits
   `audit.ActionWorkshopCanceled`, not `ActionWorkshopUpdated`. Only
   `canceled -> draft` (and no-op status) actually falls through to
   `ActionWorkshopUpdated`. The comment was wrong about `-> canceled`.
3. `NewAdminWorkshopsHandler`'s doc comment claimed "every production call
   site passes a real `*seo.Site`". Checked against
   `cmd/opencircuit/main.go:215`: `handlers.NewAdminWorkshopsHandler(workshopsStore,
   nil, auditLogger)` — the `servePostgres` path passes a literal `nil` for
   the invalidator, deliberately, per `#0051`'s review Ruling 1 (safe because
   `invalidate()` guards on `h.invalidator != nil`).
4. `docs/database.md`'s `000020_create_workshops` row was checked word for
   word against `migrations/000017:54-58` (the `campaign_interests` table
   definition). The row does **not** actually say `campaign_interests` lacks
   `ON DELETE CASCADE` — it correctly says `workshop_interests` has `ON
   DELETE CASCADE` and then, in a trailing parenthetical, correctly says
   `campaign_interests` "has no such index" (referring to
   `idx_workshop_interests_interest`/`idx_subscriber_interests_interest`'s
   precedent, not to `ON DELETE CASCADE`) — matching `#0050`'s review Ruling
   2 exactly, which is about a missing index, not a missing cascade. So the
   filed issue's characterization of this clause doesn't hold up against the
   current file. What *is* true: the sentence's antecedent for "no such
   index" is ambiguous enough, sitting right after an `ON DELETE CASCADE`
   clause, that a fast read could conclude it's talking about the cascade —
   which is very likely how this got filed. Reworded for clarity (see
   `## Fix`) rather than left as a footgun for the next reader, even though
   no factual correction was needed.

## Fix

**Design decision — pgx pseudo-nested transactions (savepoints), not a
pre-computed slug.** `mailing.CampaignStore.Create` (the cited precedent) has
no slug-retry loop to preserve, so it can't be copied verbatim; the workshops
version has to keep the property `#0050`'s reviewer required — each slug
candidate is a real `INSERT` fought out against the `UNIQUE` constraint, never
a pre-check-then-insert race, so two concurrent `Create`s with the same title
can never both win the same slug. Two ways to keep that under one
transaction:

- **Pre-compute a candidate slug outside the transaction, insert once inside
  it.** Rejected: reintroduces exactly the pre-check-then-insert race the
  original design deliberately avoided — a `SELECT` to find the next free
  suffix, then an `INSERT` a moment later, is a TOCTOU window two concurrent
  `Create`s with the same title can both pass through with the same
  candidate.
- **Savepoints (chosen).** `pgx.Tx.Begin` on an existing `Tx` returns a
  "pseudo-nested transaction" — pgx issues `SAVEPOINT`, and maps `Commit`/
  `Rollback` on that nested `Tx` to `RELEASE SAVEPOINT`/`ROLLBACK TO
  SAVEPOINT`. So `Create` now opens one outer transaction, and each slug
  attempt runs inside its own savepoint: a `unique_violation` on that
  candidate rolls back only to the savepoint (undoing just that one failed
  `INSERT`) rather than aborting the whole outer transaction — which
  Postgres would otherwise require, since any failed statement inside a
  transaction poisons it until a `ROLLBACK`/`ROLLBACK TO SAVEPOINT`. Once a
  candidate succeeds, its savepoint is released and the outer transaction
  proceeds to `replaceInterestsTx` (unchanged) and `Commit`. If the interests
  insert fails with `ErrInterestNotFound`, the deferred `tx.Rollback(ctx)`
  undoes the workshop insert along with it — no ghost row.

This keeps the "real INSERT per attempt, no pre-check" property intact while
making the whole method one atomic unit. `internal/workshops/store.go`'s
package doc comment (the "Slug generation" and new "Create is one
transaction, savepoints and all (#0134)" sections) documents this in full,
and `Create`'s own doc comment cross-references it.

The other three fixes are one-line-scope doc corrections at the sites listed
in `## Root cause` items 2–4; `docs/database.md`'s edit also adds the exact
migration line reference (`000017:54-58`) and names both indexes involved
so the sentence can't be misread the way it apparently was when this issue
was filed.

## Gotchas

- **A commit-message-only reference to `git commit -- <paths>` almost got
  this issue's fix bundled into `#0052`'s commit.** Mid-implementation, `git
  add <my 5 files>` followed by `git status` showed the *other* concurrent
  agent's already-staged `web/` files sitting in the same index alongside
  mine (neither agent ran `git add -A`; the index was simply shared state).
  A first `git commit -m ... -- <my paths>` reported "nothing to commit,
  working tree clean" because the other agent's own commit had landed
  between the `git add` and the `git commit`, sweeping my staged changes into
  *their* `#0052` commit along with their `web/` files (confirmed via `git
  show --stat` on that commit — my 5 files were listed). No content was lost
  — everything was still in the tree — but the attribution and commit message
  would have been wrong. That commit was superseded moments later by the
  other agent's own follow-up commit (same title, new hash), which did *not*
  include my files, leaving them as ordinary uncommitted working-tree changes
  again. At that point `git diff HEAD -- <my 5 files>` confirmed the new HEAD
  didn't contain my changes, so a clean `git add` + `git commit -- <paths>`
  finished correctly. **Lesson for future concurrent runs: after `git add`
  on specific paths, don't assume the following `git commit` will contain
  only what you added — re-check `git show --stat` (or `git log -1
  --name-only`) on whatever HEAD becomes immediately after, especially when
  another agent is actively committing to the same working tree.** Always
  pass the explicit pathspec to `git commit` itself (not just to `git add`)
  as a second line of defense — it commits only those paths' current index
  content regardless of what else is staged, which is what let this recover
  cleanly without touching the other agent's staged work.
- Postgres transaction semantics matter here: once one statement in a
  transaction errors, every subsequent statement is rejected until a
  `ROLLBACK` or `ROLLBACK TO SAVEPOINT` runs. That's *why* the original
  autocommitted-loop design existed in the first place (each attempt had to
  survive its own failure independently) — pgx's pseudo-nested transactions
  (`Tx.Begin` on a `Tx`) give the same independence without leaving the
  outer transaction, which is the piece that made an atomic `Create` possible
  at all.

**Ruling 1 — the savepoint design holds under Postgres semantics.** pgx v5.9.2
`tx.go` confirms the mechanism the `## Fix` describes: `dbTx.Begin` increments
`savepointNum` and issues `savepoint sp_N` (line 170-171); the returned
`dbSimulatedNestedTx.Commit` issues `release savepoint sp_N` (309) and
`Rollback` issues `rollback to savepoint sp_N` (322). Each attempt therefore
gets a **distinct** savepoint name, so a rolled-back attempt cannot be
confused with the next one. Every exit path is covered: success releases the
savepoint; a `unique_violation` rolls back to it; a non-unique insert error, a
failed `Begin`/`Commit`/`Rollback` of the savepoint, a `replaceInterestsTx`
failure, and loop exhaustion all return with the function-scope
`defer tx.Rollback(ctx)` still armed, and a plain `ROLLBACK` is legal from an
aborted-transaction state, so nothing can strand the connection. Verified by
execution rather than by reading, in a throwaway reviewer test at
`maxSlugAttempts`-realistic depth: 50 same-title `Create`s produced
`base`, `base-2` … `base-50`, meaning the 50th call rolled back **49
savepoints inside one outer transaction and still committed**. A 51st
`Create` with a valid interest id committed its `workshop_interests` row at
that depth (`count = 1`), and a 52nd with a bad id returned
`ErrInterestNotFound` leaving `count(*) = 0` at the slug it would have taken.
No savepoint leak that matters: `ROLLBACK TO SAVEPOINT` leaves the savepoint
established, so a pathological 1000-collision title would accumulate ~999
subtransactions in one transaction — legal in Postgres, past the 64-subxid
cache only in a scenario that requires a thousand identically-titled
workshops. Not a defect, and §5 is explicit that there is no performance
requirement here.
