# 0152 — The PRD index-parity guard silently skips index forms it cannot parse, and does not cover columns

| | |
|---|---|
| **Status** | open |

## Description

`#0148` added `TestPRDWorkshopAndMailingIndexParity` (`internal/db/prd_index_parity_test.go`), which replays every `CREATE`/`DROP INDEX` across `migrations/*.up.sql` and asserts `PRD.md` §6.2 names each one correctly. It works, and `#0148`'s review re-proved it bites in both branches (missing index, diverged definition). Two gaps in it are worth closing on their own clock.

**1. Unmatched statements are skipped in silence.** The extraction regex is

```
(?i)CREATE\s+INDEX\s+(\w+)\s+ON\s+(\w+)\s*(\([^;]*?\))(?:\s+WHERE\s+([^;]*?))?;
```

Probed directly (`#0148` review), it handles more than its own comment claims — functional indexes (`lower(email)`), doubled parens, `INCLUDE`, and multi-line statements all match, because Go's leftmost-first submatch semantics expand the non-greedy column-list capture past a nested close-paren. But four real SQL forms produce **no match at all**, and a no-match on the migrations side means the index simply never enters the live map and is never checked:

| Form | Result |
|---|---|
| `CREATE UNIQUE INDEX …` | silently skipped |
| `CREATE INDEX IF NOT EXISTS …` | silently skipped |
| `CREATE INDEX CONCURRENTLY …` | silently skipped |
| statement with no terminating `;` | silently skipped |

None of these exist in `migrations/` today, so the guard is correct right now. The failure mode is the one that makes a guard worse than no guard: the first `CREATE UNIQUE INDEX` anyone adds is invisible to it, and the suite stays green while the PRD falls behind — exactly the drift `#0148` was filed about.

A related, lesser fragility: the patterns run over raw file text including SQL comments, so a commented-out `-- CREATE INDEX …` in a migration would register as a live index. That direction at least fails loudly (as a false "PRD does not mention"), so it is the smaller problem.

**2. Column parity was deferred, and the deferral's stated reason is weaker than it looks.** `#0148` scoped the guard to indexes, arguing a column would require "replaying a `CREATE TABLE` plus every later `ALTER TABLE ADD COLUMN` across up to 20 files with no single-statement anchor — materially more parsing surface". `#0148`'s review prototyped exactly that during the sweep: ~30 lines, comparing both column names and their type/default text, across all 20 migrations. It reproduced the one real column drift (`email_sends.claimed_at`, live since `000018`, absent from §6.2 until `#0148` fixed it by hand) and produced no false positives on the Phase 8 forward declarations. The extraction is not materially harder than the index case; the honest reason to defer was cost, not difficulty.

## Acceptance criteria

- [ ] `TestPRDWorkshopAndMailingIndexParity` matches `CREATE UNIQUE INDEX`, `CREATE INDEX CONCURRENTLY`, and `CREATE INDEX IF NOT EXISTS`, in any combination
- [ ] **The guard fails loudly on anything it cannot parse.** Count the `CREATE …INDEX` occurrences in each migration and in §6.2, compare against the number of statements the pattern actually matched, and `t.Errorf` on a mismatch naming the file. A silent skip must become a test failure, not a gap
- [ ] SQL `--` comments are stripped before extraction on both sides, so a commented-out statement cannot register as live
- [ ] A column-parity check in the same one direction (migrations → PRD §6.2): every column a migration creates on a `prdIndexParityTables` table appears in §6.2's `CREATE TABLE` for that table. Never the reverse — §6.2 legitimately leads with `subscribers.source`/`invited_at`/`consent_basis`/`import_id`/`soft_bounce_streak`/`last_bounce_at`/`last_delivery_at`, `email_campaigns.slug`/`archive_status`/`archived_at`, and the `subscriber_imports`/`subscriber_events`/`outbound_queue` tables, all owned by open Phase 8 issues `#0123`–`#0129`
- [ ] Column *names* are the assertion; comparing type/default text is optional and should only ship if it is false-positive-free against the current tree
- [ ] Deleting `email_sends.claimed_at` from `PRD.md` §6.2 in a scratch copy fails the new check, and restoring it passes — proved before the change is called done
- [ ] `ISSUE=NNNN scripts/check.sh go ./internal/db/...` passes with all three doc-parity guards observed running

## Notes

Filed by `#0148`'s phase-3 review. `#0148` itself is sound — the drift it fixed is fixed, its sweep was complete (independently re-run at column, type, and index level: zero remaining drift), and its guard is correctly one-directional. These are hardening items, deliberately not a bounce.

The one-directional scope is the part **not** to change. A bidirectional guard would fire today on five PRD-only indexes (`idx_email_events_recipient_time`, `idx_outbound_queue_due`, and `subscriber_events`' three), every one of them genuine Phase 8 design, and would need an allowlist that itself drifts.
