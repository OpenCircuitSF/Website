## Description

`#0138` closed the missing-server-side-validation gap for `cover_image`: a bad value now gets a 400 from `Create` and `Patch` instead of being stored and later concatenated into `og:image` and the JSON-LD.

`signup_url` has the same shape and was not covered. The admin UI checks it with `isSafeLinkHref`, but nothing on the server does, so a `javascript:` URL can be **stored** by any caller that does not go through the editor.

It is not a live XSS today. `#0054`'s detail view renders the link only through `hasExternalSignup`, which `#0054`'s own fix pass gated on `isSafeLinkHref` — so a stored `javascript:` value is refused at render time. The defect is that the database is allowed to hold a value the product has decided is unsafe, and the only thing standing between it and a reader is one client-side call site.

## Root cause

`signup_url` was round-tripped through `normalizeOptionalCampaignField` in
both `AdminWorkshopsHandler.Create` and `.Patch` with no safety check at all
— unlike `cover_image`, which `#0138` gated behind `isSafeCoverImage` at the
same boundary. The only thing standing between a stored `javascript:` value
and a reader was one client-side call: `#0054`'s `hasExternalSignup`
(`web/src/lib/workshopDetail.ts`) gates rendering behind `isSafeLinkHref`
(`web/src/lib/markdown.ts`) before it becomes a `href`. That made it not a
live XSS, but it meant the database could hold a value the product has
decided is unsafe, reachable by any caller that skips the SPA — the same
missing-boundary shape `#0138` closed for `cover_image`.

## Fix

Added `isSafeLinkHref` to `internal/handlers/admin_workshops.go` — the Go
twin of `web/src/lib/markdown.ts`'s `isSafeLinkHref`, **not** of
`isSafeCoverImage`: a link is a navigation the reader chooses to follow
(unlike a cover image, which the page loads unasked), so an absolute
`http(s)://` URL to any host stays allowed (a workshop's `signup_url` is
routinely an external ticketing page) along with `mailto:`; what's rejected
is any other scheme, a protocol-relative `//host` destination and its
backslash spellings, and — per `#0138`'s bounce — any C0 control character
(0x00–0x1f) or DEL (0x7f) anywhere in the string, since a browser deletes
ASCII tab/LF/CR before resolving a URL and an interior control character can
reassemble a dangerous scheme a naive check would miss.

Wired into both `Create` and `Patch`, mirroring `isSafeCoverImage`'s call
shape exactly: `normalizeOptionalCampaignField(req.SignupURL)` first, then
`isSafeLinkHref` on the (possibly nil) result, 400 with a new
`signupURLErrorMessage` constant on rejection, before the store call.

**Trim decision.** `isSafeLinkHref` trims internally (matching the
TypeScript function's own `href.trim()`) before testing for emptiness or a
scheme, so neither `Create` nor `Patch` pre-trims the value — same
convention `isSafeCoverImage` already uses. `normalizeOptionalCampaignField`
still tests `TrimSpace(*v) == ""` but returns the untrimmed pointer (the
divergence `#0138` pass 2 flagged as "worth knowing if `#0152` generalises"),
so a `signup_url` with stray leading/trailing whitespace can still be
*stored* once it passes the safety check — unchanged, pre-existing behavior
shared by every optional campaign-style field, not something this issue
introduces. Generalizing `normalizeOptionalCampaignField` to trim is left
out of scope; the render-time gate (`hasExternalSignup`) already trims
before calling `isSafeLinkHref`, so stray whitespace never affects what's
shown.

**A real Go/TS parity bug, found and fixed by the codepoint sweep.** The
first draft used `strings.TrimSpace` for the internal trim. Sweeping leading
codepoints through the real Go and TypeScript functions side by side found
two genuine disagreements: `unicode.IsSpace` (and therefore
`strings.TrimSpace`) treats U+0085 (NEL) as whitespace where JS's
`String.prototype.trim()` does not, and does *not* treat U+FEFF
(BOM/ZWNBSF) as whitespace where JS's `trim()` does. The BOM direction is
the dangerous one: a leading-BOM `javascript:` value could have been
**accepted** by the naive Go twin while the TypeScript original correctly
rejected it — exactly the "third, subtly different rule" criterion 2
forbids. Replaced the trim with a hand-written `isJSWhitespace` predicate
that matches ECMA-262's WhiteSpace + LineTerminator productions exactly
(tab/VT/FF/CR/LF/space/NBSP/BOM plus the Unicode `Zs` separators), and swept
again — 0 mismatches.

**Is the set now complete?** Yes, for discrete DB fields that become a
rendered `href`/`src` attribute directly. A repo-wide search
(`grep -rn 'src={\|href={' web/src`, plus the `workshops` migration's schema)
turns up exactly two: `cover_image` (`#0138`) and `signup_url` (`#0152`) —
both now validated server-side. Every other `<a href>`/`<img src>` bound to a
non-constant value in the SPA (`Header.svelte`, `Footer.svelte`, `About.svelte`)
uses a hardcoded constant (`DISCORD_URL`, `LUMA_URL`), not DB content. The
third instance the issue's own notes name — Markdown link destinations
inside `body_md` — is a different shape: free text can embed arbitrarily many
links, so there's no single discrete value to accept/reject at the boundary;
instead every extracted link is individually filtered by `isSafeLinkHref`
inside `renderMarkdownPreview` itself, on both the admin preview and the
public `WorkshopDetail` render path, already reviewed sound by `#0138` pass 1
("`renderMarkdownPreview` emits no `<a>` for any rejected form"). The
separate `email_campaigns.body_md` send pipeline
(`internal/mailing/campaign_markdown.go`) has its own independent
protection via goldmark's safe-mode `isDangerousLinkURL`, unrelated to this
issue's fields.

## Gotchas

- `strings.TrimSpace`/`unicode.IsSpace` is **not** a safe stand-in for JS's
  `String.prototype.trim()` when writing a Go twin of a TypeScript security
  rule that trims internally. They disagree at U+0085 (NEL, Go trims it, JS
  doesn't) and U+FEFF (BOM, JS trims it, Go doesn't) — confirmed by
  execution, not by reading either stdlib's docs. The BOM direction is
  security-relevant (Go would have silently accepted a value TS rejects);
  the NEL direction merely makes Go stricter (fails safe, but still a
  parity break). Any future Go twin of a JS function that trims should use
  the same `isJSWhitespace`-style explicit predicate rather than
  `strings.TrimSpace`, or sweep leading-position codepoints before trusting
  the two agree.
- The admin editor's own `signup_url` field check
  (`web/src/lib/workshopAdmin.ts`'s `isHttpUrl`) is a *different*, narrower
  client-only UX convenience (http/https only, no `mailto:`/relative) — it
  is **not** the rule this issue closes. The actual safety gate this issue
  mirrors is `#0054`'s `hasExternalSignup` → `isSafeLinkHref`
  (`workshopDetail.ts`/`markdown.ts`), the one that decides whether a stored
  value is ever allowed to become a rendered `href`. Confirm which of two
  same-field client checks is the security rule before writing a server
  twin of "the" client check — this codebase has both kinds for
  `signup_url` and they are not interchangeable.
