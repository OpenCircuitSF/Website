### What was checked, and how

**The no-logic-in-templates rule holds.** Re-ran the mechanical check across
`Campaigns.svelte`, `CampaignEditor.svelte`, `CampaignSendDialog.svelte` and
`Admin.svelte`'s diff. Every `{#if}` / `{#each}` condition is a plain boolean
name; every `disabled` / `aria-disabled` / `aria-selected` is a bare identifier
or its negation; no comparison operator, `.trim()`, `.length >`, status literal
or `||` fallback chain appears in any markup. Every domain decision routes
through `lib/campaigns.ts`, `lib/preflight.ts`, `lib/audience.ts` or
`lib/sendConfirm.ts`. `grep -rn '@html' web/src` returns nothing; the preview
is `<iframe sandbox="" referrerpolicy="no-referrer" srcdoc={preview.html}>`.

Deviations found, all judged acceptable under the plan's own "could a reviewer
tell this is right without running it" test, and all in `<script>` rather than
markup: three `inFlight ? 'Sending…' : 'Send now'`-shaped label ternaries; a
handful of `$derived` comparisons over component-local UI state
(`saveState === 'saving'`, `previewTab === 'html'`, `opt.value === mode`); and
`unmet.length > 0` / `unmet === null` computed inline in both components rather
than through `isPreflightBlocked`, which consequently ships unused (as does
`sampleIsTruncated`, though `sampleCaption` covers its purpose).

**The demotion predicate is correct and non-vacuously pinned.** It ships as
`c.status === 'draft' && c.scheduled_at != null && c.started_at == null` —
loose, per `#0041`'s carried-in review finding. The test fixture asserts
`expect('scheduled_at' in c).toBe(false)`, so the key is genuinely missing
rather than spelled `null`. Proven by a review mutation on **each half
separately**: making the `started_at` comparison strict turns *"true for draft +
scheduled_at + no started_at"* red, and making the `scheduled_at` comparison
strict turns *"false for a plain draft (keys absent)"* red. Both halves are
independently covered.

**`unmet` is rendered verbatim with no second copy of the copy.** `parseUnmet`
is the only parser and serves both the 200 advisory body and the 409's
`ApiError.body`; a blank or absent `message` falls back to the raw code; order
is never re-sorted. There is no code→message table anywhere in the SPA —
`fixLocation` maps exactly one code to a subtab and returns `null` for the other
nine, which is an affordance, not a restatement.

**The send confirmation verifies against the server.** Subject, from and
recipient count all come from `/preflight`'s `summary`, which
`AdminCampaignPreflightHandler` reads off the stored row via `GatherPreflight` —
never the editor buffer. `confirmMatches` was mutation-checked in **both**
directions: forcing it always-true reddens three tests (`"is strict — 483 does
not confirm 482"`, `"needs-confirm when clear but mistyped"`,
`"needs-confirm when clear but untouched"`); forcing it always-false reddens
three others (`"matches an exact typed count"`, `"matches with thousands
separators"`, `"ready when unmet is empty, count > 0, …"`). It is a real
equality. The `sendGuardState` proof was re-run too: replacing its
`unmet.length > 0` branch with `if (false)` reddens *"blocked when unmet is
non-empty, even with a correct count"*. Double-submit is guarded three ways
(real `disabled={inFlight}`, an early return in the `onsubmit` handler, and the
status leaving `draft`); a 409 leaves the dialog mounted, re-renders the
returned list through the identical renderer and preserves the typed count.

`confirm_count` — it answered
`{"error":"confirm_count does not match the current audience count (5); reload and try again"}`.

### 1. Where it lives: a seventh Admin subtab, backed by child components

**Decision: add `campaigns` to `Admin.svelte`'s `Section` union and its subtab
bar — exactly `#0100`'s pattern — but render the section's body from new child
components in `web/src/views/admin/`, not inline.**

`Admin.svelte` is already 2,032 lines carrying six sections. Campaign compose is
a list *plus* an editor *plus* an audience panel *plus* a pre-send panel *plus*
a modal send flow; inlining it would push that file past 3,500 lines and make
every future campaign change a merge hazard against five unrelated sections.
The change to `Admin.svelte` is therefore mechanically small and reviewable:

- add `'campaigns'` to the `Section` type;
- add one `<button class="subtab">` **appended after Suppressions** (appending
  is what `#0100` did; reordering the existing six changes muscle memory for no
  benefit);
- add `{#if section === 'campaigns'}<Campaigns />{/if}`;
- **no** `loadCampaigns()` in `Admin.svelte`'s `onMount`. The existing six all
  fetch eagerly on mount; campaigns must not, because its child fetches a list
  *and* per-campaign preflight/audience. `Campaigns.svelte` loads on its own
  `onMount`, i.e. when the subtab is first shown.

New directory `web/src/views/admin/` (three files, §2). `web/src/views/` has no
subdirectories today; this is the natural home as `#0049`'s stats view and
Phase 6's workshops admin arrive, and it keeps admin-only components out of
`web/src/lib/`, which holds *reusable* motif components.

**Routing: none. The campaign id is component state, not a URL.** All six
existing admin sections are local `$state` with no URL of their own —
`router.ts`'s `STATIC_ROUTES` has a single `/admin` entry, and its one dynamic
pattern (`WORKSHOP_DETAIL`) is public-route-specific. Making campaigns the only
URL-addressable admin section would be inconsistent; making all seven
URL-addressable means re-routing five shipped sections and extending the
router — a change no issue asks for and which belongs to one issue covering all
of them. PRD §5.2's `/admin/campaigns` row is an information-architecture
sketch that the SPA already realizes as `/admin` + sections (`/admin/settings`,
`/admin/audit`, `/admin/subscribers`, `/admin/interests` are all subtabs
today, not routes); following it literally here would mean following it for
those four too.

*Rejected — a separate top-level route + view.* Loses the shared shell, the
`is_admin` gate, the sign-out header and the subtab bar, or forces them to be
duplicated; and needs a second dynamic-segment pattern in `#0014`'s router.

*Rejected — everything inline in `Admin.svelte`.* The monolith above.

*Recommendation, not scope:* if deep-linkable admin sections are ever wanted,
file one issue that converts all seven at once.

Within the subtab, list and editor are a **master/detail swap**, not a modal:
`selectedId === null` shows the list, otherwise the editor with a "Back to
campaigns" button. The existing modal pattern in `Admin.svelte` is for short
forms (deactivate, suppress); a compose screen is not that.

### 2. The `web/src/lib/` split — four modules, and the rule that keeps them honest

`#0094` records that no test in this repository imports a `.svelte` file: there
is no jsdom, no component harness, and **anything expressed in a component is
unverifiable**. That makes the split below the single most load-bearing
decision in this plan, and the one most likely to be quietly violated.

**The rule, stated so a reviewer can check it mechanically:** in the three
components, every `{#if}`, `{#each}`, `disabled`, `aria-*` and computed string
must be either (a) a call into one of the four modules below, (b) a plain
boolean/string those calls returned, or (c) a value straight off a server
response. No comparison operator, no `.trim()`, no `.length >`, no status
string literal, no `||` fallback chain in a template. If a reviewer finds
domain logic in a `.svelte` file, the change is wrong regardless of whether it
works.

`web/src/lib/admin.ts` is already 487 lines covering six sections; four new
concerns belong in new modules, not appended to it.

#### `web/src/lib/campaigns.ts` — draft state, form validation, transition rules

- `CAMPAIGN_STATUSES` (the six from `migrations/000017`), `campaignStatusLabel`,
  `campaignStatusBadgeClass` — mirroring `subscriberStatusLabel` /
  `subscriberStatusBadgeClass` in `admin.ts`.
- `AUDIENCE_MODES` — the four values with labels and one-line help text.
- `canEditCampaign(status)` → `draft | scheduled` (`#0041`'s rule).
- `canSendCampaign(status)` → `draft` only.
- `canCancelCampaign(status)` → `scheduled | sending`.
- `interestsApplyToMode(mode)` → true for `any_of`/`all_of` only. Drives whether
  the interest fieldset is enabled.
- `validateCampaignDraft({name, subject, bodyMd, mode, interestIds})` — the
  **CRUD save** gate only: name/subject/body non-empty after trimming, and (per
  `#0041`'s carried-in criterion) at least one interest for `any_of`/`all_of`.
  It deliberately knows **nothing** about the physical address, the test send,
  the audience count, or rendering — a test asserts that (§9).
- `subjectLengthAdvice(len)` / `preheaderLengthAdvice(len)` → `{count, limit,
  tone: 'ok'|'warn'|'over', message}`. **Guidance, never a block** — the
  acceptance criterion says "length guidance", and a hard cap on a subject line
  is a decision no one made.
- `wasDemotedAfterScheduling(campaign)` and `demotionExplanation(campaign)` —
  §5.
- `cancelCopy(status)` — §7.

#### `web/src/lib/preflight.ts` — the unmet-requirements list, and nothing else

```ts
export interface UnmetRequirement { code: string; message: string }
export function parseUnmet(body: unknown): UnmetRequirement[] | null
export function isPreflightBlocked(list: UnmetRequirement[]): boolean
export function fixLocation(code: string): { section: string; label: string } | null
```

- `parseUnmet` reads `{"unmet":[{code,message}]}` off **either** a 200 advisory
  body (§3) **or** an `ApiError.body` from the send endpoint's 409 — one parser,
  so both sources reach one renderer. A body that is not that shape returns
  `null` (distinct from `[]`, which means "checked, nothing unmet").
- **Order is preserved exactly as received.** `#0045` pins the **ten** codes
  (`reply_to_missing` shipped alongside the plan's nine) in a fixed order and
  has a test for it; the client must not re-sort or group.
- An entry whose `message` is missing or blank falls back to **the raw code
  string** — never to invented copy, and never dropped. A requirement the
  client does not recognise must still appear.
- **There is no code → message table in this module, or anywhere in the SPA.**
  That is the whole point: two copies of a requirement drift, and this project
  has been bitten by that repeatedly. `fixLocation` maps a code to *where the
  operator fixes it* (e.g. `physical_address_missing` → the Settings subtab) —
  an affordance, not a restatement — and returns `null` for any code it does
  not know, so an unrecognised future code renders its server message with no
  link and nothing breaks.

#### `web/src/lib/audience.ts` — the `/audience` call's shaping and presentation

- `audienceRequestKey(mode, interestIds)` — an order-independent key (mode +
  sorted ids). Used to drop a stale response: an operator ticking three boxes
  quickly must never see the count for the first tick land after the third.
- `isStaleAudience(responseKey, currentKey)`.
- `describeAudience(preview)` → `"482 recipients"` / `"1 recipient"` /
  `"No recipients match this audience."`
- `sampleIsTruncated(preview)` → `preview.sample.length < preview.count`, and
  `sampleCaption(preview)` → `"Showing 20 of 482"`. **The literal 20 appears
  nowhere in the client** — `#0044` fixes the cap server-side and it is derived
  from `sample.length`, so if the server ever changes it the caption stays true.
- `audienceErrorMessage(err)` → for an `ApiError`, the server's message
  **verbatim**; for anything else, one generic network message.

#### `web/src/lib/sendConfirm.ts` — the typed-count gate and the send-button state

- `normalizeCountInput(raw)` → `number | null`. Accepts optional surrounding
  whitespace and `,`/thin-space thousands separators (`"1,234"` → `1234`);
  rejects anything else, including decimals and trailing characters.
- `confirmMatches(raw, count)` → strict equality on the normalized value.
- `confirmHint(raw, count)` → `null` while the field is untouched or matching,
  otherwise one short line. No scolding an empty field.
- `sendGuardState({status, unmet, audienceCount, confirmRaw, inFlight})` →
  a discriminated union `{kind: 'unavailable'|'blocked'|'empty-audience'|
  'needs-confirm'|'ready'|'sending'}`. **This is the single source of truth for
  whether mail can go out from this screen**, and the one function whose
  mutation proof is named in §9.

**API wrappers stay in `web/src/lib/api.ts`**, per the existing convention
(`listInterests`, `suppressSubscriber`, …): `listCampaigns`, `getCampaign`,
`createCampaign`, `updateCampaign`, `getCampaignAudience`,
`getCampaignPreflight`, `previewCampaign`, `testSendCampaign`, `sendCampaign`,
`cancelCampaign`. New types (`Campaign`, `AudiencePreviewResponse`,
`PreflightResponse`, `UnmetRequirement`) go in `web/src/lib/types.ts` — reuse
whatever `#0041` has already landed rather than declaring a second `Campaign`.

#### The components, which hold markup and wiring only

- `web/src/views/admin/Campaigns.svelte` — the subtab root: load the list, the
  master/detail swap, "New campaign".
- `web/src/views/admin/CampaignEditor.svelte` — fields, the preview pane, the
  audience panel, the pre-send panel, the test-send control, the action row,
  and the named-but-empty progress region for `#0048`.
- `web/src/views/admin/CampaignSendDialog.svelte` — the typed-count
  confirmation (§6).

### 3. `GET /admin/campaigns/{id}/preflight` — one new read-only endpoint

The acceptance criterion "a send button disabled until every pre-send check
passes" is unimplementable without evaluating the gate *without sending*.
`#0045` puts the gate at two call sites: the send-transition handler (a 409 on
failure) and the worker. Neither can be polled — calling `POST .../send` to
find out whether it would succeed is exactly the thing that must not happen.

**Decision: this issue adds a thin, read-only handler over `#0045`'s existing
`SendStore.GatherPreflight` + `mailing.Preflight`.**

```
GET /admin/campaigns/{id}/preflight        (session + is_admin)
200 {"ok":false,
     "unmet":[{"code":"physical_address_missing","message":"…"}, …],
     "summary":{"subject":"…","from":"…","recipients":482}}
404 unknown campaign
```

- It **calls the same pure function** as the two authoritative call sites, so
  there is still exactly one copy of every requirement. It adds no requirement,
  no override, no bypass — CLAUDE.md §9's "never make the `physical_address`
  check bypassable from the UI" is untouched, because this endpoint cannot
  cause a send.
- `summary` is why the endpoint earns its keep beyond the checks: the three
  facts the operator confirms against in §6 (**subject, from address, recipient
  count**) all come from the server's read of the stored row, not from the
  editor's unsaved buffer. Confirming a destructive action against your own
  textarea is confirming against nothing.
- It writes no audit row — a dry-run read is not an auditable mutation, matching
  `#0044`'s decision for `/audience`.
- Mounted in `adminRoutes` behind a `nil` guard exactly like
  `adminCampaignAudienceH`, so `STORAGE=json` omits it. No devstore work.
- If `#0045`'s implementer has already shipped an equivalent read-only route by
  the time this issue is worked, **consume it and delete this section** rather
  than adding a second.

*Rejected — folding `unmet` into `GET /admin/campaigns/{id}`.* That endpoint is
`#0041`'s and is being implemented concurrently; and it makes every list/detail
read run a dry render and an audience count.

*Rejected — computing the list client-side.* Forbidden by both carried-in
sections, and the exact drift this project keeps paying for.

### 4. Save, preview, and the audience — why the editor autosaves

`POST /admin/campaigns/{id}/preview` (`#0046`) and
`GET /admin/campaigns/{id}/audience` (`#0044`) both read the **stored** campaign
row. A live side-by-side preview of unsaved text is therefore impossible without
changing one of those contracts.

**Decision: autosave the draft, then preview.** The editor PATCHes when the
buffer is dirty and the operator has been idle ~2s, on blur, and on an explicit
"Save draft" button; a successful save triggers the preview refresh and a
preflight refresh. Mode and interest changes save **immediately** (they are
discrete clicks, not typing) and additionally refresh `/audience`, which is what
makes the recipient count "live" per the acceptance criterion.

This means the preview always shows exactly what the worker would render from
the stored row, and a long compose survives a crashed tab.

*Rejected — teaching `#0046`'s preview endpoint to accept an unsaved body.* It
would let the operator preview one thing and send another. That is the single
trap this screen exists to prevent.

*Rejected — a client-side Markdown renderer.* A second renderer that drifts from
`#0042`, a bundle-budget hit against PRD §7.6's 60 KB, and a route by which raw
HTML in the source reaches the DOM unescaped.

**Rendering the returned HTML: a sandboxed iframe, never `{@html}`.** The
preview pane is `<iframe srcdoc={html} sandbox="" referrerpolicy="no-referrer"
title="Campaign preview">`. With no `allow-scripts` and no `allow-same-origin`,
nothing in the rendered email can execute or reach our origin, and the email
template's inline styles cannot collide with the app's. It also happens to be
the technique CLAUDE.md §8 prescribes for checking narrow layouts, since
headless Chromium's ~485 px floor makes `--window-size` misleading. A
plain-text tab beside it shows the text alternative from the same response.
(`#0043`'s template must embed no remote assets; PRD §7.6 budgets zero external
requests and a sandboxed iframe does not block image loads.)

**One interaction to surface, not hide:** this shipped in `#0045` itself (not
`#0041`): `CampaignStore.Update` clears `test_sent_at` to NULL when `subject`
**or** `body_md` changes — **not** on a `preheader` edit, deliberately, since
the preheader never reaches the rendered body a test send delivered. So an
autosave after a subject or body edit legitimately invalidates a prior test
send, and a preheader-only edit does not. The editor
must say so plainly next to the test-send control ("the last test send no
longer matches this content — send another"), driven by `test_sent_at` coming
back `null` and by `no_test_send` reappearing in the unmet list. This is correct
behaviour; the failure mode is it happening silently.

### 5. The unmet-requirements list, and the post-scheduling demotion

#### Presentation

A **"Pre-send checks" panel, always visible in the editor** — not hidden behind
the send button, not a tooltip. Its container element is rendered
**unconditionally** with `role="status" aria-live="polite"`; only its *contents*
are conditional. That is the direct application of the `role="status"` finding
carried from `#0036` to `#0063`: an element inserted into the DOM together with
its text is not reliably announced, so the region must pre-exist and be mutated.

- `unmet === null` (not yet checked): "Checking…".
- `unmet.length === 0`: "All pre-send checks pass." — a sentence about the
  *check*, not about any requirement, so it cannot drift.
- otherwise: an `<ol>` in server order, one `<li>` per entry rendering
  `{message}` **verbatim**, `data-code={code}` for testability, an
  `aria-hidden` `[ !! ]` marker (matching PRD §7.5's `[ OK ]` convention, so
  nothing is conveyed by colour alone), and — when `fixLocation(code)` is
  non-null — a real `<button>` that switches to the relevant subtab.

#### How it updates

Re-fetched after every successful save, after an audience change, after a test
send, on an explicit "Re-check" button, and on entering the editor. **Not
polled on a timer** — the settings it reads can change out of band, and the
Re-check button plus the authoritative 409 on send cover that without a
background request every few seconds. When `POST .../send` returns 409, its
`unmet` body replaces the panel's contents through the *same* `parseUnmet` →
same renderer path. One list, two sources, no second implementation.

#### The demotion

`#0045`'s worker re-checks authoritatively before a campaign leaves
`scheduled`; a campaign that fails is demoted to `draft` with a
`email_campaign.send_refused` audit row (actor NULL, metadata `codes`/`messages`).

**Detection needs no new backend field.** The demotion happens *before* the
start claim, so `started_at` stays NULL, and nothing clears `scheduled_at`.
Therefore:

```
wasDemotedAfterScheduling(c) =
    c.status === 'draft' && c.scheduled_at !== null && c.started_at === null
```

A campaign that was never scheduled has no `scheduled_at`; a cancelled one is
`canceled`, not `draft`; a sent one has `started_at`. The signal is exact
**provided `#0041` does not add an unschedule transition that leaves
`scheduled_at` set** — flagged in §10.

**What the operator sees.** A campaign matching the predicate shows, in the list
row *and* pinned at the top of the editor, a notice:

> This campaign was scheduled for {scheduled_at} but the send worker refused it
> and returned it to draft. The checks below are its current state.

followed by the live pre-send panel — which is the *actionable* answer to "why",
in the overwhelmingly common case (the address is still missing), and which
correctly reads "all checks pass — schedule it again" if someone has since fixed
it. A "View in audit log" button switches to the Audit subtab for the recorded
historical reason.

**The honest gap:** `email_campaign.send_refused` is written with actor NULL, and
`GET /admin/audit` filters only by `user_id` today, so that button cannot
pre-filter to the campaign. The row is visible in the newest-first list, which
is enough here. A `target_type`/`target_id` filter on the audit endpoint would
close it properly and should be **its own issue** — reported to the
orchestrator, not built here.

### 6. The audience panel

Driven by `GET /admin/campaigns/{id}/audience` → `{mode, interest_ids, count,
sample, warnings}`.

- **Count** is the headline, from `describeAudience(preview)`. Its container is
  rendered unconditionally (showing `—` before the first response) so an update
  announces in the live region rather than appearing as freshly-inserted text.
- **Sample** is a `<details>`/`<summary>` collapsed by default, captioned
  `sampleCaption(preview)` ("Showing 20 of 482"). Collapsed by default because
  twenty real subscriber addresses on a screen someone is presenting from is
  needless exposure; `<details>` is keyboard-operable natively with no ARIA.
- **Warnings** render verbatim, each as its own `<li>`, styled advisory
  (`text-notice`) rather than as errors — `#0044` warns rather than rejects when
  interests are attached to `all`/`none_selected`. Never suppressed, never
  reworded. The interest fieldset is additionally *disabled* in those two modes
  (`interestsApplyToMode`) — the disable is the affordance, the server warning is
  the explanation of what the stored rows mean.
- **The empty-interest 409** replaces the count with the server's message
  verbatim (`audienceErrorMessage`), in the same place the number would have
  been, so the operator reads it where they were already looking. The same
  condition independently appears in the pre-send panel as `audience_invalid`
  with the server's text. Two placements, one source, zero client copy.
- **Staleness:** each request carries `audienceRequestKey`; a response whose key
  no longer matches the current selection is dropped. A wrong count on this
  screen is a wrong number typed into a confirmation.

Interests are real `<input type="checkbox">` in a `<fieldset>` with a
`<legend>`, per PRD §7.5 and the existing `SubscribeForm.svelte`. Modes are a
radio group in their own `<fieldset>`.

### 7. The send confirmation, and cancel

#### The Send control in the editor

Shown only when `canSendCampaign(status)`. It uses **`aria-disabled="true"`
rather than `disabled`** when `sendGuardState().kind !== 'ready'`, so it stays
focusable: activating it in that state does not send — it moves focus to the
pre-send panel. A screen-reader user who tabs to a `disabled` button is told
nothing; the issue's own Notes say an operator staring at a greyed-out button
with no reason will work around it or give up. `aria-describedby` also points
the button at the pre-send panel. Variant is `primary`, not `danger` — this is
the goal of the screen, and dressing it as destructive is a dark pattern in the
obstruct direction.

#### The dialog

`role="dialog" aria-modal="true"`, following the existing modal markup in
`Admin.svelte` (backdrop, Escape to close, `stopPropagation` on the panel). It
states, in this order, **from `/preflight`'s `summary` — the server's read of the
stored row, not the editor buffer**:

1. the **subject line**, verbatim as it will be sent;
2. the **from address** (and from-name) the message will carry;
3. the **recipient count**, set large;
4. one plain sentence: *Mail cannot be unsent.*
5. the typed confirmation: `<label>Type {count} to confirm</label>` with
   `<input type="text" inputmode="numeric">`. **Not `type="number"`** — the
   spinner arrows let an operator reach the value without reading it, which is
   precisely the friction being softened. `normalizeCountInput` accepts
   thousands separators so `1,234` is not a trap.
6. "Send now" (`variant="danger"` — this *is* the irreversible moment) and
   "Cancel" as a real `<button>` of equal visual weight, never a muted link.

**No dark patterns, in either direction.** The typed count is the only friction:
no countdown, no second "are you sure", no chained dialogs, no pre-ticked
extras, and no obstruction of a legitimate send. Cancel is as easy to hit as
Send.

#### Double-submit, three layers

1. `inFlight` → the "Send now" button takes a real `disabled` and its label
   becomes "Sending…". (Real `disabled` here, unlike the gate above: there is
   nothing left to explain, and a focusable disabled control invites a second
   Enter.)
2. the dialog is a `<form onsubmit>` whose handler returns immediately when
   `inFlight` — a pointer-level guard alone does not cover the Enter key.
3. on success the dialog closes and the campaign leaves `draft`, so
   `canSendCampaign(status)` is false and the control is gone. On 409 the dialog
   stays open, renders the returned `unmet` list inside itself through the same
   renderer, and **preserves the typed count**.

No client-generated idempotency key: `#0041` validates status transitions
server-side and a second `draft → scheduled` is already a 409.

The POST body is `{"confirm_count": N}`. **The server must re-verify it** — a
typed confirmation enforced only in the browser is theatre (§10).

#### Cancel

Shown when `canCancelCampaign(status)` (`scheduled | sending`), calling
`POST .../cancel`. Its own small confirm dialog, with **no typed
confirmation** — cancel is the safe direction and friction there is itself a
dark pattern. Copy comes from `cancelCopy(status)`:

- `scheduled`: nothing has been sent yet; cancelling stops the send before it
  starts.
- `sending`: **messages already sent cannot be recalled**; cancelling stops the
  worker from sending to anyone not already mailed.

The `sending` copy deliberately carries **no number** — the remaining count is
`#0048`'s progress stream, and a stale number in this sentence would be worse
than none. `#0048` can add it.

### 8. Accessibility

`#0063` audits this; these are the commitments it will check.

- **Focus across the multi-step flow.** Entering the editor moves focus to its
  `<h2 tabindex="-1">`; returning to the list focuses the row control just left;
  opening the send dialog focuses the **dialog container** (`tabindex="-1"`),
  not the input, so the subject / from / count / "mail cannot be unsent" are
  read *before* the operator can type; closing it (Escape or Cancel) returns
  focus to the Send button. Same `tick()` + `.focus()` shape `#0036` used.
- **Live regions, and the `#0036` → `#0063` finding.** Every async region — the
  pre-send panel, the audience count, the send result — is rendered
  unconditionally from first paint with `role="status" aria-live="polite"`, and
  only its children change. Nothing is inserted together with its text.
- **Deliberately not announced:** the autosave indicator ("Saved 10:42") is a
  visual affordance with `aria-live="off"`; announcing a routine autosave every
  couple of seconds trains a user to ignore the region. Save *failures*
  announce via `role="alert"`.
- **Real controls.** Every action is a `<button>`; the subtab matches the six
  existing ones; the sample list is `<details>`/`<summary>`; interests are real
  checkboxes in a `<fieldset>`/`<legend>`; modes are a radio group.
- **The Markdown editor is a plain `<textarea>`** in the mono family. No
  CodeMirror, no rich-text widget: an external dependency against PRD §7.6's
  60 KB budget and PRD's "no runtime dependencies beyond Svelte", and every such
  editor is an accessibility liability. **Tab must move focus out of the
  textarea** — do not trap it to insert a literal tab.
- **Focus rings use `--accent`, never `--border-strong`** (CLAUDE.md §8; the
  latter measures under 3:1 against the page in both themes).
- No new colour tokens: reuse `.text-error` / `.text-muted` / `.text-notice` so
  `#0063`'s contrast pass already covers them. No information by colour alone —
  the unmet list's `aria-hidden` marker carries the visual weight and the text
  carries the meaning.
- **Narrow layout must be checked in a sized `<iframe>`**, not with
  `--window-size` (CLAUDE.md §8: headless Chromium's ~485 px floor silently
  clips a wider render and looks exactly like an overflow bug). The subtab bar's
  CSS comment currently reads "reduce padding so 4 fit on 2 rows" — a seventh
  subtab needs that re-checked.

### 12. What the neighbouring issues need to know

Recorded for the orchestrator to carry; **this plan edits no other issue file.**

- **`#0041`** — (a) `POST /admin/campaigns/{id}/send` will receive
  `{"confirm_count": N}` and **must re-verify it server-side** against a freshly
  computed count, 409ing on a mismatch; a typed confirmation enforced only in
  the browser is theatre. (b) That endpoint returns two different 409s — the
  gate's `{"unmet":[…]}` and an illegal-transition error — and they must be
  **distinguishable by body shape**, or the screen cannot tell "fix these five
  things" from "someone already sent this". (c) The campaign list and detail
  responses must include `status`, `scheduled_at`, `started_at` and
  `test_sent_at`; the first three are what detect a post-scheduling demotion
  (§5) and the last drives the test-send state. (d) **If an unschedule
  transition (`scheduled → draft`) is ever added, it must clear
  `scheduled_at`** — otherwise this screen reports an operator's own unschedule
  as a worker refusal. (e) If `#0041` clears `test_sent_at` on a content edit
  (per `#0045` §13), say so in the response so the editor can surface it rather
  than have it happen silently under an autosave.
- **`#0046`** — `POST .../preview` renders the **stored** row, and this screen
  relies on that: it autosaves and then previews, so the preview always equals
  what would be sent. **Do not add an unsaved-body override** — it would let an
  operator preview one thing and send another. The response should carry both
  the HTML and the text part; the HTML is rendered in a `sandbox=""` iframe, so
  it must be self-contained with no remote assets. **Amended 2026-08-21 by

  default; its copy should say it sends to the signed-in admin's own address,
  and should state that the unsubscribe link is real and tied to a dedicated
  test subscriber (`#0046`'s Notes), so an admin knows clicking it is safe.
  Both routes are `POST`, as this plan already assumed.
- **`#0048`** — the seam is a named, empty progress region inside
  `CampaignEditor.svelte`; `#0047` renders campaign status only and does

## Root cause

Not a bug fix — new feature work. Before this issue, `#0041`/`#0044`/`#0045`/
`#0046` had built the entire campaign backend (CRUD, the state machine, the
audience predicate, the send worker and its pre-send gate, preview and test
send) but there was no admin UI at all to drive any of it: an operator had
no way to author a campaign, see a live recipient count, know why the send
button should be disabled, or confirm an irreversible send. There was also
no read-only way to evaluate `#0045`'s `Preflight` gate without attempting an
actual `POST .../send` — which is exactly the thing that must not happen
just to populate a "why can't I send" panel.

## Fix

**Backend — one new read-only endpoint, `GET /admin/campaigns/{id}/preflight`**
(`internal/handlers/admin_campaign_preflight.go`). `AdminCampaignPreflightHandler`
calls the exact same pair of functions the two authoritative call sites use —
`SendStore.GatherPreflight` then `mailing.Preflight` — so there remains
exactly one copy of every requirement; this handler adds no requirement, no
override, and cannot cause a send (CLAUDE.md §9). It returns
`{"ok", "unmet":[{code,message}], "summary":{"subject","from","recipients"}}`;
`summary` is the send-confirmation dialog's anchor — read from the stored
row via the same `GatherPreflight` call, never from the editor's buffer. It
writes no audit row, matching `#0044`'s decision for `GET .../audience`.
Wired into `cmd/opencircuit/main.go`'s `adminRoutes`/`mountAndServe` behind
the same nil guard `sendStore`'s own construction already uses
(`MAILER_NOOP=true` or `STORAGE=json` → nil, route omitted) — which ripples
through all eight other `mountAndServe` call sites across the wiring test
files (each passes `nil` with a `not exercised` comment, following `#0041`'s
established precedent) and `admin_wiring_test.go`'s real-route table, where a
genuine `*mailing.SendStore`-backed handler now exercises the new route so
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` proves its guard too.

**Frontend — four pure `lib/` modules, three thin Svelte components,** per
the plan's §2 rule that no comparison operator, `.trim()`, `.length >`,
status literal, or `||` fallback chain may appear in a `.svelte` template
(`#0094`: nothing in a component is covered by a test):

- `web/src/lib/campaigns.ts` — status/mode vocabulary, `canEditCampaign`/
  `canSendCampaign`/`canCancelCampaign`, `interestsApplyToMode`,
  `validateCampaignDraft` (the CRUD-save gate only — deliberately blind to
  the physical address, a test send, the audience count, or rendering),
  `subjectLengthAdvice`/`preheaderLengthAdvice` (guidance, never a block),
  `wasDemotedAfterScheduling`/`demotionExplanation`, `cancelCopy`.
- `web/src/lib/preflight.ts` — `parseUnmet` (and `parseUnmetFromError`, a
  convenience wrapper over an `ApiError.body`), `isPreflightBlocked`,
  `fixLocation`. No code→message table anywhere in this module — an unknown
  code survives with its own server-supplied message; a blank/absent one
  falls back to the raw code, never invented or dropped.
- `web/src/lib/audience.ts` — `audienceRequestKey`/`isStaleAudience` (drops a
  superseded `/audience` response), `describeAudience`, `sampleIsTruncated`/
  `sampleCaption` (the literal sample cap `20` appears nowhere in this
  module — a grep-style test proves it), `audienceErrorMessage`.
- `web/src/lib/sendConfirm.ts` — `normalizeCountInput` (accepts `,`/space
  thousands separators, rejects decimals/negatives/trailing junk),
  `confirmMatches` (strict), `confirmHint`, and `sendGuardState` — the single
  source of truth for whether mail can go out from this screen, returning a
  `{kind: 'unavailable'|'blocked'|'empty-audience'|'needs-confirm'|'ready'|
  'sending'}` discriminated union.
- `web/src/views/admin/Campaigns.svelte` — the subtab root: loads on its own
  `onMount` (not `Admin.svelte`'s), the list/create form, and the
  master/detail swap via `{#if hasSelection}` + `{#key selectedCampaignId}`
  so a fresh `CampaignEditor` instance mounts per campaign.
- `web/src/views/admin/CampaignEditor.svelte` — fields (name/subject/
  preheader/body, all plain inputs and a `<textarea>` — no CodeMirror or rich
  text), autosave (idle ~2s / blur / explicit "Save draft"; mode and interest
  changes save immediately and refresh `/audience`), the sandboxed preview
  iframe (`sandbox=""`, `referrerpolicy="no-referrer"`, never `{@html}`), the
  audience panel (radio group + checkbox fieldset, disabled together when the
  mode doesn't use interests), the always-rendered "Pre-send checks" `role=
  "status"` panel (unmet list in server order, verbatim messages, a
  `fixLocation`-driven "Go to Settings" affordance), the test-send control,
  the demoted-campaign banner (`wasDemotedAfterScheduling`), and the Send/
  Cancel action row. The Send button uses `aria-disabled` (never `disabled`)
  driven by `sendGuardState`, so it stays focusable and moving focus to the
  pre-send panel is possible when blocked.
- `web/src/views/admin/CampaignSendDialog.svelte` — the typed-count
  confirmation: subject/from/recipients from the server's `summary`, "Mail
  cannot be unsent," a text `inputmode="numeric"` field (never `type=
  "number"`), and a real `disabled` (not `aria-disabled`) "Send now" only
  while a request is genuinely in flight. Focuses the dialog **container**
  on open (not the input) so the summary is announced before the operator
  can type — the same `tick()` + `.focus()` shape `#0036` used in
  `Unsubscribe.svelte`. On a 409 the dialog stays open (same component
  instance) and re-renders the returned `unmet` list through the identical
  renderer, preserving the typed count.

**`Admin.svelte` changes are the four the plan named:** the `Section` union
gained `'campaigns'`, one `<button class="subtab">` appended after
Suppressions, one `{#if section === 'campaigns'}<Campaigns .../>{/if}`
branch, and one import — no `loadCampaigns()` added to `onMount`, since the
new section loads on its own mount, unlike the six existing eager sections.

**Editor-level send gate, a deliberate reading of the plan's `aria-disabled`
rule.** `sendGuardState` needs a `confirmRaw` to reach `'ready'`, but the
typed-count field lives inside `CampaignSendDialog`, which doesn't exist
until the operator clicks Send. `CampaignEditor` resolves this by evaluating
`sendGuardState` with `confirmRaw` pinned to the live audience count's own
string form — i.e. "pre-confirmed" — which answers "is everything besides
the operator's own confirmation ready" and is what the Send button's
`aria-disabled` and click-vs-focus-panel branch key off. The REAL
confirmation is enforced only inside the dialog, which calls
`sendGuardState`/`confirmMatches` again against what the operator actually
typed. Both call sites route through the identical `lib/sendConfirm.ts`
functions; nothing is reimplemented.

**Interest checkboxes use `GET /admin/interests` (admin), not the public
`GET /api/interests`.** The public endpoint's `PublicInterest` type
deliberately omits numeric `id` (its own doc comment explains why — a public
form only ever needs slugs); campaign targeting needs the taxonomy's real
`interest_ids`, so `CampaignEditor` imports `listInterests`/`Interest` from
`lib/api.ts`/`lib/types.ts` instead.

## Gotchas

- **The public interests endpoint has no numeric id, by design** (its own
  doc comment: a public signup form only needs slugs). Campaign interest
  targeting needs real `interest_ids`, so the editor uses the *admin*
  `GET /admin/interests` instead of the public one every other subscriber-
  facing form in this codebase uses — worth remembering if a future screen
  reaches for "the interests list" and reflexively imports the public
  helper.
- **`vite build` embeds hashed asset filenames** (`index-B25lZOUQ.css` etc.)
  that differ every build; only `web/dist/index.html` is tracked by git, so
  restoring it after a verification build is sufficient — the `assets/`
  directory is gitignored and was restored from the same backup purely for
  tidiness, not because git would have flagged it.
- **`?raw` Vite imports avoid a `@types/node` dependency.** This SPA's
  `tsconfig.json` deliberately excludes Node types (`types: ["svelte",
  "vite/client"]`); a grep-style test that needs a module's own source as a
  string should use `import x from './mod.ts?raw'` (declared by
  `vite/client.d.ts`), not `node:fs`/`node:url`.
- **A pre-existing test-isolation gap, not fixed beyond this issue's own
  contribution:** several tests across `internal/handlers` seed an `active`
  subscriber via `seedSubscriberRow` with no cleanup, and at least one test
  (`TestAdminCampaigns_Send_DraftToScheduled`) implicitly assumes zero
  active subscribers exist anywhere in the shared test database. This
  issue's own two new tests were fixed to clean up after themselves, but the
  underlying fragility (any future test that seeds an uncleaned active
  subscriber can intermittently break that one, depending on file-sort
  test-execution order) remains. Worth its own issue if it recurs.

      `json:"scheduled_at,omitempty"` on `*string` fields (matching
      `subscriberView`'s existing precedent), so a NULL column is omitted from
      the JSON entirely. §5's demotion predicate as planned —

      ```
      c.status === 'draft' && c.scheduled_at !== null && c.started_at === null
      ```

      — is wrong on **both** halves against the real payload: `undefined !==
      null` is `true`, so a never-scheduled draft matches, and `undefined ===
      null` is `false`, so a genuinely demoted campaign does not. Use loose
      `!= null` / `== null`, or test key presence. Whichever form is chosen,
      the unit test §9 calls for should feed it a campaign object with the keys
      **missing**, not set to `null` — a fixture that spells out `null`
      passes while the real API response fails.

      `000017` has no such column; it arrives with `#0045`'s `000018` and
      `#0041` deliberately did not add it. Do not build the test-send state
      against a field that is currently always absent — take it from `#0046`
      once the column exists.

      **Amended 2026-08-21 by `#0046`'s third phase-3 review: this has now
      landed.** `#0046` (`5ec8774`) added `campaignView.TestSentAt`
      (`internal/handlers/admin_campaigns.go`), so every campaign response
      carries `test_sent_at`. It is tagged `json:"test_sent_at,omitempty"`,
      which means the key is **absent** when the campaign has never been
      test-sent, not `null` — the same key-presence trap the item above
      describes. Use `!= null` / `== null` or a key-presence check, and write

      `null`. `CampaignStore.MarkTestSent` is the sole writer, and
      `CampaignStore.Update` clears the column on a `subject`/`body_md` edit
      (not on a `preheader`-only edit), so the editor's autosave can move this
      field back to absent underneath the operator.
