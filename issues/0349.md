## Description

`#0337`'s guard establishes a **type-level** property — does anything in
`internal/seo` structurally satisfy an `Invalidate()`-only interface — by
scanning **method declarations** with `go/ast`. Those are not the same thing.
The scan reads declarations; the property is about method sets, and promotion
and instantiation are exactly where the two diverge.

Two reviews have now found constructs where the substitution is unsound, and
each was closed by adding another AST rule:

| Construct | `go/types` | AST guard |
|---|---|---|
| value receiver `func (s Sitemap) Invalidate()` | satisfier | missed (first bounce) |
| embedded struct field `struct{ *Site; … }` | satisfier | missed (second bounce) |
| embedded interface field `struct{ cacheInvalidator; … }` | satisfier | missed (second bounce) |
| generic receiver `func (f *FeedCache[T]) Invalidate()` | satisfier | missed (second bounce) |

The generic case shows the shape well: the receiver parses as
`StarExpr{X: IndexExpr{X: Ident}}`, so unwrapping only the star leaves an
`*ast.IndexExpr`, the `*ast.Ident` assertion fails, and the declaration is
skipped — the type never enters the scan's map at all. Two type parameters
(`IndexListExpr`) behave identically.

This is the shape CLAUDE.md §8 warns about directly: *"adding a seventh in-file
check buys a seventh bounce."* Each fix closes what it was shown and the next
review finds the adjacent construct.

**The sound oracle is `go/types.Implements` over the package's full named-type
set** — which is precisely what both reviews used as ground truth to *find*
these holes. The reason it is not in the guard is cost:
`importer.ForCompiler(fset, "source", nil)` parses the whole dependency tree
and takes ~11s, measured.

## Acceptance criteria

1. Measure whether `golang.org/x/tools/go/packages` with `NeedTypes`
   (export-data backed, typically ~1s for a single package) is fast enough to
   replace the AST scan outright. Record the measured number, not an estimate.
2. **If it is**, replace the scan with a `go/types.Implements` oracle over
   every named type in the package, and DELETE the receiver-form, generic, and
   embedding special cases along with the embedding tripwire and its
   `embeddingReviewed` allowlist. The point is to remove special cases, not to
   add a fifth one — a `go/types` oracle that keeps the AST rules beside it has
   bought nothing.
3. **If it is not**, record the measurement in the guard's doc comment with the
   date and the method, so the next reviewer does not re-open a settled
   question. State plainly that the guard is a heuristic and name the
   constructs it cannot see.
4. Either way, re-run every mutation both reviews used — re-export
   `Sitemap.invalidate`; a new type with a pointer-receiver `Invalidate()`; a
   value receiver; an embedded struct field; an embedded interface field; a
   generic receiver; and a method declared in a different file of the package —
   and record which fail. A `go/types` oracle must fail on all seven.
5. Mutations run in a throwaway worktree, never the shared tree (§8b), each
   restoration hash-verified.
6. Note that adding a `golang.org/x/tools` dependency is a real cost on a
   `t4g.nano` where `go build` is already the memory-hungry step of a deploy
   (§7). If the dependency is not already in `go.mod`, weigh that explicitly
   and say so — this is a test-only guard, and a test-only dependency that
   slows every deploy may not be worth it.
7. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout (§8).

## Added by `#0337`'s third review, 2026-08-31

That review closed `#0337` and, in doing so, measured two things this issue must
carry. It ran eleven mutations of its own beyond the seven already known and
could not break the AST scan's *soundness* — so this issue is **not** motivated
by the scan being wrong. It is motivated by what the soundness costs.

**1. The `embeddingReviewed` allowlist is keyed on a type name and does not
stay true.** An entry records *that* a type was hand-checked, not *what* was
checked about it. The review proved the consequence: allowlist a type while it
embeds a non-satisfier, then let any later unrelated edit swap the embedded
type for `*Site`, and `go/types` reports a new satisfier of both seams while
the guard reports `ok` — `#0337`'s exact defect reopened through the escape
hatch built to contain it, **with no edit to the guard file at all**. Latent
only today, since the allowlist ships empty.

A `go/types.Implements` oracle removes the allowlist entirely. **State that as
an explicit goal**: do not port the allowlist forward. The fix within the AST
approach would be a fifth in-file check, which §8 says buys a fifth bounce —
that is the reason this work was handed here rather than done there.

**2. The AST scan is build-tag-blind in the SAFE direction, and a `go/types`
oracle is not.** A `//go:build linux` file declaring `func (f *FeedCache)
Invalidate()` is caught by the current scan, because an AST walk reads every
file regardless of tags. It is **invisible** to a `go/types` check run on a
developer's mac. Production is linux/arm64 (§7), so that is a real satisfier
the naive replacement would miss — a regression, not an improvement.

So the replacement must either type-check under the production
`GOOS`/`GOARCH`, or knowingly give this up and record the loss. Decide it
deliberately; do not discover it later.

**3. An undocumented coupling worth recording either way.**
`structTypesWithEmbeddedFields` has no floor of its own — empty is its correct
answer today — and is covered only by `invalidateOnlyMethodReceivers`' floor
over the same enumeration. That coupling is load-bearing. If the AST scan
survives in any form, document it; if it is replaced, it goes away with it.

### Why the AST approach is being retired despite being sound

The review's own framing, worth preserving because it is not the obvious one:
a Go named type acquires a method in exactly two ways — a declaration whose
receiver base type is that type, or promotion from an embedded field. The guard
now covers the first exhaustively across every receiver spelling and **refuses
to answer** on the second. There is no third way in, which is why eleven
mutations could not break it.

But soundness bought with refuse-to-answer means **the first legitimate
embedded field in `internal/seo` is a hard failure**, clearable only through
the name-keyed allowlist that item 1 shows does not stay true. That is the
cost this issue exists to remove — the successor to a working guard, not a
bounce of a broken one.


## A trap for this issue's implementer specifically

`#0346`'s reviewer ran a `go/types` probe over this repo with
`packages.Load` and `GOFLAGS=-mod=mod`. `go list` promoted
`github.com/aws/smithy-go` from `// indirect` to direct in `go.mod` — a
legitimate tidy, since `internal/mailing/worker.go` does import it directly,
but an **unrequested mutation of a shared file** while other agents were live
in the checkout. It was caught from `git status` before committing and restored
with `git show HEAD:go.mod > go.mod` (§8b's pattern, no `checkout`/`restore`).

This issue's whole point is pointing a type-checking loader at this repo, so it
will hit the same thing. **Run any loader with `GOFLAGS=-mod=readonly`**, and
check `git status -- go.mod go.sum` before committing. Better still, run the
probe against a `git archive` export outside the checkout, which is what that
reviewer did for its actual measurements.
