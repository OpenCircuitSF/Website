## Description

`#0337`'s guard establishes a **type-level** property — does anything in
`internal/seo` structurally satisfy an `Invalidate()`-only interface — by
scanning **method declarations** with `go/ast`. Those are not the same thing.
The scan reads declarations; the property is about method sets, and promotion
and instantiation are exactly where the two diverge.

Two reviews have now found constructs where the substitution is unsound, and
each was closed by adding another AST rule:

| Construct | `go/types` | AST guard |
|---|---|---|
| value receiver `func (s Sitemap) Invalidate()` | satisfier | missed (first bounce) |
| embedded struct field `struct{ *Site; … }` | satisfier | missed (second bounce) |
| embedded interface field `struct{ cacheInvalidator; … }` | satisfier | missed (second bounce) |
| generic receiver `func (f *FeedCache[T]) Invalidate()` | satisfier | missed (second bounce) |

The generic case shows the shape well: the receiver parses as
`StarExpr{X: IndexExpr{X: Ident}}`, so unwrapping only the star leaves an
`*ast.IndexExpr`, the `*ast.Ident` assertion fails, and the declaration is
skipped — the type never enters the scan's map at all. Two type parameters
(`IndexListExpr`) behave identically.

This is the shape CLAUDE.md §8 warns about directly: *"adding a seventh in-file
check buys a seventh bounce."* Each fix closes what it was shown and the next
review finds the adjacent construct.

**The sound oracle is `go/types.Implements` over the package's full named-type
set** — which is precisely what both reviews used as ground truth to *find*
these holes. The reason it is not in the guard is cost:
`importer.ForCompiler(fset, "source", nil)` parses the whole dependency tree
and takes ~11s, measured.

## Acceptance criteria

   (export-data backed, typically ~1s for a single package) is fast enough to
   replace the AST scan outright. Record the measured number, not an estimate.
2. **If it is**, replace the scan with a `go/types.Implements` oracle over
   every named type in the package, and DELETE the receiver-form, generic, and
   embedding special cases along with the embedding tripwire and its
   `embeddingReviewed` allowlist. The point is to remove special cases, not to
   add a fifth one — a `go/types` oracle that keeps the AST rules beside it has
   bought nothing.
3. **If it is not**, record the measurement in the guard's doc comment with the
   date and the method, so the next reviewer does not re-open a settled
   question. State plainly that the guard is a heuristic and name the
   constructs it cannot see.
4. Either way, re-run every mutation both reviews used — re-export
   `Sitemap.invalidate`; a new type with a pointer-receiver `Invalidate()`; a
   value receiver; an embedded struct field; an embedded interface field; a
   generic receiver; and a method declared in a different file of the package —
   and record which fail. A `go/types` oracle must fail on all seven.
5. Mutations run in a throwaway worktree, never the shared tree (§8b), each
   restoration hash-verified.
6. Note that adding a `golang.org/x/tools` dependency is a real cost on a
   `t4g.nano` where `go build` is already the memory-hungry step of a deploy
   (§7). If the dependency is not already in `go.mod`, weigh that explicitly
   and say so — this is a test-only guard, and a test-only dependency that
   slows every deploy may not be worth it.
7. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout (§8).

## Added by `#0337`'s third review, 2026-08-31

That review closed `#0337` and, in doing so, measured two things this issue must
carry. It ran eleven mutations of its own beyond the seven already known and
could not break the AST scan's *soundness* — so this issue is **not** motivated
by the scan being wrong. It is motivated by what the soundness costs.

**1. The `embeddingReviewed` allowlist is keyed on a type name and does not
stay true.** An entry records *that* a type was hand-checked, not *what* was
checked about it. The review proved the consequence: allowlist a type while it
embeds a non-satisfier, then let any later unrelated edit swap the embedded
type for `*Site`, and `go/types` reports a new satisfier of both seams while
the guard reports `ok` — `#0337`'s exact defect reopened through the escape
hatch built to contain it, **with no edit to the guard file at all**. Latent
only today, since the allowlist ships empty.

A `go/types.Implements` oracle removes the allowlist entirely. **State that as
an explicit goal**: do not port the allowlist forward. The fix within the AST
approach would be a fifth in-file check, which §8 says buys a fifth bounce —
that is the reason this work was handed here rather than done there.

**2. The AST scan is build-tag-blind in the SAFE direction, and a `go/types`
oracle is not.** A `//go:build linux` file declaring `func (f *FeedCache)
Invalidate()` is caught by the current scan, because an AST walk reads every
file regardless of tags. It is **invisible** to a `go/types` check run on a
developer's mac. Production is linux/arm64 (§7), so that is a real satisfier
the naive replacement would miss — a regression, not an improvement.

So the replacement must either type-check under the production
`GOOS`/`GOARCH`, or knowingly give this up and record the loss. Decide it
deliberately; do not discover it later.

**3. An undocumented coupling worth recording either way.**
`structTypesWithEmbeddedFields` has no floor of its own — empty is its correct
answer today — and is covered only by `invalidateOnlyMethodReceivers`' floor
over the same enumeration. That coupling is load-bearing. If the AST scan
survives in any form, document it; if it is replaced, it goes away with it.

### Why the AST approach is being retired despite being sound

The review's own framing, worth preserving because it is not the obvious one:
a Go named type acquires a method in exactly two ways — a declaration whose
receiver base type is that type, or promotion from an embedded field. The guard
now covers the first exhaustively across every receiver spelling and **refuses
to answer** on the second. There is no third way in, which is why eleven
mutations could not break it.

But soundness bought with refuse-to-answer means **the first legitimate
embedded field in `internal/seo` is a hard failure**, clearable only through
the name-keyed allowlist that item 1 shows does not stay true. That is the
cost this issue exists to remove — the successor to a working guard, not a
bounce of a broken one.

### 1. The dependency's deploy cost, measured: zero

This was the decisive question and the answer is better than the implementer
claimed. `scripts/deploy.sh` line 92 runs exactly one Go command:
`go build -o "$TMPBIN" ./cmd/opencircuit`. Run that on a **completely empty
`GOMODCACHE`** against both trees:

| | module cache | `cache/download` | wall | `golang.org/x/tools` fetched |
|---|---|---|---|---|
| `4c649f6^` (before) | 90,896 KB | 16,588 KB | 6 s | no download dir at all |
| `HEAD` (after) | 90,896 KB | 16,588 KB | 7 s | no download dir at all |

Byte-identical. Not even the `.mod` file is fetched — with a complete
`require` list the go command never reads a dependency's own `go.mod`, so
module-graph pruning makes the addition free rather than cheap. `go build
./...` behaves the same, and `go list -deps ./...` contains zero
`golang.org/x/tools` packages. The only command that pulls it is
`go mod download` (+15 MB: 11,404 KB of `x/tools` source, 880 KB of `x/mod`,
2,852 KB of zips), and nothing in the deploy path runs that. So criterion 6's
`t4g.nano` concern (§ 7) does not materialise: the memory-hungry step of a
deploy is unchanged, and criterion 2's branch was the right one to take.

`go mod tidy` in an export produces exactly one delta — the pre-existing
`github.com/aws/smithy-go` promotion `#0346`'s reviewer hit — leaving
`golang.org/x/tools v0.44.0` direct and `golang.org/x/mod v0.35.0 // indirect`
precisely where the implementer placed them by hand. `go mod verify`: all
modules verified. `git status -- go.mod go.sum` clean before and after every
run.

### 2. Timing, warm and cold

Isolated the loader from the test-binary build by compiling a probe once and
then running it against a purpose-built empty `GOCACHE`:

| | |
|---|---|
| loader, **cold** `GOCACHE` | **1,299 ms** (cache grew to 6.8 MB) |
| loader, warm | **562 / 569 / 574 ms** |
| `go test -run TestInvalidatorSatisfierSet`, cold `GOCACHE` | 7.5 s wall, test itself 0.66 s |
| `go test -run TestInvalidatorSatisfierSet`, warm | 1.3 s wall, test itself 0.50–0.53 s |

The implementer's ~500–600 ms reproduces exactly, and there is no cold cliff:
the feared "half a second warm, ten seconds cold" does not happen.

**Why** it does not is worth recording, because the doc comment gets it wrong.
The loader is **not** export-data backed in this configuration. An
export-data-backed load of the same package — `GOOS=linux GOARCH=arm64
go list -export -deps ./internal/seo` on a cold cache — costs **5,406 ms and
240 MB of build cache**. The guard costs 1.3 s and 6.8 MB, i.e. it
source-type-checks the dependency tree and never cross-compiles it. The
performance claim in the doc comment is right; its stated mechanism is not.
The phrase was inherited from this issue's own criterion 1, so it is not
something the implementation introduced.

### 3. The uninstantiated-generic claim: verified constructively

Built a synthetic package and asked `go/types` directly rather than reasoning
about it. `types.Implements` on an **uninstantiated** generic `*types.Named`
and on `types.NewPointer` of one returns correct answers and does not panic —
no `types.Instantiate` needed, as claimed:

| declaration | `Implements(named)` | `Implements(*named)` |
|---|---|---|
| `type G1[T any]` + `func (g *G1[T]) Invalidate()` | false | **true** |
| `type G2[K comparable, V any]` + `func (g *G2[K,V]) Invalidate()` | false | **true** |
| `type G3[T any]` + `func (g G3[T]) Invalidate()` (value receiver) | true | **true** |
| `struct{ *PtrRec }`, `struct{ PtrRec }`, `struct{ Inv }`, `struct{ *G1[int] }`, two-level embedding | — | **true** |
| `type NamedSlice []int` + value-receiver method (non-struct underlying) | true | **true** |
| `func (w *WrongSig) Invalidate(x int)` | false | false |

So the single `types.Implements(types.NewPointer(named), …)` call really does
subsume every receiver spelling and every promotion path, and checking only the
pointer form is sufficient because `*T`'s method set is a superset of `T`'s.

### 5. The build-tag trade-off: correct, and adequately recorded

X1 and X10 prove the `GOOS=linux, GOARCH=arm64` pinning is real rather than
aspirational, and X13 proves it reaches dependencies too. The deliberate
omission of a second host-target `Load` is the right call: production is
linux/arm64 only (§ 7), so a darwin-only satisfier can never be passed into
either seam by anything that ships, and the second `Load` would cost another
~565 ms on every `go test`. It is already recorded in the doc comment
(the parenthetical at the end of the build-tag paragraph), so no further
action is needed.

One genuine bonus, unremarked by the implementer: this guard is now the only
thing in the repo that type-checks anything for linux/arm64, so a linux-only
compile error anywhere in `internal/seo` or its own declarations fails a
darwin `go test` run that would otherwise have shipped a broken deploy (X3/X4).

### 6. What was deleted — subsumed, with one exception

`#0337`'s third review's structural argument holds: a named type acquires a
method by declaration or by promotion, and the new oracle covers both (M1–M7,
X5, X13). Value receivers: M3. Both generic arities: M6/M7. Promotion through
embedded struct, embedded interface, embedded instantiated generic, and two
levels of nesting: M4, M5, and the probe table in § 3. `embeddingReviewed`'s
name-keyed defect is closed by deletion rather than hardening, as the issue
required. Both fail-closed floors survive and a third was added
(`len(names) == 0`, `concreteTypesChecked == 0`, `len(got) == 0`).

**The exception, and the one thing this review recommends filing.** The
replacement is not a strict superset of what it replaced. A package-scope
**alias to a type literal** — `type FeedCache = struct{ *Site; cached []byte }`
— is a genuine satisfier: `var _ interface{ Invalidate() } = FeedCache{}`
compiles. Under `gotypesalias=1` (the default) `scope.Lookup(name).Type()`
returns `*types.Alias`, not `*types.Named`, so the guard's type assertion skips
it silently and reports `ok`. The **old** AST guard caught this same mutation —
its `structTypesWithEmbeddedFields` tripwire inspects any `*ast.TypeSpec` whose
`Type` is an `*ast.StructType`, alias or not — verified by running the old
guard file against the identical mutation, where it fails naming `FeedCache`.

This is not a defect against any of `#0349`'s criteria, which say "every
**named** type in the package", and the construct is exotic. But it is a
measured loss of coverage relative to the guard being retired, of exactly the
class each `#0337` round turned up, so it is handed forward rather than left
implicit. It is reported to the orchestrator for filing, with the remedy, not
bounced — the same disposition `#0346`'s review chose for `#0350`/`#0351`.
