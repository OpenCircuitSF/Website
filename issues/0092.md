## Description

`#0089` replaced a `HasPrefix` fence check with a `leadingRunLength` one and closed
the two drift forms it was filed for. Its review then probed ten further fence shapes
and found **two more residuals**. Neither is a regression — the old `HasPrefix` code
behaved identically — but both are the same drift mode `#0089` targeted: a line that
CommonMark does *not* treat as a fence closer is treated as one here, so the parser
resynchronises early and a table row after it slips past the guard unnoticed.

## The two forms

1. **A closer indented four or more spaces still closes the fence.** The check runs
   on `trimmed`, which has already had all leading whitespace stripped. CommonMark
   caps a closing fence at three spaces of indentation; at four it is indented code
   inside the block. Probe yields 1 row, want 0.
2. **A closer with trailing text still closes the fence.** ` ``` nope ` has a leading
   run of three backticks and so satisfies `leadingRunLength(trimmed, fenceChar) >= fenceLen`.
   CommonMark permits only whitespace after a closing fence. Probe yields 1 row, want 0.

## Acceptance criteria

- [x] A closing fence indented 4+ spaces is not treated as a closer
- [x] A closing fence followed by non-whitespace text is not treated as a closer
- [x] Both forms added as table-driven cases to the existing `cases` slice, each
      failing before the fix and passing after — quote the failing output
- [x] The eight shapes the review confirmed correct stay correct (5-fence closed by 4
      and by 5, longer-than-opener closer, trailing whitespace after closer, closer
      indented ≤3 spaces, both tilde forms) — they are regression cover, not optional
- [x] Indentation measurement is untouched: `col += 4 - (col % 4)` is CommonMark's
      next-multiple-of-4 tab rule and was verified correct across eight probes

## Implementation notes

**Reachability, established before touching anything.** Neither illegal
closer appears in either file this guard scans (`docs/database.md`,
`CLAUDE.md` — `docTableRowLines` is only ever called on those two paths,
not on `docs/` generally). Checked directly: every fence-close line in both
files is a bare ` ``` ` with no leading indentation and nothing after it
(`grep -nP '^\s{4,}(`{3,}|~{3,})' docs/database.md CLAUDE.md` — no matches;
manual check of each closer line — none carry trailing text). So today the
bug is dormant, not exploitable, matching the issue's own framing ("neither
is a regression... not present in the docs today").

**Would it fail loud or silent if reachable?** Silent — which is what makes
it worth fixing rather than cosmetic. If a fenced code sample in
`docs/database.md` contained an illustrative `` |`NNNNNN_name`| `` row (e.g.
showing what a table row looks like) and its fence's closer used either
illegal form, the parser would resynchronize on the bogus closer and treat
the sample's row as a real one. That phantom row could then *mask* a real
drift: if the genuine table row for that migration were deleted, the
forward-parity check (`TestDatabaseDocMigrationParity`) would still find a
matching `` `NNNNNN_name` `` token in the phantom row and report no problem
— exactly the "table row after it slips past the guard unnoticed" failure
mode the issue names, and exactly the class `#0083`/`#0086`/`#0089` were all
filed to close. (It could also occasionally fail loudly instead — if the
phantom row named a stem not on disk, `verifyDocRowsHaveMigration` would
raise a false-positive error — but the dangerous direction, and the reason
this is a real defect rather than a formatting nit, is the silent one.)

`#0176` declined to replace a *different* file's extractor
(`internal/db/prd_index_parity_test.go`'s regex) on reachability grounds;
that reasoning does not transfer here; this file's own parser is not what
`#0176` was evaluating, and the issue text says as much.

**Fix.** Both residuals are in the closer check only (the `else` branch of
the fence-state switch in `docTableRowLines`); the opener check, indent
check, and comment-state handling are untouched. Reused `fenceLen` and
`leadingRunLength` exactly as `#0089` left them (no parallel check, no new
state) and added two more conditions a closer must satisfy, both measured
the same way existing checks already measure their inputs:

- **Indentation.** `leadingIndentWidth(line) <= 3` — the same helper the
  indented-code-block check already calls, applied to the *raw* line rather
  than `trimmed`, because `trimmed` (`strings.TrimSpace`) had already
  discarded the indentation the check needs to see.
- **Nothing but the run.** `run == len(trimmed)` where `run =
  leadingRunLength(trimmed, fenceChar)` — since `trimmed` already had
  *trailing* whitespace stripped by `TrimSpace`, "the run accounts for the
  whole trimmed line" is exactly CommonMark's "only whitespace may follow
  the closer's run."

```go
run := leadingRunLength(trimmed, fenceChar)
if run >= fenceLen && run == len(trimmed) && leadingIndentWidth(line) <= 3 {
    fenceChar = 0
    fenceLen = 0
}
```

No new parser, no lookahead, no new tracked state — same shape `#0089`
used for its two fixes.

### Spec check — both conditions, against a reference implementation, not from memory

`commonmark.js` 0.31.2 (the reference implementation, fetched with `npm pack
commonmark@0.31.2`) was used as the oracle. Twenty-one closer shapes were run
through it and through `docTableRowLines` at `f74cd6f` and at `f74cd6f^`, each as
`<opener>\nCODE\n<candidate>\n| row |\n<opener>\n` — "does the candidate close the
fence" is exactly "does the row after it land outside the code block."

**Post-fix: 21 of 21 agree with the reference.** Pre-fix: seven disagreed — the
two named forms in both their backtick and tilde spellings, plus the two
tab-indented spellings of form 1. The spec text the fix claims is real:
CommonMark 0.31.2 §4.5 — "The closing code fence... may be preceded by up to
three spaces of indentation, and may be followed only by spaces or tabs, which
are ignored" — and §2.2, tabs behave as if replaced by spaces to a tab stop of 4
where they define block structure.

### `run == len(trimmed)` — the condition the review was asked to scrutinise

The assumption it rests on holds: `trimmed` is `strings.TrimSpace(line)` (line
247 of the file), so trailing whitespace is already gone before the comparison.
The three ways this could have been wrong were probed rather than reasoned about:

- **Whitespace-only trailer still closes.** `` ```   ``, `` ```\t ``, and the
  mixed `` ``` \t `` all still close, matching the reference. `TrimSpace` uses
  `unicode.IsSpace`, which covers the tab, so `trimmed` is `` ``` `` and
  `run == len(trimmed)` holds.
- **A tab after the closer is whitespace to CommonMark too**, not just to Go —
  0.31.2's wording is "spaces or tabs", and the reference implementation confirms
  it closes. So `TrimSpace`'s broader notion of whitespace is not over-permissive
  here.
- **A closer longer than its opener is still accepted**, with or without a
  trailing space, because the condition compares the run to the trimmed line, not
  to `fenceLen`.

### `leadingIndentWidth(line) <= 3` — the tab question

`leadingIndentWidth` implements **column** semantics, not byte counting:
`col += 4 - (col % 4)` for a tab, `col++` for a space (`#0089`'s helper,
unmodified by this commit — `git diff f74cd6f^ f74cd6f` touches neither the
helper nor the indented-code-block check, so the fifth criterion holds by
construction). A single leading tab therefore measures 4 columns and does **not**
close, matching the reference. `` `   \t``` `` (three spaces then a tab) reaches
column 4 and also does not close, again matching. Applying the helper to the
raw `line` rather than to `trimmed` is necessary and correct — `trimmed` has
already discarded the very indentation the check needs.

### Residual found, recommended for filing — the *opener* has no indentation cap

Not a defect in this fix, and explicitly outside its scope (the implementer's
notes say the opener check is untouched), but the same class in the same
function, so it belongs on the record. CommonMark caps a fence **opener** at
three columns of indentation too — at four it is indented code, not a fence. The
opener branch checks only `leadingRunLength(trimmed, ch) >= 3`, with no
`leadingIndentWidth(line) <= 3`. Three opener-side divergences from the reference
remain at `f74cd6f`:

| Shape | CommonMark | `f74cd6f` |
|---|---|---|
| opener indented 4 spaces | not a fence — the row after it is content | opens a fence |
| opener indented 1 tab | not a fence | opens a fence |
| `` ``` foo`bar `` (backtick in a backtick fence's info string) | not a fence | opens a fence |

On their own all three fail in the **safe** direction: the guard over-suppresses,
a real row goes missing, and the forward check fails loudly. But the first one is
still enough to build a **silent** mask post-fix, because a spurious open flips
fence parity and a later info-string fence flips it back. Reproduced: with the
real `000009_create_interests` row replaced by

````text
    ```
    (this is an indented code sample, not a fence)

```
| `000009_create_interests` | phantom sample row |
```

```sql
SELECT 1;
```
````

the guard at `f74cd6f` reports `ok` while the reference implementation puts the
phantom row inside a code block. Contrived — but every round of this guard's
residuals has been, and this is now the fifth. Recommend filing it, and folding
in `#0089`'s still-open recommendation that the probe forms be committed as
subtests rather than re-derived by hand each round; a reviewer-side `cases` entry
per shape in the table above would have caught this one at the same time.
