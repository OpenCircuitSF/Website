## Description

`#0089` replaced a `HasPrefix` fence check with a `leadingRunLength` one and closed
the two drift forms it was filed for. Its review then probed ten further fence shapes
and found **two more residuals**. Neither is a regression — the old `HasPrefix` code
behaved identically — but both are the same drift mode `#0089` targeted: a line that
CommonMark does *not* treat as a fence closer is treated as one here, so the parser
resynchronises early and a table row after it slips past the guard unnoticed.

## The two forms

1. **A closer indented four or more spaces still closes the fence.** The check runs
   on `trimmed`, which has already had all leading whitespace stripped. CommonMark
   caps a closing fence at three spaces of indentation; at four it is indented code
   inside the block. Probe yields 1 row, want 0.
2. **A closer with trailing text still closes the fence.** ` ``` nope ` has a leading
   run of three backticks and so satisfies `leadingRunLength(trimmed, fenceChar) >= fenceLen`.
   CommonMark permits only whitespace after a closing fence. Probe yields 1 row, want 0.

## Acceptance criteria

- [ ] A closing fence indented 4+ spaces is not treated as a closer
- [ ] A closing fence followed by non-whitespace text is not treated as a closer
- [ ] Both forms added as table-driven cases to the existing `cases` slice, each
      failing before the fix and passing after — quote the failing output
- [ ] The eight shapes the review confirmed correct stay correct (5-fence closed by 4
      and by 5, longer-than-opener closer, trailing whitespace after closer, closer
      indented ≤3 spaces, both tilde forms) — they are regression cover, not optional
- [ ] Indentation measurement is untouched: `col += 4 - (col % 4)` is CommonMark's
      next-multiple-of-4 tab rule and was verified correct across eight probes

## Implementation notes

**Reachability, established before touching anything.** Neither illegal
closer appears in either file this guard scans (`docs/database.md`,
`CLAUDE.md` — `docTableRowLines` is only ever called on those two paths,
not on `docs/` generally). Checked directly: every fence-close line in both
files is a bare ` ``` ` with no leading indentation and nothing after it
(`grep -nP '^\s{4,}(`{3,}|~{3,})' docs/database.md CLAUDE.md` — no matches;
manual check of each closer line — none carry trailing text). So today the
bug is dormant, not exploitable, matching the issue's own framing ("neither
is a regression... not present in the docs today").

**Would it fail loud or silent if reachable?** Silent — which is what makes
it worth fixing rather than cosmetic. If a fenced code sample in
`docs/database.md` contained an illustrative `` |`NNNNNN_name`| `` row (e.g.
showing what a table row looks like) and its fence's closer used either
illegal form, the parser would resynchronize on the bogus closer and treat
the sample's row as a real one. That phantom row could then *mask* a real
drift: if the genuine table row for that migration were deleted, the
forward-parity check (`TestDatabaseDocMigrationParity`) would still find a
matching `` `NNNNNN_name` `` token in the phantom row and report no problem
— exactly the "table row after it slips past the guard unnoticed" failure
mode the issue names, and exactly the class `#0083`/`#0086`/`#0089` were all
filed to close. (It could also occasionally fail loudly instead — if the
phantom row named a stem not on disk, `verifyDocRowsHaveMigration` would
raise a false-positive error — but the dangerous direction, and the reason
this is a real defect rather than a formatting nit, is the silent one.)

`#0176` declined to replace a *different* file's extractor
(`internal/db/prd_index_parity_test.go`'s regex) on reachability grounds;
that reasoning does not transfer here; this file's own parser is not what
`#0176` was evaluating, and the issue text says as much.

**Fix.** Both residuals are in the closer check only (the `else` branch of
the fence-state switch in `docTableRowLines`); the opener check, indent
check, and comment-state handling are untouched. Reused `fenceLen` and
`leadingRunLength` exactly as `#0089` left them (no parallel check, no new
state) and added two more conditions a closer must satisfy, both measured
the same way existing checks already measure their inputs:

- **Indentation.** `leadingIndentWidth(line) <= 3` — the same helper the
  indented-code-block check already calls, applied to the *raw* line rather
  than `trimmed`, because `trimmed` (`strings.TrimSpace`) had already
  discarded the indentation the check needs to see.
- **Nothing but the run.** `run == len(trimmed)` where `run =
  leadingRunLength(trimmed, fenceChar)` — since `trimmed` already had
  *trailing* whitespace stripped by `TrimSpace`, "the run accounts for the
  whole trimmed line" is exactly CommonMark's "only whitespace may follow
  the closer's run."

```go
run := leadingRunLength(trimmed, fenceChar)
if run >= fenceLen && run == len(trimmed) && leadingIndentWidth(line) <= 3 {
    fenceChar = 0
    fenceLen = 0
}
```

No new parser, no lookahead, no new tracked state — same shape `#0089`
used for its two fixes.
