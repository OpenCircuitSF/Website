## Description

`#0109` widened what counts toward the repeated-soft-bounce threshold without
a corresponding change to the specification, and the code now does something
`PRD.md` does not sanction. **This needs a decision from the user**: either
the PRD is amended to match `#0109`, or `#0109`'s widening is reverted. It is
not a documentation-comment fix — `CLAUDE.md` §11 treats the PRD as the
specification, so no agent should resolve it unilaterally in either
direction.

Two PRD locations are in play:

- **`PRD.md:723` (§6.5, the state-machine table)** — `| `active` | 5 soft
  bounces in 30 days | `bounced` | Insert into `suppressions` |`. Uses the
  term "soft bounce" without defining it.
- **`PRD.md:824–825` (§6.7 step 4)** — "Apply the state machine from §6.5.
  Match `Bounce.bounceType == "Permanent"` as a hard bounce; `Transient`
  counts toward the soft-bounce threshold."

## Root cause

**The PRD is not internally inconsistent.** This matters, because `#0109`'s
`## Root cause` rested on the opposite reading — that §6.5 "says '5 soft
bounces', not '5 transient bounces'", and therefore left latitude. It does
leave the term undefined, but §6.7 step 4 is the clause that defines it, and
it does so explicitly under the sentence "Apply the state machine from §6.5."
§6.7 is not a competing narrower statement elsewhere in the document; it is
§6.5's definition clause. Read together the two are consistent, and they
define a soft bounce as `bounceType == "Transient"`. `#0109` did not weigh
§6.7, so the latitude it relied on was not actually there.

The shipped predicate (`internal/sesnotify/store.go:172–179`, mirrored by
`migrations/000016`'s partial index and the counted arm at
`internal/handlers/ses_notifications.go:456`) is:

```sql
WHERE event_type = 'Bounce'
  AND bounce_type IN ('Transient', 'Undetermined')
  AND (bounce_subtype IS NULL
       OR bounce_subtype NOT IN ('MessageTooLarge', 'ContentRejected', 'AttachmentRejected'))
```

That diverges from §6.7 in **both** directions, and each direction has a real
consequence for a live subscriber:

1. **Widened — `Undetermined` now counts.** §6.7 enumerates the bounceType
   mapping and names only `Permanent` and `Transient`; it is silent on
   `Undetermined`. In an enumeration of a closed three-value SES field,
   silence reads as exclusion. Consequence: an address is suppressed under a
   condition the specification never describes. `#0109`'s reasoning for this
   is sound on its own merits (an address returning only `Undetermined`
   bounces is operationally as dead as one returning `Transient` ones) — the
   problem is that it is a specification change made in code.
2. **Narrowed — three `Transient` subtypes no longer count.** This is the
   sharper divergence: §6.7 says "`Transient` counts toward the soft-bounce
   threshold" with no subtype qualification, and the code now declines to
   count `MessageTooLarge`, `ContentRejected`, and `AttachmentRejected`.
   These are bounces the PRD says count, which do not. Consequence: a dead
   address producing only those subtypes goes unsuppressed forever. Again the
   reasoning is defensible (those describe a fault in *our* message, not
   evidence the recipient's address is bad) and again it is unsanctioned.

## Fix

**The user made the decision this issue was blocked on, on 2026-08-21:
amend `PRD.md` to match the shipped code.** `#0109`'s widening is not
reverted and is not re-litigated here — this is the amendment, carried out
per the user's instruction.

**`PRD.md` §6.7 step 4** was:

> 4. Apply the state machine from §6.5. Match `Bounce.bounceType ==
>    "Permanent"` as a hard bounce; `Transient` counts toward the
>    soft-bounce threshold.

It now reads:

> 4. Apply the state machine from §6.5. Match `Bounce.bounceType ==
>    "Permanent"` as a hard bounce. A soft bounce is `bounceType ==
>    "Transient"` **or** `"Undetermined"` — an address that only ever
>    produces an unclassifiable bounce is operationally as dead as one
>    producing `Transient` ones, so silence on `Undetermined` is not
>    license to ignore it. **Except:** a `Transient` bounce whose
>    `bounceSubType` is `MessageTooLarge`, `ContentRejected`, or
>    `AttachmentRejected` never counts — those describe a fault in our own
>    message, not evidence the recipient's address is bad, and must not
>    suppress a live subscriber.

This states the shipped predicate in
`internal/sesnotify/store.go`'s `CountRecentSoftBounces` verbatim (verified
against the live SQL and the counted `case` arm in
`internal/handlers/ses_notifications.go`, not against this issue's own
`## Description`, per the instruction not to let the divergence chain reach
a fifth untrue document) and keeps the reason for each half inline, so a
future reader doesn't "simplify" the exclusion back out — the exact failure
mode `#0109` and this issue both exist to correct.

**§6.5 (the state-machine table, "5 soft bounces in 30 days") is left
unchanged.** §6.7 step 4 opens with "Apply the state machine from §6.5",
which already establishes §6.7 as §6.5's definition clause for the term —
that was the load-bearing reading in `#0112`'s own `## Root cause` above,
and it holds equally well against the amended text. Restating the predicate
in §6.5 as well would just create a second copy to drift out of sync the
next time this changes; one definition, referenced once, is the point.

**Code comments updated to cite the amended §6.7, not §6.5 alone:**

- `internal/sesnotify/store.go`'s `CountRecentSoftBounces` doc comment

  (~462–469) and the `default:` arm comment (~521–530) both updated the
