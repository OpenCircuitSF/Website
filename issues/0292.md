# 0292 — An imported subscriber gets `confirmed_at = now()` without confirming

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | subscribers / admin |
| **Phase** | 8 — Archive, imports, and delivery health |

## Description

`#0125` stamps `confirmed_at = now()` on every row a `prior_consent` import
commits. That is an undocumented decision with two visible consequences, and it
was made silently rather than argued.

**It inflates the growth dashboard.** `Growth30Days` documents its first count
as "how many subscribers were confirmed (became active)". An import of 500
addresses therefore reads as 500 confirmations on `#0061`'s dashboard, on the
day of the import. This is also what made `#0125`'s new fixtures perturb
`TestGrowth30Days_BoundaryAndSyntheticExclusion`.

**It asserts something untrue in the admin UI.** `/admin/subscribers/{id}` shows
a confirmation timestamp for a person who, in PRD §6.10's own words, "did not
confirm here". The whole point of recording consent provenance is that an
imported address's consent came from somewhere else — and then the row claims a
local confirmation event that never happened.

Note the field is not merely cosmetic: `consent_basis` already records
`imported_prior_consent`, so the information needed to tell the two apart is
present. The defect is that `confirmed_at` overstates it.

## The tension to resolve

`confirmed_at` is probably load-bearing elsewhere — a null may mean "pending" to
queries that predate imports. So this is not simply "set it to NULL"; it needs a
decision about what the column means now that a row can be `active` without ever
having confirmed locally.

## Acceptance criteria

1. Decide explicitly what `confirmed_at` means for an imported row, and record
   the decision and its reasoning in the code, not only in this issue. The three
   candidates worth weighing: leave it null; set it to `collected_at` (the
   consent really does have a date, just not a local one); keep `now()` and
   document it.
2. Audit every reader of `confirmed_at` before changing it. Enumerate them in
   the work log — a null-means-pending assumption somewhere would turn this into
   a behaviour change well beyond the dashboard.
3. `Growth30Days` does not count imported subscribers as confirmations, or its
   documented meaning changes to say what it actually counts. Either is
   acceptable; silently counting them is not.
4. `/admin/subscribers/{id}` does not present an imported address as having
   confirmed locally. Showing the consent provenance instead is the natural fix,
   since `consent_basis` and `source` are already stored.
5. `TestGrowth30Days_BoundaryAndSyntheticExclusion` passes for the right reason
   — not because a fixture was adjusted to accommodate the new rows. This is the
   `#0266` class; say explicitly which it is.
6. Any schema change goes in a NEW migration. Per CLAUDE.md §1 the greenfield
   exception expired on 2026-08-25 — existing migrations are frozen.
7. `ISSUE=NNNN scripts/check.sh` passes with no skips.
