## Description

`#0125` stamps `confirmed_at = now()` on every row a `prior_consent` import
commits. That is an undocumented decision with two visible consequences, and it
was made silently rather than argued.

**It inflates the growth dashboard.** `Growth30Days` documents its first count
as "how many subscribers were confirmed (became active)". An import of 500
addresses therefore reads as 500 confirmations on `#0061`'s dashboard, on the
day of the import. This is also what made `#0125`'s new fixtures perturb
`TestGrowth30Days_BoundaryAndSyntheticExclusion`.

**It asserts something untrue in the admin UI.** `/admin/subscribers/{id}` shows
a confirmation timestamp for a person who, in PRD §6.10's own words, "did not
confirm here". The whole point of recording consent provenance is that an
imported address's consent came from somewhere else — and then the row claims a
local confirmation event that never happened.

Note the field is not merely cosmetic: `consent_basis` already records
`imported_prior_consent`, so the information needed to tell the two apart is
present. The defect is that `confirmed_at` overstates it.

## The tension to resolve

`confirmed_at` is probably load-bearing elsewhere — a null may mean "pending" to
queries that predate imports. So this is not simply "set it to NULL"; it needs a
decision about what the column means now that a row can be `active` without ever
having confirmed locally.

## Acceptance criteria

1. Decide explicitly what `confirmed_at` means for an imported row, and record
   the decision and its reasoning in the code, not only in this issue. The three
   candidates worth weighing: leave it null; set it to `collected_at` (the
   consent really does have a date, just not a local one); keep `now()` and
   document it.
2. Audit every reader of `confirmed_at` before changing it. Enumerate them in
   the work log — a null-means-pending assumption somewhere would turn this into
   a behaviour change well beyond the dashboard.
3. `Growth30Days` does not count imported subscribers as confirmations, or its
   documented meaning changes to say what it actually counts. Either is
   acceptable; silently counting them is not.
4. `/admin/subscribers/{id}` does not present an imported address as having
   confirmed locally. Showing the consent provenance instead is the natural fix,
   since `consent_basis` and `source` are already stored.
5. `TestGrowth30Days_BoundaryAndSyntheticExclusion` passes for the right reason
   — not because a fixture was adjusted to accommodate the new rows. This is the
   `#0266` class; say explicitly which it is.
6. Any schema change goes in a NEW migration. Per CLAUDE.md §1 the greenfield
   exception expired on 2026-08-25 — existing migrations are frozen.
7. `ISSUE=NNNN scripts/check.sh` passes with no skips.

**Decision (criterion 1): leave `confirmed_at` NULL for a `prior_consent`
import.** Reasoning, recorded in code at the insert site
(`internal/subscribers/imports.go`, `Commit`) and in `Growth30Days`'s doc
comment:

- PRD §6.10 states outright that these subscribers "did not confirm here" —
  stamping a local timestamp asserts an event that never happened.
- `collected_at` was weighed and rejected: it is a `DATE`, often recent
  relative to the import (an event's sign-in sheet imported soon after), so
  using it would frequently fall inside `Growth30Days`'s 30-day window and
  reproduce the exact inflation bug this issue exists to fix, just gated on a
  different column. It would also re-arm the SES staleness guard (reader #8)
  using a semantically different date (source collection, not local
  confirmation) than that guard's own comment describes comparing against.
- `now()` + document was rejected because "document" doesn't fix the dashboard
  or the admin UI — both would need the same query/UI changes regardless, at
  which point the timestamp itself serves no purpose except being wrong.
- NULL costs nothing new: reader #3 (`RestartSignup`) already establishes NULL
  = "no local confirmation event" as an existing, well-understood meaning in
  this codebase (see also `admin_subscribers_export.go`'s pre-existing
  `formatExportTime` comment) — this issue gives that meaning one more
  producer rather than inventing a new one. `consent_basis =
  imported_prior_consent` (already stored) is what records *why* the row is
  active without a local confirmation, so no provenance is lost.

No schema change was needed for this decision — `subscribers.confirmed_at` is
already nullable (`migrations/000010`) and no CHECK constraint ties it to
`status`. Criterion 6 is satisfied vacuously: nothing to migrate.

The reviewer's list matches the implementer's twelve entries with nothing
found that it missed. Two negatives worth stating explicitly, because they are
what would have made this a wider behaviour change: **`internal/mailing`,
`internal/outbox`, and `internal/campaigns` contain zero references to
`confirmed_at`** — audience selection is by `status`, not by confirmation
timestamp, so no send path gains or loses a recipient. And nothing anywhere
uses `confirmed_at IS NULL` as a proxy for "pending"; the two writers that
care (`Confirm`, `RestartSignup`) pair it with `status` explicitly.

**The `ses_notifications.go` clearance — re-examined, and it holds, though
the reasoning is sharper than "identical to an existing case."** What that
guard protects is a *restoration*: an old bounce/complaint arriving late must
not undo an address that was legitimately cleared and then re-confirmed, and
`confirmed_at` is the marker of that restoration. The implementer's framing
("a pending row already skips this guard") is true but glosses one real
difference — an imported row is `active` and therefore mailable, where a
pending row is not, so the class of events that can reach it is not the same.
Two facts close that gap, both verified in `internal/subscribers/imports.go`:

1. **An import can never restore anything.** `existingEmails` matches
   *any* status ("an import must skip an existing row"), and
   `suppressedEmails` is reason-blind. A subscriber row produced by `Commit`
   is therefore always brand new — there is no prior state for a late event
   to undo, so the scenario the guard exists for cannot arise from an import.
2. **Where the guard is now disarmed, it fails in the safe direction.** If a
   stale event somehow did reach an imported row, applying it marks the row
   bounced or suppressed. Pre-`#0292` the row carried `confirmed_at = <import
   time>`, which *armed* the guard and would have made the handler ignore a
   genuine complaint history for that address — the wrong direction for both
   deliverability and CAN-SPAM. Disarming it is, if anything, an improvement.

So the clearance stands, and `TestSESNotifications_StaleEventGuard_PredatesConfirmedAt` (which seeds its
own confirmed row) is unaffected and passes.
