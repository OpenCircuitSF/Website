# 0086 — The docs-parity guard never checks the range's lower bound, and three markdown forms still slip a row past it

## Description

`#0083` made the docs-parity guard bidirectional, added contiguity and down-file checks, and folded `CLAUDE.md` into the same table-driven test. All four drift modes it targeted are genuinely closed — re-proven independently, with a negative control confirming the assertions do not mask one another.

Its reviewer then attacked the result and found three residuals. None blocked; all are narrower than what was fixed; none exists in the docs today.

## 1. The range's lower bound is never asserted

`rangeMatch[1]` is captured and echoed in failure messages but never compared. A stale `` `000003`–`000011` `` passes green in **both** files. Only the upper bound is checked.

This is the same class of defect the guard exists to catch — a documented claim nothing enforces — sitting inside the guard itself.

## 2. Three markdown forms still satisfy the row check

`docTableRowLines` toggles only on ```` ``` ```` fences, so a `|`-leading line is still honoured inside:

- a **4-space indented code block**
- a **multi-line HTML comment** wrapping a row
- a **`~~~` tilde fence**

Verified case by case. For contrast, the forms it correctly rejects: ordinary prose, a bullet list, a blockquoted row, and a single-line HTML comment — and it correctly accepts tight pipes, alignment colons, a nested table in a list item, and a table inside `<details>`. So the fix is real; these three are the remaining edges of the same class as the fenced-code-block mode `#0083` closed.

## 3. The placement reasoning is overstated

`#0083` kept the test in `internal/db`, where it queues behind that package's advisory lock despite needing no database. **The conclusion is right on the merits** — `internal/db` owns migrations, and the lock is an artifact of that package's single DB test. But the stated reason, that every viable target was off-limits due to concurrent work, is not quite accurate: a lock-free `internal/db/docsparity` subpackage was squarely in lane.

Not a defect. Worth correcting so the next person weighs the real tradeoff rather than an availability accident.

## Acceptance criteria

- [ ] The range check asserts the **lower** bound; a stale `` `000003`–`000011` `` fails in both files. Mutation-proven
- [ ] `docTableRowLines` rejects `|`-leading lines inside 4-space indented code blocks, multi-line HTML comments, and `~~~` tilde fences. **Each mutation-proven separately** — three conditions, three outputs
- [ ] The forms it currently accepts correctly still pass: tight pipes, alignment colons, nested table in a list item, table inside `<details>`
- [ ] The placement note in `#0083` is corrected, or the test is moved to a lock-free subpackage with the real tradeoff recorded
- [ ] Still filesystem-only — passes with `TEST_DATABASE_URL` set and unset
- [ ] `go build ./...`, `go vet ./...`, `go test ./... -count=1` green, zero skips

## Notes

Resist re-implementing a markdown parser. The goal is to reject the three named forms without accepting a dependency or becoming something nobody will maintain — a small state machine tracking fence and comment state is likely enough.

`#0083`'s reviewer also confirmed the `000001`-start assumption is load-bearing: renaming `000001` fails at position 0. That is what both documents claim, so it is defensible, but a legitimately retired migration would force a renumber. Worth knowing, not worth changing now.
