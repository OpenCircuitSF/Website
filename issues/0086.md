## 1. The range's lower bound is never asserted

`rangeMatch[1]` is captured and echoed in failure messages but never compared. A stale `` `000003`–`000011` `` passes green in **both** files. Only the upper bound is checked.

This is the same class of defect the guard exists to catch — a documented claim nothing enforces — sitting inside the guard itself.

## 2. Three markdown forms still satisfy the row check

`docTableRowLines` toggles only on ```` ``` ```` fences, so a `|`-leading line is still honoured inside:

- a **4-space indented code block**
- a **multi-line HTML comment** wrapping a row
- a **`~~~` tilde fence**

Verified case by case. For contrast, the forms it correctly rejects: ordinary prose, a bullet list, a blockquoted row, and a single-line HTML comment — and it correctly accepts tight pipes, alignment colons, a nested table in a list item, and a table inside `<details>`. So the fix is real; these three are the remaining edges of the same class as the fenced-code-block mode `#0083` closed.

## 3. The placement reasoning is overstated

`#0083` kept the test in `internal/db`, where it queues behind that package's advisory lock despite needing no database. **The conclusion is right on the merits** — `internal/db` owns migrations, and the lock is an artifact of that package's single DB test. But the stated reason, that every viable target was off-limits due to concurrent work, is not quite accurate: a lock-free `internal/db/docsparity` subpackage was squarely in lane.

Not a defect. Worth correcting so the next person weighs the real tradeoff rather than an availability accident.

## Notes

Resist re-implementing a markdown parser. The goal is to reject the three named forms without accepting a dependency or becoming something nobody will maintain — a small state machine tracking fence and comment state is likely enough.

`#0083`'s reviewer also confirmed the `000001`-start assumption is load-bearing: renaming `000001` fails at position 0. That is what both documents claim, so it is defensible, but a legitimately retired migration would force a renumber. Worth knowing, not worth changing now.

## Fix

**1. Lower bound now asserted.** In `TestDatabaseDocMigrationParity`
(`internal/db/docs_parity_test.go`), added `lowest := stems[0].version`
alongside the existing `highest`, and — mirroring the existing upper-bound
block exactly — parse `rangeMatch[1]`, compare it to `lowest`, and `t.Errorf`
naming both the stated and actual lowest stem when they disagree. Runs for
both `docs/database.md` and `CLAUDE.md` since it lives in the same
table-driven case loop as the upper-bound check.

**2. `docTableRowLines` is now a small state machine, not a single fence
toggle.** Rewrote `internal/db/docs_parity_test.go`'s `docTableRowLines` to
track three independent states per line, checked in this order:

- **Fence**, tracked by *which* character opened it (`` ` `` or `~`) rather
  than a single boolean, so a `~~~` block can only be closed by another
  `~~~` line — a `` ``` `` toggle no longer accidentally closes it (or, as
  before this fix, never recognized it as a fence at all).
- **HTML comment**, opened by a line whose trimmed form starts with `<!--`
  and does not also close on the same line, closed by the next line
  containing `-->`. A single-line comment needs no state: its trimmed form
  starts with `<!--`, not `|`, so the final prefix check already rejects it.
- **Indented code**, any line with 4+ leading raw (untrimmed) spaces. A list
  item's nested content — 2 spaces for `- `, 3 for `1. ` — never reaches 4,
  so a table nested in a list item is unaffected.

Added `TestDocTableRowLines`, a subtest-per-case table covering both the
three newly-rejected forms and the four forms that must keep passing
(`ordinary prose`, `bullet list`, `blockquoted row`, `single-line HTML
comment` reject; `tight pipes`, `alignment colons`, `nested table in a list
item`, `table inside <details>` accept) — none of these forms exist in the
real docs today, so the cases are synthetic strings passed directly to
`docTableRowLines`, not fixtures.

**3. `#0083`'s placement note corrected.** Its claim that "every viable
target was off limits" was inaccurate — a lock-free `internal/db/docsparity`
subpackage (no `TestMain`, so `testdb.Lock` never runs) was available and in
lane the whole time. Rewrote the comment block above
`TestDatabaseDocMigrationParity` to state the real tradeoff: such a
subpackage would avoid the advisory-lock queueing cost at the price of a new
package/directory boundary for one test file and a deeper relative path to
`migrations/`/`docs/`. `internal/db` is kept on that tradeoff, not because
nothing else was available. The conclusion (stay in `internal/db`) is
unchanged, per the issue's own assessment that it's "right on the merits."
