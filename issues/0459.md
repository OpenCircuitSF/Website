## Description

`TestNoCommentCitesUnresolvedPathOrSection` checks that a cited **path
resolves**. It does not check that a **claim about that path's contents** is
true.

`#0456` is the case that motivates this: two doc comments cited
`migrations/000010` for constraints and columns that live in `000023`. The guard
passed on both, because `migrations/000010` exists. `#0438` hit the same gap
from the other side — a comment quoting a `PRD.md` section correctly until the
section changed underneath it.

## The narrow version, which is tractable

Proposed by `#0456`'s reviewer, and the scoping is the substance:

> For a comment naming **both** a migration file and a constraint or column
> identifier, assert that identifier appears in that file.

That would have caught both `#0456` citations. It is checkable because migration
files are SQL — an identifier either appears in the file or it does not — unlike
a prose claim about a section's meaning.

## The boundary, which matters more than the feature

**Scope it to `migrations/` citations only, and resist widening it.** A general
prose-accuracy checker is `CLAUDE.md` §8's `#0258` spiral: six passes, each
closing what it was shown, each buying the next bounce. The reviewer that
proposed this said so explicitly, and that constraint is part of the proposal
rather than a caveat on it.

## Acceptance criteria

1. A comment naming a migration file **and** a constraint or column identifier
   fails if that identifier does not appear in that migration.
2. **Prove it against the two real `#0456` cases**: check out the pre-fix
   comments into a copy or throwaway worktree and confirm the guard fires on
   both. A guard that cannot catch the case that motivated it is decoration.
   Never `git stash` (§8a).
3. **Assert the extraction produced something.** A scan that matches no comments
   and then reports success is this repo's twice-shipped fail-open (`#0258`,
   `#0428`). An empty extraction must be an error, never an input.
4. **No false positives on the current tree**, and say how many comments the
   scan examined. `#0456`'s review verified by hand that the other citations in
   `internal/subscribers/` are correct — including three to `000010` that are
   right — so a guard flagging any of those is wrong.
5. Decide where it lives. `internal/handlers` already hosts the repo-wide
   citation family and reads every Go comment, so a sibling there is the obvious
   home — but `CLAUDE.md` §5's guard table would then need its `Reaches into`
   cell updated by hand, since that column is not machine-checked (`#0387`).
   Say which you did.
6. **One mechanism.** Do not also fix comments the guard finds; report them and
   let the orchestrator file them, unless a fix is trivially forced by making
   the tree green.

## Root cause

`TestNoCommentCitesUnresolvedPathOrSection` (and its whole citation-guard
family) resolves a cited repository *path* against the real filesystem, but a
"migrations/NNNNNN" shorthand citation (no filename, no extension) never even
matched that guard's path pattern in the first place — it requires a trailing
extension or one of the `HANDOFF`/`README`/`LICENSE` bare names. So `#0456`'s
two wrong citations weren't merely unchecked for content accuracy; the
existing guard family never recognized them as citations at all.

## Fix

Added `internal/handlers/migration_citation_content_guard_test.go`,
`TestMigrationCitationIdentifierMatchesContent`, a sibling in the existing
citation-guard family (reuses `citedTestScanRoots`, `walkGoFiles`,
`assertGoFileVisitCountPlausible`, `stripCommentMarkers`, and
`toRepoRelativePath` from `dangling_test_citation_guard_test.go`, same
package, same technique as `#0196`/`#0220`/`#0267` — not a new design).

For every Go comment (test files included) that cites `migrations/NNNNNN`,
the guard extracts candidate identifiers two ways and checks each as a whole
word against that migration's own `.up.sql` + `.down.sql` text:

1. **A bare snake_case token**, scoped to the text between the citation and
   the nearest preceding sentence/clause boundary (`.`, `:`, or `;`) —
   not the whole comment group. A dry run using the whole group produced real
   false positives (an unrelated snake_case word from an earlier, unrelated
   sentence in the same paragraph); clause-bounding is what closed that.
   Catches `#0456`'s first citation directly
   (`subscribers_source_check`/`subscribers_consent_basis_check` are literal
   snake_case text already).
2. **A struct field's own Go name, converted to snake_case** — only for a
   struct field's own doc comment (via `go/ast`, not free-text guessing), and
   only that field's own declared name. This is what catches `#0456`'s
   *second* citation, which named Go field identifiers
   (`Source, SourceDetail, ConsentBasis, ImportID, InvitedAt`) with zero
   snake_case text anywhere in the comment. Deliberately **not** extended to
   const/var docs: a real comment in the tree
   (`internal/mailing/outbox_worker.go`'s `settingQueueMaxRetries is
   migrations/000021's seeded settings row`) converts to
   `setting_queue_max_retries`, which that migration does not contain — the
   actual seeded key is `queue_max_retries`, one Go-naming-convention prefix
   short of the constant's own name, because a const documents the *key it
   holds*, not a column sharing its own name. Struct fields in this tree
   really do name their own column 1:1 (verified against three real
   `Subscriber` fields' migration SQL directly); consts do not reliably.

One additional exclusion, also earned by a real false positive found while
dry-running the guard over the whole tree: a negation marker (`no `, `not `,
`never `, `n't `, `without `) immediately before a candidate discounts it —
`internal/handlers/audit_test.go` cites a migration as evidence a foreign key
does *not* exist, naming the table on the other end of that absent key, which
is not a claim the migration contains that table.

Also updated `CLAUDE.md` §5's guard table (criterion 5 — see below).

## Gotchas

- **A window-based proximity heuristic over-triggers on multi-sentence
  comment groups.** An early version scoped snake-token extraction to a
  fixed character window (100 chars) around the citation rather than a
  clause boundary, and produced real false positives from unrelated words in
  an earlier *sentence* of the same paragraph (e.g. `created_at` mentioned
  two sentences before an unrelated `migrations/000013` citation). Clause-
  bounding (nearest preceding `.`/`:`/`;`) is what fixed it — see the `Fix`
  section above.
- **Writing about this guard reproduces its own false-positive shapes.**
  Twice — the acronym-conversion doc comment and the negation-marker doc
  comment both initially cited two different migration numbers with a shared
  identifier list in one sentence, exactly the pattern the guard is designed
  to flag, and the guard duly flagged its own file. Fixed by rephrasing (one
  migration citation per sentence) rather than by adding a self-exemption to
  the extraction logic, per `CLAUDE.md` §8's `#0392` note that this
  phase-wide pattern already cost six issues nine trips.
- Did not fold in `#0438`'s `PRD.md`-side gap — out of scope per this issue's
  own boundary (`migrations/` citations only) and per `#0176` (wontfix) on
  the cost of a heavier prose-accuracy checker.

### On the machinery: three of five parts are load-bearing, two are dead

I mutated each exclusion off in the worktree and re-ran the tree-wide guard.

| Part | Removing it | Verdict |
|---|---|---|
| clause bounding (`migrationCitationSentenceBoundary`) | 4+ false positives (`internal/workshops/main_test.go`, `internal/workshops/store.go`) | **load-bearing** |
| negation markers | 1 false positive: `"email_campaigns"` not found in `migrations/000005`, from `TestAdminAudit_TargetFilter`’s `campaignID` comment in `internal/handlers/audit_test.go` | **load-bearing** |
| `goFieldNameToSnakeCase` + field-doc path | `#0456`'s second case stops being caught | **load-bearing** |
| trailing-underscore filter (`text[end] == '_'`) | no change | **dead code** |
| `migrationCitationTruncatedSuffixPattern` | no change | **dead code** |

Both dead branches are unreachable **by construction**, not merely unexercised
by today's tree, and both doc comments state a false premise for them.

- The trailing-underscore filter cannot fire.
  `migrationCitationSnakeTokenPattern` ends in `\b`, and `_` is an RE2 word
  character, so a match is never immediately followed by `_`. Its comment says
  the real instance is `the three send_health_* settings`, "where the pattern
  alone would extract `send_health`". Measured: on that exact string the
  pattern produces **no match at all** — not `send_health`. (Nor does
  `internal/mailing/delivery_health.go`'s real citation of that text produce a
  candidate: it reports 1 citation, 0 checks.) The comment then reasons about
  "a literal-substring check", which this guard does not perform —
  `migrationContentHasIdentifier` is whole-word, so the described failure would
  be a false positive, not a silent pass.
- `migrationCitationTruncatedSuffixPattern` cannot fire either. It only matches
  when a candidate is immediately followed by `.go`/`.sql`/etc., and that `.`
  is itself a `migrationCitationSentenceBoundary`. Any such token therefore
  sits before `lo` and can never enter the window. Measured on its own cited
  instance (the `(imports_test.go) reads` … wording on
  `growthArrivalConsentBases`’ doc comment in `internal/subscribers/store.go`):
  raw token `imports_test`, `inWindow=false`.

The file's preamble says the extraction paths and exclusions were "both earned
by real instances found while dry-running this guard over the whole tree (not
invented in the abstract)". For these two that is not true, and it is the kind
of claim this guard exists to stop.

### The remedy — apply exactly this, nothing more

1. In `collectMigrationCitationSnakeCandidates`, delete the branch
   `if end < len(text) && text[end] == '_' { continue }` and delete the
   `send_health_*` justification from that function's doc comment.
2. Delete `migrationCitationTruncatedSuffixPattern`, its doc comment, and its
   use in `collectMigrationCitationSnakeCandidates`. Removing the comment also
   removes a sentence that pairs `migrations/000023` with `imports_test`, which
   is a citation-shaped pairing this file would rather not carry.
3. Keep clause bounding, the negation markers, `goFieldNameToSnakeCase` and the
   field-doc path unchanged — all three are proved load-bearing above.
4. Add one bullet to the file's "Deliberately NOT covered" list: identifier
   candidates are taken only from text **preceding** the citation, so the
   idiomatic "migrations/000023's `source` column" ordering is not checked.
   This is the right choice — I measured a naive forward window and it adds 22
   checks and **5 false positives** (`internal/db/prd_index_parity_test.go`,
   `internal/mailing/worker_store.go`, `internal/subscribers/erase.go`, and
   twice this guard's own doc comments) — but it is the largest scoping
   decision in the file and the only one the list omits.
5. In `TestMigrationCitationGuardCatchesBothRealHistoricalCases`, change
   `Reconstructed verbatim` to `Reconstructed — abridged`, since the field
   comment's third line is paraphrased rather than trimmed.
6. Do **not** add a test for either deleted branch, do not replace them with a
   different exclusion, and do not widen the extraction. Re-run and confirm the
   counts are unchanged: 74 citations, 34 identifier checks, 0 hits.
