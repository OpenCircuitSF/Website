## Description

`#0337`'s own description says this is "the hazard `CLAUDE.md` should probably
record generally", and it still is not recorded.

`#0325` renamed `(*seo.Sitemap).InvalidateWorkshops` → `Invalidate`. That
rename moved `*seo.Sitemap` onto **two unrelated single-method interfaces**
(`handlers.seoCacheInvalidator` and `mailing.ArchiveCacheInvalidator`) with no
source change of its own at either seam and **no toolchain diagnostic** — Go
interface satisfaction is structural, so nothing anywhere had to opt in.
`#0337` closed that instance by unexporting the method, but §8 carries no entry
warning that the next short-rename will do the same thing again.

Two facts belong in the entry, the second sharper than the first:

1. **Shortening an identifier is the common way an accidental satisfier
   appears.** The cheap before/after check is `go/types.Implements` over a
   package's *full* named-type set — not a hand-picked list of the types you
   already suspect. `#0337`'s review found the regression precisely because it
   widened the check from the implementer's three types to every named type in
   the package.

2. **Value receivers count.** `*T`'s method set includes value-receiver
   methods, so an AST guard that scans only pointer receivers has a hole. This
   is not hypothetical: `#0337`'s first guard justified a pointer-receiver-only
   scan in its own doc comment, and a `func (s Sitemap) Invalidate() {}`
   mutation fully restored the original regression while the guard still
   reported `ok`.

Both are already written up in `#0335`'s and `#0337`'s `## Review notes`; this
issue is to lift them into §8 where the next agent will read them.

## Acceptance criteria

1. `CLAUDE.md` §8 gains an entry, in the section's established voice — a bolded
   one-line statement of the hazard, then the concrete instance that produced
   it, then what to do instead.
2. The entry names the real instance (`#0325`'s rename, `*seo.Sitemap`, the two
   interfaces) rather than describing the hazard abstractly. §8's entries earn
   their length by being specific; a generic warning about structural typing
   would not have prevented this.
3. The entry states the value-receiver corollary explicitly, with the reason
   (`*T`'s method set includes value-receiver methods), because that is what
   makes a pointer-receiver-only guard unsound.
4. The entry gives the check to run: `go/types.Implements` over every named
   type in the package, before and after.
5. No behaviour change, no code change. Documentation only.
6. `#0337`'s guard, once its own second pass lands, is consistent with what
   this entry says — read it and make sure the doc and the guard do not
   disagree.
