Two facts belong in the entry, the second sharper than the first:

1. **Shortening an identifier is the common way an accidental satisfier
   appears.** The cheap before/after check is `go/types.Implements` over a
   package's *full* named-type set — not a hand-picked list of the types you
   already suspect. `#0337`'s review found the regression precisely because it
   widened the check from the implementer's three types to every named type in
   the package.

2. **Value receivers count.** `*T`'s method set includes value-receiver
   methods, so an AST guard that scans only pointer receivers has a hole. This
   is not hypothetical: `#0337`'s first guard justified a pointer-receiver-only
   scan in its own doc comment, and a `func (s Sitemap) Invalidate() {}`
   mutation fully restored the original regression while the guard still
   reported `ok`.

Both are already written up in `#0335`'s and `#0337`'s `## Review notes`; this
issue is to lift them into §8 where the next agent will read them.

### What is wrong

The entry opens:

> `#0325` renamed `(*seo.Sitemap).InvalidateWorkshops` → `Invalidate`. Go
> interface satisfaction is structural, so that rename alone — no source
> change at either seam — moved `*seo.Sitemap` onto two unrelated
> single-method interfaces …

Two checkable claims in that sentence are false, and the second follows from
the first:

1. **`(*seo.Sitemap).InvalidateWorkshops` never existed.** `git show
   f7771ed^:internal/seo/sitemap.go` shows `func (s *Sitemap) Invalidate()` —
   already under the short name, before `#0325`. `f7771ed`'s diff for
   `sitemap.go` is a doc comment and nothing else. What `#0325` actually
   renamed was `(*seo.Site).InvalidateWorkshops` and
   `(*seo.Renderer).InvalidateWorkshops`.
2. **Both seams did change source in that same commit** — they are the only
   reason the widening happened. `git show f7771ed^:internal/handlers/admin_workshops.go`
   gives `type workshopCacheInvalidator interface { InvalidateWorkshops() }`
   and `git show f7771ed^:internal/mailing/worker.go` gives
   `type ArchiveCacheInvalidator interface { InvalidateWorkshops() }`;
   `f7771ed` rewrites both method lines to `Invalidate()`.

So the direction is backwards. `*Sitemap` did not move onto the interfaces —
**the interfaces moved onto `*Sitemap`**, a type the commit never touched,
because `*Sitemap` already carried the short name the seams were renamed to.
Measured with `go/types.Implements` over every named type in `internal/seo`
(`golang.org/x/tools/go/packages` loader, run against `git archive` exports of
each commit, so this checkout was never disturbed):

| tree | `Invalidate()` satisfiers in `internal/seo` |
|---|---|
| `f7771ed^` (before `#0325`) | `{*Sitemap}` |
| `f7771ed` (after `#0325`) | `{*Site, *Renderer, *Sitemap}` |
| `HEAD` (after `#0337`) | `{*Site, *Renderer}` |

The middle and last rows reproduce exactly what `#0337`'s review measured. The
**first** row is the one the entry gets wrong: before the rename `*Sitemap`
was the *only* satisfier in the package, which is impossible to square with
"`#0325` renamed `(*seo.Sitemap).InvalidateWorkshops` → `Invalidate`".

This also puts the entry in direct conflict with the two places in the code
that record the same history — criterion 6's "the doc and the guard do not
disagree":

- `internal/seo/sitemap.go`'s `invalidate` doc comment: "Sitemap already had a
  method with this exact zero-parameter, zero-result signature **before
  Site.Invalidate was itself named InvalidateWorkshops (#0325's rename
  target)**. Shortening that method's name to Invalidate moved
  handlers.seoCacheInvalidator and mailing.ArchiveCacheInvalidator … onto
  \*Sitemap … **with no source change of its own**." The entry moved "no source
  change of its own" — which described `*Sitemap` — onto "either seam", where
  it is untrue.
- `internal/seo/invalidator_satisfier_guard_test.go`'s doc comment: "#0325's
  rename … **moved those two interfaces onto \*Sitemap** by accident".

And it costs the entry its lesson. As written it teaches "renaming a concrete
type's method can make it satisfy an interface" — true, obvious, and not what
happened. The surprising half, and the one that would have prevented this, is
that **shortening the method name a narrow seam requires can recruit an
untouched bystander type that already had the short name** — nothing at the
recruited type's own definition site changes, so nothing there is under review
when the rename lands.

### The remedy — apply exactly this

Replace the entry's **first** paragraph in `CLAUDE.md` §8, in full. The second
paragraph ("**Value receivers count, and this is the sharper half.** …") is
correct and stays byte-identical.

Delete:

```
- **Shortening an identifier can silently widen an interface's satisfier
  set.** `#0325` renamed `(*seo.Sitemap).InvalidateWorkshops` → `Invalidate`.
  Go interface satisfaction is structural, so that rename alone — no source
  change at either seam — moved `*seo.Sitemap` onto two unrelated

```

Insert:

```
- **Shortening an identifier can silently widen an interface's satisfier set,
  and the identifier that moves need not be on the type that gets recruited.**
  `#0325` (`f7771ed`) renamed `(*seo.Site).InvalidateWorkshops` and
  `(*seo.Renderer).InvalidateWorkshops` → `Invalidate`, and in the same commit
  renamed the method their two consuming seams require —
  `handlers.workshopCacheInvalidator` (now `seoCacheInvalidator`) and
  `mailing.ArchiveCacheInvalidator` — from `InvalidateWorkshops()` to
  `Invalidate()`. Go interface satisfaction is structural, so that rename
  moved both interfaces onto `*seo.Sitemap`, a type the commit never touched:
  `(*seo.Sitemap).Invalidate` already carried that exact zero-parameter,
  zero-result name, so passing a bare `*Sitemap` into either seam went from a
  compile error to a silent half-invalidation. Nothing failed to compile and
  no toolchain diagnostic fired. Measured with `go/types.Implements` over the
  package's full named-type set, the satisfiers were `{*Sitemap}` before the
  rename, `{*Site, *Renderer, *Sitemap}` after it, and `{*Site, *Renderer}`
  once `#0337` closed the instance by unexporting `Sitemap.invalidate`. That
  full named-type set is the check to run before and after a rename like this,
  not a hand-picked list of the ones you already suspect — `#0337`'s first
  guard checked only the three types its author already had in mind, and its
  review found the gap precisely by widening the check to every named type in
  the package.
```

#### Independent three-tree reproduction

Method, deliberately different from the first review's: three `git archive`
exports (`f7771ed^`, `f7771ed`, `HEAD`) unpacked **outside** this checkout, and
a standalone probe module (its own `go.mod`, no `golang.org/x/tools`) that
`chdir`s into each export and type-checks
`internal/{seo,handlers,mailing}` from source via
`go/importer.ForCompiler(fset, "source", nil)`. It then looks up the **real**
interface declarations — `handlers.workshopCacheInvalidator` /
`seoCacheInvalidator` (unexported, reachable because the probe type-checks the
package rather than importing it) and `mailing.ArchiveCacheInvalidator` — and
calls `types.Implements` for **every** named type in `internal/seo`'s package
scope, both `T` and `*T`. 16 named types scanned per tree, no hand-picked list:
`ArchiveEntry ArchiveSource Renderer RouteMeta Site Sitemap Workshop
WorkshopSource WorkshopStatus cacheEntry eventLD eventOrganizer eventPlace
recorder sitemapURL urlset`.

Because it resolves the seams as declared at each tree, this measures the
satisfier set **of the two interfaces themselves**, which is the sharper
question:

| tree | seams require | satisfiers in `internal/seo` |
|---|---|---|
| `f7771ed^` (before `#0325`) | `InvalidateWorkshops()` | `{*Renderer, *Site}` |
| `f7771ed` (after `#0325`) | `Invalidate()` | `{*Renderer, *Site, *Sitemap}` |
| `HEAD` (after `#0337`) | `Invalidate()` | `{*Renderer, *Site}` |

Both seams give identical sets at every tree. This is the entry's claim proved
end to end: `*Sitemap` is **outside** both interfaces before the rename and
**inside** both after it, so the previously-impossible assignment starts
compiling — and `#0337` removes it again. `go.mod`/`go.sum` were untouched
(`git status --porcelain -- go.mod go.sum` empty); the `-mod=mod` promotion trap
`#0349` records did not recur, because nothing ran `go list` in this checkout.
