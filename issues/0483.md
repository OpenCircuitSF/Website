## Description

`internal/config`'s `.env.example` guard carries a floor constant,
`minLoaderVariables`, asserting the AST walk still sees at least N variable
reads in `config.go`. Its purpose is sound and `CLAUDE.md` §8 states it: assert
the extraction produced something before trusting it, so a walk that silently
stops seeing reads fails loudly instead of passing on an empty result.

**A floor only catches shrinks.** Growth passes it unnoticed — correctly, by
design. But the doc comment beside it asserted **"exactly 20 variables today"**,
which is an *exact-count* claim a floor cannot maintain.

It went stale immediately and stayed stale. `#0433` added `MEDIA_DIR`, taking
the real count to 21, and the floor and its prose both stayed at 20. Nothing
complained, because nothing could: 21 ≥ 20.

`#0402` found it. Its plan, reasoning from the prose, said the floor was 20 and
should become 21. Its implementer re-derived the count from the AST walk
instead of trusting that, found 21 **before** its own change, and set the floor
to **22**. `#0402`'s review then re-derived it independently: parent 21, HEAD
22. Three derivations, two of them prompted only because someone distrusted the
comment.

## Root cause

`minLoaderVariables`' doc comment stated `config.go reads exactly 22 variables
today` immediately beside `len(names) < minLoaderVariables`, an inequality
check. An exact-count sentence next to a floor cannot stay true once the real
count grows past it — nothing re-checks prose, only the constant is load-bearing
— which is exactly what happened twice (`#0433`, then `#0402` raising the
constant itself).

## Fix

Chose **drop the count from the prose** (criterion 1's first option): the
comment no longer names a current count at all, only the constant does. This is
the cheaper of the two options and nothing can drift, since there is no longer
a second number to keep in sync. Pinning the count exactly (asserting equality)
was rejected because it would turn every future loader-variable addition into a
required edit here, and the issue's own text flagged that as a cost worth
naming rather than accepting silently.

The rewritten comment keeps the history (`#0428` set the constant to 20,
`#0433`'s `MEDIA_DIR` took the real count to 21 without a bump, `#0402` raised
the constant itself to 22) and keeps `CLAUDE.md` §8's assert-the-extraction
rationale and the existing instruction to lower the constant only for a
deliberate, reviewed removal — both survive unchanged in substance. Criterion 2
is satisfied: the floor's behavior (`len(names) < minLoaderVariables`) is
untouched, only the doc comment changed.

**Criterion 3** — re-derived the count independently with a standalone Go
program running the same AST walk `TestEnvExampleCoversLoaderVariables` uses
(parse `config.go`, collect every `CallExpr` whose first argument is a string
literal matching `envVarNameLiteral`) against the current working tree: 22,
agreeing with `#0402`'s two derivations and this issue's own claim.

**Criterion 4** — proved the floor still fails closed. See `## Verification`
for the mutation and its restoration.

**Criterion 5** — found one sibling in the same file carrying the identical
shape: `minScannedEnvExampleAssignments`'s doc comment asserted `.env.example`
"carries exactly 20 'NAME=' lines today," and the real count had already
drifted to 22 (undetected only because 22 still clears a floor of 20). Fixed
it the same way — dropped the exact-count sentence, kept the floor's rationale
and its "lower only on deliberate removal" instruction — since the fix was the
same one-line pattern in the same file. Left its constant at 20, unbumped: the
issue's scope is the exact-count prose defect, not tightening floor margins,
and 20 still correctly fails closed on any real shrink today (any single
`.env.example` removal drops the count to 21, which the fixed prose no longer
claims is impossible).

Also considered, and left unfixed per criterion 5's "name, don't fix" default:
`internal/outbox/claim_kinds_call_site_guard_test.go`'s
`claimKindsGuardMinPlausibleNonExemptCallSiteCount` doc comment names exact
counts ("internal/mailing holds exactly 7 non-exempt sites today," "leaving
exactly 8") but these describe worked examples inside a much longer margin
analysis, not a single "the floor equals today's total" claim next to the
constant the way the two fixed instances did — re-verifying and rewriting that
analysis safely is not a trivial, same-shape edit, so it is named here rather
than touched.

## Why the prose is the defect, not the floor

The floor did its job. It is the **claim next to it** that misled a planning
pass into prescribing a wrong number — and would have shipped one, had the
implementer not re-derived.

This is the same shape this project keeps meeting: a comment that was true when
written, drifting silently because nothing checks prose. `#0472` found it in
`CLAUDE.md`'s SES bullet, `#0475` found the slug rationale false in three
places, and `#0478` found notes never scanned. What is distinctive here is that
the false claim sat **directly beside a guard**, which lends it borrowed
authority.

## Acceptance criteria

1. **Decide between the two honest options**, and say why:
   - **Drop the count from the prose.** Describe the floor as a floor — "at
     least this many" — and let the constant be the only number. Cheapest, and
     nothing can drift.
   - **Pin the count exactly.** Assert equality rather than `<`, so adding a
     variable fails until the number is updated deliberately. Stronger, but it
     turns every added variable into a required edit here — say whether that is
     wanted before choosing it.

   Do **not** keep an exact-count sentence beside an inequality check.

2. **Preserve the floor's stated purpose.** `CLAUDE.md` §8's rule — an empty or
   shrunken extraction must be an error, never an input — must still hold, and
   the existing instruction to lower the constant only for a deliberate,
   reviewed removal must survive whatever you choose.

3. **Verify the current count yourself** rather than trusting this issue. Three
   derivations agree it is 22 at `e4a29b6`, but a fourth is cheap and this
   lineage has had six false premises corrected by measurement.

4. **Prove the guard still fails when it should.** Removing a variable read from
   the loader must trip it. A guard never seen to fail is not a guard
   (`CLAUDE.md` §8); mutate a copy rather than the tree where practical.

5. **Check whether sibling guards carry the same shape** — an exact-count claim
   in prose beside an inequality assertion. If any do, name them here; do not
   fix them in this pass unless trivial.

## Review notes

**Verdict: approve.** Criterion 1's first option — drop the count, keep the
floor — is the right choice here, and the reasoning given for it holds. A
floor's contract is one-sided by construction, so a sentence next to it
claiming an exact total is asserting something the mechanism beside it never
evaluates. Pinning equality was correctly rejected: it converts the guard from
"did the extraction work" into "has the variable set changed", which is a
different check with a different owner, and it would put a required edit in
this file on the path of every future loader variable. The rewritten prose
leaves no room to misread the number as a census — it says outright that it
names no current count on purpose and that the constant is the only number
that has to stay accurate.

**What the two constants now mean.** `minLoaderVariables` claims that the AST
walk in `TestEnvExampleCoversLoaderVariables` still finds at least that many
distinct variable-name literals in `config.go`. `minScannedEnvExampleAssignments`
claims that the line scan behind `TestEnvExampleValuesAvoidDivergentParserShapes`
still recognises at least that many assignment-shaped lines in `.env.example`.
Neither claims to equal today's total, neither is a census of what the loader
reads, and neither will notice growth — that is the design, per `CLAUDE.md` §8's
rule that a shrunken or empty extraction must be an error rather than an input.
Both comments keep that rationale and both keep the instruction to lower the
constant only for a deliberate, reviewed removal, so criterion 2 is satisfied.

**Criterion 3, re-derived independently.** Ran the same AST walk from a
standalone program against the working tree — parse `config.go`, collect every
call whose first argument is a string literal matching the guard's
variable-name shape — and got 22, with the names enumerated. That is the fifth
derivation and it agrees with the four before it. The same program measured
`.env.example` at 22 assignment-shaped lines by the scanner's own regex.

**Criterion 4, reproduced in a throwaway worktree** rather than the shared tree,
so no concurrent agent's work was ever at risk (`CLAUDE.md` §8a). Two separate
mutations, not one: renaming a variable read so the name literal stops matching,
and deleting the read outright. Both produced the same failure, and both
restored byte-identically by SHA-256. The guard fails on a genuine removal, not
only on a rename.

**Where I land on leaving the sibling constant at 20: leave it.** The slack is
real — measured, not assumed: removing two assignment lines from `.env.example`
leaves that floor untripped, and the third removal trips it. But the slack
cannot produce a silent loss, because both paths out of it are already closed.
If `.env.example` alone shrinks, `TestEnvExampleCoversLoaderVariables` fails
loudly and names the missing variables, which was confirmed by running the
package under exactly that mutation. If `.env.example` and the loader shrink
together — a genuine deliberate removal — `minLoaderVariables` has zero
headroom and trips first. So the "lower it only for a reviewed removal"
instruction still has teeth; it is enforced by the sibling floor rather than by
this one. Bumping it to 22 would be mechanically safe, since the synthetic
fixture in `TestScanEnvExampleValueShapes_DetectsEachDivergentShape` sizes
itself from the constant and hardcodes no line numbers, but it would buy no
protection that is not already there. That makes it a tightening preference
rather than a defect, and criterion 5's "name, don't fix" default covers it.

**The historical narrative in both comments checks out**, which matters because
this issue is about prose beside a guard going stale unnoticed. `#0428` set the
loader floor at 20; `#0433` added a variable and took the real count to 21
without a bump; `#0402` raised the constant to 22 while adding another. The
sibling's claim that its own prose *drifted* rather than being wrong at birth is
also true, and it is not deducible from the issue numbers, since `#0441`
introduced that constant before either of the two commits that grew the file
past it. Confirmed by ancestry and by counting `.env.example` at the commit that
introduced the constant, where it was exactly 20.

**On the `internal/outbox` call I was asked to check: the implementer's
distinction is real, and its worked example is still accurate.**
`claimKindsGuardMinPlausibleNonExemptCallSiteCount` describes a margin analysis
rather than a bare "the floor equals today's total" claim, so it is not the same
shape. Re-measured every figure in it with the guard's own scan roots, prune
rules, and name matcher: 12 non-exempt sites, split 5 in `internal/handlers` and
7 in `internal/mailing`, of which 4 are the unrelated same-named method the
comment already flags as supplying the entire margin, leaving 3 genuine calls
and a population of 8 if that collision ever went away. Every one of those
matches. Leaving it untouched was correct.

**One thing to file, found while checking that.** The *other* floor in that same
file carries a genuine instance of this issue's defect: its comment states a
measured total for a full scan over its roots, and the real figure is now three
higher, all three of the new sites being in-package additions. It went unnoticed
for the same reason this issue documents — the floor is far below either number,
so nothing could complain. It also feeds a second claim in the same comment,
the stated gap between that count and the external grep oracle's, which moves
with it. Not fixed here, per criterion 5 and the rule that subagents report
issues rather than filing them.

**One process note, not a defect in the change.** The implementer's verification
run scoped to `internal/config` and `internal/db`, but this change edits Go doc
comments, and `CLAUDE.md` §5 routes any Go comment edit through
`internal/handlers` as well — that package owns the citation-guard family and
the guard that catches a doc comment naming a different declaration in the same
file, which is a live concern here since one of these two comments deliberately
names the other constant. My own run below adds that package, and it is clean,
so nothing was actually broken; the scoping rule was simply not applied.
