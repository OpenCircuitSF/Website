## Description

**The green outline must never appear on a page title** — or on any other
non-interactive text that the app moves focus to. Not after a click, not after
keyboard navigation, not on back/forward, not in any browser or either theme.
That is the whole requirement (user, 2026-09-12).

Reported after clicking the header's home link: the home page's title,
"Hands-on electronics workshops", was outlined in the brand green.

## Why it happens — two rules, not one

On every client-side navigation, `#0238`'s route-change `$effect` in
`web/src/App.svelte` calls
`document.querySelector('h1[tabindex="-1"]')?.focus({ preventScroll: true })`,
so a screen reader announces the new page. Two rules in `web/src/app.css` then
paint that focused heading green:

1. `h1[tabindex='-1']:focus` — a 2px `--accent` outline. This is what showed
   after a mouse click. `#0238` used plain `:focus` deliberately, because Safari
   does not grant `:focus-visible` to programmatic focus.
2. `:where(a, button, summary, [tabindex]):focus-visible` — the global
   focus-ring rule. **It also matches the heading, because the heading has a
   `tabindex`.** Browsers grant `:focus-visible` to moved focus when the last
   interaction was a keypress, so after pressing Enter on a nav link this rule
   draws the same green ring. **Deleting rule 1 alone does not fix the issue.**

Every `<h1 tabindex="-1">` in `web/src` is affected. Measured with `grep` on
2026-09-12, that is **25 headings across 18 views**: Home, About, Workshops, a
workshop detail page, Archive, an archive entry, Subscribe, Subscribe-thanks,
Privacy Policy, Preferences, Unsubscribe, Confirm, Not Found, Login,
Register-verify, Recover-verify, **Account, and Admin**. The list above in this
issue originally named only nine of them; it was incomplete.

**Seen by the user on 2026-09-12, in Safari, on `/account`:** a thick green box
around the **"Open Circuit SF"** title at the left of the Account/Admin header,
which reads as a navigation link. That title is
`<h1 class="app-title" tabindex="-1">` in both `Account.svelte` and
`Admin.svelte`, so moving between Account and Admin focuses it on every switch —
this is the most visible instance of the defect and must be fixed.

Separately, the **active tab** in that header ("Account" or "Admin") is drawn in
green text by `.nav-tab.active`. That is the active-tab indicator, not a focus
outline, and is not in scope unless the user asks for it.

Four views also give their own in-page focus targets a green `:focus` outline,
and **these are in scope too** — each is non-interactive text the app moves
focus to:

- `Unsubscribe.svelte` — `.headline:focus`
- `ConfirmSubscription.svelte` — `.confirm-shell h1:focus`
- `PreferenceCenter.svelte` — `.result-message:focus`
- `Login.svelte` — `.sub-section p.text-notice:focus`

## What stays

- **The focus move itself.** Keep every `.focus()` call and every
  `tabindex="-1"`: moving focus is what announces a navigation or a result to a
  screen reader (`#0238`, `#0063`). Only the visible outline goes.
- **`preventScroll: true`.** Its absence broke back/forward scroll restoration
  once already, and `web/src/lib/appNavigationFocus.structuralGuard.test.ts`
  pins it.
- **Focus rings on real controls** — links, buttons, inputs, `select`,
  `textarea`, `summary`, and the skip link. Keyboard users need those. The fix
  for rule 2 is to **exclude non-interactive `tabindex="-1"` focus targets from
  it**, not to remove or weaken it for controls.

This is defensible for accessibility: WCAG 2.4.7 (Focus Visible) applies to
keyboard-operable components, and a `tabindex="-1"` heading or message is
neither in the tab order nor operable. Record that in the comment at the
changed rules, citing `#0238`'s original Safari reasoning, so nobody restores the
outline as a "fix".

## Acceptance criteria

1. **No page title shows a green outline, ever** — including the "Open Circuit
   SF" title in the Account and Admin headers. **Re-derive the list of affected
   headings from the code** (`grep -rnE '<h1[^>]*tabindex="-1"' web/src`), not

2. **The four in-page focus targets listed above show no outline either**, in the

4. ~~Links, buttons, inputs, `select`, `textarea`, `summary`, and the skip link

## Review notes

Reviewed as one batch with #0535 (Opus, 2026-09-12). Verdict: approve, with

**Defect fixed in review (`d170f68`).** `0a7deaf` took every `tabindex="-1"`
target out of the shared `:focus-visible` accent rule, but only the h1 rule
(and the four component rules) actively set `outline: none`. Any other
`tabindex="-1"` element that the app focuses fell back to the browser's own
focus ring. That includes two headings, CampaignEditor's `h2.editor-heading`
and `h3.preflight-heading`, and every modal dialog container. Measured in
Chromium 151 after keyboard navigation, the ring was `auto 1px
rgb(0, 95, 204)` (blue). Safari tints the same ring with the macOS accent
colour, which a user can set to green. Against the bar "never on any heading",
that is a hole. The fix is a zero-specificity `:where([tabindex='-1']):focus
{ outline: none }` rule in `app.css`, placed next to the h1 rule. It is still
author origin, so it beats the browser's stylesheet, and it outranks no
component rule.

**Guard strengthened (same commit).** The generic `<h1 tabindex="-1">` test

must actively set `outline: none`. Checked in a private worktree:

## Work log

Implemented together with #0535 (same CSS problem, shipped as one batch).

- `web/src/app.css`: `h1[tabindex='-1']:focus` now sets `outline: none`
  (was `2px solid var(--accent)`), with an added Correction comment
  explaining that #0238's Safari `:focus`-vs-`:focus-visible` reasoning is
  unchanged, only the declaration changed. The shared
  `:where(a, button, summary, [tabindex]):focus-visible` rule now reads
  `:where(button:not(.nav-tab):not(.subtab), summary,
  [tabindex]:not([tabindex='-1'])):focus-visible` — excluding every
  `tabindex="-1"` target from the accent ring (not just `<h1>`), and
  excluding `.nav-tab`/`.subtab` (which are real `<button>`s and would
  otherwise still match the `button` clause even after being excluded from
  the new link rule below). A new rule,
  `:where(a, .nav-tab, .subtab):focus-visible { outline: none;
  text-decoration-line: underline !important; ... }`, gives links and the
  link-like nav controls a non-green, non-outline keyboard indicator
  instead. `!important` is used here (the only use in the file) because
  several components set `a { text-decoration: none }` at higher
  specificity than a bare `:where(...)` rule, unlike `outline`, which
  nothing else in the codebase sets.
- The four in-page `:focus` rules (`Unsubscribe.svelte` `.headline`,
  `ConfirmSubscription.svelte` `.confirm-shell h1`,
  `PreferenceCenter.svelte` `.result-message`, `Login.svelte`
  `.sub-section p.text-notice`) each changed from `outline: 2px solid
  var(--accent); outline-offset: 2px;` to `outline: none;`, each with a
  Correction comment pointing back at `app.css`'s `h1[tabindex='-1']:focus`
  for the fuller reasoning.
- Added `web/src/lib/focusOutline.guard.test.ts` (20 tests): parses
  `app.css` (via `node:fs`, not `?raw` — see the test's own comment for why
  a `.css?raw` import silently resolved to an empty string under Vitest)
  and every `.svelte` file's `<style>` block (via `import.meta.glob`),
  extracts every rule whose selector contains `:focus`/`:focus-visible`,
  and matches each one's *structural* selector (the pseudo-class stripped)
  against real DOM candidates using jsdom's native `Element.matches()`.
  Asserts: no visible outline on any `tabindex="-1"` target (the generic
  heading, a generic non-h1 element, and the four named in-page targets);
  no accent or other visible outline on `<a>`/`.nav-tab`/`.subtab`, each of
  which must show an underline instead; ordinary buttons, `summary`, and
  form fields (`input`/`select`/`textarea`) keep their existing
  accent-based indicator; and two DOM-behaviour assertions that `.focus()`
  still lands (`document.activeElement`) on a `tabindex="-1"` heading and
  on each of the four named targets despite `outline: none`.
- Added `postcss` as an explicit `web/` devDependency (it was already

- Correction added to this issue's own criterion 4 (struck through, dated):
