# 0517 — Client-side navigation paints a green focus outline on the page title

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web / accessibility |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-12 |

## Description

Reported 2026-09-12: clicking the header's home link lands on the home page with
the page title highlighted in the brand green. The highlight is unwanted.

**It is the page's `<h1>`, not the header link.** The brand link
(`web/src/lib/Header.svelte`, `.brand-link`) carries no `aria-current` and no
active style. What turns green is the view's heading — on the home page,
`<h1 id="home-headline" class="headline" tabindex="-1">Hands-on electronics
workshops</h1>` (`web/src/views/Home.svelte`).

The chain:

1. `#0238`'s route-change `$effect` in `web/src/App.svelte` runs on every
   client-side navigation — a link click, `navigate()`, or `popstate` — and
   calls `document.querySelector('h1[tabindex="-1"]')?.focus({ preventScroll: true })`.
2. `web/src/app.css` draws a ring on exactly that element:

       h1[tabindex='-1']:focus {
         outline: 2px solid var(--accent);
         outline-offset: 2px;
       }

3. `--accent` is the brand green.

So **every route whose `<h1>` carries `tabindex="-1"`** does this, not only the
home page: Home, Workshops, a workshop detail page, Archive, Subscribe,
Subscribe-thanks, Privacy Policy, Preferences, and Login.

A fresh page load does not show it, because `#0238`'s effect deliberately skips
the first render. That is why it appears only after clicking around.

## Why it was built this way

`#0238` chose plain `:focus` rather than `:focus-visible` on purpose, and the
comment above the rule records why: **Safari does not reliably grant
`:focus-visible` to a programmatic `.focus()`**, so the ring would otherwise be
invisible exactly when the effect fires. That was a deliberate accessibility
decision, and this issue reverses its visible half. The decision should be made
explicitly, not by quietly deleting a rule.

## What must NOT change

- **The focus move itself stays.** Moving focus to the heading is what makes a
  client-side navigation announce itself to a screen reader (`#0238`). Removing
  the ring must not remove the `.focus()` call or the `tabindex="-1"`.
- **`preventScroll: true` stays.** Its absence destroyed back/forward scroll
  restoration once already (`#0238`'s bounce), and
  `web/src/lib/appNavigationFocus.structuralGuard.test.ts` pins it.
- **Interactive elements keep their focus rings.** The global
  `:where(a, button, summary, [tabindex]):focus-visible` rule serves keyboard
  users on real controls, and `--accent` is used there because it is the token
  clearing 3:1 in both themes (`CLAUDE.md` §8). Do not weaken that rule to fix
  this one.

## The accessibility argument, for the record

WCAG 2.4.7 (Focus Visible) concerns keyboard-*operable* components. A heading
with `tabindex="-1"` is neither in the tab order nor operable: it is a landing
point for programmatic focus, and suppressing its outline is a common,
defensible pattern. The cost is small but real — a sighted keyboard user loses
the visual cue of where focus landed after navigating. Record that trade-off in
the replacement comment so the next reader does not "restore" the ring as a
regression fix.

## Acceptance criteria

1. After a client-side navigation to any route, the page's `<h1>` shows **no**
   green outline or other focus decoration.
2. `document.activeElement` is still that `<h1>` after navigation — the focus
   move is intact. Assert this, don't assume it.
3. Keyboard focus rings on links, buttons, inputs, `summary`, and the skip link
   are unchanged.
4. Scroll restoration on back/forward is unchanged, and
   `appNavigationFocus.structuralGuard.test.ts` still passes unmodified.
5. **Decide the scope of the in-view state-swap focus targets explicitly**, and
   record the decision. These use the same pattern for a different purpose —
   announcing a result that replaced a form, not a navigation:
   `Unsubscribe.svelte`'s `.headline:focus`, `ConfirmSubscription.svelte`'s
   `.confirm-shell h1:focus`, `PreferenceCenter.svelte`'s
   `.result-message:focus`, and `Login.svelte`'s `.sub-section p.text-notice:focus`.
   The report covers the page title on navigation; the default is to leave these
   alone, but say so.
6. The comment at the changed rule explains why the outline is suppressed and
   cites `#0238`'s original reasoning, following `issues/Issues.md`'s correction
   convention rather than deleting the old explanation.
7. **Verified in a real browser**, Safari and one Chromium-based browser, in both
   themes. jsdom does not paint outlines, so a jsdom test alone cannot prove
   criterion 1 — say which each claim rests on. No test currently pins the
   `h1[tabindex='-1']:focus` rule, so nothing will fail on its own when it
   changes.
8. `scripts/check.sh web` passes.
