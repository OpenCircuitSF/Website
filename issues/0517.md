# 0517 — Remove the green focus outline from page titles and focus-landing text

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web / accessibility |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-12 |

## Description

**The green outline must never appear on a page title** — or on any other
non-interactive text that the app moves focus to. Not after a click, not after
keyboard navigation, not on back/forward, not in any browser or either theme.
That is the whole requirement (user, 2026-09-12).

Reported after clicking the header's home link: the home page's title,
"Hands-on electronics workshops", was outlined in the brand green.

## Why it happens — two rules, not one

On every client-side navigation, `#0238`'s route-change `$effect` in
`web/src/App.svelte` calls
`document.querySelector('h1[tabindex="-1"]')?.focus({ preventScroll: true })`,
so a screen reader announces the new page. Two rules in `web/src/app.css` then
paint that focused heading green:

1. `h1[tabindex='-1']:focus` — a 2px `--accent` outline. This is what showed
   after a mouse click. `#0238` used plain `:focus` deliberately, because Safari
   does not grant `:focus-visible` to programmatic focus.
2. `:where(a, button, summary, [tabindex]):focus-visible` — the global
   focus-ring rule. **It also matches the heading, because the heading has a
   `tabindex`.** Browsers grant `:focus-visible` to moved focus when the last
   interaction was a keypress, so after pressing Enter on a nav link this rule
   draws the same green ring. **Deleting rule 1 alone does not fix the issue.**

Every route whose `<h1>` has `tabindex="-1"` is affected: Home, Workshops, a
workshop detail page, Archive, Subscribe, Subscribe-thanks, Privacy Policy,
Preferences, and Login.

Four views also give their own in-page focus targets a green `:focus` outline,
and **these are in scope too** — each is non-interactive text the app moves
focus to:

- `Unsubscribe.svelte` — `.headline:focus`
- `ConfirmSubscription.svelte` — `.confirm-shell h1:focus`
- `PreferenceCenter.svelte` — `.result-message:focus`
- `Login.svelte` — `.sub-section p.text-notice:focus`

## What stays

- **The focus move itself.** Keep every `.focus()` call and every
  `tabindex="-1"`: moving focus is what announces a navigation or a result to a
  screen reader (`#0238`, `#0063`). Only the visible outline goes.
- **`preventScroll: true`.** Its absence broke back/forward scroll restoration
  once already, and `web/src/lib/appNavigationFocus.structuralGuard.test.ts`
  pins it.
- **Focus rings on real controls** — links, buttons, inputs, `select`,
  `textarea`, `summary`, and the skip link. Keyboard users need those. The fix
  for rule 2 is to **exclude non-interactive `tabindex="-1"` focus targets from
  it**, not to remove or weaken it for controls.

This is defensible for accessibility: WCAG 2.4.7 (Focus Visible) applies to
keyboard-operable components, and a `tabindex="-1"` heading or message is
neither in the tab order nor operable. Record that in the comment at the
changed rules, citing `#0238`'s original Safari reasoning, so nobody restores the
outline as a "fix".

## Acceptance criteria

1. **No page title shows a green outline, ever.** Verify each of these, on every
   affected route:
   - after a mouse click on a link;
   - after keyboard navigation (Tab to a link, press Enter);
   - after back and forward;
   - after clicking directly on the heading text;
   - on a fresh page load.
2. **The four in-page focus targets listed above show no outline either**, in the
   states where each receives focus.
3. `document.activeElement` is still the heading (or the in-page target) after
   each focus move. The focus move is intact — assert it.
4. Links, buttons, inputs, `select`, `textarea`, `summary`, and the skip link
   still show their `--accent` ring on keyboard focus.
5. Back/forward scroll restoration is unchanged, and
   `appNavigationFocus.structuralGuard.test.ts` passes unmodified.
6. **A test pins this**, since nothing does today: it fails if any stylesheet
   rule would give a non-interactive `tabindex="-1"` focus target a visible
   outline — including via the global `[tabindex]:focus-visible` rule — and
   fails if the control rings are removed. Prove it fails against the current
   `app.css`.
7. **Verified in real browsers** — Safari and one Chromium-based browser, both
   themes — for every case in criteria 1 and 2. jsdom does not paint outlines, so
   state which claims rest on a browser.
8. `scripts/check.sh web` passes.
