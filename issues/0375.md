## Description

`#0366` added a second-identifier count/reason pair to
`claimCommentGuardDirectionalCalibrationCases`, gated on `c.secondIdent != ""`.

**A future row that sets `wantSecondIdentFindings: 1` but forgets
`secondIdent` asserts nothing and passes.**

**Latent today**: no such row exists, and both assertions are live on the one
row that uses them — `#0366`'s reviewer verified the pair fires in both
directions on that row, including a reason-only mutation.

This is the family's signature failure one more time: an assertion that passes
because it never ran. `#0358` shipped a row whose fixture never entered the
axis; `#0363` shipped one whose fixture always fired; `#0364` exists because a
row can get its number for the wrong mechanism. This is the **skipped**
variant.

## The recommendation this issue carries

`#0366`'s reviewer recommended **recording, not closing**, and named the cost:
the one-`if` fix would be a **seventh in-file check** in a file `#0258`'s
caution now binds explicitly — six mechanisms already, each new one fresh
mutable surface.

**So the default deliverable is one honest sentence.** If a pass believes the
guard earns its place, it must argue why this differs from `#0330`, `#0347` and
`#0356`, which all ended by refusing exactly this trade — and be prepared for
the argument to be rejected.

There is a cheaper third option worth weighing: state the invariant in the
struct's own doc comment so the omission is visible at the point of authoring a
row, rather than adding a runtime check.

## Review notes

**Verdict: resolved.**

**Recording rather than closing was right, and the third option was the right
one of the three.** The one-`if` fix would be a seventh in-file mechanism in a
file `CLAUDE.md` §8's `#0258` caution binds, two `#0366` reviews declared this
family terminated, and the failure mode is an *authoring* mistake — so the
field documentation, read at exactly the moment a row is written, is a better
place for it than a runtime check that fires after the fact.

**Criterion 1 — the record says the right thing, plainly.** On
`claimCommentGuardDirectionalCalibrationCase`'s field documentation, adjacent
to the three fields it governs: "`wantSecondIdentFindings` and
`wantSecondIdentReason` are ONLY asserted when `secondIdent` is non-empty. A
future row that sets `wantSecondIdentFindings` (and/or `wantSecondIdentReason`)
while leaving `secondIdent` "" asserts NOTHING". It names the mechanism (the
`if c.secondIdent != ""` guard in
`TestClaimCommentGuardDirectionalAxisCalibrationTable`), says the row *passes*
regardless of what the fields say, distinguishes latent from live, and closes
with the actionable instruction — set `secondIdent` first, because an empty one
is not "no claim", it is "a claim that silently goes unchecked".

**Criterion 2 — premise reproduced independently, in a throwaway `git
worktree` at `c775d6b` (§8a/§8b), never the tracked tree.**

- *The omission is silent.* Inserted a 25th row named "REVIEW0374r probe:
  forgotten secondIdent asserts nothing" carrying the real
  `every-distinct-identifier` fixture, `secondIdent` left at its zero value,
  and a pair that is false twice over — `wantSecondIdentFindings: 99` (real
  answer: 0) and `wantSecondIdentReason: claimCommentGuardReasonMarkerExempt("above")`
  (real answer: resolved/`below`). `go test -run
  TestClaimCommentGuardDirectionalAxisCalibrationTable -v`:
  `--- PASS: …/REVIEW0374r_probe:_forgotten_secondIdent_asserts_nothing`.
  Passes while asserting nothing, exactly as recorded.
- *The existing row's pair fires in **both** directions.* With the probe row
  still present, two separate targeted mutations of the real
  `every-distinct-identifier` row, each applied to a fresh copy:
  - `wantSecondIdentFindings` `0` → `1` — FAIL naming that row,

    FAIL naming that row, `want {…resolved:false} got {…resolved:true}`.

  In both runs the probe row (still `secondIdent: ""`) kept passing. So the
  silence is specific to the forgotten `secondIdent`, not a general weakness in
  the pair — which is what the record claims. The reason half's
  discrimination is re-proved here directly rather than inherited from
  `#0366`'s review, which the implementer had chosen not to repeat.
