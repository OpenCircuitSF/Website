## Description

`#0150` fixed `scripts/testdb.sh gc`, which swept every agent's test database
because sweeping was the default. Its criterion 5 asked whether any other script
has the same shape — an unqualified destructive default that assumes the caller
is alone. **`scripts/db-reset.sh` does.**

A bare invocation targets the shared `opencircuit` (or `opencircuit_test`)
database, runs `pg_terminate_backend` against **every other connection to it**,
then drops and recreates it. No live-connection skip, no confirmation prompt.

It is the same class of bug as `#0150`, moved from the per-agent pool onto the
single shared name — and the blast radius is larger, because that database is
the user's dev database as well as the fallback any agent uses when it cannot
get its own (`CLAUDE.md` §5a). One agent's reflexive reset destroys another
agent's in-flight work *and* whatever the user had loaded.

**What it already gets right, and should keep:** it refuses non-localhost hosts
and refuses database names outside `opencircuit*`. Production is protected. The
gap is peer agents and the user, not production.

**But that name guard is wider than it looks.** `#0150`'s review read the script
and found the `opencircuit*` glob admits **`opencircuit_test_0055`** — so
`scripts/db-reset.sh opencircuit_test_0055` destroys another agent's per-agent
scratch database. That is precisely the `#0150` failure, reached through a
different script, and it is not hypothetical: per-agent databases are exactly
what `CLAUDE.md` §5a tells every agent to create. `$DB` is also interpolated
into the SQL unquoted.

**Nothing runs the standalone guard tests automatically.** There are now
**two** — `scripts/testdb_gc_guard_test.sh` (`#0150`) and
`scripts/dev_guard_test.sh` (`#0117`) — and `scripts/check.sh` invokes neither.
Each protects a safety property only when someone remembers it exists. Whatever
guard this issue adds needs a way to actually run, or it has the same problem
the day after it lands, and there will be three.

`#0117`'s third review measured the constraint that shapes the answer:
`dev_guard_test.sh` costs ~48s and binds `:5173`, so it does not belong in every
`check.sh` run. A `check.sh guards` target, or a documented command in
`docs/dev.md`, is the likelier fit.

**Two smaller findings from the same sweep**, recorded here rather than
separately:

- `scripts/sim.sh` defaults `OUTPUT_PATH` to the fixed shared `/tmp/opencircuit-sim.png`, so two agents running with default arguments silently overwrite each other's screenshot. Low blast radius, same hazard class as the port-8099 incident in `docs/obstacles.md` §4.
- `scripts/deploy.sh` was checked and is **fine** — single production target, an interactive `[y/N]` gate before the one destructive step, `mktemp` rather than a fixed path. Assuming solitude is correct for a production deploy. Recorded so nobody re-audits it.

`scripts/dev.sh` has the same shape and is already filed as `#0117`.

Two nits in `#0150`'s guard test, worth fixing while modelling on it: Part 2
writes its capture to a PID-suffixed `/tmp` path instead of the `$WORKDIR` it
already owns, and `createdb_raw` discards `CREATE DATABASE` errors — so a role
missing `CREATEDB` surfaces as a loud but **misdiagnosed** "REGRESSION #0150".

**A one-line hardening in `scripts/dev.sh`, folded in here.** `#0117`'s third
review found `cleanup()`'s `GO_FP` guard does not reject an **empty start
time**, unlike `is_owned` which does. If `go run` died between `GO_PID=$!` and
`GO_FP=…`, `GO_FP` becomes `"<pid>:"` and at shutdown `[ "<pid>:" = "<pid>:" ]`
matches — so `kill`/`pkill -P` run against a pid that is no longer ours. The
review verified the match happens.

Not reachable in practice: it needs a sub-millisecond death plus pid recycling
(~99k forks on macOS), and the readiness poll turns that case into
`ERROR: Go server exited unexpectedly` first. But `is_owned` already rejects
exactly this shape, so the two guards should agree.

## Acceptance criteria

- [ ] A bare `db-reset.sh` does not terminate connections it does not own — it refuses, reports what holds the database, and points at the safe alternative, the way `testdb.sh gc` now does
- [ ] Some explicit opt-in (a flag, matching `gc --all`) is required to force a reset that kicks other connections
- [ ] The existing non-localhost and non-`opencircuit*` refusals still hold — demonstrated, not assumed
- [ ] A guard test covers the refusal and the forced path, modelled on `scripts/testdb_gc_guard_test.sh`, including a mutation proving the refusal assertion is not vacuous
- [ ] The guard test operates only on databases it creates, under a prefix no real issue id can produce (`CLAUDE.md` §8b)
- [ ] `sim.sh`'s default output path is namespaced per invocation, or the collision is recorded as accepted
- [ ] A per-agent database name (`opencircuit_test_NNNN`) is refused by `db-reset.sh`, or requires the same explicit opt-in — demonstrated by attempting one
- [ ] `$DB` is not interpolated into SQL unquoted
- [ ] This guard test and the two existing ones (`scripts/testdb_gc_guard_test.sh`, `scripts/dev_guard_test.sh`) are all reachable from a command someone actually runs, or the gap is recorded as accepted
- [ ] `cleanup()`'s `GO_FP` guard rejects an empty start time, matching `is_owned`
- [ ] `CLAUDE.md` §5a's description of `db-reset.sh` matches the new behaviour

## Implementation notes

**`scripts/db-reset.sh`** — two new refuse-by-default guards, both liftable
with an explicit `--force`:

- **Name scope.** The old `opencircuit*` glob admitted anything starting
  with `opencircuit`, including a per-agent scratch database like
  `opencircuit_test_0055`. The script now accepts exactly `opencircuit` and
  `opencircuit_test` (the two it actually manages) without `--force`; any
  other `opencircuit*` name — including the per-agent shape — requires
  `--force` and gets a message pointing at `scripts/testdb.sh` (drop/list),
  which is the tool that actually owns that pool. A name not starting with
  `opencircuit` at all is refused unconditionally, exactly as before.
- **Live connections.** A bare invocation now queries
  `pg_stat_activity` for other connections to the target database before
  doing anything destructive. If any exist, it refuses, lists each one's
  pid/user/application/client address, and points at `--force` — the same
  shape `#0150` settled on for `testdb.sh gc`. Only with `--force` (or when
  there genuinely are no other connections) does it proceed to
  `pg_terminate_backend` + drop + recreate.
- **`$DB` hardening.** Added a strict identifier-charset check
  (`[A-Za-z0-9_]` only) before any of the name-scope logic runs, rejecting
  outright rather than silently stripping bad characters (silently editing
  the name could point the script at a different database than intended).
  The `DROP DATABASE`/`CREATE DATABASE` statements now double-quote `"$DB"`
  as a Postgres identifier instead of interpolating it bare.
- The unconditional, unliftable guards (non-localhost `PGHOST_URL`) are
  unchanged — per the issue, production reachability is the one thing that
  must never have an opt-in.

**`scripts/db_reset_guard_test.sh`** (new) — modeled directly on
`scripts/testdb_gc_guard_test.sh` (`#0150`), including its two nits this
issue asked to fix while modeling on it: captures go to `$WORKDIR` (a
`mktemp -d` this script owns), not a PID-suffixed `/tmp` path, and every
`psql`/`sed` step that can fail is checked rather than swallowed. Covers the
bare-refusal path, the `--force` path, a mutation proof that the refusal
guard is load-bearing, the pre-existing host/name-prefix/charset refusals,
the per-agent-name-needs-`--force` criterion, and a static check that `$DB`
is never interpolated unquoted into a `DROP`/`CREATE DATABASE` statement.
All destructive work runs against one throwaway database name,
`opencircuit0207gt` — starts with `opencircuit` (so it would need `--force`
under the real script's name guard) but has no underscore after
`opencircuit`, so it can never collide with `testdb.sh`'s
`opencircuit_test_<id>` naming scheme, and `gt` is not a digit sequence any
real issue id produces. Exercised via a private, untracked copy of
`db-reset.sh` with its name allowlist widened by one alternative (same
technique `testdb_gc_guard_test.sh` uses for `testdb.sh`'s `PREFIX`), written
into `scripts/` itself rather than `/tmp` — `db-reset.sh` resolves its own
repo root from `dirname "${BASH_SOURCE[0]}"/..`, so a copy outside
`scripts/` resolves `REPO` wrong and can't find `migrations/` (the same
gotcha `dev_guard_test.sh`'s header documents for `dev.sh`).

**`scripts/check.sh guards`** (new mode) — runs all three standalone shell
guard tests (`testdb_gc_guard_test.sh`, `dev_guard_test.sh`,
`db_reset_guard_test.sh`) in sequence. This is the "reachable from a command
someone actually runs" fix the issue asked for: `#0117`'s third review had
already measured `dev_guard_test.sh` alone at ~48s and binding `:5173` in
several parts, so folding it into `go`/`web`/`all`/the default was rejected
as the wrong fit — `guards` is its own opt-in mode instead, costing nothing
on the common path. Documented in `check.sh`'s own header and in `CLAUDE.md`
§5 and §5a.

**`scripts/dev.sh`'s `GO_FP` guard** — `cleanup()` now captures
`proc_start "$GO_PID"` once into `go_start` and requires it non-empty before
comparing against `$GO_FP`, matching `is_owned()`'s existing
`[ -n "$s" ] || return 1`. Previously, if `go run` died between `GO_PID=$!`
and `GO_FP=…` being captured, `GO_FP` became `"<pid>:"` (empty start-time
half) and could match a *currently* empty `proc_start` result the same way,
letting `kill`/`pkill -P` run against a pid this run no longer owns.

**`scripts/sim.sh`** — `OUTPUT_PATH` now defaults to
`/tmp/opencircuit-sim-$$.png` (namespaced by the run's own pid) instead of
the fixed `/tmp/opencircuit-sim.png`, so two agents running `sim.sh` with
default arguments no longer silently overwrite each other's screenshot.
`docs/dev.md` updated to match (both the options table and the worked
example).

**`CLAUDE.md`** §5 gained the `scripts/check.sh guards` line in the command
reference; §5a gained a new bullet describing `db-reset.sh`'s new
refuse-by-default behavior, its name-scope restriction, and where to find
all three guard tests — the same place `testdb.sh gc`'s equivalent note
already lives.

## Verification

**`db-reset.sh` manual smoke test** (before writing the automated guard,
against a scoped throwaway name, never `opencircuit`/`opencircuit_test`):
- Non-localhost `PGHOST_URL` → refused, exit 1.
- A database name containing `; DROP DATABASE x` → refused for an unsafe
  character, exit 1 (before any SQL ever runs).
- `opencircuit_test_0207demo` (per-agent-shaped) without `--force` → refused
  with the `scripts/testdb.sh drop/list` pointer, exit 1.
- `notopencircuit` → refused, exit 1 (unchanged prefix guard).
- Via a private scoped copy admitting `opencircuit0207gt`: created it
  cleanly with `--no-seed`; held a `pg_sleep(20)` connection open; a bare
  reset refused and the connection survived; `--force` reset succeeded and
  the connection was gone afterward (`kill -0` on its pid failed).

**`scripts/db_reset_guard_test.sh`**, run standalone twice in a row (to
confirm repeatability/cleanup) and once more inside `scripts/check.sh
guards`: **all runs — 0 failures**, 15 `PASS` lines covering setup, the bare
refusal + survived connection, `--force`'s successful reset + terminated
connection, the mutation proof (refusal guard removed → bare invocation
kills the connection again, confirming Part 1 isn't vacuous), the
pre-existing host/name-prefix/charset refusals, the per-agent-name
requiring `--force`, the static unquoted-`$DB` check, and a final
byte-identity check confirming the tracked `scripts/db-reset.sh` was never
touched (sha256 identical before/after every run). `scripts/testdb.sh list`
and a direct `pg_database` query showed zero leaked
`opencircuit0207gt*`/`opencircuit_test_0150gt_*` databases after each run.

**`scripts/check.sh guards`**, full run: **VERIFICATION PASSED**, exit 0.
All three guard suites reported all-clear —
`testdb_gc_guard_test.sh: all guards hold (0 failures)`,
`dev_guard_test.sh: all guards hold (0 failures)`,
`db_reset_guard_test.sh: all guards hold (0 failures)` — with the `#0208`
pipefail self-check passing first and no leftover processes at the end.

**`dev_guard_test.sh`**, run standalone in the background twice (once to
confirm `web/vite.config.ts`'s unrelated `#0214` change didn't regress it,
once after the `GO_FP` fix): **8/8 parts passed both times**, 0 failures,
byte-identity confirmed (`scripts/dev.sh` untouched by its own mutation
testing).

**Go/web suites unaffected**: `ISSUE=0207final scripts/check.sh go
./internal/... ./cmd/... ./web/...` — **VERIFICATION PASSED**, 16 Go
packages `ok`, zero skips (this issue touches only shell scripts and docs,
so this run is a regression check, not new coverage).

**Shell hygiene**: `bash -n` clean on every touched script
(`check.sh`, `db-reset.sh`, `dev.sh`, `sim.sh`, `db_reset_guard_test.sh`,
`testdb.sh`). `shellcheck` on each: `db-reset.sh` has one pre-existing-style
info (`SC2001`, matches `testdb.sh`'s own established style for the same
construct); `dev.sh` and `sim.sh` are clean; `db_reset_guard_test.sh` has
two intentional `SC2016` infos (single-quoted `sed`/`grep` patterns that
must NOT expand) plus three `SC2329` infos for functions invoked indirectly
via the `EXIT` trap, matching `dev_guard_test.sh`'s own established
suppression style.

**Cleanup**: every scratch database created during this work — the manual
smoke-test's `opencircuit0207gt`, the guard test's own (created/dropped
automatically per run), `opencircuit_test_0207final` — was dropped;
`scripts/testdb.sh list` at the end shows only `opencircuit_test_template`.
`pgrep -fl 'go test|\.test '` and a `lsof` check on `:5173`/`:8080` showed
nothing left running at multiple points during the work.
