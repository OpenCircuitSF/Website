## Description

`#0372`'s tree-wide survey found three further tests using the hardcoded-id
shape §8b forbids, all outside the pending/resend family it was scoped to fix:

| Site | Test | Literal target |
|---|---|---|
| `internal/handlers/admin_subscribers_import_test.go:172` | `TestAdminImports_NonAdminForbidden` | `/admin/imports/1/revoke` |
| `internal/handlers/admin_subscribers_import_test.go:471` | `TestAdminImports_Revoke_RequiresReason` | `/admin/imports/1/revoke` |
| `internal/handlers/admin_workshop_announce_test.go:286` | `TestAdminWorkshopAnnounce_NonAdminForbidden` | `/admin/workshops/1/announce` |

~~**The third is the sharpest**: a real `announce` sends **campaign email**. Anyone
mutating that auth guard to prove the test discriminates — the standard method
this phase has used on every other assertion — fires an announcement at whatever
workshop id 1 happens to be.~~

**Correction (#0376, 2026-09-01).** The struck claim is wrong, and the review
re-verified it against the code rather than against this prose.
`AdminWorkshopsHandler.Announce` (`internal/handlers/admin_workshop_announce.go`)
calls exactly three things — `h.store.GetByID`, `h.campaigns.Create`, and
`h.auditor.Record` — and `mailing.CampaignStore.Create`
(`internal/mailing/campaigns.go`) is a single `INSERT INTO email_campaigns`
plus its `campaign_interests` rows, landing at `status` default `'draft'`
(`migrations/000017_create_campaigns.up.sql`). Nothing on this path calls
`Send` or writes `outbound_queue`. The announce route is a **compose
shortcut**, which its own package doc comment states as binding ("nothing
here, or anywhere in this file, ever calls Send"). So the worst a
guard-removal proof against a *real* workshop id could have done is create
one extra draft campaign row — not send campaign email. The hardcoded id
was still the §8b defect this issue correctly fixed; only the severity
framing was overstated.

`#0372` proved the hazard is not theoretical. In an isolated export with the
guard removed, it sent an unauthenticated POST and confirmed against Postgres
that `invite_resent_at` was **burned** on the target row. It was safe only
because the target was a throwaway row it had seeded.

**§8b exists because of exactly this**: `#0024`'s guard-removal proof aimed a
`DELETE` at a hardcoded `/admin/interests/1` and permanently destroyed a seeded
taxonomy row.

**Not every hardcoded id is a hazard.** The same survey found
`interests_test.go`, `admin_campaigns_test.go` and `users_test.go` already using
a nonexistent sentinel (`99999999` / `999999`), which is safe — the request
cannot reach a real row. The defect is a **small, plausibly-real** id on a route
with a side effect.

## Acceptance criteria

1. All three tests seed a throwaway row and target **its** id, or use a
   nonexistent sentinel where the test's meaning does not require the row to
   exist. Say which you chose per test and why — they are not equivalent: a
   sentinel proves the guard fires before lookup, a seeded row proves it fires
   before the side effect.
2. **Prove each still discriminates** by mutating the auth guard — which is safe
   once the target is throwaway or nonexistent. That proof is the deliverable;
   these are currently three assertions nobody can safely check.
3. §8b: mutations run against **your own database**
   (`ISSUE=NNNN scripts/check.sh`), never the shared `opencircuit_test`.
4. **Do not send real email.** The announce route is the reason this issue
   exists. If proving criterion 2 on that test would enqueue or send anything,
   stop and report rather than proceeding — §9 makes the send worker's
   `physical_address` refusal non-bypassable, and `MAILER_NOOP` is refused
   outside localhost (§10).
5. Re-verify the survey yourself rather than trusting this table — re-run a
   tree-wide scan for the shape and report anything it finds beyond these three.
   **Five issues this phase received a wrong identifier because prose was
   transcribed as though measured**, two of them in issues the orchestrator
   wrote.
6. Per §5 name the specific tests that ran; `go build` passing is not
   verification. `gofmt` stability on every file touched.

## Fix

All three tests now target a **nonexistent sentinel id**, not a seeded
throwaway row — for all three, the assertion's own boundary fires strictly
*before* any lookup reaches the store, so seeding a real row would prove
nothing a sentinel doesn't already prove, and a sentinel is simpler and
categorically safer (§8b: "never target a literal or seeded id"). Confirmed
by direct read of each guard's code, not by assumption:

1. **`TestAdminImports_NonAdminForbidden`** (line 172) — the revoke
   sub-assertion. `RequireAdmin` sits in `adminImportsMux`'s middleware
   chain ahead of `AdminImportsHandler.Revoke`; it runs and answers 403
   before the handler parses `{id}` or touches the store. Changed
   `/admin/imports/1/revoke` → `/admin/imports/999999999/revoke`.
2. **`TestAdminImports_Revoke_RequiresReason`** (line 471) — read
   `admin_subscribers_import.go`'s `Revoke` directly: the `reason ==
   ""` check (lines 487–491) runs and returns 400 *before* line 495's
   `h.store.Revoke` call. Changed the same literal to
   `/admin/imports/999999999/revoke`.
3. **`TestAdminWorkshopAnnounce_NonAdminForbidden`** (line 286) — same
   shape as #1: `RequireAdmin` guards `AdminWorkshopsHandler.Announce`
   before `h.store.GetByID` runs. Changed `/admin/workshops/1/announce` →
   `/admin/workshops/99999999/announce`, the same sentinel
   `TestAdminWorkshopAnnounce_UnknownWorkshopNotFound` already uses two
   tests above it in the same file.

Each test's doc comment now states which guard it targets and why a
sentinel (not a seeded row) is the right choice, so the next reader does
not reintroduce a literal id.

**Criterion 4's stop condition did not fire, and the reasoning is recorded
in test 3's own doc comment.** Read `admin_workshop_announce.go` directly
before touching anything: `Announce` calls exactly one store method,
`mailing.CampaignStore.Create`, which only `INSERT`s one `email_campaigns`
row (status `draft`) and replaces its `campaign_interests` rows — it never
calls `Send`, never touches `outbound_queue`. The package doc comment says
so explicitly ("nothing here, or anywhere in this file, ever calls
Send"), and `TestAdminWorkshopAnnounce_PrefillAndLink` in the same file
already asserts `Status == draft`. So unlike `#0372`'s
`invite_resent_at` hazard, a guard-removal proof against this route was
never capable of sending real email — the issue's framing ("a real
`announce` sends campaign email") overstates the danger of this specific
route, in the same harmless direction #0372's reviewer flagged for its own
comment. The sentinel id still fully avoids even the harmless side effect
(a draft row), since a mutated guard on `/admin/workshops/99999999/announce`
hits `workshops.ErrNotFound` before `Create` is ever called — confirmed by
the mutation proof below.

**Criterion 2 — the discrimination proof**, run in an isolated `git stash
create` → `git archive` export (CLAUDE.md §8b), against a dedicated scratch
database (`opencircuit_test_0376mut`, provisioned by direct `migrate up`
through `000026` since the shared template is stale per `#0360`) — never
the shared tree, never the shared database.

Baseline first, unmutated: all three tests pass.

Two guards, mutated independently, each verified to have found and changed
exactly one match before drawing any conclusion (mirroring `#0372`'s
method):

- `internal/middleware/auth.go`'s `RequireAdmin` — the `if !u.IsAdmin {
  403 }` block removed (this is the single guard behind both #1 and #3;
  neither handler carries a second admin check). `u` discarded to keep the
  build green.
- `internal/handlers/admin_subscribers_import.go`'s `Revoke` — the
  `reason == ""` 400 check removed, keeping the `reason :=` assignment
  used later for the audit entry and the store call.
- Also removed the **second, defense-in-depth** copy of the same check in
  `internal/subscribers/imports.go`'s `ImportStore.Revoke` (the
  `ErrRevokeReasonRequired` guard) — required for #2's proof: with only the
  handler-level check removed, the test still passed, because the store
  independently re-validates `reason == ""` before beginning its
  transaction. Both layers had to come out together for the assertion to
  fail, which is itself evidence the reason check is genuinely
  defense-in-depth, not dead code.

The `404`s in all three failures are exactly the safety proof: with every

nothing was created, enqueued, or touched, which is the concrete version of
"the sentinel is safe" rather than an inference from the status codes
alone.

the whole suite stays green (the store layer is pinned separately by
`internal/subscribers/imports_test.go`'s `ErrRevokeReasonRequired`
assertion). That is not a defect in this diff and not a behavioural risk —
both layers produce the same status and message, and the store's check runs
before any database work — but the doc comment this diff adds asserts a
boundary (handler returns 400 "before it ever calls `h.store.Revoke`") that
the test itself does not demonstrate. Reported to the orchestrator as a
candidate follow-up rather than fixed here; it is outside this issue's
scope, which was the hardcoded id.
