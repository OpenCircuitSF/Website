## Description

The interest taxonomy is data, not a Go enum — new workshop themes appear constantly and adding one must not require a deploy.

> 🟢 Resolved 2026-08-19 — Reviewer re-verified independently in a throwaway `opencircuit_rev0025` database: the `interests` table matches PRD §6.2 column for column (no additions beyond the `interests_slug_format` CHECK, which backs the issue's own "lowercase, hyphenated" criterion), all twelve seeded slugs and names are byte-identical to §6.1 in its listed order, `up` → `down 1` → `down 1` leaves version 8 with no orphaned table, index, sequence, constraint, or type, and the seed is idempotent (re-running the block against a seeded, admin-edited table inserted 0 rows, overwrote nothing, left 12 distinct slugs); two mutation proofs reproduced (dropping `interests_slug_format` and re-running `TestDB_SlugFormatConstraint` fails on all four malformed slugs, restoring it passes).

## Root cause

Greenfield feature work, not a bug: nothing existed yet. The interest taxonomy needed a table (not a Go enum, per PRD §6.1) plus a Go store package for the admin CRUD (`#0024`) and the subscribe endpoint (`#0026`) to build on.

## Fix

Added `migrations/000009_create_interests.{up,down}.sql`: the `interests` table with a `slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'` CHECK constraint (`interests_slug_format`) backing the "lowercase, hyphenated" requirement at the database level (not just in Go), a `UNIQUE` constraint on `slug`, and the twelve PRD §6.1 rows seeded via `INSERT ... ON CONFLICT (slug) DO NOTHING` in `sort_order` 10, 20, … 120 (matching the PRD's listed order).

Added `internal/interests/store.go`: `Store` over `*pgxpool.Pool` with `ListActive` (active=TRUE, ordered by sort_order/name, for the public signup form), `ListAll` (for `#0024`'s admin screen), `GetBySlug`, `GetByIDs` (bulk resolve for validating a signup form's selected ids), `Create` (validates slug format in Go before hitting the DB, mapping a unique violation to `ErrDuplicateSlug`), `Update` (name/description/sort_order/active — slug is immutable through this method, since a future issue can add a dedicated rename path if the preference-center-link-breakage tradeoff is ever revisited), and `Deactivate` (sets `active = FALSE`, never deletes — per the issue's notes, `subscriber_interests` rows must keep referencing it).

Numbered `000009` ahead of the subscribers migration (`000010`, `#0025`) because `subscriber_interests` carries a foreign key to `interests`; recorded in the migration's own header comment and in `docs/database.md`.

## Gotchas

- The interests table carries seed data from the migration itself, unlike the purely structural `subscribers`/`subscriber_interests` tables. Test cleanup can't `TRUNCATE interests` the way `internal/auth`'s tests truncate their tables — that would wipe the seed for every other package's test run. Tests here instead scope their own rows under a `zz-test-` slug prefix and delete exactly those rows in `t.Cleanup`.
- `Update` deliberately does not allow changing `slug`. A signup-confirmation or preference-center link that ever embedded a slug (none currently do — everything keys off numeric interest ids) would break silently on rename; leaving slug immutable avoids the question entirely until a real need for renaming appears.



PRD §6.1, §6.2. Seed in the migration rather than in `seed` so a fresh database is immediately usable and the list is identical across environments.

Deactivating an interest must not delete it — existing `subscriber_interests` rows reference it and the historical record matters. `active = false` hides it from the signup form while preserving associations.
