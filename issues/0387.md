## Description

`#0381` landed a table in `CLAUDE.md` §5 naming the **seven packages that own
repo-wide guards** and the scan roots each one reads. Agents will use it to
decide which packages a scoped verification must include.

**Nothing checks it.** If a guard's scan root changes, or a package gains or
loses one, the table goes stale silently — the same drift shape §11's PRD-index
guard exists to catch, and the same shape `#0356`, `#0370` and `#0384` were all
filed for.

Found by `#0381`'s third review, which **deliberately declined to propose it**:
that issue's criteria 3 and 4 chose recording over mechanism, and proposing a
guard inside it would have contradicted its own settled decision. It is recorded
here so the risk is tracked rather than lost.

## The argument on each side, so this is decided rather than defaulted

**For building it**: §11 already has exactly this guard for the PRD section
index (`TestPRDSectionIndexParity`), and that guard exists because the table
drifted twice — §6.2 across two commits with neither pass noticing, and §14
wrong from birth. The §5 table is **load-bearing in the same way**: an agent
following a stale row runs the wrong package and concludes clean, which is
precisely the 18-minute red HEAD that produced `#0381`.

**Against**: `#0381` weighed and rejected mechanism, on measured timings — the
slow packages cost ~8× the fast ones, and widening every scoped run buys
protection only when an edit lands in a scan root. A parity guard is a
*different* mechanism from that one and does not inherit the rejection
automatically, but §8's `#0258` case is six passes of adding checks, and three
guard families this phase (`#0330`, `#0347`, `#0356`) ended by recording a limit
rather than closing it.

**A middle option worth weighing**: guard only the **package set** (cheap,
stable, and the half whose staleness misroutes an agent) and leave the scan-root
prose unguarded, recording that limit explicitly.

## Acceptance criteria

1. The choice is made explicitly and its reason recorded **in the table's own
   surrounding prose**, not only in this issue.
2. **If building**: the guard derives both sides from source — the package set
   and roots from the guards themselves, the table from `CLAUDE.md` — and **the
   oracle must not be a copy of the answer stored next to the question** (§8).
   `#0356`'s line-citation guard and §11's index guard are the models.
3. **If building: prove it discriminates.** Change one row's scan root and
   confirm the guard fails naming that row; add a fake repo-wide guard to a
   package not in the table and confirm it fails too. **A check that cannot fail
   pins nothing** — `#0354`, `#0358` and `#0363` each shipped exactly that this
   phase, and `#0364` exists because an assertion can pass for the wrong reason.
4. **If recording**: say precisely what is unguarded and what a reader should do
   about it, without overstating what the table establishes. Five issues bounced
   this phase for prose claiming more than the code delivers.
5. **Re-derive the seven-package set and its roots yourself** before trusting the
   table as a fixture. It took four derivations to settle — the fourth dynamic,
   measuring what the built binaries actually opened, which produced **zero**
   out-of-package reads for the other ten packages. Do not treat the table as
   ground truth for a guard whose job is to check the table.
6. Run `./internal/db/...` **and** `./internal/handlers/...` — both own
   repo-wide guards over `CLAUDE.md`, which is the rule this issue is about
   (`#0381`). Per §5 name the specific tests that ran. No `<file>.go:<int>`
   citation in any comment (`#0352`). `gofmt` stability.

### Why the middle option, and not the other two

**Why not the full parity guard.** Half the table is not machine-checkable. The
`Reaches into` cells are prose written for a human router — "every `internal/*`
package `servePostgres` imports, parsed for `*seo.Site` flow", "**the whole repo
tree** — ... walks the repo root for the set of citable paths and reads
`CLAUDE.md`'s own `##` section headings". Comparing that against source requires
first rewriting the column into a machine-readable path list, which would
destroy the routing guidance three review rounds of `#0381` tuned specifically
so an agent can act on it. The reader needs that prose more than the guard does.
So "build the parity guard" as criterion 3 imagines it — failing and *naming the
row* when a scan root changes — is not actually available at acceptable cost.

**Why not recording alone.** The against-case rests on `#0381`'s rejection and
on §8's `#0258`. Neither transfers:

- `#0381` rejected **widening every scoped run** — a recurring cost on every run
  forever, ~8× on a small package, buying protection only when an edit lands in
  a scan root. This is a different trade in every dimension: one assertion in
  the *cheapest* package (`internal/db`, ~0.4s), costing milliseconds, firing
  only when the table is actually wrong. `#0381`'s own third review said as much
  — "whether the table earns one later is a separate decision, not a defect in
  this one."
- §8's `#0258` shape is **in-file self-checks defending the file they live in**,
  where each new mechanism became surface the next edit could shadow. This is
  the opposite shape: the oracle is Go AST over test source, the subject is
  markdown prose in a different file in a different language, and no single edit
  satisfies both.
- `#0330`, `#0347` and `#0356` each recorded rather than built because the gap
  was a knowledge gap with **no cheap sound oracle available**. Here a cheap
  sound oracle exists for exactly one half of the table — and it is the half
  whose staleness produces the failure this issue exists for: an agent omits a
  package, sees green, leaves `HEAD` red.

**What decides it** is the asymmetry between the two halves. A stale
`Reaches into` cell misdescribes *why* a package is on the list; a missing
**row** makes an agent skip the package entirely and conclude clean. Only the
second reproduces `#0381`'s 18-minute red `HEAD`, and only the second is cheaply
checkable. Guard that half; say plainly that the other half is not guarded.

### The guard

`TestClaudeMDRepoWideGuardPackageSetParity`, in a new
`internal/db/claude_md_guard_table_parity_test.go`.

**Table side** — `os.ReadFile("../../CLAUDE.md")`, locate the table whose header
row is `| Package | Reaches into |`, and collect the backtick-quoted identifier
from each row's first cell. Two structural requirements, both from §8:

- Assert that header appears **exactly once** in the file. A second copy would
  let a decoy table shadow the real one, which is the failure `GUARD-0208`
  closes; the header is unique today, and §11's index table uses a different
  header so there is no collision.
- Assert the parse produced a non-empty set before comparing. An empty
  extraction must be an error, never an input — §8's `#0258` fail-open.

**Source side** — for every directory under `internal/` and `cmd/` holding at
least one `_test.go`, parse each test file with `go/parser` and walk the AST
for either detector:

1. a STRING `*ast.BasicLit` whose value contains `..` and which, resolved
   against that package's directory, escapes it;
2. a call to `runtime.Caller`, or an `os.Getwd` feeding a `filepath.Dir` chain —
   the repo-root idiom, which is the only way `internal/subscribers` appears.

Use the **AST, not a regex**. That excludes comments for free, which matters
immediately: this guard's own doc comment will quote example paths like
`"../../PRD.md"` to explain itself, and a regex oracle would count them.

**Assertion** — the two sets are equal, with a failure message naming the
offending packages in each direction and saying which side to change: a package
present in source but absent from the table means *add the row*; present in the
table but absent from source means *the reach was removed, drop the row*.

**Floor** — assert the scan visited a plausible number of test files and
packages, per the repo's `assertGoFileVisitCountPlausible` convention, so a scan
that silently walks nothing fails closed. Measured at `HEAD` for sizing, to be
**re-measured by the implementer rather than transcribed**: 157 `_test.go` files
across 17 test packages under `internal/` and `cmd/`. Set the floor well below
those, since they only ever grow.

**Why the oracle is not a copy of the answer** (criterion 2): the expected set
is never written down. One side is read out of `CLAUDE.md`'s live markdown, the
other is computed from the live Go AST. There is no third place holding
`{internal/handlers, internal/db, ...}` for the two to agree with. An edit to
the table changes one side only; an edit to a test package's source changes the
other side only.

### Proving it discriminates, and where the proof lives

Criterion 3's first mutation — change a row's scan root, expect a named failure
— **is out of scope by construction** and must not be claimed. The two mutations
that do apply, both run against a `git archive HEAD | tar -x` throwaway copy
outside the repo (§8a — never the live tree, and `#0340`'s agent is mid-flight):

- **M1, table side.** Delete `internal/seo`'s row from §5's table in the copy.
  The guard's table set becomes six, the source set stays seven, and the guard
  must fail **naming `internal/seo`**.
- **M2, source side.** Add to `internal/audit` a test doing
  `os.ReadFile(filepath.Join("..", "..", "PRD.md"))`. The source set becomes
  eight, the table set stays seven, and the guard must fail **naming
  `internal/audit`**. This is criterion 3's "fake repo-wide guard in a package
  not in the table".
- **M3, control.** The unmutated copy passes.

**The proof belongs in Go, and only in Go.** §8's test is whether the mutation
leaves the assertion falsifiable by the thing it measures. Under M1 the
guard's own computed table set moves from seven to six; under M2 its own
computed source set moves from seven to eight. In both cases the measured value
itself changes, so the in-package test is a legitimate, non-circular oracle —
the same footing as mutating scan roots rather than forcing a floor to zero.

Considered and declined, deliberately, since §8 notes the two homes are not
exclusive: an external `scripts/*_guard_test.sh` harness. The mutation it would
buy is the degenerate one — rewriting the guard so both sides derive from the
same source, whereupon it agrees with itself. That is not `#0258`'s one-line
decoy shadowing a definition; it requires rewriting the test's purpose, which is
equally true of `TestPRDSectionIndexParity` and every other Go guard here.
Adding a harness whose subject is this guard is precisely the "seventh in-file
check buys a seventh bounce" shape, arriving from the outside. Recorded, not
built.

### Where it lives, and why `internal/db`

Both `internal/db` and `internal/handlers` already own repo-wide guards over
`CLAUDE.md`, so the choice needs a reason:

1. §11's `TestPRDSectionIndexParity` — this issue's named precedent, the same
   artifact class in the same file — lives in `internal/db`.
2. `internal/db`'s `docs_parity_test.go` already reads `../../CLAUDE.md` and
   row-parses its tables, so the table-reading half has an existing convention
   to follow rather than invent.
3. It is the **cheap** package (~0.4s against `internal/handlers`' ~5-6s).
   `#0381` spent its whole decision protecting §5a's cheap-scoped-run default;
   taxing the expensive package instead would erode the same thing by a
   different route.
4. §5's routing sentence already sends every `CLAUDE.md` edit to `internal/db`,
   so the guard runs on exactly the edit that can invalidate it.

Adding it does not change `internal/db`'s own table row — that row already
claims the repo root. The implementer must confirm the new file's own
`"../../CLAUDE.md"` literal keeps `internal/db` in the source set (it does) and
that the new file introduces no eighth package.

### What stays unguarded — criterion 4 applies to the recorded half

To be written into §5's surrounding prose, stated at exactly the strength the
code delivers and no more:

- **The package column is checked; the `Reaches into` column is not.** A guard
  whose scan roots narrow or widen without changing *which package owns it*
  leaves its row stale and nothing will say so. When you change a guard's scan
  roots, update its row by hand.
- **The routing sentence beneath the table is not checked either.** `#0381`'s
  third review already recorded that it names four of the table's routable edit
  kinds and that the table, not the sentence, is the authority. That stands.
- **The source-side detector has a blind spot**: a reach assembled from a path
  with no `..` literal and no `runtime.Caller`/`os.Getwd` root resolution — an
  environment variable, say, or an absolute path — is invisible to it. Measured
  at `HEAD`, no package does this; the guard cannot see one if it appears.

The claim the prose may make is therefore: *the set of packages named here is
checked against source on every `internal/db` run; the description of what each
one reaches is not.*

## Obstacles

Per §5b. Three are real; none blocks dispatch.

1. **A live git worktree sits inside the repo tree, and a repo-root scan walks
   into it.** `git worktree list` shows
   `.claude/worktrees/agent-a16d8f8a64eadf32f` — a full second copy of the tree,
   gitignored but present on disk. My first derivation pass rooted at the repo
   root and duly reported a *duplicate* set of seven reaching packages under
   that path. **Mitigation, and it is a design constraint on the guard, not a
   nuisance**: root the source-side scan at `internal/` and `cmd/`, never at the
   repo root. Clears itself if the worktree is removed, but must not be relied
   on to be absent.
2. **Editing `CLAUDE.md` requires running two packages**, per §5's own table:
   `internal/db` and `internal/handlers`. Step 4 above edits §5's prose, so both
   must run. Do not renumber or delete any `##` heading — that fails
   `internal/handlers`' `TestNoCommentCitesUnresolvedPathOrSection` while
   `internal/db` passes clean, which is the precise trap `#0381`'s second review
   was bounced on.
3. **A concurrent agent holds `internal/mailing`, `internal/subscribers`,
   `internal/outbox` and `issues/0340.md` dirty.** The guard's source side scans
   those packages. All three are already table rows, so new escaping literals
   there cannot break the guard — but `git status` before verifying, and
   attribute any unrelated failure before blaming the change (§8a: touch none of
   them).

Checked and clear: `psql`, `migrate` and `npm` all present; no credential is
needed; no port is bound; the databases are healthy at migration 27 and clone in
~0.2s. `scripts/testdb.sh` is owned by another session, so use only
`ISSUE=NNNN scripts/check.sh` and never `template` or `db-reset.sh`.

## Root cause

Not a bug fix — this issue closes a gap. CLAUDE.md §5's repo-wide-guard table
(from `#0381`) had no mechanism checking it against source, so a package
gaining or losing a repo-wide reach could leave the table's package column
stale with nothing to say so — reproducing `#0381`'s own 18-minute red `HEAD`
(an agent's scoped verification skips a package it should have run, sees
green, moves on).

## Fix

Built the middle option the plan settled on: a parity guard over the table's
**package column only**, in `internal/db`
(`internal/db/claude_md_guard_table_parity_test.go`,
`TestClaudeMDRepoWideGuardPackageSetParity`), plus prose in CLAUDE.md §5
itself — immediately after the table — stating precisely what is guarded (the
row set) and what is not (each row's `Reaches into` text, and the routing
sentence beneath the table).

Two independently-computed sides, neither a copy of the other: the table side
reads CLAUDE.md's live markdown (asserting the `| Package | Reaches into |`
header appears exactly once, and that the parse yields at least one row); the
source side walks `../../internal` and `../../cmd` (never the repo root, to
avoid double-counting through the live `.claude/worktrees/` git worktree) and
parses every `_test.go` file's Go AST — not a regex, since this guard's own
doc comment quotes example paths a regex oracle would wrongly count — for
either an escaping `..` string-literal path segment or the
`runtime.Caller`/`os.Getwd` repo-root idiom `internal/subscribers` uses
(literal-only detection finds six packages, not seven, without it). A visit
floor (100 files / 12 dirs against a measured 157 files / 17 dirs at `HEAD`)
fails the scan closed if the roots are ever silently emptied or narrowed.

Deliberately **not built**: a full parity guard covering each row's
`Reaches into` prose or the routing sentence beneath the table (unavailable
at acceptable cost — see `## Plan`), and an external `scripts/*_guard_test.sh`
harness for the discrimination proof (considered and declined per the plan;
the proof lives in Go, in the guard test itself, because both mutations move
its own measured value).

### What was independently re-verified, and passed

**Criterion 5 — the seven-package set, re-derived by a seventh method.** Not
`go/parser`: a hand-written Go lexer in Python that strips comments, collects
interpreted and raw string literals separately from code text, and segment-tests
each literal's *decoded value* for a `..` component, then separately greps the
comment-stripped code for `runtime.Caller`, `os.Getwd`, `os.Chdir`,
`packages.Load` and `build.Default`. Over all 17 test-holding directories under
`internal/` and `cmd/` (158 `_test.go` files today), it reports exactly seven
reaching packages, matching the table row for row: `cmd/opencircuit`,
`internal/db`, `internal/handlers`, `internal/mailing`, `internal/outbox`,
`internal/seo`, `internal/subscribers`. The other ten show zero escaping
literals *and* zero occurrences of any file-reading or root-resolving idiom.

**The `internal/subscribers` trap is real and I confirmed it two ways.** Its


### Not blocking — worth a line if you are in the file anyway
