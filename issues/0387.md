## Description

`#0381` landed a table in `CLAUDE.md` §5 naming the **seven packages that own
repo-wide guards** and the scan roots each one reads. Agents will use it to
decide which packages a scoped verification must include.

**Nothing checks it.** If a guard's scan root changes, or a package gains or
loses one, the table goes stale silently — the same drift shape §11's PRD-index
guard exists to catch, and the same shape `#0356`, `#0370` and `#0384` were all
filed for.

Found by `#0381`'s third review, which **deliberately declined to propose it**:
that issue's criteria 3 and 4 chose recording over mechanism, and proposing a
guard inside it would have contradicted its own settled decision. It is recorded
here so the risk is tracked rather than lost.

## The argument on each side, so this is decided rather than defaulted

**For building it**: §11 already has exactly this guard for the PRD section
index (`TestPRDSectionIndexParity`), and that guard exists because the table
drifted twice — §6.2 across two commits with neither pass noticing, and §14
wrong from birth. The §5 table is **load-bearing in the same way**: an agent
following a stale row runs the wrong package and concludes clean, which is
precisely the 18-minute red HEAD that produced `#0381`.

**Against**: `#0381` weighed and rejected mechanism, on measured timings — the
slow packages cost ~8× the fast ones, and widening every scoped run buys
protection only when an edit lands in a scan root. A parity guard is a
*different* mechanism from that one and does not inherit the rejection
automatically, but §8's `#0258` case is six passes of adding checks, and three
guard families this phase (`#0330`, `#0347`, `#0356`) ended by recording a limit
rather than closing it.

**A middle option worth weighing**: guard only the **package set** (cheap,
stable, and the half whose staleness misroutes an agent) and leave the scan-root
prose unguarded, recording that limit explicitly.

## Acceptance criteria

1. The choice is made explicitly and its reason recorded **in the table's own
   surrounding prose**, not only in this issue.
2. **If building**: the guard derives both sides from source — the package set
   and roots from the guards themselves, the table from `CLAUDE.md` — and **the
   oracle must not be a copy of the answer stored next to the question** (§8).
   `#0356`'s line-citation guard and §11's index guard are the models.
3. **If building: prove it discriminates.** Change one row's scan root and
   confirm the guard fails naming that row; add a fake repo-wide guard to a
   package not in the table and confirm it fails too. **A check that cannot fail
   pins nothing** — `#0354`, `#0358` and `#0363` each shipped exactly that this
   phase, and `#0364` exists because an assertion can pass for the wrong reason.
4. **If recording**: say precisely what is unguarded and what a reader should do
   about it, without overstating what the table establishes. Five issues bounced
   this phase for prose claiming more than the code delivers.
5. **Re-derive the seven-package set and its roots yourself** before trusting the
   table as a fixture. It took four derivations to settle — the fourth dynamic,
   measuring what the built binaries actually opened, which produced **zero**
   out-of-package reads for the other ten packages. Do not treat the table as
   ground truth for a guard whose job is to check the table.
6. Run `./internal/db/...` **and** `./internal/handlers/...` — both own
   repo-wide guards over `CLAUDE.md`, which is the rule this issue is about
   (`#0381`). Per §5 name the specific tests that ran. No `<file>.go:<int>`
   citation in any comment (`#0352`). `gofmt` stability.
