## Description

`opencircuit seed` must idempotently ensure the `ADMIN_EMAIL` user exists and is pre-authorized as admin, so a fresh deployment has a way in.

> 🟢 Resolved 2026-08-18 — The seed command already met every acceptance criterion (`#0001` copied it, `#0002` stripped the shortener test link); this pass documented the command and the non-obvious "Recover account, not Register" first login in `docs/deployment.md` and rewrote a doc comment that still called the finished implementation a placeholder.

## Root cause

Not a bug — `#0001`'s scaffold copy already carried a `cmd/opencircuit/seed.go`
derived from ShortLinks' `seed.go`, and `#0002` had already correctly stripped
`ensureTestLink` (this project has no `links` table). The remaining behavior —
insert-or-promote the `ADMIN_EMAIL` row to an active admin via
`ON CONFLICT (email) DO NOTHING` + `UPDATE ... RETURNING id`, idempotent on
re-run — already matched every acceptance criterion. The file's own doc
comment called it "a minimal placeholder pending #0010," which overstated how
much was missing.

## Fix

No functional code changes were needed. Two things were genuinely missing and
are fixed here:

1. **`docs/deployment.md`** had no seed-command documentation at all — grepped
   and confirmed zero mentions of "seed" or "recover" before this change. Added
   a "Bootstrap admin (`opencircuit seed`)" section covering what the command
   does, its idempotency, and the non-obvious "use Recover account, not
   Register" first-login step (mirrors ShortLinks `DEPLOYMENT.md` step 6,
   per the issue's Notes).
2. **`cmd/opencircuit/seed.go`'s doc comment** called the implementation "a
   minimal placeholder pending #0010." Rewrote it to describe the finalized,
   intentionally-narrower-than-ShortLinks behavior (no test link, no interest
   taxonomy — that's `#0023`'s migration) instead of flagging it as unfinished.

## Gotchas

- The acceptance criterion "creates the `ADMIN_EMAIL` user ... if no users
  exist" reads as a conditional, but the implementation (matching ShortLinks'
  step 6 exactly) always upserts `ADMIN_EMAIL` toward `is_admin = true,
  active = true` regardless of whether other users already exist — it does not
  literally gate on `SELECT COUNT(*) FROM users = 0`. This is intentional:
  gating on "no users exist" would make `seed` a one-shot operation that
  silently does nothing on every subsequent run against a database that
  already has other (non-admin) users, which contradicts the "re-running is a
  no-op and exits 0" criterion read as "safe/idempotent," not "only works
  once." Flagging this reading for the reviewer in case the literal wording
  was intended differently.
- **Reviewer ruling on that reading (2026-08-18): accepted.** "Creates the
  `ADMIN_EMAIL` user ... if no users exist" is satisfied in intent by an
  unconditional upsert toward `is_admin = true, active = true`. A literal
  `COUNT(*) = 0` gate would be strictly worse: it would make `seed` a
  one-shot that silently does nothing on the exact populated-database case an
  operator runs it for (locked out, admin row present but demoted or
  deactivated), and it matches neither ShortLinks `DEPLOYMENT.md` step 6 nor
  the "re-running is a no-op and exits 0" criterion's convergence reading.
  Two consequences worth having on the record for `#0064`'s runbook: run
  against a populated production database, `seed` touches **only** the
  `ADMIN_EMAIL` row (verified — the `INSERT ... ON CONFLICT DO NOTHING` and
  the `UPDATE ... WHERE email = $1` are both single-row and no other user is
  read or written), and it will **silently re-promote and re-activate that
  one account** if an admin had deliberately demoted or deactivated it,
  writing no `audit_log` row while doing so. That is the same trust boundary
  as `psql` (both need shell access plus `DATABASE_URL`), so it is not a new
  privilege path, but it should be stated in the runbook.
- **Reviewer note — one cheap assertion is missing.** `TestSeedIdempotent`
  proves the id is stable and exactly one row exists across two runs, but it
  never reads `is_admin` or `active` back, so the first acceptance criterion
  ("with `is_admin = true`") — and the promote-an-existing-row semantics
  defended just above — rest on inspection of the SQL, not on a test. Not a
  blocker (the SQL sets both columns literally and `go vet`/build/tests are
  green), but a two-line `SELECT is_admin, active` assertion would pin the
  behavior against a future edit. Worth folding into whichever later pass
  next touches `cmd/opencircuit/seed_test.go`.
