`workshops.capacity` has no server-side range check anywhere. `migrations/000020:26` declares a bare `capacity INT`, and neither `Create` nor `Patch` validates the value. Only the browser rejects non-positive numbers, so any client that does not go through the admin SPA can store nonsense:

- `-1` and `0` are accepted and stored (200)
- anything above 2³¹−1 returns **500**, from a Postgres `INT` overflow, rather than a 400

Found by `#0146`'s phase-3 review while probing that issue's new `Optional[int]` wire type with nonsense inputs. It confirmed the behavior is **pre-existing and unchanged** by `#0146` — the old `*int` did exactly the same — so it is filed separately rather than folded in.

A 500 on a value the client controls is the part worth fixing regardless of what is decided about negative capacities: it turns a bad request into an apparent server fault, and it is the shape of thing that shows up in error monitoring as a mystery.

## Root cause

`workshops.capacity` (`migrations/000020:26`, a bare `capacity INT`) had no
range check anywhere on the write path. `createWorkshopRequest.Capacity` and
`patchWorkshopRequest.Capacity`'s merge (`Optional[int]`, from `#0146`) both
passed whatever the client sent straight through to
`workshops.Store.Create`/`Update` unexamined. Two distinct failure shapes
followed from the same gap: `-1`/`0` stored cleanly with a 200 (nothing ever
rejected them), and anything above `2147483647` blew past Postgres's `INT`
column range at the driver layer, which the handler's generic `default:`
error branch mapped to a bare 500 — a client-controlled bad value surfacing
as an apparent server fault. The database itself carried no constraint on
the column either, so even a caller that bypassed the handler entirely (a
direct `INSERT`/`UPDATE`, a future import path) could park a row in the same
nonsense states.

## Fix

Added `isValidCapacity(v int) bool` (`internal/handlers/admin_workshops.go`):
`v >= 1 && v <= 2147483647`. `Create` checks `req.Capacity` (when non-nil)
before calling the store; `Patch`'s existing `Optional[int]` merge switch
checks `req.Capacity.Value` only in the `default` case (present *and*
valid, i.e. a real number was sent) — the `!Present` ("leave alone") and
`!Valid` ("explicit null: clear it") branches are untouched, so the range
check applies exactly to the "set it" state and never interferes with the
three-state clear/leave-alone contract `#0146` built. Both reject with a
400 and `capacityErrorMessage`, never a stored value.

**The `0` decision, made deliberately per the issue's own instruction:**
`0` is **rejected**, not treated as "no capacity limit." `NULL` already owns
that meaning end-to-end — `workshopView.Capacity` is `*int` with
`json:"capacity,omitempty"`, so a nil capacity is simply absent from the
response, and nothing in this codebase's read path (public listing,
admin UI) ever gives a *present* zero a special "unlimited" meaning. Letting
`0` mean the same thing as `NULL` would create two wire spellings of one
idea with no way to tell, from the stored column alone, which one a given
row's author meant — exactly the kind of ambiguity `Optional[T]`'s own
three-state design (`#0146`) exists to avoid elsewhere. Rejecting `0` keeps
`NULL` the single, unambiguous "no limit" representation. (Separately, `0`
is not a meaningful capacity for a workshop in this domain either — nobody
runs a session with room for nobody — but the wire-representation argument
above is the deciding one even setting that aside.)

**Database CHECK**, added to `migrations/000020` in place (greenfield,
`CLAUDE.md` §1 — no version bump, since an in-place edit isn't a new
migration):

```sql
ALTER TABLE workshops
    ADD CONSTRAINT workshops_capacity_check
    CHECK (capacity IS NULL OR (capacity >= 1 AND capacity <= 2147483647));
```

The upper bound is technically redundant — Postgres's `INT` column type
already can't hold anything larger — but it's written out explicitly so the
constraint documents the intended range on its own, without requiring a
reader to know `INT`'s limit by heart.

**`docs/database.md`** picked up a matching clause on the `000020` migration
row, alongside the existing `workshops_status_check` note, for the same
reason that one is documented there — nothing mechanically requires it (see
"Obstacle" below), but the file already describes every other CHECK
constraint this migration adds.

**Ride-along nits (from the issue's `## Notes`), both folded in:**

- `admin_workshops_test.go`'s three `*int` `%v` prints (all three capacity
  assertions that existed before this issue, not only the one the review
  cited by line number — the file has grown since `#0146`'s review and the
  line number had drifted) replaced with a small `intPtrString` helper that
  prints `"<nil>"` or the decimal value instead of a pointer address.
- `optional.go` gained a doc paragraph stating `Optional[T]` is
  request-bodies-only: it has no `MarshalJSON`, so a response struct
  embedding it would leak `{"Value":…,"Present":…,"Valid":…}` instead of a
  plain JSON value. Nothing currently does this (`workshopView.Capacity`
  stays a plain `*int`), so this is documentation against a future mistake,
  not a fix to a live bug.

### Ruling on rejecting `0`: correct, and the reasoning is stronger than stated

Upheld, for four reasons — the first two of which the `## Fix` write-up does
not make and which are the ones that actually settle it:

1. **No legitimate workflow is broken, because the admin UI never allowed
   `0` in the first place.** `workshopAdmin.ts:382` has rejected
   `Number(capacityTrimmed) <= 0` with `Capacity must be a positive whole
   number.` since before this issue. Server-side rejection of `0` therefore
   *matches* the only interface a human uses; it removes a divergence rather
   than creating one.
2. **`capacity` cannot express "deliberately full" anyway**, so the workflow
   the objection imagines does not exist here. `migrations/000020:26`
   documents the column as `-- display only in v1`: there is no attendee
   count, no registration, no seat arithmetic — RSVPs live behind the
   external `signup_url`. A full workshop is signalled by `status` or by the
   external provider, and a rendered "Capacity: 0" would read to a visitor
   as a data-entry error, not as "full". If a full/waitlist concept is ever
   wanted it needs its own field or status value, not an overloaded
   sentinel — and rejecting `0` now keeps that door open, whereas assigning
   `0` a meaning would close it permanently.
3. `0` meaning "unlimited" would be the exact **inverse** of its natural
   reading (room for nobody), which is a worse trap than the one it avoids.
4. The implementer's own argument holds: two stored values denoting one
   meaning, with no way to recover which intent produced a given row.

One wording note, not a defect: `isValidCapacity`'s comment says the two
spellings could not be told apart "from the stored column alone." The column
*can* tell `NULL` from `0` (and `workshopView.Capacity` is `*int`, so
`omitempty` omits only nil — a stored `0` would serialize as
`"capacity":0`, not vanish). What is actually indistinguishable is the
*intent* behind two rows that would mean the same thing. The comment's claim
about nil is accurate and the conclusion is right; only that half-sentence is
loose.

### The `#0154` panic: diagnosed, not dismissed — and not provoked by this commit

Checked deliberately, from three directions. `67dcb47` (`#0154`'s final fix)
is `011504f`'s **parent**, so the worktree carries the finished version of
`internal/db/prd_index_parity_test.go`, and the file is byte-identical
between `011504f` and `HEAD`.

1. **The panic is structurally impossible in the committed code.**
   `index out of range [2] with length 2` means a `loc` from
   `FindAllStringIndex` (2 elements, no submatches) reached `matchGroup`,
   which indexes `loc[4]`/`loc[6]`/`loc[8]`. In this version `matchGroup` has
   exactly two call sites — `prd_index_parity_test.go:495` and `:680` — and
   both sit inside `columnAddPattern.FindAllStringSubmatchIndex` loops, which
   yield 10-element `loc`s for that 4-group pattern. The one loop that does
   use `FindAllStringIndex` (`checkColumnAddCoverage`, `:487`) calls
   `peekTwoWords(text[loc[1]:])` and never `matchGroup`. An in-flight version
   that passed the loose `loc` to `matchGroup` would compile and panic
   exactly as reported — consistent with reading `#0154`'s file mid-edit.
2. **It could not have been data-driven by the new CHECK.** Such a bug fires
   on the *first* loose `ALTER TABLE … ADD` in any migration, and `000020`
   already contained two of them (`email_campaigns_workshop_id_fkey` and
   `workshops_status_check`) before this commit.
3. **Proved empirically that the new CHECK is inert to the guard.** With the
   `ALTER TABLE workshops ADD CONSTRAINT workshops_capacity_check …` block
   stripped from `migrations/000020`, `TestPRDWorkshopAndMailingIndexParity`

### One new-issue candidate, unrelated to this commit

The first `ISSUE=0155rev scripts/check.sh go ./internal/...` run **failed**,
in a package this commit does not touch:

```
--- FAIL: TestSubscriberCounts_CountsLinkedAndOmitsZero (0.00s)
    store_test.go:324: Create without: interests: slug already exists
```

Diagnosed rather than re-rolled. `internal/interests/store_test.go:37`'s
`testSlug` helper builds a slug from `time.Now().UnixNano()`, and that test
calls it **twice in immediate succession**; when both calls return the same
value the second `Create` collides on `interests.slug UNIQUE`. A 200,000-pair
probe on this machine measured **189,484 identical consecutive
`time.Now().UnixNano()` pairs (94.7%), minimum delta 0ns** — Apple Silicon's
wall clock is far coarser than nanosecond, so this is a near-coin-flip flake,
not machine load (load average was 1.47 at the time) and not a regression.
The immediately following run passed with `interests ok 1.945s`. Same pattern
appears in `admin_workshops_test.go`'s `uniqueAdminWorkshopTitle`, where it
is masked by intervening HTTP round trips and by slug collision suffixing.
**Worth filing**: replace the `UnixNano` unique-value helpers with a
process-wide atomic counter (or append one). Left unfiled here because it is
outside this issue's scope and belongs to `internal/interests`, but it will
keep bouncing unrelated reviews until it is fixed.

Separately and much smaller: `workshopAdmin.ts:382` enforces a lower bound
(`> 0`, now matching the server) but **no upper bound**, so a browser user
typing `3000000000` reaches the server and gets the new 400. The behaviour is
correct and the message is descriptive, so this is not a defect — but it is
another instance of the Go↔TypeScript validator-parity gap `#0157` was filed
for, and would fit naturally in that issue's scope if it is widened beyond
URL validators.
