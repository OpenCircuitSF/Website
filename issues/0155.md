# 0155 — Nothing on the server validates `capacity`, so an API client can store 0, -1, or overflow the column

## Description

`workshops.capacity` has no server-side range check anywhere. `migrations/000020:26` declares a bare `capacity INT`, and neither `Create` nor `Patch` validates the value. Only the browser rejects non-positive numbers, so any client that does not go through the admin SPA can store nonsense:

- `-1` and `0` are accepted and stored (200)
- anything above 2³¹−1 returns **500**, from a Postgres `INT` overflow, rather than a 400

Found by `#0146`'s phase-3 review while probing that issue's new `Optional[int]` wire type with nonsense inputs. It confirmed the behavior is **pre-existing and unchanged** by `#0146` — the old `*int` did exactly the same — so it is filed separately rather than folded in.

A 500 on a value the client controls is the part worth fixing regardless of what is decided about negative capacities: it turns a bad request into an apparent server fault, and it is the shape of thing that shows up in error monitoring as a mystery.

## Acceptance criteria

- [ ] `Create` and `Patch` reject `capacity` outside a defined range with a **400**, not a 500 and not a stored value
- [ ] Decide and record the valid range. The obvious one is `1..2147483647` — but decide deliberately whether `0` should mean "no capacity limit" rather than being rejected, since `NULL` already means that and two spellings of one idea invite confusion
- [ ] The database agrees with the handler: add a `CHECK` to `migrations/000020` (greenfield, `CLAUDE.md` §1) so the constraint survives a caller that bypasses the handler entirely
- [ ] Tests cover each boundary — below the minimum, at it, at the maximum, above it — and assert the status code, not just that something failed
- [ ] `ISSUE=0155 scripts/check.sh go ./internal/...` passes

## Notes

Two non-blocking nits from the same review, worth folding in while someone is in these files:

- `internal/handlers/admin_workshops_test.go:678` prints a `*int` with `%v`, so a failure message shows a pointer address rather than a value.
- `Optional[T]` has no `MarshalJSON`, so embedding it in a **response** struct would emit `{"Value":…,"Present":…,"Valid":…}`. One doc line saying "request bodies only" closes that door before someone opens it.
