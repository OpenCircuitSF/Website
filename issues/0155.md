# 0155 — Nothing on the server validates `capacity`, so an API client can store 0, -1, or overflow the column

## Description

`workshops.capacity` has no server-side range check anywhere. `migrations/000020:26` declares a bare `capacity INT`, and neither `Create` nor `Patch` validates the value. Only the browser rejects non-positive numbers, so any client that does not go through the admin SPA can store nonsense:

- `-1` and `0` are accepted and stored (200)
- anything above 2³¹−1 returns **500**, from a Postgres `INT` overflow, rather than a 400

Found by `#0146`'s phase-3 review while probing that issue's new `Optional[int]` wire type with nonsense inputs. It confirmed the behavior is **pre-existing and unchanged** by `#0146` — the old `*int` did exactly the same — so it is filed separately rather than folded in.

A 500 on a value the client controls is the part worth fixing regardless of what is decided about negative capacities: it turns a bad request into an apparent server fault, and it is the shape of thing that shows up in error monitoring as a mystery.

## Acceptance criteria

- [x] `Create` and `Patch` reject `capacity` outside a defined range with a **400**, not a 500 and not a stored value
- [x] Decide and record the valid range. The obvious one is `1..2147483647` — but decide deliberately whether `0` should mean "no capacity limit" rather than being rejected, since `NULL` already means that and two spellings of one idea invite confusion
- [x] The database agrees with the handler: add a `CHECK` to `migrations/000020` (greenfield, `CLAUDE.md` §1) so the constraint survives a caller that bypasses the handler entirely
- [x] Tests cover each boundary — below the minimum, at it, at the maximum, above it — and assert the status code, not just that something failed
- [x] `ISSUE=0155 scripts/check.sh go ./internal/...` passes

## Root cause

`workshops.capacity` (`migrations/000020:26`, a bare `capacity INT`) had no
range check anywhere on the write path. `createWorkshopRequest.Capacity` and
`patchWorkshopRequest.Capacity`'s merge (`Optional[int]`, from `#0146`) both
passed whatever the client sent straight through to
`workshops.Store.Create`/`Update` unexamined. Two distinct failure shapes
followed from the same gap: `-1`/`0` stored cleanly with a 200 (nothing ever
rejected them), and anything above `2147483647` blew past Postgres's `INT`
column range at the driver layer, which the handler's generic `default:`
error branch mapped to a bare 500 — a client-controlled bad value surfacing
as an apparent server fault. The database itself carried no constraint on
the column either, so even a caller that bypassed the handler entirely (a
direct `INSERT`/`UPDATE`, a future import path) could park a row in the same
nonsense states.

## Fix

Added `isValidCapacity(v int) bool` (`internal/handlers/admin_workshops.go`):
`v >= 1 && v <= 2147483647`. `Create` checks `req.Capacity` (when non-nil)
before calling the store; `Patch`'s existing `Optional[int]` merge switch
checks `req.Capacity.Value` only in the `default` case (present *and*
valid, i.e. a real number was sent) — the `!Present` ("leave alone") and
`!Valid` ("explicit null: clear it") branches are untouched, so the range
check applies exactly to the "set it" state and never interferes with the
three-state clear/leave-alone contract `#0146` built. Both reject with a
400 and `capacityErrorMessage`, never a stored value.

**The `0` decision, made deliberately per the issue's own instruction:**
`0` is **rejected**, not treated as "no capacity limit." `NULL` already owns
that meaning end-to-end — `workshopView.Capacity` is `*int` with
`json:"capacity,omitempty"`, so a nil capacity is simply absent from the
response, and nothing in this codebase's read path (public listing,
admin UI) ever gives a *present* zero a special "unlimited" meaning. Letting
`0` mean the same thing as `NULL` would create two wire spellings of one
idea with no way to tell, from the stored column alone, which one a given
row's author meant — exactly the kind of ambiguity `Optional[T]`'s own
three-state design (`#0146`) exists to avoid elsewhere. Rejecting `0` keeps
`NULL` the single, unambiguous "no limit" representation. (Separately, `0`
is not a meaningful capacity for a workshop in this domain either — nobody
runs a session with room for nobody — but the wire-representation argument
above is the deciding one even setting that aside.)

**Database CHECK**, added to `migrations/000020` in place (greenfield,
`CLAUDE.md` §1 — no version bump, since an in-place edit isn't a new
migration):

```sql
ALTER TABLE workshops
    ADD CONSTRAINT workshops_capacity_check
    CHECK (capacity IS NULL OR (capacity >= 1 AND capacity <= 2147483647));
```

The upper bound is technically redundant — Postgres's `INT` column type
already can't hold anything larger — but it's written out explicitly so the
constraint documents the intended range on its own, without requiring a
reader to know `INT`'s limit by heart.

**`docs/database.md`** picked up a matching clause on the `000020` migration
row, alongside the existing `workshops_status_check` note, for the same
reason that one is documented there — nothing mechanically requires it (see
"Obstacle" below), but the file already describes every other CHECK
constraint this migration adds.

**Ride-along nits (from the issue's `## Notes`), both folded in:**

- `admin_workshops_test.go`'s three `*int` `%v` prints (all three capacity
  assertions that existed before this issue, not only the one the review
  cited by line number — the file has grown since `#0146`'s review and the
  line number had drifted) replaced with a small `intPtrString` helper that
  prints `"<nil>"` or the decimal value instead of a pointer address.
- `optional.go` gained a doc paragraph stating `Optional[T]` is
  request-bodies-only: it has no `MarshalJSON`, so a response struct
  embedding it would leak `{"Value":…,"Present":…,"Valid":…}` instead of a
  plain JSON value. Nothing currently does this (`workshopView.Capacity`
  stays a plain `*int`), so this is documentation against a future mistake,
  not a fix to a live bug.

## Gotchas

- **`isValidCapacity`'s upper bound is redundant with the column type, kept
  anyway.** Postgres's `INT` can't hold anything past `2147483647` regardless
  of the CHECK, so the CHECK's `capacity <= 2147483647` clause never actually
  fires on its own — a value that large already fails to insert with `ERROR:
  integer out of range` before the CHECK is even evaluated (confirmed in the
  direct-database proof above). It's written out anyway purely for
  self-documentation, so a reader doesn't need to know `INT`'s limit by
  heart to see the intended range.
- **PRD.md needed no edit.** `internal/db/prd_index_parity_test.go`'s own
  doc comment (as of `#0154`, read before deciding this) states its guard
  covers indexes and, as of that issue, columns — "never a CHECK
  constraint" — explicitly, by name. This issue's only migration change is
  a CHECK constraint via a separate `ALTER TABLE`, so the `capacity INT`
  column definition line PRD §6.2 transcribes is untouched and the parity
  guard has nothing to say about this change.
- **The `-run` regex trap**: `Capacity` does not match `Capacities`
  (`TestAdminWorkshops_CreateAcceptsBoundaryCapacities`,
  `...PatchAcceptsBoundaryCapacities`) — `-run
  'TestAdminWorkshops_.*Capacity'` silently skipped both boundary-accept
  tests on the first verification pass with no error, just an absence from
  the `-v` output. Worth remembering for the next `-run` filter over this
  file.
- **Go's test cache can mask an env-var-gated skip.** Running the same
  `-run` pattern twice with `TEST_DATABASE_URL` newly exported in between
  returned a cached `(cached)` result still showing the DB-gated tests
  SKIPped from the first (unset) run — `-count=1` was required to force a
  real re-run and see them pass. Not specific to this issue, but easy to
  mistake for the fix not working.
