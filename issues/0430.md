## Description

`docs/deployment.md`'s backup section quotes `#0229`'s `## Decision` as the
reason S3 upload was deferred:

> building it needs an AWS account, **which does not exist yet** (`CLAUDE.md` §10
> item 2), and the user deferred all AWS work to deployment, same as SES.

**The account exists** — `378152330719`, with SES live in it and an IAM instance
role attached (`#0426`, confirmed against the box). So the stated precondition
for the deferral has been met, and the sentence now reads as a live blocker that
is not one.

The passage also cites `CLAUDE.md` §10 item 2 for that claim; §10 item 2 records
SES as "all but done" and the account as real.

**Note `#0426` already corrected the *adjacent* instance** of this same clause,
a few hundred lines further down, with a dated correction naming the account.
This one was left because it belongs to the backups subsystem rather than IAM —
the right scope call, and why it is filed separately.

## What this issue is actually about — read before editing

**The deferral may still be correct.** "The account does not exist" was one
reason among several; the other — *"the user deferred all AWS work to
deployment"* — is a scheduling decision, not a technical precondition, and
deployment has now happened.

So the question is not merely whether the sentence is stale. It is:

- Is S3 backup upload still deliberately deferred, and if so **on what current
  grounds**?
- Or was the account's absence the load-bearing reason, in which case the
  deferral's basis has lapsed and someone should decide afresh?

**Do not silently rewrite the rationale into a different one.** If the current
grounds are not recorded anywhere, say so — an honest "the original reason has
lapsed and no replacement is recorded" is more useful than a manufactured
justification. `#0421` faced exactly this with PRD §10.3's "closest to San
Francisco" rationale and correctly declined to invent a replacement.

## Fix

**Criterion 1 — the account, verified read-only, not copied from this issue.**
`aws sts get-caller-identity` → `Account: 378152330719`, identity
`arn:aws:iam::378152330719:user/certbot-dns-updater` — the same box CLI
identity `CLAUDE.md` names elsewhere. `aws s3 ls` was refused:
`AccessDenied … not authorized to perform: s3:ListAllMyBuckets` for that
identity. Recorded rather than worked around, per §5b — this identity's
narrow grants are already documented elsewhere in this project (it can't
`ses:GetEmailIdentity` either). No AWS state was changed by either call.

**Criterion 2 — current status, recorded plainly, no invented rationale.**
`#0229`'s `## Decision` gave two grounds for deferring S3 backup upload: (a)
the AWS account did not exist, and (b) the user deferred all AWS work to
deployment. Both have lapsed: (a) the account now exists and SES is live in
it; (b) deployment happened on 2026-08-25. **No replacement decision to build
S3 upload is recorded anywhere** — not in `#0229`, not in `CLAUDE.md`, not in
any later issue found by grep. So the accurate status is: S3 upload is not
built, its original deferral grounds have both lapsed, and nobody has decided
whether to build it — an open question, not a live blocker and not a
standing deferral either. Recorded this way in both `docs/deployment.md`
locations and in a forward-pointing note on `#0229` itself; no rationale was
manufactured to fill the gap.
