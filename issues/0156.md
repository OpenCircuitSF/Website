## Description

Both found by `#0144`/`#0145`'s phase-3 review, which passed those issues and recorded these rather than bouncing. Neither is a defect today; both are cheap now and annoying later.

**1. `sameLocalDate` has no regression test.** `#0144` moved the announce body's same-day check from UTC calendar days to Pacific ones, which is correct — a late-evening Pacific event is already the next UTC day, so the short "6:00 PM to 8:00 PM" end-time form was being suppressed when it should appear. But the reviewer mutated the function **back to UTC days and the entire `internal/handlers` suite stayed green**. The behavior is right and untested, which is the state where a future refactor quietly undoes it.

The reviewer left two ready-made cases, with expected strings, in `#0144`'s `## Review notes`:
- `2026-01-14T22:00Z` → `2026-01-15T01:00Z` — spans a UTC day but not a Pacific one; must render the **short** form
- `2026-01-15T07:00Z` → `09:00Z` — spans a Pacific day but not a UTC one; must render the **long** form

**2. The binary depends on host tzdata to boot.** `announceLocation` is initialized with `mustLoadLocation("America/Los_Angeles")` at package init, so a host without the IANA database **panics the whole binary at startup**, not just the announce path. That is the correct failure mode — the reviewer confirmed there is no silent UTC fallback, and noted the real trap avoided: a failed load returns a `nil *time.Location` that *prints* as `"UTC"` and behaves as UTC in most `time` methods.

Importing `_ "time/tzdata"` in `cmd/opencircuit` embeds the database (~450 KB) so the binary carries its own copy and cannot fail this way on a `scratch`/`distroless` base.

## Root cause

Both items were pre-existing gaps recorded by `#0144`'s phase-3 reviewer
rather than defects introduced by that fix:

1. `sameLocalDate` (`internal/handlers/admin_workshop_announce.go`) compares
   two `time.Time` values' calendar dates in whatever zone they are already
   expressed in — Pacific, since callers pass values already converted via
   `announceLocation.In`. That is correct, but nothing committed pinned it:
   the reviewer's mutation spot-check (reverting the comparison to `.UTC()`
   dates) left the entire `internal/handlers` suite green.
2. `announceLocation` is initialized at package init via
   `mustLoadLocation("America/Los_Angeles")`, which panics the whole binary
   if the host has no IANA tzdata. Correct behavior (no silent UTC
   fallback), but the binary had no database of its own — it depended
   entirely on the host, which is fine on the Amazon Linux deploy target
   (CLAUDE.md §7) but would break on a future scratch/distroless base.

## Fix

1. Added `TestAnnounceWhen_SameLocalDate_ComparesPacificNotUTC` to
   `internal/handlers/admin_workshop_announce_body_test.go`, carrying over
   verbatim the two instants and expected strings from `#0144`'s
   `## Review notes` mutation spot-check:
   - `2026-01-14T22:00Z` → `2026-01-15T01:00Z` (spans a UTC day, not a
     Pacific one) → short form, `"Wednesday, January 14, 2026 at 2:00 PM
     PST to 5:00 PM PST"`
   - `2026-01-15T07:00Z` → `2026-01-15T09:00Z` (spans a Pacific day, not a
     UTC one) → long form, `"Wednesday, January 14, 2026 at 11:00 PM PST to
     Thursday, January 15, 2026 at 1:00 AM PST"`
2. Added `_ "time/tzdata"` to `cmd/opencircuit/main.go`'s import block,
   with a comment explaining it embeds the IANA database so
   `announceLocation` can load without relying on host tzdata, and that
   `mustLoadLocation`'s panic-on-missing-zone behavior is unchanged and
   still correct — this only removes the host as a source of that failure.

### Is a DST-side case missing? No — the pair is sufficient

`sameLocalDate` compares `a.Date()`/`b.Date()` on values the caller already
converted via `.In(announceLocation)`, and `Time.Date()` resolves the offset
per instant from the `*Location`. The function is therefore offset-agnostic:
PST-vs-PDT correctness lives in `time.Location`, not in this comparison, and a
summer mirror of case 1 would exercise an identical code path with 7 hours of
skew instead of 8. `#0144` already pins a PDT pair (`2026-07-15T01:00Z` →
`03:00Z`) that exercises the same-day *true* branch under daylight time. No
case is missing; nothing to file.

One genuinely uncovered edge exists and is **not** worth an issue: a range
that crosses the DST transition inside one Pacific day (`2026-03-08T09:00Z` →
`11:00Z`) renders the short form with two different zone labels — "1:00 AM PST
to 4:00 AM PDT". That is correct output, and Open Circuit SF is unlikely to run
a workshop across 2 AM on transition Sunday. Recorded here rather than filed.

### Item 2 — the size measurement, reproduced

Built `./cmd/opencircuit` twice in the worktree, with the import removed for
the second build and restored afterwards (worktree confirmed clean):

- with `time/tzdata`: **23,611,218 bytes**
- without: **23,198,226 bytes**
- **difference: 412,992 bytes** — *exactly* the implementer's figure, to the
  byte.

The absolute sizes are ~925 KB below the implementer's (24,536,146 /
24,123,154) for a benign reason: the binary embeds `web/dist` via `//go:embed`,
and only `web/dist/index.html` is tracked in git, so a fresh worktree links a
placeholder where the main checkout links a built 1.0 MB SPA. The delta —
the only number the acceptance criterion asks for — is unaffected and matches.
A standalone probe pair built outside the repo produced the same 412,992-byte
delta a third time.

`go tool nm` diffed between the two binaries shows exactly four symbols present
only in the with-tzdata build: `time/tzdata..inittask`, `time/tzdata.init.0`,
`time/tzdata.loadFromEmbeddedTZData`, and `time.registerLoadFromEmbeddedTZData`.
The three `time.*` tzdata symbols that appear in *both* are ordinary `time`
package members (`LoadLocationFromTZData`, `loadTzinfoFromTzdata`, and the nil
`loadFromEmbeddedTZData` hook), so the implementer's claim is right but is
worth stating precisely: it is the *registration* that is new, not the API.

`grep -rn 'time/tzdata' --include='*.go' .` returns exactly one hit, in
`cmd/opencircuit/main.go` — the binary's own package, not a library that would
impose the 413 KB on every consumer. Correct placement.

### The embedded database is actually used — proved, not assumed

`time/tzdata` is a *fallback*, so a machine with system tzdata proves nothing on
its own, and the implementer's probe (run on this host) could not distinguish
the two paths. `ZONEINFO` does not help either: Go tries it *in addition to*
the platform sources, not instead of them.

`sandbox-exec` does work. Denying reads of every host zone source
(`/usr/share/zoneinfo`, `/usr/share/zoneinfo.default`, `/var/db/timezone`,
`/usr/share/lib/zoneinfo`, `/usr/lib/locale`) was **not** sufficient at first —
a probe without the import still resolved the zone, because Go's
`loadLocation` has a final fallback to `$GOROOT/lib/time/zoneinfo.zip` that
exists only on a machine with a toolchain installed. Denying that path too
reproduces a `scratch`/`distroless` container faithfully, and the result is
decisive — run against the **real binaries**, not a toy probe:

```
$ sandbox-exec -f nozone.sb ./opencircuit-without-tzdata --help
panic: admin_workshop_announce: load location "America/Los_Angeles":
       operation not permitted
  ...handlers.mustLoadLocation(...)
  ...handlers.init()

$ sandbox-exec -f nozone.sb ./opencircuit-with-tzdata --help
opencircuit 0.1.0
```

That is the exact failure `#0156` item 2 describes — a panic in
`internal/handlers.init()`, taking the whole binary down before `serve` is ever
reached — and the import demonstrably prevents it. Under the same denial, a
probe using only the embedded database rendered all three pinned instants
byte-identically to the host-tzdata rendering, so the embedded copy resolves
the same zone data and does not merely load.

### One defect found, not grounds for a bounce

The import comment contains an inverted sentence:

> A missing host tzdata is the deploy target's normal case today (Amazon Linux
> ships it, CLAUDE.md §7), but a future scratch/distroless base would
> otherwise panic…

A missing host tzdata is *not* the deploy target's normal case — the
parenthetical and the following "but" both confirm a `not` was dropped. As
written the comment tells a future reader the opposite of the truth about the
production host. Zero behavioral impact, one word to fix, and the criterion
("a comment saying why") is otherwise met — the comment explains the rationale
and the failure mode rather than restating the import. Recorded for a trivial
follow-up rather than bounced, since a full implement-and-review cycle for a
missing `not` is not a good trade.
