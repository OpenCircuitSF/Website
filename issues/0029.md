## Description

The signup form used both inline on the home page and standalone at `/subscribe`: email field, interest checkbox grid, and the invisible anti-abuse fields.

> 🟢 Resolved 2026-08-19 — Independently re-verified. The uniform `202` survives the frontend by construction: `SubscribeForm.svelte` uses the subscribe response exactly once, as the ignored argument to `onSubscribeSuccess`, which returns the constant `/subscribe/thanks`; `SubscribeThanks.svelte`'s copy is static and correctly hedged ("If that address isn't already on our list"); there is no `console.` call anywhere in `web/src`, no client-side timing branch (one `await`, one navigation), and no retry. A live probe against a private `opencircuit_r3` database and a private-port build — ownership proved by a marker interest only that database holds, not by a bare `curl` 200 — found the status line, `Content-Type`, `Content-Length: 43` and body byte-identical across 50 brand-new addresses, 50 already-active addresses, 30 pending resends and 30 honeypot fills. `GET /api/interests` returns `ListActive` rows only (a seeded deactivated marker never appears), omits `id`, `active` and `subscriber_count`, ignores every query parameter offered to it, answers 405 to POST/PATCH/PUT/DELETE, and the admin `/admin/interests` route still answers 401 unauthenticated. `#0071`'s parity guard was mutation-proved in a throwaway worktree — it fails for a TS-only route and for a Go-only route, and is green again after restore — and both tables already carry all four journey routes, so no parity work was owed. Each of the three commits builds, vets and tests green independently (`go build`, `go vet`, `go test ./... -count=1 -p 1` with `TEST_DATABASE_URL` set, zero skips, `internal/handlers` 1.65–1.91s of real DB round trips, plus `svelte-check` 0 errors / 0 warnings and 145 vitest tests at each of `b335cec`, `18b9e82`, `7ed785d`); `npm run build` succeeds and `web/dist/index.html` is byte-identical to the committed placeholder. One finding is **routed rather than blocking**: the *server's* response time separates all four `POST /api/subscribe` branches with zero overlap — honeypot 0.30 ms, already-active 0.63 ms, pending-resend 0.84 ms, brand-new 1.67 ms, where the fastest brand-new sample (1.51 ms) is slower than the slowest already-active one (1.02 ms) and P(active > new) = 0.000 over 50 paired samples — which is a timing enumeration oracle in `#0026`'s `subscribe.go`, not in this issue's frontend, and needs its own issue.

## Carried in from `#0024`'s review (2026-08-19)

- [x] **Source the form's checkboxes from `ListActive`, never `ListAll`.**
      `#0024`'s admin UI tells admins that deactivating an interest "removes this
      interest from the public signup form" — but `#0026` enforces that only at
      *validation* time, rejecting inactive slugs with a 400. So a form built
      from `ListAll` makes that promise false and hands the user a 400 on a stale
      checkbox they were shown.
- [x] **There is no public interests endpoint yet.** `interests.ListActive` has
      zero non-test callers today; this issue needs to add the public read path
      as well as consume it. Do not expose the admin route to the public SPA.

## Root cause

Not a bug fix — this is new construction. Two components did not exist yet:
the public `GET /api/interests` read path (only the admin `ListAll` route
existed) and the `SubscribeForm.svelte` component itself.

## Fix

- `internal/handlers/public_interests.go` — new `PublicInterestsHandler`
  serving `GET /api/interests`, backed by `interests.Store.ListActive`
  (never `ListAll`). Response shape (`publicInterestView`) deliberately omits
  `id`, `active`, and `subscriber_count` — admin-only fields from
  `GET /admin/interests`.
- `web/src/lib/subscribe.ts` — pure, framework-free helpers backing the
  whole signup/confirm/preferences journey: UTM capture/parse
  (`captureUtmParams`/`loadUtmParams`, DOM-injectable per `theme.ts`'s
  convention), wire-body shaping (`buildSubscribeRequest`), the
  response-invariance guarantee (`onSubscribeSuccess` — always returns the
  fixed `/subscribe/thanks` route and never reads the response body), and a
  slug-toggle helper (`toggleSlug`) shared with the preference center.
- `web/src/lib/SubscribeForm.svelte` — the component itself: email input
  (`type="email"` but the `<form>` carries `novalidate` so the browser's own
  pattern constraint can never reject an RFC 6531 non-ASCII address the
  server would accept — see Gotchas), a `<fieldset><legend>` checkbox grid
  populated from `GET /api/interests`, the honeypot (`display:none` +
  `aria-hidden="true"` + `tabindex="-1"` on the input itself), the
  `rendered_at` timing-gate timestamp captured at `onMount`, and an
  `aria-live="polite"` error region tied to the email field via
  `aria-describedby`.
- `web/src/views/Subscribe.svelte` / `SubscribeThanks.svelte` — the
  standalone `/subscribe` page and the fixed `/subscribe/thanks`
  destination. `SubscribeThanks`'s copy is static and never derived from
  any prior API response, by construction.
- `web/src/views/Home.svelte` — swapped the placeholder `Panel` for a real
  `<SubscribeForm />`.
- `web/src/App.svelte`, `web/src/lib/api.ts`, `web/src/lib/types.ts` — wired
  the two new routes and the `listPublicInterests`/`subscribe` API helpers.
  `router.ts`'s `STATIC_ROUTES` and `routes.go`'s `knownStaticRoutes` already
  listed `/subscribe` and `/subscribe/thanks` from #0014/#0071 — no changes
  needed there.
- `cmd/opencircuit/main.go` — additive: constructs `PublicInterestsHandler`
  and registers `GET /api/interests`, unauthenticated, no rate limit (a
  read-only GET over a taxonomy capped at a handful of admin-created rows —
  same trust level as `GET /sitemap.xml`). `mountAndServe`'s signature grew
  a `publicInterestsH` parameter; the four `cmd/opencircuit/*_wiring_test.go`
  files needed a mechanical `nil` added at each call site to keep compiling.
  `subscribe.go`/`subscribe_test.go` (owned by the concurrent `#0081` pass)
  were not touched.
- Dev-store gap: **documented, not filled.** `STORAGE=json` passes `nil` for
  `publicInterestsH`, mirroring `subscribeH`'s existing pattern — `internal/devstore`
  has no interests-table backing, so `GET /api/interests` (like
  `POST /api/subscribe`) is unavailable under `./scripts/dev.sh` until a
  devstore backing lands. Every other route keeps working.

## Gotchas

- **Email validation is deliberately almost absent client-side.** The only
  client-side check is "non-empty"; the `<form>` carries `novalidate` so the
  browser's native `type="email"` pattern constraint never blocks
  submission. This is a direct response to the issue's own warning — an
  RFC 6531 non-ASCII address the server accepts (per `#0026`'s review) must
  not be rejected by a stricter client pattern in some browser before the
  server ever sees it. All real format/disposable-domain validation is left
  to the server's 400 response.
- **Commit ordering does not match issue numbering.** This batch's three
  commits landed `#0029` → `#0031` → `#0030` (not numeric order), because
  `ConfirmSubscription.svelte` (`#0030`) embeds `PreferenceCenter.svelte`
  (`#0031`) — building `#0030` first would have left an intermediate commit
  that didn't compile. Each commit was independently verified green
  (`go build`/`vet`/`test` + `npm check`/`test`/`build`) before the next one
  landed; see `#0031` and `#0030`'s own `## Verification` for their passes.
- **`cmd/opencircuit/main.go`'s `mountAndServe` signature is shared
  infrastructure across all three issues** (it grew `publicInterestsH` here,
  then `preferencesH` in `#0031`, then `confirmH` in `#0030`, in that
  order, matching the param order to the commit order) — the parameter order
  is not arbitrary; it was chosen specifically to let each commit be a clean,
  independently-buildable increment rather than one big signature change.

## Notes

PRD §7.3, §7.5. Hiding the honeypot with `display: none` is fine for bots but must also carry `aria-hidden="true"` and `tabindex="-1"` so a screen-reader user is never asked to fill it.

The success state must not leak whether the address was already subscribed — the component has to render identically regardless, or #0026's uniform 202 is undone at the UI layer.
