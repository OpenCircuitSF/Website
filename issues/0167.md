## Description

`#0136` moved the body preview to the server so preview output is byte-identical to what publishes. The consequence is deliberate and correct: the preview shows the **last saved** body, not what the admin is typing.

The affordance for that is incomplete. `hasPreviewContent` derives from `previewHtml` rather than from `fields.bodyMd`, so the explanatory line — *"Save the body first — the preview shows the last saved version"* — appears **only when the stored body is empty**, i.e. on a brand-new workshop.

In the common case, editing a workshop that already has a body, the admin types, clicks **Show preview**, and sees the *previous* text with no indication why. The button says "Show preview", not "Preview last saved".

Not blocking: Save is adjacent, the pane refreshes on save, and the failure mode is stale rather than wrong.

## Root cause

`hasPreviewContent` (`previewHtml.trim() !== ''`) was the only signal
gating which state the body-preview pane showed. That's the right check
for "is there anything server-rendered to show at all" — true only once
something has ever been saved — but it says nothing about whether the
rendered HTML still matches the current textarea buffer. So the "Save the
body first" cue only ever appeared in the one state where `previewHtml` is
empty: a brand-new, never-saved workshop. Editing an existing workshop
(which always has non-empty `previewHtml` after its first save) hid the
cue permanently, regardless of how far the buffer had since diverged.

## Fix

- Added `isPreviewStale(bodyMd, savedBodyMd)` to `web/src/lib/workshopAdmin.ts` —
  a pure predicate comparing the live textarea buffer (`fields.bodyMd`)
  against the workshop's last-saved body (`workshop.body_md`, treating its
  `undefined` case the same as `''`, matching `workshopToFormFields`'s
  existing convention). Exactly the `fields.bodyMd !== workshop.body_md`
  check the issue specifies.
- `WorkshopEditor.svelte` computes `previewStale` as a `$derived` from that
  predicate and, when `hasPreviewContent` is true (there's something
  rendered to show) **and** `previewStale` is true, renders a
  `role="status"` cue — *"Showing the last saved version — your edits since
  then aren't included. Save to update the preview."* — **alongside** the
  still-rendered last-saved HTML, not in place of it. The empty-body branch
  (`hasPreviewContent` false) is untouched, so the original "Nothing to
  preview yet. Save the body first…" copy still appears unconditionally for
  a brand-new workshop, satisfying the "existing empty-body copy must still
  appear" criterion for free — `previewHtml` genuinely stays `''` until the
  first save regardless of what's typed, so that branch is reached the same
  way it always was.
- No client-side re-rendering was added anywhere — `previewHtml` still
  comes only from `POST /admin/workshops/{id}/preview` (`refreshPreview`,
  called after `load()` and after every successful `save()`, unchanged).
  The stale cue is presentation-only; it never recomputes or substitutes
  for the server-rendered HTML.
- **Button-label decision**: left "Show preview" / "Hide preview"
  unchanged. That button governs the preview *pane's visibility*, not its
  freshness — renaming it (e.g. to "Preview last saved") would either be
  wrong in the common case where the buffer isn't dirty, or would need to
  flip dynamically while the pane is open (since typing after opening the
  pane doesn't currently re-toggle it), duplicating a signal the in-panel
  `role="status"` cue already carries once the pane is open. The cue is the
  single source of the staleness signal; the toggle button stays about
  show/hide only.

### Edge behaviour, probed against the real module

Imported `isPreviewStale` from `workshopAdmin.ts` itself rather than
re-implementing it:

| Buffer vs saved | Result | Verdict |
|---|---|---|
| `'a'` / `'a'` | false | correct |
| `'ab'` / `'a'` | true | correct |
| `''` / `''` | false | correct |
| `''` / `undefined` | false | correct — the never-saved workshop |
| `''` / `null` | false | correct, and worth noting: `??` covers `null` as well as `undefined`, so a JSON `"body_md": null` is as safe as an omitted key |
| `'x'` / `''` | true | the new-workshop-with-typing case |
| `'x'` / `null` | true | correct |
| `'a\n'`, `' a'`, `'a '` / `'a'` | true | see below |
| CRLF vs LF, NFC vs NFD | true | byte comparison, as specified |

**The case that matters — this issue's equivalent of `#0151`'s `[0]` vs
`[]` — is the whitespace asymmetry.** `validateWorkshopForm` sends
`body_md: fields.bodyMd.trim()` (`workshopAdmin.ts:534`), while
`isPreviewStale` compares the buffer untrimmed. So a buffer differing from the
stored body only in leading/trailing whitespace raises the cue even though
saving it would store a byte-identical body. Two things make this acceptable
rather than a bounce:

1. It over-warns rather than under-warns — the safe direction for a staleness
   cue.
2. It is transient, not sticky. `save()` assigns `workshop = await
   updateWorkshop(...)` **and** `fields = workshopToFormFields(workshop)` from
   the response, so the buffer is re-synced to whatever the server actually
   stored (trimmed included) and the cue clears on the next tick. There is no
   state in which the cue is stuck on with no way to clear it — the failure
   mode this issue was most exposed to. `confirmTransition()` also reassigns
   `workshop`, but never touches `body_md`, so publish/unpublish/cancel leave
   the cue's state alone.

Tightening the predicate to compare trimmed values would make it disagree with
criterion 1's literal `fields.bodyMd !== workshop.body_md` and with
`hasPreviewContent`'s equivalent plainness, so it is left as shipped. Reported
to the orchestrator as an optional follow-up, not filed (§9).

### The preview did not become live

`refreshPreview()` is the only writer of `previewHtml`, and its only source is
`previewWorkshop(workshopId)` → `POST /admin/workshops/{id}/preview`,
unchanged. `{@html previewHtml}` is unchanged. The editor imports nothing from
`linkSafety.ts` or any Markdown module, and the built bundle contains **zero**
occurrences of `renderMarkdownPreview` (the deleted client renderer). The cue
is rendered *above* the server HTML, not in place of it, so `#0136`'s
preview/publish parity is byte-for-byte what it was.

### The empty-body branch is genuinely untouched

The diff inserts only the `{#if previewStale}` block inside the `{:else if
hasPreviewContent}` arm; the `{:else}` line carrying "Nothing to preview yet.
Save the body first — the preview shows the last saved version." does not
appear in the diff and is byte-identical. `previewHtml` stays `''` until a
first save regardless of what is typed, so a brand-new workshop still reaches
that arm. Criterion 2 holds.

Also checked that the three arms leave no gap: there is no state in which the
pane is open, the buffer is dirty, and nothing says so — `hasPreviewContent`
false shows the empty-body copy (which already carries the same message), true
shows the new cue.

### Ruling 3 — leaving "Show preview" alone: accepted

An admin does find the cue in time. Staleness only matters once the pane is
open, and the cue is the first thing inside the pane, immediately above the
rendered HTML — it lands where attention already is. A label-based signal
would have to flip live while the pane is open (typing after opening does not
re-toggle it) and would be actively wrong in the common clean case. The
in-panel cue as the single staleness signal is the right shape.
