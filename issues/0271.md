## Description

The site publishes **`hello@opencircuitsf.com`** as its contact address. The
correct address is **`contact@opencircuitsf.com`** (user, 2026-08-25).

This is live on a site that is deploying now, and it appears in four
user-visible places plus two code constants:

| Where | What it is |
|---|---|
| `web/src/lib/Footer.svelte` | site-wide footer contact link |
| `web/src/views/About.svelte` | About page contact |
| `web/src/views/PrivacyPolicy.svelte` | **the privacy-request address** |
| `web/src/lib/subscribe.ts` | `COMPLAINED_CONTACT_EMAIL` — shown to a complained subscriber |
| `internal/handlers/preferences.go` | `complainedContactEmail` — the server half of the same string |
| `.env.example`, `docs/configuration.md` | `EMAIL_FROM` / `EMAIL_REPLY_TO` examples |

**The privacy policy one is the load-bearing instance.** `#0075` routes GDPR
erasure and data-export requests there, so it is a published commitment to a
mailbox that must be read. `CLAUDE.md` §10 item 4 already records that the
sending identity and *who reads that inbox* were undecided — this settles the
address half.

**`#0095`'s parity guard makes the two `COMPLAINED_CONTACT_EMAIL` constants a
pair**: changing one side alone fails `complained_copy_parity_test.go`. That is
working as designed and is the reason this cannot be a one-sided edit.

## Scope — what is deliberately NOT changed

**Historical records keep the old address.** `PRD.md`'s decision log, the
`issues/*.md` files that quote it, and `CLAUDE.md` §10's record of the
then-undecided identity are accounts of what was true when written. Rewriting
them would falsify the history, which is the opposite of the discipline the
citation guards enforce. Only `CLAUDE.md` §10 item 4's *status* is updated, to
record that the address is now decided.

`EMAIL_FROM` and `EMAIL_REPLY_TO` are **configuration**, not hardcoded — the
example files change, and production is an environment-variable change with no
deploy.

**`#0095`'s guard is two-sided, proved rather than assumed.** A one-sided edit
had to be shown to fail, and §8a forbids mutating the shared tree while another
agent is working in `internal/handlers` and `web/src`. So the guard's own
parsing and comparison — `parseTSStringConst` on
`COMPLAINED_CONTACT_EMAIL` and `goComplainedContactEmailConstRe` on
`complainedContactEmail`, byte-identical regexes — was re-implemented over
**in-memory copies** of the two files, with each mutation asserted to have
actually applied before it was measured:

    baseline (unmutated):   ts='contact@…' go='contact@…' -> PASS
    Go-side-only reverted:  ts='contact@…' go='hello@…'   -> FAIL (guard fires)
    TS-side-only reverted:  ts='hello@…'   go='contact@…' -> FAIL (guard fires)

`git status --porcelain -- internal/handlers web/src` was clean afterwards; no
repo file was written. The guard's oracle for each side is the *other side's
source file on disk*, not a stored copy of the expected string, so it is not
the "copy of the answer next to the question" shape §8's guard rules warn
about.
