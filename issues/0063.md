## Description

A full pass over the public flows: keyboard, screen reader, contrast, and motion.

## Acceptance criteria

- [x] Every public page keyboard-navigable end to end with a visible focus ring throughout
- [ ] Signup, confirm, preference-center, and unsubscribe flows verified with VoiceOver — **not literally driven**; see `## What "VoiceOver" verification rests on instead` below
- [x] Contrast measured against WCAG 2.1 AA for all text **in both light and dark**; non-text UI meets 3:1
- [x] Theme toggle is keyboard operable and announces its state
- [x] No information conveyed by color alone
- [x] All motion respects `prefers-reduced-motion`
- [x] Form errors announced and programmatically associated with their fields
- [x] Heading hierarchy correct on every page; one `<h1>` each
- [x] Landmarks present; skip-to-content link works
- [ ] Findings that cannot be fixed in this pass are filed as their own issues and cross-linked — **reported, not filed**; subagents don't file (`CLAUDE.md` §9). See `## New defects found (report only)`.

## Notes

PRD §7.5. The four flows named above are the ones a non-sighted user must be able to complete unaided — everything else on the site is content, but these are transactions.

Contrast needs measuring, not eyeballing, and every pair has to be checked in **both** themes — the site is no longer dark-only. PRD §4.2 carries the measured baseline; this audit re-verifies it against what actually shipped.

## Method

Two evidence classes, kept distinct throughout this file per `CLAUDE.md` §1
("say which your claims rest on"):

- **Static** — reading source, computing contrast independently rather than
  trusting the PRD table, and confirming the shipped `web/src/app.css`
  matches PRD §4.2's token values byte-for-byte.
- **Real browser** — `safaridriver` (`/System/Cryptexes/App/usr/bin/safaridriver
  -p 4499`) driving actual Safari 26.6.2 against the real Go server, real
  Postgres (a scratch database, `opencircuit_test_0063browse`, dropped when
  done), and Vite's dev server (`web/dist/index.html` was never touched — no
  `npm run build` ran). Driven entirely through `execute/sync` (never
  element-click or the Actions API, both of which are documented to kill the
  session on this machine) — interactions are real DOM method calls
  (`element.click()`, `element.focus()`, `input.dispatchEvent(new
  Event('input'))`) dispatched from inside the page, which exercise the same
  application code a real click/keystroke would, but are not literally OS-level
  input events.
  - **A genuine environment limit surfaced immediately and is disclosed
    rather than routed around**: `document.hasFocus()` returned `false` for
    the whole session — the automation window never became the OS's key
    window in this sandbox (`osascript ... to activate` ran but the frontmost
    process kept reverting to an unrelated app). That means CSS `:focus` /
    `:focus-visible` pseudo-class matching could not be visually confirmed
    live, even though `document.activeElement` (the DOM-level focus state,
    which is real and unaffected by OS window focus) could. Two things fill
    that gap: (1) `document.activeElement` identity checks, which are exactly
    as strong as a real Tab-driven focus for proving *where* focus lands —
    they only stop short of proving the *visual ring paints*; and (2) reading
    the actual parsed, running stylesheet's `CSSRule.cssText` for every
    `:focus`/`:focus-visible` rule this audit touches, confirming the
    selector and declaration reached the browser as authored. What this audit
    could **not** do: watch a real focus ring render on screen, or listen to
    VoiceOver speak. Both are named explicitly wherever a claim below depends
    on them.
  - No headless-Chromium narrow-viewport pitfall applies here (`CLAUDE.md`
    §8: the ~485px floor is a headless-Chromium-specific artifact) — Safari's
    real `window/rect` was resized to 380px directly and `document
    .documentElement.scrollWidth` compared against `window.innerWidth`.

## Contrast — recomputed independently, not read off the PRD table

Wrote a standalone WCAG 2.1 relative-luminance calculator
(`/tmp/contrast.py`, not committed — scratch) and ran it against every
token pair in `web/src/app.css`'s shipped `:root` / dark-mode values
(confirmed identical to `PRD.md` §4.2's table, hex for hex). Recomputed
ratios matched the PRD table's ranges to within rounding on every row:
`--text` 15.80–18.60 (light) / 14.35–16.80 (dark), `--text-muted`
6.44–7.58 / 6.67–7.81, `--text-faint` 4.82–5.67 / 4.78–5.60, `--accent`
4.39–5.17 / 12.65–14.80, `--accent-text` on `--accent` 5.17 / 14.80. Also
reconfirmed the two facts `CLAUDE.md` §8 already states rather than
re-deriving them as new: brand green `#68FF23` measures **1.32:1** on white
(1.3194 computed) and 14.80:1 on the dark page background.

`--border-strong` (decorative-only, focus rings deliberately use `--accent`
instead per §4.2's own rule) computes to 2.64–3.11 across the three
backgrounds in light and 2.63–3.08 in dark — consistent with, and not
contradicting, the project's standing "insufficient for a focus indicator"
call; not a new finding.

Non-text UI: the global focus ring (`app.css:268`,
`:where(a, button, summary, [tabindex]):focus-visible { outline: 2px solid
var(--accent); outline-offset: 2px; }`) uses `--accent`, which clears 3:1
everywhere per the table above.

## Theme toggle — real browser

`Header.svelte`'s toggle is a native `<button>` (keyboard-operable by
construction — Enter/Space activate any native button; not independently
re-verified with a literal keydown event, which the "execute/sync only"
constraint makes awkward to simulate faithfully). Live in Safari, starting from the default `auto` state: two `.click()` calls
observed `auto → light → dark`, each one updating
`document.documentElement`'s `data-theme` attribute AND the button's
`aria-label` (`"Theme: Auto. Activate to change."` → `"...Light..."` →
`"...Dark..."`) on the same button element (never recreated). The
announcement claim rests on established assistive-technology behavior for an
accessible-name (`aria-label`) mutation on the currently-focused element —
well-documented behavior, not something this sandbox could confirm by ear.

## Color and motion — static

No information conveyed by color alone: the `[ OK ]` decorations
(`StatusList.svelte`) are `aria-hidden`, label text carries the meaning
(matches PRD §7.5's own listed rule verbatim); every status badge across the
admin console (`grep` found 12 call sites) always pairs its color class with
a `{...Label}` text child, never color alone; the active-nav-link indicator
is both `aria-current="page"` AND a visual underline plus `font-weight: 600`
(`Header.svelte`).

Motion: exactly one animation in the whole SPA (`CommandLine.svelte`'s
cursor `blink`), already guarded by `@media (prefers-reduced-motion: reduce)
{ animation: none; }`. `web/src/app.css` has zero `transition`/`animation`
declarations of its own; no Svelte `transition:` directives anywhere in
`web/src`. Not independently exercised under a forced OS reduced-motion
setting (this sandbox has no path to toggle that) — this claim rests on
reading the CSS, not on observing the animation actually stop.

## The role="status" pattern — decided and applied (carried in from #0162/#0167)

See the carried-in section immediately below for the full background. The
decision: **a live region that must announce a state change gets ONE
persistent DOM node, present from first render, whose text (and only its
text/class) mutates** — never an `{#if}` that creates the element fresh with
its content already inside it. Applied to the four sites `#0162`'s review
named, plus two more of the same defect class this audit's live-browser pass
found while verifying the four flows (see below):

1. `web/src/views/admin/WorkshopEditor.svelte` — the preview-staleness cue
   (`#0167`): was `{#if previewStale}<p role="status">...</p>{/if}` nested
   inside the `hasPreviewContent` branch; now the `<p>` is unconditional
   within that branch, text `''` when not stale.
2. `web/src/views/admin/WorkshopEditor.svelte` — the unsaved-interests hint
   (`#0151`/`#0162`): was `{#if unsavedInterestsHint}<p role="status">
   {unsavedInterestsHint}</p>{/if}`; `unsavedInterestsHint` was already `''`
   when nothing to show, so the fix is just removing the `{#if}`.
3. `web/src/views/Admin.svelte` — the new-interest-slug format hint (the
   review's `:1283` precedent, current location `~1358`): same treatment,
   ternary text inside an unconditional `<p>`.
4. `web/src/views/Admin.svelte` — the interest-deactivation hint (the
   review's `:1451` precedent, current location `~1529`): same treatment.

**Two more found and fixed while live-verifying the four required flows**
(not among the four named sites, but the identical defect, discovered by the
kind of check this audit exists to run — see `## Real-browser proof` below
for the empirical method):

5. `web/src/views/PreferenceCenter.svelte` — `saveError`/`saveMessage`
   (Interests section) and `unsubscribeError` (Leave-the-list section) were
   each `{#if x}<p role="status"|aria-live>{x}</p>{/if}`. Now unconditional,
   `{x ?? ''}`.
6. `web/src/lib/SubscribeForm.svelte` — the form-level error message
   **looked** like the correct "present from first render, empty by
   default" pattern already (an `{:else}` branch rendering an empty
   `sr-only` paragraph with the same `id`) — and was proved live, in real
   Safari, to be the anti-pattern anyway: Svelte destroys and recreates the
   element across an `{#if}/{:else}` boundary even when both branches use
   the same tag and `id`. Fixed the same way as the others: one `<p>`,
   `class={errorMessage ? 'text-error' : 'sr-only'}`, no `{#if}`. See
   `## Real-browser proof` for the DOM-identity proof this rests on.

**Whole-panel swaps deliberately did NOT get this treatment.**
`PreferenceCenter.svelte`'s `unsubscribed`/`unsubscribeNoOp` branches and
`ConfirmSubscription.svelte`'s `confirming → success/error` transition
replace the *entire* visible panel (there is no single persistent node to
carry text across the swap) — these instead now move focus to the new
panel's own heading/result message (`tabindex="-1"`, `bind:this`, `.focus()`
after `tick()`), mirroring `Unsubscribe.svelte`'s pre-existing, already-correct
pattern for its own `confirm → done` swap. Programmatic focus movement is the
established alternative to a live region for a whole-section replacement
(WAI-ARIA APG); reusing `Unsubscribe.svelte`'s own precedent rather than
inventing a second pattern.

## Real-browser proof (not jsdom) for the role="status"/focus-movement fixes

Every fix above was proved against the real running app, not asserted from
reading the diff:

- **`PreferenceCenter.svelte` save flow** — loaded `/preferences?token=...`
  for a real seeded `active` subscriber, tagged the `saveMessage` `<p>` node
  with `el.__marker0063 = true` before clicking Save, then re-read the same
  query after the click: `{"count":1,"text":"Preferences saved. You're
  subscribed to general announcements only.","sameNode":true}`. Same node,
  text mutated.
- **`PreferenceCenter.svelte` unsubscribe flow** — a second seeded `active`
  subscriber; clicked "Unsubscribe from everything"; confirmed
  `document.activeElement` was literally the new `.result-message` node
  (`role="status"`, `tabindex="-1"`) — proof the focus-movement fix landed,
  not just that the text appeared.
- **`PreferenceCenter.svelte` complained flow** — a seeded `complained`
  subscriber; confirmed the rendered sentence and its `mailto:` anchor
  exactly match `subscribe.ts`'s composed `LEAD + CONTACT_EMAIL + TAIL` (the
  same invariant `#0095` guards mechanically on the Go side):
  `"...Contact us at hello@opencircuitsf.com if you believe this is a
  mistake."`, `anchorHref: "mailto:hello@opencircuitsf.com"`.
- **`ConfirmSubscription.svelte`** — one seeded `pending` subscriber per
  branch (confirm tokens are single-use, so a fresh row was seeded for the
  success case after an earlier request consumed the first one — confirmed
  the replay correctly fell into the *error* branch, itself a proof that
  single-use enforcement works). Both `error` (`"This link didn't work"`)
  and `success` (`"You're confirmed"`) branches: `document.activeElement`
  was the new `<h1>` (`tabindex="-1"`).
- **`SubscribeForm.svelte`** — loaded `/subscribe`, tagged the (initially
  empty) `#subscribe-form-error` node, submitted the form empty. **Before
  the fix**: `sameNode: false` (a NEW node was created — the anti-pattern,
  hiding in plain sight behind code that looked safe). **After the fix**
  (confirmed via Vite HMR picking up the edit, then re-running the identical
  script): `sameNode: true`, `className` swapped `sr-only → text-error`,
  text populated, and `aria-describedby="subscribe-form-error"` /
  `aria-invalid="true"` on the email input were both present and pointing at
  that same node.
- **End-to-end signup**: filled the real email field via a dispatched
  `input` event, clicked Submit, and landed on `/subscribe/thanks` with
  `<h1>Check your email</h1>` — the full response-invariance path (`#0026`)
  exercised against the real Go handler and Postgres, not mocked.

## What "VoiceOver" verification rests on instead

VoiceOver itself was not driven — no reliable way was found in this sandbox
to obtain OS-level window/key focus for the automated Safari session (see
`## Method`), and VoiceOver's actual announcements are audio, not something
`execute/sync` can capture. What the four flows above got instead is
stronger than a jsdom test but short of the acceptance criterion as
literally written:

- Every live-region node's `role`/`aria-live` attribute, presence from first
  render, and DOM-identity persistence across the update it exists to
  announce — confirmed in real Safari, real DOM, real application code.
- Every focus-movement fix's actual target — confirmed via
  `document.activeElement` identity, which is the DOM-level fact a screen
  reader's own focus-tracking is built on.
- The composed sentence and its `mailto:` anchor in the complained-copy
  branch, matching what `#0095`'s Go-side parity test enforces server-side.

What is **not** claimed: that VoiceOver actually spoke any of this aloud, or
that the visual focus ring painted (see `## Method`'s disclosure of the
`document.hasFocus() === false` limitation). A future pass with either a
non-sandboxed machine or a different automation path (e.g. `sim.sh`'s iOS
Simulator route, which drives a full OS with real window focus) could close
that specific gap; it is named here rather than silently assumed closed.

## New defects found (report only — not filed; `CLAUDE.md` §9)

**1. No SPA route-change accessibility handling anywhere in the router —
the most significant finding of this audit.** `web/src/lib/router.ts`'s
`navigate()` never updates `document.title` (`grep -rn "document.title"
web/src` returns zero matches in the whole tree) and nothing in
`App.svelte`/`router.ts` moves focus on a route change. Confirmed live: after
the end-to-end signup flow above navigated `/subscribe → /subscribe/thanks`
via the router (not a full page load), `document.activeElement` was
`<body>` — focus was dropped on the floor, and the tab title never changed
from whatever the entry page's server-injected title was. This means a
screen-reader user clicking any nav link, or completing any in-app action
that calls `navigate()`, gets **no signal that the page changed** beyond
whatever they happen to notice by re-exploring — no title update (the
mechanism many screen readers specifically watch for), no focus movement to
the new page's landmark or heading. This is distinct from, and larger than,
every per-component fix in this issue: those fixed six specific
already-mounted live regions/panels; this is a gap in the router itself,
affecting every one of the ~15 public routes. Fixing it properly needs a
design decision this audit's scope does not cover (title-per-route format,
whether to focus `<main>` or the new page's `<h1>`, whether skip-link
interaction should change) — recommend a Phase-1 planning pass per
`CLAUDE.md` §3 rather than folding it into this issue.

**2. `document.title` is a static placeholder in every environment this
audit could reach.** Both the Vite dev harness (`%%OC_TITLE%%`, a template
token never substituted client-side) and — inferred from finding #1's
`grep`, not independently loaded against `--built` mode this session — very
likely the built SPA too, since nothing in `web/src` ever calls
`document.title = `. Server-side injection (PRD §7.4) only ever runs once,
for the entry request; every subsequent SPA-internal navigation keeps
whatever title the entry page shipped. Same root cause as #1; listed
separately because it is independently checkable and because a fix for #1
would very likely subsume it (title-per-route is usually implemented as part
of the same route-change hook that would carry focus management).

Neither of these blocks this issue's own acceptance criteria (which name
keyboard reachability, focus-ring visibility, and the four specific flows —
all of which this audit did verify) — they are new, real findings the audit
surfaced by exercising the app rather than reading it, exactly the kind of
thing criterion 10 asks to be reported rather than silently left out of the
writeup.

## Carried in from `#0162`/`#0167`'s review (2026-08-22)

**Every `role="status"` in the admin console is created and populated in the same
tick**, by an `{#if}` that inserts the element with its text already in it — the
unsaved-interests hint, the preview staleness cue, and both `Admin.svelte`
precedents (`:1283` slug-format, `:1451` interest-deactivation). Screen-reader
support for announcing a live region inserted *with* content is inconsistent; the
robust pattern is a region present from first render whose text swaps.

`#0162`'s criteria explicitly forbade inventing a console-wide pattern there and
deferred it here. This audit should decide the pattern once and apply it to all
four sites, rather than each screen guessing.

Related, from the same review: a live region already populated at first render is
not announced by design — which is why the Announce panel's targeting sentence
correctly does **not** carry `role="status"` while the hint beside it does.

## Gotchas

- `document.hasFocus()` was `false` for the entire `safaridriver` session in
  this sandbox despite `osascript ... to activate` reporting success — CSS
  `:focus`/`:focus-visible` could not be visually confirmed live. Worked
  around via `document.activeElement` identity checks (real, unaffected by
  OS window focus) plus reading the actual parsed stylesheet's rule text.
  Disclosed in full under `## Method` rather than silently substituting a
  weaker check for a stronger claim.
- `SubscribeForm.svelte`'s pre-fix code is the clearest example in this audit
  of why "looks like the safe pattern" isn't evidence: an `{#if}/{:else}`
  with two branches sharing a tag name AND an `id` attribute reads, on a
  diff, exactly like the robust "persistent node, text swaps" pattern this
  issue's carried-in section describes — and is not, because Svelte's
  `{#if}/{:else}` compiles to two independently mounted blocks regardless of
  whether their markup happens to look identical. Only the live DOM-identity
  check (`__marker` property surviving the transition) caught it.
- Confirm tokens are single-use (`internal/subscribers` clears
  `confirm_token` on a successful confirm) — the first live-browser pass
  through `/confirm` consumed the seeded token, so testing the *success*
  branch's focus-movement fix required seeding a second `pending` row rather
  than reusing the first. The resulting "replay correctly fell into the
  error branch" observation is itself a small piece of incidental evidence
  that single-use enforcement works, not a bug.
