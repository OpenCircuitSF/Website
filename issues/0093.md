## Description

`internal/handlers/preferences.go:121` tags the field `json:"no_op,omitempty"`.
`internal/handlers/admin_subscribers.go:368` — the handler it says it mirrors — tags it
plain `json:"no_op"`.

The codebase documents the convention and then breaks it one line later:
`preferences.go:120` carries a comment saying the field "mirrors
`AdminSubscribersHandler.Suppress`'s `no_op` field, `#0032`", and line 121 does not
mirror it.

`omitempty` on a `bool` erases the difference between `false` and absent. The frontend
already encodes the split rather than the intent: `web/src/lib/api.ts:426` types the
admin field as required, `web/src/lib/types.ts:175` types this one as optional, and in
JavaScript `undefined !== false`. Harmless only because of what today's callers happen
to do with it — any consumer that branches on the field sees two different contracts
depending on which endpoint answered.

Deliberately left alone during `#0090` (out of lane, file under concurrent review).
Recording it so it is tracked rather than wished for.

## Acceptance criteria

- [x] Both handlers serialise `no_op` under one schema — prefer dropping `omitempty`
      so `false` is always explicit, matching `#0032`'s original
- [x] `web/src/lib/types.ts` updated to match if the field stops being optional
- [x] A handler test asserts the field is **present and `false`** in a non-no-op
      response from *both* endpoints — the assertion `omitempty` currently defeats
- [x] The `preferences.go:120` comment is true after the change

## Implementation notes

**Facts established before changing anything:**

- Two handlers named by this issue: `PreferencesHandler` (`internal/handlers/preferences.go`,
  `GET`/`PATCH /api/preferences`) tagged its `preferencesResponse.NoOp`
  `json:"no_op,omitempty"`. `AdminSubscribersHandler.Suppress`
  (`internal/handlers/admin_subscribers.go`, `POST /admin/subscribers/{id}/suppress`)
  tagged its `suppressResponse.NoOp` plain `json:"no_op"`. `omitempty` on a `bool`
  means a `false` value is dropped from the wire entirely — a client checking
  `body.no_op === true` sees the same thing either way, but a client checking
  `body.no_op !== undefined` (or a strict-typed client where the field is
  optional on one endpoint and required on the other, exactly what
  `web/src/lib/types.ts` had) cannot write one branch for both.
- A **third** occurrence was found that the issue text doesn't name:
  `UnsubscribeHandler.Post` (`internal/handlers/unsubscribe.go`,
  `POST /api/unsubscribe`, `#0034`) also emits a `no_op` field
  (`unsubscribeResponse.NoOp`), and its tag was already plain `json:"no_op"` —
  its doc comment explicitly says it was written to match
  `admin_subscribers.go`'s shape *in anticipation of* this issue's resolution
  ("Rather than add a third shape to that drift ... since that is the shape
  #0093 itself names as correct"). So going in, 2 of 3 no_op-bearing
  responses already agreed; `preferences.go` was the outlier.
- Client consumption: `web/src/lib/types.ts`'s `PreferencesResponse.no_op` was
  `no_op?: boolean` (optional) — the one place the drift reached the SPA's type
  layer. `web/src/lib/unsubscribe.ts`'s `UnsubscribeResult.no_op` and
  `web/src/lib/api.ts`'s admin-suppress return type both already declared
  `no_op: boolean` (required), matching the two endpoints that never carried
  `omitempty`. In practice `PreferenceCenter.svelte` doesn't currently branch
  on `res.no_op` at all — it branches on `res.unsubscribed` instead (see
  `onUnsubscribeEverything`, line ~172) — so the optional typing wasn't
  causing a live bug, only latent contract drift, matching this issue's Notes.
- No test in `preferences_test.go` asserted the field's wire presence at all
  before this change (only `admin_subscribers_test.go` did, and even that
  only by decoding into a Go struct, which can't distinguish an explicit
  `false` from an omitted key — the tag having no `omitempty` there is what
  actually guaranteed presence, not the test).
- `PRD.md` §8 (`sed -n '/^## 8\. /,/^## [0-9]/p' PRD.md`) lists both routes'
  purpose but does not specify a JSON field-tag convention for either — it
  does not settle this by itself. The issue's own acceptance criteria (citing
  `#0032`'s original design) is what settles it.

**Enumeration-oracle check (CLAUDE.md §9):** `PATCH /api/preferences` and
`POST /api/unsubscribe` are both reachable only with a valid `manage_token` —
a secret credential mailed to the subscriber, not derived from a
caller-supplied email address the way `POST /api/subscribe`'s input is.
Reaching either the no-op branch or the real-unsubscribe branch already
requires possessing that token, so making `no_op` uniformly present (instead
of sometimes omitted) does not let an unauthenticated caller learn anything
about an arbitrary email address's subscription status — there is no new
"guess an address, read the response" oracle here. `POST /admin/subscribers/
{id}/suppress` is session+admin-gated, so the same reasoning applies even
more directly. The fix converges the *shape*, not the *information* each
endpoint discloses, and does not touch either endpoint's existing 404-vs-200
distinction (`PreferencesHandler.Get`/`Patch` 404 an unknown token;
`UnsubscribeHandler.Post` always 200) — that distinction predates this issue
and is out of scope for it.

**Fix:** dropped `,omitempty` from `preferences.go`'s `NoOp` tag
(`json:"no_op,omitempty"` → `json:"no_op"`), updated its doc comment to state
this and to reference `unsubscribe.go` already matching. Updated
`unsubscribe.go`'s package doc comment ("Response schema" section), which
described `#0093` as "open, not fixed here" — now describes the fix as
landed and all three shapes as converged. Updated
`web/src/lib/types.ts`'s `PreferencesResponse.no_op?: boolean` →
`no_op: boolean` (no other `.ts`/`.svelte` file constructs a
`PreferencesResponse` literal, so nothing else needed a type-level change).

**Tests added** (acceptance criterion 3, "present and false in a non-no-op
response from both endpoints"): both new assertions parse the raw response
body into a `map[string]any` rather than decoding into a typed struct, since
struct-decoding can't distinguish an explicit `false` from an omitted key.

- `internal/handlers/preferences_test.go`,
  `TestPreferencesHandler_Patch_UnsubscribeEverything` (the ordinary,
  non-no-op unsubscribe case) — added a raw-JSON check that `"no_op"` is
  present and `false`, plus a `resp.NoOp` struct-level assertion that was

- `internal/handlers/admin_subscribers_test.go`,

### Enumeration-oracle analysis (CLAUDE.md §9) — checked by execution

The implementer's argument was tested rather than read. A throwaway probe
(deleted after the run; seeded its own subscribers via
`Create`+`Confirm`+`MarkComplained`, never a literal or seeded id) drove every
branch of both token-gated endpoints and printed the raw bodies:

```
POST /api/unsubscribe
  no token          -> 200 {"message":"If this address was on our list, it has been unsubscribed.","no_op":true}
  garbage token     -> 200 {"message":"If this address was on our list, it has been unsubscribed.","no_op":true}
  VALID complained  -> 200 {"message":"No change: this address is marked as having complained ...","no_op":true}
  VALID active      -> 200 {"message":"You've been unsubscribed.","no_op":false}

PATCH /api/preferences {unsubscribe:true}
  no token          -> 404 {"error":"invalid or expired preferences link"}
  garbage token     -> 404 {"error":"invalid or expired preferences link"}
  VALID complained  -> 200 {... ,"unsubscribed":false,"no_op":true}
  VALID active      -> 200 {... ,"unsubscribed":true,"no_op":false}

GET /api/preferences
  no token / garbage token -> 404 {"error":"invalid or expired preferences link"}
```

**1. The token really is required to reach both branches — verified by
execution, not by reading.** On `/api/preferences`, no path without a valid
`manage_token` emits a `preferencesResponse` at all: a missing token and a
garbage token both short-circuit to a byte-identical `404
{"error":"invalid or expired preferences link"}` before `patchUnsubscribe` or
`patchInterests` is ever reached, so the `no_op` field is unreachable to a
caller who does not hold a token. On `/api/unsubscribe` every input answers 200
by design (PRD §6.5), so `no_op` *is* present in the tokenless body — but its
value there is a constant `true`, identical to the garbage-token body, and it
carries no information about any address. `POST /admin/subscribers/{id}/suppress`
is session+`is_admin` gated, re-confirmed by
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` (unchanged by this commit).

**2. `writeNeutral`'s two different `message` texts for `no_op:true` — the thing
flagged for me. It is a real distinction, it is not an oracle worth closing, and
the two messages must NOT converge.** The probe confirms the premise: a garbage
token gets `"If this address was on our list, it has been unsubscribed."` while a
valid token on a complained row gets `"No change: this address is marked as
having complained ..."`. So the response does distinguish "this token is real"
from "this token is nonsense". Three reasons that is acceptable here:

- **It is not an email-enumeration oracle, which is what §9 protects against.**
  §9's rule exists because `POST /api/subscribe` is keyed on a *caller-supplied
  email address* — an attacker picks the input and walks an address space. This
  endpoint's input is a `manage_token`: 32 bytes from `crypto/rand`
  (`internal/subscribers/tokens.go:20`, documented at `store.go:23`), 256 bits
  with no attacker-choosable structure. There is no address to guess with, and
  guessing tokens is not a feasible attack.
- **Token validity is already, and necessarily, distinguishable one branch
  over.** A valid token on a live row returns `"You've been unsubscribed."` with
  `no_op:false` — a strictly louder validity signal than the complained message,
  and one the endpoint cannot give up, because RFC 8058 requires it to actually
  perform the unsubscribe and `#0036`'s `/unsubscribe` view renders that
  message. Converging the two `no_op:true` texts would therefore close no
  channel that the success branch does not already leave wide open. The only
  party who can observe any of this is someone already holding the subscriber's
  own secret token.
- **Converging them would regress two prior decisions.** Folding the complained
  text into the neutral one would tell a real complained subscriber their
  unsubscribe succeeded when nothing happened — precisely the false-success
  claim `#0031` review finding 2 forbade and `#0090`'s bounce fix hardened
  (`preferences.go` even names a contact address for exactly this case).
  Folding the other direction would tell every random caller they had
  complained, which is strictly worse. `web/src/lib/unsubscribe.ts`'s module
  doc is already precise about this: the contract is that every input returns
  the same *shape* and never a non-2xx — "differing only in the wording the
  server itself already chose". That is the correct contract and it is intact.

**3. On §9's byte-identical assertion.** `TestSubscribe_UniformResponseAcrossBranches`
compares bodies **and headers** byte-for-byte across all nine `POST
/api/subscribe` branches; it passes here, untouched. **No equivalent assertion
exists for `/api/unsubscribe` or `/api/preferences`, and none should be added** —
byte-identity is the wrong property for both. `/api/unsubscribe` deliberately
varies its message (above), and `/api/preferences` deliberately 404s an unknown
token, a decision `unsubscribe.go`'s package doc calls out as "the deliberate
opposite" of its own behaviour and `#0034` carried in explicitly. What these two
routes owe is *shape* uniformity, and that is what this issue converged and what
the new assertions now pin.

### Residual — worth a follow-up issue, not a bounce

`unsubscribe.go`'s `unsubscribeResponse.NoOp` — the third converged site — has
**no test that would catch `omitempty` being reintroduced there**. Proven:
adding `,omitempty` to it and running the whole `internal/handlers` package
gives `ok ... 2.509s`. This is not a defect in `5e88d07` (that site was already
correct before the commit and still is, and acceptance criterion 3 names only
the two endpoints the issue itself tracked, both of which are now pinned and
mutation-proven), but the commit's own doc comments now assert that *all three*
`no_op`-bearing responses share one schema while only two of the three are
enforced by a test. A raw-JSON presence assertion in
`TestUnsubscribeHandler_Post_ValidToken_UnsubscribesRotatesAndAudits`, matching
the two the implementer added, would close it. Reported to the orchestrator to
file; not filed here (CLAUDE.md §9).
