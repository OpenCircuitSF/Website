# 0093 — Two handlers serialise `no_op` under two different JSON schemas

| | |

## Description

`internal/handlers/preferences.go:121` tags the field `json:"no_op,omitempty"`.
`internal/handlers/admin_subscribers.go:368` — the handler it says it mirrors — tags it
plain `json:"no_op"`.

The codebase documents the convention and then breaks it one line later:
`preferences.go:120` carries a comment saying the field "mirrors
`AdminSubscribersHandler.Suppress`'s `no_op` field, `#0032`", and line 121 does not
mirror it.

`omitempty` on a `bool` erases the difference between `false` and absent. The frontend
already encodes the split rather than the intent: `web/src/lib/api.ts:426` types the
admin field as required, `web/src/lib/types.ts:175` types this one as optional, and in
JavaScript `undefined !== false`. Harmless only because of what today's callers happen
to do with it — any consumer that branches on the field sees two different contracts
depending on which endpoint answered.

Deliberately left alone during `#0090` (out of lane, file under concurrent review).
Recording it so it is tracked rather than wished for.

## Acceptance criteria

- [ ] Both handlers serialise `no_op` under one schema — prefer dropping `omitempty`
      so `false` is always explicit, matching `#0032`'s original
- [ ] `web/src/lib/types.ts` updated to match if the field stops being optional
- [ ] A handler test asserts the field is **present and `false`** in a non-no-op
      response from *both* endpoints — the assertion `omitempty` currently defeats
- [ ] The `preferences.go:120` comment is true after the change

## Implementation notes

**Facts established before changing anything:**

- Two handlers named by this issue: `PreferencesHandler` (`internal/handlers/preferences.go`,
  `GET`/`PATCH /api/preferences`) tagged its `preferencesResponse.NoOp`
  `json:"no_op,omitempty"`. `AdminSubscribersHandler.Suppress`
  (`internal/handlers/admin_subscribers.go`, `POST /admin/subscribers/{id}/suppress`)
  tagged its `suppressResponse.NoOp` plain `json:"no_op"`. `omitempty` on a `bool`
  means a `false` value is dropped from the wire entirely — a client checking
  `body.no_op === true` sees the same thing either way, but a client checking
  `body.no_op !== undefined` (or a strict-typed client where the field is
  optional on one endpoint and required on the other, exactly what
  `web/src/lib/types.ts` had) cannot write one branch for both.
- A **third** occurrence was found that the issue text doesn't name:
  `UnsubscribeHandler.Post` (`internal/handlers/unsubscribe.go`,
  `POST /api/unsubscribe`, `#0034`) also emits a `no_op` field
  (`unsubscribeResponse.NoOp`), and its tag was already plain `json:"no_op"` —
  its doc comment explicitly says it was written to match
  `admin_subscribers.go`'s shape *in anticipation of* this issue's resolution
  ("Rather than add a third shape to that drift ... since that is the shape
  #0093 itself names as correct"). So going in, 2 of 3 no_op-bearing
  responses already agreed; `preferences.go` was the outlier.
- Client consumption: `web/src/lib/types.ts`'s `PreferencesResponse.no_op` was
  `no_op?: boolean` (optional) — the one place the drift reached the SPA's type
  layer. `web/src/lib/unsubscribe.ts`'s `UnsubscribeResult.no_op` and
  `web/src/lib/api.ts`'s admin-suppress return type both already declared
  `no_op: boolean` (required), matching the two endpoints that never carried
  `omitempty`. In practice `PreferenceCenter.svelte` doesn't currently branch
  on `res.no_op` at all — it branches on `res.unsubscribed` instead (see
  `onUnsubscribeEverything`, line ~172) — so the optional typing wasn't
  causing a live bug, only latent contract drift, matching this issue's Notes.
- No test in `preferences_test.go` asserted the field's wire presence at all
  before this change (only `admin_subscribers_test.go` did, and even that
  only by decoding into a Go struct, which can't distinguish an explicit
  `false` from an omitted key — the tag having no `omitempty` there is what
  actually guaranteed presence, not the test).
- `PRD.md` §8 (`sed -n '/^## 8\. /,/^## [0-9]/p' PRD.md`) lists both routes'
  purpose but does not specify a JSON field-tag convention for either — it
  does not settle this by itself. The issue's own acceptance criteria (citing
  `#0032`'s original design) is what settles it.

**Enumeration-oracle check (CLAUDE.md §9):** `PATCH /api/preferences` and
`POST /api/unsubscribe` are both reachable only with a valid `manage_token` —
a secret credential mailed to the subscriber, not derived from a
caller-supplied email address the way `POST /api/subscribe`'s input is.
Reaching either the no-op branch or the real-unsubscribe branch already
requires possessing that token, so making `no_op` uniformly present (instead
of sometimes omitted) does not let an unauthenticated caller learn anything
about an arbitrary email address's subscription status — there is no new
"guess an address, read the response" oracle here. `POST /admin/subscribers/
{id}/suppress` is session+admin-gated, so the same reasoning applies even
more directly. The fix converges the *shape*, not the *information* each
endpoint discloses, and does not touch either endpoint's existing 404-vs-200
distinction (`PreferencesHandler.Get`/`Patch` 404 an unknown token;
`UnsubscribeHandler.Post` always 200) — that distinction predates this issue
and is out of scope for it.

**Fix:** dropped `,omitempty` from `preferences.go`'s `NoOp` tag
(`json:"no_op,omitempty"` → `json:"no_op"`), updated its doc comment to state
this and to reference `unsubscribe.go` already matching. Updated
`unsubscribe.go`'s package doc comment ("Response schema" section), which
described `#0093` as "open, not fixed here" — now describes the fix as
landed and all three shapes as converged. Updated
`web/src/lib/types.ts`'s `PreferencesResponse.no_op?: boolean` →
`no_op: boolean` (no other `.ts`/`.svelte` file constructs a
`PreferencesResponse` literal, so nothing else needed a type-level change).

**Tests added** (acceptance criterion 3, "present and false in a non-no-op
response from both endpoints"): both new assertions parse the raw response
body into a `map[string]any` rather than decoding into a typed struct, since
struct-decoding can't distinguish an explicit `false` from an omitted key.

- `internal/handlers/preferences_test.go`,
  `TestPreferencesHandler_Patch_UnsubscribeEverything` (the ordinary,
  non-no-op unsubscribe case) — added a raw-JSON check that `"no_op"` is
  present and `false`, plus a `resp.NoOp` struct-level assertion that was
  missing before.
- `internal/handlers/admin_subscribers_test.go`,
  `TestAdminSubscribers_Suppress_ActiveSubscriberBecomesUnsubscribed` (the
  ordinary, non-no-op suppress case) — added the same raw-JSON presence/value
  check, for symmetry and to make the "both endpoints" criterion verifiable
  by a test rather than by the tag alone.

**Convergence proof (executed, then discarded — not part of the committed
diff):** wrote a throwaway test seeding one subscriber via
`subscribers.Store.Create`+`Confirm`+`MarkComplained` for the preferences
path and one via `seedTestSubscriber(t, pool, subscribers.StatusComplained)`
for the admin path (both non-literal, throwaway ids per CLAUDE.md §8b), drove
both to their `no_op:true` branch, and printed the raw bodies:

```
preferences PATCH raw body: {...,"unsubscribed":false,"no_op":true}
admin suppress raw body:    {...,"no_op":true,"suppression_added":true,...}
```

Both carry a top-level `"no_op":true` of the same JSON type (`bool`),
present and equal. The two envelopes differ in every other field (as
intended — they answer different questions), which is not this issue's
concern; only the `no_op` field itself was ever specified to converge. The
test file was deleted after this passed (`git status` after deletion showed
only the four intended files changed) so it never entered the commit.

**`#0104` regression check:** re-ran
`TestPreferencesHandler_Patch_ComplainedBetweenLookupAndUnsubscribe_IsNoOp`,
`TestUnsubscribeHandler_Post_ComplainedBetweenLookupAndUnsubscribe_IsNoOp`,
`TestPreferencesHandler_Patch_UnsubscribeEverything_ComplainedIsNoOpNoAudit`,
and `TestUnsubscribeHandler_Post_Complained_IsSilentNoOp` — all `--- PASS`.
This change only touches the `NoOp` struct tag and doc comments; it does not
touch how either handler *decides* `noOp` (`updated.Status ==
subscribers.StatusComplained`, derived from the row `Store.Unsubscribe`
returns), so `#0104`'s fix is untouched and unregressed.
