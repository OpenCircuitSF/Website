## Description

`/confirm?token=` completes double opt-in and rolls straight into the preference center so the subscriber lands somewhere useful.

## Acceptance criteria

- [ ] `GET /confirm?token=` renders the SPA view and has no side effect — safe against link prefetchers
- [ ] `POST /api/subscribe/confirm` validates the token, sets status `active`, stamps `confirmed_at`, and clears `confirm_token`
- [ ] Unknown or expired token returns 400 with an offer to subscribe again
- [ ] A token already used returns a friendly "already confirmed" state, not an error
- [ ] On success the response includes the `manage_token` so the SPA can show the preference center inline without a second email
- [ ] Audit row `subscriber.confirmed` written
- [ ] Token compared in constant time
- [ ] Handler tests cover valid, expired, unknown, and replayed tokens

## Notes

PRD §6.3. **The GET must never mutate.** Mail clients, link scanners, and corporate security proxies prefetch every URL in a message; a confirming GET would auto-confirm addresses that never clicked — which is exactly the consent evidence double opt-in exists to produce.

Handing back the `manage_token` on success is what makes the flow feel finished rather than dumping the user on a dead-end "thanks" page.
