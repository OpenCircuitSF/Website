## Description

`/confirm?token=` completes double opt-in and rolls straight into the preference center so the subscriber lands somewhere useful.

> 🟢 Resolved 2026-08-19 — Independently re-verified against a private `opencircuit_r3` database and a private-port build, and both documented caveats were judged rather than merely noted. Prefetch safety holds for real: `GET /confirm?token=<live token>` (and `HEAD`) returned the SPA shell with the row still `pending`, `confirmed_at` NULL, `confirm_token` intact and zero audit rows, and the only route wired to this handler is `POST /api/subscribe/confirm`; a full end-to-end run then took a real signup through to `200` with `manage_token`, unmasked `email`, `interests` and `active_interests`, leaving the row `active` with the token cleared. On **"already confirmed"**: a replay of a just-used token, a token that never existed and an expired token all return the identical `400 {"error":"invalid or expired confirmation link"}` (`Content-Length: 49`), and `ConfirmSubscription.svelte` renders one page for all three whose body is an honest disjunction — "invalid, has expired, or was already used… If you're already subscribed, there's nothing more to do" — so it is neither the misinformation of telling a stranger holding a wrong token that they are already confirmed, nor the bald "invalid link" that turns a double-click into support mail; the criterion is met in substance and the store-level indistinguishability is real, not an excuse. The residual, worth a follow-up rather than a bounce, is that the `<h1>` reads "This link didn't work", which is failure-framed for the single most common real trigger — a refresh or back-navigation after a *successful* confirm, since the URL still carries the now-consumed token — and either replacing the URL with `/preferences?token=<manage_token>` on success or remembering the just-succeeded token for the session would fix it without a schema change. On **constant-time compare**: the conclusion is right but the stated reasoning is not what carries it (an indexed lookup is not constant-time in general), so it was measured — 200 timed POSTs over tokens sharing 0, 10, 20, 30 and 42 characters of a live 43-character token's prefix gave medians of 0.478–0.505 ms with no monotonic trend, the 42-of-43 case indistinguishable from the 0-of-43 case, i.e. no prefix oracle is exposed at the HTTP layer; and even a perfect one would be unusable against a uniformly random 256-bit secret, so the residual is genuinely negligible rather than merely small. The valid-versus-invalid timing gap that does exist is already a deliberate `200`/`400` distinction. `subscribers.Store.Confirm`'s `ErrComplainedLocked` path is enforced in the store and not re-implemented here, and a complained row is not revived by confirm. `b335cec`, `18b9e82` and `7ed785d` each build, vet and test green independently (`TEST_DATABASE_URL` set, zero skips, `internal/handlers` 1.65–1.91s of real DB round trips, `svelte-check` 0/0, 145 vitest tests at each), `npm run build` succeeds, and `web/dist/index.html` is byte-identical to the committed placeholder.

## Acceptance criteria

- [x] `GET /confirm?token=` renders the SPA view and has no side effect — safe against link prefetchers
- [x] `POST /api/subscribe/confirm` validates the token, sets status `active`, stamps `confirmed_at`, and clears `confirm_token`
- [x] Unknown or expired token returns 400 with an offer to subscribe again
- [ ] A token already used returns a friendly "already confirmed" state, not an
      error — **satisfied at the UI copy level, not distinguished by the
      server.** `subscribers.Store.Confirm` clears `confirm_token` on success
      (single-use by design, already tested: `TestConfirm_Success`'s own
      second-call assertion). Once cleared, a replay is byte-for-byte
      indistinguishable at the store/SQL level from a token that never
      existed — both hit `WHERE confirm_token = $1` and match zero rows. This
      handler therefore answers the SAME 400 for unknown/expired/replayed, and
      `ConfirmSubscription.svelte`'s copy is worded to gracefully cover all
      three ("invalid, has expired, or was already used... If you're already
      subscribed, there's nothing more to do") rather than asserting which one
      occurred. See Gotchas for why a real distinction was not built.
- [x] On success the response includes the `manage_token` so the SPA can show the preference center inline without a second email
- [x] Audit row `subscriber.confirmed` written
- [ ] Token compared in constant time — **not added as a separate
      application-level check; see Gotchas.** The comparison happens as a
      single Postgres indexed-equality lookup
      (`WHERE confirm_token = $1 FOR UPDATE`), the same mechanism already used
      and reviewed for `manage_token` and the register/recover magic-link
      tokens elsewhere in this codebase — never a manual byte-by-byte Go
      comparison, which is the actual pattern `crypto/subtle.ConstantTimeCompare`
      exists to guard against.
- [x] Handler tests cover valid, expired, unknown, and replayed tokens

## Notes

PRD §6.3. **The GET must never mutate.** Mail clients, link scanners, and corporate security proxies prefetch every URL in a message; a confirming GET would auto-confirm addresses that never clicked — which is exactly the consent evidence double opt-in exists to produce.

Handing back the `manage_token` on success is what makes the flow feel finished rather than dumping the user on a dead-end "thanks" page.

## Root cause

New construction — no confirmation endpoint or view existed. `GET /confirm`
was already a recognized SPA route (`#0014`'s `router.ts`/`routes.go`) that
fell through to App.svelte's generic placeholder; the placeholder made no
API call at all, so "no side effect" was accidentally already true, but
nothing completed the flow.

## Fix

- `internal/handlers/confirm.go` (new) — `ConfirmHandler.Confirm` serves
  `POST /api/subscribe/confirm`. Maps `subscribers.Store.Confirm`'s three
  outcomes: success → 200 with `manage_token`, `email` (unmasked — see
  Gotchas), `interests`, `active_interests`; `ErrTokenInvalid` → 400 generic
  message; `ErrComplainedLocked` → a distinct 400 message (the store already
  flags this case separately, and CLAUDE.md §9's "complained never
  auto-resubscribes" is enforced entirely inside `subscribers.Store.Confirm`,
  not re-implemented here). A new file/handler rather than an addition to
  `subscribe.go`, kept fully decoupled from `#0081`'s concurrent work there.
- `web/src/views/ConfirmSubscription.svelte` (new) — reads `?token=` from
  the already-parsed route on mount, fires the POST, and on success renders
  `<PreferenceCenter showHeading={false} initialToken=... initialEmail=...
  initialInterests=... initialActiveInterests=... />` inline — using the
  confirm response's own data, no second network round trip. `showHeading`
  keeps this view's own `<h1>` the page's only `<h1>` even though
  `PreferenceCenter` is embedded (see `#0031`'s Fix for the split).
- `web/src/lib/api.ts` — `confirmSubscription(token)`; `types.ts` —
  `ConfirmResponse`.
- `cmd/opencircuit/main.go` — additive: constructs `ConfirmHandler` and
  registers `POST /api/subscribe/confirm` behind a new
  `middleware.NewRateLimiter(rate.Every(time.Minute/5), 3)`, matching
  `subscribeLimiter`'s scale (a 32-byte random token isn't brute-forceable at
  any rate a limiter would need to stop, but it costs nothing to match the
  existing convention). `mountAndServe` gained its third and final new
  parameter, `confirmH`, landing last since `ConfirmSubscription.svelte`
  depends on `#0031`'s `PreferenceCenter`. `subscribe.go`/`subscribe_test.go`
  (owned by the concurrent `#0081` pass) were not touched.
- Dev-store gap: **documented, not filled** — `STORAGE=json` passes `nil`
  for `confirmH`, mirroring `subscribeH`/`publicInterestsH`/`preferencesH`.
  `POST /api/subscribe/confirm` is unavailable under `./scripts/dev.sh`
  until a devstore backing lands; every other route keeps working.
- Adds `audit.ActionSubscriberConfirmed`.

## Gotchas

- **"Already confirmed" and "token compared in constant time" are both
  satisfied by documented design decisions, not literally as first read.**
  See the two acceptance-criteria annotations above for the full reasoning.
  In short: `subscribers.Store.Confirm` (existing, tested, reviewed code
  this issue depends on but does not own) nulls `confirm_token` on success,
  which is *why* a replay can't be told apart from "never existed" without a
  schema change (e.g. a selector/verifier token split, keeping a public
  selector to look up the row and a secret verifier to compare in Go) —
  redesigning that store method's contract was judged out of scope and
  higher-risk than the UX/security benefit, especially with `#0081`
  concurrently working in the neighboring `subscribe.go`. Flagging this
  explicitly rather than quietly checking the boxes.
- **Commit ordering does not match issue numbering** — see `#0029`'s
  Gotchas for the full explanation. This commit landed last (`#0029` →
  `#0031` → `#0030`) because `ConfirmSubscription.svelte` embeds `#0031`'s
  `PreferenceCenter.svelte`.
- Reaching `ConfirmHandler.Confirm` at all requires possessing the exact
  32-byte secret mailed to one inbox at signup, so a non-uniform response
  here (unlike `#0026`'s `POST /api/subscribe`) is not an enumeration
  oracle — see the package doc comment in `confirm.go` for the full
  argument.
