### 0. Scope, and the boundary with the neighbouring issues

and the gate that refuses to run it.** Everything that decides *whether* a
campaign may send, and everything that decides *when a row leaves `queued`*,

### 1. Worker model: one in-process goroutine, started by `serve`

**Decision: an in-process goroutine on the Postgres serve path**, started when
`cfg.SendWorkerEnabled` is true, exactly as PRD §6.6 specifies. Not a separate
`opencircuit send-worker` subcommand, and not a systemd timer.

- `#0048` publishes send progress over the **same process's** SSE broker
  (`internal/events.Broker` is an in-memory fan-out, `cmd/opencircuit/main.go`).
  A separate worker process would have to reach that broker over the network —
  inventing an internal transport for a single-box deployment.
- The deploy target is one EC2 instance with one systemd unit (CLAUDE.md §7).
  A second unit is a second thing to install, monitor, and forget to restart.
- `SEND_WORKER_ENABLED` already exists precisely so that if the site is ever
  scaled to two instances, exactly one of them runs the worker. That is the
  scaling story; a separate binary is not needed to tell it.

*Rejected — separate command.* Buys process isolation we do not need and costs
the SSE seam, a second deploy artifact, and a second failure mode
(`opencircuit.service` up, `opencircuit-worker.service` down, campaigns
silently never sending).

*Rejected — a systemd timer / cron drain.* Poll-per-minute latency on an
operator-initiated action, and no place to hold the rate limiter's state.

#### Construction and lifecycle

```go
// internal/mailing/worker.go
type Worker struct {
    store    *SendStore        // §4, worker_store.go
    audience *AudienceStore    // #0044
    audit    *audit.Logger
    mailer   Mailer
    render   CampaignRenderer  // #0042/#0043's seam, §5
    settings SettingsReader    // GetSetting(ctx, key) (string, error)
    progress ProgressPublisher // nil until #0048; every call site nil-guarded

    baseURL, listDomain, fromAddr string
    envMaxSendRate, batchSize     int

    pollInterval time.Duration                       // campaignPollInterval
    now          func() time.Time                    // injectable clock
    sleep        func(context.Context, time.Duration) error
}

func NewWorker(deps WorkerDeps) (*Worker, error)
func (w *Worker) Run(ctx context.Context)            // blocks until Stop
func (w *Worker) Stop(ctx context.Context) error     // signal + bounded wait
```

- **Dev mode (`STORAGE=json`) never constructs a worker.** `internal/devstore`
  has no subscribers, suppressions, or campaigns backing at all; the worker is
  Postgres-only, nil-guarded at the call site exactly like `sesNotifyH`.
- **`MAILER_NOOP=true` refuses to construct the worker**, logging one
  `slog.Warn`. `noOpMailingMailer.Send` returns the literal message id
  `"noop"`; writing that into `email_sends.ses_message_id` would poison
  `#0038`'s bounce/complaint join key and `#0049`'s stats with rows that claim
  to have been delivered. `checkMailerNoOp` already restricts `MAILER_NOOP` to
  a localhost `BASE_URL`, so this costs nothing in production and is honest in
  dev: campaigns do not send when email is disabled.
- `Run` is `go w.Run(workerCtx)` from `mountAndServe`, alongside the existing
  `srv.Serve(ln)` goroutine.

#### Shutdown, and why the worker's context is *not* the shutdown context

This is the one lifecycle detail that is easy to get wrong in a way that
**widens the crash window of §6**. Cancelling a context that a `sent`-status
`UPDATE` is riding on turns "SES accepted, we recorded it" into "SES accepted,
we recorded nothing" — a guaranteed duplicate on the next boot, every single
deploy.

So the worker observes shutdown as a **signal, not a cancellation**:

1. `Stop` closes an internal `stopCh` and returns after `Run` exits or
   `workerCloseTimeout` elapses, whichever comes first.
2. `Run` checks `stopCh` **between messages and between batches**, never
   during one.
3. The SES call and the status write that follows it each use a **detached
   context** (`context.WithTimeout(context.Background(), …)`), following the
   precedent `releaseSendClaim` set in `internal/handlers/subscribe.go`. A
   SIGTERM arriving mid-message therefore cannot leave a message accepted by
   SES and unrecorded in Postgres.

Wiring into the existing sequence in `cmd/opencircuit/main.go` (`case sig :=
<-sigCh:`), as a fourth bounded step with its **own** context, per `#0087`'s
rule that these budgets are never shared:

```
sig received
  ├─ worker.Stop(workerStopCtx)   // NEW, first: stop claiming new work
  ├─ srv.Shutdown(shutdownCtx)
  └─ subscribeH.Close(closeCtx)
```

`worker.Stop` goes **first** because it is the only step whose work is
unbounded in principle (a 5,000-recipient drain) and the only one that can be
told to stop cheaply. `var workerCloseTimeout = 10 * time.Second`, a `var` so
the wiring test can shrink it, sized to cover one in-flight message's SES call
plus its status write — **not** sized against any measured machine load
(CLAUDE.md §5). If the budget is exceeded the process exits anyway; the
consequence is exactly the §6 crash window, which is already the designed
worst case.

#### Surviving a restart

Nothing is held in memory across a restart. The complete state of a send is
three columns in Postgres (`email_campaigns.status`, `email_sends.status`,
`email_sends.attempts`) plus `materialized_at` (§3). A restarted worker's
first poll re-claims the `sending` campaign, runs the orphan sweep (§4), and
resumes. There is no queue file, no in-memory backlog, and no leader election.

### 2. The pre-send gate

**Decision: one pure function, `mailing.Preflight`, evaluated at two call
sites — advisory in the HTTP layer, authoritative in the worker.** This is the
same shape `#0044` used for the audience predicate, and for the same reason:
a requirement expressed twice drifts.

```go
// internal/mailing/preflight.go
type PreflightFailure struct {
    Code    string // stable, machine-readable; #0047 keys off it
    Message string // operator-facing; #0047 renders it verbatim
}

type PreflightResult struct{ Failures []PreflightFailure }
func (r PreflightResult) OK() bool
func (r PreflightResult) Codes() []string

type PreflightInput struct {
    Subject          string
    BodyMarkdown     string
    AudienceMode     string
    InterestIDs      []int64
    TestSentAt       *time.Time
    PhysicalAddress  string // RAW settings value, untrimmed — see below
    SettingsErr      error  // e.g. auth.ErrSettingNotFound
    ListDomain       string
    BaseURL          string
    MailerReady      bool
    AudienceCount    int64  // -1 = not evaluated (dry-run before materialize)
    AudienceErr      error  // #0044's typed errors, surfaced verbatim
    RenderErr        error  // from the dry render below
}

func Preflight(in PreflightInput) PreflightResult
```

`Preflight` is pure — no context, no database, no clock. Every I/O concern is
the caller's. `SendStore.GatherPreflight(ctx, campaignID) (PreflightInput,
error)` does the reads, so both call sites gather identically.

**Every condition, its code, and where it is checked:**

| Code | Condition | Failure message |
|---|---|---|
| `subject_empty` | `strings.TrimSpace(Subject) == ""` | Subject is empty. |
| `body_empty` | `strings.TrimSpace(BodyMarkdown) == ""` | Body is empty. |
| `body_render_failed` | `RenderErr != nil` | Body does not render: `<err>`. |
| `physical_address_missing` | `SettingsErr != nil` **or** `strings.TrimSpace(PhysicalAddress) == ""` | Physical mailing address is not set (Settings → physical address). CAN‑SPAM §7704 requires it in every campaign email. |
| `no_test_send` | `TestSentAt == nil` | No test send has been delivered yet. |
| `audience_invalid` | `AudienceErr != nil` | `<#0044's error text, verbatim>` |
| `empty_audience` | `AudienceCount == 0` | No recipients match this audience. |
| `list_domain_unset` | `strings.TrimSpace(ListDomain) == ""` | `EMAIL_LIST_DOMAIN` is not configured; the one-click unsubscribe header would be malformed. |
| `mailer_unavailable` | `!MailerReady` | Outbound email is disabled or the SES mailer is not configured. |

The order is fixed and a test pins it, so `#0047`'s list is deterministic
rather than map-iteration-ordered.

**Notes on four of these that are not obvious:**

- **`physical_address` trims before testing for empty**, per this issue's own
  Notes: `validSettingValue` applies no format check to the key and the admin
  UI saves whitespace anyway, so `v != ""` is satisfied by a single space and
  would ship a campaign with no address — the exact CAN‑SPAM §7704 violation
  the gate exists to prevent. `auth.ErrSettingNotFound` (a deploy that skipped
  migration `000008`) is treated as *missing*, never as a hard error that
  crashes the worker: an unreadable address is an unset address.
- **`body_render_failed` comes from a dry render.** `GatherPreflight` renders
  the campaign once through `#0042`/`#0043` with the sentinel manage token
  `"PREFLIGHT-DRY-RUN"`, discards the output, and keeps only the error. PRD
  §6.6's pre-send list says "body renders"; this is how that is evidenced
  without sending anything. The sentinel never reaches a `Message` — the
  rendered bytes are dropped on the floor.
- **`empty_audience` is advisory before materialization** (`AudienceCount`
  from `#0044`'s `Preview`) and authoritative after (a `count(*)` over
  `email_sends`). `AudienceCount == -1` means "not evaluated" and produces no
  failure, so the HTTP call site can run the gate on a `draft` campaign.
- **`list_domain_unset` is checked here regardless of what `#0105` decides.**
  If `#0105` makes `EMAIL_LIST_DOMAIN` a required config field, this check is
  unreachable and harmless. If `#0105` instead drops the `mailto:` form when
  the domain is blank, this check is what still stops a campaign going out
  with a degraded header set nobody chose. Either way the worker cannot emit
  `<mailto:unsubscribe@?subject=…>`. `#0105` still blocks the **first real
  send**, per its own Notes; it does not block this issue's implementation.

  **Resolved 2026-08-21 (`#0105` review): `#0105` shipped *both* branches, and
  this gate must still be implemented — do not delete it as dead code.**
  `config.Load` now requires `EMAIL_LIST_DOMAIN` (`skipInDev: false`), *and*
  `mailing.CampaignHeaders` drops the `mailto:` form on a blank/whitespace
  `listDomain`. That makes the paragraph above read as though this check is
  now "unreachable and harmless" and therefore removable. It is not, and the
  reason is the shape of the two remaining defences: `CampaignHeaders` degrades
  **silently** — it has no error return and no logger, so a blank domain
  produces a valid-but-`mailto:`-less header set and `N` campaign messages go
  out with PRD §6.5's Path 3 quietly missing. This gate is the only guard that
  is *loud*: it refuses to let the campaign leave `scheduled` at all, so zero
  messages go out and `#0047` surfaces the reason to the operator. Deleting it
  would leave the silent degrade as the sole defence — exactly the
  "silently produces degraded output" shape this project keeps filing issues
  against. Keep the check and keep criterion 10's
  `TestWorker_RefusesWhenListDomainUnset` mutation test, which is what pins it.
  (`Preflight` takes `ListDomain` as an input field rather than reading config,
  so that test can still construct the blank case even though `config.Load`
  can no longer produce one.)

**Why this is not bypassable from the UI (CLAUDE.md §9).** The gate is not a
flag the UI sets and the worker trusts. There is no "force send" parameter, no
override column, and no admin route that skips it. The authoritative
evaluation happens **inside the worker, immediately before the campaign leaves
`scheduled`**, reading `physical_address` fresh from the database at that
moment rather than from anything cached at boot or passed in by a caller. A
request that reaches `POST /admin/campaigns/{id}/send` by any path — the UI, a
`curl`, a direct `UPDATE email_campaigns SET status='scheduled'` in `psql` —
still lands in front of the worker's own copy of the gate.

**What the operator sees.**

1. `#0041`'s send-transition handler calls `Preflight` and, when it fails,
   returns **409** with `{"unmet":[{"code":…,"message":…}, …]}`. `#0047`
   renders that list. This is the normal path and the only one an operator
   should ever hit.
2. If a campaign nonetheless reaches `scheduled` with an unmet requirement
   (the address was cleared after scheduling; someone bypassed the API), the
   worker **demotes it back to `draft`**, writes one
   `campaign.send_refused` audit row carrying the failing codes, and does not
   send. `#0047`'s screen then shows the same unmet list from the same
   function.

*Rejected — leaving a refused campaign in `scheduled`.* The worker polls every
2s; a refused campaign would re-evaluate and write an audit row 30 times a
minute forever.

*Rejected — moving a refused campaign to `failed`.* `#0041` only permits
editing while `draft` or `scheduled`, so `failed` is a dead end that needs an
admin to unstick. `draft` is the state the operator can actually fix.

**Wiring, given the queue order.** `#0041` lands before this issue, so the
send-transition handler already exists when this is implemented. This issue
adds the `Preflight` call to it (an edit in `internal/handlers`) and its
handler test. The worker's gate is mandatory regardless of whether the HTTP
call site exists.

### 4. Claim, materialize-once, and the campaign state machine

#### Campaign claim

Two distinct claims, because only one of them is "first".

**Start claim** — the transition that may happen exactly once per campaign:

```sql
UPDATE email_campaigns
   SET status = 'sending', started_at = now(), updated_at = now()
 WHERE id = (
         SELECT id FROM email_campaigns
          WHERE status = 'scheduled' AND scheduled_at <= now()
          ORDER BY scheduled_at, id
          LIMIT 1
          FOR UPDATE SKIP LOCKED)
RETURNING id, subject, preheader, body_md, audience_mode,
          test_sent_at, materialized_at, created_by;
```

The `WHERE status='scheduled'` predicate is the mutual exclusion: after the
first `UPDATE` commits, no second claimant matches. `FOR UPDATE SKIP LOCKED`
keeps two pollers from blocking on each other. The gate of §2 runs **before**
this statement (on a read of the campaign row) — a campaign with an unmet
requirement is demoted to `draft` and never enters `sending`.

**Resume claim** — for a campaign already `sending` when the worker starts (a
restart mid-send, which is the normal case after any deploy):

```sql
SELECT id, subject, preheader, body_md, audience_mode,
       test_sent_at, materialized_at, created_by
  FROM email_campaigns
 WHERE status = 'sending'
 ORDER BY started_at, id
 LIMIT 1;
```

A resume writes **no** `campaign.send_started` audit row and does **not**
re-run the gate's demotion branch — the campaign has already been started and
partially delivered; demoting it to `draft` mid-send would strand `sent` rows
under a `draft` campaign. It does still re-read `physical_address`, because
§5's footer needs it for every message; if it has become blank the worker
**stops the drain** and marks the campaign `failed` with
`campaign.send_failed` / `reason=physical_address_missing`, rather than
sending non-compliant mail. Refusing is always the correct behaviour
(CLAUDE.md §9).

One campaign at a time. There is no concurrency across campaigns; the poll
loop claims one, drains it, and returns to the ticker.

#### Materialize exactly once

```
if materialized_at IS NULL:
    res := audience.Materialize(ctx, campaignID, aud)     // #0044, chunked, idempotent
    UPDATE email_campaigns SET materialized_at = now() WHERE id = $1 AND materialized_at IS NULL
    write campaign.send_started audit with metadata.recipients = count(*)   // §9
```

`Materialize` is `ON CONFLICT DO NOTHING` and safely re-runnable, so a crash
partway through leaves `materialized_at` NULL and the next claim completes the
audience. **The one honest cost:** a subscriber who became `active` between
the crash and the resume *is* picked up by the completing run. That window is
seconds wide, only opens on a crash during materialization, and the
alternative — refusing to complete a half-materialized audience — leaves a
campaign that can never send. Named here rather than left to be discovered.

Post-materialization, `count(*) FROM email_sends WHERE campaign_id=$1` is
re-evaluated through `Preflight` with `AudienceCount` set. Zero rows here (the
pre-claim `Preview` said non-zero seconds earlier) is genuinely anomalous:
campaign → `failed`, audit `campaign.send_failed` /
`reason=empty_audience`. Nothing is sent.

#### Row-level claim: `queued → sending → sent`

`#0044` §1 sketches the batch as *claim → recheck → skip → COMMIT → send*.
That leaves the claimed rows in `status='queued'` across the SES calls, so its
"a row can leave `queued` exactly once" guard is only load-bearing for the
rows that got there first — two workers, or an old and a new process
overlapping across a restart, can both claim the same still-`queued` batch and
mail it twice.

**Decision: keep `#0044`'s transaction shape exactly, and add a per-row
atomic claim immediately before each SES call.** This refines step 5; it does
not move the recheck.

```
BEGIN                                                    -- #0044's shape, unchanged
  SELECT id, subscriber_id FROM email_sends
   WHERE campaign_id=$1 AND status='queued'
   ORDER BY id LIMIT $2 FOR UPDATE SKIP LOCKED           -- uses idx_email_sends_queued
  audience.RecheckEligibleTx(ctx, tx, campaignID, ids)   -- #0044, inside the tx
  audience.MarkSkippedTx(ctx, tx, campaignID, skipped, reason)
COMMIT

for each recipient (sequential, paced — §7):
  UPDATE email_sends SET status='sending', attempts = attempts + 1
   WHERE id=$1 AND status='queued' RETURNING attempts     -- 0 rows ⇒ someone else has it; skip
  id, err := mailer.Send(detachedCtx, msg)                -- §5 builds msg
  on success: UPDATE … SET status='sent', ses_message_id=$2, sent_at=now()
               WHERE id=$1 AND status='sending'
  on failure:  §8
```

Why this is right:

- **The claim is the same statement that increments `attempts`**, satisfying
  `#0044`'s "increment before the SES call" requirement in one round trip
  rather than two.
- **Mutual exclusion no longer depends on the single-worker invariant.** Two
  workers race on `AND status='queued'`; exactly one wins each row.
- **The restart duplicate window shrinks from a whole batch to one message**
  (§6).
- `#0044`'s `MarkSkippedTx` guard (`AND status='queued'`) is untouched — a
  skip happens inside the claim transaction while the row is still `queued`.
- `#0048`/`#0049` gain a real "in flight" bucket for free.

*Rejected — holding the claim transaction open across the batch's SES calls.*
A crash after 30 of 50 sends rolls back all 30 status updates: thirty
duplicates instead of one. Strictly worse, and it holds a transaction for
seconds.

*Rejected — a `worker_id`/`locked_at` lease column.* Solves a distributed
problem this system does not have, and needs a lease-expiry sweeper whose
timeout would have to be sized against something — precisely the trap
CLAUDE.md §5 warns about.

#### Orphan sweep

On claiming a campaign (start or resume), before draining:

```sql
UPDATE email_sends SET status='queued'
 WHERE campaign_id=$1 AND status='sending';
```

Rows stuck in `sending` are rows a previous process was mid-send on when it
died. Returning them to `queued` is what makes the restart complete the
campaign. With the single-worker invariant this is exact; with two workers
overlapping it can reset a genuinely in-flight row and produce a duplicate —
a duplicate, never a loss, which is the trade §6 takes deliberately.

#### Completion

```sql
UPDATE email_campaigns SET status='sent', completed_at=now(), updated_at=now()
 WHERE id=$1 AND status='sending'
   AND NOT EXISTS (SELECT 1 FROM email_sends
                    WHERE campaign_id=$1 AND status IN ('queued','sending'));
```

Evaluated after each batch. A campaign with only `sent`/`failed`/`skipped`
rows is done. A campaign `#0041` moved to `canceled` mid-drain no longer
matches `status='sending'`, so the worker stops claiming its rows and the
`UPDATE` is a no-op — cancel stops further sends and cannot recall sent mail,
exactly as `#0041`'s copy promises.

### 5. Per-recipient message construction

One `Message` per recipient, built inside the send loop. Nothing is hoisted.

```go
for _, r := range recipients {          // r is #0044's Recipient
    html, text, err := w.render.Campaign(CampaignRenderInput{
        Subject:         c.Subject,
        Preheader:       c.Preheader,
        BodyMarkdown:    c.BodyMarkdown,
        BaseURL:         w.baseURL,
        ManageToken:     r.ManageToken,   // FRESH, from RecheckEligibleTx
        PhysicalAddress: physicalAddress, // read fresh this campaign, non-blank
    })
    msg := Message{
        To:       r.Email,               // the email_sends SNAPSHOT
        From:     fromHeader,            // §5.2
        Subject:  c.Subject,
        HTMLBody: html,
        TextBody: text,
        Headers:  CampaignHeaders(w.baseURL, w.listDomain, r.ManageToken),
    }
    …
}
```

#### 5.1 Where `#0035`'s two unmet criteria land

- **"Headers applied to campaign mail only" — the positive half.** Every
  campaign `Message` gets `CampaignHeaders(baseURL, listDomain,
  r.ManageToken)`, constructed **inside the loop, from that recipient's own
  token**. `baseURL` is `config.Config.BaseURL` (already trailing-slash
  normalised, canonical `https://www.opencircuitsf.com`); `listDomain` is
  `config.Config.EmailListDomain`, never the apex. The negative half is
  already proved by `TestNoTransactionalMessageCarriesCampaignHeaders`, and
  this issue must not route campaign sends through the five transactional
  builders — `render.Campaign` is `#0043`'s own builder, so that test keeps
  passing untouched.
- **The campaign-body footer links.** `#0043` owns the footer markup and the
  literal PRD §6.5 labels ("Manage your interests", "Unsubscribe from
  everything"); this issue owns **the token those links interpolate**. The
  worker passes `r.ManageToken` — the *fresh* value `RecheckEligibleTx`
  returns, not the materialization-time snapshot — so `/preferences?token=…`
  and `/unsubscribe?token=…` are live for that recipient. The footer's
  unsubscribe link is the SPA's `/unsubscribe`, never `/api/unsubscribe`;
  that route belongs to the header. Both are asserted in §11's end-to-end
  test, which is the only place the real loop can be observed.

Reusing one recipient's token across a batch would let recipient A
unsubscribe recipient B with one click, and a stale token means a dead
one-click link in the header Gmail and Yahoo actually parse. Both are
mutation-tested in §11.

#### 5.2 `Message.From` (carried in from `#0027`'s review)

Add `From string` to `mailing.Message`; `SESMailer.Send` uses `msg.From` when
non-empty and falls back to `m.from` otherwise. A struct addition, not an
interface break — every existing caller compiles unchanged.

The worker composes it from the `default_from_name` setting seeded in §3:

- blank name → `From` stays empty → SES uses `EMAIL_FROM`, today's behaviour.
- name present → `"Name" <EMAIL_FROM>`, but **only if the name is printable
  ASCII containing no `"`, `\`, CR, or LF.** Anything else falls back to the
  bare address. A CR or LF in an operator-editable setting that lands in a
  header is header injection; refusing is cheaper than encoding, and RFC 2047
  encoding of a display name is not worth building for a value nobody has
  asked to internationalise. A test pins the refusal.

#### 5.3 No open-tracking pixel — including the part that is not in our code

CLAUDE.md §9 forbids open-tracking pixels. Two mechanisms could introduce one:

1. **Our template.** `#0043`'s markup contains no tracking image, and §11 adds
   a scan over every delivered HTML body that fails on a 1×1 image or any
   remote-host URL.
2. **SES itself.** An SES **configuration set** with open or click tracking
   enabled rewrites links and injects a tracking pixel *server-side*, with no
   change to our code and nothing our tests can see. Every message this worker
   sends carries `SES_CONFIGURATION_SET`. **`opencircuit-transactional` must
   have open tracking and click tracking disabled**, and that is a deployment
   fact, not a code fact — it belongs in `#0064`'s runbook and CLAUDE.md §10
   item 2's SES checklist. Flagged to the orchestrator.

### 6. Idempotency and the crash window — at-least-once, honestly

`attempts` is incremented **and committed** in the same statement that flips
the row to `sending`, before the SES call. The `sent` update commits after.

**The window is precisely this:** between the moment SES's `SendEmail`
returns a `MessageId` and the moment the `status='sent'` update commits, the
row is `sending` with the message already delivered. If the process dies in
that interval, the orphan sweep returns the row to `queued` on the next start
and the message is sent a second time. Because the loop is sequential (§7),
**at most one message per worker can be in that window at any instant** — the
duplicate is one message, not a batch.

**It cannot be closed.** SES's `SendEmail` is not enlisted in our Postgres
transaction, there is no two-phase commit between AWS and our database, and
SES v2 offers no client-supplied idempotency key on `SendEmail`. Every
possible ordering picks a failure mode:

- **Mark `sent` before calling SES** → a crash in the same window loses the
  message entirely. The subscriber never receives the campaign, `email_sends`
  says they did, and nothing anywhere reveals it.
- **Mark `sent` after calling SES** (this design) → a crash duplicates one
  message. Visible to the recipient, harmless, bounded.

For a mailing list a duplicate is an annoyance; a silent drop is a broken
promise that no dashboard, no audit row, and no bounce event will ever
surface. **At-least-once with a one-message window is the right trade, and
this system does not achieve exactly-once.** Claiming otherwise in a comment
or a work log would be false.

Incrementing `attempts` *before* rather than after is what bounds the
pathological case: a message that deterministically kills the worker (an
oversized body, a panic in rendering) would otherwise be retried forever. With
the increment committed first, it reaches `attempts = 3` and becomes `failed`.

Four independent layers, all mutation-tested in §11:

1. `UNIQUE (campaign_id, subscriber_id)` + `ON CONFLICT DO NOTHING` — the
   audience cannot gain a second row for the same subscriber.
2. `FOR UPDATE SKIP LOCKED` on the batch select — two workers never read the
   same batch.
3. `UPDATE … WHERE id=$1 AND status='queued'` — a row leaves `queued` exactly
   once; the loser of a race sends nothing.
4. `materialized_at` — the audience is computed once, never re-derived
   mid-send.

### 7. Rate limiting and SES quotas

**There is no performance requirement in this project (CLAUDE.md §5).** The
pacing exists to stay under SES's quota and to be a good sending citizen, not
to make sends fast. Nothing here is sized against measured machine load.

- **Effective rate = `min(cfg.MaxSendRate, settings.max_send_rate)`.** The env
  var is the deploy-level ceiling (`internal/config`'s own comment already
  describes it that way); the settings row is the operator's dial, editable
  from `#0009`'s Settings tab. A missing, blank, non-numeric, or non-positive
  settings value falls back to the env value — **never to unbounded**. Read
  once per batch, so an operator can throttle a running send without a
  restart; one extra tiny query per 50 messages.
- **`golang.org/x/time/rate`**, already a direct dependency — `rate.NewLimiter(rate.Limit(n), 1)`
  with `limiter.Wait(ctx)` before each send. No new dependency, no hand-rolled
  ticker.
- **Sequential sends.** One message in flight at a time. Not for throughput
  reasons — because it makes the §6 window exactly one message and makes the
  tests deterministic. At the default 10/s a 1,000-recipient campaign takes
  100 seconds, which nobody is waiting on.
- **Sandbox vs production.** In the SES sandbox (CLAUDE.md §10 item 2 — not
  yet requested) the account is capped at 200 messages/day, 1/second, and can
  only send to verified addresses. The default `max_send_rate` of 10 exceeds
  the sandbox's 1/s, so **development against the sandbox should set
  `MAX_SEND_RATE=1`**; that belongs in `docs/configuration.md` and `#0064`'s
  runbook. The worker does not detect which mode the account is in — SES does
  not expose it on the send path — it simply obeys the configured rate and
  backs off on the throttling error the sandbox produces.
- **Throttling response.** `SESMailer.Send` already retries
  `types.TooManyRequestsException` internally (4 attempts, 200/400/800 ms).
  When it surfaces *after* those retries, the worker adds a **campaign-level
  backoff**: sleep `1s, 2s, 4s, 8s, 16s`, capped at `30s`, reset to `1s` on
  the next success, and leave the row `queued` (§8). This is the "exponential
  backoff on `ThrottlingException`" the acceptance criteria name, layered
  above the mailer's per-message retry rather than duplicating it. The backoff
  sleep goes through `w.sleep`, so tests do not wait in real time.

### 8. Error handling per recipient

Classification lives in one function, `classifySendError(err) sendOutcome`,
with `sendOutcome ∈ {retryable, terminalRow, terminalCampaign}`. It uses
`errors.As` against `sesv2/types` error types — never string matching.

| SES error | Class | Row result | Why |
|---|---|---|---|
| `TooManyRequestsException` | retryable | `queued` (or `failed` at 3 attempts) | Quota, not content. Triggers §7's backoff. |
| `SendingPausedException` | terminalCampaign | rows left `queued` | Account-level pause; every subsequent send fails identically. |
| `AccountSuspendedException` | terminalCampaign | rows left `queued` | Same, and worse. |
| `MailFromDomainNotVerifiedException` | terminalCampaign | rows left `queued` | Configuration fault; identical for all 5,000 rows. |
| `NotFoundException` (missing configuration set) | terminalCampaign | rows left `queued` | Same. |
| `BadRequestException` | terminalCampaign | rows left `queued` | Malformed request we built; will not fix itself per-recipient. |
| `MessageRejected` | terminalRow | `failed` immediately | Per-address/per-content rejection. |
| `LimitExceededException` | retryable | `queued` | Daily quota; may pass tomorrow. |
| context deadline, network, any other error | retryable | `queued` | Unknown ⇒ assume transient. |
| SES returns no `MessageId` | terminalRow | `failed` immediately | `SESMailer` already errors here; the id is `#0038`'s join key and a row with no id is unreconcilable. |
| empty `ManageToken` from the recheck | terminalRow | `failed` immediately, **no SES call** | A message with a dead unsubscribe link is a compliance failure (`#0042`: fail loudly). |

- **`retryable`**: `UPDATE … SET status = CASE WHEN attempts >= 3 THEN 'failed'
  ELSE 'queued' END, error = $2 WHERE id = $1 AND status = 'sending'`. Three
  attempts total, per the acceptance criterion; `attempts` was already
  incremented by the claim, so the count is exact and survives a restart.
- **`terminalRow`**: `status='failed', error=$2` regardless of `attempts`.
  Retrying a rejection three times is three more rejections.
- **`terminalCampaign`**: stop the drain immediately, leave the remaining rows
  `queued`, set the campaign `failed`, write `campaign.send_failed` with the
  reason. Marking 5,000 rows `failed` one at a time via 5,000 doomed API calls
  is the alternative, and it is indefensible. Leaving the rows `queued` means
  that if `#0041` later offers a `failed → sending` retry transition, the
  drain resumes correctly and idempotently — flagged to `#0041`.
- **`failed` vs `skipped` are never conflated.** `#0044` owns `skipped` and
  defines it as "was in the audience at materialization, was no longer
  eligible at send time, never mailed" — a correct outcome. `failed` means
  "we tried and delivery did not happen". The worker never writes `skipped`;
  only `MarkSkippedTx` does. A test asserts an unsubscribed-mid-send recipient
  lands in `skipped`, not `failed`.
- `email_sends.error` is truncated to 500 characters before storage; an AWS
  error string can carry a request id and a long message, and the column is
  for diagnosis, not archival.

### 9. Audit

This issue owns four actions, added to `internal/audit/actions.go`. All are
written with **actor NULL** and `metadata.source = "send_worker"` — the
worker has no session and is not acting on behalf of the operator at that
moment, matching the convention `ActionSubscriberBounced` and the `ses.*`
actions already use for system-originated events.

| Action | When | Metadata |
|---|---|---|
| `campaign.send_started` | once, after materialization completes | `recipients` (the materialized `count(*)`, **the required field**), `audience_mode`, `interest_ids`, `inserted`, `chunks`, `created_by` |
| `campaign.send_refused` | the gate demoted a `scheduled` campaign to `draft` | `codes` (`Preflight` codes), `messages` |
| `campaign.send_completed` | campaign → `sent` | `sent`, `failed`, `skipped`, `duration_ms` |
| `campaign.send_failed` | campaign → `failed` | `reason` (`empty_audience`, `physical_address_missing`, or the terminal SES error class), `sent`, `remaining` |

`campaign.send_started` is written **only on the start claim**, never on a
resume, so a campaign restarted five times still has exactly one start row
with one recipient count. Written with `audit.Record` (log-and-continue): the
transition has already committed, and an audit write failure must not abort a
send in progress.

**Not audited, deliberately:**

- **Per-recipient sends.** A 5,000-recipient campaign would write 5,000 audit
  rows and drown every other action in the log. `email_sends` already *is* the
  per-recipient record, with `ses_message_id`, `sent_at`, `attempts`, and
  `error`, and `#0049` reads it.
- **Skips.** `#0044` decided the audience writes no audit rows; a `skipped`
  row with its reason is the record.
- **Batch progress.** That is `#0048`'s SSE stream, not an audit trail.
- **`draft → scheduled`, edits, cancel.** `#0041`'s, with the real admin as
  actor.

### 10. The progress seam for `#0048`

Defined here so `#0048` does not have to reshape the loop:

```go
type CampaignProgress struct {
    CampaignID                         int64
    Total, Sent, Failed, Skipped, Remaining int64
}

type ProgressPublisher interface {
    PublishCampaignProgress(ctx context.Context, p CampaignProgress)
}
```

The worker calls it **once per batch** (PRD §8 and `#0048`: batch completion,
not per message) and once at completion, always nil-guarded. `Total` is
`count(*)` over `email_sends` for the campaign — the fixed denominator
`#0044`'s plan requires — and `Remaining = queued + sending`. `Skipped` is its
own field, never folded into `Failed`. `#0045` wires `nil`; `#0048` supplies
the broker-backed implementation.

## Root cause

Not a bug fix — new subsystem. Before this issue, `email_campaigns` could
reach `scheduled` (`#0041`'s `Send`) but nothing ever moved a row further:
`internal/handlers/admin_campaigns.go`'s `campaignPreflightChecker` seam was
wired to a literal `nil` at the `cmd/opencircuit/main.go` call site, and no
code anywhere claimed a `scheduled` campaign, materialized its audience, or
called `Mailer.Send`. A campaign that reached `scheduled` simply sat there
forever.

## Fix

Built exactly to the plan, with one deliberate deviation (already flagged in
the plan's §11 and restated here for the reviewer) and a handful of
implementation choices the plan left open:

- **`internal/mailing/preflight.go`** — `Preflight(PreflightInput)
  PreflightResult`, pure, no I/O. Ten stable failure codes (the plan's nine
  plus `reply_to_missing`, carried in from `#0043`'s review) evaluated in a
  fixed, tested order:
  `subject_empty, body_empty, body_render_failed, physical_address_missing,
  reply_to_missing, no_test_send, audience_invalid, empty_audience,
  list_domain_unset, mailer_unavailable`.
- **`internal/mailing/worker_store.go`** — `SendStore`: `PeekScheduledCandidate`
  + `DemoteToDraft` (the gate's refusal path, run on a plain read before the
  atomic claim — no `FOR UPDATE SKIP LOCKED` needed there, since only the
  demote/claim `UPDATE`s themselves need to be atomic), `ClaimStart` (the
  `FOR UPDATE SKIP LOCKED` start-claim exactly as specified), `ClaimResume`,

## Gotchas

- **`AudienceStore.Preview` (not `count(*) FROM email_sends`) backs
  `GatherPreflight`'s `AudienceCount` at BOTH call sites**, including the
  worker's own pre-claim gate evaluation. This means the worker's gate
  evaluates `empty_audience` against the **live** audience predicate, not
  against any materialized snapshot — correct for a `draft`/`scheduled`
  campaign (nothing is materialized yet at gate time), and consistent with
  the plan's own note that a *separate*, later check
  (`total == 0` after `Materialize`, in `drainCampaign`) is what catches the
  genuinely anomalous post-materialization empty case.
- **The typed-nil trap was real, not hypothetical, in this issue's own
  code**: an early draft of `NewCampaignPreflightChecker` took the local
  `campaignPreflightStore` interface as its parameter type; passing a nil
  `*mailing.SendStore` into that interface parameter produces a non-nil
  interface value (Go's classic gotcha), which is exactly what `#0041`'s
  carried-in item warned against. Fixed by changing the parameter to the
  concrete `*mailing.SendStore` so the nil check happens on a plain pointer
  comparison before anything is wrapped in an interface.
- **Test tokens must avoid `@` in the mutation-testing helper.** The
  multi-recipient-header test originally generated a rotated `manage_token`
  containing `@` (borrowed from an email-address generator helper); RFC
  8058's mailto: form and the HTTPS query string both percent-encode `@` as
  `%40`, so a naive substring match against the raw token failed even though
  the real value was correctly present, encoded. Fixed by generating a
  plain numeric-suffixed token with no reserved characters.
- **`audit_log` is never truncated between `go test` runs** (it is a shared,
  append-only table other packages' suites also write to), and
  `email_campaigns.id` resets to 1 via `RESTART IDENTITY` at the start of
  every `internal/mailing` `TestMain` run. Running the suite twice in the
  same session therefore let a *second* run's fresh campaign collide with a
  *first* run's stale `audit_log` rows for the same `target_id`, producing
  spurious "2 rows, want 1" failures with no code defect behind them. Fixed
  with a `resetCampaignAuditRows` test helper that deletes-then-registers-
  cleanup for a campaign's audit rows before any exact-count assertion.

## Notes

PRD §6.6. The physical-address check is a legal gate, not a nicety — CAN-SPAM §7704 requires a valid physical postal address in every commercial message. Refusing to send is the correct behaviour and needs to be impossible to bypass from the UI.

The restart-idempotency test is the one that matters most. `UNIQUE (campaign_id, subscriber_id)` plus per-row status updates should make double-delivery impossible; prove it by actually killing the worker mid-send rather than reasoning about it.

`SEND_WORKER_ENABLED` exists so that if the site is ever scaled to two instances, exactly one runs the worker.

**The `physical_address` gate must trim before testing for empty.** Landed by
`#0009` as `settings.physical_address`, seeded `''` by migration `000008`. Two
behaviours make a naive `v == ""` check wrong:

- `validSettingValue` applies **no** format check to this key — only
  `registrations_enabled` is validated — so the stored value is arbitrary free
  text, whitespace included.
- The admin UI warns on `!addressInput.trim()` but **saves whitespace anyway**.

So a single space satisfies `v != ""` and ships a campaign with no physical
address, violating CAN-SPAM §7704 — the exact outcome this gate exists to
prevent. Use `strings.TrimSpace(v) == ""`.

Read the setting fresh at send time rather than caching it at boot. Note also
that `UpdateSetting` only mutates an existing row, so a deploy that skips
migrations leaves `PATCH /admin/settings` returning `ErrSettingNotFound` for
this key.
