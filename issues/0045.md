## Description

The background goroutine that drains queued sends at a throttled rate, with the safety checks that stop a bad campaign from going out.

## Acceptance criteria

- [ ] Worker starts with `serve` when `SEND_WORKER_ENABLED` is true and shuts down cleanly on SIGTERM
- [ ] Claims `scheduled` campaigns whose time has come and transitions them to `sending`
- [ ] Materializes the audience on first claim (#0044)
- [ ] Fetches queued rows with `FOR UPDATE SKIP LOCKED` in batches of `SEND_BATCH_SIZE`
- [ ] Throttled to the `max_send_rate` setting with exponential backoff on `ThrottlingException`
- [ ] Marks each row `sent` with its `ses_message_id`, or `failed` after 3 attempts
- [ ] Campaign transitions to `sent` with `completed_at` when no queued rows remain
- [ ] **Refuses to start a campaign when the `physical_address` setting is empty**
- [ ] Refuses to start unless a test send has been delivered to an admin
- [ ] In-flight sends survive a restart without duplicating — verified by killing the process mid-send in a test
- [ ] `go test ./internal/mailing/...` passes, including the restart-idempotency test

## Carried in from `#0044`'s plan (2026-08-21)

`#0044` owns the audience; this issue consumes it. Do not re-derive its logic:

- [ ] **Do not write the eligibility predicate here.** Call
      `RecheckEligibleTx` + `MarkSkippedTx` **inside the batch-claim
      transaction**, after the `FOR UPDATE SKIP LOCKED` select and before the
      SES call. Those two are transaction-only by design — a pool-backed
      recheck is a TOCTOU with no correct use.
- [ ] **Materialize exactly once**, on the worker's first claim — not per batch.
- [ ] **Send to `email_sends.email`** (the snapshot), but use the **fresh**
      `manage_token` the recheck returns. The token rotates on unsubscribe
      (`#0034`), and a stale one means a dead one-click link in the
      `List-Unsubscribe` header.
- [ ] **Increment `attempts` *before* the SES call**, not after. The residual
      duplicate-on-crash window is named in `#0044`'s plan.
- [ ] **This issue owns the campaign-start audit row**, with the materialized
      count in its metadata. `#0044` writes no audit row.

## Notes

PRD §6.6. The physical-address check is a legal gate, not a nicety — CAN-SPAM §7704 requires a valid physical postal address in every commercial message. Refusing to send is the correct behaviour and needs to be impossible to bypass from the UI.

The restart-idempotency test is the one that matters most. `UNIQUE (campaign_id, subscriber_id)` plus per-row status updates should make double-delivery impossible; prove it by actually killing the worker mid-send rather than reasoning about it.

`SEND_WORKER_ENABLED` exists so that if the site is ever scaled to two instances, exactly one runs the worker.

**The `physical_address` gate must trim before testing for empty.** Landed by
`#0009` as `settings.physical_address`, seeded `''` by migration `000008`. Two
behaviours make a naive `v == ""` check wrong:

- `validSettingValue` applies **no** format check to this key — only
  `registrations_enabled` is validated — so the stored value is arbitrary free
  text, whitespace included.
- The admin UI warns on `!addressInput.trim()` but **saves whitespace anyway**.

So a single space satisfies `v != ""` and ships a campaign with no physical
address, violating CAN-SPAM §7704 — the exact outcome this gate exists to
prevent. Use `strings.TrimSpace(v) == ""`.

Read the setting fresh at send time rather than caching it at boot. Note also
that `UpdateSetting` only mutates an existing row, so a deploy that skips
migrations leaves `PATCH /admin/settings` returning `ErrSettingNotFound` for
this key.

## Carried in from `#0035`'s review (2026-08-20)

`#0035` built the RFC 8058 header set but had **no campaign send path to attach
it to** — this issue is that path — so it was resolved with the positive half of
its "headers applied to campaign mail only" criterion unmet. That half is now
this issue's to satisfy. Before `#0035`'s review this file carried only a
`Depends on: #0035` line and no criterion at all, which is exactly how a
requirement falls between two issues.

- [ ] **Every campaign message carries `mailing.CampaignHeaders`, built per
      recipient.** The signature is:

      ```go
      // internal/mailing/campaign_headers.go
      func CampaignHeaders(baseURL, listDomain, manageToken string) []Header
      ```

      Call it once per recipient inside the send loop and attach the result to
      that recipient's own `Message`:

      ```go
      msg := mailing.Message{
          To:       recipient.Email,
          Subject:  campaign.Subject,
          HTMLBody: html,
          TextBody: text,
          Headers:  mailing.CampaignHeaders(cfg.BaseURL, cfg.EmailListDomain, recipient.ManageToken),
      }
      ```

      - `baseURL` is `config.Config.BaseURL` — already trailing-slash-normalised
        by `normalizeBaseURL`, canonical `https://www.opencircuitsf.com`
        (CLAUDE.md §7), never the bare apex.
      - `listDomain` is `config.Config.EmailListDomain`
        (`lists.opencircuitsf.com`). Never the apex — CLAUDE.md §9. See `#0105`,
        which must land before the first real send: that variable is currently
        neither required nor defaulted, so an unset value silently produces a
        malformed `mailto:unsubscribe@?subject=…`.
      - `manageToken` is **that recipient's own** `subscribers.manage_token`.
        Hoisting it out of the loop, or reusing one token across a batch, lets
        recipient A unsubscribe recipient B with one click.

- [ ] **The headers go on campaign mail only.** `internal/mailing`'s
      `TestNoTransactionalMessageCarriesCampaignHeaders` already proves the five
      transactional/auth templates never set `Message.Headers`; do not route
      campaign sends through those builders in a way that would change that.

- [ ] **Test it end to end on a real multi-recipient send**, against the fake
      mailer rather than in isolation: drain a queued campaign with at least
      three recipients and assert each delivered `Message` carries all three
      headers and only its own recipient's token. `#0035`'s
      `TestCampaignHeaders_MultiRecipientBatch_TokensDoNotCrossContaminate`
      proves this for the pure function by *simulating* the send loop's shape;
      only this issue can prove it for the loop that actually runs.
      `TestSESMailer_Send_MultipartWithCustomHeaders` already proves the
      transport carries arbitrary headers through to SES verbatim, so no further
      plumbing is needed below `Send`.
