## Description

`internal/db` carries a family of guards that scan **issue markdown** — citation
resolution, undefined test-function names, evidence citing a Go file by line
number, dangerous fenced blocks. They run as ordinary Go tests, so they only
ever see the issue file **as it stood when the suite last ran**.

`issues/Issues.md`'s phase 2 orders the work so that never includes the notes:

- **step 4** is the verification run;
- **step 7** drafts `## Root cause`, `## Fix`, `## Verification`, `## Files
  changed`, `## Gotchas`;
- **step 8** returns to the orchestrator.

There is no re-run between step 7 and step 8. **The text most likely to trip a
citation guard is written after the only run that could catch it.**

Phase 3 has no equivalent hole by accident: step 3 tells the reviewer to re-run
the verification itself, and the orchestrator's dispatches have separately been
telling reviewers to re-run *after* writing `## Review notes`. That convention
lives in dispatch prose, not in `Issues.md`, so it is re-invented per dispatch
and was never extended to phase 2 at all.

## Root cause

`issues/Issues.md`'s phase 2 ordered claim → fix → build-and-verify → commit →
draft notes → return, with the one test run sitting *before* the notes it was
meant to also cover. Phase 3 had the return step and the drafted-notes step in
the opposite order relative to its own last run too: step 3's re-verification
happened, then `## Resolution notes` / `## Review notes` got written afterward,
with the "re-run after the notes" convention living only in per-dispatch
prose rather than in this file. Neither gap was a defect in the guards — each
guard behaved exactly as designed against text it was never shown.

## Fix

Added one step to each phase in `issues/Issues.md`, immediately before the
step that returns or commits:

- **Phase 2, new step 8** (old step 8 renumbered to 9): re-run
  `internal/db` over the just-drafted sections by default, adding
  `internal/handlers` only when the pass touched a Go doc comment or a
  `CLAUDE.md` `##` heading — matching `CLAUDE.md` §5's reasoning for why those
  two packages differ, and keeping the expensive package opt-in per criterion
  4's cost concern.
- **Phase 3, new step 5**: the same re-run, covering both the approve and the
  bounce branches, before the resolution commit in step 4.
- **"Filing a new issue"**: a paragraph after step 8 addressing acceptance
  criterion 5 — the orchestrator's own filing path has the same gap in
  miniature (no build-and-verify step precedes its commit at all), but it is
  narrower in practice because the guards scan all of `issues/` and
  `internal/db` sits in the default package list every ordinary phase 2/3 run
  already reads. The fix there is procedural (fold the check into an existing
  planning-pass subagent when one runs; rely on the next dispatch's ordinary
  run otherwise), not a new mechanism.

No mechanism was added. Per criterion 3, this is a documentation-only change:
no pre-commit hook, no guard-for-the-guards, no linter predicting guard trips.
The fix is the documented re-run itself.

## How it surfaced

`#0476`'s implementer proved its fix with a throwaway test, deleted the file
before committing — correctly — and then named that function in its
`## Verification`. `TestNoOpenIssueVerificationCitesUndefinedTestFunction`
resolves cited names against the tree, so it failed on two lines.

The implementer's own verification run had passed, honestly and completely: the
offending text did not exist yet. The failure was found by a **third** agent, a
planning pass on an unrelated issue that happened to run `internal/db` over a
shared working tree while the file sat uncommitted.

That is the shape worth fixing. Nothing in the pipeline was looking; the catch
was luck, and it cost two agents a detour.

## Why it is worth a rule rather than more dispatch prose

This family has now tripped agents **five separate times in one session**, and
the mechanism differed every time — a run-on sentence sweeping an identifier
into the wrong migration's check, a test named before it existed, an
angle-bracket placeholder truncating to an undefined token, an admin-facing
string citing a docs path, and this one. Every trip was the guard behaving
correctly.

`CLAUDE.md` §8 already anticipates this in general terms, and its advice is to
rephrase rather than delete or relocate. What is missing is the *timing*: an
agent that writes prose after its last run has no way to learn it broke
something.

## Acceptance criteria

1. **Add the re-run to `issues/Issues.md` phase 2**, between drafting the
   sections and returning. Say which packages — `internal/db` at minimum, and
   `internal/handlers` when a Go comment or a `CLAUDE.md` heading was touched
   (`CLAUDE.md` §5).
2. **Record the phase-3 convention in the same place**, so re-running after
   writing `## Review notes` stops being per-dispatch prose.
3. **Do not build a mechanism that checks prose before it is written.**
   `CLAUDE.md` §8 is explicit that this is `#0258`'s spiral one level out. A
   documented re-run is the whole fix; a pre-commit hook, a guard-for-the-guards,
   or a linter that predicts guard trips is out of scope.
4. Keep the cost honest. `internal/db` is a small package; `internal/handlers`
   is ~8× a small one (`CLAUDE.md` §5a). The rule should ask for the cheap run
   by default and the expensive one only when the edit warrants it.
5. **Check whether the orchestrator's own issue-filing has the same hole.** New
   issue files are written and committed without any run at all. If so, say what
   the rule is there — this issue's own file included.

## Review notes

Approved on the first pass. `ISSUE=0478r scripts/check.sh go ./internal/db/...
./internal/handlers/...` reported `ok` for both packages with zero skips and
`gofmt -l` clean, at load average 2.46 — `internal/db` in 0.628s and
`internal/handlers` in 5.988s, a 9.5× ratio that confirms `CLAUDE.md` §5a's
"roughly 8×" and with it criterion 4's premise. Only `issues/Issues.md`
changed, 34 insertions and 1 deletion in one file, so there is no hook, no
guard-for-the-guards, and no linter: criterion 3 is met by construction. The
rule this issue wrote predicted `internal/handlers` was unnecessary here — no
Go comment touched, no `CLAUDE.md` heading renumbered — and running it anyway
confirmed the prediction, with nothing in that package moving.

**Criterion 5's answer is a deliberate tolerance, and this is the record
saying so plainly: issue filing is not covered.** A `## Description` and its
acceptance criteria reach git at "Filing a new issue" step 8 with no run at
all in between, and the shipped paragraph's own words for what happens next
are "caught, or not, by the next dispatch's ordinary run" — which is the
mechanism this issue's Description calls luck. Accepting that is defensible on
cost, since the alternative is a subagent per filed issue to scan Markdown,
real expense against a failure whose measured consequence was one detour. But
defensible is not the same as covered, and the paragraph should be read as
choosing to live with the gap rather than as closing it.

The paragraph understates its own fix. Phase 2's new step 8 and phase 3's new
step 5 both hard-code `./internal/db/...`, so from here on every
implementation pass and every review pass runs the issue-markdown guards
unconditionally, however narrowly the rest of that pass was scoped. Before
this change a scoped run never touched `internal/db` at all, which is why the
incidental catch was as rare as it was. The residual window for a freshly
filed issue is therefore no longer "until someone happens to run the package"
but "until the next phase-2 or phase-3 step completes for any issue" — bounded
and structural rather than lucky. The paragraph reaches its conclusion by way
of bare `scripts/check.sh` runs, which are the uncommon case; the two new
steps are the real reason it holds.

The option it does not consider is the orchestrator running
`ISSUE=NNNN scripts/check.sh go ./internal/db/...` itself at filing time. That
is cheaper than a subagent — a handful of output lines from a package that
tests in well under a second — and the orchestrator authored the text, so a
failure is rephrased from prose it already holds rather than by reading code.
**I land on `CLAUDE.md` §3 winning anyway, narrowly, and for one reason: the
failure branch.** A green run costs almost nothing, but a red one pulls the
orchestrator into read-fix-rerun, which is exactly the loop §3 keeps out of
the session that holds the queue, and there is no way to opt into only the
green half. With the residual window now one dispatch wide instead of
unbounded, the trade is not close enough to justify bending §3. The paragraph
should still have named the option and said this, because a future reader will
otherwise re-derive it from scratch.

Two imprecisions follow, neither changing what an agent should do, both worth
fixing whenever `issues/Issues.md` is next edited.

**Phase 3's step 5 sits after the step whose commit it must precede.** Its
first sentence says so explicitly and in bold, so it cannot be misread once
read — but an agent working the numbered list in order has already committed
by the time it arrives, and a check placed after the thing it was meant to
gate is the precise shape this issue exists to remove. Remedy, verbatim: fold
the re-run into step 4 as a lead-in sentence ahead of the two branches, along
the lines of "Before making either branch's commit, re-run the doc-scanning
guards over the notes you just wrote"; or split the commit out of step 4 into
its own step placed after the re-run. Do not simply renumber the re-run ahead
of step 4, because the notes must exist before there is anything to scan.

**Step 5's approve branch names a section the guards will not read.** The
issue-markdown guards restrict their scan to files whose status row reads
`open` or `in-progress`, and that exemption is deliberate.
`TestIssueVerificationCitationGuardExcludesResolvedFilesByDefault` pins it for
the undefined-test-name guard.
`TestIssueLineCitationGuardExcludesResolvedFilesByDefault` pins it for the
guard over evidence that cites a Go source file by line number. Step 4's
approve branch sets the status to `resolved` before step 5 runs, so by then
this file is excluded and its `## Resolution notes` never reaches
`TestNoOpenIssueVerificationCitesUndefinedTestFunction`. The same exclusion
keeps that text away from `TestNoOpenIssueEvidenceCitesGoFileByLineNumber`.
The bounce branch reverts the status to `open` and is scanned exactly as
described, so criterion 2 — which names `## Review notes` — is met on the
branch it names. Running the guards on approve is still correct advice, for a
reason the text does not give:
`TestResolvedOrClosedIssueCarriesClosedRow` fires on precisely the edit step 4
just made, catching a `resolved` status left without a `**Closed**` row. So
this is a right instruction carrying a rationale that is wrong for one of its
two branches. Remedy, verbatim: on the approve branch, run the guards **before**
flipping the status to `resolved`, and say that the post-flip run is what
checks the `**Closed**` row.

A third and smaller one: both new steps trigger `internal/handlers` on "a Go
doc comment", where `CLAUDE.md` §5's routing rule is broader and asks for that
package when a Go comment anywhere is edited. Nothing is lost in practice. The
subject of both new steps is Markdown, which cannot trip that package at all,
and §5 stays binding for the code edits at phase 2 step 4 whatever step 8 says.

The renumbering is clean. Old step 8 became 9, and no cross-reference in
`issues/Issues.md` names a phase-2 step above 7 — the surviving references are
to step 6 for the commit hash, to phase 2 step 4 as the verification standard,
and to step 2 in the orchestrator's own loop, all of them unmoved.

I followed the rule under review rather than only reading it. These notes were
written with the status still `in-progress`, then
`ISSUE=0478r scripts/check.sh go ./internal/db/...` was run over them — the
corrected form of step 5, deliberately ahead of the `resolved` flip so the
scan could see this text — and only then were the status, the `**Closed**`
row, and the resolution blockquote added and the commit made. The implementer
reports doing the same at phase 2 step 8, twice, having corrected a number in
its notes after the first post-notes run. That is the rule working as
designed, and it is the best evidence available that it is followable.

**What is now covered:** an implementer's `## Root cause`, `## Fix`,
`## Verification`, `## Files changed`, and `## Gotchas`, and a reviewer's
`## Review notes` on a bounce. **What is not:** a newly filed issue's
`## Description` and acceptance criteria, which reach git with no run of their
own whenever phase 1 is skipped, and a reviewer's `## Resolution notes`, which
the guards exempt by design once the status reads `resolved`.
