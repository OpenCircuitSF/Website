## Description

`certbot-renew.timer` runs and will renew the wildcard cert. **Nothing then
tells Apache to pick up the new one.** `mod_ssl` keeps serving the certificate
it loaded at start, so the renewal succeeds and the site goes on presenting the
old file until it expires.

The current cert is valid to **2026-11-16**. Renewal fires around 30 days out,
so from roughly **2026-10-17** the box holds a fresh cert that nothing is
serving, and on 2026-11-16 `www.opencircuitsf.com` starts throwing certificate
errors in every browser — along with `go.opencircuitsf.com` and every other name
the wildcard covers.

## How it was measured

`#0436`'s reviewer established it read-only, four independent ways:

- `/etc/letsencrypt/renewal-hooks/deploy/` — **empty**
- `/etc/letsencrypt/renewal-hooks/post/` — **empty**
- `/etc/sysconfig/certbot` — `PRE_HOOK=""`, `POST_HOOK=""`, `DEPLOY_HOOK=""`
- `certbot-renew.service` — a bare `ExecStart=/usr/bin/certbot renew --quiet`

And `/etc/letsencrypt/renewal/opencircuitsf.com.conf` has **no `installer =`
line**, so certbot itself never touches the web server either. That absence is
correct and deliberate — it is what keeps renewal from rewriting the vhost that
carries the `/.well-known/` carve-out (`CLAUDE.md` §7) — but it means the reload
has to come from somewhere else, and it does not.

## Why nobody noticed

The cert was issued recently enough that the timer has never had a renewal to
deploy. Everything observable says healthy: the timer fires on schedule, the
cert is valid, the site serves correctly. The failure is scheduled, not present.

`#0436` corrected the runbook's certbot command and, in the same pass, wrote
that "Certbot's own renewal timer needs no manual step here" — the opposite of
what the box shows. That sentence is `#0436`'s to fix; **the missing hook is
this issue's**, and it is a change to the box, which `#0436`'s criteria forbid.

## Acceptance criteria

1. A deploy hook exists that reloads Apache after a successful renewal — either
   a script in `/etc/letsencrypt/renewal-hooks/deploy/` or `DEPLOY_HOOK` in
   `/etc/sysconfig/certbot`. Pick one and say why.
2. It must reload rather than restart, and must be a **no-op when nothing
   renewed** — a deploy hook runs only on successful renewal, which is why it is
   the right hook of the three.
3. **Prove it without waiting for expiry.** `certbot renew --dry-run` exercises
   the renewal path; confirm the hook is invoked. A dry run does not deploy a
   real cert, so say explicitly what your proof does and does not establish.
4. The asset belongs in the repo under `deploy/`, not only on the box, so a
   rebuilt server gets it. Wire it into `docs/deployment.md`'s install steps.
5. **This is a change to production.** It needs the user's approval before it is
   applied to the box. Prepare it, prove it locally, and say exactly what needs
   running — do not apply it unasked (`CLAUDE.md` §5b, §9).
6. Do not touch the vhost, the renewal conf, or the `installer` absence. The
   `/.well-known/` carve-out serving this domain's Bluesky DID is in that vhost
   and the Go service 404s that path.

**The script's shell is clean.** Byte-scanned with `python3` (not `grep -P`,
per `CLAUDE.md` §8): pure ASCII, no CRLF, no tabs, and none of the bash-4
constructs that fail quietly on this laptop's 3.2.57 — no `${var,,}`,
`${var^^}`, `declare -A`, `mapfile`/`readarray`, `&>>`, `<<<`, or even `[[`.
It uses POSIX `[ -z … ]`. There are **no heredocs at all**, so the unquoted-
delimiter hazard does not arise. Run through an explicit `bash -c` rather than
the zsh tool shell: with `RENEWED_LINEAGE` unset it prints its refusal to
stderr and exits `1` before reaching `httpd -t`. Writing every message to
stderr is the right call — the timer runs `certbot renew --quiet`, which
suppresses stdout, so stdout messages would vanish from the journal.

**If `systemctl reload httpd` fails after `httpd -t` passes:** `set -euo
pipefail` makes the script exit non-zero at that line, before its success
message. Certbot's `_run_hook` then routes the result through
`report_executed_command`, which reports the non-zero return code together with
the hook's stdout and stderr — so the failure is visible in `journalctl -u
certbot-renew.service`. It does **not** raise, so certbot still counts the
renewal as successful and the exit code of `certbot renew` is unaffected. That
is the correct and expected shape; noted here because the issue should record
that a reload failure is *reported*, not *retried*. `httpd` and `systemctl`
resolve as bare names under systemd's default `PATH` — `/usr/sbin/httpd`,
`/usr/bin/systemctl` — so the unqualified calls are safe on this box.
`httpd.service`'s `ExecReload` is `/usr/sbin/httpd $OPTIONS -k graceful`, a
genuine graceful reload that drains in-flight requests, so the reload itself is
not a service disturbance.

### What must be fixed

**1. The approval-ready `certbot` command is unscoped, and this box has eight
lineages, not one.** `sudo certbot renew --dry-run --run-deploy-hooks` names no
`--cert-name`, so it processes **every** certificate certbot manages here.
Measured read-only: `sudo certbot certificates` lists eight — `beerbeerbeer.me`,
`eurekaplatforms.com`, `gregariousbots.social`, `opencircuitsf.com`,
`sstools.co-wildcard`, `terriblename.com`, `www.beerbeerbeer.me`,
`www.eurekaplatforms.com`. And this is not limited to the ones near expiry:
certbot's own `should_renew` returns `True` unconditionally when `dry_run` is
set ("Certificate not due for renewal, but simulating renewal for dry run"), so
all eight are attempted.

That matters because **two of those eight use `authenticator = apache`** —
`www.beerbeerbeer.me` and `www.eurekaplatforms.com` (measured by grepping
`/etc/letsencrypt/renewal/*.conf` read-only). Certbot's `--dry-run` help says
plainly: "It may trigger webserver reloads to temporarily modify & roll back
configuration files." The dry-run branch in certbot's renewal code skips only
*saving the lineage*; the authenticator runs in full beforehand. So the command
as written will have certbot's Apache plugin temporarily rewrite configuration
on the live production box and reload httpd, twice, for two domains that have
nothing to do with this project — then run the deploy hook eight times, for
eight more graceful reloads. The other six lineages additionally get real
(transient) Route 53 TXT records written and deleted in six hosted zones.

None of that is disclosed. The `docs/deployment.md` §9 paragraph explaining
"what step 3 proves, and what it does not" quotes one sentence out of the
`--dry-run` help and skips the webserver-reload warning sitting directly above
it in the same block.

**Is it safe to run?** A graceful reload is not a restart and drops no
in-flight requests, so the eight hook-driven reloads are benign. The genuine
exposure is the apache authenticator's temporary config mutation and rollback
on a shared httpd serving five other parties' domains — low probability of
harm, non-zero, and entirely avoidable. It is also gratuitous: none of it
contributes to proving this hook works.

**Remedy — scope the dry run to this project's lineage.** `certbot --help
renew`'s usage line is `certbot renew [--cert-name CERTNAME] [options]`, and
`--run-deploy-hooks` still picks up renewal-hooks-directory scripts under it, so
the proof is fully preserved while the collateral disappears: one staging
issuance, one Route 53 TXT create/delete in our own zone, one deploy-hook
invocation, one graceful reload, and no apache authenticator anywhere.

In `docs/deployment.md` §9, replace step 3's comment and command with exactly:

    # 3. Exercise the renewal path for THIS certificate only, against Let's
    #    Encrypt's *staging* server, with the deploy hook enabled, without
    #    touching the real certificate. --cert-name is required: without it
    #    certbot simulates renewal of all eight lineages on this box, two of
    #    which use the apache authenticator and would temporarily rewrite and
    #    reload Apache config for unrelated domains.
    sudo certbot renew --cert-name opencircuitsf.com --dry-run --run-deploy-hooks

and make the same substitution in `deploy/certbot/README.md`'s closing
pointer, which currently names the bare `certbot renew --dry-run
--run-deploy-hooks`.

Then add this paragraph to `docs/deployment.md` §9 immediately after the "What
step 3 proves, and what it does not" paragraph:

    **What step 3 does to the live box.** With `--cert-name` it touches one
    lineage: certbot writes and then deletes a `_acme-challenge` TXT record in
