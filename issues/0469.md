## Description

`#0468` established, and its review confirmed harder, that **backup failures are
not noticed by anyone**. The documents now say so accurately, which is what
`#0468` resolved. **This issue is the gap itself.**

`#0468`'s reviewer argued this belongs in the queue rather than in a resolved
issue's work log, and the argument is `#0468`'s own turned on itself: **a finding
recorded where nobody looks is not a signal**, and a resolved issue's work log is
exactly where a live recommendation goes to be forgotten.

## What is already established — do not re-derive it
`#0468`'s review checked the negative more thoroughly than the implementation
did, and these facts are measured:

- **systemd path units**: only two stock ones; nothing watches a directory.
- **`ec2-user`'s user manager**: `loginctl list-users` reports **`LINGER = no`**,
  so that manager exists only while a login session does — **it is not running at
  03:00 when a nightly backup fails.** This is the decisive fact, and it rules
  out the whole class of user-scope scheduling.
- **Every `OnFailure=` on the box**: ten stock units chaining to
  `emergency.target`. No chain reaches a notifier.
- **Off-box log shipping**: `rsyslog` remote forward, `systemd-journal-upload`,
  CloudWatch agent, `awslogs`, `collectd`, `telegraf`, `node_exporter`,
  `prometheus`, `datadog-agent`, `nrpe`, `zabbix-agent`, `monit` — all absent or
  inactive. **No journal content leaves the host.**
- **`amazon-ssm-agent` is `active`** — the single plausible scheduled-pull
  mechanism — but `/var/lib/amazon/ssm/` holds no association directory, so no
  State Manager association has ever run. **Recorded limit:** an AWS-side
  maintenance window cannot be proved absent from the box alone.
- **No MTA**: eight binaries absent, no `/usr/sbin/sendmail`, nothing on 25/587.
  `contact@opencircuitsf.com` is a real Workspace mailbox (`#0271`) and
  **unreachable from this box**.

## The two halves, and why neither works alone
1. **A schedule that pulls.** `#0468` deliberately did not build one, and its
   reviewer endorsed that: a timer writing `systemctl --failed` back to the
   journal produces a fact nobody reads *on a schedule*. Worse — **a unit named
   for failure-checking reads to a future maintainer as coverage that does not
   exist**, converting the honest gap back into the false reassurance `#0468`
   removed.
2. **A destination a person already looks at.** Choosing it is the user's
   decision, and this issue exists to put that decision in front of them.

## Acceptance criteria

1. **Put the choice to the user as a question answerable in one read**, with the
   options and their costs — not a recommendation dressed as a question. The
   `amazon-ssm-agent` finding and the absent MTA both narrow the field; say how.
2. **Build nothing until the user chooses** (§9 covers outward-facing sends; §5b
   covers approval-gated steps). If no answer comes, the stated options are the
   deliverable.
3. Whatever lands, **the schedule and the destination ship together.** A pull
   without a destination is the failure mode above; a destination without a pull
   is what `#0435` already has.
4. **Do not weaken `#0468`'s honest statement** while this is open. It is
   accurate until a channel exists, and reverting it to a reassurance is the
   defect `#0468` fixed.
5. Check whether `#0415`'s outcome changes the options — SES is sandboxed
   pending that issue, and if production access is granted, this project's own
   mail path becomes available.
