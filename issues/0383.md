## Description

`AdminImportsHandler.Revoke`'s `reason == ""` 400 and
`subscribers.ImportStore.Revoke`'s `ErrRevokeReasonRequired` produce an
**identical 400 body**. So removing the handler-level check leaves the whole
suite green.

Proved by mutation during `#0376`'s review: removing the handler check alone →
the test **passes**; removing both → it fails. The store layer is pinned
separately at `internal/subscribers/imports_test.go`; **the handler layer is
pinned by nothing.**

**No behavioural risk today** — both return the same status and message, and the
store's check runs before any database work (`imports.go:756`, first statement,
before `pool.Begin`). This is about **assertion honesty**, not a defect.

The live claim: `#0376` added a doc comment asserting the handler returns 400
*"before it ever calls `h.store.Revoke`"* — **a boundary the test cannot
demonstrate.** Five issues bounced this phase for doc comments claiming more
than the code delivers.

## The choice this issue must make

1. **Pin the handler layer specifically** — e.g. a fake store recording whether
   `Revoke` was called at all, so the test proves the boundary its comment
   asserts.
2. **Correct the doc comment** to say the test pins the *behaviour*, not the
   layer.

Option 2 is cheaper and removes a false claim rather than adding a mechanism —
the move `#0330`, `#0347` and `#0356` each landed on. Option 1 is more work but
makes the assertion match the intent. **Choose deliberately and record why**; do
not default.

## Acceptance criteria

1. The choice is made explicitly, with its reason recorded **in the test's own
   doc comment**, not only in this issue.
2. If option 1: prove the new assertion discriminates — remove the handler check
   alone and confirm the test now fails. **A check that cannot fail pins
   nothing**; `#0354`, `#0358` and `#0363` each shipped exactly that this phase.
3. If option 2: the corrected comment must not overstate in the other direction
   either — the behaviour *is* pinned, and the store layer *is* separately
   pinned; say both.
4. **Re-verify the two-layer premise yourself**: confirm both checks exist,
   produce identical bodies, and that removing only the handler's leaves the
   suite green. **Seven unsupported details reached issues this phase**, several
   written by the orchestrator.
5. §8b: mutations use **your own database** and never target a literal or seeded
   id. Note `#0376` retargeted this very test to a sentinel
   (`/admin/imports/999999999/revoke`) for exactly that reason — do not
   reintroduce a small id.
6. Per §5 name the specific tests that ran; `gofmt` stability; and run
   `./internal/handlers/...` so `#0356`'s repo-wide guard is in scope
   (see `#0381`).

## Fix

**Chose option 2** — corrected the doc comment rather than adding a
handler-layer-specific pinning mechanism (a fake store recording whether
`Revoke` was called). Reasoning, recorded in this decision and in the
test's own doc comment:

- Re-verified the two-layer premise directly against the code before
  deciding anything (criterion 4): `AdminImportsHandler.Revoke`'s
  `reason == ""` block returns `writeError(w, http.StatusBadRequest,
  "reason is required")` before calling `h.store.Revoke`;
  `subscribers.ImportStore.Revoke`'s first two statements are the same
  `reason = strings.TrimSpace(reason)` / `if reason == ""` check, returning
  `ErrRevokeReasonRequired`, which the handler's `switch` maps to the
  identical `writeError(w, http.StatusBadRequest, "reason is required")`.
  Both checks exist today; both bodies are byte-identical; the store's
  check runs before `tx, err := s.pool.Begin(ctx)`, i.e. before any
  database work.
- No behavioural risk today — both checks currently agree, so there is
  nothing broken to fix. The only live problem was the doc comment's
  overclaimed boundary.
- Option 1 (a fake store proving the handler-level check specifically)
  would add a mechanism to pin a distinction with zero behavioural
  consequence, for a boundary the store already independently enforces.
  Option 2 removes the false claim instead — cheaper, and the precedent
  this phase has repeatedly landed on (`#0330`, `#0347`, `#0356`).
- The corrected comment satisfies acceptance criterion 3: it states the
  test pins the *behaviour* (empty reason → 400) and explicitly says the
  store layer is *separately* pinned by
  `internal/subscribers/imports_test.go`'s `ErrRevokeReasonRequired`
  assertion — neither side is overstated.

No `#0383`-caused discrimination proof is needed under option 2, since no
new assertion was added; the decision itself, and why it does not need
one, is recorded here and in the test's doc comment.
