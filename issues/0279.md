# 0279 — Dashboard's dynamic `role` expression cannot be statically classified

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web / accessibility |
| **Phase** | 8 — Polish and follow-ups |
| **First seen** | 2026-08-27 |

## Description

`web/src/views/admin/Dashboard.svelte:115` writes

```svelte
role={w.alert ? 'alert' : 'status'}
```

inside a keyed `{#each}`. `#0242`'s live-region guard cannot classify a role it
cannot read statically, so the site is named in `KNOWN_DYNAMIC_ROLE_SITES`
rather than fixed. It is currently the **sole** entry in that allowlist, so
closing this issue empties it.

The `'alert'` half is fine — `#0243` settled that an `{#if}`-created
`role="alert"` is announced correctly.

The `'status'` half is not. It is announced on first insertion no more reliably
than the 20 loading placeholders `#0242` documents as exceptions: a keyed
re-render mutates the node in place, which is the case `role="status"` handles
well, but a **first appearance is a genuine insertion**, which is the case it
handles badly. So a warning that appears for the first time may be silent.

## Options

Both are legitimate; pick one and record why.

1. **Split into two static-role elements** — one `role="alert"` branch, one
   `role="status"` branch, each with a literal role the guard can read. Costs a
   little duplication in the template, removes the allowlist entry entirely.
2. **A persistent per-severity region** outside the `{#each}` that the row
   writes into. Matches the pattern `#0242` prefers everywhere else (a
   persistent node, not a created one), but is a larger change to how the
   dashboard reports per-workshop state.

## Acceptance criteria

1. `Dashboard.svelte:115` no longer uses a dynamic `role` expression. The role
   of every live region is statically readable.
2. `KNOWN_DYNAMIC_ROLE_SITES` is empty, and the guard fails if an entry is added
   without a written justification — or the set is removed outright if empty is
   now the permanent state. Do not leave an empty allowlist with no rule about
   what may enter it.
3. The `'status'` path is announced on first insertion. Whichever option is
   chosen, prove the announcement rather than asserting it, and say whether the
   proof rests on jsdom or a real browser (CLAUDE.md §5).
4. `#0242`'s guard passes with the entry gone, and its site counts are
   re-derived rather than edited by hand.
5. `ISSUE=NNNN scripts/check.sh web` passes.
