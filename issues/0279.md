## Description

`web/src/views/admin/Dashboard.svelte:115` writes

```svelte
role={w.alert ? 'alert' : 'status'}
```

inside a keyed `{#each}`. `#0242`'s live-region guard cannot classify a role it
cannot read statically, so the site is named in `KNOWN_DYNAMIC_ROLE_SITES`
rather than fixed. It is currently the **sole** entry in that allowlist, so
closing this issue empties it.

The `'alert'` half is fine — `#0243` settled that an `{#if}`-created
`role="alert"` is announced correctly.

The `'status'` half is not. It is announced on first insertion no more reliably
than the 20 loading placeholders `#0242` documents as exceptions: a keyed
re-render mutates the node in place, which is the case `role="status"` handles
well, but a **first appearance is a genuine insertion**, which is the case it
handles badly. So a warning that appears for the first time may be silent.

## Resolution notes

> 🟢 Resolved 2026-08-27 — `Dashboard.svelte`'s dynamic `role` expression is
> gone, `KNOWN_DYNAMIC_ROLE_SITES` is empty with `#0280`'s justification and
> staleness rules still governing anything added to it, and the `'status'`
> half is carried by a persistent, unconditionally-rendered announcer built on
> `SubscribeForm.svelte`'s established pattern. Criterion 3's proof is
> structural under jsdom and says so.

## Options

Both are legitimate; pick one and record why.

1. **Split into two static-role elements** — one `role="alert"` branch, one
   `role="status"` branch, each with a literal role the guard can read. Costs a
   little duplication in the template, removes the allowlist entry entirely.
2. **A persistent per-severity region** outside the `{#each}` that the row
   writes into. Matches the pattern `#0242` prefers everywhere else (a
   persistent node, not a created one), but is a larger change to how the
   dashboard reports per-workshop state.

## Acceptance criteria

1. `Dashboard.svelte:115` no longer uses a dynamic `role` expression. The role
   of every live region is statically readable.
2. `KNOWN_DYNAMIC_ROLE_SITES` is empty, and the guard fails if an entry is added
   without a written justification — or the set is removed outright if empty is
   now the permanent state. Do not leave an empty allowlist with no rule about
   what may enter it.
3. The `'status'` path is announced on first insertion. Whichever option is
   chosen, prove the announcement rather than asserting it, and say whether the
   proof rests on jsdom or a real browser (CLAUDE.md §5).
4. `#0242`'s guard passes with the entry gone, and its site counts are
   re-derived rather than edited by hand.
5. `ISSUE=NNNN scripts/check.sh web` passes.

## Chosen option

Option 1 (split into two static-role elements) for the classification half,
**plus** the persistent-region idea from option 2 for the reliability half —
the issue's own text makes clear splitting the role alone does not fix
criterion 3: role="status" is not reliably announced on a genuine first
insertion regardless of whether its role is written statically or
dynamically. So: the `{#each}` items became two `{#if w.alert}` branches
(`role="alert"` literal / no role at all — visual-only, styled via the same
`.alert` class as before), and a NEW persistent, unconditionally-rendered
`role="status" aria-live="polite"` paragraph was added outside the `{#each}`
(`lib/dashboard.ts`'s `statusWarningsAnnouncement`) that mutates to the
joined text of the non-alert warnings. This matches `SubscribeForm.svelte`'s
already-established `#subscribe-form-error` pattern and `#0063`'s own
decision that a live region must be a node that mutates, not one created
fresh — option 2's own framing, just scoped to the messaging alone rather
than restructuring how the whole warnings row renders.

## Root cause

`role={w.alert ? 'alert' : 'status'}` was two problems in one expression:
(1) a dynamic role value the AST guard cannot resolve statically at all, and
(2) even fully resolved, its `'status'` branch would still create a FRESH
DOM node per warning inside a keyed `{#each}` — reliable for an EXISTING
key's re-render (the guard's whole point about `role="status"` needing to
mutate, not insert), but not for a warning appearing for the first time,
which is a genuine insertion.

## Fix

- `Dashboard.svelte`: two `{#if w.alert}`/`{:else}` branches replace the
  single dynamic-role `<li>`; a new persistent `<p class="sr-only"
  role="status" aria-live="polite">{statusWarningsAnnouncement(warnings)}</p>`
  sits above the `{#if loading}` chain, unconditional from the component's
  very first render.
- `lib/dashboard.ts`: `statusWarningsAnnouncement(warnings)` joins only the
  non-alert warnings' messages (alert-severity ones are excluded —
  including them would announce the same text twice through two live
  regions at once); empty string when there is nothing to report.
- `liveRegionGuard.structuralGuard.test.ts`: `KNOWN_DYNAMIC_ROLE_SITES`
  emptied (its one entry). Left declared rather than deleted — see the
  set's own updated comment — because the general "any dynamic role/
  aria-live site fails loudly unless named" mechanism above it stays live
  and useful, and `#0280`'s justification + staleness rules already govern
  whatever gets added to it next; criterion 2's "or removed outright"
  alternative wasn't needed.
- Real-tree floors re-derived (not hand-edited): measured `alertSites`/
  `statusSites` both immediately before and after this change by running
  the enumeration test with a temporary `throw` reporting the live counts,
  swapping `Dashboard.svelte` and the guard file back to their prior
  committed content for the "before" measurement and restoring both
  byte-for-byte afterward (`shasum -a 256` verified, per CLAUDE.md §8a).
  The tree had already drifted since #0242's review recorded 56/30 —
  unrelated intervening work (the #0233/#0270/#0274 session, #0244) had
  already pushed it to 60 alertSites/31 statusSites — and this change adds
  one of each: **61 alertSites, 32 statusSites**, `loadingPlaceholders`
  unchanged at 20 (Dashboard's own two existing placeholders — "Loading
  overview…" and the empty-state notice — are untouched).

## Verification

**Criterion 3, jsdom (structural), not a real browser** (CLAUDE.md §5): 3
new tests in `Dashboard.behavior.test.ts` under `describe('Dashboard —
persistent status announcer (#0279)')`. They assert the announcer element
(`[role="status"][aria-live="polite"]`) is present in the DOM and empty
BEFORE the overview fetch resolves (proving it is not gated behind
`{#if overview}` and therefore not created fresh alongside its first
content), that its text mutates to include only non-alert warning messages
once loaded, and that it stays empty when every warning present is
alert-severity. These prove the STRUCTURAL shape #0063's decision relies on
(a pre-existing node whose text later mutates); they are not a claim that a
real screen reader spoke anything — no real-browser AT verification was run
for this issue, unlike `#0244`'s item 1 (Safari/`safaridriver`), which this
issue's own text and CLAUDE.md §5 both require disclosing.

`ISSUE=0279 scripts/check.sh web` — `npm run check`: 287 files, 0 errors,
0 warnings. `npm test`: 40 test files, **3960 tests, 0 failures** (up from
3953 after `#0280`: 3 new `statusWarningsAnnouncement` tests in

## Review notes

> 🟢 Reviewed 2026-08-27 (Opus, phase 3) — **pass**. Verified independently.

**Criterion 1.** No dynamic `role`/`aria-live` expression remains anywhere in
`web/src`: the guard's `UNCLASSIFIABLE` path reports nothing, and
`KNOWN_DYNAMIC_ROLE_SITES` is empty with no stale entry — which is only
consistent if nothing matched and nothing failed.

**Criterion 2.** The set is empty and left declared. That is acceptable under
the criterion's "do not leave an empty allowlist with no rule about what may
enter it" because `#0280`'s justification and staleness rules apply to it
unchanged — the empty array is not a hole, it is an assertion that no exception
is currently justified, and the "any dynamic role site fails loudly unless
named" mechanism above it is still live and still exercised by two synthetic
fixtures.

**The chosen approach is right, and its reasoning is the important part.**
Splitting the role alone would have satisfied criterion 1 while leaving
criterion 3 unmet — a freshly inserted `role="status"` node is unreliable
whether or not its role is written statically. Taking option 1 for the
classification half and option 2's persistent region for the reliability half
is the correct reading of the issue, not a hedge. The announcer matches
`SubscribeForm.svelte:203`'s `#subscribe-form-error` pattern as claimed
(unconditional, `sr-only` when empty, mutating text) — checked, not taken on
trust. Excluding alert-severity messages is right: the `<li>` alert branch
carries `role="alert"` and would otherwise announce the same text through two
regions.

**Criterion 3 — the proof is structural under jsdom, and the issue says so.**
The three `Dashboard.behavior.test.ts` tests prove the precondition (the node
exists and is empty before the fetch resolves, so its later change is a
mutation), not that anything was spoken. That is weaker than the criterion's
literal "prove the announcement", and the disclosure is doing real work here
rather than papering over a gap. Accepted because this project has no
repeatable browser-AT harness yet and `#0287` is already open for one; the
structural shape is the part `#0063`'s decision actually turns on, and
`SubscribeForm`'s equivalent *was* proved in real Safari, so the pattern being
copied is browser-validated even though this instance is not.

**Criterion 4 — counts re-derived, and the drift claim checked.** I measured
both trees myself with a temporary throw in a throwaway worktree, not by
reading the comment. Pre-batch (`eb6c78f^` = `1f78280`): `filesScanned` 38,
`alertSites` **60**, `statusSites` **31**, `loadingPlaceholders` 20 — against
floors of 56/30, so the tree had indeed already drifted before this batch
touched it. After the batch: 38 / **61** / **32** / 20, matching the new floors
exactly. `find web/src -name '*.svelte' | wc -l` = 38 independently.
