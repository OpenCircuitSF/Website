## Description

`#0228` fixed **object** ownership after a restore — every table, sequence and
view is reassigned to `RESTORE_OWNER`. It did not fix the **schema**.

`public` resolves to `pg_database_owner`, which is whoever created the database
— `postgres` on the documented production path. Measured by `#0228`'s review:

```
create table … as opencircuit  ->  ERROR: permission denied for schema public
```

against a restored database, where the same probe succeeds on a database made
with `createdb -O opencircuit`.

**Why this is not covered by `#0228` passing.** Its criterion is that the app
can read and write its own tables, and that genuinely holds — `SELECT` and
`INSERT` as `opencircuit` both succeed. Serving traffic works. What fails is
`CREATE TABLE`, and therefore **`migrate up`** — so the first deploy after an
incident restore fails, and `scripts/deploy.sh` runs migrations as part of an
ordinary redeploy.

The shape of the failure is the problem: a restore appears to succeed, the site
comes back, and the breakage surfaces later at the next deploy, when nobody is
thinking about the restore any more. `#0228`'s note that "the app only needs to
read and write the objects" is true of serving and false of deploying.

## Root cause

`#0228` reassigned the ownership of every **object** restored into `public`
(tables, sequences, views) to `RESTORE_OWNER`, but never touched the
**schema** those objects live in. PostgreSQL 15+ defaults `public`'s owner to
`pg_database_owner`, a pseudo-role that dynamically resolves to whoever owns
the *database* — the restoring superuser (`postgres` on the documented
production path), not `opencircuit`. `SELECT`/`INSERT` against
already-restored tables check the *table's* owner/grants, which `#0228`'s
fix set correctly, so those kept working and the restore looked completely
successful. `CREATE TABLE` checks the *schema's* `CREATE` privilege instead,
which only the schema owner (or someone granted it) has — and nothing
granted it. The gap was invisible until the next deploy's `migrate up`,
which is exactly the "problem surfaces later, when nobody is thinking about
the restore any more" shape the issue's own Description names.

## Fix

All in `scripts/db/restore.sh`'s `reassign_ownership()`, which already ran
after every restore under the same `RESTORE_OWNER` (default `opencircuit`)
and the same `RESTORE_OWNER=""` opt-out:

1. **Schema ownership**, the actual gap: a new loop over
   `pg_namespace` (same `NOT IN ('pg_catalog', 'information_schema')` filter
   the existing table/sequence/view loops already use, plus excluding
   `pg\_%`-prefixed system schemas) runs `ALTER SCHEMA %I OWNER TO …` for
   every non-system schema — `public` today, any future schema
   automatically. Placed first in the `DO $$` block, though order does not
   functionally matter here (the block runs as a superuser, which can
   `ALTER` regardless of current ownership).
2. **Materialized views, standalone types, functions/procedures** — the
   three items the review flagged as unreachable-but-uncovered. All three
   are now covered:
   - Materialized views: same shape as the existing view loop, against
     `pg_matviews`.
   - Types: enums (`typtype='e'`), domains (`'d'`), and standalone composite
     types declared with `CREATE TYPE … AS (…)` (`'c'`) — explicitly
     excluding the implicit row type every table/view/matview already has
     (ownership follows the relation, not the type) and Postgres's
     auto-generated array type per named type (not independently ownable;
     recognizable by its `_`-prefixed name).
   - Functions/procedures: keyed by identity signature
     (`pg_get_function_identity_arguments`) since overloads share a name;
     `ALTER PROCEDURE` vs `ALTER FUNCTION` branches on `prokind`.
   - **Deliberately still not covered, and said so in the script's own
     comment**: aggregates (`prokind='a'`) need `ALTER AGGREGATE`'s distinct
     signature syntax, and table/view/matview row types are already handled
     via their relation's own `ALTER`. Confirmed none of the three
     originally-flagged kinds (matviews, types, functions) exist in
     `migrations/` today (`grep -rniE 'CREATE (OR REPLACE )?(FUNCTION|TYPE|
     MATERIALIZED VIEW|PROCEDURE|DOMAIN|AGGREGATE)' migrations/` — no
     output), so this closes a latent gap rather than an active one.
3. **`RESTORE_OWNER` validation moved before the restore runs.** A new
   `validate_owner()` is called immediately after the env vars are read —
   before the dump-file existence check, before `createdb`, before
   `pg_restore`/`psql` touch anything. A malformed value now exits 2 with
   nothing done, instead of only being caught inside `reassign_ownership()`
   at the very end, after a full restore had already run.
4. **`docs/deployment.md`'s restore drill** — added step 4b, a real
   `migrate up` against the restored database as the `opencircuit` role,
   with the seeding instruction changed to withhold the last migration so
   this step has a genuine pending migration to apply rather than silently
   no-op'ing. Rewrote the "Roles and ownership" bullet to describe the
   schema-level fix, why `#0228`'s own passing drill didn't catch it
   (SELECT/INSERT succeed even when this is broken), and the before/after
   proof. Fixed the step 4 cross-reference from `see "Ownership" below` to
   `see "Roles and ownership" below`, matching the section's actual title.

**A real bug found and fixed during verification, not left in:** the first
draft of the schema-reassignment SQL comment used markdown-style backticks
around `migrate up` inside the `DO $$ … $$` block. That block is spliced
into an **unquoted** heredoc (`<<SQL`, required so bash can interpolate
`$owner` — see the script's own note on this), so those backticks were not
inert prose — bash performed real command substitution on them while
building the heredoc text, silently invoking `migrate up` (with no
`-database` flag, since `up` was consumed as part of the substituted
command) every single time `reassign_ownership` ran. Caught because it
printed `error: failed to parse scheme from source URL: URL cannot be
empty` in the middle of otherwise-clean restore output during this pass's
own verification below, not from static review — reproduced, fixed
(rewrote the comment without backticks), and re-verified silent. Worth
recording: **any text added inside this heredoc is live shell, not a
comment**, backticks and unescaped `$` included.

## Gotchas

- **The heredoc that builds the ownership-reassignment SQL is unquoted on
  purpose** (`<<SQL`, not `<<'SQL'`), so bash performs real variable and
  command substitution on its *entire* body, not just the `$owner` token it
  is there for. See `## Fix`'s backtick bug — any future edit inside that
  block needs to be read as live shell, not inert SQL/comment text.
- **This machine has no `postgres` OS role** (Homebrew Postgres uses the
  installing user as superuser), so the production path's `sudo -u postgres`
  cannot be reproduced literally in local verification. The structural
  stand-in used throughout — running as this machine's own superuser via
  `BACKUP_RUN_AS=""` — reproduces the *actual defect* (schema owned by
  someone other than `opencircuit` after a restore) correctly; it does not
  prove anything about `sudo`/peer-auth mechanics themselves, which
  `restore.sh`'s existing `BACKUP_RUN_AS` handling already covered
  separately.
