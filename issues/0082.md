## Description

`docs/database.md` carries a table of every migration and a sentence naming the range. It has now drifted **three times**:

- `#0009` added `000008` without updating it — caught in review.
- `#0023`/`#0025` added `000009`/`000010` — caught, updated.
- `#0026` added `000011` — **currently stale**: no row, and the prose still says "numbered `000001`–`000010`".

Each instance was caught by a human-equivalent reading rather than by anything mechanical, and one was missed until a later review.

> 🟢 Resolved 2026-08-19 — `docs/database.md` carries its `000011` row and a corrected `000001`–`000011` range, and `internal/db/docs_parity_test.go` now enforces both mechanically instead of relying on the next reviewer noticing. The reviewer re-ran the mutation independently — a throwaway `migrations/000012_zz_review_mutation.up.sql` with no doc row — and **both** assertions fired, each naming the offending migration *and* `docs/database.md` as the file to edit, with green restored the moment the file was removed; the two assertions were then exercised **separately** to prove neither is carried by the other, a typo'd stem failing the row check alone and a stale range sentence with all eleven rows present failing the range check alone. The guard is genuinely cheap and filesystem-only — no `pgx`, no `TEST_DATABASE_URL`, no connection of any kind, and `internal/db`'s `TestMain` is a no-op when that variable is unset — verified by running it green with the variable unset, so it rides every `go test ./...` a backend pass already performs. Three blind spots were found by probing rather than reading and are recorded below for a follow-up rather than blocking, since the issue asked only for the forward direction: a stale doc row surviving a **deleted** migration is not caught (proved by moving `000009` off disk — the suite stayed green, and the resulting numbering gap went unnoticed too), a `.up.sql` with **no matching `.down.sql`** is not caught, and the row check is a whole-file `strings.Contains` so a backticked mention inside a **fenced code block** satisfies it just as well as a real table row. On the `CLAUDE.md` question the implementer's decision to stay in its lane and record a recommendation was correct, and the reviewer's verdict is that the guard **should** now cover it — as one table-driven test over both files, not a sibling — since the hand-correction in `f5e989a` was the fourth drift of this exact class. `go build`, `go vet`, and `go test ./... -count=1` with `TEST_DATABASE_URL` exported are green with **zero failures and zero skips**, and `50d67ea` touches `docs/database.md` and `internal/db/` only.

## Why a test rather than another correction

Three occurrences is a pattern, not an accident. The table is genuinely useful — it explains *why* each migration exists, which filenames cannot — so the answer is not to delete it. But a doc that must be manually synchronised with a directory listing will drift again, and the next reviewer may not check.

## Fix

`docs/database.md`:

- Added the `000011_add_subscribers_already_subscribed_sent_at` row to the
  "Mailing list schema" table, describing the `already_subscribed_sent_at`
  claim column `#0026`'s review added and why (mirrors `confirm_sent_at`'s
  atomic claim-before-send pattern for the "already subscribed" email).
- Corrected the opening paragraph's range from `` `000001`–`000010` `` to
  `` `000001`–`000011` ``.

`internal/db/docs_parity_test.go` (new) is the guard, in the same shape as
`#0071`'s route-table parity test:

- `listMigrations` reads `migrations/*.up.sql`, extracting each file's
  6-digit version and full `NNNNNN_name` stem via
  `^(\d{6})_([a-z0-9_]+)\.up\.sql$`.
- For each migration, asserts its stem appears backtick-wrapped
  (`` `000011_add_subscribers_already_subscribed_sent_at` `` etc.) somewhere
  in `docs/database.md` — matching the exact style the doc's table already
  uses for every existing row.
- Extracts the doc's `` numbered `NNNNNN`–`NNNNNN` `` range sentence via
  regex (tolerating both the en dash the doc actually uses and a plain
  hyphen) and asserts its upper bound equals the highest migration version
  found on disk.
- Lives in `internal/db` — the package whose own doc comment already says
  it "manages the PostgreSQL connection pool and migrations" — rather than
  `internal/handlers` (where `#0071`'s parity test lives), since
  `internal/handlers` has `#0081`'s work in flight concurrently and is
  otherwise unrelated to migrations.
- Filesystem-only: no `TEST_DATABASE_URL`, no database connection. It reads
  `../../migrations` and `../../docs/database.md` relative to the package
  directory, which is `go test`'s working directory for this package
  regardless of the `go test ./...` invocation's own working directory.

### CLAUDE.md decision

`CLAUDE.md` line 37 ("`migrations/` \| `golang-migrate` up/down SQL pairs,
contiguous `000001`–`000008`") is *also* stale — a fourth instance of the
same drift, on a different file. **Decision: not covered by this test in
this pass, and not corrected in this commit.** Reasons:

1. This batch's declared scope (concurrency lane, set by the orchestrating
   task) is `internal/middleware/clientip.go` and its test, `docs/database.md`,
   a new docs-parity test, and `issues/0080.md`/`issues/0082.md` —
   `CLAUDE.md` was not included, and it is a high-traffic shared file edited
   across many issues; touching it here would be scope creep beyond what
   was authorized for this pass.
2. The fix is trivial once someone is authorized to make it (the same
   `000001`–`0000NN` prose correction applied above), but a mechanical
   guard for it would need to either duplicate `docRangePattern`-style
   parsing against `CLAUDE.md`'s different sentence shape ("contiguous
   `000001`–`000008`" vs. `docs/database.md`'s "numbered `000001`–`000011`")
   or generalize `TestDatabaseDocMigrationParity` to check both files, which
   is a real design decision (one test asserting two independent docs, or
   two guards) better made deliberately rather than folded into this pass.

**Recommendation for a follow-up issue**: correct `CLAUDE.md` line 37 to
`000001`–`000011`, and either extend `internal/db/docs_parity_test.go` to
also assert `CLAUDE.md`'s range (same technique, different regex) or add a
sibling test — whichever a reviewer prefers, since `CLAUDE.md`'s statement
says "contiguous" rather than naming every migration individually, so it
only needs the range check, not the per-row check.

**The two assertions, independently.** They fire together on a new migration, so

**Blind spots.** Probed empirically; each mutation was applied, run, and

| Scenario | Caught? | Evidence |
|---|---|---|
| Migration on disk with no doc row | ✅ yes | the mutation above |
| Doc row's stem subtly wrong (typo) | ✅ yes | `…_sent_at` → `…_sent_ats` failed the row check |
| Range prose stale | ✅ yes | fires in both directions (stated high ≠ actual high) |
| **Doc row for a migration that no longer exists** | ❌ **no** | moved `000009_create_interests.{up,down}.sql` off disk, left its row in place — suite stayed **green**. The check is one-directional: it iterates files and looks for rows, never rows looking for files |
| **Numbering gap / non-contiguity** | ❌ **no** | same probe: with `000009` absent the range still read `000001`–`000011` and passed, though the doc (and `CLAUDE.md`) both assert a *contiguous* range |
| **`.up.sql` with no matching `.down.sql`** | ❌ **no** | created `000012_zz_no_down.up.sql` with a doc row and bumped range, no `.down.sql` — **green**. `listMigrations` globs `*.up.sql` only, so a half-migration is invisible |
| **Row present only inside a code block or comment** | ❌ **no** | replaced `000011`'s table row with a fenced code block mentioning the same backticked stem — **green**. The check is `strings.Contains(doc, "`"+stem+"`")` over the whole file, with no notion of "is a table row" |

None of these block the issue — its acceptance criteria asked for the forward
direction and the range, and both are delivered and proven. They are the natural
content of the follow-up issue below.

**Cheap and filesystem-only: confirmed.** `docs_parity_test.go` imports only
`os`, `regexp`, `sort`, `strconv`, `strings`, `testing` — no `pgx`, no
`database/sql`, no `TEST_DATABASE_URL` reference. `internal/db/main_test.go`'s
`TestMain` calls `testdb.Lock()`, which returns a no-op when that variable is
unset, so the test is never gated or skipped. Verified by running it with
`TEST_DATABASE_URL` **unset**: it passed, and failed correctly under mutation in
the same state. It runs on every `go test ./...` in ~0.2 s.

One minor, non-blocking consequence of its placement: when `TEST_DATABASE_URL`
*is* set, `internal/db`'s `TestMain` takes the shared cross-package advisory
lock, so this filesystem-only test waits behind other DB packages. It does not
need a database — it just queues with ones that do. Not worth moving on its own.

**`CLAUDE.md` — the reviewer's verdict.** The implementer was right to decline:
`CLAUDE.md` was outside its lane, and "one test over two files vs. two tests" is
a design call, not a drop-in. Having declined, recording the recommendation was
the correct disposal. Now that `f5e989a` has corrected the stale line by hand —
**the fourth drift of this same class**, and the second file it has happened in —
the answer is that the guard **should** cover `CLAUDE.md`, as **one
table-driven test over both files**, not a sibling test.

Rationale for one test rather than two: the two files differ only in wording
(`` numbered `000001`–`000011` `` vs. `` contiguous `000001`–`000011` ``) and in
whether individual rows are enumerated. That is a two-field table, not a second
test:

```go
for _, f := range []struct {
    path      string
    checkRows bool   // CLAUDE.md states only a range; docs/database.md enumerates rows
}{
    {docsPath, true},
    {claudePath, false},
} { … }
```

with `docRangePattern` loosened to `(?:numbered|contiguous) \`(\d{6})\`[–-]\`(\d{6})\``.
A sibling test would duplicate the parsing, the en-dash handling, and the
`listMigrations` call for no benefit, and would itself be a thing that can drift
out of step with its twin — which is the exact failure this issue exists to stop.

**Recommended follow-up issue** (reviewer's, for the orchestrator to file):
extend `internal/db/docs_parity_test.go` to (1) cover `CLAUDE.md`'s range
statement via the table above, (2) assert the **reverse** direction — every
backtick-wrapped `NNNNNN_name` token in `docs/database.md` corresponds to a file
on disk, closing the stale-row blind spot, (3) assert contiguity from `000001`
to the highest version with no gaps, which both files' prose already claims, and
(4) assert every `*.up.sql` has a matching `*.down.sql`. Items 2 and 3 are the
ones that would have caught a deleted migration; item 4 is cheap and guards the
append-only rule in CLAUDE.md §1.
