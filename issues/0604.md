## Description

Brennan, 2026-10-18: "I need to delete these posts. Will I be able to post
the corrected post when this is fixed? We need a way to fix this."

Posts 1 (Bluesky) and 4 (Mastodon) went out with dead short links
(`#0603`). Once a post is `posted`, the app can't take it down or send it
again, and Reset refuses while anything is posted. Bluesky posts can't be
edited at all.

Three idempotency hazards make a naive "set it back to draft" wrong:
- **Bluesky:** `postBluesky` uses a deterministic record key,
  `bluesky.TID(job.CreatedAt, id)`. `Client.Post` first calls `getRecord`
  and treats an existing record as already posted. Re-creating with the
  same rkey after a delete is fragile, because the AppView caches by URI.
- **Mastodon:** `PostStatus` sends
  `Idempotency-Key: opencircuitsf-outreach-post-<id>`. Mastodon remembers
  that key for about an hour and would hand back the deleted status instead
  of posting.
- **Bodies:** a posted row's body keeps the old dead URL. `#0603`
  deliberately repairs only unsent bodies, so a re-sent body must be
  refreshed from the row's current (repaired) `short_url`.

## Acceptance criteria

- [ ] **Remote delete in the clients.**
      - `bluesky.Client.DeletePost(ctx, rkey)`: calls
        `com.atproto.repo.deleteRecord` with the repo DID and collection
        `app.bsky.feed.post`.
      - `mastodon.Client.DeleteStatus(ctx, id)`: calls
        `DELETE /api/v1/statuses/{id}`.
      - Both treat "already gone" (404 or record-not-found) as success.
      - Both redact credentials from errors, as the existing calls do.
      - Tests against fake servers, including the already-gone case.
- [ ] **A new "Delete and redo" action**:
      - Route: `POST /admin/outreach-posts/{id}/takedown`, behind admin
        auth and CSRF like the other post actions, and audit-logged with
        the remote URL.
      - It applies only to automatic-channel posts with status `posted`.
        It deletes the remote post using the stored remote id or rkey,
        then returns the row to `draft`:
        - clear `posted_at`, `remote_id` and `remote_url`;
        - clear any scheduled time and error;
        - increment a new `attempt_generation` column (or similar),
          migration `000044`;
        - refresh the body so its link is the row's current `short_url`
          (replace the old URL; a `{link}` token is untouched).
      - If the remote delete fails for a reason other than already-gone,
        the row stays `posted` and the response says why in plain words.
      - Concurrency: lock the row (`FOR UPDATE`) so a takedown can't race
        a send. Refuse if a live outbox row exists for it.
      - Manual-channel posts keep the existing Unmark.
- [ ] **Re-sending uses fresh idempotency.**
      - When `attempt_generation > 0`, the Bluesky rkey is derived from a
        new timestamp, or from the generation, so it never equals a
        deleted record's rkey.
      - The Mastodon idempotency key includes the generation.
      - Generation 0 keeps today's keys exactly, so in-flight retries are
        unaffected.
      - Tests prove a re-send after takedown creates a new record or
        status, and does not recover the deleted one.
- [ ] **SPA.**
      - A posted automatic post card shows **Delete and redo…**. It opens
        an `OutreachConfirmDialog`: "Delete this post from Bluesky? It will
        be removed for everyone, and the post goes back to draft so you
        can post it again." Follow the no-native-confirm and modal guard
        patterns.
      - On success the card shows the draft with the corrected link and
        the usual Post now/Schedule actions.
      - If Brennan already deleted the post by hand, the same button works,
        because already-gone counts as success.
      - Once nothing is posted, `can_reset` becomes true again, so Reset is
        also available.
      - jsdom tests for the dialog, the success state and the failure
        message.
- [ ] **Migration hygiene:**
      - `000044` up and down.
      - Update `docs/database.md` and the AGENTS.md range.
      - Run `internal/db` and `internal/handlers`.
      - `scripts/testdb.sh template`.
- [ ] Verified with
      `ISSUE=0604 scripts/check.sh go ./internal/bluesky/... ./internal/mastodon/... ./internal/outreach/... ./internal/handlers/... ./internal/db/... ./cmd/opencircuit/...`
      and `ISSUE=0604 scripts/check.sh web`. Zero skips. No real network
      calls; fake servers only.
