## Description

A complaint that lands **after** a confirmation claim commits but **before**
`OutboxWorker` drains the row still results in a delivered confirmation.

`OutboxWorker.render`'s `KindConfirmation` arm builds the message from
`row.Payload` and `row.Recipient` alone. Verified by `#0341`'s review: the
worker consults **neither** `subscribers.status` **nor** `suppressions` before
sending.

Both producing paths share this. `#0341` added `AND status = $4` to
`ClaimAndEnqueueConfirmation`'s claim `UPDATE`, and `AdminResendConfirmation`
checks status in Go under `FOR UPDATE` — but both, correctly, only close the
window **up to commit**. Nothing re-checks between commit and send.

**This predates `#0341` and is a different change in a different package.** It
is filed rather than folded in because closing it requires a decision, not just
a predicate.

**§9 is adjacent and binding**: *"`complained` subscribers never auto-resubscribe.
Only an admin clears that state."* A delivered confirmation to a `complained`
address is the shape that rule exists to prevent, even though the claim itself
was legitimate when taken.

## Root cause

`OutboxWorker.sendOne` built and sent a message from `row.Payload` and
`row.Recipient` alone, never re-reading the subscriber's live state between
a confirmation claim's commit and the worker actually draining the row.
`#0341` closed the window **up to commit** (the claim `UPDATE`'s own `WHERE`
clause), but nothing re-checked **after** commit — so a complaint landing in
that window (seconds, ordinarily; indefinite for `welcome`/`import_invite`
rows deferred on a missing `physical_address`) still resulted in a
delivered message to a `complained` or otherwise-ineligible address.

## Fix

Implemented exactly as `## Plan` specifies — no deviation. In summary:

1. **`sendGate`** (`internal/mailing/outbox_worker.go`), called as the first
   statement of `sendOne`, before `render`. For the four kinds in the new
   `gatedKinds` map (`confirmation`→`pending`, `already_subscribed`→`active`,
   `welcome`→`active`, `import_invite`→`pending`), it calls
   `internal/subscribers.Store.SendEligibility` (new file
   `send_eligibility.go`, not an edit to `store.go`) and re-checks three
   predicates — live `status`, `suppressions` (reason-blind), and live
   `email` matching `outbound_queue.recipient` — mirroring
   `RecheckEligibleTx`/`recheckReason` (`audience.go`) predicate-for-
   predicate. `registration`/`recovery`/`sessions_revoked`/`admin_alert`/
   `goodbye` are listed in `ungatedKinds`, each with a written reason.
2. An ineligible row transitions to the new terminal status `outbox.StatusSkipped`
   (`'skipped'`) via the new `Store.MarkSkipped` method — reason in `error`,
   `payload` blanked to `'{}'::jsonb`, `claimed_at` cleared, guarded on
   `status = 'sending'` only. Migration `000027` widens
   `outbound_queue_status_check` to add it; `000021` is untouched. The
   `.down.sql` resets `skipped` rows to `abandoned` before narrowing the
   CHECK, matching `000018`'s precedent.

   `subscriber_events`: no new `Action`, no `PRD.md` §6.11 edit, no admin

4. `render` is unmodified — confirmed by diff: the gate returns before
   `render` is ever called for an ineligible row, so `#0045`/`#0264`'s

5. `internal/handlers` is untouched — no file in that package appears in
   this commit's diff. `sendGate` runs on `OutboxWorker`'s own goroutine

   handler wrote its `202` response (`#0254` makes that response durable

## Gotchas

- `subscribers.Store.Confirm` auto-enqueues a `welcome` row inside its own
  transaction (and `Store.Create` auto-enqueues a `confirmation` row). Any
  new test seeding a subscriber via `Create`/`Confirm` and then *also*
  explicitly enqueueing the same kind ends up with two eligible rows for one
  subscriber, which can make an event count that expects exactly 1
  nondeterministic. Tests here find and drain the auto-enqueued row instead
  (mirroring the pre-existing `TestOutboxWorker_MarkSent_RecordsConfirmationSent`'s
  own pattern) rather than adding a second `Enqueue` call.
- `subscribers.Store.Unsubscribe`'s `unsubscribe_source` argument is
  CHECK-constrained to `one_click | preferences | mailto | admin`
  (`subscribers.SourceOneClick` etc.) — an arbitrary string fails loudly
  with a `23514` constraint violation, and because this package's tests
  share one `outbound_queue` table across the whole test binary run, an
  early `t.Fatalf` from that failure (before `runWorkerUntilStopped` starts
  a worker) can leave an eligible `'queued'` row for a *later* test's fresh
  worker to pick up and send — surfacing as a confusing, unrelated-looking
  failure in whichever test happens to run next. Caught and fixed during
  this issue's own verification; the "assert 0 sends" checks were also
  tightened to scope by recipient (`sentTo`, matching this file's existing
  `countInviteSent`/`countWelcomeSent` convention) rather than
  `mailer.Sent()`'s raw length, so a similar leftover row from a genuinely
  unrelated cause fails loudly rather than silently passing or silently
  misattributing.

## The decision this issue must make

A send-time re-check in `OutboxWorker.sendOne` needs a policy for the stale row,
and the three options differ in what they cost:

- **drop** it silently — loses the audit trail;
- **abandon** it (the existing terminal state) — visible in `outbox_queue`, but
  conflates "we chose not to send" with "we gave up after retries";
- **log and skip** — needs a decision about which activity-log event, and
  whether an admin is alerted.

Say which and why. Also decide whether the re-check covers **suppressions** as
well as `subscribers.status`, since those are two different tables answering two
different questions, and `#0038`'s account of the suppression layer applies.

### 1. Why a send-time re-check is a different mechanism from `#0341`'s

`#0341` and `#0263` close the window **up to commit**: a claim's `WHERE`
clause (or a `FOR UPDATE` re-read) decides whether a row is enqueued at all.
Once that transaction commits, the queue row is an instruction with no
remaining authority behind it — `OutboxWorker.render` builds the message from
`row.Payload` and `row.Recipient` and nothing else, so every fact the claim
checked is frozen at enqueue time while the subscriber's real state keeps
moving.

The project already solved exactly this for the campaign half, and the
solution is the model here. `internal/mailing/audience.go`'s package doc
comment states the rule outright:

> At send (`RecheckEligibleTx`), this is the check that is actually
> load-bearing for correctness: delete it and wrong mail goes out.

`email_sends` gets `RecheckEligibleTx` + `MarkSkippedTx`; `outbound_queue`
gets nothing. **This issue is the transactional-mail twin of that pair**, and
the plan below deliberately mirrors it predicate-for-predicate and
word-for-word so the two halves of the system read the same.

### 2. Which kinds are gated — criterion 7, answered with evidence

**The window is not confirmation-specific.** Every kind carrying a
`subscriber_id` has it, and for two of them it is *wider* than for
confirmation.

Enqueue sites, re-derived (`grep -rn 'Kind[A-Z]' --include='*.go' .`, non-test
producers only):

| Kind | Enqueued by | Subscriber status at enqueue | Window |
|---|---|---|---|
| `confirmation` | `Store.Create` (`store.go:484`), `ClaimAndEnqueueConfirmation` (`store.go:748`), `AdminResendConfirmation` (`pending.go:244`) | `pending` | enqueue → drain |
| `already_subscribed` | `ClaimAndEnqueueAlreadySubscribed` (`store.go:807`) | `active` | enqueue → drain |
| `welcome` | `Confirm` (`store.go:1062`) | `active` | enqueue → drain, **plus the indefinite defer, below** |
| `import_invite` | `ImportStore.Commit` (`imports.go:673`, `ConsentModeInvite` only), `AdminResendInvitation` (`pending.go:418`) | `pending` | enqueue → drain, **plus the indefinite defer** |

**`welcome` and `import_invite` have the widest window in the system, and it
is structural rather than incidental.** `render` refuses both when
`settings.physical_address` is blank (`errWelcomePhysicalAddressRequired`,
`errImportInviteMissingPhysicalAddress`, `#0264`/`#0129`), and
`deferMissingPhysicalAddress` requeues them with
`welcomeAddressDeferMaxRetries = math.MaxInt32` — so such a row **never**
abandons and backs off along the ordinary schedule clamped to 24h, waiting for
an admin. `CLAUDE.md` §10 item 3 records the PO box as *not started*, so this
is the current state of both kinds, not a hypothetical: a welcome enqueued
today parks in that loop indefinitely while nothing re-checks the subscriber.
`#0264`'s own review also judged the welcome **commercial** rather than
transactional — mailing a commercial message to a `complained` address is
materially worse than mailing a confirmation, which is the §9 rule's whole
point.

That is why these belong in this issue rather than a follow-up: the mechanism,
the store method, the test harness and the mutation proof are all identical,
and the marginal cost of a fourth row in a map is nil while the marginal
benefit is the largest share of the actual exposure.

**Gated kinds and the status each message is only valid for** — a package-level
map in `internal/mailing/outbox_worker.go`:

```go
var gatedKinds = map[outbox.Kind]string{
	outbox.KindConfirmation:      subscribers.StatusPending,
	outbox.KindAlreadySubscribed: subscribers.StatusActive,
	outbox.KindWelcome:           subscribers.StatusActive,
	outbox.KindImportInvite:      subscribers.StatusPending,
}
```

Positive (whitelist) rather than negative (`!= complained`), matching
`RecheckEligibleTx`'s `status == subscribers.StatusActive` and `#0341`'s own
`AND status = 'pending'` — which that issue's plan defends in so many words as
*"strictly stronger than `<> 'complained'`"*. A whitelist blocks
`unsubscribed` and `bounced` too, and catches the invite-decline path
(`store.go:1208`, `pending` → `unsubscribed`) for free.

**Ungated kinds, each with a written reason** — the `kindExceptions` shape
(`#0296` item 4: an allowlist anyone can append to without an argument is a
guard with a hole):

```go
var ungatedKinds = map[outbox.Kind]string{
	outbox.KindRegistration:    "staff auth mail to a users row, not a subscribers row — Row.SubscriberID is always nil; gating it would let a marketing suppression lock an admin out of the console",
	outbox.KindRecovery:        "same as registration — a passkey recovery link must reach an admin regardless of any list state",
	outbox.KindSessionsRevoked: "same as registration — a security notice, not list mail",
	outbox.KindAdminAlert:      "operational alert to staff, not to a subscriber",
	outbox.KindGoodbye:         "no producer yet, and a status whitelist would be WRONG for it when one lands: goodbye is sent precisely BECAUSE the address stopped being active. Whoever adds the producer must decide its own predicate rather than inherit one of the four above",
}
```

The `goodbye` entry is load-bearing, not filler: it stops a future
implementer from inheriting `active` by pattern-matching.

**Auth-mail exclusion is a correctness requirement, not a scoping
convenience.** Gating `recovery` on a `suppressions` row would mean an admin
whose address once hard-bounced can never recover their own console — an
availability failure introduced by a safety feature.

### 3. The stale-row policy: `skipped`

**Recommendation: a new terminal status `skipped`, with the reason in
`error`.** The issue offers drop / abandon / log-and-skip; this is
log-and-skip with the terminal state named precisely, and the "log" resolved
to a `slog.Warn` rather than an activity-log row (§3.4).

#### 3.1 Why not `drop`

Rejected as the issue states — it destroys the audit trail. There is no
countervailing security argument, because the only sensitive content
(`confirm_token` / `manage_token` in `payload`) is blanked to `'{}'::jsonb` by
the transition anyway, exactly as `MarkSent` and `CancelQueuedTx` already do.

#### 3.2 Why not `abandoned` — the conflation has two live consumers and one user-visible symptom

This is the decisive evidence, and it is measurable rather than aesthetic.
`abandoned` is not a neutral terminal state in this codebase; it is a
**delivery-health signal** with three readers:

1. `internal/handlers/admin_dashboard.go:357` —
   `AbandonedCountByKind(outbox.KindConfirmation)` becomes
   `abandoned_confirmations` on the admin overview, documented in
   `web/src/lib/types.ts:654` as *"how many pending signups never got a
   confirmation delivered"*. A confirmation correctly withheld from a
   complained address **did not fail to be delivered**; counting it there
   states something false about deliverability.
2. `admin_dashboard.go:370` — `outboundQueueAbandoned = counts.Abandoned > 0`
   raises a dashboard **warning** (`web/src/lib/dashboard.ts:140`,
   `outbound-queue-abandoned`). Abandoned rows are terminal and nothing ever
   clears them, so a single correctly-skipped confirmation would raise a
   permanent, never-clearing operational warning. Warning fatigue is how a
   *real* abandoned-confirmation problem then gets ignored.
3. `web/src/lib/pending.ts:64` — `queueStateBadgeClass` gives `abandoned` and
   only `abandoned` `badge-danger`, its doc comment saying it is *"the one
   state that actually explains a non-confirmation as a delivery failure"*.
   The admin pending screen would show a red **delivery failure** badge
   against a row the system deliberately and correctly withheld.

`CancelQueuedTx` is the honest counter-argument — it already routes a
deliberate non-send to `abandoned` with the reason in `error`, and its doc
comment argues that `error` is a sufficient disambiguator. Two things about
that. First, it is *nearly* invisible today only by luck: it cancels
`KindImportInvite` rows, and reader (1) is scoped to `KindConfirmation`, so
only reader (2) currently misfires on it. Second, it does misfire on reader
(2) — see the follow-up in §9.

Routing a confirmation-kind deliberate non-send to `abandoned` would light all
three. That is precisely the conflation the issue's second bullet names, and
it is not repairable by prose in the `error` column, because none of the three
readers reads `error`.

#### 3.3 Why `skipped` specifically

Because the project has already named this concept, in the sibling table, for
the sibling worker:

```go
// MarkSkippedTx transitions the given email_sends rows to status='skipped'
// with error=reason, inside the caller's own transaction q.
```

`email_sends.status` gained `'skipped'` for rows `RecheckEligibleTx` found
ineligible at send time. `outbound_queue` is the same shape (`000021`'s own
header: *"the same shape `email_sends` already uses"*) and this is the same
event. Using a different word for the same thing in the two halves of one
subsystem is itself the conflation; using the same word is the fix.

`'failed'` is available in the existing CHECK and deliberately **not** used:
`000021` reserves it *"for a future use rather than invented one here"*, and
"failed" describes a non-delivery even more strongly than "abandoned" does.

#### 3.4 No `subscriber_events` row, no new `Action`, no admin alert

`subscriber_events` is not the right log for this, and PRD §6.11 says why:
it *"is the answer to 'what has happened to this address?'"*. **Nothing new
happened to the address.** The facts that caused the skip are already in that
log, timestamped before it: `complained` (written by `applyComplaint` from the
SNS handler) and `suppressed` (written when the suppression row was added). A
third row saying "and therefore we did not send a confirmation" is a
consequence of the queue's state, which `outbound_queue` already records with
its own timestamps and its `error` text.

The cost of doing it anyway is not small. `internal/subscribers/events.go`'s
`knownActions` is documented as *"The closed set, **verbatim from PRD
§6.11**"*, so a new action means editing PRD §6.11's table — the authority it
is copied from — plus `knownActions`, plus
`TestSubscriberEventActions_EveryConstantHasCallSiteOrOwner`. Paying that to
duplicate evidence the log already holds is the wrong trade.

**No admin alert.** A skip is the system working correctly. Alerting on
correct behaviour produces exactly the warning fatigue §3.2 rejects
`abandoned` for.

**The "log" half is a `slog.Warn`** in `sendOne`, carrying `id`, `kind` and
`reason` — and **not the recipient address**: `#0277`'s lesson (§8b) is that
transcripts and logs get pasted into issue files, and the address is the one
piece of PII here that adds nothing to the diagnosis.

### 4. Suppressions vs `subscribers.status` — both, and a third

**Both, checked in one round trip, plus `RecheckEligibleTx`'s third
predicate.** They answer different questions and the project's own schema says
so.

- `subscribers.status` answers *"what is this person's relationship to the
  list?"*. It is per-subscriber, moves both directions, and is the state
  `#0341`'s claim predicate and `#0263`'s `FOR UPDATE` check already speak in.
- `suppressions` answers *"may we mail this address at all?"*. Migration
  `000012`'s header is explicit: *"a global send-block list, independent of any
  subscribers row. **Checked before every send, regardless of subscriber
  status**, and survives both unsubscribe/resubscribe cycles and hard deletion
  of the subscriber row … keyed by normalized email address, not subscriber
  id."* A status check therefore cannot subsume it: a `manual` or
  `repeated_soft_bounce` suppression can exist against a subscriber whose
  status is untouched, and `#0100` widened the key to `(email, reason)` so
  several independent reasons coexist. The check stays **reason-blind**, per
  `IsSuppressed`'s own doc comment.
- **The third predicate: the live `subscribers.email` must still equal
  `row.Recipient`.** Copied from `RecheckEligibleTx`, and for its stated
  reason — it *"has no way to fire today (there is no email-change flow) but
  makes explicit the invariant 'we mail the address we checked'"*. Without it
  the suppression is evaluated against `subscribers.email` while the message
  goes to `outbound_queue.recipient`, which is a check of one address gating a
  send to another.

**The two suppression layers, and which one this is.** `CLAUDE.md` §10 item 7
and PRD §6.7 describe two: our `suppressions` table, and SES's account-level
suppression list (already enabled — `SuppressedReasons: ["BOUNCE",
"COMPLAINT"]`). PRD §6.7: *"our list is authoritative for our sending
decisions, SES's protects the account reputation if ours ever has a bug."*
**This re-check is the first layer** — our own decision, made before the API
call, in our own vocabulary, and it is the one that must be right. SES's layer
would also drop a message to a complained address, but only *after* we have
told SES to send it: it protects the account, not the recipient, produces no
row in our queue, no reason we can show an operator, and does not exist at all
under the mock. It is a backstop for our bugs and is never a reason to skip
building this check.

### 5. Where the check runs, and why that is not a TOCTOU worth a transaction

**In `sendOne`, as the very first statement, before `render`.** Three
consequences, all intended:

- **The `#0045`/`#0264` physical-address gates are untouched.** They live
  inside `render` and are not modified, not moved, and not made conditional.
  An ineligible row simply returns before reaching them. Nothing about this
  change is reachable from the UI (§9 restricted area preserved).
- **It reaches the indefinitely-deferred rows.** A welcome parked by
  `deferMissingPhysicalAddress` returns to `queued`, is reclaimed on a later
  pass, hits the gate first, and is skipped — which is how the fix actually
  covers §2's widest window.
- Nothing is rendered for a message that will not be sent.

**No new transaction, deliberately.** `RecheckEligibleTx`'s doc comment
requires the recheck to sit inside the transaction holding the claim; here the
worker already holds the row in `'sending'`, and `ClaimRow` requires
`'queued'` while `MarkSent`/`MarkRetryOrAbandon`/`MarkSkipped` all require
`'sending'` — so no other actor can move this row while the gate runs. The
residual window (a complaint committing between the gate's `SELECT` and
`mailer.Send` returning) is microseconds and is **unclosable in principle**,
because SES accepts asynchronously: a complaint can always land a moment after
`Send` returns. The window this issue closes is queue latency — seconds to,
per §2, indefinitely. Say this in the doc comment; it pre-empts a reviewer
asking for a transaction that buys nothing.

**Carrying the predicate inside `ClaimRow`'s `WHERE` is wrong** and should not
be attempted: `claimed=false` already means "lost the race, leave the row
alone", so an ineligible row would stay `queued` and be re-selected every pass
forever.

**Requeueing instead of terminating is wrong** for the same reason
`deferMissingPhysicalAddress` is right for its case: a missing physical
address is a condition an admin will clear as a matter of course, whereas
`complained` *never* auto-resubscribes (§9) and a suppression is cleared only
by an admin acting deliberately. A row that will never become eligible must
not occupy the queue forever.

### 6. Error handling — fail-open and fail-closed, split deliberately

| Condition | Behaviour | Why |
|---|---|---|
| Gate says ineligible | `MarkSkipped` + `Warn` | the fix |
| Eligibility read returns an error | `finishFailed(row, err)` — ordinary retry/backoff | a transient DB error is exactly when we do not know; retrying is safe and the backoff schedule already exists. **Must not fail open** |
| `row.SubscriberID == nil` on a gated kind | `Warn`, then **send** (fail-open) | impossible by construction (all four enqueue sites set it) and it is the convention of every other nil-tolerant seam in this file. Fail-closed would risk silently killing real mail over a defensive branch |
| Subscriber row not found (`pgx.ErrNoRows`) | **skip**, reason `"subscriber row no longer exists"` (fail-closed) | different from the case above: we positively learned there is no subscriber. Unreachable in practice — `outbound_queue.subscriber_id` is `ON DELETE CASCADE` — so reaching it means an inconsistent database, and mailing on that basis is not defensible |
| `w.events == nil` | `Warn`, then send (fail-open) | `OutboxWorkerDeps.Events` is documented nil-tolerant; production always wires it (`cmd/opencircuit/main.go:688`) |

**Do not add a `CHECK (kind NOT IN (…) OR subscriber_id IS NOT NULL)`** to
close the nil case at the schema. It would turn a hypothetical code bug into a
constraint violation inside a signup transaction, i.e. a failed signup — worse
than the thing it guards.

### The nil-`SubscriberID` fail-open — judged explicitly

**It is right, and it is pinned.** Three findings:

1. **Unreachable in production.** All seven non-test producers of the four

2. **Fail-closed would be worse.** The failure mode of fail-open is one

   worse than the status quo it replaces, and logged at `Warn`. The failure

3. **The direction is pinned by accident, in the right direction.**
   Flipping the branch to fail-closed breaks four pre-existing tests loudly

   cannot flip it quietly. This also independently confirms the
   implementer's report that those tests reach the fail-open branch.

The honest statement for the record: **this is the one path where the gate
does nothing**, and it is defensible only because the gated kinds' producers
make it unreachable. If a future producer of a gated kind ever omits
`SubscriberID`, that mail bypasses the gate entirely with only a `Warn` to
show for it.
