## Description

`middleware.clientIP` and `handlers.clientIP` both take the **first** entry in `X-Forwarded-For` unconditionally. `deploy/apache/opencircuitsf.com.conf` uses `mod_proxy_http`, which **appends** the real peer to any client-supplied header rather than replacing it. So the first entry is whatever the client sent.

Found during `#0026`'s review, which reproduced it by simulating exactly what Apache forwards.

> 🟢 Resolved 2026-08-19 — Client IP now comes from the one hop Apache appends: `X-Forwarded-For` is honored only when the immediate peer is loopback, and only its rightmost entry, unified in `middleware.ClientIP` with `handlers.clientIP` delegating to it. The reviewer confirmed the loopback trust anchor in **code**, not in documentation: `cmd/opencircuit/main.go` hardcodes `addr := fmt.Sprintf("127.0.0.1:%d", cfg.Port)` and is the only `ListenAndServe` in the tree, with no bind-host config, flag, or default that could put the listener on `0.0.0.0` — so no non-local client can ever present a loopback peer, and `./scripts/dev.sh` (plain `go run … serve`, Vite proxying from loopback without adding `X-Forwarded-For`) inherits the same bind. The append-not-replace assumption the whole fix rests on was verified empirically rather than assumed: a real `httpd` with `mod_proxy_http` in front of an echo backend appended the peer as the **rightmost** entry in every case and **merged duplicate `X-Forwarded-For` request lines into a single header**, so Go's first-value-then-rightmost parse cannot be defeated by sending the header twice. Independently re-verified: the pre-fix bypass reproduces at 50/50 accepted and the fix throttles at 3 accepted / 47 throttled (limit 5/min, burst 3); the leftmost-trust mutation failed 12 tests across `internal/middleware`, `internal/handlers` and was restored clean; `signup_ip` written through the real `POST /api/subscribe` against a live database stores the Apache-appended peer (`198.51.100.9`) with an attacker-claimed leftmost entry present, and the real `RemoteAddr` when no trusted proxy is in front; and the **auth** limiter was proven at the route level, not by shared-function inference — 50 requests with a rotating leftmost `X-Forwarded-For` through `mountAndServe`'s real `GET /auth/login/start` over a real TCP listener gave accepted=10/throttled=40 post-fix versus accepted=50/throttled=0 under the mutation. `go build`, `go vet`, and `go test ./... -count=1` with `TEST_DATABASE_URL` are green with zero skips, and `cmd/opencircuit/main.go` is untouched. One residual, now reachable only from a process already on the box (pre-fix it was reachable from the internet): the trusted rightmost entry is not validated as an IP, so a loopback client sending `X-Forwarded-For: 1.1.1.1, not-an-ip` makes the `INET` insert fail and the signup is dropped behind the uniform 202 — `net.ParseIP`-guarding the trusted entry and falling back to the peer would close it.

## Actual behavior

```
XFF-rotating attacker (one real source IP, 50 requests): 50/50 accepted 202   (limit 5/min, burst 3)
signup_ip stored for xff-7@example.com: "172.16.0.7/32"  (attacker-supplied; real peer 198.51.100.9)
```

Two consequences, both live:

1. **Every per-IP rate limit is bypassable** by rotating a header. That is `#0026`'s criterion 2, but it is not confined to `#0026` — the same helper backs the **auth** limiters on login, registration and recovery, which shipped in Phase 1.
2. **`signup_ip` is forgeable.** PRD §6.3 stores it as consent evidence, and `#0075`'s published privacy policy tells subscribers it is recorded. Evidence an attacker chooses is not evidence.

## Notes

Trusting `X-Forwarded-For` from the left is the standard form of this bug and it is silent — every limiter looks like it works, because it does work for honest clients.

Do not fix this by trusting a fixed number of hops without checking the deployed config; `#0064` owns the runbook and the vhost is in-repo, so the answer is knowable rather than guessable.

`#0038` should know that historical `signup_ip` values recorded before this fix may be attacker-chosen.

## Root cause

`middleware.clientIP` (`internal/middleware/ratelimit.go`) and
`handlers.clientIP` (`internal/handlers/request.go`) were two independently
maintained copies of the same parse, and both took the **first**
comma-separated entry of `X-Forwarded-For` unconditionally, with no check on
who sent the request. `deploy/apache/opencircuitsf.com.conf` proxies with a
single `ProxyPass / http://127.0.0.1:8080/` under `mod_proxy_http`, which
**appends** the peer it sees to any existing `X-Forwarded-For` rather than
replacing it — so the leftmost entry of an inbound header is always whatever
the client put there, and the rightmost is the one Apache itself added.
Trusting the leftmost entry meant a client could set its own bucketing
identity for every per-IP rate limiter (`middleware.RateLimiter`, which powers
the Phase 1 auth limiters on login/registration/recovery and the Phase 3
subscribe limiter) and its own `signup_ip` (PRD §6.3 consent evidence,
published to subscribers by `#0075`'s privacy policy) by rotating a header
value — no proxy compromise required.

## Fix

Replaced both copies with a single `middleware.ClientIP` in the new
`internal/middleware/clientip.go`, and made `handlers.clientIP` a one-line
delegate to it (`internal/handlers/request.go`). `middleware.RateLimiter.Middleware`
now calls `ClientIP` directly; the old duplicate parse in `ratelimit.go` was
deleted.

`ClientIP`'s trust model, derived from what's actually deployed
(`deploy/apache/opencircuitsf.com.conf`'s single `ProxyPass`, and
`deploy/systemd/opencircuit.service`'s comment that opencircuit "listens on
127.0.0.1:8080 behind the Apache reverse proxy" — i.e. binds loopback only):

1. `X-Forwarded-For` is honored **only when the immediate peer
   (`r.RemoteAddr`) is loopback** (`127.0.0.1` / `::1`) — the address Apache
   (or a local dev/test client) always connects from. Any other peer reached
   the process directly, with no proxy in front, so its `X-Forwarded-For` (if
   any) is unauthenticated client input and is ignored outright, falling back
   to `RemoteAddr`. This is what makes the "no proxy at all" case (dev mode,
   a direct connection, or a hypothetical misrouted/direct external
   connection in production) safe: a spoofed header from a non-loopback peer
   can never override the real peer.
2. When the peer **is** loopback, exactly **one** hop is trusted — the
   **rightmost** `X-Forwarded-For` entry, since that's the one entry
   `mod_proxy_http` itself appended. Everything left of it is client-supplied.

No new config surface was added (no `TRUSTED_PROXY_COUNT` env var): the vhost
is in-repo and unambiguous — one Apache hop, no CDN, no second proxy — so the
hop count is a fact about the current deployment, hardcoded and documented in
`ClientIP`'s doc comment with an explicit note that it must be revisited if a
CDN or additional proxy layer is ever added in front of Apache. This also
avoided touching `cmd/opencircuit/main.go`, which another concurrent subagent
(`#0024`) owned this pass — a config-based trusted-proxy count would have
needed wiring there. **`main.go` was not touched and was not needed** for this
fix.

**Mutation-proof:** temporarily reverted `ClientIP` to take the leftmost
`X-Forwarded-For` entry unconditionally (no peer-trust check at all) and
reran the full `internal/middleware` and `internal/handlers` suites. Eight
tests failed exactly as expected, including `TestRateLimiterXFFRotationBypassFixed`
(back to 50/50 accepted), `TestClientIP_TrustedProxyMultiEntryUsesRightmost`,
`TestClientIP_UntrustedPeerIgnoresXFF`, `TestClientIP_DelegatesToMiddleware`
(both `handlers` subtests), and both `TestSubscribe_SignupIP*` DB-backed
tests. Restored the fix and reran clean.

**Auth limiters confirmed fixed by the same change:** `RateLimiter.Middleware`
calls the same `ClientIP` used by `handlers.clientIP` (login/registration/
recovery's audit IP attribution) — there is only one implementation left to
drift. The existing `cmd/opencircuit` integration test
`TestMountAndServe_RateLimitsAuthLoginStart` (real TCP connection to
`mountAndServe`, so `RemoteAddr` is genuinely loopback) still passes
unmodified post-fix, proving `GET /auth/login/start`'s `loginLimiter` still
buckets and throttles correctly end-to-end. `TestRateLimiterXFFRotationBypassFixed`
and `TestClientIP_TrustedProxyMultiEntryUsesRightmost` prove the rotation
bypass itself — which affected `loginLimiter`/`registerLimiter`/`recoverLimiter`
identically, since they're all the same `RateLimiter` type — is closed.

**Spoofed `signup_ip` cannot be forged:**
`TestSubscribe_SignupIPUsesRightmostTrustedProxyEntry` drives the real
`POST /api/subscribe` handler over a live test database with an
attacker-claimed leftmost `X-Forwarded-For` entry and the real peer appended
rightmost (loopback `RemoteAddr`, simulating Apache) — the stored `signup_ip`
is the rightmost/real entry. `TestSubscribe_SignupIPCannotBeSpoofedWithoutTrustedProxy`
drives the same handler with a non-loopback `RemoteAddr` (no trusted proxy in
front) and a spoofed header — the stored `signup_ip` is the real `RemoteAddr`,
never the spoofed value.

**No-proxy case tested explicitly:** `TestClientIP_NoProxyNoHeader`,
`TestClientIP_UntrustedPeerIgnoresXFF`, `TestClientIP_UntrustedPeerMultiEntrySpoofIgnored`,
`TestRateLimiterIgnoresXFFWithoutTrustedProxy`, and
`TestSubscribe_SignupIPCannotBeSpoofedWithoutTrustedProxy` all cover a
non-loopback `RemoteAddr` (i.e., no Apache in front) — with and without a
spoofed `X-Forwarded-For` present.

## Gotchas

- **The old tests' "same XFF, different RemoteAddr" pattern silently relied on
  `httptest.NewRequest`'s default `RemoteAddr` (`192.0.2.1:1234`) being
  non-loopback and constant across calls.** Under the new peer-trust check,
  any test that wants `X-Forwarded-For` honored must now pass an explicit
  loopback `RemoteAddr` (e.g. `"127.0.0.1:1111"`); tests that don't care about
  XFF at all (generic burst/isolation/replenish behavior) were switched to
  bucket via an explicit non-loopback `RemoteAddr` instead, to stop relying on
  the httptest default's specific value.
- **`#0038` should know that historical `signup_ip` values recorded before
  this fix may be attacker-chosen** (carried over verbatim from this issue's
  original notes — this fix does not retroactively correct existing rows).
- Did not add a `TRUSTED_PROXY_COUNT`-style config knob. The vhost is
  unambiguous today (exactly one Apache hop, no CDN), so a hardcoded,
  documented single-hop trust model is the honest answer per the issue's own
  guidance ("the answer is knowable rather than guessable"). If a CDN or
  additional proxy is ever put in front of Apache, `ClientIP`'s trust model
  (`internal/middleware/clientip.go`) needs to change to match — flagged
  explicitly in its doc comment — and that would be a natural point to add
  real config surface (with the same footgun-guard `#0027`'s `MAILER_NOOP`
  needed), which would require `cmd/opencircuit/main.go` wiring not attempted
  here.
