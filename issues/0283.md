## Description

`MarkSent` updates `WHERE id = $1 AND status = 'sending'`. If something released
the claim while the send was in flight, it affects zero rows: the message has
**already gone to SES**, but the row stays `'queued'` and a later pass claims and
sends it again.

`#0254` added a `Warn` when that happens, which is right and is what would have
exposed its own bug rather than letting a healthy-looking pass hide it. But the
reviewer was explicit that the warning **narrates the duplicate rather than
preventing it**.

The proven cause of a stolen claim is now structurally impossible — `#0254`
scoped both sweeps by kind, and the reviewer verified neither consumer can touch
the other's rows in either direction. So this is no longer reachable by the route
that motivated it. It stays open because the state machine still has the shape
where a lost claim means a duplicate send, and duplicate confirmation links and
recovery magic links are the thing this subsystem exists to prevent.

## The stronger fix, and why it is its own issue

Record the send unconditionally:

```sql
UPDATE outbound_queue SET status='sent', … WHERE id = $1 AND status <> 'sent'
```

so that whoever holds the claim, the fact that SES accepted the message is
written down. That changes the queue's state machine — a row can then move to
`'sent'` from a state the current model says it cannot — and it interacts with
the retry and abandonment paths. It was deliberately kept out of `#0254`'s scope
rather than folded into a bounce fix.

## Decision

**Widen the guard, but not all the way to fully unconditional.**
`MarkSent`'s `WHERE` clause now reads `status IN ('sending', 'queued')`
instead of `status = 'sending'` — recording the send whenever the row is
still in one of the two states a legitimate in-flight claim can leave it in,
and stopping short of the issue's example (`status <> 'sent'`), which would
also silently resurrect a row already `'abandoned'`.

Reasoning, in full, is written into `MarkSent`'s doc comment in
`internal/outbox/store.go` (not only here, per criterion 1) — summarized:

**Correction (post-review):** the paragraph originally here said "the call
site" (singular) and described only `OutboxWorker.sendOne`'s SES call. That
was false, and stated as verified fact — there are **two** call sites of
`Store.MarkSent`, and the second, `SubscribeHandler.processIntakeRow`
(`internal/handlers/subscribe_intake.go:250`), marks `KindSubscribeIntake`
rows, which are **not email and involve no SES call at all** (see that
Kind's own doc comment in `internal/outbox/store.go`). This decision widens
the predicate for both callers, since `MarkSent` cannot distinguish which
caller invoked it — so both are in scope below, not just the mail path.

- Both call sites always call `MarkSent` synchronously, immediately after an
  operation that genuinely completed for that row — a successful SES send
  for the mail kinds, or a finished `dispatchMutation` call for
  `KindSubscribeIntake` — so every invocation follows a real, completed
  operation, never a stale or speculative one. The only open question is
  what status the row is allowed to be in when it runs.
- `'sending'` — the expected case, unchanged.
- `'queued'` — newly admitted. This is the exact race #0283 describes: the
  claim was released or stolen back to `'queued'` while the operation that
  just completed was still in flight (`Release`, or a same-kind
  `OrphanSweep` racing a still-live claim — the residual, intra-kind version
  of `#0254`'s now-fixed cross-kind race). For the mail kinds, SES already
  has the message; recording `sent` here is what stops a second pass from
  claiming and sending it again. For `KindSubscribeIntake`, `dispatchMutation`
  already ran to completion; recording `sent` here stops a second pass from
  reprocessing the same row. That reprocessing would in fact be **safe** to
  repeat, not merely wasteful — verified directly against the code, not
  assumed: `processIntakeRow` re-reads `IsSuppressed`/`FindByEmail` fresh
  rather than trusting anything captured earlier, and `dispatchMutation` is
  idempotent by construction (`newSignup`'s `ErrEmailExists` handling makes
  a raced `Create` a safe no-op; `ClaimAndEnqueueConfirmation`/
  `ClaimAndEnqueueAlreadySubscribed` are atomic, cooldown-gated claims where
  a second send attempt is already a required no-op for ordinary concurrent
  requests). Admitting `'queued'` still avoids the redundant work of
  re-running a dispatch whose outcome is already durable.
- `'sent'` — excluded. A second `MarkSent` call for the same id must stay a
  no-op (the existing `TestOutbox_MarkSent_ScrubsPayload` idempotency
  assertion), not re-stamp `sent_at`/`ses_message_id`. For
  `KindSubscribeIntake`, `'sent'` here means "the signup attempt was durably
  processed", not "delivered by SES" — but the exclusion is identical
  either way: a second call for an already-processed row must stay a no-op
  regardless of what `'sent'` means for that kind.
- `'abandoned'` — excluded, deliberately. A row here already reached
  `MarkRetryOrAbandon`'s terminal state, keeping its error/payload as the
  diagnostic. Silently flipping that to `'sent'` would erase a decision an
  operator can currently see. Criterion 2 is explicit that resurrecting an
  abandoned row must be a deliberate, tested choice, not a side effect of a
  broader predicate — and `#0254`'s reviewer already established that the
  proven cause of the stolen-claim race (cross-kind sweep) is now
  structurally impossible, so admitting `'abandoned'` would be buying
  defence against a scenario nobody can currently produce, at the cost of a
  real, visible information loss. Left excluded; revisit only alongside a
  concrete scenario that reaches it.
- `'failed'` — reserved, unused by any writer in this codebase; excluded for
  the same reason as `'abandoned'`.
- The `Warn` `#0254` added when `MarkSent` affects zero rows is unchanged
  (criterion 5) — it still fires for the cases the new predicate excludes
  (`'sent'`, `'abandoned'`), and remains the signal that something took a
  claim even though the widened predicate now handles the one case
  (`'queued'`) that used to produce a silent duplicate send.

`MarkRetryOrAbandon`'s own `WHERE status = 'sending'` clause is unchanged
(criterion 3) — its doc comment now records why the two methods cannot
productively race each other: a given claim's lifecycle calls at most one of
`MarkSent` or `MarkRetryOrAbandon`, and in the only cross-claim interaction
(a stolen-claim race), whichever of the two commits first correctly
determines what the other can still do to the row.

**I attacked the newly-admitted `queued` state and found no defect.** Taking
the scenario directly: a send fails, `MarkRetryOrAbandon` re-queues the row for
a legitimate retry, and a stale in-flight sender from an earlier claim then
calls `MarkSent` on it. That sender's own SES call **succeeded** — the message
reached the recipient — so recording `'sent'` is correct and the retry it
suppresses would have been the duplicate this subsystem exists to prevent. The
same holds in reverse: if the stale sender had failed, it would call
`MarkRetryOrAbandon`, not `MarkSent`. A given claim's lifecycle calls at most
one of the two, and `MarkRetryOrAbandon`'s doc-comment argument to that effect
is sound — I checked it against the code rather than accepting it. Its `'queued'`
branch and its `'abandoned'` branch are both covered by that comment, and both
statements are true.

**The `'abandoned'` exclusion is the right call and I endorse it.** Its one cost
is real and worth stating: a row that was in fact delivered can end up reading
`'abandoned'` (slow successful send + a second actor exhausting retries at the
same instant). But that requires `attempts >= maxRetries` to land in exactly
that window, it preserves an operator-visible terminal decision rather than
silently erasing it, and the `#0254` `Warn` still fires. Resurrecting it would
buy defence against a scenario nobody can currently produce at the cost of real
information loss. Correct as decided.

**`MarkDone` and `MarkSent` both moving `queued → sent` is fine.** They have
disjoint callers (the fast path in `subscribe.go` vs. the recovery poller), each
records an operation that genuinely completed, and whichever lands first
excludes the other through the `'sent'` exclusion. No stall, no double-stamp, no
interaction with `#0254`'s recovery poller that leaves a row unreachable.

`claimed_at` is not cleared by `MarkSent`, but a `'queued'` row always has it
`NULL` already (every writer that produces `'queued'` — `Release`,
`MarkRetryOrAbandon`, `OrphanSweep` — nulls it), so the widening introduces no
new stale-`claimed_at` case. `next_attempt_at` is likewise left in the future on
a row that goes `queued → sent`; harmless, since `ClaimDue` filters on
`status = 'queued'`.

### What must change

**`MarkSent`'s doc comment states a false premise, and the whole enumeration
rests on it.** It opens:

> The call site (OutboxWorker.sendOne) always calls MarkSent synchronously,
> immediately after a real SES call that just succeeded for THIS row — so every
> invocation follows a genuine send, never a stale or speculative one.

There are **two** call sites of `outbox.Store.MarkSent`, not one:

- `internal/mailing/outbox_worker.go:486` — `OutboxWorker.sendOne`, the one the
  comment describes.
- `internal/handlers/subscribe_intake.go:250` —
  `SubscribeHandler.processIntakeRow`, the `#0254` recovery poller. It calls
  `MarkSent` for `outbox.KindSubscribeIntake`, **which is not email and involves
  no SES call at all**. `KindSubscribeIntake`'s own doc comment, twelve lines up
  the same file being edited, says so explicitly: "exactly reusing
  ClaimDue/OrphanSweep/MarkSent and nothing else", and "'sent' for a row of this
  kind means 'the signup attempt was durably processed', not that any mail went
  out."

This matters for three reasons, in ascending order:

1. It is simply wrong on a fact discoverable in the file under edit, and it is
   asserted as verified ("always", "every invocation"). `CLAUDE.md` is explicit
   that a comment asserting an unverified invariant is `#0263`'s and `#0095`'s
   defect class.
2. Criterion 2 asks what admitting each source state **means**. For the intake
   caller `'sent'` means something different — "durably processed" — so
   admitting `'queued'` there has a second, unstated meaning the enumeration
   never gives. (I checked it: it is also safe, because `processIntakeRow`
   re-reads everything fresh and `dispatchMutation` is idempotent by
   construction — but that is the argument the comment needed to make and did
   not.)
3. The premise is the *safety* argument for admitting `'queued'`. A future
   author who adds a third `MarkSent` caller that does **not** follow a
   completed operation would read this comment as licence.

Nothing outside `internal/outbox` mentions that this change alters the intake
path's semantics too — not the comment, not the commit message, not this issue's
`## Decision`.

- In the `'queued'` bullet, say what admitting it means for **both** kinds, and
