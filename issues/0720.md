Guides in this issue (slugs may be adjusted):

- `pi-undervoltage` — the lightning-bolt icon and why a Pi quietly slows down. Covers: the official supplies (Pi 4: 5.1 V 3 A USB-C; Zero 2W: 5 V 2.5 A micro-USB); thin or long cables drop voltage under load; the firmware flags under-voltage below about 4.63 V and throttles; phone chargers and laptop ports often can't keep up; symptoms (random reboots, SD card errors, WiFi drops, the bolt icon, `Under-voltage detected!` in `dmesg`); `vcgencmd get_throttled` and what its bits mean (bit 0 under-voltage now, 1 ARM frequency capped now, 2 throttled now, 3 soft temperature limit now; bits 16–19 the same conditions "has occurred since boot"). Demo: two parts. (a) Pick a power supply and a cable and a load (idle, WiFi, a USB drive) and watch the voltage at the Pi sag, crossing the warning line. (b) A decoder: type or pick a `get_throttled` value such as `0x50005` and see which flags are set, in plain words.
- `pi-sd-card-corruption` — why pulling the plug corrupts SD cards, and how to stop it. Covers: a write in progress when power is cut leaves the filesystem inconsistent; shut down first (`sudo poweroff`, wait for the green LED to stop); buy name-brand A1 or A2 cards and beware fakes; undervoltage (link `pi-undervoltage`) causes the same damage; for an appliance that gets unplugged (a speaker, a display), turn on the read-only overlay filesystem (`raspi-config` → Performance Options → Overlay File System) so nothing is written to the card; keep a backup image. Demo: a timeline of a file write (data blocks, then the directory entry, then the journal commit); cut power at any point on the slider and see what state the card is left in, with and without the overlay filesystem.

**`get_throttled` decoder:**

```ts
export type FlagKey = 'underVoltage' | 'freqCapped' | 'throttled' | 'softTemp';
export interface ThrottleFlag { bit: number; key: FlagKey; now: boolean; label: string; short: string }
export const THROTTLE_FLAGS: ThrottleFlag[]   // exactly these eight:
//  0 underVoltage now  'Under-voltage right now'                         short 'UV'
//  1 freqCapped   now  'CPU speed capped right now'                      short 'CAP'
//  2 throttled    now  'Throttled right now'                             short 'THR'
//  3 softTemp     now  'Soft temperature limit right now'                short 'TMP'
// 16 underVoltage past 'Under-voltage has happened since boot'           short 'UV'
// 17 freqCapped   past 'CPU speed capping has happened since boot'       short 'CAP'
// 18 throttled    past 'Throttling has happened since boot'              short 'THR'
// 19 softTemp     past 'Soft temperature limit has happened since boot'  short 'TMP'
export type ParsedThrottled = { ok: true; value: number } | { ok: false; error: string };
export function parseThrottled(input: string): ParsedThrottled
export interface Decoded { value: number; flags: ThrottleFlag[]; unknownBits: number[]; title: string; body: string; tone: 'good' | 'meh' | 'bad' }
export function decodeThrottled(value: number): Decoded
export function hex(value: number): string   // '0x' + lower-case hex, no padding: 0x50005
```

- `parseThrottled`: trim; strip an optional leading `throttled=` (case-insensitive); strip optional `0x`/`0X`; then require `/^[0-9a-f]+$/i`, read as **hex** (vcgencmd always prints hex, so bare `50005` is hex too). Errors, exactly: empty → `'Type a value, like 0x50005.'`; not hex → `'That isn’t a hex number. vcgencmd prints something like throttled=0x50005.'`; more than 8 hex digits → `'Too many digits: get_throttled is at most 8 hex digits.'` Use `parseInt(h, 16)` and test bits with `(value >>> bit) & 1` (never `<<` on bit 31).
- `decodeThrottled`: `flags` = the set documented bits in bit order; `unknownBits` = any other set bit 0–31, ascending. Title/body/tone, first match wins:
  1. bit 0 → `'Power problem now'`, bad: "The supply or cable can’t hold the voltage up right now. Use the official supply, or a short, thick cable, and unplug power-hungry USB devices."
  2. bit 16 → `'Power problem since boot'`, meh: "It’s fine this moment, but the voltage dropped at some point since boot, probably under load. The fix is the same: a better supply or cable."
  3. any of bits 1, 2, 3, 17, 18, 19 → `'Running hot'`, meh: "No power problem. The Pi slowed itself down because it got hot: add a heatsink or a case with some airflow."
  4. value 0 → `'All clear'`, good: "No under-voltage and no throttling since the Pi booted."
  5. otherwise (unknown bits only) → `'No documented flags'`, meh: "None of the eight documented flags is set." and the demo lists the unknown bits.

**SD card write timeline:**

```ts
export type StageId = 'before' | 'data' | 'journal' | 'commit' | 'inPlace' | 'flash' | 'done';
export interface Stage { id: StageId; from: number; to: number; label: string }
export const STAGES: Stage[] = [   // slider positions 0..100, inclusive, contiguous
  { id: 'before',  from: 0,  to: 9,   label: 'Nothing written yet' },
  { id: 'data',    from: 10, to: 34,  label: 'Writing the file’s data blocks' },
  { id: 'journal', from: 35, to: 54,  label: 'Writing the directory entry to the journal' },
  { id: 'commit',  from: 55, to: 59,  label: 'Journal commit' },
  { id: 'inPlace', from: 60, to: 79,  label: 'Copying the directory entry to its real place' },
  { id: 'flash',   from: 80, to: 94,  label: 'The card’s controller rewrites a whole flash block' },
  { id: 'done',    from: 95, to: 100, label: 'Done' },
];
export function stageAt(t: number): Stage          // clamp t to 0..100, round, return the containing stage
export type Fill = 'blank' | 'partial' | 'written';
export interface CardState { data: Fill; journal: Fill; directory: Fill; others: 'ok' | 'damaged'; inRam: boolean }
export interface CutResult { stage: Stage; card: CardState; file: 'old' | 'new'; title: string; body: string; tone: 'good' | 'meh' | 'bad' }
export function cutPower(t: number, overlay: boolean): CutResult
```

`cutPower` without the overlay (titles exact, bodies may be polished):

| Stage | data / journal / directory / others | file | tone | title | body gist |
|---|---|---|---|---|---|
| before | blank / blank / blank / ok | old | good | `Nothing written yet: card fine` | Nothing had reached the card. |
| data | partial / blank / blank / ok | old | meh | `Change lost, card fine` | New data is half on the card but nothing points to it yet; after boot you have the old file. |
| journal | written / partial / blank / ok | old | meh | `Change lost, card fine` | The journal entry has no commit record, so at boot it is thrown away. Old file. |
| commit | written / written / blank / ok | new | good | `Saved: the journal finishes it at boot` | Committed: at boot the journal replays and finishes the save. |
| inPlace | written / written / partial / ok | new | good | `Saved: the journal finishes it at boot` | Half-copied, but the committed journal replays at boot. |
| flash | written / written / written / damaged | new | bad | `Corrupted: other files damaged` | The card moves data in big flash blocks holding pieces of other files. Cut mid-rewrite and those files can come back damaged, even ones nobody was saving, maybe the ones the Pi needs to boot. The journal can’t fix what the filesystem never wrote. |
| done | written / written / written / ok | new | good | `Saved` | All written. Linux writes logs every few seconds, so there is always a next write: shut down first. |

With `overlay = true`, every `t`: all `blank`, others `ok`, `inRam: true`, file `old`, tone good, title `Card untouched: the save was in memory`, body "With the overlay file system on, the card is read-only. Saves go to memory and disappear at reboot, so the card is never in the middle of a write when the plug comes out."

### `TOPIC_BODIES` (plain text: no markup, no links; commands in prose are fine)

`pi-undervoltage` — demo `PiUndervoltageDemo`; tryIt: "Pick a board, a supply, a cable and what the Pi is doing, and watch the voltage at the Pi. Then decode a get_throttled value." Ideas:
1. **Symptoms that don’t look like power** — random reboots, SD card errors, WiFi dropping, USB drives disconnecting, everything slow. On the desktop a lightning bolt or a low-voltage warning appears; headless you see nothing, but the kernel log says "Undervoltage detected!".
2. **4.63 V is the line, and the cable eats into it** — official supplies give 5.1 V (Pi 4: 3 A USB-C; Zero 2W: 2.5 A micro-USB) so there is room to lose some. Below about 4.63 V at the board the firmware flags under-voltage and slows the processor. Both wires of a cable have resistance: a thin 2 m cable is close to 1 Ω there and back, so at 1 A it loses almost a volt. Phone chargers and laptop ports sag further as the Pi works harder. The numbers in the demo are a simplified model with typical values.
3. **Ask the Pi** — `vcgencmd get_throttled`: 0x0 is all clear; the low four bits are now (under-voltage, CPU speed capped, throttled, soft temperature limit), bits 16–19 the same four "since boot"; 0x50005 is the classic bad supply. `sudo dmesg | grep -i voltage` shows when.
Takeaway: "Use the official supply, or a 5.1 V supply with a short, thick cable. If get_throttled says anything but 0x0, fix the power first."

`pi-sd-card-corruption` — demo `SdWriteDemo`; tryIt: "Slide to the moment the plug comes out during a file save and see what the card is left with. Then turn on the overlay file system and try again." Ideas:
1. **Linux is always writing** — logs, settings and caches, even at idle. A save happens in steps; the filesystem’s journal covers a cut between steps, but the card’s own controller rewrites data in big flash blocks, and a cut in the middle of that can damage files nobody was saving. Under-voltage (see the under-voltage guide) does the same damage. Simplified model.
2. **Shut down, then unplug** — `sudo poweroff`, wait for the green LED to stop flashing, then pull the plug. Buy name-brand A1 or A2 cards from a real shop: fakes fail more and some claim more space than they have. Once it works, keep a backup image of the card.
3. **For a box that gets unplugged, make the card read-only** — a speaker or a display gets switched off at the wall. `sudo raspi-config` → Performance Options → Overlay File System: writes go to memory and vanish at reboot, so nothing is written to the card. To change settings, turn it off, reboot, make the change, turn it back on.
Takeaway: "Shut down before you unplug. If it will be unplugged anyway, turn on the overlay file system."

### Facts the implementer must list under `### Assumptions` (from the planner's memory, not checked against the docs today)

- Zero 2W official supply is **5.1 V** 2.5 A micro-USB (the issue says 5 V; the official Raspberry Pi 12.5 W micro-USB supply is 5.1 V). The 4.63 V threshold is "±5%" in the docs.
- The official supply's built-in cable is about 1.5 m of 18 AWG.
- Board currents (Pi 4 idle 0.6 A / busy 1.2 A; Zero 2W idle 0.15 A / busy 0.45 A; USB hard drive +0.5 A) and the supply resistances, ratings and overload sag are illustrative round numbers, not measurements.
- The kernel log line ("Undervoltage detected!" on current kernels, "Under-voltage detected! (0x00050005)" on older ones) and that `dmesg` needs `sudo` on Bookworm; hence `sudo dmesg | grep -i voltage`, which matches both.
- The Bookworm desktop shows a lightning bolt or a low-voltage notification.
- Capping or throttling without bit 0/16 set is treated as temperature.
- After `sudo poweroff` the green activity LED flashes and then stays off (the red power LED on a Pi 4 stays on).
- `raspi-config` → Performance Options → Overlay File System (it also offers to write-protect the boot partition).
- A1/A2 are SD "application performance" classes (random I/O); fake cards misreport capacity.
- The write timeline is a simplification of ext4 in ordered mode (data, then journal, commit, then the in-place copy); the issue's "data blocks, then the directory entry, then the journal commit" is kept in spirit. The flash-block rewrite (the card's wear levelling) is shown as one stage although it can happen at any write; this is the honest reason an SD card corrupts beyond what the journal can repair.
