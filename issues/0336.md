## Description

`#0324` fixed two arrival/departure asymmetries in `Growth30Days` and its
review re-derived the whole truth table — 18 scenarios run through the real
store methods — to prove it. Sixteen cells are now correct. **Two are not**,
and they are scenarios neither `#0324`'s tables nor `#0305`'s named:

| Row | Scenario | Before | After |
|---|---|---|---|
| **O** | invite accepted → unsubscribe → `RestartSignup` | 0 | **+1** |
| **P** | `prior_consent` import → unsubscribe → `RestartSignup` | 0 | **+1** |

Both are the *interaction* of `#0324`'s two halves, which is why neither half
looks wrong alone. `RestartSignup` now withdraws the departure (correctly — that
was `#0324` item 2), while the `imported_30d` arrival cannot be withdrawn. The
row is left counted as +1 while sitting in `pending`, and it stays there
persistently if the confirmation is simply abandoned.

Row **O** additionally contradicts both doc comments, which define the bucket as
"placed on the list with its own standing consent". An accepted invitation that
was later unsubscribed and restarted is *pending*, and holds no standing
consent.

### The remedy is verified

The review measured it: changing `imported_30d`'s predicate from

```
consent_basis IS NOT NULL
```

to

```
consent_basis = ConsentBasisImportedPriorConsent
```

changes **exactly one cell** — row O goes +1 → 0 — and leaves the other
seventeen byte-identical. Row P needs its own consideration; confirm whether the
same predicate covers it or whether the arrival must be withdrawn on
`RestartSignup`.

This was reported rather than bounced because it clears the same bar `#0324`
itself was filed under (from `#0311`'s review): one row per person, four
sequential actions, erring by +1.

### Added 2026-08-28 — the predicate change desymmetrises the mirror

`#0312`/`#0313`/`#0314`'s planning pass flagged a consequence this issue's
criteria do not name. `imported_30d`'s `consent_basis IS NOT NULL` and
`unsubscribed_30d`'s `NOT (source = 'import' AND consent_basis IS NULL)` are
currently **the same test on both sides of `net_30d`** — by construction and by
doc comment. Narrowing only the arrival side to
`= ConsentBasisImportedPriorConsent` breaks that symmetry.

So the fix cannot be applied to one side alone without deciding what the
departure side should now test. Criterion 1's truth table will catch the
resulting cells, but the implementer must make that decision deliberately
rather than discover it — and the doc comments asserting the mirror must be
corrected or the symmetry restored.

Additional criterion:

8. The arrival/departure mirror is either preserved or its removal is explicit:
   both predicates are stated, the doc comments claiming they are the same test
   are corrected, and the truth table covers the cells where they now differ.

### Criterion 8 — the asymmetry is correct, and it was measured, not argued

The claim that mirroring the departure guard onto `= imported_prior_consent`
would drop an accepted invitee's unsubscribe was checked by running both
predicates side by side over the same rows in one query. An accepted invitee
who unsubscribes moves the live guard's count by **+1** and the mirrored
guard's by **0**. The regression is real, so leaving `unsubscribed_30d` as
`NOT (source = 'import' AND consent_basis IS NULL)` is right.

The framing in the rewritten doc comments is the correct one and is what
`#0313` should be written against: **the arrival predicates ask which bucket a
row's standing consent belongs to; the departure predicate asks only whether
*any* arrival was ever counted.** Those are not complements once a third
`consent_basis` value exists, and forcing them to be would break the side that
must stay broad.

### Clearing `consent_basis` does not lose required provenance

Examined directly against PRD §6.10, which requires `/admin/subscribers/{id}`
to answer "why is this person on the list?".

- The historical record survives. `subscriber_events` carries `ActionImported`
  (with `ImportID` and `import_source`), `ActionInviteSent`,
  `ActionInviteAccepted`, `ActionConfirmed`, `ActionUnsubscribed`, and the
  restart's own `ActionSignupRequested{kind:"restarted"}`. The detail endpoint
  populates `events` (`internal/handlers/admin_subscribers.go`), so the batch —
  and through its `import_id`, `subscriber_imports.consent_note`,
  `collected_at`, `source_detail` — is still reachable from the exact page the
  PRD names.
- The column is *standing* consent, not history. After a restart the operative
  answer is the person's own fresh form submission, whose evidence
  (`signup_ip`, `signup_user_agent`, `utm_*`) the same `UPDATE` stamps.
- The change can only make a row claim **less** consent, never more. Carrying
  `imported_prior_consent` forward on a row whose owner has explicitly
  unsubscribed is the compliance error; withdrawing it is the correction.
- `#0129` already cleared `import_id` on restart on identical reasoning and was
  reviewed and accepted. Clearing `consent_basis` *without* it would have been
  worse: it would recreate the `import_id != nil && consent_basis == nil`
  shape that four call sites read as "an unaccepted invitation". Both are
  cleared in the same statement, so that inference stays false — re-checked at
  `Confirm`, `Unsubscribe`'s decline branch, `AdminResendConfirmation`, and
  `ExpirePendingSweep`. `ImportStore.Revoke` keys on `import_id`, so it is
  unaffected.

### Two things to file, neither blocking

1. **`admin_attested` is now a latent net `-1`.** `ConsentBasisAdminAttested`
   is declared in `store.go` and permitted by `000023`'s CHECK constraint, but
   nothing in the tree ever writes it. Post-`#0336`, `imported_30d` demands
   exactly `imported_prior_consent`, while `unsubscribed_30d` excludes only
   `IS NULL` — so the first issue that starts writing `admin_attested` on an
   import-sourced row gets an arrival counted in *neither* bucket and a
   departure counted in full: `#0311`'s bug reopened, silently. Neither the
   predicate nor the rewritten doc comments mention the value. Decide whether
   `imported_30d` should be an `IN` list, or record why `admin_attested` is out.
2. **The five-action website-signup cell still nets `-1`** (pre-existing,
   measured identical on both trees): `Create → Confirm → Unsubscribe →
   RestartSignup → Unsubscribe again while still pending` gives (0,0,1).
   `#0324` fixed the four-action version by clearing `unsubscribed_at`; the
   fifth action re-stamps it with no live arrival left in the window. `#0336`
   incidentally fixes the import-sourced counterparts (O3/P3 above), because
   the departure guard's `source = 'import' AND consent_basis IS NULL` now
   excludes them — but a website signup is `source = 'signup_form'`, so nothing
   excludes it. Same class as `#0324` item 2, one action deeper.

`#0313`, which inherits this predicate, should assert the three counts
separately rather than the net — O3 and P3 are the demonstration that net can
hide two compensating errors.
