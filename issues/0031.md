## Description

Token-authenticated page where a subscriber manages their interests or leaves entirely, reached from every email footer.

## Acceptance criteria

- [x] `GET /api/preferences?token=` returns the subscriber's interests and the full active interest list
- [x] Email is masked (`b•••••n@gmail.com`) unless the token was just issued by a
      confirm — implemented client-side, not as a server-trusted flag; see Gotchas
- [x] `PATCH /api/preferences` replaces the interest set
- [x] An empty selection keeps the subscriber `active` on general
      announcements only, and the UI says so explicitly — precisely: an empty
      PATCH never *changes* status at all (it stays whatever it already was),
      so an already-active subscriber (the normal case — a footer link only
      ever reaches active subscribers) stays active. It deliberately does
      NOT force a `pending`/`unsubscribed`/`complained` row to `active` — see
      Gotchas for why forcing that would reopen an auto-reactivation loophole.
- [x] A separate, clearly labelled "Unsubscribe from everything" action is present alongside
- [x] Invalid or rotated tokens render a neutral page offering to re-subscribe — never a raw 404
- [x] Changes are saved with visible confirmation and an audit row
- [x] Handler and component tests pass

## Notes

PRD §6.4. "Uncheck everything" is how a lot of people *try* to unsubscribe. Silently leaving them subscribed is a complaint waiting to happen, so the empty state must state plainly what it means and the real unsubscribe action must be equally prominent.

Granular management measurably reduces full unsubscribes — someone tired of homelab posts drops one interest instead of leaving the list.

The email mask exists because these URLs end up in browser history and shared screenshots.

## Root cause

New construction — no preference-center endpoint or view existed.
`GET /api/preferences` and `PATCH /api/preferences` did not exist; `/preferences`
was already a recognized SPA route (`#0014`) falling through to App.svelte's
generic placeholder.

## Fix

- `internal/handlers/preferences.go` (new) — `PreferencesHandler.Get`/`.Patch`.
  `Get` always masks (`maskEmail`: first + last local-part char kept, a
  fixed run of five bullets between them regardless of original length, so
  the mask itself never leaks local-part length). `Patch` accepts either
  `{token, interests:[slug,...]}` (replace, resolved via
  `interests.Store.GetBySlug` — *not* filtered to active, so a
  still-selected-but-since-deactivated interest survives an unrelated save
  instead of silently falling off, per that method's own doc comment which
  anticipated exactly this use) or `{token, unsubscribe:true}` (calls
  `subscribers.Store.Unsubscribe(source=preferences)`, ignoring any
  `interests` field in the same request) — see the package doc comment for
  why "Unsubscribe from everything" rides the existing PATCH route instead
  of a new one.
- `web/src/views/PreferenceCenter.svelte` (new) — two entry modes. Standalone
  (`initialToken` prop absent): reads `?token=` on mount, calls
  `GET /api/preferences`, masked email. Embedded (`initialToken` present,
  used by `#0030`'s `ConfirmSubscription`): skips the fetch, uses the
  props supplied directly — unmasked email, since the caller already proved
  fresh mailbox control via the confirm token. `showHeading` (default
  `true`) lets the embedded case suppress this component's own `<h1>` so the
  page keeps exactly one.
- `web/src/lib/subscribe.ts` — `buildSaveInterestsPatch`/
  `buildUnsubscribeEverythingPatch` (added in `#0029`'s commit, consumed
  here).
- `web/src/lib/api.ts` — `getPreferences`/`patchPreferences`; `types.ts` —
  `PreferencesResponse`.
- `cmd/opencircuit/main.go` — additive: constructs `PreferencesHandler` and
  registers `GET`/`PATCH /api/preferences` behind a new
  `middleware.NewRateLimiter(rate.Every(time.Minute/10), 5)`.
  `mountAndServe` gained `preferencesH` as its second new parameter (after
  `#0029`'s `publicInterestsH`, before `#0030`'s `confirmH`).
  `subscribe.go`/`subscribe_test.go` (owned by the concurrent `#0081` pass)
  were not touched.
- Dev-store gap: **documented, not filled** — `STORAGE=json` passes `nil`
  for `preferencesH`; `GET`/`PATCH /api/preferences` unavailable under
  `./scripts/dev.sh` until a devstore backing lands.
- Adds `audit.ActionSubscriberPreferencesUpdated` and
  `audit.ActionSubscriberUnsubscribed` — the latter is the constant this
  package's own comment had earmarked for `#0034`'s one-click endpoint,
  which should reuse it (distinguished by `metadata.source`) rather than
  mint a second name for the same event.

## Gotchas

- **The "unless fresh from confirm" unmask is a client-side hand-off, not a
  server-trusted signal.** `manage_token` never changes, so `GET
  /api/preferences` alone has no way to tell "just confirmed" apart from
  "three-month-old bookmark" — it always masks. The unmask happens entirely
  in the SPA: `ConfirmSubscription.svelte` already holds the plaintext email
  from its own `POST /api/subscribe/confirm` response (proof of fresh
  mailbox control) and passes it to `PreferenceCenter` as a prop for that
  one render; it is never sent back to or re-requested from the server.
  Deliberate — a client-asserted "fresh" flag the server trusted would be
  trivially forgeable and add nothing, since anyone who already has the
  token already has full read/write access regardless of masking.
- **Why an empty-interests PATCH does not force `status = active`.** Forcing
  it would mean a leaked/stale `manage_token` for an `unsubscribed` or
  `complained` subscriber could silently reactivate them via any PATCH
  request — exactly the kind of loophole CLAUDE.md §9 ("complained never
  auto-resubscribes") exists to close. Leaving status untouched by interest
  edits, and reserving `complained`'s one sanctioned exit for
  `AdminClearComplaint`, keeps that guarantee intact while still satisfying
  the acceptance criterion's realistic case (an active subscriber unchecking
  everything stays active).
- **Two `svelte-ignore state_referenced_locally` directives** in
  `PreferenceCenter.svelte`: Svelte 5's compiler warns when a `$state`
  initializer reads a prop directly, assuming a `$derived` was probably
  intended. Here it is not — `initialToken`/`initialEmail`/etc. are a
  one-time seed from a parent that never re-renders this component with
  different props, and a `$derived` would silently blow away in-progress
  checkbox edits on any parent re-render. Documented inline at both sites.
- **Commit ordering does not match issue numbering** — see `#0029`'s
  Gotchas. This commit landed second (`#0029` → `#0031` → `#0030`).

## Review notes

Independently re-verified 2026-08-19 (phase 3 review) against a private
`opencircuit_r3` database and a private-port build of `7ed785d`. The state
machine is right; the copy and the audit trail on top of it are not.

**What holds.** Every security property this issue claims was reproduced. An
empty interest set is a first-class state — `SetInterests` touches
`subscriber_interests` only and never `status` — and it does not force-activate
anyone: `PATCH {interests: []}` left an `active` row `active`, an
`unsubscribed` row `unsubscribed`, and a `complained` row `complained`.
`complained` cannot be revived: `subscribers.Store.Unsubscribe`'s
`CASE WHEN status = 'complained'` guard made `PATCH {unsubscribe: true}` a true
no-op (status unchanged, `unsubscribe_source` still NULL), and
`Store.Confirm` still refuses with `ErrComplainedLocked`. `GET` masks
unconditionally (`b•••••t@gmail.com` for `brennan-test@gmail.com`), an unknown
token answers `404 {"error":"invalid or expired preferences link"}`, and
`PreferenceCenter.svelte` special-cases that 404 into a neutral re-subscribe
page rather than the generic NotFound view. `#0071`'s route parity guard was
mutation-proved (fails for a TS-only route and for a Go-only route, green after
restore); all three commits build, vet and test green independently.

**1. The save confirmation makes a false statement about subscription state.**
`patchInterests` chooses its message on `len(respSlugs)` alone, so a
non-`active` subscriber saving an empty selection is told
`"Preferences saved. You're subscribed to general announcements only."` —
reproduced verbatim against an `unsubscribed` row whose own response body
carried `"status": "unsubscribed"`. The handler therefore knows the statement
is untrue as it writes it. `PreferenceCenter.svelte` renders `res.message`
verbatim and never surfaces `status` at all, so someone who unsubscribed and
then re-opens an old footer link — a completely ordinary thing to do to check
that unsubscribing worked — gets a fully functional-looking preference centre
that assures them they are still receiving general announcements. That is the
exact hazard PRD §6.4 and this issue's own Notes exist to prevent, only
inverted. The status is already in the response; make the message and the page
conditional on it (and offer a re-subscribe path for a non-`active` row rather
than a Save button that cannot do anything).

**2. "Unsubscribe from everything" reports success, and writes an audit row,
for an action that did not happen.** `PATCH {unsubscribe: true}` against a
`complained` row returned
`"You've been unsubscribed from everything."` with `"unsubscribed": true` while
the row stayed `complained` with `unsubscribe_source` NULL — and
`patchUnsubscribe` recorded `audit.ActionSubscriberUnsubscribed` with
`{"source": "preferences"}` unconditionally, because it never inspects what
`Store.Unsubscribe` returned. The audit log is the consent-evidence record PRD
§6.3 says you produce when a deliverability complaint needs answering; a
`subscriber.unsubscribed` row for someone who in fact filed a spam complaint
and never unsubscribed corrupts exactly that record, and is indistinguishable
in the admin audit view from a real one. `#0032` already settled this shape for
the admin path — it returns `no_op: true` when the target had already
complained, on the stated grounds that "the caller must show that rather than
imply the action took effect" — and this path should follow that precedent:
compare `updated.Status` against `sub.Status` (or check for
`StatusComplained`), skip the audit write when nothing changed, and say so in
the response.

**3. Neither non-`active` path has a regression test.** The auto-reactivation
loophole closure is this issue's headline security claim, and
`TestPreferencesHandler_Patch_EmptyInterests_StaysActiveGeneralAnnouncementsOnly`
exercises it only against an `active` subscriber, where the assertion
`after.Status == StatusActive` passes whether or not the handler forces the
status. Nothing in the suite fails if a future change sets `status = active` on
an empty PATCH, and nothing covers unsubscribe-on-`complained`. Add: empty
PATCH on `unsubscribed` and on `complained` (status unchanged), and
`{unsubscribe: true}` on `complained` (status unchanged, **no** audit row) —
the third one would have caught finding 2 on its own.

**Minor, not blocking.** `maskEmail` slices the local part by byte
(`local[:1]`, `local[len(local)-1:]`), so an RFC 6531 non-ASCII address — which
`#0026` deliberately accepts and `SubscribeForm.svelte` deliberately does not
filter — masks to invalid UTF-8 and renders as `\ufffd` after JSON encoding.
Use `[]rune` (or `utf8.DecodeRuneInString`/`DecodeLastRuneInString`).

**On carrying two actions on one PATCH route: accepted.** The unsubscribe path
gets the same token lookup, the same `404` for an unknown token, the same
rate limiter and the same audit action a dedicated route would have, and
`{unsubscribe: true}` is explicit rather than inferred from an empty selection,
which is the property that actually mattered. Two notes for `#0034`, which must
*not* simply reuse this handler: (a) `#0034` requires a neutral **200** for
unknown, expired and already-used tokens, the opposite of this route's `404`,
so the two error contracts are deliberately different; (b) `#0034` must rotate
`manage_token` — this route does not, so after `#0034` lands the two unsubscribe
paths would leave different post-conditions unless this one rotates too, and
`#0034`'s carried-in question about what rotation does to a `complained` row is
the same question as finding 2 above. Whatever it decides, both paths should
agree.
