## Description

Token-authenticated page where a subscriber manages their interests or leaves entirely, reached from every email footer.

> 🟢 Resolved 2026-08-19 — Re-reviewed independently against a private `opencircuit_r3b` database (created, migrated, dropped) in throwaway worktrees at `18b9e82` and `5501a9d`, so both bounced findings were reproduced before and after rather than taken on report: the false save confirmation fired for **all four** non-`active` statuses at `18b9e82` (`pending`, `unsubscribed`, `bounced` and `complained` each got "Preferences saved. You're subscribed to general announcements only." while the response body carried their real status) and all four now get the honest "…you're not currently subscribed (status: X)" message with the row provably unchanged, while `active` still saves normally ("Preferences saved." / "…general announcements only.", row still `active`, unsubscribe still writes its one audit row); the spurious audit row is gone — `PATCH {unsubscribe:true}` on a `complained` row counted **1** `subscriber.unsubscribed` row before the fix and **0** after, with `unsubscribed:false`, `no_op:true`, `status` still `complained` and `unsubscribe_source` still NULL, which is the record `#0038`/`#0060` will read and the part that mattered most. The `no_op` contract matches `#0032` exactly rather than inventing a second convention — `patchUnsubscribe` derives `noOp := before == StatusComplained` from the pre-call status just as `AdminSubscribersHandler.Suppress` does, reports it in the body, and the SPA renders a distinct panel carrying the server's explanation instead of the success panel; the one deliberate divergence (skipping the audit write entirely rather than flagging `no_op` in its metadata) is correct, because `Suppress` is recording an admin's attempt and this route has no actor to record. The `complained` loophole stays closed under every payload this route accepts — empty PATCH, full interest replacement, unsubscribe-everything, the combined `{interests, unsubscribe:true}` body and `{unsubscribe:false}` — plus a `Confirm` replay and a `RestartSignup` call, each leaving the row `complained` with `unsubscribe_source` NULL and zero unsubscribe audit rows. `maskEmail` was probed with sixteen hostile inputs (single multi-byte rune, astral-plane emoji pair, decomposed combining sequences, a lone combining mark, a two-character local part, an empty local part, no `@`, a trailing `@`, multiple and adjacent `@`, a 40-rune accented local part and already-invalid UTF-8 bytes): no panic on any of them, every output valid UTF-8, and the byte-slicing mangling that produced `\xe6•••••\xa5` at `18b9e82` is gone. All three backend mutation proofs and the frontend one were re-run independently — unconditional audit write, status-blind `preferencesSaveMessage`, byte-sliced `maskEmail`, and a `complained` case that claims an active subscription — each failed exactly the named test and passed again after a `diff`-confirmed byte-identical revert. `go build`, `go vet` and `go test ./... -count=1` are green across all 13 tested packages with zero skips and real DB durations (`internal/handlers` and `cmd/opencircuit` re-run clean in isolation against `#0084`), `npm run check` reports 0 errors / 0 warnings over 195 files, `npm test` passes 148 tests in 8 files, `npm run build` succeeds, `web/dist/index.html` is byte-identical to the committed placeholder, and `5501a9d` touches exactly its six declared files. One residual, a follow-up rather than a bounce: the non-`active` status panel offers a "Subscribe again" link for a `complained` subscriber too, and that link leads to `/subscribe`, whose uniform 202 says "Check your email to confirm." for a confirmation mail that `#0026`'s complained branch will never send — no guard is undone (the row cannot leave `complained` by any route reachable from this UI), but the component already knows the status and should suppress that affordance for `complained` and reuse the honest copy `patchUnsubscribe`'s no-op path already returns.

## Acceptance criteria

- [x] `GET /api/preferences?token=` returns the subscriber's interests and the full active interest list
- [x] Email is masked (`b•••••n@gmail.com`) unless the token was just issued by a
      confirm — implemented client-side, not as a server-trusted flag; see Gotchas
- [x] `PATCH /api/preferences` replaces the interest set
- [x] An empty selection keeps the subscriber `active` on general
      announcements only, and the UI says so explicitly — precisely: an empty
      PATCH never *changes* status at all (it stays whatever it already was),
      so an already-active subscriber (the normal case — a footer link only
      ever reaches active subscribers) stays active. It deliberately does
      NOT force a `pending`/`unsubscribed`/`complained` row to `active` — see
      Gotchas for why forcing that would reopen an auto-reactivation loophole.
- [x] A separate, clearly labelled "Unsubscribe from everything" action is present alongside
- [x] Invalid or rotated tokens render a neutral page offering to re-subscribe — never a raw 404
- [x] Changes are saved with visible confirmation and an audit row
- [x] Handler and component tests pass

## Notes

PRD §6.4. "Uncheck everything" is how a lot of people *try* to unsubscribe. Silently leaving them subscribed is a complaint waiting to happen, so the empty state must state plainly what it means and the real unsubscribe action must be equally prominent.

Granular management measurably reduces full unsubscribes — someone tired of homelab posts drops one interest instead of leaving the list.

The email mask exists because these URLs end up in browser history and shared screenshots.

## Root cause

New construction — no preference-center endpoint or view existed.
`GET /api/preferences` and `PATCH /api/preferences` did not exist; `/preferences`
was already a recognized SPA route (`#0014`) falling through to App.svelte's
generic placeholder.

## Fix

- `internal/handlers/preferences.go` (new) — `PreferencesHandler.Get`/`.Patch`.
  `Get` always masks (`maskEmail`: first + last local-part char kept, a
  fixed run of five bullets between them regardless of original length, so
  the mask itself never leaks local-part length). `Patch` accepts either
  `{token, interests:[slug,...]}` (replace, resolved via
  `interests.Store.GetBySlug` — *not* filtered to active, so a
  still-selected-but-since-deactivated interest survives an unrelated save
  instead of silently falling off, per that method's own doc comment which
  anticipated exactly this use) or `{token, unsubscribe:true}` (calls
  `subscribers.Store.Unsubscribe(source=preferences)`, ignoring any
  `interests` field in the same request) — see the package doc comment for
  why "Unsubscribe from everything" rides the existing PATCH route instead
  of a new one.
- `web/src/views/PreferenceCenter.svelte` (new) — two entry modes. Standalone
  (`initialToken` prop absent): reads `?token=` on mount, calls
  `GET /api/preferences`, masked email. Embedded (`initialToken` present,
  used by `#0030`'s `ConfirmSubscription`): skips the fetch, uses the
  props supplied directly — unmasked email, since the caller already proved
  fresh mailbox control via the confirm token. `showHeading` (default
  `true`) lets the embedded case suppress this component's own `<h1>` so the
  page keeps exactly one.
- `web/src/lib/subscribe.ts` — `buildSaveInterestsPatch`/
  `buildUnsubscribeEverythingPatch` (added in `#0029`'s commit, consumed
  here).
- `web/src/lib/api.ts` — `getPreferences`/`patchPreferences`; `types.ts` —
  `PreferencesResponse`.
- `cmd/opencircuit/main.go` — additive: constructs `PreferencesHandler` and
  registers `GET`/`PATCH /api/preferences` behind a new
  `middleware.NewRateLimiter(rate.Every(time.Minute/10), 5)`.
  `mountAndServe` gained `preferencesH` as its second new parameter (after
  `#0029`'s `publicInterestsH`, before `#0030`'s `confirmH`).
  `subscribe.go`/`subscribe_test.go` (owned by the concurrent `#0081` pass)

- Dev-store gap: **documented, not filled** — `STORAGE=json` passes `nil`

## Gotchas

- **The "unless fresh from confirm" unmask is a client-side hand-off, not a
  server-trusted signal.** `manage_token` never changes, so `GET
  /api/preferences` alone has no way to tell "just confirmed" apart from
  "three-month-old bookmark" — it always masks. The unmask happens entirely
  in the SPA: `ConfirmSubscription.svelte` already holds the plaintext email
  from its own `POST /api/subscribe/confirm` response (proof of fresh
  mailbox control) and passes it to `PreferenceCenter` as a prop for that
  one render; it is never sent back to or re-requested from the server.
  Deliberate — a client-asserted "fresh" flag the server trusted would be
  trivially forgeable and add nothing, since anyone who already has the
  token already has full read/write access regardless of masking.
- **Why an empty-interests PATCH does not force `status = active`.** Forcing
  it would mean a leaked/stale `manage_token` for an `unsubscribed` or
  `complained` subscriber could silently reactivate them via any PATCH
  request — exactly the kind of loophole CLAUDE.md §9 ("complained never
  auto-resubscribes") exists to close. Leaving status untouched by interest
  edits, and reserving `complained`'s one sanctioned exit for
  `AdminClearComplaint`, keeps that guarantee intact while still satisfying
  the acceptance criterion's realistic case (an active subscriber unchecking
  everything stays active).
- **Two `svelte-ignore state_referenced_locally` directives** in
  `PreferenceCenter.svelte`: Svelte 5's compiler warns when a `$state`
  initializer reads a prop directly, assuming a `$derived` was probably
  intended. Here it is not — `initialToken`/`initialEmail`/etc. are a
  one-time seed from a parent that never re-renders this component with
  different props, and a `$derived` would silently blow away in-progress
  checkbox edits on any parent re-render. Documented inline at both sites.
- **Commit ordering does not match issue numbering** — see `#0029`'s
  Gotchas. This commit landed second (`#0029` → `#0031` → `#0030`).
- **`patchUnsubscribe`'s no-op decision is on the audit write, not on
  `SetInterests`.** These are two different guards for two different
  reasons: `patchInterests` never skips its write (`SetInterests` has no
  status check by design — see the `preferencesInterestStore` doc comment),
  it only changes what it *says*. `patchUnsubscribe` skips the audit write
  entirely on a no-op, because "an interest edit was saved but won't take
  effect yet" is true and worth logging, while "this subscriber was
  unsubscribed" is false and would corrupt the audit trail if logged. Don't
  generalize one guard's shape onto the other.
- **`Unsubscribed: !noOp` reuses the existing field rather than adding a
  second boolean for "did it work."** `NoOp` and `Unsubscribed` are always
  complementary by construction (`noOp := before == StatusComplained`,
  `Unsubscribed: !noOp`) — there's no state where both are true or both are
  false. `NoOp` is still a separate field (rather than just inverting
  `Unsubscribed` client-side) so the JSON body says explicitly *why* nothing
  changed is expected, matching `#0032`'s `no_op` precedent instead of
  making the frontend infer it.
- **Embedded mode's `status = 'active'` seed has no server round-trip to
  fall back on if the assumption ever breaks.** It relies entirely on
  `ConfirmHandler`/`Store.Confirm`'s contract (200 only after a real
  activation) staying true. If a future change to `confirm.go` ever returns
  200 without activating (e.g., some new partial-success case), this
  component would silently show the active editor for a non-active row
  until the next PATCH/GET corrects `status`. `confirm.go` is out of this
  issue's lane (owned by `#0030`, untouched here) — flagging this coupling
  rather than adding a speculative `initialStatus` prop nobody asked for.
- **The "not currently active" panel replaces the "Leave the list" section
  too, not just the interest editor.** Deliberate: unsubscribing something
  that isn't subscribed is meaningless, and hiding it removes the one
  reachable-from-the-UI way to trigger `patchUnsubscribe`'s no-op path in
  the first place — that path is still fully guarded server-side (see the
  mutation proofs above) for the direct-API / stale-tab / race-condition
  case, which is why the backend guard exists independently of what the UI
  currently shows.
