## Description

`scripts/dev.sh` exports dev defaults for six required config variables so a
developer does not need a `.env` file — but three other unconditionally
required variables (`AWS_REGION`, `EMAIL_FROM`, and now `EMAIL_LIST_DOMAIN`)
are not among them, so `config.Load` rejects the boot. A clean checkout with no
`.env` cannot run the command that `CLAUDE.md` §5 and `issues/Issues.md`
both document as *the* way to run this project locally.

> 🟢 Resolved 2026-08-21 — Reviewer independently booted `./scripts/dev.sh` from a
> genuinely clean environment (`env -i`, no `.env` in the repo root — confirmed
> absent) on an idle machine (load average 3.19, under `CLAUDE.md` §5's ~8
> threshold). The pre-fix failure reproduced first, then the fixed script came up
> and served a request. Critically, the "no real mail, no real AWS call" property
> holds even when `STORAGE` is overridden to Postgres — proved live, not argued.

**The safety property, checked in code and live.** Confirmed the implementer's
claim by reading `serveDevMode` (`cmd/opencircuit/main.go:339–472`): it contains
no reference to a mailer, SES, or the AWS SDK, and passes `nil` for
`sesNotifyH`. The only `cfg.AWSRegion` read is `sesnotify.NewVerifier` at
`main.go:249`, inside `servePostgres`. So the three defaults are pure validation
weight under `STORAGE=json`, as claimed.

The `STORAGE`-override case the implementer did not test is the one that
mattered, and **the safety holds — with a second gate the `## Fix` does not
mention**. `mailing.NewSESMailer` (`internal/mailing/ses_mailer.go:65–78`)
requires `SES_CONFIGURATION_SET` as well as `AWS_REGION` and `EMAIL_FROM`, and
checks all three *before* `awsconfig.LoadDefaultConfig`. `dev.sh` does not export
it. Ran all three sub-cases:

| Override | Result |
|---|---|
| `STORAGE=postgres`, no `DATABASE_URL` | `config: missing required variable DATABASE_URL` |
| + unreachable `DATABASE_URL` | fails at `db.Connect` — `servePostgres` connects before it touches the mailer |
| + **reachable** DB | `constructing SES mailer: mailing: cannot construct SES mailer: missing SES_CONFIGURATION_SET` |

The third is the decisive one: even with a live database, `dev.sh`'s environment
cannot construct an SES client, and it fails *before* the AWS SDK loads a
credential chain. No AWS call is reachable from `dev.sh` on any path. And on the
one path that does construct a mailer (a developer whose `.env` supplies
`SES_CONFIGURATION_SET`), `EMAIL_FROM` is now `dev@localhost` — an unverified,
unroutable identity SES rejects — where before the change that developer's real
`hello@opencircuitsf.com` would have been used. The change *reduces* blast radius
on the override path rather than widening it.

**`.env` interaction — deliberate and safe.** `config.Load` calls
`godotenv.Load`, which is `loadFile(path, false)`: it does **not** override
variables already in the environment. So `dev.sh`'s exports shadow a real `.env`,
meaning a developer with production values in `.env` now gets `dev@localhost` and
`lists.localhost` under `dev.sh`. That is the safer direction, and it is not a
new pattern — the pre-existing six defaults (`SESSION_SECRET`, `ADMIN_EMAIL`, …)
already shadow `.env` the same way.

**`EMAIL_LIST_DOMAIN=lists.localhost` is the right call.** `EmailListDomain`'s
only consumer is `mailing.CampaignHeaders`, reachable solely through
`campaign_render.go` on the send path — never in dev mode. If a dev preview ever
does render it, the header reads `mailto:unsubscribe@lists.localhost`: inert,
unroutable, and visibly not the real `lists.opencircuitsf.com` (`CLAUDE.md` §9).
Nothing in dev breaks. A production-looking default here would have been the
actual defect.

**`EMAIL_FROM` quoting.** Nothing in the codebase parses or validates
`EMAIL_FROM` — it is passed straight to SES's `FromEmailAddress`, which accepts
the RFC 5322 display-name form. The angle brackets survive the shell verbatim
(`[Open Circuit SF <dev@localhost>]`) because the whole `${VAR:-default}` sits
inside double quotes, so `<` is never a redirection; confirmed no stray `Open`
file was created. Override still works
(`EMAIL_FROM='Custom <me@example.com>'` passes through). `.env.example:36` ships
the identical unquoted `Name <addr>` shape, so the format matches the
established convention.

**Idiom.** All three lines are `export VAR="${VAR:-default}"`, in the same block,
in the same style as the six that preceded them. No second pattern introduced.
Not setting `MAILER_NOOP` is right: `STORAGE=json` constructs no mailer for it to
guard, and setting it would add a fourth concept to a block that is currently one
idiom repeated nine times.

**`seed` proof holds.** The logic is sound — `seed.go` calls the same
`config.Load()`, so failing at `db: pinging database … connection refused`
against a deliberately-unreachable `DATABASE_URL` demonstrates that config
validation passed and the three variables no longer block it. It proves exactly
that and nothing about a live database, which is all this issue needs. `seed`
still requires a real `DATABASE_URL` regardless; that is unchanged and correctly
documented.

**Blast radius confirmed: `scripts/dev.sh` only.**
`scripts/sim.sh` matches nothing for `EMAIL|AWS|STORAGE|DATABASE|SESSION|export|
config.|.env` — it drives a Simulator screenshot against an already-running
server and reads no config. `.env.example` already ships all three variables
(lines 34, 36, 38) with real production values, which is correct for its purpose.
`deploy/` hardcodes none of them; `opencircuit.service` supplies the environment
via `EnvironmentFile=/etc/opencircuit/config.env`, which is production's concern
and untouched by a dev script. Nothing else needs a change.

One forward-looking note, already flagged in the issue body and worth keeping:
re-check `EMAIL_FROM`/`MAILER_NOOP` here when `#0045`'s send worker lands, since
that is the point at which a dev-mode send path could first exist.

## Steps to reproduce

From a checkout with no `.env` file in the repo root:

```bash
./scripts/dev.sh
```

## Expected behavior

The Go API starts on `:8080` and Vite on `:5173`, as the script's own header
comment advertises ("No PostgreSQL, no systemd, no migrations needed").

## Actual behavior


## Notes

**This is pre-existing and predates `#0105`.** `AWS_REGION` and `EMAIL_FROM`
have been in `config.Load`'s `required` table with `skipInDev: false` since
before that commit; `#0105` added `EMAIL_LIST_DOMAIN` alongside them, which
lengthens the error by one line but does not create the failure mode. Filed
from `#0105`'s review because the implementer correctly flagged it as
out of scope there, and because the next agent to run `dev.sh` will hit it.

The script clearly *intends* to be self-sufficient — it goes to the trouble of
defaulting `STORAGE`, `BASE_URL`, `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_ORIGIN`,
`SESSION_SECRET`, `ADMIN_EMAIL`, and `PORT`, each with the
`${VAR:-default}` override idiom, and its header says overrides are the only
thing a developer should need to supply. The three missing variables are an
oversight in that list, not a deliberate requirement.

`cmd/opencircuit`'s `seed` subcommand (`seed.go` calls `config.Load()`) has the
same exposure for anyone running it without a `.env`.

**Two candidate fixes, decide deliberately:**

1. **Add the three to `dev.sh`'s default block**, matching the existing idiom:

   ```sh
   export AWS_REGION="${AWS_REGION:-us-west-2}"
   export EMAIL_FROM="${EMAIL_FROM:-Open Circuit SF <hello@localhost>}"
   export EMAIL_LIST_DOMAIN="${EMAIL_LIST_DOMAIN:-lists.localhost}"
   ```

   Cheapest and preserves the script's self-sufficiency. Note the values must
   be obviously-local placeholders: a real `EMAIL_FROM` or the production
   `lists.opencircuitsf.com` would let a dev run look more production-like
   than it is. Nothing sends mail on the `STORAGE=json` path today, so a
   placeholder is safe — but re-check that when `#0045`'s send worker lands.

2. **Document `cp .env.example .env` as a prerequisite** in the script's
   header, `HANDOFF.md`, and `CLAUDE.md` §5, and have `dev.sh` fail with a
   pointed message rather than the raw config error. More honest if the intent
   is that developers should always have a real `.env`, but it contradicts the
   six defaults the script already sets.

Option 1 is probably right, but note that `.env.example`'s `SESSION_SECRET` is
deliberately left blank (a non-empty placeholder there would sign real sessions
with a published key), so option 2 alone does not actually produce a bootable
`.env` without a manual `openssl rand -hex 32` step — which strengthens the
case for option 1.

## Root cause

`internal/config/config.go`'s `required` table lists `AWS_REGION`, `EMAIL_FROM`,
and `EMAIL_LIST_DOMAIN` with `skipInDev: false` — they are validated even under
`STORAGE=json`. `scripts/dev.sh` never exported defaults for them (only the
other six required variables got the `${VAR:-default}` treatment), so
`config.Load()` rejected the boot from a clean checkout with no `.env`,
exactly as reproduced in the issue body.

Confirmed by reading `cmd/opencircuit/main.go`'s `serveDevMode` (the function
`serve()` calls when `cfg.DevMode()` is true): it never reads `AWSRegion`,
`EmailFrom`, `EmailListDomain`, `SESConfigurationSet`, or `MailerNoOp` for
anything — no SES client and no send worker are constructed on the
`STORAGE=json` path. Those three variables are pure validation weight in dev
mode; only `servePostgres` (never reached by `dev.sh`'s default `STORAGE=json`)
uses them to build `mailing.NewSESMailer` or checks `checkMailerNoOp`.

## Fix

Took **option 1** from the issue's own analysis: added the three variables to
`dev.sh`'s existing `${VAR:-default}` block, in the same place and idiom as
the other six.

- `AWS_REGION="${AWS_REGION:-us-west-2}"` — left at the real SES region.
  Confirmed inert under `STORAGE=json` (see Root cause), so there is no
  "looks production" risk from matching the real value; picking a fake region
  would only help someone who overrides `STORAGE` to exercise the Postgres
  path locally, in which case they already need to supply a real
  `DATABASE_URL` and pass `checkMailerNoOp`'s guard deliberately.
- `EMAIL_FROM="${EMAIL_FROM:-Open Circuit SF <dev@localhost>}"` — the
  `@localhost` domain can never route mail, and `dev@` (vs. production's
  `hello@`) is a second, independent tell that this is not the real address —
  matching the spirit of `ADMIN_EMAIL`'s existing `admin@localhost` default.
- `EMAIL_LIST_DOMAIN="${EMAIL_LIST_DOMAIN:-lists.localhost}"` — deliberately
  *not* `lists.opencircuitsf.com` (PRD §6.5, CLAUDE.md §9): a dev default
  must never look like the real unsubscribe subdomain, per the issue's own
  warning. `lists.localhost` follows `WEBAUTHN_RP_ID`'s existing `localhost`
  default.

**Did not set `MAILER_NOOP`.** `dev.sh`'s default `STORAGE=json` path never
constructs a mailer of either kind (see Root cause), so there is nothing for
it to guard against — and leaving it unset preserves `config.Load()`'s
documented default (`false`) rather than introducing a second precedent
alongside the six-default idiom the script already follows.

**`cmd/opencircuit/seed.go`**: no code or script change needed. It calls
`config.Load()` with the same required table, so the three new `dev.sh`
defaults resolve its exposure identically when a developer runs `seed` from
an environment carrying `dev.sh`'s exports — confirmed in `## Verification`
below by reproducing the issue's own `env -i` recipe with the fixed variables
present. `seed` still requires a real `DATABASE_URL` regardless (it has no
`STORAGE=json` branch — it always calls `db.Connect`), so there is no
`dev.sh`-equivalent default to add for that variable; it was already
documented as the one variable `dev.sh` intentionally leaves unset.

**`scripts/sim.sh`**: confirmed it reads no config (it only drives a
Simulator/Safari screenshot against an already-running server) — left
untouched, per the issue's own note.
