## Description

`docs/deployment.md`'s install step is, literally:

	sudo cp .env.example /etc/opencircuit/config.env

So `.env.example` is not only a reference — it is **the file production gets**,
by a documented instruction. That raises the bar on everything in it, and two
things currently fall short.

**Confirmed independently by the orchestrator**: the `cp` line exists, and
neither `STORAGE` nor `SES_EVENTS_TOPIC_ARN` appears in `.env.example`, while
`internal/config`'s loader reads both.

### 1. The `EMAIL_FROM` apex form has no inline caveat

`.env.example` ships `EMAIL_FROM` in the **apex** form. Production's `From:` must
sit on the verified SES subdomain identity — `contact@mailing.opencircuitsf.com`
— because **the apex form cannot send**.

That warning exists, in `docs/configuration.md`'s `EMAIL_FROM` row. It does not
exist in the file being copied. So the documented happy path installs a value
that fails, and the caveat lives in a document the operator has no particular
reason to open at that moment.

`#0418`'s review judged this closable with a single `#` comment. That is the
minimum; consider whether the value itself should carry the working form.

### 2. Two variables the loader reads are missing entirely

`internal/config`'s loader reads `STORAGE` and `SES_EVENTS_TOPIC_ARN`. Neither is
in `.env.example`. Both appear in `PRD.md` §9's block — **which is the exact gap
§9's own note says it closed on 2026-08-21.**

`SES_EVENTS_TOPIC_ARN` is the consequential one: `#0107` pins SNS handling
against it.

## Why this is worth doing properly rather than adding two lines

The interesting question is **what `.env.example` is for.** It is currently
serving two jobs — a readable reference and a production template — and the two
pull in opposite directions: a reference favours illustrative values, a template
favours working ones. The apex `EMAIL_FROM` is exactly that tension, and it was
resolved in favour of readability in a file that gets copied onto a server.

Decide which job it has. If it is a template, values should work. If it is a
reference, `docs/deployment.md` should stop telling operators to copy it.

## Acceptance criteria

1. An operator following `docs/deployment.md` verbatim does not end up with a

2. `STORAGE` and `SES_EVENTS_TOPIC_ARN` are present, with the same treatment as
   their neighbours. **Re-derive the full set the loader reads** rather than
   adding just these two — if the loader reads others that are also missing,
   that is the same defect and this issue should close all of it.
3. **Answer the reference-versus-template question explicitly** and record the

4. Nothing in `.env.example` contradicts `docs/configuration.md` or `PRD.md` §9.
   Check all three against each other; `#0418`'s review found
   `docs/configuration.md`'s `AWS_REGION` row still saying `us-west-2` after the
   template was corrected — that specific one belongs to [#0421](0421.md), but
   look for others.
5. **No secret or credential gains a real value.** `SESSION_SECRET` stays blank.
6. **No mechanism** (`#0330`/`#0347`/`#0356`/`#0381`) — though if a cheap
   `internal/config` test asserting every loader-read variable appears in

## Fix

**Criterion 3 — the reference-versus-template question, answered: template.**
`docs/deployment.md` §3's install step is a literal
`sudo cp .env.example /etc/opencircuit/config.env`, so `.env.example` *is*
what production gets, not a reference an operator reads and translates. That
settles the tension the issue describes in favour of working values: a
reference favours illustrative examples, a template favours values that boot
and send mail unedited. Recorded in two places a future editor will see it —
a new header comment at the top of `.env.example` itself, and a new sentence
at the top of `docs/configuration.md`'s intro naming that file as the
reference and `.env.example` as the template, with a pointer back here.

**Criterion 1 — `EMAIL_FROM`.** Went with the working value, not an inline
caveat: `.env.example` now ships
`EMAIL_FROM=Open Circuit SF <contact@mailing.opencircuitsf.com>`, the real
verified-identity value from `docs/email-setup.md`, replacing the apex form
that cannot send at all. Kept an inline comment too, but as a
regression guard ("do not revert this to the apex form for readability —
that was #0423's defect"), not as the primary fix — a caveat next to a value
that still doesn't work was exactly what `#0418`'s review called the
minimum, and criterion 1 asks for more than the minimum. Also softened
`docs/deployment.md`'s "fill in `EMAIL_FROM` … these require the SES account"
bullet, which pre-dated this fix and would have told an operator to invent a
value that already ships correctly — it now says the six SES-adjacent
variables already carry this deployment's real values and only need
confirming against `docs/email-setup.md`, not reinventing.

**Criterion 2 — re-derived the loader's full variable set by hand** against
`internal/config/config.go`'s `loadFromFile`, one field at a time (20 total:
`PORT`, `BASE_URL`, `DATABASE_URL`, `STORAGE`, `WEBAUTHN_RP_ID`,
`WEBAUTHN_RP_ORIGIN`, `SESSION_SECRET`, `AWS_REGION`,
`SES_CONFIGURATION_SET`, `EMAIL_FROM`, `EMAIL_REPLY_TO`, `EMAIL_LIST_DOMAIN`,

premise held exactly, nothing wider. Added both with real production values:
`STORAGE=postgres` (with a comment on the `json` dev-store escape hatch) and
the live SNS topic ARN `arn:aws:sns:us-east-1:378152330719:opencircuit-ses-events`
(already published in-repo — `docs/aws-iam-setup.md`, `docs/email-setup.md`,
`issues/0057.md`, `issues/0418.md` — so shipping it here publishes nothing
new; see criterion 5 below for why it isn't a credential).

**Criterion 4 — cross-checked all three documents against each other and
against current reality** (`docs/email-setup.md`, `CLAUDE.md` §10 item 2):
`AWS_REGION`, `SES_CONFIGURATION_SET`, `EMAIL_LIST_DOMAIN`, and
`SES_INBOUND_BUCKET` already agreed across `.env.example`,
`docs/configuration.md`, and `PRD.md` §9 (post-`#0421`). Found and fixed two
real gaps beyond the two named in the description:

- `docs/configuration.md`'s variable table had **no row at all** for
  `SES_EVENTS_TOPIC_ARN`, despite the loader reading it since `#0037`/`#0107`
  — added one.
- `PRD.md` §9's block still showed `SES_EVENTS_TOPIC_ARN=` blank with a
  comment that never acknowledged the topic now exists — corrected in place
  on the same source line (value only; the two comment lines that followed
  were condensed to one so §11's §9 line count did not move — verified 76
  raw lines via the section's own `sed` command, before and after).

**Criterion 5 — no secret gained a real value.** `SESSION_SECRET` stays
blank; `DATABASE_URL`'s password stays the `CHANGE_ME_IN_PRODUCTION`
placeholder; `ADMIN_EMAIL` stays the `you@example.com` placeholder (unlike
`PRD.md` §9's block, which predates this issue and already carries the real
admin address — left untouched, out of scope). The SNS topic ARN added for
`SES_EVENTS_TOPIC_ARN` is not a credential — it carries no authentication
material, is exactly analogous to the bucket name already shipped in

repo (see criterion 2 above), so nothing new is exposed by it appearing here
too.

**Criterion 6 — added the guard, argued.** `internal/config/env_example_guard_test.go`'s
`TestEnvExampleCoversLoaderVariables` parses `config.go`'s own AST for every
`os.Getenv`/`getInt`/`getBool` call whose first argument is a string
literal, and asserts each name it finds appears in `.env.example`. Argument
for adding it despite the "no mechanism by default" default
(`#0330`/`#0347`/`#0356`/`#0381`): the oracle is `config.go` itself, not a
second hand-maintained list living next to `.env.example` — CLAUDE.md §8's
"a guard's oracle must not be the same bytes as its subject" rule is
satisfied because the two are structurally different representations (Go
source vs. an env file) of the same fact, and mutating `config.go`'s scan
root (adding a new variable) changes what the test extracts, which is
exactly the "mutate the scan roots and `got` itself changes" shape §8 calls
a legitimate in-package Go check rather than something that needs an
external harness. This is also cheap: one AST walk, no subprocess, no
`.sh` harness, and it caught real drift on first run — proof it was not a
speculative addition. Explicitly out of scope for the guard: it only proves
loader ⊆ `.env.example` (presence), never that a shipped value is correct,
required, or safe to publish — those stay human judgment calls, both because
`got` cannot observe "is this value a secret" and because over-asserting
here is exactly `#0258`'s spiral (each additional in-file assertion is one
more thing a later edit to `config.go` could satisfy trivially without
actually fixing the underlying gap). Added the corresponding `CLAUDE.md` §5
repo-wide-guard table row for `internal/config` (reaches `../../.env.example`
from the package directory) — the new test tripped
`TestClaudeMDRepoWideGuardPackageSetParity` on first run, which is exactly
the guard working as designed (`#0387`/`#0381`).

### Bounce reason 2 — three claims this commit added are false

Each is verifiable against production or against the repo, and each sits in a
document whose only job here is to be trusted by an operator mid-deploy.

**(a) `.env.example`'s header: "Everything else below is production's actual
value."** It is not, in two places.

- `SES_INBOUND_BUCKET=opencircuitsf-inbound` names a bucket that **does not

**Remedy:** replace the final header line with one that names the exceptions,

exceptions: `SES_SANDBOX` ships the conservative `true` (production runs

**Remedy:** say "five of the six" and call out `SES_INBOUND_BUCKET` as naming a

### Not blocking, but worth the orchestrator's attention

- **The guard has a partial fail-open, and it is worth writing down rather than
  fixing here.** The empty-extraction `t.Fatal` covers a *total* failure, but a
  *shrinking* extraction passes silently. Proved in the worktree: routing the 14
  string reads through a one-line `func env(name string) string` wrapper — a
  plausible refactor — drops the extracted set to the six `getInt`/`getBool`
  names, after which `EMAIL_FROM`, `SESSION_SECRET`, `STORAGE`,
  `SES_EVENTS_TOPIC_ARN` and `ADMIN_EMAIL` can all be deleted from
  `.env.example` and the test still exits 0. So the answer to "is there an edit
  that makes both agree wrongly?" is yes, and it is an edit to `config.go`
  alone. The oracle-independence claim in the doc comment is right about
  *additions* and silent about *representation changes*. A count floor
  (`len(names) >= 20`) would close it and `got` would still move when the scan
