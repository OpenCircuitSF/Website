## Description

`docs/deployment.md`'s install step is, literally:

	sudo cp .env.example /etc/opencircuit/config.env

So `.env.example` is not only a reference — it is **the file production gets**,
by a documented instruction. That raises the bar on everything in it, and two
things currently fall short.

**Confirmed independently by the orchestrator**: the `cp` line exists, and
neither `STORAGE` nor `SES_EVENTS_TOPIC_ARN` appears in `.env.example`, while
`internal/config`'s loader reads both.

### 1. The `EMAIL_FROM` apex form has no inline caveat

`.env.example` ships `EMAIL_FROM` in the **apex** form. Production's `From:` must
sit on the verified SES subdomain identity — `contact@mailing.opencircuitsf.com`
— because **the apex form cannot send**.

That warning exists, in `docs/configuration.md`'s `EMAIL_FROM` row. It does not
exist in the file being copied. So the documented happy path installs a value
that fails, and the caveat lives in a document the operator has no particular
reason to open at that moment.

`#0418`'s review judged this closable with a single `#` comment. That is the
minimum; consider whether the value itself should carry the working form.

### 2. Two variables the loader reads are missing entirely

`internal/config`'s loader reads `STORAGE` and `SES_EVENTS_TOPIC_ARN`. Neither is
in `.env.example`. Both appear in `PRD.md` §9's block — **which is the exact gap
§9's own note says it closed on 2026-08-21.**

`SES_EVENTS_TOPIC_ARN` is the consequential one: `#0107` pins SNS handling
against it.

## Why this is worth doing properly rather than adding two lines

The interesting question is **what `.env.example` is for.** It is currently
serving two jobs — a readable reference and a production template — and the two
pull in opposite directions: a reference favours illustrative values, a template
favours working ones. The apex `EMAIL_FROM` is exactly that tension, and it was
resolved in favour of readability in a file that gets copied onto a server.

Decide which job it has. If it is a template, values should work. If it is a
reference, `docs/deployment.md` should stop telling operators to copy it.

## Acceptance criteria

1. An operator following `docs/deployment.md` verbatim does not end up with a
   configuration that cannot send mail. State how you achieved that — inline
   caveat, working value, or a changed install step.
2. `STORAGE` and `SES_EVENTS_TOPIC_ARN` are present, with the same treatment as
   their neighbours. **Re-derive the full set the loader reads** rather than
   adding just these two — if the loader reads others that are also missing,
   that is the same defect and this issue should close all of it.
3. **Answer the reference-versus-template question explicitly** and record the
   answer where the next person editing this file will see it.
4. Nothing in `.env.example` contradicts `docs/configuration.md` or `PRD.md` §9.
   Check all three against each other; `#0418`'s review found
   `docs/configuration.md`'s `AWS_REGION` row still saying `us-west-2` after the
   template was corrected — that specific one belongs to [#0421](0421.md), but
   look for others.
5. **No secret or credential gains a real value.** `SESSION_SECRET` stays blank.
6. **No mechanism** (`#0330`/`#0347`/`#0356`/`#0381`) — though if a cheap
   `internal/config` test asserting every loader-read variable appears in
   `.env.example` is warranted, say so and argue it rather than assuming either
   way.
7. Editing `PRD.md` means running `./internal/db/...` and keeping §11's
   section-index line counts exact. Run `./internal/config/...` and
   `./internal/handlers/...` as applicable. Per §5 name the specific tests that
   ran. No Go-file-plus-line-number citation (`#0352`), scanned with `python3`
   bytes rather than BSD `grep -P`.
