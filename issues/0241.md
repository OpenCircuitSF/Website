## Description

`#0095` built a parity guard tying the client's complained-subscriber copy to
the server's, and deliberately did **not** extend it to the CampaignProgress SSE
payload — using that issue's own escape hatch, and recording the narrowing
rather than taking it silently. That was the right call: the SSE case is a
structurally different problem (a Go struct versus a TypeScript interface,
rather than two string constants).

But the concern `#0095`'s 2026-08-22 amendment raised is still live and should
not die with the issue that declined it:

**A field added on the TypeScript side alone is caught by nothing.** The
existing assertion checks that the keys the server sends are handled by the
client. It does not check the converse. So a client that reads
`progress.remaining` when the server never sends it compiles, type-checks,
passes every test, and silently renders `undefined` — during a campaign send,
which is the one operation in this system with no undo.

## Acceptance criteria

- [x] Proved by mutation in both directions — add a field to the Go struct only, then to the TypeScript interface only, and confirm each fails naming the side that diverged
- [x] The guard reads both from source rather than restating either by hand; a hand-maintained third list is a third thing to drift

## Fix

Added `internal/handlers/campaign_progress_parity_test.go`
(`TestCampaignProgressParity_KeySet`), in the same filesystem-only, no-database
shape as `#0071`'s `routes_parity_test.go` and `#0095`'s
`complained_copy_parity_test.go`.

- **Go side is read via `reflect`, not text parsing.** Unlike `router.ts`'s or
  `preferences.go`'s Go halves — plain string literals the existing guards have
  no choice but to regex out of source text — `mailing.CampaignProgress` is an
  importable Go type. `reflect.TypeOf(mailing.CampaignProgress{})`'s `json`
  struct tags are the actual field names `encoding/json` emits, always in sync
  with the compiled program by construction and immune to the
  gofmt-reformat-breaks-the-regex failure mode `routes_parity_test.go`'s own
  doc comment describes. This is the honest tool here, and it sidesteps
  needing a second Go-source parser: there is nothing more authoritative to
  read than the live type itself.
- **TypeScript side has no such shortcut** — an `interface` is erased at build
  time — so `parseCampaignProgressTS` reads `web/src/lib/campaignProgress.ts`'s
  `CampaignProgress` interface block directly: an anchored block regex
  (`campaignProgressInterfaceBlockRe`) captures the declaration body, then a
  per-line walk requires every non-blank, non-comment line to match
  `campaignProgressFieldLineRe` (`name: type;` / `name?: type;`), tracking
  `/** ... */` JSDoc state (the `status` field carries a multi-line one) so
  those lines are skipped without needing to match the field regex. Any
  unrecognized line is a `campaignProgressTSParseError`, not a silent skip —
  the same structural fix `#0071`'s review required of
  `parseStaticRoutesFromRouterTS`, so a field can't go missing by "not
  matching" a scan-and-skip parser.
- **Fail-closed floor (#0275).** Both sides assert they found a plausible
  number of keys (`len(...) == 0` is fatal on the Go side via
  `campaignProgressGoJSONKeys`; a `minPlausibleKeys = 5` floor on both sides in
  the test itself) before comparing — an empty or near-empty extraction is
  treated as "the parser broke," not as "there's nothing to compare."
- **Only the key set is compared**, not field types — matching the acceptance
  criteria's own framing ("a field added on either side alone fails"). This
  guard doesn't reach for `go/types` because it never claims type equivalence
  in the first place, so there's no name-match/type-match gap to fall into
  (`CLAUDE.md`'s `#0282` note) — it's an honest string-set comparison, not a
  disguised type check.
- Corrected three doc comments that described this agreement as hand-kept —
  `internal/mailing/worker.go`'s `CampaignProgress` doc comment,
  `web/src/lib/campaignProgress.ts`'s `CampaignProgress` interface doc
  comment, and two spots in `internal/handlers/campaign_progress_test.go`'s
  `TestCampaignProgressPublisher_PublishesJSONFrameToBroker` — to name
  `TestCampaignProgressParity_KeySet` and be explicit that the existing
  hand-typed `want` map in that test only ever catches a Go-side addition.
  That test is kept, not replaced: it proves the real marshal output for
  concrete field values, which the new guard (key names only) doesn't.

### Follow-up fix (2026-08-27) — the review bounce

`54d3320` stayed; this pass fixed forward per the reviewer's `## Review notes`
rather than redesigning anything else. The defect: `parseCampaignProgressTS`'s
block-comment handling `continue`d on the **whole physical line** once a
`/** ... */` comment opened and/or closed, so a field written on the same
line as the comment's close was dropped with no error —

```
/** Estimated seconds remaining. */ eta_seconds: number;    ← was dropped, no error
*/ eta_seconds: number;                                     ← was dropped, no error
```

**Fix, in `parseCampaignProgressTS`:** both the "opens and closes a `/**` on
one line" branch and the "closes an already-open block comment" branch now
take the substring after the first `*/` on that line (block comments cannot
nest, so the first `*/` is always the real close), trim it, and — if
non-empty — require it to match `campaignProgressFieldLineRe` or raise
`campaignProgressTSParseError`, identically to any other line. There is no
longer a code path that discards a non-blank remainder silently.

**Proof the old parser actually had the hole**, without touching the shared
tree: the pre-fix `parseCampaignProgressTS` (verbatim, via `git show
HEAD:internal/handlers/campaign_progress_parity_test.go`) was copied into an

  err=<nil>

### The defect: `parseCampaignProgressTS` silently drops a field on a comment line

`## Fix` claims "Any unrecognized line is a `campaignProgressTSParseError`, not
a silent skip", and the commit message says the parser fails "closed … on any
unrecognized field line". Both are true only for lines that are *not*
comment-prefixed. The comment branch (lines 139–148) `continue`s on the whole
line, and two shapes carry live code past it:

```
/** Estimated seconds remaining. */ eta_seconds: number;     <- field dropped, no error
*/ eta_seconds: number;                                      <- field dropped, no error
```

Measured, not read. A throwaway worktree at `54d3320`, a scratch fixture test
calling `parseCampaignProgressTS` directly (deleted afterwards; the worktree is
gone and `git worktree list` shows only the main checkout):

| fixture | result |
|---|---|
| `/** the eta */ eta_seconds: number;` | **KEYS(2)** — `eta_seconds` silently absent |
| `/**\n * doc\n */ eta_seconds: number;` | **KEYS(2)** — same |
| `/*\n ghost: number;\n */` (plain block comment) | parse error ✅ |
| field inside a `/** … */` JSDoc | correctly skipped ✅ |
| `campaign_id: number; status: string;` (two per line) | parse error ✅ |
| `meta: {` … `};` (multi-line object type) | parse error ✅ |
| `status:` … `\| 'sent';` (multi-line union) | parse error ✅ |
| `campaign_id: number,` (comma separators — legal TS) | parse error ✅ |
| `export interface CampaignProgress extends Base {` | parse error ✅ |
| decoy `export interface CampaignProgress {` inside a preceding comment | parse error ✅ |
| second interface `CampaignProgressV2` / `…Extra` in the file | correct block ✅ |
| `'campaign-id': number;` (string-literal key) | parse error ✅ |
| `[k: string]: unknown;` (index signature) | parse error ✅ |
| `readonly campaign_id: number;` | parse error ✅ |
| `campaign_id: number; // the id` (trailing line comment) | parse error ✅ |
| `// eta_seconds: number;` | correctly skipped ✅ |
| `eta_seconds?: number;` (optional) | key present ✅ |
| duplicate field line | deduped, no error (harmless) |

Every shape fails closed except the two comment-line ones — and those two fail
**open**. Proved end-to-end against the real file, not just fixtures: adding

```ts
  /** Estimated seconds remaining. */ eta_seconds: number;
```

to `web/src/lib/campaignProgress.ts`'s interface and running
`go test ./internal/handlers/ -run TestCampaignProgressParity_KeySet` gives
`ok` — the guard passes with a genuine TS-only field present. The same field written
plainly on its own line fails correctly, naming `eta_seconds`. `tsc --noEmit
--strict` confirms the same-line form is a real, fully-typed interface member
(a deliberate `string` misuse of it errors as `number`), so this is live code
the parser skipped, not a formatting curiosity.

Note this hole is **new surface**, not inherited from the pattern:
`parseStaticRoutesFromRouterTS` skips only `//` lines and brace-only lines, and
skipping a `//` line is semantically *correct* in JS. Skipping the tail of a
`/** … */` line is not.

**What must change:** in `parseCampaignProgressTS`, when a line opens and closes
a block comment on the same line, or closes one, take the remainder after the
last `*/`; if it is non-empty after trimming it must match
`campaignProgressFieldLineRe` or be a `campaignProgressTSParseError`. A handful
of lines. Since neither of the two shapes can be proved by mutating the real
file (the fix makes the mutation fail, which is the point), add a small
table-driven fixture test over `parseCampaignProgressTS` covering at least those
two shapes plus one already-passing control — that is the only way the closure
stays proved. Build the fixtures from Go string literals with explicit `\n`, not
multi-line raw strings (`CLAUDE.md` §8: a malformed TS fixture reports "0
matches" rather than erroring).

Once the parser is fixed the two new doc comments become accurate as written; as
they stand, "in either direction" and "fails if … ever disagree in either
direction" overclaim, which is `#0263`'s defect class. Optional polish while
there: `worker.go` says the guard "fails the build", which is loosely true at
best — it fails a test.

### What was verified and holds

- **Both direction mutations reproduce independently.** Throwaway worktree at
  `54d3320`, mutations applied there so the shared tree was never touched
  (another agent had ~21 dirty files throughout; `git status --porcelain`
  checked before and after, and this issue's four files show an empty
  `git diff` at `HEAD`).
  - Go-only StartedAt int64 with a json tag of started_at → `--- FAIL`, "present in
    mailing.CampaignProgress's json tags but absent from … campaignProgress.ts's
    CampaignProgress interface: started_at".
  - TS-only `eta_seconds: number;` (plain form) → `--- FAIL`, "present in …
    campaignProgress.ts's CampaignProgress interface but absent from
    mailing.CampaignProgress's json tags: eta_seconds".
  Both name the side that diverged, as the criteria require.
- **`minPlausibleKeys = 5` is honest, and half of it is unreachable.** There are
  7 keys on each side, so 5 is a floor with headroom rather than a restatement
  of today's count. The TS-side floor fires as designed — shrinking the
  interface to 4 fields gives "parsed only 4 field(s) … want at least 5". The
  **Go-side floor is dead code**: `mailing.CampaignProgress` cannot lose fields
  without breaking the build at its construction sites (attempting it gives
  `unknown field Skipped in struct literal`), and reflection on a live type
  cannot silently degrade. Harmless and cheap; worth knowing it is belt, not
  braces. Note too that the floor is not what makes a partial TS parse safe —
  the key-set diff itself is, because the Go side is authoritative and a short
  TS parse surfaces as `onlyInGo`.
- **Key-set only is the right scope, and the criteria genuinely stop there.**
  Criterion 1 is "a field added on either side alone fails", and the
  Description's harm is a missing key rendering `undefined`. A Go `int64`
  against a TS `string` is a different defect that this issue never claimed;
  declining `go/types` and saying so plainly is correct, not a gap. (Wire
  *types* are separately pinned on the Go side by
  `TestCampaignProgressPublisher_PublishesJSONFrameToBroker`'s `float64`/string
  `want` values.)
- **Keeping the hand-typed `want` map is right, and it is not a second source of
  truth.** It cannot silently drift from the struct in either direction: a
  missing key fails the value compare, an extra key fails the `len(decoded) !=
  len(want)` compare. So `want` is pinned to the struct and the struct is pinned
  to the interface — transitively consistent, with no free edge. It also proves
  something the new guard does not (real marshal output for concrete values).
- **Oracle independence is sound.** For the Go→TS direction the subject is the
  compiled `mailing.CampaignProgress` and the oracle is `campaignProgress.ts` on
  disk; for TS→Go the roles swap. Neither side restates the other, and there is
  no hand-typed key list anywhere in the guard, so no edit to one side can
  satisfy the check by itself. `minPlausibleKeys` is the only hand-typed number
  and it is not a copy of the answer.
- **House pattern followed.** Same shape as `routes_parity_test.go` and
  `complained_copy_parity_test.go`: filesystem-only, no database, path constant,
  dedicated parse-error type, reader helper, and the parse-error/drift
  distinction `#0071` established. Reflection for the Go side is a genuine
  improvement over text-parsing, not a fourth pattern.
