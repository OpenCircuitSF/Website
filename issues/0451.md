## Description

`#0444`'s structural guard asserts five wiring legs of
`web/src/views/admin/CampaignEditor.svelte`. Its reviewer verified all five
against the shape the issue exists for — a leg **dropped** — and each failed
correctly and named the right thing.

It then went further and constructed two residuals, both requiring code to be
**added** rather than dropped. Both were verified by construction, and both
reported `5 passed`:

1. A **second, earlier `updateCampaign(...)` call** carrying a `slug` property
   satisfies assertion 1 even with `saveDraft`'s own `slug` property deleted.
2. A **nested function also named `onConfirmDelete`**, declared earlier and
   calling `deleteCampaign(...)`, satisfies assertion 4 even with the real
   handler's call deleted.

These are the guard's two **load-bearing** assertions — the ones whose loss is
otherwise silent, per `#0444`'s own framing.

## Why this was reported rather than bounced

`#0444`'s reviewer passed the issue deliberately, and the reasoning is worth
keeping: neither residual is reachable by the *dropped-leg* shape the issue was
filed for, there is exactly one of each construct in the component today, and
`CLAUDE.md` §8 records `#0258` buying a bounce per added mechanism. Hardening
past the stated criteria inside a passing issue is how that spiral starts.

So this is real but narrow. A decoy has to be **written deliberately** to
trigger it, which is a different threat model from an edit that quietly drops a
line.

## Acceptance criteria

1. Scope assertion 1's search to **`saveDraft`'s body** rather than the whole
   component, so an `updateCampaign(...)` call elsewhere cannot satisfy it.
2. Scope assertion 4's handler lookup to **top-level declarators**, so a nested
   function sharing the name cannot satisfy it.
3. Prove both by reconstructing the reviewer's two decoys: confirm each now
   **fails**, and confirm the five ordinary dropped-leg mutations still fail
   correctly and still fail **one test each** — `#0444`'s review established
   that no assertion stands in for another, and that property must survive.
4. **Two scope changes, no sixth assertion, no new file.** §8, and `#0444`'s
   own criterion 3. If the fix seems to want a new mechanism, stop and say why
   in the work log instead of building it.
5. Leave the other three assertions alone. They were verified sound.

## Also worth fixing while you are in there

### What must be fixed

  **Assertion 5's new `wrapsOnlyTheTrigger` check false-fails on an
  innocuous markup edit, with a message that contradicts itself.** The
  predicate requires the candidate `{#if}`'s consequent to contain *exactly
  one* non-whitespace node. Two ordinary edits break it, both verified with
  the offer gate fully intact and correct:

  - adding an HTML comment inside `{#if deleteOffered}` — a thing this
    component's markup does constantly, including in the block immediately
    below this gate;
  - adding a sibling hint element inside the gate.

  Both now fail with `` the {#if ...} nearest the "Delete campaign" trigger
  (`deleteOffered`) wraps more than just that trigger button -- the dedicated
  offer gate {#if} appears to be missing entirely ``. That message prints
  `deleteOffered` — the gate — and then asserts the gate is missing. The
  "Also worth fixing" note existed to stop this assertion naming the wrong
  subject; as built it trades a wrong-subject message in the gate-deleted
  case for a wrong-subject message in the gate-intact case, and the second is
  reachable by an edit requiring no mistake at all. Before this commit, both
  edits passed cleanly.

  **The remedy, proved in the review worktree before being written here.**
  Discriminate on whether the trigger is a **direct child** of the
  consequent, not on how many siblings it has. Replace the `consequentNodes`
  / `nonWhitespaceNodes` / `wrapsOnlyTheTrigger` block and its `throw` with:

  ```ts
  const consequentNodes = ((offerIfBlock.consequent as SvelteNode).nodes as SvelteNode[] | undefined) ?? [];
  const directlyWrapsTheTrigger = consequentNodes.some(
    (n) =>
      n.type === 'Component' &&
      n.name === 'Button' &&
      isIdentifierNamed(attrExpression(findAttr(n, 'onclick')), 'openDelete'),
  );
  if (!directlyWrapsTheTrigger) {
    throw new Error(
      `${COMPONENT_PATH}: the {#if ...} nearest the "Delete campaign" trigger (\`${srcOf(offerIfBlock.test as SvelteNode)}\`) ` +
        'has that trigger nested somewhere deeper rather than as a direct child -- the dedicated offer gate ' +
        "{#if} appears to be missing entirely, not merely re-pointed to a different gate variable (#0451, from #0444's review)",
    );
  }
  ```

  This reuses `attrExpression`, `findAttr` and `isIdentifierNamed` — all three
  already in the file, two of them already used by this same assertion's
  candidate search — so it stays a refinement of the existing lookup and adds
  no machinery, satisfying criterion 4. Measured in the review worktree: the
  guard is `5 passed` at baseline; the comment and sibling-element edits
  return to `5 passed`; E5 (gate deleted outright) still fails with the
  improved "appears to be missing entirely" message; and leg 5
  (`canDeleteCampaign` → `canEditCampaign`, gate intact) still fails
  assertion 5 alone with its original text. Re-run the two decoys, the five
  legs and the five starve probes after applying it.

  Nothing else needs to change. The two scope narrowings — the whole point of
  this issue — are correct as committed and should be left exactly as they
  are.
