## Description

`#0478` closed a real gap: an agent's resolution notes were written after its
last verification run, so guard-tripping text was never scanned. The fix added a
re-run step to phase 2 and another to phase 3.

**Phase 2's step is correctly placed. Phase 3's has two defects**, both found by
`#0478`'s own review, which recorded verbatim remedies rather than bouncing
because neither causes a wrong action with consequences beyond a fixup commit.

### 1. The step sits after the step whose commit it must precede

Phase 3's new step 5 gates the resolution commit made in step 4. Its first
sentence says so in bold — but an agent working the list in order has **already
committed** by the time it reaches step 5.

That is a check placed after the thing it gates, which is the exact shape
`#0478` exists to remove. A reader who follows the numbers rather than the bold
text gets the old behaviour back.

### 2. The approve branch scans a file the guards deliberately exempt

The issue-markdown guards scan only `open` and `in-progress` files. Two tests
pin that exemption on purpose:
`TestIssueVerificationCitationGuardExcludesResolvedFilesByDefault` and
`TestIssueLineCitationGuardExcludesResolvedFilesByDefault`.

Phase 3's step 4 flips **Status** to `resolved` before step 5 runs. So on the
approve branch, `## Resolution notes` is excluded from the citation guards by
the time the prescribed run happens — the run passes, having scanned nothing of
what was just written.

**The bounce branch is unaffected** and works exactly as described, because it
sets the status back to `open`. Criterion 2 of `#0478` named `## Review notes`,
which is the bounce branch's artifact, so that criterion is genuinely met.

Running on approve is still worth doing, but **for a reason the shipped text
does not give**: `TestResolvedOrClosedIssueCarriesClosedRow` fires on precisely
that edit, so the post-flip run checks the `**Closed**` row rather than the
prose.

## What `#0478` actually bought, for the record

Worth stating because `#0478`'s own paragraph understates it. Both new steps
hard-code `./internal/db/...`, so every implementation and review pass now runs
the issue-markdown guards **unconditionally, regardless of scoping**. Before,
a scoped run never touched that package at all, which is why the incidental
catch was so rare.

The residual window for a freshly filed issue therefore shrinks from "until
someone happens to run it" to "until the next phase-2 or phase-3 step for any
issue" — bounded and structural rather than luck. The filing path remains
uncovered by design, as a deliberate cost tolerance.

## Root cause

Phase 3's step 5 (added by `#0478`) named the run's purpose in bold but placed
it after step 4, so working the numbered list in order committed before the
run ever fired. Its approve branch compounded that: step 4 flips **Status** to
`resolved`, and the issue-markdown citation guards restrict their scan to
`open`/`in-progress` files by design, so the run — wherever it sat relative to
the commit — would have read a file already excluded from that scan.

## Fix

Confirmed the exemption first, against the two named tests rather than the
issue's prose about them.
`TestIssueVerificationCitationGuardExcludesResolvedFilesByDefault` writes a
fixture with a dangling test-name citation, shows zero failures when its
status is `resolved`, then shows one failure once flipped to `open` — the
status filter, not the section, is what excludes it.
`TestIssueLineCitationGuardExcludesResolvedFilesByDefault` pins the identical
behavior for the line-number-citation guard. Both match the issue's claim
exactly, so the description's premise stood.

Chose to **split the commit into its own step 6** rather than fold a lead-in
sentence into step 4, because the approve branch's fix is not "run before the
existing commit line" — it is "defer the `resolved` flip itself," which is a
change to step 4's content, not just to when step 5 fires relative to it. A
lead-in sentence ahead of both branches cannot express that the flip has to
wait; a separate step can carry the ordering plainly: step 4 drafts the notes
and leaves Status at `in-progress`, step 5 runs the guards (twice, on
approve), step 6 makes the commit.

Rewrote step 5 so the approve branch runs once while Status still reads
`in-progress` — this is the run the citation guards can actually see — then
flips Status and the Closed row, then runs a second time. That second run is
described as checking a different thing:
`TestResolvedOrClosedIssueCarriesClosedRow` fires on a `resolved` status
lacking a `**Closed**` row, which is unrelated to prose the citation guards no
longer read by then. The bounce branch needed no such split, since reverting
Status to `open` keeps the file in scope for its one run.

Corrected "Go doc comment" to "Go comment" in both phase 2 step 8 and phase 3
step 5, matching `CLAUDE.md` §5's broader routing rule.

No mechanism was built to check this prose — per criterion 4, the fix is text
only.

## Review notes

Approved on the first pass. Both defects `#0478`'s review recorded are gone,
the criteria are met, and the corrected phase 3 is followable — I followed it
literally to write this, which is reported below.

**The split-versus-fold reasoning is right, and the fold would not have
worked.** `#0478`'s remedy offered two options as if they were
interchangeable, and they are not, for the reason the implementer gives: the
approve branch's defect is not only *when* the run fires relative to the
commit, it is *what state the file is in* when it fires. Fixing that requires
step 4's approve branch to stop flipping **Status**, which is an edit to step
4's content. A lead-in sentence placed ahead of both branches can say "run
before you commit"; it cannot say "and do not do the thing the bullet below
tells you to do." The fold would have produced a step 4 whose approve bullet
still flipped the status before the lead-in's run could see anything, i.e. the
second defect surviving the fix for the first. The split carries the ordering
in the numbering itself, which is what a reader following numbers actually
obeys. The implementer went past choosing between two prescribed options and
argued why one of them was unavailable; that is the correct call and the
argument holds.

**The exemption, confirmed independently rather than taken from the issue's
prose.** `TestIssueVerificationCitationGuardExcludesResolvedFilesByDefault`
writes one fixture body carrying a dangling test-name citation, asserts zero
failures at status `resolved`, rewrites the same body at status `open`, and
asserts exactly one — the body is byte-identical across the two halves, so the
status row is the only variable and the exclusion is demonstrably the status
filter. `TestIssueLineCitationGuardExcludesResolvedFilesByDefault` pins the
identical shape for the sibling guard over evidence citing a Go source
location positionally. I then checked the fixtures are not proving something
about themselves: both pass an explicit predicate into the shared scan helper,
so a passing fixture would not by itself prove the live guards use that same
predicate. They do — `TestNoOpenIssueVerificationCitesUndefinedTestFunction`
and `TestNoOpenIssueEvidenceCitesGoFileByLineNumber` each build the identical
`open`/`in-progress` predicate at their real-corpus call site. The issue's
premise stands, and so does the new step 5's.

**One measured refinement, recorded rather than bounced — this lineage's sixth
false premise corrected by measurement.** The status filter is not the only
filter. Both citation guards also restrict themselves to the level-2 sections
named in `issueCitationSectionHeaders`, and `resolution notes` is not one of
its keys, while `review notes` is. So the approve branch's `## Resolution
notes` blockquote is out of the citation guards' reach at *any* status, and
step 5's sentence claiming the pre-flip run "is what lets both actually scan
the `## Resolution notes` you just wrote" is wrong in the section dimension
even though it is right in the status dimension. The step's *instruction* is
unaffected and still correct, which is why this is a note and not a bounce:
what a reviewer actually writes on approve is a `## Review notes` section —
393 issue files carry one — and that section is scanned, is in scope while the
status still reads `in-progress`, and is exactly what the pre-flip run exists
to catch. Verified on this very file: the pre-flip run below read these notes.

The imprecision is also inherited, not introduced. Step 5's opening sentence
names both sections as "exactly the issue-markdown text `internal/db`'s guards
scan"; that clause is `#0478`'s, unchanged by `9f360c3`, and `#0478`'s own
review notes attributed the approve-branch exclusion to status alone. Remedy,
verbatim, for whenever `issues/Issues.md` is next edited: in phase 3 step 5's
approve bullet, replace the section named as the pre-flip run's subject with
`## Review notes`, and say that `## Resolution notes` is outside the citation
guards' section set as well as outside their status set — so the pre-flip run
is worth doing for the review prose, not for the blockquote.

**Two runs is justified on purpose, and thinly on cost.** The text says
plainly that the second run "checks a different thing, not the same thing
twice," and names `TestResolvedOrClosedIssueCarriesClosedRow` as what it
exercises — accurate: that guard fires only on a status the pre-flip run has
not yet written, so no single run can cover both. Collapsing to one run before
the flip loses the missing-`**Closed**`-row check on this file until some
later pass happens to re-scan the directory, which is the luck model `#0478`
removed; collapsing to one run after the flip is the original defect. Two is
the minimum. What the text does not say is that the second run is nearly free
— `internal/db` measured 0.641s for the implementer and 0.533s for me — so a
reader is left to infer the cost from the "cheap package" framing one step
earlier in phase 2. Worth a clause the next time the file is edited; not worth
a bounce.

**The bounce branch reads correctly after the renumbering.** Step 4's bounce
bullet sets **Status** to `open`, so the file stays in the guards' status
scope throughout and its `## Review notes` is in their section scope too; step
5's bounce sub-bullet says so in one sentence and hands off to step 6, which
carries the bounce message and the return to the orchestrator. Nothing about
that branch changed except which number commits it.

**The renumbering is clean.** One cross-reference in `issues/Issues.md` names
phase 3 steps by number — the filing-path note's "phase 2 step 8 or phase 3
step 3/5" — and both of those are unmoved, since only the commit shifted from
4 to 6. No other reference in the file names a phase-3 step above 3, and
`CLAUDE.md` names no step numbers at all. Criterion 6 is met at both sites and
the phrase it replaced survives nowhere in either file. Criterion 4 holds by
construction: `9f360c3` touches one Markdown file, 7 insertions and 4
deletions, no mechanism.

**Where a hurried agent could still misread it.** Two places, both worth
naming even though neither is a defect. First, the approve path's second run
lives in the middle of a long prose bullet, after the sentence beginning "Only
once this run is clean" — an agent that reads step 5's bolded lead sentence,
sees the `scripts/check.sh` command line, and runs it will do the right thing
once and may never reach the instruction to flip and run again. The
information is present and correctly ordered; it is the density that is the
risk, and splitting the approve bullet into two ordered sub-steps would remove
it entirely. Second, the flip's absence from step 4 is signposted only in step
4 itself — an agent that already knows the old flow may flip the status from
habit before reading that far. The bolded "Leave Status at `in-progress` for
now" is placed exactly where that agent would be looking, which is the right
mitigation, and I found it sufficient in practice.
