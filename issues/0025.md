## Description

The `subscribers` and `subscriber_interests` tables, holding list membership independently of any user account, plus the consent evidence that makes the list defensible.

## Root cause

Greenfield feature work: the mailing list's core tables didn't exist. `#0026`–`#0034` and `#0040` all build directly on this schema, so getting the status vocabulary, token generation, email normalization, and cascade behavior right here was the point of the issue.

## Fix

Added `migrations/000010_create_subscribers.{up,down}.sql`, numbered after `000009`/`#0023` because `subscriber_interests.interest_id` references `interests`. Per PRD §6.2 exactly: `subscribers` with all consent columns (`signup_ip INET`, `signup_user_agent`, `utm_source/medium/campaign`, `created_at`, `confirmed_at`), both token columns (`confirm_token`, `manage_token`) `UNIQUE`, and the unsubscribe columns (`unsubscribed_at`, `unsubscribe_source`). Added three CHECK constraints beyond the PRD's literal DDL, each backing an acceptance criterion at the database level rather than only in Go: `subscribers_status_check` (the five-value status vocabulary), `subscribers_unsubscribe_source_check` (the four-value source vocabulary), and `subscribers_email_normalized` (`email = lower(trim(email))`). All three indexes from the PRD are present, including the partial `idx_subscribers_confirm_expires ... WHERE confirm_token IS NOT NULL`. `subscriber_interests` has the composite PK and `ON DELETE CASCADE` on both FKs.

Added `internal/subscribers/tokens.go`: `newToken()` generates 32 random bytes via `crypto/rand`, base64url-encoded — the same shape as `internal/auth/tokens.go`'s `randomURLToken`, reimplemented locally rather than importing from `internal/auth` since that package is another subagent's concurrent work area this session and its exported surface doesn't currently expose the helper anyway.

Added `internal/subscribers/store.go`: `Create` (normalizes email via `lower(trim(...))` in Go before every write, generates both tokens, populates every consent column from the `NewSignup` input — never leaves them to be backfilled later), `FindByEmail`/`FindByConfirmToken`/`FindByManageToken`, `Confirm` (transactional `SELECT ... FOR UPDATE` then `UPDATE`, so a double-clicked confirmation link can't race; validates the TTL; refuses to reactivate a `complained` subscriber with `ErrComplainedLocked`), `Unsubscribe` (idempotent, records `unsubscribe_source`), `SetInterests` (delete-then-insert in one transaction; a nil/empty slice is valid and simply clears all associations, per PRD §6.1's "zero interests is a valid state"), `InterestIDs`, and `MarkBounced`/`MarkComplained`.

**Fix pass (commit `5ce8339`, review bounce).** The original claim above — "no method in the package ever transitions a subscriber out of `complained`" — was false: `Unsubscribe` and the shared `setStatus` (backing `MarkBounced`/`MarkComplained`) wrote `status` unconditionally, so `MarkComplained` → `Unsubscribe` overwrote a recorded complaint with `unsubscribed`, after which `Confirm` no longer saw `complained` and could reach `active`. Reproduced against a real database before making any change (see `## Verification`).

Fixed by adding one constant, `statusLockedFromNonAdmin = StatusComplained`, and routing every non-admin status write through it:
- `Unsubscribe`'s `UPDATE` now sets `status`/`unsubscribed_at`/`unsubscribe_source`/`updated_at` via `CASE WHEN status = $lock THEN <unchanged> ELSE <new value> END` — a single round trip, no separate guard query. On a `complained` row this is a genuine no-op: the row is returned unchanged and **no error is returned**, because PRD §6.5 requires the one-click unsubscribe endpoint (`#0034`, unauthenticated POST from a mail provider) to answer a neutral `200` for every token state — an error here isn't something that caller could act on.
- `setStatus` (shared by `MarkBounced` and `MarkComplained`) got the identical `CASE`-guarded `UPDATE`. `MarkBounced` on a `complained` row is now also a silent no-op, for the same webhook-contract reason (SES bounce/complaint notifications must be acknowledged, not failed). `MarkComplained` on an already-`complained` row is trivially a no-op either way since it's setting the same value.
- Added `Store.AdminClearComplaint(ctx, id, now)` — the one method in the package permitted to move a subscriber out of `complained` (CLAUDE.md §9's admin-only exception), intended for `#0032`. It requires the current status to actually be `complained` (`ErrNotComplained` otherwise, disambiguated from `ErrNotFound` via a new unexported `findByID`), and resets to `unsubscribed` with `unsubscribe_source='admin'` — a conservative default that lifts the complained lock without silently resuming sends; `#0032` can choose a different resulting status later if warranted.
- Corrected the package doc comment (previously asserted the same false invariant as the old Fix text above) to state the actual guarantee: every status mutator except `AdminClearComplaint` is guarded, centrally, through `statusLockedFromNonAdmin`.

`Confirm`'s existing `ErrComplainedLocked` guard was already correct and is unchanged by this pass.

## Gotchas

- `internal/auth` and `internal/mailing` were off-limits this session (a concurrent subagent's in-flight SES mailer work). `internal/subscribers` reimplements the same `crypto/rand` → base64url token pattern already in `internal/auth/tokens.go` rather than importing it, since that package wasn't touchable and its token helper is unexported anyway. If `#0026` or later work wants a single shared token helper, extracting one to a neutral package (e.g. `internal/tokens`) is a reasonable small follow-up, not done here to stay in scope.
- `Confirm`'s complained-lock guard only fires when a `complained` subscriber still happens to have a live, unconsumed `confirm_token` — plausible if SES reports a complaint on the confirmation email itself before the recipient ever clicks confirm. Tested directly by forcing that exact state via a raw `UPDATE` in `TestConfirm_ComplainedNeverAutoResubscribes`.
- The `interests` table seeds data from its own migration, so its tests can't `TRUNCATE` between runs the way `subscribers`/`subscriber_interests` tests do; `internal/subscribers`' tests resolve seeded taxonomy rows by slug (`seededInterestID`) instead of creating their own, and truncating `subscribers`/`subscriber_interests` is safe since neither carries seed data.
- **Superseded by the fix pass:** this bullet originally read "No `Reactivate` (or any complained→active transition) method exists anywhere in this package," and the package doc comment and Fix section made the same claim about *every* mutator. Both were wrong — `Unsubscribe` and `setStatus` moved a subscriber out of `complained` without anyone intending it to, purely because their `UPDATE`s never checked current status. See `## Verification`'s "Fix pass" subsection for the reproduction and `## Fix`'s "Fix pass" paragraph for the correction. The lesson: an invariant stated in a doc comment and never tested is a claim, not a guarantee — `TestConfirm_ComplainedNeverAutoResubscribes` proved `Confirm` was safe; nothing proved the other three writers were, and one of them wasn't.
- **Database-level enforcement of the transition rule: considered, not added.** The four existing CHECK constraints (`subscribers_status_check`, `subscribers_unsubscribe_source_check`, `subscribers_email_normalized`, plus the UNIQUEs) all validate a *value* against a static rule — they need only `NEW`, not `OLD`. "Never leave `complained` except via an explicit admin action" is a *transition* rule: a CHECK constraint cannot see the previous row, so expressing this at the database would require a `BEFORE UPDATE` trigger, which then needs some way to distinguish an admin call from a non-admin one (a session GUC like `SET LOCAL app.admin_override`, a separate privileged role, or similar) since triggers fire for every writer regardless of which Go method issued the `UPDATE`. That escape-hatch mechanism doesn't have a caller yet — `#0032`'s admin screen, the only legitimate user of it, isn't built. Building the trigger now means either guessing its shape (real risk of getting the escape hatch wrong and quietly reintroducing this exact bug, just at the database layer instead of the Go layer, discoverable only by a raw `psql` test) or leaving it unable to be bypassed at all, which would make `AdminClearComplaint` itself fail once `#0032` calls it. Chose instead to centralize the guard in Go, in one place (`statusLockedFromNonAdmin`, consulted by `setStatus` and `Unsubscribe`), which is exactly the kind of single-point-of-truth the four CHECK constraints achieve for static rules — just expressed at the layer where the "who is calling" distinction actually exists. Revisit this once `#0032` lands: at that point the admin path is concrete and a trigger with a real, tested escape hatch becomes tractable instead of speculative.
- **The admin path to clear `complained`:** `Store.AdminClearComplaint(ctx, id, now)`, added in the fix pass. It is the only method in the package that does not consult `statusLockedFromNonAdmin`. It requires the subscriber to currently be `complained` (returns `ErrNotComplained` otherwise, `ErrNotFound` if the id doesn't exist), and resets status to `unsubscribed` with `unsubscribe_source='admin'` rather than directly to `active` — clearing the lock is not the same as re-establishing the double opt-in consent PRD §6.3 requires before mail resumes, so the subscriber lands in the same state a normal unsubscribe would leave them in, able to resubscribe through the ordinary flow. `#0032` is free to choose a different resulting status; this is documented as a conservative default, not a fixed contract. Covered by `TestAdminClearComplaint_Success` (also proves the row is genuinely unlocked afterward, by calling `Unsubscribe` on it post-clear and confirming it's no longer a no-op), `TestAdminClearComplaint_NotComplained`, `TestAdminClearComplaint_NotFound`.

PRD §6.2. **Do not strip Gmail dots or `+tag` suffixes.** They are distinct addresses per RFC and people use them deliberately to segment their own mail; normalizing them merges accounts that should stay separate.

The consent columns are not bookkeeping — signup IP, signup user agent, signup timestamp, and confirmation timestamp are the record produced if a deliverability complaint ever needs answering. Populate them from the start.

Tokens are 32 random bytes from `crypto/rand`, base64url-encoded — not an HMAC of the email. Random tokens are revocable by rotating the column and leak nothing if a URL ends up in a referrer header or a screenshot.
