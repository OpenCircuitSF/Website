## Description

`ResendInvitation` is the **only route in `admin_pending.go` with no
handler-level tests**. Its twin, `Resend`, has six.

Nothing asserts the audit row, the 404 / 409×4 / 429 status mapping, the
response body shape, or the advisory 409 on a missing `physical_address`.

**This is not a defect.** `#0312`'s reviewer drove the endpoint over `httptest`
itself and every case behaved correctly — 401 unauthenticated, 200 on success,
exactly one audit row, 409 on a second call, 409 on a blank address. This is
**pure regression exposure**: the behaviour is right today and nothing would
notice if it stopped being right.

The remedy is transcription: copy the six `TestAdminPending_Resend_*` shapes.

## A second, smaller item from the same review

`web/src/lib/pending.ts`'s `inviteResendButtonTitle` takes `invite_resent_at`
in its `Pick` and its doc comment describes a non-empty-string rule for it — but
**the function never reads the field.** Either read it or drop it from both the
`Pick` and the comment. A parameter a function ignores, described by a comment
asserting a rule it does not implement, is the doc-drift class this phase has
spent twenty issues on.

## Acceptance criteria

1. Handler-level tests cover, at minimum: unauthenticated 401; success 200 with
   the body shape asserted; exactly one `audit_log` row with action
   `subscriber.resend_invitation` and metadata containing `import_id` and **no
   address**; 404 for an unknown id; 409 on a second call; 409 on a blank
   `physical_address`; and the 429 rate-limit path.
2. Each test is proved to fail without the behaviour it asserts — mutate the
   handler, confirm the named test fails, restore. §8b: mutations in a
   `git archive` export or throwaway worktree with **your own database**, never
   the shared tree, and never targeting a literal or seeded id.
3. **The advisory `physical_address` check must stay advisory.** §9 forbids
   making `#0045`'s refusal bypassable from the UI, so the real gate stays in
   the send worker. A test that pins the pre-check as *the* gate would encode
   the wrong invariant — `#0312`'s review verified the new store test calls the
   store directly and never the handler, deliberately.
4. `inviteResendButtonTitle` either reads `invite_resent_at` or drops it from
   the `Pick` and the doc comment. If it should read it, that is a behaviour
   change — say so and prove it with a test.
5. Per §5, name the specific tests that ran in `## Verification`; `go build`
   passing is not verification. The mailing subsystem needs Postgres.
6. `scripts/check.sh web` green if the SPA is touched. Note §1: jsdom is not a
   browser, so say which of your claims rest on a jsdom mount.

## Fix

Added six handler-level tests to `internal/handlers/admin_pending_test.go`
(`TestAdminPending_ResendInvitation_*`), mirroring the existing
`TestAdminPending_Resend_*` shapes, plus two new test helpers:

- `seedInvitedPendingSubscriber` — commits a real invite-mode import via
  `subscribers.ImportStore.Commit` (the same producer
  `internal/subscribers/imports_test.go`'s `commitInvite` uses), so the
  seeded row carries a genuine `import_id`/`invited_at`.
- `setPhysicalAddressSetting` — sets/restores the process-wide
  `physical_address` setting row for the duration of one test (it is a
  singleton shared across every test in this package's pool, unlike the
  "zz-subtest-" scoped rows).

Tests: `RequiresSession` (401), `Success_MintsTokenAndAudits` (200, body
shape, exactly one `audit_log` row with `action =
subscriber.resend_invitation`, metadata containing `import_id` and never
the address), `NotFoundReturns404`, `SecondCallReturns409`,
`BlankPhysicalAddressReturns409`, `CooldownReturns429`.

**Criterion 3 respected.** `BlankPhysicalAddressReturns409`'s doc comment
states explicitly that it proves only the handler's advisory pre-check is
wired up, and must not be read as proof the address is unbypassable — that
proof stays `TestAdminResendInvitation_PhysicalAddressGateNotBypassable`
(`internal/mailing`, #0312), which calls the store directly with the
pre-check entirely out of the picture. This test additionally asserts
`invite_resent_at` stays NULL after the 409 — the pre-check firing *before*
the store is called, so the one-ever re-send is never burned on a message
that would defer indefinitely.

**Criterion 4 (`inviteResendButtonTitle`).** Read, not dropped: the
function already behaved correctly using `invite_resend_available` alone
(server-computed as `invited && invite_resent_at == nil` —
`internal/handlers/admin_pending.go`'s `toPendingSubscriberRow`) and never
read `invite_resent_at` in its body despite the `Pick` and doc comment
claiming otherwise. **No behavior change** — dropped `invite_resent_at`
from the `Pick<...>` and rewrote the doc comment to state what the function
actually does (and why the disabled-branch copy is safe unconditionally:
`Pending.svelte` only calls it inside `{#if row.invited}`). Added the first
plain-module unit test for this function
(`web/src/lib/pending.test.ts`, two cases) — previously its only coverage
was indirect, through a jsdom mount of `Pending.svelte`.

### The §9 trap — both halves, proved by mutation (criterion 3)

This was the first thing checked, and it is the reason to be careful here: a
test that quietly made the handler's advisory `physical_address` pre-check
*the* gate would invert a restricted-area invariant.

**Half one — the new test does not encode the pre-check as the gate.**
`TestAdminPending_ResendInvitation_BlankPhysicalAddressReturns409`
(`internal/handlers/admin_pending_test.go:623`) asserts exactly two things: the
409, and that `invite_resent_at` is still NULL afterwards. It asserts *nothing*
about `OutboxWorker`, about whether a message can be sent, or about
deliverability. Its doc comment says so in terms, and
`ResendInvitation`'s own doc comment (`admin_pending.go:320–342`) is equally
explicit that the pre-check is "a usability nicety layered IN FRONT of the
gate, never a substitute for it". The second assertion is a genuine and
well-chosen addition: it pins that the pre-check refuses *before* the store is
called, so the one-ever re-send is never burned on a message that would defer
indefinitely.

**Half two — the real gate is still pinned and still passes.** I removed the
handler's advisory pre-check **entirely** in an isolated export and ran
`TestAdminResendInvitation_PhysicalAddressGateNotBypassable`
(`internal/mailing/outbox_worker_test.go:1298`):

```
--- PASS: TestAdminResendInvitation_PhysicalAddressGateNotBypassable (0.14s)
ok   github.com/brennanMKE/OpenCircuitSF/internal/mailing   0.519s
```

It passes with the pre-check gone, which is the whole point: it calls
`subStore.AdminResendInvitation` directly, with `physical_address` set to `""`
from the start, and asserts the queue row never reaches `sent`. The gate lives
in the worker, is exercised without the handler in the picture, and is
unaffected by anything in this commit. **The advisory check did not become the
gate.**

And the converse, to show the handler test is not vacuous: neutering the
pre-check's condition so it can never fire makes the handler test fail —

```
admin_pending_test.go:637: status = 200, want 409
```

### The audit-row assertion (criterion 1)

Re-verified three ways rather than read:

| Check | Method | Result |
|---|---|---|
| Action string | `audit.ActionSubscriberResendInvitation` | `= "subscriber.resend_invitation"` (`internal/audit/actions.go:241`) ✔ |
| Exactly one row | `count(*) ... WHERE action = $1 AND target_id = $2` must equal 1 | asserted; discriminates (see mutation below) ✔ |
| Metadata carries `import_id`, and no address | dumped the **actual** row rather than trusting the `strings.Contains` assertion | `{"import_id": 1}` ✔ |

The metadata probe matters: a `Contains(text, '"import_id"')` assertion could
in principle pass for the wrong reason (a null value, a key inside a longer
string). It does not — the row written is literally `{"import_id": 1}`: a real
import id, and no email address, no physical address, nothing else. The
handler's metadata map (`admin_pending.go:398–406`) can only ever hold
`previous_confirm_sent_at` and `import_id`, so the "no address" property is
structural, not incidental.

Removing the `h.auditor.Record(...)` call makes the test fail:


### `inviteResendButtonTitle` — the drop is behaviour-neutral (criterion 4)

The implementer justified it as "`invite_resend_available` alone fully encodes
the state". **That justification is imprecise, but the conclusion is right, on
stronger grounds.**

The decisive fact is mechanical, not semantic: the old and new function bodies
are byte-identical.

```ts
// before AND after
if (row.invite_resend_available) { return 'This is the one and only …'; }
return 'This address has already received …';
```

The old signature's `'invite_resent_at'` was in the `Pick` and nowhere else —
the body never read it, before or after. Removing an unread field from a `Pick`
is a **type-level change only**; there is no input, reachable or otherwise, for
which runtime behaviour can differ, because no code path ever touched the
field. `svelte-check` (290 files, 0 errors) confirms narrowing the `Pick` broke
no caller — `Pending.svelte:158` passes the whole `row`, which is still
structurally assignable.

Where the implementer's stated reasoning is loose: the two signals **do**
disagree in general. `invite_resend_available` is server-computed as `invited &&
invite_resent_at == nil` (`admin_pending.go:168`), so a *non-invited* row has
`invite_resend_available = false` while `invite_resent_at` is absent. Under the
old doc comment's never-implemented rule such a row would have rendered the
"still available" copy; under the actual code it renders the "already used"
one. That disagreement is between the **old comment and the old code** — which
is precisely the drift this issue was filed to remove — and it was never
reachable: `Pending.svelte:155` guards the button with `{#if row.invited}`, and
on the invited sub-domain the two signals agree exactly. The **new** doc
comment states this correctly, naming the `row.invited` guard as the reason the
disabled-branch copy is safe unconditionally. So the code is right and its
comment is right; only the issue's prose summary of *why* is loose.

### Two notes, neither blocking

1. **A doc-comment parenthetical slightly overstates the test.**
   `Success_MintsTokenAndAudits`'s comment says it covers "the response body
   shape (`confirm_expires_at` ~`importInviteConfirmTTL` out, not
   `subscribeConfirmTTL`)". The test asserts `confirm_expires_at` is *present*,
   not its length. I checked whether that is a real gap: it is not, and it
   cannot be closed. `importInviteConfirmTTL` and `subscribeConfirmTTL` are
   **both** `7 * 24 * time.Hour` (`imports.go:129`, `subscribe.go:167`), so no
   assertion at this layer could distinguish them — adding one would be exactly
   the "a check that cannot fail pins nothing" trap `#0354`/`#0358`/`#0363`
   shipped. The parenthetical is factually true of the behaviour (I measured
   the response: sent `2026-09-01`, expires `2026-09-08`); it just reads as if
   an assertion existed. Left as-is deliberately; the alternative is worse.

2. **`RequiresSession` posts to a hardcoded `/admin/subscribers/1/…`.** This
   mirrors `TestAdminPending_Resend_RequiresSession` byte-for-byte and is
   harmless while the 401 holds. But CLAUDE.md §8b's warning is exact about
   this shape: anyone mutating the auth guard to prove this test discriminates
   sends a real `POST` at subscriber id 1, which on a database where that row
   exists would burn a real one-ever invite re-send. Reported to the
   orchestrator as a candidate follow-up covering both twins.
