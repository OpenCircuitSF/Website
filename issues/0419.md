## Description

`docs/seo.md` opens:

> Not yet implemented — lands with the public marketing pages (Phase 2) and
> is refined in Phase 7. This is a stub with real headings pending that
> work; `PRD.md` §7.4 is authoritative

`internal/seo` has been fully built for many issues now — per-route meta
injection, the workshop source, Event JSON-LD, the sitemap, `robots.txt`, the
archive integration, the invalidator seams, and most recently `#0273`'s
server-side per-workshop Open Graph card. `#0273` itself added 56 lines to this
file **underneath a heading still declaring the subsystem unbuilt.**

The file is 115 lines. It is not empty — it is a stub that grew, so a reader is
told the subsystem does not exist and then handed real detail about it.

**Reported independently by both `#0273`'s implementation pass and its review.**

## Root cause

`docs/seo.md` was written as a stub before `internal/seo` existed and was
never rewritten once it did — it only ever accreted new sections
underneath its original "Not yet implemented" heading (`#0273`'s +56
lines being the most recent instance) rather than being checked against
the code and revised. `PRD.md` §7.4, which the stub cited as
authoritative, has the identical problem: it still describes the
pre-implementation plan and was never updated as the subsystem was
actually built, so pointing a reader at it as ground truth was itself
part of the defect.

## Fix

Rewrote `docs/seo.md` in full against `internal/seo`'s current source
(`seo.go`, `site.go`, `jsonld.go`, `sitemap.go`, `robots.go`, `card.go`,
`workshop.go`, `archive.go`) rather than editing around the stale
heading, per criterion 2 — every factual claim in the new file was
checked against the code, not carried over from the previous draft or
from this issue's own description of what landed. Covers, as required by
criterion 4: per-route meta injection and its token list, the workshop
and archive sources, `#0055`'s Event JSON-LD (including the deliberate
divergence between a canceled workshop's JSON-LD and its social-card
fallback), the sitemap and `robots.txt`, `Site.Invalidate`'s three caches
and three callers, and `#0273`'s per-workshop card generation with its
Pacific-time rendering.

Per criterion 5, added a `## Deliberate limits` section recording three
settled decisions read from their own issues rather than paraphrased
from this issue's description: `#0153`'s no-cover-image-upload-in-v1
decision and its reasoning (volume, first-mutable-data-directory, no S3
yet) plus what would reopen it (`#0232`); `#0135`'s ruling that a
canceled workshop's card/sitemap presence stays generic even though its
JSON-LD is real and per-workshop; and `#0273`'s `og:type: website`
decision with its full reasoning (no OG `event` type, `article` implies
editorial content, `article:published_time` is a publication date not an
event date, the event semantics already live in the JSON-LD).

Per criterion 3, checked whether `PRD.md` §7.4 is still accurate rather
than deferring to it: it isn't. Added a closing `## PRD §7.4 is out of
date` section in `docs/seo.md` naming six specific ways it has drifted
(missing the archive source and `#0123` entirely, missing
`twitter:title`/`twitter:description` and the JSON-LD token, describing

itself was not edited — a concurrent pass owns it this session

One inherited error was corrected while verifying claims against the
code: the previous draft listed `GET /favicon.svg` under "Also planned"

serves it as an ordinary embedded static file from `web/dist/`, the same

No code changed — this issue is documentation only, per criterion 6 (no
mechanism).

### What must change — 1: the opening sentence claims a deployment state

The file's opening sentence reads "`internal/seo` is built and live", and then enumerates
`#0273`'s card among the things that are live. In this repository "live" is
not a loose word: `CLAUDE.md` §7 records exactly what production serves, and
production runs `ef0a58f` (2026-08-25). `#0123`'s archive source landed
2026-08-27, `#0319`'s widened invalidation and `#0273`'s card route landed
later still — `#0273`'s own acceptance criterion 9 is unticked with the deploy
named as its blocker, and its obstacle 5 says outright "Production is not
running this code". A reader who takes the sentence at face value will `curl`
`/workshops/{slug}/og.png` against the box, get a 404, and file a bug against
working code.

Replace the first paragraph with:

> `internal/seo` is fully built: per-route meta injection, `sitemap.xml`,
> `robots.txt`, schema.org `Event` JSON-LD, the archive source (`#0123`), and
> (`#0273`) a generated per-workshop Open Graph card. This document describes
> the subsystem as it exists in this tree — every claim below was checked
> against the package's source, not against the previous draft of this file.
> It deliberately says nothing about what is deployed; `CLAUDE.md` §7 is the
> record of what production runs, and parts of what follows post-date it.

Do not substitute a dated "as of today, production runs X" sentence for that
last line. A hardcoded deploy state in this file is the same drift the issue
was filed about, one deploy later.

### What must change — 2: the archive interface's contract is misstated

The "Workshop and archive sources" section says:

> Each interface returns every row regardless of status — status filtering
> (published-only, published-or-canceled, etc.) happens in `internal/seo`
> itself, so it is exercised by `go test ./internal/seo/...` rather than
> trusted to whatever the real store's `WHERE` clause happens to do.

That is true of `WorkshopSource`, whose own doc comment says "Deliberately
returns ALL workshops (every status)", and true of
`ArchiveSource.ArchiveEntryBySlug`. It is the opposite of the truth for
`ArchiveSource.ArchiveEntries`, whose doc comment says "Deliberately returns
ALL published entries (never draft/pending/withheld)" and whose method
comment reads "ArchiveEntries returns every published campaign". The real
adapter, `campaignArchiveSEOSource.ArchiveEntries`, delegates to
`mailing.CampaignStore.ListArchived`, which filters `archive_status =
'published'` in SQL, and that adapter's own doc comment states that
`Sitemap.Build`'s `Published` check "is a no-op in practice for this list".

So for the one path where withheld campaigns are actually kept out of
`sitemap.xml`, the exclusion *is* trusted to the store's `WHERE` clause — the
exact arrangement the sentence claims does not exist. This is the failure
class the issue was filed against: prose asserting a stronger verification
property than the code delivers.

Replace that sentence (from "Each interface returns" through "happens to do.")
with:

> `WorkshopSource` deliberately returns every workshop of every status, and so
> does `ArchiveSource.ArchiveEntryBySlug` for its single row: the
> published-only and published-or-canceled filtering happens in `internal/seo`
> itself, so `go test ./internal/seo/...` exercises it rather than trusting
> whatever the real store's `WHERE` clause happens to do.
> `ArchiveSource.ArchiveEntries` is the deliberate exception — it is specified
> to return only published campaigns, and the real adapter gets that from
> `mailing.CampaignStore.ListArchived`'s own `archive_status = 'published'`
> filter — so `Sitemap.Build`'s `Published` check over that list is defence in
> depth rather than the primary exclusion.

### Two smaller corrections to make in the same pass
