## Description

`internal/subscribers/imports_test.go` calls
`store.Revoke(ctx, 1, "   ", …)` — a **hardcoded import id**.

Today the blank-reason check returns before `pool.Begin`, so nothing is reached.
**But that check is precisely what a mutation proving this test discriminates
would remove** — and `ImportStore.Revoke` then runs the full transaction against
import **id 1**: unsubscribing every subscriber attributed to it and flipping it
to `revoked`.

**Found the hard way.** `#0383`/`#0385`'s reviewer hit this while performing
exactly that mutation. It was harmless only because its private database had no
row with id 1.

**This is the shape `#0372` and `#0376` swept for, and it was missed** because
the id is a **Go function argument**, not a URL path — both surveys keyed on
request paths.

§8b exists because of this class: `#0024`'s guard-removal proof aimed a `DELETE`
at a hardcoded `/admin/interests/1` and permanently destroyed a seeded taxonomy
row.

The sibling `TestImportStore_Revoke_UnknownID` uses id `0`, which is safe.

## Root cause

`TestImportStore_Revoke_RequiresReason` (`internal/subscribers/imports_test.go`)
called `store.Revoke(context.Background(), 1, "   ", time.Now())` directly, with
no row of its own backing that id. `ImportStore.Revoke`
(`internal/subscribers/imports.go`) checks `reason == ""` and returns
`ErrRevokeReasonRequired` before ever calling `pool.Begin`, so today the literal
`1` is never read. But that check is precisely the line a mutation-testing pass
proving this test discriminates would remove, and with it gone `Revoke` runs its
full transaction against whatever import id 1 is: `SELECT ... FOR UPDATE`,
unsubscribing every attributed subscriber, and marking the import `revoked`.

## Fix

Chose **the seeded throwaway row**, not a nonexistent sentinel (`#0376`'s
`999999999`). The two are not equivalent here: a sentinel only proves the guard
fires *before a lookup returns not-found* — with the guard removed, a
nonexistent id still produces a different-but-harmless outcome
(`ErrImportNotFound`), so a test built that way could not detect the guard's
removal via the destructive path at all, only via the error's identity. The
side effect this guard is standing in front of is destructive (revoke +
mass-unsubscribe), so the test needs to prove the guard fires **before that
side effect reaches a real row** — which requires the row to be real.

The rewritten test seeds one throwaway import via `store.Commit` (using the
existing `validCommitInput`/`uniqueImportEmail` helpers already used
throughout this file) and calls `Revoke` against its own id with a blank
reason. It then asserts, beyond the error value, that the seeded import's
`Status` is not `revoked` and that its subscriber's `Status` is not
`unsubscribed` — those two assertions are what make the guard's *ordering*
(before the side effect, not just before the return) provable, and what fail
when the guard is removed (see `## Verification`'s mutation proof).

### Criterion 1 — seeded row vs sentinel, judged empirically rather than from prose

The implementer's argument is that a sentinel would prove the guard fires
before a *lookup* but not before the *side effect*. I did not take that on
trust — I measured the counterfactual. In the mutated export (blank-reason
guard removed) I ran a throwaway probe calling
`Revoke(ctx, 999999999, "   ", now)`:

```
sentinel 999999999 + blank reason, guard removed -> err = subscribers: import not found
errors.Is ErrImportNotFound        = true
errors.Is ErrRevokeReasonRequired  = false
```

So a sentinel-based test **would** still fail on guard removal — but only on
the *identity of the error*, having already opened a transaction and run
`SELECT … FOR UPDATE` before finding nothing. It would demonstrate nothing
about ordering relative to the destructive work. The `## Fix` prose says
exactly this and is accurate.

**The seeded row is what makes the ordering property observable**, and the
ordering is the real subject: `ImportStore.Revoke`'s guard is the function's
own first statement, sitting directly in front of `pool.Begin`, the
`FOR UPDATE` lock, the mass-unsubscribe loop and the status flip. Only a row
that actually exists exercises that path.

**This correctly differs from `#0376`, and the difference is not drift.**
There the guards were structurally *upstream* of the store call —
`RequireAdmin` in `adminImportsMux`'s middleware chain, and the handler's own
`reason == ""` check before `h.store.Revoke` — so the request could not reach
a row whatever id it named, and a sentinel was both sufficient as proof and
strictly safer (it avoided even creating a draft row). Here the guard is
*inside* the destructive function. Same class of defect, two different
remedies, each matched to where its guard sits. **Not over-engineered**: the
cost is one `store.Commit` and two reads, against a genuinely stronger
property.

Verified the assertion is not vacuous: `validCommitInput` uses
`ConsentModePriorConsent`, so the seeded subscriber lands `active` with
`consent_basis = imported_prior_consent` — precisely one of the two statuses
Revoke's target `SELECT` matches (`status = pending OR (status = active AND
consent_basis = imported_prior_consent)`). A seed landing outside that set
would have made the subscriber assertion unfireable; this one is inside it,
and the mutation run below proves it fires.

### Criterion 3, spot-check — the in-process-store category, which is where a mistake would hide

This was the category worth attacking, since an "in-memory" store that turned
out to be Postgres-backed would be a live hazard. It is not, and the evidence
is structural rather than a judgement call:

- **`internal/devstore`** — `grep` for `pgx`, `database/sql`, `pgxpool`,
  `pool`, `TEST_DATABASE_URL` across the entire package returns **nothing**.
  `Store` holds a `map` of sessions and a slice of users behind a mutex. Both
  flagged methods **ignore the context entirely** —
  `DeleteSessionsForUser(_ context.Context, …)` and
  `DeactivateUser(_ context.Context, …)` — so there is no code path by which
  they could reach a database. Every one of the 7 constructions in
  `devstore_test.go` is a fresh `devstore.New(…)`; `id 1` is the mock admin
  that `New` itself seeds into that private instance. Not a shared row, and
  not reachable from Postgres.
- **`internal/events`** — same `grep`, same empty result. The broker's ids are
  pub/sub topic keys; `Subscribe`/`Publish`/`Unsubscribe` take **no context at
  all**. Per-test broker, no persistence.

The implementer's classification of this category is correct.
