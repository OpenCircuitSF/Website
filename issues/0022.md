The route the router falls through to, styled as a terminal error rather than a browser default.

## Root cause

Two related but separable gaps: no client-side 404 view existed, and the Go
SPA handler returned 200 for literally every unmatched path (the naive SPA
catch-all this issue's Notes warn against) because it had no concept of which
paths were real routes.

## Fix

**Client (`web/src/views/NotFound.svelte`)**: a `TerminalPanel title="404"`
composing `Prompt text="open_circuit // not_found"`, an `<h1>404 // Not
Found</h1>`, a `CommandLine command="open {$currentRoute.path}"` showing the
actual attempted path (read from the router's `currentRoute` store, `#0014`),
a `bash: {path}: command not found` line, and links to `/` and `/workshops`.
Wired into `App.svelte` for `$currentRoute.name === 'not-found'`.

**Server (`internal/handlers/routes.go`, new)**: `knownStaticRoutes` (a
`map[string]bool`) and `workshopDetailPattern` (a regex) mirror
`web/src/lib/router.ts`'s `STATIC_ROUTES`/`WORKSHOP_DETAIL` exactly, entry
for entry — **by hand, and enforced by nothing. Corrected at review,
2026-08-18:** this file's doc comment claims `#0019` reusing the table keeps
the two "in sync by construction rather than by convention". That is true of
Go-to-Go reuse and false of the Go-to-TypeScript relationship, which is the
one that matters here. The reviewer added `/privacy` to `STATIC_ROUTES` alone,
and separately `/sponsors` to `knownStaticRoutes` alone, in a throwaway
worktree: `npm run check`, `npm test`, `go build ./...` and `go test ./...` all
passed clean in both directions. Nothing generates one table from the other and
no test fails when they diverge. See `#0071`, filed from this review, which
owns closing that gap and correcting the comment. `isKnownRoute(path)` normalizes one trailing slash the same way
`parsePath` does, then checks the static table and the dynamic pattern.
`internal/handlers/static.go`'s `SPAHandler.ServeHTTP` now calls
`isKnownRoute(r.URL.Path)` for any extensionless path with no matching
embedded file: a known route still gets the SPA shell at 200 (unchanged
behavior for real routes); anything else gets the *same* SPA shell body but
at 404. `serveIndex` was changed to take the status code as a parameter
instead of hardcoding `200` via the implicit `http.ResponseWriter` default.

The existing hashed-asset-404 behavior (an extension present but no matching
embedded file → clean `404` via `http.NotFound`, not the HTML shell) was
untouched — that logic already ran before the new `isKnownRoute` check and
still does, so `/favicon.ico` and a missing bundle both still 404 as assets,
not as HTML.

## Notes

PRD §5.1. Returning 200 for every unknown path — the naive SPA catch-all — makes every typo an indexable soft-404. The handler needs the same route table #0019 uses so it can distinguish a real route from a miss.

Hashed asset paths must still 404 as assets, not fall through to the SPA shell, or a missing bundle silently returns HTML and produces a confusing MIME error in the console.

**A note on how the SPA-shell-with-404 works and what it costs.** The 404 body
is byte-identical to the 200 body — the status code is the only signal. That is
the right trade today, but it is exactly why `#0019`'s carried-in criteria
below matter: once meta injection exists, an unknown path must keep the 404
status *and* get default metadata, or the two halves of this fix stop agreeing.

**Not verified here:** whether crawlers honour the 404 in practice — an
operational outcome, not testable in this environment.
