## Resolution

**Root cause: a spare client connection, not a worker.** No background
worker, outreach or otherwise, touches this test's rows. What failed is the
server shutdown step, and the cause is on the test's client side.

The test used `&http.Client{Timeout: ...}`, which shares
`http.DefaultTransport`. When the POST is sent while the GET /health
connection is not yet back in the idle pool, the transport starts dialing a
second connection and hands the request to whichever is ready first. If the
old connection wins, the new one sits in the pool and never sends a byte. The
server sees it as `http.StateNew`, and `net/http`'s `Shutdown` counts a
`StateNew` connection as busy until it is about 5s old (Go issue 22682,
`closeIdleConns` in `net/http/server.go`). That is exactly
`shutdownServerTimeout`. So `srv.Shutdown` used its whole 5s budget,
`mountAndServe` returned an error after just over 5s, and the test's 5s wait
expired first.

**Evidence.**

- The `#0588` failure transcript (2026-10-18 16:28, load 1.4 to 3.6) has
  `#0536`'s decline line saying what held the shutdown open: listener on
  `127.0.0.1:65473`, then `srv.Shutdown did not finish within 5s ...
  1 connection(s): 127.0.0.1:65475 new`. The test makes only two requests.
  The health check took `:65474`. `:65475` was a third connection that
  never carried a request. It closed 5.08s into the test with `mountAndServe
  did not return within 5s of SIGTERM`.
- Reproduction (scratch test, since deleted). With one raw TCP connection
  opened and left silent before SIGTERM, `mountAndServe` returned after
  **5.001s** with `graceful shutdown incomplete after 5s ... 1 connection(s):
  127.0.0.1:59452 new`. Without that connection it returned in **0s**.
- Frequency (scratch test, since deleted). Against an `httptest` server
  counting connections that close without ever going active, a fresh
  default-style `http.Transport` running GET then POST dialed a spare
  connection in **2 of 300** sequences at load about 5. That is rare enough
  to pass on rerun and frequent enough to show up across a day of
  verification runs.

**Hypotheses ruled out.**

- *A worker claiming the row.* The test passes `nil` for every worker, and
  its blocking store is entered only by its own request. The only other
  goroutine in its handler is `#0254`'s intake recovery poller. That poller
  cannot pick up a fresh intake row before `intakeGraceDelay` (30s), and the
  test's `TRUNCATE subscribers ... CASCADE` also clears `outbound_queue`
  (FK) at the start. Outreach adds nothing here: `outreachPublisher` is
  `nil`.
- *A leaked goroutine from another test.* Other tests' abandoned
  `mountAndServe` instances do receive the same SIGTERM, but each one shuts
  down only its own server, and this test waits only on its own `errCh`. The
  extra `:65435 new` line in the failing log is that same spare-connection
  effect showing up in an earlier test's server. It did not cause this
  failure.
- *A silent decline.* There wasn't one. `#0536`'s line had already named
  the `new` connection. What it got wrong was the hint: it called a `new`
  connection "worth investigating" when this case is harmless.

**Fix (no deadline widened).**

- `cmd/opencircuit/ratelimit_wiring_test.go`: new `newShutdownWiringClient()`
  helper. It has its own `http.Transport` with `DisableKeepAlives: true`, so
  each request dials exactly one connection, carries exactly one request,
  and closes it. No spare connection can exist.
- `cmd/opencircuit/shutdown_wiring_test.go` and
  `cmd/opencircuit/noindex_wiring_test.go`, the two tests that SIGTERM
  `mountAndServe` and expect a prompt `nil` back, now use that helper. The
  other SIGTERM tests (`shutdown_budget`, `shutdown_decline`) expect the
  budget to expire anyway, so a spare connection cannot change their result.
- `cmd/opencircuit/shutdown_client_test.go`: new
  `TestNewShutdownWiringClient_NeverLeavesASpareConnection`. It needs no
  database. It checks what the server observes, not the client's settings:
  connections equal requests, and no connection closes without going active.
  **Mutation proof:** with the helper switched to `http.DefaultTransport`
  it fails deterministically ("client opened 2 connections for 40
  requests"). Restored, the file hash matches the copy saved aside.
- `cmd/opencircuit/main.go`: `#0536`'s shutdown-timeout log line (and its
  comment) now says a `"new"` connection has had no request read yet, that
  `net/http` holds it busy for about 5s, and that an unused pre-dialed client
  connection also produces it. A browser preconnect does the same in
  production, so the next person reading this line gets the answer from the
  line itself. The returned error text is unchanged, so `#0536`'s test
  assertions still hold.
