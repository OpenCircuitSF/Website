## Description

`#0063` settled the live-region rule and converted ten `role="status"` sites. It
enumerated a remainder of 14 `Loading…` placeholders — and did not mention that
**roughly fifty `role="alert"` regions across twenty files are created and
destroyed by `{#if}`**, the same structural shape.

Found by `#0063`'s re-review, which counted them across the tree. Public flows
are affected, not only the console: `PreferenceCenter.svelte:227`,
`Login.svelte:253/307/361`, `RecoverVerify.svelte:148`,
`RegisterVerify.svelte:148`.

**Why this is a weaker instance than the `role="status"` case**, and why the
reviewer reported it rather than bouncing `#0063`: `alert` is the one live-region
role assistive technology handles reliably **on insertion**. A node that appears
carrying alert text generally is announced, where a `status` node created at the
same moment is not. So these mostly work today.

**Why it is still worth fixing.** "Mostly works, for one role, by a different
mechanism than the rule we wrote down" is a fragile thing to leave undocumented
across fifty sites. The behaviour varies by screen reader and by whether the node
is inserted or merely re-rendered, and the codebase now contains two contradictory
patterns for the same job with nothing recording which applies where. It is also a
larger remainder than the 14 that *were* enumerated, so the enumeration reads as
more complete than it is.

## Acceptance criteria

- [ ] The `role="alert"` sites are enumerated — the count and the files, derived from the tree rather than from this issue
- [ ] A decision is recorded: convert them to the persistent-node pattern, or state explicitly that `alert`-on-insertion is relied upon and why that is sound
- [ ] Whichever is chosen, `#0242`'s AST guard covers `role="alert"` as well as `role="status"`, so the decision cannot silently rot
- [ ] Public flows are done first if the work is split — a subscriber hitting an error on `/preferences` matters more than an admin seeing one
- [ ] `scripts/check.sh web` passes

## Notes

Reported by `#0063`'s phase-3 re-review under `CLAUDE.md` §9.

**Use the compiler, not a browser.** That re-review established the right
instrument: it compiled each component with `svelte/compiler` and read the
output, confirming every conversion was `$.set_text(text_N, …)` on a node
acquired once, with no `$.if` keyed on any notice variable. That is mechanical
proof and it retires the failure mode by construction — where a browser check
only samples the paths you thought to drive. `SubscribeForm.svelte`'s original
bug was exactly a source-versus-compiled divergence, so the compiler is the
instrument that matches the defect.
