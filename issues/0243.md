## Description

`#0063` settled the live-region rule and converted ten `role="status"` sites. It
enumerated a remainder of 14 `Loading…` placeholders — and did not mention that
**roughly fifty `role="alert"` regions across twenty files are created and
destroyed by `{#if}`**, the same structural shape.

Found by `#0063`'s re-review, which counted them across the tree. Public flows
are affected, not only the console: `PreferenceCenter.svelte:227`,
`Login.svelte:253/307/361`, `RecoverVerify.svelte:148`,
`RegisterVerify.svelte:148`.

**Why this is a weaker instance than the `role="status"` case**, and why the
reviewer reported it rather than bouncing `#0063`: `alert` is the one live-region
role assistive technology handles reliably **on insertion**. A node that appears
carrying alert text generally is announced, where a `status` node created at the
same moment is not. So these mostly work today.

**Why it is still worth fixing.** "Mostly works, for one role, by a different
mechanism than the rule we wrote down" is a fragile thing to leave undocumented
across fifty sites. The behaviour varies by screen reader and by whether the node
is inserted or merely re-rendered, and the codebase now contains two contradictory
patterns for the same job with nothing recording which applies where. It is also a
larger remainder than the 14 that *were* enumerated, so the enumeration reads as
more complete than it is.

## Notes

Reported by `#0063`'s phase-3 re-review under `CLAUDE.md` §9.

**Use the compiler, not a browser.** That re-review established the right
instrument: it compiled each component with `svelte/compiler` and read the
output, confirming every conversion was `$.set_text(text_N, …)` on a node
acquired once, with no `$.if` keyed on any notice variable. That is mechanical
proof and it retires the failure mode by construction — where a browser check
only samples the paths you thought to drive. `SubscribeForm.svelte`'s original
bug was exactly a source-versus-compiled divergence, so the compiler is the
instrument that matches the defect.

## Work log

**Enumeration, derived from the tree** (`web/src/lib/liveRegionGuard.structuralGuard.test.ts`,
its own compiler-driven scan, not `grep`): **56 `role="alert"` sites across
16 files** — close to but not exactly the audit's "roughly fifty across
twenty files" estimate; the real figures are lower on files (16, not 20) and
slightly higher on sites (56, not "roughly fifty"). `grep -rn 'role="alert"'
web/src | grep -v '\.test\.ts'` independently confirms 56/16.

**Decision recorded**: kept as `{#if}`-created, not converted to the
persistent-node pattern — role="alert" is announced reliably ON INSERTION by
assistive-technology vendors (unlike `role="status"`, which needs an
already-present node to MUTATE), so the structural shape that is a defect for
`status` is sound for `alert`. This is the argument `#0063`'s re-review
already made for not bouncing on this finding; it is now the guard's own
recorded rule rather than living only in that review's prose. See
`liveRegionGuard.structuralGuard.test.ts`'s header, "The role=\"alert\"
decision" section, for the full writeup.

**Guard coverage**: built as ONE guard with `#0242` (not two), per this
issue's own criterion 3 — see `#0242`'s Work log for the shared
implementation details. The guard still requires every `role="alert"` region
resolve to real content (a dynamic expression or non-empty static text) — an
EMPTY alert region announces nothing on insertion either, so the "accept
`{#if}`-creation" decision does not become a blank check.

**Public flows were already correct, nothing to reorder**:
`PreferenceCenter.svelte:263` (line shifted from `227` by this pass's other
edits to the same file, e.g. `#0244`'s error-branch fix — same element),
`Login.svelte:253/307/361`, `RecoverVerify.svelte:148`,
`RegisterVerify.svelte:148` all pass the guard as-is — the "public flows
first" criterion doesn't require a split since no work beyond the decision +
guard was needed anywhere in the tree for `role="alert"` specifically. (The
guard's development run DID find and fix several unrelated `role="status"`
violations — see `#0242`'s Work log; none were `role="alert"` sites.)
