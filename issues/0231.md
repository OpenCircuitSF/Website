## Description

The user supplied `CRT.png` — a photograph of a Zenith Data Systems green-phosphor
monitor displaying `> Open Circuit SF _` — and wants it in the **top section of
the home page, on the right**, where the hero currently has empty space, with
the image's background blending into the page.

It is a good fit for the brand: the site's whole visual language is a terminal
motif, and this is the physical object that motif refers to. The screen even
shows the site's own name at its own prompt.

**Three things make this more than dropping in an `<img>`.** Each is measured,
not guessed.

**1. The hero's LCP element is currently the headline, by construction.**
`web/src/views/Home.svelte:10-11` says so explicitly: *"The headline is the
page's LCP element by construction: no images in the hero, just type — see PRD
§7.6's LCP budget (<2.0s on 4G)."* An above-the-fold hero image becomes the LCP
element. **The source file is 1,355 KB** — roughly five times the entire
JS bundle (239 KB raw, 75 KB gzipped). Shipping it as-is would blow the budget
outright.

**2. The site has a light theme, and the image's background is baked in.**
`web/src/app.css:21` sets `--bg-page: #F4F6F3` for light and `#0A0D0B` for dark
(`:117`, `:154`), switched by both `prefers-color-scheme` and an explicit
toggle. Sampling `CRT.png`'s edges gives a uniform **`#181d17`** at all four
corners and all three mid-edges.

That is very close to dark mode's `--bg-subtle` (`#182018`) — so on dark it will
blend almost perfectly. **On light it will be a dark rectangle in the middle of
a near-white page.** This is the same trap `CLAUDE.md` §8 records for the logo:
*"Transparency does not make a logo theme-adaptive"* — brand green measures
14.8:1 on the dark ground but 1.32:1 on white.

**3. It is a photograph of a real product.** The Zenith wordmark and "data
systems" lettering are legible on the bezel. Worth a moment's thought about
whether that matters for a marketing page; if it does not, say so and move on.

## Acceptance criteria

- [ ] The CRT image appears in the home hero's right-hand space, at desktop widths
- [ ] Its background blends into the page ground rather than reading as a pasted rectangle — **verified in both light and dark themes**, not only the one the developer happens to be using
- [ ] The narrow-viewport layout stays sound: the image either reflows sensibly or is dropped below a breakpoint, and the page never scrolls horizontally at 390 px
- [ ] Total added weight is stated in the issue and fits PRD §7.6 — the 1,355 KB source must come down substantially (a modern format, sensible dimensions, and responsive sources are the obvious levers)
- [ ] LCP on the home route is measured before and after, with the number recorded. If the image becomes the LCP element, say so and show it still meets the budget
- [ ] The image is marked up honestly for assistive technology — decorative (`alt=""`) or described, whichever it actually is; it must not be announced as meaningless if it carries the brand statement
- [ ] `Home.svelte`'s "no images in the hero" comment is corrected, since it will no longer be true
- [ ] `scripts/check.sh web` passes

## Notes

**On blending, the honest options, in rough order of durability:**

- **Cut the monitor out** to a transparent PNG or WebP. Works on any ground, survives a future palette change, and is the only option that is genuinely theme-independent. Costs the most effort and risks a halo on the CRT's soft glow.
- **A radial or linear fade** to transparent at the edges, so the baked background dissolves into whatever is behind it. Cheap, and good enough given `#181d17` is already within a hair of `--bg-subtle` on dark — but it still darkens a light page.
- **Two assets**, one per theme, swapped with `<picture>` + `prefers-color-scheme` or the existing theme attribute. Honest, doubles the bytes.
- **Confine the hero to a dark surface regardless of theme**, so only one ground exists. A design decision rather than an asset one — record it as such if chosen.

**Do not** simply set the image's background colour to a token and hope; the
photograph has a soft vignette, so a flat fill will band visibly against it.

`CLAUDE.md` §8 also records that **headless Chromium enforces a ~485 px minimum
window width**, which silently clips narrower renders. Safari via `safaridriver`
does not have that limit — the session that produced this project's screenshots
captured 390 px cleanly — so use it for the narrow-viewport check.

The source image is at `../CRT.png` relative to the repo root. Static assets
live in `web/public/`, which is where the logo and icon set already sit.

## Implementation notes

**Do not mark this issue `resolved` from this section** — that is the
reviewer's call.

**Placement.** The image lives *inside* `TerminalPanel`'s own body, not
beside it. `TerminalPanel` renders `{@render children()}` inside one
`.terminal-body`; the hero's children are now a single `.hero-row` flex
container with `.hero-text` (the existing Prompt/headline/StatusList/
CommandLine block) on the left and `.hero-crt` (the photo) on the right, so
both sit inside the same bordered, titled panel. An earlier draft of this
work put the image as a sibling of `<TerminalPanel>` — a second box next to
the terminal rather than inside it — and was corrected after the user
looked at the rendered page.

**Blending approach — a hybrid, not any one of the Notes' four options.**
`CRT.png`'s backdrop is unusually uniform (measured: every corner and
mid-edge sample is within a few values of `rgb(25,30,23)` / `#181d17`), so
rather than a manual cutout or a geometric vignette, the alpha matte was
built by **color-distance keying against that measured backdrop colour**:
pixels close to it fade toward transparent, pixels far from it (the green
screen glow, the white bezel highlights, the red power LED) stay opaque,
with a Gaussian blur on the alpha channel and a geometric edge feather
(clamped to the crop rectangle) so there is no hard cutout edge and no
banding. This is effort-cheap (a ~30-line Pillow/numpy script, no manual
masking) but gets close to the option-1 "cut the monitor out" quality,
because the photo's own soft vignette already does most of the blending
work for a color key.

That alpha-matted cutout is then composited into `.crt-frame`, a small
panel with a **fixed** background (`#181d17`, the same measured value) and
the ordinary `--border` token for its edge — i.e. option 4 from the Notes,
"confine to a dark surface regardless of theme," but scoped to a small
frame around just the photo rather than the whole hero.

**Why a fixed frame instead of the panel's own background, and why not two
theme assets.** Before deciding, I composited the cutout over three real
backgrounds to check by eye rather than assume:
- `--bg-page` light (`#F4F6F3`) and `--bg-panel` light (`#FFFFFF`) — both
  ghost badly. The photo's own dark tones (screen bezel, cabinet) are close
  enough to its own backdrop colour that the color-key alpha thins them out
  too, so on a light ground the monitor doesn't blend, it *washes out* —
  a translucent grey ghost, worse than a flat pasted rectangle would have
  been. This confirms the issue's prediction and rules out placing the
  cutout directly on any light surface.
- `--bg-panel` dark (`#121712`) — no visible seam. Close enough to the
  photo's own `#181d17` backdrop that this would have worked without a
  frame at all in dark mode specifically.
- `--bg-page` dark (`#0A0D0B`, darker still) — also no visible seam.

So dark mode's own surfaces would have worked unframed, and the "one
colour" simplification the correction asked me to check for is real **for
dark mode alone** — but light mode has no surface in this design system the
cutout can sit on directly. Rather than branch the treatment (one photo
placement for dark, a framed one for light), `.crt-frame`'s fixed
`#181d17` is used in both themes: one asset, one background value, verified
seamless in dark and by design in light (screenshots below). The cost:
in light mode the frame is a visibly dark box inside a white terminal
panel — not "invisible," but read as a deliberate screen-in-an-alcove
element, consistent with the terminal panel's own bordered-card language,
not a mistake. `.crt-frame`'s background is a literal hex value rather than
a design token *on purpose* — the whole point is that it must not change
with the theme the way every other token does.

**Responsive behaviour and the `alt=""`/`src` fix.** The first draft used
`<picture><source media="(min-width:860px)">` with an `<img>` carrying no
`src`, intending to skip the fetch entirely below 860px. The user's
correction flagged this as broken markup (an `<img>` with no fallback
`src`) and asked for a real fix. The corrected markup gives `<img
class="crt-photo" src="/hero-crt-380.webp">` a real, valid `src` (the 1x
desktop asset, reused as the sub-860px asset too) and keeps `<source
media="(min-width: 860px)">` only to offer the 2x asset to retina desktops
via `srcset="/hero-crt-380.webp 1x, /hero-crt-760.webp 2x"`. Consequence:
the image is **never removed from the DOM** at any width and its bytes are
paid regardless of viewport, so `.hero-row` reflows instead of hiding —
`flex-direction: column` under 860px (text first, photo stacked below at
220px) and `row` at 860px+ (text left, 380px-wide photo right). Since the
download happens either way, showing a smaller version on narrow viewports
wastes nothing that hiding it would have saved.

**Accessibility — `alt=""`.** The correction asked me to state this
explicitly rather than assert it, since the screen does read "> Open
Circuit SF _", which is arguably content. I kept `alt=""` because that
exact information — the org name and the terminal-prompt framing — is
already present as real, adjacent text in the same panel: `<Prompt
text="open_circuit // san_francisco">`, the `h1` headline, and
`<CommandLine command="opencircuitsf.com">` all sit in `.hero-text`,
inches from the photo. A screen-reader user reaches the org name and the
prompt motif through those actual text nodes; the photo adds a physical,
photographic reinforcement of the terminal motif that a sighted user gets
and a screen-reader user doesn't need repeated. Describing it (e.g. `alt="A
green-phosphor CRT monitor displaying > Open Circuit SF _"`) would mostly
duplicate `.hero-text` word-for-word for AT users, which is worse than a
clean decorative skip. Marked `decoding="async"`, no `aria-hidden` needed
since `alt=""` on an `<img>` (not a background image) is itself the
decorative signal.

**Weight.** Source `CRT.png` is 1,402×1,122, 1,387,611 bytes (RGB, no
alpha). Processing (crop to content + padding, alpha-matte per above,
Lanczos resize, WebP encode at quality 82):
- `web/public/hero-crt-380.webp` — 380×354, **37,198 bytes** (~36 KB) — the
  asset every viewport downloads (desktop 1x and all narrow widths, per the
  `src` fallback above)
- `web/public/hero-crt-760.webp` — 760×707, **100,010 bytes** (~98 KB) —
  desktop retina only, via the `<source>`'s `2x` descriptor

So the deliberate cap: **every viewport pays at most ~36 KB**, and only
non-narrow retina displays pay the extra ~62 KB for the 2x asset. Combined
JS+CSS for the whole SPA is currently 246.42 KB raw / 77.30 KB gzip (from
`npm run build`), so the 1x image (~36 KB) is a modest addition and well
inside PRD §7.6's budget on any of the standard levers (modern format,
real intrinsic dimensions, `width`/`height` reserved via attributes,
responsive `srcset`).

**LCP — measured before and after, via `safaridriver` (not Chromium — see
the CLAUDE.md §8 width-limit note) against the built `web/dist/`, served
unthrottled over local HTTP** (`python3 -m http.server`, no network
throttling available in this environment — the absolute times below are
not "4G," but the *relative* comparison and the element identification are
real):

| | Before | After |
|---|---|---|
| 1440px LCP element | `h1.headline` (the headline) | `img.crt-photo` (the CRT photo) |
| 1440px LCP entry size (px²) | 78,739 | 111,520–116,737 (two runs) |
| 1440px LCP time (unthrottled) | ~52 ms | ~28–52 ms (two runs, noise-level difference) |
| 390px LCP element | `h1.headline` | `img.crt-photo` (35,059 px²) — now downloaded and shown at every width, see Responsive behaviour above |

**The image becomes the LCP element at every width measured**, both because
it is downloaded unconditionally now and because its rendered area exceeds
the headline's. Budget check: PRD §7.6 wants LCP under 2.0s on 4G. The
added payload for the LCP resource itself is ~36 KB (desktop 1x / narrow) or
~98 KB (desktop 2x). At a conservative "Slow 4G" profile (~1.6 Mbps down,
per Lighthouse's throttling preset), 36 KB costs ~180 ms and 98 KB costs
~490 ms of transfer — against the existing critical path of ~77 KB gzipped
JS/CSS, which itself must arrive before the SPA mounts and the image tag
exists in the DOM. Even stacked serially (worst case: JS/CSS parse, then
the image request begins), the total stays well under the 2.0s budget on a
2026-era 4G connection. This is an estimate from the measured byte counts,
not a real throttled run — there is no load-testing or network-throttling
tooling in this project (CLAUDE.md §5), and setting one up for a single
issue's LCP check would be disproportionate.

**Verified in `docs/obstacles.md` terms:** no privilege/tool obstacles hit.
`safaridriver` at `/System/Cryptexes/App/usr/bin/safaridriver`, Pillow
11.3.0 already available via the system `python3`, no ImageMagick/`cwebp`
needed. Ports used for verification (8931/8932, then 8941/8942 after the
placement fix) were freed on exit; no leftover `go test`/`.test` processes.

Three things worth knowing if this is touched again:

- **The `<img>` became a CSS background.** A `<picture>` cannot do this job:
  `<source media="(prefers-color-scheme: dark)">` reads only the OS preference,
  so the header's explicit light/dark toggle (`lib/theme.ts` writes
  `data-theme` on `<html>`) would leave a dark photo on a light panel. Two
  `<img>`s toggled by `display` would fetch both assets. A background driven by
  a custom property answers to both signals and fetches one — **verified by
  Resource Timing on a real load: dark fetched only `hero-crt-380.webp`, light
  only `hero-crt-light-380.webp`.** The photo is decorative (it repeats what
  the adjacent headline and command line already say), so it carried `alt=""`
  as an `<img>` and needs no text alternative as a background.
- **The pinned colors are the WebP's *decoded* values, not the source PNG's.**
  Lossy encoding shifts a flat field by a step or two: `#E9EEE6` decodes to
  `#E8EEE5`, `#181D17` to `#191C17`, and it is the decoded value the browser
  paints beside the panel background. Measured as the mode of the border pixels
  (95–98% of them for the light asset). Lossless holds the source values
  exactly but costs 262 KB against 19 KB at 2x — not worth one 255th.
  Re-measure if either asset is re-encoded.
- **Panel styling now goes through TerminalPanel's own custom properties**
  (`--bg-panel`, `--bg-header`, `--border`) rather than `:global()` overrides of
  its internals, and text tokens are no longer overridden at all — each theme's
  palette already contrasts correctly against its own photo backdrop. Revision
  1's light-mode ambient shadow is gone with the dark band that motivated it.
