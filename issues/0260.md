## Resolution notes

> 🟢 Resolved 2026-08-27 — the token INSERT and its `outbound_queue` enqueue
> now share one transaction, proved by mutation rather than by reading.

## Description

`#0126` made subscriber confirmation durable by sharing one transaction between
the insert and the enqueue. **It could not do the same for registration and
recovery mail, because the premise its plan assumed is false**:
`CreatePendingRegistration` and `CreateRecoveryToken` are plain `s.pool.Exec`
calls, not transactions.

So the token is written, and the enqueue is a separate statement afterwards. A
crash in that window leaves a valid token with no mail ever sent.

**Characterised precisely by `#0126`'s review**, which is why this is a
follow-up rather than a blocker:

- **What is lost is the email, not the token.** The token row is committed and
  valid; nothing retries the send.
- **It is never a silent success.** An enqueue error returns 500 from both
  `RegisterStart` and `RecoverStart`, and a crash in the window kills the
  connection too — so the caller always learns something went wrong.
- **It is strictly narrower than before `#0126`.** The unprotected window used
  to span a full SES round trip; it is now a single INSERT.

That combination is why it is worth fixing but not urgent: the user sees an
error and retries, rather than waiting for mail that will never come.

## Acceptance criteria

- [x] The token write and its enqueue are atomic — either both commit or neither does
- [x] Proved by injecting a failure between them and confirming neither row exists, the way `#0126` proved the subscriber path
- [x] `RegisterStart` and `RecoverStart` still return 500 rather than 200 when the mail cannot be queued
- [x] Any transaction refactor of `internal/auth`'s store keeps its narrow-interface convention (`CLAUDE.md` §1) — handlers must not gain a `*pgxpool.Pool`
- [x] `ISSUE=0260 scripts/check.sh go ./internal/auth/... ./internal/handlers/...` passes with zero skips

## Root cause

`#0126`'s plan assumed `CreatePendingRegistration`/`CreateRecoveryToken`
already ran inside a transaction they could enqueue into (by analogy with
`audit.WriteTx`). They did not — both were plain `s.pool.Exec` calls — and
`RegistrationService.StartRegistration`/`RecoveryService.StartRecovery`
called `Mailer.SendVerification`/`SendRecovery` as a **separate** statement
afterward. A crash (or any failure) in that window left a committed,
`ErrTokenInvalid`-passing token row with no mail ever queued to send it —
narrower than the pre-`#0126` window (one `INSERT` instead of a full SES
round trip), but still real.

## Fix

Gave `auth.Store` its own `*outbox.Store` (constructed internally in
`NewStore`, so its exported signature is unchanged) behind a narrow
`txEnqueuer` interface — narrow specifically so a test can swap in a
poisoned implementation and prove atomicity, the same reason
`internal/subscribers.Store` exposes `EnqueueTx` against a `Querier`
interface rather than a concrete type. `CreatePendingRegistration` and
`CreateRecoveryToken` now each: `Begin` a transaction, `INSERT` the token
row, `EnqueueTx` the registration/recovery payload (the same
`registrationPayload`/`recoveryPayload` structs `SESMailer` already
defined, in the same package — no duplication), and `Commit`. Mirrors
`internal/subscribers.Store.Create`'s shape from `#0126` exactly, per that
issue's own note that "the shape exists to copy rather than invent."

`StartRegistration`/`StartRecovery` no longer call
`Mailer.SendVerification`/`SendRecovery` — the store's own transaction
already enqueued the mail, and calling the mailer afterward would
double-enqueue. Both still return the store's error on failure (`RegisterStart`/
`RecoverStart` map that to 500, unchanged) rather than swallowing it, so
criterion 3 holds without any handler-level change. `s.mailer` stays on
both services — still used for `SendSessionsRevoked` elsewhere and to avoid
touching every existing test's construction call site, none of which needed
to change signature.

**Narrow-interface convention (criterion 4):** `auth.Store` gained a
dependency (`txEnqueuer`), not `*pgxpool.Pool` exposure — `internal/handlers`
still only sees the same `RegistrationService`/`RecoveryService` interfaces
it always did. `Store.Pool()` (pre-existing, used by session middleware) is
unchanged and untouched by this issue.

## Gotchas

- **`outbound_queue` wasn't in this package's truncate list before this
  issue**, because nothing in `internal/auth` wrote to it directly (only
  `SESMailer` did, and its own tests use per-test unique recipients rather
  than relying on truncation). Several `registration_test.go`/
  `recovery_test.go` tests reuse fixed addresses (`bob@example.com`,
  `user@example.com`) across the package, so once `Store` started writing
  `outbound_queue` rows too, a stale row from an earlier test run within the
  same binary would have inflated `countOutboundQueueKind`'s counts.
  `truncateAuthTables` (called by every test via `testPool`) now truncates
  it too.

## Notes

Found by `#0126`'s phase-3 review under `CLAUDE.md` §9, which confirmed the
residual by reading the store rather than trusting the plan.

**The plan for `#0126` assumed these were transactional and they are not.** That
is worth recording as a planning-accuracy note: the plan was otherwise accurate
enough that its implementer followed it closely, and this was the one premise
that did not hold when checked against the code.

The fix likely means giving `internal/auth`'s store a `WithTx`-style entry
point, which `internal/subscribers` already has after `#0126` — so the shape
exists to copy rather than invent.

## Review notes

Reviewed independently against `6b695b8`, 2026-08-27. **Approved.**

### What was re-verified, and how

- **`ISSUE=0254r scripts/check.sh go ./internal/... ./cmd/opencircuit/...`** —
  every package `ok`, **zero skips**, `gofmt -l` clean. `internal/auth` in
  1.019s (DB-backed, not 0.00s).
- **Criterion 2 proved by mutation, not by reading.** In a throwaway worktree
  pinned to `4af0ea3`, `tx.Exec` was changed to `s.pool.Exec` in *both*
  `CreatePendingRegistration` and `CreateRecoveryToken` — i.e. the token row
  written outside the transaction, exactly the pre-fix shape. Both atomicity
  tests then failed, and failed on the right assertion:

  ```
  --- FAIL: TestCreateRecoveryToken_EnqueueFailureRollsBackBothRows
      recovery_test.go:185: pending_registrations rows for … = 1, want 0 after rollback
  --- FAIL: TestCreatePendingRegistration_EnqueueFailureRollsBackBothRows
      registration_test.go:496: pending_registrations rows for … = 1, want 0 after rollback
  ```

  The `failingTxEnqueuer` injection is therefore load-bearing, not decorative.
  The worktree was removed afterwards; the shared tree was never mutated.
- **No double-enqueue.** `grep` over non-test sources confirms
  `Mailer.SendVerification`/`SendRecovery` now have **no production call
  site** at all — the only remaining references are doc comments, the
  interface declaration, and `SESMailer`/`NoOpMailer`'s own definitions. So
  removing the call from `StartRegistration`/`StartRecovery` cannot leave a
  second enqueue behind. The payload structs (`registrationPayload`,
  `recoveryPayload`) the store now writes are the same types `SESMailer` used,
  so the JSONB contract with `internal/mailing/outbox_worker.go`'s renderer is
  byte-compatible.
- **Criterion 3 holds by inspection of the whole function**, not just the
  diff: `StartRegistration` returns `s.store.CreatePendingRegistration`'s
  error unchanged, and that error now covers the enqueue and the commit as
  well as the INSERT — so `RegisterStart`/`RecoverStart` still 500 when mail
  cannot be queued, and now also when it cannot be queued *atomically*.
- **Criterion 4 holds.** `Store` gained a `txEnqueuer`, not pool exposure;
  `internal/handlers` still sees only `RegistrationService`/`RecoveryService`.
  `internal/outbox` imports nothing internal, so no cycle.

### Two things to file (reported, not filed — CLAUDE.md §9)

1. **`MAILER_NOOP=true` no longer prints the registration/recovery magic
   link.** This is a real dev-workflow regression from this commit, not a
   correctness one. `auth.NoOpMailer.SendVerification`/`SendRecovery` log the
   full link (`mailer.go`) and were the only way to complete a local passkey
   registration against Postgres before SES exists (CLAUDE.md §10 item 2).
   They now have no caller: the store enqueues instead, and the row is drained
   by `OutboxWorker` through `noOpMailingMailer`, which logs **only the
   subject** (`cmd/opencircuit/main.go`, `MAILER_NOOP: email to %s: %s`).
   `STORAGE=json` is unaffected (`devstore.DevRegistrar`). Suggested fix:
   have `noOpMailingMailer.Send` log the rendered text body, or the queued
   payload, so the link survives.
2. **`SESMailer.SendVerification`/`SendRecovery` are now production-dead**
   while remaining on the `Mailer` interface (only `SendSessionsRevoked` is
   still called). Worth a decision — narrow the interface, or leave them with
   a doc comment saying the store owns those two enqueues now. Low priority;
   the doc comments already say it.
