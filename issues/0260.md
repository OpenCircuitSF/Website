# 0260 — Registration and recovery mail can be lost between token and enqueue

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |

| **Phase** | 8 — Archive, imports, and delivery health |

## Description

`#0126` made subscriber confirmation durable by sharing one transaction between
the insert and the enqueue. **It could not do the same for registration and
recovery mail, because the premise its plan assumed is false**:
`CreatePendingRegistration` and `CreateRecoveryToken` are plain `s.pool.Exec`
calls, not transactions.

So the token is written, and the enqueue is a separate statement afterwards. A
crash in that window leaves a valid token with no mail ever sent.

**Characterised precisely by `#0126`'s review**, which is why this is a
follow-up rather than a blocker:

- **What is lost is the email, not the token.** The token row is committed and
  valid; nothing retries the send.
- **It is never a silent success.** An enqueue error returns 500 from both
  `RegisterStart` and `RecoverStart`, and a crash in the window kills the
  connection too — so the caller always learns something went wrong.
- **It is strictly narrower than before `#0126`.** The unprotected window used
  to span a full SES round trip; it is now a single INSERT.

That combination is why it is worth fixing but not urgent: the user sees an
error and retries, rather than waiting for mail that will never come.

## Acceptance criteria

- [ ] The token write and its enqueue are atomic — either both commit or neither does
- [ ] Proved by injecting a failure between them and confirming neither row exists, the way `#0126` proved the subscriber path
- [ ] `RegisterStart` and `RecoverStart` still return 500 rather than 200 when the mail cannot be queued
- [ ] Any transaction refactor of `internal/auth`'s store keeps its narrow-interface convention (`CLAUDE.md` §1) — handlers must not gain a `*pgxpool.Pool`
- [ ] `ISSUE=0260 scripts/check.sh go ./internal/auth/... ./internal/handlers/...` passes with zero skips

## Notes

Found by `#0126`'s phase-3 review under `CLAUDE.md` §9, which confirmed the
residual by reading the store rather than trusting the plan.

**The plan for `#0126` assumed these were transactional and they are not.** That
is worth recording as a planning-accuracy note: the plan was otherwise accurate
enough that its implementer followed it closely, and this was the one premise
that did not hold when checked against the code.

The fix likely means giving `internal/auth`'s store a `WithTx`-style entry
point, which `internal/subscribers` already has after `#0126` — so the shape
exists to copy rather than invent.
