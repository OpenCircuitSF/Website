## Description

`#0284` corrected `outboxOrphanStaleAfter` in the outbox worker. **The campaign
send worker has its own, separate `orphanStaleAfter` in
`internal/mailing/worker.go`, still set to `2 * (sendMessageTimeout +
writeStatusTimeout)` = 70s, with the same defect.**

`ClaimBatch` claims up to `batchSize` recipients in one statement — stamping one
`claimed_at` — and then sends them serially behind the same rate-limiter shape.
So the last recipient in a batch has held a claim for the whole time its
predecessors took, and the constant accounts for one message only.

`#0284`'s new package doc comment already records that the two derivations
diverge, which is how this surfaced.

**Read `#0284`'s review notes before starting.** Its reviewer established two
things that apply directly here and that a first attempt is likely to get wrong:

- `rate.Limiter` regenerates tokens **while a send is in flight**, so row *k*
  starts at `max((k-1) × interval, Σ predecessor durations)`. A predecessor's
  real cost is `max(interval, its own processing time)`, and processing time is
  bounded only by the timeouts — **the rate interval is not the term to charge
  per predecessor.** Charging the interval is what made `#0284`'s first fix
  wrong.
- A window derived that way is large. `#0284` bounced for asserting a
  "structural upper bound" that did not exist; do not repeat that.

## Acceptance criteria

1. The window is derived from the batch, charging each predecessor its per-row
   **bound**, not the pacing interval. State the arithmetic in the doc comment.
2. Expressed in code from the constants it depends on, so a change to batch size
   or a timeout moves it automatically.
3. A test asserts the invariant rather than the number, and **must fail when the
   fix is reverted**. `#0284`'s reviewer measured a test of this shape that
   passed against full reversion — check yours against that failure mode
   explicitly.
4. Do not assert a bound the code does not have (criterion 4 of `#0294`, same
   reason).
5. Reconcile with `#0284`: two orphan windows in two workers with two
   derivations is the situation that produced this issue. Either share the
   derivation or document plainly why they differ.
6. Consider whether re-stamping `claimed_at` per row is the better fix here too,
   and say so if it is rather than building a large-window version.
7. Not a load exercise — CLAUDE.md §5.
8. `ISSUE=NNNN scripts/check.sh go ./internal/mailing/... ./internal/outbox/...`
   passes with no skips.
