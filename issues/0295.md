## Description

`#0284` corrected `outboxOrphanStaleAfter` in the outbox worker. **The campaign
send worker has its own, separate `orphanStaleAfter` in
`internal/mailing/worker.go`, still set to `2 * (sendMessageTimeout +
writeStatusTimeout)` = 70s, with the same defect.**

`ClaimBatch` claims up to `batchSize` recipients in one statement — stamping one
`claimed_at` — and then sends them serially behind the same rate-limiter shape.
So the last recipient in a batch has held a claim for the whole time its
predecessors took, and the constant accounts for one message only.

`#0284`'s new package doc comment already records that the two derivations
diverge, which is how this surfaced.

**Read `#0284`'s review notes before starting.** Its reviewer established two
things that apply directly here and that a first attempt is likely to get wrong:

- `rate.Limiter` regenerates tokens **while a send is in flight**, so row *k*
  starts at `max((k-1) × interval, Σ predecessor durations)`. A predecessor's
  real cost is `max(interval, its own processing time)`, and processing time is
  bounded only by the timeouts — **the rate interval is not the term to charge
  per predecessor.** Charging the interval is what made `#0284`'s first fix
  wrong.
- A window derived that way is large. `#0284` bounced for asserting a
  "structural upper bound" that did not exist; do not repeat that.

## Acceptance criteria

1. The window is derived from the batch, charging each predecessor its per-row
   **bound**, not the pacing interval. State the arithmetic in the doc comment.
2. Expressed in code from the constants it depends on, so a change to batch size
   or a timeout moves it automatically.
3. A test asserts the invariant rather than the number, and **must fail when the
   fix is reverted**. `#0284`'s reviewer measured a test of this shape that
   passed against full reversion — check yours against that failure mode
   explicitly.
4. Do not assert a bound the code does not have (criterion 4 of `#0294`, same
   reason).
5. Reconcile with `#0284`: two orphan windows in two workers with two
   derivations is the situation that produced this issue. Either share the
   derivation or document plainly why they differ.
6. Consider whether re-stamping `claimed_at` per row is the better fix here too,
   and say so if it is rather than building a large-window version.
7. Not a load exercise — CLAUDE.md §5.
8. `ISSUE=NNNN scripts/check.sh go ./internal/mailing/... ./internal/outbox/...`
   passes with no skips.

## Work log

**2026-08-27, phase-2 implementation.**

Read `#0284`'s full review history (all three passes) before touching
`worker.go`. Traced the actual claim mechanics rather than assuming the
outbox worker's shape applies here: `SendStore.ClaimBatch`
(`internal/mailing/worker_store.go:352`) runs `BEGIN; SELECT ... FOR UPDATE
SKIP LOCKED; RecheckEligibleTx; MarkSkippedTx; COMMIT` and returns only
still-eligible `Recipient`s — **it never changes a row's status or touches
`claimed_at`**. The atomic claim (`status='sending', claimed_at=now()`) is
`SendStore.ClaimRow` (`worker_store.go:426`), and it is the FIRST statement
inside `sendOne` (`worker.go:767`), called once per recipient, individually,
at the exact moment that recipient's own processing begins — confirmed by
reading the call site, not inferred.

**Finding: `worker.go` does not have the batch flaw this issue describes.**
The issue's premise — copied from `#0284`'s finding about
`outbox_worker.go` — does not hold for this file. Since `claimed_at` is
stamped per row, not once per batch, batch size never enters the orphan
bound at all: each row's claimed_at reflects when ITS OWN send started,
regardless of how many predecessors already ran ahead of it in `drainLoop`'s
serial loop. This is, architecturally, the per-row `claimed_at` re-stamp
`#0284`'s own doc comment names as the alternative to a large batch-derived
window (criterion 6) — `worker.go` has simply always worked this way, for
the orthogonal reason `ClaimBatch`'s own doc comment gives (`worker_store.go:339-346`):
holding one transaction open across a batch's SES calls would roll back
every status update on a mid-batch crash, turning a one-message duplicate
window into a batch-sized one.

**Criterion 1/2 — arithmetic.** Since there is no batch to charge
predecessors against, the two terms `#0284` needed (claim-hold vs.
predecessor-delay) collapse to one: the legitimate worst-case hold time of a
single live row. On the success path, `MarkSent` flips the row OUT of
`'sending'` before `RecordEvent` runs (`worker.go:858-880`) — unlike
`outbox_worker.go`, where `RecordEvent` running after `MarkSent` still
delays the NEXT row's start (a batch effect this file doesn't have),
`RecordEvent`'s own `writeStatusTimeout` here cannot make THIS row look more
stale than it is, because the row has already left `'sending'` by the time
`RecordEvent` starts. So the single-row bound is `sendMessageTimeout +
writeStatusTimeout` = 35s, and `orphanStaleAfter`'s existing `2 * (...)` =
70s already has a full 35s of real margin — a much healthier margin than
`outbox_worker.go`'s original near-zero one. Left the value (70s) unchanged
— there was no defect to fix, only an incorrect premise to correct in the
documentation.

**Criterion 4 — no bound asserted the code doesn't have.** Rewrote
`orphanStaleAfter`'s doc comment (`worker.go`) to name the residual
honestly, in the same spirit as `#0284`'s final accepted version: `Worker.Run`
is started as `go sendWorker.Run(context.Background())`
(`cmd/opencircuit/main.go:1380`), and `drainLoop`'s calls to `ClaimRow`
itself, plus — on the retryable/terminal-row failure paths —
`MarkFailedRow` and `MarkRetryOrFailed`, all run on that plain, undeadlined
`ctx` rather than a bounded detached context the way the success path's
`sendCtx`/`writeCtx` are. So even the 35s single-row figure is not a strict
bound; closing that would mean giving those calls their own detached,
timeout-bounded contexts — a real, separate change, reported below rather
than built here.

**Criterion 5 — reconciled with `#0284`.** Corrected

## Review notes

**Verdict: pass, and the premise really is false — independently verified from
the source, not from the implementer's account.** This is the durable finding, so
it is recorded in detail rather than summarised.

### 1. `ClaimBatch` claims nothing (`internal/mailing/worker_store.go`)

Read in full. Its transaction is `BEGIN; SELECT id … WHERE status='queued' …
FOR UPDATE SKIP LOCKED; RecheckEligibleTx; MarkSkippedTx (grouped by reason);
COMMIT`. The only `UPDATE` anywhere in it is `MarkSkippedTx`, which moves
*ineligible* rows to `'skipped'`. Every **returned** recipient is left exactly as
found: `status='queued'`, `claimed_at` NULL. The `FOR UPDATE` row locks are
released at `COMMIT`, which happens before any SES call. Confirmed against
`internal/outbox.Store.ClaimDue` for contrast, which really does
`UPDATE outbound_queue SET status=$2, attempts=attempts+1, claimed_at=now()
WHERE id IN (SELECT … LIMIT $1 FOR UPDATE SKIP LOCKED) RETURNING …` — one
batch-wide stamp. The two are genuinely different shapes.

### 2. `ClaimRow` is the first statement in `sendOne`, unconditionally, per row

`sendOne` (`worker.go`) opens with `_, claimed, err := w.store.ClaimRow(ctx,
r.SendID)` — no branch, no guard, no earlier statement. `ClaimRow` is
`UPDATE email_sends SET status='sending', attempts=attempts+1, claimed_at=now()
WHERE id=$1 AND status='queued'`. So each row's `claimed_at` is stamped when that
row's own processing starts.

Checked the surrounding loop too, which the issue's premise depended on:
`drainLoop` calls `limiter.Wait(ctx)` **before** `sendOne`, and the throttling
backoff `w.sleep` **after** it returns — so neither the rate-limiter pacing nor
the backoff is inside any row's claim window. Batch size, send rate, and
predecessor cost are all outside the bound. The issue's arithmetic premise has no
term to attach to.

### 3. `MarkSent` before `RecordEvent` — confirmed, and it is the opposite of `outbox_worker.go`

`worker.go`'s success path: `MarkSent(writeCtx, …)`, then — only if `werr ==
nil` — a fresh `eventCtx` and `RecordEvent`. The row has already left `'sending'`
before `RecordEvent` is entered. This is the term `#0284` spent a pass on, and it
genuinely vanishes here for **two** independent reasons, both of which hold:
`RecordEvent` cannot extend *this* row's staleness (the row is already `'sent'`),
and there is no batch-wide claim for it to delay. `outbox_worker.go`'s own doc
comment states the contrary ordering for that worker, and its
`sendMessageTimeout + 2*writeStatusTimeout` = 40s per-predecessor charge is
consistent with it.

### 4. The 35s figure and the 70s margin

`sendMessageTimeout = 30s`, `writeStatusTimeout = 5s` (`worker.go`), both on
detached `context.WithTimeout` contexts (`sendCtx`, `writeCtx`) — so the success
path's hold really is bounded at 35s. `orphanStaleAfter = 2 * (sendMessageTimeout
+ writeStatusTimeout)` = 70s, giving 35s of margin. The claim checks out.

Criterion 4 is honoured: the doc comment's `# Still not a STRICT bound` section
names the undeadlined failure-path writes rather than asserting a bound the code
does not have — the exact failure that bounced `#0284` twice. (One residual it
does *not* name: `w.render.Campaign` also runs between `ClaimRow` and `sendCtx`,
in-process and unbounded. It is pure CPU over one Markdown body, so it is not
worth widening anything for, and it does not undermine the honest "not a strict
bound" framing already present.)

### 5. Reversion proofs — re-run independently, in a throwaway worktree

Ran in `git worktree add … HEAD` against my own scratch database
(`opencircuit_test_0295rev`), never in the main tree. Baseline: both new tests
pass.

| Mutation | Result |
|---|---|
| `orphanStaleAfter = 20 * time.Second` | `TestOrphanStaleAfterCoversLegitimateSingleRowHold` **FAILED** — "orphanStaleAfter (20s) does not exceed … (35s)" |
| `orphanStaleAfter = sendMessageTimeout + writeStatusTimeout` (exact boundary, 35s) | **FAILED** — the assertion is strict `>`, not `>=`, so the boundary is caught too |
| **Smart** outbox-style batch claim added to `ClaimBatch` | `TestSendStore_ClaimBatch_LeavesRowsQueuedUntilClaimRow` **FAILED** — `status after ClaimBatch = "sending", want queued` |

The third is the one worth judging, and it survives a **stronger** mutation than
the implementer's own. The implementer replaced `ClaimBatch`'s `SELECT` with an
outbox-style `UPDATE … RETURNING`, which broke `RecheckEligibleTx`'s
`status='queued'` expectation, so its test failed on an *internal inconsistency*
(`recipients = []`) rather than on the property under test. I instead added the
batch-wide `UPDATE … SET status='sending', claimed_at=now()` **after**
`RecheckEligibleTx`, inside the same transaction — leaving the recheck, the skip
grouping, and the returned batch's contents completely intact, so the only
observable change is the one the guard exists to catch. It failed on exactly that
assertion. **The test pins the architecture behaviourally against a real
database; it does not restate the source.** Its oracle is a `SELECT` of the row's
actual `status`/`claimed_at`, which no edit to `ClaimBatch` can also satisfy
(CLAUDE.md §8).

The arithmetic test's oracle is likewise a different expression from its subject
— `sendMessageTimeout + writeStatusTimeout` versus the subject's `2 * (…)` — so
shrinking the margin factor moves `got` without moving `want`.

### 6. `outbox_worker.go`'s corrected package doc — accurate in both directions

Verified both halves against code, not against each other. It still correctly
describes *this* worker's defect (`ClaimDue`'s single batch-wide `UPDATE`, serial
`pass`, rate limiter dropping out of the derivation), and its new paragraph
correctly describes `worker.go`'s per-row claim. The stale sentence claiming
`worker.go` "has the same batching flaw `#0284` fixed here" is gone. Both
`orphanStaleAfter` doc comments now cross-reference each other with the reason
they differ, satisfying criterion 5.

### 7. `#0302`'s description is accurate

Confirmed: `cmd/opencircuit/main.go:1380` is `go sendWorker.Run(context.Background())`,
and `sendOne`'s `ClaimRow`, both `MarkFailedRow` call sites, and
`MarkRetryOrFailed` all take the ambient `ctx`, while only `sendCtx`/`writeCtx`/
`eventCtx` are bounded. One addition for whoever picks it up: `drainLoop`'s
`ReleaseRow` on the `sendOutcomeTerminalCampaign` path is undeadlined for the
same reason, and the row is sitting in `'sending'` while it runs — it belongs in
the same fix.
