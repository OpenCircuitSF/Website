# 0250 — Five residual gaps in `db-reset.sh`'s new guard

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | infra / tooling |
| **Phase** | 0 — Foundation |

## Description

`#0207` gave `db-reset.sh` a guard that genuinely works: a review reproduced it
against a real held connection, ran 16 bypass inputs, and **found no bypass**.
These are the leftovers it found while doing that. None is a bypass; two are
worth fixing properly.

**1. The live-connection check fails OPEN.** If `psql` errors for any reason —
wrong socket, bad credentials, server down, a transient fault — the check
returns no rows and the guard reads that as "no connections" and proceeds. The
one condition under which you most want a destructive script to stop is the one
where it cannot tell what is happening.

**2. `psql` is never checked for presence**, unlike `migrate`, which is. On a
machine without `psql` on `PATH` this compounds item 1: the check silently
succeeds and the reset proceeds.

**3. `db-reset.sh opencircuit --force` silently ignores the flag.** The option
loop breaks at the first positional argument, so a flag after the database name
is dropped. That fails *safe* — but the refusal message tells the user to run
exactly that, so following the tool's own instruction does not work.

**4. `db-reset.sh ""` resolves to `opencircuit`.** An empty argument falls
through to the default rather than being rejected. Harmless today because the
name guard still applies, but an empty string arriving from an unset variable
is how a caller accidentally targets the main database.

**5. The guard test leaks a database.** `scripts/db_reset_guard_test.sh`'s
regression case leaves `opencircuit_test_0207gt_demo` behind; the reviewer
dropped it by hand. Same class as `#0223` and `#0249` — a cleanup path that
reports success while leaving something behind.

## Acceptance criteria

- [ ] The live-connection check distinguishes "no connections" from "could not tell", and refuses on the latter
- [ ] Proved by making `psql` fail (a stub on `PATH`, or a deliberately bad connection string) and confirming the script refuses rather than proceeding
- [ ] `psql` presence is checked the way `migrate` already is
- [ ] A flag after the database name is either honoured or rejected with a message that matches what the refusal text tells the user to do — the two must not disagree
- [ ] An empty database argument is rejected rather than defaulting
- [ ] `scripts/db_reset_guard_test.sh` drops everything it creates; proved by a `pg_database` census before and after
- [ ] `bash -n` and `shellcheck` clean

## Notes

Reported by `#0207`'s phase-3 review under `CLAUDE.md` §9.

Items 1 and 2 are the ones that matter. A destructive script whose safety check
fails open is only as good as the environment it runs in, and this project's
whole reason for having the guard is that `db-reset.sh` had already been a
hazard for the entire session before `#0207` landed.

Item 3 is small but user-facing in an unusually bad way: the tool prints an
instruction that does not work.
