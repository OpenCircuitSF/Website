## Description

`#0207` gave `db-reset.sh` a guard that genuinely works: a review reproduced it
against a real held connection, ran 16 bypass inputs, and **found no bypass**.
These are the leftovers it found while doing that. None is a bypass; two are
worth fixing properly.

**1. The live-connection check fails OPEN.** If `psql` errors for any reason —
wrong socket, bad credentials, server down, a transient fault — the check
returns no rows and the guard reads that as "no connections" and proceeds. The
one condition under which you most want a destructive script to stop is the one
where it cannot tell what is happening.

**2. `psql` is never checked for presence**, unlike `migrate`, which is. On a
machine without `psql` on `PATH` this compounds item 1: the check silently
succeeds and the reset proceeds.

**3. `db-reset.sh opencircuit --force` silently ignores the flag.** The option
loop breaks at the first positional argument, so a flag after the database name
is dropped. That fails *safe* — but the refusal message tells the user to run
exactly that, so following the tool's own instruction does not work.

**4. `db-reset.sh ""` resolves to `opencircuit`.** An empty argument falls
through to the default rather than being rejected. Harmless today because the
name guard still applies, but an empty string arriving from an unset variable
is how a caller accidentally targets the main database.

**5. The guard test leaks a database.** `scripts/db_reset_guard_test.sh`'s
regression case leaves `opencircuit_test_0207gt_demo` behind; the reviewer
dropped it by hand. Same class as `#0223` and `#0249` — a cleanup path that
reports success while leaving something behind.

## Acceptance criteria

- [x] The live-connection check distinguishes "no connections" from "could not tell", and refuses on the latter
- [x] Proved by making `psql` fail (a stub on `PATH`, or a deliberately bad connection string) and confirming the script refuses rather than proceeding
- [x] `psql` presence is checked the way `migrate` already is
- [x] A flag after the database name is either honoured or rejected with a message that matches what the refusal text tells the user to do — the two must not disagree
- [x] An empty database argument is rejected rather than defaulting
- [x] `scripts/db_reset_guard_test.sh` drops everything it creates; proved by a `pg_database` census before and after
- [x] `bash -n` and `shellcheck` clean

## Implementation notes

**Item 1 — fail closed.** The live-connection query was
`CONNS="$(psql … 2>/dev/null || true)"`; any psql failure (bad socket, bad
credentials, server down, a transient fault) produced the same empty string
as "genuinely no connections," and the script proceeded. Rewritten as
`if ! CONNS="$(psql …)"; then refuse; fi`, which distinguishes "the query ran
and found nothing" from "the query didn't run." This check now runs
**unconditionally, even under `--force`** — `--force` means "I know someone
is connected, proceed anyway," not "proceed even if you can't tell whether
anyone is connected." (`set -euo pipefail` is active in `db-reset.sh`; the
`if ! VAR=$(...); then` form is what lets the failure be caught and handled
rather than exiting the whole script via `-e` before the refusal message
prints.)

**Item 2 — psql presence.** Added `command -v psql >/dev/null || { echo
"error: psql not on PATH" >&2; exit 1; }` immediately after the existing
`migrate` check, so an environment missing `psql` fails with a clear message
instead of silently feeding item 1's "could not tell" refusal path (or,
pre-fix, the fail-open bug).

**Item 3 — flag position.** The old option loop (`while : ; do case
"${1:-}" in --no-seed|--force) …; *) break;; esac; done`) stopped at the
first positional argument, so `db-reset.sh opencircuit --force` silently
dropped `--force`. Replaced with a single `for arg in "$@"` loop that
classifies each argument as `--no-seed`, `--force`, an unrecognized `--*`
flag (now rejected outright, previously silently treated as the database
name), or the one allowed positional argument (a second one is now
rejected). Flags are honoured in any position.

**Item 4 — empty database name.** `DB="${1:-opencircuit}"` treated an
explicitly-empty first argument the same as an absent one. The new loop
tracks `DB_SET` separately from `DB`'s value, so `db-reset.sh --force ""`
is rejected with an explicit message rather than silently resolving to the
real dev database name.

**Item 5 — leaked database.** `scripts/db_reset_guard_test.sh`'s `cleanup()`
now defensively drops `opencircuit_test_0207gt_demo` (the name Part 5's
regression case targets) in addition to its own scoped `$TESTDB`. A `census()`
helper (`select datname from pg_database where datname like 'opencircuit%'`)
is captured before the run starts and compared against a second capture
after the run's own cleanup — any difference fails loudly and names both
snapshots.

**New guard-test parts 7–10** prove items 1–4 end to end (see
`scripts/db_reset_guard_test.sh`'s own header comment for the full "what it
proves" list): a bad-port `PGHOST_URL` to make the connection query itself
fail (checked both without and with `--force`), a `PATH` stub that hides
`psql` while keeping `migrate` and `bash` reachable (guarded by an in-script
sanity check that the stub genuinely hides `psql` on this machine before
trusting the result — see the note below about `hash -r`), `--force` placed
after the positional database-name argument against a live connection, and
an explicit empty-string database-name argument.

**A bash-hashing gotcha hit while writing Part 8.** The guard-test script's
own long-running process had already hashed `psql`'s real location (every
earlier `psql_admin` call does that), and a prefix-assigned `PATH=… cmd`
does not by itself invalidate bash's hash table — so `PATH="$NOPSQL_PATH"
command -v psql` inside the *same process* reported the stale hashed path
regardless of the overridden `PATH`, and the sanity check that is supposed
to abort rather than prove nothing (`FATAL: psql is reachable under /bin or
/usr/bin…`) fired even though `psql` genuinely isn't under `/bin` or
`/usr/bin` on this machine. `hash -r` before the two diagnostic `command -v`
checks fixed it. This does not affect the real assertion below it —
`$REAL_SCRIPT` is invoked as a separate process per its own shebang, and a
freshly-exec'd bash process starts with an empty hash table regardless of
its parent's — but it's worth recording since the failure mode (a sanity
check with the right intent giving the wrong answer for an unrelated shell
reason) is exactly the kind of thing this project's `CLAUDE.md` §8 catalogues.

### Item 1 — the live-connection check fails closed, including under `--force`

Made `psql`'s query itself fail and confirmed refusal rather than progress.
Every one exited **1** with
`refusing: could not determine whether '…' has other active connection(s) — the check above failed …`:

| probe | `--force`? | exit |
|---|---|---|
| `PGHOST_URL=…@localhost:1` (nothing listening) | no | 1 |
| `PGHOST_URL=…@localhost:1` | **yes** | 1 |
| `PGHOST_URL=…@localhost:1`, `--force` placed **after** the name | **yes** | 1 |
| `PGHOST_URL=postgres://nosuchuser:bad@localhost:5432` (bad credentials) | **yes** | 1 |

So the claim that this runs even under `--force` holds, and holds regardless of
where `--force` sits. `opencircuit_test` still existed after each probe. Read
against the code: the refusal is `if ! CONNS="$(psql …)"` at line 154, before
the `[ "$FORCE" != "1" ]` test at line 158 and well before the
`pg_terminate_backend` at line 170 — `--force` is not consulted on the
could-not-tell path at all.

### Item 2 — `psql` presence

Built a `PATH` containing only a symlinked `migrate` plus `/bin:/usr/bin`, and
**first proved the stub genuinely hides `psql` on this machine** (it lives at
`/opt/homebrew/bin/psql`, so `/bin:/usr/bin` does not reach it) by running
`env -i PATH=… /bin/bash -c 'command -v psql'` in a *fresh* process — which
also sidesteps the bash hash-table trap the implementation notes describe.
Under that `PATH`, `scripts/db-reset.sh opencircuit_test` printed
`error: psql not on PATH` and exited 1, with and without `--force`. The check
sits at line 141, after `migrate`'s and before anything destructive.

### Items 3 and 4 — flag parsing, probed adversarially

Fourteen probes; every one behaved correctly and none touched a database:

| input | result |
|---|---|

**The positive direction of item 3 — the flag is honoured, not merely
accepted.** Held a live `psql` connection on the private
`opencircuit0250rev2`, then ran `db-reset.sh opencircuit0250rev2 --no-seed
--force` with **both flags after the name**: it printed `resetting
opencircuit0250rev2`, terminated the holder, and ran all 20 migrations
(`opencircuit0250rev2 is at migration 20`). Without `--force` the same call
refused.

**And the message the issue complained about now tells the truth.** To reach
the *connection*-refusal text (rather than the name-scope one) I used a scoped
copy with only the name allowlist widened — never the shared databases. With a
live connection held it printed:

```
refusing: 'opencircuit0250rev2' has other active connection(s) …
  pid 90064  opencircuit  psql  ::1/128
If you're certain it's safe to disconnect them, pass --force.
```

Following that instruction *with the flag in the position the message
implies* — `… opencircuit0250rev2 --no-seed --force` — then succeeded. That is
item 3's actual complaint ("the tool prints an instruction that does not
work"), closed.
