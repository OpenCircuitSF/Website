## Description

`POST /api/unsubscribe` implements RFC 8058 one-click unsubscribe. Gmail and Yahoo bulk-sender rules make this mandatory in practice.

## Acceptance criteria

- [ ] `POST /api/unsubscribe` accepts the request with **no session and no CSRF token** — the mail provider posts it, not the user's browser
- [ ] Accepts a body of `List-Unsubscribe=One-Click` and ignores its content
- [ ] Unsubscribes synchronously and responds 200 quickly
- [ ] `GET /api/unsubscribe` never mutates — it 302s to `/unsubscribe`
- [ ] Unknown, expired, or already-used tokens still return 200 with a neutral confirmation — never a 404 or 5xx
- [ ] Sets status `unsubscribed`, stamps `unsubscribed_at` and `unsubscribe_source`, and rotates the `manage_token`
- [ ] Audit row written with the source
- [ ] Handler tests cover one-click POST, prefetch GET, unknown token, and replay

## Carried in from `#0025`'s review (2026-08-19)

- [ ] **This issue's "rotates the `manage_token`" criterion has no store
      support.** Nothing in `internal/subscribers` rotates it, and
      `FindByManageToken`'s doc comment asserts the opposite ("long-lived; no
      expiry"). Add the rotation, and correct that comment — a doc comment
      asserting an untrue invariant is exactly what let `#0025`'s laundering bug
      survive review.
- [ ] **Decide what rotation does on a `complained` row**, where `Unsubscribe` is
      a deliberate no-op. Rotating there would change the row while `status`
      correctly does not.

## Carried in from `#0031` (2026-08-19) — the post-condition both routes must share

`#0031` fixed the preference-centre unsubscribe and made an explicit decision
this issue must match, or the two unsubscribe paths will leave different state
for the same address:

- [ ] **On an already-`complained` row, do nothing at all.** No `manage_token`
      rotation, no audit row, no status change — report `no_op` with an
      explanatory message. Apply the `StatusComplained` check *before* deciding
      whether to rotate the token.
- [ ] **Otherwise rotate `manage_token`** as this issue's criteria require. The
      preference centre does **not** rotate, so after this issue lands the two
      paths differ deliberately on the normal case and must converge on the
      complained case.

Two more constraints from `#0029`/`#0030`/`#0031`'s review:

- [ ] **Do not reuse `PreferencesHandler`'s error contract.** That route answers
      **404** for an unknown token; this one requires a neutral **200** for
      unknown, expired and replayed tokens, because PRD §6.5 says a provider
      seeing errors on an unsubscribe endpoint downgrades sender reputation. The
      two are deliberately opposite — do not factor them together.
- [ ] **Reuse `audit.ActionSubscriberUnsubscribed` with `source=one_click`**
      rather than minting a new constant — but only after the no-op guard above,
      or this issue inherits the spurious-audit-row bug `#0031` just fixed.

## Notes

PRD §6.5 path 1. Three things here are counter-intuitive and all three matter:

**No CSRF protection.** The POST arrives from Gmail's infrastructure, not a browser session. Standard CSRF middleware on this route breaks one-click unsubscribe entirely.

**GET must not mutate.** Mail clients and security scanners prefetch every URL in a message. A mutating GET unsubscribes people who never clicked.

**Errors are worse than useless.** A provider that sees non-200s on the unsubscribe endpoint downgrades sender reputation. Return 200 and a neutral page for every input, including garbage.
