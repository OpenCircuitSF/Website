## Description

`POST /api/unsubscribe` implements RFC 8058 one-click unsubscribe. Gmail and Yahoo bulk-sender rules make this mandatory in practice.

## Resolution notes

> 🟢 Resolved 2026-08-20 — `POST /api/unsubscribe` is wired public with no session
> and no CSRF guard, `GET` 302s without touching the store, every input answers a
> neutral 200, and the complained row is a total no-op: no status change, no
> `manage_token` rotation, no audit row.

Independently re-verified against the diff of `c47f7db`, not the drafted
`## Verification`.

**The middleware chain, not just the handler.** `mountAndServe` registers both
methods as `mux.Handle("… /api/unsubscribe", unsubscribeLimiter.Middleware(…))`
and nothing else — no `requireSession`, no `requireAdmin`, and the route is
absent from `adminRoutes`. `outerMiddleware` is `nil` on the production path
(`servePostgres` passes it explicitly), so `mux` is the whole chain. There is no
CSRF middleware anywhere in this repository — `grep -rn --include='*.go' -i csrf`
returns only comments — so the "Gmail's POST fails while every unit test passes"
failure mode does not exist here. One caveat is filed as `#0103`; see below.

**The counter-intuitive parts, each checked:**

- **`GET` never mutates.** `Get` has no store field access at all — it builds
  `/unsubscribe[?token=…]` and calls `http.Redirect` with `StatusFound`. The
  target is a fixed relative path with only the token query-escaped into it, so
  it is not an open redirect. `TestUnsubscribeHandler_Get_NeverMutates` proves
  status, `manage_token`, and audit-row count are all untouched afterwards.
- **Every input answers 200.** Every `return` in `Post` goes through
  `writeNeutral`, which is the sole caller of `writeJSON(w, http.StatusOK, …)` —
  missing token, `ErrNotFound`, an unexpected store error, the complained no-op,
  and the success path. The body is never read, so a malformed or absent body
  cannot panic or branch: RFC 8058's marker body is ignored by construction, not
  by a parse that happens to tolerate it.
- **The complained no-op is total.** `before := sub.Status` is captured before
  `Store.Unsubscribe`, and `noOp` gates both the `RotateManageToken` call and the
  audit write, in that order — so the rotation decision is made from the
  complained check, exactly as `#0031`'s carried-in criterion requires.
  `TestUnsubscribeHandler_Post_Complained_IsSilentNoOp` asserts all four
  post-conditions including `count = 0` on `audit_log`, which is the assertion
  `#0031` bounced for lacking. Not stale: `FindByManageToken` reads fresh. There
  is a narrow read-then-act window if a complaint lands between the `SELECT` and
  the `UPDATE`; the store's `statusLockedFromNonAdmin` guard still refuses the
  write, so no data is corrupted, but the handler would take the non-no-op
  branch. Filed as `#0104` rather than held against this issue — the criterion
  here mandates the pre-call check, and this implementation performs it.
- **`RotateManageToken` really rotates.** `TestRotateManageToken_Success` asserts
  a new value, that the **old** token stops resolving via `FindByManageToken`,
  and that status is untouched; `TestRotateManageToken_ComplainedIsNoOp` asserts
  the `CASE WHEN status = complained` guard holds. Both seed their own row via
  `uniqueEmail` — no literal or seeded id is targeted (`CLAUDE.md` §8b). The
  corrected `FindByManageToken` doc comment now tells the truth and names
  `RotateManageToken` as what changes the value.
- **Audit.** `audit.ActionSubscriberUnsubscribed` reused with
  `metadata.source = "one_click"`; the commit touches no file under
  `internal/audit`, so no constant was minted. The write is unreachable on the
  no-op path.
- **`no_op` schema.** `unsubscribeResponse.NoOp` is tagged `json:"no_op"`,
  matching `admin_subscribers.go`. No third shape was introduced, and this is
  the form `#0093` names as the one to standardize on.
- **Dev mode.** `unsubscribeH` is a typed `*handlers.UnsubscribeHandler` nil, and
  both routes are inside `if unsubscribeH != nil` — a concrete pointer compared
  against nil, not an interface, so there is no nil-in-interface trap. Nothing
  dereferences it. `STORAGE=json` boots with the routes simply unregistered,
  identical to `subscribeH`/`preferencesH`/`confirmH`.

**The `SuppressionStore` decision is correct — do not re-litigate it.** `#0034`
lists `#0033` as a dependency, but a dependency is not an obligation to write to
it. PRD §6.5's state machine inserts a `suppressions` row on exactly three
events — hard bounce, complaint, five soft bounces — and the `active → one-click
→ unsubscribed` row's side effects are only `unsubscribed_at`,
`unsubscribe_source`, and rotating `manage_token`. `suppressionReasons` has no
`unsubscribed` member to write, and `unsubscribed + new signup → pending` is a
transition the PRD requires to stay open. Suppressing here would convert every
ordinary unsubscribe into a permanent block. The dependency on `#0033` is
satisfied by the suppressions table existing for the bounce/complaint paths, not
by this handler calling it.

## Root cause

Not a bug fix — this issue built a route that did not exist. Two prerequisites
this issue's own carried-in review findings called out were genuinely
missing before this work: `internal/subscribers` had no way to rotate
`manage_token` (nothing called `newToken()` after `Create`), and
`FindByManageToken`'s doc comment asserted the token is "long-lived; no
expiry" — true of its lack of a TTL, but read by a future implementer as "this
value never changes," which is exactly the untrue-invariant pattern `#0025`'s
review flagged as what let that issue's laundering bug survive.

## Fix

Added `internal/handlers/unsubscribe.go`: `UnsubscribeHandler` serving
`GET`/`POST /api/unsubscribe`, wired in `cmd/opencircuit/main.go` with its own
per-IP rate limiter (10/min, burst 5 — same scale as `preferencesLimiter`, but
a separate bucket so a burst on one route can't starve the other) and no
session/CSRF middleware.

- **`GET`** never touches the store. It 302s to `/unsubscribe`, carrying the
  token along (`?token=...`) for the confirmation view `#0036` will build.
- **`POST`** reads `token` from the URL query string (matching the
  `List-Unsubscribe` header's `?token=MANAGE_TOKEN` form) and never parses or
  validates the request body — RFC 8058's `List-Unsubscribe=One-Click` body is
  a fixed, content-free marker, and rejecting an unparseable body would
  violate "every input answers 200."
- Every path through `Post` ends in `http.StatusOK` via a single
  `writeNeutral` helper, named so the invariant is impossible to miss at each
  call site: missing token, unknown/garbage/replayed token (`ErrNotFound`), a
  transient store failure, the complained no-op, and the real-unsubscribe
  success path all answer 200.
- Captures `sub.Status` **before** calling `Store.Unsubscribe` — the same
  `before := sub.Status` pattern `PreferencesHandler.patchUnsubscribe` uses
  (`#0031`) — and uses it to decide, in order: (1) skip
  `RotateManageToken` entirely on a complained row, (2) skip the audit write
  entirely on a complained row, (3) answer the same neutral 200 either way.
  This mirrors `#0031`'s established order exactly, per this issue's carried-in
  finding that the two paths "must converge on the complained case."
- On a real (non-no-op) unsubscribe: calls `Store.Unsubscribe(source=one_click)`,
  then `Store.RotateManageToken`, then writes
  `audit.ActionSubscriberUnsubscribed` with `metadata.source=one_click` — in
  that order, so a no-op never reaches the audit write.

**Store changes (`internal/subscribers/store.go`):**

- Added `RotateManageToken(ctx, id, now) (Subscriber, error)`: generates a
  fresh token via the existing `newToken()` helper and writes it, guarded by
  the same `statusLockedFromNonAdmin` `CASE WHEN status = complained THEN
  keep ELSE update` pattern every other mutator in this package already uses
  (`Unsubscribe`, `setStatus`). This is deliberate defense-in-depth, not the
  only guard — the handler already decides not to call it at all on a
  complained row, mirroring the reviewer's own reasoning (carried into this
  issue's Notes): rotation's purpose is stopping replay of a *consumed* link,
  which has no target on a row that's already terminal, and rotating there
  would instead churn the token on every unattended hit from a provider's
  retry/prefetch infrastructure.
- Corrected `FindByManageToken`'s doc comment: it no longer asserts the token
  never changes, and instead documents that `RotateManageToken` is what
  changes it, when, and why the preference center (`#0031`) deliberately
  never calls it.

**Suppression list decision (`#0033`'s `SuppressionStore`):** left untouched
by this handler, on purpose. `suppressionReasons` (`suppressions.go`) is a
closed set — `hard_bounce`, `complaint`, `manual`, `repeated_soft_bounce` —
with no `unsubscribed` member. PRD §6.5's state machine only inserts a
suppression row on a hard bounce or a complaint; a plain unsubscribe (any
source) leaves the door open to `RestartSignup` (unsubscribed + new signup →
pending, fresh confirm). Suppressing on every one-click hit would silently
convert every ordinary unsubscribe into a permanent block, contradicting the
table this endpoint is specified by.

**`no_op` response schema:** matched `admin_subscribers.go`'s
`suppressResponse.NoOp` shape (`json:"no_op"`, no `omitempty`) rather than
`preferences.go`'s (`json:"no_op,omitempty"`) or inventing a third shape.
`#0093` (open, untouched here) already tracks that the two existing shapes
disagree and names the no-`omitempty` form as the one to standardize on —
this handler's `unsubscribeResponse` is built to already match that outcome.

## Acceptance criteria

- [x] `POST /api/unsubscribe` accepts the request with **no session and no CSRF token** — the mail provider posts it, not the user's browser
- [x] Accepts a body of `List-Unsubscribe=One-Click` and ignores its content
- [x] Unsubscribes synchronously and responds 200 quickly
- [x] `GET /api/unsubscribe` never mutates — it 302s to `/unsubscribe`
- [x] Unknown, expired, or already-used tokens still return 200 with a neutral confirmation — never a 404 or 5xx
- [x] Sets status `unsubscribed`, stamps `unsubscribed_at` and `unsubscribe_source`, and rotates the `manage_token`
- [x] Audit row written with the source
- [x] Handler tests cover one-click POST, prefetch GET, unknown token, and replay

      survive review.
- [x] **Decide what rotation does on a `complained` row**, where `Unsubscribe` is
      a deliberate no-op. Rotating there would change the row while `status`
      correctly does not.

## Carried in from `#0031` (2026-08-19) — the post-condition both routes must share

`#0031` fixed the preference-centre unsubscribe and made an explicit decision
this issue must match, or the two unsubscribe paths will leave different state
for the same address:

- [x] **On an already-`complained` row, do nothing at all.** No `manage_token`
      rotation, no audit row, no status change — report `no_op` with an
      explanatory message. Apply the `StatusComplained` check *before* deciding
      whether to rotate the token.
- [x] **Otherwise rotate `manage_token`** as this issue's criteria require. The
      preference centre does **not** rotate, so after this issue lands the two
      paths differ deliberately on the normal case and must converge on the
      complained case.

Two more constraints from `#0029`/`#0030`/`#0031`'s review:

- [x] **Do not reuse `PreferencesHandler`'s error contract.** That route answers
      **404** for an unknown token; this one requires a neutral **200** for
      unknown, expired and replayed tokens, because PRD §6.5 says a provider
      seeing errors on an unsubscribe endpoint downgrades sender reputation. The
      two are deliberately opposite — do not factor them together.
- [x] **Reuse `audit.ActionSubscriberUnsubscribed` with `source=one_click`**
      rather than minting a new constant — but only after the no-op guard above,
      or this issue inherits the spurious-audit-row bug `#0031` just fixed.

## Two more from `#0031`'s review (2026-08-19)

- [x] **"Do nothing at all" must not become "answer an error".** PRD §6.5 still
      requires a neutral **200** for a complained row — the no-op has to be
      silent to the provider. That is the opposite of the preference centre's
      `404`, and the difference is deliberate.
- [x] **If anyone later wants telemetry on complained addresses hitting
      one-click, it must use a distinct action name** — never
      `subscriber.unsubscribed`. A row claiming an unsubscribe that never
      happened is indistinguishable from a real one in the admin audit view and
      corrupts the record `#0038` and `#0060` read. That distinction is the whole
      reason `#0031` bounced.

The reviewer also endorsed the no-rotation decision with a reason specific to
this issue: this is the RFC 8058 endpoint that **mail providers and security
scanners POST automatically**, so a rotating no-op would churn the token on every
unattended hit — invalidating every live footer link the person holds, as the
price of an action that changed nothing. Rotation's actual purpose, stopping
replay of a consumed unsubscribe link, has no target on a row that is already
terminal and refused by every mutator.

## Notes

PRD §6.5 path 1. Three things here are counter-intuitive and all three matter:

**No CSRF protection.** The POST arrives from Gmail's infrastructure, not a browser session. Standard CSRF middleware on this route breaks one-click unsubscribe entirely.

**GET must not mutate.** Mail clients and security scanners prefetch every URL in a message. A mutating GET unsubscribes people who never clicked.

**Errors are worse than useless.** A provider that sees non-200s on the unsubscribe endpoint downgrades sender reputation. Return 200 and a neutral page for every input, including garbage.
