## Description

All three live workshops carry a `cover_image` — `/soldering.jpg` and
`/programming_leds.jpg` — and both resolve `200` in production.

**Neither file exists in this repository.** Not in the working tree, not in
`web/public/`, and not in any commit on any branch. They live only in
`/opt/opencircuit/web/public/` on the box, as **untracked** files:

	-rw-r--r-- 66301 Sep  1 03:59 programming_leds.jpg
	-rw-r--r-- 89179 Sep  1 03:59 soldering.jpg

`git ls-files web/public/` on the deploy checkout lists the fonts, favicons and
hero images — and not these two. They reach production because
`npm run build` sweeps `web/public/` into `dist/`, which the binary embeds.

## Why this is urgent

**A deploy is imminent** (the campaign-archive work). The images survive a
`git pull` into the existing checkout, because git does not touch untracked
files. They do **not** survive:

- a fresh clone,
- `git clean`,
- rebuilding on a different host,
- restoring the box from scratch.

Any of those silently reverts all three workshops to the generic
`og-default.png` card and breaks two live image URLs. The failure is silent —
nothing errors, the pages simply lose their images.

This is `#0153`'s recorded hazard — content "put on the server outside the
product" — landing for real.

## A related observation, not a defect

`introduction-to-soldering` and `introduction-to-soldering-2` share one cover
image, so they unfurl identically today. That is correct behaviour —
`cover_image` is the override and both workshops set it to the same file — but
it is worth knowing, since it is the same *visible* symptom `#0273` exists to
fix for workshops with no cover at all.

## Decision (criterion 6)

**Build a mechanism — but not the one the criterion sketches, and not in this
issue.** The mechanism belongs in `scripts/deploy.sh`, and it is reported for
filing as its own issue rather than written by this review pass.

The reasoning, in the order the alternatives were eliminated:

- **The guard the criterion sketches cannot be built.** `cover_image` is
  admin-entered runtime data living in production's `workshops` table. Nothing
  in this repository holds those values — `git grep cover_image` outside
  `issues/` finds the migration that creates the column, the validators, the
  types, the SEO card code and their tests, and never a literal
  `/soldering.jpg` except inside test fixtures. A repository test therefore has
  nothing to scan, and no test connects to the production database. "Assert the
  workshops' `cover_image` values resolve to committed files" has no home.
- **A repository-side guard on `web/public/` would be tautological.** In any
  checkout of this repository every file under `web/public/` is tracked by
  construction; that is what a checkout *is*. The untracked file only ever
  exists in the **deploy checkout on the box**, where no test runs. A guard that
  can only be true is not a guard.
- **So the only place a mechanism can sit is the deploy path — and the signal
  already exists there and was ignored.** `scripts/deploy.sh`'s preflight
  already runs `git status --porcelain` and prints
  `note: working tree has uncommitted changes`. It fired on every deploy for the
  two days these files sat on the box. It was useless because it is
  *permanently* on: `web/dist/index.html` is modified in the deploy checkout
  after every single build (`CLAUDE.md` §8b), so the note never distinguishes a
  normal deploy from this one. A notice that is always lit carries no
  information.
- **The mechanism is consequently small and precise.** Keep the existing
  informational note for general dirt, and add a *hard* gate for untracked
  entries under `web/public/` specifically — the one directory whose contents
  `npm run build` copies verbatim into the shipped `dist/`, which is exactly how
  these two files reached production. `web/dist/index.html` shows as `M` and
  lives outside `web/public/`, so it cannot trip it; the check is one
  `git status --porcelain -- web/public/` filtered to `??`, failing with the
  offending names.

**Why not "record only", against the `#0330`/`#0347`/`#0356`/`#0381`
precedent.** That precedent is real and was weighed. It does not carry here, for
two reasons:

- Those four recorded limits in *tooling*, where the mechanism would have been a
  new guard test with its own harness and the failure mode was a weaker check.
  Here the mechanism is a few lines in a script that already makes the very call
  it needs, and the failure mode is production silently losing images while
  nothing errors.
- More decisively: **this hazard has already been recorded once, and recurred
  anyway.** `#0153`'s `## Decision` (2026-08-24) states in terms that an admin
  can reference an image "only if someone has already put it on the server by
  some means outside the product". That is this hazard, written down. Eight days
  later exactly that shipped, untracked, and was found only by an unrelated
  planning pass. On these specific facts, recording is the option with a
  demonstrated failure record.

**Why this review pass did not write it.** It is a hard failure on the
production deploy path with a deploy imminent, and a pass that authors it is
also the only pass that reviews it. It deserves its own implement-and-review
cycle. Reported to the orchestrator for filing.

## An operational consequence of this commit — read before the next deploy

**The next `git pull` on the box will abort until the two untracked copies are
removed.** Byte-identical content does not save it: git refuses to overwrite an
untracked working-tree file with a tracked one regardless of whether the bytes
match. Measured in a throwaway clone pinned to the box's current `HEAD`
(`ef0a58f`) with the two files present and untracked:

	error: The following untracked working tree files would be overwritten by merge:
		web/public/programming_leds.jpg
		web/public/soldering.jpg
	Please move or remove them before you merge.
	Aborting

Exit code `1`, `HEAD` unmoved. The remedy is one command on the box, and it is
safe precisely because the bytes are already committed and verified identical:

	rm /opt/opencircuit/web/public/soldering.jpg /opt/opencircuit/web/public/programming_leds.jpg

The same throwaway clone was then fast-forwarded successfully, and both files
landed as tracked files with the hashes below. This fails **loudly**, not
silently, so nothing is at risk — but it will stop a deploy that is not
expecting it.

  `git archive b4ba044` was extracted to a throwaway scratch directory outside

  scratch copy, and `git status --porcelain` on the repository showed no change
  to it before or after.

- **Criterion 5 — and `--porcelain` alone is NOT sufficient to answer it.**
  Re-running `git -C /opt/opencircuit status --porcelain` reproduces exactly
  what the commit message claims: the same two `??` entries and the known
  modified `web/dist/index.html`. But `--porcelain` cannot see an **ignored**
  file, and an asset placed on the box under an ignored path would be invisible
  to it while still reaching `dist/`. So `--ignored` was run as well. It adds
  only `web/node_modules/` and the `web/dist/` build outputs, and every ignored
  `web/dist/` entry derives from a tracked `web/public/` source — there is no
  ignored file on the box that is content rather than build product.
  `git ls-files --others --exclude-standard` independently agrees on the same
  two files. Separately, the Apache document root was listed: it holds leftovers
  from the retired static placeholder plus `.well-known/atproto-did`, and only
  `/.well-known/` is excepted from the proxy (§7), so none of the rest is
  served. **Conclusion: these two were the only ones, but the command named in
  the criterion could not have established that on its own.**

- **The related observation — still true, still not a defect.**
  `introduction-to-soldering` and `introduction-to-soldering-2` both carry
  `/soldering.jpg`, read from production's `workshops` table this pass. That is
