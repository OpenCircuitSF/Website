## Description

The home hero's CRT screen (`#0270`, live data from `#0274`) types a fixed
eight-command session out of a hard-coded array,
`CRT_SESSION` in `web/src/lib/crtScreen.ts`. Two of the eight are replaced at
runtime with real data — `workshops --next` from `GET /api/workshops` and
`subscribe --interests` from `GET /api/list-stats` — and the other six are
illustrative brand copy compiled into the bundle.

Changing a word on that screen is currently a code edit, a rebuild and a
deploy. The user wants to change it up from time to time, which makes it
content, not code.

**This issue moves the session into the database and gives it an admin
screen.** Each command becomes a row with its output lines, an `active` flag
and an explicit order; the admin console gets a CRT section that lists them,
toggles them, reorders them and edits their text. The live-data commands stay
live — they become rows too, marked as fed by a named data source, with their
stored lines acting as the fallback when the fetch fails.

**And one new live figure**: the number of **active subscribers per interest**.
The list currently has 4 subscribers on `microcontrollers`; that is a good
number to show on a green phosphor screen, and it is the sort of thing this
screen exists to say. `GET /api/list-stats` grows an `interests` array and the
CRT gets a source that renders it.

### Why Phase 9

Phase 9 is "Reusable as a dependency". `#0232` is about making branding and
copy configurable rather than compiled in, and `#0246` (`/crt`) notes that a
route whose entire content is one configurable brand object is a forcing
function for that work. The CRT session is the single largest block of
hard-coded brand copy in the SPA. Moving it to rows is exactly the extraction
`#0232` describes, done for the one surface that most needs it.

## Design

### 1. Schema — a new table, a new migration

`migrations/000028_create_crt_commands.up.sql` (and its `.down.sql`).
**Append-only: the greenfield exception expired 2026-08-25** (`CLAUDE.md` §1),
so this is a new file and nothing under `000001`–`000027` is touched.

```sql
CREATE TABLE crt_commands (
    id         BIGSERIAL PRIMARY KEY,
    slug       TEXT UNIQUE NOT NULL,
    command    TEXT NOT NULL,
    output     TEXT NOT NULL,          -- newline-separated lines
    source     TEXT NOT NULL DEFAULT 'static',
    sort_order INT  NOT NULL DEFAULT 0,
    active     BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ
);
```

Modelled deliberately on `interests` (`migrations/000009`): same
`slug`/`sort_order`/`active` shape, the same `^[a-z0-9]+(-[a-z0-9]+)*$` slug
CHECK constraint, the same idempotent `ON CONFLICT DO NOTHING` seed. That
table's admin section already has working ↑/↓ reorder controls, and this one
should reuse the pattern rather than invent a second one.

`source` is a CHECK-constrained enum:

| `source` | Output at render time |
|---|---|
| `static` | the stored `output` lines, verbatim |
| `workshops` | `crtWorkshopLines()` over `GET /api/workshops` |
| `list_stats` | `crtListLines()` over `GET /api/list-stats` |
| `interests` | new: active-subscriber counts per interest (§3) |

**A live row's stored `output` is its fallback, not decoration.** `#0274`'s
rule stands and is the reason the column is `NOT NULL` for every source: a
failed fetch leaves the stored copy on the glass. The screen is decorative and
must never degrade to a blank block or an error string.

Storing the lines as newline-separated `TEXT` rather than `TEXT[]`/`jsonb`
keeps the admin editor a plain `<textarea>` and the store layer trivial. Split
on `\n` at read time; trim trailing empties.

### 2. Backend

- `internal/crt/` — a new store package owning the table, per `CLAUDE.md` §1
  (SQL lives in the package that owns the table). `List(ctx)`, `ListActive(ctx)`,
  `Create`, `Patch`, `Delete`, `Reorder`.
- **Admin CRUD**, mounted in `adminRoutes()` behind `RequireSession` +
  `RequireAdmin`, mirroring the interests routes at
  `cmd/opencircuit/main.go:973-976`:

  ```
  GET    /admin/crt-commands
  POST   /admin/crt-commands
  PATCH  /admin/crt-commands/{id}
  DELETE /admin/crt-commands/{id}
  ```

  Every mutation writes an `audit` entry (`crt_command.created`,
  `.updated`, `.deleted`), as the interests handler does.
- **Public read**: `GET /api/crt-session` returning
  `{"commands":[{"cmd":"…","out":["…"],"source":"static"}]}` — active rows
  only, in `sort_order`, and **nothing else**: no ids, no `active` flag, no
  timestamps. Cached in-process on the same 60s TTL as
  `PublicListStatsHandler`, and served with `Cache-Control: public, max-age=60`.
  It is hit by every home-page visitor.
- **`STORAGE=json` has no mailing list** (`CLAUDE.md` §5) and
  `internal/devstore` will not implement this table. `GET /api/crt-session`
  must be absent under `STORAGE=json`, and the SPA must fall back to the
  compiled-in `CRT_SESSION` constant on any non-OK response — which is also
  what makes the migration safe to deploy before the rows exist.

### 3. Per-interest subscriber counts

Extend `GET /api/list-stats` with an `interests` array:

```json
{"confirmed": 37, "pending": 5,
 "interests": [{"slug":"microcontrollers","name":"Microcontrollers…","count":4}]}
```

Counts are of **`active` subscribers only**, joined through
`subscriber_interests`, restricted to `active` interests, ordered by count
descending then `sort_order`. Zero-count interests are omitted.

**On the enumeration-oracle question** (`CLAUDE.md` §9, and the long comment in
`internal/handlers/public_list_stats.go`): these counts are exact and that is
safe, by exactly the argument that already makes `confirmed` exact. Moving an
interest count requires confirming a subscription, which requires clicking a
link in an email only the address's owner receives — an attacker cannot move
the number for an address they do not control, and watching it move says
nothing about any address they are probing. Only `pending` needed the bucket,
and `pending` is untouched here. **Write this reasoning into the handler's doc
comment**; the next reader will otherwise reopen it.

A new `crtInterestLines()` in `crtScreen.ts` renders them in the screen's
lowercase register and 36-char budget, e.g.

```
> topics --subscribers
microcontrollers ...... 4
soldering ............. 3
homelab ............... 1
12 topics. pick your own.
```

### 4. Admin UI

A new `crt` section in `web/src/views/Admin.svelte`'s `Section` union and
subtab bar, backed by `web/src/views/admin/CrtCommands.svelte` and a
`web/src/lib/crtCommands.ts` module holding the logic (`CLAUDE.md` §1: logic in
plain TypeScript, components thin).

The section lists rows in order, each with:

- an **active** checkbox — inactive rows are skipped by the session;
- **↑ / ↓** controls, the same interaction `Admin.svelte` already implements for
  interests;
- the command text and a `<textarea>` for output lines;
- the `source` selector, with the live sources labelled so it is clear the
  stored lines are a fallback;
- create and delete.

Live-preview is out of scope. Seeing the change on the home page is one click.

### 5. Seed rows — "some fun options"

Seed the eight existing `CRT_SESSION` entries verbatim, with
`workshops --next` as `source='workshops'` and `subscribe --interests` as
`source='list_stats'` so today's behaviour is preserved exactly. Then seed
these as **inactive** rows the user can switch on — period-correct for a green
phosphor terminal, in the existing lowercase register:

```
> fortune                    solder flows toward heat.
                             so do good ideas.

> sl                         ( a train goes past. )
                             you typed it wrong. enjoy.

> ping bench                 bench alive, 0.4ms
                             irons hot. seats open.

> man patience               PATIENCE(1)
                             hold the iron still.
                             count to three.
                             the joint will tell you.

> finger @members            37 logged on
                             0 idle
                             all soldering.

> cat /etc/motd              no ads. no trackers.
                             no cover charge.
                             bring your hands.

> topics --subscribers       (source='interests', live)

> date                       it is always a good day
                             to fix something.

> ls /dev                    ttyUSB0  ttyUSB1
                             i2c-1  spidev0.0
                             plug something in.

> history | tail             blinked an led
                             burned a finger
                             shipped a board
```

Exact copy is the implementer's to finish; the register — lowercase, short,
dry, ≤36 characters a line — is not. `crtTruncate()` enforces the width; do
not lean on it, write to it.

## Open questions

1. **Does `/crt` (`#0246`) consume the same rows?** It should — `#0246`'s
   "one shared source" criterion is about exactly this drift. This issue builds
   the source; `#0246` consumes it when it is built. Worth a line in `#0246`.
2. **Should the interest counts be shown as a bar rather than a number?** A
   `microcontrollers ████░░ 4` histogram is more phosphor-authentic than a
   dotted leader. Left to the implementer's taste inside the 36-char budget.
3. **Rate of change.** The public endpoint caches for 60s, so an admin edit
   takes up to a minute to appear. That is fine, and the admin screen should
   say so rather than leave the user wondering whether the save took.

## Notes

Requested by the user on 2026-09-03, filed under Phase 9 at their direction.

**The compiled-in `CRT_SESSION` does not go away.** It is the fallback for
`STORAGE=json`, for a pre-seed deploy, and for a failed fetch. That means two
copies of the session exist by design — the constant and the seed rows — and
they are allowed to drift, because the constant is a floor rather than a
mirror. Say so in the constant's doc comment, or the next reader will file a
drift issue against it.

**Do not weaken `POST /api/subscribe`'s uniform 202** (`CLAUDE.md` §9). Nothing
here touches it, and nothing here may become a second route to the same
information: per-interest counts are exact only because confirmation requires
the address owner's own click.

`void loadSession().then(() => loadLiveData()).then(() => session())`, with
`script` mutated twice along the way. New: `void crtLoadScript().then((s) => {
script = s; void session(); })`, with `script` assigned once. The only
observable difference would be a reader of `script` in the window between the
two old assignments — and `grep` shows `script` is read only inside `session()`
(lines 168 and 186), which in both versions runs strictly after the chain
resolves. A rejection from either version leaves `session()` uncalled
identically.

### 2. Is the named defect closed? — yes in substance, and the residual's failure mode is the safe one

Answering the question directly, without softening it: **there is still no test
that fails if `Home.svelte` stops calling `crtLoadScript`.** No test in
`web/src/` references `Home.svelte`; the only hits are prose in comments and
`liveRegionGuard.structuralGuard.test.ts`'s repo-wide `.svelte` sweep, which
does not look at this wiring. In the strictest reading, the untested seam has
been *moved*, from ~70 lines to two.

I judge the criterion met anyway, for two reasons I want on the record rather
than assumed:

1. **The remedy was the previous reviewer's own preferred one, followed
   exactly.** That review wrote the `crtLoadScript` signature, the two-line
   `onMount` replacement, and the six test cases, and offered the structural
   guard only as an "acceptable alternative if the extraction is judged too
   invasive". The implementer took the preferred branch and transcribed it.
2. **The residual seam's failure mode is the criterion's own pass condition.**
   `script` is initialised to `crtFallbackScript()` before the call. If the
   wiring stopped calling `crtLoadScript`, or stopped assigning its result, the
   screen would run the compiled-in `CRT_SESSION` — which is precisely what
   "with `/api/crt-session` returning 404 or 500, the home CRT still runs the
   compiled-in `CRT_SESSION`" demands, and what `#0274`'s never-blank rule
   demands. The drift direction that the missing test permits degrades *toward*
   the safe state, never toward a blank block or an error string. That is a
   materially different risk from the pre-fix state, where the 404/500 decision
   itself was unobserved.

What the residual *does* permit is a silent loss of the admin-editable feature
(edits, reorders and deactivations stopping at the API and never reaching the
glass) without any test failing. That is worth a small follow-up, noted below —
not a second bounce, since the two lines at risk are the two lines the previous
review itself specified.

### 3. The byte-identity claim holds, and its oracle is independent

`crtLoadScript` per-row-failure test asserts
`expect(script[0].out).toEqual(['stored ws line one', 'stored ws line two'])`
against a **hand-written literal**, not against `sessionResp.commands[0].out`.
The expected bytes are therefore a second, independent representation of the
fact, not a reference to the subject — `CLAUDE.md` §8's "a copy of the answer
stored next to the question" hazard is avoided. `toEqual` on an array of
strings is byte equality for strings, and the assertion fails if
`crtSessionToScript`/`crtEnrichStep` alter, reorder or replace the stored
lines. The sibling `static` row's assertion pins the "other rows untouched"
half.

### 4. The short-circuit stub would record a call if one happened

`makeFetch` does `calls.push(url)` **before** the handler lookup, so an
unexpected `/api/workshops` request is recorded and only then throws. The throw
would be swallowed by `crtLoadScript`'s own `catch`, so the throw alone would
not fail the test — but `expect(calls).not.toContain('/api/workshops')` would.
The assertion is genuinely falsifiable, and the companion
`expect(script[1].out[0]).toBe('3 confirmed subscribers')` rules out the
"passes because nothing ran" degenerate case.

### 5. Render-time `crtTruncate` — both draw sites covered, one narrower gap noted

Both places `Home.svelte` writes a step's stored output to the canvas now
truncate: the `reduce.matches` branch (`...step.out.map((l) => crtTruncate(l))`)
and the typed loop (`push(crtTruncate(line))`). They cannot diverge silently in
the sense that matters — both go through the same function with the same
default `max`.

The no-op test is falsifiable and does not restate the constant: it asserts
`crtTruncate(line) === line` for every line of every `CRT_SESSION` entry, and
measured against the source, `CRT_LINE_CHARS` is 36 while the longest seeded
line is 30 (`'makerspaces, co-working rooms,'`). Lowering the constant below 30
fails the test; there are six characters of slack, which is honest headroom
rather than a tautology.

**Narrower gap, not a defect against instructions:** truncation and the admin
warning both cover a row's `out` and not its `cmd`. `'> ' + step.cmd` reaches
`typeLine`/`fillText` unclipped at both draw sites, and `crtOverBudgetLines`
inspects only `output`. The previous review's follow-up text asked for "stored
`out` lines" specifically, so this pass did what was asked; the longest seeded
command is `> subscribe --interests` at 23 characters, so nothing overflows
today. Noted for the follow-up issue.

### 6. The omitted `role="status"` on the per-row edit warning — a real, minor accessibility defect

Judged on accessibility, not on guard convenience, as it should be:

- The create form's warning is `role="status"` and is announced. The per-row
  editor's warning is the **same message, same wording, same trigger** and is
  silent to a screen-reader user. The only stated reason for the difference is
  that the second one would trip `liveRegionGuard.structuralGuard.test.ts`.
  **That is the wrong direction of reasoning** — shaping markup so a guard stays
  quiet — and it should be recorded as such even though the pass is otherwise
  careful.
- The "per-keystroke hint isn't the class of state change the rule protects"
  argument is also weaker than it looks. The message only changes when a line
  crosses the 36-character budget or when the set of over-budget line numbers
  changes; it is a state change, not keystroke chatter.
- The guard is not actually an obstacle here, it is the mechanism. The editor
  sits in `{#if editing[c.id]}`, a branch that mounts once when the admin
  clicks Edit and stays mounted across editing, whose mounting is not driven by
  the warning's own presence, and which contains a full form (well past #0306's
  8-`RegularElement` threshold). That is exactly the shape
  `KNOWN_STABLE_BRANCH_SITES` exists to admit — the same argument
  `WorkshopEditor.svelte`'s `unsavedInterestsHint` entry already rests on.

**Remedy, for the follow-up issue rather than a bounce:** add `role="status"`
to `CrtCommands.svelte`'s per-row edit warning `<p class="text-warn">` and add
one `KNOWN_STABLE_BRANCH_SITES` entry for it, whose justification states the
persistence argument above (branch mounts on Edit, stays mounted across
editing, warning's presence does not drive the branch). Replace the code
comment's guard-convenience reasoning at the same time.

I am **not bouncing on this**, and the reason is scope rather than merit: the
entire line-width feature is work the previous review explicitly designated
"worth filing as a follow-up issue", not a `#0393` acceptance criterion. It
came in as a bonus and is otherwise well done. Per `CLAUDE.md` §9 I am
reporting it for the orchestrator to number rather than filing it.

### 7. No regression in `Home.svelte`

Three types (`CrtWorkshop`, `CrtInterestCount`, `CrtSessionResponse`) and two
functions (`crtSessionToScript`, `crtEnrichStep`) were dropped from the import,
and `crtLoadScript`/`crtTruncate` added. `grep` confirms none of the five
dropped names appears anywhere else in the file, and `svelte-check` is 0/0
across 294 files — which is what proves there is no dangling reference, since
an unresolved identifier in a `.svelte` file is an error there, not a silent
`undefined`. All five remain exported from `crtScreen.ts` and are still
exercised by `crtScreen.test.ts`.

`#0270`/`#0274` behaviours are untouched by the diff: `reduce.matches`, the
`visibilitychange` listener, the `IntersectionObserver`, the blink interval,
the `generation` guard and the whole teardown are byte-identical.

### 8. `#0274`'s never-blank rule still holds, including the new empty case

`crtSessionToScript` returns `crtFallbackScript()` for `null`, `undefined`, a
non-array `commands`, and an empty `commands` — so an admin who deactivates
every row gets the compiled-in session, not an empty screen, and that path is
now asserted through the real orchestration
(`'/api/crt-session': okJson({ commands: [] })` ⇒ `toEqual(crtFallbackScript())`).
A malformed row that made `[...c.out]` throw is caught by `crtLoadScript`'s own
`try`, which is inside the same block, and also lands on the fallback. The
reduced-motion branch reads `script[0]`, which those guarantees keep non-empty.
