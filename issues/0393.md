| | |

| **Status** | open |

## Description

The home hero's CRT screen (`#0270`, live data from `#0274`) types a fixed
eight-command session out of a hard-coded array,
`CRT_SESSION` in `web/src/lib/crtScreen.ts`. Two of the eight are replaced at
runtime with real data — `workshops --next` from `GET /api/workshops` and
`subscribe --interests` from `GET /api/list-stats` — and the other six are
illustrative brand copy compiled into the bundle.

Changing a word on that screen is currently a code edit, a rebuild and a
deploy. The user wants to change it up from time to time, which makes it
content, not code.

**This issue moves the session into the database and gives it an admin
screen.** Each command becomes a row with its output lines, an `active` flag
and an explicit order; the admin console gets a CRT section that lists them,
toggles them, reorders them and edits their text. The live-data commands stay
live — they become rows too, marked as fed by a named data source, with their
stored lines acting as the fallback when the fetch fails.

**And one new live figure**: the number of **active subscribers per interest**.
The list currently has 4 subscribers on `microcontrollers`; that is a good
number to show on a green phosphor screen, and it is the sort of thing this
screen exists to say. `GET /api/list-stats` grows an `interests` array and the
CRT gets a source that renders it.

### Why Phase 9

Phase 9 is "Reusable as a dependency". `#0232` is about making branding and
copy configurable rather than compiled in, and `#0246` (`/crt`) notes that a
route whose entire content is one configurable brand object is a forcing
function for that work. The CRT session is the single largest block of
hard-coded brand copy in the SPA. Moving it to rows is exactly the extraction
`#0232` describes, done for the one surface that most needs it.

## Design

### 1. Schema — a new table, a new migration

`migrations/000028_create_crt_commands.up.sql` (and its `.down.sql`).
**Append-only: the greenfield exception expired 2026-08-25** (`CLAUDE.md` §1),
so this is a new file and nothing under `000001`–`000027` is touched.

```sql
CREATE TABLE crt_commands (
    id         BIGSERIAL PRIMARY KEY,
    slug       TEXT UNIQUE NOT NULL,
    command    TEXT NOT NULL,
    output     TEXT NOT NULL,          -- newline-separated lines
    source     TEXT NOT NULL DEFAULT 'static',
    sort_order INT  NOT NULL DEFAULT 0,
    active     BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ
);
```

Modelled deliberately on `interests` (`migrations/000009`): same
`slug`/`sort_order`/`active` shape, the same `^[a-z0-9]+(-[a-z0-9]+)*$` slug
CHECK constraint, the same idempotent `ON CONFLICT DO NOTHING` seed. That
table's admin section already has working ↑/↓ reorder controls, and this one
should reuse the pattern rather than invent a second one.

`source` is a CHECK-constrained enum:

| `source` | Output at render time |
|---|---|
| `static` | the stored `output` lines, verbatim |
| `workshops` | `crtWorkshopLines()` over `GET /api/workshops` |
| `list_stats` | `crtListLines()` over `GET /api/list-stats` |
| `interests` | new: active-subscriber counts per interest (§3) |

**A live row's stored `output` is its fallback, not decoration.** `#0274`'s
rule stands and is the reason the column is `NOT NULL` for every source: a
failed fetch leaves the stored copy on the glass. The screen is decorative and
must never degrade to a blank block or an error string.

Storing the lines as newline-separated `TEXT` rather than `TEXT[]`/`jsonb`
keeps the admin editor a plain `<textarea>` and the store layer trivial. Split
on `\n` at read time; trim trailing empties.

### 2. Backend

- `internal/crt/` — a new store package owning the table, per `CLAUDE.md` §1
  (SQL lives in the package that owns the table). `List(ctx)`, `ListActive(ctx)`,
  `Create`, `Patch`, `Delete`, `Reorder`.
- **Admin CRUD**, mounted in `adminRoutes()` behind `RequireSession` +
  `RequireAdmin`, mirroring the interests routes at
  `cmd/opencircuit/main.go:973-976`:

  ```
  GET    /admin/crt-commands
  POST   /admin/crt-commands
  PATCH  /admin/crt-commands/{id}
  DELETE /admin/crt-commands/{id}
  ```

  Every mutation writes an `audit` entry (`crt_command.created`,
  `.updated`, `.deleted`), as the interests handler does.
- **Public read**: `GET /api/crt-session` returning
  `{"commands":[{"cmd":"…","out":["…"],"source":"static"}]}` — active rows
  only, in `sort_order`, and **nothing else**: no ids, no `active` flag, no
  timestamps. Cached in-process on the same 60s TTL as
  `PublicListStatsHandler`, and served with `Cache-Control: public, max-age=60`.
  It is hit by every home-page visitor.
- **`STORAGE=json` has no mailing list** (`CLAUDE.md` §5) and
  `internal/devstore` will not implement this table. `GET /api/crt-session`
  must be absent under `STORAGE=json`, and the SPA must fall back to the
  compiled-in `CRT_SESSION` constant on any non-OK response — which is also
  what makes the migration safe to deploy before the rows exist.

### 3. Per-interest subscriber counts

Extend `GET /api/list-stats` with an `interests` array:

```json
{"confirmed": 37, "pending": 5,
 "interests": [{"slug":"microcontrollers","name":"Microcontrollers…","count":4}]}
```

Counts are of **`active` subscribers only**, joined through
`subscriber_interests`, restricted to `active` interests, ordered by count
descending then `sort_order`. Zero-count interests are omitted.

**On the enumeration-oracle question** (`CLAUDE.md` §9, and the long comment in
`internal/handlers/public_list_stats.go`): these counts are exact and that is
safe, by exactly the argument that already makes `confirmed` exact. Moving an
interest count requires confirming a subscription, which requires clicking a
link in an email only the address's owner receives — an attacker cannot move
the number for an address they do not control, and watching it move says
nothing about any address they are probing. Only `pending` needed the bucket,
and `pending` is untouched here. **Write this reasoning into the handler's doc
comment**; the next reader will otherwise reopen it.

A new `crtInterestLines()` in `crtScreen.ts` renders them in the screen's
lowercase register and 36-char budget, e.g.

```
> topics --subscribers
microcontrollers ...... 4
soldering ............. 3
homelab ............... 1
12 topics. pick your own.
```

### 4. Admin UI

A new `crt` section in `web/src/views/Admin.svelte`'s `Section` union and
subtab bar, backed by `web/src/views/admin/CrtCommands.svelte` and a
`web/src/lib/crtCommands.ts` module holding the logic (`CLAUDE.md` §1: logic in
plain TypeScript, components thin).

The section lists rows in order, each with:

- an **active** checkbox — inactive rows are skipped by the session;
- **↑ / ↓** controls, the same interaction `Admin.svelte` already implements for
  interests;
- the command text and a `<textarea>` for output lines;
- the `source` selector, with the live sources labelled so it is clear the
  stored lines are a fallback;
- create and delete.

Live-preview is out of scope. Seeing the change on the home page is one click.

### 5. Seed rows — "some fun options"

Seed the eight existing `CRT_SESSION` entries verbatim, with
`workshops --next` as `source='workshops'` and `subscribe --interests` as
`source='list_stats'` so today's behaviour is preserved exactly. Then seed
these as **inactive** rows the user can switch on — period-correct for a green
phosphor terminal, in the existing lowercase register:

```
> fortune                    solder flows toward heat.
                             so do good ideas.

> sl                         ( a train goes past. )
                             you typed it wrong. enjoy.

> ping bench                 bench alive, 0.4ms
                             irons hot. seats open.

> man patience               PATIENCE(1)
                             hold the iron still.
                             count to three.
                             the joint will tell you.

> finger @members            37 logged on
                             0 idle
                             all soldering.

> cat /etc/motd              no ads. no trackers.
                             no cover charge.
                             bring your hands.

> topics --subscribers       (source='interests', live)

> date                       it is always a good day
                             to fix something.

> ls /dev                    ttyUSB0  ttyUSB1
                             i2c-1  spidev0.0
                             plug something in.

> history | tail             blinked an led
                             burned a finger
                             shipped a board
```

Exact copy is the implementer's to finish; the register — lowercase, short,
dry, ≤36 characters a line — is not. `crtTruncate()` enforces the width; do
not lean on it, write to it.

## Acceptance criteria

- [ ] `migrations/000028_create_crt_commands.{up,down}.sql` exists; `000001`–`000027` are byte-identical to `HEAD`
- [ ] `up` then `down` then `up` against a scratch database leaves `schema_migrations` clean and not dirty
- [ ] The table carries the slug-format CHECK and a `source` CHECK, and its seed is idempotent under a re-run
- [ ] `internal/crt` owns every SQL statement touching `crt_commands`; no SQL in any handler
- [ ] The four `/admin/crt-commands` routes exist, are admin-only, and answer 401 without a session and 403 for a non-admin — proved by a test, not by inspection
- [ ] Every mutation writes an audit entry naming the actor and the row
- [ ] `GET /api/crt-session` returns active rows in order and leaks no ids, `active` flags or timestamps — asserted against the encoded JSON bytes, not the Go struct
- [ ] Reordering two rows in the admin UI changes the order the public endpoint serves
- [ ] Deactivating a row removes it from the public endpoint; reactivating restores it at its old position
- [ ] `GET /api/list-stats` gains `interests`, counting **only `active`** subscribers, joined through `subscriber_interests`, omitting zero counts — with a DB-backed test seeding a known distribution (including a `pending` and an `unsubscribed` subscriber that must NOT be counted)
- [ ] The exactness argument for per-interest counts is written into the handler doc comment alongside the existing `pending` reasoning
- [ ] `crtInterestLines()` is unit-tested for the ≤36-char budget, singular/plural, and an empty array
- [ ] With `/api/crt-session` returning 404 or 500, the home CRT still runs the compiled-in `CRT_SESSION` — tested, since this is the `STORAGE=json` path and the pre-seed deploy path
- [ ] With a live-source row's own fetch failing, that row shows its stored fallback lines rather than a blank block or an error string (`#0274`'s rule)
- [ ] The admin CRT section renders, toggles, reorders and saves — a mounted component test (`// @vitest-environment jsdom`, `CLAUDE.md` §1)
- [ ] The seeded fun rows are `active = false`, so merging this changes nothing on the live screen until the user chooses to
- [ ] `ISSUE=0393 scripts/check.sh` passes, including `internal/db` and `internal/handlers` (repo-wide guards, `CLAUDE.md` §5) and `web`
- [ ] `## Verification` names the tests that ran and says which claims rest on jsdom versus a real browser

## Open questions

1. **Does `/crt` (`#0246`) consume the same rows?** It should — `#0246`'s
   "one shared source" criterion is about exactly this drift. This issue builds
   the source; `#0246` consumes it when it is built. Worth a line in `#0246`.
2. **Should the interest counts be shown as a bar rather than a number?** A
   `microcontrollers ████░░ 4` histogram is more phosphor-authentic than a
   dotted leader. Left to the implementer's taste inside the 36-char budget.
3. **Rate of change.** The public endpoint caches for 60s, so an admin edit
   takes up to a minute to appear. That is fine, and the admin screen should
   say so rather than leave the user wondering whether the save took.

## Notes

Requested by the user on 2026-09-03, filed under Phase 9 at their direction.

**The compiled-in `CRT_SESSION` does not go away.** It is the fallback for
`STORAGE=json`, for a pre-seed deploy, and for a failed fetch. That means two
copies of the session exist by design — the constant and the seed rows — and
they are allowed to drift, because the constant is a floor rather than a
mirror. Say so in the constant's doc comment, or the next reader will file a
drift issue against it.

**Do not weaken `POST /api/subscribe`'s uniform 202** (`CLAUDE.md` §9). Nothing
here touches it, and nothing here may become a second route to the same
information: per-interest counts are exact only because confirmation requires
the address owner's own click.
