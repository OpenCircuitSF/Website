## Description

`#0389`'s review swept **all ten** two-column swaps in `outbox.Store.Counts`'
five-column `count(*) FILTER (WHERE status = $n)` query. **Nine are detected.
One survives.**

Swapping `StatusSending` and `StatusAbandoned` in the positional argument list
leaves `internal/outbox` green **and** `internal/handlers` green (`ok`, 5.590s
under the mutation), so **nothing in the tree detects it.**

**The cause is precise**: `Counts.Sending` is asserted by **no test at all**,
and `Counts.Abandoned` only ever as *unchanged* — in
`TestOutbox_Counts_ReportsSkippedDistinctlyFromAbandoned`'s "a skip must never
count as a delivery-health failure" check. **Two columns that are only ever
both-zero-delta are mutually indistinguishable.**

Pre-existing: it passes at `c921ba9^` too, so `#0389` neither caused nor widened
it. That issue closed `Queued`/`Sent` and confirmed `Abandoned`/`Skipped` was
already closed by an existing asymmetric assertion.

**This is `#0364`'s finding a third time** — an assertion passing for a reason
that does not distinguish the thing it names.

## The remedy's shape, from the review that found it

Same as `#0389`'s: **a moment where the two must move by different amounts.**
Two candidates:

- claim a row without finishing it — `Sending +1`, `Abandoned` unchanged;
- drive one to `abandoned` via the retry path past `queue_max_retries` and
  assert the other stayed put.

**`internal/handlers` cannot help**: the dashboard reaches `Counts` through an
interface, so no handler test exercises the real SQL. The assertion must live in
`internal/outbox`.

## A caution from the review that found this

Its own first mutation sweep used `${3:+-run "$3"}`, which expands to a

reason. It was caught only because the **unmutated control row also read FAIL**.

**Include an unmutated control in your sweep, and check it passes.** That is the
cheapest available protection against measuring your own harness instead of the
code, and it is the same defect this issue is about.

## Root cause

`TestOutbox_Counts` asserted `Queued` and `Sent` deltas (the latter closed by
`#0389`) but never asserted `Sending` at all, and `Counts_ReportsSkippedDistinctlyFromAbandoned`
only ever asserted `Abandoned` as *unchanged*. Two fields that are only ever
both-zero-delta cannot discriminate a swap of which SQL argument feeds which —
exactly `#0364`'s pattern a third time.

## Fix

Added a third row to `TestOutbox_Counts`: enqueue it, claim it via `ClaimDue`,
and deliberately never resolve it (no `MarkSent`/`MarkRetryOrAbandon`), which
moves the real `Sending` count `+1` and leaves `Abandoned` unchanged. Took a
`Counts()` snapshot (`midSending`) right after that claim and asserted both
`midSending.Sending == mid.Sending+1` and `midSending.Sent == mid.Sent`
(unchanged).

**One iteration was needed.** The first version took that snapshot only at
the test's final `after` point, by which time `sentKind`'s own
claim-then-`MarkSent` round trip had also pushed the real `Sending` count up
by a net `+1` on its way through — so the real `Sending` delta (`+1`, from the
new row staying claimed) and the real `Sent` delta (`+1`, from `sentID`)
coincided, and a `Sending`<->`Sent` swap reported each field under the other's
label with the same `+1` and passed undetected. Measured directly: swapping
`StatusSending` and `StatusSent` in `Counts`' argument list left the whole
package green under that version. Moving the snapshot to before `sentKind` is
touched at all — the committed version — makes the two deltas differ at that
instant (`Sending +1`, `Sent +0`), the same asymmetric-moment shape `#0389`
already used for `Queued`/`Sent`, and the only shape immune to this
coincidence.

## Gotchas

- The obvious placement — measure the new row's claim only in the test's
  existing final `Counts()` call — is exactly the shape that reproduces this
  issue's own bug one column over: it makes `Sending` and `Sent`'s deltas
  coincide at `+1` apiece by the end of the test (one from the new row
  staying claimed, one from `sentID` passing through `Sending` on its way to
  `Sent`), so a `Sending`<->`Sent` swap goes undetected by the very fix meant
  to close a different swap. Caught only by re-sweeping all ten pairs, not
  just the two the issue named — the same lesson `#0389`'s review already
  drew from checking the full swap space instead of trusting "closed one,
  therefore closed."
