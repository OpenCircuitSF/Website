## Root cause

Not a bug — new work. `#0027` landed the SES v2 sending primitive
(`internal/mailing.Mailer`/`SESMailer`/`RecordingMailer`) but nothing in the
project yet rendered a real HTML+text message: `internal/auth`'s
registration/recovery/sessions-revoked mail was plain text hand-built with
string concatenation, and the confirmation/already-subscribed mail didn't
exist at all (`#0026`, the subscribe handler, is still open). This issue
builds the render layer those four messages need, independent of `#0026`
actually wiring the confirmation/already-subscribed builders into a live
handler — that wiring is `#0026`'s job, not this one's; this issue only had
to make the builders exist, tested, and correct.

## Fix

- **`internal/mailing/templates.go`** (new) — the shared render engine: an
  `emailContent` struct (subject, preheader, eyebrow, heading, intro
  paragraphs, a CTA button, note paragraphs, and an optional mailing-list
  footer) with two methods, `renderHTML` and `renderText`, both consuming the
  same value. That is what "HTML and text rendered from one source" means
  here — each `Build*` function below populates one `emailContent` once, then
  calls both renderers, so the copy can never drift between the two formats
  the way separately hand-written HTML/text bodies would. `renderHTML` builds
  a single-column nested-table layout entirely from inline styles/attributes
  — no `<style>` tag anywhere, no flexbox, no CSS custom properties — and
  gives every background-bearing table an explicit `bgcolor="..."`
  **attribute**, not just a CSS `background-color`, because Outlook's Word
  rendering engine drops the latter on `<body>` (and can drop it elsewhere)
  but still honors the legacy attribute.
- **Contrast discipline** (`CLAUDE.md` §8: `#68FF23` is 14.8:1 on the dark
  terminal ground but only 1.32:1 on white): the bright accent green
  (`colorHeading`) is used in exactly one place, the `<h1>`, which always sits
  inside the card `<td>` — the only element whose `bgcolor` attribute
  guarantees that green ever appears in front of a dark background. The CTA
  button goes further: its text is near-black (`colorButtonText`, `#04140a`)
  on the green fill, not green-on-green or green-on-unknown, so it stays
  legible even in the hypothetical case a client strips the button's own
  background and falls back to a plain white canvas. Body copy and footer
  text never use green at all.
- **`internal/mailing/transactional_templates.go`** (new) — the four
  builders: `BuildConfirmationEmail`, `BuildAlreadySubscribedEmail`,
  `BuildRegistrationEmail`, `BuildRecoveryEmail`. Confirmation and
  already-subscribed set `ShowListFooter: true`, carrying the PRD §6.5 Path 2
  footer ("Manage your interests · Unsubscribe from everything", linking to
  `/preferences?token=` and `/unsubscribe?token=`) and an optional physical
  address line — but deliberately attach **no** `List-Unsubscribe` /
  `List-Unsubscribe-Post` / `List-Id` headers. Those are RFC 8058 one-click
  headers for **campaign** mail (`#0035`/`#0043`); `#0075`'s published privacy
  policy narrows its one-click commitment to "every campaign email" precisely
  because a double opt-in confirmation is transactional, sent synchronously
  from the subscribe handler, not a campaign send. Registration and recovery
  set `ShowListFooter: false` — they're account email with nothing to do with
  list membership, so no manage/unsubscribe links and no address. All four
  expiry lines ("this link expires in N days/minutes") are derived from a
  `time.Duration` argument via `formatDuration`, not a hand-typed string —
  `BuildConfirmationEmail` takes the confirm-token TTL (`#0026` will pass
  `subscribers.NewSignup.ConfirmTTL`), and `BuildRegistrationEmail`/
  `BuildRecoveryEmail` take `auth.registrationTTL`/`auth.recoveryTTL`
  directly, so the copy can never drift from what the store actually
  enforces.
- **`internal/auth/ses_mailer.go`** — `SendVerification` and `SendRecovery`
  now call `mailing.BuildRegistrationEmail`/`BuildRecoveryEmail` instead of
  hand-building a text-only body, re-theming them into HTML+text pairs with
  the same copy and links as before. `send` was split into `send` (still used
  by `SendSessionsRevoked`, which is unchanged and stays text-only — it isn't
  one of the four templates this issue covers) and a new `sendMessage` that
  takes an already-built `mailing.Message`, preserving the existing
  recipient-omitted error-wrapping behavior (the PII-leak guard
  `TestSESMailer_SendErrorIsWrappedWithoutRecipient` and
  `internal/handlers`' `TestAuthHandler_MailerErrorDoesNotLeakEmail` protect)
  for both paths.
- **Physical address**: `settings.physical_address` is still `''` (migration
  `000008`'s seed — CLAUDE.md §10 item 3, `#0045`'s open blocker). Rather than
  fabricate one, `BuildConfirmationEmail`/`BuildAlreadySubscribedEmail` take
  `physicalAddress string` and render the address line only when it's
  non-empty. The acceptance criterion is satisfied as template *support*,
  proven with a non-empty address in the golden fixtures; the real value
  still needs `#0026`/Phase 5 to supply it from `settings`.

## Manual verification required

The fourth acceptance criterion — rendered output checked in Gmail web, Apple
Mail, and Outlook — cannot be ticked by an agent: it needs a real inbox in
each client, and SES is not configured (`CLAUDE.md` §10 item 2). Following the
precedent of `#0018` (iOS touch icon) and `#0021` (share card), the criterion
stays unchecked and this is the procedure a human runs to close it.

1. **Get the four messages into real inboxes without SES.** The rendered
   bodies are already on disk as the golden fixtures —
   `internal/mailing/testdata/{confirmation,already_subscribed,registration,recovery}.{html,txt}`
   — and `go test ./internal/mailing/ -run TestBuild -count=1` proves they
   match what the builders emit today. Send each pair as a real
   `multipart/alternative` from any mail account you control, e.g.:

   ```bash
   python3 - <<'EOF'
   import smtplib, ssl
   from email.message import EmailMessage
   NAME = "confirmation"        # repeat for already_subscribed, registration, recovery
   TO   = "you@example.com"     # send one round to Gmail, one to iCloud, one to Outlook.com
   m = EmailMessage()
   m["Subject"] = "[render check] " + NAME
   m["From"], m["To"] = "you@example.com", TO
   m.set_content(open(f"internal/mailing/testdata/{NAME}.txt").read())
   m.add_alternative(open(f"internal/mailing/testdata/{NAME}.html").read(), subtype="html")
   with smtplib.SMTP("smtp.gmail.com", 587) as s:   # or your provider
       s.starttls(context=ssl.create_default_context())
       s.login("you@example.com", "APP-PASSWORD")
       s.send_message(m)
   EOF
   ```

   Sending the `.txt` as the main body and the `.html` as the alternative
   reproduces exactly the MIME shape `SESMailer.Send` builds from
   `Message.TextBody`/`Message.HTMLBody`.

2. **Gmail web (light and dark).** Confirm the dark page and card backgrounds
   render (Gmail keeps inline styles and `bgcolor` but strips `<head>`), the
   green `<h1>` sits on the dark card and never on white, and the CTA is
   near-black text on the green fill. Check the inbox list shows the
   preheader ("One click and you're on the list.") as the snippet rather than
   the eyebrow `$ opencircuit/confirm`.

3. **Gmail on Android/iOS with the OS in dark mode.** This is the highest-risk
   client for this design: Gmail mobile can force-recolor a message. Confirm
   the card does **not** come back light with the bright green heading on it —
   `#68FF23` measures 1.32:1 on white (`CLAUDE.md` §8), so that specific
   outcome is an unreadable heading and is the failure to look for.

4. **Apple Mail, macOS and iOS, in both appearances.** Confirm the 480px card
   stays centered with no horizontal scroll on an iPhone, the raw-URL fallback
   line wraps rather than overflowing (`word-break:break-all`), and Apple's
   automatic data detectors do not restyle the visible URL into an unreadable
   color on the dark card.

5. **Outlook desktop on Windows (the Word engine).** Confirm the `bgcolor`
   attributes produce the dark page and card — this is the whole reason they
   are there. `border-radius` will be ignored and the corners will be square;
   that is expected and acceptable. Look for white gaps between the nested
   tables and for the button rendering as a solid green block with dark text.

6. **Outlook.com web in dark mode**, which re-colors backgrounds on its own:
   confirm the heading and the button text are still legible after its
   transform.

7. **Read the plain-text alternative on its own** (Gmail's "Show original", or
   any text-only client). Every link must be present and complete; a client
   that shows only the text part must still be actionable.

8. **If any client fails**, fix `internal/mailing/templates.go`, regenerate the
   fixtures deliberately with
   `UPDATE_GOLDEN=1 go test ./internal/mailing/ -run TestBuild -count=1`,
   diff-review `internal/mailing/testdata/`, then re-run the suite *without*
   the env var so the assertions are real again, and commit template and
   fixtures together.

## Gotchas

- `SendSessionsRevoked` (the third message `internal/auth`'s `Mailer`
  interface defines) is deliberately untouched and still text-only — the
  issue's scope is "the four non-campaign messages," and sessions-revoked is
  a fifth, plain notification with no template acceptance criteria attached
  to it here. Re-theming it would be scope creep, not a fix.
- `settings.physical_address` is still `''` — this issue builds the
  rendering *capability* (render the address when given one) but does not,
  and should not, invent an address. `#0045`'s send-gate and `CLAUDE.md` §10
  item 3 remain the tracking points for when a real value exists; whichever
  issue wires `#0026`'s subscribe handler to these builders is responsible
  for passing `settings.physical_address` through.
- The golden-file tests use a `UPDATE_GOLDEN=1` env-var convention
  (`go test ./internal/mailing/... -run TestBuild... ` with it set
  regenerates `testdata/*`) rather than a `-update` flag, since this repo has
  no existing golden-file convention to match. A future template change
  should regenerate deliberately, diff-review the output, then commit both
  the template and fixture changes together — never run with the env var set
  as part of normal `go test ./...`.

## Notes

PRD §6.6. Email clients are not browsers. The terminal aesthetic translates as dark background, mono headers, and green accents — but it has to be built with 2005-era HTML techniques.

Transactional confirmation mail does not strictly require the CAN-SPAM physical address (it is not commercial mail), but including it is harmless and avoids a per-template judgment call later. Campaign mail absolutely requires it — see #0045.
