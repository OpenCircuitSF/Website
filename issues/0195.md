## Description

`#0191` documented that `sendGuardState` checks `status` **before** `inFlight`,
so a non-`draft` caller sees `sending === false` even while a send is genuinely
outstanding. It framed that as a hazard for a *future* failed-campaign-retry
reuse. `#0191`'s phase-3 review found **a narrow path to it today**.

`status` is a reactive `$props()` value and `guard` is `$derived`, so the prop
tracks `campaign.status` live. `resyncCampaignStatus`
(`web/src/views/admin/CampaignEditor.svelte:326`) reassigns `campaign` from the
server on **every SSE connect/reconnect** and on **every terminal progress
frame**. So an SSE reconnect during the `onConfirmSend` window — or another
admin sending the same campaign — flips the prop non-draft while the dialog is
still mounted with `sendInFlight === true`. By the ordering `#0191` documented,
the dialog then reads `sending === false` mid-request: the count input is
re-enabled, and Escape and the backdrop go live.

**Nothing double-sends.** `handleSubmit` still refuses, and `onCloseSend` bails
while `sendInFlight` is true. The defect is that the dialog misrepresents its
own state during a request it knows is outstanding — the same class as `#0186`,
where an irreversible action stayed live while the dialog said otherwise.

Not introduced by `#0191`; the live prop arrived with `#0189`, and no statement
in `#0191` is false about the code's mechanics. What changed is that the path is
now known to be reachable rather than hypothetical.

## Implementation notes

**The path is real — traced independently, not taken on the review's word.**
`resyncCampaignStatus` (`web/src/views/admin/CampaignEditor.svelte:326`)
reassigns `campaign = fresh` and is called from exactly two places: the
`subscribeEvent` reconnect callback (line 348, `() => void
resyncCampaignStatus()`) and `onProgressEvent` whenever `isTerminalSnapshot(p)`
(lines 294–295). The dialog mount (`{#if sendDialogOpen && preflightSummary}`,
line 814) passes `status={campaign.status}` (line 817) — a bare, live
property read every reactive tick, inside `CampaignSendDialog.svelte`'s
`$derived(sendGuardState({ status, ... }))`. `onConfirmSend`
(`CampaignEditor.svelte:503`) sets `sendInFlight = true` before `await
sendCampaign(...)` resolves, and nothing prevents a reconnect or a terminal
frame from landing — and therefore `resyncCampaignStatus` from reassigning
`campaign` — during that window. The path is reachable exactly as `#0191`'s
review described.

**Design chosen: reorder `sendGuardState` so `inFlight` is checked before
`status`** (hold `sending` true across the flip), not freeze `status` at
dialog open. Both were genuinely defensible; this one was chosen for a
reason not weighed in the issue's own framing:

- **Testability.** `#0094` is still open — there is no DOM environment or
  `@testing-library/svelte`-style harness anywhere in this repo, and no test
  imports a `.svelte` file. Freezing `status` at open is Svelte-only state
  management (a new `$state` variable set inside `onOpenSend`,
  `CampaignEditor.svelte`) with no plain-TypeScript expression of the fix —
  criterion 3's test could only exercise it by asserting on
  `sendGuardState` in isolation with a hand-picked status value, which is
  exactly what the issue says is insufficient. Reordering the branch inside
  `sendGuardState` (`web/src/lib/sendConfirm.ts`) keeps the fix inside the
  project's one tested, plain-TypeScript module, so a real test can drive it.
- **`editorGuard` (`CampaignEditor.svelte:202`) is provably unaffected.** It
  hardcodes `inFlight: false`. With `inFlight` false the new first branch
  never fires, so evaluation falls straight through to the `status` check
  exactly as before the reorder — `sendGateOpen` and `preflightPanelSummary`
  (the Send button's render gate and its `aria-describedby` text) cannot
  change outcome for any input this reorder touches, because inFlight is
  never true there. Verified by reading, not assumed: `editorGuard`'s only
  call site is line 202–210, `inFlight: false` is a literal.
- **`#0184`'s original status-before-inFlight reasoning does not transfer
  to `CampaignSendDialog`, the only consumer where `inFlight` can be
  `true`.** Re-checked against the new order as required by criterion 6:
  `#0184`'s review argued `unavailable` should win because
  `canSendCampaign` is "the render gate" — true for `editorGuard`, which
  decides whether the Send *button* renders at all. It is not true for the
  already-mounted dialog: nothing re-applies `canSendCampaign` while
  `sendDialogOpen` stays true, and `sendGuardDescription('unavailable')` is
  `''` with neither `sending` nor `blockedAgain` becoming true for that
  `kind` — so "unavailable" produced no defensive UI in the one place a
  mid-flight flip can happen, which is this issue.
- **`#0184`'s `inFlight`-before-`unmet` precedence is preserved, not just
  by claim.** The new order is `inFlight → status → unmet → ...`; `inFlight`
  is checked even earlier than before (previously `status → inFlight →
  unmet`), so it is still strictly ahead of `unmet`, and `status` sitting
  between them changes nothing: `status` never intercepts a `draft` caller
  (every real dialog case, since `canSendCampaign` gates opening it) or an
  already-`inFlight` caller (short-circuited before `status` ever runs).
  `#0186`'s two behaviour changes (blocked-panel deferring to "Sending…",
  closing the double-send `handleSubmit` gap) are both stated purely in
  terms of `inFlight` vs. `unmet` and hold unchanged.

Full reasoning is recorded in `sendGuardState`'s own doc comment
(`web/src/lib/sendConfirm.ts`), which is the module's established practice
for branch-order decisions (`#0183`, `#0184`).

**Effect on `#0191`'s probe table.** `{status:'failed', inFlight:true}` now
returns `sending` (previously `unavailable`) — that flip is the fix.
`{status:'draft', inFlight:true}` is unchanged, still `sending`.

**Criterion 4.** Both located instances of "reachable with today" were
rewritten to "opened from": `CampaignSendDialog.svelte`'s `sending` doc
comment (rewritten in full to describe the new precedence and the reachable
resync path) and `CampaignSendDialog.guard.test.ts`'s file-header comment.
`grep -rn "reachable with" web/src/` finds none remaining.

**Criterion 3 test.** Added a new `describe` block to
`CampaignSendDialog.guard.test.ts` (`CampaignSendDialog guard wiring
(#0195)`) that drives the two-step sequence directly: `inFlight` goes
`true` while `status` is `'draft'` (the ordinary submit moment), then
`status` flips to `'sending'` with `inFlight` unchanged (the mid-flight
resync). It asserts on three literal one-line copies of the component's own
gates — the count input's `disabled={sending}`, `handleKeydown`'s
`!sending`, and the backdrop's `onclick={() => !sending && onClose()}` — not
on `sendGuardState(...).kind` alone, so it is checking what the dialog's
affordances do, not just the discriminated union. Given `#0094` is open and
there is no way to mount `CampaignSendDialog.svelte` itself, this mirrors
the pattern the rest of the file already uses (`newSending`, `newBlockedAgain`
as named formulas over `guardOf`) rather than inventing a new one.

### Ruling on `#0184` — the reorder respects it, because the premise `#0184` actually decided on has since become false

`#0184`'s review gave **three** things, not one, and it is worth putting all
three on the record because the doc comment quotes only the second:

- (a) the persisted `status` is a durable, server-authoritative fact while
  `inFlight` is a transient client flag;
- (b) `unavailable` means "the control shouldn't be rendered at all"
  (`canSendCampaign` is the render gate) — the strictly stronger statement;
- (c) **"Neither ordering differs in *safety* (both disable the send), so the
  tie goes to the more authoritative fact."**

(c) is the tie-breaker — (a) and (b) only won *because* the choice was safety-
neutral. And (c) was true when it was written: `#0184`'s own review notes record
that "the dialog never calls `sendGuardState` at all" and that `kind: 'sending'`
had **no production producer**. `#0186` then wired the dialog to the guard and
`#0189` threaded the real `status` prop, which made `unavailable` reachable in a
consumer where it disables *nothing* — it re-enables the count input, Escape,
the backdrop and Cancel. The two orderings therefore now **do** differ in
safety, (c) collapses, and with it the tie that (a) and (b) were breaking.

So the implementer did **not** select a convenient reading: rebutting (b) via
"the mounted dialog is not re-gated by `canSendCampaign`" is correct and
sufficient, and "`unavailable` produced no defensive UI" is (c) in substance.
The one fair criticism is of completeness, not of the decision: the doc comment
presents `#0184`'s reasoning as the render-gate argument alone and never names
(a) or (c), so the next reader gets a thinner version of the record than the one
above. That is a write-up gap, not a defect — recorded here so the record is
whole, and not worth its own issue.

Judged independently: `inFlight`-first is right. The guard's `sending` answer is
a statement about *the request*, and during an outstanding request the dialog's
only correct job is to be inert. `status` is the more authoritative fact about
the *campaign*, but it carries no defensive meaning in the one consumer that can
observe the conflict, and the window it loses is bounded by the request's own
lifetime — `onConfirmSend`'s `finally` (editor line 522) clears `sendInFlight`,
after which the live status governs normally again and the 409 surfaces through
`sendError`. Reporting a campaign-level truth by re-enabling the controls
guarding an irreversible action is the worse trade.

### What the dialog shows in the new state — walked control by control

`status` non-draft **and** `inFlight` true now yields `sending`. Every affordance
was checked against the template, comparing old (`unavailable`) to new:

| element | old (`unavailable`) | new (`sending`) |
|---|---|---|
| count input `disabled={sending}` | **enabled** — typing changed `confirmHint` | disabled ✓ |
| Escape (`e.key === 'Escape' && !sending`) | **live** | dead ✓ |
| backdrop (`onclick={() => !sending && onClose()}`) | **live** | dead ✓ |
| Cancel `disabled={sending}` | **enabled** | disabled ✓ |
| Send `disabled={sending}`, label | enabled, "Send now", `aria-disabled` true | disabled, "Sending…" ✓ |
| `send-blocked-hint` contents (`blockedAgain`) | empty | empty — unchanged |
| `aria-describedby` text (`sendGuardDescription`) | `''` | "A send for this campaign is already in progress." |

The decisive detail is that the old state's live controls were **already inert**:
`onClose` is `onCloseSend`, which is `if (sendInFlight) return;` (line 527). So
the old order rendered controls that looked live and did nothing — the exact
"dialog misrepresents its own state" defect this issue names. The new order makes
appearance match behaviour, and introduces no new trap: the dialog was already
uncloseable while `sendInFlight`, since `#0186`.

On "right about the request, wrong about the campaign": if another admin's send
has already *completed* when the flip lands, "Sending…" is momentarily imprecise
about the campaign while remaining true about this client's outstanding request.
That window ends when the request resolves — `parseUnmetFromError` returns null
for the illegal-transition 409, so `sendError` renders the server's message and
the dialog becomes closeable. Acceptable, and strictly better than re-arming the
controls mid-request.

### The replicated gates — acceptable here, but they are commentary, not cover

`#0189` and `#0191` both dealt with a hand-rolled copy drifting from the real
thing, so this deserved a hard look. `countInputDisabled`, `escapeCloses` and
`backdropCloses` are `sending`, `!sending`, `!sending` — one-token mirrors of
`disabled={sending}`, `e.key === 'Escape' && !sending`, and `!sending &&
onClose()`. Two findings:

1. **They carry no assertive weight.** Every one is derivable from
   `expect(sendingDuringFlip).toBe(true)`, which is the assertion mutation B
   actually catches. The test earns its keep on that line, not on the three
   helpers. So this is *not* the `#0186`/`#0191` hazard class in severity: the
   dangerous replica was `normalizeCountInput`'s separator class, a
   re-implementation of real logic that could disagree with the original. An
   identity function cannot disagree with `disabled={sending}` about anything.
2. **It can still drift silently, and that is the real cost.** If the component
   ever changed `disabled={sending}` to, say, `disabled={sending || blockedAgain}`,
   these helpers would keep passing while the test's comment still claimed to
   cover the affordance. The failure mode is a stale claim of coverage, not a
   false pass on logic.

Acceptable given `#0094` is open and no `.svelte` file can be mounted — and
consistent with the pattern the file already uses (`oldSending`/`newSending`).
**What would make it detectable when it drifts:** this repo already has the
mechanism. `web/src/lib/citationGuard.test.ts` parses `.svelte` files with
`svelte/compiler`'s `parse({ modern: true })` AST from inside vitest, with no
DOM. A small structural guard in the same style — assert
`CampaignSendDialog.svelte` still contains `disabled={sending}` on the count
input and `!sending` in both the Escape handler and the backdrop `onclick` —
would turn silent drift into a loud failure at a fraction of `#0094`'s cost.
Reported below rather than filed (§9).
