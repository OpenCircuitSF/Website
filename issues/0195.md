## Description

`#0191` documented that `sendGuardState` checks `status` **before** `inFlight`,
so a non-`draft` caller sees `sending === false` even while a send is genuinely
outstanding. It framed that as a hazard for a *future* failed-campaign-retry
reuse. `#0191`'s phase-3 review found **a narrow path to it today**.

`status` is a reactive `$props()` value and `guard` is `$derived`, so the prop
tracks `campaign.status` live. `resyncCampaignStatus`
(`web/src/views/admin/CampaignEditor.svelte:326`) reassigns `campaign` from the
server on **every SSE connect/reconnect** and on **every terminal progress
frame**. So an SSE reconnect during the `onConfirmSend` window — or another
admin sending the same campaign — flips the prop non-draft while the dialog is
still mounted with `sendInFlight === true`. By the ordering `#0191` documented,
the dialog then reads `sending === false` mid-request: the count input is
re-enabled, and Escape and the backdrop go live.

**Nothing double-sends.** `handleSubmit` still refuses, and `onCloseSend` bails
while `sendInFlight` is true. The defect is that the dialog misrepresents its
own state during a request it knows is outstanding — the same class as `#0186`,
where an irreversible action stayed live while the dialog said otherwise.

Not introduced by `#0191`; the live prop arrived with `#0189`, and no statement
in `#0191` is false about the code's mechanics. What changed is that the path is
now known to be reachable rather than hypothetical.

## Acceptance criteria

- [ ] Decide and record whether a mid-flight status flip should hold `sending` true, or whether `status` should be frozen at dialog open — either is defensible; the current behaviour is neither, it is incidental
- [ ] Whichever is chosen, a send that is genuinely outstanding never leaves the count input editable or Escape/backdrop live
- [ ] A test drives the reachable path: `sendInFlight === true`, then `status` flips non-draft, and asserts what the dialog does
- [ ] Both comments' "reachable with today" becomes "opened from" — the dialog is *opened from* `draft`, but its status can change while open, which is exactly the distinction this issue turns on
- [ ] `#0186`'s mutation still turns exactly 2 tests red, and the 28 guard tests still pass
- [ ] `#0184`'s deliberate `inFlight`-before-`unmet` precedence is preserved; if the `status`/`inFlight` order changes, `#0184`'s and `#0186`'s reasoning is re-checked against the new order
- [ ] `scripts/check.sh web` passes

## Notes

Reported by `#0191`'s phase-3 review under `CLAUDE.md` §9.

The second criterion is the real requirement; the first is how you get there.
Note the branch order is load-bearing in the other direction too — `#0184`
established `inFlight` before `unmet` deliberately and `#0186` re-verified it —
so this is not a free reordering. Freezing `status` at open may be the smaller
change.

Read `#0191`'s `## Review notes` for the executed guard probes:
`{status:'failed', inFlight:true}` → `unavailable`, `{status:'draft',
inFlight:true}` → `sending`.
