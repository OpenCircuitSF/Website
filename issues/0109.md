## Description

`#0039` counts only `bounce_type = 'Transient'` toward the repeated-soft-bounce
threshold. SES's third classification, `Undetermined`, is recorded in
`email_events` and then handled by nothing: `applyBounce`'s `default:` arm
returns `nil`, and no threshold path ever reaches it. An address whose provider
consistently returns bounces SES cannot classify is, in practice, exactly as
dead as one returning `Transient` bounces — and we will send to it forever,
which is the failure mode `#0039` exists to stop.

## Root cause

Deliberate, documented scope decision in `#0039` (`c43cee1`), not an oversight —
`#0038`'s plan §8 left the call to `#0039` and `#0039` decided against counting.
The stated reasons were sound as far as they went:

- `migrations/000014`'s `idx_email_events_soft_bounce` is a **partial** index
  scoped to `event_type = 'Bounce' AND bounce_type = 'Transient'`. Widening the
  count to include `Undetermined` does not use it — verified: the current query
  plans as an `Index Only Scan` on that index, and an `OR bounce_type =
  'Undetermined'` predicate would not.
- `#0039`'s own acceptance criterion says "5 **transient** bounces".

But the decision's written justification overstates its authority in two
places, and those need correcting whichever way this issue lands:

- `applyBounce`'s `default:` arm comment and `c43cee1`'s commit message both
  attribute "5 transient bounces" to **PRD §6.5**. PRD §6.5's state-machine row
  actually reads "**5 soft bounces** in 30 days" — it does not say "transient"
  and does not exclude `Undetermined`. The narrower wording is the issue's
  acceptance criterion, not the PRD's.
- `migrations/000014`'s own column comment says `bounce_subtype` is recorded
  because "**#0039 needs this**". `#0039` never reads it. See the second
  question below.

## The two questions to settle

1. **Should `Undetermined` count?** If yes, it needs a second partial index
   (append-only — a new migration, never an edit to `000014`), or one index
   widened to `bounce_type IN ('Transient','Undetermined')`. Either way this is
   an index change plus a one-line predicate change, not a redesign. SES
   documents `Undetermined` as uncommon, so the volume argument for leaving it
   out is real; the "dead address" argument for counting it is also real. Pick
   one deliberately and record why.

2. **Should every `Transient` subtype count?** SES's `Transient` subtypes are
   `General`, `MailboxFull`, `MessageTooLarge`, `ContentRejected`, and
   `AttachmentRejected`. The last three describe **our** message, not the
   recipient's mailbox: suppressing a live subscriber because we sent five
   oversized messages in a month is a false positive that silently shrinks the
   list. `bounce_subtype` is already recorded faithfully on every row
   (`#0038`), so the filter is available at no schema cost. Low practical risk
   today — this site sends small plain-text-plus-HTML campaigns with no
   attachments — which is an argument for it being cheap to fix, not for
   ignoring it.

## Fix

Both questions decided against the exclusions `#0039` shipped, per the
reasoning laid out in this issue's own `## The two questions to settle`
(both readings matched what was proposed there):

**Q1 — `Undetermined` now counts.** PRD §6.5's state-machine row reads "5
soft bounces in 30 days"; it neither says "transient" nor excludes
`Undetermined`. An address whose provider only ever returns an unclassifiable
bounce is, operationally, exactly as dead as one returning `Transient`
bounces, and a threshold of 5 over 30 days is already forgiving toward a
classification SES documents as uncommon — the volume argument for excluding
it was real but not decisive against closing the actual hole this feature
exists to close.

**Q2 — the sender-fault `Transient` subtypes are now excluded.**
`MessageTooLarge`, `ContentRejected`, and `AttachmentRejected` describe a
fault in *our* message (too large, rejected content, a bad attachment), not
evidence the recipient's address is bad. Suppressing a live subscriber
because we sent one oversized campaign is a straightforward false positive
that silently shrinks the list — the exact failure `bounce_subtype` was
recorded (in `#0038`) to make decidable, but `#0039` never read it.

Both exclusions live entirely in one SQL predicate, not in Go: `applyBounce`
routes `Transient` and `Undetermined` through the same arm regardless of
subtype (the classification the count itself needs stays in one place, the
count query, rather than being duplicated as an early Go-side gate), so a
bounce carrying a sender-fault subtype is still recorded (unchanged from
`#0038`) but never contributes to, or crosses, the threshold — even on the
one request that happens to carry it.

- **`migrations/000016_widen_soft_bounce_counting.{up,down}.sql`** — new.
  `000014` is append-only and untouched (confirmed `000015` was the highest
  migration on disk before writing this as `000016`). Drops and recreates
  `idx_email_events_soft_bounce` under the same name, widened to
  `bounce_type IN ('Transient', 'Undetermined') AND (bounce_subtype IS NULL
  OR bounce_subtype NOT IN ('MessageTooLarge', 'ContentRejected',
  'AttachmentRejected'))`. `down.sql` restores `000014`'s original
  single-condition definition exactly.
- **`internal/sesnotify/store.go`** — `CountRecentTransientBounces` /
  `CountRecentTransientBouncesPool` renamed `CountRecentSoftBounces` /
  `CountRecentSoftBouncesPool`: the old name became actively misleading once
  the query also counts `Undetermined` rows and excludes some `Transient`
  ones. The query's `WHERE` clause is written to match `000016`'s partial
  index verbatim, which is what lets the planner use it as an index-only
  scan (see `## Verification`) rather than requiring the more general
  implication-proof machinery.
- **`internal/sesnotify/event.go`** — new exported
  `BounceSubTypeMessageTooLarge` / `BounceSubTypeContentRejected` /
  `BounceSubTypeAttachmentRejected` constants. Not referenced by production
  code (the exclusion lives in SQL); added so tests and any future caller
  don't have to duplicate the literal strings.
- **`internal/handlers/ses_notifications.go`** — `applyBounce`'s
  `case sesnotify.BounceTypeTransient:` becomes
  `case sesnotify.BounceTypeTransient, sesnotify.BounceTypeUndetermined:`,
  calling the renamed `CountRecentSoftBounces`. The `default:` arm's comment
  no longer attributes "5 transient bounces" to PRD §6.5 (the PRD says "5
  soft bounces"; that narrower wording was only `#0039`'s own acceptance
  criterion) and now correctly describes what actually reaches it: an empty
  bounce classification or one SES documents in the future beyond the three
  known values, since `Undetermined` no longer falls through to this arm.
  Audit metadata keys `transient_bounce_count`/`_window_days`/`_threshold`
  renamed `soft_bounce_count`/`_window_days`/`_threshold` for the same
  misleading-name reason as the store method (no test asserted the old key
  names, confirmed by grep before renaming).
- **`internal/handlers/admin_subscribers.go`** — `softBounceCounter`
  interface's method renamed to `CountRecentSoftBouncesPool` to match;
  `Get`'s call site updated. No behavior change — same nil-tolerant wiring
  as before.
- **`cmd/opencircuit/main.go`** — comment referencing the old method names

  by interface, which is satisfied by the renamed methods automatically).
- **`web/src/lib/admin.ts`** — `softBounceSummary`'s copy changed from "N
  transient bounce(s)" to "N soft bounce(s)": the count it renders now
  includes `Undetermined` bounces and excludes some `Transient` ones, so

## Gotchas

- **The predicate exclusion lives in SQL, not Go, deliberately.** An earlier
  draft considered an early `if isSenderFaultSubtype(ev.BounceSubType()) {
  return nil }` guard at the top of the combined arm. Rejected: it would
  duplicate the classification the count query already has to encode (to
  match the partial index), and — more subtly — it would make a sender-fault
  bounce's *own* arrival skip evaluating the threshold entirely, rather than
  correctly evaluating it and finding that bounce excluded from the count
  along with any other sender-fault rows. The two are behaviorally
  equivalent for a first-time sender-fault bounce, but not if a genuinely
  qualifying count had already reached the threshold on an earlier bounce —
  the SQL-only version still re-confirms the threshold on every arrival,
  which is the more conservative choice.
- **Keeping the index name unchanged across `000014`→`000016`** (drop and
  recreate `idx_email_events_soft_bounce` rather than adding a
  differently-named second index) means only one index has ever existed for
  this query at a time on any database that applies migrations in order —
  simpler to reason about than two partial indexes, one dead. Verified
  directly, not just by inspection: `migrate down 1` from version 16 drops to
  15 and `pg_indexes.indexdef` for `idx_email_events_soft_bounce` reads back
  as exactly `000014`'s original single-condition `WHERE (event_type =
  'Bounce' AND bounce_type = 'Transient')`; `migrate up` from 15 restores the
  widened three-condition definition byte-for-byte. Ran against the shared
  `opencircuit_test` database, ended back at version 16 not dirty.

## Notes

PRD §6.5's unsubscribe state machine is the specification; note again that it
says "soft bounces", which is the ambiguity this issue resolves.

Nothing here is urgent: no SES account exists yet (CLAUDE.md §10 item 2), so no
real bounce of any classification has ever been ingested. Settle it before the
first production campaign, not before Phase 5 starts.

Do not weaken any existing behaviour to do this. `complained` stays terminal
(CLAUDE.md §9), the suppression write stays reason-scoped and unconditional
(`#0100`), and the count read stays inside the ingestion transaction — a
pool-routed read evaluates the threshold one bounce stale, and three of
`#0039`'s tests fail if it is moved (verified by mutation during `#0039`'s
review).
