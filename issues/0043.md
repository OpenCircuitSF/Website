## Root cause

Not a bug fix — this issue builds the missing piece `#0042` deliberately left
as a documented seam. `#0042` landed `RenderMarkdownHTML`/`RenderMarkdownText`
(campaign Markdown → sanitized HTML fragment / readable plain text) and
`RenderCampaign` (orchestration: token substitution, footer, physical
address), but wrapped the fragment in a **plain light-palette** document
(`wrapCampaignHTML`), not the dark/terminal brand skin. That was a real,
reviewer-verified seam, not an oversight: `templates.go`'s
`emailContent.renderHTML` sets `color:` on each individual `<p>`/`<h1>`, so
dropping goldmark's unstyled `<p>`/`<h2>`/`<ul>` fragment straight onto the
dark card `<td>` (`bgcolor` but no `color`) would inherit the document
default (black) onto `#10231a` — near-invisible. This issue's actual work is
applying that styling to arbitrary Markdown-shaped HTML.

Separately, `#0042` had grown its own second, hand-written copy of the "Manage
your interests / Unsubscribe from everything" footer block (inline in
`wrapCampaignHTML`/`wrapCampaignText`) that duplicated — rather than reused —
`emailContent`'s `ShowListFooter` mechanism the five transactional templates
already use and `#0035`'s carried-in criterion pointed at. Two independent
footer implementations that happen to agree today is a drift risk, not a
resolved requirement.

## Fix

**Branded body styling** (`internal/mailing/campaign_body_style.go`, new
file): `styleCampaignBodyHTML` applies `templates.go`'s palette and
bulletproof font stacks to the already-sanitized body fragment via targeted,
anchored regexp substitution on goldmark's known, attribute-free output
shape — `<h1>`-`<h6>`, `<p>`, `<ul>`/`<ol>`, `<li>`, `<blockquote>`,
`<pre>`/`<code>`, `<a href="...">`, `<hr />`. This is safe specifically
because `campaign_markdown.go` enables no goldmark extensions, so every
targeted tag renders in one of a small, known set of forms (documented in the
file's package doc). The function never touches an `href`/`src` value, never
adds or removes a tag, and never re-parses or re-sanitizes the fragment — it
only inserts `style="..."` attributes into tags `RenderMarkdownHTML` already
emitted, so that function's sanitization guarantees (no raw HTML, no `<img>`,
no dangerous-scheme hrefs) are unchanged. `RenderMarkdownHTML`,
`RenderMarkdownText`, and `CampaignRenderInput` are untouched, exactly as
this issue's carried-in criteria from `#0042`'s review require.

**Dark-mode / background-stripping decision** (the `#0028` carried-in item):
decided explicitly rather than left residual. Added an explicit `color:`
(not just `bgcolor`) to `templates.go`'s card `<td>` — previously every
`<p>`/`<h1>` set its own color but the card container itself never did, which
`#0028`'s review flagged as a live risk once something *other* than
paragraph-shaped copy landed in that card. The new campaign wrapper's card
`<td>` carries the identical explicit `color:colorBodyText` as a second,
independent fallback. Net effect: a client that strips `background-color`
CSS but keeps inline `color` (the scenario `#0028`'s review actually modeled)
still renders legible text — every element sets its own color, and the two
container-level fallbacks catch anything a future goldmark node kind might
slip through unstyled. A client that ALSO strips inline `color` while forcing
its own light palette is not addressed here (no mainstream client does
this while continuing to honor the `bgcolor` *attribute*, which several of
these `bgcolor`-only elements still rely on) — see `## Gotchas`.

**Footer reconciliation** (`#0035`/`#0042` carried-in items): extracted the
footer markup itself into `listFooterHTML`/`listFooterText`
(`templates.go`), and pointed both `emailContent.renderHTML`/`renderText`
(the five transactional templates' `ShowListFooter` branch) and the new
campaign wrapper (`wrapCampaignHTML`/`wrapCampaignText`) at the same two
functions. This is neither "route campaign through `ShowListFooter`" (not
possible — `emailContent` is a fixed paragraphs+button shape, not an
arbitrary-HTML-body host) nor "keep `#0042`'s copy" (the duplication risk the
reviewer flagged) — it is the third option: one function that renders the
footer's markup, called from both document shapes. Wording (PRD §6.5's exact
labels, "Manage your interests" / "Unsubscribe from everything") and URL
construction (`/preferences?token=`, `/unsubscribe?token=` — the SPA routes,
not `/api/unsubscribe`) are therefore identical by construction, not by
convention. `TestRenderCampaign_FooterCarriesBothRequiredLabels` and
`TestRenderCampaign_TokenSubstitutedIntoFooterLinks` (both from `#0042`,
unmodified) still cover this for the campaign path — no new test was needed
to close `#0035`'s carried-in "add a test" item; it was already closed and is
now exercised through the new code path.

**The `#0085` builder-guard gap**: added `BuildCampaignMessage(to string, in
CampaignRenderInput, listDomain string) (Message, error)` — renders via
`RenderCampaign` and attaches the RFC 8058 headers via `CampaignHeaders`, the
same "one `Build*` function per kind of mail" shape the five transactional

builder guard from a `^Build[A-Za-z0-9]*Email$` name regex to a return-type
check (`isMessageBuilderFuncDecl`: exported, top-level, any result of type

**Deliberately out of scope, left for `#0045`**: `#0045`'s plan (written
2026-08-21, after this issue's `#0085`/`#0042` carried-in blocks) assigns

## Gotchas

- **Dark-mode / forced-light-mode clients are not fully solved, by
  necessity, not oversight.** A client that inverts colors *consistently*
  (swapping the whole palette, backgrounds included) generally stays legible
  because foreground/background contrast is preserved either way. The
  specific failure this design defends against — per `#0028`'s review and
  this issue's own acceptance criteria — is a client that strips
  `background-color` **CSS** while leaving inline `color` alone: every text
  element here sets its own explicit `color`, so that case stays legible.
  What is NOT defended against: a client that strips inline `color` too
  while forcing a light background — no mainstream client is known to do
  this while continuing to honor the legacy `bgcolor` **attribute** (which
  several elements here still carry as a second, independent fallback), but
  it could not be tested against a real Outlook/Gmail/Apple Mail client in
  this environment. The acceptance criteria items asking for that
  verification are left unticked above rather than assumed.
- **`ol`/`code` regexes preserve existing attributes rather than assuming
  none exist**, specifically because goldmark emits `<ol start="N">` for a
  list that doesn't start at 1 and `<code class="language-x">` for a fenced
  block with a language tag — both real CommonMark constructs an author
  could type. Worth a reviewer's attention if a future campaign body is
  tested with either construct; the fixed test fixture
  (`testCampaignMarkdown`) doesn't exercise either.
- **`mustBuildCampaignMessage` panics on error** rather than taking a
  `*testing.T` — deliberate, matching the existing `goldenFile` pattern in
  the same file, and safe only because `testCampaignInput()` is a fixed,
  always-valid fixture. Not a pattern to copy for anything that isn't a
  known-good fixture.

## Review notes on the regexp styling (2026-08-21)

`styleCampaignBodyHTML` applies inline branding by anchored regexp substitution
on HTML, which is normally a defect waiting to happen. It was probed directly
rather than read: fourteen adversarial Markdown bodies through
`RenderMarkdownHTML` → `styleCampaignBodyHTML`, checking every output for
wrong-element injection, duplicated `style=` attributes, malformed markup, and
non-idempotence. **All fourteen were clean, and every one was byte-identical on a
second pass.** It is sound — but sound *because* of the input alphabet, so the
reasons are recorded here rather than left implicit.

**Why it holds.** Three invariants of goldmark's output, in decreasing
obviousness:

1. **Text content is always HTML-escaped.** A body that legitimately contains
   `<p>` — inside a fenced block, inline code, or plain prose — never yields the
   literal bytes `<p>` in the fragment; it yields `&lt;p&gt;`. Same for `"` →
   `&quot;` in code and `<` → `&lt;` in a link title. This, not the disabled
   extensions, is the load-bearing property: the regexps can only ever match tags
   goldmark itself emitted.
2. **Attribute values are escaped or percent-encoded**, so `[^"]*` in the `href`
   and `class` patterns cannot run past its attribute's closing quote. `[t](https://example.com/?a=1&b=2"x"><p>)`
   renders as `href="https://example.com/?a=1&amp;b=2%22x%22%3E%3Cp%3E"` and is
   styled correctly, with the href preserved verbatim.
3. **Raw HTML in safe mode becomes `<!-- raw HTML omitted -->`** — `#0042`'s
   constraint, and what it actually buys here is that author-controlled tags and
   author-controlled attribute values never enter the fragment at all. Without it,
   invariant 2 fails immediately: an unescaped `"` inside an author-written
   `<a href="…">` would let the link regexp swallow the rest of the document.

**Idempotence** falls out of the substitution shape: every replacement inserts
` style="…"` immediately before the closing `>` the pattern anchored on, so on a
second pass `<h1 style="…">` no longer matches `<h([1-6])>`, `<hr style="…" />`
no longer matches `<hr\s*/?>`, and so on. It is not relied upon — `RenderCampaign`
calls the function exactly once, on the body fragment only, before wrapping, so
the wrapper's own `<p>` elements are never restyled — but it means an accidental
double application would be harmless rather than corrupting.

**What would break it,** in rough order of likelihood — a future change to any of
these must revisit this file:

- **Enabling `html.WithUnsafe()` on `campaignMarkdown`.** This is the one that
  turns a styling helper into an injection vector, by defeating invariants 1–3 at
  once. `campaign_markdown.go`'s package doc already forbids it for sanitization
  reasons; it is now also load-bearing for this file.
- **Enabling goldmark extensions** (GFM, auto-heading-IDs, typographer). This
  degrades *gracefully* rather than dangerously — `<h2 id="…">` simply stops
  matching `<h([1-6])>` and renders unstyled, inheriting the card `<td>`'s
  explicit `color`, which is legible if unbranded — but new node kinds (`<table>`,
  `<del>`, `<input type="checkbox">`) would arrive unstyled and unnoticed.
- **Swapping the Markdown renderer** for one that emits attributes on `<p>`/`<li>`,
  or that does not escape text nodes. The former degrades gracefully; the latter
  does not.
- **Reusing `styleCampaignBodyHTML` on anything that is not `RenderMarkdownHTML`
  output.** Every guarantee above is a property of the producer, not of this
  function. It is unexported and has exactly one caller today; keep it that way.

Two smaller observations, neither a defect: `isMessageBuilderFuncDecl` matches a
result type only as a bare `*ast.Ident`, so a hypothetical builder returning
`*Message` or `[]Message` would be invisible to the guard (no such builder exists,
and `allMessages()` is `map[string]Message`, so one could not be registered
anyway); and inside a blockquote the styled `<p>`'s own `color:#e7f5ec` overrides
the blockquote's `color:#9fb8ab`, so the muted blockquote tint applies only to the
rule and to any non-paragraph child — visually fine, and higher contrast rather
than lower.

## Manual verification required

The two client-rendering criteria above cannot be ticked by an agent, on the
`#0028` precedent (which in turn cites `#0018` and `#0021`): they need a real
inbox in each client, and SES is not configured (`CLAUDE.md` §10 item 2).

`issues/0028.md`'s `## Manual verification required` section is the procedure —
follow it verbatim, substituting `internal/mailing/testdata/campaign.{html,txt}`
for the transactional golden pairs, since the campaign document shares the same
palette, the same single-column table shape, and the same `bgcolor`-attribute
strategy. Three campaign-specific additions to that checklist, all of them
element kinds `#0028`'s transactional card never contains:

1. **`<blockquote>` and `<hr>`** — both are styled with `border` properties only.
   Outlook's Word engine renders `border-left` on a block element inconsistently;
   confirm the quote is still readable if the rule disappears (it should be — the
   text sets its own colour).
2. **`<pre>`/`<code>`** — the code block sets `background-color:#0b0f0d` in CSS
   with **no** `bgcolor` attribute fallback, unlike the card and outer table. If a
   client strips it the block falls back to the card's `#10231a` at 14.62:1, which
   is legible; confirm rather than assume. Also confirm `overflow-x:auto` does not
   force horizontal scrolling of the whole message on a phone.
3. **Nested `<ul>`/`<ol start="N">`** — `padding-left:22px` per level; confirm
   three-deep nesting does not push text past the 600px card on a narrow screen,
   and that an ordered list starting at a number other than 1 keeps its numbering.

The design's honest limit is unchanged from `## Gotchas`: measured with all
backgrounds stripped and the canvas forced white, body copy falls to 1.12:1,
heading green to 1.32:1 and body links to 1.57:1 — invisible. The defence that
actually carries that case is the legacy `bgcolor` **attribute** on the outer
table and the card `<td>` (both present, both verified in the golden), not the
inline `color`, which is what defends the opposite failure of an unstyled
fragment inheriting black onto the dark card. Step 5 of `#0028`'s procedure —
Outlook desktop on the Word engine — is the one that tests the former.

## Notes

PRD §6.6, §4. Dark-themed email is where clients diverge most: Outlook forces its own background in some configurations and Gmail applies its own dark-mode inversion in others. The failure mode is unreadable text, so test the specific clients listed rather than assuming.

Keep the design simple enough to survive that inversion. This is the one place where the brand yields to deliverability.
