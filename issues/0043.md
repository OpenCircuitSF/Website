## Description

The dark, terminal-styled HTML wrapper campaign content renders into, built with email-safe techniques.

## Acceptance criteria

- [ ] Single-column table layout, inline styles only — no `<style>` reliance, no flexbox, no CSS custom properties
- [ ] Outer table carries an explicit `background-color` (Outlook ignores `body` backgrounds)
- [ ] Dark ground, mono headers, green accents — recognizably the same brand as the site
- [ ] Max width 600 px; readable on a phone without zooming
- [ ] Footer with preference-center link, unsubscribe link, physical address, and the reply-to address
- [ ] Verified rendering in Gmail web, Gmail iOS, Apple Mail (macOS and iOS), and Outlook
- [ ] A light-mode-forcing client (Outlook) still produces legible text — no white-on-white

## Notes

PRD §6.6, §4. Dark-themed email is where clients diverge most: Outlook forces its own background in some configurations and Gmail applies its own dark-mode inversion in others. The failure mode is unreadable text, so test the specific clients listed rather than assuming.

Keep the design simple enough to survive that inversion. This is the one place where the brand yields to deliverability.

## Carried in from `#0028`'s review (2026-08-19)

- [ ] **Body copy is a worse background-stripping casualty than the accent
      green.** The reviewer measured every colour with all backgrounds stripped
      and the canvas forced white: the CTA button survives at **18.93:1** (its
      near-black-on-green fill works), but heading green falls to 1.32:1, inline
      links to 1.57:1, and **body copy `#e7f5ec` to 1.12:1** — effectively
      invisible. The mitigation in `#0028` was written for the green and
      incidentally leaves body text more exposed.

      On the card as designed everything is fine (body 14.62:1, muted 7.76:1,
      heading 12.46:1, footer 9.11:1), and no mainstream client strips `bgcolor`
      while keeping inline `color` — so this is a residual, not a live defect.
      But this issue inherits the same rendering engine for campaign mail, which
      goes to a far larger and less predictable set of clients. Decide
      deliberately whether to set an explicit dark `color` fallback strategy, and
      record the decision either way.

## Carried in from `#0085`'s review (2026-08-19)

- [ ] **Replace the builder guard's name regex with a return-type check when
      this issue's campaign builder lands.** `internal/mailing`'s
      `TestAllMessagesEnumeratesEveryBuildEmailFunc` finds builders by matching
      `^Build[A-Za-z0-9]*Email$`. If this issue's builder is named
      `BuildCampaignMessage` — the natural name — it is **invisible to the
      guard**, and the guard exists precisely because someone will forget to
      register a builder.

      `#0085` chose to keep the regex narrow, rejecting a bare `^Build` because
      it would catch non-`Message` helpers like `BuildAddressBlock`. That
      objection is answered by an option it did not consider: check the **return
      type** — an exported top-level func whose single result is `Message`. That
      is strictly more precise on both axes, catches `BuildCampaignMessage`, and
      does not catch a `string`-returning helper. The test already walks
      `*ast.FuncDecl`; `fn.Type.Results` is about three more lines.
- [ ] **Add the campaign builder to `allMessages()`** — or make the enumeration
      derive it — so the `{{…}}` unresolved-token property test covers it too.
