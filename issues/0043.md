## Description

The dark, terminal-styled HTML wrapper campaign content renders into, built with email-safe techniques.

## Acceptance criteria

- [ ] Single-column table layout, inline styles only — no `<style>` reliance, no flexbox, no CSS custom properties
- [ ] Outer table carries an explicit `background-color` (Outlook ignores `body` backgrounds)
- [ ] Dark ground, mono headers, green accents — recognizably the same brand as the site
- [ ] Max width 600 px; readable on a phone without zooming
- [ ] Footer with preference-center link, unsubscribe link, physical address, and the reply-to address
- [ ] Verified rendering in Gmail web, Gmail iOS, Apple Mail (macOS and iOS), and Outlook
- [ ] A light-mode-forcing client (Outlook) still produces legible text — no white-on-white

## Notes

PRD §6.6, §4. Dark-themed email is where clients diverge most: Outlook forces its own background in some configurations and Gmail applies its own dark-mode inversion in others. The failure mode is unreadable text, so test the specific clients listed rather than assuming.

Keep the design simple enough to survive that inversion. This is the one place where the brand yields to deliverability.

## Carried in from `#0028`'s review (2026-08-19)

- [ ] **Body copy is a worse background-stripping casualty than the accent
      green.** The reviewer measured every colour with all backgrounds stripped
      and the canvas forced white: the CTA button survives at **18.93:1** (its
      near-black-on-green fill works), but heading green falls to 1.32:1, inline
      links to 1.57:1, and **body copy `#e7f5ec` to 1.12:1** — effectively
      invisible. The mitigation in `#0028` was written for the green and
      incidentally leaves body text more exposed.

      On the card as designed everything is fine (body 14.62:1, muted 7.76:1,
      heading 12.46:1, footer 9.11:1), and no mainstream client strips `bgcolor`
      while keeping inline `color` — so this is a residual, not a live defect.
      But this issue inherits the same rendering engine for campaign mail, which
      goes to a far larger and less predictable set of clients. Decide
      deliberately whether to set an explicit dark `color` fallback strategy, and
      record the decision either way.

## Carried in from `#0085`'s review (2026-08-19)

- [ ] **Replace the builder guard's name regex with a return-type check when
      this issue's campaign builder lands.** `internal/mailing`'s
      `TestAllMessagesEnumeratesEveryBuildEmailFunc` finds builders by matching
      `^Build[A-Za-z0-9]*Email$`. If this issue's builder is named
      `BuildCampaignMessage` — the natural name — it is **invisible to the
      guard**, and the guard exists precisely because someone will forget to
      register a builder.

      `#0085` chose to keep the regex narrow, rejecting a bare `^Build` because
      it would catch non-`Message` helpers like `BuildAddressBlock`. That
      objection is answered by an option it did not consider: check the **return
      type** — an exported top-level func whose single result is `Message`. That
      is strictly more precise on both axes, catches `BuildCampaignMessage`, and
      does not catch a `string`-returning helper. The test already walks
      `*ast.FuncDecl`; `fn.Type.Results` is about three more lines.
- [ ] **Add the campaign builder to `allMessages()`** — or make the enumeration
      derive it — so the `{{…}}` unresolved-token property test covers it too.

## Carried in from `#0035`'s review (2026-08-20)

`#0035` landed the RFC 8058 header set and was resolved with **one of its own
acceptance criteria unmet**, because the criterion describes a campaign body
that does not exist until this issue builds it. That criterion now lives here:

- [ ] **The campaign body's footer must contain both of PRD §6.5 Path 2's
      literal labels — "Manage your interests" *and* "Unsubscribe from
      everything".** This issue's existing footer criterion says
      "preference-center link, unsubscribe link", which is the same two links
      but does not pin the wording PRD §6.5 gives verbatim, and `#0035` was
      resolved on the understanding that this issue closes the gap. Both links
      are required in *every* campaign email; granular management is the point
      (someone tired of one interest drops that interest instead of the whole
      list).

      The mechanism already exists and is already tested — do not build a new
      one. `emailContent.ShowListFooter` in `internal/mailing/templates.go`
      renders it, and `TestConfirmationAndAlreadySubscribed_CarryFooterLink`
      (`internal/mailing/templates_test.go`) proves it for the transactional
      templates. Set `ShowListFooter: true` and supply
      `ManageURL = baseURL + "/preferences?token=" + manageToken` and
      `UnsubscribeURL = baseURL + "/unsubscribe?token=" + manageToken`, the
      same construction the five existing templates use.

- [ ] **The footer's unsubscribe link is `/unsubscribe` (the SPA confirmation
      page), NOT `/api/unsubscribe`.** The latter is the RFC 8058 endpoint
      `#0035`'s `List-Unsubscribe` header targets. PRD §6.5's Path 1 and Path 2
      deliberately hit different routes; wiring the footer at `/api/unsubscribe`
      would put a state-mutating POST endpoint behind a link that mail clients
      and security scanners prefetch.

- [ ] **Add a test asserting both labels appear in the rendered campaign body**,
      in the same property-test style as the footer test above, so the criterion
      `#0035` could not close is actually closed here rather than assumed.

## Carried in from `#0042`'s review (2026-08-21)

`#0042` landed `RenderMarkdownHTML`/`RenderMarkdownText`/`RenderCampaign` in
`internal/mailing/campaign_markdown.go` and `campaign_render.go`. Three things
this issue inherits from it:

- [ ] **There are now two footer implementations, and this issue's criteria
      above tell you to use the other one.** `#0035`'s carried-in block says
      "The mechanism already exists and is already tested — do not build a new
      one … Set `ShowListFooter: true`", meaning `emailContent.ShowListFooter`
      in `templates.go`. But `#0042` built its own footer inline in
      `wrapCampaignHTML` and `wrapCampaignText` (both PRD §6.5 labels verbatim,
      `/preferences?token=` and `/unsubscribe?token=`, physical address
      appended, pinned by `TestRenderCampaign_FooterCarriesBothRequiredLabels`
      and `TestRenderCampaign_TokenSubstitutedIntoFooterLinks`). **Reconcile
      these deliberately — do not leave two footers that can drift.** Either
      route the campaign path through `ShowListFooter` and delete `#0042`'s
      copy, or keep `#0042`'s and record here why the shared mechanism does not
      fit. Whichever you pick, the two PRD §6.5 labels and the `/unsubscribe`
      (not `/api/unsubscribe`) route must stay pinned by a test; both mutations
      were verified to fail correctly during `#0042`'s review, so that coverage
      exists to carry over.

- [ ] **`wrapCampaignHTML` is the seam to replace, and the reason it is
      unbranded is real.** It already produces a valid mail-safe document —
      single-column table layout, inline styles only, explicit `bgcolor` on the
      outer table, `max-width:600px` — but on a plain light palette, not the
      brand skin. `#0042`'s reviewer verified the stated reason rather than
      accepting it: `renderHTML` in `templates.go` sets `color:` on each
      individual `<p>`/`<h1>`, and the card `<td>` (`templates.go:155`) carries
      `bgcolor`/`background-color` but **no `color`**. So dropping goldmark's
      unstyled `<p>`/`<h2>`/`<ul>` into that cell inherits the document default
      (black) onto `#10231a` — near-invisible. `emailContent` is also a fixed
      shape (`Heading` + `Paragraphs` + button), not an arbitrary-HTML-body
      host. **Styling arbitrary Markdown-shaped HTML at N levels of nesting is
      this issue's actual work**, and it must set an explicit `color` on the
      body-fragment container *and* survive the background-stripping case the
      `#0028` carried-in block above describes.

- [ ] **Do not touch `RenderMarkdownHTML`, `RenderMarkdownText`,
      `CampaignRenderInput`, or the token/address handling in
      `RenderCampaign`.** Those are meant to carry over unchanged; this issue
      replaces only the document wrapper around `bodyHTML`. Note that
      `RenderMarkdownHTML` returns a *fragment*, already sanitized (raw HTML
      suppressed, `<img>` stripped entirely, dangerous schemes neutralized) —
      do not re-sanitize it and do not escape it again on the way in.

- [ ] **Name the builder so `#0085`'s guard sees it** — see the `#0085`
      carried-in block above. `#0042` deliberately added no `Build*Email`
      function, so the guard is still unexercised for campaigns.
