## Description

Two defects in the guard coverage around `scripts/testdb.sh`, both found by the
batch review of `#0331`, `#0332`, and `#0333`. Neither was a bounce — no
acceptance criterion asked for either — but both are cheap and both weaken the
harness that is supposed to make this script safe to change.

### 1. `#0331` is unguarded

The reviewer mutated each of the three fixes in turn, against a sandboxed copy
so the harness resolved to its subject:

| Subject mutation | Harness result |
|---|---|
| `#0333`'s refusal neutered | **9 named failures**, including the shared template actually dropped |
| `#0332`'s anchor reverted to unanchored | **2 named failures**, then a fatal abort when its own later mutation could no longer find the anchored line |
| `#0331`'s `\|\| true` stripped | **`all guards hold (0 failures)`** |

So the fix that stops `template_state()` dying silently is itself invisible to
the suite. Strip its `|| true` and everything stays green.

`#0332` and `#0333` both gained external coverage in
`scripts/testdb_gc_guard_test.sh`. `#0331` is the odd one out, and the reviewer
demonstrated the cheap close: extract the function and call it directly, which is
exactly what it did by hand to prove the defect.

### 2. Part 6's mutation comment is wrong about itself

`scripts/testdb_gc_guard_test.sh` Part 6 claims its `sed` targets the line "by a
wildcard match, not a copy of its literal condition — §8". **The `sed` is a
verbatim character-for-character copy of the condition.**

The technique still works and still fails closed — the reviewer confirmed the
sibling mutation aborts loudly when its anchor goes missing, rather than passing
silently. Only the **justification** is false, and it is the kind of false that
matters: someone reading it will believe the `sed` is robust to reformatting the
condition, and it is not.

`CLAUDE.md` §8 is the section being cited, and its actual rule is that an
oracle must not be the same bytes as its subject. A comment claiming compliance
while doing the opposite is worse than no comment.

## Root cause

Both defects trace to the same source: the batch review that produced this
issue mutated all three subjects, but only two of them (`#0332`, `#0333`)
already had a dedicated harness section to extend. `#0331` lived entirely
inside `template_state()`, a function neither of `testdb.sh`'s own call sites
happens to exercise under the exact condition the fix addresses — one call
site is always reached through an `if`, which suspends `set -e`; the other is
always reached through its own command substitution, which a bash 3.2 quirk
shields. So nothing in ordinary use, and nothing in the existing harness,
ever called `template_state()` the one way that makes the missing `|| true`
matter. Part 6's comment was simply wrong: whoever wrote it described the
sed as a wildcard match without checking it against the pattern actually
used, which is a verbatim copy of the condition text.

## Fix

Added Part 7 to `scripts/testdb_gc_guard_test.sh`. It extracts
`template_state()`'s real function body from a private copy of
`scripts/testdb.sh` (an `awk` range from the definition line to its closing
brace — the same technique the reviewer used by hand), sources the
extraction into a small driver script under `set -e`, and calls the function
directly against a database name that is guaranteed never to exist. The
unmutated fragment returns `none|none` without aborting; a mutant with
`|| true` stripped aborts the driver instead, proving the assertion is
sensitive to the regression rather than vacuously true.

Corrected Part 6's comment to state plainly that the sed is a literal copy
of the condition, not a wildcard match, and explained why: the wildcard
technique the `exclude_clause` mutations use works only because it targets
an assignment, where the variable name is a stable anchor separate from its
value; a bare `if [ condition ]; then` has no such separate name, so
locating it necessarily means matching its own text. Left the sed itself
unchanged — reformatting the condition would make it a no-op, and the
existing take-effect check right below it already fails the whole run with
a FATAL message rather than silently proceeding, so the failure mode this
leaves open is closed, not silent.

No changes were made to `scripts/testdb.sh` itself for this issue; both
fixes are additions to the external harness only, per the acceptance
criteria's constraint against in-script checks.

## Gotchas

None specific to this issue. The `#0331` extraction technique (extract the
real function body, run it directly under `set -e`) generalizes to any
function whose bug depends on *how* it is called rather than *what* it
computes — ordinary input/output assertions against the existing call sites
would never have caught this one.

## Acceptance criteria

1. **Give `#0331`'s fix a guard**, in the external harness rather than in-script
   (`CLAUDE.md` §8: a guard inside the file it guards becomes new mutable
   surface). The reviewer's method — extract `template_state()` and call it
   directly — is the shape; you may choose another if you say why.
2. **Prove it by mutation**: stripping `|| true` must make the new guard fail
   and name the problem. A guard never seen to fail is not a guard.
3. **Correct Part 6's comment** to describe what its `sed` actually does. Decide
   whether to *also* make the `sed` match the claim; if you leave it literal,
   say plainly that reformatting the condition breaks the mutation and that this
   is acceptable because it fails closed.
4. **Do not add in-script checks** to `scripts/testdb.sh`. `#0258` spent six
   passes hardening a file against decoys added to that same file; the external
   harness exists to avoid that.
5. Run the harness against a **sandboxed copy**, never the real template or
   another agent's scratch database (`CLAUDE.md` §8b). The shared template is
   live and other agents' databases may exist.

## Review notes — 2026-09-09 (phase 3, of `02fa6d6` — approved)

Re-verified by mutating `scripts/testdb.sh` itself, not the harness's private
copy of it. The sandbox was a throwaway directory holding a copy of `scripts/`
plus a symlink to `migrations/`, so the harness's own repo-root resolution
pointed `REAL_SCRIPT` at the mutated subject. Running that sandbox unmutated
first is what proves the resolution actually moved — it reported all ten parts
green and hashed the sandbox copy in its byte-identity check.

| Subject mutation | Harness result |
|---|---|
| `template_state()`'s `\|\| true` stripped | aborts, exit 1, naming `#0331` |
| the signature reformatted to `template_state ()  {` | aborts, exit 1: extraction "produced nothing" |
| the refusal condition re-quoted to `"${force}"` | Part 6 aborts, exit 1: mutation "did not take effect" |

**Criterion 2 is met, and by two independent layers.** The textual precondition
catches a stripped `|| true` before the behavioural test runs, and the
behavioural assertion is itself proved sensitive by the fragment-level mutation
the harness ships, which exits 2 with no output.

**§8's empty-result rule is satisfied.** An extraction that yields nothing is a
FATAL abort with a nonzero exit, never an input — confirmed by reformatting the
function signature so the `awk` range stops matching.

**`#0258`'s ambient-fallback trap is closed here, though not by the prescribed
mechanism.** The driver is a separate `bash` process, and bash passes function
definitions through the environment, so an ambient exported `template_state`
*is* inherited — measured directly: a driver whose sourced fragment defines
nothing ran the inherited definition and printed its values instead. Neither
`env -i` nor an `unset -f` stands between the two. What closes the fail-open is
the pairing rather than the isolation: any ambient definition that satisfies the
positive assertion produces identical output for the mutant fragment, so the
mutation proof then fails loudly instead of agreeing. That was constructed and
measured, not reasoned — a non-defining fragment plus an ambient none/none
definition made the positive assertion pass falsely and the mutation proof fail,
so the guard cannot report a false green through this path. Adding
`unset -f template_state` to the driver is still worth the one line whenever
this file is next opened.

**Part 6's literal `sed` is the right call and its stated cost is real.**
Re-quoting the condition to `"${force}"` was applied to the subject and
measured: the `sed` becomes a no-op, and the take-effect check aborts the whole
run with its FATAL message rather than proceeding against an unmutated script.
One overstatement is worth recording without blocking on it — the comment says
no equivalent wildcard form exists for a bare `if`, but a pattern anchored on
the variable name and wildcarding the rest, along the lines of
`^      if \[ .*force.*\]; then`, would in fact survive that re-quoting. The
decision to stay literal still stands, because what makes it acceptable is the
proved fail-closed behaviour and not the absence of an alternative.

the shared commit belong to `#0482`, which is bounced separately.
