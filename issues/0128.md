## Description

An admin cannot see who signed up but never confirmed, cannot tell how long they have been waiting, and cannot resend a confirmation. When a confirmation email fails to arrive — SES outage, a spam folder, a typo'd address — nobody finds out.

## Implementation notes

Phase 2 (Sonnet), 2026-08-24. No separate phase-1 planning pass ran; design
decisions were made and disclosed inline (code comments + this section).

**`internal/subscribers/pending.go`** (new file) adds three methods:

- `ListPending(ctx, oldestFirst bool) ([]Subscriber, error)` — every
  `status='pending'`, `synthetic=false` row, sorted by `confirm_sent_at`.
  Reuses the existing `Subscriber` type rather than a narrower
  `PendingSubscriber` type, matching `List`'s own convention.
- `AdminResendConfirmation(ctx, id, now, cooldown, ttl) (ResendResult, error)`
  — mints a genuinely NEW `confirm_token` (unlike the public
  `ClaimAndEnqueueConfirmation`, which reuses the existing one), extends
  `confirm_expires_at`, stamps `confirm_sent_at`, and enqueues the new
  confirmation — all inside one transaction, so a committed resend can
  never leave the new token unqueued. Guarded, in order, inside the same
  transaction (`SELECT ... FOR UPDATE`): exists and not synthetic
  (`ErrPendingSubscriberNotFound`), `status='pending'` (`ErrNotPending`),
  not suppressed (`ErrResendSuppressed`), and the same
  cooldown-in-the-WHERE-clause shape `ClaimAndEnqueueConfirmation` uses
  (`ErrResendCooldownActive`) — the criterion's "rate-limited per
  subscriber so the screen cannot be used to mail-bomb an address".
- `ExpirePendingSweep(ctx, now) (int64, error)` — clears `confirm_token`
  (only) and writes one `confirmation_expired` subscriber_events row per
  address for every pending row past `confirm_expires_at`; the row stays
  `status='pending'`, per the criterion. Idempotent by construction: the
  WHERE clause requires `confirm_token IS NOT NULL`, so a repeat sweep
  over an already-cleared row is a no-op.

**Where the sweep runs — a disclosed, deliberate choice.** #0128's
criterion just says "a sweep expires pending signups". Rather than stand up
a fourth dedicated ticker in `cmd/opencircuit/main.go` (alongside the send
worker, the outbox worker, and the orphan sweep already inside it),
`ExpirePendingSweep` is called once per `OutboxWorker.pass()` — the same
poll loop that already sweeps orphaned claims and drains the queue. It is
cheap (one indexed `UPDATE ... RETURNING`, near-zero rows in the steady
state), and that worker already holds the one `*subscribers.Store` this
package is given. See `outbox_worker.go`'s `pass` doc comment for the
argument in full; a reviewer who wants a separate ticker instead should say
so, this was a judgment call under time pressure, not a forced design.

**`internal/outbox/store.go`** gains two read methods used only by this
issue: `LatestByRecipients(ctx, kind, recipients) (map[string]Row, error)`
— one query for every pending address's confirmation-mail queue state
(`DISTINCT ON (recipient) ... ORDER BY recipient, created_at DESC`), not one
per row — and `AbandonedCountByKind(ctx, kind) (int64, error)`, scoped to
one kind rather than `Counts`' account-wide total.

**`internal/handlers/admin_pending.go`** (new file, new
`AdminPendingHandler`) serves both routes, registered through
`adminRoutes()` in `cmd/opencircuit/main.go` — `#0079`'s AST guard
(`TestAdminRoutesRegisteredOnlyViaTable`) therefore covers them
structurally, and `TestMountAndServe_AdminRoutesRequireSessionAndAdmin`
(`admin_wiring_test.go`, extended to construct a real `adminPendingH`)
proves the session/admin guard end-to-end the same way it does for every
other admin route. `age_seconds`/`expired` are computed **server-side, at
response time** — the client renders them, it does not recompute a "now" of
its own. Error mapping: 404 not found, 409 not pending, 409 suppressed
(with a distinct, named reason in the response body), 429 cooldown active.

**Audit, without the address in Metadata.** A new
`audit.ActionSubscriberResendConfirmation` constant
(`internal/audit/actions.go`) is written on every successful resend.
Metadata carries only `previous_confirm_sent_at` (RFC3339, omitted for a
first-ever send) — deliberately no `email` key, so this new
`audit.Entry{}` call site does not need an entry in
`internal/handlers/audit_email_metadata_guard_test.go`'s

**Dashboard (`#0061`).** `pending` count needed no new plumbing — it was

### The mail-bomb guard holds under real concurrency

The criterion that matters most here is "rate-limited per subscriber so the
screen cannot be used to mail-bomb an address", and the doc comment
describes a mechanism the code does not use (see defect 1 below), so I did
not take it on trust. Scratch test: eight goroutines calling
`AdminResendConfirmation` simultaneously on one backdated pending
subscriber with a one-hour cooldown. Result: **`wins=1 cooldowns=7 others=0
queued_delta=1`** — exactly one success and exactly one new
`outbound_queue` row. The property is real; `SELECT ... FOR UPDATE` is what
delivers it. Scratch test removed afterwards.

### Ruling: the expiry sweep riding `OutboxWorker`'s poll loop is ACCEPTABLE

The implementer flagged this as a judgment call made under time pressure and
invited a reviewer to demand a separate ticker. I am not demanding one:

- **It genuinely runs.** `newOutboxWorker` is called unconditionally in
  `servePostgres` and wires `Events: subscribers.NewStore(pool)`, and its own
  doc comment records that this worker "always runs whenever Postgres is in
  use" with no `SEND_WORKER_ENABLED`-shaped opt-in. So the sweep is not
  hostage to a scaling knob. Under `STORAGE=json` it is inert, which is
  correct — that mode has no mailing subsystem at all.
- **It does not interact badly with `#0126`'s claim/sweep timing.** It runs
  after `OrphanSweep` and before `ClaimDue`, in its own transaction, against
  `subscribers` and `subscriber_events` — tables the queue path does not
  touch. It does not influence `processed`, so the poll cadence is unchanged.
  Lock ordering cannot cycle: both this sweep and `Confirm` take the
  `subscribers` row lock first.
- **The `Confirm`-versus-sweep race is well-behaved in both orders**, which I
  worked through rather than assumed. If `Confirm` wins, the sweep's `UPDATE`
  blocks on the locked row, then re-evaluates its `WHERE` and finds
  `confirm_token IS NOT NULL` false — no spurious `confirmation_expired`. If
  the sweep wins, `Confirm`'s lookup by `confirm_token` finds nothing and
  returns `ErrTokenInvalid`, which is the right answer for a token that had
  already expired. The `confirm_token IS NOT NULL` predicate is what makes
  both directions safe, and it is also what makes the sweep idempotent.
- **It does not interact with `#0126`'s open `Stop` defect.** That defect is
  that `OutboxWorker.Stop` does not release claimed rows despite its doc
  comment saying it does. The sweep lives in `pass`, not `Stop`, and touches
  no `outbound_queue` row, so the pending fix is orthogonal. (It does mean
  the two changes land in the same file — an orchestration ordering concern,
  not a correctness one.)

One caveat worth recording: **the sweep's frequency is not what a reader
would guess.** `Run` skips the poll wait whenever a pass claimed work, so on
a busy queue the sweep runs once per *batch*, not once per `pollInterval`.
It is idempotent and indexed, so this is harmless — but it is worth a
sentence in `pass`'s comment if anyone touches this again.

### Two doc-comment inaccuracies — report, not blockers

Neither changes behaviour; both describe a mechanism that is not the one
implemented, which is the kind of drift that misleads the next maintainer.
**Recommend the orchestrator file one small issue covering both:**

1. **`AdminResendConfirmation`'s doc comment (`internal/subscribers/pending.go`)
   misdescribes the cooldown.** It says guard 4 uses "the same
   claim-in-the-WHERE-clause shape `ClaimAndEnqueueConfirmation` uses, so a
   second concurrent admin click can't both win". It does not:
   `ClaimAndEnqueueConfirmation` really does put the cooldown in `WHERE id =
   $1 AND (confirm_sent_at IS NULL OR confirm_sent_at < $3)` and branches on
   `RowsAffected`, whereas `AdminResendConfirmation` checks it in Go after
   the `SELECT ... FOR UPDATE`. The safety property is equivalent and I
   proved it above — but the comment credits the wrong mechanism, and a
   future reader could conclude the `FOR UPDATE` is redundant and remove the
   thing that is actually doing the work. `issues/0128.md`'s Implementation
   notes repeat the same claim ("the same cooldown-in-the-WHERE-clause
   shape") and should be corrected with it.
2. **`formatPendingAge`'s doc comment (`web/src/lib/pending.ts`) advertises
   an output the function cannot produce.** It says the helper renders "the
   largest whole unit that reads naturally — "45 seconds", "12 minutes",
   "3 hours", "2 days"", but there is no seconds branch: anything under
   60s returns `'just now'`. The behaviour is fine and deliberate; the
   example is wrong.

### Everything else checked and found clean

- **Guard order in `AdminResendConfirmation` cannot be used to mail an
  address that left.** `status = 'pending'` is required before suppression
  and cooldown are even consulted, so `unsubscribed`, `bounced` and
  `complained` rows are all refused with `ErrNotPending` → 409. §9's
  "`complained` subscribers never auto-resubscribe" is not reachable from
  this endpoint. A resubscriber who came back through `RestartSignup` is
  `pending` again and is legitimately resendable.
- **Cooldown and TTL are the public endpoint's own constants**, not
  separately-tuned admin values: `subscribeResendCooldown` (1h) and
  `subscribeConfirmTTL` (7d) from `internal/handlers/subscribe.go`. This is
  the criterion's "cannot be used to mail-bomb" in the strongest available
  form — an admin cannot out-send the public path.
- **Audit metadata carries no address** — only `previous_confirm_sent_at`,
  confirmed by reading the call site and by
  `TestAdminPending_Resend_Success_MintsFreshTokenAndAudits`, which asserts
  the absence directly. `audit_email_metadata_guard_test.go` was correctly
  left untouched.
- **No new retained store of subscriber email**, which mattered given
  `#0126`'s open erasure blocker. `ListPending` and `LatestByRecipients` only
  read; `ExpirePendingSweep`'s `confirmation_expired` rows carry a non-NULL
  `subscriber_id`, so `erase.go`'s action-agnostic `UPDATE subscriber_events
  SET email = $2 WHERE subscriber_id = $1` redacts them. `#0126`'s defect 1
  does not newly apply here.
- **Route precedence is sound.** `GET /admin/subscribers/pending` competes
  with `GET /admin/subscribers/{id}`; Go 1.22+ prefers the more specific
  literal regardless of registration order, exactly as
  `/admin/subscribers/export` already relies on.
- `LatestByRecipients`'s `DISTINCT ON (recipient) ... ORDER BY recipient,
  created_at DESC, id DESC` is correct and tie-broken; the empty-slice case
  short-circuits without a query.
- Dashboard three-file agreement holds: `AbandonedConfirmations` (Go, with
  `json:"abandoned_confirmations"`), `abandoned_confirmations` in
  `types.ts`, and the rendered `<li>` in `Dashboard.svelte`. The pending
  count was already present via `STATUS_ORDER`.
- The disclosed `DELETE FROM subscriber_events` that
  `TestSubscriberEvents_AppendOnlyGuard` caught during implementation is
  genuinely absent from the committed tree.

## Notes

PRD §5.2 and §8 carry the routes; §6.3 is the flow.

`confirm_expires_at` and `idx_subscribers_confirm_expires` already exist from `migrations/000010`, so the expiry data is there — nothing reads it and nothing acts on it.

**Why this pairs with `#0126`.** Without the durable queue, "why didn't they confirm?" has no answer: the send happened on a goroutine that left no trace. With it, the pending screen can show whether the confirmation was even delivered to SES, which turns a mystery into a fact. Build them in that order.

**Do not add a bulk resend.** A button that re-mails every pending address at once is a spam complaint generator, and pending addresses are by definition the ones least likely to want mail. Per-subscriber resend only.

**Registering outside `adminRoutes()` ships an unguarded admin route that passes every test** — `#0079` is the issue that established this. New admin endpoints go in the table.
