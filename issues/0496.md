## Description

`issues/Issues.md`'s phase 2, **step 2**, already says it:

> **Set status to `in-progress`** in the markdown — working copy only, no
> commit. The Mac app picks it up immediately.

And it would work. `scripts/list-issues-by-phase` reads the **working tree**
(`path.read_text`), not committed state, so an uncommitted flip is visible in
the queue immediately.

**Agents are not doing it.** Observed three times in a row today — `#0398`,
`#0397`, and `#0397`'s second pass each reported "status left as `open`" on
completion, and the user caught the queue showing `open` for an issue actively
being implemented.

## Why it matters

`CLAUDE.md` §4 leans on this status hard in the other direction:

> **`in-progress` with nobody working it is abandoned work, and it comes
> first.** A subagent that bailed, was interrupted, or died after committing
> code but before review leaves the issue there, and nothing surfaces it except
> this script.

That rule is load-bearing and it paid out today: `#0331`, `#0332`, and `#0333`
were found sitting `in-progress` and unreviewed for **nine days**, and `#0258`'s
seventh pass had been done-but-unreviewed for **fifteen**.

The mirror image is what is broken here. **`open` while actively being worked is
indistinguishable from untouched**, so a second agent or a second session can
pick up work already in flight. This session avoided that only because one
orchestrator held the dispatch list in its own head — which does not survive the
session ending mid-issue, and this session has already spent substantial effort
on work stranded exactly that way.

## Root cause — the orchestrator's dispatch briefs, not the agents

The dispatch briefs written throughout this session end with some variant of:

> Commit code; leave `issues/NNNN.md` **uncommitted** with your resolution
> sections. **Do not** set it `resolved`.

That names the *end* state and forbids one transition, and **never mentions step
2**. An agent reading it reasonably concludes the status is not its concern
until the end. Around forty dispatches carried that shape today.

So this is not agents ignoring `Issues.md`; it is a brief that quietly overrode
it. The orchestrator wrote those briefs.

## Fix

Two prose edits to `issues/Issues.md`, both rewriting text inside an existing
numbered step — no new step, no renumbering, no new `##` heading:

- **Phase 2, step 2** now says the flip happens **before step 3's first code
  change, regardless of what the dispatch brief describes** — closing the
  loophole this issue names directly, so an implementer who only receives an
  end-state brief still has its own orientation reading (step 1) telling it
  the brief is not the whole instruction. It also says what the status is
  *for* (the queue's only signal another session can see, per `CLAUDE.md`
  §4) and states the "no commit" reasoning inline (criterion 3, below)
  instead of leaving it as an unexplained clause.
- **"Orchestrator: pick and dispatch", step 5** now requires dispatching **by
  reference, not by paraphrase**: point at phase 2 above and add only what is
  issue-specific. This is where criterion 2 is actually closed — the root
  cause was a brief that restated part of phase 2's sequence and, in
  restating it, restated it incompletely. A brief that points at phase 2
  instead of paraphrasing it cannot drift from it the way ~40 dispatches did
  today.

**Criterion 3 — kept "working copy only, no commit."** The two risks named in
the criterion are real in general but not live exposure for this pipeline
today: `scripts/list-issues-by-phase` already gives same-checkout visibility
the instant the file is saved, which is the property step 2 exists to
provide, and this pipeline dispatches phase 2 from a single checkout, not a
worktree — `CLAUDE.md` §5a reserves worktrees for disjoint-file *code* work,
not concurrent edits to the same issue markdown file, so "invisible to
another checkout" has no case to apply to today. The "lost if the tree is
reset" risk is already covered by `CLAUDE.md` §8a's blanket prohibition on
destructive git operations against a file you did not edit — a lost flip from
a reset is a §8a violation to fix at the point it happens, not a new gap
worth a mechanism here. Against that, committing the flip would add a second,
content-free commit to every issue this pipeline ever touches. The record
that actually motivated this issue — three same-day reports of the flip
never happening at all — is a briefing failure, which the step-2 and step-5
edits above address directly; nothing in that record was a commit ever being
lost to a reset or missed across a checkout.

**Criterion 5 — phase 1 has a narrower version of the hole; phase 3 does
not.** Phase 1 (planning) deliberately leaves **Status** at `open` for its
whole duration ("Filing a new issue" step 7, and the phase table's "Status
after" column) — a running planning pass is indistinguishable from an
untouched issue, the same failure shape this issue names for phase 2. It is
narrower in consequence: planning writes no code and nothing is lost if two
planning passes overlap, only duplicated effort, and `CLAUDE.md` §3 already
makes most issues skip phase 1 entirely. It is also harder to fix without a
new mechanism: the five-value status vocabulary (`## Status values`) has no
open slot for "being planned" that would not either overload `in-progress`'s
meaning (which `CLAUDE.md` §4 ties specifically to code work in flight) or
require adding a sixth status value — exactly the kind of new machinery
criterion 4 forbids for this issue. Recorded, not fixed here, per criterion
5's own instruction. Phase 3 (review) has **no equivalent hole**: **Status**
is already `in-progress` for the entire review window, inherited from phase 2
and only changed at phase 3 step 4 (to `resolved` on approve, back to `open`
on bounce), so the queue already shows "taken" correctly for the whole time a
review is in flight, with no separate flip for a reviewer to skip. An
abandoned review looks exactly like an abandoned implementation and is
already the case "Orchestrator: pick and dispatch" step 3 tells the next
session to resume, usually at phase 3.

## Acceptance criteria

1. **Make step 2 harder to skip.** It is currently one line among nine, and its
   "working copy only, no commit" clause can be read as "this does not really
   matter." Say what it is *for* — that the queue is how another session learns
   the issue is taken, per `CLAUDE.md` §4 — and that the flip happens **before**
   the first code change, not at the end.
2. **Close the orchestrator's half.** The dispatch brief is where this was
   actually lost. Record, where the orchestrator will meet it, that a phase-2
   dispatch must not describe the issue file's end state without also naming
   step 2 — or state the convention so briefs need not repeat it.
3. **Decide whether "no commit" is still right**, and say why either way. It
   keeps the tracker's history clean and the working-tree read makes it visible
   locally — but an uncommitted flip is invisible to another *checkout*, and is
   lost outright if the tree is reset. Weigh that against committing a status
   row twice per issue.
4. **Do not add a mechanism that polices this.** No guard, no hook.
   `CLAUDE.md` §8 records `#0258`'s six-pass spiral, and `#0478`/`#0479`/`#0480`
   established that a documented step plus a re-run is the whole fix for a
   process gap. A prose fix is the deliverable.
5. **Check whether phase 1 and phase 3 have the same hole.** A planning pass and
   a review pass are equally invisible while running. Say what you found; do not
   necessarily fix them in this pass.
6. **Do not renumber phase 2's steps** unless you must — `CLAUDE.md` and several
   issues cite "phase 2 step 8" and "phase 3 step 5" by number, and
   `internal/handlers`' citation guards resolve section references. If you do
   renumber, find and update every citation.

## Review notes

Approved on the first pass. Findings, in the order the acceptance criteria run.

**The flip was genuinely made on this issue itself (criterion 1's own test
case).** The filing commit `0c2bac9` wrote `| **Status** | open |`; the working
copy this review received read `in-progress`, uncommitted. That much is
verifiable. The stronger claim — that it was set *first*, before any other
work — is the implementer's self-report in `## Files changed` and cannot be
independently checked, because an uncommitted single-line edit leaves no
ordering evidence. That is not a gap to close: criterion 4 forbids exactly the
mechanism that would make it checkable, and the observable half (the status is
flipped at all) is the half the three same-day incidents failed.

**Criterion 3's decision to keep the flip uncommitted is right, and for the
reason the implementer gives last rather than first.** The decisive fact is
that none of the three reported incidents was a flip lost to a reset or missed
across a checkout — all three were flips never made. Committing the status row
would have prevented none of them while adding a content-free commit to every
issue this tracker ever touches. The cross-checkout risk is real in the
abstract but has no case to apply to today: `CLAUDE.md` §5a reserves worktrees
for concurrent *code* work on files that would otherwise collide, and the
dominant mode this whole pipeline assumes — the entirety of `CLAUDE.md` §8a is
written about agents sharing one tree — is a single checkout. Worth naming as
the one thing that would reopen the question: if phase 2 ever routinely runs in
a worktree, the new step 2's "this pipeline dispatches phase 2 from one
checkout" becomes stale and the decision deserves re-deciding. It is scoped
honestly enough ("this pipeline") that it will read as a claim about practice
rather than a law.

**Criterion 5's phase 3 claim checked and confirmed, with one conservative
misattribution.** I re-derived it from phase 3's text rather than accepting it.
Phase 2 step 2 sets `in-progress` and no later phase 2 step changes it — step 7
explicitly says to leave it there. Phase 3 inherits that, so the status reads
`in-progress` for the whole review window and an abandoned review is visible in
the queue exactly as an abandoned implementation is. The claim holds.

The misattribution: `## Fix` says the status is "only changed at phase 3 step 4
(to `resolved` on approve, back to `open` on bounce)". Step 4's bounce branch
does revert to `open`, but its approve branch says the opposite — leave the
status at `in-progress` — and the flip to `resolved` happens later, in step 5's
second sub-step, after the pre-flip guard run. The error runs in the safe
direction: the real flip is *later* than claimed, so the review window during
which the queue shows "taken" is longer than the argument assumes, and the
conclusion is strengthened rather than weakened. Left as written rather than
corrected, since it is a resolution note recording what was found, not a live
instruction.

**Criterion 6's citation survey re-derived independently, and it holds.** The
implementer's grep was narrower than the risk, so I widened it: every
step-number citation across `CLAUDE.md`, `issues/*.md`, and `docs/*.md`, then
filtered to those naming a phase or the dispatch loop. The hits name phase 2's
steps 4, 5, 7 and 8; phase 3's steps 3, 4, 5 and 6; and the orchestrator loop's
steps 2 and 3 (`#0478` cites the latter's step 2, and this file's own step 7
points back to it). None names phase 2 step 2 or the orchestrator's step 5 —
the two this commit rewrote. The point is moot in any case, because the diff
preserves both numbers in place: it is two in-place replacements of numbered
list items, `2.` for `2.` and `5.` for `5.`, with no item added, removed, or
reordered in either list. No citation anywhere could have been invalidated.

**Criterion 4 confirmed by the diff's shape.** Twelve insertions, two
deletions, one file, prose only. No test, no guard, no hook, no script.

**Does phase 2 still read as instructions? Yes — narrowly, and the ratio is
worth watching.** Step 2 grew from one line to twelve, and only the first two
and a half are imperative; the rest is rationale. By raw proportion that is
worse than the step 8 `#0480` flagged. It passes anyway, because `#0480`'s
actual complaint was *inversion* — exposition arriving before the instruction —
and this step is not inverted. Its first two sentences are bolded imperatives
carrying the complete instruction, including the loophole-closing clause, and a
reader who stops there has lost nothing. The rationale that follows was
demanded by criteria 1 and 3, which asked the step to say what the flip is for
and why "no commit" is still right.

The one line that could go is the last, which re-argues the commit decision the
issue file already argues at length. Recorded rather than trimmed: phase 3's
remit is approve or bounce, not to edit the fix, and one redundant sentence is
not worth a bounce. But phase 2 now has two steps that have grown this way, and
a third would be a pattern rather than a coincidence.

**Nothing worth filing.** The two residuals above — the worktree caveat on step
2's rationale, and the growth ratio — are recorded here and want no issue.

**Phase 3 was followable from this file alone.** This dispatch deliberately did
not restate the sequence, which made it the first test of the convention the
commit under review establishes, and the sequence held: orient, read the diff,
re-run verification independently, decide, run the guards in the prescribed
order around the status flip, commit with the index checked. Three small
frictions, all resolved by reading the whole phase before starting, as step 1
effectively requires. Step 4 calls the approve blockquote "top-of-resolution"
while step 5 calls the same artifact a "top-of-file blockquote" — the latter is
the placement the tracker actually uses. Step 4 says to "ensure the `**Commit**`
row is present" without saying what to do when the implementer omitted it, as
happened here; adding it is the obvious reading and is what this pass did.
And `## Review notes` is named under step 4's bounce branch only, so that it is
expected on approve as well is learned one step later, in step 5. None of these
cost more than a re-read, and none needs fixing.
