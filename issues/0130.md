## Description

Two latent test-isolation defects found by `#0121`'s second phase-3 review, both harmless today and both in the class `#0121` exists to eliminate. `resetSettings` permanently destroys two settings rows that migration `000018` seeded, and `TestAudit_SettingsUpdated` leaks `registrations_enabled = 'true'` with nothing to restore it.

## Acceptance criteria

- [x] `resetSettings` (`internal/handlers/settings_test.go`) re-inserts `max_send_rate` and `default_from_name` alongside the four keys it already restores, so a `DELETE FROM settings` followed by its re-seed leaves the table matching the migration seed
- [x] ~~`opencircuit_test` is repaired~~ — **done incidentally 2026-08-21**: `#0122` dropped and recreated `opencircuit_test` to pick up an in-place edit to `migrations/000018`, which re-applied the seed. This does not fix the issue: the next `internal/handlers` run destroys both rows again. The criterion is struck because there is nothing left to repair, not because the defect is gone
- [x] `worker_test_helpers_test.go:46`'s comment asserting these are "GLOBAL rows seeded by migration" is either true again or corrected
- [x] `TestAudit_SettingsUpdated` restores `registrations_enabled` with a `t.Cleanup`, or `credsTestPool` resets `settings` the way `settingsTestPool` now does
- [x] `internal/handlers` still passes under `-shuffle` on at least two fresh seeds
- [x] A direct query after a full package run shows `settings` matching the migration seed exactly — the check `#0121`'s second pass claimed and did not have

## Notes

Found during `#0121`'s second review, which verified the claim by direct query rather than taking the implementer's word for it: `resetSettings` does `DELETE FROM settings` and re-inserts only four keys, so `max_send_rate` and `default_from_name` — seeded by `migrations/000018` for `#0045`'s send worker — are gone from `opencircuit_test` right now.

**Why it is harmless today, and why that will not last.** `effectiveSendRate` falls back when `max_send_rate` is absent, and `internal/mailing`'s `setSetting` handles a missing row. So nothing fails. But the fallback is the only thing standing between this and a real failure, and a future test that asserts the seeded value rather than the fallback would fail for a reason nobody would look for in `internal/handlers`.

`TestAudit_SettingsUpdated` is the same defect class as the `settingsTestPool` teardown gap `#0121` fixed, one table over and one pool over: `credsTestPool` does not reset `settings`, and `TestMain`'s teardown truncate covers `subscriber_interests`, `subscribers`, and `audit_log` but not `settings`.

Neither is urgent. Both are cheap, and both are exactly the kind of ambient-state dependency that costs an afternoon when it finally bites.

## Root cause

`resetSettings` (`internal/handlers/settings_test.go`) does `DELETE FROM
settings` and then re-inserted only four of the six rows migration `000018`
(via `000004`, `000008`, `000015`, `000018`) seeds — `physical_address`,
`registrations_enabled`, `soft_bounce_threshold_count`, and
`soft_bounce_threshold_window_days`, but not `max_send_rate` or
`default_from_name`. `settingsTestPool` calls `resetSettings` both on entry
and via `t.Cleanup`, so every `internal/handlers` test run using it
permanently dropped those two rows from whichever database
`TEST_DATABASE_URL` named. Separately, `TestAudit_SettingsUpdated`
(`internal/handlers/audit_seams_test.go`) goes through `credsTestPool`, which
(unlike `settingsTestPool`) never resets `settings`; the test flips
`registrations_enabled` to `"true"` via its `PATCH /admin/settings` request
and had nothing restoring it afterward, leaking that value into whichever
test ran next under `-shuffle=on`.

## Fix

- `resetSettings` now re-inserts all six migration-seeded keys, including
  `max_send_rate='10'` and `default_from_name=''` (matching
  `migrations/000018_add_campaign_send_state.up.sql` exactly), and its
  doc comment was updated to describe all six rows and record why (`#0130`).
- `TestAudit_SettingsUpdated` registers `t.Cleanup(func() { resetSettings(t,
  pool) })` right after seeding the setting it mutates, so the full
  migration seed — not just `registrations_enabled` — is restored on
  teardown. This was the narrower of the two options the issue offered
  (versus changing `credsTestPool` itself, which is shared by ~30 other
  tests that never touch `settings`).
- `internal/mailing/worker_test_helpers_test.go:46`'s comment ("GLOBAL rows
  seeded by migration") needed no code change: it was never wrong about what
  migration `000018` seeds, and the fix above means an `internal/handlers`
  run no longer leaves those rows permanently missing, so the comment's
  assumption holds for any package sharing the same test database
  afterward.

## Review notes — 2026-08-22 (phase 3, approved)

Re-verified independently from the diff at `84375fb`, not from the
implementer's `## Verification`. Machine was idle throughout — `uptime`
reported load averages 2.59–2.73 at the start of every run, well under the
~8 threshold at which §5 says timing results stop meaning anything.

**The six seeded rows were checked against the migrations, not against the
issue text.** `INSERT INTO settings` appears in exactly four migrations —
`000004` (`registrations_enabled='false'`), `000008` (`physical_address=''`),
`000015` (`soft_bounce_threshold_count='5'`,
`soft_bounce_threshold_window_days='30'`) and `000018` (`max_send_rate='10'`,
`default_from_name=''`). `resetSettings`' six re-inserts match all six
key/value pairs exactly. `#0131` has `migrations/000018` dirty in the working
copy, but its edits are confined to the `email_sends` status CHECK — the
settings seed block is byte-identical to `HEAD`, so nothing here rests on
another agent's in-flight change.

**Suite runs**, each against its own cloned database per §5a:

- `ISSUE=0130rev scripts/check.sh go ./internal/handlers/...` — `ok 1.993s`,
  build and vet clean, skip audit `(no skips)`.
- `ISSUE=0130rev scripts/check.sh go ./internal/mailing/...` — `ok 0.793s`,
  skip audit `(no skips)`. Run because criterion 3 is a claim about this
  package's assumptions.

**`-shuffle` on two fresh seeds of the reviewer's own choosing**, different
from the implementer's 1111/2222, against a private scratch database
(`scripts/testdb.sh create 0130revshuf`, dropped afterward):

- `go test ./internal/handlers/... -p 2 -shuffle=7331` — `ok 1.816s`
- `go test ./internal/handlers/... -p 2 -shuffle=90210` — `ok 1.797s`

**The direct query `#0121`'s pass claimed and did not run.** After the
`-shuffle=90210` run, `SELECT key, value FROM settings ORDER BY key`
returned:

```
                key                | value
-----------------------------------+-------
 default_from_name                 |
 max_send_rate                     | 10
 physical_address                  |
 registrations_enabled             | false
 soft_bounce_threshold_count       | 5
 soft_bounce_threshold_window_days | 30
(6 rows)
```

Diffed line-by-line against the same query on `opencircuit_test_template`:
identical, no differences.

**Two controls, because a query that passes proves nothing unless it can
fail.** (a) Simulating the pre-fix `resetSettings` by hand — `DELETE FROM
settings` plus only the four original inserts — left the table at 4 rows, so
the check does detect the defect rather than passing vacuously. (b) Running
`-run TestAudit_SettingsUpdated` *alone* from that damaged 4-row state
returned the table to all six rows with `registrations_enabled='false'`, not
the `'true'` the test PATCHes it to. That confirms both the new `t.Cleanup`
fires and that it restores the full seed, independently of the rest of the
package.

**The fix repaired real residual damage, observed live.** The shared
`opencircuit_test` was found at 4 rows — `max_send_rate` and
`default_from_name` missing again, exactly as the struck criterion 2
predicted would happen after `#0122` recreated it. Running the *fixed*
`internal/handlers` suite against it took it from 4 rows to 6. The defect was
real, the repair is self-healing, and the shared database is correct again as
of this review.

**Criterion 3 (`worker_test_helpers_test.go:46`) is met without a code
change, and the implementer's reasoning holds up.** The comment asserts
provenance — that `physical_address`, `default_from_name` and `max_send_rate`
"are all GLOBAL rows seeded by migration" — and that was never factually
wrong; `000008` and `000018` do seed all three. What the defect broke was the
invariant the comment relies on, that the rows are actually *present*.
Grepping every deletion site (`delete from settings`, `truncate … settings`
across `internal`, `cmd`, `migrations`, `scripts`) shows `resetSettings` is
the only bulk delete in the tree; the sole other runtime delete is
`setSetting`'s own cleanup, which removes a key only when it found that key
absent on entry. With `resetSettings` re-seeding all six, that "absent" branch
can no longer be reached for these three keys, so the comment is true again
rather than merely un-contradicted. The cross-package dependency is
additionally documented at its origin, in `resetSettings`' doc comment, which
names `worker_test_helpers_test.go` explicitly — the better location, since
that is where the breakage starts.

All six acceptance criteria verified as ticked; none unticked.
