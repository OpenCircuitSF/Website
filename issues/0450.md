## Description

`#0441` added `TestEnvExampleValuesAvoidDivergentParserShapes`, which flags
`.env.example` values whose shape systemd's `EnvironmentFile=` and `godotenv`
read differently. Its `$VAR`/`${VAR}` detection requires the name to start with
a **letter or underscore**.

`godotenv` v1.5.1's own `expandVarRegex` matches `[A-Z0-9_]+` — **digits
included, and permitted to lead**. So a value like:

    PRICE=cost$5

expands to `cost` under godotenv (the name `5` is undefined, so it becomes the
empty string) and stays `cost$5` under systemd. That is exactly the divergence
the guard exists to catch, and it slips through.

Found by `#0441`'s reviewer while reading the library source to verify the
issue's own table. It explicitly did **not** bounce for it: `$5` is neither
`$VAR` nor `${VAR}` as `#0441`'s criteria describe them, so this is a narrow
miss rather than a fail-open, and the guard is sound for everything it claims.

## Why it is worth closing anyway

The consequence is asymmetric. A value silently *loses* text under one parser
and keeps it under the other — and `.env.example` is copied verbatim onto
production as `/etc/opencircuit/config.env` (`#0423`), so the two readings
happen on the same file in two different contexts. A truncated secret or URL is
not a boot failure; it is a **silently wrong value**, which is the harder half
of this bug class to notice.

### The narrowing is the interesting half, and it is correct

This change **widens and narrows at the same time**. The old class accepted
lowercase; `[A-Z0-9_]+` does not, so `PRICE=cost$abc` was flagged before and is
not flagged now. That is a removal of flagging, and the implementer's report
did not address it — so it was decided here on evidence rather than assumed
benign.

**What `expandVarRegex` matches, read from the module source** (located with
`go list -m -f '{{.Dir}}' github.com/joho/godotenv`, never a filesystem scan —
`CLAUDE.md` §5): in v1.5.1's `parser.go` it is compiled by a plain
`regexp.MustCompile` with **no `(?i)` flag and no case-folding of any kind**,
and its four groups are an optional backslash, the dollar, an optional open
paren, then `\{?([A-Z0-9_]+)?\}?`. The name class is genuinely uppercase-only.

The load-bearing detail is that **the name group is optional**. `expandVariables`
substitutes only when that group is non-empty; when it is empty the function
returns the matched text **unchanged**. So a `$` followed only by characters
outside `[A-Z0-9_]` is left exactly as written, and cannot diverge.

**Runtime probe against the real library** (godotenv's own `Unmarshal`, in a
throwaway `git worktree`, compared against systemd's literal-text reading):

| value | godotenv loads | diverges? | old class flagged | new class flags |
|---|---|---|---|---|
| `cost$5` | `cost` | **yes** | no | **yes** |
| `cost${5}` | `cost` | **yes** | no | **yes** |
| `cost$abc` | `cost$abc` | no | yes | no |
| `cost${abc}` | `cost${abc}` | no | yes | no |
| `cost$Abc` | `costbc` | **yes** | yes | **yes** |
| `cost$ABC` | `cost` | **yes** | yes | **yes** |
| `cost$_x` | `costx` | **yes** | yes | **yes** |
| `cost$` | `cost$` | no | no | no |

**Verdict on the narrowing: no coverage was removed.** The only two lines the
new class stops flagging — an all-lowercase `$abc` and `${abc}` — are precisely
the two the probe shows do **not** diverge, because their name group matches
empty and godotenv hands the text straight back. Every lowercase-containing
value that genuinely does diverge still gets flagged, because divergence
requires at least one `[A-Z0-9_]` character after the dollar and the new class
matches that prefix: `$Abc` is caught on its `$A`. So the change is strictly an
improvement in precision as well as in reach — it drops two false positives and
adds the digit-led true positives. Had the probe shown `$abc` expanding, this
would have been a bounce.

**What `.env.example` would do today:** nothing. Read as bytes with `python3`
(never BSD `grep -P`, §8), the tracked file contains **zero** `$` characters
across its 20 assignment lines, so neither the old nor the new class flags
anything in it and no fix to the file itself was needed. The implementer's
report of this is confirmed.

### The independently-optional braces are fidelity, not over-matching

`\{?` and `\}?` are separately optional, so the class matches the unbalanced
`${VAR` and `$VAR}`. That was checked deliberately rather than left unexamined,
and it is **right**, for a stronger reason than "a malformed value deserves
flagging": godotenv's own regex has the identical independently-optional
structure, so it too matches unbalanced forms and expands them. Probed
directly, `cost${ABC`, `cost$ABC}`, `cost${5` and `cost$5}` all load as `cost`
under godotenv while systemd keeps the literal text — every one a real
divergence, and the guard flags every one. A brace-balanced pattern would
**miss** these. Confirmed too that `cost${Abc}` loads as `costbc}` — the library
really does match `${A` and strand the closing brace, which is the same
asymmetry the guard's class reproduces.

### Criterion 4's finding is correct

Verified from `parser.go` directly. `extractVarValue`'s unquoted branch returns
`expandVariables(trimmed, vars)` unconditionally; its quoted branch calls
`expandVariables(expandEscapes(value), vars)` only inside an
`if quote == prefixDoubleQuote` block, and single-quoted values fall through
returning the trimmed text untouched. So the widening applies identically to
unquoted and double-quoted values, and single-quoted values are exempt by
construction. The probe agrees: `PRICE="cost$5"` loads as `cost`, while
`PRICE='cost$5'` loads as `cost$5`. Nothing needed building, and nothing was.

Noted, not acted on: because the scan matches on text shape and does not model
quoting, a single-quoted `$5` would be flagged even though it cannot diverge.
That is a conservative over-flag consistent with this test's stated policy of
forbidding the shape outright, and `.env.example` has no quoted values today.

### Reported, not filed (§9)

One **pre-existing** gap, present identically before and after this commit and
therefore out of scope for a one-character-class change: `PRICE=cost$(FOO)`
loads as `cost)` under godotenv but stays literal under systemd — a real
divergence that **neither** the old nor the new class flags. The cause is in
the library: `expandVariables` tests `submatch[2] == "("` to detect the paren
form, but group 2 is the dollar capture and the paren is group 3, so that
branch is unreachable and `$(FOO` is treated as a variable named `FOO`.
Catching it would mean admitting `\(?` into the pattern, which is a second
judgement call rather than the single class this issue authorised. Worth an
issue if the orchestrator agrees; not filed here.
