## Description

`#0441` added `TestEnvExampleValuesAvoidDivergentParserShapes`, which flags
`.env.example` values whose shape systemd's `EnvironmentFile=` and `godotenv`
read differently. Its `$VAR`/`${VAR}` detection requires the name to start with
a **letter or underscore**.

`godotenv` v1.5.1's own `expandVarRegex` matches `[A-Z0-9_]+` — **digits
included, and permitted to lead**. So a value like:

    PRICE=cost$5

expands to `cost` under godotenv (the name `5` is undefined, so it becomes the
empty string) and stays `cost$5` under systemd. That is exactly the divergence
the guard exists to catch, and it slips through.

Found by `#0441`'s reviewer while reading the library source to verify the
issue's own table. It explicitly did **not** bounce for it: `$5` is neither
`$VAR` nor `${VAR}` as `#0441`'s criteria describe them, so this is a narrow
miss rather than a fail-open, and the guard is sound for everything it claims.

## Why it is worth closing anyway

The consequence is asymmetric. A value silently *loses* text under one parser
and keeps it under the other — and `.env.example` is copied verbatim onto
production as `/etc/opencircuit/config.env` (`#0423`), so the two readings
happen on the same file in two different contexts. A truncated secret or URL is
not a boot failure; it is a **silently wrong value**, which is the harder half
of this bug class to notice.

## Work log

**2026-09-05, implement.** Read `godotenv` v1.5.1's vendored source directly
(`go list -m -f '{{.Dir}}' github.com/joho/godotenv`, never a filesystem
scan): `parser.go`'s `expandVarRegex` is
`` (\\)?(\$)(\()?\{?([A-Z0-9_]+)?\}? `` — the variable-name group is
`[A-Z0-9_]+`, confirming digits are included and permitted to lead, exactly
as this issue's description states.

**Fix (criterion 1 and 3, one character class):**
`internal/config/env_example_guard_test.go`'s `envDollarExpansion` changed
from `` \$\{?[A-Za-z_][A-Za-z0-9_]*\}? `` to `` \$\{?[A-Z0-9_]+\}? `` — the
two-class first-char/rest-char split collapsed into the single class
`expandVarRegex` actually uses. The floor (`minScannedEnvExampleAssignments`),
`checkScannedFloor`, and the scan's structure in `scanEnvExampleValueShapes`
were not touched. No second mechanism was added.

**Criterion 4 — quoted/escaped forms.** Read `extractVarValue` in the same
file: the unquoted branch calls `expandVariables` unconditionally; the
quoted branch calls it only when `quote == prefixDoubleQuote` —
single-quoted values are never passed through `expandVariables` regardless
of what the variable name looks like. So the
digit-leading widening applies identically to unquoted and double-quoted
values (both share the same `expandVarRegex` path), and single-quoted values
are categorically exempt from this divergence by construction — a
single-quoted `$5` cannot diverge between systemd and godotenv on this axis
no matter how the character class is written. No additional handling is
needed for the quoted forms; nothing built.
