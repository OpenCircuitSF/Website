## Description

`#0292` stopped stamping `confirmed_at` on imported subscribers, which fixed a
real overstatement: an import of 500 addresses read as 500 confirmations on the
growth dashboard, and the admin detail view claimed a local confirmation that
never happened.

**`web/src/lib/dashboard.ts`'s `formatGrowthDetail` still renders `confirmed_30d`
as "N joined, M left".** That wording was accurate when the count meant "became
active". It now means "locally confirmed", so:

- an import of 500 addresses reads as **0 joined**;
- `net_30d` can go **negative** in a month with a large import plus normal churn,
  while the list is in fact growing.

So the number has stopped overstating and started understating, in the opposite
direction from the bug `#0292` fixed. `#0292`'s criterion 3 explicitly permitted
the exclusion and scoped its wording fix to the Go doc comment, so this was
correctly out of its scope — but it is now the one remaining place where the
dashboard says something untrue.

## Acceptance criteria

1. The label stops claiming "joined" for a count that means "locally confirmed".
   Either relabel it accurately, or show an imported-in-30-days figure alongside
   so import-driven growth is visible rather than invisible.
2. `net_30d` does not read as negative in a month where the list grew. If the
   figure keeps its current definition, it must be labelled so that is obvious;
   if it changes definition, say what it now counts and update
   `Growth30Days`'s doc comment to match.
3. **Whatever the dashboard displays and whatever `Growth30Days` documents must
   agree.** The mismatch between them is the whole of this defect and of
   `#0292`'s.
4. If a new count is added, it comes from the existing query rather than a
   second round trip — `#0292`'s reviewer confirmed `Growth30Days` needed no
   query change, so the data is likely already there.
5. A test asserts the rendered figures against seeded data including an import,
   and fails if the label and the underlying count disagree again.
6. `ISSUE=NNNN scripts/check.sh web` passes, and `scripts/check.sh go ./internal/handlers/...`
   if the Go side changes.

## Work log

**Decision: redefine the count rather than only relabel it (criterion 1's
second branch).** Relabeling `confirmed_30d`'s existing meaning alone would
satisfy criterion 1's literal text but leaves criterion 2's scenario
unresolved: a month with a large `prior_consent` import and ordinary churn
would still read `net_30d` as a decline, because nothing about it would
have changed except the words next to it. So `Growth30Days`
(`internal/subscribers/store.go`) now returns a third count, `imported`:
subscribers that landed `active` with `confirmed_at` still NULL in the
window — precisely the shape a `prior_consent` import produces and a
locally-confirmed signup never does (`Confirm`/`RestartSignup` are the only
other writers of `status=active`, and both pair it with `confirmed_at`).
Chose `status = 'active' AND confirmed_at IS NULL` over `source = 'import'`
deliberately: it tracks the same test `#0292` used to define "confirmed" (a
row's own confirmed_at), so an invite-mode import row that later completes
a genuine local confirmation (`#0129`, in flight in parallel) falls into
"confirmed", not here — no double count either way, and no coupling to
`#0129`'s still-changing invite-mode shape.

**Criterion 4 — no second round trip.** Added one more `FILTER` clause to
`Growth30Days`'s existing single `SELECT`, not a new query or a call to a
different store. `#0292`'s reviewer note that "Growth30Days needed no query
change" was true of `#0292`'s own scope (it left the query untouched); this
issue changes it, which the reviewer's note doesn't foreclose — recorded in
the doc comment so a future reader sees both facts together rather than
finding them in conflict.

**Criterion 2 / 3 — net_30d redefined, both sides kept in agreement.**
`net_30d` is now `confirmed_30d + imported_30d - unsubscribed_30d`, computed
server-side in `AdminDashboardHandler.Overview` (unchanged: it was already
computed server-side, not client-side, despite the old doc comment's "the
client can compute the net itself"). `dashboard.ts`'s `formatGrowthDetail`
renders all three: `"N confirmed, M imported, K left"`. Both the Go doc
comment on `dashboardGrowth`/`Growth30Days` and the TS doc comment on
`formatGrowthDetail` state the same formula and cross-reference each other,
so criterion 3's invariant (label and doc must agree) is checked by
inspection, not just by convention.

**Criterion 5 — three tests, at three layers, all against seeded data
including a real import:**

1. `internal/subscribers/imports_test.go`,
   `TestImportStore_Commit_DoesNotInflateGrowth30Days` (extended, not
   replacing #0292's original assertion) — commits a real `prior_consent`
   import and asserts `confirmed` unchanged AND `imported` up by exactly 1,
   from the same before/after pair.
2. `internal/handlers/admin_dashboard_test.go`,
   new `TestAdminDashboardOverview_GrowthCountsImportSeparateFromConfirmed`
   — hits the real `GET /admin/overview` JSON after a real
   `ImportStore.Commit`, and asserts (a) `confirmed_30d` unchanged, (b)
   `imported_30d` up by 1, (c) `net_30d` equals
   `confirmed_30d + imported_30d - unsubscribed_30d` exactly (criterion 3's
   invariant, checked against live JSON), and (d) `net_30d` itself increased
   by 1 — not flat, not negative.
3. `web/src/lib/dashboard.test.ts`, two new `formatGrowthDetail` cases —
   one with `imported_30d: 500` against a small `confirmed_30d`/large
   `unsubscribed_30d` fixture that would read as a steep decline under the
   OLD definition (`confirmed - left = 2 - 10 = -8`) but is real growth
   under the new one (`+492`), asserting the rendered label and the net
   figure agree.
