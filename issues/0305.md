## Description

`#0292` stopped stamping `confirmed_at` on imported subscribers, which fixed a
real overstatement: an import of 500 addresses read as 500 confirmations on the
growth dashboard, and the admin detail view claimed a local confirmation that
never happened.

**`web/src/lib/dashboard.ts`'s `formatGrowthDetail` still renders `confirmed_30d`
as "N joined, M left".** That wording was accurate when the count meant "became
active". It now means "locally confirmed", so:

- an import of 500 addresses reads as **0 joined**;
- `net_30d` can go **negative** in a month with a large import plus normal churn,
  while the list is in fact growing.

So the number has stopped overstating and started understating, in the opposite
direction from the bug `#0292` fixed. `#0292`'s criterion 3 explicitly permitted
the exclusion and scoped its wording fix to the Go doc comment, so this was
correctly out of its scope — but it is now the one remaining place where the
dashboard says something untrue.

## Review notes

> 🟢 Reviewed 2026-08-27 (Opus, phase 3) — approved, with one follow-up to file.

### The `imported_30d` predicate, checked against every status

The new clause is
`count(*) FILTER (WHERE status = 'active' AND confirmed_at IS NULL AND created_at >= $1)`,
over `subscribers WHERE synthetic = false`. The status vocabulary is fixed at the
database by `migrations/000010_create_subscribers.up.sql`'s
`subscribers_status_check` — exactly `pending`, `active`, `unsubscribed`,
`bounced`, `complained` — so the enumeration below is complete:

| Status | `confirmed_at` | Counted? | Correct? |
|---|---|---|---|
| `pending` (website signup awaiting confirmation) | NULL | no — `status` clause excludes it | ✅ a pending row is not growth |
| `pending` (invite-mode import, `#0129`) | NULL | no — same clause | ✅ deliberate; an invitation is not an accepted subscription |
| `active` via `Store.Confirm` | set | no — `confirmed_at IS NULL` excludes it | ✅ that is `confirmed_30d`'s row |
| `active` via `ImportStore.Commit` | NULL | **yes** | ✅ this is the intended population |
| `unsubscribed` | either | no | see the follow-up below |
| `bounced` | either | no | see the follow-up below |
| `complained` | either | no | see the follow-up below |

**Nothing other than an import can produce `active` + `confirmed_at IS NULL`.**
Every writer of `status = active` in the tree was enumerated at `HEAD`:
`internal/subscribers/imports.go:516` and `:624` (the import INSERT, which
deliberately passes a nil `confirmedAt` since `#0292`) and
`internal/subscribers/store.go:733` (`Confirm`, which sets
`status = $2, confirmed_at = $3` in the same UPDATE). Every other status writer
moves *away* from active: `RestartSignup` (store.go:1024) sets `pending` and
explicitly nulls `confirmed_at`; `setStatusTx` writes only `bounced`/`complained`;
`AdminClearComplaint` writes `unsubscribed`, never `active`;
`Unsubscribe` writes `unsubscribed`. The admin manual-add path
(`internal/handlers/admin_subscribers.go`) routes through the ordinary signup
flow and "never creates an `active` subscriber directly" by construction. No
migration or seed inserts subscriber rows. So the predicate is exact, and it does
**not** catch pending signups — the `status = 'active'` clause is what excludes
them, exactly as the implementer's `## Work log` claims.

**The `created_at >= since` clause is load-bearing and correct.** Without it,
every historical import would be counted forever. `ImportStore.Commit` only ever
INSERTs (existing emails are routed to `skipped`/`existing`, never UPDATEd back
to active), so `created_at` is always the import's own timestamp — there is no
path by which an old row is refreshed into the window.

### Does `net_30d` double-count? No.

`confirmed_30d` requires `confirmed_at >= since`; `imported_30d` requires
`confirmed_at IS NULL`. **The two are mutually exclusive at every instant**, so a
row can never appear in both. The transition the issue asks about — an imported
subscriber who *later confirms locally* (`#0129`'s invite mode) — moves cleanly:
`Confirm` stamps `confirmed_at`, which simultaneously drops the row out of
`imported_30d` and (given the stamp is in the window) into `confirmed_30d`. Net
contribution stays exactly +1 across the move; nothing is double-counted and
nothing is dropped.

### The one residual — file this as a follow-up

`confirmed_30d` and `unsubscribed_30d` are **event** counts (a timestamp column
crossing `since`), but `imported_30d` is a **current-state** count (`status` is
active *right now*). An imported row that leaves the active state inside the same
window therefore retracts its own contribution while still being counted as a
departure. Measured, not reasoned — in a throwaway transaction on this review's
own scratch database (`opencircuit_test_0305r`, rolled back):

```
phase               confirmed  imported  unsub  net
before                      2         0      1    1
after import                2         1      1    2
after unsubscribe           2         0      2    0
```

A subscriber who joined *and* left inside the window nets **−1** instead of 0.
The same applies to `ImportStore.Revoke` (`#0125`), which is precisely designed
to unsubscribe an import in bulk — revoking a 500-address import renders as
`net_30d = −500` while the list is exactly where it started. A locally confirmed
subscriber does not have this problem, because `confirmed_at` is not cleared when
they unsubscribe.

**This is not a regression and does not block resolution.** The old code produced
the identical end state (it never counted the +1 in the first place), so the new
formula is greater than or equal to the old in every case and strictly closer to
the truth in the case this issue was filed about. But it is the same *class* of
defect — a figure whose label promises more than the count delivers — so it
should be tracked rather than left in the code silently.

Recommended follow-up, for the orchestrator to file: *"`net_30d` subtracts an
imported subscriber twice when they leave inside the same 30-day window"*, module
`subscribers / admin`, phase 8. The remedy is to make `imported_30d` an event
count like its two siblings — the cleanest form is a `subscriber_events` /
`subscriber_imports` join over the window (`created_at >= since AND source =
'import'`, independent of current status), which also makes the doc comment's
wording ("landed active via an import … since that time") literally true, since
today it describes a flow but measures a stock.
