## Description

`#0204` added a check pinning the premise `#0186`'s before/after block rests on:
no local in `CampaignSendDialog.svelte` is derived directly from `inFlight` or
`unmet.length > 0`, since both now route through `sendGuardState`. Its phase-3
review probed the boundary with ten forms and judged it **defensible** — the
green baseline is itself proof of no false positive on the real
`$derived(sendGuardState({…, inFlight}))`, and widening to "mentions `inFlight`"
would make the test a permanent false positive.

Two narrow gaps came out of that probe. Neither is a live defect; both would let
the premise silently unpin.

**1. Semantic equivalents of the old formula are missed.** These fire:
`$derived(inFlight)`, `$derived(!inFlight)`, `$derived(unmet.length > 0)`. These
do not: `$derived(inFlight === true)`, `$derived(!!inFlight)`,
`$derived(unmet.length !== 0)`, and by extension `unmet.length >= 1`. They mean
the same thing as the shapes that fire, and they can be added without widening
toward the `sendGuardState(…)` call the check must keep ignoring.

**2. `$derived.by(() => inFlight)` slips through entirely.**
`findDirectInFlightOrUnmetLocal` matches only a callee that is the `Identifier`
`$derived`; `.by` is a `MemberExpression` callee. So a refactor from `$derived`
to `$derived.by` — a mechanical, behaviour-preserving change someone might make
for readability — silently unpins the premise with nothing failing.

That is the one worth fixing. It is not an exotic spelling; it is the other
half of the same Svelte 5 rune.

**A third item, recorded rather than actionable.** `#0204` put the note about
the *re-implementation* form of the replica trap in the guard file's header,
which is the right home — but nothing **enforces** that form staying closed. The
working answer remains `#0189`'s: import and call the real function. This is an
unchanged pointer from `#0197`'s report, carried forward so it is not lost.

## Implementation notes

All changes land in
`web/src/views/admin/CampaignSendDialog.structuralGuard.test.ts`; no other
file changed. Commit `f90eb7d`.

**Item 1 — semantic equivalents.** `isDirectInFlightOrUnmetExpr` gained three
targeted checks alongside the existing `inFlight` / `!inFlight` /
`unmet.length > 0` shapes, each operating on `expr` directly (not the
single-`!`-stripped `inner`, since none of these three are reachable that
way):

- `inFlight === true` (either operand order) — new `BinaryExpression '==='`
  check against `isInFlightIdentifier` / `isBooleanLiteral(_, true)`.
- `!!inFlight` — new check for a `UnaryExpression '!'` whose argument is
  itself a `UnaryExpression '!'` whose argument is the `inFlight` identifier.
- `unmet.length !== 0` and, by the same branch, `unmet.length >= 1` — new
  `BinaryExpression '!==' | '>='` check against the existing
  `isUnmetLengthMember` helper (extracted from the old inline `unmet.length`
  test so both branches share it) and a literal `0` or `1` respectively.

Extracted `isInFlightIdentifier`, `isUnmetLengthMember`, `isBooleanLiteral`,
`isNumberLiteral` as small named predicates so the new branches read as
"is this that specific shape" rather than repeating inline AST digging.

**Item 2 — `$derived.by`.** `findDirectInFlightOrUnmetLocal` previously
required `init.callee` to be the `Identifier` `$derived`. Added
`isDerivedCallee` (that same check, named) and `isDerivedByCallee` (true for
a `MemberExpression` callee whose object is `Identifier '$derived'` and
property is `Identifier 'by'`). For a `$derived.by(fn)` match, a new
`derivedByBodyExpr` resolves the callback's value expression — the concise
body of an arrow function, or a block body's `return` argument — before
handing it to the same `isDirectInFlightOrUnmetExpr`. A callback that isn't
an arrow/function expression, or has no `return`, is simply not matched
(returns `undefined`) rather than throwing, so this stays additive.

The failing-test message for an offending declarator was also updated: it
previously assumed the `$derived(expr)` shape when formatting
(`init.arguments[0]`'s source text, wrapped in a hardcoded `` `$derived(...)` ``
template), which would have mislabeled a `$derived.by(...)` offender's call
as `$derived(...)`. It now quotes `init`'s own source span verbatim (correct
for either callee shape) and calls out "`via `$derived.by`" when relevant.

**Left alone, per the issue.** Item 3 (the re-implementation-trap note in the
file's header) needed no code and none was added.

### Extended, not relaxed — read before measured

The risk in this change was over-widening. Reading
`isDirectInFlightOrUnmetExpr` at `f90eb7d`: the three added branches are each a
**conjunction of exact AST shape tests** (`BinaryExpression '==='` against
`isInFlightIdentifier`/`isBooleanLiteral`; a doubled `UnaryExpression '!'`;
`BinaryExpression '!==' | '>='` against `isUnmetLengthMember` and a literal `0`
or `1`). No existing branch was loosened, and nothing added matches a
`CallExpression` — which is what `sendGuardState({…})` is, and therefore why the
positive control cannot fire structurally rather than merely incidentally. The
extracted predicates (`isInFlightIdentifier`, `isUnmetLengthMember`,
`isBooleanLiteral`, `isNumberLiteral`) are the old inline tests named, not
broadened; `isBooleanLiteral`/`isNumberLiteral` both use `===`, so a literal `1`
cannot satisfy the `true` test or vice versa. **Shapes were added; the predicate
was not relaxed.** The measurements below confirm the reading.
