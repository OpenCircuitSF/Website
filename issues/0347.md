## Description

`#0342` has now bounced **twice** on the same criterion — its sweep for stale
comments — and both bounces found the same *class* of defect: a comment
asserting, in the present tense, that some code calls `ClaimDue` when the file
containing it has zero `ClaimDue` call sites. `#0297` removed those calls; the
comments describing them did not go with them.

The tally so far is nine stale sites across two implementation passes and three
reviews, each pass finding what the last missed. The second review diagnosed
why: **every pass used the same instrument** — the criterion's keyword grep,
then a human read of each paragraph. The failure is in triage, not in the grep,
so repeating the grep repeats the miss.

That review's replacement instrument is the thing worth keeping. It parses each
Go file **twice** — once with `parser.ParseComments` for the comments, once
with mode `0` so comments never enter the AST — and then asks whether each
identifier a comment names actually appears in that file's *code*. Over 269
files, 4963 comment groups and 456 identifier hits, it found the three
remaining sites by construction rather than by judgement, and it reproduced the
site the first review had found by hand when pointed at the older snapshot.

`#0267`'s misattached-doc-comment guard family does not reach this class: these
are inline and doc comments that are attached to the right declaration and are
simply false about what that declaration does.

## Acceptance criteria

1. A Go guard test fails when a comment names `ClaimDue`, `SelectDue`,
   `OrphanSweep`, `ClaimRow`, or `ClaimBatch` in the present tense while the
   file's own code contains zero calls to it.
2. The census of what the code contains is taken from a mode-`0` parse, so
   comment text can never contribute to the population a comment is checked
   against. A comment must not be able to satisfy the check that measures it
   (§8 — a copy of the answer stored next to the question is not a check).
3. History paragraphs are allowed, via an explicit allowlist or an explicit
   past-tense/marker convention. `#0342`'s sweep confirmed that correctly
   framed historical references are common and legitimate — the guard must not
   force their removal. State the convention it recognises.
4. The guard is proved falsifiable: pointed at the `ffef8cf` snapshot (or an
   equivalent reconstruction) it flags `outbox_worker_test.go:746`'s
   `OutboxWorker.ClaimDue`, and against the fixed tree it does not.
5. It fails closed on empty input and on a zero-hit census — §8 records a
   fail-open that arose in exactly that way, where an extraction contributing
   nothing was read as agreement.
6. **The guard belongs in Go, not in an external shell harness.** Per §8's
   rule, the deciding question is whether the mutation leaves the assertion
   falsifiable by the thing it measures: adding a false comment changes what
   the scan finds, so the in-package test is a legitimate, non-circular oracle.
   Record that reasoning in the guard's doc comment.
7. No `.ClaimDue(` / `.OrphanSweep(` / `.SelectDue(` call-syntax literal is
   introduced into any Go comment — `scripts/go_file_visit_floor_guard_test.sh`
   greps for that syntax and comment text containing it inflates the population
   it measures. Re-run that harness and record the population (currently 42).

## Added by `#0342`'s third review, 2026-08-31

That review resolved `#0342` and, in discharging its sweep criterion three
different ways, measured two corrections this issue needs **before** anyone
implements it.

**1. Criterion 1 as written would fire on nine correct comments in one file.**
`internal/handlers/subscribe_intake_test.go` contains **nine** comment mentions
of `ClaimDue` and **zero** code calls to it. The reviewer read all nine: every
one is correct. They name `outbox.Store.ClaimDue` as an existing API — it is,
at `internal/outbox/store.go:351`, still filtering by kind — or they narrate a
deliberate worktree mutation (`:303`, `:320`, `:331`), or they state what the
test deliberately does **not** use (`:223`).

So the distinction the guard must encode is **"names a call this file's code
makes"** versus **"names a method that exists"** — *not* present tense versus
past tense. Criteria 1 and 3 above are written in terms of tense and must be
rewritten in those terms instead. Add this file as a **named negative fixture**:
a correct implementation produces zero findings in it.

**2. Add a directional axis.** Two of the three sites `#0342`'s third pass
fixed were *direction* errors — a comment saying "the same set X below is
scoped to" where nothing named X is below — and a pure existence census cannot
see one, because the identifier does exist. The axis checks a comment's
"above"/"below" claims against the named identifier's own positions in the same
file.

It is cheap and it closes a real subclass, but it needs the **high-precision
window variant**: the naive form produced 480 wide flags where the precise one
produced 16. Ungated, it is far too noisy to fail a build.

### What no instrument in this family can catch

Worth recording so a later pass does not believe the guard closes the whole
class. Three sweeps now, each with a different blind spot, and the reviewer's
own falsifiability work shows the limit is structural: these instruments find
**structural** errors — a direction the code does not satisfy, a package member
that does not exist, a wrong arity or variadic form, a missing file.

**A comment that is false about *behaviour*, while every identifier it names
exists in the right file, direction and arity, is invisible to all of them.**
That is exactly `#0342`'s original site 1 — *"a `Stop` landing anywhere in
`sendOne` still sees it as outstanding"* — which named only real things and was
simply wrong about what happens. Only a human read found it, and only a human
read will find the next one. Do not let this guard's greenness be read as
"there are no stale comments."

## Root cause

No mechanism existed to check a Go comment's claim about the claim-machinery
identifiers against the file's own code, or about a comment's "above"/"below"
position claim against the file's own layout — every prior sweep (three of
them, across `#0342`'s two implementation passes and three reviews) was a
keyword grep plus a human read, so each pass found only what the last
missed.

## Fix

Added `internal/outbox/claim_comment_referent_guard_test.go` with two guard
tests sharing one mode-0/`ParseComments` walk over `claimCommentGuardScanRoots`
(`internal/` + `cmd/`, matching this package's sibling
`claim_kinds_call_site_guard_test.go`):

- **`TestNoCommentClaimsClaimMachineryCallFileCodeLacks`** — the existence
  axis (criterion 1, corrected) plus the directional axis (the amendment's
  addition). A comment is flagged for the existence axis only when it
  writes `Type.Ident` where `Type` is declared in the FILE's OWN PACKAGE
  (not an external package's type) and the word "call"/"calls" appears
  immediately after `Ident`, and the file's own mode-0 code census for
  `Ident` is zero. This is deliberately narrower than "any bare mention
  followed by 'call'" — an early draft used that broader rule and produced
  double-digit false positives in this package's own sibling guard file and
  in `store.go`, both of which correctly and routinely write bare "X call"
  prose describing calls that happen in OTHER files they scan or declare.
  That imprecision, once fixed, is why criterion 1's own bullet list in this
  guard's doc comment now says bare mentions are never flagged regardless of
  nearby wording — see that doc comment's "What 'names a call this file's
  code makes' means here" section for the full reasoning and the concrete
  false positives that drove it.

  The directional axis anchors on each "above"/"below" occurrence and takes
  only the NEAREST target identifier before it (not every identifier in a
  fixed-width window) — an earlier draft took every identifier in a 90-char
  window and flagged a real, correct doc comment in `store.go` whose
  sentence names one method as its subject and, in a trailing parenthetical,
  points a directional word at a second, different, nearer method.

  Both axes exempt a sentence/clause carrying an explicit historical,
  hypothetical, or negating marker (criterion 3's convention — see the
  guard's own doc comment for the exact word list), scoped to the CLAUSE
  containing the identifier, not the whole comment group/paragraph. An
  early draft scoped it to the whole group and, proved by this guard's own
  falsifiability fixture, exempted the real `ffef8cf` defect because an
  unrelated "rather than" later in the same paragraph matched — the same
  class of over-broad exemption criterion 1's amendment warns about, one
  level down. Clause boundaries include the em dash ("—"), which this
  codebase writes far more than periods; an earlier draft used only
  `.;:!?` and the same falsifiability fixture caught it.

- **`TestNoClaimMachineryCallSyntaxLiteralInAnyComment`** — criterion 7,
  enforced in Go via `go/scanner` (lexer-level, so a string or raw literal
  containing the banned substrings can never be mistaken for a comment).
  Complements, not duplicates, `scripts/go_file_visit_floor_guard_test.sh`'s
  existing external, text-based oracle (CLAUDE.md §8: the two homes are not
  redundant — that harness is what a mutation to THIS file's own detection
  logic can't disarm, and this test is what runs on every ordinary
  `go test` without needing the shell harness invoked separately).

Two standing regression tests pin the required proofs permanently rather
than leaving them as one-off manual runs:

- `TestClaimCommentGuardFlagsKnownStaleSiteFromFfef8cf` — criterion 4's
  falsifiability proof, against an in-memory reconstruction of `ffef8cf`'s
  and `HEAD`'s real `internal/mailing/outbox_worker_test.go` comment text,
  fetched byte-for-byte via `git show` (including the real U+2014 em dash,
  not a retyped ASCII substitute — CLAUDE.md §8's backslash-escape gotcha
  generalizes to "don't retype punctuation a human wrote, either").
- `TestClaimCommentGuardIsCleanOnKnownNegativeFixture` — parses the REAL,
  on-disk `internal/handlers/subscribe_intake_test.go` and asserts zero
  existence-axis findings, per the amendment's named negative fixture.

Fail-closed floors (criterion 5) cover an empty scan-roots list, a low
file-visit count, a zero call census, and a zero comment-group count, all
enforced live inside `TestNoCommentClaimsClaimMachineryCallFileCodeLacks`
and separately proved in isolation
(`TestGoFileVisitFloorImplausibleGuardFiresOnEmptyOrLowCount`, the pure
function; `TestClaimCommentGuardCensusFloorCatchesRootsWithNoRealPopulation`,
the real pipeline end-to-end against `internal/audit`, a real package
confirmed by direct grep to hold zero claim-machinery mentions).

The guard's doc comment records where the oracle lives and why (criterion
6, matching §8's rule) and states explicitly what this guard family cannot
reach — a comment false about *behaviour* while every identifier it names
is structurally correct, per `#0342`'s third review's own finding — so a
green run is not misread as "the comments are accurate".

Not implemented: no `## Obstacles`/`## Plan` section exists on this issue
(phase 1 was skipped, consistent with `CLAUDE.md` §3's "mechanical, ports of
already-validated work" criterion not applying here — this one did need real
design decisions, discovered live rather than planned; recorded honestly in
`## Gotchas` below rather than glossed over).

## Gotchas

- **Getting to zero false positives on the real tree took four iterations
  measured against real code, not reasoned in the abstract.** A first
  design (bare identifier + "call"/"calls" adjacency, whole-comment-group
  historical exemption, every identifier in a fixed window for the
  directional axis) produced 17 findings on `HEAD` and failed its own
  falsifiability fixture in the opposite direction (it silently exempted
  the required positive). Each fix was driven by running the guard against
  the real tree and reading what it actually flagged, not by re-deriving
  the rule on paper — consistent with `CLAUDE.md` §8's repeated lesson this
  session (`#0342`'s own tools) that an instrument's first draft reliably
  has a bug its author cannot see by inspection alone.
- **This file is itself scanned by the citation-guard family in
  `internal/handlers`.** Two of my own draft doc comments tripped
  `TestNoCommentCitesUndefinedTestFunction` (a doc comment named a test
  function I had planned to write but never did) and
  `TestNoCommentCitesUnresolvedPathOrSection` (two doc comments cited
  `r3-0342/audit0342r3.go` and `r3-0342/commentscan0342r3.go` by path —
  real scratchpad files, but not part of this repo tree). Both were caught
  by `ISSUE=0347 scripts/check.sh go ...`, not by this file's own tests,
  which is exactly the "two homes, not exclusive" point CLAUDE.md §8 makes
  about guard families protecting each other.
- **Package #0356's plan asked whether this guard's walker is reusable.**
  Partially. `walkClaimKindsGuardFiles` (this package's existing walk
  helper, from `claim_kinds_call_site_guard_test.go`) is reused as-is, not
  duplicated. The census-building helpers
  (`claimCommentGuardBuildFileFacts`, `claimCommentGuardBuildPackageTypeIndex`)
  are new and specific to this guard's need for a per-file code census and a
  cross-file package-type index — #0356's own guard needs neither (its plan
  says so explicitly: "no code census at all"), so there is nothing further
  for it to share beyond the walk, which was already shared. If #0356 lands
  in this same package it can call `walkClaimKindsGuardFiles` directly; if
  it lands in `internal/handlers` (where the other citation guards already
  live), it will use that package's own `walkGoFiles`/`goFileVisitCountImplausible`
  pair instead, and the two guard families stay independent by design (per
  #0356's own plan §8, since their exemption models are incompatible).

   negation words are load-bearing there — several of the nine negative-fixture
   mentions rely on them):

   `claimCommentGuardHistoricalRe`.

2. In the directional axis, check **every distinct target identifier in the
   window**, not only `matches[len(matches)-1]`. Loop over `matches` with a
   `seen map[string]bool`, keeping the existing resolve-and-report body per
   identifier.

3. Change (2) alone reintroduces one real false positive —
   `internal/outbox/store.go:463`, `"ClaimRow is the second half of #0297's
   per-row claim path (see SelectDue above)"`, where the direction word sits in
   a parenthetical about `SelectDue` but the sentence subject `ClaimRow` gets
   pulled in. Fix it by scoping the window to the innermost still-open
   parenthesis when the direction word is inside one:

   ```go
   // claimCommentGuardOpenParen returns the byte offset just after the
   // innermost still-open "(" in s, or -1 if none is open.
   func claimCommentGuardOpenParen(s string) int {
   	depth := 0
   	for i := len(s) - 1; i >= 0; i-- {
   		switch s[i] {
   		case ')':
   			depth++
   		case '(':
   			if depth == 0 {
   				return i + 1
   			}
   			depth--
   		}
   	}
   	return -1
   }
   ```

   and in the window computation, after the existing `claimCommentGuardLastBoundary`
   clamp:

   ```go
   if pOpen := claimCommentGuardOpenParen(flat[:dm[0]]); pOpen > lo {
   	lo = pOpen
   }
   ```

4. Add a standing directional falsifiability regression test mirroring
   `TestClaimCommentGuardFlagsKnownStaleSiteFromFfef8cf`, built from
   `git show db9bff7:internal/mailing/outbox_worker.go` (sites A and C) — the
