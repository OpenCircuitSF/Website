## Description

Production is served by a **different EC2 instance** than every document in
this repo describes, and the old one is powered down as far as this service is
concerned. The `ssh ec2` alias — which every prepared instruction, runbook and
deploy procedure routes through — still points at the old host.

**A deploy run through the documented tooling today would target the dead box,
appear to succeed, and leave production untouched.**

Measured 2026-09-12, both hosts reached directly:

| | Old — what the docs say | **New — what actually serves production** |
|---|---|---|
| SSH alias | `ssh ec2` | **`ssh photon`** (already present in `~/.ssh/config`) |
| Hostname | `bluesky.sstools.co` | **`photon.sstools.co`** |
| Public IP | `44.222.209.183` | **`98.84.75.184`** |
| Instance | `i-0e3bd89e87d1c2364` | **`i-01c45429c78f3adf7`** |
| Type | `t4g.nano`, 418 MB | **`t4g.small`, 1846 MB, 2 vCPU, 30 GB disk** |
| IAM role | `opencircuit-instance` | **`opencircuit-web-2026`** |
| `opencircuit.service` | **dead** since 2026-09-11 00:35:44 UTC (`Result=success`) | **active** |
| HTTPS response | **503** | **200** |

Unchanged and re-measured on the new host: `us-east-1`, Amazon Linux
2023.12.20260909, Apache 2.4.68, OpenSSL 3.5.7, PostgreSQL 15.19,
`/opt/opencircuit` at `ef0a58f`, schema version `22|f`.

## How it was found

While answering whether a production deploy was ready. `systemctl is-active
opencircuit.service` on the `ssh ec2` host reported `inactive` while the public
site returned 200 — a contradiction that only resolves once you notice the two
addresses are different machines.

## Why `#0504` did not catch it

`#0504` measured the IP change and concluded **"It is the same service"**,
reasoning from `/.well-known/atproto-did` still hashing correctly and Apache
and OpenSSL versions still matching. Those checks all pass — because the new
box is a faithful rebuild of the old one. They cannot distinguish *the same
host* from *a replacement host serving the same content*, which is exactly the
distinction that matters here. `#0504`'s framing as "a stale fact rather than
an outage" is right about impact and wrong about cause, and its conclusion
needs correcting rather than merely extending.
