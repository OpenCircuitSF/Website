## Description

Production is served by a **different EC2 instance** than every document in
this repo describes, and the old one is powered down as far as this service is
concerned. The `ssh ec2` alias — which every prepared instruction, runbook and
deploy procedure routes through — still points at the old host.

**A deploy run through the documented tooling today would target the dead box,
appear to succeed, and leave production untouched.**

Measured 2026-09-12, both hosts reached directly:

| | Old — what the docs say | **New — what actually serves production** |
|---|---|---|
| SSH alias | `ssh ec2` | **`ssh photon`** (already present in `~/.ssh/config`) |
| Hostname | `bluesky.sstools.co` | **`photon.sstools.co`** |
| Public IP | `44.222.209.183` | **`98.84.75.184`** |
| Instance | `i-0e3bd89e87d1c2364` | **`i-01c45429c78f3adf7`** |
| Type | `t4g.nano`, 418 MB | **`t4g.small`, 1846 MB, 2 vCPU, 30 GB disk** |
| IAM role | `opencircuit-instance` | **`opencircuit-web-2026`** |
| `opencircuit.service` | **dead** since 2026-09-11 00:35:44 UTC (`Result=success`) | **active** |
| HTTPS response | **503** | **200** |

Unchanged and re-measured on the new host: `us-east-1`, Amazon Linux
2023.12.20260909, Apache 2.4.68, OpenSSL 3.5.7, PostgreSQL 15.19,
`/opt/opencircuit` at `ef0a58f`, schema version `22|f`.

## How it was found

While answering whether a production deploy was ready. `systemctl is-active
opencircuit.service` on the `ssh ec2` host reported `inactive` while the public
site returned 200 — a contradiction that only resolves once you notice the two
addresses are different machines.

## Why `#0504` did not catch it

`#0504` measured the IP change and concluded **"It is the same service"**,
reasoning from `/.well-known/atproto-did` still hashing correctly and Apache
and OpenSSL versions still matching. Those checks all pass — because the new
box is a faithful rebuild of the old one. They cannot distinguish *the same
host* from *a replacement host serving the same content*, which is exactly the
distinction that matters here. `#0504`'s framing as "a stale fact rather than
an outage" is right about impact and wrong about cause, and its conclusion
needs correcting rather than merely extending.

## Scope — and the boundary that matters

**In scope: live operational text**, i.e. anything an agent or operator would
act on today.

- `HANDOFF.md`'s instance/SSH entry.

  `docs/email-setup.md` (3), `docs/aws-requests.md` (2),
  `deploy/systemd/README.md` (2).
- `issues/0504.md` — **open**, and its central conclusion is wrong.
- `issues/0057.md` — **in-progress**, and its runbook is meant to be executed.
- The `opencircuit-instance` → `opencircuit-web-2026` role rename, 47 hits
  repo-wide. This one is not cosmetic: `#0057`'s `A11` grants S3 access to the
  instance role, and as written it would grant it to a role the live box does
  not use.

**Out of scope: dated historical records.** Resolved issue files record
measurements taken at a time and are not to be retroactively rewritten. This
is the same judgement `#0466`'s review reached about the stale "711 commits"
figure: dated measurements in historical context, on which no command depends,
are correct as they stand. Rewriting them would falsify the record and produce
an enormous diff that buries the operational change.

The test for each hit: **would someone act on this text today?** If yes, fix
it. If it is a record of what was measured on a past date, leave it.

## Acceptance criteria

1. Every in-scope file names `photon` / `photon.sstools.co` and the new
   instance, type, IP and IAM role, with values matching the table above.
2. `ssh ec2` no longer appears in any in-scope file. Verify `ssh photon`
   works before relying on it — it is already configured.
3. `#0504` is corrected: its "same service" conclusion is wrong, and it should
   either be closed as superseded by this issue or amended to state the two
   hosts are distinct. Say which and why.
4. The `opencircuit-instance` → `opencircuit-web-2026` change is applied
   everywhere it describes current state, and `#0057`'s `A11` in particular is
   corrected, since applying it as written grants to the wrong principal.
5. **No resolved issue file is modified.** State how many hits were left alone
   and why, so a clean result means the boundary was applied rather than missed.
6. `CLAUDE.md` §7's `t4g.nano` / 418 MB note is corrected. The old figure drove
   real guidance — "`go build` is the memory-hungry step of a deploy" — and the
   new box has 4.4× the RAM, so that guidance changes.
7. A note records that **the new box has no Go toolchain**, so the documented
   build-on-box step cannot run there as written. Do not design the replacement
   here; just make sure the next person is not surprised by it. See `#0509`.
