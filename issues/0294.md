## Description

`#0284` found the mail worker's orphan window derived from one message's bound
while `claimed_at` is stamped once per batch. **`internal/handlers/subscribe_intake.go`
has the same defect with worse arithmetic.**

`intakeBatchSize = 20`, `intakeRowTimeout = 10s`, `intakeOrphanStaleAfter = 20s`,
and the same batch-stamping `ClaimDue`. So the last row of a batch can hold a
claim for `19 × 10s + 10s = 200s` against a **20s** window — a 10x shortfall,
where the mail worker's equivalent gap was about 1s.

**The missing rate limiter cuts the wrong way.** `#0284`'s implementer argued
the intake path is less exposed because it has no rate limiter, so there is no
guaranteed per-row delay. `#0284`'s reviewer established the opposite: a rate
limiter bounds the *typical* case, not the worst case. With no limiter the
window is breached once the batch's total processing exceeds 10s — **two** hung
rows, not twenty. Two hung rows during a slow-database episode is one incident,
and a slow database is exactly what has the recovery poller busy in the first
place.

The failure mode is `#0254`'s: a sweep releasing a live claim, so the row is
reprocessed while its first processing is still running.

## Acceptance criteria

1. The window is derived from the **batch**, charging each predecessor the
   per-row *bound* (`intakeRowTimeout`), not a pacing interval. There is no rate
   limiter here, so the derivation is `intakeBatchSize × intakeRowTimeout` plus
   the last row's own bound — roughly 200s.
2. The derivation is expressed **in code from the constants it depends on**, so
   changing `intakeBatchSize` or `intakeRowTimeout` moves the window
   automatically.
3. A test asserts **the invariant, not the number**: the window must exceed the
   worst-case age of the last row in a full batch, and must fail if someone
   raises the batch size without touching the window. Note `#0284`'s reviewer
   found a test of this shape that survived full reversion of the fix *and*
   false-failed on a legitimate config change — read its review notes before
   writing yours.
4. **Do not assert a bound the code does not have.** `#0284` bounced precisely
   because its doc comment claimed "a strict, structural upper bound … by
   construction" when no such bound existed. Say exactly what is bounded and by
   what.
5. Consider the alternative the reviewer named: **re-stamping `claimed_at` per
   row**, which would make a per-row window honest and small. That touches
   `internal/outbox` and is tracked separately — if it is the better answer,
   say so and stop rather than building the large-window version.
6. Not a load exercise. Every quantity must be one of the code's own constants.
   CLAUDE.md §5 forbids sizing a constant against machine load.
7. `ISSUE=NNNN scripts/check.sh go ./internal/handlers/... ./internal/outbox/...`
   passes with no skips.
