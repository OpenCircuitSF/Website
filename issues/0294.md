## Description

`#0284` found the mail worker's orphan window derived from one message's bound
while `claimed_at` is stamped once per batch. **`internal/handlers/subscribe_intake.go`
has the same defect with worse arithmetic.**

`intakeBatchSize = 20`, `intakeRowTimeout = 10s`, `intakeOrphanStaleAfter = 20s`,
and the same batch-stamping `ClaimDue`. So the last row of a batch can hold a
claim for `19 × 10s + 10s = 200s` against a **20s** window — a 10x shortfall,
where the mail worker's equivalent gap was about 1s.

**The missing rate limiter cuts the wrong way.** `#0284`'s implementer argued
the intake path is less exposed because it has no rate limiter, so there is no
guaranteed per-row delay. `#0284`'s reviewer established the opposite: a rate
limiter bounds the *typical* case, not the worst case. With no limiter the
window is breached once the batch's total processing exceeds 10s — **two** hung
rows, not twenty. Two hung rows during a slow-database episode is one incident,
and a slow database is exactly what has the recovery poller busy in the first
place.

The failure mode is `#0254`'s: a sweep releasing a live claim, so the row is
reprocessed while its first processing is still running.

## Acceptance criteria

1. The window is derived from the **batch**, charging each predecessor the
   per-row *bound* (`intakeRowTimeout`), not a pacing interval. There is no rate
   limiter here, so the derivation is `intakeBatchSize × intakeRowTimeout` plus
   the last row's own bound — roughly 200s.
2. The derivation is expressed **in code from the constants it depends on**, so
   changing `intakeBatchSize` or `intakeRowTimeout` moves the window
   automatically.
3. A test asserts **the invariant, not the number**: the window must exceed the
   worst-case age of the last row in a full batch, and must fail if someone
   raises the batch size without touching the window. Note `#0284`'s reviewer
   found a test of this shape that survived full reversion of the fix *and*
   false-failed on a legitimate config change — read its review notes before
   writing yours.
4. **Do not assert a bound the code does not have.** `#0284` bounced precisely
   because its doc comment claimed "a strict, structural upper bound … by
   construction" when no such bound existed. Say exactly what is bounded and by
   what.
5. Consider the alternative the reviewer named: **re-stamping `claimed_at` per
   row**, which would make a per-row window honest and small. That touches
   `internal/outbox` and is tracked separately — if it is the better answer,
   say so and stop rather than building the large-window version.
6. Not a load exercise. Every quantity must be one of the code's own constants.
   CLAUDE.md §5 forbids sizing a constant against machine load.
7. `ISSUE=NNNN scripts/check.sh go ./internal/handlers/... ./internal/outbox/...`
   passes with no skips.

## Work log

**2026-08-27, phase-2 implementation.**

**Verified the claim model before deriving anything, per this issue's own
instruction (it warned #0295 got the sibling wrong).** `subscribe_intake.go`'s
`intakePass` calls `h.intake.ClaimDue(claimCtx, intakeBatchSize,
outbox.KindSubscribeIntake)` — `outbox.Store.ClaimDue`
(`internal/outbox/store.go`), the SAME single `UPDATE ... SET claimed_at =
now() ... WHERE id IN (SELECT ... LIMIT $1)` mechanism `#0284` found in
`internal/mailing/outbox_worker.go`'s `pass`: one `claimed_at` stamped for the
WHOLE returned batch. This is NOT `internal/mailing/worker.go`'s
`SendStore.ClaimRow` (`#0295`'s reference implementation, which claims
per-recipient at the moment each send begins). So this file is `#0284`'s
family, confirmed by reading the call site, not assumed from the issue title.

**Derivation (criteria 1, 2, 4, 6).** Unlike `#0284`, there is no rate limiter
anywhere in `intakePass`'s loop — `processIntakeRow` calls run back-to-back.
Each row's entire reprocessing (fresh `IsSuppressed`/`FindByEmail` reads,
`dispatchMutation`, `MarkSent`) runs inside one
`context.WithTimeout(h.sendCtx, intakeRowTimeout)`, so `intakeRowTimeout` is
both a row's failure ceiling and, under normal operation, an upper bound on
how long it can occupy the loop before the next row starts. Charging every row
in a full batch that bound gives `intakeBatchSize * intakeRowTimeout` = 200s —
but tracing `intakePass` further found ONE more term: `ClaimDue`'s own call
(`claimCtx`, also bounded by `intakeRowTimeout`) stamps the batch's shared
`claimed_at` near the START of its single `UPDATE ... RETURNING` statement
(Postgres' `now()` is transaction-start time, and an unwrapped `pool.Query`
call is its own implicit transaction), then must still scan the `RETURNING`
rows and return control to `intakePass` before row 1's own clock even starts —
real elapsed time, charged to no row, that happens between the stamp and the
first row's processing. Unlike `#0284`'s equivalent gap (`outbox_worker.go`'s
`pass` calls `ClaimDue` on `context.Background()` via
`go outboxWorker.Run(context.Background())` — literally unbounded, per that
var's own doc comment), THIS gap is itself bounded by the very same
`claimCtx`/`intakeRowTimeout`, because if it exceeded that budget the call
would fail and return no rows at all. Given `#0284`'s two bounces were both for
shipping a formula that fell short of a knowable, closeable term, this one is
closed rather than left as an unclosed residual:

```go
var intakeOrphanStaleAfter = time.Duration(intakeBatchSize+1) * intakeRowTimeout
```

= 21 × 10s = **210s** (`intakeBatchSize` terms for the batch's own row
processing, plus one more `intakeRowTimeout` for the `ClaimDue` call's own
claim-to-return gap). Named the terminal residual this does NOT close, in the
doc comment: every bound here assumes `context.WithTimeout` cancellation
actually interrupts a stuck DB/network call within its own deadline — a TCP
read the OS cannot be made to abandon on cancellation is a residual no
Go-level constant formula closes, the same CLASS of caveat `#0284`'s final
comment names for `outboxOrphanStaleAfter` (there a stronger, unconditional
version of the same assumption, since that path runs on an entirely
undeadlined context). Every quantity in the formula is one of the code's own
constants (`intakeBatchSize`, `intakeRowTimeout` = `mutateJobTimeout`); no
machine load entered the derivation (criterion 6). Moved
`intakeOrphanStaleAfter` from the `const (...)` block to its own `var`,
matching `outboxOrphanStaleAfter`'s pattern ("a var, not a const, so a test
can shrink it").

**Criterion 5 — the per-row re-stamp alternative: considered, not built,
documented as such.** Read `#0295`'s finding first, as instructed:
`internal/mailing/worker.go`'s `SendStore.ClaimRow` already IS this design (a
working reference in this codebase), stamping `claimed_at` per recipient at
the moment that recipient's own send begins, which is why that window carries
real margin instead of the near-zero the naive single-row math suggested.
Re-stamping `claimed_at` per row in `internal/outbox`'s SHARED `ClaimDue` path
would make `intakeOrphanStaleAfter` honest and small too — but that is a
change to code contended by another agent this session and tracked separately
as `#0297` (already filed, confirmed present in `issues/0297.md`, table row

### The claim model, re-verified from source rather than from the work log

This is the premise everything rests on, and `#0295` was filed on a false one,
so it was traced again rather than taken on trust:

- `internal/handlers/subscribe_intake.go:270` — `h.intake.ClaimDue(claimCtx,
  intakeBatchSize, outbox.KindSubscribeIntake)`.
- `h.intake` is a concrete `*outbox.Store` (`subscribe.go:337`), not an
  interface, so there is no other implementation to reach.
- `internal/outbox/store.go:296` — one `UPDATE outbound_queue SET status = $2,
  attempts = attempts + 1, claimed_at = now() WHERE id IN (SELECT … LIMIT $1
  FOR UPDATE SKIP LOCKED) RETURNING …`. **One `claimed_at` for the whole
  batch.** `#0284`'s family, confirmed.
- Not `internal/mailing.SendStore.ClaimRow` (`worker_store.go:426`), which is
  `WHERE id = $1` — per-row, which is exactly why `#0295` had no defect.

### The `+1` term — the part this review was asked to scrutinise

**Verdict: sound, and conservative in the safe direction.** Three things were
checked rather than assumed.

1. **Is the gap real?** Yes. `now()` in Postgres is transaction start time and
   an unwrapped `pool.Query` is its own implicit transaction, so `claimed_at`
   is stamped at the start of the statement while `ClaimDue` does not return
   until `rows.Next()` has scanned the whole `RETURNING` set. That elapsed time
   precedes row 1's own clock and is charged to no row in the `batchSize` term.

2. **Is it genuinely bounded here, unlike `#0284`'s?** Yes, and the contrast
   the comment draws is accurate on both sides. `intakePass` builds
   `claimCtx, claimCancel := context.WithTimeout(h.sendCtx, intakeRowTimeout)`
   and passes it to `ClaimDue`; pgx carries that context through both the
   `Query` and the row scan, so the whole call — stamp included — cannot exceed
   `intakeRowTimeout` without erroring out and returning no batch at all.
   `#0284`'s equivalent really is unbounded: verified
   `cmd/opencircuit/main.go:1386` is literally `go
   outboxWorker.Run(context.Background())`.

3. **Is one `intakeRowTimeout` the right size, or a convenient number?** It is
   the actual deadline on that call, so it is derived, not chosen — and it is
   an *over*-estimate of the term it covers, since the gap runs from the stamp
   to the return while the budget covers the whole call. That over-estimate is
   the formula's only slack, which matters given the `>=` assertion below.

**No term is missing — and the check that would have caught one was run.**
`#0284`'s second bounce was a missing per-row term: `RecordEvent` runs *after*
`MarkSent` inside `sendOne`, so a predecessor's contribution (40s) exceeds the
tail row's own time in claim (35s). **There is no analogue here.** Traced
`processIntakeRow` end to end: `MarkSent` is its last statement, and every call
in it — `IsSuppressed`, `FindByEmail`, `dispatchMutation` (and through it
`newSignup`/`existingSignup`/`restartSignup`/`sendConfirmation`/
`sendAlreadySubscribed`/`auditSignup`) and `MarkSent` — takes the *same* `ctx`
from one `context.WithTimeout(h.sendCtx, intakeRowTimeout)`. A context deadline
is absolute, not per-call, so the whole sequence is bounded by
`intakeRowTimeout` in total. No SES call is on this path (`#0126` moved the
send off it; `ClaimAndEnqueueConfirmation` is a DB transaction), and there is
no unbounded channel send. So predecessor cost == tail-row time-in-claim ==
`intakeRowTimeout`, and charging all `intakeBatchSize` rows the full bound is
right. The absent rate limiter is correctly *not* a term: `#0284`'s lesson is
that an interval is a pacing floor, never a cost ceiling, and with no limiter
at all there is nothing to fold in.

**The boundary case is safe.** The window and the worst case are numerically
equal (210s), so `>=` is doing real work. `OrphanSweep`'s predicate is
`claimed_at < now() - $3::interval` (`internal/outbox/store.go:585`) —
**strict** — so a row at exactly 210s is not swept. Correct as written.

### Does the 210s window assert anything it cannot support?

**No.** The doc comment names what bounds each term and stops there. It
explicitly declines the claim that bounced `#0284`: "Even 210s is not a claim
that context cancellation is instantaneous", and the residual it names
(pgx/OS honouring a deadline promptly) is the real one and covers `ClaimDue`
by name as well as the per-row calls. Every factual claim it makes about other
files was spot-checked and holds: `ClaimDue`'s batch stamp, `ClaimRow`'s
per-row stamp, and `outbox_worker.go`'s `context.Background()`.

One wording nit, not worth a bounce: "a var, not a const, so a test can shrink
it" describes a capability no test currently uses (nothing assigns
`intakeOrphanStaleAfter`, and nothing assigns `outboxOrphanStaleAfter`
either). It is copied from the sibling's precedent and is harmless.
