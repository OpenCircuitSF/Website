## Description

`docs/deployment.md:441` says "This repo currently ships migrations
`000001`–`000020`". The repo is past `000023` and production is at `000022`.

Trivial in itself. It is filed because of the class it belongs to, which has
already been expensive: **a stale fact in a deployment document read as a
current instruction is what bounced `#0125`**, cost a full re-implementation
pass, and would have left `schema_migrations` dirty at 23 on a real deploy.

`docs/database.md` has `TestDatabaseDocMigrationParity` keeping its migration
table honest, and `PRD.md`'s §11 index has
`internal/db/prd_section_index_test.go`. **`docs/deployment.md` has neither**, so
its counts drift silently — which is exactly how this one got three migrations
behind.

`#0293`'s implementer found it while sweeping the greenfield notes, correctly
judged it outside that issue's three named passages, and reported rather than
widening its own scope.

## Acceptance criteria

1. The count is corrected, and stated in a form that does not need updating on
   every migration if a cheaper form exists (a range endpoint that is derived,
   or a pointer to `docs/database.md`'s guarded table rather than a second copy
   of the same fact).
2. **Prefer removing the duplicate fact over guarding a second copy of it.** Two
   documents stating the same count is the drift source; one stating it and one
   linking to it is not.
3. If the count stays in `docs/deployment.md`, extend or mirror
   `TestDatabaseDocMigrationParity` to cover it, so it cannot drift again.
4. Sweep `docs/deployment.md` for other stale counts and version facts while
   there — production's PostgreSQL version, instance size, region, and the
   `schema_migrations` version are all recorded in CLAUDE.md §7 and were all
   measured on the box on 2026-08-25. Report what you found even if nothing.
5. Do not touch any migration file.
6. `ISSUE=NNNN scripts/check.sh go ./internal/db/...` passes — that is where the
   doc-parity guards live.

### Part 2 — `scripts/go_file_visit_floor_guard_test.sh` hardening (#0300 is
resolved; this is additive robustness on top of its settled design, not a
redesign)

Three gaps recorded in `#0300`'s review, all closed:

1. **Fail-open on missing `shasum`/`awk`.** Added both to the `command -v`
   preflight (alongside the existing `find`/`grep`/`sed`). Added a second,
   independent layer too: a new `sha_of()` helper validates every digest is
   exactly 64 hex characters before it is used, `fatal`-ing otherwise. While
   testing this I found `sha_of()`'s own `fatal` had the *same*
   subshell-only-exit problem described in gap 2 below — its call sites
   (`SHA_BEFORE`/`SHA_AFTER` accumulation loops) captured it via
   `$(sha_of …)` with no `||`, so a fatal there would have been silently
   swallowed into an empty string concatenated onto the accumulator, and my
   first `[ -z "$SHA_BEFORE" ]` guard would *not* have caught it (three
   empty joins is `"   "` — three spaces — which is not `-z`). Verified this
   with a stub `shasum` (present on `PATH`, produces empty output — the
   exact shape a preflight `command -v` check cannot see) on the version
   *before* this fix: it printed the FATAL lines to stderr, then kept
   running and printed `PASS: all three tracked guard files unchanged`,
   `0 failures`, exit 0 — a real fail-open that my own first attempt
   introduced. Fixed by making every `sha_of` call site check its exit
   status with `|| fatal …`, same shape as the `extract_const` fix below.
   The `[ -z "$SHA_BEFORE" ] || [ -z "$SHA_AFTER" ]` check in the final
   byte-identity comparison is kept as a second, now-mostly-redundant layer.
2. **`extract_const`'s `fatal` only exited its command-substitution
   subshell**, so the header's claim of "fails closed (fatal)" overstated
   the mechanism — the run still failed closed via `floor_plausible`'s
   empty-operand `||`, but printed a misleading "REGRESSION #0300" message
   after the true FATAL line. Fixed by making it genuinely fatal: both call
   sites (`REAL_VALUE=…` and `MUT_VALUE=…`) now check the substitution's
   exit status with `|| fatal "…"`, so a subshell fatal now terminates the
   whole script immediately with the real diagnosis, never falling through
   to a wrong one. Rewrote `extract_const`'s header comment to explain the
   subshell-exit mechanism explicitly, since the old wording ("fails closed
   (fatal)") was true of the function in isolation but misleading about what
   a bare `$(extract_const …)` call site gets without the `||`.
3. **The FAIL message omitted "the tree grew."** Added it to the
   REGRESSION #0300 message's cause list. Also added a header-comment note
   quantifying the growth ceiling: for `citedTestScanRootsMinPlausibleFileCount=150`
   against today's population of 258, `floor_plausible`'s integer-division
   margin trips once population reaches 302 — about 44 ordinary new `.go`
   files away, not a distant hypothetical. Documented this as an intended
   trip (the floor really has drifted out of proportion by then) whose
   correct remedy is raising the constant in the guarded Go source, not
   loosening this script's margin — per the explicit instruction not to
   weaken the `population/2` rule to raise the ceiling. Did not implement a
   WARN-band mechanism (e.g. `population > 1.5 * floor`); noted it as a
   reasonable future follow-up if the ceiling becomes a recurring nuisance,
   but out of scope here.
