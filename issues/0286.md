## Description

`#0242`'s guard requires an in-branch `role="status"` region to be either a
persistent node or a whole-panel swap with a wired focus move. To avoid false
positives it first **unwraps single-child containers**, because every multi-state
view wraps its whole branch in one container div.

`#0242`'s review established that the unwrap is **principled, not fitted** — it
checked the four sites it defends and each is genuinely a persistent node in a
stable branch, so the naive rule really did produce false positives. The unwrap
stays.

But it means the criterion holds only for the **sole-content case**. Of the 47
in-branch status sites, roughly **24 get no check at all**. This passes the
guard:

```svelte
{#if err}<div class="wrap"><h2>Oops</h2><p role="status">{err}</p></div>{/if}
```

That is `#0244`'s own item 1 shape — `PreferenceCenter`'s two-child branch. The
guard `#0242` built would not have found the defect `#0244` fixed.

The boundary is disclosed, not hidden: it is written into the guard's own header
comment under "Disclosed boundary" and in `#0242`'s work log. That is the right
instinct, and it is why `#0242` was resolved rather than bounced again. But a
disclosed gap is still a gap.

## Why it was not folded into `#0242`

`#0242`'s second pass was scoped to one falsified criterion (the guard scanned
`web/src/views` rather than `web/src`). Closing this gap means extending the
classifier to require a focus-swap target for *any* in-branch status site, plus
building a named allowlist for the genuinely stable branches — comparable in
size to the guard's original construction. Folding that into a bounce fix would
have been a redesign smuggled into a correction.

## Acceptance criteria

1. Any in-branch `role="status"` site requires a wired focus-swap target,
   regardless of whether it is the sole content of its branch.
2. The genuinely stable branches are named in an allowlist mirroring
   `KNOWN_LOADING_PLACEHOLDERS`, each with a written justification. See
   [#0280](0280.md) — if that has landed, follow whatever keying and
   justification rules it established rather than inventing new ones.
3. The single-child unwrap is either removed as no longer needed or retained
   with its reasoning restated against the new rule. Do not leave two
   overlapping mechanisms whose interaction is unexplained.
4. Prove the new rule catches the two-child shape above — a fixture exhibiting it
   must fail the guard. Per CLAUDE.md §8, the oracle must not be the same bytes
   as the subject.
5. Every site count is re-derived from the scan, not edited by hand. The current
   figures are 38 files scanned, 56 alert sites, 30 status sites, 20 placeholders.
6. The `filesScanned` floor `#0242` added stays, and the guard still fails closed
   if the scan visits implausibly few files.
7. `ISSUE=NNNN scripts/check.sh web` passes.

## Root cause

`isGoverningBranchDynamic` gated ALL of the guard's real checking, not just
the loading-placeholder classification: it returned `false` the instant a
branch had more than one significant child anywhere along the unwrap
path, and `checkFile` treated `false` as "push to statusSites, no check at
all" — no persistence check, no placeholder classification, no swap-target
check. 24 of 47 in-branch sites hit that branch.

## Fix

- **Removed `isGoverningBranchDynamic` entirely** (criterion 3's "removed
  as no longer needed"). It never controlled *what* `findFocusTargetVar`
  scanned — that was always `site.governingBranch`'s whole subtree,
  independent of fork shape — only *whether* the check ran. Once every
  in-branch site runs the same checks, the unwrap became dead code sitting
  beside the real mechanism (CLAUDE.md §8's warning), so it's gone rather
  than kept inert. `checkFile`'s new gate is simply
  `site.governingBranch === undefined` (fully unconditional → no check
  needed at all).
- **Added `KNOWN_STABLE_BRANCH_SITES`** (criterion 2, `#0280`-shaped:
  `AllowlistEntry[]`, justified, staleness-checked) for sites whose own
  presence isn't what makes their governing branch mount/unmount. Entries
  key on `Site.rawSource` (the element's own raw source), not its text —
  `site.text` collapses every `{expression}` to the literal string `'{…}'`,
  which collides across multiple purely-dynamic sites in the same file
  (e.g. Admin.svelte's `settingsNotice` and `addressNotice`). 7 entries:
  Admin.svelte's `settingsNotice` (the guard's OWN original calibration
  example) and `addressNotice`; PreferenceCenter.svelte's `saveError`,
  `saveMessage`, `unsubscribeError`; Pending.svelte's per-row resend
  notice; WorkshopEditor.svelte's `previewStale` hint. Each restates,
  for its own site, why it's a stable/multi-purpose branch rather than a
  fresh-creation risk.
- **Fixed one genuine defect** the newly-uniform check found:
  Admin.svelte's CSV-import-commit notice (`{#if importCommitResult}<p
  role="status">Committed: …</p> … <Button>Start a new import</Button>…`)
  really was created fresh alongside three siblings, dynamic text, no swap
  — the `#0244` item-1 shape. Converted it to an unconditional, persistent
  node (`lib/admin.ts`'s new `importCommitNoticeText`), matching this
  file's existing `settingsNotice`/`addressNotice` pattern. Notably, once
  unconditional, its NEW (much larger) governing branch — the whole
  Subscribers-tab content — already contains a wired focus-swap target
  (one of that tab's modal-open `.focus()` calls), so it did NOT end up
  needing a `KNOWN_STABLE_BRANCH_SITES` entry: an entry was added first,
  the real-tree test reported it as **stale** (never matched, because the
  site now passes via the swap-target check before ever reaching the
  stable-branch lookup), and it was removed rather than kept — a live
  demonstration of the staleness check doing its job.
- **Criterion 4 proof fixtures**: split the old "does not flag a role
  status node in a branch with multiple significant siblings" test (which
  asserted the OLD, now-wrong behavior) into two: one proving the fork
  shape now fails without an allowlist entry, one proving it passes once
  named in a throwaway `KNOWN_STABLE_BRANCH_SITES`-shaped array passed
  directly to `checkFile` (CLAUDE.md §8: distinct bytes from the real
  allowlist).
- Real-tree floors unchanged (verified by re-running the enumeration test):
  no site was added or removed by this issue, only reclassified.
