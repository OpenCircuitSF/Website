## Description

`#0347`'s directional axis in
`internal/outbox/claim_comment_referent_guard_test.go` is a **heuristic
window**, not a decision procedure. Its two reviews measured **six shapes**
where it is silent or spurious, none of which fires on `HEAD`:

**False negatives**
- the direction word sits inside a parenthetical the identifier is outside of —
  `// …ClaimDue's kinds filter (applied in pass, below) so…`
- the identifier is named **after** the direction word — `// Below, ClaimDue
  claims the row`
- a clause boundary separates them (em dash, ASCII `--`, or colon)
- more than 90 characters separate them

**False positives**
- non-positional "above"/"below" — `// the table below explains why`,
  `// ClaimDue's retry budget stays below eight attempts`

**Each is a deliberate calibration trade against a real opposing error**, so
none is a defect standing alone. The innermost-parenthesis scoping, for
instance, exists because without it `internal/outbox/store.go:463` regresses
into a false positive — the trade was made knowingly.

**The problem is that nothing in the tree records the trades or would notice if
a future edit widened them.** A change to the window logic currently discovers
its own consequences in a build break, or worse, does not.

This is the same lesson as `#0330` and `#0354`/`#0355` in their own families: a
check that is correct while nothing pins the part doing the work.

## Acceptance criteria

1. A small table of pinned fixtures asserts the **current** calibration in both
   directions: each measured false negative stays silent, each measured false
   positive stays flagged-or-silent as it is today, and the two real sites
   (`db9bff7`'s A and C) stay caught.
2. Each fixture names, in a comment, **which trade it pins and against what
   opposing error** — the point is that a future change must state which trade
   it is moving, not discover it. Name `store.go`'s false positive as the
   reason the parenthesis scoping exists.
3. Prove the table discriminates: mutate the window logic in each of the three
   directions (marker set, every-identifier, innermost-paren) and confirm the
   corresponding fixture fails. A fixture that cannot fail pins nothing — that
   is `#0354`'s finding, in this family.
4. Do **not** try to fix the six shapes. They are calibration, not defects, and
   widening the window re-opens the false positives it was narrowed to close.
   If a pass believes one is genuinely fixable without cost, it must say so and
   stop rather than change it.
5. No `.ClaimDue(` / `.OrphanSweep(` / `.SelectDue(` call-syntax literal enters
   any Go comment, and the harness population stays **42 total / 12
   non-exempt** — `#0347`'s first pass moved it to 43 via its own ban-list, and
   `#0323` moved it 35 → 36 the same way. Re-run
   `scripts/go_file_visit_floor_guard_test.sh` and record it.
6. Fixtures built by **extraction, not retyping** — `#0347`'s reviews confirmed
   the existing ones are byte-identical to source including a U+2014 em dash,
   and retyping one as ASCII was an early bug. `python3` or a hex dump to
   verify; BSD `grep -P` cannot prove a byte sequence present (§8).
7. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout (§8).

## Added by `#0347`'s third review, 2026-08-31

That review resolved `#0347` and measured **two more trade surfaces**, neither
recorded anywhere. It also gave this issue a second job.

**Fifth false-negative row — the marker-exemption surface.** Any of
`has not called`, `rather than`, `instead of`, or `would` appearing in the same
sentence as the direction word exempts a **genuinely stale** directional claim.
Measured against a no-marker control that correctly flags:

| Fixture (`ClaimDue` absent from the file's code, so every claim is false) | Findings |
|---|---|
| control — same false claim, **no marker** | **1 (flags)** |
| `…rather than a bare loop, so ClaimDue below claims the row.` | 0 |
| `…instead of a batch, and ClaimDue below marks it sending.` | 0 |
| `A retry would be wasteful here, so ClaimDue below claims the row…` | 0 |
| `The intake has not called the sweep yet, so ClaimDue below is what claims…` | 0 |

This is calibration, not a defect: criterion 3 of `#0347` **requires** exempting
those markers, and the alternative is concretely worse — it produces false
positives on prose `internal/mailing/outbox_worker.go` writes on `HEAD` today.

**Third false-positive row.** A genuinely historical comment whose only marker
is `never` or `cannot` is flagged, because those two are dropped from the
directional set by design. Three of four such constructed comments are false
positives today; none exists in the tree. The asymmetry is principled and
should be recorded rather than fixed: directional prose routinely asserts what
an identifier does *not* do in the same breath as where it sits — which is
exactly how both real sites survived under the broader marker set. Negation is
load-bearing for the existence axis and disarming for the directional one.

### This issue's second job: retire the prose list

`#0347`'s C2 doc addition **describes** four window limits in prose. The third
review found a fifth, and a future window change will make a sixth — at which
point the list goes stale. That is precisely the failure that produced all
three of `#0347`'s bounces: **a sentence claiming more than the code beside it
delivers.**

So this issue is now explicitly responsible for **replacing C2's prose list
with the fixture table** — making the limits executable rather than described,
and deleting the prose once the fixtures cover it. The `#0330`-style
terminating move here is not to narrow the guard but to stop describing
calibration in prose at all.

**Do not narrow or remove the directional axis.** The same review recorded that
it earns its keep: it is the only instrument that catches `#0342`'s sites A and
C — real, shipped defects invisible to the existence census, to `#0267`'s guard
family, and to three separate human sweeps. Recall 2/2 on the actual defect
population, zero false positives across 30,513 comment groups.

### B1 — BLOCKING: the `identifier-after-direction-word` row pins nothing

`claimCommentGuardDirWordRe` is a word-boundary alternation of `below|above`
with **no** `(?i)` flag — case-sensitive. The row's fixture is `// Below,

inventory to a floor. A floor claim is monotone: discovering a seventh unpinned
surface adds a row and falsifies nothing. That is the `#0330`/`#0347`/`#0356`
terminating move — narrow what the artefact claims — and this pass made it.

So the honest answer to "narrow rather than add rows" is that **this pass did
both, and both were necessary.** B3 narrowed the claim; B4 added the one row the
narrowed claim still leaned on, so that the sentence "every surface the table
pins still holds" is not quietly resting on a trade the table never sampled.
Narrowing alone would have left the every-identifier trade pinned only by the
`db9bff7` falsifiability test, which is fine but invisible from the table.

What would legitimately generate another round is a **change to the window
logic** — and that is the table working as designed, not the surface being
unbounded. A future round would be caused by new work stating which trade it
moves, which is exactly what this issue was filed to make possible.

One methodological gap I am *not* bouncing on, reported for filing below: a row
asserting `wantClaimDueFindings: 0` is unfalsifiable by inspection. You cannot
tell, by reading, whether it is silent because the window is empty, because a
marker exempted it, or because the axis never ran at all — which is precisely how
`#0347`'s third review misread the capitalisation shape as the backwards-window
limit and how B1's row survived a full review pass. I found it by instrumenting;
so did the first reviewer. Nothing in the tree does. That is a real, cheap,
genuinely terminating improvement, but it is beyond this issue's criteria and
adding it now would be the in-file-guard-stacking pattern `CLAUDE.md` §8 warns
against. The orchestrator should file it and let it stand on its own.

### Reported to the orchestrator for filing (§9)

**Title:** `A zero-expectation row in the directional calibration table cannot show why it is zero`

Every `wantClaimDueFindings: 0` row in
`claimCommentGuardDirectionalCalibrationCases` asserts only a count, so three
completely different mechanisms — the direction word never matched, a marker
exempted the sentence, or the window genuinely excluded the identifier — are
indistinguishable to a reader and to `go test`. This is not hypothetical: it is
exactly how `#0358`'s `identifier-after-direction-word` row shipped pinning
nothing (its comment named the window; its real cause was case sensitivity), how
`#0347`'s third review misread that same shape as confirming the backwards-window
limit, and it took hand-instrumentation in two separate review passes to catch.
The fix is small and converts a review ritual into a standing check: add a
`wantSilentBecause` field to `claimCommentGuardDirectionalCalibrationCase` with a
small enum (`no-direction-word-match`, `marker-exempt`, `window-excludes`), have
`TestClaimCommentGuardDirectionalAxisCalibrationTable` re-derive the mechanism
from the axis's own primitives and assert it matches, and a future zero-row then
has to declare its mechanism and be checked against it. Note the design
constraint from `CLAUDE.md` §8: the assertion must re-derive the mechanism from
`claimCommentGuardDirWordRe`/`claimCommentGuardDirHistoricalRe`/the clamps rather
than store a second copy of the answer, or it becomes an oracle made of the same
bytes as its subject. Related: `#0354` (a check pinned by nothing), `#0363` (the
case-sensitivity fix, which will flip one row's expectation).
