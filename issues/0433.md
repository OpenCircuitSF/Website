## Description

Adding a workshop image is currently two manual steps (`docs/media.md`):

	scp -i ~/.aws/AWS.pem <image>.jpg ec2-user@<host>:/var/www/media/

then typing `/media/<image>.jpg` into a plain text field. There is no upload
endpoint — `#0153` decided against one for v1, and `/media/` is the mechanism
that made that decision workable.

**The user has asked for upload support**, deferred to a later phase.

## What `#0153` decided, and what has changed

`#0153` rejected an upload endpoint on three grounds: volume too low to justify
it; it would be the first mutable-data directory in a `//go:embed` + Postgres
deploy model; and no S3 was available to choose blind.

**Two of the three have moved.** `/var/www/media` now exists as exactly that
mutable directory, with an Apache carve-out, a `-Indexes` policy and a
sandboxing CSP already in place — so the deploy-model objection is largely
answered by work that has already happened. Volume is still low.

**Read `#0153` in full before designing.** It is a settled decision and this
issue reopens it deliberately, per its own reopen condition.

## The design questions

1. **Where does the file land, and who owns it?** `/var/www/media` is
   `ec2-user`-owned; the service runs as `opencircuit` with `ProtectHome=true`.
   A writable path shared between them needs deciding, not assuming.
2. **What is accepted?** Type, size, dimensions. `docs/media.md`'s CSP makes
   nothing served from there executable regardless of extension — that is a
   backstop, not a licence to skip validation.
3. **Filename handling.** `cover_image` stores an exact path and the cache is
   `max-age=604800`, so **renaming is how you bust the cache**. A scheme that
   reuses names would serve stale images for a week.
4. **Authorisation and audit.** This is an admin-only write to the filesystem.
   The project has an audit log; say what is recorded.
5. **Does the field stay a text box?** An upload control and a hand-typed path
   can coexist; `isSafeCoverImage` deliberately accepts any same-site path.
6. **Interaction with `#0434`.** Uploads make the media directory grow, which
   changes the backup calculus.

## Added 2026-09-05 — the upload path must strip EXIF

The user's instruction, alongside authorising a one-off strip of the existing
image: **an upload endpoint must strip EXIF, specifically location and device
model, rather than storing what the phone produced.**

This is not optional polish. `#0417` found the live image carried an `APP1`
block naming `Apple`, `iPhone 16`, the software version and the capture
timestamp, served publicly. That one was stripped by hand; **an upload path that
does not strip would reintroduce it on every future workshop**, and at that
point GPS tags become likely — phones record them by default, and the one image
checked happened not to have them.

### What worked, and is worth reusing

The strip was done as **lossless JPEG segment surgery**, not a re-encode: drop
`APP1` (Exif/XMP) and `APP13` (IPTC), keep `APP0` (JFIF) and the image data
untouched. It removed 3,044 bytes and left dimensions and pixel data identical.

That approach has a real advantage over decode-and-re-encode: **no quality loss
and no dependency**. The box has neither `exiftool` nor Pillow, and adding an
imaging library to a `t4g.nano` with 418 MB of RAM shared across four services
is a cost worth avoiding if segment surgery suffices.

**But verify that claim for the formats you accept.** PNG and WebP carry
metadata in different structures entirely, and a JPEG-shaped assumption will
silently pass them through.

### Additional criteria

- Uploads are stripped of EXIF/XMP/IPTC — **at minimum GPS and device model**,
  and preferably every metadata block that is not required to render.
- **Prove it**: upload a file carrying GPS *and* device tags, and assert both are
  absent from what is stored and served. A test using a file with no GPS to
  begin with proves nothing — that is exactly the gap that let `#0417`'s image
  through.
- Say what happens to formats other than JPEG, and whether they are accepted at
  all.
- Stripping happens **server-side**. A client-side strip is a convenience, not a
  control.

## Plan

Phase-1 pass, 2026-09-06. No code written. This section answers the seven design
questions the issue poses, in the order it poses them, and records the two
decisions worth taking before anyone starts: **the split**, and **whether
`#0153` is genuinely superseded**.

### 0. Recommended split — this is two issues, not one

**Keep in `#0433` (provable locally, end to end, today):** the metadata-stripping
code, the upload endpoint, its audit record, the admin-editor control that calls
it, and the `docs/media.md` update.

**Split out (approval-gated, cannot be done by an agent alone):** everything that
changes the production box — the directory's group and mode, the
`ReadWritePaths=` line in the systemd unit, the new variable in
`/etc/opencircuit/config.env`, and the `docs/deployment.md` install step. That is
a separate issue for the orchestrator to file, blocked on the user's go-ahead,
and it is what turns the endpoint from "returns a clear 503" into "works on
production".

The split is not bookkeeping. The server-side half has a real local proof (see
question 6); the production half has none, and pinning them together means the
whole issue stalls on an approval that the code does not need in order to be
correct.

### 1. Where do uploaded bytes land, and who owns them?

**Decision: the same directory, `/var/www/media`, written by the Go service
directly, granted by group ownership plus a `ReadWritePaths=` on the unit.**

Measured on the box, read-only, on 2026-09-06:

| | |
|---|---|
| `/var/www/media` | `drwxr-xr-x  ec2-user:ec2-user`, two files, both `-rw-r--r-- ec2-user:ec2-user` |
| service user | `uid=990(opencircuit) gid=990(opencircuit)`, no supplementary groups |
| Apache | runs as `apache` |
| free disk on `/` | 9.1 G of 20 G (55% used) |
| memory | 418 MB total, ~166 MB available, 2.4 G swap |

So there are **two** independent reasons the service cannot write there today,
and only one of them is ownership:

1. It is not the owner and not in the owning group.
2. `deploy/systemd/opencircuit.service` sets `ProtectSystem=strict`, which makes
   the **entire** filesystem hierarchy read-only to the process regardless of
   permissions. Fixing the mode alone changes nothing.

The clearing commands are in `## Obstacles`. The shape is: give the directory
group `opencircuit` with mode `2775` (setgid, so files created by either writer
inherit the group), and add `ReadWritePaths=/var/www/media` to the unit.
`ec2-user` stays the owner, so the documented `scp` path keeps working unchanged.

**Alternatives considered and rejected:**

- *A service-owned directory elsewhere* (`StateDirectory=` under
  `/var/lib/opencircuit`, Apache re-aliased to it). Still needs a unit change,
  and additionally needs the vhost edited and both existing files moved. §7 is
  explicit about the cost of touching that vhost, and `#0417` proved the current
  files byte-for-byte; moving them buys nothing.
- *A writable subdirectory* (`/var/www/media/uploads/`) so the service can never
  touch the two hand-placed files. Genuinely safer in principle, but the
  protection is against a path-traversal bug that the naming scheme in question 3
  makes impossible by construction (no caller-supplied byte ever reaches a path
  component), and it splits one URL prefix into two for `docs/media.md`,
  `#0434`'s backup scope, and every future reader.
- *Bytes in Postgres, served by the Go service.* Cannot work without a vhost
  change: Apache's `/media` exclusion sits above the wildcard proxy, so a Go
  route at that prefix is unreachable. It would also put image bytes into the
  nightly `pg_dump`, spend RAM on a box that has ~166 MB available, and give
  `#0434`'s filesystem media backup nothing to back up.

**Two mechanical details that decide whether this works at all:**

- `os.CreateTemp` creates `0600`. Apache runs as a third user and reads through
  the `other` bits, so the file must be explicitly `chmod`ed to `0644` before it
  is renamed into place — otherwise every uploaded image 403s, which is exactly
  the row `docs/media.md`'s troubleshooting table already carries.
- The temp file must be created **in the target directory**, not in `/tmp`. The
  unit sets `PrivateTmp=true`, so `/tmp` is a different mount and `os.Rename`
  across it fails with `EXDEV`.

### 2. How is EXIF stripped, with no `exiftool` and no Pillow?

**Decision: segment/chunk surgery in Go over the raw bytes, on an allowlist, with
no decode and no re-encode. No new dependency, and none is needed —
`image/jpeg`, `image/png` and `image` are standard library.**

`#0417`'s hand-strip is the precedent and it worked, but it was a *denylist*
(drop `APP1` and `APP13`). Do not copy that. Copy the technique and invert the
rule: **keep only what is required to render, drop everything else.** A denylist
built from the segments one sample file happened to carry is the same class of
mistake as `#0417`'s original test gap.

**JPEG.** Walk the marker stream (`FFD8`, then segments by marker byte with
fill-byte handling, stopping at `SOS` and copying the entropy-coded data and
`EOI` verbatim). Keep `APP0` (JFIF/JFXX) and `APP2` **only** when its payload
begins with the `ICC_PROFILE` signature — `#0417`'s review ruled that colour
profiles stay, and gave the reason: stripping one degrades rendering on a
wide-gamut display to save bytes nobody is counting. Drop every other `APPn`
(`APP1` covers both Exif and XMP, `APP13` covers IPTC/Photoshop, and a MakerNote
carrying GPS lives inside `APP1`), and drop `COM`. Everything else — `DQT`,
`DHT`, `SOF`, `DRI`, `SOS` — is copied byte-for-byte, so the pixel data is
untouched and the output is bit-identical to the input minus the dropped
segments.

**PNG.** Different structure entirely, exactly as the issue warns. Walk the chunk
stream (8-byte signature, then length/type/data/CRC). Keep `IHDR`, `PLTE`,
`IDAT`, `IEND`, plus the rendering-relevant ancillaries `tRNS`, `gAMA`, `cHRM`,
`sRGB`, `iCCP`, `sBIT`. Drop everything else — which is where `eXIf`, `tEXt`,
`iTXt`, `zTXt` and `tIME` live. Recompute nothing; each kept chunk carries its
own CRC and is copied whole.

**Everything else is refused, with a specific message.** No WebP (its RIFF
`EXIF`/`XMP ` chunks are strippable, but it is a third parser for a format no
phone produces by default), no GIF, and **no SVG** — SVG is script-bearing markup
and the directory's sandboxing CSP is a backstop, not a licence, as the issue
itself says.

**HEIC deserves its own refusal message, and this is the single most likely thing
to bite the user.** An iPhone shoots HEIC unless the camera is set to "Most
Compatible", so the first real upload attempt has a good chance of being a
`.heic`. There is no way to convert it server-side without an imaging
dependency, so the 415 body must name the format and say what to do:
export/share as JPEG. Getting this message wrong turns a supported workflow into
a dead end that looks like a bug.

**No re-encode, ever.** `image/jpeg`'s encoder would recompress and lose quality,
and it is not needed: the goal is byte removal, not transcoding.

### 3. What validates an upload?

Server-side, in this order, refusing at the first failure:

1. `http.MaxBytesReader` then `ParseMultipartForm`, mirroring the existing
   subscriber-import upload path in `internal/handlers` — same construct, same
   error shape. **Cap: 5 MiB**, matching that path's constant, with the same
   convention that the number is stated in the UI copy and mirrored in a
   `web/src/lib/` constant (the two live covers are 63 KB and 89 KB).
2. **Format from magic bytes only.** Never the filename extension, never the
   client's `Content-Type` header. `image` sniffing via the registered decoders,
   or a direct signature check; either way the client does not get a vote.
3. **`image.DecodeConfig`, not `image.Decode`.** This is a memory decision, not a
   style one: the box has ~166 MB available, and fully decoding a 5 MiB JPEG that
   happens to be 8000×6000 allocates well over 100 MB of pixel buffer. Reading
   the header proves the dimensions and that the format's structure is coherent
   without allocating the image. Reject above a pixel ceiling (a megapixel cap
   plus a max edge) so an absurd header is refused before anything is written.
   The trade-off, stated plainly: this does **not** prove the entropy data
   decodes cleanly. A corrupt payload renders broken; it does not execute,
   because of `nosniff`, the `img-src 'self'; sandbox` CSP, and the format
   allowlist above.
4. Strip (question 2), then **re-run the structural walk on the output** and
   assert no dropped segment survived. The strip's own output is the thing that
   gets written, so it is the thing that gets checked.

**`isSafeCoverImage` is reused, but as a post-condition, not an input filter** —
this is the precise answer to acceptance criterion 3. Nothing the caller sends
reaches a path: the stored filename is generated server-side (below). The
endpoint's *response* is the `/media/<name>` path the editor will put in the
existing text field, so a test asserts that generated path satisfies
`isSafeCoverImage`. The validator's deliberate breadth for hand-typed paths is
untouched, and no second, subtly-different definition of a safe path is added —
the mistake the signup-URL work explicitly warned against.

**Filename scheme — `<sanitised-stem>-<hash>.<ext>`.** The stem comes from the
uploaded filename reduced through an **allowlist** to lowercase `[a-z0-9-]`,
collapsed and truncated, falling back to a fixed word when nothing survives; the
hash is a short prefix of the SHA-256 of the **stripped** bytes. This answers
three of the issue's questions at once:

- Traversal is impossible by construction — `.` and `/` are not in the allowlist,
  and the extension comes from the sniffed format, not from the name.
- The week-long `max-age` is never a problem: different bytes always produce a
  different name, which is precisely the cache-bust `docs/media.md` documents.
- Duplicate uploads of identical bytes converge on the same name instead of
  accumulating, and the directory stays readable to a human running `ls`.

### 4. Failure mode when the disk fills or a write dies midway

**Write to a temp file in the target directory, `Sync`, `Chmod(0644)`, `Close`,
then `os.Rename` into place.** Same-directory rename is atomic on the
filesystem, so Apache never serves a half-written image and an existing file is
never left truncated. Every error path removes the temp file (deferred, keyed on
whether the rename succeeded).

`ENOSPC` surfaces from the write or the `Sync` — which is why `Sync` is not
optional; without it a buffered write can succeed and the data can be lost at
close. Map it to a distinct status and a message naming disk space, so an
operator is not told "internal server error" for a condition that has one obvious
remedy. **No `statfs` preflight**: it needs a non-portable syscall for a race it
cannot actually close, and the real numbers are 9.1 GB free against ~150 KB of
media. The requirement here is not prediction, it is never leaving a partial file
and never destroying a good one.

Worth recording for whoever reads this next: `#0434` adds nightly media archives
to the same disk, so free space is no longer purely a function of the images
themselves.

### 5. Does anything need a migration?

**No.** `cover_image` stays the plain-text column it is, holding the path the
endpoint returns; `#0417` and `#0432` already established that. The audit record
uses the existing `audit_log` table and a new **Go constant** in the workshop
action family — a constant, not a schema change. Nothing new is persisted.

Recorded deliberately, because it is a real design choice: **there is no `media`
table.** A row per file would be a second source of truth that drifts from the
disk the moment anyone uses the `scp` path — which stays supported — and it would
buy nothing the filesystem does not already provide.

The frozen range still applies to anyone who disagrees: production reports
version 22, so `000001`–`000022` are frozen, and new work goes in a new numbered
file regardless. Re-derive that number rather than trusting this sentence.

**Orphan pruning is deliberately out of scope, not overlooked.** `#0153` counted
it as one of the five costs of an upload endpoint, so it gets an answer: nothing
prunes. A reliable reference count is not available — any workshop's `cover_image`
may name any path, and body Markdown may reference one too — and `-Indexes` means
an unreferenced file is not discoverable by anyone. Deleting one is an operator
action. If that is judged insufficient it is a follow-up issue, not a silent gap.

### 6. How is this tested without a real `/media/`?

**The directory is a constructor parameter, so every test uses `t.TempDir()`.**
That is the narrow-seam convention this repo already uses everywhere else, and it
is what makes the whole server half provable on a laptop.

Three layers:

1. **The strip, as pure functions over bytes** — put them in their own small
   package so they are testable without HTTP or a database. Table tests over
   synthetic JPEG and PNG inputs.
2. **The endpoint**, in `internal/handlers`, posting real multipart bodies at a
   `t.TempDir()`: the happy path (file on disk, `0644`, path returned, path
   satisfies `isSafeCoverImage`), each refusal (oversize, wrong format, HEIC's
   own message, absurd dimensions), the audit row, and the admin gate.
3. **Wiring**, in `cmd/opencircuit`, where the existing admin route-table guards
   already assert every admin route is mounted behind the session and admin
   middleware. A route with no `{id}` segment passes through that harness
   unchanged.

**The fixture is the part that needs care, and it is where `#0417` actually went
wrong.** The issue's criterion is exact: a file with **no** GPS proves nothing.
So the test must **build a JPEG carrying both GPS and device tags in Go** — SOI,
`APP0`, an `APP1` holding a hand-assembled TIFF header with `Make`/`Model` and a
GPS IFD with real latitude/longitude values, an `APP13`, then minimal
`DQT`/`SOF0`/`DHT`/`SOS`/`EOI`. Two properties make this the right call over
checking in a photo: the user has said workshop images do not go in source
control, and a synthesised fixture supports a **positive control** — the same
test asserts those bytes are *present* in the input before asserting they are
absent from the output. Without the positive control, a strip that silently did
nothing to a file that never had GPS would pass, which is the exact gap that let
the live image through.

Assert absence by **walking the marker stream**, not by searching text, and never
with BSD `grep -P` (§8). The same shape for PNG: plant `eXIf` and `tEXt` chunks,
assert them present, then absent.

**End to end locally:** `STORAGE=json` has no workshops at all — not just no
mailing list — so `dev.sh`'s default mode cannot exercise the editor. `dev.sh`
honours a `STORAGE` override, so the manual pass is `STORAGE=postgres` with a
`DATABASE_URL` and the media directory pointed at a scratch path. That proves
everything except the production directory's permissions, which cannot be proved
anywhere but production.

### 7. What happens to the images already there?

**Nothing, by design, and that is a requirement rather than an expectation.** Both
files stay where they are, keep their names, keep their `cover_image` values, and
keep being served by the same Apache carve-out. The upload path writes new files
beside them; it never renames, rewrites, or enumerates.

The permission change in question 1 alters the **directory's** group and mode, not
the files' ownership or their `0644` mode, so Apache reads them exactly as before.
`#0417` recorded both files' exact byte counts and hashes — so after any change to
that directory, verify by **hash**, not by status code, the way §7 requires for
the `.well-known` carve-out. And the `scp` workflow stays supported and stays
documented: an upload endpoint is an addition, not a replacement, and the fallback
matters on a box where the service can be down.

### Is `#0153` genuinely superseded?

Point by point, which is what acceptance criterion 2 asks for:

| `#0153`'s ground | Status now |
|---|---|
| "It would be the first mutable data directory in the deploy model" | **Lapsed.** `/var/www/media` exists, with the carve-out, `-Indexes`, the sandboxing CSP and `nosniff` already in place, and `#0434` has built its backup path. The architectural change `#0153` declined to make has already been made, for other reasons. |
| "S3 is not available, choosing blind" | **Moot.** The storage question was answered by the `/media/` work, not by S3. Nothing needs choosing. |
| "Adding an image is currently a commit, and deploys are frequent" | **Lapsed, and inverted.** Adding an image is now an `scp`, not a commit, and the user has said images must not be in source control. The premise this reason rested on no longer exists. |
| "The volume does not justify the surface" | **Still holds on volume — and is outweighed on a ground `#0153` did not have.** |

That last row is the honest answer, and it is worth stating rather than smoothing
over. Volume is still low; `#0153` was not wrong about that, and nothing here
disputes it. What supersedes the decision is a requirement `#0153` never
considered: **`#0417` proved that a hand-placed phone photo shipped device
metadata to the public web, and the mechanism that let it happen — a human
copying a file the product never inspects — is untouched by anything since.** An
upload endpoint is now the only place a strip can be *enforced* rather than
remembered. Five of the surfaces `#0153` counted are answered above (content
sniffing at 2/3, traversal at 3, size at 3, duplicate names at 3, orphan pruning
at 5); the sixth thing it did not count is the one that decides it.

So: superseded, deliberately, on the record `#0153` itself asked a later reader to
weigh — and superseded by a privacy requirement plus a completed architectural
change, not by volume.

### Interaction with `#0434`

Uploads make the directory grow, which is the calculus `#0434` names. Nothing here
changes `#0434`'s design; it archives whatever the directory holds. Worth noting
in `docs/media.md` when this lands, and worth remembering that `#0434`'s install
is itself still blocked and approval-gated.

### On a structural guard for the editor

**Recommendation: none, and this is a deliberate departure from `#0444`'s
precedent rather than an oversight.** `#0444`'s justification was that the
failure is silent *in every channel a human would check* — the field types, the
autosave reports success, the preview updates. The equivalent failure here is not
silent: if the returned path is never assigned into the cover field, the field
visibly stays empty. `CLAUDE.md` records that these guards are added reactively,
after a review finds a silent failure, and §8 warns specifically against stacking
mechanisms. The correct move is the one the obstacles catalogue prescribes: put
the decisions in a pure `web/src/lib/` module with vitest coverage (size and
format pre-checks, the HEIC message, building the form body, mapping each server
refusal to copy) and keep the component to markup and wiring. If a review later
finds a genuinely silent leg, that review files the guard — one, not a family.

### Behaviour when the directory is not configured

**Mount the route unconditionally under Postgres storage and return a specific
`503` naming the unconfigured directory** — rather than omitting the route.
Omitting it reproduces obstacle catalogue §11 exactly: a run mode that silently
lacks a subsystem while everything else looks healthy. A named 503 gives the SPA
one thing to show ("uploads are not configured on this server — use the path
field") and gives an operator a signal instead of a mystery. Log a warning at
startup when the directory is unset or not writable, checked by writing and
removing a probe file.

### Implementation order

1. The strip package and its synthetic fixtures — pure, no HTTP, no database.
2. The endpoint, the audit action constant, and the route-table entry.
3. The `web/src/lib/` module and its tests; then the editor control, keeping the
   existing text field and replacing the "no upload endpoint" hint next to it.
4. `docs/media.md`: the "Adding an image" section grows an upload path, and its
   "There is no upload endpoint" sentence goes; the `scp` route stays documented
   as the fallback. Do not touch `docs/deployment.md` — that belongs to the split
   production issue.
