# 0264 — Should a welcome email send without a physical postal address?

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | mailing / compliance |
| **Phase** | 8 — Archive, imports, and delivery health |

## Description

`#0127` added the welcome email — **the first arguably-commercial message on the
transactional send path.** That path does not enforce the `physical_address`
requirement; `#0045`'s refusal is scoped to the campaign worker, and
`CLAUDE.md` §9's rule ("never make the `physical_address` check bypassable from
the UI") is written about that worker.

So today a welcome email will send with `physical_address` empty. Nothing is
bypassed and no rule is violated — the question simply did not exist until this
message did.

**Why it matters.** CAN-SPAM §7704 requires a valid physical postal address in
every *commercial* message. `#0127`'s review ruled — correctly — that the
welcome is promotional list mail rather than transactional: it carries a
workshops CTA and RFC 8058 `List-Unsubscribe` headers precisely because it is
the kind of mail Gmail and Yahoo's bulk-sender rules govern. **The same
reasoning that justifies the unsubscribe headers implies the address
requirement.** A message cannot be commercial enough to need one-click
unsubscribe and transactional enough to skip the postal address.

The confirmation email is genuinely transactional — the recipient is not yet
subscribed — and correctly carries neither.

## Decision

**Extend the refusal to the welcome email.** Recorded by the orchestrator on
2026-08-24; the user is away and this is a compliance question with an
asymmetric cost.

- **If we refuse and were wrong**: welcome emails queue until someone sets
  `physical_address`, which is one setting and is already required before any
  campaign can send (`#0045`). The subscriber is confirmed either way; they miss
  a welcome, not their subscription.
- **If we send and were wrong**: a commercial message goes out without the
  address CAN-SPAM requires, to every confirming subscriber, and each one is a
  separate violation.

`CLAUDE.md` §10 item 3 already records the PO box as not started and blocking
`#0045`. This makes the welcome email honestly dependent on the same thing
rather than quietly exempt.

## Acceptance criteria

- [ ] The welcome email refuses to send when `physical_address` is unset, the way `#0045`'s campaign path does
- [ ] The refusal is not bypassable from the UI (`CLAUDE.md` §9's rule, applied to this path)
- [ ] A refused welcome does not lose the subscriber's confirmation — confirmation must still succeed, and the queue row must be recoverable once the address is set
- [ ] Proved: confirm with `physical_address` empty, assert the subscriber is confirmed and the welcome is not sent; set the address, assert it then sends
- [ ] The confirmation email is explicitly **not** subject to this — it is transactional and the recipient is not yet subscribed
- [ ] `render()`'s comment (see `#0263` item 3) matches whatever ships
- [ ] `ISSUE=0264 scripts/check.sh go ./internal/mailing/... ./internal/subscribers/...` passes with zero skips

## Notes

Reported by `#0127`'s phase-3 review under `CLAUDE.md` §9, which flagged it as
genuinely new rather than a violation of an existing rule.

**Reopen the decision if** the welcome email's content changes to something
purely transactional — no CTA, no promotion. The ruling follows the content, not
the name.
