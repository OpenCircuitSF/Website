## Description

`#0127` added the welcome email — **the first arguably-commercial message on the
transactional send path.** That path does not enforce the `physical_address`
requirement; `#0045`'s refusal is scoped to the campaign worker, and
`CLAUDE.md` §9's rule ("never make the `physical_address` check bypassable from
the UI") is written about that worker.

So today a welcome email will send with `physical_address` empty. Nothing is
bypassed and no rule is violated — the question simply did not exist until this
message did.

**Why it matters.** CAN-SPAM §7704 requires a valid physical postal address in
every *commercial* message. `#0127`'s review ruled — correctly — that the
welcome is promotional list mail rather than transactional: it carries a
workshops CTA and RFC 8058 `List-Unsubscribe` headers precisely because it is
the kind of mail Gmail and Yahoo's bulk-sender rules govern. **The same
reasoning that justifies the unsubscribe headers implies the address
requirement.** A message cannot be commercial enough to need one-click
unsubscribe and transactional enough to skip the postal address.

The confirmation email is genuinely transactional — the recipient is not yet
subscribed — and correctly carries neither.

## Decision

**Extend the refusal to the welcome email.** Recorded by the orchestrator on
2026-08-24; the user is away and this is a compliance question with an
asymmetric cost.

- **If we refuse and were wrong**: welcome emails queue until someone sets
  `physical_address`, which is one setting and is already required before any
  campaign can send (`#0045`). The subscriber is confirmed either way; they miss
  a welcome, not their subscription.
- **If we send and were wrong**: a commercial message goes out without the
  address CAN-SPAM requires, to every confirming subscriber, and each one is a
  separate violation.

`CLAUDE.md` §10 item 3 already records the PO box as not started and blocking
`#0045`. This makes the welcome email honestly dependent on the same thing
rather than quietly exempt.

## Implementation notes

Phase 2 (Sonnet), 2026-08-24. No separate phase-1 planning pass ran — the
Decision section above already settles the design question; this pass
implements it. Ran as one of three concurrent agents (`CLAUDE.md` §5a),
alongside `#0127`'s fix pass and `#0263`.

**Where the refusal lives.** `internal/mailing/outbox_worker.go`'s `render`
already resolves `physical_address` at SEND time for every outbound kind
(#0126's plan §3). For `outbox.KindWelcome` specifically, a blank address
now returns a new sentinel, `errWelcomePhysicalAddressRequired`, instead of
building the message. Every other kind on this path (confirmation,
already_subscribed, registration, recovery, sessions_revoked, admin_alert)
is unaffected — none of them is commercial, and `render`'s doc comment now
says so explicitly, closing `#0263` item 3.

**Recoverable, not abandoned — the load-bearing design choice.**
`sendOne` recognizes the sentinel and routes it to a new
`deferMissingPhysicalAddress` rather than the ordinary `finishFailed` path.
That method calls `outbox.Store.MarkRetryOrAbandon` with a deliberately
huge `maxRetries` (`welcomeAddressDeferMaxRetries = math.MaxInt32`), so the
row always takes the `queued` branch and backs off along the *existing*
schedule (`Backoff`, clamped to 24h) — reusing tested machinery rather than
inventing a second requeue path. This is what makes the criterion's
"recoverable once the address is set" true: an ordinary send failure would
eventually reach `queue_max_retries` and land in `abandoned`, which nothing
automatically retries even after the address is set. A refusal here can
never reach that state.

**Confirmation is untouched, and that is the point.**
`internal/subscribers.Store.Confirm` does not read `physical_address` at
all — it never did, and this issue does not change that. A subscriber's
confirmation therefore always succeeds regardless of this setting; only
the welcome *send* waits on it. This is why the fix lives entirely in the
worker's render/send path rather than in `Confirm`.

**Not bypassable from the UI (`CLAUDE.md` §9).** Grepped tree-wide:
`internal/mailing/outbox_worker.go`'s `render` is the ONLY call site of
`BuildWelcomeEmail` anywhere in `internal/`, and
`internal/subscribers/store.go`'s `Confirm` is the ONLY call site that
enqueues `outbox.KindWelcome`. There is no admin action, handler, or other
code path that can produce or send a welcome message outside this one
gated function — structurally, not just by convention.

**Error string carries no issue citation.** The sentinel's text lands in
`outbound_queue.error`, which the admin pending/dashboard screens can
surface to an admin — so, per `TestNoAdminFacingStringCitesInternalDocs`
(`#0172`/`#0175`/`#0178`/`#0181`), the literal itself says only "physical_address
is not set"; the `#0264` reference lives in the surrounding code comment,
not the string. The guard caught this on the first verification run and it
was fixed before committing.

**`render()`'s comment, corrected (closes `#0263` item 3).** The old text
("this worker deliberately does NOT refuse to send a confirmation for a
missing physical_address... refusing here would turn a cosmetic gap into a
broken signup flow") predated the welcome email and did not consider it.
Rewritten to state the rule for the six non-commercial kinds and then name
`KindWelcome` as the one deliberate exception, with the reasoning
(#0127's own commercial-mail ruling) inline.

**Named test proving both directions of the acceptance criterion:**
`TestOutboxWorker_DefersWelcome_MissingPhysicalAddress`
(`internal/mailing/outbox_worker_test.go`) —

1. Sets `settings.physical_address` to `""`, creates a real subscriber via
   `subscribers.Store.Create`, and confirms it via `subscribers.Store.Confirm`
   (a genuine call, not a direct `Enqueue` — this issue's own criterion asks
   to "confirm... assert the subscriber is confirmed"). Asserts
   `confirmed.Status == StatusActive`. Asserts the welcome (matched by
   subject, since `Create` also enqueues an ordinary confirmation email that
   sends normally regardless of this setting) is **not** among the messages
   the mailer received, and that the queued row settles back to `'queued'`
   after being claimed and deferred at least once — not `'sent'`, not
   `'abandoned'`.
2. Sets `settings.physical_address` to a real address, forces the row's
   `next_attempt_at` due immediately (the same technique
   `TestOutboxWorker_AbandonsAtMaxRetries_RetainsLastError` uses, to avoid
   waiting out the 1-minute backoff step), and asserts the **same** row
   reaches `'sent'` and exactly one welcome-subject message goes out to the
   subscriber's address.

**Mutation-proven.** Temporarily short-circuited the new guard in `render`
(`if false && strings.TrimSpace(addr) == ""`) — the test above failed as
predicted ("status = sent... want queued"), proving the guard is what the
test is actually exercising. Reverted; `shasum -a 256` confirmed
`internal/mailing/outbox_worker.go` byte-identical to the pre-mutation
file.

**Full-suite confirmation.** `ISSUE=0127fix scripts/check.sh` (run once,
covering this issue's changes together with `#0127`'s and `#0263`'s fix
passes, since all three touch overlapping files/scope in the same
concurrent-agent window): all 17 Go packages `ok`, zero skips; `npm run
check` — 278 files / 0 errors / 0 warnings; `npm test` — 35 test files /
**3,852** tests passed (unchanged — no frontend files touched by this
issue). `uptime` before every run: load average ~2.0–2.4, well under
`CLAUDE.md` §5's threshold.

**Incidental fix, disclosed.** Running the new test immediately before the
existing `TestOutboxWorker_Stop_ReleasesClaimedRow` made that unrelated
test fail deterministically (not flakily — reproduced on every run). Root
cause: that test hardcoded which of its two claimed rows would be the one
blocked mid-send, but `outbox.Store.ClaimDue`'s `UPDATE ... RETURNING`
does not actually guarantee its output order matches the claiming
subquery's `ORDER BY next_attempt_at, id` — Postgres does not define
`RETURNING` row order for a multi-row `UPDATE`. This is a pre-existing
latent fragility in that test (confirmed: it also fails when paired
immediately after other, unrelated pre-existing tests that leave the
shared `outbound_queue` table in a different physical state, and passes
again with this issue's new test skipped) — not a defect introduced by
this issue's own change, but exposed by it. Rewrote the test's post-claim
assertions to check "exactly one row sent, one queued" across the pair
rather than assuming which id is which. Not filed as a separate issue
(`CLAUDE.md` §5b): it is a test-only fragility fix, already committed
alongside this issue's own change in `611915b`, and the fix is complete.
