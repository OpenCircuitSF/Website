# 0238 — Client-side navigation announces nothing: no title change, no focus move

| | |
|---|---|
| **Status** | in-progress |

| **Phase** | 8 — Polish and follow-ups |

## Description

The SPA router changes the view without changing `document.title` and without
moving focus. Confirmed in a **real Safari session**, not jsdom: after
`navigate()`, `document.activeElement` is `<body>`.

For a sighted mouse user nothing is wrong. For everyone else the page silently
becomes a different page:

- **A screen-reader user is told nothing.** A full page load announces the new
  document; a client-side route change is just a DOM mutation, so unless
  something moves focus or a live region speaks, the navigation is silent. The
  user is left on a `<body>` that now contains different content.
- **A keyboard user loses their place.** Focus on `<body>` means the next Tab
  starts from the top of the document — including back through the header and
  skip link — rather than from the new view.
- **The tab title is wrong on every route but the first.** That is also what
  browser history, bookmarks and window switchers show, so the cost is not only
  assistive.

This is the standard SPA accessibility gap and it has a standard fix, but the
fix has real design questions (below) which is why it is filed rather than
patched into `#0063`.

## Acceptance criteria

- [ ] `document.title` reflects the current route, and is set from the same source as the view's `<h1>` so the two cannot drift
- [ ] Focus moves on client-side navigation, to a target that is decided rather than defaulted — see `## Open questions`
- [ ] The initial load is not double-announced: it already gets the browser's own navigation, so the router must not re-announce it
- [ ] Back/forward (`popstate`) behave the same as a link click
- [ ] Proved in a **real browser**, asserting `document.activeElement` identity and `document.title` after each of a link click, a programmatic `navigate()`, and a `popstate` — jsdom is not sufficient evidence here (`CLAUDE.md` §1)
- [ ] A guard fails if a route is added without a title, so the mapping cannot go stale — the failure mode `#0113` and `#0237` both record
- [ ] `scripts/check.sh web` passes

## Open questions

Worth a planning pass rather than deciding at the keyboard:

1. **What receives focus?** The `<h1>` (needs `tabindex="-1"`), the `<main>`
   landmark, or the skip-link target. Each announces something different. The
   project already has a correct precedent for whole-panel swaps in
   `Unsubscribe.svelte` — check whether it generalises before inventing.
2. **Focus move, live region, or both?** A visually-hidden `role="status"`
   announcing the new page name is less disruptive than moving focus, but does
   not fix the keyboard user's lost place. Doing both can double-announce.
3. **Where do titles live?** Co-located with each route in the route table, or
   derived from the view. `#0019`–`#0021` already built SEO metadata; this
   should reuse that rather than open a second source of truth.

## Work log

No separate phase-1 planning pass was run (this batch's implementer decided
the three Open Questions directly rather than deferring) — recorded here so
the decisions are traceable to their reasoning, per `CLAUDE.md` §3's
"planning is selective" allowance for mechanical-enough ambiguity.

**Open question 1 — what receives focus.** The view's own `<h1>`
(`tabindex="-1"`), generalizing `Unsubscribe.svelte`'s existing
whole-panel-swap precedent to every route rather than inventing a new
target. Every public/auth view's `<h1>` now carries `tabindex="-1"`
(`Home.svelte`, `WorkshopsIndex.svelte`, `WorkshopDetail.svelte`,
`About.svelte`, `PrivacyPolicy.svelte`, `Subscribe.svelte`,
`SubscribeThanks.svelte`, `NotFound.svelte`, `Login.svelte`,
`RegisterVerify.svelte`, `RecoverVerify.svelte`, `Account.svelte`,
`Admin.svelte`, `ConfirmSubscription.svelte`'s `'Confirming…'` state,
`Unsubscribe.svelte`'s `'confirm'` state, `PreferenceCenter.svelte`'s five
`showHeading` sites). A new site-wide CSS rule (`web/src/app.css`,
`h1[tabindex='-1']:focus`) supplies the accent ring with plain `:focus` (not
`:focus-visible`), matching `Unsubscribe.svelte`'s and
`PreferenceCenter.svelte`'s existing identical reasoning: Safari does not
reliably grant `:focus-visible` to a programmatic `.focus()` call.

**Open question 2 — focus move, live region, or both.** Focus move only.
Moving focus already gives assistive technology something concrete to
announce (the heading's accessible name) without a second, competing
mechanism — `Unsubscribe.svelte`'s and `ConfirmSubscription.svelte`'s
existing pattern already does exactly this for their own internal swaps,
and generalizing it (rather than adding a `role="status"` announcer
alongside it) avoids the double-announce risk the issue's own Notes flag.

**Open question 3 — where titles live.** A new `web/src/lib/pageTitle.ts`,
NOT a second copy of `internal/seo/seo.go`'s SEO title table. That Go table
governs the SERVER-rendered `<title>` for a route's FIRST paint (tuned for
crawlers/social cards); this module governs ONLY client-side navigations
after that first paint, where there is no fresh server render to defer to.
Its `STATIC_HEADING` table's values are the LITERAL text each route's `<h1>`
renders — the "same source as the view's `<h1>`" criterion 1 asks for — not
Go's SEO copy, which turned out to differ in wording (e.g. `/about`'s SEO
title is "About — Open Circuit SF"; the `<h1>` says "About Open Circuit
SF"). `pageTitle.guard.test.ts` proves this mechanically for every
"guarded" entry: it parses the cited view with `svelte/compiler` and
asserts the compiled `<h1>`'s own text equals the table value, both reading
`APP_NAME` from the same `branding.ts` import.

**The type-level guard (criterion 6).** `STATIC_HEADING` is typed
`Record<RouteName, string>`, not `Partial<...>` — TypeScript itself refuses
to compile if a `RouteName` is added to `router.ts` without a matching
entry here, which is what `npm run check` (part of `scripts/check.sh web`)
enforces. Mutation-proved: added a `'mutation-proof-fake-route'` member to
`RouteName`, confirmed `npm run check` fails naming both `pageTitle.ts` and
`pageTitle.guard.test.ts` (`Property "mutation-proof-fake-route" is missing
in type ... Record<RouteName, string>`), then reverted and confirmed
`shasum -a 256` byte-identity on `router.ts` and a clean `npm run check`
(0 errors) afterward.

**Initial-load exclusion (criterion 3).** `pageTitle.ts`'s
`shouldAnnounceNavigation()` is a one-shot module-level flag: false on its
first call, true on every call after. `App.svelte`'s new `$effect` (added
after the existing `getMe()`/`onMount` block) reads `$currentRoute`, calls
it once per route change, and only writes `document.title` / moves focus
when it returns `true` — so the route the page actually loaded on (which
already got the browser's own navigation, and for a route
`internal/seo/seo.go` has a real entry for, already has a
server-rendered `<title>`) is left untouched. Same guard covers the
`register-verify`/`recover-verify` replace-navigate `App.svelte` already
does before `sessionChecked` flips true: that effect's `if (!sessionChecked)
return;` means it never even reaches `shouldAnnounceNavigation()` for that
redirect, so the flag is correctly spent by the REDIRECTED-TO route's first
real render instead.

**Route-change effect (criteria 1, 2, 4).** One `$effect` in `App.svelte`
covers a link click, a programmatic `navigate()`, and `popstate` identically
-- all three funnel through `router.ts`'s `currentRoute` store the same way,
so nothing is special-cased per trigger. On each real (non-first)
transition: `document.title = titleForRoute(route)`, then `tick().then(...)`
moves focus to `document.querySelector('h1[tabindex="-1"]')`.

**Known, disclosed boundary**: three routes (`workshop-detail`, `confirm`,
`unsubscribe`) have a `<h1>` that varies by runtime/async state, which a
route-level table can't see. Each gets a "fallback" entry worded to match
that route's FIRST rendered state (accurate at the moment a fresh navigation
sets the title) — `pageTitle.ts`'s module doc comment names this explicitly.
A LATER async transition inside one of these views (e.g.
`ConfirmSubscription.svelte`'s `confirming -> success/error`, or
`WorkshopDetail.svelte`'s fetch resolving) does not additionally update
`document.title` today; only its own internal focus-move (pre-existing,
`ConfirmSubscription`/`Unsubscribe`) still fires. Extending title-tracking
into those transitions was judged out of proportion to this issue's scope
(§8's convention: named, not silently gapped).

**A real bug this session's own real-browser check caught**: `formatTitle`'s
first version compared `heading === APP_NAME` to decide whether to append
the brand suffix, which produced "About Open Circuit SF — Open Circuit SF"
in an actual Safari session (About's `<h1>` is "About {APP_NAME}", not an
exact match). Fixed to `heading.includes(APP_NAME)`; a synthetic fixture
test now locks in both the About and Unsubscribe shapes
(`pageTitle.guard.test.ts`).

**Re-implementation, 2026-08-27 (fixes the bounce above).** Applied exactly
the fix the reviewer verified: `App.svelte`'s route-change effect now calls
`heading?.focus({ preventScroll: true })` instead of the bare
`heading?.focus()` that defaulted to `preventScroll: false`. A doc comment
at the call site records why (`web/src/App.svelte`, next to the effect).

Added a regression test for the part of this that IS mechanically testable
without a browser: `web/src/lib/appNavigationFocus.structuralGuard.test.ts`
is a structural (AST-only, `svelte/compiler`, no mounting) guard, the same
class as `liveRegionGuard`/`modalFocusWiring`/`pageTitle.guard`, that parses
`App.svelte`'s `<script>` and asserts the `.focus()` call site passes
`{ preventScroll: true }` literally. It does NOT and cannot prove the scroll-
restoration behavior itself — jsdom has no scroll-into-view-on-focus
implementation at all, with or without `preventScroll`, so a jsdom test
asserting `window.scrollY` would pass identically regardless of this option
and would be zero evidence, not weak evidence. What it does prove: a future
edit that drops the option, or flips it back to `false`, fails loudly here
instead of silently reintroducing the defect. Mutation-proved both
directions: reverting the call to bare `heading?.focus()` fails the guard
naming the exact line and reason; the current source passes.

## Review notes

> 🔴 Bounced 2026-08-27 (phase 3) — everything this issue asked for works, and I
> reproduced each claim in a real Safari session. But the focus move **breaks
> back/forward scroll restoration**, measured in the same browser, and then
> writes the bogus offset back into the history entry.

**Independently reproduced in a real browser** (Safari 26.6.2 via
`safaridriver`, a production `npm run build` served from a throwaway worktree on
a private port, bundle hash read back from the page and matched against the
build — `CLAUDE.md` §8b):

| Step | `document.title` | `document.activeElement` |
|---|---|---|
| fresh load `/privacy` | `%%OC_TITLE%%` (untouched) | `BODY` |
| link click → `/` | `Hands-on electronics workshops — Open Circuit SF` | `H1` |
| Back (`popstate`) → `/privacy` | `Privacy Policy — Open Circuit SF` | `H1` |

So criteria 1, 2, 3 and 4's title/focus half all hold, and the first render
genuinely is not announced. Criterion 6's type-level guard is real: I added a
`'zz-probe-route'` member to `RouteName` in a worktree and `svelte-check`
failed with 2 errors naming `pageTitle.ts:72` and `pageTitle.guard.test.ts:101`.
The `<h1>` parity guard bites too — changing `WorkshopsIndex.svelte`'s heading to
`Workshops!` failed it — and it fails **closed** on an absent `<h1>`
(`found === undefined` throws) rather than passing on an empty extraction. Its
oracle is genuinely independent: the answer lives in a different file
(the view) from the subject (`pageTitle.ts`), so an edit to the table cannot
satisfy it.

**The defect.** `router.ts` carries deliberate scroll-restoration machinery
(`restoreScroll`, `RESTORE_DEADLINE_MS`, `cancelPendingScrollSave`, the rAF
re-apply loop). `App.svelte`'s new effect calls `heading?.focus()` with the
default `preventScroll: false`, so the browser scrolls the heading into view —
after `restoreScroll` has already put the page back where the user was.

Measured, both directions, same script and same session shape:

| Build | after Back: `window.scrollY` | `history.state.scrollY` |
|---|---|---|
| `35288dd` (immediately before this issue) | **1200** | **1200** |
| `74bdccf` (this issue) | **0** | **0** |

The `history.state` column is the part that makes this more than cosmetic: the
throttled scroll listener then stamps the bogus `0` into the entry, so the
user's saved position is destroyed, not merely overridden for one paint — the
exact "the damage outlives the moment" failure `cancelPendingScrollSave`'s own
doc comment was written against.

**The fix, verified.** `heading?.focus({ preventScroll: true })`. I applied only
that change in the worktree, rebuilt, and re-ran the identical script: after
Back, `window.scrollY` and `history.state.scrollY` are both `1200` again while
the title is still `Privacy Policy — Open Circuit SF` and
`document.activeElement` is still the `H1`. Link-click behaviour is unchanged
(`navigate()` already resets scroll to 0, so there is nothing to preserve
there).

**What the next pass must do:**

1. Focus with `{ preventScroll: true }`.
2. Prove it in a real browser by asserting **`window.scrollY` and
   `history.state.scrollY`** after a Back, not only `document.title` and
   `document.activeElement` — those two were green while restoration was
   broken, which is why the original pass missed it.
3. Add a regression test if one can be written without a browser; if not, say so
   and name the browser run, per `CLAUDE.md` §1's jsdom-vs-browser rule.

Nothing else in this issue needs to change. The three-Open-Question decisions,
the `pageTitle.ts`/`seo.go` split, the one-shot first-render flag (which I
confirmed cannot swallow a legitimate first *client* navigation — the
`!sessionChecked` early return sits **before** `shouldAnnounceNavigation()`, and
while `sessionChecked` is false the shell renders no links to click), and the
three disclosed `fallback` title entries are all sound.
