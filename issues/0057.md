### The region answer: `us-east-1`, and no migration

`PRD.md` §10.3 selects `us-west-2` and tells you to verify the inbound-region
list before committing. `docs/email-setup.md` repeats `us-west-2` in five
places. **Production is `us-east-1` and has been since deploy day.**

The AWS *Email Receiving endpoints* table lists **`us-east-1` →
`inbound-smtp.us-east-1.amazonaws.com`** as the first row. So the region the
project actually sits in supports SES inbound, the existing sending identity's
region is usable for receiving, and the whole project stays in one region with
no change at all. **Do not migrate to `us-west-2`.** §10.3's recommendation was
written against an assumed region that was never the one built.

An earlier attempt to establish this by resolving `inbound-smtp.<region>.amazonaws.com`
per region is **not** a valid test — all sixteen regions probed returned an A
record, including ones absent from the receiving table. The endpoint table is
the oracle; DNS is not.

### Does this depend on `#0415`?

**No.** SES's sandbox constrains *outbound* only — recipient must be a verified
identity, 200 messages/day, 1/second. AWS's email-receiving prerequisites list
exactly three items (domain verification, MX record, resource permissions) and
production access is not among them. Inbound receipt rules work identically
whether or not `ProductionAccessEnabled` is true, so `#0057` can proceed while
`#0415` is still unresolved.

The one honest connection is indirect and not blocking: path 3 only receives
traffic once campaigns carrying the `mailto:` form of `List-Unsubscribe` are
actually sent, and that does depend on sending working.

### The blast radius nobody has flagged: the active rule set is account-wide

**A region has exactly one active receipt rule set, for the whole account.**
Activating `opencircuit-inbound` in `us-east-1` therefore *replaces* whatever
is active there now. This account also hosts ShortLinks and other services.

Since `ses:DescribeActiveReceiptRuleSet` is denied to both available
identities, **this is the first thing to check and it is a hard gate.** If a
rule set is already active, the correct move is to add a rule to *that* set,
not to create and activate a new one.

### Two corrections to this issue's own acceptance criteria

**1. One action, not two.** The criteria call for "Action 1 writes to S3" and
"Action 2 publishes to SNS". Implemented literally that is wrong for `#0058`.
A standalone SNS receipt-rule action publishes the *message content* (capped at
150 KB) and carries no S3 object key. The **S3 action's own optional `TopicArn`
field** is the one that fires after the object is written and whose
notification names the object key that `#0058` needs to fetch by. So the rule
takes a **single `S3Action` with `TopicArn` set**, which satisfies both
criteria with one action and is the only shape that makes `#0058` implementable.

**2. The domain must be verified as an SES identity first.** No criterion
mentions this. AWS's setup prerequisites are explicit: "Verify your domain with
Amazon SES by publishing DNS records to prove that you own it", *then* publish
the MX. `lists.opencircuitsf.com` is not currently an SES identity, so a
second, separate DNS record is required beyond the MX. Verification for
receiving needs only the `_amazonses` TXT token; DKIM is not required on a
receive-only domain.

### The DNS changes — two new record sets, both additive

Zone `Z0825067RV8QY5UIKS96`. **Both are `CREATE`s at names that hold no record
set today. The apex `opencircuitsf.com. MX 1 SMTP.GOOGLE.COM.` is not read,
not written, and not in either change batch.**

| # | Name | Type | Current value | New value |
|---|---|---|---|---|
| D1 | `_amazonses.lists.opencircuitsf.com` | TXT | *(none; wildcard supplies a CNAME)* | the verification token SES returns from `CreateEmailIdentity` |
| D2 | `lists.opencircuitsf.com` | MX | *(none; wildcard supplies `CNAME ec2.smallsharptools.com`)* | `10 inbound-smtp.us-east-1.amazonaws.com`, TTL 300 |

**The one non-obvious consequence.** Per RFC 4592 a wildcard does not apply at
a name that owns any record. Creating D2 therefore stops
`lists.opencircuitsf.com` resolving to `ec2.smallsharptools.com` /
`44.222.209.183` for *every* type, not just MX — the name will answer NODATA
for A and CNAME.

That was checked rather than assumed, and it is safe: `EMAIL_LIST_DOMAIN` is
consumed in exactly one place, `mailing.CampaignHeaders`, and only to build the
`mailto:unsubscribe@<listDomain>?subject=…` form of `List-Unsubscribe`. Nothing
constructs an HTTPS URL on it. The `List-Id` header uses the deliberately
different singular `list.opencircuitsf.com`, which RFC 2919 makes an opaque
identifier that never needs to resolve. So nothing in the service or the SPA
depends on `lists.opencircuitsf.com` resolving to the web server.

TTL 300 on both is deliberate — it matches the zone's other short-lived records
and keeps the rollback window to five minutes.

### The AWS objects

All in **`us-east-1`**, account `378152330719`.

| # | Object | Name / ARN | Notes |
|---|---|---|---|
| A1 | SES domain identity | `lists.opencircuitsf.com` | receive-only; no DKIM, no MAIL FROM, never used to send |
| A2 | S3 bucket | `opencircuitsf-inbound` | must be in a receiving region; `us-east-1` qualifies, so no `IamRoleArn` on the action is needed |
| A3 | S3 Block Public Access | all four flags on `opencircuitsf-inbound` | the bucket holds inbound mail — it must never be public |
| A4 | S3 bucket policy | on `opencircuitsf-inbound` | allows `ses.amazonaws.com` `s3:PutObject` on `…/unsubscribe/*` only, conditioned on `AWS:SourceAccount` **and** `AWS:SourceArn` of the exact receipt rule |

| A9 | SES receipt rule | `unsubscribe`, in A8 | `Recipients: ["unsubscribe@lists.opencircuitsf.com"]`, `Enabled: true`, `ScanEnabled: true`, `TlsPolicy: Optional`; one `S3Action` → bucket A2, `ObjectKeyPrefix: "unsubscribe/"`, `TopicArn`: A6 |
| A10 | Activate A8 | `SetActiveReceiptRuleSet` | **the account-wide step** |
| A11 | IAM policy on `opencircuit-web-2026` (corrected `#0508`, 2026-09-12 — the plan named `opencircuit-instance`, the role on the instance that has since been decommissioned; the live box carries `opencircuit-web-2026` instead) | inline `opencircuit-inbound-s3` | `s3:GetObject`, `s3:DeleteObject` on `arn:aws:s3:::opencircuitsf-inbound/unsubscribe/*` — the prefix, not the bucket |
| A12 | SNS HTTPS subscription | A6 → `https://www.opencircuitsf.com/api/ses/inbound` | **deferred — see below** |

**`TlsPolicy: Optional`, not `Require`.** `Require` bounces senders that do not
offer STARTTLS. On an unsubscribe address, refusing a request because the
sender's MTA is old is the wrong failure, and RFC 8058 treats unsubscribe
handling as something that must not error.

**`Recipients` names the one mailbox, not the domain.** Scoping the rule to
`unsubscribe@lists.opencircuitsf.com` means anything else sent to the subdomain
gets SES's default 550 rather than being silently captured into S3.

**Why A12 is deferred.** `POST /api/ses/inbound` does not exist —
`#0058` builds it, and only `POST /api/ses/notifications` (from `#0037`, now
resolved) is wired today. An SNS HTTPS subscription that cannot be confirmed
by the endpoint stays `PendingConfirmation` and delivers nothing. Creating the
topic now and the subscription in `#0058` costs nothing: mail still lands in
S3 in the meantime, so nothing is lost, it simply waits. `SES_INBOUND_BUCKET`
belongs in `config.env` at the same time, since adding it requires a service
restart it does not otherwise need.

### Ordering — the MX goes last

This is the whole safety argument. Every AWS object is inert until the MX
exists, so the sequence builds the destination first and only then routes mail
to it. Each step is independently reversible.

1. **Gate.** `aws ses describe-active-receipt-rule-set --region us-east-1`. If a
   rule set is already active, stop and add a rule to it instead of A8/A10.
2. A1 — create the identity, capture the verification token.
3. D1 — publish the TXT; wait for the identity to report verified.
4. A2, A3, A5, A4 — bucket, then lock it down, then lifecycle, then policy.
5. A6, A7 — topic and its policy.
6. A8, A9 — rule set and rule.
7. A10 — activate.
8. **D2 — the MX.** Mail begins flowing only here.
9. Verify end to end: send a real message to
   `unsubscribe@lists.opencircuitsf.com` and confirm the object appears under
   `s3://opencircuitsf-inbound/unsubscribe/`.
10. A11 — the instance-role grant. Last, because nothing reads the bucket until
    `#0058`.

### Rollback

The failure mode is lost mail, so every step has an explicit undo and the
riskiest step is both last and the fastest to reverse.

| Undo | Effect |
|---|---|
| **Delete record set D2** (`lists.opencircuitsf.com MX`) | Inbound routing stops immediately; within the 300s TTL the wildcard resumes answering for that name. **This alone fully reverts the routing change.** |
| `SetActiveReceiptRuleSet` with no name, or back to the previously active set | SES stops applying the rule |
| `DeleteReceiptRule` / `DeleteReceiptRuleSet` | removes A9/A8 |
| Delete the SNS topic A6 | removes A6/A7 |
| Empty and delete the bucket A2 | removes A2–A5 |
| Delete record set D1, delete identity A1 | removes the verification |
| Delete the inline policy A11 | removes the instance-role grant |

**Confirming apex mail still flows** — the check that matters, because a
mistake here costs real human mail:

- `dig +noall +answer MX opencircuitsf.com` must still read
  `1 smtp.google.com.` and nothing else. Run it before and after and diff.
- `dig +short MX lists.opencircuitsf.com` should read
  `10 inbound-smtp.us-east-1.amazonaws.com` — and it must be the *only*
  MX at that name.
- `dig +short MX bounce.mailing.opencircuitsf.com` must still read
  `10 feedback-smtp.us-east-1.amazonses.com`, unchanged.
- Send a message from an outside address to a real Workspace mailbox on the
  apex and confirm delivery.

Nothing in this plan touches the apex, `bounce.mailing.`, `www`, the wildcard,
or the `/.well-known/` Apache exception.

### The escape hatch stays open

The issue's own note offers it and it remains the right call if any of the
above turns fiddly: point the `mailto:` at a monitored mailbox and process
unsubscribes by hand. Paths 1 and 2 are the mandatory ones; path 3 is optional
in v1, and launch volume makes manual handling honest. In particular, if the
gate at step 1 finds another service already owns the active rule set in
`us-east-1`, take the escape hatch rather than reshuffling another project's
mail handling.

### Is the rule itself well-formed?

Yes, and it is mechanically applicable rather than advice.

- **It names the credentials that count**, by enumeration rather than by
  adjective: `certbot-dns-updater`'s IAM permissions, IMDS on the instance,
  `/etc/opencircuit/config.env` on the box, public DNS. A writer does not
  have to judge what "a credential we hold" means.
- **It names what each entry must carry**: the command or probe, and the
  date it was run. Both are checkable by looking at the bullet.
- **It names where a failing claim goes instead** — Part 1, an ordering
  step, or the closing "We could not read" paragraph — which is the half
  most such rules omit, and the half that makes the rule usable rather than
  merely prohibitive. The A1 remedy exercised all three destinations at
  once.

Its one real weakness is that it is **unenforced prose**. The section has
produced a false claim on three consecutive passes, and nothing in
`scripts/check.sh` will catch a fourth. Truth of an AWS fact is not
mechanisable, but the *shape* the rule demands is: every bullet under that
