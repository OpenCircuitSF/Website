## Description

The AWS-side plumbing that routes mail sent to `unsubscribe@lists.opencircuitsf.com` into S3 and notifies the service.

## Acceptance criteria

- [ ] MX record for `lists.opencircuitsf.com` → `10 inbound-smtp.<region>.amazonaws.com`
- [ ] **The apex `opencircuitsf.com` MX is untouched**
- [ ] SES receipt rule set `opencircuit-inbound` with a rule matching the unsubscribe recipient
- [ ] Action 1 writes the message to `s3://opencircuitsf-inbound/unsubscribe/{messageId}`
- [ ] Action 2 publishes a notification to the `opencircuit-inbound-mail` SNS topic
- [ ] SNS topic subscribed to `POST /api/ses/inbound` over HTTPS
- [ ] S3 lifecycle rule deletes objects after 30 days
- [ ] IAM instance role granted `s3:GetObject` and `s3:DeleteObject` on that bucket prefix only
- [ ] End-to-end verified by sending a real message and observing the object land in S3
- [ ] Setup documented step by step in `docs/email-setup.md`

## Notes

PRD §6.5 path 3, §10.2, §10.5. **Do not point the apex MX at SES.** That would hijack all mail to `opencircuitsf.com`, including human mailboxes. The dedicated `lists.` subdomain is the entire reason this is safe.

SES inbound is region-limited — verify the current inbound-supported region list before committing, and keep the whole project in one region. PRD §10.3 selects `us-west-2`.

This path is the optional one of the three unsubscribe mechanisms. If it proves fiddly, point the `mailto:` at a monitored mailbox and process manually — volume at launch makes that entirely workable.
