## Description

The `workshops` and `workshop_interests` tables backing the public listings, plus the deferred foreign key from campaigns.

## Acceptance criteria

- [x] `workshops` table exactly per PRD §6.2, including `location_note` and `signup_url`
- [x] `workshop_interests` join table with cascade deletes
- [x] Partial index on published workshops by `starts_at DESC`
- [x] `ALTER TABLE email_campaigns ADD CONSTRAINT ... FOREIGN KEY (workshop_id) REFERENCES workshops(id)` — the constraint deferred from #0040
- [x] Slug uniqueness enforced (`slug TEXT UNIQUE NOT NULL`, verified by a rejected duplicate insert)
- [ ] Slug generation from title with a collision suffix — **out of scope for this issue**; see `## Notes`
- [x] Down migration drops cleanly, including the added constraint
- [ ] `go test ./internal/workshops/...` passes against a real database — **no such package exists yet**; see `## Notes`

## Root cause

Not a bug — this is the founding schema for Phase 6, paying off the FK
deferral `#0040`/migration `000017` left as a bare, `REFERENCES`-less
`workshop_id` column on `email_campaigns` so Phase 5 and Phase 6 could ship
independently.

## Fix

Added `migrations/000020_create_workshops.up.sql` / `.down.sql` — the next
free version (`ls migrations/` topped out at `000019`). Follows the style of
`000017_create_campaigns`: `CREATE TABLE` first, then a named
`ALTER TABLE ... ADD CONSTRAINT` CHECK for the enum-ish `status` column,
matching `email_campaigns_status_check` / `subscribers_status_check`.

Schema, exactly per PRD §6.2:

- `workshops` — every column PRD §6.2 lists, including `location_note` and
  `signup_url`; `status` CHECK-constrained to `draft | published | canceled`
  (PRD's comment vocabulary); `idx_workshops_published` partial index on
  `(starts_at DESC) WHERE status = 'published'`.
- `workshop_interests` — composite PK `(workshop_id, interest_id)`,
  `ON DELETE CASCADE` on both FKs (mutation-tested below), plus an index on
  `interest_id` matching `subscriber_interests`' and `campaign_interests`'
  precedent (PRD's own SQL block doesn't show that second index for this
  table, but every sibling join table in the schema carries one for the
  reverse-lookup direction, and there's no reason this one should be the
  exception).
- The deferred FK: `ALTER TABLE email_campaigns ADD CONSTRAINT
  email_campaigns_workshop_id_fkey FOREIGN KEY (workshop_id) REFERENCES
  workshops(id)` — no `ON DELETE` clause, matching PRD §6.2's literal
  `ALTER TABLE` text and the existing `email_campaigns.created_by ->
  users(id)` precedent (also plain, no cascade). A workshop referenced by a
  campaign can't be silently orphaned by a `DELETE`; `#0041` already models
  "cancel", not delete, for campaigns, so this is not expected to bite in
  practice.

**Two criteria are deliberately left unticked, per the phase-2 dispatch's
explicit scope note** ("Do not build the CRUD API, handlers, or UI — those
are #0051+"):

- *Slug generation from title with a collision suffix* is Go application
  logic (a function that runs at workshop-creation time), not something a
  migration can express. The migration's job — enforcing uniqueness once a
  slug is chosen — is done (`slug TEXT UNIQUE NOT NULL`, verified below).
  This is exactly the same split `email_campaigns.slug` follows: `000017`
  only declares `UNIQUE NOT NULL`; nothing in `internal/mailing` generates a
  slug from a title either, because `#0041`'s CRUD layer owns that. `#0051`
  (Build the workshops CRUD API) is where the generator belongs.
- *`go test ./internal/workshops/...` passes against a real database* — no
  `internal/workshops` package exists in this tree yet; it's created by
  `#0051`. There is nothing to run. Said plainly rather than fabricating a
  passing result: this criterion cannot be satisfied by a migration-only
  issue and should be re-verified once `#0051` lands the package.

### Ruling 1 — the FK's missing `ON DELETE` is correct; `#0051` must handle it

Approved as `NO ACTION` (blocking), **not** `ON DELETE SET NULL`, but for a
better reason than the one recorded in `## Fix`. PRD §6.2 contains **no literal
`ALTER TABLE`** for this constraint — only the migration-ordering note's "or the
FK added in a later `ALTER TABLE`" and the `workshop_id` comment "The FK to
workshops(id) is added by #0050". So "matching PRD §6.2's literal `ALTER TABLE`
text" overstates the source. What does decide it: PRD §6.2 writes `ON DELETE SET
NULL` **explicitly** where it wants that behavior — `subscriber_events`'
`subscriber_id`, `campaign_id`, and `import_id` all carry it — so silence on
this FK is a real signal, not an omission. Blocking is also the better failure
mode here: a campaign in the public archive (§6.8) says "this announced workshop
X", and `SET NULL` would silently sever that provenance on a stray delete, while
the block is loud, specific, and reversible. It is also coherent with the
cascade next to it: tags are dependent data, campaigns are independent records.

**Binding on `#0051`:** its `DELETE /admin/workshops/{id}` endpoint must catch
SQLSTATE `23503` on `email_campaigns_workshop_id_fkey` and return a `409` naming
the blocking campaigns, never a bare `500`. `#0051` also already models cancel
rather than delete for the normal case, so this path should be rare. Greenfield
(`CLAUDE.md` §1) means `000020` can still be edited if `#0051` or `#0056` finds a
concrete reason to prefer `SET NULL` — that door is open until first deploy.

### Ruling 2 — `idx_workshop_interests_interest` is justified; its stated precedent is not

Keep the index. The composite PK leads with `workshop_id`, so the reverse
direction (interest → workshops) has no usable index without it, and that is
exactly the direction `#0051`'s interest-filtered listing reads.

But the precedent claimed in `## Fix` — "matching `subscriber_interests`' and
`campaign_interests`' precedent" — is half wrong, and was checked rather than
assumed: `grep` over `migrations/*.up.sql` finds this index shape in exactly two
places, `000010` (`idx_subscriber_interests_interest`) and this migration.
`campaign_interests` in `000017` has **no** `interest_id` index. `subscriber_interests`
alone sets the precedent, and PRD §6.2 shows the index for that table and not for
the other two. That is still enough to justify the index — it is not speculative
— but the sibling set is one table, not two. (`docs/database.md`'s corresponding
sentence names both tables only for the `ON DELETE CASCADE` precedent, which is
accurate.)

### Ruling 3 — both deferrals are correct, but `#0051` does not yet carry the slug criterion

Deferring is right on both counts. Slug generation from a title with a collision
suffix is a runtime function, not something DDL can express; the migration's half
of that criterion (`slug TEXT UNIQUE NOT NULL`) is done and was proved by a
rejected duplicate insert. And `internal/workshops` genuinely does not exist —
saying so plainly beats fabricating a passing test run.

**The gap the orchestrator must close:** `#0051`'s acceptance criteria as written
say nothing about slug generation. Left alone, the deferred criterion falls
through the crack between the two issues. `#0051` needs an explicit criterion —
*generate the slug from the title, with a collision suffix, and cover it with a
test that inserts two workshops of the same title* — plus the `409` mapping from
ruling 1. Re-verify `go test ./internal/workshops/...` at `#0051`'s review.

### Ruling 4 — the `email_campaigns.slug` drift is real, already tracked, and must not be re-filed

Confirmed independently: `information_schema.columns` for `email_campaigns` on a
fully migrated database returns 16 columns and **no `slug`** (also no
`archive_status`/`archived_at`), and `grep slug migrations/*.up.sql` matches only
`000009` and `000020` — `000017` never creates the column. PRD §6.2's prose is
ahead of the schema, exactly as the implementer reported.

It is **not** unowned drift and needs no new issue: open `#0123` (Public campaign
archive, Phase 8) carries it as its first acceptance criterion — "`email_campaigns`
gains `slug TEXT UNIQUE NOT NULL`, `archive_status ...`, `archived_at ...` — added
to `migrations/000017` directly, per the greenfield note". Nothing in `#0050`
depends on the column, and nothing here should anticipate it.
