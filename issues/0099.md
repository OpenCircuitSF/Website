## Description

`#0084` fixed load-induced "context deadline exceeded" flakes from fixed 5s
DB-operation deadlines in `cmd/opencircuit` and `internal/handlers`, unifying
them onto a single documented, load-measured constant (20s in each package).
`internal/auth` was never in that issue's scope, but it carries the identical
defect class — a flat `context.WithTimeout(context.Background(), 5*time.Second)`
repeated across its own test helpers — and it reproduced during #0084's own
`-count=2` verification run:

```
--- FAIL: TestStartRegistration_DisabledReturns403 (5.00s)
    registration_test.go:147: truncate auth tables: timeout: context deadline exceeded
FAIL	github.com/brennanMKE/OpenCircuitSF/internal/auth	271.133s
```

Load average at the time: ~305-321 (`uptime`), the same ambient multi-agent
load #0084's own reproductions used. Re-running the same test targeted passed
immediately (2.96s) — the same "passes alone, fails in the full run under
load" signature #0084 diagnosed, not a real defect in the test.

## Where the deadlines are

At minimum, in `internal/auth`'s own `_test.go` files (grep for `5*time.Second`
turns up entries in `logout_all_test.go`, `login_test.go` (6 sites),
`recovery_test.go` (4 sites), `registration_test.go` (7+ sites) — not
exhaustively catalogued here; that cataloguing is this issue's first step).

## Acceptance criteria

- [ ] Apply #0084's policy to `internal/auth`: a single, documented,
      load-measured constant replacing the scattered flat 5s literals — not a
      blanket raise to a bigger arbitrary number. See #0084's
      `handlersDBOpTimeout` (`internal/handlers/credentials_test.go`) and
      `wiringDBOpTimeout`/`wiringDBConnectTimeout`
      (`cmd/opencircuit/ratelimit_wiring_test.go`) for the established pattern
      and the load-measurement methodology to reuse (or re-measure fresh —
      `internal/auth`'s statements may differ enough from a plain `TRUNCATE`
      to warrant its own numbers).
- [ ] Reproduce first (mutate the new constant back down, show the failure
      under real load, revert) — the same mutation-proof discipline #0084 and
      #0087 both used.
- [ ] `go test ./internal/auth/... -count=2` green under genuine concurrent
      load, with the load average recorded alongside the result.
- [ ] Check whether any other `testdb.Lock()`-using package (`internal/db`,
      `internal/middleware`, `internal/subscribers`, `internal/interests`)
      carries the same pattern. None reproduced a failure during #0084's
      `-count=1`/`-count=2` runs, but they were not specifically stress-tested
      for it either — a quick grep for `5*time.Second`/`10*time.Second`
      literals in each package's test files is enough to decide whether this
      issue's scope should grow to cover them too.

## Closing note — 2026-08-20 (user directive)

Closed by the user's explicit instruction after the cause of the "load" in this
issue was identified.

The load was **not** the website's traffic and not a performance requirement.
It was the CPU load average of the developer's laptop, produced by a single
orchestrator session (`4f1ef351`, ~25 hours, 197 subagents) running full
DB-backed Go suites concurrently, several in separate git worktrees that each
recompiled from scratch. Load averages of 240-320 were recorded in these issues
as "real ambient load" and treated as the baseline to design against.

They are not a baseline. They are the bug. A `TRUNCATE` against a local
Postgres with no contention completes in milliseconds; it only took 1.3-3.9s
because ~200 agents were competing for the same CPU and the same database.

Widening test deadlines to accommodate self-inflicted machine load was the wrong
fix for a marketing site with a mailing list. The correct fix -- capping agent
concurrency and scoping test runs -- is now in CLAUDE.md §5 and §5a.

**Do not reopen this, and do not file follow-ons that propose extending the
timeout policy to further packages.** If a test times out, first check
`uptime`; if the load average is above ~8, the machine is the problem, not the
deadline.
