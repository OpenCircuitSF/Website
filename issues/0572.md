## Acceptance criteria (from the review, §6 C; refreshed 2026-11-17)

Already done before this pass, by `#0583`/`#0601`: the admin Mastodon preview
(`web/src/views/admin/OutreachMastodonPreview.svelte`) draws the attachment
with an ALT badge, or "No image: alt text missing", as soon as the workshop
view carries `cover_alt`; `WorkshopOutreach.workshop.cover_alt` is already in
`web/src/lib/types.ts`. Nothing on the server sends it yet.

- `mastodon.Client.UploadMedia(ctx, data, mime, altText)` posts multipart to
  `/api/v2/media` (`file`, `description`), handles a `202` by polling
  `GET /api/v1/media/:id` (`206` = still processing, `200` = ready) within a
  bounded budget, and returns the media id; the token never appears in an
  error or a log line. `PostStatus` can carry `media_ids`.
- `workshops` gains `cover_alt` (migration `000058`, `ALTER TABLE`, at most
  1500 characters, the Mastodon description limit); the workshop editor has an
  "Image description (alt text)" field under the cover. Changing or clearing
  the cover without sending new alt text clears the old alt text.
- `postMastodon` attaches the cover when the cover bytes load (the same rules
  and bytes as the Bluesky `thumbnail`) **and** `cover_alt` is non-empty;
  otherwise it posts text only and records a visible notice on the card
  (`last_error` on the posted row, e.g. "Posted without image: no alt text.").
  An upload failure also posts text only, with a notice. No cover, no notice.
- The Bluesky card continues to use the thumbnail; a later issue may switch
  Bluesky to an `app.bsky.embed.images` post when the operator prefers an
  image over a card.
- v1 (`#0695`): `create_event` and `update_event` accept `cover_alt`,
  `get_event` returns it, and `duplicate_event` copies it.
- `httptest` tests for upload, processing poll, and the no-alt-text refusal.

### 4. Mastodon client, `internal/mastodon/client.go`

- New `UploadMedia(ctx, data []byte, mime, altText string) (string, error)`:
  - nil client → the same permanent `ErrAuth` APIError as `PostStatus`;
    empty `data` or blank `altText` → permanent `ErrInvalid` APIError,

  - Body: `mime/multipart` with a `file` part (filename `cover.jpg` or

    `ctx.Done()`, return `ctx.Err()` wrapped as
    `fmt.Errorf("mastodon: media %s still processing: %w", id, err)`), then
    `GET {base}/api/v1/media/{id}`: `206` → keep polling, `200` → return id,
    anything else → `c.apiError`. Bound by the caller's ctx only.

**The defect: the workshop editor defeats "changing the cover clears the old
alt text".** The server rule in `patchWorkshop` clears `cover_alt` only when
the PATCH does not send `cover_alt`. The editor always sends it
(`ValidatedWorkshopFields.cover_alt`, "always sent"), and nothing in
`WorkshopEditor.svelte` resets `fields.coverAlt` when the cover changes. So an
admin who uploads a new cover (`handleCoverImageFileChange` sets only
`fields.coverImage`) or types a new path, then presses Save, sends the old
picture's description with the new picture, and the server keeps it. The next
Mastodon post then goes out with alt text that describes a different image.
That is the editor, which is the usual way to change a cover, so the criterion
fails. The v1 and admin API paths are right.

**Remedy (apply as written):**

1. `web/src/lib/workshopAdmin.ts`: export a pure helper
   `coverAltForSave(original: { cover_image?: string | null; cover_alt?: string | null } | null, validated: { cover_image: string; cover_alt: string }): string`.
   It returns `''` when `validated.cover_image` differs from
   `(original?.cover_image ?? '').trim()` **and** `validated.cover_alt` equals
   `(original?.cover_alt ?? '').trim()`. Otherwise it returns
   `validated.cover_alt`. So a new cover with the old alt text clears the alt
   text, and a new cover with new alt text keeps the new text.
2. `WorkshopEditor.svelte` `save()`: after `validateWorkshopForm`, send
   `cover_alt: coverAltForSave(workshop, validated)` instead of
   `validated.cover_alt`. Also set `fields.coverAlt = ''` in
