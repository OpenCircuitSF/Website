## Description

`email_sends.status` allows `'bounced'` and `'complained'`, and PRD §6.2 documents both, but no code path writes either. SES bounce and complaint events land in `email_events` only. The two values are unreachable, so the schema and the PRD describe states that cannot occur.

## Acceptance criteria

- [ ] Decide which way this resolves — the two options are genuinely different products, not two spellings of one fix:
      - **(a) Make them reachable.** `#0038`'s ingestion also stamps `email_sends.status` when an event reconciles to a send row. Per-campaign outcome then reads from one column, and `#0049`'s reconciliation JOIN becomes a consistency check rather than the source of truth.
      - **(b) Drop them.** Remove both from the CHECK, strike them from PRD §6.2, and let `email_events` remain the sole record of what SES said. `#0049`'s JOIN stays the source of truth.
- [ ] Whichever is chosen, the CHECK constraint, PRD §6.2's comment, and `docs/database.md` agree with each other and with the code
- [ ] `#0049`'s `campaign_stats.go` and its tests are updated to match, including the test that currently asserts the raw buckets are 0
- [ ] If (a): the stamping is idempotent under SNS's at-least-once delivery, and a bounce arriving for a row already `sent` does not corrupt the send-outcome counts
- [ ] If (b): a migration drops and re-adds the CHECK (Postgres has no ALTER-in-place form), and the greenfield note in PRD §6.2 is respected — edit `000017` directly rather than stacking, while that is still allowed

## Notes

Found by `#0049`'s phase-3 review, which enumerated every writer of `email_sends.status` rather than inferring from a grep: `queued` (audience INSERT, `worker_store.go:268`/`422`), `sending` (`ClaimRow`), `sent` (`MarkSent`), `failed` (`MarkFailedRow`/`MarkRetryOrFailed`), `skipped` (`MarkSkippedTx`). That is the complete set. `internal/sesnotify` writes only to `email_events`.

**This is not urgent and `#0049` is not wrong.** The stats view reconciles from `email_events` and is correct today; its test asserting the raw buckets are 0 *in the same test that proves the reconciled figures are right* is the correct guard shape and should survive whichever option wins.

**Option (b) is the smaller change and probably the right default.** `email_events` is already the append-only record of what SES said, and PRD §6.11 (Phase 8) makes `subscriber_events` the address-level log — a third place recording the same fact invites the three from drifting. But (a) has a real argument: a per-recipient outcome column is what an operator drilling into a campaign actually wants, and a JOIN across two tables to answer "did this person get it?" is the kind of thing that gets written wrong later. Decide deliberately.

**One consequence worth knowing before choosing.** Under (b), with real bounce data the `Bounced` and `Complained` buckets are a *subset* of `Sent` rather than siblings of it, so the buckets will not sum to the total recipient count shown above them. Accurate, but confusing, and not observable until there is real SES volume. Under (a) they would be mutually exclusive and would sum.
