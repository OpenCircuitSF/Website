## Description

`email_sends.status` allows `'bounced'` and `'complained'`, and PRD §6.2 documents both, but no code path writes either. SES bounce and complaint events land in `email_events` only. The two values are unreachable, so the schema and the PRD describe states that cannot occur.

## Root cause

`migrations/000017` (`#0040`, carried in from `#0044`'s plan) copied the six-value `email_sends.status` vocabulary — `queued | sent | failed | bounced | complained | skipped` — straight from an early PRD §6.2 draft without checking who would actually write `'bounced'`/`'complained'`. Nobody ever did: `internal/sesnotify`'s SES/SNS event ingestion (`#0038`) records every bounce/complaint notification exclusively in `email_events`, and `#0049`'s per-campaign stats view (built afterward) already reconciles those two figures with a JOIN against `email_events` on `ses_message_id` rather than trusting the column — because reading the raw bucket would always report zero. `migrations/000018` (`#0045`) then widened the same CHECK to add `'sending'` and carried `'bounced'`/`'complained'` forward unexamined. `#0049`'s phase-3 review enumerated every writer of `email_sends.status` from scratch and confirmed the two values are unreachable, filing this issue.

## Fix

**Option (b) — drop them — chosen by the orchestrator**, not re-litigated here per this issue's dispatch instructions. Rationale: `email_events` is already the append-only record of what SES said (`#0038`), and PRD §6.11 (Phase 8) makes `subscriber_events` the address-level log — a third place recording the same fact (a stamped `email_sends.status`) invites the three to drift out of sync with each other. `#0049`'s reconciliation JOIN already does the right thing and stays the source of truth; option (a) would have made it merely a consistency check, at the cost of idempotent-stamping logic under SNS's at-least-once delivery that nothing in this codebase currently needs.

Concretely:

- `migrations/000017_create_campaigns.up.sql`: removed `'bounced'`/`'complained'` from `email_sends_status_check` and its preceding comment, edited in place — the project is still greenfield (`CLAUDE.md` §1), and `000017` is the migration that owns the `email_sends` table.
- `migrations/000018_add_campaign_send_state.up.sql`/`.down.sql`: `000018` drops and re-adds this same CHECK to widen it for `'sending'`, so both its `up.sql` (the widened list) and `down.sql` (the list it reverts to) needed the same removal to stay consistent with `000017`'s edited version — otherwise a rollback of `000018` would have re-admitted the two dropped values.
- `PRD.md` §6.2 and `docs/database.md`'s `000017_create_campaigns` row updated to match the new five-value vocabulary (`queued | sending | sent | failed | skipped`).
- `internal/mailing/campaign_stats.go`: package doc, `CampaignSendCounts`' doc comment, and `StatusCounts`' doc comment rewritten. `CampaignSendCounts.Bounced`/`.Complained` and the JSON response's `bounced`/`complained` fields were deliberately **kept**, not removed — the response shape (and `web/src/lib/campaignStats.ts`'s reconciled-substitution logic reading `stats.counts.bounced` in `totalSendRows`) stays stable, and the two fields now read zero by database-enforced construction rather than merely because nothing writes them.
- `internal/handlers/admin_campaign_stats_test.go`: `TestAdminCampaignStats_BucketsAllSevenStatuses` renamed to `TestAdminCampaignStats_BucketsAllValidStatuses` and no longer seeds `'bounced'`/`'complained'` rows via direct `INSERT` — the CHECK now rejects them, so the old seeding would fail every run. `TestAdminCampaignStats_ReconcilesBounceAndComplaintFromEvents`'s guard that the raw `counts.bounced`/`.complained` read `0` was kept exactly as the issue instructed — it is still the load-bearing proof that the reconciled figures come from `email_events`, not a passthrough.
- Ride-along doc corrections (all as specified in the checklist above): the `000014` → `000017`/`000018` migration citation in `campaign_stats.go`'s package doc and `issues/0049.md`'s `## Gotchas`; the `campaignStats.ts` comment about NULL/`omitempty` (also mirrored a wrong copy of the same claim in `web/src/lib/types.ts`, fixed too since it repeats the identical inaccuracy); and `issues/0049.md`'s carried-in criterion wrongly claiming `CampaignStats.svelte` has no `.length >`.

## Notes

Found by `#0049`'s phase-3 review, which enumerated every writer of `email_sends.status` rather than inferring from a grep: `queued` (audience INSERT, `worker_store.go:268`/`422`), `sending` (`ClaimRow`), `sent` (`MarkSent`), `failed` (`MarkFailedRow`/`MarkRetryOrFailed`), `skipped` (`MarkSkippedTx`). That is the complete set. `internal/sesnotify` writes only to `email_events`.

**This is not urgent and `#0049` is not wrong.** The stats view reconciles from `email_events` and is correct today; its test asserting the raw buckets are 0 *in the same test that proves the reconciled figures are right* is the correct guard shape and should survive whichever option wins.

**Option (b) is the smaller change and probably the right default.** `email_events` is already the append-only record of what SES said, and PRD §6.11 (Phase 8) makes `subscriber_events` the address-level log — a third place recording the same fact invites the three from drifting. But (a) has a real argument: a per-recipient outcome column is what an operator drilling into a campaign actually wants, and a JOIN across two tables to answer "did this person get it?" is the kind of thing that gets written wrong later. Decide deliberately.

**One consequence worth knowing before choosing.** Under (b), with real bounce data the `Bounced` and `Complained` buckets are a *subset* of `Sent` rather than siblings of it, so the buckets will not sum to the total recipient count shown above them. Accurate, but confusing, and not observable until there is real SES volume. Under (a) they would be mutually exclusive and would sum.

## Gotchas

- Editing a migration in place does **not** bump the highest migration number, so `scripts/testdb.sh create` compares version numbers only and would not have noticed the template was stale — it would have silently kept serving the old six-value CHECK to every new per-issue test database. `scripts/testdb.sh template` must be run by hand after any in-place migration edit; this is now the second time this exact pattern has mattered (see `CLAUDE.md` §5a's own note on `testdb.sh`).
- The direct-insert test fixture (`seedEmailSendRow`) is what actually breaks under this change, not any handler or store code — `TestAdminCampaignStats_BucketsAllSevenStatuses` bypassed the send worker entirely to seed a `'bounced'` row, which is exactly the kind of test that silently starts failing (constraint violation on `INSERT`, not a logic assertion) when a CHECK is tightened. Worth checking for elsewhere: `grep -rn "'bounced'\|'complained'" **/*_test.go` turned up nothing else inserting either value directly into `email_sends`.

**On keeping `Bounced`/`Complained` as always-zero response fields — reviewed
deliberately, and approved.** The concern is real in the abstract: an API field
that is now structurally incapable of being nonzero is the same shape of defect
as a CHECK value nothing writes, one layer up. Three things settle it the other
way here:

1. **Nothing renders a bucket that can only be zero.**
   `web/src/lib/campaignStats.ts`'s `buildStatBuckets` sources the `bounced`
   and `complained` buckets from `stats.reconciled`, never from
   `stats.counts` — checked in the file, not inferred. The only other reader is
   `totalSendRows`, which sums all seven `counts` fields; adding two guaranteed
   zeros is harmless *and* correct, since summing the reconciled figures there
   would double-count (they are a subset of `sent`, per this issue's own
   `## Notes`).
2. **This issue explicitly asked for the guard to survive.** `## Notes` says the
   test asserting the raw buckets read `0` "is the correct guard shape and
   should survive whichever option wins" — and that guard cannot exist without
   the fields. Removing them would have been the deviation, not keeping them.
3. **The trap is now documented at every layer** — `campaign_stats.go`'s package
   doc and both struct comments, `types.ts`, and `campaignStats.ts` all say the
   two read zero and why, and `TestAdminCampaignStats_BucketsAllValidStatuses`
   now carries its own explicit zero assertion in addition to the reconciliation
   test's.

Whether the endpoint should eventually stop shipping two structurally-zero
fields is a separate API-shape question at a different layer; it is not a defect
in this issue's execution and would contradict this issue's stated intent for
the guard.
