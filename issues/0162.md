## Description

`#0151`'s hint — *"Unsaved interest changes are not included — save first."* — inherits `class="text-muted"` from the paragraph it is appended to. So the one sentence in that panel most likely to change an admin's next action renders in the same de-emphasised grey as the surrounding explanation of what the button does.

`#0143`'s targeting sentence has the same treatment, and it carries the same weight: it is what tells an admin the draft will go to **everyone** rather than to a segment.

Both are correct, both are easy to skim past.

## Acceptance criteria

- [x] The unsaved-changes hint is visually distinguished from the surrounding explanatory copy — a warning-styled element, not muted body text
- [x] Consider the same for `#0143`'s "will target everyone on the list" sentence, which is the higher-stakes of the two. Decide whether one, both, or neither should change, and record the reasoning

- [x] Consider `role="status"` or an equivalent so the hint is announced when it appears, since it appears in response to an action rather than on load. Note `#0063` (accessibility audit) owns the console-wide version of this question — do not build a bespoke pattern here that it would then have to undo
- [x] `scripts/check.sh web` passes

## Root cause

`#0151` appended its unsaved-changes hint to the end of the Announce panel's
single `<p class="text-muted">` paragraph as a string fragment
(`announceUnsavedInterestsHint`'s old return value carried a leading space
so it could be concatenated inline), so it inherited that paragraph's muted
styling. `#0143`'s "targets everyone" sentence lived in the same paragraph
for the same reason. Neither had any element boundary of its own to carry a
different style.

## Fix

- Two judgment calls, both applied (not "one, both, or neither" left as a
  choice — both sentences are warnings, and leaving the higher-stakes one
  (`#0143`'s) muted while elevating the lesser one would have produced an
  inconsistent hierarchy):
  - **The unsaved-interests hint** (`#0151`) is now its own paragraph:
    `<p class="text-warn" role="status">`. `.text-warn` is the console's
    existing warning treatment (`app.css`, already used by `Admin.svelte`'s
    slug-format hint and its interest-deactivation notice) — no new styling
    invented. `role="status"` matches those same two existing uses: this
    hint appears and disappears purely in response to the admin checking/
    unchecking interest boxes on this screen, i.e. dynamically, in response
    to an action, which is exactly what `role="status"` is for.
  - **The targeting sentence** (`#0143`) is now its own paragraph too, with
    a new `announceTargetingClass(interestIds)` helper choosing
    `.text-warn` when the workshop has no saved interests (the "targets
    everyone" case — the higher-stakes state) and `.text-muted` otherwise.
    Deliberately **no** `role="status"` here: unlike the unsaved-interests
    hint, this sentence describes the workshop's already-loaded, saved
    state — it is present the instant the panel first renders, not
    something that newly appears in response to an in-page action, so
    there is nothing for `role="status"` to announce. Adding it anyway
    would have been the "bespoke pattern" this issue explicitly says not to
    build ahead of `#0063`.
- `announceUnsavedInterestsHint`'s return value no longer carries a leading
  space (it's a standalone paragraph now, not appended text) — its doc
  comment in `workshopAdmin.ts` explains why.
- Decision logic lives in `web/src/lib/workshopAdmin.ts`
  (`announceTargetingClass`, new); `WorkshopEditor.svelte` only renders the
  class/text the module hands it, per `CLAUDE.md`'s "SPA logic in
  `web/src/lib/`" rule.

### Ruling 1 — the `role="status"` split: accepted

The precedent claim was checked, not taken on trust. `Admin.svelte:1283` is
inside `{#if newSlugInvalid}` (appears while the admin types a slug) and
`:1451` inside `{#if editDeactivating}` (appears when the admin ticks the
Active checkbox). Both are `<p class="text-warn" role="status">`,
conditionally rendered, triggered by an in-page action. The new hint is the
same element, the same trigger class (interest checkboxes) — no bespoke
pattern.

Withholding it from the targeting sentence is right, and for a stronger
reason than the one recorded: a live region whose content is already present
when it first renders is *not* announced by design, so `role="status"` there
would either do nothing or — on mount insertion — announce the panel's
ordinary state on every load. That is noise, not access.

Confirmed in the built bundle that the split did not disturb `#0143`/`#0151`'s
settled saved-vs-buffer separation: the targeting paragraph's two thunks
compile to `()=>ol(um(r(a).interest_ids))` (the class) and
`()=>lm(r(a).interest_ids)` (the text), where `a` is the `workshop` rune —
both read **saved** state only; the `fields` buffer still reaches the hint and
nothing else.

**Console-wide weakness, deliberately not fixed here.** Every `role="status"`
in this console — this hint, both `Admin.svelte` precedents, and `#0167`'s new
cue — is created and populated in the same tick by an `{#if}`. Screen-reader
support for announcing a live region that is inserted with its content already
in it is inconsistent; the robust pattern is a region present from first
render whose text swaps. That is exactly the console-wide question `#0063`
owns, and criterion 4 forbade pre-empting it with a bespoke pattern here.
Reported to the orchestrator per `CLAUDE.md` §9 rather than filed.

### Ruling 2 — elevating both sentences: accepted

Criterion 2 asked for a decision either way with the reasoning recorded, and
both is the defensible one: warning the lesser sentence while leaving "targets
everyone" muted would have inverted the hierarchy. Making the targeting
sentence *conditional* (`.text-warn` only in the no-interests case,
`.text-muted` otherwise) is better than a blanket warn — the targeted case is
the ordinary one, and warning it would dilute the signal until neither
sentence carries any.

`announceTargetingClass`'s condition is byte-identical to
`announceTargetingDescription`'s (`interestIds.length === 0`), so the class
and the sentence cannot disagree. Probed for `#0151`'s `[0]`-vs-`[]` trap
against the real module: `announceTargetingClass([0])` → `text-muted`,
matching `announceTargetingDescription([0])`'s targeted sentence — the check
is on `.length`, never on falsiness, so an interest id of `0` behaves like any
other id.

### Copy nit, not blocking

The base paragraph now ends with "Nothing is sent — review and send the draft
from the Campaigns tab.", so the targeted-case sentence "It will be targeted
at this workshop's interests." opens a paragraph whose antecedent sits two
sentences back. It still resolves ("the draft"), and putting both warnings
immediately above the Announce button is a defensible ordering — but "The
draft will be targeted…" would be one word better. Worth folding into `#0063`
or any later copy pass that touches this panel; not worth a commit of its own.
