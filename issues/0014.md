## Description

Replace the `currentView` store navigation with real URL routing. Public pages get shared and indexed, so `/workshops/soldering-101` has to be an actual address.

## Acceptance criteria

- [x] `web/src/lib/router.ts` parses `window.location.pathname` into a typed `Route` union — *verified at review 2026-08-18*
- [x] Same-origin `<a>` clicks are intercepted and pushed with `pushState`; modified clicks (cmd/ctrl/shift, `target=_blank`, external hosts) fall through to the browser — *verified at review: a plain nav click produced zero navigation requests and changed the address bar; a cmd-click opened a second tab and left the current page's URL alone*
- [x] `popstate` restores the correct route on back/forward — *verified at review: back from `/workshops` re-rendered About at `/about`, forward re-rendered Workshops, both without a document load*
- [x] One path parameter supported: `/workshops/:slug` — *verified at review*
- [x] Unmatched paths resolve to a `not-found` route — *verified at review*
- [x] Query parameters are parsed and exposed (needed by `/confirm?token=`, `/preferences?token=`) — *verified at review: `/confirm?token=abc123&x=1` routed to `confirm` with the query preserved*
- [ ] Scroll position resets to top on navigation, except on back/forward where it restores
      — *the restore half is now fully met by `243abad` and independently
      re-verified at review 2026-08-18 (third pass) in a real headless Chromium
      (1280×800) against the Go binary serving the production build: **Back**
      restores (three entries deep), **Forward** restores a non-zero offset
      (500), and the **cross-document** `pagehide` → init-restore path restores
      (546), as does a plain reload. The **reset-to-top** half now has a hole
      the earlier passes did not: a `restoreScroll()` retry loop still in flight
      when the user navigates is never cancelled, so it scrolls the
      freshly-pushed page to the *previous* entry's offset and stamps that bogus
      value into the new entry's state. Reproduced live — see `## Review notes`,
      defect 3, for the transcript and the verified fix.*
- [x] No routing library added — the implementation is plain TypeScript, roughly 60 lines — *verified at review: no dependency added; `router.ts` is 235 lines of which ~85 are code, the rest rationale comments*
- [x] Unit tests cover path parsing, param extraction, and the click-interception predicate

## Root cause

Not a bug fix — this is the deliberate architectural departure from ShortLinks
that PRD §3.4 calls for. ShortLinks' `currentView` store had no concept of a
URL at all; a signed-in dashboard doesn't need one, but marketing pages that
get shared on Discord/social and need to be indexable absolutely do.

## Fix

Added `web/src/lib/router.ts`: `parsePath(pathname, search)` parses a path into
a typed `Route` (`{ name, path, params, query }`) against a static route table
mirroring PRD §5.1 plus the Phase 1 auth routes, with one dynamic pattern
(`/workshops/:slug`). `shouldIntercept(candidate)` is the click-interception
predicate, factored out as a pure function over a plain `InterceptCandidate`
object (button/modifier keys/target/download/href/origin) rather than a real
`MouseEvent`, so it is unit-testable without a DOM. `navigate(path, opts)`
push/replace-state's, updates the `currentRoute` store, and resets scroll.
`initRouter()` is the only DOM-touching piece — it wires a document-level click
listener and a `popstate` listener and is idempotent.

`currentView` and its `View` type were removed from `stores.ts` entirely (not
just unused) — the issue calls for retiring it as a navigation mechanism, and
leaving it in place as dead code some file could still import would recreate
exactly the divergence the issue is fixing. `pendingVerifyToken` and
`currentUser` stay, since those are genuinely transient UI/session state, not
navigation.

Every existing consumer of `currentView` was migrated in the same commit
(broader than a narrow reading of the acceptance criteria, but retiring the
store while five views still imported it would fail `npm run check`/`vite
build` on the missing export): `App.svelte`'s onMount now reads the
already-parsed `currentRoute` to detect the
register-verify/recover-verify magic-link landings (same behavior as before:
capture `?token=`, strip it via a replace-navigation, skip the `/api/me`
probe) and otherwise calls `getMe()` unconditionally to populate `currentUser`
for every other route. `Login.svelte`, `Account.svelte`, `Admin.svelte`,
`RegisterVerify.svelte`, and `RecoverVerify.svelte` had their
`currentView.set(...)` navigation calls replaced with `navigate('/...')` and
their `$currentView === 'login'` read replaced with `$currentRoute.name ===
'login'`.

Public marketing routes (home/about/workshops/subscribe/confirm/preferences/
unsubscribe) currently render a one-line placeholder naming the route in
`App.svelte`'s catch-all branch — intentional for this commit, so the router
is independently buildable/testable before `Home`/`About`/`NotFound` exist.
`#0017` adds the header/footer shell and `#0015`/`#0016`/`#0022` replace the
placeholder with real views for `home`/`about`/`not-found` in the following
commits; the remaining routes stay placeholders until their own later-phase
issues (`#0029`–`#0036`, `#0053`–`#0054`).

### `f8d1f09` — scroll restoration (bounce fix)

Reviewed at 2026-08-18 (phase 3) and bounced: the reset-to-top half worked but
back/forward did not restore scroll, because the browser's own
`history.scrollRestoration = 'auto'` fires on `popstate` before Svelte has
re-rendered the restored view, so it restores against the *outgoing* view's
(shorter) DOM and clamps to 0. Fixed exactly per the reviewer's prescription
in `## Review notes`:

1. `initRouter()` now sets `history.scrollRestoration = 'manual'`
   (feature-detected via `'scrollRestoration' in window.history`) so the
   browser never attempts — and loses — that race in the first place.
2. `navigate()` calls a new `saveScrollToCurrentEntry()` helper, which
   `replaceState`s the *outgoing* history entry's state with
   `{ scrollY: window.scrollY }` immediately before every `pushState`/
   `replaceState` it performs. The new entry itself is stamped
   `{ scrollY: 0 }`, matching the reset-to-top behavior for forward
   navigation. The same helper is wired to `pagehide` in `initRouter()`, to
   cover leaving the SPA without going through `navigate()` at all (a
   same-tab navigation away and back).
3. The `popstate` handler reads `event.state.scrollY` (defaulting to `0` if
   absent, e.g. the very first history entry) and applies it with
   `window.scrollTo(0, saved)` only after `await tick()` — giving Svelte's
   reactive `{#if $currentRoute.name === ...}` block in `App.svelte` a chance
   to swap in the restored view's markup first, so the page actually has the
   height to scroll to.

No routing library added, no change to `parsePath`/`shouldIntercept`/the
route table — additive to `navigate()`/`initRouter()` only, as scoped.

### `243abad` — Forward restoration and the cross-document read (second bounce fix)

Bounced a second time for two blocking defects (`## Review notes`, defect 1 and
defect 2). Both are fixed in `web/src/lib/router.ts`, additively — no change to
`parsePath`/`shouldIntercept`/the route table, no other file touched.

**Defect 1 — Forward replayed a stale offset.** `saveScrollToCurrentEntry()`
ran from exactly two places, `navigate()` and `pagehide`, and neither fires
when an entry is left by a *history traversal*. An entry entered by `pushState`
therefore kept the `{ scrollY: 0 }` it was stamped with at push time for as
long as the user only ever left it with Back/Forward, and Forward replayed that
stale `0`. Fixed exactly as prescribed: `initRouter()` now registers a passive,
throttled `scroll` listener that stamps the *current* entry continuously, so
whatever the user is looking at is already recorded before any traversal
begins. Stamping inside `popstate` is not an option and was not attempted — by
the time `popstate` fires the traversal has committed and `replaceState` would
write the *incoming* entry.

**Defect 2 — the `pagehide` save was write-only.** `scrollRestoration =
'manual'` turns off the browser's native restoration for *every* traversal, not
just the same-document ones `popstate` covers, and `popstate` does not fire on
a fresh document load — so the offset `pagehide` wrote was never read back, and
a cross-document Back landed at the top of a page the user had scrolled halfway
down (a net regression against the pre-`f8d1f09` `'auto'` behavior on that one
path). `initRouter()` now reads `window.history.state?.scrollY` on init and, if
it is a number greater than zero, applies it through the same restore path the
`popstate` handler uses. The `> 0` guard is deliberate: forcing
`scrollTo(0, 0)` would fight a browser that *did* restore natively via bfcache
on the same load.

Supporting changes, all in service of the two above:

1. **Throttle.** `SCROLL_SAVE_INTERVAL_MS = 400`, a wall-clock
   leading+trailing throttle — deliberately **not** `requestAnimationFrame`
   coalescing. See `## Gotchas` for the measurement and the reasoning.
2. **`saveScrollToCurrentEntry()` now cancels any pending throttled save and
   re-arms the throttle window** before it writes. Without that, a trailing
   timer armed on the outgoing page fires *after* `navigate()`'s `pushState`
   and stamps the freshly-pushed entry with the outgoing page's offset. The
   `popstate` handler cancels the pending save for the same reason.
3. **`restoreScroll(saved)`** is factored out and shared by the `popstate`
   handler and the new init restore. It still waits `await tick()` first, but
   then re-applies the offset across animation frames until either the offset
   sticks, the user scrolls (detected by the scroll position differing from the
   value the previous frame wrote), or a 1 s deadline elapses. This is what
   makes defect 2's fix actually work: `App.svelte` renders a zero-height
   `Loading…` placeholder until `GET /api/me` settles, so a single `tick()` on
   a fresh document load clamps the restore to `0` against a page with no
   height yet. A `restoreToken` counter makes a superseded restore stop
   re-applying.
4. **A `restoringScroll` flag** suppresses stamping while a restore is in
   flight, so the programmatic `scrollTo` performing the restore — and any
   mid-traversal clamp against the outgoing document's height — cannot write a
   bogus offset onto the incoming entry.
5. **`replaceState` is wrapped in `try`/`catch`.** Safari rate-limits it and
   throws a `SecurityError` past the limit; the throttle is sized well under
   that, but silently dropping one scroll stamp beats an uncaught exception out
   of a scroll handler.

**(This pass, second bounce fix.)** *Throttling strategy, and why not rAF.*
The `scroll` listener uses a **wall-clock leading+trailing throttle at 400 ms**,
not `requestAnimationFrame` coalescing. rAF coalescing sounds like the natural
choice for a scroll handler, but it still yields one `replaceState` per
animation frame — ~60 per second. Safari has historically rate-limited
`history.replaceState` to roughly 100 calls per 30 seconds and throws a
`SecurityError` past the limit, so rAF would be ~18× over it, and would hammer
the history API in every browser for no benefit. 400 ms caps it at 2.5
writes/second; instrumenting `History.prototype.replaceState` and scrolling
continuously for 10 s in a real Chromium measured **26 calls, i.e. 78 per 30
seconds** — under the limit with ~22% headroom. The leading edge stamps
immediately when scrolling starts after an idle period so a quick flick-and-Back
is still captured; the trailing edge guarantees the final resting offset is
recorded once scrolling stops, which is the value that actually matters. The
call is additionally wrapped in `try`/`catch`: dropping one scroll stamp is a
much better failure mode than an uncaught exception out of a scroll handler.

**A pending trailing save will corrupt the wrong history entry if you let it.**
This is the sharp edge of throttling here, and it is not obvious. A trailing
timer armed while the user was on page A fires ~400 ms later — by which time a
`pushState` may have moved the current entry to page B, and `replaceState`
always writes *the current entry*. The result is page B stamped with page A's
scroll offset. `saveScrollToCurrentEntry()` therefore cancels any pending
timer before writing (so `navigate()`'s explicit save disarms it), and the
`popstate` handler cancels it too. Same reason the fix could not simply stamp
from inside `popstate`: by then the traversal has committed and the write lands
on the incoming entry.

**One `await tick()` is not enough on a fresh document load.** Defect 2's fix
initially looked correct and still restored `0`. The cause is `App.svelte`:
it renders a zero-height `Loading…` placeholder until `GET /api/me` settles, so
at `initRouter()` time — and one `tick()` later — the document has no height
and `window.scrollTo(0, 546)` clamps to `0`, with nothing to move it afterwards.
This is the same failure shape as the browser's own `'auto'` restoration losing
the race, one layer up. `restoreScroll()` now re-applies across animation frames
until the offset sticks, bailing out if the scroll position differs from what it
wrote on the previous frame (that means the user is scrolling, and fighting them
would be worse than landing short) or after 1 s. The `popstate` path never
needed this — by then `sessionChecked` is long since true — but it shares the
helper, which incidentally softens (does **not** retire) the Phase 6 warning for
`#0054`.

**Restoring `> 0` only, on purpose.** The init restore skips a saved offset of
`0` rather than calling `scrollTo(0, 0)`. Real Chrome and Safari often restore
cross-document scroll via bfcache regardless of `scrollRestoration = 'manual'`;
unconditionally forcing `0` would undo that. Headless CDP disables bfcache,
which is why the defect was visible to the reviewer at all and invisible in a
normal desktop browser.

**Playwright's `page.click()` remains the wrong tool** — the trap documented by
the previous pass and confirmed again here. Its actionability check auto-scrolls
the target into view before dispatching, which zeroes `window.scrollY` before
`router.ts`'s handler runs on a page with a non-sticky header, producing a false
failure indistinguishable from the bug. Every click in this pass's proof is
dispatched in-page via `el.dispatchEvent(new MouseEvent('click', { bubbles:
true, cancelable: true, button: 0 }))`.

**A Forward assertion that does not scroll the forward entry first proves
nothing** — `expect 0` is satisfied by a handler that restores nothing at all,
which is how the previous pass shipped green with Forward broken. Section A of
the proof scrolls `/about` to 500 before Backing, so the Forward check has a
non-zero value to be wrong about.

**`--window-size` was not used** (`CLAUDE.md` §8): the browser is sized with
`newPage({ viewport: { width: 1280, height: 800 } })`. Also note the proof's
scroll targets are clamped by real page geometry — home is 1346 px tall in an
800 px viewport, so its maximum `scrollY` is 546. An early draft of the proof
asserted 700 on home and "failed" purely because the browser clamped it; check

### Defect 3 — a restore left in flight scrolls the *next* page (blocking)

`restoreScroll()` re-applies its offset across animation frames for up to
`RESTORE_DEADLINE_MS` (1 s). Nothing cancels that loop when the user navigates
during it. `navigate()` does not bump `restoreToken` and does not clear
`restoringScroll`, so after its `pushState` + `scrollTo(0, 0)` the still-live
loop sees `window.scrollY === applied` (both 0, so its user-scrolled bail-out
does not trip), keeps calling `window.scrollTo(0, saved)`, and the moment the
new view renders tall enough it yanks the freshly-pushed page down to the
*previous* entry's offset. The scroll listener then stamps that bogus offset
into the new entry's state, so it persists into every later traversal.

Reproduced live against the unmutated `243abad` build. `GET /api/me` was held
for 700 ms (`page.route`) so `App.svelte` stays on its `Loading…` placeholder —
exactly the condition the retry loop was added for. Cross-document Back into
`/` (saved 546), then a same-origin link click 150 ms into the load:

```
=========== J. restore loop + navigation during it ===========
  body height during Loading… = 209        (viewport 800 -> maxScroll 0, restore clamps, loop spins)
  path after in-window click = /about
  scrollY immediately after click = 0      (navigate() did reset to top, correctly)
PASS  J1 path is /about after the in-window nav: got "/about"
FAIL  J2 freshly pushed entry is NOT scrolled by the stale restore loop: got 545, expected 0
FAIL  J3 pushed entry state not corrupted: got 545, expected 0
```

This violates the first half of the acceptance criterion — "scroll position
resets to top on navigation" — and it corrupts `history.state`, so the damage
outlives the moment.

Mutation 2 (init restore removed) turns J2/J3 green, which pins the cause on
the restore loop specifically rather than on the scroll listener.

**Reachability.** Narrow today, routine tomorrow. Today it needs a slow
`GET /api/me` and a click inside that window, and the only links on screen
during `Loading…` are `Footer.svelte`'s `/privacy` and `/login` — real, since
`Footer` renders outside App.svelte's `{#if !sessionChecked}` guard, but not an
everyday gesture. It stops being narrow the moment a view fetches its own
content: then the loop routinely spins for hundreds of milliseconds with the
full header on screen, and clicking a nav link during it is the most ordinary
thing a user does. That is `#0054`, the very case this loop was written for.

**Prescribed fix — verified by this reviewer, 31/31.** Cancel any in-flight
restore at the top of `navigate()`. `restoringScroll` must be cleared by the
canceller itself, because the superseded loop's own `finish()` is token-guarded
and will refuse to clear it:

```ts
function cancelRestore(): void {
  restoreToken++;
  restoringScroll = false;
}

export function navigate(path: string, { replace = false }: NavigateOptions = {}): void {
  const url = new URL(path, window.location.origin);
  const route = parsePath(url.pathname, url.search);
  const target = url.pathname + url.search;

  cancelRestore();            // <-- a restore still re-applying would scroll the page we are pushing
  saveScrollToCurrentEntry();
  …
```

Applied in the worktree, rebuilt, re-run: J2/J3 green and every other check
unchanged — **31/31**, no collateral. Consider whether `pagehide` should skip
stamping while `restoringScroll` is true for the same reason (a pagehide during
a restore stamps the clamped `0` over a good saved offset); that one is
theoretical, not reproduced, and is a judgement call rather than a requirement.

### Judgement calls that are sound — do not change them

- **The 400 ms leading+trailing throttle is right, and the measurement holds.**
  Independently reproduced: instrumenting `History.prototype.replaceState` and
  scrolling one step per animation frame for 10 s in a real Chromium measured
  **26 calls (2.60/s, 78 per 30 s)** — the implementer's exact number. WebKit's
  historical limit really is ~100 state-object calls per 30 s throwing
  `SecurityError`, so the reasoning against rAF coalescing (~60/s, ~18× over) is
  correct, and the `try`/`catch` is the right belt. Two caveats worth knowing
  rather than fixing: the 22 % headroom is shared with `navigate()`'s own
  `pushState` calls, and tightening the interval is not available — 200 ms would
  be 150 per 30 s, over the limit. The disclosed ≤400 ms staleness on
  scroll-then-immediately-Back is inherent to the approach (a traversal cannot
  stamp the entry it is leaving), bounded by how far a user can scroll in
  400 ms, and an acceptable trade for staying under the rate limit.
- **The retry loop's other two failure modes are genuinely handled.** Tested
  with an unreachable offset (`replaceState({ scrollY: 5000 })` then reload, on
  a page whose max scroll is 546) so the loop is forced to spin the full
  deadline: it clamped to 546, and when the user scrolled to 100 mid-loop it
  backed off and stayed there (`K1 loop stops fighting the user: got 100`),
  then released `restoringScroll` so stamping resumed (`L1 stamping resumes
  after the loop ends: got 250`). It also cannot spin past its deadline — the
  bound is checked after every `scrollTo`, capping it at ~60 iterations.
- **The `Loading…` finding is real.** Measured `document.body.scrollHeight =
  209` during the placeholder against an 800 px viewport, i.e. `maxScroll` 0, so
  `scrollTo(0, 546)` really does clamp to 0 at init + one `tick()`. The
  reviewer's prescribed one-line init fix was indeed not sufficient on its own,
  and mutation 2 confirms the loop is what makes it work. Correctly diagnosed.
- **`saveScrollToCurrentEntry()`'s cancel-and-re-arm is correct but not
  load-bearing**, and the write-up overstates it. Removing
  `cancelPendingScrollSave()` from it (mutation 3) broke nothing: a trailing
  timer that survives a `pushState` fires *after* `navigate()`'s
  `window.scrollTo(0, 0)`, so it stamps `{ scrollY: 0 }` — which is exactly what
  the pushed entry should carry anyway. The `popstate` path is doubly covered
  (`restoreScroll()` also cancels, and the timer callback checks
  `restoringScroll`). Keep the code — it is cheap and defensible — but the
  "sharp edge" framing in `## Gotchas` should be softened to "defensive"
  rather than claimed as a bug that was fixed.
- **Scope is clean.** `243abad` touches `web/src/lib/router.ts` and nothing
  else (`git show --stat`), and `web/dist/index.html` in the main tree was left
  exactly as the concurrent agent had it.
- **Suites re-run at review** in the worktree: `npm run check` → 187 files, 0
  errors, 0 warnings; `npm test` → 7 files, 103 tests passed.
