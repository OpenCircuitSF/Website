## Description

These are follow-ups from `#0674`'s review.

1. **The guard reads a fixed migration.** `TestAPITokenScopesMatchMigration` reads `000053` by name. It should read the highest-numbered migration that (re)defines `api_tokens_scopes_check`. Otherwise, once a later migration widens the scope list, the guard keeps passing against a stale file.
2. **The web scope list has no parity test.** `web/src/lib/apiTokens.ts` copies the Go scope list by hand. Add a parity test against `apitokens.KnownScopes`, or serve the list from the admin API and drop the copy. As it stands, a scope added only on the server never appears in the create form.

## Plan

The plan pass was folded into the implementation pass, at the user's "keep moving" direction. This plan was written before any code. Batched with `#0683` and `#0686`.

- **Item 1.** Add `latestScopesMigration(dir)` to `internal/db/api_tokens_v2_migration_test.go`. It globs `*.up.sql`, sorts the names (they are zero-padded), and walks them from the highest down. It returns the first file whose text defines `api_tokens_scopes_check` with an `ARRAY[...]`. The regex is widened to accept the inline `CONSTRAINT … CHECK` in `000051`'s `CREATE TABLE` as well as `ADD CONSTRAINT`. `[^;]` stops a bare `DROP CONSTRAINT` from matching across statements. `TestAPITokenScopesMatchMigration` compares `KnownScopes` with that file's array. The proof runs on a copy of `migrations/` in `t.TempDir()`, as a Go test:
  - a fake `000998` that widens the array is picked, and parity then fails;
  - a later file that does not touch the constraint is skipped;
  - with everything after `000051` removed, the scan finds `000051`'s inline array.
- **Item 2: a parity test, not an API.** Serving the list from the admin API would need a new route, a fetch in the create form, and a loading state, and the form would still need its labels and groups in TS. A text parity guard is simpler, and as robust. It has two halves, because `KNOWN_SCOPES` is derived from `SCOPE_GROUPS`:
  - `internal/db` `TestAPITokenScopesMatchWeb` reads `web/src/lib/apiTokens.ts`. It takes the `export const SCOPE_* = '…'` values and requires them to equal `KnownScopes` as a set. `internal/db` already reaches the repo root, so no new §5 guard-table row is needed; the row's prose gains the file.
  - A vitest case in `apiTokens.test.ts` requires `KNOWN_SCOPES` to equal the set of `SCOPE_*` exports, so a constant left out of the groups also fails.
- **Verification tier.** Scoped `internal/db` and `internal/handlers` (because `AGENTS.md` changed), the web checks, and the batch's full `scripts/check.sh`. Mutations run on copies that are restored afterwards.

## Obstacles

None. Neither change touches a migration, and there is no template rebuild.

- `AGENTS.md` §5: the `internal/db` "Reaches into" cell names `web/src/lib/apiTokens.ts`.

### Assumptions

- The web list stays a hand-written copy, now guarded, rather than being served by the API (see Plan).
- A scope's TS constant must keep the `export const SCOPE_NAME = '…';` shape. If the file's shape changes so that nothing matches, the Go guard fails with a message saying so, rather than passing on an empty list.
