## Root cause

Not a bug fix — this is the first implementation of the admin subscribers screen. `#0025` (the `subscribers` store/migration) and `#0024` (the admin CRUD pattern for `/admin/interests`) had already landed; nothing existed yet at `/admin/subscribers`.

## Fix

- `internal/subscribers/store.go`: added `List` (filter by status/interest/email-substring, paginated, newest-first, `ESCAPE '\'` on the `ILIKE` so a literal `%`/`_` in a search can't act as a wildcard) and `StatusCounts` (always returns all five status keys, zero-filled). Promoted the unexported `findByID` to exported `GetByID` — `#0032`'s handler needed the same lookup `AdminClearComplaint` already used internally.
- `internal/audit/actions.go`: added `ActionSubscriberSuppressed`, `ActionSubscriberComplaintCleared`, `ActionSubscriberManualAdd`.
- `internal/handlers/admin_subscribers.go` (new): `AdminSubscribersHandler` serving `GET /admin/subscribers`, `GET /admin/subscribers/{id}`, `POST /admin/subscribers/{id}/suppress`, `POST /admin/subscribers/{id}/clear-complaint`, `POST /admin/subscribers` (manual add). `Create` deliberately does **not** reimplement the double-opt-in state machine: it holds a reference to the same `*SubscribeHandler` (`#0026`) instance `main.go` constructs and calls its unexported `newSignup`/`existingSignup`/`resolveInterestIDs` directly (legal — same package, no edit to `subscribe.go`), so a manual add gets exactly the reviewed once-per-hour resend claim, async-send timing-oracle fix, and complained guard the public endpoint has, instead of a second, divergent implementation of the same state machine.
- `cmd/opencircuit/main.go`: added `adminSubscribersH` to `adminRoutes()` (the single source of truth `TestMountAndServe_AdminRoutesRequireSessionAndAdmin` enumerates) and to `mountAndServe`'s parameter list; wired non-nil in `servePostgres`, nil in `serveDevMode` (matching `adminInterestsH`'s existing nil-guard — `internal/devstore` has no subscribers-table backing yet). Every other `mountAndServe` call site (`admin_wiring_test.go`, `ratelimit_wiring_test.go`, `shutdown_wiring_test.go`, `subscribe_wiring_test.go`) needed the one new parameter added to compile; none of their own logic changed.
- `web/src/lib/types.ts`, `api.ts`, `admin.ts` (+ `admin.test.ts`), `web/src/views/Admin.svelte`: a new "Subscribers" tab — status-counts header, filter bar (status/interest/email-substring), paginated table, a detail modal (consent evidence, interests, an email-event-history placeholder for `#0038`), a suppress modal (required note), a clear-complaint action gated to complained rows, and a manual-add form.

Carried-in criteria from `#0025`'s review:

- **`AdminClearComplaint`** is the only call `ClearComplaint` makes to move a subscriber out of `complained`; `ErrNotComplained` maps to 409, and the "Clear complaint" button is only rendered on complained rows (`canClearComplaint` in `admin.ts`).
- **`Suppress` inspects the returned `Status`** rather than assuming success: it reads the subscriber before calling `Unsubscribe`, compares to the status after, and returns `no_op: true` (with an explanatory message) when the target was already complained — the UI keeps the modal open and shows the server's explanation instead of closing on a false "success."
- **`#0033` dependency is noted, not guessed at.** `Suppress` does not write a `suppressions` row (the table/store don't exist); it calls the only sanctioned mutator available today, `Unsubscribe(source=admin)`. Both the audit metadata and the suppress-modal copy say this explicitly. Likewise `ClearComplaint`'s response and audit metadata note that no suppressions row is cleared yet, so the address may still be blocked at `#0026`'s suppressed-send gate.
- **`AdminClearComplaint` overwriting `unsubscribed_at`/`unsubscribe_source`** is surfaced in the detail modal (a note appears under the unsubscribe-evidence line for a complained subscriber) and in the `ClearComplaint` response's `message`.
- **The deferred `BEFORE UPDATE` trigger** was deliberately not added — a DB-level transition rule is `migrations`/`internal/db` territory, out of this issue's lane (and actively being reviewed under `#0083`). Reconsidered, not resolved; left unchecked below.

## Gotchas

- **Privacy scope decision.** `subscriberView` (and the TS `Subscriber` type) deliberately omits `confirm_token`/`manage_token` (live bearer credentials, never display data) and `confirm_sent_at`/`confirm_expires_at`/`already_subscribed_sent_at` (send-cooldown bookkeeping — neither disclosed by `#0075`'s privacy policy nor needed for this issue's stated admin tasks). It *includes* `status` and `unsubscribed_at`/`unsubscribe_source`, which the privacy policy discloses in prose ("stores your details with a pending status"; "we keep your record marked unsubscribed") even though the issue's literal "what the policy discloses" list (email/interests/IP/UA/UTM/confirmed_at) doesn't name them — flagging this per the task's "stop and say so" instruction rather than silently deciding. If a reviewer wants any of the omitted send-cooldown columns added, they're a small addition to `subscriberView`.
- **`Create`'s test coverage has a gap the write-up should be honest about:** a manual add against an existing *complained* address is protected twice — once by `existingSignup`'s own dispatch (never touches a complained row) and again, independently, by `subscribers.Store.Create`'s `ErrEmailExists` short-circuit (the row already exists, so even a wrong dispatch that called `newSignup` unconditionally would silently no-op rather than mutate anything). The complained-address test therefore does **not** distinguish correct dispatch from "always call newSignup" — only `TestAdminSubscribers_Create_ExistingPendingResendsConfirmation` (an existing *pending* row, which must get a resend — `newSignup` alone cannot produce that) does. Both tests are kept; only the second one is load-bearing for the dispatch logic itself.
- **`web/dist/index.html` is stale independent of this issue.** It's the ShortLinks-era placeholder (title "Short Links", old asset hashes) — `git show HEAD:web/dist/index.html` matches it, meaning no phase has rebuilt-and-recommitted it since `#0019`'s SEO templating (`%%OC_TITLE%%` etc.) landed in `web/index.html`, the actual Vite source. `npm run build` regenerates the correct, current artifact; I restored the stale committed version afterward per this pass's instructions rather than commit a dist/ regeneration out of scope for this issue. Worth its own issue if dist/ is meant to be kept in sync per-phase.

      admin will think an action took effect when it did not.

- [ ] **Revisit the deferred `BEFORE UPDATE` trigger.** `#0025` centralised the
      `complained` guard in Go and deferred a database-level transition rule. The
