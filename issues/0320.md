> 🟢 Resolved 2026-08-27 — `testdb.sh` now fingerprints `migrations/*.sql` contents into the template's `COMMENT ON DATABASE` and compares it alongside the version, so an in-place edit to an existing migration routes `create` to `#0315`'s direct-provision fallback instead of cloning a stale template.

## Description

`#0315` made `scripts/testdb.sh` fall back to provisioning from `migrations/`
when the shared template disagrees. Its freshness check — `template_matches_disk`
— compares `disk_version()` against `template_version()`, and **both yield
numbers**.

So **editing a migration in place is invisible to it.** The schema changes; the
version does not. `template_matches_disk` reports a match, `create` clones a
template built from the *old* file contents, and nothing says otherwise.

**This nearly went live during `#0315`'s own review.** `#0123`'s reviewer added a
`CHECK` constraint to `migrations/000025` with both sides still reading 25; only
its manual template rebuild kept them in step (the reviewer verified the template
carries `email_campaigns_slug_not_blank_check`).

**Pre-existing, not a regression from `#0315`** — the old hard-error path compared
the same numbers. `#0315` simply makes the mismatch survivable, which is what
brings this one into view.

## Why an edited migration is a real case here

CLAUDE.md §1 froze `000001`–`000024` because production is at 22, but a migration
created *after* the deploy and not yet applied anywhere that matters may still be
edited — `#0123`'s reviewer called `000025` "still-unfrozen", correctly. So
in-place edits are legitimate and will keep happening for the newest migration.

## Acceptance criteria

1. `build_template` records a **digest of `migrations/*.sql` contents**, not just
   the highest number — a settings row, `COMMENT ON DATABASE`, or a sidecar keyed
   to the template.
2. `template_matches_disk` compares that digest in addition to the version. A
   content mismatch routes to `#0315`'s existing `provision_from_migrations`
   fallback, introducing no new failure mode.
3. The digest covers both `.up.sql` and `.down.sql`, and is stable across
   machines — no absolute paths, no timestamps, no directory-order dependence.
4. Prove it: build a template, edit a migration in place without changing its
   number, and confirm `create` now provisions from disk rather than cloning
   stale contents. Demonstrate the **before** state too — today it clones.
5. Do not make rebuilding the template automatic (`#0315` criterion 4). A content
   mismatch routes to the fallback, exactly as a version mismatch does.
6. Keep the fast path fast — `#0315`'s review measured clone at 0.19s against
   0.29s for a full migrate. A digest computed per `create` must not erase that.
7. `ISSUE=NNNN scripts/check.sh guards` passes, and `scripts/testdb.sh`
   create/drop/gc/template all still behave.

## Work log

Added a content digest alongside the version check in `scripts/testdb.sh`:

- `disk_digest()` hashes the sorted list of `migrations/*.sql` relative
  filenames, then their contents concatenated in that same order, via
  `shasum -a 256`. Filenames are relative (`sed 's|^\./||'` after `cd` into
  `migrations/`, never an absolute path), sorted with `LC_ALL=C sort` for a
  byte-wise, locale-independent, directory-order-independent result, and
  covers both `.up.sql` and `.down.sql` (glob is `*.sql`, not `*.up.sql`).
  `require_shasum()` preflights `shasum`'s presence (per `#0301`'s lesson —
  a missing preflight let an earlier digest check silently compare two
  empty strings); `valid_digest()` asserts the output is exactly 64 lower
  hex chars before it is ever compared, and `disk_digest` hard-errors if
  `shasum` didn't produce one.
- `build_template()` stores the digest as `COMMENT ON DATABASE <template>`
  after `migrate up` finishes. Chosen over a table because it survives
  regardless of what `migrate` does to the template's own schema, and
  `template_digest()` reads it back via `pg_shdescription` — a
  cluster-catalog lookup — without a separate connection into the template
  database.
- `template_matches_disk()` now requires the version **and** the digest to
  match; a digest-only mismatch (same version, different content — the
  in-place-edit case this issue is about) routes to the same
  `provision_from_migrations` fallback `#0315` already added, with no new
  failure mode. `warn_template_mismatch()` gained a third message branch
  naming this case explicitly ("both report migration N, but the content
  digest disagrees ... likely edited in place").
- No new automatic rebuild path was added — `build_template` still has
  exactly one caller (the `template` subcommand).

**Fast-path cost**: the first working `disk_digest()` (a per-file
`printf`+`cat` loop over `find | sort`) forked roughly 100 processes for the
repo's 50 migration files and measured ~0.13s standalone against real
`migrations/` — on top of a ~0.13s baseline clone, that would have made
`create` slower than a full `migrate up` (`#0315` measured ~0.29s),
defeating the point of the fast path. Rewrote it to hash the sorted
filename list once, then the concatenated file contents fetched by one
batched `xargs cat` — ~0.02s standalone for the same 50 files, an ~8x
improvement, isolated by `time` on both versions before/after the rewrite.

### The implicit-rebuild alarm (criterion 5) — false alarm, settled by evidence

`#0319`'s reviewer reported that its `check.sh` run "rebuilt the shared test
template on its own … re-applied `000001`–`000025` before cloning". That
description is loose, and the behaviour it describes did not happen. Three
independent probes:

- **`build_template` was never called.** It stamps `COMMENT ON DATABASE`
  unconditionally, immediately after `migrate up`. The live shared
  `opencircuit_test_template` carries **no comment at all** while `migrations/`
  hashes to `8e49306b…` — so no `build_template` has run since `b0aa902`
  landed. What `#0319` observed was `provision_from_migrations` applying 25
  migrations into its *own* scratch database `opencircuit_test_0319rr`, which
  is `#0315`'s intended fallback, not a clone and not a template rebuild.
- **`#0315`'s behavioural probe, re-run against `b0aa902`**: `TEMPLATE_DB`
  pointed at a nonexistent database, `create` run — `count(*)` for that name is
  **0 before and 0 after**. The pre-`#0315` script auto-built it (1).
- **The digest branch takes the same route as the version branch.** Probe with
  an existing template at version 25 and a digest-only mismatch: the template's
  stored digest was byte-identical before and after (`8e49306b…`), the template
  did **not** gain the newly-added table, and the scratch database did. There is
  one `if template_matches_disk … else warn+provision` in the `create` case;
  the digest is a new *term* in the predicate, not a new path. `build_template`
  still has exactly one caller (line 316, `template)`), and `check.sh` only ever
  invokes `testdb.sh create` / `drop`.

**Consequence worth acting on, though:** because the shared template predates
`b0aa902` and therefore has no digest comment, `template_digest` returns `none`
for it and **every** `create` now mismatches — every agent is on the slow
direct-provision path until someone runs `scripts/testdb.sh template`
explicitly, when no one else is mid-run. That is exactly the designed
behaviour (no implicit rebuild), and it is also what makes the "it rebuilt the
template" impression so easy to form.

### `valid_digest()` is genuinely fail-closed

Re-ran `#0301`'s scenario with `shasum` stubs first on `PATH`. Four malformed
outputs — **empty**, **non-hex**, **too short** (`deadbeef`), and **uppercase
hex** — each produced `error: shasum did not produce a valid digest` and then
`create` **refused the clone** and provisioned from disk (25 migrate steps
observed each time). It never compared two empty strings and reported a match.
With `shasum` absent from `PATH` entirely, `require_shasum()` fires and
`disk_digest` exits 1, which in `template_matches_disk`'s `[ ]` yields `""`
against the template's stored 64-hex value — a mismatch, so still the fallback.
`build_template` under a broken `shasum` exits 1 **before** the `COMMENT`
statement, leaving no comment rather than an empty one.

### A stray file in `migrations/` — what actually happens

Three agents share this tree, so this was tested rather than reasoned about.
The glob is `find -maxdepth 1 -type f -name '*.sql'`:

| stray file | digest | effect on `create` |
|---|---|---|
| `…up.sql.orig` (merge artifact) | unchanged | none — outside the glob |
| `…up.sql~`, `.…swp` (editor backups) | unchanged | none — outside the glob |
| `zz_scratch.sql` (a real stray `.sql`) | changes | falls back to provisioning; `migrate` ignores the non-conforming name and the database is correct. Costs the fast path while it sits there, under a message that blames an in-place edit |
| `000026_wip.up.sql`, half-written | changes | `create` fails (`migrate` rejects the SQL) — **identical at `b0aa902^`**, so not a regression; it is `#0315`'s behaviour |
| a name with a space or a quote (`my notes.sql`, `don't.sql`) | `xargs` aborts, `disk_digest` yields nothing | falls back to provisioning; correct database, `xargs: unterminated quote` on stderr |

Every case fails **safe** — toward provisioning from disk, never toward a false
"matches" — which is the direction that matters. The costs are a lost fast path
and a misattributed message, not a wrong schema.

### Follow-ups to file (not blocking)

1. `template_digest()` re-runs `db_exists` and opens a second `psql`
   connection; ~0.04s of the 0.061s added to every `create`. Read version and
   digest in one query.
2. The `pg_shdescription` join lacks `and ds.classoid = 'pg_database'::regclass`.
   `pg_shdescription` is keyed by `(objoid, classoid)` and also holds role and
   tablespace comments, so an oid collision would return extra rows. Fails safe
   (concatenated rows → mismatch → fallback), but the filter is one clause.
3. `disk_digest`'s `find | sort | xargs cat` is not NUL-delimited, so a
   filename containing a space, quote or backslash breaks `xargs`.
   `find -print0 | sort -z | xargs -0 cat` (with the name list hashed the same
   way) would be robust. Low priority — migration names are machine-generated.
4. **Unrelated hazard found while reviewing**: `scripts/testdb.sh gc --all`
   under a `TEMPLATE_DB` override drops the **real** shared
   `opencircuit_test_template`. The sweep selects `datname like
   'opencircuit_test_%'` and excludes only `$TEMPLATE`, which the override has
   repointed elsewhere. Pre-existing (`#0150`-era), but `#0315`/`#0320` actively
   teach agents to set `TEMPLATE_DB`, so the two now compose badly. Not
   triggered here — bare `gc` was run, `--all` was not.
