# 0477 — Tagging a workshop with an interest while another admin deletes it loses the tag silently

| | |

## Description

Two admins, at the same moment: one tags a workshop with an interest, the other
deletes that interest.

The foreign key serialises them, so there is no error and no deadlock. But once
the tagging transaction commits, the delete proceeds **on its own pre-statement
snapshot** — in which no workshop referenced the interest. `Store.Delete`
returns `nil`, reports success, and the just-committed tag is cascaded away by
`workshop_interests.interest_id ON DELETE CASCADE`.

The admin who tagged the workshop sees their action succeed. The tag is gone.

## What this is not

**It is not a defect introduced by `#0474`.** Measured by `#0474`'s second
review while its concurrency rig was already standing, and reported separately
for exactly that reason. `#0024`'s original subscriber-only guard had the
**identical window**; widening the guard to three tables neither opened nor
narrowed it.

It is the residual check-then-act window inherent in the design: `NOT EXISTS`
evaluated against a snapshot cannot see a row committed after that snapshot was
taken, however many tables the clause covers.

`#0474` closed the *other* race in this area — two admins deleting the same
interest, where the outer `SELECT` and the CTE's `DELETE` disagreed and produced
a 500 instead of a 404. That one was a regression with a wrong status code. This
one is silent data loss, and it predates both.

## Why it is filed rather than fixed in `#0474`

Closing it is a **design decision**, not a transcription:

- **Lock before check** — `SELECT ... FOR UPDATE` on the interest row, or a lock
  taken on the referencing side, so the tagging transaction cannot commit
  underneath the delete's snapshot.
- **`SERIALIZABLE` isolation** for this one statement, which turns the anomaly
  into a serialisation failure the caller must retry.

Each has costs that reach beyond `Delete`: the first requires deciding which
side takes the lock and in what order, across three referencing tables, with
deadlock ordering to reason about. The second introduces retry-on-40001 as a
concept this codebase does not currently have anywhere.

Neither belongs in a bounce remedy, which is why `#0474`'s reviewer measured it
and stopped.

## Acceptance criteria

1. **Reproduce it first.** `#0474`'s second review synchronised three
   connections without a sleep: session A holds an open transaction; a goroutine
   calls the real store method; a third **observer** connection polls
   `pg_stat_activity`, identifying the blocked backend by query text and
   confirming it via `pg_blocking_pids`. Reuse that shape — the test must
   **fail closed** if the block is never observed, since a race test that never
   raced passes for the wrong reason.
2. **Decide between locking and `SERIALIZABLE`, and write down why.** Say what
   the rejected option would have cost. This is the issue's real product.
3. Whatever is chosen must cover **all three** referencing tables —
   `subscriber_interests`, `campaign_interests`, `workshop_interests` — or state
   explicitly which are out of scope and why.
4. **Say what the losing admin sees.** A silent success is the defect; an error
   they can act on is the fix. If the answer is a retry, decide whether the
   server retries or the operator does.
5. Do not weaken `#0474`'s work: the three distinct 409s, each naming the
   blocking table and ending `deactivate it instead`, must survive, as must
   `deleteOutcomeAfterRace`'s 404 on the concurrent-delete path.
6. **Use your own scratch database** (§8b). This work deliberately drives
   concurrent writes against the taxonomy — the same table `#0024` permanently
   damaged in the shared test database with a hardcoded id. Seed throwaway rows;
   never target a literal or seeded id.

## Relation

- `#0024` built the admin interests API; its guard carried this same window.
- `#0474` widened the guard to three tables and fixed the concurrent-delete
  status regression. This issue is the window neither closed.
- `#0475` is the sibling gap: no supported path to change an interest's slug.
- Deactivation (`PATCH {"active": false}`) remains the recommended path for
  retiring an interest, and is unaffected by this race.
