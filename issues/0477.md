# 0477 — Tagging a workshop with an interest while another admin deletes it loses the tag silently

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | interests |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-09-08 |

## Description

Two admins, at the same moment: one tags a workshop with an interest, the other
deletes that interest.

The foreign key serialises them, so there is no error and no deadlock. But once
the tagging transaction commits, the delete proceeds **on its own pre-statement
snapshot** — in which no workshop referenced the interest. `Store.Delete`
returns `nil`, reports success, and the just-committed tag is cascaded away by
`workshop_interests.interest_id ON DELETE CASCADE`.

The admin who tagged the workshop sees their action succeed. The tag is gone.

## What this is not

**It is not a defect introduced by `#0474`.** Measured by `#0474`'s second
review while its concurrency rig was already standing, and reported separately
for exactly that reason. `#0024`'s original subscriber-only guard had the
**identical window**; widening the guard to three tables neither opened nor
narrowed it.

It is the residual check-then-act window inherent in the design: `NOT EXISTS`
evaluated against a snapshot cannot see a row committed after that snapshot was
taken, however many tables the clause covers.

`#0474` closed the *other* race in this area — two admins deleting the same
interest, where the outer `SELECT` and the CTE's `DELETE` disagreed and produced
a 500 instead of a 404. That one was a regression with a wrong status code. This
one is silent data loss, and it predates both.

## Why it is filed rather than fixed in `#0474`

Closing it is a **design decision**, not a transcription:

- **Lock before check** — `SELECT ... FOR UPDATE` on the interest row, or a lock
  taken on the referencing side, so the tagging transaction cannot commit
  underneath the delete's snapshot.
- **`SERIALIZABLE` isolation** for this one statement, which turns the anomaly
  into a serialisation failure the caller must retry.

Each has costs that reach beyond `Delete`: the first requires deciding which
side takes the lock and in what order, across three referencing tables, with
deadlock ordering to reason about. The second introduces retry-on-40001 as a
concept this codebase does not currently have anywhere.

Neither belongs in a bounce remedy, which is why `#0474`'s reviewer measured it
and stopped.

## Acceptance criteria

1. **Reproduce it first.** `#0474`'s second review synchronised three
   connections without a sleep: session A holds an open transaction; a goroutine
   calls the real store method; a third **observer** connection polls
   `pg_stat_activity`, identifying the blocked backend by query text and
   confirming it via `pg_blocking_pids`. Reuse that shape — the test must
   **fail closed** if the block is never observed, since a race test that never
   raced passes for the wrong reason.
2. **Decide between locking and `SERIALIZABLE`, and write down why.** Say what
   the rejected option would have cost. This is the issue's real product.
3. Whatever is chosen must cover **all three** referencing tables —
   `subscriber_interests`, `campaign_interests`, `workshop_interests` — or state
   explicitly which are out of scope and why.
4. **Say what the losing admin sees.** A silent success is the defect; an error
   they can act on is the fix. If the answer is a retry, decide whether the
   server retries or the operator does.
5. Do not weaken `#0474`'s work: the three distinct 409s, each naming the
   blocking table and ending `deactivate it instead`, must survive, as must
   `deleteOutcomeAfterRace`'s 404 on the concurrent-delete path.
6. **Use your own scratch database** (§8b). This work deliberately drives
   concurrent writes against the taxonomy — the same table `#0024` permanently
   damaged in the shared test database with a hardcoded id. Seed throwaway rows;
   never target a literal or seeded id.

## Plan

Chosen approach: **lock the parent `interests` row with `SELECT ... FOR UPDATE`
before the reference check**, in a transaction, so the check runs in a snapshot
taken *after* every competing writer has released the row. `SERIALIZABLE` is
rejected; `## Findings` records the measurement that decides it.

The whole fix is `internal/interests/store.go`'s `Delete`, and it is a net
**reduction** of about 37 lines. Every step below was applied and run green in a
throwaway worktree before being written here.

1. **`internal/interests/store.go` — rewrite `Delete`'s body.** Keep the method
   signature, the three sentinels, and their priority order untouched. The new
   body is four steps, in one transaction:

   ```go
   func (s *Store) Delete(ctx context.Context, id int64) error {
   	tx, err := s.pool.Begin(ctx)
   	if err != nil {
   		return fmt.Errorf("interests: beginning delete of id %d: %w", id, err)
   	}
   	defer func() { _ = tx.Rollback(ctx) }()

   	var locked int64
   	err = tx.QueryRow(ctx,
   		`SELECT id FROM interests WHERE id = $1 FOR UPDATE`, id).Scan(&locked)
   	switch {
   	case errors.Is(err, pgx.ErrNoRows):
   		return ErrNotFound
   	case err != nil:
   		return fmt.Errorf("interests: locking id %d for delete: %w", id, err)
   	}

   	var deleted, hasSubscribers, hasCampaigns, hasWorkshops bool
   	if err := tx.QueryRow(ctx,
   		`WITH del AS (
   		    DELETE FROM interests
   		     WHERE id = $1
   		       AND NOT EXISTS (SELECT 1 FROM subscriber_interests WHERE interest_id = $1)
   		       AND NOT EXISTS (SELECT 1 FROM campaign_interests WHERE interest_id = $1)
   		       AND NOT EXISTS (SELECT 1 FROM workshop_interests WHERE interest_id = $1)
   		    RETURNING id
   		 )
   		 SELECT
   		    EXISTS (SELECT 1 FROM del),
   		    EXISTS (SELECT 1 FROM subscriber_interests WHERE interest_id = $1),
   		    EXISTS (SELECT 1 FROM campaign_interests WHERE interest_id = $1),
   		    EXISTS (SELECT 1 FROM workshop_interests WHERE interest_id = $1)`,
   		id,
   	).Scan(&deleted, &hasSubscribers, &hasCampaigns, &hasWorkshops); err != nil {
   		return fmt.Errorf("interests: deleting id %d: %w", id, err)
   	}
   	if deleted {
   		if err := tx.Commit(ctx); err != nil {
   			return fmt.Errorf("interests: committing delete of id %d: %w", id, err)
   		}
   		return nil
   	}
   	switch {
   	case hasSubscribers:
   		return ErrHasSubscribers
   	case hasCampaigns:
   		return ErrHasCampaigns
   	case hasWorkshops:
   		return ErrHasWorkshops
   	default:
   		return fmt.Errorf("interests: delete id %d removed nothing while holding its row lock; retry", id)
   	}
   }
   ```

   Three things about that shape are deliberate and must not be "simplified":

   - **The lock and the check must be two separate statements.** A lock taken
     inside the same statement as the check buys nothing, because every
     sub-statement of one query shares one snapshot — which is the whole
     mechanism of this defect. Only a statement whose snapshot is taken after
     the lock was *granted* can see a reference committed by the transaction it
     waited for.
   - **`FOR UPDATE`, not `FOR NO KEY UPDATE`.** Inserting into any of the three
     referencing tables takes a `FOR KEY SHARE` lock on the parent row to
     enforce the foreign key, and only `FOR UPDATE` conflicts with it.
     `FOR NO KEY UPDATE` was measured and still loses the tag silently.
   - **`#0474`'s CTE stays**, with its `NOT EXISTS` clauses intact. They are now
     redundant with the check above them, and that redundancy is the point: it
     is a database-level backstop on a silent-data-loss path, so a mistake in
     the lock reasoning produces a refusal rather than a cascade.

2. **Same file — delete `deleteOutcomeAfterRace` and the `stillExists`
   column.** Both existed to answer "why did the DELETE remove nothing when my
   own snapshot said it should have"; holding the row lock removes the question,
   because after `FOR UPDATE` returns a row no other transaction can remove it
   or add a reference to it. Its one covered arm — `!exists` returning
   `ErrNotFound` — moves to the lock statement's `pgx.ErrNoRows`, which is where
   `TestDelete_RaceWithConcurrentDeleteReportsNotFound` now gets its
   `ErrNotFound` from; verified, that test passes **unchanged**. Removing the
   helper is what keeps this fix from leaving behind branches that are dead but
   commented as though they were live, which is the shape that produced
   `#0474`'s own regression.

3. **Same file — rewrite `Delete`'s doc comment.** The current text explains the
   single-atomic-statement design and the READ COMMITTED fall-through to
   `deleteOutcomeAfterRace`; both are gone. The replacement must say: the lock
   is taken first and every referencing insert takes a conflicting `FOR KEY
   SHARE` lock on the same row, so the check that follows it cannot miss a
   reference committed while the delete waited; the check and the delete are one
   statement so a reported blocker is always the clause that rejected the row;
   and the `NOT EXISTS` clauses are retained as a backstop. Keep the existing
   migration citations, one per sentence — `campaign_interests` cascading per
   `migrations/000017_create_campaigns.up.sql`, and `workshop_interests`
   cascading per `migrations/000020_create_workshops.up.sql`.

4. **Same file — the package doc comment** needs one clause updated: it
   currently says `Delete` "hard-removes a row only when nothing references it
   at all". That stays true; add nothing about locking there. Check it reads
   correctly after step 3 and leave it otherwise alone.

5. **`internal/interests/delete_race_test.go` — add the regression test**, in
   this package's existing `TestDelete_...` family, named for the behaviour it
   pins: adding a reference while a delete is in flight must refuse the delete
   and keep the reference. (The name is deliberately not spelled here —
   `internal/db`'s open-issue citation guard forbids an open issue from naming a
   test the tree does not yet define, and `#0474`'s second review tripped it
   exactly this way.) Requirements:

   - **Reuse `waitUntilBlockedBy` unchanged.** It already polls a third
     observer connection for a backend the server reports as blocked, and it
     already fails closed with an explicit message when no block is ever seen.
   - **Table-driven over all three referencing tables**, so criterion 3 is
     covered by execution rather than by argument. Session A opens a
     transaction and inserts into `subscriber_interests`,
     `campaign_interests`, or `workshop_interests`; a goroutine calls the real
     `Store.Delete`; the observer confirms the block; a non-blocking receive
     confirms `Delete` has not returned; A commits; then assert the matching
     sentinel (`ErrHasSubscribers`, `ErrHasCampaigns`, `ErrHasWorkshops`) **and**
     that both the `interests` row and the reference row still exist.
   - **Seed every row throwaway** — `testSlug` for the interest, a
     `zz-test-`-prefixed slug or address for the workshop, campaign, and
     subscriber, with `t.Cleanup` deleting the parent. Never a literal or
     seeded id.
   - **Prove it fails closed**, the way `#0474`'s third review did: in a
     detached worktree, move session A's commit to before the delete starts and
     confirm the test fails at `waitUntilBlockedBy` rather than passing on a run
     in which nothing raced.
   - **Prove it fails against the parent commit** in a detached worktree
     (never `git stash`, `CLAUDE.md` §8a): against today's `Delete` it must fail
     with the delete having returned `nil` and the reference gone.

6. **`docs/mailing-list.md` — one clause.** The `DELETE` bullet says
   `interests.Store.Delete` "checks all three in one atomic statement". Replace
   that with a phrasing that says it locks the interest row first and then
   checks all three, so a reference committed while the delete was waiting is
   seen rather than cascaded away. Change nothing else in that bullet; the three
   `ON DELETE CASCADE` citations and the `PATCH {"active": false}` guidance are
   still correct.

7. **Change nothing in `internal/handlers`.** The status mapping is already
   right in both directions and was re-verified: the losing deleter gets one of
   `#0474`'s three 409s, and the losing tagger gets the 400 that

## Findings

All measurements below were taken on `opencircuit_test_0477p`, created with
`scripts/testdb.sh create 0477p` and dropped afterward, from a detached git
worktree at `b04391b` that was removed afterward. Neither
`scripts/testdb.sh template` nor `scripts/db-reset.sh` was run. `uptime` before
the runs: load averages 2.57 / 2.30 / 2.56, and 1.80 / 2.06 / 2.33 before the
longest one — far below the ~8 mark `CLAUDE.md` §5 sets. No production code was
committed; every probe file was deleted with the worktree.

**1. Reproduced, on all three tables, with the interleaving read out of the
server.** The rig is `#0474`'s: session A holds an open transaction that has
inserted the reference; a goroutine calls the real `interests.Store.Delete`; a
third observer connection polls `pg_stat_activity` for a backend that
`pg_blocking_pids` reports as waiting on A. The observer identified the blocked
backend by its query text, which began `WITH del AS ( DELETE FROM interests
WHERE id = $1 AND NOT EXISTS (SELECT 1 FROM subscriber` — `Delete`'s own
statement, not some other waiter — and a non-blocking receive confirmed `Delete`
had not returned at that moment. Only then was A committed. Results:

| Referencing table | `Delete` returned | `interests` rows after | reference rows after |
|---|---|---|---|
| `workshop_interests` | `nil` | 0 | 0 |
| `subscriber_interests` | `nil` | 0 | 0 |
| `campaign_interests` | `nil` | 0 | 0 |

So **the window is not workshop-specific**; it is identical on the subscriber
and campaign sides, which the issue asked to be checked rather than assumed. The
campaign case is the worst of the three, for the reason `#0474` already records:
a sent campaign's target segment cannot be reconstructed afterward.

**2. `#0474`'s CTE did not change the window's shape versus `#0024`'s
two-statement form.** The `NOT EXISTS` clauses are evaluated by the scan node
from the statement snapshot, *before* `ModifyTable` blocks on the row lock, so
widening the clause from one table to three neither opened nor narrowed
anything. That matches what the issue states, and the reproduction confirms it:
all three tables behave identically, including the one `#0024` originally
guarded.

**3. Candidate A — lock before check — closes it, on all three tables.**
`SELECT id FROM interests WHERE id = $1 FOR UPDATE` in a transaction, then
`#0474`'s CTE as a second statement. Observer-confirmed block each time, now on
the lock statement rather than the CTE:

| Referencing table | `Delete` returned | `interests` rows after | reference rows after |
|---|---|---|---|
| `workshop_interests` | `ErrHasWorkshops` | 1 | 1 |
| `subscriber_interests` | `ErrHasSubscribers` | 1 | 1 |
| `campaign_interests` | `ErrHasCampaigns` | 1 | 1 |

**4. The lock mode is load-bearing and was measured, not reasoned about.** The
same code with `FOR NO KEY UPDATE` does **not** block the tagging transaction —
that mode does not conflict with the `FOR KEY SHARE` lock a foreign-key insert
takes — and reproduces the original silent loss exactly: `err=<nil>`, interest
gone, tag gone. `FOR UPDATE` is required.

**5. Candidate B — `SERIALIZABLE` — also closes it, which corrects my own
starting premise.** I expected serialisable isolation on the delete alone to
detect nothing, since the racing tagger runs at READ COMMITTED like every writer
in this codebase. That expectation was wrong. All three tables returned SQLSTATE
`40001` with the interest and the reference both intact. The mechanism is not
SSI predicate locking: the foreign-key insert stamps the parent row's `xmax`
with its own lock, and under REPEATABLE READ or stricter that counts as a
concurrent update, so the error raised is `could not serialize access due to
concurrent update`. Efficacy is therefore **not** what separates the two
options.

**6. What separates them is that `SERIALIZABLE` breaks `#0474`, and criterion 5
forbids that.** Run against the *concurrent-delete* race — the one
`TestDelete_RaceWithConcurrentDeleteReportsNotFound` pins — candidate B returns
`could not serialize access due to concurrent delete` (SQLSTATE `40001`), which
matches no sentinel, so `AdminInterestsHandler.Delete`'s `default` case answers
**500**. That is precisely the regression `#0474` spent three passes removing.
Candidate A returns `ErrNotFound` on that same race, so the 404 survives and the
test passes unchanged.

**7. What a retry-on-40001 loop would actually buy, measured.** After the
`40001`, a second attempt returned `interests: has workshop tags; deactivate
instead of deleting` — exactly the answer candidate A gives on the *first*
attempt. So the retry machinery would exist only to reach an answer the lock
reaches directly, while a second retry would be needed for the concurrent-delete
case to recover the 404 that candidate A never lost.

**8. Deadlock: none possible from the delete side, and none observed.** The
delete transaction acquires exactly one lock — the parent row — and holds
nothing while waiting for it, so it cannot be a link in a cycle. The cascade
that could theoretically reach a join row is unreachable, because a join row
locked by an uncommitted competitor is still visible to the check statement and
produces a refusal before any cascade runs. Measured with 60 rounds of the real
tagging shape (`DELETE FROM workshop_interests WHERE workshop_id = $1` followed
by the insert, matching `workshops.Store`'s own replace-then-insert) racing the
locking delete: **0 deadlocks** (no SQLSTATE `40P01`), 0 lost tags, every
outcome either a clean delete or one of the sentinels.

**9. Blocking behaviour is unchanged.** Today's `Delete` already blocks on a
concurrent tagger — that is what the observer sees. The fix moves *where* it
blocks, from the CTE to the lock statement, not *whether* it blocks.

**10. Both losing admins get an actionable error; nobody retries.** With the
lock in place, whichever side loses learns why:

- **The deleter loses** (the tag committed first): one of `#0474`'s three 409s,
  each naming the blocking table and ending `deactivate it instead`.
- **The tagger loses** (the delete committed first): the insert blocks on the
  delete's `FOR UPDATE`, then fails with SQLSTATE `23503`, a foreign-key
  violation. Confirmed on all three tables. On the workshop path that is already
  mapped to `workshops.ErrInterestNotFound`, which
  `internal/handlers/admin_workshops.go` answers as **400 "one or more interest
  ids do not exist"** on both create and update.

**11. The proposed change passes the whole existing suite, unmodified.** With
candidate A applied to `internal/interests/store.go` in the worktree, all 19
existing `internal/interests` tests passed, including
`TestDelete_RaceWithConcurrentDeleteReportsNotFound`,
`TestDelete_RefusedWhenWorkshopReferencesIt`,
`TestDelete_RefusedWhenCampaignReferencesIt`,
`TestDelete_ReferencedByAllThreeReportsSubscribersFirst` and
`TestDelete_NotFound`. `internal/handlers` (7.599s), `internal/workshops`
(7.634s) and `internal/subscribers` (0.744s) all reported `ok` against it, and
`gofmt -l internal/interests/` was silent on the edited file. `go tool cover`
reports the new `Delete` at 77.3%; the uncovered statements are the four
error-wrapping paths and the backstop `default`.

**12. Scope note, as the dispatch invited.** The window is exactly as wide as
the issue assumes — no wider, no narrower. It is one window, on one row, reached
by one method, and the fix is one lock statement. No second site needs changing.
