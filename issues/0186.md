## Description

`web/src/lib/sendConfirm.ts`'s module header says consumers "must only ever branch on `.kind`, never recompute any of the conditions" — the point being that `sendGuardState` is the single place the send gate's precedence lives.

**`CampaignSendDialog.svelte` does not call `sendGuardState` at all.** It receives `sendInFlight` as a prop and consumes it as a raw boolean (`if (inFlight) return;`, `disabled={inFlight}`). The one production call site of `sendGuardState` hardcodes `inFlight: false`.

Two consequences, found by `#0184`'s review:

1. **`kind: 'sending'` has no production producer.** That branch, and its `sendGuardDescription` line, are unreachable from the UI.
2. **The dialog is doing exactly what the header forbids** — recomputing a condition the module owns.

Nothing is broken today: the raw-boolean checks happen to agree with what `sendGuardState` would return. But the module's stated invariant is not true of its only real consumer, and `#0184` has just pinned that precedence with tests — so the tests now guard a contract the app partly bypasses.

**Also, a stale comment on the same path.** `CampaignEditor.svelte:199` claims the dialog "re-evaluates `sendGuardState`". It imports only `normalizeCountInput`, `confirmMatches`, and `confirmHint`. That is the comment a future reader would trust about the send gate.

## Root cause

`CampaignSendDialog.svelte` predated `sendGuardState` entirely (or was never
migrated onto it when the module was introduced): it read `inFlight` as a
plain boolean prop and computed `blockedAgain = unmet.length > 0` itself,
duplicating exactly the conditions `sendGuardState` exists to own. Its
`handleSubmit` bail-out went further — it checked `inFlight` and the typed
count but never looked at `unmet` at all, so a same-count retry click could
call `onConfirm` again even while the "no longer ready to send" panel was
showing, which is precisely the double-send risk `#0184`'s review flagged the
inFlight-before-unmet ordering as protecting against. Because nothing in the
component asked the guard, `kind: 'sending'` had no production producer, and
the parent's own `editorGuard` hardcoded `inFlight: false`, masking the gap.

## Fix

Chose **(a)** — wired `CampaignSendDialog.svelte` through `sendGuardState`.
The case for (a) is what the issue's notes already argued: the ordering
inside `sendGuardState` is not cosmetic (`sending` warns against a retry;
`blocked`'s "Pre-send checks have not passed" invites one), and the dialog is
the one component that acts on a retry — so it is the one place that
precedence actually needs to be asked, not just possessed. (b) would have
required documenting a narrower, boolean-only contract that was *already
wrong* today (the retry-while-blocked gap below), so narrowing rather than
fixing would have shipped a "narrower but still incorrect" contract.

Concretely: `guard = sendGuardState({ status: 'draft', unmet, audienceCount:
summary.recipients, confirmRaw, inFlight })`. `status: 'draft'` is a
documented literal, not a re-derivation — the parent (`CampaignEditor.svelte`)
only ever mounts this dialog while `sendGateOpen` is true (itself gated on
`editorGuard.kind === 'ready'`, which requires `status === 'draft'`), and
closes the dialog before a successful send can move status past draft. Every
place that previously read the raw `inFlight` prop now reads a derived
`sending = guard.kind === 'sending'` instead (behaviourally identical, since
`sendGuardState` checks `inFlight` before `unmet` and `status` is fixed to
`'draft'`, so `kind === 'sending'` iff `inFlight`). `blockedAgain` now reads
`guard.kind === 'blocked'`. `handleSubmit` now gates on `guard.kind ===
'ready'` instead of re-deriving a match check, and since `ready` already
implies `confirmMatches(confirmRaw, summary.recipients)`, it passes
`summary.recipients` straight to `onConfirm` rather than re-parsing
`confirmRaw`.

This produced two deliberate, non-cosmetic behaviour changes, both found by
building the truth table rather than assumed going in:

1. **The blocked panel now defers to "Sending…"** in the one state where a
   retry has been resubmitted but the `unmet` array is still stale from the
   attempt that just failed (`inFlight` and non-empty `unmet` true at once,
   for one render). Previously both the "no longer ready to send" panel and
   the disabled/"Sending…" button rendered simultaneously — a confusing,
   self-contradictory state. Now `sending` wins, matching the precedence
   `sendGuardState` itself encodes.
2. **The double-send gap `handleSubmit` had is closed.** Before this change,
   an admin could retype (or leave typed) the matching count after a failed
   send, and clicking "Send now" again would call `onConfirm` even though
   `blockedAgain` was showing — the exact "retry while blocked" scenario the
   issue's notes warn is the one action that risks a double send. Gating on
   `guard.kind === 'ready'` refuses that submit.

Both are documented in the code (comments in `CampaignSendDialog.svelte`) and
proven in the new test file (see `## Verification`) rather than asserted.

Also fixed the stale comment at `CampaignEditor.svelte:199`: it claimed the
dialog "re-evaluates sendGuardState against what the operator actually
typed," which was false before this change (the dialog imported only
`normalizeCountInput`, `confirmMatches`, and `confirmHint`) and is now true —
reworded to say so explicitly and credit `#0186`.

**What "confirm behaviour unchanged by execution" means here, and what it
doesn't.** Nothing in a `.svelte` file is covered by a test (`#0094`, the
same limitation `#0119`'s review hit), so there is no component-render test
proving what appears on screen. The proof is two-part, matching `#0119`'s
precedent for this exact limitation:

1. **A new exhaustive-input vitest file**
   (`CampaignSendDialog.guard.test.ts`) replicates the dialog's OLD
   raw-boolean formulas (`sending = inFlight`; `blockedAgain = unmet.length >
   0`; the old `handleSubmit` bail-out, which never read `unmet`) side by
   side with the NEW guard-based formulas (`sending = guard.kind ===
   'sending'`, etc.), across 8 cases spanning every `(inFlight, unmet,
   confirmRaw)` combination the dialog can realistically be handed (idle /
   blocked / in-flight, crossed with untouched / wrong / correct typed
   count, crossed with one vs. two unmet reasons). 24 comparison tests plus
   1 sanity test (asserting exactly which cases are the two deliberate
   exceptions) — all 25 pass, executed and read, not just exit-code-checked.
2. **A structural grep** (`grep -n 'guard\.\|sendGuardState\|sending\b\|blockedAgain'
   web/src/views/admin/CampaignSendDialog.svelte`) confirms the real
   component's wiring matches what the test models exactly: `disabled=
   {sending}` on every control that was `disabled={inFlight}` before,
   `{#if blockedAgain}` reading `guard.kind === 'blocked'`, and
   `handleSubmit` gating on `guard.kind !== 'ready'` — no raw `inFlight`
   left in the template or in any handler.

What this does **not** prove: actual DOM rendering, or that a real click
sequence in a browser produces the panel/button states the truth table says
it should. That gap is the same one `#0119`'s review named for this
component and is unrelated to this issue's scope.

**Mutation-check caveat, stated rather than hidden.** Mutating the `.svelte`
source itself (e.g. reverting `handleSubmit` to `if (inFlight) return;`)
would NOT be caught by `CampaignSendDialog.guard.test.ts`, because that file
tests hand-written formulas modeling the component's logic, not the
component's compiled code (no Svelte component-testing tool is a project
dependency — see this file and `#0119`'s own review for precedent). The
grep above is what stands in for that proof, exactly as `#0119`'s
mutation-check 2 used a structural check for the same reason. `sendGuardState`
itself — the function whose precedence this issue is about — already has a
real mutation-check proof in `#0184`'s review (swapping its `inFlight`/`unmet`
branches turns a real test red); this issue does not re-derive that.

## Notes

Reported by `#0184`'s phase-3 review under `CLAUDE.md` §9. It was explicit that this does not weaken `#0184` — those tests pin a documented contract, and the contract is worth pinning either way.

Worth knowing from that review, because it is the strongest argument for option (a): the `inFlight`-before-`unmet` ordering is not cosmetic. `sending` warns against a retry, while `blocked`'s "Pre-send checks have not passed" **invites** the admin to fix and retry — the one action that risks a double send. That precedence matters, and right now the component that would act on it never asks.
