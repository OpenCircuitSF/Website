## Description

`web/src/lib/sendConfirm.ts`'s module header says consumers "must only ever branch on `.kind`, never recompute any of the conditions" — the point being that `sendGuardState` is the single place the send gate's precedence lives.

**`CampaignSendDialog.svelte` does not call `sendGuardState` at all.** It receives `sendInFlight` as a prop and consumes it as a raw boolean (`if (inFlight) return;`, `disabled={inFlight}`). The one production call site of `sendGuardState` hardcodes `inFlight: false`.

Two consequences, found by `#0184`'s review:

1. **`kind: 'sending'` has no production producer.** That branch, and its `sendGuardDescription` line, are unreachable from the UI.
2. **The dialog is doing exactly what the header forbids** — recomputing a condition the module owns.

Nothing is broken today: the raw-boolean checks happen to agree with what `sendGuardState` would return. But the module's stated invariant is not true of its only real consumer, and `#0184` has just pinned that precedence with tests — so the tests now guard a contract the app partly bypasses.

**Also, a stale comment on the same path.** `CampaignEditor.svelte:199` claims the dialog "re-evaluates `sendGuardState`". It imports only `normalizeCountInput`, `confirmMatches`, and `confirmHint`. That is the comment a future reader would trust about the send gate.

## Root cause

`CampaignSendDialog.svelte` predated `sendGuardState` entirely (or was never
migrated onto it when the module was introduced): it read `inFlight` as a
plain boolean prop and computed `blockedAgain = unmet.length > 0` itself,
duplicating exactly the conditions `sendGuardState` exists to own. Its
`handleSubmit` bail-out went further — it checked `inFlight` and the typed
count but never looked at `unmet` at all, so a same-count retry click could
call `onConfirm` again even while the "no longer ready to send" panel was
showing, which is precisely the double-send risk `#0184`'s review flagged the
inFlight-before-unmet ordering as protecting against. Because nothing in the
component asked the guard, `kind: 'sending'` had no production producer, and
the parent's own `editorGuard` hardcoded `inFlight: false`, masking the gap.

## Fix

Chose **(a)** — wired `CampaignSendDialog.svelte` through `sendGuardState`.
The case for (a) is what the issue's notes already argued: the ordering
inside `sendGuardState` is not cosmetic (`sending` warns against a retry;
`blocked`'s "Pre-send checks have not passed" invites one), and the dialog is
the one component that acts on a retry — so it is the one place that
precedence actually needs to be asked, not just possessed. (b) would have
required documenting a narrower, boolean-only contract that was *already
wrong* today (the retry-while-blocked gap below), so narrowing rather than
fixing would have shipped a "narrower but still incorrect" contract.

Concretely: `guard = sendGuardState({ status: 'draft', unmet, audienceCount:
summary.recipients, confirmRaw, inFlight })`. `status: 'draft'` is a
documented literal, not a re-derivation — the parent (`CampaignEditor.svelte`)
only ever mounts this dialog while `sendGateOpen` is true (itself gated on
`editorGuard.kind === 'ready'`, which requires `status === 'draft'`), and
closes the dialog before a successful send can move status past draft. Every
place that previously read the raw `inFlight` prop now reads a derived
`sending = guard.kind === 'sending'` instead (behaviourally identical, since
`sendGuardState` checks `inFlight` before `unmet` and `status` is fixed to
`'draft'`, so `kind === 'sending'` iff `inFlight`). `blockedAgain` now reads
`guard.kind === 'blocked'`. `handleSubmit` now gates on `guard.kind ===
'ready'` instead of re-deriving a match check, and since `ready` already
implies `confirmMatches(confirmRaw, summary.recipients)`, it passes
`summary.recipients` straight to `onConfirm` rather than re-parsing
`confirmRaw`.

This produced two deliberate, non-cosmetic behaviour changes, both found by
building the truth table rather than assumed going in:

1. **The blocked panel now defers to "Sending…"** in the one state where a
   retry has been resubmitted but the `unmet` array is still stale from the
   attempt that just failed (`inFlight` and non-empty `unmet` true at once,
   for one render). Previously both the "no longer ready to send" panel and
   the disabled/"Sending…" button rendered simultaneously — a confusing,
   self-contradictory state. Now `sending` wins, matching the precedence
   `sendGuardState` itself encodes.
2. **The double-send gap `handleSubmit` had is closed.** Before this change,
   an admin could retype (or leave typed) the matching count after a failed
   send, and clicking "Send now" again would call `onConfirm` even though
   `blockedAgain` was showing — the exact "retry while blocked" scenario the
   issue's notes warn is the one action that risks a double send. Gating on
   `guard.kind === 'ready'` refuses that submit.

Both are documented in the code (comments in `CampaignSendDialog.svelte`) and
proven in the new test file (see `## Verification`) rather than asserted.

Also fixed the stale comment at `CampaignEditor.svelte:199`: it claimed the
dialog "re-evaluates sendGuardState against what the operator actually
typed," which was false before this change (the dialog imported only
`normalizeCountInput`, `confirmMatches`, and `confirmHint`) and is now true —
reworded to say so explicitly and credit `#0186`.

### Claim 1 — the double-send path was real, and it is a UI defect rather than a duplicate send

Reconstructed from the pre-commit source (`git show 6d93213^:...`), not taken on
trust. The old `handleSubmit` was:

```js
if (inFlight) return;
const n = normalizeCountInput(confirmRaw);
if (n === null || !confirmMatches(confirmRaw, summary.recipients)) return;
onConfirm(n);
```

`unmet` appears nowhere in it, and the submit button's only disable condition was
`disabled={inFlight}`. So the path is real and reachable, not theoretical:

1. `onOpenSend` clears `sendUnmet = []` and opens the dialog (only possible while
   `sendGateOpen`, i.e. `editorGuard.kind === 'ready'`).
2. The admin types the matching count and submits — `onConfirmSend` sets
   `sendInFlight = true` and POSTs.
3. The server refuses with the `{"unmet":[...]}` 409 shape;
   `parseUnmetFromError` populates `sendUnmet`, and `finally` clears
   `sendInFlight`.
4. The dialog re-renders with `blockedAgain = unmet.length > 0` true — the "This
   campaign is no longer ready to send" panel — while `confirmRaw` still holds
   the matching count and **both the input and the Send button remain enabled**.
5. Clicking "Send now" again passes the old bail-out (`inFlight` false, count
   still matches) and calls `onConfirm` a second time.

**Severity: a real UI-correctness defect, not a data-integrity one.** It could
produce a redundant request that the server refuses, never two sends. Three
independent reasons, each checked in the source:

- The `unmet` prop is `sendUnmet`, which is populated *only* by
  `parseUnmetFromError` in `onConfirmSend`'s catch (`CampaignEditor.svelte`
  lines 513–516) and cleared only by `onOpenSend`. So "the blocked panel is
  showing" is equivalent to "the previous attempt was refused server-side and no
  send occurred." The extra click re-issues a request the server had just
  rejected, and `AdminCampaignsHandler.Send` re-runs `h.preflight.Check` and
  rejects it again.
- A genuine double-send would need the first attempt to have *succeeded* — but
  success sets `sendDialogOpen = false`, unmounting the dialog, and the old
  `if (inFlight) return;` already covered the in-flight window. The two clicks
  are strictly sequential; there is no concurrency here.
- The backstop is authoritative: `CampaignStore.Send`
  (`internal/mailing/campaigns.go`) performs a conditional
  `UPDATE email_campaigns … WHERE id = $1 AND status IN ('draft','failed')` and
  maps `pgx.ErrNoRows` to `ErrIllegalStatusTransition` → 409. The transition is
  atomic and cannot be replayed.

So the honest description is: **the dialog's irreversible primary action stayed
live while the dialog itself said the campaign was no longer ready to send.** That
is worth fixing on its own terms — it is exactly the "blocked copy invites a
retry" hazard `#0184`'s review named — but it was never one click away from
mailing the list twice. It is fixed here and fully documented in this issue, so it
needs no separate issue for the record.

**The new gate genuinely closes it.** `handleSubmit` is now `if (guard.kind !==
'ready') return;`, and `sendGuardState` returns `blocked` before it can ever
return `ready` whenever `unmet` is non-empty. Verified by execution, not reading —
see the truth table's `may-submit` row, where the two blocked-but-correctly-typed
cases are asserted `old = true, new = false`.

### Claim 2 — the `status: 'draft'` literal is safe today, and is a documented footgun under reuse

Checked the mount conditions directly rather than accepting the note.

- The dialog is mounted by `{#if sendDialogOpen && preflightSummary}`.
  `sendDialogOpen` is set true in exactly one place, `onOpenSend`, which returns
  early unless `sendGateOpen` — that is `editorGuard.kind === 'ready'`, and
  `sendGuardState`'s first branch returns `unavailable` for any
  `status !== 'draft'`. So the campaign is draft at mount.
- `canSendCampaign` (`web/src/lib/campaigns.ts:116`) is `status === 'draft'`,
  identical to the guard's own status branch, so the render gate and the guard
  cannot disagree — there is no "button renders but the gate never opens" state.
- **Nothing refetches `campaign` while the dialog is mounted.** The only
  `setInterval` in the editor is `nowTick` (line 353), a clock feeding
  `progressVerdict`, not a fetch. The other `campaign` assignments (`load`,
  `onTestSend`, `onConfirmCancel`) sit behind the modal backdrop, and
  `onConfirmSend` sets `sendDialogOpen = false` on success before the status can
  move past draft.

So the literal cannot be a lie in any state reachable today. **It does not stay
safe under reuse**, and that is worth saying plainly: the server accepts Send from
`failed` as well as `draft`, so a future "retry a failed campaign" entry point
that mounted this dialog would hand the guard `'draft'` when the truth is
`unavailable`, and the guard would answer `ready`. The mitigations are real — the
stand-in is documented both in the component header and at the derivation, and the
server's conditional UPDATE refuses regardless — so this is not a defect in the
commit. Threading `status` as a prop would be strictly better and is a one-line
change; reported below rather than filed (§9).

### Claim 3 — the truth table is complete on the dimensions that matter, faithful to the component, but its `oldMaySubmit` replica has a byte-level flaw

**Completeness.** All four `(inFlight, unmet)` combinations are present — (F,∅),
(F,≠∅), (T,∅), (T,≠∅) — which are genuinely all the reachable ones, plus a
one-vs-two-unmet variant. `audienceCount` is correctly fixed above zero: a
`summary.recipients` of 0 always arrives with a non-empty `unmet` (the server
emits `PreflightCodeEmptyAudience` whenever the count is 0), which closes the
gate, so the dialog cannot open on an empty audience — the same reachability
argument `#0184`'s review established. `status` is correctly fixed to `'draft'`,
with `sendConfirm.test.ts` covering the other branch.

`confirmRaw` is the thin dimension: `''`, `'999'` (non-matching number), and
`'482'` are covered, but whitespace-only and separator-bearing forms are not.
That under-coverage does **not** weaken the conclusion — in the real component
both the old and new formulas funnel `confirmRaw` through the same
`confirmMatches`, so old `= !inFlight && confirmMatches(raw, count)` and new

the `unmet` term. But it is what conceals the flaw below.

### The two behaviour changes, judged

**1. The blocked panel deferring to "Sending…" is correct**, and for exactly the
reason `#0184`'s review gave: `sending` ("a send is already in progress") warns
against a retry, while `blocked`'s "no longer ready to send" copy *invites* the
admin to fix and try again — the one action that risks a double send. Rendering
both at once was self-contradictory. One refinement the write-up overstates,
worth recording: after change 2, the triggering state is **no longer reachable
from this dialog at all**. `sendUnmet` is populated only in `onConfirmSend`'s
catch and cleared only by `onOpenSend`; reaching `inFlight` now requires
`guard.kind === 'ready'`, which requires `unmet` empty. It was reachable only via
the old double-send gap, which is how it was found. So change 1 is now defensive
rather than live — which is fine, and case 8 is still worth keeping as the pin
the mutation check above exercises.

**2. Closing the `handleSubmit` gap is correct and is the more important of the
two** — see Claim 1. Passing `summary.recipients` to `onConfirm` instead of
re-parsing `confirmRaw` is sound, since `ready` already implies
`confirmMatches(confirmRaw, summary.recipients)`, and it removes a re-derivation
the module header forbids.

Note that the unchecked acceptance criterion (`If (b): …`) is correctly unchecked
— (a) and (b) were mutually exclusive options and (a) was chosen.

### Reported for filing (§9 — not filed here)

Three observations, none a defect in this commit:

1. **`CampaignSendDialog.guard.test.ts:93` replicates `normalizeCountInput` with
   the wrong separator class** — ASCII space (U+0020) where the real function
   uses a thin space (U+2009), and without the `Number.isSafeInteger` guard. Inert
   today because no case contains a separator, and it fails loudly rather than
   silently if one is added. The fix is to call `normalizeCountInput`/
   `confirmMatches` directly in the replica instead of re-implementing them —
   which is also what makes the old formula genuinely "the old formula".
2. **Thread `status` into `CampaignSendDialog` as a prop** and drop the
   `'draft'` literal. Safe today (Claim 2), but the server already accepts Send
   from `failed`, so the first reuse of this dialog for a failed-campaign retry
   would silently feed the guard a false status.
3. **In `blocked` and `needs-confirm` states the Send button is enabled but
   `handleSubmit` now silently returns.** This matches the component's
   pre-existing pattern for `needs-confirm` (enabled button plus a `confirmHint`
   explaining), and the blocked panel carries `role="status"`/`aria-live`, so it
   is not a regression. But `#0119` solved the same problem better in the parent
   with `aria-disabled={!sendGateOpen}` plus an `aria-describedby` pointing at the
   reason; mirroring that here would finish the job this issue started.
