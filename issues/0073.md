# 0073 — The SEO renderer cache grows without bound on attacker-controlled keys

| | |
|---|---|

| **Phase** | 2 — Brand and marketing pages |

## Description

`internal/seo`'s `Renderer.cache` is keyed by request path and only ever written — never pruned or bounded. `InvalidateWorkshops` is the sole clearing path, and nothing calls it until `#0051`.

Any unauthenticated client can therefore grow the cache without limit by requesting distinct nonexistent paths. Measured against the real binary during `#0019`'s review: **RSS 59 MB → 212 MB after 25,000 requests to distinct unknown paths**, roughly 6 KB retained per path, with no authentication and no rate limit on the SPA route.

## Why it is also pure waste

Every unknown path renders the **identical** body — the 404 metadata bucket. Caching them per path stores thousands of copies of one value. Keying by the resolved metadata bucket rather than the raw path fixes the unbounded growth and the redundancy in one change.

## Acceptance criteria

- [ ] Cache entries are keyed by resolved metadata bucket, not raw request path — so all unknown paths share one entry
- [ ] The cache is bounded regardless of keying: a maximum entry count with a documented eviction policy, so no future key scheme can reintroduce unbounded growth
- [ ] A test drives many distinct unknown paths and asserts the entry count stays bounded — proven to bite by removing the bound and watching it fail
- [ ] Memory is re-measured the same way (RSS before and after N requests to distinct unknown paths) and the figure recorded in `## Verification`
- [ ] Cache correctness is preserved: known routes still render their own metadata, and `#0051`'s `InvalidateWorkshops` path still clears what it must
- [ ] `go build ./...`, `go vet ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported and zero skips

## Notes

Found during `#0019`/`#0020`'s review, which measured it on the running binary rather than inferring it from the code.

Severity is bounded — it needs sustained traffic to matter and the process restarts cheaply — but it is unauthenticated, trivially triggered, and grows monotonically, so it is a real availability issue rather than a tidiness one. Apache sits in front in production and could rate-limit, but relying on that leaves the defect in the service.

Note also, from the same review: `TestSite_InvalidateWorkshopsClearsBothCaches` does **not** actually guard both halves, despite `#0020`'s text and commit message claiming it does — deleting `s.sitemap.Invalidate()` leaves the suite green. The behaviour is correct; the guard is fiction. Fix that test as part of this issue, and prove the fix bites.
