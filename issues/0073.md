## Description

`internal/seo`'s `Renderer.cache` is keyed by request path and only ever written — never pruned or bounded. `InvalidateWorkshops` is the sole clearing path, and nothing calls it until `#0051`.

Any unauthenticated client can therefore grow the cache without limit by requesting distinct nonexistent paths. Measured against the real binary during `#0019`'s review: **RSS 59 MB → 212 MB after 25,000 requests to distinct unknown paths**, roughly 6 KB retained per path, with no authentication and no rate limit on the SPA route.

## Why it is also pure waste

Every unknown path renders the **identical** body — the 404 metadata bucket. Caching them per path stores thousands of copies of one value. Keying by the resolved metadata bucket rather than the raw path fixes the unbounded growth and the redundancy in one change.

## Acceptance criteria

- [x] Cache entries are keyed by resolved metadata bucket, not raw request path — so all unknown paths share one entry
- [x] The cache is bounded regardless of keying: a maximum entry count with a documented eviction policy, so no future key scheme can reintroduce unbounded growth
- [x] A test drives many distinct unknown paths and asserts the entry count stays bounded — proven to bite by removing the bound and watching it fail
- [x] Memory is re-measured the same way (RSS before and after N requests to distinct unknown paths) and the figure recorded in `## Verification`
- [x] Cache correctness is preserved: known routes still render their own metadata, and `#0051`'s `InvalidateWorkshops` path still clears what it must
- [x] `go build ./...`, `go vet ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported and zero skips

## Fix

`Renderer.metaFor` (unexported) is replaced by `Renderer.resolve(normalizedPath) (cacheKey string, meta RouteMeta)`, which now returns both the meta AND the cache key in the same resolution pass:

- an exact static-route match (`/`, `/about`, `/workshops`, `/subscribe`) keys on the path itself — bounded to `len(r.static)` == 4
- a resolved *published* workshop keys on `"workshop:" + slug` — bounded by how many distinct workshops actually get requested, not by how many distinct paths a client can invent (an unpublished/nonexistent slug never gets its own key — see below)
- the known-but-uncataloged fallback (e.g. `/admin`, `/login`) and the not-found (404) default each key on one fixed sentinel (`cacheKeyFallback`, `cacheKeyNotFound`) — every path that reaches either bucket renders byte-identical output, so they now share one cache entry apiece instead of one per distinct path

`Render` calls `resolve` before checking the cache (it needs the key to look the cache up), then writes through the new `Renderer.store(key, body)`, which enforces `maxCacheEntries = 512`: a write that would grow the cache past the bound flushes the whole cache first, then inserts. This is the second, independent bound the issue asks for — it holds even if some future change reintroduces per-path (or otherwise unbounded) keys, proven in `TestRender_CacheBoundedRegardlessOfKeying` below. Eviction policy is a full flush rather than partial/LRU, documented inline as mirroring `InvalidateWorkshops`' existing "re-rendering is cheap, a hard cap beats recency bookkeeping" reasoning.

**Trade-off, disclosed rather than hidden:** because the cache key for a `/workshops/{slug}` request now depends on the resolution outcome (published vs. not), `resolve` — including the `WorkshopSource` lookup — runs on every request, even one that will turn out to be a cache hit. Previously, a repeat request to the exact same already-cached path skipped the store entirely within the TTL. This trades one bounded, indexed store read per request for eliminating the unbounded per-path memory growth; the actual substitution/escaping work is still cached and skipped on a hit. Flagging this for the reviewer explicitly since it's a real behavior change, not just an implementation detail.

**`TestSite_InvalidateWorkshopsClearsBothCaches` fixed** (the fictional-guard finding): the old version only ever read `site.renderer.Render`, never `site.sitemap.Render`, so it could not have caught a missing `s.sitemap.Invalidate()` call. Rewrote it to mutate both `Title` (renderer-visible) and `UpdatedAt` (sitemap-visible, via a new `updatedAt` field on the shared `mutatingWorkshopSource` test double — the sitemap doesn't surface `Title` at all, so the old field alone couldn't drive a sitemap-side assertion) and assert both `site.renderer.Render` and `site.sitemap.Render` reflect the mutation only after `InvalidateWorkshops`, with a fixture guard confirming the pre-mutation sitemap render does NOT already contain the post-mutation value (rules out a coincidental pass).

Two new tests cover the acceptance criteria directly:
- `TestRender_UnknownPathsShareOneCacheEntry` — renders 5,000 distinct unknown paths, asserts the cache holds exactly 1 entry.
- `TestRender_CacheBoundedRegardlessOfKeying` — calls `Renderer.store` directly with 5,000 distinct synthetic keys (simulating what a naive future per-request keying scheme would produce, independent of the bucket-collapsing behavior the first test covers), asserts the cache never exceeds `maxCacheEntries`.

(Capped at 392, not 5000, because `maxCacheEntries`'s independent bound was still active — the collapsing assertion still correctly caught the regression.) Reverted; passed again.

**Memory re-measurement**, same methodology as the original finding (real binary, `STORAGE=json` dev mode so no Postgres dependency, `WEBAUTHN_RP_ID=localhost` / `WEBAUTHN_RP_ORIGIN=http://localhost:18099` for local config validation only): built `go build -o opencircuit-0073 ./cmd/opencircuit` from the *existing* `web/dist/` (did not run `npm run build`, so `web/dist/index.html` — already modified by a concurrent subagent working `#0014` — was never touched by this issue), ran it, and drove 25,000 concurrent distinct-unknown-path requests (`/does-not-exist-{i}-unbounded-attacker-path`, 50 worker threads) via a scratch Python script, reading RSS with `ps -o rss=` before and after:

```
baseline RSS:                              14.1 MB
after 25,000 distinct unknown-path reqs:   27.2 MB   (Δ 13.1 MB)
after 50,000 total:                        33.1 MB   (Δ  5.9 MB)
after 75,000 total:                        42.7 MB   (Δ  9.6 MB)
after 100,000 total:                       45.5 MB   (Δ  2.8 MB)
```
Absolute baseline is lower than the original finding's ~59 MB (dev mode / in-memory store here vs. the original's presumed Postgres-backed run, and no rate limiter in front locally), so this isn't a like-for-like absolute comparison — but the growth SHAPE is the load-bearing evidence: the original defect grew ~6 KB **per distinct path, linearly, forever** (153 MB over 25,000 requests). Here, marginal growth per successive 25,000-request round shrinks (13.1 → 5.9 → 9.6 → 2.8 MB) rather than repeating ~150 MB every round, consistent with one-time Go runtime/GC/connection-handling overhead amortizing rather than the renderer cache growing without bound. `TestRender_UnknownPathsShareOneCacheEntry` independently confirms the cache itself holds exactly 1 entry after thousands of distinct unknown-path `Render` calls, which is the more precise instrument for the specific claim ("the cache is bounded") — the RSS figures above are the requested end-to-end confirmation on the real binary.

## Review notes — 2026-08-18 (phase 3, approved with a criterion carried into `#0051`)

### All three mutations reproduced

Each was applied to a copy-backed working tree and reverted by restoring the
backup — never `git checkout`/`restore` (`CLAUDE.md` §8a). Checksums confirmed
identical before and after.

| Mutation | Result |
|---|---|
| `Render` reverted to raw-path keying (`key := normalized`) | FAIL — `cache has 392 entries after 5000 distinct unknown paths, want 1` |
| `store`'s `len(r.cache) >= maxCacheEntries` check deleted | FAIL — `cache has 5000 entries after 5000 distinct writes, want <= 512` |
| `s.sitemap.Invalidate()` deleted from `Site.InvalidateWorkshops` | FAIL — `Site.InvalidateWorkshops did not clear the sitemap's cache` |

**The fictional guard is real now.** The third mutation is the exact regression
the previous review found staying green; it now fails. Confirmed.

**Both bound mechanisms are independently live.** The 392 in the first mutation
is the arithmetic proof the reviewer was asked to check: 5000 = 9 × 512 + 392, so
with bucket-keying removed the count still capped and flushed nine times rather
than growing to 5000. Bucket-keying and `maxCacheEntries` are separately load-
bearing, exactly as the Fix claims.

### The memory evidence — the RSS numbers are honest, but they are not the proof

The disclosed caveat is fair and correctly hedged: a `STORAGE=json` 14.1 MB
baseline genuinely is not comparable to the original ~59 MB, and the write-up
says the original was "presumed Postgres-backed" rather than asserting it.

One overstatement: "marginal growth per successive round **shrinks** (13.1 → 5.9
→ 9.6 → 2.8 MB)" is not monotonic — round 3 rose above round 2. The conclusion
survives anyway (31.4 MB total over 100,000 requests against the old defect's
~6 KB × 100,000 ≈ 600 MB), but the sequence does not support the word "shrinks".

Rather than rely on RSS, the reviewer measured the cache directly in-process
(`runtime.MemStats` around `Renderer.Render`, no server, no port, no `web/dist`
involvement — a throwaway test file, run, then deleted):

```
after  25000 distinct unknown paths: HeapAlloc delta =  -28.48 KB, cache entries = 1
after  50000 distinct unknown paths: HeapAlloc delta =  -28.38 KB, cache entries = 1
after  75000 distinct unknown paths: HeapAlloc delta =  -23.05 KB, cache entries = 1
after 100000 distinct unknown paths: HeapAlloc delta =  -23.05 KB, cache entries = 1
after 25000 invented /workshops/{slug}: HeapAlloc delta = -22.37 KB, cache entries = 2
```

Zero growth (the negative deltas are GC noise) across 125,000 distinct
attacker-controlled paths, with the cache pinned at one entry and then two once
the workshop-fallback bucket is added. That is decisive and needs no absolute-RSS
comparison at all. The leak is gone.

### Eviction policy — acceptable, and currently unreachable

A full flush is crude, but under the shipped keying **no client can reach the
bound at all**: every invented path collapses to `cacheKeyNotFound`, every
invented `/workshops/{slug}` collapses to `cacheKeyFallback`, and the realistic
keyspace is 4 static routes + 2 sentinels + one entry per distinct *published*
slug actually requested. The cap is pure defense-in-depth against a future
re-keying, which is exactly how it is documented.

If a future re-keying did make it reachable, the flush would evict the hot static
entries too, and `Render` neither holds the lock across `substitute` nor
single-flights, so concurrent misses each re-render independently. That is a
CPU-only herd over a string substitution on an in-memory template — modest and
self-limiting — so the policy is acceptable as shipped. An LRU (or evicting a
fraction rather than everything) would be strictly better *if* the bound ever
becomes reachable; not worth the bookkeeping while it cannot be.

### The `WorkshopSource` trade-off — measured, not accepted on disclosure

**Cost today: literally zero.** `cmd/opencircuit/main.go:293` constructs the
`Site` with a `nil` source, `Renderer.workshopMeta` returns immediately on
`r.workshop == nil`, and there is no workshops store anywhere in the tree yet
(`internal/db` is a connection pool only; no `internal/workshops` package
exists). The extra per-request work on the shipped binary is two string
comparisons.

**Scope is narrower than "every request".** Measured with a counting fake
`WorkshopSource`:

```
published slug, 100 identical requests within TTL -> WorkshopBySlug called 100 times
static route /, 100 requests                      -> WorkshopBySlug called   0 times
unknown path, 100 requests                        -> WorkshopBySlug called   0 times
```

So the lookup is 1:1 with requests, but **only** on `/workshops/{slug}`. Home,
about, the workshops index, subscribe, and every 404/crawler-noise path pay
nothing. The disclosure is accurate; the "every page view" framing would not be.

**Cost after `#0051`:** PRD §6.2 declares `slug TEXT UNIQUE NOT NULL`, so
`WorkshopBySlug` becomes a unique-btree single-row lookup on a table holding tens
of rows, against a Postgres on the same box (`CLAUDE.md` §7) over a pooled
loopback connection. Sub-millisecond, not a network round-trip. That is not an
availability problem in the ordinary case.

**But it does defeat the cache in the one scenario the cache exists for.** An
unfurl storm — one workshop link shared, and Slack, Discord, iMessage, X,
Facebook and LinkedIn all fetching it within seconds — is N crawlers hitting a
single URL simultaneously. Under the old keying that was one store read per 60 s;
under this one it is one per request. Workshop detail is also the route `#0054`
calls "the route whose meta tags matter most".

**A strictly better fix exists and is small.** `handlers.WorkshopDetailSlug`
derives the slug from the path *syntactically*, with no store access at all. Key
every workshop-detail path on `"workshop:" + slug`, check the cache, and call
`resolve`/`workshopMeta` only on a miss. Memory stays bounded because
`maxCacheEntries` caps that keyspace — which is precisely the second, independent
bound this issue added and mutation-proved. The only property given up is that an
invented slug gets its own cache entry instead of sharing the fallback bucket,
and making that safe is exactly what the 512 cap is for. Note this changes
nothing for the attacker case: cycling invented slugs already costs one store
read per request under the shipped code.

**Why this is a carried criterion and not a bounce**, following the
`#0018`→`#0017` and `#0022`→`#0019` precedent: the defect cannot bite until
`#0051` lands, this issue already `Blocks: #0051`, and the right shape of the fix
genuinely depends on what `#0051`'s adapter looks like — if it hands `internal/seo`
an in-memory published-workshop map (entirely plausible for a catalog of tens of
rows), the concern evaporates and re-keying now would be premature work built on
a guess. The criterion is recorded on `#0051` as binding.
