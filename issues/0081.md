# 0081 — The async send queue has no shutdown, no regression guard, and leaks goroutines

## Description

`#0026` moved `mailer.Send` off the request goroutine into an in-process queue (256-deep, 4 workers), which closed a 100%-accurate enumeration oracle. The queue itself now needs the lifecycle work that was out of that issue's lane. Three defects, found and reproduced by `#0026`'s reviewer.

## 1. SIGTERM loses the email *and* silences the retry

There is no graceful shutdown anywhere in the repo: `mountAndServe` ends in `http.ListenAndServe`, no `signal.Notify` exists in any file, and the systemd unit sets no `KillSignal`/`TimeoutStopSec`.

Reproduced state after a kill mid-send: `confirm_sent_at` **stamped**, 0 emails sent, and **5 retries after restart → 0 emails**. The address goes quiet for up to an hour, self-healing only when the cooldown expires. The claim is never released.

**This is a regression from the pre-`#0026` behaviour**, and `#0026`'s `## Gotchas` claim that it is "no worse than before" is false — previously a killed send left `confirm_sent_at` NULL and the visitor's retry worked immediately. Every deploy is a `SIGTERM`.

## 2. Nothing guards the async-send property

Mutation-proved by the reviewer: **putting `mailer.Send` back on the request goroutine leaves the entire suite green.** The property that closed the oracle is unprotected, and the next person to touch this file can undo it silently.

## 3. `NewSubscribeHandler` leaks four goroutines per construction

The queue channel is never closed, so every handler constructed — including in tests — leaves four workers running.

## Acceptance criteria

- [ ] A `Close(ctx)` that closes the send queue and waits, bounded; an `http.Server` with `signal.Notify` in `cmd/opencircuit/main.go`; `TimeoutStopSec` in the systemd unit
- [ ] On shutdown, queued and in-flight claims are **released**, so a visitor's retry sends immediately rather than being silenced for the cooldown window
- [ ] **Reproduce the current failure first** — kill mid-send, confirm `confirm_sent_at` stamped and retries silent — then show it fixed
- [ ] A **deterministic, non-timing** regression test for the async property: use a blocking mailer and assert the `202` is written *before* the mailer is entered. Mutation-proven by moving `Send` back onto the request goroutine and watching it fail
- [ ] `NewSubscribeHandler`'s goroutines are cleaned up; no leak across repeated construction
- [ ] Correct `#0026`'s `## Gotchas` — the "no worse than before" claim is false and should not stay in the record
- [ ] `go build ./...`, `go vet ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported, zero skips, `-race` clean

## Notes

**A token-sweep ticker does not help here** — the reviewer checked. It cannot distinguish an in-flight claim from a dead one, and releasing claims older than the cooldown is a no-op since the cooldown is what expires anyway.

Keep the ratio between the send timeout and the cooldown: the unconditional `NULL` release is only safe because 30 s + 5 s is far below 1 h. If either constant changes, revisit it.

`#0045` builds the campaign send worker and owns shutdown wiring, so it is the natural sibling — but this defect is live now, in a path already reachable, and should not wait for Phase 5.
