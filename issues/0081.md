## Description

`#0026` moved `mailer.Send` off the request goroutine into an in-process queue (256-deep, 4 workers), which closed a 100%-accurate enumeration oracle. The queue itself now needs the lifecycle work that was out of that issue's lane. Three defects, found and reproduced by `#0026`'s reviewer.

## 1. SIGTERM loses the email *and* silences the retry

There is no graceful shutdown anywhere in the repo: `mountAndServe` ends in `http.ListenAndServe`, no `signal.Notify` exists in any file, and the systemd unit sets no `KillSignal`/`TimeoutStopSec`.

Reproduced state after a kill mid-send: `confirm_sent_at` **stamped**, 0 emails sent, and **5 retries after restart → 0 emails**. The address goes quiet for up to an hour, self-healing only when the cooldown expires. The claim is never released.

**This is a regression from the pre-`#0026` behaviour**, and `#0026`'s `## Gotchas` claim that it is "no worse than before" is false — previously a killed send left `confirm_sent_at` NULL and the visitor's retry worked immediately. Every deploy is a `SIGTERM`.

## 2. Nothing guards the async-send property

Mutation-proved by the reviewer: **putting `mailer.Send` back on the request goroutine leaves the entire suite green.** The property that closed the oracle is unprotected, and the next person to touch this file can undo it silently.

## 3. `NewSubscribeHandler` leaks four goroutines per construction

The queue channel is never closed, so every handler constructed — including in tests — leaves four workers running.

## Root cause

`#0026`'s phase-3 rework (`5d86b4d`) moved `mailer.Send` off the request goroutine and made the resend cooldown an atomic **claim-before-send**
(`ClaimConfirmationSend`/`ClaimAlreadySubscribedSend`, an `UPDATE` that stamps `confirm_sent_at` *before* the message is even enqueued). That claim is
exactly right for concurrency (a claim taken and then never sent is `ReleaseConfirmationClaim`'d on a normal send failure), but it created a new failure
mode that stamping-after-send never had: if the goroutine holding the claim disappears — a `SIGTERM` with no handler, which is every deploy and every
systemd restart — the compensating release code never runs. Pre-`#0026`, a killed synchronous send meant the stamp itself never happened
(`confirm_sent_at` stayed `NULL`); post-`#0026`, the stamp happens first and the send (and its release-on-failure) happens second, off-goroutine, so a
kill in between leaves the claim stamped with nothing sent and no release. Nothing in the repo caught this: no graceful shutdown existed anywhere
(`mountAndServe` ended in a bare `http.ListenAndServe`, no `signal.Notify`, no `KillSignal`/`TimeoutStopSec` in the systemd unit), so a real `SIGTERM`
terminated the process mid-send with zero chance for any Go code — deferred or otherwise — to run. `#0026`'s own `## Gotchas` recorded this as "no worse
than before this fix," which the reproduction below (and its own reviewer, `## Review verification` §5–6) shows is false: it is strictly worse, because
the earlier synchronous design had no separate claim step to leave stranded.

The second and third defects are consequences of the same gap: because nothing ever called anything resembling `Close`, there was no regression test
possible for "does a response ever wait on the mailer" that would also fail if someone quietly reintroduced a wait — and the four worker goroutines
`NewSubscribeHandler` starts had no path to ever terminate, leaking on every construction (production has one long-lived handler, so this was invisible
there; the test binary accumulates one leak per constructed handler across this package's ~20 call sites).

### Reproduction, before the fix (captured via a throwaway test, `internal/handlers/zz_shutdown_repro_test.go`, deleted before the commit — matching `#0026`'s own `zz_timing_proof_test.go` convention)

A Go test process cannot `SIGTERM` itself without killing the test binary running the assertions, so "process death mid-send" is modeled as "the
goroutine holding the claim is abandoned — nothing ever signals it, nothing ever calls its release path." That is exactly what a real, unhandled
`SIGTERM` does to every in-flight goroutine: the Go runtime stops the process immediately and no deferred function anywhere executes. From the
database's point of view the two are indistinguishable. Concretely: a signup was submitted against a mailer that blocks forever inside `Send` (release
channel never closed), the worker was confirmed to have actually entered `Send` (not merely queued), and — critically — `#0081`'s own new `Close`
method was **not called anywhere in this reproduction**, standing in for "nothing in `main.go` invokes it," which was true for every deploy before this
issue's fix:

## Fix

- **`internal/handlers/subscribe.go`** — `SubscribeHandler` gained `sendCtx`/`sendCancel` (a cancellable context every worker's per-job timeout is now
  derived from, `context.WithTimeout(h.sendCtx, sendJobTimeout)`, replacing `context.Background()`) and `closeMu`/`closed` (guarding `enqueueSend`
  against a send on a channel `Close` has closed). `Close(ctx context.Context) error`: idempotent, safe to call concurrently with in-flight `Subscribe`
  requests. It flips `closed`, cancels `sendCtx` (interrupting any send that is queued-but-not-started or actively in flight — if the mailer respects
  context cancellation, which the real `SESMailer`'s AWS SDK call does, this makes a stuck send fail in milliseconds rather than running out
  `sendJobTimeout` or forever), and closes `sendQueue` so every `runSendWorker` goroutine exits once drained. Every interrupted send takes
  `processSendJob`'s **existing** failed-send path — logged, claim released via `releaseSendClaim`'s own short-lived 5s context (deliberately not
  derived from `sendCtx`, so a release attempt is never itself defeated by the cancellation that doomed the send it's compensating for) — so this fix
  is additive to code that was already correct for an ordinary failure; it just gives shutdown a way to trigger that same path instead of the goroutine
  vanishing with no path triggered at all. `enqueueSend` now holds `closeMu` across its channel-send `select`, so it can never race `Close`'s own
  `close(h.sendQueue)` (which would panic if a send landed on it after close) — either the job is queued before `Close` closes the channel, or
  `closed` is already visible and the job takes the same drop-and-release path a saturated queue already used.
- **`cmd/opencircuit/main.go`** — `mountAndServe` now builds an `*http.Server` instead of calling `http.ListenAndServe` directly, registers
  `signal.Notify(sigCh, syscall.SIGTERM, syscall.SIGINT)`, and on receiving either signal: calls `subscribeH.Close(ctx)` (nil-guarded for dev mode) then
  `srv.Shutdown(ctx)`, both bound by one shared `shutdownTimeout` (20s) context. `Close` runs first so any request still inside `enqueueSend` when
  shutdown begins is already guarded by `closeMu`/`closed` rather than racing `srv.Shutdown`'s own drain of in-flight handlers. The three existing
  `mountAndServe`-based wiring tests (`admin_wiring_test.go`, `ratelimit_wiring_test.go`, `subscribe_wiring_test.go`) needed **no changes** — they never
  send a signal, so `mountAndServe` still blocks for the life of the test binary exactly as their own comments describe; the new behavior is additive,
  not a signature or behavior change on the path they exercise.
- **`deploy/systemd/opencircuit.service`** — added `KillSignal=SIGTERM` (systemd's existing default, set explicitly so the pairing with the process's
  own handler is visible from this file alone) and `TimeoutStopSec=30`, which must exceed `main.go`'s `shutdownTimeout` (20s) or systemd `SIGKILL`s the
  process before the graceful sequence can finish.
- **`internal/handlers/subscribe_test.go`** — added `blockingMailer` (a `Mailer` whose `Send` blocks until a test-controlled `release` channel closes
  or its `ctx` is cancelled, closing `entered` the instant `Send` is called), and three new permanent tests (below). `subscribeMux` now takes `*testing.T`
  and registers `t.Cleanup(func() { h.Close(...) })`, so this package's ~20 call sites stop leaking `sendWorkerCount` goroutines per construction —
  before `Close` existed there was no way to stop them at all.

- **`issues/0026.md`'s `## Gotchas` correction was made in the working copy, not committed with the code.** Per this issue's own instructions ("commit
  code only... do not commit the issue markdown"), `issues/0026.md` is left as an uncommitted working-copy edit alongside this issue's own `Status`
  staying at `in-progress` — both are intentional, not omissions. The correction itself: struck the "no worse than before this fix" sentence and
  replaced it with a dated correction citing `#0081`'s reproduction and fix, matching the file's own convention for superseded Gotchas elsewhere in
  that document (`~~struck~~` + a following note).
- **`internal/middleware` excluded from the "zero failures" claim, not overlooked.** A concurrently in-progress subagent (`#0080`) has an
  uncommitted throwaway reproduction file, `internal/middleware/zz_review0080_temp_test.go`, that fails by design (it's mid-reproduction of that
  issue's own bug, the same convention this issue's own now-deleted `zz_shutdown_repro_test.go` used). `internal/middleware` is explicitly outside
  this issue's lane; not touched, not fixed, not the responsibility of this pass.
- **`Close` cancels `sendCtx`, not `job.release`'s own compensating context.** `releaseSendClaim` deliberately builds its own fresh 5s
  `context.Background()`-derived context rather than reusing `sendCtx` — if it reused `sendCtx`, a shutdown-driven cancellation would defeat the very
  release call that shutdown exists to guarantee. This was already true before this issue (carried in from `#0026`'s design); worth restating because
  it's the reason `Close` works at all rather than being a second thing this issue had to add.
- **Whether a shutdown-interrupted send might have actually landed at the provider before the context cancellation reached it is not something this
  fix can resolve.** `SESMailer.Send`'s context cancellation races the SES API call the same way any HTTP client's context cancellation does — if the
  send request had already reached SES and the response was merely still in flight when cancelled, the claim is released and a retry sends a **second**
  email to that address. This is the same trade-off `#0026`'s original design already accepted for an ordinary network timeout/error (see
  `subscribe.go`'s package doc comment: "the next legitimate request for that address attempts the send again") — this issue does not change that
  trade-off, only makes shutdown take the same path instead of leaving the claim stranded. A duplicate confirmation email is a mild annoyance; a
  stranded claim silencing a real subscriber for an hour is the defect this issue exists to fix. Worth knowing for `#0045`, which reuses this pattern
  for real outbound campaign sends where a duplicate is more visible.
- **`shutdownTimeout` (20s) is a new package-level const in `cmd/opencircuit/main.go`, chosen, not derived from anything upstream.** It bounds
  `subscribeH.Close` and `srv.Shutdown` combined, on one shared context. In steady state this returns in well under a second (`sendCtx` cancellation
  makes a stuck send fail almost immediately if the mailer respects context, which `SESMailer`'s AWS SDK call does); 20s is a ceiling for the case
  where it doesn't, not an expected wait. `deploy/systemd/opencircuit.service`'s `TimeoutStopSec=30` must stay above this constant, or systemd
  `SIGKILL`s the process before the graceful sequence can finish on its own — flagged here since the two live in different files with no compiler
  link between them.
- **Neither `sendJobTimeout` (30s) nor the resend cooldowns (1h each) were changed.** The issue asked to flag this explicitly if either moved; neither
  did, so the 30s+5s-vs-1h ratio `ClaimConfirmationSend`'s unconditional-`NULL`-release safety argument depends on (see `#0026`'s `## Review
  verification` §6) is unchanged.
- **A token-sweep ticker was not built.** Per the issue's own note: it cannot distinguish an in-flight claim from a dead one, and a sweep that releases
  claims older than the cooldown is a no-op, since the cooldown predicate already expires them on its own. `Close`'s context-cancellation approach is
  the actual fix; no sweep exists in this codebase for this queue.
- **Not independently verified against a real SES send under a real `SIGTERM`.** Every test here uses `mailing.RecordingMailer` or a test-only
  blocking mailer, per `CLAUDE.md`'s "no network calls in the suite" convention (also true of `#0026`'s own tests) — the interruption mechanism
  (context cancellation reaching an in-flight AWS SDK call) is standard `net/http`/AWS-SDK-for-Go behavior, not something specific to this code, but it
  was not exercised against the real network here.

### 🔴 Blocking — `enqueueSend`'s `sendWG.Add(1)` races `Close`'s `sendWG.Wait()`, and the process panics

`enqueueSend` calls `h.sendWG.Add(1)` **before** it takes `closeMu`, so the Add
is entirely unsynchronised with `Close`'s `h.sendWG.Wait()`. That is the misuse
`sync.WaitGroup` explicitly documents ("calls with a positive delta that start
when the counter is zero must happen before a Wait") and Go detects it and
panics rather than corrupting silently. Reproduced against `94265f8`, unmodified:

```
panic: sync: WaitGroup is reused before previous Wait has returned

goroutine 89570 [running]:
sync.(*WaitGroup).Wait(0x6935417dd280)
	/opt/homebrew/Cellar/go/1.26.3/libexec/src/sync/waitgroup.go:213 +0x150
github.com/.../internal/handlers.(*SubscribeHandler).Close.func1()
	internal/handlers/subscribe.go:440 +0x2c
created by ...Close in goroutine 89569
	internal/handlers/subscribe.go:439 +0x1d0
```

Reproduction shape: one job in flight, `Close` called (so its waiter goroutine
is parked in `Wait`), then the last `Done` raced against one concurrent
`enqueueSend`. Hit at ~5,500 rounds. **Control:** the identical loop with the
concurrent `enqueueSend` removed survived 30,000 rounds clean — so the trigger
is specifically `Add` racing `Wait`, not the harness.

Why it matters rather than being a curiosity:

- The panic is in a bare goroutine inside `Close`; nothing recovers it. It
  **kills the process during graceful shutdown**, which strands exactly the
  claim this issue exists to release. The failure mode this fix removes comes
  back, now with a crash in the journal.
- `-race` does **not** flag it (the whole suite is `-race` clean), so no
  existing verification would ever surface it.
- `Close`'s own doc comment asserts it is "safe to call concurrently with
  in-flight `Subscribe` requests still calling `enqueueSend`". That is the one
  thing it is not.
- `Close`'s doc comment also tells `#0045` to "reuse this pattern ... rather
  than inventing a second one", so shipping it propagates the bug into the
  campaign send worker, where concurrency is far higher.

**Fix is small.** Move `sendWG.Add(1)` inside the `closeMu` critical section,
after the `closed` check — every Add then happens-before `Close` sets
`closed = true` under the same mutex, so no Add can ever occur once `Close` has
started waiting. (The `sendWG.Done()` on the two drop paths moves with it.)

### 🔴 Blocking (same defect, other half) — `main.go` calls `Close` *before* `srv.Shutdown`, which is the opposite of what `Close` documents

`subscribe.go`'s `Close` doc comment:

> `cmd/opencircuit/main.go`'s `mountAndServe` calls this from its SIGTERM/SIGINT
> handler, **after** `http.Server.Shutdown` has stopped accepting new
> connections and drained in-flight ones — ... by the time it returns no
> request goroutine can still be inside `enqueueSend`.

`main.go` does the reverse: `subscribeH.Close(ctx)` first, `srv.Shutdown(ctx)`
second, with its own comment arguing for that order. One of the two is wrong,
and it is the code — the doc comment describes the ordering that would make
the race above unreachable, because after `srv.Shutdown` returns there are no
request goroutines left to call `enqueueSend` at all. `main.go`'s stated reason
for going first (avoid racing `close(h.sendQueue)`) is already fully handled by
`closeMu` in either order.

Please pick one order and make the code and both comments agree.
`Shutdown`-then-`Close` is the safer of the two and is what `Close` already
claims; it should be done **in addition to** the `Add`-under-`closeMu` fix, not
instead of it (a bounded `srv.Shutdown` can return with a handler still
running).

### Non-blocking note for whoever picks this up

`mountAndServe` never calls `signal.Stop(sigCh)`. In production that is fine
(the process is exiting), but in the test binary the three other
`mountAndServe`-based wiring tests leave permanent `SIGINT`/`SIGTERM`
registrations on buffered channels nobody reads, which makes the binary
*swallow* both signals — verified with a minimal standalone program. A `Ctrl-C`
on a hung `go test ./cmd/opencircuit/...` will now leave an orphaned test
binary still holding `testdb.Lock`'s advisory lock, blocking every other
package's DB tests until it is killed by hand. A `defer signal.Stop(sigCh)` in
`mountAndServe` costs nothing and removes it.
