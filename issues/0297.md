## Description

Three orphan windows now have the same shape of problem, because `ClaimDue` and
`ClaimBatch` stamp **one `claimed_at` per batch** and then the rows are
processed serially:

| Window | Where | Honest batch-derived value |
|---|---|---|
| `outboxOrphanStaleAfter` | `internal/mailing/outbox_worker.go` | **700s** (`#0284`) |
| ~~`orphanStaleAfter`~~ | ~~`internal/mailing/worker.go`~~ | **not affected — see the correction below** |
| `intakeOrphanStaleAfter` | `internal/handlers/subscribe_intake.go` | ~200s (`#0294`) |

Each is being corrected to a value derived from `batchSize × per-row bound`,
because that is what the current claim model actually permits. The values are
honest and the derivations are right. They are also **large**, and the reason is
structural rather than necessary: the last row of a batch is treated as having
been claimed since before the first row was even attempted.

**The alternative, named by `#0284`'s reviewer: re-stamp `claimed_at` on each
row as processing of that row begins.**

> **Correction (#0295, 2026-08-27).** `internal/mailing/worker.go` is **not** one
> of the three, and **already implements exactly this design** — so the pattern
> below is not hypothetical, it has a working reference in this codebase. Read
> it first. `SendStore.ClaimBatch` never touches `claimed_at` or status; it only
> selects and rechecks eligibility, leaving rows `'queued'`. The atomic claim
> (`status='sending', claimed_at=now()`) is `SendStore.ClaimRow`, issued as the
> **first statement inside `sendOne`**, per recipient, at the moment that
> recipient's send begins. Batch size therefore never enters its bound, which is
> why its 70s window carries 35s of real margin rather than the near-zero the
> outbox worker had. The row above naming `worker.go` was wrong, and `#0295`
> resolved by correcting the premise rather than changing a constant. A row's claim age would then measure its
own processing rather than its predecessors', and every window collapses to a
per-row bound — roughly 35s for the outbox worker instead of 700s.

## Why this is worth doing, and why it is not urgent

The cost of a large window is **recovery latency on the crash path only**.
`Stop` already releases claims on graceful shutdown, so the window only governs
how long a row stays stuck after a hard kill. Nothing is incorrect today.

The cost of getting it *wrong* in the other direction is a duplicate send, which
is `#0254`'s defect — a duplicate confirmation link or recovery magic link.

So: not urgent, and deliberately not folded into `#0284`, `#0294`, or `#0295`,
each of which correctly fixed its derivation under the existing claim model
rather than changing the model inside a bounce fix.

## Acceptance criteria

1. `claimed_at` is re-stamped per row at the point processing of that row
   begins, in the shared `internal/outbox` claim path, so all three consumers
   benefit rather than one.
2. The re-stamp must not create a window where a row is claimed by nobody — the
   transition from batch claim to per-row claim has to be safe against a sweep
   running between them. Enumerate the states and prove it.
3. Each of the three windows is then re-derived from the per-row bound, and each
   doc comment states the new model. `#0284`, `#0294`, and `#0295` must be
   resolved before this starts, or this will conflict with all three.
4. **Do not assert a bound the code does not have.** `#0284` bounced for exactly
   that; its review notes carry the reasoning about `rate.Limiter` regenerating
   tokens during a send, which this change is what would finally make irrelevant.
5. The invariant tests from `#0284`/`#0294`/`#0295` are updated, not deleted, and
   each must still fail when its fix is reverted. Note `#0284`'s reviewer found
   one test that passed against full reversion — check for that failure mode
   explicitly.
6. A DB-backed test drives the crash path: kill processing mid-batch, and assert
   both that unprocessed rows are reclaimable promptly and that a row still
   being processed is not swept.
7. Not a load or performance exercise (CLAUDE.md §5). The justification is model
   correctness and recovery latency, expressed in the code's own constants.
8. `ISSUE=NNNN scripts/check.sh go ./internal/outbox/... ./internal/mailing/... ./internal/handlers/... ./cmd/opencircuit/...`
   passes with no skips.
