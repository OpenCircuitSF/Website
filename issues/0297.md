## Description

Three orphan windows now have the same shape of problem, because `ClaimDue` and
`ClaimBatch` stamp **one `claimed_at` per batch** and then the rows are
processed serially:

| Window | Where | Honest batch-derived value |
|---|---|---|
| `outboxOrphanStaleAfter` | `internal/mailing/outbox_worker.go` | **700s** (`#0284`) |
| ~~`orphanStaleAfter`~~ | ~~`internal/mailing/worker.go`~~ | **not affected — see the correction below** |
| `intakeOrphanStaleAfter` | `internal/handlers/subscribe_intake.go` | ~200s (`#0294`) |

Each is being corrected to a value derived from `batchSize × per-row bound`,
because that is what the current claim model actually permits. The values are
honest and the derivations are right. They are also **large**, and the reason is
structural rather than necessary: the last row of a batch is treated as having
been claimed since before the first row was even attempted.

**The alternative, named by `#0284`'s reviewer: re-stamp `claimed_at` on each
row as processing of that row begins.**

> **Correction (#0295, 2026-08-27).** `internal/mailing/worker.go` is **not** one
> of the three, and **already implements exactly this design** — so the pattern
> below is not hypothetical, it has a working reference in this codebase. Read
> it first. `SendStore.ClaimBatch` never touches `claimed_at` or status; it only
> selects and rechecks eligibility, leaving rows `'queued'`. The atomic claim
> (`status='sending', claimed_at=now()`) is `SendStore.ClaimRow`, issued as the
> **first statement inside `sendOne`**, per recipient, at the moment that
> recipient's send begins. Batch size therefore never enters its bound, which is
> why its 70s window carries 35s of real margin rather than the near-zero the
> outbox worker had. The row above naming `worker.go` was wrong, and `#0295`
> resolved by correcting the premise rather than changing a constant. A row's claim age would then measure its
own processing rather than its predecessors', and every window collapses to a
per-row bound — roughly 35s for the outbox worker instead of 700s.

## Why this is worth doing, and why it is not urgent

The cost of a large window is **recovery latency on the crash path only**.
`Stop` already releases claims on graceful shutdown, so the window only governs
how long a row stays stuck after a hard kill. Nothing is incorrect today.

The cost of getting it *wrong* in the other direction is a duplicate send, which
is `#0254`'s defect — a duplicate confirmation link or recovery magic link.

So: not urgent, and deliberately not folded into `#0284`, `#0294`, or `#0295`,
each of which correctly fixed its derivation under the existing claim model
rather than changing the model inside a bounce fix.

## Acceptance criteria

1. `claimed_at` is re-stamped per row at the point processing of that row
   begins, in the shared `internal/outbox` claim path, so all three consumers
   benefit rather than one.
2. The re-stamp must not create a window where a row is claimed by nobody — the
   transition from batch claim to per-row claim has to be safe against a sweep
   running between them. Enumerate the states and prove it.
3. Each of the three windows is then re-derived from the per-row bound, and each
   doc comment states the new model. `#0284`, `#0294`, and `#0295` must be
   resolved before this starts, or this will conflict with all three.
4. **Do not assert a bound the code does not have.** `#0284` bounced for exactly
   that; its review notes carry the reasoning about `rate.Limiter` regenerating
   tokens during a send, which this change is what would finally make irrelevant.
5. The invariant tests from `#0284`/`#0294`/`#0295` are updated, not deleted, and
   each must still fail when its fix is reverted. Note `#0284`'s reviewer found
   one test that passed against full reversion — check for that failure mode
   explicitly.
6. A DB-backed test drives the crash path: kill processing mid-batch, and assert
   both that unprocessed rows are reclaimable promptly and that a row still
   being processed is not swept.
7. Not a load or performance exercise (CLAUDE.md §5). The justification is model
   correctness and recovery latency, expressed in the code's own constants.
8. `ISSUE=NNNN scripts/check.sh go ./internal/outbox/... ./internal/mailing/... ./internal/handlers/... ./cmd/opencircuit/...`
   passes with no skips.

### What was verified and is correct

**The core safety claim holds.** `ClaimRow` is genuinely atomic — a single
conditional `UPDATE ... WHERE id = $1 AND status = $3` with `RETURNING`, not a
read-then-write, so `pgx.ErrNoRows` → `claimed=false` is the real exclusivity
gate and `SelectDue`'s `FOR UPDATE SKIP LOCKED` is correctly described as free
insurance rather than the guarantee. Walked the three states the criterion asks
for:

- *Crash between `SelectDue` and `ClaimRow`* — the row never left `'queued'`,
  so it is immediately reclaimable and `OrphanSweep` (which only touches
  `'sending'`) never sees it. Confirmed by
  `TestOutbox_SelectThenClaimRow_CrashMidBatch`, which also proves the sweep
  still *does* discriminate (fresh claim not swept, zero-width window swept) —
  a genuine two-directional test, not a "never sweep" assertion.
- *Two workers racing `ClaimRow`* — `WHERE status = 'queued'` means at most one
  wins; the loser gets `claimed=false` and skips. Covered by
  `TestOutbox_ClaimRow_LosingRaceReturnsClaimedFalse`.
- *`Stop` mid-loop* — `pass`'s `stopCh` check sits before each `ClaimRow`, so
  rows not yet reached are still `'queued'`.

**`releaseAll` is a no-op, and the proof is stronger than claimed.** `Stop`
calls it only on the `<-w.doneCh` branch, i.e. only after `Run` has fully
returned; and in `pass` there is no `return` between `trackClaimed` and
`untrackClaimed` (`sendOne` has no internal `stopCh` check and there is no
`recover` in this file). So `w.claimed` is empty on *every* path that reaches
`releaseAll`, not merely the graceful one. The ungraceful path does not need it
either — a hard kill runs no Go code at all, and the orphan sweep is what
recovers there. Keeping it as a defensive net is a reasonable call and
`TestOutboxWorker_ReleaseAll_ConcurrentCallsDoNotRace` still covers it.

**Both windows re-derived independently by this review, from the code's own
constants, with nothing measured off the machine:**

*`outboxOrphanStaleAfter`.* `claimed_at` is stamped server-side when
`ClaimRow`'s `UPDATE` commits, at T. The client learns within
`writeStatusTimeout` (5s — `claimCtx`'s deadline; if it expires the call errors
and the row is not processed at all). `sendOne` then bounds `render` +
`mailer.Send` together in one `sendCtx` = `sendMessageTimeout` (30s). The
terminal write — `MarkSent`, or `finishFailed`, or
`deferMissingPhysicalAddress` — each runs on one `writeCtx` of
`writeStatusTimeout` (5s) and moves the row out of `'sending'`; checked that
`finishFailed`'s *two* round trips (`effectiveMaxRetries` then
`MarkRetryOrAbandon`) share a single 5s deadline rather than getting one each.
`RecordEvent` runs after the transition. `limiter.Wait` runs *before*
`ClaimRow`, so the rate limiter is out of the bound — which is exactly what
`#0284` could not achieve under the batch model. Batch size is not a term:
at most one row is `'sending'` under this worker at a time.
**Worst case = 30 + 2×5 = 40s. Window = 2 × (30 + 5) = 70s. Margin 30s.**
Matches the implementer's figures.

*`intakeOrphanStaleAfter`.* Same shape. Round-trip residual < `intakeRowTimeout`
(10s), then `processIntakeRow` bounds unmarshal, `IsSuppressed`, `FindByEmail`,
`dispatchMutation` (synchronous — it calls `newSignup`/`existingSignup` on the
same ctx, it does not enqueue) and `MarkSent` inside one further
`intakeRowTimeout` (10s). Batch size drops out.
**Worst case < 10 + 10 = 20s. Window = 2 × 10 = 20s.** Also matches — and this
is where the first defect is (defect 3, below). Sanity check on both: the old
values fall straight out of the same formulas with batch size restored — 20 ×
(30 + 2×5) = 800 and (20+1) × 10 = 210 — so the new numbers are the old
derivations with the batch term removed, which is precisely what the change
earns. Nothing here was sized against load; `uptime` at the start of this review
was 1.39.

### Defect 2 — three doc comments call a non-detached context "detached"

This is criterion 4's class ("do not assert a bound the code does not have"),
and it sits in the derivation paragraph itself. The bound is not falsified — a
`context.WithTimeout(parent, d)` is capped at `d` whichever parent it has — but
the word *detached* has a specific, load-bearing meaning in these two files
(`context.Background()`, so the write survives ambient cancellation), and
`#0302` in this same batch uses it correctly for exactly that. Three new sites
use it for the opposite thing:

| Site | Comment says | Code is |
|---|---|---|
| `outbox_worker.go:122` | "wraps it in a detached `context.WithTimeout(ctx, writeStatusTimeout)`" | self-contradictory in one sentence |
| `outbox_worker.go:534` | "A detached, bounded context (**not the caller's ambient ctx**)" | `context.WithTimeout(ctx, …)` at line 538 — it *is* the caller's ambient ctx |
| `subscribe_intake.go:125` | "wrapped in a detached `context.WithTimeout(h.sendCtx, intakeRowTimeout)`" | derived from `h.sendCtx` |

**Remedy.** Do not change the code — deriving the claim from the ambient
context is defensible here (it stops a new claim being taken during shutdown,
which is the opposite of `#0302`'s failure-write case, where the write *must*
land). Change the three comments to say "bounded" rather than "detached", and
say in one sentence why this call is deliberately *not* detached while
`sendOne`'s writes are. `outbox_worker.go` lines 115/116/567/573 use "detached"
correctly for the `context.Background()` cases, so the file already sets the
meaning these three break.

### Defect 3 — `intakeOrphanStaleAfter` has exactly zero margin, and its test
### does not enforce the derivation

The window (20s) equals the worst case the doc comment itself computes (20s).
It is not *false* — `OrphanSweep`'s predicate is strict (`claimed_at < now() -
$3`) and a processed row's round-trip residual is strictly under 10s — but it
is the only one of the three windows with no engineered slack, against
`outboxOrphanStaleAfter`'s 30s and `orphanStaleAfter`'s 30s. And
`TestIntakeOrphanStaleAfterCoversSingleRowHold`'s oracle is `intakeRowTimeout`
alone (10s), i.e. **half** the derived bound, so the test would still pass at
11s — well inside the 20s worst case. The invariant that was derived is not the
invariant that is checked.

**Remedy.** Either raise the window to `3 * intakeRowTimeout` (30s), giving the
same 10s-of-margin-per-term posture the other two carry, or state explicitly in
the doc comment that this window is deliberately equal to its worst case and
why that is acceptable. Either way, raise the test's oracle to the derived
bound (`2 * intakeRowTimeout`) so it actually enforces the derivation — keeping
it a different *expression* from the subject, per `#0258`.

### Defect 4 — stale doc comments the change itself invalidated

Criterion 3 asks that each doc comment state the new model. Four were missed,
and three of them are in production code rather than tests:

- **`outbox_worker.go:353`, `Stop`'s own doc comment** — still says `Stop`

  `'queued'` (so a restart … picks it up immediately instead of waiting out
  `outboxOrphanStaleAfter`)". Under the new model that is unreachable, as this
  pass itself established. It also still says "whatever ids remain are exactly
  the rows `pass`'s `stopCh` check left claimed" — `pass`'s `stopCh` check now
  leaves none. `#0297` documented the no-op in the *test's* comment but left

- **`outbox_worker.go:419`, `trackClaimed`** — "so a `Stop` landing during the

  cannot observe it mid-send.
- **`subscribe_intake.go:292`, `processIntakeRow`** — "this call's own

- **`subscribe_intake.go:50`** — "`ClaimDue`'s `WHERE next_attempt_at <= now()`
  excludes it". That predicate is `SelectDue`'s for this poller now.

The last two are clearly misses rather than deliberate history: `#0297` rewrote
eight other `ClaimDue` references in that same file.

**Remedy.** Update all four. For `Stop`, say what is now true — it stops `Run`
and waits for it; `releaseAll` is retained as a defensive net that the current
`pass` provably never gives work to — which is a better comment than the one
there now, and matches what the test's doc comment already says.
