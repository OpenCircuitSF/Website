## Description

A transient bounce is not fatal, but an address that keeps soft-bouncing is dead. Suppress after a threshold rather than sending into a hole forever.

## Root cause

Not a bug fix — this issue closes the last named seam `#0038` deliberately
left open. `#0038` built the SES/SNS ingestion pipeline (one `pgx.Tx` per
message, spanning `email_events`, `suppressions`, and the subscriber status
write) and gave `applyBounce`'s `BounceTypeTransient` arm a comment naming
this issue as the owner of the counting logic and the threshold suppression.
Everything needed to build it — the partial index, the reason constant, the
`AddTx`/`MarkBouncedTx` pair — already existed; only the read and the
threshold comparison were missing.

## Fix

Followed the carried-in seam description exactly: the addition is entirely
inside `applyBounce`'s `case sesnotify.BounceTypeTransient:` arm in
`internal/handlers/ses_notifications.go`, and nothing else in `#0038`'s code
changed.

- **`internal/sesnotify/store.go`** — new `CountRecentTransientBounces(ctx, q
  querier, recipient string, since time.Time) (int, error)`, over the
  package's existing unexported `querier` so it can run inside the caller's
  `tx` (the mandatory in-transaction read `FindByEmailTx` already
  precedents). Windowed on `received_at` (not the nullable `event_at`) so it
  hits `migrations/000014`'s `idx_email_events_soft_bounce` partial index —
  confirmed genuinely no new migration was needed for this query, matching
  the carried-in note. Also added `CountRecentTransientBouncesPool`, a
  pool-only twin with no `querier` parameter, so the admin subscriber detail
  view (a different package, no open transaction) can depend on it through a
  genuine narrow interface — the same reasoning the package doc comment in
  `ses_notifications.go` already gives for why `events`/`subs`/`suppr` are
  held concretely there instead.
- **`migrations/000015_seed_soft_bounce_settings.{up,down}.sql`** — new. The
  carried-in note "no migration is needed" was about the counting query's
  index, which is correct and unchanged. It does not cover seeding the two
  new `settings` rows the "threshold values live in `settings`, not
  hardcoded" criterion requires: `UpdateSetting` only mutates an *existing*
  key, so a row must exist before `PATCH /admin/settings` can ever touch it
  — the same reason `migrations/000008` seeds `physical_address`. Seeds
  `soft_bounce_threshold_count` = `5` and
  `soft_bounce_threshold_window_days` = `30`, matching PRD §6.5's "5 soft
  bounces in 30 days". Confirmed `000014` was the highest migration on disk
  before writing this as `000015` (append-only, CLAUDE.md §1).
- **`internal/handlers/soft_bounce.go`** — new, shared between the SES
  ingestion handler and the admin subscriber detail view so the two can
  never disagree on what "the threshold" means: the two setting-key
  constants, the PRD defaults, `softBounceSettingsReader` (a genuine narrow
  interface — `GetSetting(ctx, key)` takes no `querier`, unlike the
  transaction-scoped stores), and `softBounceThreshold`, which resolves the
  configured (count, window) pair and falls back to the default (with a
  logged warning) if a row is missing or fails to parse as a positive
  integer — a config hiccup must never break SES ingestion or the detail
  view.
- **`internal/handlers/settings.go`** — `validSettingValue` gained a case for
  both new keys: PATCH must reject anything that doesn't parse as a positive
  integer, so an admin can't silently write a value `soft_bounce.go`'s
  fallback would otherwise paper over.
- **`internal/handlers/ses_notifications.go`** — `NewSESNotificationsHandler`
  gained a `settings softBounceSettingsReader` parameter (`*auth.Store`
  satisfies it via its existing `GetSetting`, unmodified). The
  `BounceTypeTransient` arm: resolves the threshold, calls
  `CountRecentTransientBounces` against `tx` (so the count includes the
  bounce this same request just inserted — never one bounce stale), and on
  `count >= threshold` performs the same `AddTx(SuppressionReasonRepeatedSoftBounce)`
  + `MarkBouncedTx` pair the `Permanent` case already uses, plus an audit row
  carrying the count/threshold/window for evidence. Below threshold, returns
  `nil` exactly as `#0038` left it. The settings read is deliberately **not**
  transaction-scoped — unlike the count, the threshold configuration has no
  staleness relationship to this request's own writes.
- **`Undetermined` bounces are decided NOT to count.** `#0038`'s plan §8
  left this as this issue's call, recommending counting since "an
  unclassifiable repeated failure is a dead address". Decided the other way:
  the partial index this query needs is scoped to
  `bounce_type = 'Transient'` only, and the acceptance criterion's own
  wording is "5 *transient* bounces". Widening the count to include
  `Undetermined` would mean either an unindexed scan or a second,
  separately-indexed query for a bounce subtype SES documents as rare.
  Recorded as a deliberate, reversible scope decision rather than silently
  matching or silently ignoring the recommendation.
- **`internal/handlers/admin_subscribers.go`** — the "admin can see the
  current soft-bounce count" criterion. New `softBounceCounter` narrow
  interface (`*sesnotify.Store` satisfies it via
  `CountRecentTransientBouncesPool`); `NewAdminSubscribersHandler` gained
  `bounces softBounceCounter, settings softBounceSettingsReader` parameters,
  both nil-tolerant (same STORAGE=json gap as `manualAdd`/`suppressions`).
  `Get` now populates three new `subscriberView` fields —
  `soft_bounce_count`, `soft_bounce_threshold`, `soft_bounce_window_days` —
  computed the same way the SES handler resolves the threshold, so the two
  can never show different numbers. Populated by `Get` only, like
  `Interests`; `List` is unchanged.
- **`cmd/opencircuit/main.go`** — `sesEventsStore` construction moved earlier
  (it is now a shared dependency of both `adminSubscribersH` and
  `sesNotifyH`); both handlers now also receive `store` (`*auth.Store`) as
  their settings dependency.
- **Web** (`web/src/lib/types.ts`, `admin.ts`, `web/src/views/Admin.svelte`)
  — `Subscriber` gained the three optional soft-bounce fields; new
  `softBounceSummary(sub)` in `admin.ts` (CLAUDE.md §1: SPA logic in
  `lib/`, components stay thin) renders "N transient bounces in the last W
  days (threshold: T)", with a distinct message when the count has already
  reached the threshold and a "Not available." fallback when the fields are
  absent (dev mode). `Admin.svelte`'s subscriber detail modal gained a "Soft
  bounces" section, right above the existing (still `#0038`-empty) "Email
  event history" section.
- **`docs/database.md`, `CLAUDE.md`** — new `000015` table row and the

  version of `TestStore_CountRecentTransientBounces_WindowSlides_ExcludesOlderEvents`
  seeded events a full minute inside/outside the window, which reads like a
  boundary test but is actually a full minute away from the operator that
  matters — it passed unchanged under a `>=`→`>` mutation. Only a fixture at

  `TestStore_CountRecentTransientBounces_WindowBoundaryIsInclusive`, added

  future "the window slides" test: "just inside" and "just at" are different

## Carried in from `#0038`'s implementation (2026-08-20)

`#0038` (`42d5104`, plus its second pass `d9e6a9c`) built the ingestion
handler and deliberately left this issue a single, named seam. Recorded here
so the seam does not have to be rediscovered by reading `#0038`'s `## Fix`.

- [x] **The insertion point is one `case` arm.**
      `internal/handlers/ses_notifications.go`'s
      `(*SESNotificationsHandler).applyBounce` switches on `ev.BounceType()`;
      its `case sesnotify.BounceTypeTransient:` arm currently returns `nil`
      with a comment naming this issue as its owner. Everything this issue
      adds goes inside that arm. Nothing else in `#0038` changes.
- [x] **It runs inside the caller's transaction.** `applyBounce` already
      receives the open `tx pgx.Tx` that spans the `email_events` insert, the
      suppression insert and the subscriber status write for one SNS message
      (`#0033`'s hard block). The count read and both writes must use that
      same `tx`, not the pool — a count read on the pool would not see the
      `email_events` row this very request just inserted, so the threshold
      would always be evaluated one bounce stale. `#0038`'s second pass
      (`d9e6a9c`) already moved the subscriber lookup in `applyRecipient` onto
      that same `tx` (`subscribers.Store.FindByEmailTx`), so there is a
      working in-transaction-read precedent in this exact call path to copy —
      and `TestSESNotifications_CrashWindowEquivalence_RetryLandsAllWrites`
      is the test that will catch it if a new write here is put on the pool
      by mistake.
- [x] **The shape of the addition**, per `#0038`'s plan §8:
      a `CountRecentTransientBounces(ctx, q, recipient, window)` read against
      `email_events` (new; `#0038` deliberately did **not** stub it, so it is
      this issue's to add in `internal/sesnotify/store.go` over that package's
      existing unexported `querier`), then — on threshold — the same
      `suppr.AddTx(ctx, tx, …SuppressionReasonRepeatedSoftBounce…)` +
      `subs.MarkBouncedTx(ctx, tx, sub.ID, now)` pair the `Permanent` arm
      already uses.
- [x] **No migration is needed.** `migrations/000014_create_email_events`
      already ships the partial index this issue's query wants:
      `idx_email_events_soft_bounce ON email_events (recipient, received_at DESC)
      WHERE event_type = 'Bounce' AND bounce_type = 'Transient'`. Note it is
      keyed on **`received_at`**, not `event_at` — window the query on
      `received_at` or the index will not be used. `event_at` is nullable
      (it is `NULL` whenever `mail.timestamp` was absent or unparseable), so
      `received_at` is also the more robust choice.
- [x] **`bounce_subtype` is recorded faithfully** on every row, so the
      out-of-office exclusion in `## Notes` above is decidable from
      `bounce_type`/`bounce_subtype` alone, exactly as that note requires.
- [x] **`Undetermined` is this issue's call.** `#0038` records the value and
      deliberately does not decide whether it counts toward the threshold; its
      plan §8 recommends counting it (an unclassifiable repeated failure is a
      dead address) but leaves the decision here.
- [x] **Thresholds come from `settings`.** `#0038` reads no settings at all
      and hardcodes no window or count, so nothing has to be un-hardcoded
      first.
- [x] **The staleness guard runs before `applyBounce`.**
      `applyRecipient` already returns early when the event's `mail.timestamp`
      predates the subscriber's `confirmed_at`, so a week-late transient
      bounce for a since-reconfirmed address never reaches this arm. Do not
      re-implement that check.
- [x] **`complained` stays terminal.** `MarkBouncedTx` routes through the
      shared `setStatusTx`, whose SQL preserves `complained` — so the
      threshold path cannot erase a complaint even when it fires
      (CLAUDE.md §9). Assert it rather than assuming it.
