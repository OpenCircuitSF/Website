## Description

User request, 2026-11-07: "add support to check if there is a matching event on Luma and show it on the Outreach screen … Showing a mismatch with Luma is also helpful so we should do that."

Open Circuit SF lists its events by hand on the Luma calendar <https://luma.com/opencircuitsf>. Nothing tells the user whether a published workshop has been added there, or whether its Luma copy still matches the site.

**Source: the calendar's public iCal feed. Luma's API is not an option.** The API needs Luma Plus, which the user is not buying yet (`#0649`). The feed needs no key:

    https://api.luma.com/ics/get?entity=calendar&id=cal-UIMZwzLquNDI2DB

It answered `200 text/calendar` on 2026-11-07 with six `VEVENT`s. Each one carries:
- `SUMMARY`
- `DTSTART` and `DTEND` in UTC
- `LOCATION`, which is folded across lines
- a `DESCRIPTION` that begins `Get up-to-date information at: https://luma.com/<id>`

The research report with citations is in the session scratchpad, `luma-research.md`.

**A hand comparison on 2026-11-07 already finds real mismatches:**

| Workshop | Site start (PT) | Luma start (PT) | Result |
|---|---|---|---|
| introduction-to-soldering | Sep 3, 6:30 PM | Sep 3, 6:00 PM | start differs |
| programming-leds | Sep 17, 7:00 PM | Sep 17, 7:00 PM | match |
| introduction-to-soldering-2 | Oct 1, 6:30 PM | Oct 1, 6:00 PM | start differs |
| programming-leds-2 | Oct 19, 6:30 PM | — | not on Luma |
| hack-night | Nov 9, 7:00 PM | Nov 9, 7:00 PM | match |
| programming-leds-3 | Nov 16, 6:30 PM | Nov 16, 6:30 PM | match |
| hack-night-2 | Nov 16, 7:00 PM | Nov 16, 7:00 PM | match |
| programming-leds-4 (draft) | Dec 14, 6:30 PM | — | expected, since it is a draft |

Notes on the feed:
- Titles differ in wording ("Intro to Soldering" against "Introduction to Soldering", "Learn to Program LEDs" against "Programming LEDs"). Exact-title matching would miss these.
- Location text varies between events.

## Scope

- **Server-side only.** The Go service fetches and parses the feed. The browser never talks to Luma, and public pages are unchanged, per AGENTS.md §9 (no third-party scripts).
- **Config:**
  - The calendar id, or feed URL, is configurable, with the value above as the default or seeded setting.
  - If it is empty, the panel says the check is not set up and nothing errors.
- **Cache:**
  - Cache the parsed feed briefly, a few minutes, so the Outreach home does not fetch on every load.
  - Fetch with a timeout. A failed fetch shows "Couldn't reach Luma" with the time of the last good read, and never blocks the rest of Outreach.
- **Matching:**
  - The planner decides the rule and records why.
  - Suggested rule: a Luma event matches a workshop when it starts on the same local date and its title is close enough, either normalised or by a token overlap.
  - Optionally, let the admin pin a workshop's Luma URL. Store it in a new migration, never by editing an applied one. A pinned URL takes precedence over the heuristic and fixes a wrong match.
- **Fields to compare:**
  - Start time and end time.
  - Title is shown, not flagged, since wording differs on purpose.
  - Location: flag it only when the street address differs, never for formatting.
- **Where it shows:**
  - The Outreach home (`#/outreach`, the timeline from `#0646` and the list under it) shows each upcoming published workshop's Luma state:
    - **On Luma**, with a link to the Luma event.
    - **Not on Luma.**
    - **Differs**, naming the field with both values, e.g. `Start: site 6:30 PM, Luma 6:00 PM`.
  - The event's own Outreach page shows the same line.
- **Leftovers:** Luma events that match no site workshop are listed once, compactly, so stray or duplicate Luma entries are visible.
- **Read-only.** Nothing is written to Luma. The admin is desktop-only (memory: no phone layout work).

### Decisions, with reasons

1. **Calendar id lives in a server setting**, `luma_calendar_id`, group `outreach`, default `cal-UIMZwzLquNDI2DB`, no env var, applies immediately. Settings already owns site-wide outreach knobs (`#0571`–`#0588`), and a saved value is editable without a deploy. A blank save falls back to the default (that is how every setting works), so **"off" is the word that turns the check off**: `Normalize` accepts `off`, a calendar id, or a pasted feed link, and `LumaCalendarID()` returns `""` for `off`. Needs migration `000050` to widen `server_setting_values_key_check`, the same shape as `000042`.
2. **No admin-pinned Luma URL. Deferred.** On the real feed the heuristic below matches all seven published workshops correctly (worked through in the fixture test), and a wrong or missed match is already visible: the workshop reads Not on Luma and the Luma event shows under "On Luma only". Pinning costs a column, an editor and a precedence rule for a failure nobody has seen. File it if a wrong match is ever reported.
3. **Matching rule** (`luma.Compare`), one-to-one:
   - A Luma event is a *candidate* for a workshop when both start on the **same calendar date in America/Los_Angeles** and their **title score is at least 0.5**. Time is not part of the match, because a start-time difference is the very thing we want to report.
   - **Title score**: lowercase, split on anything that is not a letter or digit, drop the stop words `a an the to of and for with in on at learn how`. Two tokens agree when equal, or when the shorter is at least 3 characters and is a prefix of the longer (`intro`/`introduction`, `program`/`programming`, `led`/`leds`). Score = tokens of the shorter list that agree with some token of the other, divided by the shorter list's length; 0 if either list is empty. "Intro to Soldering" against "Introduction to Soldering" scores 1; "Learn to Program LEDs" against "Programming LEDs" scores 1; "Programming LEDs" against "Hack Night" scores 0, which is what separates the two Nov 16 events.
   - **Assignment**: every candidate pair, sorted by score descending, then absolute start difference ascending, then workshop id, then Luma UID; take pairs greedily, each side used once.
   - **Fallback**: after that, on any date where exactly one workshop and exactly one Luma event are still unmatched, pair them whatever the titles say. One event each on the same day is the same event renamed, and the issue says wording differs on purpose.
   - Exact-title matching was rejected (misses 4 of 7 today); time-window matching was rejected (it would hide the start differences the panel exists to show).
4. **Fields compared** on a matched pair, at minute precision:
   - **Start**, and **End** only when both sides have one.
   - **Location** only when both sides yield a *street part*: the first comma-separated segment matching `^\d+[A-Za-z]?\s+\S`, lowercased, `.` and `#` removed, spaces collapsed, and these words shortened: street→st, avenue→ave, boulevard→blvd, road→rd, drive→dr, place→pl, lane→ln, court→ct, terrace→ter, highway→hwy, north→n, south→s, east→e, west→w, suite→ste. The site's `1736 18th Street, San Francisco, CA 94107` and Luma's `Sequoia Fabrica Community Workshop, 1736 18th St, San Francisco, CA 94107, USA` both give `1736 18th st`, so no flag. The diff shows the two full strings.
   - **Title** is never a diff. The Luma title is returned and shown as a note when it differs from the site title.
   - Time values are formatted in Pacific as `6:30 PM`; when the site and Luma values of one field fall on different Pacific dates, both are formatted `Nov 16, 6:30 PM`.
5. **States**: `on_luma` (matched, no diffs), `differs` (matched, one or more diffs), `not_on_luma`. Only **published workshops with a start time that is not past** (the `upcoming` half of `ListVisible`, status `published`, `StartsAt != nil`) get a state. **Leftovers** are unmatched Luma events with start ≥ now, in start order.
6. **Feed and cache** (`luma.Checker`): `GET https://api.luma.com/ics/get?entity=calendar&id=<id>` with a `http.Client{Timeout: 10s}`, `User-Agent: OpenCircuitSF (+https://www.opencircuitsf.com)`, body capped at 2 MiB. **A good read is cached 5 minutes; a failure 1 minute**, so a down Luma costs at most one 10 s wait a minute, not one per page load. The cache is keyed by calendar id (a changed setting refetches). One mutex guards the cache and is held across the fetch on purpose, so concurrent page loads share one request; the client timeout bounds it. Feed states: `ok`, `off` (id empty: no fetch at all), `unreachable` (transport error or non-200), `malformed` (parse error, or over the size cap). A failed read keeps `LastGoodAt` but returns **no events**: the panel never presents an old read as current.
7. **The browser never talks to Luma.** The SPA calls a new admin route, `GET /admin/outreach-luma`, and the only Luma URLs it renders are `luma.com/<id>` links the admin clicks. The home loads it **separately** from the list (not in the existing `Promise.all`), so a slow or failed Luma read never delays or breaks the rest of Outreach. Public pages are untouched.
8. **The issue's hand table is partly stale.** Production now has `programming-leds` (Sep 17) at 6:30–8:30 PM, against Luma's 7:00–8:00 PM, so that row is Differs (start and end), not a match. The fixture test below uses production's times as read today.

### API: `GET /admin/outreach-luma` (admin only, always 200 unless the workshop query fails)

```json
{
  "status": "ok",
  "read_at": "2026-11-07T23:41:00Z",
  "last_good_at": "2026-11-07T23:41:00Z",
  "events": [
    {"workshop_id": 12, "state": "differs", "luma_url": "https://luma.com/cjr6l17d",
     "luma_title": "Intro to Soldering",
     "diffs": [{"field": "start", "label": "Start", "site": "6:30 PM", "luma": "6:00 PM"}]}
  ],
  "leftovers": [{"title": "Hack Night", "starts_at": "2026-11-17T03:00:00Z", "luma_url": "https://luma.com/3y6a2mnm"}]
}
```

`status` is `ok | off | unreachable | malformed`. `read_at` is set only when `ok`; `last_good_at` is null until a good read has happened since the service started. Unless `ok`, `events` and `leftovers` are `[]`. `luma_url`, `luma_title` are null for `not_on_luma`; `diffs` is always an array. `label` is `Start`, `End` or `Location`.
