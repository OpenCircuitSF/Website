### Residuals found during review, recorded as follow-ups rather than blockers

Neither is a regression from this fix — the previous fixed-prefix check behaved
identically — and both are outside this issue's two named forms, but both are
the *same drift mode* it targeted (a line that is not a closer ends the fence,
and the rows after it are accepted):

1. **A closing fence indented 4+ spaces still closes the fence.** The close
   check runs on `trimmed`, which strips all leading whitespace, so
   ```` ␠␠␠␠``` ```` inside a fence closes it. CommonMark allows a closer at
   most 3 spaces of indentation; at 4+ it is code content. Probed:
   ```` ```\n| row |\n␠␠␠␠```\n| row | ```` yields 1 row, want 0.
2. **A closing fence with trailing text still closes the fence.** CommonMark
   allows only whitespace after a closer, but ```` ``` nope ```` has a leading
   run of 3 and satisfies `leadingRunLength(trimmed, fenceChar) >= fenceLen`.
   Probed: same shape, 1 row, want 0.

**The twelve probe-verified forms belong in the suite.** They pass today — this
review re-confirmed all twelve — but a form verified once by a probe that was
then deleted is not protected against regression, and this guard has now had
residuals found in five consecutive rounds (`#0082` → `#0083` → `#0086` →
`#0089` → the two above). They are table-driven cases in an existing `cases`
slice with an existing harness, so the addition is small and there is no cost
argument against it.

## 1. A tab-indented row is accepted

`strings.TrimLeft(line, " ")` counts spaces only. A tab is four columns of CommonMark indentation, so a tab-indented `|`-leading line inside what a renderer treats as a code block still satisfies the row check — the same drift mode `#0086` closed, reached via a different whitespace character.

## 2. A short closing fence ends a longer fence

A 4-backtick fence closed by a 3-backtick line: the inner ``` ``` ``` closes it early and following rows are accepted. CommonMark requires the closer to be at least as long as the opener. Same for a 4-tilde fence closed by `~~~`.

## Fix

Both residuals were closed as narrow additions to the existing state
machine in `docTableRowLines` (`internal/db/docs_parity_test.go`) — neither
required a new state, only a more accurate measurement within an existing
one.

**1. Tab-indented rows.** The indent check used
`len(line) - len(strings.TrimLeft(line, " "))`, which only counts leading
`' '` bytes — a line starting with a tab measured indent 0 regardless of how
much CommonMark indentation the tab actually represents. Replaced with a new
helper, `leadingIndentWidth(line string) int`, that walks the line's leading
whitespace and expands each tab to the next 4-column tab stop (`col +=
4 - (col % 4)`), matching CommonMark's tab-stop rule. Starting at column 0, a
single leading tab alone already reaches column 4 — the same threshold four
leading spaces reaches — so it's caught by the same `>= 4` comparison the
space-only check already used. Space-only lines are unaffected: each space
still adds exactly 1 column, so 4 spaces still measures 4, byte-for-byte the
same result the old check gave.

**2. Short closers on long fences.** The open/close checks used
`strings.HasPrefix(trimmed, "```")` / `"~~~"` — a fixed 3-character prefix —
so a 4-backtick (or 4-tilde) opener was closed by any inner line with 3 or
more of the same character, even though CommonMark requires the closer be at
least as long as the opener. Added `fenceLen int`, recording the opening
run's actual length (via a new `leadingRunLength(s string, ch byte) int`
helper that counts a leading run of one byte), and changed the close check
from a fixed-prefix match to `leadingRunLength(trimmed, fenceChar) >=
fenceLen`. A 3-backtick opener is still closed by a 3-backtick (or longer)
line exactly as before — `fenceLen` is 3 in that case, so the comparison is
unchanged — only a 4+-length opener now requires a matching-or-longer
closer.

Neither fix introduces a new tracked state, a lookahead, or anything
resembling a parser: both are corrections to how an existing per-line
measurement (indentation width, fence-marker length) is computed, in the
same "read this line, decide, move on" shape the rest of the function
already has.

## Gotchas

- Reverting only the fence-length fix for mutation testing left `fenceLen`
  assigned but never read, which Go's compiler treats as "declared and not
  used" (assignment alone isn't a use) — had to add a throwaway `_ =
  fenceLen` read to get a buildable mutation. Not a real code concern, just
  a note for whoever mutation-tests this again.
- No parser was needed for either residual — both were corrections to a
  per-line measurement (indent width, fence-marker run length) the function
  already computed, not new lookahead or backtracking. Consistent with the
  issue's own framing: if either fix had needed the function to remember
  more than "which state am I in and how long was its opener," that would
  have been the signal to stop and report the cure as worse than the
  residual — it never came up.
