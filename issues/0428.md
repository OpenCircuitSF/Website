## Description

`#0423` added `TestEnvExampleCoversLoaderVariables`, which parses `config.go`'s
AST for every `Getenv`/`getInt`/`getBool` call and asserts each name appears in
`.env.example`. It has an empty-extraction `t.Fatal`, so a **total** failure —
a renamed or missing `config.go` — fails closed.

**A shrinking extraction does not.**

`#0423`'s review proved it rather than arguing it. Routing the 14 direct string
reads through a one-line wrapper —

	func env(name string) string { return os.Getenv(name) }

— is a plausible refactor, an edit to `config.go` alone. It drops the extracted
set from **20 names to 6** (only the `getInt`/`getBool` ones survive), after
which `EMAIL_FROM`, `SESSION_SECRET`, `STORAGE`, `SES_EVENTS_TOPIC_ARN` and
`ADMIN_EMAIL` can all be deleted from `.env.example` and the test still exits
**0**.

So one edit **can** make both sides agree wrongly — which is exactly the
property §8 asks a guard's oracle to lack. The guard's doc comment is correct
about *additions* and silent about *representation changes*.

**Unverified by the orchestrator** — this is the reviewer's measurement.
Reproduce it before building on it.

## Root cause

`TestEnvExampleCoversLoaderVariables`'s AST walk matched a call by its
**callee's identifier** — `Getenv`, `getInt`, or `getBool` — and only then
looked at the first argument. A same-package refactor that renames the
callee (routing the 14 direct string reads through a one-line wrapper,
`func env(name string) string { return os.Getenv(name) }`) is invisible to
the loader's actual behavior but changes every one of those call sites'
identifier, so the match condition stops firing for them. Reproduced in a
throwaway worktree (`git worktree add --detach`, never the tracked tree,
per criterion 1): applying that exact wrapper and moving the 14 call sites
onto it dropped the extracted set from 20 names to 6 (only the `getInt`/
`getBool` calls, which the refactor didn't touch, survived), and deleting
`EMAIL_FROM`, `SESSION_SECRET`, `STORAGE`, `SES_EVENTS_TOPIC_ARN`, and
`ADMIN_EMAIL` from `.env.example` in that worktree still left the
unmodified guard test at `--- PASS`.

## Fix

Chose **option 3's spirit without its cost** — a structurally different
oracle, but the smallest change that closes the measured hole rather than
new mechanism (see "the judgement is the deliverable" in Acceptance
criterion 2):

Moved the match condition off the callee's identifier entirely and onto
the **shape of the first argument** — any `CallExpr`, regardless of what
function it names, whose first argument is a string literal matching
`^[A-Z][A-Z0-9_]*$` (`envVarNameLiteral`) is extracted as an environment
variable name. `env("EMAIL_FROM")`, `os.Getenv("EMAIL_FROM")`, and the
wrapper rename measured above all extract identically.

**Correction (second implementation pass, 2026-09-05):** the paragraph
below originally claimed this predicate made the fail-open
**unrepresentable**, reasoning that "the one thing that cannot be
refactored away and still compile against `loadFromFile`'s callers is the
literal name itself." **That claim is false and was measured false** by
this issue's phase-3 review: a name hoisted into a `const` block (`config.go`
already has one, for its numeric defaults) compiles and stops being a
literal call argument, dropping the extraction 20 → 15; a subset of names
assembled as `[]string{...}` elements and read in a loop drops it 20 → 18
with no missing variable at all. Both compile, both are `gofmt`/`vet`-clean.
So the predicate narrows the set of shapes that reach the fail-open — it
closes the callee-rename shape measured in this issue's `## Description` —
but it does not eliminate the fail-open, and `#0400`'s
unrepresentable-bad-state standard was claimed but not reached.

The review's remedy, applied in the same pass: raise the guard's existing
`len(names) == 0` extraction-sanity check to a real floor,
`const minLoaderVariables = 20`, which fails whenever the AST walk sees
fewer literal-shaped calls than `config.go` is known to make today. This is
a change to an assertion that already existed (CLAUDE.md §8's `#0258`
warning is about a *second* mechanism, not about strengthening one already
in place), and it discriminates: it fails under the wrapper refactor, the
`const`-hoist refactor, and the slice-literal refactor alike, and passes on
the unmutated tree, because it observes `len(names)` directly rather than
trying to enumerate syntax shapes — the property the rejected-floor
reasoning above did not credit it with. See `## Review notes` for the full
measurement and `## Verification` for this pass's four mutation runs.

The predicate change was still chosen over correcting the doc comment only
(without a floor) because the copied-to-production consequence
(`docs/deployment.md`'s `sudo cp .env.example /etc/opencircuit/config.env`)
makes the gap worth closing, not just recording — but "closing" now means
predicate **and** floor together, not the predicate alone.

**Did not** build `#0429`'s review's separate recommendation (scanning
`.env.example`'s *values* for shapes systemd and godotenv disagree on).
That closes a different hole — an unexamined value, not a shrinking key
extraction — and building both in one file is two mechanisms per
CLAUDE.md's `#0258` warning (acceptance criterion 5). It is a legitimate
gap on its own and worth its own issue if not already tracked; flagged in
the implementation report rather than filed here (subagents report, they
do not file — CLAUDE.md §9).

**Scope note on what this does not cover (corrected, second implementation
pass):** the paragraph originally here claimed a slice-literal rewrite
"would still evade this extraction." That was true of the predicate alone,
but the `minLoaderVariables` floor added in the same pass catches it too —
any rewrite that shrinks `len(names)` below 20 fails the guard, regardless
of whether `.env.example` is missing anything, because the floor observes
the count directly rather than the argument's syntax (reproduced below:
the slice-literal mutation fails with `.env.example` left fully intact).
What the combination still cannot catch is a rewrite that pads the count
back up to 20 with unrelated literal-shaped strings elsewhere in the file
while genuinely dropping a real variable's read — a materially more
elaborate, two-file forgery (`config.go` and `.env.example` would both need
matching fake entries) that neither this issue nor its review measured or
attempted. Documented in the test's own doc comment so a future reader does
not overclaim coverage.

## Why this matters more than a typical guard gap

`.env.example` is **copied onto production** by a documented install step
(`#0423`), so a variable silently missing from it is a variable production does
not get. The guard is the only thing standing between a `config.go` refactor and
that outcome.

## The remedy the review suggested, and the tension

A `len(names) >= 20` floor closes it, and `got` still moves with the scan root —
so per §8's falsifiability rule the in-package Go home stays legitimate.

**But weigh it against `#0258`**, which §8 records as six passes of adding
in-file checks to defend in-file checks. The review deliberately **recorded
rather than required** this, and that restraint is itself the precedent to
consider.

Three options, and the judgement is the deliverable:

1. **A count floor** — cheap, closes the measured hole, adds one more constant
   that can itself drift.
2. **Correct the doc comment only** — record that the guard covers additions and
   not representation changes, per `#0330`/`#0347`/`#0356`/`#0381`.
3. **A structurally different oracle** — e.g. compare against the loader's
   behaviour rather than its syntax. Likely more mechanism than this warrants;
   say so if you agree.

## A better framing, from `#0429`'s review — read this before choosing

`#0429`'s review found the **more useful** gap in this same guard, and a better
shape for closing it than the count floor below.

**The guard never reads `.env.example`'s values at all.** Its pattern
`^([A-Z][A-Z0-9_]*)=` uses only submatch 1 — the key. Proved empirically:
reverting `.env.example` to its pre-`#0429` state, with the trailing comments
that stop the service booting, leaves the whole `internal/config` package
**green**. Nothing in the repo prevents that regression today, and this is the
**only** test that reads that file at all.

**And `#` was not the only divergence.** The review compared systemd's own
`env-file.c` against `godotenv` v1.5.1 and found four shapes the two parsers
disagree about:

| Shape | systemd | godotenv |
|---|---|---|
| unquoted trailing `#` | keeps it in the value | truncates | 
| `$VAR` / `${VAR}` | **no expansion** | expands |
| `export ` prefix | builds the invalid key `export FOO`, drops the assignment | strips it |
| trailing `\` | line continuation | literal |

**`$` is the sharpest**: it fails *silently*, where `#` at least failed loudly
at boot. `export ` is silent too — the variable simply defaults.

`.env.example` currently contains none of the four (swept, seven shapes, zero
hits). So this is prevention, not a live defect.

### The review's recommendation

Assert against **the file**, since that is the copied artefact, and check for
*"any value line containing a shape systemd and godotenv disagree about"* —
which covers this defect and its three silent siblings in one check.

Explicitly **not** per-variable type-parseability, which would require the guard
to know each variable's type and would duplicate the loader.

**Weigh this against the count floor below.** They close different holes: the
floor closes a *shrinking extraction*, this closes an *unexamined value*. Doing
both is two mechanisms in one file, which `#0258` warns against — so if you take
one, say why the other is not worth it.

## Review notes — 2026-09-05 (phase 3, bounced)

**Bounced.** The predicate change is a real improvement and should stay, but
the issue's own headline condition — the guard fails open when the loader's
extraction *shrinks* — is **still open**. Two ordinary same-package refactors
shrink the extracted set and leave the guard green with five variables deleted
from `.env.example`. The `## Fix` section's central claim, and the doc comment
built on it, are falsified by measurement.

### What was independently confirmed as correct

All measurements below were made in a throwaway detached worktree pinned to
`b9e9029` (`git worktree add --detach`, removed with `git worktree remove
--force`); the tracked tree was never mutated, and `git status --porcelain`
before and after shows only the issue files other agents and I already had
dirty. No `git stash`, no `git checkout --` (CLAUDE.md §8a).

- **Scan scope is a single file** — the walk parses `config.go` alone, not the
  package and not the repo. That bounds the over-extraction risk the broadened
  predicate creates.
- **Zero over-extraction, enumerated rather than assumed.** Every `CallExpr`
  in `internal/config/config.go` whose first argument is a string literal was
  listed: the 20 environment reads, plus `Errorf("config: %s" ...)`,
  `Errorf("config: loading %s: %w" ...)`, three `Sprintf` format strings, and
  `loadFromFile(".env" ...)`. None of the five non-variable literals matches
  `^[A-Z][A-Z0-9_]*$`. The new predicate extracts **exactly the same 20 names**
  as the old one on the unmutated tree — the sets are identical, not merely
  the same size. The `required` table's `{"BASE_URL", ...}` entries are
  composite-literal elements, not call arguments, so they are not a second
  source of the same names.
- **The reported mutation proof's two load-bearing steps reproduce.** With the
  wrapper refactor applied and `EMAIL_FROM`, `SESSION_SECRET`, `STORAGE`,
  `SES_EVENTS_TOPIC_ARN`, `ADMIN_EMAIL` deleted from `.env.example`: the
  pre-fix guard (`b9e9029~1`'s copy of the file) reports `--- PASS` — the
  fail-open, reproduced — and the post-fix guard reports `--- FAIL` naming
  exactly `[ADMIN_EMAIL EMAIL_FROM SESSION_SECRET SES_EVENTS_TOPIC_ARN
  STORAGE]`. Criterion 6's plain-deletion case also still fires.
- **The `#0387` parity row still sees the reach.** The reach is expressed as
  before, an escaping `..` segment inside a string literal
  (`os.ReadFile("../../.env.example")`), which is one of the two forms
  `TestClaudeMDRepoWideGuardPackageSetParity` recognises. The commit did not
  touch that line, and the parity test passes.
- **Single mechanism preserved.** This is the same AST walk with its match
  condition changed, not a second checker bolted on. Criterion 5 is met, and
  the decision not to fold in `#0429`'s value scan was right (see below).

### Why it is bounced

**Finding 1 — the fail-open survives, in two shapes, both compiling and both
`gofmt`/`go vet` clean.**

| Mutation to `config.go` | names extracted | guard verdict with the same 5 variables deleted |
|---|---|---|
| none (control) | 20 | `--- FAIL` (correct) |
| wrapper `func env(name string) string` | 20 | `--- FAIL` (correct — this is the fix working) |
| the 5 names hoisted into a `const` block, read as `os.Getenv(envEmailFrom)` | **15** | **`--- PASS`** |
| two names assembled in a `[]string{...}` literal and read in a loop | **18** | (extraction shrinks; the deleted names are no longer demanded) |

The `const` case is the sharp one. It is not the "materially different, more
invasive rewrite" the doc comment describes: it is roughly ten lines, it is the
standard Go response to magic strings, and `config.go` **already has a `const`
block** for its defaults, so hoisting the variable names next to them is the
natural next edit to that file. It produces the identical outcome the issue was
filed over — `EMAIL_FROM` and `SESSION_SECRET` silently absent from the file
`docs/deployment.md` copies onto production.

**Finding 2 — the doc comment and `## Fix` overclaim, and the overclaim is the
load-bearing sentence.** The comment states that a renamed callee cannot evade
the match "because none of them can rename away the one thing that has to stay
a literal for `loadFromFile` to compile: the name being read." That is false as
written and was measured false: a named constant compiles, and the name stops
being a literal call argument. The scope note that follows walks part of this
back but names only the slice-literal shape and characterises it as invasive,
which is exactly the false comfort `#0423`'s review existed to prevent. This is
criterion 4's standard ("state the limitation accurately without overclaiming")
and the phase's recurring bounce reason.

**Finding 3 — `#0400`'s standard is claimed but not reached, and the rejected
option was strictly stronger on this axis.** The commit message and `## Fix`
argue the predicate makes the fail-open "unrepresentable" where a floor would
"only detect it after the fact". The predicate does not make it
unrepresentable; it narrows the set of shapes that reach it from one measured
shape to at least two others. Meanwhile the floor the argument rejects catches
**every** shrink shape, including both above, because it observes `len(names)`
rather than trying to enumerate syntax. The argument for the predicate over the
floor was made without measuring the alternative, and the measurement inverts
it.

**Where the fail-closed property comes from today, precisely:** a renamed or
unparseable `config.go` fails closed via the parse-error `t.Fatalf` (and the
package would not build); a *total* extraction failure fails closed via the
`len(names) == 0` `t.Fatal`. A **partial** shrink has no fail-closed path at
all — the only thing standing against it is the breadth of the predicate, which
findings 1 and 2 show is not enough. That is the gap to close.

### The remedy — do exactly this

1. **Keep the argument-shape predicate as committed.** It is correct, it
   over-extracts nothing, and it closes the measured wrapper case. Do not
   revert it and do not widen it further; chasing more syntactic shapes is the
   `#0258` spiral.

2. **Give the extraction-sanity assertion a real threshold.** The
   `len(names) == 0` `t.Fatal` already exists as this guard's "assert the

   from zero to the true count is a change to an existing assertion, **not a
   second mechanism** — criterion 5 and the `#0258` warning are still
   satisfied. Replace that branch with:

	const minLoaderVariables = 20

	if len(names) < minLoaderVariables {
		t.Fatalf("extracted %d environment variable name(s) from config.go, below the floor of %d — the AST walk or the envVarNameLiteral match stopped seeing reads it used to see, which is not evidence config.go reads fewer variables", len(names), minLoaderVariables)
	}

   Delete the `len(names) == 0` branch; the floor subsumes it. Document on the
   constant that it is lowered only when a variable is genuinely removed from

3. **Do not add an external shell harness for this.** CLAUDE.md §8's
