## Description

Open Circuit SF's feature set — an interest-segmented mailing list with double
opt-in, a preference centre, three unsubscribe paths, campaign sending over SES
with delivery-health handling, workshop/event listings with JSON-LD, a
passkey-authenticated admin console, and an audit log — is not specific to this
group. Another organisation running events and a mailing list needs all of it
and none of the Open Circuit SF branding.

**The goal: another project can depend on this, supply its own identity, and
switch off the integrations it does not use.**

This issue is the entry point for Phase 9. It is deliberately scoped as
*architecture and decisions* — the follow-on work should be filed as separate
issues once the shape is settled.

## The decision that shapes everything else

**"Used as a dependency" has two readings, and they lead to very different
codebases.** This must be decided before any code moves.

1. **A Go library.** Downstream imports the packages, wires its own `main`, and
   gets the pieces it wants. Maximum flexibility; the consumer owns deployment,
   migrations, and the SPA build.
2. **A configurable product.** One binary, one container, driven by a config
   file and assets. Downstream runs it rather than building against it. Far
   easier to adopt; far less flexible.

They are not mutually exclusive — (2) can be built on (1) — but attempting both
at once without deciding which is primary will produce a library with a
half-hearted binary or a binary with an accidental API.

**Recommendation: decide (1) versus (2) explicitly, in writing, before moving a
single package.**

## What already helps

- **Handlers depend on narrow store interfaces, never a concrete store**
  (`CLAUDE.md` §1). This is the seam reuse needs, and it already exists and is
  proven — `internal/devstore` substitutes for Postgres under `STORAGE=json`
  across the auth, settings, audit, and marketing surfaces.
- **`web/src/lib/branding.ts`** already centralises `APP_NAME` as the single
  source of truth for the displayed product name.
- **`web/src/lib/links.ts`** already isolates the two external integrations
  (`DISCORD_URL`, `LUMA_URL`) into one module, with a recorded note on why
  `luma.com` rather than the `lu.ma` shortener is canonical.

## The blockers, measured

**1. Every Go package is under `internal/`, so nothing can be imported.** All
fifteen — `audit auth config db devstore events handlers interests mailing
middleware seo sesnotify subscribers testdb workshops` — sit under `internal/`,
which Go's own rule makes unimportable from any other module. The only Go file
outside it is `web/embed.go`.

This is not a style problem; it is a hard compiler boundary, and it is the
single largest piece of work in Phase 9. Either packages move out of `internal/`
(deliberately, with an eye to what becomes public API and therefore
compatibility-bound), or a thin public facade is added over them.

**2. Copy is code, not configuration.** `About.svelte` and
`PrivacyPolicy.svelte` are Svelte views with prose baked in. `APP_NAME` covers
the name; it does not cover a paragraph.

**3. The two integrations are hardcoded constants, not toggles.**
`DISCORD_URL` and `LUMA_URL` are `export const`. Nothing renders conditionally
on their absence, so a deployment with no Discord shows a dead link.

## The constraint that must not be lost

**The privacy policy is legally load-bearing, and making it configurable makes
it possible for a downstream deployment to publish a policy that lies.**

`#0060` bounced on exactly this: the shipped policy promised erasure deleted
more than it did, and the fix was a fourth retained-data item that a reviewer
verified by grepping every text, jsonb, and inet column in the database.
`#0226` is open to make that correspondence a test rather than a prose comment.

If privacy copy becomes a config value, `#0226`'s guard must still hold **for
whatever copy is configured** — otherwise this issue converts a solved problem
into an unsolvable one. Concretely, a downstream operator who writes "we delete
everything" must get a failing build, not a lawsuit.

The same applies more weakly to `CLAUDE.md` §9's other restricted areas: the
uniform `202`, the `physical_address` send refusal (CAN-SPAM §7704), and
`complained` subscribers never auto-resubscribing. **None of these may become
configurable-off**, and the issue that implements configuration should say so
explicitly.

## Acceptance criteria

- [ ] The library-versus-product decision is recorded in writing, with the reasoning, before any package moves
- [ ] A named list of what becomes public API — and therefore what this project is committing to keep stable — versus what stays internal
- [ ] Branding is supplied by configuration: product name, logo assets, colour tokens, and the fonts, with a documented example of a second identity rendering correctly
- [ ] About and privacy copy are supplied by configuration rather than compiled in
- [ ] `#0226`'s privacy/erasure correspondence guard holds against **configured** copy, not just the copy that ships — a configuration that misdescribes data handling must fail
- [ ] Discord and Luma are optional: absent configuration renders no link and no empty affordance, verified by execution in both states
- [ ] The compliance invariants in `CLAUDE.md` §9 are not configurable off, and a test asserts each remains in force regardless of configuration
- [ ] A second, differently-branded instance is stood up locally from the same code, as proof rather than assertion, with screenshots
- [ ] The follow-on work is filed as discrete issues rather than absorbed into this one

## Notes

**Scope discipline matters here more than usual.** This touches every package,
and "make it reusable" is the kind of goal that expands without limit. The
deliverable of *this* issue is the decision, the public-API list, and the filed
follow-ups — not the refactor.

**On timing:** Phase 9 follows Phase 8 deliberately. Phase 8 adds the campaign
archive, bounce handling, CSV import, welcome email, and the pending-subscriber
screen — all of which change the store interfaces. Extracting a public API
before those land would mean committing to an API and then breaking it.

**On the module path:** `CLAUDE.md` §2 records the module as
`github.com/brennanMKE/OpenCircuitSF` with the GitHub repo rename `Website` →
`OpenCircuitSF` still pending (§10 item 1). A downstream consumer imports that
path, so the rename should be settled before anything depends on it.

**A naming question worth raising now, since it is cheap before extraction and
expensive after:** the domain is called "workshops" throughout — tables, routes,
the `internal/workshops` package, and the Svelte views. A reusable platform
would more naturally call them *events*. But `event` is **already taken** in this
codebase for the SSE broker (`internal/events`, `GET /api/events`), and `#0101`
uses "events" in a third sense for the Luma calendar. A rename is therefore not
a search-and-replace, and it should be a deliberate decision rather than a side
effect of extraction.
