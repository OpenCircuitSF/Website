## Description

Open Circuit SF's feature set — an interest-segmented mailing list with double
opt-in, a preference centre, three unsubscribe paths, campaign sending over SES
with delivery-health handling, workshop/event listings with JSON-LD, a
passkey-authenticated admin console, and an audit log — is not specific to this
group. Another organisation running events and a mailing list needs all of it
and none of the Open Circuit SF branding.

**The goal: another project can depend on this, supply its own identity, and
switch off the integrations it does not use.**

This issue is the entry point for Phase 9. It is deliberately scoped as
*architecture and decisions* — the follow-on work should be filed as separate
issues once the shape is settled.

## The decision that shapes everything else

**"Used as a dependency" has two readings, and they lead to very different
codebases.** This must be decided before any code moves.

1. **A Go library.** Downstream imports the packages, wires its own `main`, and
   gets the pieces it wants. Maximum flexibility; the consumer owns deployment,
   migrations, and the SPA build.
2. **A configurable product.** One binary, one container, driven by a config
   file and assets. Downstream runs it rather than building against it. Far
   easier to adopt; far less flexible.

They are not mutually exclusive — (2) can be built on (1) — but attempting both
at once without deciding which is primary will produce a library with a
half-hearted binary or a binary with an accidental API.

**Recommendation: decide (1) versus (2) explicitly, in writing, before moving a
single package.**

## What already helps

- **Handlers depend on narrow store interfaces, never a concrete store**
  (`CLAUDE.md` §1). This is the seam reuse needs, and it already exists and is
  proven — `internal/devstore` substitutes for Postgres under `STORAGE=json`
  across the auth, settings, audit, and marketing surfaces.
- **`web/src/lib/branding.ts`** already centralises `APP_NAME` as the single
  source of truth for the displayed product name.
- **`web/src/lib/links.ts`** already isolates the two external integrations
  (`DISCORD_URL`, `LUMA_URL`) into one module, with a recorded note on why
  `luma.com` rather than the `lu.ma` shortener is canonical.

## The blockers, measured

**1. Every Go package is under `internal/`, so nothing can be imported.** All
fifteen — `audit auth config db devstore events handlers interests mailing
middleware seo sesnotify subscribers testdb workshops` — sit under `internal/`,
which Go's own rule makes unimportable from any other module. The only Go file
outside it is `web/embed.go`.

This is not a style problem; it is a hard compiler boundary, and it is the
single largest piece of work in Phase 9. Either packages move out of `internal/`
(deliberately, with an eye to what becomes public API and therefore
compatibility-bound), or a thin public facade is added over them.

**2. Copy is code, not configuration.** `About.svelte` and
`PrivacyPolicy.svelte` are Svelte views with prose baked in. `APP_NAME` covers
the name; it does not cover a paragraph.

**3. The two integrations are hardcoded constants, not toggles.**
`DISCORD_URL` and `LUMA_URL` are `export const`. Nothing renders conditionally
on their absence, so a deployment with no Discord shows a dead link.

## The constraint that must not be lost

**The privacy policy is legally load-bearing, and making it configurable makes
it possible for a downstream deployment to publish a policy that lies.**

`#0060` bounced on exactly this: the shipped policy promised erasure deleted
more than it did, and the fix was a fourth retained-data item that a reviewer
verified by grepping every text, jsonb, and inet column in the database.
`#0226` is open to make that correspondence a test rather than a prose comment.

If privacy copy becomes a config value, `#0226`'s guard must still hold **for
whatever copy is configured** — otherwise this issue converts a solved problem
into an unsolvable one. Concretely, a downstream operator who writes "we delete
everything" must get a failing build, not a lawsuit.

The same applies more weakly to `CLAUDE.md` §9's other restricted areas: the
uniform `202`, the `physical_address` send refusal (CAN-SPAM §7704), and
`complained` subscribers never auto-resubscribing. **None of these may become
configurable-off**, and the issue that implements configuration should say so
explicitly.

**Does not change:** every measurement in the plan — the guard estate's size,

### 1. The unit of reuse — decide the configurable product, defer the Go library

**Decision to record: (2) a configurable product is primary. (1) a Go library is
deferred, not rejected, and gated on the three conditions in §7 below.**

The reasoning, in the order it actually decides the question:

- **The two readings are not a fork; they are strictly ordered.** A library
  whose Svelte views, SEO copy table, and email templates say "Open Circuit SF"
  is not importable in any useful sense. Externalising identity is required for
  *both* readings. Doing (2) first is therefore not a bet against (1) — it is
  the first half of (1), and it is the half that pays off on its own.
- **(2) moves no packages, so it costs nothing from the guard estate.** §6 below
  measures the estate at ~129 guard functions across 19,368 lines, of which
  roughly 12,000 lines in `internal/handlers` and `internal/db` are wholly
  coupled to this repository's root layout. Reading (2) leaves every one of them
  in place and meaningful. Reading (1) puts 25 files' worth of hard-coded scan
  roots and path-literal expectation tables in the blast radius.
- **There is no second consumer, so a public API would be designed against a
  guess.** The interfaces are narrow *per handler*, which is exactly what makes
  substitution work and exactly what does not add up to a coherent façade. The
  façade would have to be invented, and inventing it without a caller is how you
  get an API you break on first contact.
- **The mechanism (2) needs already exists and is proven.** See §3.

**What "public API" means under this decision** — the named list acceptance
criterion 2 asks for, answered as: **nothing becomes public API yet.** The
commitment recorded instead is the *configuration surface* — the site config
file's schema, the settings keys, and the asset layout — versioned and
documented as the stable interface. That is the thing a downstream depends on
under reading (2), and it is a far smaller and more honest promise than 17
packages of Go.

**The interest-taxonomy trap, which no one has noticed yet.** The 12 rows are
DML inside migration `000009`, which is **inside the frozen range** (production
is at 22; `CLAUDE.md` §1 freezes `000001`–`000022`). So the taxonomy cannot be
changed by editing the file that owns it — not by this project and not by a
downstream. A second tenant's only options today are to run the migration and
then delete twelve rows they never wanted, or to ship a migration that deletes
another organisation's taxonomy. Both are wrong. This is a real, isolated defect
that is worth fixing whether or not the rest of Phase 9 ever happens.

### 3. Optional integrations — three different meanings, and they must not be conflated

The word "optional" is doing three jobs in this issue, at wildly different
prices:

- **(a) Optional by substitution at a store seam.** The `internal/devstore`
  precedent, measured: 19 methods, 485 lines, covering auth, settings, audit and
  users only — against `internal/handlers`' 13,675 lines. It is *deliberately*
  incomplete, and `CLAUDE.md` §5 documents that `STORAGE=json` has no mailing
  list at all. **This is the expensive kind**, and the existing instance is
  evidence of the cost rather than a template to copy.
- **(b) Optional by absent configuration, with the feature degrading cleanly.**
  Absent Discord URL renders no link and no empty affordance. Two call sites
  each. **This is the cheap kind, and it is what the issue actually asks for.**
- **(c) Optional by disabling a worker.** `SEND_WORKER_ENABLED=false` already
  exists.

**SES is not optional today, and that is a measured blocker for reading (2), not
an opinion.** Two independent gates: `mailing.NewSESMailer` refuses to construct
without `SES_CONFIGURATION_SET`, so the service does not boot; and
`checkMailerNoOp` in `cmd/opencircuit/main.go` refuses to start when
`MAILER_NOOP` is set unless `BASE_URL`'s host is localhost. A second tenant on a
real domain with no SES account therefore has **no supported way to run the
binary at all**. That guard is correct and `CLAUDE.md` §10 says it must not be
weakened — so the fix is not to relax it but to add an explicit, honest third
state: a configuration that declares "this deployment does not send email",
which disables the mailing subsystem's routes the way `STORAGE=json` already
does, rather than pretending to send.

**The compile-time embedding problem, and why it is already solved.**
`web/embed.go` embeds the built SPA with `//go:embed all:dist`, so on the face
of it a one-binary product cannot be rebranded without a rebuild — which would
collapse reading (2) back into "fork the repo". It can, because
`internal/seo/site.go` **already rewrites the embedded `index.html` per request**
to inject meta tags, and `NewSite` takes the template bytes as a parameter. That
same seam can inject a `:root` custom-property block and a small brand JSON
blob, letting one binary serve a different palette, name, and copy per
deployment with no rebuild. **This is the single most important finding in this
plan**: the mechanism reading (2) needs is not speculative, it is running in
production today for a different payload.

The residue that genuinely cannot be done this way is the OG card
(`internal/seo/cardassets`, compile-time embedded PNG and TTFs) and the
favicon/manifest assets. Those need a filesystem-backed override path, which is
the same shape as `MEDIA_DIR` already has.

### 4. Where configuration lives — not in `.env`

The codebase already has **three** configuration layers, and the right answer is
to extend the second and third rather than the first:

| Layer | Size today | Character |
|---|---|---|
| `.env` → `internal/config` | 21 variables, **zero branding defaults** | Deploy-time, immutable, infrastructure only |
| `settings` table | 9 keys, admin-editable at runtime, **already includes `default_from_name` (identity) and `physical_address` (compliance)** | Runtime, operator-owned |
| `interests` table | 12 rows, admin-editable | Runtime, operator-owned |

**Branding and copy must not go in `.env`.** Three reasons, each sufficient:

- `.env.example` is the production template copied verbatim onto the box, and
  `TestEnvExampleCoversLoaderVariables` re-derives the loader's variable set from
  `internal/config/config.go`'s own AST and asserts each appears there. Every new
  branding variable would have to ship **Open Circuit SF's real identity as the
  template's real value** — precisely backwards for a reusable product.
- 183 lines of privacy prose do not fit in an environment variable.
- The config layer is currently the *cleanest* tenant-neutral thing in the
  repository. Polluting it with identity would undo that.

**Recommended shape:** one new environment variable pointing at a site
configuration file (name it in the implementing issue; `SITE_CONFIG` is the
obvious candidate) plus an optional assets directory alongside `MEDIA_DIR`. That
is **one** addition to the `.env.example` guard family instead of thirty, and it
keeps `#0423`'s work intact. Identity that an operator should be able to change
without a redeploy — organisation name, contact address, postal address, social
links — belongs in `settings`, extending the layer that already holds
`default_from_name`.

One cost to budget: `auth.Store.UpdateSetting` updates only keys that already
exist, so each new setting needs a migration to seed it plus a validation case
in the settings handler's `switch`. That is deliberate and worth keeping; it
just means "add a setting" is not free.

### 5. What must never be configurable — the constraints that travel with the code

These are not deployment policy. They are properties of the software, and a
downstream must not be able to switch them off:

| Invariant | Why | Enforced where |
|---|---|---|
| Uniform `202` from `POST /api/subscribe` | Varying it makes an email-enumeration oracle | `internal/handlers`, asserted byte-identical |
| Send refuses without `physical_address` | CAN-SPAM §7704 | `internal/subscribers` builds no message and defers |
| `complained` never auto-resubscribes | Admin action only | `internal/subscribers` |
| No third-party analytics, ad trackers, external CDNs, open-tracking pixels | PRD §2 non-goals; the site is self-contained by design | Absence, plus CSP |
| Apex MX untouched | Hijacks real human mail | Operational, `CLAUDE.md` §7 |

**The model for all of these already exists and should be stated explicitly in
the implementing issue: `physical_address` is a configurable *value* with a
non-configurable *refusal*.** The operator supplies the address; the code
refuses to send without one. Every §9 invariant should take that shape —
configure the content, never the check.

**Acceptance criterion 5 cannot be met as written, and this is the sharpest
finding in the plan.** `#0226`'s guard —
`web/src/views/PrivacyPolicy.guard.test.ts` — walks the *committed*
`web/src/views/PrivacyPolicy.svelte` with `svelte/compiler`'s parser, pulls the
`StatusList` items off the AST, and matches them against a committed fixture of
the four categories erasure actually retains. It is a **build-time test over
compiled-in copy**. The moment privacy copy becomes runtime configuration, there
is no build in which a downstream's copy exists, and no test run that could see
it. A build-time guard cannot validate a value supplied after the build.

Two viable resolutions, and the implementing issue must choose one in writing:

- **(i) Move the check to startup.** The service validates configured privacy
  copy against the retained-category list at boot and **refuses to start** if a
  required category is unnamed. Same fail-closed shape as `checkMailerNoOp`, and
  it satisfies the issue's own standard — "a downstream operator who writes 'we
  delete everything' must get a failing build" becomes a failing *boot*, which
  is as good and arguably better.
- **(ii) Do not make privacy copy configurable.** Ship it as code with
  placeholders for organisation name, contact address and jurisdiction only.
  Cheaper, keeps `#0226` untouched, and is defensible: the policy describes what
  *the software* does with data, which does not vary by tenant.

**Recommendation: (ii) for the privacy policy, (i) as the general pattern for
any other legally load-bearing copy.** The privacy policy is the one document
whose content is genuinely determined by the code rather than by the
organisation, so making it configurable buys little and risks exactly the
failure `#0060` already produced once.

### 6. The guard estate — the question that decides the cost

Measured across the tree: **1,383 Go test functions in 172 files, 78,512 lines.
28 dedicated guard files hold ~129 of those functions across 19,368 lines — 25%
of all Go test code.** Plus 7 shell harnesses (4,634 lines) and 8 web-side
structural guards.

Under **reading (2) the impact is close to zero.** Nothing moves, the repo root
keeps `CLAUDE.md`, `PRD.md` and `issues/`, and the ~15 tests that assert brand
literals keep asserting this deployment's literals because this deployment is
still the one being tested. The only real work is that a handful of those
brand-literal assertions should be re-pointed at the configured value rather
than a hard-coded string, so they prove the plumbing instead of the constant.

Under **reading (1) the impact is severe, and quantified:**

- **25 files** carry hard-coded `internal/` scan roots, `../..` depth climbs, or
  literal `internal/...` expectation tables that break on a package move — some
  loudly, some by silently scanning nothing.
- **~35 test functions across 13 files hard-fail** (they `t.Fatal` on a read
  error rather than skipping) if `CLAUDE.md`, `PRD.md`, `issues/`, `docs/`, or
  `migrations/` are absent — which they would be for any downstream consumer.
- **~12,000 lines** of the citation and tracker-parity families in
  `internal/handlers` and `internal/db` are 100% coupled to this repository's
  root layout and its `#NNNN` comment convention.
- `scripts/go_file_visit_floor_guard_test.sh` pins file-count floors derived
  from *this* tree; a smaller downstream repository fails them outright.
- `TestClaudeMDRepoWideGuardPackageSetParity` reads `CLAUDE.md` §5's table by
  package name and would need that table rewritten wholesale.

**The conclusion that matters: this estate is repo-hygiene infrastructure, not
library tests, and it must not travel with an extracted package.** That is a
clean answer rather than a cost, but it means an extraction has to consciously
partition ~129 guard functions into "stays with the repo" and "ships with the
code" — and only a small set is genuinely portable (the two `internal/mailing`
outbox guards, `internal/seo`'s invalidator-satisfier guard, and
`cmd/opencircuit`'s two AST wiring guards, the last after module-path
parameterisation). Budget the partition as its own piece of work, not as a step
inside a refactor.

One incidental finding worth recording: `CLAUDE.md` §5's repo-wide guard table
was verified against a live scan and **the package column is exactly right** —
9 rows, 8 real reachers plus `internal/media` documented as a known false
positive, and no unlisted package reaches out. The `Reaches into` prose for
`internal/seo` is narrower than reality (it credits only the `dist` placeholder
guard, while `seo_test.go` also reads `web/index.html`), which is the documented
hand-maintained staleness §5 warns about, not a guard failure. No action
required; noted so the next reader does not re-derive it.

### 7. Is it worth doing now?

**Not as filed. Yes for three narrow slices, and no for the extraction.**

Against doing the whole thing now:

- **There is no second consumer.** Every API and schema decision would be a
  guess, and the issue's own scope-discipline note predicts what happens next.
- **The module path does not resolve** (§0.4). Reading (1) is blocked on a
  rename that is `CLAUDE.md` §10 item 1 and still not done.
- **The guard partition is a large, separate project** (§6) that only reading
  (1) forces.

For doing part of it now:

- **The Discord/Luma dead-link risk is live today**, for this deployment, with
  no downstream involved. Either URL rotting renders a dead link right now.
- **The interest-taxonomy freeze is a real defect** (§2) that will only get more
  awkward as more migrations stack on top.
- **The email palette drift is unguarded** (§2) — two independent colour sets
  sharing one hex by hand.
- **The decision itself is cheap and unblocks thinking**, which is what
  acceptance criteria 1 and 2 actually ask for.

**What would have to be true before the extraction is worth starting:** a real
second consumer with named requirements; the GitHub rename settled so the module
path resolves; and the guard partition designed. Until all three hold, reading
(1) should stay deferred.

## Notes

**Scope discipline matters here more than usual.** This touches every package,
and "make it reusable" is the kind of goal that expands without limit. The
deliverable of *this* issue is the decision, the public-API list, and the filed
follow-ups — not the refactor.

**On timing:** Phase 9 follows Phase 8 deliberately. Phase 8 adds the campaign
archive, bounce handling, CSV import, welcome email, and the pending-subscriber
screen — all of which change the store interfaces. Extracting a public API
before those land would mean committing to an API and then breaking it.

**On the module path:** `CLAUDE.md` §2 records the module as
`github.com/brennanMKE/OpenCircuitSF` with the GitHub repo rename `Website` →
`OpenCircuitSF` still pending (§10 item 1). A downstream consumer imports that
path, so the rename should be settled before anything depends on it.

**A naming question worth raising now, since it is cheap before extraction and
expensive after:** the domain is called "workshops" throughout — tables, routes,
the `internal/workshops` package, and the Svelte views. A reusable platform
would more naturally call them *events*. But `event` is **already taken** in this
codebase for the SSE broker (`internal/events`, `GET /api/events`), and `#0101`
uses "events" in a third sense for the Luma calendar. A rename is therefore not
a search-and-replace, and it should be a deliberate decision rather than a side
effect of extraction.
