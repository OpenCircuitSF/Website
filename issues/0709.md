## Description

User request, 2026-11-17: "I am finding the unfurl looks the same so the feed looks a bit uninteresting. I'd like to prepare unique images for each guide which is used when URLs are unfurled. We can have Codex generate these images, so we will just need a prompt for each image."

Today every page, every guide included, sets `og:image` to `/og-default.png` (1200×630; `internal/seo/seo.go`, `image := baseURL + "/og-default.png"`). Bluesky, Mastodon and link previews therefore show the same card for all 43 topic guides and the workshop guide.

Two parts:
1. **Prompts** for an image generator (Codex), one per guide, written to a file in the repo, so the user can generate the images. Each names the target file path and size.
2. **Wiring:** a guide page uses its own image when one exists, and falls back to `/og-default.png` when it doesn't, so images can land one at a time.

## Plan

Written 2026-11-17, phase 1 (Opus · medium). Part 1, the prompts, is already done in this commit: `assets/og/guides/PROMPTS.md` holds a shared STYLE block and one prompt per guide. **The catalog has 43 guides, not 44**: 42 topics plus the `programming-leds` workshop guide (`web/src/content/guides/guides.json`). The description above miscounted.

**The description's premise is stale, and that makes this smaller.** Guides do not use `/og-default.png`. Since `#0656`, each guide's `og:image` is `{base}/guides/{slug}/og.png` (`defaultStaticRouteMeta`'s guide loop, `internal/seo/seo.go`), served by `Site.GuideCardHandler` (`internal/seo/site.go`). That handler renders the shared base card with the guide's title on it. Those title cards look nearly alike in a feed, which is the user's complaint. `Site.GuideCard`, which serves the same bytes, is also the Bluesky post thumbnail (`#0658`). So the wiring is: **when a guide has hand-made art, that same URL serves the art instead of the generated card.** Every consumer picks it up without changing: the page meta, social crawlers and the Bluesky thumbnail. **The fallback is the guide's existing generated title card, not `/og-default.png`.** That is a deliberate change from the description's wording, because the title card is the better fallback. Images can land one at a time.

**Where images live: `internal/seo/cardassets/guides/<slug>.png`**, embedded into `internal/seo` itself. Three reasons not to use `web/public/`:
- `go:embed` can't reach outside its package (see `card.go`'s doc comment), and `cardassets/` is where the card's base image already lives.
- The tests can see the files without an `npm run build`. A `web/dist` check would be empty in every Go test run.
- Nothing in the SPA needs them.

The prompts file names this path in every prompt.

### Approach

1. **`guideart.go`.**
   - `//go:embed all:cardassets/guides` into `var guideArtFS embed.FS`. The `all:` prefix plus the committed `.gitkeep` is what lets the package compile with **zero images present**. Without `all:`, a directory holding only a dotfile is a "no embeddable files" compile error.
   - `type guideArt struct { data []byte; etag string; version string }`. `version` is the first 8 hex digits of the SHA-256 of `data`. `etag` is `"\"" + version + "\""`, the same quoted form `cardCache` uses; check `card.go` and match its etag shape.
   - `func loadGuideArt(fsys fs.FS, dir string) (map[string]guideArt, error)` walks `dir`:
     - Skip names starting with `.`.
     - Every other entry must be `<slug>.png`, and `guides.Lookup(slug)` must succeed.
     - The data must decode with `image.DecodeConfig` as format `png`, at exactly `cardW`×`cardH` (1200×630, the constants in `card.go`).
     - `len(data) <= guideArtMaxBytes`, where `const guideArtMaxBytes = 1_000_000`. **Don't import `internal/bluesky` in non-test code.** A test pins the constant to `bluesky.MaxThumbBytes` instead.
     - Any violation returns an error naming the file and the rule it broke.
   - `var defaultGuideArt = mustLoadGuideArt()` panics on error, like `guides.mustLoad`. Bad embedded content is a build-time defect, and the tests below catch it before any binary ships.
2. **`site.go`.**
   - Add an unexported field `guideArt map[string]guideArt` to `Site`. `NewSite` sets it to `defaultGuideArt`.
   - Split `serveCard`'s header and body tail into `writePNG(w, r, body []byte, etag string)`: Content-Type, Cache-Control, ETag, and the 304 on a matching If-None-Match.
   - `GuideCardHandler`: after the `guides.Lookup`, if `a, ok := s.guideArt[g.Slug]`, call `writePNG(w, r, a.data, a.etag)`. Otherwise call the existing `serveCard`.
   - `GuideCard(slug)`: return `a.data, "image/png", nil` when art exists. Otherwise keep the current path.
   - Update both doc comments to say "hand-made art when present (`#0709`), else the generated card".
3. **`seo.go`.**
   - `defaultStaticRouteMeta(baseURL string)` becomes `defaultStaticRouteMeta(baseURL string, art map[string]guideArt)`.
   - `NewRenderer` passes `defaultGuideArt`.
   - Add an unexported `newRendererWithGuideArt` (or `NewSite`/`NewRenderer` delegating to `newSite(..., art)`/`newRenderer(..., art)`) so tests can inject a fixture map. Keep the exported signatures unchanged, so `cmd/opencircuit` is untouched.
   - In the guide loop, `OGImage: guideOGImage(baseURL, g.Slug, art)`. That helper returns `baseURL + "/guides/" + slug + "/og.png"`, plus `"?v=" + a.version` when art exists.
   - **The `?v=` is the cache-buster.** Mastodon, Slack and Bluesky cache a preview by image URL, so a guide shared before its art landed would keep showing the old card. The version also changes whenever an image is replaced. The `{slug}` route ignores the query string, so no route changes.
   - **`twitter:image`: do not add one.** `web/index.html` deliberately has none, and Twitter/X falls back to `og:image` (`#0273`'s settled design; see the comment at `seo.go` around `tokenOGImage`). Changing `og:image` covers it.
   - **JSON-LD:** guide routes have no JSON-LD (`jsonld.go` has no guide graph), so there is nothing to change. Say so in `## Fix`.
4. **`docs/seo.md`.** Add a short section, "Guide unfurl images (`#0709`)", after "Per-workshop Open Graph card". It covers:
   - The path, and the 1200×630 PNG under 1,000,000 bytes requirement.
   - The fallback, and that the `?v=` URL changes when an image does.
   - That `assets/og/guides/PROMPTS.md` holds the prompts, plus the crop and compress recipe.
   - The guard that requires a prompt for each guide.
   - That a new guide needs a `### <slug>` section there.
5. **`AGENTS.md` §5 table.** In the `internal/seo` row's "Reaches into" cell, append: "and, since `#0709`, `assets/og/guides/PROMPTS.md` (`TestGuidePromptsCoverCatalog`)". The package column is unchanged; the row already exists.

### Tests

- **`TestLoadGuideArt_Rules`**, table-driven over `fstest.MapFS`. Build PNG fixtures in the test with `image.NewRGBA` and `png.Encode`. Cases:
  - Valid 1200×630 for a real catalog slug: loaded, `version` 8 hex digits.
  - `.gitkeep`: ignored.
  - Unknown slug: error.
  - `.jpg` name: error.
  - 1200×600: error.
  - Not a PNG: error.
  - Over `guideArtMaxBytes`: error. Build it from noise pixels, or test the size check with a byte slice padded past the limit.
  - Empty dir: empty map, no error.
- **`TestGuideArt_EmbeddedSetIsValid`**: `loadGuideArt(guideArtFS, "cardassets/guides")` returns no error. It is trivially green with zero images and does real work once they land.
- **`TestGuideArtMaxBytesMatchesBluesky`**: `guideArtMaxBytes == bluesky.MaxThumbBytes`.
- **`TestGuideArt_ServedAndInMeta`**: build a Site and a Renderer with a fixture map holding art for one catalog guide, A, and none for another, B. Assert:

  - B's is `.../guides/B/og.png` with no query.
  - `GET /guides/A/og.png` returns exactly the fixture bytes and its ETag, and a matching If-None-Match gets a 304.
  - `GET /guides/B/og.png` returns a PNG that differs from A's fixture: the generated card.
  - `site.GuideCard("A")` returns the fixture bytes.

## Obstacles

- **Images arrive later, from the user.** The code must ship and pass with **zero images** in `internal/seo/cardassets/guides/`. That is why it's `all:` plus `.gitkeep`, and why `TestGuideArt_ServedAndInMeta` uses an injected fixture map instead of real files. The implementer must not generate or commit any image.
- **Size budget.** A detailed 1200×630 PNG straight from a generator often exceeds 1,000,000 bytes, which is Bluesky's thumbnail limit and the loader's cap. Without a cap, a too-large image would fail to load at startup, or break `#0658`'s thumbnail. `pngquant` is **not installed** on this machine (`command -v pngquant` is empty; `sips` is present). The user needs `brew install pngquant` before compressing images. That is the user's step, not the implementer's. PROMPTS.md gives the recipe.
- **Binary size.** 43 images at up to 1 MB each could add up to about 43 MB to the embedded binary. That is fine for scp deploys and the t4g.small. Note it in `## Fix`, but it doesn't block anything.
- **The scope widens in AGENTS.md.** The `internal/seo` row's prose is edited by hand, since the parity guard sees only the package column. Editing AGENTS.md means running both `internal/db` and `internal/handlers` (included in the command above).
- **Concurrent agents.** `#0572` is editing `web/src/`, and a reviewer is on `#0707`. This issue touches only `internal/seo/`, `docs/seo.md` and `AGENTS.md`, so the files don't overlap. Still check `git status --porcelain -- AGENTS.md docs/seo.md` before editing, and stage only your own paths (§8a).
