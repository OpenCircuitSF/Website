## Description

`gofmt -l` currently flags four files, none of them touched by the change that noticed:

```
cmd/opencircuit/seo_wiring_test.go
internal/db/prd_index_parity_test.go
internal/handlers/static_test.go
internal/sesnotify/verify_test.go
```

They have presumably been unformatted for some time. **`scripts/check.sh` runs `go build` and `go vet` but never `gofmt`**, so nothing in the canonical verification path reports it, and `go vet` does not care about formatting.

This surfaced during `#0156`'s review, which ran `gofmt -l` of its own accord and then had to establish that the flagged files were pre-existing rather than its own doing — a small diagnostic tax it paid on behalf of a defect that belongs to nobody.

**Concurrency collision, caught and corrected.** `cmd/opencircuit/seo_wiring_test.go`
was mid-edit by another agent (#0165, adding a `registerWiringTest(t, pool)`
call) at the moment `gofmt -w` ran on it — a `git status --porcelain` check
was run first but its result wasn't actually branched on, so the file was
formatted while dirty. Caught immediately via `git diff`, which showed the
alignment hunk mixed in with the other agent's line. Reversed just the gofmt
hunk by hand (kept `registerWiringTest(t, pool)`, restored the original
`nil, /* ... */` spacing) so the file matched exactly what #0165 had in
flight, and skipped it for that pass. #0165 committed shortly after; once the
file was clean in git again, `gofmt -w` was re-applied to it with no
conflict. Net effect: all six files are gofmt-clean, none of #0165's work was
touched.

**A gofmt quirk worth flagging, not filing further:** `internal/db/prd_index_parity_test.go`'s
diff isn't pure whitespace. Two doc comments (on `type sqlSpanKind` and
`func tokenizeSQL`) illustrate Postgres's doubled-single-quote string escape
with the literal text `'it''s'`. Since Go 1.19, `gofmt` applies "smart quote"
normalization to declaration doc comments, and it collapsed `''` into a
single Unicode right double quotation mark (`”`), producing `'it”s'`. This is
gofmt's own documented behavior (confirmed by reproducing it in isolation on
a throwaway file), not a bug in this change, and it doesn't affect build or
test behavior since it's comment-only — but it does make that specific
example less accurate as a description of SQL syntax (a doubled `''` no
longer visibly reads as "two single quotes"). Applied as-is per this issue's
"apply gofmt -w to exactly those files, nothing else" scope; worth a follow-up
issue to reword those two comments (e.g. spell out "doubled `'`" instead of
embedding literal `''`) so gofmt's doc-comment pass can't mangle them again.
Reported to the orchestrator, not filed.

Verified semantic inertness before wiring the check in: full `go test ./...`
before formatting was 891 PASS / 0 FAIL / 0 SKIP across 16 packages; after
formatting the five files that were clean to touch in that pass, identical —
891 PASS / 0 FAIL / 0 SKIP, same 16 `ok` packages, same set of test names
(only timing digits differed, as expected from run to run).

**The check.** Added a `gofmt_check()` function to `scripts/check.sh`,
alongside the existing `go_test()`/`web_check()` functions, called right
after `go vet` in the `go`, `all`, and default branches (not `web`, which
doesn't touch Go). This is purely additive — no restructuring of the existing
`run bash -o pipefail -c "..."` call sites, so it doesn't collide with
`#0208` (filed against restructuring `check.sh`) or `#0140`'s pipefail guard.

- Scope: whole repo (`gofmt -l .` from `$REPO`), not a curated list of
  package roots. Decided because `gofmt` only ever inspects `*.go` files, so
  scanning the whole tree can't false-positive on `web/`, `migrations/`, etc.,
  and it needs no maintenance as Go packages are added or moved — cheaper to
  reason about than keeping a root list in sync with the module layout.
- Fails, not warns: `gofmt -l`'s own exit code is 0 even when it lists files
  (the exact #0140 shape — real signal sitting in output nobody checks), so
  `gofmt_check` treats non-empty output itself as the failure condition and
  sets `FAILED=1`.
- Failure message names the files and gives the pasteable fix
  (`gofmt -w <files>`), per #0187.

**Mutation proof.** Introduced a pure-whitespace change (trailing spaces
after a `func` line, compiles fine — no unused-variable side effects) into
`internal/middleware/ratelimit_test.go` — a file with `git status --porcelain`
empty and `gofmt -l` clean beforehand, i.e. no one's in-flight work. Ran
`scripts/check.sh go ./internal/middleware/...`: it printed `FAILED: gofmt -l
found unformatted file(s)`, named `internal/middleware/ratelimit_test.go`,
and gave `Fix: gofmt -w internal/middleware/ratelimit_test.go`. Restored the
file from a pre-mutation copy and confirmed byte-identity with
`shasum -a 256` (same digest before and after). Re-ran `gofmt -l` on it —
clean.

### Non-empty output, not exit status, is what fails the run

Verified by execution, not by reading. On the mutated file:

```
gofmt -l stdout: [internal/config/config_test.go]
gofmt -l EXIT CODE: 0     <-- 0 despite non-empty output
```

This is precisely `#0140`'s shape — real signal sitting in output nobody checks.
`gofmt_check` does not consult that exit code at all: it captures
`out="$(gofmt -l . 2>&1)"` and branches on `[ -n "$out" ]`, setting `FAILED=1`
directly. The plumbing downstream also holds: `FAILED=1` reached the
`VERIFICATION FAILED` banner at the end of the script **and** a non-zero shell
exit (`exit 1`), both captured in the single run above. Because `gofmt_check`
sets `FAILED` itself rather than going through `run`, it is structurally immune
to the pipefail defect `#0140` fixed.

### Verdict on the smart-quote finding: real, but a follow-up, not a bounce

Read at `bac9781`. `gofmt`'s Go 1.19+ doc-comment pass collapsed `''` into `”`
in exactly two places, both in `internal/db/prd_index_parity_test.go`, both
comment-only (a repo-wide scan of the commit for introduced `”`/`“` found no
others):

```go
// literal (Postgres escapes an embedded quote by doubling it: 'it”s'), or
// unescaped `"`, `""` doubles like a string's `”` does) would close this for
```

This is **more than cosmetic as documentation**, and the implementer's own
assessment was right. Both comments exist specifically to explain how the SQL
tokenizer recognizes quote escaping, and neither example demonstrates its rule
any more:

- `'it”s'` no longer shows a doubled `'`. `”` is one ordinary character that
  Postgres would treat as literal text, so a reader who copies the example
  writes something that does not do what the sentence says.
- `` `""` doubles like a string's `”` does `` is the worse of the two — the
  sentence's whole point is the parallel between `""` and `''`, and half of it
  is now gone.

It is nonetheless **not grounds to bounce**: zero behavioural impact
(comment-only), the tokenizer code and its tests are untouched, the package
passes, and the output is what the tree's own formatter produces — which the
files are now required to match. Applying it as-is was the correct call under
this issue's "gofmt -w and nothing else" scope. Recommended follow-up (reported
to the orchestrator, not filed, per `CLAUDE.md` §9): reword the two comments so
the doc-comment pass cannot mangle them — either spell it out ("two consecutive
`'` characters") or move the example into an indented code block, which the pass
leaves alone — and confirm the rewrite is gofmt-stable. Note this is a hazard
for *new* declaration doc comments generally, now that `check.sh` enforces
`gofmt`; existing ones are already normalized, since `gofmt -l .` is empty.

**Verdict: pass.** The formatting is provably a pure `gofmt` run with an
identical test surface, and the check is real — it fails on drift, it fails on
*output* rather than on an exit code that lies, it reaches a non-zero exit, and
it runs in every Go-touching mode and none of the others.
