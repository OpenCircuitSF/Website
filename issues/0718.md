# 0718 — A second stale tab skips its version check for up to an hour after the first one reloads

| | |
|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-11-18 |

## Description

Found by `#0715`'s review. The one-hour throttle timestamp in `web/src/lib/versionCheck.ts` lives in `localStorage`, shared by every tab on the origin. With two day-old tabs open, the first tab the visitor returns to checks, finds a new build, and reloads — and writes the timestamp. The second tab, visited minutes later, sees a fresh timestamp and skips its check, so it stays on the old build for up to an hour. That falls short of the user's intent for `#0715`: coming back to a tab should update it.

## Acceptance criteria

- [ ] Alongside the throttle timestamp, store the newest server build last seen. On becoming visible, a tab whose own build (`<meta name="oc-build">`) differs from that stored build takes the same reload-or-notice path immediately, without a fetch and regardless of the throttle.
- [ ] A tab already on the stored build still obeys the hour throttle — no extra requests.
- [ ] Storage failure keeps `#0715`'s in-memory fallback behaviour.
- [ ] Unit tests with injected fakes cover the two-tab sequence, and a mutation that drops the stored-build comparison fails a test.
