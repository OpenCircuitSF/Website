## Description

Found by `#0715`'s review. The one-hour throttle timestamp in `web/src/lib/versionCheck.ts` lives in `localStorage`, shared by every tab on the origin. With two day-old tabs open, the first tab the visitor returns to checks, finds a new build, and reloads — and writes the timestamp. The second tab, visited minutes later, sees a fresh timestamp and skips its check, so it stays on the old build for up to an hour. That falls short of the user's intent for `#0715`: coming back to a tab should update it.

## Acceptance criteria

- [x] Alongside the throttle timestamp, store the newest server build last seen. On becoming visible, a tab whose own build (`<meta name="oc-build">`) differs from that stored build takes the same reload-or-notice path immediately, without a fetch and regardless of the throttle.
- [x] A tab already on the stored build still obeys the hour throttle — no extra requests.
- [x] Storage failure keeps `#0715`'s in-memory fallback behaviour.
- [x] Unit tests with injected fakes cover the two-tab sequence, and a mutation that drops the stored-build comparison fails a test.

### Approach in one paragraph

Store the newest build a server response has reported, together with the time it was seen, in a second `localStorage` key. On a visibility event, before the throttle check, a tab compares that record with its own `<meta name="oc-build">`. It goes straight to the reload-or-notice path, with no fetch and no throttle write, only when all three of these hold: the builds differ, the record was seen **after this tab loaded**, and the record is not in the future. Otherwise the existing `#0715` path runs unchanged. On every successful fetch (`same` or a mismatch) that path now also writes the record. The record is written **only from a server response**, never from a tab's own running build.

**Why "seen after this tab loaded", and why this means there is no ping-pong.** Build ids are not orderable (`0.16.2+abc`), so on its own "my build ≠ stored build" cannot tell an old tab from a new one. Three cases:

- **Old tab, newer record.** The record is newer than the tab when it was seen after the tab loaded. The server served something other than this tab's build after this tab started, so the tab is stale: reload.
- **New tab, older record.** A tab loaded after the deploy can find an older record from a check made before the deploy. That record's `at` is before the tab's `loadedAt`, so it is ignored and the tab follows the hour throttle. Without this rule that tab would reload on every focus, forever.
- **Reload lands on a stale shell.** A tab that reloads but gets a stale cached shell still has the old build. Its new `loadedAt` is now after the record's `at`, so it does not reload again. That is the same no-loop property `#0715`'s review pinned.

Because tabs never write their own build, a tab on build O and a tab on build N cannot keep overwriting each other's view of "newest". Only the server's answer moves the record.

### `versionCheck.ts`, exactly

1. Add a constant `export const SEEN_BUILD_KEY = 'oc.versionCheck.seenBuild';` next to `LAST_CHECK_KEY`.
2. Add a type and a store that mirror `createThrottleStore`. Keep `ThrottleStore` and `createThrottleStore` unchanged.
   ```ts
   export interface SeenBuild { build: string; at: number }
   export interface SeenBuildStore { get(): SeenBuild | null; set(v: SeenBuild): void }
   export function createSeenBuildStore(getStorage: () => Storage | null = () => window.localStorage): SeenBuildStore
   ```
   - `get()`: inside `try`, read `SEEN_BUILD_KEY` and `JSON.parse` it. Return it only if `typeof build === 'string' && build !== '' && Number.isFinite(at)`. A missing, malformed or wrong-shaped value, or a throw, falls through to `return memory`.
   - `set(v)`: first `memory = v`, then `try { setItem(SEEN_BUILD_KEY, JSON.stringify({ build: v.build, at: v.at })) } catch {}`. This is the same in-memory fallback as the throttle store.
3. Extend `CheckDeps` with `seen: SeenBuildStore;` and `loadedAt: number;`. `loadedAt` is the ms timestamp at which this page instance started.
4. Add a pure helper and export it for tests:
   ```ts
   export function seenNewerBuild(running: string, seen: SeenBuild | null, loadedAt: number, now: number): boolean {
     return seen !== null && seen.build !== running && seen.at > loadedAt && seen.at <= now;
   }
   ```
5. In `checkForNewVersion`, after the `runningBuild === null` skip and after `const now = deps.now();`, and **before** the `shouldCheck` throttle test:
   ```ts
   if (seenNewerBuild(deps.runningBuild, deps.seen.get(), deps.loadedAt, now)) {
     return deps.hasUnsavedWork() ? 'notify' : 'reload'; // no fetch, no throttle write
   }
   ```
   Then leave the throttle path exactly as it is: `store.set(now)` before the fetch, and the 5-minute retry `store.set(...)` on `null`. One addition: immediately after the `server === null` block (so only on a successful response), call `deps.seen.set({ build: server, at: now });`. Then do the existing `same` / `notify` / `reload` comparison. Do **not** write `seen` anywhere else, and never with `deps.runningBuild`.
6. In `startVersionWatch`, add `seen: opts.deps?.seen ?? createSeenBuildStore(),` and `loadedAt: Date.now(),` to the default `deps` object, before `...opts.deps`, so a test can override both. `startVersionWatch` is called once from `App.svelte`'s `onMount`, so `Date.now()` there is "this page load". Keep "no check on start": nothing new runs at start.
7. Update the file's header comment with one sentence: the newest build a server response reported is shared through `localStorage`, so a second stale tab reloads on focus without waiting out the hour.

New `it(...)` cases (titles as written):

1. `'seen-build store persists across instances and ignores malformed values'`. With `fakeStorage()`, `set({build:'n+2', at: 5})` and check that `getItem(SEEN_BUILD_KEY)` holds that JSON. A new instance returns it. Then `setItem(SEEN_BUILD_KEY, 'not json')`, `'{"build":3,"at":1}'` and `'{"build":"x"}'`, and check that a fresh instance's `get()` returns `null` each time.
2. `'seen-build store falls back to memory when storage throws'`. Use `createSeenBuildStore(throwingStorage)`: `get()` is `null`, then after `set` it returns the value.
3. `'a successful check records the server build; a failed check does not'`. Run `same` and `reload` cases and assert that `seen.get()` equals `{build: server, at: now}`. A `fetchBuild: async () => null` run leaves `seen.get()` as `null`.
4. `'a second stale tab reloads on focus from the build the first tab saw, without fetching'`. This is the two-tab sequence. Use one shared `fakeStorage()` `s`, and for each tab `createThrottleStore(() => s)` + `createSeenBuildStore(() => s)` (separate instances, the same storage). Tab A and tab B both run `'old+1'` with `loadedAt: 0`. At `T = 10*CHECK_INTERVAL_MS`, A's fetch returns `'new+2'` and gives `'reload'`. At `T + 60_000`, B's `fetchBuild = vi.fn(...)` gives `'reload'` and `expect(fetchB).not.toHaveBeenCalled()`. Repeat B with `hasUnsavedWork: () => true` and expect `'notify'`.
5. `'a tab already on the seen build still obeys the hour throttle'`. Same shared storage after A's check. Tab C runs `'new+2'` with `loadedAt: 0` at `T + 60_000`: the result is `'skip'` and C's fetch is not called.
6. `'a seen build recorded before this tab loaded is ignored'`. The record is `{build:'old+1', at: 100}`, and the tab runs `'new+2'` with `loadedAt: 200` and a throttle store inside the hour. The result is `'skip'`, with no fetch and no reload.
7. `'a seen build in the future is ignored'`. Call `seenNewerBuild('a', {build:'b', at: 2000}, 0, 1000)` and expect `false`. Also assert `seenNewerBuild('a', {build:'b', at: 500}, 0, 1000) === true` and that a same-build record gives `false`.
8. `'an old tab and a new tab sharing storage do not ping-pong'`. Use shared storage. Tab N (`'new+2'`, loadedAt 0) checks at T, and its fetch returns `'new+2'` (`same`). Tab O (`'old+1'`, loadedAt 0) at T+1s gives `'reload'`. Simulate O's reload landing on a stale shell: O again `'old+1'`, now with `loadedAt: T+2s`. Then alternate N and O visibility checks at T+3s…T+10s, all within the hour, with fetch spies. Every call returns `'skip'`, neither spy is called, and `s.getItem(SEEN_BUILD_KEY)` is byte-identical before and after the alternation. This proves no tab wrote its own build.
9. `'startVersionWatch reloads on focus from a newer seen build without fetching'`. Use `watchHarness({ seen: memSeen({build:'new+2', at: 5}), loadedAt: 0, store: memStore(Date.now()) })`. Make it visible and dispatch `visibilitychange`, then `flush`. Expect `reload` called once and `fetchBuild` not called. Also expect that it still does not check on start: before the event, neither was called.

## Review notes

Reviewed 2026-11-18 against `4394af74`. Verdict: **pass**, with three small test additions made in the review commit. Evidence is vitest with injected fakes (node environment). No browser was launched on the host (`AGENTS.md` §8), so real two-tab behaviour still rests on "Check after deploy".

- **Second stale tab:** a tab whose build differs from a record seen after it loaded returns `reload`, or `notify` with unsaved work or a focused field, with no fetch. Test 4 covers this, and the review added an assertion that this path leaves the throttle timestamp alone.
- **Tab on the stored build:** still skips inside the hour without fetching (test 5).
- **No loop or ping-pong:** the record moves only on a server response (`deps.seen.set({ build: server, … })` after the `null` return, never `runningBuild`). A reload resets `loadedAt` past the record, so a stale cached shell does not reload again, and a new tab ignores an older record. Test 8 also shows the stored bytes stay the same while old and new tabs alternate.
- **Malformed or future records are ignored:** non-JSON, wrong types, a missing `at`, an empty build (test added by this review), `Infinity` (via `Number.isFinite`), and `at > now`.
- **Storage failure:** the in-memory fallback works for both stores.
- **`#0715` behaviour unchanged:** no check on load, `store.set(now)` before the fetch, the 5-minute retry, the in-flight guard, and `onNotify` instead of a reload. `onNotify` in `App.svelte` only sets a flag, so repeated notifies from the seen path are idempotent.
- **Clock skew.** Tabs in one browser share `Date.now()`. If the system clock jumps backwards after a record is written, that record is in the future and ignored until the clock catches up. Meanwhile the throttle's `last > now` rule forces one ordinary check. When the clock passes the record, at most one more reload happens, which resets `loadedAt`, so this is bounded and does not loop. The worst case is a second tab on the old build for up to an hour, which is `#0715`'s behaviour. A forward jump changes nothing.
- **Extra mutations,** each applied to `versionCheck.ts` in place and restored from a scratchpad copy, with `shasum -a 256` matching `0e15b1da…ba47bb` afterwards:
  - These failed on the implementation as committed: drop `seen.at <= now` (the future test), drop `seen.build !== running` (3 tests), and write `seen` only on a mismatch (2 tests).
  - These **survived** the implementation as committed, and the review added a test for each:
    - The `startVersionWatch` default `loadedAt: Date.now()` changed to `0`. This is the production no-loop property, and the harness always injected `loadedAt`. New test: *startVersionWatch defaults loadedAt to its start…*.
    - `v.build !== ''` dropped. A `{"build":"","at":1}` case was added to the malformed list.
    - The seen path also writing the throttle. The two-tab test now asserts `LAST_CHECK_KEY` is unchanged.
  - Each of these three now fails a test. M1 was re-run and still fails 3 tests.
  - `seen.at > loadedAt` → `>=` survives. This is a same-millisecond boundary with no meaningful right answer, so it was left untested.
- **Runs:** `scripts/check.sh web` gave 154 files, 5683 tests passed (+1). `ISSUE=0718 scripts/check.sh go ./internal/db/...` gave `ok internal/db`, no skips, VERIFICATION PASSED.
