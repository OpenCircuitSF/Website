## Description

`#0129`'s fix has `RestartSignup` clear `subscribers.import_id`, so a person who
signs up on the website after their invite import was revoked is no longer
mistaken for an unaccepted invitee. That fix is correct and its review verified
the audit trail survives — the originating batch is still recorded on
`subscriber_events` rows (`imported` from `Commit`, `import_revoked` from
`Revoke`).

**But `subscriberEventView` serialises `campaign_id` and not `import_id`.** So
the data is in the database and simply not surfaced: on
`GET /admin/subscribers/{id}` the batch link is no longer reachable once
`import_id` has been cleared from the subscriber row.

Cosmetic, one field, and `#0129`'s review explicitly judged it non-blocking.

## Acceptance criteria

1. `subscriberEventView` exposes `import_id` alongside `campaign_id`.
2. The admin subscriber detail screen links to the originating import batch from
   the event, so provenance stays reachable after `RestartSignup` clears the
   subscriber-level column.
3. A subscriber with no import in their history is unaffected — the field is
   absent or null rather than rendered empty.
4. Nothing else starts reading `subscribers.import_id` as if it were durable;
   `#0129` deliberately made it a *current-state* field, and the event rows are
   the history.
5. `ISSUE=NNNN scripts/check.sh go ./internal/handlers/... ./internal/subscribers/...`
   and `scripts/check.sh web` pass with no skips.
