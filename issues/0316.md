## Description

`#0129`'s fix has `RestartSignup` clear `subscribers.import_id`, so a person who
signs up on the website after their invite import was revoked is no longer
mistaken for an unaccepted invitee. That fix is correct and its review verified
the audit trail survives — the originating batch is still recorded on
`subscriber_events` rows (`imported` from `Commit`, `import_revoked` from
`Revoke`).

**But `subscriberEventView` serialises `campaign_id` and not `import_id`.** So
the data is in the database and simply not surfaced: on
`GET /admin/subscribers/{id}` the batch link is no longer reachable once
`import_id` has been cleared from the subscriber row.

Cosmetic, one field, and `#0129`'s review explicitly judged it non-blocking.

## Resolution notes

> 🟢 Resolved 2026-08-27 — `import_id` now travels
> `subscriber_events.import_id` → `SubscriberEventRow` →
> `subscriberEventView` → `SubscriberEvent` → the Activity log, rendered
> as `(import batch #N)`. Verified the value comes from the **event row**,
> never from `subscribers.import_id`, and that no import-detail route exists
> to link to — so plain text is the correct rendering, not a shortfall.

## Acceptance criteria

1. `subscriberEventView` exposes `import_id` alongside `campaign_id`.
2. The admin subscriber detail screen links to the originating import batch from
   the event, so provenance stays reachable after `RestartSignup` clears the
   subscriber-level column.
3. A subscriber with no import in their history is unaffected — the field is
   absent or null rather than rendered empty.
4. Nothing else starts reading `subscribers.import_id` as if it were durable;
   `#0129` deliberately made it a *current-state* field, and the event rows are
   the history.
5. `ISSUE=NNNN scripts/check.sh go ./internal/handlers/... ./internal/subscribers/...`
   and `scripts/check.sh web` pass with no skips.

## Review notes

> 🟢 Reviewed 2026-08-27 (Opus, phase 3) — approved.

### Criterion 4 is the one that mattered, and it holds

The new field is sourced from the **event row**, not the subscriber row, at
every hop:

- `EventHistory`'s SELECT list changed from `action, created_at, campaign_id,
  detail` to `action, created_at, campaign_id, import_id, detail` **on
  `subscriber_events`** — an append-only table (`#0125`'s migration), whose
  `import_id` nothing in the tree ever UPDATEs or clears.
- `Get`'s events loop assigns `ImportID: e.ImportID` from that scanned row.
  `sub.ImportID` is not read anywhere in the loop.
- Independently confirmed by enumerating every non-test reference to
  `ImportID` in `internal/` and `cmd/`: this commit adds no new reader of
  `Subscriber.ImportID`. The pre-existing ones (`pending.go:170`,
  `Confirm`'s invite-accept at `store.go:813`, `Unsubscribe`'s invite-decline
  at `store.go:1024`, `subscriberView.ImportID`) are untouched.

Both structs carry a doc comment distinguishing the per-event `ImportID` from
the subscriber-level one, and so does `types.ts`'s `SubscriberEvent`. Since the
JSON response now has an `import_id` at two levels, that distinction is
load-bearing and it is written where a reader will hit it.

### The "no import-detail route" claim is accurate

Verified against the route table, not inferred. `cmd/opencircuit/main.go`
registers exactly three import routes, all POST:
`/admin/subscribers/import/preview`, `/admin/subscribers/import`, and
`/admin/imports/{id}/revoke`. There is no `GET /admin/imports` and no
`GET /admin/imports/{id}`; `web/src/views/` has no imports view, and the
router has no imports path. So there is nothing to link to, and rendering the
batch id as text is the right call rather than a shortfall — criterion 2's
"provenance stays reachable" is satisfied in the sense the issue's own
description uses. Building an imports screen is genuine new scope.

### Criteria 1 and 3

`json:"import_id,omitempty"` on a `*int64` omits the key entirely for an
ordinary signup, and `Admin.svelte` guards with `{#if ev.import_id != null}`,
so nothing renders as an empty parenthetical. Proved at both levels:
`TestSubscriberEvents_EventHistory_IncludesImportID` (store) and
`TestAdminSubscribers_Get_EventHistoryIncludesImportID` (through the real
`GET /admin/subscribers/{id}` JSON), each carrying an ordinary-signup half;
plus the extended `TestAdminSubscribers_Get_IncludesEventHistory`. All three
re-run individually and observed passing.
