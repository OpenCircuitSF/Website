## Description

`#0092` fixed the two illegal fence **closers** the docs guard accepted. Its
phase-3 review verified the fix against `commonmark.js` 0.31.2 as an oracle —
21 closer shapes, post-fix agreeing 21/21 where pre-fix disagreed on 7 — and
then found the same defect class on the **opposite branch**.

**CommonMark caps a fence opener at 3 columns of indentation too.** The opener
branch checks only `leadingRunLength(trimmed, ch) >= 3`, so `trimmed` discards
indentation exactly as the closer branch used to. Three divergences remain at
`f74cd6f`:

- an opener indented 4 spaces,
- an opener indented 1 tab (4 columns under CommonMark's tab-stop rule),
- a backtick inside a backtick fence's info string (`` ``` foo`bar ``), which
  CommonMark forbids.

**Individually each fails in the safe, loud direction — but the review
reproduced a still-silent mask post-fix.** A spurious open from an indented
`` ``` `` flips fence parity, and a later info-string fence flips it back,
letting a phantom table row past while the guard reports `ok`. That is the same
failure mode `#0092` was filed for, reached through the other branch.

The review confirmed by oracle that such a document is honest markdown — so this
is not a contrived shape, it is a shape a documentation author could write.

**A second item, from `#0089` and still open:** the probe forms both `#0092`
and this review constructed by hand should be committed as `cases` subtests. A
per-shape entry would have caught this round *and* the last one. Three passes
have now built the same probe set and thrown it away.

## Implementation notes

All changes are in `internal/db/docs_parity_test.go` (the guard is itself a
test file, per this codebase's existing pattern — no production package
owns `docTableRowLines`).

**The opener branch (`fenceChar == 0`) now mirrors the closer branch:**

```go
indented := leadingIndentWidth(line) > 3
switch {
case !indented && leadingRunLength(trimmed, '`') >= 3 &&
	!strings.Contains(trimmed[leadingRunLength(trimmed, '`'):], "`"):
	fenceChar = '`'
	fenceLen = leadingRunLength(trimmed, '`')
	continue
case !indented && leadingRunLength(trimmed, '~') >= 3:
	fenceChar = '~'
	fenceLen = leadingRunLength(trimmed, '~')
	continue
}
```

- Indentation cap: `leadingIndentWidth(line) > 3` reuses the exact helper and
  threshold the closer branch has used since `#0092` — a tab is 4 columns
  under its `col += 4 - (col % 4)` tab-stop arithmetic, so it's caught the
  same way a 4-space indent is, with no separate tab-handling code.
- Info-string check: for a backtick-run opener only, `trimmed` is sliced past
  the run and checked for any remaining backtick. A tilde-run opener has no
  such check, matching CommonMark (a backtick can't be confused with a `~~~`
  marker, so there's nothing to forbid there).
- An opener that fails to open (either reason) falls through to the existing
  indented-code-block check (`leadingIndentWidth(line) >= 4`) or is treated
  as ordinary prose — it does not silently vanish, it's handled exactly like
  any other line that was never a fence marker.

**Composed masking scenario (criterion 4).** Added
`TestDocTableRowLinesParityFlipMaskingRegression`, a standalone test asserting
`docTableRowLines` returns all three rows of a document where a 4-indented
`` ``` `` (opener residual 1) is immediately followed by a doc row naming a
migration that doesn't exist on disk, followed by `` ``` bogus`info `` (opener
residual 2), followed by a second real row. Pre-fix, the indented line
spuriously opens a fence; the info-string line, evaluated by the
*already-correct* closer branch (since state is wrongly non-zero), has
trailing text and so correctly refuses to close — meaning the fence never
closes for the rest of the document and every subsequent line, including the
stale/phantom row, is masked out of `rowLines` entirely. That row never
reaches `verifyDocRowsHaveMigration`'s reverse check, so the parity guard
would report `ok` on a document that actually names a nonexistent migration.
See `## Verification` for the direct before/after measurement.

**Probe forms committed as `cases` subtests (criterion 6, closing #0089's
open item):** three new cases in the existing "accepts" table (opener
indented 4 spaces, tab-indented opener, backtick-in-info-string opener, each
asserting the fence does *not* open and the following row *is* counted), one
new case in "rejects" (a tilde opener with a backtick in its info string,
asserting the fence *does* still open — proves the fix didn't over-correct).

**Doc comment** above `docTableRowLines` extended with a `#0224` paragraph
describing both residuals and the composition, in the same style as the
existing `#0083`/`#0086`/`#0089`/`#0092` paragraphs.
