# 0069 — Audit rollback is never asserted on a real in-flight auth action

## Description

Small, concrete, and cheap. [#0008](0008.md) claims audit rows are written inside the ceremony transaction. What is actually proven is narrower: `TestWriteTx_RollsBackWithTransaction` shows `audit.Logger.WriteTx` rolls back with *a* transaction, and other tests show rows exist after a *successful* ceremony. No test proves an audit row disappears when a real auth action fails mid-flight.

`#0008`'s implementer argued this needed fault-injection hooks in production code and narrowed the claim instead. That was right for `FinishRegistration` and `FinishLogin` — they call `tx.Commit` directly with no forceable failure point. It is **wrong for `LogoutAll`**, and the seam already exists.

## Root cause

`LoginService.commit` (`internal/auth/login.go:75`) is a function field that exists purely so tests can force a commit failure. `TestLogoutAll_NoMailWhenCommitFails` (`internal/auth/logout_all_test.go:320`) already uses it to fail `LogoutAll` at commit — *after* the `auditor.WriteTx` call at `internal/auth/login.go:358`.

That test asserts the session delete rolled back. It does not assert the `session.revoked_all` audit row is gone. The scenario is already constructed; only the assertion is missing.
