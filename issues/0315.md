## Description

`scripts/testdb.sh` refuses to create a scratch database when the shared
template is ahead of `migrations/`:

```
template opencircuit_test_template is at migration 25 but migrations/ is at 24
```

`scripts/check.sh` then **aborts before running anything**. Not one test, not a
build — the whole verification is unavailable.

That is exactly what happened while `#0123` was mid-flight: it added
`migrations/000025` and rebuilt the shared template to include it, which locked
out every other agent until the migration was committed. `#0129`'s reviewer hit
it, correctly declined to rebuild the template (that would have broken `#0123`),
and finished by hand-provisioning databases and running `check.sh`'s underlying
commands directly — with two distinct residual failures it then had to attribute
individually.

**The guard itself is right.** A template behind `migrations/` would silently
test the wrong schema, which is worse. What is missing is an escape that does not
require clobbering another agent's template.

## Why this will recur

It is structural, not a one-off. Any issue that adds a migration must rebuild the
template to test itself, and the template is shared by every concurrent agent
(CLAUDE.md §5a runs up to three). The window between "template rebuilt" and
"migration committed" is however long that issue's implementation and review
take — today, hours.

It also interacts badly with the review model: a reviewer verifying an *unrelated*
issue cannot tell whether a failure is its subject's or the template's, which is
the attribution problem §5a's per-agent databases exist to remove.

## Options

Both are legitimate; pick one and record why.

1. **Provision from the working tree's own `migrations/` when the template is
   ahead** — clone nothing, migrate a fresh database directly. Slower per
   creation (the template clone is ~0.2s and exists precisely to avoid this), but
   correct and unblocking.
2. **Per-agent templates**, keyed like the per-agent databases already are. Costs
   disk and a rebuild per agent, but removes the shared mutable resource
   entirely — which is the actual defect.

## Acceptance criteria

1. An agent whose `migrations/` is behind the shared template can still create a
   scratch database and run `scripts/check.sh`, without modifying the template.
2. The existing guard's protection survives: a database must never be provisioned
   at a schema **behind** what `migrations/` says, silently or otherwise.
3. The failure mode when provisioning genuinely cannot proceed is a clear message
   naming which side is ahead and what to do — not the current abort, which reads
   as "your environment is broken".
4. Rebuilding the shared template stays possible and stays explicit. Do not make
   it automatic — an implicit rebuild is what would clobber a concurrent agent.
5. Consider whether `scripts/testdb.sh template` should warn when another agent's
   scratch databases exist, the way `gc` already refuses without `--all` (§5a).
6. `scripts/check.sh guards` passes and `scripts/testdb.sh` still creates, drops,
   and gcs correctly.

**Chose option 1 — provision from the working tree's own `migrations/` when
the template disagrees with it.** `scripts/testdb.sh`'s `check_template_fresh`
hard-errored the moment `template_version` differed from `disk_version` in
**either** direction and told you to run `template` to fix it — which is
exactly the implicit-rebuild-adjacent trap criterion 4 forbids inviting: the
only "fix" the message offered was one that clobbers the shared resource. It's
replaced by `template_matches_disk()` (a boolean) plus `provision_from_migrations()`,
which creates one throwaway database and runs `migrate up` against it from
`$REPO/migrations` directly — the same thing `build_template()` already does
for the template itself, just aimed at a scratch database instead of the
shared one. `create` now branches: fast clone when the two agree, direct
`migrate up` (with a `warn_template_mismatch` note on stderr naming which side
is ahead and what the *manual* recovery command is) when they don't. Nothing
about `template`, `drop`, `list`, or `gc` needed to change.

Option 2 (per-agent templates) was the more thorough fix — it removes the
shared mutable resource rather than working around collisions with it — but it
does not fit this project's actual failure mode as well: the trigger here is a
**git-worktree divergence** (each worktree has its own `migrations/` on disk,
so an uncommitted migration in one worktree never appears in another's `ls`),
not routine per-agent template churn. A per-agent template still needs its
*own* freshness check against that agent's `migrations/`, so it doesn't remove
this class of mismatch — it just moves who owns the stale copy — while paying
a template-sized rebuild (`DROP`/`CREATE`/`migrate up`, ~2s) for every agent
instead of only the agents that actually hit a mismatch. Option 1 costs the
~2s only when a mismatch is live, never rebuilds a resource anyone else reads,
and is a smaller, more legible diff. If per-agent template churn (not
worktree divergence) turns out to be the dominant cause in practice, option 2
is worth revisiting — recorded here rather than silently dropped.

**When provisioning genuinely cannot proceed** (criterion 3's "clear failure
mode"): the only such case left is `migrate` missing from `PATH`, which
`provision_from_migrations()` still checks explicitly and reports by name —
same as `build_template()` already did. There is no "fallback is too slow to
matter" case in practice for this project: `migrate up` from an empty database
takes well under a second even for the full 25-migration history (measured
below), and CLAUDE.md §5 already establishes there is no performance
requirement here.

**Criterion 4 — rebuilding stays explicit.** `build_template()` is untouched
except for one addition (the criterion-5 warning below); nothing in `create`,
`reset`, or the new fallback path calls it. The one *pre-existing* implicit
build — `template_version` reporting `none` when the template doesn't exist
at all — was left alone for the "none" case specifically because there is
nothing to clobber yet, but the mismatch case (something already there that
disagrees) no longer auto-repairs itself the way it used to for "none"; it
falls back instead.

**Criterion 5 — considered, implemented as a warning, not a refusal.**
Unlike `gc`, rebuilding the template never drops another agent's scratch
database, so a hard refusal (`gc`'s shape) would be protecting against a
weaker harm than the one `gc` guards. What it *can* silently do is change
what a concurrent agent's **next** `create` clones from, turning a fast clone
into the slower fallback for anyone whose `migrations/` still matches the old
template — without this change, that agent used to get a hard *error*
instead, so the harm this warning is naming is now strictly smaller than it
was before this issue, but still worth surfacing. `build_template()` now
lists any other scratch databases present and explains the consequence for
their owners before rebuilding, on stderr, without blocking.

### The worktree-divergence diagnosis holds — and it is not hypothetical

The implementer's sharpening of the diagnosis (the trigger is git-worktree
divergence, not migration timing per se) is **confirmed by measurement, in the
wild**: at review time `git worktree list` showed a second live worktree,
`/private/tmp/oc-live` at `cc670fa`, whose `migrations/*.up.sql` count is
**20**, against **25** in the main checkout and **25** in the shared template.
Any agent running `create` from that worktree hits the exact reported abort. I
reproduced it end to end with the pre-change script (see below): exit 1, the
verbatim `template ... is at migration 25 but migrations/ is at 24` message,
and no database created — `scripts/check.sh` would abort before a single test.

**It also justifies choosing option 1.** Per-agent templates do not remove this
class of mismatch, they relocate it: a template built from agent A's tree is
stale the moment A's own `migrations/` moves (a rebase, a pull, its own new
migration), so each per-agent template still needs the same freshness check
against the same `ls migrations/`. Three further points settle it:

- **Measured, the fallback is cheaper than a per-agent template.** A full
  `migrate up` of all 25 migrations into a fresh database is **0.29s** wall;
  the clone fast path is **0.19s**. The difference is ~0.1s, not the ~2s the
  header comment estimates. A per-agent template would pay that same ~0.3s
  build *unconditionally, per agent*, then clone — strictly more work than
  simply migrating the one database each `check.sh` run needs.
- **Per-agent templates would collide with the existing namespace.** `list` and
  `gc` glob `opencircuit_test_%` and exclude only the single `$TEMPLATE`, so
  per-agent templates would be swept by `gc --all` as if they were scratch
  databases — new hazard, in exactly the area `#0150` already had to fix.
- Option 1 costs only while a mismatch is live and touches no shared resource.

Option 2 remains recorded in the work log as the fallback if per-agent template
churn ever dominates. That is the right disposition.

### Criterion 2 — the "never behind `migrations/`" protection survives

**By construction:** the clone path is now reachable only inside
`if template_matches_disk` (`template_version` = `disk_version`); every other
case routes to `provision_from_migrations`, which runs `migrate up` from
`$REPO/migrations` into an empty database. There is no path that clones a
template whose version differs from disk. Confirmed behaviourally in **both**
directions, using a **private `TEMPLATE_DB` override** and a private repo copy
holding only migrations 1-24 (so no worktree or shared file was touched):

| Scenario | template | `migrations/` | result |
|---|---|---|---|
| pre-change script, template ahead | 25 | 24 | **exit 1**, no database — the reported bug |
| post-change, template ahead | 25 | 24 | exit 0, ran 1-24, db `schema_migrations` = **24**, `email_campaigns` has no `archive` columns |
| post-change, disk ahead | 24 | 25 | exit 0, ran 1-25, db = **25** |
| post-change, matching | 25 | 25 | exit 0, clone path, **zero bytes on stderr**, db = 25, 0.19s |

Stdout in every passing case was exactly one line, the DSN (checked with `od
-c`), which is what `scripts/check.sh:782`'s `TEST_DATABASE_URL="$(...)"`
requires; all notes and `migrate` output go to stderr and reach the terminal
un-swallowed.

**Pre-existing residual, not a regression:** both the old guard and the new one
compare only the highest migration *number*. Under the greenfield rule
(CLAUDE.md §1) a migration may be edited in place, so an edited
`000025_*.up.sql` leaves both sides reading 25 and the clone path hands back the
old schema. This nearly mattered during this very review — `#0123`'s reviewer
added a `CHECK` constraint to `migrations/000025` in the working tree — and did
not only because they rebuilt the template by hand (verified: the template
carries `email_campaigns_slug_not_blank_check`). Worth a follow-up issue; see
below.

### Criterion 5 — a warning is right here; a refusal would be wrong

Concur with the implementer, for a sharper reason than "smaller harm":

- `gc --all` earns its refusal because it **destroys** other agents' databases
  irrecoverably. Rebuilding the template destroys nothing — every existing
  scratch database is an independent copy and no running test is affected.
- Post-`#0315` the entire consequence for a concurrent agent is a `create` that
  is **0.1s slower** and prints a note. Before this change the same act hard-
  blocked them, so this issue has already removed the harm a refusal would
  have been guarding.
- A refusal would have a real cost: rebuilding the template is the remedy both
  new stderr messages and the file header prescribe. Making the prescribed
  remedy require a flag whenever *any* other scratch database exists — the
  normal state under §5a's three-agent concurrency — trains agents to pass the
  flag reflexively, which is how `--all` would stop meaning anything.

One cosmetic nit, not blocking and not worth a bounce: the new listing selects
`datname like 'opencircuit_test_%' and datname <> '$TEMPLATE'`, so when
`TEMPLATE_DB` is overridden it reports the *default* shared template as
"another scratch database" (observed while building my private template).
Only affects override use. `and datname not like '${PREFIX}template%'` would
close it if anyone touches this line again.

### To file (reviewer does not file; orchestrator please allocate)

**Title:** `scripts/testdb.sh` compares migration numbers, so an edited
migration is invisible to the freshness check.
**Body:** `disk_version()` takes the highest `NNNNNN` from
`migrations/*.up.sql` and `template_version()` reads `schema_migrations.version`
— both numbers. Under the greenfield rule a migration may be edited in place,
which changes the schema without changing either number, so
`template_matches_disk` reports a match and `create` clones a template built
from the *old* file contents. Silent, and it produces failures that look like
the caller's bug. Nearly live during `#0315`'s review: `#0123` added a `CHECK`
constraint to `migrations/000025` in the working tree with both sides still
reading 25; only a manual template rebuild kept the two in step. Suggested fix:
have `build_template` record a digest of `migrations/*.sql` (a settings row, a
comment on the template database, or a sidecar file keyed to the template) and
have `template_matches_disk` compare that instead of, or in addition to, the
version number — a mismatch then routes to the existing
`provision_from_migrations` fallback with no new failure mode. Pre-existing;
predates `#0315` and is not a regression from it.
