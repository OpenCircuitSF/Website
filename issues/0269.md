## Description

Three items from `#0124`'s phase-3 review. That issue **passed** — the breaker
works, its boundaries are mutation-proved, and the resume path cannot mail an
address that has since bounced or complained. These are the leftovers.

**1. `migrations/000014`'s comment is false.** It says `000016` "is deleted
outright". It was not — it is a documented no-op, kept because
`verifyContiguous` requires a gap-free sequence. The comment contradicts
`000016` itself, `docs/database.md`, and `#0124`'s own notes. Leftover from a
rejected delete-first attempt. One line.

**2. `breakerTestMailer` emits colliding `ses_message_id`s, and the boundary
tests hold today by luck.** Its counter restarts at 1 per test while
`EventCounts` joins on `ses_message_id` alone. Measured by the reviewer: **219
event rows sharing only 100 distinct ids**, with `breaker-1` appearing six
times; a probe seeding 5 bounces read back `bounced=200`.

The boundary proofs still pass **only because the polluting id set happens to be
a subset of the polluted test's own**. That is a coincidence of the current
fixtures, not a property anyone chose — and these are the tests that pin a
circuit breaker guarding the one operation with no undo. Fix with
`testdb.Unique()` in the id. **Production is unaffected**; real SES ids are
unique.

**3. The breaker is evaluated only at the *end* of a batch.** So each `Resume`
puts a full `SEND_BATCH_SIZE` — production default **50** — on the wire before
the rate is re-checked. Measured: 300 recipients at a 100% bounce rate with
`batchSize=100` tripped at 100, then one `Resume` sent **exactly +100 more**
before re-pausing.

**This is not a bypass.** It always re-arms, and every resume is confirmed,
audited and alerted. But it is weaker than `delivery_health.go`'s own claim that
"there is no request shape that skips the worker's own check", and an operator
resuming to test a fix spends a batch each time. Calling `checkDeliveryHealth`
once at the top of `drainLoop` closes it.

**Related, worth writing down while fixing 3:** the denominator grows
*synchronously* with sends while the numerator grows *asynchronously* with
webhooks, so a resumed campaign's measured rate dilutes as it sends. That is
inherent to measuring a rate against in-flight mail, not a defect — but it means
the breaker is systematically late in proportion to batch size, which is another
argument for evaluating at the top.

### Fix-forward: the review-bounce defect (top-of-loop check stranding a fully-drained campaign)

Fixed on top of `8bd4a1b` — that commit stays; this is the delta requested by
the review below.

**The fix.** `checkAndMaybePauseDeliveryHealth` (`internal/mailing/worker.go`)
now takes a `gateOnQueuedWork bool`. `deliveryHealthResult` gained a `Queued`
field (`internal/mailing/delivery_health.go`), populated from
`CampaignStatsStore.StatusCounts`'s existing `Queued` count — already fetched
in the same query `checkDeliveryHealth` uses for `Sent`, so this costs nothing
extra. The two call sites in `drainLoop` now differ:

- **Top of the loop** (before `ClaimBatch`) passes `gateOnQueuedWork=true`: a
  trip is only actionable — worth pausing for — if `Queued > 0`. With nothing
  left queued, there is nothing further this trip could stop, so the check
  stands aside and lets the loop reach `ClaimBatch` → empty → `CompleteIfDone`,
  exactly the escape hatch that existed before #0269 added this call site.
- **End of a batch** (unchanged position) passes `gateOnQueuedWork=false`,
  unconditional exactly as before #0269: a trip discovered as the very last
  batch finishes still pauses and alerts, so the operator learns the send
  ended over threshold even though nothing more will be sent.

This is why the reviewer's "do not simply move the call below `ClaimBatch`"
constraint is preserved: the top-of-loop call is still BEFORE `ClaimBatch`
(so a genuine still-bad rate with real work queued still stops before
claiming a row, never stranding `batchSize` rows in `'sending'`) — only
*whether it acts on a trip* is now conditioned on there being work to protect,
not *where in the loop it runs*.

**Regression test.** `TestWorker_CircuitBreaker_TripsOnFinalBatch_ResumeReachesSent`

### The defect: a fully-drained campaign that ends over threshold can never reach `sent`

The top-of-loop check runs on **every** iteration, including the iteration whose
only job is to observe an empty `ClaimBatch` and call `CompleteIfDone`. So when
the breaker trips on the **last** batch — nothing left queued — the campaign is
now stuck.

Measured, same worktree, 100 recipients / `batchSize=100` / `minSample=100` /
100% bounce, so the trip lands exactly as the final batch finishes:

| | after initial drain | after Resume #1 | after Resume #2 |
|---|---|---|---|
| **at `8bd4a1b`** | `paused_delivery_health`, sent=100, queued=0 | `paused_delivery_health`, sent=100, queued=0 | `paused_delivery_health`, sent=100, queued=0 |
| **with the top-of-loop call removed** | `paused_delivery_health`, sent=100, queued=0 | **`sent`** | *(Resume rejected: illegal transition — correct, it is terminal)* |

Before this change a resume of a fully-drained campaign fell through to
`ClaimBatch` → empty → `CompleteIfDone` → `sent`. Now the top-of-loop check
trips first and `CompleteIfDone` is unreachable forever, because the rate is
genuinely still over threshold and nothing further will ever be sent to move it.

Consequences:

- The campaign never reaches its terminal `sent` state and `auditSendCompleted`
  never fires. The only exits from `paused_delivery_health`
  (`internal/mailing/campaigns.go:584,635`) are **Cancel** — which mislabels a
  campaign whose mail all went out — and **Resume**, which re-pauses.
- Every resume attempt is a *fresh* trip: `MarkPausedDeliveryHealth` returns
  `did=true` because the status was `scheduled`/`sending` in between, so
  `pauseCampaignDeliveryHealth` writes another
  `ActionEmailCampaignPausedDeliveryHealth` audit row **and enqueues another
  admin alert email** each time. An operator retrying twice generates two of
  each.
- This is not the exotic corner it might look like: a rate that crosses
  threshold on the final batch is the ordinary shape of "the send finished and
  the numbers were bad."

**What must change.** The breaker exists to stop *further* sends; when nothing
remains queued there are none to stop, and pausing is both meaningless and
unescapable. The top-of-loop evaluation must not be able to pause a campaign
that has no queued rows left — e.g. gate it on remaining queued work, or let the
"empty batch → `CompleteIfDone`" path run first on an iteration that claims
nothing. Note the ordering constraint that made "top of loop, before
`ClaimBatch`" the right place in the first place: tripping *after* `ClaimBatch`
would strand `w.batchSize` rows in `'sending'` until `OrphanSweep`, so do not
simply move the call below the claim.

**And add the regression test**, in the same shape as the existing one: a
campaign whose final batch trips must still reach `sent` on resume, with zero
further messages sent. That test fails today and passes both before this change
and after the fix, so it pins exactly the thing that regressed.

**The gate is safe, and the argument is structural rather than empirical.**
`StatusCounts` counts `Queued` as `count(*) FILTER (WHERE status = 'queued')`
for the campaign; `ClaimBatch` selects `WHERE campaign_id = $1 AND status =
'queued'`. **The same predicate.** So `Queued == 0` at the gate means the very
next statement claims nothing and sends nothing. The gate cannot let a message
through that the un-gated check would have stopped — the worst it can do is
*defer* a trip to the next evaluation, in a state where zero messages go out
either way.

The three states the re-review was asked to consider, checked against that:

- **Rows parked in `'sending'`** (an orphan not yet stale, a claim held
  elsewhere): `CompleteIfDone` requires `NOT EXISTS (… status IN ('queued',
  'sending'))`, so those rows *block completion*. The gate standing aside does
  not wrongly complete the campaign.
- **An orphan sweep about to return rows to `'queued'`**: `OrphanSweep` runs in
  `drainCampaign` before `drainLoop`, and once rows are back the next
  top-of-loop check sees `Queued > 0` and trips normally.
- **A claim held by another worker**: campaign-level claim
  (`ClaimStart`/`ClaimResume`, both status-guarded `UPDATE`s) means only one
  worker drains a campaign at a time. Even in a hypothetical where rows became
  `'queued'` between the gate's read and `ClaimBatch`, the **ungated
  end-of-batch check** fires immediately after that batch — bounded at one
  batch, i.e. exactly the pre-`#0269` behaviour, never worse.

Measured rather than only reasoned: with 200 rows forced into `'sending'` with
a fresh `claimed_at` (so `Queued == 0` while the send is genuinely unfinished)
and the campaign resumed, the pass sent **zero** further messages, did **not**
complete the campaign (it stayed `sending`), and did not pause. Returning those
rows to `'queued'` made the very next pass trip and pause, still with zero
further messages sent. **The trip is deferred, never lost, and nothing escapes
in the interval.**

**`Queued` and `Sent` cannot skew.** Both are `FILTER` aggregates in the
*single* `SELECT` `StatusCounts` already issued — one statement, one snapshot,
one MVCC view. Reading `Queued` adds no round trip and introduces no window in
which the two could disagree.
