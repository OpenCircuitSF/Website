## Description

`#0490` pinned that `serveDevMode` threads `devAutoLogin` into `mountAndServe`'s
`outerMiddleware` slot. **`servePostgres` does the same thing with
`devAdminAutoLogin`, and nothing pins it.**

Confirmed independently three times — by `#0490`'s implementer, by its reviewer,
and by the orchestrator:

- `grep -rn 'servePostgres(' cmd/opencircuit/*_test.go` returns **nothing**. No
  test calls that function.
- `#0484`'s `TestNewDevAdminAutoLogin_RealRouteTable` builds the middleware
  **itself** via `newDevAdminAutoLogin` in the test body and hands it to its own
  helper, which calls `mountAndServe` directly — so it proves the middleware
  heals when present in the chain, never that `servePostgres` puts it there.
- The only test reading that function's source is
  `TestServePostgres_OneSEOSiteFlowsToEveryConsumer`, which mentions neither
  `outerMiddleware` nor `devAdminAutoLogin`.

So the Postgres-path dev login is connected by one argument position with no
guard, and `mountAndServe` treats a nil outer middleware as "no wrapper" by
design — the failure is **silent**: the server starts, serves, and never logs
anyone in.

## Why this is worth its own issue

`#0490` was correctly scoped to `serveDevMode` by its title and criteria, so its
implementer recorded this rather than building it — the right call, and the
reason it is filed rather than smuggled in.

But the asymmetry is now the odd thing: the json path has a wiring guard and the
Postgres path, which `#0402` built precisely because the mailing subsystem
cannot be exercised under `STORAGE=json`, does not.

## The model exists — reuse it, do not redesign

`#0490` shipped `TestServeDevMode_WiresDevAutoLoginIntoMountAndServe`, itself
modelled on `#0326`'s SEO-flow guard and reusing its `findFuncDecl` and
`exprString` helpers. Its shape:

- re-parse `main.go` on every run;
- resolve `mountAndServe`'s `outerMiddleware` **parameter position by name**,
  never by index;
- locate the construction and the `mountAndServe` call;
- assert the argument at that resolved position is exactly the bound identifier.

**The by-name resolution is load-bearing**, and `#0490`'s reviewer proved it
rather than reading it: it moved the `outerMiddleware` parameter ahead of
`requireSession` in the *signature* — both have the same type, so every call
site still compiled — and the guard tracked the move, reporting index **36**
instead of 38 and naming the wrong identifier. A hardcoded index would have gone
green.

## Acceptance criteria

1. **Pin that `servePostgres` passes its constructed dev-admin middleware into
   `mountAndServe`'s `outerMiddleware` position.** Reuse `#0490`'s guard shape
   and its existing helpers; do not write a second mechanism.
2. **Prove it fails, with the mutation that matters**: replace the argument with
   a `nil` literal, keeping the identifier used so it still compiles. That is
   what the real defect looks like, since a dropped argument fails to compile
   instead. Mutate a copy, never `git stash` (`CLAUDE.md` §8a), and restore
   byte-identically with SHA-256.
3. **Also run the signature mutation** `#0490`'s reviewer used — move
   `outerMiddleware` ahead of a same-typed parameter and confirm your guard
   tracks it. Reading the code for the absence of an integer literal is
   necessary, not sufficient.
4. **Consider whether one guard should cover both call sites** rather than two
   near-identical tests. `#0490`'s exists and passes; if a shared form is
   cleaner, say so and say what it costs. **Do not** weaken or rewrite `#0490`'s
   guard to fit a generalisation — it is proved, and a regression there is worse
   than a little duplication.
5. **Do not build a mechanism that guards the guard** (`CLAUDE.md` §8;
   `#0258`'s six-pass spiral). One assertion that fails when the wiring breaks
   is the whole deliverable.
6. Note what `#0490`'s guard deliberately does **not** catch, so you inherit the
   same boundaries knowingly: a nil arriving from the constructor (unnecessary —
   the constructor refuses loudly), and any construction shape other than
   `name := ...(...)`, so inlining the call into the argument list fails it
   despite correct wiring. That is a deliberate fail-closed maintenance cost.

## Fix

Added `TestServePostgres_WiresDevAdminAutoLoginIntoMountAndServe`
(`cmd/opencircuit/servepostgres_devadminautologin_wiring_guard_test.go`), a
second AST guard mirroring `TestServeDevMode_WiresDevAutoLoginIntoMountAndServe`
(`#0490`)'s exact shape: re-parse `main.go` fresh on every run, resolve
`mountAndServe`'s `outerMiddleware` position by name via the existing
`paramIndexByName`, find `servePostgres`'s own construction of the middleware,
find `servePostgres`'s own `mountAndServe` call, and assert the argument at the
resolved position is exactly the identifier the construction bound.
`findFuncDecl`, `exprString`, and `paramIndexByName` are reused directly, not
duplicated — Go test files in one package share top-level scope.

**Handling the two-value assignment (dispatch note).** `servePostgres` builds
its middleware with `devAdminAutoLogin, err := newDevAdminAutoLogin(...)`, a
two-value assignment, versus `serveDevMode`'s single-value
`devAutoLogin := middleware.DevAutoLogin(...)`. `#0490`'s scan logic —
`for i, rhs := range assign.Rhs { ...; if i < len(assign.Lhs) { lhsIdent :=
assign.Lhs[i] } }` — turns out to require **no change** for this shape: `go/ast`
represents `a, b := f(...)` as one `*ast.AssignStmt` with `Rhs` holding a
**single** `*ast.CallExpr` (however many values it returns) and `Lhs` holding
both names. Ranging over `Rhs` therefore visits the call exactly once at
`i == 0`, and `assign.Lhs[0]` is the *first* assigned name — the middleware
value, not `err`, by this codebase's own value-then-error convention. So the
same index-into-`Rhs` logic is reused verbatim in the new file; only the
call-target match changes (a bare `*ast.Ident` named `newDevAdminAutoLogin`,
since it is a same-package call with no `middleware.`-style selector, versus
`#0490`'s `*ast.SelectorExpr` match on `middleware.DevAutoLogin`). The new
test's doc comment spells this out explicitly rather than leaving it to be
re-derived, per the dispatch's instruction not to silently widen `#0490`'s own
matcher to accept both shapes.

**Criterion 4 — two guards, not one generalisation, and what that costs.**
Chose **not** to fold both call sites into a single parameterised guard. The
two real shape differences above — selector call vs. bare identifier call, and
which matcher applies — are exactly the kind of permanent branching a shared
helper would carry for two call sites unlikely to ever gain a third sibling.
A mistake in that shared branching (matching the wrong shape against the wrong
call site) could silently pass both at once, which is a worse failure mode than
duplication. The measured cost is real but bounded: the new file is 254 lines
— 129 comment, 7 blank, 118 code — close to `#0490`'s own 215/81/8/126
proportions, and the actual duplicated *code* is small (two `ast.Inspect`
walks and the final comparison); `findFuncDecl`, `exprString`, and
`paramIndexByName` are shared code, not shared prose, and are not duplicated.
`#0490`'s guard is untouched — not its assertions, not its helpers.

**Criterion 6 — boundaries inherited and recorded.** Same as `#0490`: this
guard is agnostic to the wired value's identity beyond its name, doesn't check
error handling, and understands exactly one construction shape (a plain
`a, b := f(...)` binding), so an inlined call would fail it despite correct
wiring — a deliberate fail-closed cost. One difference from `#0490` worth
recording explicitly: unlike `middleware.DevAutoLogin` (which panics rather
than ever returning nil), `newDevAdminAutoLogin` **legitimately returns nil**
on every production boot where `DEV_ADMIN_LOGIN` isn't set (`#0402`). This
guard doesn't care — it only proves the *identifier* is threaded through,
never what it holds at runtime — but it's a boundary worth naming so a future
reader doesn't mistake "nil at runtime" for something this guard would flag.

## Prove it fails (criteria 2 and 3)

`cmd/opencircuit/main.go` was copied aside and its SHA-256 recorded
(`b45b918f0d14e2bf67ba6c0b05dbe11fb9761db8611f93d64ea60e357805d432`, matching
the hash `#0490` recorded — the file has not moved since) before any edit,
mutated twice in a copy — never `git stash` (`CLAUDE.md` §8a) — and restored
byte-identically after each, confirmed both by `shasum -a 256` and by
`git status --porcelain -- cmd/opencircuit/main.go` reporting clean.

1. **Nil literal.** Replaced the `outerMiddleware` argument at
   `servePostgres`'s `mountAndServe` call with a literal `nil`, adding
   `_ = devAdminAutoLogin` right after its construction so the identifier
   stays used and the mutation is a pure wiring defect. The guard failed:

   ```
   servepostgres_devadminautologin_wiring_guard_test.go:248: main.go:565:33: servePostgres passes nil at mountAndServe's outerMiddleware position (index 38), want the identifier "devAdminAutoLogin" bound by newDevAdminAutoLogin's own call — mountAndServe's doc comment says a nil (or wrong) outerMiddleware here means "no wrapper" BY DESIGN, so this is silent: the server starts, serves, and never logs a developer in (#0492)
   ```

2. **Signature mutation** (the one `#0490`'s reviewer used). Moved
   `outerMiddleware` ahead of `requireSession` in `mountAndServe`'s parameter
   list — both share type `func(http.Handler) http.Handler`, so every call
   site still compiled. The guard tracked the move:

   ```
   servepostgres_devadminautologin_wiring_guard_test.go:248: main.go:564:3: servePostgres passes requireSession at mountAndServe's outerMiddleware position (index 36), want the identifier "devAdminAutoLogin" bound by newDevAdminAutoLogin's own call — mountAndServe's doc comment says a nil (or wrong) outerMiddleware here means "no wrapper" BY DESIGN, so this is silent: the server starts, serves, and never logs a developer in (#0492)
   ```

   Index **36**, not 38, naming `requireSession` rather than the
   still-present `devAdminAutoLogin` — the same signature mutation applied to
   `#0490`'s own guard against this identical `main.go` change independently
   reported the same index-36 finding on its sibling call site
   (`... serveDevMode passes requireSession at mountAndServe's outerMiddleware
   position (index 36), want the identifier "devAutoLogin" ...`), run in the
   same `go test -run` invocation as proof neither guard was disturbed by the
   other's presence in the package.

3. **Dropped argument** (tried, expected to fail to compile rather than reach
   the guard — same as `#0490`). Removing the argument outright produced two
   diagnostics: `declared and not used: devAdminAutoLogin` and
   `not enough arguments in call to mountAndServe`, confirming this mutation
   is a stronger failure (the build itself refuses) rather than a gap, exactly
   `#0490`'s own characterisation of its sibling case.

`main.go` was restored from the pre-mutation copy after each of the three
mutations and confirmed byte-identical by `shasum -a 256` every time
(`b45b918f0d14e2bf67ba6c0b05dbe11fb9761db8611f93d64ea60e357805d432`), and
`git status --porcelain -- cmd/opencircuit/main.go` reported clean at the end.
The new guard test file was never touched during any mutation.

`gofmt -w` was run on the new file both before and after writing its doc
comment (which contains double-quote-adjacent prose, per `CLAUDE.md` §8's
gofmt-rewrite gotcha) with a `shasum -a 256` comparison — stable both times
(`08953a8096ae4d6d9fb519db75eb5658e8b60a48bb7b16e48d8ce21928d1f599`).

## Review notes

**Approved.** All six criteria hold. The two claims the dispatch asked me to
test hardest — that a two-value assignment needs no change to the inherited
scan, and that the two guards are genuinely independent rather than one
plausible-looking test propping up another — both survive being probed rather
than read.

**The two-value assignment claim is correct, checked against the AST rather
than the prose.** I parsed `cmd/opencircuit/main.go` with a throwaway
`go/ast` program and printed the assignment the guard keys on: it is one
`*ast.AssignStmt` with `len(Rhs) == 1`, `len(Lhs) == 2`, the call visited
exactly once at `i == 0`, and `Lhs[0]` holding `devAdminAutoLogin` with `err`
at `Lhs[1]`. So ranging over `Rhs` and indexing `Lhs` by the same `i` binds
the middleware value, exactly as the implementer reports.

**And the counterfactual the dispatch worried about fails closed rather than
passing wrongly.** Go requires a multi-value assignment's left-hand order to
follow the callee's result order, so `Lhs[0]` is the middleware for as long as
`newDevAdminAutoLogin` returns value-then-error. I still probed the inverted
shape directly, running the same program over a synthetic function whose
assignment reads error-first: the scan then binds `err`, which cannot equal
the identifier at the call site, so the guard reports a mismatch and fails.
There is no ordering under which this guard asserts on the wrong identifier
and goes green.

**Only the call-target match changed, and `#0490`'s matcher is untouched.**
The new scan tests `call.Fun.(*ast.Ident)` for the name
`newDevAdminAutoLogin`, the correct shape for a same-package call with no
package qualifier, against the sibling's `*ast.SelectorExpr` test on the
`middleware` qualifier. Everything else — the fail-closed counting of exactly
one construction and exactly one `mountAndServe` call, the `paramIndexByName`
lookup, the final positional comparison — is the inherited shape verbatim.

**The cross-check reproduces, and it is the strongest evidence here.** With
`mountAndServe`'s `outerMiddleware` parameter moved ahead of the same-typed
`requireSession`, I ran both guards in one `go test -run` invocation and both
failed independently, each tracking the move to index 36 and each naming its
own call site and its own issue number:

```
    servedevmode_devautologin_wiring_guard_test.go:185: main.go:1096:3: serveDevMode passes requireSession at mountAndServe's outerMiddleware position (index 36), want the identifier "devAutoLogin" bound by middleware.DevAutoLogin's own call — ...
--- FAIL: TestServeDevMode_WiresDevAutoLoginIntoMountAndServe (0.00s)
    servepostgres_devadminautologin_wiring_guard_test.go:248: main.go:564:3: servePostgres passes requireSession at mountAndServe's outerMiddleware position (index 36), want the identifier "devAdminAutoLogin" bound by newDevAdminAutoLogin's own call — ...
--- FAIL: TestServePostgres_WiresDevAdminAutoLoginIntoMountAndServe (0.00s)
```

**The `nil` mutation gives the complementary half of that evidence.**
Replacing `servePostgres`'s argument with a literal `nil` (adding
`_ = devAdminAutoLogin` so the identifier stays used and the mutation is a
pure wiring defect) failed with the message the implementer recorded,
verbatim, at index 38 and naming `nil` — and
`TestServeDevMode_WiresDevAutoLoginIntoMountAndServe` stayed green through
that same run, which is right, because that mutation does not touch the json
path's call site. Taken with the signature result above, the pair reads each
call site and only its own: neither test can be satisfied by the other's
subject, and neither was weakened to accommodate the other.

**Restoration is byte-identical after both mutations.** `main.go` was copied
aside before any edit and restored from that copy each time — never
`git stash`, per `CLAUDE.md` §8a — with `shasum -a 256` returning
`b45b918f0d14e2bf67ba6c0b05dbe11fb9761db8611f93d64ea60e357805d432` before and
after each, matching the hash the implementer and the earlier review both
recorded. `git status --porcelain -- cmd/opencircuit/` reported clean
afterwards, and the guard test file itself was never edited.

**Criterion 4 — I agree with two guards, and the duplication is smaller than
the line count suggests.** A shared parameterised guard would have to carry a
permanent per-site branch for the selector-versus-bare-identifier call shape,
and the failure mode of getting that branch wrong is the one this whole family
exists to prevent: a matcher pointed at the wrong subject still satisfies both
fail-closed counting steps, so it would report green for a call site nobody is
actually reading. The measured cost is mostly prose — of 254 lines, the doc
comment is 129 and the remaining 118 include the multi-line failure format
strings, leaving roughly fifty lines of genuinely duplicated mechanism in two
`ast.Inspect` walks and one comparison. I confirmed the helper reuse claim
directly: `findFuncDecl`, `exprString`, and `paramIndexByName` are each
declared exactly once in `cmd/opencircuit`, and a redefinition would be a
compile error rather than a silent fork.

**The one real cost worth naming is the prose, not the code.** This file's doc
comment restates a good deal of its sibling's reasoning, so a future change to
the shared rationale has two homes to keep honest. That is the trade the
implementer described and it is the right way round — a stale sentence is
recoverable, a shared matcher aimed at the wrong call site is not — but it is
a cost, not a free choice.

**Criterion 6's production boundary is stated, and stated correctly.** The doc
comment says outright that `newDevAdminAutoLogin` returning nil is the
*expected* value on every production boot where an operator has not set
`DEV_ADMIN_LOGIN`, unlike `middleware.DevAutoLogin`, which panics rather than
returning nil — and that this guard is therefore agnostic to what the
identifier holds at runtime, proving only that whatever the constructor
returned is threaded through. That distinction is real and it is the one a
future reader would most easily get wrong, so having it in the file rather
than only in the issue is the right placement. The inherited boundaries are
recorded too: the single understood construction shape, so an inlined call
fails the guard despite correct wiring, and error handling left to
`#0402`'s and `#0484`'s tests.

**Criterion 5 — no guard-for-the-guard.** The commit adds exactly one file and
nothing else: no shell harness, no meta-test watching this test, no in-file
self-check. `#0490`'s guard file has only its own commit in its history, so it
was not edited to fit this one.
