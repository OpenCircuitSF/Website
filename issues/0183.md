## Description

`#0179`/`#0180`'s review probed coverage **by mutation for every export**, rather than by checking which symbols the test files import. That found four survivors — mutations that change behavior and pass the suite. All four are one line each.

**1. `cancelConfirmMessage` is never tested with `undefined`, which is what the API actually sends.** `workshopView.PublishedAt` is `*string` with `omitempty`, so a NULL `published_at` reaches the SPA as an **absent key** — `undefined`, not `null`. The function is only ever exercised with `null`, so a mutation confined to its `undefined` handling passes **77/77**.

`cancelVisibilityOutcome` *is* tested with `undefined`, so the gap is only at the boundary — but this is the same "a state nobody enumerated" class the cancel dialog has now shipped three defects for (`#0171`, `#0174`, `#0177`), and the enumerated state here is *the one production actually produces*.

**2–4. Three pre-existing depth gaps in `sendConfirm.ts`**, each passing 41/41 when mutated:
- dropping U+2009 from `normalizeCountInput`'s separator class
- deleting its `Number.isSafeInteger` guard
- swapping `sendGuardState`'s `unmet` and `audienceCount === 0` branches — no existing case sets both, so the swap is invisible

These matter more than their size suggests: `sendGuardState` is `#0047`'s send gate, the mechanism `#0056`'s review leaned on when accepting the `all`-audience fallback as survivable.

## Root cause

Four one-line branches in `web/src/lib/sendConfirm.ts` and
`web/src/lib/workshopAdmin.ts` had no test that could distinguish correct
behavior from the corresponding mutation, per `#0179`/`#0180`'s mutation-sweep
review:

1. `cancelConfirmMessage` was exercised only with `null` for `published_at`,
   never `undefined` — the shape `workshopView.PublishedAt` (`*string`,
   `json:",omitempty"`, `internal/handlers/admin_workshops.go`) actually
   produces for a NULL `published_at`, since an absent key deserializes to
   `undefined` in the SPA, not `null`.
2. `sendGuardState`'s 11 test cases never set `unmet` non-empty **and**
   `audienceCount === 0` together, so the `blocked`-before-`empty-audience`
   branch order was unpinned — swapping the two branches passed the suite.
3. `normalizeCountInput`'s U+2009 thin-space separator (the doc comment's own
   promise) was untested — the existing `' 1234 '` case only exercises
   `.trim()`, not the character class.
4. `normalizeCountInput`'s `Number.isSafeInteger` guard was untested —
   nothing typed a count beyond `Number.MAX_SAFE_INTEGER`.

## Fix

Added one test case per gap, each proved by the mutation method the issue
asks for: apply the exact surviving mutation, run the suite, confirm only the
new case goes red, restore the source and re-check its md5 against the
`#0179`/`#0180` review baseline (`41330f9ecd290d0785aecbad83c0f10d` for
`sendConfirm.ts`, `7bb8b0b09bdc716f9d57617697d39511` for `workshopAdmin.ts`).

Per the fifth criterion, also swept every other export in `sendConfirm.ts` by
mutation (not by import list) rather than stopping at the four named gaps.
`confirmMatches`, `sendGuardDescription`, and `sendGuardSummaryClass` all held
under several probes (loosened equality, flipped ternary, `&&`→`||`). Two more
genuine survivors turned up and were closed the same way:

- `normalizeCountInput`'s digit-requirement regex (`/^\d+$/`) had no test for
  an input that strips down to an empty string without ever having been the
  empty string itself — e.g. a lone `','`. Loosening it to `/^\d*$/` (allowing
  an empty match) passed the full suite and silently turned a rejected input
  into `0`.
- `confirmHint`'s untouched-field check (`raw.trim() === ''`) had no test for
  a whitespace-only field distinct from the exact empty string. Narrowing it
  to `raw === ''` passed the full suite and turned "no scolding an empty
  field" into "no scolding an *exactly* empty field," scolding `'   '`
  instead.

No other export showed a reachable, un-asserted branch.
