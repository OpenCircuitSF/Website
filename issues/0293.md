## Description

The greenfield exception let `migrations/` be squashed, renumbered, or rewritten,
and told implementers to prefer editing the migration that owns a table over
stacking an `ALTER TABLE`. It was written on 2026-08-21 and it said, correctly,
that it would expire at the first deploy applying a migration to production.

**That deploy happened on 2026-08-25.** `www.opencircuitsf.com` now serves this
project, production's PostgreSQL holds a live `opencircuit` database at
`schema_migrations.version = 22`, and `#0272` is open about two specific real
`outbound_queue` rows in it.

**The notes did not expire with it.** Two days later they still read as active
instructions in at least:

| Where | What it still says |
|---|---|
| `PRD.md` §6.2's greenfield note | the exception, as current |
| `docs/deployment.md` (~line 337) | the exception ends at the first deploy — as a future event |
| `docs/deployment.md` (~line 449) | "this project is greenfield until the **first** production…" |
| `docs/deployment.md` (~line 452) | names the deploy as "the event that ends" it |
| `issues/0125.md` acceptance criterion 2 and its `## Notes` | instructs the `000010` edit directly |

`CLAUDE.md` §1 has already been corrected (2026-08-27) and now states the
exception expired, freezes `000001`–`000022`, and warns that issues filed before
2026-08-25 may still carry stale criteria. This issue is the rest of the sweep.

## Why this is urgent rather than tidy

**It has already cost a bounce.** `#0125` was filed on 2026-08-21 with an
acceptance criterion instructing an edit to `migrations/000010`. Its implementer
followed that criterion faithfully and correctly. Its review then built a scratch
database to production's version 22, ran `migrate up` against the committed
tree, and got:

```
23/u create_subscriber_imports
  (details: pq: column "import_id" referenced in foreign key constraint does not exist)
select version, dirty from schema_migrations  ->  23|t
```

A failed deploy leaving `schema_migrations` **dirty at 23** — plus every
subscriber query on the new binary erroring against a production `subscribers`
table lacking the five new columns.

The premise failed, not the execution. Any other pre-deploy issue whose criteria
name a migration edit will reproduce it exactly, and there is more than one.

## Root cause

The greenfield note was written, correctly, as a self-expiring exception —
but nothing made it self-correct on expiry. It lived as prose in four places
(`PRD.md` §6.2, three passages in `docs/deployment.md`, and inline in several
issue files' `## Notes`), and the deploy that ended it (2026-08-25) touched
none of them. Two days and one bounced review (`#0125`) later, the notes
still read as live instructions.

## Fix

1. `PRD.md` §6.2's greenfield blockquote: struck through verbatim, followed
   by a dated `**Correction (#0293, 2026-08-27).**` note stating migrations
   `000001`–`000022` are now append-only without qualification.
2. Because that grew §6.2 by 10 lines, recomputed (never by hand, per
   `#0113`) and corrected CLAUDE.md §11's `§6.2` row (335→345) and its parent
   `§6` row (942→952) in the same commit — both counted via
   `internal/db/prd_section_index_test.go`'s own `countPRDSection`
   convention, which is one less than a literal `sed -n '...' | wc -l`
   because it does not count the trailing next-heading terminator line the
   real `sed` invocation prints. Also corrected the §11 preamble's "`PRD.md`
   is N lines" sentence (1,829→1,839), guarded by
   `TestPRDSectionIndexTotalMatchesFile` — this one wasn't named in the
   issue's acceptance criteria but is gated by the same test file criterion 7
   points at, so it had to be fixed for the suite to pass.
3. `docs/deployment.md`'s three passages (~337, ~449, ~452) corrected to past

4. Swept every open issue: `grep -rn greenfield issues/` hit 21 files; of
   those, only 4 were `open` (the rest are `resolved`, left as historical

5. Settled criterion 5a in one sentence (see `## Gotchas`) and made `#0125`'s
   own annotation match it — restored its greenfield paragraph's exact
   original wording (recovered from commit `e762488`, since the committed
   text was a paraphrase, not the original) under a strikethrough, matching

6. No migration file changed.

## Gotchas

**Settled convention (criterion 5a), one sentence:** a paragraph superseded
by later events keeps its exact original wording, struck through inline,
immediately followed by a dated `**Correction (#NNNN, date).**` note — never
a paraphrase, and never silent deletion. Applied uniformly across `PRD.md`,
`docs/deployment.md`, `issues/0123.md`, `issues/0129.md`, and (fixing the
pre-existing paraphrase) `issues/0125.md`.

The §11 table numbers are **not** what `sed -n '<pattern>' PRD.md | wc -l`
reports directly — they are one less, because
`internal/db/prd_section_index_test.go`'s `countPRDSection` does not count
the trailing next-heading line that a real `sed` range print includes. This
cost one failed run before catching it; recomputing "from the row's own
command" (per criterion 2) means running the guard, not just piping through
`wc -l` by hand.

Did not touch `docs/deployment.md:441`'s "This repo currently ships
migrations `000001`–`000020`" — it's stale (production and the repo are both
past `000022`) but it's a plain migration-count drift, not a greenfield
instruction, and wasn't one of the issue's three named passages. Reporting
it rather than fixing it, to stay in scope.
