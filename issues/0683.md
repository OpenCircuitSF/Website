## Description

This is a follow-up from `#0674`'s review. The per-token limiter applies only after authentication. A request with a bad bearer token costs one database lookup and is never limited. Guessing a 256-bit key is not feasible, so this is a load concern, not an access concern.

Once write routes and `/mcp` exist (`#0675`, `#0679`), put a per-IP limiter on failed authentication there. Use the existing IP limiter with its unchanged body. Behind Apache, the client IP comes from `X-Forwarded-For`, which the existing limiters already handle.

## Plan

The plan pass was folded into the implementation pass, at the user's "keep moving" direction. This plan was written before any code. Batched with `#0682` and `#0686`.

- **`internal/middleware/apiauthfail.go`.**
  - `APIAuthFailuresPerMinute = 10`.
  - `NewAPIAuthFailureLimiter()` builds the existing `RateLimiter` with that rate, and a burst of the same size.
  - `APIAuthFailureLimit(rl)` wraps `RequireAPIToken` from the outside. It buckets by `"authfail:" + ClientIP(r)`, the same X-Forwarded-For rule as every IP limiter.
    - First it peeks at the bucket with `rate.Limiter.TokensAt`. If the bucket is empty, the request gets 429 with `Retry-After` and `Cache-Control: no-store` before the inner handler runs, so there is no token lookup.
    - Otherwise it serves the request through a status-recording writer. Only a 401 on a request carrying a token-shaped bearer spends a token, and that is exactly a lookup that found nothing.
    - A nil limiter passes requests through.
- **The body.** The 429 is the v1 envelope `{"error":{"code":"rate_limited",…}}`, like `APITokenRateLimit`'s. `RateLimiter.Middleware`'s `{"error":"rate_limit_exceeded"}` body, used by signup and login, is unchanged and is not used here. Every response on `/api/v1` and `/mcp` is the envelope.
- **Wiring.**
  - `api.RouterDeps` and `mcpserver.Deps` each gain an optional `AuthFailLimiter`.
  - `NewHTTPRouter` puts the limit outside `RequireAPIToken` on each operation route. The public OpenAPI document and the JSON 404/405 are not limited.
  - `mcpserver.NewHandler` puts it outermost.
  - `main.go` builds one instance and passes it to both, so an IP has one budget across REST and MCP. It is a struct-field edit only, so `TestAPIV1AndMCPMountedOnlyViaRegistry`'s mount shape is unchanged.
  - The per-token limiter is unchanged.
- **Tests.**
  - Middleware: refuse after the budget with no lookup (resolver call count), the envelope, `Retry-After` and no-store; successes and 403s don't count; a missing or malformed header doesn't count; buckets follow `ClientIP` (a spoofed leftmost XFF entry doesn't buy a new bucket, and another client is unaffected); nil passes through; the budget constant.
  - Real mux (`admin_wiring_test.go`), for both `/api/v1/token` and `POST /mcp`: at least 10 401s and then a 429 `rate_limited`; a valid key from the throttled IP gets 429; the same key from another IP gets 200; and an IP throttled on `/api/v1` is also throttled on `/mcp`, since the bucket is shared.
- **Verification tier.** Scoped middleware, api, mcpserver, cmd/opencircuit and handlers (Go comments changed), then the batch's full run. A mutation unwires the limiter from the v1 router.

## Obstacles

- **The existing real-mux test sends about 80 401s from 127.0.0.1**: every operation with no key and with a cookie. Counting every 401 would have broken it.
- This led to counting only token-shaped bearers. Those 401s cost no lookup, so they are not the load this issue is about.
- The new wiring cases use `X-Forwarded-For` documentation addresses (`192.0.2.x`) from the loopback peer. That leaves the loopback bucket the rest of the test uses untouched.

### Assumptions

- **The budget is 10 failed lookups per minute per IP, with a burst of 10.** A Home Assistant install polling with a mistyped key every 30 seconds never reaches it. It does see its 401s first, which say what is wrong.
- **Once an IP is over the limit, every request from it gets 429, even one with a good key.** That is what "before any DB lookup" requires. The refill is one request every 6 seconds.
- **A missing or malformed `Authorization` header is not counted**, because it costs nothing (see Obstacles). It is still refused with 429 while the IP is over the limit.
- **Concurrent bad requests from one IP can overshoot the budget by the number in flight**, because the peek and the spend are separate steps. That is harmless for a load limit.
- **Limiter entries are never evicted**, as with every `RateLimiter` (`issues/0020.md`).

## Review notes

Reviewed 2026-11-16 (opus · medium) on `main` after the merge. Batch review with `#0682` and `#0686`.

- **No bypass by header spoofing.** The bucket key is `ClientIP`. It trusts `X-Forwarded-For` only from a loopback peer, which in production is only Apache, and then it takes the **rightmost** entry, the hop Apache appended. A client cannot choose its bucket by sending its own `X-Forwarded-For`, because Apache appends to it. A direct non-loopback peer's header is ignored. `TestAPIAuthFailureLimit_BucketsByClientIP` pins the leftmost-entry case.
- **Order and sharing.** The peek (`TokensAt`) runs before the inner handler, so a throttled IP never reaches `RequireAPIToken`'s lookup. A token is spent only after a 401 on a token-shaped bearer. The two in-handler 401s in `internal/api` and `internal/mcpserver` happen only when no token is in the context, which cannot happen after `RequireAPIToken` succeeds. `verifyFromContext` fails only in that same case. So a valid key never spends from the bucket. `main.go` builds one limiter and passes it to both routers. My live run showed the shared bucket too: 10 × 401, then 429 with `Retry-After: 6`, then 429 for a good key from the same IP.
- **A legitimate key holder on a shared IP can be locked out. Accepted.** Anyone behind the same NAT, such as the workshop venue's Wi-Fi or the home network Home Assistant uses, can keep the IP over budget with 10 bad keys a minute. Every request from that IP then gets 429, including a good key. That is a denial of service, not access. It needs someone on the same network, and it ends within a minute of them stopping. Home Assistant with a mistyped key polls about twice a minute, well under the refill rate of 10 a minute, so it never locks itself out. The alternative is to let a good key through while the IP is over the limit. That would need the lookup this limit exists to avoid, so I kept the design. `docs/api.md` documents the good-key behaviour.
- **Mutation.** I removed the limiter from the `/mcp` wiring in a throwaway worktree at `7d96f699`. `TestMountAndServe_AdminRoutesRequireSessionAndAdmin` failed three ways: `/mcp` took 30 401s with no 429, a valid key from the throttled IP got 200, and the IP throttled on `/api/v1` got 401 on `/mcp`. The implementer's mutation covered the `/api/v1` side.
- No defects found.
