## Description

> ✅ **Resolved 2026-08-22** (`b619eba`, `f143032`) — verified independently by
> the phase-3 reviewer across two passes. Option (a) stands: slugs are
> server-generated and immutable through both `POST /admin/workshops` and
> `PATCH /admin/workshops/{id}`, a body carrying a `"slug"` key is rejected
> with `400`, `#0052`'s conflicting criterion is struck, and every comment in
> the tree that described the old, false "silently ignored" behavior now
> describes the real one. See `## Review notes` (pass 1) and
> `## Review notes (pass 2)`.

`#0052`'s acceptance criteria require the admin UI to let a slug be edited before a workshop is first published. `#0051`'s API makes that impossible: neither the create nor the patch request struct carries a `slug` field, and the store generates it server-side from the title with a collision suffix. `#0052`'s reviewer verified both — no `slug` on either struct, no route that accepts one — and ruled the criterion unbuildable in the UI, leaving it unticked.

So one of the two is wrong, and this issue decides which.

## Root cause — a decision, not a bug

Not a bug to diagnose: `#0052` and `#0051` genuinely disagreed about whether a
slug should be editable, and `#0051` shipped first, so the API's contract
(immutable, server-generated) is what actually exists. This issue settles the
disagreement in the API's favor.

**Decision: option (a).** Slugs stay server-generated and immutable through
both `POST /admin/workshops` and `PATCH /admin/workshops/{id}`. Reasoning,
carried forward from the orchestrator's brief and confirmed against the code
rather than re-litigated:

- `#0052`'s own `## Notes` already argue for this: a stable, server-generated
  slug is one less thing an admin can get wrong, and the collision-suffix
  retry in `internal/workshops/store.go`'s `Create` already guarantees
  uniqueness without any client input.
- `#0144`/`#0145`'s review established that `internal/workshops` `slugify`
  is an ASCII allowlist with exactly **one** write path — `Create`'s
  `INSERT`; `Update` deliberately sets eleven columns and never `slug`. That
  single-write-path guarantee is *why* `#0145` could safely interpolate a
  slug into a URL without re-validating it at read time. Making slugs
  client-supplied would reopen a second write path and pull `#0138`'s
  "a value reaches a URL unvalidated" class of defect back into scope.
- **Accepted cost, not a surprise:** a title typo caught after publish leaves
  a permanently wrong slug, since editing the title does not regenerate it.
  Proved by execution below — PATCHing only `title` leaves `stored.slug`
  byte-identical to what `Create` generated.

## Fix

This is bookkeeping, not a code change to behavior — the API already refused
a client-supplied slug and the UI already showed it read-only. What changed:

- **`#0052`'s slug criterion struck** with a note pointing here (commit
  `b619eba`, in `issues/0052.md`).
- **Confirmed the UI already matches the decision.** `WorkshopEditor.svelte`
  never renders the slug as an `<input>` — it's a plain `<p class="slug-value
  mono">{workshop.slug}</p>`, so there's no "disabled" state to mislabel. The
  hint text underneath it already reads "Auto-generated from the title and
  set once at creation -- the server does not accept edits to it through this
  screen," which correctly frames it as *generated*, not merely *disabled*.
  No UI code change was needed.
- **Found and fixed a real documentation bug while confirming the API's
  refusal.** `admin_workshops.go`'s `Create` doc comment claimed an unknown
  `"slug"` key in the request body is "simply ignored ... recognized-but-
  unsettable, intentionally not rejected." That claim is **false**, proved by
  execution (see `## Verification`): `createWorkshopRequest` has no `Slug`
  field at all, so `decodeJSON`'s `DisallowUnknownFields` rejects any request
  carrying an unknown `"slug"` key with `400 {"error":"invalid request
  body"}` — the same treatment every other unrecognized field gets elsewhere
  in this package. The same is true of `patchWorkshopRequest`. This is
  actually the *stronger* of the two options the issue asked me to weigh
  (genuinely refuses vs. silently drops) — no code behavior needed to change,
  only the comment, which now describes the real, verified behavior and
  explains why it's the intended one. No production caller is affected: the
  admin UI never includes a `"slug"` key in a create or patch payload (`grep
  slug web/src/lib/api.ts web/src/lib/workshopAdmin.ts` — the only wire-side
  `slug` field is the read-only value in the *response* type, never in a
  request-shape type).
- **Updated the two "flagged for the reviewer" header comments** in
  `web/src/lib/workshopAdmin.ts` and `WorkshopEditor.svelte` that presented
  the slug question as still open, so a future reader doesn't reopen a
  decided question. `isSlugEditable()`'s behavior (`return false`) is
  unchanged — only its doc comment now says "by design (#0137)" instead of
  "today."

consistent.** There is exactly one `DisallowUnknownFields` call site in the

  wrong.

  once in the tree, as `Optional[int]` (`admin_workshops.go:376`), and a
  scalar has no fields to leave unknown. It is a latent hole if anyone ever
  writes `Optional[SomeStruct]` — reported to the orchestrator as a possible
  follow-up, not filed here and not blocking this issue.

— "rejected with 400 (DisallowUnknownFields) rather than silently accepted or
silently ignored"), which is independent corroboration that rejection, not
dropping, is the house contract.
