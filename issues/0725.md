## Description

Second-batch Raspberry Pi guides. **Read `#0723`'s description first**: it carries the shared rules (no new set, `demoLoaders.ts`, `PROMPTS.md` sections, counts, links inside demos, the pattern in `#0719`–`#0721`).

Guides in this issue:

- `pi-wifi-dropouts` — a Pi that joins WiFi and then drops off. Band support is `pi-wifi-2-4ghz`'s job; this covers a network the Pi *can* see: WiFi power saving (check with `iw wlan0 get power_save`; turn it off with NetworkManager, `nmcli connection modify <name> 802-11-wireless.powersave 2`), weak signal (the Zero's small antenna, metal cases), the address changing (use `hostname.local` or a DHCP reservation; link `pi-find-on-network`), under-voltage (link `pi-undervoltage`), and router band steering. Demo: a diagnosis flow, as in `esp32-c3-wont-upload`: answer a few questions and get the likely cause and fix.
- `pi-run-on-boot` — start a program on boot with a systemd service and restart it when it crashes: a unit file (`[Unit]` Description, `After=`/`Wants=network-online.target`; `[Service]` `ExecStart` with an absolute path, `WorkingDirectory`, `User`, `Restart=on-failure`, `RestartSec`; `[Install]` `WantedBy=multi-user.target`), `sudo systemctl enable --now`, `systemctl status`, `journalctl -u <name> -f`; why not `rc.local` or `cron @reboot`. Demo: build the service file one line at a time; turn a line off and see the failure it causes (relative path → not found; no `Restart` → stays dead after a crash; no network wait → fails on boot; no `[Install]` → doesn't start at boot).
- `pi-backup-sd-card` — copy the whole SD card before changing anything: on a Mac with `diskutil list` and `sudo dd if=/dev/rdiskN of=pi.img bs=4m` (then compress), on Linux with `lsblk` and `dd`, on the Pi desktop with SD Card Copier; restore with Raspberry Pi Imager's "Use custom". The danger is choosing the wrong disk or swapping `if` and `of`. Demo: a disk list with the SD card and the laptop's own disk; build the `dd` command by picking source and destination, and see a clear warning when it would overwrite the wrong disk. Never present a command that writes to a disk without a bold warning.

#### 1. WiFi dropouts: a yes/no tree (copy `codeOnBoard.ts`' shape)

```ts

  supply: 'Power supply', pi: 'Pi’s WiFi chip', air: 'Signal', router: 'Router',
```

Steps (a straight chain; each Yes ends at a fix):

| id | question | spot | yes | no |
|---|---|---|---|---|
| `start` | `Does vcgencmd get_throttled print anything other than throttled=0x0?` | supply | `fix-power` | `powersave` |
| `powersave` | `Does iw wlan0 get power_save say Power save: on?` | pi | `fix-powersave` | `address` |
| `address` | `When it drops, is the Pi still on the router’s client list, maybe at a new address?` | router | `fix-address` | `signal` |
| `signal` | `Does iw dev wlan0 link show a signal weaker than −70 dBm?` | air | `fix-signal` | `steering` |
| `steering` | `Does the router use one network name for both 2.4 and 5 GHz?` | router | `fix-steering` | `fix-log` |

Details (polish freely, keep the facts):
- `start`: "Run it over SSH while the Pi is reachable. An under-voltage flag (0x50005, 0x50000 and friends) means the supply sags when the Pi gets busy, and WiFi is one of the first things to go. Not sure what the value means? Decode it in the under-voltage guide."
- `powersave`: "WiFi power saving lets the WiFi chip doze between packets. A Pi that only listens, for SSH or a web page, can stop answering for seconds at a time or drop off."
- `address`: "Look in the router’s list of connected devices. If the Pi is there under a different IP address than the one you were using, it never left: its address changed."
- `signal`: "Run it on the Pi and read the signal line. Closer to zero is stronger: −50 dBm is good, −70 dBm is weak, −80 dBm is barely there. The Zero 2W’s antenna is tiny, and a metal case blocks most of the signal."
- `steering`: "Called band steering or smart connect. The router decides which band each device uses and can move it between them; every move is a short drop."

Fixes (titles exact; bodies may be polished):

| id | title | spot | commands | links |
|---|---|---|---|---|
| `fix-power` | `Fix the power first` | supply | `vcgencmd get_throttled` | `/guides/pi-undervoltage` "Why a Pi slows down: under-voltage" |
| `fix-powersave` | `Turn off WiFi power saving` | pi | `nmcli connection show`, `sudo nmcli connection modify preconfigured 802-11-wireless.powersave 2`, `sudo reboot`, `iw wlan0 get power_save` | — |
| `fix-address` | `Use its name, or reserve its address` | router | `ping mypi.local`, `hostname -I` | `/guides/pi-find-on-network` "Where’s my Pi? Finding it on the network" |
| `fix-signal` | `Get a stronger signal` | air | `iw dev wlan0 link` | — |
| `fix-steering` | `Give the Pi its own 2.4 GHz network` | router | `iw dev wlan0 link` | `/guides/pi-wifi-2-4ghz` "2.4 GHz vs 5 GHz" |
| `fix-log` | `Catch it in the log` | pi | `journalctl -u NetworkManager -b`, `sudo dmesg \| grep -i brcmf` | — |

Bodies:
- `fix-power`: "WiFi drops out when the supply can’t hold the voltage up. Use the official supply or a short, thick cable and check get_throttled again. If the value only shows temperature flags, cool the Pi, then start over and answer No here."
- `fix-powersave`: "Find the connection’s name with nmcli connection show (Raspberry Pi Imager names it preconfigured). Setting 802-11-wireless.powersave to 2 turns power saving off for that connection, and it stays off after a reboot. Check afterwards: iw should say Power save: off."
- `fix-address`: "The router gave the Pi a new address. Connect by name instead, mypi.local (your hostname plus .local), or reserve an address for the Pi in the router’s DHCP settings so it always gets the same one."
- `fix-signal`: "Move the Pi or the router, take the Pi out of a metal case, or add an access point nearer the Pi. 2.4 GHz reaches further through walls than 5 GHz."
- `fix-steering`: "Many routers can give the 2.4 GHz band its own network name. Connect the Pi to that one, so the router can’t move it between bands."
- `fix-log`: "None of the usual causes. Leave the log open when it drops: NetworkManager says when it lost the connection and why, and brcmf lines come from the WiFi chip’s driver."

#### 2. Run on boot: a systemd unit built from toggles

```ts
export type UnitToggle = 'fullPath' | 'workdir' | 'user' | 'network' | 'restart' | 'restartSec' | 'install';
export type UnitOptions = Record<UnitToggle, boolean>;
export const ALL_ON: UnitOptions;   // every toggle true
export const UNIT_TOGGLES: { id: UnitToggle; label: string; what: string }[] = [
  { id: 'fullPath',   label: 'Full paths in ExecStart', what: 'Starts the right program no matter which folder it starts in.' },
  { id: 'workdir',    label: 'WorkingDirectory=',       what: 'The folder the program starts in.' },
  { id: 'user',       label: 'User=',                   what: 'Runs as your user, not root.' },
  { id: 'network',    label: 'Wait for the network (After= and Wants=)', what: 'Starts after the network is up.' },
  { id: 'restart',    label: 'Restart=on-failure',      what: 'Starts it again when it crashes.' },
  { id: 'restartSec', label: 'RestartSec=5',            what: 'Waits 5 s before restarting.' },
  { id: 'install',    label: '[Install] WantedBy=multi-user.target', what: 'Lets systemctl enable start it at boot.' },

```

`unitLines` returns, in order (an off line is written as a comment, `# ` + its text, so the shown file is always a valid unit file; the `fullPath` toggle changes its line instead):

(blank lines are `{ text: '', toggle: null, on: true }`).

Precedence, first match wins. `brokenPath = !fullPath && !workdir` (a relative script with no WorkingDirectory starts in `/`, so python3 is found on the search path but `log.py` is not).

Boot scenario:
1. `!install` → `noInstall`, bad, `Doesn’t start at boot`. Body: "Without an [Install] section, systemctl enable has nothing to hook into. It says so, and at boot nothing starts the service. It still runs if you start it by hand." status `Active: inactive (dead)`; log `['$ sudo systemctl enable plantlog', 'The unit files have no installation config (WantedBy=, RequiredBy=, …)']`; events `[{0,'Power on',plain},{30,'WiFi up',plain},{100,'plantlog never starts',bad}]`.
2. `brokenPath` → `badPath`, bad, `Starts, then can’t find its file`. Body: "With no WorkingDirectory the program starts in /, so python3 looks for /log.py. Use full paths: they work wherever it starts." + (restart on: " Restart=on-failure just repeats the failure every few seconds." / off: " It fails once and stays dead."). status restart on `Active: activating (auto-restart) (Result: exit-code)`, off `Active: failed (Result: exit-code)`; log `["python3: can't open file '/log.py': [Errno 2] No such file or directory", 'plantlog.service: Main process exited, code=exited, status=2']`; events `[{0,'Power on'},{35,'plantlog starts'},{37,'can’t find log.py',bad}]` (+ `{60,'tries again',bad}` when restart on).
3. `!network && restart` → `netRetry`, meh, `Fails once at boot, then the restart fixes it`. Body: "It started before the WiFi was up and couldn’t reach the server. Restart= saved it this time; waiting for network-online.target fixes the cause." status `Active: active (running)`; log `['plantlog.service: Main process exited, code=exited, status=1/FAILURE', 'plantlog.service: Scheduled restart job', 'Started plantlog.service - Plant logger.']`; events `[{0,'Power on'},{10,'plantlog starts'},{14,'no network yet',bad},{30,'WiFi up'},{40,'restarted: running',good}]`.
4. `!network` (restart off) → `netDead`, bad, `Fails at boot and stays dead`. Body: "It started before the WiFi was up, failed, and nothing started it again." status `Active: failed (Result: exit-code)`; log `['Temporary failure in name resolution', 'plantlog.service: Failed with result \'exit-code\'.']`; events `[{0,'Power on'},{10,'plantlog starts'},{14,'no network yet: dead',bad},{30,'WiFi up'}]`.
5. `!user` → `root`, meh, `Running, but as root`. Body: "It works, but as root: any file it writes belongs to root, and a bug in it can change anything on the card. Add User= with your own user name." status `Active: active (running)`; events as `running`.
6. else → `running`, good, `Running`. Body: "It waits for the network, starts as your user, and comes back if it crashes." status `Active: active (running)`; log `['Started plantlog.service - Plant logger.']`; events `[{0,'Power on'},{30,'WiFi up'},{35,'plantlog starts',good},{100,'running',good}]`.

Crash scenario (it was running; it crashes at `at: 40`):
1. `brokenPath` → `badPath` (same as above: it never ran).
2. `!restart` → `crashDead`, bad, `Crashed and stays dead`. Body: "Restart= defaults to no: when the program dies, systemd leaves it dead until someone notices." status `Active: failed (Result: exit-code)`; log `['Traceback (most recent call last):', 'plantlog.service: Main process exited, code=exited, status=1/FAILURE']`; events `[{0,'running',good},{40,'crash',bad},{100,'still dead',bad}]`.
3. `!restartSec` → `crashFast`, meh, `Restarted at once`. Body: "Without RestartSec, systemd restarts it after a tenth of a second. If it crashes straight away again, systemd soon gives up and marks it failed. A few seconds’ wait gives a flaky network or sensor time to recover." status `Active: active (running)`; events `[{0,'running',good},{40,'crash',bad},{41,'restart',meh},{100,'running',good}]`.
4. else → `crashOk`, good, `Crashed, back 5 s later`. Body: "systemd saw it exit with an error, waited 5 s and started it again. journalctl shows the crash, so you can still fix the bug." status `Active: active (running)`; log `['plantlog.service: Main process exited, code=exited, status=1/FAILURE', 'plantlog.service: Scheduled restart job, restart counter is at 1.']`; events `[{0,'running',good},{40,'crash',bad},{50,'restarted 5 s later',good},{100,'running',good}]`.

(`network`, `user` and `install` don't change the crash scenario.) Events with no tone given are `plain`. Log strings are a simplified journal: no timestamps, and say so in the demo note.

#### 3. Back up the SD card: build `dd` and guard the wrong disk

```ts
export type HostOs = 'mac' | 'linux';
export const HOSTS = [{ id: 'mac', label: 'Mac' }, { id: 'linux', label: 'Linux' }];
export type DiskKind = 'internal' | 'usb' | 'sdcard';
export interface Disk { id: string; dev: string; rawDev: string; size: string; kind: DiskKind; label: string }
export const DISKS: Record<HostOs, Disk[]> = {
  mac: [
    { id: 'disk0', dev: '/dev/disk0', rawDev: '/dev/rdisk0', size: '500.3 GB', kind: 'internal', label: 'internal: this Mac’s own disk' },
    { id: 'disk4', dev: '/dev/disk4', rawDev: '/dev/rdisk4', size: '31.9 GB',  kind: 'sdcard',   label: 'external: the Pi’s SD card, in a card reader' },
    { id: 'disk6', dev: '/dev/disk6', rawDev: '/dev/rdisk6', size: '1.0 TB',   kind: 'usb',      label: 'external: your USB backup drive' },
  ],
  linux: [
    { id: 'nvme0n1', dev: '/dev/nvme0n1', rawDev: '/dev/nvme0n1', size: '476.9G', kind: 'internal', label: 'this laptop’s own disk' },
    { id: 'sda',     dev: '/dev/sda',     rawDev: '/dev/sda',     size: '931.5G', kind: 'usb',      label: 'your USB backup drive' },
    { id: 'sdb',     dev: '/dev/sdb',     rawDev: '/dev/sdb',     size: '29.7G',  kind: 'sdcard',   label: 'the Pi’s SD card, in a USB card reader' },
  ],
};
export const IMAGE = 'pi.img';
export type EndId = string;           // a disk id, or 'file' for pi.img
export function endLabel(os: HostOs, id: EndId): string;   // 'pi.img (a file on this computer)' or `${dev} (${size}, ${label})`
export type DdVerdict = 'backup' | 'restore' | 'same' | 'eraseOwnDisk' | 'eraseOtherDrive' | 'diskOverCard' | 'notTheCard';
export interface DdPlan {
  verdict: DdVerdict; tone: 'good' | 'meh' | 'bad'; title: string; body: string;
  writesDisk: boolean;           // of= is a disk
  command: string | null;        // null whenever the plan is refused
  warning: { strong: string; rest: string } | null;   // never null when command is not null
  before: string[]; after: string[];   // copyable commands around the dd line; empty when refused
}
export function ddPlan(os: HostOs, src: EndId, dst: EndId): DdPlan;
export function ddCommand(os: HostOs, src: EndId, dst: EndId): string;   // the raw line, used by ddPlan only after the guards pass
export function isRefused(p: DdPlan): boolean;   // p.command === null
```

`ddCommand`: Mac `sudo dd if=<in> of=<out> bs=4m status=progress` using `rawDev` for disks; Linux `sudo dd if=<in> of=<out> bs=4M status=progress conv=fsync` using `dev`. The file is `pi.img`.

`ddPlan` rules, first match wins (titles exact):

1. `src === dst` → `same`, meh, `Source and destination are the same`, "Pick the SD card as one end and pi.img as the other." No command.
2. dst is a disk of kind `internal` → `eraseOwnDisk`, bad, `Stop: that’s your computer’s own disk`, body "dd doesn’t add a file to a disk, it overwrites the whole disk from the first byte. This would erase <dev>, the disk your computer runs from." No command.
3. dst is a disk of kind `usb` → `eraseOtherDrive`, bad, `Stop: that would erase your backup drive`, body "dd writes the raw disk, not a file on it: everything on <dev> would be gone. To keep the image on that drive, pick pi.img and run the command from a folder on the drive." No command.
4. dst is the SD card and src is a disk → `diskOverCard`, bad, `Stop: that copies a whole disk over the card`, body "Only an image file goes onto the card. This would overwrite the card with <src dev>." No command.
5. dst is `file` and src is a disk that isn’t the card → `notTheCard`, meh, `That’s not the SD card`, body "This copies <src dev> (<size>) into a file, not the Pi’s card. Find the card by its size: <card size>." No command.
6. src is the card, dst `file` → `backup`, good, `Backup: card → pi.img`, body "dd reads every byte of the card into pi.img: the same size as the card, empty space included. Compress it afterwards." `writesDisk: false`; warning `{ strong: 'Check the disk number twice.', rest: 'Reading the card is safe. Swap if= and of= and the same command erases it.' }`; before Mac `['diskutil list', 'diskutil unmountDisk /dev/disk4']`, Linux `['lsblk', 'sudo umount /dev/sdb1 /dev/sdb2']`; after `['gzip pi.img']` (Mac adds `'diskutil eject /dev/disk4'`).
7. src `file`, dst the card → `restore`, meh, `Restore: pi.img → card (erases the card)`, body "This works, but Raspberry Pi Imager’s Use custom does the same and lists only removable drives. Imager also reads pi.img.gz without unzipping." `writesDisk: true`; warning `{ strong: 'This erases everything on <dev> (<size>).', rest: 'Run diskutil list (lsblk on Linux) again right before, and check the size is the card’s.' }`; before as backup; after Mac `['diskutil eject /dev/disk4']`, Linux `['sync']`.

Device names in `before`/`after`/bodies come from the card disk of the chosen OS, not literals in the function (use `DISKS[os].find(d => d.kind === 'sdcard')`).

**The wrong-disk guard is the invariant, tested over every combination:** for both OSes and every (src, dst) pair from the disk ids plus `'file'`: `command !== null` ⇒ `warning !== null`; a non-null command never contains `of=` + the `dev` or `rawDev` of an `internal` or `usb` disk; `writesDisk` ⇒ the command’s `of=` is the card’s device; every refused plan has empty `before`/`after`.

Also export the Pi-desktop route as text: `COPIER_NOTE = 'On the Pi’s desktop: Accessories → SD Card Copier copies the running card to a second card in a USB reader.'`

### `TOPIC_BODIES` (plain text; commands in prose are fine, no links)

`pi-wifi-dropouts` — tryIt: "Answer the questions in order. Each one is a command or a look at the router, and each Yes ends at the likely cause and its fix." Ideas:
1. **Rule out the power first** — WiFi is one of the first things to fail when the supply sags. vcgencmd get_throttled prints 0x0 when the power has been fine since boot; anything with an under-voltage flag means fix the supply before anything else.
2. **Power saving makes a quiet Pi go deaf** — the WiFi chip can doze between packets. A Pi that mostly waits for SSH or a web page can stop answering. Check with iw wlan0 get power_save; turn it off for the connection with nmcli connection modify (connection name) 802-11-wireless.powersave 2. The value 2 means off, and it survives a reboot.
3. **Sometimes it never left** — the router may give it a new address, so the old one stops answering. Use the name, mypi.local, or reserve its address in the router. Weak signal (the Zero 2W’s small antenna, a metal case) and routers that move devices between 2.4 and 5 GHz under one network name cause real drops; a separate 2.4 GHz name fixes the second.
Takeaway: "Check get_throttled, then power saving, then the address. Most dropouts are one of those three."

`pi-run-on-boot` — tryIt: "All seven lines start on and the service works. Turn one off, pick whether the Pi boots or the program crashes, and see what systemd does." Ideas:
1. **A service file is a short recipe** — it lives in /etc/systemd/system/, named after the service. [Unit] says what it is and what to wait for; [Service] says what to run, where, as whom, and what to do when it stops; [Install] says when to start it. Then sudo systemctl daemon-reload and sudo systemctl enable --now (name).
2. **The lines that matter** — full paths in ExecStart, because a service doesn’t start in your home folder. After= and Wants=network-online.target together, so it waits for the network. Restart=on-failure with a RestartSec of a few seconds, because Restart is off by default. WantedBy=multi-user.target, or enable has nothing to hook into.
3. **Why not rc.local or cron @reboot** — both start a program once and forget it: no restart after a crash, no waiting for the network, and output that goes nowhere. A service gets all three, and systemctl status and journalctl -u (name) -f show what it’s doing.
Takeaway: "Full paths, wait for the network, Restart=on-failure, and an [Install] section. Then enable it."

`pi-backup-sd-card` — tryIt: "Pick your computer, then the source and the destination. Copy the card to pi.img and see the command; pick your own disk as the destination and see why dd won’t be shown." Ideas:
1. **Copy the whole card, not just your files** — an image of the card brings back the system exactly as it was: settings, installed programs, your project. Take one when it works, before an upgrade or a big change.
2. **dd copies whatever you point it at** — find the card by its size with diskutil list on a Mac or lsblk on Linux, unmount it, then dd if= the card of= pi.img. if is the input, of is the output. Swap them, or pick the wrong disk number, and dd overwrites that disk without asking. On a Mac, the rdisk name reads much faster than disk. Compress the image with gzip afterwards: it is as big as the card.
3. **Other ways in and out** — on the Pi’s desktop, SD Card Copier copies the running card to a second card in a USB reader. To restore, Raspberry Pi Imager’s Use custom writes pi.img or pi.img.gz to a new card, and lists only removable drives.
Takeaway: "Image the card before you change anything. Check the disk number twice, and restore with Imager’s Use custom."
