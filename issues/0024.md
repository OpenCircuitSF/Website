## Root cause

Not a bug fix — a new feature. `#0023` had already built the `interests` data
table (seeded taxonomy, slug/name/sort_order/active columns, `Deactivate`)
but left no admin-facing way to reach it: no HTTP surface, no UI, and no
hard-delete path at all (deliberately, per `#0023`'s doc comment). PRD §6.1's
whole point — "adding [a workshop theme] must not require a deploy" — was
unreachable without this issue.

## Fix

**Store (`internal/interests/store.go`):** added `GetByID` (read a single row
by id, used by the handler to merge a partial PATCH), `SubscriberCounts`
(one `GROUP BY interest_id` query over `subscriber_interests`, returning a
map keyed by interest id — interests with zero subscribers are simply
absent from the map), and `Delete`. `Delete` is deliberately narrow: a
single atomic `DELETE ... WHERE id = $1 AND NOT EXISTS (SELECT 1 FROM
subscriber_interests WHERE interest_id = $1)` either removes the row or
affects zero rows, and a follow-up existence check turns "zero rows
affected" into `ErrNotFound` or `ErrHasSubscribers` for the caller. This
does not weaken `#0023`'s "no hard-delete" design — an interest any
subscriber has ever selected can still only be hidden via `Deactivate`;
`Delete` only covers the case `Deactivate` doesn't (an interest created in
error that nobody has picked yet).

**Handler (`internal/handlers/interests.go`, new):** `AdminInterestsHandler`
serves `GET/POST/PATCH/DELETE /admin/interests[/{id}]`, all mounted behind
`RequireSession` then `RequireAdmin` in `main.go`, matching
`AdminUsersHandler`/`SettingsHandler`'s established pattern exactly
(interface-typed store dependency, `audit.Logger` fire-and-forget via
`Record`, a `now`-free handler since nothing here needs a fake clock).
`PATCH` loads the current row, merges only the JSON fields present onto it,
and calls `Update` with the full merged value (the store's `Update` takes
every field, not a partial patch). Flipping `active` writes
`interest.deactivated` or `interest.reactivated` instead of a generic
`interest.updated`, mirroring `account.deactivated`/`reactivated`.

**Routing (`cmd/opencircuit/main.go`):** constructed `AdminInterestsHandler`
reusing the `interestsStore` already built for `#0026`'s subscribe handler
(same pool, stateless wrapper — safe to share), registered the four routes
behind `requireAdmin`, and threaded a new `adminInterestsH` parameter
through `mountAndServe`. That parameter is nil in `serveDevMode`
(`STORAGE=json` has no interests-table backing, the same gap `subscribeH`
already has) and the routes are only registered when non-nil, so dev mode
keeps booting unaffected. Three other test files call `mountAndServe`
directly (`admin_wiring_test.go`, `ratelimit_wiring_test.go`,
`subscribe_wiring_test.go`) and needed a mechanical, behavior-preserving
update to their call sites to keep compiling — see `## Gotchas`.

**Frontend:** `web/src/lib/types.ts`/`api.ts` got the `Interest` type and
the four client calls; `web/src/lib/admin.ts` got `isValidInterestSlug`,
`validateNewInterest`, `sortedInterests`, `reorderSwap`, and
`hasSubscribers` as pure, DOM-free helpers; `web/src/views/Admin.svelte`
got a fourth "Interests" tab (create form, a table with ↑/↓ reorder + Edit +
Delete per row, an edit modal) following the file's existing Settings/
Users/Audit patterns rather than inventing new ones.

**`04208af` (this pass, review bounce #1 — Finding 1):** `4fc52ed`'s
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` issued only `GET`
requests, so a `requireAdmin` dropped from `POST`, `PATCH`, or `DELETE
/admin/interests` — including the destructive `DELETE` — shipped with a
green suite; only `GET` had a real-mux proof. Two changes close that gap:

- `cmd/opencircuit/main.go` now builds an `adminRoute{method, path,
  handler}` table via a new `adminRoutes(settingsH, adminUsersH,
  adminAuditH, adminInterestsH)` function — the single source of truth for
  every admin-only route `mountAndServe` registers (settings, users, audit,
  interests, all eleven `{method, path}` pairs across all four HTTP verbs
  the admin surface uses). `mountAndServe` now registers routes with `for _,
  r := range adminRoutes(...) { mux.Handle(r.method+" "+r.path,
  requireAdmin(r.handler)) }` instead of eleven individual `mux.Handle`
  calls, so there is exactly one place a route can be registered without
  the guard.
- `cmd/opencircuit/admin_wiring_test.go` calls that *same* `adminRoutes`
  function to build its authorization matrix, rather than hand-listing
  `/admin/settings` and `/admin/interests` as before. For every route it
  drives three sessions — none (want 401), non-admin (want 403), admin
  (want anything except 401/403, i.e. the request reached the real
  handler) — over the real HTTP listener `mountAndServe` itself starts.
  `resolveAdminRoutePath` substitutes each route's `{id}` with an id the
  test seeds itself: a dedicated `wiring-target@example.com` user for the
  `/admin/users/{id}` family, and a throwaway `zz-wiring-<nanoseconds>`
  interest (created via the real store, cleaned up by that prefix in
  `t.Cleanup`) for `/admin/interests/{id}` — never the seeded taxonomy,
  which is exactly what the guard-removal proof below is designed not to
  touch even while the guard is deliberately gone.

This is a **stronger** proof than a hand-kept list of routes, per the
review's suggestion: a route added to `adminRoutes` in the future is
exercised — and its guard proven — by this test automatically, with no
second edit to the test required. The failure mode this closes is
specifically a new route shipping with a guard gap and no test noticing.

## Gotchas

- **Slugs are immutable after creation, on purpose, and this pass did not
  revisit that.** `#0023`'s `Update` already took no slug parameter, with a
  doc comment explaining why: `#0044`'s audience materialisation and
  `#0056`'s announce-to-list will reference interests, and a renamed slug
  would silently redirect who a campaign reaches. This issue's PATCH
  endpoint reinforces that at the transport layer, not just the store
  layer: `patchInterestRequest` has no `slug` field, and `decodeJSON`'s
  `DisallowUnknownFields` means a client that sends one gets a 400 rather
  than having it silently dropped or (worse) accidentally wired up by a
  future edit. If a genuine rename need ever appears, it should be a new,
  explicit, separately-audited operation — not a field added to this PATCH.
- **Deactivating an interest changes what new signups can select, and the
  UI says so before the click, not after.** `#0026`'s subscribe endpoint
  validates a signup's interest slugs against `ListActive` only. The edit
  modal shows a `text-warn` line — "Deactivating removes this interest from
  the public signup form. Subscribers who already selected it keep their
  selection and history." — the moment an admin flips the Active checkbox
  off, computed from `editDeactivating = editingInterest.active &&
  !editActive` so it only appears on that specific transition, not on every
  edit.
- **The Delete button is disabled before the click, not just refused after
  it.** `hasSubscribers(interest)` (subscriber_count > 0) disables the
  control and prints the count inline ("N subscribers — deactivate
  instead"), so the server's 409 is a backstop for the racy case
  (subscriber arrives between page load and click), not the admin's first
  signal.
- **A mutation-testing run permanently deleted a seeded taxonomy row from
  the shared `opencircuit_test` database, and was caught and fixed within
  this pass.** The authorization proof requires actually removing
  `RequireAdmin` and watching a non-admin request go through for real — by
  design, that request then reaches the real handler. The first version of
  `TestAdminInterests_NonAdminForbidden`/`_Unauthenticated` targeted
  `/admin/interests/1` as a stand-in "some id" for the PATCH/DELETE cases.
  Under normal code that id is never touched (RequireAdmin blocks it), but
  id `1` is the real `microcontrollers` seed row from
  `migrations/000009_create_interests.up.sql`, and during the deliberate
  guard-removal run the DELETE actually executed and removed it. Caught
  immediately via `SELECT count(*) FROM interests WHERE slug NOT LIKE
  'zz-test-%'` reporting 11 instead of 12; restored by hand with the exact
  seed values (`INSERT INTO interests (id, slug, name, sort_order, active)
  VALUES (1, 'microcontrollers', 'Microcontrollers (ESP32, Arduino,
  RP2040)', 10, true)`), then re-verified the count was back to 12. The
  test fixtures were rewritten to seed their own throwaway "guard target"
  interest via the store and use its id, rather than ever referencing a
  literal/seeded id — safe even when the very guard being tested is
  temporarily gone. **Anyone doing authorization mutation testing against a
  shared seeded database should assume a "just pick some id" placeholder is
  never safe if the mutation under test is exactly "what happens when
  nothing stops this request."**
- **`ratelimit_wiring_test.go` and `subscribe_wiring_test.go` are not this
  issue's tests**, but adding a parameter to `mountAndServe` — a function
  four files call — required a one-line, non-functional update to each so
  the package keeps compiling. Worth flagging for the `#0026` reviewer since
  `subscribe_wiring_test.go` is presumably in their active working set; the
  diff there is exactly one `nil` inserted in the correct position, nothing
  else in that file was touched.
- **This pass (`04208af`) hit CLAUDE.md §8b directly — the section written
  because of the exact incident described above — and worked exactly as the
  guidance prescribes.** All four guard-removal mutations (`GET`, `POST`,
  `PATCH`, `DELETE` on the `/admin/interests` family, run one at a time) went
  against a private `opencircuit_fix0024` database, created with `CREATE
  DATABASE ... OWNER opencircuit`, migrated with `migrate -path migrations`,
  and dropped after the last one. `main.go` was restored between mutations by
  overwriting it from a saved copy (`cp` from a scratchpad file), never with
  `git checkout`, and its SHA-256 was reconfirmed against the pre-mutation
  copy after every restore. Every `{id}` target the wiring test uses is
  seeded fresh by the test itself (a `wiring-target@example.com` user, a
  `zz-wiring-<nanoseconds>` interest) — the shared `opencircuit_test`
  database's seeded taxonomy was never touched by any of the four mutations,
  and was independently re-confirmed at 12 rows both immediately after this
  pass's normal (unmutated) run and again after the full suite ran clean.
  This is the transferable rule from the incident above applied a second
  time, this time without a repeat.
- **A single mutation site now guards eleven routes, which is the whole
  point but is worth stating plainly.** Because `mountAndServe` registers
  every admin route from one loop over `adminRoutes(...)`, there is no
  longer a way to "forget" `requireAdmin` on one route without editing that
  loop — the prior per-`mux.Handle` version had eleven separate places a
  future edit could drop the wrapper on exactly one route and nothing else
  would look different. The trade-off: the loop can still be edited to
  special-case one route (exactly how the four mutation proofs above were
  produced, deliberately), so the real protection is the wiring test
  enumerating the same table, not the loop's shape by itself.

### Residual gap (recorded, not blocking) — the table is authoritative only for routes that go through it

The question this re-review was asked to settle: enumeration proves every route
*in* `adminRoutes` is guarded, but does it prevent a route being registered
*outside* it? **It does not.** Probed directly in the private database by
adding, next to the registration loop in `mountAndServe`:

```go
mux.Handle("GET /admin/rogue", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"rogue":true,"guard":"none"}`))
}))
```

`go test ./... -count=1` — **all 13 packages `ok`, zero failures.** A throwaway
probe against the running listener confirmed the route is live and world-open:
`unauthenticated GET /admin/rogue -> 200 ; GET /admin/settings -> 403`. Both
the probe route and the probe test were removed and `main.go` restored to
`5d1ede65f7…`.

This is a real hole, and it is worth being plain about what it does and does
not mean for this issue:

- It is **weaker** than the gap that caused the bounce. Reaching it requires
  someone to deliberately write a new `mux.Handle` for an `/admin` path instead
  of adding a line to the table sitting immediately above — and `main.go`'s own
  comment already names that as "the mistake this structure is meant to make
  hard to make." The bounced version, by contrast, was defeated by a routine
  edit to a route that *was* in the list.
- It is **not a regression and not specific to `#0024`.** It is a general
  property of `mountAndServe`: nothing enumerates the mux's registered patterns
  for any prefix (`net/http.ServeMux` exposes no way to list them), so the same
  argument applies to `/api` and `/account`. No such route exists today — the
  only `/admin` registrations in `main.go` are the 11 inside `adminRoutes`,
  verified by grep.
- Closing it needs a **different kind of test** than this issue's: a source-level
  guard (parse `cmd/opencircuit/main.go` with `go/ast` and fail if any
  `mux.Handle`/`mux.HandleFunc` pattern string outside the `adminRoutes` loop
  begins with `/admin`), since the runtime mux cannot be interrogated. That is
  its own piece of work, not a third round-trip on this one.

**Recommended follow-up (new issue):** an AST-level test in `cmd/opencircuit`
asserting that every `/admin`-prefixed route pattern registered in `main.go` is
registered through the `adminRoutes` loop, so a route added directly to the mux
fails the build rather than shipping unguarded. Acceptance criterion: adding
`mux.Handle("GET /admin/rogue", h)` to `mountAndServe` must fail the suite.
