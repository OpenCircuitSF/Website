## Description

Live progress on the campaign screen while a send runs, reusing the SSE broker carried over from ShortLinks.

## Acceptance criteria

- [ ] `GET /api/events` extended with campaign progress events
- [ ] Worker publishes progress at a sensible interval — batch completion, not per message
- [ ] Campaign detail view subscribes and shows sent / remaining / failed counts updating live
- [ ] Stream closes cleanly when the campaign completes
- [ ] Reconnects after a dropped connection without duplicating counts
- [ ] Apache vhost keeps `flushpackets=on` for `/api/events`

## Carried in from `#0044`'s plan (2026-08-21)

- [ ] **The progress denominator is `count(*)` over the campaign's
      `email_sends`**, fixed at materialization so totals never move backwards.
- [ ] **Show `skipped` as its own bucket, separate from `failed`.** They mean
      different things: `skipped` is "the list shrank under us" — someone
      unsubscribed or was suppressed between materialization and send — and is
      correct behaviour, not an error.

## Carried in from `#0045`'s plan (2026-08-21)

- [ ] **`email_sends` gains a seventh status, `sending`** (migration `000018`),
      set by a per-row atomic claim immediately before each SES call. Progress
      must compute `remaining = queued + sending`; code that buckets only the
      original six silently drops every in-flight row.
- [ ] **The seam is `ProgressPublisher.PublishCampaignProgress`**, published per
      batch. `Total` is fixed at materialization so it never moves backwards,
      and `Skipped` stays its own bucket.

      **Amended 2026-08-21 by `#0045`'s review, after reading the shipped
      code:** the seam landed exactly as specified
      (`internal/mailing/worker.go` — `ProgressPublisher` and
      `CampaignProgress{CampaignID, Total, Sent, Failed, Skipped, Remaining}`),
      with three facts this issue needs:

      - It is published **once per batch and once more at completion**, both
        nil-guarded, so `#0048` gets a final snapshot without polling.
      - **The wiring point is one line**: `newSendWorkerIfEnabled` in
        `cmd/opencircuit/main.go` currently passes `Progress: nil`. That is
        the literal `nil` `#0048` replaces with the broker-backed
        implementation — nothing else in the worker needs reshaping.
      - Every field is **recomputed from `email_sends` on each publish**
        (`SendStore.CountEmailSends`), never tracked incrementally, so a
        publish after a restart or resume is correct even though that `Worker`
        instance never saw the earlier batches. Note the failure path
        (`failCampaign`) does **not** publish — a campaign that dies on a
        terminal SES error leaves the last batch's snapshot as the final one,
        which `#0048`'s UI should reconcile against campaign status rather
        than assume progress reached `Total`.

## Carried in from `#0047`'s plan (2026-08-21)

- [ ] **The seam is a named, empty progress region in `CampaignEditor.svelte`.**
      `#0047` renders campaign status only and deliberately does not poll.

      **Amended 2026-08-21 by `#0047`'s review, after reading the shipped code
      (`9f8895c`):** the region is
      `<div id="campaign-send-progress" role="status" aria-live="polite"></div>`,
      sited after the Send/Cancel action row inside `CampaignEditor.svelte`'s
      `{:else if campaign}` branch. It is rendered **unconditionally** and
      empty, which is deliberate — an element inserted into the DOM together
      with its text is not reliably announced (the `#0036` → `#0063` live-region
      finding), so `#0048` must fill this element's *children* and must not wrap
      it in an `{#if}`.

      Two more things `#0048` inherits from what shipped. First, the editor's
      three thin components hold **markup and wiring only**: every decision
      routes through `web/src/lib/campaigns.ts`, `preflight.ts`, `audience.ts`
      or `sendConfirm.ts`, because `#0094` means nothing in a `.svelte` file is
      covered by a test. Progress formatting ("482 of 1,203 sent", a percentage,
      a stalled-vs-running verdict) belongs in a new `web/src/lib/` module with
      its own vitest file, not in the component. Second, `CampaignEditor` holds
      `campaign` in `$state` and refreshes it from each mutation's response;
      `#0048`'s stream should reconcile against `campaign.status` rather than
      assume progress reaches `Total`, per `#0045`'s note that `failCampaign`
      does not publish.
- [ ] **Supply the remaining-recipient count.** `#0047`'s `cancelCopy('sending')`
      deliberately omits the number of recipients who would still be spared by
      cancelling, because only `#0048` knows it. Without it the operator is asked
      to cancel a send without being told what cancelling saves.

## Notes

PRD §8. Publishing per-message on a 10-per-second send is 10 events per second of noise; per-batch is enough to feel live.

The Apache `flushpackets=on` directive on the SSE path carries over from ShortLinks — without it the proxy buffers and the stream appears frozen. Easy to lose when writing the new vhost (#0064).
