## Description

Live progress on the campaign screen while a send runs, reusing the SSE broker carried over from ShortLinks.

## Root cause

Not a bug — this issue's seams were already shipped by `#0045` and `#0047`
specifically for this issue to fill in: `internal/mailing/worker.go` computed
and published `CampaignProgress` snapshots against a literal `Progress: nil`
(`cmd/opencircuit/main.go`'s `newSendWorkerIfEnabled`), and
`CampaignEditor.svelte` rendered an empty, named `#campaign-send-progress`
region that nothing filled. `GET /api/events` existed and worked, but had no
publisher wired to it for campaign progress and was gated by
`requireSession` alone even though its only real consumer is admin data.

## Fix

**Backend — the broker-backed `ProgressPublisher`.**
`internal/handlers/campaign_progress.go` is a new adapter,
`NewCampaignProgressPublisher(*events.Broker, *slog.Logger)
mailing.ProgressPublisher`, following `NewCampaignPreflightChecker`'s own
nil-typed-nil-trap precaution (a nil broker returns a genuinely nil
interface, not a non-nil interface wrapping a nil pointer, so
`mailing.Worker`'s `if w.progress == nil` guard keeps working). It depends
on a narrow `campaignProgressBroker` interface (`PublishAll(events.Event)`),
mirroring `events.go`'s own `eventSubscriber` interface on the subscribing
side, so it is unit-testable with a fake broker.

`internal/events/broker.go` gained `Broker.PublishAll(event)`: a campaign
isn't owned by whichever admin happens to have it open, so progress must
reach every connected admin session, not one `userID`'s channel the way
`Publish` scopes link-style events. Same best-effort, non-blocking delivery
as `Publish` (a full/slow subscriber buffer is skipped via a `select` with a
`default`, never blocks the publisher or another subscriber).

`internal/mailing.CampaignProgress` gained `json` tags (`campaign_id`,
`total`, `sent`, `failed`, `skipped`, `remaining`) so it can be marshaled
verbatim into the SSE frame's `data` field — the arithmetic itself
(`Remaining = queued + sending`, `Skipped` as its own bucket) was already
correct as shipped by `#0045`; this issue only had to carry it over the
wire.

`cmd/opencircuit/main.go`: `newSendWorkerIfEnabled` gained a `progress
mailing.ProgressPublisher` parameter, and the broker/`eventsH` construction
moved earlier in `servePostgres` (it now has to exist before the worker is
built) so `handlers.NewCampaignProgressPublisher(broker, ...)` can be handed
straight into `WorkerDeps.Progress`, replacing the literal `nil`.

**`GET /api/events` moved from `requireSession` to `requireAdmin`.** Its one
real consumer is admin data (live campaign send progress), so
CLAUDE.md §9's "admin data" framing applies, and `EventSource` cannot set a
custom `Authorization` header — the existing session cookie is what
`requireAdmin` (which composes `RequireSession` then `RequireAdmin`) checks,
so no new auth mechanism was needed.

**Deliberate deviation from the task brief's "registered through
`adminRoutes()`":** `GET /api/events` stays wired directly in
`mountAndServe`, *not* added to the `adminRoutes()` table. Reading
`cmd/opencircuit/admin_routes_ast_test.go`
(`TestAdminRoutesRegisteredOnlyViaTable`) before making this change showed
its own doc comment already documents, and its mechanics already enforce,
that this is `/admin`-prefix-only *by design* — every `/api/*` route,
including `/api/events`, is documented there as carrying its own guard
written directly at its `mux.Handle` call site, with the AST test's comment
explicitly reasoning through why that's the right shape for `/api` (no
single table a route could "bypass" the way `/admin` routes can). Folding
`/api/events` into `adminRoutes()` would have fought that established,
tested convention for no benefit — the guard is proved either way. I kept
the route where it already lived, changed its middleware from
`requireSession` to `requireAdmin`, and added a dedicated
`events_wiring_test.go` that proves the 401/403/200 shape at the real mux,
the same standard `TestMountAndServe_AdminRoutesRequireSessionAndAdmin`
holds the table to. Updated `admin_routes_ast_test.go`'s prose (mechanics
unchanged) and `shutdown_budget_wiring_test.go` (which opens a real,
long-lived `GET /api/events` connection to prove the shutdown/close budget
split — it now seeds an admin session and composes a real `requireAdmin`
chain instead of the `passthroughAdmin` stand-in it used when the route was
merely session-gated) to match.

**Reconciling the stream against the database, not trusting it as the
source of truth.** `#0045`'s review already flagged that `failCampaign`
(the terminal-SES-error path) does not publish a closing snapshot, so a
campaign can reach `failed`/`canceled`/`sent` with no further SSE frame
ever arriving. `web/src/lib/events.ts`'s `subscribeEvent` gained an optional
`onOpen` callback, fired on the initial connection and on every automatic
reconnect (the DOM `EventSource` doesn't distinguish the two) —
`CampaignEditor.svelte` uses it to re-fetch just the campaign's `status`
(never the editable name/subject/preheader/body/mode/interest buffer, so an
operator's in-progress edit is never clobbered) on every (re)connect. This
bounds "how long can the UI show a stale state" to "however long the
stream was down," rather than "possibly forever" if the campaign finishes
during a gap with no more batches to publish. Because every
`CampaignProgress` frame is a full recomputed snapshot (never a delta —
`#0045`'s own doc comment on `publishProgress`), a reconnect can never
double-count: whatever the next frame says simply replaces whatever was
shown.

**The worker never waits on a slow/absent SSE client.**
`Broker.PublishAll`'s per-subscriber sends are a `select` with a `default`
branch (channel full → dropped for that subscriber, never blocked) inside a
single in-memory, synchronous call from the worker's own goroutine — there
is no network hop, no goroutine spawned per publish, and no context
deadline that could expire mid-send. `publishProgress`'s nil-guard
(`if w.progress == nil { return }`) means the worker's send path is
identical whether anyone is watching or not.

**Frontend — `web/src/lib/campaignProgress.ts`, a new pure module** (per
`#0047`'s established convention that nothing in a `.svelte` file is
covered by a test, `#0094`): the `CampaignProgress` payload shape (kept in
sync by hand with the Go struct's `json` tags — noted in both doc
comments), the `"campaign.progress"` event name constant,
`isProgressForCampaign` (frames are broadcast to every admin for every
campaign, so each consumer filters), `progressPercent`,
`formatProgressSummary`/`formatProgressDetail`, `shouldShowProgress` (always
true while `sending`, even before the first frame; only true for a terminal
status if a snapshot actually arrived — a terminal status with no snapshot
has nothing true from this stream to show), `progressHeading` (keyed by the
campaign's current status, never by whether `remaining` reached 0 — the
`failCampaign` non-publish case above), a `progressVerdict`
(`running`/`stalled`/`not-sending`, a 30s no-update threshold sized off the
worker's own batch cadence, not machine load), and `remainingForCancel` —
the remaining-recipient count `#0047`'s `cancelCopy('sending')` deliberately
omitted, `undefined` (never a fabricated 0) unless the campaign is
`sending` and a snapshot for THIS campaign has actually arrived.

`web/src/lib/campaigns.ts`'s `cancelCopy` gained an optional `remaining?:
number` second parameter — omitted or `undefined`, it returns the exact
original wording (proved by the pre-existing "contains no digits" test);
supplied, the `sending` case names the live count ("...stops the worker
from sending to the 706 recipients not yet mailed", with a singular
"1 recipient" case).

`CampaignEditor.svelte` fills `#campaign-send-progress`'s **children**
only — the outer `<div>` stays unconditionally rendered per `#0047`'s
review finding (an element inserted into the DOM together with its text is
not reliably announced) — with a heading, the formatted detail line, a
percent-width bar, and a stalled notice, every one of them a `$derived`
reading straight off a `lib/campaignProgress.ts` call. `onMount` subscribes
via `subscribeEvent(CAMPAIGN_PROGRESS_EVENT, onProgressEvent, undefined,
onOpen)` and starts a 5s ticker (`nowTick`) purely so the "stalled" verdict
can appear on its own, without waiting for a new frame that (by definition,
if stalled) isn't coming; both are torn down in `onMount`'s cleanup.

**Second pass (2026-08-21), addressing the review's point 1 — `campaign.status`
never refreshed when a send finishes.** The first pass refreshed
`campaign.status` from `load()`, the stream's `onOpen` (initial connect and
every automatic reconnect), and explicit mutations — but never from a
progress frame itself. On a healthy connection (the normal, successful-send
case) that left `progressHeading` reading the stale `'sending'` status
forever after the closing frame arrived, and 30s later `progressVerdict`
piled a false "stalled" warning on top of a campaign that had already
finished. The same gap left a `failed` campaign showing "Sending…"
indefinitely too.

Fixed with exactly the seam the review specified, kept out of the `.svelte`
file per `#0094`: `web/src/lib/campaignProgress.ts` gained
`isTerminalSnapshot(p)`, and `CampaignEditor.svelte`'s `onProgressEvent` now
calls `void resyncCampaignStatus()` whenever it is true, in addition to the
existing per-frame `progress`/`progressUpdatedAt` update — so a closing frame
itself, not just a reconnect, is what moves `campaign.status` off
`'sending'`. `resyncCampaignStatus`'s own doc comment was corrected to
describe this third trigger and to stop claiming `failCampaign` never
publishes (see the worker-side change below).

> **Superseded by the third pass (below).** This pass implemented the
> predicate as `p.remaining === 0` and claimed vitest coverage for "a
> `failCampaign`-style partial snapshot where `sent + failed + skipped <
> total` but nothing is left queued/sending". The second review correctly
> found that shape is **not one the worker produces**: `MarkFailedCampaign`
> never touches `email_sends`, so the failure paths publish `Remaining > 0`
> and the predicate was false on exactly the paths that needed it. The seam
> and the wiring were right; the signal was wrong. See the third pass.

**Worker-side terminal publish, also added.** The review flagged this as
"welcome but optional" since it alone doesn't fix the success path (the
client's `campaign.status` still wouldn't move without the `isTerminalSnapshot`
wiring above) — but it's one line and closes a real gap on its own: before
this pass, `failCampaign` (the worker-detected-reason path — anomalous empty
audience, `physical_address`/reply-to gone blank mid-resume, or a
terminal-class SES error via `failCampaignSES`) never published a closing
snapshot at all, so a `failed` campaign's last SSE frame was whatever the
previous *live* batch reported. `internal/mailing/worker.go`'s `failCampaign`
now calls `w.publishProgress(ctx, campaignID)` inside its existing `if did {}`
guard (the same guard that already governs the audit-row write, so a second
worker's concurrent, no-op failure attempt still publishes nothing extra).
This **is** a change to `#0045`'s worker, noted here per the review's
instruction. Verified with two new Go tests in `progress_test.go`:
`TestWorker_FailCampaign_PublishesTerminalSnapshot` and
`TestWorker_FailCampaign_NoTransitionNoPublish` (asserts no publish when
`MarkFailedCampaign`'s `did` is false).

**Third pass (2026-08-22), addressing the second review's points 3, 4 and 5 —
terminality is a fact about the campaign, not arithmetic over the counts.**

*Point 3 — the design.* The second review's framing is the one this pass
built to: `remaining === 0` is sound for what it literally tests, but it is
not *implied by* "the campaign reached a terminal status," and a failed
campaign legitimately has recipients who will never be mailed.
`MarkFailedCampaign` (`worker_store.go`) updates `email_campaigns` alone and
never touches `email_sends`, so `physical_address_missing`,
`reply_to_missing`, and every terminal-class SES error via `failCampaignSES`
leave the unsent rows `queued` and publish `Remaining > 0` on a send that has
definitively stopped. **The chosen fix carries the campaign's own status in
the snapshot**, so the client stops inferring terminality from counts:

- `internal/mailing.CampaignProgress` gained `Status string
  \`json:"status"\`` — `email_campaigns.status` as of that publish.
- `SendStore.CampaignStatus(ctx, campaignID)` is a new one-column read, and
  `publishProgress` reads it **fresh on every publish**, alongside the counts
  it already recomputed. It is never passed in by the caller, for the same
  reason `failCampaign` re-reads its counts after the transition rather than
  reusing the pre-transition ones (which the second review endorsed): the
  database is the authority, and a caller's idea of "the status I just wrote"
  can be stale the instant a concurrent cancel or another worker's transition
  lands. Every call site publishes *after* whatever transition it performs, so
  the status read can only be at-or-after the one just written — a snapshot
  can never claim a status the campaign has not reached.
- A failed status read is logged and published as `""`, never fatal: the
  counts are still true and useful.

`web/src/lib/campaignProgress.ts`'s `isTerminalSnapshot` is now
`isTerminalCampaignStatus(p.status) || p.remaining === 0`, with
`TERMINAL_CAMPAIGN_STATUSES` (`sent`/`failed`/`canceled`) exported and reused
by `shouldShowProgress` so the vocabulary is stated once. The name and the
contract now agree: it detects "this frame may be the last one for this send,"
which is precisely the trigger for a best-effort re-read — not a claim about
state. Nothing renders from it; `progressHeading`/`progressVerdict` still key
off the campaign's own status.

**Rejected: making `failCampaign` resolve its leftover `queued` rows to a
resting state so `remaining` genuinely reaches 0.** The second review already
called this "a bigger, `#0045`-owned semantic change — do not do it casually,"
and there is a second reason beyond ownership: those rows carry an
operator-facing fact. "This campaign stopped with 706 people unmailed" is
exactly what `remainingForCancel` and the cancel dialog exist to tell an
operator, and a seventh `email_sends` status invented to mean "abandoned"
would need a migration, a meaning in `#0049`'s stats view, and a decision
about whether a resumed campaign may re-queue them. Forcing the counts to
lie about reality to satisfy a predicate is the wrong direction; teaching the
predicate to read the fact it actually needs is the right one.

*Keeping Go and TypeScript in agreement (`#0095`, `#0093`).* Nothing
mechanically enforces the payload contract, so three things guard it by hand:
both struct/interface doc comments now say "add a field here, add it there in
the same commit"; `TestCampaignProgressPublisher_PublishesJSONFrameToBroker`
was tightened to decode as `map[string]any` and assert the **exact key set**
(7 keys, no more and no fewer) rather than spot-checking values; and the TS
side treats `status` as possibly-absent at runtime even though the type says
`string` — hence the `remaining === 0` **fallback**, which is deliberately
kept. If a bundle ever runs against a server without the field (or against a
worker whose status read errored), the successful-send path still works
instead of silently reinstating the original bug. A false positive costs one
extra `GET` whose answer is authoritative anyway.

*Point 4 — the boundary.* The `remaining === 0` fallback is now pinned by an
explicit `remaining: 1` negative case, which is what kills the `<= 1` mutant
the review found survived all 298 tests. `isTerminalCampaignStatus` is pinned
against the full status vocabulary in both directions, and the `#0095`
degradation path (`status: ''` and `status` missing entirely) is covered at
`remaining: 0` and `remaining: 1`.

*Point 5 — sequencing the concurrent resyncs.* `createResyncSequencer()` in
`campaignProgress.ts` (a pure factory, testable per `#0094`) makes the
assignment **monotonic in request-start order**: `resyncCampaignStatus` takes
a token from `begin()` before its `getCampaign`, and assigns `campaign` only
if `isCurrent(token)` still holds when the response lands. A superseded
response is discarded rather than applied late, so the first fetch — which can
read the database before `CompleteIfDone` commits and come back `'sending'` —
can no longer overwrite the second's `'sent'`. Ordering by *start* is sound
because a later-started read sees a database at least as fresh as an
earlier-started one, whatever order the responses arrive in.

"Skip if one is already in flight" was **rejected**: on the success path it is
the *second* request that carries the terminal status, so skipping would drop
the wrong one. Tokens count from 1 and `isCurrent` requires `token > 0`, so
the counter's own initial value cannot be mistaken for a live request. Per the
review, the discarded promise itself is left as-is (`try`/`catch` inside, at
most two frames, no storm) — ordering was the real risk.

> 🔴 Bounced 2026-08-21 by phase-3 review of `ebf77e2`.

Most of this landed well, and the parts the brief singled out for scrutiny all
hold up — see "What passed" below, and do not re-litigate them on the next

### 1. The campaign's status is never refreshed when a send finishes, so the primary success path ends in a wrong — then actively misleading — UI state

`CampaignEditor.svelte` refreshes `campaign` (and therefore `campaign.status`)
from exactly three places: the initial `load()`, `resyncCampaignStatus()` on
the SSE stream's (re)connect, and the explicit mutations
(save / test-send / send / cancel). **Nothing refreshes it when a progress
frame arrives.** On a stable connection — the normal case, the one this whole
feature exists to serve:

1. Operator clicks Send. `campaign.status = 'sending'`; the region reads
   "Sending…". Correct.
2. Frames arrive; the counts update live. Correct, and genuinely nice.
3. The worker finishes: `CompleteIfDone` fires the closing `publishProgress`
   (`remaining: 0`) and the DB status becomes `sent`.
4. The client receives that closing frame — but its own `campaign.status` is
   still `'sending'`, because nothing asked the server. `progressHeading('sending')`
   returns **"Sending…"**, over "1,203 of 1,203 sent · 0 remaining",
   indefinitely.
5. Thirty seconds later `progressVerdict` still sees `status === 'sending'`
   with no newer frame, returns `'stalled'`, and the region adds **"No update
   in a while — the worker may be paused or waiting on send-rate limits."** —
   on a campaign that completed successfully.

This is a false alarm on *every* successful send, and it defeats the exact
mechanism the `## Fix` section designed: `progressHeading` is keyed by status
rather than by `remaining === 0` precisely so the heading can never lie, but
the key it reads is never updated, so it lies anyway. It is also the closest
thing this issue has to acceptance criterion 4, "Stream closes cleanly when
the campaign completes."

The same gap makes the `failCampaign` case worse than `## Fix` describes.
The reasoning there — "`onOpen` bounds staleness to however long the stream
was down" — is sound, but only for a stream that actually dropped. With a
healthy connection there is no reconnect, `onOpen` never fires again, and
"Sending…" persists indefinitely for a `failed` campaign too. The stalled
notice is then the only signal an operator gets, and it names the wrong cause.

**On the brief's question of whether a terminal-state publish is the better
answer:** it is a good idea and cheap — `failCampaign` already calls
`CountEmailSends`, so `w.publishProgress(ctx, campaignID)` inside its
`if did {}` is one line — but it is **not sufficient on its own**, because it
does not fix the success path: the client's `campaign.status` still would not
move. The necessary fix is client-side. Do it where this issue's own
conventions already point — a predicate in `web/src/lib/campaignProgress.ts`
(something like `isTerminalSnapshot(p)` → `p.remaining === 0`) with its own
vitest coverage, driving `resyncCampaignStatus()` from `onProgressEvent`, so
the decision stays out of the `.svelte` file per `#0094`. Adding the
`failCampaign` publish as well is welcome but optional; if you add it, note
that it is a change to `#0045`'s worker.

### 2. The "transient cross-package DB-contention failure" in `## Verification` is a real defect, and the recorded diagnosis is wrong on both of its claims

`## Verification` and `## Gotchas` both record
`TestWorker_TwoWorkersOneCampaign_EachRecipientSentExactlyOnce`
(`mailer.Sent() = 25, want 24`) as pre-existing shared-DB contention from
`-p 2`, in `#0121`'s class. Neither half survives checking:

- **Cross-package DB concurrency cannot happen.** `internal/testdb.Lock()`
  takes a shared PostgreSQL session advisory lock (`0x53484F52544C4B`), and

- **It is not `#0121`.** `#0121` is three `internal/handlers` tests asserting

  Different package, different table, different mechanism.
  `internal/mailing`'s own seeds are clean (`seedScheduledCampaign` registers

The real cause is a genuine concurrency defect in `#0045`'s worker, reproduced

`drainCampaign`'s unconditional `OrphanSweep` resets **every** `sending` row

flake three times (`#0108`, `#0121`, this one); leaving the false diagnosis in

### 3. The `failed`-campaign half of the reported bug is still live: `failCampaign`'s new publish is not a terminal frame

`## Fix`, `## Files changed`, and acceptance criterion 4 all claim the new
`failCampaign` publish gives "the worker-detected-failure path a closing frame
to be terminal on, the same as a normal completion." It does not. The chain:

1. `MarkFailedCampaign` (`worker_store.go:509`) updates **`email_campaigns`
   only** — `UPDATE email_campaigns SET status='failed' ... WHERE id=$1 AND
   status='sending'`. It never touches `email_sends`.
2. So on `physical_address_missing`, `reply_to_missing`, and every
   terminal-class SES error via `failCampaignSES`, the unsent rows are still
   `queued` when `failCampaign` runs.
3. `publishProgress` computes `Remaining = queued + sending`, so the frame it
   publishes carries **`Remaining > 0`**.
4. `isTerminalSnapshot(p) => p.remaining === 0` is therefore **false**, and
   `onProgressEvent` does not call `resyncCampaignStatus()`.
5. The client keeps `campaign.status === 'sending'`. `progressHeading('sending')`
   returns **"Sending…"** indefinitely, and 30s later `progressVerdict` returns
   `'stalled'` and adds **"No update in a while — the worker may be paused or
   waiting on send-rate limits."** — on a campaign that has already failed, with
   the wrong cause named. That is verbatim the bug the first bounce reported,
   for the failure path.

Only `empty_audience` reaches a terminal frame, and only because `total == 0`
makes `Remaining` trivially 0.

**This is proved inside the commit itself.**
`TestWorker_FailCampaign_PublishesTerminalSnapshot` seeds one `sent` row and one
`queued` row and asserts the exact published snapshot as
`Remaining: 1` — a non-terminal frame, in a test named "PublishesTerminalSnapshot",
covering the path the issue text says is now terminal. The vitest case
"is true for a failCampaign-style partial snapshot with nothing left
queued/sending" describes a shape the worker does not actually produce on these
paths.

**The worker-side publish is still worth keeping** — it delivers fresh counts at
the moment of failure. It is just not, on its own, a terminal signal. Options,
implementer's choice:

- Give the client a signal that does not depend on `remaining`. The cleanest is
  to carry the campaign's status in the frame (`CampaignProgress` has no
  `status` field today — the predicate's doc comment notes this as the reason
  it reads `remaining` alone) and resync on any terminal status, not only on
  `remaining === 0`; or
- have `failCampaign` also transition the campaign's leftover `queued`/`sending`
  rows to a resting state before publishing, so `Remaining` genuinely reaches 0.
  This is a bigger, `#0045`-owned semantic change — do not do it casually.

### 5. Two terminal frames per successful send, and two unsequenced resyncs

`drainLoop` publishes at the bottom of every batch iteration, then the next
iteration's `ClaimBatch` returns empty and `CompleteIfDone` publishes again. On
the final batch the bottom-of-loop publish already reports `remaining: 0` —
**before** `CompleteIfDone` flips the status. So every successful send emits two
terminal frames a few DB round trips apart, and `onProgressEvent` fires
`void resyncCampaignStatus()` twice, concurrently, with no sequencing.

The first fetch may read the DB before `CompleteIfDone` commits and return
`'sending'`. `resyncCampaignStatus` is last-write-wins (`campaign = await
getCampaign(...)`), so if that first response is applied after the second, the
component lands back on `'sending'` with no further frames coming — reinstating
the original "Sending…" forever plus false stall. Narrow, and it needs response
reordering to bite, but both requests really are in flight at once on the normal
path, so it is not hypothetical. Guard it: track a request generation and ignore
a stale response, or skip the resync if one is already in flight.

This also answers the brief's `void`-discards-the-promise question: the discard
itself is fine (`resyncCampaignStatus` has its own `try/catch` and is
documented best-effort, and a terminal frame arrives at most twice, so there is
no request storm). The problem is ordering, not the discarded promise.

### On the two judgment calls the brief asked for

**`remaining === 0` as a terminality test — sound for what it literally tests.**
`Remaining = queued + sending` counts every row not in a resting state, across
all workers, so it cannot read 0 while any row is claimed by anyone; `#0122`'s
`sending` state is counted, not dropped. The false positives the implementer
worried about are not reachable: nothing publishes between materialization and
the first claim, and a zero-recipient audience genuinely is done. And a spurious
resync would be harmless anyway — one extra `GET`, with the server authoritative.
The defect is the opposite polarity. `remaining === 0` is not *implied by* "the
campaign reached a terminal status," and a `failed` campaign normally has
`remaining > 0`. Sound predicate, wrong sole trigger.

**Criterion 4's reinterpretation is legitimate.** The `EventSource` really is
admin-session-scoped and outlives any one campaign; there is no per-campaign
close to implement, so reading the criterion as "progress reporting settles
cleanly into a terminal state" is the honest reading, not a redefinition to fit
what was built. The reading is accepted. The checkbox is not earned, because
reporting does not settle for a failed campaign — see point 3.
