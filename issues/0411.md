## Description

The admin campaign routes are `GET`/`POST` on the collection and
`GET`/`PATCH`/`send`/`cancel`/`archive` on an item. **There is no `DELETE`.**

Campaign slugs are `UNIQUE` and minted at draft time, so a draft created by
mistake — a duplicate, a test, a mis-titled first attempt — **permanently
occupies its slug**. Combined with [#0410](0410.md) (no console UI for the slug
override), a mis-slugged draft has no console-reachable repair at all: it can be
neither re-slugged nor removed.

Concretely: a stray draft holding `09-2026` would push the real September
newsletter to `09-2026-2`, and nothing in the admin console could recover the
intended URL.

## Root cause

`AdminCampaignsHandler` (internal/handlers/admin_campaigns.go) and
`mailing.CampaignStore` (internal/mailing/campaigns.go) implemented every
campaign verb except delete: List, Create, Get, Patch, Send, Cancel, Resume.
Nothing was ever built to remove a row, so `email_campaigns.slug`'s `UNIQUE`
constraint (migration 000025) held forever once a draft minted one.

## Fix

**What may be deleted, and why.** Only a campaign whose status is `draft`.
This is the exact same boundary `Update` already draws for a slug *change*
(`ErrCampaignSlugNotEditable`, #0410) — not a new, independently-invented
rule:

- `scheduled` and past: promotion (a `go.opencircuitsf.com` short link, a
  Discord post) may already be written against the slug/archive URL (PRD
  §6.8's "load-bearing detail"). #0410's slug-repair escape hatch stops at
  draft for the identical reason, so it would be inconsistent for delete to
  reach further than edit does.
- `sent`: the campaign has a published archive page and its URL is already
  in delivered mail (PRD §6.8, acceptance criterion 2). `withheld`
  (`PATCH /admin/campaigns/{id}/archive`, #0123) already exists as the
  non-destructive lever for pulling a sent campaign from the public archive
  — that answers this issue's own question 1 without needing delete to
  touch `sent` at all.
- `sending`: in-flight `email_sends` rows exist, claimed by #0045's worker;
  `Cancel` already owns "stop this" and is the correct verb, not a second,
  overlapping one (question 2).
- `paused_delivery_health`/`failed`/`canceled`: all reachable only from a
  campaign that has already left `draft` at least once, so the same
  promotion-may-exist reasoning applies as `scheduled`.

Every other status is refused with 409 and a clear message
(`ErrCampaignNotDeletable` → "a campaign can only be deleted while it is a
draft") — never a silent no-op.

**Referential integrity (question 3).** Three tables carry a foreign key
into `email_campaigns(id)` — enumerated by reading every
`REFERENCES email_campaigns` in `migrations/`, not assumed:
`campaign_interests` and `email_sends` (both migration 000017, both
`ON DELETE CASCADE`), and `subscriber_events` (migration 000022,
`ON DELETE SET NULL`). No new migration and no explicit cleanup code was
needed for any of the three; the plain
`DELETE FROM email_campaigns WHERE id = $1 AND status = 'draft'` cascades
the first two automatically and nulls the third's `campaign_id`.
`subscriber_events` is nulled rather than cascaded because it is the
append-only activity log PRD §6.11 describes — its rows must survive the
campaign that produced them. Its `campaign_id` column's only writer is the
send worker's campaign-sent event, which fires only during a real send, so
a still-draft campaign (the only status this delete accepts) can never own
such a row today; the delete can therefore neither fail nor orphan against
it, even though `SET NULL` differs in kind from the other two tables'
`CASCADE`. `email_events` carries no `campaign_id` column at all — it is
keyed by recipient/`ses_message_id` (PRD §6.7) — so it has nothing to
cascade or null. `TestCampaignStore_Delete_CascadesReferencingRows` seeds a
`campaign_interests` row, an `email_sends` row, and a `subscriber_events`
row directly by SQL (a draft can never legitimately have an `email_sends`
row through this package's own API — materialization only happens once a
send starts, #0044) and proves the first two are gone and the third still
exists with `campaign_id IS NULL` after `Delete`.

**Hard delete, not soft (question 4) — the slug is genuinely freed.** A
soft-delete flag was considered and rejected: the row's continued existence
is exactly what would keep occupying the `UNIQUE(slug)` constraint, which is
the entire problem this issue exists to solve. `TestCampaignStore_Delete_FreesSlugForReuse`
proves release directly rather than by inference: it mints the same subject
twice, deletes the first campaign, and asserts the second gets the
IDENTICAL bare slug back (not a `-2` suffix) — Create's own collision-suffix
retry would otherwise mask a slug that was never actually freed.
`TestAdminCampaigns_Delete_FreesSlugForReuse` proves the same thing through
the HTTP route: after DELETE, PATCHing a second draft's slug to the first
campaign's former slug succeeds (200), not 409 `ErrCampaignSlugTaken`.

**Audit (question 5).** `DELETE /admin/campaigns/{id}` writes a new
`audit.ActionEmailCampaignDeleted` (`email_campaign.deleted`) row on success
only, with `name`/`subject`/`slug` in `Metadata` — the row is gone the
instant `Delete` succeeds, so the audit entry is the only remaining record
of what a stray draft's slug used to be. A refused delete (409) writes no
audit row, mirroring `ActionWorkshopDeleted`'s own "no row for a refused
mutation" convention (`AdminWorkshopsHandler.Delete`,
`AdminInterestsHandler.Delete`).

**Handler shape.** `AdminCampaignsHandler.Delete` mirrors
`AdminWorkshopsHandler.Delete` almost exactly: load the campaign first (so
audit metadata can record what it was), call `Delete`, map
`ErrCampaignNotFound` → 404 and `ErrCampaignNotDeletable` → 409, audit, and
respond `200 {"message": "campaign deleted"}` — the same response shape
`DELETE /admin/workshops/{id}` already uses.

**Route ordering.** `DELETE /admin/campaigns/{id}` is registered in
`cmd/opencircuit/main.go`'s `adminRoutes` after every other
`/admin/campaigns/{id}` sub-route block (audience/preview/test/preflight/
stats/archive), in its own block for diff hygiene, rather than immediately
after `Resume` where it was first written. **Corrected in review**: an
earlier version of this section claimed that position was required by
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin`
(cmd/opencircuit/admin_wiring_test.go) sharing one seeded campaign across
every `adminRoute` in list order. That coupling does not exist — the
reviewer measured it directly by moving the route to the earliest position
in its family in a throwaway worktree, and `cmd/opencircuit` still passed
(`TestMountAndServe_AdminRoutesRequireSessionAndAdmin`'s admin case accepts
any status that is neither 401 nor 403, so a 404 from an already-deleted
campaign satisfies it). The route's position is not load-bearing and may be
reordered freely; it stays where it was first placed only for diff
hygiene, not because moving it would break anything.

**No migration.** Both cascading foreign keys already existed in migration
000017 — nothing to add. Per #0407, this delete's own boundary check (only
`draft`, never anything already applied to production) doesn't even arise:
no schema change was needed at all.

**Console UI.** `CampaignEditor.svelte` gains a "Delete campaign" button
(shown only when `canDeleteCampaign(campaign.status)`, i.e. draft) and a
confirm dialog, modeled directly on `WorkshopEditor.svelte`'s own
delete-confirm modal — a plain "Delete this campaign? ... Keep it" dialog,
not a typed-confirmation one like Resume's. A typed-subject confirmation
(#0124's pattern) was considered and not used here: a still-draft campaign
has never sent or been scheduled, so the risk profile matches Workshop's
delete (also a plain confirm), not Resume's "un-trip a circuit breaker that
already sent real mail" case. On success the editor calls `onBack()` — the
row is gone, so there is nothing left to reload or resync, unlike
Cancel/Resume which reassign `campaign` to the server's response.

## The design questions this needs answered

This is deliberately not a one-line route addition. **A campaign is not freely
deletable**, and the constraints are real:

1. **A `sent` campaign must not be deletable.** It has a published archive page
   (PRD §6.8), and recipients hold links to it. Deleting it would 404 a URL that
   went out in email. The archive already has a `withheld` state — decide
   whether that is the correct answer for a sent campaign and delete is simply
   refused.
2. **What about `sending`?** A campaign mid-send has outbound rows in flight.
   `cancel` already exists; decide how delete relates to it rather than adding a
   second half-overlapping verb.
3. **What else references a campaign?** `outbound_queue` rows, `email_events`,
   `campaign_interests`, and anything the send worker holds. Enumerate the real
   foreign keys from the schema — do not assume this list is complete — and say
   whether delete cascades, refuses, or soft-deletes.
4. **Soft delete versus hard delete.** A soft delete keeps the row and therefore
   keeps holding the `UNIQUE` slug, which does not solve the motivating problem
   unless the slug is released or renamed. Say explicitly how the slug is freed.
5. **Audit.** Deleting a campaign is destructive and admin-initiated; the project
   has an audit log. Say what is recorded.

## Acceptance criteria

1. Deletion is possible for a campaign in a state where it is safe, and
   **refused with a clear reason** in every state where it is not.
2. A `sent` campaign's archive page is never broken by this feature.
3. The slug is genuinely freed for reuse, or the issue states plainly that it is
   not and why that is acceptable.
4. Referential integrity is handled explicitly per question 3, proved by a test
   that creates the referencing rows first.
5. The action is audited.
6. Run `./internal/mailing/...`, `./internal/handlers/...`, `./internal/outbox/...`
   and `./internal/db/...` (§5's repo-wide-guard table), plus the web suites if
   the console gains a control. Per §5 name the specific tests that ran.
7. If a migration is needed, read [#0407](0407.md) on what "frozen" actually
   means before assuming, and note `000028` is taken by another session's
   uncommitted work.

### 1. The foreign-key enumeration is incomplete — acceptance criterion 4, question 3

**Three** tables carry a foreign key into `email_campaigns(id)`, not two:

| Table | Migration | On delete |
|---|---|---|
| `campaign_interests` | `000017` | `CASCADE` |
| `email_sends` | `000017` | `CASCADE` |
| `subscriber_events` | `000022` | **`SET NULL`** |

`subscriber_events.campaign_id` is absent from `## Fix`, from the commit
message, and from `mailing.CampaignStore.Delete`'s doc comment, each of which
states that exactly two tables reference the campaign. Question 3 said "do not
assume this list is complete", and `## Fix` claims the list was derived by
reading every `REFERENCES email_campaigns` in `migrations/` — that scan returns
three matches. `outbound_queue` and `email_events` were checked independently
and are genuinely clear: neither carries a campaign reference in any form.

**Nothing is at risk today.** The send worker's campaign-sent event is the only
writer of that column, and it fires only during a real send, so a `draft` — the
only status `Delete` accepts — can never own such a row. The delete can neither
fail nor orphan. But the third reference behaves differently *in kind* from the
two that are documented: `SET NULL` silently rewrites rows in what PRD §6.11 and
migration `000022`'s own header describe as an append-only log, rather than
removing them. A reader who trusts the current doc comment would not know that.

**Remedy.**

- In `mailing.CampaignStore.Delete`'s doc comment, replace the sentence
  beginning "Two tables carry a foreign key into" with a three-table
  enumeration naming `campaign_interests` (`CASCADE`, `000017`), `email_sends`
  (`CASCADE`, `000017`) and `subscriber_events` (`SET NULL`, `000022`). State
  that `subscriber_events` is nulled rather than cascaded, that this is why the
  delete can neither fail nor orphan, and that no draft can hold such a row
  today because the send worker's campaign-sent event is that column's only
  writer.
- Apply the same correction to `## Fix`'s "Referential integrity (question 3)"
  paragraph.
- Extend `TestCampaignStore_Delete_CascadesReferencingRows` to seed a
  `subscriber_events` row against the same throwaway campaign it already
  creates, and assert that after `Delete` the row still exists with
  `campaign_id IS NULL`. Acceptance criterion 4 requires the proof test to
  create the referencing rows first, and this is the reference whose behaviour
  differs from the two already proved. Seed it against the test's own campaign,
  never a literal id (CLAUDE.md §8b).
- **Do not add a migration.** `SET NULL` is the correct behaviour for that
  column and nothing about the schema needs to change.

### 2. The route-ordering justification is false — measured, not inferred

`cmd/opencircuit/main.go`'s comment above the new registration states that
registering the campaigns DELETE earlier "would genuinely remove that campaign

- The workshops DELETE is **not** ordered last — it is registered ahead of that
  family's announce and preview routes — and the wiring test's own workshop
  fixture comment says the opposite of what is attributed to it: that DELETE

- **Measured.** In a throwaway worktree at the reviewed commit, with the
  campaigns DELETE moved to the earliest position in its family (immediately

The ordering itself is harmless and may stay. The **comment** must not, because
it invents a cross-file coupling that a later agent would then preserve or work
around — the hidden-semantics hazard, made real by being written down.

**Remedy.** Delete the justification comment above the DELETE registration and
fold the route into the existing `adminCampaignsH` block alongside the other
item verbs. If the separate block is kept for diff hygiene, replace the comment

### What I verified and found sound — do not redo it

- **The boundary is a real mirror, and the criteria constrain it only partly.**
  `Update` refuses a slug change unless status is `draft`; `Delete` accepts only
  `draft`. Same single status, independently read from both gates. The criteria
  fix two of the four edges themselves — question 1 requires `sent` to be
  undeletable, question 2 defers `sending` to `Cancel` — and leave the rest to
  the implementer, so draft-only is a choice the implementer was entitled to
  make and made consistently with `#0410`. `withheld` is correctly identified as
  the existing non-destructive lever for a sent campaign, so criterion 2 holds:
  no archive page can be broken by this feature.
- **No test targets a literal or seeded id.** Every store-level and
  handler-level test creates its own campaign through `store.Create` with a
  unique name, and `TestCampaignStore_Delete_CascadesReferencingRows` seeds its
  own interest and its own send row against that campaign. The two not-found
  tests use an id far past any sequence, which targets nothing.
- **Audit.** The new action is written on success only;
  `TestAdminCampaigns_Delete_IllegalFromScheduled` asserts a refused delete
  writes no row and leaves the status unchanged, and
  `TestAdminCampaigns_Delete_DraftSucceeds` asserts exactly one row of the new
  action. That matches the convention the interests and workshops delete
  handlers already follow. The handlers package's audit-metadata guard passes
  for the right reason: the entry is an inline composite literal whose metadata
  map the guard can resolve, and it carries no address-shaped key.
- **404 vs 409 is not a disclosure problem here.** The route is behind session
  plus admin, and an admin can already list every campaign, so distinguishing
  "no such campaign" from "not a draft" reveals nothing the same caller cannot
  read directly. This is not the uniform-`202` case CLAUDE.md §9 protects.
- **The plain confirm modal is the right call.** A draft has never sent or been
  scheduled, so the typed-subject confirmation used for resume — which un-trips
  a breaker after real mail went out — would be ceremony without a matching
  risk. It matches the workshop editor's delete dialog, and the offer gate is
  cosmetic only: the server refuses independently of what the console shows.
