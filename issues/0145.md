## Description

`#0056`'s announce draft emits a "Sign up" link only when the workshop has an external `signup_url`. It never links to the workshop's own page on the site.

So a workshop with no third-party RSVP — the ordinary case for anything run in-house — produces an announcement email that describes the event and gives the reader nowhere to go. The workshop detail page exists (`#0054`), is publicly reachable at `/workshops/{slug}`, and is exactly what a reader wants next.

## Acceptance criteria

- [x] The announce body always links to the workshop's own page at `/workshops/{slug}`, built from the configured base URL rather than a hardcoded host
- [x] The external `signup_url`, when present, is still surfaced as the primary action — the site link supplements it rather than replacing it
- [x] A test covers both shapes: with and without `signup_url`
- [x] `ISSUE=0145 scripts/check.sh go ./internal/handlers/...` passes

## Notes

Filed from `#0056`'s phase-3 review, which noted PRD §8 asks only for title, summary, date, and location in the announce body — so this is a gap in the specification as much as in the code, and worth deciding rather than silently adding.

The draft is fully editable before sending, so an attentive admin can paste the link by hand. That is the argument for it being low severity, and also the argument for fixing it: a shortcut whose output needs hand-editing every time is not much of a shortcut.

## Root cause

`announceBodyMD` only ever wrote a `[Sign up](...)` link, and only when
`wk.SignupURL` was set. PRD §8's acceptance criterion for the pre-filled
body genuinely doesn't mention a link at all (title/summary/date/location
only), so this wasn't a bug against spec — but a workshop run entirely
in-house (the ordinary case; `signup_url` is for a third-party RSVP tool)
produced a draft describing an event with no way for the reader to act on
it, which fails this file's own binding goal: a draft an admin would send
unedited.

## Fix

`announceBodyMD` now takes `baseURL string` as a second parameter and
always appends a `[View this workshop](baseURL + "/workshops/" + wk.Slug)`
link via the new `announceWorkshopURL` helper — the same
`"/workshops/"+slug` shape `internal/seo`'s sitemap, OG tags, and JSON-LD
already build canonical URLs from (`internal/seo/seo.go`, `sitemap.go`,
`jsonld.go`), so this isn't a new URL convention. `strings.TrimRight(baseURL,
"/")` guards against a double slash if `baseURL` ever carries a trailing
one (it shouldn't — `config.normalizeBaseURL` already strips it — but the
guard costs nothing and is exercised by its own test).

When `SignupURL` is set, the external link is emitted first as `[Sign
up](...)`, keeping it the primary action per the acceptance criterion, and
the site link follows as `[View this workshop](...)`, offered second so the
two don't read as duplicate CTAs. When unset, the site link is the only
call to action, which is the actual fix — the reader now always has
somewhere to go.

**Threading `baseURL` in.** `AdminWorkshopsHandler` had no config value on
it before this change (only `store`/`invalidator`/`campaigns`/`auditor`).
Rather than reach for a package-level global or read `os.Getenv` directly
inside `admin_workshop_announce.go` — both of which would make the handler
untestable without real environment state — a `baseURL string` field was
added to the struct and `NewAdminWorkshopsHandler` gained a fifth
parameter, mirroring the existing `NewAdminCampaignPreviewHandler(...,
baseURL, listDomain, fromAddr string)` pattern already used for the same
`config.Config.BaseURL` value elsewhere in this package. This is the one
part of the change with a wider blast radius than the body-builder file
itself: every call site of `NewAdminWorkshopsHandler` needed the extra
argument. All four were production or test wiring, not behavior:
`cmd/opencircuit/main.go` (`cfg.BaseURL`), `cmd/opencircuit/seo_wiring_test.go`
and `cmd/opencircuit/admin_wiring_test.go` (`cfg.BaseURL`, both already had
`cfg` in scope), and `internal/handlers/admin_workshops_test.go`'s
`adminWorkshopsMux` test helper (`"https://example.com"`, matching this
package's existing test-baseURL convention in `logging_test.go`).

`internal/handlers/admin_workshops.go` (owned by #0138's concurrent
reviewer per the dispatch note) was not dirty when this change started or
when it was committed — `git status`/`git diff --cached --name-only` were
checked both before editing and immediately before commit, and only this
batch's files were staged.

### `wk.Slug` as a URL path segment — ruling: trustworthy, and provably so

`#0138` spent two passes on "a value reaches a URL unvalidated", so this deserved
more than a shrug. The implementer relied on `workshops.Store`'s `slugify`
without re-validating. That reliance is sound, for reasons that are structural
rather than conventional:

1. **`slugify` is an allowlist, not a denylist.** `internal/workshops/store.go:138`
   is `regexp.MustCompile("[^a-z0-9]+")`, applied as
   `ReplaceAllString(strings.ToLower(title), "-")` then `strings.Trim(…, "-")`,
   with `"workshop"` substituted when the result is empty. The character class is
   ASCII-only, so **every** byte outside `[a-z0-9]` — including every character
   that could break out of a Markdown link target — is replaced, not escaped.
   The output alphabet is exactly `^[a-z0-9]+(-[a-z0-9]+)*$`.
2. **There is exactly one writer.** `INSERT INTO workshops (slug, …)` at
   `store.go:588` is the only statement in the repo that writes the column;
   `UPDATE workshops` at `store.go:654` sets eleven columns and deliberately not
   `slug` (documented as immutable). `CreateInput`/`UpdateInput` have no `Slug`
   field, so an admin cannot supply one. The collision suffix appended by the
   retry loop is `-2`, `-3`, … — digits, still in the alphabet. Migration
   `000020` backs it with `slug TEXT UNIQUE NOT NULL`.
3. **Verified empirically, not just read.** A reviewer probe ran `slugify` over
   fifteen hostile titles and asserted every result against the allowlist regexp:
   `"a) [evil](http://attacker.example"` → `a-evil-http-attacker-example`;
   `"Workshop <script>alert(1)</script>"` → `workshop-script-alert-1-script`;
   `"../../etc/passwd"` → `etc-passwd`; `"?q=1#frag"` → `q-1-frag`;
   `"TITLE\nWITH\tCONTROL\x00CHARS"` → `title-with-control-chars`;
   `"Café Ünïcode Ω 日本語 Ⅻ"` → `caf-n-code`; `"%20%2F"` → `20-2f`;
   ``"a\\b\"c'd`e"`` → `a-b-c-d-e`; `"---"` and `"!!!"` → `workshop`. All
   fifteen matched. No case produced a character needing percent-encoding or
   Markdown escaping.

So `announceWorkshopURL`'s plain concatenation is safe **today**, and safe for
the right reason — the alphabet is constrained at the only point of creation, not
merely by habit. For the record, a probe confirmed what would happen if that ever
stopped being true: a slug of `a) [evil](http://x` renders
`[View this workshop](https://h/workshops/a) [evil](http://x)`, i.e. a clean
break-out into an attacker-controlled second link. That is a hypothetical about a
future change, not a defect in this one, and the correct place to defend it is
`slugify` (where it already is) rather than a second escape at the call site.

This is materially different from `#0138`'s situation: there the value reached a
URL with nothing constraining it; here an allowlist regexp at the single write
path is the constraint.

than demanding an action, which is exactly what you want for a secondary link
sitting under a primary "Sign up". Putting the external RSVP first is also right —
it is the step that actually gets someone a seat, and the site link reads as
"more detail" rather than a competing CTA. No change requested.
