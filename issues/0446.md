## Description

`internal/db`'s `TestNoOpenIssueEvidenceCitesGoFileByLineNumber` enforces
`#0352`'s ban on Go-file-plus-line-number citations in issue evidence. It scans
only the sections named in `issueCitationSectionHeaders`, which holds
`verification`, `implementation notes`, `fix pass`, `review notes`, and three
older spellings.

**`## Work log` is not among them** — and `## Work log` is where this repo's
phase-2 convention puts implementer evidence. `Issues.md` asks for it there, and
every implementation pass this session has written one.

Found by `#0443`'s reviewer, which caught a banned citation sitting in that
issue's `## Work log` while the guard ran green over it. The reviewer removed
the citation by hand and disclosed it rather than bouncing, since the sentence
already named the enclosing declaration and nothing was falsified.

## Why this is a real gap and not a technicality

The guard exists because a line number goes stale the moment anything above it
moves, and a stale citation is worse than none — it points confidently at the
wrong code. The reviewer's characterisation is the right one: **the guard misses
exactly the text it exists for**, and there is no intent to dodge anywhere in
it. Implementers write their evidence in the conventional place and the guard
looks elsewhere.

It is also self-concealing. Because the section is out of scope rather than
exempt within it, a passing run is not evidence the issue file is clean — which
is precisely the fail-open shape `#0428` closed in a different guard this
session.

## Acceptance criteria

1. `## Work log` is scanned by `TestNoOpenIssueEvidenceCitesGoFileByLineNumber`
   alongside the existing sections.
2. **Sweep the tracker before you assume this is a one-line change.** Every open
   and in-progress issue's `## Work log` now becomes subject to the guard, and
   this session alone added dozens. Fix what the sweep finds — a citation is
   corrected by naming the enclosing declaration, which is what `#0352`
   prescribes, not by deleting the sentence.
3. Check whether `issueCitationSectionHeaders` is consulted by **more than one**
   guard. `TestIssueCitationGuardScansEvidenceSectionsNotSubjectMatter` and
   `TestNoOpenIssueVerificationCitesUndefinedTestFunction` are in the same
   family; widening a shared list widens all of them at once, and that may be
   right or may surface unrelated failures. Say which you found.
4. Consider whether the list should be **inverted** — scanning every section
   except an explicit exempt set (`## Description`, `## Relation`), rather than
   an allowlist that goes stale whenever the issue template gains a section.
   The allowlist's failure mode is silent under-scanning, which is this defect.
   Decide, record the decision, and do not build both.
5. **No new mechanism** beyond the change to the existing guard (`#0258`,
   `#0437`'s criterion 5). One list, one decision.

## Review notes

**PASS.** All five criteria met. Every load-bearing claim was re-derived
independently rather than read off the work log; two of them turned up
evidence the implementation pass did not have, and both support its
conclusions.

### Criterion 1 — the widening bites, proved by mutation before and after

The concern with criterion 2's zero result is that a broken sweep and a clean
corpus return the same answer, so the widening was proved by planting rather
than by reading the map. Two throwaway `git worktree` checkouts were made at
the commit under review and at its parent, `git worktree remove`d afterwards
(CLAUDE.md §8a — the shared tree was never touched, and `git status` before
and after shows only the two files other agents have dirty). An identical
scratch issue file, status `in-progress`, carrying one Go-file-plus-line-number
citation under a `## Work log` heading, was written into each worktree's
`issues/` directory:

- **at the parent commit**, `TestNoOpenIssueEvidenceCitesGoFileByLineNumber`
  reported `ok` — the citation was invisible, exactly the defect this issue
  describes;
- **at the commit under review**, the same test fails, naming the scratch
  file, the line, and the citation itself.

The same experiment run with a dangling `Test…` identifier in place of the
citation gives the matching result for the sibling family:
`TestNoOpenIssueVerificationCitesUndefinedTestFunction` reports `ok` at the
parent and fails naming the identifier at the commit under review. So the map
entry is live in both guard families, not merely present.

### Criterion 2 — the sweep re-derived, and the zero is a real zero

Re-derived with a standalone `python3` script over bytes (never BSD `grep -P`,
CLAUDE.md §8), reimplementing `issueSectionTitle`, `extractNamedSections`,
`issueStatus`, `issueLineCitationPattern` and both exemption predicates:

- 454 `issues/*.md` files read, 33 with an `open`/`in-progress` status row;
- of those, **18 files carry 19 `## Work log` sections totalling 23,084 bytes**
  of newly-scanned body — so the extractor is demonstrably reaching real text;
- **zero** raw pattern hits in any of them, exempt or otherwise.

The number that makes the zero trustworthy is the same scan with the status
filter removed: **41 Go-file-plus-line-number citations sit in `## Work log`
sections corpus-wide**, spread across 17 issue files — every one of them in a
`resolved` file, which both guards exclude by design and for the reason
`#0265` gives. The class is abundant historically; the currently in-scope set
is genuinely clean. A broken extractor would have found none of the 41.

Across all eight admitted sections the same sweep finds exactly one hit in the
in-scope set, in `issues/0258.md`'s fix pass, and it is correctly exempt under
the toolchain-diagnostic predicate. Nothing needed correcting, so the
implementer's decision to leave `issues/0451.md` and the other dirty files
alone (§8a) never had to be exercised.

### Criterion 3 — the sharing is real, and nothing unrelated broke

Confirmed by reading rather than by report: `issueCitationSectionHeaders` and
`extractNamedSections` are declared in `internal/db`'s Test-name-citation
guard file, and `scanIssueDirForLineCitations` in the sibling
go-file-line guard file calls `extractNamedSections` directly. One map, both
families — which the before/after mutation above then demonstrates
behaviourally rather than structurally. The scoped verification run below is
green over both packages with zero skips, so no unrelated guard was disturbed.

### Criterion 4 — the decision not to invert is accepted, now with a measurement

The recorded reasoning is that every admission in this map rests on a corpus
measurement while inversion rests on none. That is a fair statement of
`#0268`'s standard, but the argument for *declining* was itself unmeasured, so
the counterfactual was measured here: for every `open`/`in-progress` file,
which level-2 headings are **not** admitted, and how many banned-shape
citations sit under each.

The result cuts both ways and lands on the same conclusion.

- **Against the recorded reasoning:** inverting to "scan everything except
  `## Description` and `## Relation`" would newly flag exactly **one**
  citation in the whole in-scope corpus — a `## Design` section in
  `issues/0393.md` proposing where code should go, quoting a line *range*
  rather than asserting evidence. One new false flag is not the wave of
  over-scanning noise the doc comment implies.
- **For it, decisively:** the unadmitted set is **47 distinct heading
  spellings** across those 33 files, and roughly 45 of them are one-off
  narrative headings written for a single issue — several of them full
  sentences. An exempt set would have to enumerate that tail correctly on the
  first try and stay ahead of every future one-off heading, which is a
  strictly harder maintenance problem than adding a row to an allowlist when a
  template section gains evidence.

So the decision stands, for a better reason than the one recorded: not that
inversion is noisy today (it is not, measurably), but that **the exempt set is
not enumerable** while the admitted set is small, stable, and template-backed.
Criterion 4 asked for a decision and a record, not for both to be built, and
the decision is the right one. The measurement is recorded here so the next
agent revisiting this has the number rather than an intuition.

### Criterion 5 — no new mechanism

One map entry, one new test reusing the existing shared scanner, and
assertions added to two existing tests. No new predicate, no new extraction
path, no in-file self-check of the kind `#0258` warns against. Confirmed by
reading the diff.

The new test is a legitimate in-package oracle under CLAUDE.md §8's rule:
removing the map entry makes `TestIssueLineCitationGuardScansWorkLog`'s
fixture stop being extracted and the assertion fails, so the check stays
falsifiable by the thing it measures. It asserts against
`scanIssueDirForLineCitations` rather than against the map, which is what also
catches a future narrowing of `extractNamedSections` made independently of the
map.

### The self-referential trap (`#0392`)

This issue's own `## Work log` is in scope for the guard it changes, and so
are these notes. Both were byte-scanned with `python3` against the guard's own
pattern before committing: `issues/0446.md` carries **zero** matches of the
banned shape anywhere in the file, and neither guard file carries one in a Go
*comment* — the one concrete example lives in
`TestIssueLineCitationGuardScansWorkLog`'s fixture as a string literal, which
is `#0384`'s prescribed home for exactly this. The prose in both the work log
and these notes names the shape instead of writing it.
