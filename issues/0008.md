## Description

Prove that registration, login, recovery, session handling, and credential management all still work under the new module path and domain — before any new feature depends on them.

## Acceptance criteria

- [ ] Registration: email → magic link → `navigator.credentials.create()` → account + session, verified in a browser
- [ ] Login: both the conditional-UI autofill path and the explicit sign-in button issue a session
- [ ] Recovery: magic link adds a new credential to an existing account without creating a duplicate user
- [ ] Credential rename and revoke work, and revoking the last credential is refused with `409 cannot_revoke_last_credential`
- [ ] Session cookie is `HttpOnly; Secure; SameSite=Strict` with the 30-day sliding window intact
- [ ] `RequireSession` and `RequireAdmin` reject correctly (401 / 403)
- [ ] Rate limiter still applies to the auth endpoints
- [ ] Audit rows are written inside the ceremony transaction for every auth action
- [ ] `go test ./internal/auth/... ./internal/middleware/... ./internal/handlers/...` passes and the test names are recorded in `## Verification`

## Notes

PRD §3.1. This is a verification issue, not a rewrite — the expectation is that little or no auth code changes. If something is broken, it is almost certainly the module path rewrite or a route registration lost in #0002.

`WEBAUTHN_RP_ID` is the apex `opencircuitsf.com` so a passkey stays valid across apex and `www`. **`WEBAUTHN_RP_ORIGIN` is `https://www.opencircuitsf.com`** — www is the canonical host as of the 2026-08-18 deploy, and the origin must match the host the browser is actually on. Locally both are `localhost`. A mismatch between `WEBAUTHN_RP_ORIGIN` and the browser's actual origin fails the ceremony with an opaque error — check this first when a ceremony fails.

The `descope/virtualwebauthn` dependency drives the ceremony tests without a browser; keep it.
