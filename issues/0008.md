## Root cause

Nothing in the auth port itself was broken: `internal/auth`, `internal/middleware`, and `internal/handlers` already had a large, passing test suite covering registration, login, recovery, credential rename/revoke, session cookie attributes, `RequireSession`/`RequireAdmin`, the rate limiter, and ceremony-transaction audit writes. The real gap was that the suite's proof of *which relying party* it was exercising was hollow. `#0066` pointed the ceremony tests at this project's RP values, but `testRPID`/`testRPOrigin` (`internal/auth/registration_test.go`) feed **both** the server's `webauthn.Config` (via `newService`/`newLoginService`) **and** the `virtualwebauthn.RelyingParty` the fake authenticator signs with. Both sides are built from the same two Go constants, so they are self-consistent by construction and never cross-checked against an external oracle — the suite would stay green if those constants were set to any other single (wrong-but-consistent) domain pair, and it would also stay green under a same-shaped apex/www swap (RP_ID = `www.opencircuitsf.com`, RP_ORIGIN = `https://opencircuitsf.com`), since nothing in the ceremony itself distinguishes "correct" from "internally consistent." A green `internal/auth` suite was therefore not evidence the relying party matched `opencircuitsf.com` / `https://www.opencircuitsf.com`.

## Fix

Added `internal/auth/relying_party_test.go` with four tests anchored to their own literal constants (`prodRPID = "opencircuitsf.com"`, `prodRPOrigin = "https://www.opencircuitsf.com"`), never reusing `testRPID`/`testRPOrigin`:

- `TestNewWebAuthn_ConfiguredRPPinsProductionApexAndWWW` — builds a `config.Config` from the literals, calls `NewWebAuthn`, and asserts the constructed `*webauthn.WebAuthn`'s `Config.RPID` and `Config.RPOrigins` equal the apex and the `www` origin exactly (read off the constructed instance, not off the test's own constants), plus an explicit assertion that `RPID != RPOrigins[0]`.
- `TestFinishRegistration_RejectsOriginOutsideConfiguredScope` and `TestFinishLogin_RejectsOriginOutsideConfiguredScope` — drive real ceremonies (start → verify → finish) with a `virtualwebauthn.RelyingParty` whose `Origin` is `https://evil.example` (RP ID unchanged, isolating the check to the origin), asserting `FinishRegistration`/`FinishLogin` return an error and, for registration, that no `passkey_credentials` row lands.
- `TestCredentialRegisteredUnderApexRPID_ValidForWWWOrigin` — the direct pin for the apex/www relationship called out in the issue: registers and then logs in with the same credential end-to-end using RP ID = the bare apex and origin = the `www` host, with the two literal strings staying unequal throughout. This is the exact ceremony a real browser on `www.opencircuitsf.com` runs, and it's the reason `RP_ID` is the apex rather than a specific host (CLAUDE.md §7).

No production code changed — the finding was entirely in test coverage, exactly as the issue's Notes anticipated ("little or no auth code changes").

## Gotchas

- **`ValidateRPID` accidentally catches one but not both transposition shapes.** A scheme-bearing RPID (e.g. accidentally assigning the origin string to `WEBAUTHN_RP_ID`) fails fast at `NewWebAuthn` with a clear error. A same-shaped swap (RP_ID = a bare `www.` host, RP_ORIGIN = the bare apex with a scheme) is syntactically valid on both sides and passes `NewWebAuthn` silently — only the literal-value assertion in `TestNewWebAuthn_ConfiguredRPPinsProductionApexAndWWW` catches it. Don't rely on config validation alone to catch a real-world apex/www misconfiguration.
- **go-webauthn does not itself enforce "RPID must be a registrable-domain suffix of the origin."** That check is a browser/platform-authenticator responsibility before the ceremony ever reaches the server; go-webauthn only checks (a) the assertion's RP-ID hash equals `SHA256(configured RPID)` and (b) the assertion's origin is a member of the configured `RPOrigins` list. `virtualwebauthn` mirrors this — it will happily sign an attestation for any RP ID/origin combination given to it, valid or not per real browser rules. This means the apex/www *suffix relationship* itself is not something a Go-level test can independently verify; `TestCredentialRegisteredUnderApexRPID_ValidForWWWOrigin` proves the server-side half (apex RPID + www origin ceremony succeeds, with the two strings kept unequal throughout) but the browser-enforced half is one more reason the two "verified in a browser" acceptance criteria genuinely need a human.

## Manual verification required

The two acceptance criteria that name "verified in a browser" cannot be driven from this environment — there is no way to trigger a real WebAuthn platform authenticator prompt (Touch ID / Windows Hello / a security key) from a Go test or a headless agent. They are left **unticked** above and require a human with a real browser and a real authenticator. Run this against the **Postgres** path, not `STORAGE=json` dev mode — dev mode bypasses the ceremony entirely via `internal/devstore.DevRegistrar`/`DevRecoverer` and `middleware.DevAutoLogin`, so it proves nothing about the real flow.

**Production mailer note:** `servePostgres` in `cmd/opencircuit/main.go` wires `auth.NoOpMailer{BaseURL: cfg.BaseURL}` (see `internal/auth/mailer.go`). It does **not** silently drop mail — every call `log.Printf`s the full magic-link URL to the server's stdout, e.g. `NoOpMailer: verification email to alice@example.com: http://localhost:8080/register/verify?token=...`. Read the link from the terminal running `opencircuit serve`.

Setup:

```bash
# 1. Ensure the opencircuit (not opencircuit_test) database exists and is migrated.
migrate -path migrations -database "$DATABASE_URL" up

# 2. Start the server against Postgres, RP values matched to localhost, mailer to stdout.
export STORAGE=              # unset/empty — NOT "json" — so servePostgres runs, not dev mode
export DATABASE_URL='postgres://opencircuit:opencircuit@localhost:5432/opencircuit?sslmode=disable'
export BASE_URL='http://localhost:8080'
export WEBAUTHN_RP_ID='localhost'
export WEBAUTHN_RP_ORIGIN='http://localhost:8080'
export SESSION_SECRET="$(openssl rand -hex 32)"
export ADMIN_EMAIL='you@example.com'          # use the email you'll register with
export AWS_REGION='us-west-2'
export EMAIL_FROM='Open Circuit SF <hello@opencircuitsf.com>'
cd web && npm run build && cd ..
go run ./cmd/opencircuit serve
```

**Registration (email → magic link → `navigator.credentials.create()` → account + session):**

1. Open `http://localhost:8080` in a real browser (Chrome/Safari with a platform authenticator, or a browser with a security key attached) and go to the registration/sign-up view.
2. Submit the email matching `ADMIN_EMAIL` above.
3. In the terminal running `opencircuit serve`, find the line `NoOpMailer: verification email to <email>: http://localhost:8080/register/verify?token=<token>` and copy that URL.
4. Paste the URL into the browser. The SPA should load `/register/verify`, call `GET /auth/register/verify?token=...`, and trigger the browser's passkey creation prompt (`navigator.credentials.create()`).
5. Complete the platform/security-key prompt. Expect: redirect into the authenticated account view, a `sessions` row created, and (first user) `is_admin = true`.
6. Confirm in Postgres: `SELECT email, is_admin FROM users;` and `SELECT COUNT(*) FROM passkey_credentials;` — both should reflect the new account and one credential.

**Login — explicit sign-in button:**

1. Log out (or open a fresh browser profile), go to the login view, click the explicit "Sign in" button (not autofill), and complete the passkey prompt.
2. Expect: a new `sessions` row, redirect into the account view.

**Login — conditional-UI autofill path:**

1. On the login view, click into the email/username `<input>` field **without** clicking any sign-in button. Chrome/Safari should show the OS-level passkey autofill suggestion (the browser's native picker) if the field is wired with `autocomplete="webauthn"` and the page called `navigator.credentials.get()` with `mediation: "conditional"`.
2. Select the passkey from the autofill suggestion and complete the prompt.
3. Expect: same result as the explicit path — a session is issued without ever touching a submit button. This is the one path that has **no non-browser proxy at all**: the mediation behavior is entirely a browser/OS UI feature.

Record the outcome (pass/fail, browser + OS + authenticator used) directly on this issue before the reviewer sets `resolved`, since both criteria are gating and neither is covered by the automated suite.
