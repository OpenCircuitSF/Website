## Description

`#0416` committed the two live workshop cover images, which had existed only on
the server. Validating them surfaced two differences between them:

| File | Dimensions | Notes |
|---|---|---|
| `web/public/soldering.jpg` | **1200×630** | correct Open Graph card size, no EXIF payload |
| `web/public/programming_leds.jpg` | **600×450** | wrong aspect and half the width; carries Exif |

### The dimensions

1200×630 is the Open Graph card size, and it is what `soldering.jpg` uses.
`programming_leds.jpg` is 600×450 — a 4:3 photo rather than a 1.91:1 card.
Unfurlers letterbox or centre-crop it, and 600 px wide is below the width most
treat as qualifying for `summary_large_image`, which is the card type this site
declares. So the workshop using it gets a visibly worse preview than the one
next to it.

### The metadata

`programming_leds.jpg` carries an Exif block naming the capture device
(`Apple`, `iPhone 16`), the software version, and the capture timestamp
`2026:08:31 20:10:43`. It is served publicly at
`https://www.opencircuitsf.com/programming_leds.jpg`.

Nothing here is dangerous — no GPS tags were present in the header dump — but
device and timestamp metadata is conventionally stripped from published web
images, and this site is otherwise deliberate about not leaking incidental data
(§9 forbids third-party analytics and trackers for the same reason).

**Confirmed by the orchestrator** with `file(1)` against the committed bytes,
which are byte-identical to production by sha256.

## Resolved by decision and by action, 2026-09-05

### Dimensions — the user's decision: leave at 600×450

> "The current resolution is fine. I can provide better images in the future.
> We do not need 1200px. It is normally seen on a mobile phone anyway."

So criterion 1 is **withdrawn**, not deferred. The reasoning is sound and worth
recording so nobody re-files it: link previews are predominantly rendered on
phones, where a 600 px source is adequate, and better originals may arrive
later. The asymmetry with `soldering.jpg`'s 1200×630 stands as a known,
accepted difference.

### EXIF — stripped

Done directly at the user's instruction ("Yes, strip the EXIF data").

The box has neither `exiftool` nor Pillow, so this was **lossless JPEG segment
surgery** in `python3` rather than a re-encode: drop the `APP1` (Exif/XMP) and
`APP13` (IPTC) segments, keep `APP0` (JFIF) and all image data untouched.

| | Before | After |
|---|---|---|
| Bytes | 66,301 | **63,253** |
| `Exif` marker | present | **absent** |
| `iPhone` string | present | **absent** |
| Dimensions | 600×450 | **600×450** |
| Valid SOI/EOI | yes | **yes** |

Removed: `APP1` 2,988 bytes, `APP13` 56 bytes. No GPS tags were present at any
point. The original is kept at `/tmp/programming_leds.jpg.bak` on the box.

Verified served: `200`, `Content-Length: 63253`, `Content-Type: image/jpeg`.

**One consequence worth knowing.** `/media/` carries `Cache-Control: max-age=604800`,
so a client that already fetched the file keeps the EXIF-bearing copy for up to
a week. `docs/media.md` records that renaming is how that cache is busted; that
was judged not worth doing for metadata removal, since nothing sensitive was
present — no GPS — and the file is small.

### Remaining scope

**None.** Criterion 1 is withdrawn by decision; criterion 2 is done; criteria 3
and 5 were already void per the `#0416` reversal. `soldering.jpg` was checked
and carries no `APP1`.

## Verification (implementation pass, 2026-09-05)

Independently re-verified the strip and checked the whole carve-out, without
touching the box. Method: fetched each file over HTTPS, walked the raw bytes

**Every file the carve-out serves** — `/var/www/media` holds exactly two
files, matching `cover_image` on the `workshops` table:

| File | Bytes (disk / served) | `APPn` segments present | SOF dimensions |
|---|---|---|---|
| `programming_leds.jpg` | 63,253 / 63,253 | `APP0` (JFIF), `APP2` (ICC color profile — see note) | 600×450 |
| `soldering.jpg` | 89,179 / 89,179 | none | 1200×630 |

Neither file carries `APP1` (Exif/XMP) or `APP13` (IPTC). A raw-byte scan of
the full contents of both files for the literal strings `Exif`, `iPhone`, and
`Apple` came back negative for both. No text search was used for the
marker-presence claim itself — the table above comes from walking the marker
stream (`FFD8` SOI → segments by marker byte → `FFD9` EOI) and reading
width/height straight out of the `SOF0` payload, not from any tool that might
normalize them.

**Note on `programming_leds.jpg`'s `APP2`:** it is a standard `ICC_PROFILE`
color-management segment (26,692 bytes, signature `ICC_PROFILE\0` at its
start) — not Exif, not IPTC, and it contains no device, location, or
timestamp data. It is outside criterion 1's scope (`APP1`/`APP13` only) and
is not a metadata leak; noting it here only because criterion 3 asks to check
every segment, not just the ones already suspected.

**Incidental finding, not acted on:** `soldering.jpg` carries a `COM` (0xFFFE)
segment reading `Lavc62.28.10` — a libavcodec version string, evidence the
file passed through an ffmpeg-based pipeline at some point. No personal or
device metadata. Not in scope here (criteria 1/3 are about `APP1`/`APP13`
specifically) and not `#0433`'s scope either (that issue is about future
uploads, not these two existing files). Recording it in case a future pass
wants to fold "strip `COM` too" into the metadata-hygiene story; not filing an
issue for it since it discloses nothing sensitive.

**`cover_image` resolution** — `workshops` rows on production:

## Review notes (2026-09-05)

**Pass.** No code changed; the commit under review is `5a3846c`, the issue file
alone. Every claim was re-derived here rather than read, and all four checks the
review was scoped to came back clean.

### 1. Exif absence, re-parsed over the live HTTPS bytes

Fetched each URL and walked it as a marker stream in `python3` — `FFD8`, then
segments by marker byte with fill-byte handling, stopping at `SOS` — reading
width and height straight out of the `SOF0` payload. No text search was used to
establish any marker claim, and BSD `grep -P` was not used at all (§8: it reports
zero hits on bytes that are present, which is the wrong tool for proving a
negative).

| File | Served bytes | Full segment stream | `APP1` | `APP13` | SOF dimensions |
|---|---|---|---|---|---|
| `programming_leds.jpg` | 63,253 | `APP0` (JFIF), `APP2` (`ICC_PROFILE`, 26,692), `SOF0`, 4×`DHT`, 2×`DQT`, `DRI`, `SOS` | absent | absent | **600×450** |
| `soldering.jpg` | 89,179 | `COM` (`Lavc62.28.10`), `DQT`, `DHT`, `SOF0`, `SOS` | absent | absent | **1200×630** |

Both open `FFD8` and end `FFD9`, and both `Content-Length` values match the
on-disk sizes exactly. A raw-byte membership test — bytes, not a pattern engine —
for `Exif`, `iPhone`, `Apple`, `GPS`, and the XMP namespace URI came back absent
on both files, all five needles. Both also decode: converted to PNG through the
system image pipeline at their stated dimensions, which is a real decode of the
entropy data rather than a header read. Criteria 1 and 2 met.

### 2. The file list is complete

Read-only `ssh ec2 'ls -la /var/www/media'` shows the directory holds exactly
two regular files, `programming_leds.jpg` and `soldering.jpg`, and nothing else —
no backups, no strays. The implementer's list is not quietly short. Criterion 3
met. `cover_image` on production resolves for all three `workshops` rows (ids 1
and 3 to `/media/soldering.jpg`, id 4 to `/media/programming_leds.jpg`), each
returning `200`, `image/jpeg`, and the `Cache-Control`/CSP headers
`docs/media.md` specifies. Criterion 4 met.

### 3. Nothing was changed, and nothing was re-encoded — proved by bytes

Stronger evidence than a read-only claim was available, so it was taken. The
pre-strip original is still on the box; pulled it and the live file down, and
reconstructed the documented surgery locally — drop `APP1` and `APP13` from the
original, keep every other byte:

| | |
|---|---|
| Backup | 66,301 bytes |
| Removed | `APP1` 2,988 + `APP13` 56 |
| Reconstruction | 63,253 bytes |
| Live file | 63,253 bytes |
| **sha256 reconstruction vs live** | **identical** |

The served bytes also hash equal to the on-disk bytes. So the live image is the
original with exactly two metadata segments excised and every remaining byte
untouched — no re-encode, no resize, no quality change, and no second write. The
directory's own mtime predates the strip, so no file has been created or removed
there since. Criteria 5 and 6 met, and the withdrawn criteria stay withdrawn:
600×450 stands by the user's ruling, and the byte-reproducible-from-a-checkout
criterion remains void because the images are deliberately not in the repository.

### 4. The two incidental segments — verdict: no follow-up for either

**The `ICC_PROFILE` `APP2` in `programming_leds.jpg`: leave it.** It is
colour-management data — a transform describing how to interpret the file's
colour values — and carries no device, location, or timestamp. It is not a
privacy or hygiene concern in any sense the original issue was about. Its size is
not a reason either: §5 is explicit that this project has no performance
requirement and no load test, so a 26 KB profile on a 63 KB file is not a defect
to chase, and opening a thread on it would be exactly the mistake §5 names.
Removing it would also be a change with a real downside — the profile is what
makes the colours render correctly on a wide-gamut display, so stripping it
degrades the image to save bytes nobody is counting. The implementer was right to
report it and right not to act.

**The `COM` string `Lavc62.28.10` in `soldering.jpg`: leave it too.** It names
the libavcodec build that wrote the file. That identifies a tool, not a person, a
device, or a place, and it says nothing about the production host — the file was
produced elsewhere and uploaded. There is no disclosure to mitigate. Folding
"strip `COM`" into a future metadata pass would be harmless if it happened for
other reasons, but it is not worth an issue on its own, and this review is not
filing one.

Neither finding changes the outcome, and neither belongs to `#0433`, which is
about stripping metadata from images uploaded through the admin console in
future — not about these two existing files.
