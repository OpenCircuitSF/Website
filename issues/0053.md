## Root cause

Not a bug fix — new feature work. `/workshops` (`WorkshopsIndex.svelte`) and
Home's real "next up" data did not exist yet; the API they consume
(`GET /api/workshops`, #0051) landed just ahead of this issue.

## Fix

- `web/src/lib/workshops.ts` (new): pure, framework-free logic — used by both
  views. `formatWorkshopDate` (RFC 3339 UTC → the viewer's local timezone,
  matching lib/admin.ts's `formatDateTime` convention), `workshopLocationLabel`
  (fallback to "Location TBA"), `isCanceled`/`workshopBadgeLabel` (the
  "Canceled" badge decision), `hasNoUpcoming` (the empty-state decision, keyed
  on `upcoming` alone — an empty `past` list is not "nothing scheduled"), and
  `nextWorkshops`/`NEXT_UP_LIMIT` (Home's next-3 slice, no re-sorting — the API
  already returns `upcoming` in chronological order).
- `web/src/lib/WorkshopCard.svelte` (new): the one workshop card component,
  shared by `WorkshopsIndex.svelte`'s two sections and `Home.svelte`'s "next
  up" section, so a workshop renders identically in both places. Every
  decision routes through `lib/workshops.ts`; the component itself is plain
  markup. Title links to `/workshops/{slug}` — the router (#0014) already
  resolves that to the `workshop-detail` route name; until #0054 builds the
  view, App.svelte's existing catch-all renders its generic "on the way"
  placeholder for it.
- `web/src/views/WorkshopsIndex.svelte` (new): fetches `GET /api/workshops` on
  mount, renders loading/error/loaded states, and the two sections (upcoming —
  with the empty-state + inline `SubscribeForm` when nothing is scheduled —
  and past, shown even when a first-time visitor has nothing else to judge the
  group by, per this issue's own Notes).
- `web/src/views/Home.svelte`: "next up" switched from the static three-item
  `UPCOMING` placeholder to `listPublicWorkshops()` + `nextWorkshops`, with its
  own loading/error/empty states and a "See all workshops" link to
  `/workshops`. Removed the now-dead `.workshop-blurb` style.
- `web/src/App.svelte`: wired the `workshops` route to the new
  `WorkshopsIndex` view; updated the stale comment that referenced #0053/#0054
  together (only #0054/workshop-detail is still a placeholder now).
- `web/src/lib/types.ts` / `web/src/lib/api.ts`: added `PublicWorkshop`,
  `WorkshopsListResponse`, and `listPublicWorkshops()`, matching
  `internal/handlers/public_workshops.go`'s `publicWorkshopView` /
  `workshopsListResponsePublic` exactly.

## Gotchas

- **A tension with #0051's own contract, for that issue's reviewer to
  decide**: this issue's acceptance criteria say "canceled workshops shown
  with a clear canceled badge" for the index. But
  `internal/handlers/public_workshops.go`'s `List` handler (still in review as
  this was written) calls `workshops.Store.ListPublished`, whose own doc
  comment says the index returns ONLY `status='published'` rows — a canceled
  workshop never reaches `GET /api/workshops` at all, only the detail route.
  `isCanceled`/`workshopBadgeLabel` are implemented and unit-tested in
  `lib/workshops.ts` regardless (a `publicWorkshopView` always carries
  `status`, so nothing stops a canceled row from showing up here if that
  handler's behavior changes), and the badge markup is live in
  `WorkshopCard.svelte` — but under the API as committed, it is currently dead
  code on the index path, since the index never receives a canceled workshop
  to apply it to. Documented in `lib/workshops.ts`'s header comment too. Not
  fixed here — #0051 is someone else's in-flight change; flagging it for that
  issue's reviewer to decide whether the index criterion or the handler's
  `ListPublished` contract is the one that needs to change.
- `web/dist/index.html` is a committed minimal placeholder
  (`.gitignore` comment, line ~27); running `npm run build` for the manual
  verification above overwrote it with a real bundle, which had to be
  reverted before committing so as not to accidentally ship — or worse,
  collide with another concurrent agent's — a real `dist/` (CLAUDE.md §8b).

## Review notes — 2026-08-22 (phase 3, APPROVED)

Re-verified independently; nothing below is taken from `## Verification`.

**Verification re-run.** `uptime` first: load averages 2.99 / 3.05 / 3.02 —
idle, so no timing result here is machine noise. `scripts/check.sh web`
→ `VERIFICATION PASSED`: `svelte-check` **219 files, 0 errors, 0 warnings**;
`vitest run` **16 files / 366 tests passed**. Re-ran the new file alone with a
verbose reporter (`npx vitest run src/lib/workshops.test.ts
--reporter=verbose`) and read every assertion: **15 tests, all named and
passing** across the `formatWorkshopDate`, `workshopLocationLabel`,
`isCanceled`/`workshopBadgeLabel`, `hasNoUpcoming`, and `nextWorkshops`
blocks. Also ran a production Vite build to a **scratch outDir** rather than
`web/dist` (`npx vite build --outDir <scratch> --emptyOutDir`) — 192 modules
transformed, clean — which proves the new views bundle without touching the
committed `web/dist/index.html` placeholder or racing the concurrent `#0052`
agent working in `web/`. `git status` after the run showed only
`issues/0053.md` modified. No servers started, no databases created, no
`go test` processes left behind.

**The lib/component split holds (CLAUDE.md's SPA convention).** Every decision
a card or a section makes routes through `web/src/lib/workshops.ts`:
`formatWorkshopDate`, `workshopLocationLabel`, `isCanceled` /
`workshopBadgeLabel`, `hasNoUpcoming`, `nextWorkshops` / `NEXT_UP_LIMIT`.
`WorkshopCard.svelte` is three `$derived` calls into that module plus markup;
`WorkshopsIndex.svelte` holds only fetch state (`'loading' | 'loaded' |
'error'`) and template branching; `Home.svelte`'s "next up" is the same
shape. No comparison or format string is written inline in a component. One
cosmetic asymmetry, not worth a change: the past-section emptiness is an
inline `list.past.length === 0` while the upcoming side goes through
`hasNoUpcoming` — deliberate, since the two mean different things (an empty
`past` is unremarkable, an empty `upcoming` is the subscribe-prompt state).

**The tests assert behavior, not the implementation.** Spot-checked them
against plausible breakages: a `formatWorkshopDate` that returned its input
unchanged would still pass the "start alone" case but fails the
start–end-range case (which requires the en dash); dropping the
`Number.isNaN` guards fails both "Date TBA" cases; `workshopLocationLabel`
is tested against `undefined`, `''`, and `'   '`, so the `.trim()` is load
bearing; `isCanceled` is checked against `'published'`, `'draft'`, `''`, and
`'unknown'`, so a truthiness bug would be caught; `nextWorkshops` pins the
cap at 3, an explicit smaller limit, the negative-limit clamp, and — usefully
— that it does **not** re-sort. One genuine gap, recorded rather than
bounced: no test pins a `TZ` and asserts a concrete formatted string, so the
UTC→local conversion itself is asserted only indirectly (the assertions are
locale-tolerant on purpose). Worth tightening if `#0054` extends this module.

**`Home.svelte`'s four states are all present.** Read the template directly:
`loading` → "Loading…", `error` → a plain "Couldn't load upcoming workshops
right now." (the `.catch` sets it, so an API outage degrades to one line, not
a broken page), `loaded` with `upcoming.length === 0` → "Nothing scheduled
yet — check back soon, or subscribe below.", otherwise the cards. The rest of
the front door (hero, "what this is", subscribe form) is outside the
`{#if}`, so none of it depends on the fetch succeeding. The dead
`.workshop-blurb` style and the `UPCOMING` placeholder are both gone, and
`Panel` is still imported because the subscribe section still uses it (line
106) — not a leftover.

**The TS types match the Go handler field for field.** Compared
`web/src/lib/types.ts`'s `PublicWorkshop` against
`internal/handlers/public_workshops.go`'s `publicWorkshopView` one line at a
time: `slug`/`title`/`status` required on both sides (plain `string`, no
`omitempty`); `summary`, `body_md`, `starts_at`, `ends_at`, `location_name`,
`location_address`, `location_note`, `capacity`, `signup_url`, `cover_image`
are `*T`+`omitempty` in Go and optional (`?`) in TS, with `capacity?: number`
against `*int`; `interests` required on both. `WorkshopsListResponse`
matches `workshopsListResponsePublic` (`upcoming`, `past`, both required).
`PublicInterest` still matches `publicInterestView`
(`slug`/`name`/`description?`/`sort_order`). Both list fields and
`interests` are built with `make([]T, 0, n)` in the handler, so they
serialize as `[]` and never `null` — which is what lets
`hasNoUpcoming(list)` and `workshop.interests.length` be unguarded in the
components.

**Accessibility and the empty state (PRD §7.5).** One `<h1>` per page
(`Workshops`), `<h2>` per section wired with `aria-labelledby`, `<h3>` per
card — no skipped levels, and `SubscribeForm` contributes no heading of its
own so nesting it in the empty-state `Panel` does not break the outline.
`<main id="main-content">` matches the other public views' skip-link target.
The card's ` · ` separator is `aria-hidden`, matching PRD's `[ OK ]`
convention; the tag list is a real `<ul>` with `aria-label="Topics"`. The
empty state degrades well: instead of a bare "nothing here" it renders the
subscribe prompt inline, and the past section still renders its own honest
"No past workshops yet" line. At 375 px the card grid is
`repeat(auto-fit, minmax(220px, 1fr))` inside `.app-shell`'s 16 px padding
— 343 px of usable width against a 220 px minimum track, so it collapses to
one column with no horizontal overflow; `.badge` is `white-space: nowrap`
but short enough not to squeeze the title. **Noted, not bounced:** the
loading and error lines are not in an `aria-live` region, so a screen-reader
user is not told when the fetch resolves or fails. That is the same pattern
the other public views use and it is squarely in `#0063`'s (accessibility
audit) scope, which this issue already blocks — flagging it there rather
than filing a duplicate.

**The unticked criterion.** "Canceled workshops shown with a clear canceled
badge" cannot be satisfied from this side of the wire: `List` in
`internal/handlers/public_workshops.go` calls `workshops.Store.ListPublished`,
which returns only `status='published'`, so a canceled workshop never reaches
`GET /api/workshops` for the badge to apply to. That is now **[#0135](0135.md)**,
which owns the decision and the end-to-end proof. The badge logic this issue
wrote is nevertheless correct for the day the payload carries one: `isCanceled`
matches `'canceled'` and nothing else, `workshopBadgeLabel` returns `'Canceled'`
or `null`, and `WorkshopCard` renders it as `badge badge-danger` (a real
`.badge-danger` class in `app.css`) beside the title. Leaving it unticked here
is right; `#0135` ticks it.

**Known, intentional, not a defect:** cards link to `/workshops/{slug}`, which
the router already resolves to `workshop-detail` but which `#0054` has not
built — App.svelte's catch-all renders its "on the way" placeholder until then.
