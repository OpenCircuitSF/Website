## Description

`#0155` added server-side validation of `workshops.capacity` (`1..2147483647`, with a database `CHECK` behind it). `web/src/lib/workshopAdmin.ts` rejects values `<= 0` but has **no upper bound**, so an admin typing `3000000000` gets a round trip and a server 400 instead of an immediate local message.

The behavior is *correct* — the server is the boundary that matters, and it now answers 400 rather than the 500 it used to. This is a UX gap, not a defect.

Filed because it is the second instance of a Go↔TypeScript rule divergence found this session (after the URL validators), and `#0157`'s review deliberately kept it out of that fixture's scope: it is a UX nicety over an already-correct server boundary, with no computable ground truth — `2147483647` is a choice, not a fact — and it does not fit a `{rule, value: string, want: bool}` schema.

## Acceptance criteria

- [x] `validateWorkshopForm` rejects `capacity > 2147483647` with a message matching the server's, so the admin sees the same rule in both places
- [x] Unit tests cover the boundary: `2147483647` accepted, `2147483648` rejected
- [x] The bound is written once with a named constant and a comment tying it to `migrations/000020`'s `INT` column, so the next person changing one finds the other
- [x] Confirm the lower bound still matches the server's decision from `#0155` — `0` is rejected, not treated as "unlimited"
- [x] `scripts/check.sh web` passes

## Root cause

`validateWorkshopForm` (`web/src/lib/workshopAdmin.ts`) checked the raw
`capacity` input against a regex (`/^\d+$/`) and `<= 0`, but nothing checked
an upper bound. `migrations/000020_create_workshops.up.sql`'s
`workshops_capacity_check` CHECK constraint and
`internal/handlers/admin_workshops.go`'s `isValidCapacity` both cap capacity
at `2147483647` (INT's max), but the client had no matching rule, so a value
above that round-tripped to the server and came back as a 400 instead of
being caught locally.

## Fix

Added `MAX_WORKSHOP_CAPACITY = 2147483647` as a named constant in
`workshopAdmin.ts`, with a comment tying it to both
`migrations/000020_create_workshops.up.sql`'s `workshops_capacity_check` and
`internal/handlers/admin_workshops.go`'s `isValidCapacity`, so a future change
to either is more likely to be caught. `validateWorkshopForm`'s capacity
check now rejects `capacityValue > MAX_WORKSHOP_CAPACITY` in the same branch
as the existing non-numeric/non-positive check, all three cases sharing one
error message: `'Capacity must be a whole number between 1 and
2147483647.'` — this now matches
`internal/handlers/admin_workshops.go`'s `capacityErrorMessage` wording
("capacity must be a whole number between 1 and 2147483647; to remove a
capacity limit, send capacity as null (PATCH) or omit it (Create)"), modulo
the server's trailing clause about clearing capacity, which is not part of
the range-violation rule this client check enforces. The lower bound (`0`
rejected, not "unlimited") is unchanged from `#0155`'s decision — `NULL`
(an empty capacity field client-side) remains the only "no limit" spelling.

### The cited authorities are real, and they say `2147483647`

Both were read rather than taken on trust:

- `migrations/000020_create_workshops.up.sql:26` declares `capacity INT`, and
  `:58-59` attaches
  `workshops_capacity_check CHECK (capacity IS NULL OR (capacity >= 1 AND
  capacity <= 2147483647))` — the constant's comment quotes this predicate
  verbatim and it matches character for character. No other migration
  mentions `capacity`, so `000020` is the only authority and the comment
  names the right one.
- `internal/handlers/admin_workshops.go:858-860` is
  `func isValidCapacity(v int) bool { return v >= 1 && v <= 2147483647 }`,
  called from both Create (`:295`) and Patch (`:469`).

So the client constant, the handler guard, and the CHECK are the same number,
and the comment points at the two places that actually enforce it.

### The message: substantively the same rule, deliberately shorter

| | |
|---|---|
| Client | `Capacity must be a whole number between 1 and 2147483647.` |
| Server (`capacityErrorMessage`, `admin_workshops.go:834`) | `capacity must be a whole number between 1 and 2147483647; to remove a capacity limit, send capacity as null (PATCH) or omit it (Create)` |

The range clause is word-for-word identical; the client capitalises the
sentence and ends it with a period (correct for UI copy), and drops the
trailing wire-level clause. That clause is about JSON (`null` vs an omitted
key) and has no meaning for someone at a form whose "no limit" spelling is an
empty field — `validateWorkshopForm` turns `''` into `capacity: null` — so
omitting it is right, not a divergence. Criterion 1 ("a message matching the
server's") is met on the part of the message that states the rule.

### Boundary behaviour, probed past what the committed tests cover

The committed tests cover `2147483647` accepted and `2147483648` /
`3000000000` rejected. A throwaway probe (`web/src/lib/zz0168rev.probe.test.ts`,
29 assertions, deleted after the run and never committed) drove the cases the
suite does not, against the real module:

| Input (the form hands `validateWorkshopForm` a **string** — see below) | Result |
|---|---|
| `'2147483646.5'`, `'2147483647.0'` | rejected — `/^\d+$/` is evaluated first in the `||` chain, so no non-integer ever reaches the numeric comparison |
| `'Infinity'`, `'-Infinity'`, `'NaN'`, `'1e3'`, `'0x7fffffff'`, `'+5'`, `'2_147'` | rejected by the same regex |
| `'-0'`, `'-1'`, `'0'` | rejected (the regex kills the signed forms; `'0'` fails `<= 0`) |
| `'١٢٣'` (Arabic-Indic digits) | rejected — worth noting because `Number('١٢٣')` is `123` in JS; the ASCII-only `\d` catches it before the range check would have accepted it |
| `'9'.repeat(400)` | rejected — `Number` gives `Infinity`, and `Infinity > MAX_WORKSHOP_CAPACITY` |
| `'1'`, `'2147483646'`, `'2147483647'` | accepted, `capacity` exactly the integer |
| `'  30  '`, `'007'`, `'0000000002147483647'` | accepted as `30`, `7`, `2147483647` — pre-existing leading-zero/whitespace leniency, unchanged by this commit and harmless (the wire value is a JSON number, so the server sees `7`, not `007`) |
| `''` | accepted as `capacity: null` — the single "no limit" spelling |

**The call-site type was confirmed, not assumed.**
`WorkshopFormFields.capacity` is `string // raw text input`
(`workshopAdmin.ts:392`), and `WorkshopEditor.svelte:516-523` binds it to
`<input type="text" inputmode="numeric">` — not `type="number"`. So the
validator really does receive a string in production, the regex is the real
gate, and the numeric comparisons only ever run on a pure-digit string. There
is no path by which a JS `number` (and therefore a float or `Infinity`)
reaches `capacityValue` from the form.

### `0` is still rejected, and nothing treats it as unlimited

Criterion 4 verified from both ends. `validateWorkshopForm(capacity: '0')`
returns the range error (probed above, and asserted by the committed
`rejects a non-numeric or non-positive capacity` test with a comment naming
`#0155`). Blank stays the only "no limit" spelling: `''` → `capacity: null` →
`workshopToFormFields` maps a `null`/absent server value back to `''`. That
matches `#0155`'s review notes exactly — `NULL` is the single unambiguous "no
limit" representation, and `0` meaning unlimited would be the inverse of its
natural reading.

### Two non-blocking notes

1. **The number is written twice in source**, once as
   `MAX_WORKSHOP_CAPACITY` and once as a literal inside the error string
   (`2147483647` appears twice in the built bundle for this reason).
   Criterion 3's intent — "the next person changing one finds the other" — is
   met by the comment, and the committed tests assert the message text so a
   change to the constant alone would fail loudly. Still,
   `` `Capacity must be a whole number between 1 and ${MAX_WORKSHOP_CAPACITY}.` ``
   would remove the duplication for free. Not worth a bounce; noted for
   whoever next touches the line.
2. The Go side has the same duplication (`capacityErrorMessage` and
   `isValidCapacity` each spell `2147483647`), so this is a symmetry with the
   server rather than a client-only wart.
