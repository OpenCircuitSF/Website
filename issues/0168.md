# 0168 — The workshop editor has no client-side upper bound on capacity, so the browser defers to a 400

## Description

`#0155` added server-side validation of `workshops.capacity` (`1..2147483647`, with a database `CHECK` behind it). `web/src/lib/workshopAdmin.ts` rejects values `<= 0` but has **no upper bound**, so an admin typing `3000000000` gets a round trip and a server 400 instead of an immediate local message.

The behavior is *correct* — the server is the boundary that matters, and it now answers 400 rather than the 500 it used to. This is a UX gap, not a defect.

Filed because it is the second instance of a Go↔TypeScript rule divergence found this session (after the URL validators), and `#0157`'s review deliberately kept it out of that fixture's scope: it is a UX nicety over an already-correct server boundary, with no computable ground truth — `2147483647` is a choice, not a fact — and it does not fit a `{rule, value: string, want: bool}` schema.

## Acceptance criteria

- [ ] `validateWorkshopForm` rejects `capacity > 2147483647` with a message matching the server's, so the admin sees the same rule in both places
- [ ] Unit tests cover the boundary: `2147483647` accepted, `2147483648` rejected
- [ ] The bound is written once with a named constant and a comment tying it to `migrations/000020`'s `INT` column, so the next person changing one finds the other
- [ ] Confirm the lower bound still matches the server's decision from `#0155` — `0` is rejected, not treated as "unlimited"
- [ ] `scripts/check.sh web` passes

## Notes

Reported by `#0157`'s phase-3 review under `CLAUDE.md` §9, and previously noted by `#0155`'s.

Worth a moment's thought on the general question rather than just the one field: this codebase now has several rules implemented in both languages, and only the URL validators are guarded against drift. The cheap discipline is a comment on each side pointing at the other; the expensive one is `#0157`'s fixture approach. For a single integer bound the comment is almost certainly right.
