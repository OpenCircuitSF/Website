## Description

`#0454` made `issueStatus` ignore a status row that sits inside a fenced code
block, so the format template in `issues/Issues.md` stops being read as a real
issue. Its reviewer probed the hand-rolled fence walk against **18** documents
and found it diverges from CommonMark in six ways. Four diverge in the **safe**
direction — a row that should be ignored is read anyway.

**Two diverge in the dangerous direction**, both by opening a fence the real
parser would not:

1. a fence line **indented four or more columns**, or tab-indented, above the
   status row;
2. a **backtick inside a backtick opener's info string** above the status row.

In either case `issueStatus` returns empty, the file is classified as not an
issue, and **every guard silently stops scanning it** — including
`TestResolvedOrClosedIssueCarriesClosedRow`, which then checks nothing and says
nothing.

## Why this is not urgent, and why it is still worth closing

**Exposure today is zero, and structurally so.** All 454 genuine issue files
carry the status row at line 5 (one at line 7), with **zero** fence-shaped lines
above it, because the metadata table is the second block by the template's own
definition. `issueStatus` returns at the first unfenced match, so the corpus's 19
indented and 4 four-backtick fence lines — all lower in their files — cannot
reach the result.

So this is a latent hazard, not a live failure. What makes it worth a line of
code is the failure *mode*: a guard that silently stops guarding is the shape
this repo has shipped twice already (`#0258`, `#0428`), and the whole point of
`#0454` was to make the guards' scope describable.

## The remedy, as its reviewer measured it

Roughly one line: gate the fence toggle on `leadingIndentWidth(line) <= 3`, and
reject a backtick appearing in a backtick opener's info string. **Both helpers —
`leadingIndentWidth` and `leadingRunLength` — already exist in `internal/db`**,
hardened by `#0086`, `#0089`, `#0092` and `#0224`.

## Acceptance criteria

1. Both dangerous-direction divergences are closed, reusing the two existing
   in-package helpers.
2. **Do not refactor `docTableRowLines`.** `#0454`'s review established that
   extracting fence state out of that heavily-hardened function — which another
   guard family depends on — exceeds a predicate change, and `#0176` is the
   standing precedent for declining exactly that trade.
3. Leave the four **safe-direction** divergences alone unless closing them falls
   out for free. A row wrongly read as real is the failure this repo started
   with and is loud; a row wrongly ignored is silent. Fixing the silent half is
   the whole job.
4. Prove it by running the **real** `issueStatus` against the divergent shapes,
   as `#0454`'s reviewer did — not a re-implementation, which is a copy of the
   subject agreeing with itself (`#0441`'s review made this point).
5. Re-derive the corpus counts before and after and confirm **no genuine issue
   file changes classification**. `#0454` established 455 files, 454 with a
   status, 30 `open`/`in-progress` — re-derive rather than copy.
6. **No new mechanism** (§8, `#0258`). A predicate change and its test.

  **The open-strict / close-lenient asymmetry — verdict: the asymmetry is
  right, but the stated justification for it is overstated, and the probe
  found the shape that shows why.** Four unbalanced sequences were run. Three
  of them move, and all three move *toward* CommonMark rather than away:

  - an indented fence-shaped line followed by an unindented one, above the
    row, changes from reading the row to hiding it. CommonMark agrees with the
    new answer — the indented line is an indented code block, the unindented
    one opens a fence that never closes, and an unclosed fence runs to end of
    document.
  - the same with a backtick-in-info-string line in front: same movement, same
    agreement.
  - an indented line followed by two unindented ones changes from hiding the
    row to reading it, and CommonMark again agrees with the new answer.

  So the strict opener does not toggle the state the wrong way; it corrects
  the parity in every unbalanced case probed. That answers the question this
  review was asked to answer, and the asymmetry passes.

  **The residual it turned up is on the closing side, and it is pre-existing.**
  Take a fence opened at column 0, then a fence-shaped line indented four
  columns, then an unindented one, all above the row. CommonMark closes that
  fence exactly once — the four-column line is content, not a closer — and the
  row is outside every fence, so a correct parser reads it. The walk instead
  closes on the indented line and *re-opens* on the unindented one, and hides
  the row. That is a divergence in the dangerous direction, produced by the
  closer's leniency about its own indentation feeding a later opener. It
  behaves identically before and after this commit, so nothing regressed and
  nothing in criteria 1–6 asked for it; `#0454`'s 18-document probe did not
  cover it, and its "odd number of fences" row does not describe it, because
  CommonMark sees an even number of real delimiters there.

  It does mean the implementer's claim — that closing early "only ever un-hides
  a row, never hides one" — is not true in general, and the same word in the
  shipped doc comment labels the ungated closer as safe-direction without
  qualification. Corrected here rather than bounced: the behaviour is right per
  the criteria as written, the exposure is the same structural zero the rest of
  this issue rests on (a status row lives at line 5, above any fence-shaped
  line in all 458 corpus files), and a round-trip to reword a parenthetical
