## Description

`ClaimAndEnqueueAlreadySubscribed`'s claim `UPDATE`
(`internal/subscribers/store.go:795`) carries **only the cooldown predicate** —
no status term — and the caller branches on a **stale `FindByEmail` struct**.

That is `#0341`'s defect, in a second method. `#0341` added
`AND status = $4` to `ClaimAndEnqueueConfirmation`'s claim for exactly this
reason, and its review established that predicate is the sole detector of its
own mutation.

Found by `#0365`'s planning pass while mapping the send paths.

**This is the claim-time half.** `#0365` gates the **send**; a send-time gate
does not make the claim-time predicate unnecessary, because the two close
different windows — `#0341`'s review analysed all four interleavings and found
the SQL predicate not weaker than the `FOR UPDATE` form.

## Acceptance criteria

1. The claim `UPDATE` carries a status predicate appropriate to
   `already_subscribed` — note this is **`active`**, not `pending`; do not copy
   `#0341`'s value without checking which status this path legitimately serves.
2. The caller no longer branches on a stale struct where the predicate now
   decides, or it is documented why the stale read is safe.
3. **Prove it fails without the fix**: a test that claims for a subscriber whose
   status changed between `FindByEmail` and the claim. Run it against unmodified

4. §9 stays binding: `complained` subscribers never auto-resubscribe, only an
   admin clears that state; and the uniform `202` in `POST /api/subscribe`
   (`#0026`) must not vary by list membership.
5. Re-verify the premise against the tree before acting — the line number above
   is from a planning pass, and **five issues this phase received a wrong

6. Per §5 name the specific tests that ran; the mailing subsystem needs

**The asynchrony argument — checked against the code, and the conclusion
holds even though the stated mechanism does not (see R3).** `§9`'s
uniform `202` is safe: `writeSubscribeUniform202` is unconditional, is the
only place the file writes a 202, and the request goroutine never waits on
the mutation. `enqueueMutation` is a `select` on a buffered channel
(`mutateQueueCapacity = 256`) with a `default` arm that drops and logs, so
it cannot block; `runMutateWorker` goroutines drain `mutateQueue` and call
`processMutateJob` → `dispatchMutation` → `existingSignup` → this claim.
No part of the claim runs on the request path, and no handler file is in
this diff. The endpoint therefore cannot vary by list membership.

**`§9` — `complained` never auto-resubscribes.** The predicate is a
positive whitelist on `active`, so it strictly *narrows* what can be
claimed; it cannot become a route by which a `complained` row is served.
Read the whole method body: its `UPDATE` sets only
`already_subscribed_sent_at, updated_at`, and the transaction's only other
write is `outbox.EnqueueTx`. No `status` write exists on this path before
or after the change, so `complained` cannot satisfy `StatusActive` through
any transition this path can reach. The new test asserts exactly this —
status unchanged, `already_subscribed_sent_at` still `NULL`, zero
`outbound_queue` rows — and seeds its own row through `uniqueEmail`,
never a literal or seeded id (§8b).

**Criterion 2 — the stale-struct branch. Ruling: the "documented why the
stale read is safe" branch was taken, and the reasoning holds.** The caller
was not edited (`internal/handlers` is another session's file this pass,
correctly left alone). The reasoning is sound as stated: the caller's
switch decides *which* claim method to call; the predicate decides
*whether* the claim commits. A stale `active` read that is really
`complained` now loses the claim, which is the whole point. Under pgx's
default READ COMMITTED an `UPDATE` meeting a concurrently-locked row
blocks and re-qualifies its `WHERE` against the newly committed version, so
there is no read-then-act window to lose — `#0341`'s review established
this for the identical shape and I did not re-derive it.

### What must change before this can be resolved

All four are prose or metadata. None touches the SQL, the test, or the
verification — do not re-run the mutation proofs.

**R1 — `internal/subscribers/store.go`, the `# #0379` block.** The comment
asserts a delivery this tree prevents. `#0365` landed in the commit
immediately before this issue's own code commit (`733c129`, resolved at
`feb195a`), and its `sendGate` re-checks live subscriber state immediately
before sending, with `gatedKinds[outbox.KindAlreadySubscribed] =
subscribers.StatusActive`. `TestOutboxWorker_SkipsAlreadySubscribedForComplainedSubscriber`
pins it: the row is marked `outbox.StatusSkipped` and `sentTo(mailer, ...)`
is asserted `0`. Production wires `Events: subscribers.NewStore(pool)`
(`cmd/opencircuit/main.go`) and this path always sets `SubscriberID`, so
neither of `sendGate`'s two fail-open branches applies. So "and mailed" was
true before `#0365`, not before `#0379` — and the overstatement matters,
because it credits this predicate with the property `#0365` actually
provides and undersells what `#0379` really closes. Replace these three
lines:

```go
// commit — a row that turned complained in that window would still be
// claimed and mailed an already-subscribed notice. That is #0341's defect
```

with:

```go
// commit — a row that turned complained in that window would still WIN
// this claim, burning already_subscribed_sent_at and committing an
// already_subscribed outbound_queue row for a complained address. Since
// #0365 such a row is no longer delivered: internal/mailing's sendGate
// re-checks live subscriber state immediately before sending and its
// gatedKinds entry for KindAlreadySubscribed requires StatusActive, so the
// row is marked skipped instead (see
// TestOutboxWorker_SkipsAlreadySubscribedForComplainedSubscriber). #0379
// closes the EARLIER window rather than the delivery — the spurious claim,
// the wasted queue row, and the burned cooldown stamp never happen at all,
// and the send gate stops being the only thing standing between a
// complained address and this notice. That is #0341's defect
```

**R2 — `internal/subscribers/store_test.go`, the new test's doc comment.**
Same false clause, same reason. Replace these two lines:

```go
// and this claim (e.g. an SES complaint landing mid-request) would still be
// claimed and mailed an already-subscribed notice — this test fails on
```

with:

```go

```

**R3 — this file, `## Verification`, the criterion-4 paragraph.** The
sentence *"The handler writes `writeSubscribeUniform202` before this job
ever runs"* is not what the code does: `Subscribe` calls
`h.enqueueMutation(...)` **before** `writeSubscribeUniform202(w)`, so a
worker goroutine may begin the job while the response is still being
written. The `§9` conclusion is right, but it rests on a different
mechanism and the record should say the true one. Replace that sentence
with:

> `Subscribe` enqueues the job *before* it writes the response, but it never
> waits on it: `enqueueMutation` is a `select` on a buffered channel
> (`mutateQueueCapacity = 256`) with a `default` arm that drops and logs, so
> the send cannot block, and `writeSubscribeUniform202` is unconditional and
> identical on every branch. The response is therefore never gated on which
> branch the mutation takes.
