## Description

`ClaimAndEnqueueAlreadySubscribed`'s claim `UPDATE`
(`internal/subscribers/store.go:795`) carries **only the cooldown predicate** —
no status term — and the caller branches on a **stale `FindByEmail` struct**.

That is `#0341`'s defect, in a second method. `#0341` added
`AND status = $4` to `ClaimAndEnqueueConfirmation`'s claim for exactly this
reason, and its review established that predicate is the sole detector of its
own mutation.

Found by `#0365`'s planning pass while mapping the send paths.

**This is the claim-time half.** `#0365` gates the **send**; a send-time gate
does not make the claim-time predicate unnecessary, because the two close
different windows — `#0341`'s review analysed all four interleavings and found
the SQL predicate not weaker than the `FOR UPDATE` form.

## Acceptance criteria

1. The claim `UPDATE` carries a status predicate appropriate to
   `already_subscribed` — note this is **`active`**, not `pending`; do not copy
   `#0341`'s value without checking which status this path legitimately serves.
2. The caller no longer branches on a stale struct where the predicate now
   decides, or it is documented why the stale read is safe.
3. **Prove it fails without the fix**: a test that claims for a subscriber whose
   status changed between `FindByEmail` and the claim. Run it against unmodified
   code first. `#0341`'s review verified its predicate was the **sole** detector
   of its mutation — aim for the same.
4. §9 stays binding: `complained` subscribers never auto-resubscribe, only an
   admin clears that state; and the uniform `202` in `POST /api/subscribe`
   (`#0026`) must not vary by list membership.
5. Re-verify the premise against the tree before acting — the line number above
   is from a planning pass, and **five issues this phase received a wrong
   identifier because prose was transcribed as though measured.**
6. Per §5 name the specific tests that ran; the mailing subsystem needs
   Postgres. §8b: mutations use your own database, never a literal or seeded id.

## Verification

**Premise check (criterion 5), re-verified against the tree before acting.**
`ClaimAndEnqueueAlreadySubscribed`'s claim `UPDATE`, read directly from
`internal/subscribers/store.go` before any edit, was:

```sql
UPDATE subscribers
   SET already_subscribed_sent_at = $2, updated_at = $2
 WHERE id = $1 AND (already_subscribed_sent_at IS NULL OR already_subscribed_sent_at < $3)
```

— only the cooldown predicate, no status term, exactly as described. The
Description's method identity is confirmed accurate as filed; its cited line
number has drifted by a handful of lines since the planning pass (the
method's doc comment has grown), which is the ordinary drift `## Description`
already warns is possible, not a wrong identification of the method or the
defect. The defect is real and unchanged in shape.

**Criterion 1 — which status, and how it was determined.** `StatusActive`,
not `StatusPending`. Determined by reading the only caller:
`internal/handlers/subscribe.go`'s `existingSignup` dispatches on
`existing.Status` (read moments earlier by `dispatchMutation`'s
`FindByEmail`) and reaches `sendAlreadySubscribed` — the sole caller of
`ClaimAndEnqueueAlreadySubscribed` — **only** from its `StatusActive` case;
every other case (`StatusPending`, `StatusUnsubscribed`, `StatusBounced`,
`StatusComplained`, `default`) routes elsewhere or falls through to the
uniform 202 untouched. PRD §6.3's "already subscribed" notice is likewise
only meaningful for an active row. `AND status = $4` was added bound to
`StatusActive`, mirroring #0341's mechanism (same claim-in-the-WHERE-clause
shape) but not its value — copying `StatusPending` would have silently
disabled this path for every legitimate caller, which is exactly the trap
the issue named.

**Criterion 2 — the caller.** `internal/handlers` was not edited (out of
scope for this pass — another session owns it). `sendAlreadySubscribed`
still passes the `existing` struct `FindByEmail` read earlier, but this is
now documented, not merely left alone: the new doc-comment section on
`ClaimAndEnqueueAlreadySubscribed` (`internal/subscribers/store.go`) records
that the predicate is now the sole authority over whether the claim
commits — the caller's earlier read only decides which claim method to
call, never whether the send happens — the identical reasoning #0341
established for `ClaimAndEnqueueConfirmation`'s caller. Neither claim method
writes `status`, so this predicate cannot become a resubscribe path.

**Criterion 3 — the deliverable, fails-without-the-fix proof.** Added
`TestClaimAndEnqueueAlreadySubscribed_RefusesComplainedRow` and a
parameterized seed helper `seedSubscriberWithStatus` (generalizing the
existing `seedActiveSubscriber`) in `internal/subscribers/store_test.go`.
Proved it fails on the pre-fix code first, per §8a's export technique (never
the shared tree): `git archive HEAD` into a scratchpad export (HEAD was
still unmodified store.go at that point), overlaid the new test file, ran
against an isolated per-issue database:

Then ran the **whole package** against the same unmodified pre-fix code (own

`TestClaimAndEnqueueAlreadySubscribed_RefusesComplainedRow` — and all other

predicate's absence, matching #0341's review standard. Scratch export and
both scratch databases (`opencircuit_test_0379m`, `opencircuit_test_0379m4`)
were dropped afterward.

**Criterion 4 — §9.** `complained` still cannot auto-resubscribe through
this path: `ClaimAndEnqueueAlreadySubscribed` never writes `status` (only
`already_subscribed_sent_at`/`updated_at`), before or after this change — the
new predicate only ever gates whether a *notification* is claimed, never a
status transition. **The uniform `202` cannot vary.** `sendAlreadySubscribed`
runs inside `processMutateJob`, which `runMutateWorker` drains from
`h.mutateQueue` on a background goroutine, entirely off the HTTP request
path — `#0088` moved every branch-dependent write there for exactly this
reason, and `#0254` makes the durable intake row's "processed" marker
independent of which branch ran. The handler writes `writeSubscribeUniform202`
before this job ever runs; no handler file is in this pass's diff at all (see
below), so nothing here can touch the response.
