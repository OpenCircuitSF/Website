# 0158 — `testSlug` derives uniqueness from `time.Now().UnixNano()`, which repeats 94.7% of the time on this machine

## Description

`internal/interests`' `store_test.go:37` builds supposedly-unique slugs from `time.Now().UnixNano()`. On this hardware that clock is **not** fine-grained enough: a 200,000-pair probe measured **189,484 identical consecutive readings — 94.7%, minimum delta 0ns.**

So any test calling `testSlug` twice in quick succession is a near coin-flip for `slug already exists`. `TestSubscriberCounts_CountsLinkedAndOmitsZero` does exactly that, and it failed for `#0155`'s reviewer at load average **1.47** — an idle machine. The next run was green.

`internal/handlers`' `uniqueAdminWorkshopTitle` shares the pattern. It has been masked so far by intervening HTTP round trips giving the clock time to tick.

**This is not the `CLAUDE.md` §5 "the machine is busy" case, and should not be diagnosed as one.** The load average was 1.47. It is a real defect in the helper, and it will keep failing unrelated reviews of unrelated issues until it is fixed — which is the expensive part, because each time it costs someone a diagnosis before they conclude it was not their change.

## Acceptance criteria

- [ ] `testSlug` (and `uniqueAdminWorkshopTitle`, and any sibling helper with this shape) draws uniqueness from a **process-wide atomic counter**, not from a clock
- [ ] Grep for other `UnixNano()`-derived identifiers in test helpers and fix them together — the two known instances were found incidentally, not by a sweep
- [ ] A test proves the helper returns distinct values on back-to-back calls with no intervening work — the exact case that fails today
- [ ] `ISSUE=0158 scripts/check.sh go ./internal/...` passes, and `internal/interests` passes under `-shuffle` on two fresh seeds
- [ ] If a counter alone is not enough (parallel packages sharing a database), say what else is needed — a package prefix, the `ISSUE` value, or a random suffix

## Notes

Found by `#0155`'s phase-3 review while diagnosing a check-run failure that had nothing to do with the issue under review. It measured the clock resolution rather than assuming, which is why this is filed as a defect rather than dismissed as flakiness.

Worth connecting to the project's history: `CLAUDE.md` §5 records a day lost to widening test deadlines for failures that were really machine saturation. This is the mirror image — a failure that *looks* like ambient flakiness but is a deterministic bug in a helper, and dismissing it as load would be the same mistake in the other direction.
