## Description

`internal/interests`' `store_test.go:37` builds supposedly-unique slugs from `time.Now().UnixNano()`. On this hardware that clock is **not** fine-grained enough: a 200,000-pair probe measured **189,484 identical consecutive readings — 94.7%, minimum delta 0ns.**

So any test calling `testSlug` twice in quick succession is a near coin-flip for `slug already exists`. `TestSubscriberCounts_CountsLinkedAndOmitsZero` does exactly that, and it failed for `#0155`'s reviewer at load average **1.47** — an idle machine. The next run was green.

`internal/handlers`' `uniqueAdminWorkshopTitle` shares the pattern. It has been masked so far by intervening HTTP round trips giving the clock time to tick.

**This is not the `CLAUDE.md` §5 "the machine is busy" case, and should not be diagnosed as one.** The load average was 1.47. It is a real defect in the helper, and it will keep failing unrelated reviews of unrelated issues until it is fixed — which is the expensive part, because each time it costs someone a diagnosis before they conclude it was not their change.

## Acceptance criteria

- [x] `testSlug` (and `uniqueAdminWorkshopTitle`, and any sibling helper with this shape) draws uniqueness from a **process-wide atomic counter**, not from a clock
- [x] Grep for other `UnixNano()`-derived identifiers in test helpers and fix them together — the two known instances were found incidentally, not by a sweep
- [x] A test proves the helper returns distinct values on back-to-back calls with no intervening work — the exact case that fails today
- [x] `ISSUE=0158 scripts/check.sh go ./internal/...` passes, and `internal/interests` passes under `-shuffle` on two fresh seeds
- [x] If a counter alone is not enough (parallel packages sharing a database), say what else is needed — a package prefix, the `ISSUE` value, or a random suffix

## Root cause

`internal/interests/store_test.go`'s `testSlug` and `internal/handlers/admin_workshops_test.go`'s
`uniqueAdminWorkshopTitle` built "unique" identifiers from `time.Now().UnixNano()`.
On this hardware the wall clock does not advance every call — a 200,000-pair
probe measured 189,484 identical consecutive readings (94.7%, minimum delta
0ns) — so two back-to-back calls are a near coin-flip for the same value, and
any test calling such a helper twice with no intervening work is a near
coin-flip for a unique-constraint violation (`slug already exists`, duplicate
email, etc).

A tree-wide grep for `UnixNano()` / `UnixMilli()` / `UnixMicro()` in `*_test.go`
(not just the two sites the issue named) turned up **28 files** with
`time.Now().UnixNano()`-derived uniqueness helpers — slugs, emails, tokens,
titles, message IDs — across `cmd/opencircuit`, `internal/handlers`,
`internal/interests`, `internal/mailing`, `internal/sesnotify`,
`internal/subscribers`, and `internal/workshops`. `internal/subscribers`'
`uniqueSuppressionEmail` (added for `#0108`) had already worked around the
defect locally with its own `atomic.AddUint64` sequence layered on top of the
clock call — independent evidence the same bug had already bitten this
project once before and been patched in exactly one place rather than at the
root.

Every `UnixMilli()` usage found in the same sweep (`rendered_at` fixture
timestamps, and `internal/handlers/subscribe_test.go`'s timing-gate boundary
table: "well in the past", "exactly at the boundary", etc) is a genuine
timestamp value under test, not a uniqueness source, and was left untouched.

## Fix

Added `internal/testdb.Unique() int64`: an `atomic.AddInt64` counter combined
with `os.Getpid()` in the high 32 bits, low 32 bits from the counter. Every
`_test.go` file's uniqueness-driving `time.Now().UnixNano()` call was replaced
with `testdb.Unique()` (27 files; `internal/testdb` itself already exported
`Lock`/`Connect` and every DB-backed package already imports it from
`TestMain`, so this only needed adding the import to the specific files that
didn't already have it).

**Why a bare counter is not enough (the criterion's collision-scope
question).** `go test ./...` runs each package as its own OS process, so a
plain `atomic` counter is only unique *within one process* — two processes
each start at 0. Several packages mint identifiers from an *identical literal
prefix* against the *same* shared `TEST_DATABASE_URL`: both
`internal/interests` (`testSlug`) and `internal/handlers`
(`interests_test.go`'s slug helper) build interest-table slugs as
`"zz-test-<n>"`. If both processes' counters started at 1, a `go test ./...`
run could produce two `"zz-test-1"` rows in the same `interests` table and
collide — a race between packages, not within one.

Folding in `os.Getpid()` closes that gap without needing every call site to
also thread through a package name or the `ISSUE` env var: two processes
never share a PID while both are running, so the high bits disambiguate
processes and the low bits (the counter) guarantee no repeat within a
process, regardless of clock resolution. A random suffix was considered and
rejected — it reintroduces a (much smaller, but nonzero) probabilistic
collision risk for no benefit once PID+counter is deterministic and free of
collisions by construction. The `ISSUE` env var was rejected as the
disambiguator because `Unique()` is called from ordinary test code with no
access to how the harness invoked `go test`, and because it wouldn't help two
concurrent runs that happen to share the same `ISSUE` (e.g. a batch review
pass and a leftover process).

  `TestUnique_ConcurrentDistinct`) — new tests proving no repeats back-to-back

  §8a, copied `internal/testdb/testdb.go` aside, temporarily reinstated a

## Gotchas

- **A naive sed sweep corrupts prose, not just code.** The first pass replaced
  every literal `time.Now().UnixNano()` substring including inside two `#0108`
  doc comments in `internal/subscribers/suppressions_test.go` that were
  *describing* the old clock's 62%-collision behavior — the mechanical
  replacement flipped that history to read as if the new `testdb.Unique()`
  helper collided, which is backwards. Caught by grepping the diff for
  `testdb.Unique()` next to a `//` prefix and fixed by hand; worth re-checking
  after any similar sweep.
- `internal/subscribers/suppressions_test.go`'s existing `suppressionEmailSeq`
  atomic counter (from `#0108`) is now redundant with `testdb.Unique()` — both
  independently guarantee uniqueness. Left in place rather than removed, to
  avoid touching another issue's fix outside this one's scope.
- `internal/workshops/store_test.go:34` builds `"Test Workshop %d"` from the
  same pattern but has no named helper wrapping it (unlike
  `uniqueAdminWorkshopTitle`); fixed inline, not worth extracting a helper for
  one call site.

## Notes

Found by `#0155`'s phase-3 review while diagnosing a check-run failure that had nothing to do with the issue under review. It measured the clock resolution rather than assuming, which is why this is filed as a defect rather than dismissed as flakiness.

Worth connecting to the project's history: `CLAUDE.md` §5 records a day lost to widening test deadlines for failures that were really machine saturation. This is the mirror image — a failure that *looks* like ambient flakiness but is a deterministic bug in a helper, and dismissing it as load would be the same mistake in the other direction.
