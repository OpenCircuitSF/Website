## Description

> ✅ **Resolved 2026-08-22** (`b299698`) — verified independently by the
> phase-3 reviewer at load average 1.5–2.5 (idle). The sweep is complete
> (28 of 28 candidate files) and mechanical, the regression test genuinely
> bites, and the PID-prefixed counter's arithmetic holds on this platform.
> Detail in `## Review notes`.

`internal/interests`' `store_test.go:37` builds supposedly-unique slugs from `time.Now().UnixNano()`. On this hardware that clock is **not** fine-grained enough: a 200,000-pair probe measured **189,484 identical consecutive readings — 94.7%, minimum delta 0ns.**

So any test calling `testSlug` twice in quick succession is a near coin-flip for `slug already exists`. `TestSubscriberCounts_CountsLinkedAndOmitsZero` does exactly that, and it failed for `#0155`'s reviewer at load average **1.47** — an idle machine. The next run was green.

`internal/handlers`' `uniqueAdminWorkshopTitle` shares the pattern. It has been masked so far by intervening HTTP round trips giving the clock time to tick.

**This is not the `CLAUDE.md` §5 "the machine is busy" case, and should not be diagnosed as one.** The load average was 1.47. It is a real defect in the helper, and it will keep failing unrelated reviews of unrelated issues until it is fixed — which is the expensive part, because each time it costs someone a diagnosis before they conclude it was not their change.

## Acceptance criteria

- [x] `testSlug` (and `uniqueAdminWorkshopTitle`, and any sibling helper with this shape) draws uniqueness from a **process-wide atomic counter**, not from a clock
- [x] Grep for other `UnixNano()`-derived identifiers in test helpers and fix them together — the two known instances were found incidentally, not by a sweep
- [x] A test proves the helper returns distinct values on back-to-back calls with no intervening work — the exact case that fails today
- [x] `ISSUE=0158 scripts/check.sh go ./internal/...` passes, and `internal/interests` passes under `-shuffle` on two fresh seeds
- [x] If a counter alone is not enough (parallel packages sharing a database), say what else is needed — a package prefix, the `ISSUE` value, or a random suffix

## Root cause

`internal/interests/store_test.go`'s `testSlug` and `internal/handlers/admin_workshops_test.go`'s
`uniqueAdminWorkshopTitle` built "unique" identifiers from `time.Now().UnixNano()`.
On this hardware the wall clock does not advance every call — a 200,000-pair
probe measured 189,484 identical consecutive readings (94.7%, minimum delta
0ns) — so two back-to-back calls are a near coin-flip for the same value, and
any test calling such a helper twice with no intervening work is a near
coin-flip for a unique-constraint violation (`slug already exists`, duplicate
email, etc).

A tree-wide grep for `UnixNano()` / `UnixMilli()` / `UnixMicro()` in `*_test.go`
(not just the two sites the issue named) turned up **28 files** with
`time.Now().UnixNano()`-derived uniqueness helpers — slugs, emails, tokens,
titles, message IDs — across `cmd/opencircuit`, `internal/handlers`,
`internal/interests`, `internal/mailing`, `internal/sesnotify`,
`internal/subscribers`, and `internal/workshops`. `internal/subscribers`'
`uniqueSuppressionEmail` (added for `#0108`) had already worked around the
defect locally with its own `atomic.AddUint64` sequence layered on top of the
clock call — independent evidence the same bug had already bitten this
project once before and been patched in exactly one place rather than at the
root.

Every `UnixMilli()` usage found in the same sweep (`rendered_at` fixture
timestamps, and `internal/handlers/subscribe_test.go`'s timing-gate boundary
table: "well in the past", "exactly at the boundary", etc) is a genuine
timestamp value under test, not a uniqueness source, and was left untouched.

## Fix

Added `internal/testdb.Unique() int64`: an `atomic.AddInt64` counter combined
with `os.Getpid()` in the high 32 bits, low 32 bits from the counter. Every
`_test.go` file's uniqueness-driving `time.Now().UnixNano()` call was replaced
with `testdb.Unique()` (28 files; `internal/testdb` itself already exported
`Lock`/`Connect` and every DB-backed package already imports it from
`TestMain`, so this only needed adding the import to the specific files that
didn't already have it).

**Why a bare counter is not enough (the criterion's collision-scope
question).** `go test ./...` runs each package as its own OS process, so a
plain `atomic` counter is only unique *within one process* — two processes
each start at 0. Several packages mint identifiers from an *identical literal
prefix* against the *same* shared `TEST_DATABASE_URL`: both
`internal/interests` (`testSlug`) and `internal/handlers`
(`interests_test.go`'s slug helper) build interest-table slugs as
`"zz-test-<n>"`. If both processes' counters started at 1, a `go test ./...`
run could produce two `"zz-test-1"` rows in the same `interests` table and
collide — a race between packages, not within one.

Folding in `os.Getpid()` closes that gap without needing every call site to
also thread through a package name or the `ISSUE` env var: two processes
never share a PID while both are running, so the high bits disambiguate
processes and the low bits (the counter) guarantee no repeat within a
process, regardless of clock resolution. A random suffix was considered and
rejected — it reintroduces a (much smaller, but nonzero) probabilistic
collision risk for no benefit once PID+counter is deterministic and free of
collisions by construction. The `ISSUE` env var was rejected as the
disambiguator because `Unique()` is called from ordinary test code with no
access to how the harness invoked `go test`, and because it wouldn't help two
concurrent runs that happen to share the same `ISSUE` (e.g. a batch review
pass and a leftover process).

**The diff is genuinely mechanical.** Rather than reading 28 diffs by eye, I
reverse-applied the substitution: for each changed `_test.go` file, replaced
`testdb.Unique()` back with `time.Now().UnixNano()` and diffed against
`b299698^`. Every file came back identical apart from the added
`internal/testdb` import and, in six files (`events_wiring_test.go`,
`seo_wiring_test.go`, `admin_campaign_stats_test.go`,
`admin_workshops_test.go`, `interests_test.go`, `journey_testutil_test.go`),
a removed `"time"` import that compilation requires. **No assertion, fixture,
expected value, or comment changed.** The two `#0108` doc comments in
`internal/subscribers/suppressions_test.go` that the naive `sed` had corrupted
do not appear in the commit's diff at all — the hand-repair restored them
exactly, and both still read as history about the old clock rather than as
claims about `testdb.Unique()`.

**The sweep is complete.** `git grep -l 'time.Now().UnixNano()' b299698^ --
'*_test.go'` returns **28 files; all 28 were changed** (`comm` against the
commit's file list leaves nothing). 83 matching lines at the parent, 81 of
them code and 2 the `#0108` comments; there are exactly 81 `testdb.Unique()`
call sites now. Every surviving `UnixNano` in the tree is prose. Every
`UnixMilli` that remains is a genuine timestamp under test — four
`"rendered_at"` fixtures and `internal/handlers/subscribe_test.go`'s
timing-gate boundary table ("well in the past", "exactly at the boundary",
"in the future") — correctly left alone; substituting a counter there
would have changed what those tests assert. No `UnixMicro` anywhere.

**The PID-prefix design is sound, and the arithmetic checks out.** The
premise holds: `go test ./...` gives each package its own OS process, and
`internal/interests`' `testSlug` and `internal/handlers/interests_test.go`
both mint `"zz-test-<n>"` against the same `TEST_DATABASE_URL` under a
`slug TEXT UNIQUE NOT NULL` constraint (`migrations/000009`), so two
processes each starting a bare counter at 1 really could collide. On the
arithmetic:

- **PIDs fit the high half.** macOS caps PIDs at 99999 (`kern.maxproc` 16000;
  highest PID observed live during this review: 99439) — 17 bits, far
  inside the 31 available above the shift. `99999 << 32` ≈ 4.29e14, nowhere
  near `int64` overflow, and the result is always positive.
- **The low half cannot bleed into the PID bits.** The counter is masked
  (`n & 0xffffffff`), so even a pathological run wraps within the low half
  rather than incrementing the PID field. 2^32 is ~4 billion calls; the
  heaviest single caller in this tree is
  `TestUniqueSuppressionEmail_NeverCollidesAcrossManyBackToBackCalls` at
  20,000. Five orders of magnitude of headroom.
- **PID reuse across sequential runs is harmless here.** Two live processes
  cannot share a PID, so the concurrent case — the one the design targets
  — is closed by construction. A later run can reuse a PID and replay the
  same identifiers, which the old monotonic clock could not; that is a real
  (if theoretical) loss of cross-run uniqueness. It does not bite because
  `scripts/check.sh` clones a fresh per-`ISSUE` database and drops it
  afterwards, and every DB-backed package `TRUNCATE`s its own tables in
  `TestMain`, so no run ever sees a prior run's rows. Worth knowing rather
  than worth changing.
- **Identifier shape is preserved.** Within one process the PID prefix is
  constant and the counter increases, so the rendered strings stay
  equal-length and in ascending order — the property any ordering
  assertion was implicitly relying on. They are shorter than the old
  19-digit nanosecond values, which only helps against email local-part
  limits.

**The regression test genuinely bites — re-proved, not taken on report.**
In my own worktree (§8a: `cp` aside first, never `git checkout --`), I
replaced `Unique()`'s body with `return time.Now().UnixNano()` and ran
`go test ./internal/testdb/... -run TestUnique_DistinctBackToBack -count=1`
25 times: **21 failed** (5 runs: 4 failures; 20 more: 17 failures) with
`Unique() returned the same value twice back-to-back`. Restored from the copy
and confirmed byte-identical by md5 (`f2ca12f4b8e5648bc386e5c63e2ceab5` before
and after); both `testdb` tests then passed and `git status` was clean.

**The defect it fixes is real — measured, not assumed.** A fresh
200,000-pair probe on this machine reproduced the filing exactly: **189,602
identical consecutive `UnixNano()` readings, 94.8%, minimum delta 0ns.** A
probe of the *actual* `testSlug` call shape from inside a warm
`internal/interests` test binary (two calls with only a `t.Helper()` and a
`t.Cleanup` registration between them, 2,000 pairs) collided on **11%** —
which is the right order of magnitude for a test that fails for one reviewer
and passes on the rerun. I also ran the old tree's
`TestSubscriberCounts_CountsLinkedAndOmitsZero` 30 times and the whole old
`internal/interests` package 15 times under `-shuffle=on` without catching a
failure, so the in-situ rate is below 11%; that does not weaken the
diagnosis, it just explains why this survived so long. The fix removes the
clock dependency entirely, so the rate is now zero by construction rather
than small.
