## Description

This codebase now has **four** implementations of two URL-safety rules, split across two languages:

| Rule | Go | TypeScript |
|---|---|---|
| Cover image (same-origin only) | `handlers.isSafeCoverImage` | `workshopAdmin.isSafeCoverImage` |
| Link (external allowed) | `handlers.isSafeLinkHref` | `markdown.isSafeLinkHref` |

They must agree exactly. **Nothing in the build checks that they do.**

Parity has been established three separate times — by `#0138`'s two review passes and by `#0152`'s — each time with a throwaway sweep script that was deleted afterward. Two of those sweeps found real divergences:

- `#0138` pass 2 found the twins agreeing only after a fix, and swept every codepoint `0x00`–`0xFF` to prove it.
- **`#0152` found a live bypass**: `strings.TrimSpace` and JavaScript's `trim()` disagree on U+FEFF and U+0085, so the naive Go twin **accepted a `javascript:` URL that TypeScript rejected**. Invisible to every existing test.

That is the argument in one line: the parity break was a real security defect, and only an ad-hoc script that no longer exists caught it.

## Root cause

Nothing in the build re-checked Go/TypeScript agreement after the fact. `#0138`
(twice) and `#0152` each independently proved `isSafeCoverImage`/`isSafeLinkHref`
agree across languages, but each proof was a throwaway script run once and
deleted — none of it survived as a committed test. `#0152`'s find was the
sharpest argument for why that's a real defect, not a nicety: `strings.TrimSpace`
and JS `trim()` disagree on U+FEFF, so a naive Go twin accepted a `javascript:`
URL smuggled behind a BOM that the TypeScript original correctly rejected — a
live security bypass invisible to every test that existed at the time, because
none of them exercised that codepoint and none of them ran the two languages
side by side. A future edit to either `isSafeCoverImage` or `isSafeLinkHref`
(Go or TypeScript) had no committed guard against silently breaking parity.

## Fix

**The fixture, generated from ground truth, not hand-listed.**
`testdata/url_validators.json` holds 3,138 `{id, rule, source, value, want}`
cases, generated by a two-stage process rather than transcribed from memory:

1. A Node script (Node 26 runs `.ts` natively, no build step) computed the
   *exact* ECMA-262 whitespace set by sweeping every codepoint
   `0x0000`–`0x10FFFF` (surrogates skipped) through V8's real `String.prototype.trim()`
   — the same method `#0152`'s reviewer used. It independently reproduced the
   identical 25 codepoints that review found (TAB, LF, VT, FF, CR, SPACE, NBSP,
   U+1680, U+2000–U+200A, LS, PS, U+202F, U+205F, U+3000, U+FEFF), and confirmed
   six notable near-misses are correctly *not* in that set (U+0085 NEL, U+180E,
   U+200B, U+2060, U+00AD, U+3164).
2. That codepoint set, unioned with the full `0x00`–`0xFF` range, was placed into
   templates covering both rules in interior, leading, doubled-leading, and
   trailing position (e.g. `java<CP>script:alert(1)`, `<CP>//evil.host/x`,
   `/<CP>/evil.host/x.jpg`), plus curated scheme-shape, protocol-relative/backslash,
   and legitimate-case payloads (query, fragment, mid-path `//`, `..`, `%5C`,
   `%2F%2F`, non-ASCII, a bare `/`, a 10,000+ character path).
3. Every payload's "want" was computed by **executing the real functions** —
   the actual `web/src/lib/linkSafety.ts` `isSafeLinkHref` and
   `web/src/lib/workshopAdmin.ts` `isSafeCoverImage`, imported directly by the
   Node script — then cross-checked against the real Go `isSafeCoverImage`/
   `isSafeLinkHref` via a throwaway generator test
   (`GENERATE_URL_FIXTURE=1 go test ./internal/handlers/ -run TestGenerateURLFixture`,
   deleted after use). **0 mismatches across all 3,138 payloads.** Had there been
   any, generation would have aborted rather than picking a side — this issue's
   scope is to prove and freeze agreement, not to adjudicate a live divergence.

Both suites now read the identical JSON:
`internal/handlers/url_validator_fixture_test.go` (`TestURLValidatorFixture`,
one Go subtest per fixture case) and `web/src/lib/urlValidatorFixture.test.ts`
(one `it()` per case, fixture imported directly via `resolveJsonModule`). A
change to either language's rule that alters behavior on any of these 3,138
payloads is now a red build in that language; a change that breaks
*cross-language* agreement specifically requires updating both files' behavior
in lockstep, since there is no way to edit only one side's assertions.

**Decision 1 — fixture, not deduplication.** The issue asks explicitly. A real
merge into two functions (Go generating a WASM/embedded copy TypeScript calls,
or vice versa; or a schema-driven DSL both languages interpret) would be the
"real" fix, but it was rejected here for cost and fit:

- The two languages don't share a runtime. Go compiled to WASM and loaded by
  the SPA would add a build step, a bundle-size cost, and a new failure mode
  (WASM load failure) to a static marketing site with `CLAUDE.md §9`'s
  "no external CDNs... self-contained by design" constraint — for two pure
  string predicates.
- A shared DSL (e.g. a JSON rule description both `isSafeCoverImage`/
  `isSafeLinkHref` interpret) would need to express "C0∪DEL rejection", "trim
  with this exact whitespace set", "scheme allowlist", and "protocol-relative
  backslash normalization" as data — real engineering for four small,
  already-well-tested functions, and it would still need its own test suite to
  prove the DSL interpreter is correct in both languages, which is the same
  problem one level up.
- The actual risk this issue exists to close is **silent drift on a future
  edit**, not the current duplication itself. A fixture closes that risk
  completely: any edit that changes behavior on a payload the fixture covers is
  caught, in both languages, at `go test`/`vitest` time — which is exactly the
  guarantee deduplication would provide, at a fraction of the engineering cost
  and with zero new runtime dependencies.
- Cost avoided: a rough estimate for the WASM route alone is a new build target
  (`GOOS=js GOARCH=wasm`), a `wasm_exec.js` shim vendored or CDN-loaded (the
  latter forbidden by `CLAUDE.md §9`), async instantiation at SPA startup
  (`isSafeLinkHref`/`isSafeCoverImage` are called synchronously from
  `validateWorkshopForm` and `hasExternalSignup` today), and its own new test
  surface — plausibly a multi-day change against two small, stable functions
  that have not diverged in three months of active development once each
  divergence was found and closed.

**Decision 2 — fixture scope stays at URL validators; the capacity divergence
does not join it.** `#0155`'s review found `workshopAdmin.ts` has no client-side
upper bound on `capacity`, so `3000000000` round-trips to the server and comes
back as a 400 instead of a client-side message — correct behavior, same
"client and server disagree" *shape* as the URL-validator drift, but a
different kind of problem:

- The URL validators are a **security boundary**: a divergence there means one
  language accepts a payload the other correctly rejects, and the accepting
  side is what decides whether a `javascript:` URL reaches a rendered `href`.
  The stakes justify a dedicated, ground-truth-generated, 3,138-case fixture.
- The capacity check is a **UX nicety** layered on top of a boundary the server
  already enforces correctly either way (`isValidCapacity`, `#0155`). No input
  makes it into the database or gets rendered unsafely; the only cost of the
  gap is one extra round trip and a less specific error message for a browser
  user who typed a 10-digit number. There is no ground truth to compute here
  the way V8's `trim()` is ground truth for whitespace — the "right" upper
  bound is just `2147483647` (documented in `capacityErrorMessage`), a single
  literal, not a codepoint sweep.
- Folding it into *this* fixture (whose whole design is keyed on `{rule, value,
  want}` string-predicate cases) would mean building a second, differently-shaped
  fixture format for numeric bounds inside the same file, for a one-line fix
  (add `Number(capacityTrimmed) <= 2147483647` to `validateWorkshopForm`) that
  doesn't need one.
- Recommendation, not filed here per this issue's own scope (`CLAUDE.md §9`:
  subagents report issues to file, they do not file them): a follow-up issue to
  add the client-side upper-bound check directly, with a two-or-three-case unit
  test (`0`, `2147483647`, `2147483648`) — no fixture infrastructure needed.

**Coverage nit.** `TestAdminWorkshops_PatchRejectsUnsafeSignupURL` now loops over
the same 4 `badValues` `TestAdminWorkshops_CreateRejectsUnsafeSignupURL` uses
(`javascript:alert(1)`, `data:text/html,evil`, `//evil.host/x`,
`java\tscript:alert(1)`), rather than 2. Not a bounce — `Patch` calls the
identical `isSafeLinkHref` `Create` does — just a widened net, matching the
existing loop-over-`badValues` pattern `TestAdminWorkshops_CreateRejectsUnsafeSignupURL`
and the cover-image tests already use.

**Rename.** `web/src/lib/markdown.ts` → `web/src/lib/linkSafety.ts` (and
`markdown.test.ts` → `linkSafety.test.ts`), per `#0136`'s reviewer: `#0136`
deleted `renderMarkdownPreview` and every helper it used, leaving `isSafeLinkHref`
— a URL-safety predicate, not Markdown rendering — as the module's sole export.
Every import (`workshopDetail.ts`, the new `urlValidatorFixture.test.ts`) and
every Go/TypeScript/Svelte comment that named the file by path was updated in
the same commit; historical comments explaining *why* the rename happened keep
a one-line "formerly `markdown.ts`" note rather than being silently rewritten.
Pure rename plus comment/import updates — no behavior change.

### The circularity question, ruled on: the `want` column is right, not merely current

The implementer computed every `want` by executing both real implementations
and cross-checking them. That pins *agreement*, which is the point — but it
would enshrine a bug if both sides were wrong together. So I did not re-run
either implementation to check the fixture. I asked a third party what a
browser actually does.

**Systematic, all 3,138 cases.** For each payload I resolved
`new URL(value, 'https://www.opencircuitsf.com/workshops/soldering-101')` and
asked what protocol and origin come out:

```
cases 3138   unparseable 0
link_href   want=true but resolves outside http/https/mailto :  0
cover_image want=true but resolves off-origin                :  0
conservative rejects (want=false, browser would be safe): link 135, cover 582
```

The dangerous direction is empty. Nothing the fixture blesses is something a
browser would take somewhere it should not go. The 717 conservative rejects
are the fail-safe direction and every one I sampled is a deliberate
`#0138`/`#0152` ruling, not an accident.

**The named spot-checks, case by case.** `want` is the fixture's value; the
right-hand columns are the WHATWG parser's, computed independently:

| Payload | `want` | resolves to | verdict |
|---|---|---|---|
| `//evil.host/x` (both rules) | `false` | `https://evil.host/x` — **off-site** | correct |
| `///evil.host/x` (both rules) | `false` | `https://evil.host/x` — **off-site** | correct |
| `/<TAB>/evil.host/x` (both rules) | `false` | `https://evil.host/x` — parser strips the TAB | correct, and this is the whole reason the raw string cannot be trusted |
| `java<TAB>script:alert(1)` | `false` | **`javascript:alert(1)`** | correct — genuinely live |
| `java<LF>script:alert(1)` | `false` | **`javascript:alert(1)`** | correct |
| `java<CR>script:alert(1)` | `false` | **`javascript:alert(1)`** | correct |
| `java<VT>script:alert(1)` | `false` | `https://…/java%0Bscript:alert(1)` — same-origin | **stricter than required**, fail-safe (see below) |
| `java<FF>script:alert(1)` | `false` | `https://…/java%0Cscript:alert(1)` — same-origin | **stricter than required**, fail-safe |
| `<TAB|LF|VT|FF|CR>javascript:alert(1)` (all five) | `false` | **`javascript:alert(1)`** — leading C0 is stripped | correct, all five |
| `mailto:hello@opencircuitsf.com`, `MAILTO:…` | `true` | `mailto:` | correct — not a script scheme, and `#0152` decided it is allowed |
| `data:text/html,evil`, `Data:…;base64,…` | `false` | **`data:`** | correct |
| `/assets/workshops/soldering-101/photo.jpg?v=2` | `true` | same-origin `https:` | correct |
| `?a=b` | `true` | same-origin `https:` | correct |
| `https://eventbrite.com/e/…?ref=site&utm_source=x` | `true` | off-site `https:` — allowed by design, this is the **link** rule | correct |

Only two of the five VT/FF rows deserve comment, and they are the *only*
place in the whole fixture where I could argue the answer is not the tightest
one available: V8's `trim()` strips VT and FF, so both twins reject
`java<VT>script:` even though the WHATWG parser leaves the VT in place and
resolves it same-origin. That is a reject where an accept would have been
safe. It is not a wrong answer — it is the fixture recording that both
languages fail safe on the same input, which is exactly what a parity fixture
should freeze. The reverse (accept where the browser goes somewhere
dangerous) does not occur anywhere in the file.

**The near-misses are the sharp part, and they are right.** These four rows
are where a hand-written whitespace list goes wrong, and the fixture gets all
four the way the engine does:

| Payload | `want` | why that is the right answer |
|---|---|---|
| `<U+FEFF BOM>javascript:alert(1)` | `false` | V8 trims the BOM, so a `.trim()` anywhere downstream yields a bare `javascript:`. This is `#0152`'s live bypass, now pinned. |
| `<U+0085 NEL>javascript:alert(1)` | `true` | V8 does **not** trim NEL and neither does the URL parser — it resolves same-origin, so it is genuinely safe. A Go twin using `unicode.IsSpace` would answer `false` and **fail this case**. |
| `<U+180E>javascript:alert(1)` | `true` | `Zs` before Unicode 6.3, `Cf` now; V8 does not trim it. A list written from an older reference would answer `false` and fail. |
| `<U+200B ZWSP>javascript:alert(1)` | `true` | `Cf`, not `Zs`, despite reading as "a space". Same trap. |

That is the direction that matters: the fixture is a two-sided vice. It fails
a twin that is too lax (BOM) *and* a twin that is too eager (NEL, U+180E,
U+200B).

### Generation is what it claims — coverage re-derived, not taken on trust

**The V8 sweep, re-run by me.** Every codepoint `0x0000`–`0x10FFFF`,
surrogates skipped, tested with `(c + 'Z').trim() !== c + 'Z'` under Node

### Ruling on decision 1 — fixture over deduplication: **correct.**

The reasoning in `## Fix` holds up, and the strongest form of it is not the
cost argument but this: a shared DSL would need its own two-language
correctness suite, which is *this fixture, one level up*. Deduplication does
not remove the need for a cross-language check; it relocates it. And the WASM
route's blocker is concrete rather than aesthetic — `isSafeLinkHref` and
`isSafeCoverImage` are called **synchronously** from `validateWorkshopForm`
and `hasExternalSignup` today, so an async instantiation at SPA startup is a
real refactor of every call site, and `wasm_exec.js` cannot come from a CDN
(`CLAUDE.md` §9). Multi-day, against two pure string predicates that have
diverged twice and been fixed both times.

The honest limitation, recorded rather than waved away: a fixture pins
*behavior on the payloads it lists*, so a rule change on an input it does not
cover stays green in both languages. In practice that gap is narrow here —
the realistic drift vectors are the whitespace set, the control-character
range, the scheme allowlist and the backslash normalization, and my three
targeted mutations hit all but one of those and every one went red. The
residual case is adding a brand-new scheme to one language's allowlist that
the fixture has no payload for (`sms:`, say); `ftp:`, `file:`, `tel:`,
`about:`, `blob:`, `data:` and `vbscript:` are all already pinned at `false`.
Worth knowing, not worth a WASM build step.

### Ruling on decision 2 — `#0155`'s capacity divergence stays out: **correct.**

Same *shape*, different *kind*, and the fixture's design does not fit it:

- The URL validators are a security boundary where the accepting side decides
  whether a `javascript:` URL reaches a rendered `href`. The capacity check is
  a client-side convenience over a server boundary (`isValidCapacity`) that is
  already correct and already enforced. The entire cost of the gap is one
  round trip and a less specific message.
- There is no ground truth to compute. The V8 sweep exists because "what does
  the engine strip" is an empirical fact with a machine-checkable answer.
  `2147483647` is a choice, not a fact — there is nothing to ask an oracle.
- The fixture's schema is `{rule, value: string, want: bool}`. A numeric bound
  needs a second, differently-shaped record type inside the same file, to
  guard a one-line fix.

The criterion asked the implementer to *decide and record*, and it did, with
reasoning that survives scrutiny. It also correctly did **not** file the
follow-up itself (`CLAUDE.md` §9) — that recommendation is passed to the
orchestrator with this review.
