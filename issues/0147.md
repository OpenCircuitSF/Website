## Description

Two small, related defects `#0139`'s review found while confirming that issue's fix.

**1. Whitespace is not empty.** `normalizeOptionalCampaignField` compares `*v == ""` without trimming, so a value of `"   "` is stored rather than cleared. The workshop editor trims client-side and so never sends one, but `CampaignEditor.svelte` sends `preheader` straight from `bind:value`, untrimmed — so a preheader left as spaces is persisted and then reloads looking blank. The real blanking gesture yields exactly `""`, which is why this is narrow rather than serious.

Trimming inside `normalizeOptionalCampaignField` (`strings.TrimSpace(*v) == ""`) fixes both editors at once and matches what `parseOptionalTime` already does.

**2. A comment that is simply wrong.** The comment added at `CampaignEditor.svelte:384` says it sends "the trimmed value". It does not trim.

## Root cause

`normalizeOptionalCampaignField` (`internal/handlers/admin_campaigns.go:430`)
is the single helper both `admin_campaigns.go` and `admin_workshops.go` route
every optional string field through, on both Create and Patch. It compared
`*v == ""` with no trimming, so a value consisting only of spaces (`"   "`)
failed that check and was returned unchanged — stored as literal spaces
rather than being treated as a clear (`nil`). `parseOptionalTime`, the
sibling helper for `starts_at`/`ends_at`, already trims before its blank
check (`strings.TrimSpace(*raw) == ""`), so this was an inconsistency between
two helpers that are supposed to implement the same "empty means unset"
convention, not two different behaviors by design.

Verified before changing it, not assumed: both `admin_campaigns.go`'s Create
(line 381) and Patch (line 508) call sites for `preheader`, and every
optional-string field in `admin_workshops.go`'s Create (lines 269–278) and
Patch (lines 385–429) call sites, all route through this one function. A
single change to it covers both editors' Create and Patch paths at once.

`CampaignEditor.svelte:384`'s comment ("send the trimmed value") was added by
`#0139` and was simply inaccurate — `saveDraft` sent `preheader` straight
from `bind:value` with no `.trim()` anywhere in the chain.

## Fix

- `internal/handlers/admin_campaigns.go` — `normalizeOptionalCampaignField`
  now checks `strings.TrimSpace(*v) == ""` instead of `*v == ""`. `strings`
  was already imported. This is the single change that fixes both the
  workshop and campaign patch (and create) paths, confirmed by reading both
  call sites rather than trusting the issue's claim.
- `web/src/views/admin/CampaignEditor.svelte` — `saveDraft` now sends
  `preheader: preheader.trim()` instead of the raw `$state` value, and the
  `#0139` comment was corrected: it no longer claims something the old code
  didn't do, and a new `#0147` comment explains the added trim and cites the
  whitespace-clearing helper change.

**Decision — client-side trim, criterion 4:** yes, add it.
`workshopAdmin.ts`'s `validateWorkshopForm` already unconditionally trims
every optional string field (`fields.summary.trim()`, etc.) before sending,
established by `#0139`. Trimming `preheader` in `CampaignEditor.svelte` before
the PATCH/PUT brings the two editors into the same convention, makes the
`#0139` comment (as corrected) actually true, and gives users the intuitive
behavior — a preheader with accidental trailing spaces around real text is
tidied on save, exactly as `workshopAdmin.ts` already does for its fields.
The server-side fix is not made redundant by this: it remains as
defense-in-depth for any other caller of the PATCH API (a future admin
client, a script, direct API use) that doesn't go through this Svelte
component.

**Decision — trimming real content at the Go layer: no, deliberately.**
`normalizeOptionalCampaignField` now only changes what counts as *blank*; a
non-blank value is still returned exactly as received, leading/trailing
whitespace and all. Reasons:
- It's the minimal, targeted fix the issue and `#0139`'s review both
  described (`strings.TrimSpace(*v) == ""`), not a broader "always trim
  optional strings" change to a helper twelve fields route through.
- The existing codebase is already inconsistent about server-side trimming
  of *non-blank* content — `admin_campaigns.go`'s Patch trims and stores
  `name`/`subject` (`trimmed := strings.TrimSpace(*req.Name); name =
  trimmed`) but checks-without-storing-trimmed for `body_md` (`if
  strings.TrimSpace(*req.BodyMD) == "" { ... }; bodyMD = *req.BodyMD`).
  Extending trimming to every `normalizeOptionalCampaignField` caller would
  paper over that inconsistency rather than fix this issue's actual defect.
- The two admin editors already trim their own optional string fields
  client-side before sending (`workshopAdmin.ts` unconditionally;
  `CampaignEditor.svelte`'s `preheader` now too, per the decision above), so
  real content reaching the server with meaningful leading/trailing
  whitespace is already the unusual case, not the common one — the server
  change here is about the blank/non-blank boundary, not about
  normalizing everyday content.

### One follow-up, not blocking

`CampaignEditor.svelte` sends `preheader.trim()` but never writes the
trimmed value back into its `$state`, and its `saveDraft` deliberately does
not refresh the editable buffer from the response (`campaign = updated`
only, per the `#0048` comment at line 310). `WorkshopEditor.svelte` does the
opposite — `fields = workshopToFormFields(workshop)` after every save — so
the two editors match on *trim before send* but not on *reflect what was
stored*. Consequence: after saving a preheader of `"   "`, the textarea
still shows the spaces and `dirty` is false, while the server has correctly
cleared the field; the divergence disappears on reload. Purely cosmetic and
never affects stored data, so it is not a bounce — worth a separate issue if
the editors are ever unified, and named here so the next reader of that
comment is not surprised.
