## Description

Six issues — `#0429`, `#0441`, `#0450`, `#0453`, `#0457`, `#0461` — have built and
widened a guard comparing how `godotenv` and systemd's `EnvironmentFile=` read
`.env.example`. **Every one of them measured the godotenv side by running it,
and reasoned about the systemd side from documentation.**

`#0461` made that explicit as a design constraint: it chose to forbid quoted
values partly because "systemd's quoting grammar is unverifiable in this
environment". `#0461`'s reviewer corrected the framing:

> The systemd side is not unverifiable — only unverifiable **on this laptop**.
> Production runs systemd on AL2023 (`CLAUDE.md` §7); one transient unit with an
> `EnvironmentFile=` would settle the trimming and quoting questions this entire
> lineage has reasoned around.

## Why it is worth doing, and what it would settle

The lineage's one *measured* systemd fact is the one that broke production's
boot path: `#0429`, where a trailing `#` comment became part of the value. Every
other systemd claim in the guard is inference.

That is not idle: `#0461`'s bounce was caused precisely by an **undisclosed
change of the systemd oracle** — from "keeps raw bytes" to one that trims
whitespace — which no sanity check could catch, because the original test
alphabet contains no space. A measured oracle would have made that swap
impossible to make silently.

Open questions a single measurement run would answer:

- does `EnvironmentFile=` trim leading and trailing whitespace from a value?
- does it strip matched single or double quotes, and does it differ between them?
- how does it treat a backslash mid-value, and one at end of line?
- how does it treat `$VAR`, `${VAR}` and `$(…)`?

## This is production, and needs approval

**Do not run anything on the box without the user's explicit approval** (§5b,
§9). Prepare the plan, state exactly what would run, and ask.

The shape that is defensible: a **transient** systemd unit in a scratch
directory, with its own `EnvironmentFile=` holding synthetic values, whose only
action is to print its environment to the journal. It touches no project
service, no real config, and no data.

**Never** point it at `/etc/opencircuit/config.env` — that is a secrets file, and
printing it to the journal would publish the session secret and database URL.
Synthetic values only.

## Acceptance criteria

1. A written plan the user can approve or decline in one read: the exact unit
   text, the exact synthetic `EnvironmentFile=` contents, the exact commands, and
   what is removed afterwards.
2. **Nothing runs on the box until the user says so.** If approval does not come,
   the plan itself is the deliverable and the issue closes as prepared-not-run.
3. If it does run: record the measured answers as **facts with their measurement
   command**, following `#0431`'s standing distinction — a statement that cites
   its source is fine; one that asserts a production value without measuring it
   is a defect.
4. Update the guard's doc comments where a measured answer replaces an inferred
   one. **Do not change guard behaviour in this issue** unless a measurement
   shows a check is actually wrong — and if it does, that is a separate issue,
   not a widening bolted onto this one (§8, `#0258`).
5. Record any question the run leaves open rather than closing it by inference.
