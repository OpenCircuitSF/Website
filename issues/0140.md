## Description

`scripts/check.sh` — the canonical verification command every issue is told to run, and the one `CLAUDE.md` §5 says "encodes every rule so they cannot be forgotten" — **reports success when the tests it ran failed.**

It sets `set -uo pipefail` in the outer shell, but runs every check through an inner shell:

```bash
run bash -c "go test $pkgs -p 2 -count=1 2>&1 | tail -$TAIL"
```

The inner `bash -c` does **not** inherit `pipefail`, so the pipeline's exit status is `tail`'s, which is always 0. Proof:

```
$ bash -c 'false | tail -1'; echo $?
0
$ bash -o pipefail -c 'false | tail -1'; echo $?
1
```

Every check is affected in every mode — `go build`, `go vet`, `go test`, `npm run check`, `npm test` — nine call sites in total. A compile error, a vet finding, a failing test, and a type error all print their output and are then reported as `VERIFICATION PASSED`.

The skip audit was unaffected and kept working, which is part of why this survived: the script *looked* rigorous.

## How it was found

`#0054`'s phase-3 review ran the suite and watched `scripts/check.sh` print `FAIL github.com/.../cmd/opencircuit` followed by `VERIFICATION PASSED` in the same output. That is what led it to look at the runner rather than the test.

The failing test it caught — `TestMountAndServe_WorkshopMutationInvalidatesSharedSEOSite` — had passed for its implementer only because a stray `npm run build` had overwritten the embedded placeholder. Reverting that file (correctly) broke the test, and the broken script said nothing.

## Acceptance criteria

- [x] Every inner shell runs with `pipefail` — `run bash -o pipefail -c` at all nine call sites
- [x] A deliberately failing package makes the script report `VERIFICATION FAILED` — confirmed against `./cmd/opencircuit/...`, which currently has a genuinely failing test: the script now prints `FAILED (1)` and `VERIFICATION FAILED`
- [ ] A guard test, or a self-check inside the script, that fails if the pipefail regression is ever reintroduced
- [ ] The tree's real state is established under the fixed script — a full `scripts/check.sh all` run whose result is read rather than assumed
- [ ] Any issue resolved this session whose verification rested solely on `VERIFICATION PASSED` is re-checked. `#0130`, `#0131`, `#0050`, `#0051`, `#0053`, `#0134` all cite it. Most also cite named test runs read directly, which are unaffected — establish which, if any, rest on the script alone

## Notes

Fixed immediately by the orchestrator rather than queued, because every dispatch in flight depends on the script telling the truth. The remaining criteria are the parts that need someone else's eyes: the regression guard, and the audit of what the broken script may have waved through.

**The general lesson is worth keeping.** The script was trusted precisely because it was written to be trustworthy — it centralizes `TEST_DATABASE_URL`, forces `-p 2`, refuses `-count=N`, audits for silent skips. None of that helps when the exit status is discarded one layer down. A verification tool that cannot fail is worse than no tool, because it converts every "I ran the suite" into false assurance.
