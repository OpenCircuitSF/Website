## Description

`scripts/check.sh` — the canonical verification command every issue is told to run, and the one `CLAUDE.md` §5 says "encodes every rule so they cannot be forgotten" — **reports success when the tests it ran failed.**

It sets `set -uo pipefail` in the outer shell, but runs every check through an inner shell:

```bash
run bash -c "go test $pkgs -p 2 -count=1 2>&1 | tail -$TAIL"
```

The inner `bash -c` does **not** inherit `pipefail`, so the pipeline's exit status is `tail`'s, which is always 0. Proof:

```
$ bash -c 'false | tail -1'; echo $?
0
$ bash -o pipefail -c 'false | tail -1'; echo $?
1
```

Every check is affected in every mode — `go build`, `go vet`, `go test`, `npm run check`, `npm test` — nine call sites in total. A compile error, a vet finding, a failing test, and a type error all print their output and are then reported as `VERIFICATION PASSED`.

The skip audit was unaffected and kept working, which is part of why this survived: the script *looked* rigorous.

## How it was found

`#0054`'s phase-3 review ran the suite and watched `scripts/check.sh` print `FAIL github.com/.../cmd/opencircuit` followed by `VERIFICATION PASSED` in the same output. That is what led it to look at the runner rather than the test.

The failing test it caught — `TestMountAndServe_WorkshopMutationInvalidatesSharedSEOSite` — had passed for its implementer only because a stray `npm run build` had overwritten the embedded placeholder. Reverting that file (correctly) broke the test, and the broken script said nothing.

## Implementation notes

**Regression guard (criterion 3).** Added a self-check inside `scripts/check.sh`
itself, right after the `run()` helper is defined, so it executes on every
invocation before any build/vet/test work starts — it cannot be skipped by
forgetting to run a separate test file:

```bash
BAD_SITES="$(grep -n 'run bash -c' "$REPO/scripts/check.sh" | grep -v 'pipefail' || true)"
if [ -n "$BAD_SITES" ]; then
  printf '...PIPEFAIL REGRESSION (#0140): scripts/check.sh has a "run bash -c" call site
  missing "-o pipefail"...' >&2
  echo "$BAD_SITES" >&2
  exit 2
fi
```

It scans the script's own source for any `run bash -c` call site that doesn't
also mention `pipefail` on the same line — i.e. exactly the regression shape
described above (`run bash -c "... | tail ..."` without `-o pipefail`).

Proved by mutation: removed `-o pipefail` from the `go_test` call site
(originally line 92, `run bash -o pipefail -c "go test $pkgs -p 2 -count=1
2>&1 | tail -$TAIL"` → `run bash -c "..."`), ran `scripts/check.sh go
./internal/audit/...`, and the guard fired immediately (before `go build` even
ran), exit code 2:

```
=== self-check: pipefail regression guard (#0140)
PIPEFAIL REGRESSION (#0140): scripts/check.sh has a "run bash -c" call site
missing "-o pipefail". That silently discards the piped command's exit status
(it becomes tail's, which is always 0), so a failing build/vet/test/npm run

issues/0140.md. Offending line(s):
```

## Notes

Fixed immediately by the orchestrator rather than queued, because every dispatch in flight depends on the script telling the truth. The remaining criteria are the parts that need someone else's eyes: the regression guard, and the audit of what the broken script may have waved through.

**The general lesson is worth keeping.** The script was trusted precisely because it was written to be trustworthy — it centralizes `TEST_DATABASE_URL`, forces `-p 2`, refuses `-count=N`, audits for silent skips. None of that helps when the exit status is discarded one layer down. A verification tool that cannot fail is worse than no tool, because it converts every "I ran the suite" into false assurance.

### Criterion 3 — attacking the guard

A source-grepping self-check has obvious evasions, so I enumerated them. "Broken"
means the form genuinely swallows the pipeline's exit status.

| Call-site form | Guard fires? | Genuinely broken? | Verdict |
|---|---|---|---|
| `run bash -c "…"` — the actual regression | yes | yes | correct |
| a new `run bash -c` site anywhere in the file | yes | yes | correct |
| `run bash -c \` ⏎ `"…"` | yes | yes | correct |
| `run bash \` ⏎ `-c "…"` | **no** | **yes** | gap |
| `run /bin/bash -c "…"` | **no** | **yes** | gap |
| `run bash··-c "…"` (two spaces) | **no** | **yes** | gap |
| `run env bash -c "…"` | **no** | **yes** | gap |
| `SH=bash; run $SH -c "…"` | **no** | **yes** | gap |
| `run sh -c "…"` | **no** | **yes** | gap |
| bare `bash -c "…"` without `run` | no | yes — worse; status never checked at all | gap |
| `run bash -c "…"  # pipefail handled elsewhere` | **no** | **yes** | gap — any same-line mention of the word defeats it |
| `run bash -c -o pipefail "…"` | no | **no** | correct not to flag |
| `run bash -eo pipefail -c "…"` | no | **no** | correct not to flag |
| `run bash -o pipefail -c "…"` — current | no | no | correct |

The two "safe" flag-order rows were probed, not assumed:

```
bash -c 'false | tail -1'                → 0    (the bug)
bash -o pipefail -c 'false | tail -1'    → 1
bash -c -o pipefail 'false | tail -1'    → 1
bash -eo pipefail -c 'false | tail -1'   → 1
```

The gap is real, and I reproduced it end to end rather than reasoning about it.
Rewriting the `go` mode's build site as

```bash
run bash \
  -c "false 2>&1 | tail -$TAIL"
```

evades the grep entirely and reproduces the original defect exactly:
`scripts/check.sh go ./internal/audit/...` printed `VERIFICATION PASSED` and
exited `0` with `false` as its build step.

**Judgement: the residual gap does not warrant a bounce.** Every evasion requires
rewriting the *form* of a call site. The regression that actually happened — and
the only one anyone plausibly reintroduces — is deleting `-o pipefail` from a line
that otherwise stays as it is, and that is caught at all nine sites and at any
newly added single-line site. `## Implementation notes` states the scope honestly
("doesn't also mention `pipefail` on the same line"), so no one is misled about
what is enforced. A guard that catches the real regression and says plainly what
it covers is the right scope here.

### Criterion 3 — can the guard itself break the script?

No false positive today. Exactly two lines contain `run bash -c`: line 48 (the
grep itself) and line 50 (the error message). Both survive `grep -v 'pipefail'`
only because each happens to contain that word on the same line. Line 40's comment
says `bash -c` without `run`, so it does not match. The filtered result is empty.

That self-exclusion is incidental rather than designed, and I confirmed it is
load-bearing: reformatting line 48 so the `grep -v 'pipefail'` moves onto a
continuation line makes the guard flag **itself**, exit `2` on every invocation,
and brick the canonical verification command. Not a bounce — the failure is loud,
immediate, and prints the offending line, which is the guard's own, so it
diagnoses itself. But it is the one edit to this file that must not be made
casually.

The load-bearing argument survives, with one boundary worth stating precisely.
The bug replaced the pipeline's status with `tail`'s, but `tail` still printed the
command's own output, and a failing package prints `FAIL pkg` where a passing one
prints `ok pkg`. So a verification quoting an `ok` line for **every** package in
its run is sound regardless of the banner — the discriminator lives in the
content, not in the discarded status. The one way content could have been lost is
`tail -40` truncating a failure off the top, and that cannot hide these: `go test`
emits a trailing `FAIL` sentinel plus a per-package status line, both inside the
last 40 lines of every run quoted above. No re-verification of the six is
warranted.

### Reported to the orchestrator, not filed (`CLAUDE.md` §9)

1. **Optional hardening of `scripts/check.sh`.** The grep guard is needed only
   because the invariant is spread across nine call sites. Funnelling them through
   one helper — `runpipe() { run bash -o pipefail -c "$1"; }` — would make the
   property structural instead of lint-enforced, delete the whole evasion surface
   in the table above, and remove the line-48 self-brick hazard. Cheap, and
   strictly better than grepping source. Not required for this issue.
2. **`scripts/testdb.sh` mishandles a mixed-case issue token** — unrelated to this
   issue, noticed during review, and `#0150` is currently live in that file.
   `scripts/testdb.sh create 0140revX` printed
   `…/opencircuit_test_0140revX` while Postgres folded the unquoted identifier to
   `…revx`, so the returned URL named a database that does not exist and every DB
   test failed with `SQLSTATE 3D000` — which reads exactly like a real test
   failure. `drop 0140revX` then failed silently and leaked the database. I
   dropped both leaked databases by their lowercase names. Lower-casing the token
   (or refusing a non-lowercase one) would prevent it.
