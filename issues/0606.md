## Description

Brennan, 2026-10-18, 10:42 pm, on production after the deploy: "When I go to
this page I do not see any Delete and redo option at all!"

`#0604` added the button to `OutreachPostCard` via
`cardButtons().takedown`. But since `#0582`, automatic channels (Bluesky,
Mastodon) render in `OutreachAnnouncement.svelte`'s "How it will look"
previews. `OutreachWorkshop.svelte` passes
`channelFilter={(c) => !sendsItself(c)}` to `OutreachPostCards`, so a
posted Bluesky or Mastodon post never reaches a card with the button. The
jsdom tests mounted `OutreachPostCards` directly and missed this.

## Acceptance criteria

- [x] In `OutreachAnnouncement.svelte`, each auto-channel preview whose post
      is `posted` shows **Delete and redo…**. It opens the same
      `OutreachConfirmDialog` copy and calls the same `#0604` API
      (`takedownOutreachPost` or the equivalent in `api.ts`). On success it
      calls `reload()`, so the post shows as a draft, the Post button and
      Reset return, and the posted summary updates. Errors show in the
      section's existing `role="alert"`.
- [x] Apply the same check to the Reminder and Last call wave rows
      (`OutreachWaveRow.svelte`) if they show posted auto posts without
      the button.
- [x] A behaviour test mounts **`OutreachWorkshop`**, not just the card,
      with a posted Bluesky post, and finds and uses the button. This is
      the gap that let `#0604` ship without it.
- [x] Modal, no-native-confirm, live-region and jargon guards stay green.
- [x] Verified with `ISSUE=0606 scripts/check.sh web`. Evidence is jsdom.

## Relation

- Follows `#0604`.

## Resolution

Posted Bluesky and Mastodon posts now show **Delete and redo…** in the announcement previews (`OutreachAnnouncement.svelte`), which is where automatic channels render since `#0582`. The Reminder and Last call wave rows embed the same component, so they get the button too.

## Resolution notes

- The button uses `cardButtons(...).takedown` (automatic and posted), the same check as `#0604`'s card, so the two cannot disagree.
- Confirming goes through `OutreachPostDialog mode="takedown"`. There is no native confirm, and the dialog cannot be closed while the request is running. It calls `takedownOutreachPost(post.id)` and then `onChange` + `reload()`, so Post and Reset come back. Errors show in the dialog and in the section's existing `role="alert"`. No new `role="status"` was added.
