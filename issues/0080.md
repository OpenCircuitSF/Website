## Description

`middleware.ClientIP` returns the rightmost `X-Forwarded-For` entry when the peer is loopback, but **never validates that the entry is an IP address**. Found during `#0077`'s review.

The consequence is worse than a bad log line. With `X-Forwarded-For: 1.1.1.1, not-an-ip` from a loopback client:

- `signup_ip` is an `INET` column, so the insert fails
- `#0026`'s handler returns its uniform `202` regardless — that is the whole security property
- **no subscriber row is created**

A person signs up, sees success, and is silently not subscribed. The same token also becomes a rate-limit bucket key.

A port on the rightmost entry (`203.0.113.5:4444`) has the same shape — stored and bucketed verbatim.

> 🟢 Resolved 2026-08-19 — `parseXFFIP` now validates the single trusted `X-Forwarded-For` hop before it can reach an `INET` column or a rate-limit bucket, and the reviewer reproduced **both halves** of the drop independently in a private `opencircuit_review0080` database rather than taking the report on trust: replaying the parent commit's `ClientIP` verbatim, `X-Forwarded-For: 1.1.1.1, not-an-ip` from a loopback peer returned `"not-an-ip"`, `subscribers.Store.Create` failed with `ERROR: invalid input syntax for type inet: "not-an-ip" (SQLSTATE 22P02)`, and a follow-up `SELECT count(*)` confirmed **zero** subscriber rows — the silent drop — while the shipped `ClientIP` on the identical request returned the peer and left **one** row with `signup_ip = 127.0.0.1`. Adversarial probing went well past the implementer's set and `parseXFFIP` held on every case: an IPv6 with a zone (`fe80::1%eth0`), a bracketed IPv6 with a port, a hostname, leading `+`/`-`, a bare `:`, a 5,000-character token, Arabic-Indic and fullwidth Unicode digits, IPv4-mapped forms bare and bracketed, CIDR notation, empty / non-numeric / out-of-range ports, leading-zero and out-of-range octets, an embedded NUL byte, a quoted IP, and a SQL-injection-shaped payload — **34 cases, no panics, and not one verbatim pass-through**; each either yielded a genuine IP or fell back to the peer. A 500,000-input fuzz over `parseXFFIP` found **0 violations** of the invariant that any non-empty return is `net.ParseIP`-valid, and every distinct value the two sweeps produced (7 from the adversarial table, 50 more from the fuzz and exotic-form set) cast cleanly to `INET` in PostgreSQL 16 — including the shapes where Go and Postgres could plausibly have disagreed (`::`, `::1.2.3.4`, `::ffff:0.0.0.0`, `64:ff9b::1.2.3.4`). The fallback was **read, not assumed** — `ClientIP` returns `peer` whenever `parseXFFIP` yields `""` — and confirmed empirically to return the *real* peer (`::1`, `203.0.113.77`), never a hardcoded loopback, with a non-loopback peer still ignoring `X-Forwarded-For` entirely; all of `#0077`'s edge cases (empty, whitespace-only, trailing comma, `,,,`, tabs, `::1`, `[::ffff:127.0.0.1]`, bare IPv6) re-ran unchanged. Because `handlers.clientIP` is a one-line delegation to `middleware.ClientIP` and `RateLimiter.Middleware` keys its bucket map off the same return value, the one guard genuinely closes both the consent-evidence and the rate-limit halves. `go build`, `go vet`, and `go test ./... -count=1` with `TEST_DATABASE_URL` exported are green with **zero failures and zero skips**, and `ff8dec7` touches `internal/middleware/` only.

## Severity

**Loopback-only after `#0077`**, which is what keeps this off the critical path — pre-`a651798` both were internet-reachable. Today it requires something already able to connect to `127.0.0.1:8080`, which on a single-purpose EC2 box means Apache or a local process. So this is a correctness and robustness defect rather than a live exploit — but the failure mode (a signup that reports success and does not exist) is bad enough to fix rather than document.

## Fix

`internal/middleware/clientip.go` gained `parseXFFIP(entry string) string`,
called from `ClientIP` in place of trusting `rightmostXFFEntry`'s output
directly:

1. `net.ParseIP(entry)` — if it's a bare IP, trust it as-is.
2. Otherwise `net.SplitHostPort(entry)` — if that succeeds and the host
   parses as an IP, use the bare host (port stripped, not stored verbatim).
3. Otherwise return `""`, and `ClientIP` falls back to the peer address —
   exactly the existing fallback path already used for an empty XFF header,
   so no new branch was needed in `ClientIP` itself.

`RateLimiter.Middleware` (`ratelimit.go`) keys its bucket map directly off
`ClientIP`'s return value, so the same fix closes the "unparseable token as
rate-limit bucket key" half of the issue with no separate change needed
there.

`[2001:db8::1]` returning the peer rather than `2001:db8::1` is correct but worth
naming: `net.SplitHostPort` requires a port, so a bracketed literal with none is
not recognised. The result is a *safe* value either way, and mod_proxy_http does
not emit that form.

**Fuzz.** 500,000 generated inputs (hex, dots, colons, brackets, `%`, `+`, `-`,
`/`, NUL, tabs, Unicode digits) through `parseXFFIP`: **0 violations** of the
invariant that a non-empty return is `net.ParseIP`-valid. This is also true by
construction — every non-`""` return path is guarded by a `net.ParseIP` call —
so the property is structural, not merely untested-against.

**The Go/Postgres gap.** The invariant above only matters if `net.ParseIP`-valid
implies `INET`-castable. Checked directly rather than assumed: all 57 distinct
values the sweeps produced were cast with `::inet` in PostgreSQL 16.14, **zero
errors**, including `::`, `::1.2.3.4`, `0:0:0:0:0:0:1.2.3.4`, `::ffff:0.0.0.0`,
`64:ff9b::1.2.3.4`, and `ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff`.

**The fallback is genuinely reached.** `ClientIP` calls `parseXFFIP` inside a
nested `if ip := …; ip != ""` and otherwise falls through to `return peer`; the
`""` return therefore lands on the same path an absent header takes. Confirmed
against a live peer rather than inferred:

| peer | XFF | `ClientIP` |
|---|---|---|
| `[::1]:9999` | `1.1.1.1, not-an-ip` | `::1` |
| `127.0.0.1:9999` | `1.1.1.1, not-an-ip` | `127.0.0.1` |
| `203.0.113.77:9999` | `1.1.1.1, not-an-ip` | `203.0.113.77` |
| `203.0.113.77:9999` | `1.1.1.1, 8.8.8.8` | `203.0.113.77` |

**Both consumers covered.** `internal/handlers/request.go`'s `clientIP` is
`return middleware.ClientIP(r)` and `subscribe.go` sets `SignupIP: clientIP(r)`;
`ratelimit.go` keys its bucket map off `ClientIP(r)` directly. One
implementation, so the guard cannot be bypassed by one consumer and not the
other.

## Notes

`#0026`'s uniform `202` is exactly what makes this invisible: the endpoint cannot signal the failure by design, and it should not start. The fix belongs in `ClientIP`, not in the handler.

`#0077`'s reviewer verified the surrounding parse is otherwise solid — empty header, whitespace-only, trailing commas, `,,,`, tabs, IPv6 `::1` and `[::ffff:127.0.0.1]` all fall back to the peer without panicking, and an empty key is only possible if `RemoteAddr` itself is empty, which `net/http` never produces.
