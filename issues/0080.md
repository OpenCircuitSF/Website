# 0080 — An unparseable X-Forwarded-For entry silently drops a signup

| | |
|---|---|
| **Status** | open |
| **Module** | middleware / subscribers |
| **Platform** | All |
| **Phase** | 3 — Mailing list capture |
| **First seen** | 2026-08-19 |

## Description

`middleware.ClientIP` returns the rightmost `X-Forwarded-For` entry when the peer is loopback, but **never validates that the entry is an IP address**. Found during `#0077`'s review.

The consequence is worse than a bad log line. With `X-Forwarded-For: 1.1.1.1, not-an-ip` from a loopback client:

- `signup_ip` is an `INET` column, so the insert fails
- `#0026`'s handler returns its uniform `202` regardless — that is the whole security property
- **no subscriber row is created**

A person signs up, sees success, and is silently not subscribed. The same token also becomes a rate-limit bucket key.

A port on the rightmost entry (`203.0.113.5:4444`) has the same shape — stored and bucketed verbatim.

## Severity

**Loopback-only after `#0077`**, which is what keeps this off the critical path — pre-`a651798` both were internet-reachable. Today it requires something already able to connect to `127.0.0.1:8080`, which on a single-purpose EC2 box means Apache or a local process. So this is a correctness and robustness defect rather than a live exploit — but the failure mode (a signup that reports success and does not exist) is bad enough to fix rather than document.

## Acceptance criteria

- [ ] `net.ParseIP` the trusted rightmost entry; fall back to the peer address when it does not parse
- [ ] A port on the rightmost entry is stripped or rejected, not stored verbatim
- [ ] A test proves the silently-dropped signup is gone: `X-Forwarded-For: 1.1.1.1, not-an-ip` from a loopback peer must still create the subscriber row, with `signup_ip` set to the fallback
- [ ] **Mutation-proven** — remove the guard, watch the test fail, restore, report output
- [ ] Rate-limit bucketing never keys on an unparseable token
- [ ] `go build ./...`, `go vet ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported and zero skips

## Notes

`#0026`'s uniform `202` is exactly what makes this invisible: the endpoint cannot signal the failure by design, and it should not start. The fix belongs in `ClientIP`, not in the handler.

`#0077`'s reviewer verified the surrounding parse is otherwise solid — empty header, whitespace-only, trailing commas, `,,,`, tabs, IPv6 `::1` and `[::ffff:127.0.0.1]` all fall back to the peer without panicking, and an empty key is only possible if `RemoteAddr` itself is empty, which `net/http` never produces.
