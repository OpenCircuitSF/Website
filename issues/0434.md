## Description

Workshop cover images live at `/var/www/media`, served by an Apache carve-out
(`docs/media.md`). They are deliberately **not** in source control — the user's
decision, recorded in `#0416`.

`docs/media.md` names the consequence itself:

> These files are not in git and are not backed up. The nightly job is
> `pg_dump` only… **A rebuilt box comes back with the database intact and every
> workshop image broken.**

The database keeps `cover_image` pointing at `/media/…`, so a restore produces
workshops whose images 404 — the data survives and the content does not.

**The user has asked for the media folder to be included in backups.**

## Root cause

There was no filesystem leg at all: `scripts/db/backup.sh` only ever ran
`pg_dump`, and nothing in `deploy/systemd/` touched `/var/www/media`. Adding
one is prepared here; **it is not yet running anywhere**, since `#0435` (the
prerequisite this issue names) has not installed the timer this would extend,
and installing units on the box needs the user's go-ahead per acceptance #6.

## Fix

Two new scripts, one systemd change, no doc claim flipped to "backed up" yet:

- **`scripts/db/backup-media.sh`** (new) — tars `/var/www/media` into
  `$BACKUP_ROOT/media/`, the *same* root `backup.sh` already writes database
  dumps under, so `pull-backups.sh`'s existing whole-root rsync carries media
  offsite too with zero changes to that script. Content-addressed rather than
  "dump every night": it hashes the source tree (relative path + sha256 per
  file, sorted — reproducible across GNU/BSD tool differences) and skips
  writing a new archive when that manifest matches the one recorded next to
  the last archive it wrote. Pruning (`MEDIA_BACKUP_RETENTION_DAYS`, default
  14, falling back to `BACKUP_RETENTION_DAYS`) still runs every time, but in
  steady state — these files have no upload endpoint (`docs/media.md`), so
  they change only when an operator manually `scp`s a new one — this keeps
  exactly one archive on disk rather than multiplying an unchanged directory
  by the retention window. Measured against the two live covers (152 KB
  total): even the naive "dump every night" policy would cost under 2.2 MB at
  14 nights, so the dedup is headroom against larger/more frequent uploads
  later, not a fix for today's footprint on the `t4g.nano`.
- **`scripts/db/restore-media.sh`** (new) — companion to `restore.sh`.
  Extracts into a target directory, then explicitly `chown`s to
  `RESTORE_MEDIA_OWNER` (default `ec2-user:ec2-user`, matching what's on the
  box today) and `chmod`s directories `0755`/files `0644` — matching what
  Apache's `<Directory "/var/www/media">` carve-out needs and what
  `docs/media.md`'s troubleshooting table already lists 403s as caused by.
  `chown` failure (e.g. run without root, as in a local drill) is a loud
  non-fatal warning, not a silent no-op.
- **`deploy/systemd/opencircuit-backup.service`** — a second `ExecStart=`
  line runs `backup-media.sh` after `backup.sh`; systemd runs multiple
  `ExecStart=` in a `Type=oneshot` unit in order, and a non-zero exit from
  either marks the unit failed, so the existing
  `OnFailure=opencircuit-backup-alert.service` alert path covers the media
  leg too with no changes of its own. `deploy/systemd/README.md` documents
  this.
- **`docs/media.md`** — an additive, dated note under the existing "not
  backed up" bullet, per acceptance #5: it records that the scripts and unit
  now exist, and explicitly says the "not backed up" sentence stays true
  until this is actually installed and running in production. It does not
  touch that sentence itself.

**Permissions, stated exactly (acceptance #4, and the `## Obstacles`-shaped
callout the brief asked for):**

- **Reading `/var/www/media`:** no new grant needed. Verified read-only on
  the box (2026-09-05): `/var/www` is `root:root 0755`, `/var/www/media` is
  `ec2-user:ec2-user 0755`, its two files are `ec2-user:ec2-user 0644` — all
  readable via the "other" bits Apache already relies on to serve them, so
  `BACKUP_RUN_AS=postgres` can traverse and read with no change.
- **Writing `$BACKUP_ROOT`:** exactly the same open gap `#0435` already
  documents — `/var/backups/postgres` is `root:root 0700` today, so
  `postgres` cannot `mkdir` under it. This issue needs `#0435`'s fix, not a
  second one. The command that clears it belongs to `#0435`, not here.
- **Nothing was installed on the box.** No unit was copied, no timer
  touched, no file created under `/var/backups/postgres` or `/var/www/media`.
  Everything above was built and proved against scratch directories locally
  (see `## Verification`), per acceptance #6.

## Verification

Local, scratch-only (production has not been touched — see acceptance #6):

- `bash -n scripts/db/backup-media.sh` and `bash -n scripts/db/restore-media.sh`
  — both clean.
- `shellcheck scripts/db/backup-media.sh` — one informational `SC2016` on a
  single-quoted heredoc-style string, which is deliberate (the `$1` inside is
  meant to expand in the invoked sub-shell, not the outer one). `shellcheck
  scripts/db/restore-media.sh` — clean, no findings.
- End-to-end drill against namespaced scratch paths
  (`/private/tmp/.../scratchpad/0434-{src,root,restore,restore-noowner}`,
  removed after):
  1. First run against a 2-file source (`MEDIA_SOURCE_DIR` set,
     `BACKUP_ROOT` scratch, `BACKUP_RUN_AS=""`) wrote
     `media-<timestamp>.tar.gz`, `media-latest.tar.gz`, and
     `media-latest.manifest`.
  2. A second run with unchanged content printed "Unchanged since the last
     backup ... skipping a new archive" and left exactly one archive on
     disk.
  3. Modifying one file and re-running wrote a second, distinct archive.
  4. Backdating the first archive to 30 days old and re-running with
     `MEDIA_BACKUP_RETENTION_DAYS=14` pruned exactly that one file and kept
     the two recent ones — proving retention prunes by age without touching
     the fresh write.
  5. `restore-media.sh` against `media-latest.tar.gz`: `diff` of `find |
     sort` between source and restored tree showed identical **names**;
     `diff` of `find | xargs shasum -a 256` showed identical **content**;
     `stat` confirmed `0755`/`0644` applied. With the default
     `RESTORE_MEDIA_OWNER=ec2-user:ec2-user` and no root, `chown` failed and
     the script printed the documented non-fatal warning rather than
     silently continuing as a different owner. A second run with
     `RESTORE_MEDIA_OWNER=""` confirmed the opt-out skips the chown step
     cleanly.
  6. `MEDIA_SOURCE_DIR` pointed at a nonexistent path exits 2 with a named
     error, and `restore-media.sh` given a nonexistent archive exits 2 with
     a named error — neither fails silently.
- `ISSUE=0434 scripts/check.sh go ./internal/db/... ./internal/handlers/...`
  — `uptime` before the run: load average ~6.5 (machine busy but under the
  ~8 threshold, not attributed to this work). `go build`, `go vet`, and
  `gofmt -l` clean. `go test ./internal/db/... ./internal/handlers/... -p 2`:
  `internal/db` **ok in 0.486s** (real elapsed, ran against

## Gotchas

- `find` on this development machine resolves, in the interactive tool
  shell, to a Claude Code sandboxing wrapper (reports itself as `bfs`) — but
  a script actually invoked via `bash <path>` gets the real `/usr/bin/find`
  (BSD find, no `--version`, no `-printf`), which is what both new scripts
  are written against and were tested with. Worth knowing if a future agent
  tests a `find` invocation by pasting it into the tool shell directly
  rather than running the script file — it may see different `find`
  behavior than the script actually gets.
- macOS ships BSD `sort`/`xargs`/`find`, none of which have GNU's
  `-printf`/`--version` flags the way Amazon Linux's do; both scripts were
  written to the POSIX-ish common subset (`-print0` / `sort -z` / `xargs
  -0`, no `-printf`, no `stat` at all) specifically so the same script runs
  unmodified on both, rather than branching on `uname`.

## Acceptance criteria

1. `/var/www/media` is captured by whatever `#0435` establishes, on the same
   schedule.
2. **A restore is proved end to end**: files come back, with their names, and
   `cover_image` paths resolve against the restored set. Row counts alone do not
   demonstrate this.
3. Retention matches the database dumps' policy, or differs deliberately with a
   reason. Images are larger and compress poorly; say what that does to disk on
   a `t4g.nano`.
4. Permissions and ownership survive — `/var/www/media` is `ec2-user`-owned and
   Apache must read it. A restore that lands root-owned files serves 403s, which
   `docs/media.md`'s troubleshooting table already lists as a symptom.
5. `docs/media.md`'s "not backed up" statement is updated **once it is false**,
   not before.
6. **Changing production's backup configuration needs the user's go-ahead.**
   Prepare and verify what you can without it; say what remains.
