## Description

Workshop cover images live at `/var/www/media`, served by an Apache carve-out
(`docs/media.md`). They are deliberately **not** in source control — the user's
decision, recorded in `#0416`.

`docs/media.md` names the consequence itself:

> These files are not in git and are not backed up. The nightly job is
> `pg_dump` only… **A rebuilt box comes back with the database intact and every
> workshop image broken.**

The database keeps `cover_image` pointing at `/media/…`, so a restore produces
workshops whose images 404 — the data survives and the content does not.

**The user has asked for the media folder to be included in backups.**

## Root cause

There was no filesystem leg at all: `scripts/db/backup.sh` only ever ran
`pg_dump`, and nothing in `deploy/systemd/` touched `/var/www/media`. Adding
one is prepared here; **it is not yet running anywhere**, since `#0435` (the
prerequisite this issue names) has not installed the timer this would extend,
and installing units on the box needs the user's go-ahead per acceptance #6.

## Fix

Two new scripts, one systemd change, no doc claim flipped to "backed up" yet:

- **`scripts/db/backup-media.sh`** (new) — tars `/var/www/media` into
  `$BACKUP_ROOT/media/`, the *same* root `backup.sh` already writes database
  dumps under, so `pull-backups.sh`'s existing whole-root rsync carries media
  offsite too with zero changes to that script. Content-addressed rather than
  "dump every night": it hashes the source tree (relative path + sha256 per
  file, sorted — reproducible across GNU/BSD tool differences) and skips
  writing a new archive when that manifest matches the one recorded next to
  the last archive it wrote. Pruning (`MEDIA_BACKUP_RETENTION_DAYS`, default
  14, falling back to `BACKUP_RETENTION_DAYS`) still runs every time, but in
  steady state — these files have no upload endpoint (`docs/media.md`), so
  they change only when an operator manually `scp`s a new one — this keeps
  exactly one archive on disk rather than multiplying an unchanged directory
  by the retention window. Measured against the two live covers (152 KB
  total): even the naive "dump every night" policy would cost under 2.2 MB at
  14 nights, so the dedup is headroom against larger/more frequent uploads
  later, not a fix for today's footprint on the `t4g.nano`.
- **`scripts/db/restore-media.sh`** (new) — companion to `restore.sh`.
  Extracts into a target directory, then explicitly `chown`s to
  `RESTORE_MEDIA_OWNER` (default `ec2-user:ec2-user`, matching what's on the
  box today) and `chmod`s directories `0755`/files `0644` — matching what
  Apache's `<Directory "/var/www/media">` carve-out needs and what
  `docs/media.md`'s troubleshooting table already lists 403s as caused by.
  `chown` failure (e.g. run without root, as in a local drill) is a loud
  non-fatal warning, not a silent no-op.
- **`deploy/systemd/opencircuit-backup.service`** — a second `ExecStart=`
  line runs `backup-media.sh` after `backup.sh`; systemd runs multiple
  `ExecStart=` in a `Type=oneshot` unit in order, and a non-zero exit from
  either marks the unit failed, so the existing
  `OnFailure=opencircuit-backup-alert.service` alert path covers the media
  leg too with no changes of its own. `deploy/systemd/README.md` documents
  this.
- **`docs/media.md`** — an additive, dated note under the existing "not
  backed up" bullet, per acceptance #5: it records that the scripts and unit
  now exist, and explicitly says the "not backed up" sentence stays true
  until this is actually installed and running in production. It does not
  touch that sentence itself.

**Permissions, stated exactly (acceptance #4, and the `## Obstacles`-shaped
callout the brief asked for):**

- **Reading `/var/www/media`:** no new grant needed. Verified read-only on
  the box (2026-09-05): `/var/www` is `root:root 0755`, `/var/www/media` is
  `ec2-user:ec2-user 0755`, its two files are `ec2-user:ec2-user 0644` — all
  readable via the "other" bits Apache already relies on to serve them, so
  `BACKUP_RUN_AS=postgres` can traverse and read with no change.
- **Writing `$BACKUP_ROOT`:** exactly the same open gap `#0435` already
  documents — `/var/backups/postgres` is `root:root 0700` today, so
  `postgres` cannot `mkdir` under it. This issue needs `#0435`'s fix, not a
  second one. The command that clears it belongs to `#0435`, not here.
- **Nothing was installed on the box.** No unit was copied, no timer
  touched, no file created under `/var/backups/postgres` or `/var/www/media`.
  Everything above was built and proved against scratch directories locally
  (see `## Verification`), per acceptance #6.

## Gotchas

- `find` on this development machine resolves, in the interactive tool
  shell, to a Claude Code sandboxing wrapper (reports itself as `bfs`) — but
  a script actually invoked via `bash <path>` gets the real `/usr/bin/find`
  (BSD find, no `--version`, no `-printf`), which is what both new scripts
  are written against and were tested with. Worth knowing if a future agent
  tests a `find` invocation by pasting it into the tool shell directly
  rather than running the script file — it may see different `find`
  behavior than the script actually gets.
- macOS ships BSD `sort`/`xargs`/`find`, none of which have GNU's
  `-printf`/`--version` flags the way Amazon Linux's do; both scripts were
  written to the POSIX-ish common subset (`-print0` / `sort -z` / `xargs
  -0`, no `-printf`, no `stat` at all) specifically so the same script runs
  unmodified on both, rather than branching on `uname`.

## Review notes

> 🔴 Bounced 2026-09-05 (review, Opus). One defect, and it defeats the issue's
> whole purpose: in steady state the media backup **deletes its own only
> archive and never writes another**. Everything else in this change is sound
> and should be kept — the fix below is ~6 lines in one file.

### The defect: dedup + age-based pruning erase the last copy

`backup-media.sh` skips writing an archive when the content manifest matches
(lines 154-155), then prunes by **age** every run (lines 177-179). Those two
are individually correct and jointly fatal, because the skip path means the
retained archive keeps getting older while nothing replaces it. After
`MEDIA_BACKUP_RETENTION_DAYS` nights with unchanged content — which the
script's own header says is the *expected* state ("the only way a file under
MEDIA_SOURCE_DIR changes is a manual `scp` by an operator, which is rare") —
the single archive ages past retention and is deleted. The manifest still
matches on every subsequent run, so **no archive is ever written again**.

`backup.sh` carries the invariant this was copied from — "can never prune away
the only copy — today's dump has age 0" (`backup.sh` line 193), reproduced at
`backup-media.sh` lines 175-176. That invariant holds only because `backup.sh`
writes a dump on **every** run. `backup-media.sh` deliberately does not, so the
comment is now false and the guarantee is gone.

Reproduced locally against scratch paths (`.../scratchpad/0434r/{src2,root2}`,
removed after), invoking the script with `bash`, not pasting its innards:

    === night 1: first backup ===
    Content changed (or no prior manifest) — writing a fresh archive.
        ok — 4.0K
    media-20260905-083359Z.tar.gz
    media-latest.manifest
    media-latest.tar.gz

    (archive backdated to 2026-08-15 to simulate 15 nights, content untouched)

    === night 16: run again, content still unchanged, retention 14 ===
    Unchanged since the last backup (manifest matches .../media-latest.manifest) — skipping a new archive.
        pruned 1 archive(s) older than 14d
    --- what is left in the media dir now:
    media-latest.manifest
    media-latest.tar.gz

    === night 17: run again ===
    Unchanged since the last backup (manifest matches .../media-latest.manifest) — skipping a new archive.
    Done — media backup complete.
    rc=0
    --- media dir:
    -rw-r--r--  77 media-latest.manifest
    lrwxr-xr-x  29 media-latest.tar.gz -> media-20260905-083359Z.tar.gz
    --- does media-latest.tar.gz resolve?
    DANGLING / MISSING -- no restorable archive

Three things make this worse than an ordinary bug:

1. **It exits 0.** `OnFailure=opencircuit-backup-alert.service` never fires.
   The journal line each night is "Unchanged … skipping a new archive", which
   reads like success.
2. **It destroys the offsite copy too.** `scripts/db/pull-backups.sh` line 81
   runs `rsync -avz --delete-after`, so once the server-side archive is pruned
   the Mac mini's copy is deleted on the next pull. Both copies, gone.
3. **`docs/media.md` would by then claim the gap is closed**, so the failure
   this issue exists to prevent — a rebuilt box with no workshop images —
   returns silently, on a timer, roughly two weeks after install.

### Remedy — make both changes in `scripts/db/backup-media.sh`, nothing else

**(a) Never prune the archive `media-latest.tar.gz` points at.** Replace the
prune block (lines 175-179) with:

    # Prune old archives (after any fresh write, so today's archive — age 0 — can
    # never be the thing pruned away, matching backup.sh's own ordering).
    #
    # #0434 review: unlike backup.sh, this script does NOT write an archive on
    # every run — an unchanged source takes the skip path above. So "age 0"
    # alone does not protect the last copy: with no edits, the one archive on
    # disk ages past retention and gets deleted, and the manifest still matches
    # forever after, so nothing replaces it. Exclude whatever media-latest
    # currently resolves to, so the newest archive is retained regardless of age.
    keep_args=()
    if [ -L "$dir/media-latest.tar.gz" ]; then
      keep_target="$(readlink "$dir/media-latest.tar.gz")"
      [ -n "$keep_target" ] && keep_args=(! -name "$keep_target")
    fi
    pruned="$(find "$dir" -maxdepth 1 -type f -name 'media-*.tar.gz' \
                ${keep_args[@]+"${keep_args[@]}"} \
                -mtime +"$MEDIA_BACKUP_RETENTION_DAYS" -print -delete | wc -l | tr -d ' ')"
    [ "$pruned" -gt 0 ] && echo "    pruned $pruned archive(s) older than ${MEDIA_BACKUP_RETENTION_DAYS}d"

The `${keep_args[@]+"${keep_args[@]}"}` form is required — it is the same
bash-3.2 empty-array guard the file already uses for `runner` at line 159, and
a bare `"${keep_args[@]}"` trips `set -u` on macOS bash 3.2.

**(b) Do not take the skip path when the archive is gone.** Change line 154
from:

    if [ -f "$manifest_file" ] && [ "$new_manifest" = "$(cat "$manifest_file")" ]; then

to:

    if [ -f "$manifest_file" ] && [ -e "$dir/media-latest.tar.gz" ] && [ "$new_manifest" = "$(cat "$manifest_file")" ]; then

`-e` follows the symlink, so a dangling `media-latest.tar.gz` is false and the
script writes a fresh archive. This is the general guard: it also recovers from
an archive lost to a manual cleanup, a full disk, or a partial rsync, none of
which (a) covers. Make both changes, not one — (a) prevents the loss, (b)
recovers from it.

Add a matching line to the header's retention rationale so the "keeps exactly
one archive on disk indefinitely" claim (lines 37-38) is actually true.

### Reservation, stated but not blocking

The content-addressed dedup is a lot of moving parts for two files totalling
152 KB on a `t4g.nano` — the header itself concedes the naive policy would cost
under 2.2 MB at 14 nights. The manifest is a second piece of state that must
stay consistent with the archive beside it, and the defect above is exactly the
inconsistency that state made possible; a plain "tar it every night, prune by
age" has no such failure mode. This is **not** grounds to bounce and should not
be redesigned — with fixes (a) and (b) the mechanism is sound, and the
headroom argument for larger future covers is reasonable. Recorded only so the
tradeoff is on the record.
