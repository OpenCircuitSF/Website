## Description

Workshop cover images live at `/var/www/media`, served by an Apache carve-out
(`docs/media.md`). They are deliberately **not** in source control — the user's
decision, recorded in `#0416`.

`docs/media.md` names the consequence itself:

> These files are not in git and are not backed up. The nightly job is
> `pg_dump` only… **A rebuilt box comes back with the database intact and every
> workshop image broken.**

The database keeps `cover_image` pointing at `/media/…`, so a restore produces
workshops whose images 404 — the data survives and the content does not.

**The user has asked for the media folder to be included in backups.**

## Ordering — read this first

**[#0435](0435.md) must land first.** The backup timer was never installed, so
there is currently **no** backup job to extend. Adding a filesystem leg to a job
that does not run would be building on nothing.

## Acceptance criteria

1. `/var/www/media` is captured by whatever `#0435` establishes, on the same
   schedule.
2. **A restore is proved end to end**: files come back, with their names, and
   `cover_image` paths resolve against the restored set. Row counts alone do not
   demonstrate this.
3. Retention matches the database dumps' policy, or differs deliberately with a
   reason. Images are larger and compress poorly; say what that does to disk on
   a `t4g.nano`.
4. Permissions and ownership survive — `/var/www/media` is `ec2-user`-owned and
   Apache must read it. A restore that lands root-owned files serves 403s, which
   `docs/media.md`'s troubleshooting table already lists as a symptom.
5. `docs/media.md`'s "not backed up" statement is updated **once it is false**,
   not before.
6. **Changing production's backup configuration needs the user's go-ahead.**
   Prepare and verify what you can without it; say what remains.
