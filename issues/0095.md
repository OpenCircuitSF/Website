## Description

`web/src/lib/subscribe.ts`'s `COMPLAINED_NO_RESUBSCRIBE_MESSAGE` is meant to be the
same sentence `internal/handlers/preferences.go`'s `patchUnsubscribe` returns for a
no-op PATCH against an already-complained row. Three separate doc comments assert that
guarantee. **Nothing checks it.**

It survived exactly one edit before drifting. `#0090`'s bounce fix added
`"at hello@opencircuitsf.com"` to the server string and left the client string
unchanged, and the divergence was invisible to all 155 frontend tests and the entire Go
suite. It was caught only because a reviewer read both strings character by character.

Worse, the same commit *corrected* the now-false "word for word" claim in
`subscribe.ts` while **newly authoring the identical false claim** in
`PreferenceCenter.svelte`, twenty lines away — where it stands as the stated
justification for the whole split design. A comment is not the right instrument for an
invariant that two files must jointly maintain.

## Root cause

`COMPLAINED_NO_RESUBSCRIBE_MESSAGE_LEAD` / `_TAIL` / `COMPLAINED_CONTACT_EMAIL` in
`web/src/lib/subscribe.ts` and the no-op `message` string built in
`internal/handlers/preferences.go`'s `patchUnsubscribe` were kept in sync by three doc
comments asking a human to remember, with nothing that would fail a build if the
promise broke. It already broke once (`#0090`), invisibly to the whole test suite.

## Fix

Added `internal/handlers/complained_copy_parity_test.go`, in the same shape as
`#0071`'s `routes_parity_test.go` and `#0082`/`#0083`'s `docs_parity_test.go`:
filesystem-only, no database, parsing `web/src/lib/subscribe.ts` directly and
comparing it against `preferences.go`.

- `parseTSStringConst` extracts an `export const NAME = <literal>[ + <literal>...];`
  declaration's composed string value from `subscribe.ts`, concatenating every quoted
  segment in order regardless of quote style (`subscribe.ts` mixes single- and
  double-quoted segments because `LEAD`'s second half contains an apostrophe).
- Two anchored regexes pull the two Go-side halves out of `preferences.go`'s
  `message = "..." + complainedContactEmail + "..."` assignment and its
  `complainedContactEmail` const, in the same deliberately format-sensitive style as
  `routes_parity_test.go` — a parse failure (`complainedCopyParseError`) is reported
  distinctly from a content mismatch, so a reformat reads as "fix the parser," not as a
  false drift alarm.
- `TestComplainedCopyParity_LeadTailComposeToServerMessage` asserts
  `goMessageBeforeAddress == "No change: " + lowerFirst(tsLead)` and
  `goMessageAfterAddress == tsTail` — the exact composition rule `subscribe.ts`'s doc
  comment already stated (`server === "No change: " + lowerFirst(COMPLAINED_NO_RESUBSCRIBE_MESSAGE)`),
  now checked instead of asserted.
- `TestComplainedCopyParity_ContactEmail` asserts `preferences.go`'s
  `complainedContactEmail` and `subscribe.ts`'s `COMPLAINED_CONTACT_EMAIL` name the
  same address.
- Corrected the three doc comments identified in the Description (`subscribe.ts`'s
  `COMPLAINED_NO_RESUBSCRIBE_MESSAGE` doc, two spots in `subscribe.test.ts`'s
  `#0095` references, and `PreferenceCenter.svelte`'s HTML comment) to point at
  `TestComplainedCopyParity_LeadTailComposeToServerMessage` by name instead of
  asserting an unenforced promise.

**Kept narrow, not generalised**, per this issue's own Notes ("if not, say so and
keep it narrow"): the CampaignProgress SSE payload key-set assertion
(`internal/handlers/campaign_progress_test.go`,
`TestCampaignProgressPublisher_PublishesJSONFrameToBroker`) that the Notes ask this
guard to "generalise or subsume" is a structurally different problem — it compares a
hand-typed Go struct's JSON keys against a TypeScript `interface` (an object-type
declaration, not a set of string constants), and is checked in only one direction
already (Go → wire; the wire → TS direction is unchecked, exactly as the Notes
describe). Building one parser that handles both a JS string-literal-concatenation
declaration and a TypeScript interface's field list is a different, larger project
than this issue's acceptance criteria ask for, and guessing at that shared shape now
risks exactly the kind of invented convention `CLAUDE.md` and this project's history
warn against. Reporting it back rather than folding it in silently — see the
subagent's final report for a fuller description a future issue could use.

### Mutation testing

Both directions proved to fail, then were reverted and hash-verified restored (per
`CLAUDE.md` §8a — copied the two files aside first rather than using `git stash`,
since two other agents had uncommitted work in the tree at the time):

- **Go-side mutation** — changed `preferences.go`'s `"Contact us at "` to
  `"Please contact us at "`. Result:
  ```
  --- FAIL: TestComplainedCopyParity_LeadTailComposeToServerMessage (0.00s)
      complained_copy_parity_test.go:162: complained-copy parity: preferences.go's
      no-op message text before the contact address does not equal "No change: " +
      lowerFirst(subscribe.ts's COMPLAINED_NO_RESUBSCRIBE_MESSAGE_LEAD)
        preferences.go:   "No change: ... Please contact us at "
        computed from TS: "No change: ... Contact us at "
  ```
  Reverted; `shasum -a 256` matched the backup taken before the edit.
- **TypeScript-side mutation** — changed `subscribe.ts`'s
  `COMPLAINED_NO_RESUBSCRIBE_MESSAGE_TAIL` from `' if you believe this is a
  mistake.'` to `' if you think this is a mistake.'`. Result:
  ```
  --- FAIL: TestComplainedCopyParity_LeadTailComposeToServerMessage (0.00s)
      complained_copy_parity_test.go:168: ... does not equal subscribe.ts's
      COMPLAINED_NO_RESUBSCRIBE_MESSAGE_TAIL
        preferences.go: " if you believe this is a mistake."
        subscribe.ts:   " if you think this is a mistake."
  ```
  Reverted; `shasum -a 256` matched the backup taken before the edit.

Both mutations were caught by the same test in the direction the acceptance criteria
require ("fails when either side is edited alone — mutate both directions
independently").

## Gotchas

`subscribe.ts` mixes single- and double-quoted string literals within one
declaration's concatenation (`'...' + "can't..."`) because one segment contains an
apostrophe. `parseTSStringConst`'s literal regex (`tsStringLiteralRe`) has to accept
either delimiter per-literal rather than assuming one for the whole declaration, and
does — verified directly: `TestComplainedCopyParity_LeadTailComposeToServerMessage`
passes against the real file, which would fail with a truncated `LEAD` (missing its
double-quoted second half) had the parser only handled one quote style.

## Why a test is the right instrument here

This repository has already built exactly this guard, twice, and both times because the
same thing went wrong:

- `internal/db/docs_parity_test.go` (`#0082`/`#0083`) — the docs table drifted across
  **three separate migrations** before a guard existed
- `internal/handlers/routes_parity_test.go` (`#0071`) — Go/TypeScript route-table parity

Both are filesystem-only Go tests that read the other language's source and compare. The
pattern is established, cheap, and proven on this codebase.

## Acceptance criteria

- [ ] A Go parity test reads `web/src/lib/subscribe.ts` and asserts the complained-copy
      constant composes to exactly the sentence `preferences.go` returns, modulo the
      documented `"No change: "` lead-in and its recapitalisation
- [ ] The test fails when either side is edited alone — **mutate both directions
      independently**, watch each fail, quote the output, revert
- [ ] Documented divergences are expressed as structure (a lead-in constant the test
      knows about), not as a substring allowance broad enough to hide a real drift
- [ ] The three doc comments asserting the mirror are corrected to point at the test
      that now enforces it
- [ ] Follows the existing parity-test conventions in `docs_parity_test.go` and
      `routes_parity_test.go` rather than inventing a third shape

## Notes

**Amended 2026-08-22 by `#0048`'s third phase-3 review.** `#0048` added an
exact-key-set assertion over the SSE progress payload
(`TestCampaignProgressPublisher_PublishesJSONFrameToBroker`, 7 keys, no more
and no fewer), and the reviewer proved it real by adding a Go-side `StartedAt`
field and watching it fire: `payload has 8 keys, want exactly 7`.

**But the guard is one-directional**, which is this issue's whole subject. It
catches a field added or removed on the **Go** side. A field added only on the
**TypeScript** side is caught by nothing at all. Whatever mechanism this issue
lands should either generalise that assertion or subsume it — a per-payload
hand-written key-set assertion does not scale to the API surface, and the half
it does not cover is the half where a client can quietly start expecting
something the server never sends.


Recommended by `#0090`'s second review, which deliberately did **not** make it a bounce
condition — it is follow-up work, not a defect in that fix.

Depends on `#0090`'s third pass landing first: the reviewer's prescribed fix splits the
constant at the clause boundary (`_LEAD` + `EMAIL` + `_TAIL`) so the client can render
one sentence with the anchor inside it. That split is what makes this guard nearly
trivial to write — the test asserts a composition rather than comparing two opaque
strings.

Consider whether the guard should cover the other copy shared between the SPA and the
Go handlers, rather than only this one pair. If it generalises cheaply, generalise it;
if not, say so and keep it narrow.
