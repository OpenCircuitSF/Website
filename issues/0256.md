## Description

`#0248` corrected `docs/deployment.md`'s drill findings against a real run and
was resolved. **`#0126`'s migrations `000021`/`000022` landed roughly twenty
minutes later and invalidated them again.** Measured at HEAD by `#0248`'s own
reviewer:

| Documented | Actual at HEAD |
|---|---|
| step 1b lands at `19\|f` | `21\|f` |
| step 6 applies `20/u create_workshops` | `22/u create_subscriber_events` |
| constraint diff: one line, `email_campaigns` | `subscriber_events\|8` |
| sequence diff: empty ("non-empty is a real failure, full stop") | `subscriber_events_id_seq` |
| index diff: empty | `subscriber_events\|4` |
| `settings\|6` | **`settings\|7`** — `000021` seeds `queue_max_retries` |

That last row is the figure `#0248` was **bounced over twice**. It was 7, then
6, and is 7 again — not because anyone was careless, but because it was never a
constant.

**The defect is not the numbers. It is that they are numbers.** Every value in
`### What the drill found` is pinned to whatever migration was HEAD when someone
last ran it, and this project adds migrations routinely. Three passes have now
corrected this section, each correctly, and each was invalidated by ordinary
work. A fourth correction would last until migration `000023`.

**Re-pinning is the wrong fix.** The expectations must be *derived* — from HEAD
and HEAD-1 at run time — so the drill states what it is comparing rather than
what someone once observed. Where a figure genuinely cannot be derived, the
drill should print it and ask the follower to sanity-check it, not assert it.

## Acceptance criteria

- [ ] The drill's expectations are derived at run time from the current migration set, not written down
- [ ] The one genuinely-invariant claim — the constraint delta is exactly one table, caused by the rolled-back migration's own `down.sql` — is stated as the rule it is, rather than as `email_campaigns` specifically
- [ ] `settings` is not asserted as a fixed count anywhere; it changes whenever a migration seeds a key
- [ ] Proved by running the drill at HEAD **and** with one further migration added on top, and confirming both pass without editing the document
- [ ] `### What the drill found` either derives its figures or is removed — a section of recorded observations cannot survive an append-only migration set
- [ ] The `set -e` rationale stays accurate: step 7's diff is still a legitimate non-zero exit

## Root cause

`### What the drill found` recorded one specific run's observations —
migration numbers, table names excluded from comparisons, and row counts —
as prose. Every one of those facts is a function of whatever migration
happens to be HEAD, and this project adds migrations routinely
(`CLAUDE.md` §1's greenfield note notwithstanding — the schema itself keeps
moving). Three passes corrected the section and each was invalidated by
ordinary, unrelated work landing afterward, because the design itself —
recording an observation about a moving target — cannot stay correct for
long. `#0126`'s `000021`/`000022` are the fourth invalidation, twenty
minutes after `#0248`'s fix landed.

## Fix

Replaced hand-written numbers with values derived from `migrations/` at run
time:

- **Step 1a** (new) derives `HEAD_VERSION` (highest-numbered
  `migrations/*.up.sql`), `NEW_TABLES` (tables HEAD's migration
  `CREATE TABLE`s outright — comments stripped first, since `000020`'s own
  prose contains the literal phrase "attached with an ALTER TABLE" and would
  otherwise read as a second `ALTER TABLE` statement), and `ALTERED_TABLES`
  (pre-existing tables HEAD's migration modifies via `ALTER TABLE` — the
  only tables the constraint-count diff may legitimately show a difference
  for). Every later step references these variables instead of a literal
  `19`/`20`/`email_campaigns`/`workshops`.
- **Step 7's constraint-count diff** states the actual invariant: any
  difference is confined to `$ALTERED_TABLES` and caused by the rolled-back
  migration's own `down.sql`, and is **empty** whenever the migration only
  creates new tables — which is the case for HEAD's migration
  (`000022_create_subscriber_events`) right now. Verified directly: that
  migration has no `ALTER TABLE` on a pre-existing table at all, so the old
  "always exactly one line, `email_campaigns`" framing was already false for
  it, independent of this fix.
- **Row-count, sequence, and index diffs** build their exclusion lists from
  `$NEW_TABLES`/`$EXCLUDE_SQL` rather than a hand-typed `('workshops',
  'workshop_interests')`. The row-count query itself is now generated from
  `information_schema.tables` rather than a fixed list of nine table names,
  so a future migration's new table is picked up automatically once it's no
  longer HEAD's own new table. The sequence diff derives `$NEW_TABLES`' own
  sequence name(s) via `pg_get_serial_sequence` against the
  restored-and-migrated database, rather than assuming a fixed
  `<table>_id_seq` spelling.
- **`### What the drill found` removed**, per the acceptance criteria's
  explicit permission to remove rather than re-derive a section that is
  fundamentally a recorded observation. Renamed to `### Where to find a
  fresh run's actual figures`, stating why (an append-only migration set
  makes "what this schema currently looks like" wrong by construction,
  eventually, no matter how carefully measured) and pointing at the drill's
  own live output — step 1a's echoed variables and step 7's diffs — instead
  of a written-down table. Content that is genuinely durable (Extensions,
  Roles and ownership, Order and dependencies, the two real script bugs
  found, the two format-idempotency behaviors) was kept; run-specific
  numbers inside it were either generalized or explicitly marked
  illustrative-from-a-past-run rather than a claim about current HEAD.
- **The `set -e` rationale** now states step 7's constraint diff is
  non-zero *exactly when* `$ALTERED_TABLES` is non-empty (not "always
  exactly one line") — still a legitimate, permanent reason not to add
  `set -e`, regardless of which case is live for any given HEAD.

**Two real bugs found and fixed while proving this, both by running the
drill for real rather than by inspection** (see `## Verification`):

1. The table-name extraction regex was `[a-z_]+` (letters and underscore
   only) — a table name containing a digit (this section's own proof
   migration, `scratch_probe_0256`) was silently truncated at the first
   digit to `scratch_probe_`, desyncing every exclusion built from it and
   producing a real "relation does not exist" error at step 8. Fixed to
   `[a-z_][a-z0-9_]*`.
2. The first sequence-diff query used a broken `${EXCLUDE_SQL//\'/}`
   transformation that stripped the quotes an `IN (...)` clause needs,
   producing `ERROR: column "subscriber_events" does not exist` (Postgres
   parsed the unquoted table name as a column reference). Replaced with a
   `pg_get_serial_sequence`-based derivation against `$DST_DSN`, tested and
   confirmed working before it went into the document.
