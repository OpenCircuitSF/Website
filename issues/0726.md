## Description

Second-batch Raspberry Pi guides. **Read `#0723`'s description first**: it carries the shared rules (no new set, `demoLoaders.ts`, `PROMPTS.md` sections, counts, links inside demos, the pattern in `#0719`–`#0721`). Guides in this issue:

- `pi-zero-audio-out` — a Zero 2W has no headphone jack and no analog audio: the options are an I2S DAC HAT or pHAT (enabled with a `dtoverlay=` line in `/boot/firmware/config.txt`), a USB DAC through an OTG adapter (link `pi-zero-usb-ports`), HDMI audio to a TV or receiver over mini-HDMI, or Bluetooth (latency, pairing). Pairs with `pi-volumio-streaming`. Demo: pick an output and see the wiring, the setup step, and trade-offs (quality, cost, latency, extra parts). Name no specific HAT brand as a recommendation; generic descriptions, with any example overlay marked as an example.
- `pi-rgb-matrix-basics` — driving HUB75 RGB panels from a Pi 4: rows and columns (`--led-rows`, `--led-cols`), scan rate, chaining panels (`--led-chain`, data out to data in), parallel chains (`--led-parallel`, adapter-dependent), and why more pixels lower the refresh rate. Check flags against the library README. Demo: set panel size, chain length and parallel chains; see the drawn layout (data arrows), total resolution and an illustrative refresh rate. Static drawing only.
- `pi-rgb-matrix-power` — how much an RGB panel draws: a 64×32 panel at full white can draw several amps at 5 V (check a datasheet-typical figure and mark it); give the panels their own 5 V supply with thick wires, inject power per panel, share ground with the Pi, never power panels from the Pi's 5 V pin; typical content draws far less than full white. Reuse the math from `led-power-budget` (link it). Demo: panel count and size, brightness, and content (full white, typical image, text on black) → current, supply size and wire gauge advice, with a warning past the supply's rating.

**2. RGB panel basics: layout and refresh**

Reuse `#0721`'s refresh model, **extended, not reinvented**: `piProjects.refreshHz` is the same formula with the panel fixed at 64 columns and 16 scan rows. Generalised here to any panel size; the parity test below pins the two together. `piProjects.ts` is not edited.

```ts
export const LSB_NS = 130;          // same as piProjects.refreshHz
export const CLOCK_NS = 40;         // same as piProjects.refreshHz (invented, illustrative)
export const BASICS_SLOWDOWN = 2;   // a Pi 4 needs 2 or more (see the flicker guide)
export const BASICS_PWM_BITS = 11;  // library default
export function layoutRefreshHz(s: PanelSize, chain: number, pwmBits = BASICS_PWM_BITS, slowdown = BASICS_SLOWDOWN): number;
//   Math.round(1e9 / (scanRows(s) * ((2 ** pwmBits - 1) * LSB_NS + pwmBits * s.cols * chain * CLOCK_NS * (slowdown + 1))))
//   Parallel chains are clocked out together, so `parallel` is not a parameter: that is the point of them.
export type AdapterId = 'single' | 'triple';
export const ADAPTERS: readonly { id: AdapterId; label: string; maxParallel: number }[] = [
  { id: 'single', label: 'Single-chain HAT or bonnet', maxParallel: 1 },
  { id: 'triple', label: 'Three-output adapter board', maxParallel: 3 },
];
export const MAX_CHAIN = 8;
export type Flicker = 'visible' | 'camera' | 'steady';
export function flickerClass(hz: number): Flicker;   // < 100 visible, < 200 camera, else steady (#0721's thresholds)
export interface PanelPos { chainIndex: number; parallelIndex: number; x: number; y: number }   // x, y in panel pixels on the combined canvas
export interface MatrixLayout {
  width: number; height: number; pixels: number; panels: PanelPos[];
  refreshHz: number; flicker: Flicker; title: string; tone: Tone; problem: string | null; command: string;
}
export function matrixLayout(size: PanelSizeId, chain: number, parallel: number, adapter: AdapterId): MatrixLayout;
```

`matrixLayout`: `width = cols × chain`, `height = rows × parallel`, `pixels = width × height`; `panels` row-major by parallel index then chain index, `x = chainIndex × cols`, `y = parallelIndex × rows` (length `chain × parallel`). `refreshHz = layoutRefreshHz(size, chain)`, `flicker = flickerClass(refreshHz)`. If `parallel > maxParallel` of the adapter: `problem = 'This adapter drives one chain. Parallel chains need an adapter board with more outputs.'`, `title = 'One chain only on this adapter'`, `tone = 'bad'`. Otherwise `problem = null` and title/tone by flicker: steady `Steady: {hz} Hz` good; camera `Fine to the eye: {hz} Hz` meh; visible `Flicker likely: {hz} Hz` bad. `command = 'sudo ./demo -D 0 --led-rows={rows} --led-cols={cols} --led-chain={chain} --led-parallel={parallel} --led-slowdown-gpio=2 --led-show-refresh'`.

Expected values (computed by the planner with exactly that formula):

| size, chain | refreshHz |
|---|---|
| 32x16: 1, 2, 3, 4, 6, 8 | 405, 357, 318, 287, 241, 207 |
| 32x32: 1, 2, 3, 4, 6, 8 | 203, 178, 159, 144, 120, 103 |
| 64x32: 1, 2, 3, 4, 6, 8 | 178, 144, 120, 103, 81, 66 |
| 64x64: 1, 2, 3, 4, 6, 8 | 89, 72, 60, 52, 40, 33 |

Parity with `#0721`: `layoutRefreshHz(panelSize('64x32'), chain, bits, sd) === refreshHz({ ...MATRIX_START, chain, pwmBits: bits, slowdown: sd })` for chain 1–3, bits 7 and 11, slowdown 2 and 4 (e.g. (3, 11, 4) = 91, (3, 7, 4) = 219).

Layouts: `('64x32',1,1,'single')` → 64×32, 2048 px, 178, `Fine to the eye: 178 Hz`; `('64x32',6,1,'single')` → 384×32, 12288, 81, `Flicker likely: 81 Hz`; `('64x32',2,3,'triple')` → 128×96, 12288, 144, `Fine to the eye: 144 Hz`, 6 panels, last at x 64, y 64; `('64x32',2,3,'single')` → `One chain only on this adapter`; `('32x16',1,1,'single')` → `Steady: 405 Hz`.

**3. RGB panel power** (the `led-power-budget` math: full-white current × how much of the colour is lit × brightness, summed over the LEDs; here per panel instead of per LED, and with the library's `--led-brightness` percent instead of FastLED's 0–255)

```ts
export type ContentId = 'white' | 'image' | 'text';
export const PANEL_CONTENT: readonly { id: ContentId; label: string; fraction: number }[] = [
  { id: 'white', label: 'Full white', fraction: 1 },
  { id: 'image', label: 'A typical picture or video', fraction: 0.35 },
  { id: 'text', label: 'Text on black', fraction: 0.08 },
];
export const SUPPLY_SIZES_A = [2, 4, 5, 8, 10, 20, 30, 40, 60];
export const SUPPLY_CHOICES_A = [4, 10, 20, 40];
export const HEADROOM = 1.2;
export const MAX_PANELS = 6;
export function recommendedSupplyA(worstA: number): number | null;  // smallest SUPPLY_SIZES_A ≥ worstA × HEADROOM, else null
export function wireGauge(a: number): string | null;
//   ≤ 3 '20 AWG (0.5 mm²)'; ≤ 5 '18 AWG (0.8 mm²)'; ≤ 8 '16 AWG (1.3 mm²)'; ≤ 13 '14 AWG (2.1 mm²)'; ≤ 20 '12 AWG (3.3 mm²)'; else null
export function amps(a: number): string;   // a.toFixed(1) + ' A'  (2.8 → '2.8 A', 8 → '8.0 A')
export interface PanelPowerInput { size: PanelSizeId; panels: number; brightness: number; content: ContentId; supplyA: number }
export type PowerStatus = 'over' | 'whiteOver' | 'noRoom' | 'ok';
export const POWER_TITLES: Record<PowerStatus, string> = {
  over: 'Over the supply’s rating',
  whiteOver: 'OK for this content; full white would overload the supply',
  noRoom: 'Enough, with little headroom',
  ok: 'Plenty of supply',
};
export interface PanelPower {
  perPanelA: number; totalA: number; worstPerPanelA: number; worstTotalA: number;
  recommendedA: number | null; panelWire: string | null; mainWire: string | null; status: PowerStatus; tone: Tone;
}
export function panelPower(i: PanelPowerInput): PanelPower;
```

`panelPower`: `worstPerPanelA = fullWhiteA × brightness / 100`; `perPanelA = worstPerPanelA × fraction`; totals × `panels`. `recommendedA = recommendedSupplyA(worstTotalA)`; `panelWire = wireGauge(worstPerPanelA)`; `mainWire = wireGauge(worstTotalA)` (wires and supply are sized for the worst case, because any frame can be white). Status, first match: `totalA > supplyA` over (bad); `worstTotalA > supplyA` whiteOver (meh); `worstTotalA > 0.8 × supplyA` noRoom (meh); else ok (good).

Expected values (`toBeCloseTo(x, 2)` for amps):

| input (size, panels, brightness, content, supply) | perPanelA | totalA | worstTotalA | status | recommendedA | panelWire | mainWire |
|---|---|---|---|---|---|---|---|
| 64x32, 2, 100, image, 4 (**demo default**) | 1.4 | 2.8 | 8 | whiteOver | 10 | 18 AWG | 16 AWG |
| 64x32, 1, 100, white, 4 | 4 | 4 | 4 | noRoom | 5 | 18 AWG | 18 AWG |
| 64x32, 2, 100, white, 4 | 4 | 8 | 8 | over | 10 | 18 AWG | 16 AWG |
| 64x32, 2, 50, white, 10 | 2 | 4 | 4 | ok | 5 | 20 AWG | 18 AWG |
| 32x32, 4, 100, text, 4 | 0.16 | 0.64 | 8 | whiteOver | 10 | 20 AWG | 16 AWG |
| 64x64, 6, 100, white, 40 | 4 | 24 | 24 | ok | 30 | 18 AWG | null |
| 64x32, 6, 100, white, 20 | 4 | 24 | 24 | over | 30 | 18 AWG | null |

Edges: `recommendedSupplyA(50) === 60`, `recommendedSupplyA(50.1) === null`; `wireGauge(3)` 20 AWG, `wireGauge(3.01)` 18 AWG, `wireGauge(20)` 12 AWG, `wireGauge(20.5)` null.

### `TOPIC_BODIES` (plain text, no markup or links)

`pi-zero-audio-out` — tryIt: "Pick how the sound gets out and what matters most to you, and see the wiring, the setup step and where each way falls short." Ideas:
1. **No jack, four ways out** — "A Pi Zero 2W has no headphone jack and no analog audio at all. The sound has to leave as digital and become analog somewhere else: on a DAC board on the GPIO header, in a USB DAC, in the TV or receiver at the end of an HDMI cable, or in a Bluetooth speaker."
2. **A DAC HAT is the cleanest** — "An I2S DAC HAT or pHAT sits on the 40-pin header and has its own converter chip. Enable it with one dtoverlay line at the end of /boot/firmware/config.txt; the board’s maker tells you which line, then reboot and check with aplay -l. A USB DAC needs no setup at all, but plugs into the Zero’s only data port through an OTG adapter."
3. **HDMI and Bluetooth** — "HDMI carries sound to a TV or AV receiver over the mini-HDMI port, and an HDMI audio extractor splits it out for an amplifier. Bluetooth needs no wires to the speaker, but pairing takes a few commands, the sound is compressed and it arrives late: fine for music, bad for video. For a Volumio speaker, a DAC HAT or a USB DAC is the usual choice."
Takeaway: "For music, a DAC HAT or a USB DAC. HDMI if a TV or receiver is already there. Bluetooth when wires are the bigger problem than delay."

`pi-rgb-matrix-basics` — tryIt: "Pick a panel size, then add panels to the chain and parallel chains, and watch the resolution, the command line and the refresh rate change." Ideas:
1. **Rows, columns and scan** — "A HUB75 panel is named by its pixels: 64×32 is 64 columns and 32 rows, set with --led-cols=64 --led-rows=32. It never lights every row at once. A 64×32 panel lights two rows at a time and steps through all 16 pairs, fast enough that you see a full picture: that is its 1:16 scan."
2. **Chains and parallel chains** — "Panels chain from OUT to IN with a ribbon cable, and --led-chain says how many: three 64×32 panels in a chain make one 192×32 display. Parallel chains run side by side from separate outputs, set with --led-parallel. The library drives up to three on a 40-pin Pi, but only if the adapter board has the outputs; many single-chain HATs and bonnets have one."
3. **More pixels, lower refresh** — "Every refresh clocks every pixel of the chain out over GPIO, so a longer chain refreshes more slowly; below about 100 Hz you can see it flicker. Parallel chains are clocked out together, so six panels as three chains of two refresh much faster than one chain of six. --led-show-refresh prints the real number."
Takeaway: "Size sets the rows and columns, the chain makes it wider, parallel chains make it taller without slowing it down."

`pi-rgb-matrix-power` — tryIt: "Set the panels, the brightness and what they show, and pick a supply. See the current, what to buy and how thick the wires should be." Ideas:
1. **Amps, not milliamps** — "A 64×32 panel at full white and full brightness can draw around 4 A at 5 V, a 32-wide one about half that. The math is the same as for an LED strip: the full-white current times how much of each colour is lit times the brightness. Check your panel’s label or datasheet for its own figure."
2. **Most frames draw far less** — "A typical picture lights a fraction of the LEDs, and text on black even less, so a sign may average a few hundred milliamps per panel. But one white frame, a flash or a test pattern draws the full amount, so size the supply for full white at the brightness you run, plus about 20% spare. --led-brightness turns the whole panel down and the current with it."
3. **Wire it like a power tool, not a gadget** — "Give the panels their own 5 V supply. Run a pair of thick wires from the supply to each panel rather than through one panel to the next, and join the supply’s ground to a ground pin on the Pi. Never feed panels from the Pi’s 5 V pin: it can only pass what the Pi’s own supply can spare."
Takeaway: "Budget about 4 A per 64×32 panel at full white, give them their own 5 V supply with thick wires to every panel, and share ground with the Pi."

### Facts the implementer must list under `### Assumptions` (not confirmed in official docs today)

- Hardware is **assumed** as in `#0721`: HUB75 panels, `rpi-rgb-led-matrix`, a Pi 4, an adapter board. "Three-output adapter board" is a generic description; none is named or recommended.
- The README's Pi 5 notes conflict ("support has now been added" vs "not officially supported as of 2025/11"); the guides stay Pi 4 only.
- Per-panel full-white currents (32-wide 2 A, 64-wide 4 A, 64×64 the same as 64×32 because it lights the same 128 pixels at once at 1:32 scan) and the scan-follows-rows/2 rule are typical, not universal: some panels use other multiplexing (`--led-multiplexing`, `--led-row-addr-type`), not modelled.
- Content fractions (picture 0.35, text on black 0.08), the 20% headroom, the supply sizes, and the wire-gauge thresholds (conservative figures for short 5 V runs, chosen to keep voltage drop small) are illustrative.
- The refresh model is `#0721`'s illustrative model generalised (130 ns lowest-bit time from memory, invented 40 ns clock time, slowdown 2, 11 bits); the 100/200 Hz flicker thresholds are `#0721`'s.
- Zero 2W audio: no analog audio at all (no jack, PWM audio pins not broken out) is from memory beyond the product page's port list. I2S uses GPIO 18, 19, 21 (PCM pins), from memory. Many generic PCM5102-style DAC boards work with the `hifiberry-dac` overlay (from memory; hence "example only"). A class-compliant USB DAC needs no driver; HDMI audio shows as an HDMI card in `aplay -l`; Bluetooth audio on a headless Lite install needs an audio server; Bluetooth adds a noticeable delay (typically a few tenths of a second); the Zero 2W has Bluetooth 4.2. The quality/cost/delay/parts ratings are the planner's judgement.
- The Pi's 5 V pin passes through what the Pi's own supply can spare (the Pi 4 uses a 5.1 V, 3 A USB-C supply).
