## Description

`deploy/apache/README.md`, under "Obtain the Let's Encrypt certificate", says:

```bash
sudo certbot --apache -d opencircuitsf.com -d www.opencircuitsf.com
```

Measured against the live endpoint today:

```
$ openssl s_client -connect www.opencircuitsf.com:443 -servername www.opencircuitsf.com \
    | openssl x509 -noout -text | grep -A1 "Subject Alternative Name"
    DNS:*.opencircuitsf.com, DNS:opencircuitsf.com
```

**Production runs a wildcard certificate.** The documented command requests a
**two-name** certificate for the apex and `www` only, into the same lineage the
vhost points at (`/etc/letsencrypt/live/opencircuitsf.com/`). Running it
replaces the wildcard.

### What breaks

Every other name under the domain loses its certificate. That includes
**`go.opencircuitsf.com`**, the separate ShortLinks deploy — a service this
repo does not own and whose owner would have no idea why it went down. Also
`lists.` and anything else the wildcard covers.

It also changes the renewal mechanism. `CLAUDE.md` §7 records the wildcard as
renewed by `certbot-renew.timer` through the **`dns-route53`** authenticator,
which is what keeps renewal from ever touching a vhost or an ACME webroot. The
`--apache` plugin does the opposite: it edits Apache configuration to complete
an HTTP-01 challenge. So the command does not merely narrow the certificate, it
swaps a DNS-01 wildcard for an HTTP-01 two-name cert and rewires renewal to
touch the vhost on every cycle.

### Why this is filed rather than just fixed

The file **already knows**. It carries a note acknowledging the command is
wrong and saying it is being fixed. It was not fixed, and the dangerous command
is still the one a reader copies. A warning next to a runnable command is not a
safeguard — the command is what gets pasted into a terminal.

This is the same failure shape `#0057` hit three times in `docs/aws-requests.md`:
a document whose prose and whose instructions disagree, where the instruction is
the part that gets executed.

**Do not run any certbot command to test this.** The failure is irreversible
within a rate-limit window: Let's Encrypt's duplicate-certificate limit would
block reissuing the wildcard for up to a week, leaving every subdomain without
a certificate in the meantime. Verification here means reading the live cert and
the renewal configuration, never issuing one.

## Fix

`deploy/apache/README.md`'s "Obtain the Let's Encrypt certificate" section
now documents what actually produced the live certificate:
`sudo certbot certonly --dns-route53 -d opencircuitsf.com
-d '*.opencircuitsf.com'`, matching `docs/deployment.md` §9's issuance step
verbatim. The section now states the blast radius (the wildcard is shared
with `go.opencircuitsf.com`, `lists.opencircuitsf.com`, and every future
subdomain, so a two-name replacement takes them offline, and Let's
Encrypt's duplicate-certificate limit can block reissuing for up to a
week) and points renewal at `certbot-renew.timer` via the same
authenticator, which never touches a vhost. The self-acknowledging
"we are fixing this" note the issue describes is not present in the
working copy — nothing matched it; the dangerous command itself was, and
is now gone, so nothing stands next to a wrong instruction either way.

The same `--apache` two-name command in `placeholder/README.md` is
annotated as historical ("do not run against the live box", with the
wildcard/dns-route53 facts and the subdomain blast radius) rather than
rewritten — it records how the placeholder box was originally set up.

Every other `certbot` invocation in the repo was checked by
`grep -rn certbot`: `docs/deployment.md` §9's issuance command (correct,
the model for the fix), its scoped
`certbot renew --cert-name opencircuitsf.com --dry-run` (safe, lineage-
scoped), `deploy/certbot/README.md`'s renew guidance (safe), and
`FEDERATED-ACCOUNTS.md`'s one mention (a different service's proposal,
no runnable `-d` command for this domain — left alone).
