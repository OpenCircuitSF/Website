## Description

`#0253` replaced nine hardcoded ports with a per-run base derived as
`40000 + (cksum % 200) * 100`, which fixed the cross-run collisions it was filed
for. The range it picks from overlaps two things:

- **macOS's ephemeral port range**, which starts at 49152
  (`net.inet.ip.portrange.first`), so the OS may already have handed a port out.
- **Real listeners on this machine right now** — `rapportd` on 49301, LM Studio
  on 41343, `lmlink-connect` on 52714, a VS Code helper on 57106.

Because the base is a deterministic hash of the token, an agent whose `ISSUE`
hashes to base 49300 gets `part1 setup: port 49301 unexpectedly already bound`
**every time**, forever. Not flaky — reproducibly broken for that one token,
and fine for every other, which is a genuinely confusing thing to debug.

**Not a regression.** The previous fixed ports had the same exposure, and worse:
they had it for *everyone* simultaneously rather than for one token. And it
fails detectably — the script checks `port_bound` and refuses rather than
corrupting anything.

**Why it is still worth fixing:** the failure reads exactly like a real
regression in `dev.sh`'s port handling, which is what the guard tests. `#0253`'s
review already showed the pre-fix version producing a **false `REGRESSION
#0117` accusation** against `dev.sh` — the same misattribution shape as
`testdb_gc`'s false `#0223`. A spurious failure in a guard script is expensive
precisely because the guard is what you trust when something looks wrong.

## Acceptance criteria

- [ ] The derived base falls in a range not used by the OS's ephemeral allocator and unlikely to hold a real listener
- [ ] A base that is nonetheless occupied is retried rather than fatal — a deterministic permanent failure for one token is the specific defect here
- [ ] Proved by forcing a collision (bind the port the base would pick, then run) and confirming the script recovers rather than failing
- [ ] `#0253`'s concurrency proof still holds: all three guard scripts twice concurrently, zero cross-run port references, census identical
- [ ] `:5173` stays as it is — Vite's own, deliberately guarded

## Root cause

`PBASE=$(( 40000 + ( (RUNHASH % 200) * 100 ) ))` picks from 40000..59900.
`net.inet.ip.portrange.first` is 49152 on this machine (confirmed via
`sysctl`), so roughly the top half of that range is inside macOS's ephemeral
allocator, which can hand a port in it to any process at any time. The range
also directly contains real, currently-running listeners named in the issue
(41343, 49301, 52714, 57106). Since `PBASE` is a pure hash of the `ISSUE`
token with no fallback, whichever token happened to hash into an occupied
bucket failed identically on every run, while every other token was
unaffected — reproduced directly (see `## Verification`).

## Fix

- **Range moved to 20000..39900** — same 200 non-overlapping 100-wide
  buckets, same per-part offsets (`P1..P8`), entirely below the ephemeral
  floor and clear of every listener named in the issue. Verified empty via
  `lsof -iTCP -sTCP:LISTEN -P -n` at the time of writing.
- **Retry on collision.** Added `pick_pbase()`: tries the token's own hash
  first (attempt 0), so the common case is unchanged — a given `ISSUE` still
  always produces the same base. On collision (any of the run's 9 derived
  ports already bound) it rehashes `"$RUNID:$attempt"` and tries again, up to
  50 attempts, before giving up with a loud, specific error (not a silent
  hang or a misleading `part1 setup` message). Moved the
  `port_listeners`/`port_bound`/`port_free`/`port_accepts_connection`
  definitions earlier in the file so `pick_pbase()` can call `port_bound`
  before the rest of the script's setup runs.
- `:5173` is untouched, as the acceptance criteria require — it stays
  Vite's own, shared, deliberately-guarded port.

## Verification

All mutation and reproduction work used untracked private copies in
`scripts/` (the tracked file's own convention, documented in its header —
`dev.sh` self-locates its repo root via `dirname`, so a copy outside
`scripts/` resolves the wrong `REPO`) or `/tmp` for read-only extraction.
`uptime` stayed under ~6.2 throughout; not a load artifact except where noted
below.

- **`sysctl net.inet.ip.portrange.first`** → `49152` on this machine,
  confirming the range claim. `lsof -iTCP -sTCP:LISTEN -P -n` showed zero
  listeners in `[20000,40000)` at the time of writing.
- **Reproduced the original defect first**, per the acceptance criteria.
  Picked `ISSUE=0259oldproof`, computed its **old**-formula base
  (`40000 + (cksum % 200) * 100` = `51700`, so `P1=51701`), bound a holder on
  `51701`, then ran the pre-fix script (`git show HEAD:scripts/dev_guard_test.sh`
  as it stood before this fix, copied into `scripts/` as a private untracked
  file) twice against the live collision:
  both runs printed the identical
  `FAIL: part1 setup: port 51701 unexpectedly already bound — pick a
  different port and rerun` — deterministic and permanent for this one
  token, exactly as described.
- **The fixed script against the same live collision, same token**: picked a
  different base (`36200`) and printed `dev_guard_test.sh: all guards hold
  (0 failures)`, exit 0 — recovered rather than failing. Holder process
  killed and port confirmed free afterward.
- **Forced-collision proof against the new formula directly**: computed
  attempt-0's new-formula base for `ISSUE=0259collision` (`31300`), bound a
  holder on `31301`, ran the fixed script: it silently picked a different
  base (`30100`, i.e. attempt 1) and passed cleanly — `all guards hold
  (0 failures)`.
- **`#0253`'s concurrency proof, re-run**: two `dev_guard_test.sh` instances
  launched together with `ISSUE=0259concA`/`0259concB`, waited to
  completion. Grepped both logs for every 5-digit port number referenced:
  run A used the `24500`-series, run B the `23500`-series — zero overlap
  (`comm -12` on the sorted sets was empty). Both runs individually hit
  `#0253`'s own already-documented, explicitly out-of-scope residual
  failures for this specific script when two instances share one machine
  (`:5173` contention in Part 7/8's setup, and Part 4's load-sensitive `M1`
  kill-timing assertion) — neither references the other run's ports, neither
  is a namespacing or port-base defect, and both are the identical shape
  `#0253`'s own resolution already accepted and recorded (`issues/0253.md`,
  "`dev_guard_test.sh` needs a documented caveat"). This script does not use
  a database, so the `pg_database` census leg of `#0253`'s criterion is
  trivially satisfied ("identical (no databases involved)").
- **`ISSUE=0259chk scripts/check.sh guards`** — **VERIFICATION PASSED**, all
  three guard scripts (`testdb_gc_guard_test.sh`, `dev_guard_test.sh`,
  `db_reset_guard_test.sh`) reported `all guards hold (0 failures)` in the
  normal sequential path `check.sh` actually uses (no concurrency risk in
  that mode).
- A plain, single `ISSUE=0259verify bash scripts/dev_guard_test.sh` run (no
  forced collision) also passed cleanly, base `27100`, all 8 parts plus the
  byte-identity check.
- `bash -n scripts/dev_guard_test.sh` — clean. `shellcheck
  scripts/dev_guard_test.sh` — exit 0, no findings (none pre-existing on
  this file either).
- No leftover processes or bound ports after any run
  (`pgrep -fl 'go test|\.test |go run|npm run dev|vite|dev_guard_test'`
  checked clean after every trial); every forced holder and mutant script
  removed by hand or by the script's own `EXIT` trap.

## Files changed

- `scripts/dev_guard_test.sh` — moved the derived port-base range from
  `40000..59900` to `20000..39900`; added `pick_pbase()`, a bounded retry
  that rehashes on a bound base instead of failing; relocated the
  `port_bound`/`port_listeners`/etc. helpers earlier in the file so the new
  retry logic can call them.
