## Item 1 — an unaccepted invitation counts as growth. This is a regression.

**Introduced by `3c9eaf8` (`#0311`), and it reverses a decision `#0305`'s review
recorded and justified**: *"a pending invite-mode row is not growth — deliberate;
an invitation is not an accepted subscription."*

Invite-mode `Commit` inserts `status=pending, source='import', confirmed_at NULL`,
so `#0311`'s new `imported_30d` predicate matches **the moment the invitation is
sent**. Measured by `#0311`'s reviewer on both predicates, same code path:

| Scenario (invite mode) | parent | `3c9eaf8` | truth |
|---|---|---|---|
| invite sent, nobody accepts | 0 | **+1** | 0 |
| invite expires (`ExpirePendingSweep` leaves the row pending) | 0 | **+1**, permanently in-window | 0 |
| invite accepted | +1 | +1 | +1 |
| invite batch revoked while pending | **−1** | 0 | 0 |

**A 500-address invite import reads as +500 before a single acceptance**, and
stays there after every invitation expires.

`3c9eaf8` is still a **net improvement** — it fixes the revoke case the old
predicate got wrong in the other direction, and it fixed the `prior_consent`
double-subtraction `#0311` was filed for. But this half is new and wrong, and it
was resolved knowingly rather than bounced, because the remedy is not a
one-clause change (see below).

**Why `AND consent_basis IS NOT NULL` is not sufficient alone:** it restores the
invite exclusion and keeps every `prior_consent` fix, but reinstates **−N** on a
revoked pending-invite batch, because `ImportStore.Revoke` stamps
`unsubscribed_at` on rows that were never active. **Whether a revoked or expired
unaccepted invitation is a *departure* is the real design question**, and it is
about `unsubscribed_30d`, not `imported_30d`.

## Item 2 — `RestartSignup` leaves an ordinary signup at −1

Pre-existing, not from `#0311`. `RestartSignup` clears `confirmed_at` but **never
clears `unsubscribed_at`**. Measured on an ordinary website signup in one window:
after `Confirm` **+1**, after `Unsubscribe` **0**, after `RestartSignup` **−1**.

The end state is **persistent, not transient**: if the person abandons the new
confirmation email, the row sits at −1 for the rest of the window — a departure
counted with no matching arrival, the same family as `#0311`. No admin action is
needed to reach it: unsubscribe, re-enter your address, ignore the email.

Self-cancelling for `source='import'` rows; it only bites ordinary signups. One
row per person rather than bulk, which is why it is a follow-up rather than a
bounce.

`#0311`'s new doc comment describes this as out of scope, so **the tracker is the
only place it will be seen.**

## Root cause

Item 1: `3c9eaf8` (`#0311`) widened `imported_30d`'s predicate from
`status = 'active' AND confirmed_at IS NULL` to `source = 'import' AND
confirmed_at IS NULL` to fix a real stock-vs-event bug, but the new predicate
also matches an invite-mode row the instant `ImportStore.Commit` sends the
invitation (`status=pending, source='import', confirmed_at NULL`) — there was
no clause left to distinguish "placed on the list" from "merely asked".

Item 2: `RestartSignup` already clears `confirmed_at` (treating the row as a
fresh, unconfirmed signup) but never cleared `unsubscribed_at` or
`unsubscribe_source`. Since `Growth30Days`'s `unsubscribed_30d` is
`unsubscribed_at >= since` with no status/current-state qualifier, a restarted
row's earlier departure kept counting after its earlier arrival had already
been retracted from `confirmed_30d` — the exact "event survives without its
matching event" shape `#0311` fixed for imports, reached a different way.

## Fix

**Item 1.** Added `consent_basis IS NOT NULL` to the `imported_30d` FILTER.
`consent_basis` is stamped at INSERT time for a prior_consent row
(`ConsentBasisImportedPriorConsent`) but stays NULL for an invite-mode row
until `Confirm` sets `ConsentBasisDoubleOptIn` — so this restores `#0305`'s
decision (an unaccepted invitation is not growth) without reopening `#0311`'s
bug (consent_basis, like source, is never un-set once written, so a
prior_consent row that later leaves stays counted).

**Item 2's design question (criterion 2).** Decided: a revoked or expired
unaccepted invitation counts as **neither** an arrival nor a departure — the
same symmetry #0311 established for an accepted-then-departed row. Implemented
by adding `AND NOT (source = 'import' AND consent_basis IS NULL)` to the
`unsubscribed_30d` FILTER — the negation of item 1's own guard, applied on the
departure side. `ImportStore.Revoke` and `Store.Unsubscribe`'s invite-decline
branch both stamp `unsubscribed_at` on a row whose `consent_basis` is still
NULL when the invitation was never accepted; `ExpirePendingSweep` never
touches `unsubscribed_at` at all (the row is left pending), so it needed no
change. A prior_consent import, or an accepted invitee, keeps a non-NULL
`consent_basis` forever, so their later departures are unaffected and still
count — the ordinary join-then-leave symmetry stays intact for those cases.

**Item 2 (criterion 4) — fixed, not deferred.** `RestartSignup`'s UPDATE now
also sets `unsubscribed_at = NULL, unsubscribe_source = NULL` in the same
`CASE WHEN status = <locked> THEN <unchanged> ELSE NULL END` pattern already
used for `confirmed_at`/`confirm_sent_at`/`import_id`. The audit trail is not
lost — `subscriber_events` already carries the earlier `ActionUnsubscribed`
row with its own timestamp.

**Criterion 6 (wording).** `formatGrowthDetail`'s doc comment ("addresses an
import batch placed on the list") was inaccurate for an invitation, per the
issue's "Also" section. Rewrote it: an invitation "asked", it did not "place"
— the address is not standing on the list until its own eventual acceptance,
which is when it counts (as `confirmed_30d`).

**Files not touched, deliberately.** `internal/handlers/admin_dashboard.go`'s
`dashboardGrowth` doc comment references `Growth30Days`'s doc comment rather
than restating the predicate, so it needed no edit — still accurate after this
change.

## Gotchas

**My own first draft of the new tests introduced a real, reproducible cross-
test interference bug, caught before committing.** Several new tests
back-dated a `Store.Create`/`ImportStore.Commit` call's `now` argument forward
from a captured `since` (e.g. `since.Add(time.Second)`) to get causally-ordered
timestamps within one test. `Create`/`Commit` stamp `created_at` from that
argument, and `Store.List` (`TestList_PaginationBoundsAndOrdering`) orders
strictly by `subscribers.created_at DESC` with **no time-window filter at
all** — so a row whose `created_at` is even 1–4 seconds in the future is still
"newest" by the time an unrelated, later-running test queries the full table,
since the whole `internal/subscribers` package's test suite runs in well
under a second. Reproduced deterministically (4/4 runs) against my first draft,
and proved it was my change, not a pre-existing flake, by checking out
`internal/subscribers/{store,store_test,imports_test}.go` at `HEAD` into a
throwaway `git worktree` (never touching the shared tree — CLAUDE.md §8a) and
running the identical unmodified suite there: passed 2/2. Fixed by using real
`time.Now()` for every call that sets `created_at`, keeping `since`-relative
offsets only for calls that touch other timestamp columns
(`confirmed_at`/`unsubscribed_at`, which `List` never orders by). Worth a
general note for future growth-accounting tests in this file: **never
forward-date a `Create`/`Commit` call's `now`** — `since.Add(...)` is safe for
every other write in this package, just not those two.

**Confirmed no `internal/outbox/` files were read or modified** — another
agent was reviewing that package during this work, per the task's file
boundary; this issue never needed anything there.

### Why the two predicates are right (criteria 1 and 2)

`consent_basis` is genuinely append-only. The only write anywhere in the tree
is `Confirm`'s `consent_basis = COALESCE(consent_basis, $4)` — verified by
grepping every `.go` and every migration; `Revoke`, `Unsubscribe`,
`setStatusTx`, `ExpirePendingSweep`, and `RestartSignup` never touch it. And
`ImportStore.Commit` is the **only** producer of `source='import'` rows, in
exactly two shapes: invite (`consent_basis` NULL) and prior_consent
(`consent_basis` always `imported_prior_consent`, never NULL). So the
reviewer's stated worry — a row imported *without* invite mode being dropped
by `consent_basis IS NOT NULL` — cannot occur: rows G/H/I confirm it
empirically. `ConsentBasisAdminAttested` is a declared constant that nothing
ever writes.

The symmetry argument holds for the departure side too: no row with
`source='import' AND consent_basis IS NULL` can ever have been counted as an
arrival (`confirmed_30d` needs `confirmed_at`, which only `Confirm` sets, and
`Confirm` stamps `consent_basis` in the same statement). So the exclusion
cannot drop a *matched* departure. Rows E and F confirm it.

### Defect found — narrow, not bounce-worthy, follow-up recommended

Rows **O** and **P** changed from 0 to **+1**, in scenarios neither of the
issue's tables names. Both arise from the *interaction* of this change's two
halves: `RestartSignup` now withdraws the departure, while the `imported_30d`
arrival cannot be withdrawn (it is an event count, by design since `#0311`).
The result is a row sitting at **+1 while merely `pending`** — and if the
person abandons the new confirmation email it stays there for the rest of the
window, which is the same "persistent, unmatched contribution" shape this
issue was filed to remove, reached from the other direction.

Row **P** is arguably correct under the documented event semantics. Row **O**
is not: an accepted invitee has `consent_basis='double_opt_in'`, so after a
restart clears `confirmed_at` the row falls into `imported_30d` — but it was
never "placed on the list by an import with its own standing consent", which
is what both doc comments say that bucket means. So the prose and the code
disagree in exactly this cell.

I verified the remedy rather than guessing it: changing the predicate from
`consent_basis IS NOT NULL` to `consent_basis = $3`
(`ConsentBasisImportedPriorConsent`) and re-running the same 18 scenarios
changes **exactly one cell** — O, from +1 to 0 — and leaves the other
seventeen byte-identical.

**Not bounced**, on this issue's own stated severity standard: it is one row
per person, not bulk, requires four sequential user actions, errs by +1 in the
overstating direction, and every scenario the issue actually names is now
correct. That is the same threshold under which `#0324` itself was filed as a
follow-up from `#0311`'s review rather than as a bounce. Recommended as a
follow-up issue (see the reviewer's report).
