## Description

`#0384`'s predicate-2 helper, `issueLineCitationFencedBlockContainsTestMarker`,
collects every ``` ``` ``` offset in a section and pairs them **positionally** —
first with second, third with fourth.

A scanned section containing an **odd** number of fence runs — a stray ``` ``` ```
mentioned in prose, or a fence written inside a nested block — **shifts every
subsequent pair.**

Two consequences, and the second is the serious one:

1. A genuine `go test -v` transcript can be **false-flagged**, because its real
   block never forms a pair.
2. In the shifted case, **a span of ordinary prose is treated as a block** — so a
   stale citation sitting in that prose, next to anything matching the marker
   pattern, is **silently exempted**. That is a fail-open.

**Latent, not live.** `#0384`'s reviewer scanned every scanned section of every
`open`/`in-progress` file for an odd fence count and found **zero**. The guard is
correct on all real content today, and this was outside `#0384`'s criteria.

## The fix the review specified

Recognise fences **line-anchored** — a fence is a line whose first non-space run
is three or more backticks — and treat an **unterminated final fence** as running
to the end of the section, rather than indexing raw byte offsets.

## Acceptance criteria

1. Fence detection is line-anchored, and an unterminated final fence runs to the
   end of the section.
2. **Prove the fail-open is closed**: construct a section with an odd fence count
   where a stale citation sits in prose beside a marker-matching line, confirm
   the current code exempts it, and confirm the fixed code flags it. That
   demonstration is the deliverable — the defect is invisible without it.
3. **Prove the false-flag half too**: a genuine transcript in a section with an
   odd fence count must be exempt after the fix and is flagged before it.
4. `#0384`'s existing proofs must still hold — each of its three mechanisms
   (predicate 1, predicate 2, the section split) is the **sole** thing standing
   between the guard and a real hit in the corpus, proved by disabling each in
   turn against the real issue files rather than fixtures. Re-run all three.
5. The corpus survey must still come back **zero non-exempt** across
   `open`/`in-progress` files, and the guard must still catch a planted citation.
   A fix that quiets the guard is worse than the fail-open.
6. **Do not add a mechanism to defend the mechanism.** §8's `#0258` case is six
   passes of exactly that, and three guard families this phase (`#0330`,
   `#0347`, `#0356`) ended by recording a limit rather than closing it. This is a
   parsing correction, not a new layer — if it starts growing into one, stop and
   report.
7. Note the **known accepted residual** and do not claim to close it: a stale
   citation *can* still be exempted by wrapping it in a fence carrying a
   fabricated `--- PASS:` marker. `#0384`'s reviewer proved that path is open and
   accepted it, because defeating the guard requires forging tool output and
   `#0356` carries the identical blind spot. **The file discloses this in its own
   header comment** — keep that disclosure accurate.
8. Run `./internal/db/...` and `./internal/handlers/...` (`#0381`). **Your own
   issue-file edits are in scope of this very guard while the issue is
   `in-progress`** — re-run after writing them, and do not introduce a
   `<file>.go:<int>` citation (`#0352`). Per §5 name the specific tests that ran.
   `gofmt` stability.
