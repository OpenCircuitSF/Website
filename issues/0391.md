## Description

`#0384`'s predicate-2 helper, `issueLineCitationFencedBlockContainsTestMarker`,
collects every ``` ``` ``` offset in a section and pairs them **positionally** —
first with second, third with fourth.

A scanned section containing an **odd** number of fence runs — a stray ``` ``` ```
mentioned in prose, or a fence written inside a nested block — **shifts every
subsequent pair.**

Two consequences, and the second is the serious one:

1. A genuine `go test -v` transcript can be **false-flagged**, because its real
   block never forms a pair.
2. In the shifted case, **a span of ordinary prose is treated as a block** — so a
   stale citation sitting in that prose, next to anything matching the marker
   pattern, is **silently exempted**. That is a fail-open.

**Latent, not live.** `#0384`'s reviewer scanned every scanned section of every
`open`/`in-progress` file for an odd fence count and found **zero**. The guard is
correct on all real content today, and this was outside `#0384`'s criteria.

## The fix the review specified

Recognise fences **line-anchored** — a fence is a line whose first non-space run
is three or more backticks — and treat an **unterminated final fence** as running
to the end of the section, rather than indexing raw byte offsets.

## Verification

**The fix (criterion 1).** `issueLineCitationFencedBlockContainsTestMarker` in
`internal/db/issue_line_citation_guard_test.go` no longer indexes raw
three-backtick substring offsets. A new `issueLineCitationFenceLinePattern`
regex recognizes a fence line-anchored — a line whose first non-space
characters, after optional leading spaces/tabs, are a run of three or more
backticks — via `regexp`'s multiline `^` anchor. Fence-line matches are
consumed in document order and paired open/close/open/close; a trailing,
unpaired fence-line match (an odd total) is treated as open through the end
of the section (`len(text)`) via a new small helper,
`issueLineCitationLineEnd`, rather than being dropped by the old loop's
`i+1 < len(fenceOffsets)` bound. Line-anchoring is what stops a bare mention
of a fence in the middle of an ordinary sentence from counting as a fence at
all — the raw substring search the old code did found it regardless of
context.

**Criteria 2 and 3 — the demonstrations, both against real production code,
not a description of the bug.** `#0384`'s original implementation was
preserved byte-for-byte (renamed only) as a test-only function,
`preFix0391FencedBlockContainsTestMarker`, purely so both demonstrations
exercise the actual bug rather than a paraphrase of it.

- `TestIssueLineCitationFencePairingClosesFailOpen` (criterion 2, the
  serious half): a fixture with a stray fence-shaped mention in the middle
  of a sentence (never alone on its own line), a stale synthetic citation
  and a decoy marker-shaped line both sitting in the ordinary prose right
  after it, and one real fenced block later in the text — three raw
  backtick-run occurrences total, an odd count. The preserved pre-fix
  function pairs the stray mid-sentence mention with the real block's
  opening fence, so the "block" it forms spans exactly that prose and
  (wrongly) reports the citation as exempt. The fixed function never counts
  the mid-sentence mention as a fence at all, so no block covers that prose
  and the citation is correctly left un-exempt. Both assertions are in the
  one test, so it fails if either half of the before/after stops holding.
- `TestIssueLineCitationFencePairingStopsFalseFlaggingUnterminatedTranscript`
  (criterion 3): a fixture with one complete, marker-free block followed by
  a second, genuine block whose closing fence never arrives before the
  section text ends — three raw occurrences total, again odd, this time
  from a real unterminated block rather than a stray mention. The preserved
  pre-fix function's pairing loop simply stops on the unpaired trailing
  fence, so the transcript's own citation gets no benefit from the
  predicate and is wrongly left un-exempt (a false flag). The fixed
  function treats that trailing fence as open through the end of the
  section, finds the marker inside it, and correctly exempts the citation.

**The preserved-old-implementation technique — the thing to scrutinise, and
it holds.** Extracted `#0384`'s original body from `5752e74^` and the
preserved copy from `5752e74` programmatically and compared bytes: identical
modulo the 7-byte function-name change and nothing else (510 bytes vs 503).
The claim of byte-for-byte preservation is true.

More importantly, the §8 hazard it invites — an oracle stored next to its
subject, where an edit to the subject can also satisfy the oracle — does
**not** apply here, and the reason is structural rather than incidental. The
two demonstrations assert **opposite** results from the two functions on the
same input, so any edit that makes the new implementation converge on the old
one breaks an assertion rather than satisfying it. Proved by mutation in an
isolated `git archive HEAD` export, three ways, each restored afterwards:

- New implementation gutted to an unconditional `false` → the
  unterminated-transcript demonstration fails.
- New implementation's whole body replaced by a delegation to the preserved
  pre-fix function (the exact "make the subject agree with the oracle" edit)
  → **both** demonstrations fail, naming the right halves.
- The one shared dependency, `issueLineCitationTestMarkerPattern`, neutered so
  it never matches → both demonstrations fail. The oracle fails closed on its
  own inputs rather than fading to a vacuous agreement.

The two bodies also share no substring a single `sed` could rewrite in both
(`fenceLines`/`FindAllStringIndex` against `fenceOffsets`/`strings.Index`),
which is the `#0258` shape the rule was written about.

**Both demonstrations re-derived independently (criteria 2 and 3).** Rather
than run the committed tests, the reviewer extracted the three functions and
the two patterns verbatim from the source file into a standalone module and
drove them over fixtures the reviewer wrote, each written to disk and read
back as bytes with `python3` before use (§8's silent-malformed-fixture
warning). Reviewer fixture A — three raw backtick runs, one mid-sentence in
prose, a synthetic citation and a decoy marker line in the prose after it,
one real block later: pre-fix reports **exempt** (the fail-open), fixed
reports **not exempt**. Reviewer fixture B — one complete marker-free block
then a genuine transcript whose closing fence never arrives: pre-fix reports
**not exempt** (the false flag), fixed reports **exempt**. Both defects
reproduce and both are closed.

Four controls confirm each result is reached for the claimed reason and not
by accident:

- Delete the decoy marker line from fixture A and the pre-fix function drops
  to not-exempt — so the fail-open really is the marker inside the shifted
  pseudo-block, not something else in the text.
- Put fixture A's stray run alone on its own line and both functions agree it
  is exempt — the fix is line-anchoring, not a blanket refusal.
- Terminate fixture B's final fence and both functions agree it is exempt —
  the pre-fix false answer really is the dropped trailing fence.
- Strip the markers from fixture B's unterminated block and the fixed
  function drops to not-exempt — the unterminated-fence rule is not blanket
  exempting everything after a lone fence.

Four further edge probes: an indented, language-tagged fence inside a list
item still works; a citation before the first fence in a section is correctly
not exempt; a citation on the closing fence line itself is now exempt where
it previously was not (a deliberate, harmless consequence of ending a block
at the close fence's line end); and the forged-marker residual is confirmed
still open and unchanged, exactly as criterion 7 requires and as the
function's own doc comment states.
