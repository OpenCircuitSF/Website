## Description

`web/src/views/admin/Workshops.svelte:241`, the hint under the "New workshop" modal, reads:

> The slug and every other field are set from the full editor after the workshop is created.

That is false twice over:

1. **The slug is generated at creation**, from the title typed in that very modal — not later, and not in the editor.
2. **It is never settable from the editor.** `WorkshopEditor.svelte`'s own hint says the opposite: "Auto-generated from the title and set once at creation — the server does not accept edits to it through this screen."

So the admin console contradicts itself across two screens, one of which is the screen that just created the slug.

`#0137` decided slugs stay server-generated and immutable, and corrected every comment and hint it found — but this copy lives in a component neither of that issue's commits touched, so `#0137`'s "the UI already matches the decision" is incomplete.

## Root cause

`web/src/views/admin/Workshops.svelte:241`'s "New workshop" modal hint said
the slug is "set from the full editor after the workshop is created." Two
things were false: `submitCreate` calls `createWorkshop({ title })` — the
slug is generated server-side from that title at creation time, in this
modal, not later — and `WorkshopEditor.svelte`'s own hint already says the
slug can never be edited through the editor screen ("the server does not
accept edits to it through this screen"). A sweep of every `slug` occurrence
in `web/src` (not a targeted grep for this phrase) turned up no other stale
copy in either screen — the rest of the modal's copy (title field, error
text, button labels) matches current behavior.

Both carried-in items were pre-existing, minor copy/behavior gaps found by
the `#0162`/`#0167` reviewers and folded into this issue rather than filed
separately (see this issue's Notes).

## Fix

**Modal hint** (`Workshops.svelte`): replaced with "The slug is
auto-generated from this title at creation and can't be changed afterward.
Every other field is set in the full editor next." — reuses
`WorkshopEditor.svelte`'s own "Auto-generated from the title ... at
creation" phrasing so an admin reading both screens sees the same claim, and
keeps the (true) statement that everything besides the title is set in the
editor afterward.

**Announce panel targeting sentence** (`announceTargetingDescription` in
`workshopAdmin.ts`): the targeted-interests case now reads "The draft will
be targeted at this workshop's interests." instead of "It will be targeted
at this workshop's interests." — `#0162` split the panel into three separate
elements/paragraphs, so by the time this sentence renders "It" pointed at
"the draft" two sentences and one paragraph break away. Naming the subject
again removes the dangling pronoun. The no-interests fallback sentence
already said "the draft" explicitly and needed no change.

**`isPreviewStale` trimming**: changed the comparison from
`bodyMd !== (savedBodyMd ?? '')` to
`bodyMd.trim() !== (savedBodyMd ?? '').trim()`. Decision: **trim inside the
predicate**, departing from `#0167`'s literal criterion
(`fields.bodyMd !== workshop.body_md`). Reasoning: `validateWorkshopForm`
already saves `fields.bodyMd.trim()`, so an untrimmed compare can only ever
*over*-warn (flag staleness for a whitespace-only change that Save would
turn into a byte-identical `body_md`) and never under-warn (anything that
differs after trimming also differs before trimming) — there is no
protective value in keeping the untrimmed compare, and warning an admin
about a save that changes nothing is pure noise the trimmed version removes
for free. Documented in the function's doc comment, including why this
departs from #0167's original wording.

### The modal hint, clause by clause

Each clause was verified against behaviour, not against the sibling hint's
wording.

| Clause | Verified against | Holds? |
|---|---|---|
| "The slug is auto-generated from this title" | `Workshops.svelte:148` sends `createWorkshop({ title })` and nothing else; `internal/workshops/store.go:552-557` — `Create` does `title := strings.TrimSpace(in.Title)` then `base := slugify(title)`. The slug is derived from the title typed in this very modal. | ✅ |
| "…at creation" | Same `Create`; the slug is written by the one `INSERT`, before the editor is ever opened (`submitCreate` switches to the editor only after the response arrives). | ✅ |
| "…and can't be changed afterward" | `admin_workshops.go:353-354`: `patchWorkshopRequest` has "deliberately NO slug field", and `decodeJSON` uses `DisallowUnknownFields`, so a `"slug"` key is a 400 — re-proved by execution in `#0137`'s own review (4 bodies, both verbs, no partial write). No other route writes `slug`; `Delete` is the only other mutation. | ✅ |
| "Every other field is set in the full editor next." | The editor's form covers `title`, `summary`, `body_md`, `starts_at`, `ends_at`, `location_name`, `location_address`, `location_note`, `capacity`, `signup_url`, `cover_image` and the interest checkboxes, and the Status panel covers `status` — i.e. every column in `migrations/000020` that an admin sets. The only columns it does not is `published_at`/`created_at`/`updated_at`, which are server-stamped and are not "fields" in this sentence's sense. | ✅ |

Two things the criterion asked about specifically:

- **Are there fields set at creation that the editor cannot change?** No.
  Creation sets exactly `title` (editable in the editor) and `status`
  defaulting to `draft` (changeable from the Status panel). Everything else
  starts NULL.
- **Does the modal itself set anything else?** No — `submitCreate` sends a
  one-key body. The only looseness in the sentence is that `title`, which the
  modal does set, is swept into "every other field"; but it *is* also set in
  the editor next, so the sentence is not false. Not worth changing.

One deliberate simplification, recorded so nobody reads it as a defect later:
`Create` appends `-2`, `-3`… on a slug collision
(`store.go:567-571`), so the slug is generated *from* the title but is not
always `slugify(title)` exactly. "Auto-generated from this title" is still
the true and useful claim for an admin, and the editor displays the actual
slug immediately.

**Consistency with the editor's hint** (criterion 2) — the editor reads
"Auto-generated from the title and set once at creation -- the server does
not accept edits to it through this screen"
(`WorkshopEditor.svelte:395-399`, inside the `{:else}` branch of
`isSlugEditable()`, which is unconditionally `false`). The two now make the
same two claims — generated from the title, fixed at creation — in parallel
phrasing. An admin reading both has nothing to reconcile.

### Carried-in item 2 — the `isPreviewStale` trim: the claim is verified, and it holds

The argument to check was: `validateWorkshopForm` saves `.trim()`'d bodies,
so an untrimmed compare can only over-warn. Both halves were checked
independently.

**Is the save path's trim unconditional?** Yes.
`workshopAdmin.ts:586` is `body_md: fields.bodyMd.trim()`, sitting in
`validateWorkshopForm`'s single success `return` — there is no branch that
returns a `ValidatedWorkshopFields` with an untrimmed body.

**Is there any path that writes `body_md` without it?** No. A sweep of every
`body_md`/`bodyMd` occurrence in `web/src` (not a grep for `trim`) finds
exactly three writers in the workshop path, and the two that are not
`validateWorkshopForm` do not carry a body at all:

| Writer | Body sent |
|---|---|
| `Workshops.svelte:148` `createWorkshop({ title })` | none — creation cannot set `body_md` |
| `WorkshopEditor.svelte:293` `updateWorkshop(id, { title, ...rest })` | `rest` comes straight from `validateWorkshopForm`, i.e. trimmed |
| `WorkshopEditor.svelte:323` `updateWorkshop(id, { status })` | none — status-only transition |

(`CampaignEditor.svelte`/`Campaigns.svelte` also send a `body_md`, but that is
`email_campaigns`, a different table and a different screen;
`isPreviewStale` is called from exactly one place,
`WorkshopEditor.svelte:166`, with `fields.bodyMd` and `workshop?.body_md`.)

So the under-warn direction — the one that would matter — is closed: with the
only writer trimming, any buffer whose trimmed form differs from the saved
trimmed form also differs untrimmed, and the trim can only remove warnings
that a save would have made byte-identical. A probe asserted that implication
directly over a set of pairs, and confirmed inner whitespace still counts as
stale (`isPreviewStale('a  b', 'a b') === true`) — only leading/trailing
whitespace is forgiven, which is exactly what `.trim()` removes at save time.

**`savedBodyMd ?? ''` still covers both.** The declared type is
`string | undefined`, and `??` catches `null` as well; probed at runtime with
`undefined` and with a cast `null` — `('', undefined)`, `('   \n ', undefined)`,
`('', null)`, `('  ', null)` all `false`, `('x', undefined)` and `('x', null)`
both `true`.

Mutation check: reverting to `bodyMd !== (savedBodyMd ?? '')` fails the new
whitespace-only test (1 failed | 6 passed), so the change is guarded.

**Ruling on the departure from `#0167`'s literal criterion: accepted.**
`#0167`'s criterion was written as an implementation sketch
(`fields.bodyMd !== workshop.body_md`) of an intent — "tell the admin when
the rendered preview is older than what they have typed". Trimming serves
that intent more precisely, because the thing the preview will show after a
save is the trimmed body. The doc comment records both the reasoning and the
fact that it departs, which is what the criterion asked for ("decide whether
to trim … or leave it and record why").
