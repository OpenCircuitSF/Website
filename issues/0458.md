## Description

`internal/config`'s value-shape scan has been widened three times — `#0450`
(digit-leading variable names), `#0453` (the `$(…)` paren form), and whatever
closes `#0457` (the backslash family). **None of those widenings is pinned by a
committed test.**

Measured by `#0453`'s reviewer: reverting that issue's `\(?` widening leaves the
**entire `internal/config` suite green.** Each widening was proved by a
mutation run in a throwaway worktree — which is what the criteria asked for, and
those proofs were real — but a worktree proof evaporates when the worktree does.

## Why this is worth closing, carefully

The scan's own per-shape table test **calls itself a regression pin**, and for
the four original shapes it is one. It simply does not have a row for anything
added since. So the document and the artefact disagree, which is the condition
this phase has spent a dozen issues removing.

**Not a bounce on any of the three**, and worth saying why: `#0441`, `#0450` and
`#0453` all shipped this way, each criteria-compliant, and `#0453`'s reviewer
declined to bounce for it precisely because the criteria prescribed the worktree
proof and got it. This is the accumulated gap, not any one pass's defect.

## Acceptance criteria

1. Each widened form gains a row in the existing per-shape table test, so a
   revert of any widening fails a committed test.
2. **This must not touch the four-shape structure** — adding table rows is not
   adding a shape. Three reviews have verified the surrounding machinery
   (`minScannedEnvExampleAssignments`, `checkScannedFloor`, the fail-closed
   proof's use of the package constant); leave all of it alone.
3. Prove each new row **bites**: revert each widening in turn, in a throwaway
   worktree, and confirm the table test now fails naming that form. A row that
   passes both before and after is decoration.
4. **No new mechanism** (§8, `#0258`, and `#0441`'s criterion 5). Rows in an
   existing table, not a new test file.
5. If `#0457` is still open when you start, decide whether to wait for it or to
   pin what exists and let `#0457` add its own row. **Record the decision** —
   `#0457`'s criteria already ask it to state a false-positive count, so the two
   are naturally sequenced but not strictly dependent.

## Root cause

The per-shape table test proves each of the four original shapes with a
targeted `badLine`, but nothing was ever added to it for the three widenings
that followed — each of those was proved only in a throwaway `git worktree`
at the time, per its own issue's criteria, and that proof does not persist
once the worktree is removed. So the table's own doc comment describes it as
"a stable regression pin" while three real widenings sit outside what it
pins.

## Fix

Criterion 5 first: `#0457` was already `resolved` when this issue's
implementation pass started, so all three widenings exist in the shipped
pattern and are pinned together in one pass rather than pinning two now and
waiting on a fourth issue for the third. Recording this per criterion 5 —
waiting was the alternative and was not chosen, since there was nothing left
to wait for.

Added three rows to the existing `cases` table in
`TestScanEnvExampleValueShapes_DetectsEachDivergentShape`, one per widening.
Each `badLine` was chosen so it is caught **only** by the specific pattern
change that widening made, verified against the pattern's history rather than
guessed:

- `#0450` (digit-leading names): `PRICE=cost$5` — a bare digit right after the
  dollar sign, which the pre-`#0450` letter/underscore-led class cannot match
  at all, so reverting only `#0450` drops this case from one violation to
  zero.
- `#0453` (the `$(...)` form): `PRICE=cost$(FOO)` — the pattern before
  `#0453` had no optional paren admitted between the dollar and the name, so
  reverting only `#0453` drops this case from one violation to zero.
- `#0457` (backslash before a dollar): the **bare** `` PRICE=cost\$ `` — no
  variable name follows the dollar sign at all, which is the one shape the
  plain (non-backslash) alternative can never match on its own regardless of
  which widening is or isn't present. Reverting only `#0457` drops this case
  from one violation straight to zero, rather than merely changing which of
  the two violation messages fires (which is what the alternative form
  `` cost\$FOO `` would do, since the plain alternative already matches its
  trailing `FOO` even with the backslash prefix reverted — the bare form was
  chosen specifically because it does not have that ambiguity).

Nothing else in the file changed. `minScannedEnvExampleAssignments`,
`checkScannedFloor`, `envAssignmentLine`, `envTrailingComment`, and
`envDollarExpansion` itself are byte-for-byte unchanged from the parent
commit — confirmed by diffing the commit and grepping each declaration
afterward, not assumed. `scanEnvExampleValueShapes` still has exactly the
same four shape-checks behind its `(scanned int, violations []string)`
signature; the three new cases are additional rows under the existing
"dollar expansion" table entry, not a fifth `if` branch. No new test file
was added — `internal/config` still holds the same four files it did before
this change.

### The `#0457` row choice — the reasoning holds, and it is the right call

The draft chose the bare backslash-dollar form over the trailing-name variant
on the reasoning that only the backslash alternative can match the bare form.
I measured both candidates through the real scan function, swapping the
package pattern variable between the shipped and `#0457`-reverted forms:

| Candidate `badLine` value | Shipped pattern | `#0457` reverted |
|---|---|---|
| bare backslash-dollar | 1 violation, backslash message | **0 violations** |
| backslash-dollar followed by a name | 1 violation, backslash message | **1 violation**, plain `$VAR` message |

So the stated reasoning is exactly right: with the backslash alternative gone,
the plain alternative still matches the trailing name, and the trailing-name
candidate would keep its violation count at 1 while merely swapping which
message fires.

Worth recording *why* that matters, since the trailing-name form would in fact
still have bitten — the row asserts the message mentions a backslash, and the
plain message does not, so it would have failed on the substring assertion.
The bare form is strictly stronger because it fails on the **count** assertion,
which is a hard structural fact, rather than on a substring of a message whose
wording is prose and could legitimately be reworded by a later pass without
anyone intending to weaken the pin. The draft picked the more robust of two
working options, and its explanation of the mechanism is accurate.
