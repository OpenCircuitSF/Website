## Description

`internal/config`'s value-shape scan has been widened three times — `#0450`
(digit-leading variable names), `#0453` (the `$(…)` paren form), and whatever
closes `#0457` (the backslash family). **None of those widenings is pinned by a
committed test.**

Measured by `#0453`'s reviewer: reverting that issue's `\(?` widening leaves the
**entire `internal/config` suite green.** Each widening was proved by a
mutation run in a throwaway worktree — which is what the criteria asked for, and
those proofs were real — but a worktree proof evaporates when the worktree does.

## Why this is worth closing, carefully

The scan's own per-shape table test **calls itself a regression pin**, and for
the four original shapes it is one. It simply does not have a row for anything
added since. So the document and the artefact disagree, which is the condition
this phase has spent a dozen issues removing.

**Not a bounce on any of the three**, and worth saying why: `#0441`, `#0450` and
`#0453` all shipped this way, each criteria-compliant, and `#0453`'s reviewer
declined to bounce for it precisely because the criteria prescribed the worktree
proof and got it. This is the accumulated gap, not any one pass's defect.

## Acceptance criteria

1. Each widened form gains a row in the existing per-shape table test, so a
   revert of any widening fails a committed test.
2. **This must not touch the four-shape structure** — adding table rows is not
   adding a shape. Three reviews have verified the surrounding machinery
   (`minScannedEnvExampleAssignments`, `checkScannedFloor`, the fail-closed
   proof's use of the package constant); leave all of it alone.
3. Prove each new row **bites**: revert each widening in turn, in a throwaway
   worktree, and confirm the table test now fails naming that form. A row that
   passes both before and after is decoration.
4. **No new mechanism** (§8, `#0258`, and `#0441`'s criterion 5). Rows in an
   existing table, not a new test file.
5. If `#0457` is still open when you start, decide whether to wait for it or to
   pin what exists and let `#0457` add its own row. **Record the decision** —
   `#0457`'s criteria already ask it to state a false-positive count, so the two
   are naturally sequenced but not strictly dependent.
