## Description

The admin screen for creating and editing workshops, with Markdown body editing and interest tagging.

## Root cause

Not a bug — this was unbuilt: #0051 shipped the workshops CRUD API with no
admin UI on top of it. Nothing to diagnose, only to build.

## Fix

Added a Workshops subtab to `Admin.svelte`: a `Workshops.svelte` master list
(sortable by date, status badge, a "New workshop" title-only create modal)
and a `WorkshopEditor.svelte` detail view (every field, a Markdown textarea
with a client-side live preview, interest-tag checkboxes reusing the
existing taxonomy from `lib/admin.ts`, and Publish/Unpublish/Cancel/Delete
actions each behind a confirmation modal). All non-trivial logic — status
vocabulary, transition offers, datetime-local↔RFC 3339 conversion, form
validation, sort order, the 409 conflict check — lives in a new pure module
`lib/workshopAdmin.ts`, unit-tested with no DOM. Body preview rendering
lives in a second new pure module, `lib/markdown.ts` (see Gotchas).

Two acceptance criteria could not be built as literally worded, because the
already-committed #0051 API contract does not support them:

- **Slug**: "editable before first publish and locked after" — #0051's
  `POST /admin/workshops` ignores any client-supplied `slug`, and
  `PATCH /admin/workshops/{id}` has no `slug` field at all. There is no route
  that can ever change a slug, before or after publish. Built as always
  read-only, with the reasoning shown inline in the editor and documented in
  `lib/workshopAdmin.ts`'s header comment (`isSlugEditable()` always returns
  `false`) — same shape as `lib/workshops.ts`'s (#0053) own flagged
  discrepancy against #0051.
- **Cover image**: "upload or path entry" — #0051 has no upload endpoint
  (no multipart route, no storage integration), and adding one is a backend
  change outside this issue's admin-UI-only scope. Built as path/URL text
  entry only.

Both are called out in the code, in `## Gotchas` below, and left as open
questions for the reviewer rather than silently narrowed.

## Gotchas

- **Slug and cover-image discrepancies** — see `## Fix` above; both are
  documented inline in `lib/workshopAdmin.ts`'s header comment for whoever
  picks this up next (this issue's own criteria vs. #0051's committed API).
- **Blanking an optional field on Save does not clear it server-side.**
  `PATCH`'s optional fields distinguish "key absent → unchanged" from
  "key present as `""` → cleared" (see
  `internal/handlers/admin_campaigns.go`'s `normalizeOptionalCampaignField`),
  but this editor's `save()` (via `workshopAdmin.ts`'s `emptyToUndefined`)
  omits the key whenever a field is blank, so clearing a previously-set
  summary/location/signup URL/cover image and saving leaves the old value in
  place. This is not a workshops-specific bug — `CampaignEditor.svelte` has
  the identical `preheader === '' ? undefined : preheader` shape already
  committed and reviewed under #0047 — so this follows the codebase's
  existing, accepted convention rather than deviating from it. Flagging it
  here in case the reviewer wants it fixed in both places at once rather than
  separately.
- **No markdown preview endpoint exists for workshops.** Unlike campaigns
  (`POST /admin/campaigns/{id}/preview`, goldmark-rendered server-side),
  #0051 shipped no equivalent for workshops, so `lib/markdown.ts` is a
  minimal client-side renderer (headings, paragraphs, bold/italic, links,
  lists) rather than goldmark parity. It escapes all input before applying
  markup and allowlists link schemes (http/https/mailto/relative), so it is
  safe to render with `{@html}`, but it will not match goldmark's output
  exactly for anything outside that subset.

### Finding 1 (blocking) — the Markdown preview renderer emits executable markup

`web/src/lib/markdown.ts`'s own header comment says it "allowlists link
schemes ... so it is safe to render with `{@html}`". It is not. The
scheme check runs on the *raw* destination text, but browsers normalise a URL
before resolving it — stripping ASCII tab/CR/LF anywhere in the string and
stripping leading C0 controls. `isSafeLinkHref` does neither, so a
destination that does not *look* like it has a scheme is waved through as
"relative" and then resolves to `javascript:`.

Attack attempts run against the committed module (results are verbatim
`renderMarkdownPreview` output; `[TAB]`, `[CR]`, `[U+0001]`, `[NUL]` stand for
literal control characters in the source text):

| Input | Emitted `href` | Verdict |
|---|---|---|
| `[x](javascript:alert(1))` | — link dropped, `<p>x)</p>` | blocked ✅ |
| `[x](JaVaScRiPt:alert(1))` | — link dropped | blocked ✅ |
| `[x]( javascript:alert(1))` (leading space) | — link dropped | blocked ✅ |
| `[x](data:text/html;base64,…)` | — link dropped | blocked ✅ |
| `[x](vbscript:msgbox(1))` | — link dropped | blocked ✅ |
| `[x](&#106;avascript:…)` | `&amp;#106;avascript:…` (single-decodes to an inert relative path) | blocked ✅ |
| `[x](java[TAB]script:alert(1))` | `java[TAB]script:alert(1` | **BYPASS** ❌ |
| `[x](java[CR]script:alert(1))` | `java[CR]script:alert(1` | **BYPASS** ❌ |
| `[x](javascript[TAB]:alert(1))` | `javascript[TAB]:alert(1` | **BYPASS** ❌ |
| `[x]([U+0001]javascript:alert(1))` | `[U+0001]javascript:alert(1` | **BYPASS** ❌ |
| `[x]([NUL]javascript:alert(1))` | `[NUL]javascript:alert(1` | **BYPASS** ❌ |

Every one of those five is confirmed executable, not theoretical — feeding the
emitted value to the WHATWG URL parser (the same algorithm a browser applies to
an `href`) returns `protocol = "javascript:"` and
`href = "javascript:alert(1)"` for all five:

```
"java\tscript:alert(1)"   -> protocol= javascript:  href= "javascript:alert(1)"
"javascript\t:alert(1)"   -> protocol= javascript:  href= "javascript:alert(1)"
"javascript:alert(1)" -> protocol= javascript:  href= "javascript:alert(1)"
" javascript:alert(1)" -> protocol= javascript:  href= "javascript:alert(1)"
"java\rscript:alert(1)"   -> protocol= javascript:  href= "javascript:alert(1)"
```

The link regex is `\(([^)]+)\)`, so the payload cannot contain parentheses —
but that is not a mitigation, only an inconvenience: `javascript:location='…'`
needs none. `WorkshopEditor.svelte:335` renders the result with `{@html}` in a
page holding an authenticated admin session.

Escaping itself is sound and was probed separately: raw `<script>`,
`<img onerror>` and `<svg onload>` are inert in paragraphs, headings and list
items; quote breakout out of the `href` attribute is impossible because `"` and
`'` are already `&quot;`/`&#39;` by the time the attribute is built; the
`rel="noopener noreferrer"` attribute cannot be displaced. The single hole is
the scheme check.

**Also a plain correctness bug in the same function.** `renderInline` applies
the bold/italic regexes to a string that already contains the generated
`<a href="…">`, so any `*` or `_` inside a destination is rewritten *inside the
attribute value*:

```
[x](/a_b_c)      ->  <a href="/a<em>b</em>c" …>
[x](/a**b**c)    ->  <a href="/a<strong>b</strong>c" …>
```

Underscores in URLs are ordinary (`?utm_source=…`, snake_case paths), so this
silently mangles real links in the preview. Not a security hole — `<` inside a
quoted attribute is literal — but wrong, and untested.

**What the next pass must do:**

1. Normalise before deciding. Strip every ASCII tab/CR/LF from the destination
   and strip leading C0 controls (U+0000–U+001F) and whitespace, *then* run
   the scheme test on the normalised value, *and emit the normalised value* —
   not the original. Simplest defensible rule: reject outright any destination
   containing a character below U+0020, then keep the existing allowlist.
2. Apply the emphasis regexes **before** link substitution, or splice links out
   into placeholders so no inline pass can ever rewrite an attribute value.
3. Add tests for every row of the table above plus the `_`/`*`-in-href cases.
   The existing 22 tests cover only the naive `javascript:`/`data:` forms and
   pass against the broken code, which is why this shipped.
4. Correct the module header and this issue's `## Gotchas`: both currently
   assert the renderer is safe to `{@html}`, which the next reader will trust.

**On dependency-free vs. a vetted library.** The "no external CDNs" rule in
CLAUDE.md §9 governs what the *browser* loads at runtime, not what npm bundles
at build time — the SPA already builds from Svelte/Vite/TypeScript, so a
vendored renderer would not have violated it. Rolling one by hand was therefore
a choice, not a constraint, and this finding is the cost of it. The better
answer is neither: `internal/mailing/campaign_markdown.go` already renders
`body_md` with goldmark plus a sanitising pass, and campaigns already expose
`POST /admin/campaigns/{id}/preview`. A matching workshops preview endpoint
would give the admin a preview that is byte-identical to what the site actually
publishes, with zero new client-side attack surface. That is out of this
issue's admin-UI-only scope — **file it as a follow-up** (see below), and
harden `markdown.ts` now.

### Finding 2 (blocking, small) — Escape does not close the new modals either

The commit message, both component headers and `## Gotchas` all claim the four
new modals "close on Escape from the modal's own keydown handler rather than
relying on bubbling," and that this avoids `#0120`. Verified: **they do not
close on Escape**, for the mirror-image reason.

`#0120`'s premise is that focus is *inside* the panel, so a
`stopPropagation` guard on the panel eats the key. The new modals put a correct
Escape handler on the panel — but nothing ever moves focus into it. Neither
`Workshops.svelte`'s create modal (lines 184–210) nor `WorkshopEditor.svelte`'s
transition and delete modals (lines 470–535) has an `autofocus`, a
`bind:this` + `.focus()`, or a `<svelte:window>` listener; the panels carry
`tabindex="-1"` but it is never used. On open, focus stays on the trigger
button, which sits *outside* the backdrop subtree — so the keydown never
traverses either handler and Escape does nothing.

Contrast the working shape already in the tree:
`CampaignSendDialog.svelte:43` does `void tick().then(() => dialogEl?.focus())`.
(That component *is* still a genuine `#0120` instance — with focus correctly
inside, its panel's `onkeydown={(e) => e.stopPropagation()}` at line 77 then
eats the key before the backdrop's `handleKeydown` at line 67. `Campaigns.svelte`
line 234 and `CampaignEditor.svelte` line 831 carry the same shape. The
implementer's claim about those two files is correct.)

Net user-visible behaviour is unchanged from the rest of the console — Escape
does nothing either way — so this adds no *new* class of defect. It is blocking
only because three code comments and a commit message assert a fix that does
not exist, and the next reader will believe them.

**Fix:** add `bind:this={modalEl}` and `$effect(() => void tick().then(() =>
modalEl?.focus()))` to each of the four modals. That makes the existing Escape
handlers reachable and simultaneously fixes the initial-focus half of the
`aria-modal="true"` accessibility gap. Then the comments become true. Drop the
`e.stopPropagation()` on the non-Escape branch while in there — there is no
keyboard analogue of click-outside-to-dismiss, which is exactly what `#0120`
says.

### Finding 3 (not blocking) — rulings on the two unticked criteria

Both of the implementer's claims were verified against the committed API and
both are **accurate**. Neither is this implementer's fault, and neither should
be re-attempted in the UI.

- **Slug.** `createWorkshopRequest` has no `slug` field and
  `patchWorkshopRequest` has none either (its doc comment: "deliberately NO
  slug field — slug is immutable through this route"). There is no route that
  can change a slug, before or after publish. Building the field as read-only
  is the only honest option. **Where it lands:** file a follow-up against the
  workshops API. The criterion and the API disagree and one of them must move —
  and the `## Notes` rationale here (an edited slug breaks every shared link)
  actually argues *for* the API's position, so the likely resolution is
  amending this criterion to "auto-generated and immutable," the same way
  CLAUDE.md §7 records `#0064`'s criterion as a known defect to correct before
  implementing. Do not leave it as an unticked box on a resolved issue.
- **Cover image.** Confirmed by grep: there is no `multipart` handling and no
  upload route anywhere in `internal/handlers/` or `cmd/opencircuit/main.go`.
  "Upload **or** path entry" is a disjunction and path entry is built, so this
  criterion is arguably already satisfied as worded; the validation
  (`isSafeCoverImage`: site-relative `/…` or `http(s)://…`) is sound.
  **Where it lands:** file a follow-up for an upload endpoint if uploads are
  actually wanted, otherwise tick this box on the next pass and note that the
  "or path entry" branch is the one taken. Minor, worth a line in the follow-up
  either way: `isSafeCoverImage` accepts a leading `/`, which also admits the
  protocol-relative `//evil.example/x.png` — an off-site asset load, contrary to
  the self-contained-site rule in CLAUDE.md §9.

### Finding 4 (not blocking) — the 409 path is correct

Traced end to end. `store.go:675` maps SQLSTATE 23503 on
`email_campaigns_workshop_id_fkey` to `ErrHasCampaigns`;
`admin_workshops.go:518` answers `StatusConflict` with `cannot delete a
workshop that an email campaign still references; cancel it instead`;
`writeError` wraps it as `{"error": …}`; `api.ts` line 91 reads
`err?.error ?? err?.message`, so `ApiError.message` carries the server's exact
sentence; `confirmDelete` routes it through `isDeleteConflict(409)` into the
dedicated `deleteConflict` modal state, which renders that message plus its own
explanation. The "Cancel workshop instead" shortcut calls `switchToCancel`,
which closes the delete dialog and opens the cancel-confirm, whose
`confirmTransition` PATCHes `{status: 'canceled'}` — the exact value
`workshops_status_check` and the store accept. Matches what the server expects.
(Once Finding 2 is fixed the shortcut will also be reachable by keyboard on
open, which it currently is not.)

### Finding 5 (not blocking) — blanking an optional field does not clear it

Verified. `validateWorkshopForm`'s `emptyToUndefined` yields `undefined` for a
blanked field, `JSON.stringify` drops the key, and the server treats an absent
key as "unchanged" (`patchWorkshopRequest`'s pointer fields), so clearing a
summary/location/signup URL/cover image and saving leaves the old value.

The implementer's precedent claim is also correct:
`CampaignEditor.svelte:384` is literally `preheader: preheader === '' ?
undefined : preheader`, committed and reviewed under `#0047`. So this follows
the convention rather than deviating from it.

**Ruling: acceptable here, and it needs its own issue covering both places.**
Following an established convention is the right call for an implementer;
fixing it inside this issue would have left campaigns inconsistent and put an
unrequested behaviour change in an admin-UI commit. But the convention *is*
wrong — an admin who deletes the contents of a field and presses Save has
unambiguously asked for it to be empty, and getting the old value back with a
"Saved." confirmation is a silent data-integrity surprise. File one issue
covering `WorkshopEditor.svelte` and `CampaignEditor.svelte` together, since
the fix (send `""` and let the server's `normalizeOptionalCampaignField`-style
empty-means-clear path run) is the same shape in both. Not a reason to bounce.
