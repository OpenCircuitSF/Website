## Description

`#0183` pinned one adjacency in `sendGuardState` — `unmet` versus `audienceCount === 0`. `#0183`'s review then swept the **input space** rather than each export's branches, and found the other two are still unpinned:

- swapping `status !== 'draft'` and `inFlight`
- swapping `inFlight` and `unmet`

Both pass the full suite. **This is the same defect as `#0183`'s own criterion 2, one pair higher** — and it sits on `#0047`'s send gate, whose doc comment states the branches "must stay exactly as enumerated."

Three smaller `normalizeCountInput` gaps from the same sweep, all surviving mutations:

- an **ASCII space is accepted as a separator**, though the contract admits only `,` and U+2009
- the **exact `Number.MAX_SAFE_INTEGER`** boundary is unasserted
- a **leading `+`** is accepted

One further survivor — `confirmMatches` with `&& count > 0` — is benign and should be left: `empty-audience` returns first, so the cell is unreachable. Say so rather than "fixing" it.

## Root cause

Same shape as `#0183`: five branches/inputs in `web/src/lib/sendConfirm.ts`
that no test could distinguish from their mutated counterpart.

1. `sendGuardState` checks `status !== 'draft'`, then `inFlight`, then
   `unmet.length > 0`, in that order — but no existing case set
   `status !== 'draft'` **and** `inFlight` together, nor `inFlight` **and**
   `unmet` non-empty together, so both adjacent swaps were invisible to the
   suite.
2. `normalizeCountInput` already implements the documented contract
   correctly (separator class is `/[, ]/g` — comma or U+2009 only, not
   ASCII space; digit regex is `/^\d+$/`, no leading sign; the safe-integer
   guard is `Number.isSafeInteger`, which is true exactly at the boundary)
   — but nothing asserted any of the three behaviors, so a mutation at any
   of them passed the whole suite.
3. `confirmMatches`'s hypothetical `&& count > 0` mutation cannot be
   observed at all: `sendGuardState` only ever calls `confirmMatches` after
   its own `audienceCount === 0` check has already returned
   `empty-audience`, so `count` (i.e. `audienceCount`) is always `> 0` by
   the time `confirmMatches` runs from that call site. The cell is dead,
   not undertested.

## Fix

Added five new cases to `web/src/lib/sendConfirm.test.ts`, no production
source changes:

- `sendGuardState`: two cases, each setting the two conditions of one
  adjacency simultaneously (`status: 'sending', inFlight: true` →
  `unavailable`; `inFlight: true, unmet: oneUnmet` → `sending`), pinning
  branch order the same way `#0183`'s `unmet`/`audienceCount` case did.
- `normalizeCountInput`: `'1 234'` (ASCII space, distinct from the existing
  U+2009 case) added to the `rejects` table; `String(Number.MAX_SAFE_INTEGER)`
  added to the `parses` table, asserting the exact boundary is accepted;
  `'+482'` added to the `rejects` table.

**Contract decision: no change.** All three `normalizeCountInput` behaviors
were verified by direct inspection of the compiled regex bytes (the
separator class is genuinely ` `, not an ASCII space — confirmed with
`xxd`) and by evaluating the real function against each input in isolation
before writing any test. The implementation already matches the doc
comment's stated contract in all three cases; only the test coverage was
missing. An admin pasting a spreadsheet count with an ASCII space would get
a "doesn't match" hint rather than silent misacceptance, which is
acceptable — `confirmHint` still names the expected count, so the input
isn't silently swallowed, just not auto-normalized. Changing the contract to
accept ASCII space was considered and rejected: broadening the accepted
separator set is a real behavior change that deserves its own issue and
review, not a side effect of a coverage pass.

**`confirmMatches`'s `&& count > 0` survivor is left alone**, as directed.
Recorded here rather than "fixed": `sendGuardState`'s call to
`confirmMatches(input.confirmRaw, input.audienceCount)` is only reached
after the `audienceCount === 0` branch has already returned, so
`count > 0` always holds at that call site — the mutated cell is
unreachable, not a coverage gap.

### The declined contract change is the right call — and better justified than it said

Judged rather than accepted. Declining to broaden the separator set to ASCII
space is correct, for three reasons the `## Fix` note only half-states:

- **The dialog renders the count with no separator at all.**
  `CampaignSendDialog.svelte` prints `{summary.recipients}` raw (lines 87 and
  108: *"Type 4820 to confirm"*), not `toLocaleString()`. There is no
  copy-paste path that can produce a space-separated number, so the "admin
  pasting a spreadsheet count" scenario is narrower than it sounds — it would
  have to be a number the admin sourced from outside this screen.
- **This is a confirmation field for an irreversible action.** Broadening what
  counts as "the same number" makes the confirmation weaker. Strictness is the
  correct bias here, and the failure mode is a *visible* hint naming the exact
  digits to type (`confirmHint`), not silent misacceptance and not data loss.
- **ASCII space would be the wrong widening anyway.** Checked what browsers
  actually emit: `(4820).toLocaleString()` gives U+202F in `fr-FR` and U+00A0
  in `sv-SE`/`ru-RU`, a comma in `en-US`, a period in `de-DE` — and **U+2009 in
  none of them**. So the contract's existing thin-space branch is already dead
  as a paste path, and if anyone ever revisits the accepted set the real
  question is U+00A0/U+202F, not ASCII space. Not a papercut, and not worth its
  own issue.

### The enumerated order is the *right* order — walked adjacency by adjacency

The tests only earn their keep if what they cement is correct, so each
overlapping state was reasoned through rather than assumed.

The code order (`status` → `inFlight` → `unmet` → `audienceCount === 0` →
`confirmMatches` → ready) matches the `SendGuardState` doc comment's
enumeration exactly, so what the two new cases pin is the documented contract
itself, not an accident of authorship.

- **`status !== 'draft'` before `inFlight` → `unavailable` wins.** The
  overlapping state is real: an admin clicks Send, the client sets `inFlight`,
  the server flips the row to `sending`, and a refetch lands while the request
  is still outstanding. `unavailable` is the correct answer because the
  persisted status is a durable, server-authoritative fact while `inFlight` is a
  transient client flag, and because `unavailable` means "the control shouldn't
  be rendered at all" (`canSendCampaign` is the render gate) — the strictly
  stronger statement. Neither ordering differs in *safety* (both disable the
  send), so the tie goes to the more authoritative fact. Correct.
- **`inFlight` before `unmet.length > 0` → `sending` wins.** Overlap: a send is
  outstanding while a preflight refetch reports an unmet check. Here the
  ordering genuinely matters for the *message*, and `sending` is the right one:
  "A send for this campaign is already in progress" is true and warns against a
  retry, whereas `blocked`'s "Pre-send checks have not passed" would invite the
  admin to fix something and try again — the one action that risks a double
  send. Correct, and this is the adjacency where getting it backwards would
  have cost something.
- The two already-pinned adjacencies stay consistent with their own doc text:
  `blocked` before `empty-audience` (`#0183`) matches "*the checks pass* but the
  live audience count is 0", and `empty-audience` before `needs-confirm` matches
  "*everything else is clear* but the typed count does not match" — and avoids
  the absurdity of asking an admin to type `0` to confirm a send to nobody.

The whole order reads as most-durable/least-fixable first, most-transient/
most-user-fixable last, with every earlier branch a strictly stronger reason the
send cannot proceed. It is right, and it is now fully pinned.

### The `confirmMatches` survivor: right conclusion, incomplete reason

Verified by **execution**, not by reading, and the recording needs one
correction. `confirmMatches` has **three** callers, not one — `sendGuardState`
plus two direct calls from `CampaignSendDialog.svelte` (`confirmHint(confirmRaw,
summary.recipients)` at line 34 and `confirmMatches(...)` at line 56) — so
"`empty-audience` returns first, so the cell is unreachable" covers only the
first of them. Probing all three under the `&& count > 0` mutation:

| call | pristine | mutated |
|---|---|---|
| `sendGuardState({audienceCount: 0, …})` | `empty-audience` | `empty-audience` — **unaffected**, as claimed |
| `confirmMatches('0', 0)` | `true` | `false` — **affected** |
| `confirmHint('0', 0)` | `null` | `"Doesn't match — type 0 to confirm."` — **affected** |

So the cell is live at module level. It is nonetheless unreachable *in the
running app*, for a reason worth recording because it is load-bearing and was
not stated: `CampaignEditor.svelte` assigns `unmet` and `preflightSummary` from
**the same** preflight response (lines 442–443), and the server emits
`PreflightCodeEmptyAudience` whenever `AudienceCount == 0`
(`internal/mailing/preflight.go:180`). A `summary.recipients` of `0` therefore
always arrives with a non-empty `unmet`, which makes `editorGuard` `blocked`,
which keeps `sendGateOpen` false, which keeps the dialog shut. `count === 0`
cannot reach either dialog call site.

Conclusion unchanged — leave it alone, and the mutation still survives the full
suite (3,645 passed under it). But the record now says *why* for all three
callers, and the mutation would additionally be benign even if it did fire: it
would refuse to confirm a send to an empty audience.

### Reported for filing (§9 — not filed here)

Two observations from this review, neither a defect in this commit:

1. **`sendGuardState`'s `sending` branch has no production producer.** The only
   call site, `CampaignEditor.svelte`'s `editorGuard` (line 202), hardcodes
   `inFlight: false`. The real flag, `sendInFlight`, goes to
   `CampaignSendDialog` as a prop and is consumed there as a **raw boolean**
   (`if (inFlight) return;`, `disabled={inFlight}`) — the dialog never calls
   `sendGuardState` at all. So `kind: 'sending'`, and
   `sendGuardDescription`'s "A send for this campaign is already in progress."
   line, are currently unreachable from the UI. This does not weaken `#0184`'s
   two new cases — they pin a documented contract on the module that
   `sendConfirm.ts`'s own header calls the single source of truth — but the
   contract and the wiring have drifted apart, and the module header's "must
   only ever branch on `.kind`, never recompute any of the conditions below" is
   exactly what the dialog is doing.
2. **A stale comment states the opposite.** `CampaignEditor.svelte` line 199
   says the real confirmation "lives inside CampaignSendDialog, which
   re-evaluates `sendGuardState` against what the operator actually typed."
   `CampaignSendDialog.svelte` imports `normalizeCountInput`, `confirmMatches`,
   and `confirmHint` — not `sendGuardState`. One-line fix, but it is the comment
   a future reader would trust when reasoning about the send gate.
