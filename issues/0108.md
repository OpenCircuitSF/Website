## Description

`TestSuppressionStore_List_JoinsSubscriberStatus` fails with
`orphan rows = 0, want 1` on roughly half of all full-package runs, on a
completely idle machine. It is **not** a flake, not machine load, and not a
cross-package isolation problem — `uniqueSuppressionEmail` is not unique.

```go
// internal/subscribers/suppressions_test.go:11
func uniqueSuppressionEmail(t *testing.T) string {
	t.Helper()
	return fmt.Sprintf("zz-suppress-%d@example.com", time.Now().UnixNano())
}
```

macOS's wall clock advances in **1 µs** steps, and two adjacent calls to this
helper complete inside one tick once the test process is warm. Measured in
situ inside `internal/subscribers`' own test binary: **62 %** of adjacent call
pairs return byte-identical strings.

The test at `suppressions_test.go:387-388` makes exactly two adjacent calls
and requires them to differ:

```go
withSub := uniqueSuppressionEmail(t)
orphan  := uniqueSuppressionEmail(t)
```

When they collide, `Add(orphan, manual)` conflicts with `Add(withSub, manual)`
on the `(email, reason)` key and silently no-ops, and the classifying `switch`
sends every row to the `case withSub` arm — so `withSubRows` is still 2 (the
earlier assertions pass) and `orphanRows` is 0, which is precisely the
observed failure.

## Steps to reproduce

```bash
export TEST_DATABASE_URL='postgres://opencircuit:opencircuit@localhost:5432/opencircuit_test?sslmode=disable'
go test ./internal/subscribers/ -count=1     # fails ~50% of runs
```

Observed: 5 of 11 whole-package runs failed, at load average 1.4–3.0.
Reproduces identically against a private database
(`opencircuit_0038_rev`), which rules out shared-database interference.

**It passes 100 % of the time under `-run
TestSuppressionStore_List_JoinsSubscriberStatus`** — running it alone leaves
the process cold, so the first `fmt.Sprintf`/`t.Helper()` pair costs more than
1 µs and the two timestamps land in different ticks. That asymmetry is why
this reads as a flake: the obvious way to "re-run just that test" is exactly
the way that always passes.

## Expected behavior

Two calls to a helper named `uniqueSuppressionEmail` return two different
addresses, every time.

## Actual behavior

They return the same address about 62 % of the time, and the test that depends
on them differing fails about 50 % of the time.

## Notes

- Owned by `#0100` (`55a99a5`), which added
  `TestSuppressionStore_List_JoinsSubscriberStatus`; the helper itself came in
  with `#0033` (`ad6cafc`). Pre-existing, unrelated to `#0038` — nothing in
  `42d5104` touches `internal/subscribers/suppressions_test.go` or changes
  which tests run in that package.
- Fix: make the helper monotonic rather than clock-derived — an
  `atomic.Uint64` counter (or `crypto/rand`) appended to, or replacing, the
  nanosecond stamp. A `t.Name()` prefix would also work and reads better in
  failure output, but the counter is what actually guarantees the property.
- `suppressions_test.go:387-388` is the **only** adjacent pair in the tree
  that relies on two same-helper calls differing without an intervening
  database round trip. Every other `UnixNano()`-based helper
  (`uniqueEmail`, `testSubscriberEmail`, `uniqueAdminSuppressionEmail`,
  `sesUniqueID`, `uniqueSNSMessageID`) is either label-scoped or separated by
  an `INSERT`, so all of them are ≫ 1 µs apart. Fixing the one helper is
  enough; auditing the rest is optional hygiene.
- This was recorded in `#0038`'s `## Gotchas` as an unreproduced flake citing
  `CLAUDE.md` §5's ambient-load guidance. §5 does not apply — the load average
  was 1.4–3.8 throughout, far under the ~8 threshold, and §5's own instruction
  is that a failure on an idle machine is *not* the machine.
