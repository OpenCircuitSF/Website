## Description

`TestSuppressionStore_List_JoinsSubscriberStatus` fails with
`orphan rows = 0, want 1` on roughly half of all full-package runs, on a
completely idle machine. It is **not** a flake, not machine load, and not a
cross-package isolation problem — `uniqueSuppressionEmail` is not unique.

```go
// internal/subscribers/suppressions_test.go:11
func uniqueSuppressionEmail(t *testing.T) string {
	t.Helper()
	return fmt.Sprintf("zz-suppress-%d@example.com", time.Now().UnixNano())
}
```

macOS's wall clock advances in **1 µs** steps, and two adjacent calls to this
helper complete inside one tick once the test process is warm. Measured in
situ inside `internal/subscribers`' own test binary: **62 %** of adjacent call
pairs return byte-identical strings.

The test at `suppressions_test.go:387-388` makes exactly two adjacent calls
and requires them to differ:

```go
withSub := uniqueSuppressionEmail(t)
orphan  := uniqueSuppressionEmail(t)
```

When they collide, `Add(orphan, manual)` conflicts with `Add(withSub, manual)`
on the `(email, reason)` key and silently no-ops, and the classifying `switch`
sends every row to the `case withSub` arm — so `withSubRows` is still 2 (the
earlier assertions pass) and `orphanRows` is 0, which is precisely the
observed failure.

## Steps to reproduce

```bash
export TEST_DATABASE_URL='postgres://opencircuit:opencircuit@localhost:5432/opencircuit_test?sslmode=disable'
go test ./internal/subscribers/ -count=1     # fails ~50% of runs
```

Observed: 5 of 11 whole-package runs failed, at load average 1.4–3.0.
Reproduces identically against a private database
(`opencircuit_0038_rev`), which rules out shared-database interference.

**It passes 100 % of the time under `-run
TestSuppressionStore_List_JoinsSubscriberStatus`** — running it alone leaves
the process cold, so the first `fmt.Sprintf`/`t.Helper()` pair costs more than
1 µs and the two timestamps land in different ticks. That asymmetry is why
this reads as a flake: the obvious way to "re-run just that test" is exactly
the way that always passes.

## Expected behavior

Two calls to a helper named `uniqueSuppressionEmail` return two different
addresses, every time.

## Actual behavior

They return the same address about 62 % of the time, and the test that depends
on them differing fails about 50 % of the time.

## Root cause

`uniqueSuppressionEmail` (`internal/subscribers/suppressions_test.go:11`)
derived its address solely from `time.Now().UnixNano()`. macOS's wall clock
advances in 1 µs steps, and a warm test binary can execute two adjacent calls
inside a single tick, so the timestamp alone is not unique. A scratch
reproduction of the exact old helper body
(`/private/tmp/.../scratchpad/collision_check.go`, 100,000 adjacent-pair
calls in this environment) measured an **83.0%** collision rate — consistent
with the issue's own measured 62%, both far above zero, confirming the
mechanism rather than machine load.

`TestSuppressionStore_List_JoinsSubscriberStatus` (line 387–388) makes
exactly two adjacent calls — `withSub := uniqueSuppressionEmail(t)` then
`orphan := uniqueSuppressionEmail(t)` — and requires them to differ. On
collision, `Add(orphan, manual)` conflicts with `Add(withSub, manual)` on the
`(email, reason)` key and no-ops, so `orphanRows` comes back 0 instead of 1.

I audited every sibling `UnixNano()`-based test-email/ID helper in the tree
(`uniqueAuthEmail`, `uniqueSessionToken` in `internal/middleware/auth_test.go`;
`uniqueSignupEmail` in `internal/middleware/clientip_signup_test.go`;
`uniqueEmail`, `uniqueRawToken` in `internal/subscribers/store_test.go`;
`sesUniqueID` in `internal/handlers/ses_notifications_test.go`;
`uniqueAdminSuppressionEmail` in `internal/handlers/admin_suppressions_test.go`;
`testSubscriberEmail` in `internal/handlers/admin_subscribers_test.go`;
`uniqueSNSMessageID` in `internal/sesnotify/store_test.go`) and traced every
call site. None has a same-helper adjacent-call pair with no intervening
work: the middleware helpers take a `label` param that differs per call site,
and every other helper's calls within a single test are separated by a real
DB round trip (`Create`, `Add`, `INSERT`, `seedTestSubscriber`, etc.), which
costs far more than 1 µs. `uniqueSuppressionEmail` at
`suppressions_test.go:387-388` is confirmed as the only vulnerable pair, as
the issue's own notes predicted.

## Fix

Added a package-level `atomic.Uint64` counter (`suppressionEmailSeq`) and
appended it to the existing nanosecond timestamp in
`uniqueSuppressionEmail`, so every call returns a distinct address
regardless of clock resolution:

```go
var suppressionEmailSeq uint64

func uniqueSuppressionEmail(t *testing.T) string {
	t.Helper()
	seq := atomic.AddUint64(&suppressionEmailSeq, 1)
	return fmt.Sprintf("zz-suppress-%d-%d@example.com", time.Now().UnixNano(), seq)
}
```

No sibling helper needed the same fix — see the audit above; I checked all of
them and found no other instance of this defect shape.

## Gotchas

- None encountered. The tree already contained `42d5104` (#0038, bounced for
  a missing test) as expected; it was not touched, and `git status` after
  the fix showed only `internal/subscribers/suppressions_test.go` modified.
- **Review addendum on the sibling audit.** The conclusion is correct — no
  other helper has this defect — but the stated reasoning ("label-scoped or
  separated by a DB round trip") misses a third mechanism, which is the one
  actually protecting the largest group of adjacent pairs. A mechanical scan
  for the defect shape (two same-helper calls ≤3 lines apart) found ~10 real
  adjacent pairs, all in `internal/handlers/subscribe_test.go`
  (e.g. `:359`/`:362`, `:385`/`:386`, `:1582`/`:1583`). None is separated by
  a round trip and the helper takes no label — they are safe because each
  call site appends a distinct literal suffix (`+ "-pending"`, `+ "-unsub"`,
  `+ "-bot"`, `+ "-fast"`, …), so the addresses differ even on an identical
  timestamp. Worth knowing because that protection lives at the call site,
  not in the helper: a future bare `subscribeUniqueEmail(t)` added next to
  an existing call would reintroduce exactly this bug.
- Also noted, not a defect: `subscribeUniqueEmail` and `testSubscriberEmail`
  are both in `internal/handlers` and emit the byte-identical format
  `zz-subtest-%d@example.com`. Every call site of each is one-per-test with
  full test setup and DB work in between, so colliding would require two
  tests to start within the same microsecond. Not at risk, but the shared
  format is an accident rather than a design.
