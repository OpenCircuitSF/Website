## Description

The prose around `claimCommentGuardStoreGoParenSentinelRe` in
`internal/outbox/claim_comment_referent_guard_test.go` reads as though
**paren scoping** is what zeroes the `SelectDue` finding in `store.go`.

Measured by `#0374`/`#0375`'s reviewer: the paren-scoped window **does** contain
`SelectDue`, and the zero comes from **genuine resolution** — the identifier
really does resolve in the direction the comment claims. Paren scoping's actual
job there is excluding `ClaimRow`, which is a different exemption.

Cosmetic and non-blocking. But it is the same shape this phase keeps hitting: a
record that is itself misleading about the mechanism it describes — `#0358`'s
B2, `#0363`'s crossed labels, `#0366`'s "fixture-pinned" mix-up, and now this.

`#0374`'s `## Verification` carries the same attribution; its reviewer corrected
it there but deliberately did not repeat the fix in the committed comment, since
that was outside the issue's scope.

**The counterfactual, proved by mutation rather than argued.** On a copy of the
export with the open-paren clamp short-circuited (`false && pOpen > lo`), `lo`
falls from 59 to 0, the window widens to include `ClaimRow`, and the pinned
test fails naming **`ClaimRow`** — `comment says "ClaimRow" is above, but this
file's code has no ClaimRow occurrence above the comment (occurrences anywhere
in file: 1)`. `SelectDue` stays silent under the same mutation. That is the
corrected prose's exact claim, measured: paren scoping excludes `ClaimRow`;
`SelectDue`'s zero is genuine resolution and owes nothing to paren scoping.
It also shows the test is not vacuous.

**The corrected prose judged against that measurement, not against the issue.**
Each assertion checks out: the open-paren clamp (not the 90-char or
clause-boundary ones) sets the left edge here (59 vs -17 vs 0); `SelectDue` is
inside the window and is checked; it resolves because its declaration is
earlier in the file; `ClaimRow` is before the window's left edge and is never
iterated; without the clamp it would fire, having zero occurrences earlier in
the file. Nothing is claimed beyond that. The `t.Fatalf` message now attributes
each identifier's zero to its own mechanism.

**Comment-only, proved with the reviewer's own tool.** Built independently of
the implementer's (which used `go/scanner` mode 0): this one scans with
`ScanComments` **on** and filters `token.COMMENT` explicitly, so a raw string
is scanned as a `STRING` token whatever its content looks like, and it reports
the comment-token count separately. Fail-closed by construction — any scanner
error, or a zero-token stream, exits 2 rather than reporting `IDENTICAL`.
