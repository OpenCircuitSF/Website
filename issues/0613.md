# 0613 — Event types are not data: every listing is implicitly a workshop, and admins cannot add or disable a type

| | |
|---|---|
| **Status** | open |
| **Platform** | All |
| **Module** | workshops / db / admin |
| **Phase** | 6 — Workshops |
| **First seen** | 2026-11-04 |

## Description

Open Circuit SF is restarting Hack Nights: public get-togethers with no
presentation, which are not workshops. The `workshops` table has no notion of
type. Add an admin-managed `event_types` table so that types are rows, not code:
an admin can add, rename, reorder and disable a type without a deploy. Every
listing has exactly one type, and **Workshop** is the default.

This is the user's decision (2026-11-04), chosen over a fixed two-value `kind`
column for flexibility. The `workshops` table, the `workshop_id` foreign keys
and the `internal/workshops` package keep their names: renaming them would be a
large mechanical change with no user-visible gain. This issue is the data and
admin half only; `#0614` covers the public pages.

## Acceptance criteria

- [ ] A new migration (the next free number after `000044`; production is at
      `000044`, so nothing already applied may be edited) creates `event_types`
      with a unique URL-safe slug, a display name, an enabled flag, an
      is-default flag and a sort order. The database enforces at most one
      default row and that the default is enabled.
- [ ] The migration seeds, all enabled and in this order: **Workshop** (default),
      **Hack Night**, **Talk**, **Hackathon**, **Social**, **Field Trip**.
- [ ] The same migration adds a required `event_type_id` to `workshops`. Every
      existing row is backfilled to Workshop, and the foreign key refuses to
      delete a type that is in use. The down migration restores the prior schema.
- [ ] An admin can list, create, rename, reorder, enable and disable types, and
      choose the default, under the same session and admin authorization as
      `/admin/interests`. Each mutation writes an audit entry.
- [ ] A type in use cannot be deleted; the response says why and points to
      disabling instead. The default type cannot be disabled or deleted.
- [ ] A disabled type is not offered when creating a listing and is refused by
      the API for a new assignment. Existing listings keep the type, stay
      publicly visible, and can still be edited without being forced to change it.
- [ ] The workshop editor has a required type selector, pre-selected to the
      default for a new listing, and the admin list shows each listing's type.
      A create request that omits the type gets the default, so existing callers
      keep working.
- [ ] The admin console has a screen for managing types, reachable from its
      navigation, following the Interests screen's patterns.
- [ ] The public workshop API responses include each listing's type slug and
      name, so `#0614` can consume them.
- [ ] `PRD.md`, the `AGENTS.md` migration range and PRD index, and the relevant
      `docs/` page reflect the new table.

## Notes

- Prior art for the admin CRUD, audit logging and screen: the interest taxonomy
  (`internal/interests`, `/admin/interests`, its Svelte view).
- Disabling means "no new listings of this type"; it never hides history.
- `STORAGE=json` has no workshops backing, so verification must run against
  Postgres (`AGENTS.md` §5).
- Migration rules are in `AGENTS.md` §1. Rebuild the test template after adding
  the migration: `scripts/testdb.sh template`.
