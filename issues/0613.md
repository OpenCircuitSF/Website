# 0613 — Event types are not data: every listing is implicitly a workshop, and admins cannot add or disable a type

| | |
|---|---|
| **Status** | open |
| **Platform** | All |
| **Module** | workshops / db / admin |
| **Phase** | 6 — Workshops |
| **First seen** | 2026-11-04 |

## Description

Open Circuit SF is restarting Hack Nights: public get-togethers with no
presentation, which are not workshops. The `workshops` table has no notion of
type. Add an admin-managed `event_types` table so that types are rows, not code:
an admin can add, rename, reorder and disable a type without a deploy. Every
listing has exactly one type, and **Workshop** is the default.

This is the user's decision (2026-11-04), chosen over a fixed two-value `kind`
column for flexibility. The `workshops` table, the `workshop_id` foreign keys
and the `internal/workshops` package keep their names: renaming them would be a
large mechanical change with no user-visible gain. This issue is the data and
admin half only; `#0614` covers the public pages.

## Plan

Written 2026-11-04 against `0eb8194a`. The migration below was run in a private scratch database that day (since dropped): the backfill, the column default, the subquery in `RETURNING`, and all three constraint refusals behaved as described here.

### Decisions already made, so the implementer does not have to

- **Package:** new `internal/eventtypes` owns the `event_types` SQL (`AGENTS.md` §1). `internal/workshops` reads the slug and name by subquery.
- **Slug:** immutable after creation, same rule and same refusal as interests. "Rename" means the display name. `#0614` will put the slug in URLs.
- **Column default:** `workshops.event_type_id` defaults to a small SQL function returning the current default type's id. That one default does the backfill, and it keeps every raw `INSERT INTO workshops (slug, title)` working: `internal/devmocks/seed.go` and the test helpers in `internal/db`, `internal/interests` and `internal/handlers` need no edit.
- **Choosing the default is a `PATCH` field, never a sub-route.** `cmd/opencircuit/admin_wiring_test.go` sends every admin route an empty body with an admin session. A `POST .../default` needing no body would really switch the default to its throwaway row, and the suite's seed would stay wrong. `PATCH` with no body is a harmless 400.
- **Wire shape:** `event_type: {slug, name}` on public and admin views, plus `event_type_id` on admin only. `#0614` consumes `event_type`. The request field is `event_type_id`.
- **Nil means "not chosen" in the store:** `CreateInput.EventTypeID` and `UpdateInput.EventTypeID` are `*int64`. On create, nil is the default type. On update, nil keeps the current type. So none of the existing `workshops.CreateInput{...}` or `UpdateInput{...}` call sites in tests change.
- **Nav:** a new `event-types` section labelled **Event types**, in the Workshops group *after* `outreach`, because `adminRouter.test.ts` asserts `outreach` directly follows `workshops`.
- **Screen location:** its own `web/src/views/admin/EventTypes.svelte`, not more of `Admin.svelte` (2,861 lines). The behaviours copy the Interests section; the modal shape copies `Workshops.svelte`.
- **Clone of a disabled-type listing:** the copy is a new assignment, so the server refuses it and the clone dialog shows that message. It never silently changes type.
- **Seeds:** Workshop (default), Hack Night, Talk, Hackathon, Social, with `sort_order` 10 to 50. Private events are out of scope.

**Migration**

`migrations/000045_create_event_types.up.sql`:

```sql
CREATE TABLE event_types (
    id         BIGSERIAL PRIMARY KEY,
    slug       TEXT UNIQUE NOT NULL,
    name       TEXT NOT NULL,
    enabled    BOOLEAN NOT NULL DEFAULT TRUE,
    is_default BOOLEAN NOT NULL DEFAULT FALSE,
    sort_order INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
ALTER TABLE event_types ADD CONSTRAINT event_types_slug_format
    CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$');
ALTER TABLE event_types ADD CONSTRAINT event_types_default_enabled
    CHECK (NOT is_default OR enabled);
CREATE UNIQUE INDEX event_types_one_default ON event_types (is_default) WHERE is_default;

INSERT INTO event_types (slug, name, is_default, sort_order) VALUES
    ('workshop', 'Workshop', TRUE, 10), ('hack-night', 'Hack Night', FALSE, 20),
    ('talk', 'Talk', FALSE, 30), ('hackathon', 'Hackathon', FALSE, 40),
    ('social', 'Social', FALSE, 50);

CREATE FUNCTION event_types_default_id() RETURNS BIGINT LANGUAGE sql STABLE
    AS $$ SELECT id FROM event_types WHERE is_default $$;

ALTER TABLE workshops ADD COLUMN event_type_id BIGINT NOT NULL
    DEFAULT event_types_default_id()
    REFERENCES event_types(id) ON DELETE RESTRICT;
CREATE INDEX idx_workshops_event_type ON workshops (event_type_id);
```

Keep the function body free of semicolons, and add header comments in the style of `000020` explaining the default. `migrations/000045_create_event_types.down.sql` runs, in this order: `ALTER TABLE workshops DROP COLUMN event_type_id;`, `DROP FUNCTION event_types_default_id();`, `DROP TABLE event_types;`.

**Go**

  - Errors: `ErrNotFound`, `ErrInvalidSlug`, `ErrDuplicateSlug`, `ErrInUse`, `ErrIsDefault`, `ErrDisabled`.
  - `Update`: no pre-read. A 23514 on `event_types_default_enabled` maps to `ErrIsDefault`, so the check cannot race.
  - `SetDefault` must be **separate statements in one transaction**, in this order: (1) `SELECT id FROM event_types ORDER BY id FOR UPDATE`; (2) read the target, returning `ErrNotFound` or, when `enabled` is false, `ErrDisabled`; (3) `UPDATE ... SET is_default = FALSE WHERE is_default`; (4) `UPDATE ... SET is_default = TRUE WHERE id = $1`. A single-statement swap fails: measured, Postgres checks that index row by row and raises a duplicate key. The lock in step 1 is what stops two concurrent callers colliding, since each later statement gets a fresh snapshot.
  - `Delete`: in a transaction, `SELECT is_default ... WHERE id = $1 FOR UPDATE` (no row is `ErrNotFound`, true is `ErrIsDefault`), then `DELETE`. A 23503 on `workshops_event_type_id_fkey` maps to `ErrInUse`. `ON DELETE RESTRICT` is the guard, so `interests.Store.Delete`'s `NOT EXISTS` machinery, which exists because of a cascade, is not needed.
