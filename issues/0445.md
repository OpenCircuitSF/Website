## Description

`#0434`'s review found that `backup-media.sh` could prune away its only archive:
it skips writing when content is unchanged, then prunes by **age** every run, so
the retained archive keeps aging while nothing replaces it.

`backup.sh` carries the same prune code and the same stated invariant — "can
never prune away the only copy, today's dump has age 0" — and that invariant
holds **only because `backup.sh` writes every run**. This issue is to establish
whether that is actually true on every path.

**The specific question:** what happens across repeated runs where `pg_dump`
fails? If a failed run prunes before or independently of a successful write,
the same shape applies.

## Why this is much weaker than `#0434`'s case, and still worth checking

`#0434`'s instance was severe because the script **exits 0** on the skip path,
so `OnFailure=` never fires and the loss is silent for about two weeks.

Here, a failed `pg_dump` should mark the unit failed and `OnFailure=` **does**
fire, so an operator is told. That is the difference between a silent data loss
and a loud one, and it is why this is filed as a check rather than a defect.

What is identical is the downstream interaction: `pull-backups.sh` uses
`rsync -avz --delete-after`, so anything pruned locally is deleted **offsite on
the next pull** as well. A local prune is not recoverable from the copy that
exists precisely to recover it.

## Conclusion: no defect

> 🟢 Resolved 2026-09-05 — independently re-read the control flow and re-ran
> the failure sequence: `backup.sh`'s prune is unreachable on a run that does
> not publish a dump, so the check's no-defect conclusion stands and no code
> change is warranted.

`backup.sh`'s prune block cannot outlive its last dump. Unlike
`backup-media.sh`, `backup.sh` has no "unchanged, skip the write" branch that
still falls through to prune afterward — its per-database loop body has
exactly one path to the prune step, and that path passes through a successful
publish in the *same* iteration.

**The control-flow fact (`scripts/db/backup.sh`, per-database loop body):**

```
if [ "$rc" -ne 0 ] || [ ! -s "$tmp" ]; then
  echo "ERROR: ..." >&2
  rm -f "$tmp"
  failures=$((failures + 1))
  continue                    # <-- exits this database's loop iteration HERE
fi

chmod 0600 "$tmp"
mv -f "$tmp" "$final"                      # atomic publish — today's dump
ln -sfn "$base" "$dir/$db-latest.$ext"
echo "    ok — ..."

# Prune old dumps for THIS database only ...
pruned="$(find "$dir" ... -delete | wc -l ...)"
```

The `continue` on pg_dump failure (or an empty `$tmp`) jumps straight to the
next database in `${DATABASES[@]}`, never reaching the `find ... -delete`
prune below it. The prune block is therefore reached only by falling through
the `if`, which requires `mv -f "$tmp" "$final"` to have just run in this same
iteration — i.e., only immediately after a fresh write with age 0. There is no
separate "unchanged" branch (as `backup-media.sh` had before `#0434`'s fix)
that could reach prune without that write. A failed `pg_dump` for one database
also does not affect prune for a *different* database in the same run, since
`continue` only affects the current loop iteration and each database gets its
own `dir`/prune invocation.

The corollary this implies, and confirms below: a run where `pg_dump` fails
does not merely "safely" prune — it **does not prune at all**. Old dumps
accumulate through consecutive failures rather than being pruned by age, which
is conservative (never deletes the last copy) at the cost of eventually
exceeding the nominal retention window during an extended outage. That is an
availability/disk-usage tradeoff, not a data-loss defect, and it is exactly
the behavior `#0435`'s `OnFailure=` alerting exists to surface before it
matters.

## Verification — simulated failure sequence

Ran `scripts/db/backup.sh` for real (bash, not read-only) against a throwaway
root under the scratchpad, namespaced `0445`, with a fake `pg_dump` on `PATH`
(`BACKUP_RUN_AS=""` to skip sudo) so no real database or box was touched
(criterion 5):

1. **Run 1 (success):** wrote `testdb-<ts1>.dump`. Only file present, nothing
   to prune.
2. Manually aged that file's mtime to 30 days ago (`touch -t`), simulating it
   sitting well past a 14-day `BACKUP_RETENTION_DAYS`.
3. **Runs 2–4 (`FAKE_PG_DUMP_MODE=fail`, 3 consecutive nights):** each run
   exited 1 (`FAILED: 1 database(s) did not back up`). After all three, the
   30-day-old dump was **still present, untouched** — prune never ran on any
   of the three failing nights, confirmed by directory listing after each.
4. **Run 5 (success again):** wrote a fresh `testdb-<ts2>.dump` (age 0) and
   its output reported `pruned 1 dump(s) older than 14d` — the old dump was
   removed *only* in the same run that published a new one.

This is the direct, executed proof of the control-flow fact above: three
consecutive `pg_dump` failures left a dump 30 days past its 14-day retention
completely unpruned, and pruning resumed only once a fresh write succeeded in
that same run. Scratch directory removed after the run
(`rm -rf .../scratchpad/0445`), confirmed gone.

`bash -n scripts/db/backup.sh` — OK. `shellcheck scripts/db/backup.sh` — no
findings. No changes were made to `scripts/db/backup.sh`; both checks are
baseline confirmation that reading and testing it did not require or reveal
any fix.

## Review notes

> 🟢 Approved 2026-09-05 (review, Opus). Re-derived the control-flow fact from
> the script rather than from its invariant comment (criterion 1's explicit

> partial-failure case the implementer's report did not cover. No defect

**Control flow, read from `scripts/db/backup.sh` itself.** The whole file
contains exactly one deletion of a published dump — the `find … -mtime
+"$BACKUP_RETENTION_DAYS" -print -delete` at lines 194-195. It sits inside the
per-database `for` loop (line 155 … `done` at 197), *below* the atomic publish
`mv -f "$tmp" "$final"` at line 188. The failure branch at lines 180-185 ends in
`continue`, so a non-zero `rc` or an empty `$tmp` leaves the iteration before
line 188 is ever reached, and therefore before the prune. The only other
removal in the file is `rm -f "$tmp"` on line 182, which discards the failed
run's own temp file and touches no published dump. That makes the prune
reachable only by falling through the failure `if`, which requires the `mv` to
have run in the same iteration — the invariant comment on lines 192-193 is true
here for the reason it claims, unlike the copy `#0434` found in
`backup-media.sh`.

**Nothing outside the loop prunes.** Checked specifically, because a prune in a
cleanup handler would defeat the argument regardless of the loop body: the file
declares **no `trap` at all**, has no `EXIT` handler, and everything after
`done` (lines 199-204) is `echo` plus the `exit 1` on a non-zero `failures`
count. `find` appears nowhere else in the file. The single-database `continue`
on line 156 guards an empty name and returns before `$dir` is even computed.

**Failure sequence, re-run independently** (`bash`, not the zsh tool shell;
faked `pg_dump` on `PATH`, `BACKUP_RUN_AS=""`, throwaway root namespaced
`0445r`, removed afterwards). The implementer's harness shape had a trap worth
recording: `testdb-*.dump` also matches the `-latest` symlink, so a first

    dbA dir: dbA-20260905-094746Z.dump
    dbB dir: dbB-20260905-094745Z.dump

`dbA` prunes correctly alongside its own fresh write; `dbB` keeps its old dump
and its directory is untouched. `continue` affects only the current iteration,
and each database prunes its own `$dir` with a `-name "$db-*.$ext"` filter, so
one database's failure can neither suppress another's prune nor reach another's
files.

**The "loud, not silent" premise holds, verified rather than assumed.** The
partial-failure run exits `1` (`failures` is incremented per failed database and
checked after the loop), and `deploy/systemd/opencircuit-backup.service` carries
`OnFailure=opencircuit-backup-alert.service` on a `Type=oneshot` unit, so a
failed database marks the unit failed and the alert fires. This is the
difference from `#0434`, whose skip path exited `0`. The standing caveat is
`#0435`'s, not this issue's: the timer has never been installed, so nothing has
fired yet either way.

**`--delete-after` independence.** `pull-backups.sh` line 81 uses `rsync -avz
--delete-after`, so a local prune does propagate offsite on the next pull. The
no-defect conclusion does not lean on the offsite copy in any way: the argument
is that the local prune cannot run without a same-iteration local publish, so
there is never a moment at which the offsite mirror is the only surviving copy.
The mirror's behaviour is downstream of a local state that is already safe.
