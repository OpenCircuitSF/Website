## Description

`#0434`'s review found that `backup-media.sh` could prune away its only archive:
it skips writing when content is unchanged, then prunes by **age** every run, so
the retained archive keeps aging while nothing replaces it.

`backup.sh` carries the same prune code and the same stated invariant — "can
never prune away the only copy, today's dump has age 0" — and that invariant
holds **only because `backup.sh` writes every run**. This issue is to establish
whether that is actually true on every path.

**The specific question:** what happens across repeated runs where `pg_dump`
fails? If a failed run prunes before or independently of a successful write,
the same shape applies.

## Why this is much weaker than `#0434`'s case, and still worth checking

`#0434`'s instance was severe because the script **exits 0** on the skip path,
so `OnFailure=` never fires and the loss is silent for about two weeks.

Here, a failed `pg_dump` should mark the unit failed and `OnFailure=` **does**
fire, so an operator is told. That is the difference between a silent data loss
and a loud one, and it is why this is filed as a check rather than a defect.

What is identical is the downstream interaction: `pull-backups.sh` uses
`rsync -avz --delete-after`, so anything pruned locally is deleted **offsite on
the next pull** as well. A local prune is not recoverable from the copy that
exists precisely to recover it.

## Acceptance criteria

1. Determine whether `backup.sh` can reach its prune step on a run where no new
   dump was written. Read the control flow; do not infer it from the comment
   that states the invariant — that comment is what `#0434` copied into
   `backup-media.sh`, where it was false.
2. If it can, apply `#0434`'s remedy shape: exclude the current-target file from
   the prune, and make a missing target force a write. Use the file's own
   bash-3.2 `${keep_args[@]+"${keep_args[@]}"}` empty-array idiom under `set -u`.
3. If it cannot, **say why in the work log and close it** — a check that
   concludes "no defect" is a complete result here, provided the reasoning names
   the control-flow fact that makes it safe.
4. Either way, prove the conclusion by running the script against a throwaway
   directory across a simulated failure sequence, not by reading alone. Namespace
   scratch paths with the issue number and clean up (`CLAUDE.md` §8b — the
   scratchpad is not session-private in practice).
5. Do not touch `/var/backups`, `/var/www`, or anything on the box.
