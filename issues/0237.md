## Description

`#0226` restored the disclosure that some retained audit entries hold the
subscriber's email address, and scoped it correctly to the **subscriber-driven**
entries it examined. That scoping is now the problem: **five further call sites
write the subscriber's own address into `audit_log.metadata`, and all of them
survive erasure.**

Found by `#0226`'s phase-3 review, by grepping every `audit.Entry{` construction
rather than the subscriber-request handlers:

| Site | Event |
|---|---|
| `internal/handlers/admin_subscribers.go:837` | `SubscriberManualAdd` |
| `internal/handlers/admin_suppressions.go:274` | `SuppressionRemoved` |
| `internal/handlers/ses_notifications.go:443` | `SubscriberBounced` |
| `internal/handlers/ses_notifications.go:503` | `SubscriberBounced` |
| `internal/handlers/ses_notifications.go:561` | `SubscriberComplained` |

**Two distinct inaccuracies follow.**

1. **The enumeration is incomplete.** The page lists "(signup, confirmation, any
   unsubscribe or preference update, and the erasure itself)". A subscriber who
   ever bounced or complained, or who was added by an admin, has an audit row
   carrying their address that the page does not describe. Bounce and complaint
   are not edge cases — `#0038` and PRD §6.7 make them routine.

2. **"Each entry records the IP address of the request that made it" is not
   universally true.** The three SES-notification entries set no `IP` at all,
   because there is no user request behind them — the request is Amazon's.

Neither undoes `#0226`'s disclosure, which is why its review resolved rather
than bouncing a third time. But a privacy policy is a public commitment, and
this is the same class of defect: **the page describes a subset of what is
retained and reads as though it describes all of it.**

**A related correction, recorded so the record is straight:** `#0226`'s fix-pass
commit message claims it "verified against every `audit.Entry` call site". It
verified the five subscriber-driven ones. That is exactly the gap this issue
exists to close.

## Implementation notes

### Every `audit.Entry{` construction read directly, not the issue's table

`grep -rn "audit\.Entry{" internal/ cmd/` found **48 construction sites** (23
files). Read each one's `Metadata` field and its `IP` field by hand (not the
issue's table, which was independently reproduced):

- **Confirms the issue's five new sites, all writing `"email"`:**
  `internal/handlers/admin_subscribers.go:837` (`ActionSubscriberManualAdd`,
  `"email": email`, has `IP`), `internal/handlers/admin_suppressions.go:274`
  (`ActionSuppressionRemoved`, `"email": email`, has `IP`),
  `internal/handlers/ses_notifications.go:443` and `:503` (both
  `ActionSubscriberBounced`, `"email": recipient`, **no `IP` key present at
  all**), and `ses_notifications.go:561` (`ActionSubscriberComplained`,
  `"email": recipient`, **no `IP` key**).
- **Confirms the two sites #0226 already covered:** `confirm.go:154`
  (`ActionSubscriberConfirmed`, `"email": sub.Email`, has `IP`) and
  `admin_subscribers.go:970` (`ActionSubscriberErased`, `"email":
  result.Email`, has `IP` — the acting admin's, per the existing Consent
  section note).
- **One near-miss checked and excluded:**
  `internal/handlers/admin_campaign_preview.go:419`
  (`ActionEmailCampaignTestSent`) sets `"recipient_email": sub.Email`, but
  `sub` here is `h.ensureTestRecipient`'s synthetic per-admin test address
  (`testRecipientEmail`: `campaign-test+admin-<id>@<reserved test
  domain>`), never a real subscriber's PII — out of scope for a page about
  subscriber data.
- **All other 41 sites** (auth ceremonies, credentials, settings,
  interests, workshops, campaigns, mailing worker, SES topic-level
  confirmations) carry no `"email"` key in `Metadata` — checked directly,
  not assumed.

Total: **seven** real audit.Entry sites that write a subscriber's own email
address, all surviving erasure (nothing in `internal/subscribers/erase.go`
touches `audit_log`). The issue's table (five) plus #0226's original two
(confirm, erasure) account for exactly these seven — the issue's table was
accurate and complete.

### The Svelte wording

Rewrote the "How to leave" audit-log `StatusList` item in
`web/src/views/PrivacyPolicy.svelte` to name all three ORIGIN categories a
row can come from (subscriber-driven, admin-initiated, automated from the
delivery provider) instead of enumerating only the subscriber-driven ones,
list all six actions that record the email explicitly (confirmation, manual
add, suppression removal, bounce, complaint, erasure), and state the IP
rule correctly: per-request IP for subscriber- and admin-initiated entries
(the acting admin's for admin-initiated ones, including erasure), and **no
IP at all** for the automated SES-driven entries, since there is no user
request behind an SES notification.

### The durable guard (criterion 3)

`internal/handlers/audit_email_metadata_guard_test.go` is new. It walks
every production `.go` file (test files excluded — a fixture never becomes
a real inserted row) under `internal/` and `cmd/`, finds every
`audit.Entry{...}` composite literal via `go/ast`, and classifies its
`Metadata` field:

- an inline `map[string]any{...}` literal — read its keys directly;
- a bare identifier — traced through the ENCLOSING function's own
  assignments, including a conditional `x["email"] = ...` index assignment
  anywhere in the function body (the exact shape
  `admin_suppressions.go:274` and `admin_subscribers.go:694` use);
- a call to the one verified known-safe helper, `credentialMetadata`
  (device name + AAGUID for a WebAuthn credential, never PII) — resolved by
  reading that helper's own `return` statement, not trusted by name;
- anything else — reported as **unresolved**, which fails the guard. This
  is the conservative default: a Metadata expression this guard cannot
  prove either way is treated as a possible email carrier, not silently
  passed.

The result is compared against a pinned `auditEmailMetadataKnownSites`
list (file, action, count, IP-presence) for exactly the seven sites found
above. Adding an eighth site, removing one of the seven, or changing one's
count or IP-presence all fail the guard by name. This is what makes
criterion 3 hold for a genuinely new future call site, not just the five
this issue happens to know about today.

### The `PrivacyPolicy.guard.test.ts` side, and one collision found while writing it

Widened the `audit_log` category's `requiredPhrases`/`sourceRef` to match
the new wording, and added two new mutation-proof tests (categories-drop,
IP-claim-drop) reproduced against the REAL current item text via
`realItems()`, not a hand-written fixture.

While doing this, the "passes against the real, current four items" test
regressed from 4/4 to 3/4: the new audit-log wording's "a suppression
removal" phrase collided with the **existing** `suppression` category's
requiredPhrases, which was just the bare word `'suppression'`.
`matchItemToCategory` checks categories in array order and returns the
FIRST fully-satisfied one per item, so the audit-log item was being
wrongly claimed by the `suppression` category before ever reaching
`audit_log`. Fixed by strengthening `suppression`'s requiredPhrases to
`'permanent suppression entry'` (unique to that item's actual wording) —
the same "too weak a phrase" failure mode the file's own comments already
document for `email_events`, just not yet hardened for `suppression`.

## Notes

Reported by `#0226`'s phase-3 review under `CLAUDE.md` §9.

The durable fix is criterion 3. `#0226` proved a guard can pin this page against
drift; the guard's `requiredPhrases` simply did not know about these five sites.
A guard keyed to the *set of call sites that write an email* rather than to
phrases would not have this failure mode — that is the version worth building,
and it is the same lesson `#0113` recorded about prose that should have been a
guard.

Note this is the second time the policy has been wrong in the direction of
under-disclosure (`#0060`'s review bounced it for promising more deletion than
performed; `#0226` for deleting a disclosure outright). The page is
load-bearing and keeps being edited by passes whose subject is something else.
