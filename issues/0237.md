# 0237 — The privacy policy's audit-log enumeration is narrower than reality

|---|---|
| **Status** | open |
| **Platform** | Web |
| **Module** | web / compliance |
| **Phase** | 7 — Inbound and polish |

## Description

`#0226` restored the disclosure that some retained audit entries hold the
subscriber's email address, and scoped it correctly to the **subscriber-driven**
entries it examined. That scoping is now the problem: **five further call sites
write the subscriber's own address into `audit_log.metadata`, and all of them
survive erasure.**

Found by `#0226`'s phase-3 review, by grepping every `audit.Entry{` construction
rather than the subscriber-request handlers:

| Site | Event |
|---|---|
| `internal/handlers/admin_subscribers.go:837` | `SubscriberManualAdd` |
| `internal/handlers/admin_suppressions.go:274` | `SuppressionRemoved` |
| `internal/handlers/ses_notifications.go:443` | `SubscriberBounced` |
| `internal/handlers/ses_notifications.go:503` | `SubscriberBounced` |
| `internal/handlers/ses_notifications.go:561` | `SubscriberComplained` |

**Two distinct inaccuracies follow.**

1. **The enumeration is incomplete.** The page lists "(signup, confirmation, any
   unsubscribe or preference update, and the erasure itself)". A subscriber who
   ever bounced or complained, or who was added by an admin, has an audit row
   carrying their address that the page does not describe. Bounce and complaint
   are not edge cases — `#0038` and PRD §6.7 make them routine.

2. **"Each entry records the IP address of the request that made it" is not
   universally true.** The three SES-notification entries set no `IP` at all,
   because there is no user request behind them — the request is Amazon's.

Neither undoes `#0226`'s disclosure, which is why its review resolved rather
than bouncing a third time. But a privacy policy is a public commitment, and
this is the same class of defect: **the page describes a subset of what is
retained and reads as though it describes all of it.**

**A related correction, recorded so the record is straight:** `#0226`'s fix-pass
commit message claims it "verified against every `audit.Entry` call site". It
verified the five subscriber-driven ones. That is exactly the gap this issue
exists to close.

## Acceptance criteria

- [ ] The policy's audit-log description covers every entry that retains the subscriber's address, including admin-initiated and SES-driven ones — or states the rule generally rather than enumerating, if enumeration cannot be kept accurate
- [ ] The IP claim is true as written: entries created without a user request do not carry one, and the page must not imply otherwise
- [ ] `#0226`'s guard is extended so **adding a new `audit.Entry` that records an email would fail it** — the enumeration going stale again is the predictable failure, and prose cannot prevent it
- [ ] That extension is mutation-proved against the real `PrivacyPolicy.svelte`, not a fixture — copy aside, mutate, confirm the named failure, restore, prove byte-identity with `shasum -a 256`
- [ ] The wording is verified by reading every `audit.Entry{` construction in `internal/` and `cmd/`, and `## Verification` says so explicitly
- [ ] `scripts/check.sh web` and `ISSUE=0237 scripts/check.sh go ./internal/...` both pass

## Notes

Reported by `#0226`'s phase-3 review under `CLAUDE.md` §9.

The durable fix is criterion 3. `#0226` proved a guard can pin this page against
drift; the guard's `requiredPhrases` simply did not know about these five sites.
A guard keyed to the *set of call sites that write an email* rather than to
phrases would not have this failure mode — that is the version worth building,
and it is the same lesson `#0113` recorded about prose that should have been a
guard.

Note this is the second time the policy has been wrong in the direction of
under-disclosure (`#0060`'s review bounced it for promising more deletion than
performed; `#0226` for deleting a disclosure outright). The page is
load-bearing and keeps being edited by passes whose subject is something else.
