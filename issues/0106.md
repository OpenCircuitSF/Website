## Description

`#0102` fixed one vacuous assertion in `internal/sesnotify/verify_test.go`.
Reviewing that fix surfaced four more tests in the same package with the same
defect: each is named for a specific guard, but asserts only `err == nil` →
fail, and a *different* mechanism produces an error for the same input. Delete
the guard the test is named for and the test stays green. One of them is
confirmed by mutation; the rest are confirmed by construction.

## Root cause

Same shape in all four cases: the assertion was `err == nil` → fail, which is
satisfied by *any* non-nil error, not specifically the one the guard named in
the test's name would produce. A different check downstream of the named
guard (or, in one case, a completely unrelated encoding failure) produced a
non-nil error for the same crafted input, so deleting the named guard left the
test green.

- `TestFetchCertReal_NonOKStatusIsError` — the 404 response body was empty, so
  with the status check gone the fetch proceeded to `pem.Decode`, found no PEM
  block, and errored anyway (confirmed by mutation in the issue itself).
- `TestVerify_TamperedTopicArn` — the tampered `TopicArn` (`…:attacker-topic`)
  was already outside the configured allowlist, so the allowlist equality
  check (`m.TopicArn != v.topicARN`) rejects it even with the signature check
  gone.
- `TestVerify_UnsupportedSignatureVersion` — `SignatureVersion` is **not**
  part of `canonicalString` (confirmed by reading `message.go`), so relabeling
  it after signing doesn't touch the signature. But removing the `default:`
  arm of the version switch leaves `hash`/`digest` at their zero values, and
  `rsa.VerifyPKCS1v15` then fails on its own for an unrelated reason
  (`crypto/rsa: verification error`) — confirmed by mutation below.
- `TestVerify_EmptyConfiguredTopicArnRejectsEverything` — the message is
  otherwise fully valid (genuine signature, `TopicArn` already equal to the
  value the Verifier *would* accept if configured), and `Verify` fetches the
  certificate unconditionally **before** the `topicARN == ""` check runs (not
  after, as the guard's own name implies — confirmed empirically: the fake
  fetcher's `calls` counter is `1`, not `0`, under the real, unmutated code).
  So with the explicit empty-topicARN guard removed, the general
  `m.TopicArn != v.topicARN` mismatch check just below it still fires — a
  real ARN is never equal to `""` — producing a different error message
  ("does not match the configured topic" instead of "no topic ARN
  configured"). The `calls` counter the test already declared cannot
  distinguish the two cases at all, since the fetch happens either way; a
  `calls == 0` assertion (as the issue's Notes originally suggested) would
  therefore be evidence-free here and was not used.

## Fix

`internal/sesnotify/verify_test.go` only; `verify.go` is untouched (confirmed
below by `git diff` after each mutation-and-restore cycle).

- **`TestFetchCertReal_NonOKStatusIsError`** — the 404 handler now writes a
  genuine PEM (the same `testFixture` cert the other `fetchCertReal` tests
  use) instead of an empty body, so `pem.Decode` can no longer be what rejects
  the response. Added an assertion that the error text names status `404`.
- **`TestVerify_TamperedTopicArn`** — the message is now signed under a
  `TopicArn` *outside* the allowlist (`…:some-other-topic`), then tampered
  *after* signing to the one value that *is* allowlisted
  (`…:opencircuit-ses-events`). That keeps the post-tamper `TopicArn` inside
  the allowlist, so the allowlist check alone can no longer catch the tamper —
  only the fact that `TopicArn` is covered by `canonicalString` (and so the
  swap invalidates the signature) can. Asserts the error text contains
  `"signature verification failed"`.
- **`TestVerify_UnsupportedSignatureVersion`** — asserts the error text
  contains the specific message `unsupported SignatureVersion "3"`, which only
  the version-switch `default:` arm produces.
- **`TestVerify_EmptyConfiguredTopicArnRejectsEverything`** — asserts the
  error text contains `"no topic ARN configured"`, the string unique to the
  explicit `topicARN == ""` guard (as opposed to `"does not match the
  configured topic"`, which the general mismatch check produces instead if
  the named guard is removed). Also asserts `calls == 1` — not as a
  guard-detection mechanism (see Root cause: it cannot distinguish the two
  cases), but as a sanity check that the fetch still happens exactly once,
  matching the actual, documented call order.

## Steps to reproduce

Confirmed case — `TestFetchCertReal_NonOKStatusIsError` (`verify_test.go:359`),
the direct sibling of the test `#0102` repaired, in the same function:

1. Delete the `resp.StatusCode != http.StatusOK` check from `fetchCertReal`
   (`internal/sesnotify/verify.go`).
2. `go test ./internal/sesnotify/... -run TestFetchCertReal_NonOKStatusIsError -count=1`
3. **The test still passes.** Its server answers `404` with an *empty* body, so
   with the status check gone the fetch runs on to `pem.Decode`, finds no PEM
   block, and returns a non-nil error anyway — exactly the failure mode
   `#0102` documented.

## Expected behavior

Removing the guard a test is named for fails that test.

## Actual behavior

The four below all survive removal of their nominal guard.

| Test | Line | Guard it names | What else errors for the same input |
|---|---|---|---|
| `TestFetchCertReal_NonOKStatusIsError` | 359 | the `resp.StatusCode != 200` check | `pem.Decode` on the empty 404 body — **confirmed by mutation** |
| `TestVerify_TamperedTopicArn` | 169 | signature integrity over `TopicArn` | the tampered value (`…:attacker-topic`) is *also* outside the configured allowlist (`…:opencircuit-ses-events`), so the topic-ARN check rejects it with the signature check gone |
| `TestVerify_UnsupportedSignatureVersion` | 143 | the `SignatureVersion` allowlist | the message is signed as `"2"` and relabeled `"3"`; drop the version check and the signature verification fails on the version mismatch instead |
| `TestVerify_EmptyConfiguredTopicArnRejectsEverything` | 210 | "an unconfigured topic rejects everything, before any fetch" | plain ARN inequality (a real ARN `!= ""`) rejects it regardless. It also declares a `calls` counter, increments it in the fake fetcher, and then **never asserts on it** — the intended "the fetcher was never invoked" assertion is missing |

   test is named for.

   in `Verify` (the signature-integrity guard this test is named for),
   replacing it with a no-op that discards `pub`/`hash`/`digest`/`sig`.
   Result: **FAIL** — `expected error for tampered TopicArn, got nil`. With
   signature checking gone and the tampered `TopicArn` inside the allowlist,
   `Verify` now returns `nil` — the whole message passes.
4. **`TestVerify_EmptyConfiguredTopicArnRejectsEverything`** — deleted the
   `if v.topicARN == "" { ... }` block from `Verify`. Result: **FAIL** —


## Gotchas

- The issue's own `## Actual behavior` table and `## Notes` describe
  `TestVerify_EmptyConfiguredTopicArnRejectsEverything`'s guard as running
  "before any fetch" and suggest a `calls == 0` idiom. Neither holds: `Verify`
  fetches the certificate unconditionally before the `topicARN == ""` check
  ever runs, in both the guard-present and guard-removed cases, so `calls` is
  `1` either way and cannot serve as the discriminating assertion. Verified
  empirically (via a temporary `t.Logf`, since removed) before writing the
  fix — see Root cause.

## Notes

`TestVerify_HostileSigningCertURL` in the same file is the model to copy: it
asserts both that `Verify` errored *and* that `calls == 0`, which is what makes
it prove the guard ran rather than merely that something downstream failed.
`#0102`'s fix applies the same idiom.

Suggested repairs, cheapest first:

- `TestFetchCertReal_NonOKStatusIsError` — have the 404 handler write a valid
  PEM body (the `testFixture` cert, as `TestFetchCertReal_FetchesAndParses` and
  now `TestFetchCertReal_RefusesRedirect` both do), so the only thing that can
  reject it is the status check. Optionally assert the error text names `404`.
- `TestVerify_TamperedTopicArn` — tamper to a value that is still *inside* the
  allowlist so only the signature check can catch it, or assert the error is
  the signature error rather than the allowlist error.
- `TestVerify_UnsupportedSignatureVersion` — assert the error identifies the
  unsupported version, or use a message whose signature would otherwise verify.
- `TestVerify_EmptyConfiguredTopicArnRejectsEverything` — add the missing
  `if calls != 0` assertion the existing counter was clearly written for.

Not fixed under `#0102`, which was deliberately scoped to the single test it
named. Worth doing before `#0038` expands this package: these tests are the
regression net that expansion will lean on.
