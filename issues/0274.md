## Description

The live CRT on the home page (`#0270`) runs an eight-command session of
**illustrative** copy. Now that the site is up and real workshops are listed,
the screen should show the actual ones — and a line reporting how many mailing
list addresses are confirmed and how many are pending.

Both feeds are public REST APIs anyone may call, because neither exposes PII.

**`GET /api/workshops` already exists and is public** (`#0051`), returning
upcoming workshops in chronological order. The CRT needs no new endpoint for
that half — only to call it.

**The counts need a new endpoint.** Something like `GET /api/list-stats`
returning aggregate totals only:

```json
{ "confirmed": 42, "pending": 7 }
```

## This reverses `#0233`'s recorded decision, deliberately

`#0233` decided the screen stays illustrative, on three grounds. Two no longer
hold and one now has to be paid:

1. *"It duplicates the Next up section directly below."* — still true, and now
   acceptable: the user wants the real schedule on the screen, and a terminal
   showing live data is the point of the effect rather than a redundancy.
2. *"It makes a decorative element depend on a network call."* — the mitigation
   is that it must **degrade to the illustrative copy**, not to an empty screen
   or an error. The session already exists as a fallback; use it.
3. *"It changes the accessibility answer."* — **this one is real and must be
   paid.** The stage is `aria-hidden` precisely because the content repeats what
   the headline says. Real workshop dates and live counts are *information*, and
   hiding information from a screen reader is wrong.

**The accessibility resolution is the substance of this issue, not a footnote.**
The workshops are already announced by the "Next up" section below the hero, so
the screen's workshop lines remain a visual restatement — `aria-hidden` still
holds for those. The **counts are new information appearing nowhere else**, so
they need a text equivalent, or they must be treated as decorative flavour and
not as a fact anyone is expected to read.

## The oracle question — decide before shipping

`CLAUDE.md` §9 forbids weakening `POST /api/subscribe`'s uniform `202`, which
exists so the endpoint cannot be used to test whether an address is already on
the list.

**A live, exact `pending` count reintroduces a narrow version of that.** Submit
an address, poll the count: if `pending` rises, the address was new; if it does
not, it was already known. The signal is noisy on a busy list and useless on a
quiet one — but this list is currently quiet, which is the worst case.

Mitigations, in order of preference:

- **Cache the response** with a TTL long enough that a submit-then-poll cannot
  attribute a change (60s is ample, and it also protects the database).
- **Round or bucket** the counts (`"about 40"`, or nearest 5). The screen does
  not need single-address precision.
- Serve `confirmed` only, and drop `pending` entirely.

Whatever is chosen, **record why** — this is the second time this project has
had to reason about that oracle, and the first (`#0088`) cost real work.

## Acceptance criteria

- [ ] `GET /api/list-stats` returns aggregate counts only — no addresses, no ids, no timestamps that could identify a signup
- [ ] The oracle mitigation is implemented and its reasoning recorded; a submit-then-poll cannot attribute a count change to one address
- [ ] The endpoint is cached and cheap — the CRT polls it, and it must not become a per-visitor database query
- [ ] The CRT shows real workshops from `GET /api/workshops`, formatted to the screen's ~36-character line width
- [ ] **It degrades to the illustrative session** when either fetch fails or returns nothing — never a blank screen, never an error string
- [ ] With JavaScript off, the hero still shows the photograph alone, as `#0270` established
- [ ] The accessibility question is resolved explicitly per the section above, not left implicit
- [ ] A workshop with a long title does not overflow the glass — proved by rendering, not reasoning
- [ ] `ISSUE=0274 scripts/check.sh` and `scripts/check.sh web` both pass

## Notes

Filed and started on the user's instruction, 2026-08-25.

**Do not fetch on every visit if it can be avoided cheaply.** The screen already
pauses when hidden and when scrolled out of view (`#0270`); the fetches should
be similarly lazy — one fetch on first paint, not a poll loop, unless the counts
are meant to tick live.
