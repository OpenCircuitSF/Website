## Description

`godotenv` strips a backslash escape; systemd's `EnvironmentFile=` keeps it.

    PRICE=cost\$FOO

loads as `cost$FOO` under godotenv and stays `cost\$FOO` under systemd. The
value-shape scan built by `#0441` and widened by `#0450` and `#0453` does not
flag it.

**This is the largest remaining hole in that scan, and it was measured, not
guessed.** `#0453`'s reviewer brute-forced **111,110** generated values through
both readings: the guard flagged 14,637 with **zero false positives**, and of
the values that genuinely diverge and go unflagged, **3,024 all contain a
backslash — and none of the unflagged divergences lack one.** The backslash is
the whole remaining family.

This is **distinct from the trailing-backslash continuation shape** the scan
already covers: that one is about a line ending in `\`, this one about a
backslash escaping a character mid-value.

## Why it matters

`.env.example` is copied verbatim onto production as
`/etc/opencircuit/config.env` (`#0423`), so both parsers read the same bytes. A
value that silently loses a character under one and keeps it under the other is
the **silently-wrong-value** half of this bug class — the service starts, and
something downstream is subtly wrong. That is harder to notice than a boot
failure, which is the half `#0429` already fixed.

`.env.example` holds zero `$` and zero `\` bytes today, so nothing is currently
wrong; this is about the next line someone writes.

## Root cause

Read from `godotenv` v1.5.1's `parser.go` (module located with
`go list -m -f '{{.Dir}}' github.com/joho/godotenv`, never a filesystem scan)
and confirmed by probing `godotenv.Unmarshal` directly in a throwaway module:
`expandVariables` branches on `submatch[1] == "\\" || submatch[2] == "("` —
group 1 is `expandVarRegex`'s optional leading backslash. Whenever it is
present, the function strips exactly that one backslash and returns the rest
of the match completely unchanged: no substitution happens even when a valid
variable name follows, and this fires even for a bare backslash-dollar with
nothing after it, since every group after the dollar is independently
optional. systemd's `EnvironmentFile=` has no backslash-escaping at all and
keeps the backslash byte-for-byte, so any occurrence of a backslash
immediately before a dollar sign in an unquoted value diverges, regardless of
what follows.

A secondary finding, not a defect in the pre-existing scan but worth
recording: the pre-#0457 pattern already matched some backslash-preceded
dollar signs that had a valid variable name after them (its regex is
unanchored on what precedes the `$`), so those particular values were already
flagged — but with the wrong diagnosis, describing the divergence as
godotenv "expanding" the value when it actually strips the backslash and
substitutes nothing. The measured 111,110-value corpus's "false positive"
count stayed zero throughout (the divergence itself was real), but the stated
mechanism was wrong. The fix reclassifies every backslash-prefixed match into
its own branch and message, correcting this alongside closing the previously
fully-unflagged no-name case.

Probed directly against the real v1.5.1 dependency:

    value          godotenv loads  diverges?
    cost\$FOO      cost$FOO        yes (backslash stripped; FOO left
                                   literal, NOT substituted)
    cost\${FOO}    cost${FOO}      yes (brace form, same strip-only result)
    cost\$(FOO)    cost$(FOO)      yes (the backslash SUPPRESSES `#0453`'s
                                   $(...) misparse bug — submatch[1] is
                                   checked before submatch[2], so this
                                   strips and stops rather than also
                                   misparsing)
    cost\$5        cost$5          yes (digit-led name, same as #0450)
    cost\$         cost$           yes (bare backslash-dollar, no name at
                                   all, still diverges)
    cost\n         cost\n          no  (backslash not immediately before a
                                   dollar sign; expandVarRegex requires a
                                   literal "$" right after its optional
                                   backslash, so this never matches)
    cost\\$FOO     cost\$FOO       yes (only the backslash directly
                                   adjacent to the dollar sign is consumed;
                                   an earlier, non-adjacent backslash is
                                   untouched, but the pair still diverges
                                   and is still caught)

## Fix

Widened `envDollarExpansion` from `` \$\(?\{?[A-Z0-9_]+\}? `` to
`` \\\$|\$\(?\{?[A-Z0-9_]+\}? `` — an alternation admitting a leading
backslash, not a fifth shape and not a second pattern (criterion 3: extension,
matching `#0453`'s precedent for the same reason: a fifth shape means a fifth
branch and a fifth table row, which criterion 4 protects). The
backslash-prefixed alternative does not require a variable name to follow,
unlike the existing non-backslash alternative, because the library's strip
behavior is unconditional on that group while the plain-`$` case genuinely
does not diverge without a name (`#0450`'s review).

The existing dollar-expansion violation site (already a two-way branch, added
by `#0453` for the `$(...)` form) became a three-way `switch`, still inside
the same single `if match := envDollarExpansion.FindString(value); match !=
"" { ... }` guard — no new mechanism, per criterion 6. The new case is checked
first (it tests whether the matched text starts with a backslash), giving it
precedence over the `$(...)` case for the (rare, but real) case where a value
has both a leading backslash and a paren, since the backslash is what
actually determines
`godotenv`'s behavior there. The new message names `godotenv`'s strip
behavior, names systemd's byte-for-byte behavior, and explicitly says this is
NOT the trailing-backslash line-continuation shape (criterion 3) — that one is
about a backslash at the end of the value with no dollar sign involved, and it
is systemd, not godotenv, doing something unusual there.

`.env.example` holds zero `$` and zero `\` bytes (confirmed by reading it as
bytes with `python3`), so no change to that file was needed or made.

### The defect that bounces it

The `#0457` paragraph of `envDollarExpansion`'s doc comment opens by saying
the widening works by "admitting an optional leading backslash" and names the
fragment for it inline. **That fragment is not what shipped, and it is not
equivalent to what shipped.** The code uses an alternation whose
backslash-and-dollar branch requires no variable name after it; the named
fragment would instead prefix an optional backslash onto the existing branch,
which still requires a name.

This is not a wording preference. I measured it: spliced into the pattern as
the comment describes it, that fragment flags **14,637** of the corpus with
**3,024 misses** — byte-for-byte the pre-`#0457` numbers. The comment names
the one fragment that would leave every value this issue exists to catch
unflagged, including the bare backslash-dollar blind spot in the issue's own
title case.

Two things make it worth a pass rather than a footnote. First, this lineage's
documented failure mode is precisely a claim about a regex believed instead of
measured — `#0441`'s inverted table row and `#0453`'s group-numbering bug are
both that, and criterion 2 exists because of them. Second, the guard is
**dormant against the real file** (`.env.example` holds zero `$` and zero
backslash bytes) and `#0458`'s regression pins do not exist yet, so this
comment is currently the main thing standing between the pattern and a
well-meaning future "simplification" back to the fragment it names — one that
would reopen the bug with every test still green.

The rest of the paragraph is right and should stay: it goes on to describe
"the plain (non-backslash) alternative, which still does" require a name,
which is a correct description of an alternation and contradicts the fragment
named three lines above it.

### Remedy — required

Rewrite the opening of that paragraph so the fragment it names is the one that
shipped. Replace the clause about admitting an optional leading backslash, and
the fragment beside it, with wording that says the widening adds a **second
alternative** matching a backslash immediately followed by a dollar sign —
naming that two-token alternative, not an optional-backslash prefix — and add
one clause recording *why* the prefix form was rejected: it would still
require a variable name to follow, so it would miss the bare
backslash-dollar case entirely and reproduce the pre-`#0457` counts exactly.
Keep everything from "still the …" onward unchanged, keep the paragraph's
existing tab-indented blocks untouched, and do not alter the pattern itself —
the shipped pattern is correct and is not in question.

### Remedy — also fix while you are in there

The new violation message says godotenv leaves "the dollar sign and anything
after it as literal text with NO substitution". That is true of the matched
construct but over-broad for a value carrying a *second* dollar construct
later on: measured over the corpus, the claim holds exactly for 4,067 of the
4,194 values routed to this branch, and the other 127 have a later `$NAME`
that godotenv still expands. Narrow the claim to the matched construct — say
the backslash and the dollar sign it precedes are left as literal text with no
substitution *for that occurrence* — rather than implying it about the whole
value. The remedy sentence ("remove the backslash") stays correct either way,
and the line still diverges and is still flagged, so this is precision, not a
behaviour change. No test change is needed for either remedy.
