# 0620 — The test schema census retires a column for a drop that never ran at the top level

| | |
|---|---|

## Description

`#0618` taught `internal/testdb/schema_check.go` to accept a plain single-column
`DROP COLUMN`, because `000047` is the first migration to drop one. Its review found
that `parseDroppedColumns` splits on `;` naively, so five shapes wrongly retire a
column that still exists: a drop inside a `DO` block, a function body, a block
comment or a string literal, and a drop then re-add in one file. The old guard refused
the first four. Severity is low: no migration has these shapes, and the census runs
only in tests.

## Acceptance criteria

- [ ] `parseDroppedColumns` retires a column only for a real top-level statement. When
      splitting, it skips dollar-quoted bodies, block comments and string literals, so a
      drop inside one of those is refused.
- [ ] A file's statements apply in order, so a drop and re-add leaves the column expected.
- [ ] The `assertNoDestructiveDDL` error no longer says migrations never drop a column.
- [ ] `TestExpectedObjectsFromFiles_RefusesDropTableAndRename` covers all five shapes.

## Relation

- Follow-up to `#0618`, from its review.

## Plan

Written 2026-11-05 against the tree at `adbdbc50`. No code yet.

**Decisions this plan makes**

- **One quote-aware splitter, used only where the drop census needs it.** A new
  `splitStatements` replaces the naive split in `parseDroppedColumns` and drives the
  new in-order loop in `expectedObjectsFromFiles`. `parseAlterTableAddColumns` and
  `parseCreateTables` keep their code; they are now just called on one statement at a
  time. That keeps the column set the census expects from the real `migrations/`
  identical (measured below), so this change cannot quietly stop checking an
  `ADD COLUMN` it checks today.
- **A quoted body or comment stays inside its statement.** A `DO` block, a function
  body, a block comment or a string literal is never split, so a drop inside one
  lands in a statement that does not start with `ALTER TABLE` and cannot match the
  anchored `dropColumnStmtPattern`. It stays in `rest`, and `destructiveDDLPattern`
  refuses it, as the guard did before `#0618`. A block comment in front of a real
  plain drop is refused too. That fails closed, which is acceptable; no migration
  does it.
- **No error for an unterminated quote or comment.** The splitter treats the rest of
  the file as one statement. That statement cannot match the anchored pattern, so a
  drop in it is refused. Postgres would reject such a file anyway.

**Approach, `internal/testdb/schema_check.go`**

1. **`splitStatements(body string) []string`**, placed just above
   `parseDroppedColumns`, with a doc comment naming what it skips. One pass over the
   bytes with an index `i` and a `start` offset. Outside any quoted region:
   - `;` ends a statement: append `body[start:i]`, set `start = i+1`.
   - `'` starts a string literal. If the byte before it is `E` or `e` and the byte
     before that is not an identifier byte (`[A-Za-z0-9_$]`), it is an escape
     string: inside it, `\` skips the next byte. In every string, `''` is an escaped
     quote (skip both); a single `'` closes it.
   - `"` starts a quoted identifier; `""` is an escaped quote; a single `"` closes it.
   - `/*` starts a block comment. Track depth, since Postgres nests them: `/*` adds
     one, `*/` takes one away, and the comment ends at depth zero.
   - `--` skips to the next newline. `loadMigrationFiles` already strips these; this
     is only so the function is correct on its own.
   - `$` starts a dollar quote only when the byte before it is not an identifier byte
     and what follows matches `^\$([A-Za-z_][A-Za-z0-9_]*)?\$`. The tag cannot start
     with a digit, so `$1` is not an opener. The body ends at the next exact copy of
     the opening delimiter (`strings.Index` from after the opener). Inner `$$` inside
     a `$fn$` body is therefore ignored.
   - If any region is never closed, stop scanning.

   After the loop, append `body[start:]`. Return the slice with the quoted text left
   in place, since `rest` still has to contain it for `destructiveDDLPattern`.

2. **`parseDroppedColumns`**: replace `strings.Split(body, ";")` with
   `splitStatements(body)`. Nothing else in it changes, and `rest` is still
   `strings.Join(kept, ";")`. Update its doc comment to say that only a whole
   top-level statement counts, and that a drop inside a dollar-quoted body, block
   comment or string literal stays in `rest` and is refused.

3. **`expectedObjectsFromFiles`**: keep `assertNoDestructiveDDL(f)` first. Replace
   the per-file block (parse creates, parse adds, then apply drops) with one loop over
   `splitStatements(f.body)`, in order:
   - If `dropColumnStmtPattern.FindStringSubmatch(stmt)` matches, retire that column
     exactly as the current drop loop does: `delete(seenColumn, key)` and
     `slices.DeleteFunc(columns, …)`.
   - Otherwise run `parseCreateTables(f.name, stmt)`, returning its error, and
     `parseAlterTableAddColumns(f.name, stmt)`, and merge tables and columns through
     the existing `seenTable` and `seenColumn` maps unchanged.

   A drop then a re-add in one file now leaves the column expected, owned by that
   file. An add then a drop leaves it retired. Put the drop-match test in a small
   helper, `matchDropColumn(stmt) (expectedColumn, bool)`, used by both
   `parseDroppedColumns` and this loop, so the two cannot disagree. Update the doc
   comment: "A column a later statement drops is no longer expected, and one added
   again after that is."

4. **The `assertNoDestructiveDDL` error**, worded so it no longer says migrations
   never drop a column, and still citing no issue number:

   ```go
   return fmt.Errorf("testdb: %s contains %q — the cumulative schema census can "+
       "account for one destructive shape only, a top-level statement that drops "+
       "one column with ALTER TABLE <table> DROP COLUMN <column> and nothing else. "+
       "Any other drop, any rename, or a drop inside a DO block, function body, "+
       "comment or string literal would leave it expecting an object that is gone, "+
       "so the census needs extending before it can be trusted", f.name, loc)
   ```

   Also update the doc comments on `destructiveDDLPattern` and
   `assertNoDestructiveDDL` to match.

5. **Measure that the real `migrations/` gives the same census.** Before editing,
   add a throwaway `internal/testdb/zz_census_dump_0620_test.go`. It calls
   `migrationsDir()`, `loadMigrationFiles`, and `expectedObjectsFromFiles(files, 1<<30)`;
   sorts `table`, `table.column file` lines; prints their count and SHA-256 with
   `t.Log`. Run it with `go test ./internal/testdb/ -run Dump0620 -v` and record the
   output. Run it again after the change: both values must match, then **delete the
   file**. Put the two hashes in `## Verification`. It needs no database. The real
   tree has dollar bodies only in `000007`, `000045` and `000047`, all DDL sits
   outside them, and the only drop is `000047`'s plain `is_default` one, so equal
   hashes are expected.

**Tests, `internal/testdb/schema_check_test.go`**

- `TestExpectedObjectsFromFiles_RefusesDropTableAndRename`: keep the five cases and
  their `err == nil` assertion. Add these to the table, each refused:
  - `"drop inside a DO block"`:
    `DO $$ BEGIN IF false THEN ALTER TABLE widgets DROP COLUMN color; END IF; END $$;`
  - `"drop inside a function body"`:
    `CREATE FUNCTION f() RETURNS void LANGUAGE plpgsql AS $fn$ BEGIN ALTER TABLE widgets DROP COLUMN color; END $fn$;`
  - `"drop inside a block comment"`:
    `/* ALTER TABLE widgets DROP COLUMN color; */ SELECT 1;`
  - `"drop inside a string literal"`, which also covers the escaped quote:
    `SELECT 'it''s; ALTER TABLE widgets DROP COLUMN color; ok';`
  - `"drop inside an escape string"`:
    `SELECT E'\'; ALTER TABLE widgets DROP COLUMN color; ';`
    Write it in a Go raw string so the backslash reaches the file as written.
    Without the `E` rule, the string closes early and the drop would be retired.

  Then, after the loop, a sixth sub-test in the same function,
  `t.Run("drop then re-add in one file", …)`. It is not a refusal, so it asserts the
  opposite. `000001` creates `widgets (id …, color TEXT)`; `000002` is
  `ALTER TABLE widgets DROP COLUMN color; ALTER TABLE widgets ADD COLUMN color TEXT;`.
  Assert no error, and that `widgets.color` is expected with `file`
  `000002_destructive.up.sql`. In the same sub-test, a second fixture dir with the
  order reversed (add `size`, then drop `size`) asserts `widgets.size` is not
  expected. Update the function's doc comment to say it covers the destructive shapes
  and the five that `#0618`'s review found.
- `TestExpectedObjectsFromFiles_RetiresPlainDropColumn`: unchanged. The plain
  single-column drop must keep passing as is.
- New `TestExpectedObjectsFromFiles_RetiresPlainDropAfterQuotedBodies`, the shape
  `000047` has. `000001` creates `widgets (id …, color TEXT)`. `000002` contains, in
  this order: a `CREATE FUNCTION … AS $$ … ; … $$;` body with two inner semicolons, a
  `DO $tag$ BEGIN PERFORM 1; END $tag$;`, an `INSERT … VALUES ('a;b')`, then
  `ALTER TABLE widgets DROP COLUMN color;`. Assert no error and `widgets.color` not
  expected. This proves the splitter resumes at top level after each quoted region.
- New `TestSplitStatements`, table-driven, comparing `len` and the trimmed text of
  each statement:
  - `a; b` gives 2.
  - `SELECT ';'; b` gives 2.
  - `SELECT 'x''; y'; b` gives 2, for the escaped quote.
  - `SELECT E'\'; y'; b` gives 2, for the backslash escape.
  - `SELECT "a;b"; c` gives 2, for the quoted identifier.
  - `DO $$ x; y $$; z` gives 2.
  - `AS $fn$ a $$ b; $fn$; z` gives 2, for the tag and the inner `$$`.
  - `/* a /* b; */ c; */ d; e` gives 2, for nesting.
  - `SELECT $1; b` gives 2, since `$1` is not an opener.
  - `DO $$ never closed; x` gives 1, for the unterminated case.

  Use Go raw strings throughout. Per `AGENTS.md` §8, read back any fixture holding a
  backslash as bytes before trusting a zero-match or pass.

## Obstacles

- **None blocking.** The work is pure Go in one package. The DB-backed
  `TestCheckSchema_PrivateDatabase_DroppedColumnsDetected` creates its own database.
  That needs `CREATEDB` on `opencircuit`, already granted (`AGENTS.md` §5b), and
  `ISSUE=0620` gives the run its own test database.
- **No ports and no `web/dist`.** No server, browser or build of the SPA is needed.
- **Backslash fixtures.** The `E'\''` cases depend on a literal backslash on disk.
  Use Go raw strings and read the bytes back if a result looks wrong (`AGENTS.md` §8).
- **Citation guards on new comments.** The new doc comments describe the shapes the
  guard refuses. They should name `#0618` only as an issue number and cite no path
  that does not exist. `internal/handlers` is in the fast tier to catch that.
- **The throwaway dump test.** Delete it before committing, and stage
  `internal/testdb/schema_check.go`, `schema_check_test.go` and `issues/0620.md` by
  name only.
