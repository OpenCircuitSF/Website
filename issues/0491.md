## Description

`claimCommentGuardMinPlausibleFileCount` is `150`. It is validated by
`outbox_floor_plausible`, the **weak** predicate — the one with no growth
ceiling — while its population is a **file count in the hundreds**.

Measured by the orchestrator against the tree as it stands: the population is
**304**. `floor_plausible`'s rule is `floor >= population/2`, so the threshold
is 152. **`150` is already two files past it**, and nothing reports that,
because the predicate judging it never asks.

Found by `#0489`'s review, which was asked whether the growth detector covers
everything it should. It does not.

## Why the exemption does not cover this one

`outbox_floor_plausible` exists for **call-site** populations, which are an
order of magnitude smaller and where the strong rule's ratio is the wrong
instrument. That rationale is sound and should stay.

It does not extend to a file count of 304 sitting in the weak predicate's list.
This constant has the same shape as the two `#0489` just raised — a floor
against a file population that grows as the tree grows — and it is in the wrong
list.

## Why it matters now rather than later

`#0489` established that this family's whole failure mode is a floor whose
relationship to its population goes stale. It fixed the two constants that were
**caught**, precisely because they sat under the strong predicate. This one was
not caught, and by the same arithmetic it is already wrong.

`#0483`, `#0487` and `#0488` each fixed a count that drifted **silently**, for
want of a ceiling. This is the same defect with the ceiling present in the file
but pointed elsewhere.

2. **Move `claimCommentGuardMinPlausibleFileCount` to `floor_plausible()`** and

3. **Do not move the genuinely call-site-scaled constants.** The weak
   predicate's rationale is correct for them; check which of its remaining
   entries are call-site populations and which are file counts, and say what you
   found. `claimCommentGuardMinPlausibleCommentGroupCount` sits in the same loop
   — decide it explicitly rather than by association.
4. **Second criterion, from the same review**: the two 80-floors have roughly 36

### The 304-versus-305 distinction, checked independently

The implementer's account is right, and the mechanism is exact rather than
coincidental. `claimCommentGuardScanRoots` is `{"..", "../../cmd"}`, resolved
from `internal/outbox` — so `internal/` and `cmd/`, with no `web/`. The
`internal/handlers` file-count family's roots are `internal cmd web`. The
whole tracked tree holds exactly **one** `.go` file under `web/`
(`web/embed.go`), so the two populations differ by exactly one file, always,
by construction — not by a `find` catching a transient scratch file.

Both figures then moved by one while this issue was in flight, and the reason
is visible in git rather than inferred: at `ad0b7f9` the tracked `.go` count
under `internal cmd` was **304**, and at `b6cec93` it is **305**, the single
added file being `#0490`'s new `cmd/opencircuit` wiring guard. Measured on my
own tree state (`b6cec93` plus this issue's uncommitted markdown, no untracked
`.go` file present): `internal cmd` = **305**, `internal cmd web` = **306**.
So the constant's doc comment recording 304 for 2026-09-09 is already one
behind — which is exactly the staleness that comment discloses in its own
text, and exactly why the harness measures the population itself. `215` is
still well inside `[153, 431]`, so nothing needs re-deriving.

### The arithmetic

`ceil(304 / sqrt(2)) = 215`, and the bash integer form
`(304 * 70711 + 99999) / 100000` evaluates to 215 as well. `floor_plausible`
accepts `floor > 0`, `floor <= population`, and `floor >= population / 2` in
truncating integer division, so the accepted window for 215 is populations
`[215, 431]`. I probed that boundary directly on a sandbox copy rather than
computing it: population 431 passes, population 432 fails. The constant has
genuinely moved onto the strong predicate — it is judged by `floor_plausible`
in its own block, and `outbox_floor_plausible` no longer sees it.

### The comment-group decision — right answer, wrong reason, now corrected

Leaving `claimCommentGuardMinPlausibleCommentGroupCount` at 500 under the weak
predicate is **correct**, and I would not raise it. But the reason recorded on
the constant was not the load-bearing one, and it was arithmetically wrong:
it claimed a proportional floor "would need re-deriving on nearly every commit
that touches a comment". `floor_plausible`'s window is `[floor, 2*floor+1]`
whatever the scale, so a proportional floor on this population would carry the
same roughly +41% growth headroom the file-count floors carry — no more
re-derivation, not less. Left standing, that is the kind of checkable claim a
later reader disproves and then concludes the whole decision was wrong.

The decisive reason is a **unit mismatch between the two sides of the
comparison**, and it is much stronger. The external oracle counts
comment-opening *lines*; the quantity the floor is actually compared against
inside `claimCommentGuardFloorImplausible` is a `go/ast` comment *group*
count, and a multi-line line-comment block is many lines but one group.
Measured over `internal/` and `cmd/` on 2026-09-09: **37,641** comment-opening
lines against roughly **5,160** groups, a ratio near 7.3 — corroborating the
4,963 groups the constant's own doc comment already cited. Half the line
population is over 18,000, more than three times the group count a healthy
walk yields, so the strong rule would make this guard fail on every run
against a sound tree. That is `#0275`'s own failure mode, made permanent.
A one-sided bound (`floor <= population`) tolerates an over-counting proxy for
its population; a two-sided one does not.

On the "is 500 a floor in name only at 1.3%" question: **no, and 1.3% is the
wrong denominator.** Against the quantity the guard actually measures it is
`500 / 5160`, near **10%** — a real bar. It detects a walk that collapses to
under a tenth of the comment groups a healthy tree yields, which is the job
its doc comment claims for it. The file-visit dimension is separately covered
at 215 of 305 files, so this floor is not carrying the load alone.
