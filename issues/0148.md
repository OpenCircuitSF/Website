## Description

`PRD.md:671` still describes the workshops partial index as `idx_workshops_published … WHERE status = 'published'`. Both halves are stale:

- the **predicate** was widened to `status <> 'draft'` by `#0135`, so the index covers canceled workshops too;
- the **name** became `idx_workshops_visible` in `#0142`.

The predicate half is the part that matters. It records a product decision — canceled workshops stay visible on the index — that `#0135` made and the PRD never learned about.

**The reason it drifted silently is the real finding.** `TestDatabaseDocMigrationParity` guards `docs/database.md` and `CLAUDE.md` against the migrations. Nothing guards `PRD.md`, even though `CLAUDE.md` §11 treats §6.2 as tracking what actually shipped, and every issue's `## Relation` block sends implementers to the PRD as the specification. A spec that silently falls behind the schema is worse than one that is obviously out of date, because it still reads as authoritative.

## Root cause

`PRD.md` §6.2's SQL block is hand-maintained prose, not generated from anything, and nothing checked it against `migrations/` the way `TestDatabaseDocMigrationParity` checks `docs/database.md` and `CLAUDE.md`. Two independent migration changes to the workshops index (`#0135`'s predicate widen, `#0142`'s rename) each landed correctly in `migrations/000020` and in `docs/database.md`/`CLAUDE.md` — both guarded — but the PRD was not required reading for either change and nobody happened to open it.

Sweeping the rest of §6.2 against `migrations/` table by table found three more of the same class — an already-shipped fact §6.2 doesn't mention:

- `workshop_interests`: migration `000020` creates `idx_workshop_interests_interest`; §6.2's `workshop_interests` block had no index at all (its sibling `subscriber_interests` block did carry its index, so this wasn't a stylistic omission).
- `email_events`: migration `000014` creates `idx_email_events_soft_bounce`, widened in place by `000016`; §6.2 never mentioned it, even though it's the index `internal/sesnotify`'s live soft-bounce count query actually uses today.
- `email_sends`: migration `000018` adds `claimed_at` (`#0122`'s `OrphanSweep`/`ClaimRow` timestamp), live and read/written by `internal/mailing/worker.go` and `worker_store.go`; §6.2's `email_sends` table didn't list the column, even though the `outbound_queue` table two blocks later already says "orphan sweep, same shape as `email_sends`" — implying a column that, in the PRD's own text, wasn't there.

Everything else that looked like drift on first read turned out not to be: `subscribers.source/invited_at/source_detail/consent_basis/import_id` (§6.10), `subscribers.soft_bounce_streak/last_bounce_at/last_delivery_at` (§6.9 — which explicitly says it *supersedes* the shipped windowed rule), `email_campaigns.slug/archive_status/archived_at` (§6.8, `slug` owned by `#0123`), the `paused_delivery_health` campaign status (§6.9's circuit breaker), `idx_email_events_recipient_time` (§6.9's `/admin/deliverability`), and the `subscriber_imports`/`subscriber_events`/`outbound_queue` tables outright are all Phase 8 (`#0123`–`#0129`) design that has not been migrated yet. `grep`ing `internal/` for each confirmed none of it exists in Go code either. Left every one of these alone — the PRD is correctly leading, not lagging, and "fixing" them to match the unbuilt schema would mean deleting the spec Phase 8 is supposed to implement.

## Fix

**Half A — drift.** Corrected the named index (name + predicate) and added the three missing already-shipped facts above to `PRD.md` §6.2, each with a short comment in the same style as its neighbors (`email_events`'s soft-bounce index comment explicitly notes it's superseded once §6.9 ships, so a future Phase 8 issue knows to remove it then rather than being surprised it's there).

**Half B — guard, built and scoped narrowly.** Added `TestPRDWorkshopAndMailingIndexParity` in `internal/db/prd_index_parity_test.go`, sibling to `TestDatabaseDocMigrationParity`. Two deliberate scope limits, both load-bearing:

1. **One direction only — migrations → PRD, never PRD → migrations.** The guard walks every index that actually exists (replayed from `migrations/*.up.sql`, handling the one real `DROP INDEX`+`CREATE INDEX` pair — `idx_email_events_soft_bounce`, `000014`→`000016` — in file/statement order) and asserts `PRD.md` §6.2 names it correctly. It never asks the reverse question, so `idx_email_events_recipient_time` (documented for §6.9's not-yet-built `/admin/deliverability`) never enters the live-index map and is never flagged. A bidirectional check would fire on every one of the Root-cause "not actually drift" items above and would need an allowlist of known future work to silence — which just relocates the drift risk this guard exists to catch.
2. **Indexes only, not full column/constraint parity.** A `CREATE`/`DROP INDEX` statement is one self-contained, unambiguous, regexp-extractable unit. A column requires replaying a `CREATE TABLE` plus every later `ALTER TABLE ADD COLUMN` across up to 20 files with no single-statement anchor — meaningfully more parsing surface for a class that (unlike indexes, now 2-for-2 on real drift: `#0135`, `#0142`) has drifted exactly once so far (`email_sends.claimed_at`, found and fixed by hand in this same issue, not mechanically guarded). `PRD.md` §6.2 also has never attempted to transcribe `CHECK` constraints at all (`interests_slug_format`, `subscribers_email_normalized`, etc. appear nowhere in it), so there's no existing convention to hold a constraint-level guard to. If a second column drifts, that's the trigger to build the column guard; one instance with a harder extraction problem wasn't judged worth it yet.

Table scope (`prdIndexParityTables`) is exactly the set of tables §6.2 specifies with a literal `CREATE TABLE` — excludes the "copied auth tables" §6.2 names but doesn't detail (`users`, `sessions`, `audit_log`, etc.), so their indexes are correctly never checked.

Placement follows `TestDatabaseDocMigrationParity`'s own precedent (`internal/db` owns migrations) and reuses its `listMigrations`/`migrationsDir` rather than re-walking the migrations directory a second time.

## Gotchas

- `idx_email_events_soft_bounce`'s predicate has a nested `(bounce_subtype IS NULL OR ...)` inside the outer `WHERE`. The guard's predicate capture is delimited only by the statement's terminating `;`, not by paren-balancing, which is exactly what lets this one match without any paren-depth tracking — a column-list capture (`\([^;]*?\)`) would not have been safe here, which is part of why the guard doesn't try to parse column lists generically beyond the index's own column list.
- The renamed-index case doesn't produce a "definition diverged" error, it produces a "not mentioned" error — the guard is keyed by the *current* (post-rename) name, so a stale name in the PRD is invisible to it as `idx_workshops_visible` and shows up as a flat miss rather than a diff. Worth knowing when reading a future failure: a rename and a total omission look identical in this guard's output.
- `scripts/testdb.sh gc` was not run — no leftover per-agent databases needed sweeping, and per CLAUDE.md §5a it now refuses without `--all` regardless.
