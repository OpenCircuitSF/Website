## Description

`PRD.md:671` still describes the workshops partial index as `idx_workshops_published … WHERE status = 'published'`. Both halves are stale:

- the **predicate** was widened to `status <> 'draft'` by `#0135`, so the index covers canceled workshops too;
- the **name** became `idx_workshops_visible` in `#0142`.

The predicate half is the part that matters. It records a product decision — canceled workshops stay visible on the index — that `#0135` made and the PRD never learned about.

**The reason it drifted silently is the real finding.** `TestDatabaseDocMigrationParity` guards `docs/database.md` and `CLAUDE.md` against the migrations. Nothing guards `PRD.md`, even though `CLAUDE.md` §11 treats §6.2 as tracking what actually shipped, and every issue's `## Relation` block sends implementers to the PRD as the specification. A spec that silently falls behind the schema is worse than one that is obviously out of date, because it still reads as authoritative.

## Acceptance criteria

- [ ] PRD §6.2's workshops index line matches `migrations/000020` — current name and current predicate
- [ ] Sweep the rest of §6.2 against `migrations/` rather than fixing only the line named here. `#0113` already found three drifted rows in `CLAUDE.md` §11's index, and `#0050`'s review found `email_campaigns.slug` in the PRD but not in the schema (owned by `#0123`) — assume this is not the only one
- [ ] Decide whether a parity guard should cover `PRD.md` §6.2 the way `TestDatabaseDocMigrationParity` covers `docs/database.md`, and either build it or record why the PRD is deliberately allowed to lead the schema
- [ ] If a guard is built, prove it fails against the current drift before fixing the drift
- [ ] `ISSUE=0148 scripts/check.sh go ./internal/...` passes, doc-parity guards included

## Notes

Filed at the explicit request of `#0142`'s phase-3 review, which found the line, judged it out of scope for a rename issue, and wrote the exact edit into `issues/0142.md`'s `## Review notes` so filing would be cheap.

The tension worth resolving deliberately: a PRD is a specification and may legitimately lead the implementation, while `docs/database.md` is documentation and must follow it. That argues against a naive parity guard and for something narrower — perhaps a guard only over §6.2's SQL blocks, which are transcriptions of the schema rather than statements of intent.
