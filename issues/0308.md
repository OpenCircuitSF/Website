## Description

`#0296` replaced `TestMailKindsCoversEveryOutboxKind`'s bare `intakeException`
constant with `kindExceptions map[string]string`, so each exempted `Kind` carries
a reason. That is the right shape and it satisfied the criterion.

**But the reason is required by convention only.** `"KindFoo": ""` compiles and
silently exempts the kind — the very outcome the exception list exists to make
deliberate. A `Kind` exempted with no stated reason is claimed by no poller and
stalls in `'queued'` forever, which is the defect `#0254` created and `#0282`
guarded against.

`#0298` established the enforced form on the web side: `KNOWN_STABLE_BRANCH_SITES`
fires an **independent** violation when an entry's `reason` is empty, verified by
injection in that review. This is the same rule, unenforced.

`#0296`'s reviewer noted the asymmetry honestly rather than bouncing for it,
since the criterion as written was met.

## Acceptance criteria

1. `TestMailKindsCoversEveryOutboxKind` fails when any `kindExceptions` value is
   empty or whitespace, naming the offending entry.
2. **Keep the two rules independent**, as `#0298` did on the web side: an entry
   with an empty reason must fire its own violation, not be folded into the
   uncovered-kind check. An entry can be both unjustified and wrong, and the
   failure should say so.
3. **Prove it by injection, not inspection** — add an entry with an empty reason
   to the real map in a scratch copy, confirm the guard fails, then restore and
   verify the file is byte-identical. `#0298`'s review is the precedent.
4. Whitespace counts as empty. A reason of `" "` must not pass.
5. The existing entry keeps its reason intact — do not rewrite it while adding
   the rule.
6. Per CLAUDE.md §8, the oracle must not be the same bytes as the subject, and
   the guard must still fail closed on a zero-constant parse (`#0296`'s review
   mutation-proved that; do not regress it).
7. `ISSUE=NNNN scripts/check.sh go ./internal/mailing/... ./internal/outbox/...`
   passes with no skips.

## Root cause

`kindExceptions[kind]`'s presence, not its value, was what
`TestMailKindsCoversEveryOutboxKind` checked (`_, exempt :=
kindExceptions[kind]; exempt`) — an entry with an empty or whitespace-only
`reason` is present exactly like a properly-justified one, so it compiled
and silently exempted its `Kind`. Nothing forced the reason string to be
non-blank.

## Fix

Added an independent check inside `TestMailKindsCoversEveryOutboxKind`
(before the uncovered-kind loop, using `t.Errorf` so it does not halt the
test and mask the checks after it — criterion 2): every `kindExceptions`
entry whose `strings.TrimSpace(reason) == ""` is collected and reported by
name in a single `Fatalf`-shaped message, independent of whether that
kind is also uncovered. `strings.TrimSpace` makes a reason of `" "` fail
too (criterion 4). The existing `KindSubscribeIntake` entry's reason was
not touched (criterion 5).

### Criterion 2 — independence proved, not asserted

The implementer's own proof injected two *blank-reason* entries, which only
exercises one of the two rules. The reviewer ran the case the criterion is
actually about — an entry that is unjustified **and** a `Kind` that is
uncovered, in the same run — by additionally adding
`KindInjectedUnclaimed Kind = "injected_unclaimed"` to
`internal/outbox/store.go` (claimed by neither `mailKinds` nor
`kindExceptions`):

```
outbox_worker_kinds_guard_test.go:143: kindExceptions entr(ies) with an empty
or whitespace-only reason: [KindInjectedEmptyProbe] — ...
outbox_worker_kinds_guard_test.go:155: outbox.Kind constant(s) claimed by
NOBODY — neither mailKinds nor kindExceptions: [KindInjectedUnclaimed] — ...
--- FAIL: TestMailKindsCoversEveryOutboxKind (0.01s)
```

**Both violations fire; neither masks the other.** The `t.Errorf` (not
`Fatalf`) for the new rule is exactly what makes that work, and it is placed
before the uncovered-kind `Fatalf` so ordering cannot swallow it. `#0298`'s
enforced form on the web side is matched.

One honest note on scope, not a defect: the two rules can never fire on the
*same* kind, because a blank reason still confers exemption —
`if _, exempt := kindExceptions[kind]; exempt` is presence-based, unchanged by
this commit. Criterion 2's "an entry can be both unjustified and wrong" is
therefore satisfied across different kinds, which is what was proved. Making a
blank reason *void* the exemption would make one bad entry cascade into two
violations for the same kind — noisier, and closer to the masking shape
criterion 2 was written to avoid. The current split is the better reading.

### Criterion 6 — fail-closed on a zero-constant parse, still intact

`#0296`'s two mutation-proved guards were re-mutated in the worktree and both
still fire, and both still run *before* the new check:

| Mutation | Result |
|---|---|
| `../outbox` `ParseDir` filter → `return false` | `:72: found zero Kind constants in internal/outbox — the parse likely broke, not a real empty set` |
| `mailKinds` element collector's `pkgIdent.Name == "outbox"` → a non-existent package name | `:122: mailKinds parsed to zero elements — the parse likely broke, not a real empty list` |

No regression. The oracle is not the same bytes as the subject: the exemption
list is a live Go map read at runtime, the population comes from `go/ast`
parsing `internal/outbox`'s source, and the new rule reads a value the map's
own declaration supplies — an edit to one cannot satisfy the other.
