## Resolution notes

> 🟢 Resolved 2026-08-27 — `noOpMailingMailer.Send` logs the rendered body
> unconditionally again, so `MAILER_NOOP=true` prints the magic link; the
> `checkMailerNoOp` guard is byte-for-byte unchanged.

## Description

Until `#0260`, running locally with `MAILER_NOOP=true` against Postgres printed
the full magic link for a registration or recovery to the log, and that was the
way to complete a passkey registration on a machine with no SES.

`#0260` made `CreatePendingRegistration`/`CreateRecoveryToken` enqueue into
`outbound_queue` inside the token transaction, which was correct and is not in
question. But it removed the only callers of `auth.NoOpMailer.SendVerification`
and `auth.NoOpMailer.SendRecovery` — the two methods that logged the link. The
row now drains through `noOpMailingMailer`, which logs **only the subject**.

So the link still exists, is still rendered, and is still in the queue payload —
it is simply no longer visible. Recovering it means reading `outbound_queue` by
hand in `psql`.

`STORAGE=json` is unaffected: `devstore.DevRegistrar` has its own path. This
only bites the Postgres-backed local flow, which is the one anything touching
the mailing subsystem is required to use (CLAUDE.md §5).

## Why this matters more than it looks

CLAUDE.md §10 records that SES production access is still pending and that the
guard in `checkMailerNoOp` deliberately refuses `MAILER_NOOP=true` unless
`BASE_URL` is localhost. That guard is correct and must stay. The consequence is
that `MAILER_NOOP=true` is *the* local development path for auth, and it has
quietly stopped doing the one thing it was used for.

This is the obstacle class §5b describes: knowable now, cheap to clear now,
expensive when the next agent hits it mid-issue and starts debugging a
registration flow that is actually working fine.

## Acceptance criteria

1. `noOpMailingMailer.Send` logs the rendered **text body**, not just the
   subject, so the magic link appears in the log for every queued message.
2. It is not gated on kind — a welcome email or campaign draining through the
   no-op mailer logs its body too. The no-op mailer exists to make outbound mail
   visible; a per-kind allowlist would reintroduce this bug for the next kind.
3. The guard in `cmd/opencircuit/main.go`'s `checkMailerNoOp` is untouched.
   `MAILER_NOOP=true` must still refuse to start unless `BASE_URL`'s host is
   `localhost`/`127.0.0.1`. Do not weaken it to make this easier to test.
4. A test asserts a queued registration's rendered body reaches the logger —
   capture the log output rather than asserting on the mailer's arguments, since
   the defect was that a real call stopped happening at all.
5. `auth.NoOpMailer.SendVerification`/`SendRecovery` are either deleted as dead
   code or documented as retained deliberately. Do not leave two no-op mailers
   where it is unclear which one is live.
6. Manually confirmed once end to end: `./scripts/dev.sh` against Postgres with
   `MAILER_NOOP=true`, start a registration, and read the link out of the log.
   Say in `## Verification` that this was done against Postgres, not
   `STORAGE=json`.

## Fix

- `cmd/opencircuit/main.go`: `noOpMailingMailer.Send` now logs `msg.TextBody`
  (falling back to `msg.HTMLBody` only in the defensive case `TextBody` is
  empty) alongside the subject, unconditionally — not gated on kind. Every
  `Build*Email` helper in `internal/mailing` sets both bodies, so this covers
  registration, recovery, welcome, sessions-revoked, admin-alert, and
  campaign send/test-send mail the same way. `checkMailerNoOp` and
  `mailerNoOpAllowed` are untouched — confirmed by diff review, not just by
  intent.
- `internal/auth/mailer.go`: `NoOpMailer.SendVerification`/`SendRecovery`
  retained (not deleted) with doc comments recording that they have had no
  production caller since `#0260` and that this is consistent with `#0278`'s
  decision to retain the same two methods on the `Mailer` interface — see
  that issue's `## Fix` section for the full reasoning. `mailer.go`'s `Mailer`
  interface doc comment also gained a `#0278` note.
- `cmd/opencircuit/mailer_noop_test.go`: added
  `TestNoOpMailingMailer_Send_LogsRenderedBody` (asserts the rendered link
  appears in captured `log` output, via `log.SetOutput`, restored via
  `t.Cleanup`) and `TestNoOpMailingMailer_Send_LogsBodyRegardlessOfKind`
  (a non-auth-shaped message, to lock in "no per-kind allowlist").
- Sequenced before `#0278` per that issue's criterion 5, since both touch
  `internal/auth/mailer.go`'s and `internal/auth/ses_mailer.go`'s
  declarations; `#0278`'s decision (retain, not narrow) is recorded in its
  own `## Fix` section.

**Criterion 2 — genuinely kind-independent, structurally.** `mailing.Message`
(`internal/mailing/mailer.go:22`) carries no kind field at all, and `Send` has
no branch: it assigns `body`, falls back to `HTMLBody` when `TextBody` is
empty, and logs. Every `Build*Email` helper in `transactional_templates.go`
(confirmation, already-subscribed, registration, recovery, sessions-revoked,
admin-alert, welcome) plus `campaign_render.go:171` and `worker.go:896` set
`TextBody` from `renderText()`, so the fallback is genuinely defensive rather
than the normal path for any auth mail. The HTML fallback would only fire for a
campaign authored without a text body, in a localhost-only dev mode — acceptable
noise, not a leak (the guard confines `MAILER_NOOP` to localhost).

**Criterion 4 — the tests capture log output, and they kill the mutation.** Both
new tests use `log.SetOutput` into a `bytes.Buffer`, restored via `t.Cleanup`,
and assert on the captured text; neither inspects the mailer's arguments. Proved
by mutation in a throwaway worktree at `58ad750` (removed afterward; the shared
tree was never touched):

- Reverting `Send` to the pre-fix one-liner fails **both** tests, each naming the
  missing link/body.
- Adding a per-kind allowlist (body suppressed unless the subject looks like auth
  mail) fails `TestNoOpMailingMailer_Send_LogsBodyRegardlessOfKind`, so
  criterion 2 is guarded and not merely asserted in a comment.

**Criterion 6 — recovery instead of registration is sufficient here.** Both
flows were broken by the same removal in `#0260` and drain the identical path:
`CreateRecoveryToken`/`CreatePendingRegistration` → `outbox.EnqueueTx` →
`OutboxWorker` → `noOpMailingMailer.Send`. The only divergence is which
`Build*Email` helper renders the message, and both set `TextBody` the same way.
`registrations_enabled=false` on the shared dev DB made registration
unavailable; substituting recovery is the right call. What remains formally
unexercised end to end is `BuildRegistrationEmail`'s specific rendering under
`MAILER_NOOP` — covered by unit tests, not by a live run.
