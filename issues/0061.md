## Description

The landing screen for `/admin`: list health, growth, and what needs attention.

## Acceptance criteria

- [ ] Subscriber counts by status with a 30-day growth trend
- [ ] Interest distribution — subscribers per interest
- [ ] Recent campaigns with their outcomes
- [ ] Any campaign currently sending, with live progress
- [ ] Warnings surfaced: complaint rate above 0.3%, `physical_address` unset, unprocessed inbound mail, SES sandbox still active
- [ ] Loads in a single round trip
- [ ] `npm run check` and `npm test` pass

## Notes

PRD §5.2. The warnings row is the part that earns this screen — an operator should learn that the physical address is missing here, not when a send is refused on announcement day.

**Amended 2026-08-21 by `#0046`'s second phase-3 review.** The "subscriber
counts by status" tile must exclude `synthetic = true` rows (migration
`000019`, `#0046`) — the per-admin campaign test-send recipient fixtures.
`subscribers.Store.StatusCounts` already applies the exclusion unconditionally,
so reusing it is correct and sufficient; a new dashboard-specific aggregate
query must carry the predicate itself or the `pending` bucket is permanently
inflated by one per admin who has ever run a test send. The same applies to the
30-day growth trend and the interest-distribution query if either counts rows
from `subscribers` directly.

## Implementation notes

**Backend — one handler, one query per figure.** `internal/handlers/admin_dashboard.go`
adds `AdminDashboardHandler.Overview` (`GET /admin/overview`), wired through
`adminRoutes()`/`mountAndServe()` in `cmd/opencircuit/main.go` the same way
every other admin route is — no direct `mux.Handle` call, so
`TestAdminRoutesRegisteredOnlyViaTable`'s AST guard and
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin`'s enumerated guard
proof both cover it automatically. Every figure comes from exactly one
aggregate query against an existing store:

- Subscriber counts by status: `subscribers.Store.StatusCounts` (already
  excludes `synthetic = true`).
- 30-day growth: a new `subscribers.Store.Growth30Days(ctx, since)` — one
  query, two `FILTER` clauses (confirmed / unsubscribed since a cutoff),
  excluding `synthetic = true` per this issue's amendment.
- Interest distribution: `interests.Store.ListAll` + the existing
  `SubscriberCounts` (already used by the admin interests screen). Not
  synthetic-filtered — see `interestDistribution`'s doc comment for why
  that's safe today (no code path ever attaches interests to a synthetic
  row) and what would need to change if that ever stops being true.
- Recent campaigns / currently-sending campaign: one call to
  `mailing.CampaignStore.List()` (itself 2 queries regardless of campaign
  count, per its own "no pagination — count is small" doc comment), sliced
  and filtered in Go — no extra query for the "sending" lookup.
- Account-wide complaint rate: a new
  `mailing.CampaignStatsStore.AccountComplaintRate(ctx)` — one query,
  `LEFT JOIN` (not `EventCounts`' `INNER JOIN`, which would drop clean
  sends from the denominator), `count(DISTINCT s.id)` so a duplicate
  notification for the same send never double-counts. Threshold is a fixed
  0.3% (PRD §11, RFC 8058 / Gmail-Yahoo), deliberately NOT
  `send_health_complaint_pct` (the worker's own 0.1% per-campaign circuit
  breaker) — the two are independently tunable and conflating them would
  weaken one or misfire the other. A minimum sample (50 account-wide sends)
  gates the warning so a tiny sample doesn't read as "high."
- physical_address / SES sandbox: `auth.Store.ListSettings` (already a
  single small-table read) for the former; `config.Config.SESSandbox`
  (new field, default `true`) for the latter.

**"Unprocessed inbound mail" cannot be computed.** PRD §6.5 path 3 (inbound
`mailto:` unsubscribe processing) has no implementation in this codebase —
`#0058` is still `open`. There is no table this handler could aggregate, so
`warnings.inbound_mail_unavailable` is always `true` rather than a
fabricated zero. Once `#0058` ships, this handler will need a real count
wired in here.

**SES sandbox is a manually-set flag, not a live query.** Nothing in this
codebase calls AWS to ask about account-level sending status, and no SES
account exists yet (CLAUDE.md §10 item 2). `config.SESSandbox`
(`SES_SANDBOX` env var, default `true`) mirrors `MAILER_NOOP`'s shape —
an operator flips it once AWS approves production access.

**Frontend.** `web/src/lib/dashboard.ts` holds every rendering decision
(growth sign/formatting, which warnings to show and in what order, the
complaint-rate percentage string) as pure functions, per the #0047/#0049
convention that nothing in a `.svelte` file is covered by a test.
`Dashboard.svelte` is markup and wiring only, mounted as the new default
`overview` tab in `Admin.svelte` (first in both the `Section` union and the
subtab nav — PRD §5.2 lists `/admin` itself as "Overview"). Clicking a
campaign name (in "Currently sending" or "Recent campaigns") reuses
`Admin.svelte`'s existing `goToAnnouncedCampaign` deep-link mechanism to
open it in the Campaigns tab's editor, rather than duplicating that UI.
Live progress for a sending campaign reuses the existing `#0048` SSE
machinery (`subscribeEvent`/`campaignProgress.ts`) exactly as
`CampaignEditor.svelte` does, including its "re-fetch on every (re)connect"
reasoning for staying in sync with a send that starts/finishes/is canceled
during a stream gap.

**Guard-removal proof.** Temporarily changed the admin-routes loop in
`mountAndServe` (`cmd/opencircuit/main.go`) to register
`GET /admin/overview` unguarded (bypassing `requireAdmin`) and re-ran
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` against my own
isolated database (`ISSUE=0061`): it failed with
`no session: GET /admin/overview status = 200, unexpected for this case`
and the same for a non-admin session. Reverted immediately after
confirming the failure; the committed code has no trace of the mutation.

## Gotchas

- **`Confirm`'s expiry check is `ConfirmExpiresAt.After(now)` — strictly
  after, not after-or-equal.** `TestGrowth30Days_BoundaryAndSyntheticExclusion`
  first failed with "confirm token invalid or expired" because a 1-hour
  `ConfirmTTL` from a backdated `Create` call landed `confirm_expires_at`
  exactly ON the backdated `Confirm` call's own `now`, which fails the
  strict inequality. Fixed by giving the backdated fixtures a generous
  24-hour TTL instead of shrinking the test's time offsets — see the test's
  own comment for the full reasoning, in case another test needs the same
  backdating trick.
- **`interests.Store.SubscriberCounts` is not synthetic-filtered**, unlike
  everything else this issue's amendment touches. It's safe in practice
  (the only synthetic-row writer never attaches interests), but it's a
  latent gap, not a design decision — flagged in
  `admin_dashboard.go`'s `interestDistribution` doc comment as a tripwire
  for whoever changes that writer.
