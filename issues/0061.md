**Amended 2026-08-21 by `#0046`'s second phase-3 review.** The "subscriber
counts by status" tile must exclude `synthetic = true` rows (migration
`000019`, `#0046`) — the per-admin campaign test-send recipient fixtures.

## Implementation notes

**Backend — one handler, one query per figure.** `internal/handlers/admin_dashboard.go`
adds `AdminDashboardHandler.Overview` (`GET /admin/overview`), wired through
`adminRoutes()`/`mountAndServe()` in `cmd/opencircuit/main.go` the same way
every other admin route is — no direct `mux.Handle` call, so
`TestAdminRoutesRegisteredOnlyViaTable`'s AST guard and
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin`'s enumerated guard
proof both cover it automatically. Every figure comes from exactly one
aggregate query against an existing store:

- Subscriber counts by status: `subscribers.Store.StatusCounts` (already
  excludes `synthetic = true`).
- 30-day growth: a new `subscribers.Store.Growth30Days(ctx, since)` — one
  query, two `FILTER` clauses (confirmed / unsubscribed since a cutoff),
  excluding `synthetic = true` per this issue's amendment.
- Interest distribution: `interests.Store.ListAll` + the existing
  `SubscriberCounts` (already used by the admin interests screen). Not
  synthetic-filtered — see `interestDistribution`'s doc comment for why
  that's safe today (no code path ever attaches interests to a synthetic
  row) and what would need to change if that ever stops being true.
- Recent campaigns / currently-sending campaign: one call to
  `mailing.CampaignStore.List()` (itself 2 queries regardless of campaign
  count, per its own "no pagination — count is small" doc comment), sliced
  and filtered in Go — no extra query for the "sending" lookup.
- Account-wide complaint rate: a new
  `mailing.CampaignStatsStore.AccountComplaintRate(ctx)` — one query,
  `LEFT JOIN` (not `EventCounts`' `INNER JOIN`, which would drop clean
  sends from the denominator), `count(DISTINCT s.id)` so a duplicate
  notification for the same send never double-counts. Threshold is a fixed
  0.3% (PRD §11, RFC 8058 / Gmail-Yahoo), deliberately NOT
  `send_health_complaint_pct` (the worker's own 0.1% per-campaign circuit
  breaker) — the two are independently tunable and conflating them would
  weaken one or misfire the other. A minimum sample (50 account-wide sends)
  gates the warning so a tiny sample doesn't read as "high."
- physical_address / SES sandbox: `auth.Store.ListSettings` (already a
  single small-table read) for the former; `config.Config.SESSandbox`
  (new field, default `true`) for the latter.

**"Unprocessed inbound mail" cannot be computed.** PRD §6.5 path 3 (inbound
`mailto:` unsubscribe processing) has no implementation in this codebase —
`#0058` is still `open`. There is no table this handler could aggregate, so
`warnings.inbound_mail_unavailable` is always `true` rather than a
fabricated zero. Once `#0058` ships, this handler will need a real count
wired in here.

**SES sandbox is a manually-set flag, not a live query.** Nothing in this
codebase calls AWS to ask about account-level sending status, and no SES
account exists yet (CLAUDE.md §10 item 2). `config.SESSandbox`
(`SES_SANDBOX` env var, default `true`) mirrors `MAILER_NOOP`'s shape —
an operator flips it once AWS approves production access.

**Frontend.** `web/src/lib/dashboard.ts` holds every rendering decision
(growth sign/formatting, which warnings to show and in what order, the
complaint-rate percentage string) as pure functions, per the #0047/#0049
convention that nothing in a `.svelte` file is covered by a test.
`Dashboard.svelte` is markup and wiring only, mounted as the new default
`overview` tab in `Admin.svelte` (first in both the `Section` union and the
subtab nav — PRD §5.2 lists `/admin` itself as "Overview"). Clicking a
campaign name (in "Currently sending" or "Recent campaigns") reuses
`Admin.svelte`'s existing `goToAnnouncedCampaign` deep-link mechanism to
open it in the Campaigns tab's editor, rather than duplicating that UI.
Live progress for a sending campaign reuses the existing `#0048` SSE
machinery (`subscribeEvent`/`campaignProgress.ts`) exactly as
`CampaignEditor.svelte` does, including its "re-fetch on every (re)connect"
reasoning for staying in sync with a send that starts/finishes/is canceled
during a stream gap.

**Guard-removal proof.** Temporarily changed the admin-routes loop in
`mountAndServe` (`cmd/opencircuit/main.go`) to register
`GET /admin/overview` unguarded (bypassing `requireAdmin`) and re-ran
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` against my own
isolated database (`ISSUE=0061`): it failed with
`no session: GET /admin/overview status = 200, unexpected for this case`
and the same for a non-admin session. Reverted immediately after
confirming the failure; the committed code has no trace of the mutation.

## Gotchas

- **`Confirm`'s expiry check is `ConfirmExpiresAt.After(now)` — strictly
  after, not after-or-equal.** `TestGrowth30Days_BoundaryAndSyntheticExclusion`
  first failed with "confirm token invalid or expired" because a 1-hour
  `ConfirmTTL` from a backdated `Create` call landed `confirm_expires_at`
  exactly ON the backdated `Confirm` call's own `now`, which fails the
  strict inequality. Fixed by giving the backdated fixtures a generous
  24-hour TTL instead of shrinking the test's time offsets — see the test's
  own comment for the full reasoning, in case another test needs the same
  backdating trick.
- **`interests.Store.SubscriberCounts` is not synthetic-filtered**, unlike
  everything else this issue's amendment touches. It's safe in practice
  (the only synthetic-row writer never attaches interests), but it's a
  latent gap, not a design decision — flagged in
  `admin_dashboard.go`'s `interestDistribution` doc comment as a tripwire
  for whoever changes that writer.

### A dashboard is only worth having if the numbers are true

Every figure was checked against the *database*, not against the code that
produced it. I seeded my own database (`opencircuit_test_0061fix`, dropped
afterwards) with subscribers across all five statuses plus three synthetic
rows deliberately placed inside the 30-day window, interests with a known
distribution, seven campaigns across six statuses, and email sends/events
built to separate every failure mode below. Nothing targets a literal or
seeded id — every fixture row is created by the seed and looked up by
slug/name/email (CLAUDE.md §8b). The handler was driven through a throwaway
`cmd/probe0061rev` in a detached worktree at `fbdd2a6` (removed afterwards),
constructing the real `AdminDashboardHandler` over a real `pgxpool` with a
`pgx.QueryTracer` attached, so the JSON below is the shipped handler's own
output and the query count is measured, not counted by eye.

| Figure | Rendered by the handler | My own SQL | Agree |
|---|---|---|---|
| Status counts | pending 2, active 4, unsubscribed 2, bounced 1, complained 1 | `select status, count(*) from subscribers where synthetic is false group by status` → identical | ✅ |
| 30-day growth | confirmed 4, unsubscribed 1, net 3 | `count(*) filter (confirmed_at >= now()-'30 days')` = 4, unsubscribed = 1 | ✅ |
| Interest distribution | robotics 2, soldering 3, lasers 0 (+ the 12 seeded taxonomy rows at 0) | per-interest `count(*) from subscriber_interests` → identical, same order | ✅ |
| Recent campaigns | the 5 newest by `created_at DESC` (draft, sending, sent, canceled, scheduled); the 2 older ones absent | `order by created_at desc, id desc limit 5` → identical | ✅ |
| Currently sending | the single `status='sending'` campaign, and it also appears in the recent list | `where status='sending'` → same row | ✅ |
| Complaint numerator / denominator | 1 / 50 → `complaint_rate_pct` 2.0 | `count(distinct s.id)` over sends with a Complaint event = 1; `count(*) where status='sent'` = 50 | ✅ |
| Complaint sample size | 334 after topping the fixture up | `count(*) from email_sends where status='sent'` = 334 | ✅ |
| `physical_address_unset` | true for `''` **and** for `'   '`; false once a real address is set | `settings` row read back directly | ✅ |
| `ses_sandbox_active` | mirrors the constructor flag exactly (true, then false) | n/a — config flag | ✅ |
| `inbound_mail_unavailable` | always true | n/a — no table exists to aggregate | ✅ |

**Synthetic exclusion — genuinely applied, and the fixture proves it would
have been visible.** The three synthetic rows sit *inside* the window
(confirmed 2 days ago, unsubscribed 2 days ago). Counting them would have
produced `confirmed 6 / unsubscribed 2` — I ran exactly that query
(`... from subscribers` with no `synthetic` predicate) and got `6|2`, against
the handler's `4|1`. Both `StatusCounts` and `Growth30Days` carry
`WHERE synthetic = false`, and the column is `NOT NULL DEFAULT false`
(migration `000019`), so there is no third state to leak through.

**The 30-day boundary is inclusive, and it is relative to `now()`, not to the
start of a day.** `Overview` computes `since = now().Add(-30*24*time.Hour)`
and `Growth30Days` filters `confirmed_at >= $1`. Pinning `since` to a
fixture's exact `confirmed_at` and stepping one microsecond either way:

```
since = 2026-08-14T19:04:28.409310Z (exactly on the row) → confirmed=3   ← included
since = 2026-08-14T19:04:28.409311Z (+1µs)               → confirmed=2   ← excluded
since = 2026-08-14T19:04:28.409309Z (−1µs)               → confirmed=3
```

So a row landing exactly on the boundary is **inside** the window. It is a
rolling wall-clock instant, so two loads a minute apart use slightly
different windows — correct for a "last 30 days" figure. (Pedantry, not a
defect: `30*24h` is 720 hours, which is 30 calendar days ±1 hour across a DST
transition.)

**Complaint rate — both halves probed separately.**

- *A clean campaign still counts toward the denominator.* 49 of the 50 sends
  had no event at all; the denominator was 50, not 1. The `LEFT JOIN` is
  doing what its doc comment claims — an `INNER JOIN` here would have
  reported 1/1 = 100%.
- *A duplicate notification counts once.* The complained recipient carries
  **two** `email_events` rows (distinct `sns_message_id`, same
  `ses_message_id`, both `Complaint` — exactly what an SNS redelivery
  produces, and legal under the `(sns_message_id, recipient)` unique key).
  The numerator was 1, not 2. Two `Delivery` events on a *different* send
  likewise neither entered the numerator nor inflated the denominator via
  the join's fan-out.
- *Queued rows stay out.* Five `status='queued'` rows with NULL
  `ses_message_id` never reached either side.

**The 50-send minimum genuinely suppresses, at exactly the documented
boundary.** With `sent = 49` the response omits `complaint_rate_pct` entirely
and `complaint_rate_high` is false; adding one send (`sent = 50`) makes the
key appear at 2.00% with `complaint_rate_high: true`. `buildWarnings`
(`dashboard.ts`) requires `complaint_rate_pct !== undefined` before emitting
the row, so a small sample renders as *no row*, never as a fabricated 0.00%.

**The two thresholds are independent, and the 0.3% is the right side of the
line.** `dashboardComplaintRateThresholdPct = 0.3` is a package-local `const`
in `admin_dashboard.go` and is compared with a strict `>`; measured at the
boundary, `1/333 = 0.3003%` warns and `1/334 = 0.2994%` does not — matching
PRD §11's "complaint rate under 0.3%". `dashboardComplaintMinSample = 50` is
likewise local. Neither reads the settings table, and nothing in the worker
reads either of them — I grepped: `send_health_complaint_pct` and
`send_health_min_sample` appear **only inside comments** today, because PRD
§6.9's circuit breaker is not implemented yet (`#0124`). So the two numbers
cannot currently be conflated even by accident. See the follow-ups below for
the two things this exposes.

**Inbound mail is honest.** `inbound_mail_unavailable` is hardcoded `true`
with no count field at all, and the UI renders the sentence "Inbound mailto:
unsubscribe processing is not built yet, so this screen cannot report
unprocessed inbound mail" as a non-alert note. There is no zero anywhere on
that row to be misread as "nothing pending."

**`SESSandbox` is safe by default.** `getBool("SES_SANDBOX", true, &errs)` —
absent env var means "assume sandboxed", the harmless direction. The
constructor flag is the only input; the handler makes no AWS call. Flipping
it flipped `ses_sandbox_active` and nothing else.

**Query cost: 8 per load, fixed.** The tracer counted 8 statements —
`StatusCounts`, `Growth30Days`, `interests.ListAll`,
`interests.SubscriberCounts`, `CampaignStore.List` (**2**: the campaign rows
plus one `campaign_interests` fetch for all ids at once),

**No leak.** Scanning the full response body for `@`, `example.test`,

### Follow-ups to file (reported, not filed — CLAUDE.md §9)

1. **The account-wide warning is looser than AWS's own account-wide ceiling.**
   This screen's figure is account-wide, and it warns at 0.3% (PRD §11,
   Gmail/Yahoo). But PRD §6.9 opens with AWS enforcing "a complaint rate under
   **0.1%** across the whole SES account", and crossing it puts the account
   under review and then back into sandbox — taking confirmation emails down
   with it. An account sitting at 0.2% is in AWS-review territory and this
   screen says nothing. The acceptance criterion names 0.3%, so the
   implementation is correct as specified; the criterion may be the thing
   that is wrong. Worth an issue to reconcile §11's 0.3% with §6.9's 0.1% and
   decide whether the dashboard should carry two bands (0.1% AWS / 0.3%
   mailbox-provider).
2. **Two doc comments cite a constant that does not exist.**
   `admin_dashboard.go:50` and `campaign_stats.go:133` both describe
   `send_health_complaint_pct` as living in `worker.go` with a default of
   0.1. It lives nowhere — PRD §6.9's breaker is unbuilt (`#0124`). The
   reasoning is right and worth keeping; the pointer should say "`#0124`,
   not yet implemented" so the next reader does not go looking.
3. **`AccountComplaintRate`'s numerator is not status-filtered.** The
   denominator is `count(DISTINCT s.id) FILTER (WHERE s.status = 'sent')`
   but the numerator filters only on `e.event_type = 'Complaint'`. Today
   only `MarkSent` ever writes a `ses_message_id` (`MarkFailedRow` writes
   none), so a non-`sent` row can never match an event and the asymmetry is
   unreachable — but if that ever changes, a complaint on a `failed` or
   `skipped` row enters the numerator without entering the denominator, and
   a rate above 100% is representable. Adding `AND s.status = 'sent'` to the
   numerator's FILTER is free.
4. **Minor copy nit.** "SES is still in sandbox mode (200 messages/day…)" is
   stated as observed fact, but it is an operator-set env flag with no live
   AWS call behind it. Something like "SES is configured as sandboxed
   (`SES_SANDBOX`)" would not overclaim. The default is the harmless
   direction, so this is polish, not a correctness problem.

None of the four blocks resolution: 1 and 4 are specification/wording, 2 is a
comment, 3 is currently unreachable.
