## Description

Phase 3b/4 of the Outreach design: poll engagement counts for posted
Bluesky/Mastodon posts into a time series, collect mentions/replies/quotes,
and show them in the panel and results view.

## Acceptance criteria

- [ ] Migrations for `outreach_engagement` (`post_id`, `captured_at`, `likes`, `reposts`, `replies`, `quotes`) and `outreach_mentions` (`channel`, unique `remote_id`, nullable `post_id`, `kind`, `author`, `text`, `url`, `created_at`).
- [ ] Background poller: Bluesky `app.bsky.feed.getPosts` (public AppView), Mastodon `GET /api/v1/statuses/{id}`; hourly for 7 days after posting, daily to 30 days, then stop. Mentions: Bluesky `app.bsky.notification.listNotifications`, Mastodon `GET /api/v1/notifications`, every 15 minutes with a stored cursor; tie to a post when replying to/quoting it.
- [ ] Poller is disabled when the channel is not configured, logs (never silently `continue`s) on failure, and stops cleanly on shutdown (CLAUDE.md §5's `#0470` lesson).
- [ ] UI: reactions in panel cells and posts table; a Mentions and replies feed; reaction totals in the all-workshops table. The screen states Mastodon counts are as seen by our instance.
- [ ] Tests against fakes; verified with `ISSUE=0547 scripts/check.sh`.

## Resolution notes

> 🟢 Resolved 2026-10-16 — engagement snapshots and a mentions feed for Bluesky and Mastodon are polled by a Publisher-owned tracker and shown in the panel, results view and all-workshops table, verified against fakes with a full unscoped check.

## Root cause

Outreach (`#0545`) could post to Bluesky and Mastodon but read nothing back:
no engagement counts and no mentions, so the panel and results view could say
what was clicked but not what was liked, reposted, quoted or replied to.

## Fix

Followed the plan's design. `outreach.Tracker` (`internal/outreach/tracker.go`)
polls every 15 minutes: mentions per configured channel, then engagement for
every due post (`EngagementDue`: hourly to 7 days, daily to 30, then stop). The
`Publisher` starts and stops it (`PublisherDeps.Tracker`), so `mountAndServe`
and its 14 test call sites are unchanged. The tracker runs under a context
cancelled by `Stop`, so shutdown does not wait out an HTTP timeout. Migration
`000035` adds `outreach_engagement`, `outreach_mentions` and
`outreach_mention_cursors`. Engagement reaches the SPA through `#0546`'s
existing results endpoints, filled before the ShortLinks early returns, so it
shows for every status except `not_started`.

Divergences from the plan, all small:

- Migration number is `000035` (`000034` was taken by `#0549`).
- `mastodon.GetStatusCounts` does not `PathEscape` the id: the id is assigned
  to `URL.Path`, which the URL encoder escapes once, so escaping it too
  double-encoded (`%252F`). An id that is empty or contains `/ ? # \` is refused
  before any request instead.
- `mastodon.Notification` gained a `HasStatus` bool so the caller can tell a
  notification with no status from one with empty fields.
- `roundTrip` kept its signature and delegates to a new `roundTripTo` (base URL
  plus extra headers); `authed` delegates to `authedWith`. Fewer call sites
  touched than changing `roundTrip` in place.
- The SPA grew one thin component, `OutreachMentions.svelte`, shared by the
  per-workshop and all-workshops views. The channel `reactions` field is
  returned by the API but no per-channel table exists yet to show it (`#0552`
  is open); the plan said to add the column only if that table exists.
- Mastodon `quotes_count`/quote payload shapes and Bluesky `listNotifications`
  shapes are from published API docs, not observed.

### Decisions (so the implementer does not have to make them)

1. **One new background type, `outreach.Tracker`, with its own `Run`/`Stop`,
   but started and stopped by the `Publisher`, not by `mountAndServe`.**
   `#0545` already adds a `*outreach.Publisher` parameter to `mountAndServe`
   and touches all 14 `cmd/opencircuit/*_test.go` call sites; a second
   parameter would touch them all again and add a second close-timeout
   `var`. So `PublisherDeps` gains `Tracker *Tracker` (nil allowed):
   `Publisher.Run` does `if p.tracker != nil { go p.tracker.Run(ctx) }`
   before its own loop, and `Publisher.Stop` stops its own loop and then
   calls `p.tracker.Stop(ctx)` within the same budget
   (`outreachPublisherCloseTimeout`), returning the first error. `Tracker` is
   still its own type with its own tests, so neither loop's cadence leaks into
   the other (the publisher polls every 15 s; the tracker every 15 min).
   Unlike the publisher, a tracker pass **can be cut short**: it runs under a
   context cancelled when `Stop` is called, because nothing it writes is
   half-done in a harmful way (inserts are idempotent and the cursor is
   written only after the work it covers). So `Stop` returns promptly instead
   of waiting out a 15 s HTTP timeout.
2. **Cadence.** The tracker ticks every **15 minutes** (`TrackerDeps.Interval`,
   default `15*time.Minute`; tests call the unexported `pass` directly) and
   runs one pass immediately on `Run`. Each pass does (a) mentions for every
   configured channel, then (b) engagement for every **due** post. "Due" is a
   pure function, `EngagementDue(postedAt time.Time, last *time.Time, now
   time.Time) bool`:
   - age = `now − postedAt`; age ≥ 30 days → false (stop);
   - `last == nil` → true;
   - age < 7 days → `now − *last ≥ 55*time.Minute` (hourly);
   - otherwise → `now − *last ≥ 23*time.Hour + 55*time.Minute` (daily).
   The 5-minute slack keeps a 15-minute tick from drifting every capture to
   75 minutes. `last` is `max(latest captured_at in the DB, the tracker's
   in-memory last attempt for that post)` — the in-memory map
   (`attempted map[int64]time.Time`, guarded by the single `Run` goroutine,
   no mutex needed if only `pass` touches it) is what keeps a failing or
   deleted remote post from being re-fetched and re-logged every 15 minutes.
   It is lost on restart, which costs one extra attempt — acceptable.
3. **What is tracked.** Posts with `status = 'posted' AND remote_id IS NOT
   NULL AND posted_at > now() − interval '30 days'` on channel `bluesky` or
   `mastodon`, and only for a channel whose client is configured
   (`Enabled()`). A post marked posted by hand (`#0544`'s Mark posted) has no
   `remote_id` and is never tracked — say so in `docs/` (step 9), not in a
   UI apology.
4. **Insert a snapshot on every successful capture**, even when the counts
   are unchanged: the latest `captured_at` is what step 2's due check reads.
   At most ~190 rows per post (7×24 + 23); nothing to prune.
5. **A remote post that is gone** (Bluesky `getPosts` omits it; Mastodon
   404) writes no row, logs one `Info` line naming the post id and channel,
   and is marked in the in-memory `attempted` map so it is retried only at
   its next due slot. No schema for it.
6. **Mentions: the stored "cursor" is per channel, in a new tiny table
   `outreach_mention_cursors`** — not `settings` (seeded keys there are
   guarded by `internal/handlers`' `settings_test.go`, and these are machine
   state, not admin settings). The two platforms page differently:
   - **Bluesky** `listNotifications` pages *backwards* (newest first; its
     `cursor` walks to older pages), so a stored API cursor is useless for
     "what is new". Store a **high-water mark**: the `indexedAt` (RFC 3339
     string) of the newest notification seen. Each pass: fetch page 1 with no
     cursor; process items; stop when an item's `indexedAt` is **strictly
     older** than the mark (equal ones are re-processed; the unique key
     dedupes) or the page has no `cursor`; else follow `cursor`, at most
     **10 pages**. With no mark yet, the floor is `now − 30 days`. Write the
     new mark (the newest `indexedAt` from page 1) **only after the whole
     walk succeeds**, so a failure mid-walk is retried from the top next
     pass.
   - **Mastodon** `GET /api/v1/notifications` pages forward with `min_id`.
     Store the **newest notification `id`** seen. Each pass: request
     `min_id=<cursor>&limit=80&types[]=mention&types[]=quote`; the array is
     newest first, so the new cursor is element 0's `id`; save it **after each
     page** (forward paging is safe to save incrementally); repeat while a
     page returns 80 items, at most **10 pages**. With no cursor yet: one
     request without `min_id`, keep only items with `created_at ≥ now − 30
     days`, save element 0's `id`. An empty response with no cursor saves
     nothing. (`since_id` is wrong here: with more than one page of new
     notifications it returns the newest page and silently skips the gap.)
   Hitting the 10-page cap logs a `Warn` ("older notifications skipped").
7. **Tying a mention to a post** (`post_id`, nullable): build
   `map[remote_id]post_id` from `outreach_posts WHERE channel = $1 AND
   remote_id IS NOT NULL` once per pass per channel.
   - Bluesky `reason` is the kind (`mention` | `reply` | `quote`; ignore any
     other reason with a `Debug` line). Reply → `record.reply.parent.uri`,
     falling back to `record.reply.root.uri` (a reply deeper in a thread under
     our post still belongs to it). Quote → `record.embed` with `$type`
     `app.bsky.embed.record` → `embed.record.uri`, or
     `app.bsky.embed.recordWithMedia` → `embed.record.record.uri`. Fallback
     for both: `reasonSubject`. A mention (no reply/quote target of ours) →
     `post_id NULL`.
   - Mastodon `type` `quote` → kind `quote`, target
     `status.quote.quoted_status.id` (Mastodon 4.5's quote object; may be
     absent or `null` when the quote is pending/revoked → `post_id NULL`).
     `type` `mention` with `status.in_reply_to_id` matching one of our
     `remote_id`s → kind `reply`; otherwise kind `mention`. (On Mastodon a
     reply to us arrives as a `mention` notification.) Our `remote_id` for a
     Mastodon post is the status `id` on our own instance (`#0545`), which is
     exactly what `in_reply_to_id` and `quoted_status.id` carry there.
   - Mentions with no tie are **kept** (`post_id NULL`): they are shown in the
     all-workshops feed.
8. **`remote_id` stays globally unique, as the criterion says**: Bluesky
   stores the mention post's `at://` URI; Mastodon stores the status `uri`
   (its ActivityPub id, an `https://` URL) — not the notification id and not
   the instance-local status id. The two never collide, and the same status
   reached twice (a reply that also quotes) inserts once
   (`ON CONFLICT (remote_id) DO NOTHING`).
9. **Stored mention fields**: `author` = `"@" + handle` (Bluesky
   `author.handle`; Mastodon `account.acct`, which is `user@domain` for remote
   accounts); `text` = plain text capped at 1,000 runes (Bluesky
   `record.text`; Mastodon `status.content` is **HTML** → plain text with
   `golang.org/x/net/html`, already a dependency (`internal/seo` uses it):
   `<br>` → `\n`, a paragraph boundary → `\n\n`, text nodes concatenated, no
   regex tag-stripping); `url` = Bluesky
   `https://bsky.app/profile/<author.handle>/post/<rkey>` (rkey = last path
   segment of the URI), Mastodon `status.url` falling back to `status.uri`,
   **stored only if it parses as an absolute `https` URL**, else `NULL`;
   `created_at` = Bluesky `record.createdAt` (fallback `indexedAt`),
   Mastodon `status.created_at`. These are third parties' public posts shown
   only to admins; no audit rows (the tracker has no actor), only `slog`.
10. **Configuration: no new environment variable.** Each half of the tracker
    is on exactly when that channel's client is (`#0545`'s `New` returns nil
    when unconfigured). The Bluesky AppView base is a client field defaulting
    to the constant `DefaultAppViewURL = "https://public.api.bsky.app"`,
    overridable only in code (`(*Client).SetAppViewURL(u string) error`, used
    by tests) — an env var would add `.env.example` / `docs/configuration.md`
    / config-parity surface for something no deploy changes. **The Mastodon
    token now needs `read:statuses` and `read:notifications`** besides
    `write:statuses`: update the `.env.example` comment and the
    `MASTODON_TOKEN` row in `docs/configuration.md` (both written by `#0545`).
    A token without the read scopes gets 403s, which the tracker logs at
    `Error` every pass naming the needed scope — never silently.
11. **Engagement reaches the UI through `#0546`'s results endpoints**, which
    the panel already fetches; no new route. Engagement comes from our own
    database, so it is filled in **for every results status except
    `not_started`** — including `not_configured`, `unreachable`, `rejected`
    — i.e. before the handler's early returns on `h.stats == nil` and on a
    stats error.

### Step 5 — `internal/outreach/tracker.go`

```go
type TrackerDeps struct {
    Store    *Store
    Bluesky  *bluesky.Client  // nil → Bluesky half off
    Mastodon *mastodon.Client // nil → Mastodon half off
    Interval time.Duration    // default 15m
    Now      func() time.Time // default time.Now; tests pin it
    Log      *slog.Logger
}
func NewTracker(d TrackerDeps) *Tracker
func (t *Tracker) Run(ctx context.Context)
func (t *Tracker) Stop(ctx context.Context) error
```

Same `stopCh`/`doneCh`/`stopOnce`/`running` shape as `#0545`'s `Publisher`,
plus a `context.WithCancel` derived from `Run`'s ctx and cancelled by
`Stop` (decision 1). On `Run`, log once at `Info` which halves are on
(`"outreach tracker: bluesky tracking off (not configured)"` etc.); if
**both** are off, log that and return immediately (closing `doneCh`) — no
idle ticker. Each pass:

1. Per configured channel: mentions (decision 6/7) → `InsertMention` for each
   kept item; count inserted vs. duplicate.
2. `EngagementTargets(configured channels)` → keep those with
   `EngagementDue(postedAt, max(LastCaptured, attempted[id]), now)`. Bluesky:
   one `GetPostCounts` for all due URIs (the client batches); Mastodon: one
   `GetStatusCounts` per due post. Record `attempted[id] = now` for every
   attempt; `RecordEngagement` for each success.
3. One `Info` summary line per pass with counts (mentions inserted per
   channel, snapshots written, failures) — the pass is never silent.

**Logging — no silent decline path** (CLAUDE.md §5's `#0470` lesson):

| Path | Level |
|---|---|
| Channel not configured (at `Run`) | Info, once |
| Request failed (network, 5xx, 429, auth, scope) | Error, with channel and op; Mastodon 403 names `read:notifications`/`read:statuses` |
| Remote post gone (decision 5) | Info, per attempt |
| Notification skipped (unknown reason/type, no status, bad JSON) | Debug, with remote id |
| Notification older than the floor/mark ends the walk | Debug |
| 10-page cap hit | Warn |
| Store error | Error; abort that half of the pass, keep the cursor unchanged |
| Nothing due, no new mentions | covered by the per-pass Info summary |

A failure in one channel never stops the other channel's half or the
engagement half.
