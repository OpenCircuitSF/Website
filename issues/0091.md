# 0091 — Every DB-backed test builds its own connection pool, and the suite no longer finishes

| | |
|---|---|
| **Status** | open |
| **Module** | infra / testdb |
| **Platform** | All |
| **Phase** | 3 — Mailing list capture |
| **First seen** | 2026-08-19 |

## Description

`go test ./internal/subscribers/... -count=1` takes **159.6 s** on an idle machine. It ran in roughly 3 s earlier in the same session. Every test costs about the same ~5 s, so this is fixed per-test setup, not one slow test:

```
TestSetInterests_ReplacesFully              7.20s
TestGetByID_Success                         5.72s
TestDB_ManageTokenUniqueConstraint          5.62s
TestList_FiltersByStatus                    5.55s
TestList_FiltersByInterest                  5.51s
TestMarkBouncedAndMarkComplained            5.21s
TestUnsubscribe_ComplainedNeverAutoResubscribes  5.09s
…
```

## Root cause

`testPool(t)` (`internal/subscribers/store_test.go:20`) is called by **50 tests**, and each call:

1. creates a brand-new `pgxpool.Pool` via `pgxpool.New`
2. pings it
3. runs `TRUNCATE subscriber_interests, subscribers RESTART IDENTITY CASCADE`
4. registers a cleanup that truncates **again** and closes the pool

So the package builds and tears down 50 connection pools and issues 100 `TRUNCATE … CASCADE` statements, each taking a heavy table lock. The package already serialises behind `testdb.Lock()` in `TestMain`, so there is no concurrency to justify a pool per test.

## Why this is worth fixing rather than tolerating

`CLAUDE.md` §5's verification contract gates every issue on running the full suite, and reviewers are told to run it repeatedly — before a change, after, and once per mutation. At ~160 s for one package, a three-mutation review pays eight minutes of pure waiting, and that cost lands on every future issue touching this package.

It is the same family as `#0084`: test infrastructure that erodes the contract it is supposed to serve. `#0084` fixed load-sensitivity; this is the cost side of the same problem.

## Acceptance criteria

- [ ] One pool per package, created once (`TestMain` already holds the advisory lock and is the natural home), shared by every test
- [ ] Per-test isolation preserved — tests must still start from a clean table state and remain order-independent. Prove it: run with `-count=2` and with `-shuffle=on`
- [ ] Truncate once per test rather than twice, unless the second is doing something the first cannot
- [ ] **Measure before and after** and record both figures. The target is seconds, not minutes
- [ ] Check whether `internal/handlers`, `internal/audit`, `internal/interests` and `internal/auth` share the same per-test-pool pattern; fix or file them too, and say which
- [ ] `go test ./... -count=1` green with `TEST_DATABASE_URL` exported, zero skips

## Notes

Do **not** trade isolation for speed. Every test starting from a known-clean state is what makes this suite trustworthy, and `#0025`'s laundering bug was caught by exactly these tests. A shared pool with per-test truncation keeps that property; sharing *state* between tests would not.

Watch for one trap: with a shared pool, a test that leaks a transaction or a `FOR UPDATE` lock will now block its successors rather than dying with its own pool. That is arguably better — it surfaces a real defect — but it will look like a hang, so make the failure legible.

Note the earlier 52 s reading for `internal/db` in this session was **not** this defect: that was contention with a concurrently running full-suite invocation holding the advisory lock. `internal/db` is 1.08 s on an idle machine.

## Escalation observed 2026-08-19

A full-suite run during demo verification did not merely run slow — it **hard-failed**:

```
*** Test killed with quit: ran too long (11m0s).
FAIL	github.com/brennanMKE/OpenCircuitSF/internal/subscribers	660.007s
```

`go test` defaults to a 10-minute per-package timeout, and this package now exceeds
it under any concurrent database load. So this is no longer a slowness complaint:
a plain `go test ./...` on a busy machine **fails**, and the panic dump it prints
looks like a product bug rather than a timeout. Anyone bisecting or running CI hits
this. That raises the priority — the fix (a shared pool + per-test isolation instead
of 50 pools and 100 `TRUNCATE ... RESTART IDENTITY CASCADE` statements) is unchanged.

## Scope broadened 2026-08-19 — this is not one package

`#0079`/`#0084`/`#0087`'s reviewer measured the same defect next door:

> every `internal/handlers` test now takes 4–10 s (package total **622 s**), so the
> pool defect is not confined to `internal/subscribers`.

That reframes the issue. Two of the largest DB-backed packages each now exceed Go's
10-minute default per-package timeout, so **`go test ./...` cannot complete at all**.
Every consequence follows from that:

- CI cannot run the suite, and a timeout prints a register dump that reads like a
  product crash rather than a slow test.
- Every reviewer and implementer now either waits ~20 minutes or skips the full run.
  Both of the last two reviews explicitly declined to run it — with sound reasoning,
  which is exactly the problem: the project's verification contract in `CLAUDE.md` §5
  requires a full run with zero skips, and that contract is currently unsatisfiable.
- `#0084` exists because load-sensitive tests flake. This defect *is* the load.

**Fix the shared cause, not one package.** The per-test pattern — a fresh `pgxpool`
plus two `TRUNCATE ... RESTART IDENTITY CASCADE` statements per test — wants to become
a package-level pool created once and a cheaper per-test isolation strategy. Whatever
shape that takes belongs in `internal/testdb`, which already owns the cross-process
advisory lock, so both packages and any future one inherit it.

## First attempt measured 2026-08-19 — partial, preserved on a branch

A subagent rewrote 19 test files to share one pool per package, then stopped
mid-flight without committing, without a work log, and with its database still up. Its
work is preserved at `550aaf6` on branch `worktree-agent-ad3d8041624f3ded6` — **it is
a real improvement and should be built on, not restarted.**

Its approach: `internal/testdb` gains `Connect()`, each package opens one pool in
`TestMain`, and `testPool` drops both the per-test `pgxpool.New` and the cleanup-side
truncate, keeping only the entry truncate.

Measured clean by the orchestrator, one package at a time on an idle machine (the
agent's own numbers were polluted — its runs and mine were serialising on
`testdb.Lock()` against the same database):

| Package | Before | After | |
|---|---|---|---|
| `internal/subscribers` | 159.6 s | **71.9 s** | ok |
| `internal/handlers` | 622 s | **274.1 s** | **FAIL** |

```
--- FAIL: TestAdminUsers_NonAdminForbidden (5.01s)
    users_test.go:63: truncate tables: timeout: context deadline exceeded
```

### What this measurement establishes

**Sharing the pool was not the main win available, and the remaining cost is the
per-test `TRUNCATE ... RESTART IDENTITY CASCADE`.** Removing 50 pool constructions and
half the truncates bought 2.2×; the surviving truncate still costs seconds per test.
Any fix that keeps a per-test full-table truncate will land in roughly this same place.

The new failure is the same defect from the other end: `truncate tables` blew a **5 s**
context deadline. That is one of the fixed 5 s deadlines `#0084` is about, so `#0084`
and this issue meet here — a truncate that got slower under contention is exactly what
a fixed deadline turns into a red test rather than a slow one.

**Do not simply raise the deadline.** That converts a failing symptom back into the
slowness this issue exists to remove.
