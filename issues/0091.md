## Root cause

`testPool(t)` (`internal/subscribers/store_test.go:20`) is called by **50 tests**, and each call:

1. creates a brand-new `pgxpool.Pool` via `pgxpool.New`
2. pings it
3. runs `TRUNCATE subscriber_interests, subscribers RESTART IDENTITY CASCADE`
4. registers a cleanup that truncates **again** and closes the pool

So the package builds and tears down 50 connection pools and issues 100 `TRUNCATE … CASCADE` statements, each taking a heavy table lock. The package already serialises behind `testdb.Lock()` in `TestMain`, so there is no concurrency to justify a pool per test.

## Why this is worth fixing rather than tolerating

`CLAUDE.md` §5's verification contract gates every issue on running the full suite, and reviewers are told to run it repeatedly — before a change, after, and once per mutation. At ~160 s for one package, a three-mutation review pays eight minutes of pure waiting, and that cost lands on every future issue touching this package.

It is the same family as `#0084`: test infrastructure that erodes the contract it is supposed to serve. `#0084` fixed load-sensitivity; this is the cost side of the same problem.

## Acceptance criteria

- [ ] One pool per package, created once (`TestMain` already holds the advisory lock and is the natural home), shared by every test
- [ ] Per-test isolation preserved — tests must still start from a clean table state and remain order-independent. Prove it: run with `-count=2` and with `-shuffle=on`
- [ ] Truncate once per test rather than twice, unless the second is doing something the first cannot
- [ ] **Measure before and after** and record both figures. The target is seconds, not minutes
- [ ] Check whether `internal/handlers`, `internal/audit`, `internal/interests` and `internal/auth` share the same per-test-pool pattern; fix or file them too, and say which
- [ ] `go test ./... -count=1` green with `TEST_DATABASE_URL` exported, zero skips

## Notes

Do **not** trade isolation for speed. Every test starting from a known-clean state is what makes this suite trustworthy, and `#0025`'s laundering bug was caught by exactly these tests. A shared pool with per-test truncation keeps that property; sharing *state* between tests would not.

Watch for one trap: with a shared pool, a test that leaks a transaction or a `FOR UPDATE` lock will now block its successors rather than dying with its own pool. That is arguably better — it surfaces a real defect — but it will look like a hang, so make the failure legible.

Note the earlier 52 s reading for `internal/db` in this session was **not** this defect: that was contention with a concurrently running full-suite invocation holding the advisory lock. `internal/db` is 1.08 s on an idle machine.

### What this measurement establishes

**Sharing the pool was not the main win available, and the remaining cost is the
per-test `TRUNCATE ... RESTART IDENTITY CASCADE`.** Removing 50 pool constructions and
half the truncates bought 2.2×; the surviving truncate still costs seconds per test.
Any fix that keeps a per-test full-table truncate will land in roughly this same place.

The new failure is the same defect from the other end: `truncate tables` blew a **5 s**
context deadline. That is one of the fixed 5 s deadlines `#0084` is about, so `#0084`
and this issue meet here — a truncate that got slower under contention is exactly what
a fixed deadline turns into a red test rather than a slow one.

**Do not simply raise the deadline.** That converts a failing symptom back into the
slowness this issue exists to remove.

### Strategy: unique data per test, truncation only where a test needs an empty table

The measurement recorded above established that the per-test
`TRUNCATE ... RESTART IDENTITY CASCADE` was the real cost, not pool construction —
sharing the pool alone bought only 2.2× and left `internal/handlers` failing.

The fix is surgical rather than uniform, which is the part worth remembering:

- **Truncation removed** from the subscriber-facing helpers (`internal/subscribers`,
  `internal/handlers`'s `journey_testutil_test.go` and `subscribe_test.go`). Those
  tests now seed nanosecond-unique rows via `uniqueEmail(t)` / `uniqueRawToken(t)`, so
  other tests' rows are simply irrelevant to them.
- **Truncation kept** where a test genuinely asserts over a whole table —
  `internal/handlers`'s `audit_log`/`users`/`sessions` truncate still runs, which is
  what keeps `audit_test.go`'s `body.Total != 3` sound. `internal/auth` still truncates
  for the same reason.
- `internal/interests` never truncated and still doesn't: `migrations/000009` seeds the
  taxonomy, and its assertions are scoped by explicit id.

**What was given up:** isolation is no longer enforced by the database. A test that
asserts a *global* row count over `subscribers` would now be unsound, and nothing stops
someone writing one. That risk is what `TestIsolation_UniqueDataNeverCollides` exists
to catch, and it is why the truncating helpers were left in place rather than removed
everywhere for consistency.

### Attacking the isolation strategy — what was checked

Every shape that could depend on an empty table was searched for independently,
not taken from the work log:

- **Whole-table `count(*)` / exact-length assertions.** `TestList_FiltersByInterest`
  and `TestList_FiltersByStatus` were rewritten to "contains mine, excludes my
  known-excluded row" rather than an exact count. `TestStatusCounts_*` asserts a
  **delta** (`after == before+1`), not an absolute. `TestList_Searches*` scopes by
  a nanosecond-unique search term so `total == 1` is genuinely global-safe.
  `TestList_PaginationBoundsAndOrdering` asserts `total >= 3`, not `== 3`.
  Every surviving `count(*)` in a de-truncated package filters by an id or a
  unique email. **No unsound assertion found.**
- **`ORDER BY id`/`LIMIT 1` with ids no longer restarting.** `store.List` orders
  `created_at DESC, id DESC` — the id tiebreak keeps ordering total, so
  `page1[0].ID == ids[2]` is sound with rows accumulating.
- **`RESTART IDENTITY` having been load-bearing.** No test depends on a
  predictable sequence value: a search for hardcoded id literals in DB-backed
  tests found only `internal/devstore` and `internal/middleware`'s in-memory
  `bearer`/`devauth` tests, neither of which touches Postgres. Note also that
  each package's `TestMain` still does one `TRUNCATE ... RESTART IDENTITY`, so
  sequences do start at 1 per package run; `-count=2` is what actually exercises
  the non-restarted case, and it is green.
- **`t.Parallel()`.** There is **not one** `t.Parallel()` anywhere in the
  repository. Every test in every DB-backed package runs strictly sequentially,
  which is what makes the remaining "last row wins" reads sound.

### A soundness improvement the work log does not claim

Dropping the per-test truncate **removed** a hazard rather than adding one. The
deleted `truncateSubscribeTables` comment records why `audit_log` had to be
truncated alongside `subscribers`: with `RESTART IDENTITY` firing per test,
subscriber ids were **reused** across tests, so a later test's
`auditSignupCount(target_id=1)` could match an earlier test's id-1 subscriber.
Now that ids advance monotonically within a package run, that class of false
match is structurally impossible. Removing `audit_log` from that helper is
correct, not merely tolerable.

### Does `TestIsolation_UniqueDataNeverCollides` actually test isolation?

**The mutation reproduces exactly.** Control, unmutated, `-count=2`: `ok 1.176 s`.
`uniqueEmail` mutated to a constant, `-count=2`:

```
--- FAIL: TestIsolation_UniqueDataNeverCollides (0.00s)
    store_test.go:1545: Create: subscribers: email already exists
```

Two things the commit did not establish, established here:

1. **The `count == 1` assertion is live, not dead code behind the `UNIQUE`
   index.** Dropping `subscribers_email_key` in the private review database and
   re-running the mutated test produced a different, genuine failure —
   `subscribers table has 2 rows for the email this test just seeded, want 1` —
   so the assertion catches a collision on its own merits when the constraint is
   not there to catch it first. The constraint was restored immediately after.
   (A first attempt with an upper-case constant failed for the wrong reason,
   `0 rows`, because `Create` lower-cases the address; the mutation was redone
   lower-case to be faithful.)
2. **At `-count=1` in isolation the mutated test passes** (`ok 1.580 s`). It only
   fires on the repeat, or when another test in the package has already consumed
   the constant. That is the correct behaviour, but it means the test is a
   **canary on the generator, not a detector of cross-test visibility**.

**The verdict on the test, stated plainly:** it verifies that `uniqueEmail` still
produces distinct values. It does **not**, and cannot, detect the failure mode
the work log attributes to it. The work log says:

> A test that asserts a *global* row count over `subscribers` would now be
> unsound, and nothing stops someone writing one. That risk is what
> `TestIsolation_UniqueDataNeverCollides` exists to catch

That is **overstated**. Nothing in this test observes other tests' assertions; if
someone adds `SELECT count(*) FROM subscribers` tomorrow, this test stays green
while the new test rots. The honest description is "a canary that fails loudly if
the uniqueness mechanism holding up isolation ever stops being unique" — which is
worth having, and is a real assertion rather than one of this project's
assert-nothing tests, but it is narrower than advertised. Recommend correcting
that one sentence; no code change is needed.

### Newly fragile, though correct today

`internal/audit`'s three `SELECT ... FROM audit_log ORDER BY id DESC LIMIT 1`
read-backs changed meaning: they used to read *the only* row in a freshly
truncated table, and now read *the newest* row in an accumulating one. They are
sound because each test writes exactly one audit row immediately before reading
and nothing runs in parallel — but the invariant is now implicit. A future test
that adds a second `Write`, or a `t.Parallel()`, breaks them silently. Worth a
comment on those queries at some point; not a defect now.
