# 0060 — Handle GDPR erasure requests

| | |
|---|---|
| **Status** | open |
| **Module** | subscribers / admin |
| **Platform** | All |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-08-18 |

## Description

A hard delete that removes a subscriber's personal data while keeping the address suppressed so it cannot silently return.

## Acceptance criteria

- [ ] `DELETE /admin/subscribers/{id}` hard-deletes the subscriber and cascades `subscriber_interests`
- [ ] A `suppressions` row with reason `manual` is left in place so the address is not re-added
- [ ] `email_sends` rows are anonymized rather than deleted, preserving campaign counts
- [ ] `email_events` retains the raw payload for deliverability forensics but the linkage is severed
- [ ] The action requires a typed confirmation and is audited with the requester's identity
- [ ] A data-export-on-request path exists (reuse #0059 filtered to one subscriber)
- [ ] Privacy policy documents what is retained after erasure and why
- [ ] Tests confirm the subscriber is gone, the suppression remains, and counts are intact

## Notes

PRD §11. The tension here is real: erasure must be genuine, but keeping a suppression entry is what prevents the address being re-added by a later import or signup — which is itself a privacy protection. Documenting that in the privacy policy is what makes it defensible.

Anonymizing rather than deleting `email_sends` preserves the historical campaign metrics that would otherwise silently change.

## Implementation notes

**Erasure semantics — hard delete, not anonymize-in-place.** `subscribers.Store.Erase`
(`internal/subscribers/erase.go`) runs one transaction: `SELECT ... FOR UPDATE`
locks the subscriber, refuses (`ErrHasPendingSends`, 409) if any `email_sends`
row for it is `queued`/`sending`, anonymizes that subscriber's `email_sends`
rows in place, adds an idempotent `manual`-reason `suppressions` row for the
address, then `DELETE FROM subscribers`. The row and its `subscriber_interests`
rows are genuinely gone — this is not a soft delete or a status flag.

**Resolving the `complained`-never-auto-resubscribes tension (CLAUDE.md §9).**
The two are aligned, not in conflict, because `suppressions` already has no
foreign key to `subscribers` (`suppressions.go`'s package doc comment
anticipated exactly this issue) — a suppression outlives the row it was
written for. Erase always adds a `manual` row, on top of whatever the address
already carries (a `complaint` row from #0038's SES ingestion survives
untouched). A previously-complained address that gets erased ends up with
**two** independent suppression reasons, never fewer. Proved by execution:
`TestErase_PreservesAndAddsToExistingSuppressions` seeds a `complaint` row,
erases, and asserts both rows survive and `IsSuppressed` is true;
`TestAdminSubscribers_Erase_ThenAddressStaysBlockedFromResubscribing` goes
further and drives the real public `POST /api/subscribe` handler (with a real
`SuppressionStore`, not the `NoSuppressions` stub) against the erased address
afterward — 202 (uniform), no new `subscribers` row.

**What survives per table:**
| Table | After erasure |
|---|---|
| `subscribers` | row deleted |
| `subscriber_interests` | rows deleted (CASCADE via `subscribers(id)`, migration 000010 — unchanged) |
| `suppressions` | a `manual` row added (idempotent); any pre-existing rows (any reason) untouched |
| `email_sends` | rows survive, `email` overwritten with a per-row `erased-<send-id>@erased.invalid` placeholder, `subscriber_id` set NULL |
| `email_events` | untouched — no FK to `subscribers` ever existed; forensics rely on the raw payload/`recipient`, and the join chain back to a name is severed once `email_sends.email` is anonymized |
| `audit_log` | a new `subscriber.erased` row; existing rows for this subscriber are never touched (append-only) |

**Migration change (greenfield, edited in place per CLAUDE.md §1).**
`migrations/000017_create_campaigns.up.sql`'s `email_sends.subscriber_id` FK
changed from `NOT NULL ... ON DELETE CASCADE` to nullable `... ON DELETE SET
NULL`. The old CASCADE would have destroyed exactly the rows this issue's
acceptance criteria require preserving. `docs/database.md`'s row for
`000017` was updated to match; `PRD.md` §6.2's schema block was left
as-is (the one-directional migrations→PRD parity guard,
`internal/db/prd_index_parity_test.go`, only checks column names/indexes,
never nullability or `ON DELETE` behavior, and still passes).

**Why a pending/in-flight send blocks erasure.** `internal/mailing.AudienceStore.RecheckEligibleTx`
(`audience.go`) INNER JOINs `email_sends` to `subscribers` on `subscriber_id`
immediately before a send. A row whose `subscriber_id` has gone NULL (or
whose `subscribers` row is gone) matches neither side of that join, so it
would never reappear in either its `recipients` or `skipped` return — and
`MarkSkippedTx` is only ever called on rows that function returns. Erasing a
subscriber with a queued/sending row would leave it stuck at `queued`
forever with no code path to clear it. `Erase` refuses instead
(`ErrHasPendingSends`, mapped to 409) rather than reaching into
`internal/mailing` to fix that join — reported below as a follow-up, not
built here (out of this issue's `internal/subscribers`/`internal/handlers`
scope).

**Typed confirmation.** `DELETE /admin/subscribers/{id}` requires a JSON body
`{"confirm_email": "<address>"}` matching (case/whitespace-insensitively)
the target subscriber's own address — the "type the resource's name"
pattern, mirroring #0047's `confirm_count` reasoning for campaign sends. The
handler loads the subscriber and compares BEFORE calling `Erase`, so a
mismatched confirmation mutates nothing.

**Audit.** New `audit.ActionSubscriberErased` (`subscriber.erased`).
`TargetID` is the erased subscriber's former id — `audit_log.target_id`
carries no FK to `subscribers`, so the row is never orphaned by the delete
it records. Metadata: `email`, `previous_status`, `interests_removed`,
`email_sends_anonymized`, `suppression_reason` (always `"manual"`),
`suppression_preexisted`. Deliberately omits `signup_ip`/`signup_user_agent`/
UTM fields/tokens — the audit row proves the action happened and lets an
operator reconstruct its scope, not become a second plaintext copy of what
was just erased.

**Data-export-on-request.** Reuses #0059 as specified: `GET
/admin/subscribers/export?q=<email>` — `StreamExport`'s `Query` filter is
already a case-insensitive substring match against `email`, so the exact
address returns exactly one row. No new export code was written; the
`Erase` handler's doc comment documents this reuse explicitly.

**Privacy policy.** Already documents this design precisely
(`web/src/views/PrivacyPolicy.svelte`'s "Erasure" paragraph, written ahead of
this issue landing — its own comments cite `#0060` by number): the
permanent suppression entry, anonymized send-history rows, and raw
deliverability events "kept without the link back to your identity." No
change needed.

**Admin UI.** Not built in this pass — matches #0059's own sibling
precedent (that issue also shipped API-only, its Gotchas explicitly
deferring a UI affordance to "whichever issue/agent owns that screen
next"). The acceptance criteria are phrased at the API level
(`DELETE /admin/subscribers/{id}`); reported as a follow-up below.

**Files changed:** `migrations/000017_create_campaigns.up.sql`,
`docs/database.md`, `internal/subscribers/erase.go` (new),
`internal/subscribers/erase_test.go` (new), `internal/audit/actions.go`,
`internal/handlers/admin_subscribers.go`, `internal/handlers/admin_subscribers_test.go`
(mux/case-table wiring only), `internal/handlers/admin_subscribers_erase_test.go`
(new), `cmd/opencircuit/main.go`.

**Worth filing (reported, not filed — CLAUDE.md §9):**
1. `internal/mailing.AudienceStore.RecheckEligibleTx`'s `INNER JOIN subscribers`
   means a send row whose subscriber has been erased (or, in principle, any
   row whose `subscriber_id` is ever NULL) is silently invisible to the
   recheck rather than explicitly skipped — this issue's `Erase` works
   around it by refusing to erase while a send is pending, but the
   underlying join is still a latent trap for any future code path that
   might leave `email_sends.subscriber_id` NULL on a `queued` row.
2. No admin-console UI (button + confirmation modal) exists yet for either
   `DELETE /admin/subscribers/{id}` or #0059's export — both are reachable
   only by direct API call today.

### The property that matters most — verified end to end, including the `complained` case

**An erased address cannot re-subscribe into a weaker state.** Driven through
the real public `POST /api/subscribe` with a real `*subscribers.SuppressionStore`
(not the `NoSuppressions` stub), against the same database:

```
erase response: {"erased":true,...,"previous_status":"active",...}
re-subscribe after erasure: status=202 body={"message":"Check your email to confirm."}
no subscribers row exists for the address (checked by email, not just by id)
```

**The `complained` probe (CLAUDE.md §9) — the design's central claim, proved.**
Seeded a subscriber at `status='complained'` with a `complaint` suppression row
(the exact state `#0038`'s SES ingestion leaves), erased it, then re-subscribed:

```
BEFORE erase: status=complained, suppression reasons=[complaint]
AFTER  erase: suppression reasons=[complaint manual]
re-subscribe after erasure: status=202, no subscribers row created
```

I pushed one step past the shipped test to check the two reasons are genuinely
*independent* rather than one masking the other: removing the `manual` row
afterwards left `IsSuppressed` **true** on the surviving `complaint` row alone,
and a further re-subscribe still created no row. So an erased-while-complained
address ends with two orphan-safe blocking reasons, and the complaint one is
load-bearing on its own. §9's rule is preserved, not merely not-violated.

### The 409 refusal, and the check-to-delete window — no race

`Erase` takes `SELECT … FOR UPDATE` on the `subscribers` row **before** the
pending-send `EXISTS` check and holds it through the `DELETE`, all in one
transaction. I verified by execution that this genuinely closes the window
rather than merely looking like it does. Transaction A held the row exactly as
`Erase` does; transaction B then attempted the send worker's materializing
`INSERT INTO email_sends (campaign_id, subscriber_id, email, status)`:

```
OK: the concurrent INSERT blocked on Erase's SELECT ... FOR UPDATE for >1.5s
    (the FK's implicit FOR KEY SHARE on the parent conflicts with FOR UPDATE)
after Erase committed, the concurrent INSERT returned:
    ERROR: insert or update on table "email_sends" violates foreign key
    constraint "email_sends_subscriber_id_fkey" (SQLSTATE 23503)
ghost email_sends rows for the erased address after the race: 0
```

So a send cannot be materialized between the check and the delete: it blocks,
and is then rejected by the FK. Ordering the other way, B commits first and A's
`FOR UPDATE` waits, then sees the new `queued` row in a fresh read-committed
statement and returns `ErrHasPendingSends` → 409. The refusal itself is proved
by execution too (`TestAdminSubscribers_Erase_ConflictsOnPendingSend`, re-run
green), and the refusal path mutates nothing.

### `RecheckEligibleTx` — the reported trap is real; the workaround is sufficient today

Verified the claim directly rather than by reading the SQL. Same `email_sends`
row, same call, before and after NULLing `subscriber_id`:

```
with subscriber_id set:  eligible=1 skipped=0 err=<nil>
with subscriber_id NULL: eligible=0 skipped=0 err=<nil>   ← invisible
the row's status remains "queued" with no code path to change it
```

Confirmed: `audience.go`'s `JOIN subscribers s ON s.id = es.subscriber_id` is an
INNER JOIN, so a NULL-`subscriber_id` row is returned in **neither** slice, and
`MarkSkippedTx` only ever runs on rows the function returns. The row would sit
at `queued` forever.

**Verdict: the 409 workaround is sufficient for erasure specifically, and the
join should still be fixed.** Sufficient, because the lock ordering above makes
"erased with a pending send" genuinely unreachable, and I confirmed the only
two Go read sites for `email_sends.subscriber_id` are safe against NULL
(`audience.go:380` is `RETURNING` from an `INSERT`, never NULL; `audience.go:494`
is behind the INNER JOIN itself) — so nothing panics or mis-scans. Still worth
fixing, because the join *fails silently*: nothing in the codebase enforces the
invariant "a `queued` row always has a non-NULL `subscriber_id`", and the
failure mode of breaking it is an invisible stuck row rather than an error. A
`LEFT JOIN` that returns the orphan as an explicit `SkippedSend` would make the
invariant self-enforcing. Reported below, not filed (CLAUDE.md §9).

### Defect — criterion 7 is not met: the privacy policy's retention list is now factually wrong

`web/src/views/PrivacyPolicy.svelte` says, under "How to leave":

> An erasure request **hard-deletes your subscriber record — your email,
> interests, and signup details** — but **three things** are deliberately
> retained rather than deleted:

…and then enumerates exactly three: the suppression entry, the anonymized send
history, the raw deliverability events. The implementation notes conclude from
this that the page "Already documents this design precisely… No change needed."

It does not. As the real-journey census above shows, an erasure leaves a
**fourth** category the page never mentions and which its closed "three things"
enumeration actively excludes: **`audit_log` retains the subscriber's email
address in plaintext, and their signup IP.**

- `subscriber.confirmed` keeps `metadata = {"email": "<the address>"}`
  (`internal/handlers/confirm.go:156`) — not written by this change, but not
  removed by it either, and never disclosed anywhere.
- `subscriber.signup` keeps `ip_address` = the signup IP
  (`internal/handlers/subscribe.go:1104`) — which is precisely one of the
  "signup details" the same sentence promises are hard-deleted, and which the
  page's own "What we collect" list names explicitly.
- The **new** `subscriber.erased` row this change adds keeps
  `metadata = {"email": …, "previous_status": …}`. `previous_status` is a fact
  about the person (`complained`, `bounced`) that exists in no other surviving
  row.
- `subscriber.complained` / `subscriber.bounced` keep `{"email": recipient, …}`
  too (`ses_notifications.go:562`, `:444`, `:504`) for any address that ever
  bounced or complained.

So after an "erasure", one table still joins this person's email address to
their signup IP and their former subscriber state, and the published policy
tells them the opposite. That is criterion 7 ("Privacy policy documents what is
retained after erasure and why") unmet as a matter of fact, not of wording, and
it is squarely this issue's scope — "what is retained after erasure" is exactly
what this issue defines.

The audit design itself is right and should not change: `ActionSubscriberErased`
is correctly justified, `target_id` correctly carries no FK, and an erasure that
left no trace of itself would be worse. `audit_log` is append-only, so scrubbing
the pre-existing rows is not the answer either. **The page is what is wrong.**

### Worth filing (reported, not filed — CLAUDE.md §9)

1. **`internal/mailing.AudienceStore.RecheckEligibleTx`'s INNER JOIN silently
   hides a NULL-`subscriber_id` row** — verified above: neither eligible nor
   skipped, status stuck at `queued` with no code path out. `#0060` works
   around it by refusing to erase while a send is pending, and that workaround
   is airtight for erasure, but the join is a latent trap for any future path
   that leaves `subscriber_id` NULL on a `queued` row, and it fails silently
   rather than loudly. A `LEFT JOIN` returning the orphan as an explicit
   `SkippedSend` would make the invariant self-enforcing.
2. **`PRD.md` §6.2 (line 541) still specifies `subscriber_id BIGINT NOT NULL
   REFERENCES subscribers(id) ON DELETE CASCADE`**, the exact opposite of what
   shipped and of what this issue depends on. The parity guards are
   names-only, so nothing catches it, and a future reader of the spec would
   conclude that deleting a subscriber cascades away their send history. This
   is not "the spec leading the implementation" (the case
   `prd_index_parity_test.go` deliberately tolerates) — it is the spec
   contradicting it. A one-line currency edit, the same kind `#0113` made.
3. **No admin-console UI** exists for `DELETE /admin/subscribers/{id}` or for
   `#0059`'s export — both are reachable only by direct API call. (`#0219`
   already covers the export half; this is the erasure half, and it needs the
   typed-confirmation modal.)
4. **`UNIQUE (campaign_id, subscriber_id)` no longer constrains anonymized
   rows**, since PostgreSQL treats NULLs as distinct. Harmless today — an
   erased subscriber can never be re-materialized — but the migration comment
   still describes that unique key as "the idempotency guarantee" without
   noting the NULL carve-out.
