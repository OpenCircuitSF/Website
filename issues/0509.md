# 0509 — The production box has no Go toolchain, so the documented build-on-box deploy cannot run

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | deploy |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-12 |

## Description

`docs/deployment.md`'s redeploy procedure builds the binary **on the server**.
The server production actually runs — `photon.sstools.co`, see `#0508` — has no
Go toolchain:

    $ ssh photon 'command -v go'
    (nothing)
    $ echo $PATH
    /usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin

No `go` on `PATH`, and none at `/usr/local/go/bin/go` or `/opt/go/bin/go`.

So the documented deploy cannot be executed as written, and this is not a
staleness that a search-and-replace fixes — it is a missing decision about how
the binary gets built at all.

## Two options, and the trade

**1. Install Go on the box.** Keeps `docs/deployment.md`'s procedure intact and
keeps the build reproducible from the checkout that is actually deployed. Costs
disk (~600 MB for the toolchain plus module cache) and adds a thing to keep
patched. The old `t4g.nano`'s 418 MB made this genuinely painful; the new
`t4g.small` has 1846 MB and 23 GB free, so the original objection is much
weaker than it was.

**2. Cross-compile locally and ship the binary.** `GOOS=linux GOARCH=arm64 go
build`, then `scp` the artifact. No toolchain on the box, no build memory
pressure, faster deploys. Costs: the deployed binary is no longer traceable to
an on-box checkout, `CGO_ENABLED` and glibc-version skew become real
considerations, and the `scp`-a-binary path needs the same precondition
discipline `#0466` had to add for `scp`-ing scripts.

The project already leans toward `scp` for small artifacts (`#0466`), which is
weak evidence for option 2 — but a binary is not a shell script, and the
provenance argument cuts the other way.

## Acceptance criteria

1. Pick one and record the reasoning. **Either is acceptable; an unexamined
   choice is not.**
2. `docs/deployment.md`'s redeploy procedure matches the chosen approach end to
   end, with no step that assumes a toolchain that is not there.
3. If cross-compiling: pin `GOOS`/`GOARCH`/`CGO_ENABLED` explicitly, state how
   the deployed binary's provenance is recorded (commit hash embedded or
   recorded alongside), and verify the artifact runs on the box before it
   replaces the running one.
4. If installing Go: record the version, how it is updated, and confirm a real
   `go build` of this tree completes within the box's memory.
5. Verify the chosen path by actually producing a binary that runs on `photon`,
   not by reasoning that it should.

## Decision — 2026-09-12, by the user

**Option 2: cross-compile locally and ship the binary. Go will not be
installed on `photon`.**

Recorded verbatim: "We won't install the Go toolchain on the EC2 instance
photon. Instead we should compile before deployment."

**Measured feasibility, before writing the procedure** — this is not a
cross-*architecture* build. The workstation is `darwin/arm64` and `photon` is
`linux/arm64`, so only `GOOS` changes:

    $ grep -rl '"C"' --include='*.go' .        # production tree
    (only internal/subscribers/imports_test.go — a test file)

    $ GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o opencircuit-linux-arm64 ./cmd/opencircuit
    9.2s

    $ file opencircuit-linux-arm64
    ELF 64-bit LSB executable, ARM aarch64, statically linked, not stripped   (26 MB)

Statically linked with `CGO_ENABLED=0`, so the glibc-skew concern this issue
raised does not arise. Local Go is `go1.27.1 darwin/arm64`.

## What this issue now has to deliver

1. `docs/deployment.md`'s redeploy procedure rewritten around build-locally +
   ship-artifact, with **no step assuming a toolchain on the box**.
2. `GOOS=linux`, `GOARCH=arm64`, `CGO_ENABLED=0` pinned explicitly in the
   documented command, not left to the operator's environment.
3. **Provenance.** The deployed binary is no longer traceable to an on-box
   checkout, which was option 1's main advantage and is the cost being
   accepted here. Embed the commit hash at build time via `-ldflags` and
   expose it so production can be asked what it is running. Decide the surface
   — an existing health/version endpoint if one fits, a `--version` flag
   otherwise — and say why.
4. The `scp`-precondition discipline `#0466` established applies to shipping a
   binary too: state the destination, that it is writable by `ec2-user`, and
   the expected SHA-256, so a failed copy cannot look like a successful one.
5. A rollback path: keep the previous binary on the box and document swapping
   back, since there is no longer an on-box checkout to rebuild from.
6. **`web/dist` still has to be built before the Go build**, because the SPA is
   embedded via `//go:embed all:dist`. Note `CLAUDE.md` §8b's hazard — a real
   `npm run build` overwrites the tracked `web/dist/index.html` placeholder,
   and the safe restore is `git show HEAD:web/dist/index.html > …`, never
   `git checkout --`.
7. Verify by producing a binary that **actually runs on `photon`**, not by
   reasoning that it should.
