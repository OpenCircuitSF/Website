## Description

`docs/deployment.md`'s redeploy procedure builds the binary **on the server**.
The server production actually runs — `photon.sstools.co`, see `#0508` — has no
Go toolchain:

    $ ssh photon 'command -v go'
    (nothing)
    $ echo $PATH
    /usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin

No `go` on `PATH`, and none at `/usr/local/go/bin/go` or `/opt/go/bin/go`.

So the documented deploy cannot be executed as written, and this is not a
staleness that a search-and-replace fixes — it is a missing decision about how
the binary gets built at all.

## Root cause

Not a code defect — a missing decision, already recorded above by the user
(2026-09-12): cross-compile locally and ship the binary; the box never gets
a Go toolchain. What was actually missing was the follow-through: nothing
had rewritten the redeploy procedure, no build-time provenance surface
existed to compensate for the checkout traceability the decision gives up,
and the artifact had never actually been proven to run on the target host.

## Fix

- `docs/deployment.md`'s **Redeploy procedure** rewritten end to end around
  build-locally-ship-binary: pinned `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`
  in the documented build command; a numbered sequence (build SPA → build
  Go binary with `-ldflags` → `scp`-precondition (destination, writability,
  expected sha256, per `#0466`'s discipline) → bring the migrations checkout
  current if needed → prove the artifact runs → back up the previous binary
  → install and restart); and an explicit note that `scripts/deploy.sh`
  itself still assumes an on-box toolchain and is not yet updated to match
  (reported below, not filed per `CLAUDE.md` §9).
- **Provenance:** added `cmd/opencircuit.commitHash` (`main.go`), a
  package-level `string` var defaulting to `"unknown"`, set at build time via
  `-ldflags "-X main.commitHash=$(git rev-parse HEAD)"`. Exposed through the
  existing `versionString()` helper, which is what the CLI's
  default/`version`/`--version` branch already printed (`opencircuit
  <version>`) — extended to `opencircuit <version> (<commitHash>)`.
  **Chose the CLI surface over `/health`**: `GET /health`
  (`internal/handlers/health.go`) has a PRD-fixed (`PRD.md` §8), tested
  response shape answering one question — is the service and its database
  reachable — and adding a commit field to it would widen a contract
  existing tests and monitoring already depend on, to answer an unrelated
  question. The CLI branch was already the project's version surface, needs
  no running server/database/session to query, and is exactly what this
  issue's own on-box proof (below) used.
- §1 Prerequisites' Go/Node/`golang-migrate` bullets corrected: Go and
  Node.js are now framed explicitly as build-machine (workstation/CI)
  requirements, not box requirements; the `golang-migrate` CLI install
  step changed from `go install` (requires a toolchain the box will never
  have) to the project's prebuilt release tarball — verified missing on the
  box entirely today (`command -v migrate` found nothing), a real gap this
  pass surfaces but does not fix, since installing it is outside this
  issue's hard limits.
- Corrected the two stale "open question" spots `#0508` deliberately left
  for this issue: `docs/deployment.md`'s production-facts "No Go toolchain"
  row and its Prerequisites instance-type note, plus `CLAUDE.md` §7's

This is not a bounce — nothing the first two passes fixed was wrong. It
changes the transport only:

1. **Delivery mechanism replaced.** Instead of `scp`-ing a bare binary to a
   scratch path, the redeploy procedure now stages a release bundle (the
   `linux/arm64` binary, `migrations/`, the systemd unit, and a
   `SHA256SUMS` covering the bundle), publishes it with `gh release
   create`, and has `photon` fetch it with a plain, unauthenticated `curl`
   — no credential of any kind on the box, since the repo and its releases
   are both public. Step 1 (build + assemble bundle), step 2 (publish),
   and step 3 (fetch + verify on the box, replacing the old scp
   precondition) are new; steps 4–7 (prove the artifact runs, back up the
   previous binary, migrations, install) carry the same substance as the
   second pass, renumbered by one to fit the new step 2.
2. **The load-bearing change: migrations now come from the bundle, not the
   box's checkout.** `photon`'s `/opt/opencircuit` checkout is 900 commits
   behind and currently dirty (`M web/dist/index.html`, still true as
   measured this pass) — read-only, via `ssh photon 'cd /opt/opencircuit
   && git status --porcelain'`. The old procedure depended on bringing
   that checkout current with `git pull` before `migrate` could run; this
   pass removes that dependency entirely. The release bundle's own
   `migrations/` directory — the exact tree for the commit being deployed,
   already hash-verified in step 3 — is what step 6 now points `migrate
   -path` at. The checkout stays on the box for `scripts/db/restore.sh`
   and other ancillary tooling, but keeping it pulled current is no longer
   this procedure's responsibility. **This does not supply the
   `golang-migrate` tool itself** — bundling migration files is not the
   same as installing the migration binary, and `command -v migrate` on
   `photon` still finds nothing (tracked as `#0513`, open, not fixed by
   this pass). Step 6 still routes to the corrected Prerequisites bullet
   (prebuilt tarball, not `go install`).
3. **Rollback now leads with the release, not the on-box copy.** New step
   5 rollback prose: `gh release list` from the workstation to find the
   previous tag, then `curl` + `sha256sum -c` + `unzip` + `install` on the
   box — the same fetch-and-verify discipline as a forward deploy, just
   against an older tag. The on-box `opencircuit-previous` binary copy is
   kept as an explicit belt-and-braces fallback for the case the release
   infrastructure itself (GitHub, or the box's outbound path to it) is
   what's unavailable at the moment of rollback, not the primary path.
4. **Provenance gains a second, weaker pointer.** The commit hash embedded
   via `-ldflags` (unchanged from pass 1) remains the proof; the release
   tag is now also recorded as a human-facing label, with the doc explicit
   that the tag names the release while the hash proves the contents — a
   tag can in principle move, the embedded hash cannot.
5. **Scope boundary kept.** The release-publishing script itself (build,
   package, `gh release create`, tag scheme) is `#0514`, not this issue —
   the new **Step 1**/**Step 2** describe the commands an operator runs by
   hand today, and say explicitly that once `#0514` lands they collapse
   into one script invocation. `scripts/deploy.sh` is `#0512` and was not
   touched. The tag scheme used in the doc's examples (`v0.1.0-<short-sha>`)
   is explicitly marked illustrative, with `#0514` named as owning the
   real one.
6. **Two supporting spots updated for consistency, not rewritten wholesale:**
   the Prerequisites `golang-migrate` bullet no longer says migration files
   come from the box's checkout, and now names `#0513`; the production-facts
   "No Go toolchain" row now states the release-based delivery mechanism
   alongside the already-decided no-toolchain fact; the cross-reference near
   the top of **Backups** ("this is the restore point the redeploy procedure

7. **Nit 6 from the review (`sha256sum` vs `shasum -a 256` on the

## Two options, and the trade

**1. Install Go on the box.** Keeps `docs/deployment.md`'s procedure intact and
keeps the build reproducible from the checkout that is actually deployed. Costs
disk (~600 MB for the toolchain plus module cache) and adds a thing to keep
patched. The old `t4g.nano`'s 418 MB made this genuinely painful; the new
`t4g.small` has 1846 MB and 23 GB free, so the original objection is much
weaker than it was.

**2. Cross-compile locally and ship the binary.** `GOOS=linux GOARCH=arm64 go
build`, then `scp` the artifact. No toolchain on the box, no build memory
pressure, faster deploys. Costs: the deployed binary is no longer traceable to
an on-box checkout, `CGO_ENABLED` and glibc-version skew become real
considerations, and the `scp`-a-binary path needs the same precondition
discipline `#0466` had to add for `scp`-ing scripts.

The project already leans toward `scp` for small artifacts (`#0466`), which is
weak evidence for option 2 — but a binary is not a shell script, and the
provenance argument cuts the other way.

## Acceptance criteria

1. Pick one and record the reasoning. **Either is acceptable; an unexamined
   choice is not.**
2. `docs/deployment.md`'s redeploy procedure matches the chosen approach end to
   end, with no step that assumes a toolchain that is not there.
3. If cross-compiling: pin `GOOS`/`GOARCH`/`CGO_ENABLED` explicitly, state how
   the deployed binary's provenance is recorded (commit hash embedded or
   recorded alongside), and verify the artifact runs on the box before it
   replaces the running one.
4. If installing Go: record the version, how it is updated, and confirm a real
   `go build` of this tree completes within the box's memory.
5. Verify the chosen path by actually producing a binary that runs on `photon`,
   not by reasoning that it should.

## Review notes — 2026-09-12 (phase 3, fourth pass, bounced)

Reviewed as an operator running this by hand today, against live production.
**Bounced**, on two defects — one of them introduced by this pass, and both

**Blocker 1 from the third pass is genuinely fixed** and re-verified

### 1 — Step 2's `git ls-remote` guard can never pass (blocking)

`git ls-remote origin "$COMMIT"` treats its argument as a **ref-name**
pattern, not an object id. A full 40-character sha matches no ref name, so
the command prints nothing and exits `0` — for a pushed commit exactly as
much as for an unpushed one. `grep -q` then fails either way and the guard
fires `STOP`.

Measured here, both directions, against this repo's real remote:

    $ git rev-parse origin/main
    0e8ebc34c08e32498efa3c94698b2f0a25936afd     # definitively on origin

    $ git ls-remote origin 0e8ebc34c08e32498efa3c94698b2f0a25936afd
    (no output, exit 0)

    $ git ls-remote origin | head -2
    0e8ebc34c08e32498efa3c94698b2f0a25936afd	HEAD
    0e8ebc34c08e32498efa3c94698b2f0a25936afd	refs/heads/main

The object id is right there in the unfiltered listing; the pattern-filtered
call cannot see it. This is `CLAUDE.md` §8's "a checker that agrees with
itself" one notch worse — a checker that agrees with nothing. It fails
closed rather than open, which is the better of the two, but the effect
today is that the operator pushes seventeen commits and is then told to stop.

**Second defect in the same block:** `exit 1` inside `{ ... }` runs in the
current shell. Pasted into the operator's interactive shell — which step 3
explicitly instructs them to keep open through step 7 — it **closes that
shell**, discarding `$TAG`, `$COMMIT`, `$BUNDLE`, and `$REPO`. Every other
"stop here" in this procedure (step 3's hash mismatch, step 6's backup
check) is prose plus an echoed message, not a shell-terminating `exit`.

**Remedy — apply verbatim.** Replace step 2's guard block with:

    git push origin HEAD
    git ls-remote origin | grep -q "^$COMMIT" \
      || echo "STOP: $COMMIT is not on origin — do not run gh release create"

and add one sentence after it: "If that prints `STOP`, do not continue — the
push did not land where expected." Both halves verified here: dropping the
pattern and anchoring the grep gives `PASS` for `origin/main`'s head and
`FAIL` for the unpushed local `HEAD`, which is the discrimination the guard
was written to make. Two alternatives were also confirmed working
(`git merge-base --is-ancestor "$COMMIT" origin/main` after a fetch, and
`git branch -r --contains "$COMMIT"`); the `ls-remote` form above is the
smallest edit and needs no fetch.

### 2 — Step 1's new cleanup block deletes the two files step 2 uploads (blocking, a relocation)

The third pass's nit 5 asked for cleanup of `$STAGE`, `$BUNDLE`, and
`SHA256SUMS`. The block that landed is correct in content but sits at the
**end of step 1**, immediately above the step 2 heading, introduced by a
sentence reading "afterward … once this step finishes." An operator
following literally runs

    rm -rf "$STAGE" "$BUNDLE" SHA256SUMS opencircuit

and then step 2's `gh release create "$TAG" "$BUNDLE" SHA256SUMS` has
nothing to upload. It fails loudly and the recovery is a rebuild, so no
production risk — but it is a guaranteed stumble on a procedure whose whole
point is being followable literally.

**Remedy — apply verbatim.** Move the cleanup block and its two surrounding
paragraphs to the **end of step 2**, after the `gh release view "$TAG"`
confirmation, and change the lead sentence to: "**Once step 2 has confirmed
both assets attached, clean up the build residue, if this was a shared
checkout.**" Nothing else in either step changes.

### On `git push origin HEAD` inside the procedure (asked, non-blocking)

**Keep it, but as a checked precondition rather than an unconditional
action.** The push is not a convenience here — it is a hard requirement:
`gh release create --target "$COMMIT"` cannot create a tag at a commit the
remote does not have, so a procedure that pins the tag *must* ensure the
commit is pushed. Requiring the operator to have pushed beforehand and only
checking would be equally defensible, and marginally more in keeping with
this repo's habit of treating pushes as deliberate acts (`CLAUDE.md` §8a).
What tips it: seventeen unpushed commits sit on `main` right now, so on
today's run the push is a substantive repo action, not a no-op — and it is
better performed by a step that names it than discovered as a prerequisite
mid-deploy. The remedy in item 1 keeps the push and makes the check the
gate, which is the right shape. No change beyond item 1 is required.
