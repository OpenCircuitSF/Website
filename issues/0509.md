## Description

`docs/deployment.md`'s redeploy procedure builds the binary **on the server**.
The server production actually runs — `photon.sstools.co`, see `#0508` — has no
Go toolchain:

    $ ssh photon 'command -v go'
    (nothing)
    $ echo $PATH
    /usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin

No `go` on `PATH`, and none at `/usr/local/go/bin/go` or `/opt/go/bin/go`.

So the documented deploy cannot be executed as written, and this is not a
staleness that a search-and-replace fixes — it is a missing decision about how
the binary gets built at all.

## Root cause

Not a code defect — a missing decision, already recorded above by the user
(2026-09-12): cross-compile locally and ship the binary; the box never gets
a Go toolchain. What was actually missing was the follow-through: nothing
had rewritten the redeploy procedure, no build-time provenance surface
existed to compensate for the checkout traceability the decision gives up,
and the artifact had never actually been proven to run on the target host.

## Two options, and the trade

**1. Install Go on the box.** Keeps `docs/deployment.md`'s procedure intact and
keeps the build reproducible from the checkout that is actually deployed. Costs
disk (~600 MB for the toolchain plus module cache) and adds a thing to keep
patched. The old `t4g.nano`'s 418 MB made this genuinely painful; the new
`t4g.small` has 1846 MB and 23 GB free, so the original objection is much
weaker than it was.

**2. Cross-compile locally and ship the binary.** `GOOS=linux GOARCH=arm64 go
build`, then `scp` the artifact. No toolchain on the box, no build memory
pressure, faster deploys. Costs: the deployed binary is no longer traceable to
an on-box checkout, `CGO_ENABLED` and glibc-version skew become real
considerations, and the `scp`-a-binary path needs the same precondition
discipline `#0466` had to add for `scp`-ing scripts.

The project already leans toward `scp` for small artifacts (`#0466`), which is
weak evidence for option 2 — but a binary is not a shell script, and the
provenance argument cuts the other way.

## Acceptance criteria

1. Pick one and record the reasoning. **Either is acceptable; an unexamined
   choice is not.**
2. `docs/deployment.md`'s redeploy procedure matches the chosen approach end to
   end, with no step that assumes a toolchain that is not there.
3. If cross-compiling: pin `GOOS`/`GOARCH`/`CGO_ENABLED` explicitly, state how
   the deployed binary's provenance is recorded (commit hash embedded or
   recorded alongside), and verify the artifact runs on the box before it
   replaces the running one.
4. If installing Go: record the version, how it is updated, and confirm a real
   `go build` of this tree completes within the box's memory.
5. Verify the chosen path by actually producing a binary that runs on `photon`,
   not by reasoning that it should.

### 1 — Nothing tells the operator to verify a backup before migrations (blocking)

Step 3 applies `000023`-`000028` to a live database and defers to
**Migrations** above for how. Neither place mentions a backup. Tomorrow that
is six unreviewed-against-production migrations against real subscriber rows
with no stated recovery point, and `CLAUDE.md` §1 already records what a bad
one costs (`#0125` left `schema_migrations` dirty at 23 in a scratch
database; the same failure on production is a different day entirely).

The check is cheap and it exists — the box runs `host-backup-db.timer`
nightly at 03:15 UTC into `/var/backups/host/<UTC-date>-db/`, and today's
run produced `opencircuit.dump` (75,812 bytes) alongside `globals.sql` and a
`SHA256SUMS` to verify it against. Note this is **not** the
`opencircuit-backup.timer` / `/var/backups/postgres/<db>/` mechanism the
**Backups** section of this document describes; that one is not loaded on
`photon` (`systemctl list-timers --all` lists only `host-backup-db.timer`
and `host-backup-full.timer`). Do not restate the whole backup design here —
just point step 3 at the dump that actually exists.

**Remedy:** immediately before step 3's `migrate ... up`, add a block that
confirms the newest `/var/backups/host/<date>-db/opencircuit.dump` exists,
is non-zero, is from the current night, and verifies against its sibling
`SHA256SUMS`; and name `scripts/db/restore.sh` (per **Backups**) as the
recovery path if a migration goes wrong. One short block, not a rewrite.

### 2 — The irreversible step runs before the free ones (blocking)

Order as written is migrate (3) -> prove the artifact runs (4) -> back up
the previous binary (5) -> install (6). Steps 4 and 5 are non-mutating and
cost seconds; step 3 is the only irreversible one. If step 4 fails — a
mis-built binary, bytes that pass a hash check but do not execute — the
schema has already moved 22 -> 28 while the *old* binary is still the one
running, and that binary predates all six migrations.

Migrating before installing is right and should stay (`CLAUDE.md` §1's
`#0125` note is the reason). The fix is only to move the *free* checks
ahead of the irreversible one.

**Remedy:** reorder to prove-artifact -> back-up-previous-binary ->
migrations -> install, renumbering accordingly; or, if renumbering is too
invasive, open step 3 with an explicit "if this deploy includes migrations,
do steps 4 and 5 first — they are free and this one is not." Either way
step 6's "only after ..." sentence needs to match the new order.

### 3 — Rollback does not address the schema asymmetry (blocking)

Criterion 5's rollback path is executable as far as the binary goes — the
`cp` to `opencircuit-previous` and the `install`-back are concrete and
correct. But it says nothing about migrations, and after a 22 -> 28 deploy
the binary swap puts a build that predates all six migrations back in front
of a schema that has them. That asymmetry is the whole reason a
ship-the-artifact rollback is not symmetric with a rebuild-from-checkout
one, and it is the sentence criterion 5 is really asking for.

**Remedy:** a short paragraph in the rollback step saying (a) the binary
swap covers a bad *binary* against an unchanged schema and is instant; (b)
the schema does **not** revert with it; (c) `migrate ... down` is not the
reflex — the down pairs have never run against production and `CLAUDE.md`
§1's append-only discipline governs; (d) recovery from a bad *migration* is
the dump from item 1 restored per **Backups**, which is a different and much
heavier operation. Naming which failure each path covers is the point.

### 4 — The rollback step's own check cannot pass on the first deploy (blocking, one sentence)

Step 5 says to run `opencircuit-previous --version` and "confirm it still
runs **and names the prior commit**." Measured read-only on the box today:

    /usr/local/bin/opencircuit --version
    opencircuit 0.1.0

No hash — the installed binary predates this issue's `commitHash`. The first
operator to follow step 5 literally, tomorrow, hits a check that cannot pass
and has no way to know whether that means the backup is bad.

**Remedy:** one sentence — the currently-installed binary predates `#0509`
and prints `opencircuit 0.1.0` with no hash; that is expected exactly once,
and every deploy after this one will name its commit.

### 5 — `version_test.go` misses the empty-commit failure mode (non-blocking, one line)

Mutation-tested in a throwaway `git worktree` at `7cfc458` (main checkout
never touched):

- Dropping the hash from the format string — `return fmt.Sprintf("opencircuit
  %s", version)` — is **caught**: both tests fail, naming the missing hash.
- Changing the default to `var commitHash = ""` is **not caught**: both tests
  still pass, because `strings.Contains(got, commitHash)` is vacuously true
  for the empty string. `versionString()` then silently returns
  `opencircuit 0.1.0 ()`.

The live risk is low — the default is the loud `"unknown"`, and step 4 would
surface a forgotten `-ldflags` anyway — but an oracle that compares a value
against itself is `CLAUDE.md` §8's "a copy of the answer stored next to the
question" in miniature, and this one is a one-line fix.

**Remedy:** in `TestVersionStringIncludesSemVerAndCommitHash`, assert
`commitHash != ""` before the `strings.Contains` check (or assert the
parenthesised segment of the output is non-empty), so an empty default fails
rather than passing vacuously.

### 6 — `sha256sum` on the workstation side (nit, fix while in there)

Step 1 uses `sha256sum` for the local hash. Everywhere else this document
uses `shasum -a 256` for the workstation and reserves `sha256sum` for the
box (lines 146, 782, 1287 vs 785, 841). It is not broken on the machine this
was proven on — `/sbin/sha256sum` exists here and works — but it is not
stock macOS and it breaks the doc's own convention in the one step whose
output every later step compares against.
