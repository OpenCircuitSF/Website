`GET /admin/audit` filters only by `user_id`. `#0045`'s send worker writes a
`email_campaign.send_refused` row with a **NULL actor** — the worker is not a user —
so the one row explaining why a campaign was demoted from `scheduled` back to
`draft` cannot be filtered to by any means the admin UI offers.

## Acceptance criteria

- [x] The audit list can be filtered by `target_type` and `target_id`, so a
      campaign's own history is reachable
- [x] Rows with a NULL actor are reachable — a filter that implicitly requires
      a user excludes exactly the machine-written rows that most need reading
- [x] `#0047`'s campaign screen can deep-link to the filtered view rather than
      linking to the audit tab unfiltered, which is its current workaround
- [x] Tests cover a NULL-actor row and a `target_type`/`target_id` filter that
      returns it

> **Corrected 2026-08-21 from `#0041`'s review.** This issue originally named
> the action `campaign.send_refused`. The `campaign.*` prefix was retired when
> `#0068` deleted ShortLinks' campaign audit constants; `#0041` established the
> `email_campaign.*` namespace with `TargetEmailCampaign`. `#0045` must use
> `email_campaign.send_refused`, or the campaign audit trail splits across two
> namespaces and this issue's filter will not reach the refusal rows.

## Implementation

**Design decision — where the campaign-scoped audit view lives.** `#0049`
landed a per-campaign stats screen (`CampaignStats.svelte`,
`GET .../campaigns/{id}/stats`) the day before this issue was picked up, which
raised the question of whether the campaign's audit history belongs there
instead of (or in addition to) the general Audit tab. Decision: it stays in
the general Audit tab, extended with `target_type`/`target_id` filters, and
**both** the demoted-banner (`CampaignEditor.svelte`) and the stats screen
(`CampaignStats.svelte`) deep-link into it — I did not embed a second audit
table inside `CampaignStats.svelte`. Reasons:
- Admin.svelte's audit section already owns actor/target-label rendering,
  metadata formatting, and pagination (`lib/admin.ts`'s `actorLabel`,
  `targetLabel`, `formatMetadata`, `pageInfo`). Reproducing that inside
  `CampaignStats.svelte` would be a second, divergent implementation of the
  same table for no benefit — the AC only asks that the row be *reachable*,
  not that it be inline.
- `CampaignStats.svelte`'s counts (`buildStatBuckets`) are derived from
  `email_sends`/`email_events` rows that only exist once materialization has
  run. `send_refused` fires **before** materialization — a demoted campaign
  has zero `email_sends` rows — so it can never show up as a bucket or a
  failed-send row there regardless of this issue; a deep link is the only
  connection that makes sense.
- The stats screen is nonetheless where an operator's eye goes first for
  "what happened, and why" (the task brief's own framing), so it gets a
  "View audit history" button alongside the existing demoted-banner "View in
  audit log" button — both call the same `onGoToAudit(campaignId)` prop,
  which `Admin.svelte` wires to `goToCampaignAudit`.

**Backend.** `internal/audit/read.go`: replaced `ListAuditLog`'s bare
`userID *int64` parameter with a `Filter{UserID, TargetType, TargetID}`
struct and a private `whereClause()` builder that ANDs together whichever
fields are set, building the count and page queries' placeholder positions
off `len(args)` so adding a filter never desyncs the two queries. `TargetID`
only contributes a clause when `TargetType` is also non-empty — a bare
`target_id` is ambiguous across target types (e.g. `subscriber #5` and
`email_campaign #5` are unrelated rows) — documented on `Filter` itself.
`internal/handlers/audit.go`'s `List` gained `?target_type=`/`?target_id=`
parsing: a non-integer or non-positive `target_id` is a 400
(`invalid target_id`), and a `target_id` given without a `target_type` is a
400 (`target_id requires target_type`) rather than being silently dropped.
None of the three filters ever reference `actor_id`, so a NULL-actor row
(`#0045`'s `send_refused`) is reachable through `target_type`/`target_id`
exactly like any operator-written row. `internal/devstore/devstore.go`'s
`Store.ListAuditLog` (the `STORAGE=json` backend) got the matching
`audit.Filter`-shaped signature and the same AND/ambiguity semantics so the
two backends stay in parity.

**Frontend.** `lib/admin.ts`: `AUDIT_TARGET_EMAIL_CAMPAIGN` (mirrors
`audit.TargetEmailCampaign` on the Go side), `campaignAuditFilter(campaignId)`
(the one place that builds `{targetType, targetId}` for a campaign), and
`parseTargetFilter(targetTypeRaw, targetIdRaw)` (mirrors the handler's
validation, including the same "target_id requires target_type" error) —
all pure and vitest-covered, per `#0094`'s rule that nothing in a `.svelte`
file is unit-testable. `lib/api.ts`'s `listAudit` gained optional
`targetType`/`targetId` params appended to the query string. `Admin.svelte`:
added `auditTargetTypeRaw`/`auditTargetIdRaw` inputs to the existing filter
form (alongside the pre-existing user-id field, same Apply/Clear pattern);
`auditHasFilter` now covers all three filters for the Clear button's
visibility; added `goToCampaignAudit(campaignId)`, which sets the target
filter via `campaignAuditFilter`, clears the user-id filter, switches
`section` to `'audit'`, and reloads. `Campaigns.svelte`/`CampaignEditor.svelte`
/`CampaignStats.svelte`: `onGoToAudit`'s type changed from `() => void` to
`(campaignId: number) => void`, threaded down from `Admin.svelte`'s
`goToCampaignAudit`; `CampaignEditor`'s existing "View in audit log" button
now calls `onGoToAudit(campaignId)` instead of the old no-arg unfiltered
switch; `CampaignStats` gained a new "View audit history" button doing the
same.

## Review notes

Recorded by the phase-3 reviewer, 2026-08-22. Neither item blocks resolution.

**1. `target_type` is accepted as any string, and that is the right call.**
`internal/audit/actions.go` does declare a closed set of target-type constants,
so validating against it was available — but it would be wrong here.
`audit_log` is append-only history: rows written under a target type that is
later retired must stay filterable, and the table already holds exactly that
case (`TargetLink` and `TargetURLFilter` are vestigial ShortLinks values that
`#0068` left behind). A read-side allowlist would make retiring a constant
silently unreach part of the historical record. The value is parameterised
(`target_type = $N`), so there is no injection surface; the only cost is that a
typo in the free-text field renders "No audit entries." — which reads as "the
log is empty" rather than "your filter matched nothing." Mitigating context:
the typed value stays visible in the input and the Clear button is shown
(`auditHasFilter` covers all three filters), and the deep link — the path the
acceptance criteria actually require — never goes through free text, since
`campaignAuditFilter` supplies the constant. If this is ever worth improving,
the remedy is a `<datalist>` of known types on the input, not a 400.

**2. Clearing the user-id filter in `goToCampaignAudit` is required, not just
tidier.** Preserving it would AND `user_id` with the target filter, and the one
row the deep link exists to reach — `#0045`'s `send_refused` — has a NULL
`user_id`. A stale user-id filter would therefore deterministically hide the
target of the navigation. The clearing is also visible rather than silent: the
raw input fields are reassigned, so the audit form shows the exact filter that
was applied.

**3. `#0079`/`#0071`/`#0094`/§8b spot checks.** `GET /admin/audit` is inside
`adminRoutes()` (`cmd/opencircuit/main.go`), so
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` covers it automatically.
No SPA route changed — the deep link switches an internal `section` state
within `/admin`, so `#0071`'s Go/TypeScript route parity is untouched. The
decisions (`parseTargetFilter`, `campaignAuditFilter`,
`AUDIT_TARGET_EMAIL_CAMPAIGN`) live in `web/src/lib/admin.ts` with vitest
coverage; what remains in `Admin.svelte` is state assignment and navigation.
No test targets a literal or seeded row id — `audit_log.target_id` has no FK
(`migrations/000005`), and the ids used (`424242`, `919191`) are bare values in
that unconstrained column.
