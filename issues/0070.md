## Description

The site footer (#0017) links to `/privacy` per PRD §11 — the site collects
email, interests, signup IP, and UTM source, and both PRD §11 and the
signup flow require a documented, linked privacy policy. The page itself does
not exist yet: `/privacy` is not a route the router recognizes, so it
currently resolves to the terminal-styled 404 (#0022) rather than a broken
link.

## Acceptance criteria

- [ ] `/privacy` is a recognized static route in `web/src/lib/router.ts`
      **and in `internal/handlers/routes.go`'s `knownStaticRoutes`** — added at
      `#0022`'s review, 2026-08-18. The two tables are hand-maintained mirrors
      and nothing fails when they diverge (proven in both directions; see
      `#0071`). Edit only `router.ts` and `/privacy` ships as a fully rendered
      page that the server answers with HTTP 404 — invisible in a browser,
      fatal for indexing. Add a `SPAHandler` test asserting `/privacy` returns
      **200**
- [ ] `PrivacyPolicy.svelte` (or similarly named) view, wrapped in the site
      header/footer shell like Home/About
- [ ] Covers, per PRD §11: what is collected (email, interests, signup IP,
      UTM source), why, retention, and how to leave (unsubscribe/erasure)
- [ ] Linked from the footer (already wired in #0017). ~~and "next to the signup
      button" once #0029's `SubscribeForm` exists~~ — the signup-button half was
      **transferred to `#0029`** as a binding criterion at this issue's review,
      2026-08-18 (precedent: `#0018`→`#0017`, `#0022`→`#0019`). Do not treat it
      as outstanding here
- [ ] Single `<h1>`, correct heading hierarchy, composed from the motif
      components — no bespoke one-off styling
- [ ] Real, accurate copy — not lorem ipsum. Flag anything needing the user's
      input (e.g. exact retention windows, the erasure process's turnaround
      time) rather than inventing facts about the group's practices

### Tense decision — present tense kept, with one explicit disclosure line

The review flagged, non-blocking: every mechanism this page describes (double
opt-in, one-click unsubscribe, erasure) is written in the present tense for
code that does not exist yet — migrations stop at `000008`; there is no
`subscribers` table, no `/api/subscribe`, no `SubscribeForm`, no mail path
(`#0023`-`#0039`, `#0060` all `open`). The review offered two options:
soften every mechanism to "when you subscribe, we will …", or carry one line
stating the list isn't open yet.

**Decision: kept the present tense throughout, and added one explicit line**
to the intro `TerminalPanel` — "Mailing-list signup is not open yet. This
policy documents the commitment we are making about it in advance, so it is
accurate from the moment signup does open — nothing below describes something
already happening to you today."

Reasoning:
- Rewriting seven sections' worth of mechanism descriptions into conditional
  future tense ("when you subscribe, we will collect…", "if you ask us to
  erase your data, we will…") throughout is a much larger surface for
  reintroducing exactly the kind of factual drift this bounce was about —
  more sentences rewritten means more chances for a new mismatch against
  §6.2 or `#0060`. A single disclosure line is a much smaller, more
  auditable change.
- A privacy policy conventionally *is* written in the present tense as
  a standing commitment — "we collect X, we retain Y for Z" — independent of
  whether the mechanism is live at every moment a reader visits. A brand-new
  company routinely publishes its privacy policy before its product ships,
  precisely so the policy is already correct and public when the product
  does launch. That is the posture here.
- The one-line disclosure directly addresses the reviewer's actual concern —
  a visitor coming away believing they can subscribe right now and have data
  handled exactly as described — without requiring the rest of the page to
  read as hedged, provisional draft copy for a legal document that is
  otherwise meant to be taken at face value once signup does open.
- This is the same choice `#0070`'s own original Notes anticipated ("this
  page may need a follow-up pass once [#0033-#0039, #0060] land if the
  shipped mechanics differ") — a natural follow-up already exists in the
  queue's shape, so a one-line disclosure now rather than a full future-tense
  rewrite doesn't leave the page permanently wrong, only temporarily
  forward-looking, which is disclosed.

### Blocking — "That is the complete list" is still not strictly true

`web/src/views/PrivacyPolicy.svelte:94` closes the five-item "What we collect"
list with:

> That is the complete list of what signing up for the list collects.

I read every column on §6.2's `subscribers` table against that list. The five
items correctly cover `email`, `subscriber_interests`, `signup_ip`, `created_at`
(as "the timestamp of your signup"), `signup_user_agent`, and all three of
`utm_source` / `utm_medium` / `utm_campaign`. Six columns are ignorable —
`id` (surrogate key), `updated_at` (bookkeeping), `status` (a state we assign,
not data we obtain), and `unsubscribed_at` / `unsubscribe_source` (a later event,
outside signup). That leaves the break:

1. **`confirmed_at` — the decisive one, because this page contradicts itself.**
   The Consent section, two sections below, now reads "the confirming click
   **separately** records its own timestamp". That wording affirmatively places
   the confirmation timestamp *outside* the five-item list — and the list is
   closed by "That is the complete list." The page therefore says both "this is
   everything" (line 94) and, some 45 lines later, "here is an additional thing
   we record" (line 141).
   And the confirming click is unambiguously part of signing up: the same
   section opens "Signup uses double opt-in: you submit the form, then confirm."
   This defect needs no schema reading at all — it is visible on the face of the
   document.

2. **`manage_token` (`TEXT UNIQUE NOT NULL`) and `confirm_token` (`TEXT
   UNIQUE`).** Both are minted and stored as a direct consequence of signing up;
   `manage_token` is a long-lived per-subscriber credential that rides in every
   unsubscribe/preferences URL. A reader parsing "the complete list of what
   signing up for the list collects" in its plain sense would count a persistent
   identifier tied to their address. I accept the narrower reading — that "collect"
   means *obtain from or about you*, under which self-minted tokens sit outside
   the claim — and I would not bounce on the tokens alone. `confirmed_at` breaks
   the sentence under **both** readings, which is why this is blocking.

The magnitude here (a timestamp, two tokens) is smaller than the first bounce's
denial of `signup_user_agent`. The *direction* is identical: a privacy policy
asserting it holds less than it holds. This is the second attempt at a sentence
of this exact shape and the second time it overreaches, which is the argument for
not accepting a third absolute.

**Fix — pick either, both are one line.** Preferred: drop the absoluteness, e.g.
"That is everything the signup form itself collects — see Consent below for the
confirmation record." Alternative: add the confirmation timestamp as a sixth
list item and keep "complete list." The first is the durable choice: §6.2's table
does not exist in code yet (`#0025` is still `open`, migrations stop at
`000008`), so a completeness claim pinned to an unwritten migration will drift
again the moment the schema gains a column. A privacy policy owes the reader an
accurate enumeration; it does not owe them the word "complete."

### Two maintenance traps in the gate, both non-blocking, worth recording

- **The comment-evasion is real and deserves a Gotcha.** The gate greps only
  `web/src/`, so `deploy.sh`'s own header and `die` message contain the literal
  `[PLACEHOLDER:` harmlessly. The constraint binds *only* files under
  `web/src/` — and `PrivacyPolicy.svelte`'s header comment dodges it by writing
  `a bracketed "PLACEHOLDER" marker (see the literal text below)`. It works
  (none of the five hits came from that comment). But the consequence is that no
  file under `web/src/` can ever name the marker it documents, including the very
  component that uses it. A maintainer who later writes the literal string in an
  explanatory comment gets a deploy failure whose message points at `#0075` and
  at body copy, and goes hunting for a placeholder that is really a comment.
  Judgment: deliberate and defensible, but it is a trap. Cheap hardening if
  anyone touches this again — have the gate ignore `//`/`<!--` comment lines, or
  match the marker only as it appears in rendered copy.
- **`--help` uses a hardcoded `sed -n '2,30p'`.** The header grew three lines, so
  the window still covers the full gate list through gate 6 and now spills one
  code line (`set -euo pipefail`) instead of the three it spilled before — so
  this commit slightly improved it and broke nothing. It stays fragile: a gate 7
  would silently truncate the help text. Not this issue's problem to fix.
