## Description

The site footer (#0017) links to `/privacy` per PRD §11 — the site collects
email, interests, signup IP, and UTM source, and both PRD §11 and the
signup flow require a documented, linked privacy policy. The page itself does
not exist yet: `/privacy` is not a route the router recognizes, so it
currently resolves to the terminal-styled 404 (#0022) rather than a broken
link.

> 🟢 Resolved 2026-08-19 — Third review pass: the twice-bounced completeness claim is gone (dropped rather than extended, and the replacement now discloses `confirmed_at` and the `manage_token`/`confirm_token` pair outright), the three further absolutes the implementer caught on its own sweep each check out against PRD §6.1, §6.3, and §6.6, and my independent sweep found no remaining claim that understates what the page holds — the five `[PLACEHOLDER: ...]` facts remain outstanding under `#0075` and `scripts/deploy.sh` gate 1 keeps the page from deploying until they are answered.

## Acceptance criteria

- [ ] `/privacy` is a recognized static route in `web/src/lib/router.ts`
      **and in `internal/handlers/routes.go`'s `knownStaticRoutes`** — added at

      `#0071`). Edit only `router.ts` and `/privacy` ships as a fully rendered

      **200**

      header/footer shell like Home/About
- [ ] Covers, per PRD §11: what is collected (email, interests, signup IP,

## Fix

Added `PrivacyPolicy.svelte`, composed entirely from the existing motif
components (`TerminalPanel`, `Prompt`, `Panel`, `StatusList`, `TraceDivider`)
following `About.svelte`'s pattern exactly — one `<h1>` ("Privacy Policy")
inside the intro `TerminalPanel`, then `<h2>`-headed sections for what's
collected, why, retention, consent, how to leave, CAN-SPAM, contact, and
change history. Wired into `App.svelte` alongside `Home`/`About`.

`/privacy` was added to **both** route tables in the same commit:
`web/src/lib/router.ts`'s `STATIC_ROUTES` (as a new `'privacy'` `RouteName`
member) and `internal/handlers/routes.go`'s `knownStaticRoutes` — the entry
format matches the file's existing single-quoted style exactly, no trailing
comment, defined only inside the literal (per the task's explicit
constraints, since `#0071`'s guard cannot see anything outside the table).

Went beyond the acceptance criteria's letter in two ways `#0071`'s Notes
implied were expected of a "new public route": added `/privacy` to
`internal/seo/seo.go`'s `defaultStaticRouteMeta` (its own title/description/
OG tags, matching `/about`'s treatment) and to
`internal/seo/sitemap.go`'s `marketingRoutes` (so it appears in
`sitemap.xml` with a `<lastmod>`), plus updated the existing seo/sitemap
tests that enumerate the static route set so the new route is actually
exercised rather than merely not breaking anything.

The footer's existing `/privacy` link (`#0017`) needed no changes — it
already pointed at the right path. Updated its stale doc comment, which
described the page as not-yet-existing.

The "next to the signup button" placement from the criteria could not be
done: `#0029`'s `SubscribeForm` does not exist yet (still `open`). Left as
future work for whichever issue builds that component, per this issue's own
Notes.

**Four facts are marked `[PLACEHOLDER: ...]` inline in the copy** rather than
invented, because nothing in `PRD.md`, `CLAUDE.md`, or the codebase
establishes a real value:
1. The exact data-retention window after unsubscribe/erasure.
2. The erasure-request turnaround time (PRD §11 only commits to *immediate*
   unsubscribe honoring, not a specific erasure SLA).
3. Whether `hello@opencircuitsf.com` (the existing site-wide contact address,
   used as-is elsewhere) is the right address for privacy requests
   specifically, or whether a dedicated address is wanted.
4. The legal entity name/type behind "Open Circuit SF" (unincorporated
   group, LLC, nonprofit, etc.) — not stated anywhere in the source material.

A fifth gap is flagged in the CAN-SPAM section but is not new to this
issue: the physical mailing address PO box (`CLAUDE.md` §10 open item #3,
"not started") is placeholder text there too, since the address does not
exist yet to be truthfully stated.

The GDPR/CCPA posture (double opt-in, hard-delete-plus-suppression erasure)
and CAN-SPAM commitments (immediate unsubscribe) described on the page are
PRD §11's *stated design*, not yet-shipped code — `#0026`, `#0033`-`#0039`,
and `#0060` are all still `open`. This mirrors the issue's own Notes, which
anticipated exactly this and asked for a follow-up pass once those land if
the shipped mechanics differ from what's written here.

### Bounce fix (2026-08-19, `22ec78a`)

The 2026-08-18 review bounced this issue on three copy overclaims and a
missing deploy-time gate for the `[PLACEHOLDER: ...]` markers. Fixed all four,
judged against `PRD.md` §6.2's actual `subscribers` schema and `#0060`'s
acceptance criteria rather than against intent:

1. **"We do not collect anything beyond this at signup"** (was
   `PrivacyPolicy.svelte:70-74`, before this pass) — false against §6.2, which
   also stores `signup_user_agent`, `utm_medium`, and `utm_campaign`. Fixed by
   widening the "What we collect" `StatusList` to five items (added the user
   agent line, widened "the UTM source" to "the UTM parameters
   (source, medium, campaign)") and replacing the denial with "That is the
   complete list of what signing up for the list collects." — the sentence is
   now true because the list above it is now the full schema, not a
   PRD §11 four-item summary. The parallel "Why we collect it" list was
   widened the same way for internal consistency (not itself a review
   defect, but leaving it narrower than "What we collect" after fixing only
   one list would have reintroduced the same kind of mismatch).
   Schema proof: `subscribers` has `signup_user_agent TEXT`, `utm_source
   TEXT`, `utm_medium TEXT`, `utm_campaign TEXT` as four distinct columns
   (`PRD.md` §6.2).

2. **"the confirming click's IP address and timestamp are recorded alongside
   it"** (Consent section) — describes a confirm-IP column that does not
   exist and will not. Fixed by rewriting to: the signup's IP and timestamp
   are the evidence of consent (already stated in "What we collect"), and the
   confirming click separately records only its own timestamp, "not a second
   IP address" — stated explicitly so a reader can't infer two IPs are kept.
   Schema proof: `subscribers` has `signup_ip INET` (`-- consent evidence`)
   and `confirmed_at TIMESTAMPTZ`; there is no `confirm_ip` or equivalent
   column anywhere in §6.2.

3. **"You can request that we delete your data entirely"** (Erasure
   paragraph, "How to leave") — overstated the designed erasure. Fixed by
   naming the specific record now deleted (email, interests, signup details)
   and enumerating, in a new `StatusList`, the three things `#0060`
   deliberately retains: the permanent suppression entry, anonymized
   `email_sends` rows (so historical campaign counts don't change), and the
   raw `email_events` deliverability payloads with the identity linkage
   severed. Issue proof: `#0060`'s acceptance criteria state directly —
   "`email_sends` rows are anonymized rather than deleted, preserving
   campaign counts", "`email_events` retains the raw payload for
   deliverability forensics but the linkage is severed", and "Privacy policy
   documents what is retained after erasure and why."

4. **Deploy gate for the placeholders.** Added gate 1 to `scripts/deploy.sh`
   (renumbering the prior five gates 2-6), running before the SPA build:
   `grep -rn '\[PLACEHOLDER:' web/src/` and `die` on any match, naming
   `issues/0075.md` in the failure message. No unit test was added — the
   review explicitly rejected that route as leaving the suite permanently red
   until a human supplies facts nobody may invent, which contradicts
   `CLAUDE.md` §5's zero-failures contract. Verified the gate actually bites
   (see `## Verification`).

The tense decision the review flagged as non-blocking (present-tense copy
describing double opt-in, unsubscribe, and erasure for a signup flow that
does not exist in code yet — migrations stop at `000008`, no `subscribers`
table, no `/api/subscribe`) is recorded in `## Gotchas` below.

### Second bounce fix (2026-08-19, `c72ae1a`)

The 2026-08-19 review bounced this on one blocking item: the *replacement*
sentence from correction 1 above was a new instance of the same defect class —
an absolute closing claim the page's own facts contradict. Escalated to Opus
per `CLAUDE.md` §3 (same issue bounced twice).

**The blocking sentence.** `PrivacyPolicy.svelte:94` read:

> That is the complete list of what signing up for the list collects.

45 lines below, the Consent section said the confirming click "**separately**
records its own timestamp" — affirmatively placing `confirmed_at` *outside* a
list the page had just closed, while the same section opens by defining signup
as the form plus the confirming click. The page contradicted itself on its own
face, no schema reading required.

**Fix: dropped the absoluteness rather than adding a sixth bullet.** The
reviewer offered both and argued for this one; I agree. `PRD.md` §6.2's
`subscribers` table does not exist in code yet (`#0025` open, migrations stop
at `000008`), so a completeness claim pinned to an unwritten migration drifts
the moment the schema lands. A paragraph that *describes* without claiming
closure cannot be falsified by a new column. The replacement also discloses the
reviewer's weaker second break (`manage_token` / `confirm_token`) outright,
which retires it permanently instead of relying on the narrow "obtain from or
about you" reading of *collect*:

- was (one muted `<p>`): "That is the complete list of what signing up for the
  list collects. This site does not run third-party analytics, ad trackers,
  external CDNs, or email open-tracking pixels — nothing on this site phones
  home to anyone but us."
- now (two `<p>`s): "Signing up also records the time you confirm your
  subscription (see "Consent" below), and generates the tokens that make your
  unsubscribe and preference-center links work." followed by the unchanged
  `CLAUDE.md` §9 sentence, still `text-muted`.

The paragraph was split so the new *collection disclosure* sits in normal body
text rather than the de-emphasized `text-muted` style — a disclosure of what is
stored should not be styled like a footnote. (This is the same styling concern
the reviewer raised as a non-blocking quibble about the tense-disclosure line;
that line is untouched, since promoting it is a presentation change to settled
copy.) The §9 sentence stays muted, exactly as before.

**Then swept the whole page for every other absolute or closed-set claim**, as
instructed, and checked each against what the code/design actually guarantees.
Three more needed work; the rest are guaranteed and were left alone. Full
enumeration in `## Gotchas` → "Absolute-claim sweep".

1. **"interests — so we only send you workshops you actually asked to hear
   about"** (`Why we collect it`) — not guaranteed, and contradicted by the
   bullet directly above it. §6.6's audience-predicate table has an `all` mode
   whose SQL predicate is *"(none — every active subscriber)"*, and §6.1 states
   subscribers with zero interests "receive only general announcements", so
   interest-independent sends are designed in. The adjacent bullet already
   promises "workshop announcements **and the occasional list update**".
   Rewrote to describe the targeting rather than promise a ceiling: "interests
   — so a workshop announcement can go to the people who asked about that topic
   instead of the whole list".
2. **"Nothing is added to the list until you confirm."** (`Consent`) — false
   against §6.3, which inserts the full row at form submit:
   `INSERT subscribers (status='pending', confirm_token=…, manage_token=…,
   signup_ip, signup_user_agent, utm_*)` plus `subscriber_interests` rows,
   *before* the confirmation email is sent. Same defect direction as both prior
   bounces — the policy claiming it holds less than it holds. Rewrote to state
   what is actually stored and what the confirmation gates: "Submitting the
   form stores your details with a pending status; the only email an
   unconfirmed signup receives is that confirmation, because every campaign's
   audience is drawn from confirmed subscribers." The second half *is*
   guaranteed — §6.6 materializes every audience with `WHERE s.status =
   'active'`.
3. **"after which it is deleted"** (`How long we keep it`) — an unqualified
   deletion claim about data that includes the permanently-retained suppression
   entry (your address, kept by design per `#0060`). The existing cross-
   reference ("see 'How to leave' below for what happens to your record") read
   as a pointer to the *process*, not to exceptions. Narrowed the claim to the
   record it applies to and made the pointer name the exceptions: "…after which
   your subscriber record is deleted. A few records outlive it by design — see
   'How to leave' below for which ones and why." **The erasure enumeration
   itself is untouched** — the reviewer settled it as one-to-one with `#0060`,
   and this only makes the retention section point at it correctly.

**`LAST_UPDATED` bumped `2026-08-18` → `2026-08-19`.** Not asked for, and
disclosed here as a judgment call: the page's own "Changes to this policy"
section commits to "if this policy changes in a way that affects what we
collect or how we use it, we'll update this page and note the date at the top",
and this pass changes exactly that (it newly discloses `confirmed_at` and the
tokens). Leaving the date at 2026-08-18 would have made the page break its own
stated commitment. Revert if the reviewer would rather the date track a
publication/effective date instead of the last copy edit — nothing else depends
on it.

Also added one bullet to the file's header `Copy notes` recording the
invariant, so a third pass cannot reintroduce a closure claim without deleting
a comment that explains why it was removed twice. The bullet deliberately does
**not** contain the bracketed marker literal, so it cannot trip `deploy.sh`
gate 1 (verified — the gate still reports exactly five hits, all body copy).

Nothing else was changed: not the five-item "what we collect" list, not the
confirm-IP correction, not the erasure enumeration, not `scripts/deploy.sh`,
not the tense decision or the disclosure line. `c72ae1a` touches one file.

## Gotchas

  `handlers.StaticRoutes()` — by design (auth/token routes must never appear

  longer exist in `web/dist/assets/`) — it is not meant to be servable, only

  by rewriting rather than `git checkout` was the right call per `CLAUDE.md`
  §8a, since another agent could plausibly have uncommitted edits to
  unrelated files at the same time.
- **`LAST_UPDATED` is a last-edited date, not an effective date.** The page's
  own "Changes to this policy" section promises to note the date whenever what
  the page collects changes, and the 2026-08-19 pass newly disclosed
  `confirmed_at` and the tokens — so the bump was required by the page's own
  commitment, not cosmetic. The page cannot actually deploy until `#0075` is
  answered (gate 1 blocks it), so when it does, set this to the real
  publication date.

### Tense decision — present tense kept, with one explicit disclosure line

The review flagged, non-blocking: every mechanism this page describes (double
opt-in, one-click unsubscribe, erasure) is written in the present tense for
code that does not exist yet — migrations stop at `000008`; there is no
`subscribers` table, no `/api/subscribe`, no `SubscribeForm`, no mail path
(`#0023`-`#0039`, `#0060` all `open`). The review offered two options:
soften every mechanism to "when you subscribe, we will …", or carry one line
stating the list isn't open yet.

**Decision: kept the present tense throughout, and added one explicit line**
to the intro `TerminalPanel` — "Mailing-list signup is not open yet. This
policy documents the commitment we are making about it in advance, so it is
accurate from the moment signup does open — nothing below describes something
already happening to you today."

Reasoning:
- Rewriting seven sections' worth of mechanism descriptions into conditional
  future tense ("when you subscribe, we will collect…", "if you ask us to
  erase your data, we will…") throughout is a much larger surface for
  reintroducing exactly the kind of factual drift this bounce was about —
  more sentences rewritten means more chances for a new mismatch against
  §6.2 or `#0060`. A single disclosure line is a much smaller, more
  auditable change.
- A privacy policy conventionally *is* written in the present tense as
  a standing commitment — "we collect X, we retain Y for Z" — independent of
  whether the mechanism is live at every moment a reader visits. A brand-new
  company routinely publishes its privacy policy before its product ships,
  precisely so the policy is already correct and public when the product
  does launch. That is the posture here.
- The one-line disclosure directly addresses the reviewer's actual concern —
  a visitor coming away believing they can subscribe right now and have data
  handled exactly as described — without requiring the rest of the page to
  read as hedged, provisional draft copy for a legal document that is
  otherwise meant to be taken at face value once signup does open.
- This is the same choice `#0070`'s own original Notes anticipated ("this
  page may need a follow-up pass once [#0033-#0039, #0060] land if the
  shipped mechanics differ") — a natural follow-up already exists in the
  queue's shape, so a one-line disclosure now rather than a full future-tense
  rewrite doesn't leave the page permanently wrong, only temporarily
  forward-looking, which is disclosed.
