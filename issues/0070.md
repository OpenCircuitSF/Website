## Description

The site footer (#0017) links to `/privacy` per PRD §11 — the site collects
email, interests, signup IP, and UTM source, and both PRD §11 and the
signup flow require a documented, linked privacy policy. The page itself does
not exist yet: `/privacy` is not a route the router recognizes, so it
currently resolves to the terminal-styled 404 (#0022) rather than a broken
link.

## Acceptance criteria

- [ ] `/privacy` is a recognized static route in `web/src/lib/router.ts`
      **and in `internal/handlers/routes.go`'s `knownStaticRoutes`** — added at
      `#0022`'s review, 2026-08-18. The two tables are hand-maintained mirrors
      and nothing fails when they diverge (proven in both directions; see
      `#0071`). Edit only `router.ts` and `/privacy` ships as a fully rendered
      page that the server answers with HTTP 404 — invisible in a browser,
      fatal for indexing. Add a `SPAHandler` test asserting `/privacy` returns
      **200**
- [ ] `PrivacyPolicy.svelte` (or similarly named) view, wrapped in the site
      header/footer shell like Home/About
- [ ] Covers, per PRD §11: what is collected (email, interests, signup IP,
      UTM source), why, retention, and how to leave (unsubscribe/erasure)
- [ ] Linked from the footer (already wired in #0017). ~~and "next to the signup
      button" once #0029's `SubscribeForm` exists~~ — the signup-button half was
      **transferred to `#0029`** as a binding criterion at this issue's review,
      2026-08-18 (precedent: `#0018`→`#0017`, `#0022`→`#0019`). Do not treat it
      as outstanding here
- [ ] Single `<h1>`, correct heading hierarchy, composed from the motif
      components — no bespoke one-off styling
- [ ] Real, accurate copy — not lorem ipsum. Flag anything needing the user's
      input (e.g. exact retention windows, the erasure process's turnaround
      time) rather than inventing facts about the group's practices

## Fix

Added `PrivacyPolicy.svelte`, composed entirely from the existing motif
components (`TerminalPanel`, `Prompt`, `Panel`, `StatusList`, `TraceDivider`)
following `About.svelte`'s pattern exactly — one `<h1>` ("Privacy Policy")
inside the intro `TerminalPanel`, then `<h2>`-headed sections for what's
collected, why, retention, consent, how to leave, CAN-SPAM, contact, and
change history. Wired into `App.svelte` alongside `Home`/`About`.

`/privacy` was added to **both** route tables in the same commit:
`web/src/lib/router.ts`'s `STATIC_ROUTES` (as a new `'privacy'` `RouteName`
member) and `internal/handlers/routes.go`'s `knownStaticRoutes` — the entry
format matches the file's existing single-quoted style exactly, no trailing
comment, defined only inside the literal (per the task's explicit
constraints, since `#0071`'s guard cannot see anything outside the table).

Went beyond the acceptance criteria's letter in two ways `#0071`'s Notes
implied were expected of a "new public route": added `/privacy` to
`internal/seo/seo.go`'s `defaultStaticRouteMeta` (its own title/description/
OG tags, matching `/about`'s treatment) and to
`internal/seo/sitemap.go`'s `marketingRoutes` (so it appears in
`sitemap.xml` with a `<lastmod>`), plus updated the existing seo/sitemap
tests that enumerate the static route set so the new route is actually
exercised rather than merely not breaking anything.

The footer's existing `/privacy` link (`#0017`) needed no changes — it
already pointed at the right path. Updated its stale doc comment, which
described the page as not-yet-existing.

The "next to the signup button" placement from the criteria could not be
done: `#0029`'s `SubscribeForm` does not exist yet (still `open`). Left as
future work for whichever issue builds that component, per this issue's own
Notes.

**Four facts are marked `[PLACEHOLDER: ...]` inline in the copy** rather than
invented, because nothing in `PRD.md`, `CLAUDE.md`, or the codebase
establishes a real value:
1. The exact data-retention window after unsubscribe/erasure.
2. The erasure-request turnaround time (PRD §11 only commits to *immediate*
   unsubscribe honoring, not a specific erasure SLA).
3. Whether `hello@opencircuitsf.com` (the existing site-wide contact address,
   used as-is elsewhere) is the right address for privacy requests
   specifically, or whether a dedicated address is wanted.
4. The legal entity name/type behind "Open Circuit SF" (unincorporated
   group, LLC, nonprofit, etc.) — not stated anywhere in the source material.

A fifth gap is flagged in the CAN-SPAM section but is not new to this
issue: the physical mailing address PO box (`CLAUDE.md` §10 open item #3,
"not started") is placeholder text there too, since the address does not
exist yet to be truthfully stated.

The GDPR/CCPA posture (double opt-in, hard-delete-plus-suppression erasure)
and CAN-SPAM commitments (immediate unsubscribe) described on the page are
PRD §11's *stated design*, not yet-shipped code — `#0026`, `#0033`-`#0039`,
and `#0060` are all still `open`. This mirrors the issue's own Notes, which
anticipated exactly this and asked for a follow-up pass once those land if
the shipped mechanics differ from what's written here.

## Gotchas

- `internal/seo/sitemap.go`'s `marketingRoutes` and `seo.go`'s
  `defaultStaticRouteMeta` are curated hand-lists, *not* derived from
  `handlers.StaticRoutes()` — by design (auth/token routes must never appear
  in the sitemap or get a marketing OG card). Neither is protected by
  `#0071`'s parity guard, so adding a new marketing route needs a conscious,
  separate edit to both. Nothing currently guards this the way the guard
  protects `router.ts`/`routes.go` — a plausible follow-up if more marketing
  pages are added later.
- Running the built binary requires `serve` as an explicit subcommand
  (`opencircuit serve`, not bare `opencircuit`) — the bare form only prints
  the version string and exits 0 with no listener, which looks like success
  at a glance if you don't check for the "listening on" log line or `lsof`
  the port. Cost a few minutes the first time.
- `web/dist/index.html`'s committed placeholder is genuinely stale (still
  titled "Short Links", references asset hashes from a prior build that no
  longer exist in `web/dist/assets/`) — it is not meant to be servable, only
  a git-tracked placeholder that `npm run build` overwrites. Restoring it
  by rewriting rather than `git checkout` was the right call per `CLAUDE.md`
  §8a, since another agent could plausibly have uncommitted edits to
  unrelated files at the same time.

Independently re-verified 2026-08-18 (phase 3 review). **Bounced** — the route,
the parity registration, the SEO/sitemap work, the composition and the suites
are all correct and re-proved below; the *copy* makes three factual claims the

### Blocking — copy states things the schema does not do

Judged against `PRD.md` §6.2 (the actual `subscribers` schema `#0025` will
build) and `#0060`, not against §11's prose summary. §11 is a four-item
*summary* of what is collected; §6.2 is the record definition, and it stores
more than §11 lists.

1. **`web/src/views/PrivacyPolicy.svelte:70-74` — "We do not collect anything
   beyond this at signup" is false as written.** §6.2's `subscribers` table also
   records `signup_user_agent`, `utm_medium` and `utm_campaign`. The four-item
   list above it is fine as a summary; the sentence that *closes* the list is
   not, and it errs in the harmful direction — a privacy policy that
   affirmatively denies collecting data the schema stores. This sentence is the
   implementer's addition, not the PRD's. Fix: add the signup user agent to the
   list and widen "the UTM source" to the UTM parameters (source, medium,
   campaign), or drop the closing sentence's absoluteness.

2. **`PrivacyPolicy.svelte:114-119` — "the confirming click's IP address and
   timestamp are recorded alongside it" describes a column that does not and
   will not exist.** §6.2 has `signup_ip` (INET, "consent evidence") and
   `confirmed_at` (a timestamp). There is no confirm-IP field. The sentence also
   contradicts this same page's "What we collect", which correctly says "the IP
   address and timestamp of your **signup**". A reader comes away believing two
   IP addresses are stored. Fix: the signup IP and timestamp, plus the
   *timestamp* of the confirmation click.

3. **`PrivacyPolicy.svelte:133-140` — "delete your data entirely" overstates the
   designed erasure.** `#0060` deliberately retains more than the suppression
   entry the page names: `email_sends` rows are *anonymized rather than deleted*
   to preserve campaign counts, and `email_events` keeps the raw deliverability
   payload with the linkage severed. `#0060`'s own acceptance criteria include
   "Privacy policy documents what is retained after erasure and why" — this page
   is that document, and it is the one place the retention is defensible if
   stated. It currently is not. Fix: name all three (suppression entry,
   anonymized send counts, retained deliverability events) and why.

Not blocking, but note the framing: every mechanism the page describes in the
present tense — double opt-in, one-click unsubscribe honored immediately,
erasure on request — is design intent, not shipped code. Migrations stop at
`000008`; there is no `subscribers` table, no `/api/subscribe`, no
`SubscribeForm`, and no mail path at all (`#0023`-`#0039`, `#0060` all `open`).
A privacy policy legitimately describes what happens *when you subscribe*, so
future-facing framing is defensible — but Phase 2 completing is exactly the
point at which this marketing site could go live, and it would go live telling
visitors about a signup flow and unsubscribe links that do not exist. Either
soften to "when you subscribe, we will …" or carry one line saying the list is
not open for signups yet. Implementer's call; not a bounce reason on its own.

**Verified true, independently:** the "no third-party analytics, ad trackers,
external CDNs, or email open-tracking pixels" claim (`CLAUDE.md` §9) holds
against the built artifact, not just the rule. The served `/privacy` HTML
contains zero off-host `src=`/`href=` attributes; the only external URLs
anywhere in `web/dist/` are the XML namespace on the SVGs, the SIL/GitHub URLs
inside the font `LICENSE`, a `svelte.dev` string in the bundle, and the
user-clicked `discord.gg` link — fonts are self-hosted (`#0012`), no CDN, no
beacon. That sentence may stand.

### Blocking — the placeholders must not be able to reach production

Confirmed by grep against the built bundle, not by reading the source: all five
`[PLACEHOLDER: …]` strings compile verbatim into
`web/dist/assets/index-CZd73sjj.js` and render as bold body text on the live
page. `go build`, `go vet`, `go test ./...`, `npm run check`, `npm test`,
`npm run build`, and all five of `scripts/deploy.sh`'s fail-fast gates pass with
them present. Nothing would catch this.

Marking the four unknowable facts rather than inventing them was **exactly
right** — that is the acceptance criterion working as intended, and it should
not change. The defect is that the marker is invisible to the toolchain.

Rejected: a unit test that fails while any `[PLACEHOLDER:` remains. It would
leave the repository's suite red until a human supplies four facts that are
nobody's to invent, which contradicts `CLAUDE.md` §5's zero-failures standard
and trains every later agent to step over a failing test. A guard that is
normally red is not a guard.

**Required instead: a gate in `scripts/deploy.sh`**, before the SPA build,
failing with `die` if `grep -rn '\[PLACEHOLDER:' web/src/` matches. That file is
already the fail-fast path to production with five numbered gates and is the
only route the binary reaches the host by; a sixth gate costs three lines, stays
silent during development, and fails loudly at the exact moment it matters.
Document it in the header comment's gate list like the others.

Also file a `blocked-on-user` issue for the five facts themselves (retention
window, erasure turnaround, privacy contact address, legal entity, PO box) so
they live in the queue rather than only in this issue's prose — `CLAUDE.md` §10
already tracks the PO box as open item #3, but the other four are tracked
nowhere.
