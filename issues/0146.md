## Description

`#0139` made every optional **string** field clearable by sending an explicit `""`. `capacity` cannot be fixed that way: it is `*int` on the wire, and JSON `null` and an absent key both decode to Go `nil`. `patchWorkshopRequest`'s merge is `if req.Capacity != nil { … }`, so there is no client-sendable value that means "clear it".

Symptom, from the admin's side: clear the capacity box, save, reload — the old number is back, with no error and no indication anything was ignored.

This is the same defect `#0139` fixed for strings, surviving in the one field whose type cannot express the distinction.

## Acceptance criteria

- [x] `capacity` can be cleared. Pick a wire representation that distinguishes "clear" from "unchanged" — a `json.RawMessage`, a wrapper type with an `explicitly set` flag, a `**int`, or a sentinel — and say why the chosen one fits this codebase
- [x] "Unchanged" still means unchanged: a PATCH that never mentions `capacity` leaves it alone. Prove it, the way `#0139`'s review proved the string case, by mutating the guard and watching a test fail
- [x] The admin UI actually sends the clear when the box is emptied
- [x] An end-to-end test reads the value back from the **database**, not the response body, for both clear and leave-alone
- [x] Check whether any other non-string optional field has the same shape and fix them together if so
- [x] `ISSUE=0146 scripts/check.sh go ./internal/...` and `scripts/check.sh web` both pass

## Root cause

`patchWorkshopRequest.Capacity` was `*int`. `encoding/json` decodes both an
absent `capacity` key and an explicit `"capacity": null` to the same nil
pointer, so the merge's `if req.Capacity != nil { capacity = req.Capacity }`
could never see the difference between "the admin never touched this field"
and "the admin explicitly cleared it." `#0139` had already given every
optional *string* field an in-band clear sentinel (an explicit `""`, since
`""` is never valid content once trimmed) — but no integer value can play
that role for `capacity`, so the bug survived exactly where `#0139` predicted
it would.

## Fix

Added `internal/handlers.Optional[T]` (`optional.go`): a small generic type
carrying `Value T`, `Present bool` (the key appeared in the JSON object at
all), and `Valid bool` (present with something other than `null`). Embedded
as a **plain value field**, `Capacity Optional[int] \`json:"capacity"\``, not
`*string`/`*int` and not `*Optional[int]`.

Why `Optional[T]` over the issue's other options:

- **Not `json.RawMessage`**: would need hand-rolled null/absent/value parsing
  repeated at every call site: pure boilerplate for a problem the type system
  can carry instead.
- **Not `**int`**: works, but (the issue's own words) "reads badly" — a
  double pointer at a call site is easy to get backwards, and nothing in the
  type says what the two pointer levels *mean*.
- **Not a field-specific sentinel** (e.g. `-1`): would need documenting and
  re-deriving for the next field of this shape, and risks colliding with a
  value that becomes legitimate later.
- **`Optional[T]` generalizes**, and this is the second time this codebase
  has needed the three-state distinction (after #0139's strings) — enough
  repetition that the general fix is now cheaper than another one-off, per
  the issue's own note. It is also the most self-documenting of the options:
  `req.Capacity.Present` / `.Valid` read as exactly what they check.

**The non-obvious part, found by testing rather than trusted from memory**
(as the issue asked): the *first* draft used `*Optional[int]` — pointer to
the wrapper — reasoning that a nil pointer would naturally mean "absent."
That does **not** work. `encoding/json` special-cases a JSON `null` for any
field whose own Go type is a pointer by setting that pointer straight to nil,
*before* ever asking whether the pointed-to type implements
`json.Unmarshaler` — so with `*Optional[int]`, an explicit `null` and an
absent key are indistinguishable all over again, reproducing this exact bug
one level down. Confirmed with a throwaway `go run` before writing the real
code, then locked in as `TestOptional_PointerFieldDoesNotWork` in
`optional_test.go` so a future "simplify this back to a pointer" edit fails
loudly instead of silently regressing. The working shape is a **plain,
addressable struct field**: `encoding/json` takes its address and always
calls `UnmarshalJSON` when the key is present, `null` or not — verified by
`TestOptional_DistinguishesAbsentNullAndValue`.

`Patch`'s merge:

```go
capacity := current.Capacity
switch {
case !req.Capacity.Present:
    // key absent from the PATCH body: leave capacity alone.
case !req.Capacity.Valid:
    capacity = nil // key present as `null`: explicit clear (#0146).
default:
    v := req.Capacity.Value
    capacity = &v // key present with a value.
}
```

`workshopView` (the response shape) and `createWorkshopRequest` both keep
plain `*int` — neither has a "clear" concept: a response never omits a
column to mean something, and Create has nothing to leave alone yet.

**Other non-string optional fields checked, per the acceptance criterion:**
every field of `patchWorkshopRequest` and `patchCampaignRequest`, plus a
repo-wide grep for `*int`/`*int64`/`*bool`/`*float` in `internal/handlers`.
Findings:

- `patchCampaignRequest` has **no** non-string optional field at all (`Name`,
  `Subject`, `Preheader`, `BodyMD`, `AudienceMode` are `*string`;
  `InterestIDs` is `*[]int64`, see below) — nothing to fix there.
- `InterestIDs *[]int64` (both patch structs) does **not** have this bug: an
  explicit `"interest_ids": []` already decodes to a non-nil pointer to an
  empty slice, distinct from the nil pointer an absent key produces —
  clearing to zero interests already worked before this issue.
- `patchInterestRequest.SortOrder *int` / `.Active *bool`
  (`internal/handlers/interests.go`) don't have it either: `sort_order` and
  `active` are `NOT NULL` columns (`migrations/000009_create_interests.up.sql`)
  with no "clear to NULL" concept to begin with — a plain pointer's two
  states (absent / provided) are the only two states that exist for them.
- Every other `*int64`/`*bool` hit in the grep (`campaignView.WorkshopID`,
  `.CreatedBy`, `admin_subscribers.go`'s `SoftBounce*`, `audit.go`'s
  `ActorID`/`UserID`/`TargetID`, `public_workshops.go`'s `Capacity`) is a
  **response** shape, never decoded from a client PATCH body, so the
  three-state problem cannot arise there.

`capacity` was the only field in this codebase with the shape #0146 describes.

**Client side** (`web/src/lib/workshopAdmin.ts`, `web/src/lib/api.ts`):
`ValidatedWorkshopFields.capacity` changed from `capacity?: number`
(omittable) to `capacity: number | null` (always present) — matching
`#0139`'s "always send the key" convention, but with `null` as the clear
sentinel instead of `#0139`'s `""`, because that is what the server's
`Optional[int]` reads as "clear." `PatchWorkshopFields.capacity` widened to
`number | null` to accept it. `WorkshopEditor.svelte`'s `save()` already
spreads the full `validateWorkshopForm` result into `updateWorkshop` — no
Svelte-file change was needed, only the two `lib/` type/logic changes.

## Gotchas

- The pointer-wrapper pitfall (`*Optional[T]` field type) described in
  `## Fix` is the load-bearing gotcha of this issue: it looks like the
  obviously-correct generic design (nil pointer = absent, by analogy with
  every other optional field in this file) and compiles and vets cleanly,
  but silently fails to distinguish `null` from absent — reproducing #0146
  one level down. `TestOptional_PointerFieldDoesNotWork` exists specifically
  so a future edit that "simplifies" this back to a pointer fails loudly.
- `interest_ids` looks at first glance like it could have the same shape as
  `capacity` (`*[]int64`, merged with a nil check) but does not: JSON's
  empty-array literal `[]` already gives it a non-nil-vs-nil distinction that
  integers have no equivalent of. Worth remembering as the general rule this
  issue's `Optional[T]` doesn't replace: only fields with **no spare wire
  value** to reuse need the wrapper.

### Ruling on `Optional[T]` as a general type: keep it

The issue asked for the wire representation to be *decided* rather than
defaulted, and the implementer's reasoning holds up against this codebase's
conventions:

- The cost of the "new API surface" objection is small here. `Optional[T]`
  lives in `internal/handlers`, so nothing outside this repository can ever
  depend on it; it is 30 lines with one method and no state beyond three
  fields. The alternative, `**int` on one field, is smaller in type count
  but not in cognitive cost — a reader of `capacity = *(*req.Capacity)` has
  to reconstruct what each pointer level means, whereas `req.Capacity.Present`
  / `.Valid` say it.
- It is used at exactly one site today, which is the honest count — but the
  three-state need has now arisen twice (every optional string in `#0139`,
  `capacity` here), and `#0139`'s solution only worked because strings had a
  spare in-band value (`""`) to spend. The next non-string nullable column
  will have no such spare value, and this is the thing it will reach for.
- `Gotchas`' framing is the right general rule and worth preserving: only a
  field with **no spare wire value** needs the wrapper. `interest_ids`
  genuinely does not (an explicit `[]` is already distinguishable from
  absent — re-checked, correct).

### The pointer pitfall is real — reproduced independently

Not taken on the implementer's word. A standalone throwaway module
(`go run`, outside the repo) with an instrumented `UnmarshalJSON` that logs
every invocation:

```
--- *Optional[int] (pointer field) ---
{}                   -> Capacity == nil            (UnmarshalJSON never called)
{"capacity":null}    -> Capacity == nil            (UnmarshalJSON never called)
{"capacity":7}       -> {Value:7 Present:true Valid:true}
--- Optional[int] (value field) ---
{}                   -> {Value:0 Present:false Valid:false}
{"capacity":null}    -> {Value:0 Present:true  Valid:false}
{"capacity":7}       -> {Value:7 Present:true  Valid:true}
```

`encoding/json` really does zero a pointer-typed field against a JSON `null`
without ever consulting whether the pointed-to type implements
`json.Unmarshaler` — the method is not called at all in that case. The
value-field placement is load-bearing, exactly as `optional.go` documents.

### Correction: `TestOptional_PointerFieldDoesNotWork` does not catch that regression

`## Fix` and `optional_test.go`'s own comment both claim the test exists "so
a future edit that 'simplifies' this back to a pointer fails loudly instead
of silently reintroducing #0146." Verified by mutation, and that attribution
is wrong. Changing `patchWorkshopRequest.Capacity` from `Optional[int]` to
`*Optional[int]` compiles clean, and then:

- `TestOptional_PointerFieldDoesNotWork` — **PASSES**. It asserts against its
  own locally-declared struct, never against `patchWorkshopRequest`, and what
  it asserts is a `encoding/json` invariant that holds regardless of what the
  handler does. It is a documentation test of the standard library, not a
  guard on this code.
- `TestOptional_DistinguishesAbsentNullAndValue` — **PASSES**, same reason.
- `TestAdminWorkshops_PatchClearsCapacityWithExplicitNull` and
  `TestAdminWorkshops_PatchWithoutCapacityLeavesItAlone` — **FAIL**, with a
  nil-pointer panic in `Patch` (`req.Capacity.Present` on a nil
  `*Optional[int]`) surfacing as a dropped connection.

So the regression *is* caught loudly, which is what matters — but by the two
DB-backed handler tests, not by the test credited with it. The two
`Optional` tests are still worth keeping as executable documentation. No code
change is required; the comment in `optional_test.go` and the `## Fix`
paragraph above simply overstate what that one test protects.

### Nonsense inputs — probed end to end, against the database

A throwaway reviewer-only test (not committed) PATCHed each body at a
freshly-seeded workshop with `capacity=30` and read the column back:

| Body | Status | Stored |
|---|---|---|
| `{"capacity": "12"}` | 400 | unchanged |
| `{"capacity": 12.5}` | 400 | unchanged |
| `{"capacity": 12.0}` | 400 | unchanged |
| `{"capacity": true}` / `[]` / `{}` | 400 | unchanged |
| `{"capacity": 99999999999999999999}` | 400 | unchanged |
| `{"capacity": -1}` | 200 | `-1` |
| `{"capacity": 0}` | 200 | `0` |
| `{"capacity": 3000000000}` | 500 | unchanged |

The type-error cases are handled correctly and — importantly — *safely*: a
malformed value leaves `Present: true, Valid: false` on the partially-decoded
struct, which would read as "clear it", but `decodeJSON` returns an error and
`Patch` answers 400 before the merge is ever reached. No path exists where a
type error silently clears the column. Verified by reading `Patch`
(`admin_workshops.go:382-386`) and by the probe above.

The last three rows are **pre-existing gaps this commit neither introduces
nor worsens** — the old `*int` field decoded `-1`, `0` and `3000000000`
identically, and the merge stored them identically. There is no server-side
range check on `capacity` anywhere (`migrations/000020_create_workshops.up.sql:26`
is a bare `capacity INT`, and neither `Create` nor `Patch` validates), so the
only thing rejecting a negative or zero capacity is
`workshopAdmin.ts`'s client-side `Capacity must be a positive whole number`.
An API client can store `-1`, and any value above 2^31-1 becomes a 500 from
the Postgres `INT` overflow rather than a 400. **Worth filing as its own
issue** (server-side capacity validation: reject `< 1` and `> 2147483647`
with 400); deliberately out of scope here, since `#0146` is about the wire's
three states, not about the value's range.

### Nits, not blocking

- `admin_workshops_test.go:678` prints a `*int` with `%v`, so the failure
  message reads `Capacity = 0x4e913c864ee0 …` instead of the value. Cosmetic,
  and only visible when the test is already failing.
- `Optional[T]` implements `UnmarshalJSON` but not `MarshalJSON`. It is
  decode-only today and correctly so, but if a future author embeds it in a
  response struct it will marshal as `{"Value":…,"Present":…,"Valid":…}`.
  One line in the doc comment saying "request bodies only" would close that
  door.
