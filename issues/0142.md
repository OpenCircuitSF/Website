## Description

`#0135` widened the partial index in `migrations/000020` from `WHERE status = 'published'` to `WHERE status <> 'draft'`, so it now covers published **and** canceled workshops. The name stayed `idx_workshops_published`.

That was a deliberate, defensible call — the implementer judged the Go method name (`ListPublished` → `ListVisible`) to be the misleading surface that mattered, and both the migration comment and `docs/database.md` explain the predicate. The residual risk is narrow: someone meeting the index through `\d workshops`, with no comment in sight, reasonably concluding the schema drifted from its own naming.

The reason to file rather than shrug: **this is a three-line edit only while the greenfield exception holds.** `CLAUDE.md` §1 lets `migrations/` be rewritten until the first deploy applies a migration to production. After that, renaming an index means a new migration, and nobody will bother — the name will be wrong for the life of the project.

## Root cause

`#0135` widened `idx_workshops_published`'s predicate from `WHERE status = 'published'` to `WHERE status <> 'draft'` so the index would keep covering `Store.ListVisible`'s query once the public listing started showing canceled workshops alongside published ones. The predicate change was necessary and correct; the index's name was simply never revisited, so it kept claiming a narrower meaning ("published only") than what it now enforces.

## Fix

**Greenfield precondition checked first, per this issue's own last criterion.** `CLAUDE.md` §1's greenfield exception (migrations are editable in place, not append-only, until the first production deploy applies one) still holds: §7 confirms production currently serves only the static placeholder, no PostgreSQL instance holds real data, and `migrations/000020` — the migration this issue edits — was written in this same session (by `#0050`, further edited by `#0135`, both today). No evidence of any deploy exists anywhere in `CLAUDE.md`, `HANDOFF.md`, or the issue tracker. Proceeded with the in-place rename rather than stacking a new migration.

**Name chosen: `idx_workshops_visible`, not `idx_workshops_public`** (the issue's own suggestion). Reasoning: the index exists to serve exactly one Go method, `Store.ListVisible` (renamed from `ListPublished` by `#0135` for the identical reason — the old name stopped matching what the code does). Naming the index after that method keeps the two locked together for anyone who greps one and wants the other, and avoids introducing a third near-synonym (`published` / `public` / `visible`) into the codebase's vocabulary for the same concept. The predicate itself (`WHERE status <> 'draft'`) is unchanged — this is a pure rename, no migration logic changed.

Renamed in three places:
- `migrations/000020_create_workshops.up.sql` — `CREATE INDEX idx_workshops_published` → `CREATE INDEX idx_workshops_visible`; the preceding comment block gained one sentence naming the rename and its reason.
- `docs/database.md` — the `000020_create_workshops` row's index sentence updated to the new name, with a clause explaining the rename and pointing at `#0142`.
- `internal/workshops/store.go` — `ListVisible`'s doc comment (`Uses idx_workshops_published (...)`) updated to name the new index and note the rename's origin.

Grepped the whole tree (not just the three named files) for `idx_workshops_published` after the edits. Two occurrences remain outside the three files above, both deliberate history, left alone:
- `PRD.md:671` — the schema listing already showed the *pre-`#0135`* predicate (`WHERE status = 'published'`), i.e. it was already stale before this issue and was never kept in sync by `#0135` either. Out of scope for `#0142`'s three-line acceptance criteria (migration, `docs/database.md`, store doc comment); flagged in `## Gotchas` for whoever next reconciles `PRD.md` with the implementation.
- `issues/0050.md`, `issues/0051.md`, `issues/0135.md` — historical record of what was true when each was written or reviewed. Not edited, matching `#0135`'s own review precedent (Ruling 3) for its `ListPublished` → `ListVisible` rename.

## Gotchas

- **`PRD.md:671` still shows the index under the old name, with the pre-`#0135` predicate (`WHERE status = 'published'`) — pre-existing drift, not introduced here.** `#0135` never updated `PRD.md` when it widened the predicate (only `docs/database.md`, the migration, and the store doc comment), so `PRD.md`'s schema listing was already stale before this issue. `#0142`'s acceptance criteria name three specific files and don't include `PRD.md`; reconciling `PRD.md` with the implemented schema is a separate concern from this issue's scope (renaming, not re-syncing an already-drifted spec doc) and is left for whoever next touches `PRD.md` §6.2.
- **Renaming an index in place does not bump the migration's version number**, so `scripts/testdb.sh create` compares only version numbers and would silently hand out a stale template to the next per-issue database if the template weren't rebuilt by hand first (`scripts/testdb.sh template`) — flagged explicitly in the dispatch brief and confirmed here: worth remembering for any future cosmetic in-place migration edit.
- The natural (non-forced) planner choice for this query is `Seq Scan` at the seeded row counts and selectivity used here — this is expected and already documented as a non-issue by `#0135`'s review (Ruling 1: `pgx`'s generic-plan mode does the same regardless of index name, and there's no performance requirement on a table that will hold "tens of rows" in production). Forcing `enable_seqscan = off` was necessary to observe the index actually being ridden, and the rename-vs-original counter-check inside a rolled-back transaction is what actually proves the rename is inert.

### Ruling 4 — `EXPLAIN` re-run independently; the index is used and the rename is inert

Own scratch database `opencircuit_test_0142revx` (created from the template,
dropped afterwards — §8b), 6000 throwaway rows with timestamp-suffixed slugs and
no literal id targeted, 2000 per status, `ANALYZE`d. Both halves of
`ListVisible`'s query, written with literals so the planner sees real values:

**Default planner.** The *past* half rides the index unforced —

```
Sort  (cost=456.50..458.72 rows=889)
  ->  Bitmap Heap Scan on workshops  (cost=25.39..412.95 rows=889)
        Recheck Cond: ((starts_at IS NOT NULL) AND (starts_at < now()) AND (status <> 'draft'::text))
        Filter: (status = ANY ('{published,canceled}'::text[]))
        ->  Bitmap Index Scan on idx_workshops_visible  (cost=0.00..25.17 rows=889)
              Index Cond: ((starts_at IS NOT NULL) AND (starts_at < now()))
```

The *upcoming* half chose `Seq Scan` at ~37% selectivity, as the implementer
reported.

**With `enable_seqscan = off`**, the upcoming half produces exactly the shape
`#0135`'s review measured:

```
->  Bitmap Heap Scan on workshops  (cost=69.68..488.35 rows=2222)
      ->  BitmapOr  (cost=69.68..69.68 rows=2667)
            ->  Bitmap Index Scan on idx_workshops_visible   Index Cond: (starts_at IS NULL)
            ->  Bitmap Index Scan on idx_workshops_visible   Index Cond: (starts_at >= now())
```

**Rename counter-check.** Inside a transaction: `ALTER INDEX
idx_workshops_visible RENAME TO idx_workshops_published`, re-`EXPLAIN` both
halves under the same settings, `ROLLBACK`. Costs came back identical to the
digit — `611.87..617.42` (upcoming) and `456.50..458.72` (past), the same in
both directions — with only the index name differing in the plan text. After the
rollback `pg_indexes` shows only `idx_workshops_visible`. The rename is provably
inert, which is what the acceptance criterion asks.

My absolute costs differ from the implementer's (`611.87` vs `1648.72`) purely
because I seeded narrower rows and projected three columns instead of the full
`workshopColumns` list; the *shapes* and the before/after equality — the things
the criterion is about — match exactly.

`#0135`'s review separately established that under `pgx`'s generic plan
(`status = ANY(ARRAY[$1,$2])` with unknown parameters) Postgres cannot prove the
predicate implies `status <> 'draft'` and falls back to `Seq Scan` regardless of
the index's name. That is pre-existing, name-independent, and per `CLAUDE.md` §5
nothing is owed on a table that will hold tens of rows. Not this issue's problem
and not a bounce.

### Ruling 5 — `PRD.md:671` needs its own issue, not a fix here

The implementer's find is real and correctly characterised: `PRD.md:671` still
reads

```sql
CREATE INDEX idx_workshops_published ON workshops (starts_at DESC)
    WHERE status = 'published';
```

— stale in **two** ways, and stale before `#0142` existed. `#0135` widened the
predicate without carrying it back to `PRD.md`, so the spec's schema listing has
disagreed with `migrations/000020` since `77b93e7`; `#0142` adds the name to
that disagreement.

**Ruling: file it as a separate issue; do not fold it into this rename.** Three
reasons:

1. **The predicate half is a spec decision, not a typo.** `PRD.md` is the
   document everything else is checked against, and `WHERE status =
   'published'` is the *old visibility rule* — the one `#0135` deliberately
   replaced. Correcting it means recording `#0135`'s decision in the spec, which
   deserves its own commit message and its own review, not a line slipped into a
   rename's resolution.
2. **The right unit of work is wider than one line.** `CLAUDE.md` §11 records a
   prior "currency pass that synced §6.2, §8, and §9 to what actually shipped",
   so §6.2 *is* meant to track the implementation — and this row escaped that
   pass. Whoever fixes it should sweep §6.2's schema listing against
   `migrations/` rather than patch the one line a grep happened to surface.
3. **The reason it drifted silently is itself the finding.**
   `TestDatabaseDocMigrationParity` guards `docs/database.md` and `CLAUDE.md`,
   but nothing guards `PRD.md`. The new issue should decide whether to extend
   that guard to the PRD's schema block or to state explicitly that the PRD is
   narrative and `docs/database.md` is authoritative. That is a design call this
   review should not make by fiat.

Mechanically it also keeps this review's commit honest: per §8a and the dispatch
brief, only `issues/0142.md` is committed here, and a `PRD.md` spec edit does
not belong in a commit titled `#0142 Resolve`.

For the orchestrator, the filing is cheap — the concrete edit is `PRD.md:671-672`
becoming

```sql
CREATE INDEX idx_workshops_visible ON workshops (starts_at DESC)
    WHERE status <> 'draft';
```

with the surrounding §6.2 rows checked against `migrations/` in the same pass.
Suggested framing: "PRD §6.2's workshops index is two revisions behind the
migration, and nothing guards the PRD against that."
