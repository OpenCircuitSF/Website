## Description

`TestAdminPending_Resend_RequiresSession` and the new
`TestAdminPending_ResendInvitation_RequiresSession` both POST at a **literal
id**: `/admin/subscribers/1/…`.

Harmless while the 401 holds — the request never reaches the store. **The hazard
is what happens when someone tries to prove the test discriminates.** Mutating
the auth guard, which is exactly how this phase has verified every other
assertion, sends a real `POST` at subscriber **1**. On a database where that row
exists, that burns a real **one-ever** invite re-send — `invite_resent_at` is
write-once and never cleared (`#0312`), so the effect is permanent.

**§8b was written from precisely this failure**: `#0024`'s guard-removal proof
aimed a `DELETE` at a hardcoded `/admin/interests/1`, the guard was gone by
design, and it destroyed a seeded taxonomy row. The rule that followed is
absolute — **never target a literal or seeded id in a test.**

Found by `#0367`'s review, which noticed it while deliberately *not* mutating
that one test for this reason. It took `RequiresSession` on trust as the only
one of six it did not re-prove.

## Acceptance criteria

   remains in either.
2. The 401 assertion still holds and still discriminates — **prove it by
   mutating the auth guard**, which is safe once the target is a throwaway row.
   That proof is the point: it is currently the one assertion in this family
   nobody dares check.
3. §8b: mutations run against **your own database** (`ISSUE=NNNN scripts/check.sh`

5. Per §5 name the specific tests that ran; `go build` passing is not

6. `gofmt` stability on every file touched.

## Fix

Both tests now seed a throwaway row and target its own id instead of the
literal `1`:

- `TestAdminPending_Resend_RequiresSession` calls the existing
  `seedPendingSubscriber` helper and posts to
  `fmt.Sprintf("%s/admin/subscribers/%d/resend-confirmation", srv.URL, id)`.
- `TestAdminPending_ResendInvitation_RequiresSession` calls the existing
  `seedInvitedPendingSubscriber` helper (added by `#0367`, which commits a
  real invite-mode import so the row carries a genuine `import_id`) and
  posts to the equivalent `resend-invitation` URL built from that id.

Both helpers already register `t.Cleanup` to delete the seeded row (and any
`outbound_queue` rows) regardless of pass/fail, so the row seeded for this
401 check is disposed of the same way every other test in this file
disposes of its fixtures. Each test's doc comment now states the hazard
explicitly, so the next reader does not reintroduce a literal id here.

**Criterion 2 — the discrimination proof, and the "burn" mechanic made
safe.** Ran in an isolated `git stash create` → `git archive` export
(CLAUDE.md §8b), against a dedicated scratch database
(`opencircuit_test_0372mut`, provisioned by a real `migrate up` through
`000026`, created and dropped by me) — never the shared tree, never the
shared database.

Mutated the auth guard two ways at once, mirroring `#0367`'s own approach
(each independently sufficient, both removed together): the mux wiring in
`adminPendingMux` (`requireAdmin(...)` wrapper stripped from both
`resend-confirmation` and `resend-invitation` routes) and each handler's own
`actor, ok := middleware.UserFromContext(...); if !ok { 401 }` check in
`admin_pending.go` (`ok` discarded, the early return removed).

With the guard gone, both tests fail — the 401 assertion genuinely
discriminates:

```
--- FAIL: TestAdminPending_Resend_RequiresSession
    (transport EOF — handler panics on a nil *AuthUser after the guard was
    removed, once the request reaches the code after the deleted check)
--- FAIL: TestAdminPending_ResendInvitation_RequiresSession
    admin_pending_test.go:501: status = 409, want 401
    (the advisory physical_address pre-check fires next and masks the 401,
    since the scratch DB's physical_address setting starts blank — itself
    confirmation the removed check was load-bearing)
```

To prove the *specific* hazard #0372 describes — that a real request
reaches the store and burns `invite_resent_at` — added one throwaway,
mutation-only probe test in the same isolated export (never committed):
seeded an invited row, set `physical_address` so the advisory pre-check
does not intercept first, sent an unauthenticated POST with the guard
removed, and read `invite_resent_at` back from the database directly
(bypassing the panicking response). Result:

```
admin_pending_test.go:736: CONFIRMED: unauthenticated request with guard
removed burned invite_resent_at = 2026-09-01 21:08:31.315304 -0700 PDT on
throwaway row 1 (would be permanent on a real row — CLAUDE.md §8b)
```

The row was id `1` in that fresh scratch database purely because it was the
first row inserted there — reached via the `id` variable returned by
`seedInvitedPendingSubscriber`, never via a literal in source, and disposed
of by the export's own `t.Cleanup` when the probe test ended. This is the
proof the issue asks for: the 401 discriminates, and the mechanism that
made a literal `1` dangerous (a real POST reaching the store and setting a
write-once column) is now demonstrated safely because the target is always
a throwaway row.

Restored: the real working tree was never touched (`git status --porcelain`
before and after the mutation round showed only my own two intended files
dirty; `git stash list` stayed empty throughout, confirming `git stash
create` never wrote to the stash or the working tree). Scratch databases
`opencircuit_test_0372mut` and `opencircuit_test_0373mut` dropped after use.

### Criterion 1 — no literal id remains, and the row is genuinely throwaway

Read both tests directly rather than trusting the `## Fix` prose. The only
numeric path segments left anywhere in `internal/handlers/admin_pending_test.go`
are the two `999999999` not-found sentinels (lines 401, 595) and two mentions of
`/1/` **inside the new doc comments**, which are prose about the hazard, not
targets. Both live tests now build their URL with `fmt.Sprintf(..., id)` from the
id their own helper returned.

The seeded rows are genuinely per-test, not a shared fixture:

- `seedPendingSubscriber` mints `zz-pending-subtest-<testdb.Unique()>@example.com`
  plus unique confirm/manage tokens, `RETURNING id`, and registers a `t.Cleanup`
  deleting the `outbound_queue` rows then the subscriber row.
- `seedInvitedPendingSubscriber` commits a real invite-mode import per call and
  cleans up `outbound_queue`, `subscribers` and `subscriber_imports`.

Nothing else in the package reads either row, so no test can depend on one
surviving. Cleanup is real, not aspirational — I watched it run: after my
mutation round the scratch database held no `zz-pending%` rows.

### Criterion 2 — the discrimination proof, re-done independently

Mine, not a re-reading of the implementer's. In a `git archive HEAD` export in
my scratchpad, against my own scratch database `opencircuit_test_0372rev`
(created by `scripts/testdb.sh create`, `schema_migrations` = 26, dropped after).

Baseline first, unmutated, so a failure could not be mistaken for a broken
export:

```
--- PASS: TestAdminPending_Resend_RequiresSession (0.03s)
--- PASS: TestAdminPending_ResendInvitation_RequiresSession (0.02s)
```

Then removed the guard at **both** layers, each assertion checked for
applicability before it was applied (a mutation that silently no-ops is the
usual way this proof goes wrong): the `requireAdmin(...)` wrapper stripped from
the two `resend-*` mux routes, and each handler's own
`actor, ok := middleware.UserFromContext(...)` / `if !ok { 401 }` block replaced
by `actor, _ := ...`. The patch asserted it found exactly the 2 guard blocks it
expected and that the mux text actually changed; afterwards `grep
StatusUnauthorized internal/handlers/admin_pending.go` returned nothing.

Both tests then fail:

```
--- FAIL: TestAdminPending_Resend_RequiresSession (0.03s)
    admin_pending_test.go:264: POST .../resend-confirmation: EOF
--- FAIL: TestAdminPending_ResendInvitation_RequiresSession (0.03s)
    admin_pending_test.go:503: status = 409, want 401
```

**The EOF is worth naming precisely, because it is the whole point of the
issue.** The panic is at `admin_pending.go:276`, `actorID := actor.ID` — which
sits *after* `AdminResendConfirmation` has already returned successfully. So the
unauthenticated request reached the store and mutated the row before the process
noticed there was no actor. That is exactly what the new doc comment on
`TestAdminPending_Resend_RequiresSession` claims, and it is true.

### Criterion 2, second half — the burn, reproduced against Postgres

The plain mutation does not by itself demonstrate the §8b hazard on the
invitation route: the advisory `physical_address` pre-check 409s first on a
fresh database, which is why the second failure reads `409, want 401` rather
than reaching the store. So I ran my own throwaway probe in the same mutated
export (never committed, deleted with the export): set `physical_address`, seed
an invited row through the helper, send an unauthenticated `POST`, and read
`invite_resent_at` back from the database rather than from the response, since
the handler panics after the write.

```
BEFORE: id=1 email=zz-pending-invite-subtest-359510237511681@example.com invite_resent_at=<nil>
transport error (expected: handler panics on nil actor after the store write): EOF
CONFIRMED HAZARD: unauthenticated POST with guard removed burned the write-once
invite_resent_at (nil -> 2026-09-01 21:19:31.931412 -0700 PDT);
outbound_queue rows for this subscriber = 2
```

Safe only because the target was a row my own helper had just seeded — which is
the issue's thesis, now demonstrated twice by two agents independently.

**One detail worth recording so it is not mistaken for a defect later.** The
seeded row's id in a fresh scratch database *is* `1`, because it is the first row
inserted there — my probe log shows it, and so does the implementer's. The fix's
protection is not that the number is different; it is that the number is
**derived from a row the test itself created**. On any database with prior rows
the two diverge, and that is the case §8b is about.

### Criterion 4 — the survey, re-verified rather than transcribed

Re-ran a tree-wide scan of my own over every `_test.go`, matching a numeric path
segment and looking for a mutating verb within the statement (two lines back, so
multi-line `doJSON(...)` calls are caught).

**My first attempt under-reported and I am recording that**, because it is the
instrument failure this project keeps hitting: I anchored the verb alternation
with `\b` on both sides, and `\b` cannot hold between a `"` and a `,`, so every
string-literal `"POST"` was silently invisible and the scan found only the
`http.MethodPost` sites. I rebuilt it with a **self-test on three known probes
that must produce known answers**, and it now refuses to report unless the
self-test passes and the result set is non-empty.

The self-tested scan finds **exactly the three instances the issue reports, and
no others**: `admin_subscribers_import_test.go:172` and `:471`
(`/admin/imports/1/revoke`) and `admin_workshop_announce_test.go:286`
(`/admin/workshops/1/announce`). Seven further mutating-verb sites all use a
`99999999`/`999999999` sentinel and are safe, matching the issue's own reading.
The four remaining small-number hits are false positives — `want 5/1/2`-style
format strings in `t.Errorf`, not URLs. `#0376` records the three correctly.

### One accuracy note, not a bounce

`TestAdminPending_ResendInvitation_RequiresSession`'s new comment says the burn
would happen "on any database where that row exists". Strictly it also needs
`physical_address` to be set — my own run got a 409 instead precisely because it
was blank. The comment therefore overstates the *danger* slightly, and only in
the direction of more caution; it cannot mislead anyone into relying on a safety
property that is not there, which is the failure mode this phase keeps bouncing
for. Left as written.
