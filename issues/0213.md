## Description

> ✅ **Resolved 2026-08-23** (`7e0762f`) — verified independently by the
> phase-3 reviewer at load average 1.41–1.67 (idle). `PORT` is now honoured end
> to end: `PORT=51873 ./scripts/dev.sh` served a request through Vite's `:5173`
> proxy that came back from the API on `:51873`, carrying a marker that exists
> nowhere but that run. `#0117`'s ten ownership functions are **byte-identical**
> across the commit and all 8 guard-test parts pass.

`#0117`'s phase-3 review read `scripts/dev.sh` closely while checking a
different claim, and found `PORT` does not do what the script says it does.

- `dev.sh:39,41` **hardcode** `http://localhost:8080` into `BASE_URL` and
  `WEBAUTHN_RP_ORIGIN`.
- `web/vite.config.ts` hardcodes **all four** proxy targets to `:8080`.

*(Corrected by `#0213`'s review: `web/vite.config.ts` does **not** spell `5173` — it inherits Vite's default. The Description below said otherwise.)*
- `dev.sh:177` prints `→ http://localhost:${PORT}`.

So `PORT=9999 ./scripts/dev.sh` starts the Go API on 9999, prints a URL naming
9999, and leaves Vite proxying to 8080 — where nothing is listening. The
override is half-honoured, and the half that works is the half that prints.

This is **pre-existing** and not introduced by `#0117`; the review surfaced it
while confirming `#0117`'s reasoning about why auto-picking a free port was
rejected. That conclusion still stands, on better grounds than the ones
originally recorded: `5173` genuinely *is* spelled into
`README.md:61`, `docs/dev.md:12,24`, `CLAUDE.md:209`, and three `dev.sh`
messages — so threading a chosen port everywhere is real work, even though
`$PORT` specifically is not threaded the way the note claimed.

**Why it is worth fixing rather than documenting away:** a half-honoured
override is worse than no override. Someone reaching for `PORT=` is usually
trying to avoid a collision — exactly the situation `#0117` addresses — and they
get a server that starts, prints a plausible URL, and serves a front end whose
API calls go nowhere.

## Notes

Reported by `#0117`'s phase-3 review under `CLAUDE.md` §9.

The simplest correct answer may well be the second criterion — delete the
override. `#0117` already gives a collision a good failure mode (refuse and
name the holder), so `PORT=` no longer has to be the escape hatch it once was.
Removing a knob that has never fully worked is cheaper than plumbing it through
`vite.config.ts`, and leaves less to get wrong.

If it is kept, note the Vite side needs the value at config-evaluation time, so
it has to come through the environment rather than being written into the file.

## Implementation notes

**Chose the first option — honour `PORT` — not the removal the issue leaned
toward.** The issue's own suggestion to delete the override did not account for
`scripts/dev_guard_test.sh`, which already depends on `PORT` steering the Go
server's bind port: it launches `PORT=$P1 ./scripts/dev.sh` (and `$P2`, `$P3A`,
etc.) repeatedly at arbitrary high ports specifically to test `#0117`'s
ownership logic without colliding with `:8080` or with other concurrent runs.
Hardcoding `PORT` to `8080` would have made every one of those guard-test
scenarios bind (or refuse to bind) at the wrong port, breaking the very test
this issue is required to keep green. So `PORT` had to stay a real,
fully-honoured override — the guard test settled the design decision, not
just verified it afterward.

Changes, scoped to `scripts/dev.sh` and `web/vite.config.ts` only:

- `scripts/dev.sh`: reordered the env-var block so `PORT` is resolved *before*
  `BASE_URL` and `WEBAUTHN_RP_ORIGIN`, then defaulted both off `${PORT}`
  instead of the literal `8080`. Individual overrides (`BASE_URL=...`,
  `WEBAUTHN_RP_ORIGIN=...`) still work as before.
- `web/vite.config.ts`: replaced the four hardcoded `http://localhost:8080`
  proxy targets with one `apiTarget` built from `process.env.PORT` (falling
  back to `8080` for anyone running `npm run dev` directly, outside `dev.sh`).
  `dev.sh` already `export`s `PORT` before invoking `npm run dev`, so Vite sees
  it at config-evaluation time — there is no other channel, since the config
  file runs once, before any request arrives.
- Updated `dev.sh`'s header/usage comment and the `-h/--help` `sed` line range
  (grew from `2,34p` to `2,40p`) to match the new comment block, and a couple
  of comments that named `:8080` literally now say `:$PORT`.
- Left `5173` untouched — it was already consistently hardcoded (not read from
  any env var) across `web/vite.config.ts`, `README.md`, `docs/dev.md`,
  `CLAUDE.md` §"dev.sh", and `dev.sh`'s own messages, so it already meets
  criterion 4 ("explicitly fixed, not silently half-configurable") without any
  change.

**Passkey origin (criterion 3).** `WEBAUTHN_RP_ORIGIN` now defaults to
`http://localhost:${PORT}`. In `--built` mode this is exactly correct — the
front end and API share one origin at `:$PORT`, matching what a browser would
send. In hot-reload mode the browser's real origin is `:5173` (Vite), not
`:$PORT`, so this value would be wrong for a real WebAuthn ceremony there —
but that mismatch is inert: `internal/middleware.DevAutoLogin` bypasses
WebAuthn entirely whenever `STORAGE=json` (`dev.sh`'s only mode), so no live
ceremony ever checks `WEBAUTHN_RP_ORIGIN` against a request `Origin` under
`dev.sh`. Threading it to `$PORT` anyway keeps the value honest about which
port the run actually used (rather than silently naming a fixed `8080`) and
makes `--built` mode correct, at no behavioral cost in hot-reload mode. Left a
comment in `dev.sh` explaining this so a future reader doesn't assume it's
exercised. `CLAUDE.md` §7's `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_ORIGIN` guidance is
about the real production origins (§10.2/`#0064`), which this change does not
touch.

Did not touch any of `#0117`'s port-ownership functions
(`descendant_pids`/`own_pids`/`proc_start`/`port_listeners`/`own_holds_port`/
`cleanup`'s fingerprint guards), the startup refusal, or `RECLAIM_PORTS=1` —
confirmed by `scripts/dev_guard_test.sh`'s byte-identity check on `dev.sh`
still passing (see Verification).

### The decision to honour `PORT` rather than remove it — settled by evidence

**The implementer's claim holds, and it inverts this issue's own
recommendation for a good reason.** `scripts/dev_guard_test.sh` does not merely
*use* `PORT`; every one of its eight scenarios depends on `PORT` genuinely
steering the Go server's bind port. It launches `dev.sh` at eight hardcoded
high ports — `54301`, `54311`, `54321`, `54331`, `54341`, `54351`, `54361`,
`54371`, `54381` — via `PORT="$P1" "$DEVSH"` and
`launch_group ... "PORT=$port"` (lines 251, 257, 276, 282, 305, 309, 349, 390,
399, 422, 450, 465, 498, 529, 546). Had `PORT` been hardcoded to `8080` as this
issue's `## Notes` leaned toward, all eight would have aimed at `:8080` — which
on this machine is permanently held by an unrelated
`com.apple.WebDriver.HTTPService` — and would additionally have collided with
each other and with any concurrent agent. The removal option was never viable.
The second acceptance criterion is therefore left unticked as **not taken**, not
as unmet; the criteria are explicitly `Or`-joined and the first is satisfied.

I confirmed this by reading the guard test, not by trusting the report.

### The Vite side is genuinely config-evaluation-time, and its fallback is right

`dev.sh:57` `export PORT=...` runs at the top of the script; `npm run dev` is
the last line (`cd web && npm run dev`), so `process.env.PORT` is populated when
Node evaluates `vite.config.ts`. Verified the resolved config directly with
Vite's own `loadConfigFromFile` under three environments:

| `$PORT` | resolved proxy targets |
|---|---|
| unset | all four `http://localhost:8080` |
| `51873` | all four `http://localhost:51873` |
| `''` (empty) | all four `http://localhost:8080` |

The empty-string case matters: `process.env.PORT || '8080'` is the correct
operator here — `??` would have produced `http://localhost:` for an exported
but empty `PORT`. No path yields `undefined` in a target. `server.port` is left
`undefined`, so Vite's own default `5173` applies (confirmed empirically: with
`PORT=51873`, Vite still bound `5173`).

### Passkey origin (criterion 3) — no path where a ceremony sees a mismatch

Verified in the source, not from the report.

- **`dev.sh`'s default mode.** `cmd/opencircuit/main.go:86` routes
  `STORAGE=json` to `serveDevMode`, which **never calls `auth.NewWebAuthn`** —
  no `webauthn.WebAuthn` is constructed on that path at all, so
  `cfg.WebAuthnRPOrigin` never reaches `RPOrigins` (`internal/auth/webauthn.go:38`,
  the only consumer). The auth handler is wired to `devstore.DevRegistrar{}`,
  `devstore.NewDevLoginService(ds)`, and `devstore.DevRecoverer{}`, whose
  registration/recovery methods return `auth.ErrTokenInvalid` or a flat error and
  never inspect a request `Origin`. `middleware.DevAutoLogin` mints the session
  instead. The implementer's "inert" claim is correct and stronger than stated:
  the ceremony machinery is not merely bypassed, it is never built.
- **`--built` mode.** `dev.sh:277–285` runs the same binary with the same
  exported `PORT` and `exec go run ./cmd/opencircuit serve`; the SPA is served
  from `web/dist/` by that binary, so browser origin and API origin are one and
  the same `http://localhost:$PORT` — exactly what `WEBAUTHN_RP_ORIGIN` now
  says, for the default `8080` and for any chosen port. Before this change it
  said `8080` regardless, which was *wrong* for `--built` at any non-default
  port. So `--built` moves from wrong to right; hot-reload stays inert.
- **The `#0117`-style trap does not exist here.** CLAUDE.md §7's warning is that
  `WEBAUTHN_RP_ID` and `WEBAUTHN_RP_ORIGIN` must agree. A port cannot desync
  them: the RP ID is host-only (`localhost`), and the origin's host is
  `localhost` at every value of `$PORT`. Threading the port is structurally
  incapable of breaking that pairing. `serveDevMode` independently derives the
  same value (`fmt.Sprintf("http://localhost:%d", cfg.Port)`) when the variable
  is empty, so the script and the binary now agree rather than disagree.
- Even under a deliberate `STORAGE=postgres ./scripts/dev.sh`, which would
  construct a real relying party: hot-reload was already mismatched (`:8080` vs
  the browser's `:5173`) and is equally mismatched now; `--built` was mismatched
  at a non-default port and is now correct. No path is made worse.
