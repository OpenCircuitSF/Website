## Description

An interest's **display name** can be changed at runtime; its **slug** cannot.
`Store.Update` takes no slug parameter, and `patchInterestRequest` has no slug
field under `DisallowUnknownFields`, so a `PATCH` carrying one returns **400**.
That immutability is deliberate — `#0023` designed it that way.

A migration could change a slug, but **nothing blesses or warns against that**,
and it is not obviously safe: preference-center links already issued to
subscribers encode interests, and `migrations/000009` is frozen so the seed
cannot be corrected at source (`#0471`).

Found by `#0471`'s review, which noted the gap matters most in exactly the case
that motivated the parent work.

## Why it is worth settling rather than leaving implicit

**`#0232`'s spinoff will hit this directly.** The user's scope for it includes
configurable domain nouns — "upcoming events which we are calling workshops for
this website but could be called something else". A second tenant with a
different taxonomy needs different slugs, not different display names, because
slugs appear in URLs and in the preference center's own semantics.

So the question "can a slug change, and at what cost" stops being hypothetical
the moment that work starts. Answering it now is cheap; answering it inside a
larger migration is not.

## Acceptance criteria

1. **Establish what actually breaks** when a slug changes. Trace every place a
   slug is persisted or transmitted — preference-center links, any stored URL,
   `subscriber_interests` if it references by slug rather than id, import
   mappings, campaign audience definitions. **Measure rather than reason**; this
   lineage has repeatedly found the code doing something other than what the
   prose said.
2. Decide the supported answer and record it: slugs are permanently immutable; or
   they may change by migration under stated conditions; or a rename path exists
   that also rewrites what depends on them. **Any of the three is acceptable — an
   unstated answer is not.**
3. If the answer is "immutable", say so where an operator will meet it — the
   admin API's own error, and `docs/mailing-list.md`'s taxonomy section, which
   `#0471` added.
4. **Do not weaken `#0023`'s design** to make a rename possible without deciding
   criterion 2 first. Slug immutability is a deliberate constraint, not an
   oversight.
5. Do not touch `000009` — it is frozen below production's applied version
   (`CLAUDE.md` §1, re-derived as `22|f` on 2026-09-08).

### The decision (criterion 2)

**Interest slugs may change, by migration, under the five conditions stated in
step 1 below. They stay immutable through the admin API, exactly as `#0023`
designed** — so criterion 4 is satisfied by construction: nothing in this plan
adds a slug parameter to `interests.Store.Update`, and nothing lets the runtime
channel write the column.

The measurement decides it. Every table that references an interest references
it **by `id`**, never by slug: `subscriber_interests`
(`migrations/000010_create_subscribers.up.sql`), `campaign_interests`
(`migrations/000017_create_campaigns.up.sql`), and `workshop_interests`
(`migrations/000020_create_workshops.up.sql`). No URL anywhere in the product
contains an interest slug — a preference-center link is
`{BASE_URL}/preferences?token={manage_token}` and carries nothing else. So a
one-statement `UPDATE interests SET slug = …` preserves the row's `id` and every
association that hangs off it, and breaks no issued link at all.

That makes the currently-documented replacement pattern — create a new interest
and deactivate the old one — **strictly worse than the thing it was protecting
against**: it changes the `id`, so it strands every subscriber, every campaign's
recorded segment, and every workshop tag on a row that no longer appears in the
signup form. The premise that justified it is false (see Finding 1).

**What the rejected options would have cost.** *Permanently immutable* costs a
downstream twelve permanently-dead rows and twelve orphaned subscriber sets for
a constraint with no measured technical basis — and it is the one answer
`#0232` would have to undo, since a second tenant's whole taxonomy is different
slugs. *A runtime rename path* (`PATCH` accepting `slug`) costs a store method,
a duplicate-slug 409, a new audit action, an admin form field, and its tests —
built against a case that has never arisen here and that `#0232`'s second tenant
will not use, because a second tenant **seeds** its own taxonomy rather than
renaming this one. That is `#0232`'s piece C, and the migration channel is
precisely the surface piece C already builds on.

**This is therefore a documentation-and-error-message change, not a feature.**
Four files, one new test, one extended test. No migration is written by this
issue, and `migrations/000009_create_interests.up.sql` is not touched
(criterion 5).

### Steps

1. **`docs/mailing-list.md` — replace the slug sub-bullet and add the third
   channel.** In the "Changing the taxonomy" section, the first bullet's
   `slug` sub-bullet currently gives a false reason ("a slug change breaks
   every already-issued preference-center link that references it") and
   prescribes create-new-and-deactivate as the replacement route. Rewrite that
   sub-bullet to say: the slug is immutable **through the admin channel**, that
   `interests.Store.Update` takes no slug parameter, that a `PATCH` carrying
   `slug` is refused with an explicit 400 rather than silently ignored, and
   that the reason is deliberate scope — a slug is the taxonomy's stable
   external name and changing it is a reviewed, recorded operation rather than
   a form field. Delete the create-new-and-deactivate advice; replace it with a
   pointer to the new third bullet. State plainly that create-new-and-deactivate
   is **not** the way to change a slug, because it mints a new `id` and strands
   every association.

   Then add a third top-level bullet, **"Changing an existing slug"**, stating
   the blessed shape and its five conditions:

   - The statement is `UPDATE interests SET slug = 'new-slug' WHERE slug =
     'old-slug';` in a new, additively-numbered migration. Never a delete plus
     an insert: that mints a new `id`, and `subscriber_interests`,
     `campaign_interests`, and `workshop_interests` all reference the row by
     `id`, so the associations would be cascaded away rather than carried
     across.
   - The new value must satisfy the lowercase-hyphenated `interests_slug_format`
     CHECK added in `migrations/000009_create_interests.up.sql`.
   - A collision with an existing slug raises a unique violation and aborts the
     migration. That is the correct fail-closed outcome and must not be softened
     with `ON CONFLICT`.
   - Re-running the migration is a no-op, because `WHERE slug = 'old-slug'`
     matches nothing the second time. Unlike the seed channel, the matching
     `.down.sql` **may** reverse it — `UPDATE interests SET slug = 'old-slug'
     WHERE slug = 'new-slug';` removes no row and fires no cascade, so the
     no-op-down rule that governs a seeded row does not apply here.
   - The migration must **not** rewrite `audit_log.metadata`. Audit rows record
     what an operator actually did at the time and are the consent-evidence
     record; a historical row naming a since-renamed slug is correct, not stale.

   Close the bullet with the two visible, fail-closed consequences an operator
   should expect, both measured in Finding 3: a stale browser tab holding the
   old slug gets a 400 "unknown interest" on its next preference save until it
   is reloaded, and a CSV import file still carrying the old slug is reported in
   the preview's `unknown_interest_slugs` rather than silently importing without
   the link.

2. **`internal/interests/store.go` — correct `Update`'s doc comment.** It
   currently states that renaming a slug "would break any already-issued
   preference-center link that references it by slug". That is false, and
   `#0023`'s own Gotchas section already said so at the time. Replace the
   sentence with the measured reason: nothing references an interest by slug —
   the three join tables all use `id` and no URL carries a slug — so the
   immutability here is a scope decision about the admin channel, and the
   supported way to change a slug is a migration, per the "Changing the
   taxonomy" section of `docs/mailing-list.md`. Do not change the method
   signature.

3. **`internal/handlers/interests.go` — make the refusal say why (criterion 3).**
   Today a `PATCH` carrying `slug` is rejected by `decodeJSON`'s
   `DisallowUnknownFields` and the operator sees `{"error":"invalid request
   body"}`, which is byte-identical to what a typo or malformed JSON produces.
   Make the refusal explicit:

   - Add `"encoding/json"` to the file's imports.
   - Add one field to `patchInterestRequest`, a `Slug` of type
     `json.RawMessage` tagged with the JSON name `slug` plus `omitempty`:

     ```go
     Slug json.RawMessage `json:"slug,omitempty"`
     ```

     `json.RawMessage` rather than `*string` deliberately, so that the mere
     **presence** of the key is refused whatever its value, including an
     explicit `null`, which a `*string` would decode to nil and let through as
     an empty patch.
   - Immediately after the `decodeJSON` call in `Patch`, and before any field is
     merged onto the current row, add:

     ```go
     if req.Slug != nil {
         writeError(w, http.StatusBadRequest, "an interest's slug cannot be changed through this endpoint — see \"Changing the taxonomy\" in docs/mailing-list.md for the migration that can")
         return
     }
     ```

   - Rewrite `patchInterestRequest`'s doc comment: the field exists **only** to
     produce this refusal, `interests.Store.Update` still takes no slug
     parameter, and the request is rejected outright rather than partially
     applied. Drop the false preference-center-link rationale here too, the same
     way step 2 drops it from the store.

   This does not weaken `#0023` (criterion 4): the store cannot write the column,
   the whole request is refused, and the enforcement moves from an incidental
   decoder rejection to an explicit, tested one.

4. **`internal/handlers/interests_test.go` — extend the existing assertion.**
   `TestAdminInterests_PatchUpdatesFieldsAndRejectsSlug` already issues exactly
   the request in question and asserts a 400 plus an unchanged slug. Add to it:
   read the response body and assert it contains the literal substring
   `slug cannot be changed`, so the message is pinned rather than decorative.
   Add a second request in the same test sending `{"slug":null}` and assert it
   is refused with the same 400, which is the case a `*string` field would have
   let through. Do not rename the test and do not add a new test function for
   this; the request under test is the one it already makes.

5. **`internal/db/interest_taxonomy_seed_freeze_guard_test.go` — pin that the
   blessed rename migration goes quiet.** The guard bans DELETE/TRUNCATE/DROP
   against `interests` and non-idempotent INSERTs; an `UPDATE interests SET
   slug = …` trips neither today. Add one test beside the existing six,
   following their naming pattern — the same interest-taxonomy migration-guard
   prefix, ending in a phrase for allowing a slug-rename update. (The identifier
   is described rather than written because the repo-wide citation guard
   requires an open issue's test-function citations to resolve against the tree,
   and this one does not exist yet; `CLAUDE.md` §8's `#0392` note is the
   precedent.) Feed it a `000031`-numbered up/down pair containing the exact
   statements step 1 blesses — the forward `UPDATE` in the `.up.sql` and its
   reversal in the `.down.sql` — and assert `interestTaxonomyGuardViolations`
   returns zero violations for both files. Model it on
   `TestInterestTaxonomyMigrationGuardAllowsIdempotentInsert`, which is the
   existing goes-quiet test.

   This step is not optional bookkeeping. `#0471` bounced on precisely this
   shape: the document prescribed a migration pattern that the guard in this
   same file rejected, and nothing caught the disagreement until a reviewer
   probed it by hand. Pinning the newly-blessed pattern is what stops step 1's
   prose and this guard drifting apart.

6. **Verify.** `ISSUE=0475 scripts/check.sh go ./internal/interests/...
   ./internal/handlers/... ./internal/subscribers/... ./internal/db/...` — the

## Findings

Criterion 1's trace, as measured. Commands are given so they can be re-run.

### 1. What an already-issued preference-center link encodes — the sharp question

**A `manage_token` and nothing else.** Every construction site builds the same
string:

```
grep -rn 'preferences?\|/manage' internal/mailing/*.go | grep -v '_test.go'
```

Four builders in `internal/mailing/transactional_templates.go` and one in
`internal/mailing/campaign_render.go`, all of the form
`baseURL + "/preferences?token=" + manageToken`. No interest slug is present,
and there is no second parameter.

Those links are therefore **fully durable across a slug change.** The premise
recorded in `internal/interests/store.go`'s `Update` doc comment, repeated in
`internal/handlers/interests.go`'s `patchInterestRequest` doc comment, and
repeated again in `docs/mailing-list.md` — that a rename breaks issued links —
is false, and was false when written. `#0023`'s own Gotchas section says so
explicitly in the same commit that introduced the rationale: "A
signup-confirmation or preference-center link that ever embedded a slug (none
currently do — everything keys off numeric interest ids)". The conditional was
correct; the doc comment dropped it and the two later copies inherited the
absolute form.

### 2. Where an interest slug is durably persisted — two places, one of them
correct to leave alone

Schema, measured against a scratch database at migration 27
(`scripts/testdb.sh create 0475p`, dropped afterwards):

```
psql "$PGURL" -tAc "select table_name||'.'||column_name from information_schema.columns
                    where table_schema='public' and column_name like '%slug%'"
```

returns exactly three columns — `interests.slug`, `workshops.slug`,
`email_campaigns.slug`. The latter two are unrelated namespaces.

```
psql "$PGURL" -tAc "select con.conrelid::regclass, con.confrelid::regclass
                    from pg_constraint con where con.contype='f'
                    and con.confrelid='interests'::regclass"
```

returns exactly three foreign keys — `subscriber_interests`,
`campaign_interests`, `workshop_interests` — **all on `interest_id`, all
targeting `interests(id)`**. Not one references the slug. This matches the
count `#0474` established and was re-derived here rather than carried over.

The only other durable home is `audit_log.metadata`, in two shapes, found by
grepping the audit writes:

- The interests CRUD handler records `"slug"` in the metadata of the
  `interest.created`, `interest.updated` (and its deactivated/reactivated
  variants), and `interest.deleted` entries.
- The manual-add path in `internal/handlers/admin_subscribers.go` records
  `"interests": req.Interests` — the operator-supplied **slugs** — in a
  `subscriber.manual_add` entry.

Both are historical records of what happened at the time, so a rename must not
rewrite them. That is a finding in favour of the migration channel rather than
against it, and step 1 states it as a condition.

### 3. Where a slug is transmitted but never stored

- `POST /api/subscribe` takes `interests: [slug, …]` and resolves them to ids
  before writing anything (`internal/handlers/subscribe.go`).
- `GET`/`PATCH /api/preferences` take and return slugs, resolved fresh on every
  request via `GetBySlug` / `GetByIDs`. The preference center's checkbox grid is
  built from whatever the server returns **on that request**, so after a rename
  a reloaded page is immediately correct.
- The confirm response, `GET /api/interests`, the public workshop payloads, the
  admin list, the admin dashboard, and the admin subscriber detail all carry
  slugs in JSON only.
- CSV import and CSV export both use a slug column, but those are operator-held
  files outside the database. `internal/subscribers/imports.go` reports every
  unrecognised slug through `UnknownInterestSlugs`, surfaced to the admin screen
  as `unknown_interest_slugs`, so a stale import file fails visibly rather than
  importing rows with no interest linked.

The one transient breakage a rename causes: a browser tab left open across the
change still holds the old slug, and its next preference save is refused with a
400 "unknown interest". The refusal covers the whole request, so no selection is
silently dropped — it fails closed and a reload fixes it.

### 4. Candidates named in the issue that turned out **not** to reference slugs

Stating these plainly, as asked:

- **Campaign audience definitions do not.** `campaign_interests` stores
  `interest_id`, `internal/mailing/audience.go` selects `interest_id`, and the
  admin campaign handler's own error text is "one or more interest ids do not
  exist". No slug is involved in targeting.
- **Import mappings do not persist one.** `subscriber_imports` has no interest
  column at all; `ImportStore.Commit` takes an in-memory
  `InterestSlugToID` map and writes `subscriber_interests` rows by id.
- **The outbound queue does not.** Every payload struct in
  `internal/mailing/outbox_worker.go` and its producer twin in
  `internal/subscribers/store.go` was read; the only interest-bearing one is the
  welcome payload, and it carries interest **names**, deliberately captured at
  confirm time so a later preference change cannot rewrite an already-queued
  email.
- **No stored or issued URL does.** `internal/handlers/routes.go` has no route
  containing "interest"; `web/src/lib/router.ts` has no interest route; the
  sitemap emits none. The two dynamic public paths are `/workshops/{slug}` and
  `/archive/{slug}`, which are workshop and campaign slugs.
- **No sent email does.** The footer's "Manage your interests" link is the
  `manage_token` URL from Finding 1; the campaign renderer never emits a slug.
- **No production code depends on a specific seeded slug value.** Each of the
  twelve seeded slugs was grepped across `internal/`, `cmd/`, and `web/src/`
  excluding tests: the only hits are decorative marketing copy in
  `web/src/lib/crtScreen.ts` and `home-automation` used as a form-placeholder
  example in `web/src/lib/admin.ts` and `web/src/views/Admin.svelte`. None is a
  lookup.
- **`internal/devstore` has no interests at all**, consistent with `CLAUDE.md`
  §5's note that `STORAGE=json` has no mailing list.

### 5. The current admin refusal is uninformative

`decodeJSON` sets `DisallowUnknownFields` and its caller maps any decode error
to `{"error":"invalid request body"}`. So a `PATCH` attempting a rename is
indistinguishable, to the operator, from a typo'd field name or a malformed
body. `TestAdminInterests_PatchUpdatesFieldsAndRejectsSlug` asserts the 400 and
the unchanged slug but not the message, so step 3's improvement is compatible
with the existing assertion and step 4 is what makes the message load-bearing.

### 6. Worth reporting to the orchestrator, not filed (§9)

Nothing here rises to a new issue. Two observations for the record: the false
preference-center-link rationale had propagated to three separate places before
anyone measured it, which is the same prose-outruns-code pattern `#0471`,
`#0474`, and `#0343` each hit in this lineage; and `docs/mailing-list.md`'s
second channel already blesses `UPDATE interests SET … WHERE slug = '…'` for
renaming a seeded default, which — read literally — already permitted a slug
change that the first bullet forbids. Step 1 resolves that ambiguity rather than
leaving two bullets disagreeing.
