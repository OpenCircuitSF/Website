## Description

`#0353`'s alias branch in
`internal/seo/invalidator_satisfier_guard_test.go` tests:

```go
types.Implements(target, invalidateOnly) ||
    types.Implements(types.NewPointer(target), invalidateOnly)
```

Measurement by `#0353`'s reviewer shows **both disjuncts are load-bearing, for
opposite reasons**:

| Alias | Implements in | Because |
|---|---|---|
| `type X = struct{ Site }` | **pointer form only** | value-embedding a pointer-receiver type |
| `type X = *struct{ *Site }` | **value form only** | `**struct` has an empty method set |

But **replacing the `||` with either disjunct alone leaves both
`TestInvalidatorSatisfierSet` and `TestInvalidatorSatisfierSet_AliasToTypeLiteral`
green.** The synthetic `FeedCache = struct{ *Site; cached []byte }` happens to
implement in both forms, so it cannot distinguish them.

Pointer-form-only then silently misses the pointer-to-literal alias;
value-form-only silently misses the value-embed alias. Both were verified to
reopen as real, uncaught gaps under those mutations.

This is the same family as `#0349` → `#0353`: a guard whose check is correct
while nothing pins the part of it that does the work.

## Root cause

`TestInvalidatorSatisfierSet_AliasToTypeLiteral`'s only alias-to-literal
fixture was `FeedCache = struct{ *Site; cached []byte }`, which embeds `*Site`
by **pointer**. A pointer-embedding literal implements
`interface{ Invalidate() }` in both the value form (`types.Implements(target,
…)`) and the pointer form (`types.Implements(types.NewPointer(target), …)`),
because a pointer field's promoted methods land on both the struct's value
method set and its pointer method set. So the fixture is satisfied by either
disjunct alone, and the `||` connecting them was untested: removing either
half left `FeedCache` — and therefore both tests — green.

## Fix

Verified the premise independently first, with a standalone `go/types`
program (not the fixture code, a separate script) checking
`types.Implements`/`types.Implements(*T)` against two hand-built alias
shapes:

```
AliasValueEmbed (`struct{ Site }`):        value-form=false  pointer-form=true
AliasToPointerLiteral (`*struct{ *Site }`): value-form=true   pointer-form=false
```

This matches the issue's table exactly, so no correction was needed.

Added both types to the synthetic source in
`TestInvalidatorSatisfierSet_AliasToTypeLiteral`:

- `AliasValueEmbed = struct{ Site }` — a **value** embed of the
  pointer-receiver `Site`, which implements only in pointer form (promotion
  from an embedded value field lands only on the pointer method set).
- `AliasToPointerLiteral = *struct{ *Site }` — an alias to a **pointer**
  literal, which implements only in value form (`target` is already the
  pointer type; wrapping it again with `types.NewPointer` produces
  `**struct`, whose method set is always empty).

Both are asserted reported by `scanInvalidatorSatisfiers` (criterion 1).
Extended the branch's doc comment to state both reasons for the `||`, naming
both alias shapes and which form each needs (criterion 3).

No change to `scanInvalidatorSatisfiers`' logic itself — the `||` was already
correct; only the test coverage and the doc comment changed.

### 1. The premise, re-derived from `go/types` rather than transcribed

Built a standalone `go/types` program (no dependency on the guard, the fixture,
or the implementer's script) over **twenty-two** alias shapes and printed
`Implements(T)`, `Implements(*T)`, and both method-set sizes for each. The
issue's table reproduces exactly:

| Shape | `Imp(T)` | `Imp(*T)` | value method set | pointer method set |
|---|---|---|---|---|
| `AliasValueEmbed = struct{ Site }` | **false** | true | 0 | 1 |
| `AliasToPointerLiteral = *struct{ *Site }` | true | **false** | 1 | 0 |
| `FeedCache = struct{ *Site; cached []byte }` | true | true | 1 | 1 |

**The subtle half was measured, not accepted.** Hand-built (not parsed) a
`struct{ *Site }` with `types.NewStruct` and walked the indirections:
`|MS(S)|=1`, `|MS(*S)|=1`, **`|MS(**S)|=0`**, `|MS(***S)|=0`, and
`types.Implements(**S, invalidateOnly)` is **false**. So the doc comment's
"`**struct`, whose method set is always empty" is true, and true for the
structural reason it gives — the Go spec allows methods only on defined types
and on pointers to them, so an unnamed pointer-to-pointer can never acquire
one. The `always` is warranted, not rhetorical.

### One finding handed to the orchestrator, not bounced

**Two more branches of the alias handling are unpinned by any test — C4 and
C5 above.** Disabling the alias-to-pointer-to-`*types.Named` `continue`, or
the declared-interface `continue`, leaves **every test in the tree green**
while the guard starts double-counting a redundant spelling. This is not a
defect against any criterion here: `#0354`'s criteria are about the `||`
alone, and `#0353`'s review already checked both `continue`s against
`go/types` truth and found them **correct**. What is missing is a *standing
test*, exactly as it was for the `||`.

The remedy is transcription, and I proved it rather than proposing it. Adding
three declarations to the same synthetic source —

```go
type DeclaredSeam interface{ Invalidate() }
type AliasToPtrNamed = *Site
type AliasToIfaceLiteral = interface{ Invalidate() }
```

— plus two negative assertions (`got["AliasToPtrNamed"]` and
`got["AliasToIfaceLiteral"]` must both be false) **passes unmutated**, **fails
under C4** naming `AliasToPtrNamed`, and **fails under C5** naming
`AliasToIfaceLiteral`. Note the pairing is not the obvious one: an alias to a
*declared* interface (`= Seam`) never reaches the interface `continue` at all,
because the `*types.Named` `continue` fires first — only an alias to an
interface **literal** exercises it. Measured, not reasoned.
