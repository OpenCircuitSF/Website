## Description

`#0056`'s announce shortcut formats the workshop's date and time range in **UTC** in the draft campaign body. `web/src/lib/workshops.ts` formats the same workshop in the **viewer's** timezone on the public page.

So a Bay Area reader sees Pacific time on the workshop page and UTC in the email announcing it — for an SF-based organization whose workshops are physical, in-person events. The label is present, so nothing is silently wrong, and an admin reviews the draft before sending. But the two surfaces disagree about the same event, and the one that reaches people's inboxes is the one in the wrong zone.

## Root cause

`admin_workshop_announce.go`'s `announceWhen`/`announceDateLayout` formatted
`wk.StartsAt`/`wk.EndsAt` with `.UTC()` before applying the layout. The zone
label (`MST` in the layout string, Go's placeholder for "whatever zone the
`time.Time` is currently expressed in") was always correct for *some* zone —
it just wasn't the zone a Bay Area reader expects for a physical SF event,
which is exactly what `web/src/lib/workshops.ts` renders on the public
workshop page (the viewer's local zone, which for the target audience is
almost always Pacific).

## Fix

Introduced `announceLocation`, a package-level `*time.Location` loaded once
via `time.LoadLocation("America/Los_Angeles")`, and switched `announceWhen`
from `.UTC()` to `.In(announceLocation)`. The existing `announceDateLayout`
needed no change — Go's `"MST"` reference field already renders whatever
zone abbreviation the `time.Time` carries, so it now prints `PST` or `PDT`
correctly depending on the instant. The same-day check used for the
short-form end time (`"6:00 PM to 8:00 PM"` vs. two full dates) was also
switched from comparing UTC calendar days to comparing Pacific calendar
days (`sameLocalDate`, renamed from `sameUTCDate`) — a workshop starting
late evening Pacific can already be the next UTC day, so the old UTC
comparison could split a same-evening event across two "different days" in
the rendered string.

**Configuration decision (recorded per the acceptance criterion): hardcoded,
not `config.Config`.** Open Circuit SF is a single, fixed Bay Area
organization — every other location-shaped value already in `config.Config`
is a pinned fact about this one org rather than a per-deployment knob
(`WEBAUTHN_RP_ID`/`WEBAUTHN_RP_ORIGIN` are fixed to `opencircuitsf.com`; the
CAN-SPAM `physical_address` setting names one building). `PRD.md` names no
requirement for a second venue in another timezone, and `CLAUDE.md` §5's
standing instruction is not to build for a requirement that doesn't exist.
Adding a `WORKSHOP_TIMEZONE` env var now would be one more thing every
deploy must configure correctly for a value that has never needed to vary.
The value is still isolated in one named `var` (`announceLocation`, in
`admin_workshop_announce.go`) rather than inlined at each call site, so if
Open Circuit SF ever does run an event outside the Bay Area, promoting it to
a `config.Config` field is a small, local change — not a repo-wide
search-and-replace. Full reasoning is in the `announceLocation` doc comment.

### The timezone decision — ruling: hardcoding is right

Agreed, and the reasoning in `announceLocation`'s doc comment is the reasoning
this project actually runs on. Three things settle it:

1. **It is not a deployment-varying value.** A config knob earns its place when
   two deployments legitimately need different values. Staging and production
   here are the same organization at the same address; `WORKSHOP_TIMEZONE` would
   be set to `America/Los_Angeles` in every environment file that ever exists,
   which makes it a constant with an extra failure mode — a typo'd or unset
   zone would be discovered by a subscriber standing at a door.
2. **The precedent is consistent.** `WEBAUTHN_RP_ID` is configurable and is
   `opencircuitsf.com` everywhere; the CAN-SPAM `physical_address` setting names
   one building. Those are configurable because a *ceremony* and a *legal
   requirement* force them to be, not because the org is multi-venue.
3. **`CLAUDE.md` §5 is explicit** about not sizing the code against requirements
   that do not exist, and `PRD.md` names no second venue.

The escape hatch is real and cheap: one named package-level `var`, referenced at
exactly two sites (`.In(announceLocation)` in `announceWhen`). Promoting it to a
`config.Config` field later is a small local change. If Open Circuit SF ever runs
an event outside Pacific, the right fix is probably a per-workshop `timezone`
column rather than a per-deploy env var anyway — which is another argument
against spending the env var now.

### `time.LoadLocation` failure — no silent UTC fallback (verified by execution)

This was the sharpest question on the issue, because a silent UTC fallback would
reintroduce the exact bug being fixed, invisibly. It does not happen. Probed
directly:

```
LoadLocation("Not/AReal_Zone") -> loc=<nil> err=unknown time zone Not/AReal_Zone
time.Now().In(nil)             -> panics: "time: missing Location in call to Time.In"
mustLoadLocation("Not/AReal_Zone") -> panics: `admin_workshop_announce: load
    location "Not/AReal_Zone": unknown time zone Not/AReal_Zone`
```

Note the trap the implementation avoided: a failed `LoadLocation` returns a
**nil** `*time.Location`, and a nil `*time.Location` *prints* as `"UTC"` and
behaves as UTC in most of `time`'s methods — so the naive `loc, _ :=
time.LoadLocation(...)` really would have degraded to UTC-looking output. It
does not degrade here for two independent reasons: the error is checked and
panics at package init, and even an unchecked nil would panic at `.In(nil)`
rather than render UTC. Confirmed `announceLocation` resolves to
`America/Los_Angeles` in the built package.

One consequence worth stating plainly, since the doc comment understates it:
`announceLocation` is a package-level `var` in `internal/handlers`, so the panic
fires at **program init**, taking down the whole binary — not just the announce
route, as the comment's "every workshop announce would be broken regardless"
implies. On the actual deploy target (systemd on Amazon Linux, system tzdata
present) that cannot happen, so this is not a defect. It is filed as a hardening
follow-up rather than a bounce; see below.

### The `sameUTCDate` → `sameLocalDate` change is correct in both directions

Verified with two reviewer-authored probes (run in the worktree, not committed),
each chosen to fail under exactly one of the two comparison rules:

- **Spans a UTC day boundary, not a Pacific one** — `2026-01-14T22:00Z` to
  `2026-01-15T01:00Z` (Jan 14 2:00 PM → 5:00 PM PST). Renders the short form,
  `"Wednesday, January 14, 2026 at 2:00 PM PST to 5:00 PM PST"`. The old UTC
  comparison would have split one afternoon across two full timestamps.
- **Spans a Pacific day boundary, not a UTC one** — `2026-01-15T07:00Z` to
  `2026-01-15T09:00Z` (Jan 14 11:00 PM → Jan 15 1:00 AM PST). Renders the long
  form, `"Wednesday, January 14, 2026 at 11:00 PM PST to Thursday, January 15,
  2026 at 1:00 AM PST"`. The old UTC comparison would have collapsed a
  midnight-crossing event to a bare `"11:00 PM to 1:00 AM"`.

Both behave as intended. **But no committed test covers either** — see the
coverage gap below.
