## Description

Follow-ups from `#0546`'s review (see its Review notes).

## Root cause

Results rendered only chart series and per-post rows, so channels folded into "Other links" had no exact total; `classifyResultsError` logged every non-sentinel error including `context.Canceled`; the unmatched line interpolated a bare count; `OutreachPanel` fetched results only on load; `OutreachResults.load()` assigned whichever response arrived last.

## Fix

- `OutreachResults.svelte`: a "Totals by channel" table (Channel, Clicks, Reactions) from `channels[]`; unmatched line via `formatClicks`; a load sequence token discards stale responses (and stale errors).
- `OutreachPanel.svelte`: `onChange` refetches results when a post's `prepared` or `status` changed.
- `admin_outreach_results.go`: `context.Canceled` still maps to `unreachable` but is not logged.

## Review notes

Reviewed 2026-10-16 (Opus) against code commit `22c6e34`. Approved.

- **Totals table:** built from `results.channels`, not from `series`, so a channel folded into "Other links" on the chart still gets its own row with its exact `clicks`. The Reactions column reuses `reactionsLabel` from `#0547` and shows a dash when a channel has none. The jsdom test checks a two-row table, "12 clicks" with "3 likes", and "1 click" with no "1 clicks".
- **Cancelled request:** `classifyResultsError` still returns `unreachable` for `context.Canceled` (wrapped too, via `errors.Is`) but skips the log. The new Go test swaps the default slog handler, checks the cancelled case writes nothing, and checks an ordinary error is still logged.
- **formatClicks:** the unmatched line now uses it.
- **Panel refetch:** `onChange` compares the post before and after and calls `loadResults()` when `prepared` or `status` changed. That covers both prepare and mark-posted. The test drives a real Prepare link click and expects a second results call.
- **Race guard:** every `load()` takes a sequence number. A response or error from an older load returns before assigning anything, and `loading = false` sits after the try/catch, so only the current load clears it. An older load cannot clear the flag while a newer one is still running. The jsdom test holds the first request open, switches to workshop 6, then resolves the first request and confirms the title stays on the second workshop.
- **`role="status"`:** the Results status line is still rendered every time, with no conditional.
- Reran `ISSUE=0552 scripts/check.sh go ./internal/handlers/... ./internal/outreach/... ./internal/db/...`: three packages `ok`, no skips, gofmt clean, VERIFICATION PASSED. Reran `scripts/check.sh web`: svelte-check clean, 60 files and 4386 tests passed. All of this rests on jsdom and fakes, not a real browser.

Follow-up recommended (not filed; the orchestrator should decide):
1. `OutreachPanel`'s own `loadResults()` has no sequence guard. Now that `onChange` can start a refetch while `load()`'s refetch is still in flight, an older response for the same workshop could land last and show slightly stale counts. This is low impact because it is the same workshop and the next change refetches again, but the same `loadSeq` pattern would close it.
