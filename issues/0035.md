## Description

Every campaign message carries the RFC 8058 header set with a per-recipient token, plus a `List-Id`.

## Resolution notes

> 🟢 Resolved 2026-08-20 — `mailing.CampaignHeaders` builds the RFC 8058 set
> (`List-Unsubscribe` with both an HTTPS and a `mailto:` URI,
> `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, `List-Id: Open Circuit SF
> <list.opencircuitsf.com>`) per recipient, with an HTTPS URL that matches the
> shape `#0034`'s endpoint actually parses; **two of the seven acceptance
> criteria are deliberately not satisfied here and have been carried into
> `#0043` and `#0045`** — see below.

## Acceptance criteria

- [x] `List-Unsubscribe` header with both an HTTPS URL and a `mailto:` URI, per recipient
- [x] `List-Unsubscribe-Post: List-Unsubscribe=One-Click`
- [x] `List-Id: Open Circuit SF <list.opencircuitsf.com>`
- [x] The HTTPS URL carries the recipient's `manage_token`; the `mailto:` subject is `unsubscribe:<token>`
- [ ] Headers applied to campaign mail only — not to transactional confirmation or auth mail — **half proven, half blocked**: proven that none of the five existing transactional/auth templates carries these headers (see `## Fix`); cannot yet prove the positive half (that an actual campaign send does carry them) because no campaign builder or send worker exists yet — that's #0043/#0045.
- [ ] Footer of every campaign body contains both "Manage your interests" and "Unsubscribe from everything" links — **not this issue's code to write**; no campaign body exists yet (#0043, still open). See `## Fix` for the existing, already-tested mechanism #0043 must reuse.
- [x] Tests assert the headers are present and correctly per-recipient on a multi-recipient send

## Root cause

Not a bug fix — this issue adds a header-construction capability that did
not exist. `internal/mailing.Message` already had a `Headers []Header` field
and `SESMailer.Send` already carried arbitrary headers through to SES
verbatim (both landed defensively during #0027, with a doc comment already
pointing at this issue by number), but nothing in the codebase built the
actual RFC 8058 header values, and nothing called `Message.Headers` for any
real send. The campaign send path this issue's headers are *for* — the
campaign HTML template (#0043) and the send worker (#0045) — are both still
open, Phase 5 work. So this issue is scoped to the seam that exists today:
the pure header-construction function #0045 will call once it's built, with
tests that pin its behavior in isolation from the not-yet-built send loop.

## Fix

Added `internal/mailing/campaign_headers.go`:

- **`CampaignHeaders(baseURL, listDomain, manageToken string) []Header`** —
  the exported, pure function that builds the three-header set. `baseURL` is
  `config.Config.BaseURL` (canonical `https://www.opencircuitsf.com`,
  CLAUDE.md §7 — never a bare apex); `listDomain` is
  `config.Config.EmailListDomain` (`lists.opencircuitsf.com`, already present
  in `internal/config/config.go` but unused anywhere in the codebase before
  this commit — confirmed by `grep -rn EmailListDomain --include='*.go' .`
  turning up only its declaration, its `Load()` assignment, and its
  `config_test.go` assertion). `manageToken` is the recipient's own
  `subscribers.manage_token`, the same value #0034's `POST /api/unsubscribe`
  accepts as `?token=`.
  - `List-Unsubscribe` carries both forms, comma-separated and individually
    angle-bracketed per RFC 8058: `<https://.../api/unsubscribe?token=...>,
    <mailto:unsubscribe@lists.opencircuitsf.com?subject=unsubscribe%3A...>`.
    The HTTPS form points at #0034's `/api/unsubscribe` API endpoint, not the
    SPA's `/unsubscribe` confirmation page the footer's Path-2 links use —
    those are different routes serving different purposes.
  - `List-Unsubscribe-Post` is the fixed literal `List-Unsubscribe=One-Click`.
  - `List-Id` is a fixed constant `campaignListID = "Open Circuit SF
    <list.opencircuitsf.com>"` — **note the singular "list.", not "lists."**.
    PRD §6.5 and this issue's own acceptance criteria give this exact
    singular form, distinct from `EmailListDomain`'s plural
    `lists.opencircuitsf.com` (the real mail-receiving domain #0057 points at
    SES). RFC 2919 `List-Id` values are opaque identifiers, not DNS names
    that have to resolve, so the two are allowed to differ, and
    `TestSESMailer_Send_MultipartWithCustomHeaders`
    (`internal/mailing/ses_mailer_test.go`, written during #0027) already
    hard-coded this exact singular string as its fixture before this issue
    touched anything — so this is matching an existing, deliberate
    convention, not introducing a discrepancy.
  - The mailto `Subject` is percent-encoded with a small `mailtoQueryEscape`
    helper rather than bare `url.QueryEscape`, because `QueryEscape` alone is
    the HTTP/RFC 3986 convention that encodes a space as `+`; RFC 6068's
    mailto query-component syntax requires `%20`. With this project's
    `manage_token` charset (`base64.RawURLEncoding`: `A-Za-z0-9-_`, per
    `internal/subscribers/tokens.go`) the only character that actually gets
    percent-encoded today is the literal `:` in `"unsubscribe:"`
    (`%3A`) — there is no space in play yet — but the helper is correct
    regardless of future token shapes.
- Never points anything at the apex `opencircuitsf.com` MX (CLAUDE.md §9):
  the mailto host is entirely driven by the `listDomain` parameter, with no
  hard-coded apex string anywhere in the function, and
  `TestCampaignHeaders_ListUnsubscribe_CarriesMailtoFormOnListDomain` asserts
  both that the correct subdomain is present and that the apex form is not.

**What #0045 (the send worker) will need to wire, explicitly:** for each
recipient in a campaign's audience, build one `mailing.Message` with
`Headers: mailing.CampaignHeaders(cfg.BaseURL, cfg.EmailListDomain,
recipient.ManageToken)` — using **that recipient's own** `manage_token`, not
a shared value — before calling `SESMailer.Send`. The transport already
carries arbitrary headers through unchanged
(`TestSESMailer_Send_MultipartWithCustomHeaders`), so no further plumbing is
needed there.

**What #0043 (the campaign HTML template) will need to reuse, explicitly:**
the footer criterion ("Manage your interests" / "Unsubscribe from
everything") is not new code this issue could write, because no campaign
body-rendering function exists yet. That footer is already implemented and
already tested — `emailContent.ShowListFooter` in
`internal/mailing/templates.go`, exercised today by
`BuildConfirmationEmail`/`BuildAlreadySubscribedEmail` and proven by
`TestConfirmationAndAlreadySubscribed_CarryFooterLink`
(`internal/mailing/templates_test.go`). `transactional_templates.go`'s
package doc comment already says campaign mail shares this design
constraint. #0043's builder should set `ShowListFooter: true` with
`ManageURL = baseURL + "/preferences?token=" + manageToken` and
`UnsubscribeURL = baseURL + "/unsubscribe?token=" + manageToken` — the same
construction the five existing templates already use — and attach
`CampaignHeaders(...)` to the resulting `Message.Headers`. Note the
unsubscribe URL used in the footer (`/unsubscribe`, the SPA page) is
deliberately different from the one embedded in the `List-Unsubscribe`
header (`/api/unsubscribe`, the RFC 8058 API endpoint) — Path 1 and Path 2
of PRD §6.5 hit different routes on purpose.

**Broadened an existing test to fully cover this issue's own "campaign mail
only" criterion.** `internal/mailing/templates_test.go` already had
`TestConfirmationAndAlreadySubscribed_NoCampaignHeaders`, asserting zero
headers on exactly two of the five transactional templates (confirmation,
already-subscribed). This issue's acceptance criterion says "not to
transactional confirmation **or auth mail**" — auth mail being registration,
recovery, and sessions-revoked, which that test never checked. Renamed it to
`TestNoTransactionalMessageCarriesCampaignHeaders` and widened it to loop
over `allMessages()` (all five), rather than leave three of the five
templates unproven for this specific issue's requirement. No template code
changed; this only strengthens what was asserted about the existing five.

## Gotchas

- **`List-Id`'s domain is singular ("list."), `EmailListDomain`'s is plural
  ("lists.").** This looks like a typo at first glance but is not — it is
  what PRD §6.5, this issue's own acceptance criteria, and a pre-existing SES
  transport test fixture all independently specify. Do not "fix" it to match
  `EmailListDomain` in a future change without first re-reading PRD §6.5.
- **`/api/unsubscribe` (RFC 8058 header target) vs. `/unsubscribe` (footer
  Path-2 target) are deliberately different routes** — the first is #0034's
  no-session/no-CSRF API endpoint that mutates on POST, the second is the
  SPA confirmation page. #0043 needs both, pointed at the right place each.
- **This issue's own acceptance criteria items 5 and 6 cannot be fully
  closed by this commit** — see the two unchecked boxes above — because
  they describe end-to-end behavior of a campaign send that doesn't exist
  in the codebase yet (#0043, #0045, both still open Phase 5 issues). The
  code and tests here are the complete, correct seam for those issues to
  build on; they are not a claim that a campaign email carrying these
  headers has been sent or even can be built yet.

## Review notes (2026-08-20, approved)

**Header set — correct as a set.** Independently checked each of the three
against PRD §6.5 and the endpoint that has to accept them:

- `List-Unsubscribe` carries both URIs, each individually angle-bracketed and
  comma-separated (`<https://…>, <mailto:…>`), built per call from the token
  passed in — nothing in the function is shared across recipients.
- **The HTTPS URL matches what `#0034` accepts.** `CampaignHeaders` emits
  `<baseURL>/api/unsubscribe?token=<token>`;
  `internal/handlers/unsubscribe.go`'s `Post` reads
  `strings.TrimSpace(r.URL.Query().Get("token"))`, and
  `cmd/opencircuit/main.go:624` registers `POST /api/unsubscribe`. The path,
  the method, and the parameter name all line up. Escaping is right too:
  `url.QueryEscape` on the token is a no-op for the `base64.RawURLEncoding`
  charset `manage_token` actually uses, and it neutralises a CR/LF into
  `%0D%0A`, so the header cannot be split by a hostile token value.
- `baseURL` is `config.Config.BaseURL`, which `normalizeBaseURL` has already
  stripped of trailing slashes, so the concatenation cannot produce `//api`.
  The test pins the canonical `https://www.opencircuitsf.com` (CLAUDE.md §7),
  not the bare apex PRD §6.5's illustrative snippet shows.
- `List-Unsubscribe-Post` is the exact literal. `List-Id` is the exact PRD
  string, including the singular `list.` — verified against PRD §6.5 directly,
  not just against the implementer's claim.
- The `mailto:` subject decodes to `unsubscribe:<token>` and the address is on
  `lists.opencircuitsf.com`. The host comes only from the `listDomain`
  parameter; there is no apex literal anywhere in the file (CLAUDE.md §9).

**Mutation-tested, not just read.** Given three vacuous guard tests found
earlier in this session (`#0102`, the `#0103` bounce, the `#0024` gap), the two
