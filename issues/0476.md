> 🟢 Resolved 2026-09-08 — when the advisory lock itself cannot be taken,
> `Lock()` now ends the test binary via `log.Fatalf` before a single test
> runs, so no package can run unserialised believing it holds the lock. The
> connect path deliberately still returns a no-op release; the review
> measured that justification rather than accepting it.

## Description

`internal/testdb.Lock()` (`internal/testdb/testdb.go:36`) has **two fail-open
paths**. If `pgx.Connect` fails, or if `SELECT pg_advisory_lock($1)` fails, it
prints **one line to stderr** and returns a **no-op release function**:

```go
fmt.Fprintf(os.Stderr, "testdb: advisory lock failed: %v\n", err)
_ = conn.Close(ctx)
return func() {}
```

The caller cannot tell the difference. `TestMain` receives a `func()` either
way and proceeds to run the package's tests **without the lock it believes it
holds**.

## Root cause

`Lock()` flattened two failure modes with different consequences into one
branch: print a stderr line, return a no-op release. The connect-failure
path is safe under that treatment (every downstream test tries the same
unreachable database and fails or skips loudly on its own), but the
advisory-lock-failure path is not — the connection is already live at that
point, so every downstream test connects and runs normally, just
unserialized against whatever other package holds the real lock. Nothing
else fails, so the stderr line (invisible under `scripts/check.sh`'s
`tail -40`) was the only signal, and no `TestMain` branched on it.

## Fix

Treated the two paths separately in `internal/testdb/testdb.go`'s `Lock()`,
per criterion 2:

- **Connect failure**: unchanged — still returns a no-op release and logs to
  stderr, with its existing justification preserved verbatim (downstream
  tests fail loudly on the same unreachable database).
- **Advisory-lock failure**: now calls `log.Fatalf` and ends the test binary
  before any test runs, instead of returning a no-op release.

**Decision on criterion 1**: chose "fail the run" over "return a value the
caller can branch on." `Lock()` is called from thirteen `TestMain`s
(`internal/{outbox,workshops,middleware,auth,audit,subscribers,interests,
handlers,mailing,sesnotify}`, `cmd/opencircuit`, plus `internal/db`, whose
`TestMain` doesn't check errors on anything, and `internal/testdb`'s own —
the count originally written here was "fourteen" and the enumeration listed
twelve; the review recounted it and corrected both, see `## Review notes`).
Returning an `(func(), bool)`
or similar would require touching every one of them, and would still let a
`TestMain` that forgot to check the second value silently reproduce this
exact bug in a new place. A process that has already exited cannot be
ignored by any caller, so it is the option "that cannot be ignored" per the
plan. Because the signature of `Lock()` did not change, no `TestMain` needed
editing (criterion 3's "if the signature changes" did not trigger) — only
`Lock()`'s own doc comment and the package doc comment, both of which
previously stated the serialization as unconditional, needed correcting.
Both now say the guarantee holds only when `Lock()` returns normally, and
explain why the two failure paths are treated differently.

Also corrected `internal/outbox/store_test.go`'s `distinctKind` doc comment
(criterion 4): it asserted absolute cross-package serialization as
established fact ("they cannot" run concurrently). Reworded it to say that
guarantee is conditional on `Lock()` succeeding, which this issue shows it
does not always do. Left `distinctKind`'s own scoping logic and its
independent justification (it targets rows the test itself created,
regardless of anything else in the table) untouched, per the issue's
explicit instruction — that safety property never depended on the
absoluteness claim being corrected here.

Did not widen `scripts/check.sh`'s output bound (criterion 6) — the fix
makes the failure fatal and therefore visible on its own, rather than
relying on anyone reading a wider stderr capture.

## The two paths are not equally defensible

The connect path carries a comment justifying itself: *"Surface the problem but
don't block the run: the DB-backed tests will fail loudly on their own
connection attempts."* That reasoning is **sound for that path** — if the
database is unreachable, the tests cannot silently do the wrong thing, because
they cannot do anything.

**It does not transfer to the advisory-lock path, which is the dangerous one.**
There the connection already succeeded, so every DB-backed test connects fine
and runs normally — just unserialised, concurrently with whatever other package
holds the real lock. Nothing fails loudly. There is no second symptom.

## What that exposes

`internal/outbox/main_test.go` **`TRUNCATE`s `outbound_queue` on entry** while
believing it holds the lock. `internal/mailing` and `internal/handlers` enqueue
real rows into that same table from their own DB-backed tests. A `TRUNCATE`
issued without the lock, while another package's binary is mid-test, deletes
rows that test is actively asserting on.

That is a silent cross-package data loss path, and its signature is the one
this project keeps re-learning: **a single stderr line, eaten by `check.sh`'s
`tail -40`**, followed by a failure whose stated cause is somewhere else
entirely. `#0470` cost four passes to exactly that signature.

## Correcting the report this was filed from

`#0470`'s implementer reported that `internal/outbox/store_test.go`'s
`distinctKind` doc comment "explicitly relies on that serialisation being
absolute." **Read in full, it says the opposite**, and the distinction matters
to anyone fixing this:

- The comment **does assert the absoluteness as fact** — "they cannot" run
  concurrently — and cites `Lock()` plus a `pg_locks` measurement from `#0285`'s
  review as its evidence. That assertion is what this issue falsifies: it is
  true only when `Lock()` succeeds, and `Lock()` does not say when it hasn't.
- But `distinctKind`'s **own safety does not rest on it.** The comment states
  plainly that scoping by a distinct kind is "NOT defence against
  internal/mailing or internal/handlers running concurrently," and gives an
  independent reason — each assertion should concern only rows the test itself
  created, "independent of anything else that might be in the table … or any
  other change to the locking or truncation model above."

So `distinctKind` is **already correct under this bug**, by deliberate design.
The exposure is the unconditional `TRUNCATE`, not the scoped assertions. Do not
"fix" `distinctKind`.

## Acceptance criteria

1. **Decide what a failed lock should do**, and say why in the code. The
   candidates are: fail the run (`log.Fatal` from `TestMain`), or return a value
   the caller can branch on so each `TestMain` chooses. A third stderr line is
   not a candidate — that is the current behaviour.
2. Treat the **two paths separately**. The connect path's existing justification
   may well survive; the advisory-lock path's does not, and the fix should not
   flatten them into one branch without saying which reasoning applies.
3. If the signature changes, **update every `TestMain` that calls it** — and
   `Lock()`'s own doc comment, which currently states the serialisation as
   unconditional.
4. **Correct the factual assertion in `internal/outbox/store_test.go`'s
   `distinctKind` doc comment** so it no longer presents absolute serialisation
   as established fact. Leave the function and its scoping alone.
5. **Prove the fail-open exists before fixing it**, and prove the fix closes it.
   A revoked `pg_advisory_lock` privilege, an exhausted connection, or a
   deliberately wrong key are all ways to force the path. **Use your own scratch
   database** (§8b) — this test deliberately breaks the mechanism that stops
   packages colliding, so assume nothing protects the data underneath it.
6. Do **not** widen `check.sh`'s output bound to make the stderr line visible.
   The line being invisible is a symptom; a warning nobody sees is not the fix.

## Review notes

🟢 **Pass.** The decision is right, the reasoning behind it is sound, and the
one claim the fix leaves resting on prose was measured rather than accepted.

**What now happens when the advisory lock cannot be taken.** `Lock()` calls
`log.Fatalf` and the test binary ends before `m.Run()` executes a single
test. No caller receives a release function it could mistake for a real one,
and no package can proceed believing it holds a lock it does not. **The
connect path deliberately still returns a no-op release**, unchanged.

**Caller count re-derived: thirteen, not fourteen.** The argument for
choosing a hard exit over a widened signature rests on every caller being a
`TestMain`, so the review recounted instead of trusting the figure. There
are thirteen `Lock()` call sites, all of them in a `TestMain`; the
enumeration in `## Fix` listed twelve and the prose said fourteen. The
thirteenth is `internal/testdb`'s own, which lives in `lock_diagnosis_test.go`
rather than a `main_test.go` and so is easy to miss when grepping for the
conventional filename. The count was corrected in `## Fix` above. **The
error is cosmetic and does not touch the conclusion**: no caller sits
outside a `TestMain`, and there is no context in the tree where a hard exit
from `Lock()` would be the wrong behaviour. The commit message of `9e6417d`
still says "fourteen"; it was left unamended rather than rewriting a commit
another agent has already built on top of.

**The connect path's justification, measured.** Leaving one path failing
open is only defensible if an unreachable database really does fail loudly
on its own, so that claim was tested rather than accepted. With
`TEST_DATABASE_URL` pointed at a closed port, **all thirteen packages
reported `FAIL` with a nonzero exit** — including `internal/db` and
`cmd/opencircuit`, whose `TestMain` never calls `Connect` and which
therefore had the most room to pass vacuously. A `-v` run showed **zero
`--- SKIP` lines** under the unreachable DSN, confirming the packages are
failing rather than skipping. The unset case is genuinely different, as the
design intends: with the variable unset the same packages report `ok` and
exit 0. The justification holds, and the asymmetry between the two paths is
real rather than assumed.

**Both halves of the fail-open proof reproduced independently.** Run in a
dedicated scratch database, cloned and then dropped, with `EXECUTE ON
FUNCTION pg_advisory_lock(bigint)` revoked from `PUBLIC` in that database
only — `has_function_privilege` returned `f` there while the shared test
database and the template both still returned `t`, confirming the revoke did
not escape its database. Against a throwaway harness that prints a marker
before and after the call, the pre-fix tree printed **both** markers and
reported `PASS` with exit 0, while the fixed tree printed only the first
marker and exited. The before/after comparison used two throwaway git
worktrees pinned to the commit and its parent, so the shared working tree
was never moved.

**The consequence, demonstrated on a real package.** Against the same

That is the silent cross-package data-loss path from `## What that exposes`,
observed directly rather than argued.

**`log.Fatalf` from a library.** Acceptable here. Every caller is a
`TestMain` that has not yet run a test, so nothing has been set up that
needs tearing down, and the deferred functions skipped are ones that would
not have run anyway. The connection is explicitly closed on the line before
the fatal call, so it does not leak. The message names the failing operation
and states the refusal and its reason, which is enough to act on without
reading the source.

**Criterion 4 is confined to the factual assertion.** The `distinctKind` doc
comment no longer presents absolute serialisation as established fact, and

the success case only.
