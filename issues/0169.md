## Description

> ✅ **Resolved 2026-08-22** (`1db7f50`) — verified independently by the
> phase-3 reviewer in a throwaway worktree at `1db7f50`. `Optional[T]` now
> decodes its inner value with a `json.Decoder` carrying
> `DisallowUnknownFields()`, so `internal/handlers`' single decode contract
> holds *through* the wrapper for any `T`, and an unknown inner key surfaces
> as the same `400 {"error":"invalid request body"}` as an unknown top-level
> key. All four acceptance criteria met; see `## Review notes`.

`internal/handlers` has exactly **one** JSON-decoding contract: `decodeJSON` (`auth.go:392`) calls `DisallowUnknownFields()`, and all 20 request-body decodes route through it. `#0137`'s review established this by enumeration — an unknown key is *rejected*, never silently dropped.

Two decodes bypass it. One is fine: `ses_notifications.go:162` parses a third-party SNS envelope, where strictness would be wrong. The other is a latent hole:

**`Optional[T].UnmarshalJSON` (`optional.go:101`) calls `json.Unmarshal` on the inner value, which does not inherit the outer decoder's strictness.** So any struct decoded *through* an `Optional[T]` would accept unknown fields, silently, in a codebase whose stated contract is that it does not.

**Harmless today**: `Optional` is instantiated only as `Optional[int]`, and an int has no fields to be unknown. It becomes a real defect the moment someone writes `Optional[SomeStruct]` — which is exactly what a generic invites.

## Root cause

`Optional[T].UnmarshalJSON` (`optional.go`) decoded its inner value with
plain `json.Unmarshal(data, &o.Value)`. That call has no knowledge of the
outer decoder's configuration — `decodeJSON` (`auth.go:392`) calls
`DisallowUnknownFields()` on its `json.Decoder`, but that setting lives on
the `Decoder` instance, not on the bytes being decoded, so nothing carries
it through to `Optional[T]`'s own, separate `json.Unmarshal` call. Any
struct decoded *through* an `Optional[T]` field would silently accept
unknown keys, breaking `internal/handlers`' stated single-decode-contract
guarantee (`#0137`'s enumeration) the moment a second `Optional[T]`
instantiation used a struct — which `#0146` explicitly anticipated as the
type's second, structurally different use case. Harmless while `Optional`
was instantiated only as `Optional[int]`, since an `int` has no fields to be
unknown.

## Fix

**Decision: enforce.** `UnmarshalJSON` now decodes the inner value with a
`json.Decoder` over `bytes.NewReader(data)` and `DisallowUnknownFields()`,
matching `decodeJSON` exactly, instead of `json.Unmarshal`. Chose enforcement
over documenting-and-pinning because:

- `internal/handlers` has exactly one decode contract by design (`#0137`'s
  review), and `Optional[T]` is itself a request-body field — the contract
  should hold *through* it, not stop at its boundary. Documenting the gap as
  acceptable would have meant carrying a known exception to a rule the
  codebase otherwise enforces uniformly across 20 decode sites.
- `#0146`'s own note frames a second `Optional[T]` instantiation as expected,
  not hypothetical ("the next nullable non-string column would need it").
  Waiting to add strictness only when that instantiation lands would mean
  either remembering to do it then (easy to forget under the pressure of
  landing a new feature) or shipping a struct-typed `Optional[T]` that is
  quietly less strict than every other request-body field it sits beside.

**Cost, measured rather than assumed** (the issue's own instruction, and the
same discipline `#0146` used for the pointer-field pitfall). Wrote a
throwaway `go test -bench` (Apple M4 Pro) comparing plain `json.Unmarshal`
against the `json.Decoder`+`DisallowUnknownFields` shape, for both the
current `Optional[int]` case and a small struct:

```
BenchmarkPlainUnmarshalInt-12       61.08 ns/op     144 B/op   1 allocs/op
BenchmarkStrictDecodeInt-12        305.90 ns/op    2416 B/op   4 allocs/op
BenchmarkPlainUnmarshalStruct-12   248.60 ns/op     216 B/op   4 allocs/op
BenchmarkStrictDecodeStruct-12     342.30 ns/op     960 B/op   7 allocs/op
```

For the scalar case the strict decoder is ~245ns and 3 allocations more
expensive per field — a 5x relative slowdown, but sub-microsecond in
absolute terms. This happens once per `Optional[T]` field per PATCH request,
on a handler that also does a database round trip measured in milliseconds;
CLAUDE.md §5 is explicit that this project has no performance requirement
and no load test. Reasoned that trading the single-decode-contract guarantee
away to save ~250ns was not a good trade, and enforced.

Also updated the "request bodies only" doc comment (`#0155`'s line) to state
the inherited-strictness guarantee explicitly, and to say it covers any `T`
including a future struct — the opposite of narrowing it to "scalar types
only", since scalar-only containment was the alternative *not* taken.

### Ruling on enforce-vs-document: enforce was correct

The issue offered either. Enforcing is the better trade here for a reason
stronger than the one `## Fix` gives:

- The alternative was to carry a **documented exception to a rule this package
  enforces at 20 of 21 decode sites**, where the one genuine exception
  (`ses_notifications.go`'s SNS envelope) is exceptional because the payload is
  *third-party*. `Optional[T]` is not third-party — it is a first-party request
  body field of ours, sitting beside fields that are strict. A documented gap
  there is a rule with a hole in it, and the hole is invisible at the call site
  (`Capacity Optional[int]` looks exactly like every other field).
- The pin-the-behavior alternative has a worse failure mode. A test asserting
  "unknown inner fields are accepted" would have to be *deleted* by whoever
  later adds `Optional[SomeStruct]` — and deleting a test that is in your way
  is an easier, quieter action than adding strictness you were told to remember.
- The cost was measured before deciding, not asserted after. That is the part
  worth keeping.

### The benchmark: shape confirmed, numbers reproduce, conclusion holds

Not taken on report. Reproduced independently in a standalone throwaway module
(same machine, `-benchtime 300000x`, allocation counts are load-independent):

```
BenchmarkPlainUnmarshalInt-12       111.2 ns/op    152 B/op   2 allocs/op
BenchmarkStrictDecodeInt-12         288.1 ns/op   2424 B/op   5 allocs/op
BenchmarkPlainUnmarshalStruct-12    258.8 ns/op    240 B/op   5 allocs/op
BenchmarkStrictDecodeStruct-12      341.8 ns/op    984 B/op   8 allocs/op
```

Same shape as the recorded run (my int rows carry one extra alloc / 8 B, a
harness difference, not a discrepancy in the code under test). **The 16×
allocation growth on the scalar path is exactly what `json.NewDecoder` over a
`bytes.Reader` should cost**: a `json.Decoder` is a large struct that allocates
its own read buffer, so ~2.3 KB and ~3 extra allocations are a **fixed
per-decoder overhead**, not per-byte or per-field work. That is why the ratio
collapses as `T` grows — the struct case is only 1.4× slower, and a larger
struct would narrow it further. A 5× ratio on the smallest possible payload is
the least favorable measurement available, and it is still 245 ns.

**The many-fields case the benchmark does not cover** (arithmetic, not a new
benchmark): the overhead is one decoder per *present* `Optional` field, so it
scales linearly. Ten `Optional` fields all present in one PATCH = ~2.5 µs and
~23 KB of short-lived garbage per request. Against a handler that does a
database round trip measured in **milliseconds**, 2.5 µs is ~0.25% of the
request; 23 KB is less than one HTTP request's own buffers and dies in the
nursery. Still fine at ten fields, and at a hundred (25 µs / 230 KB) it would
still not be the thing to optimize. CLAUDE.md §5 is explicit that this project
has no performance requirement and no load test — sizing this code against
measured cost would be solving the wrong problem. No objection.

### Ruling on the doc line: "request bodies only" was right to keep

The third criterion asked whether `#0155`'s line should narrow to "scalar types
only". It should not, and the implementer's reasoning is sound: narrowing the
comment would have documented the *unfixed* state of the world. `Optional[T]`
is now correct for a struct `T`, so a comment restricting it to scalars would
be wrong in the other direction and would discourage exactly the second
instantiation `#0146` anticipated. The two constraints are independent —
"request bodies only" is about the missing `MarshalJSON` (still true), the new
paragraph is about inherited strictness (now true for any `T`). Both statements
are accurate as written.

### Non-blocking, worth knowing (reported, not filed — §9)

1. **`DisallowUnknownFields` stops at a custom `UnmarshalJSON`, one level
   down.** If a future `T` implements `json.Unmarshaler` itself, the decoder
   hands it the raw bytes and its own inner decoding is not strict — the same
   limitation `decodeJSON` has at the top level, and inherent to
   `encoding/json` rather than to this change. The comment's "an unknown key in
   `T` is rejected" is exact for a plain struct `T` and slightly generous for a
   `T` with hand-rolled unmarshalling. Not worth a code change; noted so the
   next reader of that comment is not surprised.
2. **`Decoder.Decode` ignores trailing data where `json.Unmarshal` rejects
   it.** No behavior change in practice: `data` always arrives as exactly one
   well-formed value from the outer decoder's scanner, and a top-level
   `json.Unmarshal` into an `Optional` still validates the whole input. Flagged
   only because it is the one semantic difference between the two calls.
