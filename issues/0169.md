## Description

`internal/handlers` has exactly **one** JSON-decoding contract: `decodeJSON` (`auth.go:392`) calls `DisallowUnknownFields()`, and all 20 request-body decodes route through it. `#0137`'s review established this by enumeration — an unknown key is *rejected*, never silently dropped.

Two decodes bypass it. One is fine: `ses_notifications.go:162` parses a third-party SNS envelope, where strictness would be wrong. The other is a latent hole:

**`Optional[T].UnmarshalJSON` (`optional.go:101`) calls `json.Unmarshal` on the inner value, which does not inherit the outer decoder's strictness.** So any struct decoded *through* an `Optional[T]` would accept unknown fields, silently, in a codebase whose stated contract is that it does not.

**Harmless today**: `Optional` is instantiated only as `Optional[int]`, and an int has no fields to be unknown. It becomes a real defect the moment someone writes `Optional[SomeStruct]` — which is exactly what a generic invites.

## Root cause

`Optional[T].UnmarshalJSON` (`optional.go`) decoded its inner value with
plain `json.Unmarshal(data, &o.Value)`. That call has no knowledge of the
outer decoder's configuration — `decodeJSON` (`auth.go:392`) calls
`DisallowUnknownFields()` on its `json.Decoder`, but that setting lives on
the `Decoder` instance, not on the bytes being decoded, so nothing carries
it through to `Optional[T]`'s own, separate `json.Unmarshal` call. Any
struct decoded *through* an `Optional[T]` field would silently accept
unknown keys, breaking `internal/handlers`' stated single-decode-contract
guarantee (`#0137`'s enumeration) the moment a second `Optional[T]`
instantiation used a struct — which `#0146` explicitly anticipated as the
type's second, structurally different use case. Harmless while `Optional`
was instantiated only as `Optional[int]`, since an `int` has no fields to be
unknown.

## Fix

**Decision: enforce.** `UnmarshalJSON` now decodes the inner value with a
`json.Decoder` over `bytes.NewReader(data)` and `DisallowUnknownFields()`,
matching `decodeJSON` exactly, instead of `json.Unmarshal`. Chose enforcement
over documenting-and-pinning because:

- `internal/handlers` has exactly one decode contract by design (`#0137`'s
  review), and `Optional[T]` is itself a request-body field — the contract
  should hold *through* it, not stop at its boundary. Documenting the gap as
  acceptable would have meant carrying a known exception to a rule the
  codebase otherwise enforces uniformly across 20 decode sites.
- `#0146`'s own note frames a second `Optional[T]` instantiation as expected,
  not hypothetical ("the next nullable non-string column would need it").
  Waiting to add strictness only when that instantiation lands would mean
  either remembering to do it then (easy to forget under the pressure of
  landing a new feature) or shipping a struct-typed `Optional[T]` that is
  quietly less strict than every other request-body field it sits beside.

**Cost, measured rather than assumed** (the issue's own instruction, and the
same discipline `#0146` used for the pointer-field pitfall). Wrote a
throwaway `go test -bench` (Apple M4 Pro) comparing plain `json.Unmarshal`
against the `json.Decoder`+`DisallowUnknownFields` shape, for both the
current `Optional[int]` case and a small struct:

```
BenchmarkPlainUnmarshalInt-12       61.08 ns/op     144 B/op   1 allocs/op
BenchmarkStrictDecodeInt-12        305.90 ns/op    2416 B/op   4 allocs/op
BenchmarkPlainUnmarshalStruct-12   248.60 ns/op     216 B/op   4 allocs/op
BenchmarkStrictDecodeStruct-12     342.30 ns/op     960 B/op   7 allocs/op
```

For the scalar case the strict decoder is ~245ns and 3 allocations more
expensive per field — a 5x relative slowdown, but sub-microsecond in
absolute terms. This happens once per `Optional[T]` field per PATCH request,
on a handler that also does a database round trip measured in milliseconds;
CLAUDE.md §5 is explicit that this project has no performance requirement
and no load test. Reasoned that trading the single-decode-contract guarantee
away to save ~250ns was not a good trade, and enforced.

Also updated the "request bodies only" doc comment (`#0155`'s line) to state
the inherited-strictness guarantee explicitly, and to say it covers any `T`
including a future struct — the opposite of narrowing it to "scalar types
only", since scalar-only containment was the alternative *not* taken.
