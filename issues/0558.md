## Description

From `#0557`'s review. `mastoMentions` (`internal/outreach/tracker.go`)
saves the newest notification id from the JSON (`items[0].ID`) with
`SetMentionCursor`, unfiltered. A NUL in that id would fail the cursor
write, so every pass would re-read the same page and the Mastodon walk would
stall, which is the failure `#0555` and `#0557` closed for mention rows. Low
risk: our own instance issues numeric ids.

Stripping is the wrong remedy here. A stripped id names a different
notification, so an id containing NUL should be rejected (logged and not
saved), not cleaned.

## Acceptance criteria

- [x] An id containing NUL is never passed to `SetMentionCursor`. The pass logs it and leaves the stored cursor unchanged, and a test proves it.
- [x] The Bluesky mention cursor path is checked for the same gap and fixed the same way if it has it.
- [x] Verified with `ISSUE=0558 scripts/check.sh go ./internal/outreach/... ./internal/db/...`.

## Resolution notes

> Implemented 2026-10-17, awaiting review. A Mastodon notification id containing NUL is rejected (logged, cursor not written, stored cursor unchanged) rather than stripped.

## Fix

New `(*Tracker).cursorSafe(ch, id)` returns false and logs a WARN ("notification id contains NUL, cursor not saved", NUL shown as the four characters `\x00`) when the id contains NUL. `mastoMentions` calls it before both `SetMentionCursor` sites. First-run site: the page's rows are already processed, the write is skipped. Walk site: rows are processed, then the walk returns without writing or advancing, since the id cannot be used as the next `min_id` either. The stored cursor stays as it was.

**Bluesky: no gap.** `blueskyMentions` saves `newest.UTC().Format(time.RFC3339Nano)`, a timestamp formatted locally from parsed `created_at` values, so no remote string reaches `SetMentionCursor`. The only remote cursor there (`pg.Cursor`) is used for pagination requests and is never stored. No change and no test for Bluesky.
