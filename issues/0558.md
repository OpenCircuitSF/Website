## Description

From `#0557`'s review. `mastoMentions` (`internal/outreach/tracker.go`)
saves the newest notification id from the JSON (`items[0].ID`) with
`SetMentionCursor`, unfiltered. A NUL in that id would fail the cursor
write, so every pass would re-read the same page and the Mastodon walk would
stall, which is the failure `#0555` and `#0557` closed for mention rows. Low
risk: our own instance issues numeric ids.

Stripping is the wrong remedy here. A stripped id names a different
notification, so an id containing NUL should be rejected (logged and not
saved), not cleaned.

## Acceptance criteria

- [x] An id containing NUL is never passed to `SetMentionCursor`. The pass logs it and leaves the stored cursor unchanged, and a test proves it.
- [x] The Bluesky mention cursor path is checked for the same gap and fixed the same way if it has it.
- [x] Verified with `ISSUE=0558 scripts/check.sh go ./internal/outreach/... ./internal/db/...`.

## Resolution notes

> Resolved 2026-10-17 after review. A Mastodon notification id containing NUL is rejected (logged, cursor not written, stored cursor unchanged) rather than stripped.

## Fix

New `(*Tracker).cursorSafe(ch, id)` returns false and logs a WARN ("notification id contains NUL, cursor not saved", NUL shown as the four characters `\x00`) when the id contains NUL. `mastoMentions` calls it before both `SetMentionCursor` sites. First-run site: the page's rows are already processed, the write is skipped. Walk site: rows are processed, then the walk returns without writing or advancing, since the id cannot be used as the next `min_id` either. The stored cursor stays as it was.

**Bluesky: no gap.** `blueskyMentions` saves `newest.UTC().Format(time.RFC3339Nano)`, a timestamp formatted locally from parsed `created_at` values, so no remote string reaches `SetMentionCursor`. The only remote cursor there (`pg.Cursor`) is used for pagination requests and is never stored. No change and no test for Bluesky.

## Review notes

Reviewed 2026-10-17 (Opus, phase 3). **Pass.**

- **Both call sites are correct.** First-run path: the page's rows are processed, then the cursor write is skipped, so the next pass takes the first-run path again. That is harmless because `InsertMention` is `ON CONFLICT (remote_id) DO NOTHING`. Walk path: the pass returns without advancing, and the next pass re-reads from the old cursor, which is just as idempotent. A NUL id cannot be the next `min_id` either, so returning is right. Moving to `items[1]` would re-include `items[0]` on the next request, so it would gain nothing.
- **Stall behaviour is acceptable and visible.** If the newest id on a page is permanently bad, every pass re-reads that page and logs a WARN naming the channel and the escaped id. Nothing advances past it. The issue asks for exactly that: reject the id and log it, do not strip it. Our own instance issues numeric ids, so this is a defensive path only.
- **No other caller.** `grep` finds three `SetMentionCursor` calls: the two Mastodon sites, which are now guarded, and Bluesky's. Mention row fields on this path were already stripped by `#0557`.
- **Bluesky claim verified by reading the code.** `blueskyMentions` stores `newest.UTC().Format(time.RFC3339Nano)` from a parsed `IndexedAt`, so the stored value is always formatted locally. `pg.Cursor` is used only as the next request's cursor and is never stored.
- **Mutation:** I copied `tracker.go` aside and made `cursorSafe` return true unconditionally. `TestTracker_MastodonNULCursorIDIsRejected` then fails on its log assertion, which shows the "write cursor" error with SQLSTATE 22021. The cursor assertion still holds under the mutation, because Postgres refuses the NUL write on its own, so the log assertion is the one doing the work. I restored the file, and its sha256 matches the saved copy (`6ef33742…c9af`).
- **Re-run:** load 3.57. `ISSUE=0558 scripts/check.sh go ./internal/outreach/... ./internal/db/... ./internal/handlers/...` reported VERIFICATION PASSED: outreach, db and handlers all `ok`, gofmt clean, no skips.
- Minor, no action needed: the test covers only the walk path. The first-run path has the same one-line guard and no test of its own.
