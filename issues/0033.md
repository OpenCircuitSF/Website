# 0033 — Create the suppressions migration and store

| | |
|---|---|
| **Status** | open |
| **Module** | subscribers |
| **Platform** | All |
| **Phase** | 4 — Unsubscribe and list hygiene |
| **First seen** | 2026-08-18 |

## Description

A global suppression list checked before every send, independent of subscriber status and surviving resubscribe attempts.

## Acceptance criteria

- [ ] `suppressions` table keyed by email, with reason, note, and created_at
- [ ] Reasons constrained to `hard_bounce`, `complaint`, `manual`, `repeated_soft_bounce`
- [ ] Store operations: add (idempotent), check, list, remove (admin only, audited)
- [ ] A suppressed address stays suppressed through a new signup — #0026's flow honors it
- [ ] Hard deletion of a subscriber (#0060) leaves the suppression row in place
- [ ] `go test ./internal/subscribers/...` covers suppression checks against every status

## Notes

PRD §6.2, §6.5. Suppression is deliberately separate from subscriber status: it is keyed by email address, not subscriber id, so it survives deletion and re-signup. That is the property that keeps a complained address from silently returning to the list.

Removing a suppression must be an explicit, audited admin action — never automatic.

## Carried in from `#0025`'s review (2026-08-19)

- [ ] **Give `suppressions.email` the identical normalisation CHECK as
      `subscribers.email`** — `lower(trim(email))`. Without it, a suppression row
      stored with different casing silently fails to match, and a suppression
      that silently fails to match is worse than none: the send proceeds and the
      person who asked to be left alone gets mail.
- [ ] **Do not rely on subscriber status as the sole send gate.**
      `Store.Confirm` currently permits `bounced` → `active`, so hard bounces
      need this suppression table as the backstop rather than status alone. The
      reviewer confirmed nothing in the `#0025` schema assumes status gates
      sending, so a pre-send suppression check drops in cleanly.

## Carried in from `#0026`'s review (2026-08-19)

- [ ] **Keep the suppressed branch's query count equal to its peers.** Today
      `NoSuppressions` returns before issuing any query, which makes `suppressed`
      the fastest branch of all (0.038 ms) and **99.0% separable** from
      `complained` by timing alone. The signal is ~26 µs — around 3,000× smaller
      than the channel `#0026` closed, and it leaks status *among members* rather
      than membership — so it is not worth contorting the design for. But a real
      suppression lookup must not make it worse: give that branch the same number
      of round trips as the others rather than short-circuiting.

## Carried in from `#0032`'s review (2026-08-19)

`#0032` shipped an admin **Suppress** button that currently performs
`Unsubscribe(source=admin)` — there is no suppressions table yet. Its reviewer
approved that on one decisive property: **no code path performs the action
without first telling the admin what it actually is.** The modal's first
paragraph, above the required note field and the submit button, reads:

> Unsubscribes this address (source: admin). This is not yet a real
> suppressions-list entry — #0033 has not landed — so a future resignup by this
> address is not blocked by this action alone.

Four things this issue must close:

- [ ] **Write the real `suppressions` row on suppress, and clear it on
      clear-complaint.** This is the carried-in criterion `#0032` left unchecked.
      Without it an admin action that reads as permanent is not.
- [ ] **Rename or disambiguate the `subscriber.suppressed` audit action.** Rows
      written before this issue mean "admin unsubscribe" and are distinguishable
      from real suppressions only by the presence of a
      `suppressions_table_note` metadata key — never by action name. Decide what
      happens to the historical rows.
- [ ] **Re-word the suppress modal and drop `text-muted`** from the sentence
      that corrects the button label. Today the overclaiming word is a
      `variant="danger"` button and the modal title, while the correction is
      styled as de-emphasised text.
- [ ] **Move the evidence-overwrite warning into the clear-complaint
      confirmation**, and record the discarded values in audit metadata.
      `AdminClearComplaint` overwrites `unsubscribed_at`/`unsubscribe_source`;
      the warning currently appears only in the detail modal and in the response
      *after* the fact, and `ClearComplaint`'s audit row records a generic note
      rather than the previous values — so the provenance is lost outright.
      `Suppress` already records `previous_status`; match it.
