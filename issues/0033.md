## Description

A global suppression list checked before every send, independent of subscriber status and surviving resubscribe attempts.

## Root cause

Not a bug fix — this issue built a subsystem PRD §6.2 specifies but that didn't
exist yet: `#0026`'s subscribe endpoint and `#0032`'s admin suppress/clear-
complaint screen were both built against a `SuppressionChecker` seam
(`handlers.NoSuppressions`) and a documented-but-unimplemented "suppress"
action, respectively, each carrying an explicit note that `#0033` would supply
the real thing.

## Fix

- **`migrations/000012_create_suppressions.{up,down}.sql`** — `suppressions`
  table: `email` (PK, `CHECK (email = lower(trim(email)))` — identical to
  `subscribers_email_normalized`, per `#0025`'s carried-in review finding),
  `reason` (`CHECK` constrained to `hard_bounce | complaint | manual |
  repeated_soft_bounce`), `note`, `created_at`. Deliberately **no foreign key**
  to `subscribers` — that's what lets a suppression survive both a resubscribe
  attempt and a subscriber's hard deletion (`#0060`).
- **`internal/subscribers/suppressions.go`** — new `SuppressionStore` type
  (kept separate from `Store` on purpose — see the file's doc comment) with:
  - `Add`/`AddTx(ctx, querier, …)` — the pool-backed method and its
    transaction-scoped twin, following the exact `querier`/`Write`/`WriteTx`
    idiom `internal/audit` establishes. This is the hard block `#0038`'s
    planning pass flagged: `AddTx` lets a future SES-event-ingestion caller
    write its `email_events` row and its suppression row in one transaction.
    `Add` is idempotent by design — a second `Add` for an already-suppressed
    address returns the **original** row (reason/note/created_at) via an
    `ON CONFLICT (email) DO UPDATE SET email = suppressions.email` no-op
    upsert, rather than erroring or letting a later reason silently replace
    an earlier one's provenance.
  - `IsSuppressed(ctx, email) (bool, error)` — satisfies
    `handlers.SuppressionChecker`'s exact signature, so it drops straight into
    `cmd/opencircuit/main.go`'s existing wiring in place of `NoSuppressions{}`.
    Costs exactly one round trip, matching `FindByEmail`'s own single round
    trip — the carried-in finding from `#0026`'s review (keep the suppressed
    branch's query count equal to its peers, since `#0088` already made every
    branch pay the same fixed synchronous cost).
  - `List(ctx)` and `Remove(ctx, email)` (returns `ErrSuppressionNotFound` if
    nothing matched) — the store-level "list" and "remove" operations the
    acceptance criteria ask for. Enforcing "admin only" and writing the audit
    row are the caller's job, exactly like `AdminClearComplaint`'s convention
    elsewhere in this package.
- **`cmd/opencircuit/main.go`** — constructs `subscribers.NewSuppressionStore(pool)`
  once and wires it into `handlers.NewSubscribeHandler` (replacing
  `handlers.NoSuppressions{}`) and into `handlers.NewAdminSubscribersHandler`.
  This closes the acceptance criterion "a suppressed address stays suppressed
  through a new signup — `#0026`'s flow honors it": the seam already existed
  in `subscribe.go` and needed only a real implementation behind it.
- **`internal/handlers/admin_subscribers.go`** — closes all four carried-in
  findings from `#0032`'s review:
  1. `Suppress` now calls `suppressions.Add` (reason=`manual`, note=the
     admin's required note) alongside `Unsubscribe`; a write failure is a 500
     rather than swallowed, since a silent gap here is exactly what `#0032`'s
     review caught. `ClearComplaint` now calls `suppressions.Remove` (treating
     `ErrSuppressionNotFound` as a non-error — nothing to remove) alongside
     `AdminClearComplaint`.
  2. `ActionSubscriberSuppressed`/`ActionSubscriberComplaintCleared`
     (`internal/audit/actions.go`) are **not** renamed — the decision, recorded
     in their doc comments, is that every such row is still "an admin
     suppressed/cleared this address" regardless of era, so renaming would
     fragment one event type across two action strings for no offsetting
     clarity. Instead the metadata key disambiguates: rows from before this
     issue carry `suppressions_table_note` (no real suppressions row exists);
     rows from after carry `suppression_added`/`suppression_removed`.
  3. `web/src/views/Admin.svelte`'s suppress modal paragraph is reworded to
     state the truth directly (a real, permanent suppression) instead of
     "correcting" an overclaiming button label, and the `text-muted` class is
     dropped — the sentence is no longer a de-emphasized caveat, since nothing
     about the danger-styled button/title is overclaiming any more.
  4. The evidence-overwrite warning moved from the read-only detail modal
     (where it was easy to miss and arrived after the fact) into the
     `confirm()` dialog `handleClearComplaint` shows before the action runs;
     the discarded `unsubscribed_at`/`unsubscribe_source` values are now
     captured (a `GetByID` read before `AdminClearComplaint` overwrites them)
     and recorded in the audit row as `previous_unsubscribed_at`/
     `previous_unsubscribe_source`, matching how `Suppress` already records
     `previous_status`.
- **`web/src/lib/api.ts`** — `suppressSubscriber`'s return type gained
  `suppression_added`; both this and `clearSubscriberComplaint`'s doc
  comments updated to describe the real behavior instead of the pre-`#0033`
  placeholder.
- **`docs/database.md`** / **`CLAUDE.md`** — new table row and the
  `000001`–`000012` range update, required by `internal/db`'s
  `TestDatabaseDocMigrationParity` guard (`#0082`/`#0083`/`#0086`).

`internal/devstore` was left untouched: it has no subscribers-table backing at
all yet (`subscribeH`/`adminSubscribersH` are both `nil` in `STORAGE=json` dev
mode, per `main.go`'s own comments), so there is nothing for suppressions to
extend there consistently with until that gap is closed by a later issue.

## Gotchas

- **`web/dist/index.html` is a committed placeholder, not a real build
  artifact** — `.gitignore` explicitly excludes the rest of `web/dist/` but
  keeps this one file so `go build ./...` embeds *something* from a clean
  checkout. Running `npm run build` (required by CLAUDE.md §5's frontend
  verification) overwrites it with the real build output; that must be
  reverted (`git checkout -- web/dist/index.html`) before committing, or the
  commit silently replaces the placeholder with a real (and, in this repo's
  current state, quite stale-looking-if-diffed) built file. Caught before
  committing here — future subagents running `npm run build` should check
  `git status` for this file specifically.
- **Removing a *manual* suppression has no admin UI path yet.** `Remove` is
  only ever called from `ClearComplaint`, which the frontend only offers on
  `complained` rows (`canClearComplaint`). A subscriber suppressed via the
  `Suppress` button ends up `unsubscribed`, not `complained` — so there is
  currently no way for an admin to reverse a manual suppression through the
  UI (only via direct DB access or a future admin action). The suppress
  modal's wording was written to not overclaim a removal path that doesn't
  exist yet; flagging for the reviewer in case a dedicated "unsuppress"
  action belongs in this issue's scope or a follow-up.
- `subscribers.querier` (the `Exec`/`QueryRow`/`Query` interface `AddTx`
  takes) is unexported and package-scoped, deliberately mirroring
  `internal/audit`'s own unexported `querier` — a future `#0038` caller in a
  different package will pass its own `pgx.Tx` positionally; Go's structural
  typing means it never needs to import this type by name.

- [x] `suppressions` table keyed by email, with reason, note, and created_at
- [x] Reasons constrained to `hard_bounce`, `complaint`, `manual`, `repeated_soft_bounce`
- [x] Store operations: add (idempotent), check, list, remove (admin only, audited)
- [x] A suppressed address stays suppressed through a new signup — #0026's flow honors it
- [x] Hard deletion of a subscriber (#0060) leaves the suppression row in place
- [x] `go test ./internal/subscribers/...` covers suppression checks against every status
- [x] Store exposes a **transaction-scoped** `AddTx(ctx, querier, …)` alongside the
      pool-backed `Add`, following the `querier`/`WriteTx` idiom `internal/audit`
      already establishes

> **Criterion added 2026-08-19, from `#0038`'s planning pass — this is a hard block.**
>
> `#0038` ingests SES bounce and complaint events, and its dedupe short-circuit is
> only sound if the event row and the suppression row are written in **one
> transaction**. Separate writes plus a crash in between leave the retry deduped
> away and the suppression permanently missing — a hard-bounced address that keeps
> receiving mail, with nothing to indicate it.
>
> If `#0033` ships pool-only, that design is impossible and the crash window
> reopens. `#0033` is Phase 4 and lands first, so the requirement has to be here
> rather than discovered later.

## Notes

PRD §6.2, §6.5. Suppression is deliberately separate from subscriber status: it is keyed by email address, not subscriber id, so it survives deletion and re-signup. That is the property that keeps a complained address from silently returning to the list.

Removing a suppression must be an explicit, audited admin action — never automatic.

## Carried in from `#0025`'s review (2026-08-19)

- [x] **Give `suppressions.email` the identical normalisation CHECK as
      `subscribers.email`** — `lower(trim(email))`. Without it, a suppression row
      stored with different casing silently fails to match, and a suppression
      that silently fails to match is worse than none: the send proceeds and the
      person who asked to be left alone gets mail.
- [x] **Do not rely on subscriber status as the sole send gate.**
      `Store.Confirm` currently permits `bounced` → `active`, so hard bounces
      need this suppression table as the backstop rather than status alone. The
      reviewer confirmed nothing in the `#0025` schema assumes status gates
      sending, so a pre-send suppression check drops in cleanly.

## Carried in from `#0026`'s review (2026-08-19)

- [x] **Keep the suppressed branch's query count equal to its peers.** Today
      `NoSuppressions` returns before issuing any query, which makes `suppressed`
      the fastest branch of all (0.038 ms) and **99.0% separable** from
      `complained` by timing alone. The signal is ~26 µs — around 3,000× smaller
      than the channel `#0026` closed, and it leaks status *among members* rather
      than membership — so it is not worth contorting the design for. But a real
      suppression lookup must not make it worse: give that branch the same number
      of round trips as the others rather than short-circuiting.

## Carried in from `#0032`'s review (2026-08-19)

`#0032` shipped an admin **Suppress** button that currently performs
`Unsubscribe(source=admin)` — there is no suppressions table yet. Its reviewer
approved that on one decisive property: **no code path performs the action
without first telling the admin what it actually is.** The modal's first
paragraph, above the required note field and the submit button, reads:

> Unsubscribes this address (source: admin). This is not yet a real
> suppressions-list entry — #0033 has not landed — so a future resignup by this
> address is not blocked by this action alone.

Four things this issue must close:

- [x] **Write the real `suppressions` row on suppress, and clear it on
      clear-complaint.** This is the carried-in criterion `#0032` left unchecked.
      Without it an admin action that reads as permanent is not.
- [x] **Rename or disambiguate the `subscriber.suppressed` audit action.** Rows
      written before this issue mean "admin unsubscribe" and are distinguishable
      from real suppressions only by the presence of a
      `suppressions_table_note` metadata key — never by action name. Decide what
      happens to the historical rows.
- [x] **Re-word the suppress modal and drop `text-muted`** from the sentence
      that corrects the button label. Today the overclaiming word is a
      `variant="danger"` button and the modal title, while the correction is
      styled as de-emphasised text.
- [x] **Move the evidence-overwrite warning into the clear-complaint
      confirmation**, and record the discarded values in audit metadata.
      `AdminClearComplaint` overwrites `unsubscribed_at`/`unsubscribe_source`;
      the warning currently appears only in the detail modal and in the response
      *after* the fact, and `ClearComplaint`'s audit row records a generic note
      rather than the previous values — so the provenance is lost outright.
      `Suppress` already records `previous_status`; match it.
