## Description

`#0433`'s planning pass found that the Go service **cannot write to
`/var/www/media` today, for two independent reasons** — and that fixing either
one alone changes nothing:

1. **Ownership.** The directory is `ec2-user:ec2-user 0755`; the service runs as
   `uid=990(opencircuit)` with no supplementary groups.
2. **`ProtectSystem=strict`** in `opencircuit.service` makes the whole hierarchy
   read-only **regardless of mode**. Correcting the group and mode without
   touching this leaves the write still failing, and the failure would look like
   a permissions bug that had just been fixed.

This issue is that enablement, split out of `#0433` on the planning pass's own
recommendation, so correct code is not stalled behind an approval it does not
need. `#0433`'s server and SPA work is fully provable locally with a temporary
directory.

## What it asks the user for

One question, answerable in one read:

> May we make two changes to production — give `/var/www/media` group ownership
> `opencircuit` with mode `2775` (setgid), and add `ReadWritePaths=/var/www/media`
> to `opencircuit.service`?

**Existing files, their URLs, and the `scp` workflow are unaffected**: the change
is to the directory's group and mode, not to the files' ownership or their `0644`
mode. The setgid bit is what keeps newly written files group-owned by
`opencircuit` so both paths keep working.

### The setgid reasoning — each of the three parts verified

This is the subtle part, and it holds in full.

1. **"The service's own writes already land group `opencircuit`."** Correct —
   its primary group *is* `opencircuit` (gid 990, confirmed above), and Linux
   assigns a new file the creating process's egid absent setgid. So setgid
   changes nothing for the service's own writes, precisely as claimed.

2. **"Setgid's real effect is on the `scp` path."** Correct. `ec2-user`'s
   primary group is `ec2-user`, so without setgid a hand-copied file lands
   group `ec2-user` while service-written files land group `opencircuit` — the
   split the bit removes. The instruction is honest that this is *forward-
   looking* rather than a present requirement, and that neither writer's
   ability to create, rename, or delete inside the directory depends on it.
   That last point is right: after `2775`, owner `ec2-user` has `rwx` and group
   `opencircuit` has `rwx`, and with no sticky bit an unlink is governed by
   directory write permission alone.

3. **"`apache` and `postgres` are neither owners nor group members, so both
   read through `other`, which `2775` leaves unchanged from `755`."** Correct,
   and I checked the membership from **both** directions rather than only the
   one the Work log used:
   - `id apache` → `uid=48(apache) gid=48(apache) groups=48(apache)`;
     `id postgres` → `uid=26(postgres) gid=26(postgres) groups=26(postgres)`.
     Neither carries gid 990.
   - `getent group opencircuit` → `opencircuit:x:990:` — the member list is
     **empty**. Nothing is in that group but the service's own primary gid.
   - `chgrp` changes the group, not the owner, so `ec2-user` remains owner and
     neither daemon matches it.

   Both therefore fall to `other`, and `755` → `2775` leaves `other` at `r-x`
   in both cases. **`apache` keeps read, so the site keeps serving; `postgres`
   keeps read, so `#0434`'s backup keeps working.** Verified end-to-end rather
   than by arithmetic alone: Apache serves both images over HTTPS right now,
   and the bytes it returns hash to the documented values (below). The backup
   claim was checked at its source too — `deploy/systemd/opencircuit-backup.service`
   really does declare `User=postgres`, in this repo's copy and on the box's,
   and its write target `/var/backups/postgres` is untouched by this change.

   The only principal that gains anything is the service itself, via the group
   write bit. That is the intent, and the widening is exactly as narrow as the
   instruction says.
