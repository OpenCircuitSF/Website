## Description

The twelve interest rows are seeded as **DML inside `migrations/000009`** — which
is **inside the frozen range**. `CLAUDE.md` §1's rule is that a migration applied
to production is never edited, and production is at version 22.

So **the file that owns the taxonomy cannot be changed by anyone**: not this
project, not a downstream. ~~Adding, renaming or removing an interest requires a
new migration that mutates rows the frozen one inserted, and nothing in the
repository says so.~~

## Why it is worth fixing rather than documenting

`PRD.md` §6.1 treats the taxonomy as product content — the thing a marketing site
would plausibly revise. Content that lives in an immutable file is content nobody
revises, and the failure is silent: someone edits `000009`, the local database
rebuilds correctly from `migrations/`, and production diverges the moment it is
next migrated from a checkout that never re-runs an applied version.

## Acceptance criteria

1. **Confirm the freeze applies.** Re-derive production's applied version with
   the read-only query in `CLAUDE.md` §1 — do not trust the number recorded
   there, which §1 itself warns goes stale. If `000009` is genuinely below the
   bound, the file is frozen and the fix is a new migration.
2. Decide **where the taxonomy should live** so it can change: a new migration
   that establishes it as ordinary data, a seed path outside `migrations/`, or
   the `settings` table. Record the reasoning; `#0232`'s plan notes `settings`
   already holds `default_from_name` and `physical_address`, which is the
   nearest precedent.
3. **Do not edit `000009`.** §1 records that `migrations/000007` exists because
   ShortLinks broke this rule once, and `#0125` was bounced for following a
   stale criterion that instructed exactly this edit.
4. Whatever lands must be **idempotent against a production database that
   already holds the twelve rows**, and must not renumber or orphan an existing
   interest — subscribers reference them.
5. Say plainly in `docs/` how someone changes the taxonomy afterwards. The
   current absence of that sentence is half the defect.

  **(1) `docs/mailing-list.md` overstates the runtime channel on two points,
  and criterion 5 makes that doc the deliverable.** Replace the whole first
  bullet of "Changing the taxonomy" with, verbatim:

  ```
  - **A live catalog change** — add, rename (the display `name` only),
    redescribe, reorder, deactivate, or hard-delete an interest no subscriber
    has ever selected — is an **admin-console action**, not a migration:
    `POST`/`PATCH`/`DELETE /admin/interests` (`internal/interests`, `#0024`).
    It takes effect immediately, with no deploy and no restart. Two limits are
    load-bearing and are not obvious from the verb list:
    - **`slug` is immutable through this channel.** `interests.Store.Update`
      takes no slug parameter and the PATCH body type has no `slug` field, so
      a PATCH carrying one is rejected with 400 rather than silently ignored
      (`#0023`'s decision: a slug change breaks every already-issued
      preference-center link that references it). To replace a slug, `POST`
      the new interest and deactivate the old one — subscribers do not move
      across, and a downstream re-theming the taxonomy wholesale is doing
      creates-and-deactivates, not renames.
    - **`DELETE` is refused (409) only when a `subscriber_interests` row
      references the interest.** `workshop_interests` and `campaign_interests`
      are `ON DELETE CASCADE` (`migrations/000020_create_workshops.up.sql`,
      `migrations/000017_create_campaigns.up.sql`) and are **not** consulted,
      so deleting an interest that no subscriber has selected but a workshop
      is tagged with, or a campaign targeted, silently drops those rows.
      Prefer `PATCH {"active": false}`: deactivation preserves the row and
      every `subscriber_interests`/`workshop_interests`/`campaign_interests`
      row that references it.
  ```

  The current text says a bare "rename", and pairs "(if unused) hard-delete"
  with a following sentence naming all three referencing tables — which invites
  exactly the wrong inference about what "unused" is measured against. Read
  the store and handler: neither package mentions `workshop_interests` or
  `campaign_interests` anywhere, and `Delete`'s `NOT EXISTS` subquery covers
  `subscriber_interests` only.
