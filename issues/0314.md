## Description

Once `ExpirePendingSweep` nulls a row's `confirm_token`, **that address can never
sign up again**. `sendConfirmation` logs "subscriber has no confirm token", sends
nothing, and returns — so the person submits the form, gets the uniform `202`
that says to check their email, and no email ever arrives. Permanently, with no
self-service recovery.

This is **pre-existing** — it belongs to `#0128`'s pending-subscriber territory
and predates `#0129`. It is filed now because `#0129` makes it materially more
likely: invite mode creates pending rows in bulk that are **expected** to expire,
since an invitation nobody accepts is the normal outcome for some fraction of any
import.

Note the interaction with `#0026`'s uniform `202`, which is a hard restricted-area
rule and must not be weakened: the endpoint deliberately cannot tell the person
anything is wrong. That is correct — it is what stops the endpoint being an
enumeration oracle — but it means the failure is *designed* to be silent, so the
fix has to be on the sending side, not the response side.

## Acceptance criteria

1. A subscriber whose `confirm_token` was nulled by expiry can sign up again and
   receive a confirmation. Decide whether that means minting a fresh token on
   the signup path, or not nulling the token on expiry, and record the reasoning
   in the code.
2. **`#0026`'s uniform `202` must hold byte-identically.** The existing handler
   test asserts this; keep it passing for the right reason, and do not let the
   fix introduce an observable difference between an expired, a fresh, and an
   unknown address.
3. `complained` subscribers still never auto-resubscribe (§9). An expiry-recovery
   path must not become a route around that.
4. Suppressions still bind on the recovered path, every reason.
5. `sendConfirmation`'s silent return is itself worth addressing — it logs and
   moves on where nothing downstream notices. At minimum it should be
   distinguishable in the logs from an ordinary no-op; consider whether it
   warrants the `Warn` treatment `#0254` gave a zero-row `MarkSent`.
6. A DB-backed test drives the whole cycle: sign up, expire, sign up again,
   confirm — and fails against the current code.
7. Check whether the invite path has the same shape and needs the same fix, since
   `#0129`'s pending rows are the ones most likely to expire.
8. `ISSUE=NNNN scripts/check.sh go ./internal/subscribers/... ./internal/handlers/...`
   passes with no skips.

### The shared decision (`#0312` + `#0313` + `#0314`, 2026-08-28)

**Who initiated the send decides which template goes out — not how the row was
created.**

- An **invitation** is a message *we* start, to an address we obtained somewhere
  else. It must carry PRD §6.10.1's provenance sentence, because the recipient
  never asked for it and that sentence is the only thing separating it from spam.
- A **confirmation** is a message we send *in reply* to a request the person made
  themselves. Its provenance is the request. §6.10.1's sentence would read as a
  non-sequitur to someone who just typed their own address into our form.

Applied to the four events these three issues are about:

| Event | Who initiated | What happens |
|---|---|---|
| An invitation fails to send, or is abandoned in the queue | nobody | Row stays `pending`, unaccepted. Recoverable only by the admin action below (`#0312`) |
| An invitation expires unaccepted | nobody | `ExpirePendingSweep` keeps today's behaviour exactly: token nulled, row left `pending`, never re-mailed by the import mechanism |
| An **expired-pending** address submits the public form | **the person** | Mint a fresh token inside the same atomic claim; send the **generic confirmation** (`#0314`) |
| A **pending invited** address submits the public form | **the person** | The row stops being an invitation: `import_id` cleared, consent evidence refreshed, any still-queued invitation cancelled, fresh token if the old one lapsed; send the **generic confirmation** (`#0313`) |
| An admin wants to re-send | **the admin** | A separate action sending `outbox.KindImportInvite` with its provenance intact — at most once per address, ever (`#0312`) |

**States and transitions.** No new `status` value, and no change to the row-state
test the whole codebase already shares — *an unaccepted invitation is
`status='pending' AND import_id IS NOT NULL AND consent_basis IS NULL`*
(`Confirm`, `Unsubscribe`, `AdminResendConfirmation`, `ExpirePendingSweep` all
derive it that way). Two transitions are **added**:

1. **Invitation → self-initiated signup** (`#0313`, public path). Clears
   `import_id`. Leaves `source = 'import'`, `invited_at`, `consent_basis` (still
   NULL) and every `subscriber_events` row untouched.
2. **Invitation → invitation, re-sent once** (`#0312`, admin path). Stamps a new
   write-once `invite_resent_at`. Does **not** re-stamp `invited_at`, does not
   touch `consent_basis`, does not change `status`.

**Transition 1 is a defect fix, not merely a recorded preference.**
`Store.Unsubscribe` reads that same row-state test and treats an unsubscribe from
a pending invited row as an **invitation decline**, which writes a `suppressions`
row ("declined an import invitation before confirming"). So today: an invited
person visits the site, signs up under their own steam, receives the generic
confirmation, changes their mind, clicks that mail's `List-Unsubscribe` — and is
**permanently suppressed** for an ordinary change of mind about a signup they made
themselves, with no self-service recovery. That is precisely the misfire `#0129`'s
blocker 2 closed for `RestartSignup` (invite → revoke → website signup); it is
still wide open on the `pending` branch, which `RestartSignup` never reaches.
Clearing `import_id` at the moment the person takes the signup over closes it at
the same source, by the same reasoning `ImportStore.Revoke`'s own doc comment
already uses: *its consent no longer derives from the import.*

**What transition 1 costs, accepted deliberately.** The person stops counting
toward `subscriber_imports.confirmed_count`, and their acceptance writes
`signup_requested` + `confirmed` rather than `invite_accepted`. That is the honest
number. They also now receive `#0127`'s welcome email, which an accepted
invitation is denied ("the invitation was the introduction") — correct, because
the invitation is no longer their introduction; the form they filled in is.
Provenance is not lost: `source = 'import'`, `invited_at`, and the `imported` /
`invite_sent` `subscriber_events` rows (which carry `import_id`) all survive, and
they are where "why did we ever mail this address" is answered from.

**The one deviation from the PRD, stated plainly.** §6.10.1 says "One invitation
per address, ever. No reminder, no re-invite on a later import." `#0312` requires
a re-send, so this deviates, and the bound is explicit:

- **Automated imports stay capped at one, unconditionally.** `invited_at` still
  governs them and is never re-stamped by anything, so re-uploading the same CSV
  can never re-invite — the property `#0129`'s notes call "the anti-abuse
  property" is untouched.
- **The exception is at most one further invitation, per address, ever**, by an
  explicit, authenticated, audited admin action on that one row, recorded in a
  new write-once `subscribers.invite_resent_at`.

What §6.10.1 exists to prevent survives intact: no bulk re-invite, and no
repeatable reminder loop against an unwilling recipient. Two is a constant, not a
loop. The alternative bound considered and rejected was gating the re-send on the
first invitation's `outbound_queue` status (`abandoned` only): it self-defeats
(`LatestByRecipients` returns the *latest* row of a kind, which after one re-send
is the re-send), it depends on queue retention, and it refuses the bounce case
`#0312` names. The queue state is still *shown* on `#0128`'s screen so the admin
can see whether the first one was abandoned before spending the one re-send.

**Order of implementation: `#0336` → `#0314` → `#0313` → `#0312`.** See each
issue's own `## Plan` for why.

### What this issue implements

**Land second, after `#0336`.** This issue owns the store primitive `#0313`
then extends, so it goes first of the three.

The fix is **mint on the signup path, not "stop nulling on expiry"** — criterion
1's explicit choice. `ExpirePendingSweep` is unchanged: nulling the token is what
makes an expired link dead, and `#0128`'s "the row is left pending rather than
deleted" plus `#0129`'s "never re-mailing" both depend on it. What changes is that
a *self-initiated* signup can always establish a live token, because the person
asking is the thing that authorises a new one.

### Step 1 — `ClaimAndEnqueueConfirmation` establishes a live token (`internal/subscribers/store.go`)

Today the method refuses outright when `sub.ConfirmToken == nil`, and the handler
refuses a second time before calling it. Rewrite it to do the whole thing in one
transaction:

1. `SELECT ` + `subscriberColumns` + ` FROM subscribers WHERE id = $1 FOR UPDATE`
   — the row lock also removes the staleness in today's contract, where the
   token that gets enqueued is whatever the *caller's* `Subscriber` happened to
   hold (read on the request goroutine, possibly minutes earlier under `#0254`'s
   recovery poller).
2. Decide in Go, from the freshly-locked row:
   - `live := sub.ConfirmToken != nil && sub.ConfirmExpiresAt != nil && sub.ConfirmExpiresAt.After(now)`
   - if `!live`, mint `newToken()` and set `confirm_expires_at = now.Add(ttl)`;
     otherwise reuse both.
3. One `UPDATE`, claiming and stamping together, exactly as today:

   ```sql
   UPDATE subscribers
      SET confirm_sent_at    = $2,
          updated_at         = $2,
          confirm_token      = $4,
          confirm_expires_at = $5
    WHERE id = $1
      AND status = $6                                    -- 'pending'
      AND (confirm_sent_at IS NULL OR confirm_sent_at < $3)
   ```
4. `EnqueueTx` the `outbox.KindConfirmation` row with the token this transaction
   just established, then commit. Unchanged in shape — the `#0126` property
   ("a claim can never be stamped for a send that then fails to be queued")
   holds by construction.

Two deliberate additions to the `WHERE` clause and the return contract:

- **`AND status = 'pending'`** closes criterion 3 at the store, not by argument.
  Today, if an SES complaint lands between `dispatchMutation`'s `FindByEmail` and
  this claim, the claim still fires on a `complained` row and mails it. The
  handler's `complained` branch and `RestartSignup`'s `statusLockedFromNonAdmin`
  guard are both upstream of this method; this is the same defence-in-depth
  backstop `RestartSignup` already carries, applied to the one mutator that
  lacked it. It is strictly stronger than `<> 'complained'`: this method is only
  ever legitimately called on a `pending` row.
- A lost claim now has two causes (cooldown active, or the row is no longer
  `pending`). Both mean "this request must not send", which is already the
  documented contract; say so in the doc comment rather than splitting the return.

Where the reuse-vs-mint choice matters: **do not mint unconditionally.** A person
who submits twice inside the TTL and clicks the *older* mail must still land on a
working link. `AdminResendConfirmation` mints unconditionally on purpose (an admin
resend is also a token rotation, `#0128`); this path is not that, and the
difference stays recorded at both sites.

### Step 2 — remove the handler's silent return (`internal/handlers/subscribe.go`)

`sendConfirmation`'s `if sub.ConfirmToken == nil { log.Error(...); return }` is
deleted, along with the store's matching `if sub.ConfirmToken == nil { return
error }` precondition. This is criterion 5's answer, and it is the stronger one:
the log line is not made louder, the condition that produced it is removed. After
step 1 there is no reachable "pending row with no token" state on this path —
establishing a token is now this method's job. The one remaining impossible state
(`newToken()` failing) is already a returned `error`, logged at `Error` by the
caller, which is where a genuine fault belongs. Record that reasoning in the doc
comment so a later reader does not restore the check as apparently-missing
defensiveness.

`h.subs`' interface in `subscribe.go` (line ~213) and every fake implementing it
move with the signature.

### Uniform 202

Nothing about this is visible from outside, and the reason is structural rather
than careful: `Subscribe` writes `writeSubscribeUniform202(w)` *after*
`enqueueMutation` hands the job to the mutate worker, and every branch —
`existingSignup`, `sendConfirmation`, the claim, the enqueue — runs on that worker
in `processMutateJob`, after the response is already written. Both the body and
the response timing are settled before any of this code runs. Add the "expired
pending" case as a branch to `TestSubscribe_UniformResponseAcrossBranches` anyway,
so the property is asserted rather than reasoned about.

### Test strategy — the mutations that must fail

The end-to-end cycle test is the oracle, and its oracle is **whether the link in
the second email actually works**, not a copy of the SQL (CLAUDE.md §8: an oracle
must not be the same bytes as its subject).

- `TestSubscribe_ExpiredPending_SignsUpAgainAndConfirms` (DB-backed,
  `internal/subscribers` or `internal/handlers`): sign up → advance past
  `confirm_expires_at` → `ExpirePendingSweep` → assert `confirm_token IS NULL` →
  sign up again through the real handler → drain the outbox → take the
  `confirm_token` **out of the enqueued payload** → `Confirm` it → assert
  `active`. Criterion 6 requires this to be **red against the current tree**;
  prove that in a throwaway worktree pinned to the parent commit, never with
  `git stash` (§8a).
  - **Mutation M1:** put `confirm_token = confirm_token` back (never mint). Must
    fail — the second signup enqueues nothing and there is no token to confirm.
  - **Mutation M1b:** mint *unconditionally* rather than only when stale. Must
    fail a second test, `TestClaimAndEnqueueConfirmation_ReusesLiveToken`, which
    submits twice inside the TTL and confirms with the **first** message's token.
- `TestClaimAndEnqueueConfirmation_RefusesComplained`: seed `pending`, flip to
  `complained` inside the test, call the method directly, assert `claimed=false`,
  zero `outbound_queue` rows, and `status` still `complained`.
  - **Mutation M2:** drop `AND status = $pending`. Must fail.
- Criterion 4: `TestSubscribe_ExpiredPending_SuppressedStaysSilent`, one subtest
  per `suppressions.reason`, asserting zero enqueues on the recovered path.
  - **Mutation M3:** remove `dispatchMutation`'s `if suppressed { return }`. Must
    fail.
- `TestSubscribe_UniformResponseAcrossBranches` gains the expired-pending branch.
  - **Mutation M4:** have that branch set a response header. Must fail (`#0129`'s
    review already proved this mutation shape works against the existing test).

## Root cause

`ClaimAndEnqueueConfirmation` refused outright when `sub.ConfirmToken` was
nil, and `subscribe.go`'s `sendConfirmation` refused a second time before
even calling it. Once `ExpirePendingSweep` nulled a pending row's token,
that address could never sign up again — the endpoint still answered the
uniform 202, and no email ever arrived, silently and permanently.

## Fix

Landed together with `#0313` in one rewrite of `ClaimAndEnqueueConfirmation`
(`internal/subscribers/store.go`) — see `#0313`'s own `## Fix` for why the
two issues' diffs are not separable and share one code commit. This issue's
half of that rewrite:

- **`ClaimAndEnqueueConfirmation` now locks and re-reads the row**
  (`SELECT … FOR UPDATE`) instead of trusting the caller's possibly-stale
  `Subscriber` — the exact staleness the plan named (`sub` may have been read
  on the request goroutine, or by `#0254`'s recovery poller, minutes
  earlier).
- **A live token is established, not merely checked for.** From the locked
  row: `live := ConfirmToken != nil && ConfirmExpiresAt != nil &&
  ConfirmExpiresAt.After(now)`. If live, the existing token is **reused** — a
  person who submits twice inside the TTL and clicks the OLDER mail must
  still land on a working link, so this method deliberately does **not**
  mint unconditionally (`AdminResendConfirmation` does, on purpose — that
  method's own doc comment explains the difference). If nil or expired, a
  fresh token is minted and `confirm_expires_at` reset to `now + ttl`. The
  refusal — both in the store and in `subscribe.go`'s matching
  `if sub.ConfirmToken == nil { … }` — is deleted outright, per criterion 5's
  "the stronger fix": there is no longer a reachable "pending row with no
  usable token" state on this path for either layer to special-case.
- **`ExpirePendingSweep` is unchanged.** Nulling the token there is still
  what makes an expired link dead (criterion 1's explicit choice, "mint on
  the signup path, not stop nulling on expiry"); what changed is that a
  self-initiated signup can always re-establish a live one.
- **`#0341`'s `AND status = 'pending'` predicate is preserved**, expressed in
  the same `WHERE` clause as before (criterion 3: `complained` still never
  auto-resubscribes — `Confirm`'s own `ErrComplainedLocked` refusal remains
  the actual resubscribe gate independently of this claim).
- **Criterion 4 (suppressions still bind).** Unchanged:
  `dispatchMutation`'s `if suppressed { return }` runs before
  `existingSignup` (and therefore before `sendConfirmation`) regardless of
  which branch would otherwise fire — the same property `#0026` already
  established, now re-asserted specifically against the expired-pending
  state.
- **Criterion 7 (the invite path has the same shape).** Yes, and it is the
  SAME code path as `#0313`'s conversion, not a second one — an invited row
  whose token was swept is recovered by this exact method when the person
  signs up themselves, converting in the same transaction.
