## Description

`#0024` made admin authorization structural: `mountAndServe` registers every entry from a single `adminRoutes()` table inside a loop that applies `requireAdmin`, and the wiring test drives that same function. Adding a route to the table proves its guard automatically.

**But nothing stops a route being registered outside the table.** Demonstrated by `#0024`'s reviewer, adding this beside the loop:

```go
mux.Handle("GET /admin/rogue", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"rogue":true,"guard":"none"}`))
}))
```

`go test ./... -count=1` → all 13 packages `ok`, zero failures. A probe against the live listener confirmed it is world-open:

```
unauthenticated GET /admin/rogue    -> 200
unauthenticated GET /admin/settings -> 403
```

## Why this was not a bounce on `#0024`

Recorded so the severity is not misread later. It is weaker than the gap that *did* bounce `#0024`: that one was defeated by a **routine** edit — adding a verb to a route already in the list — whereas this needs someone to deliberately write a new `mux.Handle` instead of adding a line to the table directly above it, which `main.go`'s own comment already names as the mistake the structure discourages. It is also not a regression and not specific to `#0024`: it is a general property of `mountAndServe` that applies equally to `/api` and `/account`, and no such route exists today — the only `/admin` registrations are the 11 inside `adminRoutes`.

## Notes

`net/http.ServeMux` exposes no way to enumerate registered patterns, which is why a runtime test cannot close this and an AST test can. That is the whole reason this is a separate issue rather than a criterion on `#0024`.

An AST test is unusual enough that it needs a comment explaining why it exists, or someone will delete it as over-engineering. The `/admin/rogue` reproduction belongs in that comment.

## Fix

Added `TestAdminRoutesRegisteredOnlyViaTable` (`cmd/opencircuit/admin_routes_ast_test.go`),
an AST-based test. `net/http.ServeMux` exposes no way to enumerate its
registered patterns at runtime, so no runtime test — however thorough — can
see a pattern that was never handed through a path the test also inspects.
Only reading the source can, hence the AST approach.

The test parses `main.go` and walks every `mux.Handle`/`mux.HandleFunc` call.
The one legitimate `/admin` registration — inside the `adminRoutes` loop —
builds its pattern from `r.method+" "+r.path`, a `*ast.BinaryExpr`, never a
string literal, so it is structurally exempt without the test needing to
know anything about loop scoping. Any OTHER call whose literal pattern's
path begins with `/admin` is, by construction, a route that bypassed the
table. The failure message names the offending file:line, the exact
pattern, and says explicitly to add it to `adminRoutes()` instead.

**`/api` and `/account` decision**: not extended to those prefixes. `/admin`
is the only prefix with a single table a route can be added to *or bypass* —
that specific shape (a table exists, therefore something can dodge it) is
what makes an AST check worth having. `/api` and `/account` have no such
table: every `/api`/`/account` `mux.Handle` call in `mountAndServe` already
carries its own guard (or deliberate, commented absence of one) written
directly at the call site. An AST rule there would have to encode "which
`/api` routes are meant to be public" — a materially different, far less
mechanical property — and public-vs-authenticated is already legible per
call site without one. Recorded in the test's own doc comment too, so the
decision travels with the code.

**Also fixed** `AdminInterestsHandler.Delete` (`internal/handlers/interests.go`):
`GetByID`'s error was checked only for `interests.ErrNotFound`; any other
error (e.g. a transient connection failure) fell through with `current`
zero-valued, and the subsequent `Delete` call could still succeed, writing
an `interest.deleted` audit row with an empty `slug`/`name`. Changed to a
`switch` with a `default: 500` branch, mirroring `Patch`'s existing pattern
exactly.

## Gotchas

- The AST test only flags **string-literal** patterns. This is deliberate,
  not a gap: the one non-literal `mux.Handle` call in the file is the
  `adminRoutes` loop itself (verified by inspection — grepped every
  `mux.Handle`/`mux.HandleFunc` call in `cmd/opencircuit/main.go`, all others
  are literals), so anything reaching `mux.Handle`/`HandleFunc` with a
  non-literal pattern outside that loop would be a new, different pattern
  someone would have to deliberately introduce — worth a fresh look if it
  ever happens, but out of scope here.
- The test parses `main.go` by relative path (`"main.go"`, resolved against
  the package's working directory at test time — standard `go test`
  behavior), not by an absolute/`runtime.Caller`-derived path. This matches
  how Go test binaries always run with cwd set to the package directory, so
  it needs no adjustment, but it does mean the test would silently no-op if
  ever run with a different working directory outside `go test` (e.g. a
  manually invoked test binary from elsewhere) — not a concern under normal
  `go test ./...`.
