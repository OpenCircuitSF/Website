## Description

Admin endpoints to manage workshops and public endpoints to read the published ones.

## Root cause

Not a bug — a build-out. `#0050` shipped the schema (`workshops`,
`workshop_interests`, and the FK from `email_campaigns.workshop_id`) but
deliberately deferred everything runtime: slug generation, the CRUD store,
and both the admin and public HTTP surfaces. None of that existed before this
issue; `internal/workshops` did not exist as a package.

## Fix

Built `internal/workshops` (`store.go`) as the data-access layer over the two
tables, following `internal/interests` and `internal/mailing`'s existing
store conventions (narrow `Store` struct over `*pgxpool.Pool`, typed sentinel
errors, side-loaded `InterestIDs` via a join-table helper mirroring
`CampaignStore.interestIDs`/`interestIDsByCampaign`).

- **Slug generation** (`slugify` + `Create`'s retry loop): lowercases the
  title, collapses non-alphanumeric runs to a single hyphen, trims leading/
  trailing hyphens, falls back to `"workshop"` if that leaves nothing. A
  collision retries with `-2`, `-3`, ... — each attempt is its own
  autocommitted `INSERT ... RETURNING`, so a `unique_violation` on one
  attempt never poisons the connection for the next. Proved with three
  workshops sharing one title (`TestCreate_SlugCollisionGetsDistinctSuffix`).
- **Status transitions live entirely in `PATCH`** (no dedicated
  `/publish`/`/unpublish`/`/cancel` routes — PRD §8's table gives workshops
  none). `Update`'s single `UPDATE` statement uses a `CASE` over the row's
  *own* `status` column (not a value read earlier in Go) to decide
  `published_at`: any→published stamps `now()`; published→draft
  (unpublish) clears it to `NULL`; published→canceled leaves it untouched
  (cancel is not unpublish — a campaign's "this announced workshop" archive
  reference should not lose its original publish timestamp to a cancellation).
  This is a genuine design decision beyond what the acceptance criteria state
  literally; it's documented at length in `store.go`'s package doc comment
  for the reviewer to scrutinize.
- **`Delete` maps SQLSTATE `23503` on `email_campaigns_workshop_id_fkey`
  specifically** (checked via `pgconn.PgError.ConstraintName`, not "any
  `23503` on this table") to `ErrHasCampaigns`, which
  `AdminWorkshopsHandler.Delete` turns into `409`. Proved by seeding a real
  referencing campaign and asserting both the `409` and that the workshop
  row survives (`TestDelete_BlockedByReferencingCampaign`,
  `TestAdminWorkshops_DeleteBlockedByCampaignReturns409`).
- **Public visibility**: `GET /api/workshops` (`ListPublished`) returns only
  `status='published'` rows, using `idx_workshops_published` for both the
  upcoming (`starts_at >= now() OR starts_at IS NULL`, TBD-dated workshops
  sort last) and past (`starts_at < now()`) queries. `GET
  /api/workshops/{slug}` (`GetBySlug`) is deliberately **wider**: it serves
  `published` *and* `canceled` (200, with `status` in the body so `#0054`'s
  frontend can render the cancellation notice), and only `draft` (or a
  missing slug) 404s — matching the Notes' "a canceled workshop stays
  visible... a 404 tells them nothing," which is about the detail page a
  shared link points at, not the index.
- **Cache invalidation**: `AdminWorkshopsHandler` takes a narrow
  `workshopCacheInvalidator` interface (`InvalidateWorkshops()`) rather than
  a concrete `*seo.Site`, and calls it after every successful mutation
  (Create, Patch, Delete — never on a refused Delete). See `## Gotchas` for
  why `cmd/opencircuit/main.go` still passes `nil` for it.
- **Audit actions**: added `workshop.created/updated/published/unpublished/
  canceled/deleted` and `TargetWorkshop` to `internal/audit/actions.go`.
  `Patch` picks the specific action name by comparing old vs. new status
  (published/unpublished/canceled), falling back to the generic `updated`
  for any other field-only change — mirrors
  `AdminInterestsHandler.Patch`'s deactivated/reactivated naming.
- **Wiring**: `cmd/opencircuit/main.go` constructs `workshopsStore`,
  `adminWorkshopsH`, and `publicWorkshopsH` alongside the other admin
  handlers; `adminRoutes()` gained the four `/admin/workshops[/{id}]` rows;
  `mountAndServe` registers `GET /api/workshops` and `GET
  /api/workshops/{slug}` unconditionally-public, matching
  `publicInterestsH`'s pattern. `serveDevMode` (`STORAGE=json`) leaves both
  handlers `nil`, matching every other Phase 5/6 handler's devstore-gap
  convention. Every wiring test that calls `mountAndServe`/`adminRoutes`
  directly (nine call sites across `cmd/opencircuit/*_test.go`) was updated
  for the two new parameters; `admin_wiring_test.go` additionally seeds a
  real throwaway workshop and extends `resolveAdminRoutePath` so the
  existing 401/403/"reaches the real handler" proof now covers
  `/admin/workshops` for free, per that test's own stated design.

## Gotchas

**The cache-invalidation wiring is genuinely incomplete, by design, and the
top-level acceptance criterion is left unchecked because of it — please
scrutinize this.** `AdminWorkshopsHandler` calls `invalidator.InvalidateWorkshops()`
on every successful mutation, and `admin_workshops_test.go` proves the call
happens (and doesn't happen on a refused Delete) with a counting fake. But
`cmd/opencircuit/main.go` passes `nil` for that argument today, so **nothing
is actually invalidated in production yet** — there's nothing calling
`InvalidateWorkshops` on a real `*seo.Site`.

Why: `*seo.Site` is constructed *inside* `mountAndServe` (`seo.NewSite(indexHTML,
cfg.BaseURL, nil)`), from the embedded `index.html` — a value that doesn't
exist yet at the point in `servePostgres`/`serveDevMode` where every other
admin handler (including this one) is built. Threading `Site` back out to
where handlers are constructed, or constructing `AdminWorkshopsHandler`
itself inside `mountAndServe`, is a real (if mechanical) restructuring I
judged out of this issue's scope, especially since **two independent existing
comments already assign exactly that wiring to `#0054`**:
`internal/seo/workshop.go`'s `WorkshopSource` doc comment ("`#0054` is
expected to wire the real implementation in") and `main.go`'s own comment on
the `seo.NewSite` call site ("nil until `#0051`... and `#0054`... land").
`#0054` is the natural point to do both at once — wire the real
`WorkshopSource` adapter *and* thread `*seo.Site` to `AdminWorkshopsHandler`
— since it already has to touch that exact code path. Concretely, today,
this costs nothing: the SEO renderer's `WorkshopSource` is *also* still
`nil`, so there is no live cache for a missed invalidation to leave stale
(the same point `main.go`'s existing comment makes about the `nil` source
being "free" for now).

This is also why the first "Carried in from `#0073`'s review" checkbox (the
`WorkshopSource`-lookup-cost-per-request concern) is marked "not yet
applicable" rather than checked or left silently alone: it only bites once a
real, non-nil `WorkshopSource` is wired in, which hasn't happened yet either.
**The reviewer should treat both of these as the single most important thing
to evaluate in this diff** — either agree the deferral to `#0054` is sound
(the seam is real, tested, and cheap to complete later), or bounce this issue

## Carried in from `#0073`'s review (2026-08-18) — binding

- [ ] *(not yet applicable — see `## Gotchas`)* **Do not leave `internal/seo` doing a `WorkshopSource` lookup on every
      `/workshops/{slug}` request once the source is no longer `nil`.**
      `#0073` moved `Renderer.resolve` ahead of the cache lookup in
      `Renderer.Render`, because the cache key for a workshop-detail path depends
      on whether the slug resolves to a *published* workshop. Measured with a
      counting fake: 100 identical requests to one published slug within the
      60 s TTL produce **100** `WorkshopBySlug` calls (static routes and unknown
      paths still produce zero, so the cost is confined to this one route).
      Today that is free — `cmd/opencircuit/main.go` passes `nil` and
      `workshopMeta` returns immediately — but this issue is what makes it real.

      Workshop detail is the crawler-visited hot path the cache exists to
      protect, and an unfurl storm (one link shared, every social platform
      fetching it at once) is exactly N crawlers hitting one URL simultaneously.
      Satisfy **one** of these before wiring the real source in:

      1. Restore the cache-hit fast path: `handlers.WorkshopDetailSlug` derives
         the slug from the path *syntactically*, with no store access. Key every
         workshop-detail path on `"workshop:" + slug`, look the cache up, and
         call `resolve`/`workshopMeta` only on a miss. Memory stays bounded
         because `maxCacheEntries` caps that keyspace — that is precisely what
         `#0073`'s second, independent bound is for, and it is mutation-proved.
         The only property given up is that an invented slug gets its own entry
         rather than sharing the fallback bucket, which the 512 cap makes safe.
      2. Or make the lookup demonstrably free: hand `internal/seo` an adapter
         backed by an in-memory published-workshop map refreshed on mutation
         (the catalog is tens of rows), rather than a live query. If you take
         this route, say so explicitly and point at the code that holds it.

      Either way, record the choice and add a test that pins it — a counting
      `WorkshopSource` asserting the call count over N repeat requests within the
      TTL is enough, and is what the reviewer used.

- [x] **`Site.InvalidateWorkshops` must be called on every mutation, and the
      call must be tested.** `#0073` repaired `TestSite_InvalidateWorkshopsClearsBothCaches`,
      which previously exercised only the renderer half and stayed green when
      `s.sitemap.Invalidate()` was deleted. The equivalent trap on this issue's
      side is a handler that mutates a workshop without calling
      `InvalidateWorkshops` at all — assert it by mutation (delete the call and
      watch a test fail), not by reading the code. Note option 2 above makes the
      invalidation path load-bearing for correctness, not just freshness.

### Ruling 1 — the `nil` invalidator is safe, the deferral is accepted, and `#0054` now owns it

**The `nil` is safe, and that is proved by execution, not by reading the
guard.** `AdminWorkshopsHandler.invalidate()` is `if h.invalidator != nil {
h.invalidator.InvalidateWorkshops() }`, so the nil is never dereferenced. A
full `Create` + six `PATCH`es + `Delete` cycle driven over HTTP against a
handler constructed with a literal `nil` invalidator completed with no panic;
`admin_wiring_test.go` independently exercises `PATCH`/`DELETE` against a
`nil`-invalidator handler on the production wiring path. Note the seam is a
plain interface method call, so a nil *interface* is the case here, not a nil
concrete pointer — the guard is the only thing standing between production and
a panic, and it is now covered from two directions.

**The deferral is accepted**, for the reason the implementer gives and one it
understates. Verified independently: `cmd/opencircuit/main.go` builds `*seo.Site`
inside `mountAndServe` from the embedded `index.html`, which `servePostgres`
does not have; and `seo.NewSite(indexHTML, cfg.BaseURL, nil)` passes a **nil
`WorkshopSource`**. Read `internal/seo/workshop.go`, `seo.go`, and `sitemap.go`:
with a nil source, `Renderer` falls back to generic default metadata for
`/workshops/{slug}` and `Sitemap` emits no workshop entries at all. So today
neither cache can hold a single workshop-derived byte, and a missed
`InvalidateWorkshops` cannot make anything stale. The cost of deferring is
provably zero right now. `*seo.Site` does have `InvalidateWorkshops()` with a
matching signature, so the seam will connect without change.

### Ruling 2 — `GetBySlug` serving `published` **and** `canceled` is correct; the index must follow, in `#0135`

Confirmed against three sources, not just the implementer's reading.

- This issue's own **Notes**: "A canceled workshop stays visible with a clear
  cancellation notice — people who saw the announcement will come looking, and a
  404 tells them nothing." That is a statement about the **detail page** a shared
  link points at, which is exactly `GET /api/workshops/{slug}`.
- The criterion two lines below it — "Cancel sets status `canceled` and the
  public page shows it as canceled rather than hiding it" — is unsatisfiable if
  the detail route 404s a canceled workshop. Read literally and in isolation,
  the two criteria contradict each other; the wider reading is the only one that
  satisfies both.
- **PRD §7.3** lists `/workshops/{slug}` as a public view and **§5.1** routes it
  publicly; PRD §8's one-line "One published workshop" is a purpose column, not
  a filter specification. `#0054`'s own criterion "Canceled workshops render a
  prominent notice at the top" requires the API to serve them.

Proved by execution, one throwaway workshop per status:

```
GET /api/workshops/…-vis-draft-…      -> 404 {"error":"workshop not found"}
GET /api/workshops/…-vis-published-…  -> 200 {"slug":…,"status":"published",…}
GET /api/workshops/…-vis-canceled-…   -> 200 {"slug":…,"status":"canceled",…}
GET /api/workshops/rev0051-no-such-slug -> 404 {"error":"workshop not found"}
```

Drafts still 404, and the draft 404 body is **byte-identical** to the
unknown-slug 404 body, so probing slugs leaks nothing about unpublished
workshops. `status` is present in the 200 body, which is what `#0054` needs to
render the notice, and the public view carries **no numeric `id`** (verified —
slug is the public identifier, matching `publicInterestView`). `GET
/api/workshops` (the index) stays `published`-only, which is a real gap — see
the amendment immediately below.

#### Amendment — the index and the detail route contradict each other

Raised by the orchestrator from the concurrent `#0053` implementer (committed
at `b5f3b51`) after this issue had been approved, and re-verified here by
execution before ruling. **Tracked in `#0135`; this issue stays approved** — see
the ownership note at the end of this amendment for why.

`PublicWorkshopsHandler.List` calls `ListPublished`, whose two queries both
filter `WHERE status = $1` bound to `StatusPublished`. So a canceled workshop
is served 200 on the detail route and is **absent from the index**. Observed,
with one published and one canceled workshop both dated 72 hours out:

```
GET /api/workshops            -> upcoming=1 past=0
  published slug rev0051b-published-... present on index: true
  canceled  slug rev0051b-canceled-...  present on index: false
GET /api/workshops/rev0051b-canceled-...  -> 200 {"status":"canceled", ...}
```

**This is the exact outcome this issue's own Notes exist to prevent.** "People
who saw the announcement will come looking" describes someone navigating to
`/workshops`, not only someone holding a direct link. As committed, a canceled
workshop silently vanishes from the listing and only a person who kept the deep
link ever learns it was canceled — a strictly worse version of the 404 the
Notes rule out, because the index answers confidently and wrongly.

It also makes a **shipped `#0053` criterion unreachable**. `#0053`'s "Canceled
workshops shown with a clear canceled badge" is a criterion on the `/workshops`
index. Its implementer built `isCanceled`/`workshopBadgeLabel` defensively and
documented in `web/src/lib/workshops.ts` that the branch cannot currently be
reached. That criterion is ticked against code that no API response can
exercise. Correctly, `#0053` did not reach into this issue's code to fix it.

PRD §5.1 and §7.3 are silent on canceled workshops in the index — both describe
`WorkshopsIndex` only as "upcoming + past" — so the PRD neither authorizes nor
forbids either behavior. The two issues' criteria are what decide it, and read
together they are unambiguous: the detail route shows canceled (this issue), and
the index shows canceled with a badge (`#0053`).

**The code that must change is `#0051`'s** —
`internal/workshops/store.go`'s `ListPublished` and
`internal/handlers/public_workshops.go`. `#0053` cannot fix it without editing
this issue's code, and `#0053`'s own criterion is correct as written and needs
no change.

**But this issue is not bounced for it, on the same test used to approve
everything else above: is any `#0051` acceptance criterion unmet?** No. "`GET
/api/workshops` returns published workshops, split into upcoming and past" is
satisfied exactly as written — the index does return published workshops, split
correctly. What is wrong is that *the criterion itself* is narrower than
`#0053`'s, and a criteria gap between two issues is not a failed
implementation. Bouncing here after approving four proved defects on that same
test would be applying two standards to one diff. (This reviewer did initially
bounce, then reversed on noticing the inconsistency; the reversal is recorded
here rather than quietly rewritten.)

`#0135` owns it, and its criteria close the crack explicitly — including
"`#0053`'s currently-unticked canceled-badge criterion is ticked here or there,
not left floating between the two issues", which is the failure mode this
amendment was written to prevent. My recommendation to `#0135`, on the merits:
**include canceled in both partitions**, keyed on `starts_at` exactly as
published rows are. A canceled *upcoming* workshop is the case that matters,
but dropping it the moment its date passes is the same silent vanish one week
later, and a badged canceled session is honest history in the past list.
Three things for whoever takes `#0135`:

- Rename `ListPublished` or rewrite its doc — the name becomes a misnomer that
  will mislead `#0054`/`#0055`.
- `migrations/000020`'s `idx_workshops_published` is partial on `WHERE status =
  'published'` and a widened query can no longer use it. **This is not a
  performance problem** — tens of rows, and `CLAUDE.md` §5 is explicit that this
  project has no performance requirement, so do not size anything against
  measured load. It is a documentation problem: either widen the predicate to
  `status <> 'draft'` (greenfield still permits editing `000020`) or correct the
  `docs/database.md` sentence and the doc comment that call it the public
  listing's hot-path index.
- **Leave the sitemap and SEO path alone.** `internal/seo` is deliberate that
  canceled workshops never appear in a sitemap or a social card; that exclusion
  lives inside `internal/seo` and is unaffected. Do not "make it consistent".

### Ruling 3 — `Update`'s `CASE` verified by execution, all three transitions

Not read from the SQL — driven over HTTP and read back from
`workshops.published_at` in the database at nanosecond precision (the JSON view
renders RFC 3339 to whole seconds, which is too coarse to distinguish a
re-stamp from a preserved value; the database column is not):

```
after create (draft)          = NULL
after draft -> published      = 2026-08-22T17:36:12.120402-07:00   (stamps)
after published -> draft      = NULL                                (clears)
after republish               = 2026-08-22T17:36:12.145369-07:00   (fresh, != first)
after published -> canceled   = 2026-08-22T17:36:12.145369-07:00   (preserved exactly)
after content-only edit       = 2026-08-22T17:36:12.145369-07:00   (untouched)
after canceled -> draft       = 2026-08-22T17:36:12.145369-07:00   (untouched)
```

All three named transitions behave as documented. Two further properties worth
recording: a **republish stamps a fresh timestamp** rather than restoring the
old one, and a **content-only PATCH never touches `published_at`** — both
correct, neither previously pinned by name. The `CASE` reads the row's own
`status` column inside the same `UPDATE`, so the decision is atomic against the
current value rather than a Go-side read, which is the right construction.

One documented consequence to be aware of downstream: `canceled -> draft` leaves
a non-NULL `published_at` on a `draft` row. That matches the package doc's
"every other transition leaves it unchanged" and leaks nothing — `ListPublished`
filters on `status`, and `GetBySlug` 404s drafts — but `#0054`/`#0055` must key
"is this live" off `status`, never off `published_at != NULL`.

**`#0134` item 1 — `workshops.Store.Create` is not atomic** (the only finding
with a runtime effect). Proved by execution: `Create` with an unknown
`interest_id` returns `ErrInterestNotFound` **and leaves the workshop row
behind** — `count(*) = 1` after the failed call — because the slug-retry loop
must `INSERT` outside a transaction and the `workshop_interests` write then runs
in a second transaction. `Update` was tested the same way and **is** atomic
(title, status, and `published_at` all rolled back), so the two disagree, and
the precedent `Create` claims to mirror, `mailing.CampaignStore.Create`, does
the insert and the interests in **one** transaction. Effect: a `POST
/admin/workshops` with a stale interest id returns 400 while silently creating a
ghost draft that burns a slug and gets **no audit row** — reachable from
`#0052`'s admin UI whenever an interest is deleted between page load and submit.
Fix with a savepoint per retry attempt, or by deleting the just-inserted row
when `replaceInterestsTx` fails, and pin it with a test asserting
`count(*) = 0`. Note `#0134`'s second criterion is the right guard: whatever
transaction structure replaces the loop must keep slug collisions working.
