## Description

Two residuals in `scripts/testdb.sh` that `#0332` and `#0333` narrowed but did
not close. Both were found by their batch review and both are verified against
the script as it stands.

### 1. The rebuild path has no live-connection check

`#0333` made `drop template` refuse without `--force`, and `--force` itself
refuse when a connection is live. **`build_template` drops unconditionally**:

	psql_admin -qc "DROP DATABASE IF EXISTS $TEMPLATE;"

No connection check, no refusal. So the asymmetry `#0333` set out to remove is
inverted rather than gone — the explicit destructive path is now guarded, and
the incidental one that destroys the same database is not.

**Something can be lost, and the sentence that stood here was wrong about
that.** It claimed Postgres refuses to drop a database with live connections,
so the only cost was a raw driver error in place of a friendly refusal. The
review pass measured the behaviour directly on this machine's PostgreSQL 16.14
and it does not refuse immediately. `DROP DATABASE` blocks, waiting for the
conflicting backend to go away, and which way it then lands depends entirely on
how long that connection lasts:

| Holder's remaining lifetime | Measured outcome |
|---|---|
| 3s | blocked 3.0s, then **succeeded** — database destroyed |
| 8s | blocked 7.9s, then **succeeded** — database destroyed |
| 20s | blocked 11.5s, then failed: `ERROR: database "..." is being accessed by other users` |

So the pre-fix cost was worse than a bad error message. A connection that ends
inside the wait window leaves the template silently destroyed under whoever was
using it, and that is the ordinary case rather than the exotic one, since a
`create` clone holds the template for well under a second. Only a connection
that outlives the window produces the refusal this paragraph originally
assumed was universal. That makes refusing before the drop the load-bearing
fix rather than a cosmetic improvement, and it is why the rebuild path's own
comment must not repeat the claim corrected here.

### 2. A `_template`-suffixed scratch database is invisible to the listing

`#0332` anchored the exclusion to `datname !~* '_template$'`, which correctly
stopped merely-containing names from being hidden. But **that one clause drives
both of `gc`'s paths** — the sweep and the bare-`gc` refusal listing.

So for a *genuinely* suffixed scratch database, the one shape `#0315` actually
teaches an agent to create, the original complaint still holds exactly:
protected from `gc --all`, which is right, and **absent from the refusal
listing**, so nobody is told it exists to clean up by hand.

`#0332`'s own comment states the standard: such a database was "not even named
in the bare-`gc` refusal listing, so nobody was told it existed to clean up by
hand. A leak, not a loss." Its criterion covered the substring case. The
suffixed case still leaks.

## Root cause

Both residuals share a shape: a single piece of state was reused for two
distinct decisions that happen to coincide most of the time. `gc`'s
`exclude_clause` decides what `--all` will not touch, and the bare-`gc`
branch read that same variable to decide what the caller is even told
exists — so protecting a database from the sweep also, incidentally, hid it
from the listing. `build_template` reused the exact database name
`drop template --force` protects, but never inherited the live-connection
check that guards that other path, so the two commands drifted out of sync
after `#0333` added the check to only one of them.

## Fix

**`build_template`'s live-connection check.** Chose to refuse before
attempting the drop, the same shape `drop template --force` already uses,
rather than letting the drop proceed and translating whatever error comes
back. Measured directly before choosing: this machine's Postgres does not
raise an immediate error when `DROP DATABASE` targets a database with a
live connection — it blocks until the connection ends, then succeeds
silently. So the pre-fix cost was not a raw driver error as the issue
description assumed from reading the code; it was an unexplained hang for
however long the in-progress connection lasted. A translate-the-error
approach would not have fixed that, since there is no error to translate
until the connection already ended on its own. Extracted the check into a
new `refuse_if_connected()` function, shared verbatim by `build_template`
and `drop template --force`'s existing branch, so the same message reports
either path's refusal and the two can no longer drift apart silently.

**The listing/sweep split.** Left `exclude_clause` and the `dbs` variable it
produces untouched — every existing mutation-proof test in Parts 4-6 targets
that exact assignment, and the acceptance criteria require those to stay
green. Added a second query, `all_dbs`, that lists every scratch database
matching the prefix regardless of protection, and changed the bare-`gc`
branch to walk `all_dbs` and annotate each entry with `(protected — ...)`
when it is absent from `dbs`, rather than only ever printing `dbs`. A
database that is genuinely `_template`-suffixed now appears in the listing,
marked protected, instead of being silently absent.

Kept `#0332`'s anchored `!~* '_template$'` exclusion exactly as it was — the
issue's own note that a `LIKE`-based rewrite would need an `ESCAPE` clause
to mean what it looks like it means was reason enough not to touch it, and
nothing in this fix required changing what counts as protected, only what
gets reported.

## Gotchas

The description's assumption that "Postgres itself refuses to drop a
database with live connections" does not hold on this machine's Postgres —
it blocks rather than erroring. This changed the fix's design: a
translate-the-raw-error approach (the acceptance criteria's other offered
option) would not have worked, since there is no error to translate until
the blocking drop eventually completes on its own. Anyone re-verifying this
by hand should expect a `DROP DATABASE` against a connected database to
hang rather than fail fast, and hold the connection only as long as
intended — a background `pg_sleep` left running past the end of a manual
test session will keep a scratch database pinned until it expires.

## Acceptance criteria

1. **Separate the two clauses.** Protection from the sweep and absence from the
   listing are different decisions; one predicate currently makes both. The
   listing should name every scratch database the sweep will not touch, marked
   as protected rather than omitted.
2. **Decide what the rebuild path should do** about live connections — refuse
   like `drop template --force` does, or proceed and let Postgres refuse but
   translate the error. Either is defensible; say which and why. Do not leave a
   raw driver error as the operator-facing outcome.
3. **Guard both in the external harness**, not in-script (`CLAUDE.md` §8), and
   prove each by mutation: reverting the fix must make the guard fail and name
   the problem.
4. **Do not regress `#0332` or `#0333`.** The anchored exclusion must still hide
   nothing from the sweep that belongs to another agent, and `drop template`
   must still refuse without `--force`. Both are pinned by the existing harness;
   it must stay green.
5. Note the `LIKE`-versus-regex trap `#0332` documented: `LIKE`'s `_` is a
   single-character **wildcard**, not a literal underscore, so a `LIKE` form
   needs an `ESCAPE` clause to mean what it appears to mean. The regex
   end-anchor was chosen deliberately to avoid it. Keep that property.
6. Work against a **sandboxed copy** and your own databases (`CLAUDE.md` §8b).
   The shared template is live at migration 28 and other agents' scratch
   databases may exist; a mutation here is a mutation to the mechanism that
   protects them.

## Review notes — 2026-09-09 (phase 3, of `02fa6d6` — bounced)

The two behaviours this issue asked for are present and both are genuinely
proved by mutation — I reverted each fix in a sandboxed copy of the subject and
watched the harness name the regression. `refuse_if_connected()` is shared
verbatim by the two paths as intended, the anchored exclusion is untouched, and
the `--all` sweep is byte-identical to its pre-commit form. Two things still
have to be fixed before this can resolve, and neither is a redesign.

### 1. The rebuild path's new comment repeats the claim this issue was correcting

`build_template`'s added comment in `scripts/testdb.sh` says that nothing was
ever lost this way, that Postgres itself refuses to drop a database with an
open connection, and that the operator merely got a raw driver error instead of
the friendly refusal. That is the premise the implementation pass explicitly
measured and rejected, and the same commit's own message says the opposite. The
header note near the top of the script carries a softer version of it, saying
the old path let a raw driver error stand in for a refusal.

My own measurement is in the corrected Description above: the drop blocks and
then, whenever the holder's connection ends inside the wait window, **succeeds
and destroys the database**. A short-lived connection is the common case, so the
pre-fix path could take the template out from under a live clone with no
diagnostic at all. Leaving a false reassurance in the script is the defect
`#0481` exists to fix one file over, which is what makes this blocking rather
than cosmetic.

**Remedy.** Rewrite both comments to state the measured behaviour: the drop
blocks for a bounded window and then either succeeds — destroying the template,
when the connection ended first — or fails with the "is being accessed by other
users" error when it did not. Drop the "nothing was ever LOST" clause and the
"raw driver error" framing from both places, and say that refusing first is what
prevents the silent destruction rather than what improves the message.

### 2. The listing split regresses the ordinary clean-state invocation

`all_dbs` selects every database matching the prefix, and the shared template
matches it. The template is excluded from the sweepable set, so the new loop
annotates it as protected and invites the reader to drop it by hand. On a
machine in its normal steady state — template present, no scratch databases —
bare `gc` changes behaviour, measured with a prefix-scoped copy of each version:

| Version | Output | Exit |
|---|---|---|
| before `02fa6d6` | `no scratch databases` | 0 |
| after `02fa6d6` | `refusing to sweep — these belong to somebody, possibly another agent:` followed by the shared template marked `(protected — looks like a template; gc --all will not touch it; drop it by hand if you mean to)` | 1 |

Two problems in one. It advises dropping the shared template by hand, which is
the exact act `#0333` made hard on purpose, and which stalls every concurrent
agent until someone rebuilds it. And it turns the clean-state invocation into a
nonzero refusal naming a database that "belongs to somebody" when there is
nothing to clean up and the database belongs to everybody. Nothing in the
harness covers this, because Part 9 always creates an ordinary scratch database
alongside the protected one.

The cause is the same shape this issue's own Root cause section diagnoses, one
level down: `$TEMPLATE` and `$DEFAULT_TEMPLATE` are excluded from the sweep for
a different reason than the anchored pattern's protectees are, and the new
annotation collapses the two reasons into one message.

**Remedy.** Exclude the two template names from `all_dbs` rather than
annotating them, keeping the anchored pattern's protectees as the only thing the
new "(protected — ...)" line describes:

    all_dbs=$(psql_admin -tAc "select datname from pg_database where datname like '${PREFIX}%' and datname <> '$TEMPLATE' and datname <> '$DEFAULT_TEMPLATE' order by 1")

That restores `no scratch databases` and exit 0 for the clean-state case,
because `all_dbs` is then empty exactly when it used to be, and it leaves the
genuinely suffixed scratch database this issue was filed about listed and
marked. Leave `exclude_clause` and `dbs` alone, as this pass correctly did.

Then extend the harness with a part that pins the restored behaviour: with only
the scoped copy's own template present and no other scratch database, bare `gc`
must print `no scratch databases` and exit 0. Prove it by mutation the way the
neighbouring parts do — reverting `all_dbs` to the un-excluded form must make
that new assertion fail and name it.
