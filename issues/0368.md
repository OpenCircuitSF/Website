## Description

`PRD.md` §6.10.1 line 106 reads, unannotated:

> One invitation per address, ever. No reminder, no re-invite on a later import.

The **approved deviation** from that rule is now recorded in four other places
and implemented in code: automated imports stay capped at one, **plus at most
one further invitation ever by an audited admin action**, in a write-once
`subscribers.invite_resent_at`. The user was asked and approved it; commit
`bcf3239` records the decision and the rejected alternative.

`#0312`'s own `## Decision` says the PRD should be updated or annotated. It has
not been.

**The PRD is listed first among this project's authoritative sources for product
scope**, so a contradiction there outranks the four places that record the
truth.

## A trap this issue must handle

**Editing §6.10.1 changes §6.10's and §6's line counts, so `CLAUDE.md` §11's
section-index table must move with it.** `internal/db/prd_section_index_test.go`
runs every row's own `sed` command and fails naming any row that disagrees — so
this will be caught, but only if you update the table in the same pass.

CLAUDE.md §11 records two ways that table has been wrong before: §6.2 drifted
across two commits with neither pass noticing, and §14 was wrong from birth
because a regeneration applied `raw + 1` against the exception it had just
documented. Re-measure; do not adjust by arithmetic.

## Acceptance criteria

1. §6.10.1 states the rule as implemented: one automated invitation per address,
   plus at most one further invitation ever by an audited admin action, in a
   write-once field. **Two is a constant, not a loop** — the annotation must not
   read as licence for a general re-invite.
2. It cites the approval (commit `bcf3239`) and `#0312`, so a later reader can
   see it was a deliberate, approved deviation rather than drift.
3. `CLAUDE.md` §11's table is updated in the same pass, with every affected row
   **re-measured by running its own `sed` command**, not adjusted arithmetically.
4. `internal/db/prd_section_index_test.go` passes, and you state which rows
   changed and their before/after counts.
5. Documentation only — no behaviour change. Prove the Go tree is untouched.
6. Do not "fix" the code to match the old PRD text. The deviation is approved and
   settled; this issue aligns the document to it, not the reverse.

## Verification

**Premise re-checked before editing**, not trusted from the description: PRD.md
line 1281 (not line 106 — the issue's line number was the offset within the
section, not the file) read exactly `- One invitation per address, ever. No
reminder, no re-invite on a later import.`, unannotated. The deviation was
confirmed already recorded in four other places: `issues/0312.md`'s own
`## Decision` section (added by `bcf3239`); `PRD.md` §6.2's own schema comment
on `invite_resent_at` (lines 454-459, already citing `#0312` and describing it
as "the bounded, user-approved deviation"); `migrations/000026_add_subscriber_invite_resent_at.up.sql`;
and `internal/subscribers/{store,pending}.go` plus
`internal/handlers/admin_pending.go`. So §6.10.1's prose was the one place
still stating the old absolute rule — even PRD.md's own §6.2 already
contradicted it.

**Fix.** Rewrote §6.10.1's "One invitation per address, ever" bullet to state
the rule as implemented (one automated invitation per address, no exception, no
automated re-invite) plus a new paragraph naming the approved deviation: an
authenticated, audited admin action may resend that one invitation at most once
more, ever, citing `#0312` and commit `bcf3239`, pointing at the write-once
`invite_resent_at` column and its CHECK constraint, and stating explicitly that
this is one bounded exception for one deliberate admin action, not a general
re-invite, and that no automated path may ever set the column — so the
annotation cannot be read as licence for a loop (criterion 1, 2, 6).

**CLAUDE.md §11 table — every affected row re-measured by running its own `sed`
command** (not adjusted arithmetically), per criterion 3. The guard's own
convention (confirmed by reading `countPRDSection` in
`internal/db/prd_section_index_test.go`) is: a row's stated count is
`sed -n '/START/,/END/p' PRD.md | wc -l` **minus 1** for the terminating
next-heading line the sed range also prints (documented exception: §14, which
has no following heading and is taken raw). Only two rows are affected — the
new text lives inside §6.10.1, which has no row of its own (§11 already notes
"§6.10 includes §6.10.1"), so the change rolls up into §6.10 and its parent §6:

| Row | Sed command run | Before | After |
|---|---|---|---|
| §6 Mailing List | `sed -n '/^## 6\. /,/^## [0-9]/p' PRD.md \| wc -l` → 967, minus 1 | 958 | 966 |
| §6.10 Subscriber import and consent provenance | `sed -n '/^### 6\.10 /,/^#\{2,3\} [0-9]/p' PRD.md \| wc -l` → 129, minus 1 | 120 | 128 |

Every other §11 row's own extraction range is heading-anchored and unaffected
(unchanged headings, unchanged line counts) — re-checked by running
`TestPRDSectionIndexParity`, which recomputes all ~48 rows itself, not just the
two touched here. Also updated the preamble's total-line-count sentence
(`PRD.md is N,NNN lines`), guarded separately by
`TestPRDSectionIndexTotalMatchesFile`: 1,845 → 1,853 (`wc -l PRD.md`).

**Left alone, out of scope:** CLAUDE.md §11's prose line "§6 (the mailing list)
is 933 lines" (just below the table) was already inconsistent with the table's

and not something `prd_section_index_test.go` parses or guards. Not touched
here; flagging it for whoever picks it up next, per this issue's scope being
the table and §6.10.1's text.

**No `.go` file in the diff** (criterion 5): `git status --porcelain` shows
