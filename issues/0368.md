## Description

`PRD.md` §6.10.1 line 106 reads, unannotated:

> One invitation per address, ever. No reminder, no re-invite on a later import.

The **approved deviation** from that rule is now recorded in four other places
and implemented in code: automated imports stay capped at one, **plus at most
one further invitation ever by an audited admin action**, in a write-once
`subscribers.invite_resent_at`. The user was asked and approved it; commit
`bcf3239` records the decision and the rejected alternative.

`#0312`'s own `## Decision` says the PRD should be updated or annotated. It has
not been.

**The PRD is listed first among this project's authoritative sources for product
scope**, so a contradiction there outranks the four places that record the
truth.

## A trap this issue must handle

**Editing §6.10.1 changes §6.10's and §6's line counts, so `CLAUDE.md` §11's
section-index table must move with it.** `internal/db/prd_section_index_test.go`
runs every row's own `sed` command and fails naming any row that disagrees — so
this will be caught, but only if you update the table in the same pass.

CLAUDE.md §11 records two ways that table has been wrong before: §6.2 drifted
across two commits with neither pass noticing, and §14 was wrong from birth
because a regeneration applied `raw + 1` against the exception it had just
documented. Re-measure; do not adjust by arithmetic.

## Acceptance criteria

1. §6.10.1 states the rule as implemented: one automated invitation per address,
   plus at most one further invitation ever by an audited admin action, in a
   write-once field. **Two is a constant, not a loop** — the annotation must not
   read as licence for a general re-invite.
2. It cites the approval (commit `bcf3239`) and `#0312`, so a later reader can
   see it was a deliberate, approved deviation rather than drift.
3. `CLAUDE.md` §11's table is updated in the same pass, with every affected row
   **re-measured by running its own `sed` command**, not adjusted arithmetically.
4. `internal/db/prd_section_index_test.go` passes, and you state which rows
   changed and their before/after counts.
5. Documentation only — no behaviour change. Prove the Go tree is untouched.
6. Do not "fix" the code to match the old PRD text. The deviation is approved and
   settled; this issue aligns the document to it, not the reverse.

### Adversarial read of the bound (criterion 1's second half)

I tried four ways to read the annotation as licence for more than two
invitations, and none of them survive the text:

1. **A general re-invite** — refused twice over: "not a general re-invite", and
   "no automated path may ever set `invite_resent_at`".
2. **A second admin resend** — "at most once more, **ever, per address**" plus
   "write-once". The bound is per address, not per import, per admin, or per
   failure. Structurally enforced by guard 5, which #0312's review and I both
   proved by mutation.
3. **Weakening the automated cap** — the qualifier "from any automated import
   path" narrows the *scope* of the absolute rule, but the following sentence
   ("skipped by every subsequent import, in whatever mode") is unchanged, and
   `invited_at` — the field the import path actually checks — is not mentioned
   as deviating from anything.
4. **A third category of path** (neither automated nor admin) — the total is
   still capped at two by the column having one guarded write site, which the
   sentence asserts and the code enforces.

The annotation claims **exactly** what the code delivers: at most two
invitations per address, the second only by an authenticated audited admin
action. It does not claim more.
