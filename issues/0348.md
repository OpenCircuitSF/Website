## Description

`internal/mailing/outbox_worker_test.go:774-784` — the checkpoint comment
inside `TestOutboxWorker_Stop_LeavesUnclaimedRowsQueued` — says which row gets
claimed first is not guaranteed.

That was true under `ClaimDue`, whose `UPDATE … RETURNING` gave no ordering
guarantee. It is false under `SelectDue`, which `#0297` substituted: a plain
`SELECT … FOR UPDATE SKIP LOCKED` with `ORDER BY next_attempt_at, id`, whose
result the caller then iterates **in order**. Claim order is now deterministic.

The result is two comments twelve lines apart in the same test giving opposite
answers to the same question — the neighbouring text, corrected by `#0342`'s
third pass, states that `id2` is deterministically never claimed.

**Only the reasoning is stale.** The test's pair-based assertion is still the
right assertion and must stay: asserting a specific row by name would pin
behaviour the test does not exist to pin, and a later legitimate ordering
change should not have to rewrite it.

Out of scope for `#0342`: `ClaimRow` is not in that issue's criterion 3 keyword
list, and rewriting this reasoning is judgement rather than the transcription
its remaining pass was scoped to.

## Review notes

**Verdict: approved.** The comment's behavioural claim was re-derived from
the live source rather than accepted from the issue or the implementer.

**Criterion 1 — is the new claim TRUE?** Checked each conjunct against the
code, because this whole issue family exists about comments that are
confidently wrong about behaviour.

- `internal/outbox/store.go:430-437` — `SelectDue` is
  `SELECT id FROM outbound_queue WHERE … ORDER BY next_attempt_at, id LIMIT $1
  FOR UPDATE SKIP LOCKED`. It is a plain `SELECT`, so its **output order is
  guaranteed** by the `ORDER BY`, and `(next_attempt_at, id)` is a *total*
  order because `id` breaks every tie. ✔
- `internal/mailing/outbox_worker.go:528` — `pass` calls `SelectDue` **once**
  per pass, and line 541 is `for _, id := range ids`: a plain in-order range
  over the returned slice. No sort, no shuffle, no map iteration, no
  goroutine. ✔
- The `stopCh` check sits at **lines 542-549, at the top of the loop body**,
  ahead of both `limiter.Wait` and `ClaimRow` (line 566). So on stop the
  current id is never claimed — which is what makes the neighbouring "id2 is
  never claimed at all" true. ✔
- `ClaimRow` is per-row, immediately before that row's own `sendOne`. So
  claim order == iteration order == `SelectDue` order. ✔
- "id1, sorted first" is right: `Enqueue` inserts
  `next_attempt_at = now() + 0`, so id1 (enqueued first, separate statement)
  has `next_attempt_at` earlier than or equal to id2's, and on a tie `id`
  puts id1 first either way. ✔

**The contrast clause was the part most likely to be wrong, and it is
right.** `ClaimDue` (`store.go:356-366`) *does* contain
`ORDER BY next_attempt_at, id` — but **inside the `WHERE id IN (SELECT …)`
subquery**. That orders *which* rows are selected, not the order the outer
`UPDATE … RETURNING` emits them. `RETURNING` output order is unspecified in
PostgreSQL and follows the update's physical processing order. The comment
says precisely *"whose `UPDATE … RETURNING` gave no ordering guarantee at
all"* — attributing the non-determinism to the `RETURNING` clause, which is
correct. Had it instead said "`ClaimDue` had no `ORDER BY`", that would have
been false. It does not. This also makes the retained `#0264` sentence
coherent: physical layout flipping the observed row is exactly the mechanism
`RETURNING` ordering is subject to, and the added tail *"back when claim
order genuinely was not guaranteed"* correctly time-scopes it to the
pre-`#0297` regime.

**Is "deterministic" unconditionally true? No — and the comment does not say
it is.** Two mechanisms defeat it under real concurrency:

1. `FOR UPDATE SKIP LOCKED` — a candidate row locked by a concurrent
   transaction is **omitted from the result set**. This changes *membership*;
   the relative order of whatever *is* returned stays sorted.
2. `ClaimRow` returning `!claimed` → `continue` (`outbox_worker.go:571-580`).
   A row lost to a concurrent poller or an orphan sweep is skipped, so the
   first *successfully claimed* row need not be the first id.

Neither can fire in this test: one worker goroutine, one pass, the test's own
two freshly-enqueued rows with unique recipients, and **no `t.Parallel()`
anywhere in `internal/mailing`** (verified by grep — the package's tests run
sequentially). The sentence's subject is explicitly "which of the two rows is
the one blocked in `sendOne`", i.e. scoped to this test, so it is accurate
within its scope. The one phrase a future reader could over-generalise is
"not a race"; the immediately following sentence defuses it by calling the
order "the loop's **current** iteration order" and anticipating "a later
legitimate change to claim order", which frames it as contingent rather than
as a durable global invariant. Recorded here rather than bounced — criterion
1 asked for exactly this statement and the mechanism it names is the true
one.
