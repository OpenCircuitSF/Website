## Description

`claimCommentGuardDirectionalCalibrationCases` in
`internal/outbox/claim_comment_referent_guard_test.go` asserts a **count**. A
row with `wantClaimDueFindings: 0` therefore cannot distinguish between:

- no direction-word match at all (the axis was never entered),
- marker-exempt (the historical regex fired),
- window excludes the identifier (the clamp or the 90-char cap).

All three look identical to a reader **and to `go test`**.

**This is not hypothetical — it has already caused two failures.** `#0358`'s
first pass shipped a row whose fixture read `// Below, ClaimDue …`: capitalised,
so `claimCommentGuardDirWordRe` never matched and the axis was never entered.
The row's comment credited the backwards-only window, which it did not test, and
the whole table stayed **green** under the exact mutation that row claimed to
guard. Separately, `#0347`'s third review probed that same fixture believing it
measured the window limit — and measured nothing.

Both times the defect was found only by **hand-instrumenting** the axis
(printing the sentence, the marker match, the computed `lo`, which clamp
produced it, and the window). Two review passes caught it that way; nothing in
the tree does.

## Acceptance criteria

1. Each zero-expectation row states **why** it is silent — a `wantSilentBecause`
   discriminant covering at least: no direction-word match; marker-exempt;
   window excludes.
2. **The discriminant is re-derived from the axis's own primitives, not stored
   as a copy of the answer.** §8 is explicit that a copy of the answer stored
   next to the question is not a check — the row must not simply carry a label
   that a future edit can leave stale while the count still passes. That is the
   whole failure mode being fixed.
3. Prove it discriminates: for each reason, mutate the axis so a row becomes
   silent for a *different* reason than its declared one, and confirm the test
   fails naming that row. A row that cannot fail pins nothing (`#0354`).
4. Re-run `#0358`'s five mutations and confirm each still moves its disjoint
   named row set: broad marker set → the three `never`/`cannot` rows;
   nearest-only → the every-identifier row; no paren clamp → the paren row plus
   the `store.go` test plus the whole-tree
   `TestNoCommentClaimsClaimMachineryCallFileCodeLacks`; forward window → the
   backwards-window row; `(?i)` → the capitalisation row.
5. **Do not change the window logic.** The axis is frozen; `#0363` owns the
   case-sensitivity fix. If this work seems to require an axis change, stop and
   report.
6. No `.ClaimDue(` / `.OrphanSweep(` / `.SelectDue(` call-syntax literal enters
   any Go comment, and the floor harness stays **42 total / 12 non-exempt**
   (`#0323`). Re-run `scripts/go_file_visit_floor_guard_test.sh` and record it.
7. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout (§8).

## Added by `#0363`'s review, 2026-09-01 — the discriminant must cover NON-ZERO rows too

Criterion 1 above is scoped to `wantClaimDueFindings: 0` rows and their three
silent reasons. **`#0363`'s review found the mirror image on a `1` row**, and no
zero-row discriminant would have caught it.

`#0363` added `(?i)` to `claimCommentGuardDirWordRe` without lowercasing the
resolution comparison it feeds:

```go
dir := flat[dm[2]:dm[3]]          // now (?i), so this can be "Below"/"Above"
    if dir == "below" && o > endOff { ok = true }
    if dir == "above" && o < startOff { ok = true }
```

With `dir == "Below"` neither comparison can ever be true, so the axis emits a
finding for **every** target identifier in the window regardless of the file's
code — a false positive on **correct** comments. Its new regression pin still
reported `1` and passed, because its fixture contains **no code at all**: with
`identOffsets` empty, `ok` is false on *either* path. The row proved axis
**entry** only.

So the two failures are the same defect with opposite signs, and **both are
invisible to a table that compares only counts**:

| Issue | Row expected | Got its number because | Named reason |
|---|---|---|---|
| `#0358` | 0 | the axis never ran | "window excludes" |
| `#0363` | 1 | the axis always fires | "entered and failed to resolve" |

### Revised criterion 1

The discriminant is **"each row states why it gets the count it gets"**, not
only why a zero row is silent. For a non-zero row that means naming **which
identifier**, **which direction word**, and **which resolution outcome**
produced the finding.

Without that, `#0364` lands and this class recurs on the next non-zero row
anyone adds.

### Why this is not the fifth in-file check §8 warns about

`#0363`'s reviewer addressed that directly, and it is worth preserving: §8's
warning is about mechanisms **defending the file they live in** against edits to
that file. `#0364` strengthens the **oracle** — does each fixture discriminate?
— rather than adding another tamper layer. It recommended explicitly **against**
closing this issue unimplemented.

## A caution from the issue that filed this

`#0358`'s reviewer noted that adding this **now** would have been the in-file
guard-stacking pattern §8 warns against, which is why it is a separate issue
rather than a third round there. Land it as its own considered change, and if
the discriminant turns out to need more machinery than the defect costs, **say
so and stop** — recording the limit is a legitimate outcome, and three separate
guard families reached exactly that conclusion (`#0330`, `#0347`, `#0356`).

## The general lesson, from `#0363`'s second review

Recorded here rather than as its own issue, on that review's recommendation.

`#0363`'s `## Description` called its one-flag fix **"measured free"** on the
strength of a **green tree**. The green tree was the wrong oracle: **no input in
the corpus reached the newly-enabled code path**, so the suite could not have
detected the false-positive bug that flag shipped.

> **A change that opens a code path no existing input exercises cannot be
> validated by running the suite.** It needs a fixture built specifically to
> reach the new path.

That is this issue's discriminant question one level up — a row, or a whole
suite, reporting the expected result for a reason other than the one being
claimed. The first pass's no-code fixture could not reach the path either, which
is exactly why it passed while the bug was live.

Worth carrying into this issue's own design: a discriminant that says *why* a
row got its number is the per-row form of the same requirement.

## Fix

`internal/outbox/claim_comment_referent_guard_test.go`:

- **Extraction, not a change (#0364, prerequisite for criterion 2).** Pulled
  the directional axis's window-left-edge computation (90-char cap, boundary
  clamp, paren clamp — all three, byte-identical) out of
  `findClaimCommentGuardFindings`'s inline code into a new named function,
  `claimCommentGuardDirectionalWindowLo(flat string, dmStart int) int`, and
  changed the axis's own call site to call it. Verified behaviour-preserving
  before writing the discriminant: all 23 pre-existing calibration rows,
  `TestClaimCommentGuardDirectionalAxisFlagsKnownStaleSitesFromDb9bff7`, and
  `TestClaimCommentGuardDirectionalAxisIsCleanOnStoreGoParenScoping` pass
  identically before and after the extraction, with no other line changed.
  This is what lets the new discriminant, below, share the SAME clamp
  arithmetic the real axis uses rather than holding an independently
  -drifting copy of it (criterion 2) — a mutation to the 90-char cap, the
  boundary set, or the paren clamp changes both consumers identically because
  they call the same function.

- **`claimCommentGuardDirectionalReason` — the discriminant (criteria 1, 2,
  the amendment).** A 5-field struct
  (`dirWordMatched`, `dirWord`, `markerExempt`, `identInWindow`, `resolved`)
  with five named constructors covering the mechanism buckets: no
  direction-word match at all; marker-exempt; window-excludes; window
  -includes-and-resolved (silent); window-includes-and-unresolved (flagged).
  `dirWordMatched`/`dirWord`/`markerExempt`/`identInWindow` are computed by
  `claimCommentGuardDiagnoseDirectional` calling the SAME shared regex vars
  and functions the axis itself calls (`claimCommentGuardDirWordRe`,
  `claimCommentGuardDirHistoricalRe`, `claimCommentGuardSentence`,
  `claimCommentGuardDirectionalWindowLo`, `claimCommentGuardIdentRe`) — not a
  duplicate implementation of the decision. `resolved` is deliberately NOT a
  third rewrite of the `dirLower == "below"`/`"above"` comparison (that exact
  comparison's case-sensitivity trap is `#0363`'s whole subject, and a
  hand-written duplicate would inherit the identical drift risk); instead it
  asks `findClaimCommentGuardFindings` itself — the REAL computation — whether
  a directional `ClaimDue` finding actually resulted, so a mutation to the
  real comparison is observed through its real output rather than missed by a
  stale copy.

- **`wantReason` added to `claimCommentGuardDirectionalCalibrationCase`**, and
  every one of the 23 pre-existing rows given the reason that matches its own
  comment's stated cause (the two resolution-pin rows, the paren-scoping row,
  the three clause-boundary rows, the >90-char row, and the
  identifier-after-direction-word row all get `WindowExcludes`; the four
  marker-exemption rows and the `since #` rescue row get `MarkerExempt`; the
  three resolution rows and the two entry-pin rows get `Resolved`/`Unresolved`
  respectively; the marker-exemption control, the two non-positional
  false-positive rows, the three `never`/`cannot` rows, and the
  every-distinct-identifier row get `Unresolved`).

- **One new row (24th), `no-direction-word-match`** (criterion 1's third
  bucket needs a real, reachable exemplar under normal conditions, not only
  under a mutation): a fixture mentioning `ClaimDue` with neither positional
  word anywhere in the sentence, so `claimCommentGuardDirWordRe` returns zero
  matches and the axis's per-match loop body never executes. This is data
  only — no axis logic changed to add it (criterion 5). Its own doc comment
  went through one self-inflicted-regression fix during this pass (see
  below).

- **`TestClaimCommentGuardDirectionalAxisCalibrationTable` extended** to also
  call `claimCommentGuardDiagnoseDirectional` per row and fail, naming the
  row, if the computed reason disagrees with `c.wantReason` — even when the
  count assertion above it already passed.

**Self-inflicted regression, found and fixed mid-pass** (matching
`#0358`'s/`#0347`'s own precedent — this guard scans its own file): the new
row's first-draft doc comment described the fixture as mentioning `ClaimDue`
"with neither below nor above", and that description sentence was itself
flagged by the directional axis running against this very file (`ClaimDue`
preceding both quoted positional words, no code anywhere in the file
resolving either). Rephrased to avoid spelling either positional word
anywhere near `ClaimDue` in the comment, with a note left explaining why,
rather than deleted — caught by running the real test suite, not assumed
clean.
