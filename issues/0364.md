## Description

`claimCommentGuardDirectionalCalibrationCases` in
`internal/outbox/claim_comment_referent_guard_test.go` asserts a **count**. A
row with `wantClaimDueFindings: 0` therefore cannot distinguish between:

- no direction-word match at all (the axis was never entered),
- marker-exempt (the historical regex fired),
- window excludes the identifier (the clamp or the 90-char cap).

All three look identical to a reader **and to `go test`**.

**This is not hypothetical — it has already caused two failures.** `#0358`'s
first pass shipped a row whose fixture read `// Below, ClaimDue …`: capitalised,
so `claimCommentGuardDirWordRe` never matched and the axis was never entered.
The row's comment credited the backwards-only window, which it did not test, and
the whole table stayed **green** under the exact mutation that row claimed to
guard. Separately, `#0347`'s third review probed that same fixture believing it
measured the window limit — and measured nothing.

Both times the defect was found only by **hand-instrumenting** the axis
(printing the sentence, the marker match, the computed `lo`, which clamp
produced it, and the window). Two review passes caught it that way; nothing in
the tree does.

## Acceptance criteria

1. Each zero-expectation row states **why** it is silent — a `wantSilentBecause`
   discriminant covering at least: no direction-word match; marker-exempt;
   window excludes.
2. **The discriminant is re-derived from the axis's own primitives, not stored
   as a copy of the answer.** §8 is explicit that a copy of the answer stored
   next to the question is not a check — the row must not simply carry a label
   that a future edit can leave stale while the count still passes. That is the
   whole failure mode being fixed.
3. Prove it discriminates: for each reason, mutate the axis so a row becomes
   silent for a *different* reason than its declared one, and confirm the test
   fails naming that row. A row that cannot fail pins nothing (`#0354`).
4. Re-run `#0358`'s five mutations and confirm each still moves its disjoint
   named row set: broad marker set → the three `never`/`cannot` rows;
   nearest-only → the every-identifier row; no paren clamp → the paren row plus
   the `store.go` test plus the whole-tree
   `TestNoCommentClaimsClaimMachineryCallFileCodeLacks`; forward window → the
   backwards-window row; `(?i)` → the capitalisation row.
5. **Do not change the window logic.** The axis is frozen; `#0363` owns the
   case-sensitivity fix. If this work seems to require an axis change, stop and
   report.
6. No `.ClaimDue(` / `.OrphanSweep(` / `.SelectDue(` call-syntax literal enters
   any Go comment, and the floor harness stays **42 total / 12 non-exempt**
   (`#0323`). Re-run `scripts/go_file_visit_floor_guard_test.sh` and record it.
7. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout (§8).

## A caution from the issue that filed this

`#0358`'s reviewer noted that adding this **now** would have been the in-file
guard-stacking pattern §8 warns against, which is why it is a separate issue
rather than a third round there. Land it as its own considered change, and if
the discriminant turns out to need more machinery than the defect costs, **say
so and stop** — recording the limit is a legitimate outcome, and three separate
guard families reached exactly that conclusion (`#0330`, `#0347`, `#0356`).
