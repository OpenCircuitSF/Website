## Description

`claimCommentGuardDirWordRe` in
`internal/outbox/claim_comment_referent_guard_test.go` is `\b(below|above)\b`
with **no `(?i)` flag**. So a sentence-initial `Below,` or `Above,` — the most
natural way to write a forward reference in Go prose — **never enters the
directional axis at all**.

**This is not a calibration trade.** `#0358` exists to record the axis's
deliberate trades, each of which buys something against a real opposing error.
This one buys nothing: nothing is gained by excluding a capitalised direction
word.

**It has already misled a review.** `#0347`'s third review probed the fixture
`// Below, ClaimDue …` believing it measured the axis's backwards-only window
limit. It did not — the regex never matched, so the axis was never entered, and
the probe measured nothing. `#0358`'s review found this by mutation: adding a
forward-looking window, the exact change that fixture claims to guard, leaves
the whole calibration table **green**.

**The fix is measured free.** `#0358`'s reviewer flipped the flag and measured:
`go test ./internal/outbox/` stays green, the whole-tree scan stays at **0
findings** across 271 files and 30,843 comment groups, and `#0342`'s sites A and
C are still caught.

It was left unfixed there only because `#0358`'s criterion 4 forbids changing
the window logic — hence this issue.

### The defect

`findClaimCommentGuardFindings`, directional axis
(`internal/outbox/claim_comment_referent_guard_test.go`):

```go
dir := flat[dm[2]:dm[3]]          // now (?i), so this may be "Below"/"Above"
...

    if dir == "above" && o < startOff { ok = true }
```

With `dir == "Below"` neither comparison can ever be true, `ok` stays `false`,
and **a finding is emitted for every target identifier in the window regardless
of what the file's code actually contains**. Before this change a capitalised
direction word was invisible (false negative, harmless); after it, every
capitalised direction word with a claim-machinery identifier in its 90-char
backward window is reported as a directional error even when the comment is
**correct** — the exact false-positive class `#0347`'s three review rounds spent
their effort eliminating (paren scoping, nearest-vs-every identifier).

Instrumented in a throwaway `git archive HEAD` export under the scratchpad
(never the tracked tree, §8b), printing the marker match, `dir`, the sentence,
the computed `lo` and which clamp produced it, the window, and the code offsets:

|---|---|---|---|

### On whether this guard family terminates

`#0358`'s review argued the family terminates because its table makes a **floor
claim** ("these behaviours are pinned") rather than an **inventory claim**
("these are all the behaviours"). Converting one row from control to regression

What this round adds is a different failure mode, and it is not a closed-claim

rather than adding another layer defending the file from edits to itself.

So: the family terminates, but not at `#0363`. It terminates when every
calibration row is shown to get its number for its named reason.

#### 1. `strings.ToLower` is exhaustively correct here, not just adequate

`strings.ToLower` is **not** in general the inverse of a `(?i)` match — Go's
regexp uses Unicode simple case folding, so `(?i)k` also matches U+212A KELVIN
SIGN and `(?i)s` also matches U+017F LATIN SMALL LETTER LONG S, neither of which
`ToLower` maps back to ASCII. That hazard is real; it just does not reach these
two words. Proved rather than argued, by enumerating **every rune in
`[U+0000, U+10FFFF]`** at each of the five byte positions of `below` and `above`
and asking the live pattern which ones it admits:

| word | position | runes admitted by `(?i)\b(below\|above)\b` |
|---|---|---|
| `below` | b, e, l, o, w | exactly 2 each — `U+0042/U+0062`, `U+0045/U+0065`, `U+004C/U+006C`, `U+004F/U+006F`, `U+0057/U+0077` |
| `above` | a, b, o, v, e | exactly 2 each — `U+0041/U+0061`, `U+0042/U+0062`, `U+004F/U+006F`, `U+0056/U+0076`, `U+0045/U+0065` |

None of `a b e l o v w` has a fold orbit member outside ASCII. So the **entire
input language of `dir` is 64 strings** (2⁵ per word), and I enumerated the full
cross-product of all 64: every one matches, and `strings.ToLower` maps every one
to its base word — **0 mismatches**. Mixed case (`BeLow`, `belOW`, `AbOvE`) is
covered by that enumeration, not by spot checks. `strings.EqualFold` would have
been equally correct and no more so; `ToLower` is the right call.

**Was flipping the flag worth it, given the axis found zero real defects and the
corpus was green by coincidence? Yes — keep it. I would not revert.** I
considered revert seriously, and the case for it is real: two implementation
passes, two reviews, and a live false-positive bug shipped in between, against
**zero** defects found in the newly-admitted population. On a pure
defects-found-per-round basis, revert wins. Four things outweigh it:

1. **The gap was not a trade, so `#0358`'s table is the wrong home for it.**
   Every other row there buys something against an opposing error; this one
   bought nothing. Recording a pure defect *as if* it were a design decision is
   what misled `#0347`'s third review once already — it probed the capitalised
   fixture believing it measured the window limit, and measured nothing. Revert
   would re-create precisely that trap, with a table entry blessing it.
2. **A guard is valued by what it will catch, not by what it caught today.**
   Sentence-initial `Below,` is the most natural way to write a forward
   reference in Go prose; my margin measurement says the tree is **one reworded
   sentence** away from the population being non-empty. "Zero defects found
   today" would condemn every floor constant in this repo by the same reasoning.
3. **The tree is measurably better instrumented than before `#0363`.** The
   pre-`#0363` code had one row pinning nothing; it now has five rows surviving
   six distinct mutations. That instrumentation is the durable asset, and it is
   worth more than the flag.
4. **Revert would leave the real hazard undocumented.** The resolution
   comparison's case-sensitivity is a genuine trap that the next person adding
   `(?i)` would fall into identically. R1's doc comment and the resolution pins
   are what stop that; reverting deletes them and keeps the trap.

**The honest lesson, and it is not "one flag was too small a change".** It is
that `#0363`'s own `## Description` called the fix "measured free" on the
strength of a **green tree** — and a green tree was the wrong oracle, because no
input in the corpus reached the newly-enabled code path. **A change that opens a
code path no existing input exercises cannot be validated by running the
suite**; it needs a fixture built specifically to reach the new path, which is
what R2 supplies and what the first pass's no-code fixture could not. That is
the same shape as `#0364`'s discriminant question, one level up, and worth
recording there rather than as a new issue.
