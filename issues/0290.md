## Description

`#0261` closed the pointer-held (`e := &audit.Entry{…}`) and map-mutating
(`delete`, `maps.Copy`) shapes. Its review then ran a wider sweep of adjacent
shapes through `scanAuditEntrySites` and found three families that still pass
silently. Reproductions for every one are in `issues/0261.md`'s
`## Review notes` table — start there rather than re-deriving them.

**None of these was introduced by `#0261`.** The `var`-declaration and
elided-literal holes predate `#0252`. This is the next round of a guard that has
now been extended five times (`#0237`, `#0252`, `#0255`, `#0257`, `#0261`), and
the recurring lesson is that each pass closes the shape it was shown.

### 1. `var` declarations bypass the family entirely

```go
var e = audit.Entry{…}     // and: var e = &audit.Entry{…}
e.Metadata = map[string]string{"email": addr}
```

`compositeLitAssignedIdents` only inspects `*ast.AssignStmt`. A `var` declaration
is an `*ast.ValueSpec`, so the literal is never mapped to its identifier and the
whole `#0252`/`#0257`/`#0261` deferred-mutation machinery never engages.

Extending to `*ast.ValueSpec` is the cheapest and most exact analogue of what
`#0261` just did.

### 2. Elided composite literals are not sites at all — the sharpest of the three

```go
[]audit.Entry{{Metadata: map[string]string{"email": addr}}}
map[string]audit.Entry{"a": {Metadata: …}}
```

Inside a slice or map of `audit.Entry`, the inner literal's `Type` is `nil`, so
the scan does not recognise it as a site. This is the worst of the three because
**a direct, inline `"email"` escapes** — no deferred mutation is involved, so
none of the existing machinery is even in play.

### 3. `maps.Insert` and friends

`delete` was added "for completeness" alongside `maps.Copy`, but `maps.Insert` —
the key-introducing sibling — is unmatched, as are the removal-only
`maps.DeleteFunc` and `clear()`.

### Also worth pinning

`p := &e; p.Metadata = …`, a factory returning `*audit.Entry`, `(*e).Metadata =
…`, and an aliased or dot-imported `maps`.

The name-match direction that is *safe* was verified: a local variable named
`maps` fails **closed** (reports `unresolved`), so the false-positive direction
is the harmless one.

### Criterion 4 — the six pins are honest

Checked each pin's *claim* against the post-fix behaviour rather than accepting
the prose, and the mechanism makes a dishonest pin structurally hard to write:
`TestAuditEmailMetadataGuardDocumentedSilentPassShapes` asserts **all three** of
`len(sites) == 1`, `unresolved == ""`, and `hasEmail == false`. A shape the guard
actually caught would set one of the latter two and fail the pin. So the pins
cannot silently cover a caught shape — they are two-sided assertions of
blindness, not comments.

Each stated mechanism also holds on inspection:

| Pinned shape | Stated reason | Verified |
|---|---|---|
| `p := &e; p.Metadata = …` | literal maps to `e`, deferred set marks `p`, names differ | yes — `auditEntryLiteralBehindIdent` unwraps `&` around a *literal*, and `&e` wraps an `*ast.Ident` |
| `(*e).Metadata = …` | `markMetadataField` needs `sel.X` to be a bare `*ast.Ident`; `(*e)` is a `ParenExpr`/`StarExpr` | yes |
| factory returning `*audit.Entry` | scope boundary — the literal and the mutation are in different function bodies | yes; the one site found is `newEntry`'s own literal, correctly classified in isolation |
| aliased `import m "maps"` | matchers compare the package identifier by name | yes |
| dot-imported `. "maps"` | `Copy(…)` is not an `*ast.SelectorExpr` at all — a different failure mode from the aliased case | yes |
| package-level `var` / func-literal shapes | the walk only enters `*ast.FuncDecl` bodies | unchanged from prior rounds, still pinned in `TestAuditEmailMetadataGuardDocumentedInvisibleShapes`, now correctly saying **two** shapes rather than three |

Every "no production site does this" claim in the pins was re-run rather than
trusted. All four greps return nothing outside the guard file's own comments:
`:= &e`, `maps "maps"` / `. "maps"`, `func clear(` / `clear :=`, and

### Criterion 7 — the `go/types` decline

Judged on its own terms rather than as inherited reasoning, and it holds:

- Items 2 and 3 genuinely are **not** type questions. An elided literal's
  container type is written explicitly in the AST one level up, so a single
  level of nesting needs no inference; the call matchers are pure call shape.
  Declining `go/types` for those costs nothing, and the pass says so.
- The pass **concedes** that the aliased/dot-imported `maps` gap *is* a type
  question and that `go/types` is what would resolve it. That concession is the
  reason this decline reads as honest rather than as the overstatement `#0296`
  is open against. The decline rests on two checkable facts — nothing in the
  tree imports `maps` aliased or dot-imported (re-verified), and the file's
  synthetic fixtures import nothing and would not type-check — not on a claim
  of zero marginal precision.

One caveat for whoever revisits this: the supporting clause citing `#0282`'s
untyped-constant finding answers the *read-side* classification question, which
is a different sub-question from import-alias resolution. It should not be read
as evidence that `go/types` could not resolve `m.Copy` — it demonstrably could.
The decline stands on the fixture constraint and the absent shape, and those are
sufficient.
