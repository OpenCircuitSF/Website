## Description

Three inaccuracies found by `#0127`/`#0128`'s review. None is a behavioural
defect — every property they describe genuinely holds — but each credits the
**wrong mechanism**, which is the kind of comment that gets a correct safeguard
deleted as redundant.

**1. `AdminResendConfirmation`'s cooldown comment names a mechanism it does not
use.** `internal/subscribers/pending.go` claims
`ClaimAndEnqueueConfirmation`'s WHERE-clause claim. The code actually checks in
Go, after `SELECT … FOR UPDATE`. The property holds — the reviewer proved it
with eight concurrent resends (`wins=1 cooldowns=7 queued_delta=1`) — but **a
reader who believes the comment could remove the `FOR UPDATE` as redundant**,
and the guard would silently become a race. `issues/0128.md` repeats the claim.

**2. `formatPendingAge` advertises an output it cannot produce.**
`web/src/lib/pending.ts` documents a `"45 seconds"` result; anything under 60s
returns `'just now'`.

**3. `render()`'s comment is now stale.** It says the worker will not refuse a
missing `physical_address` "for a confirmation" — but `#0127` added the welcome
email, the first arguably-commercial message on that path. See `#0264`, which
covers whether the behaviour should change; this item is only the comment.

### Item 1 — the cooldown comment, checked against the code

The corrected comment claims the cooldown is an ordinary Go check against a
row already locked `FOR UPDATE`, **not** a claim baked into an `UPDATE`'s
`WHERE` clause. Read the path rather than the comment, and it is right:

- `internal/subscribers/pending.go` locks the row with
  `SELECT ... WHERE id = $1 AND synthetic = false FOR UPDATE`.
- Guard 4 is a plain Go conditional —
  `if sub.ConfirmSentAt != nil && sub.ConfirmSentAt.After(now.Add(-cooldown))`
  — returning `ErrResendCooldownActive`.
- The write that follows is `UPDATE subscribers SET confirm_token = $2, ...
  WHERE id = $1` — **no cooldown predicate in the `WHERE` clause at all**.
  So the row lock really is the only thing serializing two concurrent
  callers, exactly as the new comment says.

**The contrast it draws is also real, not invented.** I checked the
mechanism it names as the counterexample:
`internal/subscribers/store.go`'s `ClaimAndEnqueueConfirmation` genuinely
does use the claim-in-the-`WHERE`-clause shape —
`UPDATE subscribers SET confirm_sent_at = $2, updated_at = $2 WHERE id = $1
AND (confirm_sent_at IS NULL OR confirm_sent_at < $3)`. The two mechanisms
differ exactly as described, which is the whole point of the correction.

**The `FOR UPDATE` note is load-bearing and specific.** It names the failure
mode ("a read-then-write race: two concurrent callers could both read
`confirm_sent_at` as 'outside the cooldown' before either writes, producing
two resends instead of one") and says plainly "do not remove it as apparently
redundant with the `WHERE` clause below — it is not redundant." That is the
comment the original defect would have caused a reader to disregard, and it
now answers the exact question a deleting reader would ask.

### Item 2 — `formatPendingAge`, checked against the code

`web/src/lib/pending.ts`'s body is `const s = Math.max(0, Math.floor(ageSeconds));
if (s < 60) return 'just now';` and then minutes/hours/days. There is **no
seconds branch**, so the old "45 seconds" example was unproducible. The
corrected doc now says "just now" (anything under 60 seconds; there is no
seconds branch) — which matches the boundary exactly, including the `Math.max(0, …)`
clamp the doc also describes.

### Item 3 — `render()`'s comment, landed in `#0264`'s `611915b`

Deferring this to `#0264` rather than editing the same comment twice in one
concurrent-agent window was the right call, and the shipped text is accurate.
Checked against `render`'s actual `switch`: the comment names the six
non-commercial kinds it does *not* refuse for (`confirmation`,
`already_subscribed`, `registration`, `recovery`, `sessions_revoked`,
`admin_alert`) and those are exactly the six non-welcome cases the switch
handles; `KindWelcome` is named as the one deliberate exception with its
reasoning inline, and the `default:` arm correctly still lists `goodbye` and
`import_invite` as having no renderer. Cross-checked against `#0264`'s own
review, where the refusal was proved in both directions.

## Notes

Reported by `#0127`/`#0128`'s phase-3 review under `CLAUDE.md` §9.

**Worth noting what let item 1 through.** `#0196`, `#0199` and `#0220` built
citation guards that check whether a cited *test or path exists*. None of them
can check whether a comment's *description of a mechanism* is true — that
requires understanding the code, not resolving a reference. This class has now
cost this project repeatedly (`#0190`, `#0192`, `#0216`, `#0237`'s seven
rounds), and the honest position is that review is the only instrument for it.

That is an argument for keeping mechanism claims **short and checkable**, or
omitting them: a comment saying "cooldown enforced here" cannot be wrong the way
"enforced by the WHERE clause in X" can.
