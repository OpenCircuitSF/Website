## Description

`#0286` widened the live-region guard so every in-branch `role="status"` site is
checked. Its review measured the result and it is a genuine widening:

| | |
|---|---|
| Status sites | 52 (4 unconditional + 48 in-branch) |

| of the 48 — **unchecked** | **0** (was 24 of 47) |

**The swap hatch is now the largest one**, and it is the loosest. A site passes
it when a focus move exists *somewhere in its governing branch* — and ~~**8 of
those 21 pass via an unrelated modal's `.focus()`**~~:

- `Admin.svelte` ×5 — `editInterestModalEl`, `subscriberDetailModalEl`, `suppressModalEl`
- `WorkshopEditor.svelte` ×2 — `transitionModalEl`

Including, pointedly, the CSV-import notice `#0286` had just fixed: it now passes
via `subscriberDetailModalEl` rather than on the persistence grounds that
actually make it correct.

**Correction (#0299 review, 2026-08-27).** The struck figure is wrong twice
over, and the bullet list under it is a different quantity from the prose.
Re-measured from the AST by the reviewer, against commit `ea08188`'s parent
tree, with an instrumented copy of the guard: **7** in-branch `role="status"`
sites match a modal-bound var under the old, untightened `findFocusTargetVar`
— exactly the seven the bullets enumerate (`Admin.svelte` 1590, 1764, 1840,
1863, 2277; `WorkshopEditor.svelte` 589, 657), so the bullets were right and
the "8" was an arithmetic slip. Of those seven, only **5** match a target
behind a *further, nested* conditional and are therefore "unrelated": the
other two (`Admin.svelte:1764` `editDeactivating`, `Admin.svelte:2277`
`suppressNotice`) sit inside the very `{#if editingInterest}` /
`{#if suppressingSubscriber}` fragment their modal's `bind:this` target sits
in, so the modal *is* their governing branch and they pass the swap hatch
correctly. The number this issue's criterion 2 is about is therefore **5**,
which is what the implementation measured and resolved.

**This is pre-existing, deliberate, and disclosed** in the guard's header, and
`#0242`'s review endorsed it. These sites previously got *no* check at all, so
nothing regressed. But the hatch is now load-bearing across far more of the tree
than when it was endorsed.

The shape is recursive and worth naming: **this hatch stands to `#0286` exactly
as `#0286`'s gap stood to `#0242`.** Each widening makes the next-loosest
mechanism the one carrying the weight.

## Acceptance criteria

1. A focus-swap target only satisfies a `role="status"` site when the focus move
   is plausibly *for that site* — same subtree, or an explicit association —
   rather than anywhere in a large governing branch.
2. The ~~8~~ **5 (corrected 2026-08-27, #0299 review — see the Description's
   correction note)** sites currently passing via an unrelated modal are each resolved: fixed
   on their own merits, or given a named stable-branch entry with a written
   reason under [#0280](0280.md)'s rules. Enumerate them and say which each got.
3. The CSV-import notice specifically should pass on the persistence grounds
   that make it correct, not via `subscriberDetailModalEl`.
4. Re-measure the hatch tally afterwards and record it, in the same form as the
   table above, so the next widening starts from a measured baseline rather than
   a re-derivation.
5. Prove the tightened rule fires: a fixture whose only focus move is in an
   unrelated part of the governing branch must fail.
6. Do not trade this for a new blanket hatch. If tightening produces more sites
   than can be fixed in one pass, allowlist them **named and justified** and say
   how many — a silent cap reads as "covered everything".
7. `ISSUE=NNNN scripts/check.sh web` passes, `filesScanned >= 35` still fails
   closed, and the counts are re-derived rather than edited by hand.

returns immediately (without recursing further) on hitting a nested
`IfBlock`/`EachBlock` while walking a site's governing branch. `root` is
always the site's own nearest-enclosing branch fragment; a

### Two things reported, not fixed — worth filing

1. **The stable-branch hatch is now the fastest-growing mechanism, and its only
   validation is a human-written sentence.** `KNOWN_STABLE_BRANCH_SITES` went
   7 → 12 in one pass while the swap hatch went 21 → 16, and by the issue's own
   recursive framing that makes it the next candidate. Its claim — "this site
   is unconditionally rendered inside a *large, stable, multi-purpose* branch" —
   is partly machine-checkable from the AST (the governing branch's significant
   node count, i.e. the property `#0286` removed as `isGoverningBranchDynamic`),
   and today rests entirely on prose. Recommend filing.
2. **Latent mis-attribution of an `{#each}`'s `{:else}` fragment.**
   `collectSites`'s `EachBlock` arm walks only `body` with the each's own
   governing branch and lets `fallback` fall through to the generic loop with
   the **outer** branch — so a `role="status"` in an each's empty-state branch
   would be attributed to the wrong branch, and at top level would be seen as
   fully unconditional and never checked. I scanned the whole tree: **zero**
   live regions currently sit in an each-else, so this is latent, not live.
   Recommend filing at low priority.
