## Description

`#0286` widened the live-region guard so every in-branch `role="status"` site is
checked. Its review measured the result and it is a genuine widening:

| | |
|---|---|
| Status sites | 52 (4 unconditional + 48 in-branch) |
| of the 48 — loading placeholders | 20 |
| of the 48 — whole-panel-swap targets | **21** |
| of the 48 — named stable-branch entries | 7 |
| of the 48 — **unchecked** | **0** (was 24 of 47) |

**The swap hatch is now the largest one**, and it is the loosest. A site passes
it when a focus move exists *somewhere in its governing branch* — and **8 of
those 21 pass via an unrelated modal's `.focus()`**:

- `Admin.svelte` ×5 — `editInterestModalEl`, `subscriberDetailModalEl`, `suppressModalEl`
- `WorkshopEditor.svelte` ×2 — `transitionModalEl`

Including, pointedly, the CSV-import notice `#0286` had just fixed: it now passes
via `subscriberDetailModalEl` rather than on the persistence grounds that
actually make it correct.

**This is pre-existing, deliberate, and disclosed** in the guard's header, and
`#0242`'s review endorsed it. These sites previously got *no* check at all, so
nothing regressed. But the hatch is now load-bearing across far more of the tree
than when it was endorsed.

The shape is recursive and worth naming: **this hatch stands to `#0286` exactly
as `#0286`'s gap stood to `#0242`.** Each widening makes the next-loosest
mechanism the one carrying the weight.

## Acceptance criteria

1. A focus-swap target only satisfies a `role="status"` site when the focus move
   is plausibly *for that site* — same subtree, or an explicit association —
   rather than anywhere in a large governing branch.
2. The 8 sites currently passing via an unrelated modal are each resolved: fixed
   on their own merits, or given a named stable-branch entry with a written
   reason under [#0280](0280.md)'s rules. Enumerate them and say which each got.
3. The CSV-import notice specifically should pass on the persistence grounds
   that make it correct, not via `subscriberDetailModalEl`.
4. Re-measure the hatch tally afterwards and record it, in the same form as the
   table above, so the next widening starts from a measured baseline rather than
   a re-derivation.
5. Prove the tightened rule fires: a fixture whose only focus move is in an
   unrelated part of the governing branch must fail.
6. Do not trade this for a new blanket hatch. If tightening produces more sites
   than can be fixed in one pass, allowlist them **named and justified** and say
   how many — a silent cap reads as "covered everything".
7. `ISSUE=NNNN scripts/check.sh web` passes, `filesScanned >= 35` still fails
   closed, and the counts are re-derived rather than edited by hand.

## Work log

Tightened `findFocusTargetVar` in
`web/src/lib/liveRegionGuard.structuralGuard.test.ts` (criterion 1): it now
returns immediately (without recursing further) on hitting a nested
`IfBlock`/`EachBlock` while walking a site's governing branch. `root` is
always the site's own nearest-enclosing branch fragment; a
`tabindex="-1"`+`bind:this` target reachable only by first entering a
FURTHER, inner conditional (a modal dialog gated behind its own `{#if
showModal}`) has its own, narrower governing branch — it mounts/unmounts on
its own trigger, not on whatever mounts the site's branch — so it no longer
counts as "for" that site. Genuinely same-branch cases (a direct sibling, no
intervening `IfBlock`/`EachBlock`) are unaffected: Login.svelte's self-bound
notices, Unsubscribe.svelte's sibling `doneHeading`, and CampaignEditor.
svelte's `headingEl` (which the file's own header already described as
covering several status regions scattered through the *same* `{:else if
campaign}` fragment) all still pass, unchanged.

**Enumeration first, before deciding fixes.** Ran a temporary instrumented
pass over the real tree (removed before verifying) listing every site
currently swept in by the OLD, untightened swap hatch, with the var each one
matched. That produced the ground truth: exactly 5 in-branch sites — not the
7 the issue's own vars-list sums to, and short of the "8" in its prose,
which appears to be an arithmetic slip in the issue text; my own measured
count is reported here in its place — pass the swap hatch via a target
behind a NESTED conditional inside their own outer branch:

  - `Admin.svelte:1590` (`newSlugInvalid` hint) — was matching
    `editInterestModalEl`, behind `{#if editingInterest}`
  - `Admin.svelte:1840` (`createSubNotice`) — was matching
    `subscriberDetailModalEl`, behind `{#if viewingSubscriber || ...}`
  - `Admin.svelte:1863` (the CSV-import notice, `importCommitNoticeText(...)`)
    — was matching `subscriberDetailModalEl`, same as above
  - `WorkshopEditor.svelte:589` (`saveNotice`) — was matching
    `transitionModalEl`, behind `{#if transitionOpen}`
  - `WorkshopEditor.svelte:657` (`unsavedInterestsHint`) — was matching
    `transitionModalEl`, same as above

Two OTHER Admin.svelte sites also match `editInterestModalEl`/
`suppressModalEl` (`Admin.svelte:1764`, the `editDeactivating` hint, and
`Admin.svelte:2277`, `suppressNotice`) but are legitimate: both sit directly
inside the SAME nested branch as their modal's own bind target (`{#if
editingInterest}` / `{#if suppressingSubscriber}` respectively), not behind
a further conditional relative to it — the modal IS their governing branch.
These are unaffected by the tightening and still pass via the swap hatch,
correctly.

**All 5 real violations resolved via a named stable-branch entry (criterion
2), none needed a code change.** Each of the 5 is itself unconditionally
rendered (not wrapped in its own `{#if}`) inside a large, stable,
multi-purpose branch — the SAME shape as `settingsNotice`/`addressNotice`/
CampaignEditor's `audience-count` (the guard's pre-existing
`KNOWN_STABLE_BRANCH_SITES` calibration examples). That persistence argument
was already true of all 5 before this issue; they had simply been
mis-credited to an unrelated modal instead. Added them to
`KNOWN_STABLE_BRANCH_SITES` with a reason explaining both the persistence
argument AND the previous mis-credit, reusing (with an appended addendum)
the existing `KNOWN_STABLE_BRANCH_REASON_TAB_PANEL` constant for the three
Admin.svelte per-tab sites, and a new `KNOWN_STABLE_BRANCH_REASON_MAIN_FORM`
constant for WorkshopEditor's two main-form sites. Criterion 3 (the
CSV-import notice specifically): its entry says explicitly that it now
passes on the persistence ground `#0286` actually made correct, not via
`subscriberDetailModalEl`.

Criterion 6 does not apply — 5 of 5 real violations were resolved with a
named, justified entry; 0 remain unresolved or capped.

**What this promotes (per the issue's own recursive framing).** The
tightening does not create a new hatch; it moves 5 sites from the swap hatch
to the (already third, already-endorsed) stable-branch hatch, which is now
the largest single-purpose classifier of the three at 12/48 -- still smaller
than the swap hatch's new total of 16/48, so the swap hatch remains the
largest mechanism. Nothing was newly promoted to "largest and loosest";
`KNOWN_STABLE_BRANCH_SITES` already carried the same per-entry justification
and staleness requirements every other allowlist here does (#0280), so this
tightening did not create new unguarded surface — it moved 5 sites onto a
mechanism that was already as strict as this file gets.

Added two fixtures (criterion 5): one proving a status site whose only
