## Description

`#0164` replaced the parity guard's three ad-hoc scanners with one tokenizer, which closed both known silent gaps and three defects earlier reviews had *accepted*. Its review found three residual items, and the third is **live in the tree today**.

**1. An unpaired apostrophe blanks everything after it — silently.** In text state the tokenizer opens a string span at the first `'` and closes it at the next one; with no next one, the rest of the input becomes blank. All four coverage checks then agree at 0/0, so nothing fires. Two rows of `#0159`'s table (`unterminated $$`, `mismatched tags`) technically regress here.

Not bounced, for reasons that hold: three of the four triggers are SQL that Postgres itself rejects, so `scripts/testdb.sh template` fails first; and truncate-to-EOF is the policy `#0154` already accepted as *right* for an unterminated block comment, now applied uniformly. The only trigger that is valid SQL is a double-quoted identifier containing an apostrophe (`"it's"`), or an `E'…\'…'` escape string — neither exists in the tree. Fix is ~10 lines: a `kindQuotedIdent` case in the same switch.

**2. Block comments do not nest, but Postgres nests them.** `/* /* */ */` leaves the tail live, so a phantom can enter the map — harmless unless it collides with a guarded table, and loud if it does. One comment line at most.

**3. `PRD.md` §6.2's prose is partly blanked, right now.** The guard tokenizes *markdown* as SQL. One unpaired apostrophe in §6.2's prose — "…`CLAUDE.md` §1's append-only rule…" — opens an **808-byte** string span, blanking **867 of §6.2's 18,660 bytes**.

Nothing is lost today (13/13 tables and 16/16 indexes still parse) and the failure direction is loud rather than silent. But it is luck, not design: a schema line landing inside a blanked span would produce a "PRD does not mention X" failure whose cause — an apostrophe in an unrelated sentence — nobody would find quickly.

## Root cause

`TestPRDWorkshopAndMailingIndexParity` and `TestPRDWorkshopAndMailingColumnParity`
both called `prepareSQLText(extractPRDSection(...))` directly — feeding
`extractPRDSection`'s whole slice of `PRD.md` markdown, prose and all,
straight into `tokenizeSQL` as though every byte of it were SQL. `tokenizeSQL`
itself is correct SQL-tokenizing code; the defect was in what got handed to
it. Ordinary English prose is riddled with the exact characters `tokenizeSQL`
treats as structural (apostrophes, semicolons implied by sentence-final
periods aren't an issue, but the apostrophe is): §6.2's closing prose contains
"…`CLAUDE.md` §1's append-only rule…", an unpaired `'` that opened a
`kindString` span running to the *next* apostrophe found anywhere later in the
section — 808 bytes away — blanking real (if unrelated) text in between.
Nothing broke today because no schema statement happened to land inside that
window, but the guard's correctness depended on that coincidence, not on its
design.

## Fix

**Item 3 (the durable fix, scoped in per the issue's own framing).** Added
`extractFencedSQL` (`internal/db/prd_index_parity_test.go`), which narrows a
`PRD.md` section down to only the content of its ` ```sql ` fenced code
block(s) via `sqlFencePattern` (`` (?s)```sql\r?\n(.*?)\r?\n``` ``), joining
multiple blocks with a blank-line separator so a future second fence can never
be read as a run-on continuation of the first. Both parity tests now call
`extractFencedSQL(t, extractPRDSection(...))` before `prepareSQLText`, so
`tokenizeSQL` only ever sees text that is actually SQL. `§6.2` today has
exactly one ` ```sql ` block (verified with `grep -n '^```'`), so this is a
no-op on the parsed content — it only removes the markdown around it, which
was never supposed to be there. If the fence is ever moved or loses its `sql`
language tag, `extractFencedSQL` fails loudly (`t.Fatalf`) rather than
silently falling back to markdown.

**Items 1 and 2 — declined**, per the issue's own "legitimate outcome"
framing (both are theoretical against SQL this repo does not write, and item 3
is the only one with a real failure mode in the tree today). The reasoning is
recorded in code, not only here, since that is where the next reader
investigating either behavior will look:

- **Item 1** (unpaired `'` in text state blanks to EOF): a ~25-line comment
  was added directly above the `'` case in `tokenizeSQL`, explaining that this
  is a deliberate, uniform application of the same truncate-to-EOF policy
  `#0154` already accepted for an unterminated block comment; that three of
  the four ways to trigger it are SQL Postgres itself rejects (so
  `scripts/testdb.sh template` / `golang-migrate` fail first); that the only
  SQL-legal trigger (a double-quoted identifier containing `'`, or an `E'...'`
  escape string) has no `kindQuotedIdent` state and does not exist anywhere in
  this tree (`grep` over `migrations/*.up.sql` and `PRD.md`'s fenced SQL); and
  that this makes two of `#0159`'s classification rows (`unterminated $$`,
  `mismatched tags`) behave differently than that issue recorded — flagged
  explicitly, not left implied.
- **Item 2** (`/* /* */ */` does not nest, unlike Postgres): a comment was
  added directly above the block-comment case explaining it closes at the
  first `*/`, that this is harmless unless a phantom name inside the
  reopened tail collides with a guarded table (in which case it's a loud
  false "PRD does not mention X", never silent), and that no block comment of
  any kind exists in `migrations/` or in `PRD.md`'s fenced SQL today.

`tokenizeSQL`'s actual scanning logic (the `switch` bodies) is **byte-for-byte
unchanged** from `#0164` — confirmed by diffing the commit and seeing every
non-comment line is either the new `extractFencedSQL`/`sqlFencePattern` or the
two call-site edits routing `PRD.md` text through it.

### 4. Why a dropped block is loud, not silent — proved end-to-end

P6/P7/P15 drop a schema-bearing block without a fatal, which reads as the exact
"the guard quietly stops guarding those tables" failure. It is not, and the
reason is `#0148`'s one-directional scope: the guard walks what **migrations**
created and asserts §6.2 names it. Anything the extractor drops from the *PRD*
side therefore surfaces as a missing mention, never as a missing check.

Proved by injection — §6.2's single fence split in two at
`CREATE TABLE workshops`, so the second half carries guarded schema, written to
`t.TempDir()` and `prdPath` pointed at it:

| Injected §6.2 | `IndexParity` | `ColumnParity` |
|---|---|---|
| A — second block tagged `` ```SQL `` | **FAILED (loud)** | **FAILED (loud)** |
| B — second block **untagged** | **FAILED (loud)** | **FAILED (loud)** |
| C — second block tagged `` ```sql `` (control) | passed | passed |
| D — the only block retagged `` ```postgres `` | **FAILED (loud)** | **FAILED (loud)** |
| E — unmodified `PRD.md` (control) | passed | passed |

A and B fail with the actionable message, naming every dropped object:

```
PRD.md §6.2 does not mention index "idx_workshops_visible" (table workshops),
defined in migrations/000020_create_workshops.up.sql — …
PRD.md §6.2's CREATE TABLE workshops does not mention column "capacity", …
```

(19 such column failures and 2 index failures per case.) D fails with the
extractor's own dedicated message, confirming the `## Fix`'s claim that losing
the `sql` tag fails loudly rather than falling back to markdown:

```

listing moved out of a fenced block, or lost its "sql" language tag? See #0173.
```

The residue is that a dropped block containing **only unguarded** content (a
Phase 8 forward declaration such as `subscriber_imports`) would vanish
silently — but that content is outside the guard's scope by design, so nothing
is lost. P10/P17's over-capture leaks prose back to the tokenizer, i.e.
degrades to the *pre-fix* state, which was itself loud-but-baffling; both
require a malformed §6.2 (an unterminated fence, or `` ```sql `` written inline
in prose).
