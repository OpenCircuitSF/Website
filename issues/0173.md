## Description

`#0164` replaced the parity guard's three ad-hoc scanners with one tokenizer, which closed both known silent gaps and three defects earlier reviews had *accepted*. Its review found three residual items, and the third is **live in the tree today**.

**1. An unpaired apostrophe blanks everything after it — silently.** In text state the tokenizer opens a string span at the first `'` and closes it at the next one; with no next one, the rest of the input becomes blank. All four coverage checks then agree at 0/0, so nothing fires. Two rows of `#0159`'s table (`unterminated $$`, `mismatched tags`) technically regress here.

Not bounced, for reasons that hold: three of the four triggers are SQL that Postgres itself rejects, so `scripts/testdb.sh template` fails first; and truncate-to-EOF is the policy `#0154` already accepted as *right* for an unterminated block comment, now applied uniformly. The only trigger that is valid SQL is a double-quoted identifier containing an apostrophe (`"it's"`), or an `E'…\'…'` escape string — neither exists in the tree. Fix is ~10 lines: a `kindQuotedIdent` case in the same switch.

**2. Block comments do not nest, but Postgres nests them.** `/* /* */ */` leaves the tail live, so a phantom can enter the map — harmless unless it collides with a guarded table, and loud if it does. One comment line at most.

**3. `PRD.md` §6.2's prose is partly blanked, right now.** The guard tokenizes *markdown* as SQL. One unpaired apostrophe in §6.2's prose — "…`CLAUDE.md` §1's append-only rule…" — opens an **808-byte** string span, blanking **867 of §6.2's 18,660 bytes**.

Nothing is lost today (13/13 tables and 16/16 indexes still parse) and the failure direction is loud rather than silent. But it is luck, not design: a schema line landing inside a blanked span would produce a "PRD does not mention X" failure whose cause — an apostrophe in an unrelated sentence — nobody would find quickly.

## Acceptance criteria

- [ ] **Extract §6.2's fenced SQL blocks before tokenizing**, rather than tokenizing markdown prose as SQL. This is the durable fix for item 3 and removes a whole class of coincidence
- [ ] Item 1: decide whether to add the `kindQuotedIdent` case, or to record that truncate-to-EOF is deliberate and uniform. Either is defensible — but if the answer is "deliberate", say so where the next reader will look, since two `#0159` rows now behave differently than that issue recorded
- [ ] Item 2: nest block comments, or state in a comment that they do not and why that is acceptable
- [ ] **Regression bar, unchanged from three prior passes**: re-run `#0154`'s and `#0159`'s classification tables (~50 rows) and `#0164`'s 27 span + 5 offset probes; the live map must still equal `information_schema.columns` at `IDENTICAL, 91 columns`; no false positives on the tree including Phase 8 forward declarations; scope stays one-directional
- [ ] `ISSUE=0173 scripts/check.sh go ./internal/...` passes with all four doc guards observed

## Notes

Reported by `#0164`'s phase-3 review under `CLAUDE.md` §9.

This is the fifth pass over this file. `#0164` was worth building — it closed five defects and deleted three scanners — but the honest question before starting a sixth is whether item 3 alone justifies it. Item 3 is the one with a real (if unlikely) failure mode nobody would diagnose; items 1 and 2 are theoretical against SQL this repo does not write. **Doing item 3 and explicitly declining 1 and 2 with reasoning is a legitimate outcome.**
