## Description

`#0295` established that `internal/mailing/worker.go` claims per row rather than
per batch, so its 70s `orphanStaleAfter` covers a single row's 35s hold with 35s
of real margin. No arithmetic defect existed and no constant changed.

**But 35s is not a strict bound**, and `#0295` documented why: the worker is
started with `Run(context.Background())`, and while the *success* path uses
bounded `sendCtx`/`writeCtx`, the **failure path does not**. `ClaimRow`,
`MarkFailedRow`, and `MarkRetryOrFailed` all run on the undeadlined ambient
context. A hung write on any of them holds `'sending'` indefinitely, with
nothing to stop it before the orphan sweep eventually reclaims the row.

**A fourth site, added by `#0295`'s reviewer:** `drainLoop`'s `ReleaseRow` on the
`sendOutcomeTerminalCampaign` path is undeadlined for the same reason, and the
row sits in `'sending'` while it runs. Treat it as part of this issue.

Nothing is broken today and the margin is generous. This is filed because the
asymmetry is invisible — the success path is carefully bounded, which makes it
easy to assume the whole function is.

## Why it matters only if the window tightens

At 70s against a 35s hold, an unbounded failure write has 35s of slack before it
can matter. If anyone later tightens `orphanStaleAfter` toward the honest per-row
bound, this becomes the term that makes the bound false — the same shape that
bounced `#0284` twice, where a comment named a bound the code did not have.

So: fix it, or record it next to the constant so the next person to tighten the
window sees it.

## Acceptance criteria

1. `ClaimRow`, `MarkFailedRow`, `MarkRetryOrFailed`, and `drainLoop`'s
   `ReleaseRow` on the `sendOutcomeTerminalCampaign` path run on a bounded,
   **detached** context — detached because a failure write must still complete
   when the ambient context is already cancelled by shutdown, which is exactly
   when these run.
2. The bound is expressed from the same constants the success path uses, not a
   new hand-picked number.
3. `orphanStaleAfter`'s doc comment is updated to state what is now bounded, and
   the residual it currently records is removed only if it is genuinely closed.
   **Do not assert a bound the code does not have** — `#0284`'s two bounces were
   both that defect.
4. A test proves a hung failure write cannot hold `'sending'` past the bound.
   Prove it fails against the current code first.
5. Graceful shutdown still completes in-flight failure writes rather than
   abandoning them — check this against `Stop`'s existing claim-release
   behaviour, which `#0269` and `#0284` both relied on.
6. `ISSUE=NNNN scripts/check.sh go ./internal/mailing/... ./internal/outbox/... ./cmd/opencircuit/...`
   passes with no skips.

## Review notes

**Verdict: resolved.** Every claim was re-checked against the code rather than
against the work log, and criterion 4's proof was reproduced independently.

### Criterion 1 — all six sites, detached and bounded

Read the diff rather than the summary. `git show c51574d -- internal/mailing/worker.go`
converts exactly six call sites, each to its own
`context.WithTimeout(context.Background(), failureWriteTimeout)` with a paired
`cancel()`:

| Site | Function |
|---|---|
| `ClaimRow` | `sendOne`, first statement |
| `MarkFailedRow` ×3 | `sendOne` — empty-token, render-failure, `sendClassTerminalRow` |
| `MarkRetryOrFailed` | `sendOne`, retryable default branch |
| `ReleaseRow` | `drainLoop`, `sendOutcomeTerminalCampaign` |

`context.Background()` is right at each of them for the reason criterion 1
gives: these are precisely the writes that run *because* something failed, and
in production `Worker.Run` is started as `go sendWorker.Run(context.Background())`
(`cmd/opencircuit/main.go`), so the ambient `ctx` never carried a deadline of
its own to inherit anyway — detaching adds a bound where there was none and
removes no cancellation that existed. The `drainLoop` case is the strongest of
the six: its `ctx` may already be at the deadline that *produced* the terminal
campaign error, so releasing on that same context is exactly the write most
likely to be cancelled before it lands.

Grepped `internal/mailing/worker.go` for `context.WithTimeout` afterwards:
every construction in the claimed-row lifecycle is now `context.Background()`-
based. No failure-path write can outlive shutdown unboundedly — each is capped
at `failureWriteTimeout` (5s), and `Worker.Stop` waits on `doneCh`, so a
shutdown blocks for a bounded time rather than abandoning a write.

### `failureWriteTimeout` is an initialization, not an alias that can drift

`var failureWriteTimeout = writeStatusTimeout` (worker.go:131) takes its value
from the success path's own constant at package init, so the two cannot
diverge silently — raising `writeStatusTimeout` raises this too. It is a `var`
rather than a `const` for the same reason `orphanStaleAfter` is: so a test can
shrink it. The new test does exactly that (200ms, restored via `t.Cleanup`),
and shrinking it does **not** perturb the success path's `writeCtx`, which is
the stated reason for keeping it as a separate name. Confirmed intentional and
correctly motivated.

### Criterion 4 — the test is load-bearing, re-proved by this review

Not taken on trust. In a throwaway worktree at `HEAD` with its own scratch
database, `sendOne`'s `ClaimRow` was reverted to the ambient `ctx`:

```
panic: test timed out after 20s
  TestWorker_SendOne_ClaimRowTimesOutRatherThanHangingIndefinitely (20s)
  ...mailing.(*SendStore).ClaimRow(...)  worker_store.go:433
  ...mailing.(*Worker).sendOne(...)      worker.go:938
```

A real blocked `UPDATE` against a row lock held on a separate connection — not
a mock — with the goroutine dump naming `ClaimRow` itself. Restoring the file
returned the test to `ok` in 0.5s. The worktree was removed and the main tree
was never touched.

### Criterion 5 — shutdown unchanged, and the reasoning checks out

`Worker.Stop` has no claim-release machinery of its own (that is
`OutboxWorker.releaseAll`, a different type this issue does not touch); it
closes `stopCh` and waits `doneCh`. The ambient `ctx` was already
`context.Background()` in production, so it was never cancelled by `Stop` even
before this change. The work log's conclusion — that this change gives the
failure writes an explicit deadline without changing when or whether they run
— is correct.

### Criterion 3 — the doc comment does not overclaim

`orphanStaleAfter`'s rewritten comment states the fuller worst case as
`failureWriteTimeout + sendMessageTimeout + writeStatusTimeout` = 5 + 30 + 5 =
40s, against a 70s window. Re-derived independently and it holds. The "Still
not a STRICT bound" section was narrowed rather than deleted, and what it now
names — OS/network-level cancellation latency, plus `w.render.Campaign`'s
CPU-only unbounded term — is genuinely still open. That is the correct
treatment under criterion 3's "removed only if it is genuinely closed".
