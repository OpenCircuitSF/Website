## Read `CLAUDE.md` §5 before touching this
§5 records **five issues** filed against timing failures that were really ~200
concurrent agents peaking at load average 320, and a day spent widening
deadlines from 5s to 20s so a local `TRUNCATE` would stop timing out. Two closed
`wontfix`. **The instinct this issue must not indulge is widening a deadline.**

This is filed *because* several passes checked the load first and found the
excuse unavailable.

## Description

`internal/handlers` intermittently fails on a deadline-bound test whose tail
shows only `context canceled` logging — no assertion failure. Sightings this
session, each with the load recorded:

| Pass | Observation |
|---|---|
| `#0453`'s review | first run failed `TestSubscribeIntakeWorker_ClaimsRowsIndividuallyNotAsBatch` — 15s deadline plus a `context canceled` cascade; clean on re-run |
| `#0465`'s review | **two** reds at loads **3.24** and **4.89**, same cascade; explicitly recorded that §5's busy reading was *not* available and chased both to green instead |
| `#0467`'s second review | first run failed at **20.475s** against a ~5.6s norm, tail showing only `context canceled`; clean on two subsequent runs, no commit landed during it, and the commit under review changed **zero Go code** |
| `#0444`'s implementation | failed at load **21.29**, passed at 11.02 — this one *is* load-attributable, and is included to mark the boundary |

The first three are the interesting ones. A test that fails at load 3.24 is not
failing because the machine is busy.

## What makes this worth a number rather than a shrug

Every pass that hit it did the right thing — recorded the load, re-ran, refused
to widen anything — and each independently concluded it was not attributable to
their change. That is four separate agents paying the same diagnostic cost and
reaching the same dead end. **The cost is now larger than the investigation.**

There is also a specific hazard in leaving it: §5's rule is a good rule, and a
genuine flake hiding behind it trains the next reader to dismiss a real defect.

## Acceptance criteria

1. **Identify the test, or tests.** The named sighting is
   `TestSubscribeIntakeWorker_ClaimsRowsIndividuallyNotAsBatch`; confirm whether
   the other cascades are the same test or a family sharing a deadline.
2. **Find the mechanism.** A `context canceled` cascade with no assertion
   failure suggests a context cancelled by a parent — a `t.Cleanup` ordering, a
   worker outliving its test, a poller still running against a closed pool.
   `#0464`'s and `#0465`'s reviews both saw it while running *only* markdown
   changes, so it is unlikely to depend on the code under test.
3. **Do not widen the deadline.** If your conclusion is that the deadline is
   genuinely too tight for correct code, say so with the measurement that shows
   it — but §5 is explicit that this is the wrong instinct and it has cost this
   project a day before.
4. **Do not chase it with `-count=N`.** §5 bans that for flake-hunting: a test
   that fails under concurrent load is not flaky, and re-running N times
   multiplies the load that caused it. If you need repetition, say why and how
   you bounded it.
5. If it turns out to be genuinely load-dependent after all, **close it saying
   so** and record the load at which it reproduces, so the next four passes do
   not each rediscover the boundary.

## Cause — found, and it is not load

A `*SubscribeHandler` starts a background `runIntakeWorker` goroutine whenever
its intake store is non-nil (`#0254`). That poller claims `KindSubscribeIntake`
rows out of `outbound_queue` every `intakePollInterval` and keeps doing so
until `Close` stops it.

`newTestSubscribeHandler` (`internal/handlers/admin_subscribers_test.go`) built
one of those handlers but **took only a pool**, so it could not register a
`t.Cleanup` and nothing ever called `Close`. It has **32 call sites**, across
`admin_subscribers_test.go`, `admin_subscribers_erase_test.go`,
`admin_subscribers_export_test.go` and `admin_suppressions_test.go` — every one
of which sorts **before** `subscribe_intake_test.go` in the package's test
order. Each leaked one live claimer for the remainder of the test binary.

Measured, from a live goroutine dump taken inside the test itself: **33
goroutines parked in `runIntakeWorker`, with distinct handler receivers**, by
the time `subscribe_intake_test.go` ran — 32 leaked, plus the one the test
under discussion legitimately owns.

The failure follows directly.
`TestSubscribeIntakeWorker_ClaimsRowsIndividuallyNotAsBatch` seeds two
immediately-due rows and then waits for **its own** handler's poller to reach a
deliberately blocking `SuppressionChecker`. All 32 leaked pollers run
`NoSuppressions`. It is a race between 34 pollers over one 5-second tick, and
whenever a leaked one got there first it **claimed and finished both rows
without ever touching the blocking checker**. The test's own poller then found
nothing due for the rest of its window, `checker.started` never closed, and the
15s wait expired.

Confirmed from the reproduced failures, not inferred — both rows read back
`status="sent" attempts=1` with a `claimed_at` **4ms and 19ms after the test
started**, and `queued-and-due subscribe_intake rows table-wide: 0`, while the
census showed zero goroutines inside `blockingSuppressionChecker.IsSuppressed`.
`attempts=1` is what rules out the fast path: `MarkDone` (the fast path's exit)
sets `claimed_at = NULL` and never increments `attempts`, so only a recovery
poller's `ClaimRow` + `MarkSent` produces that state.

**Nothing about this is load-dependent.** It is a scheduling race whose outcome
turns on which poller's 5-second tick lands in the window. Load shifts the
phase; it neither causes nor prevents the failure. Reproduced here at loads
**3.44**, **5.24** and **7.75**, matching the **3.24** and **4.89** `#0465`
recorded. `CLAUDE.md` §5's "the machine is busy" reading was correctly found
unavailable by every pass that hit it.

### Why four passes could not see it

Both of `intakePass`'s decline paths are **silent**: `SelectDue` returning no
ids (`if len(ids) == 0`), and `ClaimRow` reporting `claimed=false` (`if
!claimed { continue }`). Neither logs. In the captured failing transcript there
is **not one log line between the test's start and its `t.Fatal` 15 seconds
later** — the poller declined quietly, three ticks running.

The `context canceled` wall everyone saw is **unrelated teardown noise from
later tests**, exactly as `#0464`'s review independently found. It sits after
the `--- FAIL` line in the stream, and `scripts/check.sh` bounds output with
`tail -40`, so on the reviewers' two-package runs the failing test's name was
pushed out of the window. In the single-package failure captured here the name
survived with only 8 lines of margin — which is why `#0453` saw the name and
`#0465` did not.

## Fix

`newTestSubscribeHandler` now takes a `*testing.T` and registers `Close` as a
cleanup, so a poller's lifetime ends with the test that built it. All 32 call
sites updated.

Two things were added so this cannot cost anyone the same day again:

- `TestNoLeakedIntakePollers` — first test in `subscribe_intake_test.go`,
  asserting from the **live goroutine dump** that no handler built by an
  earlier test is still polling. The oracle is the runtime, not a counter this
  package maintains, so a bookkeeping mistake cannot satisfy it.
- `intakeQueueDiagnostic` — the 15s failure now reports each row's
  status/attempts/claimed_at/due_in, the table-wide queued-and-due count, and
  the poller census, instead of reporting nothing.

**No deadline was widened** (criterion 3) and **no `-count=N` was used**
(criterion 4). Every reproduction attempt was a sequence of separate,
non-overlapping `go test` processes, so machine load was never multiplied;
each iteration recorded `uptime` first.

### The bounce — `TestNoLeakedIntakePollers` can be silently disarmed by a rename

`const frame = "handlers.(*SubscribeHandler).runIntakeWorker"` is a hand-written
string with no compile-time tie to the method it watches, and the guard's
**pass** condition is that the string matched nothing. A name that stops
matching is therefore indistinguishable from a clean run. That is the exact
shape `CLAUDE.md` §8 forbids — "assert the extraction produced something before
hashing it: an empty result must be an error, never an input" — and §8's own
test, *does an edit to the subject also satisfy the oracle?*, answers yes here:
renaming the poller is an edit to the subject, and it satisfies the oracle.

Measured, not argued. In the worktree, with the `t.Cleanup` still mutated out so
**32 pollers were provably alive** (my census, run in the same binary, reported
`frames=32 distinct_receivers=32`), I renamed `runIntakeWorker` →
`runIntakePoller` in `subscribe.go` and `subscribe_intake.go` only:

    --- PASS: TestNoLeakedIntakePollers (0.00s)
    ok  github.com/brennanMKE/OpenCircuitSF/internal/handlers  6.521s

The whole package went green with 32 leaked claimers running. The pin was gone
and nothing said so. Ending `#0470` — an issue whose entire finding is that a
*silent decline path* cost four review passes — with a guard whose own failure
mode is a silent decline is the wrong ending, and it is a five-line fix.

`intakeQueueDiagnostic`'s other two frame literals
(`…processIntakeRow`, `…(*blockingSuppressionChecker).IsSuppressed`) have the
same defect. They are diagnostics rather than assertions, so they fail softer —
they would silently report `0` — but the fix is the same line and they should
take it.

### Remedy 1 — anchor the frame strings to the identifiers (verbatim; proved working)

In `internal/handlers/subscribe_intake_test.go`:

1. Add `"reflect"` to the import block.
2. Add this helper immediately above `countGoroutinesIn`:

		// frameName returns the exact fully-qualified stack-frame name of fn,
		// as the runtime prints it in a goroutine dump. Deriving it from the
		// function value instead of writing the string by hand is what keeps
		// goroutinesIn's callers honest: goroutinesIn reports zero both when
		// nothing is in the frame and when the name it was handed matches
		// nothing at all, and TestNoLeakedIntakePollers PASSES on zero — so a
		// hand-written literal that goes stale disarms the guard silently,
		// which is CLAUDE.md §8's "an empty result must be an error, never an
		// input". Measured during #0470's review: with 32 leaked pollers
		// provably alive, renaming runIntakeWorker made the guard pass in
		// 0.00s and the package go green. Written this way the same rename is
		// a compile error instead.
		func frameName(fn any) string {
			return runtime.FuncForPC(reflect.ValueOf(fn).Pointer()).Name()
		}

3. Replace all three literals with it:

	- `goroutinesIn("handlers.(*SubscribeHandler).runIntakeWorker")`
	  → `goroutinesIn(frameName((*SubscribeHandler).runIntakeWorker))`
	- `countGoroutinesIn("handlers.(*SubscribeHandler).processIntakeRow")`
	  → `countGoroutinesIn(frameName((*SubscribeHandler).processIntakeRow))`
	- `countGoroutinesIn("handlers.(*blockingSuppressionChecker).IsSuppressed")`
	  → `countGoroutinesIn(frameName((*blockingSuppressionChecker).IsSuppressed))`

4. In `TestNoLeakedIntakePollers`, replace
   `const frame = "handlers.(*SubscribeHandler).runIntakeWorker"` with
   `frame := frameName((*SubscribeHandler).runIntakeWorker)`.

5. `goroutinesIn`'s doc comment says frame "must be an exact stack-frame prefix
   (a "pkg.(*T).Method" string)". Update it to say the caller passes
   `frameName(...)` and why — the substring match is unchanged, since
   `frameName` returns the module-qualified name the dump prints verbatim.

Proved working, in the worktree, in the adversarial configuration: with the
method renamed **and** the leak present, the identifier-anchored guard reported
`32 intake poller goroutine(s) from earlier tests are still running` and failed
at 1.01s. `gofmt -l` clean. Do not add a positive control that constructs a
handler inside `TestNoLeakedIntakePollers` — it runs before the other intake
tests and its poller would claim their rows.

### Remedy 2 — §5 gains the converse it was missing (verbatim)

**Yes, §5 needs amending, and this is the issue's real product.** §5 as written
covers only one direction: load above ~8 means the machine, not a defect. It
says nothing about a timing failure at *normal* load, and four passes read that
silence as "not attributable to my change" and stopped — which is exactly what
the issue was filed to end. The rule was not wrong; it was half a rule, and the
missing half is where the defect was.

Insert this paragraph in `CLAUDE.md` §5 immediately after the paragraph ending
"`#0096` and `#0099` as `wontfix`.", before "**There is no performance
requirement in this project and no load test.**". Add no heading and renumber
nothing (`internal/handlers`'s citation guard reads §-numbers):

	**And the converse, which took four passes to learn (`#0470`).** The rule
	above says what a timing failure at *high* load means. It says nothing about
	one at *normal* load, and four separate passes read that silence as "not my
	change" and moved on. Read it the other way too: **a deadline-bound test
	that fails while the load average is normal is evidence of a defect, and the
	`uptime` reading is what tells you so** — it removes the only ambient
	explanation, which is the opposite of licensing a shrug. Look first for a
	**silent decline path**: a worker that `continue`s without logging, a
	`len(x) == 0` early return, a background goroutine outliving the test that
	started it. That is what makes this class of failure present as a bare
	expired deadline with no error in it. `#0470` was all three at once — a test
	helper that never `Close`d the handler it built leaked 32 background pollers
	into the rest of the package's binary, and one of them claimed the rows the
	failing test was waiting on. Nothing about it was load-dependent. Widening
	the deadline is still the wrong instinct; making the decline say something
	is the right one.

    vet: (*SubscribeHandler).runIntakeWorker undefined
         (type *SubscribeHandler has no field or method runIntakeWorker)

That is the difference the bounce turned on. A hand-written string survives that
edit and silently stops matching; a method expression cannot. §8's own test —
*can an edit to the subject also satisfy the oracle?* — now answers no for the
rename case, and the oracle is a live runtime dump rather than a copy of the
answer stored beside the question.

`frameName` returns exactly the string a dump prints, verified by printing all
three values: they are module-qualified
(`github.com/brennanMKE/OpenCircuitSF/internal/handlers.(*SubscribeHandler).runIntakeWorker`
and its two siblings), with no `-fm` suffix or wrapper name. Each is a strict
superset of the literal it replaced, so the substring match is unchanged and
slightly **more** specific than before.

### Vacuity — the guard cannot pass on an empty or truncated dump

`goroutinesIn` reads into a 4 MB buffer, and `runtime.Stack` truncates silently
at the buffer bound, so an undersized buffer would undercount toward a false
pass. Measured at the adversarial peak, after every leaking test had run: the
dump is **131,298 bytes across 589 goroutines**, not truncated, and a 64 MB
buffer returns the byte-identical length and the same count of 32. Thirty-two
times the headroom at the largest configuration this package can produce. The
empty case is unreachable — `runtime.Stack` always emits at least the calling
goroutine — and the stale-name case is now a compile error.

One residual, recorded rather than fixed: a refactor that moved the polling loop
to a different entry point while leaving the method defined but unreferenced
would count zero and pass, since Go does not flag an unused method. It is a much
more deliberate act than a rename, and the obvious counter — a positive control
building a handler inside the pin — is ruled out for a good reason: the pin runs
first, and its own handler would claim the rows the later intake tests seed.
