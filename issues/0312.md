# 0312 — A failed invitation cannot be re-sent by an admin

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | subscribers / admin |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-08-27 |

## Description

`#0129`'s `AdminResendConfirmation` correctly **refuses** an invited row — the
generic confirmation template drops the provenance sentence PRD §6.10.1 requires
an invitation to carry, so resending it would silently downgrade an invitation
into an ordinary confirmation.

**But nothing replaces it.** An invitation that fails to arrive — a transient
bounce, a typo the admin fixes, a message abandoned in the queue — cannot be
re-sent at all. The admin's only options are to re-import the address or leave
the person unable to accept.

The implementer disclosed this rather than papering over it, and `#0129`'s
reviewer confirmed the refusal itself is right.

## Acceptance criteria

1. An admin can re-send an invitation to a still-pending, unaccepted invited
   row, using `BuildImportInviteEmail` with its provenance sentence intact —
   never the generic confirmation template.
2. `AdminResendConfirmation`'s refusal stays. The two paths must be distinct, and
   the refusal message should point at the invite-resend action rather than
   simply saying no.
3. Re-sending mints or reuses a token consistently with how the public resend
   path handles it, and does not extend consent — the address is still
   unaccepted until it confirms.
4. The cooldown and abuse protections that govern the public resend path apply
   here too, or the reason they do not is recorded. An admin-triggered send is
   still a send.
5. `invite_sent` accounting stays correct: re-sending must not inflate
   `invited_count`, which counts addresses invited, not messages sent. State
   what you decided and test it.
6. The `physical_address` gate (`#0129`, CAN-SPAM §7704) applies to a re-send
   exactly as to the first send, and must not be bypassable from the UI (§9).
7. `ISSUE=NNNN scripts/check.sh` passes with no skips.

### The shared decision (`#0312` + `#0313` + `#0314`, 2026-08-28)

**Who initiated the send decides which template goes out — not how the row was
created.**

- An **invitation** is a message *we* start, to an address we obtained somewhere
  else. It must carry PRD §6.10.1's provenance sentence, because the recipient
  never asked for it and that sentence is the only thing separating it from spam.
- A **confirmation** is a message we send *in reply* to a request the person made
  themselves. Its provenance is the request. §6.10.1's sentence would read as a
  non-sequitur to someone who just typed their own address into our form.

Applied to the four events these three issues are about:

| Event | Who initiated | What happens |
|---|---|---|
| An invitation fails to send, or is abandoned in the queue | nobody | Row stays `pending`, unaccepted. Recoverable only by the admin action below (`#0312`) |
| An invitation expires unaccepted | nobody | `ExpirePendingSweep` keeps today's behaviour exactly: token nulled, row left `pending`, never re-mailed by the import mechanism |
| An **expired-pending** address submits the public form | **the person** | Mint a fresh token inside the same atomic claim; send the **generic confirmation** (`#0314`) |
| A **pending invited** address submits the public form | **the person** | The row stops being an invitation: `import_id` cleared, consent evidence refreshed, any still-queued invitation cancelled, fresh token if the old one lapsed; send the **generic confirmation** (`#0313`) |
| An admin wants to re-send | **the admin** | A separate action sending `outbox.KindImportInvite` with its provenance intact — at most once per address, ever (`#0312`) |

**States and transitions.** No new `status` value, and no change to the row-state
test the whole codebase already shares — *an unaccepted invitation is
`status='pending' AND import_id IS NOT NULL AND consent_basis IS NULL`*
(`Confirm`, `Unsubscribe`, `AdminResendConfirmation`, `ExpirePendingSweep` all
derive it that way). Two transitions are **added**:

1. **Invitation → self-initiated signup** (`#0313`, public path). Clears
   `import_id`. Leaves `source = 'import'`, `invited_at`, `consent_basis` (still
   NULL) and every `subscriber_events` row untouched.
2. **Invitation → invitation, re-sent once** (`#0312`, admin path). Stamps a new
   write-once `invite_resent_at`. Does **not** re-stamp `invited_at`, does not
   touch `consent_basis`, does not change `status`.

**Transition 1 is a defect fix, not merely a recorded preference.**
`Store.Unsubscribe` reads that same row-state test and treats an unsubscribe from
a pending invited row as an **invitation decline**, which writes a `suppressions`
row ("declined an import invitation before confirming"). So today: an invited
person visits the site, signs up under their own steam, receives the generic
confirmation, changes their mind, clicks that mail's `List-Unsubscribe` — and is
**permanently suppressed** for an ordinary change of mind about a signup they made
themselves, with no self-service recovery. That is precisely the misfire `#0129`'s
blocker 2 closed for `RestartSignup` (invite → revoke → website signup); it is
still wide open on the `pending` branch, which `RestartSignup` never reaches.
Clearing `import_id` at the moment the person takes the signup over closes it at
the same source, by the same reasoning `ImportStore.Revoke`'s own doc comment
already uses: *its consent no longer derives from the import.*

**What transition 1 costs, accepted deliberately.** The person stops counting
toward `subscriber_imports.confirmed_count`, and their acceptance writes
`signup_requested` + `confirmed` rather than `invite_accepted`. That is the honest
number. They also now receive `#0127`'s welcome email, which an accepted
invitation is denied ("the invitation was the introduction") — correct, because
the invitation is no longer their introduction; the form they filled in is.
Provenance is not lost: `source = 'import'`, `invited_at`, and the `imported` /
`invite_sent` `subscriber_events` rows (which carry `import_id`) all survive, and
they are where "why did we ever mail this address" is answered from.

**The one deviation from the PRD, stated plainly.** §6.10.1 says "One invitation
per address, ever. No reminder, no re-invite on a later import." `#0312` requires
a re-send, so this deviates, and the bound is explicit:

- **Automated imports stay capped at one, unconditionally.** `invited_at` still
  governs them and is never re-stamped by anything, so re-uploading the same CSV
  can never re-invite — the property `#0129`'s notes call "the anti-abuse
  property" is untouched.
- **The exception is at most one further invitation, per address, ever**, by an
  explicit, authenticated, audited admin action on that one row, recorded in a
  new write-once `subscribers.invite_resent_at`.

What §6.10.1 exists to prevent survives intact: no bulk re-invite, and no
repeatable reminder loop against an unwilling recipient. Two is a constant, not a
loop. The alternative bound considered and rejected was gating the re-send on the
first invitation's `outbound_queue` status (`abandoned` only): it self-defeats
(`LatestByRecipients` returns the *latest* row of a kind, which after one re-send
is the re-send), it depends on queue retention, and it refuses the bounce case
`#0312` names. The queue state is still *shown* on `#0128`'s screen so the admin
can see whether the first one was abandoned before spending the one re-send.

**Order of implementation: `#0336` → `#0314` → `#0313` → `#0312`.** See each
issue's own `## Plan` for why.

### What this issue implements

**Land last, after `#0336`, `#0314`, `#0313`.** Not because of a code
dependency — `AdminResendInvitation` touches none of `#0313`'s or `#0314`'s
lines — but because criterion 2 requires the refusal message to point at this
action, and because the *window* in which the action is available is only
well-defined once `#0313` has decided what a public submit does to an invited
row. Shipping this first would put a refusal message in front of behaviour whose
meaning had not been settled.

### Step 1 — `migrations/000026_add_subscriber_invite_resent_at`

Migrations are append-only and `000001`–`000022` are frozen (CLAUDE.md §1); the
tree is at `000025`, so this is `000026`. **This issue's own acceptance criteria
carry no greenfield language** (filed 2026-08-27, after the exception expired on
2026-08-25) — checked, nothing to correct here; `#0293` covers the remaining
stale copies in `PRD.md` §6.2 and `docs/deployment.md`.

```sql
-- up
ALTER TABLE subscribers ADD COLUMN invite_resent_at TIMESTAMPTZ;
ALTER TABLE subscribers ADD CONSTRAINT subscribers_invite_resent_requires_invite
  CHECK (invite_resent_at IS NULL OR invited_at IS NOT NULL);
-- down
ALTER TABLE subscribers DROP CONSTRAINT subscribers_invite_resent_requires_invite;
ALTER TABLE subscribers DROP COLUMN invite_resent_at;
```

No backfill is owed — the column is NULL for every existing row and that is the
correct starting value. Add the column to `subscriberColumns`, `scanSubscriber`
and `Subscriber` (`internal/subscribers/store.go`), and a row to
`docs/database.md`'s table plus its `000001`–`000025` range line (CLAUDE.md
records that this table has gone stale three times; do not make it four).
Then `scripts/testdb.sh template` — see `## Obstacles`.

### Step 2 — `AdminResendInvitation` (`internal/subscribers/pending.go`)

`AdminResendConfirmation`'s twin, deliberately a separate method rather than a
mode flag, so the two templates can never be selected by a boolean an admin UI
could get wrong. Same transaction shape, same `SELECT … FOR UPDATE` (which is
load-bearing for the same reason — the cooldown check is an ordinary Go `if`).

Guards, in order:

| # | Condition | Error |
|---|---|---|
| 1 | row exists, `synthetic = false` | `ErrPendingSubscriberNotFound` |
| 2 | `status = 'pending'` | `ErrNotPending` |
| 3 | **is** an unaccepted invitation (`import_id IS NOT NULL AND consent_basis IS NULL`) | `ErrResendNotAnInvitation` (new — the exact mirror of `ErrResendNotForInvited`) |
| 4 | the owning `subscriber_imports` row is not `revoked` | `ErrInviteImportRevoked` (new) |
| 5 | `invite_resent_at IS NULL` | `ErrInviteAlreadyResent` (new) |
| 6 | not in `suppressions` | `ErrResendSuppressed` (reused) |
| 7 | `confirm_sent_at` NULL or older than `now - cooldown` | `ErrResendCooldownActive` (reused) |

Guard 4 is not redundant with guard 2 — `ImportStore.Revoke` moves still-pending
invited rows to `unsubscribed`, so guard 2 usually catches it, but the import row
must be read anyway (step 3) and re-inviting on behalf of a batch the admin has
already disowned is exactly backwards.

Effects, one transaction:

- Mint a fresh `confirm_token` and set `confirm_expires_at = now + importInviteConfirmTTL`
  (**not** `subscribeConfirmTTL` — the invitation has its own 7-day constant in
  `imports.go`, and a re-send is still an invitation). Unconditional minting,
  matching `AdminResendConfirmation`: an admin re-send is also a token rotation.
- Stamp `confirm_sent_at = now`, `invite_resent_at = now`, `updated_at = now`.
- **Do not re-stamp `invited_at`.** This is the whole anti-abuse property
  (criterion 5, and `#0129`'s "one invitation per address, ever"): `invited_at`
  is what every subsequent import checks, so leaving it write-once means a
  re-uploaded CSV still cannot re-invite.
- Enqueue `outbox.KindImportInvite` — never `KindConfirmation` — with an
  `importInvitePayload` rebuilt from the joined `subscriber_imports` row
  (`Source`, `SourceDetail`, `CollectedAt`), the new token, the row's
  `manage_token`, and `importInviteConfirmTTL`. That is criterion 1: the
  provenance sentence comes from the same three fields `ImportStore.Commit` used,
  so the re-send says the same thing the first one said.
- Return the existing `ResendResult`.

Criterion 3, consent: `status` stays `pending`, `consent_basis` stays NULL, and
nothing writes `confirmed_at`. The address is still unaccepted, and a re-send
cannot make it otherwise. Criterion 5, `invited_count`: it lives on
`subscriber_imports`, is stamped once by `ImportStore.Commit` from that commit's
own enqueue count, and is not touched here — addresses invited, not messages sent.
Assert it, do not assume it.

Criterion 4, cooldown and abuse protections: the same `subscribeResendCooldown`
`AdminPendingHandler` already passes to `AdminResendConfirmation` applies
unchanged, plus authentication, plus an `audit_log` row, plus the once-ever
`invite_resent_at` bound the public path has no equivalent of — the admin path is
strictly *more* constrained here, not less, because the recipient never asked for
either message.

### Step 3 — refuse better (`internal/subscribers/pending.go`, `internal/handlers/admin_pending.go`)

### Step 5 — the `physical_address` gate (criterion 6, §9)

**The gate is already in the right place and must stay there.**
`OutboxWorker.render`'s `KindImportInvite` arm returns
`errImportInviteMissingPhysicalAddress` and routes to
`deferMissingPhysicalAddress`, which requeues rather than sends. Because the
re-send enqueues rather than sends, the gate applies to it automatically and is
not reachable from the UI at all — there is no handler-side flag that can skip it.

One usability wrinkle to handle **without** weakening that: if
`physical_address` is unset, the re-send burns the one-and-only
`invite_resent_at` on a message that will defer indefinitely. So
`ResendInvitation` reads `settings.physical_address` and returns a `409` naming
the missing setting *before* calling the store. This is an **advisory pre-check,
not the gate** — say so in a comment at both sites, and prove it with a test that
removes the pre-check and shows the worker still refuses and still sends nothing.
A reviewer must be able to see at a glance that §9's "must not be bypassable from
the UI" is satisfied by the worker, not by this.

### Step 6 — SPA (`web/src/lib/*`, `web/src/views/admin/Pending.svelte`)

`Pending.svelte` already renders an `Invited` badge and hard-disables its
`Resend` button for `row.invited`. Replace the disabled button with a distinct
**"Resend invitation"** action for invited rows:

- `pendingSubscriberRow` (`internal/handlers/admin_pending.go`) gains
  `invite_resend_available bool` (`invited && invite_resent_at == nil`) and
  `invite_resent_at`; `web/src/lib/types.ts` and `web/src/lib/api.ts` gain the
  field and a `resendInvitation(id)` call.
- The button's confirm copy states the bound plainly — this is the one and only
  re-send for this address — and once `invite_resent_at` is set the button is
  disabled with that as the reason, rather than the current "not available yet".
- The existing `queue_state` column is what tells the admin whether the first
  invitation was `abandoned`; keep it adjacent to the new button.
- `web/src/views/admin/Pending.behavior.test.ts` covers both states.

### Interaction with `#0336`

None directly — this issue creates no new row state that `Growth30Days` reads. A
re-sent invitation is still `pending` with `consent_basis` NULL, which both the
current `imported_30d` predicate and `#0336`'s proposed one exclude, and which the
`unsubscribed_30d` guard's negation excludes symmetrically. `#0336` should still
land first, for `#0313`'s sake (see that issue's plan); this issue does not care
which predicate is in place, and should assert that with a `Growth30Days`
before/after delta of zero across the re-send.

### Test strategy — the mutations that must fail

- `TestAdminResendInvitation_SendsInvitationWithProvenance`: seed an `invite`
  import with a distinctive `source_detail` and `collected_at`, drain, re-send,
  drain again, and assert the **rendered body** contains the provenance sentence
  built from *those seeded values*. The oracle is data the test wrote into the
  import row, not a copy of the template.
  - **Mutation M1:** enqueue `KindConfirmation` instead. Must fail.
- `TestAdminResendInvitation_RefusesSecondResend`: re-send, then re-send again.
  - **Mutation M2:** drop guard 5. Must fail.
- `TestAdminResendInvitation_DoesNotReinviteOnLaterImport`: re-send, then commit
  a **second** import containing the same address; assert it is skipped and that
  import's `invited_count` is 0, and that the first import's `invited_count` is
  unchanged. Covers criterion 5 and the `invited_at` write-once property together.
  - **Mutation M3:** re-stamp `invited_at` in the re-send `UPDATE`. Must fail.
- `TestAdminResendInvitation_PhysicalAddressGateNotBypassable`: with the handler
  pre-check removed (build-tag-free: call the store method directly), enqueue and
  drain against a blank `physical_address`; assert nothing sends and the row
  stays `queued`. The pre-existing
  `TestOutboxWorker_DefersImportInvite_MissingPhysicalAddress` (`#0129`) is the
  second, independent oracle.
  - **Mutation M4:** delete `render`'s `KindImportInvite` blank-address refusal.
    Both tests must fail.
- `TestAdminResendConfirmation_StillRefusesInvited`: criterion 2's other half —
  the generic-confirmation refusal survives, and its message names the invitation
  route.
  - **Mutation M5:** delete the `ErrResendNotForInvited` guard. Must fail — and
    assert it by draining the outbox and checking the **rendered template**, so
    the test fails for the right reason (the wrong message went out) rather than
    merely on a returned error value.
- `TestAdminResendInvitation_DoesNotExtendConsent`: `status`, `consent_basis`,
  `confirmed_at` unchanged; and `Growth30Days` delta zero across the re-send.
