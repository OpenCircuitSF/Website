# 0312 — A failed invitation cannot be re-sent by an admin

| | |
|---|---|

| **Phase** | 8 — Archive, imports, and delivery health |

## Description

`#0129`'s `AdminResendConfirmation` correctly **refuses** an invited row — the
generic confirmation template drops the provenance sentence PRD §6.10.1 requires
an invitation to carry, so resending it would silently downgrade an invitation
into an ordinary confirmation.

**But nothing replaces it.** An invitation that fails to arrive — a transient
bounce, a typo the admin fixes, a message abandoned in the queue — cannot be
re-sent at all. The admin's only options are to re-import the address or leave
the person unable to accept.

The implementer disclosed this rather than papering over it, and `#0129`'s
reviewer confirmed the refusal itself is right.

## Acceptance criteria

1. An admin can re-send an invitation to a still-pending, unaccepted invited
   row, using `BuildImportInviteEmail` with its provenance sentence intact —
   never the generic confirmation template.
2. `AdminResendConfirmation`'s refusal stays. The two paths must be distinct, and
   the refusal message should point at the invite-resend action rather than
   simply saying no.
3. Re-sending mints or reuses a token consistently with how the public resend
   path handles it, and does not extend consent — the address is still
   unaccepted until it confirms.
4. The cooldown and abuse protections that govern the public resend path apply
   here too, or the reason they do not is recorded. An admin-triggered send is
   still a send.
5. `invite_sent` accounting stays correct: re-sending must not inflate
   `invited_count`, which counts addresses invited, not messages sent. State
   what you decided and test it.
6. The `physical_address` gate (`#0129`, CAN-SPAM §7704) applies to a re-send
   exactly as to the first send, and must not be bypassable from the UI (§9).
7. `ISSUE=NNNN scripts/check.sh` passes with no skips.
