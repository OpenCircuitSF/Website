## Description

`Worker.sendOne` deliberately runs the SES call and the subsequent `sent`
write on contexts detached from the ambient one
(`context.WithTimeout(context.Background(), …)`). Changing both to derive from
`ctx` leaves `internal/mailing` and `cmd/opencircuit` fully green. This is the
file's most consequential invariant — it is what stops a shutdown mid-drain
from accepting a message at SES and then losing the `sent` write, which makes
the next resume send that recipient a **guaranteed duplicate** — and nothing
pins it.

The property holds in the shipped code, and the primary defence
(`Run(context.Background())` plus signal-based `Stop`) is covered by
`TestSendWorker_StopReturnsWithinBudgetOnSIGTERM`, so this is defence-in-depth
rather than a live hole. `#0045`'s second pass left it out, reasoning that
isolating it "would need a test seam `sendOne` doesn't currently expose". Half
of that reasoning is right and half is not — see below.

## Notes

Raised by `#0045`'s second-pass review (2026-08-21, phase 3, Opus), which
built and mutation-proved the test below before filing this. `#0045` was
approved regardless: the item was explicitly optional and the invariant holds
in the shipped code.

**What `#0045`'s second pass got right:** a naive test that hands `sendOne` an
already-cancelled `ctx` proves nothing. `ClaimRow(ctx, …)` is the *first*
statement in `sendOne` and legitimately respects the ambient context, so the
call fails there and returns `sendOutcomeSkipped` long before reaching the SES
call. That objection is correct.

**What it got wrong:** the seam already exists. `sendPreCrashHook` is a
package-level `func(sendID int64) bool` invoked *after* `ClaimRow` succeeds and
*before* the SES call, and a hook that returns `false` lets `sendOne` continue
normally. A hook that cancels the ambient context and returns `false` therefore
puts execution exactly where it needs to be: past the claim, with a cancelled
`ctx`, about to make the detached calls.

**Proven recipe** (run against a private scratch database at `000018`; passed
on the shipped code and failed on the mutation):

```go
type ctxAwareMailer struct{ sent int }

func (m *ctxAwareMailer) Send(ctx context.Context, _ Message) (string, error) {
	if err := ctx.Err(); err != nil {
		return "", err
	}
	m.sent++
	return "ctx-ok-1", nil
}
```

`RecordingMailer` ignores its context (`_ context.Context`), so it cannot
observe the SES half — a context-checking mailer is required for that
assertion. The `MarkSent` half is observable through the row status alone.

Then: seed a `sending` campaign with one queued send, `ClaimResume` and
`ClaimBatch` on a live context, install
`sendPreCrashHook = func(int64) bool { cancel(); return false }`, and call
`w.sendOne(ctx, c, recips[0], …)` with the now-cancelled `ctx`. Assert three
things — outcome is `sendOutcomeSent`, `mailer.sent == 1`, and
`sendRowStatus(...) == "sent"`.

**The mutation that must turn it red:** change both
`context.WithTimeout(context.Background(), …)` calls in `sendOne` to
`context.WithTimeout(ctx, …)`. Observed failing on all three assertions:

```
outcome = 0, want sendOutcomeSent
mailer.sent = 0, want 1 (SES call must run on a detached ctx)
send row status = "sending", want sent (MarkSent must run on a detached ctx)
```

Note `MarkSent`'s error is only logged, not returned, so asserting on
`sendOne`'s return value alone is not sufficient for the write half — the row
status is what pins it.

## Acceptance criteria

- [ ] A test in `internal/mailing` pins that `sendOne` completes the SES call
      and the `sent` write when the ambient context is already cancelled.
- [ ] It uses a context-checking mailer, not `RecordingMailer`, so the SES half
      is genuinely observed.
- [ ] It asserts the persisted row status, not only `sendOne`'s return value.
- [ ] Deriving either detached context from `ctx` turns it red; both mutations
      are stated in the test's doc comment.
- [ ] `sendPreCrashHook` is restored via `t.Cleanup`, matching the existing
      hook tests.
