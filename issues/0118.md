`Worker.sendOne` deliberately runs the SES call and the subsequent `sent`
write on contexts detached from the ambient one
(`context.WithTimeout(context.Background(), …)`). Changing both to derive from
`ctx` leaves `internal/mailing` and `cmd/opencircuit` fully green. This is the
file's most consequential invariant — it is what stops a shutdown mid-drain
from accepting a message at SES and then losing the `sent` write, which makes
the next resume send that recipient a **guaranteed duplicate** — and nothing
pins it.

The property holds in the shipped code, and the primary defence
(`Run(context.Background())` plus signal-based `Stop`) is covered by
`TestSendWorker_StopReturnsWithinBudgetOnSIGTERM`, so this is defence-in-depth
rather than a live hole. `#0045`'s second pass left it out, reasoning that
isolating it "would need a test seam `sendOne` doesn't currently expose". Half
of that reasoning is right and half is not — see below.

## Fix

Added one test, `TestWorker_SendOne_SESCallAndStatusWriteSurviveAmbientCancellation`
in `internal/mailing/worker_test.go`, using exactly the recipe proved in this
issue's `## Notes`:

- A new `ctxAwareMailer` (package-private test type) implements `Mailer` and
  checks `ctx.Err()` before recording a send — `RecordingMailer` ignores its
  context argument entirely and cannot observe this half of the invariant.
- Seeds a `sending` campaign with one queued send via the existing
  `seedScheduledCampaign`/`forceSending`/`seedQueuedSend` helpers, then calls
  the real `ClaimResume`/`ClaimBatch` to get an authentic `*claimedCampaign`
  and `Recipient` — the same objects `drainLoop` would hand `sendOne`.
- Installs `sendPreCrashHook = func(int64) bool { cancel(); return false }`.
  That hook already runs after `ClaimRow` has claimed the row and
  immediately before the SES call, so this cancels the ambient `ctx` from
  *inside* `sendOne`, at the exact instruction boundary needed — not before
  calling `sendOne`, which would fail at `ClaimRow` and prove nothing (the
  issue's own "what #0045's second pass got right").
- Calls `w.sendOne(ambientCtx, c, recipients[0], physicalAddress, fromHeader)`
  directly and asserts three observable properties: `outcome ==
  sendOutcomeSent`, `mailer.count() == 1` (the SES call actually happened
  despite the cancelled ambient ctx), and `sendRowStatus(...) == "sent"` (the
  `MarkSent` write also completed — its error is only logged, not returned,
  so the row status is the only thing that pins that half).
- `sendPreCrashHook` is restored via `t.Cleanup`, matching every other hook
  test in the file.
- A sanity assertion (`ambientCtx.Err() == nil` → `t.Fatal`) guards against a
  test-setup bug making the whole exercise vacuous by never actually
  cancelling before the calls it's supposed to be racing.

No production code changed — this issue is coverage-only, as scoped. I
considered asserting on code shape (e.g. reading `sendOne`'s source for
`context.Background()`) and rejected it: the acceptance criteria and the
issue's own reasoning are explicit that the assertion must be on the
context's observable behaviour, not on how the code happens to be written.

**Rejected alternative:** wrapping `ctx` in a custom `context.Context` that
panics on `Deadline()`/`Done()` access, to catch a call site that reads the
cancelled context's state without actually failing on it. Rejected as
needless indirection — `ctxAwareMailer.Send` checking `ctx.Err()` already
gives a mailer-side failure that's indistinguishable from what a real
context-aware AWS SDK call does when handed a cancelled context, and it
keeps the test's story to one moving part instead of two.

## Notes

Raised by `#0045`'s second-pass review (2026-08-21, phase 3, Opus), which
built and mutation-proved the test below before filing this. `#0045` was
approved regardless: the item was explicitly optional and the invariant holds
in the shipped code.

**What `#0045`'s second pass got right:** a naive test that hands `sendOne` an
already-cancelled `ctx` proves nothing. `ClaimRow(ctx, …)` is the *first*
statement in `sendOne` and legitimately respects the ambient context, so the
call fails there and returns `sendOutcomeSkipped` long before reaching the SES
call. That objection is correct.

**What it got wrong:** the seam already exists. `sendPreCrashHook` is a
package-level `func(sendID int64) bool` invoked *after* `ClaimRow` succeeds and
*before* the SES call, and a hook that returns `false` lets `sendOne` continue
normally. A hook that cancels the ambient context and returns `false` therefore
puts execution exactly where it needs to be: past the claim, with a cancelled
`ctx`, about to make the detached calls.

**Proven recipe** (run against a private scratch database at `000018`; passed
on the shipped code and failed on the mutation):

```go
type ctxAwareMailer struct{ sent int }

func (m *ctxAwareMailer) Send(ctx context.Context, _ Message) (string, error) {
	if err := ctx.Err(); err != nil {
		return "", err
	}
	m.sent++
	return "ctx-ok-1", nil
}
```

`RecordingMailer` ignores its context (`_ context.Context`), so it cannot
observe the SES half — a context-checking mailer is required for that
assertion. The `MarkSent` half is observable through the row status alone.

Then: seed a `sending` campaign with one queued send, `ClaimResume` and
`ClaimBatch` on a live context, install
`sendPreCrashHook = func(int64) bool { cancel(); return false }`, and call
`w.sendOne(ctx, c, recips[0], …)` with the now-cancelled `ctx`. Assert three
things — outcome is `sendOutcomeSent`, `mailer.sent == 1`, and
`sendRowStatus(...) == "sent"`.

**The mutation that must turn it red:** change both
`context.WithTimeout(context.Background(), …)` calls in `sendOne` to
`context.WithTimeout(ctx, …)`. Observed failing on all three assertions:

```
outcome = 0, want sendOutcomeSent
mailer.sent = 0, want 1 (SES call must run on a detached ctx)
send row status = "sending", want sent (MarkSent must run on a detached ctx)
```

Note `MarkSent`'s error is only logged, not returned, so asserting on
`sendOne`'s return value alone is not sufficient for the write half — the row
status is what pins it.

**Not over-constrained.** C2 and C3 are the counterweight: a context that
inherits `ctx`'s *values* while being uncancellable, and a structural hoist of

behaviour, not code shape — future work on `#0045`'s worker is not pinned to

rejection of a source-reading assertion was the right call.

**Call shape is authentic.** `drainLoop` (`worker.go:492`) reads
`physical_address` and `resolveFromHeader` from `ctx`, calls
`ClaimBatch(ctx, c.ID, w.batchSize)`, and dispatches

`claimAndDrain`'s entry (`worker.go:375`). The test reproduces that sequence
with the same real store objects, differing only in batch size (10 vs
`w.batchSize`, immaterial at one recipient). No path is exercised that
production does not take.

**The sanity guard is airtight, not merely probable.** `sendPreCrashHook` is
the only caller of `cancel()` in the test, so `ambientCtx.Err() != nil` after

moving the hook after the SES call would turn that test red. So the new test
cannot silently go vacuous through a hook relocation.

**Nothing latent.** `sendRowStatus` reads on `context.Background()`, so the
assertion is not itself subject to the cancellation under test.
`ctxAwareMailer`'s mutex is defensive only (`sendOne` is called on the test
goroutine). No scratch database was needed or created — the mutations change
context derivation, not an authorization guard, and every row the test touches
