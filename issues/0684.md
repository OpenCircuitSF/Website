## Description

These are follow-ups from `#0675`'s review.

1. **Abandoned rows block retries.** If `Complete` fails, or the process dies partway through an operation, the `api_idempotency_keys` row stays in flight. Every retry with that key then gets a 409 ("still in progress") for the full 24-hour TTL. Treat an in-flight row older than a few minutes (for example 5) as abandoned, and let the retry take it over.
2. **Expired rows linger.** Only `Begin` sweeps expired rows, so they stay until the next request that carries an `Idempotency-Key`. This is harmless, but a periodic sweep, or one at startup, would keep the table small.

Do this before or alongside `#0676`, which adds the first create operation.

## Fix

Commit `5ffe3dd3`, in worktree branch `worktree-agent-a77e9de9d44f39a90`, alongside `#0676`.

1. **Abandoned rows.** `api.IdempotencyInFlightTimeout = 5 * time.Minute`. In `pgIdempotencyStore.Begin`, a conflicting row with the same operation and request hash, no stored response and a `created_at` older than the timeout is taken over by `takeOver`: `UPDATE … SET created_at = now WHERE token_id, idem_key AND status_code IS NULL AND created_at <= now − 5m`. The `WHERE` re-checks both conditions, so of two retries racing for one abandoned key exactly one gets `(nil, nil)` and runs the operation; the other gets `ErrIdempotencyInFlight`. The take-over restarts the clock. A **different** request on an abandoned key is still `ErrIdempotencyMismatch` (the key was claimed for the first request). A younger in-flight row is still 409.
2. **Expired rows.** `api.SweepIdempotencyKeys(ctx, pool, now) (int64, error)` deletes rows past `IdempotencyTTL`; `Begin` uses it, and `servePostgres` runs it once at startup (a warning on failure, an info line when it removed rows). No background goroutine, so nothing outlives a test (the `#0470` shape).

`apitest.MemoryIdempotency` is unchanged (test-only, no clock).

- `TestSweepIdempotencyKeys`: removes only the key past the TTL.
