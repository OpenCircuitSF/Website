# 0513 — `golang-migrate` is not installed on the production box

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | deploy |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-12 |

## Description

Measured read-only on the production box, twice, by two separate passes:
`command -v migrate` returns nothing. The `golang-migrate` binary is not
installed there by any method.

This matters now because production sits at schema version **22** with **28**
migration files on disk, so the next deploy applies `000023`–`000028` — six
migrations that have never touched production.

`#0509` corrected the documented install method (previously `go install`, which
cannot work on a box with no Go toolchain — see `#0509`) to a **prebuilt release
tarball**, and its review confirmed the procedure routes to that bullet rather
than silently assuming the binary is present. So the *documentation* is
correct; the *box* still lacks the tool.

## Acceptance criteria

1. `golang-migrate` is installed on the production box by the documented
   prebuilt-tarball method, at a pinned version recorded in `docs/`.
2. `migrate -version` is confirmed on the box afterwards.
3. The architecture is right — the box is `aarch64`, so an `amd64` tarball
   would install cleanly and then fail to execute.
4. Record how it gets updated, or an explicit decision that it is pinned and
   updated manually.
5. Respect `#0511`: no host literals in whatever is written down.

## Relation

- Found by [#0509](0509.md)'s implementation pass; independently reconfirmed by
  its review, which re-measured `command -v migrate` on the box.
- Blocks the next production deploy's migration step in practice, though the
  install itself is a two-minute job.
- [#0512](0512.md) — any migration step in the deploy script depends on this.

## Notes

This is an install, not a decision, and it can be done during tomorrow's deploy
window rather than ahead of it. Filed so it is not discovered at the moment the
migration step is reached.
