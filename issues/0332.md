## Description

`#0327` stopped `gc --all` dropping the real shared template under a
`TEMPLATE_DB` override by excluding three things: the current `$TEMPLATE`, the
derived `$DEFAULT_TEMPLATE`, and anything matching `not ilike '%template%'`.

The third is **unanchored**. Any scratch database whose name merely *contains*
"template" — `opencircuit_test_template_probe`, `opencircuit_test_0315template`
— is now invisible to **both** `gc` paths:

- `gc --all` never sweeps it, so it leaks; and
- the bare-`gc` refusal listing never names it either, so nobody is told it
  exists to clean up by hand.

The direction is fail-safe — a leak, not a loss, which is why this is not a
bounce on `#0327`. But it is a leak nobody is informed of, on a pool `#0315`
explicitly teaches agents to create `_template`-suffixed databases in.

`%_template` (or an anchored equivalent) keeps `#0327`'s intent — protecting a
default-looking template under an override — without swallowing every database
with the word in it.

## Acceptance criteria

1. The exclusion is anchored so it matches only genuine template names, not any
   name containing the substring.
2. `#0327`'s protection is preserved: with `TEMPLATE_DB` overridden, `gc --all`
   still refuses to drop the real `opencircuit_test_template`. Re-run
   `scripts/testdb_gc_guard_test.sh` Part 4 and confirm it still passes.
3. A scratch database named with a `template`-containing but non-template name
   is either swept by `gc --all` or named in the bare-`gc` listing — it must not
   be invisible to both.
4. Any new assertion follows §8's guard rules: behavioural rather than textual
   where possible, empty extraction fails closed, and the mutation proof shows
   the assertion is sensitive rather than vacuous.
5. The `#0327` review's noted weakness is addressed or explicitly declined: its
   mutation strips the `DEFAULT_TEMPLATE` and `%template%` exclusions together,
   so it cannot show which one is load-bearing. Separate them.

## Fix

`gc`'s third exclusion clause is now `datname !~* '_template$'` — a
case-insensitive POSIX regex end-anchor — instead of `not ilike
'%template%'`. Anchoring with SQL `LIKE`'s own escape mechanism
(`ilike '%\_template' escape '\'`) was considered and rejected: `LIKE`'s `_`
is a single-character *wildcard*, not a literal underscore, so an unescaped
`%_template` would have silently matched any single character before
"template" (still not what criterion 1 wants), and the escaped form needs an
explicit `ESCAPE` clause to mean what it looks like it means. The regex form
has no such trap and reads directly as "ends with `_template`".

`DEFAULT_TEMPLATE`'s own literal exclusion is unchanged — kept even though,
given the anchored pattern and `PREFIX` always ending in `_`, it is
presently redundant for the one name it protects (see Verification,
criterion 5). It stays as an independent, cheap safeguard that does not
depend on the pattern's specific shape or on `PREFIX` continuing to end in
an underscore.

`scripts/testdb_gc_guard_test.sh` gained a new Part 5 (renumbering the old
leak census from Part 5 to Part 6) with:
- a positive check that #0332's own two motivating leak-shaped names
  (`..._template_probe`, `...0315template`) are swept by `gc --all`, not
  left invisible to both paths;
- a positive check that a genuine `..._template`-suffixed database is still
  protected (the anchor is not over-corrected);
- a mutation reverting only the anchor to the old unanchored shape,
  reproducing the #0332 leak and proving the checks above are sensitive to
  it;
- two further mutations (criterion 5) that remove `DEFAULT_TEMPLATE` and the
  anchored pattern **separately** rather than together, closing the #0327
  review's noted weakness that its single combined mutation "cannot show
  which of the two is load-bearing."

## Verification

Ran `uptime` before each run; load average 1.8–9.0 throughout this session
(shared machine, other agents active — never treated as a defect per §5).

**Regex correctness, checked directly in `psql` before touching the script**:

```
select 'opencircuit_test_template' !~* '_template$' as a,
       'opencircuit_test_other_template' !~* '_template$' as b,
       'opencircuit_test_template_probe' !~* '_template$' as c,
       'opencircuit_test_0315template' !~* '_template$' as d,
       'opencircuit_test_ordinary4' !~* '_template$' as e;
 f|f|t|t|t
```
`f` = matches the anchor = excluded from sweep (protected); `t` = not
excluded = swept. The two genuine templates (a, b) are protected; the two
leak-shaped names from this issue's own description (c, d) and an ordinary
database (e) are all correctly swept.

**Criterion 1 (anchored, not substring)** and **criterion 3 (leak case
swept or listed)**: `scripts/testdb_gc_guard_test.sh` Part 5's first two
positive checks — `opencircuit_test_<prefix>template_probe` and
`opencircuit_test_<prefix>0332template` both swept by the real (scoped)
script's `gc --all`; `opencircuit_test_<prefix>genuine_template` still
protected.

**Criterion 2 (#0327's protection preserved)**: Part 4 re-run unmodified,
still passes — `gc --all` under a `TEMPLATE_DB` override still refuses to
drop the real default-looking template and the currently-overridden one.

**Criterion 4 (guard-design audit)**: the first attempt at Part 5's
mutation-effectiveness checks used bare substring greps (`grep -Fq "!~*"`,
`grep -Fq "not ilike '%template%'"`) as the "did the mutation take effect"
oracle, and every one of them turned out to be **vacuous** — this script's
own new comments in `scripts/testdb.sh` describing the fix in prose contain
those exact substrings, so the check passed whether or not the code line
had actually changed. Caught by inspection before trusting a green run;
replaced with `grep -Fxq` on the **exact expected `exclude_clause=` line**
for all three mutants (unanchor, no-pattern, no-default) — full-line fixed-
string matches that cannot be satisfied by a comment elsewhere in the file.
Verified each new check string against a standalone copy of the mutated
line, outside the guard script, before wiring it back in.

A second bug (not a guard-design flaw, a plain test-data bug) surfaced on
first run: `NP_DEFAULTISH`/`ND_DEFAULTISH` were named
`${TESTPREFIX}template3`/`${TESTPREFIX}template4` — neither equals
`$DEFAULT_TEMPLATE` (`${TESTPREFIX}template`, no digit) nor ends in
`_template`, so of course neither mutation protected them; the resulting
`FAIL` correctly reported the test's own bug, not a script defect. Renamed
both to the actual `$DEFAULT_TEMPLATE` value.

**Criterion 5 (separating the two mutations)**: two new mutants,
`MUTANT_NOPATTERN` (removes only the anchored-pattern clause, keeps
`DEFAULT_TEMPLATE`) and `MUTANT_NODEFAULT` (removes only `DEFAULT_TEMPLATE`,
keeps the pattern):

- **Pattern-only removed**: the literal default template still survives
  (protected by `DEFAULT_TEMPLATE` alone) — but an ad hoc
  `..._someones_own_template` scratch database (neither `$TEMPLATE` nor
  `$DEFAULT_TEMPLATE`, the #0315-taught shape) **is** swept. This proves the
  pattern clause is independently load-bearing for arbitrary ad hoc
  template-shaped scratch databases — the case `DEFAULT_TEMPLATE` alone
  cannot cover.
- **`DEFAULT_TEMPLATE`-only removed**: the literal default template still
  survives, protected by the anchored pattern alone (its own name always
  ends in `_template`, since `PREFIX` ends in `_`). This is not a bounce —
  it's the honest, mutation-confirmed answer that `DEFAULT_TEMPLATE` is
  presently *redundant* with the anchored pattern for the one name it
  literally names, and is kept deliberately as an independent safeguard (it
  does not depend on the pattern's shape or on `PREFIX` continuing to end in
  `_`), not because removing it today causes an observable regression.

This directly closes the #0327 review's noted weakness: before this issue,
the single combined mutation "cannot show which of the two is load-bearing";
now each is tested alone and the result for each is recorded, not assumed.

**Guard suite, run twice** (`ISSUE=0332gt3`, `ISSUE=0332gt4`) after both
bug fixes above: 0 failures each time, byte-identity check confirms
`scripts/testdb.sh` was never itself mutated during either run.

**`shellcheck -S warning` and `bash -n`**: clean on both
`scripts/testdb.sh` and `scripts/testdb_gc_guard_test.sh`.

**Pool census**: `psql -tAc "select datname from pg_database where datname
like 'opencircuit%'"` before and after this work:
`opencircuit`, `opencircuit_live`, `opencircuit_test`,
`opencircuit_test_template`. (Another agent's `opencircuit_test_0336b`,

## Review notes

Reviewed 2026-09-09 as one pass over `#0331`, `#0332` and `#0333`.
**Approved.** All five acceptance criteria hold.

**Criterion 1, checked at the layer most likely to be wrong.** The anchor is
written inside a double-quoted shell string, so the risk is that the anchor
character is consumed by the shell before Postgres ever sees it — the same
class as the escape-that-lands-as-the-real-character trap in `CLAUDE.md` §8.
The assignment was extracted from the tracked script and evaluated under
`/bin/bash` with the two template variables stubbed; the resulting clause
ends in a literal anchored suffix pattern, so the anchor does reach SQL.
Evaluating the old and new patterns side by side in `psql` over eight names
then showed the new one sweeps every name that merely contains the word —
including the two from this issue's description and a no-separator variant —
while protecting only genuine suffixed names, and that the old pattern
protected all eight.

**Criteria 2 and 3.** The full guard suite passes with zero failures,
Part 4 (`#0327`'s protection) included and unmodified.

**Criterion 4, tested the way §8 actually asks — by mutating the subject,
not just re-running the harness.** The tracked script and the harness were
copied into a sandbox and the *subject's* exclusion was reverted to the old
unanchored shape. The harness failed loudly, naming both leak databases, and
then aborted with a FATAL when its own later mutation could no longer find
the anchored line — fail-closed, not a silent pass. That is both halves of
§8's rule demonstrated at once: the assertions are sensitive, and an
ineffective mutation is an error rather than an input. The exact-full-line
oracles are a genuinely different representation from the subject, so an
edit to the subject cannot satisfy them.

**Criterion 5.** Both clauses are mutated independently and each result is
recorded rather than assumed, including the honest finding that
`DEFAULT_TEMPLATE` is presently redundant with the anchored pattern for the
one name it protects and is kept deliberately as a shape-independent
safeguard.

**Residual, reported rather than filed (§9), out of this issue's scope.** A
genuinely `_template`-suffixed scratch database is still invisible to both
`gc` paths — protected from the sweep, and absent from the bare refusal
listing, because both read the same exclusion. Criterion 3 only ever covered
the substring case, which is fixed; but the description's complaint that
nobody is told such a database exists still applies to suffixed ones. `list`
does show them.
