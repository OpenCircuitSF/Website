## Description

User request, 2026-11-17: "We should support seeing temp as F or C and default to F for all guides. This one just shows C. Most viewers won't know how that converts to F." (about `/guides/soldering-iron-temperature`).

Temperatures appear only in °C today. Found by grep on 2026-11-17:
- `web/src/lib/topics/IronTempDemo.svelte` — the iron dial ("Iron set to N °C").
- `web/src/lib/topics/SolderWireDemo.svelte` — melting range and iron range per alloy.
- `web/src/lib/topics/soldering.ts` — alloy prose (183 °C, 183–190 °C) and the iron-temperature verdict text (`tipC`, `melt0`).
- `web/src/lib/topics/topics.ts` — guide "ideas" prose (183 °C, 217–220 °C, "Start at 330–350 °C", 350–380 °C).
- `web/src/lib/topics/transistors.ts` and `MosfetSwitchDemo.svelte` — junction temperature (`tj`) in the transistor/MOSFET guides.

Unit-of-rate values (°C/W thermal resistance) and code comments are not reader-facing temperatures; the plan decides whether any reader-facing °C/W text exists and how to treat it.

Wanted: every reader-facing temperature in the guides shows in **°F by default**, with an easy way to switch to °C, applied consistently across all guides (a single site-wide preference, remembered for the visitor). Conversions must be rounded sensibly (e.g. 183 °C → 361 °F; ranges convert both ends; a demo dial should step in friendly °F values or show both).

### Design decisions

1. **Formatter — one pure module, `web/src/lib/temperature.ts`** (outside
   `lib/topics/`, so it is the one place a unit symbol may be spelled):

   ```ts
   export type TempUnit = 'F' | 'C';
   export const DEFAULT_TEMP_UNIT: TempUnit = 'F';
   export const TEMP_UNIT_KEY = 'temp-unit';           // localStorage key
   export const TEMP_UNIT_SYMBOL: Record<TempUnit, string> = { F: '°F', C: '°C' };
   export function cToF(c: number): number             // c * 9 / 5 + 32, unrounded
   export function fToC(f: number): number             // (f - 32) * 5 / 9, unrounded
   export function tempValue(c: number, unit: TempUnit, step = 1): number
   export function formatTemp(c: number, unit: TempUnit, step = 1): string
   export function formatTempRange(lo: number, hi: number, unit: TempUnit, step = 1): string
   export function renderTemps(text: string, unit: TempUnit): string
   export function parseTempUnit(raw: string | null | undefined): TempUnit  // 'C' -> 'C', anything else -> 'F'
   ```

   **Rounding rule (one sentence, stated in the module's doc comment):** °C is
   always rounded to the nearest whole degree; °F is rounded to the nearest
   `step` (default 1). Callers pass `step = 10` for **iron settings and the tip
   temperature** (a dial value — 626 °F reads as false precision; irons step in
   5s or 10s), and the default 1 for **melting points and junction
   temperatures** (physical facts, so 183 °C → 361 °F as the issue asks). `step`
   never affects °C: every °C source value is already a chosen round number.
   `formatTemp` returns `` `${tempValue(...)} ${TEMP_UNIT_SYMBOL[unit]}` `` with
   an ASCII space, matching today's text. `formatTempRange` converts both ends,
   joins with an en dash (`–`, U+2013, as today) and one trailing symbol, and
   collapses to `formatTemp` when the two rounded ends are equal (so `183–183`
   prints once — this replaces `SolderWireDemo`'s own equality check). Use
   `Math.round` on `n / step` then `* step`; no negative temperatures exist, so
   half-away-from-zero vs half-even never matters — say so in a comment.

   **Exact output of every temperature shown today** (these are the test
   table — put them in `temperature.test.ts` verbatim):

   | Source (°C) | step | °F output | °C output |
   |---|---|---|---|
   | 183 | 1 | `361 °F` | `183 °C` |
   | 183–183 (sn63 melt) | 1 | `361 °F` | `183 °C` |
   | 183–190 | 1 | `361–374 °F` | `183–190 °C` |
   | 190 | 1 | `374 °F` | `190 °C` |
   | 217–220 | 1 | `423–428 °F` | `217–220 °C` |
   | 330–350 (leaded iron) | 10 | `630–660 °F` | `330–350 °C` |
   | 350–380 (lead-free iron) | 10 | `670–710 °F` | `350–380 °C` |
   | 25 (tj with no load) | 1 | `77 °F` | `25 °C` |
   | 125 (tj threshold) | 1 | `257 °F` | `125 °C` |
   | 150 / 450 (old dial ends) | — | dial becomes 300…840 °F (below) | unchanged |

   Also test `cToF(fToC(x)) ≈ x`, `parseTempUnit` on `null`, `''`, `'c'`
   (lowercase → `'F'`: exact match only), `'C'`, `'F'`, `'kelvin'`.

2. **Prose tokens, rendered by `renderTemps`.** Grammar:
   `{temp:LO}`, `{temp:LO-HI}`, and either with `:STEP` appended
   (`{temp:330-350:10}`). Integers only, regex
   `/\{temp:(\d+)(?:-(\d+))?(?::(\d+))?\}/g`. A malformed token is left in the
   text unchanged (visible, and caught by the test below), never thrown.
   Rewrites:
   - `topics.ts` solder-wire idea 1: `melts at exactly {temp:183}` and
     `melts at about {temp:217-220}`.
   - `topics.ts` iron-temperature idea 1: title `Start at {temp:330-350:10}`;
     body `Lead-free wants {temp:350-380:10}.`
   - `soldering.ts` `sn63.verdict`: `…liquid at {temp:183}, with no mushy…`;
     `sn60.verdict`: `Between {temp:183} and {temp:190} it is a paste, so…`
     (reads "Between 361 °F and 374 °F" — keeps the sentence shape).

   `jointAt` and `pickSwitch` build their strings at call time, so they take
   the unit as a parameter instead of using tokens (below).

3. **Unit store — `web/src/lib/tempUnit.svelte.ts`**, a rune module modelled on
   `lib/guide/progress.svelte.ts`'s guarded storage:

   ```ts
   export const tempUnit = $state<{ value: TempUnit }>({ value: readStored() });
   export function setTempUnit(u: TempUnit): void  // sets value; try { localStorage.setItem(TEMP_UNIT_KEY, u) } catch {}
   function readStored(): TempUnit                 // try { return parseTempUnit(localStorage.getItem(TEMP_UNIT_KEY)) } catch { return 'F' }
   ```

   Module-level singleton, so one choice covers every guide and survives
   client-side navigation; localStorage carries it across visits. `readStored`'s
   try/catch also covers a missing `localStorage` global (ReferenceError), which
   is the "SSR/no-JS safe" case — there is no SSR here (the Go fallback is
   static HTML), and with JS off the fallback shows no temperatures at all. No
   cross-tab `storage` listener (not needed). Export a
   `resetTempUnitForTest()` that sets `value = 'F'` without touching storage,
   for tests that share the module.

4. **The control — `web/src/lib/TempUnitToggle.svelte`**, once per guide
   page. Markup follows the demos' existing two-option pattern so it looks and
   behaves like the controls around it:

   ```svelte
   <div class="units" role="radiogroup" aria-label="Temperature units">
     {#each ['F', 'C'] as u (u)}
       <button type="button" role="radio" aria-checked={tempUnit.value === u}
         class:on={tempUnit.value === u} onclick={() => setTempUnit(u)}>{TEMP_UNIT_SYMBOL[u]}</button>
     {/each}
   </div>
   ```

   No `aria-label` on the buttons: the visible text is the accessible name
   (label-in-name), read as "degree F". Pill styling copied from the demos'
   `.group button` / `.on` rules (focus ring is the global `--accent` one).
   **Placement:** in `TopicGuide.svelte`'s "Try it" section, on the same row as
   the `Try it` eyebrow, right-aligned (flex, `justify-content: space-between`,
   wraps on narrow screens) — directly above the demo it governs and before the
   prose. **Not repeated inside the demos**; the iron demo sits immediately
   under it.

   **Shown only on guides with temperatures.** Add `temps?: true` to
   `TopicBody` in `topics.ts` and set it on exactly
   `soldering-solder-wire`, `soldering-iron-temperature`, `mosfet-switch`
   (`MosfetSwitchDemo` always shows a Temperature cell) and `bjt-vs-mosfet`
   (`SwitchPickerDemo` can show the tj reason). `TopicGuide` renders the toggle
   `{#if topic.temps}`. A parity test (below) keeps the flag honest.

5. **Wiring each surface:**
   - `TopicGuide.svelte`: import `tempUnit` + `renderTemps`; render
     `renderTemps(idea.title, tempUnit.value)`, same for `idea.body`,
     `topic.tryIt`, `topic.takeaway` (the last two carry no tokens today; it is
     free and prevents a silent miss later).
   - `SolderWireDemo.svelte`: `melt = alloy.meltC ? formatTempRange(meltC[0], meltC[1], u) : '—'`,
     `iron = alloy.ironC ? formatTempRange(ironC[0], ironC[1], u, 10) : '—'`,
     verdict `{renderTemps(alloy.verdict, tempUnit.value)}`.
   - `soldering.ts` `jointAt(dialC, alloyId, tip, unit: TempUnit = 'F')`: the
     no-melt body becomes
     `` `At the joint the tip only reaches about ${formatTemp(tipC, unit, 10)}. ${alloy.name} needs well over ${formatTemp(melt0, unit)}, so the solder just sits there.` ``
     — `tipC` may now be fractional (see the dial), which `formatTemp` rounds.
     Nothing else in `jointAt` changes; the model stays in °C.
   - `transistors.ts` `pickSwitch(loadA, supply, drive, throughHole, unit: TempUnit = 'F')`:
     line 521 becomes `` `…would reach about ${formatTemp(tj, unit)} without a heatsink.` ``.
     The `tj > 125` threshold stays in °C. `SwitchPickerDemo` passes
     `tempUnit.value`.
   - `MosfetSwitchDemo.svelte`: both `{Math.round(r.tj)} °C` →
     `{formatTemp(r.tj, tempUnit.value)}`.
   - `IronTempDemo.svelte` — **the dial steps in the visitor's unit; the model
     stays in °C.** State is `let dialC = $state(250)` (canonical). Derived:
     in °F the slider is `min=300 max=840 step=10`, in °C `min=150 max=450 step=5`
     (unchanged). `shown = unit === 'F' ? round10(cToF(dialC)) : round5(dialC)`
     (clamped to the range); `modelC = unit === 'F' ? fToC(shown) : shown`;
     `result = jointAt(modelC, solder, tip, unit)`. The slider is
     `value={shown}` with `oninput={(e) => (dialC = unit === 'F' ? fToC(+e.currentTarget.value) : +e.currentTarget.value)}`
     (not `bind:value`, since the bound number is in the display unit). So the
     model always evaluates exactly the setting the label shows, and toggling
     units keeps the dial at the equivalent position. Label:
     `Iron set to <strong>{shown} {TEMP_UNIT_SYMBOL[unit]}</strong>`; add
     `aria-valuetext={formatTemp(modelC, unit, unit === 'F' ? 10 : 1)}` to the
     slider. Scale: `{min}` / `sweet spot {tempValue(lo,u,10)}–{tempValue(hi,u,10)}` / `{max}`
     (bare numbers, as today); `pct()` takes display-unit numbers and the
     current min/max. Default 250 °C shows **480 °F** (model 248.9 °C, tip 233.9 °C —
     "Cold joint" for 63/37 with a chisel tip, the same verdict as today's
     250 °C default).

     Rejected alternative: keep a °C-stepped slider and print the conversion —
     every 5 °C step lands on an odd °F number (482, 491, 500, 509…), which is
     exactly what the user said viewers can't read.

6. **Guard — `web/src/lib/topics/tempLiterals.guard.test.ts`.** Exports
   nothing; contains a pure `findTempLiterals(src: string): string[]` and:
   - Loads sources with `import.meta.glob(['./*.ts', './*.svelte', '../TempUnitToggle.svelte', '../../views/TopicGuide.svelte', '../../content/guides/guides.json'], { query: '?raw', import: 'default', eager: true })`,

### Product decisions for the user (defaults chosen; say if you want otherwise)

1. **One unit at a time, not both.** The plan shows "630–660 °F" with a switch,
   not "630–660 °F (330–350 °C)". Showing both is cheap to add later (a
   `formatTemp` option) but doubles the length of the short guide prose.
2. **Iron settings round to 10 °F** (330–350 °C → 630–660 °F;
   350–380 °C → 670–710 °F — a stepped °F range rounds inward, so every
   setting it names lies inside the true range), and the dial steps by 10 °F. Melting points and chip
   temperatures round to 1 °F (183 °C → 361 °F). The alternative is 1 °F
   everywhere (626–662 °F), which matches no real iron's dial.
3. **°F is the default for everyone**, not chosen from the browser's locale, as
   asked. A locale-based default (°C outside the US) is a small change if
   wanted.
4. **The switch appears only on the four guides that show a temperature**, once
   per page above the demo, not inside each demo.

### The defect: in °F the lead-free sweet spot disagrees with the demo's own verdict

`IronTempDemo` labels the lead-free sweet spot **660–720** in °F, and the guide's
first idea says "Lead-free wants 660–720 °F". But the demo judges both of those
endpoints as *not* a good joint, while the same endpoints in °C (350 and 380) are
both "Good joint". Measured by mounting `IronTempDemo` (jsdom), lead-free SAC305,
chisel tip, slider driven to each value:

| Dial | Model °C | Verdict |
|---|---|---|
| 650 °F | 343.3 | It works, slowly |
| **660 °F** | 348.9 | **It works, slowly** — shown as the sweet spot's lower end |
| 670 °F | 354.4 | Good joint |
| 710 °F | 376.7 | Good joint |
| **720 °F** | 382.2 | **Too hot** — shown as the sweet spot's upper end |
| 350 °C / 380 °C | 350 / 380 | Good joint / Good joint |

Cause: `tempValue(…, 10)` rounds each end of a range to the *nearest* 10 °F, so
350 °C (662 °F) rounds down to 660, outside the true range, and 380 °C (716 °F)
rounds up to 720, also outside. A reader told 660–720 °F who sets 660 or 720 gets
a contradicting verdict. Leaded (330–350 °C → 630–660 °F) happens to round inward
at both ends, which is why the existing smoke test at 640 did not see it.

### Remedy (apply, no re-plan needed)

1. `web/src/lib/temperature.ts`: add
   `export function tempRange(lo: number, hi: number, unit: TempUnit, step = 1): [number, number]`.
   °C: `[Math.round(lo), Math.round(hi)]`. °F with `step === 1`: nearest, as today
   (keeps 361–374 and 423–428). °F with `step > 1`: **round inward** —
   `Math.ceil(cToF(lo) / step) * step` and `Math.floor(cToF(hi) / step) * step` —
   falling back to nearest-rounding both ends if that leaves `lo > hi`.
   `formatTempRange` uses `tempRange` (collapse when the two ends are equal, as now).
   Add one sentence to the module's rounding-rule comment: a stepped °F range
   rounds inward, so every setting it names lies inside the true range.
   Results: 330–350 °C → **630–660 °F** (unchanged), 350–380 °C → **670–710 °F**.
