## Description

`middleware.DevAutoLogin` bypasses WebAuthn for local development, and
`scripts/dev.sh` advertises it — "logs in automatically as admin@localhost".
But it is wired **only** in `serveDevMode`, the `STORAGE=json` path, and it
panics at construction time outside dev mode by design.

**`STORAGE=json` has no mailing list** (`CLAUDE.md` §5): no interests, no
subscribers, no campaigns, no suppressions. So every admin screen that matters
for the mailing subsystem — subscribers, imports, pending, suppressions,
deliverability, campaigns, and now `#0393`'s CRT commands — can only be
exercised against Postgres, and the Postgres path has **no way in at all**
without registering a real passkey.

Hit while testing `#0393` locally. The observed sequence, all of it a dead end:

- `dev.sh` prints "logs in automatically as admin@localhost" regardless of
  `STORAGE`, which is **wrong under Postgres** and sends you looking for a
  session that was never created.
- `GET /admin/*` answers `401`.
- `POST /auth/register/start` for the seeded `admin@localhost` returns a
  uniform `200 {"message":"Check your email"}` and creates **no**
  `pending_registrations` row, because the user already exists. The uniform
  response is correct and must not change (it is the same anti-enumeration
  reasoning as `#0026`'s 202) — but it means the flow gives no signal that it
  is the wrong one.
- It is also gated by `registrations_enabled`, which seeds `false`, and the
  only way to flip that is `PATCH /admin/settings` — which needs the admin
  session you are trying to obtain.
- `POST /auth/recover` does work and logs a magic link under `MAILER_NOOP=true`,
  but it lands on a passkey registration ceremony, which is exactly what a
  local dev loop should not require.

The workaround actually used was inserting a `sessions` row by hand and pasting
the cookie into the browser console. That works because session tokens are
stored raw, but it is not something a developer should have to derive.

## Proposed fix

A `DEV_ADMIN_LOGIN=true` env var, honoured on the Postgres path, that
establishes a session for the configured admin exactly as `DevAutoLogin` does
for the dev store.

**Guard it with the pattern this repo already has**, not a new one:
`checkMailerNoOp`/`mailerNoOpAllowed` in `cmd/opencircuit/main.go` refuse to
start unless `BASE_URL`'s host is `localhost` or `127.0.0.1`. `CLAUDE.md` §10
records that guard as correct and not to be weakened. `DEV_ADMIN_LOGIN` must
refuse identically — **fail to boot**, not silently ignore the flag, so a
production host carrying it dies loudly rather than serving an open admin
console.

Note this is a strictly stronger requirement than `DevAutoLogin`'s current
`devMode` panic, which keys off `STORAGE=json` and therefore cannot be reused
as-is.

## Plan

**The gate, decided first, because every step below follows from it.**
`DEV_ADMIN_LOGIN=true` **plus** a `BASE_URL` whose host is exactly
`localhost` or `127.0.0.1`. Set the flag with any other `BASE_URL` and
`servePostgres` returns an error, `main`'s `log.Fatalf` prints it and the
process exits non-zero — the service does not start at all. This is
`checkMailerNoOp`'s shape, deliberately, and it reuses that guard's own host
predicate rather than inventing a second one (`CLAUDE.md` §10 records the
mailer guard as correct and not to be weakened; step 2 preserves it byte-for-byte
in behaviour, name, and tests).

**The construction invariant that makes `#0409` unreachable.** The new
middleware never branches on a credential being *present*. It branches only on
a credential being *usable*, where usable means `ResolveSession` returned a
live session — the same call `RequireSession` will make a moment later. And
when it mints, it **replaces** the request's credential rather than appending
one, so the post-condition holds unconditionally:

> after the middleware runs, the token `RequireSession` will extract from the
> request is exactly the token whose validity this middleware just established.

A stale, revoked, garbage, or expired cookie therefore cannot survive into
`RequireSession`, because minting overwrites it. That is a property of the
control flow, not a case that was remembered.

### 3. `internal/middleware/devauth.go` — a sibling, not an extension

6. Add `DevAdminAutoLogin` **alongside** `DevAutoLogin`, in the same file, and
   change nothing about `DevAutoLogin` (`#0409` asks explicitly that the
   `STORAGE=json` path not move as a side effect; the presence-vs-validity
   question on that path is `#0409`'s to answer). Three reasons it is a
   sibling rather than a parameter on the existing function: its guard keys on
   `BASE_URL`, not on `STORAGE=json`; its data seam is Postgres session
   minting plus resolution, not `devstore.CreateDevSession`; and one function
   carrying two mutually exclusive guards is weaker than two functions each
   carrying one. The name matches what `#0409` already calls it.
7. Declare the seam next to it:

   - `type DevAdminSessionMinter func(ctx context.Context) (token string, expiresAt time.Time, err error)`
   - the resolver is the existing `SessionResolver` in
     `internal/middleware/auth.go`, which `*auth.Store` already satisfies via
     `ResolveSession`.

   Do **not** add an exported session-minting method to `auth.Store`. The
   closure is built in `servePostgres` from pieces that are already exported
   (`auth.NewSessionToken` and `Store.CreateSession`, whose `q` parameter the
   live `*pgxpool.Pool` satisfies structurally), so this issue leaves the
   `internal/auth` API surface unchanged.
8. Signature: `func DevAdminAutoLogin(resolver SessionResolver, mint DevAdminSessionMinter, allowed bool) func(http.Handler) http.Handler`.
   It panics at construction when `allowed` is false, or when `resolver` or
   `mint` is nil — the same structural backstop `DevAutoLogin` has. The
   load-bearing refusal is step 10's startup error; this panic exists so a
   future miswiring cannot construct it silently.
9. Use a **new** `sync.Once` (e.g. `devAdminAuthOnce`) for the startup warning.
   Sharing `devAuthOnce` with `DevAutoLogin` would swallow one of the two
   warnings. Request behaviour, in exactly this order:

   a. `tok := sessionToken(r)` — the *same* unexported extractor
      `RequireSession` uses, so header-vs-cookie precedence can never diverge
      between the two.
   b. If `tok != ""` **and** `resolver.ResolveSession(r.Context(), tok, time.Now())`
      returns no error: call `next` with the request untouched. No mint, no
      `Set-Cookie`, no new row. This is the only pass-through branch, and it is
      keyed on validity.
   c. Otherwise obtain a token from the cache-or-mint helper (step 9d), then:
      `auth.SetSessionCookie(w, token, expiresAt)`; rebuild the request's
      `Cookie` header from `r.Cookies()` with any existing
      `auth.SessionCookieName` entry **dropped** and the new one appended, via
      `r.Header.Set("Cookie", …)` — never `r.AddCookie`, which appends and
      leaves a stale value first in the header where `r.Cookie` will find it;
      and `r.Header.Del("Authorization")` when the incoming header carried a
      bearer scheme, since `sessionToken` prefers it and it has just been
      judged unusable. Then call `next`.
   d. Cache-or-mint, guarded by a `sync.Mutex` held across the whole
      operation: if a cached token exists **and** `ResolveSession` says it is
      still live, reuse it; otherwise call `mint`, store the result, and use
      it. Validating before reuse is what stops a cached token whose row was
      deleted (a `db-reset.sh`, a `TRUNCATE`, a logout) from being handed out
      dead. Holding the mutex across the whole operation makes "a first page
      load's twenty parallel asset requests create exactly one `sessions` row"
      true rather than probable; this is a dev-only path, so the
      serialisation costs nothing that matters.
   e. A `mint` error is a 500 with a named message and an `slog.Error`,
      mirroring `DevAutoLogin`'s existing failure branch.
10. The doc comment must state the step-8 invariant in full, must say that it
    is wired only from `servePostgres` behind the loopback check, and must say
    that sign-out is a no-op while the mode is active — `POST /auth/logout`
    deletes the row and clears the cookie, and the next request mints a fresh
    session, which is the mode's contract ("you are the admin") and is the
    opposite failure from `#0409`'s stuck 401. Per `CLAUDE.md` §8's rename
    hazard note, every new doc comment must name its own declaration.

### 4. `cmd/opencircuit/main.go` — the startup gate

11. Add `newDevAdminAutoLogin(ctx context.Context, cfg *config.Config, store *auth.Store, pool *pgxpool.Pool, logger *slog.Logger) (func(http.Handler) http.Handler, error)`,
    placed next to `checkMailerNoOp`, doing exactly this in this order:

    c. Resolve the identity: `store.LookupUserByEmail(ctx, strings.ToLower(strings.TrimSpace(cfg.AdminEmail)))`.

       `cmd/opencircuit/seed.go` is the one place a user is created, and this

    d. One `logger.Warn` through `devAdminAuthOnce`'s counterpart at the

       `DevAutoLogin`'s "NEVER run this in production" wording plus "refused

    e. Build the minter closure over `store`, `pool`, and `acct.ID`:

       returning `(token, expiresAt, err)`. Note this closure must use the
       **request's** context, not the startup one — take `ctx` from the
       `DevAdminSessionMinter` parameter and ignore the captured startup ctx.
    f. Return `middleware.DevAdminAutoLogin(store, minter, true)`.

## Findings

Measured against the tree at planning time, load average 2.84.

**The Postgres path really has no seam missing except the one.**
`mountAndServe` already takes an `outerMiddleware func(http.Handler) http.Handler`
parameter and applies it as the outermost wrapper around the whole mux;
`serveDevMode` passes `DevAutoLogin`'s result and `servePostgres` passes a
literal `nil` with the comment "no outer middleware in production". Nothing
else in the repo references `outerMiddleware`, and no AST guard asserts the
Postgres call site passes nil. So this issue adds no plumbing — it fills an
argument that already exists.

**`DevAutoLogin` cannot be reused, for two independent reasons.** Its guard
takes `devMode bool` and panics when false, and `servePostgres` is by
definition `DevMode() == false`. Its data seam is
`devSessionCreator.CreateDevSession(userID, ttl)`, which `*auth.Store` does not
have and which carries no `context.Context`. It also holds `devAuthAdminID = 1`
as a package constant mirroring the dev store's seeded id — a literal id, which
`CLAUDE.md` §8b forbids aiming at a real database.

**Minting a Postgres session needs no new exported API.**
`auth.NewSessionToken` and `Store.CreateSession(ctx, q, userID, token, now)` are
both already exported. `CreateSession`'s `q` parameter has an unexported
interface type, so no other package can *name* it — but a `*pgxpool.Pool`
satisfies it structurally and can be passed as a value, and `servePostgres`
already holds the live pool. That is why the plan builds a closure at the wiring
site instead of adding a `MintSession` method: the "create a session for an
arbitrary user id with no authentication" capability stays confined to one
function in `main.go` rather than becoming permanent surface on `auth.Store`.

**Where `#0409`'s defect comes from, mechanically.** `DevAutoLogin` short-circuits
on `r.Cookie(auth.SessionCookieName)` returning any non-empty value, then, in
the minting branch, calls `r.AddCookie`. `AddCookie` *appends* to the existing
`Cookie` header, and `(*http.Request).Cookie` returns the **first** match — so
even if the presence branch were removed and the cookie were always overwritten
by `AddCookie`, a stale value would still win at extraction time. Both halves
have to change together: branch on validity, and replace the header rather than
append to it. The plan's step-8 invariant is what ties them.

**`RequireSession` reads through `sessionToken`, which prefers
`Authorization: Bearer` over the cookie.** Any middleware that wants to
guarantee what `RequireSession` will see must use that same extractor and must
neutralise the header when it mints — otherwise an unusable bearer token
produces exactly `#0409`'s 401, by a different route. Nothing in `#0409`
mentions this; it is the same defect one layer over.

**`ResolveSession` is a safe validity oracle and is idempotent enough to call
twice.** It bumps `last_seen_at` and extends `expires_at` on success, so the
middleware's check followed by `RequireSession`'s check just sets the same
sliding window twice in the same request. It returns `ErrSessionInvalid` for an
unknown or expired token and `ErrAccountInactive` for a deactivated owner, and
best-effort deletes an expired row. Treating any error as "not usable" is
correct for a dev bypass.

**The admin row must already exist, and two commands create it.**
`cmd/opencircuit/seed.go`'s `ensureAdminUser` inserts `ADMIN_EMAIL` with
`is_admin = TRUE, active = TRUE`, `ON CONFLICT (email) DO NOTHING`, then
re-promotes an existing row — idempotent. `scripts/db-reset.sh` runs
`go run ./cmd/opencircuit seed` as its last step unless `--no-seed` is passed,
defaulting `ADMIN_EMAIL` to `admin@localhost`. So on a database built by
`db-reset.sh`, the identity this mode assumes is already there; on any other
database it is one command away. `LookupUserByEmail` selects only `id` and
`active`, not `is_admin`, so the startup check proves the account exists and is
active, and `RequireAdmin` remains the thing that decides admin — a non-admin
`ADMIN_EMAIL` would get a 403, which is a correct and legible outcome.

**Where `checkMailerNoOp`'s pattern actually sits.** `mailerNoOpAllowed` parses
`BASE_URL` and compares `u.Hostname()` against `localhost` and `127.0.0.1`
exactly, treating an unparseable URL as disallowed. `checkMailerNoOp` returns
early when the flag is off, returns an error when it is on and disallowed, and
otherwise emits a single `slog.Warn`. `servePostgres` returns that error, and
`main` turns it into `log.Fatalf`. `TestMailerNoOpAllowed` already covers the
sharp cases a hand-rolled check gets wrong — `sub.localhost` and
`127.0.0.1.evil.com` both false — which is the strongest argument for reusing
the predicate rather than writing a second one.

**The residual, stated plainly.** An operator who sets `DEV_ADMIN_LOGIN=true`
*and* rewrites production's `BASE_URL` to a loopback URL would get an open admin
console behind Apache's proxy. This is the same residual `CLAUDE.md` §10 already
accepts for `MAILER_NOOP`, and the second half is self-defeating in a way that
does not stay hidden: `BASE_URL` is what every magic link, confirmation link and
unsubscribe URL is built from, and `WEBAUTHN_RP_ORIGIN` must match the browser's
real origin (§7), so a production instance pointed at `localhost` breaks visibly
within one email. Shipping `DEV_ADMIN_LOGIN=false` in `.env.example`, which is
what production's `config.env` is copied from, means the variable is present and
explicitly off rather than absent and unexplained. A per-request loopback check
was considered and rejected: production traffic reaches this service *through*
Apache on `127.0.0.1`, so a remote-address check would not distinguish the case,
and layering an `X-Forwarded-For` heuristic on top is exactly the second
mechanism `CLAUDE.md` §8 warns produces a sixth pass rather than a fix.

**`.env.example` is guarded, and the guard has a floor.**
`TestEnvExampleCoversLoaderVariables` re-derives the loader's variable set from
`config.go`'s AST and asserts each name appears as a `NAME=` line, with
`minLoaderVariables` currently `20` as a floor against the walk silently
shrinking. Adding a variable without adding the `.env.example` line fails the
guard; adding both leaves the floor stale at 20 while the real count is 21,
which is why the plan raises it.

**Guard-scope routing for this change.** `internal/config` reaches the repo root
for `.env.example`; `internal/handlers` reaches the whole tree for the
comment-citation family; `internal/db` reads `issues/`, `docs/`, `PRD.md` and
`CLAUDE.md`. All three are in scope here, plus `cmd/opencircuit` and
`internal/middleware` for the code itself. `internal/seo` is not — nothing here
touches `web/dist/index.html`.

**Cookie mechanics worth knowing before debugging a browser.**
`auth.SetSessionCookie` sets `Secure` and `SameSite=Strict`. Chrome and Firefox
treat `http://localhost` as a secure context and store such cookies; this is
already what makes `DevAutoLogin` work under `dev.sh` today, so the Postgres
mode inherits both the behaviour and the caveat rather than introducing one.

## Obstacles

1. **A local Postgres database with an admin row must exist.** Without it the
   new startup check refuses to boot — by design, but it will stop an
   implementer mid-verification. Clear it before starting:

   ```bash
   scripts/db-reset.sh            # rebuilds opencircuit from migrations and seeds admin@localhost
   ```

   It refuses without `--force` if anything else holds the database, and it is
   also the user's dev database (`CLAUDE.md` §5a) — so if it reports a live
   connection, do not force it; seed instead against the existing database:


## Acceptance criteria

- [ ] `DEV_ADMIN_LOGIN=true` establishes an admin session on the `STORAGE=postgres` path without any passkey ceremony
- [ ] It is refused **at startup**, with a clear error and a non-zero exit, whenever `BASE_URL`'s host is anything but `localhost`/`127.0.0.1` — the same rule as `mailerNoOpAllowed`, tested the same way
- [ ] Unset or `false` changes nothing: the Postgres path behaves exactly as it does today, proved by a test that the admin routes still answer 401
- [ ] A single startup `WARN` is logged when it is active, matching `DevAutoLogin`'s wording about never running it in production
- [ ] The session it mints is a real `sessions` row with a normal TTL — not a bypass of `RequireSession`/`RequireAdmin`, which must keep running unchanged
- [ ] The admin user it targets is the configured `ADMIN_EMAIL`, and it fails clearly if no such user exists rather than creating one silently
- [ ] `scripts/dev.sh`'s "logs in automatically" banner tells the truth under both storage modes — it currently claims auto-login unconditionally
- [ ] `scripts/dev.sh` gains a documented way to run against Postgres; today `STORAGE`/`DATABASE_URL` must be discovered by reading the script
- [ ] `docs/dev.md` (and `docs/configuration.md`) document the variable and its localhost-only guard
- [ ] A guard test proves the flag cannot take effect on a non-localhost `BASE_URL` — the mutation to try is flipping the host, and the assertion is that startup fails
