# 0402 — No way into the admin console under `STORAGE=postgres` locally without registering a passkey

## Description

`middleware.DevAutoLogin` bypasses WebAuthn for local development, and
`scripts/dev.sh` advertises it — "logs in automatically as admin@localhost".
But it is wired **only** in `serveDevMode`, the `STORAGE=json` path, and it
panics at construction time outside dev mode by design.

**`STORAGE=json` has no mailing list** (`CLAUDE.md` §5): no interests, no
subscribers, no campaigns, no suppressions. So every admin screen that matters
for the mailing subsystem — subscribers, imports, pending, suppressions,
deliverability, campaigns, and now `#0393`'s CRT commands — can only be
exercised against Postgres, and the Postgres path has **no way in at all**
without registering a real passkey.

Hit while testing `#0393` locally. The observed sequence, all of it a dead end:

- `dev.sh` prints "logs in automatically as admin@localhost" regardless of
  `STORAGE`, which is **wrong under Postgres** and sends you looking for a
  session that was never created.
- `GET /admin/*` answers `401`.
- `POST /auth/register/start` for the seeded `admin@localhost` returns a
  uniform `200 {"message":"Check your email"}` and creates **no**
  `pending_registrations` row, because the user already exists. The uniform
  response is correct and must not change (it is the same anti-enumeration
  reasoning as `#0026`'s 202) — but it means the flow gives no signal that it
  is the wrong one.
- It is also gated by `registrations_enabled`, which seeds `false`, and the
  only way to flip that is `PATCH /admin/settings` — which needs the admin
  session you are trying to obtain.
- `POST /auth/recover` does work and logs a magic link under `MAILER_NOOP=true`,
  but it lands on a passkey registration ceremony, which is exactly what a
  local dev loop should not require.

The workaround actually used was inserting a `sessions` row by hand and pasting
the cookie into the browser console. That works because session tokens are
stored raw, but it is not something a developer should have to derive.

## Proposed fix

A `DEV_ADMIN_LOGIN=true` env var, honoured on the Postgres path, that
establishes a session for the configured admin exactly as `DevAutoLogin` does
for the dev store.

**Guard it with the pattern this repo already has**, not a new one:
`checkMailerNoOp`/`mailerNoOpAllowed` in `cmd/opencircuit/main.go` refuse to
start unless `BASE_URL`'s host is `localhost` or `127.0.0.1`. `CLAUDE.md` §10
records that guard as correct and not to be weakened. `DEV_ADMIN_LOGIN` must
refuse identically — **fail to boot**, not silently ignore the flag, so a
production host carrying it dies loudly rather than serving an open admin
console.

Note this is a strictly stronger requirement than `DevAutoLogin`'s current
`devMode` panic, which keys off `STORAGE=json` and therefore cannot be reused
as-is.

## Acceptance criteria

- [ ] `DEV_ADMIN_LOGIN=true` establishes an admin session on the `STORAGE=postgres` path without any passkey ceremony
- [ ] It is refused **at startup**, with a clear error and a non-zero exit, whenever `BASE_URL`'s host is anything but `localhost`/`127.0.0.1` — the same rule as `mailerNoOpAllowed`, tested the same way
- [ ] Unset or `false` changes nothing: the Postgres path behaves exactly as it does today, proved by a test that the admin routes still answer 401
- [ ] A single startup `WARN` is logged when it is active, matching `DevAutoLogin`'s wording about never running it in production
- [ ] The session it mints is a real `sessions` row with a normal TTL — not a bypass of `RequireSession`/`RequireAdmin`, which must keep running unchanged
- [ ] The admin user it targets is the configured `ADMIN_EMAIL`, and it fails clearly if no such user exists rather than creating one silently
- [ ] `scripts/dev.sh`'s "logs in automatically" banner tells the truth under both storage modes — it currently claims auto-login unconditionally
- [ ] `scripts/dev.sh` gains a documented way to run against Postgres; today `STORAGE`/`DATABASE_URL` must be discovered by reading the script
- [ ] `docs/dev.md` (and `docs/configuration.md`) document the variable and its localhost-only guard
- [ ] A guard test proves the flag cannot take effect on a non-localhost `BASE_URL` — the mutation to try is flipping the host, and the assertion is that startup fails

## Notes

Filed 2026-09-03 after `#0393` could not be exercised locally without hand-minting
a session row.

**Do not weaken `registrations_enabled`'s default or the uniform
`register/start` response to solve this.** Both are correct. The gap is the
absence of a dev affordance on the Postgres path, not a defect in the auth
flows — and a fix that loosens either one would trade a local inconvenience for
a production weakness.

Worth considering alongside: a `scripts/dev.sh --postgres` flag, so the whole
local mailing-subsystem loop is one documented command rather than three env
vars.
