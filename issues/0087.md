## Description

`#0081` fixed a `WaitGroup` race and reordered shutdown so `srv.Shutdown` runs before `SubscribeHandler.Close`. The ordering is right and should not be reverted. But both steps share **one** `shutdownTimeout` context, and `Shutdown` can consume all of it.

`http.Server.Shutdown` does not cancel in-flight request contexts, and `GET /api/events` (`internal/handlers/events.go:76-90`, mounted at `cmd/opencircuit/main.go:490`) returns only on client disconnect. **One open admin dashboard stream is enough.**

Demonstrated by `#0081`'s reviewer with a 2 s budget:

```
Shutdown returned after 2.00s with context.DeadlineExceeded — 0s remaining for Close
```

`Close` then still flips `closed`, cancels `sendCtx` and closes `sendQueue`, but returns immediately without waiting. The claim releases are *started* and then killed by process exit — reviving the hour-long retry silence `#0081` exists to prevent.

## Why starving `Close` is worse than starving `Shutdown`

Under the old ordering, `Close` ran first and could starve `Shutdown`; the worst case was a dropped SSE connection, which `EventSource` reconnects automatically. Under the new ordering the worst case is **stranded confirmation claims** — a visitor who saw a `202`, never got the email, and cannot retry for up to an hour.

Same shared budget, materially different consequence. That asymmetry is the reason to split it rather than enlarge it.

## Notes

**Do not revert the ordering.** `#0081`'s reviewer confirmed `Shutdown`-first is correct: `enqueueSend` is reachable only from two synchronous request paths, the package spawns no goroutines besides its worker pool and `Close`'s waiter, and it hijacks nothing — so on a nil `Shutdown` return there is genuinely no untracked path. The ordering is defence-in-depth on top of `closeMu`, not a substitute for it.

**`#0045` is told to reuse this shutdown pattern**, so it would inherit this flaw. Fix it here first.

## Fix

`mountAndServe`'s SIGTERM/SIGINT branch used one shared `ctx` for both
`srv.Shutdown(ctx)` and `subscribeH.Close(ctx)`. Split into two independent
contexts, each with its own package-level `var` (not `const`, so the new
wiring test can override them deterministically):

- `shutdownServerTimeout` (5s, was part of the old shared 20s) — bounds
  `srv.Shutdown` alone.
- `subscribeCloseTimeout` (15s, the rest of the old 20s) — bounds
  `subscribeH.Close` alone, sized to comfortably exceed
  `releaseSendClaim`'s own detached 5s context (see the "closed-drop path"
  decision below).

The ordering (`Shutdown` before `Close`) is unchanged, per the issue's
explicit instruction not to revert it.

**Two comments corrected** for overstating a conditional guarantee — both
claimed the "no request goroutine can still be inside `enqueueSend`"
property held unconditionally after `Shutdown`, when it only holds when
`Shutdown` returns **nil**:

- `cmd/opencircuit/main.go`'s shutdown-sequence comment ("makes that race
  structurally unreachable") — corrected to explain the guarantee is
  conditional on a nil return, and that the `DeadlineExceeded` case is safe
  only because `enqueueSend`'s `closeMu`-guarded check still refuses a send
  after `closed` flips true (which `Close` sets while holding the same
  lock), not because of the Shutdown-before-Close ordering itself.
- `internal/handlers/subscribe.go`'s `Close` doc comment — same correction,
  written from `Close`'s side of the same fact.

**The closed-drop path's detached 5s `releaseSendClaim` context (acceptance
criterion 4) — decision recorded, not separately tracked.** `Close`'s `Wait`
only bounds `sendWG`, and each worker's `processSendJob` defers
`sendWG.Done()` — including through `releaseSendClaim`'s own call, which
runs synchronously on the same worker goroutine before `Done()` fires. So
`Close`'s `Wait` DOES cover a worker that is still inside `releaseSendClaim`
when `Close` is called, up to that release's own 5s bound — the risk isn't
that the release is untracked, it's sizing: if `subscribeCloseTimeout` were
too close to that 5s figure, a
release beginning near the end of Close's budget could still be cut short
by `Close` returning via its own `ctx.Done()` before the release finishes.
`subscribeCloseTimeout` (15s) is sized to leave 3x headroom over that 5s
worst case — documented directly in `subscribeCloseTimeout`'s doc comment,
with an explicit instruction not to shrink it without re-deriving the
margin. Decision: splitting the budget, combined with that sizing margin,
is judged sufficient; no separate tracking mechanism for the detached
context was added.

`deploy/systemd/opencircuit.service`'s comment updated to describe the two
independent budgets (still summing to 20s, so `TimeoutStopSec=30` still
leaves the same 10s of slack — no change to the actual timeout value was
needed).

## Gotchas

- `shutdownServerTimeout`/`subscribeCloseTimeout` are `var`, not `const`,
  specifically so `shutdown_budget_wiring_test.go` can override them without
  waiting out the real 5s/15s production values. They are restored via
  `t.Cleanup` unconditionally so no other test in the same binary observes
  the shrunk values — if a future test adds its own override, it must do
  the same.
- `subscribeCloseTimeout`'s 15s value is load-bearing for the "closed-drop
  path" reasoning (3x headroom over `releaseSendClaim`'s detached 5s
  context) — don't shrink it without re-deriving that margin, per its own
  doc comment.
- The new test measures elapsed time from when the send actually started
  (`mailer.entered`), not from when `SIGTERM` was sent — because the send
  worker begins sleeping the instant it dequeues the job, before `SIGTERM`
  is even sent, so "time since SIGTERM" would not match the "≈ sendDelay"
  math the test relies on. This is explained in the test's own doc comment
  after an initial version of the test (measuring from `SIGTERM`) produced
  a passing-but-too-close-to-threshold result during development.

## Review notes

**2026-08-19 — bounced.** **The production change is correct and should be kept
exactly as it stands.** The bounce is entirely about the regression guard that
ships with it: `TestMountAndServe_ShutdownAndCloseHaveIndependentBudgets`
false-fails on correct code roughly a third of the time, and its failure message
asserts "exactly the #0087 bug" when the bug is absent.

### What was verified and is good

- **The starvation reproduction works, both directions.** Collapsing the two
  contexts back to one (`closeCtx := shutdownCtx`) reproduces it exactly:

  ```
  opencircuit: subscribe handler close: context deadline exceeded
  shutdown_budget_wiring_test.go:256: mountAndServe returned 159.248583ms after the send began
  --- FAIL: TestMountAndServe_ShutdownAndCloseHaveIndependentBudgets (8.85s)
  ```

  159 ms against the 150 ms shared budget — `Shutdown` took all of it and `Close`
  got none, with the exact log line this issue describes. Reverted (verified
  byte-identical against a saved copy) and it passes.
- **The arithmetic holds with real slack.** `shutdownServerTimeout` (5 s) +
  `subscribeCloseTimeout` (15 s) = 20 s, hard-bounded — `Shutdown` returns at its
  ctx deadline at the latest, and `Close`'s `select` returns on `ctx.Done()` — so
  the sequence cannot exceed 20 s + ε against `TimeoutStopSec=30`. 10 s of slack;
  systemd will not `SIGKILL` first. One small caveat worth a comment rather than
  a change: `servePostgres`'s `defer pool.Close()` runs *after* `mountAndServe`
  returns and is unbounded, so the true worst case is 20 s plus however long an
  in-flight statement takes to return its connection. In practice that is
  sub-second (pgx checks connections out per statement, not across the mailer
  send), so the 10 s slack absorbs it — but the systemd comment currently implies
  20 s is the whole story.
- **Both comments are correctly de-overstated.** Neither `main.go`'s
  shutdown-sequence comment nor `Close`'s doc comment now claims the
  no-goroutine-inside-`enqueueSend` property unconditionally; both scope it to a
  nil `Shutdown` return and correctly attribute the `DeadlineExceeded` case's
  safety to `enqueueSend`'s `closeMu`-guarded check rather than to the ordering.
  The `closeMu` claim was checked against the code and is accurate.

### Why it is bounced: the new test is load-sensitive and false-fails

Eleven runs of the test against **unmutated, correct** code:

| condition | elapsed measurements | result |
|---|---|---|
| one other Go package's suite running | 412, 164, 601, 228, 347 ms | 3 of 5 FAIL |
| idle machine | 342, 516, 439, 426, 500 ms | 1 of 5 FAIL |

Four false failures in ten single-test runs, each reporting *"Close appears to
have been starved of its own budget by Shutdown's open-SSE-stream delay, exactly
the #0087 bug"* — on code where `Close` was never starved at all.

**The mechanism, measured directly.** `sendStart` is captured in the *test*
goroutine after it receives `<-mailer.entered`, but `delayedMailer.Send` closes
that channel and begins its 600 ms sleep on the *worker* goroutine, while the
`POST /api/subscribe` response is still in flight. So `sendStart` systematically
lags the real start of the sleep. Instrumenting `Send` to record its own entry
time makes it unambiguous:

```
REVIEW: sendStart lags the real Send entry by 177.331625ms  -> elapsed 423.73ms  PASS
REVIEW: sendStart lags the real Send entry by 327.009834ms  -> elapsed 303.53ms  FAIL
REVIEW: sendStart lags the real Send entry by 245.157ms     -> elapsed 356.00ms  PASS
```

`elapsed + lag ≈ sendDelay (600 ms)` in every single run — including the failing
ones. That is proof the fix worked every time: `Close` always waited out the full
send. The test is measuring `sendDelay − lag`, and its 350 ms threshold trips
whenever the lag exceeds 250 ms, which is routine. The implementer's
"600.28 ms–601.45 ms every time" was an idle-machine artifact of a small lag.

**Why this matters enough to bounce rather than note.** `#0045` is told to reuse
this shutdown pattern, so it would inherit the guard too. And a test that cries
"the #0087 bug is back" on healthy code is precisely the pathology `#0084` exists
to remove — `CLAUDE.md` §5's whole verification contract depends on a red run
meaning something.

### Suggested fix — small

Record the timestamp inside `delayedMailer.Send` (`m.trueStart = time.Now()`
before `close(m.entered)`) and measure elapsed from that, not from the receive.
That makes elapsed ≈ `sendDelay` deterministically and restores the intended
~250 ms of margin on both sides of the 350 ms threshold. Raising `sendDelay`
would also work but wastes wall clock; fixing the measurement is strictly better.
Nothing in `main.go`, `subscribe.go` or the systemd unit needs to change.

## Root cause (of the bounce — the guard, not the production code)

The reviewer confirmed the production fix (`shutdownServerTimeout`/
`subscribeCloseTimeout` as independent contexts) is correct and does not
need to change. The defect was entirely in
`TestMountAndServe_ShutdownAndCloseHaveIndependentBudgets`'s own
measurement: it captured `sendStart := time.Now()` in the *test* goroutine
immediately after `<-mailer.entered`, but `delayedMailer.Send` closes
`entered` and begins its 600ms sleep on the *worker* goroutine while the
`POST /api/subscribe` HTTP response is still being written back to the
client. The test goroutine only resumes after the scheduler gets around to
it, which under load lagged the real `Send` entry by up to ~330ms
(measured directly by the reviewer). Since the test's pass/fail threshold
(350ms) sits only ~250ms above the expected ~600ms-ish total, that lag was
large enough to push a healthy run under the threshold and report the
`#0087` starvation symptom on code that never starved `Close` at all.

## Fix (this pass — the guard)

Implemented the reviewer's suggested fix exactly:
`delayedMailer` (`cmd/opencircuit/shutdown_budget_wiring_test.go`) gained a
mutex-guarded `trueStart time.Time` field, set at the very top of `Send`
(before `close(m.entered)`) on the worker goroutine, plus a `SendStart()`
accessor. The test now computes `sendStart := mailer.SendStart()` after
observing `<-mailer.entered`, instead of taking `time.Now()` itself at that
point — so elapsed time is measured from where the send actually begins,
not from where a different goroutine happens to notice it did. Both the
`delayedMailer` doc comment and the test's own comment at the read site
explain why the two are not interchangeable, per the reviewer's diagnosis.

No change was needed to `main.go`, `subscribe.go`, or the systemd unit —
the reviewer's own conclusion, confirmed correct.

`shutdown_budget_wiring_test.go` also carries `#0084`'s
`wiringDBConnectTimeout` constant swap (this file's own
`context.WithTimeout(context.Background(), 30*time.Second)` `db.Connect`
call), landed in `#0084`'s commit (`ac3baa9`) since that's where the
constant is defined and justified; this issue's commit (`cd67e7a`) carries
only the `SendStart`/`trueStart` guard fix plus the `deploy/systemd`

## Closing note — 2026-08-20 (user directive)

Closed by the user's explicit instruction after the cause of the "load" in this
issue was identified.

The load was **not** the website's traffic and not a performance requirement.
It was the CPU load average of the developer's laptop, produced by a single
orchestrator session (`4f1ef351`, ~25 hours, 197 subagents) running full
DB-backed Go suites concurrently, several in separate git worktrees that each
recompiled from scratch. Load averages of 240-320 were recorded in these issues
as "real ambient load" and treated as the baseline to design against.

They are not a baseline. They are the bug. A `TRUNCATE` against a local
Postgres with no contention completes in milliseconds; it only took 1.3-3.9s
because ~200 agents were competing for the same CPU and the same database.

Widening test deadlines to accommodate self-inflicted machine load was the wrong
fix for a marketing site with a mailing list. The correct fix -- capping agent
concurrency and scoping test runs -- is now in CLAUDE.md §5 and §5a.

**Do not reopen this, and do not file follow-ons that propose extending the
timeout policy to further packages.** If a test times out, first check
`uptime`; if the load average is above ~8, the machine is the problem, not the
deadline.
