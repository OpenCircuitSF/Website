## Description

`#0081` fixed a `WaitGroup` race and reordered shutdown so `srv.Shutdown` runs before `SubscribeHandler.Close`. The ordering is right and should not be reverted. But both steps share **one** `shutdownTimeout` context, and `Shutdown` can consume all of it.

`http.Server.Shutdown` does not cancel in-flight request contexts, and `GET /api/events` (`internal/handlers/events.go:76-90`, mounted at `cmd/opencircuit/main.go:490`) returns only on client disconnect. **One open admin dashboard stream is enough.**

Demonstrated by `#0081`'s reviewer with a 2 s budget:

```
Shutdown returned after 2.00s with context.DeadlineExceeded — 0s remaining for Close
```

`Close` then still flips `closed`, cancels `sendCtx` and closes `sendQueue`, but returns immediately without waiting. The claim releases are *started* and then killed by process exit — reviving the hour-long retry silence `#0081` exists to prevent.

## Why starving `Close` is worse than starving `Shutdown`

Under the old ordering, `Close` ran first and could starve `Shutdown`; the worst case was a dropped SSE connection, which `EventSource` reconnects automatically. Under the new ordering the worst case is **stranded confirmation claims** — a visitor who saw a `202`, never got the email, and cannot retry for up to an hour.

Same shared budget, materially different consequence. That asymmetry is the reason to split it rather than enlarge it.

## Notes

**Do not revert the ordering.** `#0081`'s reviewer confirmed `Shutdown`-first is correct: `enqueueSend` is reachable only from two synchronous request paths, the package spawns no goroutines besides its worker pool and `Close`'s waiter, and it hijacks nothing — so on a nil `Shutdown` return there is genuinely no untracked path. The ordering is defence-in-depth on top of `closeMu`, not a substitute for it.

**`#0045` is told to reuse this shutdown pattern**, so it would inherit this flaw. Fix it here first.
