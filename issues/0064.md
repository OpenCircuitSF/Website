## Review notes

**Bounced 2026-08-24.** Independent phase-3 review of `ccf134d`. Almost all
of this is strong work and unusually honest about its own limits — but one
ticked criterion does not hold, and the runbook hands the operator a
correction procedure that reproduces the same error. Criterion 8 has been

### What fails — the CSP `script-src` hash is wrong, and so is the recompute command

Criterion 8 claims `script-src` is "locked to `'self'` plus one hash for the
SPA's single inline bootstrap script", and `docs/deployment.md` states the
hash is `base64(sha256(<the exact bytes between <script> and </script> in the
*source* web/index.html>))`. **It is not.** The value shipped in
`deploy/apache/opencircuitsf.com.conf` was computed over the script's content
**with the leading newline stripped**, because the recompute snippet in
`docs/deployment.md` anchors on `r'<script>\n(.*?)</script>'`. CSP hashes the
element's child text content exactly, whitespace included.

Measured, not reasoned about:

| what was hashed | result |
|---|---|
| exact bytes between `<script>` and `</script>` (what the doc says) | `sha256-aV6Z5Fp2xyBUYGmN3Q9e0BQeIOKsDdCa35MPtxT7byg=` |
| the same, minus the leading `\n` (what the snippet does) | `sha256-dwSwJdScBQq2rtRDgx+PNrnX/IUc7TDIKGH+8kn188Y=` ← **shipped** |

Then confirmed in a **real browser** rather than from spec prose — Chromium
via Playwright, against a local server on port 47318 whose identity was
verified by a build-specific marker string in the response body
(`CLAUDE.md` §8b), serving the exact inline script under the exact shipped
CSP header:

```
[SHIPPED]  sha256-dwSwJdScBQq2rtRDgx+PNrnX/IUc7TDIKGH+8kn188Y=
  CSP violations: Executing inline script violates the following
                  Content Security Policy directive 'script-src 'self' …

[COMPUTED] sha256-aV6Z5Fp2xyBUYGmN3Q9e0BQeIOKsDdCa35MPtxT7byg=
  CSP violations: NONE — script allowed
```

The runbook is right that this fails **closed** rather than open — the
pre-paint theme guard is simply blocked and the page flashes the wrong theme
— so this is a correctness bug, not a security regression. But the runbook's
"if the printed hash differs, update the vhost" escape hatch does not save
anyone here, because the command it gives prints the *same wrong value* it
already shipped. That is what makes this worth bouncing rather than noting.

**What the next pass must do:**

1. Put the correct hash for `web/index.html`'s source into
   `deploy/apache/opencircuitsf.com.conf` —
   `sha256-aV6Z5Fp2xyBUYGmN3Q9e0BQeIOKsDdCa35MPtxT7byg=` as of `ccf134d`,
   but recompute it rather than copying this line.
2. Fix the recompute snippet in `docs/deployment.md`'s "Security headers"
   section so it captures the element's whole child text content — drop the
   `\n` from the regex (`r'<script>(.*?)</script>'`), and make sure it
   selects the bootstrap script rather than the `<script
   type="application/ld+json">` example that appears inside an HTML comment
   further up the file (a naive `<script...>` scan matches that comment too —
   this reviewer hit it).
3. Keep the existing, correct caveat that the hash is computed from source
   and not from `npm run build` output.
4. Re-verify the way this review did: the hash must be observed to *allow*
   the script in a browser, not merely to have been produced by a script.

## Gotchas

- **`web/dist/index.html` (the committed placeholder) is a tracked file**,
  not gitignored — only `web/dist/*` beyond it is ignored. This means
  running `npm run build` here would have rewritten a tracked file inside
  `web/`, which this dispatch was told not to touch and which `CLAUDE.md`
  §8b separately flags as a shared mutable resource. That is *why* the CSP
  hash rests on source rather than a real build, not an oversight — a future
  pass with `web/` in scope (or run in isolation, e.g. a worktree) should
  redo that one computation against real build output before this CSP goes
  live.
- **`httpd -t` needs an `ErrorLog` and `ServerName` even for a pure syntax
  check** — omitting them doesn't fail the check, it just prints a warning
  and then a *different* fatal error (`Cannot access directory '/usr/logs/'
  for main error log`) that looks like a real config problem but isn't one.
  Worth knowing before reading a `httpd -t` failure as "the vhost is wrong"
  when it might just be the wrapper.
- **The AL2023 `httpd` module path (`modules/`) differs from this macOS
  Apache's (`libexec/apache2/`)** — the wrapper config used to prove the
  vhost parses is not portable to AL2023 as written; only the vhost file
  itself (the thing actually being checked) is what matters for the real
  deploy, and it references no path that's macOS-specific.
