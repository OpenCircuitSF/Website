## Description

The end-to-end procedure for standing up and updating production on EC2, alongside the existing ShortLinks install.

## Acceptance criteria

- [ ] `docs/deployment.md` covering: EC2 provisioning, PostgreSQL setup, config file creation, build, migrations, seed, systemd, Apache, TLS, first admin login
- [ ] Apache vhost for `opencircuitsf.com` with **the apex redirecting to `www`** — www is canonical in production and `WEBAUTHN_RP_ORIGIN` depends on it — and `flushpackets=on` on `/api/events`

> **Criterion corrected 2026-08-18.** This read "`www` redirecting to apex", which is backwards: the live host 301s the apex to www, `#0066` built the vhost that way, and a passkey ceremony fails with an opaque error if `WEBAUTHN_RP_ORIGIN` stops matching the browser's real origin.
- [ ] systemd unit for `opencircuit` mirroring the ShortLinks hardening (`NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`, restricted address families)
- [ ] Coexistence with the ShortLinks install documented: separate ports, databases, service accounts, and config files
- [ ] Route 53 record table from PRD §10.2 reproduced with real values
- [ ] SES setup: domain verification, DKIM, custom MAIL FROM, DMARC ramp from `p=none` to `p=quarantine` to `p=reject`, production-access request
- [ ] IAM instance role policy documented, scoped per PRD §10.5
- [ ] Security headers configured: HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and a CSP with no `unsafe-inline`
- [ ] Redeploy procedure and a troubleshooting section for "deployed but the site did not change"
- [ ] The whole runbook followed once on a clean instance and corrected where it was wrong

## Carried in from `#0077`'s review (2026-08-19)

- [ ] **Document the loopback trust model.** `middleware.ClientIP` trusts
      `X-Forwarded-For` only when the peer is loopback, then takes the rightmost
      entry — the single hop Apache appends. `cmd/opencircuit/main.go:504`
      hardcodes `127.0.0.1:<port>` and there is no config knob to move it, so the
      anchor is enforced in code. The runbook must state the operational
      consequence: **nothing else on that host may proxy or tunnel into
      `127.0.0.1:8080`** — another local process, a host-network container, or an
      SSH tunnel would be trusted as if it were Apache.
- [ ] **Record the CDN failure mode.** If a CDN or second proxy is ever put in
      front, the rightmost entry becomes that proxy's egress IP: every user
      collapses into one rate-limit bucket and `signup_ip` records the CDN, with
      **no error**. `middleware.ClientIP` must be revisited before any such change.

## Carried in from `#0045`'s plan (2026-08-21)

Two deploy-time facts the code cannot enforce, both of which must appear in the
runbook:

- [ ] **The SES configuration set must have open and click tracking disabled.**
      An enabled configuration set injects a tracking pixel **server-side**, at
      send time. That violates `CLAUDE.md` §9's no-open-tracking rule with no
      code change, and **no test in this repo can observe it** — the messages we
      generate are clean either way. It is invisible until someone inspects a
      delivered message.
- [ ] **`MAX_SEND_RATE=1` while the SES account is in the sandbox** (1 message
      per second). Note `CLAUDE.md` §5: there is no performance requirement in
      this project — this value paces for SES's quota, not for throughput.

## Notes

PRD §10, §11. ShortLinks' `DEPLOYMENT.md` is the model, including its troubleshooting section on deploys that appear not to take effect — that section exists because the problem actually happened.

The CSP is worth getting right at deploy time rather than retrofitting: Vite emits hashable assets, so `unsafe-inline` is genuinely avoidable here.

The final criterion is the real one — a runbook that has never been followed is a draft.

## Carried in from `#0072`'s review (2026-08-18)

- [ ] **Correct `PRD.md` §9's `BASE_URL`, or stop treating it as the config
      template's source.** `#0072` fixed `.env.example` (apex → www) and
      `docs/configuration.md`, but `PRD.md` §9's configuration block still shows
      `BASE_URL=https://opencircuitsf.com` — the apex — two lines above a
      `WEBAUTHN_RP_ORIGIN=https://www.opencircuitsf.com` whose own comment states
      that www is canonical and that the apex 301s to it. That is the exact
      internal inconsistency `#0072` was filed about, surviving in a third source
      of truth. Since this runbook is what documents
      `/etc/opencircuit/config.env`, and `deploy/systemd/README.md` says that file
      "supplies every variable from `.env.example`", anyone regenerating the
      config from PRD §9 reintroduces the defect `#0072` just removed. Either
      correct the PRD line (a user-owned document — ask before editing) or state
      in the runbook that `.env.example` is authoritative and PRD §9 is
      illustrative.
- [ ] **The second acceptance criterion above is backwards** — it says the vhost
      should redirect `www` → apex. Production and `deploy/apache/opencircuitsf.com.conf`
      both do the opposite (apex → www, `RewriteCond %{HTTP_HOST} !^www\.`), and
      `WEBAUTHN_RP_ORIGIN` depends on www staying canonical. Already flagged in
      `CLAUDE.md` §7; repeated here so it is not missed at implementation time.
