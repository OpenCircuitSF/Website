## Description

`#0340`'s `tokenGate` withholds a queued row whose payload `confirm_token` no
longer matches the live one. `#0400` made the gated-kind set a true set, so a
member cannot be present-but-disarmed.

**Nothing checks that a gated kind's payload carries a `confirm_token` at all.**

Moving `KindAlreadySubscribed` from the ungated set into the gated set — leaving
the partition intact, so the partition guard stays green — leaves the **entire
`internal/mailing` suite passing**. But that kind's producer enqueues an
`alreadySubscribedPayload` carrying only a manage token. Measured inside the
mutant with a throwaway probe rather than inferred, `tokenGate` returns
`skip=true` with the reason *"queued row's payload carries no confirm token"*.

So **every `already_subscribed` message would be silently withheld** and nothing
in the tree notices.

## Why this is the interesting direction

`#0400` closed *"a member can be present but disarmed"* — a **security** failure,
where mail goes out that should not. This is the mirror image: *"a member can be
present but ungateable"* — an **availability** failure, where mail that should go
out never does.

Availability failures are quieter. A withheld message produces no error, no
bounce, and no queue backlog; the row terminates as `skipped` and looks handled.

The status gate has a sibling test for exactly this class,
`TestOutboxWorker_SendGate_UngatedKindsNeverSkip`. **The token gate has no
equivalent.**

**Unverified by the orchestrator.** The mutation and the probe result are
`#0400`'s reviewer's measurements. Reproduce them before building on them, and
correct this issue if they do not hold.

## The remedy the review specified

A parity guard asserting that **every member of the gated set has a producer
payload declaring a `confirm_token` JSON field**.

Derive both sides from source. The payload side should come from the actual
producer types rather than a hand-written list — a list is a copy of the answer
stored next to the question (§8), and this whole family exists because such a
copy agreed with itself.

### Criterion 6 — built, not recorded

Chose to **build** the guard, not record the limit. The `#0330`/`#0347`/
`#0356`/`#0381` precedent this criterion cites recorded limits where building
was either disproportionately expensive relative to the risk, or the failure
mode needed a planning pass to even define correctly (`#0356` explicitly
required one). Neither holds here:

- **Cost was low.** The guard is ~250 lines of `go/ast`, following the exact
  pattern this package already established in
  `outbox_worker_kinds_guard_test.go` (`collectKindConstants`,
  `filesOf`) — not a new technique, an application of one already proven in
  this file's neighbor. It runs in the low milliseconds and needs no
  database.
- **The failure is uniquely silent.** Every other gate in this file fails
  loud in some way if misconfigured — an unclaimed `Kind` stalls visibly in
  `queued` (caught by `TestMailKindsCoversEveryOutboxKind`), a status
  mis-gate produces a wrong-but-present skip reason. This one produces a
  *correct-looking* skip reason ("queued row's payload carries no confirm
  token") on every single message of the kind, forever, with the whole test
  suite green — there is no signal anywhere for an operator or a future
  reviewer to notice without deliberately probing for it.
- **The trigger is a one-line edit that looks obviously safe.** Adding a
  kind to `tokenGatedKinds` reads as "make this kind's messages re-checked
  before send" — strictly more caution, not less. Nothing about the edit
  itself hints that it also requires the kind's payload to carry a specific
  field. That is exactly the gap the record-rather-than-build precedent
  weighs against recording: a limit worth recording is one a future author
  is likely to consult before hitting it; a one-line edit that looks safe is
  one they will not.

Recording this as a known limitation in a doc comment would have reproduced
the exact failure mode under discussion: a note that has to be *found and
read* before the mistake, rather than a check that fires *at* the mistake.

### The defect: the moved delivery loop can no longer fire

`runWorkerUntilStopped` starts the worker in a goroutine and returns
immediately; the only synchronisation in this test is `waitForQueueStatus`,
which polls until the row leaves `queued`/`sending`. The commit moved the
delivery loop **above** that call, so it now reads `mailer.Sent()` micro-
seconds after the worker goroutine starts — before the worker has claimed,
rendered or sent anything (the row takes ~140 ms to resolve). It therefore
reads an empty slice on any realistic timing.

Measured, same mutation both times — `KindImportInvite` removed from
`tokenGatedKinds` and given a `tokenUngatedKinds` reason so the partition
stays intact, i.e. the token gate switched off for the one kind this test
is about:

| # | Tree | Exit | Delivery loop | Status assertion |
|---|---|---|---|---|
| K | **as committed** (loop before `waitForQueueStatus`) | 1 | **silent** — the invitation *was* delivered and it did not notice | fires, status `"sent"` |
| K2 | loop moved back below `waitForQueueStatus`, still above the status `Fatalf` | 1 | **fires** — "an invitation carrying the pre-restart confirm_token was delivered" | fires |
| R | K2's ordering, **production unmutated** | 0 | silent (correct) | passes |

K is the exact scenario the loop exists to catch, and as committed it says
nothing. Before this commit the loop was unreachable only when the status
assertion had already failed; now it is unreachable always. The `##
Verification` claim that it "can actually be the assertion that fired" is
refuted by K — it was asserted, not measured.
