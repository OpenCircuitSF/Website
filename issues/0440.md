## Description

`web/src/lib/router.test.ts`'s `parsePath` test states in its own text that it
covers **every** static PRD §5.1 route plus the auth routes. Its `cases` array
does not include `/archive`.

Found by `#0437`'s implementer while fixing the four Go-side fixtures that
omitted the same route. It did not fix this one: another agent was active in
`web/` at the time, and `#0437`'s scope named `internal/seo/` and
`internal/handlers/routes_test.go`. The restraint was correct; the omission is
still real.

## Why it matters more than one missing table row

This is the **ninth** independent account of the static route set to drift out
of agreement with production since `#0123` added `/archive`:

- `#0425` found and corrected **seven** — doc comments and prose across
  `internal/seo`.
- `#0437` found and corrected **four fixtures** in test bodies, a class `#0425`
  had not looked at.
- This is the ninth, and the first on the **TypeScript** side.

Nine drifts of one fact is not nine mistakes; it is one missing mechanism. Every
account is hand-maintained, and adding a tenth static route will drift out of
whichever of them the next author does not happen to remember.

**The specific hazard here** is that the test's own prose *claims completeness*.
A reader checking whether `/archive` is covered reads "every static PRD §5.1 /
auth route", believes it, and does not look at the array. That is worse than a
list with no claim attached to it.

### The prose claim the commit deliberately left standing — checked, and it holds

Criterion 3 lets the "parses every static PRD §5.1 / auth route" claim stay only
if criterion 2's derived check makes it true. The derived check asserts equality
with `STATIC_ROUTES`, so the claim survives **only if `STATIC_ROUTES` itself
contains the auth routes**. It does: `/login`, `/register/verify`,
`/recover/verify`, `/account`, `/admin` are all five present in the literal, and
`RouteName`'s own doc comment names exactly that set as the Phase 1 auth views.
So the equality assertion enforces auth-route coverage rather than quietly
dropping it — there is no coverage regression, and the sentence is now backed by
a test instead of by nobody.

Read against the PRD directly, the fixture is a **superset**, which is the safe
direction: PRD §5.1's table lists `/`, `/workshops`, `/archive`, `/about`,
`/subscribe`, `/subscribe/thanks`, `/confirm`, `/preferences`, `/unsubscribe`,
`/login`, `/register/verify`, `/recover/verify` — every one covered. `/account`
and `/admin` are §5.2 rows rather than §5.1, and `/privacy` (added by `#0070`)
is in neither table. So the sentence is loose about *provenance* for those
three. That looseness is **pre-existing** — the pre-`e9d239a` array held
`/privacy`, `/account` and `/admin` too — and it errs toward asserting more than
claimed, never less. Not a defect introduced here, and not worth a bounce.

### The comparison is sound, and it fails closed

`Object.entries(STATIC_ROUTES).sort()` vs `[...staticRouteCases].sort()` uses
JavaScript's default sort, which stringifies each pair — so the ordering is
lexicographic on `"path,name"`. Measured in `node` rather than reasoned about:

- a mismatched **name** and a mismatched **path** are each distinguished;
- the theoretical collision (`['a,b','c']` and `['a','b,c']` share a sort key)
  cannot produce a false **pass**, because the sort only canonicalises order —
  the assertion itself is `toEqual`, a deep structural compare, so two different
  sets can never satisfy it. A collision could at worst cause a spurious
  *failure* from ambiguous ordering, which fails closed;
- no real path or route name contains a comma, and all fifteen sort keys are
  unique, so the ambiguity is not reachable today either.

`staticRouteCases` is declared `[string, string][]` — genuine two-element
tuples, not an object or a joined string that coerces to the same text by
accident. `[...staticRouteCases]` copies before sorting, so the first test's
fixture is not mutated out from under it.

### Exporting `STATIC_ROUTES` — accepted

It widens `router.ts`'s public surface by one `Readonly<Record<string,
RouteName>>` that was already effectively public knowledge: the Go side has been
reading the same literal out of the source text since `#0071`, and
`CLAUDE.md` §1's convention puts SPA logic in `web/src/lib/` modules precisely
so it can be imported and asserted rather than restated. The alternative — a
test that re-parses `router.ts` from disk the way the Go guard does — would put
a second bespoke parser in the tree to avoid a one-word keyword, which is
`#0330`/`#0347`'s "machinery to guard machinery" trade at its worst. The
exported value is `Readonly<...>` and frozen by type rather than by
`Object.freeze`, which is the same guarantee it had as a module-private const.
No other module imports it (checked across `web/src/`), so the export is a test
seam and nothing else, and `svelte-check` reports 0 errors across 290 files.

### The Go parity guard's pattern: fortunate, but it cannot fail silently

The implementer's claim is correct — `staticRoutesBlockRe` is unanchored, so
`export const STATIC_ROUTES:` still contains the substring it matches — but the
survival is luck rather than design, and there is a second-order effect the work
log does not mention. `router.ts`'s **new doc comment now spells the literal
text the regex hunts for**, so the match no longer begins at the declaration at
all: measured with `python3` over the raw bytes, `const STATIC_ROUTES:` occurs
twice in the file, and the first occurrence (inside the doc comment) is where
the match starts. That is `CLAUDE.md` §8's "a regex that hunts for a tag finds
the one inside a comment" shape, live in this file for the first time.

It is nonetheless harmless, and the reason is the guard's own two-tier design
from `#0071`'s review — proved here rather than assumed, each probe against a
throwaway worktree:

| Probe (in the worktree) | Result |
|---|---|
| unmutated control | `TestRouteTableParity_StaticRoutes` PASS |
| an `=` added to the doc comment, no brace after it | PASS — the comment-position match fails, the engine falls forward to the real declaration |
| `= {` added to the doc comment | **FAIL, loudly** — a `routerTSParseError` reading "could not parse STATIC_ROUTES entry", naming the comment fragment it could not read; not a silent partial parse |
| regex re-anchored to `(?sm)^const` (i.e. what would have happened had it been anchored) | **FAIL, loudly** — `could not parse the STATIC_ROUTES literal` |

The `[^=]*` class cannot cross an `=`, so the capture group still starts at the
declaration's own `= {` and still yields all fifteen entries (verified: the
capture holds `'/archive': 'archive',` and fourteen siblings). And because
`parseStaticRoutesFromRouterTS` treats **any** unrecognised line as a parse
failure rather than skipping it, every way this could go wrong surfaces as "fix
the parser", never as "the tables agree". So the honest answer to "robust or
fortunate" is: the pattern's tolerance of `export` is fortunate — nothing pins
it, and the last probe shows an anchored variant would have rejected the file —
but the guard **could not have been silently disabled** by this commit, and was
not. Reported to the orchestrator as a follow-up candidate rather than folded in
(§9): if anyone wants the luck removed, the remedy is one assertion that
`staticRoutesBlockRe` finds exactly one match in `router.ts`, which would have
named the doc-comment occurrence.
