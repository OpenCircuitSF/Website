## Description

`#0186` wired `CampaignSendDialog.svelte` through `sendGuardState` and closed a
real UI-correctness gap in `handleSubmit`. Its phase-3 review passed the change
and reported three refinements. None is a live defect.

**1. The truth table's hand-rolled `normalizeCountInput` replica uses the wrong
separator class.** `CampaignSendDialog.guard.test.ts:93` writes `/[, ]/g` with an
**ASCII space (0x20)**; the real function at `web/src/lib/sendConfirm.ts:22` uses
**U+2009 thin space** (`e2 80 89`). The characters are visually identical — the
review found it by hex-dumping, which is the same trap `#0184`'s review
hex-dumped this line to avoid. It also omits the real function's
`Number.isSafeInteger` check. All 25 assertions are sound today because no case
contains a separator, and the review traced both directions to confirm it fails
*loudly* rather than silently if one is added. The fix is to stop replicating:
call `normalizeCountInput` directly, which is also what makes the old formula
genuinely "the old formula".

**2. `CampaignSendDialog` hardcodes `status: 'draft'` when calling the guard.**
Safe today — the mount gate (`sendDialogOpen && preflightSummary`),
`onOpenSend`'s `editorGuard.kind === 'ready'`, and `canSendCampaign` are all
draft-only, and nothing refetches `campaign` while the dialog is mounted. But
`CampaignStore.Send` accepts `failed` too, so the first reuse of this dialog for
a failed-campaign retry would silently feed the guard a false status. Thread
`status` in as a prop.

**3. In `blocked` and `needs-confirm`, the Send button is enabled but
`handleSubmit` silently returns.** Not a regression — it matches the component's
pre-existing `needs-confirm` pattern, and the blocked panel carries
`role="status"`/`aria-live`. But `#0119` solved exactly this in the parent with
`aria-disabled={!sendGateOpen}` plus an `aria-describedby` pointing at the
reason. Mirroring that here finishes the job `#0186` started.

## Implementation notes

**Item 1.** `web/src/views/admin/CampaignSendDialog.guard.test.ts` no longer
hand-rolls a `/[, ]/g`-plus-`\d+` replica of `normalizeCountInput` in
`oldMaySubmit`. It now imports and calls the real
`normalizeCountInput` from `lib/sendConfirm.ts` directly, so "the old
formula" is genuinely the pre-#0186 formula (minus the parsing it never
should have duplicated) rather than a second, independently-maintained copy
of it. Verified the two characters differ before touching anything:
`sendConfirm.ts:22` hex-dumps as `2f5b 2ce2 8089 5d2f 67` (U+2009,
`e2 80 89`, inside the character class) while the test's old replica at
line 93 hex-dumped as `2f5b 2c20 5d2f 67` (ASCII `0x20`) — confirmed via
`sed -n '22p' web/src/lib/sendConfirm.ts | xxd` and
`sed -n '93p' web/src/views/admin/CampaignSendDialog.guard.test.ts | xxd`
before any edit.

Added one new case, `'idle, correct count typed with a real thin-space
thousands separator'` (`audienceCount: 1482`, `confirmRaw: '1␉482'` with a
real U+2009 between `1` and `482`, constructed as `'1 482'` in source).
Hex-dumped the file afterward to confirm the byte sequence `e2 80 89`
actually landed at that line, not a lookalike ASCII space. Test count in
that file: 25 → 28 (8 → 9 cases × 3 `it.each` assertions each, plus the
one unaffected sanity test).

**Item 2.** `CampaignSendDialog.svelte` now takes `status: string` as a
prop instead of hardcoding `'draft'` in its `sendGuardState` call.
`CampaignEditor.svelte`'s single call site now passes
`status={campaign?.status ?? 'draft'}` (the `?? 'draft'` fallback only
matters for the type checker — the dialog is gated behind
`sendDialogOpen && preflightSummary`, which `onOpenSend` only sets once
`sendGateOpen`/`editorGuard.kind === 'ready'` has already required
`campaign.status === 'draft'`).

**Item 3.** Mirrored `#0119`'s treatment rather than repeating its first
(broken) attempt: the Send `<Button>` now carries
`aria-disabled={guard.kind !== 'ready'}` and
`aria-describedby="send-blocked-hint confirm-hint"`. Both ids are on
containers that are rendered **unconditionally** — only their inner content
is behind `{#if}` — so the reference never dangles in any guard state,
which is exactly the trap `#0119` shipped once and had to follow up on.
`confirm-hint` falls back to `sendGuardDescription(guard)`'s generic
`'needs-confirm'` text when the field is untouched (so it's never pointing
at empty content while `guard.kind === 'needs-confirm'`); `send-blocked-hint`
now also renders its heading text via `sendGuardDescription` rather than a
second hardcoded string, so `blocked`'s wording can't drift from the single
source of truth `#0119` established for it.
