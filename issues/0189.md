## Description

`#0186` wired `CampaignSendDialog.svelte` through `sendGuardState` and closed a
real UI-correctness gap in `handleSubmit`. Its phase-3 review passed the change
and reported three refinements. None is a live defect.

**1. The truth table's hand-rolled `normalizeCountInput` replica uses the wrong
separator class.** `CampaignSendDialog.guard.test.ts:93` writes `/[, ]/g` with an
**ASCII space (0x20)**; the real function at `web/src/lib/sendConfirm.ts:22` uses
**U+2009 thin space** (`e2 80 89`). The characters are visually identical — the
review found it by hex-dumping, which is the same trap `#0184`'s review
hex-dumped this line to avoid. It also omits the real function's
`Number.isSafeInteger` check. All 25 assertions are sound today because no case
contains a separator, and the review traced both directions to confirm it fails
*loudly* rather than silently if one is added. The fix is to stop replicating:
call `normalizeCountInput` directly, which is also what makes the old formula
genuinely "the old formula".

**2. `CampaignSendDialog` hardcodes `status: 'draft'` when calling the guard.**
Safe today — the mount gate (`sendDialogOpen && preflightSummary`),
`onOpenSend`'s `editorGuard.kind === 'ready'`, and `canSendCampaign` are all
draft-only, and nothing refetches `campaign` while the dialog is mounted. But
`CampaignStore.Send` accepts `failed` too, so the first reuse of this dialog for
a failed-campaign retry would silently feed the guard a false status. Thread
`status` in as a prop.

**3. In `blocked` and `needs-confirm`, the Send button is enabled but
`handleSubmit` silently returns.** Not a regression — it matches the component's
pre-existing `needs-confirm` pattern, and the blocked panel carries
`role="status"`/`aria-live`. But `#0119` solved exactly this in the parent with
`aria-disabled={!sendGateOpen}` plus an `aria-describedby` pointing at the
reason. Mirroring that here finishes the job `#0186` started.

## Implementation notes

**Item 1.** `web/src/views/admin/CampaignSendDialog.guard.test.ts` no longer
hand-rolls a `/[, ]/g`-plus-`\d+` replica of `normalizeCountInput` in
`oldMaySubmit`. It now imports and calls the real
`normalizeCountInput` from `lib/sendConfirm.ts` directly, so "the old
formula" is genuinely the pre-#0186 formula (minus the parsing it never
should have duplicated) rather than a second, independently-maintained copy
of it. Verified the two characters differ before touching anything:
`sendConfirm.ts:22` hex-dumps as `2f5b 2ce2 8089 5d2f 67` (U+2009,
`e2 80 89`, inside the character class) while the test's old replica at
line 93 hex-dumped as `2f5b 2c20 5d2f 67` (ASCII `0x20`) — confirmed via
`sed -n '22p' web/src/lib/sendConfirm.ts | xxd` and
`sed -n '93p' web/src/views/admin/CampaignSendDialog.guard.test.ts | xxd`
before any edit.

Added one new case, `'idle, correct count typed with a real thin-space
thousands separator'` (`audienceCount: 1482`, `confirmRaw: '1␉482'` with a
real U+2009 between `1` and `482`, constructed as `'1 482'` in source).
Hex-dumped the file afterward to confirm the byte sequence `e2 80 89`
actually landed at that line, not a lookalike ASCII space. Test count in
that file: 25 → 28 (8 → 9 cases × 3 `it.each` assertions each, plus the
one unaffected sanity test).

**Item 2.** `CampaignSendDialog.svelte` now takes `status: string` as a
prop instead of hardcoding `'draft'` in its `sendGuardState` call.
`CampaignEditor.svelte`'s single call site now passes
`status={campaign?.status ?? 'draft'}` (the `?? 'draft'` fallback only
matters for the type checker — the dialog is gated behind
`sendDialogOpen && preflightSummary`, which `onOpenSend` only sets once
`sendGateOpen`/`editorGuard.kind === 'ready'` has already required
`campaign.status === 'draft'`).

**Item 3.** Mirrored `#0119`'s treatment rather than repeating its first
(broken) attempt: the Send `<Button>` now carries
`aria-disabled={guard.kind !== 'ready'}` and
`aria-describedby="send-blocked-hint confirm-hint"`. Both ids are on
containers that are rendered **unconditionally** — only their inner content
is behind `{#if}` — so the reference never dangles in any guard state,
which is exactly the trap `#0119` shipped once and had to follow up on.
`confirm-hint` falls back to `sendGuardDescription(guard)`'s generic
`'needs-confirm'` text when the field is untouched (so it's never pointing
at empty content while `guard.kind === 'needs-confirm'`); `send-blocked-hint`
now also renders its heading text via `sendGuardDescription` rather than a
second hardcoded string, so `blocked`'s wording can't drift from the single
source of truth `#0119` established for it.

### Item 1 — verified by hex dump, in both directions

Neither the report nor an editor was trusted; the bytes were read directly.

| location | bytes | separator |
|---|---|---|
| `web/src/lib/sendConfirm.ts:22` | `2f 5b 2c` **`e2 80 89`** `5d 2f 67` | `/[,` + U+2009 + `]/g` |
| `CampaignSendDialog.guard.test.ts:89` | `27 31` **`e2 80 89`** `34 38 32 27 2c` | `'1` + U+2009 + `482',` |

The real separator class is U+2009, unchanged. The new case really does carry
`e2 80 89` — a whole-file byte scan finds that sequence at line 89 and finds no
`\u2009` escape anywhere, so it is a literal thin space in the file, not a
lookalike ASCII space and not an escape that only reads correctly in source.
(Note for the next reviewer: BSD `grep -P` on this machine silently matches
nothing rather than erroring — it reported no hits on a file that demonstrably
contains the bytes. Scan with `python3`, not `grep -P`.)

The hand-rolled replica is **gone**. `oldMaySubmit` (lines 106–110) is now
`if (c.inFlight) return false;` plus a call to the real `normalizeCountInput`,
so the `Number.isSafeInteger` gap closes with it.

**Does sharing the normalizer make the two sides agree trivially?** No, and this
was checked rather than assumed. The old side keeps its own `inFlight` bail-out
and its own `n === audienceCount` comparison; the new side is `sendGuardState`,
whose `status` / `inFlight` / `unmet` / `audienceCount === 0` branches and their
*ordering* appear nowhere on the old side. `normalizeCountInput` is the only
shared code, and it is upstream of the difference the table exists to measure —
it was never what `#0186` changed. The mutation below is the proof: if the two
sides shared the branch logic, reordering those branches could not turn anything
red, and it turns exactly two red.

One honest limit, worth recording because the file's own comment overstates it:
the new thin-space case does not *discriminate*. Both sides now call the same
normalizer, so if U+2009 support regressed, `oldMaySubmit` and `newMaySubmit`
would flip to `false` together and the `toBe` equality would still hold — the
case would stay green. The separator class is genuinely proven by execution, but
in `sendConfirm.test.ts:31`, whose `parses` table holds `['1` + U+2009 + `234',
1234]` (byte-verified here) and asserts the value positively. That is the right
place for it. The truth-table case is a reasonable belt-and-braces addition; its
comment at lines 80–83 claiming it "proves the separator class by execution" is
the part that is too strong. Reported, not bounced.

### Item 2 — the prop is right; the `?? 'draft'` fallback is the weak part

The prop threading itself is correct: `status: string` is in `Props`, in the
`$props()` destructure, and passed straight into `sendGuardState`. No `'draft'`
literal survives inside the dialog.

**When can `campaign` be nullish at the call site? Never.** The
`<CampaignSendDialog>` mount at lines 814–824 is nested inside the
`{:else if campaign}` branch opened at line 573, and line 574 in that same branch
already dereferences `{campaign.name}` with no optional chaining. So the value is
narrowed non-null there both at runtime and for `svelte-check`.

**The implementation note's justification for the fallback is empirically
false.** It says the `?? 'draft'` "only matters for the type checker". Two
experiments in the worktree, each followed by a full `npm run check`:

| form | `svelte-check` |
|---|---|
| `status={campaign.status}` (no fallback at all) | **233 files, 0 errors** |
| `status={campaign?.status ?? ''}` | **233 files, 0 errors** |

The type checker needs neither. So the fallback is unreachable dead code, and
its default was chosen in the wrong direction: `'draft'` is the **only** status
value from which `sendGuardState` can ever return `ready`, so it fails *open*.
The same component's `editorGuard` (line 204) writes `campaign?.status ?? ''`
into the very same function, and `''` yields `unavailable` — fails *closed*. The
neighbouring derivations at lines 180, 188, 190 and 193 all use `?? ''` too.

**Ruling: it does not re-create the lie, but it re-creates the literal.** It
cannot fire today, so no acceptance criterion is unmet and nothing is broken —
`#0186`'s own review passed a strictly worse version of this. But it is one
token from being right, it contradicts the file's own convention, and it is the
same "safe today, wrong under a plausible future edit" shape that produced this
issue in the first place — a maintainer hoisting the modal out of the
`{:else if campaign}` branch (a routine thing to do to a modal) would silently
hand the guard a fabricated `'draft'`. Recommended follow-up: `campaign.status`,
or `campaign?.status ?? ''` to match line 204. Reported under §9, not filed here.

### Item 3 — both ids resolve, verified by execution

`.svelte` markup carries no test coverage (`#0094`), so the component was
SSR-rendered directly (`render` from `svelte/server`, throwaway spec in the
worktree, deleted afterwards) once per prop-reachable guard state and the output
HTML inspected for the two idrefs:

| guard kind | `aria-disabled` | `send-blocked-hint` | `confirm-hint` |
|---|---|---|---|
| `needs-confirm` | `true` | present, empty | present, **"Pre-send checks pass. Confirm the recipient count to send."** |
| `blocked` | `true` | present, **"Pre-send checks have not passed. See the list below." + the unmet list** | present, empty |
| `sending` | `true` | present, empty | present, empty |
| `sending` (stale `unmet`) | `true` | present, empty | present, empty |
| `empty-audience` | `true` | present, empty | present, empty |
| `unavailable` | `true` | present, empty | present, empty |

`aria-describedby="send-blocked-hint confirm-hint"` appears in every render, and
both `id`s are in the emitted DOM in every one — **nothing dangles**, which is
exactly what `#0119` shipped broken once. `ready` is the one kind not reachable
through props (it needs the component's internal `confirmRaw` to match), but it
is closed by the same evidence: both containers survive five distinct guard
kinds, including the two whose *contents* differ, so their presence does not
track `guard` at all — and `ready` differs from `needs-confirm` only in
`confirmRaw`, which the template touches only via `bind:value`, `hint`, and
`guard`, none of which wraps a container. `Button.svelte` spreads `{...rest}`
onto the `<button>` element itself, so both attributes land on the control and
not on a wrapper.

**Is an element that exists but is empty better than a dangling reference?**
Yes, and meaningfully so here, not just cosmetically. The *announced* result is
the same — accname resolves a dangling idref to nothing, and an empty element to
nothing. Three things differ: a dangling idref is a validity error that
automated tooling flags (axe `aria-valid-attr-value`) while an empty target is
not; the description acquires text on the next state change with no id churn and
no re-announce race; and both containers carry `role="status" aria-live="polite"`,
which only works if the element is already in the DOM *before* its text arrives —
the `#0036 → #0063` live-region finding this component already cites for
`campaign-send-progress`. Removing the `{#if}` wrappers therefore improved the
live regions as a side effect, not merely the idrefs.

The one soft spot: in `sending`, `aria-disabled="true"` is announced with both
targets empty, even though `sendGuardDescription({kind:'sending'})` has a line
ready ("A send for this campaign is already in progress."). It is not a hole in
practice — the button is also natively `disabled` there and its label reads
"Sending…" — and `empty-audience` / `unavailable` are unreachable from this
dialog. Noted, not bounced.
