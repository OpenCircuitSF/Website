## Description

`claimKindsGuardMinPlausibleCallSiteCount` in
`internal/outbox/claim_kinds_call_site_guard_test.go` is a floor, set to `5`.
Its doc comment states that a full scan finds **36** call sites.

`#0483`'s review re-measured with the guard's own scan roots, prune rules, and
name matcher, and found **39** — three in-package additions since the comment
was written. Undetected for exactly the reason `#0483` documents: a floor only
catches shrinks, and 39 ≥ 5 passes silently.

**This one is worse than its two siblings**, because the stale number is not
inert. The same comment derives a further claim from it — the size of the gap
between that count and the grep oracle's 42 — and that derived arithmetic is
wrong by the same three.

## Why this is the third instance, not a coincidence

`#0483` fixed two in `internal/config/env_example_guard_test.go`:
`minLoaderVariables` claimed "exactly 20 variables today" while the real count
had reached 22, and `minScannedEnvExampleAssignments` claimed `.env.example`
"carries exactly 20 `NAME=` lines today" while it carried 22.

`#0483`'s review examined this constant at the time and **left it deliberately**,
on the reasoning that its counts sit inside a longer worked-example margin
analysis rather than a bare "floor equals today's total" claim. That distinction
is real. It then measured the analysis anyway — which is how the drift surfaced.

So the pattern is now three-for-three: every exact count written beside an
inequality in this repository has drifted, and none of them was caught by the
mechanism it was standing next to.

## Fix

Rewrote `claimKindsGuardMinPlausibleCallSiteCount`'s doc comment in
`internal/outbox/claim_kinds_call_site_guard_test.go`. The constant's value
(5) is unchanged; only the prose changed.

**Criterion 1 — re-derived, not trusted.** Wrote a standalone Go program
running the guard's own logic (`claimKindsGuardScanRoots`, the
`node_modules`/`dist` prune rule, `nameMatchesGuardedMethod`'s name match)
against the working tree: **39** total call sites (27 inside
`internal/outbox`'s own tests, 12 outside it), agreeing exactly with
`#0483`'s review figure and its exempt/non-exempt split. The stale doc
comment said 36/24/12 — the drift is entirely inside the already-exempt
population, so `claimKindsGuardMinPlausibleNonExemptCallSiteCount`'s own
count (12) was never stale and needed no change (confirmed: its 5/7
per-package breakdown still matches exactly).

Also re-derived `scripts/go_file_visit_floor_guard_test.sh`'s grep oracle
directly (running its own `count_outbox_call_sites` function, unmodified,
against the tree): **45**, not the 42 the comment cited — up by exactly the
same three the go/ast total moved, since the three additions are real
parseable Go in `internal/outbox`'s own test files (not new fixture-literal
occurrences), which grep counts identically to go/ast.

**Criteria 2 and 3 — fixed the derived arithmetic, and reshaped it so it
cannot recur.** Rather than just substituting 39/45 for 36/42 (which would
leave the *next* addition free to make the same two numbers stale again),
reframed the grep-vs-go/ast relationship as "go/ast total plus six" — six
being the count of call-site-shaped text inside
`TestClaimKindsGuardFiresOnFixtureWithNoKinds`'s raw-string fixtures, which
is intrinsic to that test's own fixture set and does not move with ordinary
call-site growth elsewhere in the tree (verified: it is still exactly 6,
unchanged since `#0303`). Whatever go/ast's total is on a given day, grep's
total is that plus six — a relationship that stays true without hand
maintenance, unlike two absolute totals that must be updated in lockstep.
The one absolute total kept in the comment (39) is explicitly marked as a
dated measurement for `#0487` (2026-09-09), not an ongoing "today" claim,
following `#0483`'s language.

**Criterion 4 — the worked example mostly does not need exact counts, and
now says so.** Two specific single-value claims in the old paragraph (the
"at most 3" worst-single-non-exempt-file figure, and "store_test.go alone
holds 20 exempt sites") supported no decision the surrounding paragraphs
did not already make more robustly, so they are gone, replaced by a
count-independent argument that is actually *stronger*: both floors are
computed by filtering the *same* `allSites` slice built by one walk
(`nonExemptCount` is that slice filtered for `!inOwnPkg`), so
`nonExemptCount <= len(allSites)` unconditionally, for any tree this guard
ever runs against — not just today's tree. Since
`claimKindsGuardMinPlausibleNonExemptCallSiteCount` (8) exceeds this floor
(5), clearing the non-exempt floor already forces the total floor to clear
too. This floor's total-population census could never independently fail a
run the non-exempt floor would pass, and that fact holds by construction,
not by measurement — it needs no re-verification as the tree grows. What
*does* still need exact figures is the grep-oracle cross-reference (the
"plus six" relationship above) and the historical drift record itself,
both kept, both now explicitly dated.

**Criterion 5 — did not raise the floor, and the slack here is closed more
completely than `#0483`'s `.env.example` precedent.** That precedent
required tracing what happens under specific mutations to show two
independent paths both close the gap. Here it is not empirical: the
subsumption argument above is a mathematical consequence of how the two
floors are computed from the same slice, true for every possible future
walk result, not merely the one measured today. Nothing here suggests
raising `claimKindsGuardMinPlausibleCallSiteCount` — its practical role was
already fully absorbed by the non-exempt floor, and inflating it to 39 (or
any other "current" number) would only reintroduce the exact defect this
issue fixes.

**Criterion 6 — see Verification below.**

Left `claimKindsGuardMinPlausibleNonExemptCallSiteCount`'s own doc comment
untouched: its counts are a worked margin analysis (as `#0483`'s review
already found), and every figure in it re-verified exactly against the
current tree, so there was nothing to fix.

## Review notes

**Verdict: approve.** Both numbers this issue turns on are wrong at the parent
commit and right at `9e20d42`, confirmed by derivations I ran myself rather
than read. The reframing that replaces the second number holds against the
drift mechanism that produced every instance in this lineage, and its residual
exposure is named inside the comment rather than hidden — the one sentence that
over-states is recorded below rather than bounced on.

**Criterion 1, re-derived independently.** A standalone program replicating the
guard's own scan roots, its `node_modules`/`dist` prune, and
`nameMatchesGuardedMethod`'s name match walked 302 `.go` files and found **39**
call sites — 27 inside `internal/outbox` (23 in its store test file, 4 in its
per-row selection test file) and 12 outside it, split 5 in `internal/handlers`
and 7 in `internal/mailing`. That is the third derivation of 39 and it agrees
with `#0483`'s review and with the implementer, including the exempt split.
Separately I extracted `count_outbox_call_sites` verbatim from
`scripts/go_file_visit_floor_guard_test.sh`, asserted the extraction was
non-empty before sourcing it (`CLAUDE.md` §8), and ran it unmodified against
the tree: **45** total and **12** non-exempt. The comment's old 36 and its
derived 42 were each stale by exactly three.

**Criteria 2 and 3 — "plus six" tested, not accepted on its word.** Compared
file by file, every file in the walk contributes the identical number to grep
and to go/ast except the guard's own file, which contributes six to grep and
zero to go/ast. Those six are exactly the fixture occurrences inside
`TestClaimKindsGuardFiresOnFixtureWithNoKinds` — one each in the arity, nil,
empty-literal and scoped fixtures, plus two in the sentinel fixture — so the
comment's account of where the gap comes from is accurate to the occurrence.
I then probed the relationship in a throwaway copy of `internal` and `cmd`:
adding one ordinary, correctly-scoped guarded call in `internal/handlers`
moved go/ast to 40 and grep to 46, leaving the difference at six. Ordinary
call-site growth — the mechanism that made 36 and 42 stale, and the mechanism
behind both of `#0483`'s instances — cannot move it. That is what makes this a
reframing rather than a fourth exact-count claim in disguise.

**Where the reframing over-states, recorded rather than bounced.** The sentence
saying the gap "moves only if" that fixture set moves is not exhaustive, and I
demonstrated both other paths in the same throwaway copy: call-shaped text in
an ordinary doc comment in `internal/handlers` took grep to 47 against go/ast's
40, a gap of seven; and two guarded calls sharing one physical source line took
go/ast to 41 against grep's 46, a gap of five. Neither is ordinary call-site
growth, and the comment already names both — the seventh-divergent-site
sentence covers the prose path and the pre-existing line-counting caveat covers
the shared-line path — so a reader who takes the paragraph whole is not
misled. Two things would still be worth tightening in a later pass: that
seventh-site warning is scoped to the comment's own paragraph when the exposure
is anywhere under the scan roots, and the word "only" claims an exhaustiveness
the next two sentences immediately withdraw.

**Criterion 4, the subsumption argument — checked, and it survives a constant
moving because it does not pretend otherwise.** Inside
`TestNoUnscopedOutboxClaimCallOutsidePackage` the non-exempt tally is the same
`allSites` slice filtered on `!inOwnPkg`, built by one walk, so it can never
exceed that slice's length; the floors are 5 and 8, so a total below 5 forces a
non-exempt count below 8 and the sibling floor would have failed too. The
argument is therefore structural rather than measured, and it holds for any
future walk. Its precondition is the constants' ordering, and the comment
states it outright — twice, once as "while 8 stays above 5" and once as the
deliberate future change that would break it — so it cannot quietly become
false the way a measured claim would. Dropping the two single-value figures the
old paragraph leaned on was the right trade: they justified a margin that this
argument justifies without any number at all.

**Criterion 5, no floor raised.** Both constants read 5 and 8 at the parent
commit and at `9e20d42`. Stronger than that: everything in the file from the
first constant's own declaration line through end of file is byte-identical to
the parent, so no guard behaviour changed, and
`claimKindsGuardMinPlausibleNonExemptCallSiteCount`'s doc comment is untouched.
Leaving this floor at 5 is right for the reason the new comment gives — its
practical bite is already absorbed by the sibling floor, and inflating it to
today's total would reintroduce precisely the defect being fixed.

**Criterion 6, mutation reproduced.** In a throwaway worktree pinned to
`9e20d42`, never the shared tree (`CLAUDE.md` §8a), I narrowed the scan roots
to the sibling config package and ran the guard:

```

    found only 0 ClaimDue/OrphanSweep/SelectDue call site(s) under [../config], want at least 5
```

The failing check is this constant's own — it runs before the non-exempt tally
is ever computed — so this is a proof of this floor firing, not its sibling's.
Restored from a copy taken before the mutation and confirmed byte-identical by
`shasum -a 256`, same digest before and after, with the worktree reporting a
clean status for that path.

**The dated-measurement language reads clearly, with one blemish.** The
paragraph carrying 39 is headed as historical, names its measuring issue and
date, and closes by telling the reader not to read 39 or any other count in the
comment as a claim about today — that is honest, and it is the same shape
`#0483` settled on. The blemish is in the grep paragraph, which writes "39 plus
six is 45 today" and so attaches the word the earlier paragraph disclaims to
the very figures it disclaims. It is a wording tension rather than a false
statement, since the disclaimer is blanket and comes first, but the word should
go.

**A fourth instance of this pattern exists, in a third file — reporting, not
filing (`CLAUDE.md` §9).** `scripts/go_file_visit_floor_guard_test.sh`'s
`count_outbox_call_sites` doc comment carries the same shape beside the same
population: it states that the function measures 42 and that the Go guard's own
comment measures 36 by go/ast, and both figures are the stale ones this issue
corrected. It was already false before `9e20d42`, so nothing here caused it,
but the two files now disagree with each other and the shell file names the Go
declaration whose comment it mis-describes. Worth an issue of its own, and
worth reframing the same way rather than re-substituting 45 and 39.

**One latent instance that is currently accurate, so not a defect today.**
`claimKindsGuardMinPlausibleNonExemptCallSiteCount`'s own comment states 12
non-exempt sites with a 5-and-7 package split and a per-file breakdown beside
it. I re-measured every figure: all exact, matching my walk site for site. That
is the same judgement `#0483`'s review reached about it, and leaving it
untouched here was correct.
