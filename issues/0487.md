## Description

`claimKindsGuardMinPlausibleCallSiteCount` in
`internal/outbox/claim_kinds_call_site_guard_test.go` is a floor, set to `5`.
Its doc comment states that a full scan finds **36** call sites.

`#0483`'s review re-measured with the guard's own scan roots, prune rules, and
name matcher, and found **39** — three in-package additions since the comment
was written. Undetected for exactly the reason `#0483` documents: a floor only
catches shrinks, and 39 ≥ 5 passes silently.

**This one is worse than its two siblings**, because the stale number is not
inert. The same comment derives a further claim from it — the size of the gap
between that count and the grep oracle's 42 — and that derived arithmetic is
wrong by the same three.

## Why this is the third instance, not a coincidence

`#0483` fixed two in `internal/config/env_example_guard_test.go`:
`minLoaderVariables` claimed "exactly 20 variables today" while the real count
had reached 22, and `minScannedEnvExampleAssignments` claimed `.env.example`
"carries exactly 20 `NAME=` lines today" while it carried 22.

`#0483`'s review examined this constant at the time and **left it deliberately**,
on the reasoning that its counts sit inside a longer worked-example margin
analysis rather than a bare "floor equals today's total" claim. That distinction
is real. It then measured the analysis anyway — which is how the drift surfaced.

So the pattern is now three-for-three: every exact count written beside an
inequality in this repository has drifted, and none of them was caught by the
mechanism it was standing next to.

## Acceptance criteria

1. **Re-derive the count yourself**, with the guard's own scan roots, prune
   rules, and name matcher — not with an ad hoc `grep`. `#0483`'s review put it
   at 39 against a documented 36; treat that as a claim to check, not an
   authority. This lineage has had several premises corrected by measurement.
2. **Fix the derived arithmetic too.** The gap-to-42 claim depends on the stale
   number, so correcting one number without the other leaves the comment
   internally inconsistent — a worse state than now.
3. **Apply `#0483`'s resolution**, whatever you conclude the right shape is:
   an exact-count sentence must not sit beside an inequality check. `#0483`
   chose to drop the count and say explicitly that the prose names no current
   total on purpose. Follow that unless you can say why this comment differs.
4. **Decide whether the worked example needs a count at all.** It exists to
   justify the margin between the floor and reality. If the argument survives
   without exact numbers, removing them is the durable fix; if it does not, say
   what keeps them honest.
5. **Do not raise the floor to today's total** as a side effect. `#0483`
   established that a floor with slack is not a defect when the loss it would
   miss is closed by a sibling guard — check whether that holds here, and say so
   either way.
6. **Prove the guard still fails on a genuine removal.** Mutate a copy, never
   `git stash` (`CLAUDE.md` §8a), and restore byte-identically with SHA-256.
