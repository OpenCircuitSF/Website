## Description

`#0058`'s auto-reply detector treats any one of six header signals as
sufficient to classify an inbound message as machine-generated and skip it.
Five of the six are sound. The sixth, `Precedence: list`, is not a
machine-generation signal at all — it marks mail as having passed through a
list manager, which is orthogonal to whether a human wrote it.

A person who replies to an Open Circuit campaign from an address that relays
through a mailing list, a group alias, or a corporate distribution list can
therefore have a genuine unsubscribe request classified as an auto-reply.

## Why the failure is not neutral

The no-match and auto-reply paths both do the right thing structurally — log,
leave the object in S3, return 200 (`#0058` criterion 5, which exists to stop
SNS redelivery looping). The consequence is that a real unsubscribe request
lands in a bucket and **nothing surfaces it**. See `#0499`, which is the
companion defect: there is no reviewer for parked objects, so the 30-day
lifecycle rule eventually deletes the evidence that the request ever arrived.

An unsubscribe request that is silently dropped is the one failure this
subsystem exists to prevent. CAN-SPAM treats unsubscribe handling as
mandatory, and `CLAUDE.md` §9 already records that this project does not get
to be casual about it.

## Suggested remedies, either acceptable

1. **Drop `list` from the `Precedence` set**, keeping `bulk`, `auto_reply` and
   `junk`. Simplest, and the three retained values are all genuinely
   machine-generation markers.
2. **Require a second, independent signal** when `Precedence: list` is the only
   one present — so a list-relayed message still needs, say, an
   `Auto-Submitted` or a null `Return-Path` before being skipped.

Whichever is chosen, add a test proving a human-written message carrying
`Precedence: list` and a resolvable unsubscribe token **is** processed.

## Acceptance criteria

1. A message whose only auto-reply signal is `Precedence: list`, carrying a
   valid token, results in an unsubscribe and an audit row with
   `source = 'mailto'`.
2. `bulk`, `auto_reply` and `junk` continue to classify as auto-replies, each
   with a test case.
3. The chosen remedy is recorded in the detector's doc comment, so the next
   reader knows `list`'s absence is deliberate rather than an oversight.
4. Do not weaken the ordering `#0058` established: the auto-reply check still
   runs **before** any token or `From:` matching.

## Root cause

`internal/inbound.isAutoReply` (`#0058`) classified `Precedence: list` as
sufficient on its own to mark a message machine-generated, alongside `bulk`,
`auto_reply`, and `junk`. Unlike those three, `Precedence: list` only records
that a message passed through a list manager (a group alias, a corporate
distribution list, a mailing-list relay) — it says nothing about whether a
human typed the message. A person replying to a campaign through such a relay
therefore had a genuine unsubscribe request classified as an auto-reply,
logged, and left in S3 with no reviewer to notice (`#0499`).

## Fix

Chose **remedy 1** from the two the issue named: dropped `list` from the
`Precedence` switch in `isAutoReply`, keeping `bulk`, `auto_reply`, and
`junk`. Went with the simpler remedy rather than requiring a second signal
(remedy 2) because the three retained values have no equivalent hazard — no
ordinary person's reply carries `Precedence: bulk`, `auto_reply`, or `junk` —
so removing only `list` closes the gap cleanly without inventing a
combination rule for the other three, and without weakening the detector's
existing any-one-sufficient structure that `#0058`'s review already approved.
Recorded the decision (and the reasoning above) directly in `isAutoReply`'s
doc comment, per acceptance criterion 3.

No changes to `internal/handlers/ses_inbound.go`: the auto-reply check
already runs before any token/`From:` matching (`#0058`'s ordering), and
narrowing `isAutoReply`'s inputs doesn't touch that call order — acceptance
criterion 4 holds by construction, confirmed by
`TestSESInboundHandler_AutoReply_IgnoredEvenWithAValidToken` (unchanged)
still passing.

Test changes:

- `internal/inbound/parse_test.go` — table-ized
  `TestIsAutoReply_PrecedenceBulk` with a `want` field per `Precedence`
  value: `true` for `bulk`, `auto_reply`, `junk`; `false` for `list`
  (acceptance criteria 1 and 2, at the unit level).
- `internal/handlers/ses_inbound_test.go` — added
  `TestSESInboundHandler_PrecedenceList_HumanReplyStillUnsubscribes`: a
  message whose only signal is `Precedence: list`, carrying a valid token,
  results in a 200, `subscribers.StatusUnsubscribed`,
  `UnsubscribeSource = subscribers.SourceMailto`, one `audit_log` row with
  `metadata->>'source' = 'mailto'`, and the S3 object deleted (acceptance
  criterion 1, at the handler level).

## Review notes

Reviewed `a6fb25e` independently (Opus, phase 3). Approved on the first pass;
no escalation question arose, so per `CLAUDE.md` §3 implementation stays on
Sonnet.

**The remedy choice is sound on its own merits, not merely permitted.** The
three retained `Precedence` values and the dropped one differ in kind, not in
degree. `bulk`, `auto_reply` and `junk` are stamped by the *generator* of a
message and are vanishingly rare on anything a person typed; `list` is stamped
by a *relay* the message merely traversed, so it carries no information about
authorship at all. That is the same distinction `#0058`'s own reviewer drew
when it reported this defect, and remedy 2's combination rule would have added
a second code path to express a fact that is better expressed by not asking
the question. Recorded in `isAutoReply`'s doc comment per criterion 3, with
`ParsedMessage.AutoReply`'s field comment forwarding to it — both readers'
entry points covered.

**Mutation verification, run independently rather than taken on trust.**
Against a private scratch database (`scripts/testdb.sh create 0498rv`, dropped
after), `internal/inbound/parse.go` copied aside to the scratchpad first and
restored from that copy afterwards, byte-identity confirmed by `shasum -a 256`
(`449ca325…f96b08` before and after; the working tree showed only
`issues/0498.md` modified throughout). Two mutations, one per direction:
