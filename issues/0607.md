## Description

The revised workflow (`issues/Issues.md`, "Build / verify command", Tiers)
has the implementer check that the change compiles before running any tests.
`scripts/check.sh` has no mode for that, so an implementer either runs a
full scoped run and finds the compile error at the end, or hand-rolls
`go build`/`go vet`/`npm run check`.

## Acceptance criteria

- [ ] `scripts/check.sh build` runs `go build ./...`, `go vet ./...` and
      `(cd web && npm run check)`, through the existing `runpipe`/`run`
      accounting, and prints the usual `VERIFICATION PASSED`/`FAILED` verdict.
      It runs no tests, needs no database, and does not create one even when
      `ISSUE` is set.
- [ ] The header comment's mode list and `AGENTS.md` §5's command block name
      the new mode and say it never counts as verification.
- [ ] `scripts/check_guard_test.sh` covers the new arm: a sandbox copy with a
      Go compile error and one with a `svelte-check` error each report
      `VERIFICATION FAILED` with a non-zero exit.
- [ ] `issues/Issues.md`'s Tiers table drops the "until it lands" fallback.
- [ ] Verified with `scripts/check.sh build`, `scripts/check.sh guards`, and
      `ISSUE=0607 scripts/check.sh go ./internal/db/... ./internal/handlers/...`
      (`AGENTS.md` edit). Zero skips.
