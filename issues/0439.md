## Description

`internal/seo` carries an idiom — *"nil until `#NNNN` lands"* — written when
those issues were open. `#0425` replaced two instances with the **real**
condition (nil only under `STORAGE=json`), which a review verified end to end
and endorsed, because a condition cannot go stale the way an issue reference
can.

**Two instances remain, and one is worse than stale.**

1. **`NewRenderer`'s doc comment** (`internal/seo/seo.go`) carries the same
   idiom. Left deliberately by `#0425`'s third pass — out of its prescribed
   scope, correct discipline.
2. **`WorkshopSource`'s interface doc** (`internal/seo/workshop.go`) states that
   `#0051` **"has not landed yet"** and that `#0054` **"is expected to wire the
   real implementation in"**.

Both issues are `resolved`, and **`workshopSEOSource` is what `#0054` wired**.

### Why the second is a different category

A stale issue reference is a pointer that has rotted. This is a **claim about
the present state of the system that is false** — an interface's own contract
telling a reader the implementation does not exist, when it does and is in the
same repository.

A reader trusting it would conclude the workshop source is unimplemented and
either duplicate it or work around a nil that never occurs in the Postgres path.

Confirmed by the orchestrator: `workshop.go` carries "`#0054` is expected to
wire the real implementation in."

## The fix, and the precedent to follow

`#0425` established the shape: **replace the issue-relative claim with the
condition it was standing in for.** `buildSEOSite`'s doc comment
(`cmd/opencircuit/main.go`) already carries the accurate form for the same fact,
and a review verified it: `DevMode()` is literally `Storage == "json"`;
`servePostgres` passes struct values, so non-nil unconditionally; `serveDevMode`
is the only other caller and passes `nil, nil`.

**Do not simply update the issue numbers.** That reproduces the defect with a
later expiry date.

## Leave these alone
The two **quotations** of `#0020`'s Notes — in `workshop.go` and
`sitemap_test.go` — are correct **as attributed quotations** of what that issue
said at the time. `#0425`'s reviewer confirmed this specifically. Rewriting a
quotation to match present reality would falsify a record, which is `#0271`'s
`## Scope` rule.

Distinguishing them from the defect above is part of the work.

### The claim is true — every construction site enumerated

Verified independently rather than accepted from the work log. `internal/seo`
exports exactly three constructors that take a `WorkshopSource`/`ArchiveSource`
— `NewSite`, `NewRenderer`, `NewSitemap` — and `NewSite` is the only one any
non-test code outside the package calls. Across the whole tree there is exactly
one non-test call: `buildSEOSite`'s, in `cmd/opencircuit/main.go`.

`buildSEOSite` in turn has exactly two non-test callers, and the dispatch
between them is total and exclusive:

| Path | Argument | Reachable when |
|---|---|---|
| `servePostgres` | `workshopSEOSource{store: workshopsStore}`, `campaignArchiveSEOSource{store: campaignsStore}` — struct values, so the interface is non-nil whatever the stores hold | `!cfg.DevMode()` |
| `serveDevMode` | literal `nil, nil` | `cfg.DevMode()` |

`serve` branches on `cfg.DevMode()` and returns from one or the other with no
third arm; `Config.DevMode()` is `return c.Storage == "json"`. `servePostgres`'s
call sits at one tab of indentation — no enclosing conditional — and
`TestServePostgres_OneSEOSiteFlowsToEveryConsumer`'s companion AST guard already
fails the build if that call count is anything but exactly one. So on the
Postgres path the source is non-nil unconditionally, and the only way to reach
a nil one is `STORAGE=json`. **No fourth path exists.**

The one wrinkle worth naming: test files *do* pass `nil` — eleven
`buildSEOSite` call sites in `cmd/opencircuit`'s wiring tests and roughly
fifteen `NewSite`/`NewSitemap`/`NewRenderer` calls inside `internal/seo` itself.
Read with maximum literalism, "nil only under `STORAGE=json`" is in tension with
that. I do not treat it as a new false assertion, for three reasons: those tests
pass nil precisely to exercise the `STORAGE=json`-shaped configuration, so they
instantiate the condition rather than contradict it; the sentence sits in a
constructor doc describing how the program wires itself, which is the register a
reader takes it in; and `#0425` shipped the identical phrase on `NewSite` and a
review endorsed it, so changing it here would put the three sibling
constructors out of step with each other for no gain. Recorded so a future
reader knows it was considered, not overlooked.

### It does match `#0425`'s endorsed pattern

`#0425` wrote "nil only under STORAGE=json, which has no workshops-table

`NewRenderer`'s sentence does read a little heavily — "source may be nil -- nil

### `archive.go`'s near-miss — I disagree with the reading, and still pass

Judged independently, as asked. `ArchiveSource`'s doc says "`#0123`'s real store
is expected to be wired in from the start (unlike `WorkshopSource`'s staged
`#0051`/`#0054` rollout)". `#0123` is resolved and `campaignArchiveSEOSource` is
wired unconditionally in `servePostgres`, so the expectation has been met.

The implementer's defence is that this is a permanent design contrast rather
than a forward-looking promise. The contrast is real and worth keeping — the
archive store genuinely was never staged behind a nil placeholder the way the
workshop store was — but **the tense does not carry it**. "Is expected to be
wired in" is present tense about a future event, and it is the same construction
as the sentence this issue had removed four files away. A reader arriving from
`sitemap.go`'s "nilable, see ArchiveSource doc (#0123)" can take it as a claim
that the archive store is not yet wired, which is the precise harm the issue's
own "Why the second is a different category" section names.

The remedy is one word — `is expected to be wired in` → `was wired in` — which
preserves the contrast intact and removes the forward-looking claim.

I am **not** bouncing for it, because file scope here has a precedent and it
points the other way. `#0425`'s third pass deliberately left `NewRenderer`'s
sibling alone as out of its prescribed scope, this issue's own Description calls
that "correct discipline", and `#0425`'s reviewer reported the `WorkshopSource`
instance for filing rather than widening its own issue — which is how `#0439`
came to exist at all. `archive.go` is a third file, named by neither of this
issue's two instances, and criterion 4 asks for the sweep to be *reported*.
Applying the same discipline: reported for filing (§9), with the remedy above
written out so the follow-up is transcription.

### The no-test decision stands

Upheld, with one correction to the reasoning. The work log says adding a pin
"would mean introducing new test surface in `cmd/opencircuit`" — that overstates
it. `servePostgres`'s existing AST guard already binds the single `buildSEOSite`
`*ast.CallExpr` in a local variable, so asserting its second and third arguments
are not the identifier `nil` would be a handful of lines inside a scan that
already walks exactly these call sites, not a new file or a new mechanism.

It should still not be added, for the reason criterion 5 gives rather than the
one offered. Criterion 5 forbids a mechanism outright, and two prior reviews
reached that independently. The property such an assertion would pin is not the
property that matters — the one that matters, that one `*seo.Site` reaches every
consumer, is already guarded — and a change making `servePostgres` pass nil
would be a deliberate design change made in the same function whose own
`buildSEOSite` doc comment states the dev-mode-only rule three lines above.
Adding a guard whose subject is the truth of a doc comment is the shape §8
records as buying one more bounce per pass. The conclusion is right; the
justification is that criterion 5 was correctly decided, not that the assertion
would have been expensive.
