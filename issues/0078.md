## Description

`internal/mailing`'s golden files compare against output containing CRLF line endings, but `.gitattributes` declares `* text=auto eol=lf`, so the committed blobs are LF. The working tree keeps whatever was written locally, so `git status` stays clean and the tests pass **on the machine that wrote them**.

A fresh clone or worktree gets LF and fails:

```
TestBuildConfirmationEmail_Golden
TestBuildAlreadySubscribedEmail_Golden
TestBuildRegistrationEmail_Golden
TestBuildRecoveryEmail_Golden
```

Found during `#0026`'s review, which built a throwaway worktree at `c0cff5d` and hit it. It arrived with `#0028` and predates `#0026`.

> 🟢 Resolved 2026-08-19 — Re-verified by `git clone`, not a worktree: a throwaway clone of the repository at pre-fix `4fc52ed` gets LF fixtures and fails all four `TestBuild*Email_Golden`, while the same clone procedure at a commit containing `0e80b9f` gets `with CRLF line terminators` on all four `.txt` fixtures, a clean `git status`, and 30/30 mailing tests passing — so the defect is genuinely closed for CI and for anyone who clones, not merely for a worktree that shares this repository's object store. The checkin-versus-checkout insight is correct and was reproduced independently in a scratch repository: `text=auto eol=lf` strips CR at **checkin** (blob LF, working tree still CRLF, `git status` clean — exactly how `#0028` introduced this), and no checkout or clone ever strips CR from an already-CRLF blob, so the naive revert-and-checkout mutation would have produced a false negative. `-text` over normalising `goldenFile()` is the right call and for the stated reason: these four fixtures are the **only** assertion of the `\r\n` contract anywhere in the repo, so a normalising comparison would have left `renderText()`'s RFC 5322 line endings covered by nothing at all.

## Why it matters more than four tests

This project's verification contract (`CLAUDE.md` §5) rests on the suite being green and meaningful. A suite that passes only on the machine that authored it is neither — it will fail on CI, on the deploy host, and for anyone else who clones. It also means **every "zero failures, zero skips" claim recorded since `#0028` was true locally and false elsewhere**, which is precisely the class of "green but proves nothing" defect this project keeps finding.

## Fix

`internal/mailing/testdata/*.txt` are the only fixtures in the package that
are actually CRLF-sensitive — `emailContent.renderText()`
(`internal/mailing/templates.go`) joins lines with a literal `"\r\n"`,
matching RFC 5322 mail body line endings and this project's other
plain-text sends (`internal/auth`). `emailContent.renderHTML()` joins with
plain `"\n"`, and `file(1)` confirms the four `.html` goldens have zero CR
bytes, so only the `.txt` files needed the override.

Added a rule to `.gitattributes`, after the binary-files block and
overriding the repo-wide `* text=auto eol=lf`:

```
internal/mailing/testdata/*.txt -text
```

`-text` unsets the `text` attribute for these four paths so git neither
normalises them to LF on checkin nor rewrites them on checkout, while still
leaving them diffable (unlike `binary`, which also disables `-diff`). Then
`git add --renormalize internal/mailing/testdata/*.txt` re-staged them under
the new attribute, and `git show :path | file -` confirmed the staged blobs
now actually contain CRLF (they didn't before — the pre-fix committed blobs
were LF, per the reproduction below). Added
`internal/mailing/testdata/README.md` explaining why the `.txt` files are
CRLF and telling a future editor not to remove the override.

## Gotchas

**Decision: `-text`, not normalising the comparison.** `goldenFile()` in
`templates_test.go` could instead do `strings.ReplaceAll(got, "\r\n",
"\n")`-style normalisation before comparing, letting the fixtures be
ordinary LF files git treats like everything else. Rejected that because
the fixture's entire job is to be a faithful record of the real
`TextBody` bytes `SESMailer` sends — `renderText()` chose `\r\n`
deliberately (comment at `templates.go:189`, matching `internal/auth`'s
existing plain-text sends and RFC 5322). Normalising the comparison would
make the test pass on a body with the *wrong* line ending: someone could
change `renderText()` to join with bare `\n` — breaking the actual RFC
5322 mail body contract — and the golden test would keep passing, silently.
That's a worse failure mode to leave lying around than an occasional
`UPDATE_GOLDEN=1` regeneration. The cost of `-text`/`binary` is exactly
what this issue is about: it opts these four paths out of git's line-ending
safety net, so a future contributor must remember `UPDATE_GOLDEN=1`
regenerates from Go code (always correct) rather than hand-editing the
fixture in an editor that might auto-convert line endings on save — noted
explicitly in the new README so nobody "tidies" the attribute away again.

**`-text` vs `binary`:** used `-text` rather than `binary`. `binary` is a
macro for `-diff -merge -text`, which would make `git diff` on these four
files opaque ("Binary files differ") — worse for code review of template
changes than the current line-count-preserving diff, which at least shows
which lines changed even though every line appears touched due to the
trailing `\r`. `-text` alone gets the normalisation opt-out without losing
diffability.

**The mutation test taught a real lesson about git internals**: naively
reverting `.gitattributes` and re-checking-out an *already-committed* blob
does **not** reproduce the bug, because `eol=lf` checkout smudging doesn't
retroactively strip CR from a blob that's already stored with CRLF — the
normalisation that caused the original defect happens at **checkin**, not
checkout. The valid mutation had to re-stage (`git add --renormalize`) the
CRLF working files under the reverted attribute to actually reproduce the
LF-blob defect, which is a more accurate mental model for how `#0028`
introduced this in the first place: whoever committed these fixtures ran
`git add` against a CRLF-on-disk file while `.gitattributes` said `text=auto
eol=lf` with no override, and git silently normalised it away at that
moment.

**One follow-up worth considering, not a blocker.** The `\r\n` contract now rests

only through a fixture whose byte-exactness depends on git configuration. Cheap
insurance for a contract nothing else guards.

## Notes

The underlying reason the goldens need CRLF is that email bodies use it — `multipart/alternative` parts are CRLF-delimited per RFC 5322. So the fixtures are genuinely byte-sensitive rather than accidentally so, which is the argument for `binary` over trying to make the tests line-ending-agnostic.

Consider whether the test should normalise before comparing instead. Either is defensible; make the choice deliberately and record it.
