## Description

`internal/mailing`'s golden files compare against output containing CRLF line endings, but `.gitattributes` declares `* text=auto eol=lf`, so the committed blobs are LF. The working tree keeps whatever was written locally, so `git status` stays clean and the tests pass **on the machine that wrote them**.

A fresh clone or worktree gets LF and fails:

```
TestBuildConfirmationEmail_Golden
TestBuildAlreadySubscribedEmail_Golden
TestBuildRegistrationEmail_Golden
TestBuildRecoveryEmail_Golden
```

Found during `#0026`'s review, which built a throwaway worktree at `c0cff5d` and hit it. It arrived with `#0028` and predates `#0026`.

## Why it matters more than four tests

This project's verification contract (`CLAUDE.md` §5) rests on the suite being green and meaningful. A suite that passes only on the machine that authored it is neither — it will fail on CI, on the deploy host, and for anyone else who clones. It also means **every "zero failures, zero skips" claim recorded since `#0028` was true locally and false elsewhere**, which is precisely the class of "green but proves nothing" defect this project keeps finding.

## Acceptance criteria

- [ ] `internal/mailing/testdata/*.txt` (and any other CRLF-sensitive fixture) marked `-text` or `binary` in `.gitattributes` so git stops normalising them
- [ ] The files recommitted with the byte content the tests actually require
- [ ] **Proven from a clean checkout**: clone or `git worktree add` to a fresh path, run `go test ./internal/mailing/...`, and show it passing — the whole point is that it currently does not
- [ ] Mutation-proven: revert the `.gitattributes` entry, confirm a fresh worktree fails again, restore
- [ ] A brief note in `docs/` or the package explaining why these fixtures are byte-sensitive, so nobody "tidies" the attribute later
- [ ] `go test ./... -count=1` green in **both** the existing tree and a fresh one

## Notes

The underlying reason the goldens need CRLF is that email bodies use it — `multipart/alternative` parts are CRLF-delimited per RFC 5322. So the fixtures are genuinely byte-sensitive rather than accidentally so, which is the argument for `binary` over trying to make the tests line-ending-agnostic.

Consider whether the test should normalise before comparing instead. Either is defensible; make the choice deliberately and record it.
