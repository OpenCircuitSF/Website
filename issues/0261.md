## Description

```go
e := &audit.Entry{Action: …}
e.Metadata["email"] = addr    // silent pass
```

`compositeLitAssignedIdents` never unwraps the `*ast.UnaryExpr`, so an entry
taken by pointer is invisible to the walk. **Both** mutation forms are blind
under a pointer — the field assignment (`e.Metadata = …`) as well as the index
assignment `#0257` just closed.

**Inherited, not introduced.** `#0257`'s change is correct for the value form;
this is the same gap one indirection out, and it predates that pass. Latent —
no production site takes an `audit.Entry` by pointer today.

**A second scope observation from the same review, worth folding in:**
mutation is not only assignment. `maps.Copy(e.Metadata, src)` and
`delete(e.Metadata, k)` both change the map without an assignment statement
anywhere, so neither helper sees them. `maps.Copy` in particular could
introduce an email key from a variable the guard never inspects.

## Notes

Reported by `#0257`'s phase-3 review under `CLAUDE.md` §9. Ninth shape found in
this file across eight review rounds.

**That review also settled a question worth recording**, because it was the
open design argument in `#0257`: it verified the read/walk split is real, not a
rationalisation. Every shape that has ever escaped this guard escaped because
the **walk matched nothing** — not because a classifier saw something and
shrugged. So inverting the reader's default would not have prevented any of the
nine. That is the strongest argument yet for the current approach, and it also
says what the *right* generalisation is: the walk needs to recognise **mutation
of a `Metadata` map by any means**, not one more node type at a time.

`maps.Copy` and `delete` are the concrete evidence that assignment-shaped
thinking is the limit — they are mutations with no assignment to match.

**`go/ast` vs. `go/types`, per `#0282`'s question, answered rather than
skipped.** `#0282` asks whether a sibling AST guard should use `go/types`
instead of a bare `go/ast` shape match, since "is this a `Kind`" is a type
question. The equivalent question here is "is `isBuiltinDeleteCall` /
`isMapsCopyCall` / `isAuditEntryType` matching the right thing by name
alone" — and the answer for this pass is that a `go/types`-based rewrite
would be strictly more work for no behavioral change today, for a reason
`#0282`'s guard does not share: **this whole file already runs on
`parser.ParseFile` with `mode 0`, never type-checked**, deliberately (see the
`writeSyntheticGoFile` doc comment: "go/parser only checks syntax, never
resolves imports, so these fixtures need no real audit package on disk") —
every synthetic fixture in this file is a bare `package fixture` file that
does not import `audit`, `maps`, or anything else, and would fail to
type-check if it were ever run through `go/types`. Switching only the two
new matchers to `go/types` while leaving `isAuditEntryType` (which has the
identical "match the literal package identifier" shape and has stood since
`#0237`) on `go/ast` would be an inconsistent half-measure; switching the
whole file would mean giving up synthetic single-file fixtures entirely, a
materially larger and unrelated change. The approximation is checked, not
assumed, the same way `isAuditEntryType`'s own doc comment checks it: no file
in this tree shadows the builtin `delete` or imports `maps` under an alias
(`grep -rn 'func delete(\|delete :=' internal cmd --include='*.go'` and a scan
of every `"maps"` import find nothing). If a future shape needs real type
resolution — `#0282`'s untyped-constant case is a good example of one that
would — that is a deliberate, reviewed change to this file's whole parsing
strategy, not a byproduct of this pass.

## Root cause

Two independent gaps, both confirmed by running the exact fixtures through
`scanAuditEntrySites` before writing any fix (see `## Verification`):

1. **The pointer form.** `compositeLitAssignedIdents` mapped an
   `audit.Entry{}` composite literal back to the identifier it was assigned
   to only when the assignment's RHS was an `*ast.CompositeLit` directly.
   `e := &audit.Entry{...}` has RHS `*ast.UnaryExpr{Op: token.AND, X:
   <the literal>}`, so the type assertion failed and no entry was ever
   recorded for `cl` in the returned map. `collectDeferredMetadataFieldIdents`
   was **not** the affected half — `e.Metadata = ...` is the identical
   `*ast.SelectorExpr` whether `e` holds a `*audit.Entry` or an `audit.Entry`
   (Go's selector syntax does not distinguish, and `go/parser` never resolves
   types), so it already saw the deferred mutation correctly. The lookup in
   `scanAuditEntrySites` (`literalIdents[cl]`) simply never found a key for
   the pointer-held literal, so the deferred-mutation check never ran and
   classification fell through to the literal's own (empty or unrelated)
   `Metadata`.
2. **`maps.Copy` and `delete`.** `collectDeferredMetadataFieldIdents` only
   ever inspected `*ast.AssignStmt` nodes. `delete(e.Metadata, k)` and
   `maps.Copy(e.Metadata, src)` are `*ast.CallExpr`s with no assignment
   anywhere, so neither was visible to the walk at all — not caught, not
   reported unresolved, simply never inspected.

## Fix

- **`compositeLitAssignedIdents`** now unwraps a single leading `&`
  (`*ast.UnaryExpr` with `Op == token.AND`) before the `*ast.CompositeLit`
  type assertion, so `ident := &audit.Entry{...}` and
  `ident = &audit.Entry{...}` are connected to `ident` the same way the value
  forms already are. `collectDeferredMetadataFieldIdents` needed no change
  for this half, per `## Root cause`.
- **`collectDeferredMetadataFieldIdents`** now also recognizes
  `delete(ident.Metadata, ...)` and `maps.Copy(ident.Metadata, ...)` as
  deferred mutations, matched by call shape alone (`isBuiltinDeleteCall`,
  `isMapsCopyCall`) with neither call's arguments inspected — the same
  conservative non-inspection its existing assignment cases already use.
  Both report the site `unresolved`, the guard's existing default for
  "cannot prove what the running code ends up with". `delete` cannot itself
  introduce a key (only remove one), so its own risk direction is a stale
  `hasEmail=true` rather than a silent pass, but the guard's answer to
  "cannot resolve" does not depend on which direction a specific gap points,
  so both calls are treated identically rather than reasoned about per case
  — satisfying acceptance criterion 2 as "handled: reported unresolved".
- The deferred-mutation failure message, previously "a struct-field
  assignment (%s.Metadata = ...) appears...", was reworded to "a Metadata
  mutation (%s.Metadata = ..., %s.Metadata[...] = ..., delete(%s.Metadata,
  ...), or maps.Copy(%s.Metadata, ...)) appears..." so it stays true now that
  two of the four recognized shapes are calls, not assignments.
- Added a new `#0261` header paragraph (this file's established
  falsifiable-boundary style) documenting both fixes, that no production site
  uses any of the four shapes today, and the re-derived census.
- **Addressed `#0275`'s fail-open hole for this one guard** (not the shared
  `walkGoFiles`/`citedTestScanRoots` infrastructure — that is `#0275`'s own,
  separate fix across all five guards in the family): added
  `auditEmailMetadataMinPlausibleFileCount` (150) and `countVisitedGoFiles`,
  and wired an assertion into `TestAuditEntryEmailMetadataMatchesKnownSites`
  that fails closed if `auditEmailMetadataScanRoots` is empty, or if the walk
  visits fewer than 150 `.go` files — chosen because the real tree has 249
  files under this guard's roots today and the single largest subdirectory
  (`internal/handlers`) has 95, so 150 sits below the real total (room to
  shrink without a false alarm) while still tripping on a narrowing to any
  one package. Deliberately scoped to just this guard's own real-tree test,
  not to `scanAuditEntrySites` itself, which is also called by every
  synthetic single-file fixture test in this file and would break all of
  them under a blanket file-count floor.
