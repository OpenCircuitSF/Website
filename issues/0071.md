## Description

`#0022` gave the Go SPA handler a route table so an unrecognized deep link
returns HTTP 404 instead of an indexable soft-404. That table,
`internal/handlers/routes.go`'s `knownStaticRoutes` plus
`workshopDetailPattern`, is a hand-typed mirror of `web/src/lib/router.ts`'s
`STATIC_ROUTES` and `WORKSHOP_DETAIL`. Nothing keeps the two honest.

`routes.go`'s own doc comment says the tables "stay in sync by construction
rather than by convention". That is true of `#0019` reusing the *Go* table from
Go, and false of the Go-to-TypeScript relationship, which is the one that
actually decides whether a page ships with the right status code. Two files in
two languages cannot be in sync by construction unless one is generated from
the other or a test fails when they diverge. Neither is the case.

**Proven at `#0022`'s review, 2026-08-18**, in a throwaway worktree, in both
directions:

- added `/privacy` to `STATIC_ROUTES` only → `npm run check` (187 files, 0
  errors), `npm test` (103 passed), `go build ./...` and `go test ./...` all
  green;
- added `/sponsors` to `knownStaticRoutes` only → same, all green.

The two tables happen to agree today. Nothing will tell anyone when they stop.

## Fix

Chose Approach 1 from the issue's own recommendation: a Go test
(`internal/handlers/routes_parity_test.go`) that parses
`web/src/lib/router.ts` directly and compares it against `routes.go`'s
tables. It rides `go test ./...`, which every backend verification pass
already runs, and needs no new build step, generator, or shared manifest —
the project has deliberately avoided adding a build step so far (per the
issue's own Approach 2 tradeoff), and a JSON manifest (Approach 3) would
touch the Vite build and the embed for a guarantee this test already
provides at far lower cost.

Two tests:

- `TestRouteTableParity_StaticRoutes` extracts the `STATIC_ROUTES` object
  literal's keys (regex over the block between `const STATIC_ROUTES: ... = {`
  and the closing `};`, then a per-entry regex for each `'path': 'Name'`) and
  diffs the resulting set against `knownStaticRoutes` in both directions.
- `TestRouteTableParity_WorkshopDetailPattern` extracts the source between
  `WORKSHOP_DETAIL`'s `= /` and the line-final `/;`, compiles it as a Go
  `regexp` (JS and Go RE2 agree closely enough for this specific pattern —
  character class, one capture group, anchors, and a backslash-escaped `/`
  that Go accepts unescaped just as well — verified by hand), and runs both
  the TS-sourced pattern and `workshopDetailPattern` against a shared table
  of paths, failing on any path where the two disagree.

Parse failures (`routerTSParseError`) are raised as `t.Fatal`, distinct from
parity failures (`t.Errorf` naming the offending path and side), so a
reformat of `router.ts` that breaks the narrow regex reads as "fix the
parser" rather than "the tables disagree" — called out explicitly in the
issue's Approach section.

Also corrected `routes.go`'s doc comment: it previously claimed the
Go-to-TypeScript relationship was "in sync by construction", which was never
true — only the Go-to-Go reuse (`#0019` reusing this table from Go) earns
that phrase. The comment now says the TypeScript mirror is instead kept
honest by `routes_parity_test.go` (this issue).

### Dynamic pattern: in scope, but normalization is hand-mirrored, not parsed

The trailing-slash normalization (`isKnownRoute` in `routes.go`,
`parsePath` in `router.ts`: strip one trailing slash on a path longer than
`"/"`) is **not** re-derived from source. It is a two-line rule already
independently documented and independently tested on each side
(`TestIsKnownRoute_TrailingSlash` here; `router.test.ts`'s equivalent on the
TS side). Re-parsing it would add another format-sensitive regex for a rule
that already has its own coverage on both sides. Instead,
`normalizeTrailingSlashForParity` reimplements that exact two-line rule once
in the test, and the test applies it identically to both the TS-sourced and
Go patterns before matching — so what's actually verified is regex
equivalence (the part with no other cross-check), while the normalization
step rides the existing per-side tests. This is a deliberate, disclosed
scope decision, not an oversight.

## Gotchas

- **Why parse-from-Go over the other two shapes.** A generated file
  (Approach 2) would be the strongest guarantee and would actually earn the
  original doc comment's wording, but it adds a `go:generate` build step this
  project has so far avoided, for a codebase where the route tables change
  rarely. A shared JSON manifest (Approach 3) is cleanest in principle but
  has the most churn — it touches `router.ts`, `routes.go`, the Vite build,
  and the embed, none of which exist today for this purpose. Parsing
  `router.ts` from a Go test needs none of that and rides a verification
  command every backend change already runs.
- **The parser is deliberately narrow and format-sensitive**, per the issue's
  own warning. It anchors on `const STATIC_ROUTES: ... = {` (the type
  annotation, unlikely to be reformatted away) and on `const WORKSHOP_DETAIL
  = /.../ ;` as a single line with no regex flags. A reformat of either
  declaration would fail parsing with a distinct `t.Fatal` message
  ("could not parse ... from ...") rather than a silent false pass or a
  parity-style `t.Errorf`, so the two failure modes cannot be confused.
- **No JS-to-Go regex translation needed for the current pattern.** Verified
  by hand (`regexp.Compile` in Go accepts `^\/workshops\/([^/]+)$` — the
  backslash-escaped slash — identically to the unescaped form) rather than
  writing a general JS-regex-to-RE2 translator, which would be its own
  source of bugs for a one-pattern use case.
- **Trailing-slash normalization is intentionally out of the parsed scope**
  (see `## Fix`) — it's asserted by mirroring, not by parsing, because it
  already has independent test coverage on both sides and re-parsing it would
  only add another format-sensitive regex without closing a real gap.
- **`web/dist/index.html`** shows as modified in `git status` throughout this
  work; it was not touched by this issue (no `npm run build` was run) — it
  predates this session's work, belongs to other in-flight work, and was left
  alone.

## Why this is not theoretical

The very next queued issue reproduces the failure. `#0070` (privacy policy
page) adds `/privacy` to `router.ts`. If that pass does not also edit
`routes.go`, `/privacy` ships as a real, fully rendered page that the server
answers with **HTTP 404** — deindexed, and reported as broken by every link
checker, while looking perfectly fine to anyone who clicks it. The reverse
drift is just as bad: a path known only to Go returns 200 and renders the
client-side 404 view, which is precisely the soft-404 `#0022` exists to
prevent.

The blast radius grows from here. `#0019` (per-route meta tags) and `#0020`
(sitemap) are both specified to build on this table, so a single silent
divergence ships wrong meta tags and a wrong sitemap at the same time.
`#0053`/`#0054` add the workshop routes on top of it.

## Acceptance criteria

- [ ] A test fails when `web/src/lib/router.ts`'s `STATIC_ROUTES` and
      `internal/handlers/routes.go`'s `knownStaticRoutes` disagree in either
      direction — a path present in one and absent from the other
- [ ] The dynamic pattern is covered too: `WORKSHOP_DETAIL` and
      `workshopDetailPattern` must accept and reject the same paths, including
      the trailing-slash normalization both sides implement independently
- [ ] The failure message names the offending path and which side is missing
      it, so the fix is obvious without reading either file
- [ ] The check runs as part of an existing verification command
      (`go test ./...` or `npm test`) — not a separate script someone has to
      remember
- [ ] Correct the false claim in `routes.go`'s doc comment: reusing the Go
      table from `#0019` is Go-to-Go reuse and genuinely is by construction;
      the TypeScript mirror is not, and after this issue it is enforced by
      *this test*, which is what the comment should say
- [ ] Mutation-verify it: delete one entry from each table in turn and confirm
      the new test fails both times — a parity test that cannot fail is worse
      than none, because it advertises a guarantee it does not provide

## Approach — pick one, do not gold-plate

Either direction is acceptable; the point is that divergence becomes loud.

1. **Assert parity from Go.** A `routes_test.go` case that parses
   `../../web/src/lib/router.ts` for the `STATIC_ROUTES` literal and compares
   the key set against `knownStaticRoutes`. Cheapest to write and it rides
   `go test ./...`, which every backend verification already runs. The cost is
   a regex over a source file, which breaks if the literal is reformatted —
   keep the parse narrow and make the failure message say "could not parse
   STATIC_ROUTES" distinctly from "tables disagree" so a reformat is not
   mistaken for a drift.
2. **Generate one from the other.** Emit a small `routes_gen.go` from
   `router.ts` via `go:generate`, and have the test assert the checked-in file
   matches what the generator produces. Genuinely by construction, and it earns
   the doc comment's original wording — but it adds a build step, which this
   project has so far avoided.
3. **A shared JSON manifest** both sides import. Cleanest in principle, most
   churn: it touches `router.ts`, `routes.go`, the Vite build and the embed.

Option 1 is the recommended default. Whichever is chosen, the criterion that
matters is that a one-sided edit turns something red.

### Why it is bounced: the parser can be silently green while the tables diverge

`staticRoutesEntryRe` (`'([^']+)':\s*'[^']*',?`) **skips lines it does not
recognize instead of failing on them**, and `parseStaticRoutesFromRouterTS`
only errors when *zero* entries match. So a partially-unparseable block parses
"successfully" with the unrecognized routes missing — and a missing route on
the TS side looks exactly like agreement.

Reproduced twice, both a clean `PASS` with the tables actually diverged:

1. **Mixed quote style on one entry.** `"/privacy": "privacy" as RouteName,`
   added to `STATIC_ROUTES` only, every other entry left single-quoted:

   ```
   === RUN   TestRouteTableParity_StaticRoutes
   --- PASS: TestRouteTableParity_StaticRoutes (0.00s)
   === RUN   TestRouteTableParity_WorkshopDetailPattern
   --- PASS: TestRouteTableParity_WorkshopDetailPattern (0.00s)
   PASS
   ```

   This is `#0070`'s exact scenario. The repo has no Prettier or ESLint config
   and `npm run check` is `svelte-check` (types only), so nothing normalizes or
   flags the quote style; code string literals happen to be single-quoted
   today purely by habit.

2. **A route composed in via spread.** A second `EXTRA_ROUTES` object holding
   `'/privacy'`, spread into `STATIC_ROUTES` with `...EXTRA_ROUTES,` — same
   clean `PASS`.

An all-double-quotes block fails loudly (case 2 in the section above) precisely
*because* it drops the entry count to zero. One divergent line does not. That
is the "reads as coverage" failure this issue was filed to eliminate: "a parity
test that cannot fail is worse than none, because it advertises a guarantee it
does not provide."

**Asked for — one change, structural rather than whack-a-mole.** Make an
unrecognized line inside the `STATIC_ROUTES` block a `routerTSParseError`
rather than a silent skip: after `FindAllStringSubmatch`, walk the block's
lines and `t.Fatal` on any non-blank, non-comment, non-brace line that no entry
regex matched ("could not parse STATIC_ROUTES entry: `<line>`"). That converts
both reproductions above from silent green into the loud, distinguishable
"fix the parser" failure the design already promises everywhere else, and it
closes the spread case, the `as const` case and any future syntax the regex has
not met. Widening the character classes to `['"]` is the minimum fix but only
covers the quote variant. This is not gold-plating — it is the difference
between a guard that can lie and one that cannot.

### Accepted as-is: the hand-mirrored trailing-slash normalization

Verdict: **sound as written, but it means AC 2's normalization clause is met by
delegation, not by this test — say so rather than implying otherwise.**

`normalizeTrailingSlashForParity` produces *test inputs*; it is not an
assertion. Because it is applied identically to both sides before matching, it
cannot cause a false pass in the regex comparison — the comparison is still a
real comparison, just over a path set. Verified concretely: changing
`isKnownRoute`'s single-strip to a `for` loop left both parity tests green,
and `TestIsKnownRoute_Miss` caught it (`isKnownRoute("/workshops//") = true,
want false`). So a one-sided normalization change is caught, by the per-side
tests, as the implementer argued.

Two honest consequences to record:

- Normalizing both sides identically means `/about/` and
  `/workshops/solder-101/` in `workshopDetailPatternParityCases` collapse onto
  their unslashed twins and add no discriminating power. Only `/workshops//`
  contributes a distinct input. The case table is smaller than it looks.
- Nothing cross-language checks the normalization *rule*. A coordinated change
  that updated each side's own test to a different rule would pass everything.
  That requires two deliberate edits and is an acceptable residual — but it is
  "by convention", the very thing this issue objects to, so it belongs in
  `## Gotchas` explicitly rather than being described as covered.

### Also record in `## Gotchas` (accepted, not blocking)

The dynamic-pattern test is **example-based**, so it only catches divergences
its eleven paths happen to expose. Narrowing the TS pattern to
`/^\/workshops\/([a-z0-9-]+)$/` — a real behavioural divergence for any slug
with an uppercase letter, underscore or dot — passes clean. That is inherent to
comparing regexes by sampling and is a fair trade against writing a
JS-to-RE2 translator; it just must not be described as full pattern
equivalence.

### For `#0070`

As `dfc26b3` stands, `#0070` **can** rely on this guard to catch a missing
`routes.go` entry for `/privacy` **only if** the new `STATIC_ROUTES` entry is
written in the file's existing single-quoted `'/privacy': 'privacy',` form. A
double-quoted entry, or one introduced by spread, ships silently. After the
parse-strictness fix asked for above, it can rely on it unconditionally.
