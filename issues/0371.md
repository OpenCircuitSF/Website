## Description

`migrations/000026_add_subscriber_invite_resent_at.up.sql`'s comment heading
reads:

> Write-once by CONSTRAINT, not merely by convention

That is **wrong**, and contradicted by its own next paragraph. The `CHECK` only
enforces `invite_resent_at IS NULL OR invited_at IS NOT NULL` — i.e. that a
resend implies an invitation. It does **not** prevent the column being written
twice.

**Write-once actually comes from application code**: `AdminResendInvitation`'s
guard 5 (`sub.InviteResentAt != nil → ErrInviteAlreadyResent`), under the same
`SELECT … FOR UPDATE` that stamps it. `#0312`'s review verified there is
**exactly one** SQL write site in the whole tree, never cleared, never
re-stamped — so the property holds, but not for the reason the comment gives.

Flagged non-blocking by `#0312`'s reviewer ("worth a one-line edit next time
this file is touched"), confirmed independently by `#0368`'s reviewer, and it
was **not** among the three items that became `#0367`/`#0368`/`#0369` — so it is
currently recorded nowhere but inside `issues/0312.md`'s prose, in a migration
file nobody otherwise has reason to reopen.

## The hard question this issue must answer first

**CLAUDE.md §1 says migrations `000001`–`000025` are frozen and that you must
never edit an existing migration.** `000026` is newer, but it has been applied
to real databases, and — decisively — **`scripts/testdb.sh` computes a content
digest over `migrations/`**. Editing even a comment changes that digest.

`#0123` amended `migrations/000025` in place on 2026-08-27, and that is
precisely why the template digest currently disagrees with `migrations/` and why
every agent's `check.sh` has been rebuilding through all migrations instead of
cloning (see `#0360`). **Repeating that to fix a comment would be a poor trade.**

So decide, and record the reasoning:

1. **Leave the migration alone** and correct the claim where it is actually
   read — `PRD.md` §6.2's schema comment, and/or the doc comment on
   `AdminResendInvitation` naming guard 5 as the enforcer. State in the issue
   that the migration comment is knowingly left stale and why.
2. **Edit the comment**, accepting a digest change — only if you can show the
   cost is genuinely nil, which means understanding exactly what `testdb.sh`
   does with the digest and what a change forces on every other agent.

**Option 1 is very likely right.** Do not choose option 2 without measuring.

## Acceptance criteria

1. The choice above is made explicitly and its reasoning recorded.
2. Wherever the correction lands, it names the **real** enforcer — guard 5 under
   `FOR UPDATE` — and states what the `CHECK` actually does
   (`invite_resent_at ⇒ invited_at`), without overstating either. Five issues
   bounced this phase for doc comments claiming more than the code delivers.
3. Re-verify the enforcement claim yourself against `HEAD` rather than trusting
   this issue: enumerate every write site of `invite_resent_at` in tracked
   `*.go` and `*.sql`, and confirm the guard is under the same transaction that
   stamps it.
4. If option 2 is chosen: **measure the digest impact before editing**, state
   what it forces on other agents, and coordinate — `#0360` is open and another
   session owns `scripts/testdb.sh` (`#0331`–`#0333`).
5. No behaviour change. If a fix seems to require one, stop and report.
