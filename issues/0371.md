## Description

`migrations/000026_add_subscriber_invite_resent_at.up.sql`'s comment heading
reads:

> Write-once by CONSTRAINT, not merely by convention

That is **wrong**, and contradicted by its own next paragraph. The `CHECK` only
enforces `invite_resent_at IS NULL OR invited_at IS NOT NULL` — i.e. that a
resend implies an invitation. It does **not** prevent the column being written
twice.

**Write-once actually comes from application code**: `AdminResendInvitation`'s
guard 5 (`sub.InviteResentAt != nil → ErrInviteAlreadyResent`), under the same
`SELECT … FOR UPDATE` that stamps it. `#0312`'s review verified there is
**exactly one** SQL write site in the whole tree, never cleared, never
re-stamped — so the property holds, but not for the reason the comment gives.

Flagged non-blocking by `#0312`'s reviewer ("worth a one-line edit next time
this file is touched"), confirmed independently by `#0368`'s reviewer, and it
was **not** among the three items that became `#0367`/`#0368`/`#0369` — so it is
currently recorded nowhere but inside `issues/0312.md`'s prose, in a migration
file nobody otherwise has reason to reopen.

## The hard question this issue must answer first

**CLAUDE.md §1 says migrations `000001`–`000025` are frozen and that you must
never edit an existing migration.** `000026` is newer, but it has been applied
to real databases, and — decisively — **`scripts/testdb.sh` computes a content
digest over `migrations/`**. Editing even a comment changes that digest.

`#0123` amended `migrations/000025` in place on 2026-08-27, and that is
precisely why the template digest currently disagrees with `migrations/` and why
every agent's `check.sh` has been rebuilding through all migrations instead of
cloning (see `#0360`). **Repeating that to fix a comment would be a poor trade.**

So decide, and record the reasoning:

1. **Leave the migration alone** and correct the claim where it is actually
   read — `PRD.md` §6.2's schema comment, and/or the doc comment on
   `AdminResendInvitation` naming guard 5 as the enforcer. State in the issue
   that the migration comment is knowingly left stale and why.
2. **Edit the comment**, accepting a digest change — only if you can show the
   cost is genuinely nil, which means understanding exactly what `testdb.sh`
   does with the digest and what a change forces on every other agent.

**Option 1 is very likely right.** Do not choose option 2 without measuring.

## Decision — the hard question, answered first

**Option 1: leave `migrations/000026` alone; correct the claim where it is
actually read.** `migrations/` is untouched by this pass — `git status
--porcelain -- migrations/` is empty throughout, and `git diff --stat --
migrations/` shows nothing. `scripts/testdb.sh` computes a content digest over
`migrations/`, and `#0360` is already open, unresolved, about that digest
disagreeing since `#0123`'s in-place amendment of `000025`; repeating that
class of cost for a comment-only fix is not worth it, and CLAUDE.md §1 says
never edit an existing migration regardless. I did not measure a digest-change
scenario for option 2 because option 1 fully satisfies the acceptance
criteria without incurring it — there is nothing to coordinate with the
`scripts/testdb.sh` owner (`#0331`–`#0333`) or with `#0360`, because
`migrations/` was never touched.

**Where the correction landed.** `internal/subscribers/pending.go`'s doc
comment on `AdminResendInvitation` was checked first and found **already
correct** — it attributes the one-ever bound to guard 5
(`ErrInviteAlreadyResent`) under the same `SELECT ... FOR UPDATE` that stamps
the column, and to nothing else in the package ever clearing or re-stamping
it; it does not mention the `CHECK` at all, so it makes no claim to correct.
No Go file was edited for this issue.

The false attribution instead lived, less directly, in `PRD.md` §6.2's schema
comment on `invite_resent_at`: it stated "write-once" immediately followed by
the `CHECK`'s text, without saying which one enforces which — the same
adjacency that makes the migration's heading misleading. Rewrote that comment
to name the real enforcer and state the `CHECK`'s actual scope explicitly
(criterion 2):

> `invite_resent_at TIMESTAMPTZ,` — `000026: write-once by CODE
> (AdminResendInvitation's guard 5 under the FOR UPDATE that stamps it), not
> by the CHECK, which only enforces invite_resent_at ⇒ invited_at. The
> bounded, user-approved deviation from "one invitation per address, ever" —
> at most ONE further invitation, by an authenticated admin action (#0312).
> CHECK (invite_resent_at IS NULL OR invited_at IS NOT NULL)`

This names guard 5 as the enforcer, states plainly that the `CHECK` does
**not** confer write-once and describes exactly what it does check
(`invite_resent_at ⇒ invited_at`), and does not overstate either — matching
criterion 2. The migration file's own comment (still headed "Write-once by
CONSTRAINT, not merely by convention", still wrong) is knowingly left stale;
this correction is recorded here as the reason.

350 means any early return — including guard 5's — leaves nothing committed.

site, under the lock, in the same transaction.
