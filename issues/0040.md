## Description

The `email_campaigns`, `campaign_interests`, and `email_sends` tables, including the uniqueness constraint that makes sending idempotent.

## Root cause

Not a bug — this is the founding schema for Phase 5. `internal/mailing`
existed only for templates, headers, and the SES mailer (`#0042`/`#0043`
territory); nothing in the tree defined `email_campaigns`,
`campaign_interests`, or `email_sends`, so `#0041`, `#0044`, and `#0045`
had no table to build against. `#0044`'s planning pass (2026-08-21) named
five requirements this migration had to carry so its own audience-
materialization work wouldn't need a follow-up `ALTER TABLE`.

## Fix

Added `migrations/000017_create_campaigns.up.sql` / `.down.sql` — the next
free version confirmed from `ls migrations/` (highest on disk was `000016`,
not the `000012`/`000013` figures earlier issues assumed). Follows the style
of `000009_create_interests` and `000010_create_subscribers`: `CREATE TABLE`
first, then named `ALTER TABLE ... ADD CONSTRAINT` CHECKs for every enum-ish
column, matching `subscribers_status_check` / `suppressions_reason_check`.

Schema, per PRD §6.2 with the five carried-in requirements from `#0044`'s
plan:

- `email_campaigns` — `status` CHECK'd to `draft | scheduled | sending |
  sent | canceled | failed`; `audience_mode` CHECK'd to `all | any_of |
  all_of | none_selected` (default `any_of` per PRD). `workshop_id` is a
  plain nullable `BIGINT` with **no** `REFERENCES` clause — `workshops`
  doesn't exist until Phase 6, and PRD §6.2's migration-ordering note says
  to keep Phase 5 independently deployable rather than reorder phases;
  `#0050` attaches the FK with a later `ALTER TABLE`.
- `campaign_interests` — join table, `ON DELETE CASCADE` on **both**
  `campaign_id` and `interest_id` (requirement 4).
- `email_sends` — `UNIQUE (campaign_id, subscriber_id)` (requirement 2), the
  idempotency key `#0044`'s `ON CONFLICT (campaign_id, subscriber_id) DO
  NOTHING` materialization insert relies on (requirement 5 — the schema
  itself doesn't forbid `DO UPDATE`, since that's expressed in the INSERT
  statement `#0044` writes, not in DDL; noting the constraint here per the
  task brief). `status` CHECK includes `skipped` alongside PRD §6.2's five
  (`queued | sent | failed | bounced | complained | skipped`) — requirement
  1. Added `idx_email_sends_queued ON email_sends (campaign_id, id) WHERE
  status = 'queued'` (requirement 3, exact name and definition from the
  plan) plus `idx_email_sends_message_id ON email_sends (ses_message_id)`
  for `#0049`'s reconciliation, both per PRD §6.2. Also added an
  `email_sends_email_normalized` CHECK (`email = lower(trim(email))`),
  matching the same guard already on `subscribers.email` and
  `email_events.recipient` — not explicitly required, but consistent with
  every other stored-email column in this schema.

`down.sql` drops the three tables in reverse dependency order
(`email_sends`, `campaign_interests`, `email_campaigns`) — a plain, clean
drop; nothing here has `000013`'s data-loss hazard that would justify a
deliberately-failing down.

Also updated `docs/database.md` (new "Campaign schema (Phase 5)" section
with a `000017_create_campaigns` row, range bumped to `000001`–`000017`,
and removed the now-implemented `suppressions`/`email_campaigns` lines from
the stale "Planned schema" list) and `CLAUDE.md`'s migration-range cell, in
the same commit as the migration — required by `internal/db`'s
`TestDatabaseDocMigrationParity`.

No store code was added. `internal/mailing` has no DB-backed code today
(confirmed: no `TEST_DATABASE_URL`/`testdb` references in the package); its
acceptance criterion ("`go test ./internal/mailing/...` passes against a
real database") is satisfied by the existing unit tests continuing to pass
with the database reachable, not by new code in this issue. `#0041`/`#0044`
build the store and CRUD API against this table and were explicitly out of
scope here.

## Carried in from `#0044`'s plan (2026-08-21)

`#0044` materializes the campaign audience into `email_sends`, which this issue
creates. Four requirements land here, and each is expensive to add later:

All five verified against the live database at review, not against the SQL text.

- [x] **`email_sends.status`'s `CHECK` must include `skipped`.** `#0044`
      re-checks eligibility inside the transaction that claims each batch: a
      recipient who was eligible at materialization but has since unsubscribed
      or been suppressed becomes `skipped` and is never mailed. `skipped` is
      already in PRD §6.2's enum. If it is omitted here, `#0044` has to ship an
      `ALTER TABLE` migration to add it.
- [x] **`UNIQUE (campaign_id, subscriber_id)`** — the idempotency key that makes
      re-running materialization safe. Live: `email_sends_campaign_id_subscriber_id_key`.
- [x] **`idx_email_sends_queued ON (campaign_id, id) WHERE status = 'queued'`** —
      the partial index the send worker's claim query needs. `EXPLAIN` confirms
      the claim query plans as an index scan over it.
- [x] **`campaign_interests` with `ON DELETE CASCADE`.** On both columns.
- [~] **The materialization insert must never be given a `DO UPDATE` clause.**
      Not expressible in DDL — this one is `#0044`'s to honour in its INSERT,
      and its plan §6 commits to it explicitly. Verified only in the negative
      here: nothing in the schema (no trigger, rule, or resetting default)
      creates a `sent` → `queued` path, and the guarded
      `… AND status = 'queued'` update was confirmed to match zero rows
      against a row already `sent`.
      `ON CONFLICT DO NOTHING` is required; `DO UPDATE` would create a documented
      path from `sent` back to `queued`, i.e. a double-send.

## Notes

PRD §6.2 and its migration-ordering note. `workshops` does not exist until Phase 6, so the `workshop_id` foreign key cannot be declared here — add the column now (nullable, no FK) and attach the constraint in #0050.

The `UNIQUE (campaign_id, subscriber_id)` constraint is what guarantees a crashed and restarted send can never double-deliver. It is the single most important line in this migration.
