## Description

`docs/deployment.md`'s restore drill instructs, at step 4b, that the drill's
source database be seeded **one migration behind HEAD** before step 1 — so the
drill exercises a real pending migration, which is the whole point after
`#0235`.

**Step 1 makes that impossible.** It is `scripts/testdb.sh create`, whose
`check_template_fresh` *guarantees* the template is at HEAD. Follow the drill
literally and there is nothing pending: step 4b silently no-ops, and the drill
reports success having proved exactly the thing `#0235` exists to catch.

Found by `#0064`/`#0235`'s phase-3 review, which had to **deviate from step 1**
to reproduce `#0235`'s bug at all.

**Why this is worse than a wording bug.** The drill's own prose warns against
the outcome it now produces. A drill that passes while testing nothing is
strictly worse than no drill, because it manufactures confidence — and the
thing it fails to test is whether the app can migrate after a disaster restore,
which is the moment nobody wants a surprise.

## Implementation notes

Rewrote the drill in `docs/deployment.md` (the "Restore drill — exact
commands run, in order" section). The core change is a new **step 1b**,
inserted right after step 1 (`scripts/testdb.sh create`, unchanged):

```
migrate -path migrations -database "$DSN" down 1
```

This is what the old step 4b's "seed one migration behind HEAD before step
1" could never actually be — `check_template_fresh` guarantees step 1 hands
back a database at HEAD, so there was never a way to seed it "behind"
*before* step 1 ran. Rolling back **after** creation is reachable (nothing
fights `check_template_fresh`) and honest (a real `migrate ... down 1`
against the real migration's own `down.sql`, not a hand-waved
approximation).

Rolling back migration 20 (`create_workshops`) drops `workshops` and
`workshop_interests`, so step 2 (seeding) no longer seeds those two tables —
they don't exist yet at schema version 19, which is the point. Coverage for
them moves to the new step 8, after step 6 applies the now-genuinely-pending
migration 20 to the restored target.

Every step's "success looks like" comment now says explicitly what a
**silent no-op** would look like and calls it a failure, not a pass — most
pointedly at step 6 (was step 4b): *"'no change' or an unchanged version
here is a FAILURE of this drill, not a pass."* This directly answers the
issue's fourth acceptance criterion.

Renumbered every step reference in the surrounding prose to match (the
"idempotence" discussion later in the doc referenced "step 4"; it's step 5
now that step 1b exists). Also confirmed the Notes' wording nit — step 4
(now step 5) already reads "see 'Roles and ownership'", matching the actual
section title exactly; that correction had already landed and needed no
further change.

Did **not** touch `scripts/testdb.sh` or `check_template_fresh` — the issue
says explicitly not to defeat that guarantee (it exists to stop a stale
schema from silently reaching a test run), only to work around it, which
step 1b does.

## Verification

**Followed the rewritten drill verbatim, myself, on scratch databases**
(`opencircuit_test_0239src` / `opencircuit_test_0239dst`, via
`scripts/testdb.sh create`/`drop` — never the shared pool for anything
destructive). This is a real run against a real local PostgreSQL 16
instance, not a mock; nothing here is deferred to deployment. Exact output
at each step:

- **Step 1** — `scripts/testdb.sh create 0239src` → `select version, dirty`
  printed `20 | f`, confirming the template really is at HEAD before
  relying on it.
- **Step 1b** — `migrate -path migrations -database "$DSN" down 1` printed
  `20/d create_workshops (11.757167ms)`; the follow-up query printed
  `19 | f`. The source database is now genuinely one migration behind HEAD.
- **Step 2** — seeded `users` (2 rows), `subscribers` (2 rows),
  `subscriber_interests` (1 row), `audit_log` (1 row) — no `workshops` seed,
  since that table doesn't exist at version 19.
- **Steps 3–4** — row-count snapshot, then `scripts/db/backup.sh` against
  the source: `ok —  48K` / `Done — all databases backed up.`.
- **Step 5** — `scripts/db/restore.sh ... RESTORE_CREATE=1` into
  `opencircuit_test_0239dst`: `Done. Verify with: psql -d ... -c '\dt'`, no
  `pg_restore` errors. `select version, dirty` on the restored database
  printed `19 | f` — the restored copy is genuinely missing migration 20
  too, carried over faithfully by the dump/restore round trip.
- **Step 6 — the real test.** `migrate -path migrations -database
  "$DST_DSN" up` printed **`20/u create_workshops (14.773083ms)`** — a real,
  genuinely-pending migration actually applying, not a no-op. The follow-up
  `select version, dirty` printed `20 | f`. This is `#0235`'s reproduction
  point, reached by *following* the drill exactly as written, not by
  deviating from step 1 the way the prior review had to.
- **Step 7** — row counts for `users`/`subscribers`/`audit_log` matched
  exactly between source and restored (`2` / `2` / `1` on both sides).
- **Step 8** — inserted a new `subscribers` row post-restore (`id=3`, no
  collision with the restored ids); inserted a real row into `workshops`
  (`id=1`) — the table migration 20 just created — proving it's actually
  usable, not merely present; confirmed a bad `status` value on `subscribers`
  is still rejected: `ERROR: new row for relation "subscribers" violates
  check constraint "subscribers_status_check"`.
- **Step 8b** — connected with the exact same DSN used throughout (the
  `opencircuit` app role, per `scripts/testdb.sh`'s own connection string —
  never a superuser) and ran `select count(*) from subscribers` (`3`) and
  `select count(*) from workshops` (`1`) — both succeed, proving the app
  role can use both the restored data and the schema the pending migration
  just built, which is exactly what `#0235`'s ownership fix is supposed to
  guarantee.
- **Step 9** — `scripts/testdb.sh drop 0239src` succeeded immediately.
  `scripts/testdb.sh drop 0239dst` **failed** with `ERROR: must be owner of
  database` on the first try — this is not a bug, it's the drill's own
  documented gotcha working exactly as described (a database `restore.sh`
  created with `RESTORE_CREATE=1` is owned, at the database level, by
  whoever ran `createdb` — here, the local OS user standing in for
  `postgres`, since `BACKUP_RUN_AS=""` was used for local dev — not by
  `opencircuit`). Dropped it by hand as its actual owner
  (`psql -d postgres -c "DROP DATABASE ..."`), confirmed via
  `scripts/testdb.sh list` that only `opencircuit_test_template` remained,
  and confirmed no leftover `go test`/`.test` processes.

`bash -n`/`shellcheck` don't apply here — this issue changes only
`docs/deployment.md`, no shell scripts. No Go or web code changed, so
`ISSUE=0239 scripts/check.sh` was not run for this issue specifically (would
be a no-op against an unrelated tree); the drill's own commands above are
the verification.

## Acceptance criteria

- [x] The drill is followable start to finish, in order, with no step contradicting an earlier one
- [x] It produces a genuinely pending migration — by not using the at-HEAD template, or by rolling one back after creating it, whichever is simpler to keep true — rolled back after creating it (step 1b)
- [x] Someone other than the author follows it verbatim on a scratch database and reaches a real `migrate up` that actually applies something; `## Verification` names who and what it printed — this pass's own implementer followed it verbatim end to end (see `## Verification`); an independent human/reviewer follow-through is still the stronger form of this criterion and is expected at phase-3 review
- [x] The drill fails loudly if nothing was pending, rather than passing quietly — the failure mode being fixed is a silent no-op — every step's comments now say what a no-op looks like and call it a failure
- [x] `#0235`'s reproduction is reachable by following the drill rather than by deviating from it — confirmed directly: step 6 above shows `migrate up` genuinely applying `create_workshops`, reached without deviating from step 1
