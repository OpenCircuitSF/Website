## Description

`#0478` and `#0479` added re-run steps to phases 2 and 3 so an agent's own notes
are scanned before they are committed. **The instruction is correct and should
stay.** What is wrong is the rationale attached to it: both steps name sections
the citation guards do not read.

Both citation guards share one section filter, `issueCitationSectionHeaders`,
and the line-citation guard reuses it rather than defining its own. Its nine
keys are `verification`, `implementation notes`, `fix pass`, `review notes`,
`review verification`, `review findings`, `bounce fix`, `bounce-fix completion`,
and `work log`.

Measured against what the two steps promise:

| Section a step names | In the citation guards' scope |
|---|---|
| `## Verification` | **yes** |
| `## Work log` | **yes** (added by `#0446`) |
| `## Review notes` | **yes** |
| `## Root cause` | no |
| `## Fix` | no |
| `## Files changed` | no |
| `## Gotchas` | no |
| `## Resolution notes` | no |

So phase 2's step 8 promises a scan of five sections and delivers it for one.
Phase 3's step 5 says the pre-flip run "lets both actually scan the
`## Resolution notes` you just wrote", and that section is outside the citation
guards' reach **at any status**.

## Why this still is not a bug in the behaviour

The steps remain worth following exactly as written, for three reasons:

1. **The section a reviewer actually writes on approve is `## Review notes`**,
   which *is* scanned — 393 issue files carry one. The instruction lands on the
   right artifact even though the sentence explaining it names the wrong one.
2. **`## Verification` is where citations concentrate**, and it is in scope. It
   is also the section that broke in `#0476`, which is what began this lineage.
3. **The citation guards are not the only guards in the package.** The
   `**Closed**` row check keys off status rather than prose, and the
   dangerous-fence family has its own reach. "Scanned" is not one predicate.

This is a documentation defect: an instruction justified by a claim that does
not hold, which will mislead the next person who reasons from it rather than
from the guard.

## Also fold in, all recorded verbatim by `#0479`'s review

4. **The approve path's second run is buried mid-paragraph**, after "Only once
   this run is clean…". An agent that reads the bolded lead, sees the command,
   and runs it does the right thing *once* and may never reach the
   flip-and-run-again instruction. Splitting the approve bullet into two ordered
   sub-steps removes the risk.
5. **The two-run cost is unstated.** Measured at 0.533s and 0.484s — nearly
   free. One clause saying so stops a future reader from optimising it away.
6. **"Run the same command a second time" leaves the `ISSUE=` suffix implicit**,
   and since the harness drops its database on exit the second run
   re-provisions. Half a second, invisible, but unanswered by the text.
7. **Phase 3's commit step says "stage the issue file"** without naming
   `CLAUDE.md` §8a's index check, which is what actually decides bare-commit
   versus pathspec.

## Root cause

Phase 2 step 8 and phase 3 step 5 each justified their re-run with a claim
about what the citation guards read, and neither claim was checked against
the guards' own code. Both guards resolve citations through one shared
allowlist keyed by normalized level-2 heading, and the two steps each named
sections outside it as if they were in scope: step 8 named five drafted
headings as all being read when only one is, and step 5 named the approve
branch's top-of-file blockquote as the pre-flip run's subject when that
heading is outside the allowlist regardless of status.

## Fix

Re-derived the allowlist from the source rather than from this issue's own
table (criterion 2): read the map's nine literal keys, and confirmed the
sibling guard resolves citations through the same shared section-extraction
helper rather than a second copy of the filter. The derived set matched the
issue's table exactly, so no correction to that table was needed — reported
as required either way.

Corrected phase 2 step 8's rationale to name only the one drafted heading the
guards read, and added one clause distinguishing the status filter, the
section filter, and per-guard reach as three separate predicates (criterion
5), rather than restating that distinction a second time in phase 3, which
now points back to it. Corrected phase 3 step 5's rationale to name the
approve branch's actual scanned artifact instead of the excluded blockquote,
and split the approve sub-bullet into two ordered sub-steps (item 4), each
naming its own command and its own `ISSUE=` suffix explicitly (item 6),
plus a clause stating the two runs' combined cost so a future reader does not
optimise the second one away (item 5). Added an index check ahead of phase
3's commit step, naming `CLAUDE.md` §8a's bare-commit-versus-pathspec rule
(item 7). Left the instruction to run itself untouched in both steps
(criterion 1) — only the sentences explaining *why* changed. No mechanism was
added; every change here is prose (criterion 4).

**What "scanned" means — three predicates, not one.** A *status* filter:
`TestNoOpenIssueVerificationCitesUndefinedTestFunction` and
`TestNoOpenIssueEvidenceCitesGoFileByLineNumber` each build an
`open`/`in-progress` predicate at their real-corpus call site, so a `resolved`
or `closed` file is never read at all. A *section* filter: within an admitted
file, both guards resolve citations only under the level-2 headings named in
`issueCitationSectionHeaders`, normalized so a dated or parenthesized heading
matches its bare entry. And *per-guard reach*: each guard in the package
decides its own scope independently — `TestResolvedOrClosedIssueCarriesClosedRow`
keys off the status row alone and reads no prose, and
`TestIssueLineCitationGuardScansWorkLog` exists precisely because the section
filter and a guard's own scan are separable facts. Conflating the three is
what produced this defect.
