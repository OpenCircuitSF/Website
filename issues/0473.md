## Description

The user, 2026-09-08:

> *"This would be done only in the spinoff website. Later we could adapt this
> website to use that spinoff and capture all content inside the db as CMS
> managed content."*

So the direction is **two-step, and this issue is the second step**:

1. **The spinoff** (`#0232`) builds the reusable platform — newsletter with
   admin screens, CMS features, and configurable upcoming events, where even the
   entity noun is configurable. **The CMS is built there, not here.**
2. **This site later becomes a consumer of it**, and its content — currently
   compiled into the binary — moves into the database as CMS-managed content.

**Strictly ordered.** Nothing here starts until the spinoff exists and has a
CMS worth adopting. `#0232` is itself marked last in the queue by the user's own
instruction, so this sits behind it.

## Three consequences worth naming before anyone starts

**1. It breaks a guard's premise, and the plan already found this.**
`#0226`'s guard is a **build-time AST walk over compiled-in copy** against a
committed fixture. Content that lives in the database exists in **no build**, so
that guard stops being able to see it. `#0232`'s plan hit this for the privacy
policy specifically and recommended *not* making that page configurable, on the
grounds it describes what the software does rather than who runs it. **That
recommendation should be revisited here rather than inherited** — the reasoning
was about a downstream tenant, and this step is about this site.

**2. It raises the cost of the backup gap.** Content compiled into the binary is
in git. Content in the database is only in the database — and this project
**has never been backed up** (`#0435`, prepared but not applied; `#0469` open on
the fact that a backup failure is not noticed by anyone). Moving content into
Postgres without those closed converts a documentation gap into a data-loss
exposure.

**3. The seam already exists, which is the encouraging part.**
`internal/seo/site.go` **already rewrites the embedded `index.html` per
request**, so the SPA's shell is not actually frozen at build time. `#0232`'s
plan identified that as the mechanism by which one binary can be rebranded with
no rebuild. The same seam is the natural place for database-sourced page content.

## Acceptance criteria

1. **Do not start until `#0232`'s spinoff exists and has a CMS.** If this is
   picked up first, the right outcome is to say so and stop.
2. Establish what this site keeps compiled versus what moves. **Not everything
   should move** — see consequence 1, and note that anything a guard currently
   pins is a deliberate decision to re-open, not an oversight to clean up.
3. `#0435` and `#0469` must be **closed, not merely prepared**, before content
   depends on the database. Say so as a precondition rather than discovering it.
4. Re-derive every figure in the inventory above. They were measured on
   2026-09-08 and this issue is expected to sit for a long time.
5. Decide what happens to the **golden fixtures** pinning the transactional
   templates. Eighteen of them exist; database-sourced content either keeps them
   meaningful some other way or retires them deliberately.
6. **No new mechanism to bridge the gap** while this waits (§8, `#0258`). If the
   spinoff is not ready, the answer is to wait, not to build half a CMS here.
