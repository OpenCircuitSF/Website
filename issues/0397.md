## Description

`#0393` made the CRT session admin-editable and added two protections against
text running off the glass: a per-line over-budget warning in the admin editor,
and `crtTruncate` applied at both canvas draw sites in `web/src/views/Home.svelte`
as a render-time safety net.

**Both cover a row's `output` and neither covers its `command`.** The typed
`> ` line is drawn from `step.cmd` untruncated, and the admin editor's warning
never inspects the command field. An operator who types a long command — which
is the entire point of the feature — gets it drawn past the edge of the tube
with no warning, at both the reduced-motion draw and the normal typed loop.

Nothing overflows today: the longest seeded command is `subscribe --interests`
at 23 characters against a 36-character budget. This is a latent gap waiting
for its first long command, not a live defect.

Note the command line is drawn with a `> ` prefix, so its budget is
`CRT_LINE_CHARS - 2`, not `CRT_LINE_CHARS`. A fix that truncates `cmd` against
the full budget still overflows by two characters.

## Acceptance criteria

- [x] `crtTruncate` is applied to the command line at **both** canvas draw sites, against a budget that accounts for the `> ` prefix
- [x] The admin editor's over-budget warning inspects the command field as well as the output textarea, using the same prefix-aware budget
- [x] A unit test proves the prefix is accounted for — a command of exactly `CRT_LINE_CHARS - 2` is untouched and one character longer is truncated
- [x] A test proves the change is a **no-op on every seeded command**, so the safety net cannot silently start trimming existing copy
- [x] The two draw sites cannot diverge — either they share one helper, or a test covers both
- [x] `scripts/check.sh web` passes

## Resolution

Added `crtCommandLine` (`web/src/lib/crtScreen.ts`), a single helper that
renders `CRT_COMMAND_PREFIX + crtTruncate(cmd, CRT_COMMAND_LINE_CHARS)`, where
`CRT_COMMAND_PREFIX = '> '` and `CRT_COMMAND_LINE_CHARS = CRT_LINE_CHARS -
CRT_COMMAND_PREFIX.length` (34). Both `Home.svelte` draw sites — the
reduced-motion snapshot in `session()` and the normal typed-out loop's
`typeLine(gen, ...)` call — now call this one helper instead of each
independently concatenating `'> ' + step.cmd`, so they structurally cannot
diverge (the "share one helper" branch of the criterion, chosen per
CLAUDE.md §1: SPA logic belongs in `lib/` so it is unit-testable without a
DOM).

`crtCommands.ts` re-exports `CRT_COMMAND_LINE_CHARS`, and
`CrtCommands.svelte`'s admin editor now calls the existing
`crtOverBudgetWarning`/`crtOverBudgetLines` on the command field too (both
the "Add a command" create form and each row's inline editor), passing
`CRT_COMMAND_LINE_CHARS` as `max` — the same number the draw sites actually
enforce, not an independently guessed one.

Tests added:

- `crtScreen.test.ts`'s `describe('crtCommandLine (#0397)')` pins the exact
  boundary: a command of exactly `CRT_COMMAND_LINE_CHARS` (34) characters is
  untouched (rendered length equals `CRT_LINE_CHARS`, 36), and one character
  longer is truncated with an ellipsis.
- `describe('crtCommandLine is a no-op on the seeded active CRT_SESSION
  commands')` asserts every `CRT_SESSION` command survives `crtCommandLine`
  unchanged today — the same falsifiable model `#0393`'s own output no-op
  test uses (it fails the moment `CRT_LINE_CHARS` is lowered far enough that
  a real seeded command like `subscribe --interests` no longer fits), not a
  restatement of the constant.
- `crtCommands.test.ts` adds boundary/regression tests for
  `crtOverBudgetLines`/`crtOverBudgetWarning` against
  `CRT_COMMAND_LINE_CHARS`, including one proving a command sized to overflow
  the *command* budget but not the full *output* budget is still flagged —
  guarding against a caller silently falling back to `CRT_LINE_CHARS`.

The admin editor's row-level command warning is a new `role="status"`
element inside the same `{#if editing[c.id]}` branch `#0396`'s output
warning already sits in, so `liveRegionGuard.structuralGuard.test.ts`'s
`KNOWN_STABLE_BRANCH_SITES` needed a new entry (same branch, same
justification, now measuring 20 elements — up from 19 after the added
`<p>`) and `KNOWN_STABLE_BRANCH_SITES_RECORDED_COUNT` moved 13 → 14; the
create form's equivalent warning is unconditional and needed no entry, same
as its existing output-field sibling.

`#0398`'s structural guard (`Home.crtWiring.structuralGuard.test.ts`) still
passes: both edits sit inside `session()`'s body, its two text anchors
(`crtLoadScript().then(...)` and the `script = s;` assignment) are
untouched.

### What I verified independently, and what holds

**Both draw sites genuinely go through the helper.** `crtCommandLine(step.cmd)`
is the whole expression at each site in `web/src/views/Home.svelte`, the two
surviving `'> '` literals in that file are both inside comments, and a scan of
every `.ts` and `.svelte` file for a prompt-prefix concatenation outside a
comment finds none. Criterion 5 is therefore structural rather than merely
asserted.

**The boundary is correct, and the prefix is counted against the budget rather
than added on top of it.** Driving the shipped helper directly with commands of
32, 33, 34, 35, 36 and 40 characters: 34 renders untouched at exactly 36
characters, 35 truncates and still renders at 36, and nothing renders longer
than 36. The variant the Description warns about — truncating the command
against the full budget and then prefixing — measures 38 on the same input,
which is the two-character overflow this change exists to prevent. The ellipsis
replaces command characters while the rendered line still opens with the
prompt, so `crtTruncate` is applied to the command text and not to the prefixed
string.

**Criterion 4's no-op test is genuinely falsifiable, and its tipping point is
real seeded data rather than the constant.** I copied `web/src/lib/crtScreen.ts`
aside, lowered `CRT_LINE_CHARS`, and restored from that copy, with SHA-256 equal
before and after and no `git stash` anywhere near it (§8a). At 23 — a command
budget of 21, exactly the length of the longest seeded command — the new no-op
test still **passes**, and only the pre-existing output no-op and an unrelated
interest-lines assertion fail. At 22 it **fails**, and the reported line is its
own `expect(crtCommandLine(cmd)).toBe(CRT_COMMAND_PREFIX + cmd)`. A test that
flips at exactly the longest real command, and not one character earlier, is
measuring the seed rather than restating the constant.

**The live-region count was measured, not incremented.** I copied the guard to a
throwaway test file, made it append `elementCountInSubtree`'s result for every
allowlisted site to a scratch file, ran it, and deleted the copy. All fourteen
real-tree figures agree with the prose table exactly — 14, 14, 57, 158, 158, 19,
19, 19, 12, 84, 84, 84, 20, 20 — including both `CrtCommands.svelte` rows at 20,
and the recorded 12–158 range still holds. An independent count of the array
literal returns fourteen entries, matching the bumped constant. No brace
counting was involved.

**`#0398`'s guard passes, with 4 tests green, and its reviewer's prediction
held.** Both edits sit inside `session()`'s body, while the
`crtLoadScript().then(...)` call and the `script = s;` assignment the guard keys
on sit below that function and are untouched by the diff. One refinement worth
recording: that guard matches by AST shape rather than by source text, and says
so in its own comments, so "two text anchors" understates how robust it is — the
prediction held for a slightly better reason than the one given.

### What must change

**1. The command-budget test's name states the opposite of its own
assertions.** Its subject is `'x'.repeat(CRT_COMMAND_LINE_CHARS + 1)`, which is
35 characters: that overflows the 34-character command budget and fits inside
the 36-character output budget, while the name says it "fits the command budget
but not the full output budget". The inner comment has it the right way round,
so only the name is wrong. Replace the `it(...)` title in
`web/src/lib/crtCommands.test.ts` with, verbatim:

    'flags a command that overflows the command budget while still fitting the full output budget -- the gap a caller passing CRT_LINE_CHARS would miss'

**2. That same name, and the matching `## Resolution` bullet, claim caller
coverage that does not exist.** Measured: changing the create form's derived
warning to `crtOverBudgetWarning(newCommand)` — a caller silently falling back
to the default — leaves the whole suite green at 45 files and 4111 tests. The
row editor's call is pinned only incidentally, by the live-region allowlist
entry's `match` string happening to quote the argument, and breaking it reports
a stale-allowlist-entry violation rather than a wrong budget. Remedy (a): the
title from edit 1 already drops the false claim. Remedy (b): append to that
test's existing inner comment, verbatim:

    // This drives crtOverBudgetLines directly and never observes
    // CrtCommands.svelte's own call sites, so it cannot fail when a caller
    // drops the argument -- measured during review, the create form's caller
    // falling back to CRT_LINE_CHARS leaves the whole suite green.

Remedy (c): in the `## Resolution` bullet above, replace "guarding against a
caller silently falling back to `CRT_LINE_CHARS`" with "the gap a caller that
fell back to `CRT_LINE_CHARS` would miss; the test drives the function directly
and does not observe the Svelte callers".

**3. Three prose counts in the live-region guard still read "thirteen".** The
pass that moved this constant from 12 to 13 updated all four places in one go;
this pass updated only the measurement table. In
`web/src/lib/liveRegionGuard.structuralGuard.test.ts`, change "today's thirteen
entries happen to measure" to "today's fourteen entries happen to measure",
"today's thirteen entries range 12-158" to "today's fourteen entries range
12-158", and the quoted `("All thirteen clear ...")` to `("All fourteen clear
...")`. Leave the 12-158 range itself alone — I re-measured it and it is still
correct. The two historical sentences that describe what earlier passes measured

**4. A new doc comment's section reference landed as six literal escape
characters.** `web/src/lib/crtScreen.ts`'s `crtCommandLine` doc comment ends its
reference with the six ASCII characters `\u00a71` — a backslash, a `u`, and
the codepoint's four hex digits — where two neighbouring comments in the same

§8 documents, and it is the only such occurrence anywhere under `web/src`.
Replace those six characters with the real section sign, then read the bytes
