## Description

`CLAUDE.md` §11 carries, in free prose immediately below the section-index
table:

> §6 (the mailing list) is 933 lines — take the subsection, not the parent.

The table row directly above it now says **966**. The prose disagrees with the
guarded row by **33 lines**.

**It sits inches from a fully guarded table and is guarded by nothing.**
`internal/db/prd_section_index_test.go` parses the table rows and runs each
row's own `sed`; it never parses surrounding prose.

Confirmed genuinely pre-existing by `#0368`'s review — `git show 4ed36ef^:CLAUDE.md`
carries it verbatim, and `git log -S` dates it to `2e55a78`. `#0368` correctly
left it alone as out of scope.

**This is the exact drift class this phase has spent twenty issues on**, and the
person it misleads is the one deciding whether to extract §6 or a subsection —
the decision §11 exists to inform.

## The choice this issue must make

1. **Reword so the sentence carries no number.** "§6 is by far the largest
   section — take the subsection, not the parent" is as useful and cannot drift.
2. **Extend the guard** to any `§N … is <number> lines` prose in §11, so the
   number stays checked.

Option 1 is cheaper and removes the failure mode rather than detecting it.
Option 2 keeps a number a reader may actually want. **Choose deliberately and
record why** — and note that this phase's repeated finding (`#0330`, `#0347`,
`#0356`) is that removing a claim beats adding a checker for it.

## Acceptance criteria

1. The stale number is gone or guarded — not merely corrected to 966. **A
   corrected number drifts again on the next edit to §6**, which is how it
   reached 33 lines out.
2. If option 2: prove the extended guard discriminates. Change the prose number
   alone and confirm the test fails, naming it. **A check that cannot fail pins
   nothing** — `#0354`, `#0358` and `#0363` each shipped exactly that this
   phase.
3. Re-measure any number you state by running the relevant row's own `sed`
   command, never by arithmetic. §11 records two ways that table has been wrong:
   §6.2 drifted across two commits unnoticed, and §14 was wrong from birth
   because a regeneration applied `raw + 1` against the exception it had just
   documented. Note §14 has no following heading, so its count is taken **raw**
   at EOF — do not re-break it.
4. `internal/db/prd_section_index_test.go`'s existing tests still pass —
   `TestPRDSectionIndexParity` and `TestPRDSectionIndexTotalMatchesFile`, named
   explicitly in `## Verification` (§5: `ok` does not say what ran).
5. Documentation only. No `.go` file in the diff unless option 2 is chosen, in
   which case the guard change is the only one.

## Decision — option chosen, and why

**Option 1: reword so the sentence carries no number.** Changed the prose at
`CLAUDE.md` (below the §11 table) from "§6 (the mailing list) is 933 lines —
take the subsection, not the parent." to "§6 (the mailing list) is by far the
largest section — take the subsection, not the parent." (the issue's own
suggested wording, verbatim).

Reasoning, recorded per criterion 1: a corrected number drifts again the next
time §6 grows — which is exactly how 933 reached 33 lines out, and this pass
demonstrated the point directly: while resolving `#0371` in the same session,
`PRD.md` §6.2's schema comment on `invite_resent_at` grew by 4 lines (to name
the real write-once enforcer instead of the migration's mistaken one), which
pushed §6's own guarded table row from 966 to 970. Had `#0370` corrected the
prose to 966, it would already be wrong again by the time this same commit
landed. This matches the phase's repeated finding (`#0330`, `#0347`, `#0356`):
removing a claim beats adding a checker for it. Extending the guard (option 2)
was rejected — it would pin a number nobody reads for precision (the sentence
only needs to convey "take the subsection"), for the cost of a new regex-based
prose scanner that itself becomes one more thing to keep in sync.

**Criterion 4's judgement call — does the reworded prose still do its job?**
Yes, and it loses nothing a reader needs. Two reasons:

1. **The imperative is untouched.** "take the subsection, not the parent" is the
   actionable half and is what §11 exists to say; the number was only the
   supporting *why*. "By far the largest section" carries that same why
   qualitatively.
2. **The number was never lost — it was a duplicate.** §6's exact line count sits
   in the guarded table row three lines above the sentence. A reader who wants
   the figure reads the row, which the parity guard keeps correct. The edit
   removes a second, unguarded copy of a fact that already has a guarded home.
   That is a single-source-of-truth fix, not an information loss.

I also checked the replacement claim is robustly true rather than merely
currently true: §6 is 970 against the next-largest top-level section (§4 at
181) — **5.4x**. "By far the largest" has enormous headroom and will not become
false through ordinary editing, which is exactly the property the numeric
version lacked.

**Criterion 1 — confirmed the stale number is gone, not corrected.** I scanned
§11 for any surviving `is <N> lines` prose outside the guarded preamble: none.
