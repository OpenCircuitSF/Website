## Description

Generated `sitemap.xml` covering the static routes plus every published workshop, and a `robots.txt` that allows the public site while excluding the admin and API namespaces.

## Root cause

Not a bug fix — new capability. No `/sitemap.xml` or `/robots.txt` route existed at all before this issue; `internal/handlers`'s catch-all SPA handler would have served the HTML shell (404, since neither path is in the known-route table) for both.

## Fix

Extended `internal/seo.Site` (introduced in #0019, same batch) rather than adding a parallel type, since both the sitemap and the meta injector need the same `WorkshopSource` and the same `InvalidateWorkshops` trigger.

`internal/seo/sitemap.go` adds `Sitemap`, built from `marketingRoutes` (`/`, `/about`, `/workshops`, `/subscribe` — a hand-curated list, deliberately **not** `handlers.StaticRoutes()`, which also contains the Phase 1 auth/token routes that must not be indexed) plus every workshop from the (still-nil-until-#0051) `WorkshopSource` whose `Status == WorkshopPublished`; draft/unpublished/canceled are filtered out inside this package rather than trusted to the eventual store's query. `internal/seo/robots.go` adds `BuildRobotsTxt`, which allows `/` and disallows `/admin`, `/account`, `/api`, `/auth`, `/confirm`, `/preferences`, `/unsubscribe`, and appends a `Sitemap:` line. `Site` gained `SitemapHandler`/`RobotsHandler` (mounted on `GET /sitemap.xml` / `GET /robots.txt` in `cmd/opencircuit/main.go`) and `InvalidateWorkshops` now clears the sitemap's cache in addition to the meta-tag renderer's.

## Gotchas

- **`marketingRoutes` is intentionally a curated subset, not `handlers.StaticRoutes()`.** Deriving it from the fuller table would have pulled in `/login`, `/account`, `/admin`, and — worse — the token-carrying `/confirm`, `/preferences`, `/unsubscribe` into the sitemap. `TestSitemap_MarketingRoutesAreKnownRoutes` still asserts every curated entry passes `handlers.IsKnownRoute`, satisfying this issue's carried-in criterion without coupling the sitemap's contents to the full route table.
- Same route-table parity finding as #0019 applies here: `internal/handlers/routes.go` and `web/src/lib/router.ts` agree today (checked programmatically — see #0019's Gotchas for the exact comparison), but nothing enforces it going forward; `#0071` is still open.
- `robots.txt` is computed once at `Site` construction (no TTL cache) since it has no dynamic/DB-backed content — only the sitemap depends on workshop data and needs the TTL+invalidate treatment.

## Acceptance criteria

- [x] `GET /sitemap.xml` returns valid XML with `<loc>` and `<lastmod>` for `/`, `/about`, `/workshops`, `/subscribe`, and each published workshop

## Carried in from `#0022`'s review (2026-08-18)

One obligation transferred here rather than left half-met on `#0022`. It is a
binding acceptance criterion for this issue.

- [x] **The 404 route is not listed in `sitemap.xml`.** `#0022`'s fifth
      criterion required this; it was trivially true there only because no
      sitemap existed. Once this issue builds one, the exclusion has to be a
      real, asserted property. The sitemap is built from an explicit list of
      published routes plus published workshops, so this should fall out of the
      design — but assert it in `go test ./internal/seo/...` rather than
      relying on it, alongside the existing draft/unpublished/canceled
      exclusions. Any path that `internal/handlers`' `isKnownRoute` rejects
      must never appear in a `<loc>`.

**Read before you start — the route table is not what it claims to be.** If you
generate the sitemap's static-route portion from
`internal/handlers`'s `knownStaticRoutes`, note that that table is a
hand-maintained mirror of `web/src/lib/router.ts`'s `STATIC_ROUTES` and nothing
enforces the two agree — the reviewer added a route to each side alone and the
full Go and TypeScript suites stayed green in both directions. A drift means a
sitemap advertising a URL the client router 404s, or omitting a real page.
`#0071` owns closing that gap. Note also that `robots.txt` must disallow
`/confirm`, `/preferences` and `/unsubscribe` even though all three *are*
known routes — "known" and "should be indexed" are different questions and the
route table answers only the first.

## Notes

PRD §7.4. Disallowing `/confirm`, `/preferences`, and `/unsubscribe` matters: those URLs carry tokens, and an indexed token URL is a token leak.

Until #0051 lands, the workshop portion of the sitemap can be empty — ship the static routes now.

## Review findings (2026-08-18) — approved, with one correction

**`TestSite_InvalidateWorkshopsClearsBothCaches` does not in fact guard both
halves.** The drafted `## Verification` and the code commit message both claim
it "guards the pairing so a future edit can't silently wire only one half back
in". The reviewer disproved that by mutation: deleting `s.sitemap.Invalidate()`
from `Site.InvalidateWorkshops` leaves the whole `internal/seo` suite green —
the test only asserts the renderer's cache was cleared and never inspects the
sitemap's. The **behavior** is correct (both caches really are cleared today,
and the criterion is met), and the path is inert until `#0051` supplies a
non-nil `WorkshopSource`, so this is not a bounce; but the guard the issue
claims to have is not there. Worth adding a `Sitemap`-side assertion when
`#0051` wires the real source in.

The three exclusion properties this issue actually turns on were each mutation-
tested and do hold: dropping the `WorkshopPublished` filter fails
`TestSitemap_ExcludesUnpublishedWorkshops` (draft/unpublished/canceled all
appear in the printed XML), and removing `/confirm` from `disallowedPaths` fails
`TestBuildRobotsTxt_TokenRoutesAreKnownButDisallowed` with the intended message.

Two notes carried from `#0019`'s review that also bear on this issue:
`.env.example` sets `BASE_URL` to the **apex**, which — now that `<loc>` and the
`Sitemap:` line are built from it — would publish a sitemap on the non-canonical
host on the documented deploy path (`CLAUDE.md` §7); and `Sitemap.built` is
stamped once at `NewSitemap` time, so a long-running process reports its start
date as every static route's `<lastmod>` forever. The latter is conservative
(never claims content is fresher than it is) and needs no fix now.
