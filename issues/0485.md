## Description

`web/tsconfig.json`'s `include` is exactly:

	"include": ["src/**/*.ts", "src/**/*.svelte"]

`web/vite.config.ts` is not under `src/`, so it is outside that glob and no
other tsconfig picks it up. **`npm run check` type-checks nothing in it.**

That was harmless while the file was declarative. It is not declarative any
more: `#0408` added `spaNavigationBypass`, a predicate with a `GET`/`HEAD`
gate, a path allowlist, query-string stripping, and header inspection, whose
correctness decides whether a browser navigation reaches Vite or Go. A silent
mistake there produces a **blank page** — the exact symptom `#0408` existed to
fix, and one that reads as a broken build rather than a type error.

## Root cause

`web/tsconfig.json`'s `include` names only `src/**/*.ts` and `src/**/*.svelte`,
and `npm run check` (`svelte-check --tsconfig ./tsconfig.json`) only resolves
files inside a tsconfig's own `include`. `web/vite.config.ts` sits at the
project root, outside that glob, so it was never a candidate for
`svelte-check` to look at regardless of what it contained.

## Fix

Widening `tsconfig.json`'s own `include` to reach `vite.config.ts` was
rejected rather than attempted: the file calls `process.env` and imports
`IncomingMessage` from `node:http`, and neither resolves without
`@types/node`. A quick `tsc --noEmit` against the file with no config changes
confirmed this directly — it reported `Cannot find module 'node:http'` and
`Cannot find name 'process'` before any fix landed. Adding `@types/node` to
`tsconfig.json`'s `types` array to fix that would hand every file under
`src/**` the ambient Node globals (`process`, `Buffer`, the `NodeJS`
namespace) that `@types/node` installs, even though everything under `src/`
runs in the browser and none of those globals exist there — exactly the
"different lib/types requirement" this issue's first criterion warned a naive
widening could cause.

Instead, added `web/tsconfig.node.json` — a second, narrow tsconfig scoped to
`vite.config.ts` alone, with its own `types: ["node"]` and no `extends` from
`@tsconfig/svelte`, since the file doesn't touch Svelte. This is the shape
Vite's own scaffolded templates use to separate build-time config from
application source. Added `@types/node` as a `devDependency` so the new
config's `node:http` and `process` references resolve, and changed the
`check` script to `tsc -p tsconfig.node.json --noEmit && svelte-check
--tsconfig ./tsconfig.json` — the new pass runs first and is cheap, and
`tsconfig.json`'s own `types` array (`["svelte", "vite/client"]`) is
unchanged, so `@types/node`'s globals never become visible to anything under
`src/`.

Proved the file is now actually checked, per criterion 2: recorded its
SHA-256, changed the tail of `spaNavigationBypass` from `return undefined;`
to `return 42;` — a value that violates its declared `string | undefined`
return type — and re-ran `npm run check`. It failed at exit code 2, naming
`vite.config.ts(64,3)` and `Type 'number' is not assignable to type
'string'.`, with `svelte-check` never reached because the new `tsc` step
short-circuited the `&&` first. Reverted the one-line change and re-hashed the
file: the SHA-256 matched the pre-edit value exactly
(`c83949fc...c98ee3e`), and `git status --porcelain -- web/vite.config.ts`
showed no diff at all afterward.

Confirmed criterion 3 by running `npm run check` again after the fix: the
`svelte-check` pass still reports the same 293 files, 0 errors, 0 warnings it
reported before this change, since `tsconfig.json`'s `include` was never
touched. No pre-existing errors surfaced anywhere, because nothing new was
added to that config's scope — the whole point of the second-tsconfig design
was to avoid widening it at all, so there was no glob expansion left to
surface a defect in some other unchecked file.

**Siblings (criterion 4), left unfixed:** `web/svelte.config.js` is the other
root-level config file outside any tsconfig's `include`. It carries a single
call to `vitePreprocess()` with no arguments and no branching logic — nothing
like `spaNavigationBypass`'s predicate — so leaving it unchecked does not
carry the same risk this issue was filed over. It is also a plain `.js` file
rather than `.ts`, so bringing it under type checking would additionally mean
deciding whether to rename it or turn on `allowJs`/`checkJs` for a second
config, which is more than this pass's scope justifies for a file with no
logic to get wrong. There is no separate Vitest config file to check either —
this project has no `vitest.config.ts`; Vitest reads its settings out of
`vite.config.ts` itself, the same file this issue already brings under
checking. `web/embed.go` is the one other root-level file under `web/`, but
it is Go source checked by `go vet`/`gofmt`, not by `npm run check`, so it was
never a candidate here.

## It has now mattered twice

- Flagged once on the abandoned worktree branch during `#0408`'s original
  review there, and left untracked.
- Flagged again by `#0408`'s review on `main`, which verified the gap itself
  rather than repeating the earlier claim.

Both times it was noticed while reviewing changes *to that very file*. That is
the tell: the only thing catching mistakes in it is human attention, applied at
exactly the moments when the file is being changed and least stable.

## What makes it worse than an ordinary uncovered file

`#0408`'s predicate is exercised only by `vite dev`. It is absent from the
production build — the built SPA is served by Go from one origin with no proxy —
so **no test in the suite runs this code**, and `vite build` output was
measured byte-identical before and after the change. Type-checking is the only
static signal available, and it is switched off.

## Acceptance criteria

1. **Bring `web/vite.config.ts` under type checking.** Options include adding it
   to `include`, adding a second tsconfig for build-time files, or a
   `tsconfig.node.json` of the shape Vite's own templates use. Pick one and say
   why.
2. **Prove it is actually checked afterwards.** Introduce a deliberate type
   error in that file, confirm `npm run check` fails and names it, then remove
   it and confirm the file is byte-identical (SHA-256 before and after). A check
   never seen to fail is not a check (`CLAUDE.md` §8).
3. **Do not break the existing check.** `npm run check` currently reports 293
   files with 0 errors and 0 warnings; whatever you change must leave it clean.
   If widening the glob surfaces pre-existing errors in other unchecked files,
   report them rather than silencing them — and say whether fixing them belongs
   here or in a separate issue.
4. **Check for siblings.** Other root-level config files (`svelte.config.js`,
   `vitest` setup, any script under `web/`) may be in the same position. Name
   them; do not necessarily fix them in this pass.
5. **Do not run `npm run build`** (`CLAUDE.md` §8b) — it overwrites the tracked
   `web/dist/index.html` placeholder, which three agents have already hit. If
   you must, restore with `git show HEAD:web/dist/index.html > web/dist/index.html`,
   never `git checkout` (§8a).

### What was verified and stands — do not redo this

  namespace, and under the same options with `"node"` appended to `types` it
  exited 0. The rejected one-line `include`-widening really would have handed
  every browser-only file the ambient Node globals, so the extra config file
  earns its place.
- **The separation holds after the change.** A throwaway module placed under
  `web/src/lib/` referencing `process` and `Buffer` still fails `npm run
  check` with the same two `Cannot find name` errors, reported at 294 files

### What must change

Three comments now assert the opposite of what this commit did. They are not
historical notes — each is written in the present tense about the current
dependency tree, and one of them offers a reproducible measurement that today
returns the opposite of what it reports.

1. **`web/src/lib/nodeFsShim.d.ts`** is the primary site and the one the other

### Why this is a bounce rather than a follow-up issue

The staleness was created by the commit under review, so it is that commit's
own debt. It also points a future agent the wrong way: a comment stating
`zero new devDependencies` as a precedent to preserve is an instruction, and
acting on it by removing the package breaks the very `tsc` step this issue
added. The remedy above is three comment edits and one `scripts/check.sh web`
run, fully specified, so the next pass stays on Sonnet per `CLAUDE.md` §3.

The design decision itself should be **recorded, not reversed**. Reversing
that precedent is defensible here and this review endorses it: the earlier
pass avoided `@types/node` because `import.meta.glob` gave a browser-safe
alternative for a file under `src/`, and `web/vite.config.ts` has no such
alternative, since it genuinely runs in Node. What was missing is that
`## Fix` never acknowledged the precedent it was overturning. Say so there
too.

knowing rather than worth changing.
