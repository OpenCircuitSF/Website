## Description

User request, 2026-11-17: "Each guide also has a heading which is the LED strip. Can we change it to use the new images instead?" Clarified: "The image at the top of each card which is a series of colored boxes."

On `/guides` (`web/src/views/GuidesIndex.svelte`), every guide card starts with a `MiniStrip` (a row of coloured boxes, `web/src/lib/topics/MiniStrip.svelte`). Since `#0709` (v0.15.0) every guide has its own 1200×630 image, embedded from `internal/seo/cardassets/guides/<slug>.png` and served at `/guides/{slug}/og.png`. The cards should show that image in place of the strip. The workshop guide card (`/workshops/programming-leds`, the `workshops` section) should do the same: its art is `programming-leds.png`, served at `/guides/programming-leds/og.png`.

Things the plan must settle:
- **Weight.** 43 images at 70–265 KB each is several MB for one page. Consider a smaller thumbnail (e.g. a width-limited variant served by the Go side) and `loading="lazy"` plus explicit `width`/`height` so the grid doesn't shift. PRD §7.6 is the performance budget.
- **Cache-busting.** `og:image` carries `?v=<hash>` (`#0709`); the SPA doesn't know the hash. Decide whether the card URL needs it (the route already sends an ETag and `max-age=3600`).
- **Fallback.** A guide added later without art: keep `MiniStrip` for it, or show the generated title card the route already falls back to.
- **Alt text.** Decorative (`alt=""`) since the card already carries the title, unless the plan argues otherwise.
- The static no-JS fallback for `/guides` (`internal/seo` fallback-copy guards, AGENTS.md §5 table) may need the same change or an explicit decision not to.
- The strip inside the guide page's "Try it with real hardware" box is **out of scope**; the user means the card image only.

## Plan

Written 2026-11-17, phase 1 (Opus · medium).

**Design in one line:** a new Go route, `GET /guides/{slug}/thumb.jpg`, serves a 640×336 JPEG made at runtime from exactly the bytes `/guides/{slug}/og.png` serves: the hand-made art when present, else the generated title card. Each card on `/guides` shows that thumbnail as a lazy, fixed-size `<img alt="">` in place of `MiniStrip`. The SPA needs no manifest and no fallback branch, and nothing new is committed except code.

### Settled points

1. **Weight: serve a Go-made thumbnail, never the full art.** Measured on 2026-11-17 over the 43 files in `internal/seo/cardassets/guides/`:

   | Variant | Total for 43 | Largest |
   |---|---|---|
   | Full art as served today (1200×630 PNG) | **6,425,421 B** (6.4 MB) | 263,193 B |
   | 640×336 PNG resized with `sips` (truecolor) | 6,980,724 B | 244,515 B |
   | 640×336 PNG with `pngquant` 60–85 | 993,531 B | 50,029 B |
   | 640×336 JPEG q75 via `sips` | 956,376 B | 38,615 B |
   | 640×336 WebP q75 via `cwebp` | 264,466 B | 13,930 B |
   | **640×336 JPEG q80 via Go (`x/image/draw.CatmullRom` + `image/jpeg`)** | **605,144 B** | **24,541 B** |

   **Choose the last row.** It's 9.4% of the full art, about 14 KB per card. With `loading="lazy"`, only the first screenful loads up front (3 to 9 cards, at most about 220 KB). Measured on the laptop, generating all 43 took 0.86 s, about 20 ms each. A t4g.small is maybe 3–5× slower. Each thumbnail is made once, on first request, and then held in memory, about 600 KB for all of them.

   **Why runtime Go rather than committed pre-made thumbnails (`sips` + `pngquant`/`cwebp`)?** WebP would be 2.3× lighter. But it would mean:
   - A second copy of every image in git.
   - A manual step the user must remember each time Codex art is replaced.
   - A staleness hazard no cheap guard can catch (a thumbnail made from the old art passes a slug-set parity check).
   - A presence manifest so the SPA knows which guides have art.

   The runtime path keeps one source of truth, and `golang.org/x/image/draw` is **already a dependency** (`go.mod` has `golang.org/x/image v0.40.0`). `internal/outreach/thumbnail.go` already uses the same scale-then-JPEG pattern. Go has no WebP encoder, so runtime means JPEG. 605 KB, lazy-loaded, is reasonable. PRD §7.6 has no image budget. Its relevant lines are **LCP < 2.0 s on 4G** (the `h1`/lede text block is the LCP element, and lazy images below it don't compete) and **0 external requests** (same-origin, so satisfied).

   **Why 640×336:** 1200×630 scaled exactly (630·640/1200 = 336). Cards are `minmax(280px, 1fr)` inside a 1040 px shell, so about 320 CSS px wide at three columns. 640 covers that at 2× DPR. A one-column card on a tablet (up to ~560 px) is slightly upscaled at 2×, which is acceptable for decorative art.
2. **Cache-busting: no `?v=` on the card URL.** The thumbnail route sends `Cache-Control: public, max-age=3600` and a strong content ETag, like `og.png`. Replaced art therefore shows on `/guides` within an hour of a deploy, and immediately on a revalidating reload. `og:image` needed `?v=` because third-party unfurl caches key on the URL and never revalidate. A browser does revalidate, so the SPA doesn't need the hash. Exposing it would mean an API or a build-time manifest for no real gain.
3. **Fallback: the generated title card, downscaled.** It comes from the same route, because the thumbnail is made from `Site.GuideCard(slug)`, which already falls back. The SPA has one code path and no art-presence knowledge. This is consistent with `#0709`'s settled fallback for `og.png`.

   The cost: a guide without art shows its title twice, once in the image and once in the card's `<strong>`. Today all 43 guides have art, so this happens only to a guide added in future before its art lands. That is acceptable for a stop-gap. **The alternative, keeping `MiniStrip` for art-less guides, is a product choice and is flagged below.** It would require a presence manifest.
4. **Alt text: `alt=""`.** The card link's accessible name is already its tags, title and hook. The art illustrates the title without adding information. A non-empty alt would make screen readers read the title twice inside one link.
5. **Static no-JS fallback for `/guides` (`internal/seo/fallback.go`): no change, by decision.** It is a text list of links for crawlers and no-JS visitors (`guideListItems`). Images there add bytes and nothing indexable. The fallback-copy guards (`TestStaticFallbackCopyMatchesSvelteViews`) compare copy strings only, and no copy changes. `internal/seo` must still run, because `GuidesIndex.svelte` is in its scan roots.
6. **Out of scope:** the strip in the "Try it with real hardware" box. `web/src/views/TopicGuide.svelte` keeps importing `MiniStrip`, so the component stays.

### Approach

1. **`internal/seo/site.go`.**
   - Generalise `writePNG` into `writeImage(w, r, contentType string, body []byte, etag string)`, with the same headers and 304 logic. Keep `writePNG` as a one-line wrapper (or replace its two call sites; either is fine).
   - Add `thumbMu sync.Mutex` and `thumbs map[string]guideThumb` to `Site`. `newSite` initialises the map.
2. **`internal/seo/guidethumb.go`.**
   - Constants:
     - `guideThumbW = 640`
     - `guideThumbH = 336`
     - `guideThumbQuality = 80`
     - `guideThumbMaxBytes = 40_000`, a ceiling with headroom over the measured 24,541 B maximum.
   - `type guideThumb struct { data []byte; etag string }`.
   - `func (s *Site) guideThumb(slug string) (guideThumb, error)`:
     - Take `s.thumbMu`, which serialises generation so a cold burst decodes one image at a time, as in `outreach`'s `shrinkMu`.
     - Return the cached entry if present.
     - Otherwise call `s.GuideCard(slug)`, then `png.Decode`, then `image.NewRGBA(640×336)`, then `draw.CatmullRom.Scale(dst, dst.Bounds(), src, src.Bounds(), draw.Src, nil)`, then `jpeg.Encode` at Q80. The art has no alpha (`sips -g hasAlpha` reports none for all 43), and the generated card is opaque.
     - Compute the etag with `cardETag(data)` and store it.
     - Both art and the generated card are build-time-fixed per slug, so the cache never needs invalidating. Note that in the doc comment.
   - `func (s *Site) GuideThumbHandler() http.HandlerFunc`:
     - `guides.Lookup(r.PathValue("slug"))` failing → `http.NotFound`.
     - An error from `guideThumb` → `http.Error` 500 plus a log line. Don't decline silently (AGENTS.md §5, `#0470`).
     - Otherwise `writeImage(w, r, "image/jpeg", t.data, t.etag)`.
     - Doc comment: serves GET /guides/{slug}/thumb.jpg (`#0710`), the /guides card image, made from the same bytes as `GuideCardHandler`.
3. **`cmd/opencircuit/main.go`.** Directly under the `/guides/{slug}/og.png` registration in `mountAndServe`, add `mux.Handle("GET /guides/{slug}/thumb.jpg", site.GuideThumbHandler())` with a one-line `#0710` comment. `mountAndServe` serves both `STORAGE=json` and Postgres, so dev mode gets it too.
4. **`web/vite.config.ts`.** Add a proxy entry so `./scripts/dev.sh` on :5173 can load thumbnails: `'^/guides/[^/]+/thumb\\.jpg$': apiTarget`. Vite treats a key starting with `^` as a RegExp. It can't collide with an SPA route, since no SPA route ends in `.jpg`. Add a comment.
5. **`web/src/lib/guides.ts`.** Add `export function guideThumbPath(slug: string): string` returning `` `/guides/${slug}/thumb.jpg` ``. Also add `export const GUIDE_THUMB = { width: 640, height: 336 } as const;`, with a comment naming `internal/seo/guidethumb.go`'s constants.
6. **`web/src/views/GuidesIndex.svelte`.**
   - Drop the `MiniStrip` import.
   - In both card kinds, replace the strip with:
     `<img class="thumb" src={guideThumbPath(t.slug)} alt="" width={GUIDE_THUMB.width} height={GUIDE_THUMB.height} loading="lazy" decoding="async" />`
     Use `g.slug` for the workshop card, which yields `/guides/programming-leds/thumb.jpg`.
   - CSS: `.thumb { display: block; width: 100%; height: auto; aspect-ratio: 640 / 336; border-radius: 4px; background: var(--guide-pcb); }`. The intrinsic width/height plus `aspect-ratio` reserve the box before load, so there is no layout shift. The background shows while loading.
   - Don't change any copy, so the fallback-copy guard stays green.

## Obstacles

- **No browser on the host** (AGENTS.md §8). Layout, no-shift and lazy loading are evidenced by markup in jsdom (sized `img`, `loading="lazy"`) rather than by a rendered check. A Tart VM check isn't worth it for this change. State that the evidence rests on jsdom.
- **Shared `web/dist/index.html`.** Only the optional `dev.sh --built` check touches it. Restore it with `git show HEAD:web/dist/index.html > web/dist/index.html`, never `git checkout`.
- **Ports.** Same optional check. Use a non-default port and confirm the response is from your build (AGENTS.md §8b).
- **Tools.** Nothing new. `golang.org/x/image` is already in `go.mod`. `pngquant`, `cwebp` and `sips` are now installed (`#0709`'s obstacle note said `pngquant` wasn't), but this plan doesn't use them.
- **Concurrent agents.** At planning time `git status` showed only `.opencode/` untracked. Stage only the files listed above, and check `git diff --cached --name-only` before committing (AGENTS.md §8a).
- **No approval-gated steps.** Deploying is the user's step.

### User decisions (product, not engineering)

1. **Fallback for a guide without art:** a downscaled generated title card (planned; the title then appears twice on that card), or keep the LED strip. The strip needs a small art-presence manifest for the SPA. The default is the title card unless the user says otherwise. Today it affects no guide.
2. **Image weight vs format:** about 605 KB total as JPEG made by the server (planned, no manual step), or about 265 KB as committed WebP thumbnails. The WebP route needs a regeneration step every time art changes. The default is the JPEG route.

## Review notes

2026-11-17, phase 3 (Opus · medium). **Pass — resolved.**

Read `9367448c` against the plan and the acceptance criteria:

- **Route.** `GET /guides/{slug}/thumb.jpg` is registered beside `og.png` in `mountAndServe` (both storage modes). An unknown slug returns 404 via `guides.Lookup`. The thumbnail is made from `Site.GuideCard`, so a guide without art gets the generated title card, the same fallback `og.png` uses. The workshop card points at `/guides/programming-leds/thumb.jpg`. `TOPICS` is still imported because grouping uses it, and `MiniStrip` stays in use in `TopicGuide.svelte`.
- **Weight**, re-measured: `guide thumbnails: 43 images, 605144 bytes total, largest 24541`, under the 40,000 B per-image cap that `TestGuideThumb_EmbeddedSetWeight` enforces.
- **Vite proxy.** The `'^/guides/[^/]+/thumb\\.jpg$'` key uses Vite's leading-`^` RegExp form and cannot match an SPA route.
- **No-JS fallback and the copy guards.** No copy changed. `internal/seo` passed with `TestStaticFallbackCopyMatchesSvelteViews` and the rest of the fallback-copy family.
