## Description

`docs/deployment.md` contradicts itself about TLS, and the wrong half is the
runnable one.

**Line 106 is right.** It records the cert as a single ECDSA **wildcard**
covering `opencircuitsf.com` and `*.opencircuitsf.com`, issued through the
**`dns-route53`** authenticator, renewed by `certbot-renew.timer` — and notes
that renewal therefore never reads the vhosts or `/.well-known/acme-challenge`,
so no Apache change in this project can break it.

**Line 889 is a command that contradicts it:**

	sudo certbot --apache -d opencircuitsf.com -d www.opencircuitsf.com

`--apache` is HTTP-01. **HTTP-01 cannot issue a wildcard** — Let's Encrypt
requires DNS-01 for `*` names. And the `-d` list names only two hosts.

Verified against the live endpoint: the served certificate's SAN is
`DNS:*.opencircuitsf.com, DNS:opencircuitsf.com`.

### What running it would do

Replace a wildcard covering every subdomain with a certificate for two names,
and switch the renewal path from DNS-01 to HTTP-01.

**`go.opencircuitsf.com` would lose coverage** — that is the ShortLinks deploy
(`CLAUDE.md` §1), a *different* project on the same box. So the blast radius
crosses a project boundary.

It would also make renewal depend on Apache and `/.well-known/acme-challenge`
again — and `CLAUDE.md` §7 records that `/.well-known/` is a deliberate
`ProxyPass … !` carve-out serving `atproto-did` from disk. Coupling renewal back
to that path is exactly the fragility line 106 says the current setup avoids.

**Found by `#0431`'s sweep**, which noticed the documented command could not
have produced the live certificate.

## A second discrepancy in the same DNS material

`docs/deployment.md`'s DNS table names the DKIM CNAME under the **apex**
(`<sel1..3>._domainkey.opencircuitsf.com`), while `docs/email-setup.md` — and
`docs/deployment.md`'s own prose 21 lines later — put it under
**`mailing.opencircuitsf.com`**.

The `mailing.` form is right: `CLAUDE.md` §10 records the verified SES identity
as `mailing.opencircuitsf.com`, and §9 forbids touching the apex, which carries
real Google Workspace mail. A DKIM record published at the apex would be both
wrong and adjacent to a restricted area.

Confirmed: both bare `_domainkey.*` names resolve only through the zone's
wildcard, so neither is a real record — the live ones carry selector prefixes.

### Blocking 1 — the file still contains two accounts of TLS (criterion 2)

Criterion 2 asks for **one account of TLS in that file, not two**. §9 is now
correct, but the prerequisites section roughly 600 lines earlier still
describes the HTTP-01 world, and an operator working the runbook top to bottom
hits it *before* reaching §9. As it stands the runbook installs the wrong
plugin and then runs a command that cannot work:

	sudo dnf install -y openssl certbot python3-certbot-apache

`--dns-route53` is provided by `python3-certbot-dns-route53`, which this line
does not install. Measured on the box, both are in fact present
(`python3-certbot-2.6.0`, `python3-certbot-apache-2.6.0`,
`python3-certbot-dns-route53-2.6.0`, `certbot-2.6.0`), so the box is fine —
the **document** is what is wrong. A fresh box built from this runbook would
fail §9's command with an unable-to-find-authenticator error.

**Remedy, verbatim.** In the `**`openssl` and `certbot`**` prerequisite,
replace the fenced command with:

	sudo dnf install -y openssl certbot python3-certbot-dns-route53

and add, immediately after that fence, a dated note in the same style the DNS
table rows in this file already use:

	**Corrected 2026-09-05, `#0436`:** this step previously installed
	`python3-certbot-apache`. That is the plugin §9 now says must never be
	used here — it is HTTP-01 and cannot issue this domain's wildcard — and
	it does not provide `--dns-route53`, so the runbook as it stood
	installed one plugin and then invoked another. Measured on the box,
	both packages are present (`python3-certbot-apache-2.6.0` and

### Blocking 3 — the rewritten reload paragraph asserts what the box contradicts

This pass rewrote the reload lead-in from "Reload once more if certbot didn't
already" to:

	Reload Apache only if a manual `certonly` run (not the timer) obtained a new
	certificate and Apache hasn't picked it up:

and the paragraph above it to open "Certbot's own renewal timer needs no manual
step here."

Read together, those tell an operator that the timer path requires no reload.
**Nothing on this box reloads Apache after a renewal — the timer's included.**
Measured read-only, four ways:

- `/etc/letsencrypt/renewal-hooks/deploy/` — empty.
- `/etc/letsencrypt/renewal-hooks/post/` — empty.
- `/etc/sysconfig/certbot` — `PRE_HOOK=""`, `POST_HOOK=""`, `DEPLOY_HOOK=""`;
  every reload example in it is commented out.
- `certbot-renew.service` — `ExecStart=/usr/bin/certbot renew --quiet`, and
  nothing else. No `ExecStartPost`, no reload.

The renewal config has no installer either, so certbot has no path to touch
Apache on its own. `mod_ssl` reads the certificate at configuration time, so
after an unattended renewal Apache keeps serving the **previous** certificate
until something reloads it.

This is the `#0431` distinction firing on this pass's own text: the work log
records exactly this finding — "no `/etc/letsencrypt/renewal-hooks/deploy/`
script exists on the box" — and then the document was written to say the
opposite for the automatic path. A statement that goes past its evidence to
assert a fact is the defect; here the evidence was in hand and pointed the
other way.

**Remedy, verbatim.** Replace the two spans above. For the timer paragraph's
opening sentence, use:

	The renewal timer itself needs no manual step — it is already installed
	and running.

For the reload lead-in, use:

	**Reload Apache after any renewal, including the timer's.** Re-verified
	read-only for this pass: `/etc/letsencrypt/renewal-hooks/deploy/` and
	`/etc/letsencrypt/renewal-hooks/post/` are both empty,
	`/etc/sysconfig/certbot` sets `PRE_HOOK`, `POST_HOOK` and `DEPLOY_HOOK`
	to the empty string, and `certbot-renew.service` is a bare
	`certbot renew --quiet`. The renewal config configures no installer. So
	nothing reloads Apache when the certificate is replaced, and `mod_ssl`
	goes on serving the previous one until it is. After a manual `certonly`,
	run the reload yourself. For the unattended path there is currently no
	mechanism at all — a gap in the box's configuration, not something this
	document can fix:

Leave the existing fenced `systemctl reload httpd` / `curl … /health` block
where it is; it is the right pair.

**Do not change anything on the box** — criterion 6 still holds, and this
remedy is documentation only. **Do not file an issue for the missing deploy
hook** (`CLAUDE.md` §9); report it and let the orchestrator allocate the
number. It is genuinely separate from `#0430` and `#0435`, neither of which
this pass absorbed — correctly.
