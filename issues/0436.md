## Description

`docs/deployment.md` contradicts itself about TLS, and the wrong half is the
runnable one.

**Line 106 is right.** It records the cert as a single ECDSA **wildcard**
covering `opencircuitsf.com` and `*.opencircuitsf.com`, issued through the
**`dns-route53`** authenticator, renewed by `certbot-renew.timer` — and notes
that renewal therefore never reads the vhosts or `/.well-known/acme-challenge`,
so no Apache change in this project can break it.

**Line 889 is a command that contradicts it:**

	sudo certbot --apache -d opencircuitsf.com -d www.opencircuitsf.com

`--apache` is HTTP-01. **HTTP-01 cannot issue a wildcard** — Let's Encrypt
requires DNS-01 for `*` names. And the `-d` list names only two hosts.

Verified against the live endpoint: the served certificate's SAN is
`DNS:*.opencircuitsf.com, DNS:opencircuitsf.com`.

### What running it would do

Replace a wildcard covering every subdomain with a certificate for two names,
and switch the renewal path from DNS-01 to HTTP-01.

**`go.opencircuitsf.com` would lose coverage** — that is the ShortLinks deploy
(`CLAUDE.md` §1), a *different* project on the same box. So the blast radius
crosses a project boundary.

It would also make renewal depend on Apache and `/.well-known/acme-challenge`
again — and `CLAUDE.md` §7 records that `/.well-known/` is a deliberate
`ProxyPass … !` carve-out serving `atproto-did` from disk. Coupling renewal back
to that path is exactly the fragility line 106 says the current setup avoids.

**Found by `#0431`'s sweep**, which noticed the documented command could not
have produced the live certificate.

## A second discrepancy in the same DNS material

`docs/deployment.md`'s DNS table names the DKIM CNAME under the **apex**
(`<sel1..3>._domainkey.opencircuitsf.com`), while `docs/email-setup.md` — and
`docs/deployment.md`'s own prose 21 lines later — put it under
**`mailing.opencircuitsf.com`**.

The `mailing.` form is right: `CLAUDE.md` §10 records the verified SES identity
as `mailing.opencircuitsf.com`, and §9 forbids touching the apex, which carries
real Google Workspace mail. A DKIM record published at the apex would be both
wrong and adjacent to a restricted area.

Confirmed: both bare `_domainkey.*` names resolve only through the zone's
wildcard, so neither is a real record — the live ones carry selector prefixes.
