# 0037 — Verify SNS message signatures

| | |
|---|---|
| **Status** | open |
| **Module** | sesnotify |
| **Platform** | All |
| **Phase** | 4 — Unsubscribe and list hygiene |
| **First seen** | 2026-08-18 |

## Description

Before any SES event is trusted, the SNS message signature must be verified. An unverified endpoint lets anyone forge bounce events and mass-suppress the list.

## Acceptance criteria

- [ ] `internal/sesnotify` verifies `SignatureVersion` 1 and 2 messages
- [ ] `SigningCertURL` validated to be HTTPS with a host under `amazonaws.com` **before** the certificate is fetched
- [ ] Canonical string built per SNS's documented field order for each message type
- [ ] Signature verified against the certificate's public key; fetched certificates cached by URL
- [ ] Unverified messages are rejected and logged — never processed
- [ ] `SubscriptionConfirmation` handled by fetching `SubscribeURL` once, then logged
- [ ] `UnsubscribeConfirmation` alerts and never acts
- [ ] Tests cover a valid signature, a tampered payload, a hostile `SigningCertURL`, and both signature versions

## Notes

PRD §6.7, §11. The `SigningCertURL` check is an SSRF guard, not a formality: without a host allowlist applied *before* the fetch, an attacker points it at an internal address and the service fetches whatever they choose.

This issue exists separately from #0038 because signature verification is a security boundary that deserves its own tests and its own review, not a paragraph inside a larger feature.

  inject a fake that never dials AWS.
- `internal/audit` establishes the `querier` idiom (`Write` / `WriteTx` over an

- Highest migration is `000011`. #0037 adds **no migration**.

### 1. Decision — manual verification, no new dependency

**Verify manually with the standard library.** `crypto/x509`, `crypto/rsa`,
`crypto/sha1`, `crypto/sha256`, `encoding/pem`, `encoding/base64` cover the
whole job in roughly 150 lines.

Justification: there is no SDK helper to prefer (see §0), so "SDK helper vs
manual" is really "third-party module vs standard library". Adding a
third-party verifier for a security boundary this small — one canonical-string
builder, one `rsa.VerifyPKCS1v15` call, one URL check — buys nothing and adds
a supply-chain surface to the one code path whose whole purpose is to be
trustworthy. The implementer should **confirm** the "no SDK helper" claim
before writing code (`go doc github.com/aws/aws-sdk-go-v2/service/sns` after a
`go get`, then drop it again) rather than take this plan's word for it; if a
helper does turn up, prefer it and record the change here.

### 2. Decision — accept SignatureVersion 1 and 2, warn on 1

`SignatureVersion` `"1"` is RSA-SHA1, `"2"` is RSA-SHA256. Accept both, as the
acceptance criteria require, and log at WARN whenever a `"1"` message is
verified so the operator can see whether the topic has actually been switched.

Justification: SHA-1's break is collision resistance, not second-preimage. To
forge a v1 message an attacker would need a chosen-prefix collision *and* would
need AWS to sign one half of it — the signature is produced by SNS's private
key, which the attacker does not hold. So v1 is not practically forgeable here.
Meanwhile the topic's signature version is set at topic creation, the topic
does not exist yet (CLAUDE.md §10 open item 2), and hard-rejecting v1 would
mean a misprovisioned topic silently drops every bounce event — a deliverability
failure that is invisible until the domain's reputation is already damaged.

**Provisioning note for whoever creates the topic (§10 open item 2): set
`SignatureVersion` to 2 on `opencircuit-ses-events`.** Once that is confirmed
in production, a follow-up issue can flip the code to reject v1 outright. Do
not add a config flag for this now — it would be a knob nobody turns.

Unknown `SignatureVersion` values (anything other than `"1"`/`"2"`) are
rejected, not defaulted.

### 3. Decision — the `SigningCertURL` host constraint

**The acceptance criterion as written is not sufficient and must be tightened.
See §9 (correction note 1).** Implement this instead:

```
scheme  == "https"                       (exact, case-insensitive)
u.User  == nil                           (no userinfo — "https://sns.us-west-2.amazonaws.com@evil.com/…")
u.Port() == ""                           (no explicit port)
host    := strings.ToLower(strings.TrimSuffix(u.Hostname(), "."))
host    matches ^sns\.[a-z0-9-]+\.amazonaws\.com$
```

and additionally require `host == "sns." + cfg.AWSRegion + ".amazonaws.com"`
when `AWSRegion` is set, which it always is in production (it is in the
`required` table). The regex is the floor; the region pin is the actual rule.

Mechanics that matter:

- Parse with `net/url.Parse` and use `u.Hostname()` — **never** substring or
  suffix matching on the raw URL string, and never `u.Host` (which carries the
  port).
- The check runs **inside `Verify`, before the fetcher seam is invoked**, so it
  cannot be bypassed by a test fake or a future caller (see §7).
- **Redirects are a second SSRF vector.** Set
  `http.Client.CheckRedirect` to return `http.ErrUseLastResponse` — refuse
  redirects entirely. AWS serves the PEM directly; a redirect is either a
  configuration change worth failing loudly on, or an attack.

### 4. Decision — certificate cache and fetch behaviour

- Cache **by exact validated URL string** in a `map[string]*x509.Certificate`
  behind a `sync.RWMutex` on the `Verifier`. AWS rotates the cert roughly
  yearly and the URL changes with it, so URL-keyed caching is
  self-invalidating.
- **Bound the map at 16 entries.** The fetch happens *before* signature
  verification — that is unavoidable, you need the key to verify — so an
  attacker who can reach the endpoint can drive cache growth with distinct
  valid-host paths. On reaching the cap, clear the map rather than implementing
  LRU; the steady state is one entry and a flush costs one refetch.
- `http.Client{Timeout: 5 * time.Second}`, response body read through
  `io.LimitReader(body, 32<<10)`, non-200 is an error.
- Reject a certificate whose `NotBefore`/`NotAfter` do not bracket now, and
  reject a public key that is not `*rsa.PublicKey`.
- **Do not attempt chain validation.** The HTTPS fetch to a pinned
  `sns.<region>.amazonaws.com` host is what authenticates the certificate;
  Go's TLS stack already validated that chain. Adding a second, hand-rolled
  chain check adds a failure mode without adding a property.
- **Fetch failure is a 500, not a 403** — see §6. A transient network error
  means verification could not be *performed*; it is not evidence the message
  is forged, and treating it as one loses the event permanently.

### 5. Decision — `SubscriptionConfirmation` is automatic but topic-pinned

**Auto-confirm, gated on a configured topic ARN allowlist.**

The hijacking risk is concrete and is the reason the gate is mandatory: a valid
SNS signature proves *SNS sent this*, **not** *our topic sent this*. Any AWS
account in the world can create a topic and subscribe our public endpoint to
it. If we auto-confirm every `SubscriptionConfirmation` that verifies, that
attacker's topic is now confirmed, and every `Notification` they publish
through it carries a genuine SNS signature and an attacker-authored `Message`
body — i.e. forged bounce and complaint events, and mass suppression of the
list. That is precisely the outcome this issue's `## Description` exists to
prevent, and signature verification alone does not prevent it.

So:

- Add `SESEventsTopicARN` to `internal/config` from `SES_EVENTS_TOPIC_ARN`.
  **Not** in the `required` table — the topic does not exist yet, and making it
  required would stop the binary booting.
- **Every** message type is checked: `msg.TopicArn` must equal
  `cfg.SESEventsTopicARN` (exact string compare). Mismatch → log at WARN with
  the offending ARN, respond `403`, do nothing else.
- If `SESEventsTopicARN` is empty, no message can match, so everything is
  rejected. Log that case at ERROR with a distinct message ("SES events topic
  ARN not configured; rejecting all SNS deliveries") so it reads as
  misconfiguration rather than attack. Register the route anyway — a 403 shows
  up in SNS's delivery-failure metrics, an unregistered route yields a bare 405
  from `ServeMux` that is harder to diagnose.
- Only after both signature and ARN check pass: fetch `SubscribeURL` once,
  `GET`, ignore the body, log at INFO, write an audit row
  (`ses.subscription_confirmed`), respond `200`.
- **Validate `SubscribeURL` with the same host allowlist as `SigningCertURL`
  before fetching it.** It is an attacker-influenced URL in exactly the same
  way. Same client, same no-redirect policy, same timeout.

Rejected alternatives: *manual* confirmation (an ops step that will be
forgotten, and its failure mode is silent — no events, no error); *config-gated
with a boolean* (a second knob that adds nothing the ARN pin does not already
give, since the ARN pin is what makes auto-confirmation safe).

`UnsubscribeConfirmation`: **never act, never fetch anything.** Log at ERROR
and write an audit row (`ses.unsubscribe_confirmation`). This message means our
endpoint has been unsubscribed from the SES events topic — we will stop
receiving bounces and complaints, and nothing else in the system will notice.
Respond `200` (there is nothing for SNS to retry).

### 6. Decision — HTTP status codes

The distinction that matters: **verification failed** vs **verification could
not be performed**.

| Condition | Status | Why |
|---|---|---|
| Body unreadable / not JSON / `Type` unknown | `200` | A malformed body is not fixed by retrying. Log it. |
| `SigningCertURL` fails the host check | `403` | Forged. SNS gives up on 4xx — correct; an attacker must not be able to make us retry. |
| Signature does not verify | `403` | Same. |
| `SignatureVersion` unsupported | `403` | Same. |
| `TopicArn` not the configured topic | `403` | Same. |
| Certificate **fetch** fails (network, non-200, timeout) | `500` | Verification could not be performed. SNS retries; the event is not lost. |
| Verified, but a downstream write fails (#0038) | `500` | See #0038 §5 — this is the one place a *valid* message must 5xx. |
| Verified and handled | `200` | |

Body size: wrap with `http.MaxBytesReader(w, r.Body, 512<<10)`. SNS caps
messages at 256 KB; 512 KB is a comfortable ceiling that still refuses a
resource-exhaustion body.

### 7. Package shape and the seam

Create `internal/sesnotify`:

```
internal/sesnotify/doc.go        package doc: what is trusted and why
internal/sesnotify/message.go    the SNS envelope type + canonical-string builder
internal/sesnotify/verify.go     Verifier: URL validation, cert fetch/cache, signature check
internal/sesnotify/*_test.go     beside the code, per CLAUDE.md
```

**This package must have no database dependency and no HTTP handler.** #0037
`Blocks` #0058 (inbound unsubscribe mail), which is a second SNS endpoint with
a completely different payload and no relationship to `email_events`. Keeping
the verifier free of storage is what makes that reuse possible. #0038 adds
`store.go` to this same package for `email_events`; the doc comment must state
that `verify.go`/`message.go` deliberately import neither `pgx` nor
`internal/handlers`, so the split survives.

The envelope:

```go
type Message struct {
    Type             string  // Notification | SubscriptionConfirmation | UnsubscribeConfirmation
    MessageId        string
    Token            string
    TopicArn         string
    Subject          string
    Message          string  // for SES config-set events this is JSON-as-a-string
    SubscribeURL     string
    Timestamp        string
    SignatureVersion string
    Signature        string
    SigningCertURL   string
    UnsubscribeURL   string
}
```

**Read `Type` from the JSON body, never from the `x-amz-sns-message-type`
header.** Headers are not covered by the signature and are entirely
attacker-controlled. The same goes for `x-amz-sns-topic-arn`. This is worth an
explicit comment at the parse site.

The seam:

```go
type Verifier struct {
    region     string
    httpClient *http.Client
    fetchCert  func(ctx context.Context, url string) (*x509.Certificate, error) // nil ⇒ real fetcher
    cache      map[string]*x509.Certificate
    mu         sync.RWMutex
    log        *slog.Logger
}

func (v *Verifier) Verify(ctx context.Context, m *Message) error
```

`Verify` calls `validateCertURL(m.SigningCertURL)` **first**, unconditionally,
and only then reaches for `fetchCert`. A test fake therefore cannot mask a
missing URL check — which is the property the hostile-URL test asserts (§8).

### 8. Canonical string — exact field order

Each included field contributes `name + "\n" + value + "\n"`, concatenated in
this order. Fields absent from the message are **omitted entirely**, not
emitted with an empty value — `Subject` is the one that actually varies.

`Notification`:

```
Message, MessageId, Subject (only if present), Timestamp, TopicArn, Type
```

`SubscriptionConfirmation` and `UnsubscribeConfirmation`:

```
Message, MessageId, SubscribeURL, Timestamp, Token, TopicArn, Type
```

Then: `base64.StdEncoding.DecodeString(m.Signature)`, hash the canonical string
with SHA-1 (v1) or SHA-256 (v2), and `rsa.VerifyPKCS1v15(pub, crypto.SHA1 |
crypto.SHA256, digest, sig)`.

**Do not add a timestamp-freshness rejection.** SNS's HTTPS retry policy can
span days, so a freshness window would drop legitimate retries; and replay of a
*signed* event is harmless because #0038's writes are idempotent and its
dedupe key is the SNS `MessageId`. Record `Timestamp` in `email_events` and let
idempotency carry the load. Note the reasoning in the code so a later reader
does not "fix" it.

### 9. Corrections to the acceptance criteria

Recorded here rather than edited into the checkbox list, per the planning
brief.

**Correction 1 — criterion 2 is insufficient as written and must be
tightened.** "`SigningCertURL` validated to be HTTPS with a host under
`amazonaws.com`" is a live forgery path, not a conservative approximation.
`amazonaws.com` is a shared-tenancy domain: `<any-bucket>.s3.amazonaws.com` is
a host under `amazonaws.com` that **anyone with an AWS account can upload an
arbitrary PEM to**. An attacker uploads a certificate for a keypair they
control, points `SigningCertURL` at their bucket, signs a forged bounce
notification with their own private key, and it verifies. The whole
verification passes and the list gets mass-suppressed — exactly the outcome
this issue exists to prevent. The constraint must be
`^sns\.[a-z0-9-]+\.amazonaws\.com$`, region-pinned where `AWS_REGION` is known
(§3). The implementer should treat the criterion as satisfied by the stricter
rule and note the tightening in `## Fix`.

**Correction 2 — criterion 7 is incomplete.** "`SubscriptionConfirmation`
handled by fetching `SubscribeURL` once, then logged" must be conditioned on
the topic-ARN allowlist (§5). Auto-confirming any signature-valid subscription
hands the endpoint to any AWS account that asks. The `SubscribeURL` also needs
the same host validation as `SigningCertURL` before it is fetched.

**Correction 3 — an unstated but required criterion: `TopicArn` allowlisting.**
Neither this issue nor #0038 mentions it, and PRD §6.7 does not either. A valid
signature proves the message came from SNS, not that it came from *our* topic.
Without the ARN check every other control in this issue is bypassable by any
AWS customer. Treat it as a criterion; it needs its own test.

### 10. Test strategy — no AWS, no network

`internal/sesnotify` tests are pure Go with **no `TEST_DATABASE_URL`
dependency** (the store arrives in #0038), so this package must report a real
non-zero duration and zero skips.

1. **Keypair and certificate generated in the test.** `rsa.GenerateKey(rand,
   2048)` → `x509.CreateCertificate` self-signed → PEM. Do this once per test
   binary in a helper, not per subtest; 2048-bit keygen is the slowest thing in
   the suite.
2. **Sign in the test.** Build the canonical string with the *same helper the
   production code uses* for the valid case (that is fine — the tampered and
   field-order cases are what catch a wrong builder), sign with SHA-1 and with
   SHA-256, base64 the result. Assert both `SignatureVersion` `"1"` and `"2"`
   verify.
   - Additionally assert one **golden canonical string** byte-for-byte against
     a literal in the test, for a `Notification` with a `Subject` and one
     without. This is what actually pins the field order — reusing the builder
     on both sides otherwise makes the round-trip tautological.
3. **Tampered payload.** Sign, then mutate `Message` (and separately
   `TopicArn`, and separately drop `Subject`) → each must fail verification.
4. **Hostile `SigningCertURL` table** — the important one. Inject a fetcher
   that **records whether it was called** and assert `Verify` returns an error
   **and the fetcher was never invoked** for each of:
   - `http://sns.us-west-2.amazonaws.com/x.pem` (not HTTPS)
   - `https://sns.us-west-2.amazonaws.com.evil.com/x.pem` (suffix trick)
   - `https://evil.com/sns.us-west-2.amazonaws.com.pem` (path trick)
   - `https://my-bucket.s3.amazonaws.com/x.pem` (**correction 1's attack** —
     must fail; passes under the criterion as literally written)
   - `https://sns.us-west-2.amazonaws.com@evil.com/x.pem` (userinfo)
   - `https://169.254.169.254/latest/meta-data/` (IMDS)
   - `https://sns.us-west-2.amazonaws.com:8443/x.pem` (port)
   - `https://sns.eu-west-1.amazonaws.com/x.pem` (wrong region, with region
     pinning on)
   - `file:///etc/passwd`, empty string
   And, as positive controls that must **pass** validation:
   `https://SNS.US-WEST-2.AMAZONAWS.COM/x.pem` (case) and
   `https://sns.us-west-2.amazonaws.com./x.pem` (trailing dot).
5. **Redirect refusal**: an `httptest` server that 302s to another host; assert
   the fetch errors rather than following. (This test drives the *real* fetcher
   against a local server, so it must call the fetcher directly with validation
   stubbed for the host — or, simpler, assert `CheckRedirect` is wired by
   exercising the client, and keep the host-check test separate.)
6. **Cache**: two `Verify` calls with the same URL invoke the fetcher once;
   17 distinct URLs do not grow the map past the cap.
7. **Fetch failure → the error is classified as retryable.** Export a sentinel
   (`ErrCertUnavailable`) so #0038's handler can map it to `500` while every
   other verification error maps to `403`. Test the classification, not just
   the error text.
8. **Envelope-vs-header**: a request whose `x-amz-sns-message-type` header says
   `Notification` but whose body `Type` says `SubscriptionConfirmation` is
   handled as the *body* says.

No `npm` verification: this issue touches no SPA code.

### 12. Suggested order

1. `Message` + `canonicalString` + the golden-string test. Get the field order
   right and pinned before anything else touches it.
2. `validateCertURL` + the hostile-URL table. Pure function, no I/O, and it is
   the actual security boundary.
3. `Verifier.Verify` with the fetcher seam; signature tests for v1 and v2 and
   the tamper cases.
4. Real cert fetcher: client, no-redirect policy, size limit, cache,
   `ErrCertUnavailable`.
5. Config variable.
6. `go build ./... && go vet ./... && go test ./internal/sesnotify/... -count=1 -v`,
   then the full suite with `TEST_DATABASE_URL` exported (CLAUDE.md §5) and
   confirm zero skips.

### 13. Left open for the implementer

- Whether to expose the region pin as a `Verifier` field or read `AWSRegion`
  at construction. Either is fine; construction-time is simpler.
- The exact cache eviction on cap (clear-all vs. drop-one). Clear-all is
  recommended for simplicity; the steady state is one entry.
- Whether `ses.subscription_confirmed` / `ses.unsubscribe_confirmation` audit
  rows use `TargetType` `"sns_topic"` or `"ses"`. Pick one and be consistent
  with #0038.
