# 0037 — Verify SNS message signatures

| | |
|---|---|
| **Status** | open |
| **Module** | sesnotify |
| **Platform** | All |
| **Phase** | 4 — Unsubscribe and list hygiene |
| **First seen** | 2026-08-18 |

## Description

Before any SES event is trusted, the SNS message signature must be verified. An unverified endpoint lets anyone forge bounce events and mass-suppress the list.

## Acceptance criteria

- [ ] `internal/sesnotify` verifies `SignatureVersion` 1 and 2 messages
- [ ] `SigningCertURL` validated to be HTTPS with a host under `amazonaws.com` **before** the certificate is fetched
- [ ] Canonical string built per SNS's documented field order for each message type
- [ ] Signature verified against the certificate's public key; fetched certificates cached by URL
- [ ] Unverified messages are rejected and logged — never processed
- [ ] `SubscriptionConfirmation` handled by fetching `SubscribeURL` once, then logged
- [ ] `UnsubscribeConfirmation` alerts and never acts
- [ ] Tests cover a valid signature, a tampered payload, a hostile `SigningCertURL`, and both signature versions

## Notes

PRD §6.7, §11. The `SigningCertURL` check is an SSRF guard, not a formality: without a host allowlist applied *before* the fetch, an attacker points it at an internal address and the service fetches whatever they choose.

This issue exists separately from #0038 because signature verification is a security boundary that deserves its own tests and its own review, not a paragraph inside a larger feature.
