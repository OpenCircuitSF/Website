## Description

`github.com/OpenCircuitSF/Website` is **public**, and tracked files carry
concrete infrastructure identifiers for the production account and host.

| Value | Tracked files |
|---|---|
| AWS account id | 18 |
| Route 53 hosted zone id | 10 |
| Instance ids (current + retired) | 21 |
| Public IPs (current + retired) | 21 |
| Hostnames (current + retired) | ~18 |
| IAM role name | 9 |

**None of these is a credential.** There is no key, token, or password to
rotate. They are reconnaissance material: together they name exactly which
account, host, DNS zone and role to aim at.

## Decision — 2026-09-12, by the user

**Redact going forward. Do not rewrite history.**

The reasoning, recorded so it is not relitigated: these values are already in
the public history of a repo with 900+ commits. Rewriting that history is
disruptive, breaks every existing clone and hash reference, and is close to
futile once anything has cloned, forked, or indexed the repository. The values
should therefore be treated as **known-public**, and the goal is to stop adding
more and to remove them from the current tree — not to pretend they were never
published.

The user also maintains a **private** repo for this material:
`github.com/brennanMKE/AWS`, checked out at `~/Developer/AWS`, which already
holds `terraform/`, `ses/`, `iam/`, `dns/`, `remote/` and `scripts/`.

## The split to apply

**Public repo — the procedure, parameterised.** Steps, ordering, safety checks,
rationale. Hosts and accounts as shell variables or placeholders
(`"$DEPLOY_HOST"`), with a line saying the concrete values live in the private
repo. A local ssh-config **alias name** such as `ssh photon` is fine — it is a
label on the operator's own machine, not an address.

**Private repo — the values**, and anything that names them: host, account,
instance, zone, role, bucket ARNs, and a wrapper script supplying them.

## Scope

In scope: every **tracked, currently-live** file — `CLAUDE.md`, `HANDOFF.md`,
`docs/`, `deploy/`, `scripts/`, and **open or in-progress** issue files.

Out of scope, deliberately:

- **Resolved issue files.** Same boundary `#0508` applied and `#0466`'s review
  established: dated records of what was measured at a time. Redacting them
  falsifies the record, and since history is not being rewritten it buys
  nothing — the same strings remain a `git log` away.
- **Git history**, per the decision above.

## Acceptance criteria

1. No tracked file that is live operational text contains the account id,
   either public IP, either instance id, the hosted zone id, either hostname,
   or the IAM role name.
2. Every place a value is removed still tells the reader **where to find it** —
   a pointer to the private repo, not a silent deletion that leaves a procedure
   unrunnable.
3. The sweep that proves criterion 1 is **whitespace-tolerant**. `#0508` was
   bounced precisely because `grep 'ssh ec2'` missed a copy wrapped across a
   line break, and its second review found the implementer's own count off by
   nine for the same class of reason. Say what you ran.
4. Resolved issue files are byte-untouched. State how many hits were left and
   why.
5. Consider a guard that fails if a restricted identifier reappears in a live
   file. Weigh it against `CLAUDE.md` §8's warning about guard sprawl and say
   where you land — **either answer is acceptable, an unexamined one is not.**
   Note the oracle problem if you do add one: a guard listing the forbidden
   strings necessarily contains them, so it must live somewhere that is not
   itself the thing being scanned, or match by pattern rather than by literal.

## Notes

Worth being clear-eyed about what this does and does not achieve. It stops the
leak growing and makes the current tree clean. It does **not** unpublish
anything. Anyone who wants these values can still read them out of history —
so no security decision should rest on their being secret.

## Fix

**The restricted set is the nine `scripts/release.sh` already encodes.**
`#0514`'s `RESTRICTED_B64` array — the AWS account id, both public IPs, both
EC2 instance ids, the hosted zone id, both hostnames, and the *current* IAM
role name — is the tracker's settled enumeration (`#0509`'s reviews counted
the same nine). This pass adopts it verbatim. Consequences, each deliberate:

- **The retired role name is not redacted.** It is not one of the nine; the
  issue's criterion 1 says "the IAM role name" singular. It survives in live
  prose that quotes it as the *old* value (`docs/aws-iam-setup.md`,
  `docs/deployment.md`, `CLAUDE.md` §7's blockquote).
- **`ec2.sstools.co`, `ec2.smallsharptools.com`, the awsdns nameserver
  hostnames, instance types/sizes, `us-east-1`, and the `photon`/`ec2` ssh
  aliases are left.** Not on the list; the aliases are explicitly permitted
  ("a label on the operator's machine, not an address").
- **`closed` and `wontfix` issue files join `resolved` as out of scope** (40
  hits across 15 files, byte-untouched — criterion 4). The issue names
  `resolved`; the same dated-record boundary is what `closed`/`wontfix` are,
  and the status filter is one line.

**The sweep** replaced values with a fixed placeholder vocabulary —
`$AWS_ACCOUNT_ID`, `$DEPLOY_HOST`, `$DEPLOY_INSTANCE_ID`, `$DEPLOY_IP`,
`$DEPLOY_ROLE`, `$ROUTE53_ZONE_ID` in commands and ARNs, and prose naming the
private repo elsewhere — so criterion 2's pointer rides in the same edit
everywhere: `CLAUDE.md` §7's lead note, `docs/aws-iam-setup.md`'s header
block, `docs/aws-requests.md`'s account line, `docs/email-setup.md`'s header,
`docs/deployment.md`'s Instance-ID row, `docs/ses-inbound-remaining.md`'s
preamble, `deploy/aws/README.md`'s Placeholders block, and comment lines in
`.env.example` and PRD §9. Two knock-on guard fixes the edits forced:
PRD §9 gained three comment lines, so `CLAUDE.md` §11's §9 row moved 76 → 79
and §11's preamble line count 1,879 → 1,882 — both caught by their guards on
the first verification run, both fixed rather than argued with.
`deploy/aws/*.json` keep valid JSON with `AWS_ACCOUNT_ID` as a template value.

**Criterion 5 — a guard was added, and here is the weighing.** For: the
going-forward rule had so far rested on per-pass manual diffs (`#0509` ran
five passes of them), and `scripts/release.sh`'s existing scan covers only
the assembled bundle at publish time — the repo tree between releases was
exactly the gap this issue exists to close. Against: `CLAUDE.md` §8's guard
sprawl. Where it lands: **added, in-package**
(`internal/db/identifier_redaction_guard_test.go`, on the default `go` arm,
not the rarely-run `guards` arm — the go_file_visit_floor precedent). The
oracle problem is resolved by single-sourcing: the guard decodes
`scripts/release.sh`'s base64 array at test time and contains no literal
itself, so a value rotation updates one array and the guard follows. It is
**exact-value, not shape-based** on purpose: shape patterns would either
false-positive (12-digit numbers, base64 blobs against a zone-id shape) or
embed lookalike fragments, and the next rotation is one array edit away.
Deliberately not an external `scripts/*_guard_test.sh` harness: a harness's
positive controls would need the real values in a tracked file, which is what
the redaction forbids; non-vacuity is proven instead by in-memory synthetic
positives built from the decoded list (verbatim flagged, wrapped-across-a-
line-break flagged, clean buffer clear). `CLAUDE.md` §8 prefers an external
harness for anything whose failure mode is "the checker was edited"; that
preference is answered here rather than followed, because the harness's own
positive controls are the thing the redaction forbids — the in-package shape
with in-memory positives is the alternative that keeps every tracked file
free of the values. Fail-closed
floors cover an emptied list, an implausibly small tree, and a missing
issue-status row.

## Verification

Whitespace-tolerant sweep, run three times (inventory → after redaction →
post-commit; criterion 3): a python3 script over `git ls-files`, reading each
tracked file's full bytes, searching them literally **and** as a copy with
separator runs removed — whitespace, backticks, asterisks, underscores and
backslashes, the class `issues/0508.md`'s second
review enumerated, which is what a line-anchored grep misses. The nine values
were decoded at runtime from `scripts/release.sh`'s `RESTRICTED_B64`; all
output names value indexes, never the values, and the script lived in
`.scratch/` (untracked, deleted afterwards).

- Before: **15 live files carried 58 value-hits** (the issue's table said
  18/10/21/21/~18/9 tracked-file occurrences — same scale, stricter value
  set).
- After: **0 live hits.** 40 hits remain in 15 `resolved`/`closed`/`wontfix`
  issue files — byte-untouched, per criterion 4 and the issue's own boundary.

Guard, first run: `ISSUE=0511 scripts/check.sh go ./internal/db/...
./internal/handlers/... ./internal/config/...` — `internal/config` added
because `.env.example` was edited, `internal/handlers` because `CLAUDE.md`
was (`CLAUDE.md` §5's reach table). It failed once — `#0511`'s own PRD §9
line additions had moved §11's preamble count — fixed, re-run:

    ok  internal/db  0.838s   ok  internal/handlers  14.598s   ok  internal/config
    gofmt -l: (clean)   go_file_visit_floor_guard_test.sh: 0 failures

Mutation proof for the new guard: appended one value to

needed.

## Gotchas

- `scripts/release.sh`'s bundle scan only ran at publish time — between
  releases the tree had no automated check, which is why five `#0509` passes
  each re-ran the manual diff by hand. The new guard closes that interval.
- The guard is exact-value and single-sourced. If the infrastructure rotates
  (new instance, new IP), the old value can be *dropped* from
  `scripts/release.sh`'s array (history keeps it) and the new one added — the
  guard and the release scan both follow that one edit.
- The retired role name, `ec2.sstools.co`, `ec2.smallsharptools.com`, and the
  awsdns nameserver hostnames remain in live files by design — outside the
  nine. If the set ever widens, it widens in `scripts/release.sh`'s array
  first.
