## Description

`CLAUDE.md` §10 item 2 describes SES production access as the one remaining
piece, with the account still sandboxed — 200/day, 1/sec, verified recipients
only — and says that **when granted**, `SES_SANDBOX=false` and
`SEND_WORKER_ENABLED=true` should be flipped.

**Production already carries exactly that flip**, read read-only from
`/etc/opencircuit/config.env`:

	SES_SANDBOX=false
	SEND_WORKER_ENABLED=true

So either access was granted and §10 was never updated, or the flags were
flipped without it. Both are worth knowing, and the difference matters: if the
account is still sandboxed, `SES_SANDBOX=false` means the code will stop
applying sandbox-aware handling while AWS still enforces sandbox limits.

### The caveat — this is not fully confirmed

`#0271`'s reviewer **could not** verify `ProductionAccessEnabled` directly. The
box's default AWS CLI identity is the `certbot-dns-updater` IAM user, which is
denied `ses:GetAccount`. The flipped flags are the only evidence available
without hunting a credential that review had no business hunting.

**So the first job is to establish the ground truth, not to edit the doc.**

## Why this matters now

The user is about to send their first real newsletter to a real list. Whether
SES is sandboxed decides whether that send reaches anyone who is not a verified
identity. §10 currently tells a reader it will not.

## Re-scoped 2026-09-05 — this is not a one-file correction

`#0431`'s second review found that the **unconfirmed sandbox state is asserted
in at least five places in `docs/deployment.md`**, plus `#0057`'s "Production
flags" facts table — not only in `CLAUDE.md` §10 item 2, which is all this issue
originally named.

**Without that inventory the next sweep of `docs/deployment.md` rediscovers the
same drift.** Three passes over that file already have.

### The distinction that matters when you fix it

`#0431`'s reviews established a rule worth keeping:

- A downstream statement that **attributes** the sandbox state to `CLAUDE.md`
  §10 item 2 is **defensible as it stands**. The uncertainty lives in the
  source; this issue owns the source; hedging every citation would duplicate one
  fix in five places.
- A statement that goes **past** its citation to assert a production
  configuration value as measured fact is **a defect**. `#0431`'s third pass
  bounced on exactly that — text claiming `SEND_WORKER_ENABLED=false` when every
  reading says `true`, with an invented causal account resolving *this issue's*
  open question on the side the evidence contradicts.

So: **fix §10 item 2, then re-read the downstream statements** and correct only
those that overclaim. Do not hedge the ones that cite properly.

### What the deploy document now says, which you must reconcile

`docs/deployment.md` records, from a read-only 2026-09-03 reading of
`/etc/opencircuit/config.env`: `SES_SANDBOX=false` **and**
`SEND_WORKER_ENABLED=true` — "the flip §10 item 2 says to make only *after*
access is granted" — and explicitly defers to this issue rather than settling
it. `MAX_SEND_RATE=10` is measured in the same reading, against
`docs/deployment.md`'s instruction to use `1` while sandboxed.

**That is the substance.** If `ProductionAccessEnabled` is **false**, production
is configured as though access were granted: sandbox-aware handling disabled and
a send rate ten times the cap. That is a live defect, not a documentation
problem, and criterion 3 already says to stop for a decision rather than change
production.

## Acceptance criteria

1. **Establish whether SES production access is actually granted**, from AWS
   rather than from the flags. `aws sesv2 get-account` returns
   `ProductionAccessEnabled`. Note the box's default identity lacks
   `ses:GetAccount` — say what identity you used, and **do not** grant new IAM
   permissions or create credentials to get the answer without asking first.
2. `CLAUDE.md` §10 item 2 reflects the measured truth, dated, and item 2's
   "remaining" framing is corrected if nothing remains.
3. **If access is NOT granted**, `SES_SANDBOX=false` on production is a live
   defect, not a doc problem — say so plainly and stop for a decision rather
   than changing production.
4. The sandbox trap §10 records stays recorded: in the sandbox SES authorises
   `SendEmail` against the *recipient's* identity ARN too, so the role policy
   needs `identity/*`, and a send to a simulator address will **not** catch a
   policy that gets this wrong.
5. **Do not touch production configuration.** Read-only only.
6. Editing `CLAUDE.md` means running **both** `./internal/db/...` and
   `./internal/handlers/...` (§5's repo-wide-guard table). Per §5 name the
   specific tests that ran. No Go-file-plus-line-number citation (`#0352`).
