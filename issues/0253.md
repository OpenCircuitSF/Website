## Description

`scripts/db_reset_guard_test.sh` creates its scratch database under a **fixed**
name, `opencircuit0207gt`. Two agents running it at once collide.

This is not hypothetical: `#0250`/`#0251`'s implementer hit exactly that
collision from a concurrent agent while working, and recorded it. It
self-resolved on retry, which is the least useful failure mode — intermittent,
unexplained, and easy to blame on the code under test rather than on the
harness.

`CLAUDE.md` §5a makes concurrent agents the norm and §8b is explicit: a shared
mutable resource must be namespaced or ownership-verified. The project already
has the convention — `ISSUE=NNNN`, `scripts/testdb.sh create NNNN` — and
`#0247` has just applied it to the restore drill for the same reason.

**The irony is the point.** This is the guard test for `db-reset.sh`, a script
whose entire defect was destroying a database another agent was using. Its test
harness has the same defect, one level down.

**A related consideration for whoever takes this:** the test deliberately
exercises destructive paths, including `--force`, which terminates connections
and drops databases. A fixed name means a concurrent run's database is a live
target for another run's `--force`. That is worse than a name clash — it is the
guard test performing the exact action the guard exists to prevent, against a
database it does not own.

- [x] Cleanup drops only what that run created; the existing `pg_database` census assertion (added by `#0250`) still passes
- [x] Proved by running the guard test twice concurrently to completion, both passing, neither touching the other's database — census before and after

## Fix pass

Fixed `scripts/testdb_gc_guard_test.sh` first, per the Notes' explicit
ordering (it can corrupt a concurrent run's database AND misattribute the
damage, which is worse than `db_reset_guard_test.sh`'s plain name clash),
then `scripts/db_reset_guard_test.sh`, then `scripts/dev_guard_test.sh`.
`git status --porcelain` was checked before starting: only
`internal/handlers/audit_email_metadata_guard_test.go` was dirty (another
agent's file, per this dispatch's constraints — never touched).

**All three scripts now derive a per-run identifier** the same way, reusing
the project's existing convention rather than inventing a second one:

```sh
RUNID_RAW="${ISSUE:-$$}"
RUNID="$(printf '%s' "$RUNID_RAW" | tr -cd '[:alnum:]' | tr '[:upper:]' '[:lower:]')"
```

`ISSUE`, falling back to the shell's own PID — the same fallback `#0247`
used for the restore drill, and for the same reason: `$$` is always a
distinct, purely-numeric token per process, which sidesteps the mixed-case
identifier fold `#0208` fixed in `testdb.sh`'s `name_for()` (a token
containing letters can make Postgres fold a database name to a spelling the
calling script never asked for). Stripping to alnum-only and lower-casing
here closes the same class of bug at every one of these three new call
sites, per the fourth acceptance criterion.

**`scripts/testdb_gc_guard_test.sh`.** `TESTPREFIX="opencircuit_test_0150gt_"`
(fixed) → `TESTPREFIX="opencircuit_test_${RUNID}gt_"`. The two private
`sed`-generated copies (`testdb_scoped.sh`, `testdb_mutant.sh`, both already
living under `mktemp -d` so their *paths* never collided) hard-coded the same
literal `"opencircuit_test_0150gt_"` as the `sed` replacement text — fixed to
interpolate `${TESTPREFIX}` instead, so the copies' `PREFIX=` now matches the
namespaced value the rest of the script checks for and scopes its `gc --all`
sweep to. `createdb_raw()` used to swallow every error
(`>/dev/null 2>&1`, no exit check); it now captures `psql`'s exit code and
output, and `exit 1`s loudly, naming the failure as a probable collision,
rather than silently appending to `CREATED_DBS` and letting the run continue
against a database it does not actually own.

**`scripts/db_reset_guard_test.sh`.** `TESTDB="opencircuit0207gt"` (fixed) →
`TESTDB="opencircuit${RUNID}gt"`, preserving the invariant the header comment
documents and now updated to describe it correctly: alnum-only `RUNID` means
`TESTDB` still starts with `opencircuit` but never contains an underscore
right after it, so it can never collide with `testdb.sh`'s
`opencircuit_test_<id>` scratch-database naming. Part 5's fixed
`opencircuit_test_0207gt_demo` → `DEMODB="opencircuit_test_${RUNID}gt_demo"`.
The private `SCOPED`/`MUTANT` copy paths
(`scripts/.db_reset_scoped_0207gt.sh` / `scripts/.db_reset_mutant_0207gt.sh`)
were themselves a fixed, shared filename — unlike `testdb_gc_guard_test.sh`'s
copies, these live directly in `scripts/` (not under `mktemp -d`; `db-reset.sh`
resolves its own repo root from its own path, so a copy has to stay inside
`scripts/`), so two concurrent runs writing the *same* path could stomp on
each other's copy mid-run or have one run's cleanup `rm -f` delete the file
the other run was still executing. Namespaced to
`.db_reset_scoped_${RUNID}.sh` / `.db_reset_mutant_${RUNID}.sh`. The
`pg_database` census — previously `datname like 'opencircuit%'`, matching
every agent's scratch database, not just this run's — is now additionally
filtered to `and datname like '%${RUNID}%'`, so a concurrent run's own
databases appearing or disappearing during this run's before/after window
can no longer make the census spuriously disagree; every database this
script itself creates embeds `RUNID` by construction, so nothing this run
could actually leak falls outside that pattern.

**`scripts/dev_guard_test.sh`.** The issue named three fixed ports
(`P1=54301`, `P2=54311`, `P3A=54321`); grepping the file for the actual
pattern found **nine**, not three — six more inline literals
(`54331`, `54341`, `54351`, `54361`, `54371`, `54381`) passed directly to
`run_foreign_survives_scenario` / `run_connector_survives_scenario` /
`run_slow_build_scenario` for Parts 3b/4/5/6/7/8, spaced by exactly 10 from
the three named ones — clearly the same deliberate numbering scheme, just
not fully enumerated in the issue text. Fixed all nine, not just the three
named, since leaving the other six fixed would still guarantee a collision
under the concurrent-run proof the last acceptance criterion demands. Added
near the top of the script:

```sh
RUNHASH="$(printf '%s' "$RUNID" | cksum | awk '{print $1}')"
PBASE=$(( 40000 + ( (RUNHASH % 200) * 100 ) ))   # 40000..59900, 200 buckets
P1="$((PBASE + 1))" ; P2="$((PBASE + 11))" ; P3A="$((PBASE + 21))"
P3B="$((PBASE + 31))" ; P4="$((PBASE + 41))" ; P5="$((PBASE + 51))"
P6="$((PBASE + 61))" ; P7="$((PBASE + 71))" ; P8="$((PBASE + 81))"
```

`cksum` gives a numeric hash regardless of whether `RUNID` itself is
numeric, so this doesn't depend on the project's `ISSUE=NNNN` convention
staying purely numeric. The three `P1=54301`-style literal reassignments at
their original call sites were deleted (they would otherwise silently
clobber the namespaced values computed above), and the six inline literals
were replaced with `"$P3B"`/`"$P4"`/`"$P5"`/`"$P6"`/`"$P7"`/`"$P8"` at their
call sites, including the one place (`$((54371))` in a failure message) that
recomputed the literal a second time rather than referencing a variable.
`:5173` — Vite's own, hardcoded, unavoidable port — is untouched, as the
issue's Notes direct; the parts that reach it already require it free and
abort rather than force through.

Two new `sed` substitutions in `db_reset_guard_test.sh` and
`testdb_gc_guard_test.sh` switched from single-quoted to double-quoted `sed`
scripts to interpolate `${TESTPREFIX}` / `${TESTDB}` into the replacement
text — `$RUNID` is always alnum-only by construction, so it can never
contain a `sed`-special character that would need escaping in that position.

## Notes

Reported by `#0250`/`#0251`'s implementer under `CLAUDE.md` §9.

The fourth criterion is the real test, and it is the same one `#0247` used: a
namespaced harness nobody has run twice at once has not been shown to work.

**Both sibling scripts were checked by `#0251`'s review, and one is worse than
this issue's subject.**

**`scripts/testdb_gc_guard_test.sh` — same defect, and it can produce a false
PASS rather than a false failure.** `TESTPREFIX="opencircuit_test_0150gt_"`
(line 53) is a fixed constant, with `${TESTPREFIX}conn` / `idle` / `mutant`
derived from it. Two things compound it:

- `createdb_raw()` swallows every error (`>/dev/null 2>&1`, no exit check), so a
  collision on `CREATE DATABASE` is **silent** and run B carries on against run
  A's database.
- Part 2 runs `gc --all` over that prefix, which **actively sweeps a concurrent
  run's databases mid-test**. Part 4's leak census then fails spuriously as
  `REGRESSION #0223` — blaming a defect that is not there.

So this one can both corrupt another run and misattribute the damage. It should
be fixed **before** `db_reset_guard_test.sh`, despite being the sibling.

**`scripts/dev_guard_test.sh` — hardcoded ports (`P1=54301`, `P2=54311`,
`P3A=54321`), but it degrades detectably.** Every part checks `port_bound`
first; Parts 1/2/3a call `fail` with "pick a different port and rerun", later
parts `SKIP`. Concurrency therefore yields a spurious failure rather than
corruption, which is the acceptable end of this spectrum. Its file-level scratch
is already namespaced (`mktemp -d`, `$$` in the mutant glob), so **only the
ports need fixing**. `:5173` is Vite's own, unavoidable, and already guarded —
leave it.

### One observation to file (not a `#0253` defect)

**`PBASE` can land on a port something else already holds.** The range is
`40000 + (cksum(RUNID) % 200) * 100`, i.e. 40000–59900, which overlaps macOS's
ephemeral range (`net.inet.ip.portrange.first` = 49152) and, on this machine
right now, real listeners: `rapportd` on 49301, LM Studio on 41343,
`lmlink-connect` on 52714, a VS Code helper on 57106. An `ISSUE` token hashing
to base 49300 would give `P1=49301` and a deterministic
`fail "part1 setup: port 49301 unexpectedly already bound"` for that agent,
every time. This is not a regression — the old fixed `54301` had the same
exposure and would have failed for *everyone* — and the script fails detectably
rather than corrupting anything. But a base drawn from an unassigned,
non-ephemeral window, or a retry on a bound base, would remove a class of
spurious failure that reads exactly like a real one.
