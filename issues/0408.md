## Description

`web/vite.config.ts` proxies four prefixes to the Go service so the browser
sees one origin. Two of them — **`/account` and `/admin`** — are *also* SPA
routes in `web/src/lib/router.ts`'s `STATIC_ROUTES`.

A blanket proxy cannot tell a browser's top-level navigation from the SPA's own
`fetch()` calls, so it sends both to Go. Loading or reloading
`http://localhost:5173/admin` therefore returns the Go binary's **embedded**
`dist/index.html` — the tracked placeholder, which carries no bundle — and the
browser renders a blank page. Clicking through from `/` works, because that
never leaves the client-side router.

**Reported by the user, 2026-09-03, testing `#0393`'s CRT admin section**, after
being told to click through rather than reload: *"That admin page does not load.
It just shows me a blank screen. That is not testable."* They were right. A dev
loop in which you cannot reload the page you are working on is not a dev loop,
and "navigate from the home page every time" is a workaround for a defect
rather than a way of working.

Measured before the fix, with Playwright against the live dev server:
`/admin` loaded directly yielded a body of **0 characters and no JavaScript
errors** — the signature of a served shell with no bundle, not of a crash. This
is why it presents as "blank" rather than as an error, and why it looks like a
broken build.

Only `vite dev` is affected. The built SPA is served by Go from a single origin
with no proxy, where the Go router resolves both namespaces itself.

## Root cause

`web/vite.config.ts` proxied `/account` and `/admin` as plain strings. Both
prefixes are also SPA routes, and a plain proxy entry has no way to tell a
browser's top-level navigation apart from the SPA's own `fetch()`/XHR calls to
the same prefix, so both were forwarded to Go, which returned its embedded
placeholder `dist/index.html` — no bundle, hence the blank page.

**This design (below, under the retitled heading) was written on 2026-09-03
but never landed in the tree.** It documents work that happened on an
**abandoned worktree branch**, `worktree-agent-a16d8f8a64eadf32f` (its
directory, `.claude/worktrees/agent-a16d8f8a64eadf32f/`, is still on disk, with
an orphaned `dev.sh --postgres` session still running out of it as of this
pass), which never merged into `main`. On that branch: `2a67730` implemented a
header-only `spaNavigationBypass` (`Sec-Fetch-Mode: navigate` alone), a real
phase-3 review (`75a4ff2`) **bounced it** — the predicate claimed every path
under `/admin`/`/account`, not just the two real SPA routes, so a GET
navigation to `/admin/subscribers/export` (a genuine `<a href download>` in
`Admin.svelte`, not a `fetch()`) or any POST navigation under either prefix
would have been served the SPA shell instead of proxying — and `c96aed5`
applied the reviewer's specified remedy (a path allowlist checked before the
headers, plus a GET/HEAD method gate). None of those three commits ever
reached `main`; only this issue's *prose*, describing the header-only design,
did (`01e4211`). This implementation pass started from that prose, reproduced
the same already-bounced header-only predicate from scratch (commit `2006b12`),
discovered the worktree history above while drafting these resolution notes,
and replaced it with the reviewed remedy (commit `f0b057f`) before returning.

## Fix

`spaNavigationBypass` in `web/vite.config.ts`, wired as the `bypass` option on
the `/account` and `/admin` proxy entries only. It checks, in order: the
request method is `GET` or `HEAD`; the request path (stripped of its query
string) is exactly `/admin` or `/account` — the `SPA_BYPASS_PATHS` allowlist,
which is what keeps a deeper API path like `/admin/subscribers/export` always
proxying regardless of headers; and only then whether the request looks like a
document navigation (`Sec-Fetch-Mode: navigate`, or that header absent with an
`Accept` containing `text/html`, for older/atypical navigations that omit it).
Returning a path from `bypass` makes Vite serve that file instead of proxying,
so navigations to exactly those two paths get the real dev-server `index.html`
with its `/@vite/client` bundle, and every other request — XHR, fetch, a
non-GET/HEAD method, or a deeper path — still reaches Go untouched.

`/api` and `/auth` keep the plain string form — neither collides with an SPA
route (`/login`, `/register/verify`, and `/recover/verify` are the auth-adjacent
SPA paths, and none of them is under `/auth`).

Added a comment on `router.ts`'s `STATIC_ROUTES` naming `SPA_BYPASS_PATHS`
directly, so a future SPA route colliding with a proxied prefix is caught by a
reader rather than discovered by a blank page — this closes the last
acceptance criterion below.

## Gotchas

- **`page.goto(..., wait_until="networkidle")` never resolves against `vite
  dev`.** Vite's HMR client keeps a WebSocket open indefinitely, which
  `networkidle` treats as ongoing network activity, so it times out at 30s.
  Used `wait_until="load"` plus a short fixed wait instead.
- **Building a "before" config for the byte-identical comparison needs the
  temp file inside `web/`, not just anywhere.** Node resolves `vite` and
  `@sveltejs/vite-plugin-svelte` relative to the config file's own directory,
  so a copy placed in the scratchpad (outside `web/`) fails with `Cannot find
  module 'vite'`. Copied it to `web/vite.config.before.0408.ts` (untracked),
  built, then deleted it — confirmed by `git status --porcelain` showing
  nothing for that path afterward.
- **Reproduced an already-bounced design before finding the history that
  bounced it.** The issue's own "Fix (applied)" heading (now retitled `## Fix`
  above, with the design moved into `## Root cause`) reads as settled and
  reviewed; nothing in the file itself signals that it was written before
  implementation, or that an earlier implementation of exactly this text was
  already found insufficient elsewhere. `git log --all -- issues/0408.md` and
  `git branch --all --contains <hash>` is what surfaced it — worth checking
  before trusting a "Fix (applied)" section at face value on any issue whose
  commit trail looks short relative to its prose.

### `f0b057f` against `c96aed5` — the remedy, not the bounced design

I diffed `web/vite.config.ts` at `HEAD` against the same file at `c96aed5` on
the abandoned `worktree-agent-a16d8f8a64eadf32f` branch, which is still
reachable from this repository. The predicate body is semantically identical:
a `SPA_BYPASS_PATHS` set holding exactly the two SPA routes, a `GET`/`HEAD`
method gate evaluated first, the query string stripped before the set lookup,
and the header test reached only after both gates pass. Four differences
exist, none of them behavioural:

- The predicate is a `function` declaration with an explicit `string |
  undefined` return type here, where the branch used a `const` arrow. This is
  marginally the better form, since the return type is stated rather than
  inferred.
- Its comment is longer here and names `subscribersExportHref` as the helper
  that builds the export link, where the branch named only the Svelte view. A
  real improvement: it points at the function a reader has to change.
- The `POST`-navigation half of the bounce is spelled out in the file here.
  The branch kept that half in its commit message and left the file
  mentioning only the download link.
- The `node:http` type import sits after the Vite imports rather than first,
  which is cosmetic.

The one place `f0b057f` deliberately departed from the branch is
`web/src/lib/router.ts`, and it was right to. The branch put its reciprocal
note inside `STATIC_ROUTES`'s doc comment; on `main` that doc comment has
since acquired load-bearing content, including the `export` keyword and a
description of the source-text anchor that `TestStaticRoutesBlockAnchorIsUnambiguous`
depends on. Carrying the branch's version over verbatim would have overwritten
that. Putting the note on the two map entries instead preserves both, and the
`internal/handlers` run below is what proves the added lines still parse —
`TestRouteTableParity_StaticRoutes` reads this declaration as source text and
is explicitly coupled to its formatting.
