# 0408 — `vite dev` proxies `/admin` and `/account` wholesale, so a direct load or reload of either renders a blank page

## Description

`web/vite.config.ts` proxies four prefixes to the Go service so the browser
sees one origin. Two of them — **`/account` and `/admin`** — are *also* SPA
routes in `web/src/lib/router.ts`'s `STATIC_ROUTES`.

A blanket proxy cannot tell a browser's top-level navigation from the SPA's own
`fetch()` calls, so it sends both to Go. Loading or reloading
`http://localhost:5173/admin` therefore returns the Go binary's **embedded**
`dist/index.html` — the tracked placeholder, which carries no bundle — and the
browser renders a blank page. Clicking through from `/` works, because that
never leaves the client-side router.

**Reported by the user, 2026-09-03, testing `#0393`'s CRT admin section**, after
being told to click through rather than reload: *"That admin page does not load.
It just shows me a blank screen. That is not testable."* They were right. A dev
loop in which you cannot reload the page you are working on is not a dev loop,
and "navigate from the home page every time" is a workaround for a defect
rather than a way of working.

Measured before the fix, with Playwright against the live dev server:
`/admin` loaded directly yielded a body of **0 characters and no JavaScript
errors** — the signature of a served shell with no bundle, not of a crash. This
is why it presents as "blank" rather than as an error, and why it looks like a
broken build.

Only `vite dev` is affected. The built SPA is served by Go from a single origin
with no proxy, where the Go router resolves both namespaces itself.

## Fix (applied)

`spaNavigationBypass` in `web/vite.config.ts`, wired as the `bypass` option on
the `/account` and `/admin` proxy entries only. Browsers set
`Sec-Fetch-Mode: navigate` on document navigations and the SPA's API calls ask
for JSON, so the two are distinguishable; returning a path from `bypass` makes
Vite serve that file instead of proxying, so navigations get the real dev-server
`index.html` with its `/@vite/client` bundle and every XHR still reaches Go.

`/api` and `/auth` keep the plain string form — neither collides with an SPA
route (`/login`, `/register/verify`, and `/recover/verify` are the auth-adjacent
SPA paths, and none of them is under `/auth`).

## Acceptance criteria

- [x] A direct load of `http://localhost:5173/admin` renders the admin console
- [x] A **reload** of that URL renders it too — this is the case the user hit
- [x] The SPA's own admin API calls still reach the Go service: an XHR to `/admin/crt-commands` returns 200
- [x] A navigation request receives the Vite bundle — asserted on `@vite/client` being present in the response
- [x] Verified in a real browser, not only by `curl`: direct load, reload, and opening the CRT tab, with zero page errors
- [ ] The same is verified for `/account`, which has the identical collision and was fixed by the same change but not exercised
- [ ] `vite build` output is unaffected — `bypass` is a dev-server option, but prove it rather than assert it, the way `#0094`'s `resolve.conditions` gate was proved byte-identical across `dist/`
- [ ] A guard, or at minimum a comment in `router.ts`, ties `STATIC_ROUTES` to the proxy table so a future SPA route colliding with a proxied prefix is caught rather than discovered by a blank page

## Notes

Fixed directly by the orchestrator rather than dispatched, because the user was
blocked mid-test and the change is six lines of dev-only configuration. It is
filed here so it gets the same review as anything else — the acceptance
criteria above include the three checks the fix did **not** make.

**The general shape is worth remembering**: a reverse proxy keyed on a path
prefix silently assumes that prefix belongs to one system. Here two systems
claim `/admin`, and the collision is invisible until someone reloads. `#0246`'s
planned `/crt` route is a new public path and does not collide; a future admin
sub-route would.
