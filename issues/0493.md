## Description

`scripts/check.sh`'s failure accounting is guarded for `run`, `runpipe`, and
`accounting_probe`. **Two other steps set `FAILED=1` directly and are in no
guarded set:**

- `gofmt_check` (`#0161`)
- `floor_guard_check` (`#0300`, wired onto the default path by `#0489` **today**)

Verified by the orchestrator: both assign `FAILED=1` in their own bodies, not
through `run`.

Measured by `#0258`'s planning pass, in sandboxes where the target step is the
**only** failure, with one added line before `case "$MODE" in`:

- `floor_guard_check() { :; }` → **`VERIFICATION PASSED`, exit 0**, over a floor
  guard that exited 1. Control run: `FAILED`, exit 1.
- `gofmt_check() { :; }` → **`VERIFICATION PASSED`, exit 0**, over an
  unformatted file. Control run: `FAILED`, exit 1.

No in-file self-check fires. **And with the stub in the tracked file of a
scratch repository, `scripts/check_guard_test.sh` reports 39 PASS / 0 failures,
exit 0** — because its Part 1 `bare` sandboxes make everything fail and its
`stubs` sandbox makes nothing fail, so the masking is total in both directions.

## Why this is not a seventh bounce of `#0258`

Both issues' acceptance criteria are about `run()` and `runpipe()` specifically.
`#0258`'s seventh pass closed all four of the sixth review's bypasses on that
stated scope, with a two-directional mutation proof.

**And `floor_guard_check` did not exist when that pass was written** — `#0489`
added it at `211bcf6` today. Folding this into `#0258` would produce exactly the
dynamic `CLAUDE.md` §8 warns about: each pass closes what it is shown, the next
review finds the adjacent shape, and the newest mechanism becomes the next
target. That section was written about `#0258` after six rounds of it.

## The fix is already designed, and its oracle was proved

From `#0258`'s planning pass — roughly 40 lines, **additive to
`scripts/check_guard_test.sh`, nothing in `scripts/check.sh`**:

1. **Two Part 1 isolation rows**, each a sandbox where only the target step
   fails, asserting the run reports failure and exits non-zero. This is the
   sound part: it detects the defect directly.
2. **A parity row** asserting the set of function names that assign `FAILED=1`
   matches a pinned list, so a future step with its own accounting is noticed.

**Be honest in the comment about what the parity row buys**: it catches
maintainer drift — which is how both instances arose — not an adversary, who
would simply edit the pinned list. The isolation rows are what actually detect
the bypass.

### Criterion 3 — the parity row (Part 6)

Enumerates `FAILED=1` assignment sites in the tracked file with
`grep -nE '^[^#]*[^A-Za-z0-9_]FAILED=1([;}]|[[:space:]]*$)'` — narrow enough
to skip the file's three prose occurrences of the literal text `FAILED=1`
(in comments/a printf string, none followed immediately by `;`, `}`, or
end-of-line) while still finding exactly the three real assignments (line 81
inside `run()`, and one line each inside `gofmt_check`/`floor_guard_check`).
Each line is mapped to its enclosing function via the nearest preceding
column-0 `name() {` header (sound for this file specifically: every function
here is defined at column 0, none nested — checked by listing every line
matching `^[A-Za-z_][A-Za-z0-9_]*\(\)` and confirming each is a real header,
never a call). The resulting set is compared against a pinned list
(`run`, `gofmt_check`, `floor_guard_check`); today it matches and the row
passes. Verified it is not vacuous by inserting a fourth accounting function
(`zzz_new_check`) into a private mutant: the row correctly **fails**,
naming the pinned set and the found set.

**Honest limitation, stated in the row's own comment**: this is not
adversarially sound. An adversary adding a new `FAILED=1` site can add its
name to the pinned list in the same edit and the row would still pass. What
it catches is a maintainer adding a new accounting site and forgetting an
isolation row — exactly how both of today's instances arose. Part 1b's rows
are what actually detect a bypass, because they run the tracked file in a
sandbox where the bypass is directly observable.

### Criterion 4/5 — nothing added to `scripts/check.sh`, no guard-on-a-guard

`scripts/check.sh` is byte-identical throughout (sha256 confirmed above).
Everything new lives in `scripts/check_guard_test.sh`, which is itself an
external harness with nothing new guarding *it* — one level, not two.

### Criterion 6 — the irreducible limit, stated

Part 1b's rows are per-failure-path and therefore finite: a future step
added to `scripts/check.sh` with its own `FAILED=1` accounting and no
isolation row of its own stays invisible until someone adds one. The parity
row makes that loud for ordinary maintainer drift (the failure mode both of
today's instances actually were), but an adversary who adds a step, its
pinned-list entry, and disarms the step in the same edit is not covered by
anything here, and nothing inside `check.sh` could cover it either — moving
the check outside the subject (`CLAUDE.md` §8) removes the "edit the guard's
own file" bypass class, not the "the guard's own list is a pinned constant"
one. That is the floor `#0258`'s seventh review already named for this whole
family, one level down.

### The parity row

**Exclusion, verified against the tracked file.** The literal text `FAILED=1`
occurs six times. The scan selects exactly the three real assignments — the one
inside the run helper, terminated by a semicolon, and one apiece inside
`gofmt_check` and `floor_guard_check`, each at end of line. It excludes all
three prose occurrences: two sit in comments, and the third sits inside a
printf format string documenting this very accounting, excluded for two
independent reasons at once.

**Non-vacuity, reproduced.** A mutant carrying a fourth accounting function was
built and the row correctly failed, naming both the pinned set and the found
set with the new name present. A second mutant establishes the boundary in the
other direction, and it is worth recording because it is a real limit of a
line-oriented scan: a `FAILED=1` written inside a single-quoted string and
followed by a semicolon **is** counted, while the same text followed by a
closing quote is not. The consequence is a false positive, so the row fails
loudly and names a function a human then looks at — it fails closed, and it
cannot produce a silent pass over a new accounting site, which is the direction
that matters. The row's own comment already scopes its claim empirically to
this file rather than asserting general string-awareness, and it states plainly
that the row is not adversarially sound, so this is a documented boundary
rather than an overclaim. It is left as is deliberately: making a bash scan
quote-aware to convert a loud false alarm into no alarm is the escalation
`CLAUDE.md` §8 warns against.

**It reads the file, not the running shell.** This is the trap the fourth pass
of `#0258` fell into, and the row avoids it structurally: the whole block
contains no `source`, no `.`, no `declare`, and no `eval`, and every read is a
`grep` or `awk` against the tracked path on disk. It was also confirmed
behaviourally — the found set tracked the bytes of the mutated file while the
harness process running the scan was unchanged.

**`runpipe`'s absence from the pinned set is correct, not an omission.** It is
defined as a one-line delegation that calls the run helper, so it never assigns
`FAILED=1` in its own body and has no accounting of its own to pin. The scan
finding it would in fact be the anomaly.

### What is guarded now, and what is not

**Guarded.** The run helper and the pipefail funnel keep their existing
definition-scan, digest, marker-count and live-behaviour machinery, plus Part 1
sandboxes asserting honesty from outside. `gofmt_check` and `floor_guard_check`
are now each guarded by an isolation row that makes that step the only failing
one and asserts the verdict and exit code from outside — the sound mechanism,
because it detects the bypass directly rather than recognising its shape.

**Not guarded.** A future step added with its own `FAILED=1` accounting and no
isolation row; the parity row makes ordinary maintainer drift loud but is not
adversarially sound, and an adversary who edits the pinned list in the same
commit is not covered. Nor is a genuine assignment written in a spelling the
line-oriented scan does not recognise. And `scripts/check.sh guards` running
the harness is circular, since the run helper there is the one under test, so
the harness's own exit code and FAIL lines are the authority — invoke it
directly when verifying the script itself.
