## Description

`scripts/check.sh`'s failure accounting is guarded for `run`, `runpipe`, and
`accounting_probe`. **Two other steps set `FAILED=1` directly and are in no
guarded set:**

- `gofmt_check` (`#0161`)
- `floor_guard_check` (`#0300`, wired onto the default path by `#0489` **today**)

Verified by the orchestrator: both assign `FAILED=1` in their own bodies, not
through `run`.

Measured by `#0258`'s planning pass, in sandboxes where the target step is the
**only** failure, with one added line before `case "$MODE" in`:

- `floor_guard_check() { :; }` → **`VERIFICATION PASSED`, exit 0**, over a floor
  guard that exited 1. Control run: `FAILED`, exit 1.
- `gofmt_check() { :; }` → **`VERIFICATION PASSED`, exit 0**, over an
  unformatted file. Control run: `FAILED`, exit 1.

No in-file self-check fires. **And with the stub in the tracked file of a
scratch repository, `scripts/check_guard_test.sh` reports 39 PASS / 0 failures,
exit 0** — because its Part 1 `bare` sandboxes make everything fail and its
`stubs` sandbox makes nothing fail, so the masking is total in both directions.

## Why this is not a seventh bounce of `#0258`

Both issues' acceptance criteria are about `run()` and `runpipe()` specifically.
`#0258`'s seventh pass closed all four of the sixth review's bypasses on that
stated scope, with a two-directional mutation proof.

**And `floor_guard_check` did not exist when that pass was written** — `#0489`
added it at `211bcf6` today. Folding this into `#0258` would produce exactly the
dynamic `CLAUDE.md` §8 warns about: each pass closes what it is shown, the next
review finds the adjacent shape, and the newest mechanism becomes the next
target. That section was written about `#0258` after six rounds of it.

## The fix is already designed, and its oracle was proved

From `#0258`'s planning pass — roughly 40 lines, **additive to
`scripts/check_guard_test.sh`, nothing in `scripts/check.sh`**:

1. **Two Part 1 isolation rows**, each a sandbox where only the target step
   fails, asserting the run reports failure and exits non-zero. This is the
   sound part: it detects the defect directly.
2. **A parity row** asserting the set of function names that assign `FAILED=1`
   matches a pinned list, so a future step with its own accounting is noticed.

**Be honest in the comment about what the parity row buys**: it catches
maintainer drift — which is how both instances arose — not an adversary, who
would simply edit the pinned list. The isolation rows are what actually detect
the bypass.

## Acceptance criteria

1. **Re-measure both stubs yourself** before fixing. This lineage has had many
   premises corrected by measurement, including several of the orchestrator's.
   Use a sandbox copy; **never edit `scripts/check.sh`** — every agent's
   verification runs through it.
2. **Add the isolation rows.** Each must fail against today's `check.sh` when
   its target is stubbed, and pass otherwise. Prove both directions.
3. **Add the parity row**, with the honest limitation stated in its comment.
4. **Do not add anything to `scripts/check.sh`.** `CLAUDE.md` §8: a guard inside
   the file it guards becomes new mutable surface, and an external harness
   cannot be disarmed by editing its subject.
5. **Do not build a mechanism that guards the harness.** One level, not two.
6. **State the irreducible limit** left afterwards: Part 1's rows are
   per-failure-path and finite, so a future step with its own accounting and no
   isolation row stays invisible until someone adds one. That is much narrower
   than "any new bypass shape", and no in-file mechanism would cover it either.
