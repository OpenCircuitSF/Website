## Description

Deduplication already tells an import which addresses are genuinely new — and those are exactly the ones whose consent is least certain. `invite` mode turns that list into a request: each new address is inserted `pending` and sent one invitation that says where we got their address, and only becomes `active` if they confirm.

## Acceptance criteria

**Mode**

- [x] `subscriber_imports.consent_mode = 'invite'` is selectable in the import wizard and is the **default** offered
- [x] The wizard states plainly what each mode does — `invite` asks, `prior_consent` asserts — so the choice is not made by accident
- [x] The preview (`#0125`) reports how many invitations an `invite` commit would send, before committing

**Insert and send**

- [x] Addresses already in `subscribers` are skipped and never invited — dedupe runs first, exactly as in `#0125`
- [x] Suppressed addresses are skipped and never invited
- [x] Addresses with a non-null `invited_at` are skipped, in **every** mode and every subsequent import — one invitation per address, ever
- [x] New addresses insert `pending` with a `confirm_token`, `confirm_expires_at`, `source = 'import'`, `import_id`, `consent_basis` left NULL, and `invited_at` stamped
- [x] One invitation per address is enqueued through `#0126`'s outbound queue with `kind = 'import_invite'`
- [x] `subscriber_imports.invited_count` reflects what was actually enqueued

**The invitation**

- [x] `BuildImportInviteEmail` added to `internal/mailing/transactional_templates.go`, HTML and plain text
- [x] The copy names the provenance in a sentence built from `source`, `source_detail`, and `collected_at` — "You gave us this address when you signed up for *Intro to Soldering* through our Google Form on 12 May 2026"
- [x] It states that doing nothing means never hearing from us again
- [x] It carries `List-Unsubscribe` and `List-Unsubscribe-Post` headers (`#0035`) and a one-click decline that suppresses the address
- [x] It carries the `physical_address` setting
- [x] Golden-file tests for HTML and text, committed with **CRLF** per `#0078`

**Confirmation**

- [x] `POST /api/subscribe/confirm` accepts an invitation token — same endpoint, same token shape, no second confirmation route
- [x] Confirming sets `active`, stamps `confirmed_at`, sets `consent_basis = 'double_opt_in'`, clears the token, and increments `subscriber_imports.confirmed_count`
- [x] A confirmed invitee is thereafter indistinguishable from a website signup except by `source` and `import_id`
- [x] **No welcome email follows an accepted invitation** — the invitation was the introduction
- [x] Expiry sweeps unaccepted invitations (`#0128`'s sweep), leaving the row `pending`, never re-mailing
- [x] `invite_sent`, `invite_accepted`, `invite_expired` subscriber events are written (`#0126`)

**Interaction with the rest of the system**

- [x] Invitations count toward `#0124`'s delivery-health thresholds — an invite batch that bounces trips the same breaker
- [x] Invitations respect the same send-rate limit as campaign mail
- [x] Revoking the import (`#0125`) revokes rows that are still `pending`; an address that **confirmed** is left alone, because its consent no longer derives from the import
- [x] `#0128`'s pending screen distinguishes an invited address from a website signup awaiting confirmation

## Notes

PRD §6.10.1 is the specification.

**Why this is a separate issue and not folded into `#0125`.** It was worth considering — the user offered the merge. `#0125` is already a large issue (schema, wizard, dedupe, suppression check, transactional commit, audit, revocation). This adds a mail template, a token lifecycle, a landing path, an expiry sweep, and a set of interactions with `#0124` and `#0128`. Splitting them also means `#0125` can ship and be useful on its own, and keeps the two consent modes reviewable independently — which matters, because they are the two halves of the project's consent story and a reviewer should be able to reason about each without the other in the way. The shared field, `consent_mode`, lands in `#0125` with only `prior_consent` implemented.

**One invitation per address, ever, is the anti-abuse property.** Without `invited_at` as a permanent marker, re-uploading the same CSV re-invites everyone who ignored it the first time — which is what a spammer does, and it is a two-line mistake to make. The check must be against `invited_at`, not against membership in the current batch.

**The provenance sentence is the difference between an invitation and spam.** It is not decorative copy and it is not optional. An invitation that cannot say where the address came from should not be sent, which is why `source_detail` and `collected_at` are mandatory on the import.

**Declining must be one click, not a non-action.** An invitation with no opt-out relies on people ignoring it, and people who ignore it stay in a `pending` state forever. A working decline that suppresses the address is what makes the whole mechanism defensible.

### Blocker 2 — a genuine website signup can be wrongly suppressed

`Store.Unsubscribe`, `Store.Confirm`, `AdminResendConfirmation`,
`ExpirePendingSweep` and the pending screen all decide "this is an
unaccepted import invitation" from the same inferred row state:
`import_id IS NOT NULL AND consent_basis IS NULL` (plus `status='pending'`
in `Unsubscribe`). The doc comments assert that state *"is reachable ONLY
via ImportStore.Commit's invite branch"*. It is not.

`Store.RestartSignup` (store.go) resets `status` to `pending` and mints a
fresh `confirm_token` **without clearing `import_id` or `consent_basis`**.
So this sequence, needing no admin action beyond a revoke:

1. An `invite` import lands the address `pending`, `consent_basis` NULL.
2. The admin revokes the batch — `Revoke` sets `status='unsubscribed'`,
   clears the token, and leaves `import_id` set / `consent_basis` NULL.
3. Weeks later the person visits the site and signs up **themselves**.
   `SubscribeHandler.existingSignup`'s `StatusUnsubscribed` branch calls
   `RestartSignup`, so the row is now a genuine website double-opt-in
   signup in progress — and is still `(pending, import_id set,
   consent_basis NULL)`.

Measured on that row (reviewer probe, own database):

```
after a genuine website signup: status="pending" import_id=true consent_basis=<nil>
MISFIRE: AdminResendConfirmation refuses a genuine website signup as 'an import invitation'
MISFIRE / WRONGLY SUPPRESSED: a genuine website signup's ordinary unsubscribe created 1 suppression(s)
```

The suppression is the serious half. `internal/handlers/subscribe.go`
silently blocks any suppressed address (uniform 202, nothing happens), so
this person is **permanently and silently locked out of the list with no
self-service recovery**, for doing nothing but signing up on the website and
then changing their mind — the exact outcome
`internal/handlers/unsubscribe.go`'s "suppression list: deliberately
untouched" commitment exists to prevent. The same row also, wrongly:

- skips the welcome email on `Confirm`, writes `invite_accepted`, and
  increments `confirmed_count` on the **revoked** import;
- is refused by `AdminResendConfirmation` (`ErrResendNotForInvited`), so an
  admin cannot rescue it either;
- gets `invite_expired` from `ExpirePendingSweep`;
- shows an "Invited" badge and a wrong-kind queue-state lookup on the
  pending screen;
- would be revoked a second time by a repeat `Revoke` of that same import.

The same state is reachable a second way: decline → suppressed → an admin
clears the suppression → the person signs up on the website.

**Recommended remedy (no migration).** Have `RestartSignup` clear
`import_id` (and leave `consent_basis` NULL) when it restarts a signup. A
person who has since signed up on the website is in exactly the position
`Revoke`'s own doc comment already reasons about — *"its consent no longer
derives from the import"* — so the row should stop claiming the import as
its provenance. Nothing is lost from the audit trail: `subscriber_events`
already carries `ImportID` on the `imported` / `invite_sent` rows, which is
where "why did we ever mail this address" is answered. This also fixes the
repeat-`Revoke` case above. Add a test that runs the three-step sequence
and asserts no suppression row and no `ErrResendNotForInvited`.

**Alternative** if `import_id` must stay on the row: stop inferring, and
record the invitation's *live* state explicitly — a new column in a new
migration above HEAD (never `000023`), e.g. `invite_pending BOOLEAN`, set by
`Commit`'s invite branch and cleared by `Confirm`, `Unsubscribe`'s decline,
`Revoke`, and `RestartSignup`. That is more code but it removes an inferred
predicate from five call sites at once.

**Do not** weaken decline-suppresses to work around this. PRD §6.10.1 is
explicit — *"a working opt-out that suppresses the address outright, so
declining is one click and not a non-action"* — and the behaviour is
correct for a row that really is a live invitation. The bug is the
predicate, not the consequence.

### Bypass attempts against the four §9 restricted-area rules — all held

Run against a private database (`opencircuit_test_0129r`), with temporary
probe files since deleted.

**1. An invited address never counts as consenting — HELD.** After
`Commit(invite)`: `status=pending`, `consent_basis` NULL, live
`confirm_token`/`confirm_expires_at`, `invited_at` stamped,
`invited_count=1`. Attempts to observe it as consenting all failed:
`Store.List{Status: active}` does not return it; `Growth30Days`'s imported
filter is `status='active' AND confirmed_at IS NULL` so a pending row is
outside it, and once confirmed it lands in `confirmed` — no double count
either way; the campaign audience predicate (`status='active' AND
synthetic=false`) excludes it; `StatusCounts` files it under `pending`.

**2. Suppressions and `complained` bind on the NEW invite branch — HELD.**
Repeated `#0125`'s bypass against the invite path specifically: run
`Preview` (reports the address as new), then insert the blocking row
*between* preview and commit, then `Commit`. For **all four** suppression
reasons (`hard_bounce`, `complaint`, `manual`, `repeated_soft_bounce`) the
address was not inserted, not enqueued, and `invited_count` stayed 0. For
**all five** existing subscriber statuses (`active`, `pending`,
`unsubscribed`, `bounced`, **`complained`**) the existing row was not
mutated, not claimed by the import (`import_id` stayed NULL), never
invited, and `invited_count` stayed 0. `Commit` re-derives both sets inside
its own transaction, unchanged from `#0125`.

**3. The `physical_address` gate cannot be bypassed from the UI — HELD.**
`internal/handlers/settings.go`'s `validateSetting` falls through to
`default: return true` for `physical_address`, so an admin **can** PATCH
whitespace into it. Every such value — `""`, `" "`, `"\t"`, `"\n"`,
`"   \t \n "` — was fed through `OutboxWorker.render` for a real
`KindImportInvite` row and every one returned
`errImportInviteMissingPhysicalAddress`; nothing rendered, nothing sent.
`render` is the only path from a queue row to a `Message`, and `Commit`
never sends directly. "Deferred indefinitely" is not a silent abandon:
`deferMissingPhysicalAddress` passes `welcomeAddressDeferMaxRetries =
math.MaxInt32` to `MarkRetryOrAbandon`, whose `attempts >= $3` can never
hold, so the row returns to `queued` with a capped backoff forever and
keeps its error text.

**4. An unhandled consent mode still fails loudly — HELD.** Constructed the
future third mode properly: added `assumed_from_vibes` to `consentModes`
*and* widened `subscriber_imports_consent_mode_check` in the private
database (the first attempt was caught by the CHECK constraint alone, which
is a second, independent backstop worth noting). `Commit` then returned
`subscribers: commit: unhandled consent mode "assumed_from_vibes" despite
passing validation`, inserted **no** subscriber, and rolled the
`subscriber_imports` row back with it. It does not fall through to the
`prior_consent` branch. The `switch`/`default` is a genuine replacement for
`ErrConsentModeNotSupported`, not a weakening.

### Ordinary unsubscribe still never suppresses — verified, with one exception

Proved directly rather than accepted: for **every** combination of
subscriber status (`pending`, `active`, `unsubscribed`, `bounced`,
`complained`) × unsubscribe source (`one_click`, `preferences`, `admin`) on
a website-origin row, zero suppressions. Also zero for a `prior_consent`
imported subscriber's unsubscribe, for a `prior_consent` import →
