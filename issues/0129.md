# 0129 — Invite imported addresses to confirm instead of assuming consent

| | |
|---|---|
| **Status** | open |
| **Module** | subscribers / mailing / admin / web |
| **Platform** | All |
| **Phase** | 8 — Archive, imports, and delivery health |
| **First seen** | 2026-08-21 |

## Description

Deduplication already tells an import which addresses are genuinely new — and those are exactly the ones whose consent is least certain. `invite` mode turns that list into a request: each new address is inserted `pending` and sent one invitation that says where we got their address, and only becomes `active` if they confirm.

## Acceptance criteria

**Mode**

- [ ] `subscriber_imports.consent_mode = 'invite'` is selectable in the import wizard and is the **default** offered
- [ ] The wizard states plainly what each mode does — `invite` asks, `prior_consent` asserts — so the choice is not made by accident
- [ ] The preview (`#0125`) reports how many invitations an `invite` commit would send, before committing

**Insert and send**

- [ ] Addresses already in `subscribers` are skipped and never invited — dedupe runs first, exactly as in `#0125`
- [ ] Suppressed addresses are skipped and never invited
- [ ] Addresses with a non-null `invited_at` are skipped, in **every** mode and every subsequent import — one invitation per address, ever
- [ ] New addresses insert `pending` with a `confirm_token`, `confirm_expires_at`, `source = 'import'`, `import_id`, `consent_basis` left NULL, and `invited_at` stamped
- [ ] One invitation per address is enqueued through `#0126`'s outbound queue with `kind = 'import_invite'`
- [ ] `subscriber_imports.invited_count` reflects what was actually enqueued

**The invitation**

- [ ] `BuildImportInviteEmail` added to `internal/mailing/transactional_templates.go`, HTML and plain text
- [ ] The copy names the provenance in a sentence built from `source`, `source_detail`, and `collected_at` — "You gave us this address when you signed up for *Intro to Soldering* through our Google Form on 12 May 2026"
- [ ] It states that doing nothing means never hearing from us again
- [ ] It carries `List-Unsubscribe` and `List-Unsubscribe-Post` headers (`#0035`) and a one-click decline that suppresses the address
- [ ] It carries the `physical_address` setting
- [ ] Golden-file tests for HTML and text, committed with **CRLF** per `#0078`

**Confirmation**

- [ ] `POST /api/subscribe/confirm` accepts an invitation token — same endpoint, same token shape, no second confirmation route
- [ ] Confirming sets `active`, stamps `confirmed_at`, sets `consent_basis = 'double_opt_in'`, clears the token, and increments `subscriber_imports.confirmed_count`
- [ ] A confirmed invitee is thereafter indistinguishable from a website signup except by `source` and `import_id`
- [ ] **No welcome email follows an accepted invitation** — the invitation was the introduction
- [ ] Expiry sweeps unaccepted invitations (`#0128`'s sweep), leaving the row `pending`, never re-mailing
- [ ] `invite_sent`, `invite_accepted`, `invite_expired` subscriber events are written (`#0126`)

**Interaction with the rest of the system**

- [ ] Invitations count toward `#0124`'s delivery-health thresholds — an invite batch that bounces trips the same breaker
- [ ] Invitations respect the same send-rate limit as campaign mail
- [ ] Revoking the import (`#0125`) revokes rows that are still `pending`; an address that **confirmed** is left alone, because its consent no longer derives from the import
- [ ] `#0128`'s pending screen distinguishes an invited address from a website signup awaiting confirmation

## Notes

PRD §6.10.1 is the specification.

**Why this is a separate issue and not folded into `#0125`.** It was worth considering — the user offered the merge. `#0125` is already a large issue (schema, wizard, dedupe, suppression check, transactional commit, audit, revocation). This adds a mail template, a token lifecycle, a landing path, an expiry sweep, and a set of interactions with `#0124` and `#0128`. Splitting them also means `#0125` can ship and be useful on its own, and keeps the two consent modes reviewable independently — which matters, because they are the two halves of the project's consent story and a reviewer should be able to reason about each without the other in the way. The shared field, `consent_mode`, lands in `#0125` with only `prior_consent` implemented.

**One invitation per address, ever, is the anti-abuse property.** Without `invited_at` as a permanent marker, re-uploading the same CSV re-invites everyone who ignored it the first time — which is what a spammer does, and it is a two-line mistake to make. The check must be against `invited_at`, not against membership in the current batch.

**The provenance sentence is the difference between an invitation and spam.** It is not decorative copy and it is not optional. An invitation that cannot say where the address came from should not be sent, which is why `source_detail` and `collected_at` are mandatory on the import.

**Declining must be one click, not a non-action.** An invitation with no opt-out relies on people ignoring it, and people who ignore it stay in a `pending` state forever. A working decline that suppresses the address is what makes the whole mechanism defensible.

**Greenfield.** No production database exists; `subscribers` columns go into `migrations/000010` directly and no backfill is owed. See PRD §6.2's greenfield note.
