## Description

`internal/db/prd_index_parity_test.go` has now been widened three times — `#0148` built it, `#0154` gave it coverage checks and column parity, `#0159` gave it multi-clause `ADD`, `ONLY`/quoted tables, and a dollar-quote lexer. Each round closed the gaps the last review found, and each round the *next* review found the same defect one layer down.

Two silent gaps remain, and `#0159`'s reviewer's verdict is that neither is fixable by a fourth widening:

1. **A `;` inside a string literal truncates an `ALTER TABLE` statement.** `alterTableStmtPattern`'s `([^;]*);` terminator is the only scanner left in the file that is not quote-aware, so `ADD COLUMN a TEXT DEFAULT 'x;y', ADD COLUMN b TEXT;` silently drops `b`. Both coverage tiers agree (1/1, 1/1), so nothing fires. Not a regression — the pre-`#0159` code dropped `b` too.
2. **A `CREATE TABLE` or `ADD COLUMN` inside a dollar-quoted body enters the live map as a phantom**, because `stripSQLComments` copies the span through rather than blanking it. The same class exists for ordinary string literals, accepted by `#0154`'s pass-2 review as wrong-but-loud.

> "This was the third round of widening the loose pattern, and it should be the last. Both residual gaps are the kind one honest tokenizer would not have." — `#0159`'s phase-3 review

## Acceptance criteria

- [ ] The migration text is scanned **once**, by a small tokenizer that understands SQL's four span types — ordinary text, `--` comments, `/* */` comments, single-quoted literals (including `''` escapes), and dollar-quoted bodies (tag-aware, non-nesting) — rather than by a series of regexes each re-deriving quote state
- [ ] Statement termination is decided by that tokenizer, so a `;` inside any span does not end a statement
- [ ] Dollar-quoted and string-literal spans are **blanked, offset-preserving**, so no `CREATE TABLE` or `ADD COLUMN` inside one can enter the live map — `#0159`'s reviewer notes this closes both phantom cases at once
- [ ] Both residual gaps get a test that fails against today's code and passes after
- [ ] **Everything the three previous rounds established stays established.** Re-run `#0154`'s 30-probe classification and `#0159`'s 39 probes; the results tables are in those issues' review notes. Any regression is a bounce
- [ ] The live map still matches `information_schema.columns` in `opencircuit_test_template` exactly — `IDENTICAL, 91 columns` is the standard both prior reviews met
- [ ] No false positives on the tree, Phase 8 forward declarations included; scope stays one-directional
- [ ] `ISSUE=0164 scripts/check.sh go ./internal/...` passes with all four doc guards observed

the file, the actual fix turned out to be small and load-bearing rather than

helper (`blankSpans`/`prepareSQLText`) subsumes three separate hand-rolled
quote/comment scanners that had each been independently patched twice, and
both named gaps close *by construction* from that one change rather than
needing a bespoke fix apiece. That combination — a named recommendation from
the last independent reviewer, and a fix that collapses duplication instead
of adding another special case — moved this from "not worth it" to "worth
doing once, correctly." Built it.

## Root cause

Three prior rounds (`#0148`, `#0154`, `#0159`) each added a scanner that had
to answer "am I inside a string literal / dollar-quoted body / comment right
now" — `stripSQLComments`, `splitTopLevel`, and
`columnsFromCreateTable`'s close-paren finder all carried their own copy of
that logic. `alterTableStmtPattern`'s statement terminator
(`([^;]*);`) never got that treatment at all, so a `;` inside a `DEFAULT`
string literal ended an `ALTER TABLE` statement early and silently dropped
every later comma-separated `ADD COLUMN` clause. Separately,
`stripSQLComments` copied dollar-quoted (and string-literal) content through
byte-for-byte rather than blanking it, so a `CREATE TABLE`/`ADD COLUMN`
written inside one of those spans still matched the strict extraction
patterns and entered the live map as a phantom.

## Fix

Added `tokenizeSQL` (`internal/db/prd_index_parity_test.go`): one
left-to-right scan that partitions migration/PRD text into `sqlSpan`s —
ordinary text, `--` line comments, `/* */` block comments, `'...'` string
literals (`''`-escape aware), and `$tag$...$tag$` dollar-quoted bodies
(tag-aware, non-nesting, reusing the existing `dollarQuoteEnd`). `blankSpans`
replaces a chosen set of those spans with ASCII spaces, byte for byte
(newlines preserved), so the result is always the same length as its input
and every byte offset still names the same span it always did.
`prepareSQLText` runs `tokenizeSQL` once per file/section and derives the two
views everything else now reads:

- `blanked` — comments, strings, *and* dollar-quoted bodies all blanked.
  This is what every extraction pattern (`createIndexPattern`,
  `createTableStart`, `alterTableStmtPattern`, …) and every coverage check
  now matches against. Blanking closes both named gaps *by construction*: a
  `;` that was inside a string literal is now a space, so it can no longer
  terminate `alterTableStmtPattern`'s `([^;]*);` early; and a `CREATE TABLE`
  / `ADD COLUMN` that was inside a dollar-quoted body is now spaces too, so
  it can never match and enter the live map as a phantom. No change to
  either regex's own text was needed for this — running the same pattern
  against cleaner input was sufficient.
- `commentsBlanked` — comments only, strings/dollar-quotes left intact. A
  capture group that needs real literal content (an index's `WHERE`
  predicate, e.g. `idx_workshops_visible`'s `status <> 'draft'`) is
  recovered from here at the same offsets `blanked` matched against, instead
  of coming back as blanked spaces. This is the one place blanking
  everything uniformly would have broken real, currently-passing behavior,
  which is why `prepareSQLText` returns both views rather than one.

`splitTopLevel` and `columnsFromCreateTable`'s close-paren finder lost their
own `inString`/dollar-quote tracking entirely — both now do plain
comma/paren-depth scanning, since every caller passes them already-blanked
text with no stray punctuation left inside any opaque span.
`liveIndexesFromMigrations`/`prdIndexesFromSection` were updated to recover
`columns`/`predicate` from `commentsBlanked` rather than the fully-blanked
text. `stripSQLComments` was removed (superseded by `prepareSQLText`).

## Gotchas

- Blanking string-literal content globally (rather than the two-view
  `blanked`/`commentsBlanked` split) would have silently broken the *real*
  index-predicate parity check this repo already relies on —
  `idx_workshops_visible`'s `WHERE status <> 'draft'` predicate is a live
  string literal that must survive for the migration-vs-PRD comparison to
  mean anything. Caught before it shipped by checking this repo's actual
  `WHERE` clauses (`grep -n "WHERE.*'" migrations/*.up.sql`) rather than
  assuming blanking everything uniformly was safe.
- Recovering predicate/column content from the *raw* file (rather than from
  `commentsBlanked`) would have let a comment's text leak into a predicate
  whenever a match's captured range extended into a now-blanked comment
  region (e.g. a trailing `-- note` before a `WHERE` clause's terminating
  `;`). `commentsBlanked` — comments blanked, strings/dollar-quotes intact —
  is the correct recovery source specifically because it can never contain
  comment text.
