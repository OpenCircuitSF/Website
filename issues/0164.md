## Description

`internal/db/prd_index_parity_test.go` has now been widened three times — `#0148` built it, `#0154` gave it coverage checks and column parity, `#0159` gave it multi-clause `ADD`, `ONLY`/quoted tables, and a dollar-quote lexer. Each round closed the gaps the last review found, and each round the *next* review found the same defect one layer down.

Two silent gaps remain, and `#0159`'s reviewer's verdict is that neither is fixable by a fourth widening:

1. **A `;` inside a string literal truncates an `ALTER TABLE` statement.** `alterTableStmtPattern`'s `([^;]*);` terminator is the only scanner left in the file that is not quote-aware, so `ADD COLUMN a TEXT DEFAULT 'x;y', ADD COLUMN b TEXT;` silently drops `b`. Both coverage tiers agree (1/1, 1/1), so nothing fires. Not a regression — the pre-`#0159` code dropped `b` too.
2. **A `CREATE TABLE` or `ADD COLUMN` inside a dollar-quoted body enters the live map as a phantom**, because `stripSQLComments` copies the span through rather than blanking it. The same class exists for ordinary string literals, accepted by `#0154`'s pass-2 review as wrong-but-loud.

> "This was the third round of widening the loose pattern, and it should be the last. Both residual gaps are the kind one honest tokenizer would not have." — `#0159`'s phase-3 review

## Root cause

Three prior rounds (`#0148`, `#0154`, `#0159`) each added a scanner that had
to answer "am I inside a string literal / dollar-quoted body / comment right
now" — `stripSQLComments`, `splitTopLevel`, and
`columnsFromCreateTable`'s close-paren finder all carried their own copy of
that logic. `alterTableStmtPattern`'s statement terminator
(`([^;]*);`) never got that treatment at all, so a `;` inside a `DEFAULT`
string literal ended an `ALTER TABLE` statement early and silently dropped
every later comma-separated `ADD COLUMN` clause. Separately,
`stripSQLComments` copied dollar-quoted (and string-literal) content through
byte-for-byte rather than blanking it, so a `CREATE TABLE`/`ADD COLUMN`
written inside one of those spans still matched the strict extraction
patterns and entered the live map as a phantom.

## Fix

Added `tokenizeSQL` (`internal/db/prd_index_parity_test.go`): one
left-to-right scan that partitions migration/PRD text into `sqlSpan`s —
ordinary text, `--` line comments, `/* */` block comments, `'...'` string
literals (`''`-escape aware), and `$tag$...$tag$` dollar-quoted bodies
(tag-aware, non-nesting, reusing the existing `dollarQuoteEnd`). `blankSpans`
replaces a chosen set of those spans with ASCII spaces, byte for byte
(newlines preserved), so the result is always the same length as its input
and every byte offset still names the same span it always did.
`prepareSQLText` runs `tokenizeSQL` once per file/section and derives the two
views everything else now reads:

- `blanked` — comments, strings, *and* dollar-quoted bodies all blanked.
  This is what every extraction pattern (`createIndexPattern`,
  `createTableStart`, `alterTableStmtPattern`, …) and every coverage check
  now matches against. Blanking closes both named gaps *by construction*: a
  `;` that was inside a string literal is now a space, so it can no longer
  terminate `alterTableStmtPattern`'s `([^;]*);` early; and a `CREATE TABLE`
  / `ADD COLUMN` that was inside a dollar-quoted body is now spaces too, so
  it can never match and enter the live map as a phantom. No change to
  either regex's own text was needed for this — running the same pattern
  against cleaner input was sufficient.
- `commentsBlanked` — comments only, strings/dollar-quotes left intact. A
  capture group that needs real literal content (an index's `WHERE`
  predicate, e.g. `idx_workshops_visible`'s `status <> 'draft'`) is
  recovered from here at the same offsets `blanked` matched against, instead
  of coming back as blanked spaces. This is the one place blanking
  everything uniformly would have broken real, currently-passing behavior,
  which is why `prepareSQLText` returns both views rather than one.

`splitTopLevel` and `columnsFromCreateTable`'s close-paren finder lost their
own `inString`/dollar-quote tracking entirely — both now do plain
comma/paren-depth scanning, since every caller passes them already-blanked
text with no stray punctuation left inside any opaque span.
`liveIndexesFromMigrations`/`prdIndexesFromSection` were updated to recover
`columns`/`predicate` from `commentsBlanked` rather than the fully-blanked
text. `stripSQLComments` was removed (superseded by `prepareSQLText`).

## Gotchas

- Blanking string-literal content globally (rather than the two-view
  `blanked`/`commentsBlanked` split) would have silently broken the *real*
  index-predicate parity check this repo already relies on —
  `idx_workshops_visible`'s `WHERE status <> 'draft'` predicate is a live
  string literal that must survive for the migration-vs-PRD comparison to
  mean anything. Caught before it shipped by checking this repo's actual
  `WHERE` clauses (`grep -n "WHERE.*'" migrations/*.up.sql`) rather than
  assuming blanking everything uniformly was safe.
- Recovering predicate/column content from the *raw* file (rather than from
  `commentsBlanked`) would have let a comment's text leak into a predicate
  whenever a match's captured range extended into a now-blanked comment
  region (e.g. a trailing `-- note` before a `WHERE` clause's terminating
  `;`). `commentsBlanked` — comments blanked, strings/dollar-quotes intact —
  is the correct recovery source specifically because it can never contain
  comment text.

| Call site | Matches against | Recovers real text from | Correct? |
|---|---|---|---|

`tokenizeSQL`'s partition was dumped span by span for every input. Classified
**right** / **wrong-but-loud** / **wrong-and-silent**.

| # | Probe | Partition | Class |
|---|---|---|---|
| 1 | `$$ x'y ; -- z $$` | one `dollar` span, whole body opaque | **right** |
| 2 | `$tag$ x'y ; $tag$` | one `dollar` span | **right** |
| 3 | tag with a digit (`$q1$`) | one `dollar` span | **right** |
| 4 | tag with an underscore (`$_q$`) | one `dollar` span | **right** |
| 5 | `$1`, `$2` positional parameters | ordinary text, never a tag opener | **right** |
| 6 | `$1$ … $1$` (tag starting with a digit) | not a dollar quote — matches Postgres, whose tag must be an identifier | **right** |
| 7 | tag inside another tag's body (`$outer$ x $inner$ y $inner$ … $outer$`) | one `dollar` span, non-nesting — Postgres's rule reproduced exactly | **right** |
| 8 | `$$` inside a `--` comment | consumed by the `line` span; the `$` branch never sees it | **right** |
| 9 | `$$` inside a `'…'` string | consumed by the `str` span | **right** |
| 10 | unterminated `$$` (no apostrophe after) | `$` falls through as an ordinary byte; following statements parse | **right** |
| 11 | unterminated `$$` **with an apostrophe after it** | `'` opens a runaway `str` span to EOF | **wrong-and-silent** — §5 |
| 12 | mismatched tags (`$a$ it's $b$`) | same runaway | **wrong-and-silent** — §5 |
| 13 | `''` escape (`'it''s'`) | one `str` span | **right** |
| 14 | string containing `--` | one `str` span | **right** |
| 15 | string containing `/*` | one `str` span | **right** |
| 16 | string containing `*/` | one `str` span | **right** |
| 17 | string containing `$$` | one `str` span | **right** |
| 18 | string containing `;` | one `str` span | **right** |
| 19 | unterminated string at EOF | `str` span runs to EOF | **wrong-and-silent** — §5 (documented policy) |
| 20 | `--` at EOF with no newline | `line` span runs to EOF | **right** |
| 21 | `--` inside a block comment | consumed by the `block` span | **right** |
| 22 | `/*` inside a line comment | consumed by the `line` span | **right** |
| 23 | apostrophe inside a `--` comment | consumed by the comment; quote state uncorrupted | **right** — the realistic case, and the one every migration in this tree relies on |

| 27 | **nested** `/* /* */ */` | closes at the *first* `*/`; Postgres nests, so text Postgres would treat as commented becomes live | **wrong-but-loud** — §5 |

**Offsets.** `blankSpans` is genuinely offset-preserving, checked rather than
assumed: for five inputs carrying multi-byte UTF-8 (`é`, `ü`, `🚀`) inside
comment, string, and dollar spans, `len(blanked) == len(commentsBlanked) ==
len(raw)` exactly, every output is still valid UTF-8, and every byte that was
not blanked is byte-identical to `raw` at the same offset. A multi-byte rune
inside a blanked span becomes N spaces, so no later offset shifts. `'\n'` is
preserved inside blanked spans, so line numbering survives too. The whole
two-view design rests on this and it holds.

for reasons checked rather than assumed:

- Three of the four triggers — an unterminated dollar quote, mismatched dollar
  tags, an unterminated string — are **SQL Postgres itself rejects**. A
  migration containing one cannot be applied, so `scripts/testdb.sh template`
  and `golang-migrate` both fail loudly on it long before parity is a
  question. And the truncate-to-EOF policy is not new or ad hoc: `#0154`'s
  pass-2 review already classified the identical behaviour for an
  **unterminated block comment** as **right** ("by design and documented").
  `tokenizeSQL`'s doc comment states the policy explicitly and now applies it
  uniformly to all three unterminated constructs instead of inconsistently to
  one.
- Only the fourth is valid SQL: a **double-quoted identifier containing an
  apostrophe** (`"it's"`), which the tokenizer has no `"` state for. The same
  hole admits `E'…\'…'` backslash-escape strings. Neither exists anywhere in
  this tree (`grep` over `migrations/*.up.sql`: no quoted identifiers outside
  comments, no `E'` strings), and neither is a form this project writes.
- Closing it is genuinely small — a fifth `kindQuotedIdent` case in the same
  `switch`, `""`-escape aware, ~10 lines — which is why it is worth filing
  rather than shrugging at.

**(b) `/* /* */ */` does not nest, but Postgres does.** The tokenizer closes at
the first `*/`, so text Postgres treats as commented out becomes live:
`/* outer /* inner */ CREATE TABLE phantom_n (zz); */` puts `phantom_n` in the
live map. Unchanged from pre-fix, harmless unless a phantom's name collides
with a `prdIndexParityTables` table, in which case it is a **loud** false
"does not mention". No block comment of any kind exists in `migrations/` or in
§6.2. **Wrong-but-loud**, worth one line in a comment at most.

**(c) `PRD.md` §6.2's prose is now partly blanked, and this is live today.**
Tokenizing 18,660 bytes of §6.2 finds 21 string spans, one of them **808 bytes
long** — opened by the unpaired apostrophe in the prose "…`CLAUDE.md` §1's
append-only rule…" and closed by the next apostrophe further down §6.2. 867
of §6.2's bytes are blanked by the string pass. Nothing is lost *today*
(`CREATE TABLE` 13 strict / 13 loose, `CREATE INDEX` 16/16, `ALTER TABLE` 0/0
— the established figures), and the failure direction is **loud**: a swallowed
PRD-side statement makes real migration columns report "does not mention".
But the message would be baffling ("§6.2 does not mention column X" when it
plainly does), and §6.2 is one prose apostrophe away from moving that 808-byte
window over a schema statement. Cheapest durable fix: extract §6.2's fenced
`sql` code blocks before tokenizing, rather than tokenizing markdown as SQL.

None of (a), (b), or (c) is reachable by anything in the tree, and all three
are narrower than the two gaps this issue closed. `#0154` pass 2 and `#0159`
both set the precedent of filing a residual ceiling rather than bouncing when
the issue's own named targets are met — and here they are, by construction.
