## Description

`#0062`'s acceptance criteria 1–4 and 7, and `PRD.md` §10.6, describe backups
going to **S3**: a bucket with encryption and public-access-block, a 30-day
lifecycle rule, and IAM scoped to a bucket prefix.

**None of that exists, and nothing in the tree is heading toward it.** What
shipped — ported from ShortLinks by `#0001` and verified working by `#0062` — is
a different design: `pg_dump` to a local directory on the database host, then an
`rsync` **pull** to an offsite Mac mini over SSH. No AWS involved at any point.
`grep` finds no `s3` or `aws` anywhere under `scripts/db/`.

`#0062` was resolved with those criteria **deliberately left unticked**, because
the verb in its title is *verify* and the restore path genuinely is verified.
This issue carries the unmet half.

**The decision is a product one and needs making rather than drifting:**

- **Build S3 upload** on top of the existing scripts — the dump step already
  works and exits non-zero on failure, so this is an added leg rather than a
  rewrite. Needs the AWS account that `CLAUDE.md` §10 item 2 records as not
  started.
- **Correct `PRD.md` §10.6** to describe the local-dump-plus-offsite-pull design
  that actually shipped, and rewrite `#0062`'s criteria to match.

Either is defensible. What is not defensible is leaving the specification
describing infrastructure nobody is building, because the next person to read
§10.6 will believe it.

**A related gap, and the reason this is not purely a documentation question:**
`#0062`'s criterion 7 covers scheduling and alerting. `backup.sh`'s non-zero
exit on failure is verified working — **and nothing consumes it.** There is no
cron entry, no systemd timer, no `OnFailure=` anywhere in `deploy/`. A backup
that fails silently every night is worse than no backup, because it is believed.

## Acceptance criteria

- [ ] The decision is recorded: S3 built, or `PRD.md` §10.6 rewritten to describe the shipped design
- [ ] If §10.6 is rewritten, `#0062`'s criteria 1–4 are updated to match, so the two stop disagreeing
- [ ] If S3 is built, the upload leg fails loudly and the round trip is re-verified end to end, including a restore *from* S3
- [ ] A schedule exists — timer or cron — and a failed backup reaches a human, not just a non-zero exit nobody reads
- [ ] `pull-backups.sh`'s offsite leg is exercised at least once against a real target, or explicitly marked unverified in the runbook with what would verify it
- [ ] `docs/deployment.md`'s "not covered" list stays accurate against whatever ships
