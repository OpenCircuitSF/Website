## Description

`#0062`'s acceptance criteria 1–4 and 7, and `PRD.md` §10.6, describe backups
going to **S3**: a bucket with encryption and public-access-block, a 30-day
lifecycle rule, and IAM scoped to a bucket prefix.

**None of that exists, and nothing in the tree is heading toward it.** What
shipped — ported from ShortLinks by `#0001` and verified working by `#0062` — is
a different design: `pg_dump` to a local directory on the database host, then an
`rsync` **pull** to an offsite Mac mini over SSH. No AWS involved at any point.
`grep` finds no `s3` or `aws` anywhere under `scripts/db/`.

`#0062` was resolved with those criteria **deliberately left unticked**, because
the verb in its title is *verify* and the restore path genuinely is verified.
This issue carries the unmet half.

**The decision is a product one and needs making rather than drifting:**

- **Build S3 upload** on top of the existing scripts — the dump step already
  works and exits non-zero on failure, so this is an added leg rather than a
  rewrite. Needs the AWS account that `CLAUDE.md` §10 item 2 records as not
  started.
- **Correct `PRD.md` §10.6** to describe the local-dump-plus-offsite-pull design
  that actually shipped, and rewrite `#0062`'s criteria to match.

Either is defensible. What is not defensible is leaving the specification
describing infrastructure nobody is building, because the next person to read
§10.6 will believe it.

**A related gap, and the reason this is not purely a documentation question:**
`#0062`'s criterion 7 covers scheduling and alerting. `backup.sh`'s non-zero
exit on failure is verified working — **and nothing consumes it.** There is no
cron entry, no systemd timer, no `OnFailure=` anywhere in `deploy/`. A backup
that fails silently every night is worse than no backup, because it is believed.

## Decision

**Rewrite `PRD.md` §10.6 to describe the shipped design, and build the
scheduling and alerting half now.** Recorded by the orchestrator on 2026-08-24
under the user's standing instruction to resolve Phase 7 rather than stall on
open questions.

Split deliberately into the half that can be done honestly today and the half
that cannot:

**Do not build S3 now.** The AWS account does not exist (`CLAUDE.md` §10 item
2), and the user deferred all AWS work to deployment, to be configured and
tested on the EC2 box. Writing an S3 upload leg against credentials nobody has
would produce exactly the thing this issue objects to — code heading somewhere
it cannot be verified. The same reasoning the user applied to SES applies here
unchanged.

**Do rewrite §10.6.** The specification currently describes a bucket, a
lifecycle rule, and a scoped IAM policy, none of which anyone is building. The
next person to read it will believe it. §10.6 should describe what shipped —
`pg_dump` to a local directory on the database host, then an `rsync` pull to an
offsite Mac mini over SSH — and record S3 as a *deferred option* gated on the
AWS account, so the intent is not lost. `#0062`'s criteria 1–4 get the same
correction, so the two stop disagreeing.

**Do build the schedule and the failure alert.** This is the genuinely
dangerous gap and it needs no AWS at all: `backup.sh` exits non-zero on failure
and *nothing consumes that exit code*. A backup that fails silently every night
is worse than no backup, because it is believed. A systemd timer plus an
`OnFailure=` unit is local configuration in `deploy/`, buildable and reviewable
now even though it is installed later.

**Honesty requirement for the offsite leg:** `pull-backups.sh` has never been
run against a real target and there is no second machine here to run it
against. It must be marked explicitly unverified in the runbook, naming what
would verify it — not left to read as tested. Per `CLAUDE.md` §10, a
verification claim must say whether it rests on a mock or on real
infrastructure.

### Findings the reviewer would like carried forward

**1. `#0062`'s `## Description` still says S3.** The criteria were corrected;
the one-line Description — the line the Mac app shows as the summary — still

**2. The backup unit's database list can silently fall through to another
project's name.** `opencircuit-backup.service` leaves
`Environment=BACKUP_DATABASES=opencircuit` commented out, so `backup.sh`

fallback in `backup.sh` is the literal string **`shortlinks`**, the *other*
project's database. It fails loudly (`pg_dump` errors, exit non-zero, the
alert fires), so it is fail-safe rather than fail-silent, but uncommenting
that line ought to be a required install step rather than an optional one.
Reported, not filed.

**3. `## Verification` names the wrong `ISSUE` token.** It records

pattern does not spread.

**Schedule and alert built — three new files, no code changes to
`backup.sh`/`restore.sh` needed:**

- `deploy/systemd/opencircuit-backup.timer` — `OnCalendar=*-*-* 07:30:00 UTC`
  (the off-peak window ShortLinks' own cron entry used), `Persistent=true`
  so a missed window still runs on the next boot, `RandomizedDelaySec=300`.
- `deploy/systemd/opencircuit-backup.service` — `Type=oneshot`, runs
  `scripts/db/backup.sh` as the `postgres` OS user (so `backup.sh`'s own
  `BACKUP_RUN_AS=postgres` default becomes a same-user no-op — no
  passwordless-`sudo` grant needed for this path), `OnFailure=
  opencircuit-backup-alert.service`. `WorkingDirectory=`/`ExecStart=` assume
  the repo lives at `/opt/opencircuit` — a placeholder matching ShortLinks'
  own `/opt/shortlinks` convention, since `CLAUDE.md` §10 item 6 records the
  real server layout as still undocumented; flagged inline and in
  `docs/deployment.md` to be corrected before install.
- `deploy/systemd/opencircuit-backup-alert.service` +
  `scripts/db/backup-alert.sh` — the failure-reaches-a-human half. Always
  logs a high-priority journal entry (`logger -p daemon.err`); optionally
  POSTs a JSON webhook if `BACKUP_ALERT_WEBHOOK_URL` is set via an *optional*
  `EnvironmentFile=-/etc/opencircuit/backup-alert.env` (leading `-` so a
  fresh box without that file yet still starts the unit and still logs).
  Deliberately never itself exits non-zero — `set -uo pipefail`, not `-e`,
  and every external command's failure path is caught and logged rather than
  propagated — so a broken webhook can't mask the underlying backup failure
  or cascade into a second failed unit obscuring the first.

**`docs/deployment.md` updated throughout the Backups section**: the S3 gap
framing is now "corrected" rather than "aspirational," the schedule/alert
pair has its own "Schedule and failure alert" subsection stating plainly what
is and isn't proven, the "not covered" list's offsite-pull bullet now states
