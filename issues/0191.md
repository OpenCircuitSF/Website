## Description

`#0189` threaded `status` into `CampaignSendDialog` as a prop, replacing the
hardcoded `'draft'` literal. Its phase-3 review passed the change and found
three follow-ups. None is a live defect — the first is unreachable today.

**1. `status={campaign?.status ?? 'draft'}` reinstates the literal, one level
up, and fails open.** At `CampaignEditor.svelte:817` `campaign` can never be
nullish: the mount sits inside `{:else if campaign}`, and line 574 already
dereferences `campaign.name` bare. The implementation note justified the
fallback as needed by the type checker; the reviewer tested that and it is
**empirically false** — `npm run check` reports 233 files / 0 errors with
`status={campaign.status}` and with `status={campaign?.status ?? ''}` alike.

So it is unreachable dead code that reinstates the literal this issue removed,
and picks the *unsafe* default: `'draft'` is the only status from which the
guard can return `ready`. The same file's `editorGuard` at line 204 uses
`?? ''` → `unavailable`, failing **closed**. It does not re-create the original
lie, because it never fires — but it is one token from being right, and it is
the wrong token.

**2. Two comments this commit left stale.**
- `CampaignSendDialog.guard.test.ts:14–17` still cites a "documented stand-in —
  see the component's own comment" that `#0189` deleted.
- `CampaignSendDialog.svelte:58–61` still justifies the `sending` branch with
  "status is always `'draft'` here", which the prop makes untrue.

**3. The part with teeth: threading `status` is a prerequisite for the
failed-campaign-retry reuse, not sufficient for it.** `sendGuardState` returns
`unavailable` **before** checking `inFlight`, so a caller passing `'failed'`
would get `sending === false` mid-request — leaving the input editable and
Escape/backdrop live during an in-flight send. `handleSubmit` still refuses, so
there is no double send, but the dialog would misrepresent its own state. This
belongs in the guard's doc comment so the next caller does not walk into it.

`sendGuardState` checks `input.status !== 'draft'` (→ `unavailable`) before

### This is a documentation change, so every statement was checked against the code

**Item 1 — removing the fallback, not inverting it, is the right call.**

The mount at `CampaignEditor.svelte:814` is nested inside the `{:else if
campaign}` branch opened at line 573 — walked the `{#if}`/`{/if}` nesting
programmatically from 573 to 830 to confirm no intervening close, so line 817
really is inside that branch, where line 574 already dereferences
`{campaign.name}` bare. `campaign` is narrowed non-null there both at runtime
and for `svelte-check`, which reports **233 files, 0 errors, 0 warnings** on the
committed bare `campaign.status` — the fallback was never load-bearing for
types, as criterion 2 requires.

Removal beats `?? ''` here, and not only on style grounds: `campaign` is typed
`Campaign | null`, so if a maintainer ever hoists the modal out of the `{:else
if campaign}` branch — the exact future `#0189` worried about — the bare form
becomes a **type error** `svelte-check` catches, whereas `?? ''` would compile
silently and merely fail closed at runtime. The stricter of the two safe
options was chosen.

### One finding, reported under §9 rather than filed — and not a bounce

The comments say the dialog is reachable only with `status: 'draft'`, and that
is true of how it is *opened*. It is not quite true for the lifetime of the
mount: `status` is a reactive `$props()` value and `guard` is `$derived`, so the
prop tracks `campaign.status` live, and `resyncCampaignStatus` (editor line 326)
reassigns `campaign` from the server on every SSE connect/reconnect and on every
terminal progress frame. A reconnect during the `onConfirmSend` window — or
another admin sending the campaign — flips the prop to `'sending'` while the
dialog is still mounted and `sendInFlight` is `true`, and by the ordering item 3
documents the dialog then reads `sending === false` mid-request: input
re-enabled, Escape and backdrop live. `handleSubmit` still refuses to act and
the editor's `onCloseSend` bails on `sendInFlight`, so there is no double send
and no dismissal — but the hazard item 3 frames as a *future* non-draft reuse
has a narrow path to it today.

This is not a defect introduced by this commit (the live prop arrived with
`#0189`), no statement in the commit is false about the code's mechanics, and
the loose phrasing is inherited from the module's own pre-existing wording —
`sendGuardState`'s doc comment has called `canSendCampaign` "the render gate"
since `#0184`. Recommend a follow-up issue: decide whether a mid-flight status
flip should hold `sending` true (or freeze `status` at open), and tighten the
two comments' "reachable with" wording to say *opened from*. Reported to the
orchestrator, not filed here.
