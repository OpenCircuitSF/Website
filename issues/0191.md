## Description

`#0189` threaded `status` into `CampaignSendDialog` as a prop, replacing the
hardcoded `'draft'` literal. Its phase-3 review passed the change and found
three follow-ups. None is a live defect — the first is unreachable today.

**1. `status={campaign?.status ?? 'draft'}` reinstates the literal, one level
up, and fails open.** At `CampaignEditor.svelte:817` `campaign` can never be
nullish: the mount sits inside `{:else if campaign}`, and line 574 already
dereferences `campaign.name` bare. The implementation note justified the
fallback as needed by the type checker; the reviewer tested that and it is
**empirically false** — `npm run check` reports 233 files / 0 errors with
`status={campaign.status}` and with `status={campaign?.status ?? ''}` alike.

So it is unreachable dead code that reinstates the literal this issue removed,
and picks the *unsafe* default: `'draft'` is the only status from which the
guard can return `ready`. The same file's `editorGuard` at line 204 uses
`?? ''` → `unavailable`, failing **closed**. It does not re-create the original
lie, because it never fires — but it is one token from being right, and it is
the wrong token.

**2. Two comments this commit left stale.**
- `CampaignSendDialog.guard.test.ts:14–17` still cites a "documented stand-in —
  see the component's own comment" that `#0189` deleted.
- `CampaignSendDialog.svelte:58–61` still justifies the `sending` branch with
  "status is always `'draft'` here", which the prop makes untrue.

**3. The part with teeth: threading `status` is a prerequisite for the
failed-campaign-retry reuse, not sufficient for it.** `sendGuardState` returns
`unavailable` **before** checking `inFlight`, so a caller passing `'failed'`
would get `sending === false` mid-request — leaving the input editable and
Escape/backdrop live during an in-flight send. `handleSubmit` still refuses, so
there is no double send, but the dialog would misrepresent its own state. This
belongs in the guard's doc comment so the next caller does not walk into it.

## Implementation notes

**Item 1.** Re-confirmed the reviewer's `npm run check` measurement myself
before touching the fallback, rather than taking `#0189`'s notes on trust:
with `CampaignEditor.svelte:817` changed to the bare `status={campaign.status}`
(no fallback at all), `npm run check` reports **233 files, 0 errors, 0
warnings** — identical to the baseline. `campaign` genuinely cannot be
nullish at that call site (nested inside `{:else if campaign}`, and line 574
in the same branch already dereferences `campaign.name` bare), so the fallback
was dead code regardless of its default. Removed it outright rather than
swapping the default to `?? ''`: a fallback that can never execute adds
nothing by existing, and the bare form matches how `campaign.name` is already
handled two lines above it.

**Item 2.** Corrected both stale comments to describe the current code
without touching any test logic:
- `CampaignSendDialog.guard.test.ts`'s file-header comment no longer cites
  the deleted "documented stand-in" for `status`; it now explains that every
  case still fixes `status: 'draft'` because that is the only status this
  dialog is reachable with today (`canSendCampaign` gates the mount), and
  that `oldSending`/`oldBlockedAgain` predate `status` existing at all.
- `CampaignSendDialog.svelte`'s `sending` comment no longer asserts "status
  is always 'draft' here" as an unqualified fact; it now scopes that
  equivalence to "every status this dialog is reachable with today" and
  cross-references `sendGuardState`'s doc comment for why a future non-draft
  reuse would break it (the `status` check runs before the `inFlight` check).
- Softened (did not remove or alter) the U+2009 case's comment in the same
  test file: it no longer claims to "prove the separator class by execution".
  Both sides of that table call the shared `normalizeCountInput`, so a
  thin-space regression would flip old and new together and the case would
  stay green — it's belt-and-braces, not the discriminating assertion. Added
  a pointer to `sendConfirm.test.ts`'s `parses` table (`['1 234', 1234]`,
  U+2009, byte-verified by `#0189`'s review) as the real positive assertion.
  The test body itself is unchanged.

**Item 3.** Verified the branch order directly in `sendConfirm.ts`:
`sendGuardState` checks `input.status !== 'draft'` (→ `unavailable`) before
`input.inFlight` (→ `sending`). Added a paragraph to the function's doc
comment recording that a non-`draft` caller — e.g. a future `'failed'`-status
retry reuse — gets `unavailable` even mid-send, so `sending === false` while
a request is genuinely outstanding, and that threading `status` through is a
prerequisite for such reuse, not sufficient for it. Branch order itself is
unchanged, per `#0184`/`#0186`.
