## Description

`#0161` made the repo gofmt-clean and wired `gofmt -l` into `scripts/check.sh`.
Its phase-3 review confirmed the commit is exactly a gofmt run — for each of the
six files, `gofmt` applied to the parent revision is **byte-identical** to the
committed content — and found the one side effect worth following up.

Since Go 1.19, gofmt's doc-comment pass applies smart quotes: a doubled `''`
collapses into a single curly `”`. `internal/db/prd_index_parity_test.go`'s doc
comments illustrate Postgres's `''` string escape, so:

- `'it''s'` became `'it”s'` — a reader copying it writes something Postgres
  treats as ordinary text, not an escaped quote.
- ``  `""` doubles like a string's `”` does `` — the sentence is *about* the
  doubling parallel, and the rewrite destroys the very thing it illustrates.

Exactly two curly-quote introductions repo-wide, both in that file, both
comment-only. **Zero behavioural impact** — the tokenizer and tests are
untouched, and this is what the tree's own formatter produces, so applying it
as-is was correct under `#0161`'s scope.

**What makes it worth an issue rather than a shrug is the new enforcement.** Now
that `check.sh` fails on unformatted files, any *new* declaration doc comment
containing `''` will be silently rewritten the first time someone runs the
formatter. Existing ones are already normalized, so this is about what happens
next, not about repairing the past.

## Acceptance criteria

- [x] Both doc comments in `internal/db/prd_index_parity_test.go` convey the doubled-`'` escape without depending on a literal `''` surviving gofmt — spell it out ("two consecutive `'` characters"), or move the example into an indented code block, which the doc-comment pass leaves alone
- [x] The rewritten comments are **gofmt-stable**: running `gofmt -w` on the file changes nothing — demonstrated, not assumed
- [x] No curly quote remains in either comment
- [x] The comments still explain the escape accurately enough that a reader can act on them
- [x] `gofmt -l .` stays empty and `#0161`'s check still reports clean
- [x] `ISSUE=0210 scripts/check.sh go ./internal/...` passes with zero skips

## Implementation notes

**Established the current bytes before touching anything.** Byte-level scan
(`python3 -c "print(open(P,'rb').read())"` and a codepoint census) of
`internal/db/prd_index_parity_test.go` before any edit found exactly two
occurrences of `\xe2\x80\x9d` (U+201D RIGHT DOUBLE QUOTATION MARK), zero of
U+201C/U+2018/U+2019 — matching `#0161`'s review notes exactly:

- line 205: `` // literal (Postgres escapes an embedded quote by doubling it: 'it”s'), or ``
- line 275: `` // unescaped `"`, `""` doubles like a string's `”` does) would close this for ``

Both `”` sit inside plain comment prose — the second is even inside
backticks (`` `”` ``) — which rules out "wrap it in backticks" as a fix:
backtick code spans are *not* exempt from gofmt's doc-comment smart-quote
pass, only genuine indented preformatted blocks (`//\t...`) are. Confirmed
this by checking that the *first* mangled instance (`'it”s'`, not
backticked) and the *second* (`` `”` ``, backticked) were both mangled
identically — if backticks protected text, only one of the two would have
been hit.

**Route chosen: indented code block, for the primary example; prose for the
second, cross-referencing site.** For the `sqlSpanKind` doc comment, moved
the `'it''s'` example into an indented code block (`//\t'it''s'`), matching
the existing convention for examples elsewhere in this codebase (e.g.
`internal/middleware/ratelimit.go`'s `NewRateLimiter` doc comment) and per
the issue's own recommendation: it depends on a property of gofmt (it
leaves preformatted blocks alone) rather than on wording nobody later
"improves" back into a doubled-quote shape. For the `tokenizeSQL` doc
comment's `kindQuotedIdent` aside, the mangled text sits mid-sentence inside
a parenthetical remark, not as a standalone illustration — interrupting
that sentence with a code block reads worse than the original. Spelled it
out in prose instead ("doubled the same way a string literal's ' is
doubled") and pointed back at the `sqlSpanKind` comment's now-fixed example,
so the escape is demonstrated once, in one place, and referenced everywhere
else. Neither route requires two straight `'` characters to sit adjacent
anywhere in plain comment text (only inside the indented block, which gofmt
skips) — that adjacency is exactly what gofmt's smart-quote pass looks for.

**Scope respected.** Both comments touched are pure doc comments on
declarations (`type sqlSpanKind` and `func tokenizeSQL`); no code, test
logic, or the tokenizer itself was changed. `git diff --stat` confirms one
file, comment-only hunks.

**Concurrency.** `#0209` was running concurrently against
`cmd/opencircuit/`, entirely disjoint from this issue's
`internal/db/prd_index_parity_test.go`. It committed mid-session
(`1257be8`, `4480ee8`); `git status --porcelain` before my own commit showed
only my file dirty, so nothing of #0209's was swept in.

## Notes

Reported by `#0161`'s phase-3 review under `CLAUDE.md` §9.

The indented-code-block route is the more durable of the two: it is a property
of gofmt's pass (it leaves code blocks alone) rather than a wording someone
might later "improve" back into the mangling shape. Whichever you choose,
criterion 2 is the one that proves it — a fix that gofmt immediately undoes is
not a fix.

`#0161`'s `## Review notes` records the two exact strings before and after, and
confirms the tokenizer is unaffected.
