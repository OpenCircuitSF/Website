> 🟢 Resolved 2026-09-09 — `serveDevMode`'s one-argument dev auto-login
> seam is now pinned by an AST call-site read that resolves the target
> parameter position by name, proved to fail against a reordered signature, a
> `nil` literal, and a dropped argument.

## Description

`cmd/opencircuit`'s `serveDevMode` builds `devAutoLogin` and passes it into
`mountAndServe`. **No test references either symbol.** Confirmed: a search of
every `_test.go` file in that package for `devAutoLogin` returns nothing.

So the middleware that lets a developer into the admin console under
`STORAGE=json` is connected by exactly one argument position, and if that
argument were dropped, reordered, or passed as nil, the suite would stay green.
`mountAndServe` treats a nil outer middleware as "no wrapper" by design, so the
failure is silent — the server starts, serves, and simply never logs anyone in.

## Why this is worth pinning

Two issues resolved today turned on this middleware behaving correctly, and
both invested real effort in its *behaviour* while leaving its *wiring*
unguarded:

- `#0409` fixed `DevAutoLogin`'s stale-cookie lockout and pinned the fix with
  `TestDevAutoLogin_StaleCookieHeals` and `TestDevAutoLogin_GarbageCookieHeals`.
  Those exercise the middleware directly.
- `#0484` extended `#0402`'s Postgres-side route-table test to five states, all
  reached through the real `mountAndServe` chain — but only for
  `DevAdminAutoLogin`, the sibling.

`CLAUDE.md` §8 already records why wiring deserves its own guard: `#0325`
renamed a method and silently moved two interfaces onto a type nobody intended,
with no compile error and no diagnostic. `#0451` is filed against
decoy-satisfiable wiring assertions. A one-argument seam with no test is the
same shape.

## Scope — deliberately small

`#0484`'s reviewer proposed the proportionate form: **a wiring guard, not a
server.** Standing `mountAndServe` up under `internal/devstore` is not required
to prove one argument is passed.

Note the reviewer also corrected a cost claim worth carrying here:
`devstore.Store` already satisfies `handlers.Pinger`, so a json-path equivalent
of the route-table test would need no pool, no `TEST_DATABASE_URL` gate, no
seeded admin, and no row cleanup — it would plausibly be *smaller* than the
Postgres version, not larger. That does not make the server-based form the
right answer here; it removes cost as the reason for rejecting it, so the
choice must rest on what actually detects the defect.

## Acceptance criteria

1. **Pin that `serveDevMode` passes a non-nil dev auto-login into
   `mountAndServe`'s outer-middleware slot.** An AST-level assertion over the
   call site is likely enough; say why the form you choose detects the defect.
2. **Prove it fails.** Drop the argument, or pass nil, in a **copy** — never
   `git stash` (`CLAUDE.md` §8a) — and confirm the guard fails naming the seam.
   Restore byte-identically with SHA-256. A guard never seen to fail is not a
   guard (§8).
3. **Apply §8's receiver and satisfier lessons.** `#0337`'s first guard scanned
   only pointer receivers and a value-receiver mutation restored the regression
   while it still reported `ok`. If your guard inspects types, cover both forms,
   and prefer `go/types` over an AST walk where method-set membership matters.
4. **Do not build a mechanism that guards the guard.** `#0258`'s six-pass spiral
   is on record. One assertion that fails when the wiring breaks is the whole
   deliverable.
5. **Check whether the Postgres side has the same gap.** `#0402`'s
   `newDevAdminAutoLogin` result is threaded into the same slot from
   `servePostgres`. `#0484` pins its *behaviour* through the real route table,
   which may already cover the wiring — **say whether it does**, and do not
   duplicate a pin that exists.

## Fix

Added `TestServeDevMode_WiresDevAutoLoginIntoMountAndServe`
(`cmd/opencircuit/servedevmode_devautologin_wiring_guard_test.go`), an
AST-level guard modelled directly on
`TestServePostgres_OneSEOSiteFlowsToEveryConsumer`
(`servepostgres_seo_instance_guard_test.go`, `#0326`) — the same shape
(one function's source builds a value that must reach a specific parameter
of another function's call) already proven in this package.

**Why this form detects the defect (criterion 1).** The guard re-parses
`main.go` fresh on every run with `go/parser`, resolves `mountAndServe`'s
`outerMiddleware` parameter position *by name* (never a hard-coded index,
so a future parameter inserted ahead of it does not stale the guard), finds
`serveDevMode`'s own `devAutoLogin := middleware.DevAutoLogin(...)`
assignment, finds `serveDevMode`'s own call to `mountAndServe`, and asserts
the argument at the resolved index is exactly the identifier
`middleware.DevAutoLogin`'s result was bound to. A runtime/server-based
test can only prove "when this middleware is present in the chain, it
heals a session" — it cannot distinguish that from "present because the
test harness wired it directly," which is exactly the shape
`TestNewDevAdminAutoLogin_RealRouteTable` uses for the Postgres sibling
(see criterion 5 below). Reading `serveDevMode`'s actual source is the only
way to prove *that specific call site* threads the value through, and an
AST read costs nothing beyond a parse — no server, no store, no `STORAGE`
gate.

Both counting steps (exactly one `middleware.DevAutoLogin(...)` call,
exactly one `mountAndServe(...)` call in `serveDevMode`) fail loudly on
zero or on more than one, rather than silently skipping — an empty scan is
evidence the scan broke, never evidence there is nothing to check
(`#0275`/`#0300`/`#0326`'s precedent).

**Criterion 3 — no type/receiver question arises here.** `#0337`'s
receiver-form hole was about interface satisfaction: does a type's method
set (which includes value-receiver methods) satisfy some interface. This
guard asks a purely syntactic question instead — is the identifier at one
literal call-argument position the same identifier another call's result
was bound to — with no interface, no method set, and no receiver form
involved anywhere. `go/types` buys nothing over `go/ast` for that question;
there is no satisfier set to widen. The doc comment on the new test states
this explicitly, so a future reader does not have to re-derive it.

**Criterion 4 — nothing beyond the one assertion.** No shell harness, no
second in-file check, no mutation-detection meta-test. The guard is one
`go test` function; its own failure message is the only signal, matching
`CLAUDE.md` §8's instruction not to build a mechanism that guards the
guard.

**Criterion 5 — the Postgres side does *not* already have this covered.**
Read `TestNewDevAdminAutoLogin_RealRouteTable`
(`cmd/opencircuit/devadmin_test.go`) directly rather than assuming: it
builds `devAdminMW` itself via a direct call to `newDevAdminAutoLogin(...)`
in the test body, then hands that value to its own
`startDevAdminWiringServer` helper, which calls `mountAndServe` **directly**
— not through `servePostgres`. Confirmed with
`grep -rn "servePostgres(" cmd/opencircuit/*_test.go`, which returns
nothing: no test anywhere in the package ever calls `servePostgres` itself.
So `#0484`'s five-state test proves `DevAdminAutoLogin`'s *behaviour* once
wired, exactly as its own review said, but it does not read `servePostgres`'s
source and therefore cannot prove `servePostgres`'s own
`mountAndServe(cfg, pool, …, devAdminAutoLogin, nil)` call site (line 564)
actually threads `newDevAdminAutoLogin`'s result into the right slot rather
than, say, a dropped, reordered, or `nil` argument there too. That is the
identical gap this issue is about, just on the sibling call site — and it is
explicitly **out of this issue's scope**: the title and criterion 1 name
`serveDevMode` only, and `#0484`'s review already flagged the `serveDevMode`
gap specifically as the "one json-specific fact left unpinned," reporting it
to the orchestrator rather than filing it. No pin exists for the Postgres
call site today, so nothing here duplicates one; a Postgres-side sibling
guard (which could reuse this test's `paramIndexByName`/`findFuncDecl`
helpers, applied to `servePostgres` and `middleware`/`newDevAdminAutoLogin`
instead) is a natural, separately-scoped follow-up, not built here per
criterion 4's boundary.

## Prove it fails (criterion 2)

`cmd/opencircuit/main.go` was backed up
(`shasum -a 256` recorded before any edit), then mutated twice in place —
never `git stash` (`CLAUDE.md` §8a) — and restored byte-identically after
each:

1. **Reorder.** Swapped `requireAdmin` and `devAutoLogin` at the call site
   (`requireSession, devAutoLogin, requireAdmin,` in place of
   `requireSession, requireAdmin, devAutoLogin,` — both arguments share the
   type `func(http.Handler) http.Handler`, so this compiles). The guard
   failed:

   ```
   servedevmode_devautologin_wiring_guard_test.go:185: main.go:1096:33: serveDevMode passes requireAdmin at mountAndServe's outerMiddleware position (index 38), want the identifier "devAutoLogin" bound by middleware.DevAutoLogin's own call — mountAndServe's doc comment says a nil (or wrong) outerMiddleware here means "no wrapper" BY DESIGN, so this is silent: the server starts, serves, and never logs a developer in (#0490)
   ```

2. **Nil literal.** Passed a literal `nil` at the same position (adding
   `_ = devAutoLogin` right after its construction so the identifier stays
   "used" and the mutation is a pure wiring defect rather than also a
   compile error). The guard failed naming the same seam:

   ```
   servedevmode_devautologin_wiring_guard_test.go:185: main.go:1097:33: serveDevMode passes nil at mountAndServe's outerMiddleware position (index 38), want the identifier "devAutoLogin" bound by middleware.DevAutoLogin's own call — mountAndServe's doc comment says a nil (or wrong) outerMiddleware here means "no wrapper" BY DESIGN, so this is silent: the server starts, serves, and never logs a developer in (#0490)
   ```

   A third mutation — dropping the argument outright — was also tried and,
   as expected, fails to *compile* (`declared and not used: devAutoLogin`)
   rather than exercising the guard's own assertion; that is a stronger
   failure (the build itself refuses), not a gap, so it needed no separate
   proof beyond noting it here.

`cmd/opencircuit/main.go` was restored from the pre-mutation copy after
each mutation and confirmed byte-identical by `shasum -a 256` both times
(`b45b918f0d14e2bf67ba6c0b05dbe11fb9761db8611f93d64ea60e357805d432`,
matching before and after both mutations), and `git status --porcelain --
cmd/opencircuit/main.go` reported clean afterward. The new guard test
itself
(`cmd/opencircuit/servedevmode_devautologin_wiring_guard_test.go`) was
never touched during either mutation.

## Gotchas

- **Dropping the argument outright doesn't reach the guard at all** — Go's
  fixed-arity call checking turns a dropped positional argument into a
  compile error (`declared and not used: devAutoLogin`) before any test
  runs. That's a stronger failure mode than the guard closing (the build
  itself refuses), so the two mutation proofs that matter are the ones that
  still compile: reorder and nil-literal, both shown above.
- **`findFuncDecl` and `exprString` are already package-scoped** from
  `#0326`'s `servepostgres_seo_instance_guard_test.go` — reused rather than
  redefined, since Go test files in the same package share top-level scope
  and a redefinition would be a duplicate-declaration compile error.

## Review notes

**Approved.** All five criteria hold, every mutation proof reproduces
independently, and the one claim the dispatch asked me to test hardest — that
the parameter position is resolved by name rather than by a hardcoded index —
survives a mutation the implementer did not run.

**The by-name resolution genuinely holds, proved rather than read.** Reading
the source establishes only that no integer literal appears between
`paramIndexByName`'s return and the argument lookup; that is necessary but not
sufficient, since a guard can resolve a name and then ignore the answer. So I
mutated `mountAndServe`'s *signature* instead of its call site, moving the
`outerMiddleware` parameter ahead of `requireSession` — both share the type
`func(http.Handler) http.Handler`, so this compiles with every call site
untouched, which is exactly the shape "a future parameter inserted ahead of it"
takes. The guard tracked the move:

```
main.go:1096:3: serveDevMode passes requireSession at mountAndServe's outerMiddleware position (index 36), want the identifier "devAutoLogin" bound by middleware.DevAutoLogin's own call
```

Index 36, not 38, and it names `requireSession` rather than the still-present
`devAutoLogin`. A hardcoded 38 would have reported a passing `devAutoLogin` and
gone green against a signature whose `outerMiddleware` slot now receives
`requireSession`, which is precisely the silent-stale failure criterion 1 was
written against.

**The `nil` mutation reproduces byte-for-byte.** Passing a literal `nil` at the
call site (with `_ = devAutoLogin` added so the identifier stays used and the
mutation is a pure wiring defect) failed with the identical message the
implementer recorded, at index 38 and naming `nil`. I also reran the dropped-argument
case: it fails to compile with two diagnostics — `declared and not used:
devAutoLogin` *and* `not enough arguments in call to mountAndServe` — so the
implementer's characterisation is right, and the guard's own
`outerIdx >= len(call.Args)` branch is unreachable through this call site in
practice. That branch is harmless fail-closed defence, not dead weight.

**Restoration is byte-identical, three times.** `cmd/opencircuit/main.go` was
copied aside before any edit and restored from that copy after each of the
three mutations — never `git stash`, per `CLAUDE.md` §8a. `shasum -a 256`
returned `b45b918f0d14e2bf67ba6c0b05dbe11fb9761db8611f93d64ea60e357805d432`
before and after every one, matching the hash the implementer recorded, and
`git status --porcelain -- cmd/opencircuit/` reported clean at the end.

**Criterion 3's applicability call is correct — I agree with it.** `#0337`'s
receiver hole exists because method-set membership is a type-checker rule an
AST walk cannot reconstruct: `*T` acquires `T`'s value-receiver methods, and a
walk that scans pointer receivers only misses that. Nothing in this guard asks
which types satisfy anything. It compares one `*ast.Ident`'s `Name` at a
resolved argument index against another `*ast.Ident`'s `Name` on an assignment's
left-hand side, and identifier identity is decided in the syntax tree — reaching
for `go/types` would add a full type-check of `package main` to answer a
question `go/ast` already answers exactly. Ceremony, correctly declined, and the
doc comment says so where the next reader will find it.

**Criterion 4 — proportionate, and the 215 lines are mostly prose.** Measured:
81 comment lines, 8 blank, 126 code — and roughly half of those 126 are the
multi-line `t.Fatalf` format strings that make each failure self-explanatory.
The actual mechanism is two `ast.Inspect` walks over `serveDevMode`'s body, one
16-line `paramIndexByName` helper, and one final comparison; `findFuncDecl` and
`exprString` are reused from `#0326`'s guard rather than duplicated. There is no
shell harness, no second in-file check, and no meta-test that watches this test
— the `#0258` spiral is not started here.

**Criterion 5 confirmed independently, and the Postgres side is unpinned.** I
did not take the implementer's finding on trust. `startDevAdminWiringServer`
takes `outerMiddleware` as its own parameter and calls `mountAndServe` directly,
and `TestNewDevAdminAutoLogin_RealRouteTable` builds that value itself with a
direct `newDevAdminAutoLogin` call in the test body. Every other test reference
to `newDevAdminAutoLogin` in this package is likewise a construction in a test
body. No `_test.go` file in `cmd/opencircuit` calls `servePostgres`; the only
test that reads its source is `TestServePostgres_OneSEOSiteFlowsToEveryConsumer`,
which never mentions `outerMiddleware` or `devAdminAutoLogin` at all. So
`servePostgres`'s own hand-off of `newDevAdminAutoLogin`'s result into the
`outerMiddleware` slot carries the identical unpinned gap, and keeping it out of
scope was right — this issue's title and criterion 1 name `serveDevMode` only.

**What this guard now catches, and what it does not.** It catches the three
ways `serveDevMode`'s hand-off can break while still compiling — a reordered
argument, a `nil` literal, and any substituted identifier — plus a parameter
inserted ahead of `outerMiddleware`, and it fails closed on a rename or move of
either function, on zero or multiple `middleware.DevAutoLogin` constructions,
and on zero or multiple `mountAndServe` calls. It does not catch a `nil`
middleware arriving from the constructor, and does not need to:
`middleware.DevAutoLogin` panics on both of its refusal paths rather than
returning nil. It does not cover `servePostgres`'s sibling seam. And it
understands exactly one construction shape — a plain `name :=
middleware.DevAutoLogin(...)` binding — so a refactor that inlined the call into
the argument list would fail this guard even though the wiring stayed correct;
that is a maintenance cost paid deliberately for fail-closed behaviour, and the
failure message names the shape it expects.
