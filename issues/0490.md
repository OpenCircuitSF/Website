## Description

`cmd/opencircuit`'s `serveDevMode` builds `devAutoLogin` and passes it into
`mountAndServe`. **No test references either symbol.** Confirmed: a search of
every `_test.go` file in that package for `devAutoLogin` returns nothing.

So the middleware that lets a developer into the admin console under
`STORAGE=json` is connected by exactly one argument position, and if that
argument were dropped, reordered, or passed as nil, the suite would stay green.
`mountAndServe` treats a nil outer middleware as "no wrapper" by design, so the
failure is silent — the server starts, serves, and simply never logs anyone in.

## Why this is worth pinning

Two issues resolved today turned on this middleware behaving correctly, and
both invested real effort in its *behaviour* while leaving its *wiring*
unguarded:

- `#0409` fixed `DevAutoLogin`'s stale-cookie lockout and pinned the fix with
  `TestDevAutoLogin_StaleCookieHeals` and `TestDevAutoLogin_GarbageCookieHeals`.
  Those exercise the middleware directly.
- `#0484` extended `#0402`'s Postgres-side route-table test to five states, all
  reached through the real `mountAndServe` chain — but only for
  `DevAdminAutoLogin`, the sibling.

`CLAUDE.md` §8 already records why wiring deserves its own guard: `#0325`
renamed a method and silently moved two interfaces onto a type nobody intended,
with no compile error and no diagnostic. `#0451` is filed against
decoy-satisfiable wiring assertions. A one-argument seam with no test is the
same shape.

## Scope — deliberately small

`#0484`'s reviewer proposed the proportionate form: **a wiring guard, not a
server.** Standing `mountAndServe` up under `internal/devstore` is not required
to prove one argument is passed.

Note the reviewer also corrected a cost claim worth carrying here:
`devstore.Store` already satisfies `handlers.Pinger`, so a json-path equivalent
of the route-table test would need no pool, no `TEST_DATABASE_URL` gate, no
seeded admin, and no row cleanup — it would plausibly be *smaller* than the
Postgres version, not larger. That does not make the server-based form the
right answer here; it removes cost as the reason for rejecting it, so the
choice must rest on what actually detects the defect.

## Acceptance criteria

1. **Pin that `serveDevMode` passes a non-nil dev auto-login into
   `mountAndServe`'s outer-middleware slot.** An AST-level assertion over the
   call site is likely enough; say why the form you choose detects the defect.
2. **Prove it fails.** Drop the argument, or pass nil, in a **copy** — never
   `git stash` (`CLAUDE.md` §8a) — and confirm the guard fails naming the seam.
   Restore byte-identically with SHA-256. A guard never seen to fail is not a
   guard (§8).
3. **Apply §8's receiver and satisfier lessons.** `#0337`'s first guard scanned
   only pointer receivers and a value-receiver mutation restored the regression
   while it still reported `ok`. If your guard inspects types, cover both forms,
   and prefer `go/types` over an AST walk where method-set membership matters.
4. **Do not build a mechanism that guards the guard.** `#0258`'s six-pass spiral
   is on record. One assertion that fails when the wiring breaks is the whole
   deliverable.
5. **Check whether the Postgres side has the same gap.** `#0402`'s
   `newDevAdminAutoLogin` result is threaded into the same slot from
   `servePostgres`. `#0484` pins its *behaviour* through the real route table,
   which may already cover the wiring — **say whether it does**, and do not
   duplicate a pin that exists.
