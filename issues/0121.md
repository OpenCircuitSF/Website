## Description

> ✅ **Resolved 2026-08-21** (`485fe54` + `95d7550`) — verified independently by
> the phase-3 reviewer at load average 1.92. All four acceptance criteria are
> met. `internal/handlers` passes under `-shuffle=on` and five numeric seeds,
> three of them (`4242424`, `19731117`, `60613`) chosen by this review and
> appearing nowhere in this file; the prior review's isolated causal repro
> (seeds `1`/`2`/`3` over the settings/preflight pair) now passes on all three,
> including seed `3`, whose failure came from a *previous process* leaking a
> non-empty `physical_address`. An ordered run and the shuffled runs both leave
> `subscribers`, `subscriber_interests` and `audit_log` at 0 rows and `settings`
> at its four reset keys. Two pre-existing latent items found during review are
> recorded in `## Review notes` and are out of this issue's scope.

Three tests in `internal/handlers` assert an **exact** audience count computed
over the whole `subscribers` table, so each one silently requires that no other
test has left an `active` subscriber behind:

- `admin_campaign_preflight_test.go` — `TestAdminCampaignPreflight_UnmetCodesInPinnedOrder`
  asserts `summary.recipients == 1`
- `admin_campaign_audience_test.go` — `TestAdminCampaignAudience_Preview_Success`
  asserts `Count == 3` and `len(Sample) == 3`
- `admin_campaigns_test.go` — `TestAdminCampaigns_Send_DraftToScheduled`
  posts a `confirm_count` the server re-verifies against the live count

They pass under the project's documented verification command only because
`TestMain` `TRUNCATE`s `subscribers` at package start and Go runs test files in
sorted order, so these three happen to run before the files that seed `active`
subscribers without cleaning up.

Proven deterministically — this is an ordering dependency, **not** a load-related
flake (`CLAUDE.md` §5):

```
$ go test ./internal/handlers/ -count=1 -shuffle=on
--- FAIL: TestAdminCampaignAudience_Preview_Success
    admin_campaign_audience_test.go:85: Count = 5, want 3
--- FAIL: TestAdminCampaignPreflight_UnmetCodesInPinnedOrder
    admin_campaign_preflight_test.go:121: summary.recipients = 6, want 1
--- FAIL: TestAdminCampaigns_Send_DraftToScheduled
    admin_campaigns_test.go:355: status = 409, want 200
        (body={"error":"confirm_count does not match the current audience count (5); reload and try again"})
```

The upstream cause is seeds without cleanup. `admin_campaigns_test.go:570` seeds
an `active` subscriber via `seedSubscriberRow` and never deletes it;
`journey_testutil_test.go` leaves several more. A single ordered run finishes
with ~48 rows still in the shared `opencircuit_test` `subscribers` table.

## Root cause

Two independent groups of tests left `active` `subscribers` rows behind
without cleanup, and the three tests named above assert an exact count over
the *whole* table rather than a delta they measured themselves:

1. `seedSubscriberRow` (`subscribe_test.go`) inserted a row and returned its
   id but never registered cleanup. It has ~18 call sites across
   `subscribe_test.go` and one in `admin_campaigns_test.go` (line 570, cited
   in the issue).
2. The journey batch (`confirm_test.go`, `preferences_test.go`,
   `unsubscribe_test.go`) seeds active subscribers directly via
   `subscribers.Store.Create` (not through a shared helper) at 20 call sites,
   confirms most of them, and never deletes the row.

`journey_testutil_test.go` itself doesn't seed anything — it only holds the
shared `journeyTestPool`/`journeyUniqueEmail` helpers the batch's actual test
files call into. The acceptance criterion naming that file really points at
the batch of files that use its helpers.

## Fix

- Added a single `t.Cleanup` inside `seedSubscriberRow` itself, deleting the
  row by the id it just captured. This covers every one of its call sites
  (including `admin_campaigns_test.go:570`) without touching each one
  individually — the two call sites in `admin_campaign_preflight_test.go`
  that already registered identical cleanup by hand now do it twice; the
  second `DELETE ... WHERE id = $1` is a no-op, so this is harmless and that
  file was left untouched.
- Added the same `t.Cleanup(func() { _, _ = pool.Exec(context.Background(),
  \`DELETE FROM subscribers WHERE id = $1\`, created.ID) })` immediately after
  each of the 20 `subs.Create`/`realStore.Create` + error-check blocks in
  `confirm_test.go`, `preferences_test.go`, and `unsubscribe_test.go`. Applied
  mechanically with a small Python script matching the uniform
  `created, err := ...Create(...); if err != nil { t.Fatalf(...) }` shape, then
  spot-checked by hand.
- Verified `subscriber_interests` and `email_sends` both have
  `ON DELETE CASCADE` to `subscribers` (migrations 000010, 000017) and
  `audit_log` has no FK to `subscribers`, so deleting a seeded row by id can't
  hit a foreign-key violation from rows the test also wrote.
- Did **not** do the "cheaper alternative" the issue's Notes section offered
  (delta-based assertions in just the three fragile tests) — the full sweep
  was tractable once I found the `seedSubscriberRow`-helper shortcut for
  group (1), and doing the real cleanup sweep also satisfies the table's
  end-of-run cleanliness criterion, which a delta-only fix would not have.
- Left `admin_subscribers_test.go`, `admin_suppressions_test.go`,
  `ses_notifications_test.go`, `admin_campaign_preview_test.go`, and
  `interests_test.go` untouched — their subscriber-seeding helpers
  (`seedTestSubscriber`, and the two ad hoc seeds in
  `admin_campaign_preview_test.go`/`subscribe_test.go:642`) already register
  `t.Cleanup` by captured id.

### Criterion 3 fails — a second ordering dependency, on `settings`

Reproduced deterministically at **load average 2.55**, with
`pgrep -f 'go test|\.test '` empty and exactly one connection to

**Root cause.** `settingsTestPool` (`settings_test.go:62`) calls

`admin_campaigns_test.go:544` both carry the comment *"physical_address is
seeded '' by migration 000008; leave it that way"* — they **depend on ambient
settings state**. In sorted file order `admin_campaign*` sorts before
`settings_test.go`, so they pass by accident. This is structurally the same
accident #0121 documents for `subscribers`, one table over.

Isolated causal proof — two tests, one process, order flipped by seed:

```
$ go test ./internal/handlers/ -shuffle=1 -run 'TestAdminSettings_PhysicalAddressRoundTrip|TestAdminCampaigns_Send_RealPreflightAdapter_Returns409UnmetShape'
=== RUN TestAdminCampaigns_Send_RealPreflightAdapter_Returns409UnmetShape  --- PASS
=== RUN TestAdminSettings_PhysicalAddressRoundTrip                        --- PASS   ok

$ ... -shuffle=2
=== RUN TestAdminSettings_PhysicalAddressRoundTrip                        --- PASS
=== RUN TestAdminCampaigns_Send_RealPreflightAdapter_Returns409UnmetShape  --- FAIL
```

Worse, `-shuffle=3` failed the preflight test **even though it ran first** —
the non-empty `physical_address` left by the *previous process* was still in
the shared `opencircuit_test` database. The leak crosses process boundaries,
because nothing resets `settings` on teardown and `TestMain` truncates only
`subscribers`.

**On the implementer's flagged "transient".** It is not transient and not a
collision with another agent. It is this defect, and the implementer saw a
sibling of it (`TestAdminCampaignPreflight_UnmetCodesInPinnedOrder`, which

`CLAUDE.md` §5's warning about load is about *timing* failures, and a missing
`physical_address_missing` code is a state assertion, not a deadline. When a
failure is about observed state rather than elapsed time, reproduce it under a
fixed seed before blaming the machine.

**On the `TestMain` teardown-truncate decision (item 3) — accepted, but the
commit message credits it with more than it does.**

A teardown truncate cannot make a package shuffle-safe. It runs after
`m.Run()`, so it does nothing about intra-run ordering: a test that leaks rows
mid-run still pollutes every test that runs after it in the same process. What
it genuinely buys is (a) criterion 4's end state and (b) no cross-*process*
leak of subscriber rows. Both are real and both are worth having.

Shuffle-safety for those 11 `pending` rows comes from somewhere else entirely,
and I verified it holds structurally rather than by luck:

- The three exact-count tests read the audience, and `audience.go:210` filters
  `s.status = 'active'`. `pending` rows are invisible to them by construction.
- The only whole-table `pending` assertion, `admin_subscribers_test.go:237`,
  is a *lower* bound (`>= 1`). Leaked rows can only satisfy it, never break it.
- `interests_test.go`'s exact `SubscriberCount != 2` is scoped to slugs created
  fresh by `testInterestSlug`, so rows attached to the seeded taxonomy cannot
  reach it.

So the decision is sound and I am not asking for it to be redone. Two caveats
for the record. First, the stated obstacle — "capturing an id" — is not the
real one: these tests know the email (`subscribeUniqueEmail(t)`), so a
`DELETE ... WHERE email = $1` needs no id. The actual obstacle is the *race*
against an async write that may land after cleanup runs, which is a better
argument for the same conclusion. Second, this leaves a tripwire: the moment
someone adds a test asserting an exact whole-table `pending` count, the
ordering dependency is back and the teardown truncate will not catch it. The
`#0091` cost argument for not paying per-test cleanup is legitimate; the
structural reason it is *safe* deserved to be the stated reason.

**Truncating `audit_log` on teardown — checked, not a widening.** `TestMain`'s
*entry* truncate already covers the identical table set, and
`truncateCredsTables` truncates `audit_log` on every `credsTestPool` call, so
the package already destroys audit rows freely mid-run. Every in-package audit
assertion is scoped by `target_id`/`action`/`slug` and runs during `m.Run()`.
On the cross-package race I was asked not to assume: I read
`internal/testdb/testdb.go` — `Lock()` takes `pg_advisory_lock` on a dedicated
session, and in `main_test.go` `release()` is called *after* the teardown
truncate, so the truncate executes inside the lock. No other DB-backed package
can be mid-run. The claim checks out.

**`setPhysicalAddressForTest` with `""` — correct.** It `UPDATE`s the row and
registers a `t.Cleanup` restoring `''`. Calling it with `""` is idempotent and
its cleanup is a no-op re-set to the same value. It restores to the *seed*, not
to a captured previous value, which would matter under nesting or
`t.Parallel` — the package has zero `t.Parallel()` calls, so it does not.

**`settingsTestPool`'s new cleanup — right scope, and `resetSettings` covers
every key the package mutates.** The `t.Cleanup` binds to the `*testing.T` of
the calling test, firing at that test's end. `resetSettings` is a full-table
reset, not key-by-key, so it restores all four keys the package touches. I
also checked the two settings mutators that bypass `settingsTestPool`:
`sesSetSoftBounceSettings` restores `5`/`30` via its own `t.Cleanup`
(correct), and `TestAudit_SettingsUpdated` — see latent item 2.
