## Description

`TestOutbox_Counts` enqueues two rows, claims **both** with
`ClaimDue(ctx, 10, AllKinds)`, marks one sent, then asserts
`counts.Queued >= 1`.

Both rows are claimed, so this test leaves **nothing** queued. The assertion
holds only because **earlier tests in the package leave queued rows behind**.

**Run alone it fails**: `Queued = 0, want at least 1` — measured by
`#0378`/`#0380`'s review.

Pre-existing; `d7ed2ed` was a pure addition to that file.

## Why this is worth pinning

`#0378`'s review was asked to judge whether a **delta-based** assertion could
pass spuriously. It concluded the delta form was sound — its failure mode is a
false FAIL, not a false pass — and then found that the *absolute* form, right
next to it, is the one that is wrong.

That inversion is the point: an assertion reading `>= 1` looks stricter than a
delta and is in fact weaker, because it silently depends on state no one
declared.

## Acceptance criteria

1. `TestOutbox_Counts` passes when run **alone** — `go test ./internal/outbox/
   -run '^TestOutbox_Counts$'`. Demonstrate that, since it is the failing case.
2. It asserts what it actually establishes. If the test means to check that
   `Counts` partitions correctly, seed each state it names rather than leaning
   on residue; if it means to check a delta, say so and measure one.
3. **Do not weaken it to pass.** Loosening the assertion further, or deleting
   it, would trade a fragile check for a vacuous one — `#0354`, `#0358` and
   `#0363` each shipped a check that could not fail, and `#0364` exists because
   an assertion can pass for the wrong reason.
4. **Survey the package for the same shape** and report what you find: any
   assertion whose truth depends on rows another test left behind. Fix only
   `TestOutbox_Counts`; **report the rest** rather than widening scope.
5. Note `testdb.Lock()` serialises packages against one database and there are
   **zero live `t.Parallel()` calls** in `internal/outbox` — so ordering is
   deterministic today, which is *why* the residue is reliable enough to hide
   this. Do not rely on that; it is the bug, not the mitigation.
6. §8b: mutations use **your own database**, never a literal or seeded id. Per
   §5 name the specific tests that ran. `gofmt` stability. Run
   `./internal/outbox/...` and `./internal/handlers/...` (`#0381`).

## Fix

`internal/outbox/store_test.go` (commit `3ab323c`):

- **`TestOutbox_Counts` rewritten (criteria 1, 2, 3).** Each of the two rows
  is now enqueued under its own `Kind` unique to this test run
  (`distinctKind`, `#0285`) instead of the shared, real `KindConfirmation`.
  `ClaimDue` is called scoped to only the `sentKind` row
  (`store.ClaimDue(ctx, 10, []Kind{sentKind})`), asserting it claimed
  exactly the one row — so it cannot touch the row left queued, which the
  previous version's `ClaimDue(ctx, 10, AllKinds)` did (claiming every due
  row up to its limit, both of this test's own rows included). The
  assertion is a before/after **delta** on `Counts()` around this test's own
  two rows (matching the sibling
  `TestOutbox_Counts_ReportsSkippedDistinctlyFromAbandoned`'s existing
  idiom), not an absolute floor — it needs no residue from any other test to
  pass, and it does not merely restate a weaker check: it seeds the queued
  state and the sent state each row's own name claims, and asserts each
  moved by exactly one.
