## Description

Nightly `pg_dump` to S3 with a proven restore. The subscriber list is the least reconstructible asset in the system.

## Acceptance criteria

- [ ] Nightly `pg_dump` to S3 via a systemd timer or cron
- [ ] 30-day S3 lifecycle retention
- [ ] Dumps are encrypted at rest and the bucket blocks public access
- [ ] IAM permissions scoped to that bucket prefix
- [x] **A restore into a scratch database is actually performed and verified** — row counts compared against production
- [x] Restore procedure documented step by step in `docs/deployment.md`
- [ ] A failed backup produces an alert rather than failing silently

## Notes

PRD §10.6. The acceptance criterion that matters is the restore, not the backup. An untested backup is a belief, not a control — and this is the one system where losing the data means losing the audience permanently.

Do this before launch, not after the first incident.

## Implementation notes

`scripts/db/backup.sh`/`restore.sh`/`pull-backups.sh` already existed (copied
from ShortLinks by `#0001`) and are generic enough to work unmodified against
the `opencircuit` database. This pass performed and verified a full restore
drill against a local PostgreSQL 16 cluster and fixed one real bug found
along the way. **Do not mark this issue `resolved` from this section** —
that is the reviewer's call.

**A real gap from this issue's own acceptance criteria, surfaced by the
drill and not fixed here:** the criteria (and `PRD.md` §10.6) describe an
**S3** backup target — 30-day S3 lifecycle, encryption at rest, a
public-access-blocked bucket, IAM scoped to a bucket prefix. **None of that
is what's implemented.** The actual scripts write dumps to a local directory
tree on the database host and rely on `pull-backups.sh` rsync-pulling them
to an offsite Mac mini over SSH — a different, already-functional design
that gets nightly dumps and an offsite copy without ever talking to AWS.
Per `CLAUDE.md` §9 I'm reporting this rather than filing it: someone should
either build S3 upload on top of these scripts, or correct `PRD.md` §10.6
and this issue's criteria 1–4 to describe the Mac-mini-pull design that
actually shipped.

**Also not addressed here (infra/provisioning work with no server yet,
`CLAUDE.md` §10):** the nightly systemd timer/cron entry itself (none
exists in `deploy/`), and wiring a real alert (cron `MAILTO=` or a systemd
`OnFailure=` unit) to `backup.sh`'s already-correct non-zero exit on
failure. `backup.sh` does its part; nothing yet consumes it.

**Bug fixed**: `scripts/db/backup.sh` and `scripts/db/restore.sh` both
defaulted `BACKUP_RUN_AS` with `${BACKUP_RUN_AS:-postgres}`, which in bash
treats an *explicitly empty* value the same as *unset* — so the scripts'
own documented local-dev path (`BACKUP_RUN_AS=""` to skip `sudo -u
postgres`) silently fell back to `sudo -u postgres` and failed with `sudo:
unknown user postgres` on any machine without a `postgres` OS user (e.g.
Homebrew Postgres). Changed both to `${BACKUP_RUN_AS-postgres}`
(unset-only) and re-verified the documented contract actually holds.
`shellcheck` and `bash -n` pass on both scripts; no other behavior changed.

See `docs/deployment.md`'s expanded "Backups" section for the full runbook:
exact commands, what "success" looks like at each step, the destructive-step
warnings, and — explicitly — what is and is not covered/re-verified.

## Verification

Ran on a local Homebrew PostgreSQL 16 cluster. `uptime` before starting:
`load averages: 1.68 1.73 1.76` (idle machine).

**Census of `opencircuit_test_*` before / after** (the CLAUDE.md §5a/§8b/#0223
requirement): before — `opencircuit_test_template` only. After — identical:
`opencircuit_test_template` only (plus `opencircuit_test_0218`, which appeared
mid-session and belongs to the concurrent `#0218` agent, not to this pass —
left untouched). No stray database of mine survived.

**Round trip performed, in order** (see `docs/deployment.md` "Restore drill"
for the copy-pasteable form):

1. `scripts/testdb.sh create 0062src` → fresh, fully-migrated scratch
   database (schema_migrations `version=20, dirty=false`).
2. Populated it with representative data across every table that matters:
   2 `users`, 5 `subscribers` (active/pending/unsubscribed/bounced) +
   4 `subscriber_interests`, 3 `suppressions` (one per reason), 2
   `audit_log` rows, 2 `workshops` (published + draft) + 1
   `workshop_interests`, 1 `email_campaigns` + 1 `campaign_interests` + 3
   `email_sends` (sent + failed), 2 `email_events`. All rows generated with
   `INSERT ... RETURNING id`, none targeting a literal or seeded id
   (CLAUDE.md §8b).
3. Snapshotted the "before" state: row counts per table, `schema_migrations`,
   every sequence's `last_value` (via `pg_sequences`, not `max(id)`),
   constraint count per table, index count per table.
4. `BACKUP_ROOT=<scratch> BACKUP_RUN_AS="" bash scripts/db/backup.sh
   opencircuit_test_0062src` — the real production script, custom format
   (`.dump`). Also ran with `BACKUP_FORMAT=plain` (`.sql.gz`) for full
   coverage of both restore code paths.
5. `BACKUP_RUN_AS="" RESTORE_CREATE=1 bash scripts/db/restore.sh <dump>
   opencircuit_test_0062dst` — restored into a **fresh, differently-named**
   database rather than destroying the source, so the drill could compare
   rather than overwrite. Repeated for the plain-format dump into a third
   database.
6. Compared restored against source: row counts, `schema_migrations`,
   sequence `last_value`s, constraint counts, index counts — **all
   identical, in both formats.**
7. Proved the restore is actually usable: inserted a new `subscribers` row
   post-restore and got id `11` with **zero collision** against the
   restored ids `6`–`10` (the sequence had legitimately advanced past the
   5-row count from an earlier failed/rolled-back seed attempt — sequence
   advancement in Postgres is non-transactional, so this is exactly the
   "sequence position, not row count" hazard the issue calls out). Also
   confirmed FK, CHECK, and UNIQUE constraints still reject bad data
   post-restore (all three attempted, all three correctly rejected).
8. `scripts/testdb.sh drop` on every scratch database created (`0062src`,
   `0062dst`, plus the plain-format pair, plus a final `0062verify`/
   `0062verifyr` pair used to confirm the `BACKUP_RUN_AS` fix).
9. `pgrep -f 'pg_dump|pg_restore|go test'` at the end showed only another
   agent's `go test` (pid owned by a different parent shell, `#0218`'s
   concurrent work) — nothing of mine left running.

**Commands**: `shellcheck scripts/db/backup.sh scripts/db/restore.sh` (clean,
exit 0), `bash -n` on both (clean). No Go or web changes in this pass, so no
`check.sh` run was needed — this issue's scope was `scripts/`, `docs/` only.

## Review notes — 2026-08-24 (phase 3, resolved)

The issue's verb is *verify*, so this review did not grade the implementer's
transcript — it ran its own round trip end to end, on its own databases, and
compared independently. `uptime` at the start: `load averages: 1.54 2.00
2.15` (idle). PostgreSQL 16.14 (Homebrew), `shellcheck` 0.11.0.

### My own round trip — both dump formats

Source: `opencircuit_test_0062rev`, created by `scripts/testdb.sh create`
(clone of the migrated template), then seeded with throwaway rows across
every table that matters — 2 `users`, 2 new `interests` (`rev0062-*` slugs,
alongside the 12 the migration seeds), 5 `subscribers` covering all five
`status` values, 4 `subscriber_interests`, 3 `suppressions` (one per
reason), 2 `audit_log`, 2 `workshops` + 1 `workshop_interests`, 1
`email_campaigns` + 1 `campaign_interests`, 3 `email_sends`, 2
`email_events`, 1 `settings`. Every id captured with `INSERT … RETURNING`;
no literal or seeded id targeted anywhere (`CLAUDE.md` §8b).

Backed up with the real `scripts/db/backup.sh` in **both** formats into a
scratch `BACKUP_ROOT`, then restored each with the real
`scripts/db/restore.sh` (`RESTORE_CREATE=1`) into a **differently named**
database — `…_0062rc` for custom, `…_0062rp` for plain — so nothing was
overwritten and the comparison was source-against-restored rather than
before-against-after.

Compared with a single snapshot script diffed three ways. **Both formats
came back byte-identical to the source on every check:**

| Check | Result |
|---|---|
| Row counts, all 18 public tables | identical (custom and plain) |
| `schema_migrations` | `version=20, dirty=f` on all three |
| Sequence `last_value` + `is_called`, from `pg_sequences` | identical, all 12 sequences |
| Constraint counts per table **and** every `pg_get_constraintdef()` | identical |
| Index counts per table **and** every `indexdef` | identical |
| Data digest (subscribers, audit_log, campaigns, sends, events, interests, settings, suppressions) | identical |

`diff src.txt rc.txt` and `diff src.txt rp.txt` both returned empty.

### Sequences — the check that actually matters

The hazard reproduced on its own in my seed: I deliberately rolled back one
`subscribers` insert, and because sequence advancement in PostgreSQL is not
transactional, `subscribers_id_seq.last_value` sat at **6 with only 5 rows**
— `max(id)` was 5. Both restores preserved `last_value = 6`, not 5. A
post-restore insert got id **7**, with the restored rows still at 1–5 and
zero duplicate ids (`group by id having count(*) > 1` → 0 rows) — confirmed
separately in both the custom-restored and plain-restored databases. Never-
called sequences (`sessions_id_seq`, `passkey_credentials_id_seq`,
`pending_registrations_id_seq`, `webauthn_challenges_id_seq`) reported
`NULL`/`is_called=false` on both sides, so the restore does not silently
"start" an unused sequence either.

Constraints are live after restore, not merely present: a bad FK
(`email_sends.campaign_id`), a non-normalized email (`subscribers_email_
normalized`), a duplicate `subscribers.email`, and an invalid `status` were
each attempted against both restored databases and each rejected by name.

My drill's numbers differ from the ones in `docs/deployment.md`'s
"Sequences" bullet (it records `10`/`5`/`11`; I got `6`/`5`/`7`) because the
gap depends on that run's rolled-back inserts. The *shape* of the hazard
reproduced exactly, which is the point.

### `BACKUP_RUN_AS` — old bug reproduced, three states confirmed

Reverted the one substitution back to `${BACKUP_RUN_AS:-postgres}` in
**scratch copies** of both scripts under the scratchpad (tracked files never
touched — `git status --porcelain scripts/` stayed empty throughout). The
old failure reproduced exactly as described, in both scripts:

```
$ BACKUP_RUN_AS="" bash <scratch-copy>/backup.sh opencircuit_test_0062rev
sudo: unknown user postgres
ERROR: pg_dump for 'opencircuit_test_0062rev' failed (rc=1) …
FAILED: 1 database(s) did not back up.
```

`restore.sh`'s scratch copy failed the same way at `createdb`, announcing
`(as postgres)` despite `BACKUP_RUN_AS=""`. This machine has no `postgres`
OS user (`dscl . -list /Users | grep -c '^postgres$'` → 0), which is the
condition that makes the bug bite.

Three states against the **fixed** scripts, both of them:

| `BACKUP_RUN_AS` | `backup.sh` | `restore.sh` |
|---|---|---|
| unset | `run as: postgres`, `sudo -u postgres` attempted | `(as postgres)`, `sudo -u postgres` attempted |
| `""` | `run as: brennan`, no sudo, full dump `ok` | `(as brennan)`, no sudo, restore completes |
| `oc0062nobody` | `run as: oc0062nobody`, `sudo: unknown user oc0062nobody` | `(as oc0062nobody)`, same |
| `$(id -un)` | `run as: brennan`, sudo correctly skipped | — |

The documented contract now holds. `bash -n` and `shellcheck` are clean on
both scripts (exit 0), and `git show --stat 918ecea` confirms the diff is
confined to `scripts/db/backup.sh`, `scripts/db/restore.sh`, and
`docs/deployment.md`.

### Failure signalling

Exit codes are distinct and a partial failure is visible, which is the
precondition criterion 7 needs (nothing consumes it yet — see below):
success `0`; any database failing to dump `1` (verified with a two-database
run where one succeeded and one did not — the good dump published, the bad
one left no `.tmp`); bad `BACKUP_FORMAT` `2`; missing dump file `2`; a plain
`.sql.gz` replay that errors `3` via `pipefail`.

One asymmetry worth knowing at 3 a.m., not stated in the runbook: a
**custom** re-restore over a populated database is genuinely idempotent
(`--clean --if-exists`; my extra post-restore row was removed and the count
returned to 5), while a **plain** `.sql.gz` replay into a non-empty database
aborts at the first `CREATE TABLE` under `ON_ERROR_STOP=1` (`relation
"audit_log" already exists`, exit 3) and leaves the target untouched. It
fails safe, and both the script header and runbook step 4 do say to restore
into a fresh target — but the two formats are not interchangeable here.

### The runbook, read as someone whose database is broken

Mostly good, and unusually honest about its own limits — the "what this does
not cover" and "must be re-verified on the server" sections are the best
part of it. Success signals are stated after the two steps that have
commands, and the destructive step is gated properly: `restore.sh` never
drops a database, and the "Before restoring over anything live" list
(confirm the target name from the command not from memory; prefer
`RESTORE_CREATE=1` into a new name; dump the current state first; don't
trust the exit code alone) is the right four things in the right order.

The "not covered" list matches reality; I checked each claim rather than
taking it: `grep -rn "s3\|aws" scripts/db/` → nothing; `grep -rn "CREATE
EXTENSION" migrations/` → nothing; `deploy/` contains only the Apache vhost
and systemd unit, no timer/cron/`OnFailure=` anywhere; `pull-backups.sh`
needs a real SSH target and was not run by me either — correctly marked
**unverified** rather than merely undocumented.

Three places where it is not copy-pasteable, or is wrong, for the next pass:

1. **Drill step 1 runs `scripts/testdb.sh create 0062src` twice** (once bare,
   once inside `$( )`), and `create` *drops* an existing database before
   recreating it — so the literal transcript destroys the database the line
   above just made. It also `-f seed.sql`s a file that exists nowhere in the
   repo.
2. **Drill step 7's cleanup silently fails.** `scripts/testdb.sh drop`
   connects as the `opencircuit` role, but a database created by
   `restore.sh` `RESTORE_CREATE=1` is owned by the OS user running it. I hit
   `ERROR: must be owner of database opencircuit_test_0062rc` — after which
   `testdb.sh` printed **"opencircuit_test_0062rc does not exist"** and
   exited happily, leaving a stray scratch database behind. I dropped both
   by hand as their owner. The false-success is a `testdb.sh` bug (its
   `&&`/`||` chain), outside this commit's diff, but the runbook walks
   straight into it and §8b/`#0223` care about exactly this stray.
3. **Table ownership is not preserved across a restore**, and the doc's
   parenthetical "(here, `opencircuit` … confirmed identical `tableowner`
   before and after)" did not hold for me: source tables were owned by
   `opencircuit`, both restored copies by `brennan`. The mechanism sentence
   right before it is correct — ownership is whoever runs the restore — but
   that means the runbook's own **production** path (`BACKUP_RUN_AS=postgres`
   → `sudo -u postgres pg_restore`) would leave every table owned by
   `postgres`, and `--no-privileges` strips the grants too, so the app role
   `opencircuit` would get `permission denied` after a real restore until
   someone reassigns ownership. Nothing in the runbook says to. That section
   is already flagged "read, not executed", so this is a follow-up rather
   than a bounce — but it is the one thing here that could turn a successful
   restore into an outage.

### Verdict on the S3 mismatch — resolving with it standing, explicitly

Criteria 1–4 (nightly `pg_dump` **to S3** via timer/cron, 30-day S3
lifecycle, encryption at rest + public-access block, IAM scoped to a bucket
prefix) and criterion 7 (a failed backup produces an *alert*) are **not
met**, and they are left unticked above. What exists is local `pg_dump` plus
an `rsync` pull to an offsite Mac mini; no code in this repo talks to AWS.
The implementer surfaced this rather than papering over it, which is the
right call.

I am resolving anyway, and this is deliberate rather than generous:

- The issue's verb is *verify*, and its own Notes say "the acceptance
  criterion that matters is the restore, not the backup. An untested backup
  is a belief, not a control." That restore is now a demonstrated control —
  demonstrated twice, by two agents, on separate data, in both formats.
- Criteria 1–4 and 7 are not implementation work that a bounce would
  produce. They need an AWS account and a server, neither of which exists
  (`CLAUDE.md` §10 items 2 and 6), and they rest on a design decision a
  human has to make first: build S3 upload on top of these scripts, or
  correct `PRD.md` §10.6 to describe the Mac-mini pull that actually
  shipped. A reviewer cannot make that call and an implementer cannot
  execute it.
- Leaving this `open` would park a verified control behind that undecided
  question and keep `#0064` blocked for it.

**Carried forward, not silently dropped** — for the orchestrator to file
(`CLAUDE.md` §9: reviewers report, they do not file):

1. **Reconcile `PRD.md` §10.6 and criteria 1–4 with what shipped** — either
   add S3 upload (bucket, lifecycle, encryption, public-access block, scoped
   IAM) on top of `backup.sh`, or rewrite §10.6 to describe the local-dump +
   offsite-`rsync`-pull design. Blocks a real deploy either way.
2. **Wire the nightly schedule and the alert** — no crontab entry, systemd
   timer, or `OnFailure=` unit exists in `deploy/`. `backup.sh`'s non-zero
   exit is verified working; nothing consumes it. This is criterion 7 and
   belongs with `#0064`'s server work.
3. **Post-restore ownership and grants** — document (and probably script)
   the `ALTER TABLE … OWNER TO opencircuit` / `REASSIGN OWNED` step after a
   restore run as `postgres`, and correct the `tableowner` parenthetical in
   `docs/deployment.md`. Finding 3 above.
4. **`scripts/testdb.sh drop` reports success when it fails** on a database
   owned by another role — it prints "does not exist" after `ERROR: must be
   owner`, leaving a stray scratch database. Small fix to its `&&`/`||`
   chain; also fold in the two drill-step defects (findings 1 and 2).
