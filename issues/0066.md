## Description

Phase 0 copied the ShortLinks skeleton and Phase 0's issues only required the *shortener* to be stripped, not the *branding*. What survives is not cosmetic: test fixtures assert `go.sstools.co` as the WebAuthn relying party, deploy files name a `shortlinks` service and config path, and several code comments cite issue numbers from another project's tracker.

This blocks [#0008](0008.md). Its acceptance criteria require the passkey stack to be verified against this project's relying party (`opencircuitsf.com` apex / `https://www.opencircuitsf.com` origin, per PRD §9), but the auth tests pin the old values, so they would pass while proving the wrong thing.

## Steps to reproduce

1. `grep -rn 'sstools\|ShortLinks' internal/ web/src/ deploy/`
2. `grep -rn '#0094\|#0097' internal/`

## Expected behavior

No ShortLinks identifier appears outside `PRD.md`, `HANDOFF.md`, `CLAUDE.md`, and issue files, where they are deliberate historical references to the source project. Every `#NNNN` reference in code resolves to an issue in *this* tracker.

## Actual behavior

- `internal/auth/registration_test.go:25-26` — `testRPID = "go.sstools.co"`, `testRPOrigin = "https://go.sstools.co"`, and `virtualwebauthn.RelyingParty{… Name: "ShortLinks" …}` at lines 342 and 441.
- `web/src/lib/webauthn.test.ts` — asserts `rpId: 'go.sstools.co'` and `name: 'ShortLinks'` across six assertions.
- `deploy/apache/go.sstools.co.conf` — vhost named for the wrong host.
- `deploy/systemd/shortlinks.service` — service name and `EnvironmentFile=/etc/shortlinks/config.env`.
- `internal/auth/ses_mailer.go` — `noreply@sstools.co` example strings.
- Tracker references carried over from ShortLinks, spread across `internal/auth/` and `internal/handlers/` (`ses_mailer.go`, `mailer.go`, `store.go`, `login.go`, `logout_all_test.go`, `registration_test.go`, `login_test.go`, `recovery_test.go`, `auth.go`, `logging_test.go`). Two kinds, and the second is worse:
  - **Dangling** — `#0094` and `#0097` do not exist in this tracker at all.
  - **Wrong** — and this is the majority. `internal/auth/login.go:40` cites `#0025`, which *does* exist here as "Create the subscribers migration", entirely unrelated to the `session.revoked_all` audit behaviour the comment describes. A reference that silently resolves to the wrong issue is more dangerous than one that resolves to nothing: a reader following it is actively misled rather than merely stopped.

**Measured scale:** 112 references across 41 files, using 30 distinct issue numbers. **21 of those 30 collide with real issues in this tracker** — `#0002`, `#0003`, `#0007`, `#0010`, `#0014`, `#0015`, `#0016`, `#0017`, `#0019`, `#0025`, `#0027`, `#0028`, `#0036`, `#0041`, `#0044`, `#0047`, `#0048`, `#0051`, `#0053`, `#0061`, `#0065`. Only nine (`#0077`, `#0083`, `#0092`, `#0093`, `#0094`, `#0096`, `#0097`, `#0098`, `#0099`) fail loudly by pointing at nothing.

## Notes

The relying-party values are the reason this is urgent rather than tidy. `WEBAUTHN_RP_ID` is the **apex** so one passkey covers apex and www; `WEBAUTHN_RP_ORIGIN` is the **www** form because that is the host the browser is actually on. They are not interchangeable and a mismatch fails ceremonies with an opaque error — see `CLAUDE.md` §7 and PRD §9.

Note the direction of the Apache redirect. `#0064`'s criteria say `www` redirects to the apex; that is **backwards** relative to production and is recorded as a known tracker defect in `CLAUDE.md` §7. Follow production, not `#0064`.

`deploy/systemd/README.md` and `deploy/apache/README.md` reference the old filenames and need updating alongside the renames.
