## Description

`UnsubscribeHandler.Post` (`#0034`) is built so that *every* path through it ends
in `http.StatusOK` — there is a `writeNeutral` helper whose entire reason for
existing is to make that invariant impossible to miss. The route wiring then
puts a per-IP rate limiter in front of it that can answer **429** before the
handler is ever reached:

```go
// cmd/opencircuit/main.go
unsubscribeLimiter := middleware.NewRateLimiter(rate.Every(time.Minute/10), 5)
mux.Handle("POST /api/unsubscribe", unsubscribeLimiter.Middleware(http.HandlerFunc(unsubscribeH.Post)))
```

`RateLimiter.Middleware` writes `429 {"error":"rate_limit_exceeded"}` and never
calls `next`. PRD §6.5 is explicit about why that matters: "a provider seeing
errors on the unsubscribe endpoint downgrades sender reputation." The `429` is
an error to a mail provider exactly as much as the `404` the handler is
carefully written to avoid.

## Root cause

Per-IP bucketing is the wrong shape for this endpoint's caller. Unlike
`/api/subscribe` or `/api/preferences`, the client here is not a human's
browser — it is Gmail's or Yahoo's infrastructure acting on
`List-Unsubscribe-Post`, and `middleware.ClientIP` correctly resolves that to
the provider's egress IP (the rightmost `X-Forwarded-For` entry Apache
appends, per `#0077`). **Every** one-click POST Gmail sends for this domain
therefore shares one bucket: 10/min sustained, burst 5. The sixth Gmail
unsubscribe in a minute gets a 429 and that person stays subscribed, silently.

The limiter also has no stated security purpose here. `main.go`'s own comment
concedes it: "a mail provider's automated POST is not brute-forcing a 32-byte
token, but matching the existing public-endpoint convention costs nothing." It
does cost something — it is the only way this route can produce a non-200.

Impact today is low and bounded: `#0035` (List-Unsubscribe headers) has not
landed, so no sent email carries this URL yet. This should be settled before
Phase 5 sends anything real.

## Fix

Dropped the rate limiter from `POST /api/unsubscribe` entirely — the first
of the two options the acceptance criteria offer, chosen over "make the
refusal path answer the same neutral 200" because it is strictly simpler
(no new refusal-path code to keep in sync with `writeNeutral`'s wording) and
because the neutral-200 behavior it would have reproduced is already every
other path's guarantee, not a new invariant to introduce. `GET
/api/unsubscribe` explicitly keeps its ordinary, 429-capable
`unsubscribeLimiter` — stated here rather than left implied, per the second
acceptance-criteria bullet: `Get` never touches the store (see
`unsubscribe.go`'s package doc comment) and exists only to redirect a click
or a security scanner's prefetch to the SPA's `/unsubscribe` view, so a 429
there just means the prefetch doesn't happen, which PRD §6.5 does not treat
as an error condition the way a POST 429 would be.

**On the DoS question the last acceptance-criteria bullet asks to settle
honestly:** no real concern is made out. `Post` performs exactly one indexed
`SELECT` against `manage_token` (`subscribers.Store.FindByManageToken`, a
btree lookup on a column that's `UNIQUE NOT NULL` per
`migrations/000010_create_subscribers.up.sql`) and, on a miss — the outcome
for any request that isn't a legitimate footer/header link — does nothing
else at all. That's cheaper than `GET /api/interests` or `GET /sitemap.xml`,
both already unlimited in this same file. Leaving the route unlimited does
not introduce a new class of exposure this service doesn't already carry
elsewhere.

Added two wiring tests in `cmd/opencircuit/unsubscribe_wiring_test.go`,
driving `mountAndServe` — the exact function `servePostgres` calls — over a
real listener:

- `TestMountAndServe_UnsubscribePost_NeverRateLimited` — 30 POSTs (six times
  the old burst of 5) from one `X-Forwarded-For` IP, each with an unknown
  token (which the handler already answers 200-neutral for, so no seeded
  subscriber is needed), asserting every single response is `200`.
  `TestMountAndServe_RateLimitsSubscribe` is the shape this is inverted
  from.
- `TestMountAndServe_UnsubscribePost_NoSessionNoCSRF` — one bare POST with
  no `Cookie` header and no CSRF-scheme header/field, asserting `200`. This
  pins `#0034`'s carried-in "no session, no CSRF" criterion at the mux
  level, where nothing previously guarded against a future edit wrapping
  the route in `requireSession` — every handler unit test in
  `internal/handlers` would still pass if that happened, because that
  wrapping lives one layer outside what those tests exercise. This
  repository has no CSRF middleware at all (confirmed by `#0034`'s review:
  `grep -rn --include='*.go' -i csrf` matches only comments), so "no CSRF
  token" here means no header or form field any CSRF scheme would need —
  there is nothing else to omit.

## Acceptance criteria

- [ ] `POST /api/unsubscribe` cannot answer `429`. Either drop the limiter from
      this route or replace the refusal path with the same neutral 200 the
      handler gives every other input — a limiter that answers 200-and-drop is
      acceptable; one that answers 429 is not
- [ ] Whatever is chosen for `GET /api/unsubscribe` is stated explicitly. A
      scanner prefetching the href and getting a 429 instead of the 302 is
      harmless, so the GET may keep an ordinary limiter — but say so rather
      than leaving it implied
- [ ] A wiring test in `cmd/opencircuit/` drives a burst well past the current
      threshold (say 30 POSTs) through `mountAndServe` and asserts every single
      response is 200. `TestMountAndServe_RateLimitsSubscribe` is the shape to
      copy, inverted
- [ ] The same wiring test — or a sibling — proves `#0034`'s first acceptance
      criterion at the mux level: `POST /api/unsubscribe` succeeds with **no
      session cookie and no CSRF token**. Nothing currently guards against a
      future change wrapping this route in `requireSession`, and the handler
      unit tests would all still pass if it did. This is the same class of gap
      `#0024`'s review found in the admin wiring test
- [ ] If any DoS concern about an unlimited public POST is real, name it — the
      handler does one indexed `SELECT` on a random 32-byte token and then
      nothing at all for a miss, so the case has to be made rather than assumed
