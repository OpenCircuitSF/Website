## Description

Every one of the 24 rows in `claimCommentGuardDirectionalCalibrationCases` is a
**single-line** comment fixture. So `strings.Join(strings.Fields(text), " ")` —
the flattening step `#0366` factored into `claimCommentGuardFlattenComment` — is
a **semantic no-op on all of them**.

Measured by `#0366`'s review: replacing that function's body with
`return text` leaves the entire `internal/outbox` package **green**.

**Pre-existing, not introduced by the extraction.** The same review confirmed
the mutation passes identically on the pre-`#0366` file with both inline copies
mutated. The extraction neither created nor widened this.

It matters because the real corpus is not single-line: `internal/outbox/store.go`
wraps the phrase the `store.go` sentinel depends on across two comment lines, and
`#0342`'s site C was found only after joining wrapped text. Flattening is
load-bearing **in the tree** and unpinned **in the table**.

## The recommendation this issue carries

`#0366`'s reviewer recommended **recording, not closing** — and gave the reason:
closing it means adding a multi-line fixture whose only purpose is to exercise
the flattening step, which is exactly the `#0330` / `#0347` / `#0356` shape those
three families ended by refusing.

`#0258`'s caution is now explicitly binding here: the guard file carries **six**
in-file mechanisms, and each new one is fresh mutable surface.

**So the default deliverable is one honest sentence, not a fixture.** If a pass
believes a multi-line fixture genuinely earns its place, it must say why this
case differs from the three that were refused — and be prepared for that
argument to be rejected.

**One correction to what "load-bearing in the tree" means, found by
measuring rather than assuming it.** I went further than criterion 3 asks
and tested whether the two real files the doc comment cites (`store.go`,
`internal/mailing/outbox_worker.go`) actually discriminate the `return
text` mutation today. They do not: a probe test reading both real files
through `findClaimCommentGuardFindings` reports the identical directional
finding count (0, from unrelated exemptions — `store.go`'s paren scoping,
`outbox_worker.go`'s real resolution) under both the real function and the
mutation. So "load-bearing" cannot honestly mean "a test would catch its
deletion" for these two sites today — it means the function performs a
real, non-trivial transform on their text (verified: `cg.Text()` for
`store.go:463` and `outbox_worker.go:475` is NOT byte-identical to
`claimCommentGuardFlattenComment` of the same, in each case a two-line wrap
collapsing to one line). The doc comment I wrote says both things — that
these are real, non-no-op transforms, AND that no current test discriminates
their removal — rather than only the first, which would have overstated the
protection this function currently has.

**Structural comment-only proof, built to a binary (`#0258`).** Wrote
`tokdiff` (Go, `go/scanner` mode 0 — comments never emitted — comparing the
full kind+literal token stream with all position info discarded), a

| probe | expected | got |

The fourth probe is this file's specific hazard (`#0366`'s reviewer
specifically probed it too): two `const` fixtures in this file are raw
strings whose *contents* are `//`-prefixed lines that are not Go comments.

its full literal value, so an edit inside one is caught; a real comment
elsewhere is dropped by mode 0 and does not move the diff either way.

Run against the real pair, `git show HEAD:...` (pre-edit) vs the working
tree (post-edit): **`VERDICT: IDENTICAL`, 5373 tokens each side** — stronger
than criterion 5's ask, since it proves the WHOLE file byte-for-byte
comment-equivalent, not only the axis declarations. Corroborated textually:
`git diff` shows 61 added lines, 0 removed, and every added line starts with
`//` (checked programmatically, not by eye).
