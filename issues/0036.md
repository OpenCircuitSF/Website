**Review checks beyond a re-run:**

- **No dark patterns.** The confirm state contains exactly one control — a
  `<Button variant="primary">` whose `.btn-primary` rule paints `--accent` on
  `--accent-text`. There is no competing "stay subscribed" affordance at any
  weight; the preference center appears in the confirm copy as plain prose
  with *no* link (so it cannot out-compete the primary action) and as a real

  Svelte's default text interpolation. `grep -rn "@html" web/src` returns

## Root cause

Not a bug fix — `/unsubscribe` (#0014's router already reserved the route
name, per `STATIC_ROUTES` in `router.ts`) had no view. `App.svelte` fell
through to the generic "this page is on the way" placeholder for it.
`#0034` (resolved earlier today) built the endpoint this view calls;
nothing on the frontend consumed it yet.

## Fix

**`web/src/lib/unsubscribe.ts` (new)** — the pure logic, kept out of the
`.svelte` file per CLAUDE.md §1 so it's unit-testable without a DOM
(`#0094` notes Svelte components have none):

- `extractToken(query)` — reads `?token=` off the route's `URLSearchParams`,
  treating absent/blank/whitespace-only the same as "no token." Never
  throws, and deliberately does no validation: `unsubscribe.go`'s `Post`
  already answers the same neutral 200 for a missing token, so there is
  nothing for the client to pre-check.
- `resolveDoneMessage(result)` — the one function the done state's copy
  runs through. It has no "invalid token" branch: a fresh valid token, an
  unknown/expired/replayed one, and an already-complained no-op all carry a
  `message` the server already chose, and this function just returns it
  unchanged. `result === null` (the request never got a response at all —
  offline, not anything the server said) is the sole case that falls back
  to a fixed `UNSUBSCRIBE_FALLBACK_MESSAGE`, worded to match the server's
  own neutral phrasing so it reads as the same kind of statement.

**`web/src/lib/api.ts`** — added `unsubscribeOneClick(token)`: `POST
/api/unsubscribe?token=...` (omits the query param entirely when `token` is
null, matching `unsubscribe.go`'s missing-token branch). Always resolves;
there is no `ApiError` branch specific to this route beyond an actual
network failure, per the handler's "every input answers 200" contract
(`#0034`).

**`web/src/views/Unsubscribe.svelte` (new)** — thin shell, three states
(`confirm` / `submitting` / `done`):

- `confirm`: a single `<h1>`, one paragraph of copy, and one primary
  `<Button variant="primary">` — no second, competing "stay subscribed"
  link (CLAUDE.md §9, PRD §6.5's dark-pattern warning). Composed from
  `TerminalPanel` + `Prompt` (page chrome) and `Panel` + `Button` (content),
  matching `About.svelte`'s established motif composition rather than
  one-off styling.
- Clicking the button fires `unsubscribeOneClick(token)` — a real POST, and
  the *only* thing on this page that mutates anything. The GET that loads
  the page never does (the redirect that lands here, `unsubscribe.go`'s
  `Get`, is itself already side-effect-free).
- `done`: renders `resolveDoneMessage(result)` inside a `Panel`, tagged
  `role="status"` for a live-region announcement, and offers "subscribe
  again" (`navigate('/subscribe')`) and a plain `/preferences` link — no
  token attached. A real (non-no-op) unsubscribe rotates `manage_token`
  server-side, so the token this view arrived with is already stale by the
  time the done state renders; carrying it forward into a `/preferences`
  link would risk a 404 there (that route *does* distinguish invalid
  tokens, unlike this one — carried-in review finding on `#0034`). A bare
  link is the one shape that's never wrong.
- Focus management: after the done state renders, `tick()` then
  `doneHeading?.focus()` moves focus to the (`tabindex="-1"`) `<h1>`, so a
  screen-reader user is told the page changed instead of focus staying on
  a button that just disappeared. Focus ring uses `--accent`
  (CLAUDE.md §8 — never `--border-strong`).

**`web/src/App.svelte`** — imported `Unsubscribe` and added the
`$currentRoute.name === 'unsubscribe'` branch (the router already had the
route registered from `#0014`); updated the stale placeholder-branch
comment that still named `#0036`.

## Gotchas

- `web/dist/index.html` looks like an ordinary build artifact but is a
  tracked placeholder with an explicit "do not overwrite" comment in
  `.gitignore` — any `npm run build` during verification dirties it and
  must be reverted before staging, every time.
- The preference-center link in the done state cannot reuse the arriving
  token: unlike this route, `/api/preferences` still 404s an invalid token,
  and a successful (non-no-op) unsubscribe here rotates it server-side.
