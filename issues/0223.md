## Description

`scripts/testdb_gc_guard_test.sh` (added by `#0150`) proves `gc` refuses to
sweep without `--all` and skips databases with live connections. To test the
live-connection skip it opens a background `pg_sleep` connection.

**Its cleanup trap kills that connection and immediately calls `dropdb_raw`.**
The kill and the connection's actual close are not synchronised, so the drop can
land while the backend is still attached — and `dropdb_raw`'s
`DROP DATABASE IF EXISTS … || true` **swallows the failure**. The scratch
database survives, silently.

Observed by `#0097`'s implementation pass: after running the guard test, a stray
`opencircuit_test_0150gt_conn` remained, with no live connection by then. It was
dropped by hand. `scripts/testdb.sh` itself was verified unchanged — the leak is
in the guard test's own cleanup, not in the tool it guards.

**Why this is worth fixing rather than tolerating:** a leaked
`opencircuit_test_*` database is exactly what `gc --all` exists to sweep, and
`#0150` made `gc` refuse by default precisely so nobody sweeps reflexively. So
the guard test that protects that refusal is quietly generating the mess the
refusal makes expensive to clean up.

**The script already contains the fix's shape.** It polls waiting *for* the
connection to appear before running its assertion; the same poll after the kill,
waiting for it to disappear, closes the gap.

## Acceptance criteria

- [x] After the kill, cleanup waits for the connection to actually close before dropping — polled, not slept
- [x] `dropdb_raw`'s failure is no longer swallowed in the cleanup path, or the cleanup verifies the database is gone afterwards and says so if not
- [x] Running the guard test twice in succession leaves no `opencircuit_test_0150gt_*` database — demonstrated by a before/after census, twice
- [x] The poll has a bounded timeout and reports the surviving pid if it expires, rather than hanging or silently continuing
- [x] All of `#0150`'s guards still pass: bare `gc` refuses, `gc --all` skips a live-connection database and drops an idle one, and the neutered-refusal mutation still sweeps
- [x] `scripts/testdb.sh` is unchanged by this work

## Implementation notes

Two changes to `scripts/testdb_gc_guard_test.sh` only — `scripts/testdb.sh` is
untouched (byte-identity self-check in the guard test itself confirms this
every run).

1. **A `terminate_backends`/`wait_for_disconnect`/`drop_and_verify` trio of
   helpers**, used everywhere the script tears down a connection it opened:
   - `terminate_backends(db)` runs `select pg_terminate_backend(pid) from
     pg_stat_activity where datname=db`. This turned out to be load-bearing,
     not cosmetic — measured directly while fixing this: killing the local
     `psql` client (the original code's approach) does **not** stop the
     backend it was talking to. A backend blocked inside `select
     pg_sleep(20)` (the guard test's own live-connection fixture) keeps
     sleeping — and keeps the connection open — for however long the sleep
     has left, regardless of whether its client is still alive, because
     Postgres does not poll the client socket while blocked inside a
     long-running function call (`client_connection_check_interval` is unset
     here). An isolated 20-iteration/10s poll after `kill` on a fresh
     `pg_sleep(20)` connection showed the backend still `active` at every
     single check. `pg_terminate_backend` sidesteps this entirely — it
     signals the backend process directly, and `pg_sleep`'s `WaitLatch` does
     respond to that signal — so the connection actually closes within
     milliseconds instead of racing (or losing to) the remainder of the
     sleep.
   - `wait_for_disconnect(db, timeout)` polls `pg_stat_activity` (bounded,
     default 20 iterations × 0.5s = 10s) until the backend is actually gone,
     rather than assuming it. On timeout it reports the surviving pid rather
     than hanging or silently continuing (AC 4).
   - `drop_and_verify(db)` calls the existing `dropdb_raw` (still `||
     true`-guarded, since a database that was never created should not fail
     the run) but then checks `db_exists` and calls `fail` — visibly, not
     swallowed — if the database is still there (AC 2).
2. **Every teardown path now uses the trio**, not the previous
   `kill; wait; dropdb_raw` sequence:
   - The `cleanup()` `trap ... EXIT` handler (the "cleanup trap" the issue
     names) — the general safety net for both normal and abnormal exits.
   - Part 2's explicit `CONN_DB`/`IDLE_DB` teardown, now with an assertion
     (`REGRESSION #0223: connection ... did not close within the poll
     timeout`) that would itself fail loudly if the race ever reopened.
   - Part 3's `MUT_DB`, for consistency and so nothing is left for the trap
     to (silently, before this fix) paper over.
3. **A new `Part 4: leak census`** queries `pg_database` for any surviving
   `opencircuit_test_0150gt_*` row after all explicit cleanup has run, and
   fails the run by name if one is found — this is a standing regression
   guard for the leak this issue fixes, not just a one-time before/after
   check (AC 3 is additionally demonstrated manually below, twice).
4. **The `EntryTruncate`-adjacent fallback wording is untouched** — that
   belongs to `#0225`, not this issue; `scripts/testdb.sh` itself is also
   untouched (AC 6), confirmed by the guard test's own sha256 bookend on
   every run.

Four census points, all empty. Both runs printed `testdb_gc_guard_test.sh:
all guards hold (0 failures)`. The ~18–21s → ~2s runtime drop the
implementation notes claim is real and reproduces — the script no longer
waits out `pg_sleep(20)`.

**Criteria 1, 2 and 4 proved by mutation, because a passing run proves none
of them.** Two mutants were built from `git show HEAD:` copies:

1. `terminate_backends` neutered to a no-op (reproducing the pre-fix
   "kill the local client and hope" teardown). Result: exit 1,
   `warning: connection to opencircuit_test_0150gt_conn did not close within
   10s (surviving pid: 58851)` followed by `FAIL: REGRESSION #0223:
   connection ... did not close within the poll timeout before cleanup
   attempted to drop it`. The poll is bounded, names the surviving pid, and
   fails loudly — criteria 1 and 4.
   Worth recording: the drop *itself* still succeeded in this mutant, because
   the 10s poll plus the preceding parts had by then outlasted the 20s sleep.
   That is why a second mutant was needed —
   **`terminate_backends` neutered alone does not exercise `drop_and_verify`.**
2. `terminate_backends` neutered **and** the explicit
   `wait_for_disconnect "$CONN_DB" 20` shortened to `2` (1s), so the drop is
   attempted while the backend is genuinely still attached. Result: exit 1
   with all three new guards firing in order:

```
warning: connection to opencircuit_test_0150gt_conn did not close within 1s (surviving pid: 59252)
FAIL: REGRESSION #0223: connection to opencircuit_test_0150gt_conn did not close within the poll timeout before cleanup attempted to drop it
FAIL: cleanup failed to drop opencircuit_test_0150gt_conn (still exists after DROP DATABASE IF EXISTS)
FAIL: REGRESSION #0223: leaked database(s) after cleanup: opencircuit_test_0150gt_conn
```

   That is criterion 2 (`drop_and_verify` no longer swallows the failure) and
   criterion 3's standing Part-4 census, both demonstrated failing on a real
   leak rather than assumed. Census after each mutant run: `(none)` — the
   exit trap eventually reclaimed the database once its sleep expired, and no
   `opencircuit%0150gt%` database survives this review.

**Criterion 5.** Every run above printed all five of `#0150`'s guards as
`PASS`, verbatim: bare `gc` refuses; bare `gc` drops nothing; `gc --all`
skips the live-connection database; `gc --all` drops the idle one; and the
neutered-refusal mutant sweeps.

**Criterion 6.** The commit touches `scripts/testdb_gc_guard_test.sh` and
`issues/0223.md` only (`git show --stat`), and the script's own sha256
bookend passed on every run.

**Coverage gap checked, and it is closed.** Part 1's `refusal_a`/`refusal_b`
databases are dropped with plain `dropdb_raw` (still swallowed) rather than
`drop_and_verify`, which looked like a hole — but Part 4's census runs after
them and before the exit trap, so a failure there is caught by name. Verified
by reading the ordering, not assumed.

**One trivial nit, not worth an issue.** Part 4's census uses
`datname like '${TESTPREFIX}%'` where `TESTPREFIX` contains unescaped `_`,
a LIKE single-character wildcard. It can only make the census *broader*, never
narrower, so it cannot produce a false pass; no real database name can collide
with it.

**What was looked for and not found:** a `wait_for_disconnect` that could hang
(it is a bounded iteration count, default 20 × 0.5s, and the warning's
`timeout*0.5` arithmetic prints the right seconds — observed "10s" and "1s");
a `drop_and_verify` whose non-zero return is silently dropped by callers (it
calls `fail`, which increments `FAILURES`, so the return value need not be
checked); and any widening of a bound to accommodate machine load (none — the
change removes a wait rather than lengthening one).
