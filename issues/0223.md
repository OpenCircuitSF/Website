# 0223 — `testdb_gc_guard_test.sh`'s cleanup races its own connection and leaks a database

## Description

`scripts/testdb_gc_guard_test.sh` (added by `#0150`) proves `gc` refuses to
sweep without `--all` and skips databases with live connections. To test the
live-connection skip it opens a background `pg_sleep` connection.

**Its cleanup trap kills that connection and immediately calls `dropdb_raw`.**
The kill and the connection's actual close are not synchronised, so the drop can
land while the backend is still attached — and `dropdb_raw`'s
`DROP DATABASE IF EXISTS … || true` **swallows the failure**. The scratch
database survives, silently.

Observed by `#0097`'s implementation pass: after running the guard test, a stray
`opencircuit_test_0150gt_conn` remained, with no live connection by then. It was
dropped by hand. `scripts/testdb.sh` itself was verified unchanged — the leak is
in the guard test's own cleanup, not in the tool it guards.

**Why this is worth fixing rather than tolerating:** a leaked
`opencircuit_test_*` database is exactly what `gc --all` exists to sweep, and
`#0150` made `gc` refuse by default precisely so nobody sweeps reflexively. So
the guard test that protects that refusal is quietly generating the mess the
refusal makes expensive to clean up.

**The script already contains the fix's shape.** It polls waiting *for* the
connection to appear before running its assertion; the same poll after the kill,
waiting for it to disappear, closes the gap.

## Acceptance criteria

- [ ] After the kill, cleanup waits for the connection to actually close before dropping — polled, not slept
- [ ] `dropdb_raw`'s failure is no longer swallowed in the cleanup path, or the cleanup verifies the database is gone afterwards and says so if not
- [ ] Running the guard test twice in succession leaves no `opencircuit_test_0150gt_*` database — demonstrated by a before/after census, twice
- [ ] The poll has a bounded timeout and reports the surviving pid if it expires, rather than hanging or silently continuing
- [ ] All of `#0150`'s guards still pass: bare `gc` refuses, `gc --all` skips a live-connection database and drops an idle one, and the neutered-refusal mutation still sweeps
- [ ] `scripts/testdb.sh` is unchanged by this work

## Notes

Reported by `#0097`'s implementation pass under `CLAUDE.md` §9.

Keep `#0150`'s containment discipline while editing: everything destructive runs
under the `opencircuit_test_0150gt_` prefix, which no real `ISSUE=NNNN` token can
produce, and the mutation runs against a **private copy** in a `mktemp -d`
workdir with the tracked script's hash asserted unchanged. `#0150`'s review
verified all of that; do not weaken it.

Note also `#0207` is open on wiring the standalone guard scripts into something
that runs them, and `#0117`'s review measured why they cannot simply join every
`check.sh` run (`dev_guard_test.sh` costs ~48s and binds `:5173`). This issue
does not depend on that, but the two will meet.
