## Description

> ✅ **Resolved 2026-08-23** (`16bfdee`) — verified independently by the
> phase-3 reviewer at load average 2.09 (idle). All five acceptance criteria
> re-proved: the call-site mutation was re-run from scratch (and its inverse,
> which pins the two call sites as genuinely separate routes), the
> `smithy.APIError` discriminator was probed against the SDK on fifteen error
> shapes, and the catch-all log line leaks nothing. See `## Review notes`.

Three residues of `#0182`, found by its pass-2 review. The first is the one that matters.

**1. The terminal-row call site has no end-to-end test.** `MarkFailedRow`'s `adminSendErrorMessage(sendErr)` argument can be replaced with `""` and **the whole suite still passes.**

`#0182`'s committed end-to-end test uses `errors.New(sesText)`, which matches no modeled SES type and therefore takes the **retryable** path — not the terminal-row path that pass 1's reviewer originally exercised with a real `&types.MessageRejected{}`. So the property holds (the reviewer re-proved the terminal route by hand), but the committed test does not cover the route it appears to.

That is the same shape as `#0171`: a test that looks like it guards a path and guards its neighbour.

**2. SDK transport and credential failures reach admins raw.** `#0182` established that everything on the raw-text branch is AWS-SDK-authored — which is true, but "AWS-authored" is not "what the recipient's mail system said". A credential refresh failure or a DNS/dial error arrives through the same site as:

> `operation error SES v2: SendEmail, … failed to refresh cached credentials …`

Same class as `#0182`, one layer narrower: an admin looking at a failed row learns nothing actionable from it, and it is an infrastructure fault rather than a delivery outcome.

**3. The unprefixed fallback is a catch-all, not an enumeration.** `!hasPrefix → adminSendBuildFailureMessage` means any *future* unprefixed return would be silently mislabelled "could not be built". `#0182` bounced once for exactly this — assuming a class rather than enumerating it — so the shape is worth closing while it is fresh.

## Root cause

**Item 1.** `#0182`'s committed `TestWorker_SESRejectionReachesFailedSendsIntact`
drove a rejection via `errors.New(sesText)` wrapped in `sesWrapPrefix`, which
`classifySendError` does not recognize as any modeled `sesv2/types` exception
(`errors.As` fails on a bare `errors.New`), so it fell through to the default
`sendClassRetryable` case — `sendOne`'s `MarkRetryOrFailed` call site, not
`MarkFailedRow`. The test's own doc comment claimed to reproduce the pass-3
reviewer's terminal-row proof, but nothing in the test actually forced that
routing, so `MarkFailedRow`'s message argument was free to change (or be
deleted) without failing anything.

**Items 2 and 3.** `adminSendErrorMessage` classified purely on whether an
error carried `SESMailer.Send`'s own `"mailing: sending via SES: "` prefix:
present and not a context error → assumed genuine SES text and passed through
raw. That conflated two different things that both carry the prefix — an
actual SES/AWS SDK response (a rejection, a quota, a throttling notice) and a
transport-level failure that never reached a response at all (a credential
refresh failure, a DNS/dial error) — showing an admin AWS SDK/Go internals for
the latter. And the `!hasPrefix` branch treated "no prefix" as sufficient to
mean "one of `SESMailer.Send`'s two argument guards," with no enumeration
enforcing that the whole way through.

## Fix

**Item 1** — added `TestWorker_SESRejectionReachesFailedSendsIntact_TerminalRow`:
drives a real `&types.MessageRejected{}` (which `classifySendError` genuinely
routes to `sendClassTerminalRow` → `MarkFailedRow`) through a real
`drainCampaign`, then reads the row back via `CampaignStatsStore.FailedSends`.
Proven to fail (see `## Verification`) when `MarkFailedRow`'s message argument
is mutated to `""` — the exact acceptance bar this issue set. Also updated the
neighboring `TestWorker_SESRejectionReachesFailedSendsIntact` (the retryable
path) to wrap a genuine `&types.LimitExceededException{}` instead of a bare
`errors.New` — a bare stand-in is not representative of anything
`SESMailer.Send` can actually return, and (see below) masked a real
classification bug once items 2/3's fix was written.

**Items 2 and 3, together.** `adminSendErrorMessage` no longer gates on
`sesWrapPrefix` first. It now classifies by error *shape*:

1. This package's own sentinels — `ErrNoMessageID`, and two new ones,
   `ErrEmptyRecipient`/`ErrEmptyBody` (replacing ad hoc `errors.New` literals
   in `ses_mailer.go`'s two argument guards with named, matchable values) —
   plus a context timeout during the retry backoff, are matched explicitly by
   `errors.Is`. This is the enumeration criterion 3 asked for: the two
   argument-guard errors are no longer inferred from "no prefix," they are
   matched by identity.
2. Anything that **is or wraps a `smithy.APIError`** (every modeled
   `sesv2/types` exception implements this interface — confirmed by reading
   `aws-sdk-go-v2/service/sesv2/types/errors.go` — and `smithy.GenericAPIError`
   covers an unmodeled one) is a genuine response from SES about *this send*:
   kept verbatim, with only our own prefix stripped if present.
3. Anything else that still carries `sesWrapPrefix` came from inside
   `SESMailer.Send`'s `SendEmail` call but never resolved to a service
   response to deserialize — a credential-chain refresh failure, a DNS/dial
   failure, wrapped by the AWS SDK in `*smithy.OperationError` without a
   `smithy.APIError` underneath. New `adminSendUnreachableMessage`: "Not sent
   — this attempt could not reach SES at all (a network or credentials
   problem on our end, not anything about this recipient or campaign). If
   this keeps happening, an engineer needs to check the server's AWS
   configuration." **Decision (item 2):** mapped to fixed text rather than
   passed through with a marker — an admin debugging a bad campaign wants the
   rejection reason verbatim (unchanged, item 2's other half), while an admin
   debugging a broken deployment needs to know it is *not* the campaign's
   fault, which "failed to refresh cached credentials" does not say plainly.
   A marker would still require the admin to know what the marker means;
   fixed text says it directly.
4. Anything left (should not happen) is logged via `slog.Default().Error`
   naming the unrecognized error, then degraded to the existing
   `adminSendBuildFailureMessage` text. **Decision (item 3):** enumeration
   over a silent catch-all — a future unenumerated `SESMailer.Send` return
   (or a different `Mailer` implementation's return) now surfaces in the
   server log instead of only a possibly-wrong admin sentence.

**Gotcha found while implementing, not part of the original plan.** The first
draft of this fix gated the `smithy.APIError` check *behind* `hasPrefix`,
reasoning "only `SESMailer.Send` wraps errors, so no prefix ⇒ one of its own
sentinels." That is false for any `Mailer` other than `SESMailer` — including
every test double in this package — none of which add the prefix.
`TestWorker_ThreeRetryableFailuresMarkRowFailed` (an existing, unrelated test)
passes a bare `&types.TooManyRequestsException{}` through `sendOne` three
times, and with the prefix-gated design each attempt logged "unrecognized
error with no SES wrap prefix" and mislabeled a real SES exception as
"could not be built." Caught by running the full scoped suite (`## Verification`)
before committing, not by a targeted test — a reminder that a fix built only
against its own new test cases can still break a real path the moment it
meets code it didn't write. The final design (above) checks
`errors.As(err, &apiErr)` directly, independent of any wrapping, which
handles both `SESMailer`'s prefixed errors and any other `Mailer`'s bare ones
identically and removed the false log lines entirely.

## Gotchas

- The prefix-gated first draft of items 2/3's fix silently broke an existing,
  unrelated test's expectations by logging every bare AWS exception a test
  double returns as "unrecognized" (see `## Fix`'s last paragraph). Only the
  full scoped suite run caught it — the new tests alone would have looked
  green. Worth remembering for future `Mailer`-adjacent changes: this
  package's test doubles do not mimic `SESMailer.Send`'s wrapping, and a
  classification function meant to serve `sendOne` generically should not
  assume they do.

  this was already true of the test before this change and is unrelated to
  this issue, but worth noting for anyone extending it.

### Item 2 — the `smithy.APIError` discriminator, checked against the SDK

**The claim holds structurally.** `sesv2@v1.66.6/types/errors.go` declares 13
modeled exception types and defines `Error()`, `ErrorMessage()`, `ErrorCode()`
and `ErrorFault()` on **all 13** — `grep -c 'func (e \*.*) ErrorFault()'` returns
13 against 13 `type … struct` declarations. A compile-time assertion listing all
13 plus `*smithy.GenericAPIError` as `[]smithy.APIError` compiles, so the
interface is satisfied by every modeled type this code can receive, and by the
unmodeled fallback. Transport and credential failures carry none of those
methods, so `errors.As(err, &apiErr)` genuinely separates "SES answered" from
"we never got an answer" — not a proxy for it.

**Boundary probes**, run as a temporary table test in `internal/mailing` against
a private database, then deleted (tree confirmed clean at `16bfdee` afterwards).
`wrapSES` = `fmt.Errorf("mailing: sending via SES: %w", …)`, `opErr` =
`&smithy.OperationError{ServiceID: "SES v2", OperationName: "SendEmail", Err: …}`
— the exact shapes production produces:

| Probe | Lands on | Right? |
|---|---|---|
| bare `*types.TooManyRequestsException` (a test double's shape) | verbatim | yes — the bug the implementer caught mid-implementation, confirmed fixed |
| `wrapSES(opErr(*types.MessageRejected))` | verbatim | yes (but see the finding below on what "verbatim" contains) |
| `wrapSES(opErr(*net.OpError))` — DNS/dial | `adminSendUnreachableMessage` | yes — item 2's headline case |
| bare `*net.OpError`, no prefix | catch-all + log | acceptable; see below |
| `wrapSES(opErr(credential refresh failure))` | `adminSendUnreachableMessage` | yes |
| `wrapSES(opErr(…%w context.DeadlineExceeded))` | `adminSendTimedOutMessage` | yes — the `errors.Is` check precedes the `APIError` check, so an SDK-surfaced deadline is not mistaken for a service response |
| bare `context.DeadlineExceeded` | `adminSendTimedOutMessage` | yes |
| `wrapSES(opErr(…%w context.Canceled))` | `adminSendTimedOutMessage` | yes |
| `wrapSES(opErr(*retry.MaxAttemptsError{Err: *types.TooManyRequestsException}))` | verbatim | yes — `MaxAttemptsError` unwraps, so a retried throttle still reads as SES's answer |
| `wrapSES(opErr(*retry.MaxAttemptsError{Err: *net.OpError}))` | `adminSendUnreachableMessage` | yes — the same wrapper over a transport fault lands on the other side, which is the discriminator doing real work rather than pattern-matching the wrapper |
| `wrapSES(opErr(*smithy.GenericAPIError))` | verbatim | yes — a future unmodeled SES exception is still SES's answer |
| `ErrEmptyRecipient` / `ErrEmptyBody` | `adminSendBuildFailureMessage`, **no** log | yes — enumerated by identity, item 3's bar |
| `ErrNoMessageID` | `adminNoMessageIDMessage` | yes |
| unrecognized bare error | catch-all **+** log | yes |

### Item 3 — the catch-all log, and what it says

`slog.Default().Error("mailing: adminSendErrorMessage saw an unrecognized error", "err", err)`
fires on an unrecognised error and **only** on an unrecognised error — the
probe asserts an empty log buffer on all 13 classified cases. Decoded as JSON,
the record is `level=ERROR`, carries the `err` attribute naming the error, and
carries no `recipient`, `email`, `to`, `send_id`, or `manage_token` key. It logs
the error value and nothing else, so **nothing leaks**: the campaign body (which
is where the manage token lives) never reaches a `Send` error, and a recipient
address can only appear if the error itself already contains one — which is true
of the admin-facing text too, and is that recipient's own row.

**Ruling on `slog.Default()` vs `w.log`: correct as shipped.**
`adminSendErrorMessage` is a package-level function with no `*Worker` receiver,
so `w.log` is not reachable without changing its signature or moving the log to
the call site. And the two are the *same logger in production*:
`cmd/opencircuit/main.go:315` passes `slog.Default()` as `WorkerDeps.Log`, and
`NewWorker` falls back to `slog.Default()` when it is nil. They diverge only
where a test injects a buffer logger. The real (minor) cost is not the logger
but the missing context: every other `w.log` line in `worker.go` carries
`"send_id", r.SendID`, and this one cannot. Reported below, not blocking.

### Worth filing (reported, not filed — §9)

1. **The "verbatim" branch shows an admin the AWS SDK's operation-error
   scaffolding, not just SES's sentence.** Both committed tests wrap a *bare*
   modeled exception, so they assert clean text like
   `MessageRejected: Email address is not verified: …`. Production never
   produces that shape: `smithy.OperationError.Error()` is
   `"operation error %s: %s, %v"` and `awshttp.ResponseError.Error()` is
   `"https response error StatusCode: %d, RequestID: %s, %v"`, so the real
   `failed_sends[].error` reads
   `operation error SES v2: SendEmail, https response error StatusCode: 400, RequestID: <uuid>, MessageRejected: …`.
   My probe confirms the `operation error SES v2: SendEmail, ` half survives the
   strip. This is **not a regression** — `#0182` behaved identically and its
   pass-2 review proved the property with the same bare-exception shape — but it
   is the same complaint `#0185` item 2 opened with ("an admin looking at a
   failed row learns nothing actionable"), surviving on the branch item 2 chose
   to leave alone. Now cheap to fix: this code already holds an
   `apiErr smithy.APIError`, so `apiErr.ErrorCode() + ": " + apiErr.ErrorMessage()`
   yields exactly what the tests already assert, for real errors too.
2. **A transport error that does not carry `sesWrapPrefix` is labelled "could
   not be built".** The transport branch discriminates on a string prefix while
   the branch above it discriminates on a type. `errors.As(err, &opErr)` against
   `*smithy.OperationError` would classify bare SDK transport errors correctly
   too, and would keep the whole function type-based. Unreachable through
   `SESMailer` today, and logged when it happens.
3. **The catch-all log line has no `send_id`.** Every other error log in
   `worker.go` names the row; this one is the only place an unenumerated
   `Mailer` return will ever surface, and it cannot be tied back to a send.
   Moving the log to `sendOne`'s two call sites (or returning a "did not
   recognise" signal alongside the string) would fix it and let it use `w.log`.
