## Description

`#0033` built the `suppressions` table and `subscribers.SuppressionStore`
(`Add`/`AddTx`/`IsSuppressed`/`List`/`Remove`), but the only admin surface over
it is a side effect of two subscriber-row actions. An admin can *create* a
manual suppression and cannot *reverse* one; `List` has no caller at all; and
the one removal path deletes a suppression without regard to why it was added.
None of this blocked `#0033` — its acceptance criteria are store-level and are
met — but the gaps compound as soon as `#0038` starts writing `hard_bounce` and
`complaint` rows.

### 1. Decision — reason-scoped rows. Primary key becomes `(email, reason)`

**Chosen: reason-scoped rows.** One `suppressions` row per (address, reason);
an address that both hard-bounced and complained carries two rows.

**Why the other two candidates fail.** Both keep one row per address, and under
`Add`'s first-writer-wins contract that row records only the *first* reason.
Walk the two orderings of the case criterion 2 names:

| Order of events | Stored row after both | `Remove(email,"complaint")` | Result |
|---|---|---|---|
| hard bounce, then complaint | `hard_bounce` (the complaint `Add` no-ops) | no reason match | hard bounce survives — correct, by luck |
| complaint, then hard bounce | `complaint` (the bounce `Add` no-ops) | reason matches, row deleted | **hard-bounce suppression destroyed** |

The second row is the whole defect, and *neither* **reason-scoped removal**
(`Remove(email, reason)` deleting only on a match) nor **a removal that
refuses on mismatch** prevents it: in that ordering the stored reason genuinely
*is* `complaint`, so both designs delete and both are correct-by-their-own-rules
while mail resumes to a permanently-failing address. The information is
destroyed at **write** time by the single-row model, not at removal time, so no
removal-side rule can recover it. They differ from each other only in which
error a mismatch returns — a UX distinction, not a correctness one. Rejected.

Reason-scoped rows is the only candidate that can represent "this address has
two independent reasons to be blocked", which is the fact the send gate needs.
It also matches PRD §6.5's state machine, where four different events each
"insert into `suppressions`" as independent facts.

**What it costs:**

- One new migration (§2) and a `Remove` signature change with exactly two call
  sites plus tests.
- `Add`'s idempotency key becomes `(email, reason)`, so the "first reason
  recorded for an address is the one that persists" sentence in its doc comment
  becomes false and must be rewritten. A second, *different* reason now inserts
  rather than no-ops. This is the intended behavior change.
- The admin list shows one row per (email, reason), so an address can appear
  more than once. §5 orders by email so those rows are adjacent.
- Removing a suppression is no longer "unblock this address" — it is "retire
  one reason". Every piece of admin copy and audit metadata has to say which
  (§4, §5).

`IsSuppressed` is deliberately **not** reason-scoped — see §3.

### 2. Migration `000013_scope_suppressions_by_reason`

Append-only (CLAUDE.md §1): a new pair, `000012` is never edited.

```sql
-- 000013_scope_suppressions_by_reason.up.sql
-- #0100: an address can have more than one independent reason to be blocked.
-- Keying on email alone made the first reason recorded the only one kept, so a
-- later admin "clear complaint" could delete a hard-bounce suppression and let
-- mail resume to a permanently-failing address. Key on (email, reason) so each
-- reason is its own removable fact. IsSuppressed stays reason-blind.
ALTER TABLE suppressions DROP CONSTRAINT suppressions_pkey;
ALTER TABLE suppressions ADD CONSTRAINT suppressions_pkey PRIMARY KEY (email, reason);
```

```sql
-- 000013_scope_suppressions_by_reason.down.sql
-- This DOWN INTENTIONALLY FAILS if any address carries more than one reason.
-- The only way to narrow the key back to (email) is to discard suppressions,
-- and silently discarding a suppression is the exact failure #0100 exists to
-- prevent. Resolve the duplicates deliberately before rolling back.
ALTER TABLE suppressions DROP CONSTRAINT suppressions_pkey;
ALTER TABLE suppressions ADD CONSTRAINT suppressions_pkey PRIMARY KEY (email);
```

**Existing rows.** Nothing to migrate and no dedupe step: the old `(email)`
uniqueness *implies* `(email, reason)` uniqueness, so the widened key can never
conflict with data already present. This is true independently of how many rows
exist — do not justify it with "the table is empty in production". (It is:
production still serves the placeholder, §0. That is a convenience, not the
argument.)

**No new indexes.** The composite PK's btree leads with `email`, so every
`WHERE email = …` lookup (`IsSuppressed`, `ListByEmail`, `Remove`) is already
served. `List` is an unfiltered scan of an internal table with no expected
scale; an index for its `ORDER BY` would be premature.

**Doc parity.** `internal/db`'s `TestDatabaseDocMigrationParity` fails unless
both are updated in the same commit:
- add a `000013_scope_suppressions_by_reason` row to `docs/database.md`'s
  migration table (and amend the `000012` row's description to say the key was
  later widened);
- change `docs/database.md:4` and `CLAUDE.md` §1's repository-layout row from
  `000001`–`000012` to `000001`–`000013`.

### 3. `IsSuppressed` does not change, and neither does the subscribe path

**Semantics: any row of any reason blocks.** `IsSuppressed(ctx, email)` keeps
its exact signature, its exact SQL, and its single round trip:

```sql
SELECT EXISTS (SELECT 1 FROM suppressions WHERE email = lower(trim($1)))
```

Do **not** add a reason parameter, a second query, an `IN` list, or any
branch. Three reasons, in order of severity:

1. **CLAUDE.md §9 / `#0026` / `#0088`.** `POST /api/subscribe` must return a
   byte-identical uniform `202` across every branch, and `#0088` closed a
   100%-accurate *timing* oracle by making every branch do exactly one
   `IsSuppressed` plus one `FindByEmail`, always, in that fixed order. Any
   change that makes the suppressed branch cheaper or costlier reopens it.
   **`internal/handlers/subscribe.go`'s request path must not be touched by
   this issue at all** beyond the two doc-comment edits in §7.
2. The send gate's question is "may we mail this address", which is
   reason-independent by definition.
3. It keeps the blast radius of the key change inside the store and the admin
   surface.

`TestSubscribe_UniformResponseAcrossBranches` is the regression gate; it must
pass untouched.

### 4. Store API (`internal/subscribers/suppressions.go`)

SQL stays in this package (CLAUDE.md §1). Changes:

| Method | Change |
|---|---|
| `Add` / `AddTx` | `ON CONFLICT (email, reason) DO UPDATE SET email = suppressions.email RETURNING …`. The no-op-update trick that keeps `RETURNING` alive is unchanged and still load-bearing. Contract becomes: **idempotent per (email, reason)** — a repeat of the same reason returns the original row (original `note`, original `created_at`); a *different* reason inserts a new row. Rewrite the doc comment's "the first reason recorded for an address is the one that persists" paragraph accordingly. |
| `IsSuppressed` | unchanged (§3). Add one sentence to its doc: reason-blind by design — any row of any reason blocks. |
| `Remove` | **`Remove(ctx, email, reason string) (Suppression, error)`.** Validates `reason` against `suppressionReasons` → `ErrInvalidSuppressionReason`. `DELETE FROM suppressions WHERE email = lower(trim($1)) AND reason = $2 RETURNING email, reason, note, created_at`. `pgx.ErrNoRows` → `ErrSuppressionNotFound`. Returns the deleted row because the row is being destroyed and the audit entry is the only remaining record of its `note`/`created_at`. **There is deliberately no reason-less removal** — the reason-blind delete must be unreachable, not merely discouraged. |
| `ListByEmail` (new) | `ListByEmail(ctx, email string) ([]Suppression, error)` — every row for one normalized address, `ORDER BY created_at DESC`. Callers: `ClearComplaint` (to report survivors) and the removal handler. |
| `List` | returns `[]SuppressionListItem` (new type: the four columns plus `SubscriberStatus *string`) via `LEFT JOIN subscribers ON subscribers.email = suppressions.email`, `ORDER BY suppressions.email ASC, suppressions.created_at DESC`. See §5 for why the join and why the order changed from newest-first. `Suppression` itself is left alone so `Add`/`Remove` keep their simple shape. `List` has no caller outside tests today, so the signature change is free. |

`SuppressionReason*` constants keep their current names.

### 5. Admin surface

#### 5a. `ClearComplaint` (`internal/handlers/admin_subscribers.go`)

- Call `Remove(ctx, after.Email, subscribers.SuppressionReasonComplaint)`.
  `ErrSuppressionNotFound` stays non-fatal (unchanged); any other error stays a
  500 (unchanged).
- Then `ListByEmail(ctx, after.Email)` for the survivors.
- `adminSuppressionWriter` grows `Remove(ctx, email, reason string) (subscribers.Suppression, error)` and `ListByEmail`. It stays a narrow
  handler-local interface (CLAUDE.md §1); `*SuppressionStore` satisfies it.
- **Confirmation copy must stop over-claiming.** Today it says "The matching
  suppression-list entry was also removed, so a future resignup is no longer
  blocked at the send gate" — a statement that becomes *false* the moment a
  `hard_bounce` row survives. Four cases:

  | removed | survivors | message suffix |
  |---|---|---|
  | yes | none | ` The "complaint" suppression-list entry was removed, and no other suppression remains for this address.` |
  | yes | some | ` The "complaint" suppression-list entry was removed, but this address is still suppressed for: hard_bounce. It remains blocked at the send gate.` |
  | no | none | ` No "complaint" suppression-list entry existed for this address.` |
  | no | some | ` No "complaint" suppression-list entry existed. This address is still suppressed for: hard_bounce.` |

  Build the reason list from `ListByEmail`, never hardcode `hard_bounce`.
- **Audit metadata.** Replace the single `suppression_removed` bool with:
  `suppression_removed` (bool), `suppression_removed_reason` (`"complaint"`),
  `suppression_removed_note`, `suppression_removed_created_at`, and
  `suppressions_remaining` (`[]string` of surviving reasons, `[]` when none).
  A later reader must be able to tell which suppression was destroyed and which
  survived without re-deriving it. Keep the existing
  `previous_unsubscribed_at` / `overwrites_note` fields.
- The subscriber's `status` handling is untouched: `AdminClearComplaint`
  remains the sole exit from `complained` (CLAUDE.md §9).

#### 5b. New handler `internal/handlers/admin_suppressions.go`

A separate handler and file, not more methods on `AdminSubscribersHandler`: a
suppression is keyed by email and can exist with **no subscribers row at all**
(hard deletion, `#0060`), so it is not a subscriber sub-resource.

```
GET  /admin/suppressions          → { "suppressions": [ … ], "count": n }
POST /admin/suppressions/remove   → body { email, reason, note }
```

`POST …/remove` rather than `DELETE /admin/suppressions/{email}`: email
addresses make poor path segments (`+`, `%`, `.`, percent-encoding), the action
requires a justification note in a body, and every other mutating admin action
in this codebase is a `POST`. Follows `Suppress`'s shape deliberately.

**Store seams** (narrow, handler-local): `suppressionLister` (`List`,
`ListByEmail`, `Remove`) and `suppressionSubscriberLookup` (`FindByEmail`
only, for the one decision in the next bullet).

**Removal rules:**

- `note` required, 400 on empty-after-trim — mirrors `Suppress`.
- `reason` must be one of the four; 400 otherwise.
- `reason == "complaint"` **and** a subscribers row exists for the address →
  **409**, message directing the admin to Subscribers → Clear complaint. This
  keeps exactly one audited path that touches a complaint (CLAUDE.md §9's
  concentration of authority), rather than opening a second one.
- `reason == "complaint"` **and no subscribers row exists** (the `#0060` orphan)
  → allowed. Otherwise an orphaned complaint suppression would be permanently
  unremovable, since `ClearComplaint` is keyed by subscriber id and unreachable.
- `ErrSuppressionNotFound` → **404** here (unlike in `ClearComplaint`, where it
  is incidental; here it is the whole request).
- **This endpoint never touches the `subscribers` table.** See §6.
- Response: `{ removed: {email, reason, note, created_at}, remaining: ["hard_bounce"], message }`, with a message that names the surviving reasons the
  same way §5a does.

**Audit.** New constant in `internal/audit/actions.go`:
`ActionSuppressionRemoved = "subscriber.suppression_removed"`, written with
`TargetType: audit.TargetSubscriber` and `TargetID` = the subscriber id when
one exists, `nil` when orphaned. Metadata: `email`, `reason`, `note` (the
admin's justification), `removed_note`, `removed_created_at`,
`suppressions_remaining`, `subscriber_status` (or `null`),
`subscriber_status_unchanged: true`. Doc-comment the constant to the same
standard as its neighbours.

**Wiring** (`cmd/opencircuit/main.go`): construct `adminSuppressionsH` next to
`adminSubscribersH` from the same `suppressionsStore` + `subscribersStore`;
declare it `nil` on the dev/`STORAGE=json` path exactly as
`adminSubscribersH` is (line ~362); add both routes **inside `adminRoutes()`**
under an `if adminSuppressionsH != nil` block. Do not register them anywhere
else — `admin_routes_ast_test.go` fails the build if you do, and
`admin_wiring_test.go` enumerates `adminRoutes(...)` so the new routes get
their RequireSession+RequireAdmin coverage automatically once the parameter is
threaded through both call sites (main.go and the test).

### 6. Reversing a manual suppression, and what it does to `status`

Criterion 1's flow: Admin → Suppressions → find the `manual` row → Remove with
a note.

**Removal changes no subscriber status, ever.** A manual suppress leaves the
row `unsubscribed`; un-suppressing leaves it `unsubscribed`. The address is no
longer blocked at the send gate, but it is still not a subscriber — it must come
back through double opt-in (`restartSignup` already handles `unsubscribed`).
Silently flipping anything to `active` would manufacture consent that was never
given. The response message must say this in as many words:
"…this does not resubscribe the address; it must opt in again."

**Interaction with CLAUDE.md §9.** Removing a `hard_bounce` or `manual`
suppression from a subscriber who is `complained` leaves the status
`complained`, so the address still cannot resubscribe — `#0026`'s complained
branch sends nothing. Nothing in this issue can auto-resubscribe a complained
subscriber, and the `reason == "complaint"` refusal in §5b means this endpoint
cannot even be used as an oblique route toward it. `AdminClearComplaint`
remains the only thing that clears `complained`.

## Root cause

`#0033` gave `suppressions` a single-column primary key (`email`) and made
`Add` idempotent per email: the first reason recorded for an address was the
only one ever kept, and any later `Add` for a different reason silently
no-opped instead of inserting. `Remove(email)` deleted by email alone. As
long as every suppression had exactly one possible reason at a time, this was
invisible. It becomes a correctness bug the moment an address can acquire a
second, independent reason to be blocked (`#0038`'s hard-bounce/complaint
ingestion): whichever reason was recorded first is the only one the database
remembers, so clearing that one reason (e.g. an admin's "clear complaint")
deletes the address's only suppression row and lets mail resume to it even
though a second, un-recorded reason (e.g. a hard bounce) still applies. The
information was destroyed at `Add` time, not `Remove` time, so no
removal-side rule could have recovered it. Separately, `SuppressionStore.List`
had no caller anywhere in the codebase, and `Remove` was reachable only from
`AdminSubscribersHandler.ClearComplaint` — a subscriber suppressed via the
**Suppress** button (ending up `unsubscribed`, not `complained`) had no route
back except direct database access.

## Fix

Followed the plan as written, reason-scoped rows: widened `suppressions`'
primary key to `(email, reason)` via `migrations/000013` (append-only per
CLAUDE.md §1; `000012` untouched). `Add`'s conflict target moved to
`(email, reason)`, so a second, different reason for an already-suppressed
address now inserts a coexisting row instead of no-opping. `Remove` gained a
mandatory `reason` parameter, validates it, and returns the deleted row (its
`note`/`created_at` are the only remaining record once it's gone) — there is
deliberately no reason-less removal path. Added `ListByEmail` and widened
`List` to a `LEFT JOIN` against `subscribers` (`ORDER BY email ASC,
created_at DESC`) so an address's several rows sit adjacent and the admin
screen can show whether a row is orphaned. `IsSuppressed` and the
`POST /api/subscribe` request path are untouched, exactly as directed — the
send gate stays reason-blind by design, and `#0026`'s uniform-202 timing
contract (`#0088`) was never touched.

`AdminSubscribersHandler.ClearComplaint` now removes only the `complaint` row
via the new `Remove(email, reason)` and reports survivors from `ListByEmail`
in both the response message (four cases, per plan §5a) and new audit
metadata (`suppression_removed_reason`, `suppression_removed_note`,
`suppression_removed_created_at`, `suppressions_remaining`).

New `internal/handlers/admin_suppressions.go` adds `GET /admin/suppressions`
and `POST /admin/suppressions/remove`, wired into `adminRoutes()` (both
`main.go` call sites plus `admin_wiring_test.go`, so
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` and
`TestAdminRoutesRegisteredOnlyViaTable` cover the new routes automatically).
`reason=complaint` removal 409s while a `subscribers` row exists for the
address (directing the admin to Subscribers → Clear complaint, the one
sanctioned path per CLAUDE.md §9) and is allowed only when the suppression is
orphaned (`#0060`). Removal never touches subscriber `status` — reversing a
manual suppression leaves the row `unsubscribed`, never `active`.

Web: `web/src/lib/api.ts` (`listSuppressions`, `removeSuppression`),
`types.ts` (`Suppression`), `admin.ts` (`SUPPRESSION_REASONS`,
`suppressionReasonLabel`, `validateSuppressionNote`,

subscriber-backed complaint row rather than letting the admin discover the
409), and a sixth `Admin.svelte` subtab (Email · Reason · Note · Added ·
Subscriber status, per-row Remove with a required-note confirm modal). Fixed
the two stale doc-comment claims named in criterion 4
(`SuppressionChecker`/`NoSuppressions` in `subscribe.go`), plus the two
carried-in-review string fixes: the suppress modal's "removing it requires a
separate admin action" now names Admin → Suppressions, and the
clear-complaint `confirm()` now says only the `complaint` entry is removed.

range (`TestDatabaseDocMigrationParity`).

No deviation from the plan.
