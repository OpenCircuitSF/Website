# 0100 — The suppression list has no admin surface, and clear-complaint removes suppressions reason-blind

|---|---|

## Description

`#0033` built the `suppressions` table and `subscribers.SuppressionStore`
(`Add`/`AddTx`/`IsSuppressed`/`List`/`Remove`), but the only admin surface over
it is a side effect of two subscriber-row actions. An admin can *create* a
manual suppression and cannot *reverse* one; `List` has no caller at all; and
the one removal path deletes a suppression without regard to why it was added.
None of this blocked `#0033` — its acceptance criteria are store-level and are
met — but the gaps compound as soon as `#0038` starts writing `hard_bounce` and
`complaint` rows.

## Acceptance criteria

- [ ] **An admin can reverse a manual suppression through the UI.**
      `SuppressionStore.Remove` is reachable today only from
      `AdminSubscribersHandler.ClearComplaint`, which `Admin.svelte` offers only
      on `complained` rows (`canClearComplaint`). A subscriber suppressed via the
      **Suppress** button ends up `unsubscribed`, not `complained` — so a
      mis-click is currently reversible only by direct database access. The
      suppress modal already tells the admin that "removing it requires a
      separate admin action"; that action needs to exist.
- [ ] **Scope suppression removal by reason, or make it explicit.** `Remove`
      deletes by email alone. Once `#0038` lands, an address that both
      hard-bounced and complained carries one row; clearing the complaint would
      silently delete the `hard_bounce` suppression and let mail flow to a
      permanently-failing address. Decide the model — reason-scoped rows,
      reason-scoped removal, or a removal that refuses when the stored reason
      isn't the one being cleared — and make `ClearComplaint`'s confirmation and
      audit metadata say which happened.
- [ ] **Give `SuppressionStore.List` a caller.** It is correct and tested but
      currently unreachable from any route or view; an admin suppression-list
      screen (email, reason, note, created_at) is the natural home, and it is
      also what makes the two criteria above discoverable.
- [ ] **Sweep the two stale doc comments in `internal/handlers/subscribe.go`.**
      `SuppressionChecker`'s comment still reads "the `suppressions` table added
      by #0033, which has not landed yet", and `NoSuppressions`' still reads
      "the SuppressionChecker wired in cmd/opencircuit/main.go until #0033
      lands". Both are false as of `ad6cafc` — `main.go` wires the real
      `subscribers.NewSuppressionStore(pool)`. `NoSuppressions` itself is still
      legitimately used as the nil-default and by tests, so keep the type and fix
      only the prose.

## Notes

PRD §6.2, §6.5. Filed by `#0033`'s review pass (2026-08-20), which approved that
issue on its own criteria — store operations add/check/list/remove, all present,
`Remove` audited at its one call site behind `RequireAdmin` — and split these
four items out rather than widening `#0033`'s scope after the fact.

The second criterion is the load-bearing one: it is a correctness problem that
only becomes reachable when `#0038` writes non-`manual` reasons, so it should be
settled before or with `#0038` rather than after.
