## Description

`#0187`'s phase-3 review extracted both `citationPattern`s verbatim and ran them
over a shared 38-case battery. Two findings about the pattern text itself.

**1. `PRD\s*§` means different things in the two guards.** Go's `\s` is
`[\t\n\f\r ]`; JavaScript's is Unicode-aware. So five shapes — **NBSP**, thin
space, VT, ZWNBSP, and ideographic space — are caught by the web half and
**missed by the Go half**. NBSP is the one that matters: it is what a word
processor or a copy-paste from a rendered document produces, so it is a
plausible spelling for an admin-facing string to acquire, and the Go guard is
the half covering handler code.

This predates `#0187` and was out of its scope. A shared character class closes
it — the two patterns should mean the same thing or the guard's coverage
depends on which language a string happens to live in.

**2. Item 3's recorded reasoning is wrong about RE2.** `#0187` accepted the
`docs/*.md` external-URL false positive rather than tightening the pattern,
reasoning that RE2 has no lookbehind so only V8 could express a scheme
exclusion, and divergence between the guards would be worse. **The premise is
true and the inference is false.** The reviewer built and ran two
RE2-compatible forms in Go, both 13/13 on intent — notably a consumed-boundary
alternation:

```
(?:^|[^:/\w])docs/\S*\.md|(?:^|[^:/\w])issues/[0-9]{4}\.md
```

which is valid verbatim in **both** engines, so it keeps the pattern text
identical rather than diverging it.

**The decision itself still stands** — the criterion explicitly permitted
accepting, the false positive is nil today, and cost-versus-nil-risk carries it
on its own. But the comment blocks in both guards record a reason that will
mislead the next engineer, and their "the two guards must not diverge" premise
is *already false* per finding 1.

## Implementation notes

**Direction chosen: widen Go to match web, via an explicit shared character
class — not the "narrow both" or "blindly widen to `\p{White_Space}`"
options.** JavaScript's `\s` is Unicode-aware by spec (ECMA-262's
`WhiteSpace` + `LineTerminator` productions) regardless of the `u`/`v` flag
and was already the guard's live, correct coverage on the web half; narrowing
it to make the comparison easier would have deleted real coverage rather than
fixed a bug. So the fix widens Go's `PRD\s*§` term to an explicit class that
lists, by codepoint, every character JavaScript's `\s` matches:

```
[\t\n\v\f\r \x{00A0}\x{1680}\x{2000}-\x{200A}\x{2028}\x{2029}\x{202F}\x{205F}\x{3000}\x{FEFF}]
```

— tab, LF, VT, FF, CR, space, NBSP (U+00A0), Ogham space mark (U+1680), the
eleven general-punctuation spaces U+2000–U+200A (includes thin space
U+2009), line/paragraph separators U+2028/U+2029, narrow no-break space
(U+202F), medium mathematical space (U+205F), ideographic space (U+3000),
and ZWNBSP/BOM (U+FEFF) — 25 codepoints total, the complete ECMA-262 `\s`
set. Used the identical class, spelled with `\uXXXX` escapes (JS has no
`\x{...}` form), in the web pattern too, so both guards now assert the exact
same codepoint set rather than one deferring to `regexp/syntax`'s `\s` and
the other to V8's.

**Built by codepoint, verified by execution, not trusted from typing.**
While preparing this, I found that literal invisible/whitespace Unicode
characters I intended to paste into source did not reliably survive as
typed — most notably, typing the six-character ASCII sequence `\`+`u00A0`
in a tool-call parameter twice materialized as an actual NBSP byte instead
of staying as literal backslash-u-zero-zero-A-zero text (confirmed with
`python3 -c "print(open(...,'rb').read())"`, which showed UTF-8 bytes
`\xc2\xa0` where six ASCII characters were intended). Worked around it by
generating the backslash character at runtime from `chr(92)` (Python) /
`String.fromCharCode(92)` (the new web test) rather than typing `\` next to
`u`, and byte-verified every edited pattern line afterward with `python3`
decoding the file and printing the codepoint of every character above
U+007E. Both shipped pattern lines contain exactly one non-ASCII character
each (`§`, U+00A7) — every whitespace codepoint is a literal ASCII escape
sequence, reviewable in a diff.

**A related, unplanned discovery while writing the web-side test:** two of
the codepoints under test — LF (U+000A) and CR (U+000D) — are ECMA-262
`LineTerminator` characters that cannot appear raw and unescaped inside a
single-quoted string literal; embedding them directly in a fixture source
string (via `String.fromCodePoint`) made the *fixture* a syntax error, not
a test of the pattern (TypeScript's parser is error-tolerant, so this
surfaced as "0 matches" rather than a thrown parse error, and would have
been very easy to misread as the pattern being broken). Fixed by generating
a `\uXXXX` escape into the fixture source for every case uniformly (again
via `String.fromCharCode(92)`, not a typed `\`), which sidesteps the
restriction entirely since it applies only to raw characters, not escape
sequences.

**Comment corrections (finding 2).** Both guards' comment blocks above
`citationPattern` are rewritten to state the real reason for accepting the
`docs/*.md` external-URL false positive: it is nil in the tree today and
the cost of tightening is real against that nil risk — not, as previously
recorded, that only V8 could express a scheme exclusion because RE2 lacks
lookbehind. That premise was true on its own but the inference from it was
false (a scheme exclusion needs only a consumed leading boundary, not
lookbehind — `#0187`'s reviewer already proved a consumed-boundary form
valid verbatim in both RE2 and V8). Also dropped the "the two guards must
not diverge" justification, since finding 1 shows they already had. The
decision to accept the false positive itself is **unchanged**; only the
recorded reasoning changed. The consumed-boundary form was not adopted — see
"Reported, not filed" below.

**Not attempted:** `#0187`'s 34-case matrix was not re-run as a standalone
probe file (it was a throwaway review artifact, later deleted, per that
issue's own review notes). Instead its coverage is exercised through the
guard's existing committed tests
(`TestCitationScanExcludesCommentsAndAllowedCitations`,
`TestCitationScanCatchesDocCitation`, `TestCitationPatternIgnoresHexColors`,
`TestCitationPatternCatchesIssueFilePath`,
`TestCitationPatternAcceptsDocsURLFalsePositive`,
`TestNoAdminFacingStringCitesInternalDocs`), all of which still pass
unchanged, plus the new `TestCitationPatternMatchesWebWhitespaceShapes` /
`'fires on every whitespace shape...'` tests this pass adds.

### The central question: do the two patterns now mean the same thing? Yes — exactly.

Both `citationPattern`s were extracted **verbatim from the shipped files** by
substring search (not `splitlines()`, which splits on U+2028/U+2029 — two of
the codepoints under test) and re-run in their real engines: Go 1.26.3
`regexp` and Node v26.7.0 (V8).

Not a spot check — an **exhaustive sweep of the entire Unicode range**,
U+0000–U+10FFFF minus the surrogates, in three independent membership sets:

| Set | Size |
|---|---|
| Go's shipped class `[\t\n\v\f\r \x{00A0}…\x{FEFF}]` | **25** |
| Web's shipped class `[\t\n\v\f\r \u00A0…\uFEFF]` | **25** |
| V8's native `\s` (`/^\s$/`) | **25** |

`comm -23` and `comm -13` are **empty in every direction, for all three
pairings**. The three sets are literally the same 25 codepoints:

| | Codepoints | Go | web | native `\s` |
|---|---|---|---|---|
| ASCII | U+0009 TAB, U+000A LF, U+000B VT, U+000C FF, U+000D CR, U+0020 SP | ✔ | ✔ | ✔ |
| Latin-1 | U+00A0 NBSP | ✔ | ✔ | ✔ |
| Ogham | U+1680 OGHAM SPACE MARK | ✔ | ✔ | ✔ |
| General punctuation | U+2000–U+200A (11: en quad … hair space, incl. U+2009 thin space) | ✔ | ✔ | ✔ |
| Line terminators | U+2028 LS, U+2029 PS | ✔ | ✔ | ✔ |
| Narrow/medium | U+202F NNBSP, U+205F MMSP | ✔ | ✔ | ✔ |
| CJK | U+3000 IDEOGRAPHIC SPACE | ✔ | ✔ | ✔ |
| Specials | U+FEFF ZWNBSP/BOM | ✔ | ✔ | ✔ |

The same sweep proves the near-misses stay out, in all three sets — U+0085
NEL, U+00AD SOFT HYPHEN, U+180E MONGOLIAN VOWEL SEPARATOR (Zs before Unicode
6.3, Cf since — the one plausible drift), U+200B ZWSP, U+200C ZWNJ, U+200D
ZWJ, U+2060 WORD JOINER, U+2064, U+3164 HANGUL FILLER, U+FFFC, and an
ordinary `A`. `[\u2000-\u200A]` stopping one short of U+200B is correct and
is where a hand-written class would most easily have drifted.

**Does the class match ECMA-262 exactly? Yes — and this is the strong form of
the answer.** It was not compared against a transcription of the spec, which
could be wrong; it was compared against **V8's own `\s`, codepoint by
codepoint across all of Unicode**, and found identical. ECMA-262 `\s` is
`WhiteSpace` (TAB, VT, FF, SP, NBSP, ZWNBSP, and USP = category Zs) plus
`LineTerminator` (LF, CR, LS, PS); the 25 above are exactly that union. The
"nearly-JS's-`\s`" failure mode the brief warned about — two guards still
disagreeing on the edges while looking unified — **did not happen**.

**The web half is provably unchanged in behaviour.** Since the new web class
is byte-for-byte equivalent in effect to native `\s`, replacing `\s` with the
explicit class is a semantic no-op on that side. So the direction chosen —
widen Go, preserve web — is exactly what shipped, and it deleted no live
coverage. Judging the direction: **correct.** JS `\s` was the guard's real,
already-live coverage; narrowing it to make the two comparable would have
removed protection to make a review easier. Widening Go to the ECMA set is
the only choice that leaves both halves at the union rather than the
intersection.

**Term-by-term, nothing else moved.** Splitting both patterns on `|` at
`17cb886~1` and `17cb886`: 7 terms each side, **6 of 7 byte-identical**, the
`PRD…§` term the only change, in both files. So no other behaviour could have
shifted as a side effect.

### Byte evidence: the pattern lines hold escape *text*, not the characters

Read both files as raw bytes, decoded as UTF-8, located the pattern line by
substring search:

```
Go : b'var citationPattern = regexp.MustCompile(`CLAUDE\\.md|PRD[\\t\\n\\v\\f\\r \\x{00A0}…\\x{FEFF}]*\xc2\xa7|…`)'
web: b'const citationPattern = /CLAUDE\\.md|PRD[\\t\\n\\v\\f\\r \\u00A0…\\uFEFF]*\xc2\xa7|…/;'
```

Every character above U+007E on each pattern line: **exactly one, `§`
(U+00A7), at offset 151 (Go) / 114 (web)** — `\xc2\xa7` in the bytes. Every
whitespace codepoint is literal ASCII backslash-escape text, reviewable in a
diff. The §8 trap (a typed `\u00A0` landing as a real NBSP byte) did not
occur.

Stronger than the line-level claim: a **whole-file** non-ASCII census found
only `§` (U+00A7 ×19 Go / ×29 web) and `—` (U+2014 ×27 / ×30, prose in
comments). There is no stray invisible character anywhere in either file —
not in a comment, not in a fixture. `grep -P` was never used to reach any of
this (§8).
