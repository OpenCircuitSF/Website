## Description

`#0060` bounced because the published privacy policy promised something the
product does not do: it said erasure hard-deletes the subscriber record and
named **three** retained things, while `audit_log` also kept the email address
and the signup IP. The fix added a fourth item and its second review verified,
by grepping every text/varchar/jsonb/inet column of every base table, that the
text now matches reality exactly.

**But the only thing holding it true is prose.** A header comment above the
`StatusList` says "keep this in step with what erasure leaves" — which is
precisely the mechanism that was already in place when this bounced.

The next change to `erase.go`, to the audit metadata, or to any table erasure
touches will drift the policy again, silently, and the failure mode is a
**false public statement about personal data** rather than a failing test.

A small `web/` unit test over the erasure `StatusList` would turn that drift
into a failing test. `#0113` is the precedent: an index that three passes kept
re-deriving by hand became a guard, and it caught real drift within hours.

**Three smaller accuracy points from the same review**, all narrower-than-reality
rather than false:

1. **The policy names only the *signup* IP.** `audit_log.ip_address` is written
   on every subscriber-driven request — the confirming click, both unsubscribe
   paths, and preference updates. The review also noted this sits awkwardly
   beside the Consent section's "not a second IP address".
2. **The parenthetical omits bounce/complaint handling** as a purpose for the
   retained deliverability events, though item 3 already discloses the substance.
3. The `subscriber.erased` audit row carries the **admin's** IP, not the
   subscriber's — worth not implying otherwise.

## Implementation notes

**What the test compares against.** Went with the "committed list" option
the Notes weighed, strengthened past a bare fixture: `ERASURE_RETAINED_CATEGORIES`
in `web/src/views/PrivacyPolicy.guard.test.ts` is a fixed array of four
categories, each with a `sourceRef` string naming the exact
`internal/subscribers/erase.go` or `internal/handlers/admin_subscribers.go`
line its claim rests on (a citation a human, or `#0220`'s own path-citation
guard, can check against the tree — not read structurally by this test,
since Go source isn't reachable from this file's own AST walk the way the
Svelte side is) and a list of `requiredPhrases` that must ALL appear,
case-insensitive substring, in a single matching `StatusList` item. Rejected
the other two options the Notes named: reading `erase.go`'s own table
handling structurally would need a second AST-walking implementation just
for this one issue's sake (Go source, from a `.test.ts` file, with no
existing precedent for it anywhere in this tree), and a plain "must be
updated deliberately" fixture with no phrase-level check would pass under a
reworded item that silently dropped a real claim — exactly the failure mode
criterion 4 exists to name.

**Reading the policy structurally.** `findErasureStatusListItems` parses
`PrivacyPolicy.svelte` with `svelte/compiler`'s own `parse` (the same
technique `citationGuard.test.ts` and `modalFocusWiring
.structuralGuard.test.ts` already use), finds the `<section
aria-labelledby="leave-h">` ("How to leave" — scoped this way rather than
"the last `<StatusList>` in the file" or "the third one", both fragile to
an earlier list gaining or losing an item), asserts there is exactly one
`<StatusList>` inside it, and reads its `items` prop's `ArrayExpression`
elements directly off the AST — never `eval`'d, never a source-text regex.
`#0094`'s jsdom harness (mounting the component) was the other option the
Notes named; not used, since reading the prop off the parsed AST needs no
DOM and stays on the fast, non-jsdom default (`CLAUDE.md` §1).

**Matching, and why two mutation tests needed a second pass.** The first
version of the "drops the bounce/complaint-handling purpose" and "narrows
back to only signup IP" mutation tests asserted against
`matchItemToCategory`'s "closest category across all four" diagnostic —
which, for an item with exactly one missing phrase, picks whichever
category happens to be FIRST in the array when multiple categories are
tied at one missing phrase each (both mutated items ended up "closest" to
`suppression`, not to their own category, since removing one phrase from
the deliverability-events or audit-log item leaves it exactly as far from
`suppression`/`email_sends` as from its real category). Fixed by asserting
the specific category's own `requiredPhrases.filter(...)` directly in
those two tests, rather than trusting the general best-guess search meant
for the main test's human-readable diagnostic. This also caught two weak
phrase choices before they shipped: a bare `"bounce"` requirement was
already satisfied by the RETAINED-EVENT-TYPES clause ("bounces,
complaints, deliveries") even after the PURPOSE clause was deleted, and a
bare `"admin"` requirement was already satisfied by the OLD wording's
"internal admin audit log entry" (describing who reads it, not whose IP
the erasure row carries) — both replaced with the longer, actually-unique
phrases now in the file (`"bounce/complaint handling"`,
`"ip of the acting admin"`).

**The three prose accuracy fixes** (criteria 5–6), verified against the
real call sites before writing them:

- `audit.Entry{..., IP: clientIP(r)}` is set in
  `internal/handlers/subscribe.go:1108` (signup),
  `confirm.go:160` (confirming click), `unsubscribe.go:245` (one-click
  unsubscribe), and `preferences.go:257,319` (preference-center unsubscribe
  and a preference update) — every one of those, not only signup. The
  erasure entry itself, `admin_subscribers.go:983`'s `IP: clientIP(r)`,
  runs inside an admin-only handler where `r` is the ADMIN's request, so
  that one row's IP is the acting admin's, never the erased subscriber's.
- The Consent section's own "not a second IP address" claim (unedited) is
  about the `subscribers` table's own columns — it has exactly one,
  `signup_ip` — and stays true regardless of what `audit_log` does; the
  erasure item's new "a separate mechanism" clause makes that explicit so
  the two sections read as complementary, not contradictory, rather than
  editing the Consent section itself.
- The deliverability-events item already named the retained event TYPES
  (bounces, complaints, deliveries); it was missing bounce/complaint
  HANDLING as a stated purpose alongside "spam/abuse forensics" — added.

**`erase.go`'s own stale doc comment**, found while writing the guard's
`sourceRef` citations: its package doc comment still said "the three
things #0075's privacy policy already promises" — stale since #0060's own
Phase 3 bounce added a fourth (the audit log), months before this pass.
Corrected in passing (comment-only; no behavior change), and now cites
`web/src/views/PrivacyPolicy.guard.test.ts` by path — verified resolvable
by `#0220`'s own path-citation guard once that file existed.

**Status left at `in-progress`.** The guard mechanism is sound and worth

### The blocker: the rewrite dropped the email-address disclosure

`#0060` was bounced by its own review for a privacy policy that named three
retained categories when four were retained — specifically because
**`audit_log` keeps the subscriber's email address and IP after erasure** and
the page did not say so. `#0060`'s fix added the fourth item, whose text was:

> an internal admin audit log entry recording earlier actions on your account
> (signup, confirmation, and the erasure itself) — **this includes your email
> address and your signup IP address**, kept so we can prove a request was
> honored…

Commit `a7b0a5b` replaced it with:

> an internal admin audit log entry for each action on your account (signup,
> confirmation, any unsubscribe or preference update, and the erasure itself)
> — each entry records the IP address of the request that made it, a separate
> mechanism from the single consent-evidence IP described above; the erasure
> entry itself carries the IP of the acting admin, not yours — kept so we can
> prove a request was honored…

**"this includes your email address" is gone.** The IP disclosure was widened
and made more accurate; the email disclosure was deleted outright. Nothing
else in the "How to leave" section restores it — the lead paragraph
immediately above the list says erasure *"hard-deletes your subscriber record
— your email, interests, and signup details"*, so a reader now finishes the
section believing the only surviving copy of their address is the suppression
key.

That is false. Verified against the code, not against the notes:

- `internal/handlers/admin_subscribers.go:975` — the `subscriber.erased`
  audit entry is written with
  `Metadata: map[string]any{"email": result.Email, "previous_status": …}`.
  The erased address is written into `audit_log` **as part of the erasure
  itself**.
- `internal/handlers/confirm.go:159` — the confirmation entry carries
  `Metadata: map[string]any{"email": sub.Email}` too, and survives.
- `internal/subscribers/erase.go` never touches `audit_log` at all —
  `grep -n 'DELETE\|UPDATE\|INSERT'` over it shows the `UPDATE email_sends`,
  the suppressions insert and `DELETE FROM subscribers`, nothing else. There
  is no redaction pass anywhere.

(For completeness: `subscribe.go:1107`, `unsubscribe.go:244` and
`preferences.go:256,318` carry `kind`/`source`/`interest_count` metadata, not
the email — so "each entry" does not universally include it, but at least two
entries per erased subscriber do, one of them created by the erasure.)

**And the new guard codifies the weaker text.** `ERASURE_RETAINED_CATEGORIES`'
`audit_log` entry requires `['audit log', 'each entry records the ip address',
'ip of the acting admin']` — no phrase requires the email disclosure. So the
guard added to stop this exact drift now holds the drift in place, and the
next reviewer who runs it will get a green result over an under-disclosing
policy. This is the outcome the issue's own dispatch warned is worse than the
drift it fixes.

**What the next pass must do:**

1. Restore an explicit statement that the retained audit entries include the
   subscriber's **email address** — the erasure entry's own metadata does,
   `admin_subscribers.go:975`. Keep the corrected IP wording; it is right.
2. Add a `requiredPhrase` to the `audit_log` category covering it (something
   an editor cannot delete without failing, e.g. `'your email address'`), and
   add its `sourceRef` to `admin_subscribers.go`'s `"email": result.Email`
   metadata line.
3. Re-check the "each entry records the IP address of the request that made
   it" phrasing against the fact that only *some* entries carry the email —
   the page should not imply every entry carries both.
