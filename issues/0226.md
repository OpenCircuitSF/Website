## Description

`#0060` bounced because the published privacy policy promised something the
product does not do: it said erasure hard-deletes the subscriber record and
named **three** retained things, while `audit_log` also kept the email address
and the signup IP. The fix added a fourth item and its second review verified,
by grepping every text/varchar/jsonb/inet column of every base table, that the
text now matches reality exactly.

**But the only thing holding it true is prose.** A header comment above the
`StatusList` says "keep this in step with what erasure leaves" — which is
precisely the mechanism that was already in place when this bounced.

The next change to `erase.go`, to the audit metadata, or to any table erasure
touches will drift the policy again, silently, and the failure mode is a
**false public statement about personal data** rather than a failing test.

A small `web/` unit test over the erasure `StatusList` would turn that drift
into a failing test. `#0113` is the precedent: an index that three passes kept
re-deriving by hand became a guard, and it caught real drift within hours.

**Three smaller accuracy points from the same review**, all narrower-than-reality
rather than false:

1. **The policy names only the *signup* IP.** `audit_log.ip_address` is written
   on every subscriber-driven request — the confirming click, both unsubscribe
   paths, and preference updates. The review also noted this sits awkwardly
   beside the Consent section's "not a second IP address".
2. **The parenthetical omits bounce/complaint handling** as a purpose for the
   retained deliverability events, though item 3 already discloses the substance.
3. The `subscriber.erased` audit row carries the **admin's** IP, not the
   subscriber's — worth not implying otherwise.

## Acceptance criteria

- [ ] A test asserts the erasure `StatusList` enumerates exactly the categories erasure actually leaves
- [ ] Adding a fifth retained thing without updating the policy fails that test — demonstrated by mutation
- [ ] Removing a category that is still retained also fails it — over-promising deletion is the same defect in the other direction
- [ ] The test names what it checks in its failure message, so the next person meets the reason rather than a mismatch
- [ ] The policy describes `audit_log.ip_address` accurately — every subscriber-driven request, not only signup — and reads consistently with the Consent section
- [ ] The deliverability-events item names bounce/complaint handling among its purposes
- [ ] `#0060`'s three regression properties still hold: a complained address stays blocked, the subscribe 202 stays byte-uniform in body and headers, and `email_sends` rows survive with counts and statuses unchanged
- [ ] `scripts/check.sh web` and `ISSUE=0226 scripts/check.sh go ./internal/... ./cmd/...` both pass

## Notes

Reported by `#0060`'s second phase-3 review under `CLAUDE.md` §9, which named
criterion 1 as the item it would file first.

The hard part is deciding what the test compares against. Options worth weighing:
a committed list the erasure code and the policy both derive from; a test that
reads `erase.go`'s own table handling structurally; or a documented fixture that
must be updated deliberately when erasure changes. **The weakest acceptable
answer is a fixture** — but even that turns silent drift into a visible diff,
which is the whole point.

Note this is a *policy* correctness guard, not a data guard: it does not need a
database. `#0094`'s jsdom harness makes the `StatusList` mountable, and
`#0216`'s AST technique makes it readable structurally — either route works.

`#0060`'s two `## Review notes` sections carry the full grep census (address in
`audit_log.metadata` ×2 and `suppressions.email`; IP in `audit_log.ip_address`
×2) and are the ground truth for criterion 1.
