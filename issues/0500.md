# 0500 — `ObjectKey()`'s prefix fallback is dead against real SES, and its failure mode is a retry-to-exhaustion loop

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | inbound |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-10 |

## Description

`#0058`'s `SESEvent.ObjectKey()` reads `receipt.action.objectKey` and, when
that is absent, composes a key from `objectKeyPrefix + messageId`.

The primary path is correct: SES writes the **full, already-prefixed** key into
`objectKey`. The fallback is believed to be unreachable, because the S3 action's
notification payload carries no `objectKeyPrefix` field at all. It was written
defensively and its composition is correct for `#0057`'s configured prefix
`unsubscribe/` (trailing slash, so no double or missing separator).

So this issue is not a bug report. It is a **confirmation task with a sharp
edge**, deliberately deferred by `#0058`'s review until real SES traffic exists.

## The sharp edge

If `objectKey` ever arrived *without* the prefix — a shape change, or a
configuration where SES behaves differently than assumed — `Fetch` would 404.
`#0058` routes an S3 fetch error to a **500**, which is correct for a genuinely
retryable error, but a 404 is not retryable: SNS would redeliver on its policy
and the message would retry to exhaustion, then be dropped. The parked-object
backstop (`#0499`) would not catch it either, because the handler never reaches
the parked path.

That is a low-probability failure with a bad shape, which is exactly the kind
worth settling with one observation rather than more defensive code.

## Acceptance criteria

1. **Once `#0057`'s rule set is activated and the `lists.opencircuitsf.com` MX
   is published**, capture the first real notification and record its actual
   JSON shape in this issue — specifically whether `objectKey` is fully
   prefixed and whether `objectKeyPrefix` appears at all.
2. If the primary path is confirmed, **delete the fallback** and say so in
   `ObjectKey()`'s doc comment, rather than leaving unreachable code that
   implies a shape SES does not produce.
3. If the fallback turns out to be reachable, keep it and add a test built from
   the captured real payload.
4. Either way, reconsider whether an S3 `NoSuchKey` specifically should route to
   the parked path (200, object noted) rather than the retryable 500, since
   retrying a missing key cannot succeed.

## Observation — 2026-09-13 (criterion 1: not yet settleable)

Inbound is live (`#0057` steps 7–8; a real mailto unsubscribe was processed
2026-09-12 23:29:18 UTC — `audit_log` row 92: `subscriber.unsubscribed`,
`{"source": "mailto", "matched_via": "from"}` — matching the SNS SignatureVersion-1
verification log line for message `82e443c2-1d9a-5004-80c0-20ddff1443bd` on
`arn:aws:sns:us-east-1:…:opencircuit-inbound-mail`). But the raw notification's
JSON shape was **not recoverable from any oracle available on the box**. What
was checked, read-only:

1. **Service logs** — `sudo journalctl -u opencircuit --since 2026-09-10`,
   grepped for `objectKey|ses|notification` and separately
   `ses_inbound|mailto|unsubscribe|parked`. Only envelope-level lines exist:
   verification/auto-confirm WARN/INFO carrying `message_id` and `topic_arn`,
   plus an invalid-envelope probe. No payload JSON, no object key.
2. **Handler code** (`internal/handlers/ses_inbound.go`) — the handler logs
   only structured fields (`message_id`, `key`, `err`) and never the raw
   notification; the success path logs nothing at all, so even the processed
   unsubscribe left no key-shaped trace in journald.
3. **CloudWatch** — `aws` CLI exists on the box, but the instance role
   (name redacted per `#0511`; see the private AWS repo) is denied
   `logs:DescribeLogGroups`
   (AccessDeniedException), so no SNS/SES delivery-log group is reachable; none
   is configured by this project regardless.
4. **The audit row** — row 92's metadata holds only the match provenance above;
   no object key, no payload. (Even a recorded *derived* key could not settle
   this: the fallback composes `objectKeyPrefix + mail.messageId`, which is
   byte-identical to the key SES writes on the primary path when the configured
   prefix is `unsubscribe/` — output can't distinguish the two.)

**Blocker:** settling criterion 1 needs a live test email from an **external**
address (SES discards same-domain mail or routes it differently, so a
self-sent probe is not the oracle) sent while `sudo journalctl -f -u
opencircuit` runs on the box — and since the handler logs no payload, the
observation pass must also capture the envelope's inner `Message` JSON another
way; the cheapest is a temporary DEBUG log of the parsed receipt action, which
is a code change this observation deliberately did not make. The orchestrator
should coordinate that capture with the user. Nothing was sent, changed, or
waited on. No recipient addresses appeared in any checked oracle (message ids
and ARNs only), so nothing needed redacting.
