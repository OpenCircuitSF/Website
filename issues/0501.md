## Description

`#0058` processes a matched inbound unsubscribe by committing the unsubscribe
first and deleting the S3 object afterwards. If the delete fails, the object
remains and SNS may redeliver the notification. Replay then behaves differently
depending on which path matched:

- **Token path** — the unsubscribe rotated the manage token, so the token in the
  replayed message no longer resolves. The replay falls through to the `From:`
  fallback if the address matches, or to the parked path if it does not.
- **`From:` path** — the address still matches, so the replay unsubscribes an
  already-unsubscribed subscriber and writes a **duplicate audit row** with
  `source = 'mailto'`.

Neither outcome harms a subscriber: the end state is unsubscribed either way,
which is what they asked for. The cost is audit-log noise and a small amount of
confusion for anyone reading the trail later.

## Root cause

The handler commits the unsubscribe before deleting the S3 object — the
load-bearing ordering this issue itself judges correct, and the fix below does
not touch it. When the delete failed, the object remained and SNS redelivered
the same notification. On the `From:` path the replay matched again and wrote a
duplicate `subscriber.unsubscribed` audit row with `source = 'mailto'`. On the
token path a replay could only re-reach the match when the first delivery's
`RotateManageToken` had failed (a failed rotation is logged only, #0034's
recorded tradeoff), leaving the original token still resolvable; with a
successful rotation the replay parks at the stale-token rule instead, which was
never the duplicate-row case.

## Fix

The recorded decision (remedy 2): stamp the SES message id on the audit row and
treat a redelivered message id as a no-op at the audit layer.

- `migrations/000029_add_audit_log_message_id` — new up/down pair (nothing
  existing was edited): a nullable `audit_log.message_id TEXT` plus a partial
  index (`WHERE message_id IS NOT NULL`) that serves exactly the idempotency
  lookup.
- `internal/audit` — `Entry.MessageID` (empty maps to SQL NULL, same convention
  as IP), written by `insert`; `Logger.MessageProcessed(action, messageID)` is
  the EXISTS lookup, scoped to action + message id; `Record.MessageID` read
  back through `ListAuditLog` and surfaced as `message_id` in the admin audit
  JSON, so the trail's join key back to the inbound message is actually
  visible.
- `internal/handlers/ses_inbound.go` — `handleNotification` threads
  `ev.Mail.MessageID` (out of the already-parsed event payload, not re-derived)
  into `handleMatch`, which now runs the redelivery check BEFORE anything
  else: a seen id skips `Unsubscribe`, `RotateManageToken`, and the audit row
  entirely, leaving only the object delete to run again — the second chance
  the failed delete needed. A nil auditor or an empty id falls back to the
  pre-#0501 behavior unchanged; a failed check is failed-open (logged, then the
  ordinary path), so the check can never block or retry a real unsubscribe.
  The unsubscribe audit row now carries `MessageID`.
- `docs/database.md` and `CLAUDE.md`'s migration-range sentence updated per
  #0082's parity guard, which fails otherwise.

## Why it is filed rather than fixed

The ordering is right as built. Committing the unsubscribe before the delete is
the correct precedence — a lost delete leaves a duplicate audit row, whereas
deleting first and then failing to commit would lose the request entirely. The
current failure mode is the benign one of the two, and `#0058`'s review
explicitly judged it low harm.

It is filed so the duplicate-row shape is a known, deliberate consequence
rather than a surprise to whoever next reads the audit trail and finds two
identical `mailto` rows seconds apart.

## Suggested remedies, if it proves worth closing

1. **Make the unsubscribe idempotent at the audit layer** — skip the audit row
   when the subscriber is already unsubscribed and the source and window match.
2. **Record the SES message id** on the audit row and treat a repeat as a
   no-op, which also gives the trail a join key back to the S3 object.
3. **Leave it**, and document the shape in `docs/` so the duplicate is
   legible rather than alarming.

Option 2 is the most useful independently of this issue, since it links audit
rows to inbound messages generally.

## Decision (recorded 2026-09-13 — user's call, made via the orchestrator)

**Remedy 2 — record the SES message id on the audit row**, and treat a
redelivered message id as a no-op at the audit layer (option 1's idempotency
falls out of it). The commit-before-delete ordering is untouched (criterion 2).
This also gives the trail the join key back to the S3 object the issue calls
the most useful outcome independently. Tests cover redelivery on both the
token path and the `From:` path (criterion 3).

## Acceptance criteria

1. Decide among the three and record the reasoning — an unexamined answer is
   not acceptable, either of the others is.
2. If a fix lands, it must not reorder the commit and the delete. That ordering
   is load-bearing and its reversal is the genuinely lossy direction.
3. A test covers redelivery of an already-processed message on both the token
   path and the `From:` path.
