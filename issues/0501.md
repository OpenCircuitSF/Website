# 0501 — A `Delete` failure after a committed unsubscribe is mildly lossy, in two different ways

| | |
|---|---|
| **Status** | open |
| **Platform** | Server |
| **Module** | inbound |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-09-10 |

## Description

`#0058` processes a matched inbound unsubscribe by committing the unsubscribe
first and deleting the S3 object afterwards. If the delete fails, the object
remains and SNS may redeliver the notification. Replay then behaves differently
depending on which path matched:

- **Token path** — the unsubscribe rotated the manage token, so the token in the
  replayed message no longer resolves. The replay falls through to the `From:`
  fallback if the address matches, or to the parked path if it does not.
- **`From:` path** — the address still matches, so the replay unsubscribes an
  already-unsubscribed subscriber and writes a **duplicate audit row** with
  `source = 'mailto'`.

Neither outcome harms a subscriber: the end state is unsubscribed either way,
which is what they asked for. The cost is audit-log noise and a small amount of
confusion for anyone reading the trail later.

## Why it is filed rather than fixed

The ordering is right as built. Committing the unsubscribe before the delete is
the correct precedence — a lost delete leaves a duplicate audit row, whereas
deleting first and then failing to commit would lose the request entirely. The
current failure mode is the benign one of the two, and `#0058`'s review
explicitly judged it low harm.

It is filed so the duplicate-row shape is a known, deliberate consequence
rather than a surprise to whoever next reads the audit trail and finds two
identical `mailto` rows seconds apart.

## Suggested remedies, if it proves worth closing

1. **Make the unsubscribe idempotent at the audit layer** — skip the audit row
   when the subscriber is already unsubscribed and the source and window match.
2. **Record the SES message id** on the audit row and treat a repeat as a
   no-op, which also gives the trail a join key back to the S3 object.
3. **Leave it**, and document the shape in `docs/` so the duplicate is
   legible rather than alarming.

Option 2 is the most useful independently of this issue, since it links audit
rows to inbound messages generally.

## Acceptance criteria

1. Decide among the three and record the reasoning — an unexamined answer is
   not acceptable, either of the others is.
2. If a fix lands, it must not reorder the commit and the delete. That ordering
   is load-bearing and its reversal is the genuinely lossy direction.
3. A test covers redelivery of an already-processed message on both the token
   path and the `From:` path.
