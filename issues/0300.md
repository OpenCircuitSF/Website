## Description

`#0275` closed the empty-roots fail-open: all five `internal/handlers` guards
now assert they parsed a plausible number of files, and `#0275`'s review
verified every floor catches a real narrowing.

| Guard family | Parsed population | Floor | Largest single package |
|---|---|---|---|
| `citedTestScanRoots` × 3 | 255 (all `.go`) | 150 | 96 |
| `TestNoAdminFacingStringCitesInternalDocs` | 111 (non-test) | 80 | 40 |
| `TestAuditEntryEmailMetadataMatchesKnownSites` | 110 (non-test) | 80 | 40 |

**But the floors themselves are ordinary constants in the files they guard.**
Setting `citedTestScanRootsMinPlausibleFileCount`, `citationGuardMinPlausibleFileCount`,
or `auditEmailMetadataMinPlausibleFileCount` to `0` leaves the whole package
green.

`TestGoFileVisitCountGuardFiresOnEmptyOrLowCount` does not close this, and
deliberately so: it uses its own literals (`0`, `3`, `150`) rather than reading a
guard's constant, which is what makes it oracle-independent under CLAUDE.md §8.
It proves the *mechanism* fires. It cannot pin a *value*.

This is exactly §8's "a guard inside the file it guards becomes new mutable
surface", and §8 also names the remedy.

## The remedy is external, and explicitly not a seventh in-file check

`#0258` spent six passes hardening `scripts/check.sh`'s self-checks against
decoys added to `scripts/check.sh`, and by pass six the newest mechanism was
itself the target. The lesson recorded in §8 is that **adding another in-file
check buys another bounce**, and that the project already has the right shape:
`scripts/db_reset_guard_test.sh` and its siblings mutate a *copy* of the thing
under test and assert its exit code and output **from outside**, wired into
`scripts/check.sh guards`.

An external harness cannot be disarmed by editing its subject.

## Acceptance criteria

1. A shell guard of the `scripts/*_guard_test.sh` shape copies the guard files,
   sets each floor constant to `0` in the copy, runs the affected tests, and
   asserts the run **still fails**. One mutation per floor, each named.
2. It also asserts the committed values **pass** against the real tree, so the
   harness fails if a floor is raised above its population — the failure mode
   that forced `#0275` to lower 150 to 80.
3. It recomputes each floor's population **from outside Go** — the parsed
   population, not the walked one (`#0275` criterion 4a) — and fails if a
   committed floor is not below it by a sensible margin. State the margin and
   why.
4. Registered in `scripts/check.sh guards`, not in the default `go`/`web`/`all`
   scopes. Follow the precedent: `dev_guard_test.sh` alone costs ~48s, which is
   why that separate target exists.
5. **Not a seventh in-file check.** If you find yourself adding a Go test in
   `internal/handlers` that reads a floor constant, stop — that is the shape
   `#0258` proved does not work.
6. `bash -n` and `shellcheck` both pass, and the script runs under **bash
   3.2.57** — CLAUDE.md §8 records that `${var,,}` and other bash-4 syntax fails
   *silently* here, and that `bash -n` and `shellcheck` both pass on it. Use
   `tr` for case folding as `scripts/testdb.sh` does.
7. `scripts/check.sh guards` passes, and the existing four guard scripts still do.

### The central argument is correct, and is hereby settled

The implementer's claim that `go test` can never be the oracle for a
floor-only mutation was checked against the source rather than accepted.
`internal/handlers/dangling_test_citation_guard_test.go:319`'s
`goFileVisitCountImplausible` has exactly two branches: `len(roots) == 0`
(independent of `floor`) and `got < floor`. `got` is `walkGoFiles`' visited
counter or `scanAuditEntrySites`' `len(files)` — both non-negative integers
— so with `floor` forced to `0` the second branch is unreachable and the
first is unaffected. A mutated-to-zero floor therefore leaves
`internal/handlers` green, which is a restatement of this issue's own bug
report rather than a disproof of it.

**Do not re-litigate this.** A future pass that "fixes" the harness by
adding a `go test` exit-code assertion against a floor-only mutation would
be asserting something true regardless of the floor's value — CLAUDE.md
§8's "a copy of the answer stored next to the question is not a check", in
its purest form. Criterion 1's literal wording ("runs the affected tests,
and asserts the run **still fails**") is unsatisfiable as written and is
superseded by what was built: the mutation still happens on a copy on disk,
and the value judged is still re-extracted from those bytes through the
identical `extract_const()` pipeline that judged the real one — only the
*judge* is bash rather than Go. That preserves criterion 1's substance.

### Does the harness itself fail open? No — five break-cases, all exit 1

This was the first thing tested, since it is `#0275`'s own lesson turned on
its author. Each case was a copy of the script placed at `scripts/` depth
(so `REPO` still resolved), mutated, and run under `/bin/bash`:

| Break | Observed | Exit |
|---|---|---|
| A — `FLOOR_ROOTS` set to three nonexistent dirs | population `0`; all three committed floors judged **NOT plausible**; 3 FAILs | **1** |
| B — `FLOOR_ROOTS` set to empty strings | `ABS_ROOTS[@]: unbound variable` (bash 3.2 + `set -u`), then `FATAL: count_go_files returned a non-numeric population ('')` | **1** |
| C — roots pointing at a real but empty directory (population `0`, no `find` stderr to give it away) | 3 FAILs, no silent pass | **1** |
| D — roots narrowed to `cmd` only (population 3/18) — i.e. **`floor > population`, `#0275`'s actual failure mode** | all three FAIL naming the floor and the population | **1** |
| E — a `FLOOR_NAMES` entry that matches nothing | `FATAL: extract_const: no 'const … = <int>' line found … Refusing to guess`, then a second fatal on the mutation check | **1** |

A population of `0` cannot produce a pass: `floor_plausible` requires
`floor > 0` **and** `floor <= population`, so any real floor against a zero
population fails the upper bound. The zero-mutation half of each pair does
"pass" under a zero population (0 is correctly implausible), but the
committed-floor half fails, and `FAILURES` is a single counter for the whole
run — so the script exits 1. **The harness fails closed on a zero or broken
population.** Confirmed by execution, not by reading.

Also verified: `count_go_files`' `grep -vc` on empty input yields `0` and
does not abort the assignment under `pipefail`; the numeric `case
*[!0-9]*)` screen on `POP` catches the empty string; and the script is
path-independent (run from `/`, from a sibling directory, and via a relative
path — identical results, 0.11s each), because `REPO` is resolved to an
absolute `pwd` inside a subshell before anything else, and the main shell
never `cd`s. That is CLAUDE.md §8's "resolve an absolute path *before*
changing directory", done correctly.

### The `population/2` margin — justified, and stronger than the stated reason

Criterion 3 asked for a margin **and why**. The header's stated reason ("a
floor of 5 out of 258 offers only token protection") argues for *a* lower
bound but not for one-half specifically. The number nevertheless earns its
place, for a reason worth recording because it is the load-bearing one:

**Half the population exceeds the largest single package in all three
cases.** Largest package today: `internal/handlers` at **97** all-`.go`
files and **40** non-test. Half the populations are **129**, **55**, **55**.
So any floor that satisfies `floor >= population/2` *necessarily* trips on a
narrowing of the scan roots to the single largest package — the "a real
narrowing would trip it" bar `#0275` criterion 3 set. That is work
`floor <= population` alone cannot do: a floor of 97, or 40, would clear
"greater than zero" and clear the upper bound while being useless against
the most plausible narrowing. Tested: `FLOOR_ROOTS` narrowed to `cmd`
(case D above) fires, and by inspection a floor lowered to 97 against a
population of 258 fails the half-margin.

Both directions fire. `floor > population` — `#0275`'s own failure mode,
the one that forced 150 down to 80 — was reproduced in case D and reported
with the population named.

**Recorded caveat, not a defect:** the margin has a growth ceiling. A floor
of 150 fails once the population reaches 302 (44 files of headroom from
today's 258); the two 80-floors fail at 162 (≈51 files of headroom). That is
arguably the desired behaviour — a floor that has fallen to half the tree
*should* be re-examined — and the failure is loud rather than silent. But
the FAIL message lists only "lowered too far, raised above the real
population, or the tree shrank", omitting **the tree grew**, which will be
the actual cause when this first fires. Whoever next touches this script
should add that fourth cause to the message; it is a one-line change and not
worth a bounce on its own.

### Two robustness notes for whoever touches this next

Neither is a fail-open and neither blocks resolution; both are recorded so
they are not rediscovered.

1. **`fatal` does not abort when called from inside a command
   substitution.** `extract_const` is invoked as `$(extract_const …)`, so
   its `exit 1` ends the subshell only; the main shell continues with an
   empty value. Case E showed the consequence: the true `FATAL` line prints
   first (good), then a stray `[: : integer expression expected` from
   `floor_plausible`, then a FAIL with a wrong diagnosis. The run still
   exits 1 — `floor_plausible`'s `[ … ] || return 1` on each comparison
   makes an empty operand fail closed — so the header's "fails closed" claim
   is true in outcome, but its parenthetical "(fatal)" overstates the
   mechanism.
2. **`shasum` and `awk` are not in the `command -v` preflight** that covers
   `find`, `grep`, and `sed`. If `shasum` were absent, `SHA_BEFORE` and
   `SHA_AFTER` would both be empty, compare equal, and the byte-identity
   check would print PASS having measured nothing — the same "agrees with
   itself" shape §8 warns about, in the integrity check rather than the
   oracle. Low risk (`shasum` is macOS base), but the two names belong in
   that preflight list.

### On the regress §8 names

This harness is itself a mutable file with no oracle above it, so it does
not escape §8's regress in principle. It escapes the part that matters:
**an edit to the subject cannot disarm it.** Disabling the floors now
requires editing `internal/handlers` *and* `scripts/go_file_visit_floor_guard_test.sh`
*and* leaves `scripts/check.sh guards` as the place that notices. That is
the same stopping point `db_reset_guard_test.sh` and its siblings already
occupy, and it is the right one.
