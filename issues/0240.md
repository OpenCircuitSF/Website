## Description

Two places where prose describes a tighter rule than anything actually checks.
Both are the same failure: a **convention** written down as though it were an
**enforcement**, so a reader trusts a guarantee that does not exist.

**1. `cover_image` is not restricted to `/assets/`.** `#0138` and `#0153` both
say cover images must be a same-origin path *(`/assets/…`)*. `isSafeCoverImage`
— `internal/handlers/admin_workshops.go:691` and its TypeScript twin — actually
accepts **any** absolute same-origin path: it requires a leading `/`, rejects
`//` (protocol-relative), and rejects control characters. The `/assets/` prefix
is convention only.

That matters because `#0153`'s decision to ship no upload endpoint rests partly
on the field being tightly constrained. It is constrained enough to stop the
attack `#0138` was about — protocol-relative and off-origin URLs — but an admin
can point it at any path on the site, and a reader of either issue would not
know that.

**2. `#0062`'s one-line `## Description` still reads "Nightly `pg_dump` to S3
with a proven restore."** S3 was decided against in `#0229`: what ships is a
local dump plus an `rsync` pull to an offsite Mac mini. The body of `#0062` was
corrected; its summary line was not — and the summary line is what tooling and
issue listings surface. This has now been re-confirmed twice by two separate
reviews, each leaving it alone because `#0062` is resolved.

It is precisely the belief `#0229` exists to stop people holding.

## Implementation notes

**Decision on criterion 1 — fix the wording, don't tighten the validator —
and why.** `isSafeCoverImage`'s actual threat model (both
`internal/handlers/admin_workshops.go` and its TypeScript twin,
`web/src/lib/workshopAdmin.ts`) is "no off-site load": require a leading
`/`, then reject `//`/backslash-normalized-`//` so it can't resolve
off-origin, plus reject control characters (the `\t`/`\n`/`\r` browser-URL-
parsing hazard `#0138` closed). A same-origin path outside `/assets/`
carries **none** of the risk that threat model exists to close — it's still
served by this origin, still same-site, still not a referer leak to a third
party. Restricting the validator to an `/assets/` prefix would trade a
real, useful convention (where cover images conventionally live) for an
arbitrary rejection with no security benefit, and no acceptance criterion
anywhere (`#0138`, `#0153`, `#0052`) ever asked for a path-prefix
enforcement — only same-origin. Tightening the code would also be a
behavior change on a **resolved** issue's shipped validator with no bug
report behind it, which is a bigger, riskier move than correcting two
sentences of prose. So: wording fixed, validator unchanged.

- **`#0138`.** Checked closely and found **already accurate** — its `## Fix`
  section states the rule as "requires a leading `/`, then rejects a
  leading `//`", never claims an `/assets/` restriction. The two places it
  mentions `/assets/` both quote `PRD.md` §6.2's own schema comment
  (`cover_image TEXT, -- path under /assets`) verbatim as supporting
  rationale for "belongs on this site", not as a description of what the
  validator checks. No edit needed; recorded here so the review doesn't
  have to re-derive that conclusion.
- **`#0153`.** This is where the actual inaccuracy lives — its `##
  Description` and `## Decision` both said cover images "must be a
  same-origin path (`/assets/…`)", which its own phase-3 review had
  already flagged (2026-08-24) as overstating the constraint, without
  fixing it. Corrected both sections in `issues/0153.md` to state what
  `isSafeCoverImage` actually enforces (a leading `/`, no `//`, no control
  characters; `/assets/…` noted as convention, not an enforced prefix), and
  added a note next to the original review-notes paragraph marking it
  corrected, with a pointer to this issue. `#0153` is `resolved`; its
  **Status** is unchanged — this is a text-only correction, logged in its
  own `## Work log`, per criterion 4.
- **`#0062`.** Its `## Description` still read "Nightly `pg_dump` to S3
  with a proven restore" — accurate to the original plan, wrong since
  `#0229`'s `## Decision` chose local `pg_dump` + offsite `rsync` to a Mac
  mini instead (no AWS account exists; deferred to deployment per
  `CLAUDE.md` §10). Rewrote the summary line to describe the shipped
  design and added a correction blockquote explaining what changed and why
  **Status** stays `resolved`. Logged in `#0062`'s own `## Work log`, per
  criterion 4.

No code changed for this issue — both fixes are documentation-only, by
decision (see above for `cover_image`; `#0062`'s summary line was never
code to begin with).
