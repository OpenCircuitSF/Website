## Description

`#0082` added `internal/db/docs_parity_test.go`, asserting every `migrations/*.up.sql` has a row in `docs/database.md` and that the stated range matches. It works — its mutation fires on both assertions independently.

But `#0082`'s reviewer probed the guard rather than reading it, and found **four drift modes it does not catch**. Each was proved by experiment, not inferred.

## What it misses

1. **A doc row for a deleted migration.** Moving `000009` off disk while leaving its row left the suite green. The check runs only one way — file → doc, never doc → file.
2. **Numbering gaps.** Both documents claim a *contiguous* range; nothing enforces contiguity, so `000009` vanishing between `000008` and `000010` passes.
3. **An `.up.sql` with no `.down.sql`.** `listMigrations` globs `*.up.sql` only. An up-only `000012` with a doc row passed green — and a migration with no down is a real operational hazard, not a documentation one.
4. **A row inside a fenced code block.** The check is `strings.Contains` over the whole file, with no notion of a table row.

> 🟢 Resolved 2026-08-19 — `internal/db/docs_parity_test.go` is now bidirectional, contiguity-aware, down-file-aware and row-structure-aware, and covers `CLAUDE.md` in the *same* table-driven test rather than a sibling, and the reviewer re-created all four mutations independently and got byte-for-byte the reported output: a `000012_ghost_migration` row with no file on disk fires the reverse check alone; moving `000009`'s files off disk *and* deleting its doc row in one step fires contiguity alone (`expected version 000009 at position 8 … but found 000010`), and re-running the *combined* mutation with the doc row restored fires the reverse check **and** contiguity together, proving the isolation is genuine and neither assertion is masking the other; removing only `000009_create_interests.down.sql` fires the down-pair check alone; and moving the `000008` row into a ```` ```text ```` fence fires the forward check while the fenced mention trips nothing — the row-structure fix is real. That fix was attacked at the boundary rather than taken on trust: ordinary prose, a bullet list, a blockquoted row and a single-line HTML-commented row are all correctly **rejected** (a bullet list not satisfying the check was the bar, and it clears it), while tight pipes `|`x`|y|` and alignment-colon rows are correctly **accepted**, as are a nested table inside a list item and a table inside `<details>`; three narrow residual false-positives remain and are recorded as follow-ups rather than blockers — a pipe-leading line inside a 4-space **indented** code block, inside a **multi-line** HTML comment, and inside a `~~~` **tilde** fence all still satisfy the check, since `docTableRowLines` only toggles on ```` ``` ````. It is genuinely one test and not two wearing one name: `checkRows` gates only the per-migration row checks, which are inapplicable to `CLAUDE.md` by construction — flipping it to `true` fails with *“missing a table row for 11 migration(s)”*, confirming `checkRows: false` is the right setting — while the file read, the `docTableRowLines`/`docStemToken` parsing, the en-dash-tolerant `docRangePattern` and the range comparison are shared verbatim across both files, which is precisely the part that drifted twice in `CLAUDE.md`. The loosened `(?:numbered|contiguous)` alternation matches both files' current wording (`docs/database.md` line 4 “numbered”, `CLAUDE.md` line 37 “contiguous”), and mutating each file's range independently fails loudly and names the file to edit; re-wording `contiguous`→`sequential` `t.Fatalf`s with an actionable message rather than passing vacuously. One gap found there and left as a follow-up: only the range's **upper** bound is asserted — `rangeMatch[1]` is captured and echoed but never compared, so a stale `` `000003`–`000011` `` passes green in both files. Contiguity's edges hold: a single `000001` is silent, an empty `migrations/` `t.Fatalf`s loudly instead of passing vacuously, a duplicated version is caught, and the `000001`-start assumption is deliberate (it is what both documents claim) though it does mean a legitimately retired migration would require renumbering — proved by renaming `000001`→`000012`, which fails at position 0. The guard is filesystem-only: `os`/`regexp`/`sort`/`strconv`/`strings`/`testing` and nothing else, green with `TEST_DATABASE_URL` **unset**, and independent of `testdb.Lock()`, which is a no-op in that case. On placement the conclusion is right for this change and the reasoning is slightly overstated — `internal/db` is the correct semantic home (it owns migrations) and the lock is an artifact of the package's one DB test, but a lock-free `internal/db/docsparity` subpackage was in-lane this pass, so “every viable target was off limits” is not quite accurate; it remains a fair non-blocking follow-up. `go build ./...` and `go vet ./...` are clean, `go test ./internal/db/... -count=1` is green with `TEST_DATABASE_URL` both set and unset, `c366ec1` touches exactly one file, and `migrations/` and `docs/database.md` are byte-identical to `HEAD` with no throwaway migration left behind.

## Also: cover `CLAUDE.md`

`CLAUDE.md`'s migration-range statement has now drifted **twice** and was corrected by hand both times — the fourth drift of this class overall, across the second file.

`#0082`'s reviewer was explicit about the shape: **one table-driven test over both files, not a sibling test.** The two differ only in wording (`numbered` versus `contiguous`) and in whether rows are enumerated — a two-field table (`{path, checkRows}`) with the range pattern loosened to `(?:numbered|contiguous)`. A sibling would duplicate the parsing and en-dash handling and become a thing that can itself drift out of step with its twin.

## Acceptance criteria

- [x] The guard asserts the **reverse** direction: a doc row naming a migration that does not exist on disk fails
- [x] Contiguity is asserted, since both documents claim it
- [x] Every `*.up.sql` has a matching `*.down.sql`
- [x] `CLAUDE.md`'s range is covered by the **same** table-driven test, not a second one
- [x] Each of the four drift modes is **mutation-proven**: create the condition, watch the specific assertion fail, revert, report the output
- [x] Failure messages name the offending migration and the file to edit
- [x] Still filesystem-only — no database, no `TEST_DATABASE_URL`
- [x] `go build ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported and zero skips

## Notes

Items 1 and 2 are what would have caught a deleted migration; item 3 catches a class of defect the docs cannot express at all.

Non-blocking placement note from the same review: the test lives in `internal/db`, so when `TEST_DATABASE_URL` *is* set it queues behind that package's shared advisory lock — it needs no database but waits with packages that do. Moving it to a package without that lock would make it faster; weigh it.

## Fix

`internal/db/docs_parity_test.go` (extended, not replaced):

- **Drift mode 1 (reverse direction)** — new `docStemToken` regex
  (`` `(\d{6}_[a-z0-9_]+)` ``) plus `verifyDocRowsHaveMigration`: walks every
  backtick-wrapped `NNNNNN_name` token found in a doc's table-row lines and
  asserts a matching `migrations/NNNNNN_name.up.sql` exists on disk. Runs
  per-file, gated by `checkRows` (see below).
- **Drift mode 2 (contiguity)** — new `verifyContiguous`: walks
  `listMigrations`' sorted stems and asserts version `i` sits at position
  `i-1` (0-indexed), i.e. the sequence is exactly `000001..NNNNNN` with no
  gaps or duplicates. Disk-only; runs once, not per doc.
- **Drift mode 3 (missing down file)** — new `verifyDownPairs`: for every
  `*.up.sql` stem, `os.Stat`s the sibling `*.down.sql` and fails naming the
  migration if absent. Disk-only; runs once, not per doc.
- **Drift mode 4 (row-structure)** — new `docTableRowLines`: splits a doc on
  newlines, toggles an `inFence` flag on lines whose trimmed form starts with
  ` ``` `, and keeps only non-fenced lines whose trimmed form starts with
  `|`. Both the forward check (already present from `#0082`, now tightened)
  and the new reverse check search only these lines — `strings.Contains`
  over the whole file is gone. A migration token in a fenced block or in
  ordinary prose no longer satisfies either direction.
- **`CLAUDE.md` coverage, same table** — `docParityCase{path, checkRows}`
  drives a single `t.Run` loop over `docsPath` (`checkRows: true` —
  `docs/database.md` enumerates a row per migration) and `claudeMDPath`
  (`checkRows: false` — `CLAUDE.md`'s "Repository layout" table states only
  the aggregate range, no per-migration rows). `docRangePattern` is loosened
  to `` (?:numbered|contiguous) `(\d{6})`[–-]`(\d{6})` `` so the same regex
  matches both files' wording. No sibling test was added.
- Failure messages name the offending migration stem and the file to edit,
  per the acceptance criterion (see the mutation outputs below).
- Still filesystem-only: no `pgx`, no `TEST_DATABASE_URL`, no network or
  database access anywhere in the file.

### Placement decision (non-blocking note from `#0082`'s review)

**Kept in `internal/db`; not moved.** `internal/db`'s `TestMain` acquires
`internal/testdb`'s shared advisory lock for the package's whole run, so this
filesystem-only test does queue behind every DB-backed test in the package
when `TEST_DATABASE_URL` is set, even though it opens no connection itself —
the review's observation is correct. But every other package that could host
it *without* paying that same tax is also gated by the identical lock via its
own `TestMain` (`internal/audit`, `internal/middleware`, `internal/interests`,
`internal/subscribers` all call `testdb.Lock()`), and the packages that
plausibly hold no lock at all — `internal/handlers`, `internal/mailing`,
`internal/auth` — are exactly the packages this issue's concurrency
instructions placed off limits this pass, with other subagents' uncommitted
work in flight there right now. Standing up a new, lock-free package purely
to host this one test is a bigger structural move than "make the guard
bidirectional" calls for, and would itself be a collision risk against that
concurrent work. Revisit if a future issue frees up a natural, lock-free home
for it.

## Gotchas

- **Isolating each mutation to one assertion took care.** The obvious
  mutation for drift mode 2 (move `000009` off disk, leave its doc row) also
  trips drift mode 1's reverse check, since it's the identical experiment
  `#0082`'s reviewer described. Removing the doc row *in the same step* as
  the disk files was what isolated contiguity alone — worth keeping in mind
  if a future reviewer re-runs "the" `000009` mutation and gets two failures
  instead of one; that is expected of the *combined* mutation, not evidence
  either check is redundant.
- **Placement**: see the dedicated section under "Fix" above — kept in
  `internal/db` deliberately, not because moving it was infeasible in
  principle, but because every viable target this pass was either equally
  locked or off-limits per the concurrency instructions.
