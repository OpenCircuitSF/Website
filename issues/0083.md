## Description

`#0082` added `internal/db/docs_parity_test.go`, asserting every `migrations/*.up.sql` has a row in `docs/database.md` and that the stated range matches. It works — its mutation fires on both assertions independently.

But `#0082`'s reviewer probed the guard rather than reading it, and found **four drift modes it does not catch**. Each was proved by experiment, not inferred.

## What it misses

1. **A doc row for a deleted migration.** Moving `000009` off disk while leaving its row left the suite green. The check runs only one way — file → doc, never doc → file.
2. **Numbering gaps.** Both documents claim a *contiguous* range; nothing enforces contiguity, so `000009` vanishing between `000008` and `000010` passes.
3. **An `.up.sql` with no `.down.sql`.** `listMigrations` globs `*.up.sql` only. An up-only `000012` with a doc row passed green — and a migration with no down is a real operational hazard, not a documentation one.
4. **A row inside a fenced code block.** The check is `strings.Contains` over the whole file, with no notion of a table row.

## Also: cover `CLAUDE.md`

`CLAUDE.md`'s migration-range statement has now drifted **twice** and was corrected by hand both times — the fourth drift of this class overall, across the second file.

`#0082`'s reviewer was explicit about the shape: **one table-driven test over both files, not a sibling test.** The two differ only in wording (`numbered` versus `contiguous`) and in whether rows are enumerated — a two-field table (`{path, checkRows}`) with the range pattern loosened to `(?:numbered|contiguous)`. A sibling would duplicate the parsing and en-dash handling and become a thing that can itself drift out of step with its twin.

## Acceptance criteria

- [ ] The guard asserts the **reverse** direction: a doc row naming a migration that does not exist on disk fails
- [ ] Contiguity is asserted, since both documents claim it
- [ ] Every `*.up.sql` has a matching `*.down.sql`
- [ ] `CLAUDE.md`'s range is covered by the **same** table-driven test, not a second one
- [ ] Each of the four drift modes is **mutation-proven**: create the condition, watch the specific assertion fail, revert, report the output
- [ ] Failure messages name the offending migration and the file to edit
- [ ] Still filesystem-only — no database, no `TEST_DATABASE_URL`
- [ ] `go build ./...`, `go test ./... -count=1` green with `TEST_DATABASE_URL` exported and zero skips

## Notes

Items 1 and 2 are what would have caught a deleted migration; item 3 catches a class of defect the docs cannot express at all.

Non-blocking placement note from the same review: the test lives in `internal/db`, so when `TEST_DATABASE_URL` *is* set it queues behind that package's shared advisory lock — it needs no database but waits with packages that do. Moving it to a package without that lock would make it faster; weigh it.
