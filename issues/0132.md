# 0132 — `resetSettings` hardcodes the migration seed a second time, so the next seeded setting silently disappears

| | |
|---|---|
| **Status** | open |

| **Platform** | All |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-08-22 |

## Description

`#0130` fixed `resetSettings` (`internal/handlers/settings_test.go`) by adding the two rows it was dropping, which makes its six re-inserts a second, hand-maintained copy of what `migrations/000004`, `000008`, `000015`, and `000018` seed. It opens with an unqualified `DELETE FROM settings` and then re-inserts that fixed list, so **any setting a future migration seeds is destroyed by every `internal/handlers` run and never restored.**

That is exactly the defect `#0130` just fixed, with the same signature: harmless while nothing asserts the seeded value, invisible until a test in a different package fails for a reason nobody would look for in `internal/handlers`.

## Acceptance criteria

- [ ] `resetSettings` no longer hardcodes the seed list — it either deletes only the keys the test itself introduced, or restores `settings` from a source of truth (the template database, or the migrations) rather than a literal
- [ ] Adding a seventh seeded setting to a new migration requires no edit to `resetSettings`, and a test proves that: seed a row outside the known six, run the package, and assert it survives
- [ ] `internal/handlers` still passes under `-shuffle` on two fresh seeds
- [ ] A direct query after a full package run still shows `settings` matching the migration seed exactly

## Notes

Found by `#0130`'s phase-3 review, which noted it after confirming the `#0130` fix itself is correct. The reviewer's framing: the fix is right, but it makes the duplication structural rather than accidental, and the structural repair is design work beyond `#0130`'s scope.

Worth knowing from that review: `resetSettings` is the **only** bulk delete of `settings` in the tree. The sole other runtime delete is `setSetting`'s own cleanup, which removes a key only when it found that key absent on entry. So this one function is the entire blast radius.

Filed as Phase 7 rather than Phase 5 because it is latent test-infrastructure hygiene of the same class as `#0094`, `#0097`, and `#0098`, and nothing in Phase 5 depends on it.
