## Description

`#0130` fixed `resetSettings` (`internal/handlers/settings_test.go`) by adding the two rows it was dropping, which makes its six re-inserts a second, hand-maintained copy of what `migrations/000004`, `000008`, `000015`, and `000018` seed. It opens with an unqualified `DELETE FROM settings` and then re-inserts that fixed list, so **any setting a future migration seeds is destroyed by every `internal/handlers` run and never restored.**

That is exactly the defect `#0130` just fixed, with the same signature: harmless while nothing asserts the seeded value, invisible until a test in a different package fails for a reason nobody would look for in `internal/handlers`.

## Acceptance criteria

- [x] `resetSettings` no longer hardcodes the seed list — it either deletes only the keys the test itself introduced, or restores `settings` from a source of truth (the template database, or the migrations) rather than a literal
- [x] Adding a seventh seeded setting to a new migration requires no edit to `resetSettings`, and a test proves that: seed a row outside the known six, run the package, and assert it survives
- [x] `internal/handlers` still passes under `-shuffle` on two fresh seeds
- [x] A direct query after a full package run still shows `settings` matching the migration seed exactly

## Notes

Found by `#0130`'s phase-3 review, which noted it after confirming the `#0130` fix itself is correct. The reviewer's framing: the fix is right, but it makes the duplication structural rather than accidental, and the structural repair is design work beyond `#0130`'s scope.

Worth knowing from that review: `resetSettings` is the **only** bulk delete of `settings` in the tree. The sole other runtime delete is `setSetting`'s own cleanup, which removes a key only when it found that key absent on entry. So this one function is the entire blast radius.

Filed as Phase 7 rather than Phase 5 because it is latent test-infrastructure hygiene of the same class as `#0094`, `#0097`, and `#0098`, and nothing in Phase 5 depends on it.

## Implementation notes

**Facts established first, by demonstration, before changing anything.**

- Canonical seed: `migrations/000004_create_settings.up.sql`
  (`registrations_enabled`), `000008_add_physical_address_setting.up.sql`
  (`physical_address`), `000015_seed_soft_bounce_settings.up.sql`
  (`soft_bounce_threshold_count`, `soft_bounce_threshold_window_days`),
  `000018_add_campaign_send_state.up.sql` (`max_send_rate`,
  `default_from_name`) — all `INSERT INTO settings ... ON CONFLICT DO
  NOTHING`. Confirmed the six literal rows `resetSettings` restated matched
  these six exactly, today, byte-for-byte against a freshly-templated
  database (`shasum -a 256` of `SELECT key, value FROM settings ORDER BY
  key` matched `opencircuit_test_template`).
- Demonstrated what happens to an unlisted setting: seeded a 7th row
  (`zz_future_setting`) directly into a private database
  (`opencircuit_test_0132`), then ran a `settingsTestPool`-backed test
  (`TestAdminSettings_NonAdminForbidden`) under the **pre-fix**
  `resetSettings`. The row was gone afterward — `DELETE FROM settings`
  removed it and the six-item literal re-seed never mentioned it. It
  vanishes silently; nothing errors, nothing warns. Exactly the defect
  class the issue describes.

**Fix shape chosen: derive from the same source the migration uses (issue's
first, most durable option), implemented as "re-run the migration's seed"
rather than "read the current live table."**

`resetSettings` now clears `settings` and replays every `INSERT INTO
settings ...;` statement `settingsSeedStatements` extracts (via a
line-anchored regex) from `migrations/*.up.sql`, verbatim — the real SQL the
migrations execute, not a Go-side paraphrase of it. A new migration that
seeds a settings row via the same idiom needs no matching edit here.

**A first attempt was rejected after it failed the full-suite check.** It
snapshotted the live `settings` table once, from `TestMain`, before any test
in the package could mutate it, and had `resetSettings` replay that snapshot
instead of a literal list. That passed every `internal/handlers`-scoped run,
including two `-shuffle=on` runs on fresh seeds — but failed under `ISSUE=0132
scripts/check.sh go ./internal/...` (the full package tree), with
`registrations_enabled` observed as `"true"` where tests expected the seeded
`"false"`. Root cause: `internal/auth`'s `registration_test.go` writes
`registrations_enabled` via its own `setRegistrationsEnabled` helper and never
restores it, and every DB-backed package under `go test ./internal/...`
shares one physical `TEST_DATABASE_URL` (packages serialize against each
other via `internal/testdb`'s advisory lock, but the *data* they leave behind
persists across that handoff). `internal/auth`'s test binary runs before
`internal/handlers`'s, so the live-snapshot approach captured that pollution
as if it were the canonical seed. The pre-#0132 hardcoded implementation
never had this problem because it forced literal values regardless of
whatever the table already held. Reading the seed from the migration files on
disk sidesteps the whole class of problem — nothing another package's tests
do to the live table can affect it.

### The parser, probed against shapes it was not designed for

`settingsSeedStmtRe` is `(?ims)^INSERT INTO settings\b.*?;`. Probed by running
the exact expression over sixteen realistic inputs. Result, with reachability
judged against what `migrations/` actually contains today (all 20 files use
`--` comments only, no `/* */` anywhere, every `INSERT` at column 0, every
statement `;`-terminated):

| Input shape | Matches? | Consequence | Reachable? |
|---|---|---|---|
| Multi-line `VALUES\n (…),\n (…);` | ✅ whole statement | correct — `(?s)` spans the newlines | yes, and handled |
| `-- INSERT INTO settings …;` (col 0) | ❌ | correctly ignored | yes, and handled |
| `  -- INSERT INTO settings …;` (indented) | ❌ | correctly ignored | yes, and handled |
| `insert into settings …;` (lowercase) | ✅ | correct — `(?i)` | yes, and handled |
| `INSERT INTO settings_history …;` | ❌ | correct — `\b` blocks the prefix collision | yes, and handled |
| `UPDATE settings SET …;` | ❌ | **never replayed** | yes, and handled |
| `DELETE FROM settings WHERE …;` | ❌ | **never replayed — reset cannot replay a delete** | yes, and handled |
| `INSERT INTO settings … SELECT …;` | ✅ whole statement | correct | yes, and handled |
| `INSERT` inside `/* … */` | ✅ | **silent false positive** — inserts a phantom row (verified: `INSERT 0 1`) | no `/* */` exists in `migrations/`; would also have to survive a `.up.sql` review |
| `';'` inside a string literal | ✅ **truncated** | **loud** — `ERROR: unterminated quoted string` → `t.Fatalf` | hypothetical; verified loud |
| `$$a;b$$` dollar-quoted | ✅ truncated | loud, same way | hypothetical |
| trailing `-- note; here` before the `;` | ✅ truncated | loud, same way | hypothetical |
| `INSERT  INTO   settings` (extra internal ws) | ❌ | silent false negative | hypothetical |
| `    INSERT INTO settings …;` (indented stmt) | ❌ | silent false negative | none today; all 20 migrations start `INSERT` at column 0 |
| `INSERT INTO public.settings …;` | ❌ | silent false negative | none today; no migration schema-qualifies |
| no trailing `;` at EOF | ❌ | silent false negative | none; `golang-migrate` files terminate statements |

**Verdict: tight enough.** The asymmetry runs the right way. Every false
positive that mangles a statement is **loud** — the truncated match is invalid
SQL, `pool.Exec` errors, and `resetSettings` calls `t.Fatalf` naming the
statement. The one *silent* false positive (an `INSERT` buried in a `/* */`
block) requires a comment style that appears nowhere in `migrations/`. The
silent false negatives all require a formatting of `INSERT INTO settings` that
no migration uses and that a reviewer of the new migration would have to wave
through.

The one gap worth naming: a later migration that changed a seeded **default**
via `UPDATE settings SET value=…` would not be replayed, so `resetSettings`
would restore the original `INSERT`'s value rather than the current one. That
shape is discouraged here anyway — CLAUDE.md §1's greenfield rule says edit the
migration that owns the table rather than stack a second one, and an edited
`INSERT` *is* picked up. It is also not a regression: the pre-`#0132`
hardcoded list had the same gap plus every gap this fix closes.

Two decisions in the extractor are right and worth recording: restricting to
`*.up.sql` keeps the four `DELETE FROM settings` statements in the `.down.sql`
files out (belt and braces — the regex would not match them either), and
`sort.Strings` on zero-padded six-digit filenames reproduces real migration
order, so `ON CONFLICT DO NOTHING` resolves a duplicate key the same way a real
migration run would.

### Both halves proved by execution

**The original defect, reproduced against the pre-fix code.** Checked out
`a1da390^` into a throwaway worktree, seeded a 7th row
(`zz_rev_future_setting='present'`) into my database, and ran
`TestAdminSettings_NonAdminForbidden` there. The test **passed**, and the row
was gone afterward — six rows left, no error, no warning. That is the issue's
"silently disappears", observed.

**The fix, proved in the form that matters.** A hand-inserted row absent from
`migrations/` is still dropped post-fix, which is correct: the contract is
"restore what the migrations seed", not "preserve whatever the table held" —
and that is precisely what makes it immune to the pollution below. So the real
criterion-2 proof is a *migration* that seeds a 7th key. Ran that: copied all
20 real migrations plus a `000021_seventh_setting.up.sql` into a temp dir,
pointed `settingsMigrationsDir` at it, called `resetSettings` — 7 rows,
`zz_rev_seventh='survives'`, with zero edits to `resetSettings`. Criterion 2
holds in the strong form, not just the fixture form.

**The fixture isolation is real, and I checked rather than assumed it.** As
written, `TestResetSettings_PreservesFutureMigrationSeed` asserts only that its
key is present — which would also pass if `resetSettings` were reading the real
`migrations/` *as well as* the fixture. Probed it directly: with
`settingsMigrationsDir` pointed at the fixture dir, `settings` holds **exactly
one row**, the fixture key, and none of the six real seeds. `os.ReadDir` reads
only the directory it is given; the isolation is genuine.

One latent constraint the mechanism depends on: `settingsMigrationsDir` is a
package-level `var` swapped in place, which is safe only because
`internal/handlers` contains **zero** `t.Parallel()` calls (verified). If a
settings test ever gains `t.Parallel()`, a concurrent `resetSettings` would
reseed the table from the fixture and wipe the real six mid-test.

### Cross-package pollution — still present; I disagree with leaving it unreported

Confirmed by execution, not by reading. `internal/auth/registration_test.go`
calls its `setRegistrationsEnabled` helper seven times (six of them with
`true`) and the file contains **no `t.Cleanup` at all**. Set
`registrations_enabled='false'`, ran `go test ./internal/auth/`, queried again:
`true`. The implementer's root-cause account of why its first, live-snapshot
attempt died under the full suite is accurate.

`#0130` does not cover this. Its title mentions a `registrations_enabled` leak,
but the leak it fixed was `TestAudit_SettingsUpdated`'s, in `internal/handlers`
— `internal/auth`'s is a second, distinct leak of the same key, untouched.

Blast radius today is nil: the only other DB-backed test reader of the key is
`internal/handlers/audit_seams_test.go`, which `#0130` gave its own
`t.Cleanup(resetSettings)`, and `settingsTestPool` now reseeds from the
migrations on entry regardless of what the table held. So this is correctly
**out of `#0132`'s scope** and is not grounds to bounce.

But "harmless today" is exactly the description in this issue's own
`## Description` of the defect it exists to fix, and this one has already cost
a full implementation pass — it is what killed the live-snapshot approach after
that approach had passed every scoped run *and* two `-shuffle=on` runs. It is
also load-bearing for criterion 4 in a way nobody chose: `settings` matches the
template after `go test ./internal/...` only because `internal/handlers` happens
to run after `internal/auth` and cleans up on the way out. Under CLAUDE.md §9 a
subagent reports rather than files, and this one recorded it in
`## Implementation notes` but did not surface it for filing. Reported to the
orchestrator for a ticket.
