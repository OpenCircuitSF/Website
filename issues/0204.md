## Description

`#0197` added a structural AST guard coupling `CampaignSendDialog.svelte`'s
three gates to what `CampaignSendDialog.guard.test.ts` claims they are. Its
phase-3 review confirmed it is genuinely structural — renaming the component's
derived variable and the helpers' parameter both leave it green — and that it
catches a *reclassification* (`!sending` → `sending`), not merely degradation to
`other`. Three items came out of that review.

**1. The fourth test's failure message is not pasteable.** Three of the four
assertions in `CampaignSendDialog.structuralGuard.test.ts` carry a `detail`
string naming the file and the expression. The fourth uses three bare
`expect(…varName).toBe(sendingVar)` calls with no message, so it fails as
`expected undefined to be 'sending'` — no file, no expression, nothing to search
for. `#0187` established for the other guard that a failure message exists to be
pasted into a search; this is the same requirement, unmet in one of four places.

**2. A weaker check was available for the declined criterion 4, and is worth
having.** `#0197` correctly declined to guard `#0186`'s `oldSending` /
`oldBlockedAgain` formulas: they snapshot pre-`#0186` behaviour that no longer
exists in the tree, so there is nothing to assert agreement with. The review
verified that premise rather than accepting it — `CampaignSendDialog.svelte`
derives nothing from `inFlight` or `unmet.length` directly any more; both route
through `sendGuardState`.

But that premise is exactly what the before/after block rests on, and nothing
pins it. Assert the **negative**: no local in the component is derived directly
from `inFlight` or `unmet.length > 0`. If that ever stops being true, the
old-formula block silently stops describing anything.

**3. The `#0184`/`#0189` form of the replica trap remains undefended, and this
guard cannot close it.** Recorded so nobody believes the class is shut.

`#0197`'s guard classifies a single identifier as `identity` / `negation` /
`other`. It cannot express a regex character class or compare a helper's *body*
to a real function's — so a fourth hand-rolled `normalizeCountInput` copy would
be exactly as invisible tomorrow as it was in `#0189`.

The working answer to that form is not a guard at all: it is `#0189`'s own fix —
**import and call the real function**, which `CampaignSendDialog.guard.test.ts`
now does. Generalising `#0197`'s mechanism to compare function bodies should be
considered only where a test genuinely cannot call the real thing.

## Notes

Reported by `#0197`'s phase-3 review under `CLAUDE.md` §9.

Item 3 is the one worth reading twice. `#0197` closes the *mirror* form of the
replica trap — a test restating a one-token expression from the component. It
does not close the *re-implementation* form, where a test rewrites a function's
logic and can therefore disagree with it. Four instances of this trap are on
record (`#0184`, `#0189`, `#0195`, and `#0197` itself as the fix); two were the
form that is now guarded, two were the form that is not.

`#0197`'s `## Review notes` carries the rename probes and both mutation results
— that is the regression suite for criterion 5.

## Implementation notes

All three items land in
`web/src/views/admin/CampaignSendDialog.structuralGuard.test.ts`; no other
file changed.

**Item 1 — pasteable failure message on the fourth test.** The three bare
`expect(classifySvelteGate(...).varName).toBe(sendingVar)` calls in "all
three gates are anchored to the same `$derived(...)` variable" now each carry
a `detail` string built the same way `assertGateMatchesHelper` already does:
the label, the file, the real expression found and its classification, and
the shared anchor `sendingVar` was resolved to. Verified by mutation, not
assumed: backed up `CampaignSendDialog.svelte` (`cp`, sha256
`2906c0cc7224eac5cb53e21f132f3613bd0751d06af9c2bbf9297d5e4251ac9c`), changed
line 178 from `disabled={sending}` to `disabled={blockedAgain}`, ran the file
alone: **2 failed / 2 passed (4)**. The fourth test's failure, verbatim:

```
AssertionError: count-input disabled (shared-anchor check): web/src/views/admin/CampaignSendDialog.svelte has `blockedAgain` (classified 'identity', of `blockedAgain`), but the shared anchor found by findSendingVarName is `sending` — this gate is not bound to the same $derived variable as the others (see #0195, #0197, #0204): expected 'blockedAgain' to be 'sending'
```

Names the file, the real expression, its classification, and the expected
anchor — pasteable into a search, unlike the prior `expected undefined to be
'sending'`. Restored from the backup; `shasum -a 256` matched before and
after.

**Item 2 — pinning the `#0186` premise.** Added
`isDirectInFlightOrUnmetExpr` (true when an expression is, at its top level
and optionally negated by one `!`, exactly `inFlight` or exactly
`unmet.length > 0`) and `findDirectInFlightOrUnmetLocal`, which searches
every `$derived(...)`-bound local in the component's instance script for one
whose top-level argument matches that shape. Deliberately narrow: it does
**not** flag the real `$derived(sendGuardState({ ..., inFlight }))` (that
argument is a `CallExpression`, not an `Identifier`/`BinaryExpression`), only
a local whose value comes directly from one of the two raw formulas
`oldSending`/`oldBlockedAgain` in `CampaignSendDialog.guard.test.ts` encode.
The new test throws a message naming the file, the offending local's name,
and its `$derived(...)` expression when found; passes silently (no offender)
otherwise.

Proved by mutation, per the issue's own example. Backed up the (already
item-1-modified) `CampaignSendDialog.svelte` (sha256 as above, unchanged by
item 1), inserted `let somethingPending = $derived(inFlight);` on the line
after the `sending` declarator (line 72), ran the structural guard file
alone: **1 failed / 4 passed (5)** — isolated to only the new test, the other
four (including the item-1 fix) stayed green. Failure, verbatim:

```
Error: web/src/views/admin/CampaignSendDialog.svelte: `somethingPending` is `$derived(inFlight)` — a local derived directly from `inFlight` or `unmet.length > 0` again, bypassing sendGuardState. CampaignSendDialog.guard.test.ts's oldSending/oldBlockedAgain before/after block compares against these two raw formulas as dead code that nothing in the component matches any more; if a live local like this exists, that comparison needs to target it instead (see #0186, #0197, #0204)
```

Restored from the backup; `shasum -a 256` matched
(`2906c0cc7224eac5cb53e21f132f3613bd0751d06af9c2bbf9297d5e4251ac9c`) before
and after.

**Item 3 — the doc comment.** Extended the file's header comment (no code
change) to name the re-implementation form explicitly: this guard's
`identity`/`negation`/`other` vocabulary over a single identifier cannot
compare a test helper's *body* to a real function's body, so a fourth
hand-rolled `normalizeCountInput` copy elsewhere would be exactly as
invisible as it was in `#0189`. States the working answer — delete the
replica, import and call the real function, the way
`CampaignSendDialog.guard.test.ts` now calls `normalizeCountInput` directly
— and says explicitly not to treat this file as having closed that form.
