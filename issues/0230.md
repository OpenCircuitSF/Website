## Description

`#0218` added `sedPatternUnsafeConstruct`, which refuses a `CLAUDE.md` §11
Extract cell containing a BRE construct that cannot be translated faithfully to
RE2. Its phase-3 review measured twelve constructs on **both** sides — real BSD
sed against a crafted corpus, and the translated regex compiled and matched
against the same corpus — and passed it. Three latent defects came out of that,
all in one function.

**1. It decides "escaped" by looking at one preceding rune, not parity.**
`runes[i-1] == '\\'` means a metacharacter preceded by an **even** number of
backslashes (≥2) is wrongly treated as escaped, so `a\\{b` and `a\\+b`
mistranslate **silently** — BSD sed reads a literal `a\{b`, RE2 reads an
interval.

The sharp part: **the correct parity scan already exists five lines away.** The
same pass fixed exactly this reasoning in `parseSedRangeCmd`, where the review
confirmed all six odd/even cases behave correctly. The logic simply was not
carried into the lint.

**2. A mid-pattern `^` or `$` slips through.** `a^b` and `a$b` are literals in
BRE; in RE2 they are anchors, so the translated pattern matches nothing and an
END pattern would silently under-count. (A *trailing* `$` is an anchor in both
and is fine.)

**3. `[{]` and `[+]` are over-rejected.** Inside a bracket expression these are
literal in both dialects, but the lint sees a bare metacharacter. This fails
**safe** — a loud refusal on a legitimate pattern — so it is the least urgent of
the three.

**Nothing in the 48 current rows reaches any of them**, and no heading anchor
plausibly would. This is about the next row somebody writes.

**A documentation nit from the same review**, worth folding in: the doc comment
says the lint "rejects **any** Extract cell containing a construct it cannot
translate faithfully". That is true only as bounded by the list immediately
following it. The apposition does bound it — so this is not the false-prose
class this repo has bounced on twice — but one sentence naming what the lint
does *not* catch would make the boundary explicit rather than inferred.

## Acceptance criteria

## Implementation notes

All changes are in `internal/db/prd_section_index_test.go`.

**Criterion 1 — shared parity scan.** Factored `parseSedRangeCmd`'s existing
backslash-counting loop into `oddPrecedingBackslashes(s string, i int) bool`:
counts the run of `'\\'` bytes immediately before index `i`; an odd count
means `i` is escaped (the last backslash in the run pairs with it and has no
partner), an even count (including zero) means it isn't. Both
`parseSedRangeCmd` and `sedPatternUnsafeConstruct` now call it instead of
each doing its own (and, in `sedPatternUnsafeConstruct`'s case, wrong)
one-byte-lookback check. `sedPatternUnsafeConstruct` was also switched from
rune iteration to byte iteration (`for i := 0; i < len(pat); i++`) so its
index lines up directly with `oddPrecedingBackslashes`'s byte-based scan — a
backslash is single-byte in UTF-8 and never a continuation byte of a
multi-byte rune, so this doesn't change behavior for anything the 48 real
rows contain (plain ASCII).

**Criterion 2 — parity replaces one-byte lookback.**
`escaped := oddPrecedingBackslashes(pat, i)` replaces
`escaped := i > 0 && runes[i-1] == '\\'`. `a\\{b` (two backslashes before
`{`, even) and `a\\+b` (two backslashes before `+`, even) are now correctly
seen as unescaped and rejected; `a\{b` (one backslash, odd) still correctly
passes as a genuine, translatable BRE interval.

**Criterion 3 — mid-pattern `^`/`$`.** Added two `case` arms:

```go
case '^':
	if !escaped && i != 0 {
		return "a mid-pattern `^` (...)", false
	}
case '$':
	if !escaped && i != len(pat)-1 {
		return "a mid-pattern `$` (...)", false
	}
```

An unescaped `^` anywhere but position 0, or an unescaped `$` anywhere but
the last byte, is rejected. A leading `^` and a trailing `$` are anchors in
both dialects (agreement) and are not flagged, matching every one of the 48
current rows (all begin with `^`, none contain `$`). An *escaped* `\^`/`\$`
is also left alone — both dialects read the escaped form as a literal, so
there's no divergence to guard against there.

**Criterion 4 — `[{]`/`[+]` over-rejection recorded as deliberate, not
fixed.** `sedPatternUnsafeConstruct` has no bracket-expression state machine
and none was added — teaching it to recognize `[...]` correctly (including
`[^]abc]`, `[]abc]`, POSIX classes, etc.) is real parser work for a case none
of the 48 rows use, in exchange for closing a fail-*safe* gap (a loud
refusal on a pattern that would actually translate fine). Documented in both
the function's own doc comment and the file's top-of-file doc comment, per
the issue's explicit alternative.

**Criterion 6 — doc comment states what the lint does not catch.** Added a
sentence to both the file-level doc comment (near the top) and
`sedPatternUnsafeConstruct`'s own doc comment naming the bracket-expression
gap explicitly, rather than leaving it inferable only from the code.

**New test:** `TestSedPatternUnsafeConstruct`, table-driven with `cases`
subtests split into `unsafe` (must be rejected) and `safe` (must pass), one
case per divergence in the issue plus the two over-rejection cases from
criterion 4, plus a representative real row (`` ^### 4\.2  ``) confirming the
ordinary case still passes.

## Notes

Reported by `#0218`'s phase-3 review under `CLAUDE.md` §9.

Criterion 1 is the one that removes the class. Two functions in one file
disagreeing about what "escaped" means is precisely the shape that produced the
original `#0113` defect and then `#0218` itself — the third instance in the same
file.

Worth reading from that review before starting, because it is measurement rather
than assertion: `\+`, `\?`, `\|` are **literal** on BSD sed (unlike GNU) and
literal-unrewritten in RE2, so `#0218`'s decision to allow them is provably
safe — verified both by a corpus match and by running a real 586-line extraction
through both paths. Do not "fix" that allowance.

Also confirmed there: all 48 START patterns match `PRD.md` exactly once, and
`mayRestart` is genuinely provokable (widening §1's START to `/^## /` makes real
sed print 401 lines against a stated 41, and the guard names the row).
