## Description

`#0218` added `sedPatternUnsafeConstruct`, which refuses a `CLAUDE.md` §11
Extract cell containing a BRE construct that cannot be translated faithfully to
RE2. Its phase-3 review measured twelve constructs on **both** sides — real BSD
sed against a crafted corpus, and the translated regex compiled and matched
against the same corpus — and passed it. Three latent defects came out of that,
all in one function.

**1. It decides "escaped" by looking at one preceding rune, not parity.**
`runes[i-1] == '\\'` means a metacharacter preceded by an **even** number of
backslashes (≥2) is wrongly treated as escaped, so `a\\{b` and `a\\+b`
mistranslate **silently** — BSD sed reads a literal `a\{b`, RE2 reads an
interval.

The sharp part: **the correct parity scan already exists five lines away.** The
same pass fixed exactly this reasoning in `parseSedRangeCmd`, where the review
confirmed all six odd/even cases behave correctly. The logic simply was not
carried into the lint.

**2. A mid-pattern `^` or `$` slips through.** `a^b` and `a$b` are literals in
BRE; in RE2 they are anchors, so the translated pattern matches nothing and an
END pattern would silently under-count. (A *trailing* `$` is an anchor in both
and is fine.)

**3. `[{]` and `[+]` are over-rejected.** Inside a bracket expression these are
literal in both dialects, but the lint sees a bare metacharacter. This fails
**safe** — a loud refusal on a legitimate pattern — so it is the least urgent of
the three.

**Nothing in the 48 current rows reaches any of them**, and no heading anchor
plausibly would. This is about the next row somebody writes.

**A documentation nit from the same review**, worth folding in: the doc comment
says the lint "rejects **any** Extract cell containing a construct it cannot
translate faithfully". That is true only as bounded by the list immediately
following it. The apposition does bound it — so this is not the false-prose
class this repo has bounced on twice — but one sentence naming what the lint
does *not* catch would make the boundary explicit rather than inferred.

## Acceptance criteria

- [ ] `sedPatternUnsafeConstruct` counts backslash **parity**, reusing the scan `parseSedRangeCmd` already implements rather than a second copy
- [ ] `a\\{b` and `a\\+b` are rejected — demonstrated by mutation, since they pass silently today
- [ ] A mid-pattern `^` or `$` is rejected, while a trailing `$` still passes
- [ ] `[{]` and `[+]` are accepted, or the over-rejection is recorded as a deliberate fail-safe
- [ ] All 48 current rows still pass, and `#0218`'s two mutations still fail naming row and construct
- [ ] The doc comment states what the lint does not catch
- [ ] `ISSUE=0230 scripts/check.sh go ./internal/...` passes with zero skips

## Notes

Reported by `#0218`'s phase-3 review under `CLAUDE.md` §9.

Criterion 1 is the one that removes the class. Two functions in one file
disagreeing about what "escaped" means is precisely the shape that produced the
original `#0113` defect and then `#0218` itself — the third instance in the same
file.

Worth reading from that review before starting, because it is measurement rather
than assertion: `\+`, `\?`, `\|` are **literal** on BSD sed (unlike GNU) and
literal-unrewritten in RE2, so `#0218`'s decision to allow them is provably
safe — verified both by a corpus match and by running a real 586-line extraction
through both paths. Do not "fix" that allowance.

Also confirmed there: all 48 START patterns match `PRD.md` exactly once, and
`mayRestart` is genuinely provokable (widening §1's START to `/^## /` makes real
sed print 401 lines against a stated 41, and the guard names the row).
