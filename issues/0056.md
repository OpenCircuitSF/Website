## Description

One action on a workshop that creates a draft campaign pre-filled from it — subject, body, and interest targeting.

## Acceptance criteria

- [x] `POST /admin/workshops/{id}/announce` creates a `draft` campaign linked via `workshop_id`
- [x] Subject and body pre-filled from the workshop title, summary, date, and location
- [x] Campaign targeting pre-set to the workshop's interests in `any_of` mode
- [x] The draft is fully editable before sending — nothing is sent by this action
- [x] The workshop screen links to the created draft
- [x] Repeated announce calls create a new draft rather than overwriting an existing one
- [x] Handler tests cover pre-fill content and the campaign/workshop link

## Notes

PRD §8. This action must never send. It is a compose shortcut; the send still goes through #0047's full guard sequence including the test send and typed count confirmation.

Creating a second draft on a repeat call is intentional — a follow-up reminder is a normal thing to send, and silently overwriting a partly-edited draft would lose work.

## Root cause

Not a bug — a new feature. Before this change, `AdminWorkshopsHandler` had
no way to create a campaign at all: `internal/mailing.CampaignInput` had no
`WorkshopID` field, and `CampaignStore.Create`'s `INSERT` never wrote
`email_campaigns.workshop_id`, so nothing in the codebase could produce the
FK link migration 000020 added for exactly this purpose.

## Fix

- `internal/mailing/campaigns.go`: added `CampaignInput.WorkshopID *int64`
  and threaded it into `Create`'s `INSERT` (`workshop_id` column). Every
  other caller of `Create` is unaffected (`nil` by default).
- `internal/handlers/admin_workshops.go`: added `announceCampaignStore`
  (a narrow `Create(ctx, mailing.CampaignInput) (mailing.Campaign, error)`
  seam — `*mailing.CampaignStore` satisfies it) and a `campaigns` field +
  constructor argument on `AdminWorkshopsHandler`.
- `internal/handlers/admin_workshop_announce.go` (new): `Announce` — a
  method on `*AdminWorkshopsHandler`, not a separate handler type (see that
  file's package doc comment for why: it lets the route mount with zero
  signature changes to `adminRoutes`/`mountAndServe`, only one new line
  inside `adminRoutes`' existing `if adminWorkshopsH != nil` block).
  Builds the pre-filled `Name`/`Subject`/`BodyMD` from the workshop's
  title/summary/start+end time/location/signup URL, sets
  `AudienceMode: any_of` + the workshop's `InterestIDs`, falling back to
  `AudienceAll` with no interest ids when the workshop has none (a
  workshop is not required to carry interests, and `any_of` with zero ids
  is refused store-side by `mailing.ErrCampaignInterestsRequired` — see
  that file's doc comment for why "fall back to all" beats surfacing that
  as an error from a one-click action). Always calls `Create` — never
  checks for an existing linked draft — so repeat calls produce separate
  drafts by construction. Writes an `email_campaign.created` audit entry
  (same action/target type `POST /admin/campaigns` uses) with
  `workshop_id`/`workshop_slug`/`via: "announce"` in the metadata.
- `cmd/opencircuit/main.go`: `campaignsStore` construction moved earlier
  so `adminWorkshopsH` can take it as a constructor argument (the same
  instance `adminCampaignsH` uses further down); one new route line inside
  `adminRoutes`' existing workshop block.
- Frontend: `web/src/lib/api.ts` gained `announceWorkshop(id)`
  (`POST /admin/workshops/{id}/announce`, returns `Campaign`).
  `WorkshopEditor.svelte` gained an "Announce" panel (button + error
  state + an "Open draft campaign" button once one exists).
  `Workshops.svelte` forwards a new `onAnnounced` prop through to it.
  `Admin.svelte` wires `onAnnounced` to switch to the Campaigns tab and
  pass the new campaign id to `Campaigns.svelte` via a new
  `openCampaignId` prop (consumed once, then cleared via
  `onOpenedCampaign`, mirroring the existing `goToCampaignAudit`
  cross-tab deep-link shape from #0114).

### Rulings on the six points raised for scrutiny

**1. It never sends, and cannot be made to send by accident — confirmed,
structurally.** `h.campaigns` is `announceCampaignStore`, a *one-method*
interface exposing only `Create`. The handler therefore has no `Send`,
`Materialize`, or worker reference available to call, so this is enforced by
the type system rather than by discipline. Confirmed by execution above (zero
`email_sends` rows, null send timestamps, `status='draft'` read straight from
the row). The `draft` status is the column default from migration `000017`
plus `CampaignStore.Create`'s own contract — `Announce` never names a status
at all. On `CLAUDE.md` §9 specifically: the `physical_address` gate lives in
`internal/mailing/worker.go` (`failCampaign(..., "physical_address_missing")`)
and `worker.go` is not in this diff; `POST /api/subscribe`'s uniform 202 is
not in this diff either. Both are untouched, as they should be — nothing here
goes near either.

**2. The interest-targeting fallback — accepted, with a recommended
follow-up.** First, the option space is narrower than it looks: there is no
"empty audience" mode to create the draft with. `internal/mailing` has exactly
four (`all`, `any_of`, `all_of`, `none_selected`), and `none_selected` is a
real segment — *subscribers who chose no interests* — not a blank the admin
fills in. So the genuine choice is `all` or refuse.

`all` is the right call, on balance. The draft is `draft`; `#0047`'s send
sequence still stands between it and any subscriber, and that sequence
includes `GET /admin/campaigns/{id}/audience` (count + sample) and a **typed
confirmation of the real recipient count**, verified server-side against the
audience engine. An operator who expected 60 recipients and is asked to type
1,847 has a loud signal. Refusing would break the one-click contract for what
is usually a data-entry omission the operator can fix in the draft anyway.

The defensible criticism is not the fallback but its **silence**. `Announce`'s
201 looks identical either way, and `WorkshopEditor.svelte`'s panel copy says
the draft is "targeted at its interests" — which is simply untrue in the
fallback case, with nothing in the UI saying so. That is worth a small
follow-up (see below); it is not worth a bounce, because the widened audience
cannot reach anyone without passing a gate that displays and verifies the
count.

**3. The `WorkshopID` FK — verified end to end, behaves correctly.** See the
end-to-end proof above: announce → 409 on delete, control → clean delete.
`CampaignInput.WorkshopID` defaults to `nil`, so every pre-existing `Create`
caller is unaffected, and the parameter count/order in the INSERT was checked
by hand against the column list.

**4. `main.go`'s `campaignsStore` restructuring — safe, and not the
`#0051`/`#0054` bug class.** The reason it is not: `mailing.CampaignStore` is
`struct { pool *pgxpool.Pool }` — entirely stateless. Sharing one instance
versus constructing two is *behaviorally identical*, which is exactly what
made `seo.Site` different (it holds a cache, so instance identity is
load-bearing, which is why `seo_wiring_test.go` proves it). The wiring tests
still prove what they claim: `seo_wiring_test.go` still hands the **same**
`site` to `AdminWorkshopsHandler` and `mountAndServe` — its actual proof —
and passes a fresh `CampaignStore` for the new argument, which is correct
because that test is not about campaigns. `admin_wiring_test.go` passes the
shared `campaignsStore`, mirroring production. Both were read, and both pass.
Separately, the new route was added *inside* `adminRoutes`' table, so
`TestMountAndServe_AdminRoutesRequireSessionAndAdmin` covers its guard
automatically and `admin_routes_ast_test.go` would catch any attempt to
register it beside the table; `_NonAdminForbidden`'s 403 confirms it
directly.

**5. `Announce` as a method on `*AdminWorkshopsHandler` — acceptable.** The
narrow-interface convention `CLAUDE.md` §1 requires is about what a handler
depends on, and `announceCampaignStore` is a single-method interface — the
convention is satisfied, arguably better than by a separate handler type
holding a fatter dependency. The real cost is that
`internal/handlers/admin_workshops.go` now imports `internal/mailing`, but
this is an inherently cross-subsystem feature (a workshop producing a
campaign) and the route is specified in PRD §8 as living under
`/admin/workshops/{id}`. The alternative cost ~10 wiring-test call-site
changes to thread a second handler through `adminRoutes`/`mountAndServe` for
one route. The `nil campaigns` → 500 tolerance is a mild smell, but it mirrors
the `invalidator` nil-tolerance precedent already in the same file, is
guarded before any dereference, and no production call site passes nil.

**6a. UTC-only dates in the pre-filled body — acceptable here, follow-up
recommended.** The output is *labeled* (`"...at 6:00 PM UTC"` — the layout
carries `MST`, so the zone is always printed), so it is inconvenient rather
than silently wrong, and it lands in a draft that `#0047` forces through a
test send and review before delivery. It is still the wrong default for an
SF-based org: `web/src/lib/workshops.ts` renders the same timestamps in the
*viewer's* local zone, so a Bay Area reader sees Pacific on the workshop page
and UTC in the email announcing it. Worth fixing, not worth blocking.

**6b. Reusing `email_campaign.created` with `via: "announce"` — acceptable as
built.** The precedent cited against it (`workshop.published` /
`workshop.unpublished` / `workshop.canceled`) is a set of distinct *state
transitions*; announce is not a new transition, it is the same creation event
`POST /admin/campaigns` produces, differing only in provenance. Keeping one
action means "who created this campaign, and when" has a single queryable
answer, with `via`/`workshop_id`/`workshop_slug` answering "how". The test
asserts exactly one such row targets the new campaign and none targets the
workshop. No change wanted.

### Recommended follow-ups (not blocking)

Not filed here — this review commits only `issues/0056.md`.

1. **Surface the audience fallback in the UI.** When the loaded workshop has
   zero interests, `WorkshopEditor.svelte`'s Announce panel should say the
   draft will target *everyone* rather than "its interests" — the workshop's
   interest ids are already loaded in that component, so this is a local,
   cheap change. This is the finding most likely to matter in production.
2. **Render the pre-filled body's date in `America/Los_Angeles`** rather than
   UTC, matching what `web/src/lib/workshops.ts` shows a Bay Area reader on
   the workshop page itself.
3. **The pre-filled body has no link to the workshop page.** It emits a
   "Sign up" link only when `signup_url` is set, so a workshop without an
   external RSVP link produces an announcement with no call to action at all.
   Adding a `/workshops/{slug}` link would fix that. (Not an acceptance
   criterion — §8 asks only for title, summary, date, and location — so out
   of scope for this issue.)

### Minor observations, no action needed

- `TestAdminWorkshopAnnounce_NonAdminForbidden` posts to a literal
  `/admin/workshops/1/announce`. §8b's "never target a literal id" rule is
  aimed at mutations that reach data; here `RequireAdmin` rejects before the
  handler runs, nothing is written, and this mirrors the existing
  `TestAdminWorkshops_NonAdminForbidden`. Fine as is.
- `t.Cleanup` ordering is correct (LIFO): campaigns are deleted before the
  workshop they reference, so cleanup never trips the FK it just proved.
- `announceWorkshop` has no `api.ts` unit test, but neither do
  `deleteWorkshop`/`updateWorkshop` — `api.ts` is a thin fetch wrapper and the
  tested logic lives in `web/src/lib/*.ts`. Consistent with convention.
- `Campaigns.svelte`'s new `$effect` writes `mode`/`activeCampaignId`, neither
  of which it reads, and the `openCampaignId !== null` guard stops the
  re-run after `onOpenedCampaign` clears it. No effect loop.
