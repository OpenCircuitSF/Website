## Description

`Create → Confirm → Unsubscribe → RestartSignup → Unsubscribe again while
pending` yields components `(confirmed 0, imported 0, unsubscribed 1)` — a net
**−1** for one person who is, at the end, exactly where they started.

**Pre-existing**, and measured identical on both sides of `#0336`'s fix, so it
is neither caused nor worsened by it. `#0324` fixed the *four*-action version by
making `RestartSignup` clear `unsubscribed_at`; the fifth action re-stamps it
with no live arrival left to offset it.

`#0336` incidentally fixes the import-sourced counterparts — its cells O3 and P3
— because `unsubscribed_30d` excludes `source = 'import' AND consent_basis IS
NULL`. A `signup_form` row has nothing to exclude it, so the same shape survives
on the public path.

Low severity: it requires five sequential actions by one person inside a 30-day
window. It is worth fixing because it is the *third* cell of this family found
by a different method than the last — `#0311` found the first by review,
`#0324`'s review found rows O and P by building a truth table, and `#0336`'s
review found this one only by asserting the three components separately instead
of the net.

## Acceptance criteria

1. The five-action website-signup sequence nets 0, component-wise, not merely in
   the net figure.
2. The fix does not reintroduce `#0324`'s four-action asymmetry or `#0336`'s
   rows O and P — re-run their truth tables and show every cell unchanged except
   the intended one.
3. Assertions are **component-wise** (`confirmed`, `imported`, `unsubscribed`
   separately). A net-only assertion is not acceptable: `#0336`'s review found
   two cells that netted zero from two opposite errors.
4. The general shape is addressed, not just five actions: state what happens at
   six and seven, and why the fix bounds the whole family rather than the next
   cell. An off-by-one that recurs at every odd action count is not fixed.
5. Consistency with the import-sourced path is stated — `#0336`'s exclusion
   handles those; say whether this fix subsumes it or sits alongside it.
6. Real `time.Now()` for every `Create`/`Commit`; order-independence proved with
   `-shuffle`, never `-count=N` (§5a). `#0324`'s first draft caused a cross-test
   flake exactly this way (`#0285`).
7. No migration needed; `000001`–`000022` frozen (§1), tree at `000025`.

## Review notes

Reviewed 2026-09-05 (Opus, phase 3): **resolved**, as one batch with
[#0343](0343.md) over commit `6100b6b`. See `#0343`'s own review notes for the
shared verification run, the machine state, and the git-hygiene record; this
section covers what is specific to the departure predicate. The load-bearing
claim — that the new positive test *subsumes* `#0336`'s exclusion rather than
sitting beside it — was established two ways, neither of them by reading the
implementer's argument back.

### The subsumption holds, derived from the writers of the two columns

`#0336` is `resolved`, so nothing else is watching it; a wrong subsumption
would silently weaken a shipped fix. Enumerated every writer of `consent_basis`
and of `confirmed_at` in the tree (four and three respectively, all in
`internal/subscribers/`) and read the SQL:

- `Store.Confirm` sets `confirmed_at = $3` and
  `consent_basis = COALESCE(consent_basis, $4)` **in the same UPDATE**.
- `Store.RestartSignup` clears `confirmed_at` and `consent_basis` **in the same
  UPDATE, under the identical `CASE WHEN status = $11` guard**.
- `ImportStore.Commit`'s direct-import INSERT writes
  `consent_basis = imported_prior_consent` with a nil `confirmed_at`; its
  invite INSERT writes neither column.

Two invariants follow, and they are exactly the two the subsumption needs:

| Invariant | Consequence |
|---|---|
| `consent_basis IS NULL` ⇒ `confirmed_at IS NULL` | wherever the old guard *excluded* a row, both new disjuncts are false — same exclusion |
| `consent_basis = 'double_opt_in'` ⇒ `confirmed_at IS NOT NULL` | wherever the old guard *counted* an import row, one new disjunct is true — same inclusion |

So the two predicates agree on every import row, and differ only for
non-import rows, which the old guard never examined. That is a generalization,
not a second guard. It is also faithful to `#0336`'s review, which measured
that mirroring the departure guard onto a bare equality would drop an accepted
invitee's unsubscribe: the `confirmed_at IS NOT NULL` disjunct is precisely
what keeps that row counted, and truth-table row D still reads (1,0,1).

### The subsumption is guarded, not merely argued — proved by mutation

Dropping the `(source = $2 AND consent_basis = ANY($3))` disjunct — an
*incomplete* subsumption, the failure mode this review was asked to rule out —
is caught immediately, by four separate tests including two pre-existing
truth-table rows:

### `TestGrowth30Days_RestartedImportRowSecondUnsubscribeStaysExcluded` is real coverage

Checked that this test exercises `#0336`'s own case rather than passing for an
accidental reason. Reverting `#0336`'s `RestartSignup` `consent_basis` clearing
(leaving the new predicate intact) fails its `P3` subtest component-wise —
`imported delta = 1, want 0` at the restart and `unsubscribed delta = 1, want
0` after the second unsubscribe — alongside the pre-existing truth table's rows
O and P. So `#0336`'s fix is still measured after this change.

Worth recording precisely, because the implementer's claim is slightly stronger
than what holds: the `O3` subtest does **not** fail under that mutation. Under
the new predicate an accepted invitee's restarted row is excluded twice over —
`confirmed_at` is cleared *and* `double_opt_in` is not in the arrival set — so
`O3`'s exclusion no longer depends on the `consent_basis` clearing at all. That
is the new predicate being strictly more robust than the old one for that row,
not a gap: row O itself is still covered by `TestGrowth30Days_TruthTable_0336`,
which fails under the same mutation.
