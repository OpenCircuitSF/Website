## Description

`#0127` shipped with `BuildWelcomeEmail`'s doc comment appended to the end of
`BuildAdminAlertEmail`'s, so `#0126`'s documentation was attributed to `#0127`'s
function. `go doc BuildAdminAlertEmail` returned a bare signature.

**Nothing in the toolchain can see this.** A contiguous `//` block is
well-formed, so `gofmt` is silent; `go vet` does not look; `check.sh` passed with
it in place. It was caught only because a reviewer ran `go doc` on the specific
symbols a bounce had named.

**The detector already exists — it just was not committed.** `#0127`'s
re-reviewer wrote a `go/ast` pass for the exact defect shape: *a declaration
whose `Doc` comment's first word names a different top-level symbol in the same
file*. Run over all of `internal/` and `cmd/`, it found **zero** mis-attributions
after the fix.

That is a cheap, precise guard for a defect class this project has now hit once
and cannot otherwise detect.

## Acceptance criteria

- [x] A guard fails when a declaration's doc comment opens by naming a different top-level symbol declared in the same file
- [x] It runs in `scripts/check.sh`'s default Go scope, not only under `all`
- [x] Mutation-proved: reattach `#0127`'s original corruption in a copy, confirm the guard names both symbols; revert, confirm clean
- [x] **No false positives on the current tree** — the reviewer's run was clean, but its first attempt produced four hits caused by its own trailing-`s` trim, so the normalisation needs care and its own test
- [x] Grouped `const`/`var` declarations legitimately sharing one comment are not flagged — that was the other source of first-pass noise
- [x] `ISSUE=0267 scripts/check.sh go ./internal/...` passes with zero skips

## Notes

Found by `#0127`'s phase-3 re-review under `CLAUDE.md` §9, which built and ran
the detector as part of sweeping for a second instance.

**Scope it honestly.** This catches one specific, mechanical shape: the first
word naming a sibling symbol. It will not catch a doc comment that is merely
wrong, or one describing the right symbol inaccurately — that is the class
`#0263` covers and which review is the only instrument for. Say so in the
guard's own comment, so nobody later assumes doc comments are verified.

Worth noting the same review found a related prose defect in `#0127`'s own
`## Fix pass`, which claimed it "inserted the blank line between
`BuildAdminAlertEmail`'s doc comment and its `func` line" — **that would
re-detach the comment**, the very defect being fixed. The code was right and the
description was wrong, in the pass fixing a documentation defect.

## Implementation notes

New file `internal/handlers/misattached_doc_comment_guard_test.go`, same
package and same shape as `#0196`'s citation guard: a `go/ast` walk over
`citedTestScanRoots` (reused directly from
`dangling_test_citation_guard_test.go`, which was clean in git status when
this was written, along with `walkGoFiles`/`skipVendoredDir`/
`toRepoRelativePath`), a small regexp naming the candidate shape, and
exclusion rules earned by real hits.

**The check.** For each top-level declaration's own leading doc comment
(`*ast.FuncDecl.Doc`; a single-spec `*ast.GenDecl.Doc`; or an individual
`*ast.ValueSpec`/`*ast.TypeSpec`'s own `Doc` inside a group), take the
comment's first bare identifier (`^[A-Za-z_][A-Za-z0-9_]*`, anchored — a
comment opening with anything else, e.g. an issue citation or ordinary
prose, yields no match and isn't checked at all). If that word names a real
top-level symbol declared elsewhere in the same file, and is not one of the
name(s) this comment is actually attached to, it's a hit.

Deliberately **no stemming or trimming** beyond what the identifier
character class itself excludes — the acceptance criteria's own warning
about a trailing-`s` trim producing four false hits is closed by construc-
tion: "BuildWelcomeEmail's" matches "BuildWelcomeEmail" because the pattern
simply stops at the apostrophe, and a plain plural like "Kinds" is left
exactly as written, so it only ever equals a real name when the author
wrote that identifier verbatim as the first token.

**Grouped const/var (acceptance criterion).** A `*ast.GenDecl` with two or
more `Specs` is a genuinely grouped block, and its group-level `Doc` is not
checked at all — only an individual member's own per-spec `Doc` is (still
fully checked, and pinned by
`TestMisattachedDocCommentGuardStillChecksPerMemberDocInsideAGroup`). This
was not a hypothetical: the first version of this guard, checking every
`GenDecl.Doc` regardless of group size, found **six** real "hits" on this
tree, all of them this codebase's own established idiom of opening a
multi-member block with a category noun or the function it supports —
`internal/mailing/campaigns.go` ("Campaign status constants..." on
`CampaignStatus*`), `internal/mailing/preflight.go` ("Preflight failure
codes" on `PreflightCode*`), `internal/subscribers/suppressions.go`
("Suppression reasons..." on `SuppressionReason*`),
`internal/subscribers/store.go` ("Unsubscribe source values..." on
`Source*`), `internal/workshops/store.go` ("Workshop status constants" on
`Status*`), and `internal/mailing/worker_test_helpers_test.go`
("newTestWorker constructs..." glued above its own supporting `const`
block). None is `#0267`'s defect shape — the real incident was
`FuncDecl`-to-`FuncDecl`, and no grouped block anywhere in this tree's
history has ever exhibited it — so the group-size exclusion is honest,
structural, and documented in the guard file's own header rather than a
name-based allowlist.

**One instance survived that rule and needed individual judgment**:
`internal/handlers/public_list_stats.go`'s `const pendingBucket = 5` (a
single-spec declaration, so the group-size rule doesn't reach it) carries a
doc opening "PublicListStatsHandler serves GET /api/list-stats...", naming
the handler TYPE declared later in the same file. Read in full, every
paragraph after the opener is substantively and exclusively about
`pendingBucket` — why it exists, what it defends against, and it names
`pendingBucket` by its own identifier partway through — the opposite of
`#0127`'s real defect, where the corrupted block contained nothing at all
about the declaration it was actually attached to. This is closed by a
small, individually-verified allowlist (`misattachedDocKnownBenignPairs`,
keyed by file so it can't silently excuse an unrelated future doc in a
different file), the same role `nonTestIdentifierAllowlist` plays for
`#0196`'s sibling guard — not a structural loosening, since nothing local
distinguishes this case from a real corruption.

**One real (very minor) instance of the actual defect, found and fixed.**
`internal/handlers/subscribe_test.go:1605` had `// snapshot returns a
race-safe copy of every counter...` — a doc unmistakably describing
`func (c *countingSubscriberStore) snapshot()` — attached instead to `type
subscriberStoreCallCounts struct{...}`, the declaration immediately above
it, leaving `snapshot()` itself with no doc of its own (the same
"undocumented, adjacent declaration got it instead" shape as `#0127`, just
lower-stakes: an unexported method on a test-only counter type). The file
was clean in git status both when first checked and immediately before this
edit (`internal/handlers` is a concurrently-edited package this session, per
the orchestrator's brief); the fix moves the two-line comment down to sit
directly above `func...snapshot()` and leaves the struct undocumented,
which is consistent with plenty of other unexported test-only helper types
in this codebase. This was the ONLY tree-wide finding treated as a real
defect rather than a guard-design gap; every other candidate the guard's
development turned up on the tree was legitimate prose the guard's
exclusion rules now correctly leave alone.

**Mutation-proved** (acceptance criterion), by direct isolated proof against
`t.TempDir()` fixtures using the real historical symbol names (safe: neither
`BuildAdminAlertEmail` nor `BuildWelcomeEmail` is a real declaration in this
guard's own file, so its own tree-wide run never sees them as anything but
prose):
`TestMisattachedDocCommentGuardCatchesThe0127Shape` reproduces the exact
corruption (a doc naming `BuildWelcomeEmail`, attached to a bare
`BuildAdminAlertEmail`) and asserts the guard names both symbols;
`TestMisattachedDocCommentGuardCleanOnceReattached` is the same fixture with
each function given its own doc — the historical fix pass's actual shape —
and asserts zero hits.
