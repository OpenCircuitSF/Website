## Description

`scripts/go_file_visit_floor_guard_test.sh` **exits 1 on `HEAD`**, with two
failures in its `internal/handlers` citation-guard section. Reproduced by the
orchestrator directly:

	FAIL: REGRESSION #0300: committed citedTestScanRootsMinPlausibleFileCount=150
	is NOT plausible against an externally-measured population of 305 ...
	(floor must stay >= population/2 ...)

	FAIL: REGRESSION #0300: committed lineCitationGuardMinPlausibleFileCount=150
	is NOT plausible against an externally-measured population of 305 ...

Both constants are `150`; the measured population is `305`; the rule the guard
enforces is `floor >= population/2`, so the threshold is `152.5`. The tree grew
past the margin and the floors did not follow.

The affected guards are named in the failure text:
`TestNoCommentCitesUnresolvedPathOrSection`,
`TestNoCommentCitesUndefinedTestFunction`,
`TestNoDocCommentNamesADifferentDeclarationInSameFile`, and
`TestNoCommentCitesGoFileByLineNumber`.

## This is the good failure mode, not the bad one

`#0483`, `#0487`, and `#0488` fixed four exact counts that had drifted **and
gone unnoticed**, because a floor only catches shrinks. **This floor is
different: it has a growth-ceiling check, and that check works.** It is telling
us, correctly and by name, that the population has outgrown the margin.

So the defect is not the mechanism. It is that **nobody ran it.**
`CLAUDE.md` §5 puts this harness behind `scripts/check.sh guards`, which is
deliberately excluded from `go`, `web`, `all`, and the default — `dev_guard_test.sh`
alone costs ~48s and binds `:5173`. So an ordinary verification never touches
it, and today `:5173` is held by orphaned processes, which makes running the
suite as a unit awkward besides.

Four separate agents ran this harness today by invoking it directly, and each
reported its own sections passing. None was asked about the file's exit code.

## A fifth stale-count instance lives in this same file

Found by `#0488`'s review. `outbox_floor_plausible`'s own header comment says
`citedTestScanRootsMinPlausibleFileCount` "sits at floor=150 against a
re-measured population of 267" and "does not fail until the population reaches
roughly 302".

**The same script measured 305 and reported that floor failing on the same
run** — a prediction its own container contradicts within one terminal scroll.
Two lesser stale figures sit in the same paragraph: "non-exempt floor is 6"
against a committed 8, and "~20 of 32".

`#0488` deliberately did **not** fix that paragraph, because its wording
depends on whatever this issue does to the floors. **It is yours.** Whatever
value you choose in criterion 2, this prose must describe it — and per
criterion 5, prose that must be hand-updated as the tree grows is the shape
that produced all five instances.

Why `#0488`'s sweep missed it, which is worth knowing before you write a
replacement: it is a `.sh` header phrased "a re-measured population of 267",
and the constant was checked at its own declaration, where it *is* framed
historically. A search for the shapes that caught the other four does not
reach it.

Four other floor constants were enumerated and read in that sweep —
`repoWideGuardScanFileFloor`, `repoWideGuardScanDirFloor`,
`migrationCitationMinPlausibleCitationCount`, and its identifier sibling. All
are historically framed and carry no defect.

## Acceptance criteria

1. **Re-derive the population yourself** — 305 is the orchestrator's single
   measurement. Six premises have been corrected by measurement in this project
   recently; do not be the seventh.
2. **Raise both floors** to satisfy the rule, and say what value you chose and
   why. Note the rule is a *ratio*, so the new value should leave headroom for
   ordinary growth rather than sitting one file above the line and failing again
   next week.
3. **Do not weaken the growth-ceiling rule** to make the failure go away. It is
   the only mechanism in this family that catches growth at all, and the four
   issues above exist because the others do not.
4. **Prove both directions still work**: the floors must still fail when the
   tree shrinks, and the ceiling must still fail when the population outgrows
   the margin. Mutate a copy, never `git stash` (`CLAUDE.md` §8a), and restore
   byte-identically with SHA-256.
5. **Decide what stops this recurring.** A floor that must be hand-raised as the
   tree grows will drift again; that is the same shape as the exact counts, one
   level up. Options include deriving the floor from the population at run time
   (which weakens it to a tautology — say so if you reject it), widening the
   margin, or surfacing the harness somewhere an ordinary run reaches. **Pick
   one and justify it.**
6. **Say whether `scripts/check.sh guards` should stay out of the default.**
   `CLAUDE.md` §5's reason is cost and the `:5173` bind, both real. If it stays
   out, name what else would have caught this — an exit-code check in CI, a note
   in the phase-3 step, or something else. The status quo demonstrably did not.

## Fix

### Criterion 1 — the population, re-derived, and why it moved

Measured on 2026-09-09 with the harness's own filter, from the repo root:

    find internal cmd web \( -name node_modules -o -name dist \) -prune -o -type f -name '*.go' -print | wc -l

**305.** Cross-checked against `git ls-files` for the same three trees: also
305, with `comm` reporting an empty untracked-only set.

The 305-vs-306 discrepancy in this issue's own description is explained, and
the explanation matters more than the number. My **first** run of the harness
this session reported **306**; a `find` minutes later reported **305**, with no
commit in between. The extra file was `internal/db/zzscratch_0268_measure_test.go`
— a scratch `_test.go` another agent had open for `#0268`, present in
`git status` when I started and deleted before my second measurement. So the
population is not merely a growing number that goes stale slowly; it is a
number that **differs between two runs minutes apart on an unchanged commit**,
because a concurrent agent's untracked file counts. Nothing that has to be
kept in sync by hand can track that, which is the whole of criterion 5's case.

### Criterion 2 — both floors raised to 216, by a stated rule

`citedTestScanRootsMinPlausibleFileCount` and
`lineCitationGuardMinPlausibleFileCount` both go `150` → **216**.

216 is not a chosen number, it is a **derived** one, and the derivation is now
written down in both constants' doc comments and in the harness header so the
next raise is arithmetic. `floor_plausible`'s two bounds — `floor <= population`
and `floor >= population/2` — say together that a floor is valid exactly while
the population sits inside the window `[floor, 2*floor+1]`. Putting the
measured population at the **geometric centre** of that window leaves the same
*proportional* headroom in both directions:

    floor = ceil(population / sqrt(2))    ->  ceil(305 / 1.41421...) = 216

Headroom that buys, at a population of 305: the ceiling does not fire until
the population reaches **434** (129 more `.go` files, +42%), and the floor does
not fire until the tree falls to **215** (90 files lost, -30%). The ratios are
1.42 and 1.41 — deliberately symmetric. For comparison, the committed `150`
had **one** file of ceiling headroom left when this issue was filed, and 216
also restores the property `#0275` criterion 3 actually cares about: it sits
comfortably above the largest single package under these roots
(`internal/handlers`, 106 files), so narrowing the roots to any one package
still trips the floor.

The harness now computes this value itself — `suggested_floor()` — and prints
it in the failure it applies to, so a future ceiling trip names its own remedy
instead of asking the next agent to invent a number. Its integer arithmetic
(`(population * 70711 + 99999) / 100000`, since bash 3.2 has no floating point)
was checked against Python's `math.ceil(p/math.sqrt(2))` at populations 12,
193, 305, 435 and 1000: identical at all five.

### Criterion 3 — the growth-ceiling rule is untouched

`floor_plausible()` is byte-for-byte what it was; the diff for that function is
empty. Nothing was added that can weaken it either: `suggested_floor()` and
`floor_failure_reason()` only compose failure *text*, are called only from
inside the existing `fail` branch, and neither is consulted by the predicate.
The value they suggest is deliberately *higher* than the bound requires (216
against a minimum of 152), so following the printed remedy tightens the guard
rather than shaving it to the line.

### Criterion 4 — both directions, proved on a copy

Both proofs ran against a **private copy of the tree**, never the tracked one:
`internal/`, `cmd/`, `web/*.go` and the harness copied into a scratch sandbox
(`cp -R`; no `git stash`, `CLAUDE.md` §8a). Baseline first — the sandbox at
full size reproduces the real tree's verdict (population 305, exit **0**, "all
guards hold") — so the two mutations below are measured against a sandbox
known to agree with reality.

**Shrink direction.** Deleted five whole packages from the sandbox
(`internal/mailing`, `internal/subscribers`, `internal/auth`, `internal/seo`,
`internal/middleware`), taking the population to **193**. Exit **1**, and both
raised floors named:

    FAIL: ... citedTestScanRootsMinPlausibleFileCount=216 is NOT plausible
    against an externally-measured population of 193. The floor sits ABOVE
    the measured population, which is #0275's own failure mode ...

**Growth direction.** Restored the sandbox and added 130 trivial `.go` files,
taking the population to **435** — one past `2*216+1`. Exit **1**, with the
ceiling named and the remedy computed from that run's own population:

    FAIL: ... citedTestScanRootsMinPlausibleFileCount=216 is NOT plausible
    against an externally-measured population of 435. The tree grew past the
    floor's margin ... THE REMEDY (#0489): set
    citedTestScanRootsMinPlausibleFileCount = 308 in
    internal/handlers/dangling_test_citation_guard_test.go ...

(308 = `ceil(435/sqrt(2))`, independently confirmed.) The two 80-floors trip in
that run too, for the same reason and with their own suggested values — which
is the ceiling doing its job, not a side effect.

**Byte-identical restoration.** No tracked file was mutated at any point, so
there was nothing to restore: every mutation happened inside the sandbox
directory. The harness's own end-of-section checks assert this from the other
side and report every tracked guard file unchanged across each run, and
`shasum -a 256` on the four floor files plus the harness matches before and
after the whole exercise.

### Criterion 5 — what stops it recurring: surface the harness

**Chosen: surface it where an ordinary run reaches it.**
`scripts/check.sh` now runs `scripts/go_file_visit_floor_guard_test.sh` in its
`go`, `all` and **default** arms, via a `floor_guard_check` helper placed
beside `gofmt_check` and called in exactly the three places `gofmt_check` is.
Measured cost: **~2.2s**, no port, no database, no build.

The reasoning, in one line: **the mechanism was never the problem — it named
this failure correctly, by name, with the affected guards listed. The problem
is that its exit code reached nobody.** So the fix belongs at the point of
delivery, not at the predicate.

*Why not derive the floor from the population at run time.* Rejected, and it
is worth being precise about why, because it looks like the tidiest option.
The floor exists so that a guard which has been **narrowed** — roots emptied,
scan list cut to one package — cannot report "no findings" from a walk that
examined almost nothing. A floor derived from the same walk it is judging
moves with the narrowing: cut the roots and both `got` and the floor fall
together, `got >= floor` stays true, and the check becomes `population >=
population/2`, which is true for every non-negative number. That is not a
weaker guard, it is **no guard**, and it is the exact fail-open `#0275` and
`#0300` were written to close. (Deriving it from an *independent* measurement
is a different proposal, and is what the harness already does.)

*Why not widen the margin.* Rejected on criterion 3's own ground. The
`floor >= population/2` bound is the only growth detector in this whole
family — `#0483`, `#0487` and `#0488` are three issues' worth of counts that
drifted **silently** precisely because their floors have no such bound.
Loosening it to make today's red go green trades the one working detector for
a quiet terminal, and it does not even solve the problem it is aimed at: a
wider margin still needs a hand-raise eventually, just later, and later is
worse because more drift has accumulated by then.

*What the choice does not fix, stated honestly.* Wiring the harness into
`check.sh` does not stop the floors needing a hand-raise as the tree grows. It
changes **who finds out and when**: from "whoever eventually runs a mode
nothing routes to, some unknown number of commits later" to "the next agent to
verify anything, on the run they were going to do anyway" — and it hands that
agent the replacement value rather than a puzzle. Combined with the doc
comments being rewritten to state the *rule* rather than a *number*, the
recurring cost drops to editing one integer that the failure message itself
spells out.

### Criterion 6 — should `scripts/check.sh guards` stay out of the default?

**Yes, the bundle stays out — but the exclusion was being read one level too
coarsely, and that misreading is what let this sit.** `CLAUDE.md` §5's stated
reason is a property of **one** member: `dev_guard_test.sh` costs ~48s and
binds `:5173` (today, held by orphaned processes, so the bundle cannot even be
run cleanly as a unit). That reason is real and it still holds for the bundle.
It was never a reason to exclude a two-second, port-free, database-free
filesystem check that happens to live in the same list. So the answer is not
"promote `guards`", it is "stop treating `guards` as the unit of promotion":
one script moves onto the ordinary path, the rest stay behind the manual gate.

Naming what else would have caught this, since the question asks: an exit-code
check in CI would have, but there is no CI on this repo, and proposing one is
proposing infrastructure rather than a fix. A note in the phase-3 step would
have depended on a reviewer remembering to read it — the same class of
dependency that failed here four times in one day. The status quo *was* "an
agent will run it directly and look", and four agents did exactly that, each
reporting its own sections passing, none looking at `$?`. A failure mode that
survives four independent competent observers in one day is not fixed by
asking for a fifth.

`CLAUDE.md` §5's passage has been updated to record the exception and the
reason for it, so the next reader does not re-derive "guard scripts are
excluded" as a category rule.

### The fifth instance — rewritten so it cannot drift

`outbox_floor_plausible`'s header comment carried three stale figures and one
self-contradiction: it predicted a ceiling "roughly 302" while the same run
reported that ceiling already breached; it said the non-exempt floor "is 6"
against a committed 8; and it argued file-domination from "~20 of 32".

The replacement quotes **no population, no floor and no percentage**, because
those are exactly the figures that drift. What it states instead is arithmetic
that is true at every scale: under `floor >= population/2`, a floor sitting at
exactly half its population has room for that population to grow by **exactly
two** before it trips — which on a call-site population counted in tens is the
next commit or two that adds a caller, and on a file-count population in the
hundreds is not. The domination argument is likewise re-made structurally
rather than numerically: the file that dominates is `internal/outbox`'s own
`store_test.go`, and the **non-exempt population excludes `internal/outbox`
wholesale, by construction of `count_outbox_call_sites`' exclude argument** —
so a domination argument can only ever bear on the total floor, never on this
one, and no count is needed to see it.

The same treatment was applied to the header comment's item 4 and its
growth-ceiling note, which carried the same class of stale figures
(`150/258 = 58%`, `80/111`, `80/110`, "roughly 44 files"): they now state the
window relationship and point at the live numbers the run prints.

### The population and the arithmetic, re-derived

The harness's own filter counts **305** `.go` files under `internal cmd web`,
and `git ls-files` over the same three trees also counts **305**, with no
untracked `.go` file present at review time. So the two universes agree today,
which is a coincidence of timing rather than a property (see below).

`216` is `ceil(305 / sqrt(2))`, confirmed against Python. The predicate accepts
a floor while the population sits in `[floor, 2*floor+1]`, so `216` is valid
across `216`&ndash;`433`: the ceiling fires at a population of `434` (+42%) and
the floor fires once the tree falls to `215` (&minus;30%). Those ratios are
1.4197 and 1.4186 &mdash; symmetric, as claimed. The bash integer form
`(population * 70711 + 99999) / 100000` matched Python's ceiling at every
population I tried, including the two used in the mutation proofs.

`#0275` criterion 3 is restored: the largest single package under these roots is
`internal/handlers` at **106** files, comfortably below 216, so narrowing the
roots to any one package still trips the floor. The doc comment's admission
that narrowing to `internal` alone would *not* trip it is correct and worth
having &mdash; `internal` alone holds **282** of the 305.

### The growth-ceiling rule was not weakened

`floor_plausible()` extracted from both sides of the commit hashes identically
(`8f1e9a95…`), so criterion 3 holds by construction rather than by reading the
diff. `suggested_floor()` and `floor_failure_reason()` are reachable only from
inside the existing `fail` branch and neither is consulted by the predicate;
the value they print is above the bound rather than at it, so following the
printed remedy tightens the floor.

### The untracked-file instability: correctly diagnosed, and correctly left alone

The population is a raw `find`, so a concurrent agent's untracked scratch test
counts. That is the right choice and should not be "fixed" to read the index:
the Go guard this oracle judges also walks the filesystem, so an oracle keyed
to `git ls-files` would be measuring a different universe than the guard whose
floor it is validating &mdash; which is how an external oracle stops being one.
At this margin the instability is immaterial: it takes 129 added files to reach
the ceiling and 90 lost files to reach the floor, so no plausible number of
scratch files moves the verdict. It would matter at a margin of one or two,
which is exactly the margin the old value had, and is a further argument for
the derived floor over a minimal one.
