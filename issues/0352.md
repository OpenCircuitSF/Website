## Description

`internal/outbox/claim_kinds_call_site_guard_test.go:204`, inside
`claimKindsGuardMinPlausibleNonExemptCallSiteCount`'s `#0322` paragraph, cites
`internal/mailing/worker.go:575` for the unrelated
`mailing.SendStore.OrphanSweep` name collision. Measured by AST census today,
that call is at **`worker.go:625`**.

`nameMatchesGuardedMethod`'s doc comment ~300 lines below in the same file
already carries the correct number. **So one file states two different
locations for the same call**, and nothing detects the divergence: the shell
harness checks constants and required-site names, and
`internal/db/prd_section_index_test.go` covers only `PRD.md`.

**Correcting `575` to `625` buys nothing.** The next unrelated edit to
`worker.go` re-breaks it — which is exactly what already happened here. A line
number in a doc comment drifts on every edit to the cited file and is checked
by nothing, and this project already knows the answer: §11's PRD index was
deliberately rewritten to be **heading-anchored rather than line-numbered**,
"so they survive edits to the PRD".

This is the third comment-accuracy defect in this one guard family
(`#0334`, `#0345`, and now this), and today three separate reviews had to
re-measure numbers in this file.

**Note for whoever picks this up**: `#0330`'s implementer reported this defect
at `nameMatchesGuardedMethod`'s comment citing `worker.go:543`/`:575`. That
report is itself wrong — `nameMatchesGuardedMethod` is correct, the string
`:543` appears nowhere in the file, and the single stale citation is the one at
line 204. Re-measure rather than trusting either that report or this paragraph.

## Acceptance criteria

1. The stale citation at line 204 no longer states a wrong location.
2. **Cited positions are replaced with stable identifiers rather than corrected
   numbers** — name the declaration and the call (`Worker.recoverOrphans`'s call
   to `SendStore.OrphanSweep`; `worker_store_test.go`'s three sites), the way
   §11's heading-anchored index does. A pass that merely updates `575` to `625`
   does not resolve this issue.
3. Apply this throughout the file, not only at line 204 — a survey of every
   `<file>.go:<int>` citation in it, each one either removed in favour of an
   identifier or justified in place.
4. Any location stated is re-measured against the tree, not copied from this
   issue or from any comment. Record the method.
5. **Consider extending the existing citation-guard family** in
   `internal/handlers` — which already catches comments citing unresolvable
   paths and undefined test functions — to flag `<file>.go:<int>` citations in
   Go doc comments repo-wide. If you judge that out of scope or not worth it,
   say so explicitly with a reason rather than silently skipping it; that
   judgement is part of this issue's deliverable.
6. Comment-only. Prove it structurally: parse both revisions with comments
   excluded, compare bytes, tool proved falsifiable first and failing closed on
   empty input (§8 — three agents found genuine fail-opens in their own
   instruments this session).
7. No `.ClaimDue(` / `.OrphanSweep(` / `.SelectDue(` call-syntax literal
   introduced into any Go comment (`#0323`'s trap — documenting the pattern once
   inflated the measured population 35 → 36). Re-run
   `scripts/go_file_visit_floor_guard_test.sh` and record the population
   (currently 42 total / 12 non-exempt).
8. `gofmt` stability: file sha256 equals sha256 of `gofmt` stdout — these are
   declaration doc comments, exactly what §8's smart-quote gotcha rewrites.
