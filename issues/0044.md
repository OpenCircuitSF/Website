## Description

Turn a campaign's targeting into a fixed set of `email_sends` rows at send time — a snapshot, so the recipient list cannot shift underneath a running send.

## Plan

Written 2026-08-21 (phase 1, Opus). Status stays `open`.

### 0. Scope, and the boundary with the neighbouring issues

This issue owns exactly one thing: **the eligibility question — "which
subscribers may receive campaign N, and which address do we mail" — and the
SQL that answers it.** Everything that asks that question routes through this
package, so the answer can never be written twice and drift.

| Owns | Does not own |
|---|---|
| the four audience predicates and the eligibility gate | the `email_sends` table itself (`#0040`) |
| `Preview` (dry-run count + sample) | campaign CRUD, status transitions, audit rows (`#0041`) |
| `Materialize` (chunked, re-runnable) | the worker loop, throttling, SES, `sent`/`failed` transitions (`#0045`) |
| the **re-check at send time** and `skipped` | the compose UI (`#0047`), SSE progress (`#0048`) |
| `GET /admin/campaigns/{id}/audience` | rendering (`#0042`, `#0043`), test sends (`#0046`) |

New file: `internal/mailing/audience.go` (+ `audience_test.go`, + a `TestMain`
for the package — see §10). `internal/mailing` currently has no DB code at all;
this is the first store in it, so it follows `internal/subscribers`'
conventions rather than inventing new ones.

### 1. Materialize, not query-at-send — and where correctness actually lives

**Decision: materialize.** `Materialize` runs once, on the worker's first
claim of a campaign, and inserts one `email_sends` row per eligible
subscriber.

What it buys:

- **A stable audience.** The recipient set cannot shift under a send that
  takes minutes. A `LIMIT`/`OFFSET` walk over a live predicate can skip or
  repeat rows as subscribers change status mid-walk; a materialized set
  cannot.
- **Resumability without double-delivery.** `UNIQUE (campaign_id,
  subscriber_id)` plus a per-row `status` means a crashed worker restarts by
  reading rows, not by recomputing who was already mailed. That is `#0045`'s
  hardest criterion and it is only achievable against a fixed row set.
- **Honest totals.** `#0048` needs `sent / remaining / failed` and `#0047`
  needs a count the operator types to confirm. Both are `count(*)` over a
  fixed denominator, not a moving one.
- **Auditability.** Six months later, "who did campaign 12 go to" is a query,
  not an archaeology exercise against a taxonomy that has since changed.

What it costs: **staleness.** Between materialization and the moment a given
row is sent, a subscriber can unsubscribe, hard-bounce, complain, or be
manually suppressed. PRD §6.5 and CLAUDE.md §9 make that a correctness
question, not a performance one — *a suppressed or unsubscribed address must
not receive mail even though it is in the snapshot.*

**Therefore the snapshot is an optimization; it is never the authority.** The
authority is a re-check immediately before send:

> **Rule.** No message leaves this system without the eligibility predicate
> having been evaluated inside the same transaction that claims the row, after
> the claim, and before the SES call.

Concretely, `#0045`'s batch loop does:

1. `BEGIN`
2. `SELECT id, subscriber_id FROM email_sends WHERE campaign_id=$1 AND
   status='queued' ORDER BY id LIMIT $2 FOR UPDATE SKIP LOCKED`
3. `AudienceStore.RecheckEligibleTx(ctx, tx, campaignID, ids)` → `(recipients,
   skipped)` (§7)
4. `AudienceStore.MarkSkippedTx(ctx, tx, campaignID, skippedIDs, reason)` —
   sets `status='skipped'`, `error=<reason>`
5. `COMMIT`, then send only to `recipients`

Step 3 is this issue's code, not `#0045`'s, precisely so the predicate exists
once. `skipped` is already in PRD §6.2's `email_sends` status enum and nothing
else in the tracker claims it; **this issue defines its meaning: "was in the
audience at materialization, was no longer eligible at send time, never
mailed."** It is deliberately distinct from `failed` (we tried and SES
refused) so the campaign stats view (`#0049`) can tell "the list shrank under
us" from "delivery broke".

*Rejected — query-at-send.* Avoids staleness by construction, but forfeits
resumability, stable totals, and the audit trail, and makes the typed-count
confirmation in `#0047` a lie the moment it is displayed. The staleness it
avoids is fully closed by the re-check above at the cost of one indexed query
per batch of 50.

*Rejected — re-materializing periodically during a send.* Would pick up
subscribers who confirmed after the send started. That makes progress totals
move backwards on the operator's screen and mails people the confirmed count
never covered. **Materialize exactly once per campaign.** The "safely
re-runnable" criterion is about crash recovery (a worker that died mid-
materialization resumes and completes it), not about picking up new signups.
A subscriber who becomes `active` after materialization simply is not in this
campaign — which is the correct, explainable behaviour.

### 2. Where the suppression check lives: **both**, and why that is not belt-and-braces theatre

- **At materialization**, as `NOT EXISTS (SELECT 1 FROM suppressions x WHERE
  x.email = s.email)` — exactly PRD §6.6's anti-join. This keeps the count the
  operator confirms honest, and keeps rows that would only ever be `skipped`
  out of the queue.
- **At send**, inside the claim transaction, per §1. This is the one that is
  load-bearing for correctness. The materialization check could be deleted and
  no wrong mail would go out; delete the send-time check and it would.

Neither call site uses `SuppressionStore.IsSuppressed` — that method takes one
address and costs a round trip, which is right for `POST /api/subscribe`
(where `#0088`'s uniform timing depends on it) and wrong for a set-valued
question. Both call sites here express suppression as **SQL against the
`suppressions` table in the same statement**, so the check is set-based and
transaction-scoped.

**Reason-blind, deliberately.** `#0100` widened the key to `(email, reason)`;
`IsSuppressed`'s doc comment records the decision that the send gate does not
care *why* an address is blocked. This issue follows it exactly: the anti-join
carries no `reason` predicate, so any row of any reason blocks. A test asserts
this for all four reasons individually (§10), so a future refactor cannot
narrow it to `hard_bounce` without a red test.

Note this crosses a package boundary — `internal/mailing` writing SQL against
`suppressions`, a table `internal/subscribers` owns. That is a deliberate,
narrow exception to CLAUDE.md §1's "SQL lives in the store package that owns
the table": the alternative is either an N+1 `IsSuppressed` per recipient, or
pulling the whole suppression list into Go and filtering there, and both are
worse than one read-only anti-join. It stays read-only — nothing in this
package ever writes `suppressions`.

### 3. Eligible statuses: `active`, and nothing else

Against the actual vocabulary in `internal/subscribers/store.go` lines 57–62
(`StatusPending`, `StatusActive`, `StatusUnsubscribed`, `StatusBounced`,
`StatusComplained` — the full set, no others exist):

| Status | Eligible | Why |
|---|---|---|
| `pending` | **no** | Double opt-in (PRD §6.3) means consent is not yet evidenced. Mailing an unconfirmed address is the exact thing the confirmation step exists to prevent, and it is the failure mode that gets a domain blocked. A `pending` row is a *request* to subscribe, not a subscription. |
| `active` | **yes** | The only confirmed-consent state. |
| `unsubscribed` | no | Consent withdrawn (PRD §6.5). |
| `bounced` | no | Address is dead; also carries a `hard_bounce` or `repeated_soft_bounce` suppression (`#0038`, `#0039`, `#0109`). |
| `complained` | no | Terminal per CLAUDE.md §9; carries a `complaint` suppression; never auto-resubscribes. |

The predicate is written `s.status = 'active'` (equality against
`subscribers.StatusActive`, referenced through the constant, not a literal in
Go) rather than a `NOT IN` list. Equality is closed under future additions to
the vocabulary: a new status added later defaults to *not* receiving mail,
which is the safe direction. A `NOT IN` list would silently opt a new status
*into* receiving campaign mail.

`idx_subscribers_status` already exists (migration `000010`) and serves this.

### 4. How interests select: PRD §6.6's four modes, verbatim, and nothing more

**Decision: implement exactly `all`, `any_of`, `all_of`, `none_selected` as
PRD §6.6 tabulates them.** No expression language, no negation, no nesting, no
date or UTM predicates.

- `#0040` already constrains `audience_mode` to these four, and `#0047`'s UI
  is specified as "the four audience modes". A richer segment language is
  scope creep with no requester and it would immediately outrun the UI.
- The four cover the real cases: everyone; anyone interested in soldering *or*
  PCB design; the narrow intersection; and general announcements to people who
  picked nothing. PRD §6.1 is explicit that zero-interest subscribers are a
  valid, expected state, and this issue's own Notes call `none_selected` a
  real segment, not an error.

Predicates, with `s` = `subscribers` and `$n` = the campaign's interest ids as
a `bigint[]`:

| Mode | Predicate |
|---|---|
| `all` | `TRUE` |
| `any_of` | `EXISTS (SELECT 1 FROM subscriber_interests si WHERE si.subscriber_id = s.id AND si.interest_id = ANY($n))` |
| `all_of` | `(SELECT count(*) FROM subscriber_interests si WHERE si.subscriber_id = s.id AND si.interest_id = ANY($n)) = cardinality($n)` |
| `none_selected` | `NOT EXISTS (SELECT 1 FROM subscriber_interests si WHERE si.subscriber_id = s.id)` |

Edge cases, decided:

- **Empty interest set with `any_of` or `all_of` → typed error**
  (`ErrAudienceInterestsRequired`), no rows written, `/audience` answers `409`
  with an explicit message. `any_of` on an empty array selects nobody
  (harmless but useless); `all_of` on an empty array evaluates `0 = 0` for
  **every** subscriber and silently becomes `all` — a mode that mails the
  entire list when the operator selected nothing. That must be impossible, and
  a typed error at both the dry-run and the materialize call site makes it so.
- **Interests attached to an `all` or `none_selected` campaign are ignored**,
  and `AudiencePreview.Warnings` says so in words. Rejecting would be hostile
  to an operator who toggled modes after picking interests; ignoring silently
  would leave them believing a filter is applied. `#0047` renders the warning.
- **Deactivated interests still select.** `interests.active = false` hides an
  interest from the signup form; the `subscriber_interests` rows survive, and
  an operator who explicitly attached that id meant it. The predicate does not
  join `interests` at all.
- Unknown ids cannot occur — `campaign_interests.interest_id` is FK-constrained.
- Unknown `audience_mode` → `ErrUnknownAudienceMode` (defence in depth behind
  `#0040`'s `CHECK`), never a silently-empty or silently-`TRUE` predicate.

**Sharing the query is a structural guarantee, not a convention.** One
unexported builder produces the fragment for all three consumers:

```go
// audienceWhere returns the full eligibility+targeting predicate and its
// args, with placeholders numbered from argOffset+1 so the same fragment
// composes into statements that already bound earlier parameters.
func audienceWhere(aud Audience, argOffset int) (sql string, args []any, err error)
```

The `argOffset` parameter is the whole trick: `Materialize` binds
`$1 = campaign_id` before the predicate, `Preview` binds nothing, and without
an offset the two would need separately-numbered copies of the same SQL —
which is exactly how "share the query, do not write it twice" gets quietly
violated. A test asserts `Preview`'s count equals the number of rows
`Materialize` inserts over a randomized fixture (§9), so divergence is a red
test rather than a wrong send.

### 5. Schema: **no new migration.** `#0040` carries it.

`email_sends` is `#0040`'s table by its own acceptance criteria, and CLAUDE.md
§1's append-only rule means this issue must not touch that migration once it
has been applied. `#0040` is numbered lower and lands first.

What this issue **requires** of `#0040` (assumptions — verify before
implementing, do not trust this list over the file on disk):

1. `email_sends` exactly per PRD §6.2, including `UNIQUE (campaign_id,
   subscriber_id)` and `email TEXT NOT NULL`.
2. `status` constrained to `queued | sent | failed | bounced | complained |
   **skipped**`. If `#0040` ships a narrower `CHECK`, this issue's `skipped`
   transition fails at runtime — and then this issue adds its own
   `ALTER TABLE ... DROP CONSTRAINT / ADD CONSTRAINT` migration, appended after
   the highest number then on disk.
3. `idx_email_sends_queued ON email_sends (campaign_id, id) WHERE status =
   'queued'` — the partial index the claim in §1 step 2 walks.
4. `campaign_interests (campaign_id, interest_id)` with `ON DELETE CASCADE`,
   and `email_campaigns.audience_mode` constrained to the four modes.

**Highest migration on disk today is `000016_widen_soft_bounce_counting`**
(`#0109`). If a migration turns out to be needed after all, it is `000017` or
higher — re-run `ls migrations/` at implementation time rather than trusting
this sentence, since `#0040`–`#0043` land in between.

**No new indexes are needed.** The materialization scan uses
`subscribers_pkey` (keyset order), `idx_subscribers_status`,
`idx_subscriber_interests_interest`, and `suppressions`' own primary key —
whose leading column is still `email` after `#0100` widened it to
`(email, reason)`, so the anti-join is unaffected.

### 6. Per-recipient state and idempotency

`Materialize` writes only `(campaign_id, subscriber_id, email)`; everything
else takes its column default (`status='queued'`, `attempts=0`,
`error=NULL`, `sent_at=NULL`, `ses_message_id=NULL`). It never updates an
existing row.

The per-row lifecycle, and who owns each transition:

| From | To | Set by | When |
|---|---|---|---|
| — | `queued` | **this issue** | materialization |
| `queued` | `skipped` | **this issue** (`MarkSkippedTx`) | re-check failed at claim time |
| `queued` | `sent` | `#0045` | SES accepted; records `ses_message_id`, `sent_at` |
| `queued` | `failed` | `#0045` | 3 failed attempts |
| `sent` | `bounced` / `complained` | `#0038` | SES event joined on `ses_message_id` |

**Idempotency has three independent layers, and each one is load-bearing:**

1. **`ON CONFLICT (campaign_id, subscriber_id) DO NOTHING`** — re-running
   materialization after a crash inserts only the rows that are missing. It
   cannot resurrect, reset, or duplicate a row that already reached `sent`.
   This is why the insert never carries a `DO UPDATE`: any update clause here
   would be a path from `sent` back to `queued`, i.e. a double-delivery bug
   written into the schema.
2. **The claim is `FOR UPDATE SKIP LOCKED` on `status='queued'`** — two
   workers, or one worker and its restarted self, cannot claim the same row.
3. **`MarkSkippedTx` and `#0045`'s `sent`/`failed` updates are all guarded by
   `AND status = 'queued'`** — a row can leave `queued` exactly once. A
   restart that replays a batch finds zero rows still `queued` and updates
   nothing.

The residual window is unavoidable and worth naming: if the process dies
*after* SES accepts a message but *before* the `sent` update commits, the row
stays `queued` and is re-sent on restart. That is a duplicate delivery, not a
lost one — the correct trade for a mailing list, and the reason `attempts` is
incremented before the SES call rather than after (`#0045`'s concern; flagged
below).

### 7. Store interface

Narrow interfaces at the consumer, concrete store in `internal/mailing`,
per CLAUDE.md §1.

```go
// internal/mailing/audience.go
package mailing

const (
    AudienceAll          = "all"
    AudienceAnyOf        = "any_of"
    AudienceAllOf        = "all_of"
    AudienceNoneSelected = "none_selected"
)

var (
    ErrUnknownAudienceMode        = errors.New("mailing: unknown audience mode")
    ErrAudienceInterestsRequired  = errors.New("mailing: audience mode requires at least one interest")
    ErrCampaignNotFound           = errors.New("mailing: campaign not found")
)

type Audience struct {
    Mode        string
    InterestIDs []int64
}

type AudiencePreview struct {
    Count    int64
    Sample   []string // at most sampleLimit addresses, id order
    Warnings []string // e.g. "interests attached but ignored in mode 'all'"
}

type MaterializeResult struct {
    Inserted int64 // rows this call created
    Scanned  int64 // rows matching the predicate, including pre-existing
    Chunks   int
}

type Recipient struct {
    SendID, SubscriberID int64
    Email                string // the snapshot on email_sends
    ManageToken          string // read FRESH from subscribers — see below
}

type SkippedSend struct {
    SendID, SubscriberID int64
    Email, Reason        string
}

type AudienceStore struct {
    pool      *pgxpool.Pool
    chunkSize int // default materializeChunkSize (1000); settable in tests
}

func NewAudienceStore(pool *pgxpool.Pool) *AudienceStore

func (s *AudienceStore) LoadAudience(ctx context.Context, campaignID int64) (Audience, error)
func (s *AudienceStore) Preview(ctx context.Context, aud Audience, sampleLimit int) (AudiencePreview, error)
func (s *AudienceStore) Materialize(ctx context.Context, campaignID int64, aud Audience) (MaterializeResult, error)

func (s *AudienceStore) RecheckEligibleTx(ctx context.Context, q querier, campaignID int64, sendIDs []int64) ([]Recipient, []SkippedSend, error)
func (s *AudienceStore) MarkSkippedTx(ctx context.Context, q querier, campaignID int64, sendIDs []int64, reason string) (int64, error)
```

**Does this store need the `…Tx(ctx, querier, …)` idiom `#0033`/`#0038`
established? Yes — for two of the five methods, and for a stronger reason than
those two had.**

`SuppressionStore.AddTx` exists so a caller can commit two writes atomically.
Here the requirement is sharper: `RecheckEligibleTx` and `MarkSkippedTx` must
run **inside the transaction that holds the `FOR UPDATE SKIP LOCKED` claim**,
or the check is a TOCTOU with a real consequence — a subscriber who
unsubscribes between the check and the claim gets mailed. A pool-backed
`RecheckEligible` would be a footgun with no correct use, so **it is not
provided**; the only form is `…Tx`. The same `querier` interface
`internal/subscribers/suppressions.go` defines (`Exec`/`QueryRow`/`Query`,
satisfied by both `*pgxpool.Pool` and `pgx.Tx`) is redeclared unexported in
`internal/mailing`, matching the existing convention rather than exporting one
from `subscribers`.

`Preview` and `Materialize` are pool-backed only. `Materialize` deliberately
runs each chunk as its own implicit transaction (§8) — wrapping it in a
caller's transaction is exactly what the "does not hold a long transaction"
criterion forbids, so no `MaterializeTx` exists.

**`email` is snapshotted; `manage_token` is not.** The snapshot satisfies the
"`email` is snapshotted at materialization time" criterion and is the address
the audit trail records. `manage_token` is read fresh in `RecheckEligibleTx`
because PRD §6.5 rotates it on unsubscribe: a token captured at
materialization could be stale by the time the message is composed, producing
an email whose one-click unsubscribe link is dead on arrival — the single most
important link in the message. Reading it fresh is free (we are already
joining `subscribers` for `status`).

`RecheckEligibleTx` additionally requires `s.email = es.email`. Today there is
no email-change flow, so this cannot fire; it is one predicate that makes the
invariant explicit — **we mail the address we checked** — rather than leaving
it as an unstated consequence of two other facts.

### 8. Chunked materialization

One statement per chunk, no explicit `BEGIN`, keyset-paginated on
`subscribers.id`:

```sql
WITH page AS MATERIALIZED (
    SELECT s.id, s.email
      FROM subscribers s
     WHERE s.id > $2
       AND s.status = 'active'
       AND NOT EXISTS (SELECT 1 FROM suppressions x WHERE x.email = s.email)
       AND <targeting predicate>
     ORDER BY s.id
     LIMIT $3
),
ins AS (
    INSERT INTO email_sends (campaign_id, subscriber_id, email)
    SELECT $1, page.id, page.email FROM page
    ON CONFLICT (campaign_id, subscriber_id) DO NOTHING
    RETURNING subscriber_id
)
SELECT COALESCE(max(page.id), $2), count(*), (SELECT count(*) FROM ins)
  FROM page;
```

- **The cursor advances from `page`, not from `RETURNING`.** This is the trap:
  `RETURNING` yields only *inserted* rows, so a re-run whose whole chunk
  conflicts would return nothing, leave the cursor unmoved, and loop forever.
  Reading `max(id)` and `count(*)` from the materialized `page` CTE advances on
  rows *scanned*. `MATERIALIZED` is explicit so both references see one
  identical evaluation regardless of planner mood.
- **Termination:** stop when `scanned < chunkSize`. A test re-materializes an
  already-complete campaign with `chunkSize = 2` and asserts it terminates with
  `Inserted == 0` — the regression test for the infinite loop above.
- **Chunk size 1000**, a named constant, overridable on the struct so tests
  exercise multi-chunk paths with 2–3 rows instead of seeding 1001.
- Each chunk is a single autocommit statement, so no transaction spans the
  whole materialization. A crash leaves a partial audience; the next call
  resumes and `ON CONFLICT` makes the overlap free.
- Two workers racing the same campaign is safe (`ON CONFLICT`), though
  `#0045`'s campaign claim already makes it unlikely.
- `ctx` is honoured per chunk, so a shutdown stops between chunks.

### 9. HTTP: `GET /admin/campaigns/{id}/audience`

New `internal/handlers/admin_campaign_audience.go` — its own handler type and
file, following `AdminSuppressionsHandler`'s precedent rather than growing
`#0041`'s campaigns handler, so the store seam stays narrow:

```go
type campaignAudiencePreviewer interface {
    LoadAudience(ctx context.Context, campaignID int64) (mailing.Audience, error)
    Preview(ctx context.Context, aud mailing.Audience, sampleLimit int) (mailing.AudiencePreview, error)
}
```

- Response: `{"mode":…,"interest_ids":[…],"count":N,"sample":[…],"warnings":[…]}`.
- **Reads only. It never inserts an `email_sends` row** — that is the
  criterion, and it is also what makes the endpoint safe to poll from the
  compose screen on every checkbox change.
- `sampleLimit` is a **server-side constant of 20**, not a client parameter.
  A client-controlled limit turns a dry-run endpoint into a bulk export of the
  subscriber list through a route whose purpose is a count.
- `ErrCampaignNotFound` → `404`; `ErrAudienceInterestsRequired` /
  `ErrUnknownAudienceMode` → `409` with the message verbatim, so `#0047` can
  render it in its "unmet pre-send requirements" list rather than showing a
  greyed-out button with no reason.
- Mounted in `adminRoutes` behind a `nil` guard exactly like
  `adminInterestsH` / `adminSubscribersH` / `adminSuppressionsH`, so
  `STORAGE=json` (which has no subscribers backing at all — see
  `internal/devstore`'s package doc) simply omits the route. **No devstore work
  is in scope.**
- Admin-gated by the existing `requireSession` → `requireAdmin` chain;
  `admin_wiring_test.go`'s table-driven tests pick the new route up
  automatically.
- **No audit row.** A dry-run read is not an auditable mutation.
  Materialization is audited by `#0045` as part of the campaign-start event.

### 10. Tests

`internal/mailing` has no `TestMain` today; add one modelled on
`internal/subscribers/main_test.go` — `testdb.Lock()`, one shared
`testdb.Connect` pool, a single entry `TRUNCATE` of
`email_sends, campaign_interests, email_campaigns, subscriber_interests,
subscribers, suppressions RESTART IDENTITY CASCADE`, `t.Skip` when the pool is
nil. The advisory lock serialises this package's binary against
`internal/subscribers`', so the two truncates cannot interleave.

Per CLAUDE.md §8b: every test seeds its **own** throwaway rows —
`uniqueEmail(t)`-style nanosecond-suffixed addresses, a campaign created in
the test — and asserts against **captured ids**. **No test targets a literal
or seeded id.** Nothing here removes a guard, so the shared
`opencircuit_test` database is appropriate; no scratch database is needed.

1. **Four modes.** Seed subscribers across a small interest matrix; assert
   each mode selects exactly the expected id set. `all_of`: a superset
   subscriber matches, a subset subscriber does not. `none_selected`: a
   subscriber with one interest is excluded.
2. **Status exclusions, exhaustive.** One seeded subscriber per status —
   `pending`, `active`, `unsubscribed`, `bounced`, `complained` — under mode
   `all`. Assert only `active` is materialized, with `pending` and
   `complained` named in individual assertions so the failure message says
   which invariant broke.
3. **Suppression exclusion is reason-blind.** A table-driven case per reason
   (`hard_bounce`, `complaint`, `manual`, `repeated_soft_bounce`) on an
   otherwise-`active` subscriber; each is excluded.
4. **Re-running materialization** (the criterion). Materialize; mark one row
   `sent` by its captured id; materialize again. Assert: row count unchanged,
   `Inserted == 0`, and the `sent` row is still `sent` with its `sent_at`
   intact.
5. **Suppressed after materialization** — the test the whole design hangs on.
   Materialize with the subscriber eligible; then (a) add a suppression, and
   in a sibling case (b) unsubscribe the subscriber. Open a transaction, call
   `RecheckEligibleTx`, assert the row comes back in `skipped`, not
   `recipients`; call `MarkSkippedTx`; assert `status='skipped'` and that a
   second recheck returns it in neither list.
6. **Preview and Materialize agree.** Randomized fixture across all four
   modes: `Preview().Count` must equal the rows `Materialize` inserts. This is
   the executable form of "share the query, do not write it twice".
7. **`Preview` writes nothing.** `count(*)` on `email_sends` before and after
   is identical.
8. **Chunking.** `chunkSize = 2` over ~7 eligible subscribers: all are
   materialized, `Chunks > 1`; then re-run and assert it terminates with
   `Inserted == 0` (the all-conflicts cursor-advance regression).
9. **Empty interest set.** `any_of` and `all_of` with no interests →
   `ErrAudienceInterestsRequired` from both `Preview` and `Materialize`, and
   **zero rows written** — the `all_of`-becomes-`all` guard.
10. **Ignored interests warn.** `all` and `none_selected` with interests
    attached: full/expected result plus a non-empty `Warnings`.
11. **`ManageToken` is fresh.** Materialize, rotate the subscriber's
    `manage_token`, recheck; the returned `Recipient.ManageToken` is the new
    value. (Pair with `#0045`'s cross-contamination test.)
12. **Snapshot/live divergence.** Directly `UPDATE` a seeded `email_sends`
    row's `email` away from its subscriber's; recheck marks it ineligible.
