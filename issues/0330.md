## Description

`#0322` raised `claimKindsGuardMinPlausibleNonExemptCallSiteCount` from 6 to 8,
closing the specific gap it was filed for: a `mailing`-only scan-roots
narrowing yields 7 non-exempt call sites, which cleared a floor of 6 while
silently dropping `internal/handlers/subscribe_intake.go` — the caller whose
loss produced `#0254`'s duplicate-send defect.

That fix is correct for the narrowing it names. It does not close the class.

A **count** is a proxy for the property actually wanted, which is
**presence**: that `subscribe_intake.go`'s `ClaimDue`/`OrphanSweep` call sites
are in the scanned population. Any narrowing that happens to leave 8 or more
non-exempt sites standing still passes the floor while dropping the one site
the guard exists to protect. The floor gets stronger only by being raised, and
each raise costs headroom against ordinary growth.

`#0322`'s review measured that headroom and found there is **none**. Four of
the 12 non-exempt sites — not three, as `#0304` stated and `#0322` copied — are
the unrelated same-named `mailing.SendStore.OrphanSweep`, the fourth being
`internal/mailing/worker.go:575`. Renaming it leaves **8**: the floor sitting
exactly at its own population. Put the other way, 8 is precisely the count of
genuine non-collision outbox call sites outside the package, so **the floor's
entire margin is currently supplied by a name collision.**

The growth direction is worse than the shrink direction, and the review
demonstrated it: adding one ordinary, correctly-scoped
`ClaimDue` call to `internal/mailing` takes that package to 8, and the
mailing-only narrowing passes again — `go test` green, harness green,
population merely grown to 13. The shrink direction at least fails loudly. The
growth direction expires **silently**, one caller wide.

A guard that trips on an unrelated rename is a maintenance trap; a guard that
passes while dropping its subject is worse; this one now does both.

`#0275` is the opposite failure mode already on record — a floor above its
population — and the two together are the argument that counting is the wrong
instrument here.

## Root cause

`claimKindsGuardMinPlausibleNonExemptCallSiteCount` (`#0322`, currently 8) is a
count over the non-exempt population with no memory of *which* sites it
counted. `#0322`'s own doc comment already demonstrates the exploit: narrowing
`claimKindsGuardScanRoots` to `internal/mailing` alone plus adding one ordinary,
correctly-scoped call anywhere in `internal/mailing` reaches 8 non-exempt sites
again, silently, with `internal/handlers/subscribe_intake.go` — the caller
`#0254`'s duplicate-send defect came from — dropped from the walk entirely. A
count can never distinguish that state from a healthy one.

## Fix

Added a presence check, `claimKindsGuardRequiredNonExemptCallSites` (a named
`[]namedCallSite{ {file, method}, ... }` list) plus a loop in
`TestNoUnscopedOutboxClaimCallOutsidePackage` that asserts, by name, that each
required `(file, method)` pair is present among the real, non-exempt walk
results — not merely that the walk found "enough" sites. Retained the existing
count floor (`claimKindsGuardMinPlausibleNonExemptCallSiteCount`) alongside it,
per acceptance criterion 5: it is the coarse "did the walk even run" backstop
(an empty `allSites` slice makes every presence lookup report "not found" for
the same reason a broken walk would, so the presence check alone cannot
distinguish "walk broken" from "walk fine, but this one file dropped" without
the floor's help), while the presence check is the precise "did it find the
ONE caller that matters" check a count structurally cannot express.

**Oracle placement (criterion 3) — deliberate, not by convention.** Per
`CLAUDE.md` §8's own distinguishing question — does the mutation change what
the walk *finds*, or only the threshold the result is compared against —
this split into two different homes:

- **In Go, in-package** (`TestPresenceCheckCatchesMailingOnlyNarrowing`, a
  permanent standing test alongside `TestNonExemptFloorCatchesScanRootsNarrowedToSelf`):
  narrowing `claimKindsGuardScanRoots` changes `got` itself — the walk
  genuinely finds different files — so an in-package `go test` is a
  legitimate, non-circular oracle for that mutation class, exactly as the
  existing `{"."}`-narrowing test already is for the count floor. Proved
  directly (not merely asserted) in a throwaway `git worktree`: narrowing to
  `{"../mailing"}` plus one added, correctly-scoped call reaches 8 non-exempt
  sites (satisfying the OLD count floor) while `subscribe_intake.go` is
  dropped — and the new presence check, not the floor, is what fails,
  confirming it closes a gap the floor alone does not. See `## Verification`.
- **External harness, `scripts/go_file_visit_floor_guard_test.sh`** (new
  `#0330` section, textual/grep-based, never parses Go): the mutation class an
  in-package test *cannot* prove anything about is an edit to
  `claim_kinds_call_site_guard_test.go` itself — weakening or emptying
  `claimKindsGuardRequiredNonExemptCallSites`, or the loop that checks it —
  since that is an edit to the guard's own subject, and an assertion living
  entirely inside that file can be satisfied by editing the same file. This
  section (a) independently confirms via `grep` on the real
  `internal/handlers/subscribe_intake.go` production source (never the guard,
  never go/ast) that the `OrphanSweep`/`SelectDue` calls it claims are
  present really exist; (b) confirms the tracked guard file's required-list
  literally names both, via an anchored line-shape grep that cannot also
  match prose describing the same file; (c) mutates a private copy with
  those two lines removed and confirms the same extraction detects zero,
  proving the check is falsifiable. This is the same shape
  `scripts/go_file_visit_floor_guard_test.sh` already uses for the three
  `#0300` floors and the two `#0304`/`#0322` outbox floors — reused rather
  than reinvented, since `extract_const`'s helpers (`sha_of`,
  `fatal`/`fail`/`pass`) already exist in that file.

**Criterion 4 (fail closed).** The presence loop's default is "not found";
an empty `claimKindsGuardRequiredNonExemptCallSites` fails closed explicitly
(`t.Fatal`, mirroring the existing `claimKindsGuardScanRoots`-empty check).
The harness's ground-truth grep and required-list extraction both call
`fatal` on a non-numeric result, matching every other extraction in that
script.

**Criterion 6 (no population inflation).** The new Go identifiers use bare
string literals (`"OrphanSweep"`, `"SelectDue"`) with no leading `.` or
trailing `(`, so `scripts/go_file_visit_floor_guard_test.sh`'s
`count_outbox_call_sites` grep pattern (`\.(ClaimDue|OrphanSweep|SelectDue)\(`)
does not match them. Confirmed by re-running the harness after the change:
total population still 42, non-exempt still 12, both unchanged. Also
confirmed by grepping the diff's added (`+`) lines directly for the call
syntax — zero hits.

## Acceptance criteria

1. The guard asserts **by name** that `internal/handlers/subscribe_intake.go`'s
   ~~`ClaimDue` and `OrphanSweep`~~ call sites appear in the non-exempt population,
   not merely that the population is large enough.

   **Correction (implementation pass, 2026-08-31).** This criterion's own
   method names were stale by the time this issue was implemented.
   `#0297`/`#0303` moved `subscribe_intake.go` off `ClaimDue` onto the
   per-row claim path, so its two guarded calls today are `OrphanSweep`
   (`:246`) and `SelectDue` (`:260`) — **zero** calls to `ClaimDue`. Measured
   independently for this pass with a standalone `go/ast` census (not
   copied from this issue, `#0345`, or any other prose): 269 files visited,
   36 total call sites, 12 non-exempt — reproducing `#0345`'s review census
   exactly. The criterion's *intent* (assert by name that this file's real
   guarded calls survive a narrowing) is what was implemented, against the
   real call sites (`OrphanSweep`, `SelectDue`), not the stale pair named
   above.
2. The assertion fails when scan roots are narrowed to any set excluding that
   file — proven by mutation, with the mutation reverted afterward.
3. The oracle for the expected call sites lives **outside** the file it
   protects, per `#0300` and `CLAUDE.md` §8: a copy of the answer stored next
   to the question is not a check. An edit to the guard's subject must not be
   able to satisfy the oracle.
4. An empty or zero-match extraction fails closed and is never treated as a
   passing input (§8, `#0275`).
5. If the count-based floor is retained alongside the presence check, its value
   is justified against measured headroom and the justification names what
   ordinary growth would trip it.
6. The presence check does not itself reproduce the `.ClaimDue(`/`.OrphanSweep(`
   substrings in a way that changes the population it measures — `#0323` hit
   exactly this, where documenting the pattern inflated the grep count 35 to 36.
