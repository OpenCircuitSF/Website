## Description

`.env.example` line 3 sets `BASE_URL=https://opencircuitsf.com` — the **apex**. Since `#0019`, that value is the source of every `og:url`, every `og:image`, every sitemap `<loc>`, and the `Sitemap:` line in `robots.txt`.

Production canonicalizes to **www**: the apex 301s to `https://www.opencircuitsf.com` (`CLAUDE.md` §7, verified against the live host). `deploy/systemd/README.md` states that `/etc/opencircuit/config.env` "supplies every variable from `.env.example`", so following the documented deploy path publishes canonical URLs that contradict the site's own redirect.

Found during `#0019`/`#0020`'s review. `internal/seo` is correct — it faithfully uses whatever `BASE_URL` provides. This is a one-line config defect with disproportionate consequences.

## Why it matters

Social crawlers and search engines are the entire audience for `#0019`'s work. Publishing apex `og:url` values against a 301 means every shared link and every indexed page advertises a URL that immediately redirects — diluting the canonical signal at exactly the moment the site starts receiving traffic. It is cheap to fix now and expensive to unwind once links are in the wild.

The same file already gets `WEBAUTHN_RP_ORIGIN=https://www.opencircuitsf.com` right, so this is an internal inconsistency rather than a considered choice.

## Fix

`.env.example`'s `BASE_URL` changed from `https://opencircuitsf.com` to `https://www.opencircuitsf.com`, with the surrounding comment expanded to state what it drives (`og:url`, `og:image`, sitemap `<loc>`, `robots.txt`'s `Sitemap:` line) and that it must match the browser's real host, mirroring `WEBAUTHN_RP_ORIGIN`'s existing warning. `docs/configuration.md`'s `BASE_URL` row got the same summary plus a new gotcha paragraph next to the existing WebAuthn one. `internal/seo` was not touched — it already trusts `BASE_URL` uniformly; confirmed by reading `seo.go`, `site.go`, `sitemap.go`, and `robots.go` in full.

**Audit of every other host-valued placeholder in `.env.example`:**

| Variable | Value | Verdict |
|---|---|---|
| `WEBAUTHN_RP_ID` | `opencircuitsf.com` (apex) | Correct as-is — deliberately the apex so one passkey covers both hosts; already documented |
| `WEBAUTHN_RP_ORIGIN` | `https://www.opencircuitsf.com` | Already correct |
| `EMAIL_FROM` / `EMAIL_REPLY_TO` | `hello@opencircuitsf.com` (apex) | Not a web-redirect concern — mail delivery follows MX records at the apex, not the HTTP 301; no inconsistency |
| `EMAIL_LIST_DOMAIN` | `lists.opencircuitsf.com` | Deliberate dedicated subdomain per `CLAUDE.md` §9 ("never point the apex MX at SES") — correct |
| `SES_INBOUND_BUCKET` | `opencircuitsf-inbound` | S3 bucket name, not a host at all |
| `DATABASE_URL` | `localhost` | Local dev placeholder, unrelated to the public site's canonical host |
| `ADMIN_EMAIL` | `you@example.com` | Generic placeholder, unrelated |

No other apex/www inconsistency found. `BASE_URL` was the sole defect.

Added `TestSite_EmittedURLsShareConfiguredHost` in `internal/seo/site_test.go`, which constructs a `Site` with a distinctive base URL (`https://configured-host.example.test`, used nowhere else in the package's tests) and asserts that `og:url`/`og:image` for both static and workshop-detail routes, every sitemap `<loc>`, and robots.txt's `Sitemap:` line all share that exact host. This guards the invariant the issue is about — a future change that hardcodes or drifts one of the four emission points away from the configured `BASE_URL` fails this test, rather than shipping.
