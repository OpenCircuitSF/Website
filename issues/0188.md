## Description

`#0185` split send failures into "ours" (fixed text), "unreachable" (fixed text), and "SES said this" (verbatim). The verbatim branch is the one nobody has tested with a **production-shaped** error.

Both committed tests wrap a **bare** modeled exception (`&types.MessageRejected{}`), which the AWS SDK never produces on its own. In production the value is nested: `smithy.OperationError.Error()` formats as `"operation error %s: %s, %v"`, and `awshttp.ResponseError.Error()` as `"https response error StatusCode: %d, RequestID: %s, %v"`. So a real failed row reads:

```
operation error SES v2: SendEmail, https response error StatusCode: 400, RequestID: <uuid>, MessageRejected: Email address is not verified
```

`#0185`'s reviewer confirmed by probe that the `operation error SES v2: SendEmail, ` half **survives the prefix strip**.

This is not a regression — `#0182` behaved identically, and its pass-2 review proved the property using the same bare shape. It is `#0185`'s **own complaint** ("implementation detail an admin cannot act on") surviving on the branch `#0185` chose not to touch, hidden because the tests use a shape production never emits.

**And it is now trivially fixable**, because the code already holds `apiErr`: `apiErr.ErrorCode() + ": " + apiErr.ErrorMessage()` yields exactly what both existing tests assert, while also being right for real errors.

**Two smaller items from the same review:**

- **The transport branch discriminates on a string prefix while the branch above it discriminates on a type.** `errors.As(err, &*smithy.OperationError)` would classify bare SDK transport errors correctly and make the whole function type-based.
- **The catch-all log has no `send_id`**, unlike every other error log in `worker.go`. Moving it to `sendOne`'s call sites would fix that and let it use `w.log` rather than `slog.Default()` — the reviewer ruled the logger choice correct as shipped (they are the same logger in production), so `send_id` is the real gap.

## Root cause

`adminSendErrorMessage`'s `smithy.APIError` branch built its return value by
calling `strings.CutPrefix(err.Error(), sesWrapPrefix)` — stripping only this
package's own `"mailing: sending via SES: "` prefix off the *formatted*
error string. That works when the modeled exception is the outermost thing
`err` wraps (`Error()` == `"MessageRejected: Email address is not
verified"`), which is exactly the bare shape every test before this issue
constructed. It never worked for what production actually returns:
smithy-go's `Client.Invoke` wraps every operation error in
`*smithy.OperationError` (`Error()` prepends `"operation error SES v2:
SendEmail, "`), and over HTTP the response deserializes into
`*awshttp.ResponseError` as well (`Error()` prepends `"https response error
StatusCode: 400, RequestID: <uuid>, "`). Stripping only the outer
`sesWrapPrefix` left both of those layers in front of the SES text, so a
real rejection reached `failed_sends[].error` as `"operation error SES v2:
SendEmail, https response error StatusCode: 400, RequestID: <uuid>,
MessageRejected: Email address is not verified"` — implementation detail an
admin cannot act on, which is precisely what `#0182`/`#0185` set out to keep
out. Confirmed via `go doc`/source read of
`sesv2/types@v1.66.6`, `smithy-go@v1.27.8`, and
`aws-sdk-go-v2@v1.43.6/aws/transport/http`: every modeled exception's
`Error()` is `fmt.Sprintf("%s: %s", ErrorCode(), ErrorMessage())`, so reading
those two methods directly reaches the same text the strip was aiming for,
regardless of how deep the SDK nests the exception.

## Fix

- **`adminSendErrorMessage`'s `smithy.APIError` branch** now returns
  `apiErr.ErrorCode() + ": " + apiErr.ErrorMessage()` instead of re-parsing
  `err.Error()`. This produces byte-identical output to the old code for a
  bare exception (both existing tests still pass unmodified in spirit) and
  is correct for a nested one, because it reads the exception's own fields
  rather than any wrapper's formatted string.
- **Transport discriminator, decided:** switched from
  `strings.HasPrefix(err.Error(), sesWrapPrefix)` to
  `errors.As(err, &opErr)` against `*smithy.OperationError`. This makes the
  whole function type-based — every branch now keys off the error's shape
  via `errors.Is`/`errors.As`, none off `err.Error()` text — and is strictly
  more correct: a `Mailer` other than `SESMailer` that returns a bare
  `*smithy.OperationError` (no `sesWrapPrefix`) now correctly classifies as
  unreachable instead of falling through to the catch-all. Verified the
  behavior is unchanged for every case the old string check handled: a bare,
  unwrapped transport error (e.g. `*net.OpError` with no prefix) still falls
  through to the catch-all under both implementations, since it is not
  itself wrapped in `*smithy.OperationError` either.
- **Catch-all log, decided:** `adminSendErrorMessage` now takes
  `(log *slog.Logger, sendID int64, err error)` instead of reaching for
  `slog.Default()` internally. Both call sites in `sendOne` pass `w.log` and
  `r.SendID`, so the catch-all log line now carries `send_id` like every
  other error log in `worker.go`. `w.log` is `slog.Default()` in production
  and in every test that doesn't inject its own logger (`NewWorker`'s
  fallback), so this is not a behavior change to *which* logger is used —
  only to what it's told.
- Updated the doc comments on `adminSendErrorMessage`, `sesWrapPrefix`, and
  `adminSendUnreachableMessage` to describe the new (type-based, field-read)
  behavior instead of the string-prefix one. `sesWrapPrefix` itself is kept
  as a documented constant (still accurately describes what `SESMailer.Send`
  emits) even though `adminSendErrorMessage` no longer inspects it.
