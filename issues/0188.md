## Description

`#0185` split send failures into "ours" (fixed text), "unreachable" (fixed text), and "SES said this" (verbatim). The verbatim branch is the one nobody has tested with a **production-shaped** error.

Both committed tests wrap a **bare** modeled exception (`&types.MessageRejected{}`), which the AWS SDK never produces on its own. In production the value is nested: `smithy.OperationError.Error()` formats as `"operation error %s: %s, %v"`, and `awshttp.ResponseError.Error()` as `"https response error StatusCode: %d, RequestID: %s, %v"`. So a real failed row reads:

```
operation error SES v2: SendEmail, https response error StatusCode: 400, RequestID: <uuid>, MessageRejected: Email address is not verified
```

`#0185`'s reviewer confirmed by probe that the `operation error SES v2: SendEmail, ` half **survives the prefix strip**.

This is not a regression — `#0182` behaved identically, and its pass-2 review proved the property using the same bare shape. It is `#0185`'s **own complaint** ("implementation detail an admin cannot act on") surviving on the branch `#0185` chose not to touch, hidden because the tests use a shape production never emits.

**And it is now trivially fixable**, because the code already holds `apiErr`: `apiErr.ErrorCode() + ": " + apiErr.ErrorMessage()` yields exactly what both existing tests assert, while also being right for real errors.

**Two smaller items from the same review:**

- **The transport branch discriminates on a string prefix while the branch above it discriminates on a type.** `errors.As(err, &*smithy.OperationError)` would classify bare SDK transport errors correctly and make the whole function type-based.
- **The catch-all log has no `send_id`**, unlike every other error log in `worker.go`. Moving it to `sendOne`'s call sites would fix that and let it use `w.log` rather than `slog.Default()` — the reviewer ruled the logger choice correct as shipped (they are the same logger in production), so `send_id` is the real gap.

## Acceptance criteria

- [ ] A genuine SES rejection reaches `failed_sends[].error` as the code and message an admin can act on, with no `operation error …` / `https response error StatusCode: …, RequestID: …` scaffolding
- [ ] **The tests use a production-shaped error** — a modeled exception nested inside `smithy.OperationError` and `awshttp.ResponseError`, as the SDK actually returns. This is the criterion that matters; the current tests pass against a shape that never occurs
- [ ] The existing bare-exception cases still behave, so a test double stays usable
- [ ] Decide on the type-based transport discriminator, and record the reasoning
- [ ] The catch-all log carries `send_id`
- [ ] `ISSUE=0188 scripts/check.sh go ./internal/...` passes with zero skips
