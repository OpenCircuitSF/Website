# 0288 — MarkDone does not clear the error from a failed attempt

## Description

`#0272` made `MarkSent` clear `error = NULL` in the same `UPDATE` that sets
`status='sent'`, so a row is never observable as sent-with-error.

**`outbox.Store.MarkDone` has the same shape and was not changed.** It also
transitions a row to `status='sent'` — from `queued` *or* `sending` — and blanks
the payload, but it leaves `error` populated. It is called from
`internal/handlers/subscribe.go:571`.

`#0272`'s reviewer confirmed this is reachable, not theoretical: the recovery
poller claims an intake row, fails it via `MarkRetryOrAbandon` (which writes the
error and puts the row back to `queued`), and then the request's fast path
`MarkDone`s that same row — the convergence `subscribe.go`'s own comment
anticipates. The row ends up `sent` carrying the error from an attempt that was
subsequently superseded.

This was **not** a `#0272` bounce: that issue's criterion 1 names `MarkSent`
specifically, and its fix is correct and complete for what it specifies.

## Acceptance criteria

1. `MarkDone` clears `error` in the same `UPDATE` that sets `status='sent'` and
   blanks the payload. One statement, not a follow-up write.
2. The `queued` → `sent` and `sending` → `sent` transitions both clear it —
   `MarkDone` admits either source state and both are reachable.
3. `MarkRetryOrAbandon` stays untouched. A `queued` row awaiting retry and a
   terminal `abandoned` row must both still keep their error, exactly as
   `#0272` established.
4. A DB-backed test drives the real convergence: fail an intake row through
   `MarkRetryOrAbandon`, then `MarkDone` it, then assert `error IS NULL` while
   the sent-state columns are set.
5. Note that [#0283](0283.md) is open on `MarkSent`'s WHERE predicate. This
   issue is the SET clause only — do not pre-empt that decision.
6. `ISSUE=NNNN scripts/check.sh go ./internal/... ./cmd/opencircuit/...` passes
   with no skips.
