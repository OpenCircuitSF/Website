## Description

Measured on production, 2026-09-12:

- Every public page is served as an empty shell. The `<body>` of `GET /` is
  exactly `<div id="app"></div>`; all visible text is rendered by the SPA.
- The SPA fetches that text from the API (`web/src/lib/api.ts`):
  `/api/workshops`, `/api/workshops/{slug}`, `/api/archive`,
  `/api/archive/{slug}`, and `/api/interests`.
- `robots.txt` (`internal/seo/robots.go`) says **`Disallow: /api`**.

Googlebot renders JavaScript, but it does **not** fetch resources that
`robots.txt` disallows. So when Google renders `/archive/09-2026` or a workshop
page, the request for its content is never made, and the rendered page has a
header and footer but none of the newsletter or workshop text. The meta tags
from `#0019` survive, because they are in the raw HTML; the body does not.

`/api` was disallowed as an obvious private namespace (`#0020`); nothing in its
rationale needs the **public, read-only, token-free** endpoints blocked. The
token-bearing reason `#0020` gives applies to `/confirm`, `/preferences`, and
`/unsubscribe`, not to these.

This is the quick, high-value half of the problem. `#0519` covers the larger
half — crawlers that do not run JavaScript at all.

## Resolution notes

> 🟢 Resolved 2026-09-12 — the three public read-only API prefixes are allowed back out of `Disallow: /api`, nothing private became crawlable, and every `/api/` response now carries `X-Robots-Tag: noindex`, verified over a live `mountAndServe`. Criterion 6 is a post-deploy Search Console check for the user and stays unchecked.

## Root cause

`internal/seo/robots.go`'s `disallowedPaths` treated `/api` as one
undifferentiated private namespace, blocking Googlebot from fetching the
three public, read-only, token-free endpoints (`/api/workshops`,
`/api/archive`, `/api/interests`) that `web/src/lib/api.ts` fetches to
render every archive and workshop page's actual content. Googlebot renders
JavaScript but never fetches a robots-disallowed resource while doing so, so
the rendered page kept its header/footer (from the SPA shell's static markup
and `#0019`'s meta tags) but lost the body text entirely.

## Fix

- `internal/seo/robots.go`: added `allowedAPIPaths` (`/api/workshops`,
  `/api/archive`, `/api/interests`) and appended explicit `Allow:` lines for
  them in `BuildRobotsTxt`, carving them back out of the blanket
  `Disallow: /api` (Google/Bing resolve conflicting directives by longest
  match, not line order, so no existing line needed to move). The doc
  comment on `allowedAPIPaths` carries the full route-by-route audit below.
- `internal/seo/robots.go`: added `NoIndexAPIMiddleware`, which sets
  `X-Robots-Tag: noindex` on any request whose path starts with `/api/`,
  before calling the wrapped handler.
- `cmd/opencircuit/main.go` (`mountAndServe`): wrapped the whole `mux` in
  `seo.NoIndexAPIMiddleware` — one call site, applied before the (usually
  nil) dev auto-login `outerMiddleware` — so the header applies
  unconditionally to every `/api/*` route without any handler needing to set
  it, and a future route added to `/api` inherits it automatically.
- `docs/seo.md`'s `## Sitemap and robots.txt` section now documents both the
  `Allow` carve-out and the `X-Robots-Tag` header.

### Criterion 2 — full `/api` route audit

Enumerated from `cmd/opencircuit/main.go`'s `mountAndServe` (the only place
routes are registered — confirmed by grepping the whole tree for
`mux.Handle`/`mux.HandleFunc`). Admin routes live under `/admin/*`, not
`/api/*`, so they cannot be reached by any `/api` prefix at all.

| Route | Verdict | Why |
|---|---|---|
| `GET /api/workshops` | **Allowed** | public, read-only, no token |
| `GET /api/workshops/{slug}` | **Allowed** (via `/api/workshops` prefix) | public, read-only, no token |
| `GET /api/archive` | **Allowed** | public, read-only, no token |
| `GET /api/archive/{slug}` | **Allowed** (via `/api/archive` prefix) | public, read-only, no token |
| `GET /api/interests` | **Allowed** | public, read-only, no token |
| `GET /api/me` | Disallowed | `requireSession` — session-gated |
| `GET /api/events` | Disallowed | `requireAdmin` — admin-gated SSE stream |
| `POST /api/subscribe` | Disallowed | state-changing (writes a pending subscriber) |
| `POST /api/subscribe/confirm` | Disallowed | token-bearing (confirmation token) |
| `GET`/`PATCH /api/preferences` | Disallowed | token-bearing (preferences token) |
| `GET`/`POST /api/unsubscribe` | Disallowed | token-bearing (unsubscribe token) |
| `GET /api/list-stats` | Disallowed | public and read-only, but not one of the three endpoints public pages render from — left out per criterion 1's exact list |
| `GET /api/crt-session` | Disallowed | same as `/api/list-stats` |
| `POST /api/ses/notifications` | Disallowed | server-to-server SNS webhook |
| `POST /api/ses/inbound` | Disallowed | server-to-server SES webhook |

No allowed prefix catches anything unintended by a **prefix match** either:
the only routes beginning with `/api/workshops`, `/api/archive`, or
`/api/interests` are the ones already marked Allowed above — there is no
`/api/workshops-*`, `/api/archive-*`, or `/api/interests-*` sibling route
that a prefix match would sweep in. `internal/seo/robots_test.go`'s
`TestBuildRobotsTxt_TokenAndPrivateAPIEndpointsStayDisallowed` pins this
same table (minus the admin routes, which are a different namespace
entirely) as a running assertion, including the explicit
`strings.HasPrefix` check against each allowed prefix.

## Review notes

Phase-3 review, Opus, 2026-09-12. **Approved.** Everything below was
re-derived independently, not taken from the drafted sections.

**Route audit (criterion 2): holds.** `mountAndServe` in
`cmd/opencircuit/main.go` is the only route registration site. A tree-wide
grep of non-test Go for `.Handle(` / `.HandleFunc(` finds nothing outside it,
and there is exactly one `http.NewServeMux`. It registers seventeen `/api`
routes, and they match the implementer's table. Every path literal inside
`adminRoutes` (67 of them) starts with `/admin`, so no admin route is
reachable by an `/api` prefix at all. The only registered paths starting with
`/api/workshops`, `/api/archive` or `/api/interests` are the list and
`{slug}` GETs, so the prefix match sweeps in nothing unintended. Each of the
three is public, unauthenticated, read-only and token-free.

**Rule ordering: no change required.** RFC 9309 specifies longest match, and
Google, Bing and CPython 3.14's `urllib.robotparser` all implement it. Fed
both orderings, CPython gives identical answers. For a strict first-match
crawler, ordering is moot here: the pre-existing `Allow: /` line (from
`#0020`, not this change) matches every path first. Simulated, such a crawler
is allowed `/admin`, `/confirm` and `/api/me` under both the shipped order
and the Allow-before-Disallow order. Moving the three `Allow` lines up would
therefore change nothing for any crawler. The only first-match-safe form
would be dropping or moving the redundant `Allow: /`, which predates this
issue and is out of scope; see the follow-up below.

**Content coverage (criterion 1): complete for indexable text.** Public views
fetch from the API as follows:

- `ArchiveIndex` and `ArchiveEntry` use `/api/archive`.
- `WorkshopsIndex`, `WorkshopDetail` and Home's next-up section use
  `/api/workshops`.
- `SubscribeForm` uses `/api/interests`.

The only disallowed read endpoints a public page touches are
`/api/crt-session` and `/api/list-stats`, both used by Home's CRT. That
screen is drawn with `fillText` onto two `<canvas>` elements inside an
`aria-hidden` plane. It is decorative, not DOM text, so allowing those
endpoints would add nothing a crawler can index. Leaving them disallowed is
correct.

**Noindex header (criterion 3): proved over the real wiring.** In a
throwaway worktree at `2531cc9`, with its own scratch database, a review-only
test (not committed) drove the real `mountAndServe` on a live socket. It
compared against the literal string `noindex`, not anything from
`internal/seo`.

- **Carried the header:** `GET /api/me` → 401, `GET /api/events` → 401,
  `POST /api/me` → 405, `GET /api/does-not-exist` → 404.
- **No header:** `/`, `/archive/09-2026`, `/workshops/soldering-101`,
  `/sitemap.xml`, `/robots.txt` and `/health`. Bare `/api` and `/apiary` also
  carry none, which is correct.
- **Served `robots.txt`:** matches the body in `## Verification` byte for
  byte.

Two mutations, both in the worktree only:

- **Wrapper removed from `mountAndServe`:** the review test failed on all
  five `/api` requests, but the shipped `internal/seo` and `cmd/opencircuit`
  suites both stayed `ok`.
- **Middleware prefix broken:** the shipped unit test failed, as it should.

So the unit test's oracle is independent and does catch a broken function.
**Nothing in the tree catches the wiring being removed.** That is a missing
regression guard, not a defect in the shipped behaviour, which is verified
correct, so it does not block. It is the first follow-up below.

**Docs (criterion 5): accurate, with one nit.** `docs/seo.md` records why the
three endpoints are allowed, and the `allowedAPIPaths` doc comment explains

`/api/crt-session`, which are none of those. They are public, read-only
endpoints left disallowed because no indexable text depends on them. The Go
doc comment says this correctly.

## Acceptance criteria

1. `robots.txt` adds `Allow` lines for exactly the public read-only endpoints
   public pages render from: `/api/workshops`, `/api/archive`, and
   `/api/interests`. Google and Bing both resolve `Allow`/`Disallow` by
   longest match, so these override `Disallow: /api` without reordering.
2. **Everything else under `/api` stays disallowed.** Enumerate the API's route
   table and confirm no allowed prefix covers an admin, auth, account, or
   token-bearing endpoint — including anything a prefix match would catch
   unintentionally.
3. API responses carry `X-Robots-Tag: noindex`, so crawlers may *fetch* the JSON
   to render a page without indexing the JSON itself as a search result.
4. `internal/seo`'s robots test asserts the new `Allow` lines and that the
   private namespaces remain disallowed.
5. `docs/seo.md`'s `## Sitemap and robots.txt` section records why these
   endpoints are allowed.
6. **Post-deploy, verified by the user:** Search Console → URL Inspection →
   *Test live URL* on `/archive/09-2026` shows the newsletter text in the
   rendered HTML and lists no blocked resources.
7. `ISSUE=NNNN scripts/check.sh go ./internal/seo/... ./internal/handlers/...`
   passes with no skips.
