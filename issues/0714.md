## Description

`scripts/ship.sh 0.16.1 --yes` deployed successfully on 2026-11-17 (`scripts/deploy.sh` printed "healthy after 2/10 attempt(s)" and confirmed the running process was the deployed binary), yet `ship.sh` itself exited **141**.

`scripts/ship.sh` line 62 runs `yes y | scripts/deploy.sh "$VERSION"` under `set -euo pipefail`. When `deploy.sh` exits, `yes` is still writing and dies of SIGPIPE (128 + 13 = 141). `pipefail` makes the pipeline report that status, so a successful deploy reads as a failure. This is the same false-alarm class `#0712` fixed for the health check: an operator trained to ignore a red exit misses the real one.

## Plan

1. `scripts/ship.sh`: replace `yes y | scripts/deploy.sh "$VERSION"` with
   `{ yes y || true; } | scripts/deploy.sh "$VERSION"`. Under `pipefail` the
   pipeline status is then `deploy.sh`'s own, so a real deploy failure still
   fails `ship.sh` with deploy's exit code. Add a one-line comment citing `#0714`
   and SIGPIPE. Do not use `exec` here or restructure the `--yes` branch.
2. New external guard `scripts/ship_sigpipe_guard_test.sh` (bash 3.2-safe,
   modelled on `scripts/deploy_health_guard_test.sh`):
   - Static: `ship.sh` contains the line `{ yes y || true; } | scripts/deploy.sh "$VERSION"`
     exactly once, and no line matching a bare `yes y |` pipe into `deploy.sh`
     (oracle is a regex/grep, not a heredoc copy of the subject — AGENTS.md §8).
   - Behavioural: in `bash -c 'set -euo pipefail; …'`, with a stub reader that
     exits immediately without reading, prove the old shape exits 141, the new
     shape exits 0 when the stub exits 0, and the new shape exits 3 when the
     stub exits 3 (a real failure still propagates).
   - Print PASS/FAIL lines and exit non-zero on any failure.
3. Wire it into `scripts/check.sh`'s `guards` arm next to the `#0712` entry, and
   add it to the header comment list near line 33 that names the guard scripts.
4. Verify: `bash -n` and run the new guard directly; `scripts/check.sh guards`
   (or, if `dev_guard_test.sh`'s port is busy, run the new guard plus
   `scripts/check_guard_test.sh` directly and say so); prove the guard fails
   against a copy of `ship.sh` with the old line (copy to the scratchpad and
   point the guard at it via an env override, e.g. `SHIP_SH=...`; never edit
   the tracked file to mutate).

Files: `scripts/ship.sh`, `scripts/ship_sigpipe_guard_test.sh` (new), `scripts/check.sh`.

## Review notes

Reviewed 2026-11-17 against `a5c7d2ad`, every command run under `bash` 3.2.57, load average 3.4.

- **The fix is correct and stays narrow.** Under `set -euo pipefail` the pipeline status is the rightmost non-zero member. The `|| true` makes the producer group exit 0 even when `yes` is killed by SIGPIPE, so the status is `deploy.sh`'s own. A reader that reads one line, sleeps and then exits (closer to `deploy.sh` than the guard's stub) gives: old shape exits 141 on success and 3 on failure; new shape exits 0 on success and 3 on failure. A real deploy failure still fails `ship.sh` with deploy's exit code. The non-`--yes` path (`exec scripts/deploy.sh`) is untouched.
- **The guard catches the regression.** `bash scripts/ship_sigpipe_guard_test.sh` passes 5/5. Run with `SHIP_SH` pointing at a scratchpad copy of `git show a5c7d2ad~1:scripts/ship.sh`, it exits 1 with both static checks failing. Four more mutated copies, all made with `sed` into the scratchpad, each exit 1: `yes y |`, `yes y|`, `yes |` and `yes y | ./scripts/deploy.sh`. The exactly-once match on the fixed line is what catches the `yes |` form. The bare-pipe regex alone would miss it, but the two checks together close it.
- **The oracle is independent of the subject.** The static checks are regexes, not a stored copy of the line. The behavioural checks run fixed shape strings in a separate `bash -c` and never read `ship.sh`, so editing `ship.sh` cannot make them agree with it. The old-shape-exits-141 precondition exits 2 if the harness cannot observe SIGPIPE, so the guard cannot pass vacuously.
- **The check.sh wiring is correct.** The guard is in the `guards` arm right after `#0712` and is named in the header list. The file is tracked `100755`, `bash -n scripts/check.sh` is clean, `shellcheck` is clean on both scripts, and `bash scripts/check_guard_test.sh` reports all guards hold (0 failures).
- `ship.sh` and `deploy.sh` were never executed. The full `scripts/check.sh guards` was not run, because `dev_guard_test.sh` binds `:5173`. The new guard and `check_guard_test.sh` were run directly instead.
