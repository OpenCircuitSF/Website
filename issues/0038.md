## Description

The SNS webhook that turns SES delivery events into suppressions and subscriber status changes.

## Acceptance criteria

- [ ] `POST /api/ses/notifications` accepts SNS payloads, signature-verified by #0037
- [ ] Raw payload inserted into `email_events` **before** interpretation
- [ ] `Bounce` with `bounceType == "Permanent"` → status `bounced` + suppression `hard_bounce`
- [ ] `Bounce` with `bounceType == "Transient"` counts toward the soft-bounce threshold (#0039)
- [ ] `Complaint` → status `complained` + suppression `complaint`; never auto-resubscribes
- [ ] Events reconciled to `email_sends` by `ses_message_id`; an event with no matching send row is still recorded and still suppresses
- [ ] Returns 200 even for payloads that cannot be interpreted — logged, not retried
- [ ] SES account-level suppression list enabled as a second layer
- [ ] `email_events` migration created with indexes on message id and recipient
- [ ] Tests cover permanent bounce, transient bounce, complaint, delivery, and an uninterpretable payload

## Carried in from `#0025`'s review (2026-08-19)

- [ ] **`MarkBounced` and `MarkComplained` return `(Subscriber, nil)` with the
      row unchanged when it is already `complained`.** That is success, not
      failure — do not treat it as an error and skip the `email_events` insert or
      the suppression insert. Both are separate steps and must still run.
- [ ] **A repeat `MarkComplained` no longer bumps `updated_at`.** `email_events`
      is the authoritative timeline; do not infer recency from the subscriber row.

## Notes

PRD §6.7. Returning non-2xx on a parse failure is the trap: SNS retries aggressively, so a parsing bug becomes a retry storm that buries the real events. Log and 200.

Recording the raw payload before interpreting it means a bug in the interpretation logic is recoverable — the evidence is still in `email_events`.

Enable SES account-level suppression too. Our list is authoritative for our sending decisions; SES's protects the account reputation if ours ever has a bug.

### 1. Decision — payload shape: parse `eventType`, accept `notificationType`

PRD §6.7 wires a **Configuration Set event destination**, whose payload is the
*event publishing* format:

```json
{"eventType":"Bounce","mail":{...},"bounce":{...}}
```

The older *identity notification* format uses `"notificationType"` instead, and
AWS's docs for the two sit side by side — an implementer can easily read the
wrong page. Parse `eventType` first and fall back to `notificationType`; treat
whichever is non-empty as the event type. Both formats agree on the `mail`,
`bounce`, `complaint`, and `delivery` sub-objects, so nothing else changes.

**The SNS `Message` field is a JSON string, not a nested object.** It must be
unmarshalled a second time. This is the single most common bug in SNS/SES
ingestion code and deserves a comment.

**Open/Click events must not be enabled on the configuration set** (CLAUDE.md
§9: no email open-tracking pixels). PRD §6.7 already lists only Bounce,
Complaint, Delivery, Reject, RenderingFailure. The handler should still
tolerate an unexpected `eventType` by recording it and returning 200 — it must
not be the thing that enforces the tracking policy, but it must not crash if
the configuration set is ever misconfigured.

### 2. Decision — the dedupe key is the SNS `MessageId`, and the unique
constraint is `(sns_message_id, recipient)`

This is the decision the brief flags as most likely to be got wrong, so the
reasoning is spelled out.

- **SNS `MessageId`** identifies one *delivery attempt group*: SNS's
  at-least-once guarantee means the same `MessageId` arrives repeatedly. This
  is the retry-dedupe key.
- **SES `mail.messageId`** identifies one *outbound email*. One email produces
  *many* events (Send, Delivery, then possibly Bounce, then possibly
  Complaint). It is **not** a dedupe key; it is the reconciliation key, and it
  is what #0049 joins on and what #0039 does *not* use.

So: store both. `sns_message_id` carries the uniqueness; `ses_message_id` is a
plain indexed column.

**Why the constraint is composite.** A single `Bounce` event carries
`bounce.bouncedRecipients[]` — an array. `email_events.recipient` is one
column, so one SNS message can legitimately produce several rows. A `UNIQUE
(sns_message_id)` would make that impossible; picking "the first recipient" and
discarding the rest silently drops suppressions. Insert **one row per
recipient**, all inside the one transaction, with `UNIQUE (sns_message_id,
recipient)`.

`recipient` must therefore be `NOT NULL DEFAULT ''` — in Postgres, `NULL`s do
not conflict, so a nullable `recipient` would defeat the dedupe entirely for
events that have no recipient list. Recipient extraction, in order:

| Event | Source |
|---|---|
| Bounce | `bounce.bouncedRecipients[].emailAddress` |
| Complaint | `complaint.complainedRecipients[].emailAddress` |
| Delivery | `delivery.recipients[]` (plain strings) |
| anything else | `mail.destination[]` |
| nothing found | one row with `recipient = ''` |

Normalise every extracted address with the same `lower(trim(…))` the
`subscribers` and `suppressions` tables enforce (see §7) — SES returns the
address as the sender supplied it, and a case mismatch means a suppression that
silently fails to match, which is worse than no suppression at all.

### 3. Decision — ordering: stale events must not overwrite newer state

At-least-once and out-of-order delivery, handled in three layers:

1. **Terminal states are already monotone in the store.**
   `subscribers.setStatus` preserves `complained` against every non-admin
   write, so a late `Bounce` cannot erase a `Complaint` regardless of arrival
   order. Nothing in this handler needs to re-implement that, and nothing in
   this handler may bypass it — `AdminClearComplaint` is the only method that
   can, and this handler must never call it.
2. **`Delivery`, `Reject`, `RenderingFailure`, and `Send` never change
   subscriber status at all.** They are recorded and nothing else. This removes
   the entire class of "a late Delivery un-bounces someone".
3. **The real remaining hazard** is a genuinely old event arriving after the
   address has been legitimately restored (admin clears the complaint or the
   suppression, the person re-signs up, re-confirms, and *then* the retry of a
   week-old bounce lands). Guard it explicitly: **skip the status transition
   and the suppression insert when the event's `mail.timestamp` is older than
   the subscriber's `confirmed_at`.** The `email_events` row is still written —
   the evidence is never discarded, only the state change is suppressed. This
   is cheap (one comparison against data already loaded) and it is the only
   place where "newer state" is at risk. It needs its own test.

Note this guard applies only when a subscriber row exists. An event for an
address with no subscriber still records and still suppresses (criterion 6).

### 4. Decision — event → state mapping

| `eventType` | `bounce.bounceType` | Extra condition | `email_events` | `suppressions` | subscriber status |
|---|---|---|---|---|---|
| `Bounce` | `Permanent` | any subType (`General`, `NoEmail`, `Suppressed`, `OnAccountSuppressionList`) | row | `hard_bounce` | → `bounced` |
| `Bounce` | `Transient` | — | row | **none** — #0039's job | unchanged |
| `Bounce` | `Undetermined` | — | row | **none** | unchanged |
| `Complaint` | — | `complaintFeedbackType != "not-spam"` | row | `complaint` | → `complained` |
| `Complaint` | — | `complaintFeedbackType == "not-spam"` | row | **none** | **unchanged** |
| `Delivery` | — | — | row | none | unchanged |
| `Reject` | — | — | row | none | unchanged |
| `RenderingFailure` | — | — | row + log at ERROR | none | unchanged |
| `DeliveryDelay`, `Send`, unknown | — | — | row | none | unchanged |

Two traps worth naming:

- **`not-spam` is not a complaint.** It is a feedback-loop report that a
  message was moved *out* of a spam folder. Suppressing on it unsubscribes
  people for the crime of rescuing our mail. Explicitly exclude it and test it.
- **`Permanent/Suppressed` and `Permanent/OnAccountSuppressionList`** mean SES's
  own account-level suppression list blocked the send. Still a hard bounce from
  our point of view — suppress.

Per the carried-in criteria from #0025's review: when `MarkBounced` /
`MarkComplained` return the row unchanged because it is already `complained`,
that is **success**. Do not branch on it, do not skip the `email_events` insert
or the suppression insert. With the single-transaction design in §5 this falls
out naturally — there is no early return to get wrong.

### 5. Decision — one transaction, and where the 200/500 line actually falls

**All writes for one SNS message happen in a single `pgx.Tx` owned by the
handler.** Copy `internal/audit`'s established idiom: each store package
exposes a `…Tx` variant over a `querier` interface that both `*pgxpool.Pool`
and `pgx.Tx` satisfy. That keeps SQL in the package that owns each table
(CLAUDE.md §1) while letting one caller make them atomic.

```
BEGIN
  for each recipient:
      INSERT INTO email_events (...) ON CONFLICT (sns_message_id, recipient) DO NOTHING
  if zero rows inserted across all recipients → COMMIT (no-op), return 200   ← redelivery
  for each recipient:
      resolve subscriber by normalised email (may be absent)
      apply §3 staleness guard
      apply §4 mapping: suppressions.AddTx(...) and subscribers.MarkBouncedTx/MarkComplainedTx(...)
  audit.WriteTx(...)
COMMIT
```

**Atomicity is what makes the dedupe short-circuit correct.** If the three
writes were separate, a crash between the `email_events` insert and the
suppression insert would leave the event recorded but unsuppressed — and SNS's
retry would then be *deduped away* by the already-present `email_events` row,
so the suppression would never happen and nothing would ever notice. Inside one
transaction, either the whole effect landed or none of it did, so "the event
row exists" is a sound proof that "the event was fully processed".

Status codes extend #0037's table with the one case that matters here:

- Payload parses but the `eventType` is unrecognised, or the JSON is malformed
  → **200**, logged. A parse bug is not fixed by retrying, and SNS's retry
  policy would turn it into a storm that buries real events. This is
  criterion 7 and PRD §6.7 item 5.
- Payload is valid but the **transaction fails** (DB down, constraint error,
  serialisation failure) → **500**. Criterion 7 is about *interpretation*, not
  *storage*: if the raw payload could not be recorded there is nothing to
  recover from later, and SNS's retry is the only thing standing between us and
  a lost bounce. Returning 200 here would discard events silently during a
  database outage. **This distinction must be a comment in the handler and must
  have a test** — it is the one place where "always 200" is wrong.

### 6. Migration `000012_create_email_events`

```sql
CREATE TABLE email_events (
    id             BIGSERIAL PRIMARY KEY,
    sns_message_id TEXT NOT NULL,
    ses_message_id TEXT,
    event_type     TEXT NOT NULL,            -- Bounce | Complaint | Delivery | Reject | ...
    bounce_type    TEXT,                     -- Permanent | Transient | Undetermined
    bounce_subtype TEXT,
    recipient      TEXT NOT NULL DEFAULT '', -- normalised lower(trim(...)); '' when the event has none
    event_at       TIMESTAMPTZ,              -- mail.timestamp / event timestamp from the payload
    payload        JSONB NOT NULL,
    received_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (sns_message_id, recipient)
);
CREATE INDEX idx_email_events_message_id ON email_events (ses_message_id);
CREATE INDEX idx_email_events_recipient  ON email_events (recipient);
-- #0039 counts transient bounces per recipient in a sliding window; this is
-- the index that query needs, added here rather than in #0039 so #0039 is a
-- pure read.
CREATE INDEX idx_email_events_soft_bounce
    ON email_events (recipient, received_at DESC)
    WHERE event_type = 'Bounce' AND bounce_type = 'Transient';
```

Add a `CHECK (recipient = lower(trim(recipient)))` to match the `subscribers`
migration's belt-and-suspenders normalisation constraint, and a `CHECK` on
`event_type` **only if** the set is genuinely closed — it is not (SES adds
event types), so leave `event_type` unconstrained and say so in a comment. This
is the opposite of `subscribers.status`, which *is* closed; the asymmetry is
deliberate and worth one line of SQL comment.

**Deviations from PRD §6.2's `email_events` definition, deliberate:**
`sns_message_id` added (there is no dedupe key in the PRD schema);
`bounce_subtype` added (#0039 needs it, and PRD §6.5's own note about
out-of-office replies depends on subType); `recipient` made `NOT NULL DEFAULT
''` and joined into the unique constraint; `event_at` added. These are
additions, not removals — every PRD column survives. Since this issue *creates*
the table, this is not an append-only violation (CLAUDE.md §1). Record the
deviation in `## Fix` so the PRD can be reconciled later.

The `.down.sql` drops the table.

### 7. What #0033 must provide (build the suppressions store to fit)

`#0033` is unimplemented. State these requirements there before or while
building it, so the mismatch is not discovered during #0038's implementation:

1. **A transaction-accepting variant.** `AddTx(ctx context.Context, q querier,
   email, reason, note string, now time.Time) error` alongside the pool-backed
   `Add`. Without it, §5's single transaction is impossible and the crash
   window in §5 reopens. Model it on `audit.Logger.WriteTx` / `audit.insert(ctx,
   q querier, …)` — that precedent already exists in this codebase, so this is
   not a new pattern.
2. **Idempotent by email.** `INSERT … ON CONFLICT (email) DO NOTHING`. A repeat
   suppression must not error and must **not** overwrite the original reason —
   the first reason is the true one, and `email_events` is the authoritative
   timeline for everything after it. Returning "already present" is success.
3. **No foreign key to `subscribers`.** Criterion 6 requires that an event with
   no matching subscriber still suppresses; #0033's own notes require the row
   to survive hard deletion (#0060). Key on email only.
4. **Exported reason constants**: `ReasonHardBounce = "hard_bounce"`,
   `ReasonComplaint = "complaint"`, `ReasonRepeatedSoftBounce =
   "repeated_soft_bounce"`, `ReasonManual = "manual"`. #0038 must never write
   these as string literals.
5. **`email` normalised `lower(trim(email))` with the same CHECK as
   `subscribers.email`** — already a carried-in criterion on #0033, and #0038
   depends on it being true.

#0038 additionally needs, in `internal/subscribers`: `MarkBouncedTx` and
`MarkComplainedTx` taking a `querier`, refactored out of the existing
`setStatus` (which becomes `setStatusTx(ctx, q, …)` with the pool-backed
methods as thin wrappers). **The `statusLockedFromNonAdmin` guard must live in
the shared implementation, not the wrapper**, so the Tx path cannot skip it.
That refactor belongs to this issue, not #0033.

### 8. The boundary with #0039 — stated so the two do not overlap

**#0038 does no counting whatsoever.** It does not read a window, does not read
`settings`, does not look at prior events. Its entire responsibility for a
`Transient` bounce is: write the `email_events` row with `bounce_type =
'Transient'` and `bounce_subtype` faithfully recorded, and change nothing else.

**#0039 adds exactly one call at exactly one place.** #0038 must structure the
per-recipient interpretation as a single named function — suggested
`applyBounce(ctx, tx, ev, sub)` — with a `case "Transient":` arm carrying a
comment naming #0039 as its owner. #0039 inserts, inside that arm and inside
the same transaction, a `CountRecentTransientBounces(ctx, q, recipient, window)`
call against `email_events` (the partial index in §6 is already there for it)
and, on threshold, performs the same `AddTx(ReasonRepeatedSoftBounce)` +
`MarkBouncedTx` pair `Permanent` already uses. Nothing else in #0038 changes.

Two boundary questions #0038 must **record but not decide**:

- Whether `Undetermined` counts toward the soft-bounce threshold. #0038 records
  the value faithfully so #0039 can choose either way. Recommendation to
  #0039: count it — an unclassifiable repeated failure is a dead address — but
  it is #0039's call.
- The threshold values (5 in 30 days) live in `settings` per #0039's criteria.
  #0038 must not hardcode them anywhere, because it must not read them at all.

### 9. Corrections to the acceptance criteria

Recorded here rather than edited into the checkbox list, per the planning brief.

**Correction 1 — criterion 6 ("Events reconciled to `email_sends` by
`ses_message_id`") cannot be implemented as a write, and should not be.**
`email_sends` is created by **#0040**, which is Phase 5, and #0038 is Phase 4
and does not list #0040 in `Depends on` — correctly, since a Phase 4 issue
gated on Phase 5 would deadlock the phase order. There is no table to reconcile
*to* when this issue is built.

Recommended restatement: *"`email_events` records `ses_message_id` on every
event, indexed, so that #0049 can reconcile campaign stats by joining
`email_sends` on it. #0038 writes no `email_sends` rows."* The second half of
the criterion — "an event with no matching send row is still recorded and still
suppresses" — survives verbatim and is genuinely testable now; it is the
important half.

This restatement is also the *better* design independently of the ordering
problem: a write-side reconciliation would need a monotone-by-severity guard on
`email_sends.status` to stop a late `Delivery` overwriting `bounced`, which is
exactly the kind of ordering bug §3 exists to avoid. A read-side join has no
such hazard.

**Correction 2 — criterion 8 ("SES account-level suppression list enabled as a

by `go test`.** The SES account itself does not exist yet: CLAUDE.md §10 open

resolution: satisfy the criterion with a documented runbook step in `docs/`
(the `aws sesv2 put-account-suppression-attributes --suppressed-reasons BOUNCE
COMPLAINT` invocation, plus what it does and does not cover) and a line in
CLAUDE.md §10's open-items table, rather than by claiming a code change.

**Correction 3 — a consequence worth stating plainly:** because the SNS topic,
the configuration set, and the SES identity do not exist yet, **#0038 cannot be
verified end-to-end against real SNS during this phase.** Everything in this
plan is unit- and DB-testable with synthesised payloads and #0037's keypair
fixture, and that is the standard the reviewer should apply. The live wiring is
a separate, later verification gated on CLAUDE.md §10 open item 2 — it should
not be claimed as done in `## Verification`.

**Correction 4 — missing criterion: topic-ARN allowlisting.** See #0037's plan

this endpoint must reject any message whose `TopicArn` is not the configured

### 10. Route, wiring, and the admin-guard invariant

Route: **`POST /api/ses/notifications`** (PRD §6.7, criterion 1).

- Registered **directly in `mountAndServe`**, not via `adminRoutes()`. It is
  `/api`, not `/admin`, so `admin_routes_ast_test.go` does not fire on it —
  that test matches only literal patterns whose path begins `/admin`, and
  #0079's recorded decision deliberately scopes it that way.
- **It must not sit behind `requireAdmin` or `requireSession`.** SNS posts with
  no bearer credential of any kind; the signature *is* the authentication.
  Wrapping it in either guard would return 403 to SNS, which retries, backs
  off, and eventually disables the subscription — bounces stop arriving and
  nothing surfaces an error.
- #0079's recorded invariant is that **every `/api` and `/account` registration
  carries its guard, or a comment explaining its deliberate absence, at the
  call site**. This route needs that comment, in the same style as
  `/api/subscribe` and `/api/preferences`: state that it is public by design,
  that `sesnotify.Verifier` plus the topic-ARN pin is the authentication, and
  that adding a session guard here breaks event ingestion silently.
- Follow the existing nil-guard convention (`if sesNotifyH != nil { … }`) so
  dev mode (`STORAGE=json`, no Postgres) still boots — `internal/devstore` has
  no `email_events` backing and none should be added.
- **No rate limiter.** Every other public route here has one; this one must
  not. A campaign send produces thousands of events in a burst from many SNS
  source IPs, and a per-IP token bucket would reject exactly the traffic the
  system exists to receive. Cost is bounded instead by
  `http.MaxBytesReader` (#0037 §6) and by the cert cache. Put that reasoning in
  the call-site comment too, since its absence would otherwise read as an
  oversight.
- `knownStaticRoutes` (`internal/handlers/routes.go`) is the **SPA** route
  table and must not gain an `/api/...` entry; `routes_parity_test.go` is
  unaffected.

### 12. Test strategy

DB-backed; **`TEST_DATABASE_URL` must be exported** and the run must show zero
skips (CLAUDE.md §5). Fixtures: synthesised SNS envelopes signed with the
test keypair from #0037's helper, so a handler test exercises the real
verifier rather than stubbing it out — the verifier's fetcher seam is the only
thing injected.

Required cases:

1. **Permanent bounce** → `email_events` row, `suppressions` row
   (`hard_bounce`), subscriber `bounced`, 200.
2. **Transient bounce** → `email_events` row with `bounce_type='Transient'`,
   **no** suppression, subscriber status unchanged, 200.
3. **Complaint** → `email_events`, `suppressions` (`complaint`), subscriber
   `complained`, 200.
4. **Complaint with `complaintFeedbackType: "not-spam"`** → `email_events`
   only, no suppression, status unchanged.
5. **Delivery** → `email_events` only, nothing else changes.
6. **Uninterpretable payload** (not JSON, and separately: valid JSON with an
   unknown `eventType`) → 200, logged, no state change.
7. **Storage failure → 500, not 200.** The important negative case. Close the
   pool or point the handler at a cancelled context; assert 500 and assert no
   partial rows.
8. **Redelivery**: post the identical signed envelope twice → exactly one
   `email_events` row per recipient, exactly one suppression row, second call
   200.
9. **Crash-window equivalence**: run the transaction, roll it back, re-post →
   all three writes land on the retry. This proves §5's atomicity claim rather
   than assuming it.
10. **Multi-recipient bounce**: two `bouncedRecipients` → two `email_events`
    rows, two suppressions, both subscribers `bounced`.
11. **Event for an address with no subscriber row** → `email_events` row and
    suppression row still written, 200 (criterion 6's surviving half).
12. **Stale event guard (§3)**: a bounce whose `mail.timestamp` predates the
    subscriber's `confirmed_at` → event recorded, **no** suppression, status
    unchanged.
13. **`complained` is not erased**: subscriber already `complained`, a
    `Permanent` bounce arrives → status stays `complained`, **and** the
    `email_events` row and the `hard_bounce` suppression are both still
    written (the carried-in criteria from #0025's review).
14. **Repeat `MarkComplained` does not bump `updated_at`** — assert the
    timestamp is unchanged across a second complaint (carried-in criterion 2).
15. **Case/whitespace normalisation**: SES reports `" Foo@EXAMPLE.com "` for a
    subscriber stored as `foo@example.com` → matched and suppressed.
16. **Unauthenticated reachability**: a wiring test in `cmd/opencircuit`
    asserting the route answers *without* a session (403 for a bad signature,
    not 403-from-the-guard). Distinguish the two by the response body or by
    posting a *valid* signature and expecting 200.
17. **Topic-ARN mismatch** → 403, zero rows written.

Discipline required by CLAUDE.md §8b:

- **Seed throwaway rows; never target a literal or seeded id.** Use a unique
  per-test email prefix (`zz-0038-<random>@example.test`) and derive ids from
