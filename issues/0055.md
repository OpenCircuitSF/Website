## Description

Structured data in each workshop page's server-injected head, making sessions eligible for rich results in search.

## Acceptance criteria

- [x] JSON-LD `Event` object injected server-side into `/workshops/{slug}`
- [x] Fields: name, startDate, endDate, eventStatus, eventAttendanceMode, location, description, organizer, image, url
- [x] Canceled workshops emit `EventCancelled` status
- [x] Organizer is Open Circuit SF with the site URL — no venue is named as organizer
- [x] ~~Validated against Google's Rich Results Test with no errors~~ — struck by
  the phase-3 review: the live tool fetches a public URL, and nothing here is
  publicly reachable yet, so this cannot be met before a production deploy.
  Structural validation against Google's documented `Event` requirements was
  done by hand instead (see `## Verification`) and judged sufficient to
  resolve on. The live-tool run now belongs to
  [#0149](0149.md) — Validate the workshop JSON-LD against Google's Rich
  Results Test once a workshop page is publicly reachable.
- [x] JSON string values escaped correctly; a title containing quotes does not break the block

## Notes

PRD §7.4. Structured data goes in the server-injected head, not the SPA — search crawlers that do render JavaScript are the exception, not the rule.

Escaping matters as much here as in #0019: an apostrophe or quote in a workshop title that breaks the JSON block silently invalidates the whole thing, and the failure is invisible without validation.

## Root cause

Nothing was wrong; this is new work. `internal/seo` (#0019/#0054) already
server-injects per-route `<title>`/`og:*`/`twitter:card` tags into the built
`index.html`, but nothing emitted schema.org structured data, so a workshop
page had no path into a Google Rich Result at all.

## Fix

Added a new `%%OC_JSONLD%%` token to `web/index.html` and `web/dist/index.html`
(placed right before `</head>`, alongside the existing `%%OC_OG_*%%` tokens),
and a new `internal/seo/jsonld.go` that builds the schema.org `Event` object
and substitutes it in via `Renderer.substitute` (`internal/seo/seo.go`).

**Which workshops get a block.** Only `published` or `canceled` workshops
(matching the public detail route's own "published OR canceled" visibility
rule, `internal/handlers/public_workshops.go`) that *also* have both a start
date and a location produce a block; `draft`, an unknown slug, or a
published/canceled workshop still missing a date or venue render nothing (no
`<script>` tag at all) rather than a block with a fabricated or empty
required field. `name`/`startDate`/`location` are schema.org/Google's
required `Event` fields for a non-virtual event — emitting an incomplete
block would fail Rich Results validation, which is worse than omitting
structured data for a workshop whose details aren't finalized yet.

**Canceled workshops — the deliberate divergence this issue's task flagged.**
`workshopRouteMeta` (renamed from `workshopMeta`) still serves a canceled
workshop's `<title>`/`og:*` tags from the generic site fallback, unchanged —
`#0135`'s review left that behavior standing so canceled workshops stay out
of link-preview cards and the sitemap. JSON-LD does the opposite on purpose:
it carries the workshop's *own* real title/dates with
`eventStatus: "https://schema.org/EventCancelled"`, because that field exists
specifically so a search result can say "this was scheduled and got
canceled" instead of either pretending the event never existed or silently
vanishing it — matching the fact that the detail page itself (#0054) still
renders a real, visible cancellation notice for anyone holding the link. This
resolves the tension the task named: the social card/sitemap stay generic
for a canceled workshop; the structured data does not.

**No online/virtual event concept exists in this schema.** `internal/
workshops.Workshop` has no is-virtual flag or meeting-link field — Open
Circuit SF is an in-person workshop space (PRD's own framing) — so
`eventAttendanceMode` is always `OfflineEventAttendanceMode` and `location`
is always a schema.org `Place` built from `location_name`/`location_address`.
If a virtual/hybrid workshop concept is ever added to the data model,
`jsonld.go`'s doc comment names exactly where to branch (emit
`OnlineEventAttendanceMode` + a `VirtualLocation` alongside/instead of the
`Place`).

**Organizer** is always a fixed `{"@type":"Organization","name":"Open Circuit
SF","url":"<baseURL>/"}`, built from `cfg.BaseURL`, never from the workshop's
own `location_name`/`location_address` — satisfies "no venue is named as
organizer" by construction, not by a check.

**Escaping.** The JSON body comes from `encoding/json.Marshal`, whose default
behavior HTML-escapes `<`, `>`, and `&` (Go does this unconditionally unless
`Encoder.SetEscapeHTML(false)` is explicitly set, which nothing here does).
That's what makes the JSON-LD token the *one* token `Renderer.substitute`
does **not** additionally run through `html.EscapeString` — the OG/title
tokens need it because they're plain text dropped into an HTML
attribute/text node, but the JSON-LD token is already a complete,
self-contained `<script>` element; a second HTML-escaping pass would corrupt
the JSON itself (turning a JSON-required `"` into `&#34;`) rather than
protect anything.

**A real bug this issue's own change would otherwise have introduced, caught
before it shipped: cache-bucket sharing.** Before this change, `resolve`
routed every workshop slug that wasn't a *published* match (draft, canceled,
unknown) into one shared `cacheKeyFallback` cache entry — safe only because
every one of those cases rendered a byte-identical generic body. Once a
canceled workshop started carrying its own per-workshop JSON-LD, two
*different* canceled workshops sharing that single cache entry would have
served one workshop's structured data on the other's page after the first
one primed the cache. Fixed by widening `workshopRouteMeta`'s "gets its own
cache key" condition from `status == published` to
`status == published || status == canceled`; draft and unknown slugs still
share the fallback bucket (their bodies are still identical — no per-workshop
data). Documented in `maxCacheEntries`' doc comment and covered by
`TestRender_JSONLD_DistinctCanceledWorkshopsDoNotShareCacheEntry`.

  the real `internal/workshops` store never produces (only

  unticked acceptance-criterion box above. The structural checks (valid JSON,
  correct field names/types per schema.org's `Event` docs, RFC 3339 dates
  with an offset) are the strongest verification available without outbound
  network access to Google's service.
- **`workshopRouteMeta`'s `ok=true` for canceled is a real behavior widening**
  worth the reviewer's attention: before this change, a canceled workshop's
  cache entry was indistinguishable from a draft's or an unknown slug's (all
  shared `cacheKeyFallback`). After this change it gets its own
  `"workshop:{slug}"` entry — same mechanism as published, just with the
  fallback `RouteMeta` instead of the workshop's own title/OG fields. Worth
  double-checking `TestRender_JSONLD_DistinctCanceledWorkshopsDoNotShareCacheEntry`

The prose token is a token. `strings.NewReplacer` does not care that it sits
inside a comment, so roughly 860 bytes of Event JSON ship twice on every
published-or-canceled workshop page, and view-source shows an explanatory
comment cut in half by a blob. Measured: `/workshops/{published-slug}` = 6111
bytes against `/about` = 4396 bytes, i.e. two copies of the same block.

**It is not exploitable** — confirmed by parsing the served page with a real
HTML parser: exactly one `application/ld+json` *element* exists (the comment
copy stays a comment), and a title containing `-->`, `--!>`, `]]>` and `<!--`
still does not break out, because `json.Marshal` escapes every `>` to the
`\u003e` escape and an HTML comment can only end on a literal `-->`/`--!>`. So
this is correctness-of-artifact and page weight, not security. It is still this
commit's own line, in the file that actually ships, and the drafted
`## Verification`'s claim that `grep -c OC_JSONLD` proves the token behaves was
made against the **placeholder** `web/dist/index.html` (that pass never ran
`npm run build`), so it never exercised the artifact production serves.

### Ruling 1 — the escaping decision is correct, and proven

`encoding/json.Marshal` escapes `<`, `>`, `&` (to `\u003c`, `\u003e`, `\u0026`)
and U+2028/U+2029 unconditionally unless `Encoder.SetEscapeHTML(false)` is set;
nothing here sets it. Declining a second `html.EscapeString` pass over the block
is right — it would corrupt the JSON, not protect it.

I tried to break out of the `<script>` element with 18 payloads, each planted in
`Title`, `Summary`, `LocationName`, `LocationAddress` **and** `CoverImage`
simultaneously, rendered through `Renderer.Render`, then parsed with a real HTML
parser rather than by substring:

| # | payload | result |
|---|---|---|
| 01 | `abc</script><img src=x onerror=alert(1)>def` | fully escaped; 1 script element, no `img`; JSON round-trips exactly |
| 02 | `abc</ScRiPt ><svg onload=alert(1)>def` | escaped; no `svg` element |
| 03 | `abc</script/foo><b>def` | escaped; no `b` element |
| 04 | `abc</script` + newline + `><b>def` | escaped, newline becomes `\n`; no breakout |
| 05 | `abc<!--<script>def` | escaped |
| 06 | `abc-->def<!--` | escaped |
| 07 | `abc<![CDATA[ ]]> def` | escaped |
| 08 | `abc</ def > ghi` | escaped |
| 09 | `abc` + U+2028 + `def` + U+2029 + `ghi` | emitted as the `\u2028`/`\u2029` JSON escapes inside the block |
| 10 | `abc%%OC_TITLE%% %%OC_JSONLD%% %%OC_OG_URL%%def` | **not** re-substituted — `strings.Replacer` is a single left-to-right pass over the template and never rescans replacement text; round-trips as the literal tokens |
| 11 | `abc\x00\x01\x07\x1b[31m def` | escaped as `\u0000`/`\u0001`/`\u0007`/`\u001b`; valid JSON |
| 12 | `abc</script> def \\ " '` | escaped; quotes and backslashes round-trip |
| 13 | `abc\xff\xfe def` (invalid UTF-8) | replaced with U+FFFD; still valid JSON |
| 14 | `abc&lt;/script&gt; &amp;amp; def` | ampersands escaped to `\u0026`; entities stay literal text |
| 15 | `abc</style></textarea></title></noscript>def` | escaped; no stray elements |
| 16 | `abc"},{"@type":"Event","name":"injected` | quotes escaped; object still has exactly 12 top-level keys, no injected sibling |
| 17 | `abc` + U+202E + U+200B + NBSP + `def` | passed through as UTF-8 inside a JSON string; inert |
| 18 | `abc<\/script><\/SCRIPT>\x3c/script\x3e def` | escaped; no breakout |

Every one: JSON parsed, values round-tripped byte-for-byte, **zero raw `<`, `>`
or `&` anywhere inside the script body**, and no stray element after the block.
End-to-end against Postgres and a real build, a workshop titled
`boom --> <img src=x onerror=alert(1)> --!> ]]> <!--` with summary
`tail -- --> end` produced: 3 comments, exactly 1 `application/ld+json` element,
no `img` tag, name round-tripped exactly. Comment breakout is structurally
impossible here — it needs a literal `-->`/`--!>`, and no `>` character can come
from the data.

The escaping is also genuinely *tested*, not incidentally passing: replacing
`json.Marshal` with an `Encoder` + `SetEscapeHTML(false)` makes
`TestRender_JSONLD_TitleWithQuotesStaysValidJSON` fail immediately, with a
literal `<script>alert(1)</script>` visible in the emitted block. Mutation
reverted; `git diff` clean afterward.

### Ruling 3 — the canceled-workshop split is coherent; keep it

`<title>`/`og:*` generic (per #0135) while the JSON-LD carries the real title,
dates and `EventCancelled` is the right split, and I would not change it. The
two surfaces answer different questions: og/Twitter cards are *promotional* —
they render unbidden in someone's feed or chat, and pushing a canceled event
into that surface actively misinforms; the sitemap is a crawl *invitation*.
JSON-LD is descriptive metadata about a page a reader already reached, and
`EventCancelled` exists for precisely this state — suppressing it means a search
result either silently vanishes or, worse, still advertises the workshop as
scheduled. It also matches what the page itself shows (#0054 renders a visible
cancellation notice), which is Google's own requirement that structured data
reflect visible content. No new issue needed. If the two surfaces are ever to be
reunified, that decision belongs to a **new issue owning canceled-workshop
metadata policy across `internal/seo`**, since it would reverse #0135's standing
ruling — not to this issue.

### Ruling 6 — schema correctness holds, and PRD §7.4 contemplates no virtual event

Against a real render: `@context` `https://schema.org`, `@type` `Event`;
required `name`, `startDate`, `location` all present; recommended `endDate`,
`eventStatus`, `eventAttendanceMode`, `image`, `organizer`, `description` all
present and correctly typed. `startDate`/`endDate` are RFC 3339 **with** a `Z`
offset (`2026-09-12T18:00:00Z`), which is what a bare date would fail.
`location` is a real `{"@type":"Place","name":...,"address":...}` — schema.org's
`address` accepts Text, so a single free-text venue field is legitimate.
`organizer` is a fixed `Organization` built from `BaseURL`, never the venue, by
construction. `image` and `url` are absolute. `endDate`/`description` are
`omitempty` and correctly absent when the row has none.

The online/virtual simplification is right: **PRD §7.4 asks only for "JSON-LD
`Event` structured data inside each workshop detail page's server-injected
`<head>`"** — it contemplates no virtual or hybrid concept, and
`internal/workshops.Workshop` has no is-virtual flag or meeting-link column to
branch on. Hardcoding `OfflineEventAttendanceMode` plus a `Place` is correct
today, and `jsonld.go`'s doc comment names where to branch if that ever changes.

One pre-existing nit, **not** this issue's to fix: `absoluteURL` prefixes
`cover_image` without validating or URL-encoding it, so a garbage `cover_image`
becomes a syntactically invalid `image` URL (JSON- and HTML-safe, just not a
URL). It reaches `og:image` the same way today, from #0019. Worth a small new
issue validating `cover_image` at the admin API boundary.
