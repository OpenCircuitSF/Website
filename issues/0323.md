## Description

`scripts/go_file_visit_floor_guard_test.sh` counts `ClaimDue`/`OrphanSweep` call
sites with **grep**; the Go guard it pins counts them with **`go/ast`**. `#0304`'s
review measured both:

| Population | grep | AST |
|---|---|---|
| **non-exempt** | **12** | **12** — agree exactly, one-for-one |
| total | **35** | **32** |

The three extras are all inside `internal/outbox` and are exactly the miscount
class grep is prone to: one occurrence in a **prose comment**
(`claim_kinds_call_site_guard_test.go:156`) and two inside **raw-string
fixtures** (lines 347 and 376, `fixtureSrc`/`scopedFixtureSrc`), where the AST
correctly counts zero.

Also worth recording: `grep -c` counts **lines**, so it under-counts when two
calls share one line.

## Why this is documentation rather than a bug

The divergence is in the **inflating** direction on the total, which only
loosens the upper bound — the safe direction. The number that governs the check
that matters, the non-exempt count, agrees exactly.

And `claimKindsGuardMinPlausibleCallSiteCount`'s doc comment says **32**, the AST
figure, while the harness measures 35. Neither is wrong for its own method; they
are simply counting different things and both call it "the population".

**Do not make the oracle parse Go.** Its independence from `go/ast` is the entire
point of the external harness (CLAUDE.md §8, `#0300`) — an oracle that used the
same parser as its subject would be the copy-of-the-answer shape that harness
exists to avoid.

## Acceptance criteria

1. Both the harness comment and `claimKindsGuardMinPlausibleCallSiteCount`'s doc
   comment record that the two counts are measured differently, state both

2. Record the direction — grep inflates the total, loosening only the upper

3. Record the `grep -c` line-versus-occurrence under-count risk.
4. **The oracle stays grep-based.** If you conclude the divergence must be closed

6. `ISSUE=NNNN scripts/check.sh guards` passes, run at least twice.

## Review notes

**Verdict: resolved.** Both populations were re-measured by the reviewer with
tooling written from scratch, and the self-referential hazard the implementer
reported was re-tested independently rather than taken on trust.

### Both populations re-derived independently

The grep side was recomputed with the harness's own predicate re-typed by hand
over `internal` + `cmd`; the go/ast side with a standalone program written for
this review that replicates `findOutboxCallSitesInFile`'s predicate
(`*ast.CallExpr` whose `Fun` is a `*ast.SelectorExpr` named `ClaimDue` or
`OrphanSweep`) over the same roots — deliberately not by calling the guard's
own functions, so the oracle is not the subject.

| Population | grep | go/ast |
|---|---|---|
| total | **35** | **32** |
| non-exempt | **12** | **12** |

Identical to the committed numbers. The per-package split is `internal/handlers`
5, `internal/mailing` 7, and all 12 non-exempt sites have `argc=3` — so the
"agree exactly, one for one" claim holds site-by-site, not just in aggregate.

### The three divergent sites, located rather than accepted

```
internal/outbox/claim_kinds_call_site_guard_test.go:232  (nameMatchesGuardedMethod's doc comment)
internal/outbox/claim_kinds_call_site_guard_test.go:423  (inside `fixtureSrc`, line 417)
internal/outbox/claim_kinds_call_site_guard_test.go:452  (inside `scopedFixtureSrc`, line 447)
```

All three are inside `internal/outbox`, so they can only ever inflate the total
and never reach the non-exempt count — confirmed by the AST run, which finds
**zero** sites in that file. The direction is inflation, which only loosens
`outbox_floor_plausible`'s `floor <= population` bound. The line numbers in
`#0304`'s review (156/347/376) have shifted because `#0321`–`#0323` added
comment text above them; the sites are the same three.

### Criterion 4 — the oracle really did stay grep-based

`count_outbox_call_sites`'s body is unchanged by this commit; `git show 5379fab`
adds only comment lines above it. Its extraction still fails closed: an empty
or non-numeric population is rejected by the `case … *[!0-9]*` guards, and a
population of `0` makes `outbox_floor_plausible` return non-zero (`floor <=
population` fails), producing a `REGRESSION` failure rather than a pass.

### The self-referential hazard — re-tested, not believed

This is the §8 "an oracle must not be the same bytes as its subject" shape in
its live form: the comment documenting a grep population is itself scanned by
that grep. The implementer reports an early draft pushed the total to 36 and
that it rephrased. Verified independently: the committed file contains exactly
**three** matching lines (listed above), the harness measures the total at
**35**, and my own from-scratch count agrees. The commit added no fourth site.

Two notes for whoever edits these comments next:

- The shell script's new paragraph **does** reproduce the matched literals
  verbatim. That is safe only because `count_outbox_call_sites` scans
  `$REPO/internal` and `$REPO/cmd` for `*.go` — `scripts/` is out of scope. It
  would stop being safe if the roots were ever widened to the repo root.
- The comment records the `grep -c` line-vs-occurrence under-count as a
  hypothetical ("if two guarded calls ever shared one source line"). It is
  already active: line 232 carries **two** occurrences on one line, which is
  precisely why the divergence measures 3 and not 4. The sentence is not false
  as written — that line holds prose, not calls — but the risk it describes is
  present today rather than in the future, and saying so would be sharper.

Neither is a defect in what was committed.
