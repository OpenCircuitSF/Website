## Description

`#0209`'s AST guard fails if any `cmd/opencircuit` file calls `<expr>.Parallel()`
with zero arguments. Its phase-3 review probed twelve shapes and found the
boundary well drawn — subtest closures, helper functions, `defer`, `go`,
parenthesised receivers and `*testing.B` are all **caught**, string literals
correctly do **not** fire, and the two misses (a method value `p := t.Parallel`,
and the explicit `(*testing.T).Parallel(t)` form) are curiosities needing
`go/types` to catch.

The one real cost of not type-checking is **over-firing**. The review verified
it by adding a non-test `seedRunner` with its own zero-arg `Parallel()` method:
the guard fires on it. That trade was accepted deliberately and the doc
comment's "Match rule" paragraph anticipates it.

**But the failure message does not.** A future author who gives some unrelated
type a `Parallel()` method meets a wall of prose about `TRUNCATE`, shared
`sessions`/`users` tables, and `registerWiringTest` — none of which applies to
them. The message is otherwise accurate and genuinely teaches; this is the one
reader it misleads.

One clause closes it — something like: *if the receiver below is not a
`*testing.T`, this guard has over-fired; see its Match rule.*

**Two cosmetic slips, recorded here rather than separately.** Neither is worth a
pass on its own; fold them in if the file is open.

- The message says "reproduced empirically in `#0209`" for a measurement
  `#0165`'s review actually made. The pointer still resolves — `#0209` is where
  it is written down — but the attribution is off by one issue.
- `#0209`'s implementation notes say the guard's doc comment mentions
  `t.Parallel()` eight times; it is seven.

## Fix

One clause, inserted into `TestNoWiringTestUsesParallel`'s failure message
(`cmd/opencircuit/wiring_parallel_guard_test.go`), right before the
`Remove t.Parallel() from:` listing so it reads naturally against the
file:line entries that follow it:

> If the receiver below is not *testing.T (or *testing.B), this guard has
> over-fired -- see this file's Match rule.

Also corrected the attribution the issue flagged: "reproduced empirically in
#0209" (crediting the unregistered-fifth-test measurement to the wrong issue)
is now "reproduced empirically by #0165's phase-3 review" — matching both the
doc comment above it (which already attributed correctly: "Its phase-3 review
measured exactly how well that works") and `#0209`'s own Description ("Its
phase-3 review confirmed the hazard by reproduction... It also confirmed the
gap the guard cannot close").

The "eight times" miscount named in this issue's Notes lives in
`issues/0209.md`'s `## Implementation notes`, not in any file this issue is
scoped to touch (`wiring_parallel_guard_test.go`, message only) — the guard
file's own doc comment never states a count, so there was nothing in scope
to correct. Left `issues/0209.md` untouched per this issue's instruction not
to rewrite `#0209`'s `## Review notes` / `## Implementation notes`.

Did not reach for `go/types`. The method-value and method-expression misses,
and the untyped-match trade generally, are `#0209`'s review's settled
decision — this issue only asked for a message clause, not a behavior
change, and the acceptance criteria confirm that ("this is a message
change, not a behaviour change").

**Judgement: not a net loss, and the placement is the right one.** The clause is
one conditional sentence, 22 words, and it self-dismisses on sight for the
reader who matters most — they look "below", see `t.Parallel()` on a
`*_wiring_test.go` line, and the condition is false. Crucially it does **not**
displace the actionable part: `Remove t.Parallel() from:` still sits immediately
before the file:line list, which is where the eye lands. Putting the clause
after the list, the only obvious alternative, would break its own referent
("the receiver **below**"). The message was already long; this adds a fifth
sentence to four, and it is the only one addressed to a reader the other four
actively mislead.

### The `*testing.B` parenthetical is true, not decorative

Exercised `scanFileForParallelCalls` directly against a `*testing.B` fixture:
`b.Parallel()` in `func BenchmarkX(b *testing.B)` is **caught**, one violation,
text `b.Parallel()` — matching `#0209`'s review. So the parenthetical is
load-bearing in the exact direction it claims: a benchmark author who trips this
guard is **not** an over-fire (the shared-table hazard is identical for a
benchmark), and without the parenthetical the clause would have told them they
were. `cmd/opencircuit` has no `func Benchmark…` today, so this is a claim about
a future reader — but it is a correct one, and it costs four words.
