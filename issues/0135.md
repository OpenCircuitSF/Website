## Description

The two public workshop routes disagree about canceled workshops.

`GET /api/workshops/{slug}` serves `published` **and** `canceled` — deliberate, and confirmed by `#0051`'s phase-3 review as required by that issue's Notes: *"a canceled workshop stays visible… a 404 tells them nothing."*

`GET /api/workshops` does not. `PublicWorkshopsHandler.List` calls `ListPublished`, which returns only `status='published'`, so a canceled workshop silently vanishes from the index.

That is the outcome the detail route's reasoning exists to prevent, one route over. Someone who bookmarked the index sees the workshop disappear with no explanation; only someone holding the direct link learns it was canceled.

`#0053` has an acceptance criterion requiring the index to show canceled workshops with a clear badge. Its implementer built and unit-tested that logic against the `status` field already in the payload, then found it unreachable and said so rather than ticking the box.

## Acceptance criteria

- [ ] Decide and record which route is wrong. The default, absent a reason to prefer otherwise: **the index should include canceled workshops**, matching the detail route and `#0053`'s criterion
- [ ] If the index changes: `ListPublished` (or a sibling) returns canceled alongside published for the public list, and the upcoming/past split still puts them where a reader expects
- [ ] `#0053`'s badge renders for real — an end-to-end check against Postgres with a seeded canceled workshop, not just the existing unit tests
- [ ] The handler tests cover a canceled workshop appearing in the index payload, and drafts still never appearing
- [ ] `#0053`'s currently-unticked "canceled shown with a badge" criterion is ticked here or there, not left floating between the two issues
- [ ] `ISSUE=0135 scripts/check.sh go ./internal/handlers/...` and `scripts/check.sh web` both pass

## Notes

Found by `#0053`'s implementer while building against `#0051`'s committed contract, and relayed to `#0051`'s reviewer mid-review. The reviewer had already ruled on the detail route (`GetBySlug` serving canceled is correct) and resolved `#0051` before the index side could be folded in, so it is filed here rather than bounced into either issue.

`#0053` did not modify `#0051`'s code, correctly — that review was in flight.

One consequence worth deciding deliberately: a canceled *past* workshop in the past list is harmless, but a canceled *upcoming* one is the case that matters, and it is the one a reader is most likely to be checking on.
