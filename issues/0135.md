## Description

The two public workshop routes disagree about canceled workshops.

`GET /api/workshops/{slug}` serves `published` **and** `canceled` — deliberate, and confirmed by `#0051`'s phase-3 review as required by that issue's Notes: *"a canceled workshop stays visible… a 404 tells them nothing."*

`GET /api/workshops` does not. `PublicWorkshopsHandler.List` calls `ListPublished`, which returns only `status='published'`, so a canceled workshop silently vanishes from the index.

That is the outcome the detail route's reasoning exists to prevent, one route over. Someone who bookmarked the index sees the workshop disappear with no explanation; only someone holding the direct link learns it was canceled.

`#0053` has an acceptance criterion requiring the index to show canceled workshops with a clear badge. Its implementer built and unit-tested that logic against the `status` field already in the payload, then found it unreachable and said so rather than ticking the box.

## Notes

Found by `#0053`'s implementer while building against `#0051`'s committed contract, and relayed to `#0051`'s reviewer mid-review. The reviewer had already ruled on the detail route (`GetBySlug` serving canceled is correct) and resolved `#0051` before the index side could be folded in, so it is filed here rather than bounced into either issue.

`#0053` did not modify `#0051`'s code, correctly — that review was in flight.

One consequence worth deciding deliberately: a canceled *past* workshop in the past list is harmless, but a canceled *upcoming* one is the case that matters, and it is the one a reader is most likely to be checking on.

## Root cause

`internal/handlers/public_workshops.go`'s `List` (`GET /api/workshops`) called `workshops.Store.ListPublished`, which filtered `WHERE status = 'published'` in both its upcoming and past queries. `GetBySlug` (`GET /api/workshops/{slug}`) applies a wider rule — published or canceled, only draft 404s — per `#0051`'s Notes ("a canceled workshop stays visible with a clear cancellation notice… a 404 tells them nothing"). The two routes disagreed, so a canceled workshop 200'd on its direct link but silently vanished from the index a bookmarking visitor would check — the exact failure the detail route's own reasoning exists to prevent, one route over. `#0053`'s `isCanceled`/`workshopBadgeLabel` (`web/src/lib/workshops.ts`) were built and unit-tested against the `status` field already in the payload shape, but the index never actually delivered a canceled workshop for them to apply to.

## Fix

**The index was the route that was wrong**, per this issue's own default: the detail route's visibility rule (published-or-canceled) is the one `#0051`'s reviewer confirmed as deliberate; the index's narrower `published`-only filter was the outlier.

- `internal/workshops/store.go`: `Store.ListPublished` → `Store.ListVisible`, renamed (not just re-documented) because the old name would actively mislead anyone reading it after this change — it no longer means "published only." Both the upcoming and past queries now filter `status IN ('published', 'canceled')` instead of `status = 'published'`.
- **Split decision — where a canceled workshop belongs in upcoming/past:** a canceled workshop is placed by the *same* `starts_at` comparison as a published one (upcoming if `starts_at IS NULL OR starts_at >= now`, past otherwise), not forced into "past" or given a third bucket. Reasoning: the case that matters is a canceled workshop whose date hasn't passed yet — a reader checking on a session they planned to attend, per this issue's own Notes. Treating "canceled" as automatically "past" would drop it from the upcoming list even though the reader still has every reason to look for it there, which just delays the silent-vanish problem this issue exists to fix rather than solving it. A canceled workshop safely in the past reads as honest history either way, so there is no cost to using the same rule uniformly for both partitions.
- `internal/handlers/public_workshops.go`: `publicWorkshopStore.ListVisible` (interface renamed to match), `List` calls it, doc comments corrected — both routes now state and apply the same visibility rule (published or canceled; draft invisible to both).
- `migrations/000020_create_workshops.up.sql`: `idx_workshops_published`'s partial predicate widened from `WHERE status = 'published'` to `WHERE status <> 'draft'` so the index still covers `ListVisible`'s query (the index's *name* is left as-is — renaming it isn't necessary for correctness and would just be more surface area to keep in sync, whereas the Go method name misleading a caller who never reads the migration was the concrete risk). Greenfield edit per `CLAUDE.md` §1 — no production deploy has applied this migration.
- `docs/database.md`: corrected the `idx_workshops_published` sentence to match the widened predicate and note why.
- `web/src/lib/workshops.ts`, `web/src/views/WorkshopsIndex.svelte`: header/doc comments updated from "this is currently dead code because the index is published-only" to describe the fix; no logic changes — `isCanceled`/`workshopBadgeLabel` were already correct and are unit-tested by `#0053`.
- **Left alone, deliberately:** `internal/seo`'s sitemap and social-card rendering. `#0051`'s reviewer was explicit that canceled workshops must never appear in the sitemap or an unfurled card, and that exclusion is independent of the public index's own visibility rule — this issue does not touch it.

### Ruling 1 — the migration edit and the widened index

The greenfield exception in `CLAUDE.md` §1 genuinely still applies: nothing is
deployed but the static placeholder (§7), no PostgreSQL instance holds real
data, and `000020` was written in this same session. Editing it in place rather
than stacking an `ALTER INDEX` is the prescribed choice.

The template **was** rebuilt — `pg_indexes` on `opencircuit_test_template`
already read `WHERE (status <> 'draft'::text)` before this review touched
anything, so every per-agent clone carries the widened predicate.

The widened index is **actually used**, checked with `EXPLAIN (ANALYZE)` on 6000
throwaway rows (2000 per status) in this review's own database, not assumed:

```
-- past query, exactly as ListVisible writes it
Sort (actual rows=2010 loops=1)
  Sort Key: starts_at DESC, id DESC
  ->  Bitmap Heap Scan on workshops (actual rows=2010 loops=1)
        Recheck Cond: ((starts_at IS NOT NULL) AND (starts_at < now()) AND (status <> 'draft'::text))
        Filter: (status = ANY ('{published,canceled}'::text[]))
        ->  Bitmap Index Scan on idx_workshops_published (actual rows=2014 loops=1)
              Index Cond: ((starts_at IS NOT NULL) AND (starts_at < now()))

-- upcoming query
->  BitmapOr
      ->  Bitmap Index Scan on idx_workshops_published   Index Cond: (starts_at IS NULL)
      ->  Bitmap Index Scan on idx_workshops_published   Index Cond: (starts_at >= now())
```

The counter-check proves the widening was **necessary**, not cosmetic: with the
old `WHERE status = 'published'` predicate restored inside a rolled-back
transaction, the new query drops to `Seq Scan on workshops`. Had the migration
been left alone, the partial index would have silently stopped being used — the
exact failure mode this review was asked to look for.

**One observation, not a defect.** `pgx` sends these as prepared statements, and
after ~5 executions Postgres switches to a *generic* plan, where `$1`/`$2` are
unknown and `status = ANY(ARRAY[$1,$2])` cannot be proven to imply
`status <> 'draft'` — that plan is `Seq Scan`, verified both by
`SET plan_cache_mode = force_generic_plan` and by executing the statement eight
times under the default `auto`. This is **pre-existing, not a regression**: the
same forced-generic check against the old published-only index and `status = $1`
also yields `Seq Scan`. Per `CLAUDE.md` §5 there is no performance requirement
here and the real table will hold tens of rows, so nothing is owed. Writing the
filter as the literal `status <> 'draft'` would make it generic-plan-stable if
anyone ever wants that, at the cost of coupling the query to "not draft" rather
than to an explicit status list.

heading, not "Past workshops". The reasoning recorded in `## Fix` (the
