## Description

Every modal in the admin console binds Escape-to-close on the **backdrop**:

```svelte
<div class="modal-backdrop" role="presentation"
     onclick={close}
     onkeydown={(e) => { if (e.key === 'Escape') close(); }}>
  <div class="modal" role="dialog" aria-modal="true" tabindex="-1"
       onclick={(e) => e.stopPropagation()}
       onkeydown={(e) => e.stopPropagation()}>
```

The panel's `onkeydown={(e) => e.stopPropagation()}` — added to mirror the
click guard that keeps a click inside the panel from dismissing it — stops the
keydown from ever bubbling to the backdrop. Since focus is inside the panel
whenever the dialog is open, **the backdrop's Escape handler is unreachable
dead code** and Escape never closes the dialog.

A `role="dialog" aria-modal="true"` with no Escape is an accessibility defect:
a keyboard user has no way out except finding and activating the Cancel button.

## Steps to reproduce

1. Open the admin console, go to any section with a modal (Users → Deactivate,
   Interests → Edit, Subscribers → detail or Suppress, Campaigns → New campaign,
   Cancel campaign, or the send confirmation dialog).
2. Press Escape.

## Expected behavior

The dialog closes.

## Actual behavior

Nothing happens.

## Notes

Repo-wide, not a regression: `web/src/views/Admin.svelte` carries the pattern at
six sites (~lines 1049, 1317, 1539, 1625 and the rest), and `#0047`'s three new
components reproduced it faithfully because the plan told the implementer to
follow the existing modal markup. Found by `#0047`'s phase-3 review.

The fix is a keydown listener on the dialog panel itself (or a `svelte:window`
one gated on the open flag) rather than on the backdrop — and the panel's
keydown `stopPropagation` should be dropped, since there is no keyboard analogue
of the click-outside-to-dismiss behaviour it was mirroring.

While in there: a modal with `aria-modal="true"` should also trap Tab within the
panel; none of these do. That belongs to the same fix or to `#0063`.

## Focus is also lost on a state swap inside an open modal (found 2026-08-22)

`#0052`'s phase-3 review, pass 2, verified a second instance of the same
console-wide gap while confirming that issue's modal fix.

`#0052` landed the pattern this issue wants — `bind:this` on the panel plus
`$effect` + `tick().then(() => el?.focus())` — and its three modals now take
focus and close on Escape, verified in a real browser against the compiled
components. But when `WorkshopEditor.svelte`'s delete modal swaps to its 409
conflict state, the `{#if deleteConflict}` branch removes the focused Delete
button. Chromium reverts `activeElement` to `<body>`, outside the backdrop
subtree, and **Escape stops working** until one Tab moves focus back inside.
The `$effect` does not re-fire, because neither the open flag nor the element
binding changed.

Not a regression — strictly better than the state this issue describes, one
case short — but it is the same defect wearing different clothes, and it is
why the fix wants to be focus *management* (trap, restore, re-focus on
content change) rather than a single `focus()` call per modal.

**Does `CampaignSendDialog` still have this shape after `#0195`/`#0197`?**
Yes, unchanged. Those two issues reworked `sendGuardState`'s branch order and
built a structural guard around the count-input/Escape/backdrop *gate
expressions* (`sending`, `!sending`), but neither touched the
*stopPropagation* structure this issue is about — the panel
(`role="dialog"`) still had `onkeydown={(e) => e.stopPropagation()}` right
next to `bind:this={dialogEl}` and the `$effect` that focuses it, exactly the
shape the issue describes, with focus genuinely inside the panel the whole
time the dialog is open (confirmed by reading the `$effect` at what is now
line ~96).

**Why each `stopPropagation` was there, and what would break if it were
removed carelessly:** every site pairs it with `onclick={(e) =>
e.stopPropagation()}` on the same panel element — the click guard that stops
a click *inside* the panel from bubbling to the backdrop's
click-outside-to-dismiss `onclick`. The keydown handler was written to
"match" that shape, but there is no keyboard analogue of "inside vs. outside
the panel" — nothing about *where* a key is pressed makes it a
click-outside-equivalent. Removing it is safe: no click behavior depends on
it, only the (broken) keydown path did.

**A second, compounding defect found while establishing blast radius, not
named in the issue's own root-cause paragraph:** of the 8 broken sites, only
`CampaignSendDialog.svelte` actually moves focus into the panel on open
(`bind:this={dialogEl}` + `$effect(() => tick().then(() =>
dialogEl?.focus()))`). The other 7 (5 in `Admin.svelte`, 1 in
`CampaignEditor.svelte`, 1 in `Campaigns.svelte`) had **no focus management
at all** — confirmed by grepping each file's `open*`/`close*` functions for
`focus()`/`bind:this`/`$effect`, finding none. So for those 7, simply
deleting the panel's `stopPropagation` would not have been sufficient on its
own: focus stays on whatever trigger element was clicked (still present in
the underlying list/table), so a keydown never reaches either the panel or
the backdrop regardless of what either handler does. The fix for those 7
therefore has two parts, not one.

**Fix shape — one shared function, applied per the two situations found:**

- `web/src/lib/modalKeydown.ts` (new): exports `isModalEscape(e, dismissible
  = true)`, the single place that decides whether a keydown event should
  dismiss a modal. Plain TypeScript, unit-tested directly
  (`modalKeydown.test.ts`, 5 cases) — the pure-logic half of the fix, per
  CLAUDE.md's "SPA logic goes in plain TypeScript modules ... Svelte
  components stay thin."
- **The 7 sites with no focus management** (5×`Admin.svelte`,
  `CampaignEditor.svelte`'s cancel dialog, `Campaigns.svelte`'s create
  dialog): each now gets `bind:this={xEl}` + a `$effect` that calls
  `tick().then(() => xEl?.focus())` when the modal opens — the exact shape
  `#0052` already established and had verified working in a real browser for
  `WorkshopEditor.svelte`/`Workshops.svelte` — plus the panel's
  `onkeydown={(e) => e.stopPropagation()}` replaced with `onkeydown={(e) => {
  if (isModalEscape(e)) closeX(); }}` (the backdrop's existing handler was
  also switched to call `isModalEscape` for consistency, a behavior-preserving
  rename since it was already `e.key === 'Escape'`). Every `closeX` call site
  is the exact same function the backdrop's `onclick` already calls
  unconditionally, so Escape now does precisely what a backdrop click already
  does — no new gating invented.
- **`CampaignSendDialog.svelte`** (the one site that already had working
  focus management): a deliberately smaller change, because
  `CampaignSendDialog.structuralGuard.test.ts` (`#0197`) reads
  `handleKeydown`'s `e.key === 'Escape' && !sending` expression verbatim off
  the **backdrop's** `onkeydown` attribute by name and by AST shape.
  Rewriting `handleKeydown` to call `isModalEscape(e, !sending)` would change
  that expression's shape and break the guard — which the task brief is
  explicit is not to be done casually. Re-reading the guard's own source
  (`findKeydownHandlerName`/`findEscapeGate` in
  `CampaignSendDialog.structuralGuard.test.ts`) confirmed it inspects only
  the backdrop's `onkeydown`, never the panel's — so the fix here is binding
  the **same `handleKeydown` function reference** (not a copy, not a
  rewrite) to the panel's `onkeydown` too, in place of the stopPropagation
  guard. This satisfies `#0197`'s guard completely unmodified (verified by
  running it, below), keeps one function as the single source of truth for
  this dialog's Escape rule, and was also needed to keep `npm run check`
  clean — deleting the panel's `onkeydown` outright (my first attempt)
  introduced a new `svelte-check` a11y warning
  (`a11y_click_events_have_key_events` on the panel's `onclick`), which
  binding `handleKeydown` there resolves the same way the other 7 sites'
  duplicated handler does.
- **`WorkshopEditor.svelte` / `Workshops.svelte`** (already fixed under
  `#0052`, browser-verified working): left untouched. They already use the
  bind:this + `$effect` + panel-Escape-check shape this issue wants, and with
  no DOM harness available (`#0094` still open) there is no way to re-verify
  a refactor onto `isModalEscape` in a real browser here — the honest
  trade-off was to accept two components with an inline
  `e.key === 'Escape'` check instead of a call to the shared helper, rather
  than risk regressing code a prior reviewer already confirmed working, for
  a purely cosmetic unification.

**Testability — what is proved by execution vs. what is not.** `#0094` is
still open: no DOM harness, no `.svelte` file is imported by a test, so a
real click-and-Escape interaction cannot be driven here. Two things ARE
executed and proven:

1. `modalKeydown.test.ts` — `isModalEscape`'s full truth table (Escape vs.
   any other key, `dismissible` true/false/default). This is the actual
   decision logic every fixed site now calls.
2. `modalEscapeGuard.test.ts` (new) — a repo-wide **structural** guard, in
   the `citationGuard.test.ts`/`CampaignSendDialog.structuralGuard.test.ts`
   style (`svelte/compiler`'s `parse({ modern: true })` AST, no DOM):
   `import.meta.glob('../views/**/*.svelte', ...)` walks every `.svelte`
   file under `web/src/views`, finds every `role="dialog" aria-modal="true"`
   element, and fails if that element's `onkeydown` is exactly the
   blind-stopPropagation shape (concise or block-body arrow function whose
   sole statement calls `<param>.stopPropagation()`), by AST shape rather
   than a text grep, so it isn't fooled by comments or a differently-named
   event parameter. This is a durable regression net, and it is proved
   against the real pre-fix tree, not just synthetic fixtures: stashed this
   issue's four component edits (`git stash push -u`, keeping the new guard
   test itself in place) and re-ran just this file against the untouched
   originals — it failed, naming **all 8** sites by exact file, line, and
   `aria-label` (`Admin.svelte:1126/1411/1633/1723/1833`,
   `CampaignEditor.svelte:835`, `CampaignSendDialog.svelte:129`,
   `Campaigns.svelte:243`), then popped the stash and re-ran green. It will
   also catch a **future** modal built by copying old markup, exactly the
   way `#0047`'s three components reproduced this bug by copying an existing
   modal. 8 synthetic-fixture cases further pin what it does and does not
   catch (matching or missing `role`/`aria-modal`, a differently-named event
   param, the block-body variant, an absent handler, a handler that
   correctly checks the key or calls `isModalEscape`).

**What this does NOT prove:** that pressing Escape in a real browser actually
closes each dialog, or that the new `$effect`s actually move focus where
intended (a `bind:this` typo, e.g., would not be caught by anything above —
`svelte-check`'s type-checking is the only mechanical check on that, and it
passed). That gap is `#0094`'s, not something this fix can close on its own.

**Tab trapping** (the issue's own "while in there" note) was left out of
scope, per the issue's own text ("belongs to the same fix or to `#0063`") —
this fix is Escape-and-focus-on-open only, not a full focus trap.
