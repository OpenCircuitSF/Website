# 0120 — Escape does not close any admin modal: the panel's `stopPropagation` keydown guard eats the key before the backdrop's handler runs

| | |
|---|---|
| **Status** | open |
| **Module** | web / admin |
| **Platform** | All |
| **Phase** | 7 — Inbound and polish |
| **First seen** | 2026-08-21 |

## Description

Every modal in the admin console binds Escape-to-close on the **backdrop**:

```svelte
<div class="modal-backdrop" role="presentation"
     onclick={close}
     onkeydown={(e) => { if (e.key === 'Escape') close(); }}>
  <div class="modal" role="dialog" aria-modal="true" tabindex="-1"
       onclick={(e) => e.stopPropagation()}
       onkeydown={(e) => e.stopPropagation()}>
```

The panel's `onkeydown={(e) => e.stopPropagation()}` — added to mirror the
click guard that keeps a click inside the panel from dismissing it — stops the
keydown from ever bubbling to the backdrop. Since focus is inside the panel
whenever the dialog is open, **the backdrop's Escape handler is unreachable
dead code** and Escape never closes the dialog.

A `role="dialog" aria-modal="true"` with no Escape is an accessibility defect:
a keyboard user has no way out except finding and activating the Cancel button.

## Steps to reproduce

1. Open the admin console, go to any section with a modal (Users → Deactivate,
   Interests → Edit, Subscribers → detail or Suppress, Campaigns → New campaign,
   Cancel campaign, or the send confirmation dialog).
2. Press Escape.

## Expected behavior

The dialog closes.

## Actual behavior

Nothing happens.

## Notes

Repo-wide, not a regression: `web/src/views/Admin.svelte` carries the pattern at
six sites (~lines 1049, 1317, 1539, 1625 and the rest), and `#0047`'s three new
components reproduced it faithfully because the plan told the implementer to
follow the existing modal markup. Found by `#0047`'s phase-3 review.

The fix is a keydown listener on the dialog panel itself (or a `svelte:window`
one gated on the open flag) rather than on the backdrop — and the panel's
keydown `stopPropagation` should be dropped, since there is no keyboard analogue
of the click-outside-to-dismiss behaviour it was mirroring.

While in there: a modal with `aria-modal="true"` should also trap Tab within the
panel; none of these do. That belongs to the same fix or to `#0063`.

## Focus is also lost on a state swap inside an open modal (found 2026-08-22)

`#0052`'s phase-3 review, pass 2, verified a second instance of the same
console-wide gap while confirming that issue's modal fix.

`#0052` landed the pattern this issue wants — `bind:this` on the panel plus
`$effect` + `tick().then(() => el?.focus())` — and its three modals now take
focus and close on Escape, verified in a real browser against the compiled
components. But when `WorkshopEditor.svelte`'s delete modal swaps to its 409
conflict state, the `{#if deleteConflict}` branch removes the focused Delete
button. Chromium reverts `activeElement` to `<body>`, outside the backdrop
subtree, and **Escape stops working** until one Tab moves focus back inside.
The `$effect` does not re-fire, because neither the open flag nor the element
binding changed.

Not a regression — strictly better than the state this issue describes, one
case short — but it is the same defect wearing different clothes, and it is
why the fix wants to be focus *management* (trap, restore, re-focus on
content change) rather than a single `focus()` call per modal.
