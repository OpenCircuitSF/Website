## Description

`internal/handlers/audit_email_metadata_guard_test.go` (`#0237`) exists to
catch audit-metadata call sites that write a subscriber email address without
being registered in `auditEmailMetadataKnownSites` and disclosed in
`PrivacyPolicy.svelte`. It classifies a site by matching metadata keys against
a set of suspect tokens.

**It does not recognise `"from"`.** `#0499` added a call site
(`internal/handlers/ses_inbound.go`, `recordParked`) that writes a `from` key
holding a real email address, and the guard classified it as carrying no email
at all.

This was measured rather than inferred: `#0499`'s reviewer ran
`scanAuditEntrySites` directly against the new site and got
`hasEmail=false, unresolved=""` — a **classification miss**, not one of the
structural blind spots the guard's own doc comment already documents.

`"from"` is the canonical email-bearing header name in the inbound subsystem,
and its counterpart `"to"` is *already* a suspect token, so the omission is an
inconsistency rather than a deliberate line.

## The trap: adding `"from"` as a token is not free

`#0499`'s reviewer censused all 205 distinct string-literal map keys across
production `internal/` and `cmd/` before recommending anything. The result
matters, because the obvious fix breaks:

- **`"from_status"`** — written by `admin_campaigns.go` for a campaign
  draft→sending transition. Under the guard's tokenising rule it splits to
  `from` / `status` and would become a **false positive**. This is exactly the
  `"recipients"` hazard the guard's own doc comment records.
- **`"subject"` is separately unsuitable** as a token, for the same reason in
  reverse: `delivery_health.go`'s `"subject"` and `admin_campaigns.go`'s
  `"old_subject"` / `"new_subject"` hold our own campaign copy, not a personal
  address.

So this needs an **exact-key match or a compound-token rule**, not another
entry in the substring list. `"sender"` is worth considering in the same pass.

## Acceptance criteria

1. The `recordParked` site in `internal/handlers/ses_inbound.go` is classified
   as email-bearing by the guard's own scanner.
2. `admin_campaigns.go`'s `"from_status"` is **not** classified as
   email-bearing — assert this explicitly, since it is the specific regression
   this issue exists to prevent.
3. Whatever rule is chosen is recorded in the guard's doc comment, including
   why a plain substring token was insufficient.
4. The guard's existing fixture continues to pass in **both** directions — it
   fails on drift either way, so a widened scanner requires the fixture updated
   in the same change.
5. Re-run the 205-key census, or an equivalent, and confirm no other false
   positive appears. Say what you searched.

## Notes

The guard's own header warns that widening it "should always be a deliberate,
reviewed change to this file, not a byproduct". This issue is that deliberate
change. Note also `CLAUDE.md` §8's rule about a guard's oracle not being the
same bytes as its subject — the fixture and the scanner must stay independent
representations.
