## Description

`#0429` fixed the two `.env.example` lines whose trailing `#` comments made
`opencircuit.service` refuse to boot, and added a targeted regression test for
**those two lines**. It did not add a general scan, so the next line written in
one of the other divergent shapes lands the same way.

The divergence is structural and will not go away: `.env.example` is read by two
different parsers with different rules.

| Shape | systemd `EnvironmentFile=` | `godotenv` |
|---|---|---|
| trailing `# comment` on a value line | part of the value | stripped |
| `$VAR` / `${VAR}` in a value | literal — no expansion | **expanded** |
| `export ` prefix | syntax error or literal | accepted and stripped |
| trailing `\` line continuation | continues the line | does not |

> **Row 2 was written inverted and is corrected above (reviewer, 2026-09-05).**
> The original text claimed systemd expands and `godotenv` is literal. It is
> the other way round, confirmed three independent ways: `joho/godotenv`
> v1.5.1's `parser.go` (`extractVarValue` → `expandVariables`, driven by
> `expandVarRegex`) expands in unquoted and double-quoted values; a runtime
> probe against the real library expands `x${A}y` and `x$Ay` to `xoney`; and
> systemd's `EnvironmentFile=` performs no shell-style expansion at all,
> keeping the literal `$`. The error was the issue author's, not the
> implementer's — the shipped failure messages already describe the correct
> direction. Rows 1, 3 and 4 were each checked independently and are correct
> as written. The divergence is real either way, so the issue stands unchanged
> in substance.

`#0423` is what makes this load-bearing: `docs/deployment.md`'s install step is
a literal `sudo cp .env.example /etc/opencircuit/config.env`, so
**`.env.example` is the production configuration template**. A shape that the
two parsers read differently is a boot failure or, worse, a silently wrong
value on the documented happy path.

Reported by `#0428`'s implementer, which deliberately did **not** build it while
fixing the loader-extraction guard — two mechanisms in one file is `#0258`'s
spiral, and this closes a different gap from that one. That restraint was right.

## Acceptance criteria

1. A test scans `.env.example`'s **value** side for the four shapes above and
   fails naming the offending line and which parser would disagree.
2. It must **fail closed on an empty extraction** (§8). A scan that parses zero
   lines and reports success is the bug class this project has already shipped
   twice — assert the scan saw a plausible number of lines before concluding
   anything.
3. Do not duplicate `#0429`'s targeted test; either widen it in place or replace
   it, and say which in the work log.
4. Decide whether the same scan belongs against **production's own**
   `config.env`. It probably does not — reading it needs `sudo` on a secrets
   file and `#0415` owns the question of what it currently contains — so record
   the decision rather than leaving it implicit.
5. Consider whether a shape should be *forbidden outright* in the template
   versus merely flagged. `export ` has no legitimate use here; `$VAR` might.

## Root cause

`TestEnvExampleCoversLoaderVariables` (`#0423`/`#0428`) only proves loader ⊆
`.env.example` on the **name** side of `NAME=value` lines; its own doc
comment already disclaimed the value side as a gap left to `#0429`'s
judgment. `#0429`'s `TestLoad_EnvExampleValuesAreSystemdParseable`
(`config_test.go`) closed that gap only for the two lines that actually broke
boot, via hardcoded historical strings — it does not read `.env.example`'s
text at all, so a new line written in any of the other three divergent
shapes (or a fresh trailing-comment line elsewhere) would land with nothing
to catch it before `docs/deployment.md`'s `sudo cp .env.example
/etc/opencircuit/config.env` install step ships it.

## Fix

Added `scanEnvExampleValueShapes` and three tests to
`internal/config/env_example_guard_test.go`:

- `TestEnvExampleValuesAvoidDivergentParserShapes` — reads the real
  `.env.example`, scans every `KEY=VALUE` line (an optional `export ` prefix
  plus a name shaped like `envVarNameLiteral`) for all four shapes in the
  issue's table, and fails naming the line, the value, and which parser
  (systemd's `EnvironmentFile=` vs. `joho/godotenv` v1.5.1, the library
  `config.go` actually uses) would disagree.
- `TestEnvExampleValueShapeFloorFailsClosedOnEmptyExtraction` — criterion 2's
  direct proof. The floor assertion was pulled out of the test body into a
  plain function, `checkScannedFloor(scanned, floor int) error`, specifically
  so this proof could call it directly with a synthetic zero-assignment
  extraction and assert a non-nil error, without going through `t.Run` (a
  subtest built to fail on purpose would mark this test's own parent
  permanently failed under Go's subtest-propagation rules — caught by running
  it and reading the result, not by reasoning about it in advance).
- `TestScanEnvExampleValueShapes_DetectsEachDivergentShape` — table-driven,
  one case per shape, against synthetic content independent of whatever
  `.env.example` currently contains.

**Criterion 3 — widened, not replaced.** `#0429`'s
`TestLoad_EnvExampleValuesAreSystemdParseable` keeps both its original
subtests unchanged; only its doc comment was widened to state explicitly why
it is not a duplicate of the new scan: it is a *behavioral* proof that
`config.go`'s `getInt`/`getBool` genuinely reject the literal value systemd's
`EnvironmentFile=` would have produced for the two historical lines
(exercised via `t.Setenv`, independent of what `.env.example`'s text
contains today), while the new test is a *text-shape* proof over the file's
actual content. The other three shapes ($VAR expansion, `export ` prefix,
trailing backslash) don't corrupt a numeric/bool field the way a trailing
comment does, so there is no `config.go`-level rejection to generalize that
test toward — widening its assertions to those shapes would have been
manufactured, not real, coverage. Per CLAUDE.md §8 ("the two homes are not
exclusive"), keeping both is deliberate.

**Criterion 4 — recorded, not built.** The scan does not read production's
own `/etc/opencircuit/config.env`. Reading it needs `sudo` on a secrets file
whose actual contents `#0415` separately owns, and this repo's test suite has
no way to observe that out-of-band drift regardless — `.env.example` is the
thing the repo can see and is the documented install source.

**Criterion 5 — forbid outright, not merely flag.** All four shapes are
`t.Errorf` failures, not warnings. `.env.example` is the literal production
template (`#0423`); every one of the four shapes either fails to boot or
silently loads a different value than the one written down, and none has a
currently legitimate use in this file. `export ` in particular has no
legitimate use here at all. `$VAR`/`${VAR}` is the one shape with a
conceivable future legitimate use (templating one value from another); until
a variable genuinely needs it, forbidding it outright is the safer default —
widening the scan for one specific, deliberate line is a smaller and more
visible change than softening the check globally.

`.env.example` itself needed no fix — the new scan reports zero violations
against the current file.

**One correction to this issue's own table, found while implementing (not
edited here — flagged for the reviewer):** row 2 (`$VAR`/`${VAR}`) states
systemd `EnvironmentFile=` **expands** and `godotenv` is **literal**. Reading
`joho/godotenv@v1.5.1`'s `parser.go` (`extractVarValue` → `expandVariables`,
using `expandVarRegex`) shows the opposite: godotenv **does** expand
`$VAR`/`${VAR}` in unquoted and double-quoted values (against variables
assigned earlier in the same file, substituting empty string if undefined),
while systemd's `EnvironmentFile=` performs no shell-style expansion at
all and keeps a literal `$`. The other three rows (trailing comment, `export
`, trailing backslash) were verified consistent with the issue's table. The
divergence itself is real either way; only the *direction* of row 2 is
inverted. The new test's failure messages describe the verified-correct
direction rather than the table's.

## Gotchas

- A `t.Run` subtest that is built to fail on purpose (to prove a floor check
  fails closed) marks its **parent** test permanently failed under Go's
  subtest semantics, regardless of what the parent does with the subtest's
  bool return afterward. First draft of
  `TestEnvExampleValueShapeFloorFailsClosedOnEmptyExtraction` used `t.Run` for
  exactly this and made the whole package permanently red. Fixed by pulling
  the floor assertion into a plain `func(scanned, floor int) error` called
  directly, with no `*testing.T` in the failure path being proved.
- `joho/godotenv@v1.5.1` actually expands `$VAR`/`${VAR}` (see `parser.go`'s
  `expandVariables`), which is the opposite of what this issue's own table
  states for that row — see the correction above.

### The Description table — my error, not the implementer's

I wrote the table and **row 2 is inverted**; it is corrected in place above,
with the correction noted beside it. Confirmed three ways:

1. **Source.** `joho/godotenv` v1.5.1's `parser.go` runs every unquoted value
   through `expandVariables`, and every double-quoted value through
   `expandVariables(expandEscapes(...))`, driven by `expandVarRegex`.
2. **Runtime probe** against the real library: `x${A}y` and `x$Ay` both resolve
   to `xoney`; an undefined name substitutes the empty string.
3. **systemd.** `EnvironmentFile=` performs no shell-style expansion —
   expansion is a property of command lines, not of environment files — so the
   `$` survives literally.

The other three rows I checked independently and all are correct as written:

- **Row 1 (trailing comment).** `extractVarValue` walks the line backward and
  truncates at a `#` preceded by whitespace, so godotenv strips it; systemd has
  no mid-line comment syntax and keeps it. This is the shape that actually
  broke boot in `#0429`, so it is confirmed empirically as well as by reading.
- **Row 3 (`export ` prefix).** `locateKeyName` trims an `export` prefix when
  followed by whitespace. systemd has no such keyword.
- **Row 4 (trailing backslash).** systemd's environment-file parser treats a
  trailing backslash as a line continuation; godotenv's unquoted path reads to
  end of line and keeps the backslash in the value.

The implementer was right to flag this and right not to edit the issue itself.

### Criterion 2 — the fail-closed proof is genuine, and stronger than claimed

The `t.Run` obstacle is real. I reproduced it in a standalone module: a parent
that does nothing but observe the subtest's `false` return is still reported
`FAIL`, because `Fail()` recurses into the parent. So the proof genuinely could
not be driven through a subtest, and extracting the assertion into a plain
`func(scanned, floor int) error` is the correct fix rather than a stylistic
one.

Three mutations against the real, compiled guard in a throwaway worktree:

| Mutation | Result |
|---|---|
| `.env.example` gutted to comments only | `TestEnvExampleValuesAvoidDivergentParserShapes` **fails**, naming the floor — fails closed |
| `minScannedEnvExampleAssignments` forced to `0` | `TestEnvExampleValueShapeFloorFailsClosedOnEmptyExtraction` **fails** |
| the `checkScannedFloor` call deleted from the real guard | that test goes quiet, but `TestEnvExampleCoversLoaderVariables` **fails** on the same gutted file |

The second row is the one worth recording, and it is better than the
implementer claimed. `CLAUDE.md` §8 warns that a floor forced to `0` can never
fire, so the proof belongs in an external harness. That warning does not bite
here: the proof passes the **package constant** into `checkScannedFloor` rather
than a hardcoded `20`, so zeroing the constant makes the proof itself fail.
This is the legitimate in-package case, not the circular one.

The third row is the residual gap, and it is honest to name it: nothing pins
that the real guard still *calls* the floor. That is `#0258`'s
"a guard inside the file it guards" limit, and buying it off would mean an
external harness for one call site. The sibling name-side guard already fails
on the only input that would exploit it, so the fail-open is not reachable in
practice.

### The four shapes, re-derived against the real guard

The implementer proved these through a harness that **duplicated the scan
verbatim**, which is a copy of the subject agreeing with itself — weaker
evidence than it looks, and correctly flagged as such in my dispatch. I redid
it properly: a detached worktree at the commit under review, one shape appended
to `.env.example` at a time, running the real test binary. Baseline clean;
each injection produced **exactly one** violation naming the right line number,
the right variable, and both parsers:

- `SEND_BATCH_SIZE=50    # keep small` → trailing-comment violation
- `EMAIL_FROM=contact@${EMAIL_LIST_DOMAIN}` → expansion violation
- `export PORT=8080` → export-prefix violation
- `BASE_URL=https://www.opencircuitsf.com\` → continuation violation

The worktree was removed and the shared tree never touched (§8a).

### Criterion 3 — widening rather than replacing is correct, and now proved

The implementer argued the division; I tested it. Loosening `getInt` to
tolerate a trailing comment — a loader-side regression with `.env.example`'s
text left untouched — is caught **only** by `#0429`'s
`TestLoad_EnvExampleValuesAreSystemdParseable`; the new text-shape scan passes
clean. The converse holds by construction: a newly added bad line is caught
only by the new scan. The two observe different things and neither subsumes the
other, so keeping both is right and the doc-comment widening states the reason
accurately.

### Criterion 5 — hard-failing all four is right, including `$VAR`

`.env.example` is copied verbatim onto production, so a shape the two parsers
read differently is a boot failure or a silently wrong value on the documented
happy path. A warning nobody sees is not a guard. `$VAR` was the one I pushed
on, since godotenv genuinely expands it and a value containing a literal `$` is
imaginable in a secret — but the file ships `SESSION_SECRET` blank and
`DATABASE_URL` with an obvious placeholder by design, so no shipped value needs
a `$` today. Forbidding it and widening later for one deliberate, reviewed line
is the smaller and more visible change. Agreed with the implementer.

### One precision finding, not a defect — worth a follow-up issue

godotenv's `expandVarRegex` names variables with the class `[A-Z0-9_]+`, which
**includes digits in the leading position**. The guard's detector requires a
letter or underscore first, so a value like `PRICE=cost$5` is not flagged —
yet godotenv expands `$5` to the empty string (yielding `cost`) while systemd
keeps `cost$5`. Verified against the real library. That is a genuine
divergence the scan misses.

It is not a bounce: `$5` is neither `$VAR` nor `${VAR}`, so it is outside the
row the criteria name, and the miss is a narrow sub-case rather than a
fail-open. The imprecision runs the other way too — the detector flags
lowercase `$var` and single-quoted `'$VAR'`, neither of which godotenv expands
— but that direction is the conservative one and is exactly what criterion 5
chose. Recommend a follow-up widening the detector's leading character class to
include digits; reported rather than filed, per §9.

### One mechanism, not a stack

One scan, one floor, and two tests that prove the scan and the floor do what
they claim. The two proof tests are falsifiability checks **on** the mechanism,
not independent defenses of the same file, so this is not `#0258`'s spiral.
The pre-existing name-side guard is a separate mechanism that predates this
issue and covers the gap this one explicitly excluded.
