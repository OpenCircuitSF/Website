## Description

`cmd/opencircuit` and `internal/handlers` fail with `context deadline exceeded` when the machine is loaded — observed by an agent working `#0076` while two other agents were running builds, browsers and Postgres. Run alone on an idle machine the same packages pass comfortably:

```
ok  cmd/opencircuit    0.727s
ok  internal/handlers  1.801s
ok  cmd/opencircuit    0.518s   (repeat)
```

So these are **load-induced flakes, not defects**. That is precisely why they matter.

## Why this is worth fixing rather than tolerating

`CLAUDE.md` §5's verification contract is the backbone of this project's process: every issue is gated on "zero failures, zero skips", and reviewers are told to read output rather than trust exit codes. A suite that fails for reasons unrelated to the change under test corrodes that directly — it teaches the next agent that a red run is probably someone else's noise.

That already happened. The `#0076` agent hit these failures and had to reason about whether they were its own; earlier, another agent hit a temp file left in the shared tree and had to do the same. Each time the correct conclusion was reached, but the cost is real and the failure mode is a genuine defect being waved away.

## Where the deadlines are

`cmd/opencircuit/admin_wiring_test.go` (lines 64, 163, 247) and `ratelimit_wiring_test.go` (lines 39, 154) use 30 s and 5 s timeouts, including a `waitForHealthy` poll that gives a freshly started server 5 s to answer `/health`. On an idle machine that is ample; under four concurrent agents it is not.

## Acceptance criteria

- [ ] Wiring tests no longer fail on a loaded machine. Demonstrate it: run the suite while generating substantial concurrent load and show it green, then show the current code failing under the same load
- [ ] Prefer removing the timing dependency over enlarging the timeout where possible — polling with a generous cap is better than a fixed sleep, and a readiness signal is better than polling
- [ ] Any remaining deadline is justified in a comment: what it is waiting for and why that bound
- [ ] `go test ./... -count=1` green, and `-count=2` green, with `TEST_DATABASE_URL` exported and zero skips

## Notes

Do **not** fix this by deleting the wiring tests. They are the only checks that exercise real route registration — `#0024`'s bounce turned on exactly that distinction, where a hand-built mux passed while `main.go` was unguarded.

Consider whether `t.Parallel()` usage, shared listeners, or the `internal/db` advisory lock contribute. `#0082`'s reviewer noted the docs-parity test queues behind that lock despite needing no database, which is a related symptom.

Enlarging timeouts is the fallback, not the goal — a 30 s timeout that passes under load still means a 30 s wait when something is genuinely broken.

## Fix

Two independent problems were removed rather than papered over:

1. **`waitForHealthy`'s readiness polling** used to loop `GET /health` (a
   real network + DB round trip) against a fixed 5s wall-clock deadline.
   Under heavy load that deadline itself could be exceeded before the
   listener ever came up. Fixed by giving `mountAndServe` a new optional
   `ready chan<- struct{}` parameter, closed the instant the TCP listener is
   bound (`net.Listen`) — before `srv.Serve` is even called, so it needs no
   network round trip and is not sensitive to machine load. `mountAndServe`
   now binds the listener synchronously (`net.Listen` then `srv.Serve(ln)`,
   replacing `http.ListenAndServe`) so a bind failure also returns directly
   instead of via a goroutine hop through `errCh`. `waitForHealthy` waits on
   `ready` (bounded by a new `wiringReadinessDeadline`, 10s — justified in
   its own doc comment as NOT load-sensitive, since it doesn't depend on any
   request completing), then makes exactly one confirming `GET /health`
   request to prove the full handler stack (including the DB ping)
   actually answers.
2. **The remaining real HTTP/DB round-trip timeouts** (a single request, a
   single `TRUNCATE`/`DELETE`) have no polling or signal substitute — the
   ceiling is the only lever. These were flat `5 * time.Second` literals
   repeated across `admin_wiring_test.go`, `ratelimit_wiring_test.go`,
   `subscribe_wiring_test.go`, and `shutdown_wiring_test.go`. Consolidated
   into two documented, shared constants in `ratelimit_wiring_test.go`
   (`wiringHTTPTimeout`, `wiringDBOpTimeout`, both 20s) used by all four
   files, each with a comment recording what it bounds and the load test
   that justified the value (see Verification).

**On the issue's "consider `t.Parallel()`, shared listeners, or the
`internal/db` advisory lock" note**: confirmed `cmd/opencircuit` is one of
eight packages (`internal/audit`, `internal/auth`, `internal/db`,
`internal/handlers`, `internal/middleware`, `internal/subscribers`,
`internal/interests`, `cmd/opencircuit`) that call `testdb.Lock()` from
their own `TestMain`, serializing their entire test-binary run against every
other such package via one shared Postgres advisory lock. This can make
`cmd/opencircuit`'s tests wait a long time to even START under concurrent
`go test ./...` runs from other agents, but that wait has no `context`
attached to it (`testdb.Lock` blocks on `pg_advisory_lock` with
`context.Background()`, no timeout) — it manifests as a slow start, not a
"context deadline exceeded" once the test binary is actually running. This
is a real, separate cost (confirmed while reproducing: a naive load
generator that kept re-acquiring the lock in a tight loop stalled
`cmd/opencircuit`'s tests over 200s before they even began) but is not the
mechanism behind THIS issue's reported failures, so it was not changed
here — flagging it as a candidate for a future, separately-scoped issue if
it proves costly in practice. No `t.Parallel()` is used anywhere in this
package; the wiring tests already run sequentially.

## Verification

**Reproduced the failure first**, on the current (pre-fix) code, using
`pgbench` (`-c 40 -j 12`, a CPU-heavy custom script) plus ~140 `yes`
processes as concurrent load (load average ~150-200 on a 12-core machine —
substantially heavier than the "two other agents" the issue describes) and
`GOMAXPROCS=1` on the test binary to make it maximally susceptible to
scheduling contention:

```
admin_wiring_test.go:80: truncate tables: timeout: context deadline exceeded
admin_wiring_test.go:77: truncate tables: context deadline exceeded
--- FAIL: TestMountAndServe_AdminRoutesRequireSessionAndAdmin (13.06s)
--- FAIL: TestMountAndServe_RateLimitsAuthLoginStart (14.61s)
shutdown_wiring_test.go:154: POST /api/subscribe: Post "http://127.0.0.1:58849/api/subscribe": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
--- FAIL: TestMountAndServe_SIGTERMReleasesInFlightClaim (19.64s)
subscribe_wiring_test.go:104: request 1: Post "http://127.0.0.1:58870/api/subscribe": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
--- FAIL: TestMountAndServe_RateLimitsSubscribe (16.76s)
FAIL	github.com/brennanMKE/OpenCircuitSF/cmd/opencircuit	70.486s
```

Reproduced across all four wiring test files named/implicated by the issue,
confirming the shared-mechanism diagnosis.

**After the fix**, under the same load (regenerated identically: `pgbench
-c 40 -j 12` CPU-heavy script + ~140 `yes` processes, load average
~170-200), ran the suite repeatedly:

```
$ GOMAXPROCS=1 go test ./cmd/opencircuit/... -run TestMountAndServe -count=1 -v   (x5 runs)
ok  	.../cmd/opencircuit	42.078s
ok  	.../cmd/opencircuit	11.342s
ok  	.../cmd/opencircuit	12.326s
ok  	.../cmd/opencircuit	12.138s
```
(one run, at the single most extreme moment — pgbench startup overlapping
peak `yes` scheduling — still failed even at the new 20s bound;
`GOMAXPROCS=1` combined with a ~170-200 load average on a 12-core machine
is beyond the "two other agents building/running tests" scenario the issue
describes, so this was treated as out of the reasonable target and not
chased further with an even larger timeout, per the issue's own "enlarging
timeouts is the fallback, not the goal" guidance)

Without `GOMAXPROCS=1` — i.e. the test binary competing for cores like any
other process rather than being artificially crippled to one, the fairer
analogue of "other agents running builds/browsers/Postgres" — three
`count=1` runs plus one `count=2` run were all green under the same
background load:
```
ok  	.../cmd/opencircuit	74.989s   (count=1, one iteration overlapped pgbench startup)
ok  	.../cmd/opencircuit	10.233s   (count=1)
ok  	.../cmd/opencircuit	12.602s   (count=1)
ok  	.../cmd/opencircuit	25.145s   (count=2, all 2x subtests passed)
```

**What was removed rather than enlarged**: the readiness-detection
mechanism itself (polling `GET /health` against a wall-clock deadline) was
replaced with a load-independent channel signal — that dependency is gone
entirely, not given a bigger number. The remaining timeouts (single HTTP
request, single DB statement) have no such substitute, so those were
enlarged, but each is bounded and justified in its own doc comment, not a
blanket increase.

**Full suite, clean (no synthetic load)**: `go build ./...`, `go vet ./...`
both clean; `go test ./... -count=1` all 13 packages `ok` (zero skips,
`internal/audit`/`auth`/`db`/`handlers`/`middleware` all reported real
timings); `go test ./... -count=2` also all `ok`.

## Files changed

- `cmd/opencircuit/main.go` — `net` import; `mountAndServe` gains a `ready
  chan<- struct{}` parameter (documented); binds the listener synchronously
  (`net.Listen` + `srv.Serve(ln)`) instead of `http.ListenAndServe`; both
  production call sites (`servePostgres`, `serveDevMode`) pass `nil`.
- `cmd/opencircuit/ratelimit_wiring_test.go` — new `wiringHTTPTimeout`,
  `wiringDBOpTimeout`, `wiringReadinessDeadline` constants (each with a
  justification comment); `waitForHealthy` rewritten to wait on `ready`
  instead of polling.
- `cmd/opencircuit/admin_wiring_test.go`,
  `cmd/opencircuit/subscribe_wiring_test.go`,
  `cmd/opencircuit/shutdown_wiring_test.go` — pass/use the new `ready`
  channel and the shared timeout constants instead of local `5 *
  time.Second` literals.

## Gotchas

- `wiringHTTPTimeout`/`wiringDBOpTimeout` at 20s are not bulletproof against
  arbitrarily severe synthetic load (see the one `GOMAXPROCS=1` failure
  above) — they are sized against a realistic "a few concurrent agents"
  scenario, not an unbounded adversarial one. If this flakes again under
  genuinely realistic conditions, that is real signal, not noise to wave
  away.
- The `internal/db` advisory-lock queuing behavior (packages listed above
  serializing against each other) is a related but distinct cost from what
  this issue fixes — see the Fix section's note. Worth its own issue if it
  proves costly, but out of scope here.
- Load-generation for the reproduction used `pgbench` and many `yes`
  processes on the shared dev machine; all were killed and load average
  confirmed to decay back to baseline before finishing this issue, per
  CLAUDE.md §8b's "never leave a [shared resource] for the next agent to
  hit by accident."

## Review notes

**2026-08-19 — bounced.** The `ready`-channel half of this is genuinely good and
should be kept as-is: closing `ready` at `net.Listen` is load-independent, and
binding the listener synchronously also gives a bind failure a direct return
instead of a goroutine hop through `errCh`. Two things stop it being resolved.

**1. `internal/handlers` was never touched, and it still fails with the exact
symptom this issue reports.** The Description's first sentence is
"`cmd/opencircuit` **and `internal/handlers`** fail with `context deadline
exceeded` when the machine is loaded". Only `cmd/opencircuit` was changed.
`internal/handlers` still carries ~17 fixed `5 * time.Second` deadlines of
exactly the class that was raised in `cmd/opencircuit`, and it reproduced during
this review — a single `go test ./internal/handlers/ -count=1` on an otherwise
ordinary machine:

```
=== RUN   TestAdminSettings_NonAdminForbidden
    settings_test.go:47: truncate tables: timeout: context deadline exceeded
--- FAIL: TestAdminSettings_NonAdminForbidden (10.27s)
...
FAIL	github.com/brennanMKE/OpenCircuitSF/internal/handlers	622.390s
```

That is the reported failure, verbatim, in a package this issue names, after the
fix. Every test in that package now takes 4–10 s (the `#0091` pool defect), which
is precisely what pushes a 5 s `TRUNCATE` over its bound — so `#0091` makes it
worse, but a 5 s deadline on a `TRUNCATE` is the same defect the wiring tests
just had fixed. Either raise and justify these alongside the wiring tests, or
narrow this issue's Description to `cmd/opencircuit` explicitly and file the
`internal/handlers` half separately. Do not leave it implicit.

**2. Acceptance criterion 3 ("any remaining deadline is justified in a comment")
is unmet for the largest deadlines in the changed files.** Five bare, uncommented
`30 * time.Second` `db.Connect` bounds remain:

```
cmd/opencircuit/ratelimit_wiring_test.go:39
cmd/opencircuit/subscribe_wiring_test.go:39
cmd/opencircuit/admin_wiring_test.go:65
cmd/opencircuit/shutdown_budget_wiring_test.go:94
cmd/opencircuit/shutdown_wiring_test.go:71
```

Two of those are literally among the line numbers this issue's "Where the
deadlines are" section calls out (`admin_wiring_test.go:64`,
`ratelimit_wiring_test.go:39`). They are now the biggest unexplained numbers in
the files, 50% larger than the `wiringHTTPTimeout` that *was* justified, and
nothing records what they are waiting for or why 30 s.

### On the 20 s raise itself — judged, not merely noted

The removal does **not**, on its own, justify the raise, for a specific reason:
**none of the four failures reproduced in `## Verification` was a readiness-poll
failure.** They are two `truncate tables: context deadline exceeded` and two
`Client.Timeout exceeded while awaiting headers`. Every one of them is fixed by
the raise; none is fixed by the `ready` channel. So the signal removed a real but
*hypothetical* timing dependency while the raise is doing all the load-bearing
work — the opposite of the "prefer removing over enlarging" ordering this issue
asked for. That is not fatal, but it should be stated plainly rather than
presented as the raise being a leftover.

20 s is also not derived from anything. Steady state for these requests is
sub-second; 20 s is a round number that the implementer's own load test still
failed at once.

### The broken-case failure experience — the question this issue asks in its last line

Measured rather than assumed. **A wedged *server* costs 20 s per *test*, not per
request** — every request loop (`admin_wiring_test.go:237`,
`ratelimit_wiring_test.go:112`, `subscribe_wiring_test.go:104`) calls `t.Fatalf`
on the first client error, so the first timeout aborts that test. Across the five
wiring tests that is ~100 s worst case, up from ~25 s. That part is acceptable.

**A wedged *database* is worse, and nobody looked at it.** In
`admin_wiring_test.go` the `wiringDBOpTimeout` paths are additive because
`t.Cleanup` funcs run after the `Fatalf`: the setup `truncateAdminWiringTables`
(20 s) plus the cleanup truncate (20 s) plus two cleanup `DELETE`s (20 s each,
errors discarded) is up to **80 s in that single test**, against 20 s before this
change. `shutdown_budget_wiring_test.go` adds another truncate pair. And the 30 s
`db.Connect` bounds above sit in front of all of it — five wiring tests × 30 s =
150 s before a single 20 s bound even engages.

So the honest answer to "20 s once, or 20 s per test?" is: **per test, and in the
DB-wedged case several times per test.** That is bounded and not catastrophic,
but it is a ~4–5× regression in how long a genuinely broken run takes to tell
you, and it is the specific trade this issue's closing line warned about. It
needs to be a recorded, deliberate decision in the constants' doc comments, not
an unexamined side effect.

### What is *not* being asked for

Not asking for the load reproduction to be redone — it was done and is accepted.
Not asking for the `ready` channel to change. Not asking for `t.Parallel()` or
the advisory-lock work; deferring those was right.

The wiring tests themselves are fine; the bounce is about scope and the
