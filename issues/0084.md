## Description

`cmd/opencircuit` and `internal/handlers` fail with `context deadline exceeded` when the machine is loaded — observed by an agent working `#0076` while two other agents were running builds, browsers and Postgres. Run alone on an idle machine the same packages pass comfortably:

```
ok  cmd/opencircuit    0.727s
ok  internal/handlers  1.801s
ok  cmd/opencircuit    0.518s   (repeat)
```

So these are **load-induced flakes, not defects**. That is precisely why they matter.

## Why this is worth fixing rather than tolerating

`CLAUDE.md` §5's verification contract is the backbone of this project's process: every issue is gated on "zero failures, zero skips", and reviewers are told to read output rather than trust exit codes. A suite that fails for reasons unrelated to the change under test corrodes that directly — it teaches the next agent that a red run is probably someone else's noise.

That already happened. The `#0076` agent hit these failures and had to reason about whether they were its own; earlier, another agent hit a temp file left in the shared tree and had to do the same. Each time the correct conclusion was reached, but the cost is real and the failure mode is a genuine defect being waved away.

## Where the deadlines are

`cmd/opencircuit/admin_wiring_test.go` (lines 64, 163, 247) and `ratelimit_wiring_test.go` (lines 39, 154) use 30 s and 5 s timeouts, including a `waitForHealthy` poll that gives a freshly started server 5 s to answer `/health`. On an idle machine that is ample; under four concurrent agents it is not.

## Acceptance criteria

- [ ] Wiring tests no longer fail on a loaded machine. Demonstrate it: run the suite while generating substantial concurrent load and show it green, then show the current code failing under the same load
- [ ] Prefer removing the timing dependency over enlarging the timeout where possible — polling with a generous cap is better than a fixed sleep, and a readiness signal is better than polling
- [ ] Any remaining deadline is justified in a comment: what it is waiting for and why that bound
- [ ] `go test ./... -count=1` green, and `-count=2` green, with `TEST_DATABASE_URL` exported and zero skips

## Notes

Do **not** fix this by deleting the wiring tests. They are the only checks that exercise real route registration — `#0024`'s bounce turned on exactly that distinction, where a hand-built mux passed while `main.go` was unguarded.

Consider whether `t.Parallel()` usage, shared listeners, or the `internal/db` advisory lock contribute. `#0082`'s reviewer noted the docs-parity test queues behind that lock despite needing no database, which is a related symptom.

Enlarging timeouts is the fallback, not the goal — a 30 s timeout that passes under load still means a 30 s wait when something is genuinely broken.
