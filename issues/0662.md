## Description

The user wants the guides to grow the newsletter and bring people to events (requested 2026-11-14). Every guide page (`/guides/{slug}` and `/workshops/programming-leds`, from `#0656`) gets:

1. **A newsletter signup box** at the end of the guide. It uses the existing double opt-in subscribe flow (PRD §6.3) unchanged. The uniform `202` from `POST /api/subscribe` must not be weakened (AGENTS §9).
2. **Upcoming events:** the next published events. Prefer related events where a match exists, for example Programming LEDs events on the LED guides. Never show drafts.
3. **Signup attribution:** record which guide a subscriber signed up from, so the admin can report signups per guide next to clicks (`#0660`). Plan this against the existing consent-provenance and source fields (PRD §6.10) before adding a column. A new column means a new migration (AGENTS §1). Attribution must not change the response or reveal whether an address already existed. If UTM parameters from a guide-post short link are present, decide whether to keep them too, so signups can be tied to a campaign.

Server-rendered fallback copy and the `internal/seo` guards must stay in step with any new static text.

## Acceptance criteria

### Decisions this plan makes

1. **No migration.** Attribution goes in the `detail` JSONB of the `signup_requested` row in `subscriber_events` (`migrations/000022`). That row is already written, inside the signup transaction, at exactly the three places a real signup starts: `Store.Create` (`{"kind":"new"}`), `Store.RestartSignup` (`{"kind":"restarted"}`) and the converting branch of `Store.ClaimAndEnqueueConfirmation` (`{"kind":"self_after_invite"}`). It is never written for a bot, a suppressed or complained address, an already-active address, or an ordinary pending resend. So "signups from a guide" counts real signups only, with no extra rule. `action` is validated in Go and `detail` has no CHECK, so adding keys needs no schema change.
   - **Why not `subscribers.source_detail`** (PRD §6.10): it is set once at INSERT and never rewritten (`#0317`'s note on `Subscriber`), so it would miss restarted and converted signups, and it would mix website attribution into a field that today means import provenance.
   - **Why not new `subscribers` columns:** the row's `utm_*` are overwritten on restart and conversion. The event row is the per-signup record that never changes, which is what a per-window report needs. Leaving out a migration also means no sequencing with `#0658`'s `000052`. **If the implementer finds a migration is needed after all, it takes the next free number at implementation time** (`ls migrations | tail -2`), not a fixed one, and updates `docs/database.md` and the range in AGENTS §1 line 37 in the same commit.
2. **UTM tags are kept too, in the same event detail.** `#0658`'s short links land on `/guides/{slug}?utm_campaign=guides&utm_content=gp{id}&utm_medium=social&utm_source={channel}`. `utm_source`, `utm_medium` and `utm_campaign` already reach the server and are stored on the subscriber row. `utm_content` is new: it is the only tag that names the post (`gp{id}`). The SPA captures it with the other three, and the server writes `utm_campaign` and `utm_content` into the event detail when they are not empty. `#0660` can then show signups per post next to clicks per post. No `utm_content` column is added.
3. **Attribution comes from the form's page, not the landing page.** The guide slug is sent only when the form is on a guide page (a `guide` prop). A visitor who lands on a guide and later subscribes on `/subscribe` is not counted for the guide. Their `utm_*` (from sessionStorage) still tie them to the campaign post.
4. **The server validates the slug and drops anything else without a word.** An unknown or empty `signup_guide` becomes `""`. It never causes a `400`, and the response never changes. `utm_content` is kept only if it is 1 to 100 bytes after trimming; otherwise it becomes `""`. Both checks take constant time and run on every request, so `#0088`'s timing property holds. They add no database query, so `TestSubscribe_SyncQueryCountEqualAcrossBranches` stays true.
5. **Upcoming events, related first.** The guide page loads `GET /api/workshops` (published only; drafts never reach it). It drops `canceled` rows and shows up to 3 from `upcoming`, related events first and then the others, each group in the server's date order.
   - On a workshop guide (`/workshops/programming-leds`), "related" means runs of that workshop: `workshopGuideForEventSlug(e.slug)?.slug === slug`.
   - On a topic guide, "related" means runs of any workshop that has a guide (`workshopGuideForEventSlug(e.slug) !== undefined`). Today that is only Programming LEDs, which every topic guide's "Try it with real hardware" section already points to.
6. **The server-rendered fallback gets the static text only, not the event list.** The fallback for a guide page gains the events heading with a "See all events" link, and the newsletter heading, intro line and a `/subscribe` link. It does not render events, so guide pages need no workshop source and stay cacheable. Events are already in the fallback HTML at `/events` and `/`.

  ```go
  // GuideSignups is one row of SignupsByGuide (#0662): signups started from a
  // guide page's form, per guide and campaign post, in a window.
  type GuideSignups struct {
      Guide       string // guide slug (internal/guides)
      UTMCampaign string // "" when the visit carried none
      UTMContent  string // "gp{id}" for a #0658 guide-post link; "" otherwise
      Requested   int    // distinct subscribers with a signup_requested event in [from, to)
      Confirmed   int    // of those, how many have a confirmed event at or after that request
  }
  func (s *Store) SignupsByGuide(ctx context.Context, from, to time.Time) ([]GuideSignups, error)
  ```
  SQL:
  ```sql
  SELECT e.detail->>'guide',
         coalesce(e.detail->>'utm_campaign', ''),
         coalesce(e.detail->>'utm_content', ''),
         count(DISTINCT e.subscriber_id),
         count(DISTINCT e.subscriber_id) FILTER (WHERE EXISTS (
             SELECT 1 FROM subscriber_events c
              WHERE c.subscriber_id = e.subscriber_id
                AND c.action = 'confirmed'
                AND c.created_at >= e.created_at))
    FROM subscriber_events e
   WHERE e.action = 'signup_requested'
     AND e.detail->>'guide' IS NOT NULL
     AND e.created_at >= $1 AND e.created_at < $2
   GROUP BY 1, 2, 3
   ORDER BY 1, 2, 3
  ```
  Use the `ActionSignupRequested` and `ActionConfirmed` constants as parameters, not literals. Comment that an erased subscriber (`subscriber_id` NULL) drops out of the counts by design. `idx_subscriber_events_action` covers the filter. Only `SELECT`, so `events_append_only_guard_test.go` is unaffected.
