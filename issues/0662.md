## Description

The user wants the guides to grow the newsletter and bring people to events (requested 2026-11-14). Every guide page (`/guides/{slug}` and `/workshops/programming-leds`, from `#0656`) gets:

1. **A newsletter signup box** at the end of the guide. It uses the existing double opt-in subscribe flow (PRD §6.3) unchanged. The uniform `202` from `POST /api/subscribe` must not be weakened (AGENTS §9).
2. **Upcoming events:** the next published events. Prefer related events where a match exists, for example Programming LEDs events on the LED guides. Never show drafts.
3. **Signup attribution:** record which guide a subscriber signed up from, so the admin can report signups per guide next to clicks (`#0660`). Plan this against the existing consent-provenance and source fields (PRD §6.10) before adding a column. A new column means a new migration (AGENTS §1). Attribution must not change the response or reveal whether an address already existed. If UTM parameters from a guide-post short link are present, decide whether to keep them too, so signups can be tied to a campaign.

Server-rendered fallback copy and the `internal/seo` guards must stay in step with any new static text.

## Acceptance criteria

- [ ] Every guide page shows a working signup box and an upcoming-events block, in both themes and at narrow widths. Say which of these claims rest on jsdom.
- [ ] A signup made from a guide records the guide slug, and an admin-facing store method returns signups per guide over a window.
- [ ] The subscribe responses are unchanged byte for byte. The existing enumeration test still passes.
- [ ] `ISSUE=0662 scripts/check.sh` passes, together with the guard packages from AGENTS §5 that this touches.

### Decisions this plan makes

1. **No migration.** Attribution goes in the `detail` JSONB of the `signup_requested` row in `subscriber_events` (`migrations/000022`). That row is already written, inside the signup transaction, at exactly the three places a real signup starts: `Store.Create` (`{"kind":"new"}`), `Store.RestartSignup` (`{"kind":"restarted"}`) and the converting branch of `Store.ClaimAndEnqueueConfirmation` (`{"kind":"self_after_invite"}`). It is never written for a bot, a suppressed or complained address, an already-active address, or an ordinary pending resend. So "signups from a guide" counts real signups only, with no extra rule. `action` is validated in Go and `detail` has no CHECK, so adding keys needs no schema change.
   - **Why not `subscribers.source_detail`** (PRD §6.10): it is set once at INSERT and never rewritten (`#0317`'s note on `Subscriber`), so it would miss restarted and converted signups, and it would mix website attribution into a field that today means import provenance.
   - **Why not new `subscribers` columns:** the row's `utm_*` are overwritten on restart and conversion. The event row is the per-signup record that never changes, which is what a per-window report needs. Leaving out a migration also means no sequencing with `#0658`'s `000052`. **If the implementer finds a migration is needed after all, it takes the next free number at implementation time** (`ls migrations | tail -2`), not a fixed one, and updates `docs/database.md` and the range in AGENTS §1 line 37 in the same commit.
2. **UTM tags are kept too, in the same event detail.** `#0658`'s short links land on `/guides/{slug}?utm_campaign=guides&utm_content=gp{id}&utm_medium=social&utm_source={channel}`. `utm_source`, `utm_medium` and `utm_campaign` already reach the server and are stored on the subscriber row. `utm_content` is new: it is the only tag that names the post (`gp{id}`). The SPA captures it with the other three, and the server writes `utm_campaign` and `utm_content` into the event detail when they are not empty. `#0660` can then show signups per post next to clicks per post. No `utm_content` column is added.
3. **Attribution comes from the form's page, not the landing page.** The guide slug is sent only when the form is on a guide page (a `guide` prop). A visitor who lands on a guide and later subscribes on `/subscribe` is not counted for the guide. Their `utm_*` (from sessionStorage) still tie them to the campaign post.
4. **The server validates the slug and drops anything else without a word.** An unknown or empty `signup_guide` becomes `""`. It never causes a `400`, and the response never changes. `utm_content` is kept only if it is 1 to 100 bytes after trimming; otherwise it becomes `""`. Both checks take constant time and run on every request, so `#0088`'s timing property holds. They add no database query, so `TestSubscribe_SyncQueryCountEqualAcrossBranches` stays true.
5. **Upcoming events, related first.** The guide page loads `GET /api/workshops` (published only; drafts never reach it). It drops `canceled` rows and shows up to 3 from `upcoming`, related events first and then the others, each group in the server's date order.
   - On a workshop guide (`/workshops/programming-leds`), "related" means runs of that workshop: `workshopGuideForEventSlug(e.slug)?.slug === slug`.
   - On a topic guide, "related" means runs of any workshop that has a guide (`workshopGuideForEventSlug(e.slug) !== undefined`). Today that is only Programming LEDs, which every topic guide's "Try it with real hardware" section already points to.
6. **The server-rendered fallback gets the static text only, not the event list.** The fallback for a guide page gains the events heading with a "See all events" link, and the newsletter heading, intro line and a `/subscribe` link. It does not render events, so guide pages need no workshop source and stay cacheable. Events are already in the fallback HTML at `/events` and `/`.
7. **Pre-checked interests come from the related workshop's existing tags (decision 3). No migration, no Go change, no new admin control.** Events already carry interests, end to end:
   - **Schema:** `workshop_interests (workshop_id, interest_id)` exists since `migrations/000020` (applied in production; production is at 51, and `000052` belongs to `#0658`). Nothing to add.
   - **Store:** `workshops.Workshop.InterestIDs`, written by `replaceInterestsTx` in `Create`/`Update` and read by `ListVisible`/`GetByID` (`internal/workshops/store.go`).
   - **Admin control:** the event editor already has an **Interests** panel of checkboxes (`web/src/views/admin/WorkshopEditor.svelte`, "Drives the public page's pre-checked subscribe prompt and campaign targeting"), saved as `interest_ids` by `PATCH /admin/workshops/{id}` (`internal/handlers/admin_workshops.go`). The user's request is already supported. The admin only has to tag the Programming LEDs events (after-deploy step 7).
   - **Public API:** every item of `GET /api/workshops` (upcoming and past) already has `interests: PublicInterest[]` (slug, name), from `publicWorkshopView.Interests` in `internal/handlers/public_workshops.go`. `WorkshopDetail.svelte` already pre-checks them through `workshopPreselectSlugs` and `SubscribeForm`'s `preselect` prop (#0029/#0054).

   The work is SPA-only:
   - **Which workshop a guide uses.** It is the relatedness rule from decision 5, factored into one predicate (`isRelatedGuideEvent`) so the events list and the pre-check cannot drift apart. On `/workshops/programming-leds`, the related events are runs of that workshop: `workshopGuideForEventSlug(e.slug)?.slug === slug`, so `programming-leds`, `programming-leds-2`, and so on. On a topic guide, they are runs of any guided workshop. Today that is the same Programming LEDs family, which every topic guide's "Try it with real hardware" CTA already points to. The `tags` in `guides.json` (`LEDs`, `serial`, …) are **not** interest slugs and are not used. No static guide-to-interest map is added: an admin changes the tags in the editor, with no deploy.
   - **Which slugs are pre-checked.** The union of the `interests[].slug` of the related events in `upcoming` (canceled ones included, since a canceled run's tags still describe the workshop), deduped in first-seen order. If no related event is upcoming, the slugs of the most recent related event in `past` (the first match, because `past` is newest first). If there is no related event at all, `[]`, so nothing is pre-checked.
   - **Mount timing.** `SubscribeForm` seeds its selection from `preselect` once, at mount, and never re-syncs (its own comment explains why). So `GuideEnd` mounts `<SubscribeForm guide={slug} preselect={…} />` only after the workshops fetch has **settled**. On success it passes the computed slugs. On failure it passes `[]`. The heading and intro render at once; only the form waits. The 2 s timing gate starts at the form's own mount, so it is unaffected.
   - **The reader can untick.** The pre-checked boxes are the ordinary checkboxes. `toggleSlug` already removes a slug, and only `selected` is posted.
   - **A pre-checked slug that is not active is never posted.** `resolveInterests` uses `interests.GetByIDs`, which does **not** filter `active`, so a workshop can expose a deactivated tag. `SubscribeForm` only renders checkboxes for `GET /api/interests` (active only), so such a slug would be checked but invisible, and posting it gets a visible `400 unknown interest`. This is a latent bug that `WorkshopDetail` has today. Fix it once, in the form: a new pure `submittableInterests(selected, active)` in `subscribe.ts` returns the selected slugs that are in the active list, in active-list order, and `onSubmit` posts that instead of `Array.from(selected)`. If the interests failed to load, no checkboxes are shown and it returns `[]`, matching what the reader saw.
   - **`/subscribe` and the uniform `202` do not change.** With no `preselect`, `selected` only ever holds slugs the reader ticked from the active list. `submittableInterests` is then the identity, apart from order: the body lists interests in display order rather than click order, and the server treats `interests` as a set. No new request field is added for this; `interests` already exists. The server is untouched by this decision, so `TestSubscribe_UniformResponseAcrossBranches` and the enumeration property cannot move. The only status outside the uniform `202` the form could cause is the existing request-shape `400` for an unknown slug, and the filter is what stops that.

### Assumptions (user may override)

Made by the planner on 2026-11-14, as the user asked, instead of open questions:

1. **A topic guide pre-checks the Programming LEDs workshop's interests**, the same "related" set decision 5 uses for its events. The planner judged a per-topic interest map (for example `delay-vs-millis` → `microcontrollers`) more precise, but it would need a hand-kept table or a schema field for something the user asked to drive from workshops. If wanted later, add an optional `interests: string[]` to each topic in `guides.json`, used ahead of the workshop's.
2. **With no upcoming related event, use the most recent past one**, so the Programming LEDs guide still pre-checks between runs. With no related event at all, nothing is pre-checked.
3. **Several related upcoming runs are unioned.** Runs of one workshop are expected to share tags. A union never hides a topic one run was given.
4. **Deactivated interests are dropped silently, client-side**, rather than by filtering `GET /api/workshops`'s tag list on the server. This keeps the public API unchanged and fixes the latent `400` for `WorkshopDetail` too. Filtering the API as well would be a reasonable follow-up, but it is not needed here.
5. **The form waits for the events fetch instead of re-syncing the pre-check later.** A late re-sync could overwrite a reader's untick, and the wait is one small request the block makes anyway.
6. **No new admin control.** The existing Interests panel on the event editor is the control. No label or copy change.

  ```go
  // GuideSignups is one row of SignupsByGuide (#0662): signups started from a
  // guide page's form, per guide and campaign post, in a window.
  type GuideSignups struct {
      Guide       string // guide slug (internal/guides)
      UTMCampaign string // "" when the visit carried none
      UTMContent  string // "gp{id}" for a #0658 guide-post link; "" otherwise
      Requested   int    // distinct subscribers with a signup_requested event in [from, to)
      Confirmed   int    // of those, how many have a confirmed event at or after that request
  }
  func (s *Store) SignupsByGuide(ctx context.Context, from, to time.Time) ([]GuideSignups, error)
  ```
  SQL:
  ```sql
  SELECT e.detail->>'guide',
         coalesce(e.detail->>'utm_campaign', ''),
         coalesce(e.detail->>'utm_content', ''),
         count(DISTINCT e.subscriber_id),
         count(DISTINCT e.subscriber_id) FILTER (WHERE EXISTS (
             SELECT 1 FROM subscriber_events c
              WHERE c.subscriber_id = e.subscriber_id
                AND c.action = 'confirmed'
                AND c.created_at >= e.created_at))
    FROM subscriber_events e
   WHERE e.action = 'signup_requested'
     AND e.detail->>'guide' IS NOT NULL
     AND e.created_at >= $1 AND e.created_at < $2
   GROUP BY 1, 2, 3
   ORDER BY 1, 2, 3
  ```
