## Description

`#0129` made `AdminResendConfirmation` refuse an invited row, because the generic
confirmation template drops the provenance sentence PRD §6.10.1 requires.

**The public path does the opposite.** A still-pending invited row whose person
submits the website subscribe form gets the **generic confirmation** resent —
the very provenance-dropping template the admin path refuses.

Found by `#0129`'s review. It is defensible: someone who arrives at the site and
signs up under their own steam is expressing consent directly, so an ordinary
confirmation arguably fits better than an invitation reminder. What is not
defensible is that the two paths disagree **by accident** rather than by a
recorded decision.

## Acceptance criteria

1. Decide explicitly what the public path should send to a pending invited row —
   the generic confirmation, the invitation, or a third thing — and record the
   decision **in the code**, not only here.
2. Whatever is chosen, the admin and public paths must be consistent with each
   other, or their difference must be justified in a comment at both sites.
3. **`#0026`'s uniform `202` is a hard restricted-area rule** (§9) and constrains
   this: the response must not vary by whether the address is already on the
   list, invited, or unknown. Whatever branch you add must be invisible from
   outside. The existing handler test asserts the bodies are byte-identical —
   keep it passing for the right reason.
4. If the invitation is sent instead, the `physical_address` gate applies, since
   that template carries it.
5. Consider the same question for the preference-centre and one-click paths, and
   report whether they have an equivalent divergence.
6. `ISSUE=NNNN scripts/check.sh go ./internal/handlers/... ./internal/subscribers/...`
   passes with no skips.

### The shared decision (`#0312` + `#0313` + `#0314`, 2026-08-28)

**Who initiated the send decides which template goes out — not how the row was
created.**

- An **invitation** is a message *we* start, to an address we obtained somewhere
  else. It must carry PRD §6.10.1's provenance sentence, because the recipient
  never asked for it and that sentence is the only thing separating it from spam.
- A **confirmation** is a message we send *in reply* to a request the person made
  themselves. Its provenance is the request. §6.10.1's sentence would read as a
  non-sequitur to someone who just typed their own address into our form.

Applied to the four events these three issues are about:

| Event | Who initiated | What happens |
|---|---|---|
| An invitation fails to send, or is abandoned in the queue | nobody | Row stays `pending`, unaccepted. Recoverable only by the admin action below (`#0312`) |
| An invitation expires unaccepted | nobody | `ExpirePendingSweep` keeps today's behaviour exactly: token nulled, row left `pending`, never re-mailed by the import mechanism |
| An **expired-pending** address submits the public form | **the person** | Mint a fresh token inside the same atomic claim; send the **generic confirmation** (`#0314`) |
| A **pending invited** address submits the public form | **the person** | The row stops being an invitation: `import_id` cleared, consent evidence refreshed, any still-queued invitation cancelled, fresh token if the old one lapsed; send the **generic confirmation** (`#0313`) |
| An admin wants to re-send | **the admin** | A separate action sending `outbox.KindImportInvite` with its provenance intact — at most once per address, ever (`#0312`) |

**States and transitions.** No new `status` value, and no change to the row-state
test the whole codebase already shares — *an unaccepted invitation is
`status='pending' AND import_id IS NOT NULL AND consent_basis IS NULL`*
(`Confirm`, `Unsubscribe`, `AdminResendConfirmation`, `ExpirePendingSweep` all
derive it that way). Two transitions are **added**:

1. **Invitation → self-initiated signup** (`#0313`, public path). Clears
   `import_id`. Leaves `source = 'import'`, `invited_at`, `consent_basis` (still
   NULL) and every `subscriber_events` row untouched.
2. **Invitation → invitation, re-sent once** (`#0312`, admin path). Stamps a new
   write-once `invite_resent_at`. Does **not** re-stamp `invited_at`, does not
   touch `consent_basis`, does not change `status`.

**Transition 1 is a defect fix, not merely a recorded preference.**
`Store.Unsubscribe` reads that same row-state test and treats an unsubscribe from
a pending invited row as an **invitation decline**, which writes a `suppressions`
row ("declined an import invitation before confirming"). So today: an invited
person visits the site, signs up under their own steam, receives the generic
confirmation, changes their mind, clicks that mail's `List-Unsubscribe` — and is
**permanently suppressed** for an ordinary change of mind about a signup they made
themselves, with no self-service recovery. That is precisely the misfire `#0129`'s
blocker 2 closed for `RestartSignup` (invite → revoke → website signup); it is
still wide open on the `pending` branch, which `RestartSignup` never reaches.
Clearing `import_id` at the moment the person takes the signup over closes it at
the same source, by the same reasoning `ImportStore.Revoke`'s own doc comment
already uses: *its consent no longer derives from the import.*

**What transition 1 costs, accepted deliberately.** The person stops counting
toward `subscriber_imports.confirmed_count`, and their acceptance writes
`signup_requested` + `confirmed` rather than `invite_accepted`. That is the honest
number. They also now receive `#0127`'s welcome email, which an accepted
invitation is denied ("the invitation was the introduction") — correct, because
the invitation is no longer their introduction; the form they filled in is.
Provenance is not lost: `source = 'import'`, `invited_at`, and the `imported` /
`invite_sent` `subscriber_events` rows (which carry `import_id`) all survive, and
they are where "why did we ever mail this address" is answered from.

**The one deviation from the PRD, stated plainly.** §6.10.1 says "One invitation
per address, ever. No reminder, no re-invite on a later import." `#0312` requires
a re-send, so this deviates, and the bound is explicit:

- **Automated imports stay capped at one, unconditionally.** `invited_at` still
  governs them and is never re-stamped by anything, so re-uploading the same CSV
  can never re-invite — the property `#0129`'s notes call "the anti-abuse
  property" is untouched.
- **The exception is at most one further invitation, per address, ever**, by an
  explicit, authenticated, audited admin action on that one row, recorded in a
  new write-once `subscribers.invite_resent_at`.

What §6.10.1 exists to prevent survives intact: no bulk re-invite, and no
repeatable reminder loop against an unwilling recipient. Two is a constant, not a
loop. The alternative bound considered and rejected was gating the re-send on the
first invitation's `outbound_queue` status (`abandoned` only): it self-defeats
(`LatestByRecipients` returns the *latest* row of a kind, which after one re-send
is the re-send), it depends on queue retention, and it refuses the bounce case
`#0312` names. The queue state is still *shown* on `#0128`'s screen so the admin
can see whether the first one was abandoned before spending the one re-send.

**Order of implementation: `#0336` → `#0314` → `#0313` → `#0312`.** See each
issue's own `## Plan` for why.

### What this issue implements

**Land third, after `#0336` and `#0314`.** `#0314` rewrites
`ClaimAndEnqueueConfirmation` into a locked, token-establishing transaction; this
issue adds the conversion inside that same transaction. Doing it in the other
order means writing the conversion twice.

Criterion 1's decision: **the public path keeps sending the generic confirmation
— and stops leaving an invitation behind while it does.** The recorded reason is
not "the generic template is arguably fine"; it is that the row is no longer an
invitation once the person signs up themselves, so the generic confirmation is
the correct template for what the row now *is*. That is what makes the two paths
consistent under criterion 2 rather than justified-as-different: after a public
submit there is no unaccepted invitation left for `AdminResendConfirmation` to
refuse.

### Step 1 — the conversion (`internal/subscribers/store.go`)

Inside `ClaimAndEnqueueConfirmation`'s transaction, after the `SELECT … FOR
UPDATE` that `#0314` adds:

```go
// The same row-state test Confirm, Unsubscribe, AdminResendConfirmation and
// ExpirePendingSweep use — derived from the row, never trusted from the caller.
converting := sub.ImportID != nil && sub.ConsentBasis == nil
```

When `converting`, the single claiming `UPDATE` additionally sets
`import_id = NULL` and refreshes `signup_ip`, `signup_user_agent`,
`utm_source`, `utm_medium`, `utm_campaign` from the caller's evidence — the
person's own submission is now this row's consent record. When not converting,
those five columns are left exactly as they are: an ordinary pending resend must
not rewrite the original consent evidence.

`invited_at`, `source`, `source_detail` and `consent_basis` are **not** touched.
`invited_at` staying stamped is what keeps `#0129`'s "skipped by every subsequent
import, in whatever mode" true — the address is still un-re-invitable, it has
simply stopped being an invitation *in progress*.

Then, still in the same transaction, when `converting`:

- `RecordEventTx` an `ActionSignupRequested` with
  `Detail{"kind": "self_after_invite"}`. This is where "the invitee took the
  signup over themselves" is answered from, and it sits alongside — never
  replacing — the earlier `imported` / `invite_sent` rows that carry `import_id`.
- Cancel any still-`queued` invitation for this subscriber (step 2).

### Step 2 — cancel a superseded invitation (`internal/outbox/store.go`)

Add:

```go
func (s *Store) CancelQueuedTx(ctx context.Context, q Querier, subscriberID int64, kind Kind, reason string) (int64, error)
```

`UPDATE outbound_queue SET status = 'abandoned', error = $reason, claimed_at =
NULL, payload = '{}'::jsonb WHERE subscriber_id = $1 AND kind = $2 AND status =
'queued'` — matching `queued` only, never `sending` (in flight; leave it) and
never `sent` (already gone). `abandoned` is the existing terminal never-sent
state; `MarkDone` is **not** usable here because it writes `sent`, which would be
a lie in the one table an operator reads to answer "did this actually go out".

This is not hypothetical tidiness. The `KindImportInvite` render path defers
indefinitely on a blank `physical_address` (`deferMissingPhysicalAddress`), so an
invitation can sit `queued` for days. Without this, a person who signs up on the
website receives their generic confirmation and then, whenever the setting is
filled in, an invitation telling them where we got an address they typed in
themselves — carrying a `confirm_token` that `#0314`'s mint may have rotated out
from under it.

### Step 3 — the handler (`internal/handlers/subscribe.go`)

`existingSignup`'s `StatusPending` branch already calls `sendConfirmation`; it now
passes `evidence` through (the signature change `#0314` starts). No new branch,
no new `switch` arm: the conversion is decided by the row inside the store, not by
the handler, which is what keeps it consistent with the four other call sites that
derive the same fact the same way.

`sendConfirmation`'s doc comment gains the decision, and `ErrResendNotForInvited`'s
doc comment in `internal/subscribers/pending.go` gains the reciprocal cross-
reference. That pair is criterion 2's "recorded in the code, at both sites" — and
what they record is that the two paths now agree, not that they differ.

### How this resolves under `#0026`'s uniform 202 — with no compromise

**The rule did not constrain this design at all, and the reason is structural.**
`Subscribe` performs a fixed, branch-free amount of work for every accepted
request — two reads (`IsSuppressed`, `FindByEmail`) and one `KindSubscribeIntake`
enqueue — then calls `enqueueMutation` and writes
`writeSubscribeUniform202(w)`. Every branch-dependent decision, this issue's
included, runs afterwards on the mutate worker inside `processMutateJob` →
`dispatchMutation` → `existingSignup`, on a goroutine whose context is derived
from `h.sendCtx` rather than the (already-returned) request. `#0088` moved the
branch decision off the request path, `#0126` moved the enqueue into the store
transaction, and `#0254` made the intake write unconditional and identically
shaped for every branch.

So, concretely: **internally**, a pending invited row is converted to a
self-initiated signup, gets a fresh token if the old one lapsed, has its queued
invitation cancelled, and is sent a `KindConfirmation`. **Externally**, the
endpoint returns the same `202` with the same body bytes, the same headers, and
the same request-path cost as an unknown address, an active one, a suppressed
one, or a honeypot fill. No branch is added before the write, no query is added to
the request goroutine, and no field of the response is touched.

The test must assert this rather than inherit it:
`TestSubscribe_UniformResponseAcrossBranches` gains a **twelfth** branch,
"pending invited row", compared on status code, the full header set minus `Date`,
and body bytes — the same comparison `#0129`'s review extended to eleven.

### Criterion 5 — the preference-centre and one-click paths

Answered, and one of them is worse than divergent.

- **Preference centre** (`internal/handlers/preferences.go`) sends no mail and has
  no invite awareness. No divergence.
- **One-click / `List-Unsubscribe`** (`internal/handlers/unsubscribe.go`) has no
  invite awareness in the handler, but `subscribers.Store.Unsubscribe` does: it
  reads the same row-state test and treats an unsubscribe from a pending invited
  row as an **invitation decline**, writing a `suppressions` row. Combined with
  today's public path — which resends the generic confirmation and leaves
  `import_id` in place — that means an invited person who signs up on the website
  themselves and then declines that confirmation is **permanently suppressed**,
  with no self-service recovery. This is `#0129`'s blocker 2 exactly, reached
  through the `pending` branch instead of the `unsubscribed` one that
  `RestartSignup` fixed.

  This plan closes it at the source rather than by special-casing `Unsubscribe`:
  once the conversion clears `import_id`, the decline branch correctly does not
  fire, because the row is no longer an invitation. `Unsubscribe` itself is
  **unchanged** — deliberately, so the four call sites keep sharing one
  definition of "unaccepted invitation" rather than growing a fifth variant.

- `TestSubscribe_PendingInvitedRow_CancelsQueuedInvitation`: leave

- `TestSubscribe_UniformResponseAcrossBranches` + the pending-invited branch.

- `TestAdminResendConfirmation_AfterPublicTakeover_NoLongerRefuses`: the direct

## Root cause

`existingSignup`'s `StatusPending` branch called `sendConfirmation`
unconditionally, and `sendConfirmation` had no awareness that the row it was
about to resend a confirmation for might be a still-unaccepted import
invitation. The row simply kept `import_id` set forever, which meant a later
ordinary `Unsubscribe` of that same row still read as "declined an import
invitation before confirming" (`Store.Unsubscribe`'s `isInviteDecline`
predicate) and wrongly suppressed a person who had signed up on the website
themselves and merely changed their mind.

## Fix

Landed together with `#0314` in one rewrite of `ClaimAndEnqueueConfirmation`
(`internal/subscribers/store.go`) — the plan's own reasoning ("this issue adds
the conversion inside that same transaction; doing it in the other order
means writing the conversion twice") — so the two issues' diffs are not
separable by file and share one code commit.

- **Step 1 — the conversion**, inside `ClaimAndEnqueueConfirmation`'s now
  `SELECT ... FOR UPDATE`-locked transaction: `converting := locked.ImportID
  != nil && locked.ConsentBasis == nil` — the identical row-state test
  `Confirm`/`Unsubscribe`/`AdminResendConfirmation`/`ExpirePendingSweep`
  already derive from the row rather than trust from the caller. When
  converting, the SAME claiming `UPDATE` (a single statement, `CASE WHEN
  $7 …` per column — not a second query) additionally clears `import_id` and
  refreshes `signup_ip`/`signup_user_agent`/`utm_source`/`utm_medium`/
  `utm_campaign` from the caller's own evidence. `invited_at`, `source`,
  `source_detail`, `consent_basis` are **not** touched — `invited_at` staying
  write-once is what keeps a re-uploaded import CSV from re-inviting the
  address (`#0129`'s anti-abuse property). A converting claim additionally
  writes one `subscriber_events` row (`ActionSignupRequested`,
  `{"kind": "self_after_invite"}`) and cancels any still-queued invitation.
- **Step 2 — `outbox.Store.CancelQueuedTx`** (`internal/outbox/store.go`, new)
  — `UPDATE outbound_queue SET status='abandoned', error=$reason,
  claimed_at=NULL, payload='{}'::jsonb WHERE subscriber_id=$1 AND kind=$2
  AND status='queued'`, matching `queued` only (never `sending`, which is
  in flight and left alone; never `sent`, already gone). `error` is set to a
  plain, non-issue-citing reason ("superseded by a self-initiated website
  signup") — `TestNoAdminFacingStringCitesInternalDocs` correctly caught an
  earlier draft that cited `#0313` in this admin-visible string.
- **Step 3 — the handler** (`internal/handlers/subscribe.go`) —
  `existingSignup`'s `StatusPending` branch now passes `evidence` through to
  `sendConfirmation`, which passes it to `ClaimAndEnqueueConfirmation`; no new
  branch or `switch` arm — the conversion is decided by the row inside the
  store, the same as every other call site that derives this fact.
  `sendConfirmation`'s and `ErrResendNotForInvited`'s doc comments both record
  the decision.

**Uniform 202 (criterion 3).** Unaffected by construction, unchanged from the
plan's own reasoning: every branch through `Subscribe` performs the same
fixed, branch-free work before `writeSubscribeUniform202`, and the
conversion runs entirely on the mutate worker, after the response is already
written. Re-asserted directly rather than reasoned about: `expired-pending`
and `pending-invited` branches were added to
`TestSubscribe_UniformResponseAcrossBranches`, which compares status, the
full header set (minus `Date`), and body bytes across all thirteen branches
now, byte-identical.

**Criterion 5 — preference-centre and one-click paths.** Answered exactly as
the plan states, verified rather than assumed: `internal/handlers/preferences.go`
sends no mail and has no invite awareness (no divergence). One-click
(`internal/handlers/unsubscribe.go`) has no invite awareness in the handler
either, but calls the SAME `Store.Unsubscribe` this fix changes the behavior
of — so the fix closes the divergence at its actual source (the shared
row-state predicate) rather than adding a fifth special case.
