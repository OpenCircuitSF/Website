## Description

`outbox.Store.MarkSent` blanks `payload` when a row succeeds but leaves
`error` untouched. A message that failed once and then delivered on a later
attempt therefore ends up as `status='sent'` **with a populated `error`
column**, and the row reads as a failure to anyone scanning the table.

This is not hypothetical. Both of the admin recovery emails on production
(`outbound_queue` ids 1 and 2) are `sent`, with a real `sent_at` and a real
`ses_message_id` — and both still carry the `AccessDeniedException` text from
the attempt before the IAM policy was corrected:

```
2,recovery,brennan@opencircuitsf.com,sent,3,2026-08-25 23:34:27.027011+00,
  "mailing: sending via SES: ... AccessDeniedException: ... is not authorized
   to perform 'ses:SendEmail' on resource '...identity/brennan@...'"
```

The user read that output as three failures. Two of them were successes.

The cost is diagnostic, not functional: nothing behaves incorrectly, but the
one table an operator has to read when mail is stuck cannot be scanned by eye,
because `error` is not a reliable indicator of whether the row failed. `status`
is — and the two disagree.

## Why the current behaviour is defensible, and still wrong

Retaining the error is deliberate elsewhere: `MarkRetryOrAbandon`'s doc comment
says an abandoned row keeps its last error, and the package comment explains
that an `abandoned` row **is** the diagnostic. That reasoning is sound for a
terminal failure. It does not extend to a success — a delivered message's
last-failed-attempt text is history, and history that is indistinguishable
from a live fault is worse than no history.

## Acceptance criteria

1. `MarkSent` clears `error` in the same `UPDATE` that sets `status='sent'`,
   `ses_message_id`, `sent_at`, and blanks `payload`. One statement, not a
   follow-up write — a row must never be observable as sent-with-error.
2. `abandoned` rows still retain their error. `MarkRetryOrAbandon` is
   unchanged, and a test asserts an abandoned row's error survives.
3. A `queued` row awaiting retry still retains the error from its most recent
   failed attempt — that is the case the column exists for.
4. A DB-backed test in `internal/outbox` covers the transition directly: fail a
   row (error populated), then succeed it, then assert `error IS NULL` while
   `ses_message_id` and `sent_at` are set.
5. The two production rows are corrected as part of resolving this, or the
   resolution explicitly records that they were left as historical artefacts.
   Do not leave that decision implicit.

## Decision on criterion 5 (the two production rows)

**Deferred, recorded explicitly rather than left implicit.** This subagent
runs locally against a per-issue test database — it cannot reach and must
not try to reach the production Postgres instance on the EC2 box
(`CLAUDE.md` §7). The two rows (`outbound_queue` ids 1 and 2, both
`status='sent'` with a stale `AccessDeniedException` in `error`) are **left
uncorrected in production** by this resolution. They are historical
artefacts of a since-corrected IAM policy, not evidence of a live fault —
`status='sent'` is already the authoritative signal — so leaving them as-is
is safe; the only cost is the same diagnostic confusion this issue exists to
prevent going forward, and it does not reoccur once `MarkSent` is deployed.

The SQL a human with production access should run once this deploys:

```sql
UPDATE outbound_queue
   SET error = NULL
 WHERE id IN (1, 2)
   AND status = 'sent';
```

(Scoped to `id IN (1, 2)` deliberately, not `WHERE status = 'sent' AND error
IS NOT NULL` — the latter would also touch any other `sent` row with a
stale error that exists by the time this runs, which is out of scope for a
one-off correction of the two rows this issue names. The `AND status =
'sent'` guard is redundant given the `id IN (...)` but kept so the statement
can never touch a row that isn't already `sent`.)

### One follow-up for the orchestrator to file — not a defect in this change

`Store.MarkDone` (added by `#0254` for `KindSubscribeIntake`, called from
`internal/handlers/subscribe.go:571`) also transitions a row to
`status='sent'` — from `queued` **or** `sending` — and blanks `payload`, but
does **not** clear `error`. This issue's stated invariant ("a row must never be
observable as sent-with-error") therefore holds on the `MarkSent` path and not
on the `MarkDone` path. It is reachable: the recovery poller can claim an
intake row, fail it via `MarkRetryOrAbandon` (error written, status back to
`queued`), and the original request's fast path then calls `MarkDone` on that
`queued` row — the two paths converging is explicitly anticipated by
`subscribe.go`'s own comment. Not a bounce, because criterion 1 names
`MarkSent` specifically; the fix is the same one-line `error = NULL`.
