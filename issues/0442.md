## Description

`TestRender_StaticRoutesGetDistinctTitles` in `internal/seo` measures exactly
what its name says: that the six static routes' titles are **distinct**. It does
not measure that any of them is **non-empty**.

Measured by `#0437`'s reviewer as an extra probe: setting `/archive`'s `Title`
to `""` in `defaultStaticRouteMeta`, leaving `OGURL` correct, **passes**. The
same mutation on `/about` passes identically — so this is route-agnostic and
pre-existing, not something `#0437` introduced.

Distinctness is not non-emptiness. One empty string is still distinct from five
non-empty ones.

## Why it is worth closing

A missing `<title>` is not a cosmetic defect on a marketing site. It is the
single strongest on-page signal a search engine reads, and the whole point of
`internal/seo` is that these six pages carry correct metadata. The subsystem's
one test named for titles would not notice.

Related and already understood: the same test detects a **missing route entry**
only through its `og:url` assertion, not its title assertion, because a route
that falls back still gets a distinct-enough title. `#0437`'s review examined
that and ruled it correct behaviour — the assertion that fires is the one whose
property actually broke. This issue is the *other* half: the property "every
static route has a real title" is asserted nowhere at all.

## Acceptance criteria

1. Every static route's rendered `<title>` is asserted **non-empty**.
2. It is also asserted to **differ from the fallback route's title** — an empty
   title and a silently-inherited fallback title are the same class of defect,
   and the distinctness assertion catches neither.
3. Prove it by mutation: empty one route's `Title`, confirm the test now fails
   naming that route, restore, and prove the restore with `shasum -a 256`. Do
   this on a copy or in a throwaway worktree — **never `git stash`** (`CLAUDE.md`
   §8a).
4. **No new mechanism.** `#0437`'s criterion 5 forbade one for that issue and
   the same reasoning applies here: this is one or two added assertions inside
   an existing test, not a new derived check. If you find yourself writing a
   third guard, stop and say why in the work log.
5. Consider whether the test's **name** should change. It currently promises
   less than it will then deliver, and `#0437`'s review found the misleading
   name was itself part of why the gap went unseen.
