## Description

`TestRender_StaticRoutesGetDistinctTitles` in `internal/seo` measures exactly
what its name says: that the six static routes' titles are **distinct**. It does
not measure that any of them is **non-empty**.

Measured by `#0437`'s reviewer as an extra probe: setting `/archive`'s `Title`
to `""` in `defaultStaticRouteMeta`, leaving `OGURL` correct, **passes**. The
same mutation on `/about` passes identically — so this is route-agnostic and
pre-existing, not something `#0437` introduced.

Distinctness is not non-emptiness. One empty string is still distinct from five
non-empty ones.

## Why it is worth closing

A missing `<title>` is not a cosmetic defect on a marketing site. It is the
single strongest on-page signal a search engine reads, and the whole point of
`internal/seo` is that these six pages carry correct metadata. The subsystem's
one test named for titles would not notice.

Related and already understood: the same test detects a **missing route entry**
only through its `og:url` assertion, not its title assertion, because a route
that falls back still gets a distinct-enough title. `#0437`'s review examined
that and ruled it correct behaviour — the assertion that fires is the one whose
property actually broke. This issue is the *other* half: the property "every
static route has a real title" is asserted nowhere at all.

## Acceptance criteria

1. Every static route's rendered `<title>` is asserted **non-empty**.
2. It is also asserted to **differ from the fallback route's title** — an empty
   title and a silently-inherited fallback title are the same class of defect,
   and the distinctness assertion catches neither.
3. Prove it by mutation: empty one route's `Title`, confirm the test now fails
   naming that route, restore, and prove the restore with `shasum -a 256`. Do
   this on a copy or in a throwaway worktree — **never `git stash`** (`CLAUDE.md`
   §8a).
4. **No new mechanism.** `#0437`'s criterion 5 forbade one for that issue and
   the same reasoning applies here: this is one or two added assertions inside
   an existing test, not a new derived check. If you find yourself writing a
   third guard, stop and say why in the work log.
5. Consider whether the test's **name** should change. It currently promises
   less than it will then deliver, and `#0437`'s review found the misleading
   name was itself part of why the gap went unseen.

## Root cause

`TestRender_StaticRoutesGetDistinctTitles`' loop over the six static paths
only ever populated a `map[string]bool` keyed by title and checked for a
collision. An empty string is a valid, distinct map key exactly like any
other — `titles[""] = true` does not error, and `len(titles) ==
len(paths)` holds whether the sixth title is `"Archive — Open Circuit SF"`
or `""`, as long as no other route already produced `""`. Distinctness and
non-emptiness are genuinely different properties and the test only checked
the first. The same blind spot covers a title that silently equals the
shared fallback bucket's title (`r.fallback.Title`, `"Open Circuit SF"`):
that string doesn't collide with any of the six real titles today, so it
would pass the map check too.

## Fix

Added two assertions inside the existing per-path loop in
`TestRender_StaticRoutesGetDistinctNonEmptyTitles` (renamed, see below),
immediately before the pre-existing distinctness check:

```go
if title == "" {
    t.Errorf("path %q produced an empty title", p)
}
if title == r.fallback.Title {
    t.Errorf("path %q produced the shared fallback's title (%q) instead of its own -- a static route silently inheriting the fallback bucket is the same class of defect as a missing route entry", p, title)
}
```

Both are ordinary comparisons in the loop already iterating every path — no
new derived check, no new fixture table, no new file. That satisfies
criterion 4: this is the "one or two added assertions inside an existing
test" the issue asked for, not a third guard.

**Criterion 2, the fallback half:** `r.fallback` is the `*Renderer`'s
unexported field holding `defaultFallbackMeta`'s output; the test file is in
`package seo` (not `seo_test`), so it reads `r.fallback.Title` directly with
no new accessor needed.

**Criterion 5, the rename:** renamed
`TestRender_StaticRoutesGetDistinctTitles` →
`TestRender_StaticRoutesGetDistinctNonEmptyTitles`. The old name promised
only distinctness, which is exactly the gap `#0437`'s reviewer found had let
this go unnoticed. Checked before renaming: the only two occurrences of the
old name anywhere under `internal/`, `cmd/`, or `web/` were the function
definition itself and its own doc comment (`grep -rn
"StaticRoutesGetDistinctTitles" internal cmd web` — one file, two lines), so
the rename leaves no dangling citation for
`internal/handlers`'s `TestNoCommentCitesUndefinedTestFunction` to catch.
The doc comment now says "Renamed from
TestRender_StaticRoutesGetDistinctTitles by #0442" — that phrasing's
"renamed from" prefix is the existing, already-reviewed discount
`citationIsExcluded` uses for exactly this shape (see
`internal/handlers/dangling_test_citation_guard_test.go`'s
`nonTestIdentifierAllowlist`/`citationIsExcluded` comments and
`templates_test.go`'s prior real instance), so it does not itself become a
dangling citation.

Older resolved issues (`#0070`, `#0425`, `#0437`) still cite the old name in
their own historical `## Verification`/review text. Left untouched
deliberately: `TestNoOpenIssueVerificationCitesUndefinedTestFunction` (the
guard that checks issue-file test citations) only scans `open`/`in-progress`
issues, and all three are `resolved`/`closed`, so nothing there needs
correcting and nothing there is checked.

### The rename's citation safety — proved, not assumed

The implementer's claim rests on a discount in
`internal/handlers/dangling_test_citation_guard_test.go`: `citationIsExcluded`
treats a case-insensitive "renamed from" appearing in the twenty characters
immediately before a cited name as a note about a retired name rather than a
live citation, and the joined multi-line text it reads means a wrapped comment
does not hide the phrase. The doc comment's "Renamed from" sits immediately
before the retired name on the same physical line, so the rule applies.

That the guard passes *for this reason* was proved rather than inferred: in the
same worktree the phrase was replaced with a non-discounted word,
`TestNoCommentCitesUndefinedTestFunction` failed naming the retired identifier
in `internal/seo/seo_test.go`, and it passed again on restore. The discount is
real, it applies here, and it is load-bearing.

The second half of the claim also checks out.
`TestNoOpenIssueVerificationCitesUndefinedTestFunction` filters issue files on
their `**Status**` row to `open`/`in-progress` only, so the three resolved
issues still naming the retired identifier are genuinely out of scope. Read
alongside `issueCitationSectionHeaders`, which admits the evidence-asserting
sections and deliberately excludes `## Description`, `## Fix`, `## Root cause`
and `## Files changed`, this issue file's own uses of the retired name in those
sections are out of scope too — confirmed by running that guard against the
tree, which passes.
