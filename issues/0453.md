## Description

    PRICE=cost$(FOO)

loads as `cost)` under `godotenv` and stays literal under systemd's
`EnvironmentFile=`. Neither `#0441`'s original `$VAR` pattern nor `#0450`'s
widened one flags it.

**The cause is a bug in the library, and it is worth understanding before
fixing anything.** `expandVariables` tests `submatch[2] == "("` to detect the
`$(…)` form — but in `expandVarRegex`, group 2 is the **dollar** capture and the
paren is group 3. That branch is therefore unreachable, so `$(FOO` falls through
to ordinary variable expansion and is read as a variable named `FOO`. The
trailing `)` survives, which is why the result is `cost)` rather than `cost`.

Measured by `#0450`'s reviewer, probing `godotenv.Unmarshal` directly rather
than reasoning from the pattern.

## Why it was reported rather than folded into `#0450`

`#0450`'s criteria authorised **one character class** — matching the guard to
what `expandVarRegex` matches. Catching this needs `\(?` admitted into the
pattern, which is a **second judgement call**, and `CLAUDE.md` §8 records
`#0258` buying a bounce per mechanism added past the stated criteria.

It is also pre-existing: `#0450` neither introduced nor worsened it.

## Why it is worth closing

`.env.example` is copied verbatim onto production as
`/etc/opencircuit/config.env` (`#0423`), so both parsers read the same file. A
value silently losing text under one and keeping it under the other is the
**silently-wrong-value** half of this bug class, which is harder to notice than
a boot failure — the service starts, and something downstream is subtly wrong.

## Root cause

`envDollarExpansion`'s pattern started matching only at `\$\{?` — the dollar
followed directly by an optional open brace. A value with a literal `(`
between the dollar and the name (the `$(FOO)` shape) has no `{` there at all,
so the guard's own regex never engaged; the value-shape scan simply never
looked at that text. This is independent of, and does not fix, the library's
own bug — it is the guard's blind spot to a form the library mishandles.

The library's own bug (confirmed by reading `parser.go`, not by guessing):
`expandVariables` decides whether a match is the parenthesized `$(…)` form —
which it is meant to leave alone — by testing `submatch[2] == "("`. But
`expandVarRegex`'s own group numbering makes group 2 the **dollar** capture
(always literally `"$"`) and group 3 the paren capture. `submatch[2]` can
never equal `"("`, so that branch is dead code, and `$(FOO` falls through to
the ordinary name-substitution branch: it reads `FOO` as a variable name
(substituting its value, or the empty string if undefined) and leaves any
trailing `)` untouched — which is why `cost$(FOO)` loads as `cost)`.

## Fix

Widened `envDollarExpansion` to admit an optional literal `(` between the
dollar and the optional brace, mirroring `expandVarRegex`'s own structure
exactly (an optional backslash, the dollar, an optional paren, an optional
brace, the name class, an optional close brace) rather than inventing a
parallel shape. **This is judged an extension of the existing `$VAR`/`${VAR}`
shape, not a fifth shape** (criterion 4): it is the identical
"godotenv-expands-this, systemd-doesn't" divergence family that
`#0441`/`#0450` already built, admitting one more optional character into the
same character-class-and-structure story #0450 already widened once. The
four-shape structure named in criterion 3 is untouched — this still lives
inside the single `if` block that already existed for dollar expansion, not a
new branch in `scanEnvExampleValueShapes`.

The violation message for a match containing `(` is worded separately from
the plain `$VAR`/`${VAR}` case, because the fact is more surprising than an
ordinary "this gets expanded" warning and calls for a different fix: this
form is not a documented feature being misused, it is a library bug, and the
message says so plainly and tells the operator to remove the syntax rather
than to define the variable it appears to reference.

### The library bug is real, and the root-cause reading is exactly right

Read from the module source, located with `go list -m -f '{{.Dir}}'
github.com/joho/godotenv` and never a filesystem scan (`CLAUDE.md` §5). In
v1.5.1 `expandVarRegex` is `` (\\)?(\$)(\()?\{?([A-Z0-9_]+)?\}? ``, so group 1
is the backslash, group 2 the **dollar**, group 3 the **paren**, group 4 the
name. `expandVariables` branches on `submatch[1] == "\\" || submatch[2] == "("`.
Group 2 is a non-optional capture of a literal `$`, so it can never equal `(`:
the paren-detection branch is unreachable dead code, exactly as the issue and
the implementer's `## Root cause` state. The one-line upstream fix really is
`submatch[3]`.

### Runtime probe, re-derived independently

Probed `godotenv.Unmarshal` directly, in a throwaway module outside this repo
against the real v1.5.1 dependency. **Every row of the implementer's table
reproduced exactly**, including the two claimed non-divergences — the rows a
wrong reading would have silently narrowed the guard with:

| value | godotenv loads | diverges? | guard matches |
|---|---|---|---|
| `cost$(FOO)` | `cost)` | **yes** | yes |
| `cost$(FOO` | `cost` | **yes** | yes |
| `cost$(FOO}` | `cost` | **yes** | yes |
| `cost$(FOO})` | `cost)` | **yes** | yes |
| `cost$(5)` | `cost)` | **yes** | yes |
| `cost${FOO)` | `cost)` | **yes** | yes (already caught pre-fix) |
| `cost$()` | `cost$()` | **no** | **no** |
| `cost$((FOO))` | `cost$((FOO))` | **no** | **no** |
| `cost$({FOO}` | `cost` | **yes** | yes |
| `a$(B)c$(D)e` | `a)c)e` | **yes** | yes |

and `FOO=bar` followed by `PRICE=cost$(FOO)` loads as `costbar)`, confirming the
fallback substitutes a defined value rather than always the empty string.

Both claimed non-divergences hold **for the stated reason**: the name group
matches empty — `$()` has no name characters, and `$((FOO))`'s second `(` is not
one — so `expandVariables` hands the text back unchanged. The widened pattern's
**required** `[A-Z0-9_]+` is precisely what keeps the guard silent on them. That
narrowing relative to godotenv's *optional* name group is load-bearing, not
incidental, and it is the reason the widening does not overreach.

### The independently-optional paren is fidelity, and no false positive exists

`\(?` and `\{?` are separately optional, so `$({FOO}` and `$(FOO}` now match.
`#0450`'s review settled the analogous brace question by observing that
godotenv's own regex has the same independently-optional structure. **The
argument holds for the paren for the same reason, and here it is confirmed
empirically rather than by symmetry**: the probe shows `cost$({FOO}` really does
load as `cost`, a genuine divergence that a paren-balanced pattern would miss.

The false-positive question is the one that matters, since `.env.example` is
copied verbatim onto production. I brute-forced it rather than reasoning about
it: **111,110 generated values** over the alphabet `$ ( ) { } A 5 _ \ x` up to
length five, each run through `godotenv.Unmarshal` and compared against
systemd's literal-text reading. The widened guard flagged **14,637** of them and
produced **zero false positives** — not one value where the guard fires and the
two parsers actually agree.

That result is structural rather than lucky. The widened pattern is
`expandVarRegex` minus the optional backslash, with the name group made
required, so every guard match is also a godotenv match with a non-empty name
group — which is exactly the condition under which `expandVariables`
substitutes. And the tracked `.env.example`, read as bytes with `python3` (never
BSD `grep -P`, §8), holds **zero** `$` and **zero** `\` characters across its 20
assignment lines, so the widening cannot flag anything in the file as it ships.

### Extension, not a fifth shape — agreed, and criterion 3 nearly forces it

Concur with the implementer. A fifth *shape* would mean a fifth `if` branch in
`scanEnvExampleValueShapes` and a fifth row in the per-shape table — the exact
structure criterion 3 forbids touching. More substantively, `$(FOO)` is not a
distinct divergence: it is the same detector, the same "godotenv expands,
systemd doesn't" mechanism, and the same remedy family as `$VAR`/`${VAR}`,
reaching the identical substitution path through the identical library regex.
Treating it as its own shape would misdescribe the mechanism.

The message split earns its place. An operator reading the plain `$VAR` wording
would conclude "define the variable, or escape the dollar" — advice that is
wrong for `$(...)`, because the form is not a documented feature at all. The new
wording says so plainly: that it looks like a no-op and is not, that the cause
is a bug in a named library function, and that the fix is to remove the syntax
rather than define anything. That is the surprising fact the issue asked to be
stated plainly, and it is stated rather than buried — the two wordings are
mutually exclusive per violation, so an operator only ever sees the one that
applies to their line.

One imprecision, noted and not a defect: the message says godotenv reads "the
text after `(`" as a variable name, which for `$({FOO}` is `{FOO}` rather than
the name `FOO`. The offending value is quoted verbatim in the same message, so
nobody is misled about which line to fix.

**1. The widening has no committed regression pin.** Reverting `\(?` from the

the real-file test passes because `.env.example` has no `$`, and the per-shape

for any of them, while the per-shape table's own doc comment describes itself as

**2. A whole uncaught divergence family: the backslash escape.** The same

returns the remainder, so `PRICE=cost\$FOO` loads as `cost$FOO` while systemd
keeps `cost\$FOO` literally. This is distinct from the existing
trailing-backslash *continuation* shape, which only inspects a backslash at end
of value. It is pre-existing, invisible to the pre-fix pattern too, and squarely
outside this issue's criteria — but it is the largest remaining hole in the
scan, and the same "copied verbatim onto production" argument applies to it.
