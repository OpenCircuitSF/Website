## Root cause

Follow-ups, not a single defect. `outbox.Store.Counts` counted every kind, so abandoned `outreach_post` rows lit the mail warning. Mastodon's `Idempotency-Key` lasts about an hour, so a late retry after an unknown outcome could post twice. `CountCharacters` counted trailing punctuation inside a URL. `thumbnail` read before checking size. Whitespace-only credentials were treated as unset without a log line.

## Fix

- `Counts` takes `WHERE kind <> 'outreach_post'`; the dashboard's queue depth and `outbound_queue_abandoned` both come from it, so social posts are excluded rather than relabelled.
- `mastodon.Client.FindRecentStatusWithURL` (verify_credentials, then the account's last 40 statuses) matches the short link as a whole token. `Publisher.postMastodon` calls it only when a prior attempt may have succeeded: this row was claimed before (`Attempts > 1`), or `outbox.Store.HasPriorAttempt(kind, recipient, excludeID)` finds an earlier `outbound_queue` row for the same post with `attempts > 0` (a manual Retry after a final failure; `QueueNow` clears `last_error`, so the history comes from the queue, not the post). Any earlier claim triggers the look, permanent-classified ones included. If the history query or the lookup fails the row retries; it never posts blind.
- `mastodon.trimLinkEnd` mirrors the Bluesky helper and `CountCharacters` uses it.
- `thumbnail` stats (regular file, size 1..limit) before `ReadFile`.
- `warnPartialPostingCredentials` compares trimmed values and warns that a variable is set but whitespace only, naming the variable, never a value.

## Review notes

2026-10-16, Opus review of `f897e50`: **bounced**, for one design defect in criterion 2. Everything else checks out.

**What is wrong.** The second trigger in `priorAttemptUnknown`, which looks for the transient marker text in `job.LastError`, never fires in production. `Store.QueueNow` (`internal/outreach/publish_store.go`) is the path a manual Retry takes, and it runs `SET status = 'queued', ... last_error = NULL` before it enqueues the new `outbound_queue` row. `Schedule` clears `last_error` the same way. The publisher reloads the job from the database when it claims the row, so by then `LastError` is always nil, and the new row's first claim has `Attempts == 1`. So a manual Retry after a final transient failure, which is the case the Fix section says is covered, posts blind with an Idempotency-Key the instance has probably forgotten by then. That case is also the likeliest to happen more than an hour later. The test never reaches this branch: `TestPublisher_MastodonRetryAdoptsStatusWhenInstanceForgotKey` only covers the `Attempts > 1` path inside a single queue row. Matching on message text was also fragile in its own right, since the producer strings in `postFailed` are separate literals that are not tied to the constant.

**The remedy (transcription, so Sonnet can do it):**

1. In `internal/outbox/store.go`, add `HasPriorAttempt(ctx, kind Kind, recipient string, excludeID int64) (bool, error)`:
   `SELECT EXISTS (SELECT 1 FROM outbound_queue WHERE kind = $1 AND recipient = $2 AND id <> $3 AND attempts > 0)`. Nothing deletes `outbound_queue` rows, so the history is still there. Add it to the publisher's outbox interface and to any fakes.
2. In `internal/outreach/publisher.go`, change `priorAttemptUnknown` to `row.Attempts > 1 || HasPriorAttempt(KindOutreachPost, row.Recipient, row.ID)`. If the query fails, treat the attempt like a failed lookup: `postFailed` with `permanent=false`, so it is never posted blind. Delete `unknownOutcomeMarker` and the `LastError` check. Any earlier claimed row triggers the look, including a permanent-classified one. A permanent classification can be wrong after a write that actually happened, and the look costs two GETs.
3. Test it through the real store: seed, `QueueNow`, run one pass against `forgetfulMasto` (the POST creates the status and answers 503), force the row to abandon (for example `maxRetries` 1 through `fakeSettings`, or a direct `UPDATE outbound_queue SET status='abandoned'`), call `s.QueueNow` again as the manual Retry, run one pass, and assert `postCount() == 1` and that the post adopts status `900`. Keep the existing first-attempt test, since it proves a fresh post never looks first.
4. Correct the Fix section bullet that describes the marker.
